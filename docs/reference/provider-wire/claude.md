The Claude Code changelog **carries no dates** — entries are numbered by version only, so a behavior's first version is pinned by **version anchor** (the release it first appears in), never by date. Release cadence is why this file names the build each fact was read at: four builds (`2.1.284` to `2.1.287`) landed on the authoring machine between September 28 and October 1, and at this pin's authoring the npm dist-tags were `stable` = `2.1.285`, `latest` = `2.1.287`, `next` = `2.1.288` — so `stable`, `latest` and `next` are **not** the same channel, and a doc that says "current" without saying which tag has said nothing.

**Census scope caveat — which artifact was read.** `@anthropic-ai/claude-code` on npm is a **wrapper**: it ships `cli-wrapper.cjs` plus an `install.cjs` postinstall, and the executable itself arrives as a platform-specific optional dependency (`@anthropic-ai/claude-code-<platform>-<arch>`). Installed with build scripts blocked, the wrapper refuses outright — "claude native binary not installed" — so there is no JavaScript-only channel to census. What this file reads is therefore the **native single-file build**, which embeds the JS bundle; the local census target and the platform package's `claude` binary are the same artifact class and byte size. Two consequences: a literal's presence in this census is evidence about the native build (the only one there is), and any CI job that wants to reproduce it must let the postinstall run — an `--ignore-scripts` install yields a wrapper that cannot even report its version. Where a substituted native implementation could differ (bundled search/glob tooling, for instance), a census result is evidence about tooling names, not about protocol shapes.

## The `--help` is non-authoritative rule

Unlike Codex (whose binary emits its own schema), Claude Code has no generated protocol dump, and its `--help` under-reports the surface. The CLI reference states this outright — quoted verbatim (Verified, Official docs, 2026-10-02):

> `claude --help` does not list every flag, so a flag's absence from `--help` does not mean it is unavailable.

**Consequence for this file:** the pinned binary governs, `--help` is a lower bound, and the docs census is the cross-check. Hidden-but-documented flags (`--permission-prompt-tool`, `--max-turns`, and others below) are normal, not deprecations. Re-verified at this pin: `--permission-prompt-tool`, `--max-turns`, `--resume-session-at` and `--rewind-files` have no entry of their own in `2.1.287 --help`, as in `2.1.251 --help` (`--permission-prompt-tool` is named only inside the `--permission-prompts` description), and all four are present in both binaries.

**And the lower bound moves in both directions — `--session-id` surfaced in `--help` at `2.1.251`.** At `2.1.245` it was one of this rule's worked examples; at `2.1.251` and `2.1.287` `--help` lists it outright (`--session-id <uuid>`), so it is not among the example set above. Nothing about the flag changed; what changed is what `--help` chooses to print. A consumer must therefore not read a flag's arrival in `--help` as the flag's introduction, any more than it reads absence as unavailability.

**And the rule's converse, which matters just as much.** A string in the binary is **not** evidence a flag or subtype is available. `--enable-auto-mode` is documented as removed in `2.1.111` and still appears in the `2.1.287` census — three times, against twice at `2.1.251` and four times at `2.1.245`, which is drift in the bundle rather than in the flag's status — dead strings survive bundling. Every claim below therefore says which kind of evidence it rests on: registry membership, a dispatcher arm, an exit-code probe, or vendor prose. Presence alone is never promoted to availability.

## Control protocol and result surface

Everything below is reproduced from the pinned binary, and each subsection states its own evidence kind.

### Control-request registry (binary census)

At `2.1.245` the control-request subtype registry is directly observable in the binary as a set of schema constructors. Each subtype below appears **exactly once** in that census (**Binary probe** provenance, **Verified** trust at `2.1.245`). The constructor pattern of §Version pin's Census method row, run over `2.1.251` and `2.1.287`, finds a constructor for every subtype below at both builds, each once except `can_use_tool` (twice at `2.1.251`, three times at `2.1.287`) and `request_user_dialog` (once, then twice), so presence is **Verified** at both builds and the exactly-once arity stays a `2.1.245` reading. That pattern is broader than the `2.1.245` registry extraction: it matches every schema `subtype` constructor, stream messages included — 98 distinct names at `2.1.251` and 151 at `2.1.287`, none dropped between them:

`interrupt`, `set_permission_mode`, `can_use_tool`, `set_model`, `get_usage`, `get_context_usage`, `get_session_cost`, `list_models`, `get_binary_version`, `apply_flag_settings`, `rewind_files`, `hook_callback`, `elicitation`, `request_user_dialog`, `mcp_message`.

Counterexample hunt, run against the same census so the set above is not read as more than it is: the bare tokens `set_effort`, `rewind`, and `compact` are **absent** as control-request subtypes (count 0 at `2.1.245`, and again at `2.1.251` and `2.1.287` under the re-run constructor pattern) — so the registry is not simply "every control verb one might expect". It is a statement about the schema-constructor census, not about the binary's strings: `rewind` and `compact` do occur as quoted literals in every one of those builds.

**The conversation cut is `rewind_conversation`, and a zero count on `rewind` said nothing about it.** The subtype this project's undo drives is `rewind_conversation {target_message_uuid, last_seen_user_message_uuid, interrupt_if_running}`, a different name from the `rewind` token the counterexample above counted; it is **not** part of the `2.1.245` census listed here, the re-run constructor pattern finds no constructor for it at `2.1.251` or `2.1.287` although it is a literal at both, and it was measured on the builds below, each recorded at its own build:

- **At `2.1.276`**, three runs of three: `interrupt_if_running: true` ended a turn that was still live, the cut landed on the session the process was already running, the two running child agents were killed about four milliseconds after the request with their progress markers frozen there, and a later message to either came back refused as stopped by the user and not resumed.
- **At `2.1.280`**: without `last_seen_user_message_uuid`, a cut past a later prompt is refused `stale_target`, compaction or not; set but older than a later prompt, it is refused `unseen_later_turn`; so the daemon sets it to the newest prompt sent. The full refusal set read from the build is `commands_queued`, `prompt_pending`, `turn_running`, `target_not_found`, `stale_target`, `unseen_later_turn`, `poll_tool_result_target`, `target_splits_tool_call`, `delivered_poll_events_in_range`, `persist_failed` and `state_changed`; all eleven are literals at `2.1.287`, and the first nine are absent from `2.1.251`.
- **A refusal is not an error frame.** It arrives as a control response of `subtype: "success"` carrying `{rewound: false, error, reason}`, so a consumer reads `rewound`, never the subtype. An accepted cut answers `{rewound: true, targetMessageUuid, prefillText, precedingAssistantUuid}`, `prefillText` being the text of the message cut.
- **At `2.1.282`, the compaction boundary**: a point after the last compaction is accepted live and kept by a plain `--resume` restart after either kind of compaction. After an **automatic** compaction a point before it is refused `target_not_found` (two of two) and no fork point is named; after `/compact` a point before it is accepted live but is lost on restart, because the loader rebuilds the session from the last `compact_boundary` in file order.

[Spec-003 §Driver-Level Rollback Mechanics](../../specs/003-queue-steer-pause-resume.md#driver-level-rollback-mechanics) binds the Claude leg to these facts. The pairing with `--replay-user-messages` is why the message identifiers the request names appear on the wire at all.

**A point before the last compaction is reached by a copy, and a restart on it** (**Binary probe**, **Verified at `2.1.282`**, with `@anthropic-ai/claude-agent-sdk` `0.3.282`). The daemon stops the process with SIGTERM, never by closing its input, which would let Claude Code finish the running turn and answer every queued prompt into the conversation being undone. It calls the Agent SDK's `forkSession(sessionId, {upToMessageId, title})` with the id of the last assistant message before the undo point and the session's own title (without a title the copy is named `<first prompt> (fork)`), and restarts the headless CLI on the copy (`--resume <fork id>`); the restarted process sent the model the kept history with no summary, and the cut held after one more turn and a second restart. Four facts shape it:

- **The fork point comes from the daemon's own record of the stream.** A stream frame's `uuid` is the session file's entry `uuid`, and the SDK's `getSessionMessages` skips everything before the last compaction in a session file over 5 MiB, so the SDK's own message list cannot supply it.
- **Ids are mapped through each row's `forkedFrom`.** `forkSession` also copies an earlier undo's dead branch into the fork, rows Claude Code never loads, so the daemon never takes the fork's row list as the conversation.
- **Prompts not yet taken up are the daemon's to keep.** A prompt the stream has not replayed as a user message is held by Claude Code only as a `queue-operation` row, which the fork does not carry; the daemon keeps each such prompt, and every prompt sent while the process is down, and writes them to the new process as soon as it is spawned.
- **The SDK's per-platform binary is not installed.** `forkSession` needs none of it (8 to 13 ms a fork with no binary on disk); one line in the workspace file, `ignoredOptionalDependencies: ["@anthropic-ai/claude-agent-sdk-*"]`, keeps out a second copy of Claude Code (about 222 MB on an Apple-silicon Mac, 239 MB on Linux x64, 242 MB on Windows x64), and the SDK takes its newest release, like every dependency. The `fork_conversation` control request needs a remote-control server and answers `{forked: false, error: "unsupported", reason: "unsupported"}` headless.

On a 5.6 MiB session file with an automatic compaction the fork took 25 ms and restarts on it kept the cut; a prompt queued at the stop was answered on the forked history once written at spawn; a fork of a file already branched by an earlier undo took 10 ms and kept both cuts. Each stays an acceptance check of the build that lands it.

**Registry membership is not availability.** The dispatcher answers an unsupported subtype with a typed refusal rather than silence. Quoted verbatim from the `2.1.287` dispatcher arm for `get_usage`:

> get_usage is not supported in this context

emitted as `{ type: "control_response", response: { subtype: "error", request_id, error } }`. At `2.1.245` and `2.1.251` the same arm appends `(onGetUsage callback not registered)`, so a consumer classifies the `error` subtype and never matches the text. A sibling arm shows the same shape for `get_context_usage`. Separately, a **cloud-hosted-session** gate rejects `rewind_files` outright and constrains `apply_flag_settings` ("apply_flag_settings keys not available in a cloud-hosted session: …"). So a driver must treat every control request as **feature-detected at call time**: send it, and classify the typed `control_response` error, rather than deciding availability from a version number.

**And the census is a lower bound, not an upper one** (**Binary probe**, **Verified** at `2.1.234`, `2.1.245`, `2.1.246` and `2.1.287`). The rule above says a censused subtype may still refuse. The converse is also true and is the sharper trap: a subtype **absent** from the census above may still answer. `mcp_set_servers` — the live server-set reconcile the SDK exposes as `setMcpServers` — appears in none of the first three builds' censused subtype registries, and at all four it answers `{"subtype":"success","response":{"added":[],"removed":[],"errors":{}}}` over `-p --input-format stream-json` with no user message sent and no billed turn. Each probe was run beside a negative control (`zzq_nonexistent_subtype`, refused every time with the typed `Unsupported control request subtype: …`), so the successes are not an artifact of a dispatcher that accepts anything. The desired set sent was **empty**, so what is Verified here is that the subtype dispatches and returns the documented reconcile envelope; a non-empty mutation is outside this probe's reach and is measured by the consumer that performs one. The constructor pattern re-run at this pin does find a constructor for `mcp_set_servers` at `2.1.251` and `2.1.287`, because it reads every schema `subtype` rather than one registry; the lesson is about what a given census instrument can see, not about this one subtype. Two consequences: this file's registry list is evidence about what the census could see, never a completeness claim; and neither presence nor absence in it may decide a capability — only the probe's own classified answer may.

**`file_suggestions` answers a file search** (**Binary probe**, **Verified at `2.1.283`**, recorded at its own build on the [`rewind_conversation` precedent](#control-request-registry-binary-census); at `2.1.287` a first query answered `success` with an empty list, the index case below). It is not in the census listed above, and over `-p --input-format stream-json` with no user message sent the request `{subtype: "file_suggestions", query}` answers `{suggestions: [{path}], cwd}`: paths only, such as `docs/specs/001-session-core.md`, with no score and no match positions, at most 15 rows, and a folder can be a row of its own, its path ending in `/`. The first query in a fresh process can come back empty while the process is still building its file index; the same query answers once the index is built.

#### Direction: some censused subtypes are refused BY NAME on the inbound channel

The rules above cover a censused subtype refusing for CONTEXT and an uncensused one answering anyway. There is a third case, and it is the one that breaks a probe (**Binary probe**, **Verified** at `2.1.251` and `2.1.287`): a censused subtype can be refused **by name**, with the identical typed refusal the negative control draws.

Measured over `-p --input-format stream-json`, one subtype per process, no user message sent and no billed turn, each run beside the `zzq_nonexistent_subtype` negative control:

| Subtype sent INBOUND (daemon → CLI) | Answer |
| --- | --- |
| `can_use_tool`, `elicitation`, `request_user_dialog` | `Unsupported control request subtype: <name>` — the negative control's own refusal, differing only in the name |
| `get_binary_version`, `get_usage`, `get_context_usage`, `get_session_cost`, `list_models`, `mcp_set_servers` | `{"subtype":"success", …}` |

The three refused names are exactly the ones the CLI **raises** — they are its outbound questions to a host, and the permission prompt among them is what `--permission-prompt-tool` plumbs. So the registry census spans **both directions** of the channel, while the inbound dispatcher carries only one of them.

The consequence is sharper than the lower-bound rule above, and it is the one a capability probe must be built around: a name-level refusal is evidence about the **inbound dispatcher**, never about the capability. Probing `can_use_tool` inbound and reading its refusal as absence would withdraw a feature every one of these builds fully carries. A consumer probing this channel must first establish that the subtype it is probing is one the daemon **sends**.

The same three probes give the in-band **version** channel: `get_binary_version` returns `{ version, buildTime }` for the build that is actually running (`2.1.234` → `2026-08-17T01:20:38Z`, `2.1.245` → `2026-08-25T04:00:18Z`, `2.1.246` → `2026-08-25T18:33:51Z`, `2.1.287` → `2026-10-01T16:02:06Z`). That is what a driver should read, because `claude --version` reports the launcher's current build — the same divergence recorded in §Version pin above, where the census target and `claude --version` came apart mid-pass.

`can_use_tool` remains the `--permission-prompt-tool` plumbing (`{tool_name, input}` → `{behavior: allow | deny, updatedInput?, message?}`); the census confirms a `{behavior: "cancelled"}` response arm alongside those.

**An unanswered `can_use_tool` is held without a ceiling** (**Binary probe**, **Verified at `2.1.278`**, carried from [Spec-010 §Required Behavior](../../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior) rather than re-measured here). The CLI held one unanswered permission request on its stream-json control channel for 900 seconds in one run and 1,500 seconds in another, sending no cancel frame either time; the answer was accepted at 904 and 1,504 seconds and the tool then ran. The ceiling a consumer must design around sits on the neighboring surface instead: an unanswered `hook_callback` is canceled by this command-line tool at 600 seconds unless the matcher registered for it carries a `timeout` of its own, and the canceled call is reported to the model as a tool that did not run.

#### A refused turn that names a fallback model asks the host

**Binary probe**, **Verified at `2.1.282`**, recorded at its own build on the [`rewind_conversation` precedent](#control-request-registry-binary-census), read from the build's own schema definitions, their descriptions and the code that raises and settles the dialog. No dialog was observed live.

`request_user_dialog` is one of Claude Code's outbound questions to a host: `{subtype: "request_user_dialog", dialog_kind, payload, tool_use_id?}`, answered by a control response carrying `{behavior: "completed" | "cancelled", result?}`, "Response from the SDK consumer for a request_user_dialog request."

- **Claude Code sends a dialog only for a kind the host declares.** The host lists the kinds it can draw in `initialize.supportedDialogKinds`: "The CLI treats ABSENCE as 'cannot display' and fails closed: without the kind declared here, a dialog-gated flow degrades to its no-dialog behavior (for 'refusal_fallback_prompt', the classic refusal error) instead of parking a dialog the consumer may mishandle. First-attached-client-wins on multi-client sessions; later initializes do not change it." And of `dialog_kind`: "A kind is only sent in sessions where some attached client declared it in initialize.supportedDialogKinds (declare exactly the kinds you can render)". A host "that receives a kind it did not declare must not answer it (an error-subtype response is discarded and the dialog stays pending) — never with {behavior: "cancelled"}, which is a real settlement treated as the user dismissing the dialog."
- **The daemon declares two kinds: `refusal_fallback_prompt`**, whose choice the build describes as "choose: retry on fallback model or edit prompt", **and `fable_overage_consent_prompt`** ([A Fable turn that needs usage credits asks the host](#a-fable-turn-that-needs-usage-credits-asks-the-host)). The build's two other kinds, `auto_mode_server_fallback` and `auto_mode_outside_reads`, are not declared. Declaring `auto_mode_outside_reads` would change nothing (**Binary probe**, **Verified at `2.1.292`**): Claude Code offers it only in an interactive session, never under `-p`, and in auto mode a `-p` session read a file outside its working folders at once, with no `can_use_tool` and no `request_user_dialog` to anyone.
- **`refusal_fallback_prompt`** asks, when the model refuses and a fallback model is named, whether to retry on that model or edit the message. Its payload is `originalModel`, `fallbackModel`, `apiRefusalCategory` (nullable, optional), `guidanceText` (optional) and `retractedMessageUuids` (optional): "Wire uuids of the already-streamed messages this refusal concerns. Evict on RESOLUTION (your own response — any choice — or control_cancel_request retirement), never on receipt; a turn torn down mid-dialog keeps the partials. Eviction is idempotent." Its answers are `retry_fallback`, `edit_prompt` and `cancelled`, and its default is `cancelled`. After `edit_prompt` Claude Code aborts the turn (the abort reason `refusal-fallback-edit`); after `cancelled`, on a turn not aborted, it ends the turn with its plain refusal.
- **Claude Code settles a waiting choice itself.** In a headless session it answers a waiting `refusal_fallback_prompt` `cancelled` when a new user message arrives (`new_user_message`), and also on a message from another session (`uds_message`) and a scheduled wake (`cron_fire`), and tells the host with `control_cancel_request {request_id}`. It does the same at its dialog deadline: "An unanswered dialog is cancelled by the CLI after its dialog deadline." The deadline is `CLAUDE_CODE_USER_DIALOG_TIMEOUT_MS` when set, otherwise the `dialogExpiry` setting (`60s`, `5m`, `10m` or `never`, "Defaults to 5m to match the long-standing remote-dialog deadline; "never" disables the deadline"), otherwise 300,000 ms.
- **The daemon turns the deadline off and answers for the person's own moves.** It spawns Claude Code with `CLAUDE_CODE_USER_DIALOG_TIMEOUT_MS=0`; the headless dialog path arms its deadline only when that figure is above zero (every site that arms a deadline from it checks the figure is above zero; re-read at `2.1.292`, where the value is parsed as a whole integer, so `0` stays `0` and a value with a unit suffix such as `5m` falls back to `dialogExpiry`), so a waiting choice waits on the person. An interrupt while the choice waits is sent as the dialog's answer `cancelled`, never as a turn teardown, because Claude Code removes the retracted messages on "your own response — any choice" while "a turn torn down mid-dialog keeps the partials". A message the person sends while the choice waits is held by the daemon, which answers `cancelled` first and then sends the message as the next turn, as Claude Code's own `new_user_message` rule does. A `control_cancel_request` for the held request, which Claude Code sends when it settles the choice itself, is recorded as `cancelled`.

#### A Fable turn that needs usage credits asks the host

**Binary probe**, **Verified at `2.1.282` and `2.1.285`**, recorded at its own build on the [`rewind_conversation` precedent](#control-request-registry-binary-census), read from each build's `fable_overage_consent_prompt` definition, the gate that raises it before a Fable request, the code that settles each answer and the `model_consent_fallback` schema. No dialog was observed live.

- **When it is asked.** Before a main turn on a model whose id starts `claude-fable-` is sent, on a first-party Pro, Max or Team sign-in once Fable needs usage credits and before consent was given with credits on, and only when the host declared the kind. Enterprise is a credits-only tier and is never asked. Compaction has its own copy of the gate and, when it applies, runs on a model that is not Fable without asking.
- **Payload and answers.** The payload is `overagesEnabled`, `modelName` (optional; the name Claude Code uses in its credit messages, such as "Fable 5"), `balanceCents` (nullable, optional) and `currency` (nullable, optional). The answers are `consent`, `switch_default` and `cancelled`, and the default is `cancelled`.
- **How each answer settles.** `switch_default` moves the session to the first of Opus, Sonnet and Haiku that is not Fable and is allowed; it rewrites the saved default model in Claude Code's user settings only when that default is Fable and the process has neither `ANTHROPIC_MODEL` nor a model of its own, so a process started with `--model` never rewrites it. `consent` stores a per-organization consent in Claude Code's own config and keeps the turn on Fable only when usage credits are then actually on; otherwise Claude Code switches models anyway, with `choice: "consent"`, because it never turns billing on from a host's answer. A host's `cancelled` is read as the person dismissing the dialog and switches the session off Fable. An abort of the turn while it waits ends the turn interrupted, with no switch. A message queued while it waits makes Claude Code settle the dialog itself, with no switch, and end the turn with an error whose `apiError` is `consent_unanswered`.
- **Undeclared, there is no switch.** The turn is sent on Fable, the API refuses it with a 429 carrying `error_code: "credits_required"`, Claude Code turns that into an assistant error with `api_error: "model_requires_usage_credits"`, and every later Fable turn fails the same way. Whether Claude Code retries that 429 before the turn fails is not settled from the build and needs a live call.
- **What the daemon does.** It declares the kind, maps the dialog to `run.usage_credits_choice_requested`, and answers `switch_default` or `consent` as the person chooses. An interrupt or an undo while the choice waits goes as the turn's own interrupt, never as `cancelled`. A message sent while it waits goes to Claude Code, and its own settlement is recorded as `unanswered`. The switch that follows is the `model_consent_fallback` frame below, and the settlement is `run.usage_credits_choice_resolved` ([Spec-005 §Run Lifecycle](../../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)).

#### What the daemon sends to a process it starts, and what it reads back

**Binary probe**, **Verified at `2.1.278` through `2.1.283`**, each fact at the build its measurement ran on; recorded at its own build on the [`rewind_conversation` precedent](#control-request-registry-binary-census).

- **Thinking.** `set_max_thinking_tokens {thinking_display: "summarized"}`, with no budget key, at every start and after every model change: without it a headless session's thinking blocks arrive with no text, and the `showThinkingSummaries` setting does not change that. `summarized` is the fullest display; the others are `highlights` (one short title per stretch of thinking) and `omitted`. The API returns summaries, never the model's own reasoning; whether the model thinks, and how much, stays with the model and the session's effort. The daemon keeps every reasoning text whole, one longer than an entry holds (16,384 characters) kept as consecutive entries and read back as one.
- **Models.** `set_model` sends a 1-token model check for an id that is not a built-in alias. The figures of models the session is not on are read at creation in one short control-only process on the same account home and base URL (about 5 s), with the window key removed.
- **Context figures.** `get_context_usage` answers the window (`maxTokens`), the compaction point (`autoCompactThreshold`), the per-category start and `autocompactSource`, with no turn, but it makes token-counting calls of its own: about 23 a read (six reads made 139). A proxy changes the figures, so each is read under the session's own base URL.
- **The compaction knob.** `apply_flag_settings {env}` sets `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` at spawn and mid-session, from the next turn. The window key carries every point from 67,000 tokens up and its point is read back from `get_context_usage`; Claude Code raises the window key to at least 100,000, so below 67,000 only the percentage key reaches, and no request reports that key's point. `autoCompactWindow` is never the knob, and `autoCompactEnabled: false` is never sent: with it Claude Code never compacts and an over-long prompt fails every later turn. Only changed keys are sent, a removed bound is sent as an empty string, and a value is checked before it is sent, because Claude Code accepts a bad value as success and drops the bound. While a key is set, `get_context_usage` reports the key's window, percentage and free space in place of the model's.
- **Figures no request reports.** The reply reserve and constant come from two `get_context_usage` reads in the creation-time control process, with `apply_flag_settings {env}` between them setting the window key and then a `CLAUDE_CODE_MAX_OUTPUT_TOKENS` value, once per model, both keys removed afterwards so no session's reply is capped (the constant read 13,000 on every build measured). Style descriptions come from `/output-style` with no argument in that same process, one line per style, `- <name>[ (current)]: <description>`, split on the names `initialize.available_output_styles` gave so a colon inside a description never misleads it; a build that stops listing the command is a version fault. Upstream request: [anthropics/claude-code#97568](https://github.com/anthropics/claude-code/issues/97568), for `get_context_usage` to report the percentage key's point.
- **Output style.** Style names come from `initialize.available_output_styles` at every start and from `reload_output_styles` when styles are reloaded; under a relocated config home the output-styles folder moves into that home. The daemon answers the composer's `/output-style` itself with `apply_flag_settings {outputStyle}` for that session alone and never sends the word as typed, because Claude Code's own command writes the project's `.claude/settings.local.json`.
- **Advisor.** A session holds its own advisor, `off` or a model, taken from the app's default when the session is created; the app keeps that default in its own settings file and never writes Claude Code's, and a later change to it never reaches an existing session. Every process the daemon starts for the session (its lead after a restart, a resume or a provider switch, and a Claude Code helper the bridge starts) carries the value at launch in `--settings {advisorModel}`, and Claude Code's own helpers follow it. The daemon answers the composer's `/advisor <model>` and `/advisor off` itself with `apply_flag_settings {advisorModel}` for that session alone and never sends the word as typed, because Claude Code's own command saves the choice machine-wide; `/advisor` with no model names the session's advisor and the choices. Claude Code's reply line is shown as sent: on a model that takes tool changes mid-conversation, on and off apply at once and a different advisor model waits for the next compaction; on another model every change waits for it.
- **Output speed.** `apply_flag_settings {fastMode}` between turns applies from the next run, with no restart and no file written; a typed `/fast` declines under `-p`, so the daemon applies it itself ([Output speed](#output-speed--fast_mode_state-is-this-providers-positive-case)).
- **Tool servers.** A session's servers are set with `mcp_set_servers` at start and sent again after each resume; a server switched off mid-session is another `mcp_set_servers` call, from the next turn. `mcp_toggle` is never used, because it saves "off" for the whole project.
- **Agents.** Saved agents ride `initialize.agents`, because plugin agents drop `hooks`, `mcpServers` and `permissionMode`; a saved agent reaches a live session by a resume at its next idle moment.
- **Steering a helper** (**Binary probe**, **Verified at `2.1.286`**, September 30, for the post-tool hook). The daemon's `PostToolUse` hook returns the person's words as `additionalContext`, aimed at a helper by `agent_id`, so the steer lands at the helper's next tool call; a steer that arrives as the helper finishes goes as `SubagentStop`'s continuation.
- **What names a helper on the stream** (**Binary probe**, **Verified at `2.1.292`**, one Haiku 4.5 session asked for a helper at effort `low`). The Agent call's input carries `effort` when the person asked for one, `low`, `medium`, `high`, `xhigh` or `max`, and the tool's own description tells the model to set it only when asked. `task_started` carries the helper's `task_id`, a `run_id` and `spawn_depth: 1`; the helper's prompt frame (a `user` frame with `parent_tool_use_id`) carries `agent_id`, equal to that `task_id`. `run_id` was on `task_started`, `task_updated`, `task_notification` and the entries of `background_tasks_changed`, and on no message frame. `parent_task_id` was absent, which the build's description gives as the case of a helper the main thread launched; for a nested task it names the helper that launched it (read from the build). The helper's own reply did not arrive as a frame, so whether a helper's `assistant` frame carries `agent_id` was not seen. The Agent SDK's changelog says, for `0.3.292` (Claude Code `2.1.292`), that every `assistant` and `user` message a helper produces carries `agent_id`, which stays the same when the helper is resumed, and that a task notification carries `origin.runId`; for `0.3.293` (Claude Code `2.1.293`) it adds an optional `subagent_type` to each `background_tasks_changed` entry, so a host names a helper's type without pairing it with `task_started` (**Official docs**, **Documented**).
- **Helpers at once.** Claude Code `2.1.286` has no setting for how many helpers run at once. For a number above zero the daemon's `PreToolUse` hook on the Agent tool holds a new helper's start until one of that session's running helpers finishes; empty is no limit, and `0` withholds the helper tool.
- **Approval rules** (**Binary probe**, **Verified at `2.1.286`**). The approval card's rules are Claude Code's own, and the daemon keeps no rule store. A session's allow and deny lists are the flag settings of its process: as the card is answered the daemon sends `apply_flag_settings {permissions}` carrying the whole allow and deny lists on each call (the card's session rules, the memory-folder allows passed at `Sandboxed` and the protected-path denies), and at Reviewed the ask list `["Bash(rm *)"]` beside them, and every process the session starts carries them at launch in `--settings`. `apply_flag_settings` merges its patch into the flag-settings layer, where `--settings` lands, one top-level key at a time: the patch is spread over the layer and a key set to `null` is removed (read from the build at `2.1.292` and `2.1.293`; its schema says "Merges the provided settings into the flag settings layer"), so a `permissions` key replaces the whole `permissions` object, and one sent without `ask` drops the ask rule; a grant, a revoke and a host block (a `WebFetch(domain:<host>)` deny, which the sandbox honors) each apply from the next call. A project allow rides the `can_use_tool` answer as a rule with `destination: "localSettings"`, so Claude Code writes it to the project's `.claude/settings.local.json`; a decline drops any rule it carries, so the daemon writes a project block's `WebFetch(domain:<host>)` deny into that file itself; a rule added to or removed from that file applies from the next call. `list_permission_rules` lists the rules in force, each with its source, which the inspector's `Rules` reads.
- **Skills and plugins.** `reload_plugins` reloads a live process's skills, commands and plugins in about 0.1 s and answers the fresh lists (**Binary probe**, **Verified at `2.1.270`**); `reload_agents` is refused as an unsupported subtype. Neither `reload_plugins` nor a second `initialize` changes the agents the process was started with, which is why a saved agent waits for the resume above (**Binary probe**, **Verified at `2.1.282`**).
- **Commits.** `attribution.commit` is left at its default, so Claude Code writes its own `Co-Authored-By` trailer naming the session's model on an agent's commits; the daemon adds no co-author trailer of its own.
- **The staged review.** `/review` of staged changes runs as a one-turn process on the session's account and model in a temporary worktree holding only the staged changes, removed afterwards (measured: five of five reviewed only the staged file; about 0.8 s to create and 0.4 s to remove the worktree on 5,000 files; $0.02 to $0.05 a review).

#### `get_usage` is EXPERIMENTAL — three separate facts, do not collapse them

**(1) The control request itself is experimental.** Its own schema description, verbatim from the `2.1.245` census and present unchanged at `2.1.287`:

> Requests the structured /usage data: session cost/usage totals plus claude.ai plan rate-limit utilization when available. Experimental — the response shape may change.

The hedge is the vendor's and is preserved as written. **Trust: Provisional**, on Verified presence — the subtype is in the registry, its shape is disclaimed by the vendor, and its dispatcher can refuse at runtime. Never assume it; probe it and handle the typed refusal. At `2.1.287` the request takes an optional boolean `skip_behaviors` (any other type is refused with `get_usage: skip_behaviors must be a boolean`), and the reply carries a `behaviors` member beside `rate_limits`: per day and per week, a request count, a session count, and the share of usage by behavior, agent, skill, plugin and tool server.

**(2) `rate_limits_available` is a field _inside_ the response, and it means something else.** It is not a feature-detect for whether the request exists. Verbatim from the same census:

> False when plan rate limits do not apply (API key, Bedrock, Vertex, or missing profile scope) — rate_limits will be null.

It sits beside `subscription_type` ("Claude.ai subscription type ('pro', 'max', 'team', 'enterprise') or null for API key / 3P provider sessions") and `rate_limits`, whose members in the `2.1.287` reply include the windows `five_hour`, `seven_day`, `seven_day_oauth_apps`, `seven_day_opus` and `seven_day_sonnet`, the `limits[]` array and `model_scoped` list of fact (3), and `extra_usage`, `spend` and `seven_day_breakdown`, beside further undocumented keys a consumer ignores.

**(3) The flat per-model keys are present in the binary and answer `null`; the per-model window arrives in `limits[]`.** Measured at `2.1.278` by sending the control request over `--input-format stream-json` before any user turn, recorded at its own build on the `rewind_conversation` precedent above, and read again at `2.1.287` on 2026-10-02 with the same shape: the request answers in about three seconds with `total_cost_usd: 0` and an empty model-usage map — **no model call** — and `rate_limits_available: true`. `five_hour` and `seven_day` carry a utilization and a reset time; `seven_day_opus` and `seven_day_sonnet` come back **`null`**. The per-model window is in a **`limits[]`** array instead, each entry carrying its own kind, its group, its percentage, its reset time and a `scope` naming the model by **display name**, and again in a `model_scoped` list. **Binary probe, Verified at `2.1.278` and `2.1.287`** — a different instrument from the string census above, which establishes that the flat keys **exist** and by construction cannot establish whether they are **populated**; whether the null reading holds at `2.1.251` was not measured. A consumer reads `limits[]`; a consumer keyed on the flat names renders an empty per-model window for an account with real per-model usage. The same read is available as rendered text by sending `/usage` as the prompt, which is likewise zero model turns (§Client-side command interception on the programmatic input surface) and is not needed while the structured reply answers.

**(4) The same request sent the instant a turn's `result` lands answers on the same process, spends nothing, and now carries the session's own spend** (**Binary probe**, **Verified at `2.1.278`**). Sent over `--input-format stream-json` right after the first `result` frame, `get_usage` answered in about 2.6 s with the keyed windows, a per-model row, and `session.total_cost_usd`, which the read before any turn had reported as zero; no turn and no cost were added, and the `init` frame is re-emitted per turn rather than once per process.

**(5) The pre-turn read can come back empty while the flag says limits apply, and that is the endpoint refusing it** (**Binary probe**, **Verified at `2.1.278`**, 2026-09-22). Sent before any turn in a fresh config home and in the default home, `get_usage` answered `rate_limits_available: true` with `rate_limits: null` for about an hour, then answered the figures again with nothing changed on the caller's side, and the process's own debug log showed the cause of the empty answers: `fetchUtilization: GET /api/oauth/usage` answered `200` and the binary logged the body as fieldless, an in-band refusal it reports to the control response only as `null`. In the binary the read is answered by a collector that fetches the account's usage endpoint when the login is a claude.ai subscription with the profile scope, answers from a fresh snapshot when one is held, and after a turn seeds that snapshot from the response headers, which is why the post-turn answer carries the two windows in the event's shape without `limits[]`. `/usage` sent as the prompt headless answers locally with `num_turns: 0` and fills nothing. A consumer treats `null` beside `true` as a refused read to retry on a ladder, keeps the last turn-delivered figures, and never draws it as zero.

**(6) Under a `claude setup-token` login the read never answers, before or after a turn** (**Binary probe**, **Verified at `2.1.278`**, 2026-09-22). In a fresh config dir holding only `CLAUDE_CODE_OAUTH_TOKEN` (`auth status` reports `authMethod: oauth_token`), `get_usage` answered `subscription_type: null`, `rate_limits_available: false`, `rate_limits: null` before any turn, again in the same process right after a haiku turn, and again in a fresh process; the turn's own `rate_limit_event` carried both `unifiedWindows` with the account's real figures. The turn's response headers do not seed a snapshot under a token. So `rate_limits_available: false` is the login saying it has no read, and `true` beside `rate_limits: null` (fact 5) is the endpoint refusing a login that has one; a driver treats them as two states.

So the correct driver logic is two-stage: **first** discover whether `get_usage` answers at all (typed refusal or not), **then** read `rate_limits_available` to learn whether plan limits are even a concept for this session, and only then read `rate_limits`. Treating a `null` `rate_limits` as a failure would misreport every API-key session.

**The `skills` row is weaker evidence than its neighbors, and is marked so deliberately.** `fast_mode_state`, `fast_mode_disabled_reason`, and `terminal_slash_commands` are distinctive snake_case wire members — a hit is almost certainly the member. `skills` is an ordinary English word inside a 217 MB build that also ships skill-plugin machinery, tool descriptions, and prose; its bare-word count of 59 is dominated by matches that have nothing to do with the handshake. **Leg 2 — the shapes, the vocabularies, and the invocability distinction. Cross-reference provenance, Derived trust.** Everything in the `Shape` and `Notes` columns comes from the shipped driver's `packages/runtime-daemon/src/provider/driver/claude/session/transport.ts#ClaudeHandshakeDeclaration`, which records these members as read from a live frame. **This pass observed no handshake frame.** No captured `system/init` fixture exists in the repository either — the files under the [driver fixtures](#driver-fixtures) path are the control-request census, the stream-surface census, and the turn-evidence transcripts, none of which carries a handshake. A string census proves a member name is *in the build*; it cannot prove the member is *emitted*, what type it carries, or what its values mean. Those claims are therefore **Derived**, and the [no-authless-probe gap](#gaps-recorded) applies to this family in full — the declaring handshake rides a turn-bearing exchange, so reaching a real one on this provider costs credentials and a billed turn.

**Two structural facts, because this is where the surface differs from the Codex one.** Neither is a defect; they are why a cross-provider normalization cannot be symmetric:

- **This enumeration publishes no scope and no enabled/disabled distinction.** There is no analog of the Codex `SkillScope` (`user | repo | system | admin`) or of its required `enabled` boolean — see [`skills/*`](codex.md#skills--the-skill-surface). Names arrive as bare strings. A normalized cross-provider entry therefore has to type both axes optional even though Codex never omits either.
- **`terminal_slash_commands` is published under its own member and is not the same set.** The provider itself separates them, and a consumer that unions the two members offers, over the programmatic surface, commands that are not invocable there. The dispatch guard is built from `slash_commands` alone; the three sets are carried separately rather than merged or dropped.

**It is a live read held as driver-session state, never a stored registry — and it is refreshed, not pinned.** The handshake is the only place these names arrive and there is no enumeration RPC to re-read them from, but the held copy is **not** fixed at establishment. Per `packages/runtime-daemon/src/provider/driver/claude/lifecycle.ts#ClaudeSessionLifecycle`, the driver keeps one entry per session and **re-records it wholesale on every handshake-bearing frame**: the inbound-frame router calls the observer whenever a frame carries a declaration, and the observer unconditionally overwrites the stored declaration together with its derived invocable-name set. The semantics are therefore **last-declaration-wins**, and because a `system/init` handshake rides each turn-bearing exchange, the held enumeration tracks the newest declaration rather than the first.

Three consequences worth stating, since they follow from that and not from the wire:

- **A refreshed declaration is visible to the next read, not to a cached one.** The normalized entry list is composed at read time from the stored raw declaration, so a later handshake changes what a subsequent read returns — the held state is what the provider most recently said.
- **Re-recording is scoped to the session's own thread.** The observer is reached only where the frame carries no subagent identity, so a child's handshake never overwrites the parent binding's enumeration.
- **A provider-session rotation invalidates rather than staleness-serves.** The held entry is keyed by the provider session id it was observed under, and a read whose current provider session does not match it returns nothing instead of the previous session's palette; the entry is dropped outright on teardown.

Nothing in the payload identifies its own origin, which is why a normalized entry has to carry the `(driverName, providerAccountId)` it was read under rather than deriving it later.

#### Output speed — `fast_mode_state` is this provider's positive case

Claude publishes a declared output-speed state with a settable level vocabulary. Codex carries the axis as `/fast`, `fast_mode`, `serviceTier` and a `Fast` tier per model — see [Output speed — a service-tier surface with no method-level axis](codex.md#output-speed--a-service-tier-surface-with-no-method-level-axis). [Spec-004 §The output-speed axis](../../specs/004-provider-driver-contract-and-capabilities.md#the-output-speed-axis) declares the axis for both drivers. The two providers express it in structurally different shapes: a declared state with a settable level vocabulary here, a per-turn service-tier override there. On this provider a level is set with `apply_flag_settings {fastMode}` between turns, from the next run, with no restart and no file written; a typed `/fast` declines under `-p`, so the daemon applies it itself. Before the opt-in, `initialize`, the start frame and the result report fast mode as `off` with `sdk_opt_in_required`, and the catalog's `supportsFastMode` says which models have it.

**Literal presence: Binary probe, Verified at `2.1.287` and `2.1.251`**, censused 2026-10-02 — counts in the census table above, plus `supportsFastMode` (3 string-lines at `2.1.287`, 4 at `2.1.251`) as a per-model axis on the catalog read, `true` at `2.1.287` on `claude-opus-5-5`, `claude-opus-5` and `claude-opus-4-8`.

**The state vocabulary, and its deliberate asymmetry: Cross-reference, Derived.** Per the shipped normalizer in the same `lifecycle.ts`, the pinned provider **reports** three states — `on`, `cooldown`, `off` — while the **settable** vocabulary the driver publishes as `outputSpeedLevels` is two: `off` and `on`. The person may not *request* a cooldown, but the provider may certainly *report* one. The two sets are different sizes on purpose, and a consumer that treats the reported vocabulary as the settable one constructs a request the provider has no way to honor. A driver whose provider publishes no per-model set declares its settable levels in one place, its descriptor's `outputSpeedLevels` — Claude's in `packages/runtime-daemon/src/provider/driver/claude/descriptor.ts#CLAUDE_DRIVER_DESCRIPTOR` as `["off", "on"]`; Codex's are read per model from its catalog.

**Detection is `probed`, and the declared state is the truth.** The `initialize` reply reports `fast_mode_state` and `fast_mode_disabled_reason` before any turn — `off` with `sdk_opt_in_required` before the opt-in, measured on `2.1.280` on 2026-09-23 — so the axis is read zero-turn on the spawn the driver makes anyway, and the **declared state** is taken as the fact, never the request's acceptance.

**Verbatim is not unbounded, and a rejected reading is absent.** The declared value is carried verbatim, but it is parsed through a strict shape whose checks range over **length, emptiness, and NUL — never over membership in any vocabulary**. That is precisely what lets `cooldown`, and any level a later build invents, pass through untouched instead of being coerced into the settable set. A reading that fails those bounds becomes **absent — not degraded and not raw** — because the absent answer already has a meaning every reader handles, and inventing a placeholder would put a state the provider is not in on the person's screen. The accompanying `output_speed_state_rejected` diagnostic carries the failing field and the offending **lengths only, never the values**, since those are the untrusted strings the parse just refused.

`fast_mode_disabled_reason` is present only where the provider supplies one; its absence means the provider gave none, never that there was none.

### Result and stream surface

**Result census** (Binary probe, Verified at `2.1.245`; every subtype and the quoted prose present at `2.1.287`). Result subtypes `success | error_max_turns | error_max_budget_usd | error_during_execution | error_max_structured_output_retries`; the `result` field is present only on `success`; trailing events (e.g. `prompt_suggestion`) can arrive **after** `result`, so the driver read-loop reads to EOF rather than breaking on `result`. The structured-output failure carries its own prose: `error_max_structured_output_retries` fires when "the cloud agent called StructuredOutput but no attempt produced a surviving valid output".

**Mid-session retry taxonomy** (Binary probe, Verified at `2.1.245`; every distinctive literal named here present at `2.1.287`). The emitted shape is `{ type: "system", subtype: "api_retry", attempt, max_retries, retry_delay_ms, error_status, error }` — note `error_status` alongside the typed `error`, and that the mapping arm is `system/api_error` → `system/api_retry`. The typed error members `authentication_failed`, `oauth_org_not_allowed`, `billing_error`, `rate_limit`, `overloaded`, `invalid_request`, `model_not_found`, `server_error`, `max_output_tokens`, `unknown` are present as literals; the union's exact arity is **Derived**, since a string census cannot prove a set is closed.

**Compaction and a turn too long to fit** (**Binary probe**, **Verified** on a September 2026 build, below this file's pin). A compaction Claude Code attempts and fails arrives as `compact_result: "failed"`; Claude Code tries again at the next turn. A turn that cannot fit even after compaction ends in a `result` with `is_error` and `terminal_reason` `prompt_too_long` or `blocking_limit`, and is cut with `rewind_conversation` and handed back as a failed send. The refill breaker is read from `is_error` with `terminal_reason: "rapid_refill_breaker"`, never from `subtype`, which reads `success`.

**Cost** (**Binary probe**, **Verified at `2.1.282`**). Each assistant message's `usage` and the per-model `costUSD` arrive with a `costBasis`; where it reads `list` or `managed`, Claude Code's own `costUSD` is the figure, and where it reads `unknown` the daemon prices the message from its `usage` at the rates of its live copy of LiteLLM's MIT-licensed price list, matched by exact model id, once, at completion. `total_cost_usd` on a persisted session's `result` frames is cumulative for the session ([A reply comes back when the message asks for one, and the transcript pairs it to its prompt](#a-reply-comes-back-when-the-message-asks-for-one-and-the-transcript-pairs-it-to-its-prompt)).

**An advisor call** is an ordinary tool call whose verb is `advisor`, its target the advisor's model by display name, live while the advisor works, with its duration. Its output line is Claude Code's own, `Advisor has reviewed the conversation and will apply the feedback`. A readable result (`advisor_result`, from an older advisor) carries the advice, which the row holds folded under that line; a sealed result (`advisor_redacted_result`, from every advisor that pairs with Opus 5 and 5.5, Sonnet 5.5, Fable and Mythos) carries none, so its row has nothing to open. A refusal reads `Advisor declined to advise on this request`, with the provider's explanation under it when one is sent; an error reads `Advisor unavailable · <the reason in words>`, never the wire's code. The advisor's spend is priced at its own model, as its own entry in `result.modelUsage`, and counted in the account's row in Cost. The advisor's thinking is never sent on any model, and the agent is not asked to repeat the advice.

**Adjacent stream subtypes present at the pin** (Binary probe, Verified): `rate_limit_event`, `compact_boundary`, `command_lifecycle`, `queued_notification`, and the model-refusal pair `model_refusal_fallback` / `model_refusal_no_fallback`. `rate_limit_event` matters to the daemon's rate-limit readings, and its role is narrower than a push channel that could stand in for a read. **Its documented shape carries no window identifier at all** — a status, an optional reset time, an optional utilization and three credits members, and nothing saying which window the utilization belongs to. A reading keyed on `(account, limit identifier)` therefore cannot be fed from it, so the event is a **hint that something moved**, and the keyed readings come from `get_usage`, whose reply names each window. Treat an arriving event as a reason to take a reading, never as the reading. **Re-read in the `2.1.278` binary (Binary probe, 2026-09-22):** the event's `rate_limit_info` now carries `rateLimitType` (`five_hour`, `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `seven_day_overage_included`, `overage`) and an optional `unifiedWindows` member with `five_hour`, `seven_day` and `seven_day_overage_included` each holding `utilization` and `resetsAt`, filled from the `anthropic-ratelimit-unified-5h-utilization` / `-5h-reset` / `-7d-utilization` / `-7d-reset` response headers on every API answer. At that build an event does name its windows, and a session's own turns carry the account's limits without the profile scope `get_usage` needs, so the daemon takes the keyed windows from every turn's event. Its scheduled read of every account, every five minutes, is a fresh short-lived reader on the account's own home sending `get_usage`, one reader at a time; the read after a turn goes to that reader too, never to the session's process. Under a `claude setup-token` login, whose read never answers (fact 6 above), the scheduled read is one minimal turn on the smallest model, whose `rate_limit_event` carries the windows (395 input and 51 output tokens measured, about $0.00065 a read), and that cost counts in the account's spend.

**A model switch and a refusal** (**Binary probe**, **Verified at `2.1.282`**, read from the build's own schema definitions and their descriptions; no frame was observed live). Four `system` subtypes report a turn that moved off its model, or a refusal no other model took. All four have a schema constructor at `2.1.251` and `2.1.287`. The build's stream-json output writes all four, although the descriptions of `model_fallback` and `model_consent_fallback` mark them `@internal` and "Not yet in the public SDKMessage union".

- `model_refusal_fallback`: the model ended the stream with `stop_reason` `"refusal"` and the turn is retried once on a fallback model. It carries `trigger: "refusal"`; `direction`, of which `retry` is emitted while `revert` and `sticky` remain in the enum for older consumers; `scope`, `session` when the session's model is swapped and `local` when only a subagent's, a side question's or a background fork's response came from the fallback model (absent from older builds, read as `session`); `original_model`; `fallback_model`; `request_id`; `api_refusal_category`, an open string such as `cyber` or `bio`, or null; `api_refusal_explanation`, the refused response's own explanation, "display only, never parse"; `retracted_message_uuids`, the messages the retry withdrew, removed on receipt; `refused_user_message_uuid`; and `content`.
- `model_fallback`: the turn moved to the configured fallback model because the primary failed, with `trigger` one of `model_not_found`, `permission_denied`, `overloaded`, `server_error`, `last_resort` and `model_blocked`, and `original_model`, `fallback_model` and `content`. It holds for that turn: the primary is tried again on the next one.
- `model_consent_fallback`: a consent gate before sending moved the session off the requested model because usage credits were declined or not provisioned, with `choice` (`consent`, `switch_default` or `cancelled`), `original_model`, an optional `original_model_name`, `fallback_model`, `persisted_as_default` (true when the saved default model was rewritten too) and `content`. It holds for the rest of the session.
- `model_refusal_no_fallback`: the model refused and no retry runs, because no fallback model is configured or the refusal category's routing declined it, with `original_model`, `request_id`, `api_refusal_category`, `api_refusal_explanation`, `refused_user_message_uuid` and `content`. At the two sites the build raises it, `content` is an empty string.

The daemon maps the first three to a model switch, `usage.model_rerouted`, and `model_refusal_no_fallback` to a refused turn, `run.failed` with `failureCategory: 'refused'`. `model_refusal_fallback` keeps its own `scope` (`local` stays `local`, absent reads `session`) with cause `safety`; `model_fallback` is scope `turn`, cause `model_blocked` for its `model_blocked` trigger and `model_unavailable` for every other; `model_consent_fallback` is scope `session`, cause `out_of_credits`. `original_model` and `fallback_model` become `fromModel` and `toModel` (the refusal's `failureCause.model` is `original_model`), `content` becomes `sentence` when it is not empty, `api_refusal_explanation` becomes `explanation`, and `api_refusal_category` becomes `safetyCategory` ([Spec-005 §Usage Telemetry](../../specs/005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). A refusal that names a fallback model asks the host first, through the `refusal_fallback_prompt` dialog the daemon declares ([A refused turn that names a fallback model asks the host](#a-refused-turn-that-names-a-fallback-model-asks-the-host)), and the daemon maps that dialog to `run.refusal_choice_requested` and its answer to `run.refusal_choice_resolved` ([Spec-005 §Run Lifecycle](../../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)). A Fable turn that needs usage credits asks the host before it is sent, through the `fable_overage_consent_prompt` dialog the daemon declares ([A Fable turn that needs usage credits asks the host](#a-fable-turn-that-needs-usage-credits-asks-the-host)), and `model_consent_fallback` is the switch that follows.

#### A conversation file resumes inside a different, signed-out config home

**Binary probe, Verified at `2.1.278`**, recorded at its own build on the [`rewind_conversation` precedent](#control-request-registry-binary-census); one live run on this machine. A session's own transcript lives at `<config dir>/projects/<project folder>/<session id>.jsonl`. Copied — that one file, nothing else — into a **fresh, signed-out** `CLAUDE_CONFIG_DIR` under `projects/<the same folder name>/`, it is **found and loaded** by `claude --resume <session id>` launched against that home: the result frame carries the original `session_id`, the earlier turn's per-model usage and cost, `num_turns: 0`, and the provider's own context report reads the resumed conversation back. The negative control is what makes the result mean something — a made-up session id against the same home answers `No conversation found with session ID: …` and exits 1, so the load is the file's and not an artifact of a permissive resume.

**What is not established.** A model **turn** on the resumed conversation under the second home's *own* login was not run, because the probe's second home had no login, so this grades the discovery-and-load leg only.

### Client-side command interception on the programmatic input surface

**A message whose first non-whitespace byte is `/` is consumed by the CLI's own command layer and never reaches the model** (**Binary probe**, **Verified** at `2.1.251` by live `claude -p --output-format stream-json` runs against the on-disk build). This is the behavior [Spec-004](../../specs/004-provider-driver-contract-and-capabilities.md) records at `2.1.245`, reproduced unchanged at `2.1.251` — so it is a standing property of this input surface, not a single-build regression. The runs are billed turns and were not repeated at `2.1.287`, where the `<local-command-stdout>` wrapper and the `Unknown command:` text below are both still literals.

The trap is that the interception is **not an error**. The stream carries a well-formed `result` frame with `subtype: "success"` and `is_error: false`, so every layer above reads a completed turn while the person's words were never sent.

**Turn-evidence discriminants on the `result` frame**, measured in one pass — three runs, same build, same model, same session shape, differing only in the message body:

| `result` field | first word command-shaped | same text, one leading newline | ordinary prose |
| --- | --- | --- | --- |
| `num_turns` | `0` | `1` | `1` |
| `duration_api_ms` | `0` | `2473` | `2972` |
| `total_cost_usd` | `0` | `0.66676` | `0.67144` |
| `modelUsage` | `{}` (empty object) | one model key | one model key |
| `is_error` | `false` | `true` (that turn hit an unrelated provider-side refusal) | `false` |

Read the table for what it settles and, more importantly, for what it does not:

- **Positive turn evidence is what discriminates.** `num_turns > 0`, a non-empty `modelUsage`, a non-zero `duration_api_ms`, and a non-zero `total_cost_usd` move together on a real turn and are all zero-valued on an intercepted one. A consumer deciding whether a message reached the model reads these.
- **`is_error` does not discriminate, and neither does the assistant frame's model marker.** The intercepted run reported `is_error: false`; the neutralized run reported `is_error: true` because that particular turn hit a provider-side refusal. And the assistant message's `message.model` reads `<synthetic>` on **both** the intercepted run and a genuine turn that ends in an API error — so `<synthetic>` is evidence of a locally-composed frame, never evidence that no turn occurred. This is the sharp trap: the most obvious single field is the wrong one.
- **Corroborating markers, deliberately not decision inputs.** The intercepted turn additionally carries `is_meta: true` on its user frame and renders the CLI's own output inside a `<local-command-stdout>…</local-command-stdout>` wrapper (observed verbatim: `<local-command-stdout>Unknown command: /zzqnotarealcommand</local-command-stdout>`). Both are strong markers and are recorded here because they are real. Neither is a safe basis for a runtime check: the set of shapes a client-side command layer can emit is open, so a consumer that recognizes **dispatch** fails open the day the wrapper changes. Recognize the presence of a turn, never the shape of a dispatch.
- **The interception is not name-gated.** `/zzqnotarealcommand` is not a command this CLI has; it was intercepted anyway and answered `Unknown command:`. The dispatch decision is therefore made on the leading byte, upstream of any command-name lookup, and a consumer cannot avoid it by avoiding real command names.
- **One leading newline was sufficient to defeat it** at `2.1.251` — the middle column above is the same message body with a single `\n` prepended, and it produced a real, billed turn. What is Verified is that this transform worked on this build. The general claim that any whitespace prefix always defeats client-side interception is not something a probe of one build establishes, so it is not made here.
- **`client_composed: true` on the user frame turns the interception off for that message** (**Binary probe**, **Verified at `2.1.292`**, three processes whose request bodies a local logging proxy recorded, in a folder holding `sub/note.txt` and `sub/CLAUDE.md`). `/config theme=dark` sent that way was a real, billed turn whose request carried the text as written, and no command ran: Claude Code's settings file was not touched. `@sub/note.txt` sent that way was not expanded and did not pull in `sub/CLAUDE.md`, where the same text sent plainly brought the file's contents and that `CLAUDE.md` into the request. Everything else a first turn carries was the same either way: the `SessionStart` hook context, the environment, the output style, the agent types, the tool servers' instructions, the skill listing, the user's `CLAUDE.md`, the date, the attribution, the 41 tools and the system prompt. The pass Claude Code runs between tool calls still ran, so when the model then read the file itself the nested `CLAUDE.md` arrived with that tool result. A composed later turn also lacks that turn's late additions: the plain second turn carried the instructions of a tool server that had just connected, and the composed one did not. So a composed message loses what its own text would pull in and that turn's late additions, and nothing else. The daemon sets `client_composed: true` on every user frame whose text it composes itself, so a leading `/` or an `@path` in that text reaches the model as written. It never sets it on the person's typed text, which goes as typed so that their `@path` expands, nor on a command it sends for Claude Code to run, such as `/goal`, because the switch stops the command from running.

### A message from another session arrives on the session's own address

Measured at `2.1.278`, recorded at its own build on the [`rewind_conversation` precedent](#control-request-registry-binary-census): a consumer's measurement at that build, not re-run at `2.1.287`, where the peer-messaging literals it names (`cross-session-message`, `verifiedPeerPid`, `notify_when_idle`, `peer_idle_notice`, `messagingSocketPath`, `peerFeatures`, `cc-socks`, `tengu_harbor_kite_win`, `tengu_send_file`, `reply_across_default_dirs`) are all present. Thirteen runs of one headless receiver each — `-p --input-format stream-json --output-format stream-json --verbose --replay-user-messages`, a scratch folder, never a repository — with a plain writer process connecting to the receiver's own inbox socket, 489 connections in total. The method was one sanity run as the baseline and then each probe varying **one** thing against the one before it — the repeat interval, the number fired at once, how many processes sent them, which of the two sender declarations moved — so a result is read off a contrast rather than off a single run. **Binary probe** provenance, **Verified at `2.1.278`**.

- **A message written to a session's address reaches it, and reaches it mid-turn.** A user frame written to the address while the receiver has a turn running is taken into that running turn: 30 of 70 written onto a busy turn were delivered into it, and a frame that **starts** a turn arrives wrapped in the CLI's own peer preamble while one arriving **mid-turn** arrives as the bare `<cross-session-message …>` element with no preamble. **Where** in the running turn the fold happens is not established by these thirteen runs; a separate run at the same build, `2.1.278`, saw it taken up immediately after the tool that was in flight finished rather than at the turn's end.
- **What proves delivery is the receiver's own stream, not the write.** A delivered message appears on the receiving stream as a `user` frame carrying `origin` with `kind: "peer"`, the declared sender, the message id, and a `verifiedPeerPid` the CLI read off the socket with no token; that frame is visible only under `--replay-user-messages`. A **dropped** message produces nothing at all — no frame, no `system` frame of any subtype, no notice — so a consumer cannot tell a delivered write from a dropped one at the writing end and must watch the receiver.
- **The writer is told nothing.** Every one of the 489 connections received **zero bytes**; the connection stayed open for the writer's own eight-second hold and the CLI never closed one in answer to a message. This is the absence of a signal rather than a signal, and the probe held each connection only eight seconds, so a notice arriving later, or only over a connection that sent an auth line, would have been missed.
- **The receiving side's own protections fire against a plain writer, and their numbers are what this build did rather than a contract.** An identical message repeated under the same declared sender is dropped, the window measured longer than 20 s and no longer than 40 s from the last **accepted** copy, a dropped attempt not restarting the clock. At most **30** messages wait at once per declared sender (31st onward dropped; 70 → 30 and 72 → 30 in a simultaneous burst, while 40 paced about one per second all arrived, and the allowance refilled once the queue drained). Above that a session-wide cap of exactly **50** fires. Both the repeat check and the per-sender allowance key on the **top-level `from` string the writer chooses**, not on the writer's process: six processes under one declared name counted as one sender (30 delivered), one process rotating six names counted as six (50 delivered). A slow reply-driven loop is bounded by none of them — 40 rounds in 43 s all delivered and all answered — so these protections stop floods and repeats and do not stop a loop.
- **A queue draining into a new turn is concatenated into one user frame** holding several `<cross-session-message>` elements, and how much bundling happens is not predictable from the input: the same 50 messages ran as 50 turns in one probe and as 11 in another, same build, same shape. A consumer must not assume one turn per message or one message per frame.
- **`SendMessage` and `ListAgents` are in a headless session's own tool list** at `2.1.278` (**Binary probe**, **Verified at `2.1.278`**); `SendFile`, present in that build, was **absent** from the same list, for the flag reason below.
- **A peer frame written to a session held at a `PreToolUse` boundary waits for the hold and lands inside the same turn** (**Binary probe**, **Verified at `2.1.278`**). With a `PreToolUse` hook sleeping 25 s on `Read`, a frame written to the address during the hold produced nothing until the held tool's `tool_result`, then arrived 4 ms after it as the bare `<cross-session-message>` element, folded into that turn, and the model acted on it in the same answer (one `result`, `num_turns: 2`). The hold itself put no frame on the wire, so a held session is indistinguishable from an idle one to a writer.
- **A `PreToolUse` hook denying `SendMessage` fires, and only the JSON form hands the model the reason alone** (**Binary probe**, **Verified at `2.1.278`**). A settings-file hook on `SendMessage` stopped the send both ways it can answer: exiting 2 with the reason on stderr made the model read `PreToolUse:SendMessage hook error: [<the hook's own file path>]: <reason>`, while printing `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<reason>"}}` and exiting 0 made it read exactly `<reason>`. Both left the call, with its full input, in the `result` frame's `permission_denials`. The daemon's own hook answers in the JSON form with one of two texts: a send to another session reads `builder is another session. Send with session_send {"to": "builder"}.`, and a send to the address an incoming message came from reads `Your answer already reaches planner when you finish this turn. To say more, use session_send {"to": "s-4a10"}.`; the session tools are served on the daemon's shared tool server `sidekicks` ([Spec-014 §Session Tool Texts](../../specs/014-multi-agent-orchestration.md#session-tool-texts)). Not measured: the model's retry with another tool under the reason.
- **A peer-prompted turn's answer is routed back to nobody** (**Binary probe**, **Verified at `2.1.278`**). A courier with no token wrote one frame to a session's address; the session ran a turn and answered, the courier's connection received zero bytes, and no connection was made to the address the courier declared as `from`, which was listening the whole run. The answer existed only on the receiving session's own stream. Not measured: a frame that instructs the receiver to call `SendMessage` back.
- **The target forms a send is written against, and which tool documents them** (**Binary probe**, **Verified at `2.1.278`**). The build's own target resolver reads three schemes off a `to` string — `uds:`, `bridge:` and `did:` — and additionally treats a bare `/….sock` path, or a `\\.\pipe\…` name, as a `uds:` target. The two forms a consumer needs are spelled out on the sibling `SendFile` tool, whose `to` field reads, verbatim, `Recipient: a peer session name from ${ListAgents}, or an explicit uds:<socket> / bridge:<session id> address`, and whose prompt repeats it as `` `to` accepts a peer session name from ${ListAgents}, or an explicit `uds:<socket>` / `bridge:<session id>` address. `` `SendMessage`'s own prompt says the opposite in words — `the name IS the address; there is no separate address syntax` — while the cross-session gate recorded below is what admits that tool's `uds:` and `bridge:` targets at all. **Not established end to end:** the one live `SendMessage` carrying `to: "uds:/tmp/cc-socks/<pid>.sock"` was stopped by a `PreToolUse` deny before the resolver ran, so an address on **that** tool is read off the binary rather than off a delivery.
- **A live-session registry on disk names every running session and how to reach it** (**Binary probe**, **Verified at `2.1.278`**, measured 2026-09-21 by reading one running session's own registry file on the authoring machine). While a session runs it keeps `$CLAUDE_CONFIG_DIR/sessions/<pid>.json`, whose fields include `sessionId`, `cwd`, `messagingSocketPath`, `name`, `status` and `peerFeatures`, with the inbox key beside it under the name the binary derives as `<pid>.<sha256-of-the-canonical-socket-path>.key`. The vendor documents that the directory exists and that a session reads it to find the others; the **per-field shape is not documented** and is version-carried — `peerProtocol` and a `peerFeatures` array exist precisely so a reader can tell what a peer supports — so a consumer treats every field as optional and degrades to `a session is running here, details unknown` rather than failing. The key files are not read: the auth line is optional on this platform and reading another session's key is the impersonation shape the CLI's own warnings are about.
- **The wrapper the receiving model reads names the sender twice** (**Binary probe**, **Verified at `2.1.278`**). The element is `<cross-session-message from="…" from-name="…" from-mode="…">`: `from` is the address the writer declared, echoed back verbatim — a path outside the default inbox directories was accepted and reported unchanged in `origin.from` — `from-name` the sender's session name, and `from-mode` how it was sent. The wrapper names the sender and says nothing about replying to it, which is why a peer-prompted answer has to be read off the receiving stream.
- **What the binary says about platforms, and what it does not** (**Official docs** for the first half, read 2026-09-21; **Binary probe**, **Verified at `2.1.278`**, for the second). The docs state that cross-session messaging needs `2.1.224` or later on macOS and Linux, **including Linux inside WSL 2**, and `2.1.234` or later on **native Windows**; that the inbox is a Unix domain socket on macOS and Linux and a **named pipe** on native Windows; and that WSL 2 and native Windows on one computer cannot reach each other, as a container and its host cannot. The binary agrees: the cross-session gate carries a Windows arm of its own (`tengu_harbor_kite_win`, defaulting on, inside the same `As()` the environment variable overrides), the messaging path option describes itself as `a Unix domain socket on Mac/Linux, a \\.\pipe\ name on Windows`, and the path builder returns `\\.\pipe\…` on that platform. What the binary's **Unix** paths cover is narrower than a platform statement: the four directory patterns it accepts for a default-directory reply — `/^\/tmp\/cc-socks(?:-(0|[1-9]\d*))?$/`, `/^\/private\/tmp\/cc-socks(?:-(0|[1-9]\d*))?$/`, `/^\/run\/user\/(0|[1-9]\d*)\/cc-socks$/` and `/^\/data\/data\/com\.termux\/files\/usr\/tmp\/cc-socks(?:-(0|[1-9]\d*))?$/` — sit behind the `reply_across_default_dirs` peer feature and are the directories a reply may cross, not the set of inboxes that exist. A session's own socket is built at `$XDG_RUNTIME_DIR/cc-socks/<pid>.sock` while that fits the platform's address field (103 bytes here), falling back to `/tmp/cc-socks-<uid>/<pid>.sock`, or `$PREFIX/tmp/cc-socks-<uid>/<pid>.sock` under Termux. **Nothing here was measured on Windows**: every run behind this section was macOS, so the Windows legs are the vendor's prose plus the binary's own branches.
- **`SendFile` is gated by a server-side flag that is off by default, not by headless mode** (**Binary probe**, **Verified at `2.1.278`**). The tool's `isEnabled` is `As() && P("tengu_send_file", false)`; `As()` is the cross-session gate (`CLAUDE_CODE_HARBOR_KITE`, default on) and `tengu_send_file` has no local override, so `SendFile` is absent from every session on this account, interactive included. The binary's limits for it are 30 MiB per file and 16 files per message. The same `As()` gates `ListAgents`, `SendMessage`'s `uds:` and `bridge:` targets, and whether the session opens an inbound address at all (`[uds-messaging] Skipped: cross-session messaging gate off`), so switching it off closes both directions.
- **The loop guard reads a chain a host writes, in one form only** (**Binary probe**, **Verified at `2.1.287`**, measured 2026-10-02). The chain is the `hop-chain` attribute of the `<cross-session-message>` element, after `from` and `from-session` and before `from-name`, holding comma-separated 24-character lowercase hex ids, each a sending session's own id as the CLI writes it, at most 32 kept. A relay showed the form: a session that forwarded a peer message with `SendMessage` gave the next receiver an `origin.hopChain` holding its own id. Written by a host, on the session's address and on its stdin lane alike, a chain holding the receiver's own id 9 times was delivered and 10 times dropped, and a chain of 28 ids was delivered and 29 dropped (the build's defaults read `maxSelfHops: 10`, `maxChainLength: 28`). A chain in any other form, socket paths for instance, is not parsed: the element loses its parse, no limit applies, and nothing reports it. A dropped message gives the writing connection zero bytes and the receiver no turn. Claude Code tells the sender about a drop only when the sender's `from` is a socket inside Claude Code's own socket folder (`/tmp/cc-socks/` on this machine): it connects to that socket and writes one frame, `{"type":"control","action":"peer_message_status","status":"dropped","reason":…,"drop_reason":"hop-runaway","orig_msg_id":…}`; for a `from` outside that folder it skips the receipt (its debug log: `hold-receipt skipped: reply address unshaped or outside our socket namespace`) and the drop shows only as a `[peer-guard] Dropped peer message … : hop-runaway` debug-log line.
- **A helper's plain name wins over a session of the same name** (**Binary probe**, **Verified at `2.1.287`**, measured 2026-10-02). The helper tool (`Agent` on the wire) takes a plain `name`. With a helper named `builder` and another live session also named `builder`, which `ListAgents` listed under `Subagents` and `Peer sessions` respectively, `SendMessage` with `to: "builder"` resumed the helper, and the other session received nothing. A helper is not reached by its seventeen-character id alone, so a rule that tells a session from a helper by the id's shape misjudges a named one.
- **A host's frame is framed for an idle session and taken bare into a running turn, on either route** (**Binary probe**, **Verified at `2.1.287`**, measured 2026-10-03). The daemon wrote `<cross-session-message from="uds:<the daemon's socket>" from-session="s-4a10" from-name="planner" from-mode="prompting">` with a one-line body, once on the session's address and once on its stdin lane. Into an idle session, on the address, Claude Code put its own header before the element, `Another Claude session sent a message:`, and its own guidance paragraph after it, and added no line about replying. On stdin it wrote the same and one closing line more: `This message was delivered by your host application, and its from= is a host session id that SendMessage cannot reach: reply through the host's own messaging tool with that id, if it provides one.` A plain stdin body with `origin: {kind: "peer"}` got no framing at all. Into a session with a turn running, on either route, the message was taken in as a queued message absorbed into that turn (`absorbed_mid_turn`), and the model saw the bare element with no header and no guidance; with the daemon's `session_send` in its tool list the model acted on it and replied to `s-4a10` in three runs of three. `from-session` survived on both routes, and with two live sessions named `planner` every one of five replies, idle and mid-turn on either route, went to `s-4a10`. Only the address route recorded the message's `msg_id` and the writer's verified process id, which pairing a reply to its message reads.

### A reply comes back when the message asks for one, and the transcript pairs it to its prompt

**Binary probe**, **Verified at `2.1.278`**, recorded at its own build on the [`rewind_conversation` precedent](#control-request-registry-binary-census). Measured 2026-09-21, in the evening, America/New_York on the authoring machine: live authenticated headless sessions under `-p --input-format stream-json --output-format stream-json --verbose --replay-user-messages`, each in its own isolated config home, with a plain node process as the writer and a second live session standing in for a Claude-shaped inbox.

- **An instructed reply is sent, and it is one plain frame.** A peer message whose own text tells the model to call `SendMessage` with `to` set to that message's `from` produces the call, and a real `type: "user"` frame lands on the writer's socket **7 ms after the `tool_use`** — 350 bytes in one write, newline-terminated, **no handshake and no auth line**, the connection then closed by the sender. The frame is `{"msgV":1,"msg_id":…,"type":"user","message":{"role":"user","content":"<cross-session-message from=\"uds:…\" hop-chain=\"…\" from-name=\"…\" from-mode=\"prompting\">\namber\n</cross-session-message>"},"priority":"next","from":"uds:…"}`. The same message with the instruction line removed produced text only, no tool call, and **zero** connections on the writer's socket — so the routed-back-to-nobody finding above is a statement about what the wrapper asks for, not about what the tool can do.
- **A `SendMessage` reply reaches any `.sock` path.** The same send landed identically on a writer socket **outside** the runtime socket directory, 4 ms after the `tool_use`: this tool puts no directory rule on a `uds:` target. When the writer instead declared a **second live session** as its `from`, that session's inbox accepted the reply **3 ms** after the `tool_use` and its `origin` came back richer than a plain socket's — `name`, `hopChain`, `fromMode` and `body`, the reply text with the wrapper already stripped. So a consumer's own inbox need not reimplement this protocol to be replied to: it needs a socket and one newline-delimited JSON read, and a Claude-shaped inbox is what buys the parsed body.
- **The transcript pairs a reply to the message that prompted it.** The file is `$CLAUDE_CONFIG_DIR/projects/<project key>/<sessionId>.jsonl`, where the project key is the session's cwd with every slash turned into a hyphen — measured rather than assumed. The peer message's own record carries `turnOrigin: "peer"`, `isMeta: true`, `promptSource: "system"` and `origin` with `kind: "peer"`, the declared `from`, a `verifiedPeerPid` and the inbound `msg_id`; the chain from it down to the `tool_use` and its `tool_result` is unbroken by `parentUuid`, and the `tool_result` record carries the **outbound** `msg_id`, which closes the pair. A file-only reader therefore walks `parentUuid` up to the nearest ancestor whose `origin.kind` is `peer`. **Lines land on disk 63–226 ms after the timestamp they carry**, and never before the same text reaches the stream — the file is a slightly later view than the wire, not an earlier one.
- **The idle notice answers a plain process, carries state only, and is the one path with a directory rule.** A writer with no prior message and no handshake sent `{"type":"control","action":"notify_when_idle","from":"uds:…","from_mode":"prompting","msgV":1,"msg_id":…}` and received `{"type":"control","action":"peer_idle_notice","orig_msg_id":…,"state":"idle","finished_at":…,…}` — `finished_at` being the millisecond of the turn's own `result`, and **no text of any kind**: the subscription is a state edge, not a content channel, and it is one-shot. It is delivered **only** where the reply address is in the receiver's own socket directory, or is named like a session socket inside one of the four default directories; otherwise the receiver drops it and says so in its own words, `notify_when_idle dropped: reply address unshaped or outside our socket namespace`. Not established: whether that notice ever carries the optional `detail` the binary spreads conditionally — no writer here received it.
- **A hook sees `to` as a bare string in every name case, so a name is decidable only against the registry.** Three `SendMessage` calls through a `PreToolUse` hook gave `tool_input.to` as `probe-md-peer` (a live session's registry name), `courier` (a name in no registry) and `abd8b8d7a99274f48` (a subagent's seventeen-character lowercase-hex id) — three bare strings of one shape. Only the `uds:` and `bridge:` forms are decidable by prefix, so a consumer that must tell a session from a subagent reads `$CLAUDE_CONFIG_DIR/sessions/*.json` at decision time and matches on `name`. The Agent SDK's changelog for `0.3.292` (Claude Code `2.1.292`) adds `recipient_kind` to a `SendMessage` call's input on the stream's `assistant` message (**Official docs**, **Documented**; a literal at `2.1.293`); whether a hook's `tool_input` carries it was not checked. The hook's `tool_input` is also **wider than the wire's**: the stream's `tool_use` carried `{to, message, type, recipient, content}` where the hook read the same plus `summary`. **One naming trap in the same pass:** the `system/init` `tools` array advertises the spawn tool as `Task` while the wire's `tool_use.name` for it is `Agent`, so a `PreToolUse` matcher written against the advertised name never fires.
- **`total_cost_usd` on a persisted session's `result` frames is cumulative for the session, not per turn.** One session's five frames read `0.0035492 → 0.0131307 → 0.0225729 → 0.0269196 → 0.0362691`. A consumer that sums them over-counts; the last value is the session's spend.

### One tool server for every session, and a call that waits

**Binary probe**, **Verified at `2.1.287`**, measured 2026-10-02 and 2026-10-03 on the authoring machine against a local HTTP tool server, with two Claude Code sessions and, for comparison, two Codex conversations ([codex.md §One tool server for every conversation, and a call that waits](codex.md#one-tool-server-for-every-conversation-and-a-call-that-waits)).

- **One server answers every session, and each session holds one connection.** Nothing was started per session. Each Claude Code session made one setup and kept one connection for all its calls, and none reconnected per call.
- **Claude Code asks for the newest MCP revision first.** It asked for 2026-07-28, in which each call is self-contained and its progress streams on its own reply, with no per-client session, standing GET stream or DELETE, and fell back to 2025-11-25.
- **Progress keeps a long call alive, and a silent call is cut at 300 seconds.** A 20-second call sending progress every 5 seconds on its own reply was taken and finished. A `session_wait` held 400 seconds with nothing sent back was cut at exactly 300 seconds: the model got `sent no response or progress for 300s; aborting` as the tool's error, and the server learned of it only when its late answer met a closed connection. Claude Code's own code sets this idle limit at 300,000 ms over HTTP and 1,800,000 ms over stdio, raised by a server entry's `timeout` or by `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`, and reset by each progress message. A tool on the in-process route over the control channel (`sdkMcpServers`, calls arriving as `mcp_message`) answered at 400 seconds, its code setting no idle limit there. The model wrote nothing while it waited.
- **A held call costs the same however long it is held.** On the in-process route, a call held 180 seconds and one held 5 seconds, in near-empty sessions, spent the same tokens: 24,801 cached input read each, 25,070 and 25,048 written to the cache, and 242 and 208 out. The model is not run again while a call is held.
- **Tools behind the tool search are looked up first unless marked always loaded.** With neither switch, the model called `ToolSearch` before `session_send` in both runs; with `_meta["anthropic/alwaysLoad"]: true` on the tool in the server's tool list, or `alwaysLoad: true` on the `--mcp-config` server entry, it called `session_send` straight away in both runs.

## Environment and update control

Environment keys a supervising daemon or CI job must know about. The rows that name no build are present at `2.1.251` and `2.1.287` (Binary probe, Verified — each re-measured at this pin; the `CLAUDE_SECURESTORAGE_CONFIG_DIR` empty-value behavior below is a `2.1.245` reading of the schema-constructor census); each row after them names the build it was measured on, recorded at its own build on the [`rewind_conversation` precedent](#control-request-registry-binary-census), and every Claude Code key among them is a literal at `2.1.287`, or, for a row measured at `2.1.292`, at that build:

| `CLAUDE_CODE_SHELL_PREFIX` | Set to the daemon's command wrapper, which then runs every shell command after Claude Code's permission decision (measured at `2.1.282`). A child agent's Bash commands pass the same prefix, and so do hook commands, status-line commands and stdio tool-server starts; the wrapper tells a Bash command apart by its string shape, `eval '<command>' < /dev/null && pwd -P >| <file>`. The wrapper runs that string as given and holds none of the command's input: Claude Code appends the `< /dev/null` itself (read in the `2.1.292` binary, where a Bash command's standard input measured as `/dev/null`), so a command that reads its input gets end of input at once, never waits on it and raises no input line for it. The wrapper's round trip without a capture measured 1.6 ms median and 10 ms at the 99th percentile. |
| `GIT_ASKPASS`, `SSH_ASKPASS`, `SSH_ASKPASS_REQUIRE=force` | Set to a daemon program, so a git or ssh prompt that would open the terminal raises the same input line with the prompt's own words. |
| `CLAUDE_AUTO_BACKGROUND_TASKS` | Set to `1`: a tool-server call still running after 120 s, or one running when a new message arrives, moves to the background; the model gets a tool result naming the task id and goes on, and when the call ends Claude Code's task notification starts a turn if none is running. The same switch moves a foreground helper to the background after 120 s. A plain call moved to the background ends with the process. |
| `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, `CLAUDE_CODE_MAX_OUTPUT_TOKENS` | The compaction knob and the creation-time reads ([What the daemon sends to a process it starts](#what-the-daemon-sends-to-a-process-it-starts-and-what-it-reads-back)). `CLAUDE_CODE_MAX_OUTPUT_TOKENS` is set only in the creation-time control process, because it caps every reply. |
| `CLAUDE_CODE_EXIT_AFTER_STOP_DELAY` | Never set: Claude Code's own idle exit would end a process holding a pending wake-up. |
| `BASH_DEFAULT_TIMEOUT_MS` | The foreground default, 120,000 ms when unset, which also sets the background default: 1,800,000 ms, or this value when larger (600,000 ms in a single-prompt `-p "<prompt>"` run). So only a value above 30 minutes raises the background default, and it raises every foreground command's default with it (read from the build at `2.1.292`). |
| `BASH_MAX_TIMEOUT_MS` | Set to `2147483647` on every process the daemon starts. The foreground ceiling is this value, or the foreground default when larger, and 600,000 ms when unset; the background ceiling is 7,200,000 ms, or the foreground ceiling when larger, capped at 2,147,483,647 ms; the background default does not move. Measured at `2.1.292`: with `86400000` the Bash tool's description read `default 1800000ms / 30 minutes, max 86400000ms / 24 hours`; with `3000000000` the model read `max 3000000000 for a foreground command` and `max 2147483647ms / 597 hours` for the background, so only the background ceiling is capped; what a foreground `timeout` above 2,147,483,647 ms does is not measured. |
| `CLAUDE_CODE_DISABLE_DANGEROUS_RM_TIMEOUT` | Never set: with it set, a removal Claude Code's critical-path check flags at `auto` goes to the auto-mode classifier, which ran it (measured at `2.1.292`; the dangerous-removal paragraph under [Direction: some censused subtypes are refused BY NAME on the inbound channel](#direction-some-censused-subtypes-are-refused-by-name-on-the-inbound-channel)). |
| `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` | The in-turn cap on unmet goal checks, 8 by default: after the 9th unmet check in a row a `system` notification with `key: "stop-hook-block-cap"` arrives, then a `result` with empty text, and the goal stays active (measured at `2.1.282`). |
| `CLAUDE_CODE_REMOTE_MEMORY_DIR` | Not used: it would join the per-session memories the daemon keeps apart. An agent's `Everywhere` memory is `~/.ai-sidekicks/agent-memory/<name>/`, linked as `agent-memory` from every config home the daemon manages, so Claude Code reads it through the link. |

**A config home's login is its own, because the keychain service name is salted with the home** (**Binary probe**, **Verified at `2.1.278`**, 2026-09-21, read from the build and confirmed live on macOS). The service name is `Claude Code-credentials` when the config home is the default one, and otherwise carries a suffix that is the first eight hex characters of the sha-256 of the home the build salts with — `CLAUDE_SECURESTORAGE_CONFIG_DIR` where that is defined, the config home otherwise. So two config homes are two logins with no sharing between them, which is what an isolated home costs and what it buys. The one way to collapse them is the **empty-string** value the table's own row already records: setting `CLAUDE_SECURESTORAGE_CONFIG_DIR` to the empty string makes the suffix empty, so a non-default home reads the **default** service name and runs under the person's own login. Confirmed both ways in one pass: the same isolated home answered `Not logged in · Please run /login` without it and ran a billed turn with it.

**On macOS a login falls back to a file when the Keychain rejects the write** (**Official docs**, read 2026-10-06). Claude Code keeps a login in the Keychain, and when the Keychain rejects the write, as when it is locked in an SSH session, it keeps the login in `.credentials.json` at mode `0600`, the storage it uses on Linux; with `CLAUDE_CONFIG_DIR` set, that file sits under the config home ([Claude Code §Credential management](https://code.claude.com/docs/en/authentication#credential-management)). Once the Keychain is writable again, it moves the login back the next time it writes a credential ([Claude Code §Not logged in or token expired](https://code.claude.com/docs/en/troubleshoot-install#not-logged-in-or-token-expired)). Which folder the file lands in when `CLAUDE_SECURESTORAGE_CONFIG_DIR` is also set is not documented and is measured by the [macOS Service Probes](../../operations/macos-service-probes.md).

**A config home's login can change inside a running process** (**Binary probe**, **Verified** on a September 2026 build, below this file's pin). `apply_flag_settings {env: {CLAUDE_SECURESTORAGE_CONFIG_DIR: <the other account's home>}}` moves a running session to the other home's sign-in from its next request, with no restart and on the same conversation; a token account moves the same way with `CLAUDE_CODE_OAUTH_TOKEN` on the same channel. No version is checked, and there is no second way to move a session's account.

**An idle process can stop and resume with nothing lost** (**Binary probe**, **Verified at `2.1.283`**). Claude Code reports its background tasks as one complete set, `background_tasks_changed`, after every change; a stop kills a running background shell, so the daemon stops a session's process only when the last set was empty. Wake-ups (`ScheduleWakeup`, its `scheduledFor`) and session-only jobs (`CronCreate`, until its last run or `CronDelete`) are never in that set, and either fires only while a process runs (**Binary probe**, **Verified at `2.1.292`**, one recurring job and one wake-up across a stop and a `--resume`): closing the input exits the process at once with either pending; a resume brings a session-only job back by itself (`resume: resurrected 1 session cron task(s)` in its debug log), and the job then fires once per schedule, with or without a message, while that process runs; the runs due while no process ran are skipped, not caught up, and a one-shot job whose time passed is dropped (read from the build); a wake-up does not come back on a resume and never fired (the build restores one only when a job folder is set, `CLAUDE_JOB_DIR`). So the daemon keeps them from their tool results and keeps the process until two minutes after they fire. The daemon stops a process by closing its input and waiting for its exit. A resume of the same conversation is ready in about 1.2 s and starts a short answer in about 2.4 s, and runs `SessionStart` hooks again with the source `resume`. A goal set with `/goal` comes back by itself (**Binary probe**, **Verified at `2.1.292`**, on Haiku 4.5): after two unmet checks in the first process, `/goal` in a resumed one read `Goal active: <condition> (not yet evaluated)`, its check count started again, and its next turn ran the goal check as it stopped, which the transcript recorded as a `goal_status` attachment with `met: true`. A met check sends no frame on the stream, where an unmet one arrives as a user message beginning `Stop hook feedback:`, and a later resume read `No goal set.` once the goal was met.

**A background command in a process the daemon starts stops at a time limit** (**Binary probe**, **Verified at `2.1.292`**, 2026-10-07; [Tools reference §Time limit for background commands](https://code.claude.com/docs/en/tools-reference#time-limit-for-background-commands), read 2026-10-07). A `-p` or stream-json session counts as unattended, so its background Bash commands stop at a limit; a session in a terminal, the desktop app or VS Code has none. Nothing a host sends turns it off: the build's one switch-off is in `claude mcp serve`, and the limit sits behind a server-side flag, `tengu_cosmic_shore`, on for the account measured (read from the build). A command started with `run_in_background` gets its `timeout`, or the background default without one, at most the background ceiling (the two timeout rows under [Environment and update control](#environment-and-update-control)); measured, `sleep 300; echo finished` started with `timeout: 5000` was stopped 5.0 s after its `task_started` frame. A foreground command still running at its timeout, 120 s by default, moves to the background unless its first word is `sleep`, and then gets the background default from the move whatever `timeout` it carried: its tool result read `Command did not complete within its 120s timeout and was moved to the background (ID: <id>). Output is being written to: <path>. You will be notified when it completes. If it is still running after 30m in the background, it will be stopped and you will be notified.`, and the command received `SIGTERM` 1,800.006 s after the `task_updated {patch: {is_backgrounded: true}}` frame. No frame carries the deadline. The stop arrives as `task_updated {patch: {status: "killed"}}`, then `task_notification` with `status: "stopped"` and `summary: "Background command \"<description>\" was stopped after reaching its background time limit"`, then `background_tasks_changed` with an empty set, and Claude Code starts a turn on its own 45 ms later, telling the model to start the command again with a longer `timeout` if the work still needs it; a background command that finishes starts a turn the same way. At default settings the model reads, in the `timeout` parameter, `Optional timeout in milliseconds (max 600000 for a foreground command)`; in the `run_in_background` parameter, ``Set to true to run this command in the background. With it, `timeout` limits how long the command may run in the background before it is stopped (default 1800000 ms, max 7200000 ms).``; and in the tool's description, `You may specify an optional timeout in milliseconds (up to 600000ms / 10 minutes for a foreground command). By default, your command will timeout after 120000ms (2 minutes).` and ``With `run_in_background` the timeout is instead how long the command may run in the background (default 1800000ms / 30 minutes, max 7200000ms / 2 hours); at that limit it is stopped and you are notified.`` (these default-setting texts are read from the build; the same templates were measured rendered with `BASH_MAX_TIMEOUT_MS` raised). On macOS and Linux a background shell is also stopped under critical memory pressure once the session has been idle 30 minutes with no turn running, unless `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1`. So the daemon sets `BASH_MAX_TIMEOUT_MS=2147483647` on every process it starts; its appended system prompt tells the agent to give a background command a `timeout` from its expected run time and to start a server with `shell_run`; its `PreToolUse` hook returns a `run_in_background` Bash call that carries no `timeout` to the agent, naming that fix; and a command's row settles on the `stopped` `task_notification`.

**Updating the installed Claude Code** (**Binary probe**, **Verified at `2.1.293`**, 2026-10-07, run in throwaway homes with `HOME`, the `XDG_*` folders and `CLAUDE_CONFIG_DIR` pointed at scratch; [Advanced setup §Update Claude Code](https://code.claude.com/docs/en/setup#update-claude-code), read 2026-10-07). On a native install `~/.local/bin/claude` links into `~/.local/share/claude/versions/<version>`, and an update adds a file there and moves the link.

- **Only the interactive screen updates in the background.** The build installs from three places only: the interactive screen's updater (once when the screen opens, then every 30 minutes), `claude update` and `claude install`. A `-p --input-format stream-json` session with no opt-out set installed nothing in 45 s, so a process the daemon starts never updates itself, with or without the opt-outs.
- **`claude update` exits 0 on every outcome, a refusal included.** Updated, already current and refused all exit 0, so the result is read from where the command points afterwards, never from its exit status or words. With `DISABLE_UPDATES=1` it printed `Updates are disabled by your administrator…` and changed nothing; with only `DISABLE_AUTOUPDATER=1` it moved 2.1.290 → 2.1.293 and moved the link. The docs say the same: "`DISABLE_AUTOUPDATER` only stops the background check; `claude update` and `claude install` still work" ([§Disable auto-updates](https://code.claude.com/docs/en/setup#disable-auto-updates)). The older `autoUpdates: false` in `~/.claude.json` is moved by the build into `env.DISABLE_AUTOUPDATER: "1"` of the person's `~/.claude/settings.json` (read from the build).
- **The command follows the config folder it runs against.** `autoUpdatesChannel` (`latest` by default, or `stable`) and `minimumVersion` apply to `claude update` as they do to the background updater, and in the throwaway home `claude update` also wrote `installMethod: "native"` into that folder's `.claude.json`. The channel's newest version is `https://downloads.claude.ai/claude-code-releases/<channel>`, plain text (the build's own text); measured at 5:52 PM it was 7 bytes, `2.1.293` on `latest` and `2.1.285` on `stable`, and a request carrying the last `ETag` was answered `304` with 176 bytes of headers. A Homebrew install follows its cask instead, `https://formulae.brew.sh/api/cask/claude-code.json` or `claude-code@latest.json`, and on a Homebrew, WinGet or apk install `claude update` only prints the package manager's own command.
- **Cleanup keeps the link's build, builds with a live lock and the two newest, and runs on every `claude update`.** Of the rest it keeps the two newest by modification time and deletes the others; a run that found the build current still deleted the third-newest unprotected build. The docs say it keeps "any version a session on the same machine is running" ([§Install on network storage](https://code.claude.com/docs/en/setup#install-on-network-storage)), but the lock, `~/.local/state/claude/locks/<version>.lock`, covers one session per build: a session takes it only when it runs from inside `versions/`, a second session on the same build got none, and once the lock's holder exited `claude update` deleted the build the second session was still running. That session still answered a message, because macOS keeps a deleted file's data for a process holding it open. So a relaunch from a recorded path can find no file, and every start resolves `claude` again.
- **One install runs at a time.** A second backs off with `Another Claude process … is currently running` (read from the build).
- **A version's release notes** (**Official docs**, read 2026-10-07). Claude Code's changelog, `https://code.claude.com/docs/en/changelog`, carries each version under its own heading, anchored by the version with its dots as dashes, so `https://code.claude.com/docs/en/changelog#2-1-293` opens 2.1.293; the page is generated from `CHANGELOG.md` in `github.com/anthropics/claude-code` and carries every version that file does.

## Gaps recorded

Honest gaps between what the pinned binary shows and what the vendor documents — recorded rather than papered over. The first two are **partly closed by measurement**:

- **`--resume-session-at` — closed on the binary side, still open on the docs side.** It is **Verified present** in the `2.1.287` binary and **Verified absent** from that same build's `--help` output — as at `2.1.251` and `2.1.245` — so the docs-vs-binary divergence is confirmed from both directions rather than asserted. It remains **absent from the live CLI reference** fetched 2026-10-02. This is the `--help`-non-authoritative rule in action. `--rewind-files` is the confirmed companion, absent from the same three places; `--session-id` and `--fork-session`, which `--help` lists at `2.1.251` and `2.1.287`, are not.
- **`--bare` becoming the print-mode default — still open, still Provisional.** The claim is that `--bare` "will become the default for `-p` in a future release" — a modal, forward-looking statement (hedge preserved as written). That exact sentence was **not** found on the CLI reference page fetched 2026-10-02; the page describes `--bare` as a minimal mode (skips auto-discovery of hooks, skills, custom commands, subagents, installed plugins, MCP servers, auto memory and CLAUDE.md; Bash, file-read and file-edit tools only). The `--bare` literal is present at `2.1.287`, which says nothing about the default. Treat the "future default" claim as **Provisional** until it is confirmed against the live docs. It matters because the flip would break OAuth headless driving (`--bare` strips OAuth/keychain); a build that flips it fails sign-in, which shows in the daemon's logs.
- **No authless protocol probe exists for this provider.** Claude Code's `-p` path needs credentials to reach a handshake, so — unlike Codex, whose `initialize` answers on a scratch home with no account — there is no way to observe Claude's stream-json handshake without a token. Without one, this provider can be measured only through version reporting, argument-acceptance exit codes, and the control-request registry census; a real handshake takes an authenticated run. Any claim about live Claude wire behavior in a governing doc must name which of those it rests on. The [command-interception](#client-side-command-interception-on-the-programmatic-input-surface) section above rests on live **authenticated** `-p --output-format stream-json` runs against the pinned build, so this file carries directly observed live-stream claims, and the gap stands: an authless handshake is unreachable on this provider, so live-wire claims here cost real credentials and real billed turns to establish, and a consumer cannot reproduce them in CI without an account.
