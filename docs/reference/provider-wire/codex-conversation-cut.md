# Codex Conversation Cut

The undo's conversation cut on the Codex `app-server`, part of the [Codex Wire Reference](codex.md), whose version pin and trust framing hold here. See the [family README](README.md) for the TRUST / PROVENANCE vocabulary this file uses.

## `thread/revert` — the undo's conversation cut

```
ThreadRevertParams   = { threadId: string, beforeTurnId: string }
ThreadRevertResponse = { thread: Thread, turnsBackwardsCursor: string | null, itemsBackwardsCursor: string | null }
```

**`thread/revert` drops the named turn and every later one from the thread's own history, and leaves the caller on the same thread.** It is in the default `ClientRequest` root at `0.162.1`, with no `#[experimental(…)]` marker in `common.rs` at `rust-v0.162.1`, so a default connection calls it: a well-formed request on a default connection is answered by the method, `thread not found: <id>` for a thread that is not loaded (**Binary probe**, **Verified at `0.162.1`**). It works only on a thread with paginated history, and a `thread/start` with no `historyMode` on a default connection returned `historyMode: "paginated"` at `0.162.1`. The generated type carries the file caveat, verbatim: "This only changes persisted conversation history. It does not revert local file changes." The reply's `thread.turns` is always empty ("hydrate retained history through `thread/turns/list`"), and the two cursors page the kept turns and items backwards through `thread/turns/list` and `thread/items/list`, both also default methods at `0.162.1`. **Binary probe, Verified at `0.155.1` and `0.156.0`**: a three-turn thread reverted before its second turn came back listing one turn, and the files the reverted turns had written were all still on disk (three runs of three at `0.155.1`); the cut holds past an automatic or an explicit compaction and across a resume, the next model request carrying the kept turns' own messages and replies rather than the compaction summary (measured at `0.156.0` and `0.161.0`). **Binary probe, Verified at `0.161.0`**, 2026-10-07, in a throwaway Codex folder signed in with a fake API key against a local mock model server that recorded every request body, the model `gpt-5.6-luna`: three turns, a compaction (one run explicit by `thread/compact/start`, one automatic, with `model_auto_compact_token_limit` below the usage the server reported), a fourth turn, a revert before the second turn, one more turn, then `thread/resume` in a fresh `codex app-server` and a turn there. In both runs that last request carried the first turn's message and reply and the post-revert turn's, and no `compaction` item. A revert before the fourth turn, resumed the same way, sent the compaction item, the three user messages the compaction kept and the later turn, and none of the first three replies.

**Whether a thread still holds a turn is read from `thread/turns/list`** (read in the source at `rust-v0.169.0`; the empty listing and the revert after it measured live, below). `ThreadTurnsListParams` is `{threadId, cursor?, limit?, sortDirection?, itemsView?}`, the direction "defaults to descending" and the item detail "defaults to summary", and the response pages `data: Turn[]` with a cursor that is `None` when "there are no more turns to return". `thread/read` with `includeTurns` is not the read: its own description says "Full-history hydration is deprecated for paginated threads; prefer a metadata-only read and page with `thread/turns/list` and `thread/items/list`.", and the server sends a deprecation notice for it on a paginated thread. A retried undo pages the list newest first, 100 turns a page, with `itemsView: "notLoaded"`, and stops at the first turn whose `startedAt` (Unix seconds) falls before the second the message was sent in, which the message's UUIDv7 id dates: no turn of the message starts after that one. It looks first for the turn the driver recorded for the message or, where that record starts empty after a restart, the turn the daemon's own log recorded the message's turn start under, and that turn listed answers at once. A known turn is where the search starts, never the proof of a cut: a faster-model retry forks the thread to before the held turn, which the fork drops, and sends the same message ids again on a new turn. So a message whose known turn is not listed, and one with no turn known, is looked for in the turns the paging passed: first the oldest turn started since the send, which a message usually opened, then the turn running at the send, which a steer joined, then the later ones oldest first, each turn's items read through `thread/items/list` with its `turnId`, 100 items a page, oldest first, until one `userMessage` item carries the message's id as its `clientId` (`UserMessage { id, client_id: Option<String>, content }`, camel-cased on the wire), or the id of the message that opened the turn the message rode in: a turn start sends only its first message's id as `clientUserMessageId`, so a later message of a continue that sent several is found by its opener's, which the daemon's log names. A message none of those turns holds is not read as cut, since a projection that failed after the durable write (below) can leave older turns listed and the message's own missing: the ask answers it unconfirmed where a turn of it is known and held where none is, and the cut goes before the known turn, or before a turn id no thread holds, which Codex's own record decides as for a thread that lists none (below). No undo is refused for a message that is still there, and no cut is recorded that Codex did not make: the driver reads a message as cut only from its own record of a revert Codex applied or refused, so the message just before the undo's point, which it reads only once the reach reads cut, is read on a listing that revert brought up to Codex's record, its turn having been in that record when the revert ran. A page whose `nextCursor` is the cursor it was asked with fails the read, as Codex's app server fails a read whose store returns a repeated cursor (`thread_processor.rs`). A turn listed with no `startedAt` cannot be dated before the send, so the paging goes past it; where no turn is dated before the send, the newest undated turn stands for the one running at the send and is read second, and the other undated turns are read last, newest first. Codex dates every turn it opens (`Session::emit_turn_started` in `codex-rs/core/src/session/mod.rs` sends the time `mark_turn_started` set when the task started, in `codex-rs/core/src/tasks/mod.rs`); a turn the history builds with no `TurnStarted` event, as an older rollout holds, has none (`new_turn` in `codex-rs/app-server-protocol/src/protocol/thread_history.rs`), and the ask counts a zero or negative time as none. **A listing with no turn shows no cut.** Codex answers an empty page with no error for a thread whose history it has not projected into its index. It projects a paginated thread on each write and at each resume of a thread that is not a helper's: `Session::record_initial_history` flushes the rollout, and the store's flush (`write_and_project` in `codex-rs/thread-store/src/local/live_writer.rs`) projects it, a failed projection only logged as a warning, so an empty listing can follow a resume. A thread cut to before its first turn lists none either, so no read tells the two apart: `thread/turns/list`, `thread/items/list` and `thread/read` with `includeTurns` all read that projection, and `thread/read` without it carries the same `preview` and no turn on both, since a revert changes only the rollout the thread's row points at (`replace_rollout_path_if_current` in `codex-rs/state/src/runtime/threads.rs`). `thread/revert` does tell them apart: before it looks for the turn it projects every rollout of the thread's lineage from the files, failing on a projection error rather than warning (`revert` in `codex-rs/thread-store/src/local/revert_thread.rs`), then finds the turn in its own record or answers `-32600 "turn not found: <id>"` with nothing changed (`find_turn` in `codex-rs/thread-store/src/local/thread_history/turn_lookup.rs`). The projection resumes where the last batch it committed left off (`materialize_to_sqlite_with_state_db` in `codex-rs/thread-store/src/local/thread_history_materialization.rs` reads from `thread_history_projection_state`'s byte offset to the file's end), so it brings a listing that lags up to the record. The refusal returns before the replacement rollout is written and before the thread's row is switched to it (`create_replacement_recorder`, `replace_rollout_path_if_current`), so the conversation is unchanged, and the lineage's fallback read passes it through as it came (`read_with_fallback` in `codex-rs/thread-store/src/local/rollout_lineage/ancestor_reads.rs` retries only a read whose ancestor file failed). The thread's runtime is not unchanged: the app server handles a refused revert as an applied one (`thread_revert_response` in `codex-rs/app-server/src/request_processors/thread_processor.rs` waits for the thread's shutdown, removes the loaded thread and cancels its requests, calls the store's revert, then reloads the thread with its history and its MCP runtime through `reload_paginated_thread` whichever way the revert ended), and a reload that fails answers its own error in place of the refusal, the thread already removed. So the ask reads a thread Codex lists no turn of as holding the message, the undo sends its cut before the turn the daemon's log names, and a refusal naming that turn is followed by the listing read again: a turn found holding the message is cut before, and a thread still listing none has the cut adopted as one Codex already made, answered as a refusal the daemon reads the ask after, which then reads the message cut away. A cut whose answer was lost leaves the driver's record naming the turn, so its retry sends the cut before that turn and meets the same refusal and adoption with no restart. With neither the driver's record nor the log naming a turn of the message, the cut goes before `sidekicks:no-turn`, an id no thread holds: Codex names a turn by a UUIDv7 (`new_submission_id` in `codex-rs/core/src/session/mod.rs`), `auto-compact-<n>` (`next_internal_sub_id`, the same file) or, for a turn its history rebuilds with none, `rollout-<n>` (`new_turn` in `codex-rs/app-server-protocol/src/protocol/thread_history.rs`), none with a colon. Its refusal brings the listing up to the record and is followed by the same search and adoption, so an undo pays at most two reverts, the refused one and the cut, and each pays the reload above. A thread whose first message Codex has taken and not yet written answers the list with `-32603` and `failed to read thread: thread-store internal error: failed to read session metadata <rollout path>: rollout at <rollout path> is empty`, which the ask reads as no turn on record, as it reads `is not materialized yet`. **Live probe**, `0.169.0`, Nov 14, 2026 at about 3:29 PM, `codex app-server` under a private `HOME` and `CODEX_HOME`, `gpt-6.1-terra` at high effort, one run: a thread with one turn reverted before it answered the revert and then listed `data: []`; after a restart of the service its `thread/resume` page, `thread/turns/list` and `thread/items/list` were each `data: []` with no cursor, `thread/read` carried `preview: "Reply with the single word ok."` and `turns: []`, a second `thread/revert` before the same turn answered `-32600 "turn not found: <that turn's id>"`, the list after it was still empty and the thread then ran a turn to `completed`. **Live probe**, `0.169.0`, a second run, `codex app-server` under a private `HOME` and `CODEX_HOME`, `gpt-6.1-terra` at high effort: on a thread with one completed turn, `thread/revert` before `sidekicks:no-turn` answered `-32600 "turn not found: sidekicks:no-turn"` and `thread/turns/list` listed the same one turn after it. On a second thread with two completed turns, loaded and idle, the projection was set back as a failed projection leaves it, in the private `thread_history_1.sqlite`: its `thread_turns` and `thread_items` rows from the older turn's `rollout_ordinal` on deleted and `thread_history_projection_state` set back to that turn's starting offset and ordinal, so the list answered `data: []`; the same revert answered the same `turn not found`, and the list after it held both turns again. A second thread with one turn, its projection rows deleted from the private `thread_history_1.sqlite` after the restart as a failed projection leaves them, listed `data: []`, and `thread/revert` before its turn was accepted and left it listing `data: []`. A third thread listed right after its first `turn/start` answered the `-32603` above, and a thread with no message answered `is not materialized yet; thread/turns/list is unavailable before first user message`. `"full"` is not asked for: the handler keeps it as "only a temporary compatibility path", and a legacy thread's list "still replays the entire rollout on every request. Rollback and compaction events can change earlier turns, so the server has to rebuild the full turn list". `thread/items/list` answers `-32601 "thread/items/list is not supported yet"` on a thread whose history mode is `ThreadHistoryMode::Legacy` (`validate_thread_for_paginated_reads` in `codex-rs/thread-store/src/local/thread_history/read.rs`), which `thread/turns/list` still serves by rebuilding the turns from the rollout (`thread_turns_list_response_inner` in `codex-rs/app-server/src/request_processors/thread_processor.rs`). On such a thread the search pages `thread/turns/list` again with `itemsView: "summary"`, which holds each turn's first user message and its last agent message (`TurnItemsView::project_items` in `codex-rs/app-server-protocol/src/protocol/turn_items_view.rs`), until it has read every turn it would have searched, and finds a message, or its opener, that opened one of them. A steer is not in the summary, so a message not found there reads as held at an undo, and as not taken at a resume, whose continue is sent as a turn's opening. The read is made when an undo asks whether its cut was already made, and at a resume only for the messages the daemon sent with no answer, to learn which of them Codex took. On a loaded legacy thread the listing also holds the turn still running: that branch of the handler merges the thread's in-memory active turn before it pages ("Persisted history may not yet include the currently running turn … so merge that in-memory snapshot before paginating.").

**A fork's copy keeps each message's `clientId`, so its absence still reads as a cut** (**Upstream source**, read at `rust-v0.169.0`: the fork's persistence in `codex-rs/core/src/session/mod.rs`; `handle_user_message` in `codex-rs/app-server-protocol/src/protocol/thread_history.rs`). A copied fork keeps the source's rollout items ("Keep the copied prefix and effective child settings in one append so a cold resume cannot observe inherited settings as the latest value."), and the history projection carries each stored user message's `client_id` onto its `UserMessage` item, so a message from before the fork is listed on the fork under the same id. A fork truncated before a user message (`ForkSnapshot::TruncateBeforeNthUserMessage` in `core/src/thread_manager.rs`) drops that message and every later one, which is a cut, so the undo reads a message the fork does not hold as cut away, as on the source.

**Two consequences a consumer builds around.** A conversation a person may undo is never started ephemeral, because an ephemeral thread carries no paginated history and `thread/revert` does not answer on it. And the cut is the **conversation** only: the files the reverted turns wrote are restored by the daemon from its own checkpoints, never by the provider and never by a git snapshot ([Spec-003 §Driver-Level Rollback Mechanics](../../specs/003-queue-steer-pause-resume.md#driver-level-rollback-mechanics)). The same cut hands back a turn too long for the model's window: a turn that fails with `codexErrorInfo: "contextWindowExceeded"` is cut before it and returned to the person as a failed send.

**Codex has no `thread/rollback`.** It is absent from the `0.162.1` generation, its request and response types included, and a request answers `-32600` with the deserializer's `unknown variant` enumeration ([Refusal shapes on the client-request channel](codex.md#refusal-shapes-on-the-client-request-channel)), measured at `0.162.1`. The upstream README at `rust-v0.162.1` says so in its own words: "`thread/rollback` has been removed from the API, including its request and response types. Requests use the generic unknown-method rejection path. Use `thread/revert` for paginated threads instead." No driver of this project registers it.

**`thread/fork` with a turn boundary is a fork, not a cut.** `thread/fork` is present and non-experimental, and carries `lastTurnId` — `v2/ThreadForkParams.ts`, verbatim:

> Optional last turn id to fork through, inclusive. When specified, turns after `last_turn_id` are omitted from the fork. The referenced turn cannot be in progress.

```
ThreadForkParams.lastTurnId?: string | null    // non-experimental
ThreadForkParams.excludeTurns?: boolean        // non-experimental
```

A fork creates a **new thread**, which is what a person's fork of a session asks for; the undo is the cut above, which leaves the caller on its own thread. Sibling boundary fields on the same type are experimental: `beforeTurnId` (`#[experimental("thread/fork.beforeTurnId")]`, "Optional turn id to fork before, excluding that turn and all later turns. Cannot be combined with `last_turn_id`.") and `path`. `excludeTurns`, "return only thread metadata and live fork state without populating `thread.turns`", is in the default generation of both `thread/fork` and `thread/resume` at the pin.
