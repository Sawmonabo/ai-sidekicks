## Regeneration

The Codex wire is regenerated from the pinned binary, never hand-transcribed. Both subcommands are still `[experimental]` at `0.160.0` and nested under `app-server` (they are not top-level — re-verified against `codex app-server --help` at this pin):

```
codex app-server generate-json-schema --out <DIR>   # JSON Schema bundle
codex app-server generate-ts          --out <DIR>   # TypeScript bindings (ts-rs)
```

At `0.160.0` the JSON Schema run emits 37 top-level files — the four protocol roots `ClientRequest.json`, `ServerRequest.json`, `ServerNotification.json`, `ClientNotification.json`, per-type files, and the aggregates `codex_app_server_protocol.schemas.json` / `…v2.schemas.json` — plus `v1/` and `v2/` subdirectories (275 files in `v2/`, up from 256 at `0.150.1`). The TypeScript run emits a parallel tree: 94 top-level files plus `v2/` (639 files, up from 595) and `serde_json/`. The split is a **legacy top-level set** and a **`v2/` subdirectory** holding the modern protocol. **Both** subcommands take `--experimental`, which adds experimental methods and fields to the output; the shapes pinned here are from the default (non-experimental) generation.

## Method namespace

The wire has two coexisting method-naming styles at `0.160.0` (the shapes below are Verified from `ClientRequest.json` / `ServerRequest.json` / `ServerNotification.json`):

- **Legacy — bare camelCase, no slash.** A small residual set: client requests `initialize`, `fuzzyFileSearch`; server requests `execCommandApproval`, `applyPatchApproval`; the client notification `initialized`; server notifications `error`, `warning`, `configWarning`, `deprecationNotice`, `guardianWarning`.
- **Modern — slash-namespaced paths** (their generated types live under `v2/`). This is where the capability surface this project drives lives: `thread/*`, `turn/*`, `account/*`, `config/*`, `mcpServer*/*`, `permissionProfile/*`, `review/start`. Note the paths are slash-namespaced method strings (e.g. `thread/revert`); they are **not** prefixed with a literal `v2/` on the wire — the `v2/` is the generated-file layout, not a method-string segment.

`ClientRequest` at `0.160.0` and at `0.161.0` unions 104 client-request methods across both styles.

## The experimental gate — a runtime filter, not a schema filter

**This is the highest-consequence fact in this file, and the generated schema alone cannot show it.** Presence of a method or notification in the default-generated schema does **not** mean a default connection receives it.

**The generator gates requests but not notifications — measured.** Both generator subcommands take an `--experimental` flag ("Include experimental methods and fields in the generated output"). Running both generations from the same `0.160.0` binary and differencing their JSON-schema union roots shows the filter is applied asymmetrically:

| Union root | Default generation | `--experimental` generation | Difference |
| --- | --- | --- | --- |
| `ClientRequest` | 104 | 167 | **+63**, including all six `thread/realtime/*` client requests |
| `ServerRequest` | 10 | 11 | +1 (`currentTime/read`) |
| `ServerNotification` | 83 | 83 | **none — the two sets are identical** |
| `ClientNotification` | 1 | 1 | none |

`0.161.0` gives `ClientRequest` 104 against 169 (**+65**), `ServerRequest` 10 against 11, `ServerNotification` 84 against 84 (**identical**) and `ClientNotification` 1 against 1. `0.159.2` gives the same four rows as the table, and the previous pin `0.150.1` showed the identical asymmetry — `ClientRequest` 95 vs 153 (+58), `ServerNotification` 79 vs 79 **identical** — as did `0.141.0` and `0.149.1` before it, so this is the mechanism's steady behavior across releases, not an artifact of one.

So for **requests**, the default schema is honest: what it omits, a default connection genuinely cannot call. For **notifications**, the default schema tells you nothing — every experimental notification is in it. The gate for notifications therefore has to live at runtime, and it does.

`initialize` carries `capabilities: InitializeCapabilities | null`, whose first field is `experimentalApi: boolean` ("Opt into receiving experimental API methods and fields", verbatim from the generated `InitializeCapabilities.ts`). The upstream source at `rust-v0.160.0` shows what that flag gates on the outbound path (Upstream source provenance, Verified — `codex-rs/app-server/src/transport.rs`, `should_skip_notification_for_connection`): the function returns `true` — skip — when `envelope.notification.experimental_reason().is_some()` and the connection's `experimental_api_enabled` is unset. The notification is dropped silently, with no error, no `deprecationNotice`, and no signal of any kind that the client is missing events.

At `0.160.0`, **22 of the 83 default-generated server notifications are gated**: all eleven `thread/realtime/*` (see below), plus `mcpServer/event/stream/notification`, `thread/queue/changed`, `project/changed`, `thread/project/updated`, `thread/environment/connected`, `thread/environment/disconnected`, `thread/settings/updated`, `autoApprovalReview/strictReviewRequired`, `process/outputDelta`, `process/exited`, and `turn/moderationMetadata`. At `0.150.1` it was 23 of 79: `thread/reverted` has since lost its marker, so a default connection now receives it, and **none of the four notifications added since carries one**. At `0.161.0` it is **23 of 84**: the same 22 plus `thread/prediction/updated`, which arrived at that build with its own `#[experimental(…)]` marker (`codex-rs/app-server-protocol/src/protocol/common.rs` at `rust-v0.161.0`). A driver that reads the generated `ServerNotification` union as its delivery contract will therefore expect about a quarter of the notification surface it never receives.

**Why 22 is a total and not a floor.** `experimental_reason()` has two sources, and both were re-checked at this pin. A variant may carry an explicit `#[experimental(…)]` marker in the `server_notification_definitions!` block — 22 do, enumerated above. Failing that, `experimental_reason_expr!` falls through to the **params type's** own `ExperimentalApi` implementation, so a variant with no marker of its own is still gated if its params type is. At this pin that fallthrough contributes nothing: of the 31 types whose `#[derive(…)]` names `ExperimentalApi` across `app-server-protocol/src/protocol/v2/` (one pattern run over both tags; it finds 28 at `rust-v0.150.1`), **none is a notification params type** (they are request params, responses, and config structs — `TurnStartParams` among them). The same two checks at `rust-v0.161.0` give 23 markers and 33 deriving types, again none a notification params type, so 23 is the total there. Re-verifying the total means re-running both checks, not just grepping for the attribute.

**Source declares 85; the binary generates 83 — count the generated schema.** The `server_notification_definitions!` invocation at `rust-v0.160.0` lists 85 variants, but the `0.160.0` binary's own default generation emits 83 arms. The two that do not reach the schema are `rawResponse/completed` and `rawResponseItem/completed` — the same two as at `0.150.1`, where the block listed 81 against a generated 79; **neither carries an experimental marker**, so the numerator above is unaffected and the denominator is the generated 83, per this family's counting basis. At `rust-v0.161.0` the block lists 86 against a generated 84, the same two missing. Anyone re-deriving 22-of-N or 23-of-N from the source block alone will get the wrong denominator.

`InitializeCapabilities` also carries `optOutNotificationMethods?: Array<string> | null` — "Exact notification method names that should be suppressed for this connection" — evaluated by the same function. Suppression is thus **two-sourced**: the experimental marker, and the client's own opt-out list.

**The server-request side carries a marker the app-server does not enforce.** The "default schema is honest" reading above holds for `ClientRequest`: the +63 the experimental generation adds there are genuinely uncallable on a default connection. `ServerRequest` is different. `item/tool/requestUserInput` sits **inside** the default-generated 10 — the default-vs-experimental delta on that root is the single unrelated `currentTime/read` — and its generated definition carries the marker "EXPERIMENTAL - Request input from the user for a tool call." That marker is a doc comment, not a gate (**Upstream source**, read at `rust-v0.150.1` and `rust-v0.160.0`): `ToolRequestUserInputParams` derives no `ExperimentalApi`, `should_skip_notification_for_connection` sees no request, and the transport's only request-side filter, `filter_outgoing_message_for_connection`, strips experimental **fields** from `item/commandExecution/requestApproval` and passes every other server request through whole. So nothing in `app-server` withholds `item/tool/requestUserInput` from a default connection; whether one reaches it depends on whether the turn offers the model its question tool, which is decided outside `app-server` and is not read here. The generator does withhold one variant on this root: `mcpServer/elicitation/request`'s params type derives `ExperimentalApi` at `0.160.0`, and its `openai/userVerification` mode appears only in the `--experimental` generation. A consumer routes `item/tool/requestUserInput` whatever its connection negotiated.

## Refusal shapes on the client-request channel

Three distinct refusals share one JSON-RPC code at this pin, and a consumer that discriminates on the code alone gets all three wrong (**Binary probe**, **Verified** at `0.160.0` and at `0.159.2`, measured by a purpose-written stdio client driving `codex app-server` through `initialize` → `initialized` on a **default** connection against a scratch `CODEX_HOME` with no login, then issuing one request per case and recording the reply verbatim).

| What was sent | Code | Message (verbatim, name substituted) |
| --- | --- | --- |
| a method string the deserializer does not accept | `-32600` | `` Invalid request: unknown variant `zzq/nonexistent_method`, expected one of `initialize`, `server/diagnostics`, `userVerification/status`, … `` |
| an accepted method, with empty params | `-32600` | `` Invalid request: missing field `threadId` `` — measured identically for `turn/steer`, `thread/goal/set`, `thread/fork` and `thread/revert`; with the `params` member left out entirely the message is `` Invalid request: missing field `params` `` |
| an accepted method the connection is not entitled to | `-32600` | `server/diagnostics requires experimentalApi capability` |

`-32601`, the standard method-not-found spelling, was not observed for any of the three. It does appear elsewhere: `thread/items/list` on a thread the home holds no rollout for answers `-32601 "thread/items/list is not supported yet"`.

**The discriminator is the message, and specifically the deserializer's own `unknown variant` enumeration.** Only the first row names a method the connection cannot call; the other two are answers from a method that exists. A consumer reading `-32600` as "no such method" therefore concludes that `turn/steer` and `thread/goal/set` are absent from every build, because both take a thread identity a bare probe does not compose. The deserializer also runs before the entitlement check, so a well-formed experimental request is needed to tell the third row from the second: at `0.150.1` `thread/revert {threadId, beforeTurnId}` answered `thread/revert requires experimentalApi capability`, and at `0.159.2` and `0.160.0` the same request answers `thread not found: <id>` for a thread that is not loaded.

Two further properties of that enumeration, and both matter to anyone parsing it:

- It lists the **deserializer's** accepted variants, which is a superset of the default-generated `ClientRequest` root: experimental methods are in it and are still refused by the third row above. **Enumeration membership is not availability** — the same rule this family's Claude reference states for its own control-request census.
- The identical `unknown variant` wording appears for enums nested **inside** an accepted request. Sending the withdrawn `AskForApproval` arm (see [Breaking type changes](#breaking-type-changes-from-earlier-builds)) draws `` Invalid request: unknown variant `on-failure`, expected one of `untrusted`, `on-request`, `granular`, `never` `` — a message about a field's value, not about the method. So the refused variant the message names must be compared against the method string that was sent; a parser that only looks for the phrase reads a rejected parameter as a missing method.

### `thread/revert` — the undo's conversation cut

```
ThreadRevertParams   = { threadId: string, beforeTurnId: string }
ThreadRevertResponse = { thread: Thread, turnsBackwardsCursor: string | null, itemsBackwardsCursor: string | null }
```

**`thread/revert` drops the named turn and every later one from the thread's own history, and leaves the caller on the same thread.** It is in the default `ClientRequest` root at `0.160.0` and at `0.159.2`, with no `#[experimental(…)]` marker in `common.rs` at `rust-v0.160.0`, so a default connection calls it: a well-formed request on a default connection is answered by the method (`thread not found: <id>` for a thread that is not loaded) where `0.150.1` answered `thread/revert requires experimentalApi capability` (**Binary probe**, **Verified at `0.159.2` and `0.160.0`**). It works only on a thread with paginated history, and a `thread/start` with no `historyMode` on a default connection returned `historyMode: "paginated"` at `0.160.0`. The generated type carries the file caveat, verbatim: "This only changes persisted conversation history. It does not revert local file changes." The reply's `thread.turns` is always empty ("hydrate retained history through `thread/turns/list`"), and the two cursors page the kept turns and items backwards through `thread/turns/list` and `thread/items/list`, both also default methods at `0.160.0`. **Binary probe, Verified at `0.155.1` and `0.156.0`**: a three-turn thread reverted before its second turn came back listing one turn, and the files the reverted turns had written were all still on disk (three runs of three at `0.155.1`); the cut holds past an automatic or an explicit compaction and across a resume, the next model request carrying the kept turns' own messages and replies rather than the compaction summary (measured at `0.156.0` and `0.161.0`). **Binary probe, Verified at `0.161.0`**, 2026-10-07, in a throwaway Codex folder signed in with a fake API key against a local mock model server that recorded every request body, the model `gpt-5.6-luna`: three turns, a compaction (one run explicit by `thread/compact/start`, one automatic, with `model_auto_compact_token_limit` below the usage the server reported), a fourth turn, a revert before the second turn, one more turn, then `thread/resume` in a fresh `codex app-server` and a turn there. In both runs that last request carried the first turn's message and reply and the post-revert turn's, and no `compaction` item. A revert before the fourth turn, resumed the same way, sent the compaction item, the three user messages the compaction kept and the later turn, and none of the first three replies.

**Two consequences a consumer builds around.** A conversation a person may undo is never started ephemeral, because an ephemeral thread carries no paginated history and `thread/revert` does not answer on it. And the cut is the **conversation** only: the files the reverted turns wrote are restored by the daemon from its own checkpoints, never by the provider and never by a git snapshot ([Spec-003 §Driver-Level Rollback Mechanics](../../specs/003-queue-steer-pause-resume.md#driver-level-rollback-mechanics)). The same cut hands back a turn too long for the model's window: a turn that fails with `codexErrorInfo: "contextWindowExceeded"` is cut before it and returned to the person as a failed send.

**Codex has no `thread/rollback`.** It is absent from the `0.159.2` and `0.160.0` generations, its request and response types included, and a request answers `-32600` with the deserializer's `unknown variant` enumeration ([Refusal shapes on the client-request channel](#refusal-shapes-on-the-client-request-channel)), measured at `0.156.0`, `0.159.2` and `0.160.0`. The upstream README at `rust-v0.160.0` says so in its own words: "`thread/rollback` has been removed from the API, including its request and response types. Requests use the generic unknown-method rejection path. Use `thread/revert` for paginated threads instead." No driver of this project registers it.

**`thread/fork` with a turn boundary is a fork, not a cut.** `thread/fork` is present and non-experimental, and carries `lastTurnId` — `v2/ThreadForkParams.ts`, verbatim:

> Optional last turn id to fork through, inclusive. When specified, turns after `last_turn_id` are omitted from the fork. The referenced turn cannot be in progress.

```
ThreadForkParams.lastTurnId?: string | null    // non-experimental at 0.160.0
ThreadForkParams.excludeTurns?: boolean        // non-experimental from 0.159.2; experimental-only at 0.150.1
```

A fork creates a **new thread**, which is what a person's fork of a session asks for; the undo is the cut above, which leaves the caller on its own thread. Sibling boundary fields on the same type are experimental: `beforeTurnId` (`#[experimental("thread/fork.beforeTurnId")]`, "Optional turn id to fork before, excluding that turn and all later turns. Cannot be combined with `last_turn_id`.") and `path`. `excludeTurns`, "return only thread metadata and live fork state without populating `thread.turns`", is in the default generation of both `thread/fork` and `thread/resume` at `0.159.2` and the pin.

### `thread/goal/*` — session goals

```
ThreadGoalSetParams      = { threadId: string, origin?: ThreadGoalMutationOrigin | null, objective?: string | null, status?: ThreadGoalStatus | null, tokenBudget?: number | null }
ThreadGoalClearParams    = { threadId: string, origin?: ThreadGoalMutationOrigin | null }
ThreadGoalMutationOrigin = "user" | "automatic"   // "Distinguishes explicit user actions from automatic goal lifecycle mutations."
```

Set / clear / get are native (`thread/goal/set`, `thread/goal/clear`, `thread/goal/get`); the wire also emits `thread/goal/updated` and `thread/goal/cleared` server notifications. All present at `0.160.0` and `0.161.0`.

**Only `origin: "user"` makes a goal the person's instruction** (**Generated schema** at `0.161.0`, where `origin` first appears on both requests; **Upstream source**, read at `rust-v0.161.0`). The generated doc comment on `origin` reads, verbatim: "Missing provenance does not supply user authorization." A `thread/goal/set` carrying an objective or a status, or a `thread/goal/clear`, with `origin: "user"` records a `user.goal` user message in the conversation's history before the goal changes, written to the conversation's file even when it is not loaded (`codex-rs/app-server/src/request_processors/thread_goal_processor.rs`, `thread_goal_user_context.rs`, `codex-rs/ext/goal/src/api.rs`). That message is kept through compaction (`codex-rs/core/src/compact.rs`), and Codex's automatic reviewer reads it as one of the person's own messages, which can authorize an action (`codex-rs/core/src/agent/control/user_authorization.rs`). With `origin` missing or `"automatic"` the goal changes and nothing is recorded. An objective whose JSON-quoted form is longer than 700 bytes is recorded whole as omitted, `user.goal.omitted` with the text `User set the goal: [objective omitted; exceeds the evidence limit].`, never cut short (`codex-rs/core/src/context/user_goal.rs`). The driver sends `origin: "user"` on both requests, because its goal is always the person's own `/goal`.

**A goal survives `thread/resume`, so nothing sets it again** (**Upstream source**, read at `rust-v0.161.0`). Codex keeps one goal per thread in a database of its own, `goals_1.sqlite` in its home, keyed by thread id (`codex-rs/state/src/sqlite.rs`, `codex-rs/state/goals_migrations/0001_thread_goals.sql`). A resume, of a loaded thread or a cold one, reads it back and answers with a `thread/goal/updated` snapshot, or `thread/goal/cleared` when the thread has none, which is the `thread/goal/cleared` the second-seat probe saw (`thread_lifecycle.rs` `send_thread_goal_snapshot_notification`, `thread_processor.rs`, `thread_goal_processor.rs` `emit_resume_goal_snapshot`). The goal extension puts an `active` goal's accounting back on resume (`codex-rs/ext/goal/src/extension.rs` `on_thread_resume`, `codex-rs/ext/goal/src/runtime.rs` `restore_after_resume`). The goal lives in the home's database and not in the rollout file, so a rollout copied into another home arrives without its goal, though its `user.goal` message is in the history. An ephemeral thread refuses goals (`thread_goal_processor.rs`).

### A rollout file resumes inside a different `CODEX_HOME`

**Binary probe, Verified at `0.155.1`** — recorded at its own build and not re-run at this pin; one live run on the authoring machine. A thread's rollout lives at `CODEX_HOME/sessions/<Y>/<M>/<D>/rollout-…-<thread id>.jsonl`. Copied — that one file, nothing else — into a **fresh** `CODEX_HOME` under the same dated path, it is **listed** by `thread/list` in that home and **loaded** by `thread/resume {threadId}` against the same thread id, with the thread's earlier turn present. **No database work is involved**: the file is the record the app-server reads, and nothing had to be written into a store to make it findable.

**What is not established.** A model **turn** on the resumed thread under the second home's *own* login was not run, so this grades the discovery-and-load leg only, as on the Claude leg ([`claude.md` §A conversation file resumes inside a different, signed-out config home](claude.md#a-conversation-file-resumes-inside-a-different-signed-out-config-home)).


### `turn/start` — per-turn overrides

Codex accepts per-turn overrides where several Claude equivalents are per-session. The default-generated `v2/TurnStartParams.ts` at `0.160.0` carries `threadId`, `input`, and the optional-nullable `disabledPluginIds`, `clientUserMessageId`, `turnTrigger`, `toolOutput`, and the overrides `cwd`, `approvalPolicy`, `approvalsReviewer`, `sandboxPolicy`, `model`, `serviceTier`, `serviceTierForTurn`, `effort`, `summary`, `personality`, `outputSchema` (a JSON Schema constraining the final assistant message — the structured-output surface). Against `0.150.1` it gained four members: `disabledPluginIds` ("Replace this thread's disabled plugin IDs. Omitted/null preserves the list; [] clears it."), `turnTrigger` ("Optional source classification for the caller that starts this turn. Ignored when this request steers an already-active turn."), `toolOutput`, and `serviceTierForTurn` (see [Output speed](#output-speed--a-service-tier-surface-with-no-method-level-axis)). `personality` is now marked "@deprecated `friendly` and `pragmatic` no longer select a style. Changing this does not rewrite the thread's existing instructions." Every override but `serviceTierForTurn` is described as holding "for this turn and subsequent turns".

The posture caveat was stated on the method's own README entry at `rust-v0.150.1`, verbatim: "Prefer experimental `permissions` profile selection by id for permission overrides; the legacy `sandboxPolicy` field is still accepted but cannot be combined with `permissions`." The README at `rust-v0.160.0` no longer carries a per-method reference, and the experimental binding still says the same thing from the other side.

**Read that together with the generated shape, because they say different things.** The preferred field, `permissions`, is **not present in the default-generated `TurnStartParams` at all** — it appears only under `--experimental`, where its own doc comment reads: "Select a named permissions profile id for this turn and subsequent turns. Cannot be combined with `sandboxPolicy`." This is **field-level** gating on a method that is not itself experimental: `TurnStartParams` is one of the types deriving `ExperimentalApi`, so the method stays in the default surface while individual fields are stripped from it — at `0.160.0` those are `responsesapiClientMetadata`, `additionalContext`, `environments`, `runtimeWorkspaceRoots`, `permissions`, `collaborationMode`, `multiAgentMode` and the new `cyberAccessProgram`. So at the pin the only per-turn posture override a default connection can send is the one the vendor calls legacy. `permissionProfile/list` was labeled **beta** in the `rust-v0.150.1` README.

**On a connection that negotiated `experimentalApi`, `permissions` behaves as its doc comment says** (**Binary probe**, **Verified at `0.156.0`**, recorded at its own build and not re-run at this pin):

- **A default connection refuses every selection path by name** (`-32600`): `thread/start.permissions requires experimentalApi capability`, and the same for `turn/start.permissions` and `thread/settings/update`.
- **`permissionProfile/list {cwd}`** answers the same on both connections: the built-in `:read-only`, `:workspace` and `:danger-full-access` and every named `[permissions.<name>]` profile.
- **A `turn/start` field is a thread setting.** `permissions: ":read-only"` on a `turn/start` refuses every write on that turn and on every later one until a `turn/start` or `thread/settings/update` names another profile; a turn with no `permissions` keeps it, and a thread resumed in a new service process runs under the last profile set. `collaborationMode` persists the same way. `turn/start` and `thread/settings/update` build the same thread-settings override; `thread/settings/update` answers `{}` when it has only queued the change, so its effect is read from the `thread/settings/updated` that follows; at `rust-v0.161.0` it still queues the change with no reply channel and answers `{}` (`codex-rs/app-server/src/request_processors/turn_processor.rs`, **Upstream source**).
- **The active profile reads back** as `activePermissionProfile {id, extends}` on the `thread/start` and `thread/resume` replies and on every `thread/settings/updated`, which fires on a turn whose `turn/start` changes a setting and after a `thread/settings/update`, and not on a turn that changes nothing. `thread/read` and `turn/started` carry no posture field, and the legacy `sandbox` view never shows a named profile's read-only folders, so only `activePermissionProfile` identifies the profile.
- **`sandboxPolicy` wipes the named profile.** A `turn/start` carrying `sandboxPolicy` alone is accepted and enforced, but `activePermissionProfile` becomes `null` on `thread/settings/updated` and `thread/resume` alike, and the profile's read-only folders drop until a `turn/start` names the profile again. The two sent together are refused with `-32600`, whose message reads ``"`permissions` cannot be combined with `sandboxPolicy`"``.
- **Plan mode locks nothing.** The plan `collaborationMode` changes the prompt, not the tools: a plan turn offers the model the same tools a build turn does, so a plan turn is read-only only through its profile. At an asking approval policy the read-only profile is not a wall: an escalated command raises `item/commandExecution/requestApproval` and a patch raises `item/fileChange/requestApproval`, and either, accepted, writes.

The presence of `approvalsReviewer` here is why the driver sets it explicitly from the session's permission level (see below).

#### Command-shaped input is delivered verbatim on this transport

**The `app-server` performs no client-side command parsing of `turn/start` input** (**Binary probe**, **Verified** at `0.150.1` by driving `codex app-server --listen stdio://` through `initialize` → `initialized` → `thread/start` → `turn/start` on a default, non-experimental connection, and again at `0.160.0` over `codex app-server` on stdio against a scratch `CODEX_HOME` with no login, sending `/status`). A first `input` element whose text begins with `/` is echoed back **byte-identical** — leading `/` intact — as a `userMessage` `ThreadItem`, and a real turn is dispatched on it (`turn/started`, then the `item/started` + `item/completed` pair, then `turn/completed`).

This is worth measuring per transport rather than assuming per vendor: the other pinned provider does the opposite on its own programmatic input surface, intercepting the same text client-side so it never reaches the model — see [the Claude reference](claude.md#client-side-command-interception-on-the-programmatic-input-surface).

**The isolation probe is what makes this decisive.** A nonexistent name (`/zzqnotarealcommand …`) would prove only that the app-server does not recognize that particular string. The probe therefore also sent `/status` — a **real** command of this CLI's interactive frontend — and the app-server echoed it verbatim as a `userMessage` and started a turn on it too. The absence of interception is therefore a property of this transport, not an artifact of picking an unknown name.

**Turn-evidence discriminants**, for a consumer that must decide whether input reached the model — all typed fields of the generated protocol, never message prose:

- `ThreadItem` discriminates the person's echo from model output by its own `type` tag: `userMessage` is the echo of what was sent, `agentMessage` is model output. The union carries 19 variants at this pin; the one added since `0.150.1` is `functionCallOutput {id, name, namespace, output}`, and `agentMessage` gained a nullable `questions` list.
- `TurnStatus` is `completed | interrupted | failed | inProgress`, delivered on `turn/completed` — the only terminal-turn notification in the `ServerNotification` root (83 arms at `0.160.0`, 84 at `0.161.0`) (there is no `turn/failed` and no `turn/interrupted`). `Turn.error` is now described as "Error associated with a failed or interrupted turn", where `0.150.1` said it was populated only on a failed one.
- A failed turn carries a typed `TurnError { message: string, codexErrorInfo: CodexErrorInfo | null, additionalDetails: string | null, misalignment: MisalignmentErrorDetails | null }` — every member present, the last three nullable — `misalignment` being the "public explanation and continuation instruction for a misalignment block" added since `0.150.1`, and `CodexErrorInfo` is itself a typed enum: `contextWindowExceeded`, `sessionBudgetExceeded`, `usageLimitExceeded`, `rateLimitExceeded`, `flexUnavailable`, `serverOverloaded`, `cyberPolicy`, `misalignmentPolicyViolation`, `tooManyDenials`, `internalServerError`, `unauthorized`, `badRequest`, `threadRollbackFailed`, `sandboxError`, `other`, plus object-shaped arms (`httpConnectionFailed`, `responseStreamConnectionFailed`, `responseStreamDisconnected`, `responseTooManyFailedAttempts`, each carrying `httpStatusCode`, and `activeTurnNotSteerable {turnKind}`). `rateLimitExceeded`, `flexUnavailable` and `tooManyDenials` are new since `0.150.1`; `threadRollbackFailed` stayed after `thread/rollback` itself left. **At `0.161.0` the union is declared open** (**Generated schema** and **Upstream source**, `rust-v0.161.0`): the generated TypeScript ends `| "other" | string | { [key: string]: unknown }`, and the JSON Schema's arms are an `anyOf` whose last arm is `{type: ["string", "object"]}`, so an arm a newer server sends arrives as a plain string or object rather than failing to decode. A consumer types `codexErrorInfo` to take an unknown string or object and matches the arms it acts on, `contextWindowExceeded` among them, by name. So "the turn failed" is readable without parsing prose, and is distinguishable from "the turn produced nothing".

**What this probe did not establish — recorded rather than papered over.** Neither pass reached the model: at `0.150.1` the probing account's quota was exhausted, so each turn settled `failed` carrying `codexErrorInfo: "usageLimitExceeded"` and a dated reset, and at `0.160.0` the scratch home had no login, so the turn settled `failed` with `codexErrorInfo: {httpConnectionFailed: {httpStatusCode: 401}}` after five reconnect attempts on the websocket and five more over HTTPS. What is **Verified** is everything upstream of the model call — that the app-server accepts command-shaped text, echoes it verbatim as the person's item, and dispatches a turn on it. That the **model** then receives those bytes unaltered is **Documented**, not Verified, on this transport: it follows from the echoed item being the model-visible history entry, but no probe here observed a model reply to command-shaped input. The pre-existing verbatim-delivery evidence for this provider is from `codex exec`, a **different frontend** — which is precisely why this transport was probed separately.

**Two notification methods reached a default connection in the same pass and are worth a consumer's attention:** `remoteControl/status/changed` and `thread/status/changed`, both delivered with `capabilities.experimentalApi = false`, at `0.150.1` and again at `0.160.0`. `remoteControl/status/changed` arrived right after `initialized`, before any thread; `thread/status/changed` framed turn dispatch. A driver whose inbound-method census was transcribed from a narrower reading of the roots routes both to its unknown-method path.

**One connection-scoped frame arrives beside the turn-scoped one.** A top-level `{"method":"error"}` notification carried the same `message` + `codexErrorInfo` payload that `turn/completed`'s `turn.error` then carried. Both were observed at `0.150.1` and at `0.160.0`, where each reconnect attempt also sent its own `error` with `willRetry: true` before the final one with `willRetry: false`, so a consumer must not treat the top-level `error` as the turn's only failure signal, nor as a duplicate it may drop before the turn settles.

`turn/steer` is a first-class, non-experimental method at `0.160.0` and at `0.159.2` (the steer capability is graduated always-on, its feature flag removed).

### `thread/start.dynamicTools` — a client-served tool, and the call that comes back

**Binary probe, Verified at `0.155.1`** — recorded at its own build and not re-run at this pin; one live authenticated run on the authoring machine, driving `codex app-server` over stdio from a purpose-written JSON-RPC host with no TUI anywhere in the path.

`thread/start` accepts a `dynamicTools` array from that ordinary programmatic client, each entry a namespace spec:

```
dynamicTools: [{ type: "namespace", name: string, description: string, tools: [{ type: "function", name: string, description: string, inputSchema: JsonValue }] }]
```

The thread established and the model called the declared tool on the first turn. **The call arrives as the server request `item/tool/call`**, carrying `threadId`, `turnId`, `callId`, `namespace`, `tool`, and the model's `arguments` — so a tool the client serves is answered on the same request channel an approval is answered on, not on a notification. The host answered `{contentItems: [{type: "inputText", text}], success: true}` and the model **read that text back in its own final answer**, which is what establishes the reply shape end to end rather than only that the reply was accepted.

One further leg came from the same run: `turn/steer` sent while that tool call was still outstanding, carrying the live `expectedTurnId`, replied with that same `turnId`, and the steered text arrived as a `userMessage` item **on that same turn** and was honored in the final answer. So a message handed to a busy conversation joins the turn already running rather than waiting for the next one.

**What is not established.** The connection negotiated `experimentalApi: true`, so this run does **not** show whether `dynamicTools` is accepted on a **default** connection at runtime. The generation points the other way: at `0.160.0` and `0.159.2` `dynamicTools` is absent from the default `ThreadStartParams` and present only under `--experimental`, the same field-level gating `turn/start` shows ([The experimental gate](#the-experimental-gate--a-runtime-filter-not-a-schema-filter), [`turn/start`](#turnstart--per-turn-overrides)), so a consumer that needs the default surface measures it there. Nothing was varied about how many namespaces or tools one thread may carry, and no refusal shape for a malformed spec was probed.

**Why it matters.** It records a surface this project does not use for its own tools: the daemon's tools, the session tools among them, reach both providers on the daemon's shared MCP tool server `sidekicks`, through one `url` entry per session, never through `dynamicTools` ([Spec-014 §Sessions Talking To Each Other](../../specs/014-multi-agent-orchestration.md#sessions-talking-to-each-other), [One tool server for every conversation, and a call that waits](#one-tool-server-for-every-conversation-and-a-call-that-waits)).

### This provider publishes no turn cap

**Upstream source, Verified, read at `rust-v0.154.0`** — recorded at the release it was read at and not re-read at this pin.

A tree-wide read of `codex-rs` for `max_turns`, `max_iterations`, `turn_limit`, `max_tool_calls`, `maxTurns` and `maxIterations` across `*.rs`, `*.toml` and `*.ts` lands in **one** file, and it is a TUI file where `turn_limit` is the row limit of a history-reading tool (`DEFAULT_READ_TURN_LIMIT` / `MAX_READ_TURN_LIMIT`). There is **no agentic-loop turn cap** in `core`, `config`, `agent-roles`, or the app-server protocol. `TurnStartParams` carries no field for one — its members are the thread id, the client message id, the input, the turn trigger, tool output, additional context, environments, cwd, workspace roots, and the posture / model / effort / summary / personality / output-schema overrides, and no iteration budget among them; the `0.160.0` generation's `TurnStartParams`, default and `--experimental`, carries none either. The agent-role file cannot hold one either: its TOML is `deny_unknown_fields`, so a stray `max_turns` key drops the whole role rather than setting a bound. The nearest native thing is a **token** budget (`features.rollout_budget`), shared across one root thread's whole tree with no per-child key, which is a different quantity and not a turn count.

**Why it matters.** A step bound on this leg is therefore the daemon's **own** count of a turn's steps, reset at each turn start, with `turn/interrupt` sent at the number — never a flag passed through to the provider ([Spec-003 §The Step Bound On A Turn](../../specs/003-queue-steer-pause-resume.md#the-step-bound-on-a-turn)).

### The shared `app-server` a terminal `codex` joins

**Two passes, each paragraph naming its own.** **Binary probe, Verified at `0.155.1`**: one pass on the authoring machine, 2026-09-21, against the person's real login, every session in a throwaway folder outside any repository; the socket and lock names were read as a string block in that build's `app-server-transport/src/transport/mod.rs` module. **Binary probe, Verified at `0.161.0`**: two passes on 2026-10-07, in throwaway Codex folders with a fake API key and a local mock model server, so no model turn was billed, beside **Upstream source** read at `rust-v0.161.0` (commit `979011409`). Times are the machine's, America/New_York.

**One socket per Codex home, not per folder.** The join target is `<CODEX_HOME>/app-server-control/app-server-control.sock`, beside `app-server-startup.lock`; `codex app-server daemon version` names the same path in its own output and prints `{"status":"running", … "appServerVersion":"0.155.1"}` while one is up. **The control socket is a websocket**: an HTTP upgrade written to it answered `HTTP/1.1 101 Switching Protocols` with `upgrade: websocket`, while a newline-terminated JSON-RPC `initialize` on the same socket answered nothing at all. A client of this service speaks websocket or it speaks to nobody. At `0.161.0` every server started with `--listen unix://<path>`, the default path included, binds its real socket at `/tmp/codex-daemon-<uid>/<sha256 of the path>`, with `/tmp` resolved first (so `/private/tmp/…` on macOS), makes `<path>` a link to it, and holds `<that socket>.lock` while it sets the socket up (`start_control_socket_acceptor`, `protected_socket_path` and `acquire_app_server_startup_lock` in `codex-rs/app-server-transport/src/transport/unix_socket.rs`; `shared_daemon_socket_directory` in `codex-rs/uds/src/daemon_directory.rs`). So `app-server-control.sock` is a link, and a server started on a path of its own makes that path a link to its own socket. A server removes on exit only a link that points at its own socket (`ControlSocketFileGuard`'s `Drop`), and at start it clears a dead link only when the link is its own default one, pointing where that same path's socket would be (`prepare_control_socket_path`).

**Which invocations join it, proved by socket endpoint rather than by inference.** At `0.155.1` joining was read as a match between an accepted socket address on the service's side and the peer of one of the terminal process's own descriptors. A plain `codex` joined — typed in the folder the service was started in **and** in a different folder, so the join follows the Codex home rather than the working directory — and so did `codex -m <model>`. `codex -c <key>=<value>` did **not** join, `codex -p <profile>` did **not**, and `codex exec` did not: the service's holder count did not move across a whole `exec` run and no descriptor matched. At `0.161.0` (source) `-c features.<name>=<bool>` for an allowlisted feature switch and `--worktree` still join, while `--no-daemon`, `--oss`, `--profile`, `CODEX_EXEC_SERVER_URL`, `--strict-config` and `--dangerously-bypass-hook-trust` run alone (`exclusion` and `config_exclusion` in `codex-rs/tui/src/daemon_startup.rs`).

**A plain `codex` starts Codex's managed daemon when nothing answers** (`0.161.0`). `daemon_auto_start` is stable and on by default from `0.157.0` (the `DaemonAutoStart` entry of `FEATURES` in `codex-rs/features/src/lib.rs`). A plain `codex` takes `<CODEX_HOME>/app-server-daemon/daemon.lock`, waiting up to 375 s for it (`run_main_inner` in `codex-rs/tui/src/startup_orchestration.rs`; `start_with_features` in `codex-rs/app-server-daemon/src/launch.rs`; `OPERATION_LOCK_TIMEOUT` and `Daemon::acquire_operation_lock` in `codex-rs/app-server-daemon/src/lib.rs`), probes the socket for 2 s (`CONTROL_SOCKET_RESPONSE_TIMEOUT` and `probe` in `codex-rs/app-server-daemon/src/client.rs`) and joins whatever answers, marking it as a server Codex does not manage (`Daemon::start`). When nothing answers it copies the CLI package into `<CODEX_HOME>/packages/app-server-daemon/` (`prepare_from_package` in `codex-rs/app-server-daemon/src/prepare_install.rs`), starts `app-server --listen unix:// --analytics-default-enabled` with only `-c features.<name>=<bool>` switches (`PidBackend::command_args` in `codex-rs/app-server-daemon/src/backend/pid.rs`; `PidBackend::start_inner` in `backend/pid_start.rs`), and starts an updater (`Daemon::start`); both are detached from the terminal (`PidBackend::start_inner`). Measured: even signed out, a plain `codex` started the server and the updater 3–4 s after launch, before the sign-in screen and before any input, and both moved under launchd when the terminal quit. **Neither exits when idle**: the server stops only on a signal or when a single-client stdio connection closes (the `stdio_connection_closed` exit in `run_main_with_transport_options`, `codex-rs/app-server/src/lib.rs`), and the updater only on a signal, auto-update off or a handoff (`run_with_http` in `codex-rs/app-server-daemon/src/update_loop.rs`); measured, both lived 20 min 25 s with no client. The updater checks first after 5 minutes and then hourly (`INITIAL_UPDATE_DELAY`; `DEFAULT_UPDATE_INTERVAL_MINUTES` in `codex-rs/app-server-daemon/src/settings.rs`), installs into the daemon's own copy and never the person's CLI (`run_installer_script`), then restarts the server with a 60 s grace before forcing it (`Daemon::try_restart_if_running`; `DEFAULT_SHUTDOWN_GRACE_SECONDS`); it does not exit when the server stops (measured: `codex app-server daemon stop` took 87 ms with no client and left the updater running) and is not started again after a reboot until the next plain `codex` (`codex-rs/app-server-daemon/README.md`). Codex's own `daemon` commands refuse to stop, restart or update a server they did not start (`Daemon::restart_with_settings`, `Daemon::try_restart_if_running` and `Daemon::stop`), and its README calls those commands experimental. On the authoring machine the managed daemon took 45–48 MB and its updater 16–20 MB, and a server asks for the model list every 4 min 30 s whoever started it (`MODELS_REFRESH_INTERVAL` in `codex-rs/app-server/src/models_refresh_worker.rs`): 40 requests in 3 hours.

**A second server on the socket is refused, and one of ours on its own path joins cleanly** (`0.161.0`). `codex app-server --listen` on a socket where anything answers fails in 29 ms, exit 1, with `Error: app-server control socket is already in use at …/app-server-control/app-server-control.sock` (`prepare_control_socket_path`), the managed daemon included. `codex app-server --listen unix://<path>` was listening 67 ms after start and starts no updater; a terminal joined it in 1.1 s with no package copy, and `daemon version` reported `backend: null`.

**How the service stops, and what a joined terminal sees** (`0.161.0`).

- **`SIGTERM` drains.** New turns are refused with `-32600` `Server is draining; retry after reconnecting`, a running turn finishes and a second signal forces the exit (`shutdown_signal` and `ShutdownState` in `codex-rs/app-server/src/lib.rs`; `server_draining_error` in `codex-rs/app-server/src/error_code.rs`). Measured: mid-reply the server kept streaming to the terminal for 12–16 s and then exited; with no reply running it exited in 110 ms. Started with the hidden `--managed-daemon` flag, it saves its loaded conversations and reloads them when it starts again (`start_recovery` in `codex-rs/app-server/src/daemon_thread_recovery.rs`, called from `run_main_with_transport_options`), and the terminal rejoined with the conversation intact.
- **`SIGKILL` loses the reply in flight.** The partly streamed text vanished and the turn showed `Conversation interrupted`; earlier messages stayed.
- **A joined terminal reconnects for 120 s, then never.** It showed `Reconnecting to server…` within 10 ms of the kill, kept the conversation on screen, and tried at 0, 1, 2 and 4 s and then every 8 s, with no random spread, until 120 s (`reconnect` in `codex-rs/tui/src/app/reconnect.rs`), only on the same socket and never starting a daemon itself (`reconnect`); after reconnecting it resends its unsent queue and holds the messages it is unsure about (the module's own comment, and `finish_reconnect`). Measured: with the server back after 20 s the terminal rejoined 3.3 s later and the next message worked; at 120.3 s it showed `Reconnect failed — check the endpoint, then relaunch` and never rejoined, even when the server came back at 135 s.
- **The start lock holds a new terminal back.** With `daemon.lock` held while no server answered, a new `codex` showed a working typing box and waited, and joined the server 0.7 s after the lock was released. Held for 375.4 s, it exited 1 with `timed out waiting for daemon operation lock … To work without the background server, rerun the same command with --no-daemon`.
- **A slow client is dropped.** A client whose outbound queue fills, 32,768 messages on the websocket, is disconnected (`send_message_to_connection` in `codex-rs/app-server/src/transport.rs`; `WEBSOCKET_OUTBOUND_CHANNEL_CAPACITY` in `codex-rs/app-server-transport/src/transport/websocket.rs`), and an overloaded server answers `-32001`.

**A terminal checks four feature switches when it starts, never on a reconnect** (`0.161.0`). It compares `api_key_model_discovery`, `code_mode_host`, `auth_elicitation` and `mcp_oauth_refresh_coordination` with the server's (`SERVER_FEATURES` and `compatibility_warning` in `daemon_startup.rs`; checked only at start, by `run_main_inner`'s `daemon_recovery::check`). On a mismatch it shows a menu: run without the daemon this time, restart, or cancel (`recovery_view` in `codex-rs/tui/src/daemon_recovery.rs`). Measured with a `0.160.1` server and a `0.161.0` terminal: `Background server has incompatible feature settings` and `This session requires api_key_model_discovery to be enabled`; `Restart` was grayed out with `This server is not managed by Codex.`, `Cancel` exits 1, and `Run without daemon this time` runs a private server no other client can see. Only those four switches are compared, so a version gap where none of their defaults moved passes unnoticed.

**Terminals move to a second service without a message** (`0.161.0`, measured on one version). A second server started on a path of its own (`--listen unix://<path>`), the Codex home's socket link swapped to it in one step: new terminals landed on it at once. The old server, stopped mid-reply, finished the reply, and its terminal moved to the new server with no reconnect message, the next message working; the old server left the link alone on exit. Once the new server stopped, the link pointed at nothing and a fresh start failed with `File exists (os error 17)`, which a plain `codex` meets too (source).

**The work survives even when the attachment does not.** `codex resume <thread id> --remote unix://<sock>` against the restarted service redrew both earlier turns, marked the turn that was in flight `Conversation interrupted - tell the model what to do differently.`, and answered a fact planted before the kill. So a stranded session is recovered by thread id, and only the running process's attachment is lost. A session that never joined — one started with `-p` — went through both kills untouched.

**What joining costs.** Real memory, read with `footprint` beside RSS: the service with one joined client **40 MB**, a joined terminal session **17 MB**, and the same session running alone **58 MB**. A terminal session is therefore ~41 MB cheaper joined than standalone.

**What a process-start `-c` reaches.** A `-c` given when the service starts applies to every conversation the service holds, so a consumer puts there only what every conversation shares, and everything else at `thread/start`. One service also has one notification opt-out list, `initialize.capabilities.optOutNotificationMethods`, and one process environment for every conversation, so the opt-out list is the union of what every conversation needs and events are routed by the `threadId` they carry. A fork loads into whichever service answered the fork. The unload delay is `thread_unload_delay_secs`, 60 s by Codex's default; this project starts every service with `-c thread_unload_delay_secs=5`. On Windows the control socket's path must fit within 108 bytes. A `model/list` that answers `-32600` asking for a restart is met by restarting the service and resuming every conversation in it. Every service this project starts on an account home it manages carries `-c features.browser_use=false`, so Codex's own browser tool stays off, and `-c features.plugins=false`, which stops the service's plugin catalog sync (about 88 MB). **Binary probe, Verified at `0.156.0`**, recorded at its own build.

**What this pass did not establish.** The turn-level legs were driven through `codex --remote unix://<sock>`, which joins the very same service process — the endpoint match says so — because a plain `codex` in a fresh folder raises the interactive directory-trust prompt and answering it writes a trust row into the person's own `config.toml`, which this pass would not modify. So the auto-join reconnect path is not proven identical to the `--remote` one, and that CLI has its own vocabulary for a remote session. At `0.161.0`, read from source only: a terminal reconnecting to a newer server skips the feature check; not seen: a new terminal joining a server that is draining, and what macOS does to the managed daemon at logout. Whether a joined terminal session is visible to a **second** client of the same service is answered in the section below.

**Why it matters.** It is the whole of how a Codex session the person typed in a terminal is reachable at all, this provider giving a session no address of its own ([Spec-014 §Sessions Talking To Each Other](../../specs/014-multi-agent-orchestration.md#sessions-talking-to-each-other)).

### A second seat on the shared service

**Binary probe, Verified at `0.155.1`** — the night of 2026-09-21, the same machine and login as the pass above; a `codex app-server --listen unix://<path>` started by hand on a scratch socket, a websocket client written for the pass holding one seat, and terminal sessions joined with `codex --remote unix://<path>` under a pseudo-terminal, every turn on `gpt-5.6-luna`. This is the leg the pass above left open — whether a joined terminal session is visible to a second client of the same service — and the answer is four times yes, with three things a daemon has to carry.

**The seat sees a joined terminal's thread at once, in one of the two listings.** `thread/loaded/list` returned the terminal's thread id the moment the terminal connected, before it had run anything. `thread/list` did not: filtered on the terminal's folder it was empty until the person's first turn had gone through, and then carried the thread with its `preview`, `name` and `status`. A directory that wants to know a terminal session is there reads the loaded list; one that wants its metadata reads `thread/list` and sees nothing until the person has said something.

**A thread's events reach the seat only once the seat has resumed it; lifecycle notifications reach every seat unasked.** Through the terminal's first turn the seat received only `thread/status/changed`, `thread/name/updated` and a `thread/started` / `thread/closed` pair for the provider's own ephemeral title thread — no `turn/*`, no `item/*`, no `thread/tokenUsage/updated`. After one `thread/resume {threadId, excludeTurns: true}` from the seat, answered in 6 ms, the terminal's next turn arrived in full: `turn/started`, the `item/*` pairs for the user message, the reasoning and the agent message, `item/agentMessage/delta`, `thread/tokenUsage/updated`, `account/rateLimits/updated`, `turn/completed`. The resume did not disturb the terminal — its screen was unchanged across the call and it ran that turn normally — so on this build `thread/resume` is the subscribe verb and per-thread delivery is per seat. The resume also emitted a `thread/goal/cleared` for the thread, with no goal set and nothing visible in the terminal.

**A turn started from the seat runs, and the terminal shows both sides.** `turn/start {threadId, input: [{type: "text", text, text_elements: []}]}` answered `{turn: {id, status: "inProgress"}}` in 4 ms, the whole event stream followed on the seat, the model answered, and the terminal painted the injected line as an ordinary user message with the reply under it. `text_elements: []` is required on the text input variant.

**A steer folds into the running turn, and so does a `turn/start` on a busy thread.** `turn/steer {threadId, input, expectedTurnId}` sent the instant the terminal's own turn started was accepted with the same turn id; the model finished its first answer, the steered user message appeared inside that same turn, a second answer followed, and one `turn/completed` closed it. A `turn/start` sent onto the busy thread did the same and returned the running turn's id rather than an error — the generated type says as much, `turnTrigger` being ignored when the request steers an active turn. So a daemon does not pick a verb by whether a turn is running; `turn/steer` earns its place through `expectedTurnId`, the only race-free way to say "fold this into the turn I saw" and the only way to learn that the turn you meant has ended.

**A terminal's quit sends nothing, and the service unloads the conversation one delay later once nobody holds it** (**Binary probe, Verified at `0.156.0`**). While a seat is subscribed, a quit sends no notification: the thread stays in `thread/loaded/list`, `thread/read` reads `idle`, and a `turn/start` on it runs with no terminal anywhere. Once neither the terminal nor any seat holds the conversation and no turn runs, the service sends `thread/closed` (with `thread/status/changed` to `notLoaded`) one unload delay later — `thread_unload_delay_secs`, 60 s by default. **A `thread/closed` can be stale**: one queued by the conversation's earlier runtime can arrive after the same conversation has been resumed, and Codex's own client confirms the conversation's status with `thread/read` before it acts on a close (release note, `0.157.0`, which fixed that client). A terminal closed mid-turn leaves the turn running in the service to its end, and the unload follows one delay after. **An unload kills a command still running** in that conversation, so a seat reads `thread/backgroundTerminals/list` before it lets a conversation go and holds it while the list shows a command; `thread/status/changed` to `idle` reaches a seat that is not subscribed, which is how a seat learns a turn ended in a conversation it does not hold. A seat resuming a conversation for a send waits for the reload before writing — up to 0.9 s for the largest conversations measured — and resumes with `excludeTurns: true`, reading history by page; in the `0.161.0` generation `thread/items/list` also pages from a known item, its `cursor` taking an opaque string or `{type: "item", itemId}`, an exclusive anchor that needs a non-empty `turnId` and reads after the item ascending (the default) or before it descending, continued with the string cursor the reply returns. A terminal's own conversation is told from its helper conversations by `threadSource: "user"` with `ephemeral: false`, never by `source` or `originator`.

**A joined terminal runs its commands in the folder the person typed `codex` in** (**Binary probe, Verified at `0.156.0`**). `thread/started` names that folder as the conversation's `cwd`, its `environments[0].cwd` and its `runtimeWorkspaceRoots`, whatever folder the service itself runs in, and a turn asking the model to run `pwd` answers it. At `0.155.1` the thread's `cwd` was the service's own working directory; at `0.156.0` it is the joining client's folder, so the folder the daemon starts a service in does not decide where a person's commands run.

**The first seat's name is stamped on every thread the service creates afterwards.** The terminal's thread recorded the probe's own `clientInfo.name` as its `originator`, and a second seat with a different name plus a second terminal still produced a thread whose originator was the first seat's. A daemon holding the first seat rewrites the recorded attribution of the person's own terminal sessions, which `thread/list`'s `originators` filter reads.

**Small facts a client of this service needs.** A client offering `permessage-deflate` gets `101 Switching Protocols` and then a dead socket (close 1006, no frames); `perMessageDeflate: false` fixes it. `codex app-server --listen` refuses a socket directory that is a symlink. Every first turn starts an ephemeral title-generation thread (`ephemeral: true`, `threadSource: "system"`) that `thread/closed` retires a minute later, so a directory built on the broadcast drops those on `ephemeral`.

**What these passes did not establish.** Where an approval request goes when two seats hold one thread — every turn here was a one-word answer under the person's own full-access configuration, so the case that decides whether the seat is safe to hold beside a person's terminal is unmeasured. Whether "first `initialize` wins" is the whole attribution rule, the daemon's seat having always connected first here. A steer arriving mid-stream, or between the model's last token and `turn/completed`, where a real `expectedTurnId` race lives. Whether a seat that never resumed a thread starts receiving its events once the thread has a completed turn behind it — the measured order was one turn without events, a resume, then a turn with all of them. On native Windows, the service's listen form, the plain `codex` join and `codex resume`.

**Binary probe, Verified at `0.161.0`**: one pass on 2026-10-07, in a throwaway standalone install with `HOME`, `CODEX_HOME` and `CODEX_INSTALL_DIR` pointed at scratch, beside **Upstream source** read at `rust-v0.161.0` and the live installer, `https://chatgpt.com/codex/install.sh`.

The installer puts a new release beside the old one, swaps `current` in one rename (`update_current_link`), and writes `<CODEX_HOME>/packages/standalone/auto-update-version` only when the release it installs is `latest`, removing it when a version was named; it deletes only `.staging.*` leftovers and never an old release (`cleanup_stale_install_artifacts`). The newest release is what `resolve_release_from_releases` reads, `https://releases.openai.com/codex/channels/latest`, whose `tag_name` names it; measured at 5:52 PM it read `rust-v0.161.0` in 52,514 bytes, 9,079 compressed, and a request carrying the last `ETag` was answered `304` with 935 bytes of headers. A Homebrew install follows its cask, `https://formulae.brew.sh/api/cask/codex.json`, which read `0.161.0`.

**`codex update` picks the update from its own path.** It runs the command for the install method it works out from where its executable sits (`run_update_command` in `codex-rs/cli/src/main.rs`; `install_method_from_exe` and `standalone_install_method` in `codex-rs/install-context/src/lib.rs`; `UpdateAction::from_install_context` and `UpdateAction::command_args` in `codex-rs/tui/src/update_action.rs`): a standalone install runs `curl -fsSL https://chatgpt.com/codex/install.sh | CODEX_NON_INTERACTIVE=1 sh` (`install.ps1` on Windows), an npm, pnpm or bun install a global install of `@openai/codex`, and a Homebrew install `brew upgrade --cask codex`; anything else exits 1 with `Could not detect the Codex installation method`. No opt-out applies to the command, and under `CODEX_NON_INTERACTIVE` the installer answers no to its own questions, `Start Codex now?` among them (`prompt_yes_no` in `install.sh`).

### `thread/fork` — a throwaway copy, and where token usage arrives

**Binary probe, Verified at `0.155.1`** — recorded at its own build and not re-run at this pin; one live authenticated run driving `codex app-server` over stdio, 2026-09-21.

The accepted shape is `thread/fork {threadId, ephemeral: true, excludeTurns: true, sandbox, approvalPolicy}`. The reply carries a new thread id and `forkedFromId` naming the live thread, and **the fork is absent from `thread/list`** while the live thread is still listed — so a throwaway copy leaves no session behind. Two refusals bound the shape, both `-32600`: `deferGoalContinuation` sent beside `ephemeral` is refused with `deferGoalContinuation` cannot be combined with `ephemeral`, and an ephemeral fork without `excludeTurns` is refused with `ephemeral paginated thread/fork requires excludeTurns: true`. The live thread was unaffected: re-asked immediately after the fork it answered from its own history in about 2 s. Not tried: `deferGoalContinuation` on a **non**-ephemeral fork.

**Token usage arrives on one notification and carries no money.** `thread/tokenUsage/updated` carries `tokenUsage.last` and `tokenUsage.total` — each `{totalTokens, inputTokens, cachedInputTokens, cacheWriteInputTokens, outputTokens, reasoningOutputTokens}` — plus `modelContextWindow`. It is **not** carried on `turn/completed`, and **no dollar figure exists anywhere on this surface**: there is no equivalent of the other provider's own cost field, so a consumer that wants money for a Codex run computes it or does without ([`claude.md` §`get_usage`](claude.md#get_usage-is-experimental--three-separate-facts-do-not-collapse-them)).

**How a request is priced from this frame.** `inputTokens` already holds the cached and cache-write tokens, so the uncached part of a request is `inputTokens − cachedInputTokens − cacheWriteInputTokens`. A request is priced by its own size at its model's standard, long-context (input past 272K on that request), cache-write and Fast rates, read from the daemon's live copy of LiteLLM's MIT-licensed price list, matched by exact model id and never by family, once, at completion, and never from fixed multipliers, and a turn is the sum of its requests; a frame whose `total` did not grow is a repeat and is not priced ([Spec-004 §Required Behavior](../../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-014 §Cost Derivation And Absent-Cost Semantics](../../specs/014-multi-agent-orchestration.md#cost-derivation-and-absent-cost-semantics)).

**Why it matters.** It is the Codex leg of composing a hand-over brief on a throwaway copy of a session rather than on the live one ([Spec-004 §The hand-over brief is the floor, and it is visibly a floor](../../specs/004-provider-driver-contract-and-capabilities.md#the-hand-over-brief-is-the-floor-and-it-is-visibly-a-floor)), and of the side question: `thread/fork {ephemeral: true, excludeTurns: true, permissions: ":read-only", approvalPolicy: "never"}` with no goal-continuation flag and no `lastTurnId`, whose reply names `:read-only` in `activePermissionProfile` and whose cost is its own `last` figure. The fork takes `permissions` rather than `sandbox`: `sandbox: "read-only"` also refuses writes, but its reply names no profile (`activePermissionProfile: null`), and the two together are refused with `-32600`; the parent keeps its own profile and approval policy (**Binary probe**, **Verified at `0.156.0`**, above this file's pin).

### Hooks passed at the service's start, and their trust

**Binary probe, Verified at `0.156.0`** (mock model), except where a bullet names another source.

A hook passed with `-c` at the service's start is the inline `hooks` key, source `sessionFlags`: `hooks.PreToolUse` and `hooks.PostToolUse`, each a list of `{matcher?, hooks: [{type = "command", command, timeout}]}`. Both payloads carry `session_id`, `turn_id`, `cwd`, `hook_event_name`, `model`, `permission_mode`, `tool_name` (`Bash` for a command), a namespaced tool's name run together after its namespace (multi-agent v2's `spawn_agent` reads `collaborationspawn_agent`; `flat_tool_name` in `codex-rs/core/src/tools/mod.rs`, read at `0.160.0`), `tool_input` (`{"command": …}`) and `tool_use_id`; the post payload adds `tool_response`, the output text only, and **no exit code**. The post hook runs only when the call counts as a success, and a refused command still counts. Inside a code cell the `tool_use_id` reads `exec-<uuid>` and equals the `commandExecution` item's id when an item exists, so a command a hook reports with no item by the end of its turn is one the sandbox refused before sending its item. A command that fails to launch is not one of them: from `0.158.0` it gets its own `commandExecution` item, started and completed, with no process id, exit code `-1`, zero duration and the launch diagnostic (release note, `0.158.0`).

- **Trust.** A hook passed with `-c` lists as untrusted in `hooks/list` until trust is written through `config/value/write` (`keyPath: "hooks.state"`, the hook's key with its `trusted_hash`, `mergeStrategy: "upsert"`); then it fires on every command, on a fork with no configuration passed again, after an unload and a resume, and after a service restart with no new write. **A trust write does not reach a conversation already loaded**, so trust is written before any conversation starts, forks or resumes. A changed hook reads `modified` and stops until trust is written again, and an untrusted hook is skipped without a word (`codex-rs/hooks/src/engine/discovery.rs`, read at `0.159.2`). Codex keys a trust record by the hook's source, event and position, not its command, so two sets of `-c` hooks on one folder — a person's own and another client's — mark each other `modified` at each trust write.
- **`hooks/list`** is in the stable request set and answers with `experimentalApi` off. Each entry carries key, event, handler type, command, matcher, timeout, source path, source, enabled, managed, hash and trust status, with `warnings` and `errors` per folder. One quirk: a project hook reads `trustStatus: "untrusted"` although the project was trusted through `-c`.
- **Timeouts fail open.** A hook that times out lets the call through, and `ask` from a pre-tool hook is unsupported and fails open, so a hook that must hold a call carries an explicit `timeout` in its `-c` entry and refuses at its own deadline a little under it.
- **A held call on a code-mode model** (**Binary probe**, **Verified at `0.159.2`**). A code-mode model, every Codex model but `gpt-5.5` on the list read at `0.159.2`, runs its tools inside a JavaScript cell that hands control back after 30 s, and the model's `wait` on that cell reaches no hook. Every service the daemon starts carries `features.code_mode.default_exec_yield_time_ms` set to the same hold as the pre-tool hook's `timeout`, the largest Codex accepts, since Codex sets no ceiling of its own on a hook's timeout, so the cell stays open while its call is held: measured, a call held 240 s then ran, and the report was true. A model that sets a shorter wait on one cell (`// @exec: {"yield_time_ms": …}`) or calls `yield_control()` gets control back while that call stays held, and the call never runs.
- **Steering a helper.** A helper a Codex agent started takes no direct input ([Conversation settings a client sets per conversation](#conversation-settings-a-client-sets-per-conversation)), so the daemon's `PostToolUse` hook returns the person's words as `additionalContext`, the helper named in the hook input, and the steer lands at the helper's next tool call; a steer that arrives as the helper finishes goes as `SubagentStop`'s continuation. This bullet records the daemon's route; the hook steer is checked live on a real v2 helper at build.
- **Handler kinds Codex skips** (**Binary probe**, **Verified at `0.159.2`**). Codex declares the `prompt` and `agent` hook kinds and skips both at load (`prompt hooks are not supported yet`), and it skips a tool hook (`mcp_tool`) at session end. The daemon's command hook fills each, and a Codex helper its lead started runs its hooks through the lead's gate, which calls a tool through the daemon's own MCP client ([Spec-026 §Required Behavior](../../specs/026-agent-definitions-and-peer-invocation.md#required-behavior)).
- **The person's own folder.** Trust records for hooks passed to a service on the person's own `~/.codex` are written into that folder's `config.toml` by the same `config/value/write`; the write touches no other entry.
- **Hooks on one conversation** (**Upstream source**, **Verified**, read at `rust-v0.156.0`). A `thread/start` `config` becomes that conversation's session-flags layer, and hooks are discovered from that layer (`codex-rs/app-server/src/config_manager.rs`, `codex-rs/hooks/src/engine/discovery.rs`). So an agent's hooks ride its conversation's `thread/start` configuration: its `hooks` table, and each hook's trust record in the same map under `hooks.state.<key>.trusted_hash`, the key `/<session-flags>/config.toml:<event>:<group>:<handler>` and the hash the `sha256:` of the hook's canonical form (`codex-rs/hooks/src/lib.rs`; `hooks.state` is read from the user and session-flags layers, `codex-rs/hooks/src/config_rules.rs`). The hooks run trusted and nothing is written to the person's `config.toml`; `bypass_hook_trust` is never set, because it would also trust project hooks the person has not trusted. `thread/fork` takes the same open `config` map. A role file carries no hooks (`codex-rs/core/src/agent/role.rs`) and a helper the lead starts runs on a copy of the lead's configuration (`codex-rs/core/src/agent/child_config.rs`), so the hooks of a lead-started helper ride the lead's `thread/start` configuration as one trusted row per event, matcher `*`, whose command reads the hook input's `agent_type`, which Codex fills from the helper's role (`codex-rs/core/src/hook_runtime.rs`), and runs only that role's hooks. Whether the daemon's computed hash matches Codex's canonical form byte for byte is measured against `hooks/list` at build.

### Conversation settings a client sets per conversation

**Binary probe, Verified at `0.156.0`**, except where a bullet names another source.

- **Flags.** `features.default_mode_request_user_input` lets the model ask the person a question in the default mode; `features.multi_agent_v2` turns on the collaboration tools, and a helper a conversation starts with `spawn_agent` is then a v2 helper (`SubAgent(ThreadSpawn)`), to which the service refuses direct input: `can_accept_direct_input` refuses only that pairing of a v2 thread and a `ThreadSpawn` source (**Upstream source**, **Verified**, read at `rust-v0.154.0`, `codex-rs/app-server/src/request_processors/thread_input.rs`), and on a depth-two v2 helper `turn/steer` and `turn/start` each answered `-32600` `direct app-server input is not allowed for multi-agent v2 sub-agents` while `turn/interrupt` answered and interrupted its turn (**Binary probe**, **Verified at `0.154.0`**). `item/tool/requestUserInput` arrives only on a connection that negotiated `experimentalApi` ([Server-requests](#server-requests--the-callback--interactive--approval-surface-codex--daemon)), and a consumer routes it whatever the flag says. The notification opt-out list a consumer sends is generated from the notifications it handles rather than typed by hand.
- **Permission profiles.** A named profile makes a folder writable and paths inside it read-only, such as a repository's git folder writable with its `hooks` and `config` and a worktree's pointer file read-only. Once any profile is defined, `default_permissions` must be set too, or the app-server exits at start.
- **Tool switches.** `features.shell_tool` and `web_search` switch those tools per conversation. There is no switch for `apply_patch`; a client that must keep it off refuses it, and its shell forms, from its own pre-tool hook.
- **The window.** `model_context_window` may be set up to the catalog row's `max_context_window`; set above the row's default it gives the larger window. `thread/tokenUsage/updated.modelContextWindow` reports the usable window, 95 % of the full one (258,400 on 272K, 828,400 on 872K), and reflects an override.
- **Reasoning.** `model_reasoning_summary = "auto"` asks for the most detailed summary the model supports; a model that gives none sends none. `turn/start.summary` also takes `concise`, `detailed` or `none` and holds for later turns; `detailed` measured no richer than `auto` (one bold heading of about the same length on each of two prompts), so every conversation runs on `auto` and no switch is offered. The API returns no model's full reasoning, only summaries. The daemon keeps every reasoning text whole, one longer than an entry holds (16,384 characters) kept as consecutive entries and read back as one.
- **Compaction.** `model_auto_compact_token_limit` sets the automatic compaction point; Codex checks it before a turn and mid-turn, and clamps it at 90 % of the window. The resolved limit appears only in the `post sampling token usage` trace line (`auto_compact_scope_limit`, with `RUST_LOG` set and `LOG_FORMAT=json`), about 330 KB of trace a turn. A count taken before the first turn runs 119 to 125 tokens under the input the first turn's `thread/tokenUsage/updated` reports, so that first report sets the slider's bottom stop. A second key, `model_post_turn_compact_threshold_percent` (0 to 100), compacts after a final response once context use reaches that share of the usable window: "Existing auto-compaction limits still apply. Omitted or zero disables turn-end compaction" (`codex-rs/config/src/config_toml.rs` at `rust-v0.161.0`, **Upstream source**); it is skipped while input is pending or when the turn was canceled (release note, `0.156.0`).
- **A loaded conversation.** Its settings (model, effort, permissions, approval policy, collaboration mode) change through `thread/settings/update`, from its next turn; new developer instructions are appended as a developer message from its next turn, through the collaboration mode's `developer_instructions` (sent with the conversation's current model and effort, because the mode sets both and a null effort resets it) or `thread/inject_items`, the earlier ones staying in its history; its base instructions change only through a fork of the conversation, which carries them as `baseInstructions`. No configuration write reaches a loaded conversation's instructions, `reloadUserConfig` included (it reloads hooks), and `developerInstructions` passed on a resume or a fork never reaches the model, so the base instructions are passed again on every later fork and resume, because a home whose config file sets `instructions` otherwise replaces them.
- **Tool servers.** A conversation's `mcp_servers` passed as a whole table replaces the configured set; passed in dotted form (`mcp_servers.<name>.<key>`) it merges into it. A tool call's timeout is 300 s.
- **Review.** `review/start` with the `custom` target reviews whatever its instructions name, such as `git diff --cached`; the review runs in a sub-thread whose model requests are not in the parent conversation's token usage, so its cost is read from the sub-thread, tied to the session by its `parentThreadId`.
- **A steer that cuts in** (**Upstream source**, read at `rust-v0.161.0`, `codex-rs/features/src/lib.rs`). The feature `instant_interrupt`, "Preempt responses and yield foreground code-mode observations on new user input", exists from `0.159.0` at the stage under development and is off by default. With it on, new input interrupts the model's reply in flight and continues the turn with that input, resending the full history on the next request, and a running code-mode cell yields without stopping (release notes, `0.159.0`). It is not measured here.

### One tool server for every conversation, and a call that waits

**Binary probe**, **Verified at `0.160.0`**, measured 2026-10-02 and 2026-10-03 on the authoring machine against a local HTTP tool server, with two Codex conversations in one Codex process and, for comparison, two Claude Code sessions ([claude.md §One tool server for every session, and a call that waits](claude.md#one-tool-server-for-every-session-and-a-call-that-waits)).

- **One server answers every conversation.** Nothing was started per conversation. Each conversation made one setup and used two connections, one setup per conversation even inside one Codex process, and none reconnected per call.
- **Codex speaks MCP revision 2025-06-18**, with a standing GET stream and a closing DELETE.
- **Codex names the conversation on every call** (**Upstream source**, read at `rust-v0.161.0`, `with_mcp_tool_call_ids_meta` in `codex-rs/core/src/mcp_tool_call.rs`). Every `tools/call` it sends carries `_meta.threadId`, the conversation that made the call, a helper's own included, and `_meta.sessionId`, and `_meta.windowId` and `_meta.itemId` when it knows them, beside any `_meta` the call already had. It is not measured here.
- **Instructions on the connection and on the conversation.** A tool server's `initialize` instructions were pasted at the top of the description of every tool on that connection. `developerInstructions` passed at `thread/start` reached the model, and a resumed conversation kept the text it started with: new text passed on the resume did not replace it.
- **A long call is held, and the model keeps writing while it waits.** A 20-second call sending progress every 5 seconds on its own reply was taken and finished; Codex passes a tool server's progress through only as `item/mcpToolCall/progress`. A `session_wait` held 400 seconds with nothing sent back answered at 410 seconds on an entry with `tool_timeout_sec: 900`, and at 400 seconds on the `dynamicTools` route. On both routes the model wrote a message about once a minute while it waited (`session_wait` is still pending…, seven times).
- **A held call costs more the longer it is held; a call answered at once and a new turn cost the same however long the wait.** Measured on the `dynamicTools` route, with the awaited session finishing after 180 seconds, in near-empty conversations: the call held 180 seconds took 9 model passes and 262,608 tokens, 240,512 of them cached input, each pass re-sending the whole conversation; a `session_wait` that answered at once telling the model to end its turn, followed by a new turn 180 seconds later carrying the result, took 4 model passes and 57,253 tokens.
- **The sender's id in the reply line decides where a reply goes.** With two sessions named `planner` in `session_list`, a framed message whose reply line named only `planner` had both sends go to the shared name; with the id in the reply line, all three sends in two runs went to `s-4a10`, and in one run more the model sent nothing and answered in its turn.

### Typing into a command, and a command that outlives its turn

**Binary probe, Verified at `0.156.0`**, recorded at its own build.

- **The executor.** `codex exec-server` runs a conversation's commands; a service registers one with `environment/add`, and a conversation starts, resumes and forks with `environments: [{environmentId, cwd}]`. An approved command reaches the executor as `process/start`, after Codex's exec policy and approval saw its argv. Only a terminal command takes typed input (**Upstream source**, read at `rust-v0.161.0`): `process/start` carries `pipeStdin: false` for every command (`exec_server_params_for_request` in `codex-rs/core/src/unified_exec/process_manager.rs`), so `process/write` writes to a command started with `tty: true`, and the model's own `write_stdin` goes the same way; to any other command the executor answers `process/write` with `stdinClosed` (`exec_write` in `codex-rs/exec-server/src/local_process.rs`), and the model's `write_stdin` is refused `StdinClosed`, except a lone `\u0003`, which interrupts the command (`write_stdin_inner`).
- **Running commands.** A command can outlive its turn: its item closes on its own `item/completed`, never on `turn/completed`, and `thread/backgroundTerminals/list` lists it until it exits. `thread/backgroundTerminals/terminate` stops one.
- **A running command has no age deadline** (**Upstream source**, read at `rust-v0.161.0`, commit `979011409`). Commands run through `unified_exec`, which is stable and on by default (the `UnifiedExec` entry of `FEATURES` in `codex-rs/features/src/lib.rs`). Its first call returns after `yield_time_ms`, 10,000 ms by default (`default_exec_yield_time_ms` in `codex-rs/core/src/tools/handlers/unified_exec.rs`) and clamped to 250–30,000 ms (`MIN_YIELD_TIME_MS`, `MAX_YIELD_TIME_MS` and `clamp_yield_time` in `codex-rs/core/src/unified_exec/mod.rs`), and the command keeps running, so the Codex leg needs no setting for a long command. `background_terminal_max_timeout`, 300,000 ms by default, bounds only how long one empty `write_stdin` poll waits (`Config::background_terminal_max_timeout` and its default in `load_config_with_layer_stack`, `codex-rs/core/src/config/mod.rs`; `write_stdin_inner` in `codex-rs/core/src/unified_exec/process_manager.rs`). Only the one-shot form, used when unified exec is off, stops a command at its `timeout_ms`, 10,000 ms by default (`handle_call` in `codex-rs/core/src/tools/handlers/unified_exec/exec_command.rs`; `DEFAULT_EXEC_COMMAND_TIMEOUT_MS` in `codex-rs/core/src/exec.rs`). A running command otherwise ends only by:
  - pruning once 64 are open, an exited one first, else the least recently used outside the 8 most recent (`prune_processes_if_needed`; `MAX_UNIFIED_EXEC_PROCESSES` in `unified_exec/mod.rs`);
  - `clean_background_terminals` (`clean_background_terminals` in `codex-rs/core/src/session/handlers.rs`) or the session's shutdown (`shutdown_session_runtime`);
  - the app server unloading a thread that has had no subscriber and no activity for its unload delay, 60 s by default (`UnloadingState` and `unload_thread_without_subscribers` in `codex-rs/app-server/src/request_processors/thread_lifecycle.rs`; the `thread_unload_delay` default in `load_config_with_layer_stack`). Whether a running command counts as activity was not read.
- **The executor's connection at `0.161.0`** (**Generated schema** and `codex exec-server --help` from the installed `0.161.0`; **Upstream source**, read at `rust-v0.161.0`). Nothing here is measured.
  - **Registration.** `environment/add {environmentId, execServerUrl, authBearerToken?, connectTimeoutMs?}` is in the `--experimental` generation only, so the connection that calls it negotiates `experimentalApi`. `authBearerToken` is "Optional raw bearer token for executor authentication, including reconnects. Requires a secure transport or a loopback destination."
  - **The executor's own listener.** `codex exec-server --listen` takes `ws://IP:PORT` (the default) or `stdio`. `--ws-auth <capability-token|signed-bearer-token>` sets how an incoming WebSocket connection authenticates, with `--ws-token-file` (the absolute path of the capability-token file) or `--ws-token-sha256` (the token's hex SHA-256); the executor checks `Authorization: Bearer <token>` before each WebSocket upgrade and refuses a bad one with HTTP 401 (release note, `0.158.0`).
  - **Process ids are unique per start.** Codex sends each `process/start` with the process id `<id>-<uuid>`, a fresh UUID each time, "Threads sharing an executor and sandbox retries can reuse a public handle while the executor still retains its previous process", and with `metadata: {threadId, toolCallId}` naming the conversation and the tool call (`codex-rs/core/src/unified_exec/process_manager.rs`). What stays the same across a command's retries is the metadata, never the process id.
  - **Message limits.** A message the executor sends Codex is refused past 8 KiB, except `process/output`, `process/exited`, `process/closed` and `http/request/bodyDelta`, which may reach 2 MiB; responses have no limit (`codex-rs/exec-server/src/client_inbound_request_limit.rs`).
  - **File methods.** The protocol carries `fs/writeBlock`, and `fs/open` takes `mode: "read" | "replace"` (read by default; replace creates or truncates the file). An executor reports both through the capability `fileWriteStreaming`, beside `capabilityDiscoveryV2`, in the `EnvironmentInfo` it describes itself with, which also carries `prependPathDirs`; the local executor reports `fileWriteStreaming: false` at `0.161.0`, so file writes do not go through the executor yet (`codex-rs/exec-server-protocol/src/protocol.rs`).

### Plugins, memory and tool-server scopes

**Binary probe, Verified at `0.156.0`**, except where a bullet names another source.

- **Plugins.** `plugin/*` and `marketplace/*` list, install and remove plugins. A service started with `-c features.plugins=false` runs no catalog sync.
- **Project trust.** A `[projects."<path>"]` table accepts only `trust_level` (**Upstream source**, `codex-rs/config/src/config_toml.rs` at `rust-v0.156.0`). The daemon passes it per process in inline-table form, `-c 'projects={"<path>"={trust_level="trusted"}}'` (**Binary probe**, **Verified at `0.154.0`**).
- **A memory folder outside the project.** A permission profile's `write` entry lets a conversation write a folder outside its working folder, which is how an agent's memory folder in the daemon's own data is writable on Codex at every level.
- **Tool-server scopes.** Codex's `project` scope is `.codex/config.toml` in the project, which a client edits in place preserving its formatting and reads back through `config/read`; Codex has no `local` scope of its own. MCP prompts are not listed or fetched by Codex, so a client that offers a server's prompts lists and gets them through its own MCP client. Codex has no MCP Tasks: it makes no task-augmented call and cannot move a long tool call to the background, so a client that needs one fronts the server on its own route.
- **A long tool call, on the daemon's route.** The daemon fronts every tool server it can reach: the conversation's `thread/start` configuration carries the whole `mcp_servers` table, each server a `url` entry on the daemon's route under the server's own name, so the model sees the same server and tool names. The route answers a call normally when it ends within 120 s. Past 120 s, or when the daemon sends the conversation a message with `turn/steer` while the call runs, the route answers Codex's pending `tools/call` with the text Claude Code gives in the same case (the tool, the seconds elapsed, the task id the call moved to, that it keeps running, that a notification brings the result, and how to stop it), and the call keeps running in the daemon's client. The route adds two tools: `task_output` returns the task's status and, once it ends, its result, and `task_stop` cancels it. When the call ends, the daemon delivers Claude Code's completion notice, `MCP task <id> (<server>/<tool>) completed.`, with the result: by `turn/steer` into the running turn if one is running, otherwise by `turn/start`; to a multi-agent v2 helper, which refuses both, it is delivered at the helper's next tool call as the post-tool hook's `additionalContext`, or as the `SubagentStop` continuation as it finishes. This bullet records the daemon's route over the surface measured above; the route itself is measured at build.

### `model/list` — the model catalog and the per-model effort vocabulary

**Generated schema**, **Verified** at `0.160.0` from the generation dated in [Version pin](#version-pin). Both types below are byte-identical in the default and `--experimental` generations, so nothing here is field-gated the way `TurnStartParams.permissions` is, and both are byte-identical to `0.150.1` (the nested `Model` is not; see below).

```
ModelListParams   = { cursor?: string | null, limit?: number | null, includeHidden?: boolean | null }
ModelListResponse = { data: Array<Model>, nextCursor: string | null }
```

**`nextCursor` is required and nullable — not optional. The distinction is load-bearing and the two generated artifacts disagree about it**, so this section transcribes the TypeScript, which is the notation [Capability shapes](#capability-shapes) declares this file follows. `v2/ModelListResponse.ts` emits `nextCursor: string | null` with no `?`: the member is **always present**, carrying `null` to mean "no more pages". The JSON Schema for the same type lists only `data` in `required`, because its `required` describes what a decoder must tolerate missing, while the ts-rs binding describes what the server actually emits. Where the two differ in this section, the TypeScript is quoted and the difference is called out. A consumer that types this member optional will not be wrong at runtime, but a consumer that treats an **absent** `nextCursor` as equivalent to a **null** one is relying on the looser artifact.
**This read is paginated and must be driven as such.** The generated comments are verbatim: `cursor` is "Opaque pagination cursor returned by a previous call."; `nextCursor` is "Opaque cursor to pass to the next call to continue after the last item. If None, there are no more items to return."; `limit` is "Optional page size; defaults to a reasonable server-side value." A consumer that reads `data` and ignores `nextCursor` silently truncates the catalog at whatever the server's default page size happens to be. Contrast [`skills/*`](#skills--the-skill-surface) below, which carries no pagination member at all — the two sibling reads on this surface do not share a convention, so neither one's handling can be inferred from the other.

**Every `Model` field is emitted — none is optional in the binding.** `v2/Model.ts` carries nineteen members and not one of them takes a `?`: `id`, `model`, `upgrade`, `upgradeInfo`, `availabilityNux`, `displayName`, `description`, `modelSpecialty`, `hidden`, `supportedReasoningEfforts`, `defaultReasoningEffort`, `inputModalities`, `supportsPersonality`, `multiAgentVersion`, `additionalSpeedTiers`, `serviceTiers`, `defaultServiceTier`, `availableAccessPrograms`, and `isDefault`. Seven of them are **required-and-nullable** rather than optional — `upgrade`, `upgradeInfo`, `availabilityNux`, `modelSpecialty`, `multiAgentVersion`, `defaultServiceTier`, `availableAccessPrograms` — so absence is expressed as `null` on a present key, never as a missing key. Against `0.150.1` the type gained `availableAccessPrograms: ModelAccessPrograms | null` ("Null when the catalog does not provide access-program metadata"; `ModelAccessPrograms` is `{ cyber: Array<CyberAccessProgram> }`), and `supportsPersonality` is now marked "@deprecated Always false; models no longer support personality selection." (The JSON Schema for the same type names only eight in `required`, listing the rest as optional-with-defaults; that is the same artifact divergence recorded above, and the emitted shape is the TypeScript one.) Note that `id` and `model` are **both** present and **both** required, as separate strings; a consumer keying on one is not keying on the other. `includeHidden` exists because the catalog carries rows the default picker suppresses — its comment reads "When true, include models that are hidden from the default picker list."

**The effort vocabulary is per-model, and the generated schema itself declines to close it.** This is the structural fact, and it is load-bearing in a way no list of values is:

```
supportedReasoningEfforts: ReasoningEffortOption[]
ReasoningEffortOption = { reasoningEffort: ReasoningEffort, description: string }   // both required
ReasoningEffort       = { "type": "string", "minLength": 1 }                        // JSON Schema artifact — the TypeScript binding is a bare string with NO length constraint
```

`ReasoningEffort` carries its own verbatim description — "A non-empty reasoning effort value advertised by the model." The JSON Schema artifact constrains a **non-empty string** (`minLength: 1`); the TypeScript binding can only say `string` and encodes no length floor, so a TypeScript consumer gets no compile-time protection against an empty value. Neither artifact emits a closed union, so the wire's own position is that the set of efforts is whatever each model advertises. No provider-wide effort list can be correct by construction, and a consumer that hardcodes one is asserting something the schema explicitly refuses to. `turn/start`'s `effort` override consumes this same type ("Override the reasoning effort for this turn and subsequent turns."), so the per-turn override is bounded by the per-model catalog rather than by any fixed vocabulary.

**The values at this pin.** **Binary probe**, **Verified**, measured 2026-10-02 at `0.160.0` by one zero-turn `model/list` after `initialize` / `initialized` on a default connection (`nextCursor: null`; `hidden: false` on every row). `0.160.0` publishes **three distinct effort lists across nine models**, with **no `minimal` on any of them**:

| Effort list | Models |
| --- | --- |
| `low \| medium \| high \| xhigh \| max \| ultra` | `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6-sol`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-daybreak-blue-latest` |
| `low \| medium \| high \| xhigh \| max` | `gpt-6-luna`, `gpt-5.6-luna` — the two rows carrying `max` without `ultra` |
| `low \| medium \| high \| xhigh` | `gpt-5.5` |

`0.159.2`, read the same way the same day, returned the same rows without `gpt-daybreak-blue-latest`. The catalog is the account's, served at run time, so the rows move without a release: against the `0.150.1` reading of 2026-08-30, `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6-sol` and `gpt-6-luna` arrived and `gpt-5.4`, `gpt-5.4-mini` and `gpt-5.3-codex-spark` left. The driver reads the catalog from Codex at every start (`driver.listModels`) and ships no copy of it. **On an API-key account the catalog comes from the server** from `0.161.0`: the feature `api_key_model_discovery` is stable and on by default there (`codex-rs/features/src/lib.rs` at `rust-v0.161.0`, **Upstream source**), Codex falls back to its bundled models only when the feature is off, and a provider's explicit catalog is authoritative, matched by exact id (release notes, `0.160.0` and `0.161.0`).

**The three lists *are* strictly nested, and a longest-list union is still wrong** (`low | medium | high | xhigh` is a prefix of `low | medium | high | xhigh | max`, which is a prefix of `low | medium | high | xhigh | max | ultra`, a totally ordered chain). Nesting makes the union well-defined; it does not make it correct, and the reason is **membership, not shape**. Collapsing to the longest list would offer `ultra` on `gpt-6-luna` and `gpt-5.6-luna` and both `max` and `ultra` on `gpt-5.5` — efforts those models do not advertise. The wire's own position is per-model, so the only faithful consumption is per-model: carry each model's published list verbatim and offer nothing outside it.

**Between `0.141.0` and `0.150.1` this type grew too, and one growth is a union widening rather than a plain field add** (measured 2026-08-31 against the `rust-v0.141.0` protocol schemas). `ModelListParams` is byte-identical from `0.141.0` to `0.160.0`, so the read itself is unchanged. `ModelListResponse` is not: by `0.150.1` `Model` had gained the optional `modelSpecialty` and `multiAgentVersion`, `ModelUpgradeInfo` the optional `retirementAt`, and the `MultiAgentVersion` definition was new — all additive — **but `InputModality` had gained a third variant, `audio`, beside `text` and `image`.** That last one is the same class as the `ReviewDecision` row in [Breaking type changes from earlier builds](#breaking-type-changes-from-earlier-builds): an exhaustive match over `InputModality` written against `0.141.0` does not cover `0.159.2` or the pin or the pin. It carries its own row in that table, with the direction called out there — `InputModality` arrives **from** the provider, so the failure is a decode or match failure on receipt rather than a rejected request.

A sibling read, `modelProvider/capabilities/read`, takes empty params and answers `{ imageGeneration: boolean, namespaceTools: boolean, webSearch: boolean }` (all required). It is a provider-wide feature triple and carries no speed, effort, or model axis.

### Output speed — a service-tier surface with no method-level axis

The heading names the shape of this surface: the **method** namespace carries no output-speed axis, and the **field and catalog** surfaces carry one. Both readings are true and they answer different questions, so they are graded separately and neither is read as the other.

**There is no output-speed axis in the METHOD namespace.** Across all four default union roots — **198 method strings** at `0.160.0` — **zero** method names match `speed`, `fast`, `turbo`, or `accel`. No method starts, stops, or sets such an axis and no notification reports one. That census is exhaustive over the method roots. **Generated schema**, **Verified** at the pin. It bounds the method namespace and nothing else: a method census cannot settle a field-and-values question, so it is not evidence about the surface below.

**The wire publishes a person-settable service-tier surface, on the default connection.** Verbatim from the **default (non-experimental)** generation at the pin:

Omitted or null inherits the thread's tier. Does not change the thread's tier or a turn being steered." | **present in the DEFAULT generation**; added since `0.150.1` |

Three details from that table matter. `serviceTier` is on `turn/start` in the **default** generation — it is emphatically **not** field-gated the way `permissions` is, so a default connection can set it. The three distinct requests — absent, explicit `null`, a value — are carried by **key presence on the optional member**, not by the doubled `| null | null` in the ts-rs output, which is that generator's rendering of a nested option and collapses to a single union arm in TypeScript (as in JSON, which has no second null); the experimental `thread/settings/update` binding states the tri-state itself: "`null` clears the current service tier; omission leaves it unchanged." And `turn/start` now carries **two** tier members: `serviceTier` sets the thread's tier from this turn on, while `serviceTierForTurn` applies to the one turn the request starts and leaves the thread's tier, and any turn it steers, alone.

**The tier values are catalog data rather than schema.** `ModelServiceTier` is three free-form strings; which tiers exist, and what they mean, is runtime data returned by `model/list`. So "which tiers does a model offer?" is answerable only from a catalog read, never from the generation — and any claim about tier values has to cite such a read.

**A catalog read publishes a speed-differentiated tier on every model, and the thread declares its own tier back.** Measured first-party by driving `codex app-server` headless at `codex-cli 0.155.1` on 2026-09-19, recorded here as a **version-anchored evidence** claim rather than as a pin. **Binary probe**, **Verified at the build measured**:

- `model/list` returned every model carrying one service tier, `{ id: "priority", name: "Fast", description: "1.5x speed, increased usage" }`, with the description reading `2x` on one model, and `defaultServiceTier` **null** on the rows read. The null default is the **catalog's** default, not the thread's current setting — reading it as the latter would report a tier the thread is not on.
- The thread's own declared tier is read back in two places: the `serviceTier` member of the `thread/start`, `thread/resume` and `thread/fork` responses, and `ThreadSettings.serviceTier` on the `thread/settings/updated` notification. So this surface has a **declared-state read**, which the pin's generation alone could not establish.
- `serviceTier` is accepted on `thread/start`, `thread/resume` and `thread/fork` as well as on `turn/start`, and `turn/start`'s own description reads "Override the service tier for this turn and subsequent turns" — so the parameter is per-turn with forward effect rather than a one-turn-only override. The one-turn override is the separate `serviceTierForTurn`, in the default generation at `0.159.2` and `0.160.0`.
- The build carries the interactive toggle for the mode in its own command table (`/fast`, bound in its key map as a fast-mode toggle) and its feature listing reports `fast_mode` as stable. That is the provider's own user-facing control for this axis. At `0.160.0`, `codex debug models` lists `additional_speed_tiers: ['fast']` on every model the catalog returns except `gpt-daybreak-blue-latest`, which lists none (read 2026-10-02).

**What the governing spec makes of it.** [Spec-004 §The output-speed axis](../../specs/004-provider-driver-contract-and-capabilities.md#the-output-speed-axis) declares `output_speed` for this driver, on the two conjuncts that axis requires and that the readings above supply: a **level vocabulary** published per model on the catalog read, and a **declared-state read** on establishment and on the settings-changed notification. The axis resolves to a **turn** boundary there, because the carrier is per-turn. The flag's detection source stays `static` with **decisiveness** the failing conjunct: a tier is three free-form strings, so reading a returned tier as an output-*speed* tier is a semantic judgment rather than a decidable read, and the zero-turn catalog channel therefore cannot decide the flag in either direction. This file records the wire; that spec adjudicates the contract.

**This provider has an output-speed axis.** `/fast`, `fast_mode`, `serviceTier` and the `Fast` tier each model publishes on `model/list` are the axis; [Spec-004 §The output-speed axis](../../specs/004-provider-driver-contract-and-capabilities.md#the-output-speed-axis) declares it for this driver, and a Fast request is priced at the list's Fast rate for its model.

**`skills/list` — the read.**

```
SkillsListParams   = { cwds?: Array<string>, forceReload?: boolean }                       // optional, NOT nullable
SkillsListResponse = { data: Array<SkillsListEntry> }                                     // required
SkillsListEntry    = { cwd: string, skills: Array<SkillMetadata>, errors: Array<SkillErrorInfo> }  // all three required
SkillErrorInfo     = { path: string, message: string }                                    // both required
```

Verbatim comments: `cwds` — "When empty, defaults to the current session working directory."; `forceReload` — "When true, bypass the skills cache and re-scan skills from disk."

**The reply is grouped per scanned working directory, not flat.** There is one `SkillsListEntry` per `cwd`, each carrying its own `skills` and its own `errors` — so a consumer wanting a single list concatenates the groups, and a per-directory scan failure surfaces as a populated `errors` array on that one group rather than as a request-level refusal. A partially-failed scan is therefore a **success** on this wire.

**There is no pagination on either side of this read** — no `cursor`, no `limit`, no `nextCursor` anywhere in the params or the response. The whole set arrives in one reply. That is the opposite convention from [`model/list`](#modellist--the-model-catalog-and-the-per-model-effort-vocabulary) above, and the difference is real rather than an omission in this reference.

**`SkillMetadata` — the entry shape.**

```
SkillMetadata = {
  name: string, description: string,
  shortDescription?: string, interface?: SkillInterface, dependencies?: SkillDependencies,
  path: AbsolutePathBuf, scope: SkillScope, enabled: boolean,
  pluginId: string | null                                    // ← required AND nullable, not optional
}
SkillScope = "user" | "repo" | "system" | "admin"
```

**Six members are emitted unconditionally and three may be absent.** `pluginId` is **required-and-nullable** — always present, carrying `null` where the owning plugin is unknown — while `shortDescription`, `interface`, and `dependencies` are genuinely optional and, in the TypeScript binding, **not** nullable: they are absent or they carry a value. (The JSON Schema types all four as nullable and names only five members in `required`; the emitted shape is the TypeScript one, per the artifact divergence recorded under [`model/list`](#modellist--the-model-catalog-and-the-per-model-effort-vocabulary).)

Three consequences of that required-set that a normalizing consumer depends on:

- **`description` is required.** What the generated shape establishes is a decoding rule and nothing more: `description` is present on every entry the reply returns, so a consumer must accept it and has no absent case to handle here. It does **not** establish what the provider does with a skill whose source file declares no description — an empty string on a returned row and no row at all plus a `SkillErrorInfo` in that group's `errors` array are both consistent with this schema, and this pass ran no runtime probe that separates them. The second is reported but not reproduced here (a missing or invalid `description` yields an `errors` entry and no skill row), so it is **Provisional**, since a schema cannot settle a runtime behavior and no probe was run to settle it here.
- **`scope` is required**, drawn from the closed four-value set above. This surface always declares a scope. The Claude handshake enumeration declares none at all, which is why a cross-provider normalized entry has to type the field optional even though Codex never omits it.
- **`enabled` is required on every returned row — and that is all the shape establishes.** Whether a disabled skill arrives as an `enabled: false` row or is filtered server-side before the response is constructed is a runtime behavior this pass ran no probe to settle; a required boolean proves only that every row the server chose to return carries the flag. A consumer that wants only active skills filters client-side either way, and a consumer counting entries must not read the count as the full scanned set or as the available set — omission and `enabled: false` are not established to mean the same thing.

`AbsolutePathBuf` carries its own verbatim description — "A path that is guaranteed to be absolute and normalized (though it is not guaranteed to be canonicalized or exist on the filesystem)." — so a `path` here is absolute but is **not** evidence the file exists.

**`skills/changed` — the invalidation signal.** The notification type is an **empty object** carrying no payload whatsoever, and its entire generated description is verbatim:

> Notification emitted when watched local skill files change.
>
> Treat this as an invalidation signal and re-run `skills/list` with the client's current parameters when refreshed skill metadata is needed.

The wire therefore specifies its own refresh discipline: there is no delta, no changed-entry list, and no means of patching a held list. The only correct response is a **full re-read** with the same parameters the consumer used originally. A consumer holding skill state discards it wholesale on this frame.

**The mutating siblings**, recorded for completeness — this project reads this family and does not currently drive these:

```
SkillsConfigWriteParams     = { path?: AbsolutePathBuf | null, name?: string | null, enabled: boolean }
SkillsConfigWriteResponse   = { effectiveEnabled: boolean }
SkillsExtraRootsSetParams   = { extraRoots: Array<AbsolutePathBuf> }
SkillsExtraRootsSetResponse = {}                                                  // empty object
PluginSkillReadParams       = { remoteMarketplaceName: string, remotePluginId: string, skillName: string }   // all required
PluginSkillReadResponse     = { contents: string | null }                         // required AND nullable
```

`skills/config/write` takes **either** a name-based **or** a path-based selector — two separately-nullable fields whose verbatim comments are "Name-based selector." and "Path-based selector." — and answers with the resolved `effectiveEnabled` rather than echoing the request, so the write's outcome is read from the reply rather than assumed from the request.

### Server-requests — the callback / interactive / approval surface (Codex → daemon)

`ServerRequest` carries 10 methods at `0.160.0` — **the same 10 as at `0.141.0` and `0.150.1`**, the one root that has not moved across any of those releases. This is the surface the daemon answers back on:

- Callback tools: `item/tool/call`; interactive input: `item/tool/requestUserInput` (**EXPERIMENTAL** — the generated definition is marked "EXPERIMENTAL - Request input from the user for a tool call."; at `0.156.0` it arrived only on a connection that negotiated `initialize.capabilities.experimentalApi = true` ([Conversation settings a client sets per conversation](#conversation-settings-a-client-sets-per-conversation)), though `app-server` itself holds no gate for it ([The experimental gate](#the-experimental-gate--a-runtime-filter-not-a-schema-filter))), `mcpServer/elicitation/request`, which gained an `openaiForm` mode in the default generation since `0.150.1`. An elicitation can come from a helper's conversation as well as the lead's, Codex having dropped its root-only guard so a helper can ask and wait (release note, `0.156.0`), and its params name the conversation it belongs to in a required `threadId` (**Generated schema**, `0.161.0`).
- Approvals (modern): `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`; (legacy) `execCommandApproval`, `applyPatchApproval`.
- `item/commandExecution/requestApproval` carries a `kind`: `command` (the default, and what a server that sends no `kind` means) asks to run a command; `writeStdin` asks to send input to a command the agent already runs with extra permissions. Codex raises the second by default from `0.158.0`. Its `itemId` is the running command's own item, it carries an `approvalId`, and its `command` is `write_stdin --session-id <n> <input>`, shell-quoted, whose last word is the input. Codex keeps no session-wide allow for it, so the driver answers it `accept` or `decline` only, and the card shows it as input to that command, never as a command to run.
- Also `attestation/generate`, and `account/chatgptAuthTokens/refresh`, which a service running on tokens a client handed it (`account/login/start {type: "chatgptAuthTokens"}`) sends when those tokens need renewing; a client answers it with fresh tokens, which it can get by running `account/read {refreshToken: true}` in that account's own home.

**The approval card's rules are Codex's own** (**Upstream source**, read at `0.159.2`). A session allow is the answer `acceptForSession`, which Codex keeps until the conversation ends. Codex has no list of them, no revoke and no session block, so the daemon's pre-tool hook, which runs before Codex's own approval for commands, file edits and tool-server calls, holds the next call on a subject the session took back and raises its card again; the daemon declines Codex's later asks for a host blocked for the session; and after a restart it answers `acceptForSession` itself on a subject the session allowed. A project rule is written by the daemon as a `prefix_rule`, or a host's as a `network_rule`, into the project's `.codex/rules/sidekicks.rules`, which Codex reads, network rules included, in conversations started after it, and the ask is answered `acceptForSession` so the current conversation does not ask again; the daemon adds that one path to the repository's `.git/info/exclude` and never touches the tracked `.gitignore`. That a held call on a subject Codex already allowed is refused when the person declines is measured by the unit that builds the hook.

Every approval server-request that reaches the driver routes through the daemon's own approval pipeline. The approval reviewer defaults to `user` in the generated schema. At every permission level but Reviewed the driver pins `approvalsReviewer: "user"`, so a config or profile override cannot hand approvals to Codex's automatic reviewer where the level does not name it. At Reviewed the driver sets Codex's own automatic reviewer, which approves routine work, blocks the rest and tells the agent why: `guardianWarning` and `autoApprovalReview/strictReviewRequired` become `moderation.review_flagged`, `turn/moderationMetadata` draws nothing and goes only to the daemon's log, a block read from `item/autoApprovalReview/completed` becomes `approval.reviewer_denied`, and `thread/approveGuardianDeniedAction` with that denial is `Allow once` ([Spec-004 §Required Behavior](../../specs/004-provider-driver-contract-and-capabilities.md#required-behavior)).

### A forced `rm`, and the removals Claude Code flags

**Binary probe**, **Verified at `0.161.0`**, measured 2026-10-07 on the authoring machine: `codex app-server` against a mock Responses provider that answered the first request with one `exec_command` call carrying the command whole and played Codex's reviewer with a fixed verdict, a scratch `CODEX_HOME`, and `HOME` and the working folder made for each run, so `~` named a throwaway folder. The posture rode `thread/start`: Full Access as `sandbox: "danger-full-access"` with `approvalPolicy: "never"`, Sandboxed as `permissions: ":workspace"` with `"never"` (the daemon's own profile extends `:workspace`), Ask for approval as `:workspace` with `"on-request"` and `approvalsReviewer: "user"`, and Approve for me as `:workspace` with `"on-request"` and `approvalsReviewer: "auto_review"`.

| Command | Full Access | Sandboxed | Ask for approval | Approve for me |
| --- | --- | --- | --- | --- |
| `rm -rf ~` | refused before it ran | refused before it ran | `item/commandExecution/requestApproval` | sent to Codex's reviewer; on its allow it ran inside the sandbox, which refused every path in the home folder |
| `rm -rf .` | refused before it ran | refused before it ran | asked, as above | sent to the reviewer; on its allow `rm` itself refused, `"." and ".." may not be removed` |
| `rm -rf *` | refused before it ran | refused before it ran | asked, as above | sent to the reviewer; on its allow it emptied the working folder |
| `rm -r ~` | ran and deleted the home folder | the sandbox refused every path; no command item | as Sandboxed | as Sandboxed, with no review |
| `rm -r *` | ran and emptied the working folder | ran and emptied it | ran, unasked | ran, with no review |

- **Codex's own check is the force option, not the target** (**Upstream source**, read at `rust-v0.161.0`). `dangerous_command_match` in `codex-rs/shell-command/src/command_safety/is_dangerous_command.rs` flags an `rm` carrying `-f` or `--force` anywhere before `--`, whatever it removes, through `sudo`, `env` and a `trap` action and inside a `bash -lc` script; a flagged command that no exec-policy rule matches is refused when approvals are off and asked for otherwise (`render_decision_for_unmatched_command` in `codex-rs/core/src/exec_policy.rs`). Nothing looks at the target, so `rm -r ~` without `-f` runs at Full Access and `rm -r *` runs at every posture whose sandbox can write the working folder.
- **A refusal reaches only the model.** With approvals off the client receives no command item and no notification for the refused call; the model's tool output reads ``exec_command failed: CreateProcess { message: "Rejected(\"`/bin/zsh -lc 'rm -rf ~'` rejected: rm -f style commands are not permitted. Use a safer approach\")" }``. A reviewer's deny ends the call as a `declined` command item, and the model reads Codex's `This action was rejected due to unacceptable risk.` with the reviewer's rationale.
- **The pre-tool hook runs first** (**Upstream source**, read at `rust-v0.161.0`, not measured). The tool registry runs `PreToolUse` hooks before the handler that applies the approval policy and this check (`codex-rs/core/src/tools/registry.rs`); a hook's block reaches the model as `Command blocked by PreToolUse hook: <reason>. Command: <command>` (`codex-rs/core/src/hook_runtime.rs`), and a hook that lets the call go on hands it to the check unchanged, so a forced `rm` the hook lets through is still refused with approvals off, asked for at Ask for approval and reviewed at Approve for me.

### `thread/realtime/*` — realtime voice (gated)

The realtime family is **gated on both directions of the wire at `0.160.0`**, and the two directions are gated by different mechanisms — which is why the generated schema on its own reads misleadingly here. Its membership is unchanged from `0.150.1`: six client requests and eleven server notifications.

- **The six client request methods** — `thread/realtime/start` / `appendAudio` / `appendText` / `appendSpeech` / `stop` / `listVoices` — are **absent from the default-generated `ClientRequest`**. All six are registered `#[experimental(…)]` in the pinned protocol source (`codex-rs/app-server-protocol/src/protocol/common.rs` at `rust-v0.160.0`), so their bindings require experimental generation. The upstream README at `rust-v0.160.0` carries no per-method reference, so it documents none of them.
- **The eleven server notifications** — `thread/realtime/started`, `…/closed`, `…/error`, `…/itemAdded`, `…/sdp`, `…/outputAudio/delta`, `…/transcript/delta`, `…/transcript/done`, `…/item/started`, `…/item/transcript/delta` and `…/item/completed` (a WebRTC-shaped surface) — **do appear in the default-generated `ServerNotification` schema**, and a driver reading only that schema would conclude they arrive. **They do not.** All eleven carry `#[experimental(…)]` markers in the same protocol source, and the transport's `should_skip_notification_for_connection` drops every experimental notification for a connection that did not set `experimentalApi` (see [The experimental gate](#the-experimental-gate--a-runtime-filter-not-a-schema-filter)). They are in the schema by construction — the generator has no notification-side experimental exclusion — and off the wire at runtime.
- **The item-scoped names sit beside the older ones; neither replaced the other.** `thread/realtime/item/started` / `…/item/transcript/delta` / `…/item/completed` are item-scoped spellings of surfaces the family already had, added at `0.150.1`, so the obvious reading is that they replaced `…/itemAdded` / `…/transcript/delta` / `…/transcript/done`. A full-list-vs-full-list set difference says otherwise: all six names are in the `0.160.0` root, each with its own marker. A consumer that treats this as a rename and drops the old spellings will stop recognizing frames the pin still publishes. What is not settled here is which spelling the upstream feature will keep — the family is Provisional either way.

**What a connection that opts in gets.** On a connection that negotiated `experimentalApi`, the family is live: `thread/realtime/start {threadId, transport: {type: "webrtc", sdp}, version: "v3", outputModality: "audio", voice, initialItems, clientManagedHandoffs: true, includeStartupContext: false}` starts a WebRTC call on the thread, answered through `thread/realtime/sdp`, with `initialItems` holding at most 128 items and about 8,192 tokens; `thread/realtime/listVoices` returns the `v1` voice list and its `defaultV1`; `thread/realtime/appendSpeech {threadId, text}` speaks a text into the call, cut at 990 tokens; `thread/realtime/stop` ends it; and every notification arrives, each carrying the `threadId` it belongs to, so a service holding several conversations routes them by that id. A call belongs to one thread. The upstream feature is still marked experimental in both directions and changed between the builds measured here; a member missing or changed on the installed build degrades that one feature and shows in the daemon's logs.
