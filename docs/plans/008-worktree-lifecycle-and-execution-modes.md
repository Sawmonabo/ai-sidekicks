## Goal

Implement the four-mode repo execution contract with worktree-first writable defaults plus the lifecycle management around worktree preparation, reuse, retirement, and ephemeral clone preparation.

## Scope

This plan covers execution mode selection, read-only and branch gating, worktree creation, ephemeral clone preparation, reuse validation, lifecycle projection, run-setup execution-root binding, and fallback handling.

## Non-Goals

- PR preparation
- Diff attribution logic
- Non-repo directory execution semantics
- Automatic repository setup-script execution during execution-root preparation

## Preconditions

- [x] Paired spec is approved
- [x] Required ADRs are accepted
- [x] Blocking open questions are resolved or explicitly deferred

## Data And Storage Changes

- Add local `worktrees`, `ephemeral_clones`, `branch_contexts`, and `run_execution_contexts` tables (D-008-5). No table is added or removed after that — the SQLite table census does not move again for this plan.
- Add `run_execution_contexts.checkout_root` (`TEXT NOT NULL`) — the durable normalized-root carrier CP-008-12's caller reads and CP-008-15's capture leg consumes (D-008-5). **This column ships in its own later migration, not the four-table CREATE:** Phase 1 already shipped that migration as version 4 (`0004-worktree-lifecycle.ts`), so the column lands by the documented table-rebuild migration — create the successor with `checkout_root TEXT NOT NULL` in canonical position, copy omitting the column, drop, rename, recreate the index (T3.2's migration paragraph carries the steps; the References row cites the procedure) — in the next-ordinal guarded block belonging to **Phase 3**, the first phase with a writer for it (T3.2's run-setup gate). Scheduling it earlier would ship a NOT NULL column no code can populate; scheduling it later would let T3.2 write a column that does not exist. A column add is not a table add, so no table-census figure moves.
- See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) for column definitions — the audited DDL there is the table's final shape, and is the verbatim migration content for every column of the Phase-1 CREATE; `checkout_root` is the one column carried there ahead of its own Phase-3 table-rebuild migration, flagged as such in its comment (schema-doc order and post-rebuild `PRAGMA table_info` order identical — no `retention_class`-style CID-last divergence).

Consent: Plan-007 T-007-2B-4 EXTENDs `packages/runtime-daemon/src/workspace/execution-root-service.ts` INSIDE Phase 2B — atomic with the identity change, so neither half ships alone — re-rooting the branch arm at `workspaces.metadata.boundRoot` (fallback `canonical_root` when the key is absent, keeping rows that predate the key byte-identical, with no backfill migration) and pointing `#verifyBranchModeBind` at the same value; the Spec-008 branch-mode sentence is corrected in the same PR (Spec-008 and this plan flip-and-restored `approved` in-swap). This plan's code comments and tests that still say "shared main checkout" update in that Phase-2B PR, not before — until it lands, shipped behavior remains lawful under the shipped per-directory identity, and Plan-007's carrier box holds the pair. **Direction:** Provide consent to [Plan-007](./007-repo-attachment-and-workspace-binding.md) (reciprocal CP-007-9). **Tasks:** T2.4 (shipped surface; the EXTEND executes under Plan-007 T-007-2B-4).
- **CP-008-15 — Turn-snapshot capture normalized to the enclosing working-tree top level (reciprocal of Plan-007 CP-007-10; consent for the Phase-2B EXTEND).** The Phase-5 snapshot service's capture legs (`git -C <executionRoot> ls-files …`) are cwd-scoped, so once CP-008-14 makes a nested `boundRoot` a lawful branch-mode execution root, an un-normalized nested capture lists only the nested prefix and the snapshot then names a narrower tree extent than the run works in — the misnamed-point shape the 2026-08-17 carried-findings adjudication closes. Consent: Plan-007 T-007-2B-4 EXTENDs `packages/runtime-daemon/src/git/turn-snapshot-service.ts` INSIDE Phase 2B — shipped together with the CP-007-9/CP-008-14 leg, because the nested shape becomes reachable exactly when branch mode re-roots at `boundRoot` — normalizing capture's execution-root input to the enclosing working-tree top level at service entry (one normalization site, so every capture addresses the whole tree the run works in), with [Spec-008 §Turn-Boundary Snapshots](../specs/008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)' applicability bullet recording the rule in the same swap. **Transport of the normalized root.** The value is derived while the tree exists and reaches the callee down a five-link carrier chain, each link a write the previous link's tree existence justifies: (1) bind-time derivation into `workspaces.metadata.checkoutRoot`; (2) rewrite of that key when provisioning installs a new execution root; (3) capture into `run_execution_contexts.checkout_root` by the T3.2 run-setup gate at context creation, deriving the top level from the just-materialized `execution_root` and healing the carrier when the workspace key is absent on a row that predates the key (never `canonical_root` — the bind-time checkout, not a provisioned run's own tree) — the heal a **Plan-007-consented delegated write** of the Plan-007-owned metadata key, registered on CP-007-10's ownership sentence: one write path, the gate applying Plan-007's provisioning-completion rewrite rule at the handoff, never a second writer discipline; (4) supply by the B9 caller as the CP-008-12 `checkoutRoot` parameter, read from the same run-context row it already reads `execution_root` and `execution_mode` from; (5) receipt by the callee. Capture re-verifies the supplied value against the live tree (it runs while the tree exists) and fails typed on disagreement. Link (3) is what makes the chain durable rather than merely persistent: like `git_common_dir`, the value is snapshotted per run at context creation, so it survives a later reprovision of the workspace row — the callee is never asked to read a `workspaces` row, let alone walk a filesystem path, to find out where the tree top is. **CP-008-12's pure-callee contract is therefore unchanged in the strict sense, not merely the compatible one:** the callee gains an input, not a lookup — it reads no `workspaces` row, performs no upward filesystem walk to normalize, and holds no dependency on the execution root still existing; the growth is confined to CP-008-12's caller-resolved enumeration. The normalization carries a concurrency corollary, closed in the adjudication PR's own review round: run tenancy re-keys on the same normalized root ([Spec-008 §State And Data Implications](../specs/008-worktree-lifecycle-and-execution-modes.md#state-and-data-implications); the CP-008-4 busy bracket), so no two active runs share one normalized checkout and a whole-tree snapshot capture never crosses another run's live state. That exclusivity is **node-scoped by the query's shape, not by assumption**: `workspaces` carries no node column, so the hold comparison reads the local daemon's `workspaces` rows joined through their `repo_mount_id` to `repo_mounts.node_id` — the same owning-node column `idx_repo_mounts_active_root` keys canonical-root uniqueness on — filtered to the deciding node (a `workspaces`-only comparison could not even express the filter). The filter is load-bearing, not decorative, because one node's local database lawfully holds rows for more than one node's mounts — D-007-7's active-root uniqueness binds per owning node precisely because the same absolute path on two different nodes both attach, two distinct node-local filesystems ([Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications)) — so two nodes' identical absolute spellings of a checkout path never enter one comparison set. No cross-node coordination is implied or required, and none is added. **Direction:** Provide consent to [Plan-007](./007-repo-attachment-and-workspace-binding.md) (reciprocal CP-007-10). **Tasks:** T5.1 (shipped callee surface; the EXTEND executes under Plan-007 T-007-2B-4, on the `checkout_root` carrier T3.2 captures).

## Design Decisions

- **D-008-1 — Contract file is `packages/contracts/src/worktree.ts`** (renamed from the pre-audit `execution-mode.ts`): the file's dominant content is the worktree/clone lifecycle domain; one-file-per-domain.
- **D-008-2 — Consolidated wire block.** Seven request/response pairs + `EphemeralCloneId`/`BranchContextId` brands + `EphemeralCloneState` enum defined in api-payload-contracts.md §Plan-008 (brands/enums declared in-block for cite stability). Clone-prepare responses report effective `cleanupPolicy` + `expiresAt`; select responses carry `executionRoot` only when resolved synchronously.
- **D-008-3 — Method namespace is `repo.*`, seven methods** (`repo.executionModeSelect`, `repo.executionRootPrepare`, `repo.worktreeReuseCheck`, `repo.ephemeralClonePrepare`, `repo.ephemeralCloneDispose`, `repo.worktreeRetire`, `repo.worktreeStatusRead`). A `worktree.*` method root was considered and rejected: the namespace-root enumeration admits `repo` and no `worktree` root; mounts/workspaces/worktrees/clones are one repo aggregate; sibling symmetry with `repo.executionModeCapabilitiesRead`. Imperative method strings stay disjoint-by-form from the past-participle Spec-005 event names.
- **D-008-4 — Error vocabulary.** §Worktree: `worktree.not_found` 404, `worktree.create_failed` 500, `worktree.branch_collision` 409, `worktree.reuse_conflict` 409, `worktree.retire_conflict` 409. §Ephemeral Clone: `clone.not_found` 404, `clone.prepare_failed` 500. §Workspace extension rows: `workspace.branch_name_required` 400 (D-008-19), `workspace.branch_mismatch` 409, `workspace.busy` 409, `workspace.execution_root_unresolved` 409. Deliberately NO `worktree.unsupported`: select-time capability refusal is `workspace.mode_unsupported` (D-007-5); prepare-time dynamic unavailability IS `worktree.create_failed` (500, matching `workspace.provisioning_failed`'s class).
- **D-008-5 — Persistence model (4 tables; DDL in local-sqlite-schema.md, verbatim per migration except the one rebuild-added column called out below).** `worktrees` carries `created_by_session_id` NOT NULL + `created_by_run_id` nullable (provenance; session/run ids event-sourced, no FK) + `cleaned_at` + the partial-unique `idx_worktrees_active_branch ON (repo_mount_id, branch_name) WHERE state NOT IN ('retired','failed')` — git-faithful: a `merged` checkout still holds its branch; `failed` creations never materialized one. `ephemeral_clones` carries `branch_name` NOT NULL (head branch inside the clone — the status read exposes branch for clone records per [Spec-008 §Interfaces And Contracts](../specs/008-worktree-lifecycle-and-execution-modes.md#interfaces-and-contracts)), `expires_at` NOT NULL, `updated_at`, `cleaned_at`, CHECKed `cleanup_policy`, and the sweep index `(state, expires_at)`; no `created_by_run_id` (the run edge lives in `run_execution_contexts`). `branch_contexts` is workspace-anchored (`workspace_id` NOT NULL) with nullable `worktree_id`/`ephemeral_clone_id`, an at-most-one CHECK, and the partial-unique binding index `idx_branch_contexts_worktree_workspace ON (worktree_id, workspace_id) WHERE worktree_id IS NOT NULL` — one binding row per (workspace, worktree) per D-008-15's upsert semantics, so the worktree-keyed `BranchContextRead` resolves exactly one row on the (worktreeId, workspaceId) pair. `run_execution_contexts` (NEW) is the per-run execution binding: `run_id` PK (event-sourced, no FK), `session_id`, `workspace_id`, `execution_mode`, `execution_root`, `checkout_root` NOT NULL (the enclosing working tree's top level for that `execution_root`, captured at context creation by the T3.2 gate from `workspaces.metadata.checkoutRoot`, derived from the just-materialized `execution_root`'s top level — with the workspace carrier healed — when the key is absent on a workspace row that predates the key, so the column is always satisfiable and needs no backfill; it is the durable normalized root CP-008-15's capture leg consumes and the fourth link of that obligation's carrier chain, supplied onward as a CP-008-12 caller-resolved parameter. **This column is the plan's one rebuild-added column:** Phase 1 shipped the four-table CREATE as migration version 4 (`0004-worktree-lifecycle.ts`), so `checkout_root` lands in a next-ordinal guarded block with **Phase 3** — the phase of T3.2, its only writer — by the documented table-rebuild, not an `ADD COLUMN`: the ALTER documentation refuses a NOT-NULL-without-default add unconditionally, and the empty-table allowance the bundled engine exhibits is undocumented. The `NOT NULL`-without-default declaration is lawful in a rebuild because the successor table is created, not altered; the copy step omits the column, so a pre-existing row would fail the engine-enforced NOT NULL at copy time — failing the migration closed instead of inventing a value — and the table is in fact row-less in every deployed instance, never having had a production writer), `git_common_dir` NOT NULL (the `git rev-parse --git-common-dir` absolute path captured at context creation — the surviving canonical git dir for snapshot-ref operations, so T5.3 prunes refs through it, never through a possibly-retired `execution_root`; worktree mode resolves to the main repo's git dir, branch/read-only to `<root>/.git`, ephemeral clone to the clone's own git dir — those refs share the clone's disposal lifecycle per T5.3), optional `worktree_id`/`ephemeral_clone_id`/`branch_context_id`, `created_at`, `released_at`, and a mode-conditional CHECK binding id presence to `execution_mode` (worktree ⇒ `worktree_id` set, ephemeral clone ⇒ `ephemeral_clone_id` set — the other root id NULL in each; every writable mode carries `branch_context_id`; read-only carries none of the three). `checkout_root` and `git_common_dir` are the two columns deliberately held OUTSIDE that mode-conditional CHECK: both are captured unconditionally, on read-only rows included, because their consumers are mode-agnostic — the CP-008-4 checkout-keyed run tenancy and the I-008-14 run gate apply to every repo-bound run regardless of mode, and a read-only run whose row lacked a checkout root could not participate in the tenancy comparison it is subject to.
- **D-008-6 — Execution-root placement + trust envelope.** Daemon-provisioned roots live under the daemon's own execution-roots directory, never inside the attached checkout — a worktree at `~/.ai-sidekicks/worktrees/<project>/<name>`, the literal the create form's path hint shows ([Spec-008 §Required Behavior](../specs/008-worktree-lifecycle-and-execution-modes.md#required-behavior)); an ephemeral clone at `<executionRootsDir>/<repoMountId>/clones/<id>`; they are in-envelope by construction ([Spec-007 §Local Trust Envelope (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#local-trust-envelope-v1-definition) daemon-provisioned-roots clause). The mount's canonical root hosts the `git -C <canonicalRoot> worktree add <rootPath> …`-shaped invocations only.
- **D-008-7 — Collision policy is provenance-split.** Caller-supplied `branchName` colliding with a live checkout → typed `worktree.branch_collision` refusal (user intent never adapted). Daemon-derived default name colliding → first-free ordinal suffix (`-2`, `-3`, …), persisted + reported verbatim. Service parameter `onCollision: 'refuse' | 'suffix'`: wire prepares always pass `refuse`; the run-setup gate's derived-name path passes `suffix`. The partial-unique index arbitrates races (insert-retry loop). Collision never implies implicit reuse.
- **D-008-8 — Base-ref policy.** Worktree base defaults to the mount's current HEAD branch; `baseRef?` overrides explicitly; a detached-HEAD mount with no explicit base ref → typed refusal (`worktree.create_failed` with detail), never a guess.
- **D-008-9 — `branch` mode is bind-only.** Prepare verifies the BOUND checkout's current branch — read at `workspaces.metadata.boundRoot`, the main checkout or a linked worktree, with the `canonical_root` fallback for a row that predates the keys (CP-008-14) — equals the requested branch context and refuses `workspace.branch_mismatch` otherwise; the daemon never runs `git checkout`/`switch`/`branch` in the bound checkout OR the main checkout. Verification carries a linked-worktree assertion (2026-08-17 carried-findings adjudication, executed with the re-rooting under Plan-007 T-007-2B-4): the branch-mode prepare fixture binds a linked worktree and asserts prepare mutates NEITHER tree — bound worktree and main checkout byte-identical before and after — because the main-checkout-only scope, written when branch mode's root WAS the main checkout, would let an implementation mutate the bound linked checkout and still satisfy the recorded immutability checks.
- **D-008-10 — Hook neutralization.** Every provisioning git invocation runs via `execFile` argv-only (no shell) with `-c core.hooksPath=<empty dir>` and `-c core.fsmonitor=false` — the second flag because the fsmonitor hook is named by config value rather than by a `hooks/`-resident file, so `core.hooksPath` never governs it (index-refreshing verbs such as `status` and `worktree add` invoke a repo-local `core.fsmonitor=<pathname>` despite an empty `core.hooksPath`; empirically confirmed on git 2.50.1); acceptance fixtures install sentinel `post-checkout`/`post-merge` hooks plus a config-named fsmonitor sentinel in a hostile fixture repo and assert no sentinel ever fires for a service invocation.
- **D-008-11 — No new event types.** This plan adds no rows to the Spec-005 registry: no `worktree.failed` event, no ephemeral-clone events — the five `worktree.*` rows Spec-005 already enumerates are union-registered by T1.1 per CP-008-5 (registration of existing rows, not new types). Rationale: worktree rows are table-sourced (not event-replayed); the failure incident is already evented as `workspace.stale` with `metadata.lastError` (single-incident-single-event); failed rows stay queryable via `repo.worktreeStatusRead`; reopening Plan-005's registry needs more than symmetry. The deliberate carve-out is pinned by a T2.1 regression test.
- **D-008-12 — Event-transition mapping.** Row creation → `worktree.created`; `creating -> ready` → `worktree.ready`; `-> dirty` → `worktree.dirty`; `-> merged` → `worktree.merged`; `-> retired` → `worktree.retired`; `-> failed` → none (the coupled `failReprovision` emits `workspace.stale`). Emission is transactional with the row write; the payload is `WorktreeLifecyclePayloadSchema` — Plan-007's family shape instantiated over `WorktreeStateSchema` (`worktreeId` populated).
- **D-008-13 — Cleanup sweep.** One daemon tick drives: (a) TTL-expired clones (`expires_at` past, state in `creating`/`ready`); (b) clones whose owning workspace is `archived` (detach cascade); (c) worktrees whose mount is `detached` (non-terminal states → retired, events emitted, metadata preserved); (d) disk removal for retired-but-uncleaned rows, idempotent, stamping `cleaned_at`. Retiring the clone backing a live (non-archived) clone-mode workspace's current root returns that workspace to `provisioning` via Plan-007 primitives — `stale` is reserved for fault paths ([Spec-007 §Ephemeral Clone Lifecycle](../specs/007-repo-attachment-and-workspace-binding.md#ephemeral-clone-lifecycle)).
- **D-008-14 — Select records; prepare materializes.** `repo.executionModeSelect` records the canonical mode and transitions the workspace (`beginReprovision` for writable targets; synchronous complete for `read-only`); per-task root materialization happens at `repo.executionRootPrepare` or the run-setup gate — architecturally forced, since worktree/clone roots are per-task and a select carries no task context. The picker fires exactly one select mutation per switch; selecting on a `stale` workspace is the repair path.
- **D-008-15 — Explicit reuse + dirty acknowledgement.** `reuseWorktreeId` names the candidate; `acknowledgeDirtyCandidate: true` is the separate consent that binds a DIRTY candidate (TOCTOU-sound: a candidate that turned dirty after the check refuses `worktree.reuse_conflict` when the ack is absent). An incompatible candidate never binds regardless of acknowledgement. Explicit reuse preserves the candidate's existing branch-context row when the candidate already belongs to the requesting workspace; cross-workspace reuse upserts the binding workspace's own `branch_contexts` row — a first binding inserts a NEW row scoped to that workspace (branch values carried over from the candidate's row, which is left untouched as history); a workspace re-binding a worktree it historically bound refreshes its existing pair row in place (carried-over branch values + `updated_at`) instead of inserting a duplicate, so exactly one row exists per (workspace, worktree) (the partial-unique `idx_branch_contexts_worktree_workspace`) — `branch_contexts.workspace_id` must always name the workspace the binding serves, or workspace-scoped consumers (approval path-scope matching, `idx_branch_contexts_workspace`) resolve the wrong workspace.
- **D-008-16 — Run-setup binding.** Plan-008's gate (registered on the Plan-003 T3.10 seam per CP-008-9) implements `assertRunReady`: resolve the queue item's `workspaceId` → `assertWritable` (writable modes; lawfully skipped when the workspace already sits `provisioning` — the open-bracket scoping of I-008-12 / CP-008-3) → materialize/bind the root (derived branch name per the slug rule, `onCollision: 'suffix'`) → `markBusy` → write the `run_execution_contexts` row. `onRunTerminal` releases in reverse: `releaseBusy`, stamp `released_at`, fire `on_run_complete` clone retirement (with the D-008-13 workspace disposition). Refusal parks the run in `starting` (`workspace.execution_root_unresolved` wrapping the underlying typed cause); a run on a busy workspace refuses `workspace.busy` (one-holding-run V1 rule).
- **D-008-17 — Status read + stale-diagnostic surface.** `repo.worktreeStatusRead` returns the session's worktree + clone rows with provenance (D-008-2 shape). The owning-workspace stale diagnostic rides Plan-007's `WorkspaceListResponse.lastError?` (additive, in the §Plan-007 block and Plan-007 T1.3). No invented wire names: Phase 4 views consume exactly the contract names.
- **D-008-18 — `ModeSwitchOptions` is an own presentational component** (props-only: `availableModes`, `restrictions`, current mode, disabled state) composed by `ExecutionModePicker`; no import from `../repo-attach/` (CP-008-13 boundary).
- **D-008-19 — Wire prepares carry the branch; the slug rule is gate-only.** The Spec-008 slug rule ([Spec-008 §Resolved Questions and V1 Scope Decisions](../specs/008-worktree-lifecycle-and-execution-modes.md#resolved-questions-and-v1-scope-decisions)) derives from run-scoped inputs (originating queue-item summary; `run-<run-short-id>` fallback) that exist only on the run-setup gate path (D-008-16). Wire-initiated prepares are pre-run by definition and carry no derivation seed: `repo.ephemeralClonePrepare` requires `branchName` on the wire, and a writable-mode `repo.executionRootPrepare` carrying neither `branchName` nor a service-side `runId` draws the typed `workspace.branch_name_required` refusal (400) before any git call — `read-only` prepares ignore the field. `ExecutionRootPrepareRequest.branchName?` optionality is therefore mode-conditional requiredness enforced service-side, not schema-optional-everywhere. Below T2.4 the mode services take `branchName` required (`worktree-service.create`, `ephemeral-clone-service.prepare` — neither holds derivation inputs); T2.4 resolves the name first (pass-through when supplied; the `run-<short-8>` fallback via the T2.2 helper when only `runId` arrived) — the queue-summary primary rule fires only at the gate, the sole holder of the summary.

non-sparse roots never write the trailer, so the common case's no-trailer OID stability stands, the whole message streamed to `commit-tree` via `-F -` on a daemon-written-and-closed stdin rather than `-m` argv — an unbounded set never meets a platform argv bound such as Windows' ~32K command line; ## Risks And Blockers

- Branch naming collisions — mitigated by D-008-7 (provenance-split policy + index-arbitrated retry)
- Git edge cases on repos with unusual worktree support — surface as typed `worktree.create_failed`, never substitution (I-008-7)
- Ephemeral clone cleanup may leak disk usage — mitigated by D-008-13 (TTL sweep + `cleaned_at` idempotent stamping); residual risk: daemon down past TTL windows
- Repositories with mandatory bootstrap steps need explicit follow-on setup flows ([Spec-008 §Fallback Behavior](../specs/008-worktree-lifecycle-and-execution-modes.md#fallback-behavior)) — out of scope here by design
- Registry regex conformance and the typed-error projection are Plan-006-owned Phase-3 preconditions; if they slip, Phases 1–2 still land
- A rollback's conversation leg is a provider-side rewind, and it is Plan-004's to own on both providers: each cuts in place on the session or thread the run already holds — Codex's `thread/revert {threadId, beforeTurnId}` and Claude Code's `rewind_conversation {target_message_uuid, interrupt_if_running}` control request ([`codex.md`](../reference/provider-wire/codex.md), [`claude.md`](../reference/provider-wire/claude.md), [Spec-004 §Per-Driver Capability Matrix](../specs/004-provider-driver-contract-and-capabilities.md#per-driver-capability-matrix)) — so no second thread or session is minted, no live provider binding is re-pointed, and nothing about this plan's snapshot legs depends on either. Neither verb touches a file, so the files come from the daemon's own per-session file checkpoint store ([Spec-013 §Required Behavior](../specs/013-persistence-recovery-and-replay.md#required-behavior)) and a snapshot only names the point to return to. What stays unverified on both is a rewind across a provider-side context-compaction boundary — whether the rewound conversation reconstructs pre-compaction context or resumes from the compacted summary alone — the case a rewind target older than a boundary lands in, which [Spec-003 §Driver-Level Rollback Mechanics](../specs/003-queue-steer-pause-resume.md#driver-level-rollback-mechanics) refuses until it is measured; re-verify each verb against the then-installed provider binary before any code coordinating it lands, per [ADR-017](../decisions/017-shared-event-sourcing-scope.md)
- Field evidence against per-turn git checkpointing, and why neither ground transfers: a surveyed reference runtime shipped per-message git checkpointing (hidden snapshot refs plus a revert that restored files) and later removed it, on two stated grounds — snapshot refs polluting ordinary repo tooling, and a file-restore path users never took. Ref pollution is foreclosed here by construction rather than by discipline: I-008-21 confines every ref to `refs/sidekicks/runs/<runId>/epoch-<E>/turn-<N>`, invisible to branch history, PR preparation, and diff attribution; I-008-22 makes each write create-only per epoch, so no ref is ever repointed; and T5.3's retention prune bounds the namespace over time (daemon-startup reconcile plus periodic sweep, ref ops routed through `run_execution_contexts.git_common_dir` so a run's refs stay reclaimable after its execution root is gone). The never-used ground is a different product shape, not a weaker version of this one: there, checkpointing was an optional per-message affordance offered to users who can run git themselves, so non-use is a real signal; here the per-turn snapshot is the daemon's own record of the point a turn ended at, which a restore aimed at a named snapshot of the session resolves against while the files themselves come from the file checkpoint store ([Spec-013 §Required Behavior](../specs/013-persistence-recovery-and-replay.md#required-behavior), [Spec-003 §Driver-Level Rollback Mechanics](../specs/003-queue-steer-pause-resume.md#driver-level-rollback-mechanics)) — so dropping it would not retire an unused affordance, it would leave a session unable to name the points it can return to

- [SQLite — Foreign Key Support §5 "CREATE, ALTER and DROP TABLE commands"](https://www.sqlite.org/foreignkeys.html#fk_schemacommands) — the primary source for T1.3's deliberate forward FK references to the Plan-007 Phase 2 tables `repo_mounts` and `workspaces`, which is what makes Plan-007 Phase 2 a Phase-**2** gate rather than a Phase-1 one. Create time is unchecked: "A CREATE TABLE command operates the same whether or not foreign key constraints are enabled. The parent key definitions of foreign key constraints are not checked when a table is created. There is nothing stopping the user from creating a foreign key definition that refers to a parent table that does not exist." Detection is deferred to statement preparation — such errors "prevent the application from preparing SQL statements that modify the content of the child or parent tables in ways that use the foreign keys" — and the page names the exact message the daemon sees: "The English language error message for foreign key DML errors is usually 'foreign key mismatch' but can also be 'no such table' if the parent table does not exist." That last clause is why `packages/runtime-daemon/src/migrations/0004-worktree-lifecycle.ts#WORKTREE_LIFECYCLE_MIGRATION_SQL` — the exported SQL constant carrying the forward `REFERENCES` clauses, which is the evidence this row rests on — documents a premature insert as `SQLITE_ERROR: no such table`, not `SQLITE_CONSTRAINT_FOREIGNKEY` (confirmed 2026-07-26).
- [SQLite — Foreign Key Support §2 "Enabling Foreign Key Support"](https://www.sqlite.org/foreignkeys.html#fk_enable) — the precondition the clause above depends on, and the reason the premise is not vacuous here: "Foreign key constraints are disabled by default (for backwards compatibility), so must be enabled separately for each database connection." The daemon enables them for every connection in `packages/runtime-daemon/src/session/migration-runner.ts#applyPragmas` (`db.pragma("foreign_keys = ON")`), so the DML-time enforcement above is the live path rather than the default-off one. - [RFC 9562 §5.7 — UUID Version 7](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7) — the field layout behind the short-id rule — `<session-short-id>` and `<run-short-id>` are the **last** 8 hex characters of their UUIDs: a v7 id is a 48-bit `unix_ts_ms` millisecond timestamp, the 4-bit `ver`, 12 bits of `rand_a`, the 2-bit `var`, and 62 bits of `rand_b`, so the first 8 hex characters are timestamp bits shared by every id minted in one 65,536 ms window and the last 8 are random bits.
