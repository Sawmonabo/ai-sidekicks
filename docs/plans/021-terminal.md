## Goal

Run every shell inside the daemon, on every operating system, through `sidekicks-terminal`: each shell's PTY on `alacritty_terminal`'s `tty` (ConPTY on Windows), read by its own read loop, with the daemon's copy of its screen on `alacritty_terminal`, and sign the Windows programs. No process sits between the daemon and its shells. `node-pty` is not used, because of the ConPTY fault cluster ADR-018 names ([openai/codex#13973](https://github.com/openai/codex/issues/13973), [microsoft/node-pty#904](https://github.com/microsoft/node-pty/issues/904), [microsoft/node-pty#887](https://github.com/microsoft/node-pty/issues/887), [microsoft/node-pty#894](https://github.com/microsoft/node-pty/issues/894)); the cost of running the PTY in the daemon's own process is that a native ConPTY crash takes the daemon down ([ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-in-the-daemon.md#decision)).

## Build Order

Daemon-foundational, beside Plan-001. Standalone for Phases 1–3 (no upstream plan dependencies); Phase 3B follows Phase 3 with no other gate, and Phases 4–5 are the release tail, whose signing step runs once [BL-108](../backlog.md#bl-108-signpath-foundations-acceptance-for-windows-signing) records SignPath Foundation's acceptance. Phase 3B's macOS tasks land in the `calling-device`, `shell-control-lease` and `terminal-daemon` units; its Windows tasks, Phase 5 and most of Phase 4 land in `windows`, and Phase 4's signing tasks in `release` ([cross-plan-dependencies §Units](../architecture/cross-plan-dependencies.md#units)).

## Scope

- `crates/sidekicks-terminal`, the library crate the daemon runs in-process on every operating system: each shell's PTY through `alacritty_terminal::tty` (ConPTY on Windows), each shell's own read loop, the write path, the exit capture and the kill semantics
- Terminal output and scrollback reaching a client as raw bytes in the frame codec's attachments ([ADR-009](../decisions/009-json-rpc-ipc-wire-format.md)), with no partial-character hold-back
- The Windows terminal in the daemon: Ctrl+C as byte `0x03` on the ConPTY input, the hard stop through the daemon's `console` mode and `taskkill /T /F`, and ConPTY taken from kernel32 with the library search set to System32
- **Windows signing** through SignPath Foundation's free open-source program: one step in the release workflow signs the Electron app and the native programs it ships, `sidekicks-daemon`, `sidekicks`, the client's `.node`, and `libpdfium` among them, under one publisher ([ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-in-the-daemon.md#decision) items 5 and 6)
- The Windows legs of CI, `windows-latest` for `x86_64-pc-windows-msvc` and `windows-11-arm` for `aarch64-pc-windows-msvc`, build and test the daemon with its terminal for x64 and arm64
- **Phase 3B — PTY substrate hardening:** the two-layer orphan-process defense per ADR-018 (per-OS kernel containment through the daemon's one spawner thread and its `shell` mode, and on Windows the daemon's own kill-on-close Job Object; daemon-side crash-safe orphan registry + boot-id-guarded sweep with the pidfd-preferred Linux signal path); a session's shells (`terminal.subscribe`, `terminal.open`, `terminal.close`, `terminal.reorder`, `terminal.output.subscribe`, `terminal.write`, `terminal.resize`) and the Spec-002 per-shell write lease enforced at the daemon terminal-write boundary (`control_lease.rs`, `terminal.control.take`), held in the daemon alone; each shell's prompt and command marks; an agent's command run in one of a session's shells through the `shell_run` callback tool, under that shell's lease held for the agent's run, answered with its exit code and output; real `signal_code` population; the terminal's own flow control propagated to the PTY per shell and per watching connection through the shell's read loop; and the I-021-1/I-021-2 Windows kill end to end on the daemon's in-process ConPTY

## Non-Goals

- WezTerm-level terminal-emulator features — the daemon's screen copy answers what a program asks its terminal and renders an agent's command output; it draws no interface
- A terminal process apart from the daemon — the PTY runs inside the daemon on every operating system, with no program, stdio protocol or package of its own

## Invariants

Invariants I-021-1 through I-021-5 come from §Windows Implementation Gotchas (which carries their rationale and primary-source citations); I-021-1 and I-021-2 hold on Windows, I-021-3 on a Windows computer with sessions in a WSL 2 distribution, and I-021-4 and I-021-5 on every platform. I-021-6 through I-021-9 land with the Phase 3B substrate hardening — their sources are the [ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-in-the-daemon.md#decision) items and the [Spec-002 §Required Behavior](../specs/002-machine-registration.md#required-behavior) shared-terminal write-lease contract, and they hold on every platform (I-021-7/I-021-8 at the daemon terminal-write boundary).

### I-021-1 — On Windows, Ctrl+C is byte `0x03` on the ConPTY input and the hard stop is the `console` mode

The daemon's kill of a shell's command on Windows MUST translate POSIX signal semantics to the console's: `SIGINT` writes byte `0x03` to the ConPTY input, which the console turns into `CTRL_C_EVENT` for every process on it while `ENABLE_PROCESSED_INPUT` is set (a program that cleared that mode reads it as a keystroke, as in a real terminal); the hard stop runs the daemon's short-lived `console <pid>` mode — `FreeConsole`, `AttachConsole(pid)`, then its own `SetConsoleCtrlHandler` routine returning TRUE (attaching resets the handler table, and the default handler would end the helper by its own break), then `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, 0)`, group 0 because `alacritty_terminal` starts shells without `CREATE_NEW_PROCESS_GROUP` — followed by escalation per I-021-2 if the child does not exit within a bounded interval. A nonzero process group receives no `CTRL_C_EVENT`, so no call sends one to the child's pid. The console calls are `sidekicks-platforms`' Windows module's. Source: §Windows Implementation Gotchas Gotcha 1 (`microsoft/node-pty#167`). **Verification:** Phase 3B Tests K2–K3 on the Windows leg, through the daemon's in-process ConPTY (T-021-3B-4).

### I-021-2 — Hard-stop teardown uses `taskkill /T /F` for full process-tree termination

A single-PID kill on Windows leaves descendants orphaned. The hard-stop path MUST invoke `taskkill /T /F /PID <root-pid>` so the entire descendant tree terminates, the root pid read from `Pty::child_watcher().pid()`, which is an `Option`. Reaping MUST be idempotent and MUST NOT block the shell's read loop — `taskkill` runs with a timeout and the shell's exit is reported even if reaping is incomplete, so the daemon can mark the shell ended without hanging on a stuck OS-level operation. Source: §Windows Implementation Gotchas Gotcha 2 (`microsoft/node-pty#437`). **Verification:** Phase 2 Test K1 (the `tests` module of `crates/sidekicks-terminal/src/kill.rs` — over a fake child at one root PID, asserts the hard stop hands `taskkill` that root PID alone with `/T /F`, so the OS walks the tree: `SIGTERM` escalates to it at the 2 s budget, `SIGKILL` invokes it at once, and the exit is reported whether the reap succeeds, fails or never returns, the last bounded at 5 s); end to end on the Windows leg at T-021-3B-4 (Tests K2–K3).

### I-021-3 — WSL 2 path translation happens in the daemon, before any spawn

`sidekicks-terminal` MUST hand a shell's spawn the paths it is given and MUST NOT invoke `wslpath` or any Windows ↔ WSL 2 path conversion. On a Windows computer the service is the native daemon; a session in a WSL 2 distribution runs its shells through that distribution's WSL server, in `sidekicks-terminal` on Linux in the person's login shell with a Linux working folder, and the daemon translates every path before the spawn, `sidekicks-platforms` for the `\\wsl.localhost` form and `wslpath` run in the WSL server for the rest; the daemon on Windows never invokes `wslpath` itself. Source: §Windows Implementation Gotchas Gotcha 3. **Verification:** held in review: `sidekicks-terminal` holds no path translation.

### I-021-4 — The app's quit never stops a shell; shells end only when the service stops

The desktop app never owns a shell. The shells run inside the daemon, and the daemon is the person's own background service, never a child of the app: quitting the app flushes the service (`daemon.flush`) and leaves the service, every run and every shell running, so no Electron quit handler touches a shell, and a server started in a shell is still serving after a relaunch. Only the service's own stop — Runtime's `Stop` or `Restart`, or the operating system's service manager stopping it — ends the shells, and that stop drains them before the daemon exits: every live shell gets the hard stop (`SIGTERM`, or the `console` mode's `CTRL_BREAK_EVENT` on Windows), and one that has not exited at `DAEMON_STOP_TERMINAL_DRAIN_MS` (2 s) is killed (`SIGKILL`, or `taskkill /T /F /PID` on Windows), inside the service's drain bound `DAEMON_STOP_DRAIN_BOUND_MS` (4 seconds), so no child process orphans when the service exits. No surface explains either rule; the behavior is the rule. **Cross-plan obligation:** Plan-001 owns the drain orchestration per [Plan-001 §Cross-Plan Obligations CP-001-1](./001-session-core.md#cp-001-1--the-terminal-drains-when-the-service-stops); Plan-021 supplies `sidekicks-terminal`'s drain. Source: §Windows Implementation Gotchas Gotcha 4 (`microsoft/node-pty#904`). **Verification:** Plan-001's Test I4 (`crates/sidekicks-daemon/tests/it/terminal_drain.rs`).

### I-021-5 — A shell starts so its worktree stays removable; the daemon performs the translation

A shell's start MUST leave its worktree removable. Windows keeps a handle on every process's current folder: the ConPTY host starts in the daemon's own folder and keeps it, and a process keeps the folder it starts in until it moves its own. The PTY therefore spawns the daemon's `shell` mode, not the shell, in a stable folder, and the mode starts the shell in the folder its start confirmation names: on Windows the mode is spawned in the system folder as Windows reports it (`FOLDERID_System`, where Windows Terminal keeps itself), starts the shell with that folder as its current folder (`Command::current_dir`) and keeps its own for its whole wait; on macOS and Linux it is spawned in the stable folder the daemon names and enters the shell's folder (`chdir`) before it execs the shell. PowerShell (`pwsh.exe`, `powershell.exe`) never moves its process folder on `Set-Location`, so it starts in the system folder and is told its worktree by its own switches, each user argument read as PowerShell's parser reads it (the switch character `-`, `/`, `--` or a Unicode dash, then any prefix of the switch's name down to the shortest form that PowerShell takes or an alias it takes, such as `-ep` for `-ExecutionPolicy`, without case). `pwsh.exe` takes `-NoLogo -WorkingDirectory <worktree>` (a trailing `\` stripped) ahead of the user's arguments, which runs as `Set-Location` before the profiles, so it combines with the user's own `-Command`; where those arguments run a script by a relative path (a `-File` form or a bare script path, which pwsh resolves against its process folder), it starts in the worktree with them unchanged, while `-File -` (standard input) and a complete script path keep the switch. `powershell.exe` takes `Microsoft.PowerShell.Management\Set-Location -LiteralPath '<worktree>'`, every character PowerShell reads as a single quote (`'`, U+2018, U+2019, U+201A, U+201B) doubled in the path, only where each user argument before it is one of Windows PowerShell's own start switches `-NoLogo`, `-NoProfile`, `-NoExit`, `-NonInteractive`, `-ExecutionPolicy <value>` (`-ep`), `-Mta`, `-Sta`, `-WindowStyle <value>`, `-InputFormat <value>`, `-OutputFormat <value>` or `-ConfigurationName <name>`, or, at the line's front, where alone its native entry reads them, `-Version <value>` as the first argument and `-PSConsoleFile <file>` first or after it, each with one dash (`-ServerMode` and `-RuntimeVersion`, which that entry reads there too, are refused): as `-NoLogo -NoExit -Command "Microsoft.PowerShell.Management\Set-Location -LiteralPath '<worktree>'"` after those arguments. A user command given as text, after `-Command` (not `-`, which reads standard input) or as a bare word, which Windows PowerShell reads as its command, every value from its first on joined by one space, becomes one argument: `Microsoft.PowerShell.Management\Set-Location -LiteralPath '<worktree>'; Microsoft.PowerShell.Utility\Invoke-Expression '<text>'`, the text a single-quoted string with every single-quote character in it doubled, so no text breaks out of it; an empty text, which `Invoke-Expression` refuses, and a whitespace text, which runs nothing, both become the `Set-Location` alone. Both cmdlets are named with their modules, so a profile's alias or function of the same name cannot take the call. `Invoke-Expression` parses the text as a script of its own, which takes `using`, a param block, named blocks and comments at its start or end, and runs it in the session's scope, so its functions and variables stay in the session; Windows Terminal's `powershell.exe` developer shell starts in the system folder too. Two exposures are named, which no start avoids: .NET's own current folder in that shell stays the spawn folder, as after any `cd` in PowerShell, and a parse error anywhere in the user's command runs none of it, after the `Set-Location` has run, so a `-NoExit` shell then sits in the worktree with the error shown. The bound is the shell's own command line: where the folder start would pass it, 32,767 UTF-16 units with its NUL (the program and every argument as Windows quotes them, the folder statement added, the text's quotes doubled, and any raw tail after one space), the shell starts in the worktree with its arguments unchanged, as does every shell whose folder start would pass it. The line that starts the `shell` mode is `<daemon> shell <daemon-pid>` alone (the pid for its parent check) and carries none of the person's input: the shell's program, arguments, folder and raw tail reach the mode in the start confirmation it reads. Two differences from a top-level `-Command` are named: `$MyInvocation` inside the text is the outer command's, its `Line` the whole wrapped command line, the `Set-Location` and the quoted text included, never the person's text alone, and a text run without `-NoExit` ends the process with `Invoke-Expression`'s own `$?`; here-strings, braces in strings and comments, `exit`, `return` and `#Requires` behave as at the top level. With any other argument (`-Login` and `-NoProfileLoadTime` among them, which only pwsh has) it starts in the worktree with the user's arguments unchanged, as every terminal starts it. `wsl.exe` starts in the system folder with `--cd <worktree>`, as Windows Terminal starts it, the switch left out where the user's arguments carry `--cd` or `~`. `cmd.exe` on a share starts there with `/K pushd "<worktree>"`, since cmd refuses a share as its start folder; the mode writes that text after the shell's arguments exactly as given (`CommandExt::raw_arg`), the path in cmd's own quoting, so `&`, `|`, `^`, `<`, `>` and `%` in it stay inert. Every other shell (`cmd.exe` on a local folder, Nushell, Git Bash, MSYS2 and Cygwin bash with `CHERE_INVOKING=1`, the system folder's `bash.exe`, which is WSL's launcher, without it, and any shell not named) starts in the worktree, as every terminal starts it, and lets go of it once it leaves; a shell still inside a worktree holds it until it leaves, so before a removal the daemon names the shells on that worktree, as the removal flow does for an occupied worktree. No shell reads a `CWD` variable: `CWD=<worktree-path>` is carried only to agent programs that read it, which start with the mode in the stable folder. The per-shell answer is `sidekicks-platforms`' `shell_folder_start`. **Cross-plan obligation:** Plan-001 owns the daemon-layer translation that applies that answer to a logical worktree-path `cwd` before the PTY starts the shell; `sidekicks-terminal` MUST NOT know about worktree semantics. Source: §Windows Implementation Gotchas Gotcha 5 (`microsoft/node-pty#647`). **Verification:** Phase 3 Test W1 (the `tests` module of `crates/sidekicks-daemon/src/session/spawn_cwd_translator.rs` — asserts the shell's folder start is applied whole, both folders and the raw tail included, and an agent program gets `CWD` in the stable folder; `sidekicks-platforms`' `shell_folder_start` tests check each shell's start) AND Phase 3 Test W2 (`crates/sidekicks-daemon/tests/it/spawn_cwd_translator.rs`, on every host — opens each shell in `sidekicks-platforms`' `SHELL_FOLDER_PROBES` for its host (`bash` on Linux; `zsh` and `bash` on macOS; `cmd.exe`, `pwsh.exe` and `powershell.exe` on Windows, the last on a folder whose name holds `’`) on a fresh folder, through the translator, the `shell` mode and the daemon's PTY, and asserts the folder is removed while the shell is open: cmd's once it has left it with `cd ..`, every other shell's at once).

### I-021-6 — No PTY or provider child outlives its supervising processes unreaped

The two-layer orphan-process defense per [ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-in-the-daemon.md#decision) item 7 (layer 1, layer 2 and the registry identity) MUST hold: **Layer 1** — per-OS kernel parent-death containment (every child spawned from the daemon's one long-lived spawner thread; Linux: `PR_SET_PDEATHSIG` armed per direct child with the `getppid()` reparent-race re-check, in a `Command` child's own `pre_exec` and in the `shell` mode a shell starts through, which execs the shell by its resolved absolute path with `execve`, and the never-leak guarantee bound to a daemon-lifecycle-bound cgroup-v2 scope killed via `cgroup.kill` by a pdeathsig-armed watchdog survivor where delegated cgroup v2 exists — best-effort process-group fallback degrading to bounded leak-until-restart elsewhere; Windows: the daemon's own Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and `JOB_OBJECT_LIMIT_BREAKAWAY_OK`, which every shell joins at creation and which the shared Codex app-server, meant to outlive the daemon, leaves through `CREATE_BREAKAWAY_FROM_JOB` (a flag any process in the job, a program in a shell included, may also pass), the daemon holding the sole, non-inheritable, never-duplicated handle, while a `Command` child that must die with the daemon runs in `process-wrap`'s `JobObject` under `KillOnDrop` with breakaway cleared; macOS: the `shell` mode's `getppid()` check, its wait for the start confirmation and its responsible-process check before it execs the shell through `posix_spawn` with `POSIX_SPAWN_SETEXEC` and the attribute that disclaims the daemon's responsibility, so the shell is its own responsible process, and the daemon's own reap of each child, which keeps the child's pid its own until the reap — the registry sweep is the load-bearing daemon-crash reaper there). **Layer 2** — the daemon-side orphan registry persisted with the crash-safe atomic recipe (same-dir temp file → `sync_all(file)` → `rename` → `sync_all(parent dir)`, on Windows `MoveFileExW` with `MOVEFILE_WRITE_THROUGH` — the parent-dir sync is the step generic atomic-write helpers omit), writing a durable **spawn-intent entry carrying a unique nonce injected into the child's environment BEFORE the child is spawned** and completing it with the identity tuple after, so no child ever exists outside the registry's view. The startup sweep kills only under a full `(boot_id, pid, start_time)` match — a mismatched boot-id proves staleness and the sweep **discards rather than signals** (fail-closed for a kill path) — and Linux signaling prefers the pidfd path (`pidfd_open` after the spawn, validated against the persisted tuple before first use; `pidfd_send_signal`) on kernels ≥ 5.3, falling back to tuple-guarded `kill(2)`. **Verification:** Phase 3B Tests O1–O5 (the `tests` module of `crates/sidekicks-daemon/src/pty/orphan/registry.rs` — O1: atomic-write recipe order incl. parent-dir sync; O2: intent-before-spawn ordering with crash-between-intent-and-spawn leaving a discardable stale intent; O3: boot-id mismatch discards every entry without signaling; the `tests` module of `crates/sidekicks-daemon/src/pty/orphan/sweep.rs` — O4: tuple match kills, tuple mismatch under a matching pid discards; O5: pidfd validation falls back to tuple-guarded signaling on start-time mismatch).

### I-021-7 — Terminal writes are lease-gated at the daemon boundary; the lease never touches the foreground process

Every write frame bound for one of a session's shells passes that shell's [Spec-002 §Required Behavior](../specs/002-machine-registration.md#required-behavior) write-lease check at the daemon terminal-write boundary, where the authenticated writer is known: a write naming a subscription that is not the calling connection's open output subscription to that shell is refused `terminal.output.subscriptionNotFound` before the lease reads it; with no holder, a device's write takes the shell for the connection it came on and the pane output subscription the write names, broadcast `taken`, and lands once that broadcast has, so of two devices writing at once exactly one takes it; a bound connection's write through another of its panes' subscriptions lands and binds that subscription to the hold, with no broadcast; every other writer the shell's hold is not bound to, a run among them and another connection of the holding device until it takes the shell, is refused `terminal.control.notHeld`, and a lease on one shell never authorizes a write to another; a provider process's own shell and its tool spawns are not terminal surfaces and sit outside the lease. A write `sidekicks-terminal` takes carries no holder, because bytes that reach it are already lease-authorized, and no lease transition ever signals, terminates, or otherwise touches the running foreground program (a take lands between frames; L10: at a level that asks, `shell_run` raises one approval card and writes nothing until it is answered, a decline writes nothing and takes no lease, the tools are withheld at spawn while the approval service is not running and a stray call answers `denied`, and a call naming another session's shell answers `failed`, and a call with `terminal_id` left out opens one shell in a session that has none and runs its command there, and answers `failed` with no shell opened while the session has one open and on a chat session; L12: a command whose output prints an end mark without the shell's nonce, or with another, keeps running and its call stays held, `agent.command.stop` sends `SIGINT` to the command's process group and, for a command that ignores it, `SIGKILL` once the 2-second budget passes, never signaling the shell's own group, its row ending `endedByPerson` and its answer ``The user stopped `<command>`.``, the same after the run has gone idle and a device holds the shell, and a call the provider cancels leaves the command running and listed until its end mark).

### I-021-8 — The terminal-owning daemon is the only lease authority

The daemon that owns a shell is the only authority for its lease, and a take is registered on the daemon's own transport and on nothing else. Each shell's lease record lives with the shell it guards: the holding device and, for a hold taken by an agent run's write path for one command, the acquiring run and that command, and the device hold that take moved the shell off, kept aside with its bindings until the run's release hands it back, which `terminal.control.changed` and the shell's holder reading name as `holderRunId` while the run holds the shell and omit while a device does; `holderDeviceId` stays the machine's own device identity, because every local writer on the machine resolves to it, and the agent's name comes from the run. The record's holder and version are on no wire but `terminal.control.changed`, the shell's `terminal.subscribe` entry and the scrollback frame that opens its output, and in no control-plane table, and every change to it broadcasts `terminal.control.changed` naming the shell, the new holder, the reason (`'taken' | 'takenByForce' | 'autoReleasedDisconnect' | 'autoReleasedPaneClosed' | 'autoReleasedCommandEnded' | 'autoReleasedRunIdle'`, per [Spec-005 §Terminal Control](../specs/005-session-event-taxonomy-and-audit-log.md#terminal-control-sessionlifecycle)) and the lease version, which every change of holder raises by one, so no change of holder goes unannounced and a reader keeps the newest. A device's lease is bound to each connection of that device that took it or wrote to it, with the pane output subscription it came through, and carries no time bound and no fence issued by any other party, so it never outlives the last of those bindings or the shell. **Verification:** Phase 3B Tests L1–L5 (each transition's broadcast and version, and the connection- and pane-bound releases) and L8–L9 (the run's take, the hold kept aside, and its command-end and run-idle releases handing the shell back).

### I-021-9 — A numeric `signal_code` asserts a real OS observation

A shell's exit carries a numeric `signal_code` ONLY when the OS reported that signal for that child's exit: on macOS and Linux the signal its exit status reports; a Windows exit carries no POSIX signal, so its `signal_code` is always absent; absence (`null` on the wire) is the ONLY no-observation encoding. An exit the daemon reports for a hard stop the system never confirmed (I-021-2) carries exit code 1 and no signal, so a real signal observation can never be confused with it. **Verification:** Phase 3B Tests SG1–SG2 (the `tests` module of `crates/sidekicks-terminal/src/exit.rs` — SG1, on the Windows leg: a Windows exit, a hard-stopped child included, carries no signal; SG2: a Unix exit by signal carries the signal the OS reported, and an unconfirmed hard stop's exit carries exit code 1 and no signal).

## Implementation Steps

1. **The crate.** Create `crates/sidekicks-terminal` as a library the daemon links, edition 2024, each shell's PTY through `alacritty_terminal::tty` (ConPTY on Windows).
2. **Each shell's PTY and read loop.** Spawn each shell from the daemon's one spawner thread, through the `shell` mode passed as `Options::shell`, and read it with its own read loop (§Target Areas, `read_loop.rs` row), feeding the one-mebibyte history window and the screen copy.
3. **The write path.** Writes reach a shell in order with one in flight; a write waits while the terminal's buffer is full and never spins, and none is made after the terminal closes (§Target Areas, `pty.rs` row). The terminal's replies to a program's queries go through the same path, at most 64 KiB of them waiting per shell: newer replies past that are dropped and logged once, and on Windows also once the console has read none of its waiting input after each 64 KiB of replies (`GetNumberOfConsoleInputEvents`, through the console helper). On macOS and Linux an interrupt, quit or suspend key sent alone goes as `ioctl(master, TIOCSIG, signal)` while the terminal refuses input, when the program's terminal settings, read from the master, have `ISIG` on and the key matches `VINTR`, `VQUIT` or `VSUSP`: the shell's read loop, which sees whether the terminal takes input, decides each such key, sending it as its signal while it is still unwritten and the terminal refuses input and otherwise writing it in line, never both; a key a failed write or the terminal's stop drops is never signaled. A `terminal.write` is answered once the queue takes its bytes, which it does while it holds less than its 64 KiB bound; it takes no slot of the connection's call cap and carries at most `TERMINAL_WRITE_MAX_BYTES` (64 KiB). In its step before its first wait, the handler counts the writes each connection has waiting on the shell and refuses one that finds `TERMINAL_WRITES_WAITING_LIMIT` (16) waiting with `terminal.write.limitReached`, and it hands a lone key to the read loop there, before the write waits on anything, so its signal can go first; a client keeps at most `TERMINAL_WRITES_WAITING_PER_SHELL` (8) writes per shell waiting, joins typed keys past that into writes sent in order as answers return, and sends an interrupt, quit or suspend key at once together with the keys before it while fewer than 16 wait (all three in `crates/sidekicks-contracts/src/terminal.rs`).
4. **Exit capture.** Read each shell's exit from its child, with its code and any signal the OS reported, and report it once.
5. **The terminal's API.** Author `crates/sidekicks-terminal/src/lib.rs` from the method list in §API And Transport Changes. Plan-001's spawn wrapper and drain call it.
6. **Kill semantics.** In `crates/sidekicks-terminal/src/kill.rs`:
   - On macOS and Linux a signal goes to the shell's process.
   - On Windows, `SIGINT` writes byte `0x03` to the ConPTY input (I-021-1).
   - `SIGTERM` (graceful hard-stop) → the `console` mode's `CTRL_BREAK_EVENT` first; if the child does not exit within 2 s, `taskkill /T /F /PID <pid>` per I-021-2.
   - `SIGKILL` (immediate hard-stop) → `taskkill /T /F /PID <pid>` directly, skipping `CTRL_BREAK_EVENT`.
   - Idempotency: if the child has already exited when the kill is called, treat it as success and report the cached exit; do not fail.
7. **ConPTY's library.** At the daemon's start `sidekicks-platforms` calls `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)`, so `alacritty_terminal`'s `LoadLibraryW("conpty.dll")` finds no copy beside the program or on `PATH` and falls back to kernel32's `CreatePseudoConsole` ([ADR-018](../decisions/018-windows-v1-tier-and-pty-in-the-daemon.md) Tripwire 3); since that search path is process-wide and cannot be reverted, every library the daemon loads at run time is checked to load from System32 or by full path.

## Windows Implementation Gotchas

Five Windows-specific implementation concerns are load-bearing for the terminal's correctness and lifecycle behavior on Windows. Each item below names the daemon-layer obligation, the implementation guidance, and the primary-source citation in `## References`.

### 1. Ctrl+C signal propagation on Windows

Windows does not have POSIX-style SIGINT delivered to a process group. The console subsystem uses `CTRL_C_EVENT` and `CTRL_BREAK_EVENT` events delivered through `GenerateConsoleCtrlEvent`, with semantics that are not equivalent to Unix `SIGINT`:

- `CTRL_C_EVENT` (`0`) is the closest analog to `SIGINT` but can be ignored or handled distinctly by the child process via `SetConsoleCtrlHandler`.
- `CTRL_BREAK_EVENT` (`1`) is generally non-ignorable and is the more reliable interrupt for misbehaving children.
- `GenerateConsoleCtrlEvent` reaches only processes attached to the **same console** as the caller, so the daemon, which holds no console of its own, sends the break from its `console` mode, which attaches to the shell's pseudo console first.
- A process-group ID of `0` broadcasts the event to all processes attached to the console, and a `CTRL_C_EVENT` sent to a nonzero process group is not delivered; since `alacritty_terminal` starts shells without `CREATE_NEW_PROCESS_GROUP`, Ctrl+C is the byte `0x03` written to the ConPTY input, which the console turns into `CTRL_C_EVENT` for every process on it while `ENABLE_PROCESSED_INPUT` is set, and the hard stop's break goes to group 0.

Daemon-layer obligation: the daemon's kill of a shell's command on Windows translates signal semantics — `SIGINT` → byte `0x03` on the ConPTY input, hard-stop → the `console` mode's `CTRL_BREAK_EVENT` followed by `taskkill /T` if the child does not exit within a bounded interval. `node-pty`'s `pty.kill()` only signals a single process and does not handle the console-group attachment correctly per [microsoft/node-pty#167](https://github.com/microsoft/node-pty/issues/167) (see `## References`); the daemon makes this translation in `crates/sidekicks-terminal/src/kill.rs` rather than relying on a PTY library's own kill.

### 2. `taskkill /T` tree-kill behavior

Killing a single PID on Windows does not kill its descendants. Children spawned by the immediate child process (shells, build tools, language servers, language-runtime workers) survive a single-PID kill and become orphans tied to the console session. This affects the daemon's session-teardown semantics: a "session ended" notification cannot assume the entire process tree has terminated.

- Use `taskkill /T /F /PID <root-pid>` (the `/T` flag instructs `taskkill` to kill the entire tree) for hard termination paths.
- For graceful shutdown, send `CTRL_BREAK_EVENT` first (per Gotcha 1), wait a bounded interval, then escalate to `taskkill /T /F`.
- Reaping must be idempotent and must not block the shell's read loop — invoke `taskkill` with a timeout and report the shell's exit even if reaping is incomplete, so the daemon can mark the shell ended without hanging on a stuck OS-level operation.
- This is a daemon-layer responsibility (the read loop reports the exit on root-PID exit; the daemon coordinates tree-kill on session end). Behavior matches the unreliability documented in [microsoft/node-pty#437](https://github.com/microsoft/node-pty/issues/437) — see `## References`.

### 3. WSL2 path translation scope

WSL 2 is first-class. On a Windows computer the service is the native daemon, and a session whose project folder is inside a WSL 2 distribution runs its work there through the WSL server, so a session's terminals sit on its providers' side of the boundary. The terminal's responsibility boundary follows from that:

- **Where each terminal runs (operative):** a session on Windows runs its shells through ConPTY in the daemon. A session in a WSL 2 distribution runs its shells through the WSL server's `sidekicks-terminal` on Linux, in the person's login shell with a Linux working folder.
- **Implementation guidance (operative):** `sidekicks-terminal` does **not** translate paths between Windows-native (`C:\Users\...`) and WSL 2 (`/mnt/c/Users/...` or `\\wsl.localhost\<distro>\home\...`) namespaces; a shell's spawn takes the paths it is handed. Path translation is the daemon's, before any spawn: `\\wsl.localhost\<distro>\p` or `\\wsl$\<distro>\p` becomes that distribution and `/p` through `sidekicks-platforms`, `/mnt/c/p` given inside a distribution becomes Windows' `C:\p` through `wslpath -w` in the WSL server, and a Linux path going back to Windows takes its `wslpath -w` form.
- `wslpath` availability: the `wslpath` command exists inside a WSL 2 distro and converts between Windows and POSIX path forms (e.g., `wslpath -w /home/foo` → `\\wsl.localhost\Ubuntu\home\foo`). It is NOT available in a Windows-native context, so the daemon runs it through the WSL server.

### 4. The app's quit and the service's stop

Electron's `will-quit` event is the app's last chance for synchronous cleanup before its process terminates. The shells are not the app's: they run inside the daemon, which runs as the person's background service, so the app's quit never reaches them — the quit calls `daemon.flush`, and the service, every run and every shell keep running.

- No handler in the app's main process drains, kills or signals a shell — not on quit, not on a window closing, not on the last window closing.
- When the service itself stops (Runtime's `Stop` or `Restart`, or the operating system's service manager), the daemon drains before it exits: (a) give every live shell the hard stop (`SIGTERM`, or the `console` mode's `CTRL_BREAK_EVENT` on Windows), (b) wait for each shell's exit up to `DAEMON_STOP_TERMINAL_DRAIN_MS` (2 s), and (c) kill a shell that has not exited (`SIGKILL`, or `taskkill /T /F /PID` on Windows — same hard-stop pattern as Gotcha 2), all inside the service's drain bound `DAEMON_STOP_DRAIN_BOUND_MS` (4 seconds).
- The race between a process exiting and its PTY children draining is the SIGABRT-on-exit class documented in [microsoft/node-pty#904](https://github.com/microsoft/node-pty/issues/904) (see `## References`); keeping the PTYs in the service, out of the app's process, and draining them at the service's own stop is what makes that hold.
- **Cross-reference:** Plan-001 (session core) owns the drain orchestration, with Plan-021 (this plan) supplying `sidekicks-terminal`'s drain.

### 5. Spawn locks cwd on Windows

Windows holds a handle on every process's current folder. As long as a process keeps a folder as its current folder, that folder cannot be deleted, moved, or unmounted — any attempt fails with `ERROR_SHARING_VIOLATION`. This breaks worktree-swap workflows (`git worktree remove`, `gitflow` cleanup) when a shell is spawned with `cwd` set to the worktree path: the worktree cannot be removed until every shell rooted under it has exited, even if the user has switched contexts and considers the worktree abandoned.

- **Implementation guidance** (per [microsoft/node-pty#647](https://github.com/microsoft/node-pty/issues/647)): the lock is a process's own current folder; the ConPTY host keeps the daemon's, so the daemon's own folder is one no update replaces or removes. The PTY spawns the daemon's `shell` mode, not the shell, in the system folder; the mode keeps that folder for its whole wait and starts the shell in the folder its start confirmation names. The rule is per shell:
  - **PowerShell** (`pwsh.exe`, `powershell.exe`) keeps the folder it starts in for its life, whatever `Set-Location` does, so it starts in the system folder and is told its folder by its own switches: `-WorkingDirectory` ahead of the user's arguments for `pwsh.exe` unless they run a script by a relative path (a `-File` form or a bare script path), and for `powershell.exe`, when each user argument is one of its own start switches (`-NoLogo`, `-NoProfile`, `-NoExit`, `-NonInteractive`, `-ExecutionPolicy`, `-Mta`, `-Sta`, `-WindowStyle`, `-InputFormat`, `-OutputFormat`, `-ConfigurationName`, and `-Version` and `-PSConsoleFile` only at the line's front, as its native entry reads them), `-NoLogo -NoExit -Command "Microsoft.PowerShell.Management\Set-Location -LiteralPath '<worktree>'"` after them, or `Microsoft.PowerShell.Management\Set-Location -LiteralPath '<worktree>'; Microsoft.PowerShell.Utility\Invoke-Expression '<text>'` for the user's own command text, given by `-Command` or as a bare word, every single-quote character in the path and the text doubled, and the `Set-Location` alone for a blank text, both cmdlets named with their modules; any other argument starts it in the worktree as every terminal starts it. Two exposures are named: .NET's own current folder in that shell stays the spawn folder, as after any `cd`, and a parse error in the user's command runs none of it, after the `Set-Location`, so a `-NoExit` shell then sits in the worktree with the error shown. The bound is the shell's own command line: a folder start that would pass it (32,767 UTF-16 units, the program, every argument as Windows quotes them and any raw tail) starts the shell in the worktree with its arguments unchanged. The line that starts the `shell` mode carries none of the person's input, which reaches the mode in its start confirmation. Two differences from a top-level `-Command` are named: `$MyInvocation` inside the text is the outer command's, its `Line` the whole wrapped command line, the `Set-Location` and the quoted text included, and a text run without `-NoExit` ends the process with `Invoke-Expression`'s own `$?`. `wsl.exe` takes `--cd` unless the user's arguments carry `--cd` or `~`, and `cmd.exe` on a share `/K pushd`, written after its arguments exactly as given, from the same folder.
  - **Every other shell** starts in the worktree: cmd and Nushell move their process folder on `cd`, and the MSYS-family bash reopens its folder for deletion, so the folder is held only while the shell sits in it, as on every other terminal on Windows.
- **Daemon-layer obligation:** the daemon's shell spawn applies `sidekicks-platforms`' folder start for the shell's program (the mode's spawn folder, the shell's folder, the arguments, the raw tail and the added environment) to the logical worktree path before the PTY starts the shell, and a shell still inside a worktree is named before that worktree's removal. This translation step is a **session-layer** responsibility (Plan-001), because `sidekicks-terminal` deliberately does not know about worktree semantics.
- The constraint is OS-level, so the translation runs on every platform.
- **Cross-reference:** [ADR-018 §Research Conducted](../decisions/018-windows-v1-tier-and-pty-in-the-daemon.md#research-conducted) row [`microsoft/node-pty#647`](https://github.com/microsoft/node-pty/issues/647) ("blocks worktree workflows") classifies the failure mode; this section provides the implementation-grade mitigation. Plan-001 (session core) owns the translation step in its session-spawn entry point; Plan-021 (this plan) supplies only the spawn's `cwd`, which carries whatever the daemon hands down.

## Windows Signing — SignPath Foundation

Windows signing goes through [SignPath Foundation](https://signpath.org)'s free open-source program ([ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-in-the-daemon.md#decision) item 5). Its terms ([signpath.org/terms](https://signpath.org/terms)) admit a project with an OSI license "without commercial dual-licensing for all components", no proprietary components, active maintenance, an existing release and a published code-signing policy, which the release workflow publishes. "The code signing certificate is issued to SignPath Foundation", so Windows names SignPath Foundation as the publisher of every binary the step signs.

- **One step, one publisher.** The release workflow's SignPath step signs the Electron app, `sidekicks-daemon`, `sidekicks`, the client's `.node` and `libpdfium`, each for x64 and arm64, so SmartScreen reputation accrues to one publisher across all of them ([ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-in-the-daemon.md#decision) item 6).
- **Why this path.** It removes SmartScreen's hard block on an unsigned file and keeps the NSIS installer's one-press update, at no cost. The certificate class is not the lever: Microsoft's [SmartScreen reputation documentation](https://learn.microsoft.com/en-us/windows/security/threat-protection/microsoft-defender-smartscreen/smartscreen-reputation) says of the EV bypass that "this behavior no longer exists", so reputation accrues by publisher and file hash for every class.
- **If the project is not eligible**, the choice goes back to the person with the remaining paths (the Microsoft Store, a bought certificate, or unsigned with SmartScreen's block at install); the distribution plan does not change silently.
- **Windows builds publish unsigned until SignPath Foundation signs** ([BL-108](../backlog.md#bl-108-signpath-foundations-acceptance-for-windows-signing)): its program asks for an existing release, so the Windows builds before its acceptance are unsigned, and if the project is not eligible, that goes back to the person and the distribution plan does not change silently.

A shell whose first prompt brings no mark — a shell with no script here, such as tcsh, or one whose startup files turned the script off — is recorded as reporting no marks. These checks and the shell's busy mark are made in one tick, with no `await` between them, so of two calls on one shell, from one run's parallel tool calls or from two runs, exactly one is accepted; a refused take clears the mark. **The take and the write:** once accepted, `shell_run` takes the shell for the calling run through `ShellControlLease::take_for_run`, given the run, the command and `is_shell_idle`, which reads the shell table's typed-input mark again in the same tick as the take, after any change of holder in flight has settled, so a keystroke admitted while the take waited refuses it with the same words as the check above, the `commandId` being the call's own tool call id, whose bound `PROVIDER_TOOL_CALL_ID_MAX_LEN` (`crates/sidekicks-daemon/src/provider/driver/contract.rs`) equals `COMMAND_ID_MAX_LEN` (`crates/sidekicks-contracts/src/command.rs`), so `holderCommandId` names the row the person sees. Past that it keeps the end, where a failure's last lines sit, cut at a whole line, behind one line saying the answer holds the last 30,000 characters of the given number of bytes the command printed. A command that ends while no call is held on it keeps its answer until a `shell_wait` collects it or its run ends. A wait costs the agent's model while it lasts on Codex — a held `session_wait` of 180 seconds took 9 model passes and 262,608 tokens on the `dynamicTools` route ([codex.md §One tool server for every conversation, and a call that waits](../reference/provider-wire/codex.md#one-tool-server-for-every-conversation-and-a-call-that-waits)) — and the bound leaves the agent to choose whether to wait again. Two other shapes were weighed and not taken: holding the call until the end mark cannot answer a command that never ends, such as a development server; answering at once and waking the conversation with a new turn when the command ends, as `session_wait` does on Codex, ends the turn, so the run leaves `running` and the run-idle release hands the shell back under every Codex command while it runs. On a Claude Code session, `agent.command.background` on a command a call is held on answers that call at once, as the bound does; on Codex the row draws no `Move to background`, as for every Codex command. **Waiting for input:** no wrapper holds a typed-in command's input, so the shell table reads its waiting from the kernel itself, through `sidekicks-platforms`' one input-wait and echo interface, whose macOS, Linux and Windows forms follow. The kernel marks no read starting on the terminal: `ptsread` wakes the master's writers only once the read returns ([`tty_dev.c` 376–397](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/tty_dev.c#L376-L397)). So between the command-start mark and its end mark the check runs 50 ms after the command's last output, then after 100 ms and 200 ms more, then every 500 ms until the command prints again, which starts the sequence over. On macOS each check reads the terminal's foreground process group with `TIOCGPGRP` on the master ([`tty_dev.c` 1025](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/tty_dev.c#L1025)), lists that group's processes with `proc_listpids(PROC_PGRP_ONLY)` ([`proc_info.c` 361–417](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L361-L417)), and goes on only while no input is queued on the terminal (`FIONREAD` reads 0) and no thread of the group is running (`PROC_PIDLISTTHREADS` and `PROC_PIDTHREADINFO`). macOS copies a thread's wait reason out to no other process, so the check then reads where each process of the group waits with Apple's `/usr/bin/sample`, which reads a process of the same user without root through the task-read right Apple's own signature grants it (`com.apple.system-task-ports.read`): once the command's output has been quiet for the quiet period, it runs `sample <pid> 0.01 1 -file <path>` once per process of the group and parses only each thread's innermost call. A process is waiting on the terminal when that call is `read`, `__read_nocancel` or `readv` and the process has the terminal open for reading, holds no socket open for reading, whose read it may be, and has no pipe open for reading whose state shows `PIPE_WANTR`, the flag `pipe_read` sets before it sleeps, read through `proc_pidfdinfo`'s `PROC_PIDFDPIPEINFO` ([`sys_pipe.c` 857](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/sys_pipe.c#L857) and [1746](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/sys_pipe.c#L1746)), since that read may be the pipe's; or when the call is `kevent` and the process holds an `EVFILT_READ` knote on the terminal. The knotes are read from each kqueue descriptor `PROC_PIDLISTFDS` lists, and from the process's work-queue kqueue, which has no descriptor and is read with descriptor −1, both with `proc_pidfdinfo`'s `PROC_PIDFDKQUEUE_EXTINFO`, which a process of the same effective user may call ([`proc_info.c` 2868](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L2868) and [2940–2955](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L2940-L2955); `pid_kqueue_extinfo` and `kevent_extinfo_emit`, [`kern_event.c` 9480](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_event.c#L9480) and [9295](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_event.c#L9295)), and from each workloop kqueue `proc_pidinfo`'s `PROC_PIDLISTDYNKQUEUES` lists, with `proc_piddynkqueueinfo`'s `PROC_PIDDYNKQUEUE_EXTINFO` under the same check ([`proc_info.c` 2469](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L2469) and [4016–4052](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L4016-L4052)), where a reader that uses Apple's dispatch library registers. The three flavors are private ([`proc_info_private.h` 176, 231 and 270](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/sys/proc_info_private.h#L176-L270)) and `proc_piddynkqueueinfo` is a libproc export its public header does not declare, so the build defines them. A process running as another effective user, such as `sudo`, refuses these reads ([`proc_info.c` 3181–3199](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L3181-L3199)), and `sample` was refused a root process on the authoring Mac. For such a program the check reads the terminal's own settings through the master, which needs no rights over the program, as on Linux: when the output is quiet, the foreground group is not the shell's, nothing is queued, the terminal has canonical input on and echo off (`ICANON` set and `ECHO` clear, read with `tcgetattr` on the master, which a probe on the authoring Mac showed reads the echo a process turned off on the terminal) and no process of the group is running, read with `/bin/ps -o stat=`, which runs as root and showed the state of root processes to the person's own user, the command is waiting on a password, as `sudo` asks for one, and `echoOff` is set; such a program that turned echo off and sleeps for another reason reads as waiting too, and its line still works. Such a program's prompt with echo on is not marked waiting. A descriptor or a knote is matched to the terminal by its device, because a program may watch a copy of the terminal's descriptor rather than its standard input, as node does, or open the terminal again, as `less` does. The master descriptor comes from `alacritty_terminal`'s `tty::Pty`, and the terminal's device path is read from it with `ptsname`. To read a thread's stack `sample` holds the thread and stops it for that instant, then lets it go ([`thread_act.c` 618–650](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/thread_act.c#L618-L650)), and it sends no signal: a read blocked on the terminal stayed blocked through five samples, and a busy loop showed no pause beyond its unsampled spread (largest gaps of 3.1–5.1 ms sampled against 0.19–8.48 ms unsampled), so the program takes its answer as it would in any terminal. One sample took 0.06–0.09 s of wall time, 0.03–0.04 s of user and 0.01 s of system processor time and 11–14 MB of peak memory on the authoring Mac, so sampling has a ceiling per command. Its workload is a quiet command that is not waiting — `sleep 600`, a `git push` waiting on the network, a build between its lines — which passes every other condition and would otherwise be sampled again and again. After its first sample, a group still not found waiting is sampled again 1 s later and then after gaps that double, up to 60 s, while its output stays quiet and nothing is typed; output or input starts the sequence over; and no command takes more than 6 samples in any minute, so its ceiling is about 0.3 s of processor time a minute, half a percent of one core, with one 11–14 MB `sample` process at a time. The build measures the daemon's processor time and peak memory per command on that workload, and on a command that prints a line every 2 seconds and never waits, against that ceiling, as this task's acceptance; the quiet period is set from the same measurement. Measured there, the knotes read node's readline, `npm init` and Python's asyncio as waiting, and none of `sleep 30`, a busy loop or a node timer with no reader; `sample` showed `read` innermost for `cat`, a shell's `read` and `less`, `__read_nocancel` for `rm -i` and Python's `input()`, and `kevent` on node readline's main thread, and it showed `__semwait_signal` for `sleep 30`, `__wait4` for a shell that ran `read -t 1` and then `sleep 30`, whose timed-out read left its pipe flag set, and `__read_nocancel` with `PIPE_WANTR` set for `sort` in `sleep 30 | sort`, none of which is read as waiting. A program that keeps a read registered on the terminal while it waits on something else also reads as waiting, such as node with a `data` listener on its input and a timer pending, until it prints or a thread of it runs; the Linux form's epoll reading shares that gap. A program that waits on the terminal with `select` or `poll` — Python's `select`, bash 5's `read -t` — shows `__select` or `poll` innermost, whose descriptors `sample` does not show, and holds no knote on a kqueue the daemon can list (`poll` registers one on a private kqueue with no descriptor, [`sys_generic.c` 1712–1755](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/sys_generic.c#L1712-L1755)), so the check never reads it as waiting; neither does it read a `read` in a process that holds a socket open for reading, nor one in a process that holds a pipe whose `PIPE_WANTR` flag is set, a flag a timed-out pipe read can leave behind, as above. Such a command keeps its input line and takes `agent.command.write`, and only the waiting mark is missing. Each check also reads the terminal's settings with `tcgetattr` on the master and sets `echoOff` while echo is off, whether or not it finds a reader, so the input line masks what is typed. `waitingForInput` follows each check, so it clears once a thread runs or input is queued; it also clears when the daemon writes into the shell or the command prints again, and the checks start over. Its Linux form, which [Plan-027](./027-windows-and-linux.md) T27.2.10 builds, keeps the three conditions: nothing queued on the terminal, no thread of the group running, and a reader found in each thread's `/proc/<pid>/task/<tid>/syscall` ([`proc/base.c` 3658](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/fs/proc/base.c#L3658)): a thread blocked in `read`, `readv` or `pread64` on a descriptor of the terminal, or in `epoll_wait`, `epoll_pwait` or `epoll_pwait2` on an epoll set whose `/proc/<pid>/fdinfo/<epfd>` lists the terminal with `EPOLLIN` ([`eventpoll.c` 1357–1372](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/fs/eventpoll.c#L1357-L1372), [2877](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/fs/eventpoll.c#L2877)), where node and Python's asyncio wait, or in `select`, `pselect6`, `poll` or `ppoll` with a descriptor set, read from `/proc/<pid>/mem` at the call's own arguments, that holds the terminal for reading. A descriptor matches the terminal by its inode and device, and a descriptor open on `/dev/tty`, such as `less` and `fzf` read, matches when the process's controlling terminal, `tty_nr` in `/proc/<pid>/stat` ([`proc/array.c` 523 and 596](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/fs/proc/array.c#L523-L596)), is this terminal, since opening `/dev/tty` attaches the real terminal but leaves the file as `/dev/tty` ([`tty_io.c` 1842–1865](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/drivers/tty/tty_io.c#L1842-L1865)). A `poll` cut short by a stop and continue or by suspend resumes as `restart_syscall`, whose `syscall` line carries no descriptor set ([`select.c` 1074–1087](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/fs/select.c#L1074-L1087)), so it is not read until it returns.      
      ```text
      List this session's shells, the terminals the person has open in it: each one's terminal id, title, who holds it now, and whether it reports command marks, which shell_run needs. Use it to pick a shell before shell_run.
      ```

      It answers one line per shell, its terminal id, its title, its holder and `reports marks` or `no marks`, joined by `·`, the holder reading `held by the person on <device>`, `held by <agent>'s run` or `held by nobody`, as in `t-2 · zsh — shop-api · held by the person on MacBook · reports marks`, and with no shell open `This session has no shells open. shell_run opens one when you leave out terminal_id.`

    - `shell_run` takes `terminal_id`, optional, and `command`, each a non-empty string, `command` holding no line break, and no other field. Its description:

      ```text
      Run one command in one of this session's shells, where the person sees it and can type into it. Use it for a command that asks questions or needs a terminal, and for a server, a watcher or anything meant to keep running until someone stops it.

      {"terminal_id": "t-2", "command": "pnpm dev"}

      The command runs in that shell as if the person typed it, so it changes the shell: a cd, an export or an alias holds for the next command. Pick the shell with shell_list; when the session has none open, leave terminal_id out and one is opened for the command, as the person would open it. The call waits up to 120 seconds; a command still running then answers with its output so far and its command_id, and shell_wait waits on it again.
      ```

      `terminal_id` reads `A shell's terminal id, from shell_list. Leave it out only when the session has no shell open; one is then opened for the command.`, and `command` reads `One line, as you would type it at the prompt. To run several commands, join them with ; or &&, or pass them to bash -c.` It answers `Exited with code <exit code>.` then the rendered lines after those an earlier answer for that command carried; past 30,000 characters, `This answer holds the last 30,000 characters of the <byte count> bytes the command printed.` then the lines; for a command still running at 120 seconds, or moved to the background by the person on Claude Code, `Still running in <terminal id> · command_id <command id>. Output so far:` then the output, then `Call shell_wait {"command_id": "<command id>"} to wait again.`; and for a command the person stopped, ``The user stopped `<command>`.`` Its refusals, each `failed` with nothing written:
      - `Not run: the command has a line break, and the shell would run each line as its own command. Join the lines with ; or &&, or pass them to bash -c.`
      - `Not run: shell <terminal id> reports no command marks, so a command in it cannot be followed. Pick a shell that reports marks from shell_list.`
      - `Not run: shell <terminal id> is busy with a command that has not ended. Wait on it with shell_wait, or pick another shell.`
      - `Not run: someone typed into shell <terminal id> since its last prompt, and your command would join their half-typed line. Pick another shell, or ask the person.`
      - `Not run: shell <terminal id> did not start the command; it may have been waiting for more input, such as a closing quote. Its line was cleared.`
      - `Not run: this session has shells open, so name one. Call shell_list to see them.`, for `terminal_id` left out while the session has a shell open.
      - `Not run: this session cannot open a shell.`, for `terminal_id` left out in a session whose shell open is refused.
      - `No shell "<terminal id>" in this session. Call shell_list to see them.`, for a shell this session does not have, another session's included.
      - A declined approval answers with the provider's own refusal, passed through unchanged.

    - `shell_wait` takes `command_id`, a non-empty string, described `The command_id from shell_run's answer.`, and answers as `shell_run` does. Its description:

      ```text

      {"command_id": "toolu_01Xy…"}
      ```

      An unknown id, another session's, or one whose answer was already collected or dropped when its run ended, answers `No command "<command id>" waits for an answer in this session.`

## Rollback Or Fallback

- A native ConPTY crash takes the daemon down with every shell, since the PTY runs in its process; the shells do not survive it ([ADR-018 §Failure Mode Analysis](../decisions/018-windows-v1-tier-and-pty-in-the-daemon.md#failure-mode-analysis)).
- A terminal bug on Windows → the next release ships the fix.

## Risks And Blockers

- **SignPath Foundation finds the project ineligible.** The choice goes back to the person with the remaining paths (the Microsoft Store, a bought certificate, or unsigned with SmartScreen's block at install); the distribution plan does not change silently.
- **`alacritty_terminal`'s `tty` falls short on a platform.** `portable-pty` (WezTerm), held in reserve behind the same API, is evaluated under [ADR-018 §Tripwires (Revisit Triggers)](../decisions/018-windows-v1-tier-and-pty-in-the-daemon.md#tripwires-revisit-triggers) Tripwire 1.
