## Goal

Ship the Spec-020 data acts and the daemon's secrets: every daemon secret is its own item in the operating system's credential store, and nothing in the daemon's database is encrypted by the app; the session purge deletes a session's rows with `secure_delete` on and checkpoints the write-ahead log with `TRUNCATE`, so no freed page and no log keeps a readable word of it; and the person can export everything the machine keeps and erase it, from Settings › Runtime and from the command line.

## Scope

- The daemon's secrets ([Spec-020 §Daemon Secrets](../specs/020-data-retention-export-and-deletion.md#daemon-secrets)): each is its own item — on macOS in the login keychain, through `keyring-core` with the platform's store, and on Linux in one file, `secrets.json` in the daemon's own data folder, readable by this account alone (mode `0600`), each item sealed through systemd's credential service by `sidekicks-platforms`' own client where that service can seal, and plain, as `gh` and Codex keep theirs, where it is absent, refuses at the first start, or would bind the seal to the Secure Boot state; never the desktop keyring or the kernel keyring, which is cleared at every restart, and never silently: the person can see where secrets are kept and how they are protected. A Mac keeps its items in the same file, plain, from the logged-out service's takeover until `sidekicks daemon uninstall` moves them back, including after that service is turned off in Login Items & Extensions. On Windows every item goes to Credential Manager through `windows-native-keyring-store` 1.1.0 at `CRED_PERSIST_LOCAL_MACHINE` (`persistence=local`), whichever unit keeps it, in the service's own process through `sidekicks-platforms` (CP-019-5); the WSL server inside a distribution holds no secret. Built behind Plan-005's `SecretKeychain` interface, reciprocating CP-005-5 (see [§Cross-Plan Obligations](#cross-plan-obligations)).
- The items this plan's store keeps: the machine's Remote Control identity key and its channel key, and the hosted sign-in's refresh token and DPoP key. The units that own the others — a pasted provider token, a workflow secret, the notification web address and its signing secret, the mail password, each tool server sign-in's refresh token and DPoP key — keep them as items the same way.
- Nothing in the daemon's database is encrypted by the app: the person's messages and every queued message's body, a message sent mid-turn among them, sit in plain columns, as `content_payload` does ([Spec-020 §Erasure In The Daemon's Database](../specs/020-data-retention-export-and-deletion.md#erasure-in-the-daemons-database)).
- The data acts, as daemon JSON-RPC verbs over the contracts in `crates/sidekicks-contracts/src/daemon/data.rs`: `daemon.dataExport.start {destination}` with `daemon.dataExport.subscribe` (`Export all data`) and `daemon.data.erase {}` (`Erase all data`). Host is daemon-bound (data-locality); shape per D-019-1.
- The purge's erasure step: `daemon.retention.purge` (Plan-005 Phase R1) deletes a session's rows in one transaction with `secure_delete` on, then checkpoints the write-ahead log with `TRUNCATE` (CP-019-2).

## Non-Goals

- **The retention bounds and `Delete old data`.** `daemon.retention.read`, `daemon.retention.update` and `daemon.retention.purge` are Plan-005 Phase R1's, with the purge's capture folder, base pins and managed workspace; this plan owns only the purge's erasure step (CP-019-2). Nothing deletes a session by age: the service drops only the diagnostic logs on its own, past `Keep diagnostic logs for`, and that bound is not a switch. Background compaction never removes anything a person could see ([Spec-020 §Retention Policy](../specs/020-data-retention-export-and-deletion.md#retention-policy)).
- **The provider's own files.** `"cleanupPeriodDays": 36500` in every Claude Code process and account home, the `settingsIgnored` read-back, and the provider files a purge removes are Plan-003's and Plan-001's ([ADR-037](../decisions/037-kept-sessions-keep-their-provider-files.md)).
- **Deleting the hosted account.** `account.delete`, `account.export` and the token denylist are Plan-015 Phase 5's control-plane account work; this plan carries the Path-2 closure it must cover (CP-019-3).

## Data And Storage Changes

### PII Data Map

Per [Spec-020 §PII Data Map](../specs/020-data-retention-export-and-deletion.md#pii-data-map), the PII the data acts reach sits in two durability tiers, and nothing is exported off the machine through telemetry. Plan-019 owns the erasure of the durable tier on the machine (below), the purge's erasure step and the erase; the control plane's side of the durable tier is owned plan-by-plan — Plan-015 (`users`, `webauthn_credentials`, `webauthn_challenges`) and Plan-025 (`devices`, `machines`, `trust_statements`) — and deleted by Plan-015's `account.delete`; Plan-017 owns the bounded-retention tier, which drops past `Keep diagnostic logs for`. These tiers classify the user's **PII content** by where it lives; account deletion's **relational** obligation is a distinct, broader lens — the complete `REFERENCES users(id)` inbound-FK closure of CP-019-3, which additionally reaches the token denylist (`revoked_jtis`/`revoked_token_families`) that FK-links to the user without carrying a PII column.

### Credential store: the daemon's secrets

Per [Spec-020 §Daemon Secrets](../specs/020-data-retention-export-and-deletion.md#daemon-secrets), each daemon secret is its own item in the operating system's credential store, and nothing in the daemon's database is encrypted by the app. The store is the production `SecretKeychain` in `credential_store.rs`, whose `SecretItems` hands each feature the keychain the place record names: `OsSecretKeychain` (`credential_store/os.rs`, on Windows Credential Manager through `sidekicks-platforms`) or `FileSecretKeychain` (`credential_store/file.rs`).

- **macOS.** One item per secret through `keyring-core` in the login keychain.
- **macOS while the person is logged out.** `sidekicks daemon install --while-signed-out` installs a system service ([Plan-005](./005-local-ipc-and-daemon-control.md) T-005r-3-11), and that service cannot reach the login keychain. So once the service is installed and takes over, the daemon moves its items to the same `secrets.json` file Linux uses, plain, at mode `0600`, each written, read back and only then deleted from the keychain, and `sidekicks daemon uninstall` moves them back the same way; each Claude Code sign-in moves with them ([Plan-023](./023-provider-accounts-and-credential-homes.md) T3.5). Settings › Runtime then shows `Secrets stored without encryption` over `Only this account can read them.`, and once the service is turned off in Login Items & Extensions, until uninstall moves them back, the same title over `Run sidekicks daemon uninstall to move them to the keychain.`, the file's path in its own row under the line, read from the same `secretsFile` ([Spec-020 §Daemon Secrets](../specs/020-data-retention-export-and-deletion.md#daemon-secrets)).
- **Linux.** The daemon keeps its items in one file in its own data folder, readable by this account alone (mode `0600`), each sealed through systemd's credential service (systemd 256 or newer) with the security chip where systemd can use it and the system key alone where not, and plain, as `gh` and Codex keep theirs, where that service is absent, refuses at the first start, or would bind the seal to the Secure Boot state, sealed once at a later start whose check finds it sealing unbound; never the kernel keyring, and never silently: Settings › Runtime and `sidekicks daemon status` name the place, or why the sealed file cannot be opened, `<path>` being that file, `secrets.json`, read from `daemon.status.read`'s `secretsFile` and its place ([Spec-020 §Daemon Secrets](../specs/020-data-retention-export-and-deletion.md#daemon-secrets)).
- **Windows.** One Credential Manager generic credential per item at `CRED_PERSIST_LOCAL_MACHINE`, through `windows-native-keyring-store` 1.1.0 with `persistence=local` (the store writes Enterprise, a roaming persistence, unless told), written and read in the service's own process through `sidekicks-platforms` (CP-019-5). No store inside a WSL 2 distribution is used: sessions there run through the WSL server, which holds no secret, so a Windows computer has one place for secrets.
- **A locked store** refuses with its cause, `locked` or `unavailable`, and the secret is stored nowhere else.
- **One call at a time per account.** Credential-store calls on one account run one at a time, and a late save finishes before the retry runs, so it never overwrites the retry's value (T19.1.4).
- **Erase** deletes every credential-store item the app made (T19.2.2).

## API And Transport Changes

### Data verbs (daemon JSON-RPC via Plan-005's host)

Methods registered by Plan-019 on Plan-005's JSON-RPC `MethodRegistry` (`daemon/data_methods.rs`), each with its params and result schemas in `crates/sidekicks-contracts/src/daemon/data.rs`. The host is **daemon-bound, not the control plane**: the handlers read the daemon's own database and its credential-store items, which a Cloudflare-Workers control plane cannot reach (data-locality — see [§Design Decisions](#design-decisions) D-019-1). Errors ride the [ADR-009](../decisions/009-json-rpc-ipc-wire-format.md) JSON-RPC envelope.

- `daemon.dataExport.start {destination}` → a job; `daemon.dataExport.subscribe` carries its progress. `destination` is the path the save dialog hands back, named `sidekicks-export-<date>`, or the command line's folder. The folder holds `sessions/<id>.jsonl` (every event, one per line, in the canonical event shape, each body decoded), `files/<session id>/…`, `sidekicks/`, `workflows/`, `accounts.json` with no credential, `hosted-account.json` when signed in (the control plane's `account.export`), and `README.txt`; never a settings value, a credential, a pasted token, a workflow secret, a key or a diagnostic log. One session at a time within 64 MiB, one job at a time; an export writes one line to the diagnostic log and no event.
- `daemon.data.erase {}` — `Erase all data`, in order: stop every run and shell as `Stop` does; sign each provider account out through its home reset ([Plan-023](./023-provider-accounts-and-credential-homes.md) T2.2), which runs the provider's own sign-out first (`claude auth logout` in each Claude Code account home, `account/logout` on each Codex service); revoke this machine's refresh family when signed in to the hosted account; delete every credential-store item the app made; on a Windows computer unmount the private mount in each distribution first, as uninstall does, so no server start finds a mount over a deleted folder; delete the data folder, the account homes it made included, each WSL 2 distribution's `~/.ai-sidekicks/` (worktrees aside) through its WSL server, and the main process's log; start again empty. Project folders stay, and a backup taken earlier keeps what it held.

## Invariants

Behavioral invariants this plan must preserve; the §Implementation Phase Sequence Tasks cite them in `Verifies invariant`.

- **I-019-1 — The export carries no secret.** An export folder holds no settings value, credential, pasted token, workflow secret, key or diagnostic log, and it streams one session at a time within 64 MiB, one export at a time. ([Spec-020 §Data Export](../specs/020-data-retention-export-and-deletion.md#data-export).) Tasks: T19.2.1.
- **I-019-2 — Erase runs in its order.** `daemon.data.erase` stops work, signs providers out and revokes the refresh family before it deletes any credential-store item, and deletes every credential-store item the app made before it deletes the data folder; project folders are never touched. ([Spec-020 §Erasure Paths](../specs/020-data-retention-export-and-deletion.md#erasure-paths) Path 1; [Spec-020 §Ordering And Atomicity](../specs/020-data-retention-export-and-deletion.md#ordering-and-atomicity).) Tasks: T19.2.2.
- **I-019-3 — Reciprocal completeness.** Every CP-019 obligation has a reciprocal entry in its owner plan; no one-sided cross-plan edge ships. For CP-019-3 (the `REFERENCES users(id)` Path-2 closure), every owner table's plan carries a live reciprocal, so the closure is complete with no silent gap. Tasks: T19.3.1.
- **I-019-4 — Nothing readable after a purge.** The purge deletes the session's rows in one transaction with `secure_delete` on and checkpoints the write-ahead log with `TRUNCATE` once it commits, so a byte scan of the database file and its log finds none of the deleted session's text. ([Spec-020 §Erasure In The Daemon's Database](../specs/020-data-retention-export-and-deletion.md#erasure-in-the-daemons-database); [Spec-020 §Ordering And Atomicity](../specs/020-data-retention-export-and-deletion.md#ordering-and-atomicity).) Tasks: T19.3.1.
- **I-019-5 — No phantom PII columns.** Every column named in the §PII Data Map resolves to a real column in its owner plan's schema. (D-019-2.) Tasks: T19.3.1.
- **I-019-6 — One purge.** `daemon.retention.purge` is the only path that deletes a session, and it runs this plan's erasure step; nothing deletes a session by age. ([Spec-020 §Retention Policy](../specs/020-data-retention-export-and-deletion.md#retention-policy); [Spec-020 §Ordering And Atomicity](../specs/020-data-retention-export-and-deletion.md#ordering-and-atomicity).) Tasks: T19.3.1.
- **I-019-7 — Each secret is its own credential-store item.** Every daemon secret — the identity key, the channel key, and the hosted sign-in's refresh token and DPoP key — is its own item, and nothing in the daemon's database is encrypted by the app; on Linux the store is one file in the data folder at mode `0600`, each item sealed through systemd's credential service where it can seal and plain where not, never the kernel keyring and never silently, and a sealed file that cannot be opened refuses and is never rewritten; a Mac keeps its items in the same file from its logged-out service's takeover until uninstall, even after that service is turned off in Login Items & Extensions. ([Spec-020 §Daemon Secrets](../specs/020-data-retention-export-and-deletion.md#daemon-secrets).) Tasks: T19.1.1, T19.1.2, T19.1.4.
- **I-019-8 — Windows items stay on the machine.** On a Windows computer every Credential Manager item is written, read and deleted at `CRED_PERSIST_LOCAL_MACHINE`, in the service's own process, whichever unit keeps it — a daemon secret, a pasted token, a workflow secret, a tool server's refresh token or DPoP key — and none at a roaming persistence. ([Spec-020 §Daemon Secrets](../specs/020-data-retention-export-and-deletion.md#daemon-secrets).) Tasks: T19.1.3.

## Cross-Plan Obligations

- **CP-019-1 — `SecretKeychain` (→ Plan-005 CP-005-5).** Plan-019 ships the production `SecretKeychain` (`credential_store.rs`), which keeps each daemon secret as its own credential-store item, satisfying Plan-005's CP-005-5 store contract. Reciprocal: Plan-005 CP-005-5.
- **CP-019-2 — The purge's erasure step (⇄ Plan-005 Phase R1, Plan-004, Plan-001).** Plan-005's `daemon.retention.purge` (Phase R1) marks the session `purgeRequested`, which locks its row, and then deletes the files only this session names: its capture folder with its snapshot refs and base pins, a chat's managed workspace (Plan-001's `ManagedWorkspaceService.delete`), and the provider's files for the session (Plan-003). Then it deletes the session's rows, its artifact manifests among them, outright in one transaction with SQLite's `secure_delete` on, so their freed pages hold nothing readable, and once the transaction commits it checkpoints the write-ahead log with `TRUNCATE`, retrying while a reader holds an older snapshot, so the log keeps no copy of the deleted rows. A failure before that transaction leaves the row `purgeRequested`, to be retried. After that commit, the artifact payloads no surviving manifest names are unlinked, and the orphan sweep reclaims one a crash leaves ([Spec-012 §Local Artifact Deletion And CAS Reclaim (V1)](../specs/012-artifacts-files-and-attachments.md#local-artifact-deletion-and-cas-reclaim-v1), Plan-011). No event of the session records the purge, because no row of the session survives to hold one ([Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)). Reciprocal: Plan-005 Phase R1. Verified at code time per Implementation Step 5.
- **CP-019-3 — Path-2 closure (⇄ Plan-015/028) — the complete inbound-FK closure `account.delete` covers.** Plan-015 Phase 5's `account.delete` deletes the hosted account over the **complete `REFERENCES users(id)` inbound-foreign-key closure** in [hosted-account-schema.md](../architecture/schemas/hosted-account-schema.md) — derived from the schema, not a hand-maintained list, so the set cannot silently drift: the `users` anchor itself plus every table carrying a `REFERENCES users(id)` column, each table counted **once** however many such columns it bears. Re-derive the set from the schema whenever a table is added or dropped. `webauthn_challenges` and `webauthn_credentials` are hard-DELETE class: a challenge row is a live ceremony transaction and a credential row is verified live, so nothing retained re-verifies either after deletion. [Spec-020 §Erasure Paths](../specs/020-data-retention-export-and-deletion.md#erasure-paths) Path-2 Mechanism names this closure ([§Design Decisions](#design-decisions) D-019-3). Each owner carries the reciprocal:
  - **Plan-015** — `users` hard-DELETE (CP-015-6); `webauthn_credentials` and `webauthn_challenges` hard-DELETE; an `authorization_requests` row the account approved hard-DELETEd with it (`ON DELETE CASCADE` on `approved_user_id`); `refresh_token_families` hard-DELETE (one row per live sign-in; revoking a family deletes its row, and `user_id` cascades); `revoked_token_families` hard-DELETE: a refresh token has no expiry of its own, so a revoked family's row stays for the account's life and goes with it; and `revoked_jtis`, which Plan-015 Phase 5 builds nullable + `ON DELETE SET NULL` on `user_id` — anonymize `user_id` and retain the `jti` key to its natural `expires_at + 24h` reap, a margin past the access token's lifetime (security-survival per [Spec-020 §Erasure Paths](../specs/020-data-retention-export-and-deletion.md#erasure-paths)). `account.delete` revokes the account's refresh families before it deletes.
  - **Plan-025** — `devices`, `machines` and `trust_statements` hard-DELETE: the account's linked devices and its machines' registrations with their public keys, and its append-only chain of signed trust statements; deletion is safe at live-verification semantics, since every machine verifies the chain it keeps itself.

  The control plane holds no notification table and no artifact copy: a push is sealed on the machine to the device's push key and the relay stores nothing that opens it, and a session's artifacts stay on the machine that ran it, so neither adds a leg to this closure.

- **CP-019-4 — Path-3 bound (⇄ Plan-017, Plan-005 Phase R1).** Plan-017's diagnostic buckets delete each log file whole once it is past `Keep diagnostic logs for`, on the service's one scheduler (Plan-005 Phase R1); `Erase all data` deletes them with the data folder. There is no per-person flush. Reciprocal: Plan-017 CP-017-1.
- **CP-019-5 — The credential store's Windows arm (⇄ Plan-005 Phase R4).** Every credential-store item is Credential Manager at `CRED_PERSIST_LOCAL_MACHINE` through `windows-native-keyring-store` 1.1.0 with `persistence=local`. The service writes, reads and deletes it in its own process through `sidekicks-platforms`' credential code, and with the service stopped `sidekicks data erase` starts the daemon program in its erase mode, which calls that same code in its own process; the CLI inside a WSL 2 distribution hands that command to the Windows CLI through interop. This plan's `OsSecretKeychain` is the daemon's only caller of that code, and every other unit that keeps an item — the pasted provider tokens, the workflow secrets, the notification web address and its signing secret, the mail password, each tool server's refresh token and DPoP key — keeps it through `OsSecretKeychain`. Reciprocal: Plan-005 Phase R4.
- **CP-019-6 — The command-line verbs (⇄ Plan-005 Phase R3).** `sidekicks data export <folder>` calls this plan's verb with the service running; `sidekicks data erase` does what `daemon.data.erase` does and is refused while the service holds the data folder; `sidekicks account delete` calls Plan-015's `account.delete`. Reciprocal: Plan-005 Phase R3.

(2) **Spec-020** carries: the daemon's secrets in [§Daemon Secrets](../specs/020-data-retention-export-and-deletion.md#daemon-secrets), the purge's erasure in [§Erasure In The Daemon's Database](../specs/020-data-retention-export-and-deletion.md#erasure-in-the-daemons-database), and the bucket-column shape (D-019-2).

## Design Decisions

The design decisions behind the plan body above.

- **D-019-1 — Data verbs → daemon JSON-RPC on the `daemon` root.** `daemon.dataExport.start`, `daemon.dataExport.subscribe` and `daemon.data.erase` are **daemon JSON-RPC methods** on Plan-005's `MethodRegistry` (data-locality: the handlers reach the daemon's own database and its credential-store items, which a Cloudflare-Workers control plane cannot). Each registers its strict params type from `crates/sidekicks-contracts/src/daemon/data.rs`, which Plan-005's `MethodRegistry` decodes with serde and checks with garde before the handler body runs ([Plan-005 §I-005-6 — Schema validation runs before handler dispatch](./005-local-ipc-and-daemon-control.md#i-005-6--schema-validation-runs-before-handler-dispatch)). The names follow the wire grammar's `domain.resource.action` form, and the progress stream is `subscribe` on the same resource beside `daemon.dataExport.start`. **Type 1.**
- **D-019-2 — Diagnostic buckets are log files, deleted whole.** Each diagnostic bucket is log files in the daemon's data folder, never a database table, and Path 3 deletes a file whole once it is past `Keep diagnostic logs for`, as [Spec-020 §PII Data Map](../specs/020-data-retention-export-and-deletion.md#pii-data-map) records; the Content column in this plan's §PII Data Map bounded tier is a gloss on what each bucket carries. **Type 1.**
- **D-019-3 — Path-2 fan-out is the complete `REFERENCES users(id)` inbound-FK closure.** Path-2 is anchored to the **schema-derived FK closure** (see CP-019-3 for the counting rule) rather than a hand-maintained list, so the set is verifiable against [hosted-account-schema.md](../architecture/schemas/hosted-account-schema.md) and cannot silently drift. [Spec-020 §Erasure Paths](../specs/020-data-retention-export-and-deletion.md#erasure-paths) Path 2 names the full closure + per-table disposition, and its "Scope: exhaustive" claim is anchored to the FK closure rather than to the §PII Data Map, which lists PII-content columns and not the FK-linkage tables. Owner: Plan-015 Phase 5's `account.delete`, which deletes the whole closure (CP-019-3). Plan-015 Phase 5 builds the token denylist with its disposition named in CP-019-3. The `revoked_*` disposition is anonymize-`user_id`-with-denylist-survival: the denylist lookup is keyed on `jti` / `family_id` (the table PRIMARY KEY), **not** on `user_id`, so anonymizing `user_id` severs the data-subject linkage without touching the revocation check — the row stays denied to its natural `expires_at` reap, so erasure does not resurrect a revoked token within its validity window. **FK-safety mechanism.** "anonymize" is realized by `ON DELETE SET NULL`, not a tombstone identifier. The one anonymize-class FK, `revoked_jtis.user_id`, which Plan-015 Phase 5 adds, is nullable with `ON DELETE SET NULL` in the control plane's one schema, so the `users` hard-DELETE auto-nulls the reference DB-side: FK-safe, and a no-op on the PRIMARY-KEY `jti`. `revoked_token_families` rows are hard-DELETEd with the account. A reserved _tombstone user row_ was rejected: it spawns a ghost-row subsystem for no gain over `SET NULL`. [Spec-020 §Erasure Paths](../specs/020-data-retention-export-and-deletion.md#erasure-paths) Path 2 FK-safety is the canonical statement. **Type 1.**

## Rollback Or Fallback

- A Linux machine whose systemd cannot seal keeps the daemon's items in the one file in the data folder at mode `0600` — no code change required; the kernel keyring is never a fallback. A locked store refuses with its cause, and the secret is stored nowhere else.

## Risks And Blockers

- **Risk**: no systemd credential service on a headless Linux host or in a container. **Mitigation**: the items go into the one file at mode `0600`, never the kernel keyring, and Settings › Runtime says where secrets are kept. **Risk**: the key a sealed file was sealed with changes (the chip cleared or replaced, the Secure Boot settings, the account or the machine id changed). **Mitigation**: the file is left as it is, every call refuses with `unavailable`, Settings › Runtime and `sidekicks daemon status` name the cause, and removing the computer and linking it again empties the file; on systemd 256 and 257 with a chip, whose seal a Secure Boot update breaks, the file stays plain until a later systemd seals unbound.
- **A deleted row's bytes stay in its freed page.** Measured on SQLite 3.53.4, one patch past the 3.53.2 that `rusqlite` 0.40.2 bundles, in write-ahead-log mode: ten rows removed by `DELETE` alone stayed byte-for-byte in the database file after a `TRUNCATE` checkpoint. The purge therefore deletes with `secure_delete` on and checkpoints with `TRUNCATE` after commit, and the purge's byte-scan test proves on every SQLite the build pins that no deleted session's text stays in the database file or the log.
