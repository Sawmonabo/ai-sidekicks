## Goal

Implement the V1 agent identity surface, parent-child run linkage, and provider-agnostic orchestration semantics in the session itself — the spend limit, the token limit and their stop conditions as a hard V1 quality gate — for concurrent multi-agent work.

## Scope

This plan covers the agent identity and configuration surface, orchestration run creation with full admission enforcement, durable run-link projection, budget accounting that interrupts at a limit the person set, the spend-limit and token-limit stop conditions, desktop surfaces for concurrent agent work, per-request pricing from the providers' own figures and a live price table (voice minutes included), the per-turn step bound, and sessions talking to each other.

## Non-Goals

- Workflow authoring syntax (Plan-014)
- Provider-native subagent APIs beyond normalized adapters (ADR-005)
- Transcript summary-row rendering (Plan-010 — D-013-10; this plan publishes the durable inputs only)

## Preconditions

Target paths below assume the implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

## Data And Storage Changes

- `run_links` (single-parent `child_run_id` PRIMARY KEY, `session_id` provenance, `reached_by` CHECK (`provider_subagent` | `bridge_run` | `workflow_step`)), `agents` (no state column: the provider-binding columns and the one pending-switch column), `session_budgets` (row-canonical limits), and `agent_tree_nodes` (the daemon's own agent tree index: one row per agent keyed by its run, its provider and the provider's own id for it (the task id or thread id, which is also what a restart resumes it by), holding the provider's own parent reference and the state the child's row draws: `running`, `completed`, `failed`, `interrupted` or `stopped`) per [Orchestration Tables (Plan-013)](../architecture/schemas/local-sqlite-orchestration-tables.md).
- `session_exchanges` (the pair of sessions trading messages and the count since the person last wrote) and `session_paused_message_queue` (every message addressed to a paused session, in arrival order, each row naming the sender's own send event rather than holding its words) per the same schema section, added to the daemon's one schema by T2.9 — the two pieces of daemon state [Spec-014 §State And Data Implications](../specs/014-multi-agent-orchestration.md#state-and-data-implications) declares durable. The session directory beside them is **not** a table: it is rebuilt from the sessions the daemon hosts when it starts.
- `run_links` and `agents` are events-canonical projections (ADR-016 Option B) rebuilt byte-equal from events; `session_budgets` is row-canonical daemon configuration (the `queue_items` posture — mutated by wire method, never evented), and so are the session-messaging tables, the `agents.pending_switch` column (written before a switch is acknowledged, since no event records a switch being asked for), and `agent_tree_nodes` (written by the daemon alone when an agent starts and when its state changes) — a message persists nothing of its own, so neither is rebuilt from the log.
- Budget **accounting** has no accumulator table: the `BudgetAccountant` is an in-memory projection over `usage_telemetry` + `run.*` events, rebuilt from events (D-013-5); per-run effective ceilings rebuild from the durable `run.queued` `effectiveRunConfig?` field, not by re-merging session defaults that may have changed mid-run. The per-turn usage rows [Plan-023](./023-provider-accounts-and-credential-homes.md) projects per provider account are a **projection over the same `usage_telemetry` events**, rebuilt from events like every other one and served through this plan's one committed-spend accessor, so the account surface's by-day and by-model figures are an axis over the accountant's own facts rather than a second accountant beside it. Every request is priced once when it completes and its figure is stored in integer micro-dollars; a request on a model the price table does not price yet is stored with its exact tokens as held and joins the fold when a fetch prices it (T2.10).
- No transcript-projection rows: this plan publishes durable events only; Plan-010 derives summary rows (D-013-10).

## API And Transport Changes

- Daemon JSON-RPC pairs per [orchestration-payloads.md §Plan-013](../architecture/contracts/orchestration-payloads.md#plan-013--multi-agent-orchestration): `orchestration.runCreate` / `orchestration.childRunLinkRead` / `orchestration.budgetRead` / `orchestration.costReceiptRead`, `agent.configUpdate` / `agent.list` (a live list: the list, then each change), `session.goalUpdate` / `session.goalClear`, `session.maxStepsUpdate`, `session.spendLimitUpdate` / `session.tokensPerRunUpdate`, and `session.terminalProviderSessionList`. Registration relies on the registry accepting camelCase method tails, and typed wire errors on the `DaemonDomainError` projection (CP-013-9).
- Owned event types in the [Spec-005 registry](../specs/005-session-event-taxonomy-and-audit-log.md): `orchestration.rejected`, the limit events `session.spend_limit_reached` / `run.token_limit_reached` (T1.1), the goal events `session.goal_updated` / `session.goal_cleared` (T1.2), and the provider-binding events `agent.provider_binding_changed` / `agent.provider_binding_change_failed` (T1.4).
- The `run.queued` payload gains optional additive linkage fields `{agentId?, parentRunId?, reachedBy?}` plus the admission-resolved `effectiveRunConfig?` threaded from the in-process `OrchestrationRunLinkCarrier` (D-013-3, CP-002-10; ADR-017 additive-only). The run's agent is `agentId` for an agent already in the projection or `resolvedAgent` for one minted from a definition, never both, and none of these members rides the run's state stream.
- Error vocabulary per [error-contracts.md](../architecture/contracts/error-contracts.md) §Orchestration / §Agent (D-013-11), plus `driver.capability_unsupported` for a switch axis the target driver does not have, and for the goal RPCs `session.not_found` for a session id the daemon does not hold, appending nothing, and `driver.capability_unsupported` where the agent's provider cannot carry a goal.
- **Contract mirror — the agent's provider binding (D-013-17).** `AgentProviderBinding {driverName, modelId, providerAccountId, effort, outputSpeed?}` — `providerAccountId` null where the agent follows its provider's current account — is the one shape the agent row, `agent.list` and the binding events share. The axes a run starts with gain `providerAccountId?` + `effort?`. `AgentConfigUpdateRequest` is `{agentId, modelId?, effort?, outputSpeed?, driverName?, interruptAndSwitch?}`, every member additive-optional per [ADR-017](../decisions/017-cross-version-compatibility.md) and an omitted member **unchanged, never reset**; it carries no account member, because which account a provider's work runs on is the provider surface's own control (`providerAccount.setCurrent`, [Spec-025 §Moving a session to another account](../specs/025-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)), and an account move settles through the same binding events. `AgentConfigUpdateResponse` gains `switch?: AgentBindingSwitchDisposition` — a **discriminated union**, not a settlement, because mutation and application are two moments: `AgentBindingSwitchPending` (`switchId`, the resolved `appliesAt` boundary, the target binding, `interruptRequested`, and `replacedSwitchId?` on a supersession) is the ordinary arm, and the **settled** arms are reachable only on the `interruptAndSwitch` arm, which holds its request open: `{ status: 'applied' } & AgentBindingSwitchOutcome`, `{ status: 'degraded' } & AgentBindingSwitchOutcome` under a **total** mapping from continuity (`applied` iff the conversation arrived whole — `in_place`; `degraded` iff it did not — `brief`), and `AgentBindingSwitchFailed` carrying the same `reason` vocabulary as `agent.provider_binding_change_failed`. Each settlement has its own arm, because an arm that waits for its own settlement must be able to express every settlement its boundary can reach. A change of model, effort or speed alone settles `in_place` at the next turn, so a pending switch that waits for the end of a run is a `driverName` change. The durable `agents.pending_switch` column stores a **superset** of the wire record — adding the device the request came from and the `'requested'` \| `'dispatched'` interrupt-dispatch marker — neither of which is ever returned to a caller or appended to a payload. `AgentBindingSwitchOutcome` carries the `continuity` naming which mechanism carried the conversation (`in_place` \| `brief`) and the `DeclaredLossKind` union. `AgentListResponse.agents` is a live list — the list, then each change — and each row returns the effective binding, the definition it was resolved from, its provider, its place in the session's agent tree, the live-scoped `observedOutputSpeed?` (the provider's own declared speed state and its reason, projected from the live runtime binding and stored in no column, so a mode the provider's account gate refused is readable beside the one that was requested rather than hidden behind it), and any `pendingSwitch?`, so a caller that did not issue the mutation still sees the binding and the switch waiting against it — all mirrored in [orchestration-payloads.md §Plan-013](../architecture/contracts/orchestration-payloads.md#plan-013--multi-agent-orchestration). `effort` is a `string` rather than a corpus enum on purpose: the valid set is the target model's driver-reported `effortLevels`, so an enum here would be a second, staler source of a provider-owned vocabulary. The response member's **presence** is the switch discriminator, so a pure rename carries no switch member at all and a consumer cannot mistake one for the other; within it, `status` discriminates a promise from a settlement — and, among settlements, an honest degrade from an ordinary success — so no consumer reads a `continuity` that a deferred switch has not produced yet, nor re-derives `degraded` for itself. These refusals reach a caller before acceptance: `agent.provider_axis_invalid` (400) for a value outside the target driver's published vocabulary, and `driver.capability_unsupported` for an axis the target driver does not have; every application step is a compare-and-set on `switchId`. The events that settle a switch are `agent.provider_binding_changed` — the session, the agent, `switchId`, the actor, `from` and `to` each with its account, the account the run landed on, `continuity` and `declaredLosses` — and `agent.provider_binding_change_failed` — the session, the agent, `switchId`, the actor, `from`, `attempted` with its account, a `reason` (`driver_unavailable`, `model_unavailable`, `effort_unavailable`, `output_speed_unavailable`, `interrupt_refused`, `target_unstartable`, `account_unavailable`) and, with `account_unavailable`, `accountState` (`reauth_required`, `home_missing`, `indeterminate` or `not_registered`).
- **Contract mirror — cost display consistency (D-013-15).** `OrchestrationBudgetState` carries the session's committed spend and a per-agent axis — `committedSpendUsdMicros` and `agentSpend: [{agent, ownUsdMicros, subtreeUsdMicros}]` over every member of the session's tree — an agent by its `agentId`, or a provider's own helper by its run and the handle the index minted for it — each member's own spend and that plus the spend of every member under it, routed up the parent chain — in integer micro-dollars, mirrored in [orchestration-payloads.md §Plan-013](../architecture/contracts/orchestration-payloads.md#plan-013--multi-agent-orchestration). They ride the one `OrchestrationBudgetState` that `orchestration.budgetRead` answers and that `session.spendLimitUpdate` and `session.tokensPerRunUpdate` answer too, so the members are required on the update replies as well, which is why the obligation binds the mutation binder (T3.1) as well as the query binder (T3.2): no event type, no error code, and no table for it. The cost receipt's `Total` is committed spend by [Spec-014 §Cost Derivation And Absent-Cost Semantics](../specs/014-multi-agent-orchestration.md#cost-derivation-and-absent-cost-semantics); what this plan adds is the asserted equality between it and `committedSpendUsdMicros` at the same fold state (I-013-15), not a payload change.
- **Contract mirror — session cost receipt (D-013-16).** One read method, `orchestration.costReceiptRead {sessionId}`, and its `SessionCostReceipt` response shape mirrored in [orchestration-payloads.md §Plan-013](../architecture/contracts/orchestration-payloads.md#plan-013--multi-agent-orchestration): the providers in the order the session first spent on them, the session's own provider first, each with its account rows `{provider, account, billingMode, tokens, usdMicros}` (`billingMode` is `subscription`, `metered` or `unknown`, and labels the figure without changing how it is derived), its `Voice` row where the session made voice calls, and its subtotal, then the session total, every amount in integer micro-dollars served from the one committed-spend accessor. It refuses a session id the daemon does not hold with `session.not_found` and appends nothing. Identities ride it as contract comments so T3.9's parity claim has something to match: each provider's rows sum to its subtotal, and the subtotals sum to the session total. **No new event type, no new error code, and no table** — the receipt is a decomposition of an existing fold, so `session_budgets` is unchanged. The account each row names comes from the per-turn usage rows, keyed on the account each request ran on, and its name and billing mode as [Plan-023](./023-provider-accounts-and-credential-homes.md) supplies them (CP-023-3) — not a Plan-013-owned surface, and this plan reads it without widening it.

- **CP-013-6 — Usage telemetry.** Consume `usage_telemetry` driver events (Plan-003) as BudgetAccountant input — the per-request priced figure the daemon stores in integer micro-dollars (the Claude Code leg's own `costUSD` per model from `modelUsage` where its `costBasis` reads `list` or `managed`, every other request priced by T2.4 from T2.10's table) and the `usage.token_count` per-turn rows as the fold input of a run's `Tokens per run` limit, **summed** by the accountant over the run's rows per their [Spec-005 §Usage Telemetry](../specs/005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) per-turn semantics (emitter discipline Plan-003 I-003-10; the accountant never differences one row against another and never re-derives what the driver already metered) — enforcement consumes, never re-derives. Further provider signals are explicit inputs with owned effects: a request `usage.model_rerouted` names is priced at the model it ran on, `toModel`, and held until the price table prices that model, so a rerouted request is never priced at the model it was sent to, verified in the owning task's test list. **Tasks:** T2.4, T2.10.
- **CP-013-7 — Transcript inputs forward.** Publish durable child-run events + carrier; [Plan-010](./010-transcript-and-reasoning.md) derives summary rows; this plan imports nothing from Plan-010 (D-013-10). **Direction:** provide (forward).

- **CP-013-10 — Normalized delegation.** Drivers without native subagent primitives still support delegated work modeled as separate linked runs ([Spec-014 §Fallback Behavior](../specs/014-multi-agent-orchestration.md#fallback-behavior); ADR-005) — no Plan-013 code may assume a native spawn API. **Direction:** consume from [Plan-003](./003-provider-driver-contract-and-capabilities.md). **Tasks:** T2.2, T2.5.
- **CP-013-11 — Committed-spend fold forward (D-013-15).** Publish the BudgetAccountant's committed-spend accessor — the single fold that produces `committedSpendUsdMicros` and each agent's spend (T2.4) — as the **sole** source for any surfaced cost figure, on every surface that displays cost. A surface may not sum a run list, re-fold usage rows, or maintain a presentation-side total — the inspector's `Cost` section and the spend carried against each agent in the session's agent list both read that accessor, and a subagent's figure is the daemon's own decomposition of its run's spend rather than a total of its own; a per-agent figure declares its aggregation scope (the agent and the agents under it) per [Spec-014 §Cost Figure Display Consistency](../specs/014-multi-agent-orchestration.md#cost-figure-display-consistency). The V1 consumer set is **in-plan, and not empty**: the agent tree (T4.1) draws each agent's spend and the inspector's `Cost` section (T4.3) draws the receipt, so the obligation binds **T4.1** and **T4.3** and **no cross-plan edge is minted** for them. **One member of the set is out of plan:** [Plan-023](./023-provider-accounts-and-credential-homes.md)'s per-account spend on the Providers page is a cost-displaying surface, so it reads this accessor too — recorded at that plan as CP-023-4, with its figures served from this accessor and its per-figure scope declarations carried per clause (b) — and the cross-plan edge **is** registered. The rest of the enumeration holds: [Plan-010](./010-transcript-and-reasoning.md)'s context ring reads the context window, never cost, and [Plan-020](./020-desktop-app-and-renderer.md) supplies the renderer substrate rather than any cost fold of its own. Inside the plan the obligation binds **every** wire surface that answers with an `OrchestrationBudgetState`: the query binder T3.2 (`orchestration.budgetRead`) and the mutation binder T3.1 (`session.spendLimitUpdate` and `session.tokensPerRunUpdate`, whose replies are that same type), both serving from T2.4's one accessor. **Direction:** provide (forward). **Tasks:** T2.4, T3.1, T3.2, T4.1, T4.3.
- **CP-013-12 — Conversation reconstitution consumed from [Plan-003](./003-provider-driver-contract-and-capabilities.md).** The switch coordinator (T2.8) reconstitutes the conversation **at the driver boundary and owns none of the machinery** ([Spec-004 §The Canonical Transcript And The Hand-Over Brief](../specs/004-provider-driver-contract-and-capabilities.md#the-canonical-transcript-and-the-hand-over-brief), Plan-003 T3.16 and T3.17). This plan calls the operations that sit there: reopening a provider's **own** conversation by the identifier it kept, when a session switches back to a provider it ran on; composing the **hand-over brief** (the daemon-internal `HandOverBrief`) for a different provider — the old provider's own summary taken on a throwaway copy of the session through the driver's `exportHandoverBrief`, asked for in one shape on both providers so each decision still holding is stated once with its current value and withdrawn values sit under `Withdrawn, do not use`, then the current diffs and branch read from disk, then every earlier step as a one-line note, then the last two exchanges verbatim for continuity, then a reference to the whole old transcript written as one plain file beside the brief whose contents enter no part of the message, with private reasoning, live tool calls and the old provider's skill and command names excluded by construction. No switch replays the canonical transcript: a switch settles `in_place` or `brief`. This plan supplies the target binding and consumes the settlement, taking `continuity` and `declaredLosses` verbatim onto the response and the `agent.provider_binding_changed` event. A `degraded` settlement is surfaced, never smoothed — the marshal-never-derive rule (I-013-10) applies to this pair exactly as it does to the budget members. **Reciprocal:** none owed back; Plan-003's obligation is to Spec-004's own contract, not to this consumer.
- **CP-013-13 — Declared output-speed state consumed from [Plan-003](./003-provider-driver-contract-and-capabilities.md)** (reciprocal of that plan's `CP-003-9`). The `agent.list` binder (T3.8) reads the provider's own declared speed state — and its provider-supplied reason — from the live runtime binding's **held observation**, and projects it as the live-scoped `observedOutputSpeed` beside the committed `outputSpeed` column. Plan-003 owns the reading, which comes from where each provider declares the state ([Spec-004 §The output-speed axis](../specs/004-provider-driver-contract-and-capabilities.md#the-output-speed-axis)): on Codex the thread's establishment reply declares the tier and the provider's settings-changed notification declares it again on every change; on Claude Code the process's `initialize` reply reports the state and its reason before any turn, and each session handshake reports it again. A live binding therefore carries an observation from its spawn or establishment onward, which the driver replaces whenever the provider declares a different state, and a binding that is not live carries none. This plan therefore **issues no provider round-trip** to serve a list read, holds no copy, and adds no column — an observation persisted anywhere would be a second and staler record of a fact the running session already holds, and would let a mode that stopped being available across a restart keep reading as accepted ([Spec-004 §The output-speed axis](../specs/004-provider-driver-contract-and-capabilities.md#the-output-speed-axis)). The member is absent while the live binding has declared nothing, which is never the mode being off; this binder never waits for the observation, never forces a turn to obtain it, and never substitutes the committed value for it. The projection is the declaration of the one binding the agent is running on, so the row pairs a request with the declaration it produced. **Tasks:** T3.8.
- **CP-013-14 — Session-tool entry and the provider texts consumed from [Plan-003](./003-provider-driver-contract-and-capabilities.md)** (reciprocal of that plan's `CP-003-11`). T2.9 serves the session tools on the daemon's shared `sidekicks` tool server and **declares nothing at spawn**: every session carries one entry for that server, its own so the server knows the session and the provider, handed over by the driver that owns the provider connection — in the `--mcp-config` set on the Claude leg, where `can_use_tool` gates a call, and in the conversation's `mcp_servers` at `thread/start` on the Codex leg, the entry carrying `default_tools_approval_mode = "approve"` and a `tool_timeout_sec` so that provider asks nothing and T2.9 applies the session's level itself. The same drivers carry what is each provider's own: the shared rules as the Claude Code connection's instructions and as the Codex conversation's `developerInstructions`, the Claude Code socket frame with `from-session`, the Codex arrival and wake-up framing on `turn/start` and `turn/steer`, the hook refusals and each provider's wait wording, every text in that provider's own driver folder; and the read-only fork a `session_ask` copy runs on. Plan-003 T3.23 owns those legs and T3.15 leg 3 the shared server, so this plan adds no spawn member and no second tool host. The set of tool servers a session starts with is that plan's too, at its T3.25 — `--mcp-config` with `--strict-mcp-config` on one leg and the conversation's own configuration at `thread/start` on the other, each of a Codex session's servers a `url` entry the daemon's own MCP client fronts (T2.7) — so the `sidekicks` entry arrives as one entry in a set this plan reads rather than assembles. The step bound's spawn flag and its Codex count are [Plan-002](./002-queue-steer-pause-resume.md) T3.11's. This plan authors **nothing** on Plan-003's side; Phase 2 states that T2.9 waits for that plan's T3.15, T3.23 and T3.25 on both drivers. **Tasks:** T2.9.

## Design Decisions

- **D-013-1 — Single contract file.** All Plan-013 wire contracts live in `packages/contracts/src/orchestration.ts` — no separate `src/orchestration/` contract directory. The in-process `OrchestrationRunLinkCarrier`, which never leaves the daemon, lives with the orchestration services in the new `packages/runtime-daemon/src/orchestration/` directory.
- **D-013-2 — Method strings.** New `orchestration` and `agent` roots, per the [orchestration-payloads.md §Plan-013 registry](../architecture/contracts/orchestration-payloads.md#plan-013--multi-agent-orchestration), registered under the registry's camelCase method-name format with typed errors on the `DaemonDomainError` projection (CP-013-9).
- **D-013-3 — Linkage carrier.** Run linkage rides optional additive `run.queued` payload fields (no new event type); `run_links` is a pure events-canonical projection; another device reading the session's log rebuilds linkage from the event alone; the admission-resolved `effectiveRunConfig` rides the same additive vehicle (the durable source for D-013-5 budget rebuild).
- **D-013-4 — Typed configs.** `OrchestrationRunConfig {tokenLimit?}` is a strict typed schema, never an open `Record<string, unknown>`; DDL comments cite the type.
- **D-013-5 — Budget substrate.** `BudgetAccountant` = in-memory projection rebuilt from events (no accumulator table); durable limits = `session_budgets` row-canonical table; `orchestration.budgetRead` with `session.spendLimitUpdate` / `session.tokensPerRunUpdate` as its wire surface; per-run effective overrides persist on `run.queued` (`effectiveRunConfig`) — enforcement rebuilds from the event, never by re-merging session values (which may change mid-run).
- **D-013-6 — System interventions.** Budget interrupts enter through Plan-002's in-process entrypoint below wire authz, with NULL-for-system actor and the standard `expectedRunVersion` reject-re-read-retry loop.
- **D-013-7 — One machine.** Every run in a session, a child run included, executes on the machine that runs the session. An orchestration request names no machine, and admission makes no machine check.
- **D-013-8 — Scheduler semantics.** No count limit of the runtime's own on pending orchestration runs, active children, or queued items; a provider's own limits apply under the person's own provider settings and its refusals surface in its own words. Admission refuses only on the state of what a run targets: create-time enforcement, zero residue, durable `orchestration.rejected` record. A reached spend limit is never a refusal: while it stands no turn starts in the session.
- **D-013-9 — Queue seam.** Orchestration admission pipeline (agent → budget gate) then in-process Plan-002 queue admission with the typed carrier; `RunId` mints at queue insert (`state: 'queued'` in the create response); zero-residue refusals.
- **D-013-10 — Transcript seam.** Events-only producer: no transcript rows, no Plan-010 imports; Plan-010 derives summary rows from the durable events + carrier.
- **D-013-11 — Error vocabulary.** [error-contracts.md](../architecture/contracts/error-contracts.md) §Orchestration / §Agent; parent-not-found reuses `run.not_found`; no token collides with an event name.
- **D-013-12 — How a child was reached.** A child's link records `reachedBy`: `provider_subagent` (the provider's own subagent), `bridge_run` (a bridge `run` call) or `workflow_step` (a workflow's `agent.run` step), durable in the run linkage, beside the agent the child runs, which is the agent that was asked. A `provider_subagent` link is written by the provider driver: Claude Code's subagent start and stop notifications and Codex's collaborating-agent events each add or close the run-link row for that subagent, so a provider's own subagents appear in the agent tree like any other child. However it was reached, a child appears in exactly three places, all fed by one source: a row in its parent's transcript where the dispatch happened, a row in the session's agent list, and its own child view. `reachedBy` is internal data: no screen, label or tag shows it or any word for how a child was reached; the screen shows the agent tree, each child's provider and model, and `via <agent>` naming the agent that was asked where the child was a peer call.
- **D-013-13 — Desktop scope.** V1 desktop ships **no** `OrchestrationRunCreate` affordance (its callers are the cross-provider bridge's `run` verb and a workflow's `agent.run` step); it renders the session's agent tree with each agent's linkage, state mark from its runs, refusal records and spend (T4.1), and the inspector's `Cost` section (T4.3).
- **D-013-14 — An agent has no lifecycle state.** An agent is in its session or it is not ([agent-and-run-model.md §Lifecycle](../domain/agent-and-run-model.md#lifecycle)), with no lifecycle state of its own; the record that creates an agent's row and every `agent.*` event payload carry the daemon-resolved values the row holds, so the projection rebuilds deterministically.
- **D-013-15 — Displayed cost and enforced cost are one fold** (per [Spec-014 §Design Decisions](../specs/014-multi-agent-orchestration.md#design-decisions)). Every surfaced cost figure is supplied by the committed-spend fold the accountant enforces against ([Spec-014 §Cost Figure Display Consistency](../specs/014-multi-agent-orchestration.md#cost-figure-display-consistency)), and the budget state — served identically on the `orchestration.budgetRead`, `session.spendLimitUpdate` and `session.tokensPerRunUpdate` replies, which are one `OrchestrationBudgetState` — carries the committed spend and each agent's spend with the agents under it from that one fold, with no second arithmetic. Each figure is the sum of priced requests, so it carries no mark: no provenance member, no estimate and no bound. An overview that shows root runs at their own cost alone, while delegated spend lands on their children, renders a large multi-run campaign at a small fraction of its true cost; routing every agent's spend up the parent chain at whatever depth it sits (D-013-12 linkage) and rolling in-session subagent usage into its run already bound the arithmetic, leaving the display rule as the residue. Three alternatives rejected: a display-side sum over the visible run list (that failure mode itself), a second presentation-side fold (two accountants over one event set diverge invisibly, since both look authoritative), and a mark on the figure — an estimate, a bound, `unpriced` — which would claim a doubt the accountant does not have. Mints no budget, no table, no event type, no wire method, and no error code ([orchestration-payloads.md §Plan-013](../architecture/contracts/orchestration-payloads.md#plan-013--multi-agent-orchestration)).
- **D-013-16 — The session cost receipt is by provider, then by account.** The receipt decomposes committed spend by provider and then by account, with a `Voice` row per provider where the session made voice calls, a `Subtotal` where a provider holds two or more rows, and the `Total`; it carries no per-run, per-turn or per-agent line ([Spec-014 §Session Cost Receipt](../specs/014-multi-agent-orchestration.md#session-cost-receipt)). The question a receipt answers is who billed what, and a turn split by an account move lands as two account rows under one provider, which a per-run axis cannot show without splitting a run. Rejected: a per-run axis beside the account axis (a second partition of the same fold that no surface draws, the per-agent spend already standing in the agent list) and a per-turn list (the transcript's own rows carry what a turn did).
- **D-013-17 — The agent's provider binding, and the switch that moves it.** The binding is `AgentProviderBinding {driverName, modelId, providerAccountId, effort, outputSpeed?}`; the request that moves it keeps the word switch (`switchId`, `pendingSwitch`) and its types are `AgentBindingSwitch*`. "Runtime binding" names only the live connection from a run to its provider process, and "execution binding" only a run's workspace and mode, so neither names this axis. Only `driverName` needs a new process: model, effort and speed settle in place through each provider's own means, and the account moves on the provider surface. The pending switch is the row's one column of daemon state, written before the acknowledgment and returned on `agent.list`, because no event records a switch being asked for; the settling events carry everything the transcript and a rebuild need. Rejected: an event appended at mutation (it reads as the binding having moved while nothing has), a per-session account switch beside the provider surface's (a session could then sit on an account the provider surface says it is not on), and treating model or effort as needing a new process (a respawn for a change neither provider needs it for).
- **D-013-18 — The price table is LiteLLM's public price list, fetched live.** The daemon prices every request the providers do not price themselves from LiteLLM's model price list (MIT), fetched as data — no library is added — at start, hourly and on first sight of a model or speed, with a copy in each release for a first start that cannot fetch. It covers every priced model both providers list, with the long-context, Fast, cache-write and one-hour cache-write rates this pricing needs. Considered: models.dev (missing rows and the one-hour cache-write field, and slower on price changes), OpenRouter's model list (its own resale prices, and terms that forbid the use), and a signed price file of our own on the release channel (a pipeline to run forever and a lag behind the list). Coverage and the license decided it. The telemetry receiver that reads the requests a provider leaves out of its stream is Node's `http` with a Zod schema for the handful of attributes it reads; an OpenTelemetry collector library was not taken, because the daemon reads only that handful of attributes.
- **D-013-19 — A Codex voice hold is stretched by `signalsmith-stretch`.** A hold on a Codex voice call is played into the call at 1.5× with the pitch kept and each pause cut to 0.2 s by `signalsmith-stretch` (MIT, its notice carried by the product) in its own AudioWorklet node, fed a second at a time, with a `pnpm patch` to its read loop so it can read a request handed over in pieces; the patch goes once an upstream release carries the fix. Considered: an audio buffer source's playback rate (it shifts the pitch) and a media element (1.1 s late in WebKit, its first 80 ms lost). Its budget is an acceptance criterion: the first sound reaches the call within 50 ms of the release, it adds at most 1.5% of one core while it plays, and it holds at most 6.4 MB, under 0.6 MB of it in the stretch. The capture and the call legs are [Spec-021](../specs/021-desktop-app-and-renderer.md)'s and [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md)'s; this plan owns the voice cost row (T2.4, T4.3).

The pairing is the file's own rather than anything this daemon writes into the text — the reply's record carries the id of the message it answers, and the chain between the two is unbroken — so what is drawn is what that session actually said ([`claude.md` §A reply comes back when the message asks for one, and the transcript pairs it to its prompt](../reference/provider-wire/claude.md#a-reply-comes-back-when-the-message-asks-for-one-and-the-transcript-pairs-it-to-its-prompt)). **No instruction line is ever added to a Claude Code frame** to make a reply come back — the reply line is Codex's framing alone — and nothing is asked of a terminal the person owns: a message that draws no reply draws none, and the row says so. `not delivered` is that same registry's answer — the entry's status turning idle with no record of the message — rather than an inference from a write that returned, since a write returning proves nothing on this path. And **this daemon's own inbox, placed in Claude Code's own socket folder, is the `from` on every delivery**, where Claude Code reports a message its inbox dropped as a `peer_message_status` frame, which is what lets a far model's own reply arrive here at all and be drawn once rather than twice. The **`PreToolUse` hook on Claude Code's `SendMessage`**, registered in the session's own `initialize` request and answered over the wire the pause hooks are answered over, denying a send whose target is another session with one of two refusal texts from the Claude Code driver's folder, printed as the JSON decision — the address an arriving message came from answered that the session's answer already goes back, with the sender's id, and any other session answered with `session_send` and that session's name ([Spec-014 §Session Tool Texts](../specs/014-multi-agent-orchestration.md#session-tool-texts)) — so every message between two sessions takes the one path while that tool keeps working for the session's own agents. What the hook judges is the call's `to` and nothing else, **the session's own helpers first**: a name or id of one of this session's own subagents or teammates, which the daemon reads off the session's stream as each starts with the plain name the helper tool gave it, or `main`, goes through untouched, as Claude Code itself sends a name shared by a helper and another session to the helper. Otherwise an address (`uds:` or `bridge:`, or a named pipe's `\\.\pipe\` name) is denied, and so is a bare name that resolves to a session — one in the daemon's own directory, or one in that provider's own live-session registry, the per-process file it writes under its configuration folder (`sessions/<pid>.json`) — while any other name goes through untouched. Reading that registry is what keeps a session the person started in their own terminal inside the rule although the daemon never started it. The **exchange interrupt**, which ends the turn on both sides and empties the queue between them as one ordinary interrupt per run through the in-process entrypoint. The **person's own message to another session**: a composer draft that begins with a session's `@name` is one Send, carried by `run.queueCreate` with an addressee member `to` ([Plan-002](./002-queue-steer-pause-resume.md)), which this service routes there as that session's own row, while a later `@name` in a message stays a mention. And the **peer arrival with no tool call**: a frame the daemon did not send, arriving on a hosted session's own stream with a peer origin, read off that stream and recorded as the same arrival, which is what makes the address the standing method whether or not the optional terminal plugin of [ADR-035](../decisions/035-claude-code-mods-are-an-optional-terminal-bridge.md) is loaded. **The shared Codex service**: one `codex` service the daemon runs on the person's own Codex folder while the Codex switch `Reach Codex sessions started in a terminal` is on, as it is by default. A terminal session that joins it is in the session directory and reached by the agents — `session_list` names it while its terminal is open, and `session.terminalProviderSessionList` answers the same entries — with no row in the sessions list, no heading, no window and no screen here. The daemon writes nothing into that folder's configuration except the trust records its own terminal-session hooks need: when the service starts, before any conversation loads, it writes trust for exactly its pre-tool hook — which reports a command, carries the pause and refuses a tool the agent lacks — and its post-tool hook through Codex's own `config/value/write` into that folder's `config.toml`, refreshes a record when a hook's command changes, and never cleans, rewrites or reorders any other entry; Codex keys a trust record by the hook's position, so where the person also passes their own `-c` hooks to a `codex` process on that folder, each side's trust write marks the other's hooks modified until they are trusted again. It moves no such session between accounts, and it stops the service only when the switch goes off and no terminal session is inside it ([Spec-014 §Sessions Talking To Each Other](../specs/014-multi-agent-orchestration.md#sessions-talking-to-each-other)). **One service per account, never one per person.** The sharing key is the credential home: every Codex conversation on one account is held by the one service running in that account's home, every session that follows the provider's current account in the current account's service and a session pinned to an account in that account's own service, and the service on the person's own Codex folder is that same thing under the switch rather than a second mechanism beside it — while a Claude Code session stays one process of its own, that provider offering nothing else. **Four conditions come with the sharing, and none of them is optional.** A conversation's folder, its configuration and its tool servers are **its own**, passed at `thread/start` and never as a flag on the service that holds it; a terminal session that joins runs its commands in the folder the person typed `codex` in, which `thread/started` names as the conversation's `cwd`, whatever folder the service itself runs in ([codex.md §A second seat on the shared service](../reference/provider-wire/codex.md#a-second-seat-on-the-shared-service)). ## Risks And Blockers

- Phase 3 registration and typed wire errors rest on two Plan-005 pieces: the registry's camelCase method-name format and the `DaemonDomainError` wire projection (CP-013-9).
- Provider-native orchestration differences can leak into product semantics unless normalized at the daemon boundary (ADR-005; CP-013-10).
