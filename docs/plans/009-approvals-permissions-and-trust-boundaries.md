## Goal

Implement the canonical approval, approval-rule, and permission-check model that decides every sensitive action a session's agents take on its machine, with the card's rules handed to the providers that keep them.

## Scope

This plan covers approval records, handing the card's approval rules to the providers that keep them, daemon-side permission checks, rule listing and revocation where the providers keep the rules, and approval visibility projections — plus permission-ask normalization, the run's execution posture with its credential deny-list reference, and the credential strip from the spawn environment.

## Non-Goals

- Identity-provider implementation details
- Notification routing for approval prompts
- Provider-specific permission UX beyond normalized capability requests

## Preconditions

Target paths below assume the canonical implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

## Data And Storage Changes

- Add durable local `approval_requests` and `approval_resolutions` storage. The daemon keeps no table of approval rules: the providers keep the card's rules, and a session's own answers are its `approval_resolutions` rows (`remembered_scope_kind`, `remembered_scope_pattern`) and its `approval.remembered` and `approval.rule_revoked` events (D-009-11). See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) §Approval Tables for column definitions — the audited DDL there is what the daemon's one schema carries (D-009-2).
- Serve pending and historical approval state from a daemon-local projection (SQL over the approval tables — D-009-6); no control-plane approval storage exists (ADR-016 Option B).
- Evaluation inputs are derived at check time, never duplicated into a dedicated store (D-009-15), and a machine carries no trust level: the Cedar principal ← the machine's owning user, recorded when it registers ([Plan-025](./025-remote-control.md)); working-folder roots ← Plan-006 `workspaces.fs_root` / Plan-007 `worktrees.fs_root` via `run_execution_contexts` (CP-009-8); project trust ← the project's attachment; a tool server carries no trust of its own, and one switched on joins the session's runs ([Plan-022](./022-mcp-server-configuration-and-governance.md)); an unresolvable input → strict per-request approval ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).
- The run's `executionPosture.credentialPolicyRef` is a plain reference naming the daemon's credential deny list the run was handed ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior) posture semantics). It rides the `run.running` posture stamp and needs no table of its own; deleting a session deletes it with the session's rows (local-sqlite-schema.md §Credential Policy Reference).

## API And Transport Changes

- The `approval.*` JSON-RPC methods (D-009-5), each called from the app: `approval.resolve`, `approval.projectionRead`, `approval.ruleList`, `approval.ruleRevoke`, `approval.denialOverride` — wire contract in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) §Plan-009 + §Approval Method-Name Registry. `PermissionCheck` is deliberately NOT a wire method: it is the daemon-internal pre-execution gate ([Spec-010 §Interfaces And Contracts](../specs/010-approvals-permissions-and-trust-boundaries.md#interfaces-and-contracts); D-009-18) — its typed shapes are the daemon's own, in `packages/runtime-daemon/src/policy/` beside the permission check, and never in `packages/contracts`.
- More calls land here beside these: `plan.resolve`, the plan verdict (T3.10), and `session.permissionLevelUpdate`, the level control (T3.11). `approval.requestCreate` is not a registered method: no other process calls it, so the daemon raises it in process — from a provider's callback, and from the workflow engine before a workflow's command step or full-tier Code step at `readonly`, `ask` and `reviewed` — and its request and response schema is the daemon's own, in `packages/runtime-daemon/src/approvals/`, with no client method. Each is built by the task named: `approval.requestCreate` (in process) and `approval.resolve` by T3.1 over T2.3, `approval.projectionRead` by T3.2 over T3.3, `approval.ruleList` and `approval.ruleRevoke` by T3.5 over T2.4 and T3.4, `approval.denialOverride` by T3.12, `plan.resolve` by T3.10 and `session.permissionLevelUpdate` by T3.11. The registered methods cross from the app to the daemon.
- Error vocabulary in [Error Contracts](../architecture/contracts/error-contracts.md) §Approval — its codes (D-009-4; `approval.denial_not_found` and `approval.denial_not_overridable` for T3.12's `Allow once`) — and §Session's `session.permission_level_unavailable`, which T3.10 and T3.11 register for a level the provider cannot run.
- Driver-native permission requests normalize into canonical approval categories, scopes, and resource descriptors before any record is written; Plan-009 owns the normalizer — authored as T2.8 (CP-009-5) — and until driver integration executes, the schema-validated `approval.requestCreate` boundary remains the enforced normalization gate. No new wire method lands with either: the ask surface and the execution-posture layer are in-process seams whose durable records ride Spec-005 events (the `approval.*` rows and the `run.running` posture stamp).

## Design Decisions

- **D-009-1 — Contracts file is `packages/contracts/src/approval.ts`** (single file, singular noun): one file per domain while it fits; a domain spans several files in its topic's folder when one file would pass 900 lines, the most any file holds, tests and data included, as the event contracts span `event/session-event.ts`, `event/envelope.ts`, `event/registry.ts`, `event/variant-types.ts`, `event/declared-variants.ts` and `event/core.ts`.
- **D-009-2 — Persistence model (the approval tables; DDL verbatim in local-sqlite-schema.md §Approval Tables).** `approval_requests` carries `session_id` + `requested_by` NOT NULL (provenance; no FK targets — sessions are control-plane rows, runs are event-sourced), required `resource_descriptor` (JSON), nullable `ask_id` (the originating provider permission ask's id, set iff normalizer-minted), a unique partial index on `(run_id, ask_id)` so a normalizer retry or a rebuild re-mint collides instead of duplicating, a `state` CHECK over `pending | approved | rejected | canceled`, and `updated_at` (a cancellation settles on the row — no resolution row). There is no deadline column: a request waits until it is answered ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)). `approval_resolutions` carries `request_id` as PRIMARY KEY (the durable wire id `approvalRequestId` — enforces the 1:1 decision row and keeps every projection column wire-derivable per I-009-9), the answering device's id, a `decision` CHECK over `approved | rejected`, `effective_scope` NOT NULL, and nullable `remembered_scope_kind`/`remembered_scope_pattern`. The daemon keeps no table of approval rules: the providers keep them (D-009-11), and the resolution's `remembered_scope_kind`/`remembered_scope_pattern` are the record of the rule the answer handed over.
- **D-009-3 — Consolidated wire block.** The request/response pairs + `RememberedRuleId` brand + `RememberedScope` + `InvalidationTrigger` + `ApprovalFlowEventPayload` defined in api-payload-contracts.md §Plan-009: create carries required `resourceDescriptor`; resolve carries `effectiveScope?` + `rememberedScope?`, the decline's optional reason line, the subject as the person corrected it and a client resolution id the resolution event echoes, and returns the recorded `effectiveScope`; the projection row carries `requestedBy`, `resourceDescriptor`, `updatedAt`, what the card shows as the daemon derived it from the request row (`subject`, `providerReason` where the provider sent one, `rememberOffered` and `projectScopeOffered`), and the resolved fields (`resolvedAt`/`decision`/`effectiveScope` and the answering device's id) present iff state ∈ {approved, rejected}; the rule list read takes `{sessionId}` and its rows carry `ruleId` and `scope` (the `RememberedScope`: scope kind, derived subject and sense), and the revoke takes `{ruleId}` and returns `{ruleId, revokedAt, invalidationTrigger: 'explicit'}`; the `ApprovalFlowEventPayload` carries the projection-rebuild fields (`requestedBy`/`resourceDescriptor` on `requested`, `effectiveScope`, the client resolution id and the answering device's id on the resolution events, and on `remembered` the rule the answer handed to the provider — `rememberedScope` with its sense, `ruleId`, origin = `approvalRequestId`) so relayed or logged events alone rebuild each daemon's projection rows and the session's own record of its rules (D-009-6/D-009-7, I-009-9).
- **D-009-4 — Error vocabulary (§Approval).** `approval.not_found` 404, `approval.already_resolved` 409, `approval.request_canceled` 409 (non-colliding with the `approval.canceled` event), `approval.persistence_unavailable` 503 (fail-closed), `approval.rule_not_found` 404, `approval.rule_already_revoked` 409, and `approval.denial_not_found` 404 and `approval.denial_not_overridable` 409, T3.12's refusals of `approval.denialOverride` for an unknown `denialId` and for a block the provider's reviewer marked not overridable. A press after the block's session has ended is refused with `session.already_closed`. Deliberate absence: no `approval.permission_denied` — the local IPC surface carries no caller principal, and a `PermissionCheck` denial is a normal `{allowed: false}` response.
- **D-009-5 — Method registry: strings on the new singular `approval` root** (`approval.resolve`, `approval.projectionRead`, `approval.ruleList`, `approval.ruleRevoke`, `approval.denialOverride`; `approval.requestCreate` registers no string, since only the daemon raises it and its schema is the daemon's own), registered in api-payload-contracts.md §Approval Method-Name Registry with the root added to the namespace-root enumeration. `PermissionCheck` registers NO wire method string: zero V1 wire consumers, and a wire preflight would invite stale-verdict (TOCTOU) authorization against the security gate. "Rule" (not "grant") is the operation vocabulary — matching `approval.rule_revoked` and `RememberedRuleId`.
- **D-009-6 — Projection is daemon-only.** No control-plane approval projection exists: shared Postgres stores zero approval tables (ADR-016 coordination records only; shared-postgres-schema invariants), so a control-plane projection would violate the storage posture, not extend it. `approval-projection-service.ts` lands in Plan-009-owned `packages/runtime-daemon/src/approvals/`.
- **D-009-7 — Events-canonical; rows are projections.** `EventLogService.append` commit IS the [Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior) durability gate; row projection updates after; startup reconcile applies `approval_flow` events newer than the rows' high-water mark; a failed append surfaces `approval.persistence_unavailable` and the gated action does not proceed.
- **D-009-8 — `approval.canceled` is an additive durable event (one of the `approval.*` variants of the shared payload).** Emitted when `cancelPendingForRun` settles pending requests on run-terminal; [Spec-005 §Approval Flow (approval_flow)](../specs/005-session-event-taxonomy-and-audit-log.md#approval-flow-approval_flow) gains the row. A cancellation settles on the request row (`state` + `updated_at`) — never a resolution row. Explicit-over-derived: a projector-derived cancellation would leave the `approval_flow` audit log incomplete.
- **D-009-9 — The policy engine is `@cedar-policy/cedar-wasm` in-process (`preparsePolicySet` and `preparseSchema` once at start, `statefulIsAuthorized` on every check; `isAuthorized` re-parses the policy text on every call and must not be used) over the rules compiled into the service.** The built-in rules are `.cedar` files under `packages/runtime-daemon/policies/`, compiled into the service with it and changed and shipped only by an app update, like any other code ([ADR-012 §Decision](../decisions/012-cedar-approval-policy-engine.md#decision)); the rules decide only the app's own tools — the workflow tools, messaging other sessions and the browser — and a provider's ask takes the daemon's designed answer in plain code (T2.13), the session's own answer, or the person's card ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)). The package is `@cedar-policy/cedar-wasm`, pinned at 4.13.0; `@cedarpolicy/cedar-wasm` does not exist on npm and is a dependency-confusion hazard.
- **D-009-10 — Rule scope and subject.** `RememberedScope { kind: 'session' | 'project'; pattern: string; sense: 'allow' | 'block' }`; `request_only` is expressed by OMITTING `rememberedScope`, never an enum member. `pattern` is the subject the daemon derived from the ask and the card's answer displayed — a command's program and its first subcommand, a network request's host, a written file's name, covering that one file as resolved against the CP-009-8 roots — and at resolve the daemon re-derives it and refuses an echoed pattern that differs, so a rule never covers more than the words the person pressed. The provider answers by the rule, so a rule holds at every level that asks, whatever level it was made at, and each rule is one provider's: a later ask on that subject in that scope is answered by an `allow` with no card, the row simply running, and refused by a `block` with no card, its row reading `Declined`. An allow and a block over the same subject in the same scope cannot both stand: making one replaces the other. The rule's **scope enum** (`RememberedScope.kind`) is session/project only.
- **D-009-11 — The providers keep the card's rules; the daemon keeps no rule store.** The answer that makes a rule hands it to the provider, and the session's own answers, which its record already holds, are what the daemon lists and carries across a restart of the provider's process. **Claude Code, session:** the session's allow and deny lists are the flag settings of its process, set by `apply_flag_settings {permissions}` as the card is answered, each call carrying the whole allow and deny lists (the card's session rules, the memory-folder allows passed at `Sandboxed` and the protected-path denies), and carried at launch by `--settings`; a grant, a revoke and a host block (a `WebFetch(domain:<host>)` deny, which the sandbox honors) each apply from the next call (measured on Claude Code 2.1.286). **Claude Code, project:** an allow's answer carries the rule with `destination: "localSettings"`, so Claude Code writes `.claude/settings.local.json`; a decline drops any rule it carries, so the daemon writes a project block's `WebFetch(domain:<host>)` deny into that file itself; a rule added to or removed from that file applies from the next call. **Codex, session:** an allow is `acceptForSession`. Codex has no list, no revoke and no session block, so the daemon's own tool hook holds the next call on a subject taken back and raises its card again; the daemon declines Codex's later asks for a host blocked for the session; and after a restart it answers `acceptForSession` itself on a subject the session allowed, carrying the person's recorded answer forward. The hook runs before Codex's own approval for commands, file edits and tool-server calls (read from Codex 0.159.2's source). **Codex, project:** the daemon writes the rule as a `prefix_rule`, or a host's as a `network_rule`, into the project's `.codex/rules/sidekicks.rules`, which Codex reads, network rules included, in conversations started after it (an attached project is trusted), and answers the ask `acceptForSession` so the current conversation does not ask again; when it writes that file it adds that one path to the repository's `.git/info/exclude`, which git never commits, and the person's tracked `.gitignore` is never touched. **A card the daemon raises itself** (a workflow's command step) offers `Always allow <subject> this session` and no `Always in this project`; that rule is kept with the session's own answers in its record, honored by the daemon itself, and listed with the session's rules in the inspector; its `Decline` fails the step with the receipt `Declined at <time>`, and the run parks on it until a resume asks again ([Spec-015 §Node-Kind Taxonomy](../specs/015-workflow-authoring-and-execution.md#node-kind-taxonomy)). **How a rule ends:** on `Revoke`; for a session rule, with its session, which is the provider's own session; and, for a rule over a tool server's tool, when that server is removed, which removes the rule from the provider's file that holds it in the same transaction as the removal. A project's rules live in the project's own folder and stay with it, so detaching a project records no end for any of them: it takes them out of force in the app, since no session works in the folder any more and the providers page lists only attached projects' rules, and leaves the files untouched. A session rule's revoke applies from the next call on both providers; a project rule's revoke removes it from the provider's file and reads `Applies from the next tool call.` under Claude Code and `Applies to conversations started after this.` under Codex. Each end is recorded as one `approval.rule_revoked` with its trigger (`explicit`, `session_end` or `server_removed`). The providers' rule files are the providers' own: the person or an agent edits them like any file, the provider follows the change itself, and the daemon adds no signature, copy, hash or check over them. An unresolvable input → fail closed ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).
- **D-009-12 — The answering device is the resolution's record.** The resolve request carries no approver: the resolution records the answering device's id, taken from the connection the answer arrived on — the machine's own screen or a linked device's channel — and the resolution event carries it, so every other device showing the card reads `Answered on <device>`. Every check's Cedar principal is the machine's owning user (CP-009-9). A pending request is raised to the session and answered on any of the person's devices, the first answer settling it; notification transport for approval prompts stays out of scope per §Non-Goals. The renderer never populates an identity of any kind.
- **D-009-13 — Run-blocking seam shape.** Provider-registration directionality mirrors shipped CP-002-8 (`RunSetupGate`): Plan-009 exposes `registerApprovalOutcomeListener` + `cancelPendingForRun`; Plan-002's engine registers and drives run-state transitions — Plan-009 never mutates run state. `onBlocking` fires after the durable commit of the pending request; `onResolved` fires exactly once when it settles (approved / rejected); a rejected outcome continues the run with the action refused. A request never settles on elapsed time, so the seam has no time-based arm.
- **D-009-14 — A request a person answers has no deadline and no sweep.** Nothing settles such a request but the person's answer, the cancellation that rides the end of the run holding it, or a move of the permission level to one that never asks; there is no lazy staleness check on read and no periodic sweep, because there is no deadline for either to notice. Cancellation events carry `actor: null` (system actor, node-emitter convention).
- **D-009-15 — Evaluation inputs are derived, never duplicated.** No dedicated trust store, no machine trust and no tool-server trust: a machine and a tool server carry no trust level, because trust is per project. The Cedar principal ← the machine's owning user, recorded when it registers; working-folder roots ← `run_execution_contexts` joined to `workspaces.fs_root` / `worktrees.fs_root` (CP-009-8); project trust ← the project's attachment, which trusts it for both providers; an unresolvable input → strict per-request ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).
- **D-009-16 — Renderer approval posture: approval rules are allow or block, and one record renders at a time.** `rememberedScope.sense` is schema-refined to agree with the decision — `approved` mints `allow`, `rejected` mints `block` — and a `block` is accepted only on a `network_access` ask, whose decline offers `Block <host> this session` with the project on the same arrow; a command's and a file's decline record nothing, and deny-by-default remains Cedar's job. The card renders one canonical record at a time with its own actions (I-009-17); there is no grouping and no group-approve, because one click fanned into N mutations breaks AC-1's explicit-approval semantics.
- **D-009-17 — `PermissionCheckResponse.reason` is a 5-value enum** (`policy_allow | remembered_rule | approved | pending_approval | denied`): `policy_allow` = a Cedar permit or a designed answer's allow (T2.13), with no human approval artifact; `remembered_rule` = the session's own answers carry an allow on this subject that the daemon answers for a provider with no verb of its own (a Codex session allow after a restart); `approved` = a recorded approved resolution covers the exact request, or the Codex ask for exactly the command that resolution edited; `pending_approval` = the request is created/open (`allowed: false`, `approvalRequestId` present); `denied` = Cedar forbid, a designed refusal (T2.13), a rejected resolution, a host the session blocked on Codex, which has no session block of its own, or fail-closed refusal (the typed 503 additionally surfaces on fail-closed paths so audit distinguishes them). Invariants: `allowed === (reason ∈ {policy_allow, remembered_rule, approved})`; the `policy_allow`/`approved` split preserves the audit distinction between machine permit and human grant.
- **D-009-18 — No wire preflight; the in-process `PermissionCheckService.check()` is the composed gate.** Evaluate → on an ask-policy outcome create the request, persisting and emitting `approval.requested`, notify the run-blocking seam → return `pending_approval` with its id. The composition is [Spec-010 §Interfaces And Contracts](../specs/010-approvals-permissions-and-trust-boundaries.md#interfaces-and-contracts)'s enforcement seam; splitting evaluate-from-create at a wire boundary would reintroduce the TOCTOU window.

### Phase 2 — Daemon policy + approval services (Cedar gate, persistence, events, seams)

**Goal.** The `policy/` + `approvals/` service layer: Cedar policy evaluation over the rules compiled into the service for the app's own tools, the daemon's designed answers to provider asks in plain code, the composed in-process permission gate, approval create/resolve/cancel with events-canonical durability, handing each rule to its provider with the daemon's own answers where Codex has no verb, the `approval_flow` emission seam, and the run-blocking seam toward Plan-002. It also carries the T2.8 permission-ask surface, the T2.9 execution-posture layer, T2.10 posture-as-authorization + callback-tool governance, the T2.11 ADR-012 benchmark, the T2.12 session-terminal guard, and the T2.13 designed answers.

## Rollback Or Fallback

- Withhold the answers that make a rule and fall back to `request_only` approvals everywhere if rule handover, revocation or rebuild behavior regresses — `provider-rule-service.ts` is the one place a rule reaches a provider, so it is removable without touching the permission gate, and `request_only` is the schema default (omitting `rememberedScope` is always valid).
- The run-blocking seam is deregistrable without touching Plan-002's engine (zero-listener operation is a tested no-op).

## Risks And Blockers

- Provider-native permission semantics may drift unless normalization is enforced before approval records are written — mitigated by the schema-validated `requestCreate` boundary now and the CP-009-5 normalizer at driver-integration time
- The level's boundary can be over-broadened unless the working-folder roots stay explicit in the subject the card shows — mitigated by D-009-15 derived inputs + the strict per-request fallback ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior))
- `@cedar-policy/cedar-wasm` is the evaluator (4.13.0 pin) — engine-version drift surfaces in T2.1/T2.2 fixtures, and a Cedar upgrade ships in an app update with the rules checked against it (D-009-9)
