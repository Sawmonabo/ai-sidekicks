## Goal

Implement versioned workflow definitions and durable workflow execution for the full V1 engine — four phase types, four gate types, parallel phases with named pools, and append-only hash-chained approval history — reusing existing session, run, approval, artifact, and recovery primitives.

## Scope

Workflow definition persistence (content-hashed, immutable versions), workflow run state, phase execution for all four V1 phase types (`single-agent`, `multi-agent`, `automated`, `human`), all four gate types, parallel phase execution with `ParallelJoinPolicy`, memory-gated admission, workflow-level gate resolution with per-run hash chain, OWN-only channel linkage, replay-deterministic projection rebuild, and the chat-invoked start surfaces with per-start authorization ([Spec-015 §Chat-Invoked Start and Start Authorization](../specs/015-workflow-authoring-and-execution.md#chat-invoked-start-and-start-authorization), ADR-027).

## Non-Goals

- Marketplace or cross-machine workflow distribution. The `shared` scope tier is node-local reuse breadth, not distribution — a `shared` definition never leaves the daemon that stores it. Cross-machine portability at V1 is the operator-moved file form of [Spec-015 §Definition file form — export and import (C-17)](../specs/015-workflow-authoring-and-execution.md#definition-file-form--export-and-import-c-17), not a service.
- External workflow-engine integration
- Workflow editor polish beyond V1 ambition
- BIND channel ownership (V1.1 criterion-gated per ADR-015)
- Cross-node workflow dispatch (Spec-022 V1.1)
- Cross-run campaign memory and the durable wake-coalescing delivery substrate (V1.1 criterion-gated — the three criteria are stated once in [Spec-015 §Non-Goals](../specs/015-workflow-authoring-and-execution.md#non-goals) and not restated here). This plan builds only the in-run fold: the park's provider-account attention key of T2.5 and its `park_attention_key` projection column, which crosses no aggregate boundary. No task here opens a per-watcher generation record, a claim / queue / deliver lifecycle, or any cross-run durable row.

## Data And Storage Changes

- **The document is node-shaped, and its bytes are the hash preimage.** A workflow definition is one JSON document — the `WorkflowDocument` type this plan adds to `packages/contracts/src/workflow/` — whose canonical bytes are the RFC 8785 canonicalization of its hashed field list, BLAKE3'd ([Spec-015 §State And Data Implications](../specs/015-workflow-authoring-and-execution.md#state-and-data-implications)). It carries its schema version, its name and an optional description, exactly one `trigger` node, the rest of the graph as `nodes`, and `edges` each naming a source node and handle and a target node and handle ([Spec-015 §Graph model — nodes, ports, and edges (SA-32)](../specs/015-workflow-authoring-and-execution.md#graph-model--nodes-ports-and-edges-sa-32)). Two sections sit **outside** the hashed body: `layout` — a position per node, an optional viewport and the sticky notes — and `pinData`, an item array per node id. A node carries its id, its kind, the kind version written at insert, its display name, its sibling order, its params, and optionally whether it is disabled, its notes, its error disposition, its retry bounds, whether it executes once over the whole input, and whether it always outputs data. The document holds **no settings block**: what a failure does is set on the node that failed, how long step data is kept and how long a run may work are the two controls on the console's Runtime settings page over the machine-local settings surface ([Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior)), and the clock a schedule reads is a param on the schedule trigger itself.
- **A node is the authored unit; a phase is the run-time one, and the run-time vocabulary is unchanged.** The definition/execution separation stands as [Spec-015 §Interfaces And Contracts](../specs/015-workflow-authoring-and-execution.md#interfaces-and-contracts) states it: `WorkflowPhaseId` identifies a phase in the definition and `PhaseRunId` one execution of it, derived from the workflow run, the phase and the attempt number. One step record exists per node attempt, keyed by the run, the node and the attempt, and it is a projection over the events the run, approval and form pipelines already emit ([Spec-015 §Execution semantics](../specs/015-workflow-authoring-and-execution.md#execution-semantics), [Spec-015 §Truth vs projection vs ephemeral (SA-25)](../specs/015-workflow-authoring-and-execution.md#truth-vs-projection-vs-ephemeral-sa-25)). The four phase kinds are nodes like any other and compile down **at run time, not at save time**, their executors calling the existing run-admission, orchestration, approval and form paths when the node runs ([Spec-015 §Implementation Notes](../specs/015-workflow-authoring-and-execution.md#implementation-notes)); those attempts are what the `workflow_phase_states` rows, the `phase_outputs` rows and the `workflow_gate_resolutions` chain record, so `PhaseState`, `WorkflowPhaseId`, the `workflow.phase_*` events and the phase DDL all stay exactly as they are. The trigger node never enters the phase sequence, never receives a phase run id and never produces a phase-state row ([Spec-015 §Graph model — nodes, ports, and edges (SA-32)](../specs/015-workflow-authoring-and-execution.md#graph-model--nodes-ports-and-edges-sa-32)).
- Add the workflow schema per [Local SQLite Schema §Workflow Tables](../architecture/schemas/local-sqlite-schema.md#workflow-tables-plan-015) (SA-24) — thirteen tables. Nine are the engine's: `workflow_definitions`, `workflow_versions`, `workflow_runs`, `workflow_phase_states`, `phase_outputs`, `workflow_gate_resolutions`, `parallel_join_state`, `workflow_channels`, `human_phase_form_state`. `workflow_definitions` and `workflow_versions` carry the document body as the hash preimage with a `layout_json` column beside it, because layout is outside the hash ([Spec-015 §Canvas layout is not definition bytes (SA-35)](../specs/015-workflow-authoring-and-execution.md#canvas-layout-is-not-definition-bytes-sa-35)). Four are added by the builder, the trigger surface and the runs surface:

| Table | Holds |
| --- | --- |
| `workflow_steps` | One row per step attempt: run id, node id, attempt, execution index, the source array, status, timings, the three payload references, cost, error. |
| `workflow_triggers` | One row per armed trigger: workflow id, node id, kind, config hash, next fire, last fire, whether it is enabled. |
| `workflow_webhook_tokens` | One row per workflow that has a webhook trigger: the token hash, when it was created, when it was last used. |
| `workflow_node_state` | The per-(workflow, node) key-value store holding trigger cursor state, so no mutable field lives on the document. |

- **A step's payloads are inline while they are small.** Its input, output and log sit on the step row under a 64 KiB cap; above the cap each becomes an artifact through the Plan-012 ingest pipeline and the row keeps the reference. One read serves either, and the panel that shows a payload says which of the two it is reading — so a run row stays small and a step's input and output stay addressable from a message.
- Source-of-truth hierarchy (SA-25): `session_events` remains canonical; `workflow_definitions`, `workflow_versions`, `phase_outputs` and `workflow_gate_resolutions` are immutable truth; `workflow_runs`, `workflow_phase_states`, `workflow_steps`, `parallel_join_state` and `workflow_channels` are projections rebuildable via Plan-013 `ProjectionRebuild`. The per-step record is a projection over events the run, approval and form pipelines already emit, which is what keeps a run's step history a function of the log rather than a second account of it. Three of the four added tables are **mutable truth** rather than projections: the armed-trigger rows, the webhook token rows and the per-node key-value store are facts about what this machine is armed to do next, which no event history reconstructs — the durable row is the truth and the in-process timer is a cache re-armed from it after a restart ([Spec-015 §Entry node and the V1 trigger surface (SA-37)](../specs/015-workflow-authoring-and-execution.md#entry-node-and-the-v1-trigger-surface-sa-37)).
- **A form draft is daemon-held.** `human_phase_form_state` carries the drafts of the human form kind and is written through `workflow.humanFormDraftSave`, so a half-filled form survives a reload rather than living in the window; typed unsent text is never put in window storage. Each autosave bumps the row's own draft version, the optimistic-concurrency token the next write checks against, and the row is keyed one draft per phase run and person.
- `workflow_gate_resolutions` carries a per-run BLAKE3 hash chain anchored to `session_events` via a dual-anchor payload (`gate_resolution_id` + `row_hash`) on the `workflow.gate_resolved` event (SA-26). Dual-hash: BLAKE3 for daemon-internal identity, SHA-256 reserved for Plan-012 artifact content (SA-27).
- **Workflow-definition scope is three-valued:** `session` | `project` | `shared`. `session` scopes a definition to its authoring session, `project` spans the sessions of one project, and `shared` is the cross-project tier — authored once and reusable by any project on the same daemon, resolved out of the same local definition store with no additional table and no sync path. Scope identity is carried by a `scope_ref` column alongside `scope`, in the shape [Spec-025 §Unified Inventory](../specs/025-mcp-server-configuration-and-governance.md#unified-inventory) already uses for scope-qualified bindings — the authoring session id at `session`, the canonical repository root (`repo_mounts.canonical_root`) at `project`, the empty string at `shared` — and the dedupe key is `(scope, scope_ref, content_hash)`, so a definition stored once at a scope is one row regardless of which session submitted it. A `scope`-only widening does not work: `project` would name no project, and a `(session_id, content_hash)` key would partition `shared` definitions by authoring session, so two sessions storing the same shared definition would produce two rows resolution cannot reconcile. `shared` widens **visibility and reuse breadth only**: it is not distribution, not a marketplace and not cross-machine sync — a `shared` definition never leaves the daemon that stores it, and [Spec-015 §Non-Goals](../specs/015-workflow-authoring-and-execution.md#non-goals) continues to exclude marketplace and global-library distribution. The `workflow_definitions.scope` column carries the domain (`CHECK(scope IN ('session','project','shared'))`) while `session_id` keeps recording the authoring session at every scope, so provenance survives the widening.
- **Copy-on-write provenance column:** `workflow_definitions.parent_content_hash`, nullable, recording the content hash of the `shared` definition a row was branched from when an author edited a shared definition (T1.7, [Spec-015 §Definition scope in the builder (SA-36)](../specs/015-workflow-authoring-and-execution.md#definition-scope-in-the-builder-sa-36)). It is provenance and **not** part of the hashed body, so a branched definition and a from-scratch definition with identical bodies still carry the same `content_hash` and converge on the dedupe key — the intended behavior, since the two are the same definition. Editing a `shared` definition in place is forbidden by construction: definition rows are immutable and the table carries no updated-at column, so an in-place edit would append a version to the shared definition and silently repoint every project on the daemon that resolves it. No table is added by it.
- **`workflow_phase_states.phase_type` admits the four V1 phase types only:** `CHECK(phase_type IN ('single-agent','multi-agent','automated','human'))` per [Spec-015 §Phase-Type and Gate-Type Taxonomy](../specs/015-workflow-authoring-and-execution.md#phase-type-and-gate-type-taxonomy). Gate types live on the gate column, never here.
- **Admission reads the machine, and only its headroom fraction is configuration:** the SA-3 gate restated from [Spec-015 §Execution semantics](../specs/015-workflow-authoring-and-execution.md#execution-semantics) — capacity is `process.availableMemory()` re-read on every tick less a headroom fraction from local daemon configuration, the reservation a phase takes is seeded per phase type and then replaced by the observed resident size of that type's recent launches on this machine per provider, a ramp interval separates grants, and one phase is always admitted. There is no capacity constant, no phase-count ceiling and no slot pool, so nothing here is a number an operator calibrates. The observed sizes and the ramp state live in memory beside the reservations — ephemeral by the same rule (SA-25), re-learned rather than restored after a restart — and this plan's own admitter counts them, consuming no other plan's pool API and adding no dependency row.
- **Park-and-resume projection columns — four columns on `workflow_phase_states`, no new table.** `park_reason` (nullable, `CHECK(park_reason IN ('waiting-human','provider-usage-limited'))` — the closed union of [Spec-015 §Park integrity and cancellability (SA-42)](../specs/015-workflow-authoring-and-execution.md#park-integrity-and-cancellability-sa-42), in the DDL-CHECK-versus-contract lockstep I-015-12 enforces), `park_cause` (nullable text, the engine-authored sentence, bounded at 8 KiB and truncated at a UTF-8 code-point boundary with a visible marker — a durable operator-facing string with no bound is an unbounded write on the projection tier), `auto_resume_at` (nullable UTC instant — the durable schedule of [Spec-015 §Provider-limit pacing and durable resumption (SA-40)](../specs/015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-40), a durable value rather than an in-memory timeout, so a parked phase resumes itself across a daemon restart) and `park_attention_key` (nullable text — provider plus account identity plus credential generation, the outage-scoped fold key; a correlation for presentation that gates no start, resume, retry or schedule fire). Per-phase rather than per-run, and the placement is load-bearing: under [Spec-015 §Graph model — nodes, ports, and edges (SA-32)](../specs/015-workflow-authoring-and-execution.md#graph-model--nodes-ports-and-edges-sa-32) two parallel branches of one run may park concurrently against different provider accounts with different reset boundaries, and a run-level schedule or fold key could hold only one of them — delaying or stranding the sibling and folding two distinct outages into one record. The table is already a projection, and all four values ride the suspension event that produced them, so the byte-equal `ProjectionRebuild` of I-015-10 holds with no exception and no schedule or fold key survives a rebuild the log does not contain. Two partial indexes back the boot sweep and the fold read: one on `workflow_phase_states(auto_resume_at)` where non-null, one on `workflow_phase_states(park_attention_key)` where non-null — both narrow by construction, and both stay the bare non-null form because the per-row CHECK already confines the columns to `state = 'suspended'`. That CHECK — `state = 'suspended' OR (auto_resume_at IS NULL AND park_attention_key IS NULL)` — makes the **phase-exit half** of SA-40's clear-on-exit rule structural rather than a code convention: SQLite enforces CHECKs per statement, so the same UPDATE that moves a phase out of `suspended` must null both live columns. The run-cancel half cannot be DDL-enforced, since run status lives in `workflow_runs` and a SQLite CHECK cannot cross tables, so SA-42's cancel clears the two live columns in the cancel's own unit of work — code-enforced and failure-injection-tested at T5.11 — while the park **record** columns carry no such coupling by design: `park_reason` and `park_cause` survive resume and cancellation untouched, so liveness is read from run status plus phase `state`, never from the presence of a park reason.
- **The engine event record is not a SQLite table (SA-43).** It is newline-delimited JSON on the Plan-018-owned bounded-retention diagnostic tier, so it adds no table, no write to the Plan-013 writer worker and no write amplification to the canonical event path — the reason the always-on posture is affordable at all. Plan-015 writes records and correlates them by `workflowRunId` / `phaseRunId` / `attemptNumber` / a monotonic per-run sequence; Plan-018 owns the bucket, its TTL and its shred-path membership (CP-015-9).
- See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) for column definitions, index rationale, and write-amplification estimates.

- Event payload schemas evolve additive-MINOR per [ADR-018](../decisions/018-cross-version-compatibility.md); the `row_hash` + `gate_resolution_id` fields on `workflow.gate_resolved` are such an addition, per the SA-26 dual-anchor scheme in §Data And Storage Changes above. The per-phase projection `WorkflowRunReadResponse` carries gains the four park members as additive-optional and **live-scoped** — emitted only while the phase is parked, which makes `parkReason` presence the wire's park discriminator and is why the `PhaseState.state` union is deliberately not widened with a sixth arm: widening it would move the I-015-12 lockstep pin and force a DDL, contract and taxonomy edit to express what an optional member already answers.

The refusal points the builder and the trigger surface add — a trigger that cannot arm, a webhook token that does not match, a Code node over its memory or time budget, an expression evaluation over its budget, and an import whose schema version is unknown — each land with a registered code in the same change as the refusal, and none ships unregistered. The extension covering the points that still carry no code is owed on that contract document and is **not taken by this plan** (the file is outside this plan's write scope); until it lands, no phase may mint an unregistered code, which is the constraint [Spec-015 §Loud-errors discipline (C-12)](../specs/015-workflow-authoring-and-execution.md#loud-errors-discipline-c-12) already imposes.
- **Chat start and the agent tools add no wire method.** The `/workflow` command root and the composer affordance are client-surface sugar resolving to the operations above (the [Spec-014 §Turn Policies](../specs/014-multi-agent-channels-and-orchestration.md#turn-policies) `@mention` precedent), and the sixteen workflow callback tools are `SessionCallbackTool`s rather than JSON-RPC methods (CP-015-7). `WorkflowRunStartRequest` carries an additive-optional `channelId` per [ADR-018](../decisions/018-cross-version-compatibility.md) — provenance and progress-surface binding, not an input to the role adjudication, but daemon-validated as a channel of the starting session before it binds a surface, so a `channelId` outside that session refuses. Each tool is adjudicated by a **named Cedar action, never by tool name** ([Spec-010 §Interfaces And Contracts](../specs/010-approvals-permissions-and-trust-boundaries.md#interfaces-and-contracts) registers all four and [Spec-015 §Chat-Invoked Start and Start Authorization](../specs/015-workflow-authoring-and-execution.md#chat-invoked-start-and-start-authorization) names them per tool): the read tools are gated on the session itself; authoring, updating, setting a schedule, enabling or disabling a workflow and posting a run's results take `Action::"workflow::author"`; running a workflow or executing one of its nodes takes `Action::"workflow::start"`; cancelling takes `Action::"workflow::cancel"` and resuming takes `Action::"workflow::resume"`. This plan consumes those adjudications through `PermissionCheckService` (CP-015-8, CP-015-11) and authors no Cedar schema entry.

## Implementation Steps

- Contracts: See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed schemas this plan consumes.

1. Define workflow-definition, version, phase-state, gate, and definition-read contracts in shared packages.
   - Full type hierarchy: `WorkflowDefinition`, `WorkflowVersion`, `WorkflowDocument` with its `WorkflowNode`, `WorkflowEdge` and `WorkflowLayout` members, `WorkflowRun`, `WorkflowStep`, `WorkflowPhaseRun`, `PhaseOutput`, `WorkflowGateResolution`, `ParallelJoinState`.
   - All 4 gate types: `auto-continue`, `quality-checks`, `human-approval`, `done`.
   - Entity separation: `WorkflowPhaseId` (the logical phase in the definition) vs `PhaseRunId` (one specific execution instance, which also anchors the OWN channel 1:1 per SA-6). `PhaseRunId` is **derived, never randomly minted**: every bit is a function of `BLAKE3(workflowRunId || nodeId || attemptNumber)` per [Spec-015 §Deterministic identity (SA-21)](../specs/015-workflow-authoring-and-execution.md#deterministic-identity-sa-21). It is therefore **not a ULID** — a ULID's leading 48 bits are a millisecond timestamp, which that preimage cannot produce, so the "ULID" wording asserted determinism and a clock at once. Treat it as a derived opaque identifier: the digest's text rendering is not yet settled and is carried as an entry in [Spec-015 §Open Questions](../specs/015-workflow-authoring-and-execution.md#open-questions), so build the derivation behind a single helper (T1.1) that every call site goes through, and do not encode a rendering assumption anywhere else. The storage column is `TEXT` under every candidate rendering, so no schema work waits on the ruling.

3. Implement phase execution for all four V1 phase types:

## Implementation Phase Sequence

The five numeric phases map 1:1 onto `## Rollout Order`, absorbing `## Implementation Steps` and `## Target Areas`; each phase carries a reviewer-checkable `**Precondition:**` line plus the machine-readable `preconditions:` block preflight consumes. Three explicit-label supplement phases — **2B, 5B, and 5C**, the Plan-007 Phase 2B / Plan-022 Phase 3B shape — carve the carrier-held and supplement-chained tasks out of their numeric homes, because a `precondition_box_checked` entry gates its **entire declaring phase** (there is no task-level leg), so a carrier box carried on a numeric phase would hold every other task in it. Supplements dispatch by explicit label only; the no-argument numeric walk resolves past them, so the numeric chain never waits on a supplement's box.

The `OWN-channel turn budget provider registered` box gates Phase 3 specifically, and Phases 2–5 each chain on the preceding phase so the walk cannot hop over it. The `ADR-026 ratified accepted` box rides Phases 1 and 5 — the two phases that own the five builder tasks — and the `ADR-027 ratified accepted` box rides Phase 5. Both are checked, so neither entry holds a phase; they stay in the block as satisfied gates, the shape every checked `precondition_box_checked` entry keeps. The two carrier boxes instead ride supplements, because their producers are **other plans' work with no sequenced landing date** and a full-phase hold of unknown duration is not acceptable breadth: the `Typed provider usage-limit signal registered` box rides **Phase 2B**, the supplement that owns exactly the two tasks (T2.5, T2.6) which read the Plan-004 carrier, and the `Engine-event diagnostic bucket registered` box rides **Phase 5C**, the supplement that owns exactly T5.13. Neither box holds T1.9, T5.11, or T5.12 — the contract-and-DDL surface is independent of both registrations, and cancellability and the repair (Phase 5B) are engine-internal, gated only on the phases whose seams they extend.

### What each layer proves

**Executor unit tests, one per node kind**, over an item fixture covering: the empty input, the single item, the many-item batch, the per-item expression re-evaluation, the item lineage the kind must emit, the failure path under each error disposition, and the redaction of any resolved secret. A branch kind additionally asserts the shape of its output array; the loop kind asserts its done-and-loop ordering and its run-index progression; the merge kind asserts each of its join modes.

**Engine tests**: traversal order under fan-out with explicit sibling order, the fan-in buffer, loop re-entry, item lineage across a branch and a merge, retry under the engine's clamps, the optional run cap, cooperative cancel, the waiting-and-resume cycle, the crash sweep leaving a `waiting` run alone, and a partial run reusing clean step data. The memory gate carries its own: a machine with no room still admits one step, a second start waits out the ramp interval, a step waiting on a person or parked on a spent provider account releases its reservation, and a kind's reservation moves from its seeded constant to what its recent runs on this machine really took.

**Expression tests**: each binding, per-item evaluation, the evaluation budget and its abort, redaction of resolved secrets, and the two lineage failure modes with the exact guidance each gives.

**Code node tests**: on the quick tier, the memory limit, the interrupt limit, no host access, and log capture into the step's log. On the full tier, the declared packages fetched before the program runs and cached in a directory the run may write, the step launched at the run's execution posture, and a sandbox that cannot start at a `sandboxed` posture refusing the step rather than running it unprotected.

**Canvas tests on the browser tier**: the controlled round trip, where a change callback produces exactly the document mutation and nothing else; a refusal during the drag for each refused shape; a drop from the palette landing at the pointer; an edge-drop opening the filtered palette; undo and redo across a coalesced drag; copy and paste re-iding nodes; handle re-registration after a param write that changes the port set; and the announcer receiving one message per structural change. These run headless and never reveal a window.

**Builder store tests**: the history cap, the dirty lattice per rule, the validation strip's contents, save-then-run against a dirty draft, and layout writes never touching the hashed body.

**Round-trip tests**: export then import reproducing the same bytes and the same content hash; a document with no layout laying out identically twice; a copy-paste fragment parsing back into the same nodes.

**Proportion**: a build proves the surface scales by stepping the console's text size — the reading matter and every box that carries it grow in one proportion, the icon strokes and the corner radii stay as drawn, and the canvas keeps its own coordinate space, where the node box, the handles, the edge geometry and the grid step are canvas units the zoom scales.

**Surface sweeps**: every screen state below is reachable, every rule with a visible consequence is observable on the screen, and every node kind in the catalog is in the palette.

### Two workflows every scenario is built from

**Morning PR digest** — twelve nodes with one branch, one merge, one loop, one agent node carrying a capability edge, and one approval:

1. `Every weekday 8:30 AM` — a schedule trigger, cron `0 30 8 * * 1-5`, timezone `America/New_York`.
2. `List open PRs` — an HTTP request, one item per pull request.
3. `Needs review?` — an If, true when the review decision is not approved.
4. `For each PR` — a loop over items, batch 1, on the true branch; outputs done and loop.
5. `Read the diff` — a repo diff on the loop branch, set to continue on its error output, so a diff it cannot read leaves by the error branch back into `For each PR` and the loop takes the next pull request.
6. `Review agent` — an `agent.run` node, the reviewer agent on a Codex account, its prompt referencing the item's title and diff.
7. `Repo search` — an MCP tool wired by a capability edge into node 6's tool input.
8. `Skipped PRs` — a set-variables node on the false branch.
9. `Merge digest` — a merge in append mode, input 1 from the loop's done output and input 2 from node 8.
10. `Approve the post` — an approval node, outputs approved and rejected.
11. `Write summary` — a write-summary node on the approved branch.
12. `Save as artifact` — a save-as-artifact node on the rejected branch.

**Nightly tests** — five nodes, the failure example: `Every night 2:00 AM` (a schedule trigger) → `Run the suite` (a shell command running the test script) → `Passed?` (an If) → `Write summary` or `Stop with error`.

## Rollback Or Fallback

- If parallel execution or gate-chain writer regresses, disable parallel blocks and restrict to sequential `single-agent` + `automated` — the engine still satisfies C-1…C-7 for V1 partial rollout.
- If the durable auto-resume schedule misbehaves, the fallback is the **unscheduled park**, which is already a first-class shipped state: stop arming `auto_resume_at` and every parked run stays visible, cancellable, and manually resumable with its stated cause. Recognition, the park itself, and cancellability are independent of the scheduler, so this degrades pacing without losing the park. The four columns stay in place — a nullable column that nothing writes costs nothing and avoids a down-migration.
- If the engine event record proves too costly, the fallback is **bounded recording, never no recording**: shed the high-frequency record classes first — ready-set ticks and gate evaluations, the classes that dominate volume — while retaining parks, schedule arming and fires, refusals, and the dispatch-intent/outcome pairs, so the records that exist precisely for the unreproducible moments survive the cost trim. The no-op writer is reserved for the one case T5.13 already requires it: bucket unavailability, where failing a run over a diagnostic sink would invert the record's non-canonical rank (I-015-22). Neither arm is a disable path — I-015-22 admits no flag that turns the record off, and a cost-motivated off switch would recreate exactly the there-was-no-second-chance blindness the always-on posture exists to avoid.

## Risks And Blockers

- Write amplification under pathological `progressed` heartbeat floods. **Named calibration criterion:** the nightly load category (Phase 4, T4.2) records per-workflow write volume against the [Local SQLite Schema §Workflow Tables](../architecture/schemas/local-sqlite-schema.md#workflow-tables-plan-015) estimate of ~42 KB / 110 writes per 10-phase workflow; a sustained nightly reading above **2× that estimate** is the trigger to add an executor rate-limit, and until it fires no rate-limit ships. The trigger is a threshold on an already-collected measurement, not a scheduled revisit.
- Per-run gate-chain verification cost scales linearly (~1 ms/row) — acceptable for operator-triggered audit; not in the hot path (T5.2 asserts the linearity and the out-of-hot-path placement).
- **How `uv` reaches a person's machine is not settled, and the Python leg of the full tier waits on it.** `bun` publishes its own binary on npm at 1.4.2, so the daemon carries it the way it carries any other pinned tool; the npm package named `uv` is an unrelated UTF-8 data validator, so npm is not the route for it (both read from the registry 2026-09-21). The candidates are a bundled binary, the platform's own package manager, or a first-run download, and T2.2 cannot ship its Python arm until one is chosen. The JavaScript and TypeScript arm is unblocked either way.
- **The Claude-leg sandbox wrapper is an early research preview.** `@anthropic-ai/sandbox-runtime` 0.0.77 says its interfaces and configuration formats may still change. The exposure is bounded by how it is used — a command wrapper and a profile, resolved through the Plan-010 posture surface rather than linked into the daemon — so a breaking change costs an argv-and-profile fix, and the Codex leg is a separate wrapper that would not break with it.
- **The boundary around the full tier is measured on macOS only.** Measured 2026-09-21 on an Apple-silicon Mac: a TypeScript program naming its package in its import line and a Python program naming its packages in its own inline metadata block each ran with their packages inside `codex sandbox` on the workspace profile, with home-directory writes and the network blocked, and the sandbox cost about 0.02 s per run. Linux and native Windows are unmeasured; on native Windows the Claude leg has no sandbox at all, so a `sandboxed` posture there refuses rather than degrades ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)).
- Non-determinism in replay if driver adapters leak wall-clock or random seed state — Plan-013 runtime-binding resume is the guard, and T5.1's replay-determinism battery (SA-31, asserting no `DeterminismViolationError` and a `deepEqual` final state) is the regression.
- **Error vocabulary gap carried, not closed.** `error-contracts.md §Workflow` defines **ten** codes for a surface with at least **twenty-two** refusal points (enumerated identically in `## API And Transport Changes`; the SA-41 repair path contributes three: a re-pin against a run that is not parked, one requested while any of the run's attempts is still in flight (the resuming phase continuing one rather than entering fresh, or a parked parallel sibling holding one — SA-41's run-wide boundary), and one whose target version cannot account for the phases the run already completed — the omitted phase id and the unreachable topology being one refusal point, since SA-41 states they are the same failure — and the SA-45 operator path contributes three: a Cedar-denied operator control, a cancel of a run that already reached `succeeded` or `failed`, and a resume of a run that is not parked). **The park and pacing surface adds none of its own** — SA-42 makes a parked run cancellable without precondition, so cancellation has no refusal to name — and that claim is scoped to the pacing rules, not to the operator surface that reaches them: the three SA-45 points are the operator surface's, minted when it landed. That file is outside this plan's write scope, so the extension is owed there and named in `## API And Transport Changes`; no Plan-015 task mints a code. Two slices are typed already: the SA-41 repair codes (`workflow.repair_not_parked`, `workflow.repair_attempt_in_flight`, `workflow.repair_version_unaccountable`) and the SA-45 operator-control codes (`workflow.control_denied`, `workflow.run_not_cancellable`, `workflow.resume_not_parked`) — **seven of the twenty-two** points carry codes, `workflow.start_denied` included — so T5.12 and T5.14 both ship typed with no residual dependency on the extension. The remaining **fifteen** refusal points cannot ship typed until it lands. Tracked as a blocker on Phases 2, 4, and 5 rather than as a task.
- **The park's typed carrier now exists, and this plan still will not fake one (CP-015-10).** Every rule in [Spec-015 §Provider-limit pacing and durable resumption (SA-40)](../specs/015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-40) hangs off a driver signal Plan-004 ships (`I-004-6`, T3.16), and C-19 forbids the stand-in it replaced — matching provider message text. The pitfall survives the carrier's arrival rather than retiring with it, because the temptation changes shape rather than disappearing: the signal is deliberately **silent** on providers and shapes it cannot name, so a driver that observes no usage limit emits nothing, and "nothing" must be read as _not known to be limited_, never as _known not to be limited_. Widening recognition to cover that silence — by message text, exit code, or bare HTTP status — is the same failure the invariant was written against, and it fails the same way: a matcher that silently stops matching converts a park back into a burned ladder with no signal that anything changed.
- **The park's operator control surface must mint its operations and its event together.** [Spec-015 §Park integrity and cancellability (SA-42)](../specs/015-workflow-authoring-and-execution.md#park-integrity-and-cancellability-sa-42) states cancellability and repair as engine state-machine rules, and the surface that reaches them is T5.14: the two operations and `workflow.cancelled` mint **together**, with T5.15 carrying the client verbs. Split apart, a cancelled run's status and its cleared live park columns would survive only in a projection a rebuild would overwrite instead of being a function of the log (SA-25, I-015-25). The surface costs a wire-registry entry pair and an event type; the alternative costs correctness.
- **The durable park write must not ride the provider event delivery path (implementation constraint on T2.5 / T2.6).** The refusal that triggers a park arrives on the driver's event stream, and the natural spelling — performing the park's durable write and the schedule's arming inline on that delivery — deadlocks: the writing path ends up waiting on a response that can only arrive through the stream it is itself blocking. The surveyed reference runtime (2026-08-12 parity survey) hit this shape twice, in independent places, and settled on the same rule both times — detach synchronously on the delivery path, then do the durable park and schedule writes off it. T2.5 and T2.6 build to that rule, and the regression is an ordering test: a park must complete while the driver's stream is still being consumed. The split leaves a crash interval — the daemon dying after the handler detaches but before the off-path park write commits — and its closure is the refusal's **reproducibility**, not a durable inbox: a spent account keeps refusing, so the restart's ordinary mid-phase resume (T2.1) re-dispatches the same attempt and either receives a fresh typed refusal and parks then — no attempt consumed, no ladder burned, per the park path's own rules — or, where the account reset during the downtime, simply proceeds, the park never having been needed. T2.5's crash-injection test pins that convergence, so SA-40's durability never rests on an in-memory signal surviving a crash.
