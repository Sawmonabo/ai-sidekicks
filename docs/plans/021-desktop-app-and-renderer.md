## Goal

Ship the Spec-021 Electron desktop app and React + Vite renderer as a three-process system (main / renderer / the background service main supervises) that lands the renderer-untrusted trust stance, the narrow typed preload bridge, the full Electron Fuses + ASAR-integrity + CSP hardening baseline, main's registry of windows in which every window is alike and none is the main one, supervision of a service spawned detached so that quitting the app leaves the service and every run and shell running, `electron-updater` 6.8.9 auto-update with its stock GitHub provider, control-plane calls forwarded to the background service, which holds every credential, code signing on macOS / Windows / Linux, and crash reports that Crashpad writes to this machine only and the service turns into stripped reports. The desktop app carries no WebAuthn: passkeys are used only outside it. The renderer ships the layout chrome, router, and composer, and **mounts** the V1 Signature Feature views that their owning plans author in those plans' own features — this plan creates a mount point and a route, never a view body. It is the desktop surface, not the authority. **The console** — the Meridian surface set [Spec-021 §Console Design (Meridian)](../specs/021-desktop-app-and-renderer.md#console-design-meridian) fixes (the icon rail, the sessions list, the session views a window holds side by side, the pane-kind set with any side pane movable into a window of its own, and the fixture scenarios the app starts on with `--fixture <scenario>`) — is registered by this plan at §Target Areas Renderer and built as the supplement Phase 1C inside that spec envelope; Phase 6 **adopts** it by mounting and moving, never by re-authoring (T-021r-6-1 EXTEND). Preview and the detached panes are built in Phase 9.

## Scope

- `apps/desktop/` — **new app package.** The Electron main process (`apps/desktop/src/main/`), the preload bridge (`apps/desktop/src/preload/`), and the React + Vite renderer (`apps/desktop/src/renderer/src/`).
- Electron runtime target: **44.x** (`44.1.0`, pinned exact) per [ADR-016 §Decision](../decisions/016-electron-desktop-app.md#decision). Electron 41 reached end-of-support on 2026-08-25 with the 44.0.0 release, and the detached-`WebContentsView` bounds fix the console's `browser` pane kind depends on (electron/electron PR #53031) reached 42 / 43 / 44 only, so V1 admits 44 alone. Every release on a supported branch carries the fixes for the Q1 2026 CVE batch (CVE-2026-34769, -34770, -34771, -34772, -34774, -34764, -34776, fixed 2026-04-02 in 39.8.5 / 40.8.5 / 41.1.0 per the [Electron GHSA feed](https://github.com/electron/electron/security/advisories)). The desktop app's `package.json` pin moves at T-021p-1B-4, together with the `better-sqlite3` 13.0.3 move [ADR-022 §Decision](../decisions/022-v1-toolchain-selection.md#decision) binds to it.
- Build toolchain: **`electron-vite`** (alex8088) v5.0.0 stable — Vite-powered main / preload / renderer build with HMR, source-code protection, and a single `electron.vite.config.ts`. Alternative considered + rejected in §Risks And Blockers.
- Packaging + auto-update: **`electron-builder`** 26.15.x + **`electron-updater`** 6.8.9 per [Spec-021 §Implementation Notes](../specs/021-desktop-app-and-renderer.md#implementation-notes) §Build And Packaging and §Auto-Updater. The packages are the macOS `.dmg` to install and `.zip` for updates (arm64 and x64), NSIS per user on Windows x64 and arm64, AppImage on Linux x64 and arm64, and `.deb` and `.rpm`, which add the project's signed apt or dnf repository, hosted on Cloudsmith's open-source plan, when installed. There is no Snap, no Flatpak, no MSI and no staged rollout. A `.deb` or `.rpm` install is the package manager's to update: it never runs the updater's own Debian or RPM installer, which would bypass the repository's signature.
- Renderer stack: React 19 + Vite 6 + TypeScript strict (per [ADR-016 §Success Criteria](../decisions/016-electron-desktop-app.md#success-criteria)).
- Preload bridge: single `window.desktopBridge` object via `contextBridge.exposeInMainWorld`; narrow typed capability surface (no `any`) per [Spec-021 §Preload Bridge Contract](../specs/021-desktop-app-and-renderer.md#preload-bridge-contract).
- Security hardening: every window a `BaseWindow` and every document it shows a `WebContentsView` created with the exact `webPreferences` set in [Spec-021 §Security Hardening Baseline](../specs/021-desktop-app-and-renderer.md#security-hardening-baseline); every release build packaged with the Electron Fuses Spec-021 declares + the ASAR Integrity Digest (new in Electron 41 via `@electron/asar` v4.1.0+); strict CSP per Spec-021.
- Service supervision: main never parents the background service, because a quit must leave the service, every run and every shell running. The service's detached start — its spawn, the per-user service `sidekicks daemon install` registers where a detached child does not outlive the app, and its native start on each platform — is [Plan-028](./028-remote-control.md) Phase 1's, and main's supervision rides it. Main reaches the service through its socket, handshakes with `daemon.hello`, watches it with `daemon.ping`, and brings a lost service back through that start on the 100 ms, 300 ms, 1 s, 3 s, 10 s backoff with the five-attempt ceiling of [Spec-021 §Implementation Notes](../specs/021-desktop-app-and-renderer.md#implementation-notes); a stop or restart that still finds the service running after its flush sends SIGTERM and, 2 s later, SIGKILL. On a Windows computer whose Claude Code and Codex live in WSL 2, supervision goes through the per-user task, which runs the service's Windows half, and that half starts and restarts the daemon inside the distribution.
- Auto-update: `electron-updater` as shipped, with its stock GitHub provider and nothing of the project's on top. It checks each download's SHA-512 against the update files `electron-builder` publishes, and the operating system's code signature decides the rest on macOS (Squirrel.Mac's designated requirement) and Windows (the installer's publisher, `verifyUpdateCodeSignature`). Main refuses a release whose version is not above the last one seen, which `updater-state.json` keeps, and `allowDowngrade` stays off. `autoDownload` and `autoInstallOnAppQuit` are off: a download starts on the person's press, is a blockmap delta where the platform has one (NSIS, the macOS zip once a previous update is cached, and AppImage), and Squirrel.Mac is handed an update only at `Restart to finish`. The app does not roll itself back; a bad release is fixed by the next one.
- Code signing: until the Apple Developer ID certificate exists ([BL-108](../backlog.md#bl-108-plan-022-windows--macos-signing-procurement-evidence)), every macOS build is signed with the project's own self-signed code-signing identity, held as a release secret, with one bundle identifier on every build, so every update meets the installed app's designated requirement and one-press update works; only notarization and the first-launch Gatekeeper prompt wait on the certificate, after which it is Developer ID Application + `xcrun notarytool`. The Windows installers are signed through SignPath Foundation's free open-source program, so Windows names `SignPath Foundation` as the publisher, and until that signing is in place (BL-108) Windows builds publish unsigned; if the project is not eligible, that goes back to the person and the distribution plan does not change silently. The project signs no Linux package itself: Cloudsmith's per-repository key signs each RPM on upload and the apt and dnf repository metadata, and a `.deb` is checked through apt's signed Release file. A release publishes its files and a checksum list.
- Crash reporting: while `Keep crash reports` is on, which is its default, Crashpad writes each crash to this machine only (`crashReporter.start({ uploadToServer: false })`); nothing is uploaded anywhere. The service turns each dump into a report on the machine — the process type, the app and service versions, the platform and the crashing thread's stack, file paths cut to their names and session ids replaced by stable hashes — symbolicates it there, deletes it with the diagnostic logs, and serves the kept reports through `daemon.crashList` to Remote Control and `sidekicks crash list`. The raw dump never leaves the machine.
- Deep-link: register the `sidekicks://` protocol handler on macOS, Windows and Linux; URL parsing happens in the main process, never in the renderer.
- E2E test harness: **Playwright `_electron`** namespace (marked experimental in the [Playwright class-electron docs](https://playwright.dev/docs/api/class-electron), but the only production-viable option; Spectron is archived).
- Monorepo placement: `apps/desktop/` as a workspace package, sibling to `packages/runtime-daemon/`, `packages/contracts/`, `packages/control-plane/` per the monorepo topology in [container-architecture.md](../architecture/container-architecture.md) §Client Delivery Sequence.

## Non-Goals

- **Pixel-level mockups and per-screen visual specifications.** [Spec-021 §Console Design (Meridian)](../specs/021-desktop-app-and-renderer.md#console-design-meridian) fixes the design language, the surface set, the pane and window model, the budgets, and — through [Spec-021 §Console Libraries](../specs/021-desktop-app-and-renderer.md#console-libraries) — the component-library and theme decisions; this plan registers the console's renderer folders and their adoption path (§Target Areas Renderer, T-021r-6-1 EXTEND) and carries its invariants (I-021-11, I-021-12), while the per-surface composition is the console's own code and fixture scenarios.
- **Daemon internals.** Owned by `daemon.md` and Spec-006 / Plan-006. This plan consumes Plan-006's daemon contract; it does not re-specify it.
- **PTY supervision from the main process.** Per [Plan-022 §Target Areas](./022-rust-pty-sidecar.md#target-areas), `PtyHostSelector` + `RustSidecarPtyHost` + `NodePtyHost` are owned by the **daemon** (`packages/runtime-daemon/src/pty/`). The main process never consumes the PtyHost contract directly. A Plan-021 edit wiring PTY supervision into the main process is a review rejection.
- **The CLI client.** The CLI's own surfaces are owned by a separate plan. Plan-021 is desktop-only.
- **The web client's and the phone apps' hosts.** They run this front end through their own implementations of the one bridge interface and are built in [Plan-028](./028-remote-control.md)'s frontend phase ([Spec-021 §Scope](../specs/021-desktop-app-and-renderer.md#scope)); this plan builds the desktop host.
- **Provider-driver protocols.** Owned by Spec-004.
- **Workflow authoring semantics.** Owned by the workflow-engine track — V1 feature 17 per ADR-015 (Spec-015 / Plan-015; the node-graph builder under ADR-026). The console mounts Plan-015's workflow screens under the Workflows destination — the runs list, a run's page and the builder — and authors none of their bodies; no workflow screen is a pane.
- **MSIX and MSI distribution.** V1 ships NSIS per user on Windows x64 and arm64. The MSI installer exists for an organization's deployment tools, which one user does not have, and `electron-updater` does not update it; MSIX, the Store's format, is not shipped either.
- **Reproducible builds.** Not claimed by V1 and no reproducible-build job, per [Spec-021 §Build And Packaging](../specs/021-desktop-app-and-renderer.md#build-and-packaging); neither `electron-builder` nor `electron-vite` guarantees bit-reproducibility.
- **Snap and Flatpak packaging.** Not shipped. Linux gets AppImage, and `.deb` and `.rpm` through the project's signed apt and dnf repository.
- **Reconciling `security-architecture.md` §Local Daemon Authentication.** Plan-021 consumes the renderer-untrusted stance as declared in [Spec-021 §Trust Stance](../specs/021-desktop-app-and-renderer.md#trust-stance), which `security-architecture.md` §Local Daemon Authentication states the same way.

Spec-021, which this plan is paired with, and the ADRs below underlie **both** the partial and the remainder. The four `**(Remainder only.)**` items below — Plan-006's daemon-control surface, Plan-028's tRPC + WebSocket clients in the background service, the Plan-006-owned contracts type exports, and the Plan-006 / Plan-028 subscription request channel — gate **only the remainder** (full main-process behavior consumes those plans' surfaces), and each is named in the precondition of every phase in [§Remainder PR Sequence](#remainder-pr-sequence) it gates. The partial has no upstream-plan preconditions per [§Partial PR Sequence](#partial-pr-sequence) — it is a standalone substrate slice authored against ADR-016 + Spec-021 alone.

- ADR-016 (Electron desktop app) — the supported-branch subset 42 / 43 / 44, with V1 on 44.x alone.
- ADR-010 (Tokens, Passkeys And The Remote Channel) — the desktop app presents no token of its own, its control-plane calls riding the background service, which holds this machine's tokens, and it carries no passkey ceremony, because passkeys are used only outside it.
- ADR-009 (JSON-RPC IPC wire format) — the wire format the preload bridge forwards.
- ADR-014 (tRPC control-plane API) — the transport the background service carries main's control-plane calls over.
- ADR-020 (V1 deployment model) — declares the hosted-SaaS and self-host options.
- ADR-024 (Electron main-process window retention) — the GC/lifecycle reachability mechanism the [Spec-021 §Acceptance Criteria](../specs/021-desktop-app-and-renderer.md#acceptance-criteria) window-retention bullet verifies.
- **(Remainder only.)** Plan-006 exposes `daemon.hello`, `daemon.flush`, `daemon.stop`, `daemon.restart` and `daemon.status.read`, which main's service supervisor calls; the service's detached start, `daemon.ping` and the `daemon.status` topic are Plan-028 Phase 1's. Plan-006 ownership of the daemon-start contract is load-bearing; if Plan-006 ships without an explicit `DaemonHello` readiness signal, Step 7 below blocks until it lands.
- **(Remainder only.)** Plan-028 exposes a tRPC v11 client + WebSocket (JSON-RPC 2.0) client surface the background service instantiates; main forwards each renderer control-plane call to the service, which sends it under this machine's credentials. The main process is a forwarder, not a protocol implementer.
- **(Remainder only.)** `packages/contracts/src/` exports `DaemonMethod` / `DaemonParams` / `DaemonResult` / `DaemonEvent` / `DaemonEventPayload` typed union per Spec-006 (owned by Plan-006). The `PlatformBridge` interface and the desktop's preload API type import them from there and re-export none of them.
- **(Remainder only.)** Plan-006 / Plan-028 resolve the per-subscription request channel that [Spec-021 §Preload Bridge Contract](../specs/021-desktop-app-and-renderer.md#preload-bridge-contract) pins as deferred — the preload bridge's `daemon.subscribe<E>(event, handler)` names an event and takes no request object, so neither `sessionId` nor `afterCursor` can travel, and `session.subscribe`, the session's one stream, which a window that fell behind re-opens after the last position it kept, has no shape to call. Type-name availability does not satisfy this; the parameterized signature must exist.

Renderer deps: `react` v19, `react-dom` v19. Playwright `_electron` for E2E testing. **Console dependencies (exact-pinned, each admitted by a [Spec-021 §Console Libraries](../specs/021-desktop-app-and-renderer.md#console-libraries) verdict row and landing with the console PR that first imports it):** `@tanstack/react-virtual`, `micromark` + `mdast-util-from-markdown` + the GFM extensions, `remend`, `katex`, `mermaid` (lazy, opt-in), `@xterm/xterm` + the WebGL / fit / search / unicode11 / serialize addons, `anser`, `diff`, `@xyflow/react` (with `@xyflow/system` in lockstep), `react-resizable-panels`, `@atlaskit/pragmatic-drag-and-drop`, `overlayscrollbars` 2.16.0 with `overlayscrollbars-react` 0.5.6 (every scroller but the transcript), `perfect-freehand`, `@base-ui/react`, `tinykeys`, `@floating-ui/react-dom`, `zustand`, `idb`, `unplugin-icons` + `@iconify-json/tabler`, and the IBM Plex Sans / Mono foundry packages; test-only `@vitest/browser-playwright`, `@playwright/test`, `axe-core` (MPL-2.0, the [ADR-020 §License](../decisions/020-v1-deployment-model-and-oss-license.md#license) waiver — bare rather than the `@axe-core/playwright` wrapper, which binds to a Playwright `Page` that the browser-mode tier does not expose), `memlab`, `size-limit`, `knip`. Nothing on the AVOID column of that table may appear here.

**No crash SDK.** `@sentry/electron` is not a dependency. Crash reports stay on this machine, so nothing needs an upload client, and its `beforeSend` scrubber never reached the raw minidump bytes, which hold heap memory; the service builds the stripped report on the machine instead, with `minidump-stackwalk` 0.27.0 in the daemon, measured before it is adopted. Self-hosted Sentry was considered and not taken: it needs 16 GB of memory and is FSL-licensed.

**No WebAuthn dependency.** `koffi`, `oauth4webapi` and an own-built macOS WebAuthn addon are not dependencies: the desktop app carries no WebAuthn, because passkeys are used only outside it.

**No keystore library.** `@napi-rs/keyring` is not a dependency of the desktop app: main keeps no keystore entry and holds no credential, and the background service holds every secret.

**No colorer in the renderer.** Code is colored once in the daemon and every surface paints the spans it is handed ([ADR-035](../decisions/035-one-syntax-colorer-in-the-daemon.md)), so `shiki` is a dependency of `packages/runtime-daemon` at the same pin and not of this package, and no Worker here colors a block or a diff. **Vitest-family lockstep.** `@vitest/browser-playwright` peers on `vitest` at the exact same version, so it is admitted through the `testing` catalog in `pnpm-workspace.yaml` beside `vitest` and `@vitest/coverage-v8`, never as a desktop-local exact pin — the catalog entry is the single pin, the family moves together, and the registry-latest rule yields to catalog lockstep for any package whose peer is exact-versioned.

### Main process

- **Main's entry point**, at the root of `main/` — **created.** Calls `app.requestSingleInstanceLock()`; reads startup config; starts the crash reporter **first** (before any other module loads); registers the `sidekicks://` protocol handler; reads `--fixture` / `--session` through main's fixture launch; builds the window used last from main's registry of windows; starts the service supervisor.
- **The window factory**, in `main/windows/` — **created.** Every window is a `BaseWindow` hosting the renderer as a `WebContentsView` with the exact `webPreferences` set in [Spec-021 §Security Hardening Baseline](../specs/021-desktop-app-and-renderer.md#security-hardening-baseline). The two ESLint selectors refuse a window or web view built outside the window factory and a hardened `webPreferences` key written as anything but its hardened literal, `window.test.ts` checks the factory builds through the locked block, and the launch smoke test asserts the hardening at run time. One private `constructLockedWindow` owns the locked literal and nothing outside the module calls it. **Every window is alike and none is the main one.** Main keeps a registry of windows — their focus order (the window used last), each one's kept place in main's window-place file, and the first window built at start — and builds every further window when the renderer calls `window.open`: `setWindowOpenHandler` answers `{ action: 'allow', createWindow }`, builds main's own `BaseWindow` from main's own options and the place the frame name's window id keys, and adopts the handed `webContents` in a `WebContentsView`, which keeps the renderer's sandbox, context isolation and CSP. The child carries no preload and no bridge of its own: one renderer drives every window, so a session's store and daemon subscriptions serve its view and its pane windows alike, and no window re-subscribes or holds a store of its own. Main pairs the two closes both ways (the window's `closed` closes the child `webContents`, the child's `destroyed` closes the window) and mirrors each window document's title onto its `BaseWindow`. A side pane moved into its own window is built the same way, and no such window is ever in Preview's relay target list. The navigation policy denies every popup except these `window.open` calls from the renderer itself. **Phase 1B (T-021p-1B-2):** the first window's `loadURL` over the custom scheme and the private `constructLockedWindow`. **Phase 1B (T-021p-1B-5), before Phase 2's bridge:** the registry, the window-open handler and the window-place file.
- **The application menu**, at the root of `main/` — **created at Phase 1B (T-021p-1B-2).** One static template with the platform's own roles on every platform — an Edit menu whose Undo, Redo, Cut, Copy, Paste and Select All reach the focused field through the system's own chain, the File menu's `New window` on `⌘⇧N`, the View menu's `System · Light · Dark` color-scheme choice with the one in force ticked, and Electron's own `{ role: "windowMenu" }`, whose platform verbs list every open window by its title — plus, on macOS, the menu-bar icon (`Tray`) that stays when the last window closes. No other module registers a section into it.
- `apps/desktop/src/main/protocol.ts` — **created.** Custom protocol (`sidekicks-renderer://`) the renderer bundle is served from — not `file://`, per Spec-021's `GrantFileProtocolExtraPrivileges` fuse-disabled posture. **Registered privileged before `app.ready` (I-021-11):** `protocol.registerSchemesAsPrivileged([{ scheme: 'sidekicks-renderer', privileges: { standard: true, secure: true, supportFetchAPI: true } }])` runs at module top level in `main/index.ts`'s import order, ahead of the ready handler, because a scheme not registered `standard` has no origin and therefore no IndexedDB and no `localStorage` — the console's persisted layouts, drafts, and pins ([Spec-021 §Console Design (Meridian)](../specs/021-desktop-app-and-renderer.md#console-design-meridian) §Persistence on the renderer scheme) would have no home. A test asserts the registration precedes `whenReady()`. **Created at Phase 1B (T-021p-1B-1)** beside the bundle handler: `installRendererProtocol(rendererRoot)` serves the built tree through the pure `resolveRendererAsset` (root-containment guard, closed content-type map, the locked CSP header on every response, streaming bodies via `net.fetch`, empty-bodied 403 / 404).
- `apps/desktop/src/main/bridge/index.ts` — **created.** IPC handler registration. One `ipcMain.handle` per preload-bridge method from [Spec-021 §Preload Bridge Contract](../specs/021-desktop-app-and-renderer.md#preload-bridge-contract).
- `apps/desktop/src/main/bridge/daemon.ts` — **created.** `daemon.call` / `daemon.subscribe` handlers. Forwards to the Plan-006 daemon client with the session token attached server-side. **Waits on the request channel in §Preconditions:** [Spec-021 §Preload Bridge Contract](../specs/021-desktop-app-and-renderer.md#preload-bridge-contract) pins the generic `daemon.subscribe<E>(event, handler)` signature as carrying no request object and defers the parameterized shape to Plan-006 / Plan-028, so every parameterized subscription the remainder needs (`session.subscribe` with `{ sessionId, afterCursor }` is the concrete case) has no shape to call until it lands. Type-name availability is not the resolution; the parameterized signature is.
- **Main's control-plane handler behind the preload bridge** — **created.** The `controlPlane.call` (request-response) handler. Main attaches no control-plane credential and holds none: the handler forwards the renderer's request, unchanged, to the background service's own `controlPlane.call` over main's own connection to the daemon, and the service sends it to the control plane under this machine's access token and a fresh DPoP proof. The handler returns only the sanitized response to the renderer, so no control-plane token crosses the bridge. A procedure the control plane defines as anonymous stays reachable while the service holds no credential: anonymous means authentication is not _required_, not that a held credential must be stripped, and the relay counts its sign-in routes per source address ([Spec-019 §Canonical Endpoint Group Registry](../specs/019-rate-limiting-policy.md#canonical-endpoint-group-registry)), so a present credential changes neither admission nor throttling.
- `apps/desktop/src/main/bridge/native.ts` — **created.** `showOpenDialog` / `showSaveDialog` / `showMessageBox` / `showNotification` / `openExternal` (with allowlist validation) / `copyToClipboard` / `revealInFileExplorer` (operating on opaque `FilePathRef` tokens).
- `apps/desktop/src/main/bridge/update.ts` — **created.** `update.getState` / `subscribe` / `requestCheck` / `requestRestart`. Forwards to the `updater.ts` state machine.
- **The service supervisor**, in the main process — **created.** Supervises the background service over [Plan-028](./028-remote-control.md) Phase 1's detached start: reaches it through its socket, handshakes with `daemon.hello`, watches it with `daemon.ping`, and brings a lost service back on [Spec-021 §Daemon Supervision Lifecycle](../specs/021-desktop-app-and-renderer.md#daemon-supervision-lifecycle)'s backoff with its five-attempt ceiling and its version-range gate. A stop or restart flushes the service with `daemon.flush` first, and a service that has not exited after it gets SIGTERM and, 2 s later, SIGKILL; a quit only flushes and leaves the service running. On a Windows computer whose providers live in WSL 2 it runs the per-user task and reads the Windows half's status (T-021r-3-1). Emits lifecycle events that the renderer observes through the bridge.
- `apps/desktop/src/main/updater.ts` — **created.** `electron-updater` with its stock GitHub provider + the refusal of a release not above the last one seen, which main's updater record, `<app-user-data>/updater-state.json`, keeps + the install-kind detection behind the cannot-update lines. Scheduled update checks on 4-hour cadence + startup + explicit user request.
- **The crash reporter**, in the main process — **created.** Starts Crashpad with `crashReporter.start({ uploadToServer: false })` while the machine settings file's `Keep crash reports` is on, read straight from the file because it starts before the service first answers. Each crash is written to this machine only. The module uploads nothing and scrubs nothing itself: the service builds the stripped report from the dump (the process type, the versions, the platform and the crashing thread's stack, file paths cut to their names, session ids replaced by stable hashes), symbolicates it on the machine, deletes it with the diagnostic logs, and serves `daemon.crashList`. The raw dump never leaves the machine. No renderer-side crash module exists.
- **The `sidekicks://` link handler**, in the main process — **created.** `app.setAsDefaultProtocolClient('sidekicks')`. On macOS: `open-url` event handler. On Windows / Linux: `second-instance` event handler (the URL arrives via `argv` on secondary-instance launch). The URL is parsed in the main process by the one `sidekicks://` parser `packages/contracts` exports — the same form `Copy link` copies and `sidekicks open` sends — and the parsed request, `session/<id>` or `workflow-run/<runId>`, is handed to the renderer through `window.subscribeToNavigationRequest`. #### Notarization Submission And Poll

[Spec-021 §Code Signing And Notarization](../specs/021-desktop-app-and-renderer.md#code-signing-and-notarization) supplies the **requirement** — the release pipeline "must include timeout + retry logic rather than synchronous blocking on notarization" — and records the observed Apple-queue delay range of **24–120+ hours**. It states no timeout value; this plan owns the concrete mechanism and the ceiling, set above that observed range so a normal queue never trips it. The design is **detached-submit + resumable poll**, not a single blocking wait:

1. **Submit detached.** `xcrun notarytool submit <artifact> --no-wait -f json` returns immediately with a submission `id`. `--no-wait` is `notarytool`'s default; the flag is passed explicitly so the shape survives a future default change.
2. **Persist the submission id.** The `id` is written to the release job's artifact store keyed by `{version, platform, artifact}` before the job may exit. This is what makes the poll resumable: a CI job that ends — timeout, runner eviction, deliberate release-engineer detach — loses nothing, because Apple's Notary service keeps processing regardless. `notarytool --timeout` is a **polling** limit, not a submission cancel: per the tool's own help text, "The Notary service will continue processing even if the timeout is reached."
3. **Poll in bounded increments.** Each poll invocation runs `xcrun notarytool wait <id> --timeout 30m -f json` (or `notarytool info <id>` for a non-blocking status read). A poll that returns `In Progress` re-queues rather than failing the release. No single CI job is held open for days.
4. **Overall abandonment ceiling: 168 hours (7 days)** from first submission, accumulated across resumed polls. The ceiling sits above the spec's documented 120-hour upper bound with headroom, so it is an abandonment signal for a genuinely stuck submission — never a resubmission trigger for a merely slow queue. Resubmission is a manual release-engineering decision after the ceiling trips, because Apple's queue treats a resubmission as new work and a resubmit-on-timeout loop is self-defeating.
5. **Terminal handling.** `Accepted` → `xcrun stapler staple <artifact>` and the artifact is releasable. `Invalid` / `Rejected` → `xcrun notarytool log <id>` is captured into the release record and the artifact is not distributed.

Pinned tool version: `notarytool` 1.1.2 (41), the version shipped with the CI image's Xcode command-line tools; the detached-submit + `info` / `wait` / `log`-by-submission-id surface this design depends on is verified against it. Bumping the CI image re-verifies `xcrun notarytool submit --help` before the release cut.

- **Component.** Each of the four body states, the frozen-marking state, the chip's three texts, the tools at rest and pressed, the hue slider appearing only under Pen, and the attachment chip from zero marks to many — all from fixture data.
- **Electron tier, headless, never a visible window.** The dual-client case end to end: two clients attached to one page through the daemon's relay, driving it from both, with exact counter arithmetic and zero detach events. `capturePage` on a hidden view, asserting the scale is read from the returned image and not from `getScaleFactors()`. The screencast's acknowledgment loop, asserting the stream does not stall at three frames. `connectOverCDP(transport)` over the relay listing exactly the open Preview pages with the console absent, a page session's `Target.getTargets` and its attach to any other target refused, and no debug port open on the machine — the regression that catches the relay's filter going missing or a `BrowserWindow` sneaking back in. Preview's scenarios drive this relay path and never a port.
- **Process inventory.** `app.getAppMetrics()` asserting one renderer per open page, one browser per machine, and no per-session process beyond that; the release of the oldest idle page when `process.availableMemory()` falls below the headroom, its renderer gone from `getAppMetrics()` within 1.5 s, and the ten-minute releases.
- **Provider round trip.** One browser call on Claude Code and one on Codex producing the same flow row; one marks attachment reaching each provider in its own image shape.
- **Tripwires.** No browser-style tab strip in the pane chrome. No devtools control. No search. No dialog, overlay, backdrop or scrim in the pane. No picture in place of a real page on the machine that runs the session.
- **Re-run by hand after a bump.** The dual-client measurement is re-run after an Electron or Playwright version change, like the live provider smoke suite, and never in continuous integration. Two claims a build must not take from third-party write-ups: that `getScaleFactors()` gives the device pixel ratio, which returns `[1]` against a real two-times capture, and that private memory can be read on macOS, which is `undefined` at this Electron.

## Data And Storage Changes

No Postgres or Durable Object schema changes, and no entry in the operating system's keystore: this machine's DPoP key, the hosted account's tokens, this machine's identity key and every other secret are the daemon's, and the local daemon session token is read from its file at every connect and never cached, because the daemon makes a new one at every restart. The desktop app stores only:

### Main-process-local config

- Main's window-place file under `<app-user-data>` — one entry per window, keyed by the window id the renderer's kept layout shares: its place, size, display and maximized or fullscreen state, and a pane's own window's place and size per pane kind. Put back before a window is built; kept beside the appearance record whose kept background paints its first frame. Written whole and atomically; an empty or unreadable file brings the app up at the display's default size.
- `<app-user-data>/appearance.json` — the appearance record: the theme, the color scheme, the text size, the transcript width, and the current theme's light and dark ground colors, every value an enum or a number. Main reads it to paint the first frame before the page loads; `window.setAppearance` writes it. A missing or broken file reads as the defaults and main repairs it.
- `<app-user-data>/keyboard-map.json` — the keyboard map: only the overridden rows, keyed by act, read and written through `keyboardMap.read()` / `keyboardMap.write()`. A missing or broken file reads as the chords the app ships with, main repairs it, and the Keyboard page says both happened.
- `<app-user-data>/updater-state.json` — current version, last-check timestamp, staged-update metadata, and the last release version seen, which the next check's refusal of an older release reads. Managed by the updater. Main reads and writes it whether or not the service runs, and no wire writes it; a missing or broken file reads as the installed version.
- `<app-user-data>/config/supervisor-state.json` — the service's PID, the time of its last `daemon.ping` reply, restart attempt count. Diagnostic only; not authoritative for the service's state.

`<app-user-data>` resolves per Electron `app.getPath('userData')`: `~/Library/Application Support/AI Sidekicks` (macOS), `%APPDATA%\AI Sidekicks` (Windows), `~/.config/AI Sidekicks` (Linux).

Each of these files is readable and writable only by the person, written whole and atomically over a schema-checked parse, and never written to a wire.

**The machine's settings file is not the app's.** `<home>/.ai-sidekicks/machine-settings.json` holds the machine-wide preferences — the auto-update preference, `Keep crash reports`, the editor, the default checkout, the new-session and keep-awake switches, the notification preferences other than their secrets, the browser's switches, the screen-reader switch, the project environment rows, the backup switch and folder, the folder new clones go into, the branch-name pattern and voice's settings. The background service is its only writer: main writes a change through `machineSettings.write(change)`, which hands it to the service's `daemon.machineSettingsUpdate {change}`, and every window reads it through `machineSettings.read()` and `machineSettings.subscribe()`, which carry `daemon.machineSettingsRead` and `daemon.machineSettingsSubscribe`. Main reads the file directly only before the service first answers, and only the auto-update preference and `Keep crash reports`, which it needs at start; the renderer never reads it.

## API And Transport Changes

### Preload bridge contract (new, owned by this plan)

The full `PlatformBridge` interface from [Spec-021 §Preload Bridge Contract](../specs/021-desktop-app-and-renderer.md#preload-bridge-contract) lives in the renderer's `services/platform/` with `PlatformBridgeProvider`; the desktop's implementation of it reads `window.desktopBridge`, whose type is the desktop's preload API type, `PreloadApi`, in `apps/desktop/src/shared/preload-api.ts`. Key requirements:

- All methods return `Promise<T>` or a synchronous primitive; no callbacks (`ipcRenderer`-style pub-sub uses the `subscribe(...): Unsubscribe` pattern).
- No property or method signature references `Token`, `DPoP` or `SessionToken` in its type or return shape.
- `FilePathRef` is an opaque branded type (`string & { __brand: 'FilePathRef' }`); the renderer cannot dereference a filesystem path — dereferencing requires a second bridge round trip.

### Daemon JSON-RPC forwarding

- Wire format: Content-Length-framed JSON-RPC 2.0 per Spec-006 / ADR-009.
- Transport: Unix domain socket (macOS / Linux) or named pipe (Windows) per Spec-006. The main process instantiates the client from Plan-006's shared client SDK.
- The main process attaches the daemon session token as an RPC-level header; the renderer never sees the token.

### Control-plane tRPC + WebSocket forwarding

- Path: main forwards each renderer control-plane call to the background service over its own connection to the daemon; the service speaks tRPC v11 over HTTPS for request/response and the Spec-028 binary wire frames on the relay WSS connection; the control plane carries no presence events (ADR-014, Spec-028).
- Main attaches no control-plane credential and holds none. The service presents this machine's access token under `Authorization: DPoP` with a fresh DPoP proof on every outbound HTTP request, and authenticates the relay WSS connection with the short-lived relay `connectionToken` over the `Sec-WebSocket-Protocol` subprotocol. The desktop app reaches the person's other machines as its machine, never as a linked device: the service negotiates and authenticates each channel to another machine with this machine's credentials.
- Response sanitization: the main process strips `set-cookie` headers and any upstream auth-material-carrying headers before returning the response body to the renderer.

### Deep-link transport

- Protocol: `sidekicks://<action>/<...args>`. Actions: `session/<id>` and `workflow-run/<runId>`. The form is one shared contract: `packages/contracts` exports the one function that composes an address and the one that parses it, and `Copy link`, main's handler and `sidekicks open` all use them, so an address copied from the app opens the same place from the command line or the operating system.
- URL arrival:
  - macOS: `app.on('open-url', (event, url) => ...)` handler.
  - Windows / Linux: `app.on('second-instance', (event, argv) => argv.find(a => a.startsWith('sidekicks://')))` handler; the URL is the last `argv` entry on secondary-instance launch.

### Update feed transport

- Transport: HTTPS GET against the project's GitHub Releases.
- Update format: `electron-builder`'s update files (`latest.yml` and its per-platform siblings), read by `electron-updater`'s stock GitHub provider, which checks the SHA-512 they list on each download. The release manifest beside them lists each artifact's SHA-256 for the service's own update; the app's updater does not read it.
- Artifact format: `.dmg` to install and `.zip` for updates (macOS), NSIS `.exe` for x64 and arm64 (Windows), AppImage (Linux). A `.deb` or `.rpm` install updates through the apt or dnf repository and the package manager, never through the app.
- Blockmap delta downloads where the platform has one: NSIS, the macOS zip once a previous update is cached, and AppImage.

## Cross-Plan Obligations

Plan-021 owns the `apps/desktop/src/{main,preload,renderer}/` **namespaces**, but several files inside them carry other plans' **content** — the per-file content exceptions this section records. The rule this section encodes: Plan-021's remainder work composes, imports, and registers that content; it never rewrites a body it does not own.

- **CP-021-2 — the remainder's daemon supervisor publishes `daemon.process.*` into the Plan-006 R3 status projector.** `daemon-supervisor.ts` owns the producer half of the process-lifecycle signal (start / ready / crash / restart / persistent-error); Plan-006 R3 owns the consumer projection and the status pill. Until this task ships, R3's pill surfaces transport state only — the documented runtime residual, not a build-order cycle. Reciprocal of CP-006-11. **Direction:** Provide to [Plan-006](./006-local-ipc-and-daemon-control.md). **Tasks:** T-021r-3-1.
- **CP-021-3 — the remainder's registry of main's bridge handlers registers the `daemon.status` handler Plan-028 Phase 1 builds.** [Plan-028](./028-remote-control.md) Phase 1 carries the service's state to the renderer as the `daemon.status` topic on `daemon.subscribe` — the link state from the liveness check and the app-and-service version range — and refuses every renderer-issued mutating call (`daemon.stop`, `daemon.restart`) unless that topic reads connected; Plan-021's registry registers that handler on the `daemon.subscribe` channel and never rewrites its body. Together with CP-021-2 this closes the renderer's status path: `daemon.subscribe('daemon.status', …)` has a live backend once this registry and the non-stub preload ship. **Direction:** Consume from [Plan-028](./028-remote-control.md). **Tasks:** T-021r-2-1.

### CP-021-8 — Provider command-and-skill enumeration consumed from [Plan-004](./004-provider-driver-contract-and-capabilities.md)

The composer's command list subscribes to `session.providerCommandsSubscribe` and reads the `provider_commands` and `context_compaction` declarations through the existing `driver.listCapabilities` cache; Plan-004 owns all three and this plan authors none of them. The subscription takes the session alone (`{ sessionId }`): the daemon follows the session's live provider process and sends the whole list again on each change the provider pushes and for each new process — a new session, or a switch of provider, account or worktree at a run boundary — so the composer never names an agent, a run or a binding, which no client-facing read publishes. Each emission carries the `(driverName, providerAccountId)` it was read under, and the composer replaces its list with each emission rather than merging or filtering an older one. That is [Spec-004 §The provider command and skill surface](../specs/004-provider-driver-contract-and-capabilities.md#the-provider-command-and-skill-surface)'s routing invariant landing on the one surface that could violate it — a composer that kept one list across a binding change would offer a Claude command to a Codex agent without any daemon call being wrong. Until the first emission the list has nothing to offer, this being a live read rather than a catalog that outlives a session.

**Resolution.** Plan-004 Phase 4 registers the subscription; this plan's Phase 6 composer consumes it. No reciprocal task is owed on Plan-004 beyond the registration it already carries, so this row is one-directional by design.

### CP-021-11 — Preview's daemon-side dependencies and the page-host namespaces live in the daemon package

[ADR-036](../decisions/036-embedded-browser-for-preview.md) puts these pieces of Preview in the daemon rather than in the main process: the context resolver, the headless browser that stands in where no desktop runs, and the agent's browser tool server hosted in process. Their dependencies are therefore **`packages/runtime-daemon`'s, not `apps/desktop`'s** — `playwright-core` 1.62.1 pinned exactly for the headless fallback and for the tool server, which is that package's own `lib/coreBundle` export (the `@playwright/mcp` shim re-exports it and pins a pre-release pair, so the shim is not taken; the export and the element-reference format are re-checked on every bump), and `@modelcontextprotocol/sdk` 1.30.0 as a direct dependency because the in-process hosting pattern binds the connection to a transport the daemon builds. This plan's renderer half adds one dependency of its own for the mark strokes, `perfect-freehand` 1.2.3, and `electron` 44.1.0 is already pinned here. The `preview.*` and `browser.*` method roots those pieces answer on are daemon JSON-RPC roots for the same reason: there are two page hosts and one endpoint, so the verbs sit where the resolver does and nothing above them branches on which host is live.

**Resolution.** §Phase 9 — Preview And Detached Panes builds all of it as this plan's tasks. T-021r-9-1 builds the Electron page host, its debugger link and the `browser` bridge namespace in the main process; T-021r-9-2 builds the daemon's Preview in `packages/runtime-daemon` — the relay with its page-session filter, the context resolver, the headless browser, the in-process tool server, the per-session page store, and the handlers behind `preview.*` and `browser.*`; T-021r-9-3 and T-021r-9-4 build the renderer's pane and Settings › Browser. The daemon's method-namespace registry stays **[Plan-006](./006-local-ipc-and-daemon-control.md)**'s: CP-006-18 registers the daemon's `preview` and `browser` roots and nothing more; T-021r-9-2 builds everything that answers on them and adds its daemon dependencies.

### CP-021-12 — Skills destination rail and routing arms (reciprocal of [Plan-030](./030-skills.md) CP-030-1)

Plan-030 authors the Skills destination as components in its own `apps/desktop/src/renderer/src/features/skills/` subtree; the icon rail, `rail-navigation.ts` and the routing module are this plan's files, and this plan admits one arm per file — the rail item with its place in the keyboard order, and the destination arm carrying that destination's four addresses. The split is the CP-021-6 shape unchanged: the owner authors the components behind the mount, the host provides the mount, and neither edits the other's subtree.

**Resolution.** Plan-030 Phase 4 is gated on this plan's Phase 6 merged, so the rail and the router exist before the arms land, and Plan-030 adds exactly those arms and edits nothing else in the three files. This plan gains no task: the rail item and the destination arm are the rail-entry and route-table registration Phase 6 already performs for every other plan-owned destination.

Configure TypeScript strict (`"strict": true`, `"noUncheckedIndexedAccess": true`, `"exactOptionalPropertyTypes": true`).
2. **Author the bridge types.** The full `PlatformBridge` interface per Spec-021, with `PlatformBridgeProvider`, in the renderer's `services/platform/`, and the desktop's preload API type, `PreloadApi`, in `apps/desktop/src/shared/preload-api.ts`; both import the Plan-006 daemon types and the Plan-028 control-plane types from `packages/contracts`. Author the conditional-type negative test (no member of the preload API type or of `PlatformBridge` includes `'token' | 'dpop' | 'secret'`) in `apps/desktop/src/shared/preload-api.test-d.ts`, beside the preload API type.
3. **Author `electron.vite.config.ts`.** `electron-vite` v5.0.0 config with three entries (main / preload / renderer). Per-target module-system shape: main emits ESM (`build.rollupOptions.output.format: 'es'`); preload emits CJS via `build.rollupOptions.output.format: 'cjs'` + an explicit `.cjs` output extension (Electron's sandboxed preload runtime is CJS-only — an ESM preload fails to register with `SyntaxError: Cannot use import statement outside a module`, and the `.cjs` extension overrides the package-level `"type": "module"` so Node loads the file as CJS regardless of the package field); renderer emits browser-ESM. Renderer loads via custom protocol, not `file://`. Enable `build.sourcemap: 'hidden'` (sourcemap emitted but not referenced from the bundle, so they stay with the build for reading a stack trace and are not shipped to end users). The `apps/desktop` `build` script uses `electron-vite build` (not `tsc -b`); this is what enables both the per-target output shape above AND the smoke-mode `define` substitution described next. **Smoke-mode gate:** declare a compile-time-static identifier `__SIDEKICKS_SMOKE_BUILD__` via Vite's `define` plugin — substituted with the literal `false` in default `electron-vite build` and with the literal `true` in `electron-vite build --mode=smoke`. Test-only probe code paths gate on this identifier in an outer `if (__SIDEKICKS_SMOKE_BUILD__ && <runtime-opt-in>)`; Rollup's tree-shaker collapses the `if (false && expr)` branch in release bundles, physically eliminating the probe body from the shipped artifact (the "test machinery never embedded in production binaries" property — see [Spec-021 §Pitfalls To Avoid](../specs/021-desktop-app-and-renderer.md#pitfalls-to-avoid)). The inner runtime opt-in remains as defense-in-depth so the probe never auto-runs even in a smoke bundle without explicit invocation.
4. **Author the window factory** in `main/windows/` — one private `constructLockedWindow` builds every window, the first at start and each further one around the renderer's own `window.open` child, as a `BaseWindow` hosting the renderer as a `WebContentsView` with the `webPreferences` block from [Spec-021 §Security Hardening Baseline](../specs/021-desktop-app-and-renderer.md#security-hardening-baseline). Add the two ESLint selectors to `apps/desktop/eslint.config.mjs` — one refusing a `BaseWindow`, `BrowserWindow` or `WebContentsView` built outside the window factory, one refusing `contextIsolation`, `sandbox`, `webSecurity`, `nodeIntegration` or `nodeIntegrationInWorker` written as anything but its hardened literal — and write `window.test.ts`, which checks the factory builds every window through the locked block.
5. **Author the preload bridge.** `apps/desktop/src/preload/index.ts` — single `contextBridge.exposeInMainWorld('desktopBridge', bridge)` call. Each bridge method delegates to `ipcRenderer.invoke('<channel>', ...)`; no direct Node API use. The bridge object must be structurally typed as the desktop's preload API type from step 2.
6. **Wire the IPC handlers.** `apps/desktop/src/main/bridge/index.ts` + the per-namespace bridge handlers §Target Areas Main process lists (the daemon, control-plane, native and update handlers, and the `window`, machine-settings, keyboard-map, app and `browser` handlers). One `ipcMain.handle('<channel>', handler)` per method. Each handler validates input against the Spec-021 contract; auth material is attached server-side; responses are sanitized before return.
7. **Author the service supervisor** in the main process — after `app.whenReady()`, supervises the background service over [Plan-028](./028-remote-control.md) Phase 1's detached start, which is not this plan's; the app never parents the service, so a quit leaves the service, every run and every shell running. Handshake with `daemon.hello`; watch with `daemon.ping`. A lost service is brought back through that start on the Spec-021 ladder (`100ms, 300ms, 1s, 3s, 10s`) and surfaces persistent error after 5 attempts. A stop or restart flushes the service with `daemon.flush`, and a service still running after the flush gets SIGTERM and, 2 s later, SIGKILL; a quit only flushes. On a Windows computer whose providers live in WSL 2, supervision goes through the per-user task (T-021r-3-1). Version-range gate: each app accepts its own service version and the previous one; outside that range, block mutating bridge calls, allow only read-only subscriptions, and name the side that is behind.
8. **Author the auto-update state machine.** `apps/desktop/src/main/updater.ts`. `autoUpdater` (from `electron-updater`) with its stock GitHub provider on a 4-hour cadence + startup + explicit check, with `autoDownload` and `autoInstallOnAppQuit` off and `allowDowngrade` off. At check time main refuses a release whose version is not above the last one seen in `updater-state.json`; the cycle is skipped and logged. A download starts only on the person's press, and `electron-updater` checks its SHA-512 against the release's update file (and on Windows the installer's publisher) before `update-downloaded`; a mismatch discards the artifact, logs and refuses. `on('update-downloaded')` handler: stage artifact at `apps/desktop/<staging-dir>`; `Restart to finish` applies it through `app.relaunch() + app.quit()`. After relaunch main handshakes with the service through `daemon.hello` as at every start; a handshake that completes with the service outside the accepted version range makes the console read-only and names the side that is behind. The app does not roll itself back; a bad release is fixed by the next one.
9. **Author the crash reporter** in the main process — called **first** in main's entry point before any other module loads. Starts Crashpad with `crashReporter.start({ uploadToServer: false })` while `Keep crash reports` is on, reading that one value straight from the machine settings file because the service has not answered yet. Crashpad covers the main process and every renderer; nothing is uploaded and no crash SDK is initialized anywhere. The service turns each dump into the stripped, symbolicated report it keeps and serves through `daemon.crashList`.
10. **Author the deep-link handler.** `apps/desktop/src/main/deep-link.ts`. `app.setAsDefaultProtocolClient('sidekicks')` at startup. `open-url` (macOS) and `second-instance` (Windows / Linux) handlers parse the URL in the main process with the one `sidekicks://` parser `packages/contracts` exports and hand the renderer the parsed request — `session/<id>` or `workflow-run/<runId>` — through `window.subscribeToNavigationRequest`; a malformed URL is refused at the parser boundary and nothing is routed.
11. **Author the renderer's layout and composer.** `apps/desktop/src/renderer/src/App.tsx` (top-level router + layout) plus `layout/` (the layout chrome) and `features/composer/` (the composer). This step authors **no feature-view body**: each Signature Feature view is created by its owning plan in that plan's own `apps/desktop/src/renderer/src/` subtree, and this step only mounts it as a route and holds the composition points.
12. **Author the build pipeline.** `apps/desktop/build/fuses.ts` + `asar-digest.ts` + `code-sign.ts`. Fuse-flipping + digest-embedding **must** precede signing; both invalidate any prior signature.

- `apps/desktop/src/main/protocol.ts` — the registration and the handler, both exported as functions so the startup order is asserted rather than assumed: `registerRendererScheme()` wraps `protocol.registerSchemesAsPrivileged([{ scheme: 'sidekicks-renderer', privileges: { standard: true, secure: true, supportFetchAPI: true } }])` and throws on a second call, because Electron accepts exactly one registration per process and a silent second call would hide a startup-order regression; `installRendererProtocol(rendererRoot)` wraps `protocol.handle('sidekicks-renderer', …)` and is called inside `whenReady()` **before** any window is constructed. The handler resolves `sidekicks-renderer://app/<path>` under the built `out/renderer` tree through one pure function, `resolveRendererAsset(rendererRoot, url)`, that decodes and normalizes the pathname, refuses any resolution that escapes the root (`..`, percent-encoded separators, backslashes, absolute paths, and symlinks — checked through `fs.realpath` against the root's own realpath), refuses any host other than `app`, and answers a miss with 404 and an escape with 403 — both with an empty body and no path echoed, so a probe learns nothing about the tree. There is no `index.html` fallback: the console routes by hash, so every navigable URL is `index.html` plus a fragment and a fallback would only turn typos into a served page. One reserved path, `/-/load-failure`, is answered from a document GENERATED in the main process and carrying the (escaped, bounded) failure reason — never read from the tree, because the failure it reports is that the tree could not be loaded and a fallback living there is missing exactly when it is needed; it is matched on the exact decoded path so nothing under it falls through, touches no filesystem call so containment is trivially true rather than checked, and carries no script, link, or retry control. ### Adversarial-Tampering Boundary

The remainder is almost entirely a tampering surface — an untrusted renderer, an untrusted inbound URL, an untrusted update feed, a credential store, a crash-report channel, a page the agent drives, and a signing pipeline — so the `000-plan-template.md` threat classes are enumerated here with the task that owns each arm. Every arm lands inside a phase; none is a floating aspiration.

| Threat class | Arm | Owning task |
| --- | --- | --- |
| Canonicalization round-trip | A `sidekicks://` URL survives parse → normalize → re-serialize with no action or argument reinterpretation. Deep-link parsing is the plan's only untrusted-input parser. | T-021r-5-4 |
| Intake validation parity | Each IPC handler's own validation is at least as strict as the contract schema — a payload the schema rejects must not pass the handler. [Spec-021 §Trust Stance](../specs/021-desktop-app-and-renderer.md#trust-stance) makes every renderer-originated payload untrusted, so handler-level leniency re-admits what the contract forbids. | T-021r-2-7 |

### Testing posture

The `@ai-sidekicks/desktop` package's test surface is split into two disjoint Vitest projects gated by Turbo:

- **`test:renderer`** — happy-dom environment, includes `src/renderer/**/__tests__/**`. Exercises React components and renderer unit logic against plain TypeScript imports. Does NOT invoke `build:smoke`; ~3 s feedback loop. `dependsOn: ["^build"]` in `apps/desktop/turbo.json` covers workspace upstreams only.
- **`test:smoke`** — node environment, includes `test/**/*.test.ts`. Spawns the BUILT `electron-vite --mode=smoke` bundle and asserts the [Spec-021 §Security Hardening Baseline](../specs/021-desktop-app-and-renderer.md#security-hardening-baseline) runtime invariants (`window.desktopBridge` defined; `window.require`, `process`, `global` all `undefined`). `dependsOn: ["build:smoke"]` same-package — Turbo's content-hash cache restores `out/**` when `src/**` + `build/**` + `electron.vite.config.ts` are unchanged, so the build runs only when sources actually changed. Cache miss costs the full ~25-30 s electron-vite build; cache hit is near-instant (Turbo restores `out/**` from `.turbo/cache/` without spawning electron-vite).

The package-level `test` script (the entry point `pnpm --filter @ai-sidekicks/desktop test` resolves to) routes through `turbo run test:renderer test:smoke --filter=@ai-sidekicks/desktop` so the outer task DAG re-resolves `build:smoke` on direct invocations — without that indirection, a bare `vitest run` script would skip the rebuild and `launch.smoke.test.ts` would fail its `existsSync` precondition checks on a cold checkout. The outer `test` task in `apps/desktop/turbo.json` carries `cache: false` to suppress Turborepo's silent input-inheritance from the root `test` task (whose `inputs` declare only `src/**` + `vitest.config.*` + `tsconfig*.json` + `package.json` — excluding both `test/**` and `build/**`); without that opt-out, edits to `apps/desktop/test/**` would cache-hit the orchestrator and skip the inner smoke suite, producing false-green CI on the very surface this posture protects.

The two ESLint selectors and `window.test.ts` hold the locked `webPreferences` block ([Spec-021 §Security Hardening Baseline](../specs/021-desktop-app-and-renderer.md#security-hardening-baseline)). The runtime smoke-test assertions in `launch.smoke.test.ts` run against the BUILT bundle; running smoke against unbuilt sources is not a supported configuration. The split only changes WHEN the build runs (gated by Turbo's content-hash cache), not the smoke gate's authority.

In the remainder, when the Playwright `_electron` E2E suite ships per Implementation Step 15, it should land as its own project (`test:e2e`) with `dependsOn: ["build:smoke"]` or `dependsOn: ["build"]` (depending on whether E2E runs against the smoke bundle or the release bundle); the renderer + smoke split established here is the substrate Playwright extends.

The two globs above are disjoint by design, but they are also **incomplete for the remainder**: `renderer` matches `src/renderer/**/__tests__/**` and `main` matches `test/**/*.test.ts`, so **no project's glob reaches them at all** — `src/main/**` and `build/**`, precisely where the remainder's main-process and build-script units live (§Test And Verification Plan has always declared them at `apps/desktop/src/main/**/*.test.ts`). Under the two-project posture those files would be authored, typechecked, linted, and never executed. T-021p-1B-3 closes this by registering a `main-unit` project in Phase 1B, in the same PR as the first such unit; the paragraph above therefore describes `test:e2e` as its own project rather than "the third". The four plan-registered projects remain mutually disjoint: `src/renderer/**/__tests__/**/*.test.{ts,tsx}`, `src/main/**/*.test.ts` + `build/**/*.test.ts`, `test/**/*.test.ts`, and E2E's `*.spec.ts`. [Spec-021 §Console Test Tiers](../specs/021-desktop-app-and-renderer.md#console-test-tiers) registers the console's own projects beside these four (T-021p-1C-1), and the no-double-discovery property is re-asserted per added project rather than inherited from this sentence: console unit tests live beside their source under `src/renderer/src/**` as `*.test.{ts,tsx}` with no `__tests__/` directory, in the `renderer` project, and the browser-mode, screenshot, accessibility, budget, and end-to-end tiers take `apps/desktop/tests/<tier>/**` globs that no other project reaches — a console project whose glob intersects any other is a review rejection under `apps/desktop/AGENTS.md`. Note that the harness self-test at `apps/desktop/test/harness/mock-bridge.test.ts` (T-021r-8-2) matches `test/**/*.test.ts` and so runs in the existing smoke project — deliberate, not incidental.

## Rollback Or Fallback

- **Renderer-level bug post-release**: auto-update ships a patched binary within 24 hours of detection; users receive it on next update-check cycle (max 4 hours) or explicit "check for updates" action.
- **A bad release**: the app does not roll itself back; the next release fixes it.
- **Daemon fails to start after 5 backoff attempts**: the app enters offline read-only mode; user can view the last-synced session state but cannot issue new runs or approvals. Manual retry button surfaced.
- **Auto-update check failure — an older release or a mismatched download**: a release whose version is not above the last one seen is refused with nothing downloaded; a downloaded artifact whose SHA-512 or Windows publisher does not match is discarded before staging. Either failure is logged to `updater-state.json`; next update-check cycle re-attempts.
- **Notarization queue delay (macOS, once the Developer ID certificate exists — [BL-108](../backlog.md#bl-108-plan-022-windows--macos-signing-procurement-evidence))**: the release pipeline's detached-submit + resumable-poll shape (§Notarization Submission And Poll) lets a delayed release candidate complete asynchronously — the submission id is persisted, Apple's Notary service keeps processing across CI-job boundaries, and no single job is held open. Only the 168-hour overall ceiling abandons a submission, and abandonment is a manual release-engineering decision, not an automatic resubmit. If notarization fails outright (rare), `notarytool log` is captured and the artifact is not distributed.

## Risks And Blockers

- **`electron-vite` v6 stability.** v5.0.0 is the stable line (released 2024-12-07); v6.0.0-beta.1 (2026-04-12) is pre-GA. **Decision: pin to v5.0.0.** Alternative considered: direct Vite + `electron-builder` wiring without a wrapper (gives maximum control; loses HMR convenience and source-code-protection baked-in). Alternative rejected because V1 desktop is a greenfield Electron app and `electron-vite` is the common production pick for one. Alternative also considered: `@electron-forge/plugin-vite` — still marked experimental in v7.11.1 (2026-01-12) per [Electron Forge Vite plugin docs](https://www.electronforge.io/config/plugins/vite). Rejected: an experimental plugin is not a V1-appropriate foundation.
- **Playwright `_electron` experimental API.** Marked experimental in the [Playwright class-electron docs](https://playwright.dev/docs/api/class-electron). Accepted: this is the only viable option (Spectron is archived). Mitigation: design test suites to tolerate minor API churn between Playwright releases; pin Playwright in `package.json` and review changelogs on every bump.
- **Crash dumps hold heap memory.** A Crashpad dump contains heap memory, which in main includes the daemon session token. **Mitigation:** nothing is uploaded — `crashReporter.start({ uploadToServer: false })`, with no crash SDK in any process — and dumps are kept on the machine only while `Keep crash reports` is on; the service builds each kept report stripped of tokens, session ids, paths and content, symbolicates it on the machine (`minidump-stackwalk` 0.27.0, measured before it is adopted), and deletes the dumps with the diagnostic logs.
- **SignPath Foundation eligibility.** Windows signing goes through SignPath Foundation's free program for open-source projects, which this plan applies for; its terms ask for an OSI license with no commercial dual-licensing, no proprietary components, an active and already-released project and a published code-signing policy, and the certificate is issued to SignPath Foundation, which is then the publisher Windows and the updater's publisher check see. Until that signing is in place ([BL-108](../backlog.md#bl-108-plan-022-windows--macos-signing-procurement-evidence)), Windows builds publish unsigned. If the project is not eligible, that goes back to the person, and the distribution plan does not change silently.
- **Smart App Control reputation cold-start on Windows.** A freshly-signed binary has low reputation in Windows Defender's Intelligent Security Graph. First-launch UX on Windows 11 will be rough until reputation accumulates. Accepted for V1. Mitigation: once SignPath Foundation's signing is in place, every release is signed by the same SignPath Foundation certificate, so reputation accrues to one publisher. The release notes and the README's install section carry the `Run anyway` guidance, because the prompt shows before the app can run.
- **Notarization queue delays on macOS.** Per [Spec-021 §Code Signing And Notarization](../specs/021-desktop-app-and-renderer.md#code-signing-and-notarization) — Apple's notarization queue can take 24–120+ hours, per [Apple Developer forum thread 813441](https://developer.apple.com/forums/thread/813441). The release pipeline's per-platform signing step therefore does **not** hold a job open on a synchronous wait: it submits detached, persists the submission id, and polls in bounded increments under a 168-hour overall abandonment ceiling set above the documented 120-hour upper bound (§Notarization Submission And Poll). Accepted as a release-latency risk; does not block V1 if release engineering is staffed for async release cutting. A timeout shorter than the documented delay range would not be a timeout at all — it would be a guaranteed resubmission cycle, and Apple's queue treats each resubmission as new work.
- **Electron 44 pin and the branch cadence.** Electron 41 is end-of-life (2026-08-25), so the 44.x target is not optional; the branch itself is supported until 2027-03-02 and V1 must expect at least one further major bump before then. The console's `browser` pane kind depends on the detached-`WebContentsView` bounds fix, which landed on 44 and reached 42 / 43 only as late backports, so V1 admits 44.x alone and carries no per-branch fix floor. **Mitigation:** the pin is exact in `apps/desktop/package.json`, a bump is its own change that re-reads [Spec-021 §Electron Version And Support Window](../specs/021-desktop-app-and-renderer.md#electron-version-and-support-window), and [ADR-016 §Decision](../decisions/016-electron-desktop-app.md#decision)'s supported-branch subset moves with the same PR that moves the pin. **Two legs ride the pin move.** (i) Electron 44 is Node ABI 149 and no `better-sqlite3` 12.x release ships a prebuild for it, so the daemon's binding would compile from source on every machine; [ADR-022 §Decision](../decisions/022-v1-toolchain-selection.md#decision) therefore moves `packages/runtime-daemon` to `better-sqlite3` 13.0.3 (Node-API, platform prebuilds bundled) **in or before** the PR that moves the Electron pin — the pin may not move first. (ii) [ADR-024](../decisions/024-electron-main-process-window-retention.md)'s window-retention mechanism holds on Electron 44.1.0, where the shipped lifecycle guard passes on macOS; each later pin move re-runs it, and a divergence is a failure of ADR-024's mechanism, never a test to loosen.
- **Console built ahead of Phase 6 (Phase 1C).** The console lands against the fixture bridge before the remainder phases that give several of its surfaces live wires, so the risk is a surface whose fixture shape drifts from the wire that eventually lands. **Mitigation:** each fixture is typed from the same interface as the real boundary it substitutes, the `PlatformBridge` among them, so a wire change breaks the fixture at compile time; a surface is wired live only against a wire its owning plan has registered; and a console PR that wires a surface live against an unregistered wire is a review rejection. Adoption at Phase 6 is a mount-and-move, never a rewrite (T-021r-6-1 EXTEND). The console's main-process floor is Phase 1B, not Phase 3: until T-021p-1B-1 / T-021p-1B-2 merge the renderer has no served origin, so the first console PR follows the Phase 1B PR rather than racing it.
- **Renderer clipboard deprecation pitfall.** Electron 40+ deprecated direct `navigator.clipboard.*` from the renderer per [Spec-021 §Implementation Notes](../specs/021-desktop-app-and-renderer.md#implementation-notes) §Renderer Bundle. The ESLint `no-restricted-imports` rule is the CI gate; a renderer file that imports `@capacitor/clipboard` or similar cross-platform clipboard library bypasses the rule. **Mitigation**: document in `apps/desktop/README.md` that clipboard access must route through the `PlatformBridge`'s `native.copyToClipboard`; add a runtime assertion (`expect(navigator.clipboard).toBeUndefined()` in renderer boot) that fails fast if a transitive dep re-introduces renderer-clipboard access.
- **Single-instance-lock race with deep-link.** [Spec-021 §Main Process Responsibilities](../specs/021-desktop-app-and-renderer.md#main-process-responsibilities) requires `app.requestSingleInstanceLock()`. Without the lock, a `sidekicks://session/<id>` URL arriving at a second instance would race with the first instance's daemon state. The lock + `second-instance` event handler is the correct pattern, but it introduces a subtle bug: if the first instance is mid-crash during URL arrival, the second instance gets the lock and may re-route the URL. Accepted: routing to a session is idempotent, so the race is a UX oddity not a security issue. Documented in `apps/desktop/RELEASE.md`.

- **Partial deliverable (Phase 1)** — workspace package substrate (`apps/desktop/src/{main,preload,renderer}/` directory tree + electron-vite v5 toolchain + minimal entrypoints + the preload API type and the `PlatformBridge` interface). Standalone (no upstream plan dependencies); unblocks [Plan-001 Phase 5](./001-session-core.md#phase-5--client-sdk-and-daemon-wiring) and [Plan-022 Phase 3](./022-rust-pty-sidecar.md#phase-3--rustsidecarptyhost--env-var-opt-in). See §Partial PR Sequence above.
- **Partial supplement — Phase 1B** — the renderer-load substrate: privileged scheme + bundle handler, the window's load, the locked window constructor, main's registry of windows with its window-open handler and window-place file, the application menu, and the `main-unit` Vitest project. Standalone (gated only on Phase 1 merged; no upstream plan dependency), so the Phase 1C console runs in the app without waiting on Plan-006 R3; T-021p-1B-4 moves the Electron and `better-sqlite3` pins. See §Partial PR Sequence.
- **Remainder** — Implementation Steps 6–14 (step 11 reduced to the router, `layout/` and `features/composer/` per §Renderer, since each Signature Feature view is created by its owning plan in that plan's own subtree; step 14's partial ban list extends with the desktop app's native-module tree) + 15–18: IPC handlers, daemon supervisor, crash reporter, auto-updater, deep-link, renderer layout + composer, build pipeline, release manifest, Playwright E2E, renderer test harness, CI gate, runbook, Preview and a side pane's own window. Decomposed into Phases 2–9 by [§Remainder PR Sequence](#remainder-pr-sequence). - **Partial supplement — Phase 1C** — the console's renderer folders at §Target Areas Renderer, built by T-021p-1C-1..8 over the Phase-1B origin, inside the [Spec-021 §Console Design (Meridian)](../specs/021-desktop-app-and-renderer.md#console-design-meridian) envelope, against the fixture scenarios.
