## Goal

Implement versioned workflow definitions and durable workflow execution for the full V1 engine — four phase types, four gate types, parallel phases with named pools, and append-only hash-chained approval history — reusing existing session, run, approval, artifact, and recovery primitives.

## Scope

Workflow definition persistence (content-hashed, immutable versions), workflow run state, phase execution for all four V1 phase types (`single-agent`, `multi-agent`, `automated`, `human`), all four gate types, parallel phase execution with `ParallelJoinPolicy`, resource-pool admission, workflow-level gate resolution with per-run hash chain, OWN-only channel linkage, replay-deterministic projection rebuild, and the chat-invoked start surfaces with per-start authorization (`Spec-017 §Chat-Invoked Start and Start Authorization`, ADR-027 — added by the 2026-08-11 chat-start amendment).

## Non-Goals

- Marketplace or cross-machine workflow distribution. The `shared` scope tier is node-local reuse breadth, not distribution — a `shared` definition never leaves the daemon that stores it. Cross-machine portability at V1 is the operator-moved file form of `Spec-017 §Definition file form — export and import (C-17)`, not a service.
- External workflow-engine integration
- Workflow editor polish beyond V1 ambition
- BIND channel ownership (V1.1 criterion-gated per ADR-015)
- Cross-node workflow dispatch (Spec-024 V1.1)
- Cross-run campaign memory and the durable wake-coalescing delivery substrate (V1.1 criterion-gated, deferred 2026-08-16 — the three criteria are stated once in `Spec-017 §Non-Goals` and not restated here). This plan builds only the in-run fold: the park's provider-account attention key of T2.5 and its `park_attention_key` projection column, which crosses no aggregate boundary. No task here opens a per-watcher generation record, a claim / queue / deliver lifecycle, or any cross-run durable row.

## Data And Storage Changes

- Add the 9-table workflow schema per [Local SQLite Schema §Workflow Tables](../architecture/schemas/local-sqlite-schema.md#workflow-tables-plan-017) (SA-24): `workflow_definitions`, `workflow_versions`, `workflow_runs`, `workflow_phase_states`, `phase_outputs`, `workflow_gate_resolutions`, `parallel_join_state`, `workflow_channels`, `human_phase_form_state`.
- Source-of-truth hierarchy (SA-25): `session_events` remains canonical; tables 1/2/5/6 are immutable truth, 3/4/7/8/9 are projections rebuildable via Plan-015 `ProjectionRebuild`.
- `workflow_gate_resolutions` carries a per-run BLAKE3 hash chain anchored to `session_events` via dual-anchor payload (`gate_resolution_id` + `row_hash`) on the `workflow.gate_resolved` event (SA-26). Dual-hash: BLAKE3 for daemon-internal identity, SHA-256 reserved for Plan-014 artifact content (SA-27).
- `human_phase_form_state` ships empty at V1; clients persist drafts via localStorage/IndexedDB per [Spec-017 §Ship-empty tables (SA-28)](../specs/017-workflow-authoring-and-execution.md#ship-empty-tables-sa-28). Table reserved for V1.x daemon-side fallback. **Reconciliation with the wire surface (A-017-25, Tier-8 audit):** `HumanPhaseFormDraftSave` is the V1.x-reserved companion of that empty table, not a V1 behavior. Its request/response shape is declared in the contract doc so the V1.x enablement is a pure additive wiring change with no contract break, and no V1 daemon handler is registered for it — the V1 wire surface is the other nine operations. A client that needs draft durability at V1 uses its own local store; the table and the operation light up together in V1.x.
- **Workflow-definition scope domain is three-valued (ratified 2026-08-10, A-017-11):** `session` \| `project` \| `shared`. `session` scopes a definition to its authoring session, `project` spans the sessions of one project, and `shared` is the cross-project tier — a definition authored once and reusable by any project on the same daemon, resolved out of the same local definition store with no additional table and no sync path. Scope identity is carried by a `scope_ref` column alongside `scope`, in the shape `Spec-028 §Unified Inventory` already uses for scope-qualified bindings — the authoring session id at `session`, the canonical repository root (`repo_mounts.canonical_root`) at `project`, the empty string at `shared` — and the dedupe key moves to `(scope, scope_ref, content_hash)` so a definition stored once at a scope is one row regardless of which session submitted it. A `scope`-only widening does not work: `project` would name no project, and a `(session_id, content_hash)` key would partition `shared` definitions by authoring session, so two sessions storing the same shared definition would produce two rows resolution cannot reconcile. `shared` widens **visibility and reuse breadth only**: it is not distribution, not a marketplace, and not cross-machine sync — a `shared` definition never leaves the daemon that stores it, and `Spec-017 §Non-Goals` continues to exclude marketplace/global-library distribution. The `workflow_definitions.scope` column carries the domain (`CHECK(scope IN ('session','project','shared'))`) while `session_id` keeps recording the authoring session at every scope, so provenance survives the widening. The pre-audit `channel` member — which appeared only on the contract doc and the DDL and never in the governing spec — is struck; a channel-scoped definition was never specified and would have collided with the Plan-016 `direct` channel kind's forced `humans-only` audience.
- **Copy-on-write provenance column (visual-builder amendment):** `workflow_definitions.parent_content_hash`, nullable, recording the content hash of the `shared` definition a row was branched from when an author edited a shared definition (T1.7, `Spec-017 §Definition scope in the builder (SA-36)`). It is provenance and **not** part of the hashed body, so a branched definition and a from-scratch definition with identical bodies still carry the same `content_hash` and converge on the dedupe key — the intended behavior, since the two are the same definition. Editing a `shared` definition in place is forbidden by construction: definition rows are immutable and the table carries no updated-at column, so an in-place edit would append a version to the shared definition and silently repoint every project on the daemon that resolves it. No table is added: the nine-table census is unchanged.
- **`workflow_phase_states.phase_type` admits the four V1 phase types only (A-017-08):** `CHECK(phase_type IN ('single-agent','multi-agent','automated','human'))` per [Spec-017 §Phase-Type and Gate-Type Taxonomy](../specs/017-workflow-authoring-and-execution.md#phase-type-and-gate-type-taxonomy). The pre-audit constraint conflated phase types with gate types (`auto-continue`, `human-approval`, `quality-checks`, `done`), carried two values (`gate`, `terminal`) in no taxonomy at all, and omitted `automated` — so an `automated` phase could not be inserted. Gate types live on the gate column, never here.
- **Resource-pool capacities are daemon-config values, not a cross-plan surface (A-017-17):** the SA-3 defaults restated from [Spec-017 §Execution semantics](../specs/017-workflow-authoring-and-execution.md#execution-semantics) — `pty_slots` capacity `min(8, cpu_count * 2)`; `agent_memory_mb` capacity `daemon_budget - overhead ≈ 192 MB` with a pessimistic 100 MB default reservation per `single-agent` phase; `max_concurrent_phases` daemon-global default 4 as the ready-set backstop. Both capacities are read from local daemon configuration and counted by this plan's own admitter — V1 consumes no other plan's pool API, so neither pool adds a dependency row. Should a future PTY host report live slot capacity instead, that becomes a declared consumption at the amendment that introduces it.
- **Park-and-resume projection columns (workflow-hardening amendment, 2026-08-16; re-homed per-phase at the 2026-08-17 review round) — four columns on one existing Plan-017-owned table, no new table.** `workflow_phase_states` gains all four: `park_reason` (nullable, `CHECK(park_reason IN ('waiting-human','provider-usage-limited'))` — the closed union of `Spec-017 §Park integrity and cancellability (SA-42)`, in the same DDL-CHECK-versus-contract lockstep I-017-12 already enforces), `park_cause` (nullable text, the engine-authored sentence, bounded at 8 KiB and truncated at a UTF-8 code-point boundary with a visible marker — a durable operator-facing string with no bound is an unbounded write on the projection tier), `auto_resume_at` (nullable UTC instant — the durable schedule of `Spec-017 §Provider-limit pacing and durable resumption (SA-40)`, a **durable value rather than an in-memory timeout**, so a parked phase resumes itself across daemon restart), and `park_attention_key` (nullable text — provider + account identity + credential generation, the outage-scoped fold key; a correlation for presentation that gates no start, resume, retry, or schedule fire). Per-phase rather than per-run, and the placement is load-bearing: under `Spec-017 §Graph model — nodes, ports, and edges (SA-32)` two parallel branches of one run may park concurrently against different provider accounts with different reset boundaries, and a run-level schedule or fold key could hold only one of them — delaying or stranding the sibling and folding two distinct outages into one record. The table is already a **projection** under the SA-25 split (row 4 of the hierarchy above), and all four values are carried by the suspension event that produced them — `parkCause`, the armed `autoResumeAt`, and the optional `parkAttentionKey` all ride the `workflow.phase_suspended` payload — so the byte-equal `ProjectionRebuild` of I-017-10 holds with no exception and no schedule or fold key survives a rebuild the log does not contain. Two partial indexes back the boot sweep and the fold read: one on `workflow_phase_states(auto_resume_at)` where non-null, one on `workflow_phase_states(park_attention_key)` where non-null — both narrow by construction, since a parked phase is a small minority of rows, and both stay the bare non-null form because the per-row CHECK already confines both columns to `state = 'suspended'`. That CHECK — `state = 'suspended' OR (auto_resume_at IS NULL AND park_attention_key IS NULL)` — makes the **phase-exit half** of SA-40's clear-on-exit rule structural rather than a code convention: SQLite enforces CHECKs per statement, so the same UPDATE that moves a phase out of `suspended` must null both live columns. It is deliberately stronger than the terminal-status-only form the original `workflow_runs` placement could express, because the two cases that blocked a `suspended`-scoped CHECK there evaporate per-phase — a parallel sibling's park is its own row, and a schedule fire that re-checked and then failed to transition leaves the phase `suspended`, where an armed value is exactly legal. The run-cancel half cannot be DDL-enforced (run status lives in `workflow_runs` and a SQLite CHECK cannot cross tables), so SA-42's cancel clears the two live columns in the cancel's own unit of work — code-enforced and failure-injection-tested at T5.11 — while the park **record** columns carry no such coupling by design: `park_reason` and `park_cause` survive resume and cancellation untouched under SA-42, so liveness is read from run status plus phase `state`, never from the presence of a park reason. **The nine-table census is unchanged**, and no truth table is touched.
- **The engine event record is not a SQLite table (SA-43).** It is newline-delimited JSON on the Plan-020-owned bounded-retention diagnostic tier, so it adds no row to the nine-table census, no write to the Plan-015 writer worker, and no write amplification to the canonical event path — the reason the always-on posture is affordable at all. Plan-017 writes records and correlates them by `workflowRunId` / `phaseRunId` / `attemptNumber` / a monotonic per-run sequence; Plan-020 owns the bucket, its TTL, and its shred-path membership (`CP-017-9`).

## Implementation Steps

- Contracts: See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed schemas this plan consumes.

1. Define workflow-definition, version, phase-state, gate, and definition-read contracts in shared packages.
   - Full type hierarchy: `WorkflowDefinition`, `WorkflowVersion`, `WorkflowPhaseDefinition`, `WorkflowRun`, `WorkflowPhaseRun`, `PhaseOutput`, `WorkflowGateResolution`, `ParallelJoinState`.
   - All 4 gate types: `auto-continue`, `quality-checks`, `human-approval`, `done`.
   - Entity separation: `WorkflowPhaseId` (the logical phase in the definition) vs `PhaseRunId` (one specific execution instance, which also anchors the OWN channel 1:1 per SA-6). `PhaseRunId` is **derived, never randomly minted**: every bit is a function of `BLAKE3(workflowRunId || phaseDefinitionId || attemptNumber)` per [Spec-017 §Deterministic identity (SA-21)](../specs/017-workflow-authoring-and-execution.md#deterministic-identity-sa-21). It is therefore **not a ULID** — a ULID's leading 48 bits are a millisecond timestamp, which that preimage cannot produce, so the pre-audit "ULID" wording asserted determinism and a clock at once (A-017-10, Tier-8 audit). Treat it as a derived opaque identifier: the digest's text rendering is not yet ratified and is carried as an entry in `Spec-017 §Open Questions`, so build the derivation behind a single helper (T1.1) that every call site goes through, and do not encode a rendering assumption anywhere else. The storage column is `TEXT` under every candidate rendering, so no schema work waits on the ruling.

## Rollback Or Fallback

- If parallel execution or gate-chain writer regresses, disable parallel blocks and restrict to sequential `single-agent` + `automated` — the engine still satisfies C-1…C-7 for V1 partial rollout.
- If the `human_phase_form_state` daemon-side fallback is needed before V1.x, the empty table already ships, so enabling it requires only a writer path and the `workflow.humanFormDraftSave` handler — no migration.
- If the durable auto-resume schedule misbehaves, the fallback is the **unscheduled park**, which is already a first-class shipped state: stop arming `auto_resume_at` and every parked run stays visible, cancellable, and manually resumable with its stated cause. Recognition, the park itself, and cancellability are independent of the scheduler, so this degrades pacing without losing the park. The four columns stay in place — a nullable column that nothing writes costs nothing and avoids a down-migration.
- If the engine event record proves too costly, the fallback is **bounded recording, never no recording**: shed the high-frequency record classes first — ready-set ticks and gate evaluations, the classes that dominate volume — while retaining parks, schedule arming and fires, refusals, and the dispatch-intent/outcome pairs, so the records that exist precisely for the unreproducible moments survive the cost trim. The no-op writer is reserved for the one case T5.13 already requires it: bucket unavailability, where failing a run over a diagnostic sink would invert the record's non-canonical rank (I-017-22). Neither arm is a disable path — I-017-22 admits no flag that turns the record off, and a cost-motivated off switch would recreate exactly the there-was-no-second-chance blindness the always-on posture exists to avoid.

## Risks And Blockers

- Write amplification under pathological `progressed` heartbeat floods. **Named calibration criterion (A-017-24):** the nightly load category (Phase 4, T4.2) records per-workflow write volume against the [Local SQLite Schema §Workflow Tables](../architecture/schemas/local-sqlite-schema.md#workflow-tables-plan-017) estimate of ~42 KB / 110 writes per 10-phase workflow; a sustained nightly reading above **2× that estimate** is the trigger to add an executor rate-limit, and until it fires no rate-limit ships. The trigger is a threshold on an already-collected measurement, not a scheduled revisit.
- Per-run gate-chain verification cost scales linearly (~1 ms/row) — acceptable for operator-triggered audit; not in the hot path (T5.2 asserts the linearity and the out-of-hot-path placement).
- Non-determinism in replay if driver adapters leak wall-clock or random seed state — Plan-015 runtime-binding resume is the guard, and T5.1's replay-determinism battery (SA-31, asserting no `DeterminismViolationError` and a `deepEqual` final state) is the regression.
- **Error vocabulary gap carried, not closed (A-017-15).** `error-contracts.md §Workflow` defines **ten** codes for a surface with at least **twenty-two** refusal points (nine at the audit, four from the visual-builder amendment, one from the explicit-topology fields, one from the `shared`-scope operator-authorization boundary, one — `workflow.start_denied` — landed by the chat-start amendment as the owed extension's first entry, and three from the workflow-hardening amendment's SA-41 repair path, enumerated identically in `## API And Transport Changes`: a re-pin against a run that is not parked, one requested while any of the run's attempts is still in flight (the resuming phase continuing one rather than entering fresh, or a parked parallel sibling holding one — SA-41's run-wide boundary), and one whose target version cannot account for the phases the run already completed — the omitted phase id and the unreachable topology being one refusal point, since SA-41 states they are the same failure — and three from the 2026-08-18 park-surface and operator-controls amendment's SA-45 path: a Cedar-denied operator control, a cancel of a run that already reached `completed` or `failed`, and a resume of a run that is not parked). **The park and pacing surface adds none of its own** — SA-42 makes a parked run cancellable without precondition, so cancellation has no refusal to name — and that claim is scoped to the pacing rules, not to the operator surface that reaches them: the three SA-45 points are the operator surface's, minted when it landed. That file is outside this plan's write scope, so the extension is owed there and named in `## API And Transport Changes`; no Plan-017 task mints a code. Two slices have since landed typed: the SA-41 repair codes at the workflow-hardening amendment's 2026-08-17 review round (`workflow.repair_not_parked`, `workflow.repair_attempt_in_flight`, `workflow.repair_version_unaccountable`) and the SA-45 operator-control codes at the 2026-08-18 amendment (`workflow.control_denied`, `workflow.run_not_cancellable`, `workflow.resume_not_parked`) — **seven of the twenty-two** points now carry codes, `workflow.start_denied` included — so T5.12 and T5.14 both ship typed with no residual dependency on the extension. The remaining **fifteen** refusal points still cannot ship typed until it lands; that number is unmoved by the 2026-08-18 growth because all three new points arrived with their codes in the same diff. Tracked as a blocker on Phases 2, 4, and 5 rather than as a task.
- **The park's typed carrier now exists, and this plan still will not fake one (CP-017-10).** Every rule in `Spec-017 §Provider-limit pacing and durable resumption (SA-40)` hangs off a driver signal that Plan-005 shipped on 2026-08-18 (`I-005-6`, T3.16), and C-19 forbids the stand-in it replaced — matching provider message text. The pitfall survives the carrier's arrival rather than retiring with it, because the temptation changes shape rather than disappearing: the signal is deliberately **silent** on providers and shapes it cannot name, so a driver that observes no usage limit emits nothing, and "nothing" must be read as _not known to be limited_, never as _known not to be limited_. Widening recognition to cover that silence — by message text, exit code, or bare HTTP status — is the same failure the invariant was written against, and it fails the same way: a matcher that silently stops matching converts a park back into a burned ladder with no signal that anything changed.
- **The park's operator control surface — residual 2026-08-16, closed 2026-08-18.** The workflow-hardening amendment shipped `Spec-017 §Park integrity and cancellability (SA-42)`'s cancellability and repair as engine state-machine rules while the wire registry carried no run-cancel, run-resume, or re-pin operation and the taxonomy carried no run-cancelled event type — both predating that amendment, since the `cancelled` run status had had no named producer from the day it was declared. The gap was recorded as a residual rather than left as a build-time discovery, then tracked as [BL-151](../archive/backlog-archive.md), and the park-surface and operator-controls amendment closed it: T5.14 ships the two operations and `workflow.cancelled`, T5.15 the client verbs, and BL-151 is `completed`. **The constraint the residual fixed in advance held exactly as written** — the operation set and the run-cancelled event minted **together**, so a cancelled run's status and its cleared live park columns are a function of the log (SA-25) rather than surviving only in a projection a rebuild would overwrite (I-017-25). What the closure cost, stated rather than elided: the census this plan's 2026-08-16 amendment deliberately held still did move — registry eleven → thirteen, taxonomy 23 → 24 — which is why the closure rode its own dated amendment with its own re-derivations rather than being folded into the one that named the residual.
- **The durable park write must not ride the provider event delivery path (implementation constraint on T2.5 / T2.6).** The refusal that triggers a park arrives on the driver's event stream, and the natural spelling — performing the park's durable write and the schedule's arming inline on that delivery — deadlocks: the writing path ends up waiting on a response that can only arrive through the stream it is itself blocking. The campaign's surveyed reference runtime (2026-08-12 parity survey) hit this shape twice, in independent places, and settled on the same rule both times — detach synchronously on the delivery path, then do the durable park and schedule writes off it. T2.5 and T2.6 build to that rule, and the regression is an ordering test: a park must complete while the driver's stream is still being consumed. The split leaves a crash interval — the daemon dying after the handler detaches but before the off-path park write commits — and its closure is the refusal's **reproducibility**, not a durable inbox: a spent account keeps refusing, so the restart's ordinary mid-phase resume (T2.1) re-dispatches the same attempt and either receives a fresh typed refusal and parks then — no attempt consumed, no ladder burned, per the park path's own rules — or, where the account reset during the downtime, simply proceeds, the park never having been needed. T2.5's crash-injection test pins that convergence, so SA-40's durability never rests on an in-memory signal surviving a crash.
