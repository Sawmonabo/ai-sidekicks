## Goal

Implement the two places a project session works in — a worktree of its own by default, or the project's checkout — plus the worktree lifecycle: creation, moving between trees, setup, removal, keeping a removed tree and putting it back, and the turn snapshots taken where a session works.

## Scope

This plan covers worktree creation at the path and on the branch the create function names, moving a session between trees, the setup card's stages, worktree removal and the kept-worktree store, lifecycle projection, the background fetch and the working-folder watch, run-setup execution-root binding, and fallback handling.

## Non-Goals

- PR preparation
- Diff attribution logic
- Non-repo directory execution semantics
- Running the repository's own setup scripts during worktree preparation (the project's own recorded setup steps run in the setup card, T3.10)

## Preconditions

Target paths below assume the implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

Plan-006 T-006-2B-3 EXTENDs `packages/runtime-daemon/src/git/turn-snapshot/service.ts` INSIDE Phase 2B — shipped together with the CP-006-8/CP-007-12 leg, because the nested shape becomes reachable exactly when `bound-root` re-roots at `boundRoot` — normalizing capture's execution-root input to the enclosing working-tree top level at service entry (one normalization site, so every capture addresses the whole tree the run works in), with [Spec-008 §Turn-Boundary Snapshots](../specs/008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)' applicability bullet recording the rule in the same swap. **Transport of the normalized root.** The value is derived while the tree exists and reaches the callee down a five-link carrier chain, each link a write the previous link's tree existence justifies: (1) bind-time derivation into `workspaces.metadata.checkoutRoot`; (2) rewrite of that key when a preparation installs a new execution root; (3) capture into `run_execution_contexts.checkout_root` by the T3.2 run-setup gate at context creation, read from `workspaces.metadata.checkoutRoot`; (4) supply by the Plan-002 caller as the CP-007-11 `checkoutRoot` parameter, read from the same run-context row it already reads `execution_root` from; (5) receipt by the callee. Capture re-verifies the supplied value against the live tree (it runs while the tree exists) and fails typed on disagreement. Link (3) is what makes the chain durable rather than merely persistent: like `git_common_dir`, the value is snapshotted per run at context creation, so it survives a later preparation of the workspace's root — the callee is never asked to read a `workspaces` row, let alone walk a filesystem path, to find out where the tree top is. **CP-007-11's pure-callee contract is therefore unchanged in the strict sense, not merely the compatible one:** the callee gains an input, not a lookup — it reads no `workspaces` row, performs no upward filesystem walk to normalize, and holds no dependency on the execution root still existing; the growth is confined to CP-007-11's caller-resolved enumeration. The normalization carries a concurrency corollary: captures of one normalized checkout run one at a time, across every session working in it ([Spec-008 §Turn-Boundary Snapshots](../specs/008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)), so a whole-tree capture never interleaves with another capture of the same tree; runs themselves are never held, and each session's undo is kept apart by the checkpoint store's per-session record of edits and command windows. **Direction:** Provide to [Plan-006](./006-repo-attachment-and-workspace-binding.md) (reciprocal CP-006-9). **Tasks:** T5.1 (shipped callee surface; the EXTEND executes under Plan-006 T-006-2B-3, on the `checkout_root` carrier T3.2 captures).
- **CP-007-14 — The capture half is extended by the checkpoint store and by workflow runs.** This plan owns `git/turn-snapshot/service.ts`. The checkpoint store ([Plan-012](./012-persistence-and-recovery.md) T12.6 and T12.7) extends its capture half with the owner's capture folder as a parameter — objects written with `GIT_OBJECT_DIRECTORY` into that folder from the owner's kept scratch index, refs written inside it, base pins under `refs/sidekicks/base/<owner id>/` — and adds the per-command captures and the public snapshot list beside the retention half's private listing. [Plan-014](./014-workflow-authoring-and-execution.md) extends it for a workflow run's snapshot points in the run's own capture folder, keyed by the workflow run's id (`…/epoch-<E>/start`, `…/pause-<N>`, `…/end`), the ref-name check admitting the point names beside `turn-<N>`. A snapshot names a point, and every file restore reads the checkpoint store. **Direction:** Provide to [Plan-012](./012-persistence-and-recovery.md) and [Plan-014](./014-workflow-authoring-and-execution.md). **Tasks:** T5.1 (the capture half they extend).

## Design Decisions

- **D-007-1 — Contract file is `packages/contracts/src/worktree/lifecycle.ts`**: the file's dominant content is the worktree lifecycle domain; one-file-per-domain.
- **D-007-2 — Consolidated wire block.** The worktree request/response pairs + the `BranchContextId` and `RemovedWorktreeId` brands defined in api-payload-contracts.md §Plan-007 (brands declared in-block for cite stability).
- **D-007-3 — Method namespace is `repo.*`** (`repo.executionRootPrepare` with `carryUncommitted`, `repo.worktreeStatusRead` keyed by project, `repo.worktreeRetire {worktreeId, discard}`, `repo.removedWorktreeList {projectId?}`, `repo.worktreeRestore {removedWorktreeId}`, `repo.removedWorktreeDelete {removedWorktreeId}`, `repo.worktreeSetupSubscribe`, `repo.worktreeSetupRetry`, `repo.branchList`, `repo.workingTreeSubscribe`), plus `session.setWorkingFolder` on the session root, whose pending intent sits on the session row. A `worktree.*` method root was considered and rejected: the namespace-root enumeration admits `repo` and no `worktree` root; mounts, workspaces and worktrees are one repo aggregate. There is no mode select (a session's place is chosen in `session.create` or `repo.workspaceBind`) and no reuse check (its figures ride the status read). Imperative method strings stay disjoint-by-form from the past-participle Spec-005 event names.
- **D-007-4 — Error vocabulary.** §Worktree: `worktree.not_found` 404, `worktree.create_failed` 500, `worktree.branch_collision` 409, `worktree.retire_conflict` 409 (with `reason: root_busy | has_changes`, and the current risks for `has_changes`), and the put-back refusals (`reason`: the project is no longer attached, the repository is no longer at its path, a worktree named `<name>-restored` already exists). §Workspace extension rows: `workspace.branch_name_required` 400 (D-007-18), `workspace.execution_root_unresolved` 409. Deliberately NO `worktree.unsupported`: a worktree that cannot be made IS `worktree.create_failed` (500, matching `workspace.preparation_failed`'s class).
- **D-007-5 — Persistence model (tables: `worktrees`, `branch_contexts`, `run_execution_contexts`, `removed_worktrees`; DDL in local-sqlite-schema.md, one schema per database).** `worktrees` carries `created_by_session_id` NOT NULL + `created_by_run_id` nullable (provenance; session/run ids event-sourced, no FK) + `cleaned_at` + the partial-unique `idx_worktrees_active_branch ON (repo_mount_id, branch_name) WHERE state NOT IN ('retired','failed')` — git-faithful: a `merged` checkout still holds its branch; `failed` creations never materialized one. `branch_contexts` is workspace-anchored (`workspace_id` NOT NULL) with a nullable `worktree_id`, and the partial-unique binding index `idx_branch_contexts_worktree_workspace ON (worktree_id, workspace_id) WHERE worktree_id IS NOT NULL` — one binding row per (workspace, worktree) per D-007-15's upsert semantics, so the worktree-keyed `BranchContextRead` resolves exactly one row on the (worktreeId, workspaceId) pair. `run_execution_contexts` (NEW) is the per-run execution binding: `run_id` PK (event-sourced, no FK), `session_id`, `workspace_id`, `execution_mode`, `execution_root`, `checkout_root` NOT NULL (the enclosing working tree's top level for that `execution_root`, captured at context creation by the T3.2 gate from `workspaces.metadata.checkoutRoot`; it is the durable normalized root CP-007-13's capture leg consumes and the fourth link of that obligation's carrier chain, supplied onward as a CP-007-11 caller-resolved parameter; T3.2 is its only writer), `git_common_dir` NOT NULL (the `git rev-parse --git-common-dir` absolute path captured at context creation — the surviving canonical git dir: the base pins under `refs/sidekicks/base/<owner id>/` are removed through it and its objects are the alternate a capture is read with, so pin removal never goes through a possibly-retired `execution_root`; `provisioned-worktree` resolves to the main repo's git dir, `bound-root` to the bound checkout's own), optional `worktree_id`/`branch_context_id`, `created_at`, `released_at`, and a mode-conditional CHECK binding id presence to `execution_mode` (`provisioned-worktree` ⇒ `worktree_id` set; `bound-root` ⇒ `worktree_id` NULL; both carry `branch_context_id`). `checkout_root` and `git_common_dir` are the columns deliberately held OUTSIDE that mode-conditional CHECK: both are captured unconditionally, in either place, because their consumers are place-agnostic — the one-at-a-time capture per checkout and the I-007-14 run gate apply to every repo-bound run. `removed_worktrees` holds one row per kept worktree: `id`, `mount_id`, `project_id`, `worktree_name`, `original_path` (where `Put back` returns it), `branch`, `head_commit`, `removed_at`, `size_bytes` and `size_read_at`, the size read once after the discard, off its path; its pins live as refs in the repository, never as a column.
- **D-007-6 — Worktree placement + trust envelope.** Daemon-created worktrees live under the daemon's own execution-roots directory, never inside the attached checkout — at `~/.ai-sidekicks/worktrees/<project>/<session-short-id>-<task-slug>/`, flat, `<project>` being the slug fixed at attach and never the display name, on the branch `sidekicks/<session-short-id>/<task-slug>` under the default pattern; the folder is flat while the branch keeps its three parts, because git names a worktree's record after the folder's last part. One daemon function names the folder and the branch, creates the tree, and answers the create form's fixed parts, suggested tail and path hint ([Spec-008 §Required Behavior](../specs/008-worktree-lifecycle-and-execution-modes.md#required-behavior)). Kept worktrees sit in the project's `.removed/` folder under the same execution-roots directory, so the discard is one rename on one volume. Worktrees are in-envelope by construction ([Spec-007 §Local Trust Envelope (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#local-trust-envelope-v1-definition) daemon-created-roots clause). The mount's canonical root hosts the `git -C <canonicalRoot> worktree add <rootPath> …`-shaped invocations only.
- **D-007-7 — Collision policy is provenance-split.** Caller-supplied `branchName` colliding with a live checkout → typed `worktree.branch_collision` refusal (user intent never adapted). Daemon-derived default name colliding → first-free ordinal suffix (`-2`, `-3`, …), persisted + reported verbatim. Service parameter `onCollision: 'refuse' | 'suffix'`: wire prepares always pass `refuse`; the run-setup gate's derived-name path passes `suffix`. The partial-unique index arbitrates races (insert-retry loop). Collision never implies implicit reuse.
- **D-007-8 — Base-ref policy.** Worktree base defaults to the mount's current HEAD branch; `baseRef?` overrides explicitly; a detached-HEAD mount with no explicit base ref → typed refusal (`worktree.create_failed` with detail), never a guess.
- **D-007-9 — `bound-root` is bind-only.** Prepare binds the BOUND checkout — read at `workspaces.metadata.boundRoot`, the main checkout or a linked worktree (CP-007-12) — on the branch it is on, and the daemon never runs `git checkout`/`switch`/`branch` in the bound checkout OR the main checkout. A branch changed there outside the console is written back to the session's record (`session.branch_changed`, T3.10), never refused. Verification carries a linked-worktree assertion: the `bound-root` prepare fixture binds a linked worktree and asserts prepare mutates NEITHER tree — bound worktree and main checkout byte-identical before and after — so an implementation that changed the bound linked checkout cannot pass the immutability checks.
- **D-007-10 — The repository's own git config.** Every git invocation the service makes runs via `execFile` argv-only (no shell) and sets no `core.hooksPath` or `core.fsmonitor` override, so the repository's own hooks and its own fsmonitor run as they do on the person's git calls; the `Agent-Run` trailer's hooks folder on git older than 2.54, which forwards every hook to the repository's own, is a separate mechanism ([Spec-009 §Required Behavior](../specs/009-gitflow-pr-and-diff-attribution.md#required-behavior)).
- **D-007-11 — No new event types.** This plan adds no rows to the Spec-005 registry: no `worktree.failed` event — the `worktree.*` rows Spec-005 already enumerates are union-registered by T1.1 per CP-007-4. Rationale: worktree rows are table-sourced (not rebuilt from events); a failed setup step is the setup card's own stream (`repo.worktreeSetupSubscribe`), and a worktree that could not be made is evented as `workspace.stale` with `metadata.lastError` (single-incident-single-event); failed rows stay queryable via `repo.worktreeStatusRead`. The deliberate carve-out is pinned by a T2.1 regression test.
- **D-007-12 — Event-transition mapping.** Row creation → `worktree.created`; `creating -> ready` → `worktree.ready`; `-> dirty` → `worktree.dirty`; `-> merged` → `worktree.merged`; `-> retired` → `worktree.retired`; `-> failed` → none (the coupled `failRootPreparation` emits `workspace.stale`). Emission is transactional with the row write; the payload is `WorktreeLifecyclePayloadSchema` — Plan-006's lifecycle payload shape instantiated over `WorktreeStateSchema` (`worktreeId` populated).
- **D-007-13 — Cleanup sweep.** The service's one scheduler drives: (a) worktrees whose mount is `detached` (non-terminal states → retired, events emitted, metadata preserved), their folders left on disk as they are, because detaching a project touches nothing on disk; (b) disk removal for rows `repo.worktreeRetire` retired and not yet cleaned, idempotent, stamping `cleaned_at`. The sweep skips a mount whose origin is `managed` — a chat's workspace goes only with its session's purge, where the service's one purge, `daemon.retentionPurge` (`Delete old data`), deletes it through `ManagedWorkspaceService.delete` — and never touches a kept worktree, which goes only with the person's `Delete now`.
- **D-007-14 — The place is chosen at binding; prepare materializes.** A session's place is chosen in `session.create`'s `binding` or in `repo.workspaceBind` on convert ([Spec-007 §Interfaces And Contracts](../specs/007-repo-attachment-and-workspace-binding.md#interfaces-and-contracts)); root materialization happens at `repo.executionRootPrepare` or the run-setup gate. `Create and move here` is one `repo.executionRootPrepare` on the session's own workspace, which prepares it again in place; moving into an existing tree is `session.setWorkingFolder`, applied at once while idle and at the run boundary mid-turn. A prepare on a `stale` workspace after repair is the repair path.
- **D-007-15 — Moving into a tree is the person's pick.** `session.setWorkingFolder` names the tree; any worktree git lists for the repository is accepted, one the person made binding as an existing checkout that is never stamped as one this daemon provisioned, and the switcher's row has already shown its uncommitted count and the sessions using it. Moving into a tree preserves the tree's existing branch-context row when it already belongs to the moving workspace; otherwise it upserts the workspace's own `branch_contexts` row — a first binding inserts a NEW row scoped to that workspace (branch values carried over from the tree's row, which is left untouched as history); a workspace re-binding a worktree it historically bound refreshes its existing pair row in place — so exactly one row exists per (workspace, worktree) (the partial-unique `idx_branch_contexts_worktree_workspace`).
- **D-007-16 — Run-setup binding.** Plan-007's gate (registered on the Plan-002 T3.9 seam per CP-007-8) implements `assertRunReady`: read the run's workspace from the session the run belongs to → `assertWritable` (lawfully skipped when the workspace already sits `preparing` — the open-bracket scoping of I-007-12 / CP-007-3) → materialize/bind the root (branch name per the pattern, its tail from the session's title or, before the session has one, its provisional title, `run-<run-short-id>` only when no usable words remain; `onCollision: 'suffix'`) → write the `run_execution_contexts` row. `onRunTerminal` stamps `released_at`. Refusal parks the run in `starting` (`workspace.execution_root_unresolved` wrapping the underlying typed cause). Nothing holds the workspace: another session's run may start in the same folder.
- **D-007-17 — Status read + stale-diagnostic surface.** `repo.worktreeStatusRead`, keyed by project, returns the repository-root row and each worktree with its base, ahead and behind figures, uncommitted count, the sessions using it and `countsAsOf`, plus the create form's fixed parts, suggested tail and path hint from the one create function. The owning workspace's `lastError` rides `repo.mountRead`'s rows of what uses the mount ([Plan-006](./006-repo-attachment-and-workspace-binding.md) D-006-1).
- **D-007-18 — Wire prepares carry the branch; the slug rule is gate-only.** The Spec-008 naming rule ([Spec-008 §Branch, Base And Preparation Rules](../specs/008-worktree-lifecycle-and-execution-modes.md#branch-base-and-preparation-rules)) fills the branch pattern with a tail derived from the session title, or from its provisional title (the first words of the first message) through the one function the session's naming uses when the session has no title yet, and falls back to `run-<run-short-id>` only when no usable words remain, which happens only on the run-setup gate path (D-007-16); on the wire, the create form sends the name the status read suggested (D-007-17). Wire-initiated prepares are pre-run by definition and carry no derivation seed: a `provisioned-worktree` `repo.executionRootPrepare` carrying neither `branchName` nor a service-side `runId` draws the typed `workspace.branch_name_required` refusal (400) before any git call — `bound-root` prepares ignore the field. `ExecutionRootPrepareRequest.branchName?` optionality is therefore mode-conditional requiredness enforced service-side, not schema-optional-everywhere. Below T2.3 the worktree service takes `branchName` required (`worktree-service.create` holds no derivation inputs); T2.3 resolves the name first (pass-through when supplied; the `run-<short-8>` fallback via the T2.2 helper when only `runId` arrived) — the title-derived rule, the provisional title included, fires at the gate for a tree the gate makes itself.
- **D-007-19 — The warm step is one `git status` plus the watches.** The setup card's third stage runs one `git status` in the new tree while nothing else runs, then starts the tree's watches (the working-folder watch and the git-folder watch), and the `@` file index only if the daemon keeps it live; the ship facts and the branch list cache nothing, so the warm step reads neither early.
- **D-007-20 — Branch names follow the person's pattern.** The create function fills the machine's `Branch names` pattern (`sidekicks/{session}/{title}` by default) or the project's own: `{title}` exactly once, `{session}` optional. The tail is shaped as typed (lowercase; characters outside `a-z 0-9 . _ -` become hyphens; a leading `.`, `_` or `-` dropped); a derived tail, from the session title or before it has one from its provisional title (the first words of the first message, through the one function the session's naming uses), then has repeated `-` and `.` collapsed, a trailing `-`, `.` or `.lock` trimmed, and is cut at a word break near 40 characters, with `run-<run-short-id>` only when no usable words remain; a branch keeps its name when the title changes. The form shows the whole name under the field as `Will be created as <name>.` The whole name is checked by `git check-ref-format --branch` and against every branch in the repository, prefixes included, and a refusal's line under the field is git's error line exactly as git prints it, `fatal:` included (`fatal: 'x y' is not a valid branch name`), with none of git's `hint:` lines. The daemon knows the branches it made by its worktree records, never by their names.
- **D-007-21 — Removal keeps what it discards.** `repo.worktreeRetire {worktreeId, discard: true}` first ends the tree's Terminal pane shells and project processes through their owners and unlocks a locked record, then copies git's per-worktree record (all of `<git common folder>/worktrees/<name>/` but `gitdir` and `commondir`), packs the objects the kept index names that HEAD's tree does not, keeps the LFS objects that staged pointers name in the kept folder's `lfs-objects/`, pins every commit git's saved worktree state names (`ORIG_HEAD`; `MERGE_HEAD` in a merge; in a rebase the replayed HEAD, `onto` and `orig-head`) as up to five refs under `refs/sidekicks/removed/<id>/`, moves the folder whole into `worktrees/<project>/.removed/<name>-<removed id>/` by one rename — or, where the rename would cross a volume, copies it (`cp -c -R` for APFS clones, a real copy elsewhere) and deletes the original only once the copy is complete — and prunes; a rename the operating system refuses because a program outside the app holds a file open refuses the discard with `worktree.retire_folder_held` and removes nothing; the result carries `kept: {removedWorktreeId}`. `Put back` returns the tree on its own branch when that branch still points at the recorded commit (in a rebase, the recorded `orig-head`) and no other worktree holds it, otherwise on `<branch>-restored`; it moves the entries, the record, the pack and the LFS objects back, refreshes the index and deletes the pins. Budget, on a 54,011-entry, 829 MB worktree: the discard press adds at most 250 ms and `Put back` takes at most 200 ms; no process is added.
- **D-007-22 — Worktrees across the WSL boundary.** A worktree whose repository or folder is on the other side's disk is created with `git worktree add --lock`, or locked with `git worktree lock` after a move, so the other side's git never prunes it; the discard unlocks it before its own prune. When the service moves between Windows and the distribution, it runs `git worktree repair` from the main worktree with each linked worktree's new path after the first good start, recording each repair with the old path so a failed move can put it back.

## Risks And Blockers

- Branch naming collisions — mitigated by D-007-7 (provenance-split policy + index-arbitrated retry)
- Git edge cases on repos with unusual worktree support — surface as typed `worktree.create_failed`, never substitution (I-007-7)
- Kept worktrees hold disk until the person deletes them — by design; the runtime settings page shows each one's size beside `Delete now`
- Repositories with mandatory bootstrap steps need explicit follow-on setup flows ([Spec-008 §Fallback Behavior](../specs/008-worktree-lifecycle-and-execution-modes.md#fallback-behavior)) — out of scope here by design
- Registry regex conformance and the typed-error projection are Plan-005-owned Phase-3 preconditions; if they slip, Phases 1–2 still land
- A rollback's conversation leg is a provider-side rewind, and it is Plan-003's to own on both providers: each cuts in place on the session or thread the run already holds — Codex's `thread/revert {threadId, beforeTurnId}` and Claude Code's `rewind_conversation {target_message_uuid, interrupt_if_running}` control request ([`codex.md`](../reference/provider-wire/codex.md), [`claude.md`](../reference/provider-wire/claude.md), [Spec-004 §Per-Driver Capability Matrix](../specs/004-provider-driver-contract-and-capabilities.md#per-driver-capability-matrix)) — so no second thread or session is minted, no live runtime binding is re-pointed, and nothing about this plan's snapshot legs depends on either. Neither verb touches a file, so the files come from the daemon's own per-session file checkpoint store ([Spec-013 §Required Behavior](../specs/013-persistence-and-recovery.md#required-behavior)) and a snapshot only names the point to return to. Across a compaction the two differ: Codex's `thread/revert` holds past a compaction and needs a conversation that was not started ephemeral, while Claude Code refuses a point before an automatic compaction with `target_not_found`, so the daemon reaches that point by forking at the last assistant message before it and restarting on the fork, inside the daemon; `rewind_conversation` needs `last_seen_user_message_uuid` set to the newest prompt (else `stale_target`), and its refusal arrives as `subtype: "success"` with `rewound: false` ([Spec-003 §Driver-Level Rollback Mechanics](../specs/003-queue-steer-pause-resume.md#driver-level-rollback-mechanics)); re-verify each verb against the then-installed provider binary before any code coordinating it lands, per [ADR-016](../decisions/016-shared-event-sourcing-scope.md)
- Field evidence against per-turn git checkpointing, and why neither ground transfers: a surveyed reference runtime shipped per-message git checkpointing (hidden snapshot refs plus a revert that restored files) and later removed it, on two stated grounds — snapshot refs polluting ordinary repo tooling, and a file-restore path users never took. Ref pollution is foreclosed here by construction rather than by discipline: I-007-17 confines every ref to the owner's capture folder under `refs/sidekicks/runs/<runId>/epoch-<E>/turn-<N>`, outside the person's repository and invisible to branch history, pull requests, and diff attribution; I-007-18 makes each write create-only per epoch, so no ref is ever repointed; and T5.2 removes a run's refs with the run or its session (ref ops routed through `run_execution_contexts.git_common_dir` so a run's refs stay reclaimable after its execution root is gone). The never-used ground is a different product shape, not a weaker version of this one: there, checkpointing was an optional per-message affordance offered to users who can run git themselves, so non-use is a real signal; here the per-turn snapshot is the daemon's own record of the point a turn ended at, which a restore aimed at a named snapshot of the session resolves against while the files themselves come from the file checkpoint store ([Spec-013 §Required Behavior](../specs/013-persistence-and-recovery.md#required-behavior), [Spec-003 §Driver-Level Rollback Mechanics](../specs/003-queue-steer-pause-resume.md#driver-level-rollback-mechanics)) — so dropping it would not retire an unused affordance, it would leave a session unable to name the points it can return to

## References

- [RFC 9562 §5.7 — UUID Version 7](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7) — the field layout behind the short-id rule — `<session-short-id>` and `<run-short-id>` are the **last** 8 hex characters of their UUIDs: a v7 id is a 48-bit `unix_ts_ms` millisecond timestamp, the 4-bit `ver`, 12 bits of `rand_a`, the 2-bit `var`, and 62 bits of `rand_b`, so the first 8 hex characters are timestamp bits shared by every id minted in one 65,536 ms window and the last 8 are random bits.
