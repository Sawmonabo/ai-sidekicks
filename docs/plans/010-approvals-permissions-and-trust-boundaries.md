## Goal

Implement the canonical approval, remembered-grant, and permission-check model that governs local execution trust.

## Scope

This plan covers approval records, remembered grants, daemon-side permission checks, trust invalidation, and approval visibility projections — plus driver-ask normalization, execution-posture authorization with the content-addressed credential-policy artifact store, and the allow-listed spawn-environment boundary.

## Non-Goals

- Identity-provider implementation details
- Notification routing for approval prompts
- Provider-specific permission UX beyond normalized capability requests
- Cross-node dispatch approval envelopes (Spec-022 — Plan-024; this plan provides the category enum only)

## Data And Storage Changes

- Add durable local `approval_requests`, `approval_resolutions`, and `remembered_approval_rules` storage plus invalidation hooks tied to runtime-node trust changes. See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) §Approval Tables for column definitions — the audited DDL there is the verbatim migration content (D-010-2).
- Serve pending and historical approval state from a daemon-local projection (SQL over the approval tables — D-010-6); no control-plane approval storage exists (ADR-017 Option B).
- Trust-evaluation inputs are derived at check time, never duplicated into a dedicated trust store (D-010-15; the B13 `credential_policy_artifacts` store below is not one — it persists cited credential-policy documents, not trust-evaluation inputs): node trust ← `node_trust_state.trust_level`; own-node determination ← the daemon's attach-binding owner-user identity (Plan-002); envelope roots ← Plan-007 `workspaces.fs_root` / Plan-008 `worktrees.fs_root` via `run_execution_contexts` (CP-010-9); unestablishable provenance → strict per-request approval ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).
- Add the content-addressed `credential_policy_artifacts` store: `sha256`-keyed rows persisting the RFC 8785 JCS-canonicalized credential-policy artifact document that `executionPosture.credentialPolicyRef` cites ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior) posture semantics). Rows persist **write-ahead** — before the first `run.running` posture stamp citing the ref, the ADR-019 spawn-intent ordering discipline — and are retained at least as long as any run event citing them — indefinitely in V1: compaction preserves the stub's posture object (ref included) and the Plan-020 crypto-shred clears `pii_payload` only, so no V1 path deletes a citing row, and growth stays bounded by content-addressing (one row per distinct effective policy, never per run). The deletion leg is T2.9's `pruneUnreferencedArtifacts`, invoked at the V1.1 `gdpr.sessionPurge` completion — the only operation that removes citing rows; Plan-020 reserves its stub in V1 — an explicit future consumer, never a V1 cleanup guarantee. See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) §Credential Policy Artifacts — the audited DDL there is the verbatim migration content (the T1.3 convention).

## Design Decisions

- **D-010-1 — Contracts file is `packages/contracts/src/approval.ts`** (single file, singular noun; replaces the pre-audit `approvals/` directory form): one-file-per-domain per the shipped `session.ts`/`event.ts`/`repo.ts`/`worktree.ts` convention; avoids firing the deferred subdirectory-convention call.
- **D-010-2 — Persistence model (3 tables; DDL verbatim in local-sqlite-schema.md §Approval Tables).** `approval_requests` carries `session_id` + `requested_by` NOT NULL (provenance; no FK targets — sessions are control-plane rows, runs are event-sourced), required `resource_descriptor` (JSON), nullable `ask_id` (the originating driver-ask association, set iff normalizer-minted), a unique partial index on `(run_id, ask_id)` so a normalizer retry or a replay re-mint collides instead of duplicating, 4-state CHECK incl. `canceled`, and `updated_at` (a cancellation settles on the row — no resolution row). There is no deadline column: a request waits until it is answered ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)). `approval_resolutions` carries `request_id` as PRIMARY KEY (the durable wire id `approvalRequestId` — enforces the 1:1 decision row, replaces the former minted `id` + unique per-request index, and keeps every projection column wire-derivable per I-010-9), `approver_id` NOT NULL, 2-value `decision` CHECK, `effective_scope` NOT NULL, and nullable `remembered_scope_kind`/`remembered_scope_pattern`. `remembered_approval_rules` carries grantor `user_id`, `session_id`, `node_id`, origin FK `created_from_request_id` (→ `approval_resolutions(request_id)`, the durable id carried on `approval.remembered`), `run_id` with CHECK `(scope_kind = 'run') = (run_id IS NOT NULL)`, explicit `scope_kind` enum, nullable `scope_pattern`, and the `revoked_at` ⇔ `invalidation_trigger` co-presence CHECK over the closed trigger set `{explicit, node_trust_change, session_end}`.
- **D-010-3 — Consolidated wire block.** Six request/response pairs + `RememberedRuleId` brand + `RememberedScope` + `InvalidationTrigger` + `ApprovalFlowEventPayload` defined in api-payload-contracts.md §Plan-010: create carries required `resourceDescriptor`; resolve carries optional `approver` + `effectiveScope?` + `rememberedScope?` and returns the recorded `approverId` + `effectiveScope`; the projection row carries `requestedBy`, `resourceDescriptor`, `updatedAt`, and the resolved quad (`resolvedAt`/`decision`/`approverId`/`effectiveScope`) present iff state ∈ {approved, rejected}; rule rows carry grantor, node, optional `runId`, and revocation metadata; the `ApprovalFlowEventPayload` carries the projection-rebuild fields (`requestedBy`/`resourceDescriptor` on `requested`, `approver`/`effectiveScope` on the resolution events, and the rule projection on `remembered` — grantor = `approver`, bound `nodeId`, binding = `rememberedScope`/`runId`, origin = `approvalRequestId`) so relayed or replayed events alone rebuild each daemon's projection rows, `remembered_approval_rules` included (D-010-6/D-010-7, I-010-9).
- **D-010-4 — Error vocabulary (§Approval, 7 rows).** `approval.not_found` 404, `approval.already_resolved` 409, `approval.request_canceled` 409 (new; non-colliding with the `approval.canceled` event), `approval.persistence_unavailable` 503 (fail-closed), `approval.rule_not_found` 404, `approval.rule_already_revoked` 409, and the eighth row `approval.policy_artifact_corrupt` 500 (T2.9's read-boundary content-address recompute failing closed; mirrored in §API And Transport Changes). Deliberate absence: no `approval.permission_denied` in V1 — the local IPC surface carries no caller principal, `PermissionCheck` denial is a normal `{allowed: false}` response, and minting a cross-node authorization code is Plan-024's call.
- **D-010-5 — Method registry: five strings on the new singular `approval` root** (`approval.requestCreate`, `approval.resolve`, `approval.projectionRead`, `approval.ruleList`, `approval.ruleRevoke`), registered in api-payload-contracts.md §Approval Method-Name Registry with the root added to the namespace-root enumeration. `PermissionCheck` registers NO wire method string: zero V1 wire consumers, and a wire preflight would invite stale-verdict (TOCTOU) authorization against the security gate. "Rule" (not "grant") is the operation vocabulary — matching `remembered_approval_rules`, `approval.rule_revoked`, and `RememberedRuleId`. Supersedes the pre-audit Spec-021 plural `approvals.listPending` gloss.
- **D-010-6 — Projection is daemon-only.** The pre-audit control-plane `approval-projection-service.ts` Target Area is struck: shared Postgres stores zero approval tables (ADR-017 anchors-only; shared-postgres-schema invariants), so a control-plane projection would violate the storage posture, not extend it. `approval-projection-service.ts` lands in Plan-010-owned `packages/runtime-daemon/src/approvals/`.
- **D-010-7 — Events-canonical; rows are projections.** `EventLogService.append` commit IS the [Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior) durability gate; row projection updates after; startup reconcile replays `approval_flow` events newer than the rows' high-water mark; a failed append surfaces `approval.persistence_unavailable` and the gated action does not proceed.
- **D-010-8 — `approval.canceled` is an additive durable event (6 `approval_flow` variants).** Emitted when `cancelPendingForRun` settles pending requests on run-terminal; [Spec-005 §Approval Flow (approval_flow)](../specs/005-session-event-taxonomy-and-audit-log.md#approval-flow-approval_flow) gains the row. A cancellation settles on the request row (`state` + `updated_at`) — never a resolution row. Explicit-over-derived: a projector-derived cancellation would leave the `approval_flow` audit timeline incomplete.
- **D-010-9 — V1 policy engine is `@cedar-policy/cedar-wasm` in-process (`preparsePolicySet` and `preparseSchema` once after signature verification, `statefulIsAuthorized` on every check; `isAuthorized` re-parses the policy text on every call and must not be used) over the build-embedded, signature-verified compiled policy set.** The verified artifact (as enforced in-process) is the canonical bytes of the compiled Cedar policy set + a detached signature under the operator release key with the daemon's pinned signing algorithm (Ed25519 default, ECDSA P-256 compliance fallback — [ADR-012 §Signing Algorithm](../decisions/012-cedar-approval-policy-engine.md#signing-algorithm)), verified against the pinned `OPERATOR_PUBLIC_KEY` on every daemon start BEFORE any `PermissionCheck`; verification failure → refuse to start (typed log `policy-artifact-signature-invalid`). Container-image signing remains the distribution pipeline's supply-chain layer; the compiled-policy-set verification above applies in **both** topologies (the shell-spawned desktop daemon where no image exists, and containerized/self-hosted daemon builds), and containerized daemons additionally refuse to start if the launched image cannot be verified against the pinned operator public key ([ADR-012 §Scope By Phase](../decisions/012-cedar-approval-policy-engine.md#scope-by-phase) — both topologies). YAML sources live at `packages/runtime-daemon/policies/default-policy.yaml`; `scripts/compile-policies.mjs` compiles them in the package build; content transcribes security-architecture §Permission Matrix + [Spec-010 §Default Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#default-behavior). Package name corrected from the pre-audit `@cedarpolicy/cedar-wasm` (nonexistent on npm — dependency-confusion hazard); version pin 4.11.x. **V1.1** (criterion-gated, ADR-012): (a) `policy-bundle-v{N}.cedar.tar.gz` build/sign/verify CLI surface (`sidekicks policy bundle build/sign/verify`), (b) daemon-side verifier with monotonic version counter and rollback rejection, (c) `ApprovalPolicyEngineUnavailable` recovery-status plumbing, (d) freshness-window timestamp enforcement — the V1→V1.1 delta is policy SOURCE only (embedded → runtime signed bundle); the evaluator does not change. Operational procedures: [Cedar Policy Signing And Rotation](../operations/cedar-policy-signing-and-rotation.md).
- **D-010-10 — Remembered-scope matching semantics.** `RememberedScope { kind: 'run' | 'session'; pattern?: string }`; `request_only` is expressed by OMITTING `rememberedScope`, never an enum member. Candidate set: unrevoked ∧ same `session_id` ∧ same `node_id` ∧ same `category` ∧ (kind = `session` ∨ (kind = `run` ∧ rule.run_id = request.runId)). Pattern absent → category-wide within that boundary; pattern present → category-derived semantics: path categories (`file_write`, `destructive_git`) = normalized-absolute-path prefix containment against the envelope roots; `network_access` = exact host equality (no wildcards in V1); all other categories = exact scope-token equality. The rule's `user_id` is written as the GRANTOR (D-010-3: grantor = `approver`) and serves as the audit key; the rule's **scope enum** (`RememberedScope.kind`) is run/session only, and `idx_remembered_rules_user(user_id, category)` indexes the grantor axis.
- **D-010-11 — Invalidation: on-next-use re-evaluation is the correctness mechanism.** The grant-match path re-validates every rule's preconditions at use time; the push seam — a synchronous `node_trust_state` transition hook — calls `revokeDependentRules` to shrink the live window and emit timely `approval.rule_revoked` events, but it is the audit/timeliness layer: only use-time re-validation satisfies revoke-before-next-use ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)). Unresolvable trust input → fail closed ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).
- **D-010-12 — Approver identity model.** Wire `approver?: UserId` is OPTIONAL and informational: absent on the local socket → the daemon records its node-owner user binding (the same attach-binding read as D-010-15's own-node determination); present → cross-checked (local: vs the owner binding; PASETO-authenticated surfaces: vs the verified `sub`) — mismatch → `auth.principal_mismatch`. `approval_resolutions.approver_id` stays NOT NULL (the RECORD is mandatory per [Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)); `ApprovalResolveResponse.approverId` returns the recorded server truth (AC-3 observable). The renderer never populates an approver identity. **Addressed principal.** A pending request raised by the composed gate is **addressed to the turn's effective principal** — the principal whose decision the pipeline awaits, and therefore the one recorded as `approver_id` on resolution. This decides who the pipeline asks and records, not how they are reached — notification transport for approval prompts stays out of scope per §Non-Goals. On the local socket the effective principal reduces to the node-owner binding above whenever the turn is not intervention-opened; an intervention-opened turn's principal arrives through the admitting-principal carrier the §Preconditions box registers, and an unresolved principal fails closed — the request is refused. **Mints no** DDL, migration, wire field, or error code.
- **D-010-13 — Run-blocking seam shape.** Provider-registration directionality mirrors shipped CP-003-8 (`RunSetupGate`): Plan-010 exposes `registerApprovalOutcomeListener` + `cancelPendingForRun`; Plan-003's engine registers and drives run-state transitions — Plan-010 never mutates run state. `onBlocking` fires after the durable commit of the pending request; `onResolved` fires exactly once when it settles (approved / rejected); a rejected outcome continues the run with the action refused. A request never settles on elapsed time, so the seam has no time-based arm.
- **D-010-14 — A request a person answers has no deadline and no sweep.** Nothing settles such a request but the person's answer, the cancellation that rides the end of the run holding it, or a move of the permission level to one that never asks; there is no lazy staleness check on read and no periodic sweep, because there is no deadline for either to notice. The `gate` category is the one no person answers — it is the pre-turn moderation check the daemon makes for itself — and its own denial settlement is [Plan-014](./014-multi-agent-channels-and-orchestration.md)'s ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)). Cancellation events carry `actor: null` (system actor, node-emitter convention).
- **D-010-15 — Trust-evaluation inputs are derived, never duplicated.** No dedicated trust store (the `credential_policy_artifacts` store persists credential-policy documents, not trust-evaluation inputs): node trust ← `node_trust_state.trust_level` with the V1 value set `'untrusted' | 'envelope_trusted'` and fail-closed READ-boundary enforcement (any out-of-set value evaluates as `untrusted`; the Plan-010-owned elevation write parses at the boundary; no retroactive DDL CHECK on Plan-002's shipped migration); own-node determination ← the daemon's attach-binding owner-user identity; envelope roots ← `run_execution_contexts` joined to `workspaces.fs_root` / `worktrees.fs_root` (CP-010-9); unknown provenance → strict per-request ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).
- **D-010-16 — Renderer approval posture: allow-only remembered rules, ungrouped V1 rendering.** `rememberedScope` is schema-refined valid only with `decision: "approved"` (`{rejected, rememberedScope}` → typed rejection; the remember control binds to Approve only; deny-by-default remains Cedar's job). V1 renders one card per canonical record with per-record actions — grouping is a permitted later presentation addition that must preserve per-record identity/actions (deliberate non-exercise of [Spec-010 §Implementation Notes](../specs/010-approvals-permissions-and-trust-boundaries.md#implementation-notes)'s allowance; group-approve would fan one click into N mutations against AC-1's explicit-approval semantics).
- **D-010-17 — `PermissionCheckResponse.reason` is a 5-value enum** (`policy_allow | remembered_rule | approved | pending_approval | denied`): `policy_allow` = Cedar/own-node-envelope permit with no human approval artifact; `remembered_rule` = matched an unrevoked rule that passed at-use re-validation; `approved` = a recorded approved resolution covers the exact request; `pending_approval` = the request is created/open (`allowed: false`, `approvalRequestId` present); `denied` = Cedar forbid, a rejected resolution, or fail-closed refusal (the typed 503 additionally surfaces on fail-closed paths so audit distinguishes them). Invariants: `allowed === (reason ∈ {policy_allow, remembered_rule, approved})`; the `policy_allow`/`approved` split preserves the audit distinction between machine permit and human grant.
- **D-010-18 — No wire preflight; the in-process `PermissionCheckService.check()` is the composed gate.** Evaluate → on an ask-policy outcome create the request, persisting and emitting `approval.requested`, notify the run-blocking seam → return `pending_approval` with its id. The composition is [Spec-010 §Interfaces And Contracts](../specs/010-approvals-permissions-and-trust-boundaries.md#interfaces-and-contracts)'s enforcement seam; splitting evaluate-from-create at a wire boundary would reintroduce the TOCTOU window.
- **D-010-20 — the intervention-opened turn's principal is read from the durable admitting stamp, resolved by row linkage rather than by run history**. T2.2 resolves a steer-opened or replacement-opened turn's effective principal from `interventions.admitting_principal_id` — the daemon-resolved, transport-authenticated identity Plan-003's T2.4 stamps at acceptance under D-003-4's `origin` discriminator — and reaches a run-bound replacement turn's admitting intervention through the queue item's `admitting_intervention_id` linkage. **Rationale (the hardened call):** reading the wire's `initiatorId` is refused outright by [Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior) and ADR-011 — it is caller-asserted, so trusting it hands any caller the choice of whose grants apply, which is the confused-deputy escalation the turn-scoped rule exists to close. Anchoring the association on the row makes the answer a fact recorded at admission rather than a guess reconstructed later, and it survives replay unchanged. The resolution is fail-closed in every failure mode (absent linkage, dangling linkage, principal-less admitting intervention all deny). Entails I-010-25, the CP-010-12 ⇄ CP-003-14 pair, and the `api-payload-contracts.md §Authenticated Principal And Authorization Model` class registration; mints no DDL here (the columns are Plan-003-owned), no wire shape, and no error code — a wire-vs-daemon principal mismatch reuses the existing `auth.principal_mismatch`.
