## Goal

Implement the canonical approval, remembered-grant, and permission-check model that decides every sensitive action a session's agents take on its machine.

## Scope

This plan covers approval records, remembered grants, daemon-side permission checks, remembered-rule revocation, and approval visibility projections — plus permission-ask normalization, execution-posture authorization with the content-addressed credential-policy artifact store, and the allow-listed spawn-environment boundary.

## Non-Goals

- Identity-provider implementation details
- Notification routing for approval prompts
- Provider-specific permission UX beyond normalized capability requests

## Preconditions

- **The admitting-principal carrier.** T2.2's turn-scoped principal resolution requires the accepted intervention's admitting principal durably recorded daemon-side — the transport-resolved caller identity the daemon admitted the intervention under, never the client-supplied wire `initiatorId`, which [ADR-011](../decisions/011-generic-intervention-dispatch.md) keeps informational and which [Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior) explicitly refuses as a principal source. The carrier has three parts: the **producer at acceptance** — [Plan-003](./003-queue-steer-pause-resume.md) T2.4 stamps `interventions.admitting_principal_id` from the daemon's transport-resolved caller identity in the same write that creates the intervention row, universally rather than per-type, beside an explicit `origin` discriminator whose table-level CHECK makes the principal required exactly on the `user` arm (D-003-4 / D-010-20); the **authorization-path consumer** — T2.2's turn-scoped resolution and T2.7's remembered-grant reads take that stamp for a turn a steer opens, read from the steer's own row rather than inferred from run history (CP-010-12 ⇄ CP-003-14, carrying **I-010-25**); and the **api-payload registration** — the class rule stands in [api-payload-contracts.md §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model) naming this column as the second instance of the `approval_resolutions.approver_id` pattern (D-010-12). Resolution is fail-closed: an unresolved principal or an admitting intervention carrying no principal each adjudicate as a deny. [Plan-003](./003-queue-steer-pause-resume.md) states the producer side.

Target paths below assume the canonical implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

## Data And Storage Changes

- Add durable local `approval_requests`, `approval_resolutions`, and `remembered_approval_rules` storage plus the revocation paths: an explicit revoke, and the end of a session for that session's session-scope rules. See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) §Approval Tables for column definitions — the audited DDL there is what the daemon's one schema carries (D-010-2).
- Serve pending and historical approval state from a daemon-local projection (SQL over the approval tables — D-010-6); no control-plane approval storage exists (ADR-017 Option B).
- Evaluation inputs are derived at check time, never duplicated into a dedicated store (D-010-15; the `credential_policy_artifacts` store below is not one — it persists cited credential-policy documents, not evaluation inputs), and a machine carries no trust level: the session's owner ← the machine's owning user, recorded when it registers ([Plan-028](./028-remote-control.md)); working-folder roots ← Plan-007 `workspaces.fs_root` / Plan-008 `worktrees.fs_root` via `run_execution_contexts` (CP-010-9); project trust ← the project's attachment; tool-server trust ← that server's own trust record ([Plan-025](./025-mcp-server-configuration-and-governance.md)); an unresolvable input → strict per-request approval ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).
- Add the content-addressed `credential_policy_artifacts` store: `sha256`-keyed rows persisting the RFC 8785 JCS-canonicalized credential-policy artifact document that `executionPosture.credentialPolicyRef` cites ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior) posture semantics). Rows persist **write-ahead** — before the first `run.running` posture stamp citing the ref, the ADR-019 spawn-intent ordering discipline — and are retained at least as long as any run event citing them : only `Delete old data`, which removes a chosen finished session with its run events (Plan-006's `daemon.retentionPurge`), and `Erase all data` remove a citing row, and growth stays bounded by content-addressing (one row per distinct effective policy, never per run). The deletion leg is T2.9's `pruneUnreferencedArtifacts`, which runs after each purge; `Erase all data` deletes the store whole. See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) §Credential Policy Artifacts — the audited DDL there is what the daemon's one schema carries (the T1.3 convention).

## API And Transport Changes

- The `approval.*` JSON-RPC methods (D-010-5), each called from the app: `approval.resolve`, `approval.projectionRead`, `approval.ruleList`, `approval.ruleRevoke`, `approval.denialOverride` — wire contract in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) §Plan-010 + §Approval Method-Name Registry. `PermissionCheck` is deliberately NOT a wire method: it is the daemon-internal pre-execution gate ([Spec-010 §Interfaces And Contracts](../specs/010-approvals-permissions-and-trust-boundaries.md#interfaces-and-contracts); D-010-18) — its typed shapes are the daemon's own, in `packages/runtime-daemon/src/policy/` beside the permission check, and never in `packages/contracts`.
- More calls land here beside these: `plan.resolve`, the plan verdict (T3.11), and `session.permissionLevelUpdate`, the level control (T3.12). `approval.requestCreate` is not a registered method: no other process calls it, so the daemon raises it in process from a provider's callback, and its request and response schema is the daemon's own, in `packages/runtime-daemon/src/approvals/`, with no client method. None of these is built yet, and each is built by the task named: `approval.requestCreate` (in process) and `approval.resolve` by T3.1 over T2.3, `approval.projectionRead` by T3.2 over T3.3, `approval.ruleList` and `approval.ruleRevoke` by T3.5 over T3.4, `approval.denialOverride` by T3.13, `plan.resolve` by T3.11 and `session.permissionLevelUpdate` by T3.12. The registered methods cross from the app to the daemon.
- Error vocabulary in [Error Contracts](../architecture/contracts/error-contracts.md) §Approval — its codes (D-010-4; `approval.policy_artifact_corrupt` for T2.9's read-boundary integrity check, and `approval.denial_not_found` and `approval.denial_not_overridable` for T3.13's `Allow once`).
- Driver-native permission requests normalize into canonical approval categories, scopes, and resource descriptors before any record is written; Plan-010 owns the normalizer — authored as T2.8 (CP-010-6) — and until driver integration executes, the schema-validated `approval.requestCreate` boundary remains the enforced normalization gate. No new wire method lands with either: the ask surface and the execution-posture layer are in-process seams whose durable records ride Spec-005 events (the `approval.*` rows and the `run.running` posture stamp).

## Design Decisions

- **D-010-1 — Contracts file is `packages/contracts/src/approval.ts`** (single file, singular noun): one-file-per-domain per the shipped `session.ts`/`event.ts`/`repo.ts`/`worktree.ts` convention.
- **D-010-2 — Persistence model (the approval tables; DDL verbatim in local-sqlite-schema.md §Approval Tables).** `approval_requests` carries `session_id` + `requested_by` NOT NULL (provenance; no FK targets — sessions are control-plane rows, runs are event-sourced), required `resource_descriptor` (JSON), nullable `ask_id` (the originating provider permission ask's id, set iff normalizer-minted), a unique partial index on `(run_id, ask_id)` so a normalizer retry or a replay re-mint collides instead of duplicating, a `state` CHECK over `pending | approved | rejected | canceled`, and `updated_at` (a cancellation settles on the row — no resolution row). There is no deadline column: a request waits until it is answered ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)). `approval_resolutions` carries `request_id` as PRIMARY KEY (the durable wire id `approvalRequestId` — enforces the 1:1 decision row and keeps every projection column wire-derivable per I-010-9), `approver_id` NOT NULL, a `decision` CHECK over `approved | rejected`, `effective_scope` NOT NULL, and nullable `remembered_scope_kind`/`remembered_scope_pattern`. `remembered_approval_rules` carries grantor `user_id`, `session_id` (the session the rule was made in), `project_id`, the key a `project` rule is found by from any session on that project (present iff `scope_kind = 'project'`), origin FK `created_from_request_id` (→ `approval_resolutions(request_id)`, the durable id carried on `approval.remembered`), the `scope_kind` enum `session | project`, `sense` `allow | block` (`block` only on `network_access`), `made_at_level` over the permission levels, `scope_pattern` holding the subject the daemon derived, `mcp_binding_digest` (the binding's lifelong digest, named as `command_receipts.mcp_binding_digest` is) for a rule whose subject is a tool server's tool, and the `revoked_at` ⇔ `invalidation_trigger` co-presence CHECK over the trigger set `{explicit, session_end, project_detached, server_trust_withdrawn}`.
- **D-010-3 — Consolidated wire block.** The request/response pairs + `RememberedRuleId` brand + `RememberedScope` + `InvalidationTrigger` + `ApprovalFlowEventPayload` defined in api-payload-contracts.md §Plan-010: create carries required `resourceDescriptor`; resolve carries optional `approver` + `effectiveScope?` + `rememberedScope?`, the decline's optional reason line, the subject as the person corrected it and a client resolution id the resolution event echoes, and returns the recorded `approverId` + `effectiveScope`; the projection row carries `requestedBy`, `resourceDescriptor`, `updatedAt`, and the resolved quad (`resolvedAt`/`decision`/`approverId`/`effectiveScope`) present iff state ∈ {approved, rejected}; rule rows carry grantor, scope kind, the project key of a project rule, sense, subject, `madeAtLevel` and revocation metadata; the `ApprovalFlowEventPayload` carries the projection-rebuild fields (`requestedBy`/`resourceDescriptor` on `requested`, `approver`/`effectiveScope`, the client resolution id and the answering device's id on the resolution events, and the rule projection on `remembered` — grantor = `approver`, binding = `rememberedScope` with its sense, `madeAtLevel`, origin = `approvalRequestId`) so relayed or replayed events alone rebuild each daemon's projection rows, `remembered_approval_rules` included (D-010-6/D-010-7, I-010-9).
- **D-010-4 — Error vocabulary (§Approval).** `approval.not_found` 404, `approval.already_resolved` 409, `approval.request_canceled` 409 (non-colliding with the `approval.canceled` event), `approval.persistence_unavailable` 503 (fail-closed), `approval.rule_not_found` 404, `approval.rule_already_revoked` 409, `approval.policy_artifact_corrupt` 500 (T2.9's read-boundary content-address recompute failing closed; mirrored in §API And Transport Changes), and `approval.denial_not_found` 404 and `approval.denial_not_overridable` 409, T3.13's refusals of `approval.denialOverride` for an unknown `denialId` and for a block the provider's reviewer marked not overridable. A press after the block's session has ended is refused with `session.already_closed`. Deliberate absence: no `approval.permission_denied` — the local IPC surface carries no caller principal, and a `PermissionCheck` denial is a normal `{allowed: false}` response.
- **D-010-5 — Method registry: strings on the new singular `approval` root** (`approval.resolve`, `approval.projectionRead`, `approval.ruleList`, `approval.ruleRevoke`, `approval.denialOverride`; `approval.requestCreate` registers no string, since only the daemon raises it and its schema is the daemon's own), registered in api-payload-contracts.md §Approval Method-Name Registry with the root added to the namespace-root enumeration. `PermissionCheck` registers NO wire method string: zero V1 wire consumers, and a wire preflight would invite stale-verdict (TOCTOU) authorization against the security gate. "Rule" (not "grant") is the operation vocabulary — matching `remembered_approval_rules`, `approval.rule_revoked`, and `RememberedRuleId`.
- **D-010-6 — Projection is daemon-only.** No control-plane approval projection exists: shared Postgres stores zero approval tables (ADR-017 coordination records only; shared-postgres-schema invariants), so a control-plane projection would violate the storage posture, not extend it. `approval-projection-service.ts` lands in Plan-010-owned `packages/runtime-daemon/src/approvals/`.
- **D-010-7 — Events-canonical; rows are projections.** `EventLogService.append` commit IS the [Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior) durability gate; row projection updates after; startup reconcile replays `approval_flow` events newer than the rows' high-water mark; a failed append surfaces `approval.persistence_unavailable` and the gated action does not proceed.
- **D-010-8 — `approval.canceled` is an additive durable event (one of the `approval.*` variants of the shared payload).** Emitted when `cancelPendingForRun` settles pending requests on run-terminal; [Spec-005 §Approval Flow (approval_flow)](../specs/005-session-event-taxonomy-and-audit-log.md#approval-flow-approval_flow) gains the row. A cancellation settles on the request row (`state` + `updated_at`) — never a resolution row. Explicit-over-derived: a projector-derived cancellation would leave the `approval_flow` audit timeline incomplete.
- **D-010-9 — The policy engine is `@cedar-policy/cedar-wasm` in-process (`preparsePolicySet` and `preparseSchema` once per verified bundle, `statefulIsAuthorized` on every check; `isAuthorized` re-parses the policy text on every call and must not be used) over one signed bundle form that carries the built-in approval rules and every later one.** A bundle is one file, `approval-rules-<version>.bundle`: a manifest in RFC 8785 canonical JSON, made with the daemon's existing canonicalizer, `{version, builtAt, cedarVersion, schemaSha256, policiesSha256, keyIds}`; the compiled Cedar schema and policy text; and the signatures. The set built into the service is the first bundle, in the same form, checked the same way at every start: one verify path, never two. **Two signatures, both required:** an Ed25519 and an ML-DSA-65 signature over the canonical manifest bytes, which carry the content hashes, each checked with `node:crypto` against the key pairs pinned in the service build, `current` and `next` ([ADR-012 §Signing Algorithm](../decisions/012-cedar-approval-policy-engine.md#signing-algorithm)). **The public signing record:** the release workflow also signs each bundle keyless through Sigstore, and the daemon verifies that record offline with `@sigstore/verify`'s `Verifier` against the Sigstore trusted root shipped in its build, requiring a transparency-log entry and pinning the signer three ways — the issuer, the release workflow's identity as a pattern over any release tag, and the repository's and its owner's numeric ids in the certificate's extensions. **Always rising:** the daemon stores the highest verified `version` and its `builtAt` in its database, refuses a candidate that is not newer or was built earlier than the running bundle, and applies no expiry, so a machine left offline keeps running the last rules it verified. **Retired keys:** a retirement statement naming retired key ids, signed by the other pinned pair and published with the newest bundle re-signed by that pair, is recorded in the daemon's database for good, and anything signed by a retired key is refused. **A refused candidate changes nothing:** the daemon keeps evaluating with the bundle it runs, never loads unverified rules, and records `policy_bundle.rejected {version, reason}` with `reason` one of `signature`, `key_retired`, `record`, `not_newer`, `malformed` and `cedar`. **Delivery and swap:** a bundle is one more file on the update feed, fetched at the update check the service already makes; a verified bundle is preparsed and swapped in between two checks, with no restart and no check evaluated across the swap — an approval already asked keeps its question and the new rules apply from the next check — and `policy_bundle.loaded {version, builtAt}` is recorded. **The only start refusal:** the daemon refuses to start only when no bundle verifies at all, not even the one built into it; the daemon status and Settings › Runtime's service line then read `Stopped: its approval rules did not pass their signature check. Reinstall the app to restore them.` While it runs, `sidekicks daemon status` prints `Approval rules: bundle <n> · built <date>` (`built in` for the first bundle), and the daemon status read carries the same as `approvalRules {version, builtAt, source: "built_in" | "update"}`. **Pinned material:** the two key pairs, the trusted root, the identity pattern and the two ids are a build input; dev and test builds pin test material the test setup makes and run the same verifier, so only the pins differ from a release build, never the path. YAML sources live at `packages/runtime-daemon/policies/default-policy.yaml`; `scripts/compile-policies.mjs` compiles them; building and signing a bundle are release-workflow scripts, never `sidekicks` verbs, because the person never handles a bundle; content transcribes security-architecture §Permission Matrix + [Spec-010 §Default Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#default-behavior). The package is `@cedar-policy/cedar-wasm`, pinned at 4.11.x; `@cedarpolicy/cedar-wasm` does not exist on npm and is a dependency-confusion hazard. **Dependencies:** `@sigstore/verify` 4.1.2 is added (Apache-2.0, with `@sigstore/core`, `@sigstore/bundle` and `@sigstore/protobuf-specs`, 944 KiB on disk); under the Electron runtime `@sigstore/core` calls `crypto.verify` with no digest for EC keys, which BoringSSL refuses and the library reports as a failed check, so a one-line `pnpm patch` passes `sha256` for EC and RSA keys when the caller names none — the digest Node's OpenSSL uses for both — offered upstream and carried until a release contains it. `sigstore` itself is not used, because its update-framework client fails on the Electron runtime the same way and a shipped trusted root needs no such client; `@noble/post-quantum` is not added, because ML-DSA-65 is native in `node:crypto` on the service's runtime (Node 24.16 or later, and Electron's). Operational procedures: [Cedar Policy Signing And Rotation](../operations/cedar-policy-signing-and-rotation.md).
- **D-010-10 — Remembered-scope matching semantics.** `RememberedScope { kind: 'session' | 'project'; pattern: string; sense: 'allow' | 'block' }`; `request_only` is expressed by OMITTING `rememberedScope`, never an enum member. `pattern` is the subject the daemon derived from the ask and the card's answer displayed — a command's program and its first subcommand, a network request's host, a written file's name — and at resolve the daemon re-derives it and refuses an echoed pattern that differs, so a rule never covers more than the words the person pressed. Candidate set: unrevoked ∧ same `category` ∧ (kind = `session` ∧ same `session_id` ∨ kind = `project` ∧ same project) ∧ the session's level now in force is the rule's `made_at_level` or a less careful one. Subject semantics: a command matches its program and first subcommand; `network_access` = exact host equality, with no wildcards; `file_write` = that one file, as its normalized absolute path resolved against the CP-010-9 roots; all other categories = exact subject equality. A matching `allow` answers the ask with no card; a matching `block` refuses it with no card, and its row reads `Declined`. An allow and a block over the same subject in the same scope cannot both stand: recording one replaces the other. The rule's `user_id` is written as the GRANTOR (D-010-3: grantor = `approver`) and serves as the audit key; the rule's **scope enum** (`RememberedScope.kind`) is session/project only, and `idx_remembered_rules_user(user_id, category)` indexes the grantor axis.
- **D-010-11 — Invalidation: on-next-use re-evaluation is the correctness mechanism.** The grant-match path re-validates every rule's preconditions at use time — unrevoked; for a session rule, its session still open; for a project rule, its project still attached; for a rule over a tool server's tool, the binding it comes from still present and trusted. The push seams call `revokeDependentRules`, each in the same transaction as the act that ends the rules, and emit one timely `approval.rule_revoked` per rule: the synchronous session-close hook with `session_end` for the closed session's session rules; `repo.detach` with `project_detached` for every rule of the detached project; and `mcp.setTrust` withdrawing trust, a settings change that withdraws it or removing the binding, each with `server_trust_withdrawn` for every rule over that binding's tools. The seams are the audit and timeliness layer: only use-time re-validation satisfies revoke-before-next-use ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)). A project rule outlives the session it was made in and ends by an explicit revoke or when its project is detached, or, for a rule over a tool server's tool, when the trust of the binding its tool comes from is withdrawn or that binding is removed. An unresolvable input → fail closed ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).
- **D-010-12 — Approver identity model.** Wire `approver?: UserId` is OPTIONAL and informational: absent on the local socket → the daemon records its owner-user binding (the machine's owning user, the same read as D-010-15's owner input); present → cross-checked against that user, on the local socket and for a linked device inside its encrypted channel to the machine, which binds the same user — mismatch → `auth.principal_mismatch`. `approval_resolutions.approver_id` stays NOT NULL (the RECORD is mandatory per [Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)); `ApprovalResolveResponse.approverId` returns the recorded server truth (AC-3 observable). The renderer never populates an approver identity. **Addressed principal.** A pending request raised by the composed gate is **addressed to the turn's effective principal** — the principal whose decision the pipeline awaits, and therefore the one recorded as `approver_id` on resolution. This decides who the pipeline asks and records, not how they are reached — notification transport for approval prompts stays out of scope per §Non-Goals. On the local socket the effective principal reduces to the machine's owning user above whenever the turn is not intervention-opened; an intervention-opened turn's principal arrives through the admitting-principal carrier (CP-010-12, §Preconditions), and an unresolved principal fails closed — the request is refused. **Mints no** DDL, wire field, or error code.
- **D-010-13 — Run-blocking seam shape.** Provider-registration directionality mirrors shipped CP-003-8 (`RunSetupGate`): Plan-010 exposes `registerApprovalOutcomeListener` + `cancelPendingForRun`; Plan-003's engine registers and drives run-state transitions — Plan-010 never mutates run state. `onBlocking` fires after the durable commit of the pending request; `onResolved` fires exactly once when it settles (approved / rejected); a rejected outcome continues the run with the action refused. A request never settles on elapsed time, so the seam has no time-based arm.
- **D-010-14 — A request a person answers has no deadline and no sweep.** Nothing settles such a request but the person's answer, the cancellation that rides the end of the run holding it, or a move of the permission level to one that never asks; there is no lazy staleness check on read and no periodic sweep, because there is no deadline for either to notice. Cancellation events carry `actor: null` (system actor, node-emitter convention).
- **D-010-15 — Evaluation inputs are derived, never duplicated.** No dedicated trust store (the `credential_policy_artifacts` store persists credential-policy documents, not evaluation inputs), and no machine trust: a machine carries no trust level, because trust is per tool server and per project. The session's owner ← the machine's owning user, recorded when it registers; working-folder roots ← `run_execution_contexts` joined to `workspaces.fs_root` / `worktrees.fs_root` (CP-010-9); project trust ← the project's attachment, which trusts it for both providers; tool-server trust ← that server's own trust record ([Plan-025](./025-mcp-server-configuration-and-governance.md)); an unresolvable input → strict per-request ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).
- **D-010-16 — Renderer approval posture: remembered rules are allow or block, and one record renders at a time.** `rememberedScope.sense` is schema-refined to agree with the decision — `approved` mints `allow`, `rejected` mints `block` — and a `block` is accepted only on a `network_access` ask, whose decline offers `Block <host> this session` with the project on the same arrow; a command's and a file's decline record nothing, and deny-by-default remains Cedar's job. The card renders one canonical record at a time with its own actions (I-010-19); there is no grouping and no group-approve, because one click fanned into N mutations breaks AC-1's explicit-approval semantics.
- **D-010-17 — `PermissionCheckResponse.reason` is a 5-value enum** (`policy_allow | remembered_rule | approved | pending_approval | denied`): `policy_allow` = a Cedar permit with no human approval artifact; `remembered_rule` = matched an unrevoked rule that passed at-use re-validation; `approved` = a recorded approved resolution covers the exact request; `pending_approval` = the request is created/open (`allowed: false`, `approvalRequestId` present); `denied` = Cedar forbid, a rejected resolution, or fail-closed refusal (the typed 503 additionally surfaces on fail-closed paths so audit distinguishes them). Invariants: `allowed === (reason ∈ {policy_allow, remembered_rule, approved})`; the `policy_allow`/`approved` split preserves the audit distinction between machine permit and human grant.
- **D-010-18 — No wire preflight; the in-process `PermissionCheckService.check()` is the composed gate.** Evaluate → on an ask-policy outcome create the request, persisting and emitting `approval.requested`, notify the run-blocking seam → return `pending_approval` with its id. The composition is [Spec-010 §Interfaces And Contracts](../specs/010-approvals-permissions-and-trust-boundaries.md#interfaces-and-contracts)'s enforcement seam; splitting evaluate-from-create at a wire boundary would reintroduce the TOCTOU window.
- **D-010-20 — the steer-opened turn's principal is read from the durable admitting stamp on the steer's own row, never from run history**. T2.2 resolves a steer-opened turn's effective principal from `interventions.admitting_principal_id` on the steer's own row — the daemon-resolved, transport-authenticated identity Plan-003's T2.4 stamps at acceptance under D-003-4's `origin` discriminator. **Rationale:** reading the wire's `initiatorId` is refused outright by [Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior) and ADR-011 — it is caller-asserted, so trusting it hands any caller the choice of whose grants apply, which is the confused-deputy escalation the turn-scoped rule exists to close. Anchoring the association on the row makes the answer a fact recorded at admission rather than a guess reconstructed later, and it survives replay unchanged. The resolution is fail-closed in every failure mode (an unresolved principal and a principal-less admitting intervention both deny). Entails I-010-25, the CP-010-12 ⇄ CP-003-14 pair, and the `api-payload-contracts.md §Authenticated Principal And Authorization Model` class registration; mints no DDL here (the columns are Plan-003-owned), no wire shape, and no error code — a wire-vs-daemon principal mismatch reuses the existing `auth.principal_mismatch`.

## Rollback Or Fallback

- Disable remembered grants and fall back to `request_only` approvals everywhere if grant invalidation or replay behavior regresses — the grant-evaluator seam makes rule matching removable without touching the permission gate, and `request_only` is the schema default (omitting `rememberedScope` is always valid).
- The run-blocking seam is deregistrable without touching Plan-003's engine (zero-listener operation is a tested no-op).

## Risks And Blockers
