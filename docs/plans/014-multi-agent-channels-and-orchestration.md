## Goal

Implement session-scoped channels, the V1 agent identity surface, parent-child run linkage, and provider-agnostic orchestration semantics — turn policies, budgets, stop conditions, and moderation hooks as a hard V1 quality gate — for concurrent multi-agent work.

## Scope

This plan covers channel creation and lifecycle, the agent identity and configuration surface, orchestration run creation with full admission enforcement (budget, turn policy), durable run-link projection, internal-helper visibility, budget accounting with warning/interrupt thresholds, idle and turn-limit stop conditions, moderation gates, round-robin arbitration with partition pause, and desktop surfaces for concurrent agent work.

## Non-Goals

- Workflow authoring syntax (Plan-015)
- Provider-native subagent APIs beyond normalized adapters (ADR-005)
- Channel-level permission restrictions (V1-deferred per [Spec-014 §Resolved Questions](../specs/014-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions)) — no agent-scoped read grants
- Cross-machine `targetNodeId` dispatch ([Spec-022](../specs/022-cross-node-dispatch-and-approval.md)/Plan-024 — D-014-9)
- Conclusion detection (V2 per [Spec-014 §Stop Conditions](../specs/014-multi-agent-channels-and-orchestration.md#stop-conditions))
- Timeline summary-row rendering (Plan-011 — D-014-14; this plan publishes the durable inputs only)
- Realtime/voice channels — reserved behind the R8 capability gate per [Spec-014 §Resolved Questions and V1 Scope Decisions](../specs/014-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions): the upstream flag is under development, no channel-model change lands until it stabilizes, and this plan schedules no realtime task (the reservation is a gate, not work)

## Data And Storage Changes

- `channels` (user channels only — main is synthesized per D-014-15), `run_links` (single-parent `child_run_id` PRIMARY KEY, `session_id` provenance, `link_type` CHECK, `internal_helper`, `producing_node_id`), `agents` (4-state domain lifecycle), and `session_budgets` (row-canonical limits) per [Local SQLite Schema §Channel and Orchestration Tables](../architecture/schemas/local-sqlite-schema.md#channel-and-orchestration-tables-plan-014).
- `session_exchanges` (the pair of sessions trading messages and the count since the person last wrote) and `session_paused_message_queue` (every message addressed to a paused session, in arrival order, each row naming the sender's own send event rather than holding its words) per the same schema section, added by T2.18 on their own migration ordinal — the two pieces of daemon state [Spec-014 §State And Data Implications](../specs/014-multi-agent-channels-and-orchestration.md#state-and-data-implications) declares durable. The session directory beside them is **not** a table: it is rebuilt from the sessions the daemon hosts when it starts.
- `channels`, `run_links`, and `agents` are events-canonical projections (ADR-017 Option B) rebuilt byte-equal on replay; `session_budgets` is row-canonical daemon configuration (the `queue_items` posture — mutated by wire method, never evented), and so are the two session-messaging tables — a message persists nothing of its own, so neither is rebuilt from the log.
- Budget **accounting** has no accumulator table: the `BudgetAccountant` is an in-memory projection over `usage_telemetry` + `run.*` events, rebuilt on replay (D-014-5); per-run effective ceilings rebuild from the durable `run.queued` `effectiveRunConfig?` field, not by re-merging session defaults that may have changed mid-run. The per-turn usage rows [Plan-026](./026-provider-accounts-and-credential-homes.md) projects per provider account are a **projection over the same `usage_telemetry` events**, rebuilt on replay like every other one and served through this plan's one committed-spend accessor, so the account surface's by-day and by-model figures are an axis over the accountant's own facts rather than a second accountant beside it.
- No timeline-projection rows: this plan publishes durable events only; Plan-011 derives summary rows (D-014-14).
- The channel-directory publication (D-014-22) adds **no daemon-side storage**: no new table, no column, and no acknowledgment ledger — the T2.14 publisher derives every publication and the startup/reconnect re-publication sweep from the durable channel-lifecycle events alone ([Spec-014 §State And Data Implications](../specs/014-multi-agent-channels-and-orchestration.md#state-and-data-implications)). The directory's backing store is the **control-plane** `session_channel_directory` table ([Shared Postgres Schema §Session Channel Directory (Plan-014)](../architecture/schemas/shared-postgres-schema.md#session-channel-directory-plan-014)) — this plan owns and builds it (T2.17). `ChannelConfig.turnsPerAgent` (D-014-23) likewise adds no column: it rides the existing `channels.config` JSON value like every other `ChannelConfig` member.

## API And Transport Changes

- Thirteen daemon JSON-RPC pairs per [api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md#plan-014--multi-agent-channels-and-orchestration): `channel.create` / `channel.mute` / `channel.unmute` / `channel.archive` / `channel.rosterRead`, `orchestration.runCreate` / `orchestration.childRunLinkRead` / `orchestration.budgetRead` / `orchestration.budgetUpdate`, `agent.configUpdate` / `agent.list`, plus `session.goalUpdate` / `session.goalClear` (session-goal RPCs). Registration is gated on registry regex conformance (camelCase tails) and typed wire errors on the `DaemonDomainError` projection.
- Ten owned event types in the [Spec-005 registry](../specs/005-session-event-taxonomy-and-audit-log.md) (the owned set grows to twelve with the two `session.goal_*` events whose schema + union registration land in T1.2, per T1.1): `channel.created` / `channel.muted` / `channel.unmuted` / `channel.archived`, `agent.config_updated`, `arbitration.paused` / `arbitration.resumed`, `orchestration.rejected`, `usage.budget_warning`, `moderation.review_flagged`.
- The `run.queued` payload gains optional additive linkage fields `{agentId?, parentRunId?, linkType?, internalHelper?, producingNodeId?}` plus the admission-resolved `effectiveRunConfig?` threaded from the in-process `OrchestrationRunLinkCarrier`, and the path-independent server stamps `admittedUnpricedCapCents?` (native-cap unpriced admissions) + `admittedModelFamily?` (every admission — derived pricing, family caps, and warnings all key off it; ordinary `run.queueCreate` admissions stamp them directly at the queue write, the orchestration path via the carrier) (D-014-3, CP-003-10; ADR-018 additive-only).
- Error vocabulary per [error-contracts.md](../architecture/contracts/error-contracts.md) §Channel / §Orchestration / §Agent (D-014-16), plus the §Session `session.goal_delivery_failed` (502) and `session.goal_mutation_in_flight` (409) mappings for the goal RPCs.
- **Channel-directory publication transport (D-014-22).** The T2.14 publisher is a daemon-to-control-plane **client** of one idempotent control-plane ingest mutation — a tRPC surface in the ADR-014 control-plane API family, alongside the daemon's existing control-plane client calls — whose request contract, backing store, and channel-list read path **this plan also owns and builds**, at T2.17. It adds **no daemon JSON-RPC method**: the thirteen-pair registry above is unchanged, and no client SDK surface exists for it — publication is a daemon-internal side effect of the channel lifecycle, never caller-invocable. Each publication carries the channel's metadata (`channelId`, `sessionId`, `name?`, `state`) plus the origin-ordering keys (`originNodeId`, `originSeq` — read from the lifecycle payload, where T2.2 server-stamps them per the [Spec-005 §Channel and Agent Lifecycle](../specs/005-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle) mirror; envelope `occurredAt` + `id`) per [Spec-014 §Interfaces And Contracts](../specs/014-multi-agent-channels-and-orchestration.md#interfaces-and-contracts). `ChannelConfig.turnsPerAgent` and the fourth `InterruptReason` member `workflow_phase_cancelled` (D-014-23) likewise add no wire method — both ride existing contract shapes, mirrored in [api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md#plan-014--multi-agent-channels-and-orchestration) with the `run.completed`/`run.interrupted` `trigger` union in the §Plan-003 mirror widened in step.
- **Contract mirror — same-agent provider switch (D-014-26).** The axes a run starts with gain `providerAccountId?` + `effort?`; `AgentConfigUpdateRequest` gains `driverName?` + `effort?` + `interruptAndSwitch?` (and `outputSpeed?`, the fifth provider axis — validated against the target driver's published `outputSpeedLevels`, spawn-bound, and carried through `pendingAxes` like the rest); `AgentConfigUpdateResponse` gains `switch?: AgentProviderSwitchDisposition` — a **discriminated union**, not a settlement, because mutation and application are two moments: `AgentProviderSwitchPending` (`switchId`, the resolved `appliesAt` boundary, the `pendingAxes` target record that forced it — the moved axes **and** the values they move to, one shape shared with the `agent.config_updated` payload — `interruptRequested`, and `replacedSwitchId?` on a supersession) is the ordinary arm, and the three **settled** arms are reachable only on the `interruptAndSwitch` arm, which holds its request open: `{ status: 'applied' } & AgentProviderSwitchOutcome`, `{ status: 'degraded' } & AgentProviderSwitchOutcome` under a **total** mapping from continuity (`applied` iff the conversation arrived whole — `in_place` or `resumed`; `degraded` iff it did not — `brief` or `replayed`), and `AgentProviderSwitchFailed` carrying the same closed `reason` vocabulary as `agent.provider_switch_failed`. Four arms rather than two, because an arm that waits for its own settlement must be able to express every settlement its boundary can reach. The durable `agents.pending_switch` slot stores a **superset** of the wire record — adding the daemon-resolved `admittingPrincipalId` (the §Authenticated Principal class rule) and the `'requested'` \| `'dispatched'` interrupt-dispatch marker — neither of which is ever returned to a caller or appended to a payload. `AgentProviderSwitchOutcome` carries the `continuity` arm naming which mechanism carried the conversation (`in_place` \| `resumed` \| `brief` \| `replayed`) and the closed `DeclaredLossKind` union, both landing beside it; `AgentListResponse.agents` additionally returns the effective `providerAccountId?` / `effort?` / `outputSpeed?`, the live-scoped `observedOutputSpeed?` (the provider's own declared speed state and its reason, projected from the live binding and stored in no column, so a mode the provider's account gate refused is readable beside the one that was requested rather than hidden behind it; **absent until observed**, the declaring handshake being turn-bearing rather than carried on the spawn), and any `pendingSwitch?`, so a caller that did not issue the mutation can still see the axis and the queued intent, and every axis a caller can move is an axis a caller can read back — all mirrored in [api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md). Every added request member is additive-optional per [ADR-018](../decisions/018-cross-version-compatibility.md) and an omitted member is **unchanged, never reset**. `effort` is a `string` rather than a corpus enum on purpose: the valid set is the target model's driver-reported `effortLevels`, so an enum here would be a second, staler source of a provider-owned vocabulary. The response member's **presence** is the switch discriminator, so a pure rename carries no switch member at all and a consumer cannot mistake one for the other; within it, `status` discriminates a promise from a settlement — and, among settlements, an honest degrade from an ordinary success — so no consumer reads a `continuity` that a deferred switch has not produced yet, nor re-derives `degraded` for itself. One error code is minted — `agent.provider_axis_invalid` (400), taking the agent namespace to three. **The account is not an axis of this mutation at all** — which account a provider's work runs on is the provider surface's own control (`providerAccount.setCurrent`, [Spec-026 §Moving a session to another account](../specs/026-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)) — so no account member and no account refusal is mirrored here; `AgentListResponse` still returns the effective `providerAccountId` as a read-back of the binding a run resolved.
- **Contract mirror — cost display consistency (D-014-24).** `OrchestrationBudgetState` gains four members — `committedSpendCents`, `observedPricedCostCents`, `observedUnpricedDebitCents`, and the aggregate `costStatus` — mirrored in [api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md#plan-014--multi-agent-channels-and-orchestration), carrying the two fold identities as contract comments so T1.2's field-for-field parity claim has something to match. They ride the existing `orchestration.budgetRead` / `orchestration.budgetUpdate` response shape — `OrchestrationBudgetUpdateResponse` **is** `OrchestrationBudgetState`, so the members are required on the update reply too, which is why the obligation binds the mutation binder (T3.1) as well as the query binder (T3.2): **no new wire method** (the thirteen-pair registry is unchanged), no new event type, no error code, and no table. `usage.budget_warning` is unchanged — its `observedValue` was already defined as committed spend by [Spec-014 §Cost Derivation And Absent-Cost Semantics](../specs/014-multi-agent-channels-and-orchestration.md#cost-derivation-and-absent-cost-semantics); what this plan adds is the asserted equality between it and `committedSpendCents` at the same fold state (I-014-24), not a payload change.
- **Contract mirror — session cost receipt (D-014-25).** One new read method, `orchestration.costReceiptRead`, and its `SessionCostReceipt` response shape mirrored in [api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md#plan-014--multi-agent-channels-and-orchestration), carrying the two partition identities as contract comments so T3.9's parity claim has something to match. The wire-method registry therefore moves thirteen → fourteen pairs; **no new event type, no error code, and no table** — the receipt is a decomposition of an existing in-memory fold, so `usage.budget_warning` and `session_budgets` are unchanged and `usage.cost_update` is unchanged. One axis is supplied rather than minted here: the paying account arrives as the `run.queued` server stamp `admittedProviderAccountId` plus the registry's billing mode ([Plan-026](./026-provider-accounts-and-credential-homes.md), CP-026-3) — not a Plan-014-owned surface, and this plan reads it without widening it.

## Design Decisions

- **D-014-1 — Single contract file.** All Plan-014 contracts live in `packages/contracts/src/orchestration.ts` (ChannelCreate included) — no separate `src/channels/` or `src/orchestration/` contract directory; the shipped `packages/contracts/src/channels.ts` stays untouched per its anti-leakage test.
- **D-014-2 — Method strings.** `channel` root co-extension (`create` / `mute` / `unmute` / `archive` / `rosterRead` — the first daemon-native handlers under the already-declared root) plus new `orchestration` and `agent` roots, per the [api-payload-contracts.md §Plan-014 registry](../architecture/contracts/api-payload-contracts.md). Registry regex conformance and the typed-error projection gate registration.
- **D-014-3 — Linkage carrier.** Run linkage rides optional additive `run.queued` payload fields (no new event type); `run_links` is a pure events-canonical projection; relay peers rebuild linkage from the event alone; the admission-resolved `effectiveRunConfig` rides the same additive vehicle (the durable source for D-014-5 budget rebuild and I-014-14 idle replay).
- **D-014-4 — Typed configs.** `ChannelConfig {turnPolicy?, roundRobinOrder?, moderation?, turnsPerAgent?}` (`turnsPerAgent` per D-014-23) and `OrchestrationRunConfig {tokenLimit?, idleTimeoutMs?}` replace the former `Record<string, unknown>` placeholders; DDL comments cite the types.
- **D-014-5 — Budget substrate.** `BudgetAccountant` = in-memory replay-rebuilt projection (no accumulator table); durable limits = `session_budgets` row-canonical table; `orchestration.budgetRead` / `budgetUpdate` wire surface; per-run effective overrides persist on `run.queued` (`effectiveRunConfig`) — enforcement rebuilds from the event, never by re-merging session values (which may change mid-run).
- **D-014-6 — Roster read.** New daemon-native `channel.rosterRead` (channels rows + synthesized main + typed config + arbitration facet); the shipped `channel.list` daemon-as-gateway directory read is untouched; arbitration/lifecycle events are opaque re-read signals to clients.
- **D-014-7 — System interventions.** Budget/idle/moderation interrupts enter through Plan-003's in-process entrypoint below wire authz, with NULL-for-system actor and the standard `expectedRunVersion` reject-re-read-retry loop.
- **D-014-8 — Turn + idle definitions.** Turn = one completed assistant-output cycle per (channel, agent); consecutive counter resets on interleave; at-limit completes with `trigger: 'turn_limit'` (Plan-003's trigger set gains the value) + same-agent admission refusal. Activity = any appended event carrying the run's id; idle sweep is a daemon-owned per-run timer. `InterruptReason = budget_exhausted | idle_timeout | moderation_denied | workflow_phase_cancelled` (closed set — the fourth member per D-014-23, invoked only by the workflow engine's SA-9 cascade).
- **D-014-9 — Single-node V1.** `targetNodeId` must be locally attached or absent; non-local → typed `orchestration.node_not_local`; cross-node dispatch is Spec-022/Plan-024 (criterion edge — never conflate the surfaces).
- **D-014-10 — Moderation mechanics.** Pre-turn gate = `PermissionCheckService.check({category: 'gate'})` before the turn's `assistant_output` append; in-memory buffering while pending; deny discards + system-cancels (`moderation_denied`); approve appends unchanged; post-turn = `moderation.review_flagged` (informational). Lands after Plan-010 Phase 2.
- **D-014-11 — Scheduler semantics.** No count limit of the runtime's own on executing channels, pending orchestration runs, active children, or queued items; a provider's own limits apply under the person's own provider settings and its refusals surface in its own words. Admission refuses only on the budgets and turn policy the person set and on the state of what a run targets (cost ceiling, turn limit, node locality, channel state, agent readiness): create-time enforcement, zero residue, durable `orchestration.rejected` record.
- **D-014-12 — Channel lifecycle.** `active` ↔ `muted` (mute/unmute; `channel.unmuted` registered), `active`|`muted` → `archived` (terminal); admission to archived → `channel.inactive`; mute suppresses attention, not execution.
- **D-014-13 — Queue seam.** Orchestration admission pipeline (agent → budget → turn gate) then in-process Plan-003 queue admission with the typed carrier; `RunId` mints at queue insert (`state: 'queued'` in the create response); zero-residue refusals.
- **D-014-14 — Timeline seam.** Events-only producer: no timeline rows, no Plan-011 imports; Plan-011 derives summary rows from the durable events + carrier.
- **D-014-15 — Main-channel model.** `channels` holds user channels only; main is projected (no row, no event — both shipped consumers' posture); reads synthesize main; `channel.create` refuses `MAIN_CHANNEL_NAME` (`channel.name_reserved`); `targetChannelId` accepts the derived main id without a row; no `is_main` column.
- **D-014-16 — Error vocabulary.** [error-contracts.md](../architecture/contracts/error-contracts.md) §Channel (3 codes) / §Orchestration (3 codes) / §Agent (3 codes); parent-not-found reuses `run.not_found`; no token collides with an event name.
- **D-014-17 — Link types.** `spawn` (helper, output to parent's channel context) / `delegate` (bounded task, own target channel) / `handoff` (parent transfers continuation and completes); caller-declared, default `spawn`, durable.
- **D-014-18 — Desktop scope.** V1 desktop ships **no** `OrchestrationRunCreate` affordance (creation via SDK/CLI now; Plan-015 workflows later); it renders roster, lifecycle controls, linkage, and refusal records. V1 ships no user-mute and no pause-channel interaction. **Scope clarification (D-014-24):** that list enumerates the view's _interaction_ scope and is not a closed enumeration of what it displays — the governing Spec-021 render contract (the line T4.1 cites) additionally has this view render **session budget state** read via `orchestration.budgetRead`, which is a read-only display carrying no affordance and so never contradicted the no-`OrchestrationRunCreate` posture above. T4.1 carries that render under the CP-014-16 verbatim-display obligation.
- **D-014-19 — Turn-policy state.** Derived projections only (no new table): round-robin cursor from the durable `run.queued(channelId, agentId)` sequence + config order (non-empty `roundRobinOrder` required at create); arbitration pause from `arbitration.*` events; `request-based` is structurally satisfied in V1 (every agent run is explicitly created) and adds no admission check.

- **D-014-22 — Channel-directory publication** (full publication per [Spec-014 §Resolved Questions and V1 Scope Decisions](../specs/014-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions)). Every accepted channel-lifecycle transition is published — after the durable event append, at-least-once, never blocking the daemon-local operation — to the control-plane channel directory: minimal metadata only (`channelId`, `sessionId`, the triggering event's `lifecycleEventKind` — so the ingest can identify a creation under reordering — `name?`, `state`), plus the origin-ordering keys (`originNodeId` + `originSeq` — server-stamped on the lifecycle payloads themselves per the Spec-005 mirror, so they survive relay re-sequencing in every durable copy; envelope `occurredAt` + `id` for the cross-origin comparator — the §Session Goals two-stage register precedent), with a startup/reconnect re-publication sweep derived from the durable events alone (no ack ledger, no new daemon table); the upsert converges as a deterministic per-origin candidate-retention fold (a single-winner comparator would be order-dependent under an origin clock rewind): one retained candidate per origin (same-origin `originSeq`-max; keyless legacy publications share one envelope-ordered slot), visible state resolved from the retained set — terminal `archived` (D-014-12) latching, otherwise the envelope-lexicographic-max candidate — on the `state` axis only, the create-once binding governing `name` independently so a late-arriving creation publication still binds it on an archived row without reviving it ([Spec-014 §Interfaces And Contracts](../specs/014-multi-agent-channels-and-orchestration.md#interfaces-and-contracts); the state-based-merge construction per [Spec-014 §References](../specs/014-multi-agent-channels-and-orchestration.md#references), the Preguiça CRDT overview). **Single owner:** this plan owns the whole directory — the producer (T2.14, `channel-directory-publisher.ts`, I-014-23) and the control-plane half alike (T2.17: the `channel.directoryPublish` ingest mutation, the retention fold, the `session_channel_directory` store, and the channel-list read path), both under CP-014-15. Splitting the producer from the ingest that folds its publications would put one contract across two build boundaries, and the convergence fold is the correctness argument; the daemon-to-control-plane call is an ordinary client call either way. Two legs ride the store and are not optional: the Spec-020 PII-map + erasure routing for the directory rows, without which the ingest does not go live, and the create-once origin-authentication binding on the disclosure-bearing fields. The disclosure boundary — the control plane learns existence metadata, never content — is stated in [Spec-014 §Interfaces And Contracts](../specs/014-multi-agent-channels-and-orchestration.md#interfaces-and-contracts).
- **D-014-23 — Plan-015 provider legs: per-channel turn budget + workflow interrupt reason** (the single-definition-home convention). `ChannelConfig` gains `turnsPerAgent?` — optional positive integer; the per-channel override of the session's `turn_limit_per_agent` (absent = session value); enforced by the T2.6 arbiter under the unchanged D-014-8 counting semantics (I-014-13's effective limit) — and `InterruptReason` grows to the four-member closed set with `workflow_phase_cancelled`, invoked only by the workflow engine's SA-9 `REQUEST_CANCEL`/`TERMINATE` cascade through the D-014-7 in-process entrypoint. Plan-015 sets the former at OWN-channel creation and names the latter in its cascade, authoring neither (CP-014-6). No new budget, wire method, event type, error code, or column (the override rides `channels.config` JSON). Like every `ChannelConfig` member the override is **create-time-fixed** — V1 ships no post-create channel-config mutation, so an overridden channel recovers from its limit by the interleaving-turn reset alone while the raise lever (`orchestration.budgetUpdate`) reaches only session-default channels; the post-create override mutation is the criterion-gated V1.1 seam recorded in [Spec-014 §Resolved Questions and V1 Scope Decisions](../specs/014-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions).
- **D-014-24 — Displayed cost and enforced cost are one fold** (per [Spec-014 §Resolved Questions and V1 Scope Decisions](../specs/014-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions)). Every surfaced cost figure is supplied by the committed-spend fold the accountant enforces against ([Spec-014 §Cost Figure Display Consistency](../specs/014-multi-agent-channels-and-orchestration.md#cost-figure-display-consistency)), and the budget state — served identically on the `orchestration.budgetRead` and `orchestration.budgetUpdate` replies, which are one `OrchestrationBudgetState` — **decomposes the number it already reported** rather than adding arithmetic: `observedPricedCostCents` + `observedUnpricedDebitCents` are exactly the two folds `observedCostCents` was already rebuilt from (D-014-5), `committedSpendCents` is the enforced sum, and the aggregate `costStatus` reuses the row-level Spec-005 vocabulary with aggregate semantics defined at the spec subsection — observability only, never a policy input, per the unchanged never-branch-on-provenance rule. Field-driven: the reference-runtime parity survey (2026-08-12, a first-party field observation) observed root runs displayed at their own ledger cost while delegated spend landed on their children, rendering a large multi-run campaign at a small fraction of its true cost; a receipt row per child run at whatever depth it sits (D-014-17 linkage, [Spec-014 §Session Cost Receipt](../specs/014-multi-agent-channels-and-orchestration.md#session-cost-receipt)) and roll-up of in-session subagent usage already bound the arithmetic, leaving the display rule as the residue. Three alternatives rejected: a display-side sum over the visible run list (the surveyed failure mode itself), a second presentation-side fold (two accountants over one event set diverge invisibly, since both look authoritative), and labelling the total a lower bound (true of a row-counting fold, false of this one — an unpriced run is charged its **full admitted cap**, so the figure over-states settled spend, and where the mid-run tier-(c) residue of clause (c) is present it is a bound in neither direction: non-exactness surfaces through the aggregate `costStatus`, never through a bound label). Mints no budget (the three-budget table is the closed set it was), no table, no event type, no wire method, and no error code; the wire members are additive-optional-free growth on an existing response shape ([api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md#plan-014--multi-agent-channels-and-orchestration)).

**Goal:** the session carries a collapsed, clickable cost line that expands into a decomposition of the committed-spend fold along both its axes.

- **T2.15 — Session cost receipt fold (D-014-25).**
  - **Files:** `packages/runtime-daemon/src/orchestration/budget-accountant.ts` (EXTEND).
  - **Provides:** the receipt accessor — a **decomposition of T2.5's existing committed-spend fold** along two partition axes (per run, per paying provider account), served from that same accessor and never re-folded beside it. Adds keys to the fold, not arithmetic: each unit of committed spend lands in exactly one row of each axis, the priced / unpriced-debit / reserved legs decompose along the axes exactly as clause (c)'s members do, and every row carries the aggregate `costStatus` vocabulary rather than any new honesty marker. Derivation stays **emit-once**: the receipt folds persisted `usage.cost_update` values plus cap-stamped terminal debits plus active reservations, and re-prices nothing at read time.

## Rollback Or Fallback

- Collapse delegated work to the synthesized main channel while preserving explicit parent-child linkage if channel delivery regresses ([Spec-014 §Fallback Behavior](../specs/014-multi-agent-channels-and-orchestration.md#fallback-behavior) — provenance preserved).
- The orchestration namespace is daemon-local: unregistering the Phase 3 binders disables the surface without touching Plan-003's queue.

## Risks And Blockers

- **Registry regex conformance and the typed-error projection (Plan-006-owned)** gate Phase 3 registration and typed wire errors; Phase 3 carries explicit precondition checkboxes (CP-014-12).
- Ordering: T2.8 requires Plan-010 Phase 2 (CP-014-5); the build order must respect it.
- Channel-level restriction policy remains V1-deferred ([Spec-014 §Resolved Questions and V1 Scope Decisions](../specs/014-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions)); every channel in a session is readable by the session's one user, and no agent-scoped read grant exists.
- Provider-native orchestration differences can leak into product semantics unless normalized at the daemon boundary (ADR-005; CP-014-13).
- Arbitration-pause and visibility detection latency is bounded by the roster poll cadence (CP-014-8) — acceptable for V1, documented at the arbiter.
