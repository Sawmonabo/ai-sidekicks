## Execution Windows (V1 Carve-Out)

Plan-008 ships in two windows — a **Tier 1 bootstrap-deliverable** (tRPC server skeleton + `sessionRouter` + SSE substrate) that unblocks [Plan-001](./001-shared-session-core.md) Phase 5, and a **Tier 5 remainder** that completes the relay/presence/invite surface. The split is documented authoritatively in [cross-plan-dependencies.md §5 Plan-008 Bootstrap-vs-Remainder Carve-Out](../architecture/cross-plan-dependencies.md#plan-008-bootstrap-vs-remainder-carve-out-tier-1--tier-5); this section is the plan-side restatement so engineers reading Plan-008 in isolation see the split.

The carve-out follows the **substrate-vs-namespace decomposition rule** documented authoritatively in [Plan-007 §Execution Windows](./007-local-ipc-and-daemon-control.md#execution-windows-v1-carve-out) — the _transport substrate_ (tRPC server + sessionRouter + SSE plumbing) is what Plan-001 Phase 5 consumes; the _relay/presence behavior_ is what Plan-008 owns canonically. Substrate ships first.

### Tier 1 — Plan-008-Bootstrap (tRPC server + `sessionRouter` + SSE substrate)

Lands alongside Plan-001 to unblock Plan-001 Phase 5 (`sessionClient` over the control-plane transport). Scope:

- **tRPC v11 server skeleton** — Cloudflare Workers host (entry point: `fetchRequestHandler` from `@trpc/server/adapters/fetch`) + tRPC v11 router registration scaffolding per [ADR-014](../decisions/014-trpc-control-plane-api.md). Local development uses the workerd runtime via `wrangler dev` (Miniflare v3); Tier 5 production deploys to Cloudflare Workers without runtime change. Bootstrap ships only the skeleton; relay broker / presence register / invite handlers are Tier 5.
- **`sessionRouter` HTTP handlers** — typed tRPC procedures for `SessionCreate`, `SessionRead`, `SessionJoin` exposing the existing `packages/control-plane/src/sessions/session-directory-service.ts` (already shipped in Plan-001 Phase 4). The router wraps the service; it does not re-implement directory logic.
- **SSE substrate for `SessionSubscribe`** — `SessionSubscribe` is request-only on the wire — the response is an `AsyncIterable<EventEnvelope>` SSE stream per `packages/contracts/src/session.ts#SessionSubscribeRequest`. The Tier 1 bootstrap ships the SSE transport plumbing (tRPC `subscription` procedure + Server-Sent-Events HTTP framing) that `sessionClient.subscribe` consumes from the control-plane side. Event sourcing into the stream remains Plan-006's domain; Plan-008-bootstrap supplies only the transport.

### Tier 5 — Plan-008-Remainder (relay + presence + invite acceptance)

Lands at Plan-008's original Tier 5 slot once Plan-002 (invite/presence) is complete. Tier 5 placement is unchanged because relay coordination depends on Plan-002. Scope:

- **Relay broker** (`relay-broker-service.ts`) — pairwise X25519 + XChaCha20-Poly1305 negotiation, relay sharding, WebSocket Hibernation per the original [§Implementation Steps](#implementation-steps) below.
- **Presence register fan-out** — Plan-008-remainder adds a **sibling** hosted-relay-presence-fan-out file under Plan-002's `packages/control-plane/src/presence/` directory. Plan-002 owns `presence-register-service.ts` (shipped NS-26 / PR #108); Plan-008-remainder EXTENDS the **directory**, never the file (CP-008-6; F-008r-D).
- **Invite-acceptance handoff** — wires Plan-002 invite resolution into the Tier 1 `sessionRouter`.
- **Reconnect association + relay negotiation** — `RelayNegotiation`, `SessionResumeAfterReconnect`, presence re-association.
- **Postgres tables** — `session_directory` and `relay_connections` per [Shared Postgres Schema](../architecture/schemas/shared-postgres-schema.md).
- **Client surfaces** — `apps/desktop/src/renderer/src/session-join/`, `apps/cli/src/session-join/`, and `packages/client-sdk/src/sessionJoinClient.ts`.

## Goal

Implement authenticated shared-session join, presence registration, and relay negotiation without shifting execution authority into the control plane.

## Scope

This plan covers join APIs, invite acceptance handoff, presence registration, relay negotiation, reconnect association, and client surfaces for shared-session join.

## Non-Goals

- Local IPC implementation
- Runtime-node attach internals
- Provider transport protocols

## Invariants

The following invariants are **load-bearing** and MUST be preserved across all Plan-008 PRs and downstream extensions. They split by execution window because Plan-008's scope expands materially between Tier 1 bootstrap and Tier 5 remainder.

### I-008-1 — Tier 1 bootstrap is operator-development-only behind a feature flag

Plan-008-bootstrap (Tier 1) ships the tRPC v11 server skeleton + `sessionRouter` + SSE substrate to unblock Plan-001 Phase 5. **It does not constitute a production-ready control-plane host.** The bootstrap MUST be gated behind a feature flag (or equivalent operator-only entry point) and MUST NOT be exposed on a non-loopback bind path or routed to from production deployments until Plan-008-remainder lands at Tier 5.

**Why load-bearing.** `Spec-027 §Required Behavior` governs the daemon-side bind-time secure-defaults surface (Plan-007's domain), but the SaaS Cloudflare Workers host that Plan-008-bootstrap creates is **explicitly outside Spec-027 scope** per [ADR-020](../decisions/020-v1-deployment-model-and-oss-license.md) (the SaaS deployment model is operator-provisioned hosting; Spec-027 governs self-host operator-facing daemon defaults). Production auth, rate-limiting (Plan-021), PASETO v4 token validation (Plan-018), and relay encryption (Plan-008-remainder) are all **NOT YET PRESENT** at Tier 1 — exposing the bootstrap to production traffic would bypass those surfaces entirely.

**Verification.** I-008-1 has TWO gates that BOTH must be enforced:

1. **Feature-flag gate.** Tier 1 PR must wire the bootstrap behind a feature flag (e.g., `CONTROL_PLANE_BOOTSTRAP_ENABLED=1`) that defaults off; production deployment configurations MUST NOT set the flag until Tier 5. Negative-path test: handler refuses to serve when the flag is unset in a production `wrangler` environment.
2. **Approved-dev-environment allow-list gate (per F-008b-1-04 — Workers-runtime equivalent of the original loopback-bind gate; allow-list pivot per Codex PR #20 round 4).** The Worker handler MUST refuse to serve any request unless the deployed environment is the explicit local-development marker (`env.ENVIRONMENT === 'development'`), returning HTTP 503 immediately before any router dispatch even when the feature flag is set. This is **allow-list semantics**, not deny-list — the gate refuses on `undefined`, `'production'`, `'staging'`, `'test'`, `''`, and any value other than the explicit `'development'` marker. The allow-list framing closes the round-4 exposure path Codex flagged: a deny-list `!== 'production'` gate would still pass on a default `wrangler deploy` Worker (no `--env`) where `ENVIRONMENT` is unset (because `ENVIRONMENT="development"` is also moved out of top-level `[vars]` to `.dev.vars` per the round-4 amendment — see T-008b-1-1), even after `wrangler secret put CONTROL_PLANE_BOOTSTRAP_ENABLED 1` (which targets the same default top-level Worker). Allow-list semantics require the `ENVIRONMENT` value itself to be explicitly present, so the only path to satisfying both gates on a deployed Worker is adversarial-admin behavior (`wrangler secret put ENVIRONMENT development` against a deployed Worker), which is outside I-008-1's accidental-exposure threat model. Cloudflare Workers do not expose a host-bind surface (the runtime maps requests via Cloudflare's edge routing per [ADR-014](../decisions/014-trpc-control-plane-api.md)), so the original Fastify-era loopback-bind gate translates to environment-scoped allow-list refusal. Positive-path test: `wrangler dev` (workerd locally) serves with flag set because `.dev.vars` supplies `ENVIRONMENT=development`. Negative-path test: table-driven over `undefined`, `'production'`, `'staging'`, `'test'`, `''` — handler refuses with 503 in every row even with flag set. Coordinate language with Spec-027's bind-time secure-defaults pattern (Plan-007's domain) — Spec-027 governs the daemon-side bind surface; I-008-1 is the SaaS-host parallel for the control-plane bootstrap. **Tier 5 gate-semantics obligation:** at Tier 5, the allow-list MUST widen to include the explicit `'production'` marker once relay/presence/invite surfaces ship and PASETO/rate-limiting (Plan-018, Plan-021) gate production traffic — tracked as part of I-008-2 Tier 5 wiring.

### I-008-2 — Tier 5 production invariants apply once their substrates land

The production-grade invariants that apply **at Tier 5** — PASETO v4 token validation on every endpoint (per [ADR-010](../decisions/010-paseto-webauthn-mls-auth.md) + [Plan-018](./018-identity-and-participant-state.md), the co-tier Tier 5 PASETO issuer), relay-broker encryption (pairwise X25519 + XChaCha20-Poly1305 per [ADR-010](../decisions/010-paseto-webauthn-mls-auth.md)), and invite-acceptance handoff to [Plan-002](./002-invite-membership-and-presence.md) (Tier 2, shipped NS-14/NS-26) — decompose into the concrete, individually-testable guarantees **I-008-4 … I-008-11** below. Plan-008-remainder MUST gate those surfaces on their dependencies being satisfied per [cross-plan-dependencies.md §5](../architecture/cross-plan-dependencies.md#5-canonical-build-order).

**Rate-limiting is NOT a Tier-5 surface (mis-tiering correction).** The original I-008-2 listed "rate-limiting middleware (per Plan-021)" among the surfaces that "apply at Tier 5 once … Plan-021 … substrates land" — but [Plan-021](./021-rate-limiting-policy.md) is **Tier 6, strictly downstream of Plan-008** (per [Plan-021 §Tier Placement](./021-rate-limiting-policy.md#tier-placement): "Strictly downstream of Plan-008 — this plan consumes Plan-008's tRPC router and WS frame hook"). Plan-021's substrate cannot "land at Tier 5"; it lands at Tier 6 and **mounts its `rateLimitProcedure` middleware onto Plan-008's `packages/control-plane/src/server/` host** (per [cross-plan-dependencies.md §2 `packages/control-plane/src/server/` row](../architecture/cross-plan-dependencies.md#2-package-path-ownership-map): "Plan-021 (Tier 6 — rate-limiter middleware mount)"). Plan-008-remainder therefore exposes a stable mount surface but does **not** wire rate-limiting — exactly mirroring [Plan-002 CP-002-3](./002-invite-membership-and-presence.md#cross-plan-obligations) (invite-endpoint rate-limit deferred to Tier 6 post-Plan-021, [BL-120](../backlog.md)). The reciprocal obligation is **CP-008-5** below.

**Why load-bearing.** Shipping Tier 5 surfaces without their dependencies would either silently no-op (auth bypass) or hard-fail at runtime. The dependency tier graph is the only way to keep the substrate composition correct.

**Verification.** Tier 5 PRs must reference and wire the actual Plan-018 (PASETO issuer) + Plan-002 (invite/presence) surfaces — not stubs. Integration tests must exercise the full PASETO-auth + relay-encryption stack end-to-end before Tier 5 PRs merge (concrete per-surface assertions: I-008-4 … I-008-11). Rate-limit wiring is verified at **Tier 6** by Plan-021 against this plan's mount surface (CP-008-5), not here.

### I-008-3 — Substrate wraps, never re-implements, the directory service

Plan-008-bootstrap's `sessionRouter` and `session-router.ts` MUST wrap the existing `packages/control-plane/src/sessions/session-directory-service.ts` shipped by Plan-001 Phase 4. Re-implementing directory logic in the router would fork the lock-ordering invariant (per [Plan-001 §Invariants I-001-1](./001-shared-session-core.md#invariants)) and break the `Querier`-driven test pattern Plan-001 Phase 5 strengthens.

**Why load-bearing.** Plan-001 owns the directory service. Plan-008 owns the HTTP transport. Conflating the two violates the Plan-001 ownership row in [cross-plan-dependencies.md §2 `packages/control-plane/src/sessions/`](../architecture/cross-plan-dependencies.md#2-package-path-ownership-map).

**Verification (per F-008b-1-05 resolution).** Three concrete enforcement mechanisms — all three MUST land in the Phase 1 PR:

1. **Constructor injection.** `session-router.ts` exports a factory function that accepts a `SessionDirectoryService` instance: `createSessionRouter(directoryService: SessionDirectoryService): TRPCRouter`. The router's procedures call `directoryService.*` methods exclusively; the factory does NOT instantiate a `Querier` or `pg.Pool` directly. Same pattern for `session-subscribe-sse.ts`: `createSessionSubscribeSse(directoryService: SessionDirectoryService): SseHandler`.
2. **ESLint `no-restricted-imports` rule.** Forbid `pg`, `pg-pool`, and `@databases/pg` imports from `packages/control-plane/src/sessions/session-router.ts` and `packages/control-plane/src/sessions/session-subscribe-sse.ts`. Rule lives in the package-level ESLint config; CI enforces it.
3. **Unit-test introspection assertion.** Test asserts (via TypeScript symbol introspection or a small AST walker) that the two files' exported symbols call only `directoryService.*` methods at the top-level execution path. The integration-test layer reuses Plan-001 Phase 4's `Querier`-driven test pattern — the router inherits I-001-1 lock-ordering by routing through the directory service.

### Tier 5 production invariants (decomposition of I-008-2): I-008-4 … I-008-11

The following decompose the I-008-2 umbrella into the concrete, individually-testable production guarantees the Tier 5 remainder MUST hold. Each cites its Spec-008 / ADR-010 source and is proven by a named surface in the [§Test And Verification Plan](#test-and-verification-plan). Kept compact deliberately — the umbrella invariants (I-008-1/2/3) carry the verbose rationale; these are the enforceable leaves.

### I-008-4 — PASETO v4 validation on every Tier-5 endpoint

Every control-plane Tier-5 endpoint (`SessionJoin`, `PresenceRegister`, `RelayNegotiation`, `SessionResumeAfterReconnect`) **and** the relay WSS handshake MUST validate a PASETO v4.public token before any dispatch ([Spec-008 §Relay Connection Lifecycle](../specs/008-control-plane-relay-and-session-join.md#relay-connection-lifecycle) `Sec-WebSocket-Protocol: paseto-v4, <base64url(token)>`; `Spec-008 §Interfaces And Contracts`). Validation consumes the Tier-1-shipped `@ai-sidekicks/crypto-paseto` `verify` primitive (PR #92) against the [Plan-018](./018-identity-and-participant-state.md)-published issuer key (CP-008-4). No endpoint serves on an absent / expired / invalid token. Rate-limit middleware is a separate Tier-6 layer (CP-008-5), not part of this invariant.

### I-008-5 — Relay is zero-knowledge (E2EE; never plaintext)

The relay broker MUST forward only opaque per-recipient `{sender_ephemeral, recipient_id, seq, nonce, ciphertext+tag}` envelopes and MUST NOT decrypt, inspect, or persist plaintext payloads (`Spec-008 §Relay Encryption`, `Spec-008 §Relay Connection Lifecycle`, `Spec-008 §Trust Properties` — honest-but-curious relay threat model; the broker routes on `recipient_id` alone and forwards `sender_ephemeral`/`seq`/`nonce`/`ciphertext+tag` opaquely). Relay sharding and WebSocket Hibernation operate on ciphertext frames only.

### I-008-6 — Session-granularity forward secrecy via ephemeral-key zeroization

Each participant generates an ephemeral X25519 key pair **per session** (not per message); the secret key and all derived pairwise session keys MUST be zeroed in memory at session end (`Spec-008 §Relay Encryption`, `Spec-008 §Relay Connection Lifecycle`, `Spec-008 §Trust Properties`). Compromise of the long-term Ed25519 identity key MUST NOT reveal past session keys.

### I-008-7 — Control-plane `SessionKeyBundle` admission is identity-bound and single-use

Before distributing any `SessionKeyBundle` the control plane MUST: (a) verify the Ed25519 signature over `session_id ‖ ephemeral_x25519_public` (`Spec-008 §Relay Encryption`, `Spec-008 §Relay Negotiation`); (b) reject any bundle whose Ed25519 signing key is not bound to a registered participant identity (`Spec-008 §Trust Properties`); and (c) reject reused ephemeral X25519 public keys across distinct sessions (`Spec-008 §Relay Negotiation`). A compromised control plane cannot forge valid Ed25519 signatures.

### I-008-8 — In-session replay protection via AEAD-bound monotonic sequence

Per-sender monotonic sequence numbers MUST be bound into the AEAD associated data (alongside `recipient_id`) **and** carried in the envelope in the clear so the receiver can reconstruct the associated data; a tampered `seq` fails the AEAD tag. Recipients MUST reject out-of-order / replayed frames within a session (`Spec-008 §Relay Encryption`, `Spec-008 §Trust Properties`).

### I-008-9 — Reconnect re-associates, never duplicates, participant identity

Switching between direct and relay connectivity, or reconnecting within the grace window, MUST re-associate the same participant presence rather than mint a second session identity (`Spec-008 §Fallback Behavior`; **`Spec-008 §Acceptance Criteria` (AC2)**). `SessionResumeAfterReconnect` accepts the prior participant / client handle (`Spec-008 §Interfaces And Contracts`).

### I-008-10 — Control plane is never the execution authority

Control-plane join / relay / presence MUST NOT become the source of truth for run-execution state, and relay connectivity MUST NOT be treated as proof of execution authority (`Spec-008 §State And Data Implications`, `Spec-008 §Pitfalls To Avoid`; **`Spec-008 §Acceptance Criteria` (AC3)**).

### I-008-11 — Join is a membership action separable from relay connectivity

`SessionJoin` (membership) MUST succeed independently of relay (connectivity): a relay-setup failure leaves the join valid with degraded remote connectivity, never a failed join (`Spec-008 §Fallback Behavior`, `Spec-008 §Implementation Notes`; **`Spec-008 §Acceptance Criteria` (AC1)**). The V1 pairwise participant cap (≤ 10, `Spec-008 §Relay Encryption`) is the **same** cap Plan-001's join already enforces (`resource.limit_exceeded`, [Spec-001 §Resource Limits](../specs/001-shared-session-core.md#resource-limits)) — the relay inherits it; no separate relay-side cap is enforced.

### I-008-12 — Client event-stream resume is floor-checked, gap-safe, and at-most-once-applied

Campaign-B12 consumer-contract invariant (it enforces the consumer rule [Plan-006 T4.3](./006-session-event-taxonomy-and-audit-log.md#t43--replay-servicets-for-eventreadaftercursor--eventreadwindow) states producer-side; it is **not** part of the I-008-4 … I-008-11 decomposition of I-008-2). Any Plan-008 client surface that resumes a session event stream MUST: **(a)** resume from `acknowledged ?? earliest` (`SessionReadResponse.timelineCursors`, [api-payload-contracts.md §Tier 1: Plan-001 — Shared Session Core (Task 4.2)](../architecture/contracts/api-payload-contracts.md#tier-1-plan-001--shared-session-core-task-42)); **(b)** treat the gap predicate `decodeEventCursor(acknowledged) < decodeEventCursor(earliest)` — and its two converging siblings, an unresolvable `acknowledged` cursor (the typed `event.cursor_unresolvable`) and a live-stream sequence gap — as events-lost: reset the projection and resume from `earliest`, while a clean floor (`decode(acknowledged) === decode(earliest)`) MUST NOT trigger a reset (the T4.3 no-false-resync rule); **(c)** never double-apply a sequence under at-least-once delivery — a high-water-mark of the last applied `sequence` dedupes both the drain/live overlap and reconnect redelivery (SSE `Last-Event-ID` resumption floors replay at the last-delivered cursor, so redelivery of already-applied events is the expected steady state); and **(d)** when `earliest` is absent (a pre-widening responder, version skew), skip gap detection and conservatively full-replay from start-of-log (the cursorless read) rather than trusting `acknowledged` unchecked.

**Why load-bearing.** A resume that skips the floor check silently loses events whenever the acknowledged position has fallen below the surviving floor — every downstream projection (timeline rendering, recovery replay, rollback anchors) is corrupted with no diagnostic. A resume without the high-water-mark double-applies under at-least-once delivery, corrupting projections in the opposite direction. Plan-006 T4.3 states this contract from the producer side; I-008-12 is the consumer-side enforcement Plan-008's client surfaces carry (CP-008-10), and it is what keeps the `Spec-008 §Default Behavior` "live replay cursors as part of successful join" promise honest end-to-end.

**Verification.** Tests T-008r-4-T21..T29 (T-008r-4-13 — nine named tests per the [campaign design §4 W2 B12 row](../superpowers/specs/2026-07-01-capability-enhancements-design.md)).

### CP-008-9 — Per-frame admission seam owed to [Plan-021](./021-rate-limiting-policy.md) (Tier 6, downstream; minted at the Tier-6 audit, D-021-2)

R3's zero-knowledge DO relay broker MUST expose a **per-decoded-frame admission seam** — an injectable hook invoked once per decoded inbound frame, **before** fan-out: `onFrame(connection, frame) → { proceed: true } | { proceed: false, sendFrame: <in-band error frame> } | { proceed: false, close: { code, retryAfter } }`. The hook receives **ciphertext-envelope metadata + the authenticated connection principal only** — never plaintext payload — preserving I-008-5 (the broker stays zero-knowledge; rate-limit accounting needs frame counts and principals, not content). The hook returns the outcome; the **broker** performs the resulting send/close (single-signal contract — the hook never writes to the connection). Default when no hook is injected: admit-all (R3 ships with the seam unbound; Plan-021's Phase 3 binds `wsRateLimit` into it).

**Why bidirectional.** Plan-021's WS enforcement (`ws.message`, 60/min/participant per [Spec-021 §Canonical Endpoint Group Registry](../specs/021-rate-limiting-policy.md#canonical-endpoint-group-registry)) cannot exist without a hosted per-frame interception point, and Spec-021's drop-frame overflow semantics (in-band `rate_limited` frame on counter trip; close `4029` only on active block, `4003` on ban — Plan-021 D-021-9, [api-payload-contracts.md §Relay Rate-Limit Signalling](../architecture/contracts/api-payload-contracts.md#relay-rate-limit-signalling)) constrain the seam's outcome shape. R3 reviewers must know the seam is load-bearing for Tier 6 and keep it stable; Plan-021 consumes it as [CP-021-5](./021-rate-limiting-policy.md#cross-plan-obligations). The self-host relay path is independent (Plan-025 wires `wsRateLimit` into its own frame handler — no seam consumption).

## Ratified Design Decisions (Tier 5 audit, 2026-05-30)

The Tier-5 plan-readiness audit (NS-17) authored the un-tasked Plan-008 remainder (R1–R4) and surfaced four named Open Decisions plus twelve per-phase ODs (the latter author-resolved in-band — see the §Decision Log NS-17 rows). - **OD-008r-1 — three relay error codes registered (Type 1).** `relay.bundle_rejected` (403; R3 bundle-admission of an unregistered identity — OD-3-1), `relay.replay_rejected` (R4 monotonic-seq replay — I-008-8), and `relay.bundle_signature_invalid` (R4 client-side peer-bundle re-verify) are registered in `error-contracts.md` at swap. None reuses the handshake-scoped `relay.authentication_failed`.
- **OD-008r-2 — durable `relay_seen_ephemeral_keys` store (Type 2).** The I-008-7(c) cross-session ephemeral-reuse guard has no storage home in the frozen per-session-DO schema (discard-on-close structurally cannot observe cross-session reuse), so a durable uniqueness-indexed `relay_seen_ephemeral_keys` store is added to the R1 relay migration + `shared-postgres-schema.md` at swap. **Retention is full-horizon by design, not an open sliver.** The dedup key (the ephemeral X25519 public key) is client-minted with no server-anchored birth time, so no bounded TTL can enforce the I-008-7(c) cross-session-reuse guard without reopening the `Spec-008 §Relay Negotiation` forward-secrecy hole — a windowed store forgets a key the client can then re-present under a fresh timestamp. The store therefore remembers every key for the (session × participant) lifetime; growth is an ops concern (time-partition, never `DROP`), decoupled from the security property. The audit ratifies the store as durable + uniqueness-indexed + **full-horizon** (the committed `shared-postgres-schema.md` `relay_seen_ephemeral_keys` design, NS-17 round-6); any future bounding is a separate Spec-008 Type-2 decision, not a V1 open question.
- **OD-008r-3 — inject Plan-018 `RelayConnectionTokenIssuer` (CP-008-4 surface (c); Type 1).** The 300s `RelayNegotiationResponse.connectionToken` is a PASETO v4.public **sign** that MUST NOT run inside the verify-only zero-knowledge broker (I-008-5). R3's `RelayNegotiation` endpoint (T-008r-3-6) consumes a constructor-injected issuer whose signing key + custody stay entirely with Plan-018; R3 authors no sign. The issuer-surface shape is Plan-018-owned.
- **OD-008r-4 — participant signer-provider deferred to ADR-021 / Plan-023; `client-sdk` module placement (Type 1).** R4 owns the Ed25519 signing _operation_ via an injected sign-only `Ed25519IdentitySigner` (CP-008-8); concrete key custody is deferred to ADR-021 (CLI at-rest) / ADR-010 + Plan-023 (desktop WebAuthn-PRF). A `FixtureEd25519IdentitySigner` keeps R4 buildable + unit-testable ahead of the custody producers. The participant relay crypto lands as a `packages/client-sdk/src/relay/` **module** (not a new `packages/crypto-relay/` package — no second cross-package consumer forces one, and minting a package would be unauthorized scaffolding). The reciprocal `provides` note on the custody producer is a fix-in-place obligation at swap.

