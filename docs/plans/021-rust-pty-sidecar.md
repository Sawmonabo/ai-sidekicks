## Goal

Ship a Rust PTY sidecar binary implementing the `PtyHost` contract, distributed per-platform via npm `optionalDependencies`, signed for Windows and macOS per each platform's trust-chain requirements, and wired as the **Windows-primary** PTY backend with `node-pty` as the macOS/Linux primary and the Windows fallback. This closes the structural fix named by ADR-018 against the `node-pty` ConPTY bug cluster ([openai/codex#13973](https://github.com/openai/codex/issues/13973), [microsoft/node-pty#904](https://github.com/microsoft/node-pty/issues/904), [microsoft/node-pty#887](https://github.com/microsoft/node-pty/issues/887), [microsoft/node-pty#894](https://github.com/microsoft/node-pty/issues/894)).

## Build Order

Daemon-foundational, beside Plan-001. Standalone for Phases 1–3 (no upstream plan dependencies); Phase 3B follows Phase 3 with no other gate, and Phases 4–5 are the release tail, whose signing steps run once [BL-108](../backlog.md#bl-108-plan-021-windows--macos-signing-procurement-evidence) records SignPath Foundation's acceptance and the Apple Developer ID certificate. The plan's phases sit in the dispatch groups [cross-plan-dependencies §Dispatch groups](../architecture/cross-plan-dependencies.md#dispatch-groups) lists.

## Scope

- Rust `sidecar-rust-pty/` crate built on `portable-pty ≥ 0.9.0` (WezTerm), pinned via `Cargo.toml` + `Cargo.lock` committed to the repo
- LSP-style Content-Length stdio framing (ADR-009 parity), JSON control channel + length-prefixed binary frames for stdout/stderr
- Six platform packages (`@ai-sidekicks/pty-sidecar-{win32-x64,win32-arm64,darwin-arm64,darwin-x64,linux-x64,linux-arm64}`) + umbrella `@ai-sidekicks/pty-sidecar` meta-package with `optionalDependencies` + `os`/`cpu` filters, matching the [esbuild platform-package pattern](https://www.npmjs.com/package/esbuild) (26 `@esbuild/*` packages in 0.28.0, released 2026-04-02); the six cover every platform Electron 44 ships, Windows on ARM included
- `PtyHost` TypeScript interface in the daemon's `packages/runtime-daemon/src/pty/` — two implementations (`RustSidecarPtyHost`, `NodePtyHost`) + a `PtyHostSelector` that picks Windows-primary / Unix-primary defaults with an env-var override
- Daemon-side sidecar supervision: spawn, health check, respawn on crash, fall back to `NodePtyHost` if the sidecar binary is not resolvable
- **Windows signing** through SignPath Foundation's free open-source program: one step in the release workflow signs the Electron app, the sidecar and the service's Windows half (`sidekicks-windows-half.exe`) under one publisher ([ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-sidecar.md#decision) items 7 and 8)
- **macOS signing**: until the Apple Developer ID certificate exists ([BL-108](../backlog.md#bl-108-plan-021-windows--macos-signing-procurement-evidence)), each macOS sidecar binary is signed with the project's own self-signed code-signing identity, the one every macOS build carries; afterward, Apple Developer ID Application codesign + `xcrun notarytool` (standalone Mach-O sidecar binaries cannot be stapled per [Apple notarytool docs](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow) — quote: "Although tickets are created for standalone binaries, it's not currently possible to staple tickets to them"; Gatekeeper fetches the ticket via `gktool` at first launch on a network-connected machine), on the same certificate identity as Spec-021's desktop app (reuse of identity; net-new operation since npm-delivered Mach-O binaries ship outside the .app bundle and therefore are NOT covered by the app's notarization ticket)
- **Linux**: no universal signing model; ship the ELF stripped
- CI cross-compile matrix using `cargo-zigbuild v0.22.2` (2026-04-16), with native `macos-14` / `macos-15` arm64 runners for `darwin-arm64` to side-step [cargo-zigbuild#316](https://github.com/rust-cross/cargo-zigbuild/issues/316) (aarch64-apple-darwin iconv linker regression with `zstd-sys` dependencies under Rust ≥ 1.82) and native `windows-11-arm` runners for `win32-arm64`; the same workflow's Windows legs build the service's Windows half (`packages/service-windows-half`) for x64 and arm64
- **Phase 3B — PTY substrate hardening:** tier-1 respawn-as-recovery (5/60 s crash budget + inter-attempt backoff + manual reset) and tier-2 hardened resync (additive sidecar wire pair); the two-layer orphan-process defense per ADR-018 (per-OS kernel containment incl. sidecar-side `child_guard.rs`; daemon-side crash-safe orphan registry + boot-id-guarded sweep with the pidfd-preferred Linux signal path); a session's shells (`pty.list`, `pty.open`, `pty.close`, `pty.reorder`, `pty.outputSubscribe`, `pty.write`, `pty.resize`) and the Spec-002 per-shell write lease enforced at the daemon terminal-write boundary (`control-lease.ts`, `session.takeControl`), held in the daemon alone; real `signal_code` population; the terminal's own flow control propagated to the PTY per shell and per watching connection (the additive flow-control pair and the `PtyHost` pause / resume it answers); and the I-021-1/I-021-2 Windows kill wire-through into `pty_session.rs::kill()`

## Non-Goals

- WezTerm-level terminal-emulator features — the sidecar muxes PTYs, it does not render UI
- Sidecar-layer TLS or authentication — the sidecar talks stdio only, parent-child, inheriting the daemon's process boundary
- Upgrading the `node-pty` fallback to `useConptyDll: true` — deferred per ADR-018 Tripwire 3 until [microsoft/node-pty#894](https://github.com/microsoft/node-pty/issues/894) closes
- macOS or Linux sidecar as primary — those platforms use in-process `node-pty` by default per ADR-018; the sidecar is still published there as an env-var-selectable override and as insurance against future platform-specific `node-pty` regressions
- A hash check of the sidecar binary before it runs — the daemon runs the binary it resolves, and a corrupt binary shows as a terminal that fails to start

## Invariants

Invariants I-021-1 through I-021-5 come from §Windows Implementation Gotchas (which carries their rationale and primary-source citations) and MUST hold across the daemon ↔ sidecar boundary on Windows; I-021-6 arises from the daemon ↔ sidecar wire-race contract; I-021-7 through I-021-12 land with the Phase 3B substrate hardening — their sources are the [ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-sidecar.md#decision) items and the [Spec-002 §Required Behavior](../specs/002-runtime-node-attach.md#required-behavior) shared-terminal write-lease contract, and they hold on every platform (I-021-9/I-021-10 at the daemon terminal-write boundary).

### I-021-1 — Windows kill semantics translate at `PtyHost.kill`, not `portable-pty` default

`PtyHost.kill(sessionId, signal)` on Windows MUST translate POSIX signal semantics to the `GenerateConsoleCtrlEvent` API: `SIGINT` → `CTRL_C_EVENT`; hard-stop → `CTRL_BREAK_EVENT` followed by escalation per I-021-2 if the child does not exit within a bounded interval. Implementation lives in `pty_session.rs::kill()`; the sidecar MUST NOT delegate to `portable-pty`'s default kill behavior on Windows. Source: §Windows Implementation Gotchas Gotcha 1 (`microsoft/node-pty#167`). **Verification:** Phase 2 Test K1 (`packages/runtime-daemon/src/pty/__tests__/node-pty-host.kill-translation.test.ts` — asserts `SIGINT` invokes `windows.GenerateConsoleCtrlEvent(CTRL_C_EVENT, child.pid)` rather than `process.kill`); Phase 3 Test K2 substrate (`packages/sidecar-rust-pty/src/kill_translation.rs::tests` — asserts the POSIX → Win32 translator maps `SIGINT` → `CTRL_C_EVENT` and the hard-stop signal sequence to `CTRL_BREAK_EVENT`); end-to-end `pty_session.rs::kill()` Windows-arm wire-through lands at T-021-3B-6 (§Implementation Phase Sequence Phase 3B; Tests K5–K6), with Windows e2e validation completing under Phase 5's CI surface.

### I-021-2 — Hard-stop teardown uses `taskkill /T /F` for full process-tree termination

A single-PID kill on Windows leaves descendants orphaned. The hard-stop path MUST invoke `taskkill /T /F /PID <root-pid>` so the entire descendant tree terminates. Reaping MUST be idempotent and MUST NOT block the sidecar's main loop — invoke `taskkill` with a timeout and emit `ExitCodeNotification` even if reaping is incomplete, so the daemon can mark the session terminated without hanging on a stuck OS-level operation. Source: §Windows Implementation Gotchas Gotcha 2 (`microsoft/node-pty#437`). **Verification:** Phase 2 Test K3 (`packages/runtime-daemon/src/pty/__tests__/node-pty-host.tree-kill.test.ts` — spawns a parent with two grandchildren; asserts hard-stop reaps the entire tree via `taskkill /T /F` and times out at 2 s emitting `ExitCodeNotification` regardless of OS-reaping completion); Phase 3 Test K4 substrate (`packages/sidecar-rust-pty/src/tree_kill.rs::tests` — asserts `taskkill_argv(pid)` produces the canonical `["taskkill", "/T", "/F", "/PID", <decimal-pid>]` argv); end-to-end wire-through lands at T-021-3B-6 (§Implementation Phase Sequence Phase 3B; Tests K5–K6), with Windows e2e validation completing under Phase 5's CI surface.

### I-021-3 — Sidecar does NOT translate WSL2 paths; that translation is daemon-layer

The sidecar MUST pass `SpawnRequest.cwd` and `SpawnRequest.env` paths to `portable-pty` verbatim and MUST NOT invoke `wslpath` or any Windows ↔ WSL2 path conversion. Any `wslpath`-style translation is a daemon-layer step that runs **before** the `SpawnRequest` reaches the sidecar. On a Windows computer whose providers live in WSL 2 the service runs inside that distribution, its shells run through the Linux daemon's `node-pty` in the person's login shell with a Linux working folder, and the daemon translates every path with `wslpath` there (a path in another distribution's share is refused), so the sidecar, which stays native-Windows only, never serves that arrangement. Negative invariant: scope-boundary declaration that prevents sidecar / daemon coupling. Source: §Windows Implementation Gotchas Gotcha 3. **Verification:** Phase 3 Test W1 (`packages/sidecar-rust-pty/src/wsl_pass_through.rs::tests` — feeds the sidecar a `\\wsl.localhost\Ubuntu\home\foo` path and asserts the path is forwarded to `portable-pty` byte-identical; lint `clippy::ban_path_translation` rejects `wslpath` invocation in the crate).

### I-021-4 — The app's quit never stops a shell; the sidecar drains only when the service stops

The desktop app never owns the sidecar or its shells. The sidecar is a child of the daemon, and the daemon is the person's own background service, never a child of the app: quitting the app flushes the service (`daemon.flush`) and leaves the service, every run and every shell running, so no Electron quit handler touches the sidecar, and a server started in a shell is still serving after a relaunch. Only the service's own stop — Runtime's `Stop` or `Restart`, or the operating system's service manager stopping it — ends the shells, and that stop drains the sidecar before the daemon exits: emit `KillRequest` for every live session, await `ExitCodeNotification` per session with a bounded timeout, close the sidecar's stdin, await its exit, and escalate to `taskkill /T /F /PID <sidecar-pid>` on timeout, so no child PTY process orphans when the service exits. No surface explains either rule; the behavior is the rule. **Cross-plan obligation:** Plan-001 owns the drain orchestration per [Plan-001 §Cross-Plan Obligations CP-001-1](./001-session-core.md#cp-001-1--the-sidecar-drains-when-the-service-stops); Plan-021 supplies the `PtyHost.shutdown(options)` drain protocol surface (method signatures pinned, see §Target Areas `packages/runtime-daemon/src/pty/pty-host.ts` row), which both `RustSidecarPtyHost` and `NodePtyHost` implement so the lifecycle wiring stays backend-agnostic ([ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-sidecar.md#decision) item 4 polymorphism). Source: §Windows Implementation Gotchas Gotcha 4 (`microsoft/node-pty#904`). **Verification:** `packages/runtime-daemon/src/pty/__tests__/node-pty-host.shutdown.test.ts` (in-process backend) and `packages/runtime-daemon/src/pty/__tests__/rust-sidecar-pty-host.shutdown.test.ts` (out-of-process backend, including the sidecar stdin-close → child-exit → taskkill escalation chain and the `-1` crash-sentinel suppression on the deliberate exit). Plan-021 Phase 3 supplies the `PtyHost.shutdown(options)` drain primitives + sidecar `KillRequest` wire support at T-021-3-1 unconditionally.

### I-021-5 — `SpawnRequest.cwd` carries a stable path; daemon performs worktree translation

The sidecar's protocol-level `SpawnRequest.cwd` MUST always carry a stable, unmovable parent directory (e.g., the daemon's own working dir or the user-home root). Worktree paths live in the command-string-or-env layer above (`cd <worktree-path> && ` shell prefix or `CWD=<worktree-path>` environment propagation). **Cross-plan obligation:** Plan-001 owns the daemon-layer `PtyHost.spawn(spec)` translation that converts a logical worktree-path `spec.cwd` into the (stable parent dir, prefixed command) tuple before forwarding to the sidecar; the sidecar MUST NOT know about worktree semantics. The constraint is OS-level; `NodePtyHost` fallback inherits the same constraint. Source: §Windows Implementation Gotchas Gotcha 5 (`microsoft/node-pty#647`). **Verification:** Phase 3 Test W2 (`packages/runtime-daemon/src/pty/__tests__/spawn-cwd-translation.test.ts` — feeds the spawn-cwd-translator a logical worktree path and asserts the outgoing `SpawnRequest.cwd` carries the daemon's stable parent dir + the command string carries the `cd <worktree-path> && ` prefix) AND Phase 3 Test W3 (`packages/runtime-daemon/src/pty/__tests__/no-error-sharing-violation.test.ts` — spawns a long-running session with logical worktree cwd, asserts `git worktree remove <worktree-path>` succeeds without `ERROR_SHARING_VIOLATION` while the session runs). NodePtyHost (Phase 2) inherits the same translator path so I-021-5 is verified across both backends.

### I-021-6 — `PtyHost.onExit` / `onData` fire for every successfully-spawned session, including pre-spawn-response wire events

`PtyHost.onExit(sessionId, exitCode, signalCode?)` MUST fire exactly once for every session where `PtyHost.spawn()` returned a successful `SpawnResponse` (i.e., the wire `SpawnResponse.error` field was absent), regardless of how soon the child exits relative to spawn-response delivery. The same completeness clause holds for `PtyHost.onData(sessionId, chunk)` for every chunk the sidecar's stdout/stderr reader pump emits between spawn and exit. This includes sub-millisecond-lived children whose `ExitCodeNotification` AND/OR `DataFrame` is observed on the wire BEFORE the matching `SpawnResponse` frame (the race is reachable: per `packages/sidecar-rust-pty/src/pty_session.rs` `spawn()`, `spawn_reader_task` + `spawn_waiter_task` are spawned BEFORE the dispatcher queues `SpawnResponse` on `dispatch_tx`, and `merge_to_writer`'s unbiased `tokio::select!` can pick `outbound_tx` first).

Out-of-process backends with separate wire channels for response dispatch vs. async events (`RustSidecarPtyHost`'s sidecar emits `SpawnResponse` on `dispatch_tx` and `ExitCodeNotification` / `DataFrame` on `outbound_tx`) MUST:

1. Buffer pre-spawn `ExitCodeNotification` + `DataFrame` envelopes keyed by `session_id` when the inbound frame arrives for a session_id that has not yet appeared in the daemon's session table.
2. Replay the buffered envelopes after registering the session via spawn-response handling — order preserved (data chunks in arrival order; exit notification last per the wire's exactly-once-per-session contract).
3. Defer the replay to a separate I/O turn (e.g., `setImmediate` with `unref()` so the daemon process can exit while a replay is queued) so the consumer's `await spawn()` continuation runs and records `sessionId` in consumer-side state BEFORE the buffered listener fan-out fires. Without this defer, `onExit(sessionId, ...)` would fire synchronously inside the drain loop, before the consumer's `await spawn()` continuation has scheduled `sessions.set(sessionId, ...)` on its own microtask, breaking the substitutability-with-`NodePtyHost` invariant.
4. Clear pre-spawn buffers on supervisor teardown (`handleChildExit` / `handleChildError`) — the sidecar's monotonic `session_id` counter resets on respawn (per `packages/sidecar-rust-pty/src/pty_session.rs`), so retention across supervisor lifetimes would cause stale-id replay against a fresh child's fresh session.
5. Honor the post-`close()` onExit-suppression contract: a session_id removed from the session table by `close()` MUST suppress (not buffer) subsequent `ExitCodeNotification` / `DataFrame` for that id, preserving the "MUST NOT fire after `close()` resolves" clause on the `PtyHost.onExit` contract surface.

In-process backends (`NodePtyHost`) inherit this invariant structurally: `pty.spawn()` returns the child handle synchronously and the `child.onExit` / `child.onData` JS-callback subscriptions complete inside the same synchronous spawn frame, so no async wire race can lose events for sub-millisecond-lived children. `NodePtyHost` therefore satisfies I-021-6 by construction.

Source: `packages/runtime-daemon/src/pty/pty-host.ts` `onData` + `onExit` rustdoc (the consumer-visible contract surface); `packages/sidecar-rust-pty/src/main.rs` `merge_to_writer` (the wire-side race source); `packages/sidecar-rust-pty/src/pty_session.rs` `spawn()` (the pre-emit ordering source).

**Verification:** Phase 3 Tests PE1–PE5 (`packages/runtime-daemon/src/pty/__tests__/rust-sidecar-pty-host.test.ts`) — PE1: ExitCodeNotification-before-SpawnResponse same-chunk (onExit fires after spawn() resolves); PE2: DataFrame-before-SpawnResponse same-chunk (onData fires after spawn() resolves); PE3: DataFrame + ExitCodeNotification + SpawnResponse same-chunk preserving wire arrival order (onData fires before onExit, both fire after spawn() resolves); PE4: cross-chunk DataFrame-before-SpawnResponse (buffer survives drain-cycle boundary); PE5: pre-spawn buffer cleared on supervisor teardown (a fresh post-respawn session reusing a previously-buffered session_id does not replay stale events). `NodePtyHost` inherits I-021-6 structurally; no additional test required for the `node-pty` code path.

### I-021-7 — Sidecar respawn is bounded recovery, never session continuity

Supervisor respawn after a sidecar crash is **tier-1 recovery** under the ADR-018 crash budget (5 failures per 60 s window, the systemd-StartLimit-parallel budget of [ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-sidecar.md#decision) item 10): attempts are separated by deterministic inter-attempt backoff (250 ms base, doubling per consecutive failure, 4 s cap — deterministic, no jitter, so tests can assert the schedule), budget exhaustion enters fail-stop (`PtyBackendUnavailable` per T-021-3-1) rather than a hot crash-loop, and an explicit in-process manual-reset operation (`resetCrashBudget()` on `RustSidecarPtyHost`, re-probed through `PtyHostSelector`) is the sanctioned path out of fail-stop short of a daemon restart (a remote affordance through which the person makes the reset registers under Plan-005's `daemon.*` namespace when that plan lands — the mechanism itself ships here). Sessions live at crash time are concluded through the ADR-018 §Decision item 9 crash-time `onExit(sessionId, -1)` contract — a respawned child starts with an empty session table and sessions are NEVER silently rebound onto it (composes with I-021-6 point 4: pre-spawn buffers clear on supervisor teardown). **Verification:** Phase 3B Tests RP1–RP2 (`packages/runtime-daemon/src/pty/__tests__/rust-sidecar-pty-host.test.ts` — RP1: backoff schedule asserted between consecutive respawns and budget exhaustion surfaces `PtyBackendUnavailable` after the 5th in-window failure with crash-time onExit fired per live session; RP2: `resetCrashBudget()` clears fail-stop, a fresh spawn succeeds, and the budget window restarts).

### I-021-8 — No PTY or provider child outlives its supervising processes unreaped

The two-layer orphan-process defense per [ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-sidecar.md#decision) item 10 (layer 1, layer 2 and the registry identity) MUST hold: **Layer 1** — per-OS kernel parent-death containment (Linux: `PR_SET_PDEATHSIG` armed per direct child with the `getppid()` reparent-race re-check, spawns originating from the daemon-lifetime main thread only, and the never-leak guarantee bound to a daemon-lifecycle-bound cgroup-v2 scope killed via `cgroup.kill` by a pdeathsig-armed watchdog survivor where delegated cgroup v2 exists — best-effort process-group fallback degrading to bounded leak-until-restart elsewhere; Windows: Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, both breakaway flags cleared, the daemon holding the sole, non-inheritable, never-duplicated handle; macOS: kqueue `EVFILT_PROC` live watch — the registry sweep is the load-bearing daemon-crash reaper there), with the sidecar arming its own children through `child_guard.rs`. **Layer 2** — the daemon-side orphan registry persisted with the crash-safe atomic recipe (same-dir temp file → `fsync(file)` → `rename` → `fsync(parent dir)` — the parent-dir fsync is the step generic atomic-write helpers omit), writing a durable **spawn-intent entry carrying a unique nonce injected into the child's environment BEFORE the child is spawned** and completing it with the identity tuple after, so no child ever exists outside the registry's view. The startup sweep kills only under a full `(boot_id, pid, start_time)` match — a mismatched boot-id proves staleness and the sweep **discards rather than signals** (fail-closed for a kill path) — and Linux signaling prefers the pidfd path (`pidfd_open` validated against the persisted tuple before first use; `pidfd_send_signal`) on kernels ≥ 5.3, falling back to tuple-guarded `kill(2)`. **Verification:** Phase 3B Tests O1–O5 (`packages/runtime-daemon/src/pty/__tests__/orphan-registry.test.ts` — O1: atomic-write recipe order incl. parent-dir fsync; O2: intent-before-spawn ordering with crash-between-intent-and-spawn leaving a discardable stale intent; O3: boot-id mismatch discards every entry without signaling; `packages/runtime-daemon/src/pty/orphan-reaper/__tests__/sweep.test.ts` — O4: tuple match kills, tuple mismatch under a matching pid discards; O5: pidfd validation falls back to tuple-guarded signaling on start-time mismatch; plus `packages/sidecar-rust-pty/src/child_guard.rs::tests` — pdeathsig arm + `getppid()` re-check on Linux, Job-Object attach flags on Windows).

### I-021-9 — Terminal writes are lease-gated at the daemon boundary; the lease never touches the foreground process

Every write frame bound for one of a session's shells passes that shell's [Spec-002 §Required Behavior](../specs/002-runtime-node-attach.md#required-behavior) write-lease check at the daemon terminal-write boundary, where the authenticated writer is known: no holder ⇒ refused `pty.control_not_held` (fail-closed — writes never succeed implicitly), and a lease on one shell never authorizes a write to another; a provider process's own shell and its tool spawns are not terminal surfaces and sit outside the lease. The PTY-sidecar wire stays untouched — `WriteRequest` carries no holder field because bytes that reach the sidecar are already lease-authorized — and no lease transition ever signals, terminates, or otherwise touches the running foreground program (a take lands between frames; stopping a program is a run intervention or terminal action, never a lease side-effect). **Verification:** Phase 3B Tests L1–L7 (`packages/runtime-daemon/src/pty/__tests__/control-lease.test.ts`, mapping Spec-002's lease acceptance criteria — L1: an uncontested take of a named shell holds at once and broadcasts `pty.control_changed` naming that shell, every other shell keeping its own holder; L2: a write to an unheld shell is refused `pty.control_not_held`, and a lease on one shell never authorizes a write to another; L3: a plain take of a held shell is refused `pty.control_held_by_other` carrying `holderDeviceId`, and succeeds after the holder's connection ends or a forced take moves the lease — no verb releases a shell; L4: a forced take moves the lease off another device with `reason: 'taken_by_force'`, leaves the foreground program and every other shell untouched, and is refused `pty.control_held_by_other` while the hold belongs to a run that is writing; L5: a connection's end releases exactly the leases that connection took (`auto_released_disconnect`), a run's hold is released on that run's first transition out of `running` (`auto_released_run_idle`), and a different run's take re-binds the record with no broadcast; L6: a resize from a connection that does not hold the shell is refused `pty.control_held_by_other`; L7: a close is refused while a run holds the shell and, while another device holds it, succeeds only with `force: true`).

### I-021-10 — The terminal-owning daemon is the only lease authority

The daemon that owns a shell is the only authority for its lease, and a take is registered on the daemon's own transport and on nothing else. Each shell's lease record lives with the shell it guards: the holding device and, for a hold taken by an agent run's write path, the acquiring run, which `pty.control_changed` and the shell's holder reading name as `holderRunId` while the run holds the shell and omit while a device does; `holderDeviceId` stays the machine's own device identity, because every local writer on the machine resolves to it, and the agent's name comes from the run. The record is on no wire but `pty.control_changed` and in no control-plane table, and every change to it broadcasts `pty.control_changed` naming the shell, the new holder and the reason (`'taken' | 'taken_by_force' | 'auto_released_disconnect' | 'auto_released_run_idle'`, per [Spec-005 §PTY Control](../specs/005-session-event-taxonomy-and-audit-log.md#pty-control-session_lifecycle)), so the record never changes silently. A lease belongs to the connection that took it and carries no time bound and no fence issued by any other party, so it never outlives that connection or the shell. **Verification:** Phase 3B Tests L1–L5 (each transition's broadcast and the connection-bound release).

### I-021-11 — A numeric `signal_code` asserts a real OS observation

`ExitCodeNotification.signal_code` (wire) and `PtyHost.onExit`'s `signalCode` (runtime) carry a number ONLY when the OS reported that signal for that child's exit: the sidecar sources the real value from the underlying Unix exit status (`ExitStatusExt::signal()`), bridging `portable_pty`'s `ExitStatus::signal()` strsignal-string caveat (per the ADR-018 §Research Conducted `portable-pty ExitStatus` row: `signal: Option<String>`, and `with_signal()` hard-codes `code: 1`) through a libc signal-name → number table when only the string form is observable; absence (`null` on the wire, omitted at the contract surface) is the ONLY no-observation encoding; Windows exits carry no POSIX signal and stay `null`. The synthetic sentinels stay reserved and distinct per ADR-018 §Decision item 9 (`-1` sidecar-crash with `signalCode` omitted; `NodePtyHost.invokeTaskkill`'s `exitCode = 1` with `signalCode` omitted) — a real signal observation can never be confused with either. **Verification:** Phase 3B Tests SG1–SG2 (`packages/sidecar-rust-pty/tests/pty_session.rs` — SG1: a SIGKILL-terminated child emits `signal_code: 9` and a clean exit emits `signal_code: null`; `packages/runtime-daemon/src/pty/__tests__/node-pty-host.test.ts` parity arm — SG2: `NodePtyHost` forwards node-pty's real Unix signal number and never fabricates one on Windows, sentinels unchanged).

### I-021-12 — Daemon ↔ sidecar session-table divergence is reconciled fail-closed, never adopted

When the supervisor detects state divergence without a sidecar crash (framing desync, transport stall recovered by ping, a reconcile probe), **tier-2 hardened resync** reconciles via the additive `resync_request` / `resync_response` wire pair, the tier-2 message of [ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-sidecar.md#decision) item 10: sessions the daemon knows but the sidecar no longer lists are concluded per the §Decision item 9 no-observation posture (`onExit(sessionId, -1)`, `signalCode` omitted); sessions the sidecar lists but the daemon does not know are **terminated and swept — never adopted** (adoption would fabricate daemon session state with no record); matched sessions continue untouched (the hardening win over tier-1: no live-PTY interruption). Resync composes beneath the existing guards — it never bypasses the post-`close()` suppression or pre-spawn buffer rules (I-021-6) — and a failed reconcile escalates to tier-1 respawn under I-021-7's budget. **Verification:** Phase 3B Tests RS1–RS4 (`packages/sidecar-rust-pty/tests/protocol_roundtrip.rs` — RS1: resync pair serde round-trip with the session-enumeration payload; `packages/runtime-daemon/src/pty/__tests__/rust-sidecar-pty-host.test.ts` — RS2: daemon-only session concluded with `-1` + no signal; RS3: sidecar-only session receives `KillRequest` and is registry-swept, never surfaced to consumers; RS4: matched sessions' data pumps continue uninterrupted across a resync, and a reconcile failure escalates to a budget-accounted respawn).

## API And Transport Changes

- **New `PtyHost` contract** (TypeScript, `packages/runtime-daemon/src/pty/pty-host.ts`): methods `spawn(spec)`, `resize(sessionId, rows, cols)`, `write(sessionId, bytes)`, `kill(sessionId, signal)`, `close(sessionId)`, `shutdown({ perSessionTimeoutMs, hostTimeoutMs })` (polymorphic lifecycle drain per Plan-001 §CP-001-1 — returns `DrainResult`), and `pause(sessionId)` / `resume(sessionId)` (Phase 3B, T-021-3B-7 — the terminal's flow control reaching the process behind it); event streams `onData(sessionId, chunk)`, `onExit(sessionId, exitCode)`. Implementations: `RustSidecarPtyHost`, `NodePtyHost`.
- **New stdio wire protocol** (daemon ↔ sidecar): LSP-style `Content-Length: N\r\n\r\n<body>` framing (identical to ADR-009). JSON envelope carries a `kind` discriminant and either a control message or a binary-frame descriptor. Binary stdout/stderr chunks ride their own `DataFrame { session_id, stream: "stdout"|"stderr", bytes: base64 }` message so the JSON framer stays a single path (trade-off accepted: base64 overhead vs second framer — single framer wins for V1 simplicity; revisit if throughput becomes a constraint per ADR-018 Assumption 4).
- **Terminal-control and shell method surface (Phase 3B):** `session.takeControl {sessionId, terminalId, force?}` (daemon JSON-RPC ONLY; no release verb — a lease ends when another device takes it, when a forced take moves it, or when the connection that took it ends), `session.setTerminalFlowControl {sessionId, terminalId, paused}` (T-021-3B-7), and the shell verbs `pty.list`, `pty.open`, `pty.close {sessionId, terminalId, force?}`, `pty.reorder`, `pty.outputSubscribe`, `pty.write` and `pty.resize` (T-021-3B-8). The [api-payload §Session Terminal-Control Method Registry](../architecture/contracts/api-payload-contracts.md#session-terminal-control-method-registry) defines the take and the flow-control signal; Plan-021 mints their schemas in a new single-domain contracts file `packages/contracts/src/terminal-control.ts` (T-021-3B-3). Refusals are the typed [Error Contracts §PTY](../architecture/contracts/error-contracts.md#pty) codes; every lease transition broadcasts `pty.control_changed` per [Spec-005 §PTY Control](../specs/005-session-event-taxonomy-and-audit-log.md#pty-control-session_lifecycle).
- **Sidecar wire addition (Phase 3B):** the tier-2 resync pair `resync_request` / `resync_response` — the additive tier-2 message of [ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-sidecar.md#decision) item 10, keeping the message set's symmetric-response convention. `WriteRequest` stays untouched (no user field — lease enforcement sits at the daemon boundary per I-021-9). The same phase adds the flow-control pair `flow_control_request` / `flow_control_response` (T-021-3B-7) on the same additive footing and with the same symmetric-response convention, and `PtyHost` gains `pause(sessionId)` / `resume(sessionId)` so the daemon drives both backends through one call.
- **`signal_code` fidelity (Phase 3B):** `ExitCodeNotification.signal_code` carries real OS signal observations per I-021-11; the wire shape (`number | null`) is unchanged — only the population semantics harden.

## Implementation Steps

1. **Scaffold Rust crate.** Create `packages/sidecar-rust-pty/` with `Cargo.toml` declaring `portable-pty = "0.9"`, `serde`, `serde_json`, `tokio` (current LTS), `clap`. Set `rust-version = "1.85"` and commit `Cargo.lock`.
2. **Implement Content-Length framing.** Port the ADR-009 framing semantics into Rust (`src/framing.rs`): read `Content-Length: N\r\n\r\n`, read exactly N bytes, hand off to dispatcher; write is the inverse. Unit-test the round-trip on a byte-level fixture.
3. **Define protocol types.** In `src/protocol.rs`, declare serde structs for `SpawnRequest` (command, args, env, cwd, rows, cols), `SpawnResponse` (session_id), `ResizeRequest`, `WriteRequest`, `KillRequest`, `ExitCodeNotification`, `PingRequest` / `PingResponse`, `DataFrame`. Mirror these types in `packages/runtime-daemon/src/pty/pty-host-protocol.ts` so TS and Rust agree by hand-authored parity (no code-gen — trade-off accepted: two-sided hand edit vs adding a schema compiler).
4. **Implement per-session PTY holder.** In `src/pty_session.rs`, wrap `portable_pty::PtyPair` keyed by an internally-minted `session_id: String`. Spawn stdout/stderr reader tasks that chunk (e.g., 8 KiB) and emit `DataFrame` messages with a monotonically-increasing sequence number.
5. **Wire exit-code capture.** Await the child-process waitable for each session; on exit, emit `ExitCodeNotification { session_id, exit_code, signal_code? }` and drop the `PtyPair`.
6. **Define `PtyHost` interface.** Author `packages/runtime-daemon/src/pty/pty-host.ts` from the method list in §API And Transport Changes; export type-only. Plan-001's spawn wrapper and drain import it.
7. **Implement `RustSidecarPtyHost`.** In `packages/runtime-daemon/src/pty/rust-sidecar-pty-host.ts`, resolve the platform package (`require.resolve('@ai-sidekicks/pty-sidecar-${platform}-${arch}/bin/sidecar')`, in `packages/runtime-daemon/src/pty/sidecar-binary-path.ts`), spawn it as a child process with `stdio: ['pipe', 'pipe', 'inherit']`, wire Content-Length framing (`packages/runtime-daemon/src/pty/sidecar-frame-codec.ts`) on stdin/stdout, and expose the `PtyHost` contract. Supervise with crash-respawn (exponential backoff, cap 5 failures per 60 s, then surface `PtyBackendUnavailable`).
8. **Implement `NodePtyHost` fallback.** In `packages/runtime-daemon/src/pty/node-pty-host.ts`, in-process `node-pty` wrapper against the same `PtyHost` contract. Used as **macOS/Linux primary** and as **Windows fallback** when the sidecar binary is not resolvable. **Windows kill-translation guidance** (critical — Phase 2 satisfaction of I-021-1 + I-021-2 inside the `node-pty` code path is load-bearing): on `process.platform === 'win32'`, the `kill(sessionId, signal)` path MUST translate POSIX semantics:
   - `SIGINT` → invoke `windows.GenerateConsoleCtrlEvent(CTRL_C_EVENT, child.pid)` (FFI via `koffi` or `ffi-napi`; `node-pty` itself does not expose this primitive — `node-pty.kill()` only signals a single PID per [microsoft/node-pty#167](https://github.com/microsoft/node-pty/issues/167)).
   - `SIGTERM` (graceful hard-stop) → `CTRL_BREAK_EVENT` first; if child does not exit within 2 s, escalate to `child_process.spawn('taskkill', ['/T', '/F', '/PID', String(child.pid)])` per I-021-2.
   - `SIGKILL` (immediate hard-stop) → `taskkill /T /F /PID <pid>` directly, skipping `CTRL_BREAK_EVENT`.
   - On non-Windows platforms the path is a pass-through to `node-pty.kill(signal)`.
   - Idempotency: if the child has already exited when the kill is invoked, treat as success and emit `onExit` from the cached exit-code; do not throw.
9. **Wire `PtyHostSelector`.** In `packages/runtime-daemon/src/pty/pty-host-selector.ts`:
   - **Phase 2 default (all platforms): `NodePtyHost`**. The `RustSidecarPtyHost` branch is unimplemented at Phase 2 and throws "not yet wired" if forced via env-var.
   - **Phase 5 default-flip on `win32`: `RustSidecarPtyHost`**, falling back to `NodePtyHost` if the sidecar binary is not resolvable (log a loud warning; this is ADR-018 Failure Mode "Sidecar binary missing on user machine"). **macOS/Linux remain on `NodePtyHost` primary at Phase 5 and beyond.**
   - **Env-var override `AIS_PTY_BACKEND`** (case-sensitive lowercase): values `'rust-sidecar'` selects sidecar on all platforms (requires the optional sidecar package to be installed on macOS/Linux; throws `PtyBackendUnavailable` with a clear message otherwise); `'node-pty'` selects NodePtyHost on all platforms; any other value (including empty string) falls back to platform default + ``console.warn(`AIS_PTY_BACKEND='${value}' unrecognized; falling back to platform default`)``.
10. **CI cross-compile workflow.** Author `.github/workflows/sidecar-build.yml` with a 6-target matrix, plus the service's Windows half:
    - **Workflow shell (inheriting ADR-022 §Axis 1 + Axis 5 conventions):**
      - `on: { push: { branches: [develop, main] }, pull_request: { paths: [packages/sidecar-rust-pty/**, .github/workflows/sidecar-build.yml] }, workflow_dispatch: {} }`

## Windows Implementation Gotchas

Five Windows-specific implementation concerns are load-bearing for the sidecar's correctness and lifecycle behavior on Windows. These do **not** change the architecture (the `PtyHost` contract still abstracts the backend choice) but they DO change the daemon-layer responsibilities the sidecar must satisfy. Each item below names the daemon-layer obligation, the implementation guidance, and the primary-source citation in `## References`.

### 1. Ctrl+C signal propagation on Windows

Windows does not have POSIX-style SIGINT delivered to a process group. The console subsystem uses `CTRL_C_EVENT` and `CTRL_BREAK_EVENT` events delivered through `GenerateConsoleCtrlEvent`, with semantics that are not equivalent to Unix `SIGINT`:

- `CTRL_C_EVENT` (`0`) is the closest analog to `SIGINT` but can be ignored or handled distinctly by the child process via `SetConsoleCtrlHandler`.
- `CTRL_BREAK_EVENT` (`1`) is generally non-ignorable and is the more reliable interrupt for misbehaving children.
- `GenerateConsoleCtrlEvent` requires the child process to be attached to the **same console** as the caller; if the child was spawned with `CREATE_NEW_CONSOLE` or detached, the event will not reach it. The sidecar must spawn children attached to the ConPTY's pseudo-console so that `GenerateConsoleCtrlEvent` propagates.
- A process-group ID of `0` broadcasts the event to all processes attached to the console. Where a single child process is the target, pass that child's PID and verify the child is in the ConPTY's process group at spawn time.

Daemon-layer obligation: `PtyHost.kill(sessionId, signal)` on Windows must translate signal semantics — `SIGINT` → `CTRL_C_EVENT`, hard-stop → `CTRL_BREAK_EVENT` followed by `taskkill /T` if the child does not exit within a bounded interval. `node-pty`'s `pty.kill()` only signals a single process and does not handle the console-group attachment correctly per [microsoft/node-pty#167](https://github.com/microsoft/node-pty/issues/167) (see `## References`); the Rust sidecar must implement this translation in `pty_session.rs::kill()` rather than relying on `portable-pty`'s default kill behavior.

### 2. `taskkill /T` tree-kill behavior

Killing a single PID on Windows does not kill its descendants. Children spawned by the immediate child process (shells, build tools, language servers, language-runtime workers) survive a single-PID kill and become orphans tied to the console session. This affects the daemon's session-teardown semantics: a "session ended" notification cannot assume the entire process tree has terminated.

- Use `taskkill /T /F /PID <root-pid>` (the `/T` flag instructs `taskkill` to kill the entire tree) for hard termination paths.
- For graceful shutdown, send `CTRL_BREAK_EVENT` first (per Gotcha 1), wait a bounded interval, then escalate to `taskkill /T /F`.
- Reaping must be idempotent and must not block the sidecar's main loop — invoke `taskkill` with a timeout and emit an `ExitCodeNotification` even if reaping is incomplete, so the daemon can mark the session terminated without hanging on a stuck OS-level operation.
- This is a daemon-layer responsibility (the sidecar emits exit-code on root-PID exit; the daemon coordinates tree-kill on session end). Behavior matches the unreliability documented in [microsoft/node-pty#437](https://github.com/microsoft/node-pty/issues/437) — see `## References`.

### 3. WSL2 path translation scope

WSL 2 is first-class. On a Windows computer whose Claude Code and Codex live in WSL 2, the service runs inside that distribution — the daemon plus the service's Windows half — so it sits on the providers' side of the boundary. The sidecar's responsibility boundary follows from that:

- **Where the sidecar runs (operative):** the sidecar serves a service that runs natively on Windows. A service inside a WSL 2 distribution runs its shells through the Linux daemon's `node-pty`, in the person's login shell with a Linux working folder, so the sidecar never runs there; it stays native-Windows only.
- **Implementation guidance (operative):** The sidecar does **not** translate paths between Windows-native (`C:\Users\...`) and WSL 2 (`/mnt/c/Users/...` or `\\wsl.localhost\<distro>\home\...`) namespaces. Path arguments handed to `SpawnRequest.cwd` and `SpawnRequest.env` are passed through to `portable-pty` verbatim. Path translation is the daemon's, inside the distribution, before any spawn: `\\wsl.localhost\<this distro>\p` or `\\wsl$\<this distro>\p` becomes `/p`, `C:\p` becomes its `wslpath -u` form (`/mnt/c/p` by default), a Linux path going back to Windows takes its `wslpath -w` form, and a path in another distribution's share is refused.
- `wslpath` availability: the `wslpath` command exists inside a WSL 2 distro and converts between Windows and POSIX path forms (e.g., `wslpath -w /home/foo` → `\\wsl.localhost\Ubuntu\home\foo`). It is NOT available in a Windows-native context. The sidecar runs Windows-native and therefore does not invoke `wslpath`.

### 4. The app's quit and the sidecar's shutdown

Electron's `will-quit` event is the app's last chance for synchronous cleanup before its process terminates. The sidecar is not the app's: it is a child of the daemon, which runs as the person's background service, so the app's quit never reaches it — the quit calls `daemon.flush`, and the service, every run and every shell keep running.

- No handler in the app's main process drains, kills or signals the sidecar or a shell — not on quit, not on a window closing, not on the last window closing.
- When the service itself stops (Runtime's `Stop` or `Restart`, or the operating system's service manager), the daemon drains before it exits: (a) emit `KillRequest` for every active session to the sidecar, (b) wait for `ExitCodeNotification` for each (with a bounded timeout, e.g., 2 s), (c) close the sidecar's stdin (which signals the sidecar to exit cleanly), (d) wait for the sidecar process exit (with a second bounded timeout), and (e) escalate to `taskkill /T /F /PID <sidecar-pid>` if the sidecar does not exit within the timeout — same hard-stop pattern as Gotcha 2.
- The race between a process exiting and its PTY children draining is the SIGABRT-on-exit class documented in [microsoft/node-pty#904](https://github.com/microsoft/node-pty/issues/904) (see `## References`), which the sidecar architecture is designed to avoid; keeping the PTYs in the service, out of the app's process, and draining them at the service's own stop is what makes that hold.
- **Cross-reference:** Plan-001 (session core) owns the drain orchestration, with Plan-021 (this plan) supplying the polymorphic `PtyHost.shutdown(options)` drain protocol and sidecar `KillRequest` primitives.

### 5. Spawn locks cwd on Windows

Windows holds a directory lock on the cwd passed at PTY spawn for the lifetime of the spawned process. As long as the child process is running, that working-directory cannot be deleted, moved, or unmounted — any attempt fails with `ERROR_SHARING_VIOLATION`. This breaks worktree-swap workflows (`git worktree remove`, `gitflow` cleanup) when the sidecar spawned a session with `cwd` set to the worktree path: the worktree cannot be removed until every session rooted under it has exited, even if the user has switched contexts and considers the worktree abandoned.

- **Implementation guidance** (per [microsoft/node-pty#647](https://github.com/microsoft/node-pty/issues/647)): the sidecar must **not** invoke `portable_pty::PtySize::spawn_command` with `SpawnRequest.cwd` set directly to the worktree path. Two equivalent mitigations:
  - **(a) Stable parent dir + `cd &&` shell prefix:** spawn the child from a stable, unmovable parent directory (e.g., the daemon's own working dir or the user-home root), then prepend a `cd <worktree-path> && ` clause to the command string. The shell's `cd` does not lock the parent dir at the OS level; only the spawn-call cwd is locked.
  - **(b) Stable parent dir + `env.CWD` propagation:** same stable-parent spawn, but pass the worktree path via an environment variable (`CWD=<worktree-path>`) that the agent CLI consumes internally. Choice between (a) and (b) depends on whether the spawned program respects `cd` semantics or expects an env-var (most agentic CLIs accept `cd`; some workflow runners use `CWD`).
- **Daemon-layer obligation:** the daemon-layer `PtyHost.spawn(spec)` wrapper translates `spec.cwd` (logical worktree path) into the (stable parent dir, prefixed command) tuple before forwarding to `RustSidecarPtyHost`. The sidecar's protocol-level `SpawnRequest.cwd` field always carries a stable path; the worktree path lives in the command-string-or-env layer above. This translation step is a **daemon-layer** responsibility (Plan-001) rather than a sidecar-layer one, because the sidecar deliberately does not know about worktree semantics.
- **NodePtyHost fallback** has the same constraint — `node-pty.spawn({ cwd })` exhibits the identical Windows behavior. The daemon-layer translation MUST run regardless of which `PtyHost` implementation is selected; the constraint is OS-level, not backend-specific.
- **Cross-reference:** [ADR-018 §Research Conducted](../decisions/018-windows-v1-tier-and-pty-sidecar.md#research-conducted) row [`microsoft/node-pty#647`](https://github.com/microsoft/node-pty/issues/647) ("blocks worktree workflows") classifies the failure mode; this section provides the implementation-grade mitigation. Plan-001 (session core) owns the daemon-layer translation step in its session-spawn entry point; Plan-021 (this plan) supplies only the sidecar-layer protocol primitive (`SpawnRequest.cwd` carries whatever the daemon hands down).

## Windows Signing — SignPath Foundation

Windows signing goes through [SignPath Foundation](https://signpath.org)'s free open-source program ([ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-sidecar.md#decision) item 7). Its terms ([signpath.org/terms](https://signpath.org/terms)) admit a project with an OSI license "without commercial dual-licensing for all components", no proprietary components, active maintenance, an existing release and a published code-signing policy, which the release workflow publishes. "The code signing certificate is issued to SignPath Foundation", so Windows names SignPath Foundation as the publisher of every binary the step signs.

- **One step, three binaries.** The release workflow's SignPath step signs the Electron app, the sidecar binaries for `win32-x64` and `win32-arm64`, and the service's Windows half (`sidekicks-windows-half.exe`, x64 and arm64), so SmartScreen reputation accrues to one publisher across all of them ([ADR-018 §Decision](../decisions/018-windows-v1-tier-and-pty-sidecar.md#decision) item 8).
- **Why this path.** It removes SmartScreen's hard block on an unsigned file and keeps the NSIS installer's one-press update, at no cost. The certificate class is not the lever: Microsoft's [SmartScreen reputation documentation](https://learn.microsoft.com/en-us/windows/security/threat-protection/microsoft-defender-smartscreen/smartscreen-reputation) says of the EV bypass that "this behavior no longer exists", so reputation accrues by publisher and file hash for every class.
- **If the project is not eligible**, the choice goes back to the person with the remaining paths (the Microsoft Store, a bought certificate, or unsigned with SmartScreen's block at install); the distribution plan does not change silently.
- **Until the acceptance lands** ([BL-108](../backlog.md#bl-108-plan-021-windows--macos-signing-procurement-evidence)), Windows builds publish unsigned and the signing step is skipped.

The shape is the library's own answer: xterm.js calls that watermark a safety net in its `WriteBuffer` source and names flow control propagated to the PTY as the fix (read 2026-09-21). **Spec coverage:** [Spec-021 §Console Libraries](../specs/021-desktop-app-and-renderer.md#console-libraries) (the terminal row's flow-control rule); Spec-002 §Required Behavior (a shell's output keeps pace with its slowest live reader). **Verifies invariant:** none — no invariant is minted here; Tests FC1–FC3. Both additions are additive in the same way T-021-3B-5's resync pair is: the sidecar message set gains messages and the Phase 2 `PtyHost` contract gains methods, with no Phase 1–3 message or signature rewritten, so the phase header's no-rewrite rule holds.
- **T-021-3B-8** A session's shells. **Status:** not built. **Files:** `packages/contracts/src/pty.ts` (`TerminalId`, defined once and imported by the lease and flow-control shapes, and the params and results of every `pty.*` verb below; `pty.outputSubscribe`'s frames are the shared stream frame of `packages/contracts/src/jsonrpc-streaming.ts`, whose drop mark is a member of that frame and of no one reply), `packages/runtime-daemon/src/pty/` (the session → shell → PTY-handle map), the `pty.*` handlers in `packages/runtime-daemon/src/ipc/handlers/`, `packages/runtime-daemon/src/pty/__tests__/terminal-sessions.test.ts`. **Wires:** list and follow the session's shells with `pty.list`, a live list, so a shell opened on another device arrives as a new tab; open a shell with `pty.open`, in the person's login shell with its working directory the session's own tree, the machine's own limit refused in words; close one with `pty.close {sessionId, terminalId, force?}`, sent once per shell, refused `pty.control_held_by_other` while a run holds the shell and, while another device holds it, refused unless it carries `force: true`, which a client sends only after the person confirms in place; reorder shells with `pty.reorder`, the order held by the daemon; a shell's live output with `pty.outputSubscribe`, replayed at its last size and then the tail, from a one-mebibyte replay window per shell; type into a shell with `pty.write`, gated by that shell's lease; resize with `pty.resize`, which only the connection holding the shell may send, other devices drawing it at its own size and the last size staying while no one holds it. **Spec coverage:** Spec-002 §Required Behavior (a session's shells; the resize and close holds). **Verifies invariant:** I-021-9 (Tests L6–L7); Tests SH1–SH3.

## Rollout Order

1. Ship the Rust crate + `PtyHost` interface + `NodePtyHost` impl behind a `PtyHostSelector` whose default on all platforms is `NodePtyHost` (no behavioral change).
2. Ship `RustSidecarPtyHost` implementation guarded by `AIS_PTY_BACKEND=rust-sidecar` env-var (opt-in only).
3. Obtain signing: SignPath Foundation's acceptance for Windows and the Apple Developer ID Application certificate for macOS; until then Windows builds publish unsigned and macOS builds carry the self-signed identity.
4. Publish signed sidecar binaries to npm at pre-release versions (e.g., `0.0.1-rc.N`).
5. Flip `PtyHostSelector` default on Windows to `RustSidecarPtyHost` with `NodePtyHost` as fallback; leave macOS/Linux on `NodePtyHost` primary.
6. Monitor the Windows shell pass-rate and SmartScreen reputation accrual (target: established-publisher status per ADR-018 Success Criteria).

## Rollback Or Fallback

- `PtyHostSelector` default on Windows can flip back to `NodePtyHost` via env-var override without a release.
- Sidecar binary missing at runtime → `RustSidecarPtyHost` throws at construction → selector auto-fallbacks to `NodePtyHost` with a loud warning banner in daemon logs (per ADR-018 Failure Mode "Sidecar binary missing on user machine").
- A sidecar-originated bug on Windows → env-var override forces `NodePtyHost`; the next release flips the default back; ADR-018 Tripwire 1 evaluates sidecar sunset.

## Risks And Blockers

- **Apple Developer ID cert procurement.** Until the certificate exists, macOS builds, the sidecar's included, carry the project's self-signed identity, and the first launch asks the person to open the app from Finder's menu; nothing else waits on it. Plan-021 reuses the desktop app's certificate once it exists, at no additional procurement cost.
- **SignPath Foundation finds the project ineligible.** The choice goes back to the person with the remaining paths (the Microsoft Store, a bought certificate, or unsigned with SmartScreen's block at install); the distribution plan does not change silently.
- **[cargo-zigbuild#316](https://github.com/rust-cross/cargo-zigbuild/issues/316)** — aarch64-apple-darwin iconv linker regression under Rust ≥ 1.82 with `zstd-sys` transitive deps. Mitigated by using GitHub Actions' native `macos-14` / `macos-15` Apple Silicon runners, avoiding the cross-compile path for that target entirely.
- **`portable-pty` 0.8.x → 0.9.0 breaking migration** — the crate swapped its serial-port dep from `serial` to `serial2` in the 0.9.0 bump (repo move to `wezterm/wezterm` org on 2025-02-07). Mitigation: start at 0.9.0, never back-port to 0.8.x.
- **`portable-pty` maintainer continuity** — no formal maintainer-handoff statement after the wezterm org repo move; the plan starts at 0.9.0, released 2025-02-11. Bounded by the fallback path: `PtyHost` selector can pick `NodePtyHost` on any platform if `portable-pty` becomes unmaintained (ADR-018 Assumption 1's "What Breaks If Wrong" path).
- **Apple notarization queue 24–120+ hour delays** ([Spec-021 §macOS](../specs/021-desktop-app-and-renderer.md#macos), [Apple Developer Forums 813441](https://developer.apple.com/forums/thread/813441)). Mitigated by async submit + poll release-pipeline pattern (step 12.4 above).
- **Linux: no OS-level signature check at sidecar spawn.** No Gatekeeper / SmartScreen equivalent exists for npm-distributed ELF binaries, and the daemon adds no check of its own; a corrupt binary shows as a terminal that fails to start.
