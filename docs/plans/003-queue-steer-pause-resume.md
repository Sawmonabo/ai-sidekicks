## Goal

Implement daemon-backed queue state and authoritative intervention handling for active runs.

## Scope

This plan covers queue persistence, intervention records, run-state transitions, and client control surfaces for queue, steer, pause, resume, and interrupt.

## Non-Goals

- Workflow scheduling
- Provider-specific pause emulation beyond declared capabilities
- Notification routing

## Design Decisions

This plan's design decisions. Each is registered in the corpus it touches: Spec-003 / Spec-005 for version derivation and emission, `api-payload-contracts.md §Method-Name Registry` for the wire method names, and `error-contracts.md` for the refusal codes.

- **D-003-1 `version` = any-run-progression counter.** The `expectedRunVersion` stale-replay guard (I-003-7 / T2.8) compares against a run `version` derived as an **any-run-progression counter** (reading (b)): it increments on every run progression — applied interventions included — not only on `run.*` state-machine transitions (reading (a)). **Rationale (the hardened call):** reading (a) fails to catch two steers racing on a still-`running` run (zero new `run.*` events → the second stale steer passes undetected); reading (b) closes that replay window. Plan-003 authors T1.7's accessor _shape_ and T2.8's guard _behavior_; the `version` _derivation_ follows this semantics. Spec-003 / Spec-005 define the `version` field on the `run.*` payload and its increment/emission point.
- **D-003-2 `expectedRunVersion` is mandatory (fail-closed).** The comparand is **required** on every intervention request ([Spec-003 §Interfaces And Contracts](../specs/003-queue-steer-pause-resume.md#interfaces-and-contracts) mandatory reading); the absent-comparand case is **rejected**, not applied. An optional comparand would let a caller bypass the stale-replay guard by omitting the field — the hardened reading fails closed. T2.8 authors the present-comparand guard; the absent case rejects. Entails a Spec-003 clarification (executed at swap).
- **Scope extension — the mandatory comparand binds `run.pause` / `run.resume`, not only interventions.** The `RunPauseRequest` / `RunResumeRequest` contracts (`docs/architecture/contracts/api-payload-contracts.md §Plan-003 — Queue Steer Pause Resume`) carry the **same mandatory** `expectedRunVersion` guard, with `RunControlAck` echoing the advanced `runVersion` so the caller threads the fresh comparand forward. This **extends D-003-2 beyond its original intervention-only scope**: a stale `pause` replayed against a run that has since progressed is the identical replay hazard the guard exists to close, so the comparand fails closed the same way (T3.4 / T3.5 apply the T2.8 guard before composing). `pause` / `resume` remain **orchestration-layer run-control verbs, not interventions** — they hold no `InterventionType` (`steer | interrupt | cancel | rollback`) membership and are not serialized through the intervention queue (ADR-011) — so this is a deliberate cross-cutting extension of the mandatory-comparand obligation, recorded here and reflected in the `api-payload-contracts.md` run-control comment at swap.
- **D-003-3 the eight `run.*` method strings.** `run.queueList` / `run.queueCreate` / `run.queueCancel` / `run.intervene` / `run.pause` / `run.resume` / `run.subscribeState` / `run.subscribeQueue` (CP-003-4) are the wire contract, registered in `api-payload-contracts.md §Method-Name Registry` at swap. Reciprocal `provides` is recorded on [Plan-006](./006-local-ipc-and-daemon-control.md), the `run.*` namespace owner.

- **D-003-4 — the intervention admission path carries an explicit `origin` discriminator, and the principal is required by database constraint on the user arm**. The `interventions` row records `origin TEXT NOT NULL CHECK(origin IN ('user', 'system'))` beside the nullable `admitting_principal_id`, with a table-level CHECK binding them: the principal is present exactly when `origin = 'user'`. **Rationale (the hardened call):** the alternative readings both fail. Inferring the origin from `initiator_id IS NULL` conflates a genuinely system-originated intervention with a user intervention whose initiator was simply not supplied, and it makes the security-relevant distinction a side effect of an unrelated column's nullability — a property no constraint can defend and any later change to `initiator_id`'s optionality would silently invert. Making the principal unconditionally `NOT NULL` is likewise wrong: Plan-014's budget / idle / moderation interrupts enter in-process below the wire authorization boundary with a NULL-for-system actor (CP-003-10), so there is no user to name, and forcing a synthetic one would put a fabricated identity into the audit record. The explicit discriminator keeps both arms honest and — because `origin` carries **no DEFAULT** — fails an unstamped insert closed at the database rather than defaulting into the arm that requires no principal. The daemon-resolved principal itself follows the shipped `approval_resolutions.approver_id` model (D-010-12) rather than minting a second convention, and a wire-supplied principal that contradicts the daemon's resolution refuses with the existing `auth.principal_mismatch` — deliberately reusing that error rather than adding a near-duplicate, since it already names this exact class of caller-asserts-vs-transport-proves conflict. Entails the T1.4 CREATE columns, T2.4's acceptance-time stamp, and the paired Plan-010 consumption (CP-003-14 ⇄ CP-010-12, registered there as D-010-20).

## Risks And Blockers

- Provider capability mismatch can produce misleading controls
- Queue concurrency across multiple clients needs strict daemon serialization
- **Fork-across-compaction semantics are unverified on both provider legs.** What a provider rewind reconstructs across its own context-compaction boundary — pre-compaction context, or the compacted summary alone — is the open question the [Spec-003 §Driver-Level Rollback Mechanics](../specs/003-queue-steer-pause-resume.md#driver-level-rollback-mechanics) ADR-017 re-verification obligation records, and it is unanswerable from the checked-in probe records alone. I-003-20 makes this **fail closed rather than blocking**: every V1 driver refuses boundary-crossing targets, so T3.16 ships without waiting on the re-verification, and the refusal lifts per-driver only when that verification lands against a then-installed binary. The risk is therefore scope, not correctness — some rewind targets a user might want are refused until the question is answered.
- **The `resend-unapplied` arm depends on queue admission being able to fail after a confirmed rewind.** If T2.9's admission path is in practice infallible once the run is `paused`, the committed-then-failed arm becomes unreachable and its test would assert nothing; T3.17's test plan therefore drives the arm through an injected admission failure rather than hoping to observe one, and the arm stays specified because the caller's text must be recoverable even from an arm that is rare.
- **The composite's desktop affordance is placed and assigned.** Where an edit-message control belongs spans the Spec-011 timeline surface (whose rows the composite supersedes) and the renderer shell's composer area, neither of which this plan owns; T4.7's `--replace-message` keeps the composite reachable from the CLI. The placement: a hover-revealed pencil in the user `user.message` row's footer opening an inline editor — authored by **T4.8** in this plan's `run-controls/` subtree, mounted by Plan-011 at the row-footer composition point (**CP-003-15**), and sequenced behind the replacement-send wire-arm registration, which is in place. What remains is ordinary sequencing, not an open design question: the affordance ships dormant in Phase 4 and activates from Phase 3B, so the desktop surface stays unreachable-by-omission (never fail-open) until the handler, the composite, and the wire arm are all in place.
