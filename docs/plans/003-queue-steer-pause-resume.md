## Goal

Implement daemon-backed queue state and authoritative intervention handling for active runs.

## Scope

This plan covers queue persistence, intervention records, run-state transitions, and client control surfaces for queue, steer, pause, resume, and interrupt — the waiting messages' edit, reorder and delivery timeout, a child's own controls, the answer to a restart's mismatch, and the run side of an undo among them.

## Non-Goals

- Workflow scheduling
- Notification routing

## Preconditions

- **Plan-005 epoch-attribution carrier (CP-003-12):** the durable typed epoch-attribution field on the event-append surface — [Spec-003 §Required Behavior](../specs/003-queue-steer-pause-resume.md#required-behavior) mandates the stamp; T3.11 writes it, T3.14's supersede projection consumes it. It is [Plan-005](./005-session-event-taxonomy-and-audit-log.md) T1.9's cross-cutting `sourceEpoch` + `sourcePosition` payload carrier pair: `SourceEpochSchema` / `SourcePositionSchema` plus their payload-key constants and the `withEpochStamp` pairing helper in `packages/contracts/src/event.ts`, registered in Spec-005 at §Event Type Enumeration (run-scoped-variant admission). The stamp stays on the row for as long as its session exists: no background pass rewrites a row a person can see, and only deleting a whole session writes audit stubs, so the supersede projection always reads the stamp from the row itself. T3.11 waits on Plan-005 Phase 1.
- **Local node-owner principal binding:** the local-socket run-control adjudication (T2.5, and T3.4 / T3.5 identically) requires the daemon's **node-owner user identity** as its Cedar principal. The daemon's standing control-plane-authentication posture names the identity ([daemon.md §Responsibilities](../architecture/daemon.md#responsibilities)). T2.5, T3.4 and T3.5 read it from the calling principal [Plan-006](./006-local-ipc-and-daemon-control.md) Phase 2B stamps on the dispatch context. Plan-016's credential/identity provider seam is that principal's resolution source and is not a dispatch gate: while the seam is unwired the principal is absent, and an absent principal adjudicates as a deny. The Phase 2 and Phase 3 preconditions name Plan-006 Phase 2B.
- **Admitting-principal carrier:** a turn a steer opens executes under the admitting intervention caller's effective principal ([Spec-003 §Required Behavior](../specs/003-queue-steer-pause-resume.md#required-behavior)'s admits paragraph; [Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)), which requires the durable, replay-stable admitting-principal carrier that Plan-010 T2.2 / T2.7 consume ([Plan-010](./010-approvals-permissions-and-trust-boundaries.md) CP-010-12). The client-supplied `initiator_id` is informational and never a principal source. Plan-003 is the producer leg: T2.4 stamps `interventions.admitting_principal_id` beside the `origin` discriminator.
- **Snapshot-callee checkout-root parameter:** T3.13's capture call-site supplies the caller-resolved `checkoutRoot` — read from `run_execution_contexts.checkout_root` beside the execution root — as a [Plan-008](./008-worktree-lifecycle-and-execution-modes.md) CP-008-12 input. The parameter joins `captureTurnSnapshot` when Plan-007 Phase 2B extends `git/turn-snapshot-service.ts` (CP-008-15), and the `checkout_root` column lands with Plan-008 Phase 3 / T3.2, its only writer. T3.13 waits on both producers, so it is never written against the signature without the parameter.

## Design Decisions

This plan's design decisions. Each is registered in the corpus it touches: Spec-003 / Spec-005 for version derivation and emission, `api-payload-contracts.md §Method-Name Registry` for the wire method names, and `error-contracts.md` for the refusal codes.

- **D-003-1 `version` = any-run-progression counter.** The `expectedRunVersion` stale-replay guard (I-003-7 / T2.8) compares against a run `version` derived as an **any-run-progression counter** (reading (b)): it increments on every run progression — applied interventions included — not only on `run.*` state-machine transitions (reading (a)). **Rationale:** reading (a) fails to catch two steers racing on a still-`running` run (zero new `run.*` events → the second stale steer passes undetected); reading (b) closes that replay window. Plan-003 authors T1.7's accessor _shape_ and T2.8's guard _behavior_; the `version` _derivation_ follows this semantics. Spec-003 / Spec-005 define the `version` field on the `run.*` payload and its increment/emission point.
- **D-003-2 `expectedRunVersion` is mandatory (fail-closed).** The comparand is **required** on every intervention request ([Spec-003 §Interfaces And Contracts](../specs/003-queue-steer-pause-resume.md#interfaces-and-contracts) mandatory reading); the absent-comparand case is **rejected**, not applied. An optional comparand would let a caller bypass the stale-replay guard by omitting the field — the mandatory reading fails closed. T2.8 authors the present-comparand guard; the absent case rejects.
- **Scope extension — the mandatory comparand binds `run.pause` / `run.resume`, not only interventions.** The `RunPauseRequest` / `RunResumeRequest` contracts (`docs/architecture/contracts/api-payload-contracts.md §Plan-003 — Queue Steer Pause Resume`) carry the **same mandatory** `expectedRunVersion` guard, with `RunControlAck` echoing the advanced `runVersion` so the caller threads the fresh comparand forward. D-003-2 therefore **covers pause and resume as well as interventions**: a stale `pause` replayed against a run that has since progressed is the identical replay hazard the guard exists to close, so the comparand fails closed the same way (T3.4 / T3.5 apply the T2.8 guard before composing). `pause` / `resume` remain **orchestration-layer run-control verbs, not interventions** — they hold no `InterventionType` (`steer | interrupt | cancel`) membership and are not serialized through the intervention queue (ADR-011) — so this is a deliberate cross-cutting extension of the mandatory-comparand obligation, which the `api-payload-contracts.md` run-control comment also states.
- **D-003-3 the `run.*` method strings.** `run.queueList` / `run.queueCreate` / `run.queueCancel` / `run.queueReorder` / `run.intervene` / `run.pause` / `run.resume` / `run.childSteer` / `run.childInterrupt` / `run.childPauseSet` / `run.childrenStop` / `run.subscribeState` / `run.subscribeQueue` (CP-003-4) are the wire contract, registered in `api-payload-contracts.md §Method-Name Registry`. The reciprocal `provides` is on [Plan-006](./006-local-ipc-and-daemon-control.md), the `run.*` namespace owner.

- **D-003-4 — the intervention admission path carries an explicit `origin` discriminator, and the principal is required by database constraint on the user arm**. The `interventions` row records `origin TEXT NOT NULL CHECK(origin IN ('user', 'system'))` beside the nullable `admitting_principal_id`, with a table-level CHECK binding them: the principal is present exactly when `origin = 'user'`. **Rationale:** the alternative readings both fail. Inferring the origin from `initiator_id IS NULL` conflates a genuinely system-originated intervention with a user intervention whose initiator was simply not supplied, and it makes the security-relevant distinction a side effect of an unrelated column's nullability — a property no constraint can defend and any later change to `initiator_id`'s optionality would silently invert. Making the principal unconditionally `NOT NULL` is likewise wrong: Plan-014's budget / idle interrupts enter in-process below the wire authorization boundary with a NULL-for-system actor (CP-003-10), so there is no user to name, and forcing a synthetic one would put a fabricated identity into the audit record. The explicit discriminator keeps both arms honest and — because `origin` carries **no DEFAULT** — fails an unstamped insert closed at the database rather than defaulting into the arm that requires no principal. The daemon-resolved principal itself follows the shipped `approval_resolutions.approver_id` model (D-010-12) rather than minting a second convention, and a wire-supplied principal that contradicts the daemon's resolution refuses with the existing `auth.principal_mismatch` — deliberately reusing that error rather than adding a near-duplicate, since it already names this exact class of caller-asserts-vs-transport-proves conflict. Entails the T1.4 CREATE columns, T2.4's acceptance-time stamp, and the paired Plan-010 consumption (CP-003-14 ⇄ CP-010-12, registered there as D-010-20).
