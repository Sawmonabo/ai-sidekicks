## Goal

Implement the normalized provider driver contract, capability registry, and runtime binding persistence. Drivers execute within the local daemon as the execution authority (per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior)); the contract is the boundary between the session domain and provider-specific lifecycles. Phase 4 SDK exposure ships under a dedicated `driver.*` JSON-RPC namespace registered through Plan-006's namespace registry.

## Scope

This plan covers (a) the daemon's `ProviderDriver` interface in `packages/runtime-daemon` + the capability-flag schema clients read in `packages/contracts` (widened by the code leg) + per-tool `idempotency_class` metadata, (b) the in-daemon provider registry + runtime-binding persistence (`runtime_bindings`, `driver_capabilities` SQLite tables), (c) two initial drivers (Codex, Claude) implemented against the contract as local-runtime-node integrations, each operation graded `native`, `emulated`, `degraded` or `absent` on each, (d) capability refresh on its triggers + recovery-aware binding storage extension points, (e) typed SDK exposure of capability + intervention surfaces with degraded-fallback semantics (`status: "applied" | "degraded"`), and (f) the provider-admission contract, and the bridges each driver builds to its provider's own cloud tasks and voice.

## Non-Goals

- Multi-agent workflow semantics (Plan-007)
- Provider-specific UI tuning beyond capability exposure (out-of-scope for V1)
- A driver for a provider other than Claude Code and Codex, an agent runtime of the product's own, or a provider marketplace; [Spec-004 §Interfaces And Contracts](../specs/004-provider-driver-contract-and-capabilities.md#interfaces-and-contracts) lists the providers and every place that lists them, and a later provider joins only by widening that list.
- Shared hosted execution drivers — drivers execute within the local daemon per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior) + ADR-005. Work a provider runs in its own cloud is reached through that provider's own verbs under the session's account, never hosted by this runtime (T3.37).

## Preconditions

This plan rests on ADR-005, ADR-011, ADR-015, ADR-017 and ADR-029, and builds on:

- Plan-001 Phase 3's daemon schema;
- Plan-001 Phase 2's branded-id contracts;
- Plan-006's JSON-RPC client transport;
- **the daemon's own MCP client, which T5.1 builds on** — the daemon runs one MCP client of its own, for its own calls and for the servers it fronts on Codex, while a provider's own connections stay the provider's ([Spec-025 §Non-Goals](../specs/025-mcp-server-configuration-and-governance.md#non-goals)). That client makes a call task-augmented wherever the tool allows one, records the task handle before answering anything else, and runs the recovery poll (`tasks/get` → `tasks/result`), so T5.1 has its daemon-side caller.

Target paths below assume the implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

## Data And Storage Changes

Plan-004 owns these SQLite tables, the first four built in Phase 2 and `cloud_tasks` in T3.37:

- `runtime_bindings` — persists driver-instance ↔ session/run bindings. Plan-004's driver tasks also adds the driver-boundary subagent emitter/normalizer task — `subagent.started` / `subagent.completed` appends per the Plan-005 event-coverage registry's single-owner assignment; Plan-014's native-subagent governor consumes those rows and is gated on that task. Plan-013 extends with recovery-aware persistence methods (per CP-004-1; row-level recovery state lives in Plan-013's dedicated `recovery_checkpoints` table, not on `runtime_bindings`).
- `driver_capabilities` — caches the capability-flag matrix per active driver instance. The flag set is the daemon's one schema's `capability_flag` CHECK, and the schema's test proves each member inserts and a non-member fails; a flag added to the set adds no table and no column. The rows are rewritten whenever a capability read on one of §Default Behavior's triggers in [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md#default-behavior) finds a changed snapshot.
- `driver_tools` — per-tool metadata keyed `(driver_name, tool_name)`, persisting each tool's `idempotency_class` so the daemon's two-phase command-receipt protocol ([Spec-004 §Recovery Consequences](../specs/004-provider-driver-contract-and-capabilities.md#recovery-consequences)) resolves crash-recovery dispatch class without round-tripping the driver. T2.4 hydrates it into `listCapabilities` after restart.
- `driver_contract_meta` — per-driver parent row (`driver_name` PK) holding the advertised `contract_version` that cold-start cache hydration (T2.4) reconstructs into `GetCapabilitiesResult.capabilities.contractVersion` without round-tripping the driver (the cache-as-source-of-truth path). (the canonical table additionally caches the `cli_version_raw`/`cli_version_semver` pair; hydration treats a NULL pair as a cache miss and refreshes from the driver, since the required `GetCapabilitiesResult.cliVersion` is never fabricated — the columns sit in the daemon's one schema.)
- `cloud_tasks` — one row per task a session sent to its provider's cloud: the session, the provider, the provider's own task id, and the last state and attempts the provider reported. It holds no state the provider did not report (T3.37).

See [Local SQLite Schema §Driver and Runtime Binding Tables](../architecture/schemas/local-sqlite-schema.md#driver-and-runtime-binding-tables-plan-004) for column definitions (the Phase 2 tables carry the `Owner: Plan-004` annotation).

## API And Transport Changes

- Add typed driver capability + driver runtime events to the client SDK under a dedicated `driver.*` JSON-RPC namespace registered through Plan-006's namespace registry (per CP-006-6).
- Define the internal driver interface (canonical long-form names per [api-payload-contracts.md §Plan-004 — Provider Driver Contract (Internal Interface)](../architecture/contracts/api-payload-contracts.md#plan-004--provider-driver-contract-internal-interface) `interface ProviderDriver`). The base operations are `createSession`, `resumeSession`, `startRun`, `interruptRun`, `applyIntervention`, `respondToRequest`, `closeSession`, `listModels`, `listModes`, `getCapabilities`. The Spec-004 surface adds `forkConversation` (the provider leg of forking a session), `rewindConversation` (undo's conversation cut, in place), `setSessionGoal` and `clearSessionGoal` (the provider's own goal), `probeAuth`, `exportTranscript` and `replayTranscript`, `exportHandoverBrief`, `compactContext` and `listProviderCommands` — every operation with its interface member, per-driver implementation, normalizer and conformance test in the tasks below. Undo and fork are separate operations: undo is the provider's own conversation cut plus the daemon's file checkpointer, and fork makes a new conversation and leaves the source untouched.
- Add the client-facing names this plan's drivers serve beyond `driver.*`, each with its payload in [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md) and its schema in `packages/contracts/src/` (`command.ts` for `command.*`, `session.ts` for the `session.*` names, `cloud.ts` and `voice.ts`): the running commands `command.list` (live), `command.stop`, `command.background` and `command.write {sessionId, commandId, text?, endOfInput?}`, with the event `command.ended`; the session reads and actions `session.providerCommandsSubscribe`, `session.modeUpdate`, `session.sideQuestionAsk {question}`, `session.reviewStart {target}`, `session.memoryRead`, `session.autoMemoryUpdate`, `session.hookList` and `session.restart`; the cloud tasks `cloud.taskStart {sessionId, prompt, environment?, attempts?}` → `{taskId}`, `cloud.taskList {sessionId}` (live), `cloud.taskRead {taskId}`, `cloud.taskDiffRead {taskId, attempt?}` and `cloud.taskApply {taskId, attempt?}`, with the event `cloud.task_updated`; and voice: `voice.dictationStart {sessionId}`, `voice.dictationWrite`, `voice.dictationStop {cancel}`, `voice.dictationSubscribe`, `voice.callStart {sessionId, offerSdp}` → `{answerSdp}`, `voice.callStop`, `voice.callSubscribe`, `voice.voiceList`, `voice.stateUpdate {sessionId | null}` and `voice.stateSubscribe`. None of the event kinds is minted here; each is registered in [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md).
- Add the driver-namespace error codes to the JSON-RPC error registry (all present at [error-contracts.md §Driver](../architecture/contracts/error-contracts.md#driver)): `driver.unavailable` (503), `driver.timeout` (504), and `driver.capability_unsupported` (400 — note that this is the SDK seam's wire-error for invocation of an undeclared capability, distinct from the per-call `degraded` status returned by `applyIntervention` per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior); the two are not in conflict — `driver.capability_unsupported` covers the static "this driver does not support that capability at all" gate, `degraded` covers the dynamic "this intervention type is not supported but a fallback action is available" outcome); and the admission code `driver.cli_version_below_floor` (409), mapped and tested at this same Phase-4 seam.
- SDK seam Zod schemas: `DriverInterventionResultSchema = z.object({ status: z.enum(['applied', 'degraded']), fallbackAction: z.string.optional })` (per the Phase 4 envelope shape; see Phase 4 below).
- SDK factory pattern: daemon-only `createDaemonProviderClient(JsonRpcClient): DriverClient`. No control-plane variant per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior): drivers run in the local daemon, and work a provider runs in its own cloud is reached through the provider's own verbs (T3.37), never through a hosted driver.

### Phase 4 — Client SDK exposure + degraded-fallback

**Goal:** Author the typed SDK surface for capability + intervention controls under a dedicated `driver.*` JSON-RPC namespace (per Plan-006 CP-006-6). Daemon-side IPC handlers + SDK-side Zod-validated wrappers ship together. Subscription primitive reuses `LocalSubscriptionProducer<T>` per Plan-006 CP-006-4 precedent.

**Precondition:** Phases 1 and 2 merged.

**Design decisions:**

1. **Factory pattern**: daemon-only `createDaemonProviderClient(JsonRpcClient): DriverClient` — no control-plane variant. Aligns with [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior) (driver authority is local-daemon-resident; work a provider runs in its own cloud is reached through the provider's own verbs, T3.37, never through a hosted driver). Matches MCP/LSP best practice (single-transport for local-only capability servers).
2. **Namespace**: dedicated `driver.*` (added to Plan-006's remainder namespace registry per CP-006-6). The client-facing method names follow canonical long-form per ADR-009 and Plan-006 I-006-9: `driver.listCapabilities`, `driver.interruptRun`, `driver.applyIntervention`, `driver.listModels`, `driver.listModes`, `driver.compactContext`, plus the subscription method `driver.subscribeEvents`; the live `/` list reaches clients as `session.providerCommandsSubscribe` (T4.9). **Admission by the governing principle:** `compactContext` and the live `/` list both operate on an already-existing session, and neither establishes, restores, starts, nor tears down a session-or-run domain object, so neither is orchestration-owned. They differ from the parity operations kept daemon-internal below in the one respect that decided those: those operations each have an existing client route (the conversation cut through `session.restore`, the fork through `session.fork`, the goal pair through Plan-014's goal service), and these have none — a composer affordance and a command autocomplete can be reached by no verb this namespace already carries, and adding an intervention for compaction would widen `Spec-003`'s V1 control set. Registration rides CP-006-6, which lists this plan's client-facing methods; that plan builds the `register` substrate. **Lifecycle operations stay daemon-internal.** The four session/run **lifecycle** operations — `driver.createSession`, `driver.resumeSession`, `driver.startRun`, `driver.closeSession` — are **daemon-internal**: invoked only by the session/run orchestration layer on the in-daemon `ProviderRegistry` (T2.3), never registered as client-callable JSON-RPC methods. Governing principle: a `driver.*` method is client-facing iff it operates on an already-existing session/run (capability introspection, intervention/control, model/mode reads, event subscription); methods that **establish, restore, start, or tear down** a session-or-run domain object are orchestration-owned, because orchestration must persist the runtime binding and emit the canonical lifecycle event around the driver call. This honors [Spec-004 §Example Flows](../specs/004-provider-driver-contract-and-capabilities.md#example-flows) (the driver "only sees `interruptRun` followed later by `startRun`" — those lifecycle calls are driven BY orchestration, not by clients) and the Phase-4 goal above ("capability + intervention controls"). Exposing the lifecycle verbs as client-callable would let a renderer/CLI start or destroy a provider session/run while bypassing the orchestration that owns `runtime_bindings` persistence + canonical `run.*` event emission. The in-daemon `ProviderDriver` interface (T1.1's base operations and T1.8's additions, all daemon-internal per T4.8) keeps every operation — only its client JSON-RPC exposure is narrower. Clients reach lifecycle indirectly through the orchestration namespaces (`session.*` per Plan-001 — `session.create` maps to `directoryService.createSession` per `docs/architecture/contracts/api-payload-contracts.md §Plan-028 — Remote Control Bootstrap (control-plane tRPC)`, NOT `driver.createSession`; `run.*` per Plan-003).
3. **Envelope shape**: Zod-validated `DriverInterventionResult` at SDK seam (`{ status: 'applied' | 'degraded'; fallbackAction?: string }`) mirroring driver-internal shape ([Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-004 §Fallback Behavior](../specs/004-provider-driver-contract-and-capabilities.md#fallback-behavior-1)) with wire-level validation. ### Driver Authoring Rules

Two rules govern every driver, normalizer and parser task in this plan.

**CLI-currency verification.** Every CLI-mechanism claim is verified at authoring time against the binaries the [provider-wire reference](../reference/provider-wire/README.md) family pins, read from that family rather than restated here; behaviors pin by version anchor, never by date, and the driver's own admission floors are [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior)'s. Codex protocol claims are regenerated from the binary's own `codex app-server generate-ts` / `generate-json-schema` output, which is canonical over prose; hand-transcription is prohibited. Claude `--help` is not authoritative — the published docs govern. For the rewind path: on Codex the cut is `thread/revert {threadId, beforeTurnId}` on the same thread, and `0.156.0` has no `thread/rollback` (`-32600 unknown variant`), so T3.15 leg 1 registers no handler for it ([`codex.md`](../reference/provider-wire/codex.md#threadrevert--the-undos-conversation-cut)). On Claude, `rewind_conversation` reports a refusal as `subtype: "success"` with `rewound: false`, so the driver reads `rewound`; and `--resume-session-at`, which the fork uses, is binary-probe-only and absent from the live CLI reference, so before any driver code invoking it lands the implementer verifies it against the then-installed binary ([`claude.md`](../reference/provider-wire/claude.md) §Gaps recorded). The daemon's file checkpointer ([Plan-008](./008-worktree-lifecycle-and-execution-modes.md)) is the durable file path regardless of the provider leg.

**No silent loss; fail open at the parse boundary, fail closed on a malformed frame.** A wire kind the driver recognizes but cannot map to a registered `SessionEventType` — an unknown-but-parseable kind, a kind whose contracts registration has not yet landed, **or** a registered kind whose `SessionEventSchema` payload variant has not yet landed — is **fail-open**: it routes to the T3.11 default-branch diagnostic and is **never dropped and never forced into an envelope against a missing type or a missing union variant**, exactly the seam Plan-005's `EVENT_DISPOSITION_BY_KIND` and its exhaustiveness test delegate to the Plan-004 normalizer. Payload variants are Plan-004-owned, on the emitter-authors-payload rule: each variant registers through the `SessionEventSchema` union-registration seam with — or before — the first normalizer change that emits its kind, so emission turns on variant by variant and never by a registry entry alone. A **malformed frame** — bytes that do not parse as a valid provider wire message at all — is **fail-closed**: the driver rejects it with a typed parse error rather than fabricating a partial event. Provider correlation identifiers (`tool_use_id`, `parent_tool_use_id`, Codex item/call ids) are copied **verbatim** onto the normalized event — never reformatted, re-cased, re-padded, or re-encoded — because tool-event pairing is by exact-string match and a reformatted correlation id is the single most common documented cause of pairing failure.

Test: a stubbed provider that returns success on a malformed replay fails the operation (T3.20); a reordered pipeline fails the pairing assertion (T3.19).
- **I-004-9** — What cannot be carried is declared, and a diminished continuation is visibly diminished. Every operation that reconstitutes a session under a different provider, model, or account emits a **required** declared-loss list whose empty value is a positive claim that nothing was dropped; an operation settled on the hand-over brief reports `degraded` and never `applied`; and a structurally invalid history is classified a permanent refusal rather than retried. Source: [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-004 §Canonical Transcript Export And Replay](../specs/004-provider-driver-contract-and-capabilities.md#canonical-transcript-export-and-replay). Enforced by: T3.21 (hand-over-brief floor + `degraded` settlement), T3.22 (permanent classification). Test: a tight verbatim budget in the brief never splits a tool exchange (T3.21); a permanently-refusing provider is called exactly once (T3.22).
- **I-004-10** — Version decides admission and nothing else; every capability is decided on its own. A build at or above the configured floor attaches, above the pin included, and a build below it refuses fail-closed; above the floor no capability is resolved from a version comparison or a registry census, and every capability carrying an **admissible** probe — zero-turn, non-mutating, and decisive at the granularity the capability is consumed at — is resolved from that probe against the running build rather than from a static table, with each result reported under its detection source; a capability with no admissible probe resolves from the matrix and is **declared** `static` with the failing conjunct named, which is a stated property rather than an unwritten probe. Either way a moved provider surface withdraws exactly one flag and never a session. The version compared, the version recorded on the run's binding, and the version of the process that runs the session are one reading, and that process's auto-updater is disabled so the reading stays true for the session's life. Source: [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-004 §Capability discovery](../specs/004-provider-driver-contract-and-capabilities.md#capability-discovery). Enforced by: T3.23 (resolution, in-band read, floor gate, binding persistence), T3.24 (per-capability probes + detection source), T3.25 (auto-update suppression + the Codex posture on the `permissions` profile). Test: an above-pin build attaches and keeps every still-answering capability while a refusing probe withdraws only its own flag (T3.24); the binding row's version equals the spawned process's own report under launcher drift (T3.23); every probe-table entry declares a mechanism, each `static` entry names its failing admissibility conjunct, and the suite fails if any entry claims `probed` without one (T3.24); a probe suite spends zero billed turns — asserted at the provider transport, not at the daemon's event stream — and fails when its negative control succeeds (T3.24).

- **I-004-11** — A driver never emits a provider's cumulative counter as a per-turn figure, and no normalized token axis counts a token twice. Every usage emission is a per-axis delta derived from **one base register per provider thread and axis, advanced in stream order** — never a base snapshot copied at turn dispatch — and attributed to **the turn the metered frame itself names**, never to whichever turn is open at arrival. Base establishment is two-armed: a fresh provider session — replay-seeded included — bases at **zero**, its first reading metering in full, and a provider-native resume bases at **the daemon's own prior-emitted cumulative sum for that thread**, never at the first post-resume reading. A context compaction does not re-base; a decrease on a declared-cumulative axis floors at zero with a recorded diagnostic rather than emitting negative spend; and a wire-declared per-turn figure **corroborates** the derived interval — mismatch diagnosed — and never substitutes for it. The normalized axes are a partition — the input axis is uncached input, subtracted only where the breakdown's own sum identity confirms containment, with an unconfirmed identity emitting unsubtracted plus a diagnostic — and cost is derived from the provider's full breakdown, never by re-multiplying that partition. Source: [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-004 §Interfaces And Contracts](../specs/004-provider-driver-contract-and-capabilities.md#interfaces-and-contracts). Enforced by: `provider/usage-delta-accountant.ts` as the single metering path both normalizers emit through (T3.11), with the floor-hit, the cross-check mismatch, the failed containment identity, and the retained cache split all landing on the T3.11 `DriverDiagnosticRecord` channel. Test: T3.11's cumulative-sequence, interleaved-attribution, fresh-first-reading, replay-seeded-is-fresh, resume-prior-emitted-sum, compaction-no-re-base, late-frame, floor-hit, cross-check-mismatch, nested-cache, and failed-identity assertions (AC19).
- **I-004-12** — Only the session's own thread projects, and no child's spend or interactive request is lost. Every inbound provider frame is classified by family against the pinned stream-surface census before any projection decision: a thread-scoped family routes by explicit thread identity, a censused connection- or account-scoped family routes without one, and an unrecognized family with no thread identity quarantines. Thread identities register ahead of the refusal rule — the session's own at establishment, a child's from the provider's parent-linked announcement — with a present-but-unregistered identity held in a bounded pending-registration buffer (released on registration, shed with a diagnostic on timeout) distinct from the quarantine an absent or unrecognized identity enters, both bounded and reported, never projected and never attributed to the parent by arrival order. Usage counters and child-raised interactive requests are both carved out **ahead of** suppression — provider-attributed subagent spend lands on the (`runId`, `provider`, `subagentId`) triple, provider-internal child spend lands on the parent run at run scope, and a child's request routes through the same dispatch/approval pipeline as the parent's and is answered on the child's own correlation — so suppression governs the child's transcript projection alone; child lifecycle reaches the timeline only as `subagent.started` / `subagent.completed`. Source: [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-014 §Provider-Native Subagents](../specs/014-multi-agent-orchestration.md#provider-native-subagents). Enforced by: `provider/thread-frame-router.ts` as the single routing decision both normalizers consult (T3.11), consumed unchanged by T3.14's terminal-emission boundary, which adds no second routing decision. Test: T3.11's foreign-thread-suppression, connection-scoped-pass, unknown-family-quarantine, absent-identity-quarantine, quarantine-shed, pending-hold-release, hold-timeout-shed, child-spend-attribution, compaction-child-run-scope, child-request-carve-through, and surviving-lifecycle-pair assertions (AC20).
- **I-004-13** — A console-parity operation settles on the provider's own evidence, and a provider command is bound to where it was read from. `compactContext` reports success only after the provider's typed compaction frame is observed, never on the request being accepted; a `driver_command` frame carrying a provider command is dispatched only after that command's literal name is found in the enumeration read for **that session's** `(driverName, providerAccountId)`; and an entry from `listProviderCommands` is offerable and dispatchable only through agents of that same binding. Source: [Spec-004 §Desktop Console Parity Surfaces](../specs/004-provider-driver-contract-and-capabilities.md#desktop-console-parity-surfaces); [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior) (the `driver_command` frame and its two guards). Enforced by: T3.26 legs (a) and (b). Test: an ack-without-a-compaction-frame settles as a failure; an absent command name refuses before sending; a cross-binding dispatch refuses as `driver.capability_unsupported` (T3.26; T4.9).

### CP-004-5 — Recovery-needed surface owed to [Plan-005](./005-session-event-taxonomy-and-audit-log.md) / [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)

**Capability state is stored, never evented.** The driver tables hold the current capability state, `hydrate()` rebuilds it without replaying anything, and the cache invalidates from the writer's `snapshotChange` (T2.4). Nothing reads a capability event, so Plan-004 emits none.

**Recovery-needed condition reuses existing `run.failed` surface.** [Spec-004 §Fallback Behavior](../specs/004-provider-driver-contract-and-capabilities.md#fallback-behavior) calls for drivers to "surface a visible `recovery-needed` condition" on resume-handle failure. [Spec-005 §Run Lifecycle (run_lifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle) already declares this surface: `run.failed` payload includes `recoveryCondition?: 'recovery-needed'`. Plan-004 does NOT emit a separate `driver.recovery_needed` event. Instead:

1. Plan-004's `resumeSession` returns a typed failure result (T3.1, T3.6).
2. Plan-013's recovery dispatcher receives the typed result.
3. Plan-013 emits the existing `run.failed` event with `recoveryCondition: 'recovery-needed'`.

This keeps the recovery-needed signal on the canonical run-lifecycle surface where downstream consumers already subscribe; avoids creating a parallel driver-specific recovery event.

**What Plan-005 supplies.** Plan-005 Phase 3 defines `providerFailureDetail?: string` on the `run.failed` payload (the `RunStateChangeEvent` member, in [`api-payload-contracts.md` §Plan-003 — Queue Steer Pause Resume](../architecture/contracts/api-payload-contracts.md#plan-003--queue-steer-pause-resume)). **Why bidirectional.** Recovery-needed flows through Plan-013, not directly from the driver, so the driver's `resumeSession` return type stays a pure typed failure result; this plan's result feeds Plan-005's `run.failed` field.

### CP-004-6 — Cross-cutting symbol co-location (`InterventionType` enum + `RunId` brand / `RunIdSchema` + `ArtifactId` brand / `ArtifactIdSchema`) owed to [Plan-003](./003-queue-steer-pause-resume.md) + [Plan-010](./010-approvals-permissions-and-trust-boundaries.md) + [Plan-012](./012-artifacts-files-and-attachments.md)

The cross-cutting `InterventionType = "steer" | "interrupt" | "cancel" | "faster_model_retry"` enum (`docs/architecture/contracts/api-payload-contracts.md §Shared Enums`; the `provider-driver.ts` union carries the same members and `ApplyInterventionParams` the first three, undo being `session.restore`'s conversation cut through the dedicated `rewindConversation` op rather than an intervention, and Plan-003's consumers arrive only after **T1.8** ships the union — its Phase 1 waits on Plan-004 Phase 1 — so union and consumers never diverge) is consumed by both Plan-003's `run-control.ts` and Plan-004's `provider-driver.ts`. Resolution: Plan-004 Phase 1 (T1.4) co-locates the `InterventionType` re-export in `provider-driver.ts` since Plan-004 ships earlier. Plan-003 imports the enum from Plan-004 — a forward, build-order-consistent import.

The **`RunId` brand (`type RunId`) and its validator `RunIdSchema`** co-locate in the same `provider-driver.ts` by the identical logic, and for an additional structural reason: `RunId` is `InterventionType`'s struct-mate in `ApplyInterventionParams` (`{ type: InterventionType; targetRunId: RunId; … }`, `docs/architecture/contracts/api-payload-contracts.md §Plan-004 — Provider Driver Contract (Internal Interface)`). Earliest-consumer placement governs each symbol independently: `type RunId` is first consumed by the Phase 1 `ProviderDriver` interface method params (T1.1), and `RunIdSchema` is first consumed by the Phase 4 `InterruptRunParamsSchema` (T4.2) — so both home in Plan-004, the `type` and `Schema` paired in one file per the established `session.ts` `brandedUuidIdSchema` convention. Plan-003 imports `RunId`; Plan-010 imports both `RunId` and `RunIdSchema` — each an upward, forward edge. Authoring `RunIdSchema` in Plan-003's `run-control.ts` would be a backward import for Plan-004's own `InterruptRunParamsSchema` consumer, i.e. structurally forbidden.

**Precedent.** This matches Plan-001's ownership pattern for the brands it actually ships (`SessionId` and `UserId` co-located in `session.ts` Phase 2 — each `type X` paired with its `XSchema` per the `brandedUuidIdSchema` convention; their earliest-shipping consumer is Plan-001). The governing rule is **earliest-consumer placement**: a cross-cutting symbol is declared in the contract file of its earliest-shipping consumer, and every later plan imports it upward — never re-inventing a parallel definition. `RunId` / `RunIdSchema` are **not** in Plan-001 / `session.ts` (Plan-001 ships no run-domain symbol); their earliest-shipping consumer is Plan-004, so they home in `provider-driver.ts`.

**The `ArtifactId` brand (`type ArtifactId`) and its validator `ArtifactIdSchema`** join the same file under the identical rule and with one difference worth stating: unlike `InterventionType` and `RunId`, whose semantics are Plan-003's and this plan's, `ArtifactId`'s shape is **[Spec-012](../specs/012-artifacts-files-and-attachments.md)'s and [Plan-012](./012-artifacts-files-and-attachments.md)'s**, so this is a homing decision and not an ownership one — the `node-id.ts` precedent, where `NodeId` sits in a dependency-free leaf with its owner's shape verbatim. Earliest-consumer placement selects this file because `SteerPayload.attachments` (T1.4) is the first member typed `ArtifactId[]`, ahead of Plan-003's `run-control.ts` `steer` arm and of Plan-012's own `artifacts/`, whose Task 1 imports the brand rather than restating it. A change to the brand's spelling or accept set is Spec-012's and Plan-012's to make, and is made in this file; a second declaration of that brand anywhere would be a second source of truth for what an artifact id is.

**Why bidirectional.** Plan-003 reviewers see the import-from-Plan-004 of `InterventionType` + `RunId` + `ArtifactId` / `ArtifactIdSchema`; Plan-010 reviewers see the import of `RunId` + `RunIdSchema`; Plan-012 reviewers must import `ArtifactId` / `ArtifactIdSchema` at Task 1 rather than declaring a sibling; and Plan-004 reviewers must know these symbols are shared and must not relocate them without coordinating with Plan-003 + Plan-010 + Plan-012.

### CP-004-11 — Driver-spawn capability report and the MCP set-replacement non-interference guarantee owed to [Plan-025](./025-mcp-server-configuration-and-governance.md)

Plan-025 T28.3.2 depends on this plan's driver-spawn capability report. T3.24 provides it, in two parts. **The report:** a per-capability result carrying each flag's `CapabilityDetectionSource`, produced at spawn and refreshed on T3.12's triggers. **The guarantee:** `mcp_set_servers` is **not a capability flag** and appears on no report, and no capability probe sends it, because an empty set would clear a live session's servers. **Owed to:** Plan-025 T28.3.2, which consumes T3.24's report.

### CP-004-12 — Console-parity surfaces published to [Plan-011](./011-live-timeline-visibility-and-reasoning-surfaces.md), [Plan-021](./021-desktop-app-and-renderer.md), and [Plan-014](./014-multi-agent-orchestration.md)

This plan publishes three things the desktop-console parity legs consume, and authors nothing on their side. A client answers a provider's ask through `approval.resolve` or `question.resolve`, never through the driver; the daemon delivers that answer with the driver op `respondToRequest`. **(a)** `driver.compactContext` (T4.9) and the `context_compaction` declaration, read through the existing `driver.listCapabilities` cache, gate and drive the composer's compaction popover. **(b)** `session.providerCommandsSubscribe` (T4.9) and the `provider_commands` / `output_speed` declarations feed the composer's command list and its speed control. The **routing invariant travels with the data, not with the consumer's discipline**: every entry the read returns carries the `(driverName, providerAccountId)` it was read under, so a consumer replaces its list with each emission rather than filtering an older one, and a cross-binding dispatch refuses at this plan's boundary as `driver.capability_unsupported` rather than relying on the renderer to have filtered correctly. **(c)** The provider's own **declared** output-speed state and its provider-supplied reason, **held as driver-session state against the binding** (T3.26, T3.27), on the Claude leg the process's `initialize` reply reports it before any turn and each session handshake reports it again, so that leg's binding carries an observation from its spawn onward. Reading it costs **no provider round-trip** — the binder reads state the driver already holds, and never waits for, forces, or spends a turn to obtain it — which is what lets a list read serve it without starting, resuming, or interrogating a provider process, and it is deliberately stored nowhere on either side: a persisted observation would be a second and staler record of a fact the running session already holds, and would let a mode that stopped being available across a restart keep reading as accepted.

**Owed to:** Plan-011 T4.10 / T4.11, Plan-021 T-021r-6-2, and Plan-014 T3.20. **Reciprocals:** Plan-011's `CP-004-12` obligation row, Plan-021's `CP-021-8`, and Plan-014's `CP-014-21`. This plan's side is T3.26 and T4.9; leg (d) publishes a value T3.26 already captures.

### CP-004-13 — Machine-authored content column consumed from [Plan-005](./005-session-event-taxonomy-and-audit-log.md) (⇄ CP-005-15)

(i) What T3.20 consumes is the **`HydratedSessionEvent`** projection Plan-005 T3.6 declares and T3.8 builds — the event paired with a closed two-arm `content` union — never a body spliced into `payload`; the `unavailable` arm carries the reason, which is where this plan's `'turn_content_unavailable'` gets its truth value instead of being inferred from an absent key. (ii) The column is local to the machine that runs the session and is never relayed or backfilled. A session runs on one machine, and a device that drives it through Remote Control reaches that machine's daemon, so the fold runs where every row of the session was written and reads each body the daemon logged. Plan-005 Phase 3B creates `session_events.content_payload` — the durable home for assistant- and tool-generated prose — together with its extended write path and the read path. This plan is the **consumer and the reason the column exists**: [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md) rules the daemon's canonical transcript authoritative for the content of a provider session, [Spec-004 §Canonical Transcript Export And Replay](../specs/004-provider-driver-contract-and-capabilities.md#canonical-transcript-export-and-replay) scopes that transcript's content to what [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)'s taxonomy carries, and without this column that taxonomy would carry a record that an assistant spoke rather than a record of what it said.

This plan authors **nothing** on Plan-005's side — no column, no codec — and takes one task-scoped hold in return: **T3.20 dispatches only after Plan-005 Phase 3B merges**, for the reason stated in that task's own entry (a post-replay assertion over content-free turns cannot distinguish an accepted replay from a silently dropped one). T3.19 is deliberately **not** held: its fold and export are correct over a body-less log.

**Owed to:** nothing — this is a consumer-side registration. **Reciprocal:** Plan-005's `CP-005-15`.

**What the two loss members report.** A turn with no `content_payload` body is what `'turn_content_unavailable'` reports, and a `contentTruncated` row is what `'turn_content_truncated'` reports; Plan-005 T3.6 writes the `contentTruncated` flag and T3.7 tests it. T3.19's fold reads both conditions into `declaredLosses`, per the Fold step of [Spec-004 §Canonical Transcript Export And Replay](../specs/004-provider-driver-contract-and-capabilities.md#canonical-transcript-export-and-replay), and T3.19's tests cover each. `api-payload-contracts.md` registers both loss kinds, so the fold emits a registered kind rather than a free string.
