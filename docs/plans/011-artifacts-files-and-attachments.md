## Goal

Implement immutable artifact publication and attachment ingestion — with a PDF's first page — the session's staging verbs and the cover of a staged picture, the artifact reads every linked device calls, deletion with CAS reclaim, and the session sweep the purge calls.

## Scope

This plan covers artifact ids and manifests, attachment ingest and its validation pipeline, the ingest worker (a PDF's first page, the cover), payload storage, a chat file's versions, `artifact.list` and `artifact.read`, the staging verbs, artifact deletion with CAS reclaim, and the session sweep the purge calls.

## Non-Goals

- Full artifact preview UX
- Notification behavior for artifact publication
- Renderer views: the inspector's artifact section, the files-written row, the file surface, the quick look and its cover control call this plan's methods and are built with the console ([Plan-020](./020-desktop-app-and-renderer.md))

## Data And Storage Changes

- Add durable `artifact_manifests` and `artifact_payload_refs` records with provenance and producer metadata, in the one collapsed schema and its test. A chat file's versions are manifests of one path in the chat's managed workspace, each with its version number and the time it was written.
- Keep manifest storage separate from large payload storage while preserving content-addressed lookup or equivalent immutable payload identity.
- An artifact is never changed in place. A covered picture is a new artifact, and the uncovered copy it replaces is deleted.
- See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) for column definitions.
- **No schema change is made for the ingest stream protocol.** The ingest stream registry, its per-stream completion records, and the aggregate spool reservation are in-memory daemon state — a stream dies with the process and its spool goes quiescent for the `mtime` reaper — so no table is minted for a transient whose lifetime `max_ingest_stream_lifetime` already bounds, and the accepted cost is the named residual (a retried `Complete` after eviction ends as a second manifest row over one deduplicated CAS payload). An outside picture is stored as it came (T14.8), and a PDF's first-page picture and page count are stored beside the PDF.
- **No schema change is made for the CAS reference count** — it is derived by query over `artifact_payload_refs.storage_path` (I-011-4), deliberately not a stored counter column. Recorded here because "add a refcount column" is the obvious wrong turn and its absence should read as a decision, not an omission.

## API And Transport Changes

- Add `ArtifactPublish`, `ArtifactRead` (the wire method `artifact.read`), `artifact.list` and `AttachmentIngest` to shared contracts and the typed client SDK, and serve the session's staging verbs `session.attachmentAdd`, `session.attachmentRemove` and `session.attachmentCover`. `artifact.read` takes `{artifactId, version?}` and returns the version in view, how many versions exist and when the one in view was written; `artifact.list {sessionId}` returns the session's plans and, on a chat session, its files and folders with their versions.
- `AttachmentIngest` is carried as the `AttachmentIngestInit` / `AttachmentIngestChunk` / `AttachmentIngestComplete` trio under the Spec-006 4 MB frame ceiling, and `AttachmentIngestCompleteResponse` carries `derivedMediaType` and `derivedSizeBytes` — the server's own findings over the spooled bytes; Init's `mediaType` (**optional** — the pipeline's declaration-absent path is a first-class state a required field could never exercise) / `declaredSizeBytes` are annotated **advisory**, never persisted as fact (I-011-3). Attachment references on any carrier are typed `ArtifactId[]`, order-preserving, with an explicit unresolved marker rather than a silent omission (I-011-5).
- **No wire member is added, removed, or retyped by the stream protocol.** `AttachmentIngestCompleteRequest` still carries only the `ingestId` — which is exactly why the completion record is keyed on the stream and **stamped** with the committed digest rather than discriminated on a caller-supplied one: a _divergent_ Complete has no wire form to take, so the stamp is a fail-closed defense-in-depth check, never a new field. The retry semantics change only what a **second identical call** returns: the original response, verbatim, for as long as the stream's registry entry lives. No error code is minted by the stream protocol: `artifact.ingest_stream_invalid` (409) and `artifact.ingest_capacity_exhausted` (429) are registered in [error-contracts.md §Artifact](../architecture/contracts/error-contracts.md#artifact).
- Return manifest metadata first and use explicit payload handles for large or deferred content reads.

## Invariants

- **I-011-1 (Immutability):** A published artifact's payload is content-addressed (SHA-256) and never mutated in place; a live workspace path is never treated as durable payload identity. ([Spec-012 §Required Behavior](../specs/012-artifacts-files-and-attachments.md#required-behavior); verified by T14.2, T14.3, T14.12.)
- **I-011-2 (Never changed in place):** An artifact is never changed in place: a changed form is a new manifest with its own id — a covered picture is a new artifact, and a chat's later write to a path is a new version beside the earlier ones, which it never replaces. ([Spec-012 §State And Data Implications](../specs/012-artifacts-files-and-attachments.md#state-and-data-implications); verified by T14.9, T14.12.)

- **I-011-3 (Server-derived ingest, any file):** For caller-supplied bytes crossing the client→daemon trust boundary — the `AttachmentIngest` trio, and a boundary-crossing `ArtifactPublish`, because the pipeline binds to the boundary rather than to a method name (a boundary-crossing publish declaring the `file` family is refused outright and directed to `AttachmentIngest`) — the daemon derives media type and size **from the payload bytes it received**, and a caller-declared `mediaType` or `sizeBytes` is advisory input, never persisted as fact and never used to make an admission decision. No file is refused for its type and nothing is rewritten: the derived type decides only whether a file offered as a picture goes to the provider as a picture, in a format that provider takes, and what the manifest records. The pipeline of [Spec-012 §Ingest Validation And Payload Bounds (V1)](../specs/012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1) runs **before** any byte reaches the CAS or any manifest row is written, so a refused payload leaves no durable artifact behind, and a stream breaching its own declared total is terminated with its spool deleted. The other `artifactType` families are producer-fixed and do not traverse this path **when the daemon itself produces them**; the same families arriving across the trust boundary do. **"Bounded" means bounded under concurrency, and "retry-safe" means retry-safe for the whole trio.** Three rules join this invariant. **(a) Completion is idempotent within its stream's lifetime.** The `AttachmentIngestComplete` response is recorded on that stream's registry entry, stamped with the committed digest, and a retry returns that saved result verbatim — no pipeline re-run, no second manifest row. A lost response must not cost the caller the re-upload of a large file, and the opposite failure is equally prohibited: re-running the pipeline and minting a second manifest for one completed stream. Completion surrenders the reservation, the count slot, and the spool at commit, so a completed entry pins no budget; past `max_ingest_stream_lifetime` the entry and its record are evicted and a retry takes the ordinary `artifact.ingest_stream_invalid` (409), whose named residual is one extra manifest row over a deduplicated CAS payload — never duplicated bytes, never a lost artifact. **(b) The admission ledger is reserve-then-install.** The aggregate admission ledger (`max_active_ingest_streams` plus the reservation total against the spool volume's free space, read at admission) tests and spends inside one critical section: a bound checked outside the mutation that spends it is exceeded by up to one payload per racing caller, which is the parallel-submission form of the very denial-of-disk the budget exists to stop. **(c) Every call on one `ingestId` is single-flight, and the reaper's eviction path takes the same exclusion** — sequence validation, spool append, running-count and last-chunk-digest advance, and acknowledgment are atomic per call, so an original racing its own retry cannot double-append or compare against half-updated state, and a stream is never served and evicted at once. The exclusions compose in one total acyclic order — per-`ingestId` → the admission ledger → per-`storage_path` ([Spec-012 §Implementation Notes](../specs/012-artifacts-files-and-attachments.md#implementation-notes)). A refused Init still creates nothing, and that is asserted through **admission** — the next Init admitting once a slot or reservation frees — never through an identifier the refusal never issued. ([Spec-012 §Ingest Validation And Payload Bounds (V1)](../specs/012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1); verified by T14.4.)
- **I-011-4 (Reclaim-at-zero):** A CAS payload is reclaimed only when its derived reference count reaches zero — the count is **computed over `artifact_payload_refs.storage_path`, never stored in a counter column**, so it cannot drift out of agreement with the rows it summarizes and no reconciliation job is owed. The purge removes a session's manifests and their payload-refs, and the cover removes the uncovered copy and its payload-ref; a shared blob survives while any other manifest still references it (the T14.2 / T14.3 dedup guarantee is exactly the case that makes this load-bearing). Reclaim is concurrency-excluded per storage key: every CAS writer checks-and-references inside that key's in-process exclusion, every reclaimer — the boot sweep included — derives-and-unlinks inside it, and the unlink re-derives the count after commit and aborts above zero, so no interleaving of a same-hash publish with a reclaim leaves a manifest over missing bytes. That per-key exclusion is the **leaf** of this plan's single acquisition order — per-`ingestId` → the ingest admission ledger → per-`storage_path` ([Spec-012 §Implementation Notes](../specs/012-artifacts-files-and-attachments.md#implementation-notes)) — so the ingest path's exclusions compose with this one rather than racing or deadlocking against it; `AttachmentIngestComplete` is the path that holds a stream exclusion and then takes this leaf for its step-3 CAS rename. ([Spec-012 §Local Artifact Deletion And CAS Reclaim (V1)](../specs/012-artifacts-files-and-attachments.md#local-artifact-deletion-and-cas-reclaim-v1); verified by T14.7.)
- **I-011-5 (No silent attachment drop):** An attachment reference carried by any turn-scoped payload is a typed `ArtifactId`, never an opaque `unknown`, and the reference list is **order-preserving**: the position an attachment occupies on the way in is the position it occupies on the way out. An attachment that cannot be delivered — a deleted artifact, including a payload reclaimed under I-011-4 — is rendered as an **explicit unresolved marker in its own position** and never omitted, because a silently shortened list makes the recipient reason about a message that was never sent; the marker names its cause, `deleted`. ([Spec-012 §Required Behavior](../specs/012-artifacts-files-and-attachments.md#required-behavior), [Spec-012 §Fallback Behavior](../specs/012-artifacts-files-and-attachments.md#fallback-behavior); verified by T14.5.)
- **I-011-6 (Original pictures):** A picture from outside the daemon — staged by attach, paste or drop, staged from another device, or written by an agent and shown in the transcript or the inspector — is stored, drawn and sent as its original bytes: nothing re-encodes it, strips its metadata or bounds its pixels before a decode. A PDF's first page is drawn only in the ingest worker, and a crash or a hang in the worker refuses that one file and never faults the daemon. ([Spec-012 §Ingest Validation And Payload Bounds (V1)](../specs/012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1) step 2; verified by T14.8.)
- **I-011-7 (Covered means gone):** After `session.attachmentCover`, the bytes a provider can receive for that attachment have every pixel under each box drawn black, not masked over, and the uncovered copy is deleted from the store; a sent picture is never covered. ([Spec-012 §Required Behavior](../specs/012-artifacts-files-and-attachments.md#required-behavior); verified by T14.9.)

### Phase 2 — Ingest And Publication Producers

**Precondition:** Phase 1 merged.

T14.2's `artifact-id.ts` brands the output of the daemon-wide UUIDv7 generator `mintUuidV7` (`packages/runtime-daemon/src/ids/uuid-v7.ts`) rather than generating bits of its own. T14.2 + T14.3 + T14.4 + T14.5 — the two independent producers (ingest and publish, each writing its own manifest) plus the CAS payload store, and the ingest-validation pipeline and the typed attachment-reference carrier; §Rollout Order steps 1–2 (local payload storage; attachment ingest and artifact publication in local sessions). **T14.4 lands in this phase deliberately, not in a tail phase:** it is the pipeline on the `AttachmentIngest` path T14.2 builds, and a pipeline that ships after the ingest it wraps means shipping a byte-accepting interface that records the caller's declaration as fact first — the pipeline and its producer are one slice. T14.5 joins them because the carrier it resolves names the artifacts this phase's producers mint.

#### Tasks

- **T14.2 — Attachment ingest + immutable payload store.** Implement `runtime-daemon/src/artifacts/attachment-ingest-service.ts` and `payload-store.ts`: normalize name/media-type/size, compute SHA-256, write the CAS-keyed payload blob, and — **in one transaction** — persist the attachment's own `artifact_manifests` row (`state` = `published`, an uploaded attachment _is_ a published artifact the moment it is ingested, [Spec-012 §Default Behavior](../specs/012-artifacts-files-and-attachments.md#default-behavior) newly-uploaded-attachments bullet + [Spec-012 §Example Flows](../specs/012-artifacts-files-and-attachments.md#example-flows) design-reference-image flow; **`created_by` stamped with the device the ingesting request came from** — NULL only for a daemon-produced artifact, because a producer that leaves the stamp NULL silently converts every request-originated upload into an unattributable artifact) followed by its `artifact_payload_refs` row (manifest first, to satisfy the `manifest_id NOT NULL REFERENCES artifact_manifests(id)` FK — [`artifact_payload_refs`](../architecture/schemas/local-sqlite-schema.md#artifact-tables-plan-011)), and return the minted `ArtifactId` (the manifest row's `id`). **This task CREATEs the corpus's one artifact-id minter, `runtime-daemon/src/artifacts/artifact-id.ts`, exporting `mintArtifactId(): ArtifactId`** — which **CONSUMEs `mintUuidV7` from `packages/runtime-daemon/src/ids/uuid-v7.ts`** (the daemon-wide RFC 9562 generator, Plan-001-owned per the `packages/runtime-daemon/src/ids/` ownership row) and **brands** its output as `ArtifactId`. It generates no bits of its own: the **UUIDv7** per [RFC 9562 §5.7](https://www.rfc-editor.org/rfc/rfc9562#section-5.7) that [Spec-012 §Required Behavior](../specs/012-artifacts-files-and-attachments.md#required-behavior)'s manifest bullet requires of every daemon-minted manifest id comes from that one generator, and this module is the call plus the brand. **A helper is necessary rather than a convention, and the reason is measured, not assumed:** the established daemon id idiom is `crypto.randomUUID()` (so named in `packages/runtime-daemon/src/workspace/workspace-event-emitter.ts` — evidence only that the daemon calls it, not of what it mints), and that emits **v4** on Node's own reference, [`crypto.randomUUID()`](https://nodejs.org/api/crypto.html#cryptorandomuuidoptions): "Generates a random RFC 4122 version 4 UUID" — the layout [RFC 9562 §5.4](https://www.rfc-editor.org/rfc/rfc9562#section-5.4) carries forward unchanged — so a producer reaching for the house idiom would mint a well-formed id that **passes `ArtifactIdSchema`** (which accepts any RFC 9562 form by design) while violating the spec's minting rule, silently and with no test that could catch it. **Consuming rather than re-implementing is that same rule one level up:** a private §5.7 implementation here would be a second daemon-side generator wearing an artifact-shaped name, and the `packages/runtime-daemon/src/ids/` ownership row makes `uuid-v7.ts` the daemon's only one. **Its unit test asserts what a consumer owns, and re-proves nothing the generator already proves.** Over a batch of minted ids it asserts the **version nibble reads `7`** (the most significant 4 bits of octet 6, [RFC 9562 §4.2](https://www.rfc-editor.org/rfc/rfc9562#section-4.2)), the **variant bits read `10`** ([§4.1](https://www.rfc-editor.org/rfc/rfc9562#section-4.1)), the value **parses under `ArtifactIdSchema`** and is typed as the **branded** `ArtifactId` rather than a bare string, and **no two minted ids are equal** — plus one **ordering smoke assertion** over that batch (the ids are non-decreasing), which holds whether or not the batch happens to share a millisecond and so is deterministic on any host. It deliberately stops there. The **same-tick counter ordering, the clock-rollback floor, and the 12-bit overflow rollover are consumed properties of `mintUuidV7`, proved deterministically in that generator's own suite** (`packages/runtime-daemon/src/ids/__tests__/uuid-v7.test.ts`), which is where an injected time source belongs: `UuidV7Minter` takes `readCurrentTimestampMilliseconds` and `fillWithRandomBytes` as injectable dependencies, and under a frozen clock that suite asserts ids strictly increasing with the [RFC 9562 §6.2](https://www.rfc-editor.org/rfc/rfc9562#section-6.2) Method 1 `rand_a` counter incrementing by exactly one per mint, a clock stepped backwards still yielding a strictly greater id stamped with the retained tick, and — under a saturated random fill that pins the seed — the counter exhausting at `0xfff` inside one tick before the next mint advances the emitted timestamp by a millisecond and reseeds. Restating any of those here would need a clock this task does not own and would prove the generator twice; a batch assertion that demanded equal decoded timestamps without one would be timing-dependent, and one that only checked non-decreasing output would exercise no counter branch — which is exactly why the property is asserted where the injection lives. A negative control pins that this task's own test can fail: `crypto.randomUUID()`'s output — the idiom this helper exists to displace — is refused by the same version assertion. ## Rollback Or Fallback

- A picture is stored and sent as its original bytes; one the provider will not take is refused in that provider's own words. A PDF the worker cannot open keeps its name-only quick look.

## Risks And Blockers

- Artifact immutability will be undermined if live workspace paths are allowed to masquerade as durable payload identity
- Pressure for user-specific redaction can create accidental in-place mutation unless every changed form is written as a new artifact

## Design Decisions

- **D-011-1 — The OCI manifest envelope is realized as dedicated `artifact_manifests` columns + a named `ArtifactManifest` wire shape.** [Spec-012 §Interfaces And Contracts](../specs/012-artifacts-files-and-attachments.md#interfaces-and-contracts) specifies an OCI-inspired envelope (`size`, `digest`=content_hash, and the freeform `metadata` that carries the file name). This plan authors the `artifact_manifests.size_bytes` column (local-sqlite-schema.md) and the matching `ArtifactManifest` wire shape (api-payload-contracts.md).
- **D-011-2 — `ArtifactPublish`/`ArtifactRead` compose a single named `ArtifactManifest`; publish embeds the manifest metadata (no `manifestUrl` pointer).** [Spec-012 §Interfaces And Contracts](../specs/012-artifacts-files-and-attachments.md#interfaces-and-contracts) mandates that publish return "artifact id **and** manifest metadata"; a `manifestUrl` pointer would drift from that clause ([Spec-012 §Interfaces And Contracts](../specs/012-artifacts-files-and-attachments.md#interfaces-and-contracts) grants handle/inline latitude to the _payload_ on `ArtifactRead` only, never to the manifest). The wire embeds `manifest: ArtifactManifest` on publish and `manifest` + `payloadHandle?`/`payload?` on read.
- **D-011-3 — The `artifactType` discriminator is the union `file | diff | summary | log | design | workflow_output`.** [Spec-012 §Required Behavior](../specs/012-artifacts-files-and-attachments.md#required-behavior) lists the artifact families (`summary` covers the plan/summary family), and `workflow_output` is the [Spec-015 §Output Mode Specification](../specs/015-workflow-authoring-and-execution.md#output-mode-specification) workflow phase-output type. The typed union is the contract (api-payload-contracts.md `ArtifactType`); the schema CHECK mirrors it (`CHECK(artifact_type IN ('file','diff','summary','log','design','workflow_output'))`).
- **D-011-4 — The ingest worker uses `sharp` and `@hyzyla/pdfium`.** `sharp` 0.35.5 (Apache-2.0, prebuilt libvips 8.18.7) writes the first page's PNG and the covered copy, can restrict libvips to named loaders and ships prebuilt binaries. `@hyzyla/pdfium` 2.1.13 (MIT, PDFium in WebAssembly, no native build) draws a PDF's first page; `mupdf` was rejected as AGPL, and `pdfjs-dist` (Apache-2.0, 34.8 MB) because it is built to render in a browsing context, which is what this rule keeps PDFs out of.

## References

Source for the SQLite collation premise T14.5's case-preserving resolver rests on:

- [SQLite — Datatypes In SQLite, §7 Collating Sequences](https://www.sqlite.org/datatype3.html#collation) — the built-in `BINARY` collating function "compares string data using memcmp(), regardless of text encoding", and §7.1 states that when two `TEXT` values are compared and neither operand carries a `COLLATE` clause or a column-level collation, "the BINARY collating function is used for comparison". `artifact_manifests.id` is declared `TEXT PRIMARY KEY` with no `COLLATE`, so its primary-key index and every equality lookup against it compare bytes: `ABC…` and `abc…` are two different keys, which is why the resolver canonicalizes the caller's spelling before the lookup rather than trusting the database to fold case.
