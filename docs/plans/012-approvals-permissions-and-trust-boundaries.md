## Goal

Implement the canonical approval, remembered-grant, and permission-check model that keeps shared collaboration membership separate from local execution trust.

## Scope

This plan covers approval records, remembered grants, daemon-side permission checks, trust invalidation, and approval visibility projections.

## Non-Goals

- Identity-provider implementation details
- Notification routing for approval prompts
- Provider-specific permission UX beyond normalized capability requests
- Cross-node dispatch approval envelopes (Spec-024 — Plan-027 at Tier 9; this plan provides the category enum only)

## Data And Storage Changes

- Add durable local `approval_requests`, `approval_resolutions`, and `remembered_approval_rules` storage plus invalidation hooks tied to runtime-node trust and membership changes. See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) §Approval Tables for column definitions — the audited DDL there is the verbatim migration content (D-012-2).
- Serve pending and historical approval state from a daemon-local projection (SQL over the approval tables — D-012-6). Cross-participant visibility in V1 rides roster-gated relay distribution of `approval_flow` events into each peer daemon's own local projection (ADR-017 Option B); no control-plane approval storage exists.
- Trust-evaluation inputs are derived at check time, never duplicated into a fourth store (D-012-15): node trust ← `node_trust_state.trust_level`; own-node determination ← the daemon's attach-binding owner-participant identity (Plan-003); envelope roots ← Plan-009 `workspaces.fs_root` / Plan-010 `worktrees.fs_root` via `run_execution_contexts` (CP-012-9); unestablishable provenance → strict per-request approval (Spec-012 line 78).

## API And Transport Changes

- Five `approval.*` JSON-RPC methods (D-012-5): `approval.requestCreate`, `approval.resolve`, `approval.projectionRead`, `approval.ruleList`, `approval.ruleRevoke` — wire contract in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) §Plan-012 + §Approval Method-Name Registry (Tier 6). `PermissionCheck` is deliberately NOT a wire method: it is the daemon-internal pre-execution gate (Spec-012 line 84; D-012-18) — its typed shapes ship in `approval.ts` as the in-process API.
- Error vocabulary in [Error Contracts](../architecture/contracts/error-contracts.md) §Approval — 7 codes (D-012-4).
- Driver-native permission requests normalize into canonical approval categories, scopes, and resource descriptors before any record is written; Plan-012 owns the normalizer that lands with driver integration (CP-012-6), and until then the schema-validated `approval.requestCreate` boundary is the enforced normalization gate.

## Ratified Design Decisions (Tier-6 audit, 2026-06-10)

- **D-012-1 — Contracts file is `packages/contracts/src/approval.ts`** (single file, singular noun; replaces the pre-audit `approvals/` directory form): one-file-per-domain per the shipped `session.ts`/`event.ts`/`repo.ts`/`worktree.ts` convention; avoids firing the BL-097 §7(d) deferred subdirectory-convention call.
- **D-012-2 — Persistence model (3 tables; DDL verbatim in local-sqlite-schema.md §Approval Tables).** `approval_requests` carries `session_id` + `requested_by` NOT NULL (provenance; no FK targets — sessions are control-plane rows, runs are event-sourced), required `resource_descriptor` (JSON), nullable `expiry_at`, 5-state CHECK incl. `canceled`, and `updated_at` (expiry/cancel settle on the row — no resolution row). `approval_resolutions` carries `request_id` as PRIMARY KEY (the durable wire id `approvalRequestId` — enforces the 1:1 decision row, replaces the former minted `id` + unique per-request index, and keeps every projection column wire-derivable per I-012-9), `approver_id` NOT NULL, 2-value `decision` CHECK, `effective_scope` NOT NULL, and nullable `remembered_scope_kind`/`remembered_scope_pattern`. `remembered_approval_rules` carries grantor `participant_id`, `session_id`, `node_id`, origin FK `created_from_request_id` (→ `approval_resolutions(request_id)`, the durable id carried on `approval.remembered`), `run_id` with CHECK `(scope_kind = 'run') = (run_id IS NOT NULL)`, explicit `scope_kind` enum, nullable `scope_pattern`, and the `revoked_at` ⇔ `invalidation_trigger` co-presence CHECK over the closed trigger set `{explicit, membership_change, node_trust_change, session_end}`.
- **D-012-3 — Consolidated wire block.** Six request/response pairs + `RememberedRuleId` brand + `RememberedScope` + `InvalidationTrigger` + `ApprovalFlowEventPayload` ratified in api-payload-contracts.md §Plan-012: create carries required `resourceDescriptor`; resolve carries optional `approver` + `effectiveScope?` + `rememberedScope?` and returns the recorded `approverId` + `effectiveScope`; the projection row carries `requestedBy`, `resourceDescriptor`, `updatedAt`, and the resolved quad (`resolvedAt`/`decision`/`approverId`/`effectiveScope`) present iff state ∈ {approved, rejected}; rule rows carry grantor, node, optional `runId`, and revocation metadata; the `ApprovalFlowEventPayload` carries the projection-rebuild fields (`requestedBy`/`resourceDescriptor`/`expiryAt` on `requested`, `approver`/`effectiveScope` on the resolution events, and the rule projection on `remembered` — grantor = `approver`, bound `nodeId`, binding = `rememberedScope`/`runId`, origin = `approvalRequestId`) so relayed or replayed events alone rebuild each daemon's projection rows, `remembered_approval_rules` included (D-012-6/D-012-7, I-012-9).
- **D-012-4 — Error vocabulary (§Approval, 7 rows).** `approval.not_found` 404, `approval.already_resolved` 409, `approval.request_expired` 410 (renamed from the pre-audit `approval.expired` — error codes never collide byte-for-byte with Spec-006 event names), `approval.request_canceled` 409 (new; non-colliding with the `approval.canceled` event), `approval.persistence_unavailable` 503 (fail-closed), `approval.rule_not_found` 404, `approval.rule_already_revoked` 409. Deliberate absence: no `approval.permission_denied` in V1 — the local IPC surface carries no caller principal, `PermissionCheck` denial is a normal `{allowed: false}` response, and minting a cross-participant authorization code is Plan-027's call.
- **D-012-5 — Method registry: five strings on the new singular `approval` root** (`approval.requestCreate`, `approval.resolve`, `approval.projectionRead`, `approval.ruleList`, `approval.ruleRevoke`), ratified in api-payload-contracts.md §Approval Method-Name Registry with the root added to the Tier-1 namespace-root enumeration. `PermissionCheck` registers NO wire method string: zero V1 wire consumers, and a wire preflight would invite stale-verdict (TOCTOU) authorization against the security gate. "Rule" (not "grant") is the operation vocabulary — matching `remembered_approval_rules`, `approval.rule_revoked`, and `RememberedRuleId`. Supersedes the pre-audit Spec-023 plural `approvals.listPending` gloss.
- **D-012-6 — Projection is daemon-only.** The pre-audit control-plane `approval-projection-service.ts` Target Area is struck: shared Postgres stores zero approval tables (ADR-017 anchors-only; shared-postgres-schema invariants), so a control-plane projection would violate the ratified storage posture, not extend it. `approval-projection-service.ts` lands in Plan-012-owned `packages/runtime-daemon/src/approvals/`; cross-participant visibility rides roster-gated relay distribution of `approval_flow` events into each peer daemon's own projection (ADR-017 Option B). V1.1 revisit rides the MLS promotion gates.
- **D-012-7 — Events-canonical; rows are projections.** `EventLogService.append` commit IS the Spec-012 line 76 durability gate; row projection updates after; startup reconcile replays `approval_flow` events newer than the rows' high-water mark; a failed append surfaces `approval.persistence_unavailable` and the gated action does not proceed.
- **D-012-8 — `approval.canceled` is an additive durable event (7 `approval_flow` variants).** Emitted when `cancelPendingForRun` settles pending requests on run-terminal; Spec-006 §Approval Flow gains the row (line 236) and the registry moves 125 → 126. Expiry/cancel settle on the request row (`state` + `updated_at`) — never a resolution row. Explicit-over-derived: a projector-derived cancellation would leave the `approval_flow` audit timeline incomplete.
- **D-012-9 — V1 policy engine is `@cedar-policy/cedar-wasm` in-process (`isAuthorized`) over the build-embedded, signature-verified compiled policy set.** The verified artifact (as enforced in-process) is the canonical bytes of the compiled Cedar policy set + an Ed25519 detached signature under the operator release key, verified against the pinned `OPERATOR_PUBLIC_KEY` on every daemon start BEFORE any `PermissionCheck`; verification failure → refuse to start (typed log `policy-artifact-signature-invalid`). Container-image signing remains the distribution pipeline's supply-chain layer (the V1 daemon is shell-spawned, not containerized). YAML sources live at `packages/runtime-daemon/policies/default-policy.yaml`; `scripts/compile-policies.mjs` compiles them in the package build; content transcribes security-architecture §Permission Matrix + Spec-012 §Default Behavior. Package name corrected from the pre-audit `@cedarpolicy/cedar-wasm` (nonexistent on npm — dependency-confusion hazard); version pin 4.11.x (current stable at amendment date). **V1.1** (criterion-gated, ADR-012): (a) `policy-bundle-v{N}.cedar.tar.gz` build/sign/verify CLI surface (`sidekicks policy bundle build/sign/verify`), (b) daemon-side verifier with monotonic version counter and rollback rejection, (c) `ApprovalPolicyEngineUnavailable` recovery-status plumbing, (d) freshness-window timestamp enforcement — the V1→V1.1 delta is policy SOURCE only (embedded → runtime signed bundle); the evaluator does not change. Operational procedures: [Cedar Policy Signing And Rotation](../operations/cedar-policy-signing-and-rotation.md).
- **D-012-10 — Remembered-scope matching semantics.** `RememberedScope { kind: 'run' | 'session'; pattern?: string }`; `request_only` is expressed by OMITTING `rememberedScope`, never an enum member. Candidate set: unrevoked ∧ same `session_id` ∧ same `node_id` ∧ same `category` ∧ (kind = `session` ∨ (kind = `run` ∧ rule.run_id = request.runId)). Pattern absent → category-wide within that boundary; pattern present → category-derived semantics: path categories (`file_write`, `destructive_git`) = normalized-absolute-path prefix containment against the envelope roots; `network_access` = exact host equality (no wildcards in V1); all other categories = exact scope-token equality. The rule's `participant_id` is the GRANTOR — an audit + membership-invalidation key, never a match key (the spec's scope axes are run/session, never actor).
- **D-012-11 — Invalidation: on-next-use re-evaluation is the correctness mechanism.** The grant-match path re-validates every rule's preconditions at use time; push seams — a synchronous `node_trust_state` transition hook and a `membership.*` event-application hook (the daemon's local projection of relay-delivered membership events) — call `revokeDependentRules` to shrink the live window and emit timely `approval.rule_revoked` events, but they are the audit/timeliness layer: relay delivery is asynchronous, so only use-time re-validation satisfies revoke-before-next-use (Spec-012 line 77). Unresolvable membership input → fail closed (Spec-012 line 78).
- **D-012-12 — Approver identity model.** Wire `approver?: ParticipantId` is OPTIONAL and informational: absent on the local socket → the daemon records its node-owner participant binding (the same attach-binding read as D-012-15's own-node determination); present → cross-checked (local: vs the owner binding; PASETO-authenticated surfaces: vs the verified `sub`) — mismatch → `auth.principal_mismatch`. `approval_resolutions.approver_id` stays NOT NULL (the RECORD is mandatory per Spec-012 line 59); `ApprovalResolveResponse.approverId` returns the recorded server truth (AC-3 observable). The renderer never populates an approver identity.
- **D-012-13 — Run-blocking seam shape.** Provider-registration directionality mirrors shipped CP-004-8 (`RunSetupGate`): Plan-012 exposes `registerApprovalOutcomeListener` + `cancelPendingForRun`; Plan-004's engine registers and drives run-state transitions — Plan-012 never mutates run state. `onBlocking` fires after the durable commit of the pending request; `onResolved` fires per resolution path (approved / rejected / expired) exactly once; rejected/expired continue the run with the action refused.
- **D-012-14 — Expiry is hybrid.** Lazy settle on every read/match touching a pending request (zero staleness at decision time) + a 60-second daemon sweep (timely `approval.expired` emission + parked-run unblock via the D-012-13 seam with outcome `expired`); expiry/cancel events carry `actor: null` (system actor, node-emitter convention).
- **D-012-15 — Trust-evaluation inputs are derived, never duplicated.** No fourth store: node trust ← `node_trust_state.trust_level` with the V1 value set ratified as `'untrusted' | 'envelope_trusted'` and fail-closed READ-boundary enforcement (any out-of-set value evaluates as `untrusted`; the Plan-012-owned elevation write parses at the boundary; no retroactive DDL CHECK on Plan-003's shipped migration); own-node determination ← the daemon's attach-binding owner-participant identity; envelope roots ← `run_execution_contexts` joined to `workspaces.fs_root` / `worktrees.fs_root` (CP-012-9); unknown provenance → strict per-request (Spec-012 line 78).
- **D-012-16 — Renderer approval posture: allow-only remembered rules, ungrouped V1 rendering.** `rememberedScope` is schema-refined valid only with `decision: "approved"` (`{rejected, rememberedScope}` → typed rejection; the remember control binds to Approve only; deny-by-default remains Cedar's job). V1 renders one card per canonical record with per-record actions — grouping is a permitted Tier-8+ presentation addition that must preserve per-record identity/actions (deliberate non-exercise of Spec-012 line 103's allowance; group-approve would fan one click into N mutations against AC-1's explicit-approval semantics).
- **D-012-17 — `PermissionCheckResponse.reason` is a 5-value enum** (`policy_allow | remembered_rule | approved | pending_approval | denied`): `policy_allow` = Cedar/own-node-envelope permit with no human approval artifact; `remembered_rule` = matched an unrevoked rule that passed at-use re-validation; `approved` = a recorded approved resolution covers the exact request; `pending_approval` = request created/open (`allowed: false`, `approvalRequestId` present); `denied` = Cedar forbid, rejected/expired resolution, or fail-closed refusal (the typed 503 additionally surfaces on fail-closed paths so audit distinguishes them). Invariants: `allowed === (reason ∈ {policy_allow, remembered_rule, approved})`; the `policy_allow`/`approved` split preserves the audit distinction between machine permit and human grant.
- **D-012-18 — No wire preflight; the in-process `PermissionCheckService.check()` is the composed gate.** Evaluate → on an ask-policy outcome create the request + emit `approval.requested` + notify the run-blocking seam → return `pending_approval` with the new id. The composition is Spec-012 line 84's enforcement seam; splitting evaluate-from-create at a wire boundary would reintroduce the TOCTOU window.
