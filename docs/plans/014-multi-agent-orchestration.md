## Goal

Implement the V1 agent identity surface, parent-child run linkage, and provider-agnostic orchestration semantics in the session itself — budgets with the per-agent turn limit and stop conditions as a hard V1 quality gate — for concurrent multi-agent work.

## Scope

This plan covers the agent identity and configuration surface, orchestration run creation with full admission enforcement (budget, turn limit), durable run-link projection, internal-helper visibility, budget accounting with warning/interrupt thresholds, idle and turn-limit stop conditions, desktop surfaces for concurrent agent work, per-request pricing from the providers' own figures and a live price table (voice minutes included), the per-turn step bound, and sessions talking to each other.

## Non-Goals

- Workflow authoring syntax (Plan-015)
- Provider-native subagent APIs beyond normalized adapters (ADR-005)
- Timeline summary-row rendering (Plan-011 — D-014-14; this plan publishes the durable inputs only)

## Preconditions

Target paths below assume the implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

## Data And Storage Changes

- `run_links` (single-parent `child_run_id` PRIMARY KEY, `session_id` provenance, `reached_by` CHECK (`provider_subagent` | `bridge_run` | `workflow_step`), `internal_helper`), `agents` (no state column: the provider-binding columns and the one pending-switch column), `session_budgets` (row-canonical limits), and `agent_tree_nodes` (the daemon's own agent tree index: one row per agent keyed by its run, its provider and the provider's own id for it (the task id or thread id, which is also what a restart resumes it by), holding the provider's own parent reference and the state, `running` or `completed`) per [Local SQLite Schema §Orchestration Tables (Plan-014)](../architecture/schemas/local-sqlite-schema.md#orchestration-tables-plan-014).
- `session_exchanges` (the pair of sessions trading messages and the count since the person last wrote) and `session_paused_message_queue` (every message addressed to a paused session, in arrival order, each row naming the sender's own send event rather than holding its words) per the same schema section, added to the daemon's one schema by T2.18 — the two pieces of daemon state [Spec-014 §State And Data Implications](../specs/014-multi-agent-orchestration.md#state-and-data-implications) declares durable. The session directory beside them is **not** a table: it is rebuilt from the sessions the daemon hosts when it starts.
- `run_links` and `agents` are events-canonical projections (ADR-017 Option B) rebuilt byte-equal on replay; `session_budgets` is row-canonical daemon configuration (the `queue_items` posture — mutated by wire method, never evented), and so are the session-messaging tables, the `agents.pending_switch` column (written before a switch is acknowledged, since no event records a switch being asked for), and `agent_tree_nodes` (written by the daemon alone when an agent starts and when it finishes) — a message persists nothing of its own, so neither is rebuilt from the log.
- Budget **accounting** has no accumulator table: the `BudgetAccountant` is an in-memory projection over `usage_telemetry` + `run.*` events, rebuilt on replay (D-014-5); per-run effective ceilings rebuild from the durable `run.queued` `effectiveRunConfig?` field, not by re-merging session defaults that may have changed mid-run. The per-turn usage rows [Plan-026](./026-provider-accounts-and-credential-homes.md) projects per provider account are a **projection over the same `usage_telemetry` events**, rebuilt on replay like every other one and served through this plan's one committed-spend accessor, so the account surface's by-day and by-model figures are an axis over the accountant's own facts rather than a second accountant beside it. Every request is priced once when it completes and its figure is stored in integer micro-dollars; a request on a model the price table does not price yet is stored with its exact tokens as held and joins the fold when a fetch prices it (T2.19).
- No timeline-projection rows: this plan publishes durable events only; Plan-011 derives summary rows (D-014-14).

## API And Transport Changes

- Daemon JSON-RPC pairs per [api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md#plan-014--multi-agent-orchestration): `orchestration.runCreate` / `orchestration.childRunLinkRead` / `orchestration.budgetRead` / `orchestration.budgetUpdate` / `orchestration.costReceiptRead`, `agent.configUpdate` / `agent.list` (a live list: the list, then each change), `session.goalUpdate` / `session.goalClear`, `session.maxStepsUpdate`, and `session.terminalCodexList`. Registration relies on the registry accepting camelCase method tails, and typed wire errors on the `DaemonDomainError` projection (CP-014-12).
- Owned event types in the [Spec-005 registry](../specs/005-session-event-taxonomy-and-audit-log.md): `orchestration.rejected`, `usage.budget_warning` (T1.1), the goal events `session.goal_updated` / `session.goal_cleared` (T1.2), and the provider-binding events `agent.provider_binding_changed` / `agent.provider_binding_change_failed` (T1.13).
- The `run.queued` payload gains optional additive linkage fields `{agentId?, parentRunId?, reachedBy?, internalHelper?}` plus the admission-resolved `effectiveRunConfig?` threaded from the in-process `OrchestrationRunLinkCarrier` (D-014-3, CP-003-10; ADR-018 additive-only).
- Error vocabulary per [error-contracts.md](../architecture/contracts/error-contracts.md) §Orchestration / §Agent (D-014-16), plus `driver.capability_unsupported` for a switch axis the target driver does not have, and for the goal RPCs `session.not_found` for a session id the daemon does not hold, appending nothing, and `driver.capability_unsupported` where the agent's provider cannot carry a goal.
- **Contract mirror — the agent's provider binding (D-014-26).** `AgentProviderBinding {driverName, modelId, providerAccountId, effort, outputSpeed?}` — `providerAccountId` null where the agent follows its provider's current account — is the one shape the agent row, `agent.list` and the binding events share. The axes a run starts with gain `providerAccountId?` + `effort?`. `AgentConfigUpdateRequest` is `{agentId, modelId?, effort?, outputSpeed?, driverName?, interruptAndSwitch?}`, every member additive-optional per [ADR-018](../decisions/018-cross-version-compatibility.md) and an omitted member **unchanged, never reset**; it carries no account member, because which account a provider's work runs on is the provider surface's own control (`providerAccount.setCurrent`, [Spec-026 §Moving a session to another account](../specs/026-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)), and an account move settles through the same binding events. `AgentConfigUpdateResponse` gains `switch?: AgentBindingSwitchDisposition` — a **discriminated union**, not a settlement, because mutation and application are two moments: `AgentBindingSwitchPending` (`switchId`, the resolved `appliesAt` boundary, the target binding, `interruptRequested`, and `replacedSwitchId?` on a supersession) is the ordinary arm, and the **settled** arms are reachable only on the `interruptAndSwitch` arm, which holds its request open: `{ status: 'applied' } & AgentBindingSwitchOutcome`, `{ status: 'degraded' } & AgentBindingSwitchOutcome` under a **total** mapping from continuity (`applied` iff the conversation arrived whole — `in_place` or `resumed`; `degraded` iff it did not — `brief` or `replayed`), and `AgentBindingSwitchFailed` carrying the same `reason` vocabulary as `agent.provider_binding_change_failed`. Each settlement has its own arm, because an arm that waits for its own settlement must be able to express every settlement its boundary can reach. A change of model, effort or speed alone settles `in_place` at the next turn, so a pending switch that waits for the end of a run is a `driverName` change. The durable `agents.pending_switch` column stores a **superset** of the wire record — adding the daemon-resolved `admittingPrincipalId` (the §Authenticated Principal class rule) and the `'requested'` \| `'dispatched'` interrupt-dispatch marker — neither of which is ever returned to a caller or appended to a payload. `AgentBindingSwitchOutcome` carries the `continuity` naming which mechanism carried the conversation (`in_place` \| `resumed` \| `brief` \| `replayed`) and the `DeclaredLossKind` union. `AgentListResponse.agents` is a live list — the list, then each change — and each row returns the effective binding, the definition it was resolved from, its provider, its place in the session's agent tree, the live-scoped `observedOutputSpeed?` (the provider's own declared speed state and its reason, projected from the live runtime binding and stored in no column, so a mode the provider's account gate refused is readable beside the one that was requested rather than hidden behind it; **absent until observed**, the declaring handshake being turn-bearing rather than carried on the spawn), and any `pendingSwitch?`, so a caller that did not issue the mutation still sees the binding and the switch waiting against it — all mirrored in [api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md). `effort` is a `string` rather than a corpus enum on purpose: the valid set is the target model's driver-reported `effortLevels`, so an enum here would be a second, staler source of a provider-owned vocabulary. The response member's **presence** is the switch discriminator, so a pure rename carries no switch member at all and a consumer cannot mistake one for the other; within it, `status` discriminates a promise from a settlement — and, among settlements, an honest degrade from an ordinary success — so no consumer reads a `continuity` that a deferred switch has not produced yet, nor re-derives `degraded` for itself. These refusals reach a caller before acceptance: `agent.provider_axis_invalid` (400) for a value outside the target driver's published vocabulary, and `driver.capability_unsupported` for an axis the target driver does not have; every application step is a compare-and-set on `switchId`. The events that settle a switch are `agent.provider_binding_changed` — the session, the agent, `switchId`, the actor, `from` and `to` each with its account, the account the run landed on, `continuity`, `declaredLosses` and `turnContinued` — and `agent.provider_binding_change_failed` — the session, the agent, `switchId`, the actor, `from`, `attempted` with its account, a `reason` (`driver_unavailable`, `model_unavailable`, `effort_unavailable`, `output_speed_unavailable`, `interrupt_refused`, `target_unstartable`, `account_unavailable`) and, with `account_unavailable`, `accountState` (`reauth_required`, `home_missing`, `indeterminate` or `not_registered`).
- **Contract mirror — cost display consistency (D-014-24).** `OrchestrationBudgetState` carries the session's committed spend and a per-agent axis — `committedSpendUsdMicros` and `agentSpend: [{agent, ownUsdMicros, subtreeUsdMicros}]` over every member of the session's tree — an agent by its `agentId`, or a provider's own helper by its run and the handle the index minted for it — each member's own spend and that plus the spend of every member under it, routed up the parent chain — in integer micro-dollars, mirrored in [api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md#plan-014--multi-agent-orchestration). They ride the existing `orchestration.budgetRead` / `orchestration.budgetUpdate` response shape — `OrchestrationBudgetUpdateResponse` **is** `OrchestrationBudgetState`, so the members are required on the update reply too, which is why the obligation binds the mutation binder (T3.1) as well as the query binder (T3.2): **no new wire method**, no new event type, no error code, and no table. `usage.budget_warning` is unchanged — its session-cost `observedValue` is committed spend by [Spec-014 §Cost Derivation And Absent-Cost Semantics](../specs/014-multi-agent-orchestration.md#cost-derivation-and-absent-cost-semantics); what this plan adds is the asserted equality between it and `committedSpendUsdMicros` at the same fold state (I-014-24), not a payload change.
- **Contract mirror — session cost receipt (D-014-25).** One read method, `orchestration.costReceiptRead {sessionId}`, and its `SessionCostReceipt` response shape mirrored in [api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md#plan-014--multi-agent-orchestration): the providers in the order the session first spent on them, the session's own provider first, each with its account rows `{provider, account, billingMode, tokens, usdMicros}` (`billingMode` is `subscription`, `metered` or `unknown`, and labels the figure without changing how it is derived), its `Voice` row where the session made voice calls, and its subtotal, then the session total, every amount in integer micro-dollars served from the one committed-spend accessor. It refuses a session id the daemon does not hold with `session.not_found` and appends nothing. Identities ride it as contract comments so T3.9's parity claim has something to match: each provider's rows sum to its subtotal, and the subtotals sum to the session total. **No new event type, no new error code, and no table** — the receipt is a decomposition of an existing fold, so `usage.budget_warning` and `session_budgets` are unchanged. The account each row names comes from the per-turn usage rows, keyed on the account each request ran on, and its name and billing mode as [Plan-026](./026-provider-accounts-and-credential-homes.md) supplies them (CP-026-3) — not a Plan-014-owned surface, and this plan reads it without widening it.

- **CP-014-21 — Declared output-speed state consumed from [Plan-004](./004-provider-driver-contract-and-capabilities.md)** (reciprocal of that plan's `CP-004-12`). The `agent.list` binder (T3.20) reads the provider's own declared speed state — and its provider-supplied reason — from the live runtime binding's **held observation**, and projects it as the live-scoped `observedOutputSpeed` beside the committed `outputSpeed` column. Plan-004 owns the reading, and **when** it happens matters: not on the spawn or the resume (both resolve before any turn-bearing exchange, and [Spec-004 §The output-speed axis](../specs/004-provider-driver-contract-and-capabilities.md#the-output-speed-axis)'s detection-source ruling establishes that the declaring handshake is emitted only as part of one) but on the **first turn-bearing exchange**, after which the driver holds it against the binding for that binding's life. This plan therefore **issues no provider round-trip** to serve a list read, holds no copy, and adds no column — an observation persisted anywhere would be a second and staler record of a fact the running session already holds, and would let a mode that stopped being available across a restart keep reading as accepted ([Spec-004 §The output-speed axis](../specs/004-provider-driver-contract-and-capabilities.md#the-output-speed-axis)). The member is absent in these cases, none of which is the mode being off: no binding is live, the bound driver does not declare `output_speed`, or the binding is live and declaring but **no turn-bearing exchange has carried the handshake yet**. The third is the one a read taken right after a switch applies will hit, so this binder never waits for the observation, never forces a turn to obtain it, and never substitutes the committed value for it. The projection is the declaration of the one binding the agent is running on, so the row pairs a request with the declaration it produced. **Tasks:** T3.20.

This plan authors **nothing** on Plan-004's side; Phase 2 states that T2.18 waits for that plan's T3.29 and T3.31 on both drivers. **Tasks:** T2.18, T2.20.

## Design Decisions

- **D-014-1 — Single contract file.** All Plan-014 wire contracts live in `packages/contracts/src/orchestration.ts` — no separate `src/orchestration/` contract directory. The in-process `OrchestrationRunLinkCarrier`, which never leaves the daemon, lives with the orchestration services in `packages/runtime-daemon/src/orchestration/`.
- **D-014-2 — Method strings.** New `orchestration` and `agent` roots, per the [api-payload-contracts.md §Plan-014 registry](../architecture/contracts/api-payload-contracts.md), registered under the registry's camelCase method-name format with typed errors on the `DaemonDomainError` projection (CP-014-12).
- **D-014-3 — Linkage carrier.** Run linkage rides optional additive `run.queued` payload fields (no new event type); `run_links` is a pure events-canonical projection; another device reading the session's log rebuilds linkage from the event alone; the admission-resolved `effectiveRunConfig` rides the same additive vehicle (the durable source for D-014-5 budget rebuild and I-014-14 idle replay).
- **D-014-4 — Typed configs.** `OrchestrationRunConfig {tokenLimit?, idleTimeoutMs?}` is a strict typed schema, never an open `Record<string, unknown>`; DDL comments cite the type.
- **D-014-5 — Budget substrate.** `BudgetAccountant` = in-memory replay-rebuilt projection (no accumulator table); durable limits = `session_budgets` row-canonical table; `orchestration.budgetRead` / `budgetUpdate` wire surface; per-run effective overrides persist on `run.queued` (`effectiveRunConfig`) — enforcement rebuilds from the event, never by re-merging session values (which may change mid-run).
- **D-014-7 — System interventions.** Budget and idle interrupts enter through Plan-003's in-process entrypoint below wire authz, with NULL-for-system actor and the standard `expectedRunVersion` reject-re-read-retry loop.
- **D-014-8 — Turn + idle definitions.** Turn = one completed assistant-output cycle per (session, agent); consecutive counter resets on interleave and is kept by the budget accountant (T2.5) against the session's `turn_limit_per_agent`; at-limit completes with `trigger: 'turn_limit'` (Plan-003's trigger set gains the value) + same-agent admission refusal. Activity = any appended event carrying the run's id; idle sweep is a daemon-owned per-run timer. `InterruptReason = budget_exhausted | idle_timeout`.
- **D-014-9 — One machine.** Every run in a session, a child run included, executes on the machine that runs the session. An orchestration request names no machine, and admission makes no machine check.
- **D-014-11 — Scheduler semantics.** No count limit of the runtime's own on pending orchestration runs, active children, or queued items; a provider's own limits apply under the person's own provider settings and its refusals surface in its own words. Admission refuses only on the budgets the person set and on the state of what a run targets (cost ceiling, turn limit): create-time enforcement, zero residue, durable `orchestration.rejected` record.
- **D-014-13 — Queue seam.** Orchestration admission pipeline (agent → budget → turn gate) then in-process Plan-003 queue admission with the typed carrier; `RunId` mints at queue insert (`state: 'queued'` in the create response); zero-residue refusals.
- **D-014-14 — Timeline seam.** Events-only producer: no timeline rows, no Plan-011 imports; Plan-011 derives summary rows from the durable events + carrier.
- **D-014-16 — Error vocabulary.** [error-contracts.md](../architecture/contracts/error-contracts.md) §Orchestration / §Agent; parent-not-found reuses `run.not_found`; no token collides with an event name.
- **D-014-17 — How a child was reached.** A child's link records `reachedBy`: `provider_subagent` (the provider's own subagent), `bridge_run` (a bridge `run` call) or `workflow_step` (a workflow's `agent.run` step), durable in the run linkage, beside the agent the child runs, which is the agent that was asked. A `provider_subagent` link is written by the provider driver: Claude Code's subagent start and stop notifications and Codex's collaborating-agent events each add or close the run-link row for that subagent, so a provider's own subagents appear in the agent tree like any other child. However it was reached, a child appears in exactly three places, all fed by one source: a row in its parent's transcript where the dispatch happened, a row in the session's agent list, and its own child view. `reachedBy` is internal data: no screen, label or tag shows it or any word for how a child was reached; the screen shows the agent tree, each child's provider and model, and `via <agent>` naming the agent that was asked where the child was a peer call.
- **D-014-18 — Desktop scope.** V1 desktop ships **no** `OrchestrationRunCreate` affordance (its callers are the cross-provider bridge's `run` verb and a workflow's `agent.run` step); it renders the session's agent tree with each agent's linkage, state mark from its runs, refusal records and spend (T4.3), and the inspector's `Cost` section (T4.6).
- **D-014-20 — An agent has no lifecycle state.** An agent is in its session or it is not ([agent-and-run-model.md §Lifecycle](../domain/agent-and-run-model.md#lifecycle)), with no lifecycle state of its own; the record that creates an agent's row and every `agent.*` event payload carry the daemon-resolved values the row holds, so the projection replays deterministically.
- **D-014-24 — Displayed cost and enforced cost are one fold** (per [Spec-014 §Design Decisions](../specs/014-multi-agent-orchestration.md#design-decisions)). Every surfaced cost figure is supplied by the committed-spend fold the accountant enforces against ([Spec-014 §Cost Figure Display Consistency](../specs/014-multi-agent-orchestration.md#cost-figure-display-consistency)), and the budget state — served identically on the `orchestration.budgetRead` and `orchestration.budgetUpdate` replies, which are one `OrchestrationBudgetState` — carries the committed spend and each agent's spend with the agents under it from that one fold, with no second arithmetic. Each figure is the sum of priced requests, so it carries no mark: no provenance member, no estimate and no bound. An overview that shows root runs at their own cost alone, while delegated spend lands on their children, renders a large multi-run campaign at a small fraction of its true cost; routing every agent's spend up the parent chain at whatever depth it sits (D-014-17 linkage) and rolling in-session subagent usage into its run already bound the arithmetic, leaving the display rule as the residue. Three alternatives rejected: a display-side sum over the visible run list (that failure mode itself), a second presentation-side fold (two accountants over one event set diverge invisibly, since both look authoritative), and a mark on the figure — an estimate, a bound, `unpriced` — which would claim a doubt the accountant does not have. Mints no budget, no table, no event type, no wire method, and no error code ([api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md#plan-014--multi-agent-orchestration)).
- **D-014-25 — The session cost receipt is by provider, then by account.** The receipt decomposes committed spend by provider and then by account, with a `Voice` row per provider where the session made voice calls, a `Subtotal` where a provider holds two or more rows, and the `Total`; it carries no per-run, per-turn or per-agent line ([Spec-014 §Session Cost Receipt](../specs/014-multi-agent-orchestration.md#session-cost-receipt)). The question a receipt answers is who billed what, and a turn split by an account move lands as two account rows under one provider, which a per-run axis cannot show without splitting a run. Rejected: a per-run axis beside the account axis (a second partition of the same fold that no surface draws, the per-agent spend already standing in the agent list) and a per-turn list (the transcript's own rows carry what a turn did).
- **D-014-26 — The agent's provider binding, and the switch that moves it.** The binding is `AgentProviderBinding {driverName, modelId, providerAccountId, effort, outputSpeed?}`; the request that moves it keeps the word switch (`switchId`, `pendingSwitch`) and its types are `AgentBindingSwitch*`. "Runtime binding" names only the live connection from a run to its provider process, and "execution binding" only a run's workspace and mode, so neither names this axis. Only `driverName` needs a new process: model, effort and speed settle in place through each provider's own means, and the account moves on the provider surface. The pending switch is the row's one column of daemon state, written before the acknowledgment and returned on `agent.list`, because no event records a switch being asked for; the settling events carry everything the transcript and replay need. Rejected: an event appended at mutation (it reads as the binding having moved while nothing has), a per-session account switch beside the provider surface's (a session could then sit on an account the provider surface says it is not on), and treating model or effort as needing a new process (a respawn and a replay for a change neither provider needs them for).
- **D-014-27 — The price table is LiteLLM's public price list, fetched live.** The daemon prices every request the providers do not price themselves from LiteLLM's model price list (MIT), fetched as data — no library is added — at start, hourly and on first sight of a model or speed, with a copy in each release for a first start that cannot fetch. It covers every priced model both providers list, with the long-context, Fast, cache-write and one-hour cache-write rates this pricing needs. Considered: models.dev (missing rows and the one-hour cache-write field, and slower on price changes), OpenRouter's model list (its own resale prices, and terms that forbid the use), and a signed price file of our own on the release channel (a pipeline to run forever and a lag behind the list). Coverage and the license decided it. The telemetry receiver that reads the requests a provider leaves out of its stream is Node's `http` with a Zod schema for the handful of attributes it reads; an OpenTelemetry collector library was not taken, because the daemon reads only that handful of attributes.
- **D-014-28 — A Codex voice hold is stretched by `signalsmith-stretch`.** A hold on a Codex voice call is played into the call at 1.5× with the pitch kept and each pause cut to 0.2 s by `signalsmith-stretch` (MIT, its notice carried by the product) in its own AudioWorklet node, fed a second at a time, with a `pnpm patch` to its read loop so it can read a request handed over in pieces; the patch goes once an upstream release carries the fix. Considered: an audio buffer source's playback rate (it shifts the pitch) and a media element (1.1 s late in WebKit, its first 80 ms lost). Its budget is an acceptance criterion: the first sound reaches the call within 50 ms of the release, it adds at most 1.5% of one core while it plays, and it holds at most 6.4 MB, under 0.6 MB of it in the stretch. The capture and the call legs are [Spec-021](../specs/021-desktop-app-and-renderer.md)'s and [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md)'s; this plan owns the voice cost row (T2.5, T4.6).

- **T3.20 — `agent.configUpdate` provider axis on the wire + SDK** (D-014-26)
  - **Files:** `packages/runtime-daemon/src/ipc/handlers/` (EXTEND T3.1 — the agent mutation binders, where T3.1 authors them); `packages/client-sdk/src/orchestrationClient.ts` (EXTEND)

Authorization is likewise unmoved: the mutation authorizes exactly as `agent.configUpdate` already does and the interrupt leg as `Action::"intervene"` already does, so no Cedar action is added and a grant of "may reconfigure an agent" does not silently acquire "may interrupt anyone's run". **The declared-state read-back.** This binder additionally composes `observedOutputSpeed` onto each returned row, and it is the one member on this response that is **not** read from the `agents` row: it is the provider's own declared speed state, taken from the live runtime binding's **held observation** through CP-014-21 and written to no column, so it cannot go stale. It is a read of **held driver-session state and issues no provider round-trip** — building a list read must never start, resume, or interrogate a provider process. It is **live-scoped**, and **when** the observation exists matters: the declaring handshake is turn-bearing, so the spawn and the resume that establish a binding cannot report it, and the driver records it on the **first turn-bearing exchange** instead. The member therefore has these absent causes — no live binding, a binding whose driver does not declare `output_speed`, and a live declaring binding **not yet observed** — and this binder never waits for the third, forces a turn to resolve it, or substitutes the committed value for it. Presence stays the discriminator for "this was read from the provider"; absence means nothing has been read yet or ever, never that the mode is off. The projection is the declaration of the one binding the agent is running on, whose spawn realized the `outputSpeed` served beside it. Without it a caller reads back only what was requested, and a provider that accepts the opt-in and leaves the mode off is indistinguishable from one that honored it — the false success [Spec-004 §The output-speed axis](../specs/004-provider-driver-contract-and-capabilities.md#the-output-speed-axis) prohibits, reproduced on the read side. The disagreement is deliberately **not** reclassified as a switch failure: the switch applied and the provider then declared something else, so `agent.provider_binding_change_failed` is not emitted for it and `output_speed_unavailable` keeps its narrower meaning.
  - **Consumes:** T1.13 contracts; T2.16 coordinator; the live runtime binding's held session-handle state for the declared-speed read-back (CP-014-21).
  - **Spec coverage:** Spec-014 §Same-Agent Provider Switch (the mutation surface and its authorization); Spec-014 §Interfaces And Contracts (the agent surface).
  - **Verifies invariant:** I-014-25.
  - **Tests:** the SDK marshals the settlement verbatim and derives nothing from it (I-014-16); a response to a pure rename carries no `switch` member, so presence is a usable discriminator, and a deferred switch's `switch.status` is `pending` with no `continuity` member to misread; an `agent.list` read taken by a user other than the mutator shows the pending switch and the effective — never the pending — provider axis; `agent.provider_axis_invalid` reaches the caller with its `axis` and `value` fields intact; a row whose live binding reports a declared state differing from the committed `outputSpeed` returns **both** values with the provider's reason, and the same read taken after that binding is disposed returns the committed value with `observedOutputSpeed` **absent** rather than stale — the pair that proves the member is live-scoped and column-free; and the read issues **zero** driver calls in both cases, asserted on call counts, so a list read can never start or interrogate a provider process. Absence has three causes, and a test asserting one of them proves nothing about the others: a read taken against a **live, declaring, not-yet-observed** binding returns the committed `outputSpeed` with `observedOutputSpeed` **absent** — and still issues zero driver calls, so the binder is shown not to force the handshake it is waiting on — while the same binding read again **after** its first turn-bearing exchange returns the observation; and after a provider switch lands at the end of a run, the read projects the new binding's declaration, never the old one's.

## Risks And Blockers

- Phase 3 registration and typed wire errors rest on two Plan-006 pieces: the registry's camelCase method-name format and the `DaemonDomainError` wire projection (CP-014-12).
- Ordering: T2.7's blocking-state integration arms require Plan-010 Phase 2; the build order must respect it.
- Provider-native orchestration differences can leak into product semantics unless normalized at the daemon boundary (ADR-005; CP-014-13).
