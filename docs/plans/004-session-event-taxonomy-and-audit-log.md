## Goal

Implement the canonical append-only session-event contract — providing the register-and-append-path infrastructure every other plan emits into.

## Scope

This plan covers the `EventEnvelope` contract and version semantics, the event taxonomy registry per [Spec-005 §Event Type Summary](../specs/005-session-event-taxonomy-and-audit-log.md#event-type-summary) (written into contracts by T1.9, Plan-013 T1.4, and Plan-014 T1.3), append-only persistence with per-session sequence allocation, the machine-authored `content_payload` column, catch-up reads, live subscriptions, and the deletion of a session's rows the whole-session purge calls. It also owns the cross-cutting `sourceEpoch` + `sourcePosition` epoch-attribution payload carrier pair (the CP-002-12 registration, T1.8 — stamped and consumed by Plan-002's rollback legs; registered here because the typed payload-field shape lives in this plan's `event/envelope.ts` contract surface).

Plan-004 is the canonical emitter of `event.compacted` in `event_maintenance`; the `backup.*` types of `event_maintenance` are the backup job's ([Plan-005](./005-local-ipc-and-daemon-control.md) Phase R1). It is not the emitter of the remaining categories — see §Event Taxonomy Coverage for the ownership boundary.

## Non-Goals

- The daemon's diagnostic buckets ([Plan-017](./017-observability-and-failure-recovery.md))

## Content Payload Column (Machine-Authored Prose)

Plan-004 owns the read/write semantics for `session_events.content_payload BLOB`, which this plan creates rather than inherits. Phase 3B builds it.

The append path (`events/log-service.ts`) writes the column in the statement that writes the row. A body is kept whole; a body of 1 KiB or more is compressed with raw deflate at level 6, and a smaller body is stored as it is, the encoding recorded in the payload. The column is plain, like every other column.

Two write-path rules hold:

- **Sole write path.** The append path is the only route by which `content_payload` bytes are constructed; callers MUST NOT produce them anywhere else, so the compression rule has one home. The content member `contentLength` is set by this write alone, under an internal guard on the append path that is not a wire code.
- **`event_maintenance` carries no `content_payload`.** The discriminated-union type on `RawEventInput` makes this column unconstructible for that category: its rows sit on the sentinel session, which no purge removes, so a body on such a row would be a body no purge could remove.

**Read path.** Two cases, and in **neither** is `payload` mutated. The reader returns a **`HydratedSessionEvent`**: the event exactly as stored, paired with the closed two-arm `content` union T3.4 declares. (1) `content_payload IS NULL` — `content` takes the **unavailable** arm: there was never a body; it never fabricates an empty body, because an empty body reads as "the assistant said nothing" and that is a different and false claim. (2) Non-NULL — `content` takes the **available** arm carrying the body beside the `contentLength` the payload already states. Case (1) is the condition the canonical-transcript fold reports as `'turn_content_unavailable'` ([Spec-005 §Session Lifecycle](../specs/005-session-event-taxonomy-and-audit-log.md#session-lifecycle-session_lifecycle)). **Merging the body into `payload` is prohibited, not merely undesirable**: the body-bearing `SessionEventSchema` variants T3.4 registers are strict and declare no body member, so a merge would add an undeclared member that fails validation. T3.6's `content/read.ts` is bound by the same rule.

## Erasure Paths Cross-References

Plan-004's part in the data acts of [Spec-020](../specs/020-data-retention-export-and-deletion.md):

- **A purge leaves nothing readable.** A purge deletes the session's rows with SQLite's `secure_delete` on, in one transaction, so the freed pages hold nothing readable, and checkpoints the write-ahead log with `TRUNCATE` once the delete commits; `Erase all data` deletes the app's credential-store items and the store (CP-004-5).
- **Data acts record no user event.** A session's purge (`Delete old data`) records no event of the session, whose rows it deletes; it deletes them after the files only that session names, and before the artifact payloads no surviving manifest names, through T3.2 with `secure_delete` on, checkpointed with `TRUNCATE` after commit ([Spec-020 §Ordering And Atomicity](../specs/020-data-retention-export-and-deletion.md#ordering-and-atomicity)); `Export all data` writes one line to the diagnostic log; `Erase all data` leaves no log to write into ([Spec-005 §Data Acts](../specs/005-session-event-taxonomy-and-audit-log.md#data-acts)). Plan-004 provides the append path for the session events and the row deletion; it does not order the purge's steps.

## Cross-Version Compatibility Surface

Plan-004 owns the `EventEnvelope` contract's integration with [ADR-017](../decisions/017-cross-version-compatibility.md):

- `.version` format `"MAJOR.MINOR"` per [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #1.
- Producer-set at emit per §Decision #2; never copied from received events.
- Unknown-MAJOR events persisted as version stubs retaining full canonical bytes per §Decision #5 (read-side behavior per §Decision #9 accept-and-stub); the row's `.version` stays the producer's original — version-stubbing never rewrites the canonical row.
- Unknown-MINOR optional fields and enum values preserved verbatim per [Spec-005 §EventEnvelope Version Semantics](../specs/005-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics) + [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #8 (MINOR additive-only).
- An app outside its service's version range gets `DaemonHelloAck { compatible: false, reason }` with `version.floor_exceeded` or `version.ceiling_exceeded` at the connection handshake, never a join-time or write-time typed error, per §Decision #4 + §Decision #10.
- Event-type registry extensions within the same envelope MAJOR are additive-only per §Decision #8 — event-type renames are explicitly forbidden because readers dispatch on the name.

#### Event-Kind Disposition Table

The provider drivers (Plan-003) normalize both provider wires into a normalized event vocabulary before the taxonomy maps them onto the `SessionEventType` literals — the type registry above. This table is the **disposition contract** for that mapping: every normalized kind resolves to exactly one disposition — `adopt` (maps to an existing category), `rename` (maps under a different canonical name to resolve a wire collision), `correlate` (folds into an existing row via `correlation_id` — no category and no new persisted type), or `discard` (consumed transiently or dropped) — under a **no-silent-capability-loss default**: `adopt`/`rename` is the default, and every `correlate` or `discard` carries a stated reason, so a capability-bearing kind is never dropped silently. The normalized kinds are the rows below, together with the current-wire delta families. ##### T2.1 — RFC 8785 JCS canonicalizer

Files: `packages/runtime-daemon/src/events/canonicalizer.ts` (NEW) + `packages/contracts/src/event/envelope.ts` (EXTEND — `EVENT_ENVELOPE_SEQUENCE_MAX`). Provides: `canonicalizeEvent(envelope: EventEnvelope): CanonicalBytes` returning phantom-branded `Uint8Array` constructible only inside this module; `canonicalizeJson(value: unknown): CanonicalBytes`, the generic entry point for any caller that needs canonical JSON bytes (CP-004-1); `normalizeOccurredAt(occurredAt: string): string`, the RFC 3339 UTC millisecond narrowing `canonicalizeEvent` applies to `occurredAt` before projecting — **exported** because the narrowing is many-to-one, so T3.1's `EventLogService.append` MUST persist exactly the normalized string rather than the producer's raw spelling (the `session_events.occurred_at` column is declared at that precision, and a raw spelling both violates that column contract and drops the row out of every lexical date-range scan), and `canonicalizeEvent` hands back bytes rather than that string, so exporting the narrowing is the only way to give the append path the exact value without duplicating it; in-package surface for now, `src/index.ts` not re-exporting this module; `EVENT_ENVELOPE_SEQUENCE_MAX` (`Number.MAX_SAFE_INTEGER`), the parse-boundary half of the sequence-injectivity ceiling, bound on `EventEnvelopeSchema.sequence` — its canonicalizer-side counterpart `assertRepresentableSequence` covers the direct-caller path the wire schema never sees, and the two surfaces are **deliberately un-shared** (importing the const would make them agree by construction, wrong value included; T2.2's `canonicalizer.golden.test.ts` asserts the agreement instead, so either side drifting fails a test). The module's **refusal boundary is part of what it provides** — CP-004-1 states it to every caller by identifier. The generic entry point carries these refusals: `assertWithinCanonicalDepth` (the `CANONICAL_JSON_MAX_DEPTH` policy ceiling), `assertWellFormedStrings` (the RFC 8785 §3.2.2.2 MUST-terminate refusal over unpaired UTF-16 surrogates) and `assertNoToJsonOverride`, which refuses any value carrying a callable `toJSON` at any depth and which a value arriving through `JSON.parse` can never trip, since parsed output cannot carry a function-valued member. Reentrancy is owner-scoped via an `AsyncLocalStorage` (`node:async_hooks`) context carrying the held-lock token: an `append` issued inside a `sessionAppendLock.run` critical section runs in that same async context, reads the token, and reuses the hold rather than re-acquiring (so a holder's own `append` never self-deadlocks); ANY caller outside that context — including same-session concurrent work on a different async chain — sees no token and blocks until release. **Release-on-settle is unconditional:** the hold releases in a `finally` owned by the frame that ACQUIRED it: an acquiring `critical` that REJECTS releases the hold and propagates the rejection unchanged, with the `AsyncLocalStorage` held-lock token torn down on the same settle path so a rejected acquisition can never leave a stale token visible to a later same-context call; a REENTRANT frame that rejects propagates the rejection unchanged WITHOUT releasing the hold or touching the token — only the acquiring frame settles the physical hold, so an outer owner that CATCHES an inner rejection and continues still holds the lock, its next nested call is still recognized as reentrant, and the hold releases exactly once when the owner frame settles — load-bearing because `append`'s refusals throw INSIDE the critical section, so a leak-on-rejection would wedge the session unrecoverably (the module-singleton state makes the wedge process-lifetime). The lock state is process-global by design and the module publishes no reset: each T3.3 test file starts from a fresh module through the test runner's module isolation, and within a file every arm settles the holds it takes, so no held lock leaks across arms. The four lock properties are T3.3-tested: nested-call progress (an inner `append` completes under the outer hold), concurrent same-session blocking (two parallel `sessionAppendLock.run` calls on one session serialize — the second waits for the first to release), cross-session non-blocking (locks on distinct sessions run concurrently), and owner-scoped rejection-release (a rejecting acquiring `critical` releases the hold — a subsequent same-session acquisition proceeds — while an inner REENTRANT rejection caught by the outer owner releases nothing: the arm asserts the outer's next nested call still runs reentrantly and the hold releases exactly once on the owner's settle). The daemon's one schema carries a partial UNIQUE index `idx_session_events_run_terminal_once` on `session_events (json_extract(payload, '$.runId'), json_extract(payload, '$.runVersion')) WHERE category = 'run_lifecycle' AND type IN ('run.completed', 'run.failed', 'run.interrupted', 'run.stopped')` — the schema-level backstop for the terminal exactly-once property: a second terminal row for the same `(runId, runVersion)` epoch raises a SQLite UNIQUE-constraint error (fail-loud, never a silent append-if-absent API). The index is scoped to the four terminal `run_lifecycle` types — the `completed` / `interrupted` / `stopped` / `failed` terminal run states — so non-terminal `run_lifecycle` rows and every other category insert freely, and NULL `runId` / `runVersion` rows bypass the index (SQLite treats NULLs as distinct); the non-null-key precondition is the Plan-002 T3.6 emitter's leg, and this index is the defense-in-depth backstop behind that guard, not a replacement for it. The same schema carries the projection-level terminal-key check that Spec-005's at-most-once-terminal-emission rule assigns to this schema work as a trigger trio, because its update legs compare the new row against `OLD`, which a CHECK constraint cannot read: `trg_run_terminal_key_insert` (`BEFORE INSERT`), `trg_run_terminal_key_update` (`BEFORE UPDATE OF payload, category, type`), and `trg_run_terminal_key_promote` (`BEFORE UPDATE OF category, type` — rejects re-typing a non-terminal row INTO the terminal set outright; terminal rows are INSERT-only, so a null-keyed promotion cannot slip the OLD-keyed update leg and the NULL-distinct index), with full DDL in [local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md). The INSERT leg, scoped `WHEN NEW.category = 'run_lifecycle' AND NEW.type IN ('run.completed', 'run.failed', 'run.interrupted', 'run.stopped')`, aborts (`SELECT RAISE(ABORT, …)`) when the terminal key is NULL **or the wrong SQLite storage class** — `json_type` must be `'text'` for `runId` (a `RunId` string) and `'integer'` for `runVersion` (the any-run-progression counter per [Spec-005 §Run Lifecycle (run_lifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)) — so a type-drifted `"7"`-vs-`7` key that would slip past the storage-class-keyed UNIQUE index is caught; this closes the NULL-key bypass the UNIQUE index cannot catch (NULLs are distinct) and fails loud on exactly the malformed terminal rows the backstop exists to guard. The **`UPDATE` leg is load-bearing** and is keyed off `OLD` (a row that WAS terminal cannot escape by mutation): beyond the same NULL/type checks it also aborts a value-changing key rewrite (`json_extract(NEW…)` `IS NOT` `json_extract(OLD…)`, null-safe — a bug rewriting `(R,7)` to another non-null pair would otherwise free the index slot for a duplicate terminal) and a `category`/`type` de-scope (`NEW.category IS NOT OLD.category OR NEW.type IS NOT OLD.type` — flipping a terminal row out of the guarded set is the same escape), so a terminal row keeps its `runId` / `runVersion` / `category` / `type` for its whole life. A promotion regression test accompanies the trio: an `UPDATE` re-typing a non-terminal row to `('run_lifecycle', 'run.completed')` with NULL keys must abort on the promote leg, never silently satisfy the NULL-distinct index. **A normalization obligation lands on this append path, met before canonicalization and inherited from T2.1:** `append` MUST persist the **normalized** `occurredAt` — the string T2.1's exported `normalizeOccurredAt` returns — never the producer's raw input, because the wire schema admits `+05:00` offsets and omitted seconds while the `session_events.occurred_at` column is declared RFC 3339 UTC at millisecond precision (a raw spelling both violates the column contract and drops the row out of every lexical date-range scan). The obligation has no other home: T2.1 can normalize `occurredAt` but never persist it. Depends: T2.1; the `session_events` columns Plan-001 creates; Plan-001 `I-001-1` (sequence as canonical order key). IdempotencyClass: `manual_reconcile_only` per append non-retry-safety (a retried append allocates a second sequence).

Provides, as `EventLogService` methods: `readAfterCursor(params): Promise<EventReadAfterCursorResponse>` returning `{events, nextCursor, hasMore}`; `readWindow(params): Promise<EventReadWindowResponse>` bounded by `[fromSequence, toSequence]`. **Cursor encoding (predecessor-position model): an `EventCursor` is a log POSITION**, an integer ≥ -1 rendered as a decimal string under the existing opaque `EventCursor` brand — clients keep treating it as opaque. Position `-1` is start-of-log (before the first row); a position ≥ 0 is an event's `sequence` (`EventEnvelope.sequence` stays nonnegative). The daemon-side `encodeEventCursor(position: number): EventCursor` / `decodeEventCursor(cursor: EventCursor): number` pair (exported from `packages/contracts/src/session/id.ts` beside `EventCursorSchema`) has domain **integer ≥ -1**: `decodeEventCursor` raises the typed `CURSOR_UNRESOLVABLE` error (registered in `packages/contracts/src/error.ts`, the contracts error-taxonomy pattern) for a non-integer or a value `< -1` (a corrupted value), never a silent parse and never a dual-format fallback decoder. Cursor semantics: a cursor denotes a log position, and `readAfterCursor` scans strict `sequence > decodeEventCursor(afterCursor)` in ascending order; the `afterCursor` parameter is **optional** — present ⇒ scan after that position; **absent ≡ the start-of-log position `-1`**, so a cursorless read returns the full surviving range, matching a `session.subscribe` opened with no `afterCursor` exactly (catch up from the start). `hasMore` is `true` exactly when the page cap leaves rows still beyond `nextCursor`, and `nextCursor` is `encodeEventCursor` of the last returned event's sequence (an empty page returns the input cursor unchanged with `hasMore: false`; a cursorless call's effective input is the start-of-log position `-1`, so an empty cursorless page returns `encodeEventCursor(-1)` — `nextCursor` is wire-required and is never absent or invented). Resumption: each change a `session.subscribe` frame carries holds `encodeEventCursor(envelope.sequence)` as its `cursor`, derived from the delivered envelope's required `sequence` field (`EventEnvelope.sequence`, `packages/contracts/src/event/envelope.ts` — always present, so `LocalSubscriptionProducer<EventEnvelope>` already carries it and no notification-schema change is needed) — a subscriber that re-opens `session.subscribe` with its last-delivered change's cursor as `afterCursor` resumes exactly after that sequence. Also populates the required `transcriptCursors.earliest: EventCursor` — **the position immediately BEFORE the oldest surviving row**, hence a directly resumable cursor (the `SessionReadResponseSchema` widening + `session.read` materializer are in Files; architecture mirror in [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md)): `encodeEventCursor(-1)` for every session, because no row of a kept session is ever deleted: background work removes nothing, and `Delete old data`, the only deletion, deletes whole sessions, so the floor moves for no session a screen can read — no screen is open on a session the purge removes. Because `earliest` is a real position, `readAfterCursor(earliest)` scans `sequence > -1` and returns the full surviving range with no off-by-one — no separate cursorless-floor primitive is needed. Consumer rule: **resume from `acknowledged ?? earliest`** — with no acknowledged cursor, resume from `earliest`; the gap predicate `decodeEventCursor(acknowledged) < decodeEventCursor(earliest)` ⇒ the acknowledged position fell below the surviving floor ⇒ events were lost ⇒ reset the projection and resume from `earliest` (a clean floor `earliest = encodeEventCursor(N-1)` against `acknowledged = encodeEventCursor(N-1)` gives `N-1 < N-1` = false, so no false resync). Two failure modes converge on that one reset-and-resume-from-`earliest` path: a `CURSOR_UNRESOLVABLE` decode (a corrupted cursor) and the gap predicate above. ## Authoring Decisions

Decisions this plan makes that the spec does not.

- **Event contracts directory placement.** Extend the top-level `packages/contracts/src/event*.ts` file that holds the concern (the list under Target Areas); a new `event-`-prefixed sibling is added only when an extension would take a file past 900 lines, the most any file holds, tests and data included. The contracts package has no `events/` subdirectory; no other plan adopts a subdirectory pattern.
- **JCS library: vendor vs in-house.** Vendor — `canonicalize` package (Erdtman's RFC 8785 reference implementation; ships with the RFC). T2.2 lifts the RFC 8785 Appendix B Table 1 number-serialization vectors verbatim as a sub-suite to catch version-drift bugs. In-house implementation rejected per ECMA-262 ToString edge-case risk.
- **Golden-vector storage: inline hex vs JSON fixture.** Inline hex strings in the test file, beside the assertion that reads them; PR-diff is the audit trail for byte-stable artifacts. crypto-paseto's `packages/crypto-paseto/src/v4-local.ts`, as [Plan-015](./015-hosted-account-and-identity.md) T5.6 builds it, is checked against the official PASETO vectors, which stay in the package's JSON fixture because that file is vendored whole from upstream.
- **Live-stream gap detection mechanism.** The session stream marks a gap itself: a frame tells a screen the daemon dropped changes for it, and the screen resubscribes after the last cursor it holds. No cursor-carrying heartbeat is needed: when a screen that fell behind has caught up on its queue, the daemon sends it one frame with no changes, carrying the drop mark and the newest cursor, so a session that goes quiet right after a drop still tells the screen it is behind.

## Cross-Plan Obligations

Each obligation gets a CP-004-N ID. One Plan-002-facing seam is body-registered rather than CP-rowed, per the T3.1 `sessionAppendLock` publication precedent: the T1.8 `sourceEpoch` + `sourcePosition` carrier pair (the CP-002-12 registration — the obligation ledger is Plan-002's row).

- **CP-004-1 — T2.1's canonicalizer is the workspace's one RFC 8785 implementation.** Phase 2 T2.1's `canonicalizeEvent` + `canonicalizeJson` are the single source of truth for RFC 8785 JCS; any plan that needs canonical JSON bytes MUST consume them — never re-implement or fork. **The generic entry point is BOUNDED, not unlimited. It carries refusals of different KINDS, and each is a guarantee to every caller:** (i) the **policy ceiling** — `canonicalizeJson` refuses any value nesting containers past a fixed ceiling (`CANONICAL_JSON_MAX_DEPTH`, 64), a bound of the product's own, since the pinned `canonicalize@5.1.0` walks with an explicit stack and sets no depth limit; (ii) the **RFC-mandated refusal** — `canonicalizeJson` refuses any string value or property name carrying an unpaired UTF-16 surrogate, because RFC 8785 §3.2.2.2 makes terminating on such data a normative MUST which the pinned `canonicalize@5.1.0` also refuses, but with a bare `Lone surrogate is not allowed` that names no location, so the guard runs first and says where the character sits without quoting the text; and (iii) the **determinism refusal** — `assertNoToJsonOverride` refuses any value carrying a callable `toJSON` at any depth, a `toJSON` being arbitrary caller code that need not return on a later canonicalization what it returned on an earlier one. (i) is checked first, and that order is a correctness constraint rather than a diagnostic preference — the depth walk is what makes the later walks terminate on cyclic input — so a value defective in more than one way reports the over-deep refusal and never another. Three consequences for any caller that feeds the entry point a value from outside the process, one deliverable each: (1) a **registered rejection reason** for an over-deep value; (2) a **distinct** registered rejection reason for an ill-formed one — (1) and (2) MUST NOT collapse into a single reason, an over-deep value and an ill-formed one being different client errors whose merger destroys the diagnostic (every refusal is a plain throw at T2.1, so each is caught and mapped at the caller's boundary, never surfaced raw to a remote party); and (3) the **depth ceiling ONLY** can be raised — a ceiling that proves too tight for a real payload is **raised in T2.1's constant**, never escaped by forking the canonicalizer. **(3) does not extend to (ii) or (iii).** The well-formedness refusal is a normative MUST-terminate — never raised or relaxed in either direction, since relaxing it violates RFC 8785 — so catch-and-map per (2) is the only available response there; the determinism refusal is what lets re-canonicalizing a value reproduce the bytes it gave before, so it is never relaxed either. A value that arrives through `JSON.parse` can never trip (iii): parsed output carries no function-valued member — a wire `{"toJSON":"x"}` parses to a STRING, and `"__proto__"` parses as an ordinary own data property rather than a prototype mutation — so the predicate is unsatisfiable on parsed input. A value a caller CONSTRUCTS in process (an object literal carrying a `Date`, a `Buffer`, or any class instance with a `toJSON`) meets a live refusal.
- **CP-004-2 — `CapabilityDetails` + `providerFailureDetail` carry-forward with Plan-003 (answers CP-003-3).** Phase 1 T1.4 removes the `CapabilityDetails` event-payload wrapper and the `runtime_node.capability_*` payload aliases: a driver's capability record lives in the driver capability tables and `GetCapabilitiesResult`, and no session event carries it. Phase 3 audit-mirror adds `providerFailureDetail?: string` to `run.failed` payload (`RunStateChangeEvent` in `docs/architecture/contracts/run-control-payloads.md §Plan-002 — Queue Steer Pause Resume`), an ADR-017-compliant additive-only MINOR addition.
- **CP-004-3 — Plan-001's columns keep their owner.** Plan-004 Phase 3 reads the columns Plan-001 creates and never re-shapes them (Plan-001 I-001-2). The column Plan-004 needs (`session_events.content_payload`) is Plan-004's addition to the daemon's one schema.
- **CP-004-4 — Plan-012 recovery-dispatcher consumes T4.1 read-after-cursor.** Plan-012's recovery path calls the daemon-internal `EventLogService.readAfterCursor` in `packages/runtime-daemon/src/events/log-service.ts`, which T4.1 extends, to rebuild projections from the last `projection_cursors.last_sequence` checkpoint. T4.1's `readAfterCursor` signature is the binding interface.
- **CP-004-5 — Plan-019's data acts delete a session's rows only through T3.2.** A session's purge deletes its rows through T3.2, `content_payload` with them, with SQLite's `secure_delete` on, and checkpoints the write-ahead log with `TRUNCATE` once the delete commits ([Spec-020 §Ordering And Atomicity](../specs/020-data-retention-export-and-deletion.md#ordering-and-atomicity)); and `Erase all data` deletes the app's credential-store items and the store, so no row survives it. Plan-019 therefore deletes a session's rows only through T3.2 and deletes the store whole.
- **CP-004-6 — Plan-015 daemon credential provider for the daemon's control-plane calls.** The daemon authenticates to the control plane as the node-owner user — the daemon's standing posture per [daemon.md §Responsibilities](../architecture/daemon.md#responsibilities) (the daemon authenticates to the control plane using PASETO v4 tokens), so no custody contract is violated: Spec-021's auth-material exclusivity clause binds main-process-vs-renderer, is desktop-only, and expressly cedes daemon internals to that component doc — presenting a PASETO v4.public access token with a per-request DPoP proof signed by a daemon-held key the token's `cnf.jkt` binds (api-payload-contracts.md §Authenticated Principal; a token is bound to the one key its `cnf.jkt` names, so the daemon never presents a token another process holds). **The token reaches the daemon through device-code sign-in.** Signing in yields a DPoP-bound (`cnf.jkt`) rotating refresh token, kept as its own item in the operating system's credential store; the daemon trades it at the control plane for short-lived PASETO v4.public access tokens, each trade returning a new refresh token. Presenting a refresh token that was already used revokes its whole family, as signing out does, and access tokens are never stored, so each attempt mints fresh material. The protocol layer is owned by ADR-010; the issuance implementation is Plan-015's PASETO wiring. Plan-004 therefore declares a constructor-injected credential-provider INTERFACE — `DaemonCredentialProvider` in `daemon-credential-provider.ts` (invoked per attempt, each retry carrying fresh material; an auth failure is a retryable transport failure on the caller's backoff), with the implementation + composition-root wiring owed by Plan-015 — an injected interface with a runtime assertion against the stub, so build order is preserved. The seam is deliberately credential-class-agnostic: if a future ADR-010 change mints a distinct node-scoped credential (a relay `connectionToken` purpose-scoped model), the interface absorbs it unchanged — that change is ADR-010's + Plan-015's to author, not this plan's. Plan-015 Phase 5 authors the decomposition: T5.1/T5.2 the implementation + issuance/refresh path, and T5.3 the composition-root wiring with the runtime stub assertion at the live sites. The callers are each injected by their own plan: the daemon's call to the control plane's `push.send` ([Plan-016](./016-notifications-and-attention-model.md) builds the call; [Plan-025](./025-remote-control.md) Phase 5 builds the senders), and [Plan-025](./025-remote-control.md)'s `runtimenode.register` (Phase 3) and `runtimenode.certificateChallengeSet` (Phase 8). The reciprocal is registered as [Plan-015 CP-015-7](./015-hosted-account-and-identity.md#cross-plan-obligations) — which also carries the matching implementation-derived edge on the Plan-015 row and the Plan-015 header-Dependencies clause.
- **CP-004-7 — Plan-003 consumes `content_payload` at the canonical-transcript fold (⇄ CP-003-10).** Phase 3B ships the column, its write path, and the read path. [Plan-003](./003-provider-driver-contract-and-capabilities.md)'s canonical-transcript fold is its first consumer and its reason for existing: [ADR-027](../decisions/027-canonical-transcript-is-authoritative.md) makes the transcript authoritative for the content of a provider session, and a projection over `session_events` can only be authoritative for content the rows hold. Plan-003 takes one task-scoped hold on this phase, and Plan-004 owes nothing back beyond shipping it: Plan-003's T3.17, the hand-over brief, dispatches only after this phase merges, because the brief's notes and word-for-word tail are the bodies this column holds; T3.16's fold is not held, being correct over a body-less log, declaring each body-less turn `turn_content_unavailable`. Plan-004 does **not** own the fold's loss reporting: the step-1 (Fold) `DeclaredLossKind` member this column's state produces, `'turn_content_unavailable'` (no body to read), is declared by Plan-003's fold from the row state this plan writes.

## Invariants

Each invariant gets an I-004-N ID with the enforcement strategy and the test that confirms it.

- **I-004-1-01 — Category/type bijection.** Every event type belongs to exactly one category; `SESSION_EVENT_CATEGORY_BY_TYPE` holds exactly the types §Event Type Enumeration lists, each in one category, and its values are exactly `EventCategory`'s members. The assertion tracks the `SessionEventType` union, which T1.9, Plan-013 T1.4, and Plan-014 T1.3 widen in turn under CP-013-2 and CP-014-1. Enforced by a type-level exhaustiveness check. Cite: [Spec-005 §Event Type Summary](../specs/005-session-event-taxonomy-and-audit-log.md#event-type-summary).
- **I-004-1-02 — Event-type-string immutability.** Type strings are immutable wire identifiers; renames are forbidden once a type is registered. Enforced via build-time const-assertion + [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #8 (MINOR additive-only). Cite: [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #8.
- **I-004-1-03 — Envelope field set is fixed; serialized order is RFC 8785 lex-sort.** The Zod schema declares the canonical field set; RFC 8785 §3.2.3 mandates UTF-16 code-unit lex-sort serialization. Enforced via Phase 2 T2.2 golden-vector tests. Cite: [Spec-005 §Canonical Form](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-form); RFC 8785 §3.2.3.
- **I-004-1-04 — `EventEnvelope.version` immutability.** Producer-set at emit; never rewritten, on read or on upgrade. Enforced via the `EventEnvelopeVersion` brand, whose docstring says in plain words that the version is set once at emit and never rewritten. Cite: [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #2, #6; [Spec-005 §EventEnvelope Version Semantics](../specs/005-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics).
- **I-004-2-01 — Canonical bytes are byte-stable across implementations.** T2.2 golden-vector tests + the RFC 8785 Appendix B Table 1 number-serialization conformance vectors guarantee byte-identical output for semantically-equal envelopes. Cite: RFC 8785 Appendix B (Table 1 — ECMAScript-Compatible JSON Number Serialization Samples).
- **I-004-2-02 — The canonicalizer's refusals cover the serialized tree, and its refusal order is observable.** `canonicalizer.ts` raises these refusals itself: `normalizeOccurredAt`'s four guards (a lexical shape outside RFC 3339 with an uppercase `T` and a `Z` or `±HH:MM` offset; sub-millisecond precision the canonical form cannot hold, refused rather than truncated because truncation would silently change the recorded timestamp; a lexically-valid but non-existent calendar date, caught by reading the fields back after the setters roll them over; and an offset fold landing outside the four-digit-year range `toISOString` renders, in both directions), `assertRepresentableSequence` (a `sequence` outside the IEEE-754 safe-integer range, where distinct sequences collapse onto one double and two different events could share one position in a log whose sequence is its order key), the `CANONICAL_JSON_MAX_DEPTH` ceiling (a bound of the product's own — the exact-pinned `canonicalize@5.1.0` walks with an explicit stack and sets no depth limit, and `canonicalizeJson` accepts any value a caller hands it), `assertNoToJsonOverride` (any value carrying a callable `toJSON` at any depth — arbitrary caller code that would otherwise divert the serializer onto a tree no guard inspected, and re-invoking it on a later canonicalization need not reproduce the earlier bytes), `assertWellFormedStrings` (RFC 8785 §3.2.2.2's MUST-terminate obligation over any unpaired UTF-16 surrogate in a string value or a member name — the library refuses it too, with a bare message that names no location), and the no-JSON-representation guard (a top-level `undefined`, function, or symbol, for which the serializer returns no output and the encoder would otherwise hand its caller zero canonical bytes). Three further refusals originate inside `canonicalize@5.1.0` and surface with its bare wording (`NaN is not allowed`, `Infinity is not allowed`, `Circular reference detected`); they are inventoried here, not owned — and the cycle refusal is SHADOWED in both shapes that could reach it: the depth walk drives an own-property cycle past the ceiling and reports it as depth exhaustion first, and a cycle closed only through a `toJSON` result is refused by `assertNoToJsonOverride` one guard later, before any serialization runs. What survives of it is the non-idempotent-accessor residual below, not a live path. **Which refusal sits on which entry point is forced by RFC 8785 conformance in both directions, not a placement choice:** well-formedness is generic because §3.2.2.2 obliges it for every string in every input, member names included, while the sequence refusal is event-only because Appendix B Table 1 lists unsafe integers as inputs with MANDATED outputs, so a generic unsafe-number refusal would fail the very specification this module implements; the `occurredAt` guards are reachable on two surfaces — inside `canonicalizeEvent`'s projection and through the exported `normalizeOccurredAt` T3.1's append path calls directly — and the no-JSON-representation guard is generic in effect as well as in placement, unreachable through `canonicalizeEvent`, whose top-level value is always the projection object and therefore always serializes (the guard fires on a top-level `typeof canonicalText !== "string"`, which the library returns only where it delegates to `JSON.stringify` for a non-object). **The first refusal to fire is the only one a caller sees, so the order IS the diagnostic:** `canonicalizeJson` runs the depth ceiling → the `toJSON` refusal → well-formedness → whatever the serializer itself refuses (the three library throws fire inside that call, ahead of the last guard) → no-JSON-representation, and `canonicalizeEvent` runs sequence → `occurredAt` → the three it inherits, in that same relative order. Depth-FIRST is a CORRECTNESS constraint rather than a diagnostic preference: neither of the two walks behind it carries cycle detection or a bound of its own, and it is the depth walk — which reports a cycle as depth exhaustion — that makes both terminate on cyclic input at all, so demoting it turns a refusal into a hang. The `toJSON` refusal's own position, between the ceiling and well-formedness, is a correctness constraint too and in the other direction: placed any later it would be walking a tree the well-formedness guard had already been diverted away from. **The refusals reach the serialized tree, and one residual keeps that from being unconditional.** `assertNoToJsonOverride` closes the wider of the two bypasses this invariant scopes itself around: without it, a shallow object whose `toJSON` returned a deeper or ill-formed tree would clear every guard and be serialized anyway. The guard tests `typeof node.toJSON === "function"` down the whole prototype chain rather than `Object.hasOwn`, deliberately — an inherited `toJSON` diverts the serializer exactly as an own one does. **It REFUSES rather than inspecting the diverted output, and non-determinism is why:** a `toJSON` is arbitrary caller code re-invoked on every canonicalization, so the same value can serialize to different bytes on two canonicalizations, and byte-stable canonical form turns on re-canonicalizing the value and getting the same bytes — a guard that walked the `toJSON` RESULT would still have to assume the serializer later saw that same result. Depth-ceiling evasion and §3.2.2.2 evasion are the second and third motivations, both subsumed by refusing the carrier outright. **The surviving residual is the non-idempotent ACCESSOR.** The depth walk's `Object.values` invokes each own enumerable getter once, `assertNoToJsonOverride`'s a second time, `assertWellFormedStrings`' `Object.entries` a third, and the serializer again per object member, so a getter returning different values across them puts the guard walks and the serializer on different trees, and is the only remaining way to hand the serializer a tree no guard inspected. It is unreachable for a value that arrives through `JSON.parse` — parsed output carries neither accessors nor a callable `toJSON`, the latter because a parsed `{"toJSON":"x"}` yields a STRING — which is what makes the scoped claim load-bearing rather than weak. The over-refusal direction stays harmless by construction: a dropped `undefined` or symbol member's NAME is still checked, and an array's non-index own enumerable properties are walked. Beyond that accessor residual, three more are characterized rather than closed: nothing upstream refuses ahead of this module on the well-formedness axis (`EventEnvelopeSchema` admits lone surrogates in `actor`, `correlationId`, `causationId`, and in `payload` keys and values alike, so the canonicalizer is the first and only refusal on that path); `assertRepresentableSequence` re-checks no schema domain rule, so a negative-but-safe `sequence` passes here and is refused at the parse boundary alone; and T1.8's `sourceEpoch` / `sourcePosition` pair rides inside `payload` as untyped JSON, carrying the identical collapse hazard with the parse boundary as its only enforcement. Enforced in `canonicalizer.ts` (T2.1); every family is pinned by T2.2's `canonicalizer.golden.test.ts`, whose dedicated precedence tests fix the order. Cite: RFC 8785 §3.2.2.2 (the lone-surrogate MUST-terminate obligation) + Appendix B Table 1 (the mandated unsafe-number outputs that forbid a generic sequence refusal); [Plan-004 §Cross-Plan Obligations](./004-session-event-taxonomy-and-audit-log.md#cross-plan-obligations) (CP-004-1 — the generic entry point's refusals as guarantees to every caller, the over-deep and ill-formed refusals caught and mapped to distinct rejection reasons with only the policy ceiling raisable).
- **I-004-3-01 — The append path is the sole write path for `content_payload`, and the column is unconstructible for `event_maintenance`.** The column's branded output type is constructible only on the append path, and the discriminated union on `RawEventInput` denies this column to `event_maintenance` — the category's rows sit on the sentinel session, which no purge removes, so a body there would be a body no purge could remove. Enforced by the type system plus T3.5's type-level assertion; falsified by a compile that accepts either construction.
- **I-004-4-01 — A read after a cursor neither skips nor repeats a row.** `readAfterCursor` returns only rows with `sequence` greater than the cursor's position, in ascending order, and its `nextCursor` resumes exactly after the last row it returned, so the session stream's handoff from catching up to following has no duplicate and no gap. Enforced in `EventLogService.readAfterCursor` (`packages/runtime-daemon/src/events/log-service.ts`); verified by T4.1's tests. Cite: [Spec-005 §Interfaces And Contracts](../specs/005-session-event-taxonomy-and-audit-log.md#interfaces-and-contracts); [Spec-005 §Fallback Behavior](../specs/005-session-event-taxonomy-and-audit-log.md#fallback-behavior).

## Parallelization Notes

- Contracts (envelope + taxonomy + error codes) block all runtime-daemon work; author first.
- The canonicalizer requires contracts only, and its golden vectors pin its output.
- The session purge and the `EventLogService` reads can proceed in parallel once the append path is stable.

## Test And Verification Plan

- RFC 8785 JCS golden-vector conformance tests (standard vectors + project-specific edge cases: null-vs-absent, nested object ordering, numeric canonicalization, millisecond-precision `occurredAt`).
- Version-stub round-trip: an unknown-MAJOR event is persisted verbatim; the log row's `.version` remains the producer's original; on upgrade a receiver that knows the type reads the stub's preserved bytes as that event without rewriting the row.
- Purge tests: `Delete old data` on an archived or closed session deletes every row of that session, and records one `event.compacted` on the sentinel session. Background jobs change no row a person can see: the repack after each purge reports `page_count × page_size` and `freelist_count` before and after.
- Catch-up read tests: `readWindow` is bounded.
- End-to-end lifecycle: session.created → 50+ events → archive → purge deleting its rows → no row of the purged session remains, no byte of its words or bodies is left in the database or write-ahead-log files, and the other sessions' rows are unchanged.
- Content-column tests (Phase 3B): a row with a machine-authored body and a row without one each land the column and payload members they owe and no others; a long body is stored whole with its full `contentLength`; and the read projection never fabricates an empty body on an unavailable row.

2. Enable the canonicalizer (Phase 2 — depends on step 1).
3. Enable the durable append path (T3.1) + the purge's row deletion (Phase 3 — depends on step 2).

Within the supplement the order IS binding: T3.5 tests a column T3.4 creates, and T3.6 reads the column T3.4 writes.

## Rollback Or Fallback

- If a new envelope MAJOR regresses, freeze new event-category adoption; [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #5 version-stub behavior keeps older readers consuming the log as opaque rows until the rollback lands.
- If the purge's row deletion regresses (wrong rows deleted, rows left behind), refuse purges until it is fixed — every kept session stays whole and correct without it; the repack removes nothing a person can see and keeps running.

## Risks And Blockers

- **Canonicalization drift.** Any divergence from RFC 8785 JCS (field ordering, null-vs-absent, numeric canonicalization) produces canonical bytes two honest implementations disagree on, so two readers of one event disagree on its bytes. A single shared canonicalizer implementation plus golden-vector tests are load-bearing.
- **Category drift.** Event-type renames or category reassignments on existing wire types violate [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #8. Enforced by the taxonomy enum + contract tests; new types are additive-only.
