## Goal

Implement the canonical append-only session-event contract — providing the register-and-append-path infrastructure every other plan emits into.

## Scope

This plan covers the `EventEnvelope` contract and version semantics, the event taxonomy registry per [Spec-005 §Event Type Summary](../specs/005-session-event-taxonomy-and-audit-log.md#event-type-summary) (written into contracts by T1.9, Plan-013 T1.4, and Plan-014 T1.3), append-only persistence with per-session sequence allocation, the machine-authored `content_payload` column, catch-up reads, live subscriptions, and the deletion of a session's rows the whole-session purge calls. It also owns the cross-cutting `sourceEpoch` + `sourcePosition` epoch-attribution payload carrier pair (the CP-002-12 registration, T1.8 — stamped and consumed by Plan-002's rollback legs; registered here because the typed payload-field shape lives in this plan's `event/envelope.rs` contract surface).

Plan-004 is the canonical emitter of `session.event.compacted` in `eventMaintenance`; the `daemon.backup.*` types of `eventMaintenance` are the backup job's ([Plan-005](./005-local-ipc-and-daemon-control.md) Phase R1). It is not the emitter of the remaining categories — see §Event Taxonomy Coverage for the ownership boundary.

## Non-Goals

- Full transcript UI rendering (Plan-010)
- The daemon's diagnostic buckets ([Plan-017](./017-observability-and-failure-recovery.md))
- Emission of events owned by other plans: `session.*` lifecycle (Plan-001 — except the two `session.goal.*` events, which are Plan-013-owned per the census row below: the goal set/clear RPC surface; and the three provider-surface observations, Plan-003-normalized), the `daemon.backup.*` events (the backup job, [Plan-005](./005-local-ipc-and-daemon-control.md) Phase R1), the `mcp.*` governance events ([Plan-022](./022-mcp-server-configuration-and-governance.md)), `user.message.sent` (the Plan-002 queue-submit surface), and the provider-surface `agent.run.*`/`usage.*` additions (Plan-003 normalizer per the census rows below)
- Orchestration of the data acts — the session purge, `Export all data` and `Erase all data` of [Spec-020](../specs/020-data-retention-export-and-deletion.md) (Plan-004 provides the append path and the row deletion the purge calls)

## Content Payload Column (Machine-Authored Prose)

Plan-004 owns the read/write semantics for `session_events.content_payload BLOB`, which this plan creates rather than inherits. Phase 3B builds it.

The append path (`events/log_service.rs`) writes the column in the statement that writes the row. A body is kept whole; a body of 1 KiB or more is compressed with zstd at level 3, and a smaller body is stored as its UTF-8 bytes, the encoding recorded in the payload as `contentEncoding: "zstd"` on a compressed body. One codec, `events/content/codec.rs`, encodes on the append path and decodes for every reader of the column: the hydrated read path, the transcript projector, the search index's row text and the export. The column is plain, like every other column.

Two write-path rules hold:

- **Sole write path.** The append path is the only route by which `content_payload` bytes are constructed; callers MUST NOT produce them anywhere else, so the compression rule has one home. The content member `contentLength` is set by this write alone, under an internal guard on the append path that is not a wire code.
- **`eventMaintenance` carries no `content_payload`.** The discriminated-union type on `RawEventInput` makes this column unconstructible for that category: its rows sit on the sentinel session, which no purge removes, so a body on such a row would be a body no purge could remove.

**Read path.** Two cases, and in **neither** is `payload` mutated. The reader returns a **`HydratedSessionEvent`**: the event exactly as stored, paired with the closed two-arm `content` union T3.4 declares. (1) `content_payload IS NULL` — `content` takes the **unavailable** arm: there was never a body; it never fabricates an empty body, because an empty body reads as "the agent said nothing" and that is a different and false claim. (2) Non-NULL — `content` takes the **available** arm carrying the body beside the `contentLength` the payload already states. Case (1) is the condition the canonical-transcript fold reports as `'turnContentUnavailable'` ([Spec-005 §Session Lifecycle](../specs/005-session-event-taxonomy-and-audit-log.md#session-lifecycle-sessionlifecycle)). **Merging the body into `payload` is prohibited, not merely undesirable**: the body-bearing `SessionEvent` variants T3.4 registers are strict and declare no body member, so a merge would add an undeclared member that fails validation. T3.6's `content/read.rs` is bound by the same rule.

## Erasure Paths Cross-References

Plan-004's part in the data acts of [Spec-020](../specs/020-data-retention-export-and-deletion.md):

- **A purge leaves nothing readable.** A purge deletes the session's rows with SQLite's `secure_delete` on, in one transaction, so the freed pages hold nothing readable, and checkpoints the write-ahead log with `TRUNCATE` once the delete commits; `Erase all data` deletes the app's credential-store items and the store (CP-004-5).
- **Data acts record no user event.** A session's purge (`Delete old data`) records no event of the session, whose rows it deletes; it deletes them after the files only that session names, and before the artifact payloads no surviving manifest names, through T3.2 with `secure_delete` on, checkpointed with `TRUNCATE` after commit ([Spec-020 §Ordering And Atomicity](../specs/020-data-retention-export-and-deletion.md#ordering-and-atomicity)); `Export all data` writes one line to the diagnostic log; `Erase all data` leaves no log to write into ([Spec-005 §Data Acts](../specs/005-session-event-taxonomy-and-audit-log.md#data-acts)). Plan-004 provides the append path for the session events and the row deletion; it does not order the purge's steps.

## Cross-Version Compatibility Surface

Plan-004 owns the `EventEnvelope` contract's integration with [ADR-017](../decisions/017-cross-version-compatibility.md):

- `.version` format `"MAJOR.MINOR"` per [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #1.
- Producer-set at emit per §Decision #2; never copied from received events.
- Unknown-MAJOR events persisted as version stubs retaining full canonical bytes per §Decision #5 (read-side behavior per §Decision #9 accept-and-stub); the row's `.version` stays the producer's original — version-stubbing never rewrites the canonical row.
- Unknown-MINOR optional fields and enum values preserved verbatim per [Spec-005 §EventEnvelope Version Semantics](../specs/005-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics) + [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #8 (MINOR additive-only).
- An app outside its service's version range gets `ConnectionInitializeResponse { compatible: false, reason }` with `connection.version.floorExceeded` or `connection.version.ceilingExceeded` at the connection handshake, never a join-time or write-time typed error, per §Decision #4 + §Decision #10.
- Event-type registry extensions within the same envelope MAJOR are additive-only per §Decision #8 — event-type renames are explicitly forbidden because readers dispatch on the name.

#### Event-Kind Disposition Table

The provider drivers (Plan-003) normalize both provider wires into a normalized event vocabulary before the taxonomy maps them onto the `SessionEventType` literals — the type registry above. This table is the **disposition contract** for that mapping: every normalized kind resolves to exactly one disposition — `adopt` (maps to an existing category), `rename` (maps under a different canonical name to resolve a wire collision), `correlate` (folds into an existing row via `correlation_id` — no category and no new persisted type), or `discard` (consumed transiently or dropped) — under a **no-silent-capability-loss default**: `adopt`/`rename` is the default, and every `correlate` or `discard` carries a stated reason, so a capability-bearing kind is never dropped silently. The normalized kinds are the rows below, together with the current-wire delta families. The provider-wire reference docs — [`docs/reference/provider-wire/README.md`](../reference/provider-wire/README.md), [`claude.md`](../reference/provider-wire/claude.md), [`codex.md`](../reference/provider-wire/codex.md) — each pinned by its own §Version pin table rather than by a number restated here, and carrying the per-wire evidence for each kind (they document the wire surfaces, not this table), pinning the primary provider sources a reviewer can follow: the [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference) and the full-history [`anthropics/claude-code` changelog](https://github.com/anthropics/claude-code) (`CHANGELOG.md`, version-anchored), both accessed 2026-07-02, and the Codex `app-server` JSON schema regenerated from the pinned binary via `codex app-server generate-json-schema`. Family-level dispositions are used for the delta rows — per-member normalization is Plan-003 T3.5/T3.10 driver detail. Totality over the **known** set holds by the T1.7 registry's type, a record keyed by every kind; the **unknown** residual is backstopped at runtime by the Plan-003 T3.5/T3.10 normalizer default-branch diagnostic (the bundle), so an unrecognized wire kind surfaces a diagnostic rather than vanishing. The `rate_limits` collision resolution and the nine explicitly-discarded Claude system subtypes are the boundary inputs that travel with the table.

Provides: `EventLogService.append(envelope, options)`, an async method returning `{id, sequence}`, as the sole append path: the database writer allocates each session's next `sequence` in the row's own write, and the per-session lock orders a session's appends. **Publishes `sessionAppendLock` (a `KeyedLock<SessionId>`, taken as `sessionAppendLock.run(sessionId, critical)`) from the dependency-leaf `session/append_lock.rs`** (process-wide lock state, so every user — `append`, the purge — serializes on the same per-session lock; the leaf uses neither) — the per-session append lock, whose hold is a value: `append` queues its row under it, so a holder's writes land in the order it made them. The lock orders writes and nothing more, so Plan-002's T3.6 terminal emitter puts its `(runId, runVersion)` check in the terminal event's write as a guarded statement. Reentrancy is a type: `sessionAppendLock.run` hands its critical section the hold, and an `append` made under it is given that hold and takes no lock, so a holder's own `append` cannot wait on its own lock, and a task the holder spawns takes an owned hold it is given; ANY caller without the hold — including same-session concurrent work on a different task — waits until release. No task-local carries the hold. **Release-on-settle is unconditional:** the hold is a guard dropped by the frame that ACQUIRED it: an acquiring `critical` that REJECTS releases the hold and propagates the rejection unchanged; an `append` made through the hold that rejects propagates the rejection unchanged WITHOUT releasing the hold, since it acquired nothing — only the acquiring frame settles the physical hold, so an outer owner that CATCHES an inner rejection and continues still holds the lock, its next `append` through the hold still runs, and the hold releases exactly once when the owner frame settles — load-bearing because `append`'s refusals throw INSIDE the critical section, so a leak-on-rejection would wedge the session unrecoverably (the process-wide state makes the wedge process-lifetime). The lock state is process-global by design and the module publishes no reset: each T3.3 test starts from fresh lock state because nextest runs every test in its own process, and every arm settles the holds it takes. The four lock properties are T3.3-tested: nested-call progress (an `append` made through the hold completes under it), concurrent same-session blocking (two parallel `sessionAppendLock.run` calls on one session serialize — the second waits for the first to release), cross-session non-blocking (locks on distinct sessions run concurrently), and owner-scoped rejection-release (a rejecting acquiring `critical` releases the hold — a subsequent same-session acquisition proceeds — while an inner rejection of an `append` made through the hold, caught by the outer owner, releases nothing: the arm asserts the outer's next `append` through the hold still runs and the hold releases exactly once on the owner's settle). The append writes the run key SQL reads as typed columns of the `STRICT` table, `run_id TEXT` and `run_version INTEGER`, set for the event types that carry them, so no index, trigger or query reads a run key out of the payload's JSON. The daemon's one schema carries a partial UNIQUE index `idx_session_events_run_terminal_once` on `session_events (run_id, run_version) WHERE category = 'runLifecycle' AND type IN ('agent.run.completed', 'agent.run.failed', 'agent.run.interrupted', 'agent.run.stopped')` — the schema-level backstop for the terminal exactly-once property: a second terminal row for the same `(runId, runVersion)` epoch raises a SQLite UNIQUE-constraint error (fail-loud, never a silent append-if-absent API). The index is scoped to the four terminal `runLifecycle` types — the `completed` / `interrupted` / `stopped` / `failed` terminal run states — so non-terminal `runLifecycle` rows and every other category insert freely, and NULL `run_id` / `run_version` rows bypass the index (SQLite treats NULLs as distinct); the non-null-key precondition is the Plan-002 T3.6 emitter's leg, and this index is the defense-in-depth backstop behind that guard, not a replacement for it. Beside it a partial UNIQUE index on `session_events (run_id, turn_number) WHERE category = 'runLifecycle' AND type IN ('agent.turn.completed', 'agent.turn.interrupted', 'agent.turn.failed')` backstops the turn's once-rule, every started turn getting exactly one end ([Spec-005 §Run Lifecycle (runLifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-runlifecycle)): `turn_number` is a typed `INTEGER` column the append writes beside `run_id` from the turn events, a second end of one turn raises a UNIQUE-constraint error, and the run engine's emission gate, keyed by run and turn number, drops a duplicate report before it reaches the write. The same schema carries the projection-level terminal-key check that Spec-005's at-most-once-terminal-emission rule assigns to this schema work as a trigger trio, because its update legs compare the new row against `OLD`, which a CHECK constraint cannot read: `trg_run_terminal_key_insert` (`BEFORE INSERT`), `trg_run_terminal_key_update` (`BEFORE UPDATE OF run_id, run_version, category, type`), and `trg_run_terminal_key_promote` (`BEFORE UPDATE OF category, type` — rejects re-typing a non-terminal row INTO the terminal set outright; terminal rows are INSERT-only, so a null-keyed promotion cannot slip the OLD-keyed update leg and the NULL-distinct index), with full DDL in [local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md). The INSERT leg, scoped `WHEN NEW.category = 'runLifecycle' AND NEW.type IN ('agent.run.completed', 'agent.run.failed', 'agent.run.interrupted', 'agent.run.stopped')`, aborts (`SELECT RAISE(ABORT, …)`) when the terminal key is NULL; the key's types are the `STRICT` columns', `TEXT` for `run_id` (a `RunId` string) and `INTEGER` for `run_version` (the any-run-progression counter per [Spec-005 §Run Lifecycle (runLifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-runlifecycle)), so no key of another type reaches the index; this closes the NULL-key bypass the UNIQUE index cannot catch (NULLs are distinct) and fails loud on exactly the malformed terminal rows the backstop exists to guard. The **`UPDATE` leg is load-bearing** and is keyed off `OLD` (a row that WAS terminal cannot escape by mutation): it aborts a value-changing key rewrite (`NEW.run_id IS NOT OLD.run_id` or `NEW.run_version IS NOT OLD.run_version`, null-safe, so a nulling is refused by the same clause — a bug rewriting `(R,7)` to another non-null pair would otherwise free the index slot for a duplicate terminal) and a `category`/`type` de-scope (`NEW.category IS NOT OLD.category OR NEW.type IS NOT OLD.type` — flipping a terminal row out of the guarded set is the same escape), so a terminal row keeps its `runId` / `runVersion` / `category` / `type` for its whole life. A promotion regression test accompanies the trio: an `UPDATE` re-typing a non-terminal row to `('runLifecycle', 'agent.run.completed')` with NULL keys must abort on the promote leg, never silently satisfy the NULL-distinct index. **A normalization obligation lands on this append path, inherited from T2.1:** `append` MUST persist the **normalized** `occurredAt` — the string T2.1's exported `normalizeOccurredAt` returns — never the producer's raw input, because the wire schema admits `+05:00` offsets and omitted seconds while the `session_events.occurred_at` column is declared RFC 3339 UTC at millisecond precision (a raw spelling both violates the column contract and drops the row out of every lexical date-range scan). The obligation has no other home: T2.1 can normalize `occurredAt` but never persist it. Depends: T2.1; the `session_events` columns Plan-001 creates; Plan-001 `I-001-1` (sequence as canonical order key). IdempotencyClass: `manualReconcileOnly` per append non-retry-safety (a retried append allocates a second sequence).

Position `-1` is start-of-log (before the first row); a position ≥ 0 is an event's `sequence` (`EventEnvelope.sequence` stays nonnegative). The daemon-side `encodeEventCursor` (position to `EventCursor`) / `decodeEventCursor` (`EventCursor` to position) pair (public from `crates/sidekicks-contracts/src/session/event_cursor.rs` beside `EventCursor`) has domain **integer ≥ -1**: `decodeEventCursor` raises the typed `CURSOR_UNRESOLVABLE` error (registered in `crates/sidekicks-contracts/src/session/event_cursor.rs`, beside the codec) for a non-integer or a value `< -1` (a corrupted value), never a silent parse and never a dual-format fallback decoder. Cursor semantics: a cursor denotes a log position, and `readAfterCursor` scans strict `sequence > decodeEventCursor(afterCursor)` in ascending order; the `afterCursor` parameter is **optional** — present ⇒ scan after that position; **absent ≡ the start-of-log position `-1`**, so a cursorless read returns the full surviving range, matching a `session.event.subscribe` opened with no `afterCursor` exactly (catch up from the start). `hasMore` is `true` exactly when the page cap leaves rows still beyond `nextCursor`, and `nextCursor` is `encodeEventCursor` of the last returned event's sequence (an empty page returns the input cursor unchanged with `hasMore: false`; a cursorless call's effective input is the start-of-log position `-1`, so an empty cursorless page returns `encodeEventCursor(-1)` — `nextCursor` is wire-required and is never absent or invented). Resumption: each change a `session.event.subscribe` frame carries holds `encodeEventCursor(envelope.sequence)` as its `cursor`, derived from the delivered envelope's required `sequence` field (`EventEnvelope.sequence`, `crates/sidekicks-contracts/src/event/envelope.rs` — always present, so `SubscriptionNotifyParams<EventEnvelope>` already carries it and no notification-schema change is needed) — a subscriber that re-opens `session.event.subscribe` with its last-delivered change's cursor as `afterCursor` resumes exactly after that sequence. Also populates the required `transcriptCursors.earliest: EventCursor` — **the position immediately BEFORE the oldest surviving row**, hence a directly resumable cursor (the `SessionReadResponse` widening + `session.read` materializer are in Files; architecture mirror in [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md)): `encodeEventCursor(-1)` for every session, because no row of a kept session is ever deleted: background work removes nothing, and `Delete old data`, the only deletion, deletes whole sessions, so the floor moves for no session a screen can read — no screen is open on a session the purge removes. Because `earliest` is a real position, `readAfterCursor(earliest)` scans `sequence > -1` and returns the full surviving range with no off-by-one — no separate cursorless-floor primitive is needed. Consumer rule: **open at `acknowledged ?? latest`** — a screen reads the `transcript.read` window before that cursor ([Plan-010](./010-transcript-and-reasoning.md) T2.4) and opens `session.event.subscribe` after the window's newest row, so it never catches up the whole log; the gap predicate `decodeEventCursor(acknowledged) < decodeEventCursor(earliest)` ⇒ the acknowledged position fell below the surviving floor ⇒ events were lost ⇒ reset the window and open it at `latest` (a clean floor `earliest = encodeEventCursor(N-1)` against `acknowledged = encodeEventCursor(N-1)` gives `N-1 < N-1` = false, so no false resync). Two failure modes converge on that one reset-and-open-at-`latest` path: a `CURSOR_UNRESOLVABLE` decode (a corrupted cursor) and the gap predicate above. Depends: Phase 1 contracts; Plan-001's daemon schema; [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #9 (unknown-MAJOR accept-and-stub). IdempotencyClass: `idempotent` (pure read).

- **Verifies invariant:** I-004-4-01 — a read from cursor N returns the rows after N in ascending order, none skipped or repeated; a page the cap cuts short reports `hasMore: true`, and the read from its `nextCursor` starts at the row right after its last one.

## Authoring Decisions

Decisions this plan makes that the spec does not.

- **Event contracts directory placement.** Extend the `crates/sidekicks-contracts/src/event/` module that holds the concern (the list under Target Areas); a new sibling module in `event/` is added only when an extension would take a file past 900 lines, the most any file holds, tests and data included. The contracts crate has no `events/` module; no other plan adopts one.
- **JCS library: vendor vs in-house.** Vendor — `serde_json_canonicalizer` 0.3.2 (RFC 8785 over `serde_json` values). T2.2 lifts the RFC 8785 Appendix B Table 1 number-serialization vectors verbatim as a sub-suite to catch version-drift bugs. In-house implementation rejected per the edge-case risk of ECMA-262's Number-to-string rule.
- **Golden-vector storage: inline hex vs JSON fixture.** Inline hex strings in the test file, beside the assertion that reads them; PR-diff is the audit trail for byte-stable artifacts. The one JSON fixture is the official PASETO vectors that check `pasetors`' use ([Plan-015](./015-hosted-account-and-identity.md) T5.6), vendored whole from upstream.
- **A screen that falls behind.** The session stream never drops a change, so no gap is marked; a screen resumes after the last cursor it holds, and one far behind the log's head takes the snapshot read [Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior) sets. No cursor-carrying heartbeat is needed.

## Cross-Plan Obligations

Each obligation gets a CP-004-N ID. One Plan-002-facing seam is body-registered rather than CP-rowed, per the T3.1 `sessionAppendLock` publication precedent: the T1.8 `sourceEpoch` + `sourcePosition` carrier pair (the CP-002-12 registration — the obligation ledger is Plan-002's row).

- **CP-004-1 — T2.1's canonicalizer is the daemon's one RFC 8785 entry point.** Phase 2 T2.1's `canonicalizeEvent` + `canonicalizeJson` are the daemon's one RFC 8785 entry point, and any daemon code that needs canonical JSON bytes MUST consume them — never re-implement or fork; every Rust caller uses the same exact-pinned `serde_json_canonicalizer` 0.3.2, and `sidekicks-contracts`' `trust::chain` makes the chain's canonical bytes. **The generic entry point is BOUNDED, not unlimited. It carries one refusal of its own, and that refusal is a guarantee to every caller:** the **policy ceiling** — `canonicalizeJson` refuses any value nesting containers past a fixed ceiling (`CANONICAL_JSON_MAX_DEPTH`, 64), a bound of the product's own, held whatever the pinned `serde_json_canonicalizer` 0.3.2 allows. RFC 8785 §3.2.2.2's MUST-terminate obligation over unpaired UTF-16 surrogates is met before the value reaches it: a `serde_json::Value` holds only valid UTF-8 text, and `serde_json` refuses a lone surrogate escape where the value is parsed. Three consequences for any caller that feeds the entry point a value from outside the process, one deliverable each: (1) a **registered rejection reason** for an over-deep value; (2) a **distinct** registered rejection reason for an ill-formed one, refused at the caller's parse — (1) and (2) MUST NOT collapse into a single reason, an over-deep value and an ill-formed one being different client errors whose merger destroys the diagnostic (every refusal is a typed error at T2.1 and at the parse, so each is caught and mapped at the caller's boundary, never surfaced raw to a remote party); and (3) the **depth ceiling ONLY** can be raised — a ceiling that proves too tight for a real payload is **raised in T2.1's constant**, never escaped by forking the canonicalizer. **(3) does not extend to well-formedness:** it is a normative MUST-terminate, never relaxed, since relaxing it violates RFC 8785, so catch-and-map per (2) is the only available response there.
- **CP-004-2 — The capability record + `providerFailureDetail` carry-forward with Plan-003 (answers CP-003-3).** Phase 1 T1.4 keeps every capability record out of the session events: a driver's capability record lives in the driver capability tables and `GetCapabilitiesResult`, and no session event carries it. Phase 3 audit-mirror adds `providerFailureDetail?: string` to `agent.run.failed` payload (`RunStateChangeEvent` in `docs/architecture/contracts/run-control-payloads.md §Plan-002 — Queue Steer Pause Resume`), an ADR-017-compliant additive-only MINOR addition.
- **CP-004-3 — Plan-001's columns keep their owner.** Plan-004 Phase 3 reads the columns Plan-001 creates and never re-shapes them (Plan-001 I-001-2). The column Plan-004 needs (`session_events.content_payload`) is Plan-004's addition to the daemon's one schema.
- **CP-004-4 — Plan-012 recovery-dispatcher consumes T4.1 read-after-cursor.** Plan-012's recovery path calls the daemon-internal `EventLogService.readAfterCursor` in `crates/sidekicks-daemon/src/events/log_service.rs`, which T4.1 extends, to rebuild projections from the last `projection_cursors.last_sequence` checkpoint. T4.1's `readAfterCursor` signature is the binding interface.
- **CP-004-5 — Plan-019's data acts delete a session's rows only through T3.2.** A session's purge deletes its rows through T3.2, `content_payload` with them, with SQLite's `secure_delete` on, and checkpoints the write-ahead log with `TRUNCATE` once the delete commits ([Spec-020 §Ordering And Atomicity](../specs/020-data-retention-export-and-deletion.md#ordering-and-atomicity)); and `Erase all data` deletes the app's credential-store items and the store, so no row survives it. Plan-019 therefore deletes a session's rows only through T3.2 and deletes the store whole.
- **CP-004-6 — Plan-015 daemon credential provider for the daemon's control-plane calls.** The daemon authenticates to the control plane as the machine's owner — the daemon's standing posture per [daemon.md §Responsibilities](../architecture/daemon.md#responsibilities) (the daemon authenticates to the control plane using PASETO v4 tokens), so no custody contract is violated: Spec-021's auth-material exclusivity clause binds main-process-vs-renderer, is desktop-only, and expressly cedes daemon internals to that component doc — presenting a PASETO v4.public access token with a per-request DPoP proof signed by a daemon-held key the token's `cnf.jkt` binds (api-payload-contracts.md §Authenticated Principal; a token is bound to the one key its `cnf.jkt` names, so the daemon never presents a token another process holds). **The token reaches the daemon through the service's own sign-in**, the authorization-code sign-in with PKCE, PAR and DPoP the service runs itself ([Plan-015](./015-hosted-account-and-identity.md) T5.4). Signing in yields a DPoP-bound (`cnf.jkt`) rotating refresh token, kept as its own item in the operating system's credential store; the daemon trades it at the control plane for short-lived PASETO v4.public access tokens, each trade returning a new refresh token. Presenting a refresh token that was already used revokes its whole family, as signing out does, and access tokens are never stored, so each attempt mints fresh material. The protocol layer is owned by ADR-010; the issuance implementation is Plan-015's PASETO wiring. Plan-004 therefore declares a constructor-injected credential-provider INTERFACE — `DaemonCredentialProvider` in `daemon_credential_provider.rs` (invoked per attempt, each retry carrying fresh material; an auth failure is a retryable transport failure on the caller's backoff), with the implementation + composition-root wiring owed by Plan-015 — an injected interface with a runtime assertion against the stub, so build order is preserved. The seam is deliberately credential-class-agnostic: if a future ADR-010 change mints a distinct machine-scoped credential (a relay `connectionToken` purpose-scoped model), the interface absorbs it unchanged — that change is ADR-010's + Plan-015's to author, not this plan's. Plan-015 Phase 5 authors the decomposition: T5.1/T5.2 the implementation + issuance/refresh path, and T5.3 the composition-root wiring with the runtime stub assertion at the live sites. The callers are each injected by their own plan: the daemon's call to the control plane's `device.push.send` ([Plan-016](./016-notifications-and-attention-model.md) builds the call; [Plan-025](./025-remote-control.md) Phase 5 builds the senders), and [Plan-025](./025-remote-control.md)'s `machine.register` (Phase 3) and `machine.certificateChallenge.update` (Phase 8). The reciprocal is registered as [Plan-015 CP-015-7](./015-hosted-account-and-identity.md#cross-plan-obligations) — which also carries the matching implementation-derived edge on the Plan-015 row and the Plan-015 header-Dependencies clause.
- **CP-004-7 — Plan-003 consumes `content_payload` at the canonical-transcript fold (⇄ CP-003-10).** Phase 3B ships the column, its write path, and the read path. [Plan-003](./003-provider-driver-contract-and-capabilities.md)'s canonical-transcript fold is its first consumer and its reason for existing: [ADR-027](../decisions/027-canonical-transcript-is-authoritative.md) makes the transcript authoritative for the content of a provider session, and a projection over `session_events` can only be authoritative for content the rows hold. Plan-003 takes one task-scoped hold on this phase, and Plan-004 owes nothing back beyond shipping it: Plan-003's T3.17, the hand-over brief, dispatches only after this phase merges, because the brief's notes and word-for-word tail are the bodies this column holds; T3.16's fold is not held, being correct over a body-less log, declaring each body-less turn `turnContentUnavailable`. Plan-004 does **not** own the fold's loss reporting: the step-1 (Fold) `DeclaredLossKind` member this column's state produces, `'turnContentUnavailable'` (no body to read), is declared by Plan-003's fold from the row state this plan writes.

## Invariants

Each invariant gets an I-004-N ID with the enforcement strategy and the test that confirms it.

- **I-004-1-01 — Category/type bijection.** Every event type belongs to exactly one category; `SESSION_EVENT_CATEGORY_BY_TYPE` holds exactly the types §Event Type Enumeration lists, each in one category, and its values are exactly `EventCategory`'s members. The assertion tracks the `SessionEventType` union, which T1.9, Plan-013 T1.4, and Plan-014 T1.3 widen in turn under CP-013-2 and CP-014-1. Enforced by a type-level exhaustiveness check. Cite: [Spec-005 §Event Type Summary](../specs/005-session-event-taxonomy-and-audit-log.md#event-type-summary).
- **I-004-1-02 — Event-type-string immutability.** Type strings are immutable wire identifiers; renames are forbidden once a type is registered. Enforced via build-time const-assertion + [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #8 (MINOR additive-only). Cite: [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #8.
- **I-004-1-03 — Envelope field set is fixed; serialized order is RFC 8785 lex-sort.** The `EventEnvelope` struct declares the canonical field set; RFC 8785 §3.2.3 mandates UTF-16 code-unit lex-sort serialization. Enforced via Phase 2 T2.2 golden-vector tests. Cite: [Spec-005 §Canonical Form](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-form); RFC 8785 §3.2.3.
- **I-004-1-04 — `EventEnvelope.version` immutability.** Producer-set at emit; never rewritten, on read or on upgrade. Enforced via the `EventEnvelopeVersion` newtype, whose doc comment says in plain words that the version is set once at emit and never rewritten. Cite: [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #2, #6; [Spec-005 §EventEnvelope Version Semantics](../specs/005-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics).
- **I-004-2-01 — Canonical bytes are byte-stable across implementations.** T2.2 golden-vector tests + the RFC 8785 Appendix B Table 1 number-serialization conformance vectors guarantee byte-identical output for semantically-equal envelopes. Cite: RFC 8785 Appendix B (Table 1 — ECMAScript-Compatible JSON Number Serialization Samples).
- **I-004-2-02 — The canonicalizer's refusals cover the serialized tree, and its refusal order is observable.** `canonicalizer.rs` raises these refusals itself: `normalizeOccurredAt`'s four guards (a lexical shape outside RFC 3339 with an uppercase `T` and a `Z` or `±HH:MM` offset; sub-millisecond precision the canonical form cannot hold, refused rather than truncated because truncation would silently change the recorded timestamp; a lexically-valid but non-existent calendar date; and an offset fold landing outside the four-digit-year range, in both directions), `assertRepresentableSequence` (a `sequence` outside the IEEE-754 safe-integer range, where distinct sequences collapse onto one double — the number form RFC 8785 serializes — and two different events could share one position in a log whose sequence is its order key), and the `CANONICAL_JSON_MAX_DEPTH` ceiling (a bound of the product's own on any value a caller hands `canonicalizeJson`). What a JavaScript canonicalizer must refuse besides, the types rule out: a `serde_json::Value` is a tree of owned nodes holding only valid UTF-8 text, so it carries no cycle, no caller code that could serialize differently on a later call, no `NaN` or infinity and no unpaired surrogate, and `serde_json` refuses a lone surrogate escape at parse. **Which refusal sits on which entry point is forced by RFC 8785 conformance, not a placement choice:** the sequence refusal is event-only because Appendix B Table 1 lists unsafe integers as inputs with MANDATED outputs, so a generic unsafe-number refusal would fail the very specification this module implements; the `occurredAt` guards are reachable on two surfaces — inside `canonicalizeEvent`'s projection and through the public `normalizeOccurredAt` T3.1's append path calls directly. **The first refusal to fire is the only one a caller sees, so the order IS the diagnostic:** `canonicalizeJson` runs the depth ceiling, then the serializer; `canonicalizeEvent` runs sequence → `occurredAt` → the depth ceiling. The append path never canonicalizes an event: it calls `normalizeOccurredAt` alone, so this order binds the callers that keep canonical bytes, not the append. Two residuals are characterized rather than closed: `assertRepresentableSequence` re-checks no schema domain rule, so a negative-but-safe `sequence` passes here and is refused at the parse boundary alone; and T1.8's `sourceEpoch` / `sourcePosition` pair rides inside `payload` as untyped JSON, carrying the identical collapse hazard with the parse boundary as its only enforcement. Enforced in `canonicalizer.rs` (T2.1); every family is pinned by T2.2's golden-vector tests, whose dedicated precedence tests fix the order. Cite: RFC 8785 §3.2.2.2 (the lone-surrogate MUST-terminate obligation) + Appendix B Table 1 (the mandated unsafe-number outputs that forbid a generic sequence refusal); [Plan-004 §Cross-Plan Obligations](./004-session-event-taxonomy-and-audit-log.md#cross-plan-obligations) (CP-004-1 — the generic entry point's refusals as guarantees to every caller, the over-deep and ill-formed refusals caught and mapped to distinct rejection reasons with only the policy ceiling raisable).
- **I-004-3-01 — The append path is the sole write path for `content_payload`, and the column is unconstructible for `eventMaintenance`.** The column's newtype output is constructible only on the append path, and the discriminated union on `RawEventInput` denies this column to `eventMaintenance` — the category's rows sit on the sentinel session, which no purge removes, so a body there would be a body no purge could remove. Enforced by the type system plus T3.5's type-level assertion; falsified by a compile that accepts either construction.
- **I-004-4-01 — A read after a cursor neither skips nor repeats a row.** `readAfterCursor` returns only rows with `sequence` greater than the cursor's position, in ascending order, and its `nextCursor` resumes exactly after the last row it returned, so the session stream's handoff from catching up to following has no duplicate and no gap. Enforced in `EventLogService.readAfterCursor` (`crates/sidekicks-daemon/src/events/log_service.rs`); verified by T4.1's tests. Cite: [Spec-005 §Interfaces And Contracts](../specs/005-session-event-taxonomy-and-audit-log.md#interfaces-and-contracts); [Spec-005 §Fallback Behavior](../specs/005-session-event-taxonomy-and-audit-log.md#fallback-behavior).

## Parallelization Notes

- Contracts (envelope + taxonomy + error codes) block all daemon work; author first.
- The canonicalizer requires contracts only, and its golden vectors pin its output.
- The session purge and the `EventLogService` reads can proceed in parallel once the append path is stable.

## Test And Verification Plan

- RFC 8785 JCS golden-vector conformance tests (standard vectors + project-specific edge cases: null-vs-absent, nested object ordering, numeric canonicalization, millisecond-precision `occurredAt`).
- Version-stub round-trip: an unknown-MAJOR event is persisted verbatim; the log row's `.version` remains the producer's original; on upgrade a receiver that knows the type reads the stub's preserved bytes as that event without rewriting the row.
- Purge tests: `Delete old data` on an archived or closed session deletes every row of that session, and records one `session.event.compacted` on the sentinel session. Background jobs change no row a person can see: the repack after each purge reports `page_count × page_size` and `freelist_count` before and after.
- Catch-up read tests: `readWindow` is bounded.
- End-to-end lifecycle: session.created → 50+ events → archive → purge deleting its rows → no row of the purged session remains, no byte of its words or bodies is left in the database or write-ahead-log files, and the other sessions' rows are unchanged.
- Content-column tests (Phase 3B): a row with a machine-authored body and a row without one each land the column and payload members they owe and no others; a long body is stored whole with its full `contentLength`; and the read projection never fabricates an empty body on an unavailable row.

## Rollout Order

1. Land envelope contracts + taxonomy enum + error-contract version codes (Phase 1).
2. Enable the canonicalizer (Phase 2 — depends on step 1).
3. Enable the durable append path (T3.1) + the purge's row deletion (Phase 3 — depends on step 2).
4. Enable catch-up reads (Phase 4 — depends on step 3).
5. Enable the durable home for machine-authored prose — the `content_payload` column and its write on the append path, its tests, and the hydrated read path (Phase 3B, T3.4 → T3.5 → T3.6 in that order). **Depends on step 3 and on nothing later**: it extends the durable append path T3.1 owns, and is listed last without having to follow step 4 — it may be built before or after it. Within the supplement the order IS binding: T3.5 tests a column T3.4 creates, and T3.6 reads the column T3.4 writes.

## Rollback Or Fallback

- If a new envelope MAJOR regresses, freeze new event-category adoption; [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #5 version-stub behavior keeps older readers consuming the log as opaque rows until the rollback lands.
- If the purge's row deletion regresses (wrong rows deleted, rows left behind), refuse purges until it is fixed — every kept session stays whole and correct without it; the repack removes nothing a person can see and keeps running.

## Risks And Blockers

- **Canonicalization drift.** Any divergence from RFC 8785 JCS (field ordering, null-vs-absent, numeric canonicalization) produces canonical bytes two honest implementations disagree on, so two readers of one event disagree on its bytes. The daemon's one canonicalizer entry point, the one exact-pinned library every Rust caller uses, and the golden-vector tests are load-bearing.
- **Category drift.** Event-type renames or category reassignments on existing wire types violate [ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #8. Enforced by the taxonomy enum + contract tests; new types are additive-only.
