## Goal

Implement the canonical append-only session-event contract — providing the register-and-append-path infrastructure every other plan emits into.

## Scope

This plan covers the `EventEnvelope` contract and version semantics, the event taxonomy registry per [Spec-005 §Event Type Summary](../specs/005-session-event-taxonomy-and-audit-log.md#event-type-summary) (written into contracts by T1.10, Plan-014 T1.13, and Plan-015 T1.3), append-only persistence with per-session sequence allocation, the machine-authored `content_payload` column, replay reads, live subscriptions, and the audit stubs the whole-session purge leaves. It also owns the cross-cutting `sourceEpoch` + `sourcePosition` epoch-attribution payload carrier pair (the CP-003-12 registration, T1.9 — stamped and consumed by Plan-003's rollback legs; registered here because the typed payload-field shape lives in this plan's `event-envelope.ts` contract surface).

Plan-005 is the canonical emitter of `event.compacted` in `event_maintenance`; the `backup.*` types of `event_maintenance` are the backup job's ([Plan-006](./006-local-ipc-and-daemon-control.md) Phase R1). It is not the emitter of the remaining categories — see §Event Taxonomy Coverage for the ownership boundary.

## Non-Goals

- Full timeline UI rendering (Plan-011)
- The daemon's diagnostic buckets and its loopback `/metrics` endpoint ([Plan-018](./018-observability-and-failure-recovery.md))
- Emission of events owned by other plans: `session.*` lifecycle (Plan-001 — except the two `session.goal_*` events, which are Plan-014-owned per the census row below: the goal set/clear RPC surface; and the three provider-surface observations, Plan-004-normalized), `session.clock_*` (Plan-013), `policy_bundle.*` ([Plan-010](./010-approvals-permissions-and-trust-boundaries.md)'s signed policy-bundle verifier), the `backup.*` events (the backup job, [Plan-006](./006-local-ipc-and-daemon-control.md) Phase R1), the `mcp.*` governance events ([Plan-025](./025-mcp-server-configuration-and-governance.md)), `user.message` (the Plan-003 queue-submit surface), and the provider-surface `run.*`/`usage.*` additions (Plan-004 normalizer per the census rows below)
- Orchestration of the data acts — the session purge, `Export all data` and `Erase all data` of [Spec-020](../specs/020-data-retention-and-gdpr.md) (Plan-005 provides the append path and the stub builder the purge calls)
- Signed policy-bundle loading and verification ([Plan-010](./010-approvals-permissions-and-trust-boundaries.md) owns the verifier and emits the `policy_bundle.*` events; Plan-005 registers the types only)

## Content Payload Column (Machine-Authored Prose)

Plan-005 owns the read/write semantics for `session_events.content_payload BLOB`, which this plan creates rather than inherits. Phase 3B builds it.

The append path (`event-log-service.ts`) writes the column in the statement that writes the row. A body over the bound below is truncated to it; a body of 1 KiB or more is then compressed with raw deflate at level 6, and a smaller body is stored as it is, the encoding recorded in the payload. The column is plain, like every other column.

Two write-path rules hold:

- **Sole write path.** The append path is the only route by which `content_payload` bytes are constructed; callers MUST NOT produce them anywhere else, so the truncation and compression rules have one home. The content members `contentLength` and `contentTruncated` are set by this write alone, under an internal guard on the append path that is not a wire code.
- **`event_maintenance` carries no `content_payload`.** The discriminated-union type on `RawEventInput` makes this column unconstructible for that category, because I-005-3-01 ([§Invariants](#invariants)) makes the category never stubbed, so a body on such a row would be a body no mechanism in this plan may ever remove.

**Read path.** Two cases, and in **neither** is `payload` mutated. The reader returns a **`HydratedSessionEvent`**: the event exactly as stored, paired with the closed two-arm `content` union T3.6 declares. (1) `content_payload IS NULL` — `content` takes the **unavailable** arm with its reason: `absent`, there was never a body, or the row was stubbed when its session was deleted; it never fabricates an empty body, because an empty body reads as "the assistant said nothing" and that is a different and false claim. (2) Non-NULL — `content` takes the **available** arm carrying the body beside the `contentLength` / `contentTruncated` the payload already states. Case (1) is the condition the canonical-transcript fold reports as `'turn_content_unavailable'` ([Spec-005 §Session Lifecycle](../specs/005-session-event-taxonomy-and-audit-log.md#session-lifecycle-session_lifecycle)). **Merging the body into `payload` is prohibited, not merely undesirable**: the body-bearing `SessionEventSchema` variants T3.6 registers are strict and declare no body member, so a merge would add an undeclared member that fails validation. T3.8's `content-read.ts` is bound by the same rule.

**Bound.** The append path enforces `CONTENT_PAYLOAD_PLAINTEXT_MAX = 262144` bytes of UTF-8 per body, truncating an over-bound body at a codepoint boundary and setting `contentTruncated: true` in `payload` while `contentLength` keeps the **pre-truncation** length. It truncates rather than refusing: refusing the append would drop the turn, which is a worse and less honest outcome than storing a prefix that says it is one. No sentinel character is written into the text. The fold reports the prefix as `'turn_content_truncated'`.

## Erasure Paths Cross-References

Plan-005's part in the data acts of [Spec-020](../specs/020-data-retention-and-gdpr.md):

- **A purge leaves nothing readable.** A purge stubs the session's rows with SQLite's `secure_delete` on, in one transaction, so the freed pages hold nothing readable, and checkpoints the write-ahead log with `TRUNCATE` once the delete commits; `Erase all data` deletes the app's credential-store items and the store (CP-005-12).
- **Data acts record no user event.** A session's purge (`Delete old data`) is recorded as `session.purge_requested` then `session.purged`, and its rows become audit stubs through T3.2's stub builder, deleted with `secure_delete` on and checkpointed with `TRUNCATE` after commit ([Spec-020 §Ordering And Atomicity](../specs/020-data-retention-and-gdpr.md#ordering-and-atomicity)); `Export all data` writes one line to the diagnostic log; `Erase all data` leaves no log to write into ([Spec-005 §Data Acts](../specs/005-session-event-taxonomy-and-audit-log.md#data-acts)). Plan-005 provides the append path for the session events and the stub builder; it does not order the purge's steps.

- Unknown-MAJOR events persisted as version stubs retaining full canonical bytes per §Decision #5 (read-side behavior per §Decision #9 accept-and-stub); the row's `.version` stays the producer's original — version-stubbing never rewrites the canonical row.
- Unknown-MINOR optional fields and enum values preserved verbatim for future upcasting per [Spec-005 §EventEnvelope Version Semantics](../specs/005-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics) + [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #8 (MINOR additive-only) composed with §Decision #6 (upcaster chain on read).
- An app outside its service's version range gets `DaemonHelloAck { compatible: false, reason }` with `version.floor_exceeded` or `version.ceiling_exceeded` at the connection handshake, never a join-time or write-time typed error, per §Decision #4 + §Decision #10.
- Event-type registry extensions within the same envelope MAJOR are additive-only per §Decision #8 — event-type renames are explicitly forbidden because readers dispatch on the name.

Reentrancy is owner-scoped via an `AsyncLocalStorage` (`node:async_hooks`) context carrying the held-lock token: an `append` issued inside a `withSessionAppendLock` critical section runs in that same async context, reads the token, and reuses the hold rather than re-acquiring (so the emitter's wrap never self-deadlocks); ANY caller outside that context — including same-session concurrent work on a different async chain — sees no token and blocks until release. **Release-on-settle is unconditional:** the hold releases in a `finally` owned by the frame that ACQUIRED it: an acquiring `critical` that REJECTS releases the hold and propagates the rejection unchanged, with the `AsyncLocalStorage` held-lock token torn down on the same settle path so a rejected acquisition can never leave a stale token visible to a later same-context call; a REENTRANT frame that rejects propagates the rejection unchanged WITHOUT releasing the hold or touching the token — only the acquiring frame settles the physical hold, so an outer owner that CATCHES an inner rejection and continues still holds the lock, its next nested call is still recognized as reentrant, and the hold releases exactly once when the owner frame settles — load-bearing because `append`'s refusals throw INSIDE the critical section, so a leak-on-rejection would wedge the session unrecoverably (the module-singleton state makes the wedge process-lifetime). ## Authoring Decisions

Decisions this plan makes that the spec does not.

- **Event contracts directory placement.** Extend the top-level `packages/contracts/src/event*.ts` file that holds the concern (the list under Target Areas); a new `event-`-prefixed sibling is added only when an extension would take a file past about 900 lines. The contracts package has no `events/` subdirectory; no other plan adopts a subdirectory pattern.
- **JCS library: vendor vs in-house.** Vendor — `canonicalize` package (Erdtman's RFC 8785 reference implementation; ships with the RFC). T2.3 lifts the RFC 8785 Appendix B Table 1 number-serialization vectors verbatim as a sub-suite to catch version-drift bugs. In-house implementation rejected per ECMA-262 ToString edge-case risk.
- **Golden-vector storage: inline hex vs JSON fixture.** Inline hex strings in the test file. Matches crypto-paseto convention (the `packages/crypto-paseto/src/internal/v4-local-deterministic.ts#encryptV4LocalDeterministic` golden-token tests in `packages/crypto-paseto/src/__tests__/v4-local.test.ts`); PR-diff is the audit trail for byte-stable artifacts.
- **Audit-stub representation: column add vs payload discriminator.** New `session_events.retention_class TEXT` column. Partial index `WHERE retention_class IS NULL` keeps hot-path replay queries fast; explicit column makes stub state visible at row inspection; category-exclusion enforcement easier with typed column than JSON-field probe.
- **`summary` generation rule.** T3.2's stub builder generates `summary` from the original payload ([Spec-005 §Compacted Event Format](../specs/005-session-event-taxonomy-and-audit-log.md#compacted-event-format)).
- **Live-stream gap detection mechanism.** Sequence-number monotonicity check in the SDK's `EventClient.subscribe` (Option (b)) as canonical gap-detection; SSE reconnect via `Last-Event-ID` header (Option (a)) as reconnect path. No cursor-carrying heartbeat (Option (c)) is needed: when a screen that fell behind has caught up on its queue, the daemon sends it one frame with no changes, carrying the drop mark and the newest cursor, so a session that goes quiet right after a drop still tells the screen it is behind.

## Cross-Plan Obligations

Each obligation gets a CP-005-N ID. One Plan-003-facing seam is body-registered rather than CP-rowed, per the T3.1 `withSessionAppendLock` publication precedent: the T1.9 `sourceEpoch` + `sourcePosition` carrier pair (the CP-003-12 registration — the obligation ledger is Plan-003's row).

- **CP-005-3 — T2.1's canonicalizer is the workspace's one RFC 8785 implementation.** Phase 2 T2.1's `canonicalizeEvent` + `canonicalizeJson` are the single source of truth for RFC 8785 JCS; any plan that needs canonical JSON bytes MUST consume them — never re-implement or fork. **The generic entry point is BOUNDED, not unlimited. It carries refusals of different KINDS, and each is a guarantee to every caller:** (i) the **policy ceiling** — `canonicalizeJson` refuses any value nesting containers past a fixed ceiling (`CANONICAL_JSON_MAX_DEPTH`, 64), a stack-overflow guard, since the pinned `canonicalize@3.0.0` recurses once per nesting level with no guard of its own; (ii) the **RFC-mandated refusal** — `canonicalizeJson` refuses any string value or property name carrying an unpaired UTF-16 surrogate, because RFC 8785 §3.2.2.2 makes terminating on such data a normative MUST while the pinned `canonicalize@3.0.0` escapes it through `JSON.stringify` and keeps going, emitting bytes no conforming verifier will ever reproduce; and (iii) the **determinism refusal** — `assertNoToJsonOverride` refuses any value carrying a callable `toJSON` at any depth, a `toJSON` being arbitrary caller code that need not return at verification time what it returned at signing time. (i) is checked first, and that order is a correctness constraint rather than a diagnostic preference — the depth walk is what makes the later walks terminate on cyclic input — so a value defective in more than one way reports the over-deep refusal and never another. Three consequences for any caller that feeds the entry point a value from outside the process, one deliverable each: (1) a **registered rejection reason** for an over-deep value; (2) a **distinct** registered rejection reason for an ill-formed one — (1) and (2) MUST NOT collapse into a single reason, an over-deep value and an ill-formed one being different client errors whose merger destroys the diagnostic (every refusal is a plain throw at T2.1, so each is caught and mapped at the caller's boundary, never surfaced raw to a remote party); and (3) the **depth ceiling ONLY** can be raised — a ceiling that proves too tight for a real payload is **raised in T2.1's constant**, never escaped by forking the canonicalizer. **(3) does not extend to (ii) or (iii).** The well-formedness refusal is a normative MUST-terminate — never raised or relaxed in either direction, since relaxing it violates RFC 8785 — so catch-and-map per (2) is the only available response there; the determinism refusal is what lets re-canonicalizing a value reproduce the bytes that were signed, so it is never relaxed either. A value that arrives through `JSON.parse` can never trip (iii): parsed output carries no function-valued member — a wire `{"toJSON":"x"}` parses to a STRING, and `"__proto__"` parses as an ordinary own data property rather than a prototype mutation — so the predicate is unsatisfiable on parsed input. A value a caller CONSTRUCTS in process (an object literal carrying a `Date`, a `Buffer`, or any class instance with a `toJSON`) meets a live refusal.

Cite: [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #8.
- **I-005-1-03 — Envelope field set is fixed; serialized order is RFC 8785 lex-sort.** The Zod schema declares the canonical field set; RFC 8785 §3.2.3 mandates UTF-16 code-unit lex-sort serialization. Enforced via Phase 2 T2.3 golden-vector tests. Cite: [Spec-005 §Canonical Form](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-form); RFC 8785 §3.2.3.
- **I-005-1-04 — `EventEnvelope.version` immutability.** Producer-set at emit; never rewritten on read (upcaster chain mutates in-memory representation only). Enforced via `EventEnvelopeVersion` brand + JSDoc cite to [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #2/#6. Cite: [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #2, #6; [Spec-005 §EventEnvelope Version Semantics](../specs/005-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics).
- **I-005-2-03 — Canonical bytes are byte-stable across implementations.** T2.3 golden-vector tests + the RFC 8785 Appendix B Table 1 number-serialization conformance vectors guarantee byte-identical output for semantically-equal envelopes. Cite: RFC 8785 Appendix B (Table 1 — ECMAScript-Compatible JSON Number Serialization Samples).
- **I-005-2-09 — The canonicalizer's refusals cover the serialized tree, and its refusal order is observable.** `canonicalizer.ts` raises these refusals itself: `normalizeOccurredAt`'s four guards (a lexical shape outside RFC 3339 with an uppercase `T` and a `Z` or `±HH:MM` offset; sub-millisecond precision the canonical form cannot hold, refused rather than truncated because truncation would silently change the recorded timestamp; a lexically-valid but non-existent calendar date, caught by reading the fields back after the setters roll them over; and an offset fold landing outside the four-digit-year range `toISOString` renders, in both directions), `assertRepresentableSequence` (a `sequence` outside the IEEE-754 safe-integer range, where distinct sequences collapse onto one double and two different events could share one position in a log whose sequence is its replay key), the `CANONICAL_JSON_MAX_DEPTH` ceiling (a stack-exhaustion guard — the exact-pinned `canonicalize@3.0.0` recurses once per nesting level with no bound of its own, and `canonicalizeJson` accepts any value a caller hands it), `assertNoToJsonOverride` (any value carrying a callable `toJSON` at any depth — arbitrary caller code that would otherwise divert the serializer onto a tree no guard inspected, and re-invoking it when a signature is checked need not reproduce the bytes that were signed), `assertWellFormedStrings` (RFC 8785 §3.2.2.2's MUST-terminate obligation over any unpaired UTF-16 surrogate in a string value or a member name — the library instead escapes it through `JSON.stringify` and emits valid-but-non-conforming text), and the no-JSON-representation guard (a top-level `undefined`, function, or symbol, for which the serializer returns no output and the encoder would otherwise hand its caller zero canonical bytes). Three further refusals originate inside `canonicalize@3.0.0` and surface with its bare wording (`NaN is not allowed`, `Infinity is not allowed`, `Circular reference detected`); they are inventoried here, not owned — and the cycle refusal is SHADOWED in both shapes that could reach it: the depth walk drives an own-property cycle past the ceiling and reports it as depth exhaustion first, and a cycle closed only through a `toJSON` result is refused by `assertNoToJsonOverride` one guard later, before any serialization runs. What survives of it is the non-idempotent-accessor residual below, not a live path. **Which refusal sits on which entry point is forced by RFC 8785 conformance in both directions, not a placement choice:** well-formedness is generic because §3.2.2.2 obliges it for every string in every input, member names included, while the sequence refusal is event-only because Appendix B Table 1 lists unsafe integers as inputs with MANDATED outputs, so a generic unsafe-number refusal would fail the very specification this module implements; the `occurredAt` guards are reachable on two surfaces — inside `canonicalizeEvent`'s projection and through the exported `normalizeOccurredAt` T3.1's append path calls directly — and the no-JSON-representation guard is generic in effect as well as in placement, unreachable through `canonicalizeEvent`, whose top-level value is always the projection object and therefore always serializes (the guard fires on a top-level `typeof canonicalText !== "string"`, which the library returns only where it delegates to `JSON.stringify` for a non-object). **The first refusal to fire is the only one a caller sees, so the order IS the diagnostic:** `canonicalizeJson` runs the depth ceiling → the `toJSON` refusal → well-formedness → whatever the serializer itself refuses (the three library throws fire inside that call, ahead of the last guard) → no-JSON-representation, and `canonicalizeEvent` runs sequence → `occurredAt` → the three it inherits, in that same relative order. Depth-FIRST is a CORRECTNESS constraint rather than a diagnostic preference: neither of the two walks behind it carries cycle detection or a bound of its own, and it is the depth walk — which reports a cycle as depth exhaustion — that makes both terminate on cyclic input at all, so demoting it turns a refusal into a hang. The `toJSON` refusal's own position, between the ceiling and well-formedness, is a correctness constraint too and in the other direction: placed any later it would be walking a tree the well-formedness guard had already been diverted away from. **The refusals reach the serialized tree, and one residual keeps that from being unconditional.** `assertNoToJsonOverride` closes the wider of the two bypasses this invariant scopes itself around: without it, a shallow object whose `toJSON` returned a deeper or ill-formed tree would clear every guard and be serialized anyway. The guard tests `typeof node.toJSON === "function"` down the whole prototype chain rather than `Object.hasOwn`, deliberately — an inherited `toJSON` diverts the serializer exactly as an own one does. **It REFUSES rather than inspecting the diverted output, and non-determinism is why:** a `toJSON` is arbitrary caller code re-invoked on every canonicalization, so the same value can serialize to different bytes at signing time and at verification time, and a signature over canonical bytes turns on re-canonicalizing the value and comparing bytes — a guard that walked the `toJSON` RESULT would still have to assume the serializer later saw that same result. Depth-ceiling evasion and §3.2.2.2 evasion are the second and third motivations, both subsumed by refusing the carrier outright. **The surviving residual is the non-idempotent ACCESSOR.** The depth walk's `Object.values` invokes each own enumerable getter once, `assertNoToJsonOverride`'s a second time, `assertWellFormedStrings`' `Object.entries` a third, and the serializer again per object member, so a getter returning different values across them puts the guard walks and the serializer on different trees, and is the only remaining way to hand the serializer a tree no guard inspected. It is unreachable for a value that arrives through `JSON.parse` — parsed output carries neither accessors nor a callable `toJSON`, the latter because a parsed `{"toJSON":"x"}` yields a STRING — which is what makes the scoped claim load-bearing rather than weak. The over-refusal direction stays harmless by construction: a dropped `undefined` or symbol member's NAME is still checked, and an array's non-index own enumerable properties are walked. Beyond that accessor residual, three more are characterized rather than closed: nothing upstream refuses ahead of this module on the well-formedness axis (`EventEnvelopeSchema` admits lone surrogates in `actor`, `correlationId`, `causationId`, and in `payload` keys and values alike, so the canonicalizer is the first and only refusal on that path); `assertRepresentableSequence` re-checks no schema domain rule, so a negative-but-safe `sequence` passes here and is refused at the parse boundary alone; and T1.9's `sourceEpoch` / `sourcePosition` pair rides inside `payload` as untyped JSON, carrying the identical collapse hazard with the parse boundary as its only enforcement. Enforced in `canonicalizer.ts` (T2.1); every family is pinned by T2.3's `canonicalizer.golden.test.ts`, whose dedicated precedence tests fix the order. Cite: RFC 8785 §3.2.2.2 (the lone-surrogate MUST-terminate obligation) + Appendix B Table 1 (the mandated unsafe-number outputs that forbid a generic sequence refusal); [Plan-005 §Cross-Plan Obligations](./005-session-event-taxonomy-and-audit-log.md#cross-plan-obligations) (CP-005-3 — the generic entry point's refusals as guarantees to every caller, the over-deep and ill-formed refusals caught and mapped to distinct rejection reasons with only the policy ceiling raisable).
- **I-005-3-01 — `event_maintenance` is never stubbed.** `event_maintenance` events are never stubbed; only `Erase all data`, which deletes the whole store, removes them — stubbing `event.compacted` would destroy the record of the purge it describes. Enforced by the purge's stub selector, which excludes the category (T3.2); T3.5's purge E2E covers it (a purge spares the never-stubbed category). The category also cannot carry `content_payload` (I-005-3-05). - **I-005-4-04 — An audit read of a deleted session's retained rows returns audit stubs, never silent omission.** `readAfterCursor` / `readWindow` return all sequence positions; a stubbed position carries `payload.retentionClass === 'audit_stub'`. Only the whole-session purge writes stubs, so no live session's read meets one. T4.3 and T4.9 tests assert. Cite: [Spec-005 §Fallback Behavior](../specs/005-session-event-taxonomy-and-audit-log.md#fallback-behavior); [Spec-005 §Replay Interaction with Compacted Regions](../specs/005-session-event-taxonomy-and-audit-log.md#replay-interaction-with-compacted-regions).
- **I-005-4-05 — `EventSubscription` replay-then-live cursor handoff is monotonic.** Strict sequence order; no duplicate at boundary; no gap at boundary. T4.5 test verifies. Cite: [Spec-005 §Interfaces And Contracts](../specs/005-session-event-taxonomy-and-audit-log.md#interfaces-and-contracts); [Spec-005 §Fallback Behavior](../specs/005-session-event-taxonomy-and-audit-log.md#fallback-behavior).

## Test And Verification Plan

- RFC 8785 JCS golden-vector conformance tests (standard vectors + project-specific edge cases: null-vs-absent, nested object ordering, numeric canonicalization, millisecond-precision `occurredAt`).
- Version-stub round-trip: an unknown-MAJOR event is persisted verbatim; the log row's `.version` remains the producer's original; an upcaster chain re-interprets on upgrade without rewriting the row.
- Purge stub tests: `Delete old data` on an archived or closed session stubs every row, and records one `event.compacted` on the sentinel session; `event_maintenance` rows are never stubbed; the audit-stub format preserves envelope-level fields (id, sessionId, sequence, occurredAt, category, type, actor). Background jobs change no row a person can see: the repack after each purge reports `page_count × page_size` and `freelist_count` before and after.
- Replay tests: `EventReadAfterCursor` surfaces `retentionClass: 'audit_stub'` for a deleted session's stubbed rows; `EventReadWindow` is bounded.
- End-to-end lifecycle: session.created → 50+ events → archive → purge stubbing its rows → every `content_payload` of the purged session is NULL, no byte of its words or bodies is left in the database or write-ahead-log files, and the other sessions' rows are unchanged.
- Content-column tests (Phase 3B): a row with a machine-authored body and a row without one each land the column and payload members they owe and no others; the bound cuts at a codepoint boundary with `contentTruncated: true` beside a PRE-truncation `contentLength` and no sentinel in the text, while a complete body OMITS the marker entirely; the stub write NULLs `content_payload` and preserves `contentLength` / `contentTruncated`; both byte-accounting statements count the column, proven by a storage-threshold pass that fires on content-heavy rows whose `payload` columns alone are far under the threshold and does NOT fire on the same rows without their bodies; and the read projection never fabricates an empty body on any unavailable path.

## Rollout Order

1. Land envelope contracts + taxonomy enum + error-contract version codes (Phase 1).
2. Enable the canonicalizer (Phase 2 — depends on step 1).
3. Enable the durable append path (T3.1) + the purge's stub builder (Phase 3 — depends on step 2).
4. Enable replay reads and live subscription catch-up (Phase 4 — depends on step 3).
5. Enable the durable home for machine-authored prose — the `content_payload` column and its write on the append path, the stub-write and byte-accounting legs, and the hydrated read path (Phase 3B, T3.6 → T3.7 → T3.8 in that order). **Depends on step 3 and on nothing later**: it extends the durable append path T3.1 owns, and is listed last without having to follow step 4 — it may be built before or after it. Within the supplement the order IS binding: T3.7 clears a column T3.6 creates, and T3.8 reads the column T3.6 writes.

## Rollback Or Fallback

- If a new envelope MAJOR regresses, freeze new event-category adoption; [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #5 version-stub behavior keeps older readers consuming the log as opaque rows until the rollback lands.
- If the purge's stubbing regresses (audit stubs malformed, wrong categories stubbed), refuse purges until it is fixed — every kept session stays whole and correct without it; the repack removes nothing a person can see and keeps running.

## Risks And Blockers

- **Canonicalization drift.** Any divergence from RFC 8785 JCS (field ordering, null-vs-absent, numeric canonicalization) produces canonical bytes two honest implementations disagree on, so a `machineSignature` over them fails to verify. A single shared canonicalizer implementation plus golden-vector tests are load-bearing.
- **Category drift.** Event-type renames or category reassignments on existing wire types violate [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #8. Enforced by the taxonomy enum + contract tests; new types are additive-only.
- **Invariant enforcement regressions.** If the stub builder ever mis-categorizes an `event_maintenance` event, the invariant is violated silently. Enforced by the stub selector's category exclusion, which T3.5's purge E2E covers, and by the type that denies the category a `content_payload`.
