## Goal

Implement the canonical append-only session-event contract, its tamper-evident integrity protocol, and the PII-column indirection — providing the register-and-append-path infrastructure every other plan emits into.

## Scope

This plan covers the `EventEnvelope` contract and version semantics, the event taxonomy registry per [Spec-005 §Event Type Summary](../specs/005-session-event-taxonomy-and-audit-log.md#event-type-summary) (written into contracts by T1.10, Plan-014 T1.13, and Plan-015 T1.3), append-only persistence with BLAKE3 hash chain and Ed25519 signatures over RFC 8785 JCS canonical bytes, Merkle anchor emission into the shared `event_log_anchors` table (metadata only per [ADR-017](../decisions/017-shared-event-sourcing-scope.md)), the PII-column indirection pattern (`pii_payload` ciphertext + `pii_ciphertext_digest`), replay reads, live subscriptions, and the audit stubs the whole-session purge leaves. It also owns the cross-cutting `sourceEpoch` + `sourcePosition` epoch-attribution payload carrier pair (the CP-003-12 registration, T1.9 — stamped and consumed by Plan-003's rollback legs; registered here because the typed payload-field shape lives in this plan's `event.ts` contract surface).

Plan-005 is the canonical emitter of the `audit_integrity` category and of `event.compacted` in `event_maintenance`; the `backup.*` types of `event_maintenance` are the backup job's ([Plan-006](./006-local-ipc-and-daemon-control.md) Phase R1). It is not the emitter of the remaining categories — see §Event Taxonomy Coverage for the ownership boundary.

## Non-Goals

- The daemon's diagnostic buckets and its loopback `/metrics` endpoint, the audit-integrity families included ([Plan-018](./018-observability-and-failure-recovery.md))

- Orchestration of the data acts — the session purge, `Export all data` and `Erase all data` of [Spec-020](../specs/020-data-retention-and-gdpr.md) (Plan-005 provides the append path and the stub builder the purge calls)
- Signed policy-bundle loading and verification ([Plan-010](./010-approvals-permissions-and-trust-boundaries.md) owns the verifier and emits the `policy_bundle.*` events; Plan-005 registers the types only)

### Bootstrap Wiring

The bullets above name the file each service lives in. This subsection names who **constructs** each one in production, so a reader cannot mistake a built module for a running one; wiring another task owns is named with that task.

- **`packages/runtime-daemon/src/bootstrap/index.ts` is the daemon's only composition root.** It loads the Spec-024 secure-defaults config, exposes the pre-bind assertion Plan-006 gates listener binds on (I-006-1), and constructs every Phase-3 daemon service; the T3.1/T4.2 events wiring described in the `bootstrap/index.ts` bullet above is **T4.2's edit (F-005-HALT-04)**, and each bullet below names who calls the service it constructs.
- **`EventLogService` (T3.1)** — production construction is T4.2's. Its `haltSource` dependency is optional and defaults to the vacuous `NeverHaltedIngestHaltSource`, a deliberate **fail-OPEN** default: until T4.2 passes the `IngestHaltRegistry`, no halt is observable and every session is admitted. Its `contentKeys` — the T3.6 `SessionContentKeyStore` that seals both partitions of every event — is likewise composition-root-injected per CP-005-1.
- **`IngestHaltRegistry` (T3.1)** — the production halt-state carrier, constructed by T4.2's edit. Its halted set is populated by T4.2's key-reuse observer in the registry → service → observer construction order that same T4.2 edit owns.
- **`Compactor` (T3.2)** — `tick`'s production caller is the service's one scheduler, which runs every background job and runs this one hourly when no purge is running; the tick retires unused session content keys and changes no row a person can see. The stub builder's caller is the whole-session purge (`daemon.retentionPurge`, [Plan-006](./006-local-ipc-and-daemon-control.md) Phase R1). The sentinel-key gate stays: a stubbing pass probes the daemon-scope sentinel session's signing key before mutating any row and refuses with zero rows mutated when it is unresolvable, so **stubbing stays inert until CP-005-7 provisions that key** — which makes the stub builder a SECOND consumer of the sentinel-key provisioning precondition, beside T4.2's `key_reuse_detected` emitter.
- **`MerkleAnchorService` (T3.3)** — constructed by the composition root. Its callers are the append path, whose `onEventAppended` call after each committed row drives the anchoring cadence, and the purge stub builder's anchor-before-stub force-fire through the injected anchor seam; the upload leg depends on the credential provider below, so the durable partition queue drains once Plan-016's credential provider is wired.
- **`DaemonCredentialProvider` (T3.3, CP-005-13)** — an interface Plan-005 declares; the implementation and its composition-root wiring are Plan-016's PASETO work (decomposed as Plan-016 T5.4–T5.7); without them every credentialed leg (anchor upload, T4.2's roster read and T4.10's registrar; the seam's full consumer set is live-plus-forward-declared per CP-005-13) is unreachable by construction rather than by flag.
- **Control-plane `event-anchors/` (T3.3).** `createEventAnchorRouter` is mounted into the namespaced control-plane router on the control-plane `host.ts`, meeting CP-005-2, and `EventLogAnchorStore` is constructed there over that host's `Querier`.

## Data And Storage Changes

- Implement read/write semantics for the `session_events` columns Plan-001 creates per [Plan-001 §Cross-Plan Schema Ownership](./001-session-core.md#cross-plan-schema-ownership): `monotonic_ns`, `prev_hash`, `row_hash`, `daemon_signature`, `pii_payload`, plus the payload-embedded `pii_ciphertext_digest` field.
- Add `session_events.content_payload` (BLOB, nullable) — the durable encrypted home for **machine-authored** prose: the assistant message body, the reasoning-update body, and tool-call arguments / result / error bodies . Plan-005 adds it to the daemon's one schema in Phase 3B, unlike the Plan-001 list above. It is a **sibling of `pii_payload`, not a widening of it**: both columns are sealed AES-256-GCM under the session's one content key and partition one row's text by authorship — `pii_payload` what the person wrote, this column what the machine wrote — told apart by their associated data, `session_id || event_id` here and `session_id || "ais.session-pii.v1" || event_id` there, so neither column's ciphertext authenticates as the other's. Excluded from the canonical bytes, committed to by the payload-embedded `contentCiphertextDigest`, and carrying **no column naming its key** — `session_id` is already a canonical signed member, so the key's binding is signed already and a second column would restate it. NULL on every row with no machine-authored body, and NULL **by construction** on every `audit_integrity` / `event_maintenance` row. ## Integrity Protocol

Plan-005 implements the tamper-evidence protocol defined in [Spec-005 §Integrity Protocol](../specs/005-session-event-taxonomy-and-audit-log.md#integrity-protocol).

### Canonical Serialization

Per [Spec-005 §Canonical Serialization Rules](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules):

- Canonicalization: [RFC 8785 JSON Canonicalization Scheme (JCS)](https://datatracker.ietf.org/doc/html/rfc8785). Phase 2 T2.1's canonicalizer is the daemon's one implementation of it (CP-005-3).
- Hash function: [BLAKE3](https://github.com/BLAKE3-team/BLAKE3-specs/blob/master/blake3.pdf) for both the hash-chain digest and the `pii_ciphertext_digest`.
- Signature scheme: [RFC 8032 §5.1 — Ed25519](https://datatracker.ietf.org/doc/html/rfc8032#section-5.1).
- Fields included (the canonical set — membership only; serialized order is mandated by RFC 8785 §3.2.3 UTF-16 code-unit lex-sort of member names, NOT the order listed here): `id`, `sessionId`, `sequence`, `occurredAt`, `category`, `type`, `actor`, `payload`, `correlationId`, `causationId`, `version`.
- Present-but-null fields are serialized as `null`, not omitted — "absent" vs "present-but-null" are wire-distinguishable.
- `occurredAt` is RFC 3339 UTC with millisecond precision (`YYYY-MM-DDTHH:MM:SS.sssZ`) so ordering is byte-stable.
- `pii_payload` is NOT in the canonical form. Events with non-NULL `pii_payload` embed `pii_ciphertext_digest` inside `payload` (and `payload` IS canonical) so the signature commits to a one-way digest of the ciphertext.

### Hash Chain

Every `session_events` row:

- `prev_hash` = `row_hash` of the immediately-prior row for the same `session_id` (genesis row uses 32 zero bytes as `prev_hash`).
- `row_hash` = `BLAKE3(prev_hash || canonical_bytes(row))`.

Verification: recompute `canonical_bytes(row)`, recompute `BLAKE3(prev_hash || canonical_bytes(row))`, compare to the stored `row_hash`. Mismatch halts replay at the offending sequence and surfaces `audit_integrity_failed` with `failureMode = 'hash_mismatch'`.

### Ed25519 Signatures

- `daemon_signature` = `Ed25519(daemon_signing_key, canonical_bytes(row))`.
- Verification uses the `NodeId`-resolved public key from the session verification-key roster per [Security Architecture §Audit Log Integrity](../architecture/security-architecture.md#audit-log-integrity).

### Merkle Anchor Emission

Per [Spec-005 §Anchoring Cadence](../specs/005-session-event-taxonomy-and-audit-log.md#anchoring-cadence):

- Anchors fire on the earlier of `ANCHOR_INTERVAL_EVENTS = 1000` events OR `ANCHOR_INTERVAL_SECONDS = 300` seconds since the previous anchor.
- Anchor payload = `(session_id, node_id, start_sequence, end_sequence, merkle_root, root_signature, anchored_at)` — metadata only.
- `root_signature` = `Ed25519(daemon_signing_key, anchor_claim)` — same daemon key used for row signatures, over the RFC 8785 canonicalization of the five-member anchor claim `{endSequence, merkleRoot, nodeId, sessionId, startSequence}` per [Spec-005 §Anchoring Cadence](../specs/005-session-event-taxonomy-and-audit-log.md#anchoring-cadence) (a `merkle_root` alone would leave the coordinates a coverage test runs against unsigned).
- Anchors are uploaded to Postgres `event_log_anchors`; no session event payloads are sent to the control plane per ADR-017.
- Partition tolerance: if control-plane upload fails, anchors queue locally and flush on reconnect without re-signing. Local hash chain and signatures provide tamper-evidence without the anchor tier; anchors provide external cross-observer consistency.

## PII Columns

Plan-005 owns the read/write semantics for the `session_events.pii_payload BLOB` column Plan-001 creates, and for its machine-authored sibling `session_events.content_payload BLOB` and the `session_content_keys` table that holds its wrapped sealing key, both of which this plan creates rather than inherits (§Content Payload Column below).

### Encrypt-Then-Digest-Then-Sign Order

The write-path order is LOAD-BEARING for [Spec-020 §Signature Safety Under Shred](../specs/020-data-retention-and-gdpr.md#signature-safety-under-shred). Reversing any step breaks the safety proof — a signature directly over `pii_payload` ciphertext would leave signed bytes on disk after a shred, enabling length and structure attacks.

1. Extract PII fields from the in-memory event object (user messages, file paths, code snippets per [Spec-020 §PII Payload Column Pattern](../specs/020-data-retention-and-gdpr.md#pii-payload-column-pattern)).
2. Seal PII under the session's content key with AES-256-GCM: a random 96-bit IV per write, wire `iv || ciphertext || tag`, AAD = `session_id || "ais.session-pii.v1" || event_id` (key resolved through T3.6's `SessionContentKeyStore`, which mints it on the session's first write that seals a body; table at [Local SQLite Schema §Session Content Keys (Plan-005)](../architecture/schemas/local-sqlite-schema.md#session-content-keys-plan-005)). The label keeps this ciphertext from authenticating as the row's `content_payload`, which the same key seals under AAD = `session_id || event_id`. Output: `pii_ciphertext` bytes.
3. Compute `pii_ciphertext_digest = BLAKE3(pii_ciphertext)`.
4. Embed **one** member into the `payload` field: `pii_ciphertext_digest` (which bytes the row holds). The key that sealed them is the session's, which `session_id`, already a canonical signed member, names.
5. Canonicalize the envelope (per §Canonical Serialization above). `pii_payload` is excluded; the embedded digest is included because it lives inside `payload`, so the signed bytes commit to the ciphertext without carrying it.
6. Compute `row_hash = BLAKE3(prev_hash || canonical_bytes)` and `daemon_signature = Ed25519(canonical_bytes)`.
7. Persist the row: `payload` (carrying the digest), `pii_payload` (ciphertext), `row_hash`, `daemon_signature`.

The single write path is `pii-indirection.ts`; callers MUST NOT construct `pii_payload` bytes by any other route.

### Read Path

- `pii_payload IS NULL` — no decryption; return payload verbatim.
- `pii_payload` non-NULL and decryption key available — load ciphertext, open it under the session's content key, merge decrypted PII back into the payload for the authorized caller.
- `pii_payload` non-NULL and the session's content key does not open it — the master key is unavailable, the session's `session_content_keys` row is missing, or the ciphertext fails its AEAD tag — return the envelope + payload (including `pii_ciphertext_digest`) with the PII partition replaced **as a unit** by a single `<pii-unavailable>` marker at one reserved payload key, never field by field: the PII field _names_ are themselves inside the ciphertext the reader cannot open, so per-field marking would demand a schema the reader does not have. This case is a custody fault, never a shred state: no row keeps ciphertext whose key is gone (a deletion stubs the row and NULLs `pii_payload`, an erase deletes the store). Signature and hash verification remain valid because canonical bytes exclude `pii_payload`. T4.3's `replay-service.ts` implements this partition-level projection, and T3.5's purge-safety suite pins it (marker at one reserved key, plus the negative property that no plaintext byte survives the projection) against a suite-local reader. The content partition fails the same way at the same moment, through its own reason.

### Content Payload Column (Machine-Authored Prose)

`content_payload` is built by Phase 3B and reuses the Encrypt-Then-Digest-Then-Sign order above **step for step**, substituting only the associated data and the embedded member: step 2 seals under the same session content key — a random 32-byte AES-256 key generated once per session and held wrapped in `session_content_keys`, never derived from the master key — with AAD = `session_id || event_id`; step 3 computes `contentCiphertextDigest = BLAKE3(content_ciphertext)`; step 4 embeds that digest, as it embeds `pii_ciphertext_digest` for the PII partition. Steps 1, 5, 6, and 7 are unchanged, and a row carrying both columns runs the order once over both partitions rather than twice — one canonicalization per row (I-005-2-06) is not weakened by a second ciphertext.

Two write-path rules are inherited deliberately, not merely by analogy:

- **Sole write path.** `pii-indirection.ts` is extended to seal this column too, and remains the only route by which either ciphertext is constructed; callers MUST NOT produce `content_payload` bytes anywhere else. Housing both codecs in one module is the point — it is the module the digest-embedding and canonicalization order lives in, and a second sealing module would be a second place for that order to drift.
- **`audit_integrity` and `event_maintenance` carry no `content_payload`.** The same discriminated-union type on `RawEventInput` that makes `pii_payload` unconstructible for those categories (I-005-2-07) makes this column unconstructible for them, and for the same reason: [§Audit Integrity Invariant](#audit-integrity-invariant) makes those categories never stubbed, so a destroyable body on such a row would be a body no mechanism in this plan may ever destroy.

**Read path.** Three cases, mirroring §Read Path above with one difference that matters — and in **none** of them is `payload` mutated. The reader returns a **`HydratedSessionEvent`**: the verified event exactly as its signature covers it, paired with the closed two-arm `content` union T3.6 declares. (1) `content_payload IS NULL` — `content` takes the **unavailable** arm with reason `absent`; there was never a body. (2) Non-NULL, and the session content key unwraps from `session_content_keys` and opens the ciphertext — `content` takes the **available** arm carrying the plaintext body beside the `contentLength` / `contentTruncated` the signed payload already states. (3) Non-NULL and **unopenable** — the daemon master key is unavailable, the wrapped key row is missing, or the ciphertext fails its AEAD tag — `content` takes the **unavailable** arm with the reason that distinguishes those cases; it never fabricates an empty body, because an empty body reads as "the assistant said nothing" and that is a different and false claim. Case (3) is exactly the condition the canonical-transcript fold reports as `'turn_content_unavailable'` ([Spec-005 §Session Lifecycle](../specs/005-session-event-taxonomy-and-audit-log.md#session-lifecycle-session_lifecycle)); there is no case for a destroyed key, because no row keeps ciphertext whose key is gone: a purge deletes the session's content key and stubs its rows with `content_payload` NULL, and `Erase all data` deletes the store. **Merging the body into `payload` is prohibited, not merely undesirable**: the five `SessionEventSchema` variants are strict and declare no body member, so a merge would either add an undeclared member that fails validation or make an already-verified payload differ from the bytes its signature covers. T3.8's `content-read.ts` is bound by the same rule.

**Bound.** The sealer enforces `CONTENT_PAYLOAD_PLAINTEXT_MAX = 262144` bytes of UTF-8 plaintext, truncating an over-bound body at a codepoint boundary and setting `contentTruncated: true` in `payload` while `contentLength` keeps the **pre-truncation** length. It truncates rather than refusing: refusing the append would drop the turn, which is a worse and less honest outcome than storing a prefix that says it is one. No sentinel character is written into the text. The fold reports the prefix as `'turn_content_truncated'`.

## Erasure Paths Cross-References

Plan-005's part in the data acts of [Spec-020](../specs/020-data-retention-and-gdpr.md):

- **No row outlives its key.** A purge overwrites the session's wrapped content key with zeros, deletes it and then stubs its rows, in one transaction, and checkpoints with `TRUNCATE` after commit, so every body it leaves in freed pages is ciphertext whose key is gone; `Erase all data` destroys every custody copy of the master key and deletes the store. No signed row keeps ciphertext whose key is gone, and the binding check of I-005-2-11 needs no shred carve-out (CP-005-12).
- **Data acts record no user event.** A session's purge (`Delete old data`) is recorded as `session.purge_requested` then `session.purged`, and it deletes the session's content key before its rows (overwritten with zeros, then deleted, with a `TRUNCATE` checkpoint after commit; [Spec-020 §Ordering And Atomicity](../specs/020-data-retention-and-gdpr.md#ordering-and-atomicity)), which become audit stubs through T3.2's stub builder; `Export all data` writes one line to the diagnostic log; `Erase all data` leaves no log to write into ([Spec-005 §Data Acts](../specs/005-session-event-taxonomy-and-audit-log.md#data-acts)). Plan-005 provides the append path for the session events and the stub builder; it does not order the purge's steps.

## Audit Integrity Invariant

Events in the `audit_integrity` category (`audit_integrity_verified`, `audit_integrity_failed`, `key_reuse_detected`) **and** the `event_maintenance` category (`event.compacted`, `backup.completed`, `backup.failed`, `backup.restored`) are subject to a shared invariant:

> **These events are never stubbed. Only `Erase all data`, which deletes the whole store, removes them.**

The invariant is declared symmetrically in [Spec-005 §Audit Integrity](../specs/005-session-event-taxonomy-and-audit-log.md#audit-integrity-audit_integrity) and [Spec-005 §Event Maintenance](../specs/005-session-event-taxonomy-and-audit-log.md#event-maintenance-event_maintenance). Rationale:

- Stubbing `audit_integrity_failed` would destroy the record that a chain break was detected — a verifier could not distinguish "no failure occurred" from "the failure record was stubbed away."
- Stubbing `event.compacted` would destroy the record of the purge it describes.

Plan-005 enforces the invariant at two layers:

- The purge's stub builder (`compactor.ts`) excludes rows where `category IN ('audit_integrity', 'event_maintenance')` from the rows it stubs, and a contract test fails if a row from those categories ever reaches its selector.
- `pii-indirection.ts` refuses to write `pii_payload` for events in either category (these categories have `pii_payload = NULL` by construction — their content carries no user PII).

## Cross-Version Compatibility Surface

Plan-005 owns the `EventEnvelope` contract's integration with [ADR-018](../decisions/018-cross-version-compatibility.md):

- `.version` format `"MAJOR.MINOR"` per [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #1.
- Producer-set at emit per §Decision #2; never copied from received events.
- Unknown-MAJOR events persisted as version stubs retaining full canonical bytes per §Decision #5 (read-side behavior per §Decision #9 accept-and-stub); the row's `.version` stays the producer's original — version-stubbing never rewrites the canonical row.
- Unknown-MINOR optional fields and enum values preserved verbatim for future upcasting per [Spec-005 §EventEnvelope Version Semantics](../specs/005-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics) + [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #8 (MINOR additive-only) composed with §Decision #6 (upcaster chain on read).
- An app outside its service's version range gets `DaemonHelloAck { compatible: false, reason }` with `version.floor_exceeded` or `version.ceiling_exceeded` at the connection handshake, never a join-time or write-time typed error, per §Decision #4 + §Decision #10.
- Event-type registry extensions within the same envelope MAJOR are additive-only per §Decision #8 — event-type renames are explicitly forbidden because readers dispatch on the name.

Reentrancy is owner-scoped via an `AsyncLocalStorage` (`node:async_hooks`) context carrying the held-lock token: an `append` issued inside a `withSessionAppendLock` critical section runs in that same async context, reads the token, and reuses the hold rather than re-acquiring (so the emitter's wrap never self-deadlocks); ANY caller outside that context — including same-session concurrent work on a different async chain — sees no token and blocks until release. **Release-on-settle is unconditional (F-005-HALT-01):** the hold releases in a `finally` owned by the frame that ACQUIRED it: an acquiring `critical` that REJECTS releases the hold and propagates the rejection unchanged, with the `AsyncLocalStorage` held-lock token torn down on the same settle path so a rejected acquisition can never leave a stale token visible to a later same-context call; a REENTRANT frame that rejects propagates the rejection unchanged WITHOUT releasing the hold or touching the token — only the acquiring frame settles the physical hold, so an outer owner that CATCHES an inner rejection and continues still holds the lock, its next nested call is still recognized as reentrant, and the hold releases exactly once when the owner frame settles — load-bearing because the gate refusal below throws `daemon.ingest_halted` INSIDE the critical section while `clear(sessionId)` acquires this same hold, so a leak-on-rejection would wedge the session unrecoverably (the module-singleton state makes the wedge process-lifetime, and the un-halt path itself deadlocks). The four lock properties are T3.5-tested: nested-call progress (an inner `append` completes under the outer hold), concurrent same-session blocking (two parallel `withSessionAppendLock` calls on one session serialize — the second waits for the first to release), cross-session non-blocking (locks on distinct sessions run concurrently), and owner-scoped rejection-release (a rejecting acquiring `critical` releases the hold — a subsequent same-session acquisition proceeds — while an inner REENTRANT rejection caught by the outer owner releases nothing: the arm asserts the outer's next nested call still runs reentrantly and the hold releases exactly once on the owner's settle). The same schema carries the projection-level terminal-key check that Spec-005's at-most-once-terminal-emission rule assigns to this schema work as a trigger trio, because its update legs compare the new row against `OLD`, which a CHECK constraint cannot read: `trg_run_terminal_key_insert` (`BEFORE INSERT`), `trg_run_terminal_key_update` (`BEFORE UPDATE OF payload, category, type`), and `trg_run_terminal_key_promote` (`BEFORE UPDATE OF category, type` — rejects re-typing a non-terminal row INTO the terminal set outright; terminal rows are INSERT-only, so a null-keyed promotion cannot slip the OLD-keyed update leg and the NULL-distinct index), with full DDL in [local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md). Stubbed rows are gap-inverted — a stubbed row is never a hole in the sequence scan; each stubbed position surfaces its audit-stub envelope at that exact sequence, so the cursor advances monotonically across stubbed rows and a reader can never step past one without observing it (the I-005-4-04 no-silent-omission guarantee at the cursor layer). ## Authoring Decisions

Decisions this plan settles that the spec does not.

- **Event contracts directory placement.** Resolved: Extend `packages/contracts/src/event.ts` top-level per Plan-001's contracts package layout (extend the canonical file; do not fork a sibling). The `events/` subdirectory referenced by prior plan iterations does not exist; no other plan adopts a subdirectory pattern.
- **RFC 8785 lex-sort vs [Spec-005 §Canonical Serialization Rules](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules) listed order.** Resolved: RFC 8785 §3.2.3 UTF-16 code-unit lex-sort is non-negotiable (the canonical-bytes invariant depends on it). [Spec-005 §Canonical Serialization Rules](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules) lists field MEMBERSHIP, not serialized order — ("Fields included (the canonical set; serialized order is mandated by RFC 8785 §3.2.3 UTF-16 code-unit lex-sort of member names, not the order listed here)"). T2.3 golden vectors assert the lex-sorted output as ground truth.
- **Daemon Ed25519 signing-key custody.** Resolved: Plan-005 T2.7 self-contains the signing-key source. Phase 2 ships the `DaemonSigningKeySource` interface + `OsKeystoreSealedDaemonSigningKeySource` implementation; per-session Ed25519 keys are sealed under the OS-keystore master key ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key): `@napi-rs/keyring` 2.1.0 on macOS and on Linux, pinned to the Secret Service, and on Windows a Credential Manager entry the service's Windows half writes at `CRED_PERSIST_LOCAL_MACHINE`) and stored as ciphertext in the local `daemon_signing_keys` SQLite table per ADR-004 SQLite-local-state boundary — the key never leaves the machine. T2.7 splits the seal out as an injected `DaemonSigningKeySealer` and carries no keystore code: the `daemon_signing_keys.sealed_private_key` byte format is the one sealing format [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key) gives every daemon private key, its master-key header naming the key that sealed it so a master-key rotation's re-seal reads one format, and Plan-020 implements it — so the design depends on Plan-020 for the implementation, registered as CP-005-11. That dependency causes no build-order inversion, because it rests on the injected interface: this module imports nothing from Plan-020 and pulls no native keyring binding into the append path's consumers. Roster registration happens at local session establishment per [security-architecture.md §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature), through CP-005-7's two legs (composition-root call-site, leg A; T4.10 registration write, leg B).
- **JCS library: vendor vs in-house.** Resolved: Vendor — `canonicalize` package (Erdtman's RFC 8785 reference implementation; ships with the RFC). T2.3 lifts the RFC 8785 Appendix B Table 1 number-serialization vectors verbatim as a sub-suite to catch version-drift bugs. In-house implementation rejected per ECMA-262 ToString edge-case risk.
- **Golden-vector storage: inline hex vs JSON fixture.** Resolved: Inline hex strings in the test file. Matches crypto-paseto convention (the `packages/crypto-paseto/src/internal/v4-local-deterministic.ts#encryptV4LocalDeterministic` golden-token tests in `packages/crypto-paseto/src/__tests__/v4-local.test.ts`); PR-diff is the audit trail for byte-stable artifacts.
- **`pii_ciphertext_digest` position + wire shape.** Resolved: Top-level field on `payload` (matches [Spec-005 §Canonical Serialization Rules](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules) + [Spec-020 §Argument](../specs/020-data-retention-and-gdpr.md#argument) literal reading); wire shape is **lowercase hex 64-char string** (matches BLAKE3 reference output convention; T2.3 golden vectors are reviewer-friendly in hex).
- **Partition-anchor queue durability.** Resolved: Design A — new SQLite table `pending_anchor_uploads` with columns mirroring `AnchorPayload` plus `attempt_count`, `last_attempt_at`, `last_error`; `UNIQUE(session_id, node_id, start_sequence, end_sequence)` constraint. Survives daemon restart; queryable for operator triage; storage footprint bounded at ≤ 1 anchor per 300s per session. Design B (reconstruct from Postgres deltas) fails the no-re-signing constraint; Design C (in-memory) fails durability.
- **Audit-stub representation: column add vs payload discriminator.** Resolved: Design B — new `session_events.retention_class TEXT` column. Partial index `WHERE retention_class IS NULL` keeps hot-path replay queries fast; explicit column makes stub state visible at row inspection; two-layer enforcement easier with typed column than JSON-field probe.
- **`summary` field max-length and generation rule.** Resolved: T3.2's stub builder generates `summary` from the original payload and truncates it before signing so the projection holds the `EVENT_CANONICAL_BYTES_MAX` bound, and refuses to stub a row whose projection is still oversized with `summary` emptied, reporting the refusal on the purge's result ([Spec-005 §Compacted Event Format](../specs/005-session-event-taxonomy-and-audit-log.md#compacted-event-format)).
- **Live-stream gap detection mechanism.** Resolved: Sequence-number monotonicity check in the SDK's `EventClient.subscribe` (Option (b)) as canonical gap-detection; SSE reconnect via `Last-Event-ID` header (Option (a)) as reconnect path. No cursor-carrying heartbeat (Option (c)) is needed: when a screen that fell behind has caught up on its queue, the daemon sends it one frame with no changes, carrying the drop mark and the newest cursor, so a session that goes quiet right after a drop still tells the screen it is behind.

- **CP-005-3 — T2.1's canonicalizer is the workspace's one RFC 8785 implementation.** Phase 2 T2.1's `canonicalizeEvent` + `canonicalizeJson` are the single source of truth for RFC 8785 JCS; any plan that needs canonical JSON bytes MUST consume them — never re-implement or fork. **The generic entry point is BOUNDED, not unlimited. It carries refusals of different KINDS, and each is a guarantee to every caller:** (i) the **policy ceiling** — `canonicalizeJson` refuses any value nesting containers past a fixed ceiling (`CANONICAL_JSON_MAX_DEPTH`, 64), a stack-overflow guard, since the pinned `canonicalize@3.0.0` recurses once per nesting level with no guard of its own; (ii) the **RFC-mandated refusal** — `canonicalizeJson` refuses any string value or property name carrying an unpaired UTF-16 surrogate, because RFC 8785 §3.2.2.2 makes terminating on such data a normative MUST while the pinned `canonicalize@3.0.0` escapes it through `JSON.stringify` and keeps going, emitting bytes no conforming verifier will ever reproduce; and (iii) the **determinism refusal** — `assertNoToJsonOverride` refuses any value carrying a callable `toJSON` at any depth, a `toJSON` being arbitrary caller code that need not return at verification time what it returned at signing time. (i) is checked first, and that order is a correctness constraint rather than a diagnostic preference — the depth walk is what makes the later walks terminate on cyclic input — so a value defective in more than one way reports the over-deep refusal and never another. Three consequences for any caller that feeds the entry point a value from outside the process, one deliverable each: (1) a **registered rejection reason** for an over-deep value; (2) a **distinct** registered rejection reason for an ill-formed one — (1) and (2) MUST NOT collapse into a single reason, an over-deep value and an ill-formed one being different client errors whose merger destroys the diagnostic (every refusal is a plain throw at T2.1, so each is caught and mapped at the caller's boundary, never surfaced raw to a remote party); and (3) the **depth ceiling ONLY** can be raised — a ceiling that proves too tight for a real payload is **raised in T2.1's constant**, never escaped by forking the canonicalizer. **(3) does not extend to (ii) or (iii).** The well-formedness refusal is a normative MUST-terminate — never raised or relaxed in either direction, since relaxing it violates RFC 8785 — so catch-and-map per (2) is the only available response there; the determinism refusal is what lets re-canonicalizing a row reproduce the bytes that were signed, so it is never relaxed either. A value that arrives through `JSON.parse` can never trip (iii): parsed output carries no function-valued member — a wire `{"toJSON":"x"}` parses to a STRING, and `"__proto__"` parses as an ordinary own data property rather than a prototype mutation — so the predicate is unsatisfiable on parsed input. A value a caller CONSTRUCTS in process (an object literal carrying a `Date`, a `Buffer`, or any class instance with a `toJSON`) meets a live refusal.

Registration semantics are pinned: register-once per key, with one current key per `(session_id, node_id)`; a same-key replay is an acknowledged no-op (retry-safe re-registration); the registration `sidekicks rotate-keys` makes, signed by the machine key and by the retiring key, marks the current key retired and makes the new one current, and rows signed before it keep verifying under the retired key; any other registration presenting a DIFFERENT key is refused with a typed error before any row mutation, never silently overwritten — the control-plane mirror of T4.2's `refuse_on_rotation` posture, pinned as I-005-4-08 and the concrete backing for security-architecture.md's rotation posture. **Resolution semantics.** [Spec-005 §Canonical Serialization Rules](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules) (the daemon public key is the `NodeId`-resolved public key from the session verification-key roster — served by `runtimenode.signingkeyroster` over `daemon_signing_public_keys`) governs the EXTERNAL verifier; the daemon-local verifier (T4.1) checking rows it authored resolves its own `session_id`-keyed `daemon_signing_keys` store — the degenerate `NodeId` = self arm — since no daemon-local roster mirror exists (`node_capabilities`/`node_trust_state` carry no key column). What leg B buys in V1: session-scope anchors uploaded to `event_log_anchors` become independently verifiable by parties other than the emitting daemon — without the roster row, `root_signature` is verifiable by no one but its author, a gap Spec-005 states for node-scope anchors and leg B closes for session-scope. A forgeable-key objection does not reach leg B: a session-scope key is bound to `(session_id, node_id)` by the machine identity key's signature on the registration, which the control plane checks against `runtime_nodes.public_key` for `nodeId` — a machine the caller must own — and a device checks against the machine key its own statement chain trusts, so no machine other than the one the registration names can plant a key; and a genuine daemon refused the different-key 409 for its own slot appends the durable `audit_integrity_failed` `failureMode: 'signing_key_slot_conflict'`, so a conflicting registration still leaves a durable alarm the moment that daemon registers. No master-key crypto leaks across the boundary in either leg: `create` returns the public key only (the T2.7 custody split).

- **CP-005-11 — Plan-020 daemon master-key custody for TWO seams: the daemon signing-key seal boundary (with the `sealed_private_key` byte format) and the session-content-key wrap.** Phase 2 T2.7 declares `DaemonSigningKeySealer` (`seal(sessionId, privateKey)` / `unseal(sessionId, sealedPrivateKey)`) as an INJECTED interface and ships no keystore code at all; `@napi-rs/keyring` is deliberately absent from `signing-key-source.ts`'s import graph. Plan-020 ships the implementation, sealing under the OS-keystore-managed daemon master key whose custody ladder is [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key) (the keychain rung: on macOS one login-keychain entry and on Linux one Secret Service entry, both through `@napi-rs/keyring` 2.1.0, every entry opened with `{linux: {store: "secret-service"}}` so the kernel keyring, which empties at reboot, is never used and a Linux machine with no Secret Service refuses; on Windows one Credential Manager generic credential written by the service's Windows half at `CRED_PERSIST_LOCAL_MACHINE`, never at a roaming persistence, whether the service runs on Windows or in a WSL 2 distribution), building on the master-key custody ladder Plan-020 already owns at `packages/runtime-daemon/src/bootstrap/daemon-key-store.ts`. **Plan-020 also implements the byte format of `daemon_signing_keys.sealed_private_key`:** it is the one sealing format [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key) gives every daemon private key — XChaCha20-Poly1305 under the master key behind the master-key header, with `AAD = header || purpose || row id || "ais.master-wrap.v1"`, where the row id is the session id — so the master-key rotation's re-seal reads one format and every sealed key names the master key that sealed it. T2.7 declares the OPERATION; Plan-020's sealer writes that format. **The `sessionId` AAD binding is part of the format:** the interface passes `sessionId` on both sides, and the sealer binds it as the row id in the associated data. `DaemonSigningKeySource.read` derives the public half of whatever `unseal` returns and refuses it unless it matches that row's `daemon_signing_keys.public_key`, so a blob copied between rows surfaces as a refusal naming the row rather than as rows signed under another session's key; that is a backstop, not a substitute, because an AEAD that will not open never produces the key material in the first place. `unseal` is asynchronous because [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key) wipes the in-memory master key on an idle timer on the hardware and keychain tiers, so the first `unseal` after a wipe awaits a keychain read and an enclave or TPM unwrap, with no person involved. Composition root MUST inject the real sealer — NEVER a test fake — and ships a runtime assertion against the fake outside tests; both land at Plan-020 with the implementation they guard, Phase 2 shipping only the interface plus test-only fakes. Interface + stub + composition-root-injection shape matches CP-005-1 and reciprocates the same Plan-020 keystore boundary Plan-006 registers as CP-006-8. **No build-order inversion:** the dependency runs through an injected interface, so this module imports nothing from Plan-020 and pulls no native binding into the append path's consumers — the property the `daemon_signing_keys` row in cross-plan-dependencies.md requires, and the reason the keyring import is kept out: on CI legs where a headless Linux box has no Secret Service, [Spec-021 §Native Keystore](../specs/021-desktop-app-and-renderer.md#native-keystore) requires the keystore layer to detect the no-keystore case and refuse rather than silently fall back. **The second seam is a widening of this obligation rather than a second one.** T3.6's `session-content-key-store.ts` declares `DaemonMasterKeySource` as an INJECTED interface with no production implementation in this package, for the identical reason T2.7 declares `DaemonSigningKeySealer` — the custody ladder is Plan-020's, and importing it here would pull a native keyring binding into the append path's consumers and invert the build order. The difference from the first seam: this store writes its own envelope in-module (the master-key header, a 24-byte random nonce, wire `header || nonce || ciphertext || tag`, `AAD = header || session_id || "ais.session-content-wrap.v1" || key_version`), the format [Local SQLite Schema §Session Content Keys](../architecture/schemas/local-sqlite-schema.md#session-content-keys-plan-005) fixes, so this seam owes Plan-020 key MATERIAL only, where the first owes it material and the sealer that writes Spec-020's sealing format. The reciprocal call runs the other way as well: `sidekicks rotate-keys` invokes `SessionContentKeyStore.rewrapAll` — synchronous by contract — inside the rotation's one `BEGIN EXCLUSIVE` transaction, the one that also re-seals every daemon private key and marks the new master key `active` and the old one `outgoing` before it commits ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key), steps 4 and 5), since a better-sqlite3 transaction cannot span an `await` and a promise-returning re-wrap would commit around nothing, leaving a crash window in which some blobs name the new master key while `master_keys` still names the old one active. A mint wraps under the key `master_keys` names `active`, and its transaction confirms that key is still `active` before it commits — the store's mint fence — so no content key commits under a retired master key or under one that exists only in memory.
- **CP-005-12 — Plan-020's data acts must leave no row holding ciphertext whose key is gone, and must clear `pii_payload` only through the stub builder, unless the binding verification rule allows the partial clear.** I-005-2-11 makes `BLAKE3(pii_payload)` = the signed `pii_ciphertext_digest` an unconditional check over every non-NULL `pii_payload`, in BOTH retention states. It is correct against the data acts as [Spec-020](../specs/020-data-retention-and-gdpr.md) specifies them: a session's purge deletes the session's content key (overwritten with zeros, then deleted, with a `TRUNCATE` checkpoint after commit; [Spec-020 §Ordering And Atomicity](../specs/020-data-retention-and-gdpr.md#ordering-and-atomicity)) and then, in the same transaction, stubs its rows through T3.2's stub builder, which NULLs `pii_payload` and `content_payload` in one statement and re-projects `payload` without a digest ([Spec-005 §Compacted Event Format](../specs/005-session-event-taxonomy-and-audit-log.md#compacted-event-format)), so every stubbed row lands in the both-absent state of the check; and `Erase all data` destroys every custody copy of the master key and deletes the store, so no row survives it. No row keeps ciphertext whose key is gone, so no shred carve-out is needed and rule 2 runs wherever `pii_payload` is non-NULL. **If a Plan-020 act ever clears `pii_payload` on a row it keeps outside the stub builder, or keeps a row whose key it destroyed,** that row's digest check flips to `pii_ciphertext_digest_unbound`, and the act pages on every run. Plan-020 therefore owns one of two obligations: change rows only through the stub builder and delete the store whole, or the skip condition in [Security Architecture §Verification Rules](../architecture/security-architecture.md#verification-rules) rule 2 and I-005-2-11 covers the partial clear. **The collision is the point** — an unwritten rule would let a partial clear happen silently and leave a row unbound forever.
- **CP-005-13 — Plan-016 daemon credential provider for the T4.10 registrar.** The T4.10 registrar authenticates as the node-owner user — the daemon's standing posture per [daemon.md §Responsibilities](../architecture/daemon.md#responsibilities) (the daemon authenticates to the control plane using PASETO v4 tokens), so no custody contract is violated: Spec-021's auth-material exclusivity clause binds main-process-vs-renderer, is desktop-only, and expressly cedes daemon internals to that component doc — presenting a PASETO v4.public access token with a per-request DPoP proof signed by a daemon-held key the token's `cnf.jkt` binds (api-payload-contracts.md §Authenticated Principal; a token is bound to the one key its `cnf.jkt` names, so the daemon never presents a token another process holds). **The token reaches the daemon through device-code sign-in.** Signing in yields a DPoP-bound (`cnf.jkt`) rotating refresh token, sealed under the daemon master key; the daemon trades it at the control plane for short-lived PASETO v4.public access tokens, each trade returning a new refresh token. Presenting a refresh token that was already used revokes its whole family, as signing out does, and access tokens are never stored, so each attempt of the registrar's session-lifetime retry loop mints fresh material. The protocol layer is owned by ADR-010; the issuance implementation is Plan-016's PASETO wiring. Plan-005 therefore declares a constructor-injected credential-provider INTERFACE — `DaemonCredentialProvider` at T3.3's `daemon-credential-provider.ts`, declared at its Phase-3 first consumer so no earlier-phase task imports a later-phase symbol (invoked per attempt, each retry carrying fresh material; an auth failure is a retryable transport failure on the existing backoff), with the implementation + composition-root wiring owed by Plan-016 — the CP-005-1/CP-005-11 injected-interface shape, runtime assertion against the stub included, so build order is preserved. The caller enumeration is live-plus-forward-declared: the live callers (T3.3 uploader, T4.2 roster caller, T4.10 registrar), plus the forward-declared calls, each injected by its own plan: the daemon's call to the control plane's `push.send` ([Plan-017](./017-notifications-and-attention-model.md) builds the call; [Plan-028](./028-remote-control.md) Phase 5 builds the senders), and [Plan-028](./028-remote-control.md)'s `runtimenode.register` (Phase 3) and `runtimenode.certificateChallengeSet` (Phase 8). T2.5 verifies. **Scope.** What the canonical form holds out is the PII PARTITION'S CONTENT — the plaintext and the ciphertext — which is why the invariant is worded "commit to `pii_ciphertext_digest`, **not raw ciphertext**" rather than as a rule about anything that references that partition. The key that sealed the partition needs no member of its own: it is the session's content key, which the signed `session_id` names. The partition itself stays out, and T2.5 leg 1's sentinel assertions are what keep it out. Cite: [Spec-020 §Signature Safety Under Shred](../specs/020-data-retention-and-gdpr.md#signature-safety-under-shred); [Spec-005 §Canonical Serialization Rules](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules).

Cite: [Security Architecture §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature) (`daemon_signature` covers the SAME `canonical_bytes(row)` that feeds `row_hash` — signing and hashing share one byte string, so a verifier never re-canonicalizes).
- **I-005-2-07 — `audit_integrity` and `event_maintenance` categories carry no `pii_payload`.** Discriminated-union type on `RawEventInput`: events in these categories have `pii_payload: never`. Cite: [Spec-005 §Audit Integrity (audit_integrity)](../specs/005-session-event-taxonomy-and-audit-log.md#audit-integrity-audit_integrity) (audit_integrity never-stubbed invariant + base payload shape); [Spec-005 §Event Maintenance (event_maintenance)](../specs/005-session-event-taxonomy-and-audit-log.md#event-maintenance-event_maintenance) (event_maintenance never-stubbed invariant + base payload shape).
- **I-005-2-08 — `verifyRow`'s check order is observable, and the placeholder stage precedes the chain stage.** First failure wins, so the order IS the verdict for a row failing more than one check: (1) structural chain-column shape → `hash_mismatch`; (2) all three integrity columns zero-filled → `signature_placeholder`; (3) `BLAKE3(prev_hash || canonical_bytes)` recompute → `hash_mismatch`; (4) Ed25519 over the same canonical bytes → `signature_mismatch`. Stage 2 anywhere later is dead code — a placeholder row zero-fills the chain columns too, so it would fail stage 3 first and `signature_placeholder` could never be returned. Three properties are load-bearing on the same function: Ed25519 verification is ZIP-215-strict (`{ zip215: false }` — not the library default for this curve), daemon and user signatures are never cross-validated, and key-resolution / plumbing bugs (wrong-width key, non-`Uint8Array` input) throw rather than returning a tampering verdict that would raise `audit_integrity_failed` on every row they touch. Enforced in `signer.ts` (T2.2); all five pinned by T2.3's `signer.golden.test.ts`. Cite: [Spec-005 §Integrity Protocol](../specs/005-session-event-taxonomy-and-audit-log.md#integrity-protocol) (placeholder signatures are refused, never retro-signed); [Security Architecture §Verification Rules](../architecture/security-architecture.md#verification-rules) (rule 1's all-placeholder exception is what MANDATES the stage-2 position rather than merely permitting it, keeping rule 2's precondition reachable).
- **I-005-2-09 — The canonicalizer's refusal set is closed over the serialized tree, and its refusal order is observable.** `canonicalizer.ts` raises six refusal families itself and no seventh: `normalizeOccurredAt`'s four guards (a lexical shape outside RFC 3339 with an uppercase `T` and a `Z` or `±HH:MM` offset; sub-millisecond precision the canonical form cannot hold, refused rather than truncated because truncation would leave `daemon_signature` not committing to the recorded timestamp; a lexically-valid but non-existent calendar date, caught by reading the fields back after the setters roll them over; and an offset fold landing outside the four-digit-year range `toISOString` renders, in both directions), `assertRepresentableSequence` (a `sequence` outside the IEEE-754 safe-integer range, where distinct sequences collapse onto one double and two different events could share a `row_hash` in a chain built to be injective), the `CANONICAL_JSON_MAX_DEPTH` ceiling (a stack-exhaustion guard — the exact-pinned `canonicalize@3.0.0` recurses once per nesting level with no bound of its own, and `canonicalizeJson` accepts any value a caller hands it), `assertNoToJsonOverride` (any value carrying a callable `toJSON` at any depth — arbitrary caller code that would otherwise divert the serializer onto a tree no guard inspected, and re-invoking it at verification time need not reproduce the bytes that were signed), `assertWellFormedStrings` (RFC 8785 §3.2.2.2's MUST-terminate obligation over any unpaired UTF-16 surrogate in a string value or a member name — the library instead escapes it through `JSON.stringify` and emits valid-but-non-conforming text), and the no-JSON-representation guard (a top-level `undefined`, function, or symbol, for which the serializer returns no output and the encoder would otherwise hand the signer zero canonical bytes). Three further refusals originate inside `canonicalize@3.0.0` and surface with its bare wording (`NaN is not allowed`, `Infinity is not allowed`, `Circular reference detected`); they are inventoried here, not owned — and the cycle refusal is SHADOWED in both shapes that could reach it: the depth walk drives an own-property cycle past the ceiling and reports it as depth exhaustion first, and a cycle closed only through a `toJSON` result is refused by `assertNoToJsonOverride` one guard later, before any serialization runs. What survives of it is the non-idempotent-accessor residual below, not a live path. **Which refusal sits on which entry point is forced by RFC 8785 conformance in both directions, not a placement choice:** well-formedness is generic because §3.2.2.2 obliges it for every string in every input, member names included, while the sequence refusal is event-only because Appendix B Table 1 lists unsafe integers as inputs with MANDATED outputs, so a generic unsafe-number refusal would fail the very specification this module implements; the `occurredAt` guards are reachable on two surfaces — inside `canonicalizeEvent`'s projection and through the exported `normalizeOccurredAt` T3.1's append path calls directly — and the no-JSON-representation guard is generic in effect as well as in placement, unreachable through `canonicalizeEvent`, whose top-level value is always the projection object and therefore always serializes (the guard fires on a top-level `typeof canonicalText !== "string"`, which the library returns only where it delegates to `JSON.stringify` for a non-object). **The first refusal to fire is the only one a caller sees, so the order IS the diagnostic:** `canonicalizeJson` runs the depth ceiling → the `toJSON` refusal → well-formedness → whatever the serializer itself refuses (the three library throws fire inside that call, ahead of the last guard) → no-JSON-representation, and `canonicalizeEvent` runs sequence → `occurredAt` → the three it inherits, in that same relative order. Depth-FIRST is a CORRECTNESS constraint rather than a diagnostic preference: neither of the two walks behind it carries cycle detection or a bound of its own, and it is the depth walk — which reports a cycle as depth exhaustion — that makes both terminate on cyclic input at all, so demoting it turns a refusal into a hang. The `toJSON` refusal's own position, between the ceiling and well-formedness, is a correctness constraint too and in the other direction: placed any later it would be walking a tree the well-formedness guard had already been diverted away from. **The closure claim reaches the serialized tree, and exactly ONE residual keeps it from being unconditional.** `assertNoToJsonOverride` closes the wider of the two bypasses this invariant scopes itself around: without it, a shallow object whose `toJSON` returned a deeper or ill-formed tree would clear every guard and be serialized anyway. The guard tests `typeof node.toJSON === "function"` down the whole prototype chain rather than `Object.hasOwn`, deliberately — an inherited `toJSON` diverts the serializer exactly as an own one does. **It REFUSES rather than inspecting the diverted output, and non-determinism is why:** a `toJSON` is arbitrary caller code re-invoked on every canonicalization, so the same value can serialize to different bytes at signing time and at verification time, and this module's entire protocol turns on re-canonicalizing a row and comparing bytes — a guard that walked the `toJSON` RESULT would still have to assume the serializer later saw that same result. Depth-ceiling evasion and §3.2.2.2 evasion are the second and third motivations, both subsumed by refusing the carrier outright. **The surviving residual is the non-idempotent ACCESSOR.** The depth walk's `Object.values` invokes each own enumerable getter once, `assertNoToJsonOverride`'s a second time, `assertWellFormedStrings`' `Object.entries` a third, and the serializer three more times per object member — **six** invocations through `canonicalizeJson`, all measured — so a getter returning different values across them puts the four walks and the serializer on different trees, and is the only remaining way to hand the serializer a tree no guard inspected. It is unreachable for a value that arrives through `JSON.parse` — parsed output carries neither accessors nor a callable `toJSON`, the latter because a parsed `{"toJSON":"x"}` yields a STRING — which is what makes the scoped claim load-bearing rather than weak. The over-refusal direction stays harmless by construction: a dropped `undefined` or symbol member's NAME is still checked, and an array's non-index own enumerable properties are walked. Beyond that accessor residual, three more are characterized rather than closed: nothing upstream refuses ahead of this module on the well-formedness axis (`EventEnvelopeSchema` admits lone surrogates in `actor`, `correlationId`, `causationId`, and in `payload` keys and values alike, so the canonicalizer is the first and only refusal on that path); `assertRepresentableSequence` re-checks no schema domain rule, so a negative-but-safe `sequence` passes here and is refused at the parse boundary alone; and T1.9's `sourceEpoch` / `sourcePosition` pair rides inside `payload` as untyped JSON, carrying the identical collapse hazard with the parse boundary as its only enforcement. Enforced in `canonicalizer.ts` (T2.1); every family is pinned by T2.3's `canonicalizer.golden.test.ts`, whose four dedicated precedence tests fix the order. Cite: [Spec-005 §Canonical Serialization Rules](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules) (RFC 8785 JCS; `occurredAt` normalized to millisecond precision so ordering is byte-stable); RFC 8785 §3.2.2.2 (the lone-surrogate MUST-terminate obligation) + Appendix B Table 1 (the mandated unsafe-number outputs that forbid a generic sequence refusal); [Plan-005 §Cross-Plan Obligations](./005-session-event-taxonomy-and-audit-log.md#cross-plan-obligations) (CP-005-3 — the generic entry point's refusals as guarantees to every caller, the over-deep and ill-formed refusals caught and mapped to distinct rejection reasons with only the policy ceiling raisable).
- **I-005-2-10 — The stored `occurred_at` spelling is bound to the signature, and the binding holds in both retention classes.** `canonicalizeEvent` normalizes exactly ONE canonical member — `occurredAt`, through `normalizeOccurredAt` — and passes every other member through byte-for-byte, so for that one column `daemon_signature` commits to the INSTANT rather than to the bytes `session_events.occurred_at` actually holds. The many-to-one narrowing that makes hash reproduction robust is therefore the same property that leaves the stored spelling uncommitted: an at-rest rewrite of the column into a different spelling of the same instant (a `+00:00` or `-05:00` offset in place of `Z`, appended trailing-zero digits) re-canonicalizes to identical bytes, so the chain hash AND the Ed25519 signature both still verify, and a verifier reproducing the hash from the respelled column agrees with the attacker rather than catching them. The damage is not cosmetic: `occurred_at` is a TEXT column ordered and windowed lexically, so a respelled row sorts out of position and drops out of the very date-range scans an audit walk uses — pinned green by `post-purge-verify.test.ts` controls whose UPDATEs this predicate is what makes catchable. **The binding is a SECOND check, not a stronger verification, and no amount of re-verification substitutes for it.** `isCanonicalOccurredAt` (T2.1, exported over the module's own `CANONICAL_OCCURRED_AT_PATTERN`) tests the stored string against the canonical form, which admits exactly one spelling per instant and is a fixed point of `normalizeOccurredAt`; composed with a green `verifyRow`, canonical means the stored string IS the signed string and non-canonical means it is a respelling — a conjunction neither half states alone. **It applies to stubbed rows too, which is the non-obvious half.** I-005-3-03 check (c) requires `occurred_at` to byte-equal the signed projection's `occurredAt`, so it catches a respelling applied AFTER the stub is written (`stub_scalar_mismatch`); it cannot catch one applied BEFORE, because [Spec-005 §Compacted Event Format](../specs/005-session-event-taxonomy-and-audit-log.md#compacted-event-format) preserves the original timestamp verbatim — a row respelled while live has the bad spelling copied into the projection, signed into the stub bytes, and byte-equal to its column forever. Stubbing LAUNDERS the live-path defect into signed bytes, which is why this predicate is the only binding that catches the respelling in either state. **Never throwing is load-bearing rather than defensive style:** T4.1 consumes it inside a range walk, where a single throw would abort the walk and silence audit of the entire tail, so it returns a verdict on every input — including the non-string a BLOB-affinity tamper can put in a TEXT column. Residual, characterized rather than closed: the check is LEXICAL, so `2026-02-30` and `T25:00:00` satisfy it while naming no instant; nothing is lost, because every such string is refused by `normalizeOccurredAt`'s guards and so cannot sit on a verifying row, and re-deriving the calendar read-back here would duplicate that guard and give it a second way to disagree with itself. - **I-005-2-11 — The `pii_payload` ciphertext column is bound to the signature that covers its digest, and the binding is checked.** [Spec-005 §Canonical Serialization Rules](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules) excludes `pii_payload` from the canonical form — so the signed bytes commit to the ciphertext without carrying it — and binds the column indirectly instead, requiring a `pii_ciphertext_digest` member (BLAKE3 over the ciphertext bytes) inside the signed `payload` on every row whose column is non-NULL. **Minting a commitment is not the same as enforcing one.** Without a rule that recomputes the digest, the column carries no integrity binding of any kind: substituting, truncating, or deleting `pii_payload` at rest leaves `row_hash` and `daemon_signature` both green, exactly as an `occurred_at` respelling does without I-005-2-10. `isCiphertextDigestBound` (T2.4, exported beside `embedCiphertextDigest` so mint and check cannot drift apart) closes it, and it is a POSTCONDITION of `verifyRow` rather than a precondition — the digest lives inside the bytes the Ed25519 check authenticates, so recomputing it against an unverified payload proves nothing. **The predicate decides every state, and some of them are absences rather than mismatches**, which is why the verdict is named `pii_ciphertext_digest_unbound`: bytes with a digest compare; - **I-005-3-08 — The session content key is stored wrapped, survives master-key rotation, and goes only with its session or the master key.** The key that seals both partitions of a session's events — `pii_payload` and `content_payload` — and the person's words on its interventions and queue items is a random 32-byte AES-256 key persisted only as an XChaCha20-Poly1305 envelope in `session_content_keys`, and is **never derived** from the daemon master key. Derivation is prohibited, because `sidekicks rotate-keys` ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key)) replaces that master: a derived key would change with every rotation and leave every existing body on the daemon permanently unreadable. Rotation therefore re-wraps this table **inside the rotation's one `BEGIN EXCLUSIVE`**, the transaction that also re-seals every daemon private key and marks the new master key `active`, so the all-or-nothing guarantee covers every wrap and no crash window leaves a content key under a master key `master_keys` does not name; a mint wraps under the `active` key and confirms it is still `active` before it commits. This key dies with its session: a purge deletes it first, in the transaction that stubs that session's rows, so every body the purge leaves in freed pages is ciphertext whose key is gone, and the hourly key sweep deletes a key no stored body uses. The wrap itself **binds master key, session and key version**: the master-key header naming the key that sealed it, a 24-byte random nonce, wire `header || nonce || ciphertext || tag`, `AAD = header || session_id || "ais.session-content-wrap.v1" || key_version` — the master-key wrap [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key) specifies, with its own info string. Without that AAD the envelope authenticates under the master key alone, so a blob swapped between two rows or replayed under a replaced `key_version` unwraps cleanly and merely fails to open that session's bodies — a key substitution indistinguishable from an ordinary `'turn_content_unavailable'`, with the ciphertext-digest verifier still green because the event ciphertext was untouched. Enforced by T3.6's key store and the rotation entry point it exposes; falsified by a key derivable from the master, by a re-wrap pass outside the rotation's transaction, by a mint that commits under a key `master_keys` does not name `active`, by any path other than the session's purge, the hourly sweep of a key no stored body uses, or `Erase all data` that destroys it, or by a wrapped blob that unwraps after being moved to another session's row, replayed under another `key_version`, or relabeled to another key id.

The ENFORCEMENT half — halting ingest from every locally-hosted colliding identity, never first-wins, un-halting as an explicit action by the person — is **plan-owned**, and deliberately so: neither Spec-005 nor [Security Architecture §Verification Rules](../architecture/security-architecture.md#verification-rules) states an ingest-halt duty anywhere, and the one halt Spec-005 does state belongs to `audit_integrity_failed` halting REPLAY — a different operation on a different surface. This plan designs the enforcement on top of the spec's detection-only signal rather than restating spec text, which is the plan-owned arm of the invariant-grounding rule; promoting it into Spec-005 would add a Required-Behavior duty to that spec.
- **I-005-4-04 — An audit read of a deleted session's retained rows returns audit stubs, never silent omission.** `readAfterCursor` / `readWindow` return all sequence positions; a stubbed position carries `payload.retentionClass === 'audit_stub'`. Only the whole-session purge writes stubs, so no live session's read meets one. T4.3 and T4.9 tests assert. Cite: [Spec-005 §Fallback Behavior](../specs/005-session-event-taxonomy-and-audit-log.md#fallback-behavior); [Spec-005 §Replay Interaction with Compacted Regions](../specs/005-session-event-taxonomy-and-audit-log.md#replay-interaction-with-compacted-regions).
- **I-005-4-05 — `EventSubscription` replay-then-live cursor handoff is monotonic.** Strict sequence order; no duplicate at boundary; no gap at boundary. T4.5 test verifies. Cite: [Spec-005 §Interfaces And Contracts](../specs/005-session-event-taxonomy-and-audit-log.md#interfaces-and-contracts); [Spec-005 §Fallback Behavior](../specs/005-session-event-taxonomy-and-audit-log.md#fallback-behavior).
- **I-005-4-06 — Zod-validated wire envelopes at SDK seam.** Malformed responses rejected at the SDK boundary, not silently coerced. T4.6 + T4.7 tests verify. Cite: Plan-004 Phase 4 precedent.
- **I-005-4-08 — Signing-key roster registration is register-once per key, and a different key is refused before any row mutation unless the retiring key signs it.** The control-plane register path (`signing-key-service.ts`, T4.10) holds one current key per `(session_id, node_id)` and stores each key once: a first registration INSERTs, a same-key replay is an acknowledged no-op, the registration `sidekicks rotate-keys` makes — signed by the machine key and by the retiring current key — marks that key retired and makes the new one current in the same transaction, and every other different-key registration, a retired key offered again included, is refused with the typed `runtimenode.signingkeyregister_conflict` (HTTP 409 / tRPC `CONFLICT`) and no row written — never a silent overwrite, and never a raw driver unique-violation surfacing in place of the typed refusal under a concurrent race. This is the control-plane mirror of I-005-4-03's daemon-side `refuse_on_rotation` posture on a disjoint surface (the two enforcement sites share no code, types, or wire contract), so the posture holds on both of its surfaces. T4.10 tests verify: register-once, same-key idempotence, different-key typed refusal, a signed rotation retiring the current key, a rotation with a failing retiring-key signature refused with nothing written, a retired key refused, and the concurrent different-key race resolving to exactly one stored key plus one typed conflict. Cite: [Security Architecture §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature) (the register-once / different-key-refusal posture); [Spec-005 §Canonical Serialization Rules](../specs/005-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules) (the `NodeId`-keyed roster the register path feeds).
- **I-005-4-09 — The registrar's refusal collapse and attempt preconditions are conjunctive and cannot silently narrow.** Two surfaces where a dropped predicate is silent are pinned. (1) The register path's collapsed authorization refusal spans its whole negative space — an unknown machine, another machine's `nodeId`, a machine the caller does not own, and a `machineSignature` that is missing or fails to verify all refuse with the ONE typed `runtimenode.permission_denied`, byte-indistinguishable (the binding is the machine identity key's signature; the CP-005-13 credential proves only the caller's token, per [Security Architecture §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature)); a regression distinguishing any arm — or softening one into tRPC `NOT_FOUND` — still passes every register-once test, so the T4.10 suite asserts each refusal arm plus the collapse (byte-indistinguishable responses). (2) The daemon registrar never attempts registration before BOTH attempt preconditions hold — the injected credential provider has produced a token and the daemon's node identity has resolved from the injected node-registry read (`node_trust_state`, written when the machine registers) — the plan's own two-surface reasoning made durable as an invariant rather than left as task prose. Enforced in `signing-key-service.ts` + `signing-key-registrar.ts` (T4.10); T4.10 tests verify. ## Parallelization Notes

- Contracts (envelope + taxonomy + error codes) block all runtime-daemon work; author first.
- Canonicalizer + signer + `pii-indirection` require contracts only and produce golden-vector artifacts the rest of the stack validates against.
- Merkle-anchor service, integrity verifier, compactor, and replay service can proceed in parallel once the append path is stable.

## Test And Verification Plan

- RFC 8785 JCS golden-vector conformance tests (standard vectors + project-specific edge cases: null-vs-absent, nested object ordering, numeric canonicalization, millisecond-precision `occurredAt`).
- Hash-chain tests: genesis row, multi-row chain integrity, chain-break detection produces `audit_integrity_failed` with `failureMode = 'hash_mismatch'`.
- Signature tests: daemon-only and dual (daemon + user) signatures, `refuse_on_rotation` posture enforcement — one Ed25519 public key observed under two distinct `(session_id, node_id)` identities produces `key_reuse_detected` (a key is registered once and a signed rotation retires the old key rather than reusing it, so the detectable violation is the cross-identity collision).
- Version-stub round-trip: an unknown-MAJOR event is persisted verbatim; the log row's `.version` remains the producer's original; an upcaster chain re-interprets on upgrade without rewriting the row.
- PII indirection tests: the signature still verifies over canonical bytes with `pii_payload` cleared; an event whose PII partition cannot be opened surfaces `pii_ciphertext_digest` but no plaintext and replaces the user's whole PII partition with a single `<pii-unavailable>` marker at one reserved payload key (partition-level, not per field).
- Encrypt-order regression tests: a deliberately-misordered write path (signing before digest-embedding) is rejected by contract tests.
- Purge stub tests: `Delete old data` on an archived or closed session deletes its content key before any row changes, stubs every row after a covering anchor lands, and records one `event.compacted` on the sentinel session; `audit_integrity` and `event_maintenance` rows are never stubbed; the audit-stub format preserves envelope-level fields (id, sessionId, sequence, occurredAt, category, type, actor). Background jobs change no row a person can see: the hourly key sweep deletes only keys no stored body uses, and the repack after each purge reports `page_count × page_size` and `freelist_count` before and after.
- Merkle-anchor tests: earlier-of cadence fires correctly; anchor payload is metadata only; `root_signature` verifies under the daemon public key over the anchor claim ([Spec-005 §Anchoring Cadence](../specs/005-session-event-taxonomy-and-audit-log.md#anchoring-cadence) — with a negative control: a queued record whose coordinates are rewritten after signing fails verification).
- Replay tests: `EventReadAfterCursor` surfaces `retentionClass: 'audit_stub'` for a deleted session's stubbed rows; `EventReadWindow` is bounded.
- End-to-end lifecycle: session.created → 50+ events → archive → purge deleting the session's content key and stubbing its rows → integrity verification succeeds over the full chain, confirming the signature-safety property with every `pii_payload` of the purged session cleared.
- Content-partition tests (Phase 3B): the codec's three routing cases (user partition alone, machine content alone, both on one row) each land the columns and signed members they owe and no others; the wrap's TWO required negatives — a blob moved to another session's row and a blob replayed under another `key_version` each fail to unwrap; the plaintext bound cuts at a codepoint boundary with `contentTruncated: true` beside a PRE-truncation `contentLength` and no sentinel in the text, while a complete body OMITS the marker entirely (writing `false` would change the canonical bytes of every complete row); the stub write NULLs `content_payload`, drops `contentCiphertextDigest` from the stub, and preserves `contentLength` / `contentTruncated`; both byte-accounting statements count the sealed column, proven by a storage-threshold pass that fires on content-heavy rows whose `payload` columns alone are far under the threshold and does NOT fire on the same rows without their bodies; and the read projection reports a replaced ciphertext as tampering rather than loss, reports a non-`Uint8Array` non-NULL column unbound rather than skipping it, passes a clean row whose column is NULL, and never fabricates an empty body on any unavailable path.

## Rollout Order

**Prerequisite** — the provisioning call-site (`DaemonSigningKeyProvisioner.create(sessionId)`, T2.7) binds at the FIRST production composition root that wires T3.1's durable append path, not at any fixed step boundary: until that composition root exists, every step-4 caller is a test suite provisioning its own keys, and the fail-closed null-key throw in `EventLogService.append` keeps the gap loud until the composition root carries the call-site + runtime assertion per the CP-005-1 assertion pattern (CP-005-7 leg A). **Step 4 (Phase 3) is where a signing gate binds, not step 2** — T3.1's `EventLogService` is the first code that durably writes a row and therefore the first production reader of a session signing key; Phase 2 builds the signer and the key source as modules whose only callers are unit suites generating their own keypairs, so gating step 2 would block work whose failure mode is unreachable. Phase 3 is NOT gated on work outside this plan: the append path signs with keys its own callers provision, and the production call-site obligation travels with the composition root (leg A — and that same composition root STARTS leg B's registrar at session establishment, the two-legged CP-005-1 assertion recorded at T4.10). Leg B (T4.10 session-establishment signing-key registration) is built in Phase 4 — the read-side/verifier phase, step 6 below — and is what makes the step-4 session-scope anchor uploads independently verifiable after the fact: it gates the verifiability claim, not Phase 3. Tracked under CP-005-7.

1. Land envelope contracts + taxonomy enum + error-contract version codes (Phase 1).
2. Enable the append-only write primitives — BLAKE3 chain, Ed25519 signer, signing-key source — behind internal feature gating (Phase 2 — depends on step 1).
3. Enable PII indirection (encrypt → digest → embed → sign order) (Phase 2 — depends on step 2).
4. Enable the durable append path (T3.1) + the purge's stub builder and the hourly key sweep + Merkle anchor emission (Phase 3 — depends on step 3; the Prerequisite's call-site obligation binds at the production composition root, not at this step's start).
5. Enable replay reads and live subscription catch-up (Phase 4 — depends on step 4).
6. Enable integrity verifier + observer-pattern `key_reuse_detected` + session-establishment signing-key registration (T4.10 — makes the step-4 session-scope anchor uploads independently verifiable) (Phase 4 — depends on step 5).
7. Enable the durable encrypted home for machine-authored prose — the `content_payload` column and its wrapped `session_content_keys` home, the second codec inside `pii-indirection.ts`, the stub-write and byte-accounting legs, and the verify-on-read projection (Phase 3B, T3.6 → T3.7 → T3.8 in that order). **Depends on step 4 and on nothing later**: it extends the durable append path T3.1 owns, and is listed last without having to follow them — it may be built before, between, or after either. ## Rollback Or Fallback

- If a new envelope MAJOR regresses, freeze new event-category adoption; [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #5 version-stub behavior keeps older readers consuming the log as opaque rows until the rollback lands.
- If the purge's stubbing regresses (audit stubs malformed, wrong categories stubbed), refuse purges until it is fixed — every kept session stays whole and correct without it; the hourly key sweep and the repack remove nothing a person can see and keep running.
- If Merkle anchor emission regresses (upload failure, signature mismatch), disable the anchor service — the local hash chain and row signatures retain tamper-evidence on each daemon's log.
- If the integrity verifier produces false-positive `audit_integrity_failed`, disable the verifier; chain and signatures remain durable on disk for later re-verification.

## Risks And Blockers

- **Canonicalization drift.** Any divergence from RFC 8785 JCS (field ordering, null-vs-absent, numeric canonicalization) produces hashes and signatures that two honest daemons cannot reconcile. A single shared canonicalizer implementation plus golden-vector tests are load-bearing.
- **PII write-path order.** Reversing the encrypt → digest → embed → sign order breaks [Spec-020 §Signature Safety Under Shred](../specs/020-data-retention-and-gdpr.md#signature-safety-under-shred). Enforced by making `pii-indirection.ts` the sole write path and by encrypt-order regression tests.
- **Category drift.** Event-type renames or category reassignments on existing wire types violate [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #8. Enforced by the taxonomy enum + contract tests; new types are additive-only.
- **Anchor cadence under partition.** If the daemon cannot reach the control plane for >300 seconds, anchors queue locally. The per-daemon hash chain + signatures retain tamper-evidence on each local log; the anchor tier provides external cross-observer consistency that catches up on reconnect.
- **Invariant enforcement regressions.** If the stub builder ever mis-categorizes an `audit_integrity` or `event_maintenance` event, the invariant is violated silently. Enforced at two layers (stub builder, pii-indirection) to prevent single-layer regressions.
- **CP-005-7 sequencing.** The provisioning call-site (leg A) binds at the first production composition root that wires T3.1's durable append path — T3.1 is the sole durable writer and so the first production signing-key reader, since `SessionService.append` is guarded test-only by T3.1's precondition; the [§Rollout Order](#rollout-order) Prerequisite paragraph carries the gate. The registration leg (B) is this plan's own T4.10 (Phase 4), at session establishment. An unprovisioned session surfaces as a null-signing-key throw on the first `EventLogService.append` — fail-closed by design, a load-bearing sequence dependency, not a runtime bug.
