## Execution Windows (V1 Carve-Out)

Plan-005 ships in two windows — a **partial deliverable** (substrate + `session.*` namespace) that unblocks [Plan-001](./001-session-core.md) Phase 5, and a **remainder** that completes the daemon control surface. This section documents the split so engineers reading Plan-005 in isolation see it.

### Plan-005-Partial (substrate + `session.*` namespace)

Lands alongside Plan-001 to unblock Plan-001 Phase 5. Scope:

- **[Spec-006 §Wire Format](../specs/006-local-ipc-and-daemon-control.md#wire-format) substrate** — `crates/sidekicks-daemon/src/ipc/local_gateway.rs` and `crates/sidekicks-daemon/src/ipc/protocol_negotiation.rs` implementing JSON-RPC 2.0 in the frame codec (`crates/sidekicks-contracts/src/jsonrpc/framing.rs`: each frame a 10-byte header and a body of at most 65,509 bytes, a message's bytes carried as attachments beside its JSON), the message bound [Spec-006 §Wire Format](../specs/006-local-ipc-and-daemon-control.md#wire-format) fixes, protocol-version negotiation, the typed error model, and supervision hooks. OS-local transport (Unix domain socket / Windows named pipe) is the only transport; there is no loopback fallback.
- **Spec-023 daemon-side bind-time substrate** — `crates/sidekicks-daemon/src/bootstrap/secure_defaults.rs` implementing `SecureDefaults::load` + `local_ipc_path()` + fail-closed enforcement, with validation scope limited to the OS-local socket or named pipe the partial exposes. Honors §Invariants I-005-1 (load-before-bind), I-005-2 (fail-closed), and I-005-4 (validation surface widens with bind surface) at the partial's bind surface; Plan-005-remainder extends the validation surface to the first-run-key, update and backup settings (the daemon binds no TCP port for clients).
- **The three `session.*` handlers Plan-001 needs** — typed handlers for `SessionCreate`, `SessionRead`, `SessionEventSubscribe` (the Plan-001 vertical-slice contracts). They do not close the `session.*` namespace: every other `session.*` method registers against the same registry from the plan that owns it, in the change that builds it (CP-005-2), among them [Plan-022](./022-mcp-server-configuration-and-governance.md)'s `session.mcpServer.subscribe` and `session.mcpServer.enabled.update`. No run-control, project-folder, `artifact.*` or `daemon.*` methods in this window.
- **The daemon client (per [Spec-006 §Wire Format](../specs/006-local-ipc-and-daemon-control.md#wire-format))** — `crates/sidekicks-client`, which decodes every reply with serde and garde and exposes the daemon transport for the session client; the desktop loads it through its Node-API package, `packages/client-sdk`.

### Plan-005-Remainder (other namespaces + supervision + Spec-023)

Lands beside Plan-003 (runtime bindings) and Plan-004 (event taxonomy) — all three are gated only on the partial's completion. Scope:

- The JSON-RPC method namespaces extending the substrate's namespace registry — the run controls (`agent.run.*`, `agent.queueItem.*`, `agent.childRun.*`), the project folders (`repoMount.*`, `workspace.*`, `worktree.*`, `project.*`), `artifact.*`, `daemon.*`, the driver's client-facing methods (`provider.model.list`, `provider.mode.list`, `provider.command.list`, `agent.run.context.compact`), `preview.*`, `browser.*`. Of these, **Plan-005-remainder OWNS `daemon.*`** (supervision verbs per [Spec-006 §Interfaces And Contracts](../specs/006-local-ipc-and-daemon-control.md#interfaces-and-contracts)); the driver's methods are owned by [Plan-003](./003-provider-driver-contract-and-capabilities.md) Phase 4 (the client-facing verbs CP-005-4 (a) lists; the session/run lifecycle ops are daemon-internal per Plan-003 §Phase 4 decision #2); the run controls, the project folders and `artifact.*` are owned by their respective downstream plans (Plan-002 / Plan-006 / Plan-011) and land with the consuming plan per the `presence.*` precedent. **`preview.*` and `browser.*` are registered here** (CP-005-10); everything that answers on them, with the daemon dependencies it needs, is [Plan-020](./020-desktop-app-and-renderer.md) T-020r-8-2's. Registration boundaries declared in CP-005-4 (the driver's methods) and CP-005-10 (the two page-host roots) below.
- The Spec-023 secure-defaults surface owned by Plan-005 adds in the remainder `daemon_key_store.rs` (row 3 — the store the machine's identity key is kept through: [Plan-025](./025-remote-control.md) Phase 1 mints the key under the machine's id once the credential store exists, and the credential store is Plan-019's) and the CLI `daemon update` command (row 7b — out-of-process; its `--check`, with the desktop's main process, is where the service's update is checked, row 7a); the daemon runs no update poller and takes no setting for one. The partial already ships the bind-time `SecureDefaults` validation surface (`secure_defaults.rs`) scoped to the OS-local socket or named pipe it exposes; §Invariants I-005-1 / I-005-2 / I-005-4 hold at every execution window per the validation-surface-widens-with-bind-surface rule.
- The CLI delivery track (`crates/sidekicks-cli`) and the renderer's connection line (the boot card before the service first answers, the composer's working line after it), which reads the `daemon.status` topic [Plan-025](./025-remote-control.md) Phase 1 builds. The gateway's `SupervisionHooks` are in-process callbacks inside the service, which feed the daemon's own `daemon.status.read` and never leave it.
- **The service's own control surface** (Phase R1): `daemon.flush` and the `daemon.ping` answer, retention with the diagnostic-log expiry, configuration, the machine's settings file, the keep-awake hold, backups and crash reports, beside the status, stop and restart verbs. The command line's install, sign-in, update and data verbs are Phase R3's.
- **Windows and WSL 2** (Phase R4): on every Windows computer the service is the native daemon, doing every Windows-only job in its own process through `sidekicks-platforms`; a session whose project folder is inside a WSL 2 distribution runs there through the WSL server, a helper mode of the Linux daemon program that the daemon starts in that distribution while it has work and reaches over one channel. [ADR-039](../decisions/039-sessions-in-wsl-2-distributions.md) records the decision.

### Substrate-vs-Namespace Decomposition Rule (Methodology)

**Rule:** Cross-cutting infrastructure plans MAY be split into an earlier substrate-deliverable + a later namespace-deliverable when (a) the substrate is single-owned and load-bearing for an earlier consumer, AND (b) the namespaces have natural cohesion with their owning plans. Substrate ships first; namespaces ship with their owning plans.

**Rationale.** Spec-006 conflates two concerns — the cross-cutting _transport substrate_ (correctly single-owned by Plan-005: only one set of framing, version-negotiation, and error semantics may exist in the system) and the domain-specific _method namespaces_ (which cohere with their owning plans: a method belongs with the plan that owns its domain — `session.create` with session core, `session.mcpServer.subscribe` with MCP governance, `agent.run.*` with run orchestration, etc.). Without a carve-out, Plan-001 Phase 5 either (a) inherits an undeclared forward dependency on Plan-005's remainder, breaking build-order discipline, or (b) duplicates the wire substrate in Plan-001, breaking single-ownership of the transport layer. The carve-out preserves both invariants by isolating the substrate beside the consumer while leaving namespace implementations at their natural plan boundaries.

**Applicability.** Apply this pattern when the Inter-Plan Dependency Graph would otherwise need an undeclared forward dependency from an earlier plan to a later infrastructure plan. The pattern is _not_ a license to fragment well-scoped plans for parallelism reasons — both criteria (a) and (b) must hold.

**Trade-off accepted.** Plan-005 readers must navigate two windows instead of a single linear sequence; the cross-link from cross-plan-dependencies.md keeps the canonical build order discoverable. This cost is paid once at plan-authoring time; the alternative (silent forward dependency) imposes a recurring cost on every PR-execution agent.

## Goal

Implement the typed local daemon control surface shared by the desktop renderer and CLI, including daemon supervision and protocol negotiation.

## Scope

This plan covers OS-local IPC transport, version negotiation, daemon lifecycle commands, shared daemon client implementation, and the first-class CLI delivery path.

## Non-Goals

- Relay or remote transport
- Provider-driver internal transports
- Browser-only local client support

## Invariants

The following invariants are **load-bearing** and MUST be preserved across all Plan-005 PRs and downstream extensions. They are restated here at top level so that consumers of Plan-005's substrate (Plan-001 Phase 5, the `presence.*` handlers, Plan-005-remainder namespace handlers) can find them without reading the §Secure Defaults table first.

### I-005-1 — Load-before-bind

`SecureDefaults::load(config)` MUST run **before** any daemon listener binds. `LocalGateway::start`, which binds, takes the `&SecureDefaults` that only `SecureDefaults::load` makes, so binding before loading does not compile.

**Why load-bearing.** Bootstrap-order inversion silently exposes a pre-validation listener to network input. The type holds the order, so no runtime test is needed.

### I-005-2 — Fail-closed on invalid security settings

`SecureDefaults::load` MUST fail closed on an invalid security setting — there is no "best-effort partial start" path. A downgrade the person sets through a row's override starts. An invalid setting is a start error (`SecureDefaultsError`) that ends the start, never a wire refusal. The settings are a Rust struct with one field, `local_ipc_path`, so no key outside the validation scope (e.g., `firstRunKeysPolicy`) can be passed or silently dropped.

**Why load-bearing.** Best-effort starts mask configuration drift; the override surface is the only sanctioned path for downgrades. Verification: the `secure_defaults.rs` test that an empty socket path ends the start with `EmptyLocalIpcPath`, and the address bound's test beside `check_socket_path`.

### I-005-3 — `SecureDefaults` exposes only the checked socket path

`SecureDefaults` exposes only `local_ipc_path()`, the checked socket path; no secret is reachable through it.

**Why load-bearing.** `local_ipc_path()` is what the gateway binds on; a secret leaking through this surface is a one-way security regression.

### I-005-4 — Validation surface widens with bind surface

These invariants apply to whatever bind paths the daemon exposes at the current execution window. Plan-005-partial ships a minimal bind surface (the OS-local socket or named pipe only) and a `SecureDefaults` validation surface scoped accordingly; Plan-005-remainder adds the first-run-key, update and backup settings (the daemon binds no TCP port for clients). The invariants hold at every window — the validation surface widens as the bind surface widens.

**Why load-bearing.** A static validation surface would either over-validate in the partial (refusing remainder-scope keys silently) or under-validate in the remainder (allowing settings outside the bind paths). Per-window scoping is the only way to keep the invariants honest.

### I-005-5 — Namespace registry rejects duplicate method-name registration

The method-namespace registry MUST reject any second `register(method,...)` call with an already-registered method name at registration time (not at dispatch time). The error is a programmer error and surfaces at once during daemon bootstrap.

**Why load-bearing.** A registry that silently accepts duplicates exposes a non-deterministic dispatch surface — the second handler may shadow the first, the first may shadow the second, or both may run. Every consumer of the registry (Phase 3 `session.*`, the `presence.*` handlers, Plan-005-remainder's `daemon.*`, and the downstream-owned run controls, project folders and `artifact.*`) depends on this for boot-time correctness.

### I-005-6 — Schema validation runs before handler dispatch

Every JSON-RPC request MUST decode with serde into the method's params type, and pass that type's garde checks, from the method table before the handler body executes. Validation failures map to JSON-RPC `-32602 Invalid Params` per [error-contracts.md §JSON-RPC Wire Mapping](../architecture/contracts/error-contracts.md#json-rpc-wire-mapping); the handler is NEVER invoked.

**Why load-bearing.** Handlers must trust their typed input. A handler that runs on a malformed payload either crashes (degrades to internal-error responses) or produces garbage downstream (corrupts SQLite state, emits invalid events). Schema-validates-before-dispatch is the only invariant that pushes the validation responsibility off the handler author.

### I-005-7 — Handler errors map to JSON-RPC error codes with sanitized payloads

Errors returned from handler bodies MUST map to JSON-RPC error codes per [error-contracts.md §JSON-RPC Wire Mapping](../architecture/contracts/error-contracts.md#json-rpc-wire-mapping) — every registered domain refusal (e.g. `session.notFound`, `auth.token.expired`) answers the one application number `-31000`, its name riding as `data.type` and its category as `data.category` in the two-layer envelope; only protocol outcomes keep JSON-RPC §5.1's numbers, and an id that resolves to nothing is a domain refusal with category `notFound`, never `-32602`; unregistered errors collapse to JSON-RPC `-32603 InternalError` with sanitized message; a panic ends the service through its panic hook, and the supervisor restarts it. Backtraces and secrets MUST never leak through the response.

**Why load-bearing.** Handler errors are the primary observability + security surface. Backtrace leakage is a one-way information regression; collapsing all errors to `-32603` without preserving registered domain codes destroys the typed error envelope downstream consumers depend on.

### I-005-8 — Method names follow the wire-name grammar

Every method name follows the wire-name grammar of [local-ipc-payloads.md §Wire-Name Grammar](../architecture/contracts/local-ipc-payloads.md#wire-name-grammar): dotted lowerCamelCase segments, two to four (e.g. `session.create`, `session.providerCommand.subscribe`), the same grammar events and error codes follow; protocol methods alone keep the `$/` slash form. The check runs at build time: one `const fn is_wire_name` in `crates/sidekicks-contracts` holds the grammar, and each name the contracts declare is asserted against it where it is declared, in `methods!`, `refusal_codes!` and `session_event_types!` and beside the two hand-built descriptors, so a name off the grammar fails the build and never reaches the registry, which checks only that no name is registered twice (I-005-5).

**Why load-bearing.** Without format enforcement, downstream plans may register `session.create`, `session/create`, `Session.create`, and `sessionCreate` simultaneously. The registry would treat these as distinct methods (correctly per the literal string) but the client consumer would have no way to choose. Asserting each declared name at build time is the mechanical guarantee, and it reads only the contract's own declared names. The dotted form keeps an app name from ever reading as a protocol method, and the lowerCamelCase segments keep the wire-format method names symmetric with the handler and client identifiers (`session.create` → the session client's `create`).

### I-005-9 — Subscribe-init response precedes the first notification frame

For any subscription-establishing method (e.g. `session.event.subscribe`), the daemon MUST emit the JSON-RPC response carrying the assigned `subscriptionId` BEFORE the first `$/subscription/notify` frame referencing that id. Daemon enforcement is the frame codec writer's ack rule: the writer writes no chunk of a subscription's lane until the `END` chunk of the subscribe response has been written, and every hop hands messages over in the order their `END` chunks were written. The paired client enforcement is that `crates/sidekicks-client` registers the subscription's route as it decodes the subscribe response, before it hands the result to the caller and before it decodes the next message, so a notify that arrives in the same read routes to a known `subscriptionId`. Both sides are load-bearing; the invariant covers both.

**Why load-bearing.** Without daemon-side ordering enforcement, the client has no way to learn the `subscriptionId` before the first notify arrives — even immediate client-side registration cannot install a route for an unknown id. Without client-side registration before the next message, the daemon's correct response-before-notify ordering is still insufficient under normal frame coalescing (a single transport read containing both the response and the first notify): a client that registered the route only once its caller resumed would dispatch the first notification first and drop it as an unknown subscription. The pair is the contract; either side alone leaks first-notification reliability.

### I-005-10 — A subscription's end releases its feed on every path

For every subscription the daemon opens (`Subscription` in `crates/sidekicks-daemon/src/ipc/stream/subscriptions.rs`, its frames the wire shapes `SubscriptionNotifyParams`, `SubscriptionEndParams` and `SubscriptionCancelRequest` in `crates/sidekicks-contracts/src/jsonrpc/streaming.rs`), what its feed follows MUST be released on each of the three ways a subscription ends: (a) the daemon's own end, when the feed finishes or a read fails, (b) the connection closing, which `Subscriptions::cleanup_transport` turns into a cancel of each of that connection's subscriptions, and (c) the client's `$/subscription/cancel`. The gateway drops a subscription once its lane's last frame is written, and `Subscription`'s `Drop` releases the feed on every one of those paths. When the daemon ends a stream it says so: one `$/subscription/end` frame with reason `completed` when the feed finished, or `refused` carrying the error it ended the stream for. A client's own `$/subscription/cancel`, a closed connection, and a subscribe refused before its acknowledgment send no end frame, since the client either asked for the end, is gone, or never received the id.

Six rules are load-bearing (canonical statement: `Subscriptions` and `Subscription` in `crates/sidekicks-daemon/src/ipc/stream/subscriptions.rs`): (1) the release runs once, in `Drop`, whichever path ended the subscription; (2) the entry leaves the subscription table before the feed is released, so nothing the release reaches finds the subscription still open; (3) the daemon's own end and a cancel are settled under the table's lock: a cancel that comes first ends the stream with no end frame and answers `canceled: true`, and an end that comes first sends its end frame and the cancel answers `canceled: false`; (4) a cancel answers only once the subscription's lane has closed, after its feed was released; (5) only the connection that owns a subscription can cancel it, and an unknown id and another connection's id both answer `canceled: false`, so no connection can probe for another's; (6) a connection's close cancels only that connection's subscriptions, and a feed waiting at its send gate when its subscription is canceled ends there, since the gate closes only after the cancel, so a closed gate never reads as a finished stream.

**Why load-bearing.** Every subscribe handler (`session.event.subscribe` in `crates/sidekicks-daemon/src/ipc/handlers/session/event_subscribe.rs`; `daemon.*` from Plan-005-remainder; the run controls, the project folders and `artifact.*` from their downstream owning plans; and `presence.*`) answers its acknowledgment and a feed, nothing else, so what the feed follows is released by the subscription that owns it: a handler writes no cleanup of its own and cannot leak a watcher on a path it forgot. A feed reads its next frame from its stored record at its cursor, or the newest state, rather than being called from the store as events land, so no release runs inside a store's own call and nothing re-enters the subscription table.

### I-005-11 — Daemon never self-swaps while IPC has active clients

The daemon never replaces its own running binary while the local-IPC gateway has active client connections. Nothing in the daemon downloads or swaps its program, even behind a flag — only the CLI-invoked `sidekicks daemon update` (out-of-process, daemon-restart afterward) is sanctioned to perform the swap. The invariant holds by construction: the daemon carries no download or swap code, so there is nothing to call and no test (a test that would still pass with the feature deleted proves nothing).

**Why load-bearing.** [Spec-023 §Required Behavior](../specs/023-self-host-secure-defaults.md#required-behavior) row 7a verbatim says "The daemon MUST NOT self-swap its binary while IPC is live." [Spec-023 §Pitfalls To Avoid](../specs/023-self-host-secure-defaults.md#pitfalls-to-avoid) reinforces: "row 7a forbids self-swap while IPC is live. Plan-005 MUST NOT give the daemon a 'download + swap' path even behind a flag." This is a runtime-state property — at startup, IPC has zero clients, so I-005-1 (load-before-bind) does NOT subsume this. I-005-11 is the live-state property: even AFTER startup, even AFTER all bootstrap invariants have been satisfied, the daemon has no path that swaps its program. The invariant is symmetric to I-005-1 in spirit (one guards startup-order; the other guards runtime-state).

### I-005-12 — CLI workspace package is import-isolated

`crates/sidekicks-cli` depends only on `sidekicks-contracts`, `sidekicks-client`, the CLI parser (`clap` 4.6.7 with its derive feature) and the crates its own output and tests need; it never depends on `sidekicks-daemon` or `sidekicks-control-plane`, and nothing under `apps/desktop` is reachable from a crate. The crate's `[dependencies]` table is the boundary: Cargo refuses a `use` of a crate the table does not list, so the isolation needs no lint of its own.

**Why load-bearing.** The CLI is the first delivery track per [Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior) and ADR-009 — it MUST consume the daemon strictly through the JSON-RPC IPC contract, not by reaching into daemon internals. If the CLI imported daemon code directly, the wire contract would be silently bypassable and the daemon client / control-plane / desktop / CLI clients would diverge. Enforcement is mechanical: `crates/sidekicks-cli/Cargo.toml`, which Phase R3 creates, lists the crate's dependencies, and the build fails on any other import; a new dependency is a change to that table a reviewer sees.

### I-005-13 — CLI exit codes are a closed deterministic mapping

Every CLI failure exit code is produced by the single canonical mapper T-005r-3-3 authors, `exitCodeForFailure`, from **exactly two typed failure sources**. Source (a), **daemon-originated**: a `JsonRpcErrorCode` carried on a JSON-RPC error envelope (the client library's `JsonRpcRemoteError`), mapped over the `docs/architecture/contracts/error-contracts.md §Numeric Code Space (per JSON-RPC 2.0 §5.1)` code set. Source (b), **CLI-local**: a failure raised inside the CLI process with no envelope to carry a code — a parse refusal, a background service that does not answer or closes the connection mid-call, a reader that closed the pipe the CLI writes to, and an error escaping a command body — classified inside that one mapper into one of four local-failure kinds: `usage` (a `clap::Error`), `unavailable` (the client's transport-unavailable or transport-closed error), `brokenPipe` (an `io::Error` whose kind is `ErrorKind::BrokenPipe`) → 141, or `software` (everything else, a caught panic among them, which exits 70, or 1 under `daemon update --check`). Both sources enter that one mapper; neither bypasses it. No ad-hoc exit codes (e.g., `std::process::exit(1)` for an unmapped error) are permitted, and neither is a second mapping table.

A command whose computed result is a negative state has not failed: it reports that state's exit code through the shared program — `daemon status` on a degraded service exits 1 (T-005r-3-5), and `daemon update --check` exits 100 or 1 (T-005r-3-14). The unit that builds the first such command adds that path to `program.rs` and its test, and these codes stay part of the closed set listed in `exit_codes.rs`.

A failure's exit code comes from these two sources only: a CLI-local failure has no wire code to map, so without a typed local kind the implementation would have to invent an exit code at the failure site, which is exactly the ad-hoc source this invariant forbids. Classifying and mapping inside one mapper keeps every exit code attributable to one table. The mapper's own drift guard sits **inside** those two sources rather than beside them: `UnmappedExitCodeError` — raised by the T-005r-3-3 table when a daemon-originated code carries no assignment — is raised at CLI exit-translation time and is therefore itself a CLI-local failure of kind `software`. The T-005r-3-2 boundary wraps its own mapper call, so the error is handled where it is raised: it is reported on stderr, the process exits the mapped **70**, and the guard neither recurses into the mapper nor escapes the boundary. Drift is loud in the test suite and deterministic in production, and adds no exit-code source of its own. Classification is by error type and variant (a `match`), or for a broken pipe by the `io::Error`'s kind, never by message text.

**Why load-bearing.** The CLI composes into scripts and CI pipelines; non-deterministic exit codes break automation. A closed mapping makes the failure semantic part of the wire contract: `-32602` invalid params → exit 64, a `-31000` domain refusal → the exit its `data.category` maps to, a background service that does not answer → exit 69, `-32603` internal error → exit 70, and a call the person canceled with Ctrl-C (`-32800`, or a refusal of category `canceled`) → the command ending the way a Ctrl-C ends it, so a script running it stops too (every code's assignment is listed at T-005r-3-3, and R3-T5 in T-005r-3-10 slice a checks the mapping is total).

### I-005-14 — Daemon-lifecycle CLI commands ack `ConnectionInitializeResponse` before reporting success

`sidekicks daemon start` and `sidekicks daemon restart` MUST NOT exit 0 on the local socket accepting the connection alone; they MUST wait for `ConnectionInitializeResponse` within a deadline (default 10s, override `--timeout <ms>`) before reporting success.

**Why load-bearing.** A daemon that accepted the connection but failed to complete the handshake (e.g., protocol-version mismatch emitting `request.protocolVersion.invalid` per the admission gate, `ConnectionReader::admit` of `LocalGateway` in `crates/sidekicks-daemon/src/ipc/local_gateway/connection.rs`) is not actually usable; reporting success here would mask the failure. A person's scripts rely on the `daemon start` exit status to gate what they run next.

### I-005-15 — Supervision events are single-emit per transport boundary

For each transport the daemon's gateway accepts, its `SupervisionHooks` (T-005p-2-1) fire exactly one `onConnect` when that optional hook is given (the daemon gives none), followed by at most one `onError` (terminal) and exactly one `onDisconnect` (terminal). Duplicate emissions for the same transport indicate a gateway bug.

**Why load-bearing.** `daemon.status.read` (T-005r-1-3) projects the service's state from these hooks, so a duplicate emission would race that projection.

### I-005-16 — The renderer draws an unknown connection state as `degraded`

The renderer (T-005r-3-9) draws a state of [Plan-025](./025-remote-control.md) Phase 1's `daemon.status` topic that it does not know exactly as it draws `degraded`: the working line's `Connection lost` and `Not connected.`, with `Retry`, never `connected` and never words of its own for the state.

**Why load-bearing.** Fail-closed on unknown enum values prevents new-future-value-introduces-a-bypass attacks. The forward-compat surface is real: if a later service adds a state to the topic, this invariant ensures an older desktop app degrades safely rather than rendering "connected" against an unrecognized signal.

### I-005-17 — Mutating-op gate for renderer-issued `daemon.restart`

A `daemon.restart` call originating from the renderer (Runtime's `Restart`) MUST be gated by a server-side check that the calling session has a valid `ConnectionInitializeResponse` (per [Spec-006 §Fallback Behavior](../specs/006-local-ipc-and-daemon-control.md#fallback-behavior): mutating operations are blocked until versions are compatible). The renderer disables no control while the link is down (T-005r-3-9), so this server-side check is the only gate.

**Why load-bearing.** Trust-boundary discipline per [Spec-021 §Trust Stance](../specs/021-desktop-app-and-renderer.md#trust-stance) — the renderer is NOT a direct daemon client. Even though Plan-020's `no-restricted-imports` ESLint rule blocks the renderer from binding a JSON-RPC client, the IPC bridge handler is the only channel and MUST re-validate every mutating call against the daemon's typed-error envelope. Server-side enforcement at the substrate mutating-op gate (the pre-dispatch admission gate, `ConnectionReader::admit` of `LocalGateway` in `crates/sidekicks-daemon/src/ipc/local_gateway/connection.rs`) is the authoritative check; the renderer-facing checkpoint on the `daemon.status` bridge topic, which [Plan-025](./025-remote-control.md) Phase 1 builds, refuses the renderer-issued call with an actionable error envelope if the daemon-status state machine is not `connected`.

### I-005-18 — CLI process streams are role-separated

Every byte `crates/sidekicks-cli` writes goes to the stream its role assigns. **stdout carries result payload only** — the human-readable or `--json` rendering a caller pipes or parses, plus the output of an explicitly requested `--help`, `--version` or `help` command, whose payload IS that text. **stderr carries every diagnostic** — banners, progress notices, the refusal for an unparseable or unknown invocation, the usage text accompanying such a refusal, and every error message. A command that **fails to produce its result** writes nothing to stdout: a parse refusal, an unknown invocation, and an error escaping a command body each leave stdout byte-empty. A non-zero exit is not that condition. A command that successfully renders a result describing a negative or unhealthy subject writes that result to stdout and reports the subject's state through its exit code — the discriminator is result-versus-diagnostic, never zero-versus-non-zero. `daemon status --json` against a `degraded` daemon is the named instance: it emits its canonical JSON payload on stdout and exits `1` (T-005r-3-5), and the same shape recurs across the workspace wherever a command reports a negative outcome it successfully computed.

**Why load-bearing.** `daemon status --json` (T-005r-3-5) is a machine-readable contract. A failure that writes diagnostic text onto the same stream corrupts the caller's parse while I-005-13's exit code reports failure — the two signals disagree, and in a shell pipeline the corrupted parse is what the next stage consumes. Enforcement is structural first and lint second, and that ordering is itself the claim: no lint rule set closes this hole, so the guarantee does not rest on one. The **structural** layer is that every command is a subcommand of the one `clap` derive `Cli` in `crates/sidekicks-cli/src/program.rs`, writes its result through the injected `CommandContext`'s `stdout` writer (an `impl Write`) and nothing else, only once it can no longer fail, and fails by returning an error. Arguments are parsed with `Cli::try_parse_from`, never `parse` or `clap::Error::exit`, so a refusal comes back as a `clap::Error` the program writes to the injected writers itself, and `run_program` is the process's one error boundary, which writes every diagnostic to the context's `stderr` and never to stdout. `crates/sidekicks-cli/src/main.rs` is the one file that names the real process streams: it builds the context from the locked `std::io::stdout()` and `std::io::stderr()` and returns `std::process::ExitCode`, never calling `std::process::exit`, which skips every destructor and any buffer the command holds itself (it flushes only the standard library's own stdout). R3-T7 asserts against the injected writers rather than against the process. The **lint** layer is Clippy's `print_stdout` and `print_stderr`, denied over the crate, so a `println!` or `eprintln!` (which also panics on a closed pipe) fails the build; it narrows the spellings an author reaches for by habit and is not claimed exhaustive, since a writer opened on the real streams outside `main.rs` defeats it, which is why the injected writers and the one boundary, rather than the lints, make a bypass a correctness question instead of an open one. The scope is the whole workspace, not this plan's own commands: **every** plan that authors a command into `crates/sidekicks-cli/src/commands/` joins the program the way CP-005-7 states, an obligation restated on each consuming ownership row rather than left to this prose — today [Plan-014](./014-workflow-authoring-and-execution.md), [Plan-015](./015-hosted-account-and-identity.md), [Plan-022](./022-mcp-server-configuration-and-governance.md), [Plan-023](./023-provider-accounts-and-credential-homes.md), and [Plan-024](./024-agent-definitions-and-peer-invocation.md), each carrying a §2 package-path ownership row — the same workspace-wide binding I-005-12 already places on those plans. Verified by R3-T7 (T-005r-3-10 slice a).

### I-005-19 — The dispatch context carries the calling connection's device

Every handler the substrate dispatches receives the calling connection's device on its `HandlerContext`, resolved by the gateway from the transport that carried the request and by nothing else, never from a request body field. A write records that device. Nothing checks ownership: no handler authorizes a read or a write by a person's identity. The device is a dispatch-context fact and never a wire field, so no request schema gains a member for it and a caller-supplied one is never trusted (the informational-body-fields rule).

**Why load-bearing.** Without the device, `HandlerContext` carries only `transportId`. Resolving the device once, in the component that already holds the transport, gives every namespace that records a write's device the same value, rather than each resolving its own (CP-005-9).

### I-005-20 — A request `id` is bounded at the request boundary, and a refusal never echoes an unbounded one

A JSON-RPC request whose `id` exceeds `JSON_RPC_ID_MAX_BYTES` once JSON-encoded is refused as `-32600 Invalid Request` before any handler runs, and **every** error frame the gateway emits for that request carries `id: null` rather than the offending value. The bound is enforced at the request boundary because JSON-RPC requires a response to echo the request's `id`: it is the one response member no response schema chooses, so no reply can be bounded by bounding replies. The measure is taken on the JSON-encoded form, so escaping is covered and one rule reads identically across the string, number, and null id forms the envelope admits. The refusal fails the **request**; the connection stays open.

**Why load-bearing.** The frame codec's message-size limit is absolute in both directions, and an oversized **response** cannot carry its own error — the reply that would have reported the fault is the reply that will not encode — so the send path drops the connection instead. Without this bound, an id large enough to displace a whole reply is contract-valid, and every answer to that request, including its error, becomes unencodable: a dropped session reachable from well-formed input alone. Enforcement has one site, the admission gate, which refuses the request under `id: null`; a message the envelope parse cannot read yields no id at all, so every refusal before that gate answers `id: null` too, and the one frame guaranteed to be small never carries the oversized echo. A client response is refused under its id only when that id is within the bound. Verified by the `ipc::local_gateway` oversized-id test, which asserts the refusal shape, the null echo, and — as its negative control — that an id at the bound is accepted and echoed.

### CP-005-7 — The shared CLI program and its one error boundary owed to every plan authoring into `crates/sidekicks-cli/src/commands/`

**Why bidirectional.** Phase R3 reviewers see that I-005-18's workspace-wide claim is met by a named obligation on each of those plans rather than by Plan-005 prose alone; each consuming plan's reviewers see the shared program as a hard dependency of their command modules, so a command that parses its own arguments or writes to the real process streams — which bypasses the one boundary and the injected writers, so the command reports and exits on its own — is a contract breach a reviewer can name.

### CP-005-8 — `transcript.*` JSON-RPC method namespace registration and the declared frame-size limit owed to [Plan-010](./010-transcript-and-reasoning.md) Phase 1

Plan-005-remainder owns the substrate's namespace registry and Phase 2 owns its frame codec. [Spec-006 §Wire Format](../specs/006-local-ipc-and-daemon-control.md#wire-format) fixes it and the frame codec enforces it in both directions — the reader refuses a message whose JSON passes the bound and the writer refuses to emit one. Plan-010's page builders have to size a reply against the message it will become, because an oversized **response** cannot carry its own error: the send path closes the connection rather than answering, so an unpageable reply is a dropped session and not a request failure. A second literal copy of the number would drift from the codec silently, and the drift would surface as closed connections rather than as a failing test. The **value** therefore lives once, as `MAX_MESSAGE_BYTES` in `crates/sidekicks-contracts/src/jsonrpc/framing.rs`, which the frame codec and Plan-010's page builders both read. **Enforcement stays here and only here.**

**Why bidirectional.** Plan-010 reviewers see the registry and the frame codec as hard dependencies of Phase 1 — its method strings resolve against this plan's `MethodRegistry`, and every page it returns is bounded by this plan's frame codec. Plan-005 reviewers must know that `transcript.*` is part of the registered namespace set, and that the message bound has a declared home outside the substrate with a second reader, so a future change to it is a two-consumer change rather than a local one.

Two further substrate rules ride this same obligation. **(a) The request-id bound (I-005-20),** authored by that plan's Phase 1. `JSON_RPC_ID_MAX_BYTES` (256 bytes) is declared beside the message bound in `crates/sidekicks-contracts/src/jsonrpc/message.rs` and enforced at one site, the pre-dispatch refusal in `ConnectionReader::admit` (`crates/sidekicks-daemon/src/ipc/local_gateway/connection.rs`); a message the envelope parse cannot read yields no id, so every refusal before that gate answers `id: null` and no oversized id reaches the one frame guaranteed to be small. [Spec-006 §Wire Format](../specs/006-local-ipc-and-daemon-control.md#wire-format) and `§Acceptance Criteria` carry it, and **I-005-20** on this plan states the guarantee. The invariant is minted here rather than on the consuming plan because the guarantee is the substrate's — every namespace registered against this registry inherits it, and Plan-010 is only the first caller whose replies could not otherwise be bounded. **(b) The subscribe-init ordering barrier.** The frame codec's writer holds a subscription's lane until the `END` chunk of the subscribe response has been written (the writer's ack rule), one rule every streaming handler inherits with no barrier module of its own; it is what makes I-005-9 hold for `session.event.subscribe` and every later subscription, and W-005p-3-T6 exercises it.

## Secure Defaults (Spec-023 daemon-side rows)

Plan-005 owns the daemon-side enforcement of [Spec-023 §Required Behavior](../specs/023-self-host-secure-defaults.md#required-behavior) rows 3, 4, 7a and 7b. The enforcement layer is a typed `SecureDefaults` configuration module that runs in the daemon bootstrap path before any listener starts, validates overrides explicitly, fails closed on invalid settings, and exposes only typed non-secret effective settings to downstream daemon modules.

| Spec-023 Row | Daemon-Side Behavior | `SecureDefaults` Enforcement Point |
| --- | --- | --- |
| 3 — Auto-generated strong secrets on first run (daemon keys) | [Plan-025](./025-remote-control.md) Phase 1 mints the machine's identity key into the daemon's credential store ([Plan-019](./019-data-retention-export-and-deletion.md)) under the machine's id once the credential store exists, kept through `DaemonKeyStore` as its own item in the operating system's credential store ([Spec-020 §Daemon Secrets](../specs/020-data-retention-export-and-deletion.md#daemon-secrets)), never kept as a key file; nothing in the daemon's database is encrypted by the app; the first-run sentinel is the relay's ([Plan-025](./025-remote-control.md) Phase 8), not the daemon's | `daemon_key_store.rs` (the trait this plan owns) |
| 4 — Loopback bind by default (daemon) | The daemon's local IPC is a Unix domain socket or a named pipe with no network address, and it has no bind setting of its own | `secure_defaults.rs` |
| 7a — Auto-update checked from the app and the CLI (daemon) | The daemon runs no update check of its own and takes no setting for one; the service's update is checked by the desktop's main process and by `sidekicks daemon update --check`; daemon MUST NOT self-swap while IPC is live | `crates/sidekicks-cli/src/commands/daemon/update.rs` (`--check`); nothing in the daemon |
| 7b — Opt-in self-update (CLI) | `sidekicks daemon update` fetches the release's manifest and the target binary and checks the binary against the SHA-256 the manifest lists for its platform, and nothing more; waits for running work to finish, naming it and never stopping it, then swaps the service's program atomically and restarts it, with platform-specific rules; updates the service alone | `crates/sidekicks-cli/src/commands/daemon/update.rs` |

**Invariants.** See top-level §Invariants — I-005-1 (load-before-bind), I-005-2 (fail-closed), I-005-3 (`SecureDefaults` exposes only `local_ipc_path()`), I-005-4 (validation surface widens with bind surface). The invariants govern this entire §Secure Defaults table; the top-level placement makes them discoverable to consumers (Plan-001 Phase 5, the `presence.*` handlers) without requiring them to read this section first.

### Phase R4 — Windows and WSL 2

**Goal:** On every Windows computer the background service is the native daemon, and a session whose project folder is inside a WSL 2 distribution runs in that distribution through the WSL server, a helper mode of the Linux `sidekicks-daemon` program (`sidekicks-daemon wsl`) that the daemon starts there while the distribution has work and reaches over one channel. Every Windows-only job runs in the daemon's own process through `sidekicks-platforms`. The behavior is [Spec-006 §The service on a Windows computer](../specs/006-local-ipc-and-daemon-control.md#the-service-on-a-windows-computer); the decision and what was weighed against it are [ADR-039](../decisions/039-sessions-in-wsl-2-distributions.md).

**When:** the Other platforms group ([cross-plan-dependencies.md §Platform order](../architecture/cross-plan-dependencies.md#platform-order)), in two units. The native service on Windows — T-005r-4-2, T-005r-4-6, T-005r-4-8's signed-out task and `banners` instance, T-005r-4-10 and T-005r-4-11 — is unit `windows`. The rest, sessions in WSL 2 distributions, is unit `windows-wsl`, built after unit `windows`, [Plan-019](./019-data-retention-export-and-deletion.md)'s credential store and the Linux runtime archives the Windows installers carry ([Plan-020](./020-desktop-app-and-renderer.md) T-020r-6-5); it keeps T-005r-4-8 for sessions in a distribution while the person is signed out.

**Precondition:** Phase R3 merged — R4 gives R3's `daemon install`, `uninstall`, `start` and `status` their Windows forms and runs the same CLI in a Windows terminal and inside a distribution. - **T-005r-4-2** (Files: `sidekicks-platforms`' pipe code, which the daemon serves with and `crates/sidekicks-client` connects through; the Windows token writer) — One per-user named pipe, `\\.\pipe\ai-sidekicks-<user SID>`, served by the daemon itself through `sidekicks-platforms`. **Server:** tokio's `ServerOptions` with `first_pipe_instance(true)`, `reject_remote_clients(true)` and an access list that grants the person alone on every instance; `ERROR_ACCESS_DENIED` on the first instance means another program holds the name, so the daemon refuses to serve, writes the reason to the status file (T-005r-4-6), releases the mutex and exits nonzero, and the task tries again a minute later. It checks each accepted client's process belongs to the person through `GetNamedPipeClientProcessId` and that process token's user, then walks the client's parent chain and refuses with `auth.callerRefused` one that descends from a process the service started, or that runs through a process serving a Codex service the daemon dials, with the daemon socket's exceptions ([Security Architecture §Local Daemon Authentication](../architecture/security-architecture.md#local-daemon-authentication)); a parent that cannot be opened, or whose start time is later than its child's because it took a freed process id, ends the chain the way the system's first process ends it on macOS and Linux, since Windows never moves a process to a new parent, and the chain is judged by what was read up to it, so a process whose parent in the daemon's tree has exited reads as the person's own; a child a same-user process started with another recorded parent (`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`) reads as that parent's, which the start-time test does not catch (the known reach security-architecture names). Each accepted connection speaks the frame codec to the same connection handler a Unix-socket connection gets. **Client:** `crates/sidekicks-client` connects through `sidekicks-platforms`' `connect_socket`, which opens the pipe with the standard library's `OpenOptions`, `custom_flags(FILE_FLAG_OVERLAPPED)` and `security_qos_flags(SECURITY_IDENTIFICATION)` (which sets `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`, so a rogue server cannot act as the caller), opens it up to 40 times, 50 ms apart, while every instance answers `ERROR_PIPE_BUSY`, and before writing a byte checks that the process serving the pipe runs as the person: `GetNamedPipeServerProcessId`, that process token's user, and `EqualSid` against the client's own; a wrong user or any failed call closes the handle and the token is never sent; the handle then becomes `interprocess`'s stream through its `TryFrom<OwnedHandle>` conversion, one stream type on every system and no `unsafe` in the open. Before its first byte the client also checks the run folder (`GetSecurityInfo`): its owner is the person, SYSTEM or the Administrators, who own what an elevated process makes, and its access list lets in no account but those three. **Token:** the daemon makes it at every start and writes `%LOCALAPPDATA%\ai-sidekicks\run\daemon.token` with a user-only access list; clients read it at every connect. The service binds no TCP port for its clients, so no other machine reaches it. **What can reach the daemon on this computer**, each with its gate: on Windows, the pipe (user-only, the parent-chain check above, the daemon token as the first message), the terminal bridge's HTTP socket (the caller check, the daemon token as `Authorization: Bearer`), the `sidekicks` tool server's loopback port (each session's secret), the command channel's folders (each conversation's own folder, each party known by the public key read from its process's command line, [Plan-003](./003-provider-driver-contract-and-capabilities-phase-3.md) T3.28), Codex's pass-through relay (its own bearer token) and the daemon's Claude Code inboxes (pipes with the daemon pipe's user-only access list, no caller check); inside a distribution, each carried to the daemon by its WSL server (T-005r-4-14), the WSL server's Unix socket in its run folder (mode `0600`, the caller check, the daemon token as the first message), the terminal bridge's HTTP socket (the caller check, the daemon token as `Authorization: Bearer`), the `sidekicks` tool server's in-distribution loopback port (each session's secret), the command channel's folders (each conversation's own folder, each party known by the public key read from `/proc/<pid>/cmdline`), Codex's pass-through relay (its own bearer token) and the daemon's Claude Code inboxes (sockets of mode `0600`, no caller check). **Tests:** a squatter holding the name makes the server refuse and exit nonzero, and the client's owner check refuse before its first write — each killed by a mutation that drops the check. **Spec coverage:** Spec-006 §The service on a Windows computer (reaching the daemon from Windows).
- **T-005r-4-3** (Files: the daemon's end of the channel; the WSL server's end) — One channel per distribution with work: HTTP/2 over the standard input and output of one long-lived `wsl.exe`, `h2` 0.4.20 on tokio on both ends, the daemon the client and the WSL server the server, never a link per connection. **Ready:** `<prefix>{protocolVersion, pid}` on the server's standard output within 10 seconds for a running distribution, and within the cold-start probe's figure from a stopped virtual machine; the ready line carries no token. Anything before the prefix is `wsl.exe`'s own launch message, decoded as the distribution list is decoded and shown word for word under T-005r-4-7's line. **Streams:** one control stream, opened first, carries the daemon's requests and the server's reports; one stream each carries a provider process's standard input and output, a PTY, a file read or listing, a watch, a carried connection, and each local client of the server's endpoints. **Memory:** a stream flow window of 1 MiB and a connection window of 16 MiB on both ends, every writer sending through the capacity `h2` grants its stream (`reserve_capacity`, then `poll_capacity`). **Three `h2` defaults set on purpose:** the small-DATA-frame budget, which closes the connection with `ENHANCE_YOUR_CALM` when spent, is raised so a terminal's stream of small frames never trips it, and the WSL server coalesces a PTY's reads while its stream waits for capacity; the local error-reset limit is lifted, because its count never resets over a channel that lives for days; nothing pings at idle — a PING goes out only when a call passes its deadline, and no answer within 5 seconds ends the channel and the daemon restarts the server. **Bytes:** a standard handle that is not a console is relayed raw both ways; where the binary-integrity probe fails on a supported WSL build, the channel carries its frames base64-encoded on the same link. **Principal:** the daemon treats the channel as its own child's standard input and output; every local client of the server's endpoints still sends the daemon token as its first message. The server stops itself on end of input or a failed write to its output, because a killed `wsl.exe` sends it no signal. **Tests:** 50 MB each way at once through a real child's standard input and output passes at these settings, and a 60-second terminal flood keeps the channel open. **Spec coverage:** Spec-006 §Interfaces And Contracts (the channel).

- **T-005r-4-6** (Files: `daemon install` and `uninstall` on Windows; the daemon's start, mutex, sign-out handling and status file; the main process's cannot-start reading) — The service on Windows. **Start:** `sidekicks daemon install`, run by the CLI or by the main process, registers the per-user task `\AI Sidekicks\Background service` with a logon trigger, at the person's normal privilege and never "with highest privileges", set to restart the daemon after 1 minute if it fails, which runs `sidekicks-daemon`; its parent is Task Scheduler, never the app. The main process's start is running the task, at once where the mutex is free, saying `Starting the background service…` meanwhile. **One daemon at a time:** before any start the daemon takes the per-user mutex `Global\ai-sidekicks-service-<user SID>`, created with a user-only access list; `ERROR_ACCESS_DENIED` on its create means another program holds the name, handled as the pipe's squatter (`connectionNameTaken`). Main and the CLI check the mutex to tell whether the service is alive. **Sign-out:** the daemon keeps a hidden top-level window (a message-only window gets no broadcast), answers `WM_QUERYENDSESSION` with TRUE at once and never calls `ShutdownBlockReasonCreate`, and on `WM_ENDSESSION` flushes what it can and returns within about 4 seconds, inside the 5 Windows allows; every SQLite commit is already durable, and a turn in flight resumes from the provider's own conversation file at the next start. **Why it cannot start:** the daemon writes `%LOCALAPPDATA%\ai-sidekicks\run\service-status.json` beside the token when its start fails, never on a timer; when the pipe is absent, the main process and the Windows CLI check the mutex and read the file, and the `daemon.status` topic carries `cannotStart {reason: connectionNameTaken}`, which Runtime and `sidekicks daemon status` draw as `The background service cannot start because another program on this computer is using its connection. Restarting Windows usually clears it.` **Uninstall:** `sidekicks daemon uninstall`, from either kind of terminal, stops the service, then removes the logon task, the signed-out task where it was added, and the token and status files; it keeps the store, the account homes, the agent memory, the worktrees, the backups and the credential entries. **Tests:** a second start while the mutex is held exits without starting a daemon; a mutex another account created first stops the start as `connectionNameTaken`. **Spec coverage:** Spec-006 §The service on a Windows computer (start and lifetime; sign-out; why it cannot start; uninstall).
- **T-005r-4-7** (Files: the daemon's WSL server supervisor; the WSL server's environment capture; `crates/sidekicks-contracts/src/session/controls/events.rs`) — The WSL server's start, lifetime and failures. **Start**, when work first needs the distribution: the first time after that distribution started, the private mount (T-005r-4-13) with a one-shot `wsl.exe -d <distro> -u root --exec mount …` unless it is already there; then the system folder's `wsl.exe` (the folder as Windows reports it) as `wsl.exe --cd ~ -d <distro> --exec <home>/.ai-sidekicks/runtime/sha256-<digest>/bin/sidekicks-daemon wsl`, `<home>` the runtime row's absolute path, created suspended with no window in the daemon's Job set to `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`, then resumed, so `wsl.exe` ends with the daemon and a Windows program an agent started through interop outlives a stop, restart, update or crash. Its standard error is drained and thrown away for the process's whole life; the server writes its log lines to the daemon over the channel. Only the daemon runs `wsl.exe`; main, the Windows CLI and the `banners` instance never do, except under T-005r-4-8's fallback. **Work** keeps a distribution's server running: a session's provider process there (a Claude Code process until it sleeps, or the account's Codex service there while any Codex session there exists); that place's terminal Codex service while its switch is on; an account's five-minute read there; a terminal, running command or workflow step there; an armed file-watch trigger on a root there; an open session view's watches; a Preview carry or shared port into it; a backup or restore copying its part; a connected client of its endpoints. **Idle exit:** the server exits 10 minutes after the last work ends, closing its standard output first, and WSL then stops the distribution and the virtual machine on its own timers; the person's `.wslconfig` is never edited. **Stop:** a stop request on the control stream; the server ends its processes as `Stop` does, closes its output and exits within the service's drain bound; only if it still runs, `wsl.exe -d <distro> --exec kill -TERM <pid>` and, 2 seconds later, `-KILL`; never `wsl --terminate` or `wsl --shutdown`. **Unexpected exit** (the person's own `wsl --shutdown`, a WSL update): the daemon restarts the server when work needs it at 100 ms, 300 ms, 1 s, 3 s and 10 s, and each session resumes from the provider's own conversation file; Windows sessions are never touched. **Environment:** at each start the server runs the person's login shell once, as T-005r-3-12 does: a login and interactive shell in the home folder, with standard input from `/dev/null` and standard error discarded, running the program's own `environment <marker>` mode, which prints the environment between two marker lines, under a 5-second deadline; it keeps the environment between the markers, less `SHLVL`, `PWD` and `OLDPWD`, as the base its provider environments draw from; a missed deadline or missing markers ends the shell with its whole group, and the start proceeds with the passwd entry's environment and one log line naming the cause; provider binaries under the Windows drive mounts are ignored. **Deadlines:** every `wsl.exe` the daemon starts has one and is killed through its Job when it misses it: 10 seconds to start a server in a running distribution, the cold-start probe's figure from a stopped virtual machine, 5 for the list, 30 for a provider check, the runtime's copy by its size. After two missed deadlines with no success between them the daemon marks WSL as not answering and starts no more `wsl.exe`, trying again once after each wake and once an hour. **Sleep and wake:** the daemon's own sleep and wake are native; a server whose link ended in a sleep is restarted after the wake under these deadlines. **Sign-out:** on `WM_ENDSESSION` the daemon stops its WSL servers inside T-005r-4-6's 4 seconds. **Uninstall:** `sidekicks daemon uninstall` (T-005r-4-6) also removes, in each distribution with a runtime row, after the private mount is unmounted, `~/.ai-sidekicks/runtime/` and the `~/.local/bin/sidekicks` link, through a one-shot `wsl.exe --exec` (a stopped distribution is started for it, once). **Notices**, each a `session.notice.posted` and one flow row on the sessions it stops, never on Windows sessions and never the service's own cannot-start reading (T-005r-4-6): `wslNotAnswering {sessionId}` on every session in any distribution, `WSL is not answering. Restarting Windows brings it back.`; `distributionRestartFailed {sessionId, distro, error?}` after the fifth failed restart of one server, `Ubuntu stopped and could not start again. Restarting Windows usually brings it back.` with the error under it word for word, absent where the last start printed nothing before its deadline; `distributionRemoved {sessionId, distro}` on a session in a distribution that is no longer on this computer (`wsl --unregister`, a reset, or WSL uninstalled), `Ubuntu is no longer on this computer, so this session cannot run.`, the store and every transcript untouched and that distribution's runtime row dropped. **Tests:** the server exits on end of input and on a failed write; two missed deadlines stop further spawns until a wake; the fifth failed restart writes `distributionRestartFailed` once per session and touches no Windows session. **Spec coverage:** Spec-006 §The service on a Windows computer (sessions in a distribution: start, lifetime, failures; sign-out and uninstall in a distribution).

### Phase 2C — Substrate supplement: the socket path is length-checked before bind

**Goal:** the daemon refuses a socket path the platform cannot hold, and says so in its own words.

**Precondition:** Phase 2 merged.

#### Tasks

- **T-005p-2C-1** (Files: `crates/sidekicks-daemon/src/bootstrap/secure_defaults.rs` EXTEND + `crates/sidekicks-daemon/src/ipc/local_gateway.rs` EXTEND) — Check the resolved socket path against the platform's own address field before the bind, and choose the run directory so it fits. A Unix domain socket address is a fixed-size field — 104 bytes on macOS, 108 on Linux, whose `sun_path` that width is documented on in `unix(7)` (read 2026-09-21) — that the platform will neither truncate nor redirect, so the daemon picks a run directory short enough that the socket name still fits inside it with room for the file name. **The limit is the platform's own, never this plan's:** the path is checked with `std::os::unix::net::SocketAddr::from_pathname`, which refuses an over-long path with `InvalidInput` before any system call; the two numbers above are what those two platforms report today, not constants the code carries, so the figure in the refusal is the running platform's own and a third platform needs no edit here. Handed a longer one, it **refuses to bind and says the path is too long for a socket on this platform**, naming the limit and the length it was given, rather than passing through the malformed-address message at least one client library above the socket reports instead of a length ([Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior)). The daemon refuses the path itself, at startup, before any client is on the socket, so the refusal is its own startup message and no wire code: no new error code, no new setting, and no second place the path is decided.
- **Spec coverage:** Spec-006 §Required Behavior (the socket path has a hard length limit, so the daemon's run directory is short by design).
- **Tests:** a run directory at the running platform's own limit binds and answers a hello, and a path one byte over that limit is refused before the bind with the limit and the observed length both in the message. **Those two sides together are what prove the number came from the platform**, and neither alone does: a check holding the wrong constant fails the first side wherever the kernel is more generous than the constant — the path is refused although the bind would have worked — and fails the second wherever it is stricter, the check passing a path the bind then rejects with the platform's own malformed-address text, which is exactly the message this task exists to stop a person seeing. So the pair is run on each platform the suite runs on rather than asserted once against a stub, which would only check the stub. The refusal is the daemon's own startup message, with no wire code.

### Phase 2D — Substrate supplement: the subscription frame is batched, carries changes only, and never waits for a consumer

**Goal:** a change stream's feed (`ChangeFeed` in `crates/sidekicks-daemon/src/ipc/stream/frame_batcher.rs`) emits batched frames rather than one frame per event, and a consumer that cannot keep up is never waited for and never dropped for.

**Precondition:** Phase 2 merged — the primitive this phase widens is T-005p-2-5's.

#### Tasks

- **T-005p-2D-1** (Files: `crates/sidekicks-contracts/src/jsonrpc/streaming.rs` EXTEND + `crates/sidekicks-daemon/src/ipc/stream/frame_batcher.rs` CREATE — the change stream's frames, carried by the subscription T-005p-2-5 created) — Give the producer a batched frame that never waits for a consumer, so a fast session and a slow screen stop being the same problem. **The batch.** The producer sends the first change after a quiet spell at once and coalesces what follows into frames at the cadence [Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior) sets, so a single change is never held for a window while a burst still collapses into one delivery. **The frame carries changes and never the whole record**, and every change on it carries its own cursor, which is what lets a consumer say where it got to without the producer tracking it. **No drop.** The producer never waits for a consumer and never drops for one: it holds only the consumer's cursor and reads the next frame from the record once the lane has credit, so what a consumer holds is complete, never silently short, and the record rather than the consumer is the truth. **Far behind.** When a consumer's next frame is read while its cursor is further behind the record's head than Spec-006's threshold, counted in events and then in bytes, the producer sends it one frame with no changes that says it is behind and carries the head cursor, and the stream carries on from the head; the consumer takes one snapshot read instead of every change. Nothing else is minted: the frame is the already-registered `$/subscription/notify` shape widened with that mark, the snapshot is the read the surface already serves, and no new method, error code or setting appears. The frame's declared shape is registered at [local-ipc-payloads.md §Plan-005 — Local IPC And Daemon Control](../architecture/contracts/local-ipc-payloads.md#plan-005--local-ipc-and-daemon-control); the daemon's side stays canonical in code per that file's §Source-of-Truth Policy.
- **Spec coverage:** [Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior) (the subscription frame is batched, carries changes with their cursors, drops nothing and never blocks, and a subscription far behind takes a snapshot read).
- **Verifies invariant:** I-005-9 (the subscribe-init response still precedes the first frame, batched or not), I-005-10 (the far-behind frame ends nothing — a consumer sent it is still subscribed, so its feed is not released).
- **Tests:** a consumer that never reads does not stall the producer — asserted on the producer continuing to accept events while that consumer's cursor stands still, which is the property a producer awaiting its consumer would fail; a consumer that stops reading for fewer changes than the threshold and then reads receives every change in order, its rows equal to a never-behind consumer's exactly; a consumer that stops reading past the threshold receives exactly one frame with no changes, carrying the head cursor, and then only changes after the head, the negative control being a consumer one change short of the threshold, which receives every change and no such frame; and the first change after a quiet spell leaves at once rather than after a window, while a second change inside the window waits for it, which is the difference between the throttle this task specifies and a debounce.

## Dependency Decisions

**The command line parses with `clap` 4.6.7's derive subcommands.** The criteria: maintained, widely used, documented, light, and an API that meets I-005-13 and I-005-18 without workarounds. `clap` ([crates.io](https://crates.io/crates/clap), [repository](https://github.com/clap-rs/clap)), MIT or Apache-2.0, is the parser the Rust ecosystem uses most; `Parser::try_parse_from` returns every refusal, help and version as a `clap::Error` the program writes itself, with `exit_code()` telling success from refusal, so the injected writers and the one error boundary need no workaround, and it offers a near command for a mistyped one. The command line is one native binary, so no bundler is needed, and I-005-12's import isolation is the crate's `[dependencies]`, so no lint plugin is needed either. The port's library survey found no other maintained parser at this scale (252.4 million downloads at 4.6.7), so none was weighed against it; the exit-code table stays code of our own.

**Ctrl-C ends the command through `signal-hook` 0.4.5's `signal_hook::low_level::emulate_default_handler`** ([docs.rs](https://docs.rs/signal-hook/0.4.5/signal_hook/low_level/fn.emulate_default_handler.html)), in `sidekicks-platforms`' macOS and Linux code: it puts SIGINT's default action back and raises it in one async-signal-safe call, falling back on abort, where `nix` 0.31.3 and `libc`, already beside it, would be the same reset and raise written and kept by hand. Windows takes no crate: the command exits `0xC000013A` (`STATUS_CONTROL_C_EXIT`).

**The data-folder lock is `std::fs::File::try_lock` on `daemon.lock`.** The standard library's file lock (`flock` on macOS and Linux, `LockFileEx` on Windows) needs no lock library. The `File` is held open for the daemon's life, and the standard library opens files close-on-exec on macOS and Linux and not inheritable on Windows, so no child of the service holds it. The lock sits on its own file, never the database file, because on Linux NFS `flock` is emulated with `fcntl` locks, which would collide with SQLite's own.

**`daemon.status.read` reads the service's processes through `sysinfo` 0.39.6**, which lists the daemon and every process under it and reads each one's processor time and resident memory on macOS, Linux and Windows; the daemon sums the tree and divides the processor figure by the machine's cores. A parser of our own over `ps` and `/proc` would be code kept forever for what it already does. Also weighed: `libproc` 0.14.11, which reads macOS alone; `sysinfo` gives one interface on all three systems, which decided it.

**The purge deletes Claude Code's session files itself, with no Agent SDK.** The Agent SDK's `deleteSession()` (`@anthropic-ai/claude-agent-sdk` `sdk.d.ts`) removes a session's transcript and its folder only, so the daemon keeps its own deletes over the pinned build's per-session list (T-005r-1-9) rather than taking the SDK for two of those paths.

**The service's process identity is read with no library.** `sidekicks-platforms`' `process_identity`, which the daemon's status reply and, through the client helper, the desktop main process's check before each signal read, reads the system directly: on Linux a file under `/proc` per reading and the boot id once per reader, on macOS `proc_pidinfo` per reading and a `sysctl` once per reader, with no child process per reading. A start computed as the current time less the elapsed time, as process libraries give it, moves with a change of the clock, so two readings of one process could not be compared exactly; `proc_pidinfo` gives the start the system recorded, to the microsecond.

**Phase R4's choices.**

- **The WSL server is a mode of the Linux `sidekicks-daemon` program**, `sidekicks-daemon wsl`, beside `hook provider`, so the daemon on Windows does every Windows-only job in its own process and no other binary is built or signed.
- **`h2` 0.4.20** for both ends of each WSL server's channel, the daemon the client and the WSL server the server, over the standard input and output of the `wsl.exe` that runs it: a maintained HTTP/2 implementation with flow control, so the channel's multiplexing, backpressure and memory bounds are the protocol's, not code of our own.
- **`windows` 0.62.2** for the Win32 calls (power, the daemon's own kill-on-close job and the toast history through `UI_Notifications`, which `windows-sys` does not bind), Microsoft's own bindings.
- **`windows-native-keyring-store` 1.1.0** under `keyring-core` for Credential Manager, written with `persistence=local`, so no entry is written at Enterprise persistence, which roams with a domain profile.
- **tokio's named-pipe `ServerOptions`** for the pipe's server, which takes the first-instance flag, the remote-client refusal and an access list; the client opens the pipe with the standard library's `OpenOptions` and `security_qos_flags(SECURITY_IDENTIFICATION)`, without which a rogue server could act as the caller, checks that the process serving it runs as the person (`GetNamedPipeServerProcessId`, that process token's user, `EqualSid`), and converts the open file into `interprocess`'s stream.
- **The Linux runtime is `sidekicks-daemon` and `sidekicks` built for glibc and musl** on x64 and arm64, each archive with its SHA-256, with no Node runtime and no native module beside them: the musl `sidekicks-daemon` is the dynamic build with `libgcc_s.so.1` and `libpdfium.so` beside it, and the musl `sidekicks` one static program.

**Re-evaluate Phase R4's channel when** the binary-integrity probe finds `wsl.exe`'s standard input and output do not carry bytes intact, or the channel probe finds it too slow for Preview's debugger traffic.
