## Goal

Implement immutable artifact publication, attachment ingestion, and manifest-first visibility handling across local and shared session contexts.

## Scope

This plan covers artifact ids and manifests, attachment ingest, payload storage, visibility classification, shared-replication state, and the cross-node artifact relay: eager-pin ciphertext upload, authenticated `(user, node)`-scoped fetch with ack-driven delivery, refcount/TTL GC with quota accounting, and erasure fan-out.

## Non-Goals

- Full artifact preview UX
- Notification behavior for artifact publication
- Remote object-store vendor selection

- [x] Paired spec is approved
- [x] Required ADRs are accepted
- [x] Blocking open questions are resolved or explicitly deferred

Target paths below assume the canonical implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

## Data And Storage Changes

- Add durable `artifact_manifests`, `artifact_payload_refs`, and replication-status records with provenance, visibility class, and producer metadata.
- Keep manifest storage separate from large payload storage while preserving content-addressed lookup or equivalent immutable payload identity.
- Treat any redacted or summarized shared form as a separate derivative artifact record rather than as in-place mutation metadata on the original artifact.
- See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) for column definitions.
- Add the control-plane `artifact_relay_blobs` + `artifact_relay_recipients` tables per [Shared Postgres Schema §Artifact Relay Blob Store](../architecture/schemas/shared-postgres-schema.md#artifact-relay-blob-store-plan-012) — blob lifecycle metadata, per-`(user, node)` wrapped CEKs (durable artifact keys, thumbprint-tagged), delivery refcounts, fetch grace leases. Ciphertext chunk bytes live in the deployment's object store, never in Postgres. Both user references join the CP-020-6 erasure closure (see §Cross-Plan Obligations CP-012-2).
- The `artifact_manifests.replication_status` CHECK carries the spec-named value set: `pending_replication | pinned | over_cap | quota_exceeded | expired`.
- Add `artifact_manifests.relay_cek_ciphertext` — the publisher-retained, master-key-wrapped per-artifact CEK ([Local SQLite Schema §Artifact Tables](../architecture/schemas/local-sqlite-schema.md#artifact-tables-plan-012)). Written at Task 7's publish leg and read at every later re-publish as the re-wrap source, so a late joiner is granted access without the publisher re-encrypting the payload. Never leaves the publishing daemon and is never event-carried.
- Add the unique index `idx_artifact_relay_recipients_thumbprint` on `artifact_relay_recipients(ciphertext_digest, user_id, key_thumbprint)` ([Shared Postgres Schema §Artifact Relay Blob Store](../architecture/schemas/shared-postgres-schema.md#artifact-relay-blob-store-plan-012)) — the injectivity the key-thumbprint fetch selector depends on (I-012-6, CP-012-6). Additive DDL, no new table.
- **No schema change is made for the ingest stream protocol.** The ingest stream registry, its per-stream completion records, and the aggregate spool reservation are in-memory daemon state — a stream dies with the process and its spool goes quiescent for the `mtime` reaper — so no table is minted for a transient whose lifetime `max_ingest_stream_lifetime` already bounds, and the accepted cost is the named residual (a retried `Complete` after eviction ends as a second manifest row over one deduplicated CAS payload). The unobtainable-payload write-back reuses `artifact_manifests.replication_status`, whose existing CHECK already admits `expired` — this plan supplies the recipient-side writer that value lacked, not a new column.
- Add `artifact_relay_blobs.bytes_reclaimed_at TIMESTAMPTZ` ([Shared Postgres Schema §Artifact Relay Blob Store](../architecture/schemas/shared-postgres-schema.md#artifact-relay-blob-store-plan-012)) — `NULL` until the TTL sweep confirms the ciphertext object is reclaimed, then the start of the `relay_tombstone_grace` purge clock and the predicate byte-quota accounting filters on. Additive nullable column, no new table. No migration is owed: no `artifact_relay_*` DDL has shipped, so the column lands in the table's **first** `CREATE TABLE` shape. **No relay-side content reference count is added** and I-012-12's derived-CAS-refcount rule is deliberately **not** extended to the relay: `ciphertext_digest` is the blob table's primary key and per-artifact CEKs make two publishes of the same plaintext two different ciphertexts, so no second row can name one stored object and the reclaim is a plain idempotent object-store delete. Recorded because "gate the reclaim on a refcount" is the obvious wrong turn here, and its absence should read as a finding, not an omission. **Plus one partial index**: `artifact_relay_blobs (expires_at) WHERE state = 'expired' AND bytes_reclaimed_at IS NULL`, so the sweep's reclaim-retry pass seeks the unreclaimed tombstones directly instead of scanning the whole grace-window population, which grows with every sweep and is dominated by rows already reclaimed. The `expires_at` index alone cannot isolate them.
- **No schema change is made for the CAS reference count** — it is derived by query over `artifact_payload_refs.storage_path` (I-012-12), deliberately not a stored counter column. Recorded here because "add a refcount column" is the obvious wrong turn and its absence should read as a decision, not an omission.
- Add the daemon-local `artifact_encryption_keys` table per [Local SQLite Schema §Artifact Tables](../architecture/schemas/local-sqlite-schema.md#artifact-tables-plan-012) — one row per `(user, key_thumbprint)` with a partial unique index pinning exactly one active key; rotation **retires** (sets `retired_at`) rather than replaces, and retired rows persist until every relay row bearing their thumbprint is delivered or TTL-expired. The row joins the Spec-020 **Path-1** crypto-shred set (CP-012-2).

## API And Transport Changes

- Add `ArtifactPublish`, `ArtifactRead`, `ArtifactVisibilityUpdate`, `AttachmentIngest`, and `ArtifactDelete` to shared contracts and the typed client SDK — **five** named local interfaces.
- `AttachmentIngest` is carried as the `AttachmentIngestInit` / `AttachmentIngestChunk` / `AttachmentIngestComplete` trio under the Spec-006 1 MB frame ceiling, and `AttachmentIngestCompleteResponse` carries `derivedMediaType` and `derivedSizeBytes` — the server's own findings over the spooled bytes; Init's `mediaType` (**optional** — the pipeline's declaration-absent path is a first-class state a required field could never exercise) / `declaredSizeBytes` are annotated **advisory** and are reconciled, never persisted as fact (I-012-11). `ArtifactDeleteResponse` carries `payloadDisposition` and `rePublishForeclosed` so both consequences of a delete are visible at the call (I-012-12 — the disposition union reports a failed unlink truthfully, and the foreclosure member is grounded in the destroyed local CEK rather than a relay-liveness claim the daemon cannot derive). Attachment references on any carrier are typed `ArtifactId[]`, order-preserving, with an explicit unresolved marker rather than a silent omission (I-012-13). All of it is additive on an unshipped surface: no `AttachmentIngest` or `ArtifactDelete` reference exists under `packages/` or `apps/`.
- **No wire member is added, removed, or retyped by the stream protocol.** `AttachmentIngestCompleteRequest` still carries only the `ingestId` — which is exactly why the completion record is keyed on the stream and **stamped** with the committed digest rather than discriminated on a caller-supplied one: a _divergent_ Complete has no wire form to take, so the stamp is a fail-closed defence-in-depth check, never a new field. The retry semantics change only what a **second identical call** returns: the original response, verbatim, for as long as the stream's registry entry lives. No error code is minted: `artifact.ingest_stream_invalid` (409), `artifact.ingest_capacity_exhausted` (429), and `artifact.relay_expired` (410) are all already reserved in [error-contracts.md §Artifact](../architecture/contracts/error-contracts.md#artifact).
- The relay wire surface adds `ArtifactUploadInit` / `ArtifactUploadChunk` / `ArtifactUploadComplete` / `ArtifactFetchAuthorize` / `ArtifactFetchComplete` — five named methods which, together with the per-chunk authenticated fetch GETs, carry the six [Spec-019](./019-rate-limiting-policy.md) registry rows (`artifact.upload.init/chunk/complete`, `artifact.fetch.authorize/chunk/complete`); `ArtifactFetchComplete` is the authenticated post-verification delivery ack (I-012-8).
- Return manifest metadata first and use explicit payload handles for large or deferred content reads.
- Add the relay transfer surface per [Spec-012 §Cross-Node Artifact Relay (V1)](../specs/012-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1): `ArtifactUploadInit` / `ArtifactUploadChunk` / `ArtifactUploadComplete` (resumable, received-set discoverable) and `ArtifactFetchAuthorize` (`(user, node)`-scoped per I-012-10, DPoP-bound, 5–15 min PASETO fetch token) + per-chunk authenticated GETs, then `ArtifactFetchComplete` (the post-verification delivery ack, I-012-8); additive `artifact.published` event fields (`ciphertextDigest`, `chunkSize`, `chunkCount`, `chunkManifest`/`manifestDigest`, `cekCommitment`, `retentionTier` — wrapped CEKs are relay-held per-recipient rows returned at fetch-authorize, never event-carried); `replicationStatus` value-set refinement on the existing manifest field.

## Invariants

- **I-012-1 (Immutability):** A published artifact's payload is content-addressed (SHA-256) and never mutated in place; a live workspace path is never treated as durable payload identity. ([Spec-012 §Required Behavior](../specs/012-artifacts-files-and-attachments.md#required-behavior); verified by Task 2, Task 3.)
- **I-012-2 (Derivative-not-mutation):** A redacted/summarized shareable form is a separate manifest (own id, `subject` → original); the original manifest is never UPDATEd in place. ([Spec-012 §State And Data Implications](../specs/012-artifacts-files-and-attachments.md#state-and-data-implications); verified by Task 4, Task 12.) **Deletion inherits this:** `ArtifactDelete` on a manifest another manifest names as its `subject` is refused rather than satisfied by nulling the referent's `subject` — a null-out is exactly the in-place mutation of a foreign row this invariant prohibits, and it would silently sever the derivative's provenance chain (Task 12).
- **I-012-3 (Relay ciphertext-only):** No relay-side store (Postgres coordination rows or object-store chunks) ever holds plaintext payload or an unwrapped CEK; every relay-held key is wrapped to a durable per-`(user, node)` artifact-encryption key the relay does not possess. ([Spec-012 §Cross-Node Artifact Relay (V1)](../specs/012-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1) Required Behavior; verified by Task 7, Task 8, Task 10.)
- **I-012-4 (Loud integrity):** A chunk failing its signed-manifest digest is rejected and re-requested; an unwrapped CEK failing the signed `cekCommitment` refuses decrypt; a payload failing the post-decrypt CAS digest surfaces an integrity error — no code path yields silently-wrong bytes. ([Spec-012 §Cross-Node Artifact Relay (V1)](../specs/012-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1) failure modes; verified by Task 8.)
- **I-012-5 (Pinned means available):** `replicationStatus` reaches `pinned` only after every ciphertext chunk is relay-acknowledged **and the upload finalize has verified the assembled ciphertext against the ciphertext digest declared at upload-init** (the relay's CAS key — never the plaintext CAS digest, which the relay cannot compute; the CAS key is verified, never trusted; a re-pin re-verifies the stored copy, so re-publish repairs at-rest corruption, and re-anchors `expires_at` to the tier TTL — a fresh grant of the same bytes), and a `pinned` artifact's fetch path never depends on publisher reachability; publishes that cannot pin surface `over_cap` / `quota_exceeded` on the manifest (no blob row exists for them) — never a silent local-only fallback. **The converse direction is enforced too: a manifest stops claiming `pinned` once its own node observes that the pin is gone.** Either fetch-path refusal that establishes the payload is no longer obtainable — `artifact.relay_expired` (410) at the `ArtifactFetchAuthorize` mint, at a chunk GET, or on a resume after mid-fetch eviction, **or** a zero-row `artifact.no_access_key` (404), where a fetch lands once a GC path has removed the blob row and its recipient rows have cascaded away — transitions that node's own manifest row from `pinned` to `expired` in the same pass, before the error surfaces. The invariant keys on the fact rather than on either code, so it holds regardless of which lifecycle path retired the node's access. Without it `pinned` is a one-way latch on every recipient node: the relay's TTL sweep and watermark eviction run in the control plane and emit no event, so a recipient can observe expiry only by fetching, and a row left at `pinned` beside a dead blob makes this invariant's own claim — that a `pinned` artifact's fetch path never depends on publisher reachability — false of the persisted state a consumer actually reads. The write is a local single-writer update on a value the column already permits, is idempotent, applies only to a `pinned` row (a row already carrying a degraded status was never pinned), and is undone by an ordinary re-publish re-pin, so the status tracks availability rather than latching in either direction. **On the relay side, `state = 'pinned'` alone is not the liveness predicate.** Every relay read path evaluates a live pin as **`state = 'pinned' AND expires_at > now()`**, never `state` alone: the sweep is hourly, so a blob sits past its TTL for up to an hour before the sweep reaches it, and a read path trusting `state` would serve bytes the retention bound has already released and would make the sweep's schedule, rather than the contracted TTL, the thing that decides what the relay serves. The `artifact.relay_expired` (410) a past-TTL fetch receives is therefore correct **with no sweep in existence at all**, which is why it is a fetch-path obligation (Task 8) and not a garbage-collection side effect (Task 9). The offline-availability guarantee this invariant states is bounded by the same predicate: it holds while the pin is live and ends at the artifact's retention TTL. The same restatement is carried on **both** schema surfaces that attach the guarantee to `'pinned'` unqualified — the [Shared Postgres Schema §Artifact Relay Blob Store](../architecture/schemas/shared-postgres-schema.md#artifact-relay-blob-store-plan-012) blob-state comment (the relay side) and the [Local SQLite Schema §Artifact Tables (Plan-012)](../architecture/schemas/local-sqlite-schema.md#artifact-tables-plan-012) `artifact_manifests.replication_status` comment (the recipient side). The recipient side is the one that matters most: the sweep runs past the node boundary and emits no event, so a manifest row can read `pinned` while the relay has already released the bytes, and the fetch-path write-back is what reconciles it. ([Spec-012 §Cross-Node Artifact Relay (V1)](../specs/012-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1), [Spec-012 §Fetch (authenticated; relay-served in V1)](../specs/012-artifacts-files-and-attachments.md#fetch-authenticated-relay-served-in-v1), [Spec-012 §TTL sweep disposition (V1)](../specs/012-artifacts-files-and-attachments.md#ttl-sweep-disposition-v1); verified by Task 7, Task 8, Task 9.)
- **I-012-6 (Durable-key wrap):** A relay CEK is wrapped only to a durable artifact-encryption key (daemon-local `artifact_encryption_keys`, Spec-020 master-key custody, Ed25519-identity-attested) — never to an ADR-010 session-ephemeral X25519 key; a recipient daemon restarted between publish and fetch still unwraps its relay-held CEK, thumbprint-selected. (Spec-012 Publish step 3 + §Resolved Questions; verified by Task 7, Task 8.) **The thumbprint is also the fetch selector, and therefore must be injective per recipient row.** `artifact_relay_recipients` carries at most one row per `(ciphertext_digest, user_id, key_thumbprint)`, enforced by the unique index CP-012-6 registers, so the thumbprint set a daemon presents at `ArtifactFetchAuthorize` resolves to **exactly one** row or to none — never to an ambiguous set. This is what lets the mint derive `node_id` from the resolved row (I-012-10) instead of trusting a caller-supplied node identity: the durable key that unwraps the CEK and the key that names the row are the same key, so possession of the private half is what the whole path is keyed on. A **thumbprint is a public-key fingerprint, not a credential** — it is presented, never trusted as proof; authorization is carried by the authenticated `sub`, session access, the DPoP proof, and the `user_id` equality pinned inside the same predicate. Presenting another user's thumbprint resolves zero rows, because `user_id` is fixed to the caller's `sub` in the same lookup.
- **I-012-7 (Per-node delivery):** Delivery tracking and the refcount-zero GC trigger operate at `(user, node)` granularity — one user's fetch on one node never truncates another of their nodes' pending delivery; erasure removes all of a user's node rows in one user-keyed statement. (Spec-012 Delete steps 8–9; verified by Task 9, Task 10.)
- **I-012-8 (Ack-driven delivery):** `delivered_at` is written **only** by an authenticated `ArtifactFetchComplete` ack sent after the fetching node's chunk-manifest, `cekCommitment`, and CAS verifications all succeed — never inferred from a chunk GET; an un-acked fetch leaves the blob to its TTL rather than risking a premature GC of the last relay copy. The acked row is resolved from the fetch token's own `(user, node)` claims (I-012-10), never from a caller-supplied node id, and the ack is idempotent. (Spec-012 Fetch step 6 + Delete step 8; verified by Task 8, Task 9.)
- **I-012-9 (Rotation retains):** A retired artifact-encryption key is retained (thumbprint-keyed, never used for new wraps) until every relay row wrapped to it is delivered or TTL-expired, so rotation never strands a within-TTL pinned blob behind an offline publisher; exactly one active key exists per user per node. (Spec-012 Publish step 3; verified by Task 7, Task 8.) The daemon evaluates the retention predicate locally as `retired_at + 30 d + a 48 h skew margin` (the `extended`-tier TTL ceiling bounds it on the relay clock; the margin absorbs daemon-vs-relay skew) rather than querying the relay. The rule's second leg is **no late wraps**: rotation immediately re-attests the new active key to session peers and publishers wrap to the latest attestation per `(user, node)`, so a wrap to a retired thumbprint is confined to the seconds-scale re-attestation race and every row bearing it TTL-expires inside the purge bound — a session-frozen attestation cache would let stale wraps outlive the purge. **Third leg — a re-pin UPDATEs the recipient row in place rather than adding one.** The recipient row's primary key is `(ciphertext_digest, user_id, node_id)`, which the thumbprint is deliberately **not** part of, so a re-publish to a node that has since rotated must UPSERT on that key — replacing `wrapped_cek` and `key_thumbprint` — never INSERT. An INSERT violates the primary key, and a second row for one node would break I-012-7's per-node refcount by making one node's delivery need two acks. The consequence for this invariant is a **narrowing**: the retained retired key must cover exactly those rows no re-publish has since moved off its thumbprint, not every row ever wrapped to it, because a re-pinned row is now readable under the node's current active key and the retired key is irrelevant to it. Retention is still evaluated on the local `retired_at + 30 d + 48 h` predicate — the narrowing shrinks what is at risk, never the window.
- **I-012-10 (Node-bound fetch authorization):** A relay fetch token is scoped to `(user, node)`, the binding made at mint per RFC 9449 §5: the issuer stamps `(user, node)` as issuer-signed token claims, and sets the `cnf` confirmation claim from that call's DPoP proof, with no standing thumbprint→node registry (a bare `cnf`/jkt thumbprint is possession material, not an identity). **What the invariant prohibits, precisely:** the node-claim **value** is always **issuer-derived from the caller's own attach-state rows** and a **client-supplied raw node identity is never trusted**. It does _not_ prohibit a request field as such — a **validated opaque selector that picks among the caller's own attachment rows** is permissible, because the issuer still derives the value and still refuses any row not owned by the authenticated `sub`. The relay selects the wrapped CEK and resolves the `ArtifactFetchComplete` target row from the issuer-signed claims after verifying possession, so a node presenting a token minted for itself can neither read a sibling node's wrapped CEK nor mark that sibling delivered. **Mint-time authorization is user-granular, not node-granular** (`ArtifactFetchAuthorize` is a control-plane route whose access token carries `sub` and `cnf` and no node claim, and **V1 defines no node-identity credential** per [security-architecture.md §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature)), the same bound the Plan-005 T4.10 registrar resolves at, so a same-user sibling daemon obtaining a token for another of that user's nodes is not cryptographically excludable. **The V1 residual is availability and attestation/attribution integrity — not delivery attribution alone, and not confidentiality.** **(a) Availability:** `ArtifactFetchComplete` proves no CEK unwrap, so a compromised sibling forges the ack, clears the blob's last outstanding row, and refcount-zero GC destroys it; the honest node's own row cascades away with the blob so it does surface `artifact.no_access_key`, but that error's remedy is a publisher re-publish — unavailable in exactly the publisher-offline case the guarantee exists for. **(b) Attestation integrity (victim-node lockout):** the verifier's check is only that an attestation is signed by _a_ long-term Ed25519 identity key registered to that user, and a user carries several — each workstation holds its own, separately registered ([trust-and-identity.md §Edge Cases](../domain/trust-and-identity.md#edge-cases); no key is shared or copied between nodes) — so nothing binds the signing identity to the `node_id` it attests, and any user-authorized registered identity can bind an attacker-held X25519 key to a victim node's `node_id` and receives the CEK of every artifact published after the spoof (Spec-012 Publish step 3). Neither leg widens plaintext reach — an attached sibling is already an intended recipient holding the CEK under its own attested key, and plaintext reach by an authorized node is user-granularity sharing working as designed; the reachable harm is that the honest sibling is locked out and attribution is corrupted. Cross-user availability and confidentiality are untouched. Spec-012 §Required Behavior, the §Failure modes publisher-offline row, and both §Acceptance Criteria rows now carry the matching threat-model scope; the closure for all three legs is the cross-plan-dependencies.md Plan-012 row (added here — four rows now share the Plan-016/Plan-002 node-identity primitive). **The key-thumbprint selector satisfies this rule rather than relaxing it.** The issuer derives `node_id` from the **`artifact_relay_recipients` row the presented thumbprint set resolves**, which is a row the issuer reads, pinned to the caller's own `user_id`, and never a value the caller states — a validated selector over the caller's own rows, not a raw node identity. **The mint additionally carries a corroboration step:** having derived `node_id`, the issuer requires an **active-state `runtime_node_attachments` row for that `node_id`, with `user_id` = the authenticated `sub`, in the blob's own `session_id`** (a row attesting another user's `node_id` must fail corroboration, never mint claims describing an attachment that does not exist) before minting, so a stale recipient row for a node that has since detached no longer yields a token. It can only refuse more, and it is why the Plan-002 dependency edge is corroboration (Dependencies row). **Mint-time authorization remains user-granular**, and the compromised same-user-sibling residual above is untouched: the sibling holds its own durable key and its own thumbprints, so it resolves its own row exactly as designed. The selector disambiguates the caller's own nodes; it is not a defence against that residual, whose closure is the §V1.1+ row named above. (Spec-012 Fetch steps 5–6; verified by Task 8.)

- **I-012-11 (Server-derived, bounded ingest):** For caller-supplied bytes crossing the client→daemon trust boundary — the `AttachmentIngest` trio, and a boundary-crossing `ArtifactPublish`, because the pipeline binds to the boundary rather than to a method name (a boundary-crossing publish declaring the `file` family is refused outright and directed to `AttachmentIngest`) — the daemon derives media type and size **from the payload bytes it received**, and a caller-declared `mediaType` or `sizeBytes` is advisory input that is reconciled against the derived value, never persisted as fact and never used to make an admission decision. Every bound in [Spec-012 §Ingest Validation And Payload Bounds (V1)](../specs/012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1) is applied **before** any byte reaches the CAS or any manifest row is written, so a refused payload leaves no durable artifact behind; a payload whose signature cannot be determined is refused rather than admitted on the strength of its declared type unless that type is on the signature-exempt textual allow-list **and** the bytes prove well-formed UTF-8 — in which case the recorded classification is the declared subtype admitted under the exemption, an allow-list-bounded declaration rather than trust in the declaration (fail-closed — the one arm where "unknown" must not read as "probably fine"); a payload that fails a content gate (steps 3–8) is quarantined outside the CAS with no manifest, removed at `ingest_quarantine_ttl` or earlier under the `ingest_quarantine_max_bytes` oldest-`mtime`-first eviction (an entry that cannot fit even an emptied quarantine is deleted rather than held), while a stream breaching the byte bound is terminated with its spool deleted — refused garbage, never quarantined. The other five `artifactType` families are producer-fixed and do not traverse this path **when the daemon itself produces them**; the same families arriving across the trust boundary do. **"Bounded" means bounded under concurrency, and "retry-safe" means retry-safe for the whole trio.** Three rules join this invariant. **(a) Completion is idempotent within its stream's lifetime.** The `AttachmentIngestComplete` response is recorded on that stream's registry entry, stamped with the committed digest, and a retry replays it verbatim — no gate re-run, no second manifest row. A lost response must not cost the caller a 100 MB re-upload, and the opposite failure is equally prohibited: re-running steps 3–8 and minting a second manifest for one completed stream. Completion surrenders the reservation, the count slot, and the spool at commit, so a completed entry pins no budget; past `max_ingest_stream_lifetime` the entry and its record are evicted and a retry takes the ordinary `artifact.ingest_stream_invalid` (409), whose named residual is one extra manifest row over a deduplicated CAS payload — never duplicated bytes, never a lost artifact. **(b) Both byte ledgers this pipeline bounds are reserve-then-install.** The aggregate admission ledger (`max_active_ingest_streams` plus the `ingest_spool_max_bytes` reservation total) and the quarantine directory (`ingest_quarantine_max_bytes`) each test and spend inside one critical section: a bound checked outside the mutation that spends it is exceeded by up to one payload per racing caller, which is the parallel-submission form of the very denial-of-disk each cap exists to stop. **(c) Every call on one `ingestId` is single-flight, and the reaper's eviction path takes the same exclusion** — sequence validation, spool append, running-count and last-chunk-digest advance, and acknowledgement are atomic per call, so an original racing its own retry cannot double-append or compare against half-updated state, and a stream is never served and evicted at once. The exclusions compose in one total acyclic order — per-`ingestId` → the admission ledger → at most one of per-`storage_path` or the quarantine directory ([Spec-012 §Implementation Notes](../specs/012-artifacts-files-and-attachments.md#implementation-notes)). A refused Init still creates nothing, and that is asserted through **admission** — the next Init admitting once a slot or reservation frees — never through an identifier the refusal never issued. ([Spec-012 §Ingest Validation And Payload Bounds (V1)](../specs/012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1); verified by Task 11.)
- **I-012-12 (Reclaim-at-zero):** A CAS payload is reclaimed only when its derived reference count reaches zero — the count is **computed over `artifact_payload_refs.storage_path`, never stored in a counter column**, so it cannot drift out of agreement with the rows it summarizes and no reconciliation job is owed. `ArtifactDelete` removes one manifest and its own payload-ref; the shared blob survives while any other manifest still references it (the Task 2 / Task 3 dedup guarantee is exactly the case that makes this load-bearing). Reclaim is concurrency-excluded per storage key: every CAS writer checks-and-references inside that key's in-process exclusion, every reclaimer — the boot sweep included — derives-and-unlinks inside it, and the unlink re-derives the count after commit and aborts above zero, so no interleaving of a same-hash publish with a reclaim leaves a manifest over missing bytes. That per-key exclusion is one **leaf** of this plan's single acquisition order — per-`ingestId` → the ingest admission ledger → at most one of per-`storage_path` or the quarantine directory, the two leaves never held together ([Spec-012 §Implementation Notes](../specs/012-artifacts-files-and-attachments.md#implementation-notes)) — so the ingest path's exclusions compose with this one rather than racing or deadlocking against it; `AttachmentIngestComplete` is the path that holds a stream exclusion and then takes this leaf for its step-8 CAS rename. Deletion is refused rather than cascaded when the manifest is another manifest's `subject` (I-012-2), and a delete that destroys the last local copy of a live relay pin proceeds but must surface that re-publish is no longer possible — the publisher's plaintext is gone, so the loss is stated at the call rather than discovered at the next re-pin. ([Spec-012 §Local Artifact Deletion And CAS Reclaim (V1)](../specs/012-artifacts-files-and-attachments.md#local-artifact-deletion-and-cas-reclaim-v1); verified by Task 12.)
- **I-012-13 (No silent attachment drop):** An attachment reference carried by any turn-scoped payload is a typed `ArtifactId`, never an opaque `unknown`, and the reference list is **order-preserving**: the position an attachment occupies on the way in is the position it occupies on the way out. An attachment that cannot be delivered — a deleted artifact (including a payload reclaimed under I-012-12), `local-only` visibility on a remote node, an over-cap payload — is rendered as an **explicit unresolved marker in its own position** and never omitted, because a silently shortened list makes the recipient reason about a message that was never sent; the marker is **cause-bearing**, naming which member of that closed union applies, because the remedies differ per cause and honest degradation beats uniform opacity. The carrier is additionally bound by `max_attachments_per_carrier`, refused as a whole rather than truncated to fit. **The cause is read from persisted state, and every member of the union has a writer.** The marker's replication-status arm reads the rendering node's own `artifact_manifests.replication_status`, never live relay state the renderer cannot observe, so a cause is nameable exactly when some writer has recorded it: `pending_replication`, `over_cap`, and `quota_exceeded` are publish-path values reaching recipients through manifest-first replication, and `expired` is written by the fetching node's own relay-410 handling (I-012-5). That writer is what makes the union's sixth member reachable rather than a token no row ever carries — and it forecloses the worse state, where an expiry-blocked attachment presents a still-`pinned` manifest matching **no** member of a closed union. ([Spec-012 §Required Behavior](../specs/012-artifacts-files-and-attachments.md#required-behavior), [Spec-012 §Fallback Behavior](../specs/012-artifacts-files-and-attachments.md#fallback-behavior); verified by Task 13.)
- **I-012-14 (Relay admission precedes the body, and rate refusal is never quota refusal):** Every one of the six `Spec-019` relay registry rows is admitted **before any byte of the request body is consumed** — the property is stated over the request, not over a transport, because the six rows do not share one: `artifact.fetch.chunk` is a per-chunk authenticated GET ([Spec-012 §Cross-Node Artifact Relay (V1)](../specs/012-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1)), while the upload legs' transport is deliberately unshaped in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) ("Deliberately not typed here yet — no invented shapes"), so the obligation binds whichever way they land. **But it constrains the transport rather than merely adapting to it**, because one of the two candidate mountings cannot satisfy it: tRPC's fetch adapter must read and parse the request body to resolve the procedure's input before any procedure-level middleware runs, so a `rateLimitProcedure` wrap on a body-bearing upload leg admits **after** the payload has already been consumed — precisely the byte spend this invariant exists to prevent, and worst on `artifact.upload.chunk`, the largest and most frequent body of the six. The rule is therefore: a row whose request carries a body is admitted at the **host/raw-route seam before the body parser**, via `checkAdmission`, keyed on identity available outside the body (the authenticated user or session from the token, and the upload id from the path or a header — never from a parsed field); `rateLimitProcedure` is available only to a row whose surface is a tRPC procedure **and** whose admission key is resolvable without reading the body. If the upload legs land as tRPC procedures, this invariant is what forces a pre-parse admission hook in front of them rather than a middleware wrap, and that consequence is deliberate. **The property is a floor on how late admission may run, never a licence to run it before the caller is known.** A caller-keyed row is admitted only once the identity it keys on is **authenticated**, which for the three `artifact.fetch.*` rows means after the fetch token's signature _and_ its RFC 9449 DPoP proof validate: the token is sender-constrained, so its `sub` names a user but does not establish that the presenter is that user until the proof is checked. Admitting on the unproven `sub` would let anyone holding a leaked fetch token without its proof key drain the legitimate user's bucket with proofs that were always going to be rejected — a refusal charged to the victim. The two bounds do not conflict, because DPoP validation reads only the request's headers and the presented token: authentication completes, admission runs, and the request body (upload rows) or response payload (fetch rows) is still untouched. What that ordering deliberately does **not** do is make this plan the owner of the anonymous-tier disposition: `Spec-019`'s `unauthenticated.request` fallback bucket is scoped by that spec to unauthenticated **procedures**, and its wiring is assigned to Plan-019 T21.3-6 by the D-019-6 table, so a raw-GET fetch route's pre-authentication coverage is `Spec-019`'s question and that row's owner's to answer. This invariant claims only what it can enforce here — a failed authentication is charged to nobody's caller-keyed bucket, least of all the victim's. **Second clause:** a request-rate refusal and a byte-quota refusal are distinguishable at the client. Both are `429`, and conflating them is a real failure — a caller told "slow down" retries after the window and succeeds, while a caller over its storage quota must free bytes or stop, and retrying is futile. The rate refusal carries `Spec-019`'s canonical `RateLimitResponse` with its window timing fields; the quota refusal is the Task-9 backpressure arm, whose publish degrades to `quota_exceeded` and whose retry advice is not a window. Neither borrows the other's envelope.
- **I-012-15 (Tombstoned expiry; shred before reclaim):** The hourly TTL sweep **retains** the blob's coordination row as a **payload-free tombstone** at `state = 'expired'` — a row naming a digest, a session, a byte count, and timestamps, with every `artifact_relay_recipients` row for that digest hard-DELETEd at the sweep's intent and `publisher_user_id` `NULL`ed at its reclaim confirmation — so a post-TTL fetch is refused the typed `artifact.relay_expired` (410) instead of collapsing into the zero-row `artifact.no_access_key` (404) that means "you hold no grant". The other two GC paths keep the removing disposition: refcount-zero delete and watermark eviction delete the row and cascade the recipient rows. **The sweep's order is one-way and mandatory:** the shred and the state transition commit in **one** transaction; the object-store bytes are reclaimed strictly after that commit; `bytes_reclaimed_at` and the `publisher_user_id` `NULL` are stamped together, last (the reference is held exactly as long as the bytes it attributes, so stored bytes are never charged to nobody). The coordination row is the **only** index into the stored object, so a crash at any point must leave a retryable tombstone carrying `bytes_reclaimed_at IS NULL` rather than an orphaned object that no row names, no quota counts, and no later pass revisits — and the retry is safe precisely because the relay holds no content reference count (`ciphertext_digest` is the primary key and per-artifact CEKs preclude cross-publication dedup), so the reclaim is a plain idempotent object-store delete rather than a refcount-gated one. A tombstone **spends no byte quota** from the moment its bytes are reclaimed (accounting filters on `bytes_reclaimed_at IS NULL`), is **purged** once `bytes_reclaimed_at + relay_tombstone_grace` elapses — after which the same fetch takes the 404 arm — and is **cleared** by a re-publish UPSERT that re-anchors `expires_at`, returns `state` to `pending_replication`, and nulls `bytes_reclaimed_at`, without which a re-pinned blob would be purged on the previous reclaim's clock while live — **but that UPSERT is fenced**: a re-publish arriving on a row at `state = 'expired' AND bytes_reclaimed_at IS NULL` is refused `429` with `Retry-After` rather than re-pinning, because the reclaim it would race is an external delete the `SKIP LOCKED` claim's transaction has already committed across. **Stages (2) and (3) additionally run under a session-level advisory lock keyed on the digest**, so that same committed-transaction gap cannot put two sweep passes on one key: a pass that cannot take the lock skips the row rather than deleting behind the holder, and a holder that dies releases with its session, leaving the retryable `NULL` intact. The tombstone carries **no user reference once its reclaim confirms**, and its one pre-reclaim reference is the already-enumerated `artifact_relay_blobs.publisher_user_id` anonymize-class FK, so it adds no row to the [Spec-020 §PII Data Map](../specs/020-data-retention-and-gdpr.md#pii-data-map) and no leg to the CP-020-6 closure at either stage; what the sweep does to the two references the relay does carry is the disposition Spec-020 already assigns each of them, fired by a lifecycle trigger rather than an erasure request (CP-012-2). ([Spec-012 §TTL sweep disposition (V1)](../specs/012-artifacts-files-and-attachments.md#ttl-sweep-disposition-v1), [Spec-012 §Delete (refcount + TTL + crypto-shred)](../specs/012-artifacts-files-and-attachments.md#delete-refcount--ttl--crypto-shred) step 8; verified by Task 9.)

under `ArtifactIdSchema`** and is typed as the **branded** `ArtifactId` rather than a bare string, and **no two minted ids are equal** — plus one **ordering smoke assertion** over that batch (the ids are non-decreasing), which holds whether or not the batch happens to share a millisecond and so is deterministic on any host. It deliberately stops there. The **same-tick counter ordering, the clock-rollback floor, and the 12-bit overflow rollover are consumed properties of `mintUuidV7`, proved deterministically in that generator's own suite** (`packages/runtime-daemon/src/ids/__tests__/uuid-v7.test.ts`), which is where an injected time source belongs: `UuidV7Minter` takes `readCurrentTimestampMilliseconds` and `fillWithRandomBytes` as injectable dependencies, and under a frozen clock that suite asserts 512 ids strictly increasing with the [RFC 9562 §6.2](https://www.rfc-editor.org/rfc/rfc9562#section-6.2) Method 1 `rand_a` counter incrementing by exactly one per mint, a clock stepped 5,000 ms backwards still yielding a strictly greater id stamped with the retained tick, and — under a saturated random fill that pins the seed — the counter exhausting at `0xfff` inside one tick before the next mint advances the emitted timestamp by a millisecond and reseeds. A negative control pins that this task's own test can fail: `crypto.randomUUID()`'s output — the idiom this helper exists to displace — is refused by the same version assertion. **This module carries the same structural guard T14.3's does:** a source-level check that `artifact-id.ts` imports `mintUuidV7` and references neither `randomUUID` nor `getRandomValues`, so an edit that inlines a generator here fails rather than passing on a version-agnostic schema. - **T14.11 — Ingest validation pipeline.** Implement the ordered gate chain of [Spec-012 §Ingest Validation And Payload Bounds (V1)](../specs/012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1) in a dedicated `packages/runtime-daemon/src/artifacts/ingest-validation.ts`, invoked by `attachment-ingest-service.ts` (Task 2) **before** any byte reaches the CAS or any manifest row is written — against the wire shape the transport dictates: `AttachmentIngest` is carried as the `AttachmentIngestInit` / `AttachmentIngestChunk` / `AttachmentIngestComplete` trio ([Spec-012 §Ingest Validation And Payload Bounds (V1)](../specs/012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1) transport binding — the Spec-006 1 MB frame ceiling makes single-call ingest un-implementable at the size cap), where Init refuses a declared total above the cap up front, each Chunk appends to a daemon-spooled temporary file **outside the CAS** with the running count refused at the cap and the spool deleted on breach (an over-cap stream is refused garbage, never quarantined), and Complete runs steps 3–8 over the spooled bytes — **and this task ships the full stream protocol** ([Spec-012 §Ingest Validation And Payload Bounds (V1)](../specs/012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1) stream protocol): Init admission refuses `artifact.ingest_capacity_exhausted` (429, transient, no stream state) at `max_active_ingest_streams` or when the aggregate of open streams' declared totals would breach `ingest_spool_max_bytes`, with the Init declaration enforced as the stream's spool **reservation and per-stream ceiling** (a chunk pushing the running decoded count past it refuses `artifact.too_large` and deletes the spool — unenforced declarations would make the admission arithmetic gameable); sequencing retains the last acknowledged sequence number plus the last appended chunk's SHA-256, acknowledging an exact replay idempotently **without re-appending** while a gap, regression, or same-sequence different-bytes chunk terminates the stream and refuses `artifact.ingest_stream_invalid` (409), the same code every later call on a terminated, lifetime-expired, or unknown `ingestId` receives — and every later `Chunk` on a completed one, the single carved exception being a replayed `Complete` on a completed stream whose completion record survives (the hardening rules below); and stream tenure is wall-clock-bounded by `max_ingest_stream_lifetime` from Init, enforced on-call **and by the reaper pass** — every pass of the same daemon-local reaper this task ships evicts over-lifetime registry entries, terminating the stream, releasing its reservation and count slot, and deleting its spool, so a silently-abandoned stream cannot pin the admission budget (the in-memory stream registry carries the Init timestamp — a crashed daemon's streams die with the process and their spools go quiescent for the `mtime` reaper) — step 8's admitting CAS rename committing the payload as the pipeline's final successful act — with an abandoned stream's spool reaped by the same `mtime`-clocked reaper this task ships, chunk bytes riding the JSON wire as RFC 4648 base64 bounded by the fixed wire-derived `max_attachment_chunk_bytes` (512 KiB — base64 expansion plus envelope fits the frame ceiling by arithmetic) with every byte bound binding the decoded count — and land the bounds as a typed, operator-overridable config object in `packages/contracts/src/artifacts/ingest-limits.ts` (the `relay-limits.ts` precedent from Task 9 — defaults live in code with an import target, never transcribed from a table) — including the `ingest_quarantine_max_bytes` aggregate quarantine bound and the **normative default allow-list** (the signature-exempt textual subset plus the signature-verified binary set, SVG deliberately absent — [Spec-012 §Bounds (normative defaults; operator-tunable)](../specs/012-artifacts-files-and-attachments.md#bounds-normative-defaults-operator-tunable)), with an operator override replacing the list wholesale, the fixed wire-derived `max_attachment_chunk_bytes` (512 KiB — the base64 frame-fit chunk ceiling, deliberately not operator-tunable because the Spec-006 frame ceiling it derives from is not), and the three stream-protocol bounds `max_active_ingest_streams`, `ingest_spool_max_bytes`, and `max_ingest_stream_lifetime`, with the cross-parameter relation `ingest_spool_max_bytes` ≥ 2 × `max_attachment_ingest_bytes` validated at config load (a violating override is refused, never accepted into a daemon where every maximal Init would 429 permanently). **This task additionally ships three stream-protocol hardening rules** ([Spec-012 §Ingest Validation And Payload Bounds (V1)](../specs/012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1) stream protocol — the completion-record and single-flight rules, plus the serialization clause on the admission rule). **(i) A completion record makes `AttachmentIngestComplete` retry-idempotent.** The Complete leg records the `AttachmentIngestCompleteResponse` it returned on that stream's registry entry, stamped with the digest the run committed; a `Complete` arriving on a stream that already holds one replays that response verbatim — same `artifactId`, same `contentHash` — re-running no gate and inserting no second `artifact_manifests` row. Commit still releases the stream's reservation, count slot, and spool, and the entry survives only to hold the record, so a completed stream pins no admission budget; the lifetime reaper evicts completed entries the same way it evicts live ones, taking the record with them. A record whose stamp disagrees with the entry's own committed state fails closed to `artifact.ingest_stream_invalid` — defence in depth against a state a daemon-minted single-use `ingestId` makes unreachable, since `AttachmentIngestCompleteRequest` carries no member beyond the `ingestId` and a _divergent_ Complete has no wire form. **(ii) Both byte ledgers are reserve-then-install.** Init admission is one critical section over reading the open-stream count and the reserved-byte total, testing both bounds, and installing the entry with its reservation — never a check followed by a separate write, which two concurrent Inits each pass before either writes. The quarantine writer takes the same shape under the quarantine directory's own exclusion: measure the aggregate, evict oldest-`mtime`-first until the entry fits, reserve its bytes, install — with the TTL reaper's pass under that same exclusion so a reap cannot race the eviction loop's accounting. **(iii) Every call on one `ingestId` runs inside a critical section keyed by that `ingestId`**, covering sequence validation, spool append, running-count and last-chunk-digest advance, and acknowledgement as one unit, so an original and its retry racing after a lost response take the replay path rather than double-appending. The lifetime reaper's eviction takes the same exclusion — snapshotting candidates under the admission ledger, releasing it, then acquiring each candidate's exclusion and re-checking state before evicting — so eviction never deletes a spool mid-append or releases a reservation mid-commit. Acquisition order across all of it is total and acyclic: per-`ingestId` → the admission ledger → at most one of the Task-12 per-`storage_path` CAS exclusion or the quarantine directory, never both ([Spec-012 §Implementation Notes](../specs/012-artifacts-files-and-attachments.md#implementation-notes)); `Init` takes the ledger alone, introducing no back edge. The nine steps ship in order: size cap → count cap → magic-byte sniff → declared-vs-derived reconciliation → extension + media-type allow-list (deny-by-default) → the undetermined-signature closure → path validation + CAS address derivation → the antivirus **seam** whose admitting arm lands the CAS-keyed storage rename → quarantine. **This task also ships the quarantine reaper**, because the component that writes quarantine owns reaping it: a daemon-local directory scan that unlinks entries whose filesystem `mtime` is older than `ingest_quarantine_ttl`, per [Spec-012 §Ingest Validation And Payload Bounds (V1)](../specs/012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1) step 9. It is deliberately **not** Task 9's hourly relay sweep — that one runs in the control plane over pinned blobs, a different store on the other side of the node boundary — and it deliberately needs **no table**: quarantined bytes are referenced by nothing by construction, so `mtime` is the arrival clock and the directory is the index. A TTL asserted with no reaper is the promised-but-unrunnable class, which is why the owner is named here rather than left to the relay. `AttachmentIngestCompleteResponse` carries `derivedMediaType` / `derivedSizeBytes` — the server's own findings, returned so the caller can see what was actually recorded rather than assume its declaration survived. **Library decision — adopt [`file-type`](https://github.com/sindresorhus/file-type) v22.0.2, do not hand-roll signature detection.** Verified at the registry rather than recalled: version `22.0.2`, MIT, `"type": "module"` (ESM-only), `engines.node >= 22` — satisfied by this repo's `>=22.12.0` floor — with roughly 3.4k dependent packages and a publish cadence in months, not years. The build-it alternative was rejected on maintenance grounds, not effort: a hand-rolled sniffer means owning a signature table of hundreds of formats plus their offset and container quirks, and a stale table fails **open** (an unrecognized real format looks undetermined), which is the one direction this pipeline must not fail. The library is scoped as a **detector, not a policy engine** — allow-listing, reconciliation, and every refusal decision stay in our code, so swapping detectors changes no security behavior. Two integration constraints are contract-relevant and drive the design rather than being worked around: it detects **binary** signatures only and returns nothing for text formats (`.txt`, `.csv`, `.svg`), which is precisely why step 6's signature-exempt subset plus a UTF-8 well-formedness check exists instead of treating "undetermined" as "fine"; and it must be handed a **bounded leading prefix** with detection under a timeout, never pointed at container interiors, per the section's own scope limit. **Assertion:** an oversize payload is refused with `artifact.too_large` (413) before the parser is invoked at all (asserted by a detector spy that must never be called); a payload whose declared `mediaType` contradicts its leading signature is refused with `artifact.unsupported_media_type` (415) and is **not** silently corrected; a payload whose extension is allow-listed but whose derived type is not is refused, and so is the converse; a payload with an undetermined signature and a non-exempt declared type is refused, while the same payload with a signature-exempt declared type and well-formed UTF-8 bytes is accepted **and records the declared subtype, admitted under the exemption** — never a subtype invented from the bytes (the recorded classification is "allow-list-bounded declaration over byte-proven UTF-8"); a double-extension and an embedded-null filename each fail step 5 after full decoding; every refusal at steps 3–8 leaves **zero** CAS entries and **zero** `artifact_manifests` rows, with the bytes in quarantine and unreachable via `ArtifactRead`; the reaper unlinks a quarantined file whose `mtime` is older than `ingest_quarantine_ttl` and leaves a younger one in place (asserted by back-dating `mtime` across the boundary in both directions, so the test fails if the reaper is a no-op **or** over-eager); a quarantined entry's stored path derives from server-generated material only — a traversal-shaped or null-byte filename that fails step 5 reaches quarantine as bytes under a digest-or-random name, never as a path component; a new quarantine entry that would breach `ingest_quarantine_max_bytes` evicts existing entries oldest-`mtime`-first until it fits (asserted with back-dated `mtime`s proving the older entry is evicted before the younger); #### Tasks

- **T14.8 — Authenticated relay fetch + integrity.** Implement the fetch half: `ArtifactFetchAuthorize` mints a `(user, node)`-scoped, DPoP-bound (RFC 9449), 5–15 min PASETO fetch token against the caller's session access — `node_id` stamped as an issuer-signed claim and `cnf` bound from that call's DPoP proof per RFC 9449 §5, never a trusted client-supplied raw node identity (I-012-10). **Why the node selector is needed at all:** with two nodes of one user attached, `sub` names only the user, `cnf` is possession material rather than an identity, and no request field disambiguates — so the issuer has multiple candidate attach rows and no rule to choose among them. **The selector is the caller's artifact-encryption key-thumbprint set.** The daemon presents the thumbprints of the artifact-encryption keys **it itself holds** — the values in its own `artifact_encryption_keys` rows, active and retired alike, which are the same values that tag its `artifact_relay_recipients` rows. The issuer resolves the predicate `ciphertext_digest` = the digest under fetch, `user_id` = the authenticated `sub`, and `key_thumbprint` ∈ the presented set. **Exactly one row must match.** On one row, the issuer derives `node_id` **from that row** and proceeds. On zero rows, it refuses with `artifact.no_access_key` (404) — the caller has session access but no grant, whose remedy is a publisher re-publish. On two or more rows it refuses **fail-closed** with `artifact.fetch_unauthorized`, never picking one: a multi-match means the uniqueness the whole derivation rests on has been violated, and guessing which node the caller meant is precisely the client-supplied node identity I-012-10 forbids. **Then the issuer corroborates:** it requires an **active-state `runtime_node_attachments` row for the derived `node_id`, with `user_id` = the authenticated `sub`, in the blob's own `session_id`** before minting — so a recipient row for a node that has since detached does not yield a token, and neither does one whose attested `node_id` names **another user's** attached node (the user leg: the attestation-spoofing residual lets a registered identity attest a foreign `node_id`, and a node-and-session-only corroboration would mint a token whose `(user, node)` claims describe no attachment that exists). The blob's `session_id` keeps the predicate strictly tighter than session access alone — `runtime_node_attachments` is UNIQUE on `(node_id, session_id)` and carries `user_id`, so all three legs resolve on one row — and binds the grant to the session the artifact actually belongs to. **The corroboration failure refuses with `artifact.fetch_unauthorized` (403), never `artifact.no_access_key`**: the caller demonstrably holds a wrapped-CEK grant — the recipient row resolved cleanly — so the 404's re-publish remedy would mislead every client that surfaces it; what lapsed is the node's attachment, and the remedy is re-attaching the node to the session (Spec-012 Fetch step 5, failure-mode table).

**Relay-side liveness is enforced on this path, not inherited from the sweep** ([Spec-012 §TTL sweep disposition (V1)](../specs/012-artifacts-files-and-attachments.md#ttl-sweep-disposition-v1)). Three rules land here rather than with Task 9, because each is correct **with no TTL sweep in existence** and the phase that builds the sweep is a later PR — the same reasoning that split T14.14 from T14.15, and this plan's own rule that a gate cannot precede the call site it is installed on. **(a) Read-time expiry.** Every relay read path evaluates a live pin as `state = 'pinned' AND expires_at > now()`, never `state` alone; a fetch against a row past its TTL is refused `artifact.relay_expired` (410) immediately. The sweep is hourly, so without this a blob is served for up to an hour past the retention bound the operator set, and the schedule rather than the contract decides what the relay serves. **(b) Liveness is checked before the thumbprint selector at the mint.** `ArtifactFetchAuthorize` evaluates the blob's liveness first and refuses 410 there, ahead of resolving the recipient rows of Fetch step 5. Ordering it the other way makes the answer depend on whether the sweep has run: before the sweep's shred the selector resolves a row and the mint would issue a token for bytes that are gone or going, and after it the same request resolves zero rows and takes the 404. Liveness-first returns the same 410 on both sides of the sweep. It discloses nothing new, because replication is manifest-first — every device in the session already holds a manifest row naming the digests published to the session — and the check is on the blob the caller named, never on a grant the caller has not yet demonstrated. **(c) The unobtainable-payload write-back ships here, not with Task 9.** The fetching daemon's `pinned` → `expired` transition fires on either refusal that establishes the payload is unobtainable — `artifact.relay_expired` (410) or a zero-row `artifact.no_access_key` (404). The write-back belongs to the task that makes relay expiry reachable, and this task makes both refusals reachable with no sweep in existence: leaving it a phase behind would ship a producer whose 410 leaves a manifest at `pinned`, breaking the acceptance criterion that a marker rendered afterwards reports `expired` from persisted state and handing the unresolved-marker renderer a still-`pinned` row matching no member of its closed union. Its file is `relay-transfer-service.ts`, which this task already touches for the fetch half. The rule is fact-keyed, not code-keyed; idempotent; applied only to a `pinned` row — and T14.9 re-asserts it as a regression over the sweep paths that phase makes reachable. **(d) `Cache-Control: no-store` on relay fetch responses.** Both 404 and 410 are heuristically cacheable by default (RFC 9110 §15.5.5, §15.5.11), so a cached refusal would outlive the re-publish that remedies it and turn a recoverable state into a permanent one — and the re-publish remedy is what every 410 on this path promises.

**Why a set and not a single thumbprint:** rotation **retires rather than replaces** (I-012-9), so a daemon legitimately holds several thumbprints at once and the row it needs may be tagged with any of them; demanding one value would make a rotated node unable to name its own pre-rotation grant. **Why this is authorization-safe:** a thumbprint is a **public-key fingerprint, not a credential** — it is presented, never trusted as proof of anything. Authorization is carried entirely by the authenticated `sub`, session access, the DPoP proof, and the `user_id` equality pinned inside the same lookup; presenting another user's thumbprint resolves zero rows because `user_id` is fixed to the caller's own `sub` in the same predicate, so the worst a forged set achieves is a 404 for a row that was never the caller's. **What it does not change:** I-012-10 is unchanged — the node half is still issuer-derived, now from the recipient row instead of an attach row — and mint-time authorization stays **user-granular**, so the compromised same-user-sibling residual is untouched (that sibling holds its own durable key and its own thumbprints, and resolves its own row exactly as designed). **The TTL sweep's disposition, ordering, and purge stage** (I-012-15). Each hourly pass claims due rows with `SELECT … FOR UPDATE SKIP LOCKED`, so overlapping passes and multiple relay processes divide the work and a row already being swept is skipped rather than waited on — control-plane Postgres row locking, unrelated to the four daemon-local in-process exclusions of [Spec-012 §Implementation Notes](../specs/012-artifacts-files-and-attachments.md#implementation-notes), which order resources on the other side of the node boundary and therefore never compose with these. For each claimed row the pass runs three stages **in this order, which is one-way**: **(1) commit the intent** — in one transaction, hard-DELETE every `artifact_relay_recipients` row for the digest (that delete **is** the wrapped-CEK crypto-shred, CP-012-2's second and lifecycle-driven trigger) and set `state = 'expired'`, leaving `bytes_reclaimed_at` `NULL` **and `publisher_user_id` still set**; **(2) reclaim** the ciphertext object from the object store; **(3) confirm** by stamping `bytes_reclaimed_at` **and `NULL`ing `publisher_user_id` in that same transaction** (dropping the identity at intent would leave stored bytes charged to no publisher for as long as the reclaim kept failing, so the identity is held exactly as long as the bytes are). Deleting the row first and reclaiming after is prohibited, not merely discouraged: the coordination row is the **only** index into the stored object, so a crash between the two would orphan bytes that no row names, no quota counts, and no later pass revisits. The chosen order fails the other way — a crash leaves a tombstone carrying `bytes_reclaimed_at IS NULL`, which the next pass picks up and retries — and the retry is safe because the relay holds no content reference count, making the reclaim a plain idempotent object-store delete rather than a refcount-gated one (I-012-12's derived-CAS-refcount rule is local-CAS-only and is deliberately not extended here). **Publish is fenced against an in-flight reclaim**: an UPSERT arriving on a row at `state = 'expired' AND bytes_reclaimed_at IS NULL` is refused `429` with `Retry-After` — the relay publish path's existing transient-backpressure refusal, so no code is minted — because re-pinning there re-uploads the digest under the very content-addressed key the still-running reclaim is about to delete, leaving a `pinned` row whose bytes the sweep destroyed and nothing left to detect it. The `SKIP LOCKED` claim cannot cover this: its transaction commits before the external delete begins, so the two writers are never in one lock scope. **That same gap admits a second writer pair the fence does not reach, so the reclaim carries its own exclusion**: two relay processes can both hold a row at `state = 'expired' AND bytes_reclaimed_at IS NULL` — one having just committed intent, the other because that is the retry predicate — and run two deletes of the same key, the first confirming and lifting the fence while the second is still in flight to destroy a re-pinned blob's fresh bytes. Stages (2) and (3) therefore run under a **session-level advisory lock keyed on the digest** (`pg_try_advisory_lock`, taken after the intent commits, released after the confirming commit), and a pass that cannot take it skips the row rather than deleting behind another worker; a holder that dies releases with its session, leaving `bytes_reclaimed_at IS NULL` for the next pass ([Spec-012 §TTL sweep disposition (V1)](../specs/012-artifacts-files-and-attachments.md#ttl-sweep-disposition-v1)). The same pass also runs the **purge stage**: a tombstone whose `bytes_reclaimed_at + relay_tombstone_grace` has elapsed is DELETEd outright, after which the same fetch takes the zero-row `artifact.no_access_key` (404) arm. Both stages are driven off the existing `idx_artifact_relay_blobs_expires` index — due pins by `expires_at`, purgeable tombstones by `expires_at < now() - relay_tombstone_grace`, a superset since `bytes_reclaimed_at >= expires_at` always — so neither of those two needs an index of its own. The **reclaim-retry** pass does, and takes the partial index `idx_artifact_relay_blobs_unreclaimed` on `(expires_at) WHERE state = 'expired' AND bytes_reclaimed_at IS NULL`: `bytes_reclaimed_at IS NULL` is not a prefix of the `expires_at` index, so without it every hourly retry scans the whole grace-window population — which grows each pass and is dominated by rows already reclaimed — to find a handful of failed deletes. The re-publish path (Task 7) must UPSERT `bytes_reclaimed_at` back to `NULL` alongside re-anchoring `expires_at` and returning `state` to `pending_replication`; without that clear, a re-pinned blob is purged on the previous reclaim's clock while live. **Metrics** (OpenTelemetry, per pass): rows claimed, recipient rows shredded, bytes reclaimed, tombstones purged, live tombstone count, and — the one worth alerting on — the count of tombstones carrying `bytes_reclaimed_at IS NULL` across more than one pass, which is the only externally visible signature of an object store refusing deletes while the database has already shredded the keys. **Assertion:** the last intended recipient's _acked_ fetch deletes the blob and its recipient rows, while an identical fetch that never acks leaves them until TTL; an expired-TTL blob is swept and a subsequent fetch returns `artifact.relay_expired` (410, [error-contracts.md](../architecture/contracts/error-contracts.md)) — not a bare 404, so a client distinguishes "was pinned, TTL elapsed, re-publish to restore" from "never had a grant". **That arm rests on the retained-row disposition** ([Spec-012 §TTL sweep disposition (V1)](../specs/012-artifacts-files-and-attachments.md#ttl-sweep-disposition-v1)): the sweep retains the blob row as a payload-free tombstone at `state = 'expired'`, which is what lets the mid-fetch failure-mode row promise a 410 at all, and a post-TTL fetch is refused 410 for `relay_tombstone_grace` and the zero-row 404 only after the tombstone is purged. The write-back is keyed on the fact rather than on one code, so it covers both codes of the lifecycle — **and the fetching daemon's own manifest row reads `expired` after that refusal, not `pinned`** — a **regression** assertion here rather than a deliverable of this task, since T14.8 ships the write-back in Phase 5 where the two refusals first become reachable and this task only adds the sweep paths that reach them — asserted by reading the row back on the mint arm and again on a mid-fetch resume arm (the write-back is scoped to the fact, not to the mint, so a resume-path 410 must not leave a `pinned` row beside a dead blob), **and asserted a third time on the zero-row arm** — a blob taken by refcount-zero delete or watermark eviction cascades its recipient rows away, so the next fetch mint resolves zero rows and is refused `artifact.no_access_key` (404), which must transition a still-`pinned` row to `expired` exactly as the 410 does (otherwise every cascade-path loss keeps a row claiming a pin that is gone) — with a row already carrying `over_cap` left unchanged under both codes, a repeat refusal of either kind changing nothing, and a subsequent re-publish re-pin returning the row to `pinned` so the status does not latch — which is what makes T14.13's unresolved marker able to report the `expired` cause from persisted state at all; ## Design Decisions

- **D-012-1 — The OCI manifest envelope is realized as dedicated `artifact_manifests` columns + a named `ArtifactManifest` wire shape.** [Spec-012 §Interfaces And Contracts](../specs/012-artifacts-files-and-attachments.md#interfaces-and-contracts) specifies an OCI-inspired envelope (`subject`, `size`, `annotations`, `digest`=content_hash). This plan authors `artifact_manifests.subject` (self-referential FK), `size_bytes`, and `annotations` columns (local-sqlite-schema.md) and the matching `ArtifactManifest` wire shape (api-payload-contracts.md), plus the CP-012-1 obligation that Plan-009's `diff_artifacts.artifact_manifest_id` FK references.
- **D-012-2 — `annotations` is a dedicated OCI string→string column, not folded into freeform `metadata`.** The OCI `annotations` map is a first-class manifest property ([OCI image-manifest spec](https://github.com/opencontainers/image-spec/blob/main/manifest.md)); it gets its own `artifact_manifests.annotations` column and a distinct `ArtifactManifest.annotations` wire field so the at-rest shape is 1:1 with the wire, while `metadata` stays purely freeform daemon-side provenance.
- **D-012-3 — `ArtifactPublish`/`ArtifactRead` compose a single named `ArtifactManifest`; publish embeds the manifest metadata (no `manifestUrl` pointer).** [Spec-012 §Interfaces And Contracts](../specs/012-artifacts-files-and-attachments.md#interfaces-and-contracts) mandates that publish return "artifact id **and** manifest metadata"; a `manifestUrl` pointer would drift from that clause ([Spec-012 §Interfaces And Contracts](../specs/012-artifacts-files-and-attachments.md#interfaces-and-contracts) grants handle/inline latitude to the _payload_ on `ArtifactRead` only, never to the manifest). The wire now embeds `manifest: ArtifactManifest` on publish and `manifest` + `payloadHandle?`/`payload?` on read; producer inputs (`subject?`, `annotations?`) are accepted at publish so the `annotations` column and derivative `subject` are not write-dead. Aligns the wire to the spec — not a new owner decision.
- **D-012-4 — The `artifactType` discriminator is a closed six-value union: `file | diff | summary | log | design | workflow_output`.** [Spec-012 §Required Behavior](../specs/012-artifacts-files-and-attachments.md#required-behavior) enumerates five families (`summary` covers the plan/summary family); `workflow_output` (the [Spec-015 §Output Mode Specification](../specs/015-workflow-authoring-and-execution.md#output-mode-specification) workflow phase-output type) is the sixth. The Required-Behavior families list admits "at least" the five, so this is an additive discriminator value, not a families-list rewrite. The closed typed union is the contract (api-payload-contracts.md `ArtifactType`); the schema CHECK mirrors it (`CHECK(artifact_type IN ('file','diff','summary','log','design','workflow_output'))`).
- **D-012-5 — The envelope-interior application-payload discriminator is relay-owned, with a consumer registration seam; Plan-012 registers `artifact_key_attestation` through it.** Task 7's artifact-key attestation rides the one pairwise ciphertext envelope beside the device-to-node method-proxy traffic that envelope also carries, refusing a new relay frame message type, and neither side defined the discriminator that separates the two on receipt — Task 7's attestation leg was unbuildable as written. The envelope and its frame-type surface belong to the relay ([Plan-028](./028-remote-control.md) Phase 3), so the discriminator is **authored with the relay**: the required string tag member `kind` on every payload sealed directly into the envelope. **Unknown-kind is fail-closed** — the client coordinator's demux drops an absent or unrecognized `kind` with a logged refusal and never dispatches it. **Registration seam:** a consuming plan appends its own arm and keeps its payload schema in its own contract domain, so Plan-012's `artifact_key_attestation` arm references a schema under `packages/contracts/src/artifacts/` and the relay owns only the tag, the union, and the exhaustiveness rule (CP-012-4). The `SessionEventSchema` union-registration seam is the corpus's established one-owner-many-registrants shape (cross-plan-dependencies.md `packages/contracts/src/` row). All of it is additive-only and unshipped on both sides, so no version bump is owed.

## References

Source for the SQLite collation premise T14.13's case-preserving resolver rests on:

- [SQLite — Datatypes In SQLite, §7 Collating Sequences](https://www.sqlite.org/datatype3.html#collation) — the built-in `BINARY` collating function "compares string data using memcmp(), regardless of text encoding", and §7.1 states that when two `TEXT` values are compared and neither operand carries a `COLLATE` clause or a column-level collation, "the BINARY collating function is used for comparison". `artifact_manifests.id` is declared `TEXT PRIMARY KEY` with no `COLLATE`, so its primary-key index and every equality lookup against it compare bytes: `ABC…` and `abc…` are two different keys, which is why the resolver canonicalizes the caller's spelling before the lookup rather than trusting the database to fold case.
