## Goal

Implement versioned workflow definitions and durable workflow execution for the full V1 engine — every node kind in the catalog, those that run an agent or ask a person among them, parallel steps admitted by one memory gate, and append-only approval history — reusing existing session, run, approval, artifact, and recovery primitives.

## Scope

Workflow definition persistence (content-hashed, immutable versions), workflow run state, step execution for every node kind in the catalog — `agent.run`, `agent.multi-agent`, `human.approval` and `human.form` among them — with each node's `onError` and `retry`, parallel steps joined through `flow.merge`'s modes, memory-gated admission, approval resolution recorded in `workflow_gate_resolutions`, multi-agent steps run as orchestration runs in the run's session, replay-deterministic projection rebuild, and the chat-invoked start surfaces with per-start authorization ([Spec-015 §Chat-Invoked Start and Start Authorization](../specs/015-workflow-authoring-and-execution.md#chat-invoked-start-and-start-authorization), ADR-025).

## Non-Goals

- Marketplace or cross-machine workflow distribution. The `shared` scope tier is node-local reuse breadth, not distribution — a `shared` definition never leaves the daemon that stores it. Cross-machine portability at V1 is the file form of [Spec-015 §Definition file form — export and import (C-17)](../specs/015-workflow-authoring-and-execution.md#definition-file-form--export-and-import-c-17), a file the person moves, not a service.
- External workflow-engine integration
- Workflow editor polish beyond V1 ambition
- A durable cross-run delivery substrate. This plan builds only the in-run fold: the park's provider-account attention key of T2.5 and its `park_attention_key` projection column, which crosses no aggregate boundary. No task here opens a per-watcher generation record, a claim / queue / deliver lifecycle, or any cross-run durable row. The only values one run leaves the next are the ones a `Set variables` step keeps with `Keep for later runs`, read as `$vars` (a value over 64 KiB stored as an artifact and read back the same way) and cleared with `Clear kept values` (`workflow.keptVarsClear`), built at T2.11.

## Data And Storage Changes

- **The document is node-shaped, and its bytes are the hash preimage.** A workflow definition is one JSON document — the `WorkflowDocument` type this plan adds to `packages/contracts/src/workflow-definition.ts`, the one schema the window and the service share, written as literal unions with no TypeScript enum, with no second serialization — whose canonical bytes are the RFC 8785 canonicalization of its hashed field list, BLAKE3'd ([Spec-015 §State And Data Implications](../specs/015-workflow-authoring-and-execution.md#state-and-data-implications)). It carries its schema version, its name and an optional description, exactly one `trigger` node, the rest of the graph as `nodes`, and `edges` each naming a source node and handle and a target node and handle ([Spec-015 §Graph model — nodes, ports, and edges (SA-30)](../specs/015-workflow-authoring-and-execution.md#graph-model--nodes-ports-and-edges-sa-30)). Three sections sit **outside** the hashed body: `layout` — a position per node, an optional viewport and the sticky notes — `pinData`, an item array per node id, and `tags`, the workflow's tags, so a change to any of them mints no version. A node carries its id, its kind, the kind version written at insert, its display name, its sibling order, its params, and optionally whether it is disabled, its notes, its error disposition, its retry bounds, whether it executes once over the whole input, and whether it always outputs data. The document holds **no settings block**: what a failure does is set on the node that failed, how long a run may work is a control on the console's Runtime settings page over the machine-local settings surface ([Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior)), and the clock a schedule reads is a param on the schedule trigger itself.
- **A node is the authored unit; a step is one execution of it.** The definition/execution separation stands as [Spec-015 §Interfaces And Contracts](../specs/015-workflow-authoring-and-execution.md#interfaces-and-contracts) states it: `WorkflowNodeId` identifies a node in the definition and `StepRunId` one execution of it. One step record exists per node attempt, keyed by the run, the node, the attempt and the execution index, in `workflow_steps`, and it is a projection over the events the run, approval and form pipelines already emit ([Spec-015 §Execution semantics](../specs/015-workflow-authoring-and-execution.md#execution-semantics), [Spec-015 §Truth vs projection vs ephemeral (SA-24)](../specs/015-workflow-authoring-and-execution.md#truth-vs-projection-vs-ephemeral-sa-24)). The kinds that run an agent or ask a person are nodes like any other — `agent.run`, `agent.multi-agent`, `human.approval` and `human.form` — and compile down **at run time, not at save time**, their executors calling the existing run-admission, orchestration, approval and form paths when the node runs ([Spec-015 §Implementation Notes](../specs/015-workflow-authoring-and-execution.md#implementation-notes)); each attempt is a step recorded in `workflow_steps` with its payloads, and the answer to a `human.approval` step, like the answer to a chain's question, is also a row of the `workflow_gate_resolutions` chain; a form's answer is not. The trigger node never enters the step sequence, never receives a `stepRunId` and never produces a step row ([Spec-015 §Graph model — nodes, ports, and edges (SA-30)](../specs/015-workflow-authoring-and-execution.md#graph-model--nodes-ports-and-edges-sa-30)).
- Add the workflow schema per [Local SQLite Schema §Workflow Tables](../architecture/schemas/local-sqlite-schema.md#workflow-tables-plan-014) (SA-23) — every table `STRICT` (columns typed `INTEGER`, `REAL`, `TEXT`, `BLOB` or `ANY`, JSON stored as `TEXT`), as every table in the daemon's collapsed SQLite schema is. Some carry over from the engine's schema: `workflow_definitions`, `workflow_versions`, `workflow_runs`, `workflow_gate_resolutions` and `human_phase_form_state`, the last keyed by run and node and holding a form step's draft. `workflow_definitions` and `workflow_versions` carry the document body as the hash preimage with a `layout_json` column beside it, because layout is outside the hash ([Spec-015 §Canvas layout is not definition bytes (SA-33)](../specs/015-workflow-authoring-and-execution.md#canvas-layout-is-not-definition-bytes-sa-33)); `workflow_definitions` also carries the workflow's `tags`, outside the hash for the same reason; a version's row also holds the lock of each full-tier Code node it carries and who saved it, the person or the agent that did. `workflow_runs` carries the run's `session_id` and the chain columns — `chain_root_run_id` and `chain_from_error` on every run, `chain_run_count` and `chain_kept_going` on a chain's first run — and a run in a project session references its one `run_execution_contexts` row (T2.10). The rest are added:

| Table | Holds |
| --- | --- |
| `workflow_steps` | One row per step attempt: run id, node id, attempt, execution index, the source array, status, timings, the payload references, cost, error, the park columns, and `wait_deadline_at`, the instant a step waiting on a person gives up, set only where its `Timeout` is. |
| `workflow_triggers` | One row per armed trigger: definition id, node id, kind, config hash, next fire, last fire, whether it is enabled. |
| `workflow_webhook_tokens` | One row per workflow that has a webhook trigger: the token hash, when it was created, when it was last used. |
| `workflow_node_state` | The per-(workflow, node) key-value store holding trigger cursor state, so no mutable field lives on the document, and the values `Keep for later runs` keeps: one entry per (workflow, name), with the value, the run that kept it and when. |
| `workflow_secrets` | One row per secret: its daemon-minted id, scope, scope reference and name, with no value column; the value is sealed in the operating system's keychain ([ADR-036](../decisions/036-workflow-secrets-in-the-os-keychain.md)). |

No other table holds step state or step output, and no table holds join state: `flow.merge`'s modes decide how branches join.

- **A step's payloads are inline while they are small.** Its input, output and log sit on the step row under a 64 KiB cap; above the cap each becomes an artifact through the Plan-011 ingest pipeline and the row keeps the reference. One read serves either, and the panel that shows a payload says which of the two it is reading — so a run row stays small and a step's input and output stay addressable from a message.
- Source-of-truth hierarchy (SA-24): `session_events` remains canonical; `workflow_definitions`, `workflow_versions`, `workflow_gate_resolutions` and the immutable step payloads are truth; `workflow_runs` and `workflow_steps` are projections rebuildable via Plan-012 `ProjectionRebuild`. The per-step record is a projection over events the run, approval and form pipelines already emit, which is what keeps a run's step history a function of the log rather than a second account of it. Some of the added tables are **mutable truth** rather than projections: the armed-trigger rows, the webhook token rows, the per-node key-value store and the secret records are facts about what this machine is armed to do next, which no event history reconstructs — the durable row is the truth and the in-process timer is a cache re-armed from it after a restart ([Spec-015 §Entry node and the V1 trigger surface (SA-35)](../specs/015-workflow-authoring-and-execution.md#entry-node-and-the-v1-trigger-surface-sa-35)).
- **A form draft is daemon-held.** `human_phase_form_state` carries the drafts of the human form kind and is written through `workflow.humanFormDraftSave`, so a half-filled form survives a reload rather than living in the window; typed unsent text is never put in window storage. Each autosave bumps the row's own draft version, the optimistic-concurrency token the next write checks against, and the row is keyed by run and node, one draft per waiting form.
- `workflow_gate_resolutions` is the append-only record of gate answers, one row per answer with a per-run `sequence` monotonic from 1, and the `workflow.gate_resolved` event names its row by `gateResolutionId`. BLAKE3 is the daemon-internal identity hash and SHA-256 stays Plan-011's artifact-content hash (SA-25).
- **Workflow-definition scope is one of:** `session` | `project` | `shared`. `session` scopes a definition to the one session its `scope_ref` names, `project` spans the sessions of one project, and `shared` is the cross-project tier — authored once and reusable by any project on the same daemon, resolved out of the same local definition store with no additional table and no sync path. Scope identity is carried by a `scope_ref` column alongside `scope`, in the shape [Spec-024 §Unified Inventory](../specs/024-mcp-server-configuration-and-governance.md#unified-inventory) already uses for scope-qualified bindings — the session's id at `session`, the project record's id at `project`, the empty string at `shared` — and the dedupe key is `(scope, scope_ref, content_hash)`, so a definition stored once at a scope is one row regardless of which session submitted it. A `scope` without its `scope_ref` would not be storable: `project` would name no project, and a key on the submitting session and `content_hash` would partition `shared` definitions by session, so two sessions storing the same shared definition would produce two rows resolution cannot reconcile. `shared` widens **visibility and reuse breadth only**: it is not distribution, not a marketplace and not cross-machine sync — a `shared` definition never leaves the daemon that stores it, and [Spec-015 §Non-Goals](../specs/015-workflow-authoring-and-execution.md#non-goals) continues to exclude marketplace and global-library distribution. The `workflow_definitions.scope` column carries the domain (`CHECK(scope IN ('session','project','shared'))`), and the table has no session column: runs, not definitions, live in sessions.
- **Copy-on-write provenance column:** `workflow_definitions.parent_content_hash`, nullable, recording the content hash of the `shared` definition a row was branched from when an author edited a shared definition (T1.6, [Spec-015 §Definition scope in the builder (SA-34)](../specs/015-workflow-authoring-and-execution.md#definition-scope-in-the-builder-sa-34)). It is provenance and **not** part of the hashed body, so a branched definition and a from-scratch definition with identical bodies still carry the same `content_hash` and converge on the dedupe key — the intended behavior, since the two are the same definition. Editing a `shared` definition in place is forbidden by construction: versions are immutable, so an in-place edit would append a version to the shared definition and silently repoint every project on the daemon that resolves it. No table is added by it.
- **Admission reads the machine, and only the headroom is configuration:** the SA-3 gate restated from [Spec-015 §Execution semantics](../specs/015-workflow-authoring-and-execution.md#execution-semantics) — capacity is `process.availableMemory()` re-read on every tick, less a headroom of 20 % of physical memory and at least 1 GiB, less the reservation of every step admitted and not yet finished. A step's reservation is its kind's starting figure per provider until that workflow node has run, and then the peak that node reached on this machine; a quick Code step's is its own memory budget plus 32 MiB for its thread plus nine times its input. A step whose size is an estimate starts at least 1.5 s after the last such start; a quick step starts as soon as it fits. Ready steps wait in one line in the order they became ready, across every run, and the gate weighs only the head of the line; when nothing is running, the head is admitted whatever its size. No step, node or workflow carries a priority or a weight. There is no capacity constant, no step-count ceiling and no slot pool. The observed peaks live in memory beside the reservations — ephemeral by the same rule (SA-24), re-learned rather than restored after a restart — and this plan's own admitter counts them, consuming no other plan's pool API and adding no dependency row.
- **Park-and-resume projection columns — on `workflow_steps`, no new table.** `park_reason` (nullable, `CHECK(park_reason IN ('waiting-human','provider-usage-limited'))` — the union of [Spec-015 §Park integrity and cancelability (SA-40)](../specs/015-workflow-authoring-and-execution.md#park-integrity-and-cancelability-sa-40), in the DDL-CHECK-versus-contract lockstep I-014-8 enforces), `park_cause` (nullable text, the engine-authored sentence, bounded at 8 KiB and truncated at a UTF-8 code-point boundary with a visible marker — a durable person-facing string with no bound is an unbounded write on the projection tier), `resume_at` (nullable UTC instant — the durable schedule of [Spec-015 §Provider-limit pacing and durable resumption (SA-38)](../specs/015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-38), a durable value rather than an in-memory timeout, so a parked step resumes itself across a daemon restart) and `park_attention_key` (nullable text — provider plus account identity plus credential generation, the outage-scoped fold key; a correlation for presentation that gates no start, resume, retry or schedule fire). Per-step rather than per-run, and the placement is load-bearing: under [Spec-015 §Graph model — nodes, ports, and edges (SA-30)](../specs/015-workflow-authoring-and-execution.md#graph-model--nodes-ports-and-edges-sa-30) two parallel branches of one run may park concurrently against different provider accounts with different reset boundaries, and a run-level schedule or fold key could hold only one of them — delaying or stranding the sibling and folding two distinct outages into one record. The table is already a projection, and all these values ride the suspension event that produced them, so the byte-equal `ProjectionRebuild` of I-014-7 holds with no exception and no schedule or fold key survives a rebuild the log does not contain. Partial indexes back the boot sweep and the fold read: one on `workflow_steps(resume_at)` where non-null, one on `workflow_steps(park_attention_key)` where non-null — both narrow by construction, and both stay the bare non-null form because the per-row CHECK already confines the columns to `status = 'waiting'`. That CHECK — `status = 'waiting' OR (resume_at IS NULL AND park_attention_key IS NULL)` — makes the **step-exit half** of SA-38's clear-on-exit rule structural rather than a code convention: SQLite enforces CHECKs per statement, so the same UPDATE that moves a step out of `waiting` must null both live columns. The run-cancel half cannot be DDL-enforced, since run status lives in `workflow_runs` and a SQLite CHECK cannot cross tables, so SA-40's cancel clears the live columns in the cancel's own unit of work — code-enforced and failure-injection-tested at T5.20 — while the park **record** columns carry no such coupling by design: `park_reason` and `park_cause` survive resume and cancellation untouched, so liveness is read from run status plus step status, never from the presence of a park reason.
- **The engine event record is not a SQLite table (SA-41).** It is newline-delimited JSON on the Plan-017-owned bounded-retention diagnostic tier, so it adds no table, no write to the writer worker and no write amplification to the canonical event path — the reason the always-on posture is affordable at all. Plan-014 writes records and correlates them by `workflowRunId` / `stepRunId` / `attemptNumber` / a monotonic per-run sequence; Plan-017 owns the bucket, its TTL and its Path-3 membership (CP-014-9).
- See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) for column definitions, index rationale, and write-amplification estimates.

## Implementation Steps

- Contracts: See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed schemas this plan consumes.

1. Define workflow-definition, version, step, gate, and definition-read contracts in shared packages.
   - Full type hierarchy: `WorkflowDefinition`, `WorkflowVersion`, `WorkflowDocument` with its `WorkflowNode`, `WorkflowEdge` and `WorkflowLayout` members, `WorkflowRun`, `WorkflowStep`, `WorkflowGateResolution`.
   - Approvals: an approval is a `human.approval` node with `approved` and `rejected` outputs, and each answer is a row of `workflow_gate_resolutions` (step 5).
   - Entity separation: `WorkflowNodeId` (the node in the definition) vs `StepRunId` (one specific execution instance), a step attempt keyed by the run, the node, the attempt and the execution index.
   - What a failure does is the failing node's `onError` — `stop`, `continue` or `continue-error-output` — beside its `retry { maxTries, waitMs }`, which the engine clamps; a retry adds a new attempt row (C-9).
2. Implement durable workflow definition versioning and workflow-run persistence. ## Implementation Phase Sequence

The five numeric phases map 1:1 onto `## Rollout Order`, absorbing `## Implementation Steps` and `## Target Areas`; each phase carries a `**Precondition:**` line. Three supplement phases — **2B, 5B, and 5C** — hold the park-and-resume and engine-record tasks, so the phases they extend never wait on them, and no numeric phase waits on a supplement.

- **T5.20 — Park cancelability.**
  - **Files:** `packages/runtime-daemon/src/workflow/workflow-run-service.ts` (EXTEND from T5.15), `packages/runtime-daemon/src/workflow/park-scheduler.ts` (EXTEND from T2.6).
  - **Provides:** cancellation as a legal transition into the `canceled` run status from **every** suspended or waiting state — human-waiting, provider-usage-limited, and any future park reason alike — with no precondition and no wait. ### What each layer proves

**Executor unit tests, one per node kind**, over an item fixture covering: the empty input, the single item, the many-item batch, the per-item expression re-evaluation, the item lineage the kind must emit, the failure path under each error disposition, and the redaction of any resolved secret. A branch kind additionally asserts the shape of its output array; the loop kind asserts its done-and-loop ordering and its run-index progression; the merge kind asserts each of its join modes. Every kind ships with its spec, its executor, a unit test over the executor with an item fixture, and a fixture scenario beat so the console's fixture bridge can render it.

**Engine tests**: traversal order under fan-out with explicit sibling order, the fan-in buffer, loop re-entry, item lineage across a branch and a merge, retry under the engine's clamps, the optional run cap, cooperative cancel, a run ending failed or canceled canceling its running siblings with `workflow.step_canceled` and `First to arrive` canceling the losers, a chain waiting on its question at its count, the waiting-and-resume cycle, the crash sweep leaving a `waiting` run alone, and a partial run reusing clean step data. The memory gate carries its own: a machine with no room still admits one step, a second provider, bun or Python start waits out the 1.5 s between such starts while a quick step starts as soon as it fits, a step waiting on a person or parked on a spent provider account releases its reservation, and a step's reservation moves from its kind's starting figure to the peak its workflow node reached on this machine.

**Expression tests**: each binding, per-item evaluation, the evaluation yielding every 4 ms and stopping when its run is canceled, a regular expression running on `re2js` in time linear in its input and a backreference refused when the pattern compiles, redaction of resolved secrets, and the lineage failure modes with the exact guidance each gives.

**Code node tests**: on the quick tier, each step on its own thread — the memory limit, the cancel flag and `terminate()` 250 ms after it, a thread out of heap failing only its step with `workflow.step_thread_failed`, no host access, and log capture into the step's log. On the full tier, the lock written when the version saves; the first run installing from that lock outside the sandbox into the version's code folder and a later run installing nothing; the unpin preload and the daemon's own `bunfig.toml` on every bun step, so a worktree's `.env` and `bunfig.toml` never reach it; the step writing only the worktree and its own temporary folder inside both providers' sandboxes; `Clear Bun cache`, `Clear uv cache` and `Clear all caches` leaving every code folder and the managed Python and a later run fetching nothing; an install the disk cannot hold failing its step with `workflow.code_install_failed` (`disk_space`) and clearing no cache; and a sandbox that cannot start refusing the step with `workflow.sandbox_unavailable` rather than running it unprotected.

**Canvas tests on the browser tier**: the controlled round trip, where a change callback produces exactly the document mutation and nothing else; a refusal during the drag for each refused shape; a drop from the palette landing at the pointer; an edge-drop opening the filtered palette; undo and redo across a coalesced drag; copy and paste re-iding nodes; handle re-registration after a param write that changes the port set; and the announcer receiving one message per structural change. These run headless and never reveal a window.

**Builder store tests**: the history cap, the dirty lattice per rule, the validation strip's contents, save-then-run against a dirty draft, and layout writes never touching the hashed body.

**Round-trip tests**: export then import reproducing the same bytes and the same content hash; a document with no layout laying out identically twice; a copy-paste fragment parsing back into the same nodes.

**Proportion**: a build proves the surface scales by stepping the console's text size — the reading matter and every box that carries it grow in one proportion, the icon strokes and the corner radii stay as drawn, and the canvas keeps its own coordinate space, where the node box, the handles, the edge geometry and the grid step are canvas units the zoom scales.

**Surface sweeps**: every screen state below is reachable, every rule with a visible consequence is observable on the screen, and every node kind in the catalog is in the palette.

### Two workflows every scenario is built from

**Morning PR digest** — twelve nodes with one branch, one merge, one loop, one agent node carrying a capability edge, and one approval:

1. `Every weekday 8:30 AM` — a schedule trigger, cron `0 30 8 * * 1-5`, timezone `America/New_York`.
2. `List open PRs` — an HTTP request, one item per pull request.
3. `Needs review?` — an If, true when the review decision is not approved.
4. `For each PR` — a loop over items, batch 1, on the true branch; outputs done and loop.
5. `Read the diff` — a repo diff on the loop branch, set to continue on its error output, so a diff it cannot read leaves by the error branch back into `For each PR` and the loop takes the next pull request.
6. `Review agent` — an `agent.run` node, the reviewer agent on a Codex account, its prompt referencing the item's title and diff.
7. `Repo search` — an MCP tool wired by a capability edge into node 6's tool input.
8. `Skipped PRs` — a set-variables node on the false branch.
9. `Merge digest` — a merge in append mode, input 1 from the loop's done output and input 2 from node 8.
10. `Approve the post` — an approval node, outputs approved and rejected.
11. `Write summary` — a write-summary node on the approved branch.
12. `Save as artifact` — a save-as-artifact node on the rejected branch.

**Nightly tests** — five nodes, the failure example: `Every night 2:00 AM` (a schedule trigger) → `Run the suite` (a shell command running the test script) → `Passed?` (an If) → `Write summary` or `Stop with error`.

## Rollback Or Fallback

- If parallel execution or the gate-resolution writer regresses, disable parallel steps and restrict runs to sequential `agent.run` steps and the kinds that run no agent and ask no person — the engine still satisfies C-1…C-7 for V1 partial rollout.
- If the durable auto-resume schedule misbehaves, the fallback is the **unscheduled park**, which is already a first-class shipped state: stop arming `resume_at` and every parked run stays visible, cancelable, and manually resumable with its stated cause. Recognition, the park itself, and cancelability are independent of the scheduler, so this degrades pacing without losing the park. The park columns stay in place — a nullable column that nothing writes costs nothing.
- If the engine event record proves too costly, the fallback is **bounded recording, never no recording**: shed the high-frequency record classes first — ready-set ticks and gate evaluations, the classes that dominate volume — while retaining parks, schedule arming and fires, refusals, and the dispatch-intent/outcome pairs, so the records that exist precisely for the unreproducible moments survive the cost trim. The no-op writer is reserved for the one case T5.24 already requires it: bucket unavailability, where failing a run over a diagnostic sink would invert the record's non-canonical rank (I-014-18). Neither arm turns the record off: it is a diagnostic log written for every run (I-014-18).

## Risks And Blockers

- Write volume under a flood of `progressed` heartbeats. The engine commits the step rows one turn of its loop started or settled in one transaction and hands that turn's events to the event log as one batch, and there is no write rate limit: twenty steps starting and finishing together cost 1.3 to 2.3 ms of the daemon's time in one transaction, and a sustained 10,000 step boundaries cost 17 to 19 µs each. **Named calibration criterion:** the nightly load category (Phase 4, T4.2) records per-workflow write volume against the [Local SQLite Schema §Workflow Tables](../architecture/schemas/local-sqlite-schema.md#workflow-tables-plan-014) estimate of ~42 KB / 110 writes per 10-step workflow; a sustained nightly reading above **2× that estimate** is a defect in the engine's batching, found and fixed there. The trigger is a threshold on an already-collected measurement, not a scheduled revisit.
- **`uv` reaches a person's machine as one pinned release, fetched at the first save that locks a Python step.** `bun` publishes its own binary on npm at 1.4.2, so the daemon carries it the way it carries any other pinned tool; the npm package named `uv` is an unrelated UTF-8 data validator, and `uv`'s standalone installer edits shell profiles, so neither is the route. The daemon keeps each platform's sha256 for the pinned `uv` release in its source; the first save that locks a Python step fetches the archive into a daemon-owned folder and checks it against that value before unpacking it whole, and a mismatch or no network leaves that save's Python steps `Packages not locked` in plain words (T1.12). The risk is a machine with no network at that first save, whose Python steps cannot run until a later save locks them; the JavaScript and TypeScript arm needs no fetch of the tool.
- **The Claude-leg sandbox is an early research preview.** `@anthropic-ai/sandbox-runtime` 0.0.78 says its interfaces and configuration formats may still change. The daemon links it as a library, and runs `@openai/codex`'s native binary for the Codex leg, never either package's npm launcher script, each of which would add a 15 to 38 MB Node process to every step. A breaking change costs a call-site and settings fix in the daemon, and the Codex leg would not break with it.
- **The boundary around the full tier is measured on macOS and Linux.** On an Apple-silicon Mac and on Linux (Debian 12 in a container), a TypeScript program and a Python program each ran with their packages inside both providers' sandboxes, with home-directory and cache writes refused and writes confined to the worktree and the step's own temporary folder, and the sandbox cost about 0.02 s per run. Windows is unmeasured, and so is either sandbox started by the daemon on a real Ubuntu 24.04 desktop, where AppArmor strips the capabilities of a user namespace made by a program that has no profile and no loaded profile names `bwrap`. A sandbox that cannot start refuses its step with `workflow.sandbox_unavailable`, naming the provider and the wrapper's own error, and never runs it unprotected ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)).
- Non-determinism in replay if driver adapters leak wall-clock or random seed state — T5.1's replay-determinism battery (SA-29, asserting no `DeterminismViolationError` and a `deepEqual` final state) is the guard.
- **The park reads only the typed carrier and never fakes one (CP-014-10).** Every rule in [Spec-015 §Provider-limit pacing and durable resumption (SA-38)](../specs/015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-38) hangs off a driver signal Plan-003 ships (`I-003-6`, T3.39), and C-19 forbids matching provider message text in its place. The risk is reading too much into the signal: it is deliberately **silent** on providers and shapes it cannot name, so a driver that observes no usage limit emits nothing, and "nothing" must be read as _not known to be limited_, never as _known not to be limited_. Widening recognition to cover that silence — by message text, exit code, or bare HTTP status — is the same failure the invariant was written against, and it fails the same way: a matcher that silently stops matching converts a park back into a burned ladder with no signal that anything changed.
- **The park's run control surface must mint its operations and its event together.** [Spec-015 §Park integrity and cancelability (SA-40)](../specs/015-workflow-authoring-and-execution.md#park-integrity-and-cancelability-sa-40) states cancelability and repair as engine state-machine rules, and the surface that reaches them is T5.22: the two operations and `workflow.canceled` mint **together**, with T5.23 carrying the client verbs. Split apart, a canceled run's status and its cleared live park columns would survive only in a projection a rebuild would overwrite instead of being a function of the log (SA-24, I-014-21). The surface costs a wire-registry entry pair and an event type; the alternative costs correctness.
- **The durable park write must not ride the provider event delivery path (implementation constraint on T2.5 / T2.6).** The refusal that triggers a park arrives on the driver's event stream, and the natural spelling — performing the park's durable write and the schedule's arming inline on that delivery — deadlocks: the writing path ends up waiting on a response that can only arrive through the stream it is itself blocking. The rule is to detach synchronously on the delivery path, then do the durable park and schedule writes off it. T2.5 and T2.6 build to that rule, and the regression is an ordering test: a park must complete while the driver's stream is still being consumed. The split leaves a crash interval — the daemon dying after the handler detaches but before the off-path park write commits — and its closure is the refusal's **reproducibility**, not a durable inbox: the restart's crash sweep moves the run to `crashed` (T5.1), and a spent account keeps refusing, so a retry from that step (T2.8) either receives a fresh typed refusal and parks then — no attempt consumed, no retry spent, per the park path's own rules — or, where the account reset during the downtime, simply proceeds, the park never having been needed. T2.5's crash-injection test pins that convergence, so SA-38's durability never rests on an in-memory signal surviving a crash.
