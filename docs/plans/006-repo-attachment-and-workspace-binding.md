## Goal

Implement the project: a git repository attached once per machine as a durable RepoMount, or cloned from a URL and then attached; the project record and its actions; and explicit binding of a session's workspace to one of its places.

## Scope

This plan covers repo root resolution, the machine-level RepoMount and the project record beside it, clone from a URL, the machine's folder list (on the machine and for another device), workspace creation when a session binds, and mount and workspace health projection. A folder that is not a git repository is refused at attach.

## Non-Goals

- Worktree lifecycle
- PR preparation
- Rich diff UI
- Renderer views: the console's new-session picker, clone card, projects settings page and runtime settings page call this plan's methods and are built with the console ([Plan-020](./020-desktop-app-and-renderer.md))

## Preconditions

- **Repo identity keys on the git common directory.** Repo identity keys on the repository's git common directory, not on the enclosing working tree's own top level, so N linked worktrees of one repository resolve as ONE repository ([Spec-007 §Repo Identity And Common-Directory Keying (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-identity-and-common-directory-keying-v1-definition), the [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) canonical-root bullet, and acceptance criteria 4 and 5). [Phase 2B](#phase-2b--repo-identity-keying-and-resolution-hardening) builds it. **Phase 3 waits on Phase 2B**, because Phase 3 is the wire surface over an identity the daemon would otherwise still be computing wrong.

Target paths below assume the implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

## Invariants

- **I-006-1 — Canonical-root fidelity.** Every persisted RepoMount records the symlink-resolved absolute canonical repository root — the MAIN checkout's working-tree root, identified by the repository's git common directory (I-006-11) — and a user-entered path is never stored as the canonical root without resolution. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) + [Spec-007 §Pitfalls To Avoid](../specs/007-repo-attachment-and-workspace-binding.md#pitfalls-to-avoid) (pitfall); path-canonicalization bugs leak outside the trust envelope (§Risks And Blockers) and corrupt every downstream workspace/worktree root derivation (Plan-007/Plan-008). **Verification.** T1.5 unit tests (subdirectory input resolves to repo root; symlinked input resolves to realpath); T-006-2B-1 unit tests (a linked worktree's input resolves to the main-checkout root, not to the worktree's own top level); T2.3/T2.6 attach integration tests assert the persisted `canonical_root` carries the resolver output, not the request input.
- **I-006-2 — Explicit resolution failure.** Canonical-root resolution failure aborts attach with typed `repo.root_resolution_failed`; the daemon never guesses a root or silently substitutes the user-entered path. **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior); silent substitution converts a user typo into a durable wrong-root mount that every later run executes against. **Verification.** T1.5 failure-path tests; T1.4 typed-error test; T2.3 attach integration test (failed resolution persists no `repo_mounts` row).
- **I-006-3 — Membership checked at the pick.** A workspace execution root resolves — post-symlink, platform-normalized — to the canonical root of the repo mount its session is bound to or a folder inside it, to a working tree git lists for that repository (`git worktree list --porcelain`), or to a daemon-created execution root admitted by provenance; containment is component-boundary-aware and case-folded, and a linked worktree nested beneath the canonical root counts only when git lists it, never by lexical containment. Membership is checked once, when the person picks the place, and traversal or symlink escape is refused with the path-redacted `TrustEnvelopeViolationError`. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) with [Spec-007 §Local Trust Envelope (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#local-trust-envelope-v1-definition); this is the boundary between the session and the rest of the person's filesystem, and once identity keys on the common directory (I-006-11) a linked worktree is no longer inside its own repository's canonical root, so containment alone would refuse working trees the repository owns. **Verification.** T1.6 adversarial unit tests (`..` traversal, symlink escape, path-prefix collision, absolute-path escape); T-006-2B-2 admission tests (a listed working tree admitted; an unlisted sibling directory and a working tree of another repository refused; a nested worktree git no longer lists refused despite lexical containment while its listed twin admits); T2.4 bind integration test.
- **I-006-4 — A folder that is not a git repository is refused, never attached.** Attach refuses a path git positively reports as not a repository with `repo.root_resolution_failed`, reason `not_a_repository`, which the screen draws as `Could not attach: not a git repository`, and persists nothing; that verdict counts only when UNCONTRADICTED by a visible `.git` entry at the supplied path — damaged or unreadable repository metadata refuses `"vcs_error"`, never `not_a_repository`. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) + [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior) + AC3; a project is a repository, and reporting damaged metadata as "not a repository" hides the damage. **Verification.** T3.6 refusal tests: a plain directory refuses and leaves no `repo_mounts` row; an empty `.git` directory and a dangling gitfile refuse `"vcs_error"`.
- **I-006-5 — Repo-mount rows persist resolved identity plus provenance.** Every `repo_mounts` row stores the user-entered attach path (`local_path`, provenance), the resolver-produced canonical root (`canonical_root`), the owning `node_id`, and a lifecycle state (`attached`, `detached` or `archived`); trust-envelope enforcement and node-ownership routing key off `canonical_root`, never `local_path`. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) ("not only the user-entered path" — both values are meaningful), [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications) (canonical root + owner node + lifecycle state), [Spec-007 §Implementation Notes](../specs/007-repo-attachment-and-workspace-binding.md#implementation-notes) (node ownership). **Verification.** T2.1 schema test (NOT NULL `node_id`/`canonical_root`, state CHECK); T2.3 service test (attach with a subdirectory input stores the resolved root in `canonical_root` alongside the entered subpath in `local_path`).
- **I-006-6 — Workspace identity is stable across execution-mode switches.** No code path creates a new `workspaces` row for a mode switch; preparing the root again updates `execution_mode`/`fs_root` in place on the same `id`. **Why load-bearing.** [Spec-007 §Execution Mode Transitions](../specs/007-repo-attachment-and-workspace-binding.md#execution-mode-transitions) ("This is NOT a new workspace"); downstream run/diff attribution keys off the stable workspace id. **Verification.** T2.4 test — full `beginRootPreparation`/`completeRootPreparation` cycle retains `id` and row count.
- **I-006-7 — An unavailable execution root is observable as `stale` on every daemon read surface, and the write gate refuses stale workspaces.** **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior): stale transition + "new write runs must be blocked until repair." **Verification.** T2.5 test (probe-fail → health projection reports stale and reports the transition owed); T2.4 test (`markStale` persists the transition the projection derives; `assertWritable` throws `workspace.stale`).
- **I-006-8 — Every repo-mount/workspace state transition appends its matching Spec-005 `session_lifecycle` event exactly once.** **Why load-bearing.** The durable transcript is the product's audit surface; emission at the transition site (single seam, T2.2) prevents drift between rows and events. **Verification.** T2.2/T2.3/T2.4 tests assert the emitted event type sequence per transition (bind → `workspace.preparing` then `workspace.ready`; stale → `workspace.stale`; detach → one `workspace.archived` per dependent, each only after the commit that made it true, beside the project-level `repo.detached` ([Spec-007 §Detach Semantics (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#detach-semantics-v1-definition)). `repo.attached` and `repo.detached` are not session events and are not on the session event list.).
- **I-006-9 — Every `repo.*` method validates daemon-side before dispatch.** Each registered method carries its canonical contracts Zod request AND response schema, so the substrate validates inbound params before the handler runs and outbound results before they hit the wire; client-only workspace binding is structurally impossible. **Why load-bearing.** [Spec-007 §Pitfalls To Avoid](../specs/007-repo-attachment-and-workspace-binding.md#pitfalls-to-avoid) names "Allowing client-only workspace binding with no daemon validation" as the failure mode; the substrate validates only what is registered with it — a handler registered with permissive schemas silently reopens the pitfall. **Verification.** T3.3 assertions (1) and (3): schema-invalid params are rejected with the deps spy at zero calls; registration asserted against the canonical contracts schema objects.
- **I-006-10 — A client marshals; it never derives daemon-owned repo/workspace state.** The desktop reaches the `repo.*` methods through `callDaemon`, which parses each reply against the method's schema; no client caches or computes health, git metadata, or a canonical root, and daemon-owned projections ride through verbatim. **Why load-bearing.** [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications) places repo health and git metadata in daemon-owned projection state "rather than client cache"; a deriving or caching client forks the source of truth and breaks the stale-workspace blocking contract downstream. **Verification.** Holds by construction: the desktop's only route to these methods is `callDaemon`, which returns the parsed reply or a refusal and keeps no projection of its own, so there is no client copy to drift and no test to write.
- **I-006-11 — Repo identity keys on the git common directory; execution roots stay per-working-tree.** Resolution identifies a repository by its git COMMON directory and returns the MAIN checkout's working-tree root as the canonical root, so — wherever git's worktree list names the main working tree (in the `--separate-git-dir` and submodule layouts the attached folder is its own root, per acceptance criterion 4) — every working tree of one repository resolves to one identical `repo_mounts.canonical_root`, while `workspaces.fs_root` continues to name the per-working-tree path the user bound or the daemon created. **Why load-bearing.** [Spec-007 §Repo Identity And Common-Directory Keying (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-identity-and-common-directory-keying-v1-definition); identity is the key for the active-mount uniqueness index and for every daemon cache, filesystem watch, remote fetch, and throttle window scoped to a repository — keying those on the enclosing working tree instead silently multiplies them per worktree, and the plausible over-correction (returning the common directory itself as the workspace path) would root every worktree's execution at the main checkout, which is a different and worse bug. **Verification.** T-006-2B-1 unit tests over real multi-worktree git fixtures: attach from the main checkout and from each of two linked worktrees yields one identical canonical root, and each resolution simultaneously reports that working tree's own distinct root; T-006-2B-3 acceptance test asserts the second worktree attach is refused `repo.already_attached` against the first mount while a bind rooted at that worktree still succeeds with its own `fs_root` — and that the refusal also fires through the service-level identity comparison when two attach paths resolve to DIFFERENT canonical roots sharing one common directory (the planted-holder pair the canonical-root index cannot see).
- **I-006-12 — Resolution refuses rather than misattributes.** A supplied path that does not exist, a path git cannot answer for, and a working tree that is neither the main working tree git names nor one git lists for the repository (a planted `.git` pointer file) are each refused with a typed `RepoRootResolutionError`; none walks up to an ancestor, and none is reported as not a git repository (`not_a_repository`). **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior) + [Spec-007 §Repo Identity And Common-Directory Keying (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-identity-and-common-directory-keying-v1-definition); walking up lexically from a path that does not exist attributes it to whatever repository contains its parent (a dotfiles repository at the person's home directory makes that wrong for nearly every path beneath it), and a planted pointer file would let any folder claim a repository. **Verification.** T-006-2B-1 unit tests, one refusal arm per clause plus a negative control per arm proving the honest shape still resolves.
- **I-006-13 — Identity mismatch is observable, not just refused.** A git-backed mount whose re-derived common directory no longer equals the attach-persisted anchor (`repo_mounts.metadata.commonDir`) both refuses binds and run handoffs through the persisted-identity match AND projects `RepoMountHealth.status = "identity_mismatch"` on every subsequent health-reporting read until re-attach (`repo.mountReattach`, T3.11); `unreachable` takes precedence when the canonical root cannot be probed at all, the verdict is derived at read time and never persisted. **Why load-bearing.** [Spec-007 §Repo Mount Health (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-mount-health-v1-definition) + acceptance criterion 6; without the third member the health projection keeps answering `healthy` for a mount whose every bind is refusing — a lying read model that tells the person nothing is wrong exactly when re-attach is the required recovery. **Verification.** T-006-2B-4 tests: a retargeted mount projects `identity_mismatch` on mount read — the health surface; the wire workspace list carries no health member, its workspaces surfacing the mismatch as the `stale` + `lastError` transition at the next run handoff; an unreachable root whose anchor would also mismatch projects `unreachable` (precedence pinned discriminatingly); the honest multi-worktree shape projects `healthy`.
- **I-006-14 — A mount belongs to the machine.** A repository is attached once per machine: attach takes no session and no node, the daemon stamps its own node on the mount, the active-mount uniqueness is per machine by canonical root and by common directory, and a second project record for an origin already attached is refused. A session binds to the mount in `session.create`'s own step, or through `repo.workspaceBind` on convert. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior); the machine's folder list names each folder once with what uses it, and a per-session mount can neither list once nor refuse removal only while live work uses the project. **Verification.** T3.6 tests: two sessions of one project bind to one mount; a second attach of the same origin mints no record; a node id in the request is not accepted.
- **I-006-15 — A clone keeps no credential.** Git's questions reach the person through the daemon's askpass program and the answer goes to git and nowhere else; no credential is written by the app. The address or path the person typed passes to git in an argument list, never through a shell, and git's own transport rules decide. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior); a stored answer would be a credential the app never promised to hold. **Verification.** T3.8 tests: the answer to a password question appears in no row, log line or event.
- **I-006-16 — Another device sends the path it was shown.** `repo.folderList` lists the machine's folders with each entry's path, and `repo.attach` from another device takes the path of the folder it was shown, resolved and refused exactly as a path chosen on the machine is. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior); another device's `Open folder…` attaches through the one resolver the machine's own chooser uses. **Verification.** T3.9 tests: a listed folder's path attaches; a listed folder that is not a git repository refuses `not_a_repository`.

- **CP-006-7 — Workspace envelope root for approval path-scope matching (the Plan-009 walk).** `workspaces.fs_root` is the canonical workspace envelope root Plan-009's working-folder evaluation resolves for path-category approvals: a path matches by prefix containment against the run's resolved execution root (read via Plan-007's `run_execution_contexts` binding — see Plan-007 CP-007-10), and a path of unknown provenance falls back to strict per-request approval ([Spec-010 §Fallback Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)). Plan-009 reads `fs_root` + workspace state only — never writes Plan-006-owned rows. Ordering: Plan-009 builds after Plan-006 (this surface is a precondition). **Direction:** Provide to [Plan-009](./009-approvals-permissions-and-trust-boundaries.md) (reciprocal CP-009-8). **Tasks:** T2.1 (the `workspaces` DDL ships `fs_root`).
- **CP-006-8 — The `bound-root` execution root is the workspace's bound working tree.** Under common-directory keying, `repo_mounts.canonical_root` names the repository's main checkout, not the tree the user bound, so a `bound-root` run rooted at it would move every linked-worktree workspace's runs to the main checkout (the I-006-11 relocation bug class). T-006-2B-3 roots the `bound-root` arm of the execution-root service at `workspaces.metadata.boundRoot` — the admitted bind origin, recorded when the workspace is bound and never cleared by `beginRootPreparation` (which releases `fs_root` on the way into `preparing`, exactly why the origin needs its own durable carrier) — inside `packages/runtime-daemon/src/workspace/execution-root-service.ts`, a Plan-007-extended file per the ownership row (Plan-007's reciprocal CP-007-12), and [Spec-008 §Turn-Boundary Snapshots](../specs/008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots) names the workspace's bound checkout as the `bound-root` execution root. The leg ships inside Phase 2B, atomic with the identity change, because either half alone re-opens the relocation. **Direction:** Consume from [Plan-007](./007-worktree-lifecycle-and-execution-modes.md) (reciprocal CP-007-12). **Tasks:** T-006-2B-3.
- **CP-006-9 — Turn-snapshot capture normalized to the enclosing working-tree top level.** A nested `boundRoot` makes an un-normalized capture too narrow: capture's `git -C <executionRoot> ls-files` legs are cwd-scoped and list only the nested prefix ([git-ls-files(1)](https://git-scm.com/docs/git-ls-files) — the no-pathspec listing covers the current working directory), so a snapshot taken at a nested root would name a narrower tree extent than the run works in. T-006-2B-3 normalizes capture's execution-root input to the enclosing working-tree top level at the `packages/runtime-daemon/src/git/turn-snapshot/turn-snapshot-service.ts` service entry (a Plan-007-owned file per the ownership row; Plan-007's reciprocal CP-007-13) — one normalization site, so every capture addresses the whole tree the run works in — the top level derived while the tree exists and carried durably as `workspaces.metadata.checkoutRoot`, and [Spec-008 §Turn-Boundary Snapshots](../specs/008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)' applicability rule records the normalization. Captures of one normalized checkout run one at a time, across every session working in it; runs are never held, and every file restore reads the checkpoint store ([Plan-012](./012-persistence-and-recovery.md)). **How the recorded value reaches the callee.** The normalized root is **supplied**, not looked up: Plan-007 CP-007-11 keeps capture a pure callee, so the EXTEND does not add a `workspaces` read inside the snapshot service — it adds a caller-resolved `checkoutRoot` parameter, which the Plan-007 T3.2 run-setup gate captures per run into `run_execution_contexts.checkout_root` (from this plan's persisted `workspaces.metadata.checkoutRoot`) and the caller reads from that same row. This plan owns the bind-time write and the rewrite of the metadata key when a worktree becomes the execution root, and is the key's only writer; Plan-007 owns the column and the parameter. Capture, running while the tree exists, re-verifies the supplied value against the live tree and fails typed on disagreement. Ships inside Phase 2B with the CP-006-8 `bound-root` leg, because the nested-`boundRoot` shape becomes reachable exactly when `bound-root` roots at `boundRoot`. **Direction:** Consume from [Plan-007](./007-worktree-lifecycle-and-execution-modes.md) (reciprocal CP-007-13). **Tasks:** T-006-2B-3.

## Design Decisions

Each decision below is binding contract surface for the Tasks blocks.

- **D-006-1 — `repo.*` method-name strings.** Registered in `api-payload-contracts.md` §Repo Method-Name Registry: `repo.attach` (mutation; a path, from the machine's chooser or the folder another device was shown), `repo.mountRead` (query), `repo.mountList` (query), `repo.workspaceBind` (mutation; convert), `repo.detach` (mutation; Projects' `Delete` and Runtime's `Remove`), `repo.mountReattach` (mutation; the lost-folder banner's `Re-attach`), `repo.projectList` (live), `repo.projectRename`, `repo.projectArchive`, `repo.projectReactivate`, `repo.projectSetupUpdate`, `repo.projectEnvironmentUpdate`, `repo.projectBranchPatternUpdate` (mutations), `repo.clone`, `repo.cloneAnswer`, `repo.cloneCancel`, `repo.largeFilesPull` (mutations), `repo.cloneSubscribe` (stream), `repo.cloneFolderRead` (query), and `repo.folderList` (query). Tail style is dotted-camelCase per the `METHOD_NAME_FORMAT`. There is no execution-mode capabilities read: every project mount offers both places and a chat's workspace only its own root. `repo.mountList` replaces the per-session workspace list, which listed a different object. Method strings (imperative) are disjoint-by-form from the durable event names (past participle: `repo.attached`).
- **D-006-2 — `RepoMountHealth` is a derived projection object, never persisted.** Shape: `{ status: "healthy" | "unreachable"; checkedAt: string }` or `{ status: "identity_mismatch"; isRepository: boolean; checkedAt: string }` (ISO-8601; `identity_mismatch` is derived at read time from the attach-persisted identity anchor, with `unreachable` taking precedence and re-attach, `repo.mountReattach` (T3.11), the named recovery; `isRepository` says whether the mismatched root is still a git repository, which decides whether the banner offers `Re-attach` or `Open folder…`). A render-ready discriminant (`status`) plus probe provenance (`checkedAt`). No `unknown` member — the on-read probe floor (D-006-5) means every read carries a fresh verdict. `unreachable` (not `stale`) avoids overloading the workspace-state vocabulary across axes. No `health` column lands in `repo_mounts` — [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications) pins health to projection state, not row state; the identity verdict is likewise derived per read, never stored. Semantics in [Spec-007 §Repo Mount Health (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-mount-health-v1-definition).
- **D-006-3 — `repo.*` error vocabulary.** error-contracts.md §Repo: `repo.not_found` (404), `repo.root_resolution_failed` (422), `repo.already_attached` (409), `repo.detach_conflict` (409, refused while an agent runs anywhere in the project), `repo.folder_unreachable` (a folder in another WSL distribution), `repo.reattach_refused` (422, `repo.mountReattach` on a mount that does not read `identity_mismatch`), `repo.reattach_conflict` (409, `repo.mountReattach` refused while an agent runs anywhere in the project, naming the running agent and its session), `repo.root_resolution_failed`'s `not_a_repository` reason for a folder that is not a git repository, and the clone and project refusals, each code landing with its contract; §Workspace gains `workspace.stale` (409, the write-gate code). `repo.not_found` follows the `session.not_found` / `workspace.not_found` naming.
- **D-006-4 — Mount-first single funnel; every mount is a git repository.** `repo.attach` accepts a local path and refuses a path that is not a git repository; a chat's managed workspace is git-initialized from its first byte, so it is a git mount too. A workspace always binds by `repoMountId` (there is no mount-less workspace; `workspaces.repo_mount_id` is NOT NULL).
- **D-006-5 — Both places on every project mount; health detection is two-layer.** Every project mount offers a worktree of its own and the project's checkout, and a chat's managed workspace offers only its own root, so no capability is computed or read. A worktree that cannot be made surfaces when it is made, through the [Spec-007 §Execution Mode Transitions](../specs/007-repo-attachment-and-workspace-binding.md#execution-mode-transitions) failure path (Plan-007's surface), and the daemon never substitutes the checkout. Health detection: (1) on-read probe floor — every health-reporting read surface and every write gate synchronously probes filesystem availability before answering, persisting the `stale` workspace transition at probe time; (2) the mount-health re-probe runs on the working-folder watch and its slow tick, once at service start and once when the machine wakes, under the service's one scheduler; a mount that turns `unreachable` or `identity_mismatch` stops new runs in its sessions, and one banner under the session header, where its other banners sit, names the folder — `<folder> can't be reached · new runs wait until it's back` for `unreachable`, `<folder> is a different repository now · new runs are stopped` for `identity_mismatch`, carrying T3.11's `Re-attach` while the folder is still a git repository and `Open folder…` once it is not — and goes on its own when the folder is back. The banner reads the mount's health from `repo.mountRead`, and each verdict the re-probe changes is sent as `repo.mount_health_changed {repoMountId, health}` on the stream of every session on that mount. The inspector's `Mount` fact reads the same `health` in the banner's words, `Healthy`, `Can't be reached` or `A different repository now`, so the two never disagree.
- **D-006-6 — Detach semantics (V1).** Defined in [Spec-007 §Detach Semantics (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#detach-semantics-v1-definition): refuse with `repo.detach_conflict`, naming the running session, while an agent runs anywhere in the project (no force-detach in V1); otherwise forget the project record, archive the project's sessions, transition the mount to `detached` and archive all dependent workspaces, recording `repo.detached` + one `workspace.archived` each, leaving the project's approval rules in the providers' own files in the project's folder ([Plan-009](./009-approvals-permissions-and-trust-boundaries.md) D-009-11); `detached` is terminal for the row — re-attach creates a new mount row. The console's detach doors are the projects settings page's `Delete` and the runtime settings page's `Remove` on the project's folder, one act. Contract shapes: `RepoDetachRequest { repoMountId }` / `RepoDetachResponse { repoMountId, state, archivedWorkspaceIds }` in api-payload-contracts.md §Plan-006, the reply gaining that the project record was forgotten.
- **D-006-7 — `repo_mounts` persistence model: provenance + canonical columns; per-machine uniqueness; no default workspace.** `local_path` keeps the user-entered attach path (provenance; [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) "not only the user-entered path" implies both are known); `canonical_root` carries the resolver output and is the key for trust-envelope checks and dedupe. The active-mount uniqueness binds the canonical root on this machine, with no session column: two entered aliases resolving to one root are one mount, and detached rows stay re-attachable as new rows. Additional columns: `node_id` (the daemon's own node, stamped by the daemon and never taken from the caller), `origin` (`attached` for a project's folder, `managed` for a chat's workspace, naming its one chat), `updated_at`. The project record beside the mount holds the display name, the folder slug fixed at attach, setup steps, environment rows, the branch-name pattern when set, whether it is archived, and a cloning mark while a clone runs. `workspaces` carries `metadata TEXT NOT NULL DEFAULT '{}'` (`lastError` key per [Spec-007 §Execution Mode Transitions](../specs/007-repo-attachment-and-workspace-binding.md#execution-mode-transitions)) and an `execution_mode` CHECK over `'bound-root' | 'provisioned-worktree'`. Attach creates no workspace and `RepoAttachResponse` carries no default workspace id: a session's workspace is made when the session is created in the project, or converted into it.

- [POSIX.1-2024 — `opendir()` (The Open Group Base Specifications Issue 8, IEEE Std 1003.1-2024)](https://pubs.opengroup.org/onlinepubs/9799919799/functions/opendir.html) — the primary source for the readability probe's error discrimination. `opendir()` shall fail with `[EACCES]` when "Search permission is denied for the component of the path prefix of dirname or read permission is denied for dirname", and with `[ENOTDIR]` when "A component of dirname names an existing file that is neither a directory nor a symbolic link to a directory" — the read-permission clause is what makes an opendir-class probe the enumerability check a mode-`0111` directory fails, and the `[ENOTDIR]` clause is what lets the one probe subsume the file refusal. Quoted from the `opendir()` error list, not `fdopendir()`'s — the page's FIRST `[ENOTDIR]` entry belongs to `fdopendir()` and reads differently (confirmed 2026-07-25).
- [POSIX.1-2024 — `realpath()` (The Open Group Base Specifications Issue 8, IEEE Std 1003.1-2024)](https://pubs.opengroup.org/onlinepubs/9799919799/functions/realpath.html) — the primary source for the traversability-not-readability contrast the readability probe exists to close. `realpath()`'s sole shall-fail `[EACCES]` is "Search permission was denied for a component of the path prefix of file_name" — search on the PREFIX, never read on the final component; the page's one other `[EACCES]` is a may-fail confined to relative inputs, which the resolver's step-1 absoluteness gate refuses before `realpath` runs — which is why a mode-`0111` directory resolves through the resolver's step 2 yet fails the opendir probe: the two functions demand different permissions of the same directory (confirmed 2026-07-25).
