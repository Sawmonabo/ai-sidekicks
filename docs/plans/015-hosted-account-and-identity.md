## Goal

Implement the hosted account's one user record, its name, its passkeys and the daemon's credential seam.

## Scope

This plan covers the hosted account's one user record and its name read and update.

## Non-Goals

- Organization directory sync
- Billing or subscription identity state
- Guest or anonymous identity, and hardware-security-module custody: the product has one user

## Preconditions

Target paths below assume the canonical implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

## Data And Storage Changes

- Extend `users` (owner: Plan-001 — Plan-015 adds `display_name` and `identity_ref` columns to the control plane's one schema; columns recorded in [hosted-account-schema.md §Users and Identity (Plan-015)](../architecture/schemas/hosted-account-schema.md#users-and-identity-plan-015)). `users.identity_ref` carries a `UNIQUE` constraint (see D-015-2 — the account's random WebAuthn user handle).
- A passkey resolves to its one user through its `webauthn_credentials` row (T6.1), and the account read reads from `users`.
- Device keys live in the `devices` table [Plan-025](./025-remote-control.md) Phase 2 creates and machine keys in its Phase 3 `machines` table — one row per linked device and per machine, carrying its public key with its algorithm, its name, platform and version, FK-anchored to `users(id)` and therefore inside the [Spec-020 §Path 2 — Hosted account rows (hard DELETE)](../specs/020-data-retention-export-and-deletion.md#path-2--hosted-account-rows-hard-delete) exhaustive inbound-FK closure (CP-015-6). Plan-015 creates no key table and serves no read of the key set; the one key it writes is a machine's public key at enrollment (T5.4), into Plan-025's `machines`, the control plane's admission record for the service's registration. Trust is the chain's: a key is trusted only with its statement in the account's statement chain, kept in `trust_statements` — a machine's with `machine.added`, a device's with `device.linked` — and another machine learns it only from that chain ([Plan-025 §Phase 2 — Identity keys and the statement chain](./025-remote-control.md#phase-2--identity-keys-and-the-statement-chain)). The closure costs nothing, because every machine checks a key against the statement chain at live time.
- Add shared `webauthn_credentials` and `webauthn_challenges` tables (CREATE; T6.1). `webauthn_credentials` holds one row per enrolled authenticator credential — `user_id` (required, referencing `users(id)`), `credential_id` as the primary key (base64url, authenticator-minted and unique by the WebAuthn spec's own construction, and the id a `passkeyId` names), `public_key` (required; the COSE key the verifier returns), `aaguid` (required; the authenticator's AAGUID, which names the passkey's provider), `signature_counter` (required, starting at 0), `transports`, `registered_at`, `last_used_at`, plus a `user_id` index. `webauthn_challenges` holds the outstanding ceremony transactions keyed by the challenge itself, with a unique, required `transaction_id` correlator beside it and a NULLABLE `user_id` (the signed-in user adding a passkey; NULL for a sign-in, whose user is known only from the verified response, and for account creation), a `ceremony` discriminator, and `expires_at`. Both carry the `REFERENCES users(id)` FK for the same reason `devices` does — it places them inside the [Spec-020 §Path 2 — Hosted account rows (hard DELETE)](../specs/020-data-retention-export-and-deletion.md#path-2--hosted-account-rows-hard-delete) exhaustive inbound-FK closure (CP-015-6), and the closure costs nothing because a WebAuthn credential is verified live and no retained row re-verifies one post-erasure.
- Add the token tables (CREATE; T6.6): `refresh_token_families` (one row per live sign-in: a machine's, or a phone's or browser's), the denylist tables `revoked_jtis` and `revoked_token_families`, and `dpop_proof_jtis`, which holds each DPoP proof's `jti` until its `iat` window closes so a proof is accepted once. Add `authorization_requests` (CREATE; T5.4), one row per pending sign-in, written by its pushed authorization request: the `request_uri`, the PKCE challenge, the `state` it is bound to, the redirect address, the thumbprint of the DPoP key that signed the request, the machine's id, identity key, channel key, name, platform and version, its expiry, and, once the sign-in page approves it, the approved user and the authorization code; for `Create an account` also the pending `identity_ref` and name and the first passkey's assertion over the challenge made from the PKCE challenge.
- See [Hosted Account Schema](../architecture/schemas/hosted-account-schema.md) for column definitions.

## API And Transport Changes

- Add `account.read` and `account.name.update` to shared contracts and the typed client (`sidekicks-client`).
- Expose the one user: the stable id and the name, with no presence.
- Client surfaces reach these reads through the local daemon JSON-RPC gateway (I-015-3), not a direct control-plane client.
- No `account.*` method registers or reads a key: a key enters only with its statement in the account's statement chain — a machine's with `machine.added`, a device's with `device.linked` — and another machine learns it only from that chain ([Plan-025 §Phase 2 — Identity keys and the statement chain](./025-remote-control.md#phase-2--identity-keys-and-the-statement-chain)); no key bytes ride `AccountReadResponse` (I-015-5).
- Add the **five** WebAuthn operations — the four ceremony operations `WebAuthnRegistrationOptionsIssue` / `WebAuthnRegistrationVerify` and `WebAuthnAuthenticationOptionsIssue` / `WebAuthnAuthenticationVerify`, plus the authenticated credential-lifecycle operation `WebAuthnCredentialRevoke` — as routes on the control plane's `axum` router (CP-015-8). These are **control-plane** routes and deliberately not `account.*` daemon methods: the callers are the web client and the iPhone app, which create and use the owner's passkeys, the sign-in page at `/oauth/authorize`, which uses one to verify the person before T5.4 approves a machine's sign-in, and any linked device that removes one from the Devices page — never the desktop app, which carries no WebAuthn — so no JSON-RPC method string is registered, the `account.*` registry does not move, and the I-015-3 daemon-as-gateway rule is untouched. They are enumerated in [hosted-account-payloads.md](../architecture/contracts/hosted-account-payloads.md) §WebAuthn Ceremony Procedure Registry with their per-operation authentication posture, which is **not uniform**: the two authentication operations admit an uncredentialed caller, because sign-in is what mints the credential and demanding one first would make the flow unreachable on a cold install, while the two registration operations require one, except account creation's registration on the sign-in page (T5.4), which makes a new account, adds nothing to one that exists, is bound to that page's authorization request, is good once and is throttled under the same `auth.endpoint` row. The uncredentialed pair is bounded by the server-minted single-use ceremony transaction id rather than by a session, and is throttled under the existing [Spec-019 §Canonical Endpoint Group Registry](../specs/019-rate-limiting-policy.md#canonical-endpoint-group-registry) `auth.endpoint` row — that registry does not move either, since a per-transaction axis has nothing to bound when single-use consumption already caps attempts per transaction at one. Two refusal codes are registered in `error-contracts.md`: `account.passkey.challengeInvalid` (400) and `account.passkey.verificationFailed` (400).
- Add the control plane's tokens and its signed-in check (T6.6): the issuer that mints the PASETO v4.public access token and the v4.local refresh token, the RFC 9449 proof checks in both forms, and the one signed-in procedure every signed-in control-plane route mounts on, which verifies the access token and its proof, matches `cnf.jkt` and refuses a denylisted `jti`. Plan-015's own signed-in routes mount on it, and so do [Plan-025](./025-remote-control.md)'s `device.*` routes, its `machine.register`, `machine.rename`, `machine.remove` and `machine.certificateChallenge.update` routes and relay negotiation.
- Implement the real `DaemonCredentialProvider` behind Plan-004's declaration (CP-004-6 / CP-015-7): PASETO v4.public access token under the `DPoP` scheme + per-attempt RFC 9449 proof (T5.1), the token's issuance-into-the-daemon path + refresh whenever a caller's access token has expired (T5.2), and composition-root injection at every consuming site with the runtime stub assertion (T5.3).
- Add the control plane's hosted-account routes (T5.4, T5.5): the authorization-code sign-in the service runs, as OAuth routes that speak the RFCs' own wire (form bodies and `error` codes, the one exception to the JSON procedure shape) — `/oauth/par` ([RFC 9126](https://www.rfc-editor.org/rfc/rfc9126)), `/oauth/authorize` with the sign-in page, `/oauth/token` for the code's redemption and the refresh-token trade that rotates the DPoP-bound token family, and `/oauth/revoke` ([RFC 7009](https://www.rfc-editor.org/rfc/rfc7009)) — the result pages `/signed-in`, `/signed-in/code` and `/sign-in-failed`, then `account.delete`, and `account.export`, which answers the data export's `hosted-account.json`. The OAuth routes refuse with the standard codes `invalid_grant`, `invalid_request_uri`, `invalid_dpop_proof` and `use_dpop_nonce`. The other routes' request and response shapes are `crates/sidekicks-contracts/src/account.rs` and their refusal codes join `crates/sidekicks-contracts/src/error.rs`.
- Add the daemon's account sign-in methods beside `account.read` (T5.4), which the desktop's Devices page and the command line both call: `account.signIn`, `account.signInCode.submit`, `account.signInAttempt.cancel`, `account.signIn.subscribe` and `account.signOut`, with the shapes, refusals and failure reasons [Hosted Account Payload Contracts §Account Sign-In Method Registry](../architecture/contracts/hosted-account-payloads.md#account-sign-in-method-registry) gives them. The command-line verbs are [Plan-005 §Phase R3 — Client Delivery](./005-local-ipc-and-daemon-control.md#phase-r3--client-delivery)'s, and the Devices page's sign-in block is [Plan-025](./025-remote-control.md) Phase 7's.

## Invariants

Behavioral guarantees this plan must preserve. Each is bound to the Tasks that uphold it (see §Implementation Phase Sequence).

- **I-015-1 — One user per account.** The hosted account is exactly one user record; no sign-in, passkey or device link mints a second user. Backed by `users.identity_ref UNIQUE` and by `webauthn_credentials.credential_id` as its primary key, through which each passkey resolves to its one user. ([Spec-016 §Required Behavior](../specs/016-hosted-account-and-identity.md#required-behavior) + [Spec-016 §Pitfalls To Avoid](../specs/016-hosted-account-and-identity.md#pitfalls-to-avoid) + [Spec-016 §Acceptance Criteria](../specs/016-hosted-account-and-identity.md#acceptance-criteria) — the last is where the count and the multi-device case are stated together, "One authenticated user stays one user, even with multiple active devices."; ADR-001.) Tasks: T2.1, T2.2.
- **I-015-2 — Self-scoped name update.** `account.name.update` updates the calling user's own name and carries no actor-override field — the target is resolved from the authenticated identity, never from the request, so no request shape can name a subject other than the caller. ([Spec-016 §Interfaces And Contracts](../specs/016-hosted-account-and-identity.md#interfaces-and-contracts); ADR-007.) Tasks: T1.2, T3.2.
- **I-015-3 — Daemon-as-gateway single transport.** Client surfaces (SDK, CLI) reach account reads through the local daemon JSON-RPC gateway, never a direct control-plane client; the daemon proxies control-plane-stored identity truth. (ADR-008 transport-boundary decision.) Tasks: T4.1, T4.2.
- **I-015-4 — Daemon credentials are DPoP-bound, never `Bearer`.** Every credential the daemon mints for a control-plane call carries the `DPoP` authorization scheme with a matching per-attempt proof (`{jti, htm, htu, iat, ath}` per RFC 9449) — never `Bearer` — and production construction never leaves the refusing stub bound at a composition root; the control plane's signed-in procedure accepts only the `DPoP` scheme. ([Spec-016 §Required Behavior](../specs/016-hosted-account-and-identity.md#required-behavior); ADR-010; CP-004-6.) Tasks: T5.1, T5.2, T5.3, T5.4, T6.6.
- **I-015-5 — No verification-key bytes on the account read.** Key material lives only in each linked device's `devices` row and each machine's `machines` row, and reaches another machine only through the signed statement chain; `AccountReadResponse` never carries key bytes. Scoped, not absolute: `users.identity_ref` (the account's passkey user handle, never key material, D-015-2) rides the user record and is unaffected. ([Spec-016 §State And Data Implications](../specs/016-hosted-account-and-identity.md#state-and-data-implications).) Tasks: T1.1.
- **I-015-6 — WebAuthn challenges are single-use and short-lived, and the transaction id is the ceremony's only correlator.** A challenge is recorded when ceremony options are issued and consumed atomically at verification — the consuming statement is a `DELETE ... RETURNING`, so two concurrent verifications of one challenge cannot both find a row — and an unconsumed challenge expires on its own clock. A verification whose challenge or transaction id is unknown, already consumed, or expired refuses with `account.passkey.challengeInvalid` and writes nothing. Because the two **authentication** operations admit an uncredentialed caller ([Spec-016 §Required Behavior](../specs/016-hosted-account-and-identity.md#required-behavior) — sign-in is what mints the credential, so demanding one first makes the flow unreachable after a reinstall), this fence is the only thing binding that caller: it is scoped to the transaction the server issued, never to a session, and the pair is throttled under the [Spec-019 §Canonical Endpoint Group Registry](../specs/019-rate-limiting-policy.md#canonical-endpoint-group-registry) `auth.endpoint` row rather than a row of its own. ([Spec-016 §Required Behavior](../specs/016-hosted-account-and-identity.md#required-behavior) + [Spec-016 §State And Data Implications](../specs/016-hosted-account-and-identity.md#state-and-data-implications); ADR-010.) Tasks: T6.1, T6.2, T6.3, T6.4.
- **I-015-7 — Verification runs through the maintained library, never a local parser.** Attestation objects, authenticator data, and COSE public keys are parsed and verified only by the pinned verification dependency; this codebase contains no CBOR or COSE decoding on the WebAuthn path, and a verification failure is reported as one opaque `account.passkey.verificationFailed` regardless of which check failed. ([Spec-016 §Required Behavior](../specs/016-hosted-account-and-identity.md#required-behavior) + [Spec-016 §Pitfalls To Avoid](../specs/016-hosted-account-and-identity.md#pitfalls-to-avoid).) Tasks: T6.2, T6.3.
- **I-015-8 — The signature counter advances only by a conditional write in the transaction that consumed the challenge.** The verification consumes the challenge, reads the stored counter and advances it inside one write transaction, which SQLite runs one at a time on both relays, and the advance is an update that matches only while the stored value is below the presented one. A read-then-write split across two transactions defeats the check against the one adversary it exists to detect: two concurrent replays of a cloned authenticator each read the old counter and each conclude it advanced. ([Spec-016 §Required Behavior](../specs/016-hosted-account-and-identity.md#required-behavior).) Tasks: T6.1, T6.3.
- **I-015-9 — Every token-issuing route validates a token-request DPoP proof and binds what it issues to that proof's key.** The authentication-verify route and `/oauth/token` issue tokens to a caller they have not authenticated, so what makes the tokens safe is that they are sender-constrained rather than bearer. Each validates an [RFC 9449 §5](https://datatracker.ietf.org/doc/html/rfc9449#section-5) token-request proof — `typ` `dpop+jwt`, `htm` / `htu` matching this request, a fresh `iat`, a single-use `jti`, an embedded public `jwk` of a permitted algorithm, a signature verifying under it, and **`ath` required to be absent** rather than merely unchecked — and computes the issued tokens' `cnf.jkt` as that key's JWK SHA-256 thumbprint. `/oauth/par` takes the same proof ([RFC 9449 §10.1](https://datatracker.ietf.org/doc/html/rfc9449#section-10.1)) and keeps its key's thumbprint on the authorization request, and `/oauth/token` redeems that request's code only under a proof from the same key, so a code is useless to anyone but the service that asked for it. The signed-in procedure's [§4.3](https://datatracker.ietf.org/doc/html/rfc9449#section-4.3) validator cannot serve these routes: it validates a proof accompanying an already-issued access token and requires the `ath` hash of one, which does not exist until the route decides to issue it, so T6.6 builds the §5 validator beside it. A missing, malformed, replayed, or `ath`-bearing proof, or one under another key than the request's, refuses the whole request. ([Spec-016 §Required Behavior](../specs/016-hosted-account-and-identity.md#required-behavior).) Tasks: T5.4, T6.3, T6.6.
- **I-015-10 — A revoked credential can complete no ceremony, on any installation.** Revocation deletes the `webauthn_credentials` row through the authenticated `WebAuthnCredentialRevoke` route, and the verification leg resolves the signing credential from that table on every assertion — so a revoked authenticator fails resolution and receives the same opaque `account.passkey.verificationFailed` as an unknown one, issuing no token pair anywhere. The invariant is on the **server** row rather than on any client state because the authentication pair is deliberately reachable without a session: a passkey the platform still holds would otherwise sign in from any other browser or phone, which is the failure this invariant names. ([Spec-016 §Required Behavior](../specs/016-hosted-account-and-identity.md#required-behavior).) Tasks: T6.3, T6.5.

## Cross-Plan Obligations

Surfaces this plan shares with, consumes from, or owes back to other plans. Each names the provider plan and whether reciprocity is present or owed.

- **CP-015-1 — `users` columns (record-only).** Plan-015 adds `display_name` and `identity_ref` to the Plan-001-owned `users` table in the control plane's one schema (columns recorded in `docs/architecture/schemas/hosted-account-schema.md §Users and Identity (Plan-015)`). Provider: Plan-001 (owner).
- **CP-015-2 — The identity context's producer (D-015-1).** The identity T2.1 maps is produced by the sign-in this plan owns (T5.4): the service runs the authorization-code sign-in, the sign-in page verifies the person with a passkey (T6.3's verifier) before it approves the authorization request, and the request is approved for the account that passkey belongs to, or, when no account exists yet and the person chooses `Create an account`, for the account the page makes with the typed `Name` and its first passkey. T2.1 writes that new account's user record, and a sign-in takes the account as its input. No other plan produces it, and no per-user secret crosses the seam.
- **CP-015-3 — `account.*` JSON-RPC namespace: names registered + daemon-side handlers authored.** T4.1/T4.2 consume `account.read` / `account.name.update` method strings; these are registered in the Plan-005 daemon method-name registry, **and the daemon-side handlers that answer them are authored by T4.4** (`crates/sidekicks-daemon/src/ipc/handlers/account/{read,name_update}.rs`, registered on `registry.rs`) — registering a method name is not the same as implementing its handler, so the client-side consume (T4.1) requires the daemon-side responder (T4.4) or the call resolves to `request.methodNotFound`. The namespace carries no key verb — a key enters only with its statement in the account's statement chain ([Plan-025 §Phase 2 — Identity keys and the statement chain](./025-remote-control.md#phase-2--identity-keys-and-the-statement-chain)) — and each of its methods is answered by T4.4 under the same no-method-without-responder rule — the registry table at [hosted-account-payloads.md §Account Method-Name Registry](../architecture/contracts/hosted-account-payloads.md#account-method-name-registry) carries the same rows. Plan-015's `account.*` handlers are registered under Plan-005's `ipc/handlers/`, as the `presence.*` handlers are.

## Design Decisions

The design decisions behind the plan body above. [Spec-016 §State And Data Implications](../specs/016-hosted-account-and-identity.md#state-and-data-implications), `hosted-account-schema.md`, `api-payload-contracts.md` and `error-contracts.md` record what they fix.

- **D-015-1 (CP-015-2) — The identity context comes from the sign-in page's approval.** The service runs the authorization-code sign-in, and the sign-in page approves the authorization request only after a passkey verifies the person, so the account the passkey belongs to, or the account `Create an account` makes on that page, is the identity this plan resolves. This plan builds both the approval (T5.4) and the user record (T2.1), so no contract between plans carries the identity. It carries no secret: this plan produces no per-user secret for any consumer.
- **D-015-2 — `users.identity_ref` is the account's WebAuthn user handle.** The account is keyed by its own id: `identity_ref` is random bytes minted when the account is created, at most 64 of them and carrying no personal data ([WebAuthn Level 3 §5.4.3](https://www.w3.org/TR/webauthn-3/#dictionary-user-credential-params)), and every passkey the account holds carries it as its user handle. The column holds the handle's bytes as unpadded base64url, WebAuthn's own JSON form for the user id, and `users.id` stays the key. No outside sign-in makes or finds the account, so no outside id is stored beside it. [Spec-016 §State And Data Implications](../specs/016-hosted-account-and-identity.md#state-and-data-implications) and `docs/architecture/schemas/hosted-account-schema.md §Users and Identity (Plan-015)` state it.
- **D-015-3 — Plan-015 authors the daemon-side `account.*` handlers (T4.4).** T4.4 authors `crates/sidekicks-daemon/src/ipc/handlers/account/{read,name_update}.rs` (daemon-as-gateway proxy to the control-plane account services), registered on `registry.rs`, **reusing the per-namespace-handler pattern** every daemon namespace follows — no new mechanism — so every `account.*` call the client makes (T4.1) has a daemon-side responder under the daemon-as-gateway transport (I-015-3). Plan-015's `account.*` handlers are registered under Plan-005's `ipc/handlers/` (the reciprocal of CP-015-3). **Type 1.**

The verifier awaits, so the check runs before the transaction and the conditional update re-reads the row inside it. **Its reply carries the verdict and a freshly issued PASETO access/refresh pair** sender-bound to the DPoP key the caller proved possession of on this request ([ADR-010](../decisions/010-tokens-passkeys-and-the-remote-channel.md)). **That proof is the token-request form and needs its own validator.** The signed-in procedure's §4.3 validator checks a proof accompanying an already-issued access token and therefore requires `ath`, the hash of that token — a check this route cannot run, because the token it will bind does not exist until the route decides to issue it. This leg validates the [RFC 9449 §5](https://datatracker.ietf.org/doc/html/rfc9449#section-5) **token-request** proof with T6.6's §5 validator instead: `typ` is `dpop+jwt`, the `htm` / `htu` claims match this request's own method and URI, `iat` is inside the accepted window, `jti` is single-use over that window, the embedded `jwk` is a public key of a permitted algorithm and carries no private parameters, the signature verifies under it — and `ath` is **required to be absent**, not merely unchecked, so a proof minted for some other request cannot be replayed onto this one. The relying party then computes the issued pair's `cnf.jkt` as the JWK SHA-256 thumbprint of that key, which is the only thing that makes "sender-bound" true here: without it the route would hand an unauthenticated caller a bearer pair. A missing, malformed, replayed, or `ath`-bearing proof refuses the whole verification. Issuance is what makes the unauthenticated sign-in path reachable rather than merely permitted: a cold install has no stored refresh token, so a ceremony that only unlocks one is unreachable exactly after a reinstall. It is unconditional on success rather than conditional on the caller saying it has no token, which would take the client's word for its own state; the DPoP proof binds the pair to a key and establishes no identity, so the procedure stays pre-authentication. Every failure arm — unknown credential, a missing or foreign user handle, an absent user-verified flag, bad signature, wrong origin, wrong `rpId`, and regressed counter — returns the one opaque `account.passkey.verificationFailed`, so the reply is no oracle for which check failed.
  - Note: **the library's authentication result is not a discriminated union, and this task closes that at the call site.** `VerifiedRegistrationResponse` narrows — a `false` verdict makes the payload `never`, so the compiler forces the check — but `VerifiedAuthenticationResponse` carries a non-optional `authenticationInfo` beside its boolean, so code that reads `newCounter` or `userVerified` without first testing `verified` type-checks and silently accepts a failed assertion. The service therefore branches on `verified` before touching the payload and returns the refusal from that branch, with a test that asserts a `verified: false` result advances no counter and stamps no `last_used_at`. I-015-7 puts parsing in the library; it does not put judgment there.
  - Note: **the counter check is worthless outside one transaction (I-015-8).** A read and a write in two transactions are defeated by exactly the adversary a signature counter exists to detect — two concurrent replays from a cloned authenticator each read the pre-existing value, each find the presented counter greater, and each commit. The challenge is consumed and the counter's advance written in one write transaction, which SQLite runs one at a time on both relays, and the advance is conditional on the stored value still being below the presented one. Tests drive **both commit orders** of two interleaved verifications: with equal counters the first to commit wins and the other is refused; with different counters, the higher committing first refuses the lower, and the lower committing first lets both through, the counter settling at the higher.

It was rejected because single-use is the property that matters: a stateless token is replayable until it expires unless a durable fence records its consumption, and that fence is itself a row in the same SQLite database. The stateless design therefore does not remove the write; it adds a second signing secret to rotate beside a write it still has to perform. - Account tests (T5.4, T5.5): the sign-in issues a refresh token bound to the key that signed its pushed request, and a callback with a wrong `state`, `iss` or Host is refused while the attempt keeps waiting; `Create an account` whose assertion comes from a passkey other than the one its attestation registered is refused with `account.passkey.verificationFailed` and writes no user record, credential or approval, and one whose assertion answers a challenge not made from that request's PKCE challenge is refused the same way; sign-out deletes the DPoP key before any network call and sends the owed revoke once the relay is reachable; a reused refresh token revokes its family; `account.delete` leaves no Path-2 row naming the user, deletes the account's revoked families and keeps its unreaped `revoked_jtis` rows with `user_id` null; `account.export` returns no row of another account
- WebAuthn counter tests driving two interleaved verifications of one credential in **both** commit orders, proving the counter settles at the higher value with the loser refused, and proving the counter is read and advanced in the transaction that consumed the challenge (I-015-8)
- WebAuthn pre-authentication reachability tests proving a caller holding no credential completes both authentication legs, that the pair is correlated only by the server-minted transaction id, and that a response presented under a different transaction id is refused by the same consuming statement (I-015-6)
- Credential-seam tests proving every mint carries the `DPoP` scheme + per-attempt proof (never `Bearer`, I-015-4), refresh-reuse detection fails the mint closed, and the runtime stub assertion rejects a production root still bound to `DeferredDaemonCredentialProvider`

## Rollout Order

1. Land the user record's columns, the control plane's account store and tokens, and the passkey relying party (Phases 2 and 6, T5.6) — before the account unit and before Plan-025's passkey link and the web client's and the iPhone app's passkey screens
2. Land the daemon credential seam (Phase 5's T5.1, T5.2 and T5.3) before any CP-015-7 caller goes live
3. Land the account unit (Phase 5's T5.4 and T5.5); a machine enrolls at its sign-in (T5.4)
4. Land the account read and name update contracts, then enable the account read and the name update with their daemon handlers (Phases 1 and 3, T4.4)
5. Land the SDK client and the `account show` and `account rename` commands (T4.1, T4.2)
