## Goal

Build Remote Control: one user, many linked devices, each session executing on one of the user's machines, of which there may be any number, with every device able to do everything the desktop can.

## Scope

The daemon as a running background service, the machine's and each device's identity keys, the machine's registration and the encrypted channel through the person's own relay, the method proxy that carries a device's calls to the machine, devices, linking and revocation on the account's statement chain, push sealed on the machine, the device recorded on each event it sends, and — last and gated — the screens and the clients that surface all of it: the Devices page in Settings, the web client, the Android app, the iPhone app and the desktop app as a client of other machines.

## Non-Goals

Anything that admits a second account to a session. Anything that puts a second machine behind one session or moves a session between machines: a session runs on the machine it was started on for its whole life. A relay that serves other people.

## Build order

Backend Phases 1 to 6 in order, except that a resolution's answering device in Phase 6 needs only Plan-005 Phase 2B and does not wait for Phases 2 to 5; Phase 8 after Phase 3, then Phase 7's screens and clients. Within Phase 7 the web client comes first; the Devices page and the one-column fold follow it; the Android app follows the fold; the iPhone app comes last; the desktop app as a client of other machines follows the web client and the main process's window registry; the `sidekicks devices` commands follow Phase 5.

## Foundations

The phases build on these rather than rebuild them; none carries a task.

- **A device's connected state is read from its relay connection**, keyed by device rather than by account: `Connected now` while it holds a relay connection this moment, and `Last seen` at the end of its last one, with no heartbeat deciding it. A machine's reachability is read from its relay connection the same way (Phase 3); presence beats carry only `appVisible` (Phase 5).
- **The control plane's HTTP host**, `axum` on `worker` entered through `#[event(fetch)]`, serving the machine routes (one POST per procedure with a JSON body) with a shared context and its typed error answer: a refusal answers `{code, category, message}` (`ControlPlaneRefusal`) at the status its code registers in [Error Contracts](../architecture/contracts/error-contracts.md), 422 unless the code registers another (429 for `rate_limited`), a body that does not parse 400 through axum's `JsonRejection`, an unknown route 404 from the router's fallback, and an internal failure answers with a fixed message. Phase 3 adds the machine routes' refusals.
- **`crates/sidekicks-client`'s session methods on the daemon transport**, the client's methods from the method table.
- **The daemon session store and projector**: SQLite-backed append and read, and a pure fold from the event stream to a session snapshot.
- **The control plane's table for them**: `users`, in the SQLite database the relay keeps the account's data in ([deployment-topology §Account Storage](../architecture/deployment-topology.md#account-storage)).

## Phases

### Phase 1 — The daemon as a running process

This phase makes the daemon a process anyone can start. It gains an entry point, a local socket, a request/response surface over that socket, and a lifecycle — start, ready, shut down, and come back after a crash with its state rebuilt from SQLite. At its first start the start itself mints the machine's id and reads the machine's friendly name; the machine's identity key is minted under that id once the credential store exists ([Plan-019](./019-data-retention-export-and-deletion.md)), so the id never waits on the key. The friendly name comes from `scutil --get ComputerName` on macOS; on Linux `PRETTY_HOSTNAME` from `/etc/machine-info`, falling back to the static hostname; on Windows `GetHostNameW` through `sidekicks-platforms`' machine-name read, the DNS host name without its domain, never `%COMPUTERNAME%`. `crates/sidekicks-client`'s local transport is pointed at that socket.

The desktop app's main process starts the service and watches it, and never owns its life. A quit must leave the service running, and a utility-process child dies at quit, so the main process starts the service as a service of its own — on macOS the per-user login agent the installed app registers and launchd runs ([Plan-020](./020-desktop-app-and-renderer.md) T-020r-3-4), elsewhere detached — and reaches it through its socket (on Linux a logout ends a detached child unless lingering is on, which the install turns on); where a detached child does not survive the app, it starts the service through the per-user service the command line installs. On a Windows computer whose Claude Code and Codex live in WSL 2, the start is running the per-user logon task, and the main process reads the Windows half's mutex and status file instead of spawning anything ([Plan-005](./005-local-ipc-and-daemon-control.md) T-005r-4-6, T-005r-4-7). Main reaches the service only through the client helper (the daemon client in its `utilityProcess`), which holds the daemon session token. The client helper opens its connection with the handshake (`daemon.hello`), waiting up to 10 seconds for its answer, sends `daemon.ping` only after 5 seconds with no frame from the service, counts the link as dead after 20 seconds with none, and reports the link's state to main, which restarts the service with backoff (100 ms, 300 ms, 1 s, 3 s, 10 s), giving up after the fifth failed start. A service whose link died that way was never asked to stop, so it gets SIGTERM at once, which starts its drain, and SIGKILL only if it still runs once the drain bound and 2 seconds have passed (6 seconds); the service always has a full drain bound and 2 seconds from the moment it is first asked to stop, by `daemon.stop` or by SIGTERM. When the service is asked to stop or restart, after the flush and the request, the main process waits up to the service's drain bound (4 seconds), the whole drain's own bound `DAEMON_STOP_DRAIN_BOUND_MS`, so a write still running at it has time to finish rather than roll back, for it to exit, and only a daemon still running after that gets SIGTERM and, 2 seconds later, SIGKILL, so no signal cuts its drain short ([Plan-001 CP-001-1](./001-session-core.md#cp-001-1--the-terminal-drains-when-the-service-stops)). The boot card's `Retry` starts the service (`daemon.requestStart()`). The main process carries the service's state to the renderer as the `daemon.status` topic on `daemon.subscribe`: the link state from the liveness check, whether the main process started the service or found one running, and the version range — each app accepts its own service version and the previous one, and outside that range the console is read-only, naming the side that is behind with a press to its fix. The link state is `connected`, `transient_disconnect` while a lost link is being brought back, `degraded` once the backoff gives up, or `unknown` for a lost link whose cause the main process does not recognize, which reads as `degraded` and never as `connected`; each link reports one connect, at most one error and exactly one loss, so no subscriber counts a loss twice. The bridge refuses every renderer-issued mutating call (`daemon.stop`, `daemon.restart`) unless that topic reads connected, with a valid handshake behind it, returning a typed error; the daemon's own pre-dispatch gate is the check that decides. A quit flushes the service (`daemon.flush`, main's call through the client helper) and leaves it, every run and every shell running; only Settings › Runtime's `Stop` and `Restart` end work. Nothing in this phase is remote.

**Done when**

- The daemon starts from a command and answers a method call over its local socket.
- A client that loses the socket reconnects without losing session state.
- Shutdown is clean, and a restart rebuilds the session from its own event log.
- The machine's id and name exist after the first start and are the same after every later start; the identity key exists after the first start that has the credential store, minted under that id, and is the same after every later start.
- The desktop app starts the service as a service of its own, never its child, and quitting the app leaves the service, its runs and its shells running.
- A hung service is noticed within 20 seconds, gets SIGTERM at once and SIGKILL only if it still runs 6 seconds later, and is restarted with backoff; a killed one is noticed when its socket closes.
- The client helper waits up to 10 seconds for `daemon.hello` after a start; five failed starts in a row stop the restarts and surface the persistent state.
- A stop or restart sends `daemon.flush` first, then the request, then waits up to the service's drain bound for it to exit, and only a service still running after that gets SIGTERM and, 2 seconds later, SIGKILL; a quit sends `daemon.flush` alone.
- On a Windows computer whose providers live in WSL 2, the main process starts the service by running the per-user task and reads the Windows half's mutex, and spawns nothing itself.
- A lost link with a cause the main process does not recognize reads `unknown`, drawn as `degraded`, never `connected`; each link reports one connect, at most one error and exactly one loss.
- A renderer-issued `daemon.restart` without a connected status topic is refused with a typed error.

### Phase 2 — Identity keys and the statement chain

**Precondition:** Phase 1 merged.

This phase builds the identity keys, and the statement chain that decides which of them a machine trusts.

- **The machine key** is the service's Ed25519 identity key, minted in Phase 1, kept in the operating system's credential store as its own item, through `keyring-core` with the platform's store; on native Windows it is written through `sidekicks-platforms` in the service's own process at `CRED_PERSIST_LOCAL_MACHINE`, and the Windows half writes it only for a service in a WSL 2 distribution ([ADR-020](../decisions/020-cli-identity-key-storage-custody.md)).
- **A device key** is made on the device and never exported: P-256 in the iPhone's Secure Enclave, in the Android Keystore (StrongBox where there is one), and a non-extractable WebCrypto key in the web client.
- **Every public key carries its algorithm**: a device or machine key `p256` or `ed25519`, a passkey its COSE algorithm (EdDSA, ES256 or RS256), its key the COSE key its `passkey.added` carries ([Plan-015](./015-hosted-account-and-identity.md) T6.2).
- **A passkey's signature.** A machine verifies a statement a passkey signs with `@simplewebauthn/server`'s `verifyAuthenticationResponse`, so no COSE is decoded in this codebase ([Plan-015](./015-hosted-account-and-identity.md) I-015-7). It recomputes the challenge from the signature's `challengeNonce` and the statement's hash and passes it as `expectedChallenge`, and the signature's `clientDataJSON.origin` and `rpIdHash` are checked against the same origin list and `rpId` the control plane verifies passkeys with (Plan-015 T6.2). The machine holds its own copy and never takes it from the control plane at run time, which would let the party whose word the chain exists to check pick what it is checked against: `rpId` and the `https://` origin are the control-plane host the machine signed in against and trades its tokens with, fixed at that sign-in and kept with the machine's sign-in, and the `android:apk-key-hash:` origins, facts of the phone app's signing certificates, ship as constants in the service's release. Rule 15: the daemon runs `@simplewebauthn/server` 14.0.3 on `rquickjs`, the library the control plane verifies passkeys with, so one maintained library reads every passkey signature; its record is in Plan-015 T6.2.
- **Channel keys.** Every device and machine also keeps an X25519 channel key beside its identity key, for Phase 3's channel: the machine's kept in the credential store as its own item, like its identity key, on the phones in the Keychain and the Android Keystore's wrapped storage, in the web client a non-extractable WebCrypto key.
- **The statement chain.** The account's trust is an append-only chain of signed statements the control plane keeps — `device.linked`, `device.renamed`, `device.revoked`, `passkey.added`, `passkey.removed`, `runtimenode.added`, `runtimenode.renamed` and `runtimenode.removed` — each naming the hash of the one before it, each kind a past-tense fact, and each announced by a control-plane event that carries its kind as its name. The person's first machine opens it with a `runtimenode.added` it signs itself and, right after it, records the account's first passkey in a `passkey.added` signed by its machine key, from the `firstPasskey` the token route returns ([Plan-015](./015-hosted-account-and-identity.md) T5.4): the service, which runs the sign-in, completes the token exchange and, in the same step, has `verifyAuthenticationResponse` verify that passkey's assertion under its key against the challenge it recomputes from the page's nonce and the sign-in's PKCE verifier, SHA-256(nonce ‖ SHA-256(verifier)), which only the service holds, then signs both statements with the machine key, so nothing waits in between; at that first sign-in the machine has no earlier trust, so the first passkey is taken on the control plane's word bound to that sign-in, trust on first use, and every later key needs the chain; the row's platform is the AAGUID's provider name, falling back to the browser that made it. A later machine joins either at its own sign-in, its `runtimenode.added` signed by one of the account's passkeys on the relay's sign-in page, or by linking, its `runtimenode.added` signed by the device or machine that links it. The control plane keeps the chain in `trust_statements` and serves it through `device.statementList {after}`, a signed-in route on the control plane's signed-in procedure (Plan-015 T6.6). On each machine, `device.statementApply {statements}` (its shapes, like `device.statementList`'s, in `crates/sidekicks-contracts/src/device.rs`) verifies the chain and keeps it in the machine's own `trust_statements` with the devices the machine trusts, and `device.trustedList` is the machine's own verified view.
- **Statement intake.** The control plane verifies every statement posted to it before it stores it or acts on it (closing a revoked device's channel, dropping its push address, denylisting its tokens, the enrollment check): the signature, and that the signer was still trusted at that point in the chain, with the same Rust chain check every machine runs (`sidekicks-contracts`' `trust::chain`), so a revoked device's later statement is refused at the door, at about 0.2–0.3 ms of Worker CPU. Every machine verifies the chain itself as well; nothing reads the control plane's check to decide trust.
- **Where a key is trusted.** A machine trusts a key only when a path of `runtimenode.added`, `device.linked` and `passkey.added` statements reaches it from the machine's own key, each signed while its signer was still trusted at that point in the chain. A `device.revoked`, `runtimenode.removed` or `passkey.removed` ends the key it names at that point: a statement that key signs afterward is refused, and what it signed before stands, so every device, machine and passkey it added stays trusted. An ended key is never trusted again. A removed machine that is linked again first mints a new identity key under its same machine id, and its new `runtimenode.added` trusts that key and moves every device's pin for the id; its store, sessions and id stay. Phase 3's handshake reads that verified view and nothing else. A device reads the chain (`device.statementList`) in the relay transport the one front end carries on every device host (Phase 7); the desktop app, which reaches other machines as its machine, makes that read through its own service.
- **`devices`** in the one schema holds each device's id, name, kind and platform, public key with its tag, and revocation. A machine's identity key is never a `devices` row: it lives on the machine's `runtime_nodes` row (Phase 3). The control plane resolves a device id to its public key there for relay admission only, which is for spam and cost; no machine reads that lookup to decide trust.

**Done when**

- A device key made in hardware signs, and no code path reads its secret half.
- Every public key carries its algorithm, and a key with an unknown tag or COSE algorithm is refused.
- A passkey's signature on a statement verifies only under the challenge its nonce and the statement's hash give, and only from an origin on the list.
- A machine trusts a device key only through a verified chain from its own machine key; a key the chain does not reach, or reaches only through a statement its signer made after its own key was ended, is refused, whatever the control plane's `devices` row says.
- A statement a key signs after the `device.revoked`, `runtimenode.removed` or `passkey.removed` that names it is refused, while every device, machine and passkey that key added before stays trusted; an ended key is never trusted again, and a removed machine's rejoin is trusted only under the new key its new `runtimenode.added` names.
- A chain with a broken hash link or a bad signature is refused whole, and the machine keeps the last chain it verified.
- The control plane refuses a posted statement whose signature does not verify or whose signer was no longer trusted at that point in the chain, and stores nothing and acts on nothing for it.
- A first passkey swapped in without an assertion over this sign-in's challenge is refused: a `firstPasskey` whose assertion does not verify under its own key, or verifies only against another sign-in's challenge, gets no `passkey.added`, and the machine records nothing for it.
- A device id that resolves to no key fails closed rather than defaulting to anything.

### Phase 3 — The relay and the channel

**Precondition:** Phase 2 merged.

The control plane gains a relay the person deploys for themself, in their own Cloudflare account or on their own server. It forwards sealed frames and inspects none of them. On Cloudflare the relay is a Durable Object written in Rust on `worker` 0.8.7, whose `#[durable_object]` needs a direct `wasm-bindgen` dependency in `crates/sidekicks-control-plane`; the account's data lives in that object's SQLite ([deployment-topology §Account Storage](../architecture/deployment-topology.md#account-storage)), and its measured cost and delay are in [deployment-topology §Relay Cost And Delay](../architecture/deployment-topology.md#relay-cost-and-delay).

- **The machine registers.** At its first connection to the control plane the machine registers (`runtimenode.register`, its shapes in `crates/sidekicks-contracts/src/runtime_node/registration.rs`, on the daemon's credential through the control plane's signed-in procedure and account store, [Plan-015](./015-hosted-account-and-identity.md) T6.6) with its id, public key, name, platform and service version, under the owner whose user id the daemon minted at its first start (`local_machine.owner_user_id`), keyed by the machine and that owner and never by a session. When the hosted account the person signs in to already exists under another user id, attaching that account to the machine's owner is this phase's step: a registration under any user id other than the owner's makes the daemon refuse every workflow start an agent or a trigger asks for. The control plane accepts it only for a key enrolled to that owner: the service's own sign-in, started by the Devices page's `Sign in` or by `sidekicks sign-in` and never with the service stopped, enrolls the identity key's public half as this machine's key, the keys carried on the sign-in's pushed authorization request and the machine's row written by the token route ([Plan-015](./015-hosted-account-and-identity.md) T5.4), and a removed machine linked again re-enrolls the new key it mints with its new `runtimenode.added`. The control plane keeps that key as the machine's current key in `runtime_nodes.public_key`, never in `devices`; a replaced machine key is kept only in the chain's statement that ended it. `runtimenode.rename` lets the person rename it. The machine keeps one outbound relay connection while its service runs, and its reachability is read from that connection: reachable while it is up, not reachable after 45 seconds without a frame, with no heartbeat.
- **Typed refusals.** The control plane's typed error answer lives in `crates/sidekicks-control-plane/src/server/router.rs`: a refusal is a `ControlPlaneRefusal` answered with the body `{ code, category, message }` at the status its code registers in [Error Contracts](../architecture/contracts/error-contracts.md), 422 unless the code registers another (429 for `rate_limited`), so a caller reads the code without parsing the message, and a 500 carries the fixed message `Unexpected internal error`, never the internal error's text. This phase adds the machine routes' first typed refusal, `runtimenode.permission_denied`, a `ControlPlaneRefusal` whose body is `{ code, category, message }`. It also brings the router's own refusals into the `ErrorResponse` envelope of [Error Contracts §Error Response Shape](../architecture/contracts/error-contracts.md#error-response-shape): an unknown procedure (the router's fallback, 404), a body that does not parse (axum's `JsonRejection`, 400), a wrong method and an internal failure each answer with a registered namespaced `code`, an internal failure with `system.internal_error`, and the codes this needs are added to the registry in `crates/sidekicks-contracts` in the same change.
- **One channel per device and machine**, carrying every session and screen on that machine, on the Noise Protocol Framework's KK handshake and transport in one of two profiles, `Noise_KK_25519_AESGCM_SHA256` offered first and `Noise_KK_25519_ChaChaPoly_SHA256` second, with no construction of the product's own. Each end's X25519 channel key is certified by its identity key in the statement that trusts it. A fresh handshake runs on every connection and every 10 minutes on a long one, and the old keys are erased.
- **The channel's first frame** carries the channel version and the profiles the device runs; the machine answers with the first it also runs or closes the connection with `channel.no_common_profile`. Both ends bind the offer and the answer into the handshake's prologue. AES-GCM is offered first because WebKit's WebCrypto refuses ChaCha and AES-GCM is 3–6× cheaper there; there is no fallback outside the two profiles. The classical handshake is not post-quantum, and the docs say so; the hybrid profile joins later through this negotiation, on the same keys and frames, once its specification is finished and reviewed.
- **Relay access.** `RelayNegotiationRequest` carries no session id: negotiation, a signed-in route on the same procedure, hands back a relay endpoint and a short-lived connect token bound to the device and the machine. The relay holds at most one live connection per key; a new one closes the one before it, so the newest connection wins, and a key that keeps displacing itself, three times within a minute, is flagged.
- **The relay's own rules.** The relay counts requests on its sign-in routes only — sign-in, token refresh and device linking — and answers a caller over the limit with 429 and a `Retry-After` ([Plan-018](./018-rate-limiting-policy.md)): on the Workers relay in the per-identity Durable Object, one global counter that rotating edge locations do not reset, and on the Compose relay in the relay process's memory. A counter error fails that one request like any backend error. On the WebSocket the relay sees only encrypted frames and counts none: it forwards each device's frames as fast as the machine drains them, and backpressure on the channel bounds frames and bytes in both directions. A relay's key is pinned only when it has no publicly trusted certificate: a pinned relay whose key changed is refused and recorded (`relay.pin_refused`, `relay.spki_mismatch`), and `sidekicks relay repin --force` accepts the new one through the daemon's `relay.repin {spkiHash}`, which refuses and changes nothing when the hash does not match the key the relay presents. The relay block of `sidekicks daemon status`, the `relay` field of `daemon.status.read`, counts since the service started.
- **The channel's two ends.** The machine's end is `snow`, built with `ring-accelerated`, in `sidekicks-daemon`'s `remote` module. The shared channel package, new under `packages/`, holds the channel for the web client and the phones: the Noise handshake and transport code. The first frame's shape, the profile names and `channel.no_common_profile` are wire, so their Rust types live in `crates/sidekicks-contracts`, their generated TypeScript in `packages/contracts`, which the package imports. The package implements `KK` from Noise revision 34 on WebCrypto's X25519, AES-GCM, SHA-256 and HKDF, with `@noble/ciphers` 2.4.0 for ChaChaPoly, tested against snow's and cacophony's `KK` vectors and against `snow`: `noise-handshake` 4.2.0, `@libp2p/noise` 17.0.4, `salty-crypto` 1.0.0-rc.4, `@lukeburns/clatterjs` 1.0.0, `@niomon/noise-js` 2.0.1, `noise-protocol` 3.0.2 and `snow` 0.10.0 as WebAssembly were considered, and each takes its Diffie-Hellman and cipher as synchronous calls over private-key bytes, so none runs on a non-extractable WebCrypto key. `@noble/ciphers` joins the workspace catalog beside `@noble/hashes`, and the package takes it through `catalog:`. The package's key exchange is an asynchronous call its host supplies: in the web client WebCrypto's `deriveBits` on the non-extractable channel key, so the static and ephemeral private keys never leave WebCrypto; on a phone a bridge member that runs every exchange on the channel key natively, and that also makes each handshake's ephemeral X25519 key natively, returns only its public half, runs that handshake's exchanges on it and erases it when the handshake ends, so neither the key the Keychain or the Android Keystore's wrapped storage holds nor any ephemeral private key enters the page. X25519 `deriveBits` from a non-extractable WebCrypto key works in a `capacitor://`-style WebKit page, both sides agreeing, and that page's AES-256-GCM output was measured byte-identical to Node's for the same key, nonce and data. Every Noise message is at most 65,535 bytes, each direction's nonce counter refuses at 2^64−1, and Noise's `Rekey()` is never called, because the fresh handshake on every connection and every 10 minutes replaces it. The key-exchange results, the chaining key and the handshake's and transport's cipher keys pass through JavaScript memory in the page hosts, an AES-GCM transport key only until it is imported into WebCrypto, a ChaCha one for the channel's life, so erasing them at a rekey is best effort there. One full handshake in a WebKit page, each profile, is timed once in this phase's run, since it repeats every 10 minutes. Remote Control ships with no outside review gate.
- The relay stores nothing beyond the live connection, so there is no mailbox to drain and nothing to read after both ends disconnect.
- **The desktop app's control-plane calls.** The service answers `controlPlane.call {procedure, input}` and `controlPlane.subscribe {procedure, input}` on its local socket for the desktop app, over the client helper's connection (the renderer's calls reach the helper over the `MessagePort` main hands the page through the preload), their schemas in `crates/sidekicks-contracts/src/device.rs`, beside the procedures they forward: it attaches this machine's access token and signs each request's DPoP proof. A `controlPlane.call` `procedure` is one of `device.linkStart`, `device.linkRedeem`, `device.link`, `device.linkCancel`, `device.rename`, `device.revoke`, `device.forget`, `device.statementList`, `device.pushAddressSet`, `runtimenode.rename` and `runtimenode.remove`, a `controlPlane.subscribe` `procedure` is `device.list`, and relay negotiation or any other procedure is refused. A `controlPlane.call` waits for the control plane no longer than the deadline [Spec-027 §Interfaces And Contracts](../specs/027-remote-control.md#interfaces-and-contracts) sets, the connection's own bound within it, and past it is answered `relay.connection_failed` with its `reason`, which `controlPlane.call`'s contract registers among its refusals; the client keeps that section's limit on `controlPlane.call`s in flight on a connection, holding further ones in order.
- **The device list's live read.** The service holds one Server-Sent Events stream of `device.list` per machine for every local reader, a second only across a token's renewal, opened with the first `controlPlane.subscribe` and closed after the last, and sends each reader the newest list, never a queue of them, each value `live`, `held` or `unread` as Spec-027 describes. It reads the stream with reqwest 0.13.5's `bytes_stream()` into `sse_stream::SseByteStream` (`sse-stream` 0.3.0, already in the workspace, which parses `id` and `retry`), no new crate: `reqwest-eventsource` pins reqwest 0.12, and `eventsource-client` fixes its headers when the client is built, so it cannot sign a fresh DPoP proof for each dial. Each list is checked against `DeviceListSnapshot` before it is kept. The service keeps the last list after the last reader leaves, and a new first reader gets it at once as `held {connecting}`, then `live`; with nothing kept, the first value waits for the first dial's outcome, at most the connection's bound Spec-027 sets. A sign-out drops the kept list. A stream with no byte for 45 seconds, three missed keepalives ([ADR-013](../decisions/013-control-plane-api.md)), is dropped and its readers get `held {unreachable}`; the service dials again at once on the scheduler's wake signal, on the network-change signal and when its relay connection returns, each of which starts its retry waits over at 1 second, and otherwise after its retry waits, 1 second doubling to 32 seconds with no jitter, refreshing the access token before every dial. A network change while the stream is live dials a second stream as a token's renewal does, moves its readers to it at its first list and closes the first, and keeps the first when the second cannot be dialed. Before its access token expires, the service dials a second stream under a fresh token, moves its readers to it at its first list and closes the first, so a token's expiry never shows a reader a held list. The figures are first settings, tuned at the endurance run. Budget: with two windows and the CLI following the list for an hour while a phone changes networks every minute, one stream, and a second only across a token's renewal; the kept list and one waiting list per reader; one dial per drop and at most four more an hour from token expiry; one whole list per change; measured once in this phase's run.
- **The relay connection's return.** The service dials its relay connection again after its retry waits, 1 second doubling to 32 seconds with no jitter, and at once on the scheduler's wake signal and on the network-change signal, each of which starts its waits over at 1 second. A network change while the connection is open sends a WebSocket ping at once, and no pong within 5 seconds drops the connection and dials again. One signal acts on the relay connection and the device-list stream alike, and a dial already under way is not started again. `sidekicks-platforms`' network watch reports a change only after 1 second with no further event, and only when the usable addresses or the network path changed; a change means try now, never that the network works. The figures are first settings, tuned at the endurance run. Budget: no wakeup and no thread of the service's own while the network is unchanged; at most one ping or dial per connection per reported change; measured once in this phase's run.

**Done when**

- Two endpoints exchange frames the control plane cannot decrypt, proven by a test that holds the relay's whole view and fails to read a payload.
- A connect token replayed for another device or machine is refused, and an expired one is refused.
- A refused registration reaches the caller with `{ code, category, message }` as the response body, the code read without parsing the message.
- A dropped connection reconnects with a fresh handshake, and a long connection rekeys every 10 minutes, erasing the old keys.
- A machine that answers with a key the device has not pinned, and no later `runtimenode.added` for its id behind it, is refused.
- A web client in WebKit and a machine agree on `Noise_KK_25519_AESGCM_SHA256`; a peer offering only `Noise_KK_25519_ChaChaPoly_SHA256` gets that profile.
- The channel package passes the four `KK` vectors in snow's and cacophony's vector files, one per profile in each, run through the same `deriveBits` path as production, and a WebKit page completes a handshake and exchanges frames with the daemon's `snow` in both profiles.
- A wrong static key on either end fails the handshake, and a channel key other than the one its identity key certified is refused.
- Each profile's nonce layout matches `snow`'s (AES-GCM's big-endian counter, ChaChaPoly's little-endian one), each direction keeps its own counter, which refuses at 2^64−1, and a replayed or reordered frame fails.
- A truncated message, one over 65,535 bytes, a bad tag, and an invalid or all-zero key exchange each fail closed with no state advanced; a frame that fails to open ends the channel, and a failed handshake leaves no keys.
- WebCrypto's X25519 runs the handshake on the lowest browser of each supported host: Safari and iOS 17, Chrome and Android WebView 133, Firefox 130.
- An altered profile offer fails the handshake on both ends, and a machine with no common profile closes the connection with `channel.no_common_profile`.
- A key that connects from two places three times in a minute is flagged, and its newest connection is the one that stays open.
- A relay whose certificate chains to a root the operating system trusts is never pinned, and a renewal that changes its key connects; a pinned relay whose key changed is refused and records `relay.pin_refused`, and `sidekicks relay repin --force` accepts the new key over the daemon's `relay.repin {spkiHash}`; a hash that does not match the key the relay presents is refused and changes nothing.
- A machine registers once, keyed by machine and owner, and reads as not reachable 45 seconds after its relay connection goes quiet; a registration whose key is not the one enrolled to that owner is refused.
- After both endpoints disconnect there is no stored frame anywhere on the control plane.
- A `controlPlane.call` or `controlPlane.subscribe` naming a procedure off its list, relay negotiation included, is refused and never reaches the control plane; one on the list reaches the control plane under the machine's token and a fresh DPoP proof.
- A `controlPlane.call` to a control plane that accepts the connection and never answers is answered `relay.connection_failed` with `reason` `timed_out` at the deadline, on a paused clock.
- Two readers of `controlPlane.subscribe` share one stream, and once both have left a third gets the kept list at once as `held`, then `live`; a stream silent past 45 seconds turns its readers `held {unreachable}`, on a paused clock; a list that fails `DeviceListSnapshot`'s check never reaches a reader.
- The relay connection and the device-list stream, each in a 32-second retry wait, dial at once on a reported network change; a change while the relay connection is open pings it, and redials only when no pong comes within 5 seconds.

### Phase 4 — Phone-to-host method proxy with terminal streaming

**Precondition:** Phase 3 merged.

The client transport gains a relay arm. This phase writes the channel's stream framing, how its streams are numbered, opened, closed and kept apart, and with it the contracts of `preview.portTunnelOpen`, `preview.portTunnelResume` and `preview.portTunnelClose`, since each shared-port connection is one of those streams. A call from a device is sealed, relayed, opened by the daemon, executed against the machine, and answered back over the same channel. Event subscriptions ride the same channel, so the transcript streams to a device live rather than by polling, and a reconnecting device resumes every stream from its last event. Terminal traffic is the hard case and gets its own handling: it is high-rate, ordered, and bidirectional, so it carries backpressure and a resume point instead of being a best-effort stream that silently drops. A shared port is one byte stream per TCP connection the device's listener accepts (`preview.portTunnelOpen`, `preview.portTunnelClose`, their shapes in `crates/sidekicks-contracts/src/preview/methods.rs`), its bytes carried as attachments beside the JSON, never base64, at most 256 KB buffered each way, under the same backpressure; the machine forwards only to listed ports on its own loopback. A tunnel is bound to the device and resumes by byte offset after a reconnect (`preview.portTunnelResume {tunnelId, receivedOffset}`), each side keeping its unacknowledged tail, which the 256 KB window bounds, for a grace period. Another device's Preview is a live picture: a screencast the service produces on whichever host runs the page (`preview.screencastSubscribe`, carrying the frames, the page's right-click menu, a file chooser or a File System Access picker the device's press or key opened, and a file the page saved for the device, a `save` element and its `savePart` parts of at most 256 KiB under the channel's backpressure, so a part never holds a shell's typing behind a message near the 4 MB cap, with the device's answers on `preview.screencastAck`, `preview.screencastInput`, `preview.screencastEdit`, `preview.screencastFileChoose` and `preview.screencastSaveAck`), with focus emulation, the device's touches reaching the page as touch events, carried over the same channel with no debug port on either host. The method proxy keeps the last `presence.heartbeat` per device, so a device's presence is always its latest.

**Done when**

- Every method the local transport serves is served over the relay, with one suite run against both.
- Transcript events stream to a device with no gaps across a reconnect.
- Terminal output streams to a device and input streams back, with ordering preserved and a bounded buffer under load.
- A slow device applies backpressure rather than making the machine buffer without limit, on every stream the machine sends: the terminal, the live picture, a saved file's parts, a shared port's bytes and a voice reply.
- A shared-port connection whose device reconnects within the grace period resumes from its byte offset through `preview.portTunnelResume`, with no byte lost or repeated.
- A forward to a port that is not on the list, or to an address that is not the machine's loopback, is refused.
- A device that opens a session through its machine gets the same session id and its full history, and opening it never forks the session, changes its id or resets its runs.
- Several devices driving one session through its machine at once leave its transcript whole, every event in one order.
- A device's presence on a machine is the last `presence.heartbeat` the machine received from it, and the relay forwards every heartbeat frame unread.

### Phase 5 — Devices, linking and revocation

**Precondition:** Phases 2 and 3 merged.

Linking, renaming, revoking and removing are statements in the chain Phase 2 builds, and every machine verifies them itself.

- **On the control plane:** `device.list` (what the Devices page in Settings draws: a live read of machines, devices and passkeys, with each one's connected state and last-seen time, the relay writing last seen at most once a minute, the relay's flag on a key seen in two places at once, and, on a revoked device, which machines have not yet applied its revoke, and the events: each statement's, carrying its kind as its name — `device.linked`, `device.renamed`, `device.revoked`, `passkey.added`, `passkey.removed`, `runtimenode.added`, `runtimenode.renamed` and `runtimenode.removed` — beside `device.forgotten` and `runtimenode.registered`, and after every change, a statement's or any other, the whole `DeviceListSnapshot` again with `statementHead`, the chain's newest statement; its keepalives and its end at the access token's expiry, and at once on the token family's revocation, are [ADR-013](../decisions/013-control-plane-api.md)'s), `device.linkStart`, `device.linkRedeem`, `device.link`, `device.linkCancel`, `device.rename`, `device.revoke`, `device.forget` and `runtimenode.remove`, which posts `runtimenode.removed`. Where the open stream is held, in a Durable Object or in a Worker that reaches one over a hibernatable WebSocket, is settled by a probe on a deployed relay before it is built, since a Durable Object holding a stream is billed for wall-clock time while it is active; the relay object's measured cost and delay are in [deployment-topology §Relay Cost And Delay](../architecture/deployment-topology.md#relay-cost-and-delay). The `device.*` shapes are in `crates/sidekicks-contracts/src/device.rs`, and `runtimenode.rename` and `runtimenode.remove` in `crates/sidekicks-contracts/src/runtime_node/registration.rs`.
- **On each machine, over the channel:** the chain head is exchanged at every channel open and applied through Phase 2's `device.statementApply`, and a revoking device also sends its statement to every machine it can reach.
- **Linking** is a 5-minute single-use link whose fragment carries a 32-byte linking secret the control plane never sees, confirmed by six digits both sides compute from that secret, both devices' keys and the list of machine keys: HKDF-SHA256, the secret as input key, an empty salt, the RFC 8785 bytes of `{linkingKey, newKey, machineKeys}` (keys base64url, `machineKeys` sorted by raw key bytes) as info, the first 4 output bytes big-endian mod 10^6, zero-padded to six. One fixed test vector (the secret, both devices' keys, the machine keys and the expected six digits), committed with the code that computes the digits, is checked by the service and by the phone. A passkey links a device with no other device at hand, outside the desktop app only, through [Plan-015](./015-hosted-account-and-identity.md) Phase 6's WebAuthn ceremony routes (CP-015-8).
- **A removed machine linked again.** Removing a machine posts `runtimenode.removed`, stops every port it shares and closes every forward open on it, and the machine comes back only by being linked, as a new computer joins. Before it is linked again its service mints a new identity key under its same machine id; its new `runtimenode.added` trusts that key and moves every device's pin for the id, and its store, sessions and id stay as they were. The service mints its identity key at first start and at this rejoin, and never otherwise.
- **Revoking** closes the revoked device's channel at once rather than waiting for anything to expire. Every device and passkey the revoked device linked or added before stays trusted: a device it linked carries `Linked from <device>, which you revoked. Revoke it if that device was lost.` on its card, and a passkey it added carries `Added from <device>, which you revoked. Remove it if that device was lost.` on its row, both read from the chain.
- **Push.** `device.pushAddressSet {platform: apns | fcm | webPush, address}` at link time and whenever the platform changes the address, stored with the device and dropped at revoke; `device.notificationSettingsSet` hands each machine the device's switches and push keys; `push.send` carries a notice the machine sealed, its request and the plaintext notice the phone apps and the service worker open being in `crates/sidekicks-contracts`, the notice beside the attention types in `attention.rs`, their generated TypeScript in `packages/contracts`; and the APNs, FCM and VAPID senders on the control plane present the person's own credentials. There is no notification-preferences table and no control-plane queue.
- **Presence.** Each device sends `presence.heartbeat`, carrying `PresenceHeartbeat`, on each machine connection it holds, when `appVisible` changes and otherwise every 15 seconds; the machine keeps the last one per device in memory only. Presence is per machine and held by the machine, never by the control plane: `presence.read {}` and `presence.subscribe {}` report the devices connected to this machine and whether an app window is in front on each, a lock or sleep counting as not in front, with no session id.

**Done when**

- Linking a second device works end to end, from an unlinked state to a device driving a session, on both sides of the six-digit check.
- Linking, renaming and revoking are statements in the account's chain, and every machine verifies the chain itself; a link is a fact of the account, never of a session.
- Re-linking on the same key is refused.
- A revoke withheld from one machine is caught at the next connection of any other device.
- Revoking closes the revoked device's connection promptly and its next call refuses; a device it linked before stays linked and reads `Linked from <device>, which you revoked. Revoke it if that device was lost.`, and a passkey it added reads `Added from <device>, which you revoked. Remove it if that device was lost.`
- A removed machine linked again connects under its new key: every device moves its pin for the machine's id on the new `runtimenode.added`, the old key stays refused, and the machine's sessions are there as they were.
- A rename reaches every device, and every machine the next time it connects.
- `device.list` carries a key's two-places flag and, on a revoked device, the machines that have not yet applied the revoke; removing a machine stops every port it shares and closes every forward open on it.
- A device's relay connection opening sends the whole list with that device connected; a `device.list` stream ends at its access token's expiry, and at once when the token's family is revoked.
- A sealed push reaches a device whose connection is down, and the relay cannot open it.

Rule 15: on the machine, Web Push encryption (RFC 8291, `aes128gcm`) is `web-push-native` 0.5.0 (`default-features = false, features = ["serialization"]`) in `sidekicks-daemon`, and the push seal is `hpke` 0.14.1 (feature `aes`: `XWing`, `HkdfSha256`, `AesGcm256`, base mode), so the control plane never holds a plaintext notice. On the control plane the senders are plain `fetch` with WebCrypto signing rather than `apns2`, `google-auth-library` and `web-push`: APNs posts to `api.push.apple.com`, which Cloudflare's proxy upgrades to HTTP/2; FCM's HTTP v1 API takes an RS256 assertion signed through WebCrypto; APNs and VAPID sign ES256 through WebCrypto's ECDSA P-256; this keeps `rsa` 0.9 (RUSTSEC-2023-0071) out of the tree.

The document and folder pickers are a small plugin of the app's own over the Storage Access Framework, as the iPhone's device key is a plugin of that app's own: a save opens `ACTION_CREATE_DOCUMENT` with the cleaned name as `EXTRA_TITLE` when the `save` element arrives, the device taking no part until the person picks, so the channel's backpressure holds the rest on the machine, then writes each part to `ContentResolver.openOutputStream` on the picked document's address, a cancel ending the save as delivered; a folder picker opens `ACTION_OPEN_DOCUMENT_TREE`, lists the tree through `DocumentsContract.buildChildDocumentsUriUsingTree`, and reads each file through `ContentResolver.openInputStream` part by part into the attachment ingest, each with its path inside the folder ([Android: Access documents and other files from shared storage](https://developer.android.com/training/data-storage/shared/documents-files)). Considered and not used: `@capawesome/capacitor-file-picker` 8.1.0 (MIT, the newest), whose `pickDirectory` opens `ACTION_OPEN_DOCUMENT_TREE` but returns only the tree's address, with nothing that lists or reads it, which has no create-document call and whose `copyFile` copies a whole file between two addresses ([`FilePickerPlugin.java`](https://github.com/capawesome-team/capacitor-plugins/blob/main/packages/file-picker/android/src/main/java/io/capawesome/capacitorjs/plugins/filepicker/FilePickerPlugin.java)); and `@capacitor/filesystem` 8.1.4, which reads `content://` files but documents no write to one ([Capacitor: Filesystem](https://capacitorjs.com/docs/apis/filesystem)).
- **The iPhone app** ([Spec-028](../specs/028-connect-an-ios-app-and-drive-control.md)): the one front end in a Capacitor shell, native only for the Secure Enclave key, the channel key's exchanges run natively on the key the Keychain holds, so it never enters the page, the Notification Service Extension, the cover, the scan, the page view for shared ports, the share sheet for a file a page in Preview saved and staging each machine's console bundle as the Android app does, passkeys through the same routes, for which the control plane serves `/.well-known/apple-app-site-association` (`webcredentials`) from the deployment settings this app's signing supplies ([Apple: supporting associated domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains)), and, after each sign-in, `ASCredentialUpdater.reportAllAcceptedPublicKeyCredentials` and, after the account's name changes, `reportPublicKeyCredentialUpdate(relyingPartyIdentifier:userHandle:newName:)`; a linking link opened on the phone going straight to linking's next step; iOS 26 and later; signed under the person's own Apple developer account.
- **The desktop app as a client of other machines**: the desktop app reaches the person's other machines as its machine, through its own service, which holds this machine's keys and relay tokens and negotiates and authenticates one channel per other machine, so the main process holds no key and no channel; the machine switch, the bell merged across machines, the loopback listener for shared ports, and the system save dialog for a file a page in Preview on another machine saved from this app's press: its own service, through which the stream runs, writes the `savePart` parts into its staging folder instead of passing them to the renderer, and main, once the dialog has a path, reads them part by part (`preview.saveRead {saveId, offset}`) and writes the chosen file itself, so no part crosses the renderer or the window's IPC and no path crosses on a WSL 2 computer.
- **`sidekicks devices`**, with `link`, `rename`, `revoke` and `forget`, each with `--json`. `sidekicks devices` reads the list through the service's `controlPlane.subscribe`: it prints the first `live` or `held` value, a `held` list with when it was read, then cancels the read, and on `unread` exits 69 naming why.

The front end runs in WebKit as well as Chromium: every page declares its doctype and `utf-8`, and the renderer build's `build.cssTarget` names the desktop's Chromium and the Safari and iOS versions the hosts carry, so the build writes the `-webkit-` forms. There is no connected-devices banner: who is connected is on the Devices page's cards. Every client with a hardware back gesture obeys the dismiss-only rule the spec sets: Back walks the same ladder the escape key walks and never interrupts a turn.

### Phase 8 — Self-host deployment

**Precondition:** Phase 3 merged.

There is nothing to deploy until the relay exists. This phase makes the relay a thing the person can stand up, and it is the owner of the relay-side half of [Spec-023: Self-Host Secure Defaults](../specs/023-self-host-secure-defaults.md) — rows 1, 2, 3, 4, 5, 8, and 9.

The relay runs behind a TLS front rather than terminating TLS itself: Caddy v2 on `:443`, with `:80` open only for the ACME HTTP-01 challenge. `DEPLOY_MODE` is declared at config time and decides the issuance path, and renewals run on ACME Renewal Information windows rather than a fixed fraction of the certificate's life. `RELAY_BIND` stays container-internal and is never port-forwarded by the shipped Compose file, and a non-loopback bind with no TLS in front of it exits non-zero at config-parse time instead of starting. The first run is a one-shot service in the Compose file, the `first-run` mode of the relay's native program (`sidekicks-control-plane`'s self-host target), that the relay waits on (`depends_on` with `condition: service_completed_successfully`). It generates the relay's secrets, persists them `0600` and writes the first-run sentinel: the control plane's two token keys, the Ed25519 key that signs access tokens and the symmetric key that seals refresh tokens, with `getrandom::fill`; the Web Push VAPID key pair (ECDSA P-256, RFC 8292), whose public key the relay serves to the web client for its push subscription. The APNs and FCM credentials are issued by Apple and Google, so the person supplies them and the relay keeps them. A relay that finds the sentinel absent with its secrets present refuses to start, naming the sentinel and the secrets it found. The startup banner prints the relay's effective binds, TLS mode and fingerprint, and each active override on its own `WARNING:` line. The Compose relay keeps the account's data in a SQLite file on a volume of the stack, which the relay's one process alone opens through the control plane's account store ([Plan-015](./015-hosted-account-and-identity.md) T6.6; [deployment-topology §Account Storage](../architecture/deployment-topology.md#account-storage)). The file is backed up through SQLite while the relay runs, never as a plain copy of a file under a live writer, by SQLite's online backup API through `rusqlite`'s `backup` feature, as the service's own database is ([Spec-013 §Backup Policy](../specs/013-persistence-and-recovery.md#backup-policy)).

On the Compose relay a server-name router sits in front of Caddy on `:443`, so a shared port's address (`https://<port>-<machine label>.<relay's domain>/`) passes through by its server name to the machine, which ends TLS itself; each machine has a wildcard name under the person's domain. The relay is the authoritative DNS server for one subzone the person delegates to it with two NS records (plus glue when the server's name is inside it), answering each machine's `_acme-challenge.<machine>` TXT and its own `*.<machine>` A/AAAA records from its store, which `runtimenode.certificateChallengeSet` writes, so no DNS-provider credential sits on the server and no record waits to spread; that server is `hickory-server` in the relay's native program, on UDP and TCP 53 beside `:443` and `:80`, authoritative only, with no recursion and with response-rate limiting. The relay stores the challenge record (`runtimenode.certificateChallengeSet`, in `crates/sidekicks-contracts/src/runtime_node/registration.rs`) only for a machine that proves its key: the request carries the machine identity key's signature (`machineSignature`) over the canonical `{nodeId, challengeValue}`, checked against `runtime_nodes.public_key`, and the record stands for the minutes of a challenge. In the web client `Open` first fetches a one-time ticket over the channel (`preview.portTicketIssue {port}`), good for 60 seconds, which the machine trades for a cookie scoped to that address (`HttpOnly`, `Secure`, `SameSite=Lax`) that lives until the port stops being shared or the device is revoked; a request without it gets a plain 404. Caddy takes `ACME_PROFILE`, empty by default. The Workers relay cannot pass TLS through and TLS is never ended at Cloudflare, so there the web client has no shared ports and says so.

**The machine's certificate client.** The machine holds its shared-port name's certificate and ends TLS itself, so the client that obtains that certificate runs in the daemon: it obtains the certificate with a maintained ACME client library, answering the DNS challenge through `runtimenode.certificateChallengeSet`. Choosing the library is this task's acceptance, recorded in this plan with what was considered and what decided it.

The relay process is measured under the named workload — one person, their machines and their devices, on one relay — against the budget in [deployment-topology §Infrastructure Requirements](../architecture/deployment-topology.md#infrastructure-requirements); the baseline is recorded in the PR that lands this phase, and measured again after each relay change that affects it.

**Done when**

- A `git clone` plus one command brings up the relay and Caddy with a valid certificate and no hardening steps read first.
- A non-loopback bind without TLS refuses to start, naming the option that is wrong.
- A certificate renews on an ARI window in a test that advances the clock, without a rate-limit retry storm.
- The first-run step generates the two token keys and the VAPID key pair once, each `0600` and never printed to a log, and the relay starts only after it exits successfully; with the sentinel deleted and the secrets present, the relay refuses to start and names them.
- The account's SQLite file is backed up while the relay writes to it, and the backup opens as a whole database.
- The relay keeps the APNs and FCM credentials the person supplies, since Apple and Google issue them.
- The banner prints on every start and names every active override on its own `WARNING:` line.
- A shared port opens in a browser tab at its machine's address, and the relay's view of the connection holds no plaintext.
- The relay answers a machine's `_acme-challenge.<machine>` TXT and `*.<machine>` A/AAAA records for the delegated subzone from its store, refuses a recursive query, and holds no DNS-provider credential.
- The daemon obtains its shared-port name's certificate through the chosen ACME client library, answering the DNS challenge through `runtimenode.certificateChallengeSet`, and the library choice is recorded.
- The relay process, measured under the named workload, fits the deployment-topology budget, and the baseline is recorded.
