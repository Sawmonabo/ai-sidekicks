## Execution Windows (V1 Carve-Out)

Plan-006 ships in two windows — a **partial deliverable** (substrate + `session.*` namespace) that unblocks [Plan-001](./001-session-core.md) Phase 5, and a **remainder** that completes the daemon control surface. This section documents the split so engineers reading Plan-006 in isolation see it.

### Plan-006-Partial (substrate + `session.*` namespace)

Lands alongside Plan-001 to unblock Plan-001 Phase 5. Scope:

- **[Spec-006 §Wire Format](../specs/006-local-ipc-and-daemon-control.md#wire-format) substrate** — `packages/runtime-daemon/src/ipc/local-ipc-gateway.ts` and `packages/runtime-daemon/src/ipc/protocol-negotiation.ts` implementing JSON-RPC 2.0 with LSP-style Content-Length framing (`Content-Length: <byte-count>\r\n\r\n`), 4 MB max-message-size, protocol-version negotiation, the typed error model, and supervision hooks. OS-local transport (Unix domain socket / Windows named pipe) is the only transport; there is no loopback fallback.
- **Spec-024 daemon-side bind-time substrate** — `packages/runtime-daemon/src/bootstrap/secure-defaults.ts` implementing `SecureDefaults.load` + `effectiveSettings` + fail-closed enforcement, with validation scope limited to the OS-local socket or named pipe the partial exposes. Honors §Invariants I-006-1 (load-before-bind), I-006-2 (fail-closed), and I-006-5 (validation surface widens with bind surface) at the partial's bind surface; Plan-006-remainder extends the validation surface to the first-run-key, update and backup settings (the daemon binds no TCP port for clients).
- **The three `session.*` handlers Plan-001 needs** — typed handlers for `SessionCreate`, `SessionRead`, `SessionSubscribe` (the Plan-001 vertical-slice contracts). They do not close the `session.*` namespace: every other `session.*` method registers against the same registry from the plan that owns it, in the change that builds it (CP-006-3), among them [Plan-025](./025-mcp-server-configuration-and-governance.md)'s `session.mcpServerList`, `session.mcpServerUpdate` and `session.mcpResourceList`. No `run.*`, `repo.*`, `artifact.*`, `settings.*`, or `daemon.*` namespaces in this window.
- **SDK Zod layer (per [Spec-006 §Wire Format](../specs/006-local-ipc-and-daemon-control.md#wire-format))** — the typed wrapper in `packages/client-sdk/` exposing the daemon transport for `sessionClient`. Following the MCP TypeScript SDK pattern.

### Plan-006-Remainder (other namespaces + supervision + Spec-024)

Lands beside Plan-004 (runtime bindings) and Plan-005 (event taxonomy) — all three are gated only on the partial's completion. Scope:

- The JSON-RPC method namespaces extending the substrate's namespace registry — `run.*`, `repo.*`, `artifact.*`, `settings.*`, `daemon.*`, `driver.*`, `event.*`, `preview.*`, `browser.*`. Of these, **Plan-006-remainder OWNS `daemon.*`** (supervision verbs per [Spec-006 §Interfaces And Contracts](../specs/006-local-ipc-and-daemon-control.md#interfaces-and-contracts)) and **`settings.*`** (effective-settings read-projection per I-006-3); `driver.*` is owned by [Plan-004](./004-provider-driver-contract-and-capabilities.md) Phase 4 (the client-facing verbs CP-006-6 (a) lists, `driver.subscribeEvents` among them; the session/run lifecycle ops are daemon-internal per Plan-004 §Phase 4 decision #2); `event.*` is owned by [Plan-005](./005-session-event-taxonomy-and-audit-log.md) Phase 4 (T4.7's read/replay trio — the canonical member list lives at Plan-005 CP-005-4); `run.*` / `repo.*` / `artifact.*` are owned by their respective downstream plans (Plan-003 / Plan-007 / Plan-012) and land with the consuming plan per the `presence.*` precedent. **`preview.*` and `browser.*` are registered here** (CP-006-18); everything that answers on them, with the daemon dependencies it needs, is [Plan-021](./021-desktop-app-and-renderer.md) T-021r-9-2's. Registration boundaries declared in CP-006-6 (`driver.*`), CP-006-7 (`event.*`) and CP-006-18 (the two page-host roots) below.
- The Spec-024 secure-defaults bootstrap surface owned by Plan-006 widens in the remainder to the first-run-key, update and backup settings (the daemon binds no TCP port for clients) — `first-run-keys.ts` (row 3 — the machine's identity key generated at first start; the credential store is Plan-020's), `update-notify.ts` (row 7a — periodic poller, not a bind-time gate), and the CLI `self-update` command (row 7b — out-of-process). The partial already ships the bind-time `SecureDefaults` validation surface (`secure-defaults.ts`) scoped to the OS-local socket or named pipe it exposes; §Invariants I-006-1 / I-006-2 / I-006-5 hold at every execution window per the validation-surface-widens-with-bind-surface rule.
- The CLI delivery track (`apps/cli/`) and the main process's **transport-supervision** consumer, its daemon-status projector, + the renderer's connection line (the boot card before the service first answers, the composer's working line after it). The transport-supervision projector watches the main process's own link to the service (the socket closing; `daemon.ping` after 5 s with no frame, the link counted dead after 20 s with none) and projects `daemon.status.*` events, which reach the renderer on the `daemon.status` bridge topic [Plan-028](./028-remote-control.md) Phase 1 builds; the gateway's `SupervisionHooks` are in-process callbacks inside the service, which feed the daemon's own `daemon.status.read` and never leave it. Concern-disjoint from Plan-021's service supervisor in the main process (which owns starting the service as the person's own background service, never as the app's child, + [Plan-021 §Implementation Steps](./021-desktop-app-and-renderer.md#implementation-steps) backoff ladder `100ms/300ms/1s/3s/10s`) per the concern-split resolution; see CP-006-11 below.
- **The service's own control surface** (Phase R1): `daemon.flush` and the `daemon.ping` answer, retention with the diagnostic-log expiry, configuration, the machine's settings file, the keep-awake hold, backups and crash reports, beside the status, stop and restart verbs. The command line's install, sign-in, update and data verbs are Phase R3's.
- **The service on WSL 2** (Phase R4): on a Windows computer whose Claude Code and Codex live in a WSL 2 distribution, the service runs there as the daemon plus the service's Windows half, a small native Windows program; on native Windows the same program runs as the daemon's child, so every Windows-only job has one implementation. [ADR-041](../decisions/041-the-service-on-wsl-2.md) records the decision.

### Substrate-vs-Namespace Decomposition Rule (Methodology)

**Rule:** Cross-cutting infrastructure plans MAY be split into an earlier substrate-deliverable + a later namespace-deliverable when (a) the substrate is single-owned and load-bearing for an earlier consumer, AND (b) the namespaces have natural cohesion with their owning plans. Substrate ships first; namespaces ship with their owning plans.

**Rationale.** Spec-006 conflates two concerns — the cross-cutting _transport substrate_ (correctly single-owned by Plan-006: only one set of framing, version-negotiation, and error semantics may exist in the system) and the domain-specific _method namespaces_ (which cohere with their owning plans: a method belongs with the plan that owns its domain — `session.create` with session core, `session.mcpServerList` with MCP governance, `run.*` with run orchestration, etc.). Without a carve-out, Plan-001 Phase 5 either (a) inherits an undeclared forward dependency on Plan-006's remainder, breaking build-order discipline, or (b) duplicates the wire substrate in Plan-001, breaking single-ownership of the transport layer. The carve-out preserves both invariants by isolating the substrate beside the consumer while leaving namespace implementations at their natural plan boundaries.

**Applicability.** Apply this pattern when the Inter-Plan Dependency Graph would otherwise need an undeclared forward dependency from an earlier plan to a later infrastructure plan. The pattern is _not_ a license to fragment well-scoped plans for parallelism reasons — both criteria (a) and (b) must hold. **Precedent:** the shipped `packages/crypto-paseto/` workspace package is a sibling instance — a single substrate package carved out ahead of the later plan that consumes it, so an earlier consumer needs no forward dependency. That carve-out and Plan-006 share the same substrate-vs-namespace decomposition shape.

**Trade-off accepted.** Plan-006 readers must navigate two windows instead of a single linear sequence; the cross-link from cross-plan-dependencies.md keeps the canonical build order discoverable. This cost is paid once at plan-authoring time; the alternative (silent forward dependency) imposes a recurring cost on every PR-execution agent.

## Goal

Implement the typed local daemon control surface shared by the desktop renderer and CLI, including daemon supervision and protocol negotiation.

## Scope

This plan covers OS-local IPC transport, version negotiation, daemon lifecycle commands, shared client SDK implementation, and the first-class CLI delivery path.

## Non-Goals

- Relay or remote transport
- Provider-driver internal transports
- Browser-only local client support

## Invariants

The following invariants are **load-bearing** and MUST be preserved across all Plan-006 PRs and downstream extensions. They are restated here at top level so that consumers of Plan-006's substrate (Plan-001 Phase 5, the `presence.*` handlers, Plan-006-remainder namespace handlers) can find them without reading the §Secure Defaults table first.

### I-006-1 — Load-before-bind

`SecureDefaults.load(config)` MUST run **before** any daemon listener binds. Attempting to bind a listener before `SecureDefaults.load` completes is a programmer error and MUST throw.

**Why load-bearing.** Bootstrap-order inversion silently exposes a pre-validation listener to network input. Test must assert load-bearing throw on out-of-order bind attempts.

### I-006-2 — Fail-closed on invalid security settings

`SecureDefaults.load` MUST fail closed on an invalid security setting — there is no "best-effort partial start" path. A downgrade the person sets through a row's override starts, and shows as its own `WARNING:` line on the start banner (Spec-024 row 10). In the partial, the daemon MUST also refuse settings keys outside the partial's validation scope (e.g., first-run-keys policy) with an `unknown_setting` validation error — silent drop is forbidden.

**Why load-bearing.** Best-effort starts mask configuration drift; the override surface is the only sanctioned path for downgrades. Verification: negative-path tests on remainder-scope settings keys in the partial.

### I-006-3 — `effectiveSettings` exposes only non-secret typed values

`SecureDefaults.effectiveSettings` exposes only non-secret typed values (the local IPC path, override flags). Raw keys and secrets are NEVER exposed through this view.

**Why load-bearing.** `effectiveSettings` is consumed by every downstream daemon module (gateway, banner, supervision); a secret leaking through this surface is a one-way security regression.

### I-006-5 — Validation surface widens with bind surface

These invariants apply to whatever bind paths the daemon exposes at the current execution window. Plan-006-partial ships a minimal bind surface (the OS-local socket or named pipe only) and a `SecureDefaults` validation surface scoped accordingly; Plan-006-remainder adds the first-run-key, update and backup settings (the daemon binds no TCP port for clients). The invariants hold at every window — the validation surface widens as the bind surface widens.

**Why load-bearing.** A static validation surface would either over-validate in the partial (refusing remainder-scope keys silently) or under-validate in the remainder (allowing settings outside the bind paths). Per-window scoping is the only way to keep the invariants honest.

### I-006-6 — Namespace registry rejects duplicate method-name registration

The method-namespace registry MUST reject any second `register(method,...)` call with an already-registered method name at registration time (not at dispatch time). The error is a programmer error and surfaces synchronously during daemon bootstrap.

**Why load-bearing.** A registry that silently accepts duplicates exposes a non-deterministic dispatch surface — the second handler may shadow the first, the first may shadow the second, or both may run. Every consumer of the registry (Phase 3 `session.*`, the `presence.*` handlers, Plan-006-remainder's `settings.*` / `daemon.*`, and the downstream-owned `run.*` / `repo.*` / `artifact.*`) depends on this for boot-time correctness.

### I-006-7 — Schema validation runs before handler dispatch

Every JSON-RPC request MUST Zod-parse against the registered schema before the handler body executes. Validation failures map to JSON-RPC `-32602 Invalid Params` per [error-contracts.md §JSON-RPC Wire Mapping](../architecture/contracts/error-contracts.md#json-rpc-wire-mapping); the handler is NEVER invoked.

**Why load-bearing.** Handlers must trust their typed input. A handler that runs on a malformed payload either crashes (degrades to internal-error responses) or produces garbage downstream (corrupts SQLite state, emits invalid events). Schema-validates-before-dispatch is the only invariant that pushes the validation responsibility off the handler author.

### I-006-8 — Handler-thrown errors map to JSON-RPC error codes with sanitized payloads

Errors thrown from handler bodies MUST map to JSON-RPC error codes per [error-contracts.md §JSON-RPC Wire Mapping](../architecture/contracts/error-contracts.md#json-rpc-wire-mapping) — the JSON-RPC §5.1 numeric `code` carries the spec discriminator and the registered project dotted-namespace identifier (e.g. `session.not_found`, `auth.token_expired`) rides as `data.type` in the two-layer envelope; unregistered exceptions collapse to JSON-RPC `-32603 InternalError` with sanitized message. Stack traces and secrets MUST never leak through the response.

**Why load-bearing.** Handler-thrown errors are the primary observability + security surface. Stack-trace leakage is a one-way information regression; collapsing all errors to `-32603` without preserving registered domain codes destroys the typed error envelope downstream consumers depend on.

### I-006-9 — Method names conform to the canonical format declared in api-payload-contracts.md

The registry MUST mechanically validate method-name format at `register(method,...)` call time, refusing names that don't match the canonical convention. The canonical format is `dotted-camelCase` (every segment starts lowercase and may include uppercase letters internally, the first segment included — e.g. `event.readAfterCursor`, `driver.listCapabilities`, `settings.effectiveRead`, `providerAccount.list`) per [api-payload-contracts.md §Plan-006-Partial — Local IPC Daemon Control](../architecture/contracts/api-payload-contracts.md#plan-006-partial--local-ipc-daemon-control). Implementations MUST evaluate `method` against the regex `/^[a-z][a-zA-Z0-9]*(\.[a-z][a-zA-Z0-9]*)+$/` and throw on mismatch. The regex permits camelCase identifiers in every segment (each segment starts lowercase but may include uppercase internally) while still rejecting leading-uppercase, leading-digit, separator-other-than-dot, or non-ASCII forms.

**Why load-bearing.** Without format enforcement, downstream plans may register `session.create`, `session/create`, `Session.create`, and `sessionCreate` simultaneously. The registry would treat these as distinct methods (correctly per the literal string) but the SDK consumer would have no way to choose. Format enforcement at registration time is the only mechanical guarantee. The dotted-camelCase convention (not snake_case) matches the JSON-RPC method naming used by LSP and MCP, which keeps the wire-format method names symmetric with the TypeScript handler/SDK identifiers (`session.create` → `sessionClient.create(...)`, `event.readAfterCursor` → `eventClient.readAfterCursor(...)`).

### I-006-10 — Subscribe-init response precedes the first notification frame

For any subscription-establishing method (e.g. `session.subscribe`), the daemon MUST emit the JSON-RPC response carrying the assigned `subscriptionId` BEFORE the first `$/subscription/notify` frame referencing that id. Daemon enforcement uses `setImmediate(...)` (or equivalent macrotask deferral) to defer initial-replay emission until after the response envelope is queued on the transport. The paired SDK enforcement is synchronous dispatcher-entry registration inside `#handleResponse` (`packages/client-sdk/src/transport/jsonRpcClient.ts`), installed BEFORE the in-flight request promise resolves so that subsequent coalesced inbound frames within the same transport read can route to a known `subscriptionId`. Both sides are load-bearing; the invariant covers both.

**Why load-bearing.** Without daemon-side ordering enforcement, the SDK has no way to learn the `subscriptionId` before the first notify arrives — even synchronous SDK-side registration cannot install a dispatcher entry for an unknown id. Without SDK-side synchronous registration, the daemon's correct response-before-notify ordering is still insufficient under normal wire frame coalescing (a single transport read containing both the response and the first notify): the SDK's `.then`-deferred microtask would not run until after the next inbound frame is dispatched, dropping the first notification as an unknown-subscription. The pair is the contract; either side alone leaks first-notification reliability.

### I-006-11 — `LocalSubscriptionProducer<T>.onCancel` fires across all externally-imposed cancel paths

For any `LocalSubscriptionProducer<T>` instance (the producer-side primitive at `packages/contracts/src/jsonrpc-streaming.ts`), registered `onCancel` handlers MUST fire across all three externally-imposed cancel paths: (a) `cancel` server-initiated unilateral cancel, (b) `cleanupTransport` transport-disconnect bulk cleanup, (c) CLIENT-initiated `$/subscription/cancel` via the registered cancel-method handler. `complete` (natural producer-driven termination) does NOT fire handlers.

Eight semantic sub-invariants are load-bearing (canonical statement: `packages/contracts/src/jsonrpc-streaming.ts#LocalSubscriptionProducer`, the onCancel semantics block): (1) registration-after-cancel fires synchronously, (2) registration-after-complete is silently dropped, (3) multi-handler firing in registration order, (4) per-handler error isolation, (5) two-layer try/catch in bulk cleanup, (6) remove-from-maps-then-fire ordering so re-entrant handlers observe post-cancel state, (7) mirrors AbortSignal-style semantics, (8) idempotent registration.

**Why load-bearing.** The Plan-006-substrate namespace handlers (`settings.*` / `daemon.*` from Plan-006-remainder; `run.*` / `repo.*` / `artifact.*` from their downstream owning plans) and the `presence.*` handlers register subscriptions through the same `LocalSubscriptionProducer<T>` shape and must close upstream-watcher leaks the same way `session-subscribe.ts` does (via `sub.onCancel(unsubscribe)`). Without this invariant pinned at plan-body level, every future handler author re-discovers the re-entrant failure mode (registered onCancel handlers firing from inside the upstream's `onEvent` call stack — re-entrant unsubscribe). The consumer-side precondition is named on `SessionSubscribeDeps.subscribeToSession`'s returned function: the unsubscribe callback must tolerate snapshot-during-emit / queued-removal.

### I-006-12 — Daemon refuses self-swap while IPC has active clients

The daemon MUST refuse to replace its own running binary while the local-IPC gateway has active client connections. The notify-by-default poller (`update-notify.ts`, Phase R2) MUST NOT download + swap even behind a flag — only the CLI-invoked `sidekicks self-update` (out-of-process, daemon-restart afterward) is sanctioned to perform the swap.

**Why load-bearing.** [Spec-024 §Required Behavior](../specs/024-self-host-secure-defaults.md#required-behavior) row 7a verbatim says "The daemon MUST NOT self-swap its binary while IPC is live." [Spec-024 §Pitfalls To Avoid](../specs/024-self-host-secure-defaults.md#pitfalls-to-avoid) reinforces: "row 7a forbids self-swap while IPC is live. Plan-006 MUST NOT implement notify-by-default as 'download + swap' even behind a flag." This is a runtime-state property — at startup, IPC has zero clients, so I-006-1 (load-before-bind) does NOT subsume this. I-006-12 is the live-state property: even AFTER startup, even AFTER all bootstrap invariants have been satisfied, an attempted self-swap is a programmer error and MUST throw / refuse. The invariant is symmetric to I-006-1 in spirit (one guards startup-order; the other guards runtime-state).

### I-006-13 — CLI workspace package is import-isolated

`apps/cli/src/**` may import only from `@ai-sidekicks/contracts`, `@ai-sidekicks/client-sdk`, the CLI library (`clipanion@4.0.0-rc.4` per T-006r-3-1 scaffold pin), and Node built-ins. Direct imports of `@ai-sidekicks/runtime-daemon`, `@ai-sidekicks/control-plane`, or any `apps/desktop/**` path are forbidden.

**Why load-bearing.** The CLI is the first delivery track per [Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior) and ADR-009 — it MUST consume the daemon strictly through the JSON-RPC IPC contract, not by reaching into daemon internals. If the CLI imported daemon code directly, the wire contract would be silently bypassable and the SDK / control-plane / desktop / CLI clients would diverge. Enforcement is mechanical: `apps/cli/eslint.config.mjs` declares the `no-restricted-imports` rule mirroring Plan-021's renderer partial-substrate enforcement; CI build fails on violation.

### I-006-14 — CLI exit codes are a closed deterministic mapping

Every CLI exit code is produced by the single canonical mapper T-006r-3-3 authors, from **exactly two typed failure sources**. Source (a), **daemon-originated**: a `JsonRpcErrorCode` carried on a JSON-RPC error envelope, mapped over the `docs/architecture/contracts/error-contracts.md §Numeric Code Space (per JSON-RPC 2.0 §5.1)` code set. Source (b), **CLI-local**: a failure raised inside the CLI process with no envelope to carry a code — a pre-resolution parse refusal, a static-`schema` validation failure, and an error escaping a command body — normalized at the T-006r-3-2 boundaries into one of two local-failure kinds, `usage` or `software`, before it reaches the mapper. Both sources enter that one mapper; neither bypasses it. No ad-hoc exit codes (e.g., `process.exit(1)` for an unmapped error) are permitted, and neither is a second mapping table.

Exit codes come from these two sources only: a CLI-local failure has no wire code to map, so without a typed local kind the implementation would have to invent an exit code at the throw site, which is exactly the ad-hoc source this invariant forbids. Classifying at the boundary and mapping centrally keeps every exit code attributable to one table. The mapper's own drift guard sits **inside** those two sources rather than beside them: `UnmappedExitCodeError` — raised by the T-006r-3-3 table when a daemon-originated code carries no assignment — is thrown at CLI exit-translation time and is therefore itself a CLI-local failure of kind `software`. Each T-006r-3-2 boundary wraps its own mapper call, so the throw is caught where it is raised, the process exits the mapped **70**, and the guard neither recurses into the mapper nor escapes to the pinned build's stdout-writing outer catch. Drift is loud in the test suite and deterministic in production, and adds no exit-code source of its own.

**Why load-bearing.** The CLI composes into scripts and CI pipelines; non-deterministic exit codes break automation. A closed mapping makes the failure semantic part of the wire contract: `transport.unavailable` → exit 69, `session.not_found` → exit 78, etc. (every code's assignment is listed at R3-T7, the exit-code totality test in T-006r-3-15 slice a).

### I-006-15 — Daemon-lifecycle CLI commands ack `DaemonHelloAck` before reporting success

`sidekicks daemon start` and `sidekicks daemon restart` MUST NOT exit 0 on TCP-accept alone; they MUST wait for `DaemonHelloAck` within a deadline (default 10s, override `--timeout <ms>`) before reporting success.

**Why load-bearing.** A daemon that accepted the connection but failed to complete the handshake (e.g., protocol-version mismatch emitting `invalid_protocol_version` per the `dispatchFrame` gate in `packages/runtime-daemon/src/ipc/local-ipc-gateway.ts#LocalIpcGateway`) is not actually usable; reporting success here would mask the failure. A person's scripts rely on the `daemon start` exit status to gate what they run next.

### I-006-17 — Supervision events are single-emit per transport boundary

For each link the main process opens to the service, the Phase R3 supervision consumer (T-006r-3-7, T-006r-3-8) emits exactly one connect event followed by at most one error (terminal) and exactly one link loss (terminal). Duplicate emissions for the same link boundary indicate a state-machine bug. The daemon's gateway keeps the same rule for its own `SupervisionHooks` per transport (T-006p-2-1).

**Why load-bearing.** The renderer's connection line (T-006r-3-11) and the Plan-021 process supervisor (per CP-006-11) both subscribe to the projected `daemon.status.*` stream; double-emit would race the state machine and surface inconsistent UI / restart-counter increments. Enforcement: the state machine's tests assert XState v5 guards explicitly preventing duplicate emissions per link.

### I-006-18 — Supervision-status state machine is fail-closed on unknown reasons

If the Phase R3 supervision consumer meets a link-loss reason outside the set the main process's projector defines — e.g., a close cause the client transport adds later — the state machine MUST default to the `degraded` state, never `connected`. The renderer (T-006r-3-11) draws an unknown reason exactly as it draws `degraded`: the working line's `Connection lost` and `Not connected.`, with `Retry`, and never words of its own for the reason.

**Why load-bearing.** Fail-closed on unknown enum values prevents new-future-value-introduces-a-bypass attacks. The forward-compat surface is real: if a later change adds a disconnect reason to the enum, this invariant ensures older CLI / desktop binaries degrade safely rather than rendering "connected" against an unrecognized signal.

### I-006-19 — Mutating-op gate for renderer-issued `daemon.restart`

A `daemon.restart` call originating from the renderer (Runtime's `Restart`) MUST be gated by a server-side check that the calling session has a valid `DaemonHelloAck` (per [Spec-006 §Fallback Behavior](../specs/006-local-ipc-and-daemon-control.md#fallback-behavior): mutating operations are blocked until versions are compatible). The renderer disables no control while the link is down (T-006r-3-11), so this server-side check is the only gate.

**Why load-bearing.** Trust-boundary discipline per [Spec-021 §Trust Stance](../specs/021-desktop-app-and-renderer.md#trust-stance) — the renderer is NOT a direct daemon client. Even though Plan-021's `no-restricted-imports` ESLint rule blocks the renderer from binding a JSON-RPC client, the IPC bridge handler is the only channel and MUST re-validate every mutating call against the daemon's typed-error envelope. Server-side enforcement at the substrate mutating-op gate (the `dispatchFrame` pre-dispatch gate in `packages/runtime-daemon/src/ipc/local-ipc-gateway.ts#LocalIpcGateway`) is the authoritative check; the renderer-facing checkpoint on the `daemon.status` bridge topic, which [Plan-028](./028-remote-control.md) Phase 1 builds, refuses the renderer-issued call with an actionable error envelope if the daemon-status state machine is not `connected`.

### I-006-20 — CLI process streams are role-separated

Every byte `apps/cli/` writes goes to the stream its role assigns. **stdout carries result payload only** — the human-readable or `--json` rendering a caller pipes or parses, plus the output of an explicitly requested `--help` / `--version`, whose payload IS that text. **stderr carries every diagnostic** — banners, progress notices, the refusal for an unparseable or unknown invocation, the usage text accompanying such a refusal, and every error message. A command that **fails to produce its result** writes nothing to stdout: a parse refusal, an unknown invocation, and an error escaping a command body each leave stdout byte-empty. A non-zero exit is not that condition. A command that successfully renders a result describing a negative or unhealthy subject writes that result to stdout and reports the subject's state through its exit code — the discriminator is result-versus-diagnostic, never zero-versus-non-zero. `daemon status --json` against a `degraded` daemon is the named instance: it emits its canonical JSON payload on stdout and exits `1` (T-006r-3-5), and the same shape recurs across the workspace wherever a command reports a negative outcome it successfully computed.

**Why load-bearing.** `daemon status --json` and `settings effective-read --json` (T-006r-3-5, T-006r-3-6) are machine-readable contracts. A failure that writes diagnostic text onto the same stream corrupts the caller's parse while I-006-14's exit code reports failure — the two signals disagree, and in a shell pipeline the corrupted parse is what the next stage consumes. The pinned parser does not supply this separation: `clipanion@4.0.0-rc.4` routes its parse refusals AND any error escaping a command body to the run context's **stdout**, and renders the escaped error with a full stack trace under a hardcoded exit `1` — a stack-trace leak onto the person's terminal and a total bypass of the I-006-14 mapping. That is what makes T-006r-3-2's two-leg wrapper mandatory rather than stylistic. Enforcement is structural first and lint second, and that ordering is itself the claim: no lint rule set closes this hole, so the guarantee does not rest on one. The **structural** layer is that every command body is reached through the single project base command class T-006r-3-2 authors in `apps/cli/src/base-command.ts` and writes its result through `this.context.stdout` and its diagnostics through `this.context.stderr` — the injected streams, never the process's own — so error-to-stream routing has exactly one implementation, and R3-T8b asserts against those injected streams rather than against the process. The **lint** layer is defense in depth over the spellings an author reaches for by habit, and is deliberately not claimed exhaustive: `apps/cli/eslint.config.mjs` carries `no-console` over `apps/cli/src/**` — a `console.*` call inside a command body writes to the process's real stdout instead of the injected context stream, so an assertion against the injected stream passes green on absent output — an `importNames: ['stdout', 'stderr']` entry against `node:process` added to the **same `no-restricted-imports` invocation** that carries I-006-13's import allow-list, at the `apps/cli/src/**` scope I-006-13 already states — catching the `import { stdout } from 'node:process'` spelling that writes no `process` member expression and that I-006-13's Node-built-ins allowance otherwise admits — and a `no-restricted-properties` ban on `process.stdout` / `process.stderr` member access, the one rule scoped to `apps/cli/src/commands/**`, which `no-console` does not reach. Sharing I-006-13's single invocation is mandatory, not tidiness: ESLint flat config **replaces** a rule's options at the last matching config object rather than merging them, so a second `no-restricted-imports` block scoped to `commands/**` would silently drop I-006-13's import allow-list for exactly the command files that most need it. Aliasing, a `globalThis` hop, and dynamic member access defeat all three, which is why the base class rather than the linter is what makes a bypass a correctness question instead of an open one. Only the property ban is `commands/`-scoped, and it stops there by path rather than by disabling comment: `apps/cli/src/main.ts` builds the run context out of the real process streams (T-006r-3-2) and is the one file that must name them. It needs no exemption from the import entry — a default `import process from 'node:process'` reaches `process.stdout` without naming a restricted import. The scope is the whole workspace, not this plan's own commands: **every** plan that authors a command file into `apps/cli/src/commands/` imports and extends that same base class, an obligation carried by CP-006-15 and restated on each consuming ownership row rather than left to this prose — today [Plan-014](./014-multi-agent-orchestration.md), [Plan-015](./015-workflow-authoring-and-execution.md), [Plan-025](./025-mcp-server-configuration-and-governance.md), [Plan-026](./026-provider-accounts-and-credential-homes.md), and [Plan-027](./027-agent-definitions-and-peer-invocation.md), each carrying a §2 package-path ownership row — the same workspace-wide binding I-006-13 already places on those plans. Verified by R3-T8b (T-006r-3-15 slice a).

### I-006-21 — The dispatch context carries the calling connection's device

Every handler the substrate dispatches receives the calling connection's device on its `HandlerContext`, resolved by the gateway from the transport that carried the request and by nothing else, never from a request body field. A write records that device. Nothing checks ownership: no handler authorizes a read or a write by a person's identity. The device is a dispatch-context fact and never a wire field, so no request schema gains a member for it and a caller-supplied one is never trusted (the informational-body-fields rule).

**Why load-bearing.** `HandlerContext` shipped with `transportId` and nothing else. Resolving the device once, in the component that already holds the transport, gives every namespace that records a write's device the same value, rather than each resolving its own (CP-006-17).

### I-006-22 — A request `id` is bounded at the request boundary, and a refusal never echoes an unbounded one

A JSON-RPC request whose `id` exceeds `JSON_RPC_ID_MAX_BYTES` once JSON-encoded is refused as `-32600 Invalid Request` before any handler runs, and **every** error frame the gateway emits for that request carries `id: null` rather than the offending value. The bound is enforced at the request boundary because JSON-RPC requires a response to echo the request's `id`: it is the one response member no response schema chooses, so no reply can be bounded by bounding replies. The measure is taken on the JSON-encoded form, so escaping is covered and one rule reads identically across the string, number, and null id forms the envelope admits. The refusal fails the **request**; the connection stays open.

**Why load-bearing.** The framer's message-size limit is absolute in both directions, and an oversized **response** cannot carry its own error — the reply that would have reported the fault is the reply that will not encode — so the send path drops the connection instead. Without this bound, an id large enough to displace a whole reply is contract-valid, and every answer to that request, including its error, becomes unencodable: a dropped session reachable from well-formed input alone. Enforcement is two-sited, and both sites are required rather than belt-and-braces: the envelope gate refuses the request, and the id-extraction helper — through which the `jsonrpc` and `method` gates build their error frames, and which answers _before_ the id gate — falls back to Null, without which the one frame guaranteed to be small would be the very one carrying the oversized echo. Verified by the `local-ipc-gateway` gateway suite's oversized-id group, which asserts the refusal shape, the null echo on both gate orders, and — as its negative control — that an id one byte under the bound is accepted and echoed.

Two further substrate touches ride this same obligation, both authored by that plan's Phase 1 — one of them new wire behavior on this plan's own framer, the other pure extraction. **(a) The request-id bound (new behavior, I-006-22).** `JSON_RPC_ID_MAX_BYTES` is declared beside the frame cap in `packages/contracts/src/jsonrpc.ts`, re-exported here, and enforced in `local-ipc-gateway.ts` at two sites — the pre-dispatch refusal in `#dispatchFrame`, and `extractIdSafely`'s drop-to-Null, which covers the earlier envelope gates that answer before that refusal runs and would otherwise echo an oversized id into the one frame guaranteed to be small. [Spec-006 §Wire Format](../specs/006-local-ipc-and-daemon-control.md#wire-format) and `§Acceptance Criteria` carry it, and **I-006-22** on this plan states the guarantee. The invariant is minted here rather than on the consuming plan because the guarantee is the substrate's — every namespace registered against this registry inherits it, and Plan-011 is only the first caller whose replies could not otherwise be bounded. **(b) The subscribe-init ordering barrier (extraction).** `packages/runtime-daemon/src/ipc/subscription-ack-barrier.ts` holds the buffering `registerSessionSubscribe` had inline, extracted verbatim. It changes no behavior of `session.subscribe` — the diagnostics it logs are byte-identical and I-006-3-T6 exercises the extracted module unmodified — and it is what makes I-006-10 hold for `session.subscribe`.

### CP-006-17 — The calling connection's device on `HandlerContext`, owed to every namespace that records a write's device

Phase 2B (T-006p-2B-1) widens `HandlerContext` with the calling connection's device and has the gateway stamp it at dispatch, per I-006-21. The contract surface is (a) the additive optional member on the `HandlerContext` interface in `packages/contracts/src/jsonrpc-registry.ts` — additive per that interface's own stated evolution commitment, so no existing handler or test changes; and (b) the gateway-side resolution from the transport that carried the request, never from a request body.

**Why bidirectional.** Every plan whose writes record the device they came from (an approval's answering device among them, which `Answered on <device>` reads) reads this member rather than resolving the device itself. A consuming plan may register its own reciprocal later without this obligation changing, the asymmetry CP-006-15 already records.

### CP-006-18 — The daemon's page-host namespaces `preview.*` and `browser.*`, owed to [Plan-021](./021-desktop-app-and-renderer.md) CP-021-11

Plan-006-remainder owns the substrate's namespace registry, and the Preview pane's two method roots are **daemon** JSON-RPC roots rather than main-process ones. There are two page hosts and one endpoint — the desktop's own native page view, and the daemon's headless browser where no desktop is open on that machine — and one resolver in the daemon returns the active one, so nothing above the roots branches on which host is live ([ADR-036](../decisions/036-embedded-browser-for-preview.md)). Putting the verbs anywhere but the daemon would leave the no-desktop case with no surface at all. The contract surface is the registration of both roots in the substrate's namespace registry, under the canonical method-name strings of the [Page-Host Method Registry](../architecture/contracts/api-payload-contracts.md#page-host-method-registry), which conform to I-006-9's dotted-camelCase format unchanged. Everything that answers on them — the endpoint resolver, the headless page host that stands in where no desktop runs, the agent's browser tool server hosted in the daemon's own process, and the daemon dependencies those pieces need — is one build unit, [Plan-021](./021-desktop-app-and-renderer.md) T-021r-9-2. Plan-021 authors the renderer surface, the Electron page host and the preload bridge namespace that shares the word `browser` with this root and is a different surface — the bridge positions and captures a page, these roots manage pages, site data and the node-wide switches.

**Why bidirectional.** Plan-021's Preview pane and Settings › Browser read these roots, so they have a named registration rather than an unassigned obligation. This plan registers the roots and builds nothing behind them.

**Class, not a single consumer.** A later surface that drives the same page — a linked device watching the live picture — reads the same roots through the same resolver and adds no second registration; this row names Plan-021 because it is the first consumer.

## Secure Defaults (Spec-024 daemon-side rows)

Plan-006 owns the daemon-side enforcement of [Spec-024 §Required Behavior](../specs/024-self-host-secure-defaults.md#required-behavior) rows 3, 4, 7a, 7b, and 10. The enforcement layer is a typed `SecureDefaults` configuration module that runs in the daemon bootstrap path before any listener starts, validates overrides explicitly, fails closed on invalid settings, shows each active override on the start banner, and exposes only typed non-secret effective settings to downstream daemon modules.

| Spec-024 Row | Daemon-Side Behavior | `SecureDefaults` Enforcement Point |
| --- | --- | --- |
| 3 — Auto-generated strong secrets on first run (daemon keys) | At the service's first start, the machine's identity key generated and kept through `DaemonKeyStore` as its own item in the operating system's credential store ([Spec-020 §Daemon Secrets](../specs/020-data-retention-and-gdpr.md#daemon-secrets)), never kept as a key file; nothing in the daemon's database is encrypted by the app; the first-run sentinel is the relay's ([Plan-028](./028-remote-control.md) Phase 8), not the daemon's | `first-run-keys.ts` |
| 4 — Loopback bind by default (daemon) | The daemon's local IPC is a Unix domain socket or a named pipe with no network address, and it has no bind setting of its own | `secure-defaults.ts` |
| 7a — Auto-update notify-by-default (daemon) | Daemon polls GitHub Releases (or a feed the person configures) on a cadence owned by this plan; newer release → CLI invocation prompt + first-run-banner line + `security.update.available` log event; daemon MUST NOT self-swap while IPC is live | `update-notify.ts` |
| 7b — Opt-in self-update (CLI) | `sidekicks self-update` fetches the release's manifest and the target binary and checks the binary against the SHA-256 the manifest lists for its platform, and nothing more; waits for running work to finish, naming it and never stopping it, then swaps the service's program atomically and restarts it, with platform-specific rules; updates the service alone | `apps/cli/src/commands/self-update.ts` |
| 10 — Loud first-run banner (daemon content) | On every daemon process start, single-screen stdout banner enumerates: effective bind addresses, backup state (off, or the folder and the last run), update channel + mode, each active override as its own `WARNING:` line, in the format Spec-024 row 10 sets; content provided by `SecureDefaults.effectiveSettings` view; `BANNER_FORMAT=json` emits same payload as single JSON line | `secure-defaults.ts` exposes the content contract; Plan-006 prints the banner (CP-006-9) |

**Invariants.** See top-level §Invariants — I-006-1 (load-before-bind), I-006-2 (fail-closed), I-006-3 (`effectiveSettings` non-secret only), I-006-5 (validation surface widens with bind surface). The invariants govern this entire §Secure Defaults table; the top-level placement makes them discoverable to consumers (Plan-001 Phase 5, the `presence.*` handlers) without requiring them to read this section first.

**Override coverage.** Every row with an override path listed in [Spec-024 §Fallback Behavior](../specs/024-self-host-secure-defaults.md#fallback-behavior) shows its active override as its own `WARNING:` line on the start banner (row 10), on every start.

### Phase R4 — The service on WSL 2

**Goal:** On a Windows computer whose Claude Code and Codex live in a WSL 2 distribution, the background service runs in that distribution as the daemon plus the service's Windows half, and every Windows-only job has one implementation, the Windows half, on native Windows too, where it runs as the daemon's child. The behavior is [Spec-006 §The service on a Windows computer](../specs/006-local-ipc-and-daemon-control.md#the-service-on-a-windows-computer); the decision and what was weighed against it are [ADR-041](../decisions/041-the-service-on-wsl-2.md).

**When:** Phase 10, Other platforms ([cross-plan-dependencies.md §Platform order](../architecture/cross-plan-dependencies.md#platform-order)).

**Precondition:** Phase R3 merged — R4 extends R3's `daemon install`, `uninstall`, `start` and `status`, and runs the same CLI on both sides. Phase R1 merged — the Windows half serves R1's keep-awake hold and carries its verbs. Plan-022 Phase 4 merged — the release's cross-compile and Windows signing ([Plan-022 §Phase 4 — CI Cross-Compile Matrix + Signing Stages](./022-rust-pty-sidecar.md#phase-4--ci-cross-compile-matrix--signing-stages)) builds and signs `sidekicks-windows-half.exe`. The credential store's daemon side, [Plan-020](./020-data-retention-and-gdpr.md), consumes the Windows half's credential-store verbs T-006r-4-10 builds, so it follows this phase. Every probe in §Test And Verification Plan's Phase R4 table runs on a Windows machine before the first R4 PR opens; a probe's result that contradicts a task below changes the task before it is built.

- `packages/service-windows-half/` (CREATE) — the Windows half: the Rust crate and its binary `sidekicks-windows-half.exe`, x64 and arm64.
- The daemon's channel end, its `--windows-half-stdio` start, its `--take-in <from>` one-shot and the Windows arms of its jobs (EXTEND `packages/runtime-daemon/`).
- The client SDK's Windows pipe client (EXTEND `packages/client-sdk/`), used by the main process and the Windows CLI.
- The CLI's `daemon install --windows | --wsl <distro>`, `daemon move`, and `--while-signed-out` on a WSL computer (EXTEND `apps/cli/`).
- The main process's place list, move and cannot-start reading on its service supervisor, beside Plan-021's `daemon.requestUpdate()`.
- Tests: the in-phase tests named on each task; the probes are §Test And Verification Plan's.

#### Tasks

- **T-006r-4-1** (Files: `packages/service-windows-half/`) — The Windows half. A Rust crate on `tokio`, binary `sidekicks-windows-half.exe`, with three start roles: resident on a WSL computer, holding the daemon's `wsl.exe` (T-006r-4-6); `--daemon-child`, started by the native daemon as its child, serving the same pipe over the same channel; and `--desktop`, the logon task's instance while the signed-out task holds the service (T-006r-4-8). Its channel's control stream, opened first by the Windows half, carries its verbs both ways: `keystore.get`, `keystore.set`, `keystore.delete`, `banner.post`, `banner.withdraw`, `awake.hold`, `awake.release`, `wake.set`, `power.report`, `portOwner.read`, `portCarry.open {port, family} → {windowsPort}`, `portCarry.close {port}` and `status.report`, one object per job under the registry pattern. One-shot, the same code runs `keystore get | set | delete <entry>`, the secret on standard input and output, for the credential store while the service is stopped. It runs from `%LOCALAPPDATA%\ai-sidekicks\windows-half\<version>\`, which the main process fills at install and update, so an app update never replaces a running file; the new one takes over at the next service restart, and the folder before it stays. **Spec coverage:** Spec-006 §The service on a Windows computer (two processes on WSL); Spec-006 §Interfaces And Contracts (the Windows half's verbs and start arguments).
- **T-006r-4-2** (Files: the Windows half's pipe server; the client SDK's Windows pipe client; the Windows token writer) — One per-user named pipe, `\\.\pipe\ai-sidekicks-<user SID>`, on both kinds of Windows computer. **Server:** `CreateNamedPipeW` with an access list that grants the person alone, `PIPE_REJECT_REMOTE_CLIENTS`, and `FILE_FLAG_FIRST_PIPE_INSTANCE` on the first instance; `ERROR_ACCESS_DENIED` there means another program holds the name, so it refuses to serve, writes the reason to the status file, releases the mutex and exits nonzero. It checks each accepted client's process belongs to the person through `GetNamedPipeClientProcessId`. On native Windows the daemon's own pipe server is this one, as its `--daemon-child`, because libuv's pipe server creates its pipe with a null descriptor and no remote-client refusal. **Client:** the client SDK opens the pipe with `CreateFileW` through `koffi`, flags `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION | FILE_FLAG_OVERLAPPED`, checks the pipe's owner is the person with `GetSecurityInfo(handle, SE_KERNEL_OBJECT, OWNER_SECURITY_INFORMATION)` before writing a byte (falling back to `GetNamedPipeServerProcessId` if the owner cannot be read), and wraps the handle as a Node socket through `_open_osfhandle` and `new net.Socket({fd})`. **Token:** the Windows half writes `%LOCALAPPDATA%\ai-sidekicks\run\daemon.token` with a user-only access list at every daemon start; clients read it at every connect. **Record:** `%LOCALAPPDATA%\ai-sidekicks\service.json` names the place in use. - **T-006r-4-3** (Files: the daemon's channel end; the Windows half's channel end) — The channel between the daemon and the Windows half is HTTP/2 over the attached process's standard input and output: `node:http2`'s `performServerHandshake` on the daemon's side, the `h2` crate on the Windows half's. Both ends set `maxSessionMemory` to 128 MB (Node's default of 10 fails a 50 MB echo) with the matching `h2` send buffer, a stream flow window of 1 MiB and a connection window of 16 MiB. The control stream is opened first; each pipe client and each carried port connection is a stream of its own, handed on the daemon's side to the same connection handler a Unix-socket client gets. The daemon's ready line on standard output is `<prefix>{protocolVersion, pid}`, carrying no token, and the channel's own version rides it. The daemon stops itself when its input ends or a write to its output fails, because a killed `wsl.exe` sends it no signal. **Tests:** 50 MB each way at once through a real child's standard input and output passes at these settings. **Spec coverage:** Spec-006 §Interfaces And Contracts (the channel).
- **T-006r-4-4** (Files: the main process's service supervisor; the Windows half's discovery) — Where the service runs, and the places. - **T-006r-4-6** (Files: the Windows half's start, lifetime and stop; `daemon install` and `uninstall` on a WSL computer) — Start: `sidekicks daemon install` registers a per-user logon task, `\AI Sidekicks\Background service`, at the person's normal privilege, set to restart the Windows half after 1 minute if it fails, which runs the Windows half as a no-window program. The Windows half runs `%SystemRoot%\System32\wsl.exe --cd ~ -d <distro> --exec <home>/.ai-sidekicks/runtime/sha256-<digest>/bin/sidekicks-daemon --windows-half-stdio`, created suspended with no console in a Job set to `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`, so `wsl.exe` ends with the Windows half and a Windows program an agent started through interop outlives a stop. The daemon is ready when its ready line arrives within 10 seconds. That attached `wsl.exe` keeps the distribution and the virtual machine running for the service's whole life (WSL's `instanceIdleTimeout` is 15 seconds and `vmIdleTimeout` 60 on Windows 11; systemd does not keep WSL alive); the person's `.wslconfig` is never edited. A daemon that exits unexpectedly is started again at 100 ms, 300 ms, 1 s, 3 s and 10 s; after the fifth failure the Windows half records the error word for word in the status file. **One daemon at a time:** every start takes the per-user mutex `Global\ai-sidekicks-service-<user SID>`. **Stop:** `DaemonStop` with a 10-second grace, then `wsl.exe -d <distro> --exec kill -TERM <pid>` and, if it still runs, `-KILL`; never `wsl --terminate` or `wsl --shutdown`. It writes `%LOCALAPPDATA%\ai-sidekicks\run\service-status.json` when its state changes, never on a timer. ### Phase 2C — Substrate supplement: the socket path is length-checked before bind

**Goal:** the daemon refuses a socket path the platform cannot hold, and says so in its own words.

**Precondition:** Phase 2 merged.

#### Tasks

- **T-006p-2C-1** (Files: `packages/runtime-daemon/src/bootstrap/secure-defaults.ts` EXTEND + `packages/runtime-daemon/src/ipc/local-ipc-gateway.ts` EXTEND) — Check the resolved socket path against the platform's own address field before the bind, and choose the run directory so it fits. A Unix domain socket address is a fixed-size field — 104 bytes on macOS, 108 on Linux, whose `sun_path` that width is documented on in `unix(7)` (read 2026-09-21) — that the platform will neither truncate nor redirect, so the daemon picks a run directory short enough that the socket name still fits inside it with room for the file name. **The limit is read from the platform the daemon is running on, at run time, and never from this plan:** the two numbers above are what those two platforms report today, not constants the code carries, so the figure in the refusal is the running platform's own and a third platform needs no edit here. Handed a longer one, it **refuses to bind and says the path is too long for a socket on this platform**, naming the limit and the length it was given, rather than passing through the malformed-address message at least one client library above the socket reports instead of a length ([Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior)). The refusal is the already-registered `invalid_local_ipc_path` source-side code of the Phase-1 validator, so nothing is minted: no new error code, no new setting, and no second place the path is decided.
- **Spec coverage:** Spec-006 §Required Behavior (the socket path has a hard length limit, so the daemon's run directory is short by design).
- **Tests:** a run directory at the running platform's own limit binds and answers a hello, and a path one byte over that limit is refused before the bind with the limit and the observed length both in the message. **Those two sides together are what prove the number came from the platform**, and neither alone does: a check holding the wrong constant fails the first side wherever the kernel is more generous than the constant — the path is refused although the bind would have worked — and fails the second wherever it is stricter, the check passing a path the bind then rejects with the platform's own malformed-address text, which is exactly the message this task exists to stop a person seeing. So the pair is run on each platform the suite runs on rather than asserted once against a stub, which would only check the stub. The refusal names `invalid_local_ipc_path` rather than a new code.

### Phase 2D — Substrate supplement: the subscription frame is batched, carries changes only, and never waits for a consumer

**Goal:** `LocalSubscriptionProducer<T>` emits batched frames rather than one frame per event, and a consumer that cannot keep up is dropped for and told so rather than waited for.

**Precondition:** Phase 2 merged — the primitive this phase widens is T-006p-2-5's.

#### Tasks

- **T-006p-2D-1** (Files: `packages/contracts/src/jsonrpc-streaming.ts` EXTEND + `packages/runtime-daemon/src/ipc/streaming-primitive.ts` EXTEND — the two files T-006p-2-5 created) — Give the producer a batched frame and a drop rule, so a fast session and a slow screen stop being the same problem. **The batch.** The producer coalesces what it is handed into one frame per 16 ms or 50 events, whichever comes first, and the window opens on the **first** event rather than on the last, so a single event is never held longer than one window while a burst still collapses into one delivery. **The frame carries changes and never the whole record**, and every change on it carries its own cursor, which is what lets a consumer say where it got to without the producer tracking it. **The drop.** The producer never waits for a consumer. One that falls behind is dropped for, and the very next frame that fits carries a flag saying a gap opened; the consumer then repairs against the daemon's own record by cursor, and past the point the record can still fill takes a snapshot read from beyond the gap instead of a fill — so what a consumer holds is either complete or visibly short, never silently short, and the record rather than the consumer is the truth. **The catch-up frame.** When a consumer that was dropped for has caught up on its queue, the producer sends it one frame with no changes, carrying the gap flag and the newest cursor, so a subscription that goes quiet right after a drop still tells its consumer it is behind; a consumer more than 1,024 events behind repairs with a snapshot read rather than a fill. Nothing is minted for any of it: the frame is the already-registered `$/subscription/notify` shape widened, the repair is the `afterCursor` read that surface already takes, and no new method, error code or setting appears. The frame's declared shape is registered at [api-payload-contracts.md §Plan-006 — Local IPC And Daemon Control](../architecture/contracts/api-payload-contracts.md#plan-006--local-ipc-and-daemon-control); the producer type itself stays canonical in code per that file's §Source-of-Truth Policy.
- **Spec coverage:** [Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior) (the subscription frame is batched, carries changes with their cursors, and flags a gap rather than blocking).
- **Verifies invariant:** I-006-10 (the subscribe-init response still precedes the first frame, batched or not), I-006-11 (the drop path is not a cancel path — a dropped-for consumer is still subscribed, so no `onCancel` handler fires).
- **Tests:** a consumer that never reads does not stall the producer — asserted on the producer continuing to accept events while that consumer's queue stands still, which is the property a producer awaiting its consumer would fail; the gap flag appears on exactly one frame per gap and not on every frame after it, the negative control being a second slow stretch, which must raise its own single flag rather than leave the first one standing; the repair is asserted on **both its arms, which do not converge to the same thing and must not be tested as if they did** — within the record's reach the cursor fill is lossless, so that consumer's rows equal a never-behind consumer's exactly; past the record's reach the snapshot deliberately skips what the record can no longer supply, so the rows are **not** equal and the check is that the consumer holds a gap where they were rather than two stretches joined seamlessly, which is the silently-short state the whole mechanism exists to prevent; a single event still leaves inside one window rather than waiting for the batch to fill, which is the difference between the throttle this task specifies and a debounce; and a consumer dropped for with no further events arriving receives exactly one empty frame carrying the gap flag once its queue drains, the negative control being a consumer never dropped for, which receives none.

## Dependency Decisions

**`clipanion@4.0.0-rc.4` is a terminal exact pin, not a placeholder waiting for a stable v4.** `4.0.0-rc.4` is the package's newest version and its `latest` dist-tag, published 2024-09-06; the last stable line is `3.2.1` (2023-06-05); the upstream repository publishes no GitHub Releases, and its tag stream stops at `v0.16.1`. A "watch for the stable-v4 tag and bump" posture would have nothing to watch, so the pin is re-evaluated on the triggers below.

The pinned build's costs are bounded and owned by T-006r-3-1's three refusals, which I-006-20 makes a plan-wide invariant:

- It routes both parse refusals and errors escaping a command body to the run context's **stdout**, the latter with a full stack trace under a hardcoded exit `1`, bypassing the I-006-14 mapping.
- `Command.validateAndExecute` applies a command's static `schema` typanion cascade and throws `Invalid option schema` from there **before** `execute` is called, so a base class that guards only `execute` never sees a schema-validation failure and lets it escape to stdout on that same hardcoded `1`.
- Its Node platform module reaches for `require('async_hooks')` from inside an `.mjs` module, which throws under a pure-ESM bundle whenever `enableCapture: true` meets injected context streams — the test configuration; production's default streams short-circuit before the `require`, so the defect is latent exactly where it is least visible.

Its `UnknownSyntaxError` / `AmbiguousSyntaxError` classes are declared in the type surface but exported through neither the package root nor any subpath, so classification is by `error.name` and the library's `error.clipanion` discriminator. None of these is a reason to leave: the v3 line is two years older and drops the typed decorators V1's commands are written with.

**Re-evaluate the pin when** (i) upstream publishes any clipanion version newer than `4.0.0-rc.4`; (ii) an OSV / GHSA advisory is filed against `clipanion` or `typanion`; (iii) a Node release breaks either published entry point (`./lib/advanced/index.mjs` or `./lib/platform/node.mjs`) under the pinned bundle; or (iv) Yarn drops or vendors clipanion, retiring the precedent.

**The data-folder lock is an exclusive SQLite lock through the pinned `better-sqlite3` 13.0.3.** The daemon already carries it, so no lock library is added; the lock is an fcntl record lock on macOS and Linux, which no child of the service inherits, and the handle is kept referenced for the daemon's whole life because garbage collection would close an unreferenced handle and drop the lock. Whether a child inherits the handle on Windows is measured before Phase R3's sign-in lands there.

**Phase R4's choices.**

- **The Windows half is Rust on `tokio`**, the runtime the PTY sidecar already uses, so the release builds and signs one more binary in the pipeline it has rather than a second toolchain. A pipe server built inside the daemon through `koffi` was weighed and not taken: it would be a second pipe implementation beside the Windows half's, and libuv's own pipe server gives Everyone read access and accepts remote clients.
- **`h2` 0.4.19** for the Windows half's channel end and **`node:http2`'s `performServerHandshake`** (in Node since 20.12 and 21.7, under the Node 24.16 floor) for the daemon's: both are maintained HTTP/2 implementations with flow control, so the channel's multiplexing, backpressure and memory bounds are the protocol's, not code of our own.
- **`windows` 0.62.2** for the Win32 calls (pipes, Job objects, power and toast history), Microsoft's own bindings.
- **`windows-native-keyring-store` 1.1.0** for Credential Manager, written with `persistence=local`, because `@napi-rs/keyring` 2.1.0 passes only the entry's target and so writes every entry at Enterprise persistence, which roams with a domain profile.
- **`koffi`** for the client's `CreateFileW` with the identification-level flags and the owner check, which Node's `net` cannot pass: without those flags a rogue server could act as the caller.
- **The standalone Node.js bundle** for the Linux runtime, not `vercel/pkg`, which is archived (last push January 3, 2024) and cannot keep native modules beside the runtime as plain files. The musl archives use the Node.js project's unofficial-builds musl binaries, because Alpine's own `nodejs` package is a system package a bundle cannot carry.

**Re-evaluate Phase R4's channel when** the binary-integrity probe finds `wsl.exe`'s standard input and output do not carry bytes intact, or the channel probe finds it too slow for Preview's debugger traffic.
