## Goal

When this plan is done, Skills is a working rail destination. One list shows every skill folder on the machine — the console's own, Claude Code's and Codex's, global and project, and the skills installed plugins carry, read-only — each with its origin, its path, its file count, where it is available, what to type to call it, and whether its provider switches it off or it fails to load; a skill whose folder was renamed or deleted outside the console keeps its record in a `Folder gone` group until it is reattached or discarded. A folder opens into an editor that authors the whole folder: the front-matter fields above, a Files list with the entry file pinned first, and every supporting file addable, renamable and deletable in place. Availability is one switch per provider with an origin-derived default and no lock, written through that provider's own per-session off switch, and a widening scan that reports and never blocks; a skill may be off everywhere, its row showing neither provider pressed and no call line. Underneath, the daemon watches the origins, parses every entry file itself, writes folders, runs the scan and hands each provider a pack of every skill available to it — over the one watch, the one record mechanism and the one session pack Plan-024 builds for agents — so a skill authored once reaches both providers and a skill saved mid-session goes live without a restart.

## Non-Goals

- **No gallery of the console's own and no plugin service.** Skills made elsewhere arrive as plugins from each provider's own catalogs, found and installed in `Browse plugins`, which [Plan-024](./024-agent-definitions-and-peer-invocation.md) Phase 6 builds with the daemon's plugin homes. This plan lists a plugin's skills read-only (Phase 7) and publishes nothing.
- **No Commands view and no second registry.** The session composer's `/` and `$` list reads the registry this plan builds; it does not get a copy of it.
- **No writing into a provider's own tree.** A new folder lands under the console's own tree only; a provider's folder is edited where it is, and no field of the console's is written into a file a provider owns.
- **No tool-server work.** Tool servers are machine configuration and belong to their Settings page.
- **No agent-definition work, and no skill reference on a definition.** The definition record and its editor are [Plan-024](./024-agent-definitions-and-peer-invocation.md)'s. Nothing attaches a skill to a definition: every skill available on the provider an agent runs on reaches that agent in the session pack. This plan extends Plan-024's watch, record mechanism and session pack with skills under CP-026-2, and authors no other Plan-024 file.
- **No rail or routing ownership.** The icon rail and the routing module are Plan-020's files. The rail's Skills item is Plan-020's own, built with the rail's five destinations; this plan adds one destination arm to the routing module and authors nothing else there.

## Cross-Plan Obligations

### CP-026-2 — The watch, the record and the session pack in [Plan-024](./024-agent-definitions-and-peer-invocation.md)-owned files

The daemon's file watch over the agent origins, the record kept beside a provider's file with its orphan and reattach rules, and the one session pack module, `packages/runtime-daemon/src/agents/session-pack.ts`, are files Plan-024 builds. Skills need the same three things: a watch over the skill roots, a record beside a provider's folder holding availability and icon, and skills in each provider's pack. A second watch, a second record store or a second pack would be two mechanisms doing one job.

**Resolution.** Plan-024 builds the watch and the record in its T2.1 and the pack in its T3.7, and admits this plan's extensions: the skill roots registered on the watch, the skill record kept through the same record mechanism, and the skills added to the pack. Plan-026 Phase 1 gates on Plan-024 Phase 2 merged and Phase 3 on Plan-024 Phase 3 merged, so each mechanism exists before skills join it.

**Why surfaced here.** The obligation originates in this plan's destination, while the mechanism lives in files another plan owns.

## Target Areas

Nothing about skills lives in the agents feature; that feature keeps the library and the definition editor.

- `packages/runtime-daemon/src/skills/` (NEW) — the skill roots registered on Plan-024's watch, the daemon's own parse of every `SKILL.md`, the whole-folder write, the scan the widening control renders, the console's own per-folder record kept through Plan-024's record mechanism, and the skills added to Plan-024's session pack (CP-026-2). The console never writes a folder and never computes a pack.
- The daemon's one local schema and its test (EXTEND) — the `skill_records` table, the console's own record per skill folder.
- `packages/runtime-daemon/src/ipc/handlers/` (EXTEND) — the skill method namespace, nine operations: `skill.list`, `skill.subscribe`, `skill.fileRead`, `skill.create`, `skill.update`, `skill.availabilityUpdate`, `skill.scan`, `skill.recordReattach` and `skill.recordDiscard`.
- `packages/contracts/src/skill.ts` (NEW) — the folder record with its `orphaned`, `disabledInProvider` and `loadError` facts, the file entry, the availability record, the scan result, the request/response pairs, and the refusal codes, `skill.path_refused` (reason `escapes_folder` \| `duplicate_path` \| `names_entry_file` from a save, `not_listed` from a send's picked skill), `skill.write_refused` (reason `plugin_read_only` \| `not_orphaned`) and `skill.name_taken` (`folderPath`), as strict schemas.
- `packages/client-sdk/src/` (EXTEND) — the typed client the console and the CLI both call, plus its named exports in the package's `index.ts`.

## Phases

### Phase 1 — Contracts, and the daemon's read over the three origins

Precondition: Plan-005 Phase R1 merged; Plan-024 Phase 2 merged.

The contract module and the daemon's read half. The contracts carry the folder record with its `orphaned`, `disabledInProvider` and `loadError` facts — each its own field, the spellings the agent list uses — the per-file entry (path, size, and whether the daemon could read it), the availability record, the scan result, the method pairs and the refusal codes, as strict schemas that reject unknown keys. The daemon registers the eight file roots on Plan-024's watch — the console's own, global and project; Claude Code's own, global and project; Codex's `$HOME/.agents/skills`, `~/.codex/skills` and `<project>/.codex/skills`; and the project's `.agents/skills`, which carries the Codex origin — creates a root that does not exist yet so a later write is visible to a running session, and parses every `SKILL.md` itself, reading front matter with the maintained `yaml` library Plan-024's store already reads agent files with. A folder that fails that parse carries `loadError` with its reason; one a provider's own configuration switches off carries `disabledInProvider`; Codex's `skills/list` is read as evidence beside the parse, its `errors` (`{path, message}`) matched to a row by path, because it loads without error a skill with no name, a name that differs from its folder, a duplicate name and front matter it repairs, and never reports a system skill's error. The console's own record for each skill folder lives in one table this phase creates in the daemon's one schema, `skill_records`: its `skillId`, kept through a rename made in the app, its origin and scope, its folder path, its availability and icon, and whether it is orphaned, the folder path then being the last path the folder was known at; it is the skill half of Plan-024's record mechanism. A record whose folder is renamed or deleted outside the console is kept, marked `orphaned` with the last path the folder was known at. `skill.list` answers with one entry per folder carrying its id (`skillId`), which a rename made in the app keeps, its origin, its scope, its path, its name and description, its file list, its availability, its icon, its call form and its facts. A file it cannot read is listed with its size and no body rather than dropped.

Done when: `skill.list` returns every skill folder from every file origin at both scopes with its origin, scope, path, front matter, file list and facts; a folder created, edited or removed on disk changes the next read with no restart; a folder with broken front matter carries its load error although Codex loaded it; and a provider's folder removed on disk leaves its record orphaned rather than dropped, its `skill_records` row keeping its `skillId`, availability, icon and last path.

### Phase 2 — The folder write, the availability record and the widening scan

Precondition: Plan-026 Phase 1 merged.

The daemon's write half. `skill.update` is a whole-folder save: it applies the front-matter fields, each file's body, the files added, renamed and removed, and the icon together, and leaves the folder untouched when it refuses; path normalization drops leading slashes and `.` and `..` segments before a path is judged, so no file can land outside its folder, and a path it cannot take is refused as `skill.path_refused`, naming the path, with the reason `escapes_folder`, `duplicate_path` or `names_entry_file`. `skill.create` creates a new folder under the console's own tree only, with the typed name folded to a folder name and a collision suffixed rather than overwritten; a folder in a provider's tree is edited in place with its name taken from the directory. On a folder of the console's own, a new name renames the folder, keeping its `skillId`; a name another folder of the console's own holds in the same place is refused as `skill.name_taken`, naming that folder (`folderPath`), and nothing is renamed. The console's own per-folder record is the `skill_records` row Phase 1 creates; its person-set fields are availability and icon, with the origin-derived default; `skill.availabilityUpdate` sets one provider on or off with no lock, so a skill may be off everywhere. `skill.recordReattach` attaches an orphaned record to a folder, taking the token the platform's folder chooser returned, accepted only while the record is orphaned and refused otherwise as `skill.write_refused` with the reason `not_orphaned`; `skill.recordDiscard` drops one. `skill.subscribe` sends the whole `skill.list` reply again each time a save from any window or the watch changes it. `skill.scan` reads every file in a folder against each provider's published tool names and call sigils and returns the files, the tool names as words, and for each tool what will happen instead on the target provider; it stores nothing. Saving a folder of the console's own under a name another folder of its own already packs under, one global and one project, is answered by `skill.update` with that packed-name collision, naming the other folder, so the screen warns before the save.

Done when: a folder can be created, edited and saved through the daemon; a path that would escape the folder, a duplicate path and a path naming the entry file are each refused with its `skill.path_refused` reason; a rename of a folder of the console's own keeps its `skillId`, and one onto a name another of its own holds in the same place is refused with `skill.name_taken` naming that folder, with nothing renamed; a change switching a provider's own skill off its own provider and one switching a skill off its last provider are each accepted; an orphaned record reattaches to a picked folder and a reattach of a record that is not orphaned is refused with `skill.write_refused` (`not_orphaned`); a subscriber receives the whole list after a save and after a change on disk; and a scan of a folder returns the files that name the other provider's tools with what each tool does instead on the target, or nothing where none does.

### Phase 3 — The session pack and mid-session liveness

Precondition: Plan-026 Phase 2 merged; Plan-003 Phase 3 merged; Plan-024 Phase 3 merged.

The provider-facing half. At launch the daemon adds every skill available to a provider to that provider's session pack — the one pack module Plan-024 builds (CP-026-2) — and hands it over through that provider's own loading path, namespaced so a packed skill can never shadow one of the provider's own: each origin packs as a plugin of its own, whose name the provider puts before its skills. On Claude Code each is a plugin folder passed with `--plugin-dir`, carrying skills only; on Codex each is a plugin through its configuration. A skill in a provider's own tree keeps its bare name in that provider's session. Only a skill made in the console packs as `sidekicks`, so it reads `sidekicks:<name>`. A skill crossing to the other provider always carries where it came from, never only when two names meet: a Claude Code skill packs for Codex in the plugin `claude` (`$claude:<name>`), a Codex skill packs for Claude Code in the plugin `codex` (`/codex:<name>`), and a plugin's skill packs for Codex in a plugin of the plugin's own name (`$<plugin name>:<skill name>`). A provider's own skills colliding with each other in its own session are the project's to resolve; the pack adds nothing for them. Two folders of one origin that share a name at the global and the project place both pack, the global one under the name and the project one with the `-2` suffix a new skill takes, and saving a folder of the console's own under a name another of its own already packs under warns first. A skill switched off on a provider is switched off through that provider's own per-session off switch — Claude Code's `skillOverrides` in the session's settings, Codex's session config — which the daemon writes; nothing writes the person's own config files, and the window never touches a provider folder. Nothing is copied into `.claude`, `.codex` or the repository. A skill saved mid-session is carried into the live session: on Codex by its own `skills/changed` notification, on Claude Code by the daemon's `reload_plugins` control request, sent after the write so the session picks the folder up without a restart. The composer's `/reload` presses the same refresh by hand; Plan-024 carries its handler. The call-form line the console states is derived here, once, per origin-and-provider pair.

Done when: a session started after a skill is authored can invoke it under the namespaced form, a skill in a provider's own tree is invocable under its bare name, a Claude Code skill is invocable on Codex as `$claude:<name>` and a Codex skill on Claude Code as `/codex:<name>`, two folders of one origin sharing a name are both invocable, the project one with `-2`, a skill saved while a session is running is invocable in that same session on both providers without a restart, and a skill switched off on a provider, that provider's own skill included, does not load in that provider's session while no config file of the person's is written.

### Phase 4 — The destination: addresses and the list

Precondition: Plan-026 Phase 3 merged; Plan-020 Phase 5 merged.

The screen's first half. The rail's Skills item, which Plan-020 builds drawing the open book, opens this screen and is marked current on it to assistive technology as well as drawn. The routing module gains the addresses: `#/skills`; a folder at `#/skills/<id>` and one of its files at `#/skills/<id>/<file path>`, with the `skillId` the list carries, so two folders that share a name never share an address and a rename made in the app keeps it; and the new-skill form at `#/skills?new`, a query on the list's address, so a skill folder keeps its real name, `new` included. The screen's layout is built — the title, the count, one search field and `New skill`, no view strip and no tabs, the shared sessions track and bell carried unchanged — and then the list: the caption and its note, one row per folder with its glyph tile, name and summary, origin mark, folder and size, availability line, call form, widen line and provider facts (`Off in Claude Code` or `Off in Codex`, and `Didn't load · <reason>`, each only while it holds and both when both hold), ordered by folder name under `Intl.Collator`, searched case-folded across name, summary, origin words and every file path inside the folder; after the rows, the `Folder gone` group, each row keeping the record's icon and availability, reading the last path the folder was known at, and carrying `Reattach…`, which opens the platform's folder chooser, and `Discard`, which asks in place. The list's in-flight, refused and empty arms are built with it, the in-flight arm's loading note reading `Reading the skills on this machine…` while the count reads `—`. The skill list is the console's shared store over the contract shapes (`zustand` 5.0.15 parsed with `zod` 4.6.5), read from `skill.list` and kept current from `skill.subscribe`, and its widgets come from the console's own widget set (`@base-ui/react` 1.8.0), styled from the console tokens.

Done when: the rail reaches Skills, each of its addresses renders its own state, and the list shows every folder the daemon reports with every row part, ordering, search, the provider facts, the `Folder gone` group with its acts, and its non-populated arms with the in-flight words; a save in another window reaches the list without a re-read.

### Phase 5 — The folder editor

Precondition: Plan-026 Phase 4 merged.

The screen's second half. The open folder: the top strip with `All skills`, the unsaved mark, `Cancel` and `Save`; the front-matter fields with the note saying which field lives where; the twelve-icon field on every origin, a new skill starting with the bolt and a record that holds no icon drawing the bolt; the global-or-project choice on a new skill only, opening on Global whether or not a project is attached, held with its reason, `No project is attached`, while none is, and naming in its own label the project the person came from — the session's project when the destination was opened from a session, otherwise the project of the most recently focused session — as `This project · <name>`, with the machine's other known projects one press away in its list; the path line naming the folder and following the typed name, with its verbs. Then the folder in two columns — the Files panel with the entry file pinned first, the file count, the current-row mark, the entry file's **the skill** mark in place of its rename and delete controls, and the three in-place questions for adding, renaming and deleting, each answering a refused path in its own row with the reason and moving nothing else on the screen; and the body column with the open file's name, its kind word and its body in the mono or reading face its extension chooses, the body read through `skill.fileRead` when the file opens, a text file of any size opening, and one past the memory budget the console works out from the machine it runs on drawn read-only and only in part, naming its real size and how much is shown. While a folder is open the header carries the skill's name in place of the title, and the count, the search field, `Browse plugins` and `New skill` are put away until the folder is closed. A save of a folder of the console's own under a name another of its own already packs under warns before it saves; a save confirms with a note saying what it wrote. The keyboard set lands here — save, escape, the search key, row movement, and the leaving-with-changes question that names every changed field by its label and every changed file by its path — as does the two-column fold to one under the narrow threshold, asked of the pane rather than the window.

Done when: a folder can be opened, every field and every file edited, a file added, renamed and deleted through the in-place questions, and the whole folder saved; a delete falls the editor back to the entry file; a refused path is answered in its own row; and leaving with changes asks and names what changed; the header carries the skill's name while a folder is open; a new skill starts on the bolt and on Global, its project choice held with `No project is attached` while none is; and a save under a name another of the console's own folders packs under warns first.

### Phase 6 — Availability on the screen, and the composer's Skills group

The last surface, and the second reader. On the row and in the open folder, the availability control per provider reading as pressed or not pressed, with no lock: a provider's own skill switches off its own provider like any other, and a skill may be off everywhere, its row showing neither provider pressed and no call line. ### Phase 7 — A plugin's skills

Precondition: Plan-026 Phase 6 merged; Plan-024 Phase 6 merged.

The fourth origin, read-only. The daemon reads the skills of every installed plugin from its own plugin homes, never from an account home, which holds no plugins: on Claude Code, `claude plugin list --json` in the Claude Code plugin home names each plugin's `installPath`, and its `skills/` folder is read from there; on Codex, `plugin/installed` and `plugin/read` in the Codex plugin home, whose plugin detail lists the plugin's skills. `skill.list` carries each such skill with the origin `plugin` and the plugin's name, its folder path under the plugin home, its file count, its availability — the provider the plugin was installed for — and its call form: on Claude Code the plugin's own namespace, `/<plugin name>:<skill name>`, the plugin reaching the session through its own `--plugin-dir`; on Codex the daemon's pack, a plugin of the plugin's own name, `$<plugin name>:<skill name>`, always. Every writing operation refuses a plugin's skill with `skill.write_refused` and the reason `plugin_read_only`, and `plugin.installed` and `plugin.uninstalled` change the list and reach `skill.subscribe`. On the screen the row is drawn like any other, marked `plugin · <plugin name>`, with neither availability control pressable: each keeps reading as pressed or not and also reads as unavailable, its reason a tooltip that opens on pointer hover and on keyboard focus, closes when either leaves, and is tied to the control so a screen reader reads it with the control, the row itself carrying none of those words, and a forced click changes nothing, because the hold is enforced when the click is handled too; opened, the folder draws its fields and files with no control — no `Save`, no `Add file`, no rename or delete — under the line `Installed by a plugin. Update or remove it in Browse plugins.`; and the header gains `Browse plugins` beside `New skill`, opening `#/sidekicks/plugins`, put away with the rest while a folder is open.

Done when: a skill a plugin installed appears in the list with its mark, path, fixed availability and call form, `$<plugin name>:<skill name>` on Codex; it opens read-only with the line; a forced click on either held availability control changes nothing, and its tooltip opens on hover and on focus; every write to it is refused; installing or removing a plugin changes the list in every open window; and `Browse plugins` in the header opens the plugin view.

### Sweeps over the built screen

Run over every state above: the rail draws five destinations in order with Skills current; the screen says `sidekick` and never agent; no sentence begins with `You`; no wire spelling appears beyond file names, paths and the provider's own call form, read over every accessible name as well as every visible word; every glyph-only control carries a word for a name; no horizontal overflow at 1440 × 900; no runtime error on any state; both color schemes render; reduced motion is respected; one remote origin; and every chrome size root-relative with every text size and line height a type-scale token, so the screen at a larger root is the same screen in one proportion.

Tooling is the console's existing tiers ([Spec-021 §Console Test Tiers](../specs/021-desktop-app-and-renderer.md#console-test-tiers)): Vitest with happy-dom for unit, Vitest browser mode through `@vitest/browser-playwright` for the browser and accessibility tiers with `axe-core` 4.13.0 run in-page, `@playwright/test` 1.63.0's Electron launcher for the end-to-end flow, `@testing-library/react` for the console unit tier, and `knip` 6.39.0 with `dependency-cruiser` 18.5.0 for the structural gates.

## Risks

- **The scan's provider vocabulary ages.** Tool names and call sigils change as the providers ship. Keep the vocabulary in one table and the scan's output words rather than wire spellings, so an upstream rename changes the table and not the screen. Nothing is re-checked on a version bump: a tool a provider renamed shows as a scan miss in the daemon's logs and is investigated when seen.
- **A provider adds or moves a skill root.** The watch's root list is one place for exactly this reason; a new root is one entry, and a folder found there keeps that provider's origin mark and shows the root in its path.
- **A mid-session save that the provider never sees.** On Claude Code a scope directory that did not exist when a session started stays invisible for that session's whole life unless the reload request is sent. Create the roots before launch and send the reload after every write; a save that reports success and does not reach the running session is the failure this mitigates.
- **The skill roots on the watch cost handles and wake-ups.** They join the one watch Plan-024 builds rather than a second one: one recursive watch per root with a debounce, a burst of writes coalesced into one registry rebuild, and no polling.
- **A very large folder or file.** A skill folder has no depth cap and no file cap by design. List every file and open every text file; past the memory budget the console works out from the machine it runs on, draw the file read-only and only in part, naming its real size and how much is shown, rather than refusing it or hiding the row.
