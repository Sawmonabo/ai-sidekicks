## Goal

When this plan is done, every interface that the earlier phases build and check on macOS has its Windows and its Linux implementation, and each is measured on a machine of its own kind. The earlier phases keep the code portable: each piece that differs by operating system sits behind one interface in the plan phase that owns it, which builds the macOS form. This plan adds the other two forms, so the same product runs on all three systems before the release.

## Non-goals

- **The terminal sidecar.** [Plan-021](./021-rust-pty-sidecar.md) owns it whole: its host, protocol, crash budget and respawn, the cross-compile of both Rust crates for x64 and arm64 and its publish script, with the arm64 package. Its Phase 4, its Phase 5 and its Phase 3B sidecar-only tasks are built beside this plan, and this plan holds no task for them.
- **The service on WSL 2 and the Windows half.** [Plan-005](./005-local-ipc-and-daemon-control.md) Phase R4 owns everything `sidekicks-windows-half.exe` does on either kind of Windows computer (the daemon's pipe, the credential store's Windows arm, banners and their withdrawal, keep-awake, the wake timer, the logon task, the port carry) and the daemon's WSL arm. This plan holds the rest of the Windows code.
- **Packaging, signing and the update path.** They are the release's, after this plan.

## Target areas

- `apps/desktop/src/main` — the Windows and Linux forms of the native verbs, the taskbar count, the window chrome, the `sidekicks://` address registration, and a session view's native drag on Wayland
- `apps/desktop/src/renderer` — the Windows and Linux key legends and file-manager wording
- `packages/runtime-daemon/src` — the Windows and Linux forms of the service's provider, credential, keep-awake, wake, messaging, command-wrapper and capture interfaces
- `apps/cli` — the Linux user service with lingering

## Phases

Each phase is one pull request. A task names the plan whose interface it implements; that plan's spec and done-when are the acceptance, run on a machine of the task's own kind.

- **T27.2.10 — The waiting signal.** "The waiting signal through `/proc/<pid>/syscall`, through what the right to read shows where that is refused, and a password prompt through the terminal's own settings": for a Codex command in the wrapper's terminal and for a command typed into a session's shell alike, the three conditions of [Plan-021](./021-rust-pty-sidecar.md) T-021-3B-9 — nothing queued on the terminal, no thread of its foreground group running, and a reader found in each thread's `/proc/<pid>/task/<tid>/syscall` across the group's processes: a thread blocked in `read`, `readv` or `pread64` on the terminal, in `epoll_wait`, `epoll_pwait` or `epoll_pwait2` on an epoll set whose `/proc/<pid>/fdinfo/<epfd>` lists the terminal, or in `select`, `pselect6`, `poll` or `ppoll` with a descriptor set, read from `/proc/<pid>/mem`, that holds the terminal for reading; a descriptor on `/dev/tty` counts as the terminal when `tty_nr` in the process's `stat` names it. The `syscall` file gives the call by number, which the check maps per processor architecture: arm64 numbers `read` 63, `readv` 65, `pread64` 67, `pselect6` 72, `ppoll` 73, `epoll_pwait` 22 and `epoll_pwait2` 441 and has no `select`, `poll` or `epoll_wait` ([`unistd.h`](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/include/uapi/asm-generic/unistd.h)), which x86_64 adds. Reading `syscall` never stops the thread, and a running thread reads `running` ([proc_pid_syscall(5)](https://man7.org/linux/man-pages/man5/proc_pid_syscall.5.html)); one thread's reads took 27.5 µs in a container probe, so the group comes from `TIOCGPGRP` on the master, never from a scan of `/proc`. In a session's shell, the shell's own prompt read looks exactly like a command's readline read, and only the foreground group tells them apart: a reader counts while the terminal's foreground group is not the shell's own, and a reader in the shell's own group counts only between a command's start and end marks, where it is a builtin of the shell run as the command, such as `read`. The wrapper's terminal has no shell prompt, so there every reader of the terminal counts. A program that reads the terminal through io_uring waits in the ring, not in a read of the terminal, so this check does not see it: the command keeps its input line, and only the waiting mark is missing. The `syscall` and `mem` reads need the right to attach, which Yama at level 1, the kernel's default, grants a reader over its own descendants ([`yama_lsm.c` 352–368](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/security/yama/yama_lsm.c#L352-L368)): the wrapper reads the command it started, inside Codex's sandbox through the `/proc` the sandbox mounts for its own process namespace, and the daemon a command typed into a shell it started. A process whose parent exits is handed to its nearest child subreaper, and otherwise to the system's first process, which takes it out of the daemon's descendants, so the daemon marks itself a child subreaper with `PR_SET_CHILD_SUBREAPER` ([prctl(2)](https://man7.org/linux/man-pages/man2/prctl.2.html)) and reaps such a process when it exits. Where `/proc` refuses those reads (Yama's ptrace scope at 2, which lets only a holder of `CAP_SYS_PTRACE` attach, or at 3, which lets none, [Yama](https://www.kernel.org/doc/html/latest/admin-guide/LSM/Yama.html)), the check reads what needs only the right to read, which Yama never checks: each thread's `/proc/<pid>/task/<tid>/wchan` ([`proc/base.c` 413–423](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/fs/proc/base.c#L413-L423) and [3686](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/fs/proc/base.c#L3686)), the process's descriptors in `/proc/<pid>/fd` and their `fdinfo`. A thread sleeping in `do_epoll_wait` on an epoll set whose `fdinfo` lists the terminal with `EPOLLIN` is waiting on it, exactly as above. A thread sleeping in `wait_woken`, where the terminal's line discipline sleeps for input ([`n_tty.c` 2158](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/drivers/tty/n_tty.c#L2158)), is waiting on the terminal when its process holds the terminal open and no socket, inotify, fanotify or vsock descriptor, a read of any of which can sleep there too, and when it cannot be a writer: the line discipline's writer sleeps in `wait_woken` too, on a full output buffer, so the thread counts only while the master holds no unread output (`FIONREAD` on the master reads 0) and its reader, the daemon for a session's shell and the wrapper for its terminal, has not paused its reads. A thread sleeping in `poll_schedule_timeout` ([`select.c` 234](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/fs/select.c#L234)) may wait on the terminal or on nothing, as a `select` with no descriptors used as a sleep does, so it is not read as waiting; a `select` or `poll` reader under Yama at 2 or 3, and a reader of the terminal that holds a socket or an inotify, fanotify or vsock descriptor, keep their input line, and only the waiting mark is missing. A program running with raised privileges (setuid, setgid or file capabilities) or marked not dumpable refuses every read but its `stat`, and a `poll` resumed as `restart_syscall` shows no descriptor set. For a program that refuses the reads, the check reads the terminal's own settings through the master, which needs no right over the program, since `tcgetattr` on a master answers with the terminal's settings ([`tty_ioctl.c` 764–776](https://github.com/torvalds/linux/blob/602042bf29f6efde39cfb5fdd9289bf4854bc0c5/drivers/tty/tty_ioctl.c#L764-L776)): when the output is quiet, in a session's shell the foreground group is not the shell's, the terminal has canonical input on and echo off (`ICANON` set and `ECHO` clear), and a member of the foreground group sleeps (state `S` in its `stat`), the command is waiting on a password, as `sudo`, `su`, `passwd`, `getpass`, a shell's `read -s`, ssh and git ask for one, and `echoOff` is set; such a program that turned echo off and sleeps for another reason reads as waiting too, and its line still works, and such a program's prompt with echo on keeps its input line and is not marked waiting. A command under `sudo` after its password runs in a terminal `sudo` opens for it, which this check does not see: it keeps its input line, and only the waiting mark is missing. Weighed and not taken as signs of a reader: `TIOCPKT_IOCTL`, which reports only when the program turns on external processing (`EXTPROC`), so it is not passive; `FIONREAD` on the master; and the line discipline's read wait queue. Under WSL 2 a Windows program started from a Linux shell runs behind WSL's interop stub, expected to relay the terminal to it over a socket, which T27.1.11 measures; the stub is not counted as the reader, and the Windows program is never marked waiting. A command the check cannot read keeps its input line, and only the waiting mark is missing. Implements the command wrapper in [Plan-003](./003-provider-driver-contract-and-capabilities-phase-3.md) T3.28 and the shell table's waiting check in [Plan-021](./021-rust-pty-sidecar.md) T-021-3B-9.
