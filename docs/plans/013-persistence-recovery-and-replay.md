## Goal

Implement durable local persistence, replay rebuild, and startup recovery for session execution state.

## Scope

This plan covers SQLite-backed canonical local persistence, replay services, runtime-binding restoration, startup recovery sequencing, and recovery-status surfaces. It also owns the per-session **file checkpoint store** [Spec-013 §Required Behavior](../specs/013-persistence-recovery-and-replay.md#required-behavior) defines — the copies the daemon takes before each edit and at each prompt boundary, held with the session outside the checkout and surviving a resume and a restart. That store is the single source a message-anchored file restore reads from, on both providers; [Plan-003](./003-queue-steer-pause-resume.md)'s T3.13 is its caller, for a message-anchored restore and a named-snapshot restore alike; the turn-boundary snapshots of [Plan-008](./008-worktree-lifecycle-and-execution-modes.md) name the point a snapshot-anchored restore returns to.

## Non-Goals

- Operator runbook authoring
- Long-term retention tuning
- Provider-specific internal persistence formats

## Data And Storage Changes

- Add or extend local `session_events`, `session_snapshots`, `command_receipts`, `runtime_bindings`, `queue_items`, and approval-state tables for recovery completeness.
- Add recovery-status projection data and replay cursors needed to expose healthy, replaying, degraded, or blocked startup state.
- The per-session file checkpoint store keeps its copies **with the session and outside the checkout**, so a copy never appears in a diff and survives a working-folder move, and it keeps its own index of them beside the copies. No local table is added for it and no existing table grows a column: the store is file-backed node-local state, and this plan mints no schema for it.
- See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) for column definitions.

- The file checkpoint store's payload shapes — the dry-run preview, the closed set of restore targets, and the restore's own report — are registered in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md). **The dry-run read and the restore call have no ratified method names, so this plan registers none**: both operations are owed, and each name lands with the surface that registers it. Until then the store is reached in-process by its daemon-side caller.

## Invariants

- **I-013-1 (no observable double-application; execution multiplicity is per-class):** What holds uniformly is the effect, not the execution count — naming one guarantee for both would be wrong. **Execution multiplicity is per-class, and [Spec-013 §Idempotency Classes and Recovery Behavior](../specs/013-persistence-recovery-and-replay.md#idempotency-classes-and-recovery-behavior) is authoritative for it rather than this entry:** the startup sweep RE-EXECUTES `idempotent` and `compensable` receipts and never re-executes `manual_reconcile_only`, which halts the affected run with a `recovery-needed` condition instead. An implementation MUST NOT suppress that retry in this invariant's name. Within a single boot the two-phase receipt commit's Phase-2 optimistic compare-and-set (`UPDATE ... SET started_at = now() WHERE started_at IS NULL`) admits exactly one claimant per receipt, so concurrent recovery workers never double-invoke — a concurrency bound, not an across-restart one. **What holds across every class is that no side effect is OBSERVABLY applied twice**, by a different mechanism per class: a `compensable` retry carries the receipt's `dedupe_key` so the remote side can reject the duplicate, and `manual_reconcile_only` is never retried at all, paying an operator escalation for that. `idempotent` is the named residual rather than a third mechanism — the spec assigns the remote half to the tool ("External deduplication (if any) is the tool's responsibility"), so what this plan holds is the driver's declared class, never a remote-side guarantee. That composite is the referent Spec-013's "enforces exactly-once semantics" names. [Spec-013 §Idempotency Protocol](../specs/013-persistence-recovery-and-replay.md#idempotency-protocol), [Spec-013 §Two-Phase Receipt Commit](../specs/013-persistence-recovery-and-replay.md#two-phase-receipt-commit), [Spec-013 §Idempotency Classes and Recovery Behavior](../specs/013-persistence-recovery-and-replay.md#idempotency-classes-and-recovery-behavior).
- **I-013-2 (idempotent rebuild):** `ProjectionRebuild` for a session over the same canonical event range yields identical projection state regardless of how many times it runs. [Spec-013 §Interfaces And Contracts](../specs/013-persistence-recovery-and-replay.md#interfaces-and-contracts), [Spec-013 §Acceptance Criteria](../specs/013-persistence-recovery-and-replay.md#acceptance-criteria).
- **I-013-3 (no premature admission):** No mutable operation is accepted until startup recovery has restored canonical local truth or the node is in an explicit blocked/degraded state. [Spec-013 §Default Behavior](../specs/013-persistence-recovery-and-replay.md#default-behavior), [Spec-013 §Acceptance Criteria](../specs/013-persistence-recovery-and-replay.md#acceptance-criteria).
- **I-013-4 (no silent run loss):** A persisted driver handle that cannot be resumed transitions its run to `failed` with visible recovery-failure detail; it never silently disappears or restarts as a new run. [Spec-013 §Fallback Behavior](../specs/013-persistence-recovery-and-replay.md#fallback-behavior), [Spec-013 §Acceptance Criteria](../specs/013-persistence-recovery-and-replay.md#acceptance-criteria).

- [ ] **T15.6 — Build the per-session file checkpoint store: capture, retention, and durability.**
  - Capture rides **the same tool hook the daemon already registers to hold a run** — one mechanism, never a second interception path. Before the agent or one of its child runs edits a file, and at every prompt that starts a turn, the store copies that file aside as it was, one copy per content version; the file-editing tools are Claude Code's `Write`, `Edit`, `MultiEdit` and `NotebookEdit` and Codex's `apply_patch`, and a file created since the checkpoint is recorded as new so a restore deletes it rather than leaving it behind. Re-verify the tool names against the then-installed provider binaries before this code lands, the way the rollback verbs are re-verified.
  - The copies are held **with the session and outside the checkout**: they never appear in a diff, they survive a working-folder move, and they survive a resume and a daemon restart — the store's index is part of the node's durable local state and is read back at startup rather than rebuilt from the tree.
  - **Retention is a bound with a floor.** The last hundred checkpoints of a session are kept, and **every file's first copy is retained** past that bound, so evicting by count never leaves a file whose only copy has gone — the state in which a restore silently cannot put a file back.
  - **What a shell command wrote is outside the store**, on both providers, because no tool call announced it. The store records nothing for it and claims nothing about it; saying so is the dry run's job (T15.7).
  - **Target paths:** `packages/runtime-daemon/src/persistence/checkpoints/`
  - **Spec coverage:** [Spec-013 §Required Behavior](../specs/013-persistence-recovery-and-replay.md#required-behavior) (the per-session file checkpoint store: the two capture points, the copies held with the session outside the checkout, the hundred-checkpoint bound, survival across a resume and a restart, and shell writes being outside it)

- [ ] **T15.7 — The restore dry run, the restore itself, and its skip report.**

- [ ] **T15.5 — Resume position-compare + divergence halt-for-human, with the rollback interplay guard.**
  - On every successful resume (`DriverResumeResult.status: 'resumed'` — a failed resume follows T15.3's explicit-failure arm), compare the driver-reported normalized `sessionPosition` against the daemon-recorded position derived from the local log. Both recovery attach modes — adopting a live provider session (preferred per Spec-013 §Default Behavior) and cold resume from a stored handle — traverse the single driver `resumeSession → DriverResumeResult` ingress, so the compare gates **every** successful attach: no adoption path finalizes without it (Spec-004's fresh-session sentence — "caught by this comparison rather than silently adopted"). Equal → recovery proceeds. Diverged → **the local log is authoritative** ([ADR-017](../decisions/017-shared-event-sourcing-scope.md)) and the run **halts for human action**: it enters `waiting_for_input` carrying `recovery-needed` together with the daemon-derived `RecoverySpanClassification` of the diverged span — derived **direction-aware**: a daemon-ahead span (provider behind; the span is daemon-recorded events the provider is missing) folds the span's daemon-recorded content (receipt `idempotency_class` values and event kinds) — reads only → `read_only`; writes all idempotent/compensable → `idempotent_write`; any `manual_reconcile_only` or side-effecting content of unknown class → `irreversible`; a **provider-ahead** span (`sessionPosition` above the daemon-recorded position) exists only provider-side with no daemon-recorded content to fold and is `unclassifiable` **by construction** — never vacuously `read_only`; any otherwise-underivable span → `unclassifiable`, handled **exactly as `irreversible`** (fail-closed). V1 consumes the classification as **audit metadata only** — every divergence halts; recording it makes tiered auto-resolution a future policy flip gated on this task's CI divergence-injection tests. The daemon never silently re-emits locally recorded events into the provider session and never silently discards provider-side events; the halt surfaces on both existing owner-visible channels Spec-013 §Fallback Behavior names — `RecoveryStatusRead`'s `blocked` state (Plan-013-owned; implemented by this plan) and Spec-011's `run.blocked` timeline row — never a new notification surface. T15.5's daemon-side deliverable serves both: the recorded run state + `recovery-needed` condition + classification IS what the `run.blocked` row renders, and rendering it is Plan-011's obligation under Spec-011, which already carries that row — so this plan takes no dependency edge on it. The compare also catches a provider silently returning a **fresh session** on resume (e.g. Claude on a working-directory mismatch): past the initial boundary a fresh session's position cannot match the recorded one — and position equality alone is **not** identity proof at the initial boundary (a fresh session can report the same initial position as a run that crashed before advancing), so the compare composes with the driver's I-004-5 no-silent-replacement duty: the driver reports `resumed` only for the provider session its handle names (deterministic session binding), surfacing a replacement session as such, and a same-position fresh session therefore takes the failed/divergence arm, never silent acceptance. A run already `waiting_for_input` at crash time keeps its state — no self-transition row, per run-state-machine.md's §Derived Failure And Recovery Signals rule — with the stale pre-crash input request replaced by the `recovery-needed` reconciliation block, never left masking the divergence. A divergence halt from any waiting source also **settles the superseded block** before reconciliation: the pending approval or driver ask that created the old blocking state is canceled as moot through Spec-005's existing terminals (`approval.canceled` / `driver_ask.canceled`, whose cause rows register the divergence settlement) — and a **permission-backed approval settles both surfaces**: the approval reaches `approval.canceled` and its originating ask (the persisted `askId` association, Plan-010 T2.8) reaches the paired `driver_ask.canceled`, so the native ask can no longer answer against a dead block. A stale approval is never left actionable against a diverged run; a late resolution or late ask answer finds a canceled request and no-ops.
  - **Rollback interplay guard (consumes ADR-017's rollback ruling):** the daemon-recorded comparand respects rollback markers — a `run.rolled_back` event on the run's log establishes the **new authoritative position floor** (the rollback applied-variant's driver-confirmed `sessionPosition`, domain-validated per its api-payload block) as a **re-based baseline, not a static pin**: later locally recorded events advance the comparand from that floor, so the compare always targets the latest daemon-recorded position folded from the log (post-rollback re-execution included — a run that legitimately advanced past the floor before the crash compares against its advanced position, never falsely halted against the original floor), and rollback and recovery never fight over position truth. **Dispatched-but-unconcluded rollback reconciliation (consumes Spec-003 §Required Behavior's reconciliation rule):** before the compare renders any divergence verdict, a durable dispatched-but-unconcluded `rollback` intervention row on the run (the write-ahead `interventions` marker — accepted-before-dispatch) is reconciled first, "before anything else touches the run": a driver-reported position at the row's `targetPosition` (or a discovered post-fork binding at it) **completes the intervention forward** — remaining legs, durable outcome, forward `run.rolled_back`, binding repoint — establishing the floor the compare then passes against; an unchanged position concludes it by Spec-003's no-rewind path with the floor unmoved; a **valid-but-different rewind-consistent position** — a domain-valid recorded turn boundary strictly below the pre-dispatch position but not `targetPosition` — completes as Spec-003's confirmed position-mismatch outcome (`degraded` naming the mismatch, file leg skipped fail-closed, forward `run.rolled_back` at the observed confirmed position, floor re-based there): under ADR-017's log authority nothing but the dispatched rollback rewinds a provider session, so a rewind-consistent observation is corroborated as that rollback's confirmed floor, never guessed from ambiguity; only a divergence neither branch explains — a position above the pre-dispatch position, or no recorded boundary — takes the halt. One further Spec-003-mandated exception: the **file-leg recovery intervention** (the carve-out-admitted current-position target) reconciles as **at-target, never no-rewind** — there at-target and unchanged coincide by construction, and reconciliation takes the completion branch to the restore fixpoint rather than stranding the partially restored tree the recovery exists to finish. The crash window between a driver-confirmed rewind and the marker append therefore completes forward instead of stranding as a blanket halt.

## Design Decisions

- **D-013-1 — `ReplayReadAfterCursor` retains a sequence-position cursor (`afterSequence: number`), not the `EventCursor` brand.** The replay read advances over the canonical `session_events.sequence` integer (the `replay_cursors.last_sequence` state machine), so a numeric sequence position is the natural cursor and makes idempotent rebuild (I-013-2) trivially verifiable. The sibling `EventReadAfterCursor` uses the opaque `EventCursor` brand because client-facing event reads must tolerate cursor-format evolution (Plan-005). The two read models intentionally differ; reconciling them to a single brand is a non-blocking refinement **not** adopted in V1 — `docs/architecture/contracts/api-payload-contracts.md §Plan-013 — Persistence Recovery And Replay` keeps `afterSequence: number`.
