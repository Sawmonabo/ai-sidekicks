## Goal

Ship the Node.js deployment package that hosts Spec-008's v2 relay protocol for operators running their own control-plane per ADR-020 Option 1 (free self-host) and Option 2 (self-host-your-own-relay). Execute the technology choices already locked in [Spec-025](../specs/025-self-hostable-node-relay.md) — Fastify v5 + `@fastify/websocket`, Node.js 22 LTS, Postgres 17, Caddy for TLS termination, in-house PASETO v4.public on `@noble/curves` / `@noble/ciphers`, `rate-limiter-flexible` Postgres backend behind Plan-021's abstraction — and deliver: a single runnable process, a shared PASETO primitive package, a reference `docker-compose.yml`, an operator runbook, and the supply-chain hardening baseline (npm provenance, `--ignore-scripts`, `npm audit signatures`).

The protocol-level invariant from `Spec-025 §Required Behavior` governs acceptance: a daemon must not be able to distinguish the Node self-host relay from the Cloudflare Workers hosted backend at the protocol level. This plan therefore consumes Plan-008's shared **wire** surfaces (the `decodeRelayFrame` codec + `RelayFrameType` enum in `@ai-sidekicks/contracts`) while **re-implementing the R3 runtime _semantics_** (connect-token verify, frame dispatch, graceful drain) in its own modules over the shared `verifyV4Public` primitive — no portable Plan-008 state-machine symbol exists to import (D-025-2). Both backends share that one primitive and the same `sessionId` implicit-assertion, so a daemon cannot distinguish them at the protocol level.

## Scope

- `packages/crypto-paseto/` — **new, owned by this plan.** Shared PASETO v4 primitives per [ADR-010 §`packages/crypto-paseto`](../decisions/010-paseto-webauthn-mls-auth.md): **v4.public** (Ed25519 sign / verify / key management) on `@noble/curves`, AND **v4.local** (XChaCha20 stream cipher + BLAKE2b-MAC encrypt-then-MAC, per the [PASETO v4.local spec](https://github.com/paseto-standard/paseto-spec/blob/master/docs/02-Implementation-Guide/01-Payload-Processing.md#v4local) — **not** XChaCha20-Poly1305 AEAD) on `@noble/ciphers` (XChaCha20) and `@noble/hashes` (BLAKE2b). Consumed by this plan (verifier — v4.public only), Plan-018 (issuer — access tokens via v4.public, refresh tokens via v4.local), and Plan-002 Phase 2 (invite-token issuer via v4.local per CP-002-4). Ships with the PASETO RFC conformance vector test suite covering both primitives.
- `packages/relay-node/` — **new, owned by this plan.** The Node.js self-host relay process: Fastify v5 bootstrap, `@fastify/websocket` frame handling, PASETO verification middleware, Plan-021 rate-limiter wiring, graceful-shutdown lifecycle, structured-JSON logging, operator HTTP surface (`/healthz`, `/readyz`, `/metrics`).
- `deploy/self-host/` — **new, owned by this plan.** Reference deployment assets: `docker-compose.yml` (Compose Spec, no `version:` field; five services — a one-shot `pg-cert-init` that provisions the Postgres CA + server cert before `postgres` starts, `postgres`, a one-shot `migrate` schema applier, `relay-node`, and `caddy` — with `postgres` gated on `pg-cert-init` `service_completed_successfully` and `relay-node` gated on `migrate` `service_completed_successfully` + Postgres `service_healthy, restart: true`), `pg-cert-init.sh`, `Caddyfile`, `.env.example`, operator README outline.
- `packages/relay-node/Dockerfile` — **new, owned by this plan.** Distroless or Debian-slim base, non-root UID/GID, read-only root FS where Node.js permits.
- `.github/workflows/relay-node-release.yml` — **new, owned by this plan.** Build + publish container image to GHCR with provenance attestations; publish npm package with provenance.
- `docs/operator-guide/self-host-relay.md` — **new, owned by this plan.** Operator-facing runbook: deployment flow, env var reference, the 500-req/s rate-limiter ceiling, PASETO key rotation procedure, Postgres 17 minimum, graceful-shutdown behavior.

## Non-Goals

- **v2 protocol definition.** Spec-008 is authoritative. Any change to the handshake / session-join / message-framing **protocol definition** lands in Plan-008, not here. This plan imports Plan-008's shared **wire** surface (the `decodeRelayFrame` codec + `RelayFrameType` enum, hoisted to `@ai-sidekicks/contracts`) and re-implements the R3 runtime semantics locally (D-025-2); it never re-defines the protocol.
- **Cloudflare Workers backend.** Hosted deployment ships separately per [Deployment Topology](../architecture/deployment-topology.md). The runtime bundle this plan produces must contain zero Cloudflare-specific code paths (enforced in acceptance criteria).
- **Kubernetes Helm chart.** Out of scope per `Spec-025 §Non-Goals` and ADR-020 deployment-options commitment. Operators who want Kubernetes run Compose-in-Kube or author their own Helm chart; no V1 support.
- **Enterprise operator features.** OIDC/SAML SSO, HSM-backed signing keys, SOC 2 artifacts, offline-root signing — all V1.1+. BL-060 tracks V1 secure-by-default; this plan consumes BL-060's posture.
- **Redis backend for rate-limiter-flexible.** `Spec-025 §Fallback Behavior` notes Postgres backend saturates at ~500 req/s per namespace; operators exceeding that shard the namespace or adopt Redis post-V1. This plan does not ship Redis wiring.
- **New protocol features in self-host only.** ADR-020 feature-parity commitment: protocol changes ship to both deployments or to neither.
- **Grafana dashboard.** `Spec-025 §Open Questions` leans toward shipping a minimal reference dashboard; that is deferred to post-V1. This plan ships `/metrics` in Prometheus text format only.

## Target Areas

- `packages/crypto-paseto/` — **created by this plan.** Shared PASETO v4 primitives.
  - `src/v4-public.ts` — `signV4Public(payload, secretKey, footer?, implicitAssertion?)`, `verifyV4Public(token, publicKey, footer?, implicitAssertion?)`, `generateV4PublicKeyPair()` — all Ed25519 on `@noble/curves`, exported as free functions (not methods).
  - `src/v4-local.ts` — `encryptV4Local(payload, key, footer?, implicitAssertion?)`, `decryptV4Local(token, key, footer?, implicitAssertion?)` — free functions taking a 32-byte symmetric `key` argument (the package ships no symmetric-key generator; callers supply 32 random bytes). XChaCha20 stream cipher + BLAKE2b-MAC (encrypt-then-MAC, **not** XChaCha20-Poly1305 AEAD) with BLAKE2b-KDF derivation of `ek` / `n2` / `ak` on `@noble/ciphers` (XChaCha20) + `@noble/hashes` (BLAKE2b) per [PASETO v4 spec §v4.local payload processing](https://github.com/paseto-standard/paseto-spec/blob/master/docs/02-Implementation-Guide/01-Payload-Processing.md#v4local).
  - `src/pae.ts` — shared pre-auth encoding serialization used by both primitives (PASETO standard §PAE).
  - `src/key-ring.ts` — `KeyRing`: a primitive-agnostic, in-memory 32-byte-key **store** with rotation — `active()`, `byId(id)`, `rotate(next)` over `KeyRingEntry { id; key /* 32 bytes */; createdAt; retiredAt? }`, enforcing exactly-one-active + 32-byte-key + no-duplicate-id invariants and deep-cloning entries on intake/readout. It does **no** verification or decryption and has **no** time/rotation window — the rotation window is the consuming verifier's concern (the relay's `paseto-verifier.ts`, step 6; keyed on wall-clock signing-key validity, never the token's `iat`). Plan-018 Tier 5 loads entries from its storage backend and hands them to the constructor.
  - `src/test/rfc-vectors-v4-public.test.ts` — PASETO v4.public conformance vectors from the PASETO spec repo.
  - `src/test/rfc-vectors-v4-local.test.ts` — PASETO v4.local conformance vectors from the PASETO spec repo (separate JSON vector file per primitive).
- `packages/relay-node/` — **created by this plan.** The relay process.
  - `src/server.ts` — Fastify v5 bootstrap; registers `@fastify/websocket`, auth middleware, rate-limit middleware, operator HTTP routes.
  - `src/auth/paseto-verifier.ts` — does **not** consume the crypto-paseto `KeyRing` class (its single-active-entry invariant cannot hold the relay's simultaneous current+prior verification keys, and it exposes no candidate enumeration). The verifier parses `PASETO_PUBLIC_KEYS` into its own in-process candidate set, tries each signing key live in the `Spec-025 §Fallback Behavior` rotation window (wall-clock — the relay accepts both the prior and current signing keys during the window and rejects a token whose signing key is outside it, `Spec-025 §Fallback Behavior`; the token's `iat` is never consulted for key selection, since it is unauthenticated before signature verification and Spec-008 connect-tokens carry no `iat` claim) via the shipped `verifyV4Public` free function (`sessionId` implicit-assertion); extracts the `sub` claim into `request.participantId` (A-025-10, D-025-2; step 6).
  - `src/rate-limit/wire-postgres-limiter.ts` — instantiates Plan-021's `PostgresRateLimiter` per `(endpoint group, tier variant)` pair (Plan-021 D-021-4) over a shared injected `pg.Pool`; composes Plan-021's `createAdmissionCheck` enforcement pipeline (ban → block → counter, D-021-3) and exposes its verdict to the relay's raw HTTP routes through a Fastify `onRequest` hook mapping refusals to the `Spec-021 §Overflow Response` shape (the rows `Plan-021 §Endpoint wiring ownership (D-021-6)` assigns to Plan-025 step 7; the relay serves no tRPC, so the tRPC-only `rateLimitProcedure` is not consumed — Plan-021 CP-021-3 deliberately omits it) and wires `wsRateLimit` into the `@fastify/websocket` message handler; registers Plan-021's admin-bans routes (`POST/GET/DELETE /admin/bans*`) on the Fastify host, authenticated by the Spec-027 Row 3 relay admin token (Plan-021 D-021-1/D-021-10).
  - `src/ws/frame-handler.ts` — decodes frames using Plan-008's shared `decodeRelayFrame` codec, then dispatches via the relay's **own re-implemented** v2 frame-dispatch semantics (D-025-2 — Plan-008 R3's relay-broker dispatch lives in a Cloudflare-Worker `control-plane` build target, so there is no portable handshake/dispatch state machine to import — the relay re-implements the R3 frame-dispatch semantics locally over that shared codec), running the per-frame rate check before dispatch.
  - `src/ops/health.ts` — `/healthz`, `/readyz` (with Postgres probe) as public routes; `/metrics` (Prometheus text format) behind its Spec-027 Row 9b bind/auth secure-default gate (loopback default), NOT public.
  - `src/ops/graceful-shutdown.ts` — SIGTERM / SIGINT handler; stops accepting new connections; drains in-flight WS with `SHUTDOWN_DRAIN_TIMEOUT_MS` timeout (default 30s); force-closes with code `1001 Going Away` on timeout.
  - `src/ops/logger.ts` — pino-based structured JSON logger with token-masking redactor at the log-emit boundary (regex strips anything matching PASETO v4.public prefix `v4.public.`).
  - `src/config/env.ts` — env-var parsing with schema validation (`zod`); fails loudly at startup on missing or malformed values.
  - `src/tls/` (deploy-mode.ts, fingerprint-emitter.ts) — **created by this plan.** [Spec-027 Row 1](../specs/027-self-host-secure-defaults.md#required-behavior) auto-TLS surface. `deploy-mode.ts` parse-time validates `DEPLOY_MODE=public|lan` (rejects LAN-suffix hostname under `public` — `.localhost`, `.local`, `.home.arpa`, `.internal`, RFC1918; rejects publicly-resolvable hostname under `lan`). `fingerprint-emitter.ts` emits SPKI-SHA256 (RFC 7469, base64) + SSH-style `SHA256:<hex>` whole-cert hash for internal-CA certs to stdout + `./data/trust/fingerprint.txt` (mode 0600). Caddy's own TLS configuration is **not** generated by a relay module (D-025-9): it lives in the single committed env-parameterized `deploy/self-host/Caddyfile` (`tls {$AIS_CADDY_TLS}` → `internal` for `DEPLOY_MODE=lan` or the operator's ACME email for `public`; `protocols {$AIS_CADDY_TLS_MIN:tls1.3}` honoring [RFC 9773 ARI](https://datatracker.ietf.org/doc/html/rfc9773) renewal windows; T-025d-15-1), so the deploy path ships no runtime Caddyfile generator — Caddy owns its config natively and substitutes env at parse time. `DEPLOY_MODE=public` → DNS-01 when a provider plugin is declared else HTTP-01; `DEPLOY_MODE=lan` → `tls internal` with no public-ACME fallback.
  - `src/config/insecure-flag.ts`, `src/config/legacy-tls12.ts` — **created by this plan.** Spec-027 Row 2 + Row 8 override parsers. `INSECURE=1` (Row 2) and `LEGACY_TLS12=1` (Row 8) each emit a loud startup banner + exactly one `security.default.override=<name>` log event per startup. `legacy-tls12.ts` loosens the relay's own Node TLS surfaces to `minVersion: 'TLSv1.2'` and records the override; the Caddy-edge TLS floor is governed by the committed Caddyfile's `protocols {$AIS_CADDY_TLS_MIN:tls1.3}` — the caddy service's one-line entrypoint shim computes the internal `AIS_CADDY_TLS_MIN` from the operator's single `LEGACY_TLS12` flag (then `exec`s stock `caddy run` against the committed Caddyfile) so the Row-8 override reaches the Caddy edge too under one flag (D-025-9), and no relay module rewrites Caddy's config. Non-loopback bind without TLS MUST be rejected at parse-time when `INSECURE` is unset — except where TLS terminates at a declared trusted front proxy, which satisfies the encryption requirement (the container-internal `0.0.0.0:8787` behind Caddy is therefore the secure default and passes parse-time without `INSECURE=1`; [Spec-027 §Bind-Address Reconciliation](../specs/027-self-host-secure-defaults.md#bind-address-reconciliation) / D-025-6).
  - `src/postgres/` (ssl-verify-full.ts, weak-auth-probe.ts, version-probe.ts) — **created by this plan.** [Spec-027 Row 5](../specs/027-self-host-secure-defaults.md#required-behavior) Postgres hardening. `ssl-verify-full.ts` is a thin relay wrapper over the shared Worker-free `parsePgSslConfig` helper at `packages/control-plane/src/postgres/ssl-config.ts` (D-025-9 — the same parser the `migrate` one-shot consumes, so the two Postgres clients cannot drift): the shared helper parses `PG_SSLMODE` into a node-postgres `ssl` object passed to Node's `TLSSocket` (the driver exposes no `mode` option, and any `sslmode` left in `DATABASE_URL` would _replace_ this object and silently drop the CA — so the connection string MUST carry no `sslmode`): `verify-full` → `{ ssl: { ca: <ca-bundle>, rejectUnauthorized: true, servername: <database-url-host>, minVersion: 'TLSv1.3' } }`, `verify-ca` → `{ ssl: { ca: <ca-bundle>, rejectUnauthorized: true, checkServerIdentity: () => undefined, minVersion: 'TLSv1.3' } }` (the TLS 1.3 floor per Spec-027 Row 8, which names Postgres TLS explicitly — the shared `parsePgSslConfig` reads `LEGACY_TLS12` and sets `minVersion: LEGACY_TLS12 ? 'TLSv1.2' : 'TLSv1.3'`, so `migrate` and the relay loosen the Postgres-client floor symmetrically; a harmless no-op in the bundled deploy where `postgres:17` offers TLS 1.3, the genuine escape hatch only for an external legacy Postgres), and refuses `disable|allow|prefer|require` at parse-time (CVE-2024-10977 rationale — `require` is MITM-exploitable via libpq error-message injection); the relay wrapper adds the `verify-ca` loud banner + `security.default.override` event. `weak-auth-probe.ts` runs `SELECT auth_method FROM pg_hba_file_rules WHERE error IS NULL` and refuses to start on `trust`/`password`/`md5` rules. `version-probe.ts` enforces `server_version_num ≥ 170000` (PG 17 minimum); logs advisory if `< 180000`. The Postgres server cert (`SAN=<compose-service-name>`, default `postgres`, so the `DATABASE_URL` host matches the issued cert) is **not** produced by a relay module — it is generated by the `pg-cert-init` one-shot before `postgres` starts (T-025d-14-1, D-025-9), since the relay boots after Postgres and cannot provision the cert the Postgres server needs at its own startup.
  - `src/self-update/` (cli.ts, manifest-verifier.ts, sigstore-verifier.ts) — **created by this plan.** [Spec-027 Row 7b](../specs/027-self-host-secure-defaults.md#required-behavior) CLI opt-in self-update. `ai-sidekicks self-update` entry point; dual-path verification — Ed25519 signature on release manifest AND Sigstore bundle (`gh attestation verify` semantics OR embedded `@sigstore/verify` against `actions/attest-build-provenance` bundle) — BOTH MUST pass; either alone is refusal. Anti-rollback (`version <= last_seen_version` rejected), anti-freeze (`now > expires_at` rejected), `previous_manifest_hash` chain validation. Rationale: post-Shai-Hulud (2025-09/11, 25k+ npm repos) + post-Axios (2026-03-31, hijacked-maintainer direct-publish) incidents established dual-path as the V1 floor.

- `deploy/self-host/docker-compose.yml` — **created by this plan.** A one-shot `pg-cert-init` + Postgres 17 + a one-shot `migrate` (the step-19 schema applier) + relay-node + Caddy v2 (five services). ## Data And Storage Changes

- **No new owned tables.** The relay owns no SQLite and no Postgres tables; it is stateless at the _database_ level beyond in-flight WebSocket bookkeeping in memory. All persistent **database** state is owned by upstream plans (Plan-008, Plan-018, Plan-021 — plus Plan-014's `artifact_relay_*` coordination rows once its cross-node relay legs land, see the CP-014-3 bullet below) or by rate-limiter-flexible itself.
- **Artifact relay blob store — CP-014-3 reciprocal (2026-07-08).** With cross-node shared artifacts pulled into V1 ([ADR-015 amendment 2026-07-08](../decisions/015-v1-feature-scope-definition.md#amendment-2026-07-08-v11-deferred-features-3--2-cross-node-shared-artifacts-pulled-into-v1)), the self-host deployment composition gains an object-storage surface for artifact ciphertext per [Spec-014 §Cross-Node Artifact Relay](../specs/014-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1): a filesystem-backed volume or S3-compatible service serving the blob-store HTTP surface, plus the Spec-014 operator knobs (`node_relay_storage_max`, retention-tier TTL presets, quotas) through this plan's config surface. Plan-014 CREATEs the deployment-agnostic artifact-relay service and owns its Postgres coordination rows; this plan's reciprocal is composition-level only (compose service + volume + config wiring) and lands with Plan-014's Tasks 7–10, after that plan's readiness-audit delta. Object storage is not a database table, so the no-new-owned-tables invariant above stands.
- **Relay-local trust material on disk (not a table).** The relay writes two operator-facing files on its `./data` named volume: the first-run admin token — the bearer **secret** — at `./data/admin-token` (step 22 / T-025s-3, the canonical Spec-027 path), and, under `DEPLOY_MODE=lan`, the **public** internal-CA fingerprint at `./data/trust/fingerprint.txt` (step 20 / T-025s-1). The secret stays out of the `./data/trust/` directory, which holds only publishable trust-verification material (the fingerprint clients pin + the `first-run.complete` sentinel) — a deliberate security-class separation (D-025-8). These are the relay's only persistent **local** state — not database rows, but they MUST survive container recreation (a fresh admin token on every recreate would lock operators out). The reference Compose persists them on a named volume mounted into the `relay-node` service (step 14 / T-025d-14-1), and the read-only root FS makes `./data` the sole writable path. (Caddy's own `/data` cert + ACME-account store is likewise volume-backed — step 14 — so redeploys do not re-issue certs against Let's Encrypt rate limits.)
- **Rate-limiter-flexible namespace tables (`ratelimit_*`).** The library auto-creates these on first use via its Postgres store. They do NOT ship in the Plan-008 / Plan-018 / Plan-021 migration sequence. The operator runbook must note this so operators understand why extra tables appear. The one-time auto-creation happens on the relay's first cold start against a fresh Postgres; subsequent starts are no-ops.
- **PASETO key material is not stored by the relay.** Public keys arrive via `PASETO_PUBLIC_KEYS` env var (JSON array of keys with rotation metadata). The relay never holds signing keys; issuance and rotation are Plan-018's concerns. This plan's verifier treats keys as ephemeral config.

## Spec-027 Secure-Defaults Surface

This subsection is authoritative for Plan-025's Spec-027 row coverage. BL-094's charter enumerated "rows 1/2/4/5/7b/8/10" against an early-draft Spec-027 numbering that differs from the final spec's numbering; Spec-027's final numbering governs here, and where charter row-text conflicts with the final spec, the final spec supersedes. Two concrete drifts the reader must know:

- **Row-number drift.** The charter's (1/2/4/5/7b/8/10) map by position to Spec-027 final rows (1/2/5/8/10/7b/3). No behavior is dropped — Plan-025 owns every charter row plus Spec-027 Row 4 (loopback bind default for the relay's container-internal `0.0.0.0:8787` per [Spec-027 §Bind-Address Reconciliation](../specs/027-self-host-secure-defaults.md#bind-address-reconciliation)), yielding 8 rows of coverage.
- **Policy drift on Postgres TLS.** Charter "Row 4: Postgres `sslmode=require` default" is deliberately superseded by [Spec-027 Row 5 `sslmode=verify-full` default](../specs/027-self-host-secure-defaults.md#required-behavior). `sslmode=require` is MITM-exploitable per [CVE-2024-10977](https://www.postgresql.org/support/security/CVE-2024-10977/) (2024-11-14 — libpq server error-message injection; fixes in PG 17.2 / 16.6 / 15.10 / 14.15 / 13.18); `verify-full` is the MITM-defeating posture (hostname-bound chain validation). Spec-027 Row 5's own rationale column records this escalation; Plan-025 implements it — the Postgres client defaults to `verify-full`, accepts `verify-ca` with a loud banner, and refuses `disable | allow | prefer | require` at config-parse time.

## Implementation Steps

1. **Create `packages/crypto-paseto/` package skeleton.** Scaffold TypeScript package with `@noble/curves`, `@noble/ciphers`, and `@noble/hashes` as dependencies (all pinned to exact versions in `pnpm-lock.yaml`). Export types `PasetoPublicKey`, `PasetoSecretKey`, `PasetoSymmetricKey`, `PasetoToken` (token-string discriminant covering both v4.public and v4.local).
2. **Implement PASETO v4 primitives.** Both primitives share the pre-auth-encoding (PAE) serialization in `src/pae.ts` per the PASETO standard.
   - **v4.public** in `src/v4-public.ts`: header `v4.public.` + base64url(payload `||` 64-byte Ed25519 signature) + optional footer. Ed25519 ops go through `@noble/curves/ed25519`. Reference RFC: [PASETO v4 §v4.public](https://github.com/paseto-standard/paseto-spec/blob/master/docs/02-Implementation-Guide/01-Payload-Processing.md#v4public).
   - **v4.local** in `src/v4-local.ts`: header `v4.local.` + base64url(32-byte nonce `||` ciphertext `||` 32-byte BLAKE2b-MAC tag) + optional footer. Per spec: 32-byte CSPRNG nonce → BLAKE2b-KDF (info strings `paseto-encryption-key` + `paseto-auth-key-for-aead`) → derives 32-byte XChaCha20 key (`ek`) + 24-byte stream nonce (`n2`) + 32-byte BLAKE2b-MAC key (`ak`) → XChaCha20 stream-encrypt the payload, then BLAKE2b-MAC the PAE over `(header || nonce || ciphertext || footer || implicit)` to produce the 32-byte tag. **This is encrypt-then-MAC, not XChaCha20-Poly1305 AEAD.** XChaCha20 via `@noble/ciphers/chacha`; BLAKE2b-MAC via `@noble/hashes/blake2`. Reference RFC: [PASETO v4 §v4.local](https://github.com/paseto-standard/paseto-spec/blob/master/docs/02-Implementation-Guide/01-Payload-Processing.md#v4local).
3. **Author RFC conformance vector test suites.** In `src/test/rfc-vectors-v4-public.test.ts` and `src/test/rfc-vectors-v4-local.test.ts`, load the official vectors from the PASETO spec repo (separate JSON vector files per primitive) and assert `signV4Public`/`verifyV4Public` (v4.public) and `encryptV4Local`/`decryptV4Local` (v4.local) match every vector — including the negative test vectors for tampered ciphertext, invalid signatures, and footer-injection. **Both suites are gating acceptance criteria** — the package cannot ship without both green.
4. **Implement the `KeyRing` key store.** In `src/key-ring.ts`, implement `KeyRing` as a primitive-agnostic, in-memory store of 32-byte keys with rotation: `KeyRingEntry { id; key /* 32 bytes */; createdAt; retiredAt? }` and the methods `active()` (the single non-retired entry), `byId(id)`, and `rotate(next)` (returns a **new** instance with the prior active entry retired). The constructor enforces exactly-one-active + 32-byte-key + no-duplicate-id invariants and deep-clones entries on intake and readout. ## Rollback Or Fallback

- **PASETO RFC vector regression.** Non-negotiable: cannot ship. If a dependency bump introduces a vector regression, pin the dependency back and investigate before releasing.
- **Postgres backend saturation in operator deployments.** `Spec-025 §Fallback Behavior` documents the ~500 req/s ceiling. Operator runbook provides namespace-sharding workaround. If an operator exceeds even sharded capacity, they adopt Redis as a V1.1+ migration path (out of scope here).
- **Caddy cert renewal failure.** Caddy retains the prior valid certificate until expiry (Caddy native behavior). Operators monitor `caddy_acme_certificate_renewal_failure` metric; operator runbook documents the DNS/ACME diagnosis path.
- **Fail-open on rate-limiter backend outage.** Plan-021's fail-open wrapper handles this (60s default grace, then 503). This plan does not override Plan-021's behavior.
- **Container image pull failure from GHCR.** Operators can build locally from source (`docker compose build`); the runbook documents this fallback.
- **Version pin on `ws` transitive (via `@fastify/websocket`).** If a new `ws` CVE lands during operator deployment, pin `@fastify/websocket` to the version tree that resolves `ws` ≥ the fixed version and release a point update. `Spec-025 §Implementation Notes` already flags this.

## Risks And Blockers

- **In-house PASETO correctness risk.** Rolling our own PASETO is the chosen path (`Spec-025 §Implementation Notes` rejected `panva/paseto` as archived and `paseto-ts` for single-maintainer concentration). Mitigation: the RFC conformance vector suite is a gating acceptance criterion; the implementation is ~150 LOC of composable noble primitives. Deliberate mitigation via test rigor, not via falling back to an unmaintained library.
- **Plan-018 + Plan-002 co-dependency on `packages/crypto-paseto/`.** Plan-018 (issuer for access tokens via v4.public + refresh tokens via v4.local) and Plan-002 Phase 2 (issuer for invite tokens via v4.local per CP-002-4) must consume the package this plan creates. If either lands before Plan-025's package is published, they cannot compile. Mitigation: land `packages/crypto-paseto/` (Tier 1 Partial — v4.public + v4.local substrate, steps 1–4) as the first deliverable of this plan, ahead of Plan-002 Phase 2 and Plan-018's scheduled starts. Both consumer plans name this plan in their Dependencies; `cross-plan-dependencies.md` §2/§3/§5 record the carve-out.
- **Plan-008 protocol surface not yet stable.** This plan cannot wire the WS frame handler (step 8) until Plan-008 publishes its v2 protocol package. Mitigation: steps 1–4 (crypto-paseto) and steps 13–19 (deploy + docs) proceed independently of Plan-008; the relay-node process assembly (steps 5–12) waits on Plan-008's package export.
- **Node.js 22 LTS adoption friction for operators.** Some operators run Node 20 (Iron) pipelines today; Iron goes EOL 2026-03-24 (pre-V1-GA per project roadmap, but some ops teams move slowly). Mitigation: operator runbook documents Node 22 as baseline; containerized deployment hides the Node version from operator hosts (they only need Docker).
- **Postgres 17 adoption friction.** Spec-025 bases Postgres 17. Operators on Postgres 15/16 must upgrade. Mitigation: operator runbook explicitly states "Postgres 17 minimum" in the prerequisites section; the `/readyz` endpoint's Postgres probe includes a `server_version` check that refuses to start if below 17.
- **Caddy vs nginx operator preference.** Spec-025 chose Caddy as the default; some operators prefer nginx. Mitigation: operator runbook includes a brief "using nginx instead" appendix showing the 5-line reverse-proxy config; not a supported deploy target but unblocks preference.
- **Supply-chain posture not enforced at install time.** `pnpm install --frozen-lockfile --ignore-scripts` + `npm audit signatures` live in CI, but operators who run a package install locally may not get the same guarantees. Mitigation: operator runbook tells operators NOT to install from source; they deploy via container image. The in-repo `pnpm-lock.yaml` pins exact versions so any rebuilds use audited trees.
- **Compose Spec `depends_on.restart: true` requires Docker Compose v2.20+.** Older Compose versions silently ignore the key, so the relay is not recreated when Postgres is **explicitly** recreated via `docker compose up` (the `restart: true` scope — it does not cover container-runtime crash restart, which the per-service `restart: unless-stopped` policy handles regardless of Compose version). Mitigation: operator runbook states "Docker Compose v2.20+" as a prerequisite; the `docker compose up` CI smoke test runs on a current Compose version.

The relay container has no durable on-disk state beyond ephemeral logs," which contradicted this plan's §Data And Storage Changes (the first-run admin token `./data/admin-token` and, under `DEPLOY_MODE=lan`, the internal-CA fingerprint `./data/trust/fingerprint.txt` — `0600` files on a named volume that MUST survive container recreation; steps 14 / 20 / 22) and the Spec-027 Rows 1/3 mandate that creates them. - **D-025-9 — The Postgres TLS material, the Caddy edge TLS config, and the Postgres client trust are provisioned at the deployment-bootstrap layer, not by relay-node `src/` modules: a one-shot `pg-cert-init` container provisions the CA + SAN-matching server cert, the single committed env-parameterized `deploy/self-host/Caddyfile` owns Caddy's TLS natively, and a shared Worker-free `parsePgSslConfig` helper backs both the relay and the `migrate` `verify-full` clients.** Rounds 8–11 assigned TLS-material generation to relay-node modules (`src/tls/caddy-config-generator.ts`, `src/postgres/cert-gen-helper.ts`) consumed by containers — `postgres`, `caddy`, `migrate` — that boot **before** the relay process exists, an ordering impossibility that left the artifacts undelivered on a fresh `docker compose up` (NS19-E/F/G). (2) **Caddy TLS →** Caddy owns its config natively in the single committed `deploy/self-host/Caddyfile` (`tls {$AIS_CADDY_TLS}` selecting the operator's ACME email or `internal`; `protocols {$AIS_CADDY_TLS_MIN:tls1.3}` pinning the TLS 1.3 floor) via Caddy's parse-time [environment-variable substitution](https://caddyserver.com/docs/caddyfile/concepts#environment-variables), with the caddy service's entrypoint shim **deriving** `AIS_CADDY_TLS` from `DEPLOY_MODE` + `AIS_ACME_EMAIL` (so `DEPLOY_MODE` is the single source of truth and a `public` deploy with an empty `AIS_ACME_EMAIL` fails the shim loudly); the prior `src/tls/caddy-config-generator.ts` generator is **removed** (T-025d-15-1). (3) **Client trust →** a shared Worker-free `parsePgSslConfig` helper at `packages/control-plane/src/postgres/ssl-config.ts` parses `PG_SSLMODE` into the `ssl` object (refusing `disable|allow|prefer|require`), refuses a `DATABASE_URL` carrying any node-postgres SSL query param (`sslmode`/`sslcert`/`sslkey`/`sslrootcert` — any one replaces the `ssl` object and drops the CA per the node-postgres SSL docs, so the helper is the single enforcement point both clients share), and reads `LEGACY_TLS12` to set `minVersion: LEGACY_TLS12 ? 'TLSv1.2' : 'TLSv1.3'` (Spec-027 Row 8 names Postgres TLS), consumed by `migrate` deep-relative and by `relay-node` via a Worker-free postgres-ssl sub-path export (mirrors CP-021-3); the relay's `ssl-verify-full.ts` becomes a thin wrapper that delegates the floor to the helper, so both clients loosen symmetrically (T-025d-19-1 / T-025s-5). This folds in **R11-2** (`migrate` declares no persistent data volume of its own — it mounts only the `pg-tls` CA read-only) and **R11-4** (the TLS 1.3 pin lives in the committed Caddyfile's `protocols {$AIS_CADDY_TLS_MIN:tls1.3}`; the caddy service's entrypoint shim computes `AIS_CADDY_TLS_MIN` from the single `LEGACY_TLS12` flag — `tls1.2` when set, else `tls1.3` — alongside deriving `AIS_CADDY_TLS` per (2) above, then `exec`s stock `caddy run`, because Caddy applies a `{$VAR:default}` default **only when the var is unset** ([`parse.go`](https://github.com/caddyserver/caddy/blob/master/caddyconfig/caddyfile/parse.go) `os.LookupEnv` + `if !found`), so a pure-Compose `${LEGACY_TLS12:+tls1.2}` would leave a set-empty var that silently drops the floor). No spec amendment is owed: Spec-027 Row 5 names "a cert-generation helper" generically (not a relay process), and Row 8 mandates `tls { protocols tls1.3 }` (the committed default satisfies it), names Postgres TLS explicitly (the shared helper sets `minVersion: 'TLSv1.3'` by default, `'TLSv1.2'` under the override), and sanctions exactly one override token `LEGACY_TLS12` (the shim keeps the Caddy edge on that one flag — no second operator knob enabling 1.2 outside the banner-emitting path). Supersedes the round-8 cert-gen mechanism. Records a reconciled deployment-bootstrap contract, not a new wire surface. (Surfaced by Codex round-11 review; ratified with the advisor + author in round 12.)
- **D-025-10 — The self-host relay recovers the implicit-assertion `sessionId` from the relay-endpoint URL path segment, pinned by a Spec-008 content-only amendment.** The PASETO connect-token verify binds `sessionId` as the v4 implicit assertion (`Spec-008 §Relay Negotiation`), which the verifier MUST hold **independently of the token**. The hosted relay satisfies this because its Durable Object is session-sharded (it _is_ the per-session endpoint); the self-hostable single Fastify process is **not** sharded, and how it obtains `sessionId` out-of-band was unpinned (round-18 KscWI). The audit pinned the carrier in the contract: the `RelayNegotiationResponse` relay-endpoint URL carries `sessionId` as a path segment (`wss://<host>/relay/<sessionId>`), so any non-sharded verifier recovers it from the dialed URL — a `Spec-008 §Relay Negotiation` content-only amendment plus the `RelayNegotiationResponse.relayEndpoint` contract comment (api-payload-contracts.md); Spec-008 stays `approved` (same content-only-amendment precedent as the D-025-4/5/6/7 Spec-027 reconciliations). The relay realizes it as the Fastify route `/relay/:sessionId` and reads the param at the WS upgrade (steps 5/6). This pins the previously-unpinned **carrier**; it does not weaken D-025-2's no-import boundary (the verify is still re-implemented over the shared `verifyV4Public`, importing no `control-plane` symbol), and owes no Plan-008 task edit — no Plan-008 task constructs the relay-endpoint URL, so the grammar lives in the Spec-008 contract the negotiation builds to, not in a plan step. Records a reconciled contract carrier, not a new wire surface. (Surfaced by Codex round-18 review.)
