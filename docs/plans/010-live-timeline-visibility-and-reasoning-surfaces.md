## Goal

Implement the replay-backed session timeline, child-run visibility, reasoning surfaces, and composer usage meters used by the primary session experience.

## Scope

This plan covers timeline projections, live subscribe plus replay recovery, child-run summaries and expansion, reasoning-availability surfaces, the composer's context ring with its compaction popover ([Spec-011 §Context Window and Usage Meters](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#context-window-and-usage-meters)), and the question card.

## Non-Goals

- Notification routing
- Provider-specific reasoning rendering beyond normalized surfaces
- Full timeline design polish

## Invariants

- **I-010-1** — Every run-scoped timeline row carries the complete attribution triple `runId` + `position` + `epoch`, all-or-none; a partial row fails SDK schema parse rather than being delivered. **Run-scopedness is decided by three tests, not by category alone**: the row's category where that category is closed on the run-scoped side (`run_lifecycle`), the row's canonical event type against the census of `Spec-005` types whose registered payload names a run unconditionally, and — for the types whose run identity is registered OPTIONAL, which no type-level test can decide — the row's own payload naming one. A row answering any of the three and carrying the attribution-free `kind` is refused, because such a row is reachable by no run filter and permanently current under rollback projection. Grounds in [Spec-011 §Required Behavior](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#required-behavior).
- **I-010-2** — A rolled-back turn is never dropped from the timeline; it is marked superseded and stays renderable. Grounds in [Spec-003 §Required Behavior](../specs/003-queue-steer-pause-resume.md#required-behavior).
- **I-010-3** — The `superseded` marker is single-field (`targetPosition`); run identity and source epoch are read from the containing row, so live marking and replay marking cannot disagree. **The same no-second-source rule binds the row's payload**: where a projection echoes the canonical run identity or the `sourceEpoch` / `sourcePosition` origin keys, each must equal the row's own outer `runId` / `epoch` / `position`. Run identity is checked under **both** registered spellings — `runId`, and the intervention family's `targetRunId`, which is the same fact named from the other side of the relationship ([Spec-005 §Queue and Intervention (interactive_request)](../specs/005-session-event-taxonomy-and-audit-log.md#queue-and-intervention-interactive_request)) — because a rule reading only the first leaves every intervention row free to be filed under one run while naming another, and the row's own general-arm refusal already treats both spellings as run attribution. The run-identity half binds every arm carrying an outer `runId`; the origin-key half binds the arm that carries ordinals. Echoing is optional and absence passes; disagreement is refused, because consumers key filtering and superseded treatment on the outer triple while the row's detail and provenance are read from the payload, so a row stating two attributions is filed under one turn and sourced from another. Grounds in [Spec-011 §Required Behavior](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#required-behavior).
- **I-010-4** — Superseding is epoch-scoped: a re-executed reused ordinal in a later epoch renders current while the earlier epoch's same ordinal stays superseded. Grounds in [Spec-003 §Required Behavior](../specs/003-queue-steer-pause-resume.md#required-behavior).
- **I-010-5** — Every `run.rolled_back` boundary payload validates into the typed `RunRolledBackEvent` shape at projection; no consumer receives an untyped cutoff or performs a cast. Grounds in [Spec-011 §Required Behavior](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#required-behavior).
- **I-010-6** — The rollback boundary is delivered visibility-resolved to every filtered subscription admitting any of the affected run's rows. Grounds in [Spec-011 §Required Behavior](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#required-behavior).
- **I-010-7** — Reasoning unavailability always produces a visible explanation surface; a provider's own redaction never renders as absence. Grounds in [Spec-011 §Acceptance Criteria](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#acceptance-criteria).
- **I-010-8** — Every reasoning text the provider supplied is kept whole for as long as the session's events are kept: a text longer than one entry (16,384 characters) is stored as consecutive entries in order and read back as one, and no retention step trims, rewrites or drops it. Grounds in [Spec-011 §Required Behavior](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#required-behavior).
- **I-010-9** — No renderer surface settles a question or a compaction: a question card closes and the compaction affordance shows its completed state **only** from what the daemon recorded — the question's attention entry resolving; the `usage.context_compacted` row — never from a dispatch being accepted or a locally predicted value. A question card holds no countdown at all, because an agent's question waits until it is answered. Grounds in [Spec-011 §Timeline Entry Types](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#timeline-entry-types) (the question card) and [Spec-011 §Context Window and Usage Meters](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#context-window-and-usage-meters).
- **I-010-10** — A child-run summary whose detail is incomplete stays visible and says so **explicitly**: its completeness marker is required, its incomplete arm names its cause, `detail_fetch_failed`, together with the time observed, and the row's event count on that arm is a lower bound rather than a total. Incompleteness is never inferred from a low count and never rendered as absence. Grounds in [Spec-011 §Fallback Behavior](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#fallback-behavior).
- **I-010-11** — Every reply of `TimelineRead`, `ReasoningSurfaceRead`, and `ChildRunExpand` rides **one** transport message body. The bound is stated on the reply's **encoded size** against the page's own byte budget, `TIMELINE_PAGE_MAX_BYTES`, a fixed size declared apart from the substrate's 4 MB message-size limit and under it (CP-005-12), never on a row count — the row's free-form text fields and its opaque payload are each bounded independently of any count, so no count ceiling bounds the page — and it is a parse-time refusal rather than a transport-time discovery, because an oversized response cannot carry its own error and closes the connection instead. A producer that stops short of the caller's window reports `hasMore` and hands back the cursor that continues it; a terminal page may carry a cursor and is never required to. **The budget bounds aggregation and never bounds a page below one entry.** A continuing reply carries at least one entry — a page that promises more and delivers none re-offers the same cursor forever while reading like progress — so where the first candidate alone exceeds the budget the producer pages that single entry rather than answering with zero, and the reply is refused **for its size** at the response boundary, naming the member and its measured bytes on an error frame the substrate can deliver. The undeliverable row is therefore reported structurally, on every producer, and nothing oversized reaches the wire. A **terminal** page carries no such floor: an empty final page is the honest answer to a continuation whose cursor already sat at the end and to a filtered read that matched nothing. Grounds in [Spec-011 §Interfaces And Contracts](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#interfaces-and-contracts).
- **I-010-12** — A returned page is internally consistent with the header it carries: its entries never move backwards in sequence, every run-scoped entry of a `ChildRunExpand` reply belongs to the run that reply names, and a child-run summary is never its own parent. Each of the three is a schema-level refusal on the response, not a renderer convention, so a projection bug surfaces at the contract boundary rather than as a mis-ordered or misattributed surface. Grounds in [Spec-011 §Interfaces And Contracts](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#interfaces-and-contracts).
- **I-010-13** — Every timeline reply is scoped to the request that asked for it: a `TimelineRead` page contains rows of the requested session only, and a `ChildRunExpand` reply names the requested run. No response schema can state this — a schema never sees the request — so it is enforced at the daemon binder, on the caller's own parsed request. A cross-scope reply is refused as an **internal** failure and never delivered, because the caller asked a well-formed question and the daemon assembled a well-formed answer about a different subject, which correlates to the caller's own request id and is therefore indistinguishable from a correct answer. **Two further replies are judged against the request rather than against themselves**, and by the same mechanism for the same reason. A page may not exceed the window the caller asked for: the effective ceiling is `TimelineRead`'s own `limit` where the request named one and the default row ceiling where it did not, and a response schema can bound a page only at the default, so a read for ten rows answering with the maximum is otherwise well-formed and a client sizing a viewport, a budget, or a render pass from its own request is handed more with nothing on the reply saying so — `ChildRunExpand` declares no `limit`, so its ceiling is that default, stated on the same binder so one rule covers both paged reads. And: a `ReasoningSurfaceRead` answering `available` with **no entries** is correct on a continuation whose cursor already sat at the end of the surface, and a defect on a **first** read, where it renders as a surface that exists and shows nothing — indistinguishable from the unavailable state while asserting the opposite. The response schema cannot separate the two, because the request is what separates them; it carries the half it can see (the continuing arm's non-empty floor, which is the arm that can loop) and this binder carries the half it cannot. Grounds in [Spec-011 §Interfaces And Contracts](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#interfaces-and-contracts).

## API And Transport Changes

- Add `TimelineRead`, `ReasoningSurfaceRead`, and `ChildRunExpand` to shared contracts and the typed client SDK, with the reads that complete the transcript — `timeline.bodyRead`, `timeline.patchRead` and `timeline.search`, registered through the same timeline method table — and the session's live figures and question: `session.contextSubscribe`, `session.autoCompactUpdate`, `turn.usage`, `turn.tasks`, the `question.asked` record and `question.resolve` ([Spec-011 §Interfaces And Contracts](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#interfaces-and-contracts)).
- The transcript has one live stream, the session's own `session.subscribe`; a reconnecting client resumes it by cursor, and replay windows come from `timeline.read`.
- Give all three reads the same continuation shape: `TimelineReadRequest`, `ReasoningSurfaceReadRequest`, and `ChildRunExpandRequest` each take an optional `afterCursor`, and each response carries `hasMore` with `nextCursor` **required** on the continuing arm and optional on the terminal one — the asymmetry deliberate, so a caller moving from a completed read to `session.subscribe` has an after-cursor to hand it wherever the daemon has one. The reasoning surface takes the split inside its `available` state only; `unavailable` carries no continuation, having no entries to continue.
- Bound every page on its **encoded size** against its own byte budget, `TIMELINE_PAGE_MAX_BYTES` — a 1,000,000-byte reply less a reserve — declared apart from the substrate's 4 MB message-size limit (CP-005-12) and under it, so a page never grows with the transport limit; checked once per reply and paired with the existing row ceiling, with the producer's page fill stopping at whichever trips first. The reserve the budget subtracts is likewise derived from enforced rules rather than assumed ones: the echoed request `id` is bounded at the request boundary by Plan-005 (CP-005-12), so no id the substrate accepted can displace a page this budget sized. A row-count ceiling alone cannot carry this: `TimelineRow` mirrors the canonical event envelope's unbounded `payload` record, and even excluding it the ceiling's worst case over the row's independently-bounded free-form text fields exceeds the budget outright.
- The timeline row model carries an optional single-field `superseded` marker — `{targetPosition}`, present exactly when the row's turn is superseded, absence meaning current; the marker's run identity and source epoch are the containing row's own `runId` + `epoch`, so no duplicated fields exist to disagree and live marking is identical to replay marking by construction — identical on `TimelineRead` windows and on live delivery ([API Payload Contracts](../architecture/contracts/api-payload-contracts.md) mirrors the shape); run-scoped rows are the required-attribution variant `RunScopedTimelineEntry` — `runId` + `position` + `epoch` all required, all-or-none by construction, a partial row failing SDK schema parse (the projection-resolved originating run position and execution epoch — Plan-002 T3.16's uniform row-to-turn assignment and row attribution; the session `sequence` is never a run position, and reused ordinals mean `position` can never recover the epoch) — and every timeline surface returns the `TimelineRow` union, genuinely discriminated on the literal `kind` field (`rollback_boundary` | `run` | `general` — consumers narrow structurally on `row.kind`, never probing the free-form `type`), whose boundary arm is the typed `TimelineRollbackBoundary` (payload validated into the `RunRolledBackEvent` shape at projection; the SDK parser hands consumers the narrowed arm, never a cast) carrying the rewind cutoff, the comparands of the live-stream client rule: cached rows of that run with `position` above it mark — each marker just the boundary's cutoff against the row's own identity, identical to replay by construction — and rows delivered after the boundary arrive marker-precomputed — a late straggler pre-marked exactly when its stamped attribution ranks above the run's effective lineage-minimum cutoff for its epoch, current within the surviving history; new-epoch rows unmarked — per [Spec-011 §Required Behavior](../specs/011-live-timeline-visibility-and-reasoning-surfaces.md#required-behavior).

### Phase 1 — Timeline Contracts

**Precondition:** none. Implementation Step 1; gates both parallel legs §Parallelization Notes names ("once row schemas are fixed").

#### Tasks

- **T1.1** — Define the `TimelineRow` discriminated union in `packages/contracts/src/timeline/` — arms `TimelineRollbackBoundary` | `RunScopedTimelineEntry` | `TimelineEntry`, genuinely discriminated on the literal `kind` field, mirroring [API Payload Contracts](../architecture/contracts/api-payload-contracts.md). `RunScopedTimelineEntry` requires `runId` + `position` + `epoch` all-or-none with the optional single-field `superseded` marker. The `general` arm's refusal is three-legged per I-010-1 — the closed `run_lifecycle` category, the derived census of `Spec-005` types whose registered payload names a run unconditionally, and the row's own payload naming one under `runId` or the intervention family's `targetRunId` — with the census **derived from Plan-004's per-category type arrays** rather than transcribed. The `run` arm additionally refuses a payload whose echoed run identity — under **either** spelling, `runId` or `targetRunId` — or whose echoed `sourceEpoch` / `sourcePosition` disagrees with the row's own outer triple, per I-010-3; the run-identity half of that check reads the same exported key list the general arm's third leg reads, so the two guards cannot drift apart.
  - **Spec coverage:** Spec-011 §Timeline Entry Types
  - **Verifies invariant:** I-010-1, I-010-3
- **T1.2** — Define `ChildRunSummary` (`runId`, `parentRunId`, `state`, `eventCount`, `completeness`) in `packages/contracts/src/timeline/`, mirroring [API Payload Contracts](../architecture/contracts/api-payload-contracts.md). `completeness` is a **required** discriminated union on `state`: `complete` carries nothing else, `incomplete` requires both `cause` — always `detail_fetch_failed` — and `observedAt`. A Zod `discriminatedUnion` with strict arms, so a complete row cannot carry a cause and an incomplete one cannot omit it.
  - **Spec coverage:** Spec-011 §Timeline Entry Types
  - **Verifies invariant:** I-010-10
  - **Tests:** the complete arm round-trips; the one cause round-trips on the incomplete arm; an absent `completeness` fails; the incomplete arm without `cause` or without `observedAt` fails; a cause outside the set fails; a `state` outside the two arms selects no arm; the complete arm carrying `cause` or `observedAt` fails strict parse; a non-ISO `observedAt` fails.
- **T1.3** — Define `ReasoningSurfaceReadRequest` / `ReasoningSurfaceReadResponse` in `packages/contracts/src/timeline/` — the response a closed discriminated union on `availability: 'available' | 'unavailable'` mirroring [API Payload Contracts](../architecture/contracts/api-payload-contracts.md): `available` requires the bounded `reasoningEntries` and `unavailable` carries none — a Zod `discriminatedUnion` with strict arms, so no two states serialize identically and a state-inconsistent field set fails parse. The request takes an optional `afterCursor` and the `available` state splits again on `hasMore` — a nested `discriminatedUnion` inside the outer one — `nextCursor` required where more remains and **at least one entry** required with it, since a page that promises more and delivers none re-offers the same cursor forever. The terminal arm carries neither requirement: an empty final page is how a continuation says it reached the end of a surface that does exist, which `unavailable` would misstate. The floor that remains — an empty `available` page on a **first** read, which collapses onto `unavailable` while asserting the opposite — cannot be a schema rule, because only the request separates a first read from a continuation; it is enforced at the daemon binder under I-010-13 (T1.4). The `unavailable` state carries no continuation members at all, having no entries to continue, so a paging field on them fails strict parse rather than reading as an empty remainder. The request is strict, so the `cursor` spelling is refused rather than ignored: the member is `afterCursor` on all three reads, matching `TimelineReadRequest`.
  - **Spec coverage:** Spec-011 §Interfaces And Contracts
  - **Verifies invariant:** I-010-7, I-010-11
  - **Tests:** each state round-trips; `available` without `reasoningEntries` fails; entries on `unavailable` fail strict parse; an `available: boolean` field fails parse (no tolerant fallback arm); the `available` state without `hasMore` fails; `hasMore: true` without `nextCursor` fails while `hasMore: false` parses with and without one; `hasMore: true` with an empty entry list fails and the same page with one entry parses; `hasMore: false` with an empty entry list parses; a continuation member on the `unavailable` state fails; a request spelling the cursor `cursor` fails.
- **T1.4** — Register the first timeline method strings — `timeline.read`, `timeline.reasoningSurfaceRead`, `timeline.childRunExpand` — in the [Timeline Method-Name Registry](../architecture/contracts/api-payload-contracts.md#timeline-method-name-registry) and against the daemon IPC `MethodRegistry`, so every operation's method string resolves and not merely its schema name. The query binder additionally enforces **request scope** on the way out (I-010-13): it wraps its handler so a `TimelineRead` page of another session's rows and a `ChildRunExpand` reply naming another run are refused before the registry sees the value, reusing the substrate's own `invalid_result` result-validation code so the refusal lands as `-32603` with the offending coordinates in `data.fields.issues` and mints no error code. The same binder carries two checks that are about the request rather than the reply's subject. A page exceeding the window the caller asked for — the request's own `limit` where it named one, the default row ceiling where it did not, and that same default for the expansion, whose request declares no limit — is refused, which no response schema can do, since the caller's number is on the request.
