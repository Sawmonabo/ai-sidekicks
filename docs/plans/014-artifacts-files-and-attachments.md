## Goal

Implement immutable artifact publication, attachment ingestion, and manifest-first visibility handling across local and shared session contexts.

## Scope

This plan covers artifact ids and manifests, attachment ingest, payload storage, visibility classification, shared-replication state, and (per the 2026-07-08 scope growth) the cross-node artifact relay: eager-pin ciphertext upload, authenticated `(participant, node)`-scoped fetch with ack-driven delivery, refcount/TTL GC with quota accounting, and erasure fan-out.

## Non-Goals

- Full artifact preview UX
- Notification behavior for artifact publication
- Remote object-store vendor selection

## Invariants

- **I-014-1 (Immutability):** A published artifact's payload is content-addressed (SHA-256) and never mutated in place; a live workspace path is never treated as durable payload identity. (Spec-014 line 50; verified by Task 2, Task 3.)
- **I-014-2 (Derivative-not-mutation):** A redacted/summarized shareable form is a separate manifest (own id, `subject` → original); the original manifest is never UPDATEd in place. (Spec-014 line 147; verified by Task 4.)
- **I-014-3 (Relay ciphertext-only):** No relay-side store (Postgres coordination rows or object-store chunks) ever holds plaintext payload or an unwrapped CEK; every relay-held key is wrapped to a durable per-`(participant, node)` artifact-encryption key the relay does not possess. (Spec-014 §Cross-Node Artifact Relay (V1) Required Behavior; verified by Task 7, Task 8.)
- **I-014-4 (Loud integrity):** A chunk failing its signed-manifest digest is rejected and re-requested; an unwrapped CEK failing the signed `cekCommitment` refuses decrypt; a payload failing the post-decrypt CAS digest surfaces an integrity error — no code path yields silently-wrong bytes. (Spec-014 §Cross-Node Artifact Relay (V1) failure modes; verified by Task 8.)
- **I-014-5 (Pinned means available):** `replicationStatus` reaches `pinned` only after every ciphertext chunk is relay-acknowledged **and the upload finalize has verified the assembled ciphertext against the digest declared at upload-init** (the CAS key is verified, never trusted; a re-pin re-verifies the stored copy, so re-publish repairs at-rest corruption), and a `pinned` artifact's fetch path never depends on publisher reachability; publishes that cannot pin surface `over_cap` / `quota_exceeded` on the manifest (no blob row exists for them) — never a silent local-only fallback. (Spec-014 §Cross-Node Artifact Relay (V1); verified by Task 7, Task 9.)
- **I-014-6 (Durable-key wrap):** A relay CEK is wrapped only to a durable artifact-encryption key (daemon-local `artifact_encryption_keys`, Spec-022 master-key custody, Ed25519-identity-attested) — never to an ADR-010 session-ephemeral X25519 key; a recipient daemon restarted between publish and fetch still unwraps its relay-held CEK, thumbprint-selected. (Spec-014 Publish step 3 + §Resolved Questions 2026-07-09; verified by Task 7, Task 8.)
- **I-014-7 (Per-node delivery):** Delivery tracking and the refcount-zero GC trigger operate at `(participant, node)` granularity — one participant's fetch on one node never truncates another of their nodes' pending delivery; erasure removes all of a participant's node rows in one participant-keyed statement. (Spec-014 Delete steps 8–9; verified by Task 9, Task 10.)
- **I-014-8 (Ack-driven delivery):** `delivered_at` is written **only** by an authenticated `ArtifactFetchComplete` ack sent after the fetching node's chunk-manifest, `cekCommitment`, and CAS verifications all succeed — never inferred from a chunk GET; an un-acked fetch leaves the blob to its TTL rather than risking a premature GC of the last relay copy. The acked row is resolved from the fetch token's own `(participant, node)` claims (I-014-10), never from a caller-supplied node id, and the ack is idempotent. (Spec-014 Fetch step 6 + Delete step 8; verified by Task 8, Task 9.)
- **I-014-9 (Rotation retains):** A retired artifact-encryption key is retained (thumbprint-keyed, never used for new wraps) until every relay row wrapped to it is delivered or TTL-expired, so rotation never strands a within-TTL pinned blob behind an offline publisher; exactly one active key exists per participant per node. (Spec-014 Publish step 3; verified by Task 7, Task 8.) The daemon evaluates the retention predicate locally as `retired_at + 30 d + a 48 h skew margin` (the `extended`-tier TTL ceiling bounds it on the relay clock; the margin absorbs daemon-vs-relay skew) rather than querying the relay. The rule's second leg is **no late wraps**: rotation immediately re-attests the new active key to session peers and publishers wrap to the latest attestation per `(participant, node)`, so a wrap to a retired thumbprint is confined to the seconds-scale re-attestation race and every row bearing it TTL-expires inside the purge bound — a session-frozen attestation cache would let stale wraps outlive the purge.
- **I-014-10 (Node-bound fetch authorization):** A relay fetch token is scoped to `(participant, node)`, the binding made at mint per RFC 9449 §5: the issuer resolves `node_id` from the authenticated node-attach context of the `ArtifactFetchAuthorize` call, stamps `(participant, node)` as issuer-signed token claims, and sets the `cnf` confirmation claim from that call's DPoP proof — never from a client-supplied request field, and with no standing thumbprint→node registry (a bare `cnf`/jkt thumbprint is possession material, not an identity). The relay selects the wrapped CEK and resolves the `ArtifactFetchComplete` target row from the issuer-signed claims after verifying possession, so one node can neither read a sibling node's wrapped CEK nor mark that sibling delivered. (Spec-014 Fetch steps 5–6; verified by Task 8.)

Cloudflare) for the resumable-upload substrate versus minimal bespoke chunk endpoints — the crypto/manifest/authorization envelope is ours either way; the evaluation criteria are the standing four (correctness, modern practice, regression surface, vulnerability surface) plus dependency health. **Assertion:** a publish within cap yields relay rows with every chunk stored and `replication_status='pinned'`; a node that attached before the publish but never fetched anything is in the wrapped-key recipient set (keygen + attestation happened at its attach, not lazily); killing the uploader mid-transfer and re-running resumes from the received-set without re-sending acknowledged chunks; an over-cap publish uploads nothing and surfaces `over_cap`; a finalize whose assembled digest mismatches the declaration is rejected and never pins; a re-pin against a corrupted stored blob discards it and re-uploads; a publish after a peer's rotation wraps to the peer's new key (re-attestation replaced the cache), while a publish racing the in-flight re-attestation wraps to the retired key and stays fetchable until delivered/TTL — inside the purge bound; a late joiner granted access by re-publish receives a current-epoch `artifact.published` event and verifies the fetch end-to-end against it; the publishing node has no recipient row of its own (no blob's refcount waits on its publisher); a solo-session publish uploads nothing, retains the CEK, and stays `pending_replication`, and the re-publish after the first peer attaches performs the initial pin that the peer then fetches end-to-end. **Spec coverage:** Spec-014 §Cross-Node Artifact Relay (V1) Publish steps 1–4, size/quota table. **Verifies invariant:** I-014-3, I-014-5. **Consumes:** durable artifact-encryption keys ← `artifact_encryption_keys` (Spec-022 master-key custody); attestation transport ← Plan-008 R4 pairwise-encrypted relay channels; `artifact.published` event append ← Plan-006 `EventLogService.append`.

- **Task 8 — Authenticated relay fetch + integrity (2026-07-08 growth).** Implement the fetch half: `ArtifactFetchAuthorize` mints a `(participant, node)`-scoped, DPoP-bound (RFC 9449), 5–15 min PASETO fetch token against session membership — `node_id` resolved by the issuer from the mint call's authenticated node-attach context and stamped as issuer-signed claims, `cnf` bound from that call's DPoP proof per RFC 9449 §5, never a client-supplied field (I-014-10) (consumes `packages/crypto-paseto` primitives ← Plan-025 Tier 1 Partial, shipped Tier 1; issuer-integration seam pinned at the audit delta); per-chunk authenticated GETs verify each chunk against the signed manifest on arrival (reject + re-request on mismatch), unwrap the CEK returned by `ArtifactFetchAuthorize` with the thumbprint-selected durable artifact key from `artifact_encryption_keys` (I-014-6 — unwrap works after daemon restart because the key survives in the master-key-wrapped store), verify it against the signed `cekCommitment` before decrypt, decrypt, verify the whole-payload CAS digest, and only then send the authenticated `ArtifactFetchComplete` ack — the sole writer of `delivered_at`, which also releases the fetch grace lease (I-014-8; the relay never infers delivery from a chunk GET). The relay resolves the acked row as `(ciphertext_digest, participant_id, node_id)` from the digest plus the token's own claims, and the write is idempotent (a replayed ack is a no-op returning success). Non-member, expired-token, and unbound-DPoP fetches are refused with `artifact.fetch_unauthorized`; a member with no recipient row (post-publish joiner) receives the reserved `artifact.no_access_key` (404) error — distinct from the 403, so clients surface the re-publish remedy. **Assertion:** a participant on a second node fetches and verifies a pinned artifact with the publishing daemon stopped; a recipient daemon restarted between publish and fetch still unwraps (durable key, not session-ephemeral); a corrupted chunk is re-requested and the fetch still completes; a tampered whole-payload fails post-decrypt with a loud integrity error; a wrapped CEK failing the `cekCommitment` check refuses decrypt; a fetcher killed after its last chunk GET but before verification leaves `delivered_at` NULL and the blob intact; a node that rotated its artifact key still unwraps a blob pinned to its retired key; a non-member token mint is refused; a post-publish joiner's fetch fails with `artifact.no_access_key`, not `artifact.fetch_unauthorized`; a token minted for node A cannot fetch node B's wrapped CEK nor ack node B's row (the sibling-node attack — B's `delivered_at` stays NULL and the blob survives); a replayed ack is an idempotent no-op. **Spec coverage:** Spec-014 §Cross-Node Artifact Relay (V1) Fetch steps 5–6, failure modes (digest mismatch, publisher offline). **Verifies invariant:** I-014-3, I-014-4, I-014-10.

- **Task 9 — Relay GC, quotas, and backpressure (2026-07-08 growth).** Implement the lifecycle half of `artifact-relay-service.ts`: refcount-zero delete (all `delivered_at` set across every `(participant, node)` recipient row, each written only by that node's `ArtifactFetchComplete` ack — I-014-7 + I-014-8: neither a sibling node's fetch nor a bare chunk GET advances delivery), hourly TTL sweep over `expires_at`, 90%-of-`node_relay_storage_max` watermark eviction (delivered/nearest-TTL first), incomplete-upload reaping at `incomplete_upload_ttl`, grace-lease respect (no eviction while a lease is live), per-session/per-participant byte-quota accounting, and `429` + `Retry-After` backpressure per the six Spec-021 relay rows. **Assertion:** the last intended recipient's _acked_ fetch deletes the blob and its recipient rows, while an identical fetch that never acks leaves them until TTL; an expired-TTL blob is swept and a subsequent fetch returns the explicit expired/unavailable error; an in-flight lease blocks eviction until released; an over-quota upload receives `429` with `Retry-After` and the publish degrades to `quota_exceeded`. **Spec coverage:** Spec-014 §Delete steps 8, size/quota/retention table, failure modes (relay full, mid-fetch expiry, publisher dies mid-upload, recipient crashes before verifying). **Verifies invariant:** I-014-5, I-014-8. **Consumes:** Spec-021 registry rows (`artifact.upload.*`, `artifact.fetch.*`) ← Plan-021 enforcement substrate.

- **Task 10 — Erasure fan-out + degraded-status surfaces (2026-07-08 growth).** Ship the CP-014-2 Path-2 reciprocal: participant erasure DELETEs their daemon-local `artifact_encryption_keys` row (the Path-1 half — the durable artifact key's only copy) and hard-DELETEs their `artifact_relay_recipients` rows across all their nodes in one participant-keyed statement (the Path-2 half; together the crypto-shred, I-014-7), relies on `ON DELETE SET NULL` for `artifact_relay_blobs.publisher_participant_id`, fans out to every relay node holding the blob, and emits the erasure audit event without logging keys or plaintext; verify the deployment satisfies one of the two Spec-014 §State And Data Implications backup mechanisms (PITR window ≤ erasure SLA, or separately-destroyable KEK). Surface `replicationStatus` in the desktop artifacts views (Task 6 tree): pinned/pending, and the explicit "unavailable while the publisher is offline" state for `over_cap`/`quota_exceeded`/`expired`. **Assertion:** erasing a participant removes their local `artifact_encryption_keys` row and exactly their recipient rows (others' delivery state untouched), decrements the intended-recipient set so refcount semantics stay consistent, and emits the audit event; an erased participant's fetch authorization is refused; the desktop view renders the degraded status for an over-cap artifact. **Spec coverage:** Spec-014 §Delete step 9, failure modes (participant erased mid-life, over-cap), acceptance criteria (erasure, degraded status). **Verifies invariant:** I-014-2 pattern (no in-place mutation of others' rows), I-014-3. **Consumes:** erasure orchestration contract ← Plan-022 CP-022-6 (Plan-022 orchestrates; this plan owns its table dispositions).

## Ratified Design Decisions (Tier-7 audit)

- **D-014-1 — The OCI manifest envelope is realized as dedicated `artifact_manifests` columns + a named `ArtifactManifest` wire shape.** Spec-014:78 specifies an OCI-inspired envelope (`subject`, `size`, `annotations`, `digest`=content_hash). The audit authored `artifact_manifests.subject` (self-referential FK), `size_bytes`, and `annotations` columns (local-sqlite-schema.md) and the matching `ArtifactManifest` wire shape (api-payload-contracts.md), plus the CP-014-1 obligation that Plan-011's `diff_artifacts.artifact_manifest_id` FK references. This is a NEW contract surface — it is why Plan-014 was flipped to `review` and re-promoted only on ratification.
- **D-014-2 — `annotations` is a dedicated OCI string→string column, not folded into freeform `metadata`.** The OCI `annotations` map is a first-class manifest property ([OCI image-manifest spec](https://github.com/opencontainers/image-spec/blob/main/manifest.md)); it gets its own `artifact_manifests.annotations` column and a distinct `ArtifactManifest.annotations` wire field so the at-rest shape is 1:1 with the wire, while `metadata` stays purely freeform daemon-side provenance.
- **D-014-3 — `ArtifactPublish`/`ArtifactRead` compose a single named `ArtifactManifest`; publish embeds the manifest metadata (no `manifestUrl` pointer).** Spec-014:74 mandates that publish return "artifact id **and** manifest metadata"; the prior `manifestUrl` pointer was drift from that clause (Spec-014:75 grants handle/inline latitude to the _payload_ on `ArtifactRead` only, never to the manifest). The wire now embeds `manifest: ArtifactManifest` on publish and `manifest` + `payloadHandle?`/`payload?` on read; producer inputs (`subject?`, `annotations?`) are accepted at publish so the `annotations` column and derivative `subject` are not write-dead. Aligns the wire to the spec — not a new owner decision.
- **D-014-4 — The `artifactType` discriminator is a closed six-value union: `file | diff | summary | log | design | workflow_output`.** Spec-014:41 enumerates five families (`summary` covers the plan/summary family); the audit adds `workflow_output` (the Spec-017:237 Tier-8 workflow phase-output type) as an additive sixth value. The Required-Behavior families list admits "at least" the five, so this is an additive discriminator value, not a families-list rewrite. The closed typed union is the contract (api-payload-contracts.md `ArtifactType`); the schema CHECK mirrors it (`CHECK(artifact_type IN ('file','diff','summary','log','design','workflow_output'))`).
