## Goal

Implement immutable artifact publication, attachment ingestion, and manifest-first visibility handling across local and shared session contexts.

## Scope

This plan covers artifact ids and manifests, attachment ingest, payload storage, visibility classification, shared-replication state, and (per the 2026-07-08 scope growth) the cross-node artifact relay: eager-pin ciphertext upload, authenticated `(participant, node)`-scoped fetch with ack-driven delivery, refcount/TTL GC with quota accounting, and erasure fan-out.

## Non-Goals

- Full artifact preview UX
- Notification behavior for artifact publication
- Remote object-store vendor selection

## Invariants

- **I-014-1 (Immutability):** A published artifact's payload is content-addressed (SHA-256) and never mutated in place; a live workspace path is never treated as durable payload identity. (`Spec-014 §Required Behavior`; verified by Task 2, Task 3.)
- **I-014-2 (Derivative-not-mutation):** A redacted/summarized shareable form is a separate manifest (own id, `subject` → original); the original manifest is never UPDATEd in place. (`Spec-014 §State And Data Implications`; verified by Task 4.)
- **I-014-3 (Relay ciphertext-only):** No relay-side store (Postgres coordination rows or object-store chunks) ever holds plaintext payload or an unwrapped CEK; every relay-held key is wrapped to a durable per-`(participant, node)` artifact-encryption key the relay does not possess. (`Spec-014 §Cross-Node Artifact Relay (V1)` Required Behavior; verified by Task 7, Task 8.)
- **I-014-4 (Loud integrity):** A chunk failing its signed-manifest digest is rejected and re-requested; an unwrapped CEK failing the signed `cekCommitment` refuses decrypt; a payload failing the post-decrypt CAS digest surfaces an integrity error — no code path yields silently-wrong bytes. (`Spec-014 §Cross-Node Artifact Relay (V1)` failure modes; verified by Task 8.)
- **I-014-5 (Pinned means available):** `replicationStatus` reaches `pinned` only after every ciphertext chunk is relay-acknowledged **and the upload finalize has verified the assembled ciphertext against the ciphertext digest declared at upload-init** (the relay's CAS key — never the plaintext CAS digest, which the relay cannot compute; the CAS key is verified, never trusted; a re-pin re-verifies the stored copy, so re-publish repairs at-rest corruption, and re-anchors `expires_at` to the tier TTL — a fresh grant of the same bytes), and a `pinned` artifact's fetch path never depends on publisher reachability; publishes that cannot pin surface `over_cap` / `quota_exceeded` on the manifest (no blob row exists for them) — never a silent local-only fallback. (`Spec-014 §Cross-Node Artifact Relay (V1)`; verified by Task 7, Task 9.)
- **I-014-6 (Durable-key wrap):** A relay CEK is wrapped only to a durable artifact-encryption key (daemon-local `artifact_encryption_keys`, Spec-022 master-key custody, Ed25519-identity-attested) — never to an ADR-010 session-ephemeral X25519 key; a recipient daemon restarted between publish and fetch still unwraps its relay-held CEK, thumbprint-selected. (Spec-014 Publish step 3 + §Resolved Questions 2026-07-09; verified by Task 7, Task 8.)
- **I-014-7 (Per-node delivery):** Delivery tracking and the refcount-zero GC trigger operate at `(participant, node)` granularity — one participant's fetch on one node never truncates another of their nodes' pending delivery; erasure removes all of a participant's node rows in one participant-keyed statement. (Spec-014 Delete steps 8–9; verified by Task 9, Task 10.)
- **I-014-8 (Ack-driven delivery):** `delivered_at` is written **only** by an authenticated `ArtifactFetchComplete` ack sent after the fetching node's chunk-manifest, `cekCommitment`, and CAS verifications all succeed — never inferred from a chunk GET; an un-acked fetch leaves the blob to its TTL rather than risking a premature GC of the last relay copy. The acked row is resolved from the fetch token's own `(participant, node)` claims (I-014-10), never from a caller-supplied node id, and the ack is idempotent. (Spec-014 Fetch step 6 + Delete step 8; verified by Task 8, Task 9.)
- **I-014-9 (Rotation retains):** A retired artifact-encryption key is retained (thumbprint-keyed, never used for new wraps) until every relay row wrapped to it is delivered or TTL-expired, so rotation never strands a within-TTL pinned blob behind an offline publisher; exactly one active key exists per participant per node. (Spec-014 Publish step 3; verified by Task 7, Task 8.) The daemon evaluates the retention predicate locally as `retired_at + 30 d + a 48 h skew margin` (the `extended`-tier TTL ceiling bounds it on the relay clock; the margin absorbs daemon-vs-relay skew) rather than querying the relay. The rule's second leg is **no late wraps**: rotation immediately re-attests the new active key to session peers and publishers wrap to the latest attestation per `(participant, node)`, so a wrap to a retired thumbprint is confined to the seconds-scale re-attestation race and every row bearing it TTL-expires inside the purge bound — a session-frozen attestation cache would let stale wraps outlive the purge.
- **I-014-10 (Node-bound fetch authorization):** A relay fetch token is scoped to `(participant, node)`, the binding made at mint per RFC 9449 §5: the issuer stamps `(participant, node)` as issuer-signed token claims, and sets the `cnf` confirmation claim from that call's DPoP proof, with no standing thumbprint→node registry (a bare `cnf`/jkt thumbprint is possession material, not an identity). **What the invariant prohibits, precisely** (narrowed 2026-08-08 at round 3): the node-claim **value** is always **issuer-derived from the caller's own attach-state rows** and a **client-supplied raw node identity is never trusted**. It does _not_ prohibit a request field as such — a **validated opaque selector that picks among the caller's own attachment rows** is permissible if the deferred audit adopts one, because the issuer still derives the value and still refuses any row not owned by the authenticated `sub` (this is what keeps the invariant compatible with Task 8's recorded `attachmentId` candidate). The relay selects the wrapped CEK and resolves the `ArtifactFetchComplete` target row from the issuer-signed claims after verifying possession, so a node presenting a token minted for itself can neither read a sibling node's wrapped CEK nor mark that sibling delivered. **Mint-time authorization is participant-granular, not node-granular** (scoped 2026-08-08 — the prior wording, "the authenticated node-attach context", named a mechanism V1 does not supply: `ArtifactFetchAuthorize` is a control-plane route whose access token carries `sub` and `cnf` and no node claim, and **V1 defines no node-identity credential** per [security-architecture.md §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature)), the same bound the Plan-006 T4.10 registrar resolves at, so a same-participant sibling daemon obtaining a token for another of that participant's nodes is not cryptographically excludable. **The V1 residual is availability and attestation/attribution integrity — not delivery attribution alone, and not confidentiality** (corrected across PR #301 rounds 1 and 3: round 0's "delivery attribution only" was too narrow, round 1's "confidentiality" was wrong). **(a) Availability:** `ArtifactFetchComplete` proves no CEK unwrap, so a compromised sibling forges the ack, clears the blob's last outstanding row, and refcount-zero GC destroys it; the honest node's own row cascades away with the blob so it does surface `artifact.no_access_key`, but that error's remedy is a publisher re-publish — unavailable in exactly the publisher-offline case the guarantee exists for. **(b) Attestation integrity (victim-node lockout):** the verifier's check is only that an attestation is signed by _a_ long-term Ed25519 identity key registered to that participant, and a participant carries several — each workstation holds its own, separately registered ([trust-and-identity.md §Edge Cases](../domain/trust-and-identity.md#edge-cases); no key is shared or copied between nodes) — so nothing binds the signing identity to the `node_id` it attests, and any participant-authorized registered identity can bind an attacker-held X25519 key to a victim node's `node_id` and receives the CEK of every artifact published after the spoof (Spec-014 Publish step 3). Neither leg widens plaintext reach — an attached sibling is already an intended recipient holding the CEK under its own attested key, and plaintext reach by an authorized node is participant-granularity sharing working as designed; the reachable harm is that the honest sibling is locked out and attribution is corrupted. Cross-participant availability and confidentiality are untouched. Spec-014 §Required Behavior, the §Failure modes publisher-offline row, and both §Acceptance Criteria rows now carry the matching threat-model scope; the closure for all three legs is the [cross-plan-dependencies.md §V1.1+ Cross-Plan Extensions](../architecture/cross-plan-dependencies.md#v11-cross-plan-extensions) Plan-014 row (added here — four rows now share the Plan-018/Plan-003 node-identity primitive). (Spec-014 Fetch steps 5–6; verified by Task 8.)

## Ratified Design Decisions (Tier-7 audit)

- **D-014-1 — The OCI manifest envelope is realized as dedicated `artifact_manifests` columns + a named `ArtifactManifest` wire shape.** `Spec-014 §Interfaces And Contracts` specifies an OCI-inspired envelope (`subject`, `size`, `annotations`, `digest`=content_hash). The audit authored `artifact_manifests.subject` (self-referential FK), `size_bytes`, and `annotations` columns (local-sqlite-schema.md) and the matching `ArtifactManifest` wire shape (api-payload-contracts.md), plus the CP-014-1 obligation that Plan-011's `diff_artifacts.artifact_manifest_id` FK references. This is a NEW contract surface — it is why Plan-014 was flipped to `review` and re-promoted only on ratification.
- **D-014-2 — `annotations` is a dedicated OCI string→string column, not folded into freeform `metadata`.** The OCI `annotations` map is a first-class manifest property ([OCI image-manifest spec](https://github.com/opencontainers/image-spec/blob/main/manifest.md)); it gets its own `artifact_manifests.annotations` column and a distinct `ArtifactManifest.annotations` wire field so the at-rest shape is 1:1 with the wire, while `metadata` stays purely freeform daemon-side provenance.
- **D-014-3 — `ArtifactPublish`/`ArtifactRead` compose a single named `ArtifactManifest`; publish embeds the manifest metadata (no `manifestUrl` pointer).** `Spec-014 §Interfaces And Contracts` mandates that publish return "artifact id **and** manifest metadata"; the prior `manifestUrl` pointer was drift from that clause (`Spec-014 §Interfaces And Contracts` grants handle/inline latitude to the _payload_ on `ArtifactRead` only, never to the manifest). The wire now embeds `manifest: ArtifactManifest` on publish and `manifest` + `payloadHandle?`/`payload?` on read; producer inputs (`subject?`, `annotations?`) are accepted at publish so the `annotations` column and derivative `subject` are not write-dead. Aligns the wire to the spec — not a new owner decision.
- **D-014-4 — The `artifactType` discriminator is a closed six-value union: `file | diff | summary | log | design | workflow_output`.** `Spec-014 §Required Behavior` enumerates five families (`summary` covers the plan/summary family); the audit adds `workflow_output` (the `Spec-017 §Output Mode Specification` Tier-8 workflow phase-output type) as an additive sixth value. The Required-Behavior families list admits "at least" the five, so this is an additive discriminator value, not a families-list rewrite. The closed typed union is the contract (api-payload-contracts.md `ArtifactType`); the schema CHECK mirrors it (`CHECK(artifact_type IN ('file','diff','summary','log','design','workflow_output'))`).
