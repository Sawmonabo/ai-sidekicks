## Goal

Implement immutable artifact publication, attachment ingestion, and manifest-first visibility handling across local and shared session contexts.

## Scope

This plan covers artifact ids and manifests, attachment ingest, payload storage, visibility classification, shared-replication state, and (per the 2026-07-08 scope growth) the cross-node artifact relay: eager-pin ciphertext upload, authenticated `(participant, node)`-scoped fetch with ack-driven delivery, refcount/TTL GC with quota accounting, and erasure fan-out.

## Non-Goals

- Full artifact preview UX
- Notification behavior for artifact publication
- Remote object-store vendor selection

## Invariants

- **I-014-1 (Immutability):** A published artifact's payload is content-addressed (SHA-256) and never mutated in place; a live workspace path is never treated as durable payload identity. (`Spec-014 §Required Behavior`; verified by Task 2, Task 3.)
- **I-014-2 (Derivative-not-mutation):** A redacted/summarized shareable form is a separate manifest (own id, `subject` → original); the original manifest is never UPDATEd in place. (`Spec-014 §State And Data Implications`; verified by Task 4, Task 12.) **Deletion inherits this:** `ArtifactDelete` on a manifest another manifest names as its `subject` is refused rather than satisfied by nulling the referent's `subject` — a null-out is exactly the in-place mutation of a foreign row this invariant prohibits, and it would silently sever the derivative's provenance chain (Task 12).
- **I-014-3 (Relay ciphertext-only):** No relay-side store (Postgres coordination rows or object-store chunks) ever holds plaintext payload or an unwrapped CEK; every relay-held key is wrapped to a durable per-`(participant, node)` artifact-encryption key the relay does not possess. (`Spec-014 §Cross-Node Artifact Relay (V1)` Required Behavior; verified by Task 7, Task 8, Task 10.)
- **I-014-4 (Loud integrity):** A chunk failing its signed-manifest digest is rejected and re-requested; an unwrapped CEK failing the signed `cekCommitment` refuses decrypt; a payload failing the post-decrypt CAS digest surfaces an integrity error — no code path yields silently-wrong bytes. (`Spec-014 §Cross-Node Artifact Relay (V1)` failure modes; verified by Task 8.)
- **I-014-5 (Pinned means available):** `replicationStatus` reaches `pinned` only after every ciphertext chunk is relay-acknowledged **and the upload finalize has verified the assembled ciphertext against the ciphertext digest declared at upload-init** (the relay's CAS key — never the plaintext CAS digest, which the relay cannot compute; the CAS key is verified, never trusted; a re-pin re-verifies the stored copy, so re-publish repairs at-rest corruption, and re-anchors `expires_at` to the tier TTL — a fresh grant of the same bytes), and a `pinned` artifact's fetch path never depends on publisher reachability; publishes that cannot pin surface `over_cap` / `quota_exceeded` on the manifest (no blob row exists for them) — never a silent local-only fallback. **Extended 2026-08-17 by the ingest-protocol hardening amendment — the converse direction is enforced too: a manifest stops claiming `pinned` once its own node observes that the pin is gone.** Either fetch-path refusal that establishes the payload is no longer obtainable — `artifact.relay_expired` (410) at the `ArtifactFetchAuthorize` mint, at a chunk GET, or on a resume after mid-fetch eviction, **or** a zero-row `artifact.no_access_key` (404), where a fetch lands once a GC path has removed the blob row and its recipient rows have cascaded away — transitions that node's own manifest row from `pinned` to `expired` in the same pass, before the error surfaces. The invariant keys on the fact rather than on either code, so it holds regardless of which lifecycle path retired the node's access. Without it `pinned` is a one-way latch on every recipient node: the relay's TTL sweep and watermark eviction run in the control plane and emit no event, so a recipient can observe expiry only by fetching, and a row left at `pinned` beside a dead blob makes this invariant's own claim — that a `pinned` artifact's fetch path never depends on publisher reachability — false of the persisted state a consumer actually reads. The write is a local single-writer update on a value the column already permits, is idempotent, applies only to a `pinned` row (a row already carrying a degraded status was never pinned), and is undone by an ordinary re-publish re-pin, so the status tracks availability rather than latching in either direction. (`Spec-014 §Cross-Node Artifact Relay (V1)`, `Spec-014 §Fetch (authenticated; relay-served in V1)`; verified by Task 7, Task 9.)
- **I-014-6 (Durable-key wrap):** A relay CEK is wrapped only to a durable artifact-encryption key (daemon-local `artifact_encryption_keys`, Spec-022 master-key custody, Ed25519-identity-attested) — never to an ADR-010 session-ephemeral X25519 key; a recipient daemon restarted between publish and fetch still unwraps its relay-held CEK, thumbprint-selected. (Spec-014 Publish step 3 + §Resolved Questions 2026-07-09; verified by Task 7, Task 8.) **Extended 2026-08-16 — the thumbprint is also the fetch selector, and therefore must be injective per recipient row.** `artifact_relay_recipients` carries at most one row per `(ciphertext_digest, participant_id, key_thumbprint)`, enforced by the unique index CP-014-6 registers, so the thumbprint set a daemon presents at `ArtifactFetchAuthorize` resolves to **exactly one** row or to none — never to an ambiguous set. This is what lets the mint derive `node_id` from the resolved row (I-014-10) instead of trusting a caller-supplied node identity: the durable key that unwraps the CEK and the key that names the row are the same key, so possession of the private half is what the whole path is keyed on. A **thumbprint is a public-key fingerprint, not a credential** — it is presented, never trusted as proof; authorization is carried by the authenticated `sub`, session membership, the DPoP proof, and the `participant_id` equality pinned inside the same predicate. Presenting another participant's thumbprint resolves zero rows, because `participant_id` is fixed to the caller's `sub` in the same lookup.
- **I-014-7 (Per-node delivery):** Delivery tracking and the refcount-zero GC trigger operate at `(participant, node)` granularity — one participant's fetch on one node never truncates another of their nodes' pending delivery; erasure removes all of a participant's node rows in one participant-keyed statement. (Spec-014 Delete steps 8–9; verified by Task 9, Task 10.)
- **I-014-8 (Ack-driven delivery):** `delivered_at` is written **only** by an authenticated `ArtifactFetchComplete` ack sent after the fetching node's chunk-manifest, `cekCommitment`, and CAS verifications all succeed — never inferred from a chunk GET; an un-acked fetch leaves the blob to its TTL rather than risking a premature GC of the last relay copy. The acked row is resolved from the fetch token's own `(participant, node)` claims (I-014-10), never from a caller-supplied node id, and the ack is idempotent. (Spec-014 Fetch step 6 + Delete step 8; verified by Task 8, Task 9.)
- **I-014-9 (Rotation retains):** A retired artifact-encryption key is retained (thumbprint-keyed, never used for new wraps) until every relay row wrapped to it is delivered or TTL-expired, so rotation never strands a within-TTL pinned blob behind an offline publisher; exactly one active key exists per participant per node. (Spec-014 Publish step 3; verified by Task 7, Task 8.) The daemon evaluates the retention predicate locally as `retired_at + 30 d + a 48 h skew margin` (the `extended`-tier TTL ceiling bounds it on the relay clock; the margin absorbs daemon-vs-relay skew) rather than querying the relay. The rule's second leg is **no late wraps**: rotation immediately re-attests the new active key to session peers and publishers wrap to the latest attestation per `(participant, node)`, so a wrap to a retired thumbprint is confined to the seconds-scale re-attestation race and every row bearing it TTL-expires inside the purge bound — a session-frozen attestation cache would let stale wraps outlive the purge. **Third leg, added 2026-08-16 with the thumbprint selector — a re-pin UPDATEs the recipient row in place rather than adding one.** The recipient row's primary key is `(ciphertext_digest, participant_id, node_id)`, which the thumbprint is deliberately **not** part of, so a re-publish to a node that has since rotated must UPSERT on that key — replacing `wrapped_cek` and `key_thumbprint` — never INSERT. An INSERT violates the primary key, and a second row for one node would break I-014-7's per-node refcount by making one node's delivery need two acks. The consequence for this invariant is a **narrowing**: the retained retired key must cover exactly those rows no re-publish has since moved off its thumbprint, not every row ever wrapped to it, because a re-pinned row is now readable under the node's current active key and the retired key is irrelevant to it. Retention is still evaluated on the local `retired_at + 30 d + 48 h` predicate — the narrowing shrinks what is at risk, never the window.
- **I-014-10 (Node-bound fetch authorization):** A relay fetch token is scoped to `(participant, node)`, the binding made at mint per RFC 9449 §5: the issuer stamps `(participant, node)` as issuer-signed token claims, and sets the `cnf` confirmation claim from that call's DPoP proof, with no standing thumbprint→node registry (a bare `cnf`/jkt thumbprint is possession material, not an identity). **What the invariant prohibits, precisely** (narrowed 2026-08-08 at round 3): the node-claim **value** is always **issuer-derived from the caller's own attach-state rows** and a **client-supplied raw node identity is never trusted**. It does _not_ prohibit a request field as such — a **validated opaque selector that picks among the caller's own attachment rows** is permissible if the deferred audit adopts one, because the issuer still derives the value and still refuses any row not owned by the authenticated `sub` (this is what keeps the invariant compatible with Task 8's recorded `attachmentId` candidate). The relay selects the wrapped CEK and resolves the `ArtifactFetchComplete` target row from the issuer-signed claims after verifying possession, so a node presenting a token minted for itself can neither read a sibling node's wrapped CEK nor mark that sibling delivered. **Mint-time authorization is participant-granular, not node-granular** (scoped 2026-08-08 — the prior wording, "the authenticated node-attach context", named a mechanism V1 does not supply: `ArtifactFetchAuthorize` is a control-plane route whose access token carries `sub` and `cnf` and no node claim, and **V1 defines no node-identity credential** per [security-architecture.md §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature)), the same bound the Plan-006 T4.10 registrar resolves at, so a same-participant sibling daemon obtaining a token for another of that participant's nodes is not cryptographically excludable. **The V1 residual is availability and attestation/attribution integrity — not delivery attribution alone, and not confidentiality** (corrected across PR #301 rounds 1 and 3: round 0's "delivery attribution only" was too narrow, round 1's "confidentiality" was wrong). **(a) Availability:** `ArtifactFetchComplete` proves no CEK unwrap, so a compromised sibling forges the ack, clears the blob's last outstanding row, and refcount-zero GC destroys it; the honest node's own row cascades away with the blob so it does surface `artifact.no_access_key`, but that error's remedy is a publisher re-publish — unavailable in exactly the publisher-offline case the guarantee exists for. **(b) Attestation integrity (victim-node lockout):** the verifier's check is only that an attestation is signed by _a_ long-term Ed25519 identity key registered to that participant, and a participant carries several — each workstation holds its own, separately registered ([trust-and-identity.md §Edge Cases](../domain/trust-and-identity.md#edge-cases); no key is shared or copied between nodes) — so nothing binds the signing identity to the `node_id` it attests, and any participant-authorized registered identity can bind an attacker-held X25519 key to a victim node's `node_id` and receives the CEK of every artifact published after the spoof (Spec-014 Publish step 3). Neither leg widens plaintext reach — an attached sibling is already an intended recipient holding the CEK under its own attested key, and plaintext reach by an authorized node is participant-granularity sharing working as designed; the reachable harm is that the honest sibling is locked out and attribution is corrupted. Cross-participant availability and confidentiality are untouched. Spec-014 §Required Behavior, the §Failure modes publisher-offline row, and both §Acceptance Criteria rows now carry the matching threat-model scope; the closure for all three legs is the [cross-plan-dependencies.md §V1.1+ Cross-Plan Extensions](../architecture/cross-plan-dependencies.md#v11-cross-plan-extensions) Plan-014 row (added here — four rows now share the Plan-018/Plan-003 node-identity primitive). **The rule is UNCHANGED by the 2026-08-16 key-thumbprint selector; only the mechanism that satisfies it moved, and the mint got stricter** (stated explicitly because an amendment that rewrites the selector and leaves its governing invariant silent reads as an oversight). What this invariant prohibits — a node-claim value that is anything other than issuer-derived, and any trust in a client-supplied raw node identity — is exactly as binding as before. Under the superseded `attachmentId` shape the issuer derived `node_id` from a `runtime_node_attachments` row; it now derives it from the **`artifact_relay_recipients` row the presented thumbprint set resolves**, which is still a row the issuer reads, still pinned to the caller's own `participant_id`, and still never a value the caller states. A thumbprint set is the same category of input the 2026-08-08 round-3 narrowing already ruled permissible — a validated selector over the caller's own rows — not a raw node identity. **The mint additionally gains a corroboration step it did not have:** having derived `node_id`, the issuer requires an **active-state `runtime_node_attachments` row for that `node_id`, with `participant_id` = the authenticated `sub`, in the blob's own `session_id`** (the participant leg added 2026-08-17, PR #341 round 2 — a row attesting another participant's `node_id` must fail corroboration, never mint claims describing an attachment that does not exist) before minting, so a stale recipient row for a node that has since detached no longer yields a token. That is a strict narrowing of what mints — it can only refuse more — and it is why the Plan-003 dependency edge survives as corroboration (Dependencies row). **Mint-time authorization remains participant-granular**, and the compromised same-participant-sibling residual above is untouched: the sibling holds its own durable key and its own thumbprints, so it resolves its own row exactly as designed. The selector disambiguates the caller's own nodes; it was never a defence against that residual, whose closure is still the §V1.1+ row named above. (Spec-014 Fetch steps 5–6; verified by Task 8.)

- **I-014-11 (Server-derived, bounded ingest):** For caller-supplied bytes crossing the client→daemon trust boundary — the `AttachmentIngest` trio, and a boundary-crossing `ArtifactPublish`, because the pipeline binds to the boundary rather than to a method name (a boundary-crossing publish declaring the `file` family is refused outright and directed to `AttachmentIngest`) — the daemon derives media type and size **from the payload bytes it received**, and a caller-declared `mediaType` or `sizeBytes` is advisory input that is reconciled against the derived value, never persisted as fact and never used to make an admission decision. Every bound in `Spec-014 §Ingest Validation And Payload Bounds (V1)` is applied **before** any byte reaches the CAS or any manifest row is written, so a refused payload leaves no durable artifact behind; a payload whose signature cannot be determined is refused rather than admitted on the strength of its declared type unless that type is on the signature-exempt textual allow-list **and** the bytes prove well-formed UTF-8 — in which case the recorded classification is the declared subtype admitted under the exemption, an allow-list-bounded declaration rather than trust in the declaration (fail-closed — the one arm where "unknown" must not read as "probably fine"); a payload that fails a content gate (steps 3–8) is quarantined outside the CAS with no manifest, removed at `ingest_quarantine_ttl` or earlier under the `ingest_quarantine_max_bytes` oldest-`mtime`-first eviction (an entry that cannot fit even an emptied quarantine is deleted rather than held), while a stream breaching the byte bound is terminated with its spool deleted — refused garbage, never quarantined. The other five `artifactType` families are producer-fixed and do not traverse this path **when the daemon itself produces them**; the same families arriving across the trust boundary do. **Extended 2026-08-17 by the ingest-protocol hardening amendment — "bounded" means bounded under concurrency, and "retry-safe" means retry-safe for the whole trio.** Three rules join this invariant. **(a) Completion is idempotent within its stream's lifetime.** The `AttachmentIngestComplete` response is recorded on that stream's registry entry, stamped with the committed digest, and a retry replays it verbatim — no gate re-run, no second manifest row. A lost response must not cost the caller a 100 MB re-upload, and the opposite failure is equally prohibited: re-running steps 3–8 and minting a second manifest for one completed stream. Completion surrenders the reservation, the count slot, and the spool at commit, so a completed entry pins no budget; past `max_ingest_stream_lifetime` the entry and its record are evicted and a retry takes the ordinary `artifact.ingest_stream_invalid` (409), whose named residual is one extra manifest row over a deduplicated CAS payload — never duplicated bytes, never a lost artifact. **(b) Both byte ledgers this pipeline bounds are reserve-then-install.** The aggregate admission ledger (`max_active_ingest_streams` plus the `ingest_spool_max_bytes` reservation total) and the quarantine directory (`ingest_quarantine_max_bytes`) each test and spend inside one critical section: a bound checked outside the mutation that spends it is exceeded by up to one payload per racing caller, which is the parallel-submission form of the very denial-of-disk each cap exists to stop. **(c) Every call on one `ingestId` is single-flight, and the reaper's eviction path takes the same exclusion** — sequence validation, spool append, running-count and last-chunk-digest advance, and acknowledgement are atomic per call, so an original racing its own retry cannot double-append or compare against half-updated state, and a stream is never served and evicted at once. The exclusions compose in one total acyclic order — per-`ingestId` → the admission ledger → at most one of per-`storage_path` or the quarantine directory (`Spec-014 §Implementation Notes`). A refused Init still creates nothing, and that is asserted through **admission** — the next Init admitting once a slot or reservation frees — never through an identifier the refusal never issued. (`Spec-014 §Ingest Validation And Payload Bounds (V1)`; verified by Task 11.)
- **I-014-12 (Reclaim-at-zero):** A CAS payload is reclaimed only when its derived reference count reaches zero — the count is **computed over `artifact_payload_refs.storage_path`, never stored in a counter column**, so it cannot drift out of agreement with the rows it summarizes and no reconciliation job is owed. `ArtifactDelete` removes one manifest and its own payload-ref; the shared blob survives while any other manifest still references it (the Task 2 / Task 3 dedup guarantee is exactly the case that makes this load-bearing). Reclaim is concurrency-excluded per storage key (the PR #341 round-2 fold's second tranche, 2026-08-17): every CAS writer checks-and-references inside that key's in-process exclusion, every reclaimer — the boot sweep included — derives-and-unlinks inside it, and the unlink re-derives the count after commit and aborts above zero, so no interleaving of a same-hash publish with a reclaim leaves a manifest over missing bytes. That per-key exclusion is one **leaf** of this plan's single acquisition order — per-`ingestId` → the ingest admission ledger → at most one of per-`storage_path` or the quarantine directory, the two leaves never held together (`Spec-014 §Implementation Notes`, 2026-08-17) — so the ingest path's exclusions compose with this one rather than racing or deadlocking against it; `AttachmentIngestComplete` is the path that holds a stream exclusion and then takes this leaf for its step-8 CAS rename. Deletion is refused rather than cascaded when the manifest is another manifest's `subject` (I-014-2), and a delete that destroys the last local copy of a live relay pin proceeds but must surface that re-publish is no longer possible — the publisher's plaintext is gone, so the loss is stated at the call rather than discovered at the next re-pin. (`Spec-014 §Local Artifact Deletion And CAS Reclaim (V1)`; verified by Task 12.)
- **I-014-13 (No silent attachment drop):** An attachment reference carried by any turn-scoped payload is a typed `ArtifactId`, never an opaque `unknown`, and the reference list is **order-preserving**: the position an attachment occupies on the way in is the position it occupies on the way out. An attachment that cannot be delivered — a deleted artifact (including a payload reclaimed under I-014-12), `local-only` visibility on a remote node, an over-cap payload — is rendered as an **explicit unresolved marker in its own position** and never omitted, because a silently shortened list makes the recipient reason about a message that was never sent; the marker is **cause-bearing**, naming which member of that closed union applies, because the remedies differ per cause and honest degradation beats uniform opacity. The carrier is additionally bound by `max_attachments_per_carrier`, refused as a whole rather than truncated to fit. **Extended 2026-08-17 by the ingest-protocol hardening amendment — the cause is read from persisted state, and every member of the union has a writer.** The marker's replication-status arm reads the rendering node's own `artifact_manifests.replication_status`, never live relay state the renderer cannot observe, so a cause is nameable exactly when some writer has recorded it: `pending_replication`, `over_cap`, and `quota_exceeded` are publish-path values reaching recipients through manifest-first replication, and `expired` is written by the fetching node's own relay-410 handling (I-014-5's 2026-08-17 extension). That writer is what makes the widened union's sixth member reachable rather than a token no row ever carries — and it forecloses the worse state, where an expiry-blocked attachment presents a still-`pinned` manifest matching **no** member of a closed union. (`Spec-014 §Required Behavior`, `Spec-014 §Fallback Behavior`; verified by Task 13.)

## Ratified Design Decisions (Tier-7 audit)

- **D-014-1 — The OCI manifest envelope is realized as dedicated `artifact_manifests` columns + a named `ArtifactManifest` wire shape.** `Spec-014 §Interfaces And Contracts` specifies an OCI-inspired envelope (`subject`, `size`, `annotations`, `digest`=content_hash). The audit authored `artifact_manifests.subject` (self-referential FK), `size_bytes`, and `annotations` columns (local-sqlite-schema.md) and the matching `ArtifactManifest` wire shape (api-payload-contracts.md), plus the CP-014-1 obligation that Plan-011's `diff_artifacts.artifact_manifest_id` FK references. This is a NEW contract surface — it is why Plan-014 was flipped to `review` and re-promoted only on ratification.
- **D-014-2 — `annotations` is a dedicated OCI string→string column, not folded into freeform `metadata`.** The OCI `annotations` map is a first-class manifest property ([OCI image-manifest spec](https://github.com/opencontainers/image-spec/blob/main/manifest.md)); it gets its own `artifact_manifests.annotations` column and a distinct `ArtifactManifest.annotations` wire field so the at-rest shape is 1:1 with the wire, while `metadata` stays purely freeform daemon-side provenance.
- **D-014-3 — `ArtifactPublish`/`ArtifactRead` compose a single named `ArtifactManifest`; publish embeds the manifest metadata (no `manifestUrl` pointer).** `Spec-014 §Interfaces And Contracts` mandates that publish return "artifact id **and** manifest metadata"; the prior `manifestUrl` pointer was drift from that clause (`Spec-014 §Interfaces And Contracts` grants handle/inline latitude to the _payload_ on `ArtifactRead` only, never to the manifest). The wire now embeds `manifest: ArtifactManifest` on publish and `manifest` + `payloadHandle?`/`payload?` on read; producer inputs (`subject?`, `annotations?`) are accepted at publish so the `annotations` column and derivative `subject` are not write-dead. Aligns the wire to the spec — not a new owner decision.
- **D-014-4 — The `artifactType` discriminator is a closed six-value union: `file | diff | summary | log | design | workflow_output`.** `Spec-014 §Required Behavior` enumerates five families (`summary` covers the plan/summary family); the audit adds `workflow_output` (the `Spec-017 §Output Mode Specification` Tier-8 workflow phase-output type) as an additive sixth value. The Required-Behavior families list admits "at least" the five, so this is an additive discriminator value, not a families-list rewrite. The closed typed union is the contract (api-payload-contracts.md `ArtifactType`); the schema CHECK mirrors it (`CHECK(artifact_type IN ('file','diff','summary','log','design','workflow_output'))`).
- **D-014-5 — The envelope-interior application-payload discriminator is a Plan-008-owned discriminated union with a consumer registration seam; Plan-014 registers `artifact_key_attestation` through it.** _(Ratified 2026-08-12 by the relay-scope targeted readiness-audit delta, not by the Tier-7 audit above.)_ Task 7's artifact-key attestation and Plan-008's history backfill both ride application payloads inside the one pairwise ciphertext envelope, each refusing a new relay frame message type, and neither side defined the discriminator that separates them on receipt — Task 7's attestation leg was unbuildable as written. The envelope and its frame-type surface are Plan-008's per [cross-plan-dependencies.md §2](../architecture/cross-plan-dependencies.md), so the union is **authored under Plan-008** in `packages/contracts/src/session-join.ts`: `RelayApplicationPayload`, a Zod `discriminatedUnion` over the required string tag member `kind` whose vocabulary is `RelayApplicationPayloadKind`. Plan-008's own three arms are `history_backfill_request`, `history_backfill_chunk`, and `relayed_session_event`; `HistoryBackfillEntry` is chunk-interior and carries no tag. **Unknown-kind is fail-closed** — the client coordinator's demux drops an absent or unrecognized `kind` with a logged refusal and never dispatches it. **Registration seam:** a consuming plan appends its own arm and keeps its payload schema in its own contract domain, so Plan-014's `artifact_key_attestation` arm references a schema under `packages/contracts/src/artifacts/` and Plan-008 owns only the tag, the union, and the exhaustiveness rule (CP-014-4 ⇄ Plan-008 CP-008-16). **Ratifying this from a Plan-014 delta rather than deferring it is precedented three ways:** the NS-19 Tier-7 readiness audit ratified D-025-1's hoist of the `RelayFrameType` wire enum into Plan-008's `session-join.ts` on the ground that the values are a wire-protocol fact contracts must own, without flipping Plan-008; the `SessionEventSchema` union-registration seam is the corpus's established one-owner-many-registrants shape (cross-plan-dependencies.md §2 `packages/contracts/src/` row); and CP-003-5 was registered by a delta as an additive cross-plan row plus additive unshipped exports in another plan's table without flipping that plan. All of it is additive-only and unshipped on both sides, so no version bump, no Plan-008 or Spec-008 status flip, and no Spec-008 body change.

  **Finding 1 — `AttachmentIngestComplete` is retry-idempotent (T14.11).** The round-4 dispatch contract promised that a transport failure means "retry the same call", and that was true only of `Chunk`: a lost `Complete` response left the caller holding a stream it could not name and a payload it would have to re-upload in full. Three scoping decisions kept it from becoming a general relaxation of terminal invalidation: the exception is carved for a replayed `Complete` alone (a `Chunk` on a completed stream is still the 409); completion **surrenders the reservation, count slot, and spool at commit** so a completed entry can never pin `max_active_ingest_streams` or the reservation budget, with only the record surviving; and the record shares the entry's in-memory lifetime exactly, so `max_ingest_stream_lifetime` eviction bounds replayability.
