## Goal

Implement durable local persistence, replay rebuild, and startup recovery for session execution state.

## Scope

- Operator runbook authoring
- Long-term retention tuning
- Provider-specific internal persistence formats

## Invariants

- **I-015-1 (no observable double-application; execution multiplicity is per-class):** What holds uniformly is the effect, not the execution count — naming one guarantee for both is what made every pre-2026-08-08 spelling of this entry wrong, round 1's included (Codex PR #300 rounds 1–2). **Execution multiplicity is per-class, and `Spec-015 §Idempotency Classes and Recovery Behavior` is authoritative for it rather than this entry:** the startup sweep RE-EXECUTES `idempotent` and `compensable` receipts and never re-executes `manual_reconcile_only`, which halts the affected run with a `recovery-needed` condition instead. An implementation MUST NOT suppress that retry in this invariant's name. Within a single boot the two-phase receipt commit's Phase-2 optimistic compare-and-set (`UPDATE ... SET started_at = now() WHERE started_at IS NULL`) admits exactly one claimant per receipt, so concurrent recovery workers never double-invoke — a concurrency bound, not an across-restart one. **What holds across every class is that no side effect is OBSERVABLY applied twice**, by a different mechanism per class: a `compensable` retry carries the receipt's `dedupe_key` so the remote side can reject the duplicate, and `manual_reconcile_only` is never retried at all, paying an operator escalation for that. `idempotent` is the named residual rather than a third mechanism — the spec assigns the remote half to the tool ("External deduplication (if any) is the tool's responsibility"), so what this plan holds is the driver's declared class, never a remote-side guarantee. That composite is the referent Spec-015's "enforces exactly-once semantics" names. `Spec-015 §Idempotency Protocol`, `Spec-015 §Two-Phase Receipt Commit`, `Spec-015 §Idempotency Classes and Recovery Behavior`.
- **I-015-2 (idempotent rebuild):** `ProjectionRebuild` for a session over the same canonical event range yields identical projection state regardless of how many times it runs. `Spec-015 §Interfaces And Contracts`, `Spec-015 §Acceptance Criteria`.
- **I-015-3 (no premature admission):** No mutable operation is accepted until startup recovery has restored canonical local truth or the node is in an explicit blocked/degraded state. `Spec-015 §Default Behavior`, `Spec-015 §Acceptance Criteria`.
- **I-015-4 (no silent run loss):** A persisted driver handle that cannot be resumed transitions its run to `failed` with visible recovery-failure detail; it never silently disappears or restarts as a new run. `Spec-015 §Fallback Behavior`, `Spec-015 §Acceptance Criteria`.

- [ ] **T15.5 — Resume position-compare + divergence halt-for-human (campaign B14; P1-5 with the R8 interplay guard).**
  - On every successful resume (`DriverResumeResult.status: 'resumed'` — a failed resume follows T15.3's explicit-failure arm), compare the driver-reported normalized `sessionPosition` against the daemon-recorded position derived from the local log. Both recovery attach modes — adopting a live provider session (preferred per Spec-015 §Default Behavior) and cold resume from a stored handle — traverse the single driver `resumeSession → DriverResumeResult` ingress, so the compare gates **every** successful attach: no adoption path finalizes without it (Spec-005's fresh-session sentence — "caught by this comparison rather than silently adopted"). Equal → recovery proceeds. Diverged → **the local log is authoritative** ([ADR-017 Decision Log, 2026-07-02](../decisions/017-shared-event-sourcing-scope.md#decision-log)) and the run **halts for human action**: it enters `waiting_for_input` carrying `recovery-needed` together with the daemon-derived `RecoverySpanClassification` of the diverged span — derived **direction-aware**: a daemon-ahead span (provider behind; the span is daemon-recorded events the provider is missing) folds the span's daemon-recorded content (receipt `idempotency_class` values and event kinds) — reads only → `read_only`; writes all idempotent/compensable → `idempotent_write`; any `manual_reconcile_only` or side-effecting content of unknown class → `irreversible`; a **provider-ahead** span (`sessionPosition` above the daemon-recorded position) exists only provider-side with no daemon-recorded content to fold and is `unclassifiable` **by construction** — never vacuously `read_only`; any otherwise-underivable span → `unclassifiable`, handled **exactly as `irreversible`** (fail-closed). V1 consumes the classification as **audit metadata only** — every divergence halts; recording it makes tiered auto-resolution a future policy flip gated on this task's CI divergence-injection tests. The daemon never silently re-emits locally recorded events into the provider session and never silently discards provider-side events; the halt surfaces on both existing owner-visible channels Spec-015 §Fallback Behavior names — `RecoveryStatusRead`'s `blocked` state (Plan-015-owned; implemented by this plan) and Spec-013's `run.blocked` timeline row — never a new notification surface. T15.5's daemon-side deliverable serves both: the recorded run state + `recovery-needed` condition + classification IS what the `run.blocked` row renders, and rendering it is Plan-013's pre-existing Tier-8 obligation under Spec-013 (build-order successor of this Tier-7 plan — the two-channel visibility is complete at V1 by tier order, with no new Plan-015 dependency edge and no Plan-013 amendment: that row already sits in its spec). The compare also catches a provider silently returning a **fresh session** on resume (e.g. Claude on a working-directory mismatch): past the initial boundary a fresh session's position cannot match the recorded one — and position equality alone is **not** identity proof at the initial boundary (a fresh session can report the same initial position as a run that crashed before advancing), so the compare composes with the driver's I-005-5 no-silent-replacement duty: the driver reports `resumed` only for the provider session its handle names (deterministic session binding), surfacing a replacement session as such, and a same-position fresh session therefore takes the failed/divergence arm, never silent acceptance. A run already `waiting_for_input` at crash time keeps its state — no self-transition row, per run-state-machine.md's §Derived Failure And Recovery Signals rule — with the stale pre-crash input request replaced by the `recovery-needed` reconciliation block, never left masking the divergence (replacement emphasis campaign B14). ## Ratified Design Decisions (Tier-7 audit)

- **D-015-1 — `ReplayReadAfterCursor` retains a sequence-position cursor (`afterSequence: number`), not the `EventCursor` brand.** The replay read advances over the canonical `session_events.sequence` integer (the `replay_cursors.last_sequence` state machine), so a numeric sequence position is the natural cursor and makes idempotent rebuild (I-015-2) trivially verifiable. The sibling `EventReadAfterCursor` uses the opaque `EventCursor` brand because client-facing event reads must tolerate cursor-format evolution (Plan-006). The two read models intentionally differ; reconciling them to a single brand is a non-blocking refinement **not** adopted in V1 — `docs/architecture/contracts/api-payload-contracts.md §Plan-015 — Persistence Recovery And Replay` keeps `afterSequence: number`. This resolves the cursor-model reconcile the audit flagged as a non-blocking owner decision.
