## Goal

Implement the normalized provider driver contract, the provider registry keyed by the open provider id and built from one table of drivers, each driver's descriptor, and runtime binding persistence. A provider is one driver folder plus one table entry: shared code holds the open id and the shapes every provider fills, and reaches a provider only through its descriptor and the driver interface. Drivers execute within the local daemon as the execution authority (per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior)); the contract is the boundary between the session domain and provider-specific lifecycles. Phase 4 SDK exposure ships as `provider.model.list`, `provider.mode.list`, `provider.command.list` and `agent.run.context.compact`, registered through Plan-005's namespace registry.

## Scope

This plan covers (a) the daemon's `ProviderDriver` interface in `crates/sidekicks-daemon`, split into the core trait every driver implements and the optional legs a driver has or lacks, + each driver's descriptor + the capability flags the daemon gates its own calls on, which no client reads (widened by the code leg) + per-tool `idempotencyClass` metadata, (b) the in-daemon provider registry, keyed by the open `ProviderId` and filled at start from one table of drivers, + runtime-binding persistence (`runtime_bindings`, `driver_capabilities` SQLite tables), (c) the Codex and Claude Code drivers implemented against the contract as integrations on the local machine, each operation graded `native`, `emulated`, `degraded` or `absent` on each, (d) capability refresh on its triggers + recovery-aware binding storage extension points, (e) typed SDK exposure of the model and mode reads and the console-parity surfaces, with the intervention dispatcher's degraded-fallback semantics (`status: "applied" | "degraded"`) kept inside the daemon, and (f) the provider-admission contract, and the voice and cloud-task legs each driver builds in its own folder to its provider's own voice and cloud tasks.

## Non-Goals

- Multi-agent workflow semantics (Plan-006)
- Provider-specific screen code: screens draw product concepts from what the provider read (`provider.list`) and the session's provider state send, and name no provider
- A general driver for agents that speak another protocol, an agent runtime of the product's own, or a provider marketplace. Claude Code and Codex are the drivers this plan builds; another provider joins as its own driver folder plus one entry in the drivers table, with no change to shared code ([Spec-004 §Interfaces And Contracts](../specs/004-provider-driver-contract-and-capabilities.md#interfaces-and-contracts)).
- Shared hosted execution drivers — drivers execute within the local daemon per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior) + ADR-005. Work a provider runs in its own cloud is reached through that provider's own verbs under the session's account, never hosted by this runtime (T3.31).

## Preconditions

This plan rests on ADR-005, ADR-011, ADR-014, ADR-016 and ADR-027, and builds on:

- Plan-001 Phase 3's daemon schema;
- Plan-001 Phase 2's id newtype contracts;
- Plan-005's JSON-RPC client transport;
- **the daemon's own MCP client, which T5.1 builds on** — the daemon runs one MCP client of its own, for its own calls and for the servers it fronts on Codex and a server that demands DPoP tokens on Claude Code, while a provider's own connections stay the provider's ([Spec-024 §Non-Goals](../specs/024-mcp-server-configuration-and-governance.md#non-goals)). That client, on `rmcp` 3.5.1 with the daemon's own bridge for a 2025-11-25 server's tasks (`CustomRequest`s through its own `StreamableHttpClient` over `reqwest`, signing DPoP on every request with `p256`), takes a task wherever the server makes a call one, records the task handle before answering anything else, and runs the recovery poll (`tasks/get` to a terminal status, then the result: `tasks/result` on a 2025-11-25 server, inline on a 2026-07-28 one), so T5.1 has its daemon-side caller.

Target paths below assume the implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

Phase 2 (runtime persistence):

It names no provider.

Each provider's code sits in its own folder under `provider::driver` (`crates/sidekicks-daemon/src/provider/driver/claude/`, `crates/sidekicks-daemon/src/provider/driver/codex/`), so module privacy keeps every module outside the driver interface's own files from naming a provider; that one provider's module never reaches the other's, and that only the daemon's start reads the build functions, are held in review.

## Data And Storage Changes

Plan-003 owns these SQLite tables, the first four built in Phase 2 and `cloud_tasks` in T3.31:

- `runtime_bindings` — persists driver-instance ↔ session/run bindings. Plan-003's driver tasks also adds the driver-boundary subagent emitter/normalizer task — `agent.subagent.started` / `agent.subagent.completed` appends per the Plan-004 event-coverage registry's single-owner assignment; Plan-013's native-subagent governor consumes those rows and is gated on that task. Plan-012 extends with recovery-aware persistence methods (per CP-003-1; row-level recovery state lives in Plan-012's dedicated `recovery_checkpoints` table, not on `runtime_bindings`).
- `driver_capabilities` — caches the capability-flag matrix per active driver instance. The flag set is the daemon's one schema's `capability_flag` CHECK, and the schema's test proves each member inserts and a non-member fails; a flag added to the set adds no table and no column. The rows are rewritten whenever a capability read on one of §Default Behavior's triggers in [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md#default-behavior) finds a changed snapshot.
- `driver_tools` — per-tool metadata keyed `(provider_name, tool_name)`, persisting each tool's declared `idempotency_class` ([Spec-004 §Tool Metadata](../specs/004-provider-driver-contract-and-capabilities.md#tool-metadata)); [Plan-022](./022-mcp-server-configuration-and-governance.md)'s per-tool overrides lay the person's assignment over it, giving the effective class Settings › MCP servers shows. T2.4 hydrates it into the capability read after restart without round-tripping the driver.
- `driver_contract_meta` — per-driver parent row (`provider_name` PK) holding the advertised `contract_version` that cold-start cache hydration (T2.4) reconstructs into `GetCapabilitiesResult.capabilities.contractVersion` without round-tripping the driver (the cache-as-source-of-truth path). (the canonical table additionally caches the `cli_version_raw`/`cli_version_semver` pair; hydration treats a NULL pair as a cache miss and refreshes from the driver, since the required `GetCapabilitiesResult.cliVersion` is never fabricated — the columns sit in the daemon's one schema.)
- `cloud_tasks` — one row per task a session sent to its provider's cloud: the session, the provider, the provider's own task id, the environment label it runs in, and the last state and attempts the provider reported. The label a project's most recent Codex task ran in is the one offered first for that project's next task. It holds no state the provider did not report (T3.31).

See [Local SQLite Schema §Driver and Runtime Binding Tables](../architecture/schemas/local-sqlite-schema.md#driver-and-runtime-binding-tables-plan-003) for column definitions (the Phase 2 tables carry the `Owner: Plan-003` annotation).

## API And Transport Changes

- Add the client-facing driver reads and console-parity verbs to the client SDK as `provider.model.list`, `provider.mode.list`, `provider.command.list` and `agent.run.context.compact`, registered through Plan-005's namespace registry (per CP-005-4). No client reads a capability flag: each provider's fixed facts (its built-in tools, its fixed output-speed levels, its words and its own Settings rows) reach clients in the provider read, `provider.list`, built from the descriptors and each driver's live reads, and a client interrupts a run only through `agent.run.intervene` ([Plan-002](./002-queue-steer-pause-resume.md)), never through a driver verb.
- Define the internal driver interface (canonical long-form names per [provider-driver-payloads.md §Plan-003 — Provider Driver Contract (Internal Interface)](../architecture/contracts/provider-driver-payloads.md#plan-003--provider-driver-contract-internal-interface) `interface ProviderDriver`). The base operations are `createSession`, `resumeSession`, `startRun`, `interruptRun`, `applyIntervention`, `respondToRequest`, `closeSession`, `listModels`, `listModes`, `getCapabilities`. The Spec-004 surface adds `moveSessionToFork` (moves the session onto a fork of its conversation), `rewindConversation` (undo's conversation cut, in place), `setSessionGoal` and `clearSessionGoal` (the provider's own goal), `probeAuth`, `exportHandoverBrief`, `compactContext` and `listProviderCommands` — every operation with its interface member, per-driver implementation, normalizer and conformance test in the tasks below. Undo and fork are separate operations: undo is the provider's own conversation cut plus the daemon's file checkpointer, and fork makes a new conversation and leaves the source untouched. The core interface also carries what each provider answers live: `listModels` takes an account, the account-facts read (sign-in kind, usage windows under the provider's own labels, and whether voice, cloud tasks and usage resets apply to that account), the typed session options with their whole observed state, and applying a setting checked against the driver's declared row; each driver maps its tools onto the shared tool words inside its event normalizer.
- Add the client-facing names this plan's drivers serve beyond those, each with its payload in [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md) and its schema in `crates/sidekicks-contracts/src/` (`command.rs` for `agent.command.*`, `session/methods.rs` for the `session.*` names, `cloud.rs` and `voice.rs`): the running commands `agent.command.subscribe` (live), `agent.command.stop`, `agent.command.background` and `agent.command.write {sessionId, commandId, text?, endOfInput?}`, with the event `agent.command.ended`; the session reads and actions `session.providerCommand.subscribe`, `session.mode.update`, `session.sideQuestion.ask {question}`, `session.codeReview.start {target}`, `session.memory.read`, `session.autoMemory.update`, `session.hook.list` and `session.restart`; the cloud tasks `cloud.task.start {sessionId, prompt, environment?, attempts?}` → `{taskId}`, `cloud.task.subscribe {sessionId}` (live), `cloud.task.read {taskId}`, `cloud.task.diff.read {taskId, attempt?}` and `cloud.task.apply {taskId, attempt?}`, with the event `cloud.task.updated`; and voice: `voice.dictation.start {sessionId}`, `voice.dictation.write`, `voice.dictation.stop {cancel}`, `voice.dictation.subscribe`, `voice.call.start {sessionId, offerSdp}` → `{answerSdp}`, `voice.call.stop`, `voice.call.subscribe`, `voice.list`, `voice.state.update {sessionId | null}` and `voice.state.subscribe`. None of the event kinds is minted here; each is registered in [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md).
- Add the provider error codes to the JSON-RPC error registry (all present at [error-contracts.md §Provider](../architecture/contracts/error-contracts.md#provider)): `provider.notFound` (404), `provider.unavailable` (503), `provider.timeout` (504), and `provider.capability.unsupported` (422 — note that this is the SDK seam's wire-error for invocation of an undeclared capability, distinct from the per-call `degraded` status returned by `applyIntervention` per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior); the two are not in conflict — `provider.capability.unsupported` covers the static "this driver does not support that capability at all" gate, `degraded` covers the dynamic "this intervention type is not supported but a fallback action is available" outcome).
- Driver result types: `ApplyInterventionResponse`, the driver's own struct `{status, fallbackAction?}` in `crates/sidekicks-daemon/src/provider/driver/run_control.rs`, whose `status` is `applied` or `degraded` and whose `fallbackAction` is an optional string, returned to the orchestration that called the driver (per the Phase 4 envelope shape; see Phase 4 below).
- Client pattern: the driver methods are `sidekicks-client`'s, over the daemon connection only. No control-plane variant per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior): drivers run in the local daemon, and work a provider runs in its own cloud is reached through the provider's own verbs (T3.31), never through a hosted driver.

### Phase 4 — Client SDK exposure + degraded-fallback

**Goal:** Author the typed SDK surface for the model and mode reads and the console-parity verbs as `provider.model.list`, `provider.mode.list`, `provider.command.list` and `agent.run.context.compact` (per Plan-005 CP-005-4). A subscription rides the daemon's subscription lane (`crates/sidekicks-daemon/src/ipc/stream/subscriptions.rs`) and the frames in `crates/sidekicks-contracts/src/jsonrpc/streaming.rs`, per Plan-005 CP-005-3 precedent.

**Precondition:** Phases 1 and 2 merged.

**Design decisions:**

1. **Client pattern**: the driver methods are `sidekicks-client`'s, over the daemon connection only — no control-plane variant. Aligns with [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior) (driver authority is local-daemon-resident; work a provider runs in its own cloud is reached through the provider's own verbs, T3.31, never through a hosted driver). Matches MCP/LSP best practice (single-transport for local-only capability servers).
2. **Names**: the client-facing methods sit under `provider.*` and `agent.run.*` (added to Plan-005's remainder namespace registry per CP-005-4). Their names follow canonical long-form per ADR-009 and Plan-005 I-005-8: `provider.model.list`, `provider.mode.list`, `agent.run.context.compact` and `provider.command.list` (`{sessionId, agentId}`, an agent's `/` list read once); a run's state reaches clients on `agent.run.subscribe` ([Plan-002](./002-queue-steer-pause-resume.md)), the live `/` list as `session.providerCommand.subscribe` (T4.8), and each provider's fixed facts on the provider read, `provider.list`. **No client reads a capability flag, and no client calls `interruptRun` or `applyIntervention`:** both stay the driver's internal calls, and a client interrupts only through `agent.run.intervene` ([Plan-002](./002-queue-steer-pause-resume.md)), whose orchestration calls the driver. **Admission by the governing principle:** `compactContext` and the live `/` list both operate on an already-existing session, and neither establishes, restores, starts, nor tears down a session-or-run domain object, so neither is orchestration-owned. They differ from the parity operations kept daemon-internal below in the one respect that decided those: those operations each have an existing client route (the conversation cut through `session.restore`, the fork through `session.fork`, the goal pair through Plan-013's goal service), and these have none — a composer affordance and a command autocomplete can be reached by no verb the wire already carries, and adding an intervention for compaction would widen `Spec-003`'s V1 control set. Registration rides CP-005-4, which lists this plan's client-facing methods; that plan builds the `register` substrate. **Lifecycle operations stay daemon-internal.** The four session/run **lifecycle** operations — the driver's `createSession`, `resumeSession`, `startRun` and `closeSession` — are **daemon-internal**: invoked only by the session/run orchestration layer on the in-daemon `ProviderRegistry` (T2.3), never registered as client-callable JSON-RPC methods. Governing principle: a driver method is client-facing iff it operates on an already-existing session/run and no other namespace already carries it (model/mode reads, compaction, an agent's command read); methods that **establish, restore, start, or tear down** a session-or-run domain object are orchestration-owned, because orchestration must persist the runtime binding and emit the canonical lifecycle event around the driver call. This honors [Spec-004 §Example Flows](../specs/004-provider-driver-contract-and-capabilities.md#example-flows) (the driver "only sees `interruptRun` followed later by `startRun`" — those lifecycle calls are driven BY orchestration, not by clients) and the Phase-4 goal above. Exposing the lifecycle verbs as client-callable would let a renderer/CLI start or destroy a provider session/run while bypassing the orchestration that owns `runtime_bindings` persistence + canonical `agent.run.*` event emission. The in-daemon `ProviderDriver` interface (T1.1's base operations and T1.7's additions, all daemon-internal per T4.7) keeps every operation — only its client JSON-RPC exposure is narrower. Clients reach lifecycle indirectly through the orchestration namespaces (`session.*` per Plan-001 — `session.create` maps to `directoryService.createSession` per `docs/architecture/contracts/remote-control-payloads.md §Plan-025 — Remote Control Bootstrap (control-plane HTTP routes)`, NOT the driver's `createSession`; `agent.run.*` per Plan-002).
3. **Envelope shape**: `ApplyInterventionResponse` (`{ status: 'applied' | 'degraded'; fallbackAction?: string }`), the driver's own type in `crates/sidekicks-daemon/src/provider/driver/run_control.rs`, is the driver's return to the orchestration that called it ([Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-004 §Fallback Behavior](../specs/004-provider-driver-contract-and-capabilities.md#fallback-behavior-1)), which dispatches the fallback; a client sees the intervention's outcome on `agent.run.intervene`'s response. Distinct from orchestration `InterventionState` lifecycle enum per LSP/MCP separation-of-concerns precedent.
4. **Recovery-needed surface**: surfaced via a typed return-value contract from `resumeSession` (T3.1, T3.6), then propagated by Plan-012's recovery dispatcher to the existing `agent.run.failed` event with `recoveryCondition: 'recoveryNeeded'` per [Spec-005 §Run Lifecycle (runLifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-runlifecycle). Plan-003 does NOT emit a separate recovery event of its own — see CP-003-3 for the full handoff sequence.

### Driver Authoring Rules

Two rules govern every driver, normalizer and parser task in this plan.

**CLI-currency verification.** Every CLI-mechanism claim is read from the [provider-wire reference](../reference/provider-wire/README.md) family, where each fact carries the version it was measured at, rather than restated here; behaviors are anchored by version, never by date. Codex protocol claims are regenerated from the binary's own `codex app-server generate-json-schema` output through `typify`, which is canonical over prose; hand-transcription is prohibited. Claude `--help` is not authoritative — the published docs govern. For the rewind path: on Codex the cut is `thread/revert {threadId, beforeTurnId}` on the same thread, and Codex has no `thread/rollback` (absent from the generated schema; `-32600 unknown variant`), so T3.15 leg 1 registers no handler for it ([`codex.md`](../reference/provider-wire/codex.md#threadrevert--the-undos-conversation-cut)). On Claude, `rewind_conversation` reports a refusal as `subtype: "success"` with `rewound: false`, so the driver reads `rewound`; and `--resume-session-at`, which the fork uses, is binary-probe-only and absent from the live CLI reference, so before any driver code invoking it lands the implementer verifies it against the then-installed binary ([`claude.md`](../reference/provider-wire/claude.md) §Gaps recorded). The daemon's file checkpointer ([Plan-007](./007-worktree-lifecycle-and-execution-modes.md)) is the durable file path regardless of the provider leg.

**No silent loss; fail open at the parse boundary, fail closed on a malformed frame.** A wire kind the driver recognizes but cannot map to a registered `SessionEventType` — an unknown-but-parseable kind, a kind whose contracts registration has not yet landed, **or** a registered kind whose `SessionEvent` payload variant has not yet landed — is **fail-open**: it routes to the T3.11 default-branch diagnostic and is **never dropped and never forced into an envelope against a missing type or a missing union variant**, exactly the seam Plan-004's `EVENT_DISPOSITION_BY_KIND` and its exhaustiveness test delegate to the Plan-003 normalizer. Payload variants are Plan-003-owned, on the emitter-authors-payload rule: each variant registers through the `SessionEvent` union-registration seam with — or before — the first normalizer change that emits its kind, so emission turns on variant by variant and never by a registry entry alone. A **malformed frame** — bytes that do not parse as a valid provider wire message at all — is **fail-closed**: the driver rejects it with a typed parse error rather than fabricating a partial event. Provider correlation identifiers (`tool_use_id`, `parent_tool_use_id`, Codex item/call ids) are copied **verbatim** onto the normalized event — never reformatted, re-cased, re-padded, or re-encoded — because tool-event pairing is by exact-string match and a reformatted correlation id is the single most common documented cause of pairing failure.

### CP-003-1 — `runtime_binding/store.rs` recovery-aware extension contract owed to [Plan-012](./012-persistence-and-recovery.md)

Plan-003 Phase 2 (T2.2) owns `crates/sidekicks-daemon/src/provider/runtime_binding/store.rs`. Plan-012 extends the store with recovery-aware persistence methods. The extension contract:

- The `RuntimeBindingStore` exposes `findResumableBindings(...)` as a queryable seam where Plan-012 may add recovery-aware predicates (e.g., bindings with stale checkpoints, bindings marked `recoveryNeeded` via the dedicated `recovery_checkpoints` table at `docs/architecture/schemas/local-sqlite-schema.md §Recovery Tables (Plan-012)`).
- Row-level recovery state lives in Plan-012's `recovery_checkpoints` table (not on `runtime_bindings`). Plan-003's `resumeSession` returns the typed failure result (T3.1/T3.6); Plan-012's recovery dispatcher receives the result and writes the corresponding row to `recovery_checkpoints` via a Plan-012-defined extension method on `RuntimeBindingStore`, then emits the existing `agent.run.failed` event with `recoveryCondition: 'recoveryNeeded'` per [Spec-005 §Run Lifecycle (runLifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-runlifecycle).

**Why bidirectional.** Plan-012 reviewers see the consumer dependency; Plan-003 reviewers (especially Phase 2 PR authors) must know that the binding-store's public method surface is contractually required to support Plan-012's recovery dispatch without further Plan-003 changes.

### CP-003-3 — Recovery-needed surface owed to [Plan-004](./004-session-event-taxonomy-and-audit-log.md) / [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)

**Capability state is stored, never evented.** The driver tables hold the current capability state, `hydrate()` rebuilds it without applying any event, and the registry's snapshot is replaced by each reading the refresh declares through the writer (T2.4, T4.4). Nothing reads a capability event, so Plan-003 emits none.

**Recovery-needed condition reuses existing `agent.run.failed` surface.** [Spec-004 §Fallback Behavior](../specs/004-provider-driver-contract-and-capabilities.md#fallback-behavior) calls for drivers to "surface a visible `recoveryNeeded` condition" on resume-handle failure. [Spec-005 §Run Lifecycle (runLifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-runlifecycle) already declares this surface: `agent.run.failed` payload includes `recoveryCondition?: 'recoveryNeeded'`. Plan-003 does NOT emit a separate recovery event of its own. Instead:

1. Plan-003's `resumeSession` returns a typed failure result (T3.1, T3.6).
2. Plan-012's recovery dispatcher receives the typed result.
3. Plan-012 emits the existing `agent.run.failed` event with `recoveryCondition: 'recoveryNeeded'`.

This keeps the `recoveryNeeded` signal on the canonical run-lifecycle surface where downstream consumers already subscribe; avoids creating a parallel driver-specific recovery event.

**What Plan-004 supplies.** Plan-004 Phase 3 defines `providerFailureDetail?: string` on the `agent.run.failed` payload (the `RunStateChangeEvent` member, in [`run-control-payloads.md` §Plan-002 — Queue Steer Pause Resume](../architecture/contracts/run-control-payloads.md#plan-002--queue-steer-pause-resume)). It mirrors the `failed`-variant `providerFailureDetail` field of `DriverResumeResult` (in [`provider-driver-payloads.md` §Plan-003 — Provider Driver Contract (Internal Interface)](../architecture/contracts/provider-driver-payloads.md#plan-003--provider-driver-contract-internal-interface), authored by Plan-003 T1.5): Plan-012's recovery dispatcher reads the typed failure detail from the driver result and emits it on the canonical `agent.run.failed` event, so the audit log carries a reason the person can act on without re-querying the driver.

**Why bidirectional.** Recovery-needed flows through Plan-012, not directly from the driver, so the driver's `resumeSession` return type stays a pure typed failure result; this plan's result feeds Plan-004's `agent.run.failed` field.

### CP-003-9 — Console-parity surfaces published to [Plan-010](./010-transcript-and-reasoning.md), [Plan-020](./020-desktop-app-and-renderer.md), and [Plan-013](./013-multi-agent-orchestration.md)

Reading it costs **no provider round-trip** — the binder reads state the driver already holds, and never waits for, forces, or spends a turn to obtain it — which is what lets a list read serve it without starting, resuming, or interrogating a provider process, and it is deliberately stored nowhere on either side: a persisted observation would be a second and staler record of a fact the running session already holds, and would let a mode that stopped being available across a restart keep reading as accepted.

**Owed to:** Plan-010 T4.6 / T4.7, Plan-020 T-020r-5-2, and Plan-013 T3.8. **Reciprocals:** Plan-010's `CP-003-9` obligation row, Plan-020's `CP-020-4`, and Plan-013's `CP-013-13`. This plan's side is T3.21 and T4.8; leg (d) publishes a value T3.21 already captures.

### CP-003-10 — Machine-authored content column consumed from [Plan-004](./004-session-event-taxonomy-and-audit-log.md) (⇄ CP-004-7)
