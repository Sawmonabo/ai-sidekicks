## Goal

Implement the normalized provider driver contract, capability registry, and runtime binding persistence. Drivers execute within the local daemon as the execution authority (per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior)); the contract is the boundary between the session domain and provider-specific lifecycles. Phase 4 SDK exposure ships under a dedicated `driver.*` JSON-RPC namespace registered through Plan-005's namespace registry.

## Scope

This plan covers (a) the daemon's `ProviderDriver` interface in `packages/runtime-daemon` + the capability-flag schema clients read in `packages/contracts` (widened by the code leg) + per-tool `idempotency_class` metadata, (b) the in-daemon provider registry + runtime-binding persistence (`runtime_bindings`, `driver_capabilities` SQLite tables), (c) two initial drivers (Codex, Claude) implemented against the contract as local-runtime-node integrations, each operation graded `native`, `emulated`, `degraded` or `absent` on each, (d) capability refresh on its triggers + recovery-aware binding storage extension points, (e) typed SDK exposure of capability + intervention surfaces with degraded-fallback semantics (`status: "applied" | "degraded"`), and (f) the provider-admission contract, and the bridges each driver builds to its provider's own cloud tasks and voice.

## Non-Goals

- Multi-agent workflow semantics (Plan-006)
- Provider-specific UI tuning beyond capability exposure (out-of-scope for V1)
- A driver for a provider other than Claude Code and Codex, an agent runtime of the product's own, or a provider marketplace; [Spec-004 §Interfaces And Contracts](../specs/004-provider-driver-contract-and-capabilities.md#interfaces-and-contracts) lists the providers and every place that lists them, and a later provider joins only by widening that list.
- Shared hosted execution drivers — drivers execute within the local daemon per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior) + ADR-005. Work a provider runs in its own cloud is reached through that provider's own verbs under the session's account, never hosted by this runtime (T3.31).

## Preconditions

This plan rests on ADR-005, ADR-011, ADR-014, ADR-016 and ADR-027, and builds on:

- Plan-001 Phase 3's daemon schema;
- Plan-001 Phase 2's branded-id contracts;
- Plan-005's JSON-RPC client transport;
- **the daemon's own MCP client, which T5.1 builds on** — the daemon runs one MCP client of its own, for its own calls and for the servers it fronts on Codex, while a provider's own connections stay the provider's ([Spec-024 §Non-Goals](../specs/024-mcp-server-configuration-and-governance.md#non-goals)). That client makes a call task-augmented wherever the tool allows one, records the task handle before answering anything else, and runs the recovery poll (`tasks/get` → `tasks/result`), so T5.1 has its daemon-side caller.

Target paths below assume the implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

## Data And Storage Changes

Plan-003 owns these SQLite tables, the first four built in Phase 2 and `cloud_tasks` in T3.31:

- `runtime_bindings` — persists driver-instance ↔ session/run bindings. Plan-003's driver tasks also adds the driver-boundary subagent emitter/normalizer task — `subagent.started` / `subagent.completed` appends per the Plan-004 event-coverage registry's single-owner assignment; Plan-013's native-subagent governor consumes those rows and is gated on that task. Plan-012 extends with recovery-aware persistence methods (per CP-003-1; row-level recovery state lives in Plan-012's dedicated `recovery_checkpoints` table, not on `runtime_bindings`).
- `driver_capabilities` — caches the capability-flag matrix per active driver instance. The flag set is the daemon's one schema's `capability_flag` CHECK, and the schema's test proves each member inserts and a non-member fails; a flag added to the set adds no table and no column. The rows are rewritten whenever a capability read on one of §Default Behavior's triggers in [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md#default-behavior) finds a changed snapshot.
- `driver_tools` — per-tool metadata keyed `(driver_name, tool_name)`, persisting each tool's declared `idempotency_class` ([Spec-004 §Tool Metadata](../specs/004-provider-driver-contract-and-capabilities.md#tool-metadata)); [Plan-022](./022-mcp-server-configuration-and-governance.md)'s per-tool overrides lay the person's assignment over it, giving the effective class Settings › MCP servers shows. T2.4 hydrates it into `listCapabilities` after restart without round-tripping the driver.
- `driver_contract_meta` — per-driver parent row (`driver_name` PK) holding the advertised `contract_version` that cold-start cache hydration (T2.4) reconstructs into `GetCapabilitiesResult.capabilities.contractVersion` without round-tripping the driver (the cache-as-source-of-truth path). (the canonical table additionally caches the `cli_version_raw`/`cli_version_semver` pair; hydration treats a NULL pair as a cache miss and refreshes from the driver, since the required `GetCapabilitiesResult.cliVersion` is never fabricated — the columns sit in the daemon's one schema.)
- `cloud_tasks` — one row per task a session sent to its provider's cloud: the session, the provider, the provider's own task id, the environment label it runs in, and the last state and attempts the provider reported. The label a project's most recent Codex task ran in is the one offered first for that project's next task. It holds no state the provider did not report (T3.31).

See [Local SQLite Schema §Driver and Runtime Binding Tables](../architecture/schemas/local-sqlite-schema.md#driver-and-runtime-binding-tables-plan-003) for column definitions (the Phase 2 tables carry the `Owner: Plan-003` annotation).

## API And Transport Changes

- Add typed driver capability + driver runtime events to the client SDK under a dedicated `driver.*` JSON-RPC namespace registered through Plan-005's namespace registry (per CP-005-4).
- Define the internal driver interface (canonical long-form names per [api-payload-contracts.md §Plan-003 — Provider Driver Contract (Internal Interface)](../architecture/contracts/api-payload-contracts.md#plan-003--provider-driver-contract-internal-interface) `interface ProviderDriver`). The base operations are `createSession`, `resumeSession`, `startRun`, `interruptRun`, `applyIntervention`, `respondToRequest`, `closeSession`, `listModels`, `listModes`, `getCapabilities`. The Spec-004 surface adds `forkConversation` (the provider leg of forking a session), `rewindConversation` (undo's conversation cut, in place), `setSessionGoal` and `clearSessionGoal` (the provider's own goal), `probeAuth`, `exportHandoverBrief`, `compactContext` and `listProviderCommands` — every operation with its interface member, per-driver implementation, normalizer and conformance test in the tasks below. Undo and fork are separate operations: undo is the provider's own conversation cut plus the daemon's file checkpointer, and fork makes a new conversation and leaves the source untouched.
- Add the client-facing names this plan's drivers serve beyond `driver.*`, each with its payload in [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md) and its schema in `packages/contracts/src/` (`command.ts` for `command.*`, `session/session.ts` for the `session.*` names, `cloud.ts` and `voice.ts`): the running commands `command.list` (live), `command.stop`, `command.background` and `command.write {sessionId, commandId, text?, endOfInput?}`, with the event `command.ended`; the session reads and actions `session.providerCommandsSubscribe`, `session.modeUpdate`, `session.sideQuestionAsk {question}`, `session.reviewStart {target}`, `session.memoryRead`, `session.autoMemoryUpdate`, `session.hookList` and `session.restart`; the cloud tasks `cloud.taskStart {sessionId, prompt, environment?, attempts?}` → `{taskId}`, `cloud.taskList {sessionId}` (live), `cloud.taskRead {taskId}`, `cloud.taskDiffRead {taskId, attempt?}` and `cloud.taskApply {taskId, attempt?}`, with the event `cloud.task_updated`; and voice: `voice.dictationStart {sessionId}`, `voice.dictationWrite`, `voice.dictationStop {cancel}`, `voice.dictationSubscribe`, `voice.callStart {sessionId, offerSdp}` → `{answerSdp}`, `voice.callStop`, `voice.callSubscribe`, `voice.voiceList`, `voice.stateUpdate {sessionId | null}` and `voice.stateSubscribe`. None of the event kinds is minted here; each is registered in [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md).
- Add the driver-namespace error codes to the JSON-RPC error registry (all present at [error-contracts.md §Driver](../architecture/contracts/error-contracts.md#driver)): `driver.unavailable` (503), `driver.timeout` (504), and `driver.capability_unsupported` (400 — note that this is the SDK seam's wire-error for invocation of an undeclared capability, distinct from the per-call `degraded` status returned by `applyIntervention` per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior); the two are not in conflict — `driver.capability_unsupported` covers the static "this driver does not support that capability at all" gate, `degraded` covers the dynamic "this intervention type is not supported but a fallback action is available" outcome).
- SDK seam Zod schemas: `DriverInterventionResultSchema = z.object({ status: z.enum(['applied', 'degraded']), fallbackAction: z.string.optional })` (per the Phase 4 envelope shape; see Phase 4 below).
- SDK factory pattern: daemon-only `createDaemonProviderClient(JsonRpcClient): DriverClient`. No control-plane variant per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior): drivers run in the local daemon, and work a provider runs in its own cloud is reached through the provider's own verbs (T3.31), never through a hosted driver.

### Phase 4 — Client SDK exposure + degraded-fallback

**Goal:** Author the typed SDK surface for capability + intervention controls under a dedicated `driver.*` JSON-RPC namespace (per Plan-005 CP-005-4). Daemon-side IPC handlers + SDK-side Zod-validated wrappers ship together. Subscription primitive reuses `LocalSubscriptionProducer<T>` per Plan-005 CP-005-3 precedent.

**Precondition:** Phases 1 and 2 merged.

**Design decisions:**

1. **Factory pattern**: daemon-only `createDaemonProviderClient(JsonRpcClient): DriverClient` — no control-plane variant. Aligns with [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior) (driver authority is local-daemon-resident; work a provider runs in its own cloud is reached through the provider's own verbs, T3.31, never through a hosted driver). Matches MCP/LSP best practice (single-transport for local-only capability servers).
2. **Namespace**: dedicated `driver.*` (added to Plan-005's remainder namespace registry per CP-005-4). The client-facing method names follow canonical long-form per ADR-009 and Plan-005 I-005-8: `driver.listCapabilities`, `driver.interruptRun`, `driver.applyIntervention`, `driver.listModels`, `driver.listModes`, `driver.compactContext`, plus the subscription method `driver.subscribeEvents`; the live `/` list reaches clients as `session.providerCommandsSubscribe` (T4.9). **Admission by the governing principle:** `compactContext` and the live `/` list both operate on an already-existing session, and neither establishes, restores, starts, nor tears down a session-or-run domain object, so neither is orchestration-owned. They differ from the parity operations kept daemon-internal below in the one respect that decided those: those operations each have an existing client route (the conversation cut through `session.restore`, the fork through `session.fork`, the goal pair through Plan-013's goal service), and these have none — a composer affordance and a command autocomplete can be reached by no verb this namespace already carries, and adding an intervention for compaction would widen `Spec-003`'s V1 control set. Registration rides CP-005-4, which lists this plan's client-facing methods; that plan builds the `register` substrate. **Lifecycle operations stay daemon-internal.** The four session/run **lifecycle** operations — `driver.createSession`, `driver.resumeSession`, `driver.startRun`, `driver.closeSession` — are **daemon-internal**: invoked only by the session/run orchestration layer on the in-daemon `ProviderRegistry` (T2.3), never registered as client-callable JSON-RPC methods. Governing principle: a `driver.*` method is client-facing iff it operates on an already-existing session/run (capability introspection, intervention/control, model/mode reads, event subscription); methods that **establish, restore, start, or tear down** a session-or-run domain object are orchestration-owned, because orchestration must persist the runtime binding and emit the canonical lifecycle event around the driver call. This honors [Spec-004 §Example Flows](../specs/004-provider-driver-contract-and-capabilities.md#example-flows) (the driver "only sees `interruptRun` followed later by `startRun`" — those lifecycle calls are driven BY orchestration, not by clients) and the Phase-4 goal above ("capability + intervention controls"). Exposing the lifecycle verbs as client-callable would let a renderer/CLI start or destroy a provider session/run while bypassing the orchestration that owns `runtime_bindings` persistence + canonical `run.*` event emission. The in-daemon `ProviderDriver` interface (T1.1's base operations and T1.8's additions, all daemon-internal per T4.8) keeps every operation — only its client JSON-RPC exposure is narrower. Clients reach lifecycle indirectly through the orchestration namespaces (`session.*` per Plan-001 — `session.create` maps to `directoryService.createSession` per `docs/architecture/contracts/api-payload-contracts.md §Plan-025 — Remote Control Bootstrap (control-plane tRPC)`, NOT `driver.createSession`; `run.*` per Plan-002).
3. **Envelope shape**: Zod-validated `DriverInterventionResult` at SDK seam (`{ status: 'applied' | 'degraded'; fallbackAction?: string }`) mirroring driver-internal shape ([Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-004 §Fallback Behavior](../specs/004-provider-driver-contract-and-capabilities.md#fallback-behavior-1)) with wire-level validation. Distinct from orchestration `InterventionState` lifecycle enum per LSP/MCP separation-of-concerns precedent.
4. **Subscription primitive**: `driver.subscribeEvents` returns `LocalSubscriptionProducer<DriverEvent>` per Plan-005 CP-005-3 (the shared streaming primitive). `DriverEvent` is the Plan-004-owned union of existing event-category types relevant to driver runtime — `run_lifecycle`, `assistant_output`, `tool_activity`, `interactive_request`, `approval_flow` (a permission ask's `approval.requested`), `artifact_publication` and `usage_telemetry`; capability state is stored, never evented (T2.4). `usage_telemetry` is the canonical category name per [Spec-005 §Usage Telemetry](../specs/005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) and `packages/contracts/src/event/envelope.ts` literal union.
5. **Recovery-needed surface**: surfaced via a typed return-value contract from `resumeSession` (T3.1, T3.6), then propagated by Plan-012's recovery dispatcher to the existing `run.failed` event with `recoveryCondition: 'recovery-needed'` per [Spec-005 §Run Lifecycle (run_lifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle). Plan-003 does NOT emit a separate `driver.recovery_needed` event — see CP-003-3 for the full handoff sequence.

### Driver Authoring Rules

Two rules govern every driver, normalizer and parser task in this plan.

**CLI-currency verification.** Every CLI-mechanism claim is read from the [provider-wire reference](../reference/provider-wire/README.md) family, where each fact carries the version it was measured at, rather than restated here; behaviors are anchored by version, never by date. Codex protocol claims are regenerated from the binary's own `codex app-server generate-ts` / `generate-json-schema` output, which is canonical over prose; hand-transcription is prohibited. Claude `--help` is not authoritative — the published docs govern. For the rewind path: on Codex the cut is `thread/revert {threadId, beforeTurnId}` on the same thread, and Codex has no `thread/rollback` (gone from the generated schema; `-32600 unknown variant`), so T3.15 leg 1 registers no handler for it ([`codex.md`](../reference/provider-wire/codex.md#threadrevert--the-undos-conversation-cut)). On Claude, `rewind_conversation` reports a refusal as `subtype: "success"` with `rewound: false`, so the driver reads `rewound`; and `--resume-session-at`, which the fork uses, is binary-probe-only and absent from the live CLI reference, so before any driver code invoking it lands the implementer verifies it against the then-installed binary ([`claude.md`](../reference/provider-wire/claude.md) §Gaps recorded). The daemon's file checkpointer ([Plan-007](./007-worktree-lifecycle-and-execution-modes.md)) is the durable file path regardless of the provider leg.

**No silent loss; fail open at the parse boundary, fail closed on a malformed frame.** A wire kind the driver recognizes but cannot map to a registered `SessionEventType` — an unknown-but-parseable kind, a kind whose contracts registration has not yet landed, **or** a registered kind whose `SessionEventSchema` payload variant has not yet landed — is **fail-open**: it routes to the T3.11 default-branch diagnostic and is **never dropped and never forced into an envelope against a missing type or a missing union variant**, exactly the seam Plan-004's `EVENT_DISPOSITION_BY_KIND` and its exhaustiveness test delegate to the Plan-003 normalizer. Payload variants are Plan-003-owned, on the emitter-authors-payload rule: each variant registers through the `SessionEventSchema` union-registration seam with — or before — the first normalizer change that emits its kind, so emission turns on variant by variant and never by a registry entry alone. A **malformed frame** — bytes that do not parse as a valid provider wire message at all — is **fail-closed**: the driver rejects it with a typed parse error rather than fabricating a partial event. Provider correlation identifiers (`tool_use_id`, `parent_tool_use_id`, Codex item/call ids) are copied **verbatim** onto the normalized event — never reformatted, re-cased, re-padded, or re-encoded — because tool-event pairing is by exact-string match and a reformatted correlation id is the single most common documented cause of pairing failure.

Base establishment is two-armed: a fresh provider session bases at **zero**, its first reading metering in full, and a provider-native resume bases at **the daemon's own prior-emitted cumulative sum for that thread**, never at the first post-resume reading. Source: [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-014 §Provider-Native Subagents](../specs/014-multi-agent-orchestration.md#provider-native-subagents). Source: [Spec-004 §Desktop Console Parity Surfaces](../specs/004-provider-driver-contract-and-capabilities.md#desktop-console-parity-surfaces); [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior) (the `driver_command` frame and its two guards). - **I-003-13** — A turn whose delivery was not confirmed is never re-sent automatically, because a resend repeats its spend. A send left unknown by a dropped connection, a timeout or a daemon restart is settled by reading the provider's conversation back before any further send on that session and comparing person-authored turns by position, never by text; a conversation that cannot be read back fails the run with the turn unsent. ### CP-003-3 — Recovery-needed surface owed to [Plan-004](./004-session-event-taxonomy-and-audit-log.md) / [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)

**Capability state is stored, never evented.** The driver tables hold the current capability state, `hydrate()` rebuilds it without applying any event, and the cache invalidates from the writer's `snapshotChange` (T2.4). Nothing reads a capability event, so Plan-003 emits none.

**Recovery-needed condition reuses existing `run.failed` surface.** [Spec-004 §Fallback Behavior](../specs/004-provider-driver-contract-and-capabilities.md#fallback-behavior) calls for drivers to "surface a visible `recovery-needed` condition" on resume-handle failure. [Spec-005 §Run Lifecycle (run_lifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle) already declares this surface: `run.failed` payload includes `recoveryCondition?: 'recovery-needed'`. Plan-003 does NOT emit a separate `driver.recovery_needed` event. Instead:

1. Plan-003's `resumeSession` returns a typed failure result (T3.1, T3.6).
2. Plan-012's recovery dispatcher receives the typed result.
3. Plan-012 emits the existing `run.failed` event with `recoveryCondition: 'recovery-needed'`.

This keeps the recovery-needed signal on the canonical run-lifecycle surface where downstream consumers already subscribe; avoids creating a parallel driver-specific recovery event.

**What Plan-004 supplies.** Plan-004 Phase 3 defines `providerFailureDetail?: string` on the `run.failed` payload (the `RunStateChangeEvent` member, in [`api-payload-contracts.md` §Plan-002 — Queue Steer Pause Resume](../architecture/contracts/api-payload-contracts.md#plan-002--queue-steer-pause-resume)). It mirrors the `failed`-variant `providerFailureDetail` field of `DriverResumeResult` (in [`api-payload-contracts.md` §Plan-003 — Provider Driver Contract (Internal Interface)](../architecture/contracts/api-payload-contracts.md#plan-003--provider-driver-contract-internal-interface), authored by Plan-003 T1.6): Plan-012's recovery dispatcher reads the typed failure detail from the driver result and emits it on the canonical `run.failed` event, so the audit log carries a reason the person can act on without re-querying the driver.

**Why bidirectional.** Recovery-needed flows through Plan-012, not directly from the driver, so the driver's `resumeSession` return type stays a pure typed failure result; this plan's result feeds Plan-004's `run.failed` field.

### CP-003-4 — Cross-cutting symbol co-location (`InterventionType` enum + `RunId` brand / `RunIdSchema` + `ArtifactId` brand / `ArtifactIdSchema`) owed to [Plan-002](./002-queue-steer-pause-resume.md) + [Plan-009](./009-approvals-permissions-and-trust-boundaries.md) + [Plan-011](./011-artifacts-files-and-attachments.md)

The cross-cutting `InterventionType = "steer" | "interrupt" | "faster_model_retry"` enum (`docs/architecture/contracts/api-payload-contracts.md §Shared Enums`; the `provider/driver/driver.ts` union carries the same members and `ApplyInterventionParams` the first two, undo being `session.restore`'s conversation cut through the dedicated `rewindConversation` op rather than an intervention, and Plan-002's consumers arrive only after **T1.8** ships the union — its Phase 1 waits on Plan-003 Phase 1 — so union and consumers never diverge) is consumed by both Plan-002's `run/control.ts` and Plan-003's `provider/driver/driver.ts`. Resolution: Plan-003 Phase 1 (T1.4) co-locates the `InterventionType` re-export in `provider/driver/driver.ts` since Plan-003 ships earlier. Plan-002 imports the enum from Plan-003 — a forward, build-order-consistent import.

The **`RunId` brand (`type RunId`) and its validator `RunIdSchema`** co-locate in the same `provider/driver/driver.ts` by the identical logic, and for an additional structural reason: `RunId` is `InterventionType`'s struct-mate in `ApplyInterventionParams` (`{ type: InterventionType; targetRunId: RunId; … }`, `docs/architecture/contracts/api-payload-contracts.md §Plan-003 — Provider Driver Contract (Internal Interface)`). Earliest-consumer placement governs each symbol independently: `type RunId` is first consumed by the Phase 1 `ProviderDriver` interface method params (T1.1), and `RunIdSchema` is first consumed by the Phase 4 `InterruptRunParamsSchema` (T4.2) — so both home in Plan-003, the `type` and `Schema` paired in one file per the established `session/session.ts` `brandedUuidIdSchema` convention. Plan-002 imports `RunId`; Plan-009 imports both `RunId` and `RunIdSchema` — each an upward, forward edge. Authoring `RunIdSchema` in Plan-002's `run/control.ts` would be a backward import for Plan-003's own `InterruptRunParamsSchema` consumer, i.e. structurally forbidden.

**Precedent.** This matches Plan-001's ownership pattern for the brands it actually ships (`SessionId` and `UserId` co-located in `session/session.ts` Phase 2 — each `type X` paired with its `XSchema` per the `brandedUuidIdSchema` convention; their earliest-shipping consumer is Plan-001). The governing rule is **earliest-consumer placement**: a cross-cutting symbol is declared in the contract file of its earliest-shipping consumer, and every later plan imports it upward — never re-inventing a parallel definition. `RunId` / `RunIdSchema` are **not** in Plan-001 / `session/session.ts` (Plan-001 ships no run-domain symbol); their earliest-shipping consumer is Plan-003, so they home in `provider/driver/driver.ts`.

**The `ArtifactId` brand (`type ArtifactId`) and its validator `ArtifactIdSchema`** join the same file under the identical rule and with one difference worth stating: unlike `InterventionType` and `RunId`, whose semantics are Plan-002's and this plan's, `ArtifactId`'s shape is **[Spec-012](../specs/012-artifacts-files-and-attachments.md)'s and [Plan-011](./011-artifacts-files-and-attachments.md)'s**, so this is a homing decision and not an ownership one — the `node-id.ts` precedent, where `NodeId` sits in a dependency-free leaf with its owner's shape verbatim. Earliest-consumer placement selects this file because `SteerPayload.attachments` (T1.4) is the first member typed `ArtifactId[]`, ahead of Plan-002's `run/control.ts` `QueueItemCreate` and of Plan-011's own `artifacts/`, whose Task 1 imports the brand rather than restating it. A change to the brand's spelling or accept set is Spec-012's and Plan-011's to make, and is made in this file; a second declaration of that brand anywhere would be a second source of truth for what an artifact id is.

**Why bidirectional.** Plan-002 reviewers see the import-from-Plan-003 of `InterventionType` + `RunId` + `ArtifactId` / `ArtifactIdSchema`; Plan-009 reviewers see the import of `RunId` + `RunIdSchema`; Plan-011 reviewers must import `ArtifactId` / `ArtifactIdSchema` at Task 1 rather than declaring a sibling; and Plan-003 reviewers must know these symbols are shared and must not relocate them without coordinating with Plan-002 + Plan-009 + Plan-011.

### CP-003-8 — Driver-spawn capability report and the MCP set-replacement non-interference guarantee owed to [Plan-022](./022-mcp-server-configuration-and-governance.md)

Plan-022 T28.3.2 depends on this plan's driver-spawn capability report. T3.19 provides it, in two parts. **The report:** a per-capability result carrying each flag's `CapabilityDetectionSource`, produced at spawn and refreshed on T3.12's triggers. **The guarantee:** `mcp_set_servers` is **not a capability flag** and appears on no report, and no capability probe sends it, because an empty set would clear a live session's servers. The driver sends it for one purpose only: installing the session's own server set right after start and after each resume, and changing it when a switch flips (T3.25). That set is the one Plan-022 governs — which servers a session may have — so the driver carries Plan-022's decision and adds nothing to it, and never uses `mcp_toggle`, which would write the switch into the project's settings.

**Owed to:** Plan-022 T28.3.2, which consumes T3.19's report.

### CP-003-9 — Console-parity surfaces published to [Plan-010](./010-transcript-and-reasoning.md), [Plan-020](./020-desktop-app-and-renderer.md), and [Plan-013](./013-multi-agent-orchestration.md)

This plan publishes three things the desktop-console parity legs consume, and authors nothing on their side. A client answers a provider's ask through `approval.resolve` or `question.resolve`, never through the driver; the daemon delivers that answer with the driver op `respondToRequest`. **(a)** `driver.compactContext` (T4.9) and the `context_compaction` declaration, read through the existing `driver.listCapabilities` cache, gate and drive the composer's compaction popover. **(b)** `session.providerCommandsSubscribe` (T4.9) and the `provider_commands` / `output_speed` declarations feed the composer's command list and its speed control. Both declarations are per-binding and both legs of the speed axis are live, so the consumer reads the axis's boundary from the driver rather than assuming one: a change resolves to a run boundary on one provider and a turn boundary on the other. The **routing invariant travels with the data, not with the consumer's discipline**: every entry the read returns carries the `(driverName, providerAccountId)` it was read under, so a consumer replaces its list with each emission rather than filtering an older one, and a cross-binding dispatch refuses at this plan's boundary as `driver.capability_unsupported` rather than relying on the renderer to have filtered correctly. **(c)** The provider's own **declared** output-speed state and its provider-supplied reason, **held as driver-session state against the binding** (T3.21, T3.22), on the Claude leg the process's `initialize` reply reports it before any turn and each session handshake reports it again, so that leg's binding carries an observation from its spawn onward. The Codex leg declares its tier on the establishment reply itself and again on its settings-changed notification, so its binding carries an observation from establishment onward. A consumer is **absent-until-observed** on either leg and renders no absence as the mode being off. It is readable on the binding the agent is running on, so Plan-013's `agent.list` binder can project it as the live-scoped `observedOutputSpeed` beside the committed column, **absent until observed** and never defaulted. Reading it costs **no provider round-trip** — the binder reads state the driver already holds, and never waits for, forces, or spends a turn to obtain it — which is what lets a list read serve it without starting, resuming, or interrogating a provider process, and it is deliberately stored nowhere on either side: a persisted observation would be a second and staler record of a fact the running session already holds, and would let a mode that stopped being available across a restart keep reading as accepted.

**Owed to:** Plan-010 T4.6 / T4.7, Plan-020 T-020r-5-2, and Plan-013 T3.8. **Reciprocals:** Plan-010's `CP-003-9` obligation row, Plan-020's `CP-020-4`, and Plan-013's `CP-013-13`. This plan's side is T3.21 and T4.9; leg (d) publishes a value T3.21 already captures.

### CP-003-10 — Machine-authored content column consumed from [Plan-004](./004-session-event-taxonomy-and-audit-log.md) (⇄ CP-004-7)

(i) What T3.16's fold consumes is the **`HydratedSessionEvent`** projection Plan-004 T3.4 declares and T3.6 builds — the event paired with a closed two-arm `content` union — never a body spliced into `payload`; the `unavailable` arm carries the reason, which is where this plan's `'turn_content_unavailable'` gets its truth value instead of being inferred from an absent key. (ii) The column is local to the machine that runs the session and is never relayed or backfilled. A session runs on one machine, and a device that drives it through Remote Control reaches that machine's daemon, so the fold runs where every row of the session was written and reads each body the daemon logged. Plan-004 Phase 3B creates `session_events.content_payload` — the durable home for assistant- and tool-generated prose — together with its extended write path and the read path. This plan is the **consumer and the reason the column exists**: [ADR-027](../decisions/027-canonical-transcript-is-authoritative.md) rules the daemon's canonical transcript authoritative for the content of a provider session, [Spec-004 §The Canonical Transcript And The Hand-Over Brief](../specs/004-provider-driver-contract-and-capabilities.md#the-canonical-transcript-and-the-hand-over-brief) scopes that transcript's content to what [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)'s taxonomy carries, and without this column that taxonomy would carry a record that an assistant spoke rather than a record of what it said.

This plan authors **nothing** on Plan-004's side — no column, no codec — and takes one task-scoped hold in return: **T3.17 dispatches only after Plan-004 Phase 3B merges**, because the hand-over brief's notes and word-for-word tail are the turn bodies the column holds (that task's own entry). T3.16 is **not** held: its fold is correct over a body-less log, declaring each body-less turn `turn_content_unavailable`.

**Owed to:** nothing — this is a consumer-side registration. **Reciprocal:** Plan-004's `CP-004-7`.

**What the loss member reports.** A turn with no `content_payload` body is what `'turn_content_unavailable'` reports; a long body is stored whole, so no turn is a prefix. T3.16's fold reads that condition into `declaredLosses`, per the Fold step of [Spec-004 §The Canonical Transcript And The Hand-Over Brief](../specs/004-provider-driver-contract-and-capabilities.md#the-canonical-transcript-and-the-hand-over-brief), and T3.16's tests cover it. `api-payload-contracts.md` registers the loss kind, so the fold emits a registered kind rather than a free string.

This plan publishes three spawn-bound legs [Plan-013](./013-multi-agent-orchestration.md) T2.9 consumes and authors neither side of. **(a)** Each driver declares the daemon's own session tools at spawn — the twelve of [Spec-014 §Session Tool Texts](../specs/014-multi-agent-orchestration.md#session-tool-texts), on the session's entry for the shared `sidekicks` server on both providers, eleven on Claude Code — carries its provider's own texts for them, and routes their calls to the daemon rather than answering them, the session's level applied by `can_use_tool` on Claude Code and by the daemon under the entry's `approve` mode on Codex.
