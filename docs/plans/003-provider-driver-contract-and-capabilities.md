## Goal

Implement the normalized provider driver contract, capability registry, and runtime binding persistence. Drivers execute within the local daemon as the execution authority (per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior)); the contract is the boundary between the session domain and provider-specific lifecycles. Phase 4 SDK exposure ships under a dedicated `driver.*` JSON-RPC namespace registered through Plan-005's namespace registry.

## Scope

This plan covers (a) the daemon's `ProviderDriver` interface in `packages/runtime-daemon` + the capability-flag schema clients read in `packages/contracts` (widened by the code leg) + per-tool `idempotency_class` metadata, (b) the in-daemon provider registry + runtime-binding persistence (`runtime_bindings`, `driver_capabilities` SQLite tables), (c) two initial drivers (Codex, Claude) implemented against the contract as local-runtime-node integrations, each operation graded `native`, `emulated`, `degraded` or `absent` on each, (d) capability refresh on its triggers + recovery-aware binding storage extension points, (e) typed SDK exposure of capability + intervention surfaces with degraded-fallback semantics (`status: "applied" | "degraded"`), and (f) the provider-admission contract, and the bridges each driver builds to its provider's own cloud tasks and voice.

## Non-Goals

- Multi-agent workflow semantics (Plan-006)
- Provider-specific UI tuning beyond capability exposure (out-of-scope for V1)
- A driver for a provider other than Claude Code and Codex, an agent runtime of the product's own, or a provider marketplace; [Spec-004 §Interfaces And Contracts](../specs/004-provider-driver-contract-and-capabilities.md#interfaces-and-contracts) lists the providers and every place that lists them, and a later provider joins only by widening that list.
- Shared hosted execution drivers — drivers execute within the local daemon per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior) + ADR-005. Work a provider runs in its own cloud is reached through that provider's own verbs under the session's account, never hosted by this runtime (T3.31).

## Preconditions

This plan rests on ADR-005, ADR-011, ADR-014, ADR-016 and ADR-027, and builds on:

- Plan-001 Phase 3's daemon schema;
- Plan-001 Phase 2's branded-id contracts;
- Plan-005's JSON-RPC client transport;
- **the daemon's own MCP client, which T5.1 builds on** — the daemon runs one MCP client of its own, for its own calls and for the servers it fronts on Codex, while a provider's own connections stay the provider's ([Spec-024 §Non-Goals](../specs/024-mcp-server-configuration-and-governance.md#non-goals)). That client makes a call task-augmented wherever the tool allows one, records the task handle before answering anything else, and runs the recovery poll (`tasks/get` → `tasks/result`), so T5.1 has its daemon-side caller.

Target paths below assume the implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

## Data And Storage Changes

Plan-003 owns these SQLite tables, the first four built in Phase 2 and `cloud_tasks` in T3.31:

- `runtime_bindings` — persists driver-instance ↔ session/run bindings. Plan-003's driver tasks also adds the driver-boundary subagent emitter/normalizer task — `subagent.started` / `subagent.completed` appends per the Plan-004 event-coverage registry's single-owner assignment; Plan-013's native-subagent governor consumes those rows and is gated on that task. Plan-012 extends with recovery-aware persistence methods (per CP-003-1; row-level recovery state lives in Plan-012's dedicated `recovery_checkpoints` table, not on `runtime_bindings`).
- `driver_capabilities` — caches the capability-flag matrix per active driver instance. The flag set is the daemon's one schema's `capability_flag` CHECK, and the schema's test proves each member inserts and a non-member fails; a flag added to the set adds no table and no column. The rows are rewritten whenever a capability read on one of §Default Behavior's triggers in [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md#default-behavior) finds a changed snapshot.
- `driver_tools` — per-tool metadata keyed `(driver_name, tool_name)`, persisting each tool's declared `idempotency_class` ([Spec-004 §Tool Metadata](../specs/004-provider-driver-contract-and-capabilities.md#tool-metadata)); [Plan-022](./022-mcp-server-configuration-and-governance.md)'s per-tool overrides lay the person's assignment over it, giving the effective class Settings › MCP servers shows. T2.4 hydrates it into `listCapabilities` after restart without round-tripping the driver.
- `driver_contract_meta` — per-driver parent row (`driver_name` PK) holding the advertised `contract_version` that cold-start cache hydration (T2.4) reconstructs into `GetCapabilitiesResult.capabilities.contractVersion` without round-tripping the driver (the cache-as-source-of-truth path). (the canonical table additionally caches the `cli_version_raw`/`cli_version_semver` pair; hydration treats a NULL pair as a cache miss and refreshes from the driver, since the required `GetCapabilitiesResult.cliVersion` is never fabricated — the columns sit in the daemon's one schema.)
- `cloud_tasks` — one row per task a session sent to its provider's cloud: the session, the provider, the provider's own task id, the environment label it runs in, and the last state and attempts the provider reported. The label a project's most recent Codex task ran in is the one offered first for that project's next task. It holds no state the provider did not report (T3.31).

See [Local SQLite Schema §Driver and Runtime Binding Tables](../architecture/schemas/local-sqlite-schema.md#driver-and-runtime-binding-tables-plan-003) for column definitions (the Phase 2 tables carry the `Owner: Plan-003` annotation).

## API And Transport Changes

- Add typed driver capability + driver runtime events to the client SDK under a dedicated `driver.*` JSON-RPC namespace registered through Plan-005's namespace registry (per CP-005-4).
- Define the internal driver interface (canonical long-form names per [provider-driver-payloads.md §Plan-003 — Provider Driver Contract (Internal Interface)](../architecture/contracts/provider-driver-payloads.md#plan-003--provider-driver-contract-internal-interface) `interface ProviderDriver`). The base operations are `createSession`, `resumeSession`, `startRun`, `interruptRun`, `applyIntervention`, `respondToRequest`, `closeSession`, `listModels`, `listModes`, `getCapabilities`. The Spec-004 surface adds `forkConversation` (the provider leg of forking a session), `rewindConversation` (undo's conversation cut, in place), `setSessionGoal` and `clearSessionGoal` (the provider's own goal), `probeAuth`, `exportHandoverBrief`, `compactContext` and `listProviderCommands` — every operation with its interface member, per-driver implementation, normalizer and conformance test in the tasks below. Undo and fork are separate operations: undo is the provider's own conversation cut plus the daemon's file checkpointer, and fork makes a new conversation and leaves the source untouched.
- Add the client-facing names this plan's drivers serve beyond `driver.*`, each with its payload in [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md) and its schema in `packages/contracts/src/` (`command.ts` for `command.*`, `session/methods.ts` for the `session.*` names, `cloud.ts` and `voice.ts`): the running commands `command.list` (live), `command.stop`, `command.background` and `command.write {sessionId, commandId, text?, endOfInput?}`, with the event `command.ended`; the session reads and actions `session.providerCommandsSubscribe`, `session.modeUpdate`, `session.sideQuestionAsk {question}`, `session.reviewStart {target}`, `session.memoryRead`, `session.autoMemoryUpdate`, `session.hookList` and `session.restart`; the cloud tasks `cloud.taskStart {sessionId, prompt, environment?, attempts?}` → `{taskId}`, `cloud.taskList {sessionId}` (live), `cloud.taskRead {taskId}`, `cloud.taskDiffRead {taskId, attempt?}` and `cloud.taskApply {taskId, attempt?}`, with the event `cloud.task_updated`; and voice: `voice.dictationStart {sessionId}`, `voice.dictationWrite`, `voice.dictationStop {cancel}`, `voice.dictationSubscribe`, `voice.callStart {sessionId, offerSdp}` → `{answerSdp}`, `voice.callStop`, `voice.callSubscribe`, `voice.voiceList`, `voice.stateUpdate {sessionId | null}` and `voice.stateSubscribe`. None of the event kinds is minted here; each is registered in [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md).
- Add the driver-namespace error codes to the JSON-RPC error registry (all present at [error-contracts.md §Driver](../architecture/contracts/error-contracts.md#driver)): `driver.unavailable` (503), `driver.timeout` (504), and `driver.capability_unsupported` (400 — note that this is the SDK seam's wire-error for invocation of an undeclared capability, distinct from the per-call `degraded` status returned by `applyIntervention` per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior); the two are not in conflict — `driver.capability_unsupported` covers the static "this driver does not support that capability at all" gate, `degraded` covers the dynamic "this intervention type is not supported but a fallback action is available" outcome).
- SDK seam Zod schemas: `DriverInterventionResultSchema = z.object({ status: z.enum(['applied', 'degraded']), fallbackAction: z.string.optional })` (per the Phase 4 envelope shape; see Phase 4 below).
- SDK factory pattern: daemon-only `createDaemonProviderClient(JsonRpcClient): DriverClient`. No control-plane variant per [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior): drivers run in the local daemon, and work a provider runs in its own cloud is reached through the provider's own verbs (T3.31), never through a hosted driver.

### Phase 4 — Client SDK exposure + degraded-fallback

**Goal:** Author the typed SDK surface for capability + intervention controls under a dedicated `driver.*` JSON-RPC namespace (per Plan-005 CP-005-4). Daemon-side IPC handlers + SDK-side Zod-validated wrappers ship together. Subscription primitive reuses `LocalSubscriptionProducer<T>` per Plan-005 CP-005-3 precedent.

**Precondition:** Phases 1 and 2 merged.

**Design decisions:**

1. **Factory pattern**: daemon-only `createDaemonProviderClient(JsonRpcClient): DriverClient` — no control-plane variant. Aligns with [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior) (driver authority is local-daemon-resident; work a provider runs in its own cloud is reached through the provider's own verbs, T3.31, never through a hosted driver). Matches MCP/LSP best practice (single-transport for local-only capability servers).
2. **Namespace**: dedicated `driver.*` (added to Plan-005's remainder namespace registry per CP-005-4). The client-facing method names follow canonical long-form per ADR-009 and Plan-005 I-005-8: `driver.listCapabilities`, `driver.interruptRun`, `driver.applyIntervention`, `driver.listModels`, `driver.listModes`, `driver.compactContext`, plus the subscription method `driver.subscribeEvents`; the live `/` list reaches clients as `session.providerCommandsSubscribe` (T4.9). **Admission by the governing principle:** `compactContext` and the live `/` list both operate on an already-existing session, and neither establishes, restores, starts, nor tears down a session-or-run domain object, so neither is orchestration-owned. They differ from the parity operations kept daemon-internal below in the one respect that decided those: those operations each have an existing client route (the conversation cut through `session.restore`, the fork through `session.fork`, the goal pair through Plan-013's goal service), and these have none — a composer affordance and a command autocomplete can be reached by no verb this namespace already carries, and adding an intervention for compaction would widen `Spec-003`'s V1 control set. Registration rides CP-005-4, which lists this plan's client-facing methods; that plan builds the `register` substrate. **Lifecycle operations stay daemon-internal.** The four session/run **lifecycle** operations — `driver.createSession`, `driver.resumeSession`, `driver.startRun`, `driver.closeSession` — are **daemon-internal**: invoked only by the session/run orchestration layer on the in-daemon `ProviderRegistry` (T2.3), never registered as client-callable JSON-RPC methods. Governing principle: a `driver.*` method is client-facing iff it operates on an already-existing session/run (capability introspection, intervention/control, model/mode reads, event subscription); methods that **establish, restore, start, or tear down** a session-or-run domain object are orchestration-owned, because orchestration must persist the runtime binding and emit the canonical lifecycle event around the driver call. This honors [Spec-004 §Example Flows](../specs/004-provider-driver-contract-and-capabilities.md#example-flows) (the driver "only sees `interruptRun` followed later by `startRun`" — those lifecycle calls are driven BY orchestration, not by clients) and the Phase-4 goal above ("capability + intervention controls"). Exposing the lifecycle verbs as client-callable would let a renderer/CLI start or destroy a provider session/run while bypassing the orchestration that owns `runtime_bindings` persistence + canonical `run.*` event emission. The in-daemon `ProviderDriver` interface (T1.1's base operations and T1.8's additions, all daemon-internal per T4.8) keeps every operation — only its client JSON-RPC exposure is narrower. Clients reach lifecycle indirectly through the orchestration namespaces (`session.*` per Plan-001 — `session.create` maps to `directoryService.createSession` per `docs/architecture/contracts/remote-control-payloads.md §Plan-025 — Remote Control Bootstrap (control-plane tRPC)`, NOT `driver.createSession`; `run.*` per Plan-002).
3. **Envelope shape**: Zod-validated `DriverInterventionResult` at SDK seam (`{ status: 'applied' | 'degraded'; fallbackAction?: string }`) mirroring driver-internal shape ([Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-004 §Fallback Behavior](../specs/004-provider-driver-contract-and-capabilities.md#fallback-behavior-1)) with wire-level validation. Distinct from orchestration `InterventionState` lifecycle enum per LSP/MCP separation-of-concerns precedent.
4. **Subscription primitive**: `driver.subscribeEvents` returns `LocalSubscriptionProducer<DriverEvent>` per Plan-005 CP-005-3 (the shared streaming primitive). `DriverEvent` is the Plan-004-owned union of existing event-category types relevant to driver runtime — `run_lifecycle`, `assistant_output`, `tool_activity`, `interactive_request`, `approval_flow` (a permission ask's `approval.requested`), `artifact_publication` and `usage_telemetry`; capability state is stored, never evented (T2.4). `usage_telemetry` is the canonical category name per [Spec-005 §Usage Telemetry](../specs/005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) and `packages/contracts/src/event/envelope.ts` literal union.
5. **Recovery-needed surface**: surfaced via a typed return-value contract from `resumeSession` (T3.1, T3.6), then propagated by Plan-012's recovery dispatcher to the existing `run.failed` event with `recoveryCondition: 'recovery-needed'` per [Spec-005 §Run Lifecycle (run_lifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle). Plan-003 does NOT emit a separate `driver.recovery_needed` event — see CP-003-3 for the full handoff sequence.

### Driver Authoring Rules

Two rules govern every driver, normalizer and parser task in this plan.

**CLI-currency verification.** Every CLI-mechanism claim is read from the [provider-wire reference](../reference/provider-wire/README.md) family, where each fact carries the version it was measured at, rather than restated here; behaviors are anchored by version, never by date. Codex protocol claims are regenerated from the binary's own `codex app-server generate-ts` / `generate-json-schema` output, which is canonical over prose; hand-transcription is prohibited. Claude `--help` is not authoritative — the published docs govern. For the rewind path: on Codex the cut is `thread/revert {threadId, beforeTurnId}` on the same thread, and Codex has no `thread/rollback` (absent from the generated schema; `-32600 unknown variant`), so T3.15 leg 1 registers no handler for it ([`codex.md`](../reference/provider-wire/codex.md#threadrevert--the-undos-conversation-cut)). On Claude, `rewind_conversation` reports a refusal as `subtype: "success"` with `rewound: false`, so the driver reads `rewound`; and `--resume-session-at`, which the fork uses, is binary-probe-only and absent from the live CLI reference, so before any driver code invoking it lands the implementer verifies it against the then-installed binary ([`claude.md`](../reference/provider-wire/claude.md) §Gaps recorded). The daemon's file checkpointer ([Plan-007](./007-worktree-lifecycle-and-execution-modes.md)) is the durable file path regardless of the provider leg.

**No silent loss; fail open at the parse boundary, fail closed on a malformed frame.** A wire kind the driver recognizes but cannot map to a registered `SessionEventType` — an unknown-but-parseable kind, a kind whose contracts registration has not yet landed, **or** a registered kind whose `SessionEventSchema` payload variant has not yet landed — is **fail-open**: it routes to the T3.11 default-branch diagnostic and is **never dropped and never forced into an envelope against a missing type or a missing union variant**, exactly the seam Plan-004's `EVENT_DISPOSITION_BY_KIND` and its exhaustiveness test delegate to the Plan-003 normalizer. Payload variants are Plan-003-owned, on the emitter-authors-payload rule: each variant registers through the `SessionEventSchema` union-registration seam with — or before — the first normalizer change that emits its kind, so emission turns on variant by variant and never by a registry entry alone. A **malformed frame** — bytes that do not parse as a valid provider wire message at all — is **fail-closed**: the driver rejects it with a typed parse error rather than fabricating a partial event. Provider correlation identifiers (`tool_use_id`, `parent_tool_use_id`, Codex item/call ids) are copied **verbatim** onto the normalized event — never reformatted, re-cased, re-padded, or re-encoded — because tool-event pairing is by exact-string match and a reformatted correlation id is the single most common documented cause of pairing failure.

Test: a build of any version attaches and keeps every still-answering capability while a refusing probe withdraws only its own flag (T3.19); the binding row's version equals the spawned process's own report under launcher drift (T3.18); every probe-table entry declares a mechanism, each `static` entry names its failing admissibility conjunct, and the suite fails if any entry claims `probed` without one (T3.19); a probe suite spends zero billed turns — asserted at the provider transport, not at the daemon's event stream — and fails when its negative control succeeds (T3.19).

- **I-003-10** — A driver never emits a provider's cumulative counter as a per-turn figure, and no normalized token axis counts a token twice. Every usage emission is a per-axis delta derived from **one base register per provider thread and axis, advanced in stream order** — never a base snapshot copied at turn dispatch — and attributed to **the turn the metered frame itself names**, never to whichever turn is open at arrival. Base establishment is two-armed: a fresh provider session bases at **zero**, its first reading metering in full, and a provider-native resume bases at **the daemon's own prior-emitted cumulative sum for that thread**, never at the first post-resume reading. A context compaction does not re-base; a decrease on a declared-cumulative axis floors at zero with a recorded diagnostic rather than emitting negative spend; and a wire-declared per-turn figure **corroborates** the derived interval — mismatch diagnosed — and never substitutes for it. The normalized axes are a partition — the input axis is uncached input, subtracted only where the breakdown's own sum identity confirms containment, with an unconfirmed identity emitting unsubtracted plus a diagnostic — and cost is derived from the provider's full breakdown, never by re-multiplying that partition. Source: [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-004 §Interfaces And Contracts](../specs/004-provider-driver-contract-and-capabilities.md#interfaces-and-contracts). Enforced by: `provider/usage-delta-accountant.ts` as the single metering path both normalizers emit through (T3.11), with the floor-hit, the cross-check mismatch, the failed containment identity, and the retained cache split all landing on the T3.11 `DriverDiagnosticRecord` channel. Test: T3.11's cumulative-sequence, interleaved-attribution, fresh-first-reading, resume-prior-emitted-sum, compaction-no-re-base, late-frame, floor-hit, cross-check-mismatch, nested-cache, and failed-identity assertions (AC19).
- **I-003-11** — Only the session's own thread projects, and no child's spend or interactive request is lost. Every inbound provider frame is classified by family against the pinned stream-surface census before any projection decision: a thread-scoped family routes by explicit thread identity, a censused connection- or account-scoped family routes without one, and an unrecognized family with no thread identity quarantines. Thread identities register ahead of the refusal rule — the session's own at establishment, a child's from the provider's parent-linked announcement — with a present-but-unregistered identity held in a bounded pending-registration buffer (released on registration, shed with a diagnostic on timeout) distinct from the quarantine an absent or unrecognized identity enters, both bounded and reported, never projected and never attributed to the parent by arrival order. Usage counters and child-raised interactive requests are both carved out **ahead of** suppression — provider-attributed subagent spend lands on the (`runId`, `provider`, `subagentId`) triple, provider-internal child spend lands on the parent run at run scope, and a child's request routes through the same dispatch/approval pipeline as the parent's and is answered on the child's own correlation — so suppression governs the child's transcript projection alone; child lifecycle reaches the transcript only as `subagent.started` / `subagent.completed`. Source: [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior), [Spec-014 §Provider-Native Subagents](../specs/014-multi-agent-orchestration.md#provider-native-subagents). Enforced by: `provider/thread-frame-router.ts` as the single routing decision both normalizers consult (T3.11), consumed unchanged by T3.14's terminal-emission boundary, which adds no second routing decision. Test: T3.11's foreign-thread-suppression, connection-scoped-pass, unknown-family-quarantine, absent-identity-quarantine, quarantine-shed, pending-hold-release, hold-timeout-shed, child-spend-attribution, compaction-child-run-scope, child-request-carve-through, and surviving-lifecycle-pair assertions (AC20).
- **I-003-12** — A console-parity operation settles on the provider's own evidence, and a provider command is bound to where it was read from. `compactContext` reports success only after the provider's typed compaction frame is observed, never on the request being accepted; a `driver_command` frame carrying a provider command is dispatched only after that command's literal name is found in the enumeration read for **that session's** `(driverName, providerAccountId)`; and an entry from `listProviderCommands` is offerable and dispatchable only through agents of that same binding. Source: [Spec-004 §Desktop Console Parity Surfaces](../specs/004-provider-driver-contract-and-capabilities.md#desktop-console-parity-surfaces); [Spec-004 §Required Behavior](../specs/004-provider-driver-contract-and-capabilities.md#required-behavior) (the `driver_command` frame and its two guards). Enforced by: T3.21 legs (a) and (b). Test: an ack-without-a-compaction-frame settles as a failure; an absent command name refuses before sending; a cross-binding dispatch refuses as `driver.capability_unsupported` (T3.21; T4.9).

- **I-003-13** — A turn whose delivery was not confirmed is never re-sent automatically, because a resend repeats its spend. A send left unknown by a dropped connection, a timeout or a daemon restart is settled by reading the provider's conversation back before any further send on that session and comparing person-authored turns by position, never by text; a conversation that cannot be read back fails the run with the turn unsent. Test: T3.14's dropped-acknowledgment cases — turn present, turn absent, no read-back.

### CP-003-1 — `runtime-binding-store.ts` recovery-aware extension contract owed to [Plan-012](./012-persistence-and-recovery.md)

Plan-003 Phase 2 (T2.2) owns `packages/runtime-daemon/src/provider/runtime-binding-store.ts`. Plan-012 extends the store with recovery-aware persistence methods. The extension contract:

- The `RuntimeBindingStore` exposes `findResumableBindings(...)` as a queryable seam where Plan-012 may add recovery-aware predicates (e.g., bindings with stale checkpoints, bindings marked recovery-needed via the dedicated `recovery_checkpoints` table at `docs/architecture/schemas/local-sqlite-schema.md §Recovery Tables (Plan-012)`).
- Row-level recovery state lives in Plan-012's `recovery_checkpoints` table (not on `runtime_bindings`). Plan-003's `resumeSession` returns the typed failure result (T3.1/T3.6); Plan-012's recovery dispatcher receives the result and writes the corresponding row to `recovery_checkpoints` via a Plan-012-defined extension method on `RuntimeBindingStore`, then emits the existing `run.failed` event with `recoveryCondition: 'recovery-needed'` per [Spec-005 §Run Lifecycle (run_lifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle).

**Why bidirectional.** Plan-012 reviewers see the consumer dependency; Plan-003 reviewers (especially Phase 2 PR authors) must know that the binding-store's public method surface is contractually required to support Plan-012's recovery dispatch without further Plan-003 changes.

### CP-003-3 — Recovery-needed surface owed to [Plan-004](./004-session-event-taxonomy-and-audit-log.md) / [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)

**Capability state is stored, never evented.** The driver tables hold the current capability state, `hydrate()` rebuilds it without applying any event, and the cache invalidates from the writer's `snapshotChange` (T2.4). Nothing reads a capability event, so Plan-003 emits none.

**Recovery-needed condition reuses existing `run.failed` surface.** [Spec-004 §Fallback Behavior](../specs/004-provider-driver-contract-and-capabilities.md#fallback-behavior) calls for drivers to "surface a visible `recovery-needed` condition" on resume-handle failure. [Spec-005 §Run Lifecycle (run_lifecycle)](../specs/005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle) already declares this surface: `run.failed` payload includes `recoveryCondition?: 'recovery-needed'`. Plan-003 does NOT emit a separate `driver.recovery_needed` event. Instead:

1. Plan-003's `resumeSession` returns a typed failure result (T3.1, T3.6).
2. Plan-012's recovery dispatcher receives the typed result.
3. Plan-012 emits the existing `run.failed` event with `recoveryCondition: 'recovery-needed'`.

This keeps the recovery-needed signal on the canonical run-lifecycle surface where downstream consumers already subscribe; avoids creating a parallel driver-specific recovery event.

**What Plan-004 supplies.** Plan-004 Phase 3 defines `providerFailureDetail?: string` on the `run.failed` payload (the `RunStateChangeEvent` member, in [`run-control-payloads.md` §Plan-002 — Queue Steer Pause Resume](../architecture/contracts/run-control-payloads.md#plan-002--queue-steer-pause-resume)). It mirrors the `failed`-variant `providerFailureDetail` field of `DriverResumeResult` (in [`provider-driver-payloads.md` §Plan-003 — Provider Driver Contract (Internal Interface)](../architecture/contracts/provider-driver-payloads.md#plan-003--provider-driver-contract-internal-interface), authored by Plan-003 T1.6): Plan-012's recovery dispatcher reads the typed failure detail from the driver result and emits it on the canonical `run.failed` event, so the audit log carries a reason the person can act on without re-querying the driver.

**Why bidirectional.** Recovery-needed flows through Plan-012, not directly from the driver, so the driver's `resumeSession` return type stays a pure typed failure result; this plan's result feeds Plan-004's `run.failed` field.
