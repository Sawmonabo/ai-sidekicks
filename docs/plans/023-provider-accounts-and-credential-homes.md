## Goal

Deliver the node-local provider-account plane: a registry of provider accounts, per-account isolated credential homes wired into the existing constructed-environment discipline, account resolution from a definition's or workflow step's pin or the provider's current account, with fail-closed validation at spawn, the account switch that moves unpinned sessions in place, the account identity and credential generation that other specs consume by name, and the per-account cost attribution the session cost receipt and the Providers page's spend lines read.

## Scope

- The `provider_accounts` table and its contracts.
- The account registry service: registration, listing, default selection, removal, and the durable authentication-probe state, keyed per `(driver, account)`.
- Account identity and credential generation as defined derivations, produced here and consumed elsewhere.
- Per-account credential homes: construction, the reserved run-provisioned variables, spawn-time validation, and the fail-closed refusals.
- Answering the provider-initiated credential-refresh server request from the provider's own renewal in the account's home.
- The `providerAccount` wire namespace, the `provider` root beside it (each provider's own settings, standing rules, install and conversation import), the CLI surface, and the per-account spend read the Providers page draws.

## Non-Goals

- **No cost fold of its own.** Every cost figure this plan surfaces is supplied by the Plan-013 `BudgetAccountant`'s committed-spend accessor. This plan builds no second accountant ([Spec-014 §Cost Figure Display Consistency](../specs/014-multi-agent-orchestration.md#cost-figure-display-consistency) clause (a)). What it does own is the **per-turn usage projection** the by-day and by-model slices are group-bys over: a projection of the same `usage_telemetry` events the accountant folds, rebuilt on replay like every other one, served through that same accessor, and not a second set of arithmetic.
- **No session cost receipt.** The receipt itself is Plan-013's surface; this plan provides the account axis it reads (CP-023-3).
- **No Plan-003 driver-internal authoring.** The account leg of the driver contract lands in Plan-003's own tasks under CP-023-1; this plan does not author files in the provider-driver tree.
- **No control-plane surface.** No Postgres table, no tRPC procedure, no relay payload.
- **No first-run step.** First run asks nothing about providers: a provider is installed, registered and signed in on Settings › Providers, which reads this plan's registry and readiness derivation ([Spec-025 §Node provider readiness and the sign-in handoff](../specs/025-provider-accounts-and-credential-homes.md#node-provider-readiness-and-the-sign-in-handoff)).

## Invariants

The following invariants are **load-bearing** and MUST be preserved across all Plan-023 PRs and downstream extensions.

### I-023-1 — Account identity is opaque, immutable, and never derived from credential material

An account's `accountId` is daemon-minted at registration, opaque to callers, immutable for the account's lifetime, and never reused after removal. It is not derived from a credential, token, email address, subscription identifier, or filesystem path.

**Grounds in.** [Spec-025 §Account identity and credential generation](../specs/025-provider-accounts-and-credential-homes.md#account-identity-and-credential-generation).

**Why load-bearing.** Every consumer of the account axis keys on this value: the attention-key fold at Plan-014, the quota display at Plan-010, the cost receipt at Plan-013, and this plan's own registry. An identity derived from credential material would fragment an account's history at every token refresh — the same account would appear as several — and would place account material on every payload carrying it, breaching the inherited no-token-custody posture.

**Verification.** Registry unit tests assert identity stability across a simulated re-authentication, a billing-mode correction, and a default change; a rejection row asserts that a caller-supplied `accountId` at registration is refused.

### I-023-2 — Credential generation is monotonic per account and never resets

`credentialGeneration` starts at 1 and strictly increases at each credential-home lifecycle transition the daemon performs or observes. It never decreases and never resets, including across a home reset.

**Grounds in.** [Spec-025 §Account identity and credential generation](../specs/025-provider-accounts-and-credential-homes.md#account-identity-and-credential-generation).

**Why load-bearing.** The attention-key fold at [Spec-015 §Provider-limit pacing and durable resumption (SA-38)](../specs/015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-38) composes on the generation held stable across a refusing dispatch; a reset would let a repaired account's fresh refusals fold into the stale epoch, so the person's re-authentication would appear not to have worked. Monotonicity is also what lets any consumer order two observations without a clock.

**Verification.** Registry tests assert strict increase across each transition class and assert that a home reset increments rather than restarts; a replay test asserts the value is durable, not recomputed.

### I-023-3 — A provider process is never spawned against an unvalidated account

Before spawn the daemon MUST establish that the account is registered and that its credential home exists. Any other outcome refuses the run before any provider process is created. No sign-in check runs before a session starts: a run on an account whose login has gone starts and meets the provider's own refusal.

**Grounds in.** [Spec-025 §Validation at spawn — fail-closed](../specs/025-provider-accounts-and-credential-homes.md#validation-at-spawn--fail-closed).

**Why load-bearing.** The two failure modes this forecloses are both silent: falling back to the default account bills the wrong account; falling back to ambient configuration makes the paying account unknowable and defeats the receipt. The refusal is what makes the cost receipt's paying-account column trustworthy.

**Verification.** Spawn-path tests assert refusal with no child process created for each of: unregistered account and absent home. A negative control asserts that a registered account with its home present spawns whatever its stored sign-in reading.

### I-023-4 — Reserved credential-home variables are daemon-set, never inherited, and never empty

The provider credential-home variables are a named set for each provider. The daemon is their sole writer; an inherited or caller-supplied value of a reserved name is discarded at environment construction rather than merged; and the daemon emits an absolute path or omits the variable entirely — never an empty string.

**Grounds in.** [Spec-025 §Credential homes and the constructed environment](../specs/025-provider-accounts-and-credential-homes.md#credential-homes-and-the-constructed-environment).

**Why load-bearing.** The reservation is the only thing that makes account binding trustworthy: a caller able to set the home could redirect a run's credentials to an account it was not authorized to spend from. The empty-string clause closes a distinct and sharper hole — on at least one provider leg an empty value behaves as unset _and_ suppresses the companion variable, silently collapsing a home partition back to the shared credential entry. That failure is both fail-open and silent, so it cannot be caught by observing that the run succeeded.

**Verification.** Environment-construction tests assert reserved names are stripped from a polluted inherited environment before provisioning, assert the daemon-set value survives, and assert that an empty value is never emitted for any account. A rejection row asserts a registration whose home path is empty or relative is refused.

### I-023-5 — Exactly one current account per provider, enforced by the schema

At most one row per provider carries the current-account flag — the column the schema calls the default flag — enforced by a partial unique index rather than by application code.

**Grounds in.** [Spec-025 §The account registry](../specs/025-provider-accounts-and-credential-homes.md#the-account-registry).

**Why load-bearing.** Two current accounts make run admission non-deterministic in the exact place where determinism decides who pays, and they would make the account switch ambiguous as well — a press that moves live sessions has to have one unambiguous destination. Enforcing it in application code leaves the invariant true only while every write path remembers it; enforcing it in the index makes the violating state unrepresentable.

**Verification.** The schema's test inserts a second current account for one provider and asserts the constraint rejects it; a same-provider handover test asserts the transactional clear-then-set path succeeds.

### I-023-6 — The daemon brokers credential refresh and stores nothing

Answering the current-account Codex service's credential-refresh server request resolves the account the service runs on, runs `account/read {refreshToken: true}` in that account's own home so the provider's own code renews the login there, re-reads the renewed tokens from that home's `auth.json`, and hands them to the service. The tokens the daemon hands the service live only in its memory: the daemon does not write them into its persistence, does not log them, does not place them on any event or error payload, and does not serve them to any client.

**Grounds in.** [Spec-025 §Credential-refresh brokering](../specs/025-provider-accounts-and-credential-homes.md#credential-refresh-brokering), [ADR-026 §Decision](../decisions/026-provider-credential-custody-posture.md#decision).

**Why load-bearing.** This is the one code path where credential material transits daemon-adjacent machinery, so it is the one place the bounded-custody posture could be lost by accident rather than by decision. A refresh answered from the wrong home also hands one account's credential to another account's service — the precise mix-up per-account isolation exists to prevent.

**Verification.** Refresh tests assert no credential-shaped value reaches storage, logs, events, errors or a client; assert the answer comes from the requesting service's own account home after the provider's renewing read ran there; assert the refusal path for an unregistered account and for a missing home; and assert a refresh leaves `credentialGeneration` unchanged.

### I-023-7 — Sharing a credential home is never a fallback

No execution path, degradation, recovery, or error handler causes two accounts to resolve to the same credential home.

**Grounds in.** [Spec-025 §Fallback Behavior](../specs/025-provider-accounts-and-credential-homes.md#fallback-behavior).

**Why load-bearing.** Every other degradation in this plan is safe — refusing is visible. Sharing a home is the one degradation that silently destroys the person's credentials, and it is the state the whole isolation design exists to make unreachable. Stating it as an invariant makes it reviewable rather than merely intended.

**Verification.** A registry constraint asserts home-path uniqueness across accounts; a spawn test asserts that every refusal path leaves home assignment unchanged rather than coalescing.

### I-023-8 — Provider readiness is derived, stored-read, and advisory

Readiness is computed per provider by the same resolution the spawn path performs — resolve the default account, then report that account's **stored** last observed authentication probe result verbatim, with two registry-shape arms where resolution reaches no account. Deriving it MUST NOT spawn a provider process, MUST NOT open, parse, copy, or transmit credential material, MUST NOT compute a keychain entry name, and MUST NOT run a provider sign-in command. It authorizes nothing: a session starts whatever readiness last reported, and I-023-3 re-validates registration and the home at spawn.

**Grounds in.** [Spec-025 §Node provider readiness and the sign-in handoff](../specs/025-provider-accounts-and-credential-homes.md#node-provider-readiness-and-the-sign-in-handoff).

**Why load-bearing.** A readiness surface is worth having only if every reader sees one derivation. Re-deriving the predicate anywhere else guarantees that two readers eventually disagree; probing on every read turns a pollable surface into a provider-process fork bomb; and letting readiness authorize a spawn would convert a cached observation into a grant.

**Verification.** A registry read against a two-account node asserts zero child processes spawned and zero credential-file opens, with the reply's observation timestamp equal to the stored row's. A negative control mutates the stored probe result and asserts the readiness arm follows it without a new probe. A spawn bound to an account whose stored reading is authenticated but whose home has since been removed asserts refusal.

### I-023-9 — No surface claims authentication it has not observed, and remedies disclose in messages only

No surface reports a provider as authenticated on any reading other than the authenticated arm — `indeterminate` included, which renders as undetermined rather than as a sign-in failure — and no authenticated claim is manufactured from a plan label, a subscription echo, a declared billing mode, or the existence of a home directory. Guidance naming a credential home or a provider sign-in invocation is **for the person only**, and the rule binds the **reader rather than the encoding**: it reaches the person through message text or through the readiness reply's `remedy` member on the device-authorized `providerAccount.list` — and never an event payload, anything the control plane can read, a refusal envelope, or a log line. That the remedy travels structured does not relax the rule; it is why the rule has to be stated about the audience. Provider sign-in process output is never placed in an error payload, an event, or a log.

**Grounds in.** [Spec-025 §Node provider readiness and the sign-in handoff](../specs/025-provider-accounts-and-credential-homes.md#node-provider-readiness-and-the-sign-in-handoff).

**Why load-bearing.** Both halves close a disclosure or honesty leak that is invisible until it matters. A false authenticated claim sends the person away satisfied while every run meets the provider's sign-in refusal; a credential-home path on an evented payload or anything the control plane can read puts a node-local filesystem location — recorded as an account-plane PII residual in [Spec-020 §PII Data Map](../specs/020-data-retention-and-gdpr.md#pii-data-map) — into a durable, replicated record it was never scoped for; and provider sign-in output may carry OAuth state, PKCE values, or credential fields.

**Verification.** A table-driven assertion over every readiness arm that only the authenticated arm renders as authenticated, and that the `remedy` member is present on each non-authenticated arm and absent on the authenticated one. An event-payload and log-scrape test asserting no credential-home path appears on any emitted event, log line, or relay frame the control plane can read for a node with a husked home — the readiness reply excluded by construction, since it is the one surface for the person that the rule permits. A refusal test asserting the error payload carries neither captured provider output nor the remedy.

### I-023-10 — Credential material crosses exactly one input and no output

The daemon accepts credential material on exactly one wire input — `ProviderAccountRegisterRequest.nonInteractiveToken` — and emits it on none. No reply, event, notification, error payload, log line, metric, span attribute, or diagnostic dump carries it, in any shape or under any name; no argument vector carries it; and it is never written into a credential home. Admission requires all of [ADR-026](../decisions/026-provider-credential-custody-posture.md) D2's conditions and refuses on any failure, with the refusal naming the failed condition and never quoting the supplied value. The sealed value lives in the operating system's keychain and reaches a provider only on the channel the provider documents: a Claude Code setup token on `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`, a pipe per spawn, and on `CLAUDE_CODE_OAUTH_TOKEN` through `apply_flag_settings {env}` at an account switch; a Codex API key by `account/login/start {type: "apiKey", apiKey}` to a service started with `-c cli_auth_credentials_store="ephemeral"`. It is never a variable in a process's start-up environment.

**Grounds in.** [Spec-025 §Non-Goals](../specs/025-provider-accounts-and-credential-homes.md#non-goals), [Spec-025 §Non-interactive token registration](../specs/025-provider-accounts-and-credential-homes.md#non-interactive-token-registration), [ADR-026 §Decision](../decisions/026-provider-credential-custody-posture.md#decision).

**Why load-bearing.** [ADR-026 §Failure Mode Analysis](../decisions/026-provider-credential-custody-posture.md#failure-mode-analysis-t2) names incremental widening as a failure mode. Stated as _one input, zero outputs_, the rule makes a widening plain to a reviewer: a second credential-accepting member on the `providerAccount` contract is that widening. The output half is the security-critical half: a token sealed correctly and then rendered into a refusal message has been disclosed regardless of how it was stored, and at least one upstream provider leg has shipped a fix for exactly that class.

**Verification.** A leak test driving a token through a successful registration, a refused one, and a forced error, asserting its bytes appear in no reply, notification, or error payload. A redaction test driving a registration through the transport's request-logging path and asserting the member is absent from the emitted record. A refusal test asserting that the supplied value appears in no byte of a registration refusal. A seal test asserting registration refuses with `provideraccount.credential_seal_refused` and its `cause` (`locked` or `unavailable`) where the keychain refuses, with nothing written anywhere else. A home test asserting no file inside the credential home changes across a token-mode registration.

### I-023-11 — The daemon reads a credential only where ADR-026 names it, and the provider renews its own inside its own home

The background observer takes its reading by asking each provider **its own limits question inside that account's own daemon-owned credential home**, and on one leg that read renews the provider's login as a side effect, which is the keep-alive. The daemon itself MUST NOT write or copy credential material, MUST NOT read it beyond the moves [ADR-026](../decisions/026-provider-credential-custody-posture.md) names, and MUST NOT speak a provider token endpoint. The observer's home MUST NEVER be the person's own `~/.claude` or `~/.codex`, because the race the rotation rule guards against exists only where two holders share one grant. It is single-flight per account and **initiates** no reading while a turn is live on that account: recording a rolling update the provider pushes with the turn is not initiating one, and the turn-end read on the other leg runs in the account's own reader once the turn has ended, never in the session's process. It writes the stored health pair as its third sanctioned writer, and **a renewal the provider performs inside its own home is not a credential-home lifecycle transition**, so it MUST NOT bump `credentialGeneration`, which stays bound to I-023-2's transitions.

**Two acts on this plane spend a turn, and each is priced as one.** At a window's reset the daemon sends one short message on the provider's smallest model in a throwaway process in that account's own home; and a pasted Claude token, which has no `get_usage` read, is read every five minutes by that same turn, whose `rate_limit_event` is the reading. Both are deliberately outside the observer's zero-cost rule rather than exceptions inside it: the reading costs nothing wherever the provider offers a turn-free read, and a turn is spent only where a window must begin or no other read exists. Both share the per-account opt-out, and each usage row is an ordinary per-turn row under that account with no session attributed to it, counted in the account's spend.

**Grounds in.** [Spec-025 §Credential-home health observation](../specs/025-provider-accounts-and-credential-homes.md#credential-home-health-observation), [Provider Wire Reference §claude](../reference/provider-wire/claude.md), [Provider Wire Reference §codex](../reference/provider-wire/codex.md).

**Why load-bearing.** Both pinned providers rotate refresh tokens **single-use with no grace window**, so a **lost** rotation does not degrade a credential — it **ends the person's login**, with a browser sign-in as the only remedy. That is what makes the two halves of this invariant load-bearing in opposite directions.

The **isolation** half is what makes the renewal safe: a rotation is lost when two holders of one grant race for it, which is the observed failure mode of the surveyed tool that refreshes on a timer against the person's own store. Inside a home nothing but our own provider processes ever opens, there is no second holder, and the provider's own guard covers our own neighbors — on the Codex leg it re-reads its credential file under its refresh lock before renewing and skips when another process got there first. The **custody** half is what keeps the daemon out of it: the renewal is the provider's own code, running in its own home, doing what it does for itself; a daemon that wrote the file or spoke the token endpoint would be a second holder of the grant, the one the isolation removed. The daemon's reads of a renewed token are ADR-026's named moves, taken after the provider has renewed and under its lock.

The generation clause protects a different consumer: [Spec-015 §Provider-limit pacing and durable resumption (SA-38)](../specs/015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-38) keys parked work on `(accountId, credentialGeneration)`, so an observer that bumped on a routine renewal — many times a day per account on the five-minute cadence — would end a parked-work attention epoch and stale every stored quota reading for nothing that changed.

**Verification.** A **custody** test running a full observation cycle against seeded homes on both provider legs and asserting the daemon wrote no credential file or keychain entry, read none beyond the moves ADR-026 names, and issued no request to a provider token endpoint of its own — with the Codex home's own refresh marker **permitted to move**, since that renewal is the point. A **home** test asserting every registered account's home resolves to a daemon-owned absolute path and that a home equal to the person's own ambient provider directory is refused at registration. A **call-surface** test asserting the observer's provider-call allowlist holds exactly the two reads per leg this plan names, the turn-end read in the account's own reader, the window-start message and a pasted token's read turn, and nothing else — and that nothing is sent to a session's process. A **concurrency** test asserting the observer is single-flight per account and takes no reading while a turn is live on that account. A **generation** test asserting an observation writes the stored pair, that a renewal observed inside a home leaves `credentialGeneration` unchanged, and that a parked-work attention key resolves identically across it. A **cost** test asserting neither leg's turn-free read is charged a model turn, that the window-start turn and a pasted token's read each spend exactly one turn on the provider's smallest model, in a process holding no session, counted in that account's spend, and that both are suppressed with the account's opt-out.

### I-023-12 — Quota readings key on the limit identifier, and newest observation wins

An account's quota readings are keyed `(accountId, limitId)`, with the window length carried as an attribute of the reading and **naming the window**, never its position in the provider's reply. Each leg's identifier comes from the carrier that is populated: on the Claude leg the `limits[]` entries, a per-model entry keyed from the model's display name and never from the flat per-model keys, which answer null; on the Codex leg the keys of `rateLimitsByLimitId`. A reading naming no limit takes the reserved identifier `default`. Where two readings key alike, the later `observedAt` is current and `source` breaks only exact ties. A `probe`-source reading **set** is the account's whole standing and replaces the stored set; a `run`-source reading is the provider's own sparse push and is merged into it, pruning nothing it does not name. Every reading carries its read time and every rendered window shows it.

**Grounds in.** [Spec-025 §Per-limit provider quota](../specs/025-provider-accounts-and-credential-homes.md#per-limit-provider-quota), [Provider Wire Reference §claude](../reference/provider-wire/claude.md).

**Why load-bearing.** The pinned Claude surface publishes several limits at once of which **more than one share a 10080-minute window** — the account-wide weekly window and a per-model weekly window are two different limits over the same length. A key of `(account, windowMins)` therefore admits only one of them, the survivor decided by arrival order, so a node would render one weekly limit as the account's weekly standing while the others silently vanished and which one survived would change between restarts. That is a wrong number presented confidently, which is worse than no number.

Three further clauses each close a way the same surface goes wrong quietly:

- **Reading the flat per-model keys.** They exist in the binary and answer null, so a design keyed on them renders an empty per-model window for an account with real per-model usage — a full allowance the daemon never observed.
- **Reading a window's position as its meaning.** The provider has moved a given window between the primary and secondary slots of one limit id, so a surface that labeled the primary slot would relabel every bar the day that moved.
- **Treating a sparse push as a whole reading.** Both providers' pushed updates carry the windows that moved and no others, so a push that replaced the stored set would delete every window it happened not to name.

The precedence clause closes the ordering failure: with two sanctioned sources writing one key, ordering by arrival, or by preferring one source over the other, lets a stale reading mask real consumption — and the existing display rule already refuses to drop a lower utilization except when window identity is confirmed, which only a stable key makes possible. The read time is what keeps an old reading honest rather than current: on an idle account a correct percentage can be hours old, and a percentage with no read time is presented as now.

**Verification.** A store test writing several readings for one account across distinct limits that share one window length and asserting all are retained and readable. A per-leg derivation test asserting a Claude per-model window is keyed from the model's display name in `limits[]` and that a reply whose flat per-model keys are null yields no window from them. A labeling test asserting a window is named from its reported length and that swapping two windows between the primary and secondary slots of one limit id changes no label. A degenerate-case test asserting a reading with no limit identifier lands under `default` and that the single-window shape round-trips unchanged. A completeness test asserting a `probe` set replaces the stored set and a `run` reading merges into it without pruning. A precedence test writing an older reading after a newer one for the same key and asserting the newer stands, plus an equal-timestamp test asserting the source tiebreak fires only there. A freshness test asserting every stored reading carries its read time and that a reading with none is refused rather than rendered.

## Cross-Plan Obligations

Plan-023 declares the following obligations on adjacent plans (or inherits obligations declared by them). Implementation cannot proceed (or must defer specific surfaces) without these being satisfied or explicitly staged.

### CP-023-1 — Plan-003 threads account identity through the driver contract and spawn path

Plan-003 owns the provider-driver tree and the spawn-bound configuration record. It carries the account leg: the optional account data leg on the session-create and resume parameter surfaces, its persistence through the binding's spawn-bound configuration record so a resume re-realizes the same account, the per-`(driver, account)` scoping of the cached authentication state and its refresh cadence, and the reserved credential-home variables in the constructed child environment.

**Resolution.** Plan-003 Phase 3B ([Plan-003 §Phase 3B — Provider-account seam + typed usage-limit signal](./003-provider-driver-contract-and-capabilities.md#phase-3b--provider-account-seam--typed-usage-limit-signal)) carries it. Plan-023 authors no file under the provider-driver tree; it supplies the registry read the Plan-003 tasks consume.

### CP-023-2 — Plan-003 mints the typed provider-limit signal that this plan's account plane keys on

The typed provider usage-limit signal is a Plan-003-owned driver-contract surface (a sibling axis beside the recovery-condition set, never a widening of it). Plan-023 consumes it: the signal's account scoping keys on this plan's `accountId` and `credentialGeneration`.

**Resolution.** Plan-003 Phase 3B, task T3.44. Plan-023's consumption is read-only and adds no member to the signal.

### CP-023-3 — Plan-013 consumes the account axis on the session cost receipt

Plan-013 owns the committed-spend fold and the session cost receipt. This plan provides the paying account for each run (the admission stamp) and the account's billing mode (the registry read); Plan-013 renders them as receipt columns and enforces the billing-mode labeling rule.

**Resolution.** Plan-013 Phase 4B ([Plan-013 §Phase 4B — Session cost receipt](./013-multi-agent-orchestration.md#phase-4b--session-cost-receipt)) carries it. Plan-023 supplies data and asserts no display behavior of its own beyond the labeling rule stated in [Spec-025 §Billing mode](../specs/025-provider-accounts-and-credential-homes.md#billing-mode).

### CP-023-4 — Plan-023 joins the CP-013-11 committed-spend-fold consumer set

[Plan-013 §Cross-Plan Obligations](./013-multi-agent-orchestration.md#cross-plan-obligations) CP-013-11 obliges any plan that grows a cost-displaying surface to source every figure from the accountant's committed-spend accessor The per-account spend and the across-accounts total this plan draws on the Providers page are such a surface.

**Resolution.** The per-account spend read (T4.1) is a projection over the accountant's accessor with no independent fold, and the [Spec-014 §Cost Figure Display Consistency](../specs/014-multi-agent-orchestration.md#cost-figure-display-consistency) clause (b) declaration is carried per figure.

### CP-023-5 — Plan-010 renders the account-scoped provider quota

[Spec-011 §Rate-Limit Display](../specs/011-transcript-and-reasoning.md#rate-limit-display) states the account-scoped, event-sourced form. The producer side — account identity and credential generation on the account-scoped quota event — is registered here; the renderer is Plan-010's.

**Resolution.** The producer side is registered here; the renderer task is Plan-010-owned work and is deliberately not authored here.

### CP-023-6 — Plan-022's config-home observation is account-relative

Plan-022 observes provider configuration files inside a provider home and derives a per-binding governance digest from them. Once a binding's home is account-selected, the configuration Plan-022 observes is account-relative: two accounts of one provider may present different MCP inventories, and a governance digest is meaningful only within its account's home.

**Resolution.** Not a code dependency in either direction — the two plans share a substrate rather than an interface, and this plan writes nothing into a provider config file ([Spec-025 §Non-Goals](../specs/025-provider-accounts-and-credential-homes.md#non-goals), inheriting [Spec-024 §Non-Goals](../specs/024-mcp-server-configuration-and-governance.md#non-goals)). ## Data And Storage Changes

- Three new node-local tables per [Local SQLite Schema §Provider Account Tables (Plan-023)](../architecture/schemas/local-sqlite-schema.md#provider-account-tables-plan-023): `provider_accounts` (the registry), `provider_account_usage_windows` (the newest quota reading per `(accountId, limitId)`) and `provider_account_usage_turns` (the per-turn usage projection, one row per turn, built by T1.3). `provider_accounts` carries the observed authentication mode, the last observed refresh time, the recorded sign-in time, and the per-account observer opt-out, and the plan's tables are all in the daemon's one schema, proven by its test.
- The `provider_accounts` row also carries the name of an account added by a pasted token or API key (`display_label`, present only on those accounts and unique per provider without regard to case) and `wake_for_window_start_enabled` beside `window_start_enabled`; the provider root's settings live in one daemon table, one row per provider. The DDL for each is in [Local SQLite Schema §Provider Account Tables (Plan-023)](../architecture/schemas/local-sqlite-schema.md#provider-account-tables-plan-023).
- **The sealed token is not a column and not a table.** The [ADR-026](../decisions/026-provider-credential-custody-posture.md) D2 value lives in the operating system's keychain keyed by account identity, and never inside a credential home: daemon-owned bytes written into provider-owned space are indistinguishable from the provider's own to every later reader, including the provider's own tooling, which may rewrite or prune what it finds there. Every table in this plane keeps its no-credential-material property exactly; `provider_accounts` records only that an account's **observed** mode is the token mode, which is a label and not the material.
- **Row-canonical daemon configuration, not evented** — the `session_budgets` posture. The registry is the machine's own configuration, mutated by wire method from this machine or any linked device; it is not a session fact, carries no session scope, and takes no part in session replay. This is why it needs no event type and appears in no session transcript.
- **No control-plane table.** The shared schema's permitted row classes do not admit provider-account rows, and this plan does not widen that enumeration.
- **One per-turn usage projection, `provider_account_usage_turns`, and no parallel ledger.** Cost enforcement stays the in-memory fold at Plan-013; this plan projects the same `usage_telemetry` events into one append-only row per turn carrying the provider, the account, the credential generation observed with it, the session, the run, the model, the token counts, and the cost with the provenance the Plan-013 derivation ladder assigned it. It is events-canonical and rebuilt byte-equal on replay, it is a child of the registry and cascades away with its account, and it adds an **axis** rather than an accountant: a running total cannot be sliced by a day or a model it never kept. The account axis still rides the `run.queued` admission stamp; what this adds is the per-turn row the slices read.
- The provider-reported identity fields are personal data and are mapped at [Spec-020 §PII Data Map](../specs/020-data-retention-and-gdpr.md#pii-data-map); the one label the person types that the registry holds is the name of an account added by a pasted token or API key, which the provider names nowhere. The credential-home path is a filesystem location; no credential material is stored in this table.

## API And Transport Changes

- A node-local `providerAccount.*` JSON-RPC namespace: `list`, `subscribe`, `register`, `update` (billing mode, the keep-fresh switch, the window-start and wake switches, and the name of a pasted-credential account), `remove`, `setCurrent` — the verb that makes an account its provider's current one and, in the same act, moves every unpinned running session on that provider in place, its reply naming `movingSessions`, a session at `reviewed` moving onto a Claude Code account whose plan lacks auto mode running at `ask` with one `session.notice` of kind `level_unavailable` naming the level it left — `resetCredentialHome`, `probe`, **`login`, `loginCancel`**, `memoryImport` and `usageRead`. The subscription carries a wire-only notification and never an `EventEnvelope`, so the registry stays un-evented and no Spec-005 event type is minted by it. Registered under Plan-005's namespace registry at this plan's tier, the `driver.*` / `mcp.*` precedent. Shapes in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md).
- A sibling node-local `provider.*` root: `list`, `update`, `probe`, `protectedPathList`, `standingRuleList`, `standingRuleRevoke`, `terminalPluginUpdate`, `install`, `installSubscribe` and `installStop`; and the conversation import, `session.importPreview`, `session.import`, `session.importSubscribe` and `session.importStop` (T4.4 to T4.6).
- Run creation carries no account input; run admission stamps the resolved account — the run's definition or workflow-step pin, else the provider's current account — on the `run.queued` payload as a path-independent server stamp (`admittedProviderAccountId`, never client-suppliable — the `admittedModelFamily` precedent).
- The account-scoped quota event gains account identity and credential generation ([Spec-005 §Usage Telemetry](../specs/005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). Both payload growths are additive-optional under ADR-017.
- The registry list reply gains a per-provider **readiness projection** — exactly one entry per provider the request selects, carrying the derived state, the timestamp of the stored observation it was derived from, and the per-arm remedy. It is **required**: a reply permitted to omit readiness would push every client back into deriving it locally, which is what I-023-8 exists to forbid. **Readiness adds no verb to the namespace** and mints no refusal code, because every arm mirrors a refusal already registered.
- The `register` verb gains **one write-only member** carrying the [ADR-026](../decisions/026-provider-credential-custody-posture.md) D2 non-interactive token class — the single credential-accepting input on this wire, which I-023-10 makes checkable. It appears on no reply.
- The account-scoped quota event gains an additive-optional `limitId` and the axis re-keys onto `(providerAccountId, limitId)` (CP-023-7, I-023-12). Absent means the reserved `default` identifier, so no already-registered producer becomes invalid.
- Refusal codes for the fail-closed paths in [Error Contracts](../architecture/contracts/error-contracts.md) — among them `signin_unsupported`, `signin_in_flight` and `credential_seal_refused`.

## Test And Verification Plan

- **Unit:** registry CRUD and constraint rejection rows; identity stability and generation monotonicity; default-handover transaction; home-path validation (absolute, daemon-owned, outside any worktree, unique); environment construction under a polluted inherited environment.
- **Integration:** spawn refusal for each unvalidated-account class (unregistered account, absent home) with no child process created; resume re-realizing the same account from the durable record and refusing when it cannot; refresh brokering against the correct home with no material reaching storage, logs, events, or errors; two runs on two accounts of one provider running at once.

- **Adversarial-Tampering Boundary.** The verification suite exercises: a caller-supplied `accountId` at registration (rejected); a caller-supplied `admittedProviderAccountId` on run creation (ignored, server-stamped); reserved credential-home variables supplied by the caller, by the inherited environment, and by an execution posture (all discarded); an empty-string reserved variable (never emitted, and treated as a defect when observed); a home path pointing inside a repo working tree (rejected); a home path equal to another account's (rejected by uniqueness); a token-refresh server request arriving on a pinned session's own service (never expected, and refused), and one arriving on the current-account service answered only from that account's own home; and an account input on run creation (rejected by the schema).

## Rollback Or Fallback

- The registry is additive node-local configuration; with no accounts registered the daemon refuses provider runs with a typed refusal rather than misbehaving. The remedy for an **empty registry** is registration, not repair: the person registers an account through the node-local `providerAccount.register` surface (T2.1) and authenticates it into that account's own credential home, after which the same run starts. Re-authentication is the remedy for a **different** state — a registered account whose credentials have expired, which shows as the provider's own sign-in refusal on the run and on Settings › Providers — and is documented at [Provider Failure Runbook §Provider Re-Authentication (Per Account)](../operations/provider-failure-runbook.md#provider-re-authentication-per-account).
- The tables are plain additions to the daemon's one schema with no data dependency, so reverting them costs nothing beyond the registry rows.
- **There is no rollback that shares a credential home** (I-023-7). If the account plane must be disabled entirely, the correct degradation is to refuse provider runs, not to fall back to ambient credentials.

## Risks And Blockers

- **Provider credential-home variable names are version-fragile**, and one of the two Claude variables has no vendor documentation at all. Mitigated by resolving the reserved set from the provider reference at build time rather than embedding names in normative prose; a renamed variable shows as a failed sign-in in the daemon's logs and is investigated when seen.
- **Provider sign-in is surfaced where it is used** — Settings › Providers names an account that is not signed in and the one remedy that applies to it, so the gap shows there before the first refused run. The residual this leaves is honest and named rather than closed: a credential-free probe cannot distinguish a healthy first-party login from one whose stored credential has since been destroyed, so the authenticated arm is necessary and not sufficient. It is bounded by the provider's own sign-in refusal on the run and the per-account re-authentication runbook, and it is deliberately **not** closed by reading credential bytes — that would reverse the no-token-custody posture [ADR-026](../decisions/026-provider-credential-custody-posture.md) records.
