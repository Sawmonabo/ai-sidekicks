## Goal

Implement the project: a git repository attached once per machine as a durable RepoMount, or cloned from a URL and then attached; the project record and its actions; and explicit binding of a session's workspace to one of its places.

## Scope

This plan covers repo root resolution, the machine-level RepoMount and the project record beside it, clone from a URL, the machine's folder list (on the machine and for another device), workspace creation when a session binds, and mount and workspace health projection. A folder that is not a git repository is refused at attach.

## Non-Goals

- Worktree lifecycle
- PR preparation
- Rich diff UI
- Renderer views: the console's new-session picker, clone card, projects settings page and runtime settings page call this plan's methods and are built with the console ([Plan-021](./021-desktop-app-and-renderer.md))

## Preconditions

- [ ] **Repo identity keys on the git common directory.** Repo identity keys on the repository's git common directory, not on the enclosing working tree's own top level, so N linked worktrees of one repository resolve as ONE repository ([Spec-007 §Repo Identity And Common-Directory Keying (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-identity-and-common-directory-keying-v1-definition), the [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) canonical-root bullet, and acceptance criteria 4 and 5). `### Phase 2B — Repo Identity Keying And Resolution Hardening` is the owning code lane; this box checks when Phase 2B merges. **Phase 3 waits on Phase 2B**, because Phase 3 is the wire surface over an identity the daemon would otherwise still be computing wrong.

Target paths below assume the canonical implementation topology defined in [Container Architecture](../architecture/container-architecture.md).

## Invariants

- **I-007-1 — Canonical-root fidelity.** Every persisted RepoMount records the symlink-resolved absolute canonical repository root — the MAIN checkout's working-tree root, identified by the repository's git common directory (I-007-15) — and a user-entered path is never stored as the canonical root without resolution. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) + [Spec-007 §Pitfalls To Avoid](../specs/007-repo-attachment-and-workspace-binding.md#pitfalls-to-avoid) (pitfall); path-canonicalization bugs leak outside the trust envelope (§Risks And Blockers) and corrupt every downstream workspace/worktree root derivation (Plan-008/Plan-009). **Verification.** T1.5 unit tests (subdirectory input resolves to repo root; symlinked input resolves to realpath); T-007-2B-1 unit tests (a linked worktree's input resolves to the main-checkout root, not to the worktree's own top level); T2.3/T2.6 attach integration tests assert the persisted `canonical_root` carries the resolver output, not the request input.
- **I-007-2 — Explicit resolution failure.** Canonical-root resolution failure aborts attach with typed `repo.root_resolution_failed`; the daemon never guesses a root or silently substitutes the user-entered path. **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior); silent substitution converts a user typo into a durable wrong-root mount that every later run executes against. **Verification.** T1.5 failure-path tests; T1.4 typed-error test; T2.3 attach integration test (failed resolution persists no `repo_mounts` row).
- **I-007-3 — Trust-envelope containment.** A workspace execution root always resolves — post-symlink, platform-normalized — within the canonical root of the repo mount its session is bound to, OR within one of that repository's own git-registered working trees admitted under the same bidirectional-link and physical-containment screens, OR within a daemon-created execution root admitted by provenance (an arm the registration screens never narrow); containment is working-tree-boundary-aware — a candidate whose own enclosing working tree is not the admitted root it is tested against (a linked worktree nested beneath the canonical root) admits only through the registration arm, never by lexical containment; traversal or symlink escape is rejected with typed `repo.outside_trust_envelope`, and membership of a user-supplied root is re-verified at the run boundary — not only at bind — with loss of membership blocking the run and transitioning the workspace to `stale`. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) with the §Local Trust Envelope (V1 Definition) at [Spec-007 §Local Trust Envelope (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#local-trust-envelope-v1-definition); this is the security boundary between the session and the rest of the person's filesystem, and once identity keys on the common directory (I-007-15) a linked worktree is no longer path-contained in its own repository's canonical root, so containment alone would reject binds to working trees the repository demonstrably owns. **Verification.** T1.6 adversarial unit tests (`..` traversal, symlink escape, path-prefix collision, absolute-path escape); T-007-2B-3 admission tests (a registered working tree admitted; an unregistered sibling directory, a one-way pointer, and a registration whose git directory is not physically contained by the claimed common directory each rejected; a de-registered worktree NESTED beneath the canonical root rejected despite lexical containment while its registered twin admits); T-007-2B-4 run-boundary tests (a worktree unregistered after bind refuses at the next `assertWritable` and lands `stale`; a daemon-created root under the same loss stays writable); T2.4 bind integration test.
- **I-007-4 — A folder that is not a git repository is refused, never attached.** Attach refuses a path git positively reports as not a repository with `repo.root_resolution_failed`, reason `not_a_repository`, which the screen draws as `Could not attach: not a git repository`, and persists nothing; that verdict counts only when UNCONTRADICTED by a visible `.git` entry at the supplied path — damaged or unreadable repository metadata refuses `"vcs_error"`, never `not_a_repository`. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) + [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior) + AC3; a project is a repository, and reporting damaged metadata as "not a repository" hides the damage. **Verification.** T3.8 refusal tests: a plain directory refuses and leaves no `repo_mounts` row; an empty `.git` directory and a dangling gitfile refuse `"vcs_error"`.
- **I-007-5 — Repo-mount rows persist resolved identity plus provenance.** Every `repo_mounts` row stores the user-entered attach path (`local_path`, provenance), the resolver-produced canonical root (`canonical_root`), the owning `node_id`, and a lifecycle state from the closed set; trust-envelope enforcement and node-ownership routing key off `canonical_root`, never `local_path`. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) ("not only the user-entered path" — both values are meaningful), [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications) (canonical root + owner node + lifecycle state), [Spec-007 §Implementation Notes](../specs/007-repo-attachment-and-workspace-binding.md#implementation-notes) (node ownership). **Verification.** T2.1 schema test (NOT NULL `node_id`/`canonical_root`, state CHECK); T2.3 service test (attach with a subdirectory input stores the resolved root in `canonical_root` alongside the entered subpath in `local_path`).
- **I-007-6 — Workspace identity is stable across execution-mode switches.** No code path creates a new `workspaces` row for a mode switch; preparing the root again updates `execution_mode`/`fs_root` in place on the same `id`. **Why load-bearing.** [Spec-007 §Execution Mode Transitions](../specs/007-repo-attachment-and-workspace-binding.md#execution-mode-transitions) ("This is NOT a new workspace"); downstream run/diff attribution keys off the stable workspace id. **Verification.** T2.4 test — full `beginRootPreparation`/`completeRootPreparation` cycle retains `id` and row count.
- **I-007-7 — An unavailable execution root is observable as `stale` on every daemon read surface, and the write gate refuses stale workspaces.** **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior): stale transition + "new write runs must be blocked until repair." **Verification.** T2.5 test (probe-fail → health projection reports stale and reports the transition owed); T2.4 test (`markStale` persists the transition the projection derives; `assertWritable` throws `workspace.stale`).
- **I-007-9 — Every repo-mount/workspace state transition appends its matching Spec-005 `session_lifecycle` event exactly once.** **Why load-bearing.** The durable timeline is the product's audit surface; emission at the transition site (single seam, T2.2) prevents drift between rows and events. **Verification.** T2.2/T2.3/T2.4 tests assert the emitted event type sequence per transition (bind → `workspace.preparing` then `workspace.ready`; stale → `workspace.stale`; detach → one `workspace.archived` per dependent, each only after the commit that made it true, beside the project-level `repo.detached` ([Spec-007 §Detach Semantics (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#detach-semantics-v1-definition)). `repo.attached` and `repo.detached` are not session events and are not on the session event list.).
- **I-007-10 — Every `repo.*` method validates daemon-side before dispatch.** Each registered method carries its canonical contracts Zod request AND response schema, so the substrate validates inbound params before the handler runs and outbound results before they hit the wire; client-only workspace binding is structurally impossible. **Why load-bearing.** [Spec-007 §Pitfalls To Avoid](../specs/007-repo-attachment-and-workspace-binding.md#pitfalls-to-avoid) names "Allowing client-only workspace binding with no daemon validation" as the failure mode; the substrate validates only what is registered with it — a handler registered with permissive schemas silently reopens the pitfall. **Verification.** T3.4 assertions (3) and (5): schema-invalid params are rejected with the deps spy at zero calls; registration asserted against the canonical contracts schema objects.
- **I-007-11 — The SDK marshals; it never derives daemon-owned repo/workspace state.** `repoClient` caches nothing and computes no health, git metadata, or canonical root client-side; daemon-owned projections ride through verbatim. **Why load-bearing.** [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications) places repo health and git metadata in daemon-owned projection state "rather than client cache"; a deriving or caching SDK forks the source of truth and breaks the stale-workspace blocking contract downstream. **Verification.** T3.5 pass-through assertions: every response field equals the daemon-supplied payload; no transformation, no memoization between calls.
- **I-007-15 — Repo identity keys on the git common directory; execution roots stay per-working-tree.** Resolution identifies a repository by its git COMMON directory and returns the MAIN checkout's working-tree root as the canonical root, so — in every layout where git records the main working tree (the ordinary and submodule layouts; the `--separate-git-dir` layout's linked worktrees take the deliberate refusal arm instead, per the narrowed acceptance criterion 4) — every working tree of one repository resolves to one identical `repo_mounts.canonical_root`, while `workspaces.fs_root` continues to name the per-working-tree path the user bound or the daemon created. **Why load-bearing.** [Spec-007 §Repo Identity And Common-Directory Keying (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-identity-and-common-directory-keying-v1-definition); identity is the key for the active-mount uniqueness index and for every daemon cache, filesystem watch, remote fetch, and throttle window scoped to a repository — keying those on the enclosing working tree instead silently multiplies them per worktree, and the plausible over-correction (returning the common directory itself as the workspace path) would root every worktree's execution at the main checkout, which is a different and worse bug. **Verification.** T-007-2B-1 unit tests over real multi-worktree git fixtures: attach from the main checkout and from each of two linked worktrees yields one identical canonical root, and each resolution simultaneously reports that working tree's own distinct root; T-007-2B-4 acceptance test asserts the second worktree attach is refused `repo.already_attached` against the first mount while a bind rooted at that worktree still succeeds with its own `fs_root` — and that the refusal also fires through the service-level identity comparison when two attach paths resolve to DIFFERENT canonical roots sharing one common directory (the direct-to-common holder pair the canonical-root index cannot see).
- **I-007-16 — Resolution refuses rather than misattributes.** A supplied path that does not exist, git metadata that is present but unusable, a linked-worktree link that is not bidirectional or whose registration is not physically contained by the common directory it claims, and a git pointer file that is not a regular file are each refused with a typed `RepoRootResolutionError`; none of them continues the ancestor scan, and none is reported as not a git repository (`not_a_repository`). **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior) + [Spec-007 §Repo Identity And Common-Directory Keying (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-identity-and-common-directory-keying-v1-definition); walking up lexically from a path that does not exist attributes it to whatever repository contains its parent (a dotfiles repository at the person's home directory makes that wrong for nearly every path beneath it), continuing past unusable metadata attributes a damaged repository to its parent, a one-way pointer file is attacker-writable and would let a planted `.git` claim any repository, and an unscreened non-regular pointer (a FIFO named `commondir`) wedges the scan indefinitely. **Verification.** T-007-2B-2 unit tests, one refusal arm per clause plus a negative control per arm proving the honest shape still resolves; the FIFO arm is POSIX-gated with a seam-driven twin that runs on every platform.
- **I-007-17 — Identity mismatch is observable, not just refused.** A git-backed mount whose re-derived common directory no longer equals the attach-persisted anchor (`repo_mounts.metadata.commonDir`) both refuses binds and run handoffs through the persisted-identity match AND projects `RepoMountHealth.status = "identity_mismatch"` on every subsequent health-reporting read until re-attach; `unreachable` takes precedence when the canonical root cannot be probed at all, the verdict is derived at read time and never persisted, and a mount whose anchor is not yet persisted never projects the member. **Why load-bearing.** [Spec-007 §Repo Mount Health (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-mount-health-v1-definition) + acceptance criterion 6; without the third member the health projection keeps answering `healthy` for a mount whose every bind is refusing — a lying read model that tells the person nothing is wrong exactly when re-attach is the required recovery. **Verification.** T-007-2B-5 tests: a retargeted mount projects `identity_mismatch` on mount read — the health surface; the wire workspace list carries no health member, its workspaces surfacing the mismatch as the `stale` + `lastError` transition at the next run handoff; an unreachable root whose anchor would also mismatch projects `unreachable` (precedence pinned discriminatingly); the honest multi-worktree shape projects `healthy`; a mount whose anchor is not yet persisted never projects `identity_mismatch`.
- **I-007-18 — A mount belongs to the machine.** A repository is attached once per machine: attach takes no session and no node, the daemon stamps its own node on the mount, the active-mount uniqueness is per machine by canonical root and by common directory, and a second project record for an origin already attached is refused. A session binds to the mount in `session.create`'s own step, or through `repo.workspaceBind` on convert. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior); the machine's folder list names each folder once with what uses it, and a per-session mount can neither list once nor refuse removal only while live work uses the project. **Verification.** T3.8 tests: two sessions of one project bind to one mount; a second attach of the same origin mints no record; a node id in the request is not accepted.
- **I-007-19 — A clone keeps no credential and fetches only over https and ssh.** Git's questions reach the person through the daemon's askpass program and the answer goes to git and nowhere else; no credential is written by the app. Only https and ssh URLs clone, and the protocol allow list reaches submodule fetches. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior); a stored answer would be a credential the app never promised to hold, and a `file://` or `ext::` URL runs outside the transports the design allows. **Verification.** T3.10 tests: a `file://` URL and a bare local path refuse before git starts; a submodule on a disallowed protocol fails the clone; the answer to a password question appears in no row, log line or event.
- **I-007-20 — Another device names a folder only by a token the service minted.** `repo.attach` from another device takes a `folderToken` that `repo.folderList` minted for a folder it listed; the token lives ten minutes in the service's memory, and no path string from another device reaches the resolver. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior); a path typed on a phone would reach any folder the service can read. **Verification.** T3.11 tests: an expired or unknown token refuses; a token never listed refuses; a listed token attaches.

- **CP-007-10 — Turn-snapshot capture normalized to the enclosing working-tree top level.** A nested `boundRoot` makes an un-normalized capture too narrow: capture's `git -C <executionRoot> ls-files` legs are cwd-scoped and list only the nested prefix ([git-ls-files(1)](https://git-scm.com/docs/git-ls-files) — the no-pathspec listing covers the current working directory), so a snapshot taken at a nested root would name a narrower tree extent than the run works in. T-007-2B-4 normalizes capture's execution-root input to the enclosing working-tree top level at the `packages/runtime-daemon/src/git/turn-snapshot-service.ts` service entry (a Plan-008-owned file per the ownership row; Plan-008's reciprocal CP-008-15) — one normalization site, so every capture addresses the whole tree the run works in — the top level derived while the tree exists and carried durably as `workspaces.metadata.checkoutRoot`, and [Spec-008 §Turn-Boundary Snapshots](../specs/008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)' applicability rule records the normalization. Captures of one normalized checkout run one at a time, across every session working in it; runs are never held, and every file restore reads the checkpoint store ([Plan-013](./013-persistence-recovery-and-replay.md)). **How the recorded value reaches the callee.** The normalized root is **supplied**, not looked up: Plan-008 CP-008-12 keeps capture a pure callee, so the EXTEND does not add a `workspaces` read inside the snapshot service — it adds a caller-resolved `checkoutRoot` parameter, which the Plan-008 T3.2 run-setup gate captures per run into `run_execution_contexts.checkout_root` (from this plan's persisted `workspaces.metadata.checkoutRoot`; an absent key is derived from the just-materialized `execution_root`'s top level with the carrier healed — never `canonical_root`, the bind-time checkout) and the caller reads from that same row. Capture, running while the tree exists, re-verifies the supplied value against the live tree and fails typed on disagreement. ## Design Decisions

Each decision below is binding contract surface for the Tasks blocks.

- **D-007-1 — `repo.*` method-name strings.** Registered in `api-payload-contracts.md` §Repo Method-Name Registry: `repo.attach` (mutation; a path on the machine, or a `folderToken` from another device), `repo.mountRead` (query), `repo.mountList` (query), `repo.workspaceBind` (mutation; convert), `repo.detach` (mutation; Projects' `Delete` and Runtime's `Remove`), `repo.projectList` (live), `repo.projectRename`, `repo.projectArchive`, `repo.projectReactivate`, `repo.projectSetupUpdate`, `repo.projectEnvironmentUpdate`, `repo.projectBranchPatternUpdate` (mutations), `repo.clone`, `repo.cloneAnswer`, `repo.cloneCancel`, `repo.largeFilesPull` (mutations), `repo.cloneSubscribe` (stream), `repo.cloneFolderRead` (query), and `repo.folderList` (query). Tail style is dotted-camelCase per the `METHOD_NAME_FORMAT`. There is no execution-mode capabilities read: every project mount offers both places and a chat's workspace only its own root. `repo.mountList` replaces the per-session workspace list, which listed a different object. Method strings (imperative) are disjoint-by-form from the durable event names (past participle: `repo.attached`).
- **D-007-2 — `RepoMountHealth` is a derived projection object, never persisted.** Shape: `{ status: "healthy" | "unreachable" | "identity_mismatch"; checkedAt: string }` (ISO-8601; `identity_mismatch` is derived at read time from the attach-persisted identity anchor, with `unreachable` taking precedence and re-attach the named recovery). A render-ready discriminant (`status`) plus probe provenance (`checkedAt`). No `unknown` member — the on-read probe floor (D-007-5) means every read carries a fresh verdict. `unreachable` (not `stale`) avoids overloading the workspace-state vocabulary across axes. No `health` column lands in `repo_mounts` — [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications) pins health to projection state, not row state; the identity verdict is likewise derived per read, never stored. Semantics in [Spec-007 §Repo Mount Health (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-mount-health-v1-definition).
- **D-007-3 — `repo.*` error vocabulary.** error-contracts.md §Repo: `repo.not_found` (404), `repo.root_resolution_failed` (422), `repo.outside_trust_envelope` (403), `repo.already_attached` (409), `repo.detach_conflict` (409, refused while an agent runs anywhere in the project), `repo.folder_unreachable` (a folder in another WSL distribution), `repo.root_resolution_failed`'s `not_a_repository` reason for a folder that is not a git repository, and the clone and project refusals, each code landing with its contract; §Workspace gains `workspace.stale` (409, the write-gate code). Adjudication: `repo.root_resolution_failed` over the competing `repo.canonical_root_unresolvable` (two-of-three subagent convergence + status 422); `repo.outside_trust_envelope` over `repo.path_outside_trust_envelope` (two-of-three convergence); `repo.not_found` over `repo.mount_not_found` (matches the `session.not_found` / `workspace.not_found` registry precedent).
- **D-007-4 — Mount-first single funnel; every mount is a git repository.** `repo.attach` accepts a local path, or from another device a folder token, and refuses a path that is not a git repository; a chat's managed workspace is git-initialized from its first byte, so it is a git mount too. A workspace always binds by `repoMountId` (there is no mount-less workspace; `workspaces.repo_mount_id` is NOT NULL).
- **D-007-5 — Both places on every project mount; health detection is two-layer.** Every project mount offers a worktree of its own and the project's checkout, and a chat's managed workspace offers only its own root, so no capability is computed or read. A worktree that cannot be made surfaces when it is made, through the [Spec-007 §Execution Mode Transitions](../specs/007-repo-attachment-and-workspace-binding.md#execution-mode-transitions) failure path (Plan-008's surface), and the daemon never substitutes the checkout. Health detection: (1) on-read probe floor — every health-reporting read surface and every write gate synchronously probes filesystem availability before answering, persisting the `stale` workspace transition at probe time; (2) the mount-health re-probe runs on the working-folder watch and its slow tick, once at service start and once when the machine wakes, under the service's one scheduler; a mount that turns `unreachable` or `identity_mismatch` stops new runs in its sessions, and the session's banner names the folder.
- **D-007-6 — Detach semantics (V1).** Defined in [Spec-007 §Detach Semantics (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#detach-semantics-v1-definition): refuse with `repo.detach_conflict`, naming the running session, while an agent runs anywhere in the project (no force-detach in V1); otherwise forget the project record, archive the project's sessions, transition the mount to `detached` and archive all dependent workspaces, recording `repo.detached` + one `workspace.archived` each, and revoke every remembered approval rule of the project with `project_detached` in the same transaction, one `approval.rule_revoked` per rule ([Plan-010](./010-approvals-permissions-and-trust-boundaries.md) D-010-11); `detached` is terminal for the row — re-attach creates a new mount row. The console's detach doors are the projects settings page's `Delete` and the runtime settings page's `Remove` on the project's folder, one act. Contract shapes: `RepoDetachRequest { repoMountId }` / `RepoDetachResponse { repoMountId, state, archivedWorkspaceIds }` in api-payload-contracts.md §Plan-007, the reply gaining that the project record was forgotten.
- **D-007-7 — `repo_mounts` persistence model: provenance + canonical columns; per-machine uniqueness; no default workspace.** `local_path` keeps the user-entered attach path (provenance; [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) "not only the user-entered path" implies both are known); `canonical_root` carries the resolver output and is the key for trust-envelope checks and dedupe. The active-mount uniqueness binds the canonical root on this machine, with no session column: two entered aliases resolving to one root are one mount, and detached rows stay re-attachable as new rows. Additional columns: `node_id` (the daemon's own node, stamped by the daemon and never taken from the caller), `origin` (`attached` for a project's folder, `managed` for a chat's workspace, naming its one chat), `updated_at`. The project record beside the mount holds the display name, the folder slug fixed at attach, setup steps, environment rows, the branch-name pattern when set, whether it is archived, and a cloning mark while a clone runs. `workspaces` carries `metadata TEXT NOT NULL DEFAULT '{}'` (`lastError` key per [Spec-007 §Execution Mode Transitions](../specs/007-repo-attachment-and-workspace-binding.md#execution-mode-transitions)) and an `execution_mode` CHECK over `'bound-root' | 'provisioned-worktree'`. Attach creates no workspace and `RepoAttachResponse` carries no default workspace id: a session's workspace is made when the session is created in the project, or converted into it.

This supplement amends the Phase-1 resolver and trust-envelope modules and the Phase-2 attach/bind services, all of which have shipped: it EXTENDs those files and adds one new module, and it rewrites no shipped task row. Every surface it consumes already exists — the system `git` binary, the `GitFileExecutor` / `PathRealpathResolver` / `DirectoryReadabilityProbe` injectable seams, the `RepoRootResolutionError` reason union, and the `toComparableComponents` / `isContainedWithin` / `componentsEqual` comparison primitives — except one: T-007-2B-4's fixture reads `run_execution_contexts.checkout_root`, which Plan-008 Phase 3 delivers. It authors the one surface that was missing, a repository-registration reader. Phase 3 names this phase in its own precondition, so it never runs across the identity change.

**Goal.** Move repo identity off the enclosing working tree's top level and onto the repository's git common directory, so N working trees of one repository resolve as ONE repo mount, and harden resolution so a nonexistent path, unusable git metadata, a non-bidirectional worktree link, or a non-regular pointer file is refused rather than misattributed to an ancestor repository. Execution roots stay per-working-tree throughout — this phase changes the identity key, never where work happens. Sits between §Rollout Order steps 1 and 2: identity is corrected while the only consumer is the daemon's own service layer, before step 2 exposes attach through the SDK/CLI and bakes the wrong semantics into an observable surface. **Capture ordering.** T-007-2B-4's whole-checkout capture extent ships with the rule that captures of one normalized checkout run one at a time, across every session working in it, so two workspaces bound to subdirectories of one checkout never capture the same tree at once; runs themselves are never held.

- **T-007-2B-2 — Git pointer-file reader + repository-registration verification.**
  - **Files:** `packages/runtime-daemon/src/workspace/git-repository-layout.ts` (CREATE), `packages/runtime-daemon/src/workspace/__tests__/git-repository-layout.test.ts` (CREATE)
  - The module every direct filesystem read of git's on-disk layout routes through, so the screens cannot be applied in one call site and forgotten in another. `readPointerFile(path)` opens the entry non-blocking (`O_RDONLY | O_NONBLOCK`), validates the OPENED descriptor with `fstat` — refusing anything that is not a REGULAR file — and reads through that same descriptor under a fixed byte ceiling, so the regular-file and bounded-read guarantees hold for the object actually read: a pre-open `stat` alone leaves the TOCTOU window where the checked path is swapped for a FIFO or device node between check and open (a FIFO named `commondir` or `gitdir` planted in a scanned directory is the concrete shape — the open blocks indefinitely and wedges the scan), and trusting pre-open size metadata for the bound has the same race; the non-blocking flag makes even a FIFO's open return immediately so the `fstat` verdict, not the open, decides. `classifyGitDirEntry(workingTreeRoot)` returns the three-way verdict the contract requires — ABSENT (no `.git` entry), a DIRECTORY (a main checkout), or a POINTER (`gitdir:` file) — and, separately, UNUSABLE for an entry that is present but unreadable, malformed, or naming something that is not a usable git directory; an absent entry is a continue-condition for any caller that scans, an unusable one is a STOP that refuses — a rule the daemon must enforce ITSELF, because git does not: git's own upward discovery hard-stops only on the unusable pointer-file shape and silently skips an unusable `.git` DIRECTORY at an ancestor (empirically probed, git 2.50.1), which is precisely how a damaged repository gets attributed to its parent; T-007-2B-1's at-path-and-strictly-between screen is this classifier's consumer for that arm. `verifyWorkTreeRegistration(commonDir, workingTreeRoot)` requires git's link to be BIDIRECTIONAL — the working tree's `.git` file names a git directory, AND that git directory's registration under `<commonDir>/worktrees/<name>/gitdir` names this working tree's own `.git` back — and additionally requires the registration to be physically contained by the common directory it claims (the registered git directory's grandparent canonically equals that common directory), because a pointer file is attacker-writable and must never establish repository membership by itself. `listRegisteredWorkTrees(commonDir)` enumerates `<commonDir>/worktrees/*/gitdir`, resolving git ≥ 2.48 relative registrations against the registration file's own directory, and returns only entries that pass the same verification. Every path comparison in the module canonicalizes BOTH sides (symlink-resolved and absolutized) before comparing: on macOS `/tmp` is `/private/tmp`, so an uncanonicalized registration value never equals its canonicalized peer and a legitimate working tree is silently refused.

- **T-007-2B-3 — Registered-working-tree trust-envelope admission.**
  - **Files:** `packages/runtime-daemon/src/workspace/trust-envelope.ts` (EXTEND), `packages/runtime-daemon/src/workspace/__tests__/trust-envelope.test.ts` (EXTEND)
  - `TrustEnvelopeValidator` gains the registered-working-tree arm the identity change makes necessary: once the canonical root is the main checkout's root, a linked worktree of that repository is generally NOT path-contained within it, so containment alone would reject binds to working trees the repository demonstrably owns. A git-backed mount's envelope becomes its canonical root PLUS the working-tree paths `listRegisteredWorkTrees` returns for that repository, each admitted only through T-007-2B-2's bidirectional-link and physical-containment verification. Registration is read from the repository at bind time and never cached, so a working tree git no longer registers is no longer in the envelope. This arm governs USER-SUPPLIED bind paths only and never narrows the provenance admission of daemon-created execution roots: a daemon-created worktree whose registration an external `git worktree prune` has removed stays admitted by provenance and is retired by the Plan-008 sweep, so the two admission rules cannot disagree in that window. Containment WITHIN an admitted registered working tree is then checked by exactly the shipped rule — resolve first, then compare component-boundary-aware and case-folded — so `..` traversal, symlink escape, prefix collision, and absolute-path escape are refused inside a registered worktree exactly as they are inside the canonical root. Containment is additionally WORKING-TREE-BOUNDARY-AWARE per the defining rule: before admitting a candidate by containment in an admitted root, the validator derives the candidate's own enclosing working-tree top level, and a candidate whose enclosing working tree is NOT the root it is being tested against — a linked worktree NESTED beneath the canonical root is the concrete shape — is never admitted by lexical containment; it admits only as (or within) a registered working tree through the registration arm, so de-registering a nested worktree ejects it from the envelope exactly as it does a sibling one, and lexical containment cannot resurrect it. The WIRE form is fixed by [Spec-007 §Local Trust Envelope (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#local-trust-envelope-v1-definition) containment bullet and changes no schema: a RELATIVE `WorkspaceBind.directory` resolves against the canonical root exactly as shipped, and an ABSOLUTE `directory` is how a bind names a registered working tree (or any admitted root) — mandatory where no relative spelling exists, as for a worktree on another Windows drive — with admission for both forms decided by post-resolution containment within the union of admitted roots. The admission check is exposed for reuse at the RUN boundary (T-007-2B-4 wires it into run handoff), so bind-time and run-time membership verify through one code path rather than two drifting ones. Bind-time derivation additionally MATCHES the attach-persisted identity: attach records the canonicalized common directory as `repo_mounts.metadata.commonDir` (inside the existing metadata JSON column — no DDL; T-007-2B-4's attach leg writes it), and the common directory this task re-derives from the mount's canonical root at bind time must equal it; a mismatch — the root's `.git` entry moved or retargeted since attach — refuses with `reason: "root_mismatch"`, the mount projecting `identity_mismatch` per [Spec-007 §Repo Mount Health (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-mount-health-v1-definition) on every subsequent health-reporting read (T-007-2B-5's derivation), rather than silently following the new target, with re-attach as the named recovery, and an ABSENT key (a row that predates the key) is REPAIRED at this first contact rather than degraded past: the validator surfaces the successfully re-derived common directory and the bind transaction persists it as `repo_mounts.metadata.commonDir` (the spec's anchor-repair rule — first observation defines identity, the pre-repair retarget the named residual), so the match applies from the very next derivation, while a re-derivation that fails with no anchor present refuses through the typed resolution error exactly as a fresh attach would. The run-boundary reuse inherits the same match, so a post-attach retarget cannot walk binds or runs onto a different repository.
  - **Tests:** multi-worktree fixture — a bind naming a registered linked worktree by ABSOLUTE `directory` is admitted and returns the symlink-resolved root; a nested subdirectory of that worktree is admitted; `directory: "../sibling"` from inside the worktree is refused; an absolute `directory` resolving outside every admitted root is refused; a symlink inside the worktree pointing outside every admitted root is refused; a sibling directory that is NOT a registered working tree of the mount's repository is refused; a working tree registered by a DIFFERENT repository is refused (admission is per-repository, not per-machine); a linked worktree nested BENEATH the canonical root whose registration has been deleted is refused even though it is lexically contained in the canonical root, while its registered twin admits through the registration arm (the working-tree-boundary fixture); the read-at-bind-time-never-cached rule is pinned DISCRIMINATINGLY — between two binds of the same worktree path, only the ADMINISTRATIVE registration (`<commonDir>/worktrees/<name>`) is deleted while the working-tree directory itself stays present and readable, so the second bind can fail only because membership is re-read and no longer verifies (a `git worktree remove` fixture would delete the directory too, letting a registration-caching implementation pass by failing on path resolution instead); and — the provenance-scoping arm — a daemon-created execution root whose registration has been pruned out from under it stays admitted, proving the registration screens never narrow provenance admission.
