## Goal

Implement durable RepoMount attachment and explicit workspace binding for session execution.

## Scope

This plan covers repo root resolution, RepoMount persistence, workspace creation, execution-mode capability exposure, and workspace health projection.

## Non-Goals

- Worktree lifecycle
- PR preparation
- Rich diff UI

- [x] Paired spec is approved
- [x] Required ADRs are accepted
- [x] Blocking open questions are resolved or explicitly deferred

## Invariants

- **I-007-1 — Canonical-root fidelity.** Every persisted RepoMount records the symlink-resolved absolute canonical repository root — the MAIN checkout's working-tree root, identified by the repository's git common directory (I-007-15) — and a user-entered path is never stored as the canonical root without resolution. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) + [Spec-007 §Pitfalls To Avoid](../specs/007-repo-attachment-and-workspace-binding.md#pitfalls-to-avoid) (pitfall); path-canonicalization bugs leak outside the trust envelope (§Risks And Blockers) and corrupt every downstream workspace/worktree root derivation (Plan-008/Plan-009). **Verification.** T1.5 unit tests (subdirectory input resolves to repo root; symlinked input resolves to realpath); T-007-2B-1 unit tests (a linked worktree's input resolves to the main-checkout root, not to the worktree's own top level); T2.3/T2.6 attach integration tests assert the persisted `canonical_root` carries the resolver output, not the request input.
- **I-007-2 — Explicit resolution failure.** Canonical-root resolution failure aborts attach with typed `repo.root_resolution_failed`; the daemon never guesses a root or silently substitutes the user-entered path. **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior); silent substitution converts a user typo into a durable wrong-root mount that every later run executes against. **Verification.** T1.5 failure-path tests; T1.4 typed-error test; T2.3 attach integration test (failed resolution persists no `repo_mounts` row).
- **I-007-3 — Trust-envelope containment.** A workspace execution root always resolves — post-symlink, platform-normalized — within the canonical root of a repo mount attached to the same session, OR within one of that repository's own git-registered working trees admitted under the same bidirectional-link and physical-containment screens, OR within a daemon-provisioned execution root admitted by provenance (an arm the registration screens never narrow); containment is working-tree-boundary-aware — a candidate whose own enclosing working tree is not the admitted root it is tested against (a linked worktree nested beneath the canonical root) admits only through the registration arm, never by lexical containment; traversal or symlink escape is rejected with typed `repo.outside_trust_envelope`, and membership of a user-supplied root is re-verified at the run boundary — not only at bind — with loss of membership blocking the run and transitioning the workspace to `stale`. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) with the §Local Trust Envelope (V1 Definition) at [Spec-007 §Local Trust Envelope (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#local-trust-envelope-v1-definition); this is the security boundary between the session and the rest of the operator's filesystem, and once identity keys on the common directory (I-007-15) a linked worktree is no longer path-contained in its own repository's canonical root, so containment alone would reject binds to working trees the repository demonstrably owns. **Verification.** T1.6 adversarial unit tests (`..` traversal, symlink escape, path-prefix collision, absolute-path escape); T-007-2B-3 admission tests (a registered working tree admitted; an unregistered sibling directory, a one-way pointer, and a registration whose git directory is not physically contained by the claimed common directory each rejected; a de-registered worktree NESTED beneath the canonical root rejected despite lexical containment while its registered twin admits); T-007-2B-4 run-boundary tests (a worktree unregistered after bind refuses at the next `assertWritable` and lands `stale`; a daemon-provisioned root under the same loss stays writable); T2.4 bind integration test.
- **I-007-4 — Honest non-git classification.** A non-git path is classified `vcsType: "none"` at resolution time and is never presented as a git mount; conversely `"none"` requires git's positive not-a-repository verdict UNCONTRADICTED by a visible `.git` entry at the supplied path — damaged or unreadable repository metadata refuses `"vcs_error"`, never a plain-directory mount. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) + [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior) + AC3; misclassification makes the capability projection lie about git-backed modes ([Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior)). **Verification.** T1.5 classification tests; T2.5 capability-read tests inherit.
- **I-007-5 — Repo-mount rows persist resolved identity plus provenance.** Every `repo_mounts` row stores the user-entered attach path (`local_path`, provenance), the resolver-produced canonical root (`canonical_root`), the owning `node_id`, and a lifecycle state from the closed set; trust-envelope enforcement and node-ownership routing key off `canonical_root`, never `local_path`. **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) ("not only the user-entered path" — both values are meaningful), [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications) (canonical root + owner node + lifecycle state), [Spec-007 §Implementation Notes](../specs/007-repo-attachment-and-workspace-binding.md#implementation-notes) (node ownership). **Verification.** T2.1 migration test (NOT NULL `node_id`/`canonical_root`, state CHECK); T2.3 service test (attach with a subdirectory input stores the resolved root in `canonical_root` alongside the entered subpath in `local_path`).
- **I-007-6 — Workspace identity is stable across execution-mode switches.** No code path creates a new `workspaces` row for a mode switch; re-provisioning updates `execution_mode`/`fs_root` in place on the same `id`. **Why load-bearing.** [Spec-007 §Execution Mode Transitions](../specs/007-repo-attachment-and-workspace-binding.md#execution-mode-transitions) ("This is NOT a new workspace"); downstream run/diff attribution keys off the stable workspace id. **Verification.** T2.4 test — full beginReprovision/completeReprovision cycle retains `id` and row count.
- **I-007-7 — An unavailable execution root is observable as `stale` on every daemon read surface, and the write gate refuses stale workspaces.** **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior): stale transition + "new write runs must be blocked until repair." **Verification.** T2.5 test (probe-fail → health projection reports stale and reports the transition owed); T2.4 test (`markStale` persists the transition the projection derives; `assertWritable` throws `workspace.stale`).
- **I-007-8 — Capability projection never silently substitutes a mode.** Every mode absent from `availableModes` appears in `restrictions` with a reason string. **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior) explicit-gap mandate. **Verification.** T2.5 test — `vcs_type 'none'` mount yields `availableModes ['read-only']` + 3 populated restriction entries.
- **I-007-9 — Every repo-mount/workspace state transition appends its matching Spec-005 `session_lifecycle` event exactly once.** **Why load-bearing.** The durable timeline is the product's audit surface; emission at the transition site (single seam, T2.2) prevents drift between rows and events. **Verification.** T2.2/T2.3/T2.4 tests assert the emitted event type sequence per transition (attach → `repo.attached` + `workspace.ready`; stale → `workspace.stale`; detach → `repo.detached` + one `workspace.archived` per dependent — mount event first: every cascade row write rides the `repo.detached` append's transaction, and an archive event may only follow the commit that made it true ([Spec-007 §Detach Semantics (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#detach-semantics-v1-definition))).
- **I-007-10 — Every `repo.*` method validates daemon-side before dispatch.** Each registered method carries its canonical contracts Zod request AND response schema, so the substrate validates inbound params before the handler runs and outbound results before they hit the wire; client-only workspace binding is structurally impossible. **Why load-bearing.** [Spec-007 §Pitfalls To Avoid](../specs/007-repo-attachment-and-workspace-binding.md#pitfalls-to-avoid) names "Allowing client-only workspace binding with no daemon validation" as the failure mode; the substrate validates only what is registered with it — a handler registered with permissive schemas silently reopens the pitfall. **Verification.** T3.4 assertions (3) and (5): schema-invalid params are rejected with the deps spy at zero calls; registration asserted against the canonical contracts schema objects.
- **I-007-11 — The SDK marshals; it never derives daemon-owned repo/workspace state.** `repoClient` caches nothing and computes no health, git metadata, canonical root, or capability values client-side; daemon-owned projections ride through verbatim. **Why load-bearing.** [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications) places repo health and git metadata in daemon-owned projection state "rather than client cache"; a deriving or caching SDK forks the source of truth and breaks the stale-workspace blocking contract downstream. Mirrors the `runtimeNodeClient` read-side never-mask stance. **Verification.** T3.5 pass-through assertions: every response field equals the daemon-supplied payload; no transformation, no memoization between calls.
- **I-007-12 — Renderer mutations are explicit actions.** The `repo-attach/` renderer views MUST NOT invoke `repo.attach` or `repo.workspaceBind` as a mount/render side effect; both fire only from an explicit user click. The only mount-triggered wire calls in the subtree are reads (`repo.workspaceList`, `repo.executionModeCapabilitiesRead`). **Why load-bearing.** [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) (attach is an explicit action) + [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) (binding is explicit) + [Spec-007 §Pitfalls To Avoid](../specs/007-repo-attachment-and-workspace-binding.md#pitfalls-to-avoid) (no auto-writing before a mode is explicitly chosen): an auto-fired attach/bind couples a trust-bearing action to navigation — the exact wrong-UX shape the shipped AttachFlow idle-state precedent rejects. **Verification.** T4.4 component tests: the mock-bridge `daemon.call` spy is NOT invoked on render of `RepoAttachView` / `WorkspaceBindView` mutation paths, and is invoked exactly once per mutation after the explicit click.
- **I-007-13 — Stale workspaces are rendered, labeled, never hidden.** The workspace list renders every workspace the read returns; a `stale` workspace stays in the rendered set with its `stale` state and a write-runs-blocked-until-repair label. No `.filter(...)` drops a row by `state`, and the view computes no client-side health scalar (health is daemon-owned projection state). **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior) (stale transition + write-block until repair) + [Spec-007 §Interfaces And Contracts](../specs/007-repo-attachment-and-workspace-binding.md#interfaces-and-contracts) (WorkspaceList exposes health) + [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications) (daemon-owned projection, not client cache) + §Risks And Blockers (stale handling "needs clear UX and blocking behavior"). The render-side never-mask posture mirrors I-002-1 admit-not-eject on the shipped NodeRoster. **Verification.** T4.4 workspace-list test: fixture containing a `stale` workspace asserts the row renders with `data-workspace-state="stale"` and the write-blocked label, alongside `ready` peers.
- **I-007-14 — Execution-mode capabilities render verbatim; the renderer never substitutes a mode.** The bind/capabilities surface offers exactly the daemon-returned `availableModes` (with `restrictions` reasons rendered verbatim) and MUST NOT offer, default to, or substitute any execution mode the daemon did not return. **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior) (expose the capability gap explicitly "rather than silently substituting a different mode") + [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) (canonical four-mode taxonomy, ADR-006) + [Spec-007 §Pitfalls To Avoid](../specs/007-repo-attachment-and-workspace-binding.md#pitfalls-to-avoid) (no client-only binding decisions): the daemon is the capability authority; a renderer-synthesized mode option is precisely the silent substitution the spec forbids. **Verification.** T4.4 bind-view test: fixture `availableModes: ["read-only", "branch"]` with a `worktree` restriction reason asserts exactly two mode options render, the restriction reason text renders verbatim, and no `worktree` / `ephemeral clone` option exists in the DOM.
- **I-007-15 — Repo identity keys on the git common directory; execution roots stay per-working-tree.** Resolution identifies a repository by its git COMMON directory and returns the MAIN checkout's working-tree root as the canonical root, so — in every layout where git records the main working tree (the ordinary and submodule layouts; the `--separate-git-dir` layout's linked worktrees take the deliberate refusal arm instead, per the narrowed acceptance criterion 4) — every working tree of one repository resolves to one identical `repo_mounts.canonical_root`, while `workspaces.fs_root` continues to name the per-working-tree path actually bound or provisioned. **Why load-bearing.** [Spec-007 §Repo Identity And Common-Directory Keying (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-identity-and-common-directory-keying-v1-definition); identity is the key for the active-mount uniqueness index and for every daemon cache, filesystem watch, remote fetch, and throttle window scoped to a repository — keying those on the enclosing working tree instead silently multiplies them per worktree, and the plausible over-correction (returning the common directory itself as the workspace path) would root every worktree's execution at the main checkout, which is a different and worse bug. **Verification.** T-007-2B-1 unit tests over real multi-worktree git fixtures: attach from the main checkout and from each of two linked worktrees yields one identical canonical root, and each resolution simultaneously reports that working tree's own distinct root; T-007-2B-4 acceptance test asserts the second worktree attach is refused `repo.already_attached` against the first mount while a bind rooted at that worktree still succeeds with its own `fs_root` — and that the refusal also fires through the service-level identity comparison when two attach paths resolve to DIFFERENT canonical roots sharing one common directory (the direct-to-common holder pair the canonical-root index cannot see).
- **I-007-16 — Resolution refuses rather than misattributes.** A supplied path that does not exist, git metadata that is present but unusable, a linked-worktree link that is not bidirectional or whose registration is not physically contained by the common directory it claims, and a git pointer file that is not a regular file are each refused with a typed `RepoRootResolutionError`; none of them continues the ancestor scan, and none is reclassified as the plain-directory fallback. **Why load-bearing.** [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior) + [Spec-007 §Repo Identity And Common-Directory Keying (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-identity-and-common-directory-keying-v1-definition); walking up lexically from a path that does not exist attributes it to whatever repository contains its parent (a dotfiles repository at the operator's home directory makes that wrong for nearly every path beneath it), continuing past unusable metadata attributes a damaged repository to its parent, a one-way pointer file is attacker-writable and would let a planted `.git` claim any repository, and an unscreened non-regular pointer (a FIFO named `commondir`) wedges the scan indefinitely. **Verification.** T-007-2B-2 unit tests, one refusal arm per clause plus a negative control per arm proving the honest shape still resolves; the FIFO arm is POSIX-gated with a seam-driven twin that runs on every platform.
- **I-007-17 — Identity mismatch is observable, not just refused.** A git-backed mount whose re-derived common directory no longer equals the attach-persisted anchor (`repo_mounts.metadata.commonDir`) both refuses binds and run handoffs through the persisted-identity match AND projects `RepoMountHealth.status = "identity_mismatch"` on every subsequent health-reporting read until re-attach; `unreachable` takes precedence when the canonical root cannot be probed at all, the verdict is derived at read time and never persisted, and a mount persisting no anchor (a plain-directory mount) never projects the member. **Why load-bearing.** [Spec-007 §Repo Mount Health (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-mount-health-v1-definition) + acceptance criterion 6; without the third member the health projection keeps answering `healthy` for a mount whose every bind is refusing — a lying read model that tells the operator nothing is wrong exactly when re-attach is the required recovery. **Verification.** T-007-2B-5 tests: a retargeted mount projects `identity_mismatch` on mount read — the health surface; the wire workspace list carries no health member, its workspaces surfacing the mismatch as the `stale` + `lastError` transition at the next run handoff; an unreachable root whose anchor would also mismatch projects `unreachable` (precedence pinned discriminatingly); the honest multi-worktree shape projects `healthy`; a plain-directory mount never projects `identity_mismatch`.

T-007-2B-4 re-roots the branch arm at `workspaces.metadata.boundRoot` — the admitted bind origin, recorded at workspace creation and never cleared by `beginReprovision` (which releases `fs_root` on the way into `provisioning`, exactly why the origin needs its own durable carrier) — falling back to `canonical_root` when the key is absent so rows that predate the key keep byte-identical behavior, inside `packages/runtime-daemon/src/workspace/execution-root-service.ts`, a Plan-008-extended file per the ownership row; the EXTEND is consented by Plan-008's reciprocal CP-008-14, and [Spec-008 §Turn-Boundary Snapshots](../specs/008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)' branch-mode sentence is corrected in the same swap (Spec-008/Plan-008 flip-and-restored `approved`). The leg ships INSIDE Phase 2B — atomic with the identity change, because landing either half alone re-opens the relocation — so the Preconditions carrier box holds it exactly as it holds the rest of Phase 2B. **Direction:** Consume consent from [Plan-008](./008-worktree-lifecycle-and-execution-modes.md) (reciprocal CP-008-14). **Tasks:** T-007-2B-4.
- **CP-007-10 — Turn-snapshot capture/restore normalized to the enclosing working-tree top level (Plan-008-consented EXTEND).** A nested `boundRoot` makes turn-snapshot capture asymmetric with restore: capture's `git -C <executionRoot> ls-files` legs are cwd-scoped and list only the nested prefix ([git-ls-files(1)](https://git-scm.com/docs/git-ls-files) — the no-pathspec listing covers the current working directory), while restore's `read-tree --reset -u` updates the WHOLE working tree regardless of cwd ([git-read-tree(1)](https://git-scm.com/docs/git-read-tree) — the read tree replaces the index wholesale and `-u` updates the working tree from it), so a rollback from a snapshot captured at a nested root can erase pre-snapshot state outside that prefix. T-007-2B-4 normalizes BOTH capture and restore execution-root inputs to the enclosing working-tree top level at the `packages/runtime-daemon/src/git/turn-snapshot-service.ts` service entry — one normalization site, both directions, so capture and restore always operate on the same tree extent, the top level derived while the tree exists and carried durably as `workspaces.metadata.checkoutRoot` so restore consumes the recorded value rather than re-deriving from a nested path the turn may have deleted — a Plan-008-owned file per the ownership row; the EXTEND is consented by Plan-008's reciprocal CP-008-15, and [Spec-008 §Turn-Boundary Snapshots](../specs/008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)' applicability rule records the normalization in the same swap. **How the recorded value reaches the callee.** The normalized root is **supplied**, not looked up: Plan-008 CP-008-12 keeps capture and restore pure callees, so the EXTEND does not add a `workspaces` read inside the snapshot service — it adds a caller-resolved `checkoutRoot` parameter, which the Plan-008 T3.2 run-setup gate captures per run into `run_execution_contexts.checkout_root` (from this plan's persisted `workspaces.metadata.checkoutRoot`; an absent key is derived from the just-materialized `execution_root`'s top level with the carrier healed — never `canonical_root`, the bind-time checkout) and the caller reads from that same row. This plan owns the bind-time write and the provisioning-completion rewrite of the metadata key — consenting to exactly one delegated writer: the Plan-008 T3.2 absent-key heal, which persists the top level derived from the just-materialized execution root back into the carrier under this plan's provisioning-completion rewrite rule rather than minting a second write path (the reciprocal CP-008-15 registers the delegation on the Plan-008 side); Plan-008 owns the column, its migration, and the parameter. Capture, running while the tree exists, re-verifies the supplied value against the live tree and fails typed on disagreement; restore consumes it untouched, which is what lets a rollback survive the turn deleting the nested bound directory outright. Ships INSIDE Phase 2B with the CP-007-9 branch-arm leg, because the nested-`boundRoot` shape becomes reachable exactly when branch mode re-roots at `boundRoot`. **Direction:** Consume consent from [Plan-008](./008-worktree-lifecycle-and-execution-modes.md) (reciprocal CP-008-15). **Tasks:** T-007-2B-4.

## Design Decisions

Each decision below is binding contract surface for the Tasks blocks.

- **D-007-1 — `repo.*` method-name strings.** Six wire strings registered in `api-payload-contracts.md` §Repo Method-Name Registry: `repo.attach` (mutation), `repo.mountRead` (query), `repo.workspaceBind` (mutation), `repo.executionModeCapabilitiesRead` (query), `repo.workspaceList` (query), `repo.detach` (mutation). Tail style is dotted-camelCase per the `METHOD_NAME_FORMAT`; `repo.executionModeCapabilitiesRead` keeps interface-name symmetry with `WorkspaceExecutionModeCapabilitiesRead*` (the shorter `repo.workspaceCapabilities` variant was rejected — it minted a third name diverging from both interface and schema names). Method strings (imperative) are disjoint-by-form from the Spec-005 durable event names (past participle: `repo.attached`).
- **D-007-2 — `RepoMountHealth` is a derived projection object, never persisted.** Shape: `{ status: "healthy" | "unreachable" | "identity_mismatch"; checkedAt: string }` (ISO-8601; the third member added by the identity work — derived at read time from the attach-persisted identity anchor, with `unreachable` taking precedence and re-attach the named recovery). Merges the audit's competing proposals: a render-ready discriminant (`status`) plus probe provenance (`checkedAt`). No `unknown` member — the on-read probe floor (D-007-5) means every read carries a fresh verdict. `unreachable` (not `stale`) avoids overloading the workspace-state vocabulary across axes. No `health` column lands in `repo_mounts` — [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications) pins health to projection state, not row state; the identity verdict is likewise derived per read, never stored. Semantics in [Spec-007 §Repo Mount Health (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#repo-mount-health-v1-definition).
- **D-007-3 — `repo.*` error vocabulary.** error-contracts.md gains §Repo: `repo.not_found` (404), `repo.root_resolution_failed` (422), `repo.outside_trust_envelope` (403), `repo.already_attached` (409), `repo.detach_conflict` (409); §Workspace gains `workspace.stale` (409, the write-gate code). Adjudication: `repo.root_resolution_failed` over the competing `repo.canonical_root_unresolvable` (two-of-three subagent convergence + status 422); `repo.outside_trust_envelope` over `repo.path_outside_trust_envelope` (two-of-three convergence); `repo.not_found` over `repo.mount_not_found` (matches the `session.not_found` / `workspace.not_found` registry precedent).
- **D-007-4 — Mount-first single funnel; `VcsType = "git" | "none"`.** Non-git directories ride the SAME funnel as git repositories: `repo.attach` accepts any local path; a non-git path yields a RepoMount with `vcsType: "none"` and reduced capabilities. `WorkspaceBindRequest` always binds by `repoMountId` — [Spec-007 §Interfaces And Contracts](../specs/007-repo-attachment-and-workspace-binding.md#interfaces-and-contracts)'s "or directory root" arm is satisfied by the plain-directory mount, not by a mount-less bind path (there is no mount-less workspace; `workspaces.repo_mount_id` is NOT NULL).
- **D-007-5 — V1 capability matrix is static by `vcs_type`; health detection is two-layer.** Matrix: `'git'` → `availableModes` = all four modes, `defaultMode 'worktree'` (ADR-006 — the default WRITABLE coding mode; the fresh-workspace initial posture is always `read-only` per [Spec-007 §Default Behavior](../specs/007-repo-attachment-and-workspace-binding.md#default-behavior) and is not what `defaultMode` reports); `'none'` → `['read-only']`, `defaultMode 'read-only'`, `restrictions` populated with a reason per excluded mode. Dynamic per-repo worktree-unavailability (ADR-006 accepted trade-off) is NOT probed at capability-read time in V1: it surfaces at provisioning time through the [Spec-007 §Execution Mode Transitions](../specs/007-repo-attachment-and-workspace-binding.md#execution-mode-transitions) failure path (Plan-008's surface); a later static probe extends `restrictions` additively without contract change. Health detection: (1) on-read probe floor — every health-reporting read surface and every write gate synchronously probes filesystem availability before answering, persisting the `stale` workspace transition at probe time (zero scheduler dependency); (2) background refresh ([Spec-007 §Default Behavior](../specs/007-repo-attachment-and-workspace-binding.md#default-behavior)) via a daemon idle-scheduler tick re-probing attached mounts, default interval 60s (configurable), mirroring the Plan-005 compactor's idle-scheduler precedent — the scheduler wiring may land with Phase 3 if the seam is not exposed at Phase-2 time; the on-read floor keeps [Spec-007 §Fallback Behavior](../specs/007-repo-attachment-and-workspace-binding.md#fallback-behavior) satisfied either way.
- **D-007-6 — Detach semantics (V1).** Defined in [Spec-007 §Detach Semantics (V1 Definition)](../specs/007-repo-attachment-and-workspace-binding.md#detach-semantics-v1-definition): refuse with `repo.detach_conflict` while any dependent workspace is `busy` (no force-detach in V1); otherwise transition the mount to `detached` and archive all dependent workspaces, emitting `repo.detached` + one `workspace.archived` each; `detached` is terminal for the row — re-attach creates a new mount row; V1 detach is SDK/CLI-surfaced only (no renderer detach view). Contract shapes: `RepoDetachRequest { repoMountId }` / `RepoDetachResponse { repoMountId, state, archivedWorkspaceIds }` in api-payload-contracts.md §Plan-007.
- **D-007-7 — `repo_mounts` persistence model: provenance + canonical columns; active-root uniqueness; required default workspace.** `local_path` keeps the user-entered attach path (provenance; [Spec-007 §Required Behavior](../specs/007-repo-attachment-and-workspace-binding.md#required-behavior) "not only the user-entered path" implies both are known); a NEW `canonical_root` column carries the resolver output and is the key for trust-envelope checks and dedupe. Partial unique index `idx_repo_mounts_active_root ON repo_mounts(session_id, node_id, canonical_root) WHERE state = 'attached'` — uniqueness binds the CANONICAL root per owning node (two entered aliases resolving to one root on one node are one mount; the same absolute path on two different nodes is two distinct node-local filesystems — [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications) — and both attach), detached rows stay re-attachable as new rows. Additional columns: `node_id` (owner; [Spec-007 §State And Data Implications](../specs/007-repo-attachment-and-workspace-binding.md#state-and-data-implications)), `updated_at` (lifecycle-mutation timestamp, symmetric with `workspaces`). `workspaces` gains `metadata TEXT NOT NULL DEFAULT '{}'` (`lastError` key per [Spec-007 §Execution Mode Transitions](../specs/007-repo-attachment-and-workspace-binding.md#execution-mode-transitions)) and its `execution_mode` DDL default flips to `'read-only'` ([Spec-007 §Default Behavior](../specs/007-repo-attachment-and-workspace-binding.md#default-behavior) initial posture; `'worktree'` is the default writable RUN mode per ADR-006, not the row default). `RepoAttachResponse.defaultWorkspaceId` is REQUIRED — attach unconditionally creates the default read-only workspace for git and non-git mounts alike ([Spec-007 §Default Behavior](../specs/007-repo-attachment-and-workspace-binding.md#default-behavior) + [Spec-007 §Interfaces And Contracts](../specs/007-repo-attachment-and-workspace-binding.md#interfaces-and-contracts)).
