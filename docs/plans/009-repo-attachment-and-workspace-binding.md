## Goal

Implement durable RepoMount attachment and explicit workspace binding for session execution.

## Scope

This plan covers repo root resolution, RepoMount persistence, workspace creation, execution-mode capability exposure, and workspace health projection.

## Non-Goals

- PR preparation
- Rich diff UI

## Invariants

- **I-009-1 — Canonical-root fidelity.** Every persisted RepoMount records the symlink-resolved absolute canonical repository root; a user-entered path is never stored as the canonical root without resolution. **Why load-bearing.** `Spec-009 §Required Behavior` + line 121 (pitfall); path-canonicalization bugs leak outside the trust envelope (§Risks And Blockers) and corrupt every downstream workspace/worktree root derivation (Plan-010/Plan-011). **Verification.** T1.5 unit tests (subdirectory input resolves to repo root; symlinked input resolves to realpath); T2.3/T2.6 attach integration tests assert the persisted `canonical_root` carries the resolver output, not the request input.
- **I-009-2 — Explicit resolution failure.** Canonical-root resolution failure aborts attach with typed `repo.root_resolution_failed`; the daemon never guesses a root or silently substitutes the user-entered path. **Why load-bearing.** `Spec-009 §Fallback Behavior`; silent substitution converts a user typo into a durable wrong-root mount that every later run executes against. **Verification.** T1.5 failure-path tests; T1.4 typed-error test; T2.3 attach integration test (failed resolution persists no `repo_mounts` row).
- **I-009-3 — Trust-envelope containment.** A workspace execution root always resolves — post-symlink, platform-normalized — within the canonical root of a repo mount attached to the same session; traversal or symlink escape is rejected with typed `repo.outside_trust_envelope`. **Why load-bearing.** `Spec-009 §Required Behavior` with the §Local Trust Envelope (V1 Definition) at `Spec-009 §Local Trust Envelope (V1 Definition)`; this is the security boundary between the session and the rest of the operator's filesystem. **Verification.** T1.6 adversarial unit tests (`..` traversal, symlink escape, path-prefix collision, absolute-path escape); T2.4 bind integration test.
- **I-009-4 — Honest non-git classification.** A non-git path is classified `vcsType: "none"` at resolution time and is never presented as a git mount. **Why load-bearing.** `Spec-009 §Required Behavior` + line 56 + AC line 129; misclassification makes the capability projection lie about git-backed modes (`Spec-009 §Fallback Behavior`). **Verification.** T1.5 classification tests; T2.5 capability-read tests inherit.
- **I-009-5 — Repo-mount rows persist resolved identity plus provenance.** Every `repo_mounts` row stores the user-entered attach path (`local_path`, provenance), the resolver-produced canonical root (`canonical_root`), the owning `node_id`, and a lifecycle state from the closed set; trust-envelope enforcement and node-ownership routing key off `canonical_root`, never `local_path`. **Why load-bearing.** `Spec-009 §Required Behavior` ("not only the user-entered path" — both values are meaningful), line 73 (canonical root + owner node + lifecycle state), line 117 (node ownership). **Verification.** T2.1 migration test (NOT NULL `node_id`/`canonical_root`, state CHECK); T2.3 service test (attach with a subdirectory input stores the resolved root in `canonical_root` alongside the entered subpath in `local_path`).
- **I-009-6 — Workspace identity is stable across execution-mode switches.** No code path creates a new `workspaces` row for a mode switch; re-provisioning updates `execution_mode`/`fs_root` in place on the same `id`. **Why load-bearing.** `Spec-009 §Execution Mode Transitions` ("This is NOT a new workspace"); downstream run/diff attribution keys off the stable workspace id. **Verification.** T2.4 test — full beginReprovision/completeReprovision cycle retains `id` and row count.
- **I-009-7 — An unavailable execution root is observable as `stale` on every daemon read surface, and the write gate refuses stale workspaces.** **Why load-bearing.** `Spec-009 §Fallback Behavior`: stale transition + "new write runs must be blocked until repair." **Verification.** T2.5 test (probe-fail → health projection reports stale; transition persisted); T2.4 test (`assertWritable` throws `workspace.stale`).
- **I-009-8 — Capability projection never silently substitutes a mode.** Every mode absent from `availableModes` appears in `restrictions` with a reason string. **Why load-bearing.** `Spec-009 §Fallback Behavior` explicit-gap mandate. **Verification.** T2.5 test — `vcs_type 'none'` mount yields `availableModes ['read-only']` + 3 populated restriction entries.
- **I-009-9 — Every repo-mount/workspace state transition appends its matching Spec-006 `session_lifecycle` event exactly once.** **Why load-bearing.** The durable timeline is the product's audit surface; emission at the transition site (single seam, T2.2) prevents drift between rows and events. **Verification.** T2.2/T2.3/T2.4 tests assert the emitted event type sequence per transition (attach → `repo.attached` + `workspace.ready`; stale → `workspace.stale`; detach → `workspace.archived` per dependent + `repo.detached`).
- **I-009-10 — Every `repo.*` method validates daemon-side before dispatch.** Each registered method carries its canonical contracts Zod request AND response schema, so the substrate validates inbound params before the handler runs and outbound results before they hit the wire; client-only workspace binding is structurally impossible. **Why load-bearing.** `Spec-009 §Pitfalls To Avoid` names "Allowing client-only workspace binding with no daemon validation" as the failure mode; the substrate validates only what is registered with it — a handler registered with permissive schemas silently reopens the pitfall. **Verification.** T3.4 assertions (3) and (5): schema-invalid params are rejected with the deps spy at zero calls; registration asserted against the canonical contracts schema objects.
- **I-009-11 — The SDK marshals; it never derives daemon-owned repo/workspace state.** `repoClient` caches nothing and computes no health, git metadata, canonical root, or capability values client-side; daemon-owned projections ride through verbatim. **Why load-bearing.** `Spec-009 §State And Data Implications` places repo health and git metadata in daemon-owned projection state "rather than client cache"; a deriving or caching SDK forks the source of truth and breaks the stale-workspace blocking contract downstream. Mirrors the `runtimeNodeClient` read-side never-mask stance. **Verification.** T3.5 pass-through assertions: every response field equals the daemon-supplied payload; no transformation, no memoization between calls.
- **I-009-12 — Renderer mutations are explicit actions.** The `repo-attach/` renderer views MUST NOT invoke `repo.attach` or `repo.workspaceBind` as a mount/render side effect; both fire only from an explicit user click. The only mount-triggered wire calls in the subtree are reads (`repo.workspaceList`, `repo.executionModeCapabilitiesRead`). **Why load-bearing.** `Spec-009 §Required Behavior` (attach is an explicit action) + line 43 (binding is explicit) + line 122 (no auto-writing before a mode is explicitly chosen): an auto-fired attach/bind couples a trust-bearing action to navigation — the exact wrong-UX shape the shipped AttachFlow idle-state precedent rejects. **Verification.** T4.4 component tests: the mock-bridge `daemon.call` spy is NOT invoked on render of `RepoAttachView` / `WorkspaceBindView` mutation paths, and is invoked exactly once per mutation after the explicit click.
- **I-009-13 — Stale workspaces are rendered, labeled, never hidden.** The workspace list renders every workspace the read returns; a `stale` workspace stays in the rendered set with its `stale` state and a write-runs-blocked-until-repair label. No `.filter(...)` drops a row by `state`, and the view computes no client-side health scalar (health is daemon-owned projection state). **Why load-bearing.** `Spec-009 §Fallback Behavior` (stale transition + write-block until repair) + line 67 (WorkspaceList exposes health) + line 75 (daemon-owned projection, not client cache) + §Risks And Blockers (stale handling "needs clear UX and blocking behavior"). The render-side never-mask posture mirrors I-003-1 admit-not-eject on the shipped NodeRoster. **Verification.** T4.4 workspace-list test: fixture containing a `stale` workspace asserts the row renders with `data-workspace-state="stale"` and the write-blocked label, alongside `ready` peers.
- **I-009-14 — Execution-mode capabilities render verbatim; the renderer never substitutes a mode.** The bind/capabilities surface offers exactly the daemon-returned `availableModes` (with `restrictions` reasons rendered verbatim) and MUST NOT offer, default to, or substitute any execution mode the daemon did not return. **Why load-bearing.** `Spec-009 §Fallback Behavior` (expose the capability gap explicitly "rather than silently substituting a different mode") + line 44 (canonical four-mode taxonomy, ADR-006) + line 123 (no client-only binding decisions): the daemon is the capability authority; a renderer-synthesized mode option is precisely the silent substitution the spec forbids. **Verification.** T4.4 bind-view test: fixture `availableModes: ["read-only", "branch"]` with a `worktree` restriction reason asserts exactly two mode options render, the restriction reason text renders verbatim, and no `worktree` / `ephemeral clone` option exists in the DOM.

## Ratified Design Decisions

Decisions below were adjudicated by the Tier-6 plan-readiness audit (2026-06-10) and ratified at its swap, per the Plan-004 D-004-3 precedent. Each is binding contract surface for the Tasks blocks.

- **D-009-1 — `repo.*` method-name strings.** Six wire strings ratified in `api-payload-contracts.md` §Repo Method-Name Registry (Tier 6): `repo.attach` (mutation), `repo.mountRead` (query), `repo.workspaceBind` (mutation), `repo.executionModeCapabilitiesRead` (query), `repo.workspaceList` (query), `repo.detach` (mutation). Tail style is dotted-camelCase per the Tier-1 `METHOD_NAME_FORMAT`; `repo.executionModeCapabilitiesRead` keeps interface-name symmetry with `WorkspaceExecutionModeCapabilitiesRead*` (the shorter `repo.workspaceCapabilities` variant was rejected — it minted a third name diverging from both interface and schema names). Method strings (imperative) are disjoint-by-form from the Spec-006 durable event names (past participle: `repo.attached`).
- **D-009-2 — `RepoMountHealth` is a derived projection object, never persisted.** Shape: `{ status: "healthy" | "unreachable"; checkedAt: string }` (ISO-8601). Merges the audit's competing proposals: a render-ready discriminant (`status`) plus probe provenance (`checkedAt`). No `unknown` member — the on-read probe floor (D-009-5) means every read carries a fresh verdict. `unreachable` (not `stale`) avoids overloading the workspace-state vocabulary across axes. No `health` column lands in `repo_mounts` — `Spec-009 §State And Data Implications` pins health to projection state, not row state. Semantics in `Spec-009 §Repo Mount Health (V1 Definition)`.
- **D-009-3 — `repo.*` error vocabulary.** error-contracts.md gains §Repo: `repo.not_found` (404), `repo.root_resolution_failed` (422), `repo.outside_trust_envelope` (403), `repo.already_attached` (409), `repo.detach_conflict` (409); §Workspace gains `workspace.stale` (409, the write-gate code). Adjudication: `repo.root_resolution_failed` over the competing `repo.canonical_root_unresolvable` (two-of-three subagent convergence + status 422); `repo.outside_trust_envelope` over `repo.path_outside_trust_envelope` (two-of-three convergence); `repo.not_found` over `repo.mount_not_found` (matches the `session.not_found` / `workspace.not_found` registry precedent).
- **D-009-4 — Mount-first single funnel; `VcsType = "git" | "none"`.** Non-git directories ride the SAME funnel as git repositories: `repo.attach` accepts any local path; a non-git path yields a RepoMount with `vcsType: "none"` and reduced capabilities. `WorkspaceBindRequest` always binds by `repoMountId` — `Spec-009 §Interfaces And Contracts`'s "or directory root" arm is satisfied by the plain-directory mount, not by a mount-less bind path (there is no mount-less workspace; `workspaces.repo_mount_id` is NOT NULL).
- **D-009-5 — V1 capability matrix is static by `vcs_type`; health detection is two-layer.** Matrix: `'git'` → `availableModes` = all four modes, `defaultMode 'worktree'` (ADR-006 — the default WRITABLE coding mode; the fresh-workspace initial posture is always `read-only` per `Spec-009 §Default Behavior` and is not what `defaultMode` reports); `'none'` → `['read-only']`, `defaultMode 'read-only'`, `restrictions` populated with a reason per excluded mode. Dynamic per-repo worktree-unavailability (ADR-006 accepted trade-off) is NOT probed at capability-read time in V1: it surfaces at provisioning time through the `Spec-009 §Execution Mode Transitions` failure path (Plan-010's surface); a later static probe extends `restrictions` additively without contract change. Health detection: (1) on-read probe floor — every health-reporting read surface and every write gate synchronously probes filesystem availability before answering, persisting the `stale` workspace transition at probe time (zero scheduler dependency); (2) background refresh (`Spec-009 §Default Behavior`) via a daemon idle-scheduler tick re-probing attached mounts, default interval 60s (configurable), mirroring the Plan-006 compactor's idle-scheduler precedent — the scheduler wiring may land with Phase 3 if the seam is not exposed at Phase-2 time; the on-read floor keeps `Spec-009 §Fallback Behavior` satisfied either way.
- **D-009-6 — Detach semantics (V1).** Ratified in `Spec-009 §Detach Semantics (V1 Definition)`: refuse with `repo.detach_conflict` while any dependent workspace is `busy` (no force-detach in V1); otherwise transition the mount to `detached` and archive all dependent workspaces, emitting `repo.detached` + one `workspace.archived` each; `detached` is terminal for the row — re-attach creates a new mount row; V1 detach is SDK/CLI-surfaced only (no renderer detach view). Contract shapes: `RepoDetachRequest { repoMountId }` / `RepoDetachResponse { repoMountId, state, archivedWorkspaceIds }` in api-payload-contracts.md §Plan-009.
- **D-009-7 — `repo_mounts` persistence model: provenance + canonical columns; active-root uniqueness; required default workspace.** `local_path` keeps the user-entered attach path (provenance; `Spec-009 §Required Behavior` "not only the user-entered path" implies both are known); a NEW `canonical_root` column carries the resolver output and is the key for trust-envelope checks and dedupe. Partial unique index `idx_repo_mounts_active_root ON repo_mounts(session_id, node_id, canonical_root) WHERE state = 'attached'` — uniqueness binds the CANONICAL root per owning node (two entered aliases resolving to one root on one node are one mount; the same absolute path on two different nodes is two distinct node-local filesystems — `Spec-009 §State And Data Implications` — and both attach), detached rows stay re-attachable as new rows. Additional columns: `node_id` (owner; `Spec-009 §State And Data Implications`), `updated_at` (lifecycle-mutation timestamp, symmetric with `workspaces`). `workspaces` gains `metadata TEXT NOT NULL DEFAULT '{}'` (`lastError` key per `Spec-009 §Execution Mode Transitions`) and its `execution_mode` DDL default flips to `'read-only'` (`Spec-009 §Default Behavior` initial posture; `'worktree'` is the default writable RUN mode per ADR-006, not the row default). `RepoAttachResponse.defaultWorkspaceId` is REQUIRED — attach unconditionally creates the default read-only workspace for git and non-git mounts alike (`Spec-009 §Default Behavior` + line 81).
