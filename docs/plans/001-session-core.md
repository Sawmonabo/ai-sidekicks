## Goal

Implement the minimum session creation, snapshot, and rebuild foundation used by all later features.

## Scope

This plan covers session ids, lead-agent creation, session-owner binding, local event append, and typed session read or subscribe APIs, and the session directory and lifecycle the desktop app drives: create with the lead and the place it works, list, rename and the session's own title, archive, unarchive and close, pin and mute, converting a chat to a project, fork, search, the `@` file search, a chat's managed workspace, and an idle Claude Code session's sleep and wake.

## Non-Goals

- The machine's registration with the control plane
- Queue and intervention behavior

## Invariants

The following invariants are **load-bearing** and MUST be preserved across all Plan-001 PRs and downstream extensions.

### I-001-1 — Sequence is the canonical order key

Local Runtime Daemon SQLite rebuild MUST order `session_events` by `sequence ASC`, never by `monotonic_ns`. The `monotonic_ns` column is within-daemon debug data only (per [local-sqlite-schema §session_events](../architecture/schemas/local-sqlite-schema.md#session-events-plan-001-extended-by-plans-004-012)); it can be non-monotonic across rows after clock adjustments and MUST NOT influence rebuild or projection.

**Why load-bearing.** Rebuild determinism is the foundation for [ADR-016](../decisions/016-shared-event-sourcing-scope.md) event-sourcing semantics. Plan-004 (event taxonomy) and Plan-012 (persistence and recovery) build on this invariant.

**Verification.** Test D3 in §Test And Verification Plan asserts `Rebuild uses sequence not monotonic_ns even when monotonic_ns is non-monotonic across rows`.

### I-001-2 — Columns another plan owns carry no Plan-001 logic

The columns and tables listed in §Cross-Plan Schema Ownership (Plan-001 creates them in the one schema; other plans own what they mean) carry no read or write logic from Plan-001. Plan-001 creates their types and nullability as the schema docs define them; the owners (Plan-004 events, Plan-019 data retention, Plan-015 identity) author all read/write logic in their own plans.

**Why load-bearing.** Each of these columns has one owner, so what it means is written in one place.

**Verification.** Review of each Plan-001 change: it adds no read or write of these columns.

## Cross-Plan Obligations

Plan-001 owns the daemon-side session lifecycle and the shell spawn's entry-point wrapper. Two daemon-layer obligations (CP-001-1, CP-001-2) are declared by Plan-021 (Terminal) and surface here for bidirectional citation locality, so a Plan-001 reviewer sees the obligations without first reading Plan-021. Each entry states the obligation, the source citation, and the resolution.

### CP-001-1 — The terminal drains when the service stops

[Plan-021 §Invariants I-021-4](./021-terminal.md#i-021-4--the-apps-quit-never-stops-a-shell-shells-end-only-when-the-service-stops) declares that the desktop app's quit never stops a shell: the shells run inside the daemon through `sidekicks-terminal`, and the daemon is the person's own background service, never a child of the app, so quitting the app leaves the service, every run and every shell running. The shells end only when the service itself stops — Runtime's `Stop` or `Restart`, or the operating system's service manager stopping it — and that drain must finish before the daemon exits, or the shells' child processes orphan (primary source cited at [Plan-021 §Windows Implementation Gotchas Gotcha 4](./021-terminal.md#4-the-apps-quit-and-the-services-stop)).

**Resolution.** Plan-001 wires the drain into the daemon's own stop sequence, ahead of the daemon's exit; nothing in the app's quit reaches it. The stop calls `sidekicks-terminal`'s drain once, the same on every operating system: each live shell gets the hard stop (`SIGTERM` on macOS and Linux, the `console` mode's `CTRL_BREAK_EVENT` on Windows), the drain waits for its exit up to `DAEMON_STOP_TERMINAL_DRAIN_MS`, and escalates to `SIGKILL` (`taskkill /T /F /PID <pid>` on Windows) on timeout. `DAEMON_STOP_TERMINAL_DRAIN_MS` lives in `crates/sidekicks-contracts/src/daemon/lifecycle.rs`, beside the whole drain's own bound, `DAEMON_STOP_DRAIN_BOUND_MS` (4 seconds), so a write still running at it has time to finish rather than roll back: a client that ends the service (main's supervisor or the CLI) waits that long after the stop for the process to exit before it sends any signal, so no signal cuts the drain short.

**Why surfaced in Plan-001.** This obligation lives at the daemon's session-lifecycle layer (Plan-001 owns the session-lifecycle daemon code), not in `sidekicks-terminal` (Plan-021 supplies only each shell's close and stop). Without the bidirectional citation, a Plan-001 reviewer would have no signal that the drain at the service's stop is a Plan-001 obligation.

### CP-001-2 — A shell's spawn performs daemon-layer cwd-translation for worktree paths

[Plan-021 §Invariants I-021-5](./021-terminal.md#i-021-5--a-shell-starts-so-its-worktree-stays-removable-the-daemon-performs-the-translation) declares that a shell's start MUST leave its worktree removable. Windows keeps a handle on every process's current folder: the ConPTY host starts in the daemon's own folder and keeps it, and a process keeps the folder it starts in until it moves its own. The daemon's `shell` mode, which the PTY spawns and which waits for the shell's life, never moves its folder, and neither does a shell that ignores its own `cd` for its process folder; spawned in the worktree, either would lock it for the shell's life (`ERROR_SHARING_VIOLATION`), and `git worktree remove` would fail until the shell exited (the `microsoft/node-pty#647` class — primary source cited at [Plan-021 §Windows Implementation Gotchas Gotcha 5](./021-terminal.md#5-spawn-locks-cwd-on-windows)).

**Resolution.** Plan-001 [Phase 5 — Client SDK And Daemon Wiring](#phase-5--client-sdk-and-daemon-wiring) ships a daemon-layer spawn translator (`crates/sidekicks-session/src/spawn_cwd_translator.rs`) that every start on a worktree goes through. For a shell it asks `sidekicks-platforms` (`ShellFolderStart`, `shell_folder_start`) how that program is started so that it opens in its folder: the folder the PTY spawns the daemon's `shell` mode in, the folder the mode starts the shell in, the arguments, any text the mode writes after them exactly as given, and the added environment; the PTY hands the mode the program, arguments, folder and that text in its start confirmation, so the mode's own command line carries none of the person's input. The mode, not the shell, is what the PTY spawns in the stable folder: on macOS and Linux the stable folder the daemon names, the mode entering the worktree (`chdir`) before it execs the shell; on Windows the system folder, which the mode keeps for its whole wait while it starts the shell in its folder. On Windows PowerShell 7 takes `-WorkingDirectory` (unless the user's arguments run a script by a relative path), Windows PowerShell 5.1 a trailing `-NoLogo -NoExit -Command` carrying `Microsoft.PowerShell.Management\Set-Location -LiteralPath`, or that statement put before a `Microsoft.PowerShell.Utility\Invoke-Expression` of the user's own command text, given by `-Command` or as a bare word (only where every user argument before it is one of 5.1's own start switches), `wsl.exe` `--cd` (unless the user's arguments carry `--cd` or `~`) and `cmd.exe` on a share `/K pushd`, each starting in the system folder, and every other shell starts in the worktree and lets go of it once it leaves. For an agent program that reads `CWD` it sets that entry, and the mode and the program start in the stable folder. The per-shell form lives in the platforms crate behind that one interface; the daemon applies it.

**Why surfaced in Plan-001.** ADR-006 (Worktree-First Execution Mode) bakes worktree paths into the daemon's session-spawn entry point. The translation MUST happen between the daemon's logical worktree-path API and the shell's spawn — i.e., in Plan-001's session-lifecycle code, not in `sidekicks-terminal` (which deliberately does not know about worktree semantics, per Plan-021 I-021-3 / I-021-5). Plan-021 carries an explicit `**Precondition:**` line on this wrapper because its Windows end-to-end test would surface `ERROR_SHARING_VIOLATION` on Windows CI without it.

## Data And Storage Changes

Plan-001 creates the first tables of the daemon's one SQLite schema and the control plane's one schema, among them the columns and tables later plans give meaning to. Both are SQLite and they are two separate databases, the daemon's on each machine and the control plane's inside the relay, per [ADR-004](../decisions/004-sqlite-local-state-and-hosted-account.md) and [deployment-topology §Account Storage](../architecture/deployment-topology.md#account-storage). The column-level definitions are canonical in the schema docs below; this plan body lists the elements other plans own.

- Add the minimal `users` identity-anchor table (`id`, `created_at`) to Control Plane storage **before** any FK-bearing shared table. The anchor comes first because `machines.user_id`, `devices.user_id` and the other user-bearing tables `REFERENCES users(id)`, and Plan-001 executes before Plan-015. Plan-001 owns the physical CREATE of the minimal shape only; the identity columns (`display_name`, `identity_ref`, `metadata`) are added to the control plane's one schema by Plan-015. See [Hosted Account Schema §Users Identity Anchor](../architecture/schemas/hosted-account-schema.md#users-identity-anchor-plan-001).
- Add local `session_events` and `session_snapshots` tables to Local Runtime Daemon SQLite.
- Add the local `session_console_state` table to Local Runtime Daemon SQLite — the session-scoped console store the composer draft, its staged attachments, the per-session step bound and a Claude Code session's own advisor live in ([Session Tables §Session Console State (Plan-001)](../architecture/schemas/local-sqlite-session-tables.md#session-console-state-plan-001)).
- The daemon's session record gains the members Phase 6 writes: `shape` (`chat` or `project`), set at create; `place`, the session's place from `session.created`, NULL on macOS and Linux; the name; whether the session is pinned and its place among the pinned; `muted_at`, rebuilt from the mute events; the pending working-folder move; and `scratchForDefinitionId` for Try it's scratch session. The record also carries the session's `group`, an indexed column naming one of its project's groups. Beside the record the daemon keeps `session_groups` (each project's groups, a name unique in its project ignoring case), `session_links` (one row per pair of sessions and kind, with its count and its first and last time, indexed from both ends), `session_tags` (indexed by tag) and each session's precomputed related list ([Session Tables §Session Directory (Plan-001)](../architecture/schemas/local-sqlite-session-tables.md#session-directory-plan-001)). The daemon also keeps its own full-text index on Tantivy over session titles, message text, tool calls, group names and tags for `session.search`, fed from SQLite, the store of record, through an outbox table written in the same transaction as the rows it indexes ([ADR-041](../decisions/041-session-search-on-tantivy.md)), and the wake-ups and session-only jobs a Claude Code session holds, kept from their tool results so the idle sleep can read them. No member carries a provider account supplied by a client.
- Create `session_events.monotonic_ns INTEGER NOT NULL` per [Spec-013 §Clock Handling](../specs/013-persistence-and-recovery.md#clock-handling) (semantics owned by Plan-004).
- See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) for canonical column definitions of `session_events` and `session_snapshots`.

## API And Transport Changes

- Add `SessionCreate`, `SessionRead`, and `SessionEventSubscribe` to the shared contracts, the daemon and the daemon client (`crates/sidekicks-client`). Another of the user's devices calls the same methods on the machine's daemon over its channel ([Plan-025](./025-remote-control.md)); the control plane serves no session method.
- `session.create` carries the session's one lead agent — a saved agent definition named (`leadDefinitionId`), or the axes spelled out in `lead` (its driver, model and effort) — with the lead's model and effort, and in a project a `binding` naming the project and where the session works, a worktree of its own or the project's checkout; Try it's scratch session adds `scratch: true`. The request carries no provider-account member. Its reply echoes the binding the daemon resolved for the lead: the driver, the model, the effort and the provider account ([Spec-001 §Interfaces And Contracts](../specs/001-session-core.md#interfaces-and-contracts)). The same resolved values ride `session.created`, which is where that agent's row in the session's `agents` projection is born, because no verb attaches an agent to a session ([Spec-005 §Event Type Enumeration](../specs/005-session-event-taxonomy-and-audit-log.md#event-type-enumeration)).
- `SessionRecord` carries two additive-optional members this plan's `session.read` answers with, both read by the session inspector and by nothing else. **`maxStepsPerTurn`** is that session's own bound on how many steps one turn may take, projected from the session record and absent where the person set none; its write is `session.maxSteps.update`, an owed verb registered in [session-payloads.md §Session Method-Name Registry](../architecture/contracts/session-payloads.md#session-method-name-registry) with the rest of the console's session mutations and built with them rather than here. **`address`** is the address another session writes to when it messages this one: the inbox the daemon holds for the session, one socket, `<16 hex>.sock` in Claude Code's default socket folder on a Mac and on Linux and the named pipe `\\.\pipe\cc-msg-<32 hex>` on Windows, stable for the session's whole life and derived from the session id, so it is present whether or not a process is running and it mints no read of its own. The override's durable home is `session_console_state` ([Session Tables §Session Console State (Plan-001)](../architecture/schemas/local-sqlite-session-tables.md#session-console-state-plan-001)), the daemon's own session-scoped store beside the draft and the staged attachments, a table of the daemon's one schema; the address is derived from the session id and adds no column anywhere.
