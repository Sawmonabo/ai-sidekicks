## Goal

Ship the Spec-020 crypto-shredding model and every data act it serves: the person's words land sealed under their session's content key, as the machine's do; the daemon master key opens unattended through the custody ladder, and every blob sealed under it names its key; the session purge deletes a session's content key before its rows, so no freed page keeps a readable word of it; the master key rotates in six crash-safe steps that a start resumes or rolls back; and the person can export everything the machine keeps, erase it, and rotate its keys, from Settings › Runtime and from the command line.

## Scope

- Create the `master_keys` SQLite table owned by this plan: one row per master key in custody, with its key id, its state (`active`, `incoming`, `outgoing` or `retired`) and its creation time ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key)).
- `session_events.pii_payload BLOB` and the `master_keys` table are in the daemon's one schema, so the schema is compatible with crypto-shredding from the start; the schema's test proves both (T22.2.1, T22.3.2).
- Daemon master-key custody: **the master key opens unattended under the person's login, and its plaintext never touches persistent storage** ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key)). The ladder, tried in order: **hardware wrap** — a Secure Enclave key on a Mac that has one, through the `sidekicks-keywrap` Swift helper, and a TPM key through NCrypt on Windows; **keychain** — one entry through `@napi-rs/keyring` 2.1.0, opened with `{linux: {store: "secret-service"}}`, or on Windows one Credential Manager credential at `CRED_PERSIST_LOCAL_MACHINE`; **passphrase file** — the [ADR-021](../decisions/021-cli-identity-key-storage-custody.md) version-byte XChaCha20-Poly1305 file under an Argon2id key (OWASP params `m=19456, t=2, p=1`), opened after each start by `daemon.unlock {passphrase}`; **refuse to start** — never a plaintext master (`keytar` is archived/unmaintained and is not used). On Windows, native and WSL alike, every Windows step runs in the service's Windows half (CP-020-8), and every Credential Manager entry the service writes, not only the master key's, goes through it at `CRED_PERSIST_LOCAL_MACHINE`. The in-memory master is held under `sodium_mlock` and wiped with `sodium_memzero`. Shipped behind `OsKeystoreSealedDaemonKeyStore`, reciprocating Plan-006 CP-006-8 (see [§Cross-Plan Obligations](#cross-plan-obligations)).
- One custody root: the machine's identity key, its channel key, the hosted account's DPoP key and refresh token, and the MCP governance key are each sealed under the master key in one format — XChaCha20-Poly1305 behind the master-key header, with `AAD = header || purpose || row id || "ais.master-wrap.v1"` — and stored in the daemon's database.
- Key ids: each master key in custody has a key id (16 random bytes, written as 32 lowercase hex characters), recorded in `master_keys` with its state (`active`, `incoming`, `outgoing` or `retired`); its custody entries are named by it (`master-key.<key id>`, `daemon-master.<key id>.enc`), and every blob sealed under the master key, each `session_content_keys` wrap included, begins with the master-key header naming the key that sealed it ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key)).
- The person's words are sealed under their session's content key: `pii_payload` on `session_events`, `interventions` and `queue_items` is AES-256-GCM under the key `SessionContentKeyStore` resolves for the session — the random 32-byte AES-256 key that also seals the session's `content_payload` — with `AAD = session_id || "ais.session-pii.v1" || row id` (the event id, the intervention id or the queue item id), a 12-byte random nonce and wire format `iv || ciphertext || tag`. Plan-005's write path seals it, as it seals the content partition; the label keeps a row's PII ciphertext from authenticating as that row's `content_payload`, whose AAD is `session_id || event_id`. No per-user key exists, and no content key is derived from any credential, identity record or other surviving secret, so deleting a session's key row, or destroying the master key that wraps it, is an irreversible cryptographic erasure (the crypto-shred precondition, [Spec-020 §PII Payload Column Pattern](../specs/020-data-retention-and-gdpr.md#pii-payload-column-pattern)).
- Master-key wraps use XChaCha20-Poly1305 behind the master-key header — one format byte and the 16-byte id of the key that sealed the blob — with a 24-byte random nonce and wire format `header || nonce || ciphertext || tag`; the AAD is the header followed by the blob's own: `session_id || "ais.session-content-wrap.v1" || key_version` for a content key, `purpose || row id || "ais.master-wrap.v1"` for a sealed private key. **Rationale.** XChaCha20-Poly1305's 192-bit random nonce eliminates the nonce-collision risk that AES-256-GCM's 96-bit nonce creates for a master-wrap key whose nonces are randomly generated across many rotations; per [RFC 8439 §4](https://datatracker.ietf.org/doc/html/rfc8439) and [draft-irtf-cfrg-xchacha-03](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-xchacha-03), the 192-bit nonce space is safe for arbitrary random nonces. Session content remains AES-256-GCM: its random 96-bit nonce is collision-safe within one session's bounded write volume (the [NIST SP 800-38D §8.3](https://csrc.nist.gov/publications/detail/sp/800-38d/final) random-nonce ceiling of ~2³² messages per key applies _per session key_, not across the whole event log). The AAD is a record-binding / tamper-evidence mechanism and has **no** effect on nonce-collision probability.
- PII splitter: a pure, content-aware function `splitPii(event) → {payload, pii_payload}` that the emitter invokes per write. The emitter decides at the call site whether a given field carries PII (by passing the field to the `piiPayload` branch of the splitter input); the splitter does not consult a per-event-type registry attribute. Non-PII events write a NULL `pii_payload`. **Rationale.** Spec-005's event taxonomy does not carry a per-event `pii:true|false` attribute and is not planned to — classifying every event type into PII buckets is brittle because a single event type can carry PII on one call-site and none on another (e.g. `run.prompt_submitted` carries PII when the prompt is user-authored, none when the prompt is a system template). Call-site classification is the only model that stays correct under this ambiguity.
- The data acts, as daemon JSON-RPC verbs over the contracts in `packages/contracts/src/daemon-data.ts`: `daemon.dataExport {destination}` with `daemon.dataExportSubscribe` (`Export all data`), `daemon.dataErase {}` (`Erase all data`), `daemon.keyRotate` (`sidekicks rotate-keys`, carrying the machine's passphrase on the passphrase-file tier and the recovery passphrase when one is set) and `daemon.unlock {passphrase}` (the passphrase-file tier). Host is daemon-bound (data-locality); shape per D-020-3.
- The purge's key step: `daemon.retentionPurge` (Plan-006 Phase R1) overwrites a session's wrapped content key with zeros and deletes its row before the session's rows in one transaction, then checkpoints the write-ahead log with `TRUNCATE` (CP-020-5).

## Non-Goals

- **The retention bounds and `Delete old data`.** `daemon.retentionRead`, `daemon.retentionUpdate` and `daemon.retentionPurge` are Plan-006 Phase R1's, with the purge's stub builder, capture folder, base pins and managed workspace; this plan owns only the key step the purge runs first (CP-020-5). Nothing deletes a session by age: the service drops only a run's step data and the diagnostic logs on its own, each past its own bound, and neither bound is a switch. Background compaction never removes anything a person could see ([Spec-020 §Retention Policy](../specs/020-data-retention-and-gdpr.md#retention-policy)).
- **The provider's own files.** `"cleanupPeriodDays": 36500` in every Claude Code process and account home, the `settings_ignored` read-back, and the provider files a purge removes are Plan-004's and Plan-001's ([ADR-039](../decisions/039-kept-sessions-keep-their-provider-files.md)).
- **Deleting the hosted account.** `account.delete`, `account.export`, the token denylist and `account_audit` are Plan-016 Phase 5's control-plane account work; this plan carries the Path-2 closure it must cover (CP-020-6).
- **Content-key regeneration.** A content key is never regenerated: the [NIST SP 800-38D](https://csrc.nist.gov/publications/detail/sp/800-38d/final) §8.3 bound is 2^32 seals a key. A master-key rotation re-wraps it, raising `key_version` by one and stamping `rotated_at`.

## Data And Storage Changes

### PII Data Map (Three Durability Tiers)

Per [Spec-020 §PII Data Map](../specs/020-data-retention-and-gdpr.md#pii-data-map), the PII the data acts reach sits in two durability tiers, and nothing is exported off the machine through telemetry. Plan-020 owns the schema and write-path for the durable-tier SQLite side (below) and the erase that destroys it; the Postgres side of the durable tier is owned plan-by-plan — Plan-016 (`users`, `identity_mappings`, `webauthn_credentials`, `webauthn_challenges`, `account_audit`) and Plan-028 (`devices`, `runtime_nodes`, `trust_statements`) — and deleted by Plan-016's `account.delete`; Plan-018 owns the bounded-retention tier, which drops past `Keep diagnostic logs for`. These tiers classify the user's **PII content** by where it lives; account deletion's **relational** obligation is a distinct, broader lens — the complete `REFERENCES users(id)` inbound-FK closure of CP-020-6, which additionally reaches the token denylist (`revoked_jtis`/`revoked_token_families`) that FK-links to the user without carrying a PII column.

### SQLite: `master_keys` (new, owned by Plan-020)

One row per master key in custody: `key_id` (16 random bytes written as 32 lowercase hex characters, the name of the key's custody entries and the id its master-key header carries), `state` (`active`, `incoming`, `outgoing` or `retired`, at most one row in each of `active`, `incoming` and `outgoing`, enforced by a partial unique index on `state`, and one `retired` row for each older key a backup still names) and `created_at`. Outside a rotation exactly one row is `active`. The DDL is in [Local SQLite Schema §GDPR and Recovery Tables](../architecture/schemas/local-sqlite-schema.md#gdpr-and-recovery-tables-spec-020-plan-013), and the rotation that moves a key through the states is [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key).

### SQLite: `session_events.pii_payload`

`pii_payload BLOB` is on the `session_events` column list in the daemon's one schema. [Spec-020 §Schema Requirements](../specs/020-data-retention-and-gdpr.md#schema-requirements) requires this separation in the V1 schema, and the schema's test proves the column is there (T22.3.2).

### Filesystem: master-key custody (KEK-wrapped, plaintext never persisted)

Per [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key), the 32-byte master key is **never persisted in plaintext**. It is generated once (`crypto.getRandomValues`) and resolved through the custody ladder at each start, with no prompt except on the passphrase-file tier. The store is `OsKeystoreSealedDaemonKeyStore` at `bootstrap/daemon-key-store.ts`, composing the rungs in `crypto/`.

- **Tier 1 — hardware wrap.** macOS: a Secure Enclave P-256 key-agreement key made with CryptoKit; its 284-byte handle sits in the data folder, and the master key is wrapped to it (ephemeral P-256, ECDH, HKDF-SHA-256, AES-256-GCM) inside the `sidekicks-keywrap` helper, whose crash is a refusal. An Intel Mac without a T2 chip starts at tier 2. Windows: a user-scoped, non-exportable key in the Microsoft Platform Crypto Provider, wrapped and unwrapped with NCrypt in the service's Windows half (CP-020-8). Linux: none until a probe on a machine with a TPM chooses between `systemd-creds` and the TPM2 software stack.
- **Tier 2 — keychain.** One entry, whose account is `master-key.<key id>`, through `@napi-rs/keyring` 2.1.0, opened with `{linux: {store: "secret-service"}}`, holding the master key hardware-wrapped where tier 1 exists. On Windows one Credential Manager generic credential at `CRED_PERSIST_LOCAL_MACHINE`, written by the Windows half through `windows-native-keyring-store` 1.1.0 with `persistence=local`, because the 2.1.0 binding's Windows path writes Enterprise. On Linux with lingering and a locked keyring the service starts locked; a run needing sealed content fails its step with `Retry from this step`, and the key is read again at each run and each retry. (`keytar` is archived/unmaintained and is not used.)
- **Tier 3 — passphrase file**: `daemon-master.<key id>.enc`, the [ADR-021](../decisions/021-cli-identity-key-storage-custody.md) version-byte XChaCha20-Poly1305 file under an **Argon2id** key (`m=19456, t=2, p=1`, [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)), supplied by `@noble/hashes` v2.x `argon2id`, at mode `0600`; on Windows it sits in the Windows data folder and the Windows half reads it. The person chooses the passphrase at first start (`sidekicks daemon install` or the Runtime service line); after each start the service is locked until `daemon.unlock {passphrase}`, and stays unlocked while it runs.
- **Tier 4 — refuse**: with no tier working, the daemon **exits non-zero** and says why in `sidekicks daemon status`. It MUST NOT fall back to a plaintext master or a master held only in memory ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key)).
- **Envelope AAD**: the passphrase file's full 50-byte header binds the version byte into the AEAD (D-020-1(b)).
- **Key ids and the master-key header**: each master key in custody has a key id, recorded in `master_keys`, and its custody entries are named by it; the Secure Enclave or TPM key is the machine's and is kept across rotations. Every blob sealed under the master key begins with the header — one format byte and the 16-byte key id, ahead of the 24-byte nonce, the ciphertext and the tag — bound into the AAD, and a reader opens each blob with the key its header names (`master-key-header.ts`).
- **One sealing format**: every daemon private key is sealed under the master key with XChaCha20-Poly1305 behind the header and `AAD = header || purpose || row id || "ais.master-wrap.v1"` (`daemon-key-sealer.ts`); each content key's wrap carries the same header ahead of its own AAD.
- **In-memory protection**: the unwrapped master is held under `sodium_mlock` and zeroed with `sodium_memzero` on shutdown and, on tiers 1 and 2, after the idle wipe; the master key is never in a backup — a backup carries only the recovery passphrase's 98-byte envelope, once the person sets one.
- **Audit**: emit one `daemon.master_key_source` event on resolution, whose `source` names the custody tier that opened the key (taxonomy registration — see [§Design Decisions](#design-decisions) D-020-5; registered in Spec-005).

## API And Transport Changes

### Data verbs (daemon JSON-RPC via Plan-006's host)

Methods registered by Plan-020 on Plan-006's JSON-RPC `MethodRegistry` (`ipc/handlers/data-handlers.ts`), each with its params and result schemas in `packages/contracts/src/daemon-data.ts`. The host is **daemon-bound, not the control plane**: the handlers read daemon-local `session_content_keys` and `master_keys` rows and the `sodium_mlock`-held master key, which a Cloudflare-Workers control plane cannot reach (data-locality — see [§Design Decisions](#design-decisions) D-020-3). Errors ride the [ADR-009](../decisions/009-json-rpc-ipc-wire-format.md) JSON-RPC envelope.

- `daemon.dataExport {destination}` → a job; `daemon.dataExportSubscribe` carries its progress. `destination` is the path the save dialog hands back, named `sidekicks-export-<date>`, or the command line's folder. The folder holds `sessions/<id>.jsonl` (every event decrypted, one per line, in the canonical event shape), `files/<session id>/…`, `sidekicks/`, `workflows/`, `accounts.json` with no credential, `hosted-account.json` when signed in (the control plane's `account.export`), and `README.txt`; never a settings value, a credential, a pasted token, a workflow secret, a key or a diagnostic log. One session at a time within 64 MiB, one job at a time; an export writes one line to the diagnostic log and no event.
- `daemon.dataErase {}` — `Erase all data`, in order: stop every run and shell as `Stop` does; sign each provider account out (`claude auth logout` in each Claude Code account home, `account/logout` on each Codex service); revoke this machine's refresh family when signed in to the hosted account; destroy the master key's hardware key, the custody entry of every key id in `master_keys`, every backup-key item in iCloud Keychain and every keychain entry the app made; delete the data folder, the account homes it made included; start again empty. Project folders stay, and a backup taken earlier keeps what it held.
- `daemon.keyRotate` — carries the machine's passphrase when the master key is on the passphrase-file tier and the recovery passphrase when one is set, each checked before anything changes and never kept, and runs [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key)'s six steps: create the new key and key id in locked memory; write its custody entry (with its recovery envelope and iCloud Keychain item where those are on) and verify each by reading it back; record it `incoming` in `master_keys`; re-wrap every `session_content_keys` row through `rewrapAll` and re-seal every `daemon_secrets` row under it, each header naming the new id, and in the same `BEGIN EXCLUSIVE` transaction mark it `active` and the old key `outgoing`; then, once no header names the old id, delete the old key's envelope and mark its row `retired`; its custody entry and row go when the last backup sealed with it ages out, and at once when no backup names it. At each start the service applies Spec-020's table to a rotation a crash interrupted, resuming or rolling it back before it serves. A custody change runs the same steps with the current key under a new key id. It also mints a new identity key; the `runtimenode.key_rotated` statement (Plan-028 Phase 5) retires the old identity key, and Plan-016 Phase 5 re-enrolls the new one with the control plane.
- `daemon.unlock {passphrase}` — hands the passphrase to a service whose master key is on the passphrase file; refused on any other tier.

## Invariants

Behavioral invariants this plan must preserve; the §Implementation Phase Sequence Tasks cite them in `Verifies invariant`.

- **I-020-1 — Plaintext master key never persisted.** The plaintext daemon master key is never written to any persistent surface the daemon controls — it lives only hardware-wrapped, in the keychain entry, in the passphrase file, or in locked memory; no plaintext file, backup, log, or daemon-managed swap holds raw key bytes. ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key).) Tasks: T22.1.2, T22.1.1.
- **I-020-2 — Refuse over plaintext fallback.** With no custody tier that opens, the daemon exits non-zero, says why in `sidekicks daemon status`, and never synthesizes or persists a plaintext master. ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key).) Tasks: T22.1.2.
- **I-020-3 — Unattended where the machine allows.** On a machine with a usable security chip or keychain the master key opens with no person present; only the passphrase-file tier waits for `daemon.unlock`, and the passphrase is never kept. ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key).) Tasks: T22.1.2, T22.1.3, T22.1.6.
- **I-020-4 — Passphrase file binds the version byte.** The passphrase file's AEAD associated data is the full 50-byte header including the version byte; a flipped version byte fails authentication. ([ADR-021 §Tier 3 — Argon2id passphrase file](../decisions/021-cli-identity-key-storage-custody.md#tier-3--argon2id-passphrase-file); [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key); D-020-1(b).) Tasks: T22.1.4.
- **I-020-5 — Master key memory-locked + wiped.** The unwrapped master lives only in `sodium_mlock`-locked memory and is `sodium_memzero`-wiped on shutdown. ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key).) Tasks: T22.1.5.
- **I-020-6 — Master key never in a backup.** The master key is in no backup or export the daemon writes; a backup carries only the recovery passphrase's wrapped envelope, once the person sets one. ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key).) Tasks: T22.1.5, T22.4.1.
- **I-020-7 — Per-session key isolation.** Each session's content key is an **independent random 32-byte AES-256 key** (CSPRNG at the session's first sealed write); no key material is shared across sessions, derived from a common secret, or re-derivable from any surviving credential or identity record. This is the crypto-shred precondition (I-020-14 / [Spec-020 §PII Payload Column Pattern](../specs/020-data-retention-and-gdpr.md#pii-payload-column-pattern)): the key's only copy is the wrapped `session_content_keys.encrypted_key_blob`, so deleting that row, or destroying the master key that wraps it, destroys it irrecoverably, and with it every word of the session, the person's and the machine's. Tasks: T22.5.1.
- **I-020-8 — Bounded nonce-collision safety.** PII AES-256-GCM random 96-bit nonces stay within the NIST SP 800-38D §8.3 collision bound because write volume is bounded per session key, not across the event log; the AAD provides record-binding and separates the PII partition from the content partition under the one key, never nonce safety. (NIST SP 800-38D §8.3.) Tasks: T22.3.1.
- **I-020-9 — Every master-key wrap binds its row and names its key.** A content key's wrap AAD is the master-key header followed by `session_id || "ais.session-content-wrap.v1" || key_version`, and a sealed private key's is the header followed by `purpose || row id || "ais.master-wrap.v1"`; a wrapped blob cannot be replayed under another row or another key version, or relabeled to another master key. ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key); D-020-6.) Tasks: T22.2.2, T22.2.4.
- **I-020-10 — `key_version` counts wraps.** A content key is never regenerated; each master-key rotation re-wraps the row, raises `key_version` by one and stamps `rotated_at`, in the transaction that makes the new master key active, and the AAD binding refuses any earlier wrap. (Plan §Non-Goals; [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key).) Tasks: T22.4.3.
- **I-020-13 — `splitPii` is pure.** `splitPii` performs no encryption or IO; the same input yields the same partition. Tasks: T22.3.1.
- **I-020-14 — Key destruction renders PII irrecoverable.** A session's content key is a random DEK with **no derivation**, so once the purge has deleted its row, or `Erase all data` has destroyed every custody copy of the master key it is wrapped under, no surviving secret — credential, **identity record**, or backup taken without a recovery envelope — recovers plaintext PII. (A credential- or identity-derived key would survive via its surviving source secret; the random-DEK construction (D-020-2) is what makes this invariant hold.) ([Spec-020 §PII Payload Column Pattern](../specs/020-data-retention-and-gdpr.md#pii-payload-column-pattern); [Spec-020 §Acceptance Criteria](../specs/020-data-retention-and-gdpr.md#acceptance-criteria).) Tasks: T22.3.1, T22.4.2, T22.5.1.
- **I-020-15 — The export carries no secret.** An export folder holds no settings value, credential, pasted token, workflow secret, key or diagnostic log, and it streams one session at a time within 64 MiB, one export at a time. ([Spec-020 §Data Export](../specs/020-data-retention-and-gdpr.md#data-export).) Tasks: T22.4.1.
- **I-020-16 — Erase runs in its order.** `daemon.dataErase` stops work, signs providers out and revokes the refresh family before it destroys any key, and destroys every custody copy of the master key and every keychain entry the app made before it deletes the data folder; project folders are never touched. ([Spec-020 §Erasure Paths](../specs/020-data-retention-and-gdpr.md#erasure-paths) Path 1; [Spec-020 §Ordering And Atomicity](../specs/020-data-retention-and-gdpr.md#ordering-and-atomicity).) Tasks: T22.4.2.
- **I-020-17 — Rotation never commits under a memory-only key.** `daemon.keyRotate` writes and verifies the new key's custody entry and records it `incoming` in `master_keys` before it wraps anything under it; re-wraps every content key and re-seals every `daemon_secrets` row in the same transaction that makes the new key `active`; and deletes the old key's custody entry only after no header names it and the last backup sealed with it has aged out. A start after a crash at any step resumes or rolls back as Spec-020's table says, and every row opens under the key its header names. ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key).) Tasks: T22.4.3.
- **I-020-18 — Schema doc matches wrap cipher.** `local-sqlite-schema.md` documents every master-key wrap as XChaCha20-Poly1305 behind the master-key header (matching the daemon's one schema), not AES-256-GCM. Tasks: T22.4.5.
- **I-020-19 — Reciprocal completeness.** Every CP-020 obligation has a reciprocal entry in its owner plan; no one-sided cross-plan edge ships. For CP-020-6 (the `REFERENCES users(id)` Path-2 closure), every owner table's plan carries a live reciprocal, so the closure is complete with no silent gap. Tasks: T22.5.1.
- **I-020-20 — Key first at purge.** The purge overwrites the session's `encrypted_key_blob` with a same-length `zeroblob` and deletes its `session_content_keys` row before the session's rows in the same transaction, checkpoints with `TRUNCATE` after commit, and no foreign-key cascade blocks or reorders that delete. ([Spec-020 §Ordering And Atomicity](../specs/020-data-retention-and-gdpr.md#ordering-and-atomicity).) Tasks: T22.3.2, T22.5.1.
- **I-020-21 — No phantom PII columns.** Every column named in the §PII Data Map resolves to a real column in its owner plan's schema. (D-020-4.) Tasks: T22.5.1.
- **I-020-22 — One purge.** `daemon.retentionPurge` is the only path that deletes a session, and it runs this plan's key step first; nothing deletes a session by age. ([Spec-020 §Retention Policy](../specs/020-data-retention-and-gdpr.md#retention-policy); [Spec-020 §Ordering And Atomicity](../specs/020-data-retention-and-gdpr.md#ordering-and-atomicity).) Tasks: T22.5.1.
- **I-020-23 — One sealing format.** Every other daemon key — identity key, channel key, the hosted account's DPoP key and refresh token, the MCP governance key — is sealed under the master key with XChaCha20-Poly1305 behind the master-key header and `AAD = header || purpose || row id || "ais.master-wrap.v1"`, and a sealed blob moved to another row or purpose, or relabeled to another master key, fails to open. ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key).) Tasks: T22.1.7.
- **I-020-24 — Windows custody stays in the Windows half.** On a Windows computer, native or WSL, every hardware-wrap and Credential Manager step runs in the service's Windows half at `CRED_PERSIST_LOCAL_MACHINE`; every Credential Manager entry the service writes goes that way, whichever unit writes it — the master key's, a pasted token's, a workflow secret's, a tool server's refresh token or DPoP key — and none at a roaming persistence; the Windows half holds the master key only for the one unwrap and never sees a key sealed under it, and custody never moves between sides. ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key).) Tasks: T22.1.6.

## Design Decisions

The design decisions this plan settles, each folded into the plan body above.

- **D-020-1 — Master-key custody Type-2 parameters → ratified.** (a) The spec's custody ladder (hardware wrap, keychain, Argon2id passphrase file, refuse-over-plaintext; reject keytar/base64) and its one sealing format are spec-canonical ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key); Plan-006 CP-006-8). (b) The passphrase file's AEAD associated data is the **full 50-byte header**, so the version byte is bound into the AEAD, as [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key) states ([ADR-021 §Tier 3 — Argon2id passphrase file](../decisions/021-cli-identity-key-storage-custody.md#tier-3--argon2id-passphrase-file)). **Type 2.**
- **D-020-2 — Content keys are random DEKs, one per session, and the person's words are sealed under them.** A session's content key is a **random 32-byte AES-256 DEK** (CSPRNG at the session's first sealed write), wrapped under the master key, whose only copy is `session_content_keys.encrypted_key_blob`; it seals both partitions of the session's rows, the person's words (`pii_payload`, under the `ais.session-pii.v1` label) and the machine's (`content_payload`). No key is derived from a Plan-016 secret. **Rationale (the hardened call, not the convenient one):** a credential- or identity-derived key is re-derivable from a secret that _survives_ the key's deletion (the credential, or Plan-016's immutable identity record), so deleting it would **not** destroy it — silently defeating the GDPR Art. 17 crypto-shred erasure guarantee ([Spec-020 §PII Payload Column Pattern](../specs/020-data-retention-and-gdpr.md#pii-payload-column-pattern), I-020-14). Envelope encryption (a random DEK wrapped by a KEK) is the AWS KMS / Google Cloud KMS / Rails ActiveRecord Encryption consensus and the construction under which destroying the key, or the key that wraps it, is true cryptographic erasure. Sealing the person's words under the session's key rather than a key of their own is what lets the purge, which deletes that key before the rows, leave no readable copy of them in freed pages; a key of the person's own would outlive every purge. No key is derived for this: master-wrap = XChaCha20-Poly1305, passphrase key = Argon2id, PII and content = AES-256-GCM, content key = random DEK. The one HKDF in the ladder is the Secure Enclave wrap's (ephemeral P-256, ECDH, HKDF-SHA-256, AES-256-GCM), and it runs inside the `sidekicks-keywrap` helper over the enclave's agreement, never over a person's secret. **Type 2.**
- **D-020-3 — Data verbs → daemon JSON-RPC on the `daemon` root.** `daemon.dataExport`, `daemon.dataExportSubscribe`, `daemon.dataErase`, `daemon.keyRotate` and `daemon.unlock` are **daemon JSON-RPC methods** on Plan-006's `MethodRegistry` (data-locality: the handlers reach daemon-local `session_content_keys`, `master_keys` and the `sodium_mlock`-held master, which a Cloudflare-Workers control plane cannot). Each registers its strict params schema from `packages/contracts/src/daemon-data.ts`, which Plan-006's `MethodRegistry.dispatch` Zod-parses before the handler body runs ([Plan-006 §I-006-7 — Schema validation runs before handler dispatch](./006-local-ipc-and-daemon-control.md#i-006-7--schema-validation-runs-before-handler-dispatch)). The names follow the `daemon` root's `<noun><Verb>` form, and the progress stream is `<noun>Subscribe` beside `daemon.dataExport`. **Type 1.**
- **D-020-4 — Diagnostic bucket-PII shape → ratified `bucket_payload BLOB`.** `local-sqlite-schema.md` is the build-time authority: the four per-field column names in the §PII Data Map bounded tier ([Spec-020 §PII Data Map](../specs/020-data-retention-and-gdpr.md#pii-data-map)) are a documentation gloss; the canonical shape is the single `bucket_payload BLOB`, and the §PII Data Map is reconciled to match. **Type 1.**
- **D-020-5 — `daemon.*` event taxonomy → registered in Spec-005.** `daemon.master_key_source` and `daemon.pii_split_ambiguous` are registered in the Spec-005 taxonomy. `daemon.pii_split_ambiguous` is reconciled against any Plan-005 `daemon.pii_split_*` sibling to avoid a duplicate. **Type 1.**
- **D-020-6 — Wrap-AAD binding.** Every master-key wrap's AAD begins with the master-key header, which names the key that sealed the blob, and then binds the row: `session_id || "ais.session-content-wrap.v1" || key_version` for a content key, `purpose || row id || "ais.master-wrap.v1"` for a sealed private key. `key_version` counts the row's wraps, raised by one at each master-key rotation (I-020-10); binding it and the header keeps a wrapped blob from being replayed under another version, rolled back to an earlier wrap or relabeled to another master key, so the envelope is right in the daemon's one schema ([Spec-020 §Schema Requirements](../specs/020-data-retention-and-gdpr.md#schema-requirements)). **Type 2.**
- **D-020-7 — Path-2 fan-out is the complete `REFERENCES users(id)` inbound-FK closure.** Path-2 is anchored to the **schema-derived FK closure** (see CP-020-6 for the counting rule) rather than a hand-maintained list, so the set is verifiable against [shared-postgres-schema.md](../architecture/schemas/shared-postgres-schema.md) and cannot silently drift. [Spec-020 §Erasure Paths](../specs/020-data-retention-and-gdpr.md#erasure-paths) Path 2 names the full closure + per-table disposition, and its "Scope: exhaustive" claim is anchored to the FK closure rather than to the §PII Data Map, which lists PII-content columns and not the FK-linkage tables. Live owner: Plan-016 Phase 5's `account.delete`, which deletes the whole closure (CP-020-6). Plan-016 Phase 5 builds the token denylist and `account_audit` with their dispositions named in CP-020-6. The `revoked_*` disposition is anonymize-`user_id`-with-denylist-survival: the denylist lookup is keyed on `jti` / `family_id` (the table PRIMARY KEY), **not** on `user_id`, so anonymizing `user_id` severs the data-subject linkage without touching the revocation check — the row stays denied to its natural `expires_at` reap, so erasure does not resurrect a revoked token within its validity window (the GDPR Art. 17(3) security carve-out). **FK-safety mechanism.** "anonymize" is realized by `ON DELETE SET NULL`, not a tombstone identifier. The one anonymize-class FK, `revoked_jtis.user_id`, which Plan-016 Phase 5 adds, is nullable with `ON DELETE SET NULL` in the control plane's one schema, so the `users` hard-DELETE auto-nulls the reference DB-side: FK-safe, and a no-op on the PRIMARY-KEY `jti`. `revoked_token_families` rows are hard-DELETEd with the account. A reserved _tombstone user row_ was rejected: it spawns a ghost-row subsystem for no gain over `SET NULL`. [Spec-020 §Erasure Paths](../specs/020-data-retention-and-gdpr.md#erasure-paths) Path 2 FK-safety is the canonical statement. **Type 1.**
- **D-020-8 — `daemon.*` events bind to a reserved node-scope sentinel `session_id`.** Plan-020's two `daemon.*` events (`daemon.master_key_source`, `daemon.pii_split_ambiguous` — D-020-5) are daemon-scope, not session-scope, but the local `session_events` store pins `session_id NOT NULL` and every envelope carries a `sessionId`. Resolution (no new replay mechanism): these events bind to a **reserved node-scope sentinel `session_id`** in the daemon-local `session_events` store, reusing the existing per-session monotonic-sequence machinery with the sentinel as the partition key — the sentinel forms its own sequence partition exactly as a real session id does. The local SQLite `session_events.session_id` carries **no** foreign key (it is `TEXT NOT NULL`, not a `REFERENCES` — confirmed in [local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md)), so a sentinel value is admissible without a phantom `sessions` row. [Spec-005 §Security Events](../specs/005-session-event-taxonomy-and-audit-log.md#security-events-security_events) defines the sentinel binding for these registered daemon-scope events. **Sentinel value.** The reserved sentinel is pinned to the **RFC 9562 §5.10 Max UUID** `ffffffff-ffff-ffff-ffff-ffffffffffff` — admissible under the branded-id validator (the `packages/contracts/src/internal/branded.ts#brandedUuidIdSchema` factory's `RFC_9562_TEXT_FORM` predicate, which carries the Max UUID as its own alternative), so it passes the wire `EventEnvelopeSchema`'s UUID-branded `SessionIdSchema` (a non-UUID sentinel would be rejected before append/serialization), and chosen over the Nil UUID to stay distinguishable from an accidental nil/zero-init and structurally disjoint from the `gen_random_uuid()` v4 space; canonical in [Spec-005 §Security Events (security_events)](../specs/005-session-event-taxonomy-and-audit-log.md#security-events-security_events). **Type 1.**

## Implementation Steps

1. ## Test And Verification Plan

- **Unit, master-key header**: a blob sealed under one master key fails to open when its header is changed to name another key id or its format byte is changed, and a reader opens each blob with the key its header names.
- **Unit, `split-pii`**: given emitter inputs with explicit `{payload, piiPayload}` partitions, confirm routing only — `splitPii` is a **pure partition** that performs no encryption (sealing is Plan-005-owned per T22.3.1); given ambiguous mixed-shape inputs (nested records with unclassified fields), confirm fallback routes the whole ambiguous record to `pii_payload` and emits `daemon.pii_split_ambiguous`.
- **Schema**: the daemon schema's test asserts that `PRAGMA table_info(session_events)` carries `pii_payload` and `PRAGMA table_info(master_keys)` carries `key_id`, `state` and `created_at`.
- **Integration, write-path**: end-to-end session creation → event write → SQLite inspection shows `pii_payload` is ciphertext bytes (not plaintext JSON) that opens only under the session's content key with the `ais.session-pii.v1` label, and that the `payload` column contains only non-PII fields.
- **Integration, master-key resolution event**: each successful custody tier emits exactly one `daemon.master_key_source` event naming that tier; the refuse path emits none and exits non-zero.
- **Integration, master-key custody**: the keychain entry holds the hardware-wrapped key where tier 1 exists (never raw bytes); the passphrase file round-trips under Argon2id and the service stays locked until `daemon.unlock`; with no tier the daemon exits non-zero with no plaintext written; a tampered enclave handle is a refusal and never a daemon fault. **Manual**: on a Mac with a Secure Enclave confirm an unattended start; on Windows confirm the Credential Manager entry is local-machine and not Enterprise, from both a native and a WSL service; on Linux with lingering confirm a run started before login fails its step and the retry after login succeeds.
- **Integration, sealing format**: a daemon private key sealed for one row or purpose fails to open under another.
- **Integration, rotation**: after `daemon.keyRotate` every event, content key and daemon secret opens under the new master key, every header names it, and the old key is `retired` in `master_keys` with its custody entry kept; a restore on this machine of a backup taken before the rotation opens, and once the backup run prunes the last backup sealed with the old key, its custody entry and row are gone. A process killed after each of the six steps and during step 4 restarts, resumes or rolls back as Spec-020's table says, and every row opens; no blob is ever committed under a key whose custody entry was not first written and verified. A custody change leaves every header naming the new key id, and a backup taken before it still restores. On the passphrase-file tier, and with a recovery passphrase set, a rotation without the passphrase it needs is refused before step 1. 10,000 sessions re-wrap within 2 s.
- **Integration, export**: the folder holds every session's events decrypted and none of the excluded classes (a seeded pasted token, workflow secret and key are searched for and absent); memory stays within 64 MiB on a store larger than it.
- **Integration, erase**: the six steps run in order; afterward no keychain entry the app made remains, the data folder is gone, a project folder is untouched, and the next start opens as on first launch.
- **Integration, purge key step**: after a purge the session's content-key row is gone in the same transaction as its rows; a typed message and a machine-authored body copied from a freed page or the write-ahead log before the purge do not open, and a byte scan of the database file and the write-ahead log after the purge finds none of the session's typed text and no copy of its wrapped content key.

4. Land the data verbs in `data-handlers.ts` (`packages/runtime-daemon/src/ipc/handlers/`, registered on Plan-006's `MethodRegistry` per D-020-3) + documentation updates (Steps 9–10), then the purge's key step (Step 11).

## Rollback Or Fallback

- A machine with no usable security chip starts at the keychain tier, and one with no keychain at the passphrase file — no code change required. There is no plaintext fallback; refuse-to-start is the only terminal state. On Linux with lingering, a locked keyring at start leaves the service locked, and the next run or retry after login reads the key.
- If an emitter passes a mixed-shape record where PII/non-PII partitioning is ambiguous (e.g. a nested object where some keys are PII and others are not, with no explicit partition), the splitter's default policy is **route the whole ambiguous record to `pii_payload`** (err on the side of encryption). Emit a `daemon.pii_split_ambiguous` event with the event type + field path for operator audit. This is a containment fallback, not a rollback. The emitter should partition fields explicitly on the next write path touch.
- If `pii_payload` or `master_keys` is missing from the daemon's one schema, the schema's test fails before merge.
- A rotation a crash interrupts is resumed or rolled back at the next start by Spec-020's table, with no person involved; a service whose custody is locked at start applies the table once it is unlocked.

## Risks And Blockers

- **Risk**: an emitter forgets to partition PII fields explicitly and passes PII as plain `payload`. **Mitigation**: code review rule — every event emission that could plausibly carry PII content (user text, file content, prompt bodies, provider outputs) MUST route through `splitPii` with an explicit `piiPayload` argument; the splitter's ambiguous-record containment fallback (route-to-pii_payload + `daemon.pii_split_ambiguous` event) protects against accidental plaintext writes but is not the primary safeguard.
- **Risk**: neither a security chip nor a keychain is usable on a headless host. **Mitigation**: the passphrase file (Argon2id) is the fallback — _not_ a plaintext file — and refuse-to-start is the only terminal state. Platform-coverage tests exercise every tier.
- **Risk**: the Linux hardware tier is unbuilt until a probe on a machine with a TPM chooses between `systemd-creds` and the TPM2 software stack, and the Windows TPM tier's cost is unmeasured. **Mitigation**: Linux starts at the keychain tier; T22.1.6 measures the Windows tier before it ships.
- **Design note**: every content key is a **random DEK**, one per session (envelope encryption), not a credential- or identity-derived key — so there is no `ikm`-mutation data-loss class and no Plan-016 producer dependency (D-020-2). This is also the crypto-shred correctness precondition ([Spec-020 §PII Payload Column Pattern](../specs/020-data-retention-and-gdpr.md#pii-payload-column-pattern)). A content key is never regenerated; rotation re-wraps it under a new master key and raises `key_version` (I-020-10).
- **A deleted key row's bytes stay in its freed page.** Measured on SQLite 3.53.4, the version the pinned `better-sqlite3` embeds, in write-ahead-log mode: ten wrapped keys removed by `DELETE` alone stayed byte-for-byte in the database file after a `TRUNCATE` checkpoint, where the master key would still unwrap them. The key step therefore overwrites the wrapped key with zeros of the same length before it deletes the row, and checkpoints with `TRUNCATE` after commit; measured the same way, none of the ten stayed in the database file or the log. No `secure_delete` pragma is set. The purge's byte-scan test repeats the measurement on every SQLite the build pins.

## Schema And Code-Path Ownership

Plan-020's schema — `session_events.pii_payload` and `master_keys` — is in the daemon's one schema, while Plan-020's implementation code paths (the custody ladder, the sealer, the master-key header, rotation, export, erase and the purge's key step) ship here. Plan-020 owns the `master_keys` table and its code paths. Plan-020's place in the build order is the dispatch group [cross-plan-dependencies §Dispatch groups](../architecture/cross-plan-dependencies.md#dispatch-groups) lists it in.
