## Goal

Implement durable local persistence, projection rebuild, and startup recovery for session execution state.

## Scope

This plan covers SQLite-backed canonical local persistence, projection rebuild services, runtime-binding restoration, startup recovery sequencing — the restart compare with its read-only add and its question (`run.recoveryResolve`) — and the `recovery` field on `daemon.status.read`. It also owns the per-session **file checkpoint store** [Spec-013 §Required Behavior](../specs/013-persistence-and-recovery.md#required-behavior) defines — the copies the daemon takes before each edit and at each prompt boundary, and the captures it takes before and after every command an agent or a child runs, held with the session outside the checkout and surviving a resume and a restart — and the session verbs that read it, the dry run `session.restorePreview` and the undo `session.restore`. That store is the single source every file restore reads from, on both providers, for a message and a named snapshot alike. [Plan-002](./002-queue-steer-pause-resume.md)'s T3.13 is the run side of an undo whose scope includes the conversation (CP-012-1), and the turn-boundary snapshots and the capture half of [Plan-007](./007-worktree-lifecycle-and-execution-modes.md)'s snapshot service, which this plan extends with the owner's capture folder (CP-012-2), name the point a snapshot-anchored undo returns to.

## Non-Goals

- Runbook authoring
- Long-term retention tuning
- Provider-specific internal persistence formats

## Data And Storage Changes

- Add or extend local `session_events`, `session_snapshots`, `command_receipts`, `runtime_bindings`, `queue_items`, and approval-state tables for recovery completeness, in the one schema per database and its schema test.
- Add recovery-status projection data and projection cursors needed to expose healthy, rebuilding, degraded, or blocked startup state.
- The per-session file checkpoint store keeps its copies **with the session and outside the checkout** — outside a chat's managed workspace too, which is a chat's checkout — so a copy never appears in a diff and survives a working-folder move, and it keeps its own index of them beside the copies. Every git capture — the per-command captures, the turn snapshots and a workflow run's points — is written into its owner's capture folder (a session's or a workflow run's), with its refs inside it; the only refs in the person's repository are the base pins under `refs/sidekicks/base/<owner id>/`. No local table is added for either and no existing table grows a column: both are file-backed node-local state. A session's copies and capture folder are retained on archive, held in every backup, and deleted with the session at purge, the capture folder with its pins.
- See [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md) for column definitions.

## API And Transport Changes

- Add the `recovery` field to `daemon.status.read`, which states healthy, rebuilding, degraded or blocked; there is no recovery read of its own. Add `ProjectionRebuild`, `EventsReadAfterSequence`, and `RuntimeBindingRead` APIs to the typed client SDK and daemon contract.
- Expose machine-readable recovery outcomes, failure categories and recovery conditions through the same contracts.
- The undo's session verbs are `session.restorePreview {sessionId, target, scope}`, the dry run, which changes nothing, and `session.restore {sessionId, target, scope, clientIdempotencyKey, resend?, includeAlsoChanged}`, the undo; their request and result are [Spec-003 §Interfaces And Contracts](../specs/003-queue-steer-pause-resume.md#interfaces-and-contracts)'s one undo contract and the dry run's figures are `session.restorePreview`'s response in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md). `session.snapshotList {sessionId}` lists a session's snapshots from its capture folder. Every undo outcome is the event `session.restore_finished`.
- The restart question's answer is `run.recoveryResolve {runId, choice: keep_provider | undo_to_agreed | continue_provider | hand_over}`, recorded as `run.recovery_resolved`; a read-only surplus added with no question is `run.recovery_steps_added {count, provider}`.

## Invariants

- **I-012-1 (a restart re-executes no command receipt):** The startup sweep re-executes no command: an in-flight receipt with a durable MCP task handle at a server reached at an address resumes through `tasks/get` and `tasks/result`, delivered once, and every other in-flight receipt halts its run with a `recovery-needed` condition for the person. Within a single boot the two-phase receipt commit's Phase-2 optimistic compare-and-set (`UPDATE ... SET started_at = now() WHERE started_at IS NULL`) admits exactly one claimant per receipt, so concurrent workers never double-invoke. [Spec-013 §Idempotency Protocol](../specs/013-persistence-and-recovery.md#idempotency-protocol), [Spec-013 §Two-Phase Receipt Commit](../specs/013-persistence-and-recovery.md#two-phase-receipt-commit), [Spec-013 §In-Flight Receipts After A Restart](../specs/013-persistence-and-recovery.md#in-flight-receipts-after-a-restart).
- **I-012-2 (idempotent rebuild):** `ProjectionRebuild` for a session over the same canonical event range yields identical projection state regardless of how many times it runs. [Spec-013 §Interfaces And Contracts](../specs/013-persistence-and-recovery.md#interfaces-and-contracts), [Spec-013 §Acceptance Criteria](../specs/013-persistence-and-recovery.md#acceptance-criteria).
- **I-012-3 (no premature admission):** No mutable operation is accepted until startup recovery has restored canonical local truth or the node is in an explicit blocked/degraded state. [Spec-013 §Default Behavior](../specs/013-persistence-and-recovery.md#default-behavior), [Spec-013 §Acceptance Criteria](../specs/013-persistence-and-recovery.md#acceptance-criteria).
- **I-012-4 (no silent run loss):** A persisted driver handle that cannot be resumed transitions its run to `failed` with visible recovery-failure detail; it never silently disappears or restarts as a new run. [Spec-013 §Fallback Behavior](../specs/013-persistence-and-recovery.md#fallback-behavior), [Spec-013 §Acceptance Criteria](../specs/013-persistence-and-recovery.md#acceptance-criteria).

- **T15.6 — Build the per-session file checkpoint store and the command captures: capture, capture folder, retention, and durability.** Not built.
  - **Edit capture** rides **the pre-tool hook the daemon registers to hold a run for a pause** — one mechanism, never a second interception path. Before the agent or any of its children edits a file, and at every prompt that starts a turn, the store copies that file aside as it was, one copy per content version; the file-editing tools are Claude Code's `Write`, `Edit`, `MultiEdit` and `NotebookEdit` and Codex's `apply_patch`, and a file created since the checkpoint is recorded as new so an undo removes it rather than leaving it behind. Re-verify the tool names against the then-installed provider binaries before this code lands, the way the cut verbs are re-verified.
  - **Command captures.** Around every command an agent or any of its children runs, the daemon captures the working folder itself, outside every sandbox: before the command starts, holding the start until the capture is written, and when it ends, holding nothing. On Claude Code the captures answer the daemon's command wrapper, run as `CLAUDE_CODE_SHELL_PREFIX` after Claude Code's permission decision: `starting` is acknowledged at once and answered `go` once the before-capture is written, and `exited` with the exit code triggers the after-capture while the tool result never waits for it; the wrapper tells a Bash command apart by its string shape, and hook, status-line and tool-server commands take no capture. On Codex they answer the daemon's relay in front of `codex exec-server`, which holds an approved `process/start` until the before-capture is written and passes `process/exited` at once, each start carrying `metadata: {threadId, toolCallId}` so each capture is tied to its command's row and thread. A command's window runs from its before-capture to its after-capture, a background command's included. What changed between the two captures (`git diff-tree -r -z --no-renames`) enters the store as ordinary copies under the checkpoint of the prompt that started the turn, and for each path changed after a point the earliest version recorded after it wins, whichever leg recorded it. An edit during a command's window is seen by both legs, and both record the same before-image. A capture that fails, or no acknowledgment of `starting` within 10 s, lets the command run uncovered, and the checkpoint records it so the dry run names it `ran while the service could not capture it`. The same capture runs, with no handshake, around each workflow step the daemon spawns or calls itself.
  - **The capture folder** (CP-012-2). Every capture is written through Plan-007's capture half with the owner's capture folder as a parameter, never a second git runner: only `GIT_INDEX_FILE` (the owner's scratch index, seeded once from a copy of the repository's own index and kept) and `GIT_OBJECT_DIRECTORY` set, `git update-index -q --refresh`, the staging pipeline of [Spec-008 §Turn-Boundary Snapshots](../specs/008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots) (`git ls-files -co --exclude-per-directory=.gitignore` into `git update-index --add --remove -z --stdin`, never `git add -A`), `git write-tree --missing-ok`, read back with the repository's objects as an alternate. At the owner's first capture and whenever HEAD moved, the objects HEAD's tree lacks are packed into the folder (`git rev-list --objects <tree> --not HEAD^{tree}` into `git pack-objects`); each kept point pins the person's own commit it stood on, one ref per distinct commit under `refs/sidekicks/base/<owner id>/`, and a command's own capture needs no pin. A capture records HEAD; the files changed by a command during which HEAD moved are named `changed by a git command that moved the branch`. A capture lists the turn snapshot's own listing plus the project's ignored files that sit outside an ignored folder, less the files over 10 MiB.
  - **Large files** are never hashed: each is shadowed by a copy-on-write clone in the session's folder (`clonefile` on APFS, `FICLONE` on Btrfs and XFS, block cloning on ReFS and Dev Drive), found at the first capture from the index's recorded sizes and a stat of each untracked path, and re-statted at every capture; a large file whose size or times changed outside a command's window is re-shadowed at the next before-capture; at an after-capture a changed one's shadow becomes its store copy and a fresh shadow is cloned. On a volume that cannot clone, a large file a command changed is named `too large to keep` and never copied.
  - **Sessions sharing a folder.** Captures of one working folder run one at a time, across every session working in it. The store records each session's own edits and command windows, so an undo puts back only its own session's changes and marks a path another session also changed since the point `also changed by <session>`.
  - **The public snapshot list.** `session.snapshotList {sessionId}` reads the session's capture folder through a public list method added beside the retention half's private ref listing, one git read per inspector open, each row a snapshot's opaque id, its name and its time.
  - The copies are held **with the session and outside the checkout** — outside a chat's managed workspace too: they never appear in a diff, they survive a working-folder move, and they survive a resume and a daemon restart — the store's index is part of the node's durable local state and is read back at startup rather than rebuilt from the tree.
  - **Retention.** Every checkpoint of a session is kept for the session's life, for both legs, removed only by an undo or by deleting the session or its data.
  - **Repack and purge.** The service's hourly sweep, a job on its one scheduler, prunes nothing and repacks each capture folder from its own objects only (`git rev-list --objects --missing=allow-any <kept refs>` into `git pack-objects --missing=allow-any`), never `git repack -l`, which drops the local copy that protects a capture; a workflow run's points are never pruned while the run's record exists. The owner's purge deletes its capture folder and its base pins.
  - **Budget.** Workload: a 5,000-file checkout and a session of up to 10,000 edits over 1,700 files, and a 50,000-file checkout for the command leg. A checkpoint copy holds an edit at most 5 ms at the 99th percentile for a file up to 1 MiB; a turn-boundary snapshot takes at most 150 ms, at the turn boundary only; a before-capture holds a command at most 125 ms median (200 ms at the 99th percentile) at 5,000 files and 350 ms median (450 ms) at 50,000; an after-capture costs about 1.2 ms per changed file, off the agent's path; refs are packed only on the hourly sweep and after bulk deletes, never on the edit or turn path. Each is measured before and after the change.

## Risks And Blockers

- No compaction runs on a schedule, so rebuild time can grow with the log (correctness is compaction-independent per [Spec-013 §Snapshot Compaction](../specs/013-persistence-and-recovery.md#snapshot-compaction); only rebuild performance is affected)
- Recovery ordering mistakes can admit mutable work before canonical local truth is trustworthy

## Design Decisions

- **D-012-1 — `EventsReadAfterSequence` retains a sequence-position cursor (`afterSequence: number`), not the `EventCursor` brand.** The rebuild read advances over the canonical `session_events.sequence` integer (the `projection_cursors.last_sequence` state machine), so a numeric sequence position is the natural cursor and makes idempotent rebuild (I-012-2) trivially verifiable. The sibling `EventReadAfterCursor` uses the opaque `EventCursor` brand because client-facing event reads must tolerate cursor-format evolution (Plan-004). The two read models intentionally differ; reconciling them to a single brand is a non-blocking refinement **not** adopted in V1 — `docs/architecture/contracts/api-payload-contracts.md §Plan-012 — Persistence And Recovery` keeps `afterSequence: number`.
