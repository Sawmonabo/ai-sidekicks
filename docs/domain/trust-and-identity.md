# Trust And Identity

## Purpose

Define how cryptographic trust and identity are established, verified, and maintained across the session boundary in V1. This domain doc brings together the trust-ceremony semantics that are also described in [security-architecture.md](../architecture/security-architecture.md), [ADR-010](../decisions/010-tokens-passkeys-and-the-remote-channel.md), [ADR-021](../decisions/021-cli-identity-key-storage-custody.md), and [Spec-024](../specs/024-self-host-secure-defaults.md) — first-run secret generation, fingerprint display and verification, identity-key provisioning, and the lifecycle states an identity moves through.

## Scope

This document covers `IdentityMaterial`, `Fingerprint`, and `TrustState` for the person's machines, their linked devices, and a self-host deployment, plus the first-run ceremony that brings a fresh identity into use.

## Definitions

- `IdentityMaterial`: the long-term cryptographic material that authenticates a machine, a device, or a deployment. Concretely: each machine's Ed25519 identity key and its X25519 channel key, minted at the service's first start; each linked device's identity key (P-256 in a phone's hardware, a non-extractable WebCrypto key in the web client) and its X25519 channel key ([ADR-010 §Decision item 4](../decisions/010-tokens-passkeys-and-the-remote-channel.md#decision)); the machine's DPoP key and the PASETO v4 access and refresh tokens the control plane issues against it ([ADR-010 §Decision item 2](../decisions/010-tokens-passkeys-and-the-remote-channel.md#decision)); the daemon master key each machine's service makes at its first start, and the per-session signing keys sealed under it ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key)); and — on a self-host deployment — the relay's first-run secrets, the control plane's Ed25519 key that signs access tokens and its symmetric key that seals refresh tokens, the Web Push VAPID key pair and the relay's Postgres password ([Spec-024 §Required Behavior row 3](../specs/024-self-host-secure-defaults.md#required-behavior)).
- `Fingerprint`: a stable, human-displayable digest of a public-key or certificate object used to verify out-of-band that two parties hold matching cryptographic state. Two fingerprint forms are normative in V1: an [RFC 7469](https://datatracker.ietf.org/doc/html/rfc7469) SPKI-SHA256 base64 pin (survives keypair-preserving certificate rotation) and an SSH-style `SHA256:<hex>` whole-certificate hash (rotates on every re-issue). Both are surfaced together so what the person sees cannot conflate them ([Spec-024 §Required Behavior row 1](../specs/024-self-host-secure-defaults.md#required-behavior), [§Pitfalls](../specs/024-self-host-secure-defaults.md#pitfalls-to-avoid)).
- `TrustState`: the lifecycle position of a piece of identity material — `unprovisioned`, `provisioned`, `verified`, `bound`, `rotating`, `revoked`, or `compromised`. The state machine is enumerated in [§Trust-State Lifecycle](#trust-state-lifecycle).
- `FirstRunCeremony`: the deterministic state transition from "no on-disk identity material" to "all required secrets generated, fingerprints emitted, sentinel written" on a fresh self-host deployment ([Spec-024 §State And Data Implications](../specs/024-self-host-secure-defaults.md#state-and-data-implications)).
- `CustodyTier`: where identity material lives at rest. On a machine, every daemon private key — the identity key, the channel key, the MCP governance key, the DPoP key and the refresh token — is sealed under the daemon master key in one format and stored in the daemon's database as a row of `daemon_secrets`, keyed by its purpose. The master key opens unattended under the person's login from the first tier that works: a hardware wrap (the Secure Enclave on a Mac that has one, the TPM on Windows), the OS keychain, a passphrase file opened with `sidekicks daemon unlock`; with none of them the service refuses to start and says why ([ADR-021 §Custody Tiers](../decisions/021-cli-identity-key-storage-custody.md#custody-tiers)). On a device, the identity key is made on the device and never exported. No key is derived from a passkey ([ADR-010 §Identity Key Storage](../decisions/010-tokens-passkeys-and-the-remote-channel.md#identity-key-storage)).

## What This Is

This model defines the cryptographic anchors that make every other trust property in the system possible: which key authenticates a user, which fingerprint the person visually verifies, what state an identity is in at any moment, and what transitions are allowed between those states.

## What This Is Not

- This is not the device registry. Which user a session belongs to, and which devices are linked to that account, is owned by [User And Device Model](./user-and-device-model.md). Identity is the cryptographic precondition; the registry is the account-scoped record of it.
- This is not policy. What actions an authenticated user may take is owned by [ADR-007](../decisions/007-device-trust-and-permission-model.md) and the Cedar policy engine ([ADR-012](../decisions/012-cedar-approval-policy-engine.md)).
- This is not transport security. How traffic is protected on the wire is owned by [security-architecture.md §Transport Security Requirements](../architecture/security-architecture.md#transport-security-requirements). The transport layer consumes the identity material defined here; it does not redefine it.
- This is not the machine registry. Which machines the account has, their names and whether each is reachable are owned by [Runtime Node Model](./runtime-node-model.md) and [Spec-002](../specs/002-runtime-node-attach.md); which machine and device keys the account trusts is the statement chain in [Spec-028 §Device registration and revocation](../specs/028-remote-control.md#device-registration-and-revocation). This doc defines the keys the chain names.
- This is not approvals. Per-action approval policy is owned by [Artifact Diff And Approval Model](./artifact-diff-and-approval-model.md) and [Spec-010](../specs/010-approvals-permissions-and-trust-boundaries.md).
- This is not the implementation specification. Storage formats, OS keystore APIs, and probe sequences are owned by [ADR-021](../decisions/021-cli-identity-key-storage-custody.md), [security-architecture.md §Authentication Implementation Specification](../architecture/security-architecture.md#authentication-implementation-specification), and [Spec-024 §Interfaces And Contracts](../specs/024-self-host-secure-defaults.md#interfaces-and-contracts).

## Invariants

The following invariants hold across all identity material in V1.

- **First-run secret generation is sentinel-driven.** On a fresh self-hosted relay, the relay generates its required secrets — the control plane's access-token signing key and refresh-token key and its Postgres password, each via `crypto.randomBytes(N ≥ 32)`, and the Web Push VAPID key pair — and writes a `./data/trust/first-run.complete` sentinel ([Spec-024 §Required Behavior row 3](../specs/024-self-host-secure-defaults.md#required-behavior)); a machine's keys are minted by its own service at its first start. Secrets cannot be pre-seeded via env vars or `.env.example`. Deleting the sentinel while the relay's secrets are present does not regenerate them: the relay refuses to start, naming the sentinel and the secrets it found ([Spec-024 §State And Data Implications](../specs/024-self-host-secure-defaults.md#state-and-data-implications)).
- **Public material surfaces with private material.** Public fingerprints, public keys, and bind-address disclosures are printed to stdout AND embedded as a header comment in the on-disk file at first run, mirroring the [`age-keygen`](https://github.com/FiloSottile/age) UX pattern. Private material lives only in the file body ([Spec-024 §Required Behavior row 3](../specs/024-self-host-secure-defaults.md#required-behavior)).
- **Both fingerprint forms are surfaced together.** When a self-signed or internal-CA certificate is in use, the person sees both the [RFC 7469](https://datatracker.ietf.org/doc/html/rfc7469) SPKI-SHA256 base64 pin AND the SSH-style `SHA256:<hex>` whole-cert hash, on stdout and persisted at `./data/trust/fingerprint.txt` ([Spec-024 §Interfaces And Contracts](../specs/024-self-host-secure-defaults.md#interfaces-and-contracts)). The SPKI pin survives keypair-preserving cert rotation; the whole-cert hash matches what browsers display. Conflating the two in what the person sees is a [§Pitfalls](#pitfalls-to-avoid) violation.
- **Key custody is tier-laddered, never silently substituted.** A machine's master key opens from the first tier that works — hardware wrap, OS keychain, passphrase file, refusal — and every other daemon private key is sealed under it ([ADR-021 §Custody Tiers](../decisions/021-cli-identity-key-storage-custody.md#custody-tiers), [ADR-021 §One Custody Root](../decisions/021-cli-identity-key-storage-custody.md#one-custody-root)). Silent backend substitution — Linux kernel `keyutils`, a locked macOS `login.keychain-db`, enterprise-policy-blocked Windows credential writes — is explicitly prohibited; the keychain tier is accepted only after a write-probe-read-delete cycle that catches all three silent-fallback modes within a single synchronous round-trip.
- **Identity-key rotation is never silent.** A machine's identity key is minted at the service's first start, and again only at `sidekicks rotate-keys` and when a removed machine is linked again. Any other path that would return "no identity key found" MUST refuse rather than mint a replacement. `sidekicks rotate-keys` posts a `runtimenode.key_rotated` statement signed by the old key and the new one; from that point in the chain a statement the old key signs is refused, what it signed before stands, and the old key is never trusted again. A removed machine that is linked again first mints a new key under its same machine id, and its new `runtimenode.added` statement moves every device's pin for that id, as a rotation does; its store, sessions and id stay. Every device moves its pin only on one of those statements ([ADR-021 §Refuse-On-Rotation Invariant](../decisions/021-cli-identity-key-storage-custody.md#refuse-on-rotation-invariant)). A silent replacement would be refused by every linked device, since each pins the old key.
- **Daemon master-key rotation is explicit and crash-safe.** The daemon master key is rotated only by `sidekicks rotate-keys` — never on a calendar schedule, and never on a session's end, a purge or an erasure ([security-architecture.md §Daemon Master Key Rotation](../architecture/security-architecture.md#daemon-master-key-rotation)). A rotation writes and verifies the new key's custody entry and records its key id in the store before it wraps anything under it; re-wraps every session content key and re-seals every daemon private key while the old key stays in custody; makes the new key active in the same transaction as the re-wrap; and deletes the old key's custody entries only after no sealed blob still names it and the last backup sealed with it has aged out. Every sealed blob names the key id that sealed it, no row is ever committed under a key that exists only in memory, and an interrupted rotation resumes or rolls back at the next start ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key)). Erasure is `Erase all data`, which destroys every custody copy of the master key.
- **Plaintext private-key material lives only in daemon memory.** Every decrypted daemon private key resides only in the daemon process's memory. The CLI binary itself never holds one; CLI invocations request signing operations from the daemon over the [Spec-006 local IPC](../specs/006-local-ipc-and-daemon-control.md) contract ([ADR-021 §Plaintext-In-Daemon-Memory Only](../decisions/021-cli-identity-key-storage-custody.md#plaintext-in-daemon-memory-only)). The daemon zeroes the buffer on process exit and on idle-timeout eviction.
- **No hardware-rooted protection is claimed where the primitives do not provide it.** The Secure Enclave and the TPM wrap the master key; they do not hold the Ed25519 or X25519 keys, which are sealed under the master key in software, because the Secure Enclave exposes only NIST P-256. The Secure Enclave binding is to the Mac, not to the app: it keeps a copied data folder or disk image unreadable elsewhere and does not stop code running as the same person on the same Mac. Credential Guard protects only domain passwords, not the generic credential the service writes. Linux has no hardware tier ([ADR-021 §Explicitly NOT Claimed](../decisions/021-cli-identity-key-storage-custody.md#explicitly-not-claimed)).
- **A machine's identity is its pinned key, reached over one channel per device.** Every device pins each machine's Ed25519 identity key when the key enters the account's statement chain (`runtimenode.added`), and refuses a machine that answers under a known id with a different key and no `runtimenode.key_rotated` or later `runtimenode.added` statement for that id behind it. A device reaches a machine only over its own channel on the Noise Protocol Framework's `Noise_KK_25519_ChaChaPoly_SHA256`, with no construction of the product's own, on X25519 channel keys that the chain certifies, rekeyed on every connection and every 10 minutes ([Spec-028 §The encryption envelope](../specs/028-remote-control.md#the-encryption-envelope)). The relay holds one live connection per key, and a key seen on two connections that keep displacing each other is flagged. What a device knows of a machine's health is whether its relay connection is live and which version it runs.

## Identity Material Provisioning

Provisioning is the act of bringing identity material into existence and into a state where it can be used. Each material type has a distinct provisioning path; the paths share the invariants above but differ in primitive, authority, and storage tier.

### Machine and device identity keys

Each machine's Ed25519 identity key per [RFC 8032 §5.1](https://datatracker.ietf.org/doc/html/rfc8032#section-5.1) is the anchor every device trusts that machine by. It signs the machine's statements in the account's chain, including the `runtimenode.added` that first trusts it and the certificate over the machine's X25519 channel key, and every device pins it ([ADR-010 §Decision item 4](../decisions/010-tokens-passkeys-and-the-remote-channel.md#decision), [Spec-028 §The encryption envelope](../specs/028-remote-control.md#the-encryption-envelope)).

| Holder | Provisioning path |
| --- | --- |
| Machine | Minted by the service at its first start with its X25519 channel key, both sealed under the daemon master key, and minted again only at `sidekicks rotate-keys` and when a removed machine is linked again, under the same machine id ([ADR-021 §Machine Identity](../decisions/021-cli-identity-key-storage-custody.md#machine-identity)). `sidekicks sign-in` enrolls the public half with the control plane as this machine's key under the signed-in person, read through the daemon's custody code while the service is stopped. The service's registration at its start (`runtimenode.register`) carries that key, and the control plane accepts it only for a key enrolled to that owner and keeps it on the machine's `runtime_nodes` row; the machine's `runtimenode.added` statement enters it in the account's chain, signed by the machine itself for the account's first machine and by the device or machine that links it for every later one. The CLI never holds the decrypted private key — signing operations are brokered through the local daemon over [Spec-006](../specs/006-local-ipc-and-daemon-control.md). |
| Phone | A P-256 identity key made in the iPhone's Secure Enclave or the Android Keystore, and an X25519 channel key in the Keychain or the Keystore's wrapped storage; neither is exported. The `device.linked` statement that trusts the device carries both public halves, the channel key certified by the identity key ([Spec-029](../specs/029-ios-remote-client.md)). |
| Web client | A non-extractable WebCrypto identity key and channel key, entered in the chain the same way. |

**One key per device and per machine is the normal case, not an edge case.** Remote Control means the account holder drives sessions from several devices at once, across any number of machines, so each machine and each device holds its own identity key, entered separately in the account's chain. That is what lets the log record which device acted, not merely that the account did: each device signs the events it originates and the machine verifies that signature before it appends. A key seen on two live relay connections is flagged, which is what surfaces an attacker's copy of a key.

### PASETO v4 access and refresh tokens (per machine)

The control plane issues PASETO v4 tokens per [paseto.io](https://paseto.io/): `v4.public` access tokens (15-minute TTL, signed with the control plane's Ed25519 key, never stored) and a `v4.local` refresh token (XChaCha20 stream cipher with a BLAKE2b-MAC, encrypt-then-MAC, under the control plane's symmetric key) ([security-architecture.md §Control-Plane Authentication](../architecture/security-architecture.md#control-plane-authentication)). Both carry a `cnf.jkt` confirmation claim binding them to the machine's DPoP key thumbprint per [RFC 9449](https://www.rfc-editor.org/rfc/rfc9449). The refresh token is sealed under the daemon master key and lasts until sign-out or revocation; each trade for an access token returns a new refresh token and spends the old one, and its `family` claim detects reuse — presenting a spent refresh token revokes the entire family. PASETO v4 conformance is provided by the in-house `packages/crypto-paseto/` library on top of audited `@noble/curves`, `@noble/ciphers` and `@noble/hashes` primitives ([ADR-010 §PASETO v4 Implementation Library](../decisions/010-tokens-passkeys-and-the-remote-channel.md#paseto-v4-implementation-library)).

A machine signs in with `sidekicks sign-in`, which runs the [RFC 8628 OAuth 2.0 Device Authorization Grant](https://www.rfc-editor.org/rfc/rfc8628): the CLI prints a code and an address, opens the address in the browser where one exists, and waits until the grant is approved. There is no second flow for the desktop app.

### DPoP key (per machine)

The DPoP key per [RFC 9449](https://datatracker.ietf.org/doc/html/rfc9449) is the machine's key pair, sealed under the daemon master key like every daemon private key. Each API request presents the access token as `Authorization: DPoP <token>` ([RFC 9449 §7.1](https://www.rfc-editor.org/rfc/rfc9449#section-7.1) — never `Bearer`, unlike the daemon session token below) and includes a signed `DPoP` header proving possession of the private key, whose claims carry the token's `ath` hash ([RFC 9449 §4.3](https://www.rfc-editor.org/rfc/rfc9449#section-4.3) requires `ath` when a proof accompanies an access-token presentation); the control plane verifies the DPoP signature against the `cnf.jkt` thumbprint embedded in the access token, sender-constraining the token to the machine that minted the proof ([security-architecture.md §Control-Plane Authentication](../architecture/security-architecture.md#control-plane-authentication)). The private key never leaves the daemon.

### Self-host deployment secrets (per deployment)

On a fresh self-hosted relay, the relay's first-run ceremony generates the relay's own secrets, the control plane's Ed25519 key that signs access tokens and its symmetric key that seals refresh tokens, the Web Push VAPID key pair and the relay's Postgres password; a machine's master key and its keys are never deployment secrets, since each machine's service makes them on its own custody ladder ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key)). All are emitted via `crypto.randomBytes(N ≥ 32)` and persisted with mode `0600` on Unix-like platforms or the equivalent ACL on Windows. Public material — fingerprints and public keys — is printed to stdout and to a header comment in the file; private material lives only in the file body ([Spec-024 §Required Behavior row 3](../specs/024-self-host-secure-defaults.md#required-behavior)). The `./data/trust/first-run.complete` sentinel records that the ceremony finished; its absence with no secrets on disk runs the ceremony, its absence with the relay's secrets present refuses start, naming the sentinel and the secrets found, and its presence with missing secrets refuses start ([Spec-024 §State And Data Implications](../specs/024-self-host-secure-defaults.md#state-and-data-implications)).

### Daemon session token (per daemon process)

A 256-bit session token is generated at daemon start via `crypto.randomBytes(32)`, written with owner-only access — `$XDG_RUNTIME_DIR/ai-sidekicks/daemon.token` with mode `0600` on macOS and Linux, `%LOCALAPPDATA%\ai-sidekicks\run\daemon.token` with a user-only access list on Windows, for a native daemon and one in WSL 2 alike — and rotated on every daemon restart. The desktop app's main process and the CLI read it at every connect and present it in the `Authorization: Bearer` header on every IPC request, and the daemon verifies it with `crypto.timingSafeEqual` to prevent timing attacks ([security-architecture.md §Local Daemon Authentication](../architecture/security-architecture.md#local-daemon-authentication)). The token is the transport-layer peer of the at-rest custody model defined in ADR-021.

## Fingerprint Verification Ceremony

A fingerprint is what the person looks at when they need to verify, out of band, that the cryptographic state on their workstation matches the cryptographic state on a peer or service. V1 surfaces two fingerprint forms together because their semantics differ and conflating them is a known footgun.

### The two forms and why both are needed

- **SPKI-SHA256 ([RFC 7469](https://datatracker.ietf.org/doc/html/rfc7469), base64).** A digest of the certificate's `SubjectPublicKeyInfo` field. It survives any certificate rotation that re-issues against the same public key and therefore identifies the **keypair**, not the certificate document. This is the right form to display when the person is establishing a trust pin they expect to outlive certificate expiry / re-issuance.
- **SSH-style whole-cert hash (`SHA256:<uppercase-hex-with-colons>`).** A digest of the entire DER-encoded certificate. It rotates on every re-issue and matches the form most browsers and command-line tools display. This is the right form when the person is comparing what their CLI shows against what their browser shows for the same connection.

What the person sees MUST distinguish the two ([Spec-024 §Pitfalls — Whole-cert fingerprint mislabeled as "public-key fingerprint"](../specs/024-self-host-secure-defaults.md)). Misframing the SPKI pin as "the certificate fingerprint" leads the person to think their pin invalidates on cert renewal; misframing the whole-cert hash as "the public-key fingerprint" leads the person to think the hash should be stable across rotation.

### When the ceremony runs

The fingerprint ceremony runs on `DEPLOY_MODE=lan` self-host deployments, where Caddy uses `tls internal` (an internal CA the person's clients do not yet trust) and the person has to verify out-of-band that the certificate they see in their browser matches the one the relay is serving ([Spec-024 §Required Behavior row 1](../specs/024-self-host-secure-defaults.md#required-behavior)). Both fingerprint forms are printed to stdout during the first-run banner AND persisted at `./data/trust/fingerprint.txt`, so the person can compare what the CLI emitted, what the file contains, and what their browser displays — three independent surfaces that should agree.

In `DEPLOY_MODE=public`, public-CA-issued certificates are trusted by clients out of the box and the fingerprint ceremony is not necessary; the SPKI pin is still computed and persisted for a person who wants to set up additional defense-in-depth pinning, but no banner ceremony is run.

### Identifier ≠ fingerprint

[Syncthing](https://docs.syncthing.net/dev/device-ids.html) derives its `device-id` from the SHA-256 of the DER-encoded certificate, making the identifier and the fingerprint the same artifact. V1 does not adopt this — PASETO `kid` claims per ADR-010 carry the user identifier ([Spec-024 §Implementation Notes](../specs/024-self-host-secure-defaults.md#implementation-notes)). The display convention (show fingerprints where the person expects to look up identity) is copied from Syncthing; the identifier conflation is not.

### Fingerprint rotation

Rotating the underlying keypair MUST rewrite `./data/trust/fingerprint.txt` AND emit a banner warning on the next startup that pins have changed ([Spec-024 §State And Data Implications](../specs/024-self-host-secure-defaults.md#state-and-data-implications)). The SPKI pin changes only on keypair change; the whole-cert hash changes on every re-issue. The person sees both deltas in the banner.

## Trust-State Lifecycle

Identity material moves through a finite set of trust states. The first-run transition is fixed by [Spec-024 §State And Data Implications](../specs/024-self-host-secure-defaults.md#state-and-data-implications), master-key rotation semantics by [security-architecture.md §Daemon Master Key Rotation](../architecture/security-architecture.md#daemon-master-key-rotation), the silent-rotation prohibition by [ADR-021 §Refuse-On-Rotation Invariant](../decisions/021-cli-identity-key-storage-custody.md#refuse-on-rotation-invariant), and when a machine or device key is trusted, rotated or revoked by the account's statement chain ([Spec-028 §Device registration and revocation](../specs/028-remote-control.md#device-registration-and-revocation)).

### States

| State | Meaning | Source |
| --- | --- | --- |
| `unprovisioned` | No identity material exists for this scope. For a self-host deployment: the `./data/trust/first-run.complete` sentinel is absent and no secrets are on disk. For a machine: the service has not yet minted its identity key. | [Spec-024 §State And Data Implications](../specs/024-self-host-secure-defaults.md#state-and-data-implications); [ADR-021 §Custody Tiers](../decisions/021-cli-identity-key-storage-custody.md#custody-tiers) |
| `provisioned` | Identity material has been generated and persisted. Sentinels and headers are in place. The material is usable but has not yet been verified out-of-band by the person. | [Spec-024 §Required Behavior row 3](../specs/024-self-host-secure-defaults.md#required-behavior) |
| `verified` | The person has compared the displayed fingerprint against an out-of-band source (browser, paired device, peer-shared value) and accepted the match. Verification is the person's act, not automatic. | [Spec-024 §Required Behavior row 1, row 10](../specs/024-self-host-secure-defaults.md#required-behavior) |
| `bound` | The key is trusted in the account's statement chain, which every machine verifies itself: a path of `runtimenode.added`, `device.linked`, `passkey.added` and `runtimenode.key_rotated` statements reaches it from the machine's own key, each signed while its signer was still trusted at that point in the chain, and devices pin it. From this state a machine's key changes only by `sidekicks rotate-keys` and its `runtimenode.key_rotated` statement, or by a removed machine's rejoin and its new `runtimenode.added`; any other change is refused by every device. The replaced key signs nothing more, and what it signed before stands. | [Spec-028 §Device registration and revocation](../specs/028-remote-control.md#device-registration-and-revocation); [ADR-021 §Refuse-On-Rotation Invariant](../decisions/021-cli-identity-key-storage-custody.md#refuse-on-rotation-invariant) |
| `rotating` | The material is mid-rotation. For a machine's identity key: a `sidekicks rotate-keys` run is in progress, minting the new key and posting the `runtimenode.key_rotated` statement signed by the old key and the new one; it completes or rolls back. The daemon master key's rotation is not a trust state of its own: its progress is recorded in the `master_keys` table — the new key `incoming` beside the `active` old one, then the old key `outgoing` — and an interrupted rotation resumes or rolls back at the next start. | [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key); [ADR-021 §Refuse-On-Rotation Invariant](../decisions/021-cli-identity-key-storage-custody.md#refuse-on-rotation-invariant) |
| `revoked` | The material has been replaced or invalidated. For the daemon master key: once no sealed blob names the outgoing key's id it is `retired` in `master_keys`, and its custody entries and row are deleted when the last backup sealed with it ages out, or at once when no backup names it, as Spec-020 describes. For tokens: `jti` or `family` is on the revocation list. For a device, machine or passkey key: a `device.revoked`, `runtimenode.removed`, `passkey.removed` or `runtimenode.key_rotated` statement names it on the chain and ends it at that point. A statement it signs afterward is refused; what it signed before stands, so every device, machine and passkey it added stays trusted; a device a since-revoked device linked reads `Linked from <device>, which you revoked. Revoke it if that device was lost.` on its card, and a passkey it added reads `Added from <device>, which you revoked. Remove it if that device was lost.` on its row. An ended key is never trusted again. | [Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key), [security-architecture.md §Token Revocation](../architecture/security-architecture.md#token-revocation); [Spec-028 §Device registration and revocation](../specs/028-remote-control.md#device-registration-and-revocation) |
| `compromised` | The material is known to be exposed (CVE in the implementing primitive, exfiltrated file, a key seen on two live relay connections, a reused refresh token). Treated as `revoked` for use, but `compromised` is preserved as a distinct state so audit and incident-response paths can act on it. | [ADR-021 §Failure Mode Analysis](../decisions/021-cli-identity-key-storage-custody.md#failure-mode-analysis); [Spec-028 §Device registration and revocation](../specs/028-remote-control.md#device-registration-and-revocation) |

### Transitions

```text
unprovisioned ──first-run ceremony──> provisioned
provisioned ──the person's out-of-band match──> verified
verified ──entered in the statement chain──> bound
bound ──sidekicks rotate-keys──> rotating
rotating ──runtimenode.key_rotated on the chain──> bound  (new material)
rotating ──rollback──> bound  (old material)
bound ──CVE / exfiltration signal──> compromised
verified ──fingerprint mismatch on re-display──> compromised
compromised ──out-of-band remediation + new ceremony──> unprovisioned
```

A few transitions deserve explicit notes because the source docs make them load-bearing:

- **`unprovisioned → provisioned`** runs, for a self-hosted relay, only when the `./data/trust/first-run.complete` sentinel is absent. The sentinel's presence with missing secrets blocks relay startup with a message naming the sentinel and the missing secrets rather than silently regenerating ([Spec-024 §State And Data Implications](../specs/024-self-host-secure-defaults.md#state-and-data-implications)). For a machine it runs once, at the service's first start, which mints the identity key and seals it under the master key.
- **`provisioned → verified`** is gated on the person by design. The first-run banner (Spec-024 row 10) lists the fingerprints; the person chooses when to mark them verified (typically by comparing the CLI-emitted fingerprint with the browser-displayed cert).
- **`verified → bound`** is the moment after which any silent rotation becomes catastrophic. From `bound`, the only safe rotation path is explicit: `sidekicks rotate-keys`, for a machine's identity key and the daemon master key alike. [ADR-021's Refuse-On-Rotation Invariant](../decisions/021-cli-identity-key-storage-custody.md#refuse-on-rotation-invariant) is what prevents accidental re-entry to `unprovisioned` from `bound`. For a machine, this transition is three steps. First, `sidekicks sign-in` enrolls the public half with the control plane under the signed-in person, read through the daemon's custody code while the service is stopped. The enrollment is made once: the control plane refuses a different key for an enrolled machine, before any row mutation, unless `sidekicks rotate-keys` re-enrolls it with its `runtimenode.key_rotated` statement, or a removed machine linked again re-enrolls its new key with its new `runtimenode.added`. Second, the service's registration at its start (`runtimenode.register`) is accepted only for that enrolled key. Third, the `runtimenode.added` statement enters the key in the chain. For a device, the transition is the `device.linked` statement.
- **`rotating → bound`** is a machine identity key's: the new key is `bound` once its `runtimenode.key_rotated` statement is on the chain. The daemon master key does not pass through `rotating`: its rotation is recorded in `master_keys` (`active`, `incoming`, `outgoing`, `retired`), the re-wrap and the switch to the new key commit in one `BEGIN EXCLUSIVE` transaction, and a crash between any two of the rotation's steps is resumed or rolled back at the next start, so every sealed blob opens under the key its header names ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key)).
- **`bound → compromised`** can fire on a fingerprint mismatch detected at re-display (the `./data/trust/fingerprint.txt` value no longer matches what the running cert emits) or on an external signal (CVE in `@noble/curves`/`@noble/ciphers` or the Noise library; a key seen on two live relay connections; a reused refresh token). The mismatch path is documented in [Spec-024 §State And Data Implications](../specs/024-self-host-secure-defaults.md#state-and-data-implications) via the rotation-warning-banner contract.
- **`compromised → unprovisioned`** is not automatic — out-of-band remediation must complete (revoking the old material at the control plane, retiring affected sessions) before a new ceremony begins.

## Relationships To Adjacent Concepts

- [User And Device Model](./user-and-device-model.md) — consumes this model. A device becomes usable only once its key is entered in the account's statement chain (`bound`). The device lifecycle is independent of the trust-state lifecycle but interacts at device-revocation time: the `device.revoked` statement ends the device's key at that point in the chain, its channels are closed, and its tokens are revoked; every device and passkey it linked before stays trusted, flagged on its card or row as linked or added from a device the person revoked.
- [Runtime Node Model](./runtime-node-model.md) — a machine's registration (id, name, platform, version) is a record about the machine; its identity key is the trust. A device trusts a machine only through that key in the chain, and what a machine may do is governed by the approval policy engine, not by identity state.
- [Artifact Diff And Approval Model](./artifact-diff-and-approval-model.md) — approvals are answered from devices whose keys are `bound`. The answering device signs its resolution with its own identity key, the machine verifies it before it appends, and a `revoked` or `compromised` key's new signatures are refused.
- [Session Model](./session-model.md) — the session lifecycle. No rotation is tied to a session's end: the master key rotates only by `sidekicks rotate-keys`, and a channel's keys belong to a connection, not a session. The one key a session owns is its content key, which seals both the person's words and the machine's in that session; `Delete old data` deletes it before the session's rows, overwritten with zeros first and with a `TRUNCATE` checkpoint after commit, so what the purge leaves in freed pages cannot be read ([Spec-020 §Ordering And Atomicity](../specs/020-data-retention-and-gdpr.md#ordering-and-atomicity)).

## Example Flows

- **Example 1: Self-host first-run ceremony (deployment trust).** The person runs `git clone && DEPLOY_MODE=lan HOSTNAME=ai-sidekicks.localhost docker compose up`. Compose starts the relay behind Caddy with its Postgres; no daemon runs in the deployment. Sentinel `./data/trust/first-run.complete` is absent, so the relay enters `unprovisioned`. It generates its first-run secrets, the control plane's two token keys, the VAPID key pair and the Postgres password, before Postgres and the relay start; writes them with mode `0600`; emits the first-run banner listing both fingerprint forms; and writes the sentinel. Identity moves to `provisioned`. The person opens a browser, confirms the cert fingerprint matches what the banner printed, and accepts the trust prompt — identity moves to `verified`. The relay starts accepting connections; each machine keeps its own daemon master key on the machine (Example 2), and a machine that connects through this relay becomes `bound` once its `runtimenode.added` statement enters the account's chain.
- **Example 2: A machine's first start and sign-in (machine trust).** Fresh install on a Linux workstation. The service starts for the first time and runs the custody ladder: there is no hardware tier on Linux; the keychain tier checks that `DBUS_SESSION_BUS_ADDRESS` is set, that a live `org.freedesktop.DBus.GetNameOwner("org.freedesktop.secrets")` returns `org.gnome.keyring`, and that a write-probe-read-delete cycle succeeds. The keychain tier is accepted and holds the master key. The service mints its Ed25519 identity key and X25519 channel key and seals both under the master key. The person runs `sidekicks sign-in` with the service stopped (sign-in is refused while the service holds the data folder), approves the code in a browser, and the control plane issues a refresh token bound to the machine's DPoP key, which the CLI seals under the master key. Through the same custody code the CLI reads the machine's public key and enrolls it with the control plane as this machine's key under the person. When the service starts again, it registers the machine (`runtimenode.register`) with its id, that key, its name, platform and version, the control plane accepts the registration because the key is enrolled to that owner, the machine's `runtimenode.added` statement enters the chain, and identity moves `unprovisioned → provisioned → verified → bound`. Later starts find the sealed key; the refuse-on-rotation rule blocks any code path that would silently mint a new one.
- **Example 3: Daemon master key rotation.** The person runs `sidekicks rotate-keys` (`daemon.keyRotate`). The daemon creates a new master key and its key id in locked memory; writes the new key's custody entry, on the keychain tier the entry `master-key.<key id>`, and its recovery envelope and iCloud Keychain item where those are on, reads the entry back and compares it with the key in memory; and records the new key in `master_keys` as `incoming` beside the `active` old key. Inside one `BEGIN EXCLUSIVE` transaction it re-wraps every `session_content_keys` row under the new key — the inner key unchanged, each row's `key_version` raised by one and its `rotated_at` stamped — re-seals every daemon private key, each blob's header naming the new key id, and marks the new key `active` and the old one `outgoing`. It then confirms that no blob names the old key id, marks the old key `retired` and deletes its recovery envelope; its custody entry and row go when the last backup sealed with it ages out, and at once when no backup names it. The same run mints a new identity key, re-enrolled with a `runtimenode.key_rotated` statement signed by the old key and the new one, after which a statement the old key signs is refused while what it signed before stands. Had the machine lost power after the custody write and before the store recorded the new key, the next start would delete the unrecorded entry and keep the old key; had it lost power after the `incoming` row was written, the next start would open the new key's entry and finish the rotation. Nothing else rotates the key: no session end, purge or erasure triggers a rotation, and `Erase all data` destroys the master key instead ([Spec-020 §Daemon Master Key](../specs/020-data-retention-and-gdpr.md#daemon-master-key)).
- **Example 4: No keychain and no hardware on a CI runner.** The service starts on a headless Linux CI runner with no `DBUS_SESSION_BUS_ADDRESS` and no security chip. The hardware and keychain tiers fail; the ladder falls to the passphrase file, and the service waits, locked, until `sidekicks daemon unlock` hands it the passphrase. If no passphrase file can be written either, the service does not start and `sidekicks daemon status` names the failed preconditions and the remedy. No key is minted and identity remains `unprovisioned`.
- **Example 5: Fingerprint mismatch detected at re-display.** The relay restarts after Caddy's certificate was changed by hand, outside the rotation flow. The new cert's whole-cert hash differs from `./data/trust/fingerprint.txt`. The relay emits the rotation-warning banner ([Spec-024 §State And Data Implications](../specs/024-self-host-secure-defaults.md#state-and-data-implications)) marking the deployment identity as `compromised` from the person's perspective. The person either accepts the new fingerprint (back to `verified`) or initiates an investigation; the system does not auto-trust the change.

## Edge Cases

- **Identity state lags device registration.** A device can be mid-link — its link code entered, its key not yet in the chain — and the machine refuses its channel until the `device.linked` statement lands; nothing about the device is trusted before then.
- **Fingerprint rotation without keypair change.** A cert re-issue that preserves the SPKI keypair changes the whole-cert hash but not the SPKI-SHA256 pin. The banner warns about the whole-cert delta but identity remains `bound`; the SPKI pin is what survives.
- **Master key cannot be opened.** Every daemon private key, the DPoP key and the refresh token among them, is sealed under the master key, so a service whose master key does not open holds none of them. It does not mint replacements (§Invariants); it waits locked for its passphrase on the passphrase tier, fails a run's step with `Retry from this step` while the keychain is locked, and otherwise does not start and says why.
- **Daemon restart with token rotation.** The 256-bit daemon session token rotates on every daemon restart per security-architecture.md §Local Daemon Authentication. The desktop app's main process and the CLI read the token file at every connect, so the next connect picks up the new token. Identity material is unaffected — the daemon session token is a transport-layer artifact, not identity material.
- **Sentinel file deleted by the person.** Deleting `./data/trust/first-run.complete` while secrets are still on disk does not silently regenerate. The relay refuses to start with a message naming the sentinel and the secrets it found — preventing accidental loss of the original first-run trust state.

## Pitfalls To Avoid

- **Treating SPKI pin and whole-cert hash as interchangeable.** They are not. See [§Fingerprint Verification Ceremony](#fingerprint-verification-ceremony).
- **Generating an ephemeral identity key when "no key found".** This is the silent-rotation footgun [ADR-021's Refuse-On-Rotation Invariant](../decisions/021-cli-identity-key-storage-custody.md) is designed to prevent.
- **Claiming hardware-rooted protection that the primitives do not provide.** The Secure Enclave and the TPM wrap the master key; the Ed25519 and X25519 keys are sealed under it in software. The Secure Enclave binding is to the Mac, not to the app. The Windows credential the service writes is DPAPI-wrapped, not Credential Guard-protected. The [ADR-021 §Explicitly NOT Claimed](../decisions/021-cli-identity-key-storage-custody.md#explicitly-not-claimed) disclaimers exist precisely so this domain doc does not get cited as evidence of properties that do not hold.
- **Pre-seeding self-host secrets via env vars or `.env.example`.** Spec-024's first-run model rejects this pattern as the dominant cause of placeholder-secret leaks in production self-host deployments.
