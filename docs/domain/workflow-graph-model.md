# Workflow Graph Model

The node kinds and the graph a workflow document is made of, which [Spec-015: Workflow Authoring And Execution](../specs/015-workflow-authoring-and-execution.md) requires.

## Node-Kind Taxonomy

**Every kind the runtime offers is a node, and a run executes nodes as steps.** The kinds that run an agent or ask a person — `agent.run`, `agent.multi-agent`, `human.approval` and `human.form` — are nodes like any other; their executors reimplement nothing and delegate at run time to the existing run, orchestration, approval and form machinery ([Workflow Implementation Notes](../architecture/workflow-implementation-notes.md)). There is no separate phase type and no gate type: an approval is a `human.approval` node with `approved` and `rejected` outputs, a step follows the one before it along an edge, and a run ends when its last steps settle.

What a failure does is the failing node's `onError` — `stop`, `continue` or `continue-error-output` — beside its `retry` bounds, which the engine clamps ([Spec-015 §Loud-errors discipline (C-12)](../specs/015-workflow-authoring-and-execution.md#loud-errors-discipline-c-12)). Step statuses are the list of [Spec-015 §Execution semantics](../specs/015-workflow-authoring-and-execution.md#execution-semantics).

**The V1 node catalog follows, grouped by category.** The name a person reads on a palette row and the one line under it are part of the design and are written here.

**Key shapes.** `flow.if` has two `main` outputs named true and false. `flow.switch` derives its output count from its rules. `flow.loop-items` has outputs named done and loop, in that order, and its body's last node wires back into its input. `flow.merge` has N inputs and one output, with append, combine-by-field, combine-by-position, choose-branch and first-to-arrive modes; `First to arrive` passes on the first input to succeed and cancels the branches still running. `flow.set-vars` carries `Keep for later runs`, off by default: on, the values the step writes are also kept for the workflow when the step succeeds, one entry per name, replacing that name's earlier value, read by later runs through `$vars` ([Spec-015 §Provider-limit pacing and durable resumption (SA-37)](../specs/015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-37)); the node shows, under its params, what is kept now — each name, its value and the run that kept it — with `Clear kept values`. `human.approval` has approved and rejected outputs on the wait mechanism. `agent.run` has one `main` input, one `main` output, an unbounded `tool` input, and params for the definition, the per-node binding, the prompt, an optional output schema and an optional timeout, where the definition is absent for General and the binding holds only the rows the author changed ([Spec-015 §Agent steps (SA-6, SA-8, SA-9)](../specs/015-workflow-authoring-and-execution.md#agent-steps-sa-6-sa-8-sa-9)). `developer.mcp-tool`, `developer.callback-tool` and `developer.code` each expose a `tool` output, so any of them can be wired into an agent node; `developer.callback-tool` has no other handle and one param, the daemon callback tool it exposes, chosen from `callbackTool.list` by the label a person reads there, and the agent it is wired into holds that tool for the step whatever its tool allowlist says. Each agent kind — `agent.run`, `agent.multi-agent` and `agent.ask-question` — also exposes a `tool` output, so one agent calls another as a tool. An agent node wired that way runs only when the agent it is wired into calls it, and the call is peer invocation ([Spec-026 §Peer invocation](../specs/026-agent-definitions-and-peer-invocation.md#peer-invocation)): the call carries the task in the calling agent's words, under the node's own prompt; the called agent runs as a child of the caller in the run's session, shown under it in the agent tree on its own provider account; and the caller gets the called agent's final output back as the tool result, an object fitting the node's output schema where it sets one. A refusal reaches the caller on the tool result's `denied` or `failed` arm, never as an error of the run. A sticky note is a kind with no handles and a resize affordance, added from the canvas controls rather than the palette.

**The Code node's two tiers, and the one boundary a program runs inside.** The quick tier is the default and starts no process: the WebAssembly interpreter of [Workflow Implementation Notes](../architecture/workflow-implementation-notes.md), on a thread of its own, held to a memory budget (256 MiB by default, settable) and the step's `Timeout`, empty by default, for shaping items, with no packages and nothing of the host bound into it. The full tier runs a real child process — JavaScript and TypeScript under `bun`, Python in an environment `uv` builds — and a step names its packages in its own code: JavaScript and TypeScript in the import line, with or without a version (`import { camelCase } from "lodash-es@4.17.21"`), and Python in the script's inline metadata block (`# /// script` … `dependencies = [...]`). Locking and installing happen behind save and run; there is no install screen.

- **Packages are locked when a version is saved.** Every version write — Save, Restore, Duplicate and import — locks each Code node whose code differs from the version it was written from, or that carries no lock; every other node carries its lock forward, so a restored version installs the packages it ran with, and a Duplicate or an import that changes no code needs no network. An export carries each node's lock. For JavaScript and TypeScript the daemon reads the step's import specifiers with bun's own transpiler (`Bun.Transpiler.scanImports`), leaves out relative paths and Node's and bun's built-in modules, writes a `package.json` naming each package at the version its import gives or at `latest`, and runs `bun install --lockfile-only`; two imports that name one package at different versions refuse the save. A save whose packages cannot be locked — a package that does not resolve, or no network — is kept, its node showing `Packages not locked` with the tool's own words, and that version cannot run until a later save locks it. For Python it runs `uv lock --script`; the first save on a machine that locks a Python step also fetches `uv` and installs the Python `uv` manages into the daemon's folder, shared by every step. A bare import locks to the newest release at save, and a script with no `requires-python` locks for the newest Python. The version's row holds the step and its lock, and a lock made on one system installs on another.
- **A run installs from the lock and never resolves again.** At a version's first run on a machine the daemon writes the step, its lock and its `package.json` from the version's row into that version's code folder, `~/.ai-sidekicks/workflows/<workflow-id>/versions/<version>/steps/<step-id>/`, and installs there as a plain process with the network on, outside the sandbox: `bun install --frozen-lockfile`, which puts `node_modules` beside the step, or `uv export --script --locked` into hashed requirements, `uv venv` on the managed Python the lock's `requires-python` allows, and `uv pip sync --require-hashes` into the folder's own `.venv`. Later runs of that version reuse the folder, and their install only checks it. Installs into one folder run one at a time; a second run of the same version waits for the first one's install. Packages come from one cache per tool in the daemon's folder, so a package version is fetched once for every workflow. Install scripts run as bun's default trust list allows them, and a source-only Python package is built here. The install runs with `npm_config_devdir` and `TMPDIR` pointed into the daemon's folder, so the Node headers `node-gyp` fetches for a native build land under the daemon's cache rather than the person's own: bun runs that build even for a package that sets `"gypfile": false` ([oven-sh/bun#43903](https://github.com/oven-sh/bun/issues/43903)), such as `better-sqlite3`. A version's folder, `workflows/<workflow-id>/versions/<version>/`, is removed once a newer version of its workflow is saved and no run of it is live, and a later run of that version rebuilds it from its row; deleting a workflow removes its whole folder, `workflows/<workflow-id>/`.
- **The step runs with the worktree as its working folder**, or, on a run in a chat that names no project, the chat's own folder, or, on a `None` run, the run's own folder ([Spec-015 §Session transcript surfacing](../specs/015-workflow-authoring-and-execution.md#session-transcript-surfacing)). JavaScript and TypeScript run as `bun --config=<the daemon's own empty bunfig.toml> --no-env-file --preload <unpin preload> <code folder>/step.ts`: the daemon names the file `step.ts` or `step.js`, and the preload, shipped with the daemon, rewrites each versioned specifier in an import position (`from`, `import`, `import(`, `require(`) to its bare name before bun resolves it, so the lock supplies the version; any other string is left alone. `--config` and `--no-env-file` keep the worktree's own files out of the step: without them bun runs the preloads a worktree's `bunfig.toml` names and loads its `.env` into `process.env`, which Python never does. A step reads a secret through a sensitive field ([Spec-015 §Secrets — by reference only (C-15)](../specs/015-workflow-authoring-and-execution.md#secrets--by-reference-only-c-15)), never from a file in the worktree. Python runs as `<code folder>/.venv/bin/python <code folder>/step.py` with `PYTHONDONTWRITEBYTECODE=1`, with no `uv` at run. A step's temporary files go to its run's own folder, `~/.ai-sidekicks/workflows/<workflow-id>/runs/<run-id>/<step-id>/tmp/`, which is removed when the step ends, so nothing but the step's own output lands in the worktree. Both folders sit in the daemon's folder and never under `/tmp`, because on Linux Codex's `/tmp` deny hides all of `/tmp`, a grant for one folder included.
- **The database is the one source of truth, and the disk holds only what it rebuilds.** The canvas, the layout, each code step's source and lock, the versions and the runs live in the daemon's database; nothing on disk is an editable copy of a workflow, and Export and Import are its only file forms. What the daemon writes for a workflow sits in one folder named by the workflow's id, which a rename never changes:

  ```
  ~/.ai-sidekicks/
    workflows/
      <workflow-id>/
        versions/<version>/steps/<step-id>/   the step's source, package.json and lock, node_modules/ or .venv/
        runs/<run-id>/                        a `None` run works here; it starts empty and goes with the run's record
        runs/<run-id>/<step-id>/tmp/          the step's scratch files, removed when the step ends
    cache/bun/  cache/uv/                     the shared package caches
  ```

  Everything under `workflows/` is rebuilt from the database and safe to delete: a run whose code folder is gone installs it again from the version's row.

- **The package caches are disposable, and the person bounds them.** A version's code folder lasts until its own removal above; the two caches only speed installs up. Clearing one never breaks an installed folder, because an install copies each file out of the cache (a clone on macOS, a hard link on Linux) and a later run's check reads only the folder. `Cache limit` under `Package cache` on the Runtime settings page reads `Unlimited` by default, and then the daemon never clears a cache on its own; with a size set, after each successful install the daemon reads that tool's cache and clears it when it is larger, never the other tool's. `Clear Bun cache`, `Clear uv cache` and `Clear all caches` clear on request. A clear never touches a code folder or the managed Python, which every installed `.venv` runs on. Installs and a clear of one cache run one at a time: a clear waits for the installs using that cache, and an install waits for a clear. The daemon never clears a cache to make room for an install ([Spec-015 §Fallback Behavior](../specs/015-workflow-authoring-and-execution.md#fallback-behavior)).

**A workflow carries its own permission level.** Each workflow has a level, set on the workflow from the builder's level pill and starting at `YOLO`, and every run of it uses that level wherever the run lives, a chat's session or the workflow's own: every step of the run runs at it, as every agent of a session runs at the session's level, and a change reaches a live run from its next step. The level sits beside the definition outside its hashed body, so a change mints no version (`workflow.permissionLevelUpdate`).

The full tier and `developer.shell` both run at the **run's permission level** ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)), exactly as a command an agent runs does: the asking levels — Read-only, Ask and Reviewed — ask before the step runs, at Reviewed too because no provider's reviewer sees a step the daemon runs; that ask is the daemon's own approval card, so it offers `Always allow <subject> this session`, kept with the run's session's own answers and honored by the daemon itself, and no `Always in this project`; a declined ask fails the step with the receipt `Declined at <time>`, so the run parks on it as on any failed step — `Fix in a fresh session` is offered, `workflow.runResume` runs the step again, which asks again, and nothing after it runs; `sandboxed` runs the step inside the provider's own sandbox — Claude Code's through `@anthropic-ai/sandbox-runtime` linked as a library, Codex's through `codex sandbox` under a named permission profile, run from `@openai/codex`'s native binary — with writes confined to the step's working folder — the worktree, a chat's own folder, or a `None` run's own folder — and the step's own temporary folder; `yolo` runs it with no sandbox. Codex's profile extends `:workspace` with `filesystem."/tmp" = "deny"` and `filesystem."<temporary folder>" = "write"`, and Codex starts with `TMPDIR` set to that folder, because `:workspace` alone leaves `/tmp` and whatever `TMPDIR` Codex starts with writable. Claude Code's sandbox takes `allowWrite: ["<working folder>", "<temporary folder>"]` and `denyWrite: ["/tmp/claude", "/private/tmp/claude", "~/.npm/_logs", "~/.claude/debug"]` and starts with `CLAUDE_CODE_TMPDIR` set to that folder, because it otherwise keeps its own `/tmp/claude` and `~/.npm/_logs` writable. The code folders and the shared caches are read from inside and never written. The network reaches only what the person's own provider settings allow — off on Codex unless their profile enables it, and their own domain allowlist on Claude Code — except that on Linux Codex's run profile carries `network = { enabled = true }`, because with the network off Codex's Linux sandbox refuses bun's writes to a child process's pipes. The engine builds no sandbox of its own, and at `sandboxed` a sandbox that cannot start refuses the step rather than running it unprotected ([Spec-015 §Fallback Behavior](../specs/015-workflow-authoring-and-execution.md#fallback-behavior)).

**The browser kinds run in the session's own managed browser** — the desktop's page host where a desktop is open on the executing machine, otherwise the daemon's headless browser, both driven through one path — Playwright over the Chrome DevTools Protocol, which reaches the desktop's page views through the daemon's relay, with no listening debug port on either host — and sharing the one saved site-data set. A run's page is the same page a person sees in the session's preview surface; nothing browser-shaped is created per step.

## Graph model — nodes, ports, and edges (SA-29)

**Every kind in the catalog is a first-class node.** The document is node-shaped end to end: what the author drew is what is stored, and nothing is compiled into a different shape at save time.

| Node kind | Persisted as | Count | Notes |
| --- | --- | --- | --- |
| Trigger node | the document's own `trigger` slot | exactly one, mandatory | Names how a run of this definition begins (§Entry node and the V1 trigger surface (SA-34)). It never runs as a step: it receives no `stepRunId` and leaves no step record. |
| Every other kind | one entry in the document's `nodes` list | one per node | Carries its kind, the kind version written at insert, its params and its `order`. Among them, the kinds that run an agent or ask a person delegate at run time to the existing run, orchestration, approval and form machinery ([Workflow Implementation Notes](../architecture/workflow-implementation-notes.md)). |

A node's params carry **references** — an agent definition, a provider account, a tool binding identity, a secret reference — and never a nested node, which is why the agent and the paying account are params rather than wired sub-nodes ([Spec-015 §Agent steps (SA-6, SA-8, SA-9)](../specs/015-workflow-authoring-and-execution.md#agent-steps-sa-6-sa-8-sa-9)).

**A handle is `main` or `tool`.** `main` carries items between nodes. `tool` carries a capability: an MCP-tool node, a callback-tool node or another agent wired into an agent node's `tool` input becomes callable by that agent, unbounded in cardinality, through each provider's own mechanism: on Claude Code the wired nodes' servers join the agent's set through `mcp_set_servers` at start and after each resume, the process started with `--strict-mcp-config`, and on Codex each is an `mcp_servers.<id>` entry in the conversation's `thread/start` configuration. A callback-tool node's tool and a wired agent reach it on the daemon's own `sidekicks` tool server, the one that carries the session and workflow tools; a wired agent is called by peer invocation ([Spec-026 §Peer invocation](../specs/026-agent-definitions-and-peer-invocation.md#peer-invocation)), runs only when it is called and never as a step of the main flow, and hands its final output back as the tool result. The kinds with a `tool` output are `developer.mcp-tool`, `developer.callback-tool`, `developer.code` and the three agent kinds. There is no reserved third type: the account that pays, an approval and the repository each already have one home — the account is the `Account` row under the node's agent, an approval is the `human.approval` node, and the repository is the run's recorded folder or the `path` a git node names — and a handle would be a second control setting the same value.

A handle is identified by one string of the form `"<mode>/<type>/<index>"` — `inputs/main/0`, `outputs/main/1`, `inputs/tool/0` — parsed tolerantly: a string whose type is neither `main` nor `tool` parses as `main`, so a document still opens, and is refused at save with the finding `handle_type_unknown`. One handle primitive therefore renders both data ports and capability ports, and a branch index and connection type are recoverable from the stored edge alone.

**Edges are keyed by node id, never by node name.** A name is a mutable label; every edge, every expression index and every step record resolves through the id, so a rename is a metadata edit rather than a graph-wide rewrite. An edge is stored as its own id plus the source node and handle and the target node and handle, in the document's `edges` list, so the stored bytes are the complete executable graph and no edge lives outside them.

**Which sibling runs first is a number, not a position.** Each node carries an explicit integer `order`, defaulted from the order the nodes were added and edited on the node itself, so moving a node on the canvas never changes what the run does. One traversal ships; there is no second execution order.

## Graph shapes that are refused (SA-30)

The builder refuses these at **edit time** — a connection that would produce one cannot be completed, and a document that already contains one cannot be saved:

1. **A self-edge.**
2. **Any cycle** among `main` handles, walking the outgoers from the target. The one exempt shape is an edge whose target is a loop node's own input, because closing a loop body is the loop rather than a cycle.
3. **A handle-type mismatch**: `main` never connects to `tool`.
4. **A second edge into an input handle that accepts one.**
5. **Any edge whose target is the trigger node.**
6. **An edge out of a terminal kind** — a terminal kind ends the run, and an outgoing edge would assert a successor the engine will never reach.
7. **A `tool` edge into a node that has no `tool` input.**
8. **An orphan node** — one reached neither by `main` edges from the trigger nor by its `tool` edge into a reached node — and **a document with no nodes**, or with no trigger or more than one.
9. **An edge naming a node the document does not hold.**
10. **A node id used twice**, the trigger's included; a document carrying one cannot be read, so it is refused before the other rules are checked.

A refusal during a drag is shown as a red connection line plus a one-line reason in the validation strip — never a toast, and never an edge that is created and then removed.

**Edit-time validation mirrors the daemon check; it never replaces it.** Every rule above is re-evaluated server-side at `workflow.definitionCreate`, and the daemon's answer is authoritative. A client that skips, weakens, or predates a rule produces a **refusal**, not a persisted definition — the fail-closed direction. Refusals surface as `workflow.definition_refused` with its finding list ([Spec-015 §Fallback Behavior](../specs/015-workflow-authoring-and-execution.md#fallback-behavior)), registered in [error-contracts.md](../architecture/contracts/error-contracts.md) §Workflow; the builder mints no error surface of its own ([Spec-015 §Loud-errors discipline (C-12)](../specs/015-workflow-authoring-and-execution.md#loud-errors-discipline-c-12)).

## Tool bindings are references, never inline policy (SA-31)

A node may bind tools. The binding a definition persists is a **reference only**: the scope-qualified binding identity plus a tool name, resolved at step launch through the [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md) §Tool Metadata layer that [Spec-024](../specs/024-mcp-server-configuration-and-governance.md) §Tool-Level Overrides feeds.

A workflow definition **MUST NOT** carry any governance facet inline. Specifically, a tool binding in a definition carries no `enabled`, no `approvalMode`, and no `idempotencyClass` value: a tool's approval lives only in Settings › MCP servers, where those three facets are set through the Spec-024 override operations, independent per binding scope, and a workflow file that sets one of them on a node is refused as an ordinary parse error naming the field. The builder's inspector therefore **displays** the effective facets read-only, sourced live from the governance surface, and offers no control that writes them.

Whether a binding is switched on is likewise not a definition concern: a switched-off binding refuses at launch under the Spec-024 rules, and the builder shows that state rather than overriding it.

## Canvas layout is not definition bytes (SA-32)

The **canonical definition** is the JCS-canonicalized JSON body the BLAKE3 content hash already covers. Canvas geometry — each node's coordinates, the viewport's pan and zoom, the sticky notes, and any other purely visual attribute — is **excluded from that body** and from the hash preimage, and so is a node's pinned data. Dragging a node or pinning an output changes no byte of the definition, mints no content hash and creates no version. This exclusion is **hash-scope only, never semantics-scope**: nothing that affects execution may be moved into the layout channel to escape hashing, and every field the engine reads stays inside the hashed body.

Layout is nonetheless **persisted and portable**, because it is part of the document rather than a client's private note. It lives in the document's own `layout` section and is stored in a column beside the definition body, and the file form of §Definition file form — export and import (C-17) carries it as an optional top-level section outside the hashed body. A workflow an agent authored or a user exported therefore carries its picture with it instead of arriving as an arrangement a machine invented.

Where a document does arrive with no layout — written through the SDK, the CLI or an agent — it is laid out **deterministically, left to right**, by the same layered layout library in the daemon and in the renderer, so a definition is never unopenable, opens the same way twice, and looks the same wherever it is opened ([Workflow Implementation Notes](../architecture/workflow-implementation-notes.md)).

## One workflow library (SA-33)

The machine holds **one workflow library**. Every workflow in it is visible and runnable from every chat, every project session and the Workflows tab; nothing ties a workflow to a session, a chat or a project, so the builder and the Workflows tab show no scope group, no scope control and no scope chip.

- **Loading** lists every workflow in the library as one list, and a name names one workflow.
- **Saving** creates a new immutable version of the workflow open in the builder.
- **A name is used once, ignoring case.** A save, an import or an agent's create whose name another workflow holds, in any letter case, is refused with `workflow.definition_refused`, finding `name_taken`; Duplicate picks the first free name of `<name> copy`, `<name> copy 2`, `<name> copy 3` and on.
- **The repository is the run's, not the workflow's.** A run started in a session works in that session's recorded folder; a run nobody started from a session works in the repository its Run now panel or its trigger's `Repository` names, or in none ([Spec-015 §Session transcript surfacing](../specs/015-workflow-authoring-and-execution.md#session-transcript-surfacing)).

## Entry node and the V1 trigger surface (SA-34)

Every definition has exactly one entry node — its trigger — and that node records **how a run begins**. V1 ships eight kinds, and every arm is honored at ship time; none is declared and left unwired.

| Kind | How a run begins |
| --- | --- |
| `trigger.manual` | Run now in the builder or on a workflow's row, the chat run verb, or an agent's own run tool. |
| `trigger.schedule` | Cron or every-N, in the trigger's own timezone, with a missed-fire policy of skip or catch-up-once. |
| `trigger.file-watch` | A path, a set of globs and the event kinds to honor, debounced 250 ms. |
| `trigger.webhook` | The daemon's loopback listener, with a per-workflow bearer token and a response mode of immediate or on-finish. |
| `trigger.session-event` | An event-type filter over the session log — a run finished, an approval resolved, an artifact published. |
| `trigger.chat` | A message in a session ([Spec-015 §Chat-start surface (SA-35)](../specs/015-workflow-authoring-and-execution.md#chat-start-surface-sa-35)). |
| `trigger.sub-workflow` | The entry point an Execute workflow node calls, taking the parent's items in and handing the child's terminal items back, the child's run carrying its parent's id. |
| `trigger.error` | Any other workflow failing, receiving that run's id, its error and its last node. |

**A workflow is either enabled or not.** Enabling arms every trigger it declares; disabling disarms all of them, and the workflow stays that way until someone changes it back. A workflow with no trigger that can arm cannot be enabled, and the toggle says so rather than silently accepting. The enabled toggle on a workflow's row acts immediately and reverts visibly where the daemon refuses it.

**Arming is durable; the timer is only a cache.** Each armed trigger holds its own row — kind, config hash, next fire, last fire, whether it is enabled — and the in-process timer is a cache over that row. On daemon start, after the projection rebuild completes, every enabled workflow re-arms from its rows. A fired occurrence carries a dedup key of the workflow, the node and the scheduled instant, so neither a restart nor a double-arm can fire twice. Trigger cursor state lives in the daemon's per-(workflow, node) key-value store and never on the document, so the document stays hashable and safe to edit.

**Two policies decide what a fire does, and they answer different questions.**

- The **missed-fire** policy is per schedule and covers a fire that arrived while the daemon was down: skip the occurrence, or catch up exactly once. The run's trigger record says which happened.
- The **overlap** policy covers a fire arriving while a run of the same workflow is still going. It is one control on the trigger that fires — the schedule node's and the webhook node's alike, because every workflow has exactly one trigger — named **While a run is going**, with three values: **Skip**, the default, where no run is created and the workflow's row and that trigger's own panel show the skipped time and the run that was still going (`3:00 AM skipped · the 2:00 AM run was still going`), so a skip is visible without widening the run status list; **Wait, then run once**, where the next run starts when the current one finishes and several fires that arrived meanwhile collapse into one; and **Run alongside**, where a second run starts regardless. A start a person or an agent asked for always starts, because someone asked. File-watch is already debounced, and a loop's sub-workflow calls are sequential by the loop.

**Runs that start runs form a chain, and the person decides how far one goes.** A run started by a person, a schedule, a webhook, a chat message or a file event nobody's step made begins a chain of its own. A run started by an `Execute workflow` node, by an error trigger, by a session-event trigger on an event another run emitted, or by a file-watch trigger on a path a run's step wrote joins the chain of the run that started it, and carries that chain's first run: `workflow.runRead` returns it as `chainRoot {runId, definitionId, workflowName, startedAt, runCount}`, where `runCount` is how many runs the chain has started from its first run, the first run included. An agent that starts a workflow through its run tool starts a chain of its own, as a chat start does. A run that belongs to a chain an error trigger joined never fires an error trigger when it fails: its failure reaches the person as the `Failed` banner, so no two error workflows can fire each other.

- The engine counts the runs each chain has started, the first run included. When a chain has started as many as `Ask me after one start leads to` allows — one select on the Runtime settings page beside `Stop a run after`, of 25, 100, 500 or 2,000 runs or `Never ask`, on at 100 by default, kept as `workflowChainAskAfterRuns` on `daemon.configRead` and `daemon.configUpdate` (a number, or `null` for `Never ask`) — the next start in it waits for the person instead of starting. The engine raises one approval for the whole chain, on the chain's first run and in that run's session, and every start the chain makes meanwhile waits behind that one question. An `Execute workflow` step whose child is held reads `waiting` with cause `chain`; a held session-event fire creates no run until the answer.
- The question reads `Summarize folder has started 100 runs from its 2:00 AM start. Keep going?`, naming the workflow of the chain's first run, the count and the first run's start in the machine's own clock, with `Keep going` and `Stop them all`. It stands on the first run's page and as that session's question card, and the first answer through either settles both; a held `Execute workflow` step's live line reads `waiting on you · 100 runs from one start`. Once answered it becomes a one-line receipt with no way back, `Kept going at 100 runs` or `Stopped at 100 runs`. The first run's `workflow.runRead` carries it as `chainQuestion` — `{ state: "open" }` while it is open, and `{ state: "answered"; decision: "approved" | "rejected"; runCount; answeredAt }` once answered, which the receipt reads — and the count the question and the live line read is `chainRoot.runCount`. `Keep going` starts everything held and does not ask again for that chain; `Stop them all` cancels every run of the chain still going, the first run included, each reading `canceled`. The question rides `workflow.gateResolve` — `approved` for `Keep going`, `rejected` for `Stop them all` — so it is recorded in `workflow_gate_resolutions` like any approval, counted by the bell, bannered as `Waiting on you`, and holds no reservation while it waits. `Never ask` never raises it; the count is still kept.
- Nothing refuses a chain: there is no depth cap and no save-time refusal of a workflow that reaches itself, so a recursive walk finishes, and the number at which the person is asked is the person's.
- A file-watch fire joins a chain when a path in it was written by a step of a run in that chain. The daemon knows those paths from its own records: a `Write files` step's writes, which the daemon makes itself; a capture of the step's checkout before and after every step whose writes come from a process the daemon starts or calls — `Run a command`, a full-tier Code program, `Git`, `Run tests` and an `MCP tool` call — taken directly, with no handshake, into the capture folder ([Spec-015 §Interfaces And Contracts](../specs/015-workflow-authoring-and-execution.md#interfaces-and-contracts)); and an agent step's own edits and commands, which the per-edit checkpoint and the command wrapper on Claude Code or the relay on Codex already capture. A write outside the step's checkout, which only the YOLO level or an approved ask allows, is outside every capture; for it, a file-watch event on a path outside the checkout that arrives while a step's process or command is running, or within 1 s of its after-capture, counts as that step's, which can only bring the chain's question sooner. A fire whose paths fall in a checkout whose after-capture is still running waits for it, and each step's written paths are kept in memory until 1 s after its after-capture, then dropped. A fire with paths from more than one chain joins the chain that has started the most runs. A before-capture adds about 105 ms median to the start of such a step on a 5,000-file checkout and 276 ms on 50,000; the after-capture costs about 1 ms per changed file, off the run's path.

Editing a schedule writes a new version and re-arms the trigger only after a successful save. A workflow's own row and the builder's toolbar both read the schedule as off or as the next fire, written in the trigger's timezone and in the machine's own clock.

**One webhook address per workflow, on one port for the machine.** The daemon's loopback listener binds a single configured port — the default one constant chosen from a range no common developer tool uses — and the console's settings hold the one control that changes it. A workflow's address is therefore `http://127.0.0.1:<port>/hooks/<the workflow's id>` and changes only when the user changes the port. The path is the workflow's own id, so two workflows can never share one and the author never types one; the trigger has no `Path` field. The webhook trigger's own panel shows the full address under an **Address** heading with `Copy the address` beside it, and under both the line "One port for every workflow, set in Settings. The address changes only when you change the port." Where the port is already held at daemon start the listener does not start and nothing moves: settings show the port and that it is in use, and every webhook trigger shows the same reason in place of its address — "Port 7391 is in use, so the listener did not start and this workflow has no address. Change the port in Settings and the address comes back unchanged." — with no address and no copy control while that stands. No ephemeral port, and no silent move to the next free one. On a Windows computer whose daemon runs in a WSL 2 distribution, the listener binds the distribution's loopback, where Windows reaches it only through WSL, so "held" also covers the port on the Windows side: in WSL's default networking, a Windows loopback listener on that port that is not WSL's own relay, or no listener at all because Windows reserves the port; in mirrored networking, the distribution's own bind failing because a Windows program holds it. When the check says held, the daemon closes the listener it opened in the distribution, so nothing listens and the same line stands. `workflow.webhookListenerRead` reads the port and whether it is listening or taken.

**The token sits under `Address` too.** With no token the section reads `Create token`, and every call to the address is refused until a token exists. A token just created or rotated is shown once, with `Copy token`, and is never shown again: only its hash is kept. After that the token reads `Created <date>` — `Created today` on the day it was made — with `Last used <time>` once it has been used, and `Rotate token`, which confirms in place with `The old token stops working at once.` under `Cancel` and `Rotate token`; confirming makes the old token invalid at that moment and shows the new one once (`workflow.webhookTokenRotate`). A local program fires the webhook with `POST` to the address and `Authorization: Bearer <token>`; the daemon hashes the presented token and compares that hash with the kept one in constant time (`crypto.timingSafeEqual`), and a call with the wrong token, or any call while no token exists, is refused with `workflow.webhook_token_mismatch`.

**Every trigger but `trigger.chat` and `trigger.sub-workflow` carries one `Repository` param**: a list of the person's projects plus `None`, starting at `None`. It names the repository a run the trigger starts works in when nobody started it from a session, and the Run now panel opens on it; a `chat` start works in its session's recorded folder, or in the folder of the project it names ([Spec-015 §Session transcript surfacing](../specs/015-workflow-authoring-and-execution.md#session-transcript-surfacing)), and a `sub-workflow` child in its parent's.

**Run now opens one panel before anything starts.** Its first field is `Repository`, seeded from the trigger's: the repository this run works in, or `None` for a workflow that touches no code; a workflow holding a Git, Read a repo diff or Run tests step refuses `None` in place, naming those steps, and does not start. Beside it stand the inputs the workflow declares on its trigger, each one named, typed, and carrying the value it starts on: one labeled field per input, drawn from its type — a checkbox for a yes or no, a list for a choice, a folder picker for a path, a box otherwise — seeded from those values, with the ones that may be left alone marked `(optional)`. Run starts the latest saved version in the repository chosen with what was filled in, and a required field left empty says so in place while the panel stays open: it reads `<name> is needed before this can run.`, naming the field because the line sits away from it, while a form step's line sits under its own field and reads `Fill in this field.`. Run this node and Run from here work in the trigger's repository and ask only for declared inputs; on a `trigger.chat` or `trigger.sub-workflow` trigger, which carries no `Repository`, they open this same panel first, its `Repository` starting at `None`, and a workflow holding a Git, Read a repo diff or Run tests step refuses `None` there, naming those steps. Typed in a chat, `/workflow run <name>` opens this same panel for a workflow holding such a step, listing the person's projects, and the run works in the project chosen.

**Three daemon dependencies carry this surface** and are recorded with the rest in [Workflow Implementation Notes](../architecture/workflow-implementation-notes.md): `croner` computes a schedule's next fire in its timezone; the file-watch trigger uses Node's own recursive `fs.watch` on the pinned Node 24 line, debounced 250 ms, with `picomatch` filtering the globs; and `@dagrejs/dagre` lays out a document that arrives with no layout section — an agent's, the CLI's or the SDK's — in the daemon as in the renderer. The durable next-fire row remains the truth; none of the three holds state that outlives the process.

## Definition file form — export and import (C-17)

A workflow definition has one canonical file form, and it is the file the authoring commitment already names, carrying the schema-version marker the versioning commitment already requires. **No second schema dialect exists**: the file is the definition, and its canonical bytes are the JCS-canonicalized JSON of the parsed document — which is precisely the existing hash preimage, so a definition's content hash is identical whether it arrived through the builder, the SDK, or a file.

The document has exactly two top-level parts:

1. The **definition body** — the hashed, canonical part. Everything the engine reads.
2. An **optional `layout` section** — the canvas geometry, outside the hashed body. An importer that does not understand it, or a consumer that does not want it, ignores it and loses nothing executable. A file written through the CLI or the SDK omits it entirely, and the document it produces is laid out deterministically when it is opened (§Canvas layout is not definition bytes (SA-32)).

Export serializes the current version to that one form, body plus the optional layout section, and writes it to the file the platform's own save chooser picked (`native.showSaveDialog`). Import reads the file the platform's own open chooser picked (`native.showOpenDialog`) and submits the parsed body through the ordinary create path with the ordinary validation, all or nothing, so an imported definition is subject to every refusal rule above and to the ordinary tool-governance resolution — an import can never carry governance state with it, and an import whose schema version is unknown refuses with its registered code rather than being read optimistically. Round-tripping holds in both directions: builder → file → CLI → daemon and CLI → file → builder produce the same definition body bytes and therefore the same content hash.
