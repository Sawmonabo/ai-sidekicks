# GDPR Manual Erasure Runbook

## Purpose

Service a verified GDPR Article 17 ("right to erasure") data-subject request **by hand** in V1. The automated `DELETE /users/{id}/data` endpoint is deferred to V1.1 — the V1 `gdpr.*` daemon methods are not-implemented stubs per [Plan-022 §API And Transport Changes](../plans/022-data-retention-and-gdpr.md#api-and-transport-changes) and [Spec-022 §V1 Erasure Scope Boundary](../specs/022-data-retention-and-gdpr.md#v1-erasure-scope-boundary) — but V1 ships the full erasure _capability_: the schema, the crypto-shred write-path, and the `ON DELETE SET NULL` FK severance. This runbook is the operator procedure that drives that capability to a compliant erasure without reading the spec internals. (Data _export_ — the separate GDPR Art. 20 portability prerequisite — is V1.1, **not** part of the V1 erasure capability; its cross-session assembly facility is deferred to the automated handler, so the Preconditions below treat a pending export request as a _hold_ condition, not a step this procedure performs. See [Spec-022 §V1 Erasure Scope Boundary](../specs/022-data-retention-and-gdpr.md#v1-erasure-scope-boundary).)

It renders [Spec-022 §Shred Fan-Out](../specs/022-data-retention-and-gdpr.md#shred-fan-out) as an ordered, idempotent operator sequence. The V1.1 automated handler will execute the **same** three paths in the **same** order ([Plan-022 §Implementation Steps step 11](../plans/022-data-retention-and-gdpr.md#implementation-steps)).

## Symptoms

Run this procedure when **all** of the following hold:

- A data subject (or an admin acting on their behalf) has submitted a verified erasure request for a known `user_id`.
- The automated path is unavailable: a call to the daemon `gdpr.userDelete` method returns JSON-RPC `-32603` with `data.type = "gdpr.endpoint_not_v1"` (the V1 stub — the method is registered but returns not-implemented in V1, per the [GDPR Method-Name Registry](../architecture/contracts/api-payload-contracts.md#gdpr-method-name-registry-tier-5)). An unregistered name (e.g. `gdpr.delete`) would instead return `-32601` (method not found), which is _not_ this condition.
- The request is not blocked by a legal-hold or security carve-out (token-revocation denylist survival is expected and compliant — see Preconditions — not a block).

## Detection

Establish **scope** before mutating anything — separate identification from remediation:

1. **Resolve the `user_id`.** Confirm the UUID against the control-plane `users` row: `SELECT id, display_name, identity_ref FROM users WHERE id = :pid;`.
2. **Enumerate the blast radius** against [Spec-022 §PII Data Map](../specs/022-data-retention-and-gdpr.md#pii-data-map) — the authoritative list of every PII-carrying path. The erasure touches **two durability domains**:
   - **Daemon-local SQLite** (Paths 1 + 3): `user_keys`, `artifact_encryption_keys` (Tier 7 — Plan-014; absent before it lands), `session_events.pii_payload`, `interventions.pii_payload` (the Spec-004 replacement-send at-rest copy — same DEK, added 2026-08-17), and the four diagnostic buckets (`driver_raw_events`, `command_output`, `tool_traces`, `reasoning_detail`).
   - **Control-plane Postgres** (Path 2): the full `REFERENCES users(id)` inbound-FK closure — verifiable against [shared-postgres-schema.md](../architecture/schemas/shared-postgres-schema.md), so the set is the source of truth and cannot drift behind a hand-maintained list — plus the identity-keyed Plan-021 rate-limit tables, which carry TEXT identities instead of FKs and ride the [Spec-022 §Shred Fan-Out](../specs/022-data-retention-and-gdpr.md#shred-fan-out) disposition list explicitly (`rate_limit_escalations` hard-DELETE; `admin_bans` retained — see Path 2). **Deployment scope:** the closure spans dependency tiers, so a given deployment may not yet contain every table — `cross_node_dispatch_coordination` lands in Tier 9 (Plan-027) and `revoked_jtis` / `revoked_token_families` at the post-V1 BL-070 build. Before each Path-2 statement, guard existence (`SELECT to_regclass('<table>') IS NOT NULL;`) and **skip absent tables**: a table that does not exist holds no rows to erase, so skipping it is correct, not a closure gap. The `DELETE FROM users` cascade likewise fires `ON DELETE SET NULL` only on the FKs that exist.
3. **Confirm no in-flight runs** for the user — a live run may re-author `pii_payload` after the shred. Quiesce the user's sessions or wait for completion.

## Preconditions

- **Export before erasure — hold if a portability request is pending (V1 scope below).** Crypto-shred is irreversible, so a pending data-export / portability request (GDPR Art. 20) MUST be satisfied — or its deferral explicitly decided by the controller — before any key deletion. **What V1 lacks is not decryption:** the daemon decrypts `pii_payload` routinely whenever the user's content key is unlocked in an authenticated session. It is the cross-session **export-assembly** facility — `GET /users/{id}/export`, which gathers every event authored by or mentioning the user into one decrypted JSON archive — that is deferred to V1.1 ([Spec-022 §V1 Erasure Scope Boundary](../specs/022-data-retention-and-gdpr.md#v1-erasure-scope-boundary)). The `user.exported` event is emitted by **that V1.1 handler** ([Spec-006 §User Lifecycle](../specs/006-session-event-taxonomy-and-audit-log.md#user-lifecycle-user_lifecycle)); this manual procedure does **not** synthesize it, and `user.exported` is therefore **not** a precondition gate the operator can satisfy by hand in V1. Before proceeding, confirm one of: **(a)** no export / portability request is pending for this user; **(b)** a pending request was already satisfied through whatever out-of-band means the deployment used (V1 ships no cross-session export-assembly command, so any V1 export is necessarily bespoke); or **(c)** the controller has explicitly decided to erase now and defer portability until the V1.1 export handler ships.
- **Durable request marker.** Emit `user.purge_requested` through the daemon's canonical append path so the operation has a durable anchor; if any path below fails, this remains the most-recent state and the request stays retryable ([Spec-022 §Shred Fan-Out](../specs/022-data-retention-and-gdpr.md#shred-fan-out)).
- **Access to both stores.** Operator credentials for the daemon-local SQLite store **and** the control-plane Postgres database. On hosted SaaS these are different systems; on self-host they may share a host.
- **Shared-terminal write lease cleared daemon-side first (where the Plan-024 lease table exists, post-Phase-3B).** The terminal-owning daemon is the sole lease authority and the lease record never changes without its `pty.control_changed` broadcast ([Spec-006 census row](../specs/006-session-event-taxonomy-and-audit-log.md#pty-control-session_lifecycle)), so Path 2's `ON DELETE SET NULL` must never be the primary lease transition: before Path 2, end the user's active sessions through the normal flow — the authorization-loss force-clear frees any lease they hold at the terminal-owning daemon and publishes the transition (`reason: 'auto_released_authorization_lost'`, [Spec-003 §Required Behavior](../specs/003-runtime-node-attach.md#required-behavior)). Verify before the DELETE: `SELECT count(*) FROM session_terminal_leases WHERE holder_user_id = :pid;` returns `0`. The check cannot go stale — a user whose authorization has ended cannot re-take (authorization precedes lease state) — and the FK's `SET NULL` remains a DB-side idempotent backstop that lands on an already-`NULL` holder in the documented flow (an out-of-flow direct DELETE still converges to the same fail-closed lease-free state, but bypasses the broadcast — which is why this precondition exists).
- **Daemon append access.** The signed audit events (`event.shredded`, `user.purge_requested`, `user.purged`) MUST be written through the daemon's canonical append path (Ed25519-signed + BLAKE3 hash-chained per [Spec-006 §Integrity Protocol](../specs/006-session-event-taxonomy-and-audit-log.md#integrity-protocol)) — **never** a raw `INSERT` into `session_events`, which breaks the chain and fails verification.
- **Understand denylist survival.** Where `revoked_jtis` / `revoked_token_families` exist (post-BL-070 — they are absent in a V1-only deployment), their rows survive erasure by design — `user_id` is auto-nulled, but the denylist key persists until its natural `expires_at + 24h` reap (the GDPR Art. 17(3) security carve-out). This is **not** a precondition failure.

## Recovery Steps

Execute the three paths **strictly in order** — `Path 1 → Path 2 → Path 3` — then emit the audit events (`event.shredded`, then the aggregate `user.purged`). The ordering is load-bearing: each path closes a re-derivation window the next would otherwise leave open, and `event.shredded` is emitted only **after Path 3** so the audit marker never precedes diagnostic-PII clearance ([Spec-022 §Shred Fan-Out](../specs/022-data-retention-and-gdpr.md#shred-fan-out), Path 3 ordering). No ACID transaction spans the three paths (SQLite and Postgres are distinct durability domains); each path is individually idempotent, so a failed run is safely re-executed from the top.

### Path 1 — Crypto-shred the SQLite event log (daemon-local)

1. Delete the per-user key: `DELETE FROM user_keys WHERE user_id = :pid;` (daemon-local SQLite). This destroys the AES-256-GCM key; every `pii_payload` ciphertext the user authored, across every session — `session_events` and `interventions` rows alike (the Spec-004 replacement-send copy shares the DEK) — becomes permanently unrecoverable. (`user_keys` is a separate table from the signed event chain, so this DELETE does not affect hash-chain integrity.)

2. Delete the durable artifact-encryption key: `DELETE FROM artifact_encryption_keys WHERE user_id = :pid;` (daemon-local SQLite, **on every node the user runs** — the store is per-daemon). This destroys the X25519 private half that unwraps relay-held CEKs, completing the crypto-shred whose Postgres half is the Path-2 `artifact_relay_recipients` DELETE ([Spec-014 §Cross-Node Artifact Relay (V1)](../specs/014-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1) Delete step 9). Skip if absent — the table lands with Plan-014 Tasks 7–10 (Tier 7); a user who never published or received a shared artifact has no row.

The `event.shredded` audit artifact **records this Path-1 crypto-shred**, but it is **emitted later — after Path 3** — so the "shredded" marker never precedes the diagnostic-bucket flush (the Path 3 buckets hold _plaintext_ PII until flushed). Emit it under [§Emit the audit events](#emit-the-audit-events) below, **not here** ([Spec-022 §Shred Fan-Out](../specs/022-data-retention-and-gdpr.md#shred-fan-out), Path 3 ordering).

_Idempotency:_ a re-run where the key row is already gone affects zero rows.

### Path 2 — Hard-delete + sever Postgres rows (control plane)

Run as a **single Postgres transaction** (one durability domain — the whole path succeeds or is reported failed; the daemon does not partially advance):

1. Hard-DELETE the user's rows from the no-retention-basis tables present in your deployment. The predicate differs by table shape:
   - **Plain `user_id` tables** — `identity_mappings`, `user_identity_keys` (Plan-018 T5.1, Tier 5 — skip if absent per the Detection deployment-scope note; person-bound workstation identity keys, safe to delete at live-verification semantics), `webauthn_credentials` and `webauthn_challenges` (Plan-018 T6.1, Tier 5 — skip if absent per the same note; enrolled WebAuthn credentials and in-flight ceremony challenges, likewise safe at live-verification semantics), `notification_preferences`, `notification_queue`, `runtime_node_attachments`: `DELETE FROM <table> WHERE user_id = :pid;`. The durable node-attach audit trail is the crypto-shredded `runtime_node.*` event stream, not `runtime_node_attachments`. `notification_queue` (Plan-019) holds queued-but-undelivered notifications; each row carries a derived `summary` render string, so the row is hard-DELETEd rather than FK-severed — an `ON DELETE SET NULL` would leave the personal content behind ([Shared Postgres Schema §Notification Queue (Plan-019)](../architecture/schemas/shared-postgres-schema.md#notification-queue-plan-019), CP-019-1 ⇄ CP-022-6). Skip if absent per the Detection deployment-scope note — it is Tier 8 (Plan-019).
   - **`artifact_relay_recipients` (Plan-014, Tier 7 — cross-node artifact relay per the [ADR-015 amendment 2026-07-08](../decisions/015-v1-feature-scope-definition.md#amendment-2026-07-08-v11-deferred-features-3--2-cross-node-shared-artifacts-pulled-into-v1)).** Composite PK `(ciphertext_digest, user_id, node_id)`; use `DELETE FROM artifact_relay_recipients WHERE user_id = :pid;` — the user-keyed predicate sweeps **all of their node rows** in one statement. Dropping the rows **is** the relay-side crypto-shred: each row holds a wrapped CEK for one of the user's nodes, so deletion removes both their decryption material and their place in every blob's intended-recipient set ([Spec-022 §Shred Fan-Out](../specs/022-data-retention-and-gdpr.md#shred-fan-out) hard-DELETE class). Expected side effect: a blob whose remaining recipients have all fetched becomes refcount-zero and is deleted by the relay's next GC sweep — no operator action needed. Skip if absent per the Detection deployment-scope note — it is Tier 7 (Plan-014).
   - **`cross_node_dispatch_coordination`** has **no `user_id` column** — it references the user twice, as `caller_user_id` **and** `target_user_id` ([Shared Postgres Schema §Cross-Node Dispatch Coordination](../architecture/schemas/shared-postgres-schema.md#cross-node-dispatch-coordination-plan-027), the table's two `REFERENCES users(id)` columns), each `NOT NULL REFERENCES users(id)` with the default `NO ACTION`. Use a two-column predicate: `DELETE FROM cross_node_dispatch_coordination WHERE caller_user_id = :pid OR target_user_id = :pid;`. The generic `WHERE user_id = :pid` would error on the missing column and leave these rows behind — and because both FKs are `NOT NULL` with the default `NO ACTION`, any survivor makes the `DELETE FROM users` statement in step 2 fail outright. Skip if absent per the Detection deployment-scope note — it is Tier 9 (Plan-027).
   - **`rate_limit_escalations` (Plan-021, Tier 6)** is keyed by TEXT identity, **not** a `user_id` FK — it sits outside the FK closure and needs an explicit identity-keyed selector: `DELETE FROM rate_limit_escalations WHERE identity = :pid AND identity_type = 'user';` (ephemeral ≤ 1-hour escalation state; [Spec-022 §Shred Fan-Out](../specs/022-data-retention-and-gdpr.md#shred-fan-out) hard-DELETE class, Plan-021 D-021-13). Skip if absent per the Detection deployment-scope note. Self-host only — hosted escalation state lives in Durable Objects, outside Postgres; that DO state is self-evicting (every field horizon-bounded ≤1 hr; the single-alarm sweep `deleteAll`s the instance once expired — [Plan-021 D-021-13](../plans/021-rate-limiting-policy.md)), so hosted erasure needs no DO step and there is no queryable surface to verify (eviction is pinned by Plan-021's T21.2-4 test).
   - **`admin_bans` (Plan-021, Tier 6) is deliberately NOT deleted or anonymized.** Rows are retained under the GDPR Art. 17(3) abuse-prevention legitimate-interest carve-out — including rows whose `identity_type = 'user'` identity matches the erased user and rows naming the erased user in `issued_by`/`revoked_by` (TEXT columns, no FK, so the step-2 user hard-DELETE does not touch them). Erasure must not un-ban an identity; operator attribution must survive ([Spec-022 §Shred Fan-Out](../specs/022-data-retention-and-gdpr.md#shred-fan-out) retain class). Revoked/expired rows become purgeable 90 days after revocation/expiry via normal operations, not via this runbook.
2. Hard-DELETE the user anchor: `DELETE FROM users WHERE id = :pid;`. This triggers the `ON DELETE SET NULL` severance DB-side on every anonymize-class FK that exists — `revoked_jtis.user_id` / `revoked_token_families.user_id` once BL-070 has shipped (born `ON DELETE SET NULL`), plus `artifact_relay_blobs.publisher_user_id` once Plan-014's cross-node relay tables have shipped at Tier 7 (likewise born `ON DELETE SET NULL` — the published blob survives to refcount-zero delete, watermark eviction, or its TTL sweep plus `relay_tombstone_grace`; only the publisher linkage severs), plus `session_terminal_leases.holder_user_id` once Plan-024 Phase 3B has shipped the lease table (likewise born `ON DELETE SET NULL` — a DB-side idempotent backstop that lands on an already-`NULL` holder when the lease-clear Precondition above was honored; auto-nulling converges on the same fail-closed lease-free state while the per-session row survives) ([Spec-022 §Shred Fan-Out FK-safety](../specs/022-data-retention-and-gdpr.md#shred-fan-out); Plan-022 D-022-7).
3. If any statement fails (FK constraint, row lock, connection loss), roll back the transaction and report Path 2 failed — do not advance. An FK-constraint violation on the `users` DELETE has three possible causes: **(a)** step 1's `cross_node_dispatch_coordination` delete was skipped or left a row, whose `caller_user_id` / `target_user_id` FKs are `NOT NULL NO ACTION`; or **(b)** a Plan-014 `artifact_relay_recipients` row survived step 1 — its `user_id` FK is likewise `NOT NULL NO ACTION`, so the hard-DELETE-class delete must precede the anchor delete; or **(c)** a Plan-018 `user_identity_keys` or `webauthn_credentials` row survived step 1 — each `user_id` FK is likewise `NOT NULL NO ACTION` (added 2026-08-15, Plan-018 T5.1; 2026-09-01, Plan-018 T6.1). Note that `webauthn_challenges.user_id` is NULLABLE and so cannot block the parent delete, but its rows are still deleted in step 1. Re-run step 1 against all three table shapes, then retry from Path 1.

_Idempotency:_ a DELETE of an already-deleted row affects zero rows.

### Path 3 — Flush diagnostic buckets (daemon-local)

1. For each bounded-retention diagnostic table — `driver_raw_events`, `command_output`, `tool_traces`, `reasoning_detail` — issue `DELETE FROM <table> WHERE user_id = :pid;` (daemon-local SQLite). This short-circuits the ≤ 7-day TTL sweep. Summary-only variants (e.g. `reasoning_summary`) are non-PII by construction and are not a shred path ([Spec-020 §Required Behavior](../specs/020-observability-and-failure-recovery.md#required-behavior)).
2. Record `diagnostic_rows_purged` counts per table.

_Idempotency:_ flushing already-empty buckets affects zero rows.

### Emit the audit events

After **all three** paths complete, emit the two signed audit events through the daemon's canonical append path, **in this order**:

1. **`event.shredded`** — `{userId, affectedSessionIds[], piiPayloadsCleared, shredReason}` ([Spec-006 §Event Maintenance](../specs/006-session-event-taxonomy-and-audit-log.md#event-maintenance-event_maintenance)). This is the audit artifact for the **Path-1** crypto-shred, emitted **here, after Path 3**, so the "shredded" marker never precedes the diagnostic-bucket flush ([Spec-022 §Shred Fan-Out](../specs/022-data-retention-and-gdpr.md#shred-fan-out) — _the scoped flush is issued before `event.shredded` emission_). Its payload carries no PII and is retained indefinitely. (Plan-006 / Plan-022 describe this emission as triggered "on Path-1 completion" — that assigns its _ownership_ and names the operation it _records_, not its position relative to Path 3, which `Spec-022 §Shred Fan-Out` sequences.)
2. **`user.purged`** — `{purgedAt, affectedSessionIds[], piiPayloadsCleared}` ([Spec-006 §User Lifecycle](../specs/006-session-event-taxonomy-and-audit-log.md#user-lifecycle-user_lifecycle)), the terminal audit artifact of the whole operation. **Never** emit `user.purged` against a partial shred.

## Validation

The erasure is complete when **all** of the following hold:

- `user.purged` is present in the event log and verifies under [Spec-006 §Integrity Protocol](../specs/006-session-event-taxonomy-and-audit-log.md#integrity-protocol).
- **Path 1:** `SELECT count(*) FROM user_keys WHERE user_id = :pid;` returns `0`. Spot-check that a previously-readable `pii_payload` for the user no longer decrypts (key absent) — one `session_events` row and, where present, one `interventions` row stamped `pii_user_id = :pid` (same DEK, both must fail). **On every node the user runs**, `SELECT count(*) FROM artifact_encryption_keys WHERE user_id = :pid;` returns `0` (active **and** retired rows — the predicate is user-keyed, so one statement covers both). Verify per node, not once: the store is daemon-local, and a single surviving row leaves the X25519 private half that unwraps relay-held CEKs intact, so the Path-2 `artifact_relay_recipients` DELETE would no longer prove a crypto-shred. Skip only where the table is genuinely absent (pre-Tier-7 deployments per the Detection deployment-scope note) — an unreachable node is **not** an absent table, and erasure is incomplete until it is reached.
- **Path 2:** `SELECT count(*) FROM users WHERE id = :pid;` returns `0`; and — where `revoked_*` exist in the deployment (post-BL-070) — the denylist rows still exist with `user_id IS NULL` and their key intact. Where the Plan-018 identity-key table exists (Tier 5+): `SELECT count(*) FROM user_identity_keys WHERE user_id = :pid;` returns `0` — every registered workstation identity key deleted (Plan-018 T5.1, 2026-08-15) — and `SELECT count(*) FROM webauthn_credentials WHERE user_id = :pid;` returns `0` (Plan-018 T6.1, 2026-09-01). Where the Plan-021 tables exist (Tier 6+): `SELECT count(*) FROM rate_limit_escalations WHERE identity = :pid AND identity_type = 'user';` returns `0`, and any `admin_bans` rows matching the identity **still exist unmodified** (the retain class is a positive check — a missing ban row means the runbook over-deleted). Where the Plan-014 relay tables exist (Tier 7+): `SELECT count(*) FROM artifact_relay_recipients WHERE user_id = :pid;` returns `0`, and blobs the user published that are still **live** (`state = 'pinned'` AND `expires_at > now()`) read `publisher_user_id IS NULL` while remaining fetchable by their surviving recipients. A blob at `state = 'expired'` is **out of scope for this check** (narrowed 2026-08-26): it is a TTL tombstone, and its recipient rows were dropped by the relay's own hourly sweep rather than by this erasure, so their absence is no evidence about what the runbook did — and it is correctly not fetchable either way. The exclusion keys on `state = 'expired'` **alone**, never on the publisher reading `NULL`: the sweep drops the publisher identity only when its object-store reclaim confirms, so an unreclaimed tombstone still names its publisher and a `NULL`-keyed exclusion would silently stop covering it ([Spec-014 §TTL sweep disposition (V1)](../specs/014-artifacts-files-and-attachments.md#ttl-sweep-disposition-v1)). Where the Plan-024 lease table exists (post-Phase-3B): `SELECT count(*) FROM session_terminal_leases WHERE holder_user_id = :pid;` returns `0` — any lease the user held reads `holder_user_id IS NULL` (freed fail-closed; the row survives as session coordination state).
- **Path 3:** each diagnostic table returns `0` rows for `:pid`.
- The `event.shredded` + `user.purged` audit pair is intact — these are never compacted or shredded per [Spec-006 §Event Maintenance](../specs/006-session-event-taxonomy-and-audit-log.md#event-maintenance-event_maintenance).

## Escalation

- **Partial shred / per-path failure.** The operation stays at `user.purge_requested` (the durable anchor); the failure is logged for retry per [Spec-022 §Fallback Behavior](../specs/022-data-retention-and-gdpr.md#fallback-behavior). Re-run the **entire** sequence from Path 1 — all three paths are idempotent, so re-execution converges. Do not hand-patch a half-completed state.
- **FK-closure drift.** If a Path-2 DELETE encounters a `REFERENCES users(id)` table not listed here, the [shared-postgres-schema.md](../architecture/schemas/shared-postgres-schema.md) inbound-FK closure is the source of truth — extend the procedure to cover the row, do not skip it, and flag the gap for a runbook update. A forward-declared closure table may also link the user through a **table-specific FK column** rather than a bare `user_id` — e.g. the Tier-9 `cross_node_dispatch_coordination` references `users(id)` via `caller_user_id` / `target_user_id` — so confirm each table's actual erasure predicate against that schema before applying the generic `WHERE user_id = :pid`; the owning tier's plan-readiness audit pins the exact predicate when the table enters a live deployment.
- **No daemon append interface in the deployed build.** If the operator cannot reach the daemon's canonical append path to emit the signed audit events, do **not** raw-`INSERT` them — escalate. The audit emission must use the signed path; raw rows fail integrity verification and corrupt the chain.
- **Signed-bytes concern.** A retained Ed25519 signature does not re-introduce PII after shred (it commits to `pii_ciphertext_digest`, not plaintext) — see [Spec-022 §Signature Safety Under Shred](../specs/022-data-retention-and-gdpr.md#signature-safety-under-shred). No action needed; do not attempt to strip signatures.

## On-Call Routing

GDPR erasure requests route to the data-protection on-call (privacy / compliance), who coordinates with a daemon / control-plane operator holding both-store access. Erasure is operator-initiated, never automated in V1.
