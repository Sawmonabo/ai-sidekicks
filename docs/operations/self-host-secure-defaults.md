# Self-Host Secure Defaults

## Purpose

Describe the secure defaults that are active out-of-the-box for a self-host deployment of AI Sidekicks: what is on without the person configuring anything, how to verify each default is actually active, what the override path is, and the one-line reason the default is what it is. This doc is the hands-on companion to [Spec-024](../specs/024-self-host-secure-defaults.md); it does not state requirements — it describes current shipped behavior in declarative form.

If a row in the table below does not match what your deployment is doing, treat that as a deviation worth investigating — the first-run banner (row 10) should agree with this doc on every fresh boot.

## The Eleven Defaults

| # | What is on by default | How to verify it is active | How to opt out / override | Reason the default is what it is |
| --- | --- | --- | --- | --- |
| 1 | **Relay traffic over TLS via Caddy.** The person declares `DEPLOY_MODE=public` (default) or `DEPLOY_MODE=lan`. `DEPLOY_MODE=public` uses ACME — DNS-01 preferred when a DNS provider plugin is configured, HTTP-01 otherwise; renewals follow RFC 9773 ARI windows (exempt from Let's Encrypt rate limits). `DEPLOY_MODE=lan` uses Caddy's internal CA (`tls internal`) directly, prints SPKI-SHA256 + SSH-style fingerprints, and persists them at `./data/trust/fingerprint.txt`. Caddy does NOT silently fall back from a failed public-ACME issuance to an internal CA (caddyserver/caddy#4735); a mismatched mode/hostname combination is refused at parse time. | `curl -vk https://<host>/` shows `TLS 1.3` with issuer `Let's Encrypt` (`DEPLOY_MODE=public`) or `Caddy Local Authority` (`DEPLOY_MODE=lan`). `cat ./data/trust/fingerprint.txt` shows both SPKI-SHA256 and SSH-style hashes under `DEPLOY_MODE=lan`. | Mismatch refusal: `DEPLOY_MODE=public` with `.localhost` / `.local` / `.home.arpa` / `.internal` / RFC1918 hostname, OR `DEPLOY_MODE=lan` with a public DNS hostname, exits non-zero at parse time. `--relay-no-tls` permitted only when bind is loopback; non-loopback + no-TLS refused at parse time. | DNS-01 reaches private hosts HTTP-01 cannot; ARI-coordinated renewals don't get rate-limited. The person's declared intent beats runtime auto-detect on a security-critical branch. |
| 2 | **Refuse-to-start without encryption on non-loopback binds.** The relay, in the Compose deployment, and the daemon, on each of the person's machines, each check `<bind> + <TLS mode>` for every network listener at config-parse time; the process exits non-zero with the offending option named. | Set a non-loopback `METRICS_BIND` with no `METRICS_AUTH` on the relay, or on a machine's service → expect a non-zero exit at config-parse time naming the option. | `--insecure` (or `INSECURE=1`) starts the relay anyway, printing a loud banner every boot and emitting `security.default.override=insecure_bind`. The daemon has no insecure mode: its one listener that can leave loopback, `/metrics`, takes a non-loopback bind only with TLS and `METRICS_AUTH` (row 9). | A docs-only "don't do this" warning (Supabase-style) has been shown to fail in the field; the check lives in the code. |
| 3 | **All secrets auto-generated on first run.** Each machine's service makes its own master key at its first start and keeps it on the [custody tiers](../decisions/021-cli-identity-key-storage-custody.md#custody-tiers), never in the clear; the machine's identity key is sealed under it in the daemon's database. None of these is a file in this folder. Public material (fingerprints, public keys) is printed to both stdout and the top of the relay's fingerprint file. | `ls -la ./data` → no `*.key` file; `./data/trust/first-run.complete` is the sentinel. Startup banner (row 10) prints the fingerprints. | No override. Secrets cannot be pre-seeded via env vars or `.env.example`. Sentinel file `./data/trust/first-run.complete` records that generation ran; if it is missing while the relay's secrets are present, the relay refuses to start with a message naming the sentinel and the secrets it found, so regenerating them is the person's explicit act. | Supabase's experimental `generate-keys.sh` has shipped with bugs (issue #42562 — writes a non-existent env var). The spec ships generation, not an optional helper. |
| 4 | **No network address for the daemon's clients.** On each machine the daemon's local IPC is a Unix domain socket or a named pipe with no network address, and its one listener that can leave loopback, `/metrics` (row 9a), defaults to `127.0.0.1`. In the Compose deployment, the relay's `RELAY_BIND=0.0.0.0:8787` is container-internal (Caddy fronts on `:443`). | On a machine, the listening TCP sockets (`ss -ltn` on Linux) show the daemon's `/metrics` on `127.0.0.1` and no other daemon listener off loopback. On the Compose host, `netstat -ltn` shows only `:443` (Caddy) reachable from outside. | No override gives the daemon a network address for its clients. A non-loopback `METRICS_BIND` requires `METRICS_AUTH` and the listener's TLS keypair — row 9's check refuses the combination otherwise. | Localhost-first closes the entire class of "daemon on public Wi-Fi by accident" incidents. |
| 5 | **Postgres `sslmode=verify-full`, plus weak-auth rejection and version probe.** The relay refuses to start if `pg_hba.conf` contains any enabled line with `trust`, `password`, or `md5`. The relay refuses to start if Postgres `server_version_num < 170000`. A non-fatal advisory is logged for `< 180000`. | On a running deployment: `PGSSLMODE=verify-full psql …` succeeds for your relay's connection string. Attempt to connect to a MITM'd DB → connection refused. `SELECT current_setting('server_version_num')` returns ≥ `170000`. `SELECT auth_method FROM pg_hba_file_rules` contains only `scram-sha-256` / `cert` / `oauth`. | `sslmode=verify-ca` with a loud banner is accepted; `disable`, `allow`, `prefer`, `require` are refused. No override for weak auth methods. | CVE-2024-10977 (libpq MITM error-message injection, 2024-11-14) is exploitable under `require` and defeated by `verify-ca`/`verify-full`. Postgres 14 reaches end of life on 2026-11-12; requiring 17 keeps the relay off a database past its end of life. |
| 6 | **Backups, off until the person turns them on.** Nothing is backed up until the person turns on `Back up automatically` under `Backups` on Settings › Runtime. The folder is `<home>/.ai-sidekicks/backups` by default, at mode `0700`; on a Windows computer whose service runs in WSL it is the Windows home's `.ai-sidekicks\backups`, so the backups outlive the distribution. Once on, the service copies its database whole once a day and after every `Delete old data`, keeps 7 daily and 4 weekly copies, and keeps the machine's settings file, the conversation files, chat workspaces, checkpoint copies and the agent memory folder as one mirror. The service never uploads a backup. | `Backups` on Settings › Runtime shows the last run, and the folder holds the database copies. The daemon's `/metrics` → `backup_success_total` increments on each run. | `Back up to` with `Choose…` picks another folder, an external drive or a synced folder included; `Back up now` runs one at once; `Restore…` restores, and `sidekicks db restore <backup>` does the same on a machine with no app. Off is the default, not an override, so the banner shows no override line for it and no `security.default.override` event is emitted. [Spec-013 §Backup Policy](../specs/013-persistence-recovery-and-replay.md#backup-policy) owns how a backup runs. | Whether and where copies of the person's sessions are kept is the person's choice, and only a folder on another drive protects against losing the disk. |
| 7a | **Auto-update — notify-by-default (daemon).** Daemon polls GitHub Releases on a cadence owned by Plan-006. On detection of a newer version: surface a prompt on next CLI invocation, add a line to the next startup banner, emit `security.update.available`. Daemon MUST NOT self-swap its binary while IPC is live. | `/metrics` → `auto_update_check_status` gauge (`0=ok / 1=behind / 2=poll_failed`). Startup banner includes `Update available: vX.Y.Z` when behind. | `AUTO_UPDATE_CHECK=off` disables polling. | A running daemon with open IPC sockets and file locks cannot safely self-replace mid-session. |
| 7b | **Auto-update — opt-in self-update (CLI).** `sidekicks self-update` checks the downloaded program against the SHA-256 the release's manifest lists for its platform, and nothing more; a mismatch triggers refusal. After the check it waits for running work to finish, naming it, never stopping it, then swaps the service's program and restarts it. It updates the service alone; the app updates from Settings › General. | `sidekicks self-update --check` only reports: it exits 0 when up to date, 100 when an update is waiting, and 1 when it could not check. A download whose checksum does not match will show `FATAL:` and refuse. | No override — the checksum check is not bypassable. (On an install a package manager owns, `self-update` replaces no file and names that package manager's own command, such as `sudo apt update && sudo apt upgrade` or `sudo dnf upgrade`.) | A long-running service is replaced only when the person asks, out of session, and only with the bytes the release published for it. |
| 8 | **TLS 1.3 minimum everywhere TLS is used.** Node `minVersion=maxVersion=TLSv1.3`. Caddy `tls { protocols tls1.3 }`. | `openssl s_client -connect <host>:443 -tls1_2` → handshake fails. `-tls1_3` → succeeds. | `--legacy-tls12` or `LEGACY_TLS12=1` with a loud banner and `security.default.override=legacy_tls12`. | TLS 1.2 is not formally deprecated (RFC 8996 deprecates only 1.1 and earlier), but 1.3-only is feasible (>92% cross-browser support) and closes the downgrade-attack surface. |
| 9 | **Security `/metrics` exports on a Prometheus v0.0.4 endpoint bound to `127.0.0.1`.** **9a — daemon scope.** Exposed counter families: `token_auth_failure_total`, `cedar_deny_total` (Cedar policy-engine denies per ADR-012), `relay_connection_churn_total`, `backup_success_total`, `auto_update_check_status` (gauge), plus the Plan-018-owned `retention_policy_override` warning gauge (`1` while a diagnostic-bucket retention-TTL override beyond 30 days is active — outside the row-9a set). Rate-limit families are control-plane-side, not daemon-side: the daemon has no rate-limit enforcer, so the canonical `rate_limit_*` families are emitted by the control plane and exported on the relay endpoint (9b). **9b — relay scope.** The relay exposes an equivalent Prometheus v0.0.4 `/metrics` endpoint under the same bind/auth posture, adding `relay_ws_connections_active`, `relay_ws_frames_total`, `relay_http_requests_total`, `relay_http_request_duration_seconds` (histogram), plus the canonical rate-limit families `rate_limit_trip_total`, `rate_limit_backend_error_total`, `rate_limit_failclosed_total`. | **9a:** `curl http://127.0.0.1:<metrics-port>/metrics` against the daemon returns Prometheus-format text; every row-9a daemon family present, plus the Plan-018-owned `retention_policy_override` warning gauge. **9b:** the same scrape against the relay's metrics port returns all row-9b relay families. | `METRICS_BIND=off` disables the endpoint entirely on either surface. A non-loopback `METRICS_BIND=<host>:<port>` is accepted only with auth configured — `METRICS_AUTH=bearer` (token read from `METRICS_AUTH_TOKEN_FILE`; the file is re-read on the authorization path, so replacing its contents rotates the credential without restart) or `METRICS_AUTH=mtls` (client CA `METRICS_TLS_CLIENT_CA_FILE` + SPKI-SHA256 fingerprint allow-list `METRICS_TLS_CLIENT_ALLOWLIST_FILE`), with the listener keypair `METRICS_TLS_CERT_FILE` / `METRICS_TLS_KEY_FILE` required on any non-loopback bind in both modes; missing or invalid credential material is a config-parse-time error (fail closed); the contract is owned by Plan-018 and consumed by Plan-028 for the relay. A non-loopback bind with no auth is refused at config-parse time, and scraping without the configured credential is rejected. | A person running blind cannot detect credential-stuffing, rate-limit ceiling breaches, or update-check flatlines. Loopback default avoids making metrics an attack surface. One bind/auth contract shared by daemon and relay gives the person one posture to audit instead of two. |
| 10 | **Loud first-run banner on every process start.** Single-screen printout enumerating: TLS mode + fingerprint; all bind addresses; backup state (off, or the folder and the last run); update channel + mode; any active `security.default.override=*` rows. | Restart daemon or relay → expect the banner on stdout. A `BANNER_FORMAT=json` mode emits the same payload as one JSON line (for structured-log environments). | No opt-out. `BANNER_FORMAT=json` is a format switch, not a suppression. | A person who ran `docker compose up` on a borrowed laptop without ever reading docs MUST still be told what security posture they got. |

## Operational Events To Expect

These are shipped-behavior facts that will affect the person running the deployment over the V1 lifecycle. They are not requirements — they are heads-up notes.

- **Let's Encrypt is shortening certificate lifetimes.** Its opt-in `tlsserver` profile issues 45-day certificates; its default `classic` profile moves to 64-day certificates on 2027-02-10 and to 45-day certificates on 2028-02-16 ([announcement](https://letsencrypt.org/2025/12/02/from-90-to-45)). The deployed ACME client is ARI-driven (RFC 9773) and handles each of these lifetimes without code changes, so the change is transparent to the person — but expect shorter cert validity periods in dashboards and monitoring after each step.
- **Postgres 14 reaches end-of-life on 2026-11-12.** The relay's startup probe already refuses to start against `server_version_num < 170000`, so a person still on PG 14, 15 or 16 will see a clear failure. Plan your upgrade to PG 17 (or PG 18, recommended) before upgrading the relay.
- **Let's Encrypt short-lived certificates (`shortlived`, 160 hours) are an opt-in.** The Compose relay's Caddy takes `ACME_PROFILE`, empty by default, which leaves Caddy's own profile; `ACME_PROFILE=shortlived` requests the short-lived certificates. Let's Encrypt: "Short-lived certificates are opt-in and we have no plan to make them the default at this time." The relay's key is pinned only when its certificate is not publicly trusted, so a short-lived certificate never trips the pin.
- **Postgres 18 is supported, and so is Postgres 17.** The relay's behavior 5 advises (not requires) PG 18 for the `oauth` auth method and the `md5_password_warnings` knob. A person on PG 17 will see the advisory line on startup logs but the relay will proceed.

## Verifying A Deployment Against This Doc

If you are auditing or triaging a self-host deployment and want a single pass:

1. Restart the daemon and the relay. Capture the first-run banner of each (row 10).
2. Compare the banner against the table above, column by column.
3. For any row where the banner shows an override (`security.default.override=*`), check the reason — overrides are legitimate when explicitly chosen; they are not legitimate when the person did not set them.
4. Scrape `/metrics` on loopback (row 9). All row-9a daemon counter families — plus the Plan-018-owned `retention_policy_override` warning gauge — should be present on the daemon endpoint (9a), and all relay families on the relay endpoint (9b).
5. Confirm `./data/trust/first-run.complete` exists and `./data/trust/fingerprint.txt` contains both the SPKI-SHA256 pin and the SSH-style hash.
6. Try a deliberate violation: set a non-loopback `METRICS_BIND` with no `METRICS_AUTH` on the relay, and on a machine's service. Expect each to exit non-zero at config-parse time, naming the option (rows 2 and 9). If either starts, it is not on the shipped code path and MUST be investigated.
