## Purpose

A person may drive provider CLIs from more than one paid account: a personal subscription and a work seat, two organizations, a metered API key beside a plan-included subscription. V1 must let a runtime node hold several accounts per provider, choose which one pays for a given run, keep each account's credential material in its own isolated home so the accounts cannot corrupt one another, and report spend per account so that plan-included usage is never silently added to billed dollars.

This spec defines the **provider account** as a first-class node-local entity: how it is registered, how it is identified, how its credential home is constructed and validated, how a run selects one, and what the rest of the corpus may assume about it. Two surfaces elsewhere in the corpus already presuppose an account axis without defining it — the account-scoped provider-quota snapshot (`usage.rate_limit_update`, [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) and the per-phase park schedule that exists because "two parallel branches of one run may park concurrently against different provider accounts" ([Spec-015 §Provider-limit pacing and durable resumption (SA-37)](015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-37)). This spec is the canonical home those surfaces resolve against.

## Scope

- The provider-account registry: registration, listing, current-account selection, removal, and the account's durable fields.
- **Account identity** and **credential generation** — the two derivations other specs consume by name.
- Per-account isolated credential homes: construction, the environment discipline that reaches the provider child, validation at spawn, and the fail-closed refusal when an account is unregistered or its home is missing.
- Per-provider current account plus the pins a saved agent definition and a workflow step carry, and the authorization posture of each.
- **Billing mode** (`subscription` / `metered` / `unknown`) as a recorded, displayed property.
- The concurrency posture: runs on one account, and on two accounts of one provider, run at once.
- The disposition of the provider-initiated credential-refresh request within the bounded custody posture [ADR-026](../decisions/026-provider-credential-custody-posture.md) sets: the one Codex service that runs on tokens the daemon hands it sends it, and the daemon answers it with tokens the provider's own code renewed inside that account's own home.
- **Brokered interactive sign-in** and the bounded **non-interactive token** registration path — the two legs ADR-026 authorizes, and the boundary that keeps everything else refused.
- The per-account **credential-home health observation** cadence, its opt-out, and the freshness horizons it renders.
- **Per-limit provider quota**: the limit identifier that keys an account's quota windows, and the durable per-account window registry that holds the newest reading of each.

## Non-Goals

- **Bounded token custody — one class, one input, and nothing else**, under [ADR-026](../decisions/026-provider-credential-custody-posture.md). Credential material lives where each provider stores it, and the daemon never logs, shows, or serves it: **no event, error, log, metric, or wire-read payload carries credential material, ever**. The one custody class is ADR-026's D2 class — a provider-minted non-interactive credential (a Claude Code setup token, or an OpenAI API key for Codex), supplied by the person on the `register` verb's dedicated write-only input, sealed in the operating system's credential store, or in the daemon's `secrets.json` file where that store cannot be used, and handed only to processes bound to that account, on the channel the provider documents. The class is what the ADR describes: minted by the provider for the person's own account, consumed on a channel the provider documents, carrying no refresh token, so possession mints no successors, supplied deliberately through the dedicated non-echoing input, and handed over so it stays out of every tool, shell and subagent subprocess the provider spawns. Beyond that class the daemon moves a credential, without copying or showing it, in exactly the places ADR-026 names (§Credential-refresh brokering, §Credential homes and the constructed environment). What this spec principally adds is a **location** discipline — which home a provider process reads and writes — and the one custody claim it makes is the class above, bounded on its face.
- **No provider config-file ownership.** Provider config files stay provider-owned, and [ADR-026 §Decision](../decisions/026-provider-credential-custody-posture.md#decision) bounds what the daemon does inside a provider's home. Choosing which home a provider process uses is a spawn-time environment decision and is **not** a write into a provider config file, and this spec claims no ownership over the bytes inside a home. A provider's settings reach it as flag settings — Claude Code's `--settings` at each start and `apply_flag_settings` mid-session, Codex's `-c` at each start — and are never written into its files. The daemon writes into a provider's files only for a named act: each Claude Code account home's own `settings.json` carries `"cleanupPeriodDays": 36500` (§Credential homes and the constructed environment); revoking one of a provider's own standing rules edits the file the provider keeps it in (§Interfaces And Contracts); turning on `Use Sidekicks in terminal Claude Code` installs the app's plugin through Claude Code's own `claude plugin` commands and writes the one setting that switches plugin hooks on into the `env` of the person's `~/.claude/settings.json`, and turning it off removes exactly those; a tool server added, changed or removed at a scope is written through the provider's own mechanism wherever one exists — `claude mcp add-json --scope` on Claude Code, `config/value/write` / `config/batchWrite` on Codex's `$CODEX_HOME/config.toml` — and a project's `.codex/config.toml`, which no provider mechanism writes, only by a format-preserving edit renamed into place while the file still hashes to what the daemon last read, counted once `config/read` lists the server ([Spec-024 §Configuration Mutation](024-mcp-server-configuration-and-governance.md#configuration-mutation)); and while `Reach Codex sessions started in a terminal` is on, the person's own `~/.codex/config.toml` also receives the trust records the daemon's terminal-session hooks need.
- **No account provisioning or billing integration.** The daemon does not create provider accounts, purchase plans, read invoices, or call any vendor billing API. Billing mode is declared by the person or observed from the provider, never fetched.
- **No control-plane account records.** Accounts and their spend are node-local. Nothing about a provider account is written to the control plane; the shared schema's permitted row classes do not admit them and this spec does not widen that set.
- **No first-run step.** First run asks nothing about providers; a provider is installed, registered and signed in on Settings › Providers, from the registry and the readiness derivation this spec defines (§Node provider readiness and the sign-in handoff).
- **No control-plane rate-limit policy.** Provider-side throttling is expressly a Non-Goal of [Spec-019](019-rate-limiting-policy.md); this spec's provider-quota surfaces do not belong there and do not amend it.

## Required Behavior

### The account registry

- A runtime node holds zero or more **provider accounts** per provider. Each is registered, from this machine or any linked device, with a provider and a credential home; the daemon mints the account's identity and records the registration durably. A home the daemon creates is its own folder, `~/.ai-sidekicks/accounts/<account id>/`.
- **An account is identified on every surface by the identity its own provider reports, and by nothing this product invents.** The identity is three fields read from the provider itself — the address it returns, the plan in the provider's own word, and the organization where the plan carries one — with no generated name and no computed suffix anywhere. All three fields are part of the identity rather than decoration, because **one address can hold two accounts** of the same provider on different plans, and an identity of address alone could not tell them apart. Both pinned providers publish the three: Claude Code's own credential-status read reports the address, the subscription type and the organization name, and the Codex sign-in token carries the address and the plan type. Where a provider reports no organization, the identity is two fields; absence is not filled in. The plan is stored as the provider sends it and drawn in the provider's own name for it: Claude Code's plan word capitalized, and on Codex the name Codex's own app gives the plan id, never the id: `free` Free, `go` Go, `plus` Plus, `prolite` Pro, `pro` Pro (More), `promax` Pro (Max), `team` and `self_serve_business_usage_based` Business, `self_serve_business_prolite` Business Premium, `business`, `ent26`, `enterprise_cbp_usage_based` and `enterprise` Enterprise, `enterprise_cbp_automation` Enterprise (Automation), `edu` Edu, `edu_plus` Edu Plus, `edu_pro` Edu Pro; `unknown` draws no plan word, and an id not in this list reads in sentence case, as any unlabeled code does.
- **An account added by a pasted token or API key is named by the person, because its provider names it nowhere.** The paste form carries `Name`, and the account reads that name beside the credential's kind, `Work · Codex API key`. The name is required, trimmed, and differs from that provider's other account names compared by full Unicode case folding (`foldName` in the contracts package), so `Straße` and `STRASSE` are one name: a missing one is refused with `Name this account.` and a duplicate with `Another <provider> account already has this name.` It is renamed in place. Every other account keeps the provider-reported identity and carries no name of the person's.
- **Billing mode, and the name of an account added by a pasted token or API key, are the account row's only fields the person authors.** The provider-reported identity and the credential-home path are read-only: a surface that let either be typed over would let the person relabel one account as another, and historical spend is keyed to identity.
- Registration is authorized by the device that asks (§Authorization Posture): this machine's own client or any linked device may register an account, and no session may.
- Exactly one account per provider MAY be marked the **default**, and that mark is the provider's **current** account — one fact under two words, the registry's and the Providers page's. It is what new sessions start on and what every unpinned running session on that provider moves to when it is pressed (§Moving a session to another account). Where a provider has accounts registered but none marked default, run admission for that provider refuses rather than guessing (§Fallback Behavior).
- Removing an account MUST NOT delete its credential home, MUST NOT run the provider's own sign-out, and MUST NOT be permitted while a session runs on that account: the refusal names those sessions, so the person can move them first. The home is the person's material; deregistration forgets the registry row, not the person's credentials. **Running the provider's sign-out here would be a destructive side effect on material that is not this product's**: on at least one pinned leg signing out can end the login of the account being left, so a person who merely wanted the row gone would find the credential gone too, and signing in again would be a full browser round trip rather than a re-registration. Ending a login is the separate, deliberate sign-out act (§Interfaces And Contracts), and the two are never folded into one.

### Account identity and credential generation

Two derivations are defined here because other specs consume them by name and none of them defines either.

- **Account identity** is the daemon-minted, opaque, immutable `accountId` recorded at registration. It is stable across credential rotation, re-authentication, a billing-mode correction, and default changes — it names _which account_, never _which credential_. It is never derived from a credential, an email address, a subscription identifier, or any path, so nothing about it leaks account material, and it is never reused after removal.
- **Credential generation** is a monotonically increasing integer stamped on the account row, starting at 1 at registration and incremented by the daemon at **every credential-home lifecycle transition it performs or observes**: a completed re-authentication, a home reset the person starts, and a transition of the account's probe result into or out of `authenticated` **as established by the deliberate probe verb**. A background health observation is deliberately not one of these: it writes the stored health pair and never bumps the generation, however its reading compares to the stored one (§Credential-home health observation) — a bump tells every consumer the home changed, so an observer that bumped on a transient fault would report a change that never happened. It names _which credential era_, so a consumer can tell "the same account, re-authenticated" from "the same account, unchanged" without inspecting credential material.

The pair `(accountId, credentialGeneration)` is the corpus's account-plane key. [Spec-015 §Provider-limit pacing and durable resumption (SA-37)](015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-37) groups the runs waiting on one spent account into one attention entry keyed by its `providerAccountId`, which is **this** `accountId`; the entry lasts while steps wait on the account and goes when the last of them resumes, so a generation bump neither splits it nor ends it. The account-scoped quota display (§Provider Quota Is Account-Scoped) and the cost receipt's paying-account column ([Spec-014 §Session Cost Receipt](014-multi-agent-orchestration.md#session-cost-receipt)) consume the same `accountId`.

### Credential homes and the constructed environment

Each account owns an **isolated credential home** — a daemon-managed directory holding exactly that account's provider credential material, distinct from every other account's home and from the person's own ambient provider configuration.

Isolation is the mechanism, and it exists for a specific failure: provider credential files are rewritten in place on token refresh, so two concurrent processes sharing one home can interleave writes and destroy a refresh token that only one of them holds the successor to. Separate homes give each account its own credential file and its own lock scope, so a refresh on one account cannot corrupt another. This is why homes are per-account and not per-provider.

The home reaches the provider child **inside the one place the daemon builds a provider child's environment** and never beside it. [Plan-003 §Phase 3 — Codex + Claude driver implementations](../plans/003-provider-driver-contract-and-capabilities.md#phase-3--codex--claude-driver-implementations) builds every provider child's environment there, first spawn and resume alike: the login-shell environment the daemon captured at start ([Spec-006 §Required Behavior](006-local-ipc-and-daemon-control.md#required-behavior)), not the daemon's own, with the session's own pairs replacing base pairs of the same name — the environment rows from Settings › Projects merged in (a project's row over the `Every project` row of the same name, and every name the app sets itself dropped from the rows), the effective credential policy's secret variables stripped, and the run-provisioned variables set. The daemon strips only the secret variables and builds no allow-list of its own. This spec adds normative content to that regime rather than contradicting it:

- The provider **credential-home variables are a named subset of the run-provisioned variables**, set by the daemon at spawn from the selected account's home and from nothing else. They are **reserved to the daemon**: the daemon is their sole writer, an inherited or caller-supplied value of a reserved name is discarded at construction rather than merged, and no session, run, workflow, execution posture, or MCP configuration surface may set one. This spec is where that reservation is stated, and the construction site that strips denied variables is where it is applied (§Implementation Notes).
- The Claude leg's existing rule — strip the provider's ambient variables, supply configuration through the explicit settings flag rather than the person's home — is **unchanged in kind**. The strip is of _inherited ambient_ values; the daemon then sets the reserved credential-home variable as a run-provisioned value. Stripping and provisioning are two stages of one construction, not a contradiction.
- Beneath the strip, the Codex leg's own `shell_environment_policy` (`inherit: "none"` and an explicit `set`) is defense in depth for the commands Codex runs: its explicit set carries the merged environment rows and the reserved variable.
- **On the Claude leg the daemon also names the per-project folder the provider keeps its conversations under, and names it the same in every account's home.** That provider stores a session's conversation file at `<home>/projects/<project folder>/<session id>.jsonl`, and it derives the folder name from the working directory unless told otherwise. Naming it is load-bearing rather than tidy: that folder is also where the provider keeps a project's automatic memory, so a name that varied would split one project's memory across directories. One name per project, the same in every home, set by the daemon at spawn like every other reserved variable.
- The reserved set is **per-provider and asymmetric**, and the asymmetry is a design constraint rather than an inconvenience to abstract away. Codex co-locates account identity and tokens in a single file under one platform-uniform home directory, relocated by one documented variable (`CODEX_HOME`). Claude Code splits the tuple across two stores — account identity in its own configuration file, tokens in a platform-dependent store (an OS keychain on macOS; a credentials file on Linux) — relocated by different variables with different scoping rules (`CLAUDE_CONFIG_DIR`, documented to hold `.credentials.json` on every platform, the file macOS falls back to included, and to key the macOS keychain entry ([Claude Code §Credential management](https://code.claude.com/docs/en/authentication#credential-management)), and a separate secure-storage variable that is undocumented). **No symmetric cross-provider abstraction is available**, and a design that assumes one will be correct on at most one provider. Each provider's concrete reserved set is recorded in the provider-wire reference with the version it was measured at, per that reference's rules ([Provider Wire Reference §Versions](../reference/provider-wire/README.md#versions)) — variable names move, and one of the two Claude variables has no vendor documentation to move with it.

- **The daemon sets a reserved variable to an absolute path or does not set it at all.** An empty-string value is not a permitted spelling of "unset". On the Claude leg an empty value is known to behave as unset _and_ to suppress the companion variable, collapsing a home partition that would otherwise have held — a failure that is both fail-open and silent. The daemon therefore never emits an empty reserved variable, and treats an empty value observed in a constructed environment as a construction defect rather than a default.
- **Each account keeps its own credential store, apart from any session's configuration folder.** On Claude Code the store is a folder chosen with `CLAUDE_SECURESTORAGE_CONFIG_DIR`, set for every process to the account's own store folder, so changing that one variable is how a running session changes account in place (§Moving a session to another account); on Codex it is the account's `CODEX_HOME`. Every Codex process of an account home starts with `-c cli_auth_credentials_store="file"`, Codex's own default store ([Codex `defaults.toml`](https://github.com/openai/codex/blob/main/codex-rs/config/defaults.toml)), so a Codex sign-in is always `auth.json` in that home at mode `0600`, never a keychain item; the one Codex service that takes a pasted API key starts with `"ephemeral"` instead (§Non-interactive token registration).
- **What the daemon puts in an account's home beside the provider's own files.** Each Claude Code home's `settings.json` carries `"cleanupPeriodDays": 36500`, as does the `--settings` JSON of every Claude Code process the daemon starts, so the provider's own transcript cleanup never deletes a conversation file a kept session resumes from; the daemon reads the effective value back after each spawn, and a managed policy that sets a lower one is raised as a provider setting that was ignored. Each Claude Code home links `agent-memory` to the daemon's one `All projects` memory folder, `~/.ai-sidekicks/agent-memory/`, under which each agent's `<name>/` folder sits, so an agent's memory is the same on every account and both providers; a Codex session writes that folder through a permission profile's `write` entry.
- **Environment names the app sets itself are refused at save.** An environment row a person adds on Settings › Projects, in the list for every project or for one project, whose name the daemon sets itself — the reserved credential-home variables among them — is refused there with `The app sets this.`, from one rule in `packages/contracts` ([Spec-007 §Fallback Behavior](./007-repo-attachment-and-workspace-binding.md#fallback-behavior)).
- **The daemon keeps each secret as its own item in the operating system's credential store**, a pasted provider credential and a workflow secret's value among them. The daemon opens its own items itself; no client holds or relays them. Every item is opened with `{linux: {store: "secret-service"}}`, so on Linux the kernel keyring, which empties at reboot, is never used; on Linux with no Secret Service answering, the daemon keeps its items in one file in its own data folder, readable by this account alone (mode `0600`), as `gh` and Codex do, and a Mac keeps them in the same file from the approved logged-out service's takeover until `sidekicks daemon uninstall` moves them back, including after that service is turned off in Login Items & Extensions, and never while it waits for approval, because that service cannot reach the login keychain ([Spec-020 §Daemon Secrets](020-data-retention-export-and-deletion.md#daemon-secrets)); it never falls back silently, and the person can see where secrets are kept. On Windows every entry is written through the service's Windows half at `CRED_PERSIST_LOCAL_MACHINE`, never at a roaming persistence, whether the service runs on Windows or in a WSL 2 distribution.
- **On a Windows computer whose providers run in WSL 2, the account homes live on the service's side**, in the distribution the background service runs in, and the keychain entries stay on Windows for both sides. A move of the service between Windows and a distribution carries each account home whole, less its sign-in file and each Claude Code home's `agent-memory` link, which the new side makes again; each sign-in file is moved into the same account's folder on the new side once the old side has fully stopped, deleting the old copy, never copying it, so every account stays signed in and two live copies never exist. A move that fails puts the newest sign-in file back first.

**Authentication must survive the constructed environment.** A provider process that reaches a home holding no usable credential is not authenticated, however well-formed its environment is. Two known hazards bound the design and are named rather than assumed:

- Provider minimal-startup modes can bypass the credential machinery entirely — the pinned Claude reference records that the minimal mode strips OAuth and keychain access ([Provider Wire Reference §Gaps recorded](../reference/provider-wire/claude.md#gaps-recorded), a **Provisional**-trust claim). A driver leg MUST NOT select such a mode for an account-bound spawn.
- On platforms where provider credentials are held in an OS keychain rather than in the home directory, the keychain entry a provider addresses may be a function of its configured home. Where that holds, per-account homes give per-account keychain entries and isolation is preserved; where it does not, the home is not by itself an isolation boundary on that platform. **The daemon treats the keychain entry as opaque**: it never computes, derives, predicts, or addresses a provider's keychain entry name, and it never asserts partitioning by construction, with one named exception: on a Mac, the `--while-signed-out` service once it is approved and takes over, and `sidekicks daemon uninstall`, move each Claude Code account's sign-in between that account's keychain entry and its `.credentials.json`, addressing the entry by the name the pinned build is measured to use (below), and only to move it ([ADR-026](../decisions/026-provider-credential-custody-posture.md); [Spec-006 §The service on a Mac while logged out](006-local-ipc-and-daemon-control.md#the-service-on-a-mac-while-logged-out)). Isolation on such a platform is established **empirically**, by observing that two accounts' homes yield independent authentication states against the pinned build (below) — never by reasoning about how an entry name is built. The vendor documents that its home variable keys the macOS keychain entry to that directory ([Claude Code §Credential management](https://code.claude.com/docs/en/authentication#credential-management)), but not how the entry is named; and the entry-naming scheme, where it can be observed at all, is undocumented, version-fragile, and sensitive to inputs outside the daemon's control.
- **Measured on macOS at the pinned provider build, that keychain entry _is_ a function of the home**: the service name is the default one only for the default configuration home, and otherwise carries a suffix derived from the home the build salts with, so each home's login is its own ([Provider Wire Reference §Environment and update control](../reference/provider-wire/claude.md#environment-and-update-control)). The reading does not move the rule above — the daemon still addresses no entry and still establishes isolation by observation rather than by construction — but it fixes how the secure-storage variable is set: always to the account's own store folder, an absolute path, and **never to the empty string**, and the same folder holds the account's `.credentials.json` where Claude Code keeps the login in a file because the keychain rejects its write, as under a Mac's system service (the probes in [macOS Service Probes](../operations/macos-service-probes.md) confirm the folder), because that variable's honored empty-string value collapses every home onto the default service name, and a home that borrowed another home's login would spend from an account nobody chose.

**Isolation does not make two sessions unreachable to each other.** A session running in one account's credential home is reachable from a session running in another **by its address, not by its name**: the daemon's own directory of its sessions and their addresses is what spans the homes, and it is the daemon — which runs both processes — that looks the address up and delivers the message ([Spec-014 §Sessions Talking To Each Other](014-multi-agent-orchestration.md#sessions-talking-to-each-other)). No credential home is shared, mounted into another, or read to do it, and nothing about a message between two sessions touches either one's credential material. The address is the handle rather than the name for the same reason this section exists: each home keeps its own layout, down to the per-project folder a provider files conversations under (above), so a directory keyed on what each home calls things would have to reach inside the homes to build itself — which is the sharing this section forbids. The daemon knows both sessions because it started them, not because it read either home.

### Brokered interactive sign-in

Authorized by [ADR-026](../decisions/026-provider-credential-custody-posture.md) D1, and **not** custody: the daemon supplies a working directory and a process, and learns nothing.

- The daemon MAY **execute the provider's own first-party sign-in flow** for a registered account: it constructs the invocation itself, spawns the provider's binary **unmodified**, and pins that account's credential home through the reserved variables §Credential homes and the constructed environment already defines. Nothing is patched, and no built-in authentication method is removed, disabled, or restricted.
- **On a WSL computer the flow runs on the service's side**, against the account's home in the distribution the service runs in, and touches no keychain: Linux gives Claude Code no keychain, so it keeps its credentials file in that home, and Codex keeps its `auth.json` there. The verification address reaches the desktop's main process, which opens it in the Windows browser. Codex's callback `localhost:1455` reaches the distribution through WSL's forward (NAT) or the shared loopback (mirrored); where it cannot, the finish-by-hand path below applies, beside the providers' own fallbacks: Claude Code accepts a pasted code, and Codex has `codex login --device-auth`.
- **The daemon never reads the result.** It does not read, parse, copy, cache, relay, or persist the credential the flow writes. The macOS move of an existing sign-in once the `--while-signed-out` service is approved and takes over, and at `sidekicks daemon uninstall` (§Credential homes and the constructed environment) is no part of a sign-in flow, and a flow run while a Mac's system service runs writes its file the way Claude Code and Codex write it themselves. The credential is written by the provider's own tooling into the provider's own store inside that home, exactly as it would be had the person run the command themselves. The broker has **no read path into the home at all** — this is a property of its shape, not a discipline its callers must observe.
- **What travels to the caller is a typed, validated whitelist — never the provider's raw output.** Exactly four fields may leave the broker: a verification URL, an optional device code, an opaque daemon-minted attempt identifier, and an optional attempt expiry. The daemon **parses** them out of the process stream and emits them as typed members; it never forwards a line of that stream verbatim, and any text it cannot parse into those fields is discarded rather than surfaced. This is what reconciles the broker with §Node provider readiness and the sign-in handoff's rule that provider sign-in output is never surfaced: that rule bars the **stream**, and it is narrowed here only to admit the three parsed fields, because a sign-in stream may also carry OAuth state, PKCE values, and credential fields that must never reach a client. The URL is validated against the provider's own documented verification host before it is emitted, so a compromised or unexpected stream cannot redirect the person. The expiry is admitted under the same parse-and-validate discipline rather than as an exception to it — parsed to an RFC 3339 instant, required to be in the future and within the provider's documented attempt ceiling, and **omitted rather than surfaced** where it fails either test — and it is carried because a person handed a device code with no visible bound will type a dead one; it is a bound on the attempt, never a provider state field. A provider arm that emits no parseable verification material cannot be brokered and is refused with a typed refusal naming the provider, rather than spawning a flow the person cannot complete.
- **The verification material is emitted so the person can finish the flow by hand.** When the sign-in was started from another device, the verification address and code come to that device, and the address opens in that device's browser, never on the machine; they are served as data either way, so a browser that failed to open is not a dead end. Where the provider supplies a code, it travels with its own remaining life so the person is not handed a code that has already died; an expired attempt says it expired rather than silently failing.
- **An attempt ends settled, never abandoned.** Every attempt reaches exactly one of completed, canceled, expired or failed, and the failed arm carries a typed reason the surface can name together with the fact that starting again is the next act. An attempt left in neither a completed nor a failed state would leave the person watching a flow that will never answer, and the single-attempt-per-account rule would then hold that account's sign-in shut.
- The flow is **cancelable by the attempt identifier**, and cancellation is a first-class outcome rather than an abandonment: a broker that could only be abandoned would leave a provider-side login slot occupied.
- **One brokered attempt per account at a time.** A second start against an account with one in flight is refused (§Fallback Behavior), because at least one pinned provider silently drops the previous attempt when a new one starts.
- Completion is **observed, not asserted**: the daemon learns the outcome from the provider's own completion signal, correlates it on the attempt identifier, and then takes an ordinary health observation (§Credential-home health observation) to establish the account's state. A completion reported as successful is not by itself a reading that the account is authenticated — only an observation is.
- **An account a sign-in begins has no row until its provider has named it.** While the flow runs, the Providers page shows `Signing in…` in the place the new row will take, and the row appears once the observation after completion reports the account's identity (§The account registry). A sign-in that ends without an identity — closed, failed, expired, or completed without one — deletes the registration it began, as removal does, so no account is ever listed without a name. A sign-in run again on an account that already has its row leaves that row in place whatever the outcome.
- Sign-in is authorized as registration is (§Authorization Posture): this machine's own client or any linked device may start it, and no session may.
- The **calling surface is the provider-management surface and its CLI parity verb**; first run has no provider step to call it from.
- The **registry stays un-evented.** Completion reaches interested clients on a read-shaped subscription carrying a wire-only notification, never a durable session event and never an `EventEnvelope`: an account act on the machine's registry has no session to belong to, and minting a session event type for it would put account administration into a session's audit log.

### Non-interactive token registration

Authorized by [ADR-026](../decisions/026-provider-credential-custody-posture.md) D2. This is the one custody claim this spec makes, and it is bounded on its face.

- The `register` verb — **and no other verb, input, flag, configuration key, or environment variable** — MAY accept a provider-minted non-interactive credential for the account being registered: a Claude Code setup token, or an OpenAI API key for Codex. The input is **write-only**: it is accepted, never returned, never echoed, never logged, never rendered, and never placed on any reply, event, error, metric, or diagnostic payload. The same registration carries the account's required name (§The account registry).
- The daemon does not mint, exchange, refresh, or derive credential material, and **never speaks a provider token endpoint**: a token arrives already minted by the provider's own tooling.
- The supplied value is kept as its own item in the operating system's credential store, verified by write-probe-read-delete rather than assumed, or, where that store cannot be used — on Linux with no Secret Service, and on a Mac whose secrets are in the file — in the daemon's `secrets.json` file, readable by this account alone ([Spec-020 §Daemon Secrets](020-data-retention-export-and-deletion.md#daemon-secrets)). A value the credential store cannot take is **refused with its cause and stored nowhere else**. A locked keychain reads `This machine's keychain is locked, so the token was not stored. Unlock it, then paste the token again.`, and a store the daemon picked that fails to save it reads `This machine has no keychain the app can store a token in, so the token was not stored. Use Sign in instead.` (`provideraccount.credential_seal_refused` with `cause: locked | unavailable`). A Mac tells the two apart by the keychain's own error: `errSecInteractionNotAllowed` is locked, `errSecNotAvailable` or `errSecNoSuchKeychain` is unavailable; a Mac whose secrets are not in the file and whose service finds no login keychain refuses with `unavailable`. On the file path neither refusal is drawn: a missing Secret Service is never `unavailable`, and a Mac whose secrets are in the file never reaches the keychain. Where the keychain refuses, registration refuses: an account is not registered in token mode on a host that cannot store the token.
- **Availability is not durability, so every keychain entry names its store.** On Linux the keystore binding can fall back silently to an in-memory kernel keyring that is lost at reboot and publishes no way to ask which backend answered, so a write-probe-read-delete would pass against a store that will be empty tomorrow, and the account would present an unexplained re-authentication demand rather than a storage fault. Every entry is therefore opened with `{linux: {store: "secret-service"}}`: the kernel keyring is never used, the person is never asked to choose, and a Linux machine with no Secret Service, like a Mac whose secrets are in the file, keeps the item in the daemon's own items file, never silently. On Windows every entry is written through the service's Windows half at `CRED_PERSIST_LOCAL_MACHINE`, never at a roaming persistence, whether the service runs on Windows or in a WSL 2 distribution.
- **The sealed value is not written into the credential home.** §Non-Goals claims no ownership over the bytes inside a home, and daemon-owned bytes in provider-owned space would be indistinguishable to a later reader — and to the provider's own tooling. It lives in daemon-owned state keyed by `accountId`.
- It reaches the provider **only** on the channel the provider documents, never as a variable in a process's start-up environment, because every child a process starts reads that environment; the hand-over happens at the same single construction site that assembles every provider process and applies the reserved-variable discipline. On Claude Code a setup token reaches each spawn on `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`, a pipe written once per spawn — the registration-time observation below and every provider process bound to the account — and an account switch hands it on `CLAUDE_CODE_OAUTH_TOKEN` through `apply_flag_settings {env}`. On Codex a pasted API key reaches the account's service by `account/login/start {type: "apiKey", apiKey}` on the daemon's connection; the service is started with `-c cli_auth_credentials_store="ephemeral"`, so the key lives only in that service's memory and never in Codex's plaintext `auth.json`, and it is sent again after every restart of that service. **The channel is chosen so the credential stays out of every child:** a provider process executes model-directed tools, so a credential it passes to a child is one any command the model issues can read. Both legs are observed to keep it out: at Claude Code 2.1.282 the token delivered on the file descriptor is kept out of every child the session starts, and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is never set; on Codex the key never enters any process's environment. The project's own probe re-runs the Claude Code observation when the project moves to a new Claude Code version. Documentation asserting the behavior is not observation. The credential is never exported to a shell, written to a file the provider does not own, or passed as a command-line argument — an argument vector is readable by any process running as the same user.
- An account registered this way records its **observed** authentication mode on its registry row rather than an assumed one. The observation is made by a **registration-time status invocation**, spawned once as part of registration with the supplied credential handed to that one child on its channel: a non-interactive, single-purpose invocation that runs no model-directed code. The registration transaction commits only if that invocation reports an authenticated mode; a mode the daemon has not observed is stored as absent, never as a default, and the registration is refused rather than left pending.
- The re-login horizon for a token-mode account is the provider's own fixed lifetime measured from the token's **issuance** time, which is not the registration time: a token is minted out of band and may be registered days or months later, so anchoring the horizon to registration would shift it forward by the token's pre-registration age and could tell the person a credential is still good after it has expired. The horizon is therefore computed **only** from an issuance timestamp the daemon can obtain from the provider's own status surface or that the person supplies explicitly; where neither exists the estimate is **null and rendered as unknown**, never defaulted to the registration time. It is **rendered as an expectation, never as fact** — the value is a property of the provider's issuance policy, which the daemon does not control and cannot verify.
- A **terminal authentication refusal on a token-mode account is not retryable and not refreshable**: the class carries no refresh token by construction, so there is no successor to mint. The account's stored reading moves to `reauth_required` and the remedy the surface names is to mint a fresh token at the provider and re-supply it — never a retry, and never a refresh attempt.
- **Re-supply targets the existing account and preserves its identity.** The register verb carries an optional `accountId`; supplied, it means _replace this account's sealed token_ rather than _create an account_, and exactly one input still accepts credential material, because no second verb, flag, or field is minted. Deregistering and registering again is **not** the remedy: registration daemon-mints a new immutable identity, so that path would discard the account and detach the spend, quota, and attention history keyed to it. A successful replacement bumps `credentialGeneration` — it is a new credential for the same account — re-runs the registration-time observation, and destroys the prior sealed value.
- **The registry row and the sealed value are two durability domains, so the lifecycle is an intent protocol rather than a claim of atomicity.** Requiring both to change in the _same operation_ would not make them atomic: SQLite and the OS keychain commit independently, and a crash between them leaves either a live unreachable credential or a registered account with no token. Registration therefore **seals first, then commits the row**, so a crash strands a sealed value that no row references; removal **marks the row's intent first, then destroys the secret, then deletes the row**, so a crash strands a row already marked unusable. A reconciliation sweep at daemon start destroys every sealed value whose `accountId` matches no row and completes every row left marked for removal, and admission refuses any account whose row is intent-marked. Neither crash window can leave a usable credential the person cannot see.

- **A pasted Claude token's limits are read by a turn.** A token minted by `claude setup-token` carries the inference scope only, and `get_usage` needs the profile scope: measured at Claude Code 2.1.278 under a freshly minted token, `get_usage` answers `rate_limits_available: false` and `rate_limits: null` before any turn, after a turn in the same process, and in a fresh process, and `subscription_type` is `null`. Every API answer to the token carries the `anthropic-ratelimit-unified-5h-*` and `-7d-*` headers, and the CLI emits them on the stream as `rate_limit_event` with `unifiedWindows` (five-hour and seven-day utilization and reset). So the account is read by a turn: every five minutes, on the same timer as every other account's read, the daemon sends the window-start turn's command (§Credential-home health observation), thinking off, in an empty folder outside any project, on that account, and that turn's `rate_limit_event` is the read; each live turn refreshes the rows too, and they read `read 7:24 PM` like any read. The read spends a real turn and is priced as one — measured at 395 input and 51 output tokens, about $0.00065 at list price and about $0.19 a day — and is counted in that account's tokens and spend, never as free; the paste form and `Keep this account fresh` say so. Each read also starts a closed five-hour window. `Check now` sends the same turn at once, under the same 60-second floor. That `false` is the login's own statement that it has no read, and the daemon never confuses it with the refused read of a signed-in account, which answers `rate_limits_available: true` beside `rate_limits: null`.
- **A Codex API-key account has no limits to read.** Codex refuses `account/rateLimits/read` for an API key (`chatgpt authentication required to read rate limits`, measured at Codex 0.156.0), so such an account draws no limit rows, no `Keep this account fresh` and no window-start switch, and the daemon spends no read or turn on it.

### Credential-refresh brokering

The pinned Codex surface includes a server request the provider sends **to the daemon** to refresh its authentication tokens (`account/chatgptAuthTokens/refresh`, [Provider Wire Reference §Server-requests](../reference/provider-wire/codex.md#server-requests--the-callback--interactive--approval-surface-codex--daemon)). It arrives only on a service running on tokens a client handed it, which is how the one Codex service for the current account runs (§Moving a session to another account). **The daemon answers it with tokens the provider itself renewed, and mints nothing.**

- **The current-account service runs on tokens the provider minted, held only in the daemon's memory.** The daemon hands the service the account's own sign-in tokens with `account/login/start {type: "chatgptAuthTokens"}`, reading them from that account's home, where the provider's own sign-in wrote them. They are never stored, logged, shown, or given to a client.
- **The refresh request is answered by the provider's own renewal.** The daemon runs `account/read {refreshToken: true}` in that account's own home, where the provider's own code renews the login under its own refresh lock, re-reads the renewed tokens from that home's `auth.json`, and answers with them. A refused refresh reads `account: null, requiresOpenaiAuth: true`, which the account's row shows as signed out. The daemon never speaks a token endpoint; the renewal is the provider's, in the provider's home. The same re-read follows each five-minute limits read, so a token the provider renewed reaches the service that runs on it before the service asks.
- **A pinned session never runs on handed tokens.** A session pinned to an account runs in that account's own service on its own sign-in, where the provider keeps its own login and the request never arrives.
- **Nothing about a refresh is a credential-home lifecycle transition**, so it never bumps `credentialGeneration` (§Account identity and credential generation) and never moves an account's stored health reading. What renews a login is the provider's own code running inside its own home (§Credential-home health observation): the provider keeping its own credential current in the place it keeps it, not a credential this product replaced.
- **Dictation's access token is the one Claude Code credential the app reads.** Dictation needs a Claude Code access token, so the daemon reads it from the account's own store; when it expires within five minutes it is renewed through the account's own reader, under Claude Code's own refresh lock, and never by the daemon. A pasted Claude token dictates too, and is never renewed.

### Selection at run start

- Every provider run resolves exactly one account **before spawn**: the account its saved agent definition or its workflow step pins, where one does, otherwise that provider's current account, the one marked default. Pinning is the only way a run's account is anything but the current one; no client supplies an account per run, and no session surface offers one (§Moving a session to another account).
- The resolved account is **stamped on the run**. It is stamped on the run's admission record as a path-independent server stamp (`admittedProviderAccountId`, [Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)) — never client-suppliable — and persisted through the binding's spawn-bound configuration record so that a resume or crash-relaunch re-realizes **the same account**. A resume MUST NOT silently rebind to a different account; where the original account can no longer be realized, the resume refuses fail-closed rather than paying from an account the caller never chose. The one act that changes a running session's account is the person moving the provider's current account (§Moving a session to another account): the change lands at the session's next request, it is recorded on the session's transcript with the account the run landed on, and the spend splits at the provider's acknowledgment.
- **A workflow step that runs an agent resolves its account by this same rule, and per step rather than per run.** A step's own binding carries either the provider's default — meaning whichever account is marked default **at the moment the run starts**, resolved then rather than frozen when the workflow was authored — or one specific account chosen from the registry's own list, by the identity each provider reports. There is no separate paying-account control and no second account list: an account means nothing until the provider is known, and two controls setting one value can disagree. Resolution happens at **step launch, inside the daemon**, which is what lets two parallel branches of one run resolve different accounts of one provider and park independently against each one's limits; the resolved account is stamped on the step rather than on the run.
- **A step record stores the reference, never the value.** A step's provider parameter carries the account identifier, a credential parameter carries a reference into the secret store rather than a secret, and every value resolved at launch is redacted from logs and from step payloads before either is written. A workflow definition is a document the person may export, import and hand to an agent to author, so a definition that could hold a resolved credential would carry it wherever the definition went.
- Account identity is **spawn-bound state**, so it travels the same data-leg path as the rest of the spawn-bound surface and is re-injected from the durable record on resume rather than re-requested from the client.

### Moving a session to another account

Changing which account a provider's work runs on is an act on the provider surface, not an act inside a session. Pressing an account there, pressing `Set as default`, the control that moves its `Default` mark, or releasing the `Cycle accounts` chord on it makes that account the provider's **current** account, and every running session on that provider that is not pinned to an account moves to it. The chord — `⌥⌘A` by default, rebindable on the Keyboard page like every other — is held rather than pressed: while it is held a small strip lists that provider's saved accounts with a mark on one, each repeat of the key moves the mark, and the account under the mark when the key is released becomes current, so one gesture is one change however many accounts it passed over. On the Providers page the strip belongs to the provider section under focus; on a session screen it belongs to that session's provider. The session surface reports which account a session is on; the composer's `/account <name>` is a shortcut to the same act on that session's provider, and there is no per-session switch: one control setting one fact, on the page that owns the fact.

- **Every unpinned session moves in place, from its next request.** On Claude Code the daemon sends each such session `apply_flag_settings {env: {CLAUDE_SECURESTORAGE_CONFIG_DIR: <the new account's store folder>}}` — a token account's `CLAUDE_CODE_OAUTH_TOKEN` on the same channel — and its next request runs on the new account: between turns the next turn's first request, in the middle of a turn the model call after the step in flight, a running tool finishing and never repeated. On Codex every session that follows the current account runs in the one Codex service the daemon keeps for the current account, on tokens the daemon hands it (§Credential-refresh brokering), and the switch is one `account/login/start {type: "chatgptAuthTokens"}` on that service with the new account's tokens, so every conversation in it uses the new account from its next request, a running command finishing and never repeated. Measured at Codex 0.156.0: a replacement handed in while a 6-second command ran was accepted in 0.025 s, the command ran once, and the next model request went through on the new tokens. Neither leg holds, interrupts, copies, resumes or sends `continue`, and nothing of the conversation is re-sent.
- **A session at a level its new account cannot run moves with the rest at `Ask`.** `Reviewed` on a Claude Code account whose plan lacks auto mode is the case: the session moves like every other and runs at `Ask`, the nearest more careful level, and one row in its flow, written by the app itself, reads `Reviewed isn't available on this Claude Code account`, stored as the `session.notice` kind `level_unavailable` naming the level it left ([Spec-005 §Session Lifecycle](005-session-event-taxonomy-and-audit-log.md#session-lifecycle-session_lifecycle)). The level chip opens the level list as always, so the person picks another; nothing is blocked.
- **The move is the same on every version.** Every installed version switches a session's account in place: no feature checks a version number, and there is no second way to move a session's account. A running tool finishes and is never repeated, nothing is interrupted, and the conversation and its reasoning stay where they are. Before build acceptance a switch is measured onto a real second account on each provider, with the earlier reasoning (Claude Code's signed thinking, Codex's encrypted reasoning) carried across.
- **One faint collapsed row marks it, at the acknowledgment.** The transcript gains `Switched all sessions to <name>`; opened, it names the account it came from, the account it went to and the time; `<name>` is the account as the Providers page lists it — the address the provider reports with the plan where one address holds two accounts, or the name the person gave an account added by a pasted token or API key. An account switch lands at the acknowledgment and draws no waiting slot. Each moved agent's change settles as `agent.provider_binding_changed`, carrying the binding it left and the one it moved to with their accounts, the account the run landed on, `continuity: in_place` and an empty loss list.
- **A move never rewrites a credential, and it runs while the account being left is still valid.** It writes no token, keychain entry or provider login: on Claude Code it points a running process at another account's store, and on Codex it hands the service tokens the provider minted and the daemon holds only in memory. It is something the person does while the old account still works.
- **A dead target refuses in place.** Where the account being moved to cannot be realized (§Validation at spawn — fail-closed), or its last read showed its Claude Code login gone (`rate_limits_available: false` with `subscription_type: null`), the switch is refused before it is sent, the current mark does not move, and the refusal carries the target's own remedy; a target whose login is dead reads `account <name> · login expired · Sign in again` in place.
- **A switch that fails after it was accepted hands the previous account back.** An accepted switch whose login then fails shows as the provider's refusal of the next request, and the daemon hands the previous account back — the previous store on Claude Code, the previous account's tokens on Codex — so the session stays on the account it had. The switch is one transaction to the person: the previous account stays active for that session, no success row is drawn, and one system message lands, `Switch to account <name> failed · login expired · Sign in again`, with `Sign in again` drawn only for a login failure — no banner, toast, dialog or standing error. The agent's change settles as `agent.provider_binding_change_failed` with the attempted binding, the reason `account_unavailable`, and the account's state (`reauth_required`, `home_missing`, `indeterminate` or `not_registered`).
- **The session's cost keeps counting across the move, and the split lands at the acknowledgment.** A turn that spans a switch is charged to both accounts: the spend up to the provider's acknowledgment of the switch stays under the account it ran on, the spend after it goes under the new one, and the session's receipt sums them into the same total (§State And Data Implications, [Spec-014 §The mutation surface](014-multi-agent-orchestration.md#the-mutation-surface)). **The provider's own per-process figure never reaches the screen on either leg** — it is an input the accountant baselines against, not a number the person is shown, and showing it would make a session look as though its spend had reset.
- **Pinned means pinned.** A saved agent definition or a workflow step set to a specific account stays on that account when the provider's current account moves ([Spec-026](026-agent-definitions-and-peer-invocation.md), [Spec-015](015-workflow-authoring-and-execution.md)); on Codex it runs in that account's own service on its own sign-in. New sessions start on the current account.
- **A relaunch applies the same rule.** An unpinned session the daemon brings back after a restart, whose provider's current account is by then another one, moves like any other unpinned session, from its next request.

### Validation at spawn — fail-closed

- Before a provider process is spawned against an account, the daemon MUST validate that the account is registered and that its credential home exists.
- Any other outcome **refuses the run before spawn**. A missing home and an unregistered account are refusals, never fallbacks: falling back to the default account or to the person's ambient configuration would silently bill the wrong account.
- **No sign-in check runs before a session starts.** The provider is started and signs in on its own; a sign-in that has failed shows as the provider's own refusal on the run. The one refusal on the account's sign-in state is a known-dead target of an account switch (§Moving a session to another account).
- The driver contract's authentication probe is **required of every driver and is not capability-gated** — that posture is preserved exactly, and this spec adds no authentication capability flag. What it adds is the **scope** of the probe and of the daemon's cached authentication state: both become per-`(driver, account)` rather than per-driver, because a node with two accounts on one provider has two independent authentication states and a single per-driver record cannot represent them.

### Billing mode

- Every account records a **billing mode**: `subscription` (usage is included in a plan the person already pays for), `metered` (usage accrues billed charges per token), or `unknown`.
- Billing mode is declared by the person at registration and may be corrected later; the daemon does not infer it from spend and does not fetch it from a vendor.
- **Every surfaced cost figure attributable to an account carries that account's billing mode.** Subscription-mode usage MUST NOT be presented as billed dollars without the label, and MUST NOT be silently summed with metered spend into a single unlabeled currency total. A total spanning more than one mode states that it does.
- **`unknown` is the honest-absence arm and is never resolved by guessing.** It means the person has not declared how this account bills — not that the account is metered, and not that the figure is zero. A figure attributable to an `unknown`-mode account is labeled as undeclared and is subject to the same prohibition as a subscription figure: it is never presented as billed dollars, and never folded unlabeled into a currency total. The remedy is for the person to correct the mode on the registration, which is why the mode is editable after registration rather than fixed at it.

  This rule is not a stylistic preference; it is the posture the provider itself publishes about its own figure. Anthropic's cost documentation states that the CLI's session cost block "is intended for API users", that subscribers "have usage included in their subscription, so the session cost figure isn't relevant for billing purposes", and — on the provenance of the number — that the figure is computed locally "from token counts priced at standard list rates", does not reflect promotional or contracted pricing, and "may differ from your actual bill" ([Claude Code costs](https://code.claude.com/docs/en/costs), accessed 2026-08-18; **Documented**). A locally-derived, list-rate figure presented as a subscriber's bill is wrong in the way the vendor explicitly warns about, and this spec's labeling requirement is what keeps that presentation from occurring. The same provenance caveat is why a cost figure is a **spend estimate for this node's usage**, never a statement about the person's invoice, on either billing mode.

- **A figure that spans more than one billing mode says so.** Where a surface totals spend across the person's accounts, that total states that it spans more than one mode rather than presenting one currency figure over accounts that do not bill alike. Per account the figure is carried with that account's own mode; across accounts the reading is the modes it covers, not an average of them. This is the positive half of the prohibition above: the rule bars an unlabeled sum, and this says what a labeled one looks like.
- Billing mode is **presentation and labeling only**. It is never an input to budget enforcement: the committed-spend fold ([Spec-014 §Cost Figure Display Consistency](014-multi-agent-orchestration.md#cost-figure-display-consistency)) enforces the same ceiling arithmetic regardless of mode, for the same reason enforcement must not branch on cost provenance — one ceiling, no dual trust regimes.

### Provider quota is account-scoped

- A provider quota snapshot describes **an account's** standing with its provider, not a session's and not the node's. It spans every session that account's runs touch.
- The account-scoped quota event therefore **carries the account it describes** (`providerAccountId`, plus the credential generation observed with it). Without that identifier a consumer on a multi-account node could not attribute a snapshot to an account at all, which is what makes it part of the event rather than context a reader is expected to supply.
- **An account's numbers live on the account surface and nowhere else, and no second usage screen is added beside it.** An account's quota standing and its spend are properties of the account, so the surface that lists accounts is where they are read. No session-scoped surface carries an account's quota windows or an account-wide spend figure: what a session shows is its own context reading and the spend attributable to its own work, which are different facts about a different subject, and putting an account's standing on a session surface would invite a reader to act on one session's figure as though it bounded the account. Spend and tokens **by day and by model** are drawn on the account surface, per account and summed across a provider's accounts, because the durable per-turn usage table those slices are group-bys over is what the accountant keeps (§State And Data Implications).
- **A share of a limit is never summed across accounts, and what a provider's own line carries instead is its tightest account.** A limit belongs to one account, so adding two accounts' shares would describe an allowance neither of them has. Across a provider's accounts the surface names the account standing closest to one of its limits — that account's own identity, the limit, and the share of it used — beside the tokens and spend that are summed over that provider's rows (§State And Data Implications). Tokens and spend add up because they are consumption; a percentage of an allowance does not.
- The typed provider-limit signal the drivers normalize refusals into ([Spec-004 §Fallback Behavior](004-provider-driver-contract-and-capabilities.md#fallback-behavior)) is likewise account-scoped, and its consumers key on `(accountId, credentialGeneration)`.

### Credential-home health observation

The registry's stored reading is only as useful as it is fresh. A pull-on-read model — written by the deliberate probe verb alone — would leave a node the person never probed and never ran anything on serving a reading taken once and never revisited, and would leave an account nobody has used for weeks quietly signed out. A background observer therefore keeps every registered account's reading and its login current, and this subsection states precisely what it may and may not do.

- The observer is **homed in this spec's own plane**, not in [Spec-004](004-provider-driver-contract-and-capabilities.md)'s capability-refresh cadence. The two are different subjects — that one refreshes a driver's declared capabilities, this one observes an account's credential state — and CP-023-1 already places the per-`(driver, account)` scoping of cached authentication state on the driver-contract side. Nothing in Spec-004's contract is widened here.
- It runs **per registered account** on a fixed cadence, **default-on**, with a durable **per-account opt-out** so the person can silence an account they are not using without deregistering it. The schedule is durable rather than an in-memory timer, so a daemon restart does not silently stop observing.
- **The observer reads with the provider's own code, inside the account's own home, and never touches a token itself.** The prohibition on calling a path documented to refresh proactively is **scoped to a shared home** and does not reach a per-account home. Its whole reason was a race between the daemon and the person's own CLI holding one grant, and that race cannot occur in a directory the person's CLI never opens: an account's home is daemon-owned, addressed by the reserved variable, and is never `~/.claude` or `~/.codex` (§Credential homes and the constructed environment). What stays prohibited is the real constraint: the daemon MUST NOT read, write, copy or transport credential material beyond the moves [ADR-026](../decisions/026-provider-credential-custody-posture.md) names (§Credential-refresh brokering, §Credential homes and the constructed environment), and MUST NOT speak a provider's token endpoint itself. Renewal is the provider's own code running inside its own home, caused by asking that home a question it answers with a signed call.
- **What it reads is each provider's own limits surface, and neither read costs a model turn.** On the Codex leg the account-scoped rate-limit read (`account/rateLimits/read` with `excludeResetCreditDetails: true`, the flag the vendor's own comment scopes to background usage polls), sent to the account's own service or, when none runs, to a short-lived `codex app-server` in the account's home, returns every limit bucket for that account. On the Claude leg the `get_usage` control request is sent by a fresh short-lived reader on the account's own store, **before any turn is sent**, and returns the short window, the weekly window and the weekly window per model before the reader exits. Both are measured on the pinned builds to answer with no model call and no spend ([Provider Wire Reference §claude](../reference/provider-wire/claude.md), [§codex](../reference/provider-wire/codex.md)). The one account read by a turn is a pasted Claude token, which has no `get_usage` read (§Non-interactive token registration); a Codex API-key account is not read at all.
- **On the Codex leg the read renews the login as a side effect, and that is the intent rather than a cost.** The read's own handler resolves the account's authentication first, and that resolution is where the provider applies its own renewal rule — within minutes of the short token's expiry, or when its last renewal is older than its own multi-day threshold. So one call both returns the limits and keeps the login alive, and an account nobody has used for weeks is still signed in. The rotation it spends is the provider's own, taken by the provider, inside the provider's own home, under the provider's own guard: before renewing it re-reads its file under its lock and skips when another process already renewed (§Concurrency Posture).
- **Every account is read every five minutes, at all times**, whether or not the provider surface is open. Claude Code's readers run one at a time, staggered across the five minutes. `Check now` runs the same read at once when the account's last read is at least 60 seconds old and otherwise answers the last read; the 60-second floor is the daemon's, and the page runs no timer of its own. When the Claude Code usage endpoint refuses a read in-band the answer carries `rate_limits: null` beside `rate_limits_available: true`, which is a refused read and never a zero: the account's last turn-delivered figures stand with their time and the row says `from its last turn`. A read the provider throttles or refuses is held per account on a durable ladder — ten minutes, twenty, forty, then an hour — that survives a daemon restart, and while the hold lasts the probe verb answers with the wait rather than retrying; after the second refused read in a row the row reads `Cannot tell right now`. **A dead Claude Code login is told from a throttle by the read's own answer**: a refresh the server refused leaves the account's store blank, and the read answers `rate_limits_available: false` with `subscription_type: null`, so the row reads `Login expired · Sign in again` at once, with no ladder wait, and the account is refused as a switch target. An access token the server revoked before its expiry reads like a throttle, so each reader writes the provider's debug file in its throwaway folder, and a bootstrap or profile 401 there before a fieldless answer makes the row read `Cannot tell right now` at once. Single-flight per account, and **never while a turn is live on that account** — the read reaches the provider rather than the filesystem, and a live turn brings its own figures (below).
- **A turn on any session refreshes that account's limits at once, without waiting for the cadence.** On the Codex leg the provider pushes its own rolling update with the turn (`account/rateLimits/updated`, the push half of the same surface the pull reads), so the daemon has only to record what arrives. On the Claude leg the turn's own closing `rate_limit_event` names both windows, and at the turn's end the daemon runs the account's own reader, never the session's process, so a session's process only ever runs its own turns. The daemon normalizes the shapes the provider uses — the event's fraction and epoch seconds, the read's percentage and ISO time — to one, and a turn-end read restarts the account's five-minute timer.
- **An account whose freshness is switched off is read on neither cadence, and the deliberate probe still reads it.** The per-account opt-out stops every automatic read of that account — the background cadence and the while-the-surface-is-open cadence alike — without signing it out; the probe verb is the person asking, and it always answers.
- **The local, no-network read stays, for the state a limits read does not report.** `claude auth status --json` on the Claude leg and the account read with refresh suppressed on the Codex leg both perform no network call and renew nothing; they are what reports which authentication mode a home is in, and what answers at all when the machine is offline. The two reads are different instruments for different facts and neither stands in for the other.
- **A renewal the provider performs inside its own home is not a credential-home lifecycle transition.** It does not bump `credentialGeneration` (§Account identity and credential generation). A generation bump marks every quota reading before it as predating a change, and a routine renewal changed nothing the person or a consumer needs told about — bumping on it would stale every stored window, many times a day, for nothing. What it does move is the row's **last observed credential-refresh time**, which is the field this observation finally has a writer for.
- **The moment a window resets, the daemon spends one smallest turn on that account so the new window's clock starts then.** A provider counts a window from the first message in it, so while nobody is working the clock stands still and the reset the person is waiting for arrives later than it had to. At each window's reset the daemon sends one short line to the smallest model in that provider's own catalog — `haiku` on the Claude leg — in a **throwaway process in that account's own credential home, outside every session**, and keeps nothing of it. On Claude Code it starts the five-hour window only; on Codex it starts every closed window of the bucket the turn billed, the bucket named by the turn's own `account/rateLimits/updated`. A window is closed when its reset time is past or absent, and one turn is sent per closed window, at its reset timer, at daemon start, at sign-in, at wake and at any read that shows it; a started window reads as a future reset time within five hours of the send. The turn on Claude Code is `claude -p --model haiku` with no tools and thinking off, on the account's store with a throwaway configuration folder, in an empty folder outside any project; on Codex it is `codex exec` in the account's home on the smallest model that bills the bucket. It carries **its own per-account switch, on by default, which sits under the freshness opt-out rather than beside it**: switching it off leaves the limits read running on its cadence, and switching the freshness opt-out off stops the window start as well, so it never runs while that opt-out is off.
- **The limits read starts no window; the window start spends exactly one turn per window.** The two are deliberately different acts: the read is the one that must cost nothing, and this is the one that must cost something, because a window that has not been spent in has not begun. That turn lands in the per-turn usage table like any other, under the account that paid for it and with no session to attribute it to (§State And Data Implications), and it is drawn only where every turn is drawn — in that account's tokens for the day and the week, and in its spend where the provider reports a cost — never as a row of its own. Nothing announces the start: the limit row carries the new window's reset time at the next read.
- **A window that resets while the machine sleeps starts at the reset only if the machine is woken for it.** Under the window-start switch sits one more per-account switch, `Wake this computer for it`, off by default and off with its parent. On macOS and Linux turning it on installs a small helper, asking once for an administrator password: the first account turned on installs it and the last one turned off uninstalls it, and a helper that did not install leaves the switch off and reads `The helper was not installed: <reason>.` The helper does one thing: it takes a wake time from this person's background service, at most eight days ahead, and schedules the machine to wake one minute before it; it holds no account, token or setting, and runs nothing else. On macOS it is a launchd daemon registered through `SMAppService` that calls `IOPMSchedulePowerEvent`; on Linux a system service that sets a systemd timer with `WakeSystem=true`. On Windows the service schedules the wake itself with `SetWaitableTimer`, which needs no privilege, so there is no helper. Asleep with the switch off, the window starts at the wake.
- **A read that cannot be taken changes no reading and says so.** Where the machine is offline or the provider does not answer, the account keeps its last reading with the time it was taken, or `from its last turn · <time>` where its figures came from the account's own last turn, and after the second refused read in a row the row reads `Cannot tell right now`. No bar moves, no window is dropped, and nothing reads as zero used — an empty meter is a claim about an allowance the daemon did not observe.
- **The honest residual, stated rather than papered over.** The limits read establishes that the account's credential was accepted by the provider at the moment of the read, which is more than a local read establishes and still not a standing guarantee. A credential revoked between two reads reads as authenticated until the next read, a run, or a deliberate probe finds otherwise, and the surface carries **when the reading was taken** rather than presenting it as now (§Per-limit provider quota). What the read cannot do on the Claude leg is extend the login's own horizon: the vendor documents that only an interactive sign-in renews that, and its own status read carries no expiry field. So a Claude account asks to be signed in again at its horizon whatever the observer does, and the design's job is that the person hears it from the provider surface with a one-press sign-in beside it — `Login expired · Sign in again`, from the structured authentication failure the read returns — and never from a session that died.
- The observer is a **third writer of the stored pair** — joining the deliberate probe verb and the registration-time status invocation — under the same rule the contract registry already states: the row records observations, and every validation that actually observes an account's authentication state writes it back. **The generation-bump authority is not widened.** `credentialGeneration` still bumps only on the credential-home lifecycle transitions §Account identity and credential generation names, so a background observation is never by itself a lifecycle transition. This matters concretely: a transient observation failure that bumped the generation would mark every stored quota reading as predating a change that never happened.
- Observation is **excluded against the account's own live work** and is single-flight per account: at most one observation per account at a time, and none while that account's credential home is being reset or a brokered sign-in is in flight against it.

- **The account row warns before a login expires, and reads no credential to do it.** `Login expires in about N days` is drawn from seven days out, warning-colored from three, from the sign-in moment the broker recorded plus the provider's login horizon. On Claude Code the horizon is 30 days from the sign-in: the CLI fixes the refresh token's lifetime at sign-in from the token response's `refresh_token_expires_in`, the provider's server caps the login there, and a refresh does not extend it. On Codex the access token lasts 240 hours and Codex renews it, rotating the refresh token, only once it is eight days old, which the five-minute read brings about, so a read costs no rotation; a Codex row has no fixed horizon and no sign-in expectation, and warns only when a read comes back refused. A token account has no refresh age and no sign-in expectation.
- **The account row draws ages, never countdowns**: when the account was last checked, when its credential was last seen refreshed, and how long its sign-in is expected to last, the last marked as an expectation. The one exception is `Login expires in about N days`, from seven days out and in the warning color from three.

### Per-limit provider quota

- An account's quota standing is **not one window**. The pinned Claude surface publishes several distinct limits at one time, **more than one of them over the same window length** ([Provider Wire Reference §claude](../reference/provider-wire/claude.md)), so a key of `(account, window length)` cannot hold them: one would overwrite another, and which survived would depend on arrival order.
- Quota readings are therefore keyed by **`(account, limit identifier)`**, with the window length carried as a property of the reading rather than as part of its key. A reading that names no limit identifier is the provider's single unnamed limit and takes the reserved identifier `default`, so a provider publishing one window needs no special case and the single-window shape is valid as the degenerate case.
- **Each leg's identifier is read from the carrier the provider actually populates.** On the Claude leg the windows come from the `get_usage` reply's `limits[]` list: each entry carries its own kind and, where it is scoped to a model, that model's **display name**, and the identifier is those two together — the per-model weekly window for one model is a different limit from the per-model weekly window for another, and from the account-wide weekly window over the same length. The flat per-model keys beside that list (`seven_day_opus`, `seven_day_sonnet`) **answer null and are not read**; a design keyed on them would render an empty per-model window for an account with real per-model usage. On the Codex leg the windows come from the reply's `rateLimitsByLimitId` map, whose keys are the provider's own metered limit identifiers.
- **A window is classified by its length in minutes, never by its position in the reply.** Each Codex limit identifier carries a primary and a secondary window, and the provider has moved a given window between those two positions; a reader that called the primary slot "the short window" would relabel every bar the day that moved. The reading carries the length the provider reported and the surface names the window from it. This is not in tension with the key above: the **key** is the limit identifier, and the **label** is read from the length — keying on the length is what collapses two limits into one, and reading a position as a meaning is what mislabels one.
- **Every reading carries when it was taken, and the surface shows it.** A percentage with no read time invites the person to plan against a number that may be hours old, and on an idle account it will be. The read time stands in words beside the reading — `read 7:24 PM` — on every window; an account with no reading yet reads `Not read yet` with no bar at all; and a reading the daemon could not refresh keeps its figure and its read time, or reads `from its last turn · <time>` where its figures came from the account's own last turn (§Credential-home health observation).
- **A window whose figure came from the account's own last turn says so where its read time would stand.** One pinned provider records its limit standing into the conversation file it writes as a turn runs. Where an account has had no read of its own since — an idle account between cadences is the case — that window stands in its usual place with that figure, carrying the time of the turn that produced it and saying it came from that turn rather than from a read, so it is never presented as current. It is **not written into the registry**: the two sanctioned sources below stay the only writers of what the account's stored set holds, exactly as a vendor's own usage figure is shown without being folded into this plane's own table (§State And Data Implications).
- **A whole-account read marks itself complete, so a sparse push never prunes what it does not mention.** The deliberate probe and the observer's limits read both return every window the account has, and a reading set marked complete replaces the account's stored set. The providers' pushed updates are explicitly **sparse** — they carry the windows that moved and no others — so a pushed set is merged into the stored one and never treated as the whole truth. Without the distinction one sparse push would delete every window it happened not to name.
- The newest reading per key is held durably per account, and **the registry read is what delivers it**: `providerAccount.list` returns the stored windows alongside the accounts, so a client that connects after a reading was taken — or after a daemon restart — renders quota standing immediately instead of waiting for the next probe or run to produce one. The subscription remains a live tail and deliberately sends no catch-up; the read is the snapshot. Durability is what makes an account's quota visible on a node that has not run anything since restart. **A stored reading keeps the provenance it was observed under**: because the durable row is fed by both sanctioned sources, a window served from the registry may carry `source: 'run'` just as legitimately as `source: 'probe'`. Provenance is a property of the reading, not of the transport that delivers it, so a consumer must accept both values on a stored snapshot and must not infer provenance from the fact that a reading arrived on a read rather than on an event.
- **Newest wins, by observation time — except that a same-window reading never moves backward.** Where two readings key alike, the one with the later observation timestamp is current, and the source of the reading breaks ties only when the timestamps are equal. **The one exception is the same-window high-water guard**, which is the existing consumer rule and is retained here rather than contradicted: when the incoming reading matches the stored one on both `limitId` and `resetsAt`, a **lower** `usedPercent` is dropped, because usage rises monotonically inside one window. Without the guard a single erroneous or out-of-order low reading would overwrite the durable row and present a 90%-consumed account to a reconnecting client as 20%-consumed — the durability of one row per key is exactly what makes the unguarded overwrite destructive. Ordering by anything else — arrival, or a preference for one source — would let a stale reading mask real consumption.
- **A credential-home rebuild neither clears nor invalidates a reading, and deregistering the account takes every reading with it.** The two dispositions differ because the two facts differ: a quota window describes the **provider-side allowance**, which keeps running while a home sits empty and which the person re-authenticates back into, so discarding the readings would destroy the pacing evidence the rebuild's own remedy depends on — whereas a reading has no meaning at all without the account it was read for. Each reading therefore records the credential generation it was observed under, exactly as the account-scoped quota event already carries one, and a reading whose generation is behind the account's current generation is rendered **stale rather than current**. This is the boundary between the two stored observations: a generation bump **invalidates** the stored health reading, which describes the home, and merely **ages** a quota reading, which does not.
- **A reading is delivered as three facts, and each is readable without a meter.** Every window carries the provider's own label for that limit, the share of it used, and when it resets. A surface may draw a meter, but nothing about a quota is legible only from a meter's length: the share and the reset time stand in words beside it, because a bar has no accessible reading of its own and a figure a reader cannot state is a figure they cannot act on.
- **A window that has reset reads as reset, not as its old figure.** The newest reading after a reset is the reset one, and a surface shows it as reset rather than holding the pre-reset share until something else moves. Together with the newest-wins rule above this closes both directions: a stale high reading never survives a reset, and a reset reading never loses to the older high one.
- **A reading taken before the account's credential generation changed is presented as predating it.** The reading itself survives the change — a provider-side allowance is not reset by a local credential rebuild, as the disposition rule below states — but it was observed under a generation that is over, so it is carried with that fact rather than as a current reading. A surface that showed it as current would invite the person to plan against an allowance nothing has re-observed.
- **An account whose quota could not be read says so, and shows no meter.** An unreadable reading is not zero used: an empty meter is a claim about the allowance, and a surface that drew one would report a full allowance the daemon never observed. The absence is stated in words in the meter's place.
- Quota readings reach the registry from **two sanctioned sources**: the account-scoped quota event carrying what a provider pushed during real traffic, and the deliberate limits read. The background health observer performs **that same limits read on its cadence** rather than a third kind of read (§Credential-home health observation), so it adds a caller and not a provenance: a reading it took is recorded under the same provenance the person's own press produces. The two sources differ in completeness as well as in provenance, which is what the complete-set rule above turns on: a limits read describes an account's whole standing, and a pushed frame describes the windows that moved.

### Node provider readiness and the sign-in handoff

Readiness answers, ahead of any run, the question run admission will ask: **would a provider run for this provider be admitted on this node right now?** It exists because a node on which nobody has authenticated is otherwise indistinguishable from a healthy one until the first run refuses.

- **Readiness is a derivation of the registry, never a second source of truth.** Per provider it is computed by the same resolution §Selection at run start performs — resolve that provider's default account, then read that account's **stored health state** — and it is reported in the same vocabulary: two registry-shape arms mirroring the two resolution refusals (no account registered; accounts registered with no default), otherwise the resolved account's stored health state **verbatim**. The arm count is therefore not a design choice but a consequence: the health vocabulary's arms plus those two, and it widens only when one of them does. No other surface recomputes it. Two derivations of one predicate eventually disagree, and the one the person is looking at is the one enforcing nothing.
- **Readiness is served from the stored observation, not from a fresh one.** What the registry row holds is the **stored outcome of the last validation** — the authentication probe's reading together with the credential-home observation taken at that same moment, which is exactly what the account's health state names. That distinction is load-bearing rather than pedantic: a missing-home reading is not something an authentication probe returns, so calling the stored value "the last probe result" would imply a live filesystem check at read time. There is none. Readiness reads the row, reports **when** that observation was taken, and performs no process spawn, no filesystem test, and no credential read of its own — so a surface may poll it. **Every validation that observes an account's authentication state writes the pair back**, and that set is exactly **three**: the deliberate per-account probe verb, the **registration-time status invocation** §Non-interactive token registration performs (on first registration and again on re-supply), and the background health observer §Credential-home health observation homes. Nothing else writes it, and none of the three is optional — a stored value that recorded only _explicit probes_ would leave a node nobody probed serving `indeterminate` forever while every run started fine, which is the same lie in the opposite direction from the one this section exists to prevent. The probe verb applies §Account identity and credential generation's boundary rule in the same transaction as the health write, so a repaired or destroyed credential starts its new generation exactly when the observation that establishes it is recorded. The registration-time invocation establishes an account's **first** reading rather than crossing a boundary — at first registration the row is born at generation 1, and on re-supply the replacement has already bumped — so it writes the pair with no bump of its own. The observer deliberately does not either: it writes the reading and never bumps the generation, because marking every reading as predating a change on a transient fault is the harm that rule exists to produce only when a home genuinely changed. Readiness itself never writes: it is a reader of what they wrote. The **read path applies no age test and has no `stale` arm**: the staleness ceiling in §Implementation Notes binds the probe caller's refresh obligation, not the reader, and the observation timestamp travels on the reply precisely so a caller may apply its own. Adding a read-path age test would be a second predicate — the thing this section exists to prevent — and would make a surface's rendering depend on when it happened to look.
- **Readiness authorizes nothing.** It is advisory. A ready reading is a statement about the last observation, not a grant; a session starts whatever readiness last reported, and a sign-in that has failed shows as the provider's own refusal (§Validation at spawn — fail-closed).
- **No surface reports a provider as authenticated on any reading other than the authenticated arm.** An `indeterminate` probe is not authenticated — and is not a sign-in failure either: it means the probe could not decide, and it is rendered as undetermined. The same rule bars manufacturing an authenticated claim out of a plan label, a subscription echo, a declared billing mode, or the existence of a home directory: none of those is evidence of a usable credential, and treating one as evidence produces a surface that tells the person everything is fine while admission refuses.
- **Detection is credential-free and never authenticates.** Deriving readiness reads registry rows and the driver contract's existing zero-turn authentication probe. It never opens, parses, copies, or transmits credential material; it never computes a keychain entry name; and it never runs a provider sign-in command. The daemon does not sign the person in as a side effect of looking.
- **The handoff discloses the remedy and stops.** On any non-authenticated arm the surface names what the person must do. That is **several different actions, not one**, and the surface names the one that applies and no other: with nothing registered, register; with accounts registered and none default, choose a default — the daemon lists the candidates and refuses to elect one, because electing one would bind a run's spend to an account the person never chose; with an account resolved whose credential home holds no credential at all, sign in against **that account's own home** to put one back in it; with an account resolved whose credential has stopped being accepted and whose **observed authentication mode is interactive**, the provider's own first-party sign-in against that account's home; and with one whose observed mode is the **non-interactive token** class, mint a fresh token at the provider and supply it, because such an account **cannot refresh itself** — so its remedy is never a retry and never a refresh, and the interactive remedy is never drawn on it. **The remedy is chosen by the account's observed mode, never offered as a menu**: a person shown both remedies would try the one that cannot work. Only an arm that has resolved an account names a home, because only such an arm has one. The surface then hands the person into that flow. Guidance naming a command or a filesystem location travels **in message text for the person only: never in an event payload, never in anything the control plane can read, and never in a log line**. The client **displays** the invocation; it never executes it on the person's behalf.
- **A refusal names the fault; readiness names the remedy.** A run refused on the account plane carries its typed refusal code and nothing more — the remedy is deliberately **not** copied onto the refusal, because a refusal envelope travels wherever errors travel and the disclosure rule below bars a credential home from every one of those places. A client that wants to offer the remedy after a refusal therefore **routes on the typed code and then reads readiness** for the provider concerned, on the same device-authorized surface that composes it. This is not an extra hop grudgingly accepted: the refusal is a fact about one dispatch, readiness is the node's current state, and reading the second is what makes the offered remedy current rather than a snapshot of the moment something failed. Where the refused run was pinned to an account by its saved agent definition or its workflow step, the remedy the person needs concerns **that** account, which the provider-default projection may not describe — the default may be perfectly healthy while the pinned account is the one signed out, and handing the person a remedy for an account that is not broken is worse than handing them none. The readiness read is therefore **account-scopable**: a caller may pin the derivation to one named account instead of the provider's default, and the post-refusal path pins it to the account the refusal names whenever it names one. Pinning to an account that no longer exists refuses on the already-registered unknown-account code rather than falling back to the default, since a silent fallback is how the wrong-account remedy would come back.
- **The remedy travels on the readiness entry that obliges it, and nowhere else.** A surface required to display the remedy must be able to obtain it, and the only surface that can compose it correctly is the daemon: it alone knows which account resolution reached and which home that account holds. So the remedy rides the readiness entry, and the schema holds the rule: it refuses a non-authenticated entry without the remedy its state calls for, and an authenticated entry that carries one. It is deliberately **not** a second RPC: a client that had to make one would render a state and a remedy fetched at two different moments, and the pair could disagree. Two consequences follow and are binding. First, the remedy is **derived at composition time and never stored**: no column holds it, so it cannot go stale against the row it describes. Second, the message-text-only rule above is what governs it — the remedy is message text for the person that happens to travel structured, so the same prohibition applies unchanged: it does not reach an event payload, anything the control plane can read, or a log line, and no refusal or telemetry surface echoes it. A registry read is answered only to this machine's own client or to a linked device inside its Noise channel, so what it discloses reaches only the person's own devices.
- **No surface offers a credential refresh, and a refresh is visible only as a time moving.** Renewing a login is the provider's own code running inside that account's own home, brought about by the limits read (§Credential-home health observation), and the only trace it leaves on a surface is the account's last-observed-refresh time moving. A refresh the provider itself asks the daemon for is answered from the provider's own renewal (§Credential-refresh brokering), so nothing about it reaches a surface at all. A refresh control would offer an act the person cannot usefully take — the daemon does not mint, exchange or derive credential material — and on a token account it would offer one that cannot exist at all.
- **Provider sign-in output is never surfaced.** Whatever a provider's sign-in process emits may carry OAuth state, PKCE values, or credential fields. It is not placed in an error payload, an event, or a log. A refusal reports that sign-in did not complete — not what the provider printed.
- **An honest limit, stated rather than papered over.** A credential-free probe reports what the provider CLI says about itself, and a signed-out first-party CLI can report a shape indistinguishable from a healthy account whose stored credential has since been destroyed. Readiness therefore **cannot promise a usable credential**: the authenticated arm is necessary, not sufficient. The compensating controls are the ones already specified — the provider's own refusal at run start (§Validation at spawn — fail-closed) and the per-account re-authentication remedy (§Fallback Behavior) — not a stronger predicate. Readiness must not be strengthened by reading credential bytes to break the tie: the bounded-custody posture (§Non-Goals) is not tradeable for a better banner — bounded custody admits one named input, not a credential read on this path.
- **A path is a hint, never a state.** Where a surface mentions the person's ambient configuration directory it does so from path existence alone, labels it a hint, and never renders it as an authentication state — on platforms where provider credentials live in an OS keychain the path carries no signal at all. Ambient configuration is never inherited, copied, or adopted as an account's home (§Credential homes and the constructed environment).
- **The provider's command is found in a fixed order.** `Auto-detect` looks on the service's own PATH, then the login shell's PATH, then where each provider's own installer puts its command: Claude Code `~/.local/bin/claude` (`%USERPROFILE%\.local\bin\claude.exe` on Windows), Codex `~/.local/bin/codex` (`%LOCALAPPDATA%\Programs\OpenAI\Codex\bin\codex.exe`). In a WSL distribution a command found under the Windows drive mounts is ignored, because a Windows `claude` or `node` reached through `appendWindowsPath` fails with Claude Code's documented `exec: node: not found`. After an install the service reads the login shell's environment again, because Claude Code's installer adds its folder to no PATH on macOS. A change to the command re-checks it where it now points and re-reads that provider's model catalog.
- **A missing provider installs with one press, on every platform, where the service runs.** `Install` runs the provider's own documented installer once, as the person, with no administrator step, no terminal and no input: it runs in a session of its own with its input empty — Codex's with `CODEX_NON_INTERACTIVE=1` — so a question an installer would ask goes unanswered and never waits; it has no time limit of the app's own, the installer's own timeouts bound it, and `Cancel` stops it and everything it started without undoing what it already wrote. The installers are each vendor's own, and none asks for an administrator: Claude Code's `curl -fsSL https://claude.ai/install.sh | bash` on macOS and Linux and `irm https://claude.ai/install.ps1 | iex` on Windows; Codex's `curl -fsSL https://chatgpt.com/codex/install.sh | sh` and `powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"`. The commands live in one table beside the provider check, and the same command is what a failure shows. While it runs the row reads `Installing Claude Code…` with `Cancel`. A failure reads `Claude Code did not install: <the installer's own reason>`, the reason trimmed to its last lines with anything shaped like a credential removed, and the command under it as text to run by hand. On a WSL computer it runs inside the distribution the service uses.
- **The service keeps each provider current itself, on the person's own install.** At its start and then every 10 minutes it reads that provider's latest-version marker, a request that carries the last answer's tag, so an unchanged marker sends back no body: Claude Code's channel, `https://downloads.claude.ai/claude-code-releases/<channel>`, on the channel the person's own `autoUpdatesChannel` names, `latest` unless it says `stable`; Codex's `https://releases.openai.com/codex/channels/latest`; and a Homebrew install's own cask. When the marker names a build the provider's command does not resolve to, and the service has not tried that build since it started, it runs the provider's own update command from the same table as the install: `claude update`, `codex update`, or the package manager's own upgrade, such as `brew upgrade --cask claude-code` or `winget upgrade Anthropic.ClaudeCode`. It runs as the person, where the service runs, with no terminal and no input, in the login shell's environment and against the person's own provider configuration: never against an account's home, under which `codex update` cannot find its install and `claude update` follows that folder's channel and writes into it, and never with the opt-outs a driver-spawned child carries. On an apt, dnf or apk install, which needs an administrator, the section shows that command instead of running it. The marker only decides whether the provider's command runs: the service downloads and runs nothing the marker names. The result is read from the version the provider's command resolves to afterwards, never from the command's exit status or words, because `claude update` exits 0 when it refuses. A provider the person keeps from updating itself is checked and never updated on the service's own: Claude Code with `DISABLE_AUTOUPDATER` or `DISABLE_UPDATES` set where Claude Code reads it, the `env` block of the person's own settings or of Claude Code's managed settings or the login shell's environment, or with the older `autoUpdates: false`; and a standalone Codex install with no `auto-update-version` file, which its installer writes only for an install that follows the latest release. Its section reads `Update available · <version>`. Each section carries `Update`, which runs the same command at once, and one line with the last result; under `DISABLE_UPDATES` Claude Code refuses that command itself, and the line says so in Claude Code's words. On a standalone Codex install with no `auto-update-version`, `Update` runs Codex's own installer with the newest version named rather than `codex update`, which would set the install to follow the latest release: the installer installs that build and leaves the install off automatic updates, as it leaves every install of a named version ([Codex wire reference §Updating the installed Codex](../reference/provider-wire/codex.md#updating-the-installed-codex)). A run that leaves the provider on its old build keeps `Update available · <version>`, and the last-result line names the failure with its reason. An update made anywhere else, in a terminal or by a package manager, is seen at once by the watch on where the provider's command points, and every open session then moves to the new build by itself ([Spec-011 §Required Behavior](011-transcript-and-reasoning.md#required-behavior)); the service keeps a record of each provider's builds, one per build its command resolved to and one per build the marker names for a provider the person keeps from updating itself, and the bell lists each once ([Spec-017 §The Console's Attention Surfaces](017-notifications-and-attention-model.md#the-consoles-attention-surfaces)). A provider process is always started through the provider's command and never from a recorded path, because an update deletes older builds ([Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior)).
- **State words.** An account whose provider answered that its login is gone reads `Login expired · Sign in again`, whichever way it signed in, with the one remedy that brings it back: the provider's own sign-in against that account's own folder, or a freshly minted token pasted in. `Cannot tell right now` is never collapsed into it: the first means look again, the second means sign in.

### The accounts half of the Providers page

Each provider's section on Settings › Providers ends with the accounts registered against it, under one line: `New sessions run on the account marked Default. A sidekick or a workflow step can be set to a specific account instead.` The words a person reads there:

- **The row.** The identity the provider reports, then the billing chip, then `Default` on the one marked; a token or API-key account reads its name and the credential's kind (`Work · Codex API key`, `Personal · Claude Code token`) with `Rename` on the row, in place, one field, Enter commits, Escape cancels.
- **The state.** `Signed in · checked 3 minutes ago` · `Login expired · Sign in again` · `Cannot tell right now · last checked 12 minutes ago` · `No credential in this account's folder`. Under it, the one remedy that applies and no other: `Sign in against this account's own folder to put a credential back in it.`; `Sign in again through the provider's own sign-in, against this account's own folder.`; on a token account, `This account cannot refresh itself. When the token stops working, mint a new one and paste it here. Mint a fresh token at the provider and paste it below.`; undecided, `Nothing is wrong that can be seen from here. The next check may settle it; pressing Check now asks again.`
- **The ages.** `Last checked 4 minutes ago · last refreshed 3 hours ago · sign-in expected to last until about Oct 12`, and `Not known` where it is unknown; a token account's line has neither `last refreshed` nor a sign-in expectation, and a Codex row has no sign-in expectation.
- **Keeping it fresh.** `Keep this account fresh`, on, under `Read every five minutes, whether or not this page is open. The read asks Claude Code for this account's own limits, spends nothing, signs nothing in and touches no credential.` (the same line naming Codex under Codex), and one more line: `Answering that read lets Claude Code renew its own login, so an account nobody uses stays signed in up to the 30 days a Claude sign-in lasts.` under Claude Code, `Answering that read lets Codex renew its own login, so an account nobody has used for weeks stays signed in.` under Codex. Where the system browser does not open, the line under them reads `Could not open the browser. Copy the address beside it to sign in.`, the address still beside the button. ### Vendor authentication-policy constraints

The handoff above is a handoff, and not a login form, for reasons the vendor publishes. They are recorded here as normative constraints at **Documented** trust grade against the vendor's own policy page:

- **The provider binary runs unmodified.** The policy states that "The Claude Code binary must not be modified". The daemon spawns the vendor CLI as shipped, and patches nothing.
- **No built-in authentication method is removed, disabled, or restricted.** The policy states that customers "may not remove, disable, or restrict any authentication method built into it". A readiness surface therefore does not steer the person toward one authentication method, and billing mode stays a label (§Billing mode) rather than becoming a gate on registration.
- **No credential custody or intermediation.** The policy states that developers "may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow". This is the rule that fixes the shape of provider sign-in: `Sign in` hands off to the provider's own flow and the app never collects what that flow writes; the one credential a person gives the app is a token they minted at the provider themselves. On this plane's wire the statement is bounded rather than absolute: **exactly one input accepts credential material** — the `register` verb's write-only non-interactive-token member — and it takes the one class [ADR-026](../decisions/026-provider-credential-custody-posture.md)'s D2 describes (§Non-Goals). The clause's other half is satisfied structurally by the brokered leg: sign-in **does** complete through the vendor's own flow, in the vendor's unmodified binary, because that is literally what the daemon spawns.
- **The person authenticates with their own credential.** The policy requires that "Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential", billed to that end user. This **restates** the node-local posture already specified rather than adding a new prohibition: accounts and their credential homes are node-local (§Non-Goals, §State And Data Implications), so an account is the credential of the person whose node holds it, and no shared or pooled provider credential exists that could be handed to anyone else.

## Default Behavior

- With exactly one account registered for a provider, that account is the default.
- A run pays from the account its saved agent definition or its workflow step pins, and from the provider's current account where neither pins one.
- Billing mode defaults to `unknown`, and `unknown` is displayed as `unknown` rather than assumed to be either mode.
- A newly registered account's credential generation is 1.
- Account selection is not a session-visible act: the default path emits no approval and no prompt.

## Fallback Behavior

- **No account registered for the provider.** Run admission refuses with a typed refusal naming the provider. V1 does not fall back to the person's ambient credentials — an ambient fallback would make the paying account unknowable and would defeat the receipt.
- **Accounts registered, none marked current.** Refuse. Choosing arbitrarily would bill an account the person did not choose, and the set is not orderable in a way the person would recognize as a choice.
- **Selected account's home missing.** Refuse fail-closed (§Validation at spawn). The person's remedy is re-authentication against that home; the procedure is [Provider Failure Runbook §Provider Re-Authentication (Per Account)](../operations/provider-failure-runbook.md#provider-re-authentication-per-account).
- **Two accounts never share a home.** A shared home is not a permitted fallback under any condition: it is the corruption case the isolation exists to prevent.
- **The person cannot complete a sign-in where they are.** A headless or no-TTY environment, or a host with no reachable browser, cannot complete an in-place browser sign-in. The surface degrades in a stated order rather than refusing outright. **First**, where the provider publishes a device-code arm, the brokered sign-in returns the verification URL and user code and the person completes the flow on any other device — no credential reaches the daemon, and this is the preferred arm on every provider that offers it. **Second**, where the provider publishes no device-code arm, the surface offers the non-interactive token path (§Non-interactive token registration) under ADR-026's D2. **Third**, where neither is available, the surface refuses to prompt, states which provider is not ready, and prints the out-of-band remedy — the account's credential home and the provider's own first-party sign-in invocation — for the person to run where a browser exists. It still does **not** offer a general environment-variable credential override: an unbounded override accepts refresh tokens, session cookies, and interactively-minted credentials indistinguishably from the bounded class, which is the intermediation §Vendor authentication-policy constraints bars and which [ADR-026 §Alternatives, Option D](../decisions/026-provider-credential-custody-posture.md#option-d-general-environment-variable-credential-override-rejected) rejects on that ground.
- **A brokered sign-in is already in flight for this account.** Refuse the second start with a typed refusal naming the in-flight attempt, rather than starting it. At least one pinned provider holds exactly one active login slot and **silently drops the previous attempt** when a new one starts ([Provider Wire Reference §codex](../reference/provider-wire/codex.md)), so a permissive second start would strand a person who is mid-flow on another device with no signal that their code had stopped working.
- **The health observer cannot decide.** Where the observation cannot be taken — the home is unreadable, the provider's own status surface answers nothing usable, or the observation times out — the stored reading is `indeterminate` and is **never** collapsed into `reauth_required`. The two have different remedies: `indeterminate` means look again, `reauth_required` means the person must sign in. Conflating them nags the person through a full sign-in over a transient fault.
- **Provider reports a usage limit.** The run parks on the typed signal rather than consuming a retry ladder, per [Spec-015 §Provider-limit pacing and durable resumption (SA-37)](015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-37); the procedure is [Provider Failure Runbook §Provider Usage-Limit Outage](../operations/provider-failure-runbook.md#provider-usage-limit-outage).

## Concurrency Posture

Running two accounts of one provider **at the same time** is the design intent, and the mechanism that makes it work already exists: on Claude Code one process per session and on Codex one service per account, each bound to one account at a time ([ADR-031](../decisions/031-one-claude-process-per-session-one-codex-service-per-account.md)), and per-account isolated credential homes so no two accounts share a credential file or a lock. A Claude Code session changes account in place at its next request, through `apply_flag_settings {env: {CLAUDE_SECURESTORAGE_CONFIG_DIR}}` pointed at the new account's own store folder, or `CLAUDE_CODE_OAUTH_TOKEN` for a pasted-token account, and its cost splits at the acknowledgment (§Moving a session to another account). Nothing in this spec's own machinery prevents it.

**Two processes of ours on one account's home tolerate each other, and the reason is the provider's own guard rather than anything of ours.** Two Claude Code sessions on one account are two processes in one home, and every Codex conversation on an account runs in that account's one service (ADR-031), so the neighbor a provider has to tolerate inside one home is a second process of its own — a second Claude Code session, or a `codex` the person runs in their own Codex folder beside the daemon's service — and the daemon's own reads add a caller on the observer's cadence. On the Codex leg the provider re-reads its credential file under its own refresh lock **before** renewing and skips its renewal when another process got there first, which is what makes a second process on one home safe rather than merely likely to work. On the Claude leg the vendor documents that a token another session expired or rotated is refreshed and the request retried once. The daemon's own reads are single-flight per account on top of that, and never taken while a turn is live on the account (§Credential-home health observation), so the neighbors are two provider processes and not three. **The residual is narrow and named:** two processes renewing in the same instant, which the Codex guard cannot exclude because it is a re-read and not a mutual exclusion across processes. Where it happens the account's row reads `Login expired · Sign in again`, the registration and every stored reading stay, and the remedy is one press.

**Nothing serializes runs by account.** Runs bound to one account, and runs bound to two accounts of one provider, run at once, as a provider runs many processes on one sign-in. Account selection at run start, one account per run, and per-account isolated homes are normative and unconditional, and a shared home is never the answer to a fault.

Three engineering constraints are why each account keeps its own home, each carried at its honest trust grade and attributed to the vendor that actually states it:

- **Credential-file refresh races — one vendor states the rule, the other is silent, and this spec does not launder the difference.** Codex publishes an imperative prohibition on sharing a credential file across concurrent execution and directs one file per runner or per serialized stream, and documents that a successful refresh writes new tokens back to that file, so a stale copy is superseded ([OpenAI Codex CI/CD authentication](https://learn.chatgpt.com/docs/auth/ci-cd-auth), accessed 2026-08-18; **Documented**). That is a citable, vendor-stated constraint and it is the direct basis for per-account isolation on the Codex leg. **Anthropic publishes no equivalent statement** — no rotation, locking, or concurrency rule appears in the Claude Code authentication or environment-variable references. The identical isolation requirement on the Claude leg is therefore **this project's conservative default**, adopted because the failure it prevents is unrecoverable and the vendor's silence is not evidence of safety. Neither vendor documents a file-locking mechanism; the documented safety model on the one leg that has one is exclusive access, not locking. Isolated homes remove the shared writer, which is the design's whole basis for running accounts at once.
- **Config-home environment variables.** The reserved variables are the only channel by which a process is pointed at a home. If a provider resolves any credential state from a path that ignores that variable — or if a variable's documented effect is scoped to platforms other than the one in use — isolation is incomplete on that leg, and only a measurement against the binary can tell.
- **Keychain entry derivation — documented on both legs, and still a probe.** Where credentials live in an OS keychain, isolation holds only if the entry a provider addresses varies with its configured home, and **both vendors state that it does**: Anthropic documents that the configured home keys the macOS keychain entry to that directory, so a process with a different home reads a different entry, and Codex derives its keyring key from a hash of its canonical home. The measurement on macOS at the pinned build (§Credential homes and the constructed environment) **confirms** that documented property, and the entry name stays undocumented, version-fragile, and not the daemon's to compute (§Pitfalls To Avoid). Observe isolation; never derive it.

Neither vendor ships first-class multi-account support at the pinned versions. Codex's own issue tracker records that the CLI assumes a single account and that swapping the home directory is the acknowledged manual workaround, characterized there as tedious rather than as unsupported ([openai/codex#4432](https://github.com/openai/codex/issues/4432), open, accessed 2026-08-18; **Verified** as to the issue's text and state). That is corroboration for the mechanism this spec builds on — relocating the home is how the ecosystem does multi-account today — and simultaneously the reason the daemon must own the mechanism carefully rather than assume the provider will grow into it.

## Authorization Posture

Account operations are authorized by the device that asks, and never by a session.

- **Every linked device may manage accounts; no session may.** Registering an account, removing one, signing it in or out, setting the provider's current account, and resetting a credential home are open to this machine's own client and to every linked device alike, because a device's trust comes from the account's statement chain and a device that chain does not trust is refused at the channel, before any method runs ([Spec-027](027-remote-control.md)). Over the relay each call travels inside that device's end-to-end Noise channel, so the control plane carries it and cannot read it. No session-scoped authority grants any of these acts, and no Cedar action is minted for them: a session-scoped action would let an agent's call reconfigure the person's paid accounts.
- **The registry read takes the same gate, because of what it discloses.** It discloses every registered account and each one's readiness and remedy (§Node provider readiness and the sign-in handoff), so the read is answered only to a caller the mutating verbs admit — this machine's own client or a linked device — and never to a session-scoped caller or to a local process the daemon does not admit as this machine's client. Over the relay the reply travels inside the device's Noise channel, which is what keeps the remedy's message-text-only discipline whole: the control plane never reads it.
- **Which account pays is chosen on the provider surface, not per run.** A run carries the account its definition or workflow step pins, or the provider's current one, and the daemon resolves it — so there is no per-run selection to authorize and no session-facing account act. Moving the current account is the provider surface's own verb (`providerAccount.setCurrent`) and is authorized there.

The person, from any of their devices, decides which accounts exist and which is current; a run takes the account its definition pins or the provider's current one.

## Interfaces And Contracts

- A node-local `providerAccount` wire namespace carries registry read and mutation, current-account selection, and the per-account authentication probe. Concrete method names and payload shapes are registered in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md); run creation carries no account member.
- **Billing mode is correctable in place, and so is the name of an account added by a pasted token or API key**; the name travels as `displayLabel`, present only on those accounts, and account names are trimmed and compared by full Unicode case folding (`foldName`). A correction is a plain registry write: it does not touch the credential home, is not a credential-home lifecycle transition, and therefore does not bump `credentialGeneration`. Account identity — the address, plan and organization the provider itself reports — the account's provider, and its credential-home path are **not** correctable, because each of those is what historical spend is keyed to or resolved through, and none of them is this product's to author. The correction path is required rather than convenient: since account identity is immutable and never re-derivable, a person who could not correct a mis-declared billing mode would have to remove and re-register, minting a new identity and orphaning that account's spend history — so its absence would silently push the person into destroying their own cost record. It is also the mechanism the `unknown` billing mode is resolved through. The provider-reported identity fields are refreshed from the provider's own reading rather than edited, and their retention and erasure obligations are recorded in [Spec-020 §PII Data Map](020-data-retention-export-and-deletion.md#pii-data-map).
- Run admission resolves the account from the run's pin or the provider's current account and stamps the result on the run's admission record ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)); it takes no account input from a caller.
- The account-scoped quota event carries account identity and credential generation ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)).
- The driver contract gains account-scoped authentication state and the typed provider-limit signal ([Spec-004 §Fallback Behavior](004-provider-driver-contract-and-capabilities.md#fallback-behavior)).
- The registry read reply carries, beside the accounts, a **per-provider readiness projection**: exactly one entry for each provider the request selects — never zero, never two — derived as §Node provider readiness and the sign-in handoff specifies and served from the stored last-probe result, with the timestamp of that observation. Its state vocabulary is registered in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) and widens only in lockstep with the account health vocabulary it embeds. **The namespace gains no verb**: readiness is an additive member on a reply that already exists.
- The brokered sign-in leg adds a **start** verb, a **cancel** verb, and a read-shaped **subscription** to the same node-local namespace. The subscription carries a wire-only notification and never an `EventEnvelope`, so the registry remains un-evented (§State And Data Implications) and no [Spec-005](005-session-event-taxonomy-and-audit-log.md) type is minted. Start returns the provider's verification material and an opaque attempt identifier; cancel takes that identifier and reports whether an attempt was canceled or none matched.
- The `register` verb gains **one write-only member** carrying the [ADR-026](../decisions/026-provider-credential-custody-posture.md) D2 token class. It appears on no reply, and the namespace's no-credential-payload rule is otherwise unchanged: **exactly one input on this wire accepts credential material, and it is that one**.
- The registry row gains five durable fields — the observed authentication mode, the last observed credential-refresh time, the recorded sign-in time, the per-account observation opt-out, and the per-account window-start switch that sits under it (§Credential-home health observation) — each nullable where absence is honest and never defaulted into a value the daemon has not observed.
- The account-scoped quota event gains an **additive-optional limit identifier**, and the axis re-keys onto it (§Per-limit provider quota). Absent means the reserved `default` identifier, so no existing producer becomes invalid.
- **The namespace carries a sign-out verb, and sign-out is the credential-home reset rather than a registry mutation.** It ends the login the provider's own store holds inside that account's home and does nothing else: the registry row keeps its place, its identity, its billing mode, its quota readings and its spend history, and signing in again signs **that same account** back in rather than registering a second one. It is therefore a credential-home lifecycle transition and **bumps `credentialGeneration`**, which is what marks every quota reading taken before it as predating the change (§Per-limit provider quota). It is deliberately not the removal verb and neither stands in for the other: removal forgets the registry row and leaves the home's bytes untouched, sign-out ends the login and leaves the row. It carries no credential material outward in either direction — the no-credential-payload rule is unchanged — and it is never refused.
- **Setting a provider's current account is one verb on this namespace, and it is the whole of the account switch.** `providerAccount.setCurrent` marks an account current for its provider and, in the same act, moves every running session on that provider that is not pinned to an account (§Moving a session to another account). `Default` on screen, `isDefault` on the wire and `is_default` in the table name the same fact. There is no second verb and no per-session switch verb: the verb's reply names the account that is now current and the sessions the daemon is moving (`movingSessions`), and each session's move settles on that session's own transcript rather than on this reply. An account move writes no pending switch: it lands at the provider's acknowledgment. One control setting one fact is what keeps the two readings from disagreeing — a per-session switch beside a provider-wide current account would let a session sit on an account the provider surface says it is not on. A session's own surface reports which account it is on, and its composer's `/account <name>` calls this same verb (§Moving a session to another account).
- **Copying the person's own ambient memory store into an account's home is a one-time operation the person starts, on the namespace, `providerAccount.memoryImport`.** A person whose provider memory lives in their own ambient provider directory can copy it **once** into a named account's home; the operation reports how many entries it copied, or that there was nothing to copy, and is offered no more for that account afterwards. The row carries `Import memories from <provider> in the terminal` until it has run once; while it runs it reads `Importing…` with the button disabled, then `Imported <n> memories on <date>` where the button stood, or `Nothing to import`, and nothing opens a dialog. On Claude Code the same press copies the person's own agent notes, `~/.claude/agent-memory/<name>/`, into the service's one agent-memory folder, `~/.ai-sidekicks/agent-memory/<name>/`, never overwriting a file that is there, and counts them in the same `Imported <n> memories` line; that folder is shared by every account on purpose, because an agent's notes belong to the agent. The two stores are never joined and nothing is copied back: the ambient directory is the person's and the home is the account's, and a continuing synchronization would make it impossible to say which store a running session read. This is an act by the person on an account's own home rather than a claim of ownership over its bytes — the same boundary §Brokered interactive sign-in draws.
- The account half of the Providers page is the namespace above. Its **provider half is a sibling `provider` root**, provider-level rather than account-level and belonging to no account row, and its verbs are registered in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), and [Plan-023 §Phase 4](../plans/023-provider-accounts-and-credential-homes.md) carries each:
  - `provider.list` — each provider's status (installed, version, and the newer build its latest-version marker names, while there is one) and its own settings. It is live: the list, then each change a `provider.update`, a re-check or an update makes, so a provider whose `Available for new sessions` switch flips reaches the composer's provider rows at once, with no restart.
  - `provider.update` — one setting per press: `commandPath`, `availableForNewSessions`, `helpersAtOnce`, `autoCompactPercent`, `outputStyle`, and `terminalSessionsReachable` (Codex only). A setting left unset reads the value the provider reports at start, except `helpersAtOnce`, whose empty value means no limit (on Codex the daemon passes `features.multi_agent_v2.max_concurrent_threads_per_session` at the largest value Codex accepts) and whose `0` withholds the provider's helper tool; the settings are held in one daemon table and reach the provider as flag settings at each start or mid-session through `apply_flag_settings`, never written to its files, except `outputStyle`, which reaches only sessions started later. The output-style list is read from the installed build (`initialize.available_output_styles`), and a session's own style changes with `/output-style`, which the daemon answers with `apply_flag_settings {outputStyle}` for that session alone and never sends as typed, because Claude Code's own command writes the project's `.claude/settings.local.json`.
  - `provider.probe {provider}` — `Check again`: resolve the command again and re-read its version.
  - `provider.protectedPathList` — the protected paths, each with its source.
  - `provider.standingRuleList` and `provider.standingRuleRevoke` — **the provider's own standing rules**, each in the provider's own words with its scope (an account home or a project) and its source file: Codex's `.rules` files (`rules/default.rules` under each account home and each trusted project's `.codex/rules/`) and Claude Code's `permissions` in its user, project and project-local settings files. A project's rules are listed only while the project is attached: deleting a project, or removing its folder on Runtime, takes its rules out of force in the app, while they stay in the project's own folder in the providers' files. The revoke edits the provider's file, and the provider follows the change as it does on its own: Claude Code from the next tool call, and a loaded Codex conversation keeps the rules it loaded with until it reopens, which is Codex's behavior; the revoke's line reads `Applies from the next tool call.` under Claude Code and `Applies to conversations started after this.` under Codex. The daemon adds nothing over these files — no copy, no hash and no check — and the person or an agent may edit them like any file. The approval card's rules are kept in the same places, and the session inspector's `Rules` reads the same files, with the session's own answers, for one session (`approval.ruleList` and `approval.ruleRevoke`); the daemon keeps no rule store of its own.
  - `provider.terminalPluginUpdate {provider, enabled}` — `Use Sidekicks in terminal Claude Code` (§Non-Goals), off by default, under Claude Code only.
  - `provider.install {provider}`, `provider.installSubscribe` (`running | installed | failed {reason, command}`, its first message the last outcome) and `provider.installStop` — the one-press install (§Node provider readiness and the sign-in handoff).
  - `provider.installUpdate {provider}` and `provider.installUpdateSubscribe` (`running | updated {fromVersion, toVersion} | current {version} | notUpdated {version, reason, command} | needsAdministrator {command}`, its first message each provider's last outcome) — `Update` and the line with the last result, the scheduled run reporting on the same stream (§Node provider readiness and the sign-in handoff). `provider.update` already names the settings write, so the update run is `installUpdate`; it has no stop verb, because `Update` has no `Cancel`.
  - `session.importPreview`, `session.import`, `session.importSubscribe` and `session.importStop` — importing a provider's own existing conversations: counting the projects an import would attach before it runs, starting it, following it (the last outcome per provider, with its failed files, kept until that provider's next import and sent as the stream's first message) and stopping it.
  - `providerAccount.update` gains `windowStartEnabled` and `wakeForWindowStartEnabled`, whose reply carries `wakeHelper: installed | notInstalled {reason}` (§Credential-home health observation); `providerAccount.usageRead` reads tokens and spend by day and by model, with provider totals (§State And Data Implications).
- Refusal codes for the fail-closed paths are registered in [Error Contracts](../architecture/contracts/error-contracts.md).
- Every registry operation and each background read above is recorded by name, owner and task: `providerAccount.list`, `.subscribe`, `.register`, `.update`, `.remove`, `.setCurrent`, `.probe`, `.resetCredentialHome`, `.login`, `.loginCancel`, `.memoryImport` and `.usageRead`, the five-minute limits read with its turn-end read, and the window start. Their method rows live in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), their build tasks in [Plan-023](../plans/023-provider-accounts-and-credential-homes.md); the two background reads cross no client boundary and are this spec's and its plan's alone.

## State And Data Implications

- One new node-local table, `provider_accounts`, holds the registry: account identity, provider, the provider-reported identity fields, credential-home path, billing mode, credential generation, default flag, and the **stored last-validation reading** — the account's health state together with the RFC 3339 timestamp of the observation it records, held as a nullable pair set and cleared together and NULL until a probe has ever been taken. That pair is the readiness projection's only source, which is what lets a registry read answer the admission question without spawning a provider process or opening a credential file (§Node provider readiness and the sign-in handoff). It is deliberately not `updated_at`: that column moves on any row mutation, so a billing-mode correction — a field the person authors — would read as a fresh authentication observation. DDL and constraints live in [Provider Account Tables (Plan-023)](../architecture/schemas/local-sqlite-provider-account-tables.md).
- **No control-plane table.** Provider accounts and their spend are node-local; nothing about them is written to the shared schema.
- **One durable per-turn usage projection, rebuilt from the events the accountant already folds.** The per-turn usage event ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) is the durable record of a turn's consumption, and this plane projects those events into a node-local table, `provider_account_usage_turns`, holding **one row per turn**: the time, the provider, the account identity, the credential generation observed with it, the session, the run, the model, the token counts (input, output, cache read, cache write, reasoning), and the cost with the provenance the derivation ladder already assigns it ([Spec-014 §Cost Derivation And Absent-Cost Semantics](014-multi-agent-orchestration.md#cost-derivation-and-absent-cost-semantics)). It is **a projection and not a second accountant**: the same events feed it and feed the committed-spend fold, it is rebuilt like every other projection, and every figure it answers is served through the one committed-spend accessor [Spec-014 §Cost Figure Display Consistency](014-multi-agent-orchestration.md#cost-figure-display-consistency) names. What it adds over the fold is not a second arithmetic but an **axis**: the fold keeps running totals, and a total cannot be sliced by a day or a model it never kept. Rows are appended and never rewritten, and they are children of the registry, so an account's rows go when the account does. The session and the run are **absent** on a turn no session owns — the window-start turn is the one that spends outside every session (§Credential-home health observation) — so the account's own totals include it and no session's receipt does.
- **The account column is what makes the figures honest on a multi-account node, and the per-turn event must carry it.** Without it a provider's total silently pools every account, which is the failure mode of every tool surveyed on this ground. The event therefore carries the account it was charged to and the credential generation observed with it, exactly as the account-scoped quota event does (§Interfaces And Contracts).
- **The token counts are taken from the carrier that is complete on each leg.** On the Claude leg they come from the result frame's **per-model** usage block rather than its top-level one: the top-level block counts the outer loop only and undercounts as soon as helper conversations run, so a node reading it would under-report a session's real consumption. On the Codex leg the provider reports those token counts per turn and **no cost at all**. The row still carries whatever provenance the derivation ladder assigns it, because enforcement needs one number on one ladder, and a Codex turn's cost is priced from the daemon's price table. **Every dollar figure on the account surface is the cost with no mark** — no `tokens only`, `est.` or `unpriced` — on both providers, `All accounts · today <n> tokens · <cost>`.
- **What is drawn from it.** Per account: its lifetime spend carried with its billing mode, then its tokens for today and this week, and, expanded, by day and by model. Per provider across its accounts: today's tokens and what they cost, summed over that provider's rows. Neither is assembled by a client from the other, and neither is assembled from per-session receipts. A figure carries no cost-provenance label: billing mode (§Billing mode) is the only label a figure carries.
- **No provider report of totals, streaks or peak days is drawn.** The provider's own figures on the account surface are its usage windows, which already count work done outside the app; every token and dollar figure beside them is this table's, because two lifetime figures on one row that count different things disagree by design.
- The provider-reported identity fields — the address, the plan and the organization — are user-referencing data held on the row so an account can be named on a surface without a provider read, and they are refreshed from the provider's own reading rather than authored here. Their retention and erasure obligations are recorded in [Spec-020 §PII Data Map](020-data-retention-export-and-deletion.md#pii-data-map). The credential-home path is a filesystem location, not credential material; no credential material is stored in this table or in any other.
- Credential generation is durable and monotonic per account; it is never reset, including across a home reset, so a stale consumer can always order two generations.
- A second node-local table, `provider_account_usage_windows`, holds the **newest quota reading per `(account, limit identifier)`** with its window length, observation time, and source. It is a child of the registry and is removed with its account. It carries no credential material and no user identity.
- **The sealed token is not a column.** The [ADR-026](../decisions/026-provider-credential-custody-posture.md) D2 value lives in the operating system's credential store, or in the daemon's `secrets.json` file where that store cannot be used, keyed by account identity, not in `provider_accounts` and not in any other table. The registry records only that an account's **observed** mode is the token mode — a label, not the material — so the no-credential-column property of every table in this plane is preserved exactly.
- The observed authentication mode may reveal an account's provider-side email and organization where the provider's status surface reports them. Those are user-referencing data and their retention and erasure obligations are recorded in [Spec-020 §PII Data Map](020-data-retention-export-and-deletion.md#pii-data-map) alongside the account's provider-reported identity.
- **The registry remains un-evented.** Nothing in this plane appends a durable session event, the brokered sign-in included; its completion travels a wire notification on a read-shaped subscription and reaches no session transcript.

## Example Flows

- `Example: The person registers a personal subscription account and a work metered account for one provider, marks the personal one default, and starts a run whose definition pins no account — the personal account pays, and the run's admission record carries its account identity.`
- `Example: A saved agent definition pins the work account. A run started from that definition binds the work account, the daemon validates its home, spawns against that home, and the session cost receipt attributes the run's spend to the work account labeled metered.`
- `Example: The daemon crashes mid-run. On relaunch the binding's durable spawn-bound record re-realizes the same account; the home has since been logged out, the provider refuses the resumed run in its own words, and the run stays on that account rather than continuing on the default account.`
- `Example: The Codex service for the current account sends the daemon its token-refresh server request. The daemon runs the provider's own renewing read in that account's home, answers with the tokens the provider renewed there, stores nothing, and leaves the account's credential generation and stored health reading where they were.`
- `Example: The person marks the work account current while a Claude Code session is mid-turn. The session's next model request runs on the work account; the transcript gains Switched all sessions to <name> at the acknowledgment; the spend before it stays on the personal account and the spend after it lands on the work account, under one running total.`
- `Example: The provider reports a usage limit on the work account. The typed signal holds the step waiting with cause account, and the runs waiting on the work account fold into one attention entry keyed by its providerAccountId; the personal account's runs are unaffected, because the entry is account-scoped.`

## Implementation Notes

- The registry is small and node-local; a read-through cache is fine, but the authentication probe result is time-sensitive and must not be served stale past the driver contract's refresh cadence.
- The default flag is best enforced as a partial unique index rather than in application code, so two defaults for one provider are impossible by construction rather than by discipline.
- Credential-home paths must be validated as daemon-owned locations outside any repo working tree before they are written to the registry; a home inside a worktree would be captured by workspace lifecycle operations that have no business touching credentials.
- The reserved-variable set is the daemon's alone. The cleanest enforcement is to apply the reservation at the same construction site that already strips denied variables, so there is exactly one place where the child environment is assembled and exactly one place to audit.

## Pitfalls To Avoid

- **Do not treat the credential home as custody, and do not use it as one.** Pointing a provider at a directory is not storing its tokens, and a design that reads, copies, caches, or transports the material inside a home violates the posture even if it never persists it — that prohibition is unchanged. Its converse holds too: the one class of credential material the daemon may hold ([ADR-026](../decisions/026-provider-credential-custody-posture.md) D2) does **not** go into the home either. Daemon-owned bytes written into provider-owned space are indistinguishable from the provider's own to every later reader, the provider's tooling included. Seal it in the operating system's credential store, or the daemon's `secrets.json` file where that store cannot be used, in daemon-owned state.
- **Do not let an account fall back.** Every fallback in the account plane is a silent mis-billing. Refuse instead.
- **Do not key the account plane on the credential.** A rotated credential is the same account; an identity derived from credential material would fragment an account's history at every refresh and would leak account material into every payload carrying it.
- **Do not conflate the two "account identity" terms.** The control-plane user sense in the domain model is unrelated to this one.
- **Do not sum subscription and metered usage into an unlabeled dollar figure.** That is the single most misleading thing a multi-account cost surface can do.
- **Do not emit an empty reserved variable, and do not read one as a default — on either variable of a pair.** On at least one provider leg an empty value behaves as unset and silently returns the process to the shared credential entry, so the partition appears configured and is not. The hazard is **not one variable but two independent routes to the same collapse**: emptying the companion variable reaches it as directly as emptying the primary, and a filter that guards only the one everybody names is half a filter. Absent means absent; empty means defective; filter every reserved name at the single construction site, both halves of every pair.
- **Do not compute a provider's keychain entry name.** It is undocumented, version-fragile, and depends on inputs the daemon does not control. Observe isolation; never derive it.
- **Do not refuse an authentication method the vendor ships.** §Vendor authentication-policy constraints forbids removing, disabling, or restricting any built-in authentication method, and an account may legitimately be an API key, a third-party inference provider, or an externally-brokered credential rather than a subscription sign-in. The recorded mode is an observation with a tolerant unknown arm and never a gate.
- **Do not generalize one vendor's documented rule to the other.** Only one of the two providers publishes a concurrency constraint on its credential file. Adopting the same discipline on both is correct; attributing it to both is not.
- **Do not widen the driver capability set with an authentication flag.** The authentication probe is required of every driver by design; a flag would make it optional.
- **Do not let the daemon touch a credential beyond ADR-026's named moves, and do not let a per-account home be `~/.claude` or `~/.codex`.** The observer asks a provider a question inside a home the daemon owns and lets the provider's own code renew its own login there; the daemon writes no credential file, speaks no token endpoint, and reads a provider's store only where [ADR-026](../decisions/026-provider-credential-custody-posture.md) names it. Pointed at the person's own home the same read becomes the race the rotation rule exists to prevent — two holders of one grant, and a lost rotation ends their login. The isolation is what makes the read safe, so the read is never taken anywhere else.
- **Do not treat a provider path answering successfully as proof that credentials work.** At least one pinned path returns success while discarding the outcome of the refresh it was asked to perform, so a permanently-dead credential answers it cleanly. Liveness of the surface is not usability of the credential.
- **Do not key quota readings on the window length, and do not read a window's position as its meaning.** One pinned provider publishes several limits that share a window length; keying on the length collapses them and the survivor depends on arrival order, so the key is the limit identifier. The mirror error is the other way round: a provider has moved a given window between its primary and secondary slots, so a surface that labeled the primary slot as the short window would relabel every bar the day that moved. Key on the identifier; label from the length the provider reported.
- **Do not collapse `indeterminate` into `reauth_required`.** They have different remedies — look again versus sign in — and the collapse costs the person a full sign-in over a transient fault.
- **Do not echo, log, or render the token input.** It is write-only on every surface, diagnostics included. A value that appears in a log line has been disclosed regardless of where it was sealed, and at least one upstream leg has shipped a fix for exactly this class — error strings that carried a token into a message the caller could read.

## Acceptance Criteria

- [ ] AC-1 — A node registers two accounts for one provider with distinct homes; both are listed under the identity each provider reports, exactly one is default, and a second default for the same provider is rejected by the schema.
- [ ] AC-2 — Account identity is stable across re-authentication, a billing-mode correction, and default changes; credential generation strictly increases at each credential-home lifecycle transition and never resets.
- [ ] AC-3 — A run whose definition pins no account binds the provider's current account; a run started from a definition or a workflow step that pins one binds the pinned account, and no client request can name either.
- [ ] AC-4 — The bound account is stamped on the run's admission record, is not client-suppliable, and is re-realized identically on resume from the durable spawn-bound record.
- [ ] AC-5 — A spawn against a missing home or an unregistered account refuses before spawn with a typed refusal, and no provider process is created; a spawn against a registered account with its home present runs no sign-in check, and a signed-out home shows as the provider's own refusal on the run.
- [ ] AC-6 — The child environment for an account-bound spawn carries the reserved credential-home variable set by the daemon; a caller-supplied or inherited value of a reserved name is discarded rather than merged.
- [ ] AC-7 — The current-account Codex service runs on tokens handed with `account/login/start {type: "chatgptAuthTokens"}` and held only in the daemon's memory; its token-refresh server request is answered with tokens read from the account's home after `account/read {refreshToken: true}` ran there; nothing is stored, logged or shown, no credential generation moves, and no stored health reading moves; a pinned session's own service never sends the request.
- [ ] AC-8 — The account-scoped quota event carries account identity and credential generation, and a two-account node attributes each snapshot to the correct account.
- [ ] AC-9 — Every surfaced account-attributable cost figure carries its account's billing mode across every value (`subscription`, `metered`, `unknown`), and a total spanning more than one mode states that it does; a figure from a `subscription` or `unknown` account is never presented as billed dollars.
- [ ] AC-10 — Two runs bound to one account, and two runs bound to two accounts of one provider, run at once, and no execution path shares a credential home.
- [ ] AC-11 — A node with no accounts reports the no-account arm for every provider it supports; registering one account and probing it authenticated moves that provider to the authenticated arm; and **a provider whose accounts include no default at all** reports the no-default arm. That third case is seeded directly — two accounts, neither flagged default — and **not** by adding a second account beside an existing default: registering a non-default account leaves the first account's default intact, so readiness correctly keeps resolving it, and asserting `no_default` there would require silently clearing a default and changing which account pays. The reply carries exactly one readiness entry per selected provider in every case.
- [ ] AC-12 — Deriving readiness spawns no provider process and reads no credential material: a registry read against a two-account node performs no authentication probe and opens no credential file, and the reply carries the timestamp of the **stored** observation rather than a fresh one.
- [ ] AC-13 — No surface reports a provider as authenticated on any reading other than the authenticated arm — `indeterminate` included.
- [ ] AC-15 — A brokered sign-in against a registered account spawns the provider's own unmodified binary with that account's home pinned, returns the provider-emitted verification material and an opaque attempt identifier, and completes without the daemon reading, copying, or persisting any credential; a second start against the same account while one is in flight is refused, and cancellation by attempt identifier releases the provider-side attempt.
- [ ] AC-16 — Sign-in completion reaches clients on the read-shaped subscription as a wire notification, appends no durable session event, and is followed by an ordinary health observation before the account is reported authenticated — a completion reported successful does not by itself move the stored reading.
- [ ] AC-17 — The `register` verb accepts a Claude Code setup token or an OpenAI API key on its write-only member, with a required name, trimmed and compared by full Unicode case folding (`foldName`), that differs from that provider's other account names; the value is kept in the operating system's credential store, on Linux as a Secret Service item or, with no Secret Service answering, in the daemon's own `0600` items file, and, on a Mac whose secrets are in the file, in that same file, never written into the credential home, never returned on any reply, and never present in any log line, error message, metric, or diagnostic dump. A locked keychain and an unavailable one each refuse with their own line and `cause`, and nothing is stored anywhere else.
- [ ] AC-18 — On Claude Code the token reaches each spawn on `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR` and a command the model runs cannot read it; on Codex the key reaches the service by the `apiKey` login, no `auth.json` is written, and it is sent again after a service restart; the credential is never in an argument vector or a sibling account's process. A terminal authentication refusal on such an account moves the stored reading to `reauth_required` and triggers no retry and no refresh attempt.
- [ ] AC-19 — The background observer reads every account every five minutes, honors the per-account opt-out, runs Claude Code readers one at a time, is single-flight per account, takes no reading while a turn is live on that account, and **issues only the reads this spec names** — that leg's limits read and its local status read, and for a pasted Claude token the one minimal turn. Across a full cycle: no credential file or keychain entry is written or copied by the daemon, and none is read beyond the moves ADR-026 names; no model turn is charged except a pasted token's read, which lands in that account's spend; every window the account has is stored with its read time; a Codex API-key account is not read; and on the Codex leg the account's own last-refresh marker **is permitted to move**, which is the renewal the cadence exists to cause, while `credentialGeneration` and every stored quota reading's generation stay where they were. `Check now` within 60 seconds of the last read answers that read.
- [ ] AC-20 — An observation writes the stored health pair without bumping `credentialGeneration`, a transient observation failure included.
- [ ] AC-21 — Quota readings for one account across distinct limits sharing one window length are held and rendered as distinct, keyed by limit identifier; a reading naming no limit identifier is stored under the reserved `default` identifier; where two readings key alike the later observation time wins, with the source breaking only exact ties; a per-model window is keyed from the model's display name on the leg that reports one and is **not** read from that leg's null flat keys; every window is labeled from its reported length rather than from its position in the reply; a complete reading set replaces the account's stored set while a sparse pushed update merges into it and prunes nothing; and every rendered window carries its read time.
- [ ] AC-22 — `providerAccount.setCurrent` on a provider with one idle and one busy unpinned session, and one session pinned to another account: both unpinned sessions run their next request on the new account with no hold, interrupt, copy, resume or `continue` — on Claude Code through `apply_flag_settings {env}`, on Codex through one `chatgptAuthTokens` login on the current-account service, a running tool or command finishing once and never repeated; the pinned session does not move; no credential file, keychain entry or provider login is written anywhere in the sequence; and each moved session's transcript carries one row, `Switched all sessions to <name>`; a moved Claude Code session at `Reviewed` whose new account's plan lacks auto mode runs at `Ask` and carries one more row, `Reviewed isn't available on this Claude Code account`, from the `session.notice` kind `level_unavailable`, and nothing is blocked. Before build acceptance the same switch is measured onto a real second account on each provider, with the earlier reasoning (Claude Code's signed thinking, Codex's encrypted reasoning) carried across.
- [ ] AC-23 — `providerAccount.setCurrent` naming an account that is unregistered or whose home is missing, or whose last Claude Code read answered `rate_limits_available: false`, refuses in place: the current mark does not move, no session moves, and the refusal carries that account's own remedy. A switch the provider refuses after it was accepted leaves the previous account active, draws no success row, lands `Switch to account <name> failed · login expired · Sign in again`, and settles as `agent.provider_binding_change_failed` with `account_unavailable`.
- [ ] AC-24 — A turn on either leg appends exactly one per-turn usage row carrying the provider, the account, the credential generation observed with it, the session, the run, the model, the token counts and the cost with the provenance the derivation ladder assigned it; a Claude row's tokens match the provider's per-model block on a turn that ran a helper conversation, and a Codex row carries no provider-supplied cost. A turn no session owns writes its row with the session and the run absent, and that row counts in the account's totals and in no session's receipt. The projection rebuilds identically from the event log. Per-account, per-provider, by-day and by-model figures are group-bys over those rows served through the one committed-spend accessor, no surface re-sums them or derives one from another, and no figure carries a cost-provenance label.
- [ ] AC-25 — Removing an account runs no provider sign-out: the account's credential home is byte-identical across the removal and the provider still reports that home as signed in; the row, its readings and its usage rows are gone; and removal is refused while a session runs on that account, the refusal naming those sessions.
