## Purpose

Define the canonical control semantics for queued work, active-run steering, pause and resume, and interrupt behavior.

## Scope

This spec covers queue admission, interventions, blocked states, and the control outcomes the person sees.

## Non-Goals

- Provider-specific transport details
- Workflow-level orchestration semantics
- Notification policy

## Required Behavior

- **A message sent while a run is active is delivered into that run.** It is persisted as a queue item before anything else happens to it, and it is then delivered to the running run at its next step boundary on both V1 providers — never held back for a later run and never silently turned into a second one. Until the run takes it the item is waiting, and it says so. Several such sends stack in the order they were sent and are delivered in the one order the daemon holds for them. The daemon stamps every message with an id of its own — a UUID on Claude Code, `clientUserMessageId` on Codex — and that id is what lets a waiting message be withdrawn, edited or moved. `Remove` withdraws it, and nothing reaches the agent. `Edit` is one daemon call that replaces the waiting message in place, so the edited message keeps its place: the old item reads `superseded`, and the call is refused once the agent has taken the message. A reorder is one order the daemon holds over the messages still waiting, replaced whole. On Claude Code the message is handed to the provider at once and the provider holds it until its next tool boundary, so a withdrawal is that provider's own cancel on the id, an edit is a cancel of that message and of every message after it and a resend in order, and a reorder is a cancel of the waiting messages and a resend in the new order; on Codex the daemon holds the message itself and steers it in at the tool boundary, so an edit replaces the item in the daemon's own hold and a reorder reorders that hold — a cancel and a resend there would put the message last — and a steer aimed at a request that has already gone out lands at the step after, the item waiting until then. Delivering one waiting message ahead of the rest is an interrupt of the run followed by that message, the remainder following in order as the next turn's messages. An item that has not been delivered because the daemon cannot be reached stays waiting; an item whose delivery failed, or that has waited longer than the daemon's own delivery timeout, is recorded as not delivered with its reason and can be sent again from the item itself. The two are distinguishable states, never one hopeful one. Follow-up work that is not a user message — orchestration-authored input — stays an ordinary queue item admitted in canonical order.
- `pause` is an orchestration-layer construct the daemon owns: it stops the run after the step already in flight — by the provider's own hooks where the provider has them and by a boundary interrupt where it does not, per the pause-mechanism bullet below — and persists conversation history and run state; nothing is queued to resume it. The resulting `paused` state must not mean queue-drain suspension or blocked waiting. Pause is one toggle rather than a pair of controls: the same control continues the run, and so does sending anything to it, in both cases from exactly where it stopped with nothing repeated. There is no pause-immediately variant and no separate resume control. While the step in flight is still finishing, the run is `pausing` and not yet `paused`, and that is a state a reader can see; waiting messages stay waiting while the run is paused and are delivered when it continues; and a paused run can still be interrupted.
- `resume` must return a `paused` run to active execution with the same run id.
- `interrupt` must transition a run directly to `interrupted`. Interruption is a synchronous or near-synchronous provider call with no intermediate state. It reaches the run it names and nothing else inside the session: the agents that run dispatched are spared and keep working, and an interrupt never cascades, on a lead run or on a child. The one thing it reaches outside the run is the other end of a live exchange with another session, whose turn ends with this one and whose queued messages are dropped, as [Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other) states. The command the run was running is ended with it. Whatever was waiting for that run is delivered at once as the next turn, so an interrupt with messages waiting leaves the run working again; with nothing waiting the run rests `interrupted` until a later send returns it to running. On Claude Code the daemon declares the per-task stop affordance so a plain interrupt never sweeps the run's background subagents, and where a child is running in the foreground the daemon first moves that child to the background, so the interrupt spares it as it spares every background child; on Codex the daemon ends the command the interrupt leaves running.
- **Stopping everything is the separate act, and it is not atomic.** One control stops the run and every agent it dispatched at every depth, one stop per agent identifier taken from the daemon's own record of the run tree; an agent whose stop failed is reported on its own and stops nothing else from being reached. It is the one stop that does **not** deliver what was waiting: the run's waiting messages are withdrawn rather than sent as the next turn, and their text is handed back to the user to send again. What a stopped child then accepts is the per-provider rule above — final on Claude Code, re-enterable on Codex.
- **Where a provider reports the daemon's own interrupt in the same frame shape as an execution error, the daemon records it as an interrupt and never as a failure.** It marks the turns it interrupted itself and reads its own mark rather than the frame's; a provider that ends a stopped turn as interrupted and a failed one with a code is followed as it reports. A child's failure is read from that child's own update and never from the lead's result, which can report success while a child dies.
- Waiting for approval or input must remain `waiting_for_approval` or `waiting_for_input`, not `paused`.
- Every intervention outcome must be visible in the canonical event stream.
- Queue items must support cancellation before admission.
- **The states of a turn.** A run is idle before it starts and running while it works; an approval or an input request leaves it waiting and answering that returns it to running; it is done when it finishes. `Interrupt` takes a running run to `interrupted`, and a send — or the waiting messages going as the next turn — takes it back to running. `Pause` takes a running run through `pausing` to `paused`, and the toggle or a send takes it back to running. A run freezes its checkout root when it starts, so a working-folder move asked for while it runs is recorded as an intent on the session and applied when the run reaches a boundary. A child run carries the same machine on its own: it pauses and continues on its own toggle, its own interrupt takes it to `interrupted` and a steer takes it back to running, a stop that reaches a subtree takes it to `interrupted` — final on Claude Code, where the provider refuses every later message to a child the user stopped, so no send returns it to running, and re-enterable on Codex, where a send starts it again — and a finished child returns to running on a send into its own steer box, its pause and interrupt coming back with the run.
- **How the pause is made true on each provider.** The daemon pauses with the provider's own hooks where the provider has them and with a boundary interrupt where it does not; the hooks are registered for the session over the wire or passed on the command line, and no hook is ever written into a file. On a Claude Code lead run it is hooks registered in the session's `initialize` request and answered over the wire: one ends the turn after the step in flight, the other denies whatever a woken lead tries while the pause holds, both carrying the same reason — so a lead a child wakes runs one model call, is denied its tool, and stops again. On a Claude Code child run it is a hold on that child's next tool callback; a hold a daemon restart orphaned there can never be answered, so the child it was holding is drawn as interrupted and continues from its own box. On Codex, lead or child, it is the boundary interrupt: the hook holds the thread's next call, the daemon interrupts the turn, the hook denies the parked call so it cannot run, and starting the next turn is the continue; a command still running finishes first, and the run is pausing until it has. That hook is the daemon's one pre-tool hook — the same hook that reports a command — passed with `-c` when the account home's Codex service starts, so it serves every conversation on that service, with an explicit timeout under which the hook refuses at its own deadline, because a hook that times out fails open; and because Codex runs no untrusted hook, the daemon trusts it and its post-tool partner through Codex's `config/value/write` before any conversation loads. The pause writes nothing else into a Codex configuration file, and the trust write never cleans, rewrites or reorders any other entry there. The user's own hooks keep running beside the daemon's, and a hook the provider refuses at `initialize` is learned from that refusal and remembered rather than retried, with the control that depended on it saying why it is unavailable.
- **A child run's controls are the session's controls.** Every live child run takes the same pause, interrupt and steer the session's own run takes, whatever dispatched it and whichever provider it runs on. Interrupting one child reaches that child alone: the agents it dispatched keep going, and so does whatever dispatched it. Continuing a parent continues the parent alone. Steering an interrupted child starts it again with everything it knew, and a finished child starts again on a send — as a new turn on its own thread where a finished thread refuses a steer, and by asking the lead to message the child where the provider offers no way to reach it directly. A child stopped for good on Claude Code takes no later message at all, because the provider refuses every message to a child the user stopped; the same stop on Codex is an interrupt the child comes back from. A paused child's hold is lossless: its next tool callback simply goes unanswered, so the child burns no tokens and loses nothing, and the hold ends only by an answer — allow from the toggle, or deny carrying the user's own typed words, which the child reads as its instruction. The hold is routed per child by the id the hook payload carries for the acting thread, it works at every permission level including the least careful one, and it is held open by setting the callback's timeout far past any wait a person would sit through; a provider canceling a held callback is a lost pause and never a release, and a hold left unanswerable by a daemon restart leaves its child interrupted rather than held forever. Freezing one child at the process level is not offered, because both providers run their subagents inside the parent process: a process freeze stays an option only for pausing a whole session. A capability a provider refuses is learned from the refusal and remembered for that child, never read from an experimental opt-in surface.
- **Undo: going back to a point in the session's own history.** `Undo to here` on one of the person's own messages, `Restore` on a snapshot in the inspector, and the rewind menu's three rows — `Restore conversation and files`, `Restore conversation` and `Restore files` — are one operation with one contract, on both providers and never absent. In the same session it puts back the conversation by the provider's own conversation cut and the files by the daemon's own checkpointer: the conversation and the files together, the conversation alone, or the files alone, to the moment before one of the person's own messages or to a named snapshot. It is not an intervention and adds no run control. Its target is always a stable message or snapshot identity; any position the operation needs stays inside the daemon and the provider adapter. Nothing is applied before the dry run has been read and answered: the dry run names the files it will put back, the lines that change, the files it will skip counted by reason (a symbolic link, a hard link, something that is not a file, a moved folder, a file too large to keep, a branch a command moved), the commands still running after the point, the agents that would stop and whether they can resume, the ignored folders it does not restore, whether commands ran after the point, and the paths another session in the same folder changed since the point, which stay as they are unless the person includes them. Before an undo that would stop agents or commands started after the point, it asks in place, naming each count from the daemon's own record of the run tree; on Claude Code it adds that those agents cannot be resumed, because the conversation cut there ends them for good, while on Codex the cut leaves them running and the daemon stops each by its own id, resumably. Declining changes nothing. On an answer the undo stops those commands first, each by its provider's own verb, and those agents one stop per id, ends a turn still running, and then restores. It is offered through a running turn, and it is never refused because a turn is running or because the point lies before a compaction. A message sent while the undo runs is never lost: it is answered on the undone conversation.

  The files are the daemon's own per-session checkpoint store ([Spec-013 §Required Behavior](013-persistence-recovery-and-replay.md#required-behavior)), which keeps a copy of each file before every edit the agent or any of its children makes and at every prompt that starts a turn, and a capture before and after every command an agent or a child runs — so what an agent's shell commands wrote goes back too, on both providers. Two sessions in one folder keep their changes apart: an undo puts back only its own session's changes. The git snapshot never puts files back. Where the session works — its own worktree or the project's checkout — changes nothing about an undo, because the copies are held with the session outside the checkout.

  **One result, reported as one row.** An undo can apply in part: the conversation can go back while the files cannot, or the reverse. Its result names what was asked for, what was restored — the conversation and the files, the conversation, the files, or nothing — and, for each part asked for that did not apply, its failure with the daemon's own reason. Every outcome is stored as one event, `session.restore_finished`; `run.rolled_back` records the conversation cut alone, and an undo of the files alone appends none. When everything asked for applied, the transcript row reads `Restored to before <the message's first words>`, `Restored to <snapshot name>`, or `Files restored to before <…>` for files alone. When part applied, it names the part that did in those words and the part that did not with its cause: `Restored to before <…> · files not restored · <cause>` or `Files restored to before <…> · conversation not restored · <cause>` (`Restored to <snapshot name>` and `Files restored to <snapshot name>` for a snapshot). When nothing applied, it reads `Undo failed · <cause>`, naming each distinct cause, as in `Undo failed · <one cause> · <another cause>`, and a cause both parts share once, and the conversation and the files are as they were. The cause is the daemon's own, in words. A snapshot name that sits mid-sentence lowercases its first letter only, and a name that opens on an acronym keeps it. The turns after the point stay in the transcript marked superseded, and only when the conversation went back; the authoritative log never truncates or rewrites ([ADR-017](../decisions/017-shared-event-sourcing-scope.md)). A retried call under the same idempotency key never cuts twice.

- **Edit and resend is one operation, offered for every message the person sent, on both providers and through a running turn.** The pencil puts the message, with everything it carried, back into the draft, and Enter resends it from that point. The resend is the undo above at its conversation-and-files scope, carrying the edited message: one intent, one call, one idempotency key, one result. It puts the conversation and the files back to the moment before that message with the same dry run as an undo, whose count the editing row shows before Enter: a skipped file is named, and a path another session in the same folder also changed since the point is named and left as it is unless the person includes it. Then it sends the replacement. It asks first under the same rule as an undo when agents or commands started after the point are still running; declining keeps the edit and changes nothing. While it is in flight the turns it will supersede dim and stay readable and pressable, and they are marked superseded when the cut lands, never before. The edited message goes at once as the next send on the cut conversation; nothing holds it for a later resume. A resend that fails, for any reason, puts the edited message back in the composer with everything it carried and lands one system message naming the cause, `Resend failed · <cause>`; where the cut had already landed, that same row goes on to say the conversation went back, `Resend failed · <cause> · restored to before <the message's first words>`, rather than leaving the conversation cut with nothing sent.
- **Post-interrupt late-event absorption.** A provider **run-lifecycle** event — a run-state-transition report — that arrives for a run already in a terminal state (`completed`, `interrupted`, `failed`) is **absorbed, never appended**: a terminal-class straggler routes into the at-most-once terminal emitter ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle) emission contract) and no-ops there; a non-terminal lifecycle straggler is dropped from the lifecycle path entirely and recorded only as a `run.late_event.absorbed` **diagnostic non-event** on the daemon's telemetry (an OTel log record per [Observability Architecture](../architecture/observability-architecture.md) — never a `session_events` row), with no state transition and no `runVersion` advance. Absorption also keys on **execution epoch**, not current run state alone: the epoch is the interval between accepted `run.rolled_back` cuts ([Run State Machine §Invariants](../domain/run-state-machine.md#invariants)), and a run-lifecycle event sourced from the execution before a cut that arrives after it is absorbed identically — the Spec-005 `(runId, runVersion)` key cannot catch it, because the cut advanced `runVersion`. Epoch attribution needs no wire token: the driver owns one serialized connection to its provider process, so the confirmation of the driver's `rewindConversation` is an **in-stream fence** that totally orders the cut against event delivery; once it confirms, the driver delivers no run-lifecycle event of the execution before the cut, and the daemon's per-binding cursor — an **(epoch, position) pair** whose position advances at each turn boundary observed in the binding's ordered delivery and freezes at the fence — absorbs any straggler that slips through. Run-lifecycle events are attributed per **runtime binding**, and both arms of the rule are V1. A cut made in place — Codex's `thread/revert`, and Claude Code's `rewind_conversation` for a point after the last compaction — keeps the run on its runtime binding, whose **delivery generation rotates at the fence**: the confirmation closes the generation before the cut, and deliveries after the fence open the new epoch. A cut to a point before Claude Code's last compaction is made by a fork and a restart (§Driver-Level Rollback Mechanics), which mints a new provider session: the old runtime binding **freezes wholesale** at the fence, every delivery on it belonging to the epoch before the cut at its retained (epoch, position) pair, and the new runtime binding opens the new epoch. Absorption is scoped to the run-lifecycle family: non-lifecycle provider events arriving in the same window — usage telemetry above all, plus assistant output, tool activity, and artifact publication — append normally under their own families' rules (late usage telemetry must still reach the cost ledger; absorption never drops billable usage), but never epoch-blind: a non-lifecycle row the cursor attributes to the epoch before a cut appends **carrying that attribution durably**, stamped at ingestion from the straggler's **operation association** — the run engine records each provider-side operation (tool call, message item, artifact production) against the (epoch, turn) current when it opened, and the straggler's correlation key resolves that recorded pair, because re-executed turns reuse ordinals and a content-asynchronous straggler (a long-running tool's progress, a delayed usage aggregate, a late-completing artifact upload) must rank by its operation's opening pair rather than by when it arrived. A straggler with no resolvable operation linkage takes the retained pair of the closed generation or the frozen binding, which sits above the point the cut went back to, so it is always superseded with its epoch and never resurfaces as current; on the in-place arm a delivery after the fence is current by the fence's order. It is never a read-time guess and never the run's current position. The typed stamp is the cross-cutting `sourceEpoch` + `sourcePosition` payload pair ([Spec-005 §Event Type Enumeration](005-session-event-taxonomy-and-audit-log.md#event-type-enumeration)), which §Driver-Level Rollback Mechanics' supersede projection consumes, so replayed projections mark a late row superseded exactly like the in-time rows of its epoch. The near-synchronous interrupt hedge above is the _reason_ the window exists — a provider may emit briefly after the daemon records the terminal; canonical-stream visibility of the intervention outcome is satisfied by the terminal event itself, and absorption adds no second visible outcome.

- **Every accepted intervention durably records the principal that admitted it.** The daemon resolves the caller's **transport-authenticated** identity at acceptance and persists it on the intervention row, alongside a daemon-resolved `origin` discriminator naming which admission path produced the row. Resolution is the one §Interfaces And Contracts states for run control ([API Payload Contracts §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model)): the daemon's node-owner user identity on the local socket, and the same identity for a linked device inside its encrypted channel to the machine, since one account owns the machine. The wire `initiatorId` is **never** the source — it stays routing/audit metadata per [ADR-011](../decisions/011-generic-intervention-dispatch.md), and a request whose body actor disagrees with the verified identity is refused through the existing `auth.principal_mismatch` error, never trusted and never silently normalized. `origin` is `'user'` for a request admitted over an identity-carrying transport and `'system'` for the in-process orchestration entrypoint that sits below the wire authorization boundary and carries no user at all; the principal is **required exactly on the user arm and forbidden on the system arm**, enforced as a storage constraint so a user-origin row can never persist unidentified and a system-origin row can never smuggle an identity in. The discriminator is resolved, not inferred: a client-supplied `initiatorId`'s absence is not evidence of a system admission. Recording the principal on the row — rather than reconstructing it later from run history — is what makes it **replay-stable**, since a run accumulates interventions over its life and history offers no single answer to which one authorized a given unit of work. Producers write the stamp inside the transaction that accepts the intervention — never a second write that a crash could separate. Consumers are the authorization path: a turn opened by an accepted intervention adjudicates under the recorded principal ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)'s turn-scoped resolution, covering the steer-opened arm), and an unresolved principal adjudicates as a **deny**, never as the run initiator.
- **Queue-item bodies rest sealed, exactly as intervention bodies do.** A queue item's send body is persisted through the same PII split this spec specifies for intervention bodies: the text is sealed into the item's PII-bearing field under the session's content key — the one key that seals the session's events — with associated data `session_id || "ais.session-pii.v1" || queue item id`, while the plaintext payload retains only the non-PII members. One key per session makes erasure structural: the purge overwrites the session's wrapped content key with zeros and deletes it before it deletes the session's rows, with a `TRUNCATE` checkpoint after commit ([Spec-020 §Ordering And Atomicity](./020-data-retention-and-gdpr.md#ordering-and-atomicity)), so the event copy and the queue copy of the person's words become unreadable in the same act, with no second erasure path to forget. Content authored by orchestration rather than by the person — a workflow phase input, an orchestrated child-run prompt — is sealed the same way, under the same key: it is the session's private content too, so a purge leaves none of it readable. Queue rows remain **durable and never-evented**, drained but never deleted and canonical for audit and replay; this rule changes what a row stores at rest, not its lifecycle. Queryability is unaffected because every field admission and drain select on — state, run binding, session — is its own column and none of them is content.

## Default Behavior

- A user message sent while a run is active is persisted as a queue item and then delivered into that same run at its next step boundary. Queueing is how the message is made durable, not a way of holding it back for a later run.
- Queue ordering default is FIFO within the target scheduling scope.
- If a driver does not support steer natively, the intervention must be rejected or degraded to a new queue item. Both V1 providers deliver a message handed to them mid-run into the running run, so neither reaches that degrade; it is the rule for a driver that cannot. Pause does not require driver support either — it is an orchestration-layer run-control mutation (`run.pause` / `run.resume`), composed by the daemon out of the session's own hooks and, where a provider has none, a boundary interrupt (stop at the step boundary and persist; the toggle's second press or a send continues), and **not** dispatched through the driver-facing `applyIntervention` path that steer/interrupt/cancel follow ([ADR-011](../decisions/011-generic-intervention-dispatch.md); no intervention type is minted for it — see [Queue And Intervention Model](../domain/queue-and-intervention-model.md)).

## Fallback Behavior

- If `steer` is requested against a run that cannot accept it, the system must either reject the intervention or explicitly degrade it to a new queue item.
- If a paused run cannot be resumed because driver state is lost, the system must transition it through recovery logic and then to `failed` or `interrupted`; it must not pretend the same run resumed.
- If queue persistence is temporarily unavailable, the system must reject new queue creation rather than silently storing queue state only in client memory.

## Interfaces And Contracts

- `QueueItemCreate`, `QueueItemList`, and `QueueItemCancel` must operate against runtime-owned durable state.
- `InterventionRequest` must include target run id, intervention type, and a **mandatory** version guard (`expectedRunVersion`). The guard is **fail-closed**: the comparand is required on every intervention, and an absent comparand is **rejected**, never applied — an optional guard would let a caller bypass stale-replay protection by omitting the field (Plan-003 D-003-2). `expectedRunVersion` is compared against the target run's `runVersion` — an **any-run-progression counter** that increments on every run progression, applied interventions included (not only `run.*` state-machine transitions), so two steers racing on a still-`running` run cannot both pass undetected (Plan-003 D-003-1). `runVersion` is the run aggregate's optimistic-concurrency token, distinct from the immutable `EventEnvelope.version` wire-contract field ([Spec-005 §EventEnvelope Version Semantics](005-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics)). Payload fields vary by type: `steer` includes `expectedTurnId`, `content`, and optional `attachments` — typed `ArtifactId[]`, an ordered list of ids into [Spec-012](012-artifacts-files-and-attachments.md)'s manifest space and never an untyped element or an inline byte payload, carrying that spec's order-preserving, never-silently-dropped, refused-whole-rather-than-truncated carrier contract as [API Payload Contracts §Plan-004 — Provider Driver Contract (Internal Interface)](../architecture/contracts/api-payload-contracts.md#plan-004--provider-driver-contract-internal-interface) states it once for both ends of the carrier; `interrupt` and `cancel` include optional `reason`. Every intervention request additionally carries a **mandatory** requester-generated `clientIdempotencyKey` (UUID) — the second, orthogonal guard ([Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior)): `expectedRunVersion` defeats stale replays of outdated intent, the key defeats duplicate applications of the same intent (replay-or-conflict, `intervention.idempotency_conflict`). The replay-or-conflict body comparison is **PII-safe by construction** for a steer's `content`, which rests encrypted: whether a reused key carries the same or a differing body is decided by decrypting the stored envelope under the session's content key (the key `SessionContentKeyStore` resolves for the intervention's session, its target run's session) and comparing plaintexts — never by comparing ciphertexts (the envelope is nonce-randomized, so equal plaintexts encrypt unequal) and never by persisting a plaintext digest beside the envelope (a retained digest sits outside the envelope's encryption, so it would outlive the text it hashes as a guessing oracle — in a backup, or in the database's freed pages after a purge or [Spec-020](020-data-retention-and-gdpr.md) `Erase all data`) — and a stored body that will not decrypt, a custody fault since no act deletes a session's content key while the session's rows remain, settles the reuse fail-closed as `intervention.idempotency_conflict` ([Queue And Intervention Model](../domain/queue-and-intervention-model.md) owns the canonical rule). See [Queue And Intervention Model](../domain/queue-and-intervention-model.md) for canonical payload shapes.
- `InterventionResult` must distinguish the 6 canonical intervention states: `requested`, `accepted`, `applied`, `rejected`, `degraded`, and `expired`. A version guard mismatch produces `expired`. An authorization failure produces `rejected`.
- Intervention dispatch uses `applyIntervention` (see [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md) and [ADR-011](../decisions/011-generic-intervention-dispatch.md)), which routes to the appropriate driver-specific handler based on intervention type and declared capabilities. The Cedar `principal` for authorizing an intervention is the caller's verified user identity: on the daemon's local socket, which carries no PASETO token, the daemon's node-owner user binding resolved through the Plan-016-gated credential/identity provider seam (a named [Plan-003 §Preconditions](../plans/003-queue-steer-pause-resume.md#preconditions) prerequisite); a linked device reaches run control only inside its encrypted channel to the machine, from a device key the account trusts, and binds the same node-owner identity, since one account owns the machine; `initiatorId` and any body-level actor fields are informational only. See [API Payload Contracts §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model). The Cedar **action** for a run-control intervention is `Action::"intervene"` on the target `Run` resource. Authorization is never evaluated against run authorship — the session's user may intervene on any run in the session, whatever started it ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior) owns the rule). The same adjudication governs the orchestration-layer `run.pause` / `run.resume` run-control mutations even though they never ride `applyIntervention` (they are daemon-handled orchestration verbs holding no `InterventionType` membership): their handlers evaluate the identical `Action::"intervene"` request — same `Run` resource, same authorship-blind rule — before composing any run-state mutation, per [Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)'s governed-identically rule, so the dispatch-path split is transport plumbing, never an authorization boundary.
- **Undo is `session.restore`, not an intervention.** On a session, `session.restorePreview({ target, scope })` answers the dry run and changes nothing, and `session.restore({ target, scope })` applies it. `target` is a stable message identity or snapshot identity, never a numeric or provider position; `scope` is `"conversation-and-files"`, `"conversation"` or `"files"`. The request takes a per-session `clientIdempotencyKey`, so a retried call never cuts twice; a `resend` member carrying the edited message makes edit and resend one call; and `includeAlsoChanged` — false unless the person pressed the include line — also puts back the paths another session in the same folder changed since the point. The result carries `requested` (the same values), `restored: "conversation-and-files" | "conversation" | "files" | "nothing"`, the figures of what went back, and for each requested part that did not apply `failures.conversation` / `failures.files` with a `reason`; when the call carried a resend that did not go after the cut landed, the result says so with its reason. Every outcome is stored as `session.restore_finished`; `run.rolled_back` records the conversation cut alone. The checkpoint store, the dry run's figures and its skip reasons are [Spec-013 §Interfaces And Contracts](013-persistence-recovery-and-replay.md#interfaces-and-contracts)'s. The conversation half is the driver's `rewindConversation` ([Spec-004 §Interfaces And Contracts](004-provider-driver-contract-and-capabilities.md#interfaces-and-contracts)), made against the session's live runtime binding, which the daemon resolves; clients never name a binding or a position. The driver's `forkConversation` (`ForkConversationParams`, `ForkConversationResult`) serves `session.fork` and never an undo.
- **The queue calls.** `run.queueCreate` takes one typed message — its text and its attachments (`ArtifactId[]`), the id the daemon stamps on it, and its target, the lead or a child's handle — plus an optional addressee `to` naming another session, which is how the person writes to another session with `@name` from the composer: one Send, which the daemon routes. For an edit it carries `replacesQueueItemId`, and that one call replaces the waiting message in place: the old item becomes `superseded`, the edited message keeps its place, and the call is refused once the agent has taken the message. `run.queueList` returns each waiting item with its text, its state and, for an item not delivered, its reason. `run.queueCancel` is `Remove` alone. `run.queueReorder {sessionId, childHandle?, queueItemIds}` takes the full new order and is refused unless `queueItemIds` names exactly the items still waiting; the daemon reorders its own hold on Codex and cancels and resends in the new order on Claude Code. `run.queueList`, `run.subscribeQueue`, `run.queueCancel` and `run.queueReorder` take a child's handle too, so a child's waiting rows work as the lead's.
- **The run streams.** `run.subscribeState` carries the run's state (its member `newState`, `pausing` among the values), its activity and the row dots; `run.subscribeQueue` carries the waiting items. One state stream per session in view carries the lead and every child, and one queue stream per agent flow on screen, so a window holds at most three run streams whatever the fan-out; a session out of view reads `session.list` and resubscribes from its cursor when it returns. Each subscription is batched like every session stream and queues at most 1,024 events before the screen is dropped for; the screen then repairs from the daemon's record by cursor, or by a snapshot read past that gap, and a screen that fell behind and has caught up on its queue gets one frame with no changes, carrying the drop mark and the newest cursor, so a session that goes quiet right after a drop still tells the screen it is behind. Workload: a session of 40 children with four lanes streaming; the screen side is held to [Spec-021](021-desktop-app-and-renderer.md)'s frame, heap and streaming budgets.
- **Interrupt, pause and resume on the lead.** `run.intervene` with `type: "interrupt"` is `Interrupt`: it carries `pending: "nextTurn" | "returnToDraft"` — the waiting messages go as the next turn, or they return to the draft, one line per message in send order — and `deliverFirst`, naming the waiting row `Send now` delivers first. It ends a live exchange with another session on both sides. On Claude Code the daemon declares `perTaskStopAffordance` in the session's `initialize` request, so an interrupt of the lead spares the children it dispatched, and it first moves a child running in the foreground to the background, so the interrupt spares that child too; on Codex the daemon ends the command the interrupt leaves running. `Interrupt everything` is this call plus `run.childrenStop`. `run.pause {targetRunId, expectedRunVersion}` acknowledges with the state `pausing` and emits `run.pausing`, then `run.paused`; it is refused on an invalid transition, an unknown run, a stale version, or a pause the provider cannot give, with that reason. `run.resume {targetRunId, expectedRunVersion}` is the toggle's second press and acknowledges `running`; a send continues a paused run through the same daemon path, and the waiting messages go as the continue.
- **Recovery after a restart.** When a restart finds the provider's record and the daemon's disagreeing beyond steps that only read, the person's answer travels as `run.recoveryResolve`, whose choices, question and recorded events [Spec-013 §Interfaces And Contracts](013-persistence-recovery-and-replay.md#interfaces-and-contracts) defines. On the run engine's side a restart settles each run it finds as `failed` or `interrupted`.
- See [Queue And Intervention Model](../domain/queue-and-intervention-model.md) § Boundary: Interventions vs Interactive Requests for the steer/respondToRequest distinction.
- The run-control surface on the wire is `run.subscribeState` and `run.subscribeQueue` (the live run state, and the items waiting for the run), `run.queueList`, `run.queueCreate`, `run.queueCancel` and `run.queueReorder`, `run.intervene`, `run.pause` / `run.resume`, `run.recoveryResolve`, and the child controls `run.childSteer`, `run.childInterrupt`, `run.childPauseSet` and `run.childrenStop`. The canonical stream carries the run-lifecycle events the state machine defines — `run.queued`, `run.starting`, `run.provider_initialized`, `run.running`, `run.turn_started`, `run.waiting_for_approval`, `run.waiting_for_input`, `run.pausing`, `run.paused`, `run.interrupted`, `run.completed`, `run.failed` and `run.rolled_back` (an undo's conversation cut alone) — with `run.step_limit_reached` (a turn ended at `Max steps per turn`, carrying the count behind `Continue`), `run.recovery_steps_added` (`{count, provider}`, the steps a restart added from the provider's own record) and `run.recovery_resolved` (the answer to a restart's mismatch); the intervention lifecycle `intervention.requested`, `intervention.accepted`, `intervention.applied`, `intervention.rejected`, `intervention.degraded` and `intervention.expired`; and an undo's one outcome event, `session.restore_finished`.
- **The child controls.** Steering a named child, interrupting it and toggling its pause are driver operations with calls of their own: `run.childSteer {targetRunId, childHandle, content, expectedRunVersion, clientIdempotencyKey}`, onto the child's own queue, which the daemon holds and which the queue reads take too; `run.childInterrupt {targetRunId, childHandle, expectedRunVersion, clientIdempotencyKey}`; and `run.childPauseSet {targetRunId, childHandle, paused, expectedRunVersion, clientIdempotencyKey}`, the toggle's two presses in one call. Each is offered only where the provider's initialization frame declares support for it. `run.childrenStop {runId}` is the one stop that walks a subtree: the daemon walks its own index of the run's children at every depth, one stop per id, never relayed through the lead, and reports each child's outcome, so a failure is reported per row. The child calls share one refusal, `run.child_control_refused`, with the reason `child_unknown`, `child_ended` or `provider_refused`; a hold the provider lost is reported as lost in the result, never as a refusal and never as a release. `childHandle` names only a provider's own subagent; a child the daemon bridges as its own run is steered and stopped through that run's own calls. The daemon owns the mechanism behind them: on Claude Code the pause is the hold on the child's next tool callback and the interrupt is that hold plus the end of the child's running command — never the provider's own stop verb, because a child stopped that way refuses the lead's next message and the wire offers no way to address the child directly — while a steer to a running child goes through the lead; on Codex all of them ride the child's own thread, `turn/steer`, `turn/interrupt`, and the boundary interrupt that makes the pause, for a child of the v1 collaboration shape at any depth, while a v2 subagent takes the interrupt directly and its steer goes through its parent. A paused child continues on the toggle's second press — `run.childPauseSet` with `paused: false`, which on Claude Code answers the held callback allow — or on a send into its box, which answers the hold deny carrying the person's words as the child's steer.

## State And Data Implications

- Queue items require durable storage and ordering metadata.
- Interventions require durable audit records even when they fail.
- Blocked states must remain associated with the same run id and same event lineage.
- **Intervention audit records carry an identity, not just an outcome.** The durable intervention record must hold the daemon-resolved admitting principal and the `origin` discriminator beside the outcome fields, with the storage layer enforcing that the two agree — principal present exactly on the user arm. Neither field is client-writable.

  **The resolved authority is published per turn, not left to be re-derived.** Recording the admitting principal on the intervention row makes the authority _resolvable_; it does not make it _reachable_ by a consumer that meters a turn rather than admitting one. At every turn boundary the run engine opens, it therefore resolves that turn's effective principal — the admitting user of the intervention that opened the turn (a steer), otherwise the user who started the run, otherwise the `system` arm where no user caused it — and publishes it as an **immutable per-turn scope** on the run's execution context, where the driver's usage normalizer reads it and carries it onto the metered row ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). Per-turn and immutable are both load-bearing: the normalizer stamps from the scope **bound to the turn whose stream produced the frame**, never from a mutable "current turn" read when the frame arrives, because a metered row for one turn routinely lands after the next turn has opened and a read-at-emission stamp would attribute that spend to whoever caused the following turn. A published scope is never mutated; a new turn mints a new one. The resolution rule itself is unchanged and stays owned by [Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior); what this adds is the obligation to publish it, so that no downstream fold has to recover the identity by ordering metered rows against turn-boundary events — the derivation the [api-payload-contracts.md §Authenticated Principal](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model) class rule forbids. The value is published and never emitted by this spec's surface: it mints no event, no column, and no wire member here.

- **Both durable tables store message bodies sealed.** Intervention rows and queue rows each carry a ciphertext field beside their plaintext payloads, sealed under the session's content key; an intervention's session is its target run's session. The key is what makes each table erasable: the purge overwrites the session's wrapped content key with zeros and deletes it before it deletes the session's rows, with a `TRUNCATE` checkpoint after commit, and `Erase all data` destroys the master key that wraps every content key. The field is nullable — a row that carries no body leaves it unset.

## Driver-Level Steer Mechanics

- **Codex driver**: native `turn/steer`. The daemon holds the message and steers it in at the thread's next tool boundary, so the content joins the running conversation as a new user turn and the turn continues from it; a steer aimed at a request that has already gone out lands at the step after. Because the daemon holds the waiting messages, an edit replaces the item in that hold and a reorder reorders it; a cancel and a resend there would put the message last.
- **Claude driver**: Claude Code accepts a message handed to it mid-turn and holds it until its next tool boundary, where the content joins the running conversation as a new user turn — so steer is delivered inside the same run, with no interrupt and no second run. The daemon's own id on each message is what a withdrawal, an edit or a reorder acts on: withdrawing is the provider's cancel on that id; an edit is a cancel of that message and of every message after it and a resend in order, made inside the one daemon call so the edited message keeps its place; and a reorder is a cancel of the waiting messages and a resend in the new order.
- **Generic driver fallback**: a driver that can accept nothing mid-run degrades to queue plus interrupt — interrupt the active run, hold the content as a queue item, and admit it as the next run, with the conversation history preserved. Neither V1 provider reaches this path.

### Steer Content Injection Point

- On both V1 providers: the content appears as a new user message in the running conversation at the next step boundary, and the model reads it as a follow-up the user sent.
- For degraded steer (queue + interrupt): content becomes the initial message of the new run. Previous conversation history is loaded from the session event log.
- In every case: steer content is marked with `source: 'steer'` in the event payload so the timeline can distinguish it from normal user messages.

The typed payload shapes for steer, interrupt, and cancel interventions are defined in [Queue And Intervention Model](../domain/queue-and-intervention-model.md) and verified against API contracts in that document's Field-Level Consistency section.

### The Step Bound On A Turn

`Max steps per turn` is how many steps a turn may take before it ends — one bound, the person's own, and **unlimited until they set a number**. With none set each provider does what it does on its own, which on both V1 providers is no cap at all, so the runtime adds no ceiling the providers do not have. The value every session starts from is the Runtime settings page's ([Spec-006 §Required Behavior](006-local-ipc-and-daemon-control.md#required-behavior)), and a session may carry its own override, set in one row of that session's inspector and held on the session record ([Spec-001 §Interfaces And Contracts](001-session-core.md#interfaces-and-contracts)). A number typed on the settings page governs sessions started later and reaches a session already running at its next turn; `Unlimited` puts the providers' own behavior back.

- **Claude Code driver**: the number is passed as `--max-turns` when the process starts, and that provider ends the turn itself at the limit. A change made to a live session applies at its **next** turn, by reopening that provider's own conversation by its id in a process started with the new flag — never by ending the turn that is running. The provider's own word for a step here is a turn, so `--max-turns` bounds the steps inside one exchange rather than how many exchanges a conversation may hold; the console says steps because that is what it bounds.
- **Codex driver**: that provider publishes no turn cap, so the daemon counts the steps of a turn itself — the count reset at each turn start — and calls `turn/interrupt` when it reaches the number. The count is the daemon's own, per turn, and never a running total across turns.

Either way the turn ends where it reached and the transcript carries one flow row, `Step limit reached · 40 · Continue`, stored as the run event `run.step_limit_reached` carrying the count so it survives a reload, whose press carries that same turn on; a message arriving from another session carries it on the same way ([Spec-014 §Sessions Talking To Each Other](014-multi-agent-orchestration.md#sessions-talking-to-each-other)). **The bound ends a turn and not a run**: it is not a budget, it mints no interrupt reason, it joins no stop condition, and the run stays exactly where it was, which is why `Continue` is a press and not a new run. It is the one bound on how long a turn runs, and it is the only thing that bounds how long two sessions go on messaging each other.

## Driver-Level Rollback Mechanics

- **Undo and fork are two things.** The conversation half of an undo is the driver method `rewindConversation`, the provider's own cut, made on the session the undo is in. `session.fork` is the design's Fork: it mints a new session of the same shape carrying history up to and including a message, the parent running on untouched; its provider leg is the driver method `forkConversation` (`ForkConversationParams`, `ForkConversationResult`) — Claude Code's `--resume-session-at` with `--fork-session`, Codex's `thread/fork` at an inclusive turn. A fork is never an undo.
- **Claude driver, the cut.** The cut is the control request `rewind_conversation {target_message_uuid, last_seen_user_message_uuid, interrupt_if_running}`. The driver translates the undo's message identity into the provider's message id and runs `--replay-user-messages`, so message ids appear on the wire. `last_seen_user_message_uuid` must name the newest prompt the daemon sent, or a cut past a later prompt is refused `stale_target`, compaction or not. A refusal arrives as `subtype: "success"` with `rewound: false`, so the driver reads `rewound`, never the subtype. The driver sends `interrupt_if_running: true`, so the cut itself ends a turn that is still live. The same flag makes the cut one-way for the run's agents: every agent started at or after the point is killed and recorded as stopped by the person, after which the provider refuses every later message to it, so those agents cannot be resumed and the question asked before an undo says so. Measured on Claude Code 2.1.276, three runs of three: the two running children were killed about four milliseconds after the request, and a later message to either came back refused. A point after the conversation's last compaction — `/compact` or automatic — is cut here in place, and a restart keeps that cut.
- **Claude driver, a point before the last compaction.** After an automatic compaction Claude Code refuses a cut to a point before it with `target_not_found`, and a cut to such a point that Claude Code does accept, after `/compact`, is lost at the next restart, because the resume rebuilds the session from the compaction summary. So for a point before the last compaction the adapter uses the Agent SDK's public `forkSession(sessionId, {upToMessageId, title})`, and the undo holds across every later restart. The adapter stops the process with SIGTERM — never by closing its input, which would let Claude Code finish the running turn and answer every queued prompt into the conversation being undone. It forks at the last assistant message before the point, with the session's own title, taking that message's id from the daemon's own record of the stream: a stream frame's `uuid` is the session file's entry `uuid`, and the SDK's own message read skips everything before the last compaction in a session file over 5 MiB. It restarts the headless CLI on the fork (`--resume <fork id>`) and writes every prompt not yet taken up — a prompt the stream has not replayed as a user message, which Claude Code keeps only as a queue row the fork does not carry — and every prompt sent while the process was down to the new process as soon as it spawns, where Claude Code answers them on the forked history. It maps message ids through each row's `forkedFrom`, because a session file that already branched from an earlier undo carries the dead branch's rows into the fork, rows Claude Code never loads, so the fork's row list is never taken for the conversation. The daemon imports only `forkSession` from `@anthropic-ai/claude-agent-sdk` — a file operation, with no model call and no process — because the session file format is Claude Code's private one and changes between versions, which the SDK tracks; the SDK's per-platform binary is left out of the install, and the SDK version is pinned and moves with the supported Claude Code version. The headless `fork_conversation` control request answers `unsupported` and is not used. All of this stays inside the daemon: the session keeps its identity, no second session appears anywhere, and nothing on screen names a provider session, a copy or a restart; the steps show only in the daemon's logs and events.
- **Codex driver.** The cut is `thread/revert {threadId, beforeTurnId}`, which drops that turn and every later one, cuts the thread's history and nothing else, and stays on the same thread. It keeps the cut past an automatic or an explicit compaction and across a resume, the next model request carrying the kept turns' own messages and replies rather than the summary. It works only on a thread with paginated history, so a conversation the person may undo is never started ephemeral. Codex 0.156.0 has no `thread/rollback`: a call to it is answered `-32600 unknown variant`. A turn still running is interrupted first and the revert follows, so the revert never races a live turn. The cut leaves the thread's agents running, and the daemon stops each agent started after the point by its own id, resumably — the opposite of the Claude leg, which is why the question asked before an undo is worded per provider. Measured on Codex 0.155.1, three runs of three: a three-turn thread reverted before its second turn came back listing one turn, the files the reverted turns had written were all still on disk, and an agent the third turn had started was still running and addressable after the cut.
- **The same cut hands back a turn too long for the window.** A turn that cannot fit even after compaction ends refused, and the provider keeps the refused message, so every later turn would fail the same way. The daemon cuts that turn at once with the same verb — `rewind_conversation` naming that message and the newest one the daemon sent, or `thread/revert` before that turn — and hands it back as a failed send: its words and attachments go back into the composer, and the rows the turn had already drawn stay marked superseded.
- **Neither verb touches a file.** Both cut conversation history only, so the files are always the daemon's own per-session checkpoint store ([Spec-013 §Required Behavior](013-persistence-recovery-and-replay.md#required-behavior)) — one mechanism, the same on both providers, never the provider's own file rewind and never a driver leg. That store is what every undo reads from, anchored on one of the person's own messages or on a named snapshot of the session, the snapshot only naming the point to return to ([Spec-008 §Turn-Boundary Snapshots](008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)). It covers what an agent's shell commands wrote, on both providers, through a capture before and after every command.
- **A confirmed cut.** The daemon appends `run.rolled_back` only for a cut the provider confirmed — `rewound: true` on Claude Code, the revert's answer on Codex, the restart on the fork — and that confirmation is the in-stream fence §Required Behavior's absorption reads. A refused cut appends nothing, and the undo's result names the conversation's failure with the provider's reason in the daemon's words.
- **Timeline presentation**: turns cut away are never deleted from `session_events`; projections mark them superseded — the turns after the point of the accepted `run.rolled_back` event — so clients render the undone history distinctly rather than dropping it. Late non-lifecycle appends from the epoch before a cut carry §Required Behavior's durable epoch stamp (the `sourceEpoch` + `sourcePosition` carrier pair, [Spec-005 §Event Type Enumeration](005-session-event-taxonomy-and-audit-log.md#event-type-enumeration)), so replay ranks them with their source epoch — never by append order — and the supersede marking survives projection rebuilds.

## Implementation Notes

- Queueing and intervention logic must live in the daemon or equivalent runtime authority, not in the currently open client.
- UI affordances may be optimistic, but canonical run state changes must come from runtime truth.
- Capability-aware controls are required so unsupported operations do not masquerade as working.
- Pause is an orchestration-layer construct. The daemon stops the run after the step in flight — through the hooks it registers for the session or passes to the provider's service, or a boundary interrupt where the provider has no hook for it — and persists conversation history and run state to local SQLite; nothing is queued to resume it. No intervention type is minted for pause, no hook is written into a file, and the pause's only configuration write is the trust records Codex needs for the daemon's own hooks (§Required Behavior).

## Pitfalls To Avoid

- Using client memory as the queue of record
- Calling reread or reattach semantics `resume`
- Treating waiting states as paused states
- Turning a message sent during a run into a second run, or holding it back until the run ends, when both V1 providers deliver it into the running run at its next step boundary
- Appending a late provider run-lifecycle event to a terminal run's timeline (the absorption rule exists precisely for this window) — or, inversely, absorbing non-lifecycle events the rule never covered (late usage telemetry is billable and must append) — or keying absorption on current run state alone, which misses stragglers from the execution before an undo's cut arriving after it (the epoch gate exists for exactly that arrival order)
- Treating an undo as log truncation — the authoritative log never truncates; the cut is a forward `run.rolled_back` event plus projection-level supersede marking
- Truncating or renumbering the rendered timeline when an edit and resend starts rather than when its `run.rolled_back` boundary is appended — the turns it will supersede dim and stay readable and pressable until the cut lands, and a cut that fails leaves them as they were
- Holding an edited message for a later resume, or reporting a resend as sent when the cut landed and the send did not — the resend goes at once, and a failed one puts the message back in the composer and says so on its row
- Comparing idempotency-key reuse bodies by ciphertext or by a persisted plaintext digest — the PII envelope is nonce-randomized, so ciphertext comparison always conflicts, and a retained digest outlives the text it hashes as a guessing oracle, in a backup or in the database's freed pages after a purge or `Erase all data`; the only admissible comparison is decrypt-and-compare under the session's content key, failing closed to `intervention.idempotency_conflict` when the stored body will not decrypt

## Acceptance Criteria

- [ ] A user message sent while a run is active is durable before it is delivered, is then delivered into that same run at its next step boundary on both V1 providers keeping the run id, and never becomes a second run; several such messages are delivered in the one order the daemon holds, which `run.queueReorder` replaces whole; an edit replaces a waiting message in place in one `run.queueCreate` call, its old item `superseded` and the edited message in its place, and is refused once the agent has taken the message; and a message that has waited past the daemon's delivery timeout reads not delivered with its reason and is sent again from its own row.
- [ ] An interrupt ends the run it names and the command that run was running, spares the agents that run dispatched, and delivers whatever was waiting for that run as the next turn; with nothing waiting the run rests `interrupted`.
- [ ] No undo is applied before its dry run has been answered; an undo of the files alone appends no `run.rolled_back` and marks no turn superseded; and an undo that would stop agents or commands started after the point asks first, naming each count from the daemon's own tree, and on Claude Code adds that those agents cannot be resumed.
- [ ] Pause (stop after the step in flight and persist, with nothing queued to resume it) and resume operate on the same run id and same run history: the toggle's second press, or a send, continues the run from exactly where it stopped with nothing repeated, waiting messages are delivered on the continue, and a paused or pausing run can still be interrupted.
- [ ] Unsupported intervention requests result in explicit `degraded` or `rejected` outcomes rather than silent behavior changes.
- [ ] With `Max steps per turn` unset, a turn on either provider runs to its own end and nothing of this runtime's counts, caps or interrupts it. With a number set, a Claude Code session is started carrying it as `--max-turns` and a Codex turn is ended by the daemon's own per-turn count at that number; either way the turn ends there, the run is left where it was rather than interrupted, the flow carries `Step limit reached · 40 · Continue`, and the press carries the same turn on. A number set on a live session takes effect at its next turn and never ends the turn in flight, and a per-session override leaves the settings-page value alone.
- [ ] A provider run-lifecycle event arriving for a run already terminal never appends a `session_events` row and never advances `runVersion`: a terminal-class straggler no-ops in the at-most-once terminal emitter; a non-terminal lifecycle straggler surfaces only as the `run.late_event.absorbed` OTel diagnostic; and a run-lifecycle event sourced from the execution before an undo's cut, arriving after the cut, is absorbed identically — never appended against the new epoch — on a runtime binding the cut kept and on one a fork and restart froze alike. Non-lifecycle provider events in the same window (usage telemetry foremost) still append under their own families' rules.
- [ ] An undo is one `session.restore` call aimed at a message or snapshot identity, never a position, with one of the scopes, and it reports what it did as one row and one `session.restore_finished` event: everything asked for applied, part applied naming the part that did not and its cause, or `Undo failed · <cause>` with the conversation and the files as they were; turns after the point are marked superseded only when the conversation went back; a call retried under the same idempotency key never cuts twice; it is offered through a running turn and ends that turn itself; and a message sent while it runs is answered on the undone conversation.
- [ ] The conversation cut holds on both providers: on Claude Code `rewind_conversation` carries the newest prompt the daemon sent as `last_seen_user_message_uuid`, a refusal is read from `rewound: false`, and a point before the last compaction is reached by the fork and the restart on it, which holds across a later restart, keeps the session's identity and names no copy or restart on screen; on Codex `thread/revert` cuts a conversation that was never started ephemeral and holds past a compaction and across a resume. What an agent's shell commands wrote goes back with the files on both providers.
- [ ] Run-control authorization is owner-only and blind to what started a run: the session's owner passes the `Action::"intervene"` adjudication against a run **whatever started it** — for interventions and for the orchestration-layer `run.pause` / `run.resume` identically — with `initiatorId` and the run's origin never read as authorization inputs; a denied intervention settles `rejected`, and a denied `run.pause` / `run.resume` request is rejected untouched with no run-state mutation composed (the orchestration verbs hold no `InterventionType` membership and settle no `InterventionResult`). Every session runs on the one machine that runs it, so every run is a run of the machine owner's own agents, adjudicated under the node-owner user principal the daemon itself binds on its local socket ([API Payload Contracts §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model)).
- [ ] Edit and resend is the undo carrying the edited message, at the conversation-and-files scope — one call, one idempotency key, one result — offered on every message the person sent, on both providers and through a running turn; the turns it will supersede dim and stay readable until the cut lands and are marked superseded only then; the edited message goes at once as the next send on the cut conversation; and a resend that fails puts the edited message back in the composer with everything it carried, its row naming the cause and, where the cut had landed, saying that the conversation went back and the resend did not.

## Design Decisions

- A person reorders their own waiting messages on one run. A message sent into a running turn waits as a row at the end of the transcript, and on hover or keyboard focus that row offers a grip that drags it — or the up and down arrows with the row focused — to move it in the stack, beside `Edit`, which puts it back into the draft and sends it back into its own place, `Remove`, after which nothing reaches the agent, and `Send now`, which interrupts the turn, delivers that row first and lets the rest follow in order as the next turn's messages. A reorder is one order the daemon holds over the messages still waiting, sent whole as `run.queueReorder`: on the Claude driver the message has already gone to the provider, which holds it to the next tool boundary, so the daemon cancels those rows and resends them in the new order; on the Codex driver the daemon holds the message itself and reorders its own hold, because a cancel and a resend there would put the message last. This is the **send order of one person's own waiting messages on one run**. The admission queue carries no priority attribute: nothing ranks one run's work ahead of another's, and admission itself stays canonical queue order.
- The run controls are the ones §Interfaces And Contracts names — the queue calls, the interrupt, pause and resume, the answer to a restart's mismatch, and the child controls — over canonical queue order. Undo is not one of them: an undo is `session.restore`, a session operation rather than a run control, and edit and resend is that same call. The same-agent provider switch is not one either: `agent.configUpdate`'s `interruptAndSwitch` flag dispatches the **existing** `interrupt` intervention rather than minting a control ([Spec-014 §Same-Agent Provider Switch](014-multi-agent-orchestration.md#same-agent-provider-switch), D-014-26).
