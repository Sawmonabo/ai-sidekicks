## Purpose

Define the canonical control semantics for queued work, active-run steering, pause and resume, and interrupt behavior.

## Scope

This spec covers queue admission, interventions, blocked states, and the control outcomes the person sees.

- Workflow-level orchestration semantics

## Required Behavior

- **A message sent while a run is active is delivered into that run.** It is persisted as a queue item before anything else happens to it, and it is then delivered to the running run at its next step boundary on both V1 providers — never held back for a later run and never silently turned into a second one. Until the run takes it the item is waiting, and it says so. Several such sends stack in the order they were sent and are delivered in the one order the daemon holds for them. The daemon stamps every message with an id of its own — a UUID on Claude Code, `clientUserMessageId` on Codex — and that id is what lets a waiting message be withdrawn, edited or moved. `Remove` withdraws it, and nothing reaches the agent. `Edit` is one daemon call that replaces the waiting message in place, so the edited message keeps its place: the old item reads `superseded`, and the call is refused once the agent has taken the message. A reorder is one order the daemon holds over the messages still waiting, replaced whole. On Claude Code the message is handed to the provider at once and the provider holds it until its next tool boundary, so a withdrawal is that provider's own cancel on the id, an edit is a cancel of that message and of every message after it and a resend in order, and a reorder is a cancel of the waiting messages and a resend in the new order; on Codex the daemon holds the message itself and steers it in at the tool boundary, so an edit replaces the item in the daemon's own hold and a reorder reorders that hold — a cancel and a resend there would put the message last — and a steer aimed at a request that has already gone out lands at the step after, the item waiting until then. Delivering one waiting message ahead of the rest is an interrupt of the run followed by that message, the remainder following in order as the next turn's messages. An item that has not been delivered because the daemon cannot be reached stays waiting; an item whose delivery failed, or that has waited longer than the daemon's own delivery timeout, is recorded as not delivered with its reason and can be sent again from the item itself. The two are distinguishable states, never one hopeful one. Follow-up work that is not a user message — orchestration-authored input — stays an ordinary queue item admitted in canonical order.
- `pause` is an orchestration-layer construct the daemon owns: it stops the run after the step already in flight — by the provider's own hooks where the provider has them and by a boundary interrupt where it does not, per the pause-mechanism bullet below — and persists conversation history and run state; nothing is queued to resume it. The resulting `paused` state must not mean queue-drain suspension or blocked waiting. Pause is one toggle rather than a pair of controls: the same control continues the run, and so does sending anything to it, in both cases from exactly where it stopped with nothing repeated. There is no pause-immediately variant and no separate resume control. While the step in flight is still finishing, the run is `pausing` and not yet `paused`, and that is a state a reader can see; waiting messages stay waiting while the run is paused and are delivered when it continues; and a paused run can still be interrupted.
- `resume` must return a `paused` run to active execution with the same run id.
- `interrupt` must transition a run directly to `interrupted`. Interruption is a synchronous or near-synchronous provider call with no intermediate state. It reaches the run it names and nothing else inside the session: the agents that run dispatched are spared and keep working, and an interrupt never cascades, on a lead run or on a child. The one thing it reaches outside the run is the other end of a live exchange with another session, whose turn ends with this one and whose queued messages are dropped, as [Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other) states. The command the run was running is ended with it. Whatever was waiting for that run is delivered at once as the next turn, so an interrupt with messages waiting leaves the run working again; with nothing waiting the run rests `interrupted` until a later send returns it to running. On Claude Code the daemon declares the per-task stop affordance so a plain interrupt never sweeps the run's background subagents, and where a child is running in the foreground the daemon first moves that child to the background, so the interrupt spares it as it spares every background child; on Codex the daemon ends the command the interrupt leaves running. Its row in the flow reads `Turn interrupted`; while agents the turn dispatched are still running its text is `N sidekicks still running` (`1 sidekick still running`), and while it was in an exchange with another session its text names that ([Spec-011 §Flow Row Kinds](011-transcript-and-reasoning.md#flow-row-kinds)).
- **Stopping everything is the separate act, and it is not atomic.** One control stops the run and every agent it dispatched at every depth, one stop per agent identifier taken from the daemon's own record of the run tree; an agent whose stop failed is reported on its own and stops nothing else from being reached. It is the one stop that does **not** deliver what was waiting: the run's waiting messages are withdrawn rather than sent as the next turn, and their text is handed back to the user to send again. What a stopped child then accepts is the per-provider rule above — final on Claude Code, re-enterable on Codex. Its row in the flow reads `Sidekicks stopped` on Claude Code and `Sidekicks interrupted` on Codex, its text the names of the agents that stopped, in dispatch order, separated by commas; an agent whose stop failed is left out of that text and carries the failure on its own row. Neither interrupt row says how the stop was done.
- **Where a provider reports the daemon's own interrupt in the same frame shape as an execution error, the daemon records it as an interrupt and never as a failure.** It marks the turns it interrupted itself and reads its own mark rather than the frame's; a provider that ends a stopped turn as interrupted and a failed one with a code is followed as it reports. A child's failure is read from that child's own update and never from the lead's result, which can report success while a child dies.
- Waiting for approval or input must remain `waiting_for_approval` or `waiting_for_input`, not `paused`.
- Every intervention outcome must be visible in the canonical event stream.
- Queue items must support cancellation before admission.
- **The states of a turn.** A run is idle before it starts and running while it works; an approval or an input request leaves it waiting and answering that returns it to running; it is done when it finishes. `Interrupt` takes a running run to `interrupted`, and a send — or the waiting messages going as the next turn — takes it back to running. `Pause` takes a running run through `pausing` to `paused`, and the toggle or a send takes it back to running. A run freezes its checkout root when it starts, so a working-folder move asked for while it runs is recorded as an intent on the session and applied when the run reaches a boundary. A child run carries the same machine on its own: it pauses and continues on its own toggle, its own interrupt takes it to `interrupted` and a steer takes it back to running, a stop that reaches a subtree — `Interrupt everything` or `Stop all running` — takes a running or interrupted child to its own `stopped` state, final on Claude Code, where the provider refuses every later message to a child the user stopped, so no send returns it to running, and re-enterable on Codex, where a send takes it from `stopped` back to running — and a finished child returns to running on a send into its own steer box, its pause and interrupt coming back with the run.
- **How the pause is made true on each provider.** The daemon pauses with the provider's own hooks where the provider has them and with a boundary interrupt where it does not; the hooks are registered for the session over the wire or passed on the command line, and no hook is ever written into a file. On a Claude Code lead run it is hooks registered in the session's `initialize` request and answered over the wire: one ends the turn after the step in flight, the other denies whatever a woken lead tries while the pause holds, both carrying the reason `Paused by you` — so a lead a child wakes runs one model call, is denied its tool, and stops again. On a child run — a provider's own helper at any depth on either provider, or an agent the bridge runs — it is the daemon's pre-tool hook holding that child's next tool call, with no time limit; a hold a daemon restart orphaned on Claude Code can never be answered, so the child it was holding is drawn as interrupted and continues from its own box. On a Codex lead run it is the boundary interrupt: the hook holds the thread's next call, the daemon interrupts the turn, the hook denies the parked call so it cannot run, and starting the next turn is the continue; a command still running finishes first, and the run is pausing until it has. On Codex that hook is the daemon's one pre-tool hook — the same hook that reports a command — passed with `-c` when the account home's Codex service starts, so it serves every conversation on that service, with its timeout set to a day as on Claude Code, since Codex sets no ceiling on a hook's timeout, and a hold ends only by an answer, allow or deny, never by the hook ending; and because Codex runs no untrusted hook, the daemon trusts it and its post-tool partner through Codex's `config/value/write` before any conversation loads. The pause writes nothing else into a Codex configuration file, and the trust write never cleans, rewrites or reorders any other entry there. The user's own hooks keep running beside the daemon's, and a hook the provider refuses at `initialize` is learned from that refusal and remembered rather than retried, with the control that depended on it saying why it is unavailable.
- **A child run's controls are the session's controls.** Every live child run takes the same pause, interrupt and steer the session's own run takes, whatever dispatched it and whichever provider it runs on. Interrupting one child reaches that child alone: the agents it dispatched keep going, and so does whatever dispatched it. Continuing a parent continues the parent alone. A steer to a running child lands at its next tool call, or as it finishes. Steering a paused or interrupted child starts it again with everything it knew, and a finished child starts again on a send — a provider's own helper through its parent, which is asked to message it, and an agent the bridge runs as a new turn or message on its own conversation. A child stopped for good on Claude Code takes no later message at all, because the provider refuses every message to a child the user stopped; the same stop on Codex is an interrupt the child comes back from. A paused child's hold is lossless: its next tool callback simply goes unanswered, so the child burns no tokens and loses nothing, and the hold ends only by an answer — allow from the toggle, or deny carrying the user's own typed words, which the child reads as its instruction. The hold is routed per child by the id the hook payload carries for the acting thread, it works at every permission level including the least careful one, and it is held open by setting the callback's timeout far past any wait a person would sit through; a provider canceling a held callback is a lost pause and never a release, and a hold left unanswerable by a daemon restart leaves its child interrupted rather than held forever. Freezing one child at the process level is not offered, because both providers run their subagents inside the parent process: a process freeze stays an option only for pausing a whole session. A capability a provider refuses is learned from the refusal and remembered for that child.
- **Undo: going back to a point in the session's own history.** `Undo to here` on one of the person's own messages, `Restore` on a snapshot in the inspector, and the rewind menu's three rows — `Restore conversation and files`, `Restore conversation` and `Restore files` — are one operation with one contract, on both providers and never absent. In the same session it puts back the conversation by the provider's own conversation cut and the files by the daemon's own checkpointer: the conversation and the files together, the conversation alone, or the files alone, to the moment before one of the person's own messages or to a named snapshot. It is not an intervention and adds no run control. Its target is always a stable message or snapshot identity; any position the operation needs stays inside the daemon and the provider adapter. Nothing is applied before the dry run has been read and answered: the dry run names the files it will put back, the lines that change, the files it will skip counted by reason (a symbolic link, a hard link, something that is not a file, a moved folder, a file too large to keep, a branch a command moved), the commands still running after the point, the agents that would stop and whether they can resume, the ignored folders it does not restore, whether commands ran after the point, and the paths another session in the same folder changed since the point, which stay as they are unless the person includes them. Before an undo that would stop agents or commands started after the point, it asks in place, naming each count from the daemon's own record of the run tree; on Claude Code it adds that those agents cannot be resumed, because the conversation cut there ends them for good, while on Codex the cut leaves them running and the daemon stops each by its own id, resumably. Declining changes nothing. On an answer the undo stops those commands first, each by its provider's own verb, and those agents one stop per id, ends a turn still running, and then restores. It is offered through a running turn, and it is never refused because a turn is running or because the point lies before a compaction. A message sent while the undo runs is never lost: it is answered on the undone conversation.

  The files are the daemon's own per-session checkpoint store ([Spec-013 §Required Behavior](013-persistence-and-recovery.md#required-behavior)), which keeps a copy of each file before every edit the agent or any of its children makes and at every prompt that starts a turn, and a capture before and after every command an agent or a child runs — so what an agent's shell commands wrote goes back too, on both providers. Two sessions in one folder keep their changes apart: an undo puts back only its own session's changes. The git snapshot never puts files back. Where the session works — its own worktree or the project's checkout — changes nothing about an undo, because the copies are held with the session outside the checkout.

  **One result, reported as one row.** An undo can apply in part: the conversation can go back while the files cannot, or the reverse. Its result names what was asked for, what was restored — the conversation and the files, the conversation, the files, or nothing — and, for each part asked for that did not apply, its failure with the daemon's own reason. Every outcome is stored as one event, `session.restore_finished`; `run.rolled_back` records the conversation cut alone, and an undo of the files alone appends none. When everything asked for applied, the transcript row reads `Restored to before <the message's first words>`, `Restored to <snapshot name>`, or `Files restored to before <…>` for files alone. When part applied, it names the part that did in those words and the part that did not with its cause: `Restored to before <…> · files not restored · <cause>` or `Files restored to before <…> · conversation not restored · <cause>` (`Restored to <snapshot name>` and `Files restored to <snapshot name>` for a snapshot). When nothing applied, it reads `Undo failed · <cause>`, naming each distinct cause, as in `Undo failed · <one cause> · <another cause>`, and a cause both parts share once, and the conversation and the files are as they were. The cause is the daemon's own, in words. A snapshot name that sits mid-sentence lowercases its first letter only, and a name that opens on an acronym keeps it. The turns after the point stay in the transcript marked superseded, and only when the conversation went back; the authoritative log never truncates or rewrites ([ADR-016](../decisions/016-shared-event-sourcing-scope.md)). A retried call under the same idempotency key never cuts twice.

- **Edit and resend is one operation, offered for every message the person sent, on both providers and through a running turn.** The pencil puts the message, with everything it carried, back into the draft, and Enter resends it from that point. The resend is the undo above at its conversation-and-files scope, carrying the edited message: one intent, one call, one idempotency key, one result. It puts the conversation and the files back to the moment before that message with the same dry run as an undo, whose count the editing row shows before Enter: a skipped file is named, and a path another session in the same folder also changed since the point is named and left as it is unless the person includes it. Then it sends the replacement. It asks first under the same rule as an undo when agents or commands started after the point are still running; declining keeps the edit and changes nothing. While it is in flight the turns it will supersede dim and stay readable and pressable, and they are marked superseded when the cut lands, never before. The edited message goes at once as the next send on the cut conversation; nothing holds it for a later resume. A resend that fails, for any reason, puts the edited message back in the composer with everything it carried and lands one system message naming the cause, `Resend failed · <cause>`; where the cut had already landed, that same row goes on to say the conversation went back, `Resend failed · <cause> · restored to before <the message's first words>`, rather than leaving the conversation cut with nothing sent.
- **Post-interrupt late-event absorption.** A provider **run-lifecycle** event — a run-state-transition report — that arrives for a run already in a terminal state (`completed`, `interrupted`, `stopped`, `failed`) is **absorbed, never appended**: a terminal-class straggler routes into the at-most-once terminal emitter ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle) emission contract) and no-ops there; a non-terminal lifecycle straggler is dropped from the lifecycle path entirely and recorded only as a `run.late_event.absorbed` **diagnostic non-event** on the daemon's telemetry (an OTel log record per [Observability Architecture](../architecture/observability-architecture.md) — never a `session_events` row), with no state transition and no `runVersion` advance. Absorption also keys on **execution epoch**, not current run state alone: the epoch is the interval between accepted `run.rolled_back` cuts ([Run State Machine §Invariants](../domain/run-state-machine.md#invariants)), and a run-lifecycle event sourced from the execution before a cut that arrives after it is absorbed identically — the Spec-005 `(runId, runVersion)` key cannot catch it, because the cut advanced `runVersion`. Epoch attribution needs no wire token: the driver owns one serialized connection to its provider process, so the confirmation of the driver's `rewindConversation` is an **in-stream fence** that totally orders the cut against event delivery; once it confirms, the driver delivers no run-lifecycle event of the execution before the cut, and the daemon's per-binding cursor — an **(epoch, position) pair** whose position advances at each turn boundary observed in the binding's ordered delivery and freezes at the fence — absorbs any straggler that slips through. Run-lifecycle events are attributed per **runtime binding**, and both arms of the rule are V1. A cut made in place — Codex's `thread/revert`, and Claude Code's `rewind_conversation` for a point after the last compaction — keeps the run on its runtime binding, whose **delivery generation rotates at the fence**: the confirmation closes the generation before the cut, and deliveries after the fence open the new epoch. A cut to a point before Claude Code's last compaction is made by a fork and a restart (§Driver-Level Rollback Mechanics), which mints a new provider session: the old runtime binding **freezes wholesale** at the fence, every delivery on it belonging to the epoch before the cut at its retained (epoch, position) pair, and the new runtime binding opens the new epoch. Absorption is scoped to the run-lifecycle family and a provider's permission ask: a permission ask the cursor attributes to the epoch before a cut is absorbed as a lifecycle straggler is — nothing is appended, no pending approval opens, no run-state transition fires, and the daemon logs it — because it is no passive row and only the approval normalizer, which it never reaches, fills `approval.requested`. The other non-lifecycle provider events arriving in the same window — usage telemetry above all, plus assistant output, tool activity, and artifact publication — append normally under their own families' rules (late usage telemetry must still reach the cost ledger; absorption never drops billable usage), but never epoch-blind: a non-lifecycle row the cursor attributes to the epoch before a cut appends **carrying that attribution durably**, stamped at ingestion from the straggler's **operation association** — the run engine records each provider-side operation (tool call, message item, artifact production) against the (epoch, turn) current when it opened, and the straggler's correlation key resolves that recorded pair, because re-executed turns reuse ordinals and a content-asynchronous straggler (a long-running tool's progress, a delayed usage aggregate, a late-completing artifact upload) must rank by its operation's opening pair rather than by when it arrived. A straggler with no resolvable operation linkage takes the retained pair of the closed generation or the frozen binding, which sits above the point the cut went back to, so it is always superseded with its epoch and never resurfaces as current; on the in-place arm a delivery after the fence is current by the fence's order. It is never a read-time guess and never the run's current position. The typed stamp is the cross-cutting `sourceEpoch` + `sourcePosition` payload pair ([Spec-005 §Event Type Enumeration](005-session-event-taxonomy-and-audit-log.md#event-type-enumeration)), which §Driver-Level Rollback Mechanics' supersede projection consumes, so rebuilt projections mark a late row superseded exactly like the in-time rows of its epoch. The near-synchronous interrupt hedge above is the _reason_ the window exists — a provider may emit briefly after the daemon records the terminal; canonical-stream visibility of the intervention outcome is satisfied by the terminal event itself, and absorption adds no second visible outcome.

- **Every accepted intervention records the device it came from.** A request that arrived over a connection, from this machine's own window or a linked device, and a queued message both record the device they came from, found by the daemon from the admitting connection at acceptance and never taken from the request; the daemon's own in-process stop when a spend or token limit is reached arrives over no connection, and its intervention, like an orchestration-authored queue item, records no device — a NULL `device_id` means the daemon itself wrote the row, and only those two daemon paths write one. No request names a person ([ADR-011](../decisions/011-generic-intervention-dispatch.md)). Producers write the device inside the transaction that accepts the intervention — never a second write that a crash could separate. Nothing checks who sent a run-control request: a connection carries its device, and every device the account links may steer, interrupt, pause and resume any run of the session, whatever started it.
- **Queue-item bodies are stored plain, exactly as intervention bodies are.** A queue item's send body sits in the item's `payload` as plain text, like every other column. Content authored by orchestration rather than by the person — a workflow phase input, an orchestrated child-run prompt — is stored the same way. A purge deletes the session's rows with SQLite's `secure_delete` on, so the freed pages hold nothing readable, and checkpoints the write-ahead log with `TRUNCATE` once the delete commits ([Spec-020 §Ordering And Atomicity](./020-data-retention-and-gdpr.md#ordering-and-atomicity)), so the event copy and the queue copy of the person's words go in the same act, with no second erasure path to forget. Queue rows remain **durable and never-evented**, drained but never deleted and canonical for audit. Every field admission and drain select on — state, run binding, session — is its own column and none of them is content.

## Default Behavior

- A user message sent while a run is active is persisted as a queue item and then delivered into that same run at its next step boundary. Queueing is how the message is made durable, not a way of holding it back for a later run.
- Queue ordering default is FIFO within the target scheduling scope.
- The person's steer is always a queue send (`run.queueCreate`): the message is persisted as a queue item and delivered into the running run at its next step boundary, which both V1 providers do, so a steer has no degrade path. Pause does not require driver support either — it is an orchestration-layer run-control mutation (`run.pause` / `run.resume`), composed by the daemon out of the session's own hooks and, where a provider has none, a boundary interrupt (stop at the step boundary and persist; the toggle's second press or a send continues), and **not** dispatched through the driver-facing `applyIntervention` path that steer and interrupt follow ([ADR-011](../decisions/011-generic-intervention-dispatch.md); no intervention type is minted for it — see [Queue And Intervention Model](../domain/queue-and-intervention-model.md)).

## Fallback Behavior

- If a paused run cannot be resumed because driver state is lost, the system must transition it through recovery logic and then to `failed` or `interrupted`; it must not pretend the same run resumed.
- If queue persistence is temporarily unavailable, the system must reject new queue creation rather than silently storing queue state only in client memory.

## Interfaces And Contracts

- `QueueItemCreate`, `QueueItemList`, and `QueueItemCancel` must operate against runtime-owned durable state.
- `InterventionRequest` must include target run id, intervention type, and a **mandatory** version guard (`expectedRunVersion`). The guard is **fail-closed**: the comparand is required on every intervention, and an absent comparand is **rejected**, never applied — an optional guard would let a caller bypass the stale-request guard by omitting the field (Plan-002 D-002-2). `expectedRunVersion` is compared against the target run's `runVersion` — an **any-run-progression counter** that increments on every run progression, applied interventions included (not only `run.*` state-machine transitions), so two steers racing on a still-`running` run cannot both pass undetected (Plan-002 D-002-1). `runVersion` is the run aggregate's optimistic-concurrency token, distinct from the immutable `EventEnvelope.version` wire-contract field ([Spec-005 §EventEnvelope Version Semantics](005-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics)). Payload fields vary by type: `steer`, which only the daemon builds when it delivers a queued message, includes `expectedTurnId`, `content`, and optional `attachments` — typed `ArtifactId[]`, an ordered list of ids into [Spec-012](012-artifacts-files-and-attachments.md)'s manifest space and never an untyped element or an inline byte payload, carrying that spec's order-preserving, never-silently-dropped, refused-whole-rather-than-truncated carrier contract as [API Payload Contracts §Plan-003 — Provider Driver Contract (Internal Interface)](../architecture/contracts/api-payload-contracts.md#plan-003--provider-driver-contract-internal-interface) states it once for both ends of the carrier; `interrupt` includes an optional `reason`. Every intervention request additionally carries a **mandatory** requester-generated `clientIdempotencyKey` (UUID) — the second, orthogonal guard ([Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior)): `expectedRunVersion`, the stale-request guard, defeats a stale request carrying outdated intent; the key, the duplicate-request guard, defeats duplicate applications of the same intent (return-or-conflict, `intervention.idempotency_conflict`). Whether a reused key carries the same or a differing body is decided by comparing a steer's stored `content` with the request's ([Queue And Intervention Model](../domain/queue-and-intervention-model.md) owns the canonical rule). See [Queue And Intervention Model](../domain/queue-and-intervention-model.md) for canonical payload shapes.
- `InterventionResult` must distinguish the 6 canonical intervention states: `requested`, `accepted`, `applied`, `rejected`, `degraded`, and `expired`. A version guard mismatch produces `expired`. An authorization failure produces `rejected`.
- Intervention dispatch uses `applyIntervention` (see [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md) and [ADR-011](../decisions/011-generic-intervention-dispatch.md)), which routes to the appropriate driver-specific handler based on intervention type and declared capabilities. A request carries no actor field: the write records the device its connection carries. The orchestration-layer `run.pause` / `run.resume` run-control mutations never ride `applyIntervention` (they are daemon-handled orchestration verbs holding no `InterventionType` membership), and neither path checks who sent the request.
- **Undo is `session.restore`, not an intervention.** On a session, `session.restorePreview({ target, scope })` answers the dry run and changes nothing, and `session.restore({ target, scope })` applies it. `target` is a stable message identity or snapshot identity, never a numeric or provider position; `scope` is `"conversation-and-files"`, `"conversation"` or `"files"`. The request takes a per-session `clientIdempotencyKey`, so a retried call never cuts twice; a `resend` member carrying the edited message makes edit and resend one call; and `includeAlsoChanged` — false unless the person pressed the include line — also puts back the paths another session in the same folder changed since the point. The result carries `requested` (the same values), `restored: "conversation-and-files" | "conversation" | "files" | "nothing"`, the figures of what went back, and for each requested part that did not apply `failures.conversation` / `failures.files` with a `reason`; when the call carried a resend that did not go after the cut landed, the result says so with its reason. Every outcome is stored as `session.restore_finished`; `run.rolled_back` records the conversation cut alone. The checkpoint store, the dry run's figures and its skip reasons are [Spec-013 §Interfaces And Contracts](013-persistence-and-recovery.md#interfaces-and-contracts)'s. The conversation half is the driver's `rewindConversation` ([Spec-004 §Interfaces And Contracts](004-provider-driver-contract-and-capabilities.md#interfaces-and-contracts)), made against the session's live runtime binding, which the daemon resolves; clients never name a binding or a position. The driver's `forkConversation` (`ForkConversationParams`, `ForkConversationResult`) serves `session.fork` and never an undo.
- **The queue calls.** `run.queueCreate` takes one typed message — its text and its attachments (`ArtifactId[]`), the id the daemon stamps on it, and its target, the lead or a child's handle — plus the skills the person picked from the composer's `/` and `$` list, each by its name and folder as `skill.list` gives them, which a Codex agent receives as Codex's own skill input item naming the `SKILL.md` path the daemon builds from that folder, and an optional addressee `to` naming another session, which is how the person writes to another session with `@name` from the composer: one Send, which the daemon routes. The daemon refuses a send whose picked skill matches no row of `skill.list` by name and folder, with `skill.path_refused` (`not_listed`) ([Spec-029 §The call form](029-skills.md#the-call-form)). For an edit it carries `replacesQueueItemId`, and that one call replaces the waiting message in place: the old item becomes `superseded`, the edited message keeps its place, and the call is refused once the agent has taken the message. `run.queueList` returns each waiting item with its text, its state and, for an item not delivered, its reason. `run.queueCancel` is `Remove` alone. `run.queueReorder {sessionId, childHandle?, queueItemIds}` takes the full new order and is refused unless `queueItemIds` names exactly the items still waiting; the daemon reorders its own hold on Codex and cancels and resends in the new order on Claude Code. `run.queueList`, `run.subscribeQueue`, `run.queueCancel` and `run.queueReorder` take a child's handle too, so a child's waiting rows work as the lead's.
- **The run streams.** `run.subscribeState` carries the run's state (its member `newState`, `pausing` among the values), its activity and the row dots; `run.subscribeQueue` carries the waiting items. One state stream per session in view carries the lead and every child, and one queue stream per agent flow on screen, so a window holds at most three run streams whatever the fan-out; a session out of view reads `session.list` and resubscribes from its cursor when it returns. Each subscription is batched like every session stream and queues at most 1,024 events before the screen is dropped for; the screen then repairs from the daemon's record by cursor, or by a snapshot read past that gap, and a screen that fell behind and has caught up on its queue gets one frame with no changes, carrying the drop mark and the newest cursor, so a session that goes quiet right after a drop still tells the screen it is behind. Workload: a session of 40 children with four lanes streaming; the screen side is held to [Spec-021](021-desktop-app-and-renderer.md)'s frame, heap and streaming budgets.
- **Interrupt, pause and resume on the lead.** `run.intervene` with `type: "interrupt"` is `Interrupt`: it carries `pending: "nextTurn" | "returnToDraft"` — the waiting messages go as the next turn, or they return to the draft, one line per message in send order — and `deliverFirst`, naming the waiting row `Send now` delivers first. On Claude Code `nextTurn` is the interrupt with `cancel_queued` false, whose surviving messages start the next turn themselves, and on Codex the daemon's own `turn/start` once `turn/completed` arrives `interrupted`; `returnToDraft` and `Interrupt everything` drop what is waiting, `cancel_queued` true on Claude Code and the daemon's own hold on Codex. It ends a live exchange with another session on both sides. On Claude Code the daemon declares `perTaskStopAffordance` in the session's `initialize` request, so an interrupt of the lead spares the children it dispatched, and it first moves a child running in the foreground to the background, so the interrupt spares that child too; on Codex the daemon ends the command the interrupt leaves running. `Interrupt everything` is this call plus `run.childrenStop`. `run.pause {targetRunId, expectedRunVersion}` acknowledges with the state `pausing` and emits `run.pausing`, then `run.paused`; it is refused on an invalid transition, an unknown run, a stale version, or a pause the provider cannot give, with that reason. `run.resume {targetRunId, expectedRunVersion}` is the toggle's second press and acknowledges `running`; a send continues a paused run through the same daemon path, and the waiting messages go as the continue.
- **Recovery after a restart.** When a restart finds the provider's record and the daemon's disagreeing beyond steps that only read, the person's answer travels as `run.recoveryResolve`, whose choices, question and recorded events [Spec-013 §Interfaces And Contracts](013-persistence-and-recovery.md#interfaces-and-contracts) defines. On the run engine's side a restart settles each run it finds as `failed` or `interrupted`.
- See [Queue And Intervention Model](../domain/queue-and-intervention-model.md) § Boundary: Interventions vs Interactive Requests for the steer/respondToRequest distinction.
- The run-control surface on the wire is `run.subscribeState` and `run.subscribeQueue` (the live run state, and the items waiting for the run), `run.queueList`, `run.queueCreate`, `run.queueCancel` and `run.queueReorder`, `run.intervene`, `run.pause` / `run.resume`, `run.recoveryResolve`, and the child controls `run.childSteer`, `run.childInterrupt`, `run.childPauseSet` and `run.childrenStop`. The canonical stream carries the run-lifecycle events the state machine defines — `run.queued`, `run.starting`, `run.provider_initialized`, `run.running`, `run.turn_started`, `run.waiting_for_approval`, `run.waiting_for_input`, `run.pausing`, `run.paused`, `run.interrupted`, `run.completed`, `run.failed` and `run.rolled_back` (an undo's conversation cut alone) — with `run.step_limit_reached` (a turn ended at `Max steps per turn`, carrying the count behind `Continue`), `run.recovery_steps_added` (`{count, provider}`, the steps a restart added from the provider's own record) and `run.recovery_resolved` (the answer to a restart's mismatch); the intervention lifecycle `intervention.requested`, `intervention.accepted`, `intervention.applied`, `intervention.rejected`, `intervention.degraded` and `intervention.expired`; and an undo's one outcome event, `session.restore_finished`.
- **The child controls.** Steering a named child, interrupting it and toggling its pause are driver operations with calls of their own: `run.childSteer {targetRunId, childHandle, content, expectedRunVersion, clientIdempotencyKey}`, onto the child's own queue, which the daemon holds and which the queue reads take too; `run.childInterrupt {targetRunId, childHandle, deliverFirst?, expectedRunVersion, clientIdempotencyKey}`, which interrupts that child alone and sends its pending steers as its next turn, answering the hold with them — Escape with focus in the child's view makes this call — and with `deliverFirst` sends the named pending steer first, the pending row's `Send now`, a child's pending steer rows carrying the lead's four actions, reorder, `Edit`, `Remove` and `Send now`; and `run.childPauseSet {targetRunId, childHandle, paused, expectedRunVersion, clientIdempotencyKey}`, the toggle's two presses in one call. Each is offered on a child at any depth, on either provider, by the daemon's own mechanism below. `run.childrenStop {runId}` is the one stop that walks a subtree: the daemon walks its own index of the run's children at every depth, one stop per id, never relayed through the lead, and reports each child's outcome, so a failure is reported per row. The child calls share one refusal, `run.child_control_refused`, with the reason `child_unknown`, `child_ended` or `provider_refused`; a hold the provider lost is reported as lost in the result, never as a refusal and never as a release. `childHandle` names only a provider's own subagent; a child the daemon bridges as its own run is steered and stopped through that run's own calls. The daemon owns the mechanism behind them, and for a provider's own helper it is the same on both providers at every depth: a steer to a running child is returned by the daemon's post-tool hook as added context aimed at that child — by `agent_id` on Claude Code, by the helper the hook input names on Codex — and a steer that arrives as the child finishes is the continuation its helper-finish hook (`SubagentStop`) returns; the pause is the daemon's pre-tool hook holding the child's next call; the interrupt is that hold plus the end of the child's running command — never the provider's own stop verb, because on Claude Code a child stopped that way refuses the lead's next message and the wire offers no way to address the child directly; and a finished child, and a failed one, is continued through its parent, the lead asked to message it, by `SendMessage` on Claude Code and `followup_task` on Codex. Nothing sends `turn/start` or `turn/steer` to a helper a Codex agent started: every such helper is a multi-agent v2 helper, to which Codex refuses direct input, while `turn/interrupt` reaches it, so every stop that walks a subtree — `run.childrenStop`, an undo's sweep and `Interrupt everything` — sends `turn/interrupt` to each Codex helper in it, and `stop_task` to each Claude Code child in it, which is final, the provider refusing every later message to that child. A daemon restart that leaves a Codex helper's hold with no daemon to answer it draws that helper as interrupted, and it continues through its parent. An agent the bridge runs is a top-level conversation of its provider and takes its steer, interrupt and continue directly — `turn/steer` or a new turn on Codex, a message on the Claude Code process's input — and the same hold for its pause. A paused child continues on the toggle's second press — `run.childPauseSet` with `paused: false`, which answers the held call allow — or on a send into its box, which answers the hold deny carrying the person's words as the child's steer.

## State And Data Implications

- Queue items require durable storage and ordering metadata.
- Interventions require durable audit records even when they fail.
- Blocked states must remain associated with the same run id and same event lineage.

- **Both durable tables store message bodies plain.** Intervention rows and queue rows each keep their message body in the row's `payload` as plain text; an intervention's session is its target run's session. A purge deletes the session's rows with `secure_delete` on, with a `TRUNCATE` checkpoint after commit, and `Erase all data` deletes the store.

## Driver-Level Steer Mechanics

- **Codex driver**: native `turn/steer`. The daemon holds the message and steers it in at the thread's next tool boundary, so the content joins the running conversation as a new user turn and the turn continues from it; a steer aimed at a request that has already gone out lands at the step after. Because the daemon holds the waiting messages, an edit replaces the item in that hold and a reorder reorders it; a cancel and a resend there would put the message last.
- **Claude driver**: Claude Code accepts a message handed to it mid-turn and holds it until its next tool boundary, where the content joins the running conversation as a new user turn — so steer is delivered inside the same run, with no interrupt and no second run. The daemon's own id on each message is what a withdrawal, an edit or a reorder acts on: withdrawing is the provider's cancel on that id; an edit is a cancel of that message and of every message after it and a resend in order, made inside the one daemon call so the edited message keeps its place; and a reorder is a cancel of the waiting messages and a resend in the new order.

### Steer Content Injection Point

- On both V1 providers: the content appears as a new user message in the running conversation at the next step boundary, and the model reads it as a follow-up the user sent.
- Steer content is marked with `source: 'steer'` in the event payload so the transcript can distinguish it from normal user messages.

The typed payload shapes for steer and interrupt interventions are defined in [Queue And Intervention Model](../domain/queue-and-intervention-model.md) and verified against API contracts in that document's Field-Level Consistency section.

### The Step Bound On A Turn

`Max steps per turn` is how many steps a turn may take before it ends — the person's own, and **unlimited until they set a number**. With none set each provider does what it does on its own, which on both V1 providers is no cap at all, so the runtime adds no ceiling the providers do not have. The value every session starts from is the Runtime settings page's ([Spec-006 §Required Behavior](006-local-ipc-and-daemon-control.md#required-behavior)), and a session may carry its own override, set in one row of that session's inspector and held on the session record ([Spec-001 §Interfaces And Contracts](001-session-core.md#interfaces-and-contracts)). A number typed on the settings page governs sessions started later and reaches a session already running at its next turn; `Unlimited` puts the providers' own behavior back.

- **Claude Code driver**: the number is passed as `--max-turns` when the process starts, and that provider ends the turn itself at the limit. A change made to a live session applies at its **next** turn, by reopening that provider's own conversation by its id in a process started with the new flag — never by ending the turn that is running. The provider's own word for a step here is a turn, so `--max-turns` bounds the steps inside one exchange rather than how many exchanges a conversation may hold; the console says steps because that is what it bounds.
- **Codex driver**: that provider publishes no turn cap, so the daemon counts the steps of a turn itself — the count reset at each turn start — and calls `turn/interrupt` when it reaches the number. The count is the daemon's own, per turn, and never a running total across turns.

Either way the turn ends where it reached and the transcript carries one flow row, `Step limit reached · 40 · Continue`, stored as the run event `run.step_limit_reached` carrying the count so it survives a reload. That event is not terminal: **the run then ends as `run.interrupted` with `trigger: step_limit`**, the way the spend and token limits end it — on Claude Code after the provider ended the turn itself with `error_max_turns`, on Codex after the daemon's own `turn/interrupt`. `Continue` is a send into that interrupted run, which returns the same run to `running` with everything it knew ([Run State Machine](../domain/run-state-machine.md)), and a message arriving from another session carries it on the same way ([Spec-014 §Sessions Talking To Each Other](014-multi-agent-orchestration.md#sessions-talking-to-each-other)). The bound is not a budget. It and the two limits beside it, the spend limit and the token limit ([Spec-014 §Budget Policies](014-multi-agent-orchestration.md#budget-policies)), are the bounds on how long a turn runs; all three are the person's own, the runtime sets none of its own, and they are the only bounds on how long two sessions go on messaging each other.

## Driver-Level Rollback Mechanics

- **Undo and fork are two things.** The conversation half of an undo is the driver method `rewindConversation`, the provider's own cut, made on the session the undo is in. `session.fork` is the design's Fork: it mints a new session of the same shape carrying history up to and including a message, the parent running on untouched; its provider leg is the driver method `forkConversation` (`ForkConversationParams`, `ForkConversationResult`) — Claude Code's `--resume-session-at` with `--fork-session`, Codex's `thread/fork` at an inclusive turn. A fork is never an undo.
- **Claude driver, the cut.** The cut is the control request `rewind_conversation {target_message_uuid, last_seen_user_message_uuid, interrupt_if_running}`. The driver translates the undo's message identity into the provider's message id and runs `--replay-user-messages`, so message ids appear on the wire. `last_seen_user_message_uuid` must name the newest prompt the daemon sent, or a cut past a later prompt is refused `stale_target`, compaction or not. A refusal arrives as `subtype: "success"` with `rewound: false`, so the driver reads `rewound`, never the subtype. The driver sends `interrupt_if_running: true`, so the cut itself ends a turn that is still live. The same flag makes the cut one-way for the run's agents: every agent started at or after the point is killed and recorded as stopped by the person, after which the provider refuses every later message to it, so those agents cannot be resumed and the question asked before an undo says so. Measured on Claude Code 2.1.276, three runs of three: the two running children were killed about four milliseconds after the request, and a later message to either came back refused. A point after the conversation's last compaction — `/compact` or automatic — is cut here in place, and a restart keeps that cut.
- **Claude driver, a point before the last compaction.** After an automatic compaction Claude Code refuses a cut to a point before it with `target_not_found`, and a cut to such a point that Claude Code does accept, after `/compact`, is lost at the next restart, because the resume rebuilds the session from the compaction summary. So for a point before the last compaction the adapter uses the Agent SDK's public `forkSession(sessionId, {upToMessageId, title})`, and the undo holds across every later restart. The adapter stops the process with SIGTERM — never by closing its input, which would let Claude Code finish the running turn and answer every queued prompt into the conversation being undone. It forks at the last assistant message before the point, with the session's own title, taking that message's id from the daemon's own record of the stream: a stream frame's `uuid` is the session file's entry `uuid`, and the SDK's own message read skips everything before the last compaction in a session file over 5 MiB. It restarts the headless CLI on the fork (`--resume <fork id>`) and writes every prompt not yet taken up — a prompt the stream has not replayed as a user message, which Claude Code keeps only as a queue row the fork does not carry — and every prompt sent while the process was down to the new process as soon as it spawns, where Claude Code answers them on the forked history. It maps message ids through each row's `forkedFrom`, because a session file that already branched from an earlier undo carries the dead branch's rows into the fork, rows Claude Code never loads, so the fork's row list is never taken for the conversation. The daemon imports only `forkSession` from `@anthropic-ai/claude-agent-sdk` — a file operation, with no model call and no process — because the session file format is Claude Code's private one and changes between versions, which the SDK tracks; the SDK's per-platform binary is left out of the install, and the SDK version is pinned and moves with the supported Claude Code version. The headless `fork_conversation` control request answers `unsupported` and is not used. All of this stays inside the daemon: the session keeps its identity, no second session appears anywhere, and nothing on screen names a provider session, a copy or a restart; the steps show only in the daemon's logs and events.
- **Codex driver.** The cut is `thread/revert {threadId, beforeTurnId}`, which drops that turn and every later one, cuts the thread's history and nothing else, and stays on the same thread. It keeps the cut past an automatic or an explicit compaction and across a resume, the next model request carrying the kept turns' own messages and replies rather than the summary. It works only on a thread with paginated history, so a conversation the person may undo is never started ephemeral. Codex has no `thread/rollback`: it is gone from the generated schema, and a call to it is answered `-32600 unknown variant`. A turn still running is interrupted first and the revert follows, so the revert never races a live turn. The cut leaves the thread's agents running, and the daemon stops each agent started after the point by its own id, resumably — the opposite of the Claude leg, which is why the question asked before an undo is worded per provider. Measured on Codex 0.155.1, three runs of three: a three-turn thread reverted before its second turn came back listing one turn, the files the reverted turns had written were all still on disk, and an agent the third turn had started was still running and addressable after the cut.
- **The same cut hands back a turn too long for the window.** A turn that cannot fit even after compaction ends refused, and the provider keeps the refused message, so every later turn would fail the same way. The daemon cuts that turn at once with the same verb — `rewind_conversation` naming that message and the newest one the daemon sent, or `thread/revert` before that turn — and hands it back as a failed send: its words and attachments go back into the composer, and the rows the turn had already drawn stay marked superseded.
- **Neither verb touches a file.** Both cut conversation history only, so the files are always the daemon's own per-session checkpoint store ([Spec-013 §Required Behavior](013-persistence-and-recovery.md#required-behavior)) — one mechanism, the same on both providers, never the provider's own file rewind and never a driver leg. That store is what every undo reads from, anchored on one of the person's own messages or on a named snapshot of the session, the snapshot only naming the point to return to ([Spec-008 §Turn-Boundary Snapshots](008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)). It covers what an agent's shell commands wrote, on both providers, through a capture before and after every command.
- **A confirmed cut.** The daemon appends `run.rolled_back` only for a cut the provider confirmed — `rewound: true` on Claude Code, the revert's answer on Codex, the restart on the fork — and that confirmation is the in-stream fence §Required Behavior's absorption reads. A refused cut appends nothing, and the undo's result names the conversation's failure with the provider's reason in the daemon's words.
- **Transcript presentation**: turns cut away are never deleted from `session_events`; projections mark them superseded — the turns after the point of the accepted `run.rolled_back` event — so clients render the undone history distinctly rather than dropping it. Late non-lifecycle appends from the epoch before a cut carry §Required Behavior's durable epoch stamp (the `sourceEpoch` + `sourcePosition` carrier pair, [Spec-005 §Event Type Enumeration](005-session-event-taxonomy-and-audit-log.md#event-type-enumeration)), so a rebuild ranks them with their source epoch — never by append order — and the supersede marking survives projection rebuilds.

## Implementation Notes

- Queueing and intervention logic must live in the daemon or equivalent runtime authority, not in the currently open client.
- UI affordances may be optimistic, but canonical run state changes must come from runtime truth.
- Capability-aware controls are required so unsupported operations do not masquerade as working.
- Pause is an orchestration-layer construct. The daemon stops the run after the step in flight — through the hooks it registers for the session or passes to the provider's service, or a boundary interrupt where the provider has no hook for it — and persists conversation history and run state to local SQLite; nothing is queued to resume it. No intervention type is minted for pause, no hook is written into a file, and the pause's only configuration write is the trust records Codex needs for the daemon's own hooks (§Required Behavior).

## Pitfalls To Avoid

- Using client memory as the queue of record
- Calling reread or reattach semantics `resume`
- Treating waiting states as paused states
- Turning a message sent during a run into a second run, or holding it back until the run ends, when both V1 providers deliver it into the running run at its next step boundary
- Appending a late provider run-lifecycle event to a terminal run's transcript (the absorption rule exists precisely for this window) — or, inversely, absorbing non-lifecycle events the rule never covered (late usage telemetry is billable and must append) — or keying absorption on current run state alone, which misses stragglers from the execution before an undo's cut arriving after it (the epoch gate exists for exactly that arrival order)
- Treating an undo as log truncation — the authoritative log never truncates; the cut is a forward `run.rolled_back` event plus projection-level supersede marking
- Truncating or renumbering the rendered transcript when an edit and resend starts rather than when its `run.rolled_back` boundary is appended — the turns it will supersede dim and stay readable and pressable until the cut lands, and a cut that fails leaves them as they were
- Holding an edited message for a later resume, or reporting a resend as sent when the cut landed and the send did not — the resend goes at once, and a failed one puts the message back in the composer and says so on its row

## Acceptance Criteria

- [ ] A user message sent while a run is active is durable before it is delivered, is then delivered into that same run at its next step boundary on both V1 providers keeping the run id, and never becomes a second run; several such messages are delivered in the one order the daemon holds, which `run.queueReorder` replaces whole; an edit replaces a waiting message in place in one `run.queueCreate` call, its old item `superseded` and the edited message in its place, and is refused once the agent has taken the message; and a message that has waited past the daemon's delivery timeout reads not delivered with its reason and is sent again from its own row.
- [ ] An interrupt ends the run it names and the command that run was running, spares the agents that run dispatched, and delivers whatever was waiting for that run as the next turn; with nothing waiting the run rests `interrupted`.
- [ ] No undo is applied before its dry run has been answered; an undo of the files alone appends no `run.rolled_back` and marks no turn superseded; and an undo that would stop agents or commands started after the point asks first, naming each count from the daemon's own tree, and on Claude Code adds that those agents cannot be resumed.
- [ ] Pause (stop after the step in flight and persist, with nothing queued to resume it) and resume operate on the same run id and same run history: the toggle's second press, or a send, continues the run from exactly where it stopped with nothing repeated, waiting messages are delivered on the continue, and a paused or pausing run can still be interrupted.
- [ ] Unsupported intervention requests result in explicit `degraded` or `rejected` outcomes rather than silent behavior changes.
- [ ] With `Max steps per turn` unset, a turn on either provider runs to its own end and nothing of this runtime's counts, caps or interrupts it. With a number set, a Claude Code session is started carrying it as `--max-turns` and a Codex turn is ended by the daemon's own per-turn count at that number; either way the turn ends there, the flow carries `Step limit reached · 40 · Continue` from `run.step_limit_reached`, the run then ends `run.interrupted` with `trigger: step_limit`, and the press is a send into that run, returning the same run to `running`. A number set on a live session takes effect at its next turn and never ends the turn in flight, and a per-session override leaves the settings-page value alone.
- [ ] A provider run-lifecycle event arriving for a run already terminal never appends a `session_events` row and never advances `runVersion`: a terminal-class straggler no-ops in the at-most-once terminal emitter; a non-terminal lifecycle straggler surfaces only as the `run.late_event.absorbed` OTel diagnostic; and a run-lifecycle event sourced from the execution before an undo's cut, arriving after the cut, is absorbed identically — never appended against the new epoch — on a runtime binding the cut kept and on one a fork and restart froze alike. A provider permission ask sourced from the execution before the cut is absorbed the same way: nothing is appended and no approval is left pending. Non-lifecycle provider events in the same window (usage telemetry foremost) still append under their own families' rules.
- [ ] An undo is one `session.restore` call aimed at a message or snapshot identity, never a position, with one of the scopes, and it reports what it did as one row and one `session.restore_finished` event: everything asked for applied, part applied naming the part that did not and its cause, or `Undo failed · <cause>` with the conversation and the files as they were; turns after the point are marked superseded only when the conversation went back; a call retried under the same idempotency key never cuts twice; it is offered through a running turn and ends that turn itself; and a message sent while it runs is answered on the undone conversation.
- [ ] The conversation cut holds on both providers: on Claude Code `rewind_conversation` carries the newest prompt the daemon sent as `last_seen_user_message_uuid`, a refusal is read from `rewound: false`, and a point before the last compaction is reached by the fork and the restart on it, which holds across a later restart, keeps the session's identity and names no copy or restart on screen; on Codex `thread/revert` cuts a conversation that was never started ephemeral and holds past a compaction and across a resume. What an agent's shell commands wrote goes back with the files on both providers.
- [ ] Run control is blind to what started a run: an intervention, a `run.pause` and a `run.resume` from any connected device apply to a run **whatever started it**, with the run's origin never read as an input, and no request is refused for who sent it.
- [ ] Edit and resend is the undo carrying the edited message, at the conversation-and-files scope — one call, one idempotency key, one result — offered on every message the person sent, on both providers and through a running turn; the turns it will supersede dim and stay readable until the cut lands and are marked superseded only then; the edited message goes at once as the next send on the cut conversation; and a resend that fails puts the edited message back in the composer with everything it carried, its row naming the cause and, where the cut had landed, saying that the conversation went back and the resend did not.

## Design Decisions

- A person reorders their own waiting messages on one run. A message sent into a running turn waits as a row at the end of the transcript, and on hover or keyboard focus that row offers a grip that drags it — or the up and down arrows with the row focused — to move it in the stack, beside `Edit`, which puts it back into the draft and sends it back into its own place, `Remove`, after which nothing reaches the agent, and `Send now`, which interrupts the turn, delivers that row first and lets the rest follow in order as the next turn's messages. A reorder is one order the daemon holds over the messages still waiting, sent whole as `run.queueReorder`: on the Claude driver the message has already gone to the provider, which holds it to the next tool boundary, so the daemon cancels those rows and resends them in the new order; on the Codex driver the daemon holds the message itself and reorders its own hold, because a cancel and a resend there would put the message last. This is the **send order of one person's own waiting messages on one run**. The admission queue carries no priority attribute: nothing ranks one run's work ahead of another's, and admission itself stays canonical queue order.
- The run controls are the ones §Interfaces And Contracts names — the queue calls, the interrupt, pause and resume, the answer to a restart's mismatch, and the child controls — over canonical queue order. Undo is not one of them: an undo is `session.restore`, a session operation rather than a run control, and edit and resend is that same call. The same-agent provider switch is not one either: `agent.configUpdate`'s `interruptAndSwitch` flag dispatches the **existing** `interrupt` intervention rather than minting a control ([Spec-014 §Same-Agent Provider Switch](014-multi-agent-orchestration.md#same-agent-provider-switch), D-013-17).
