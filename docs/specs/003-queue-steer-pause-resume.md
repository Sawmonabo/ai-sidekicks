## Required Behavior

- **A message sent while a run is active is delivered into that run.** It is persisted as a queue item before anything else happens to it, and it is then delivered to the running run at its next step boundary on both V1 providers — never held back for a later run and never silently turned into a second one. Until the run takes it the item is waiting, and it says so. Several such sends stack in the order they were sent and are delivered in that order. The daemon stamps every message with an id of its own — a UUID on Claude Code, `clientUserMessageId` on Codex — and that id is what lets a waiting message be withdrawn or replaced: on Claude Code the message is handed to the provider at once and the provider holds it until its next tool boundary, so withdrawing it is that provider's own cancel on the id, replacing its text is a cancel and a fresh send, and reordering the waiting messages is a cancel of them and a resend in the new order; on Codex the daemon holds the message itself and steers it in at the tool boundary, so a steer aimed at a request that has already gone out lands at the step after and the item stays waiting until then. Delivering one waiting message ahead of the rest is an interrupt of the run followed by that message, the remainder following in order as the next turn's messages. An item that has not been delivered because the daemon cannot be reached stays waiting; an item whose delivery actually failed is recorded as not delivered and can be sent again from the item itself. The two are distinguishable states, never one hopeful one. Follow-up work that is not a user message — orchestration-authored input — stays an ordinary queue item admitted in canonical order.
- `pause` is an orchestration-layer construct the daemon owns: it stops the run after the step already in flight — by the provider's own hooks where the provider has them and by a boundary interrupt where it does not, per the pause-mechanism bullet below — persists conversation history and run state, and queues a resume event. The resulting `paused` state must not mean queue-drain suspension or blocked waiting. Pause is one toggle rather than a pair of controls: the same control continues the run, and so does sending anything to it, in both cases from exactly where it stopped with nothing repeated. There is no pause-immediately variant and no separate resume control. While the step in flight is still finishing, the run is pausing and not yet paused, and that is a state a reader can see; waiting messages stay waiting while the run is paused and are delivered when it continues; and a paused run can still be interrupted.
- `resume` must return a `paused` run to active execution with the same run id.
- `interrupt` must transition a run directly to `interrupted`. Interruption is a synchronous or near-synchronous provider call with no intermediate state. It reaches the run it names and nothing else: the sidekicks that run dispatched are spared and keep working, and an interrupt never cascades, on a lead run or on a child. The command the run was running is ended with it. Whatever was waiting for that run is delivered at once as the next turn, so an interrupt with messages waiting leaves the run working again; with nothing waiting the run rests `interrupted` until a later send returns it to running. On Claude Code the daemon declares the per-task stop affordance so a plain interrupt never sweeps the run's background subagents, and where a child is running in the foreground the daemon first moves that child to the background, so the interrupt spares it as it spares every background child; on Codex the daemon ends the command the interrupt leaves running.
- Waiting for approval or input must remain `waiting_for_approval` or `waiting_for_input`, not `paused`.
- Every intervention outcome must be visible in the canonical event stream.
- Queue items must support cancellation before admission.
- **The states of a turn.** A run is idle before it starts and running while it works; an approval or an input request leaves it waiting and answering that returns it to running; it is done when it finishes. `Interrupt` takes a running run to `interrupted`, and a send — or the waiting messages going as the next turn — takes it back to running. `Pause` takes a running run through pausing to `paused`, and the toggle or a send takes it back to running. A run freezes its checkout root when it starts, so a working-folder move asked for while it runs is recorded as an intent on the session and applied when the run reaches a boundary. A child run carries the same machine on its own: it pauses and continues on its own toggle, its own interrupt takes it to `interrupted` and a steer takes it back to running, a stop that reaches a subtree takes it to stopped — final on Claude Code, where the provider refuses every later message to a child the user stopped, and re-enterable on Codex, where a send starts it again — and a finished child returns to running on a send into its own steer box, its pause and interrupt coming back with the run.
- **How the pause is made true on each provider.** The daemon pauses with the provider's own hooks where the provider has them and with a boundary interrupt where it does not, registering everything for the session over the wire and writing nothing into the user's own configuration files. On a Claude Code lead run it is two hooks registered in the session's `initialize` request and answered over the wire: one ends the turn after the step in flight, the other denies whatever a woken lead tries while the pause holds, both carrying the same reason — so a lead a child wakes runs one model call, is denied its tool, and stops again. On a Claude Code child run it is a hold on that child's next tool callback. On Codex, lead or child, it is the boundary interrupt: the hook holds the thread's next call, the daemon interrupts the turn, the hook denies the parked call so it cannot run, and starting the next turn is the continue; a command still running finishes first, and the run is pausing until it has. The user's own hooks keep running beside the daemon's, and a hook the provider refuses at `initialize` is learned from that refusal and remembered rather than retried, with the control that depended on it saying why it is unavailable.
- **A child run's controls are the session's controls.** Every live child run takes the same pause, interrupt and steer the session's own run takes, whatever dispatched it and whichever provider it runs on. Interrupting one child reaches that child alone: the sidekicks it dispatched keep going, and so does whatever dispatched it. Continuing a parent continues the parent alone. Steering an interrupted child starts it again with everything it knew, and a finished child starts again on a send — as a new turn on its own thread where a finished thread refuses a steer, and by asking the lead to message the child where the provider offers no way to reach it directly. A child stopped for good on Claude Code takes no later message at all, because the provider refuses every message to a child the user stopped; the same stop on Codex is an interrupt the child comes back from. A paused child's hold is lossless: its next tool callback simply goes unanswered, so the child burns no tokens and loses nothing, and the hold ends only by an answer — allow from the toggle, or deny carrying the user's own typed words, which the child reads as its instruction. The hold is routed per child by the id the hook payload carries for the acting thread, it works at every permission level including the least careful one, and it is held open by setting the callback's timeout far past any wait a person would sit through; a provider cancelling a held callback is a lost pause and never a release, and a hold left unanswerable by a daemon restart leaves its child interrupted rather than held forever. Freezing one child at the process level is not offered, because both providers run their subagents inside the parent process: a process freeze stays an option only for pausing a whole session. A capability a provider refuses is learned from the refusal and remembered for that child, never read from an experimental opt-in surface.
- **Restoring a session to a point in its own history.** A user restores to the moment before one of their own messages, and the same operation serves a restore aimed at a named snapshot of the session rather than at a message. It is a scope on the `rollback` intervention and adds no control: the conversation and the files together, the conversation alone, or the files alone. The first two run the legs this section already specifies. The files-only scope runs the file leg with no conversation rewind at all, so it appends no rewind boundary and marks no turn superseded — superseded marking applies solely on an accepted `run.rolled_back` boundary — and its outcome is recorded on the durable intervention row like every other. The file leg of a message-anchored restore reads from the daemon's own per-session file checkpoint store ([Spec-013 §Required Behavior](013-persistence-recovery-and-replay.md#required-behavior)) — the only thing any restore reads from, on either provider, whether it is anchored on one of the user's own messages or on a named snapshot of the session; a snapshot-anchored restore differs only in naming the point it returns to ([Spec-008 §Turn-Boundary Snapshots](008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)). No scope is applied before its dry run has been answered, and a dry run a caller has not answered is not a pending intervention: what that dry run names, the rule that a skipped file is named rather than dropped in silence, and the fact that what a shell command wrote lies outside what a restore can put back are all carried by that store's contract, cited above. A restore that would stop sidekicks asks first, naming how many were started after the point from the daemon's own record of the run tree; on Claude Code it adds that those sidekicks cannot be resumed, because the conversation cut there ends them for good, while on Codex the cut leaves them running and the daemon stops each by its own id, resumably. Declining changes nothing.
- **Edit-and-resend is offered for every message the user sent, on both providers, and through a running turn.** Nothing narrows it to the newest message, to one provider, or to a run that happens to be idle: where a turn is still running the conversation cut ends that turn as part of the same operation, so the edit never waits for the answer it is replacing (§Driver-Level Rollback Mechanics). The replacement-send leg above is how it is carried out, and the three structural guards are the only grounds on which it is refused. Like a restore, the resend asks first when sidekicks started after that point are still live, naming how many from the daemon's own record of the run tree and, on the provider whose conversation cut ends them for good, saying that they cannot be resumed; declining keeps the edited text and changes nothing.
- **Post-interrupt late-event absorption (campaign B2, P1-8).** A provider **run-lifecycle** event — a run-state-transition report — that arrives for a run already in a terminal state (`completed`, `interrupted`, `failed`) is **absorbed, never appended**: a terminal-class straggler routes into the at-most-once terminal emitter ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle) emission contract, campaign B1) and no-ops there; a non-terminal lifecycle straggler is dropped from the lifecycle path entirely and recorded only as a `run.late_event.absorbed` **diagnostic non-event** on the daemon's telemetry (an OTel log record per [Observability Architecture](../architecture/observability-architecture.md) — never a `session_events` row), with no state transition and no `runVersion` advance. Absorption also keys on **execution epoch**, not current run state alone (the epoch is the interval between accepted `run.rolled_back` rewinds — a confirmed conversation rewind advances it regardless of the file-leg disposition — [Run State Machine §Invariants](../domain/run-state-machine.md#invariants)): a run-lifecycle event sourced from the pre-rollback execution that arrives after a rollback has re-opened the run in `paused` is absorbed identically even though the run is no longer terminal — the Spec-005 `(runId, runVersion)` at-most-once key cannot catch these (rollback advanced `runVersion`), so appending one would record a stale terminal against the new epoch or force an illegal transition. The epoch attribution is concrete and needs no wire token: run-lifecycle events are attributed per **binding**, and because both V1 cuts happen in place on the binding the run already holds, the driver's `rollbackTo` confirmation is an **in-stream fence** (the driver owns one serialized provider connection, which totally orders the confirmation against event delivery) — so the driver quiesces pre-rollback lifecycle delivery once `rollbackTo` resolves, and the daemon's per-binding cursor — an **(epoch, position) pair** whose position component advances at each turn boundary observed in the binding's ordered delivery and freezes at the fence — absorbs any straggler that slips through (§Driver-Level Rollback Mechanics). For the pause-first composite the absorption window opens **earlier than the fence**: from the moment the composite issues its internal interrupt, run-lifecycle events sourced from the interrupted execution are the pause's expected echo — consumed by the pause application exactly as the client pause path consumes its own interrupt's echo, or absorbed as above, never routed as spontaneous transitions — so a late `run.interrupted` arriving after the internal pause but before the `rollbackTo` confirmation cannot re-terminalize the mid-composite run or release its root (the rollback bullet below). Absorption is scoped to the run-lifecycle family: non-lifecycle provider events arriving in the same window — usage telemetry above all, plus assistant output, tool activity, and artifact publication — append normally under their own families' rules (late usage telemetry must still reach the cost ledger; absorption never drops billable usage) — but never epoch-blind: a non-lifecycle row the per-binding cursor attributes to a pre-rollback epoch appends **carrying that attribution durably** (the daemon stamps the source-epoch linkage onto the appended row at ingestion — the pair **from the straggler's operation association**: the run engine records each provider-side operation (tool call, message item, artifact production) against the **(epoch, turn) current when it opened**, in-stream and pre-fence, and the straggler's correlation key resolves that recorded pair — re-executed turns reuse ordinals, so the association must carry the epoch alongside the turn, and delivery order bounds only the _emission_ turn, so a content-asynchronous straggler (a long-running tool's progress, a delayed usage aggregate, a late-completing artifact upload) must rank by its _operation's_ opening pair, not the last-observed boundary. Binding lineage differs by mechanism without changing the value source, and **both V1 legs sit on the same arm of that rule**: each provider's conversation cut happens **in place**, on the session or thread the run is already bound to (§Driver-Level Rollback Mechanics), so one provider binding spans epochs and its **delivery generation rotates at the fence** — the `rollbackTo` confirmation closes the pre-rollback generation while post-fence deliveries open the new epoch at the confirmed floor, with per-generation attribution. The rule's other arm — a **fork-superseded** binding, which would freeze wholesale with every delivery pre-epoch at its retained (epoch, position) pair — is retained as mechanism-generic contract for a mechanism that mints a new provider session, and **has no V1 instance**; it is not machinery V1 builds or tests. A straggler with no resolvable operation linkage takes the retained pre-rollback generation's pair — in V1 always that closed generation's frozen pair, since a post-fence delivery on the same binding is current by the in-stream fence's total order — a conservative upper bound strictly above its epoch's rewind cutoff (that generation closed at the run's then-current position, and admission requires the target strictly below it), so an unattributable pre-epoch straggler is always superseded with its epoch, never resurfacing as current — never a read-time guess and never the post-rollback run's current position; append-time knowledge is never discarded), so replayed projections mark it superseded exactly like the in-time rows of the epoch it belongs to and stale output can never resurface as current timeline state (the typed stamp shape is owned by the campaign's Plan-005 bundle — registered 2026-07-20 as the cross-cutting `sourceEpoch` + `sourcePosition` payload pair, [Spec-005 §Event Type Enumeration](005-session-event-taxonomy-and-audit-log.md#event-type-enumeration); §Driver-Level Rollback Mechanics' supersede projection consumes it). The near-synchronous interrupt hedge above is the _reason_ the window exists — a provider may emit briefly after the daemon records the terminal; canonical-stream visibility of the intervention outcome is satisfied by the terminal event itself, and absorption adds no second visible outcome.
- **Rollback intervention (campaign B2 — R8 run time-travel, V1 feature #19 per [ADR-015](../decisions/015-v1-feature-scope-definition.md)).** `rollback` is a first-class intervention type on the existing generic dispatch: `applyIntervention('rollback', {targetPosition})`, carrying the same mandatory fail-closed `expectedRunVersion` guard and mandatory `clientIdempotencyKey` as every intervention (§Interfaces And Contracts) — a rollback racing a progressing run expires exactly like a stale steer. `targetPosition` is the **normalized session position** (a `number`, the [Spec-004](004-provider-driver-contract-and-capabilities.md) `rollbackTo` position vocabulary) identifying the turn boundary to rewind to — **domain-validated fail-closed at admission**: an integer ≥ 0 naming a turn boundary recorded in this run's history **strictly below the run's current position**; non-integer, negative, current, future, or boundary-less values are rejected pre-dispatch with no leg applied (the wire arm carries the matching runtime bound — [API Payload Contracts](../architecture/contracts/api-payload-contracts.md)). The accepted intervention's value serializes onto the forward `run.rolled_back` event ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle) per-type row — this contract is that row's named structural-type owner), identically on the confirmed path (the confirmed-floor rule below). **State-gated:** legal from `paused`, `waiting_for_approval`, `waiting_for_input`, and the three terminal states; a `running` target is first brought to `paused` via the existing orchestration-layer pause path (interrupt + persist), and rollback applies from `paused` — every rollback takes that path, the edit-and-resend composite included (§Required Behavior's edit-and-resend bullet) — the pause is an **unguarded internal sub-step of the atomic rollback application**, not a client `run.pause` request: it queues **no resume event** (the client pause path's queued resume is not part of the sub-step — rollback lands and stays `paused`, and a surviving marker would re-run the pre-rollback continuation), **every fail-closed pre-dispatch validation — the target-position domain check, the compaction-boundary classification (the compaction bullet below), the uncompacted-rewind-span check, the capability check — completes at admission, before the pause sub-step** (a refused rollback of a `running` run leaves it running, untouched — pausing first and then refusing would itself be a leg applied), the intervention's `expectedRunVersion` guard is evaluated **exactly once, at admission**, against the caller-observed pre-pause `runVersion` (the internal pause's own progression cannot expire the very intervention that initiated it), and the intervention response returns the post-composition `runVersion`; rollback is the **only** path out of a terminal state ([Run State Machine §Rollback Transitions](../domain/run-state-machine.md#rollback-transitions-campaign-b2), this bundle). A rollback from a waiting state voids the pending block — the awaited approval or input request is canceled as moot when the turn that raised it is rewound, the void applying **exactly on the confirmed conversation rewind, never at admission or dispatch**: a conversation leg that fails or confirms no rewind leaves the block pending and the run in its waiting state, per the no-rewind path below (the approval reaches `approval.canceled`, a driver ask reaches `driver_ask.canceled` — Spec-005's existing terminals; the void mints no new event type). A concurrent resolution racing the rollback serializes on the run's progression: a resolution that applies first advances `runVersion`, so the in-flight rollback correctly expires; a rollback that applies first cancels the block, and the late resolution finds a canceled request and no-ops. A queued resume pending against the target run at application time is voided the same way — canceled as moot, because the position it would resume from has been rewound — under the same progression-serialized race rule. **Same-run resurrection, not fork-new-run:** budgets, supersede-marking, and the `expectedRunVersion` guard are all run-scoped; a fork would orphan all three. Re-executed turns reuse position ordinals, which is why snapshot identity is **epoch-namespaced** — the post-rollback execution's turn-6 capture must never collide with (or silently resolve to) the superseded epoch's turn-6 tree ([Spec-008 §Turn-Boundary Snapshots](008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots), this bundle's ruling; implemented by the campaign's Plan-008 bundle). Modeled as a **forward** `run.rolled_back` event on the authoritative log ([ADR-017 Decision Log, 2026-07-02](../decisions/017-shared-event-sourcing-scope.md#decision-log)): the log never truncates or rewrites, and rolled-back turns remain queryable history **marked superseded by projection**. Successful rollback lands the run in `paused` at the rewound position. Leg ordering is **fail-closed**: the **rewind span must be live** — every row of the target run the position cutoff would mark superseded (the rewound tail strictly above `targetPosition`) is uncompacted at admission, and a rollback whose rewind span intersects already-compacted history is refused whole (the same standing-refusal class: compaction irreversibly replaced those rows' payloads with audit stubs, destroying the per-row attribution the supersede projection needs — [Spec-005 §Compacted Event Format](005-session-event-taxonomy-and-audit-log.md#compacted-event-format) — while rows at or below the target compact freely, staying current and taking no mark), with detection reading the stubs' preserved run identity: every audit stub of a run-scoped row preserves its `runId`, plus its originating position when the rollback-attribution source resolved one at compaction — [Spec-005 §Compacted Event Format](005-session-event-taxonomy-and-audit-log.md#compacted-event-format)'s `originPosition` — so the span check counts the target run's **unstamped** stubs strictly above `targetPosition`, or position-less (a stub written before rollback support shipped, whose position is unknowable), as span intersections, while `sourceEpoch`-stamped stubs are already attributed and never block; and the check is **not check-then-forget**: the span check and the write-ahead intervention row's durability are atomic under the session's append serialization (the per-session append lock), and from that durability until the intervention concludes the span is **compaction-deferred** — the compactor's per-row attribution answers _defer_ for rows a dispatched-but-unconcluded rollback's span covers (leaving them live for a later pass; the durable intervention row survives restart, so the deferral holds across a crash until the [Spec-013](013-persistence-recovery-and-replay.md) reconciliation concludes the row) and its per-row attribute-and-stub runs under the same lock — so idle compaction can neither stub the rewound tail in the admission-to-boundary window (no accepted boundary exists yet for compaction-time stamping, so those stubs would be stranded unattributable) nor race the span check over a row mid-stub; the conversation leg (the driver's capability-gated `rollbackTo` parity operation, campaign B3) applies next — **a conversation-leg failure ends the intervention with no file mutation and never auto-resumes**: when the driver reports `degraded` or the reconciliation rule below concludes no rewind occurred, the intervention ends `degraded` with the disposition naming exactly what applied — the internal pause for a `running` source (the run stays `paused` at its pre-rollback position with `runVersion` reflecting the pause; an implicit resume would re-run the very continuation the caller asked to rewind away from — recovery is a fresh rollback, now from `paused`, or an explicit `run.resume`), nothing for every other source (dispatch occurred, so pre-dispatch `rejected` is definitionally unavailable — [Queue And Intervention Model §Driver Result To Lifecycle Mapping](../domain/queue-and-intervention-model.md#driver-result-to-lifecycle-mapping)) — and **a terminal-source rollback that does not confirm the conversation rewind changes nothing**: the run stays terminal and its working folder is untouched ([Run State Machine §Rollback Transitions](../domain/run-state-machine.md#rollback-transitions-campaign-b2)); once the driver confirms, the daemon **validates the driver-confirmed floor equals `targetPosition` before the file leg** (`DriverRollbackResult.applied.sessionPosition` — §Driver-Level Rollback Mechanics) — the confirmed floor is untrusted driver output and first passes the **same domain validation as the request target**: an invalid report (non-integer, negative, unrecorded boundary) or a no-op report (equal to the pre-rollback position) is treated as a no-rewind conversation-leg failure per the path above, minting no `run.rolled_back` and superseding nothing; then, on a valid-but-different confirmed position (mismatch) the file leg is skipped fail-closed (never a restore against a boundary the conversation is not at), the run follows conversation truth — `paused` at the **confirmed** position — the intervention ends `degraded` naming the position-mismatch disposition (requested vs confirmed), and the forward event records the confirmed position (the event never lies about where the run landed) — and the confirmed floor additionally passes the settlement-time compaction-boundary reclassification (the compaction bullet below): a `boundary-diverged` conclusion degrades the same way, file leg skipped fail-closed, run at conversation truth; the file leg restores last, copying each file back from the session's own file checkpoint store ([Spec-013 §Required Behavior](013-persistence-recovery-and-replay.md#required-behavior)), and a file-leg failure after a confirmed conversation rollback is surfaced as a **`degraded`** intervention outcome naming every file it did not put back and why — the same never-silent, per-file rule the dry run's own skip list follows ([Spec-013 §Fallback Behavior](013-persistence-recovery-and-replay.md#fallback-behavior)) — with recovery being a fresh restore to the same point, which puts back what the failed one did not — never `applied`, which would hide the file-leg failure ([Queue And Intervention Model](../domain/queue-and-intervention-model.md): `degraded` is the lifecycle's partial-effect terminal, and `failed` is not an intervention state). The run-state consequence follows the **conversation leg**: once that leg is confirmed, the run's authoritative position has rewound, so the run lands `paused` at `targetPosition` and the forward `run.rolled_back` event is appended **even when the file leg then fails** — recording anything else would silently diverge the daemon's recorded position from the provider's. Replaying the same `clientIdempotencyKey` returns the recorded partial outcome (replay-or-conflict — never a re-execution); recovery is a **fresh** rollback intervention to the same `targetPosition`, which re-runs both legs. **Dispatch ambiguity is reconciled, never guessed**: the accepted intervention row is durable **before** driver dispatch (the `interventions` table's lifecycle state is the write-ahead dispatch-intent marker), and neither provider protocol offers a rollback dedupe key — the provider-boundary idempotency mechanism is **absolute-position targeting**: `rollbackTo` addresses an absolute normalized position, never a relative drop-count on the daemon's wire, so a retry after an unconfirmed attempt converges instead of double-rewinding (§Driver-Level Rollback Mechanics — the Codex driver resolves `targetPosition` to the boundary turn id at each dispatch, so a re-dispatch names the same boundary rather than recomputing a delta; a re-dispatch on either provider re-issues the same in-place cut against the same binding, which is idempotent at that boundary rather than compounding). On daemon restart — or a driver throw/timeout leaving the attempt unconfirmed — every rollback row dispatched-but-unconcluded is reconciled by the [Spec-013](013-persistence-recovery-and-replay.md) resume position-compare **before anything else touches the run**: a provider position at `targetPosition` completes the intervention forward — remaining legs (the recorded `replacementSend` among them wherever the 2026-08-16 amendment's composite staged one, never left unsent), durable outcome, `run.rolled_back`; an unchanged provider position concludes it by the no-rewind path above; only after reconciliation is redispatch legal, converging by the same absolute-position rule. A `read-only` run changed no file, so it has nothing to put back, and a run whose working folder no longer exists — an ephemeral clone past disposal, a worktree retired by the cleanup sweep, or a recorded checkout root that has gone from disk — has nowhere to put anything back into: both roll back **conversation-only**, with the outcome recording why the file leg did not run. The session's checkpoints outlive all of those, being held with the session outside the checkout ([Spec-013 §Required Behavior](013-persistence-recovery-and-replay.md#required-behavior)), so the conversation-only branch is about the folder and never about the copies. A confirmed rollback of a run whose recorded checkout root is gone **releases** that run's execution context atomically with the re-open, recording the vanished-checkout cause, so the non-resumable rule below governs it structurally, while a conversation leg that does not confirm releases nothing ([Plan-003](../plans/003-queue-steer-pause-resume.md)'s rollback tasks own the typed outcome detail); a **rootless** run re-opened this way is **non-resumable**: `run.resume` against a run whose execution context is released with no existing root is refused with a typed error — nothing recreates a disposed clone or retired worktree, and re-execution takes a fresh run on the same branch through normal admission — so the rolled-back history is queryable and correct without ever activating a run against a nonexistent root ([Run State Machine §Rollback Transitions](../domain/run-state-machine.md#rollback-transitions-campaign-b2)).
- **Compaction-boundary-aware rewind targeting (2026-08-16 amendment).** Rewind-target validation is **compaction-boundary-aware**, and the boundary in question is the **provider's context-window compaction** — never the daemon's audit-log retention compaction. The two are distinct mechanisms with distinct rewind consequences and must not be conflated: the retention pass replaces this system's own event payloads with audit stubs and is governed by the uncompacted-rewind-span check above ([Spec-005 §Compacted Event Format](005-session-event-taxonomy-and-audit-log.md#compacted-event-format)), while a provider-side compaction rewrites the **provider's** live conversation context in place and is recorded here as a `usage.context_compacted` row ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). Let **B** be the greatest originating position among the target run's `usage.context_compacted` rows that are **current** — not already marked superseded by an earlier accepted rewind, so a boundary a prior rollback rewound past never gates a later one. That currency filter is stated for correctness, not because V1 reaches it: while every driver keeps the refusal below, no accepted rewind can supersede a compaction row — a boundary-clear target leaves the row at or below `targetPosition`, and the supersede cutoff marks only `turn > targetPosition`, so both the strictly-above and the equal arm leave it current — and the filter therefore becomes live exactly when a driver's re-verified boundary-crossing semantics does. B is resolved through the same operation-association rule that ranks every content-asynchronous straggler (the absorption bullet above) — the stamped originating position on a late row, the payload's operation linkage on an in-time one, and the row's own timeline slot only as the linkage-less fallback that rule already carries — never as a bare append-order read taken in preference to association. The distinction is **precision, not safety**: no row is ever appended before the operation it reports, so a slot-ranked boundary can only sit at or above the true one, and a slot-ranked B therefore over-refuses and can never silently admit a crossing target. Association is nonetheless required first, because that over-refusal would deny every legitimate rewind across the span between a compaction's originating turn and its late delivery — precisely the span a long-running turn makes widest. Classification is three-valued and **fails closed**:
  - **No boundary.** The run has no current `usage.context_compacted` row, and every target the domain check admits stays admissible. This is the V1 default: no V1 driver ships a compaction operation, so a boundary arises only from provider-native auto-compaction ([Spec-014 §Resolved Questions and V1 Scope Decisions](014-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions)).
  - **Boundary-clear** — `targetPosition` at or above B. The rewound tail lies strictly above the target, so the compaction row is not in it, the row stays current, and the provider legitimately keeps its compacted context: recorded state and provider state agree. The ordinary path applies unchanged. This deliberately includes a target **equal** to B — rewinding to the compaction's own turn boundary keeps the compaction, it does not reverse it.
  - **Boundary-crossing** — `targetPosition` strictly below B, **or** a current `usage.context_compacted` row the association rule resolves to no originating position at all — no stamp, no operation linkage, and no recoverable timeline slot. A row that resolves only through the linkage-less slot fallback is **not** in this arm: it ranks, conservatively and at or above its true position, and is classified on that rank like any other. The supersede cutoff would mark the compaction row rewound, asserting the compaction is undone, while no provider wire offers a compaction-restore operation ([Spec-014 §Resolved Questions and V1 Scope Decisions](014-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions): "neither provider wire exposes a compaction-restore operation" — the recoverability that section grants is an audit and re-derivation guarantee, deliberately not a live-conversation undo), and what a provider rewind actually reconstructs across its own compaction boundary — pre-compaction context, or the compacted summary alone — is exactly the question §Driver-Level Rollback Mechanics leaves open on both legs: neither cut was measured against a provider-side compaction boundary, and that section's compaction-boundary anchoring rule scopes the ADR-017 re-verification it owes to what **each** provider's rewind reconstructs across its own boundary, so neither leg is verified. Such a target is **refused whole, fail-closed, pre-dispatch**, with no leg applied and a machine-readable cause persisted on the durable intervention row — the same standing-refusal class as the uncompacted-rewind-span check, and for the same reason: admitting it would leave the rendered timeline asserting one context state while the provider holds another. A position-less compaction row classifies as crossing for **every** target of that run, because evidence of a compaction that cannot be proven to sit at or below the target must be treated as sitting above it — exactly as the span check treats a position-less audit stub as a span intersection.

  The classification is **provider-agnostic**, binding both legs identically, because it is a property of compaction being a context rewrite rather than of either wire's rewind mechanism: the Codex leg cuts the thread's turns, which does not un-compact a rewrite the provider has already applied to its own transcript, and the Claude leg cuts at a message address whose reconstructed context across a boundary is unverified. The refusal is **liftable, not permanent**: a driver whose declared capabilities carry re-verified boundary-crossing rewind semantics — verified against the then-installed binary under the same ADR-017 row that governs both rewind mechanisms — admits crossing targets on its own legs, and every other driver keeps the refusal. V1 registers no such capability member: the [Spec-004](004-provider-driver-contract-and-capabilities.md) capability surface carries no boundary-crossing-rewind declaration, so V1 classification reads **no capability input** and the refusal is unconditional on every driver — the lift is a named future Spec-004 amendment that registers the member, never a latent runtime branch waiting on a declaration no shipped driver can make. It follows that "undo the compaction" is not expressible as any admissible target in V1: it is definitionally the boundary-crossing class, never something a target at or above B achieves.

  **Classification is two-point: admission and settlement.** Admission classifies the requested target against the boundary set current at admission; the boundary set can move before the driver's `rollbackTo` confirmation — a `usage.context_compacted` row emitted pre-rewind but delivered late, or one emitted between admission and dispatch — and the in-stream fence bounds exactly how far: the driver's serialized provider connection totally orders event delivery against the `rollbackTo` confirmation (the absorption bullet above), so every boundary row the provider emitted before the rewind is delivered by the time the confirmation arrives. The confirmed floor is therefore **reclassified at settlement against the then-current boundary set** — the same three-valued classification, its third arm now actionable-degraded rather than refusable, because dispatch has happened and no wire un-rewinds: a confirmed floor the settlement classification finds strictly below the then-newest current B settles the intervention **`degraded`** naming the **`boundary-diverged`** disposition — the file leg is skipped fail-closed, a staged `replacementSend` is suppressed (`resendDisposition: 'unapplied'`), the run follows conversation truth `paused` at the confirmed floor, and the forward `run.rolled_back` records the confirmed position with the divergence cause persisted on the durable row. The settled outcome names **both** sides of that comparison — the confirmed floor and the boundary it diverged from — with one narrowing (2026-08-25): where the then-current boundary set's newest row is **position-less** (the unknowable-position shape admission rejects outright, arriving here only between admission and the driver's confirmation), the outcome names the confirmed floor beside an explicitly **null** comparand rather than omitting the member, so a divergence is never reported as an unstated cause and the absent-member reading stays unavailable to a parser. **`run.resume` then holds the line:** resume against a run whose current position sits strictly below the newest current B refuses fail-closed with a typed error — the same standing-refusal family as the rootless-resume refusal, and the backstop for the one window settlement cannot see: a boundary row whose content-asynchronous delivery lags past settlement (the absorption bullet's long-tool span). A boundary-diverged run is therefore **non-resumable in V1** exactly as the rootless class is — its history stays queryable and correct, re-execution takes a fresh run on the same branch through normal admission, and the refusal lifts with the same future capability amendment that lifts the crossing-target refusal (no rollback can move the run forward to clear the boundary — targets sit strictly below the current position by the domain check — so the resume refusal is the class's terminal shape, not a recoverable degrade).

- **Atomic edit-and-resend (2026-08-16 amendment).** Correcting a previously-sent user message — editing its text and re-dispatching it — is an **optional replacement-send leg on the `rollback` intervention above**, never a new intervention type, wire method, or event type: `applyIntervention('rollback', {targetPosition, replacementSend})`, where `replacementSend` carries the corrected message body. The whole operation is **one intervention**: one durable `interventions` row, one `clientIdempotencyKey`, one `expectedRunVersion` guard evaluated once at admission, one application under the session's append serialization — the same atomicity the pause-first composite already holds, extended by one leg rather than forked into a second mechanism. Every rule the rollback bullet states applies unchanged: the target-position domain check, the compaction-boundary classification, the uncompacted-rewind-span check, the capability check, confirmed-floor validation, epoch advance, supersede-by-projection, and write-ahead dispatch reconciliation. Five additions are specific to the replacement leg.

  **The replacement leg admits; it does not dispatch — and it admits run-bound.** On a fully-successful rewind (the admission condition below) the corrected message is admitted as a durable queue item against the rewound run through the ordinary user-send path (the `user.message` row plus queue admission — admission in the user-send sense of durable acceptance into the queue: the row persists in queue-state **`queued`**, reaching the queue-state `admitted`'s run-bound arm only at the `run.resume` drain's delivery), and the queue item is **durably bound to that run**: admission stamps `queue_items.target_run_id` with the rewound run's id, and a run-bound item is **delivered into its bound run as that run's next provider send on its next `run.resume`** — never converted into a new run, which is what admission means for an unbound follow-up item ([Queue And Intervention Model §State Model](../domain/queue-and-intervention-model.md#state-model) carries both admitted-state arms). The binding is composite-internal in V1: `QueueItemCreate` mints no run-bound items — `target_run_id` is stamped solely by this leg's admission (and by its reconciliation completion), so the queue wire request shape is unchanged. The run lands `paused` at the confirmed position exactly as a bare rollback does — **no auto-resume**, and no second driver-facing call: the composite's only driver contact remains the conversation leg (plus the internal interrupt the pause-first path adds on a `running` source). The admission and the intervention's terminal settlement commit in **one durable transaction** — the queue item, its `user.message` row, and the intervention's outcome are a single atomic write, never two (the failure-taxonomy bullet below carries the crash consequence). **Admission is conditioned on the composite's other legs, fail-closed:** the replacement admits **only** when the confirmed floor **equals** `targetPosition` (a position-mismatch degrade suppresses it — a corrected message must never be delivered after a boundary the caller did not authorize it to follow), the settlement-time boundary reclassification concludes boundary-clear (a `boundary-diverged` degrade — the compaction bullet above — suppresses it), **and** the file leg completed or the run legitimately takes the conversation-only branch (a file leg that failed suppresses it — delivering the corrected prompt into a half-restored folder would execute the caller's intent against state the rewind never produced); a suppressed replacement stays recoverable on the durable intervention row, and the caller's recovery is a fresh composite to the same point **with the replacement leg re-attached** — guard (i) is clean, since suppression admitted nothing. Every composite settlement that reaches a terminal result additionally reports the resend outcome **structurally**: the rollback outcome detail carries a `resendDisposition` member (`'admitted'` | `'unapplied'`) — **schema-optional on the wire, producer-obligated at settlement**: with a single exception no member of a rollback result identifies its request as composite (`replacementSend` is request-side and the result does not echo it), so requiredness is not expressible at the strict-parse boundary; the schema parses the member optional on every rollback result **except the composite-only `resend-unapplied` degraded arm — the exception, and the counterexample to that premise, since a bare rollback can never settle there: on that arm requiredness IS expressible, so the schema REQUIREs the member (`'unapplied'`, its only admissible value) rather than admitting a settlement that omits the very leg the disposition exists to report** (2026-08-25 narrowing) — and the daemon's tested producer obligation is that a composite settlement always populates it and a bare rollback settlement never does — so a caller reads the resend outcome from a typed member rather than parsing a disposition taxonomy whose primary job is naming the earliest-failing leg — in V1 the value is determined by the terminal state (`applied` ⇒ `'admitted'`, every `degraded` arm ⇒ `'unapplied'`), and it is carried structurally anyway so the resend outcome stays typed if the admission-condition arms ever widen. The drained replacement's turn additionally executes under the **admitting intervention caller's** effective principal — [Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)'s turn-scoped effective-principal rule, extended 2026-08-17 to the run-bound replacement send as its intervention-opened arm, durably recorded via the admitting-principal carrier that [Plan-010 §Preconditions](../plans/010-approvals-permissions-and-trust-boundaries.md#preconditions)' carrier box registers — because a corrected prompt authored by an intervening user must not execute with the run initiator's authority. The queued replacement drains on the next `run.resume` of its bound run — necessarily as the **next** send, because guard (i) below refuses the composite while any earlier pending send exists on the target run: at admission the rewound run's queue holds no older send to deliver first, so the resend-next ordering is enforced by refusal at the gate rather than by a queue-priority mechanism V1 explicitly defers (§Resolved Questions' queue-priority deferral). "Resend" therefore guarantees the corrected message is durably re-submitted and will be delivered next in order — never that it is already on the provider wire when the intervention settles. Anything else would contradict the rollback bullet's two standing rules (a confirmed rollback lands `paused`; the composite never auto-resumes) for the sake of one leg.

  **The caller's text is durable before anything destructive runs — and it rides the PII envelope, never the plaintext payload.** (The 2026-08-18 amendment generalizes this paragraph's split to **every** user-authored intervention body — steer directive text included, per the at-rest-split bullet below — of which the `replacementSend` body specified here is the composite's instance; the mechanism, the erasure parity, the retention bound, and the export leg are identical for each.) The accepted intervention row is durable **before** driver dispatch (the rollback bullet's write-ahead dispatch-intent marker), and the `replacementSend` body is persisted **on that row through the same user-keyed PII split the ordinary `user.message` path applies** ([Spec-005](005-session-event-taxonomy-and-audit-log.md)'s `splitPii` discipline, Plan-005's `PiiEncryptor` seam): the corrected text encrypts into the row's PII-bearing field (`interventions.pii_payload`, stamped `interventions.pii_user_id` = the requesting user), while the plaintext `interventions.payload` carries only the non-PII rollback members and the replacement leg's presence — a user message body never lands plaintext at rest here when the event path it replaces would have encrypted it. Erasure parity is structural, not procedural: crypto-shred is user-key deletion (Plan-020 Path 1), so the key deletion that shreds the `user.message` event copy shreds this copy identically — no second erasure path exists to forget. The corrected text therefore survives every failure arm including a daemon crash mid-composite, recoverable under the requester's live user key. V1 has no daemon-side composer-draft surface to stage it in — daemon-side draft persistence is deferred past V1 and `human_phase_form_state` ships empty ([Spec-015 §State And Data Implications](015-workflow-authoring-and-execution.md#state-and-data-implications)) — which is precisely why the intervention row, already the reconciliation source, carries it. The copy is retention-bounded and export-registered like the event copy it mirrors ([Spec-020 §PII Data Map](020-data-retention-and-gdpr.md#pii-data-map) carries the row): past the [Spec-020](020-data-retention-and-gdpr.md) 90-day full-retention bound the daemon's retention pass NULLs `interventions.pii_payload` while retaining the non-PII intervention audit record for the row's lifetime — a plain NULL-out, safe here where the `session_events` copy must instead compact to an audit stub, because no digest, signature, or anchor binding attaches to the intervention row's ciphertext — and the user data-subject export (`GET /users/{id}/export`) includes the decrypted replacement-send bodies of intervention rows stamped with the user, since text that exists only on a refused or suppressed intervention row is still that user's authored content.

  **Three structural refusal guards, each fail-closed at admission, pre-dispatch, and whole-intervention.** A `running` target is not among them: the pencil is offered through a running turn, so the composite takes the same pause-first path as a bare rollback and the conversation cut ends the live turn itself (§Driver-Level Rollback Mechanics). (i) **No pending send.** A run holding **any earlier pending send** refuses the composite, in either of its two forms: an accepted send whose provider delivery is not yet confirmed — the window between the admitted `user.message` row and the provider's `user_text` wire echo folding into it as delivery confirmation, where the target cannot be validated against a turn boundary the provider has not yet acknowledged — or an **undrained queued send** admitted before the composite, which ordinary FIFO would deliver ahead of the replacement and thereby make the corrected message not the next send, the very promise the leg exists to keep. Front-inserting the replacement ahead of the older item is not an admissible fix: that is a queue-priority override, which V1 explicitly defers (§Resolved Questions' queue-priority deferral). The pending-send order is not the composite's to reorder — the caller's remedy is to move, cancel (`QueueItemCancel`) or drain the waiting rows themselves, on the rows' own controls (§Resolved Questions and V1 Scope Decisions), then re-issue; the queued-send arm of this refusal lifts if and when V1.1 priority overrides land. (ii) **A user-authored target of this run.** `targetPosition` must name a turn boundary opened by a user-authored `user.message` of the target run; a boundary opened by any other origin has no user send to replace. An orchestration-authored boundary — a workflow phase's input or an orchestrated child run's ([Spec-014](014-multi-agent-channels-and-orchestration.md), [Spec-015](015-workflow-authoring-and-execution.md)) — therefore refuses the composite, since rewriting one would rewrite a phase input outside the workflow's own authoring surface. Bare rollback of such a boundary stays admissible; only the replacement leg is refused. (iii) **A resumable target.** The leg's whole promise is delivery on the bound run's next `run.resume`, so a target run that can never resume is refused: the rollback bullet's **rootless** class — a run whose execution context is released with no existing root (a disposed ephemeral clone, a retired worktree), which that bullet already marks non-resumable with a typed refusal, together with an execution context — live, which the confirmed rollback itself releases into that class, or already released, a terminal source arriving in it — whose recorded checkout root no longer exists on disk (admitting its replacement would settle a send onto a run the same settlement just made — or found — non-resumable — Codex PR #346 round 2) — could hold a queued replacement only as a dead letter, so the composite refuses it whole rather than admitting a send no resume will ever drain. Bare rollback of a rootless run stays admissible (conversation-only, queryable history); only the replacement leg is refused — and the caller's path to re-execution is the one the rollback bullet already names: a fresh run on the same branch through normal admission, carrying the corrected text as its input. **Which guard refused is reported structurally (2026-09-06 amendment).** A refusal raised by any of the three settles `rejected` carrying, beside the machine-readable `rejectionReason` cause, the **closed-union `rejectionGuard`** member naming the guard — `'no-pending-send'` | `'user-authored-target'` | `'resumable-target'`, the three names above kebab-cased with the leading article dropped, each naming the condition its guard requires rather than restating the failure. The member is **arm-scoped** (the `rollback` `rejected` arm, never the shared response base, since only a composite raises these guards) and, within that arm, **schema-optional and producer-obligated** exactly as `resendDisposition` is and for the same reason — no member of a `rejected` response identifies its request as composite, so requiredness is not expressible at the strict-parse boundary — with the daemon's tested obligation being that a guard refusal always populates it and every other refusal family never does — the **six** [Queue And Intervention Model §Intervention State Transition Table](../domain/queue-and-intervention-model.md#intervention-state-transition-table) admits for a rollback: capability, authorization, target-position domain, compaction-boundary, incompatible target run state, and uncompacted-rewind-span. `rejectionReason` is unchanged: the typed member exists so a client renders a per-guard remedy by an **exhaustive** switch, which its sibling's open vocabulary cannot support at any amount of care. A fourth guard is an amendment of this paragraph and of that union together, never a free string; and the union is a wire vocabulary only — the eligibility predicate stays the daemon's, and any client-side projection of it remains fail-closed and never a second source of eligibility truth. **The literal is durable, so the replay contract holds across a restart.** The daemon persists the refusing guard on the intervention's own row beside the machine-readable cause, and an idempotent replay of the same `clientIdempotencyKey` returns a `rejectionGuard` **equal to the recorded one** — a daemon restart between the refusal and the replay included. It is stated because it does not follow from the sibling: the recorded outcome of a `rejected` intervention is reconstructed from the durable row (the wire contract carries no `result` on that state), and `rejectionReason`'s vocabulary is open and unenumerated, so the literal cannot be recovered from it without the match against an unpublished value set this member abolishes. A replay may therefore never omit the member, and may never re-derive it by re-evaluating the guards — the run has moved on, and re-evaluation would answer about the run's state now rather than about the refusal that was recorded.

  **The failure taxonomy is three-valued, and the caller's text is recoverable in every arm that reaches intervention creation.** **Refused** — any pre-dispatch validation fails: nothing dispatched, no leg applied, the intervention settles `rejected` (or `expired` on a guard mismatch), and the caller still holds its own text. One refusal family settles with **no intervention row at all**: a cross-node composite denied by the target owner's approval or rejected by the pre-approval authorization check is refused before intervention creation (§Interfaces And Contracts' cross-node rule — no intervention state, no `InterventionResult`), so the durable-row guarantees of this bullet do not attach there; the refusal returns on the wire and the caller-side surface that authored the text (the CLI invocation, the composer) remains its holder. **Committed-then-failed** — the conversation rewind is confirmed but the replacement send is not admitted, in either of two shapes: an admission-condition suppression (the admits-paragraph above — the disposition then names the earlier-failing leg, precedence following leg order: `boundary-diverged`, then position-mismatch, then a file leg that failed), or an admission that itself fails after a fully-successful rewind — the **`resend-unapplied`** disposition, reserved for exactly that arm — which is therefore the one degraded disposition that **displaces a completed file restore** rather than following a file leg that was skipped fail-closed or that failed, so it reports that restore the way a completed restore reports itself — the files it put back and the files it skipped, each skip with its reason — keeping the never-silent rule intact across the displacement ([Spec-013 §Fallback Behavior](013-persistence-recovery-and-replay.md#fallback-behavior)). Either way the intervention settles `degraded` carrying `resendDisposition: 'unapplied'`, the run lands `paused` at the confirmed position with `run.rolled_back` appended exactly as a bare rollback does (run state follows the confirmed conversation leg), and the text stays recoverable on the durable intervention row under the requester's user key. **Transport-lost** — the outcome is unknown to the caller through a driver throw, timeout, or daemon restart: the existing write-ahead reconciliation resolves it, and the [Spec-013](013-persistence-recovery-and-replay.md) position-compare's completion branch drives the staged `replacementSend` forward among the remaining legs — concluding a confirmed rewind without re-dispatching it would strand the very text this leg exists to preserve. The completion branch admits and settles in the **same single transaction** the live path uses, which is what makes recovery crash-idempotent: an intervention observed unconcluded at restart **proves** no admission occurred (the two outcomes cannot diverge — there is no window between an admitted replacement and an unsettled intervention for a crash to land in), so reconciliation never re-admits a message the run already holds, and replaying the same `clientIdempotencyKey` returns the recorded outcome rather than sending twice.

  **Superseded marking applies solely on the accepted `run.rolled_back` boundary.** It is driven by that event's confirmed position and by nothing else — not by the composite's admission, not by its dispatch, and not by the replacement send. A client MAY dim the turns a pending composite would rewind, and MUST NOT remove or renumber them before the boundary appends: a composite whose conversation leg does not confirm applies no rewind at all (the no-rewind path above), so an optimistic truncation would delete history the run still holds (§Implementation Notes' optimistic-affordance rule). Because the replacement send appends **after** the boundary in the session's append order, a consumer observes rewind-then-resend from ordering alone, and the composite needs no linkage field on either row to be rendered correctly.

- **Every accepted intervention durably records the principal that admitted it (2026-08-18 amendment).** The daemon resolves the caller's **transport-authenticated** identity at acceptance and persists it on the intervention row, alongside a daemon-resolved `origin` discriminator naming which admission path produced the row. Resolution follows the three mechanisms the approval pipeline's shipped approver identity already uses ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)): the daemon's node-owner user identity on the local socket, the verified PASETO `sub` on authenticated surfaces, and `caller_token.sub` on the [Spec-022](022-cross-node-dispatch-and-approval.md) cross-node arm. The wire `initiatorId` is **never** the source — it stays routing/audit metadata per [ADR-011](../decisions/011-generic-intervention-dispatch.md), and a request whose body actor disagrees with the verified identity is refused through the existing `auth.principal_mismatch` error, never trusted and never silently normalized. `origin` is `'user'` for a request admitted over an identity-carrying transport and `'system'` for the in-process orchestration entrypoint that sits below the wire authorization boundary and carries no user at all; the principal is **required exactly on the user arm and forbidden on the system arm**, enforced as a storage constraint so a user-origin row can never persist unidentified and a system-origin row can never smuggle an identity in. The discriminator is resolved, not inferred: a client-supplied `initiatorId`'s absence is not evidence of a system admission. Recording the principal on the row — rather than reconstructing it later from run history — is what makes it **replay-stable**, since a run accumulates interventions over its life and history offers no single answer to which one authorized a given unit of work. A queue item admitted by an intervention carries a **row-anchored linkage** to that intervention for the same reason, so its drain resolves one admitting row rather than scanning a history. Producers write the stamp inside the transaction that accepts the intervention — for the edit-and-resend composite, the single durable transaction that already commits the admission and the settlement together, never a second write that a crash could separate. Consumers are the authorization path: a turn opened by an accepted intervention adjudicates under the recorded principal ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)'s turn-scoped resolution, covering both the steer-opened and replacement-send-opened arms), and an unresolved principal adjudicates as a **deny**, never as the run initiator.
- **User-authored queue-item bodies rest encrypted, exactly as intervention bodies do (2026-08-18 amendment).** A queue item's user-authored send body is persisted through the same user-keyed PII split this spec already specifies for intervention bodies: the text encrypts into the item's PII-bearing field under the authoring user's key with that user stamped as the owner, while the plaintext payload retains only the non-PII members. Before this rule the queue row held the body in plaintext while the `user.message` event copy of the same text was already encrypted — one send, two at-rest copies, one of them unprotected and, worse, unreachable by erasure: no column on the queue row named a user, so the [Spec-020](020-data-retention-and-gdpr.md) fan-out had no selector for the table at all. The owner stamp **is** that selector, and same-key parity makes erasure structural: the one user-key deletion that shreds the event copy shreds the queue copy in the same act, with no second erasure path to forget. Content authored by orchestration rather than by a user — a workflow phase input, an orchestrated child-run prompt — stays plaintext with both fields unset: it is session work product rather than user PII, and the system admission path holds no user key to encrypt under. Queue rows remain **durable and never-evented**, drained but never deleted and canonical for audit and replay; this rule changes what a row stores at rest, not its lifecycle. Queryability is unaffected because every field admission and drain select on — state, priority, run binding, channel, session — is its own column and none of them is content.

## Default Behavior

- A user message sent while a run is active is persisted as a queue item and then delivered into that same run at its next step boundary. Queueing is how the message is made durable, not a way of holding it back for a later run.
- Queue ordering default is FIFO within the target scheduling scope.
- If a driver does not support steer natively, the intervention must be rejected or degraded to a new queue item. Both V1 providers deliver a message handed to them mid-run into the running run, so neither reaches that degrade; it is the rule for a driver that cannot. Pause does not require driver support either — it is an orchestration-layer run-control mutation (`run.pause` / `run.resume`), composed by the daemon out of the session's own hooks and, where a provider has none, a boundary interrupt (stop at the step boundary, persist, queue a resume), and **not** dispatched through the driver-facing `applyIntervention` path that steer/interrupt/cancel follow ([ADR-011](../decisions/011-generic-intervention-dispatch.md); no intervention type is minted for it — see [Queue And Intervention Model](../domain/queue-and-intervention-model.md)).

## Fallback Behavior

- If `steer` is requested against a run that cannot accept it, the system must either reject the intervention or explicitly degrade it to a new queue item.
- If a paused run cannot be resumed because driver state is lost, the system must transition it through recovery logic and then to `failed` or `interrupted`; it must not pretend the same run resumed.
- If queue persistence is temporarily unavailable, the system must reject new queue creation rather than silently storing queue state only in client memory.

## Interfaces And Contracts

- `QueueItemCreate`, `QueueItemList`, and `QueueItemCancel` must operate against runtime-owned durable state.
- `InterventionRequest` must include target run id, intervention type, and a **mandatory** version guard (`expectedRunVersion`). The guard is **fail-closed**: the comparand is required on every intervention, and an absent comparand is **rejected**, never applied — an optional guard would let a caller bypass stale-replay protection by omitting the field (Plan-003 D-003-2). `expectedRunVersion` is compared against the target run's `runVersion` — an **any-run-progression counter** that increments on every run progression, applied interventions included (not only `run.*` state-machine transitions), so two steers racing on a still-`running` run cannot both pass undetected (Plan-003 D-003-1). `runVersion` is the run aggregate's optimistic-concurrency token, distinct from the immutable `EventEnvelope.version` wire-contract field ([Spec-005 §EventEnvelope Version Semantics](005-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics)). Payload fields vary by type: `steer` includes `expectedTurnId`, `content`, and optional `attachments` — typed `ArtifactId[]` since 2026-09-08 (CP-012-7), an ordered list of ids into [Spec-012](012-artifacts-files-and-attachments.md)'s manifest space and never an untyped element or an inline byte payload, carrying that spec's order-preserving, never-silently-dropped, refused-whole-rather-than-truncated carrier contract as [API Payload Contracts §Plan-004 — Provider Driver Contract (Internal Interface)](../architecture/contracts/api-payload-contracts.md#plan-004--provider-driver-contract-internal-interface) states it once for both ends of the carrier; `interrupt` and `cancel` include optional `reason`; `rollback` (campaign B2) includes a **mandatory** `targetPosition` — the normalized session position (a `number`, [Spec-004](004-provider-driver-contract-and-capabilities.md) `RollbackToParams.position` vocabulary) of the turn boundary to rewind to — plus an **optional** `replacementSend` (2026-08-16 amendment) carrying the corrected message body of the atomic edit-and-resend composite (§Required Behavior): absent on a bare rollback, and its presence is exactly what selects the composite's three additional refusal guards, its admission-conditioned resend with the structural `resendDisposition` result member, and its `resend-unapplied` disposition, so no separate discriminator is required. The matching optional member on the wire union's `rollback` arm is a named [Plan-003 §Preconditions](../plans/003-queue-steer-pause-resume.md#preconditions) merge prerequisite against [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) rather than an edit carried by this amendment (registered 2026-08-25 as that arm's optional `replacementSend` member — [API Payload Contracts §Plan-003 — Queue Steer Pause Resume](../architecture/contracts/api-payload-contracts.md#plan-003--queue-steer-pause-resume) — so the named prerequisite box now reads `- [x]` and this sentence records a discharged obligation rather than an outstanding one; the V1 control set is unwidened, and the three narrowings that registration surfaced — the `resend-unapplied` arm's REQUIRED `resendDisposition`, that arm's displaced never-silent restore report, and the nullable settlement comparand — are folded into §Required Behavior above under the 2026-08-25 amendment blockquote, with both Status rows flipping and restoring `approved` in that same swap). Every intervention request additionally carries a **mandatory** requester-generated `clientIdempotencyKey` (UUID) — the second, orthogonal guard ([Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior), campaign B3): `expectedRunVersion` defeats stale replays of outdated intent, the key defeats duplicate applications of the same intent (replay-or-conflict, `intervention.idempotency_conflict`). The replay-or-conflict body comparison is **PII-safe by construction** on the composite: whether a reused key carries the same or a differing `replacementSend` body is decided by decrypting the stored envelope under the requester's live user key (the injected `PiiEncryptor` seam) and comparing plaintexts — never by comparing ciphertexts (the envelope is nonce-randomized, so equal plaintexts encrypt unequal) and never by persisting a plaintext digest beside the envelope (a retained digest of erased text would survive [Spec-020](020-data-retention-and-gdpr.md) Path-1 crypto-shred as a guessing oracle) — and a stored body rendered undecryptable by user-key shred settles the reuse fail-closed as `intervention.idempotency_conflict` ([Queue And Intervention Model](../domain/queue-and-intervention-model.md) owns the canonical rule). See [Queue And Intervention Model](../domain/queue-and-intervention-model.md) for canonical payload shapes.
- `InterventionResult` must distinguish the 6 canonical intervention states: `requested`, `accepted`, `applied`, `rejected`, `degraded`, and `expired`. A version guard mismatch produces `expired`. An authorization failure produces `rejected`.
- Intervention dispatch uses `applyIntervention` (see [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md) and [ADR-011](../decisions/011-generic-intervention-dispatch.md)), which routes to the appropriate driver-specific handler based on intervention type and declared capabilities. The Cedar `principal` for authorizing an intervention is the caller's verified user identity: the verified PASETO `sub` on every identity-carrying transport (control-plane, relay, and the cross-node dispatch path, where the target binds the principal to the verified `caller_token.sub` per [Spec-022](022-cross-node-dispatch-and-approval.md)'s envelope rules), and — on the daemon's local socket, which carries no PASETO token — the daemon's node-owner user binding resolved through the Plan-016-gated credential/identity provider seam (a named [Plan-003 §Preconditions](../plans/003-queue-steer-pause-resume.md#preconditions) prerequisite); `initiatorId` and any body-level actor fields are informational only. See [API Payload Contracts §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model). The Cedar **action** for a run-control intervention is `Action::"intervene"` on the target `Run` resource, with the run's **hosting node** carried in the request context. Authorization is never evaluated against run authorship — the session's user may intervene on any run in the session, whatever started it ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior) owns the rule); a non-local hosting node **adds** the target-node-owner approval requirement (an approval in the `tool_execution` category per [Spec-022](022-cross-node-dispatch-and-approval.md)), so cross-node intervention is a request, never standing authority. The same adjudication governs the orchestration-layer `run.pause` / `run.resume` run-control mutations even though they never ride `applyIntervention` (they are daemon-handled orchestration verbs holding no `InterventionType` membership): their handlers evaluate the identical `Action::"intervene"` request — same `Run` resource, same hosting-node context, same authorship-blind rule, same cross-node node-owner approval leg — before composing any run-state mutation, per [Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)'s governed-identically rule, so the dispatch-path split is transport plumbing, never an authorization boundary.
- **Rollback routing (campaign B2).** `rollback` is a full intervention on the client→daemon wire — the `InterventionRequestPayload` union in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) carries a `rollback` member, and the request flows through the same authorization, `expectedRunVersion` guard, idempotency ledger, and `InterventionResult` lifecycle as every other type. At the driver boundary it does **not** ride `ApplyInterventionParams`: the conversation leg dispatches through the driver's dedicated, capability-gated `rollbackTo` parity operation ([Spec-004 §Interfaces And Contracts](004-provider-driver-contract-and-capabilities.md#interfaces-and-contracts), campaign B3) — `RollbackToParams {sessionId, position, bindingId}` returning `DriverRollbackResult` (`applied {sessionPosition, bindingId?}` | `degraded {fallbackAction?}`). The `bindingId` leg key is **daemon-resolved at dispatch** — run→bindings is 1:many, so the daemon names the run's live provider binding exactly as it does for goal delivery; client rollback payloads never carry it (clients address the run). Neither V1 leg mints a second binding: both conversation cuts happen in place on the session the run is already bound to (§Driver-Level Rollback Mechanics), so the result's optional `bindingId` is absent on each and exists for a mechanism that would mint one. The optional `replacementSend` of the 2026-08-16 amendment's edit-and-resend composite never crosses this boundary at all: it is daemon-held state — persisted on the write-ahead intervention row through the user-keyed PII envelope (§Required Behavior's at-rest split), then admitted through the ordinary user-send path once the conversation rewind confirms — so `RollbackToParams` is unchanged by the composite and the driver leg cannot distinguish a bare rollback from one carrying an edit ([Queue And Intervention Model §Field-Level Consistency](../domain/queue-and-intervention-model.md#field-level-consistency) carries the same non-forwarding rule). A driver whose capabilities do not declare rollback support produces a **static refusal** (`driver.capability_unsupported`, the [Queue And Intervention Model §Driver Result To Lifecycle Mapping](../domain/queue-and-intervention-model.md#driver-result-to-lifecycle-mapping) no-documented-fallback carve-out) — there is no orchestration-layer emulation, because a synthesized rollback (replaying a truncated history into a fresh run) would violate same-run resurrection and silently fork budgets and supersede-marking.
- See [Queue And Intervention Model](../domain/queue-and-intervention-model.md) § Boundary: Interventions vs Interactive Requests for the steer/respondToRequest distinction.
- The run-control surface on the wire is `run.subscribeState` and `run.subscribeQueue` (the live run state, and the items waiting for the run), `run.queueList`, `run.queueCreate` and `run.queueCancel`, `run.intervene`, and `run.pause` / `run.resume`. The canonical stream carries the run-lifecycle events the state machine defines — `run.queued`, `run.starting`, `run.provider_initialized`, `run.running`, `run.turn_started`, `run.waiting_for_approval`, `run.waiting_for_input`, `run.paused`, `run.interrupted`, `run.completed`, `run.failed` and `run.rolled_back` — and the intervention lifecycle `intervention.requested`, `intervention.accepted`, `intervention.applied`, `intervention.rejected`, `intervention.degraded` and `intervention.expired`.
- **Three child-control operations, one per control.** Steering a named child run, interrupting it, and toggling its pause are three driver operations with three matching calls of their own, each carrying the child the operation acts on, and each gated by what the provider declares in its initialization frame rather than by a version compare. The daemon owns the mechanism behind them: on Claude Code the pause is the hold on the child's next tool callback and the interrupt is that hold plus the end of the child's running command — never the provider's own stop verb, because a child stopped that way refuses the lead's next message and the wire offers no way to address the child directly — while a steer to a running child goes through the lead; on Codex all three ride the child's own thread, `turn/steer`, `turn/interrupt`, and the boundary interrupt that makes the pause, for a child of the v1 collaboration shape at any depth, while a v2 subagent takes the interrupt directly and its steer goes through its parent. Continuing a child is a send, never an operation of its own.

## State And Data Implications

- Queue items require durable storage and ordering metadata.
- Interventions require durable audit records even when they fail.
- Blocked states must remain associated with the same run id and same event lineage.
- **Intervention audit records carry an identity, not just an outcome (2026-08-18 amendment).** The durable intervention record must hold the daemon-resolved admitting principal and the `origin` discriminator beside the outcome fields, with the storage layer enforcing that the two agree — principal present exactly on the user arm. A queue item admitted by an intervention must hold a durable reference to that intervention row, so the drained turn's authority is resolvable from the item alone. Neither field is client-writable.

  **The resolved authority is published per turn, not left to be re-derived (2026-08-26).** Recording the admitting principal on the intervention row makes the authority _resolvable_; it does not make it _reachable_ by a consumer that meters a turn rather than admitting one. At every turn boundary the run engine opens, it therefore resolves that turn's effective principal — the admitting user of the intervention that opened the turn (a steer, or a rollback carrying `replacementSend`), otherwise the user who started the run, otherwise the `system` arm where no user caused it — and publishes it as an **immutable per-turn scope** on the run's execution context, where the driver's usage normalizer reads it and carries it onto the metered row ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). Per-turn and immutable are both load-bearing: the normalizer stamps from the scope **bound to the turn whose stream produced the frame**, never from a mutable "current turn" read when the frame arrives, because a metered row for one turn routinely lands after the next turn has opened and a read-at-emission stamp would attribute that spend to whoever caused the following turn. A published scope is never mutated; a new turn mints a new one. The resolution rule itself is unchanged and stays owned by [Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior); what this adds is the obligation to publish it, so that no downstream fold has to recover the identity by ordering metered rows against turn-boundary events — the derivation the [api-payload-contracts.md §Authenticated Principal](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model) class rule forbids. The value is published and never emitted by this spec's surface: it mints no event, no column, and no wire member here.

- **Both durable tables store user-authored bodies encrypted and owner-stamped (2026-08-18 amendment).** Intervention rows and queue rows each require a user-keyed ciphertext field and a user owner stamp beside their plaintext payloads. The owner stamp is what makes each table addressable by the [Spec-020](020-data-retention-and-gdpr.md) erasure and export paths; a table holding user content with no user column is not erasable, which is the defect this closes for queue items. Both fields are nullable — orchestration-authored rows legitimately carry neither.

## Driver-Level Steer Mechanics

- **Codex driver**: native `turn/steer`. The daemon holds the message and steers it in at the thread's next tool boundary, so the content joins the running conversation as a new user turn and the turn continues from it; a steer aimed at a request that has already gone out lands at the step after.
- **Claude driver**: Claude Code accepts a message handed to it mid-turn and holds it until its next tool boundary, where the content joins the running conversation as a new user turn — so steer is delivered inside the same run, with no interrupt and no second run. The daemon's own id on each message is what a withdrawal, a replacement or a reorder acts on: withdrawing is the provider's cancel on that id, replacing the text is a cancel and a fresh send, and reordering is a cancel of the affected messages and a resend in the new order.
- **Generic driver fallback**: a driver that can accept nothing mid-run degrades to queue plus interrupt — interrupt the active run, hold the content as a queue item, and admit it as the next run, with the conversation history preserved. Neither V1 provider reaches this path.

### Steer Content Injection Point

- On both V1 providers: the content appears as a new user message in the running conversation at the next step boundary, and the model reads it as a follow-up the user sent.
- For degraded steer (queue + interrupt): content becomes the initial message of the new run. Previous conversation history is loaded from the session event log.
- In every case: steer content is marked with `source: 'steer'` in the event payload so the timeline can distinguish it from normal user messages.

The typed payload shapes for steer, interrupt, cancel, and rollback interventions are defined in [Queue And Intervention Model](../domain/queue-and-intervention-model.md) and verified against API contracts in that document's Field-Level Consistency section.

## Driver-Level Rollback Mechanics

- **Claude driver**: native, and in place. The conversation cut is the control request `rewind_conversation {target_message_uuid, interrupt_if_running}`; the driver owns the normalized-position → message-identifier translation and runs `--replay-user-messages` so message-identifier rewind targets appear on the wire. The cut happens on the session the run is already bound to — no second session is minted and the run keeps its live provider binding — so a rewind is not a relaunch and nothing has to be repointed. The driver sends `interrupt_if_running: true`, so the cut itself ends a turn that is still live: a rewind needs no separate interrupt ahead of it, and the composite of §Required Behavior therefore rewinds a `running` target rather than refusing it. The same flag is what makes the cut one-way for the run's sidekicks: every sidekick started at or after the cut is killed and recorded as stopped by the person, after which the provider refuses every later message to it, so those sidekicks cannot be resumed and the question asked before a restore says so. Measured on Claude Code 2.1.276, three runs of three: the two running children were killed about four milliseconds after the request and their progress markers froze there, and a later message to either came back refused, reading that the agent was stopped by the user and was not resumed.
- **Codex driver**: native, and in place. The conversation cut is `thread/revert {threadId, beforeTurnId}`, which cuts the thread's own history and nothing else — the same thread, so the run keeps its live provider binding here too. Measured on Codex 0.155.1, three runs of three: a three-turn thread reverted before its second turn came back listing one turn, the files the reverted turns had written were all still on disk, and a sidekick the third turn had started was still running and still addressable after the cut. Two consequences are normative. The daemon stops such a sidekick itself, one stop per id from its own record of the run tree, and each one is resumable afterwards — the opposite of the Claude leg, which is why the question asked before a restore is worded per provider (§Required Behavior). And the predecessor `thread/rollback {threadId, numTurns}` is not a method V1 may build on: it was refused `-32600 "paginated threads do not support thread/rollback"` on all three runs, and its deprecation now lives in the generated type itself (primary source: [Codex Wire Reference §`thread/rollback`](../reference/provider-wire/codex.md#threadrollback--session-time-travel-conversation-leg), with the successor recorded in the same file). Whether a turn still running must be interrupted before the revert, and in which order, is not measured (§Resolved Questions and V1 Scope Decisions).
- **Neither verb touches a file.** Both cut conversation history only, measured above, so **file restore is the daemon's own per-session file checkpoint store** ([Spec-013 §Required Behavior](013-persistence-recovery-and-replay.md#required-behavior)) — one mechanism, the same on both providers, never the provider's own file rewind and never a driver leg. That store is what every restore reads from — a restore anchored on one of the user's own messages, and a restore aimed at a named snapshot of the session alike, the snapshot only naming the point to return to ([Spec-008 §Turn-Boundary Snapshots](008-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)). What a shell command wrote lies outside the checkpoint store on both providers, and the dry run says so before anything is put back.
- **Confirmed floor**: `DriverRollbackResult`'s `applied` variant carries a REQUIRED driver-confirmed `sessionPosition` — the new authoritative recovery floor consumed by the [Spec-013](013-persistence-recovery-and-replay.md) resume position-compare (campaign B5/B14) — plus the optional `bindingId` above, which no V1 leg sets, because neither cut mints a provider session or thread and the run keeps the binding it had. A successful rollback without a confirmed floor is structurally inexpressible, and the daemon validates the confirmed floor **equals the requested `targetPosition` before the file leg**, after first applying the same domain validation as the request target (an invalid or no-op confirmed floor is a no-rewind failure, never an event; §Required Behavior) — a valid-but-different floor skips the restore fail-closed and ends the intervention `degraded` naming the position-mismatch disposition, with the forward event recording the confirmed position (§Required Behavior). Resolving `applied` also **quiesces the pre-rollback stream**: after `rollbackTo` resolves, the driver delivers no further run-lifecycle events from the pre-rollback execution on the run's binding — implementable without a wire token because the driver owns one serialized provider connection, so the `rollbackTo` confirmation is an in-stream fence ordering the epoch boundary against event delivery; any straggler that slips through is absorbed by §Required Behavior's execution-epoch gate, never appended.
- **Timeline presentation**: rolled-back turns are never deleted from `session_events`; projections mark them superseded (turn > post-rollback position of the accepted `run.rolled_back` event) so clients render the rewound history distinctly rather than dropping it. Late pre-epoch non-lifecycle appends carry §Required Behavior's durable epoch stamp (the `sourceEpoch` + `sourcePosition` carrier pair, [Spec-005 §Event Type Enumeration](005-session-event-taxonomy-and-audit-log.md#event-type-enumeration)), so replay ranks them with their source epoch — never by append order — and the supersede marking survives projection rebuilds.
- **Compaction-boundary anchoring (2026-08-16 amendment).** Wherever a driver's declared capabilities admit a boundary-crossing rewind at all (§Required Behavior's compaction-boundary classification), that driver's normalized-position → provider-address translation MUST anchor at the boundary's **pre-compaction** leaf, not at whatever address the post-compaction prelude chain resolves to. The failure this closes is one of ordering, not arithmetic: a provider-side compaction writes its effects — the boundary marker, the generated summary, and any caveat the provider injects — as ancestors of the invoking turn's own echo, so a translation that anchors on that echo's immediate parent lands **inside** the compaction's own prelude and hands the provider its compacted context back, while this system has already marked the boundary rewound. This spec binds the anchoring rule directly — its authority is the ordering hazard just stated, not any external implementation, and each driver's conformance is established by the ADR-017 re-verification against the then-installed provider binary that this section already owes (the first-party evidence path; the 2026-08-12 reference-runtime parity survey's first-party observation of the same hazard corroborates the shape but is not its source of authority): anchor at the last address preceding the boundary, taken **only** when every intervening address between the requested target and the boundary is a compaction-prelude address; where the chain is off-pattern, degrade to the ordinary anchor rather than guessing; and bound the ancestor walk so a malformed or cyclic chain cannot spin the translation. The daemon never re-derives a target from the driver's anchoring — the driver reports whatever floor it actually reached and §Required Behavior's confirmed-floor validation adjudicates it unchanged, so an anchoring that lands anywhere other than the accepted `targetPosition` surfaces as the ordinary position-mismatch degrade rather than as a silent divergence. Until the ADR-017 re-verification this section owes settles what each provider's rewind reconstructs across its own compaction boundary, no V1 driver declares the capability and the classification refuses every boundary-crossing target: this rule is the contract that re-verification is verifying **against**, not a claim that either wire already satisfies it.

## Implementation Notes

- Queueing and intervention logic must live in the daemon or equivalent runtime authority, not in the currently open client.
- UI affordances may be optimistic, but canonical run state changes must come from runtime truth.
- Capability-aware controls are required so unsupported operations do not masquerade as working.
- Pause is an orchestration-layer construct. The daemon stops the run after the step in flight — through the hooks it registers for the session, or a boundary interrupt where the provider has no hook for it — persists conversation history and run state to local SQLite, and queues a resume. No intervention type is minted for pause and nothing is written into the user's own configuration files.

## Pitfalls To Avoid

- Using client memory as the queue of record
- Calling reread or reattach semantics `resume`
- Treating waiting states as paused states
- Turning a message sent during a run into a second run, or holding it back until the run ends, when both V1 providers deliver it into the running run at its next step boundary
- Appending a late provider run-lifecycle event to a terminal run's timeline (the absorption rule exists precisely for this window) — or, inversely, absorbing non-lifecycle events the rule never covered (late usage telemetry is billable and must append) — or keying absorption on current run state alone, which misses pre-rollback stragglers arriving after a rollback re-opened the run (the epoch gate exists for exactly that arrival order)
- Treating rollback as log truncation — the authoritative log never truncates; rollback is a forward `run.rolled_back` event plus projection-level supersede marking
- Conflating the daemon's audit-log retention compaction with the provider's context-window compaction — they are different mechanisms with different rewind consequences, gated by different checks (the uncompacted-rewind-span check and the compaction-boundary classification respectively), and a rewind cleared by one is not thereby cleared by the other
- Reading a compaction boundary off the arrival slot of its `usage.context_compacted` row without first attempting operation association — the error direction is conservative rather than unsafe (nothing is appended before the operation it reports, so a slot-ranked boundary sits at or above the true one), which is exactly why the mistake survives testing: it never admits a crossing rewind, it silently refuses every legitimate one in the span between the compaction's originating turn and its late delivery. Reading the same conservatism the other way is the genuinely unsafe twin — concluding that because slot-ranking cannot admit a crossing target, an unresolvable row may be skipped rather than refused
- Truncating or renumbering the rendered timeline when an edit-and-resend composite is admitted or dispatched rather than when its `run.rolled_back` boundary is appended — a composite whose conversation leg never confirms applies no rewind at all, so the optimistic truncation would delete history the run still holds
- Admitting the replacement send after a degraded arm — a position-mismatch, `boundary-diverged`, or file-leg-failed settlement must suppress the resend (`resendDisposition: 'unapplied'`), never deliver the corrected message after a boundary, or into a tree, the caller did not authorize it to follow
- Comparing idempotency-key reuse bodies by ciphertext or by a persisted plaintext digest — the PII envelope is nonce-randomized, so ciphertext comparison always conflicts, and a retained digest of erased text survives crypto-shred as a guessing oracle; the only admissible comparison is decrypt-and-compare under the requester's live key, failing closed to `intervention.idempotency_conflict` when the key is shredded

## Acceptance Criteria

- [ ] A user message sent while a run is active is durable before it is delivered, is then delivered into that same run at its next step boundary on both V1 providers keeping the run id, and never becomes a second run; several such messages are delivered in the order they were sent.
- [ ] An interrupt ends the run it names and the command that run was running, spares the sidekicks that run dispatched, and delivers whatever was waiting for that run as the next turn; with nothing waiting the run rests `interrupted`.
- [ ] No restore is applied before its dry run has been answered; a files-only restore appends no rewind boundary and marks no turn superseded; and a restore that would stop sidekicks started after the point asks first, naming the count from the daemon's own run tree.
- [ ] Pause (stop after the step in flight, persist, queue a resume) and resume operate on the same run id and same run history: the same control continues the run from exactly where it stopped with nothing repeated, waiting messages are delivered on the continue, and a paused run can still be interrupted.
- [ ] Unsupported intervention requests result in explicit `degraded` or `rejected` outcomes rather than silent behavior changes.
- [ ] A provider run-lifecycle event arriving for a run already terminal never appends a `session_events` row and never advances `runVersion`: a terminal-class straggler no-ops in the at-most-once terminal emitter; a non-terminal lifecycle straggler surfaces only as the `run.late_event.absorbed` OTel diagnostic; a run-lifecycle event sourced from the pre-rollback execution epoch, arriving after a rollback re-opened the run, is absorbed identically — never appended against the new epoch; and during a pause-first rollback composite, run-lifecycle events sourced from the internally-interrupted execution — arriving after the pause, before the `rollbackTo` confirmation — are consumed or absorbed, never re-terminalizing the mid-composite run. Non-lifecycle provider events in the same window (usage telemetry foremost) still append under their own families' rules.
- [ ] A `rollback` intervention from every legal source state — `paused`, `waiting_for_approval`, `waiting_for_input`, each terminal state, and `running` via the pause-first path (guard evaluated once at admission against the pre-pause `runVersion`; every fail-closed pre-dispatch validation precedes the internal pause — a refusal leaves the run running — and the pause queues no resume event) — lands the run, **on a conversation-leg-confirmed rewind**, in `paused` at the confirmed position — `targetPosition` on the equal-floor path, the driver-confirmed floor on a position-mismatch degrade (the failure-path criterion below; the event never lies about the landing position) — with a forward `run.rolled_back` event appended (plus the `run.paused` state event for state-changing sources; in-place from `paused` emits only `run.rolled_back`; a waiting source's pending block is voided — canceled as moot — exactly on that confirmation, never before it) and prior turns marked superseded by projection, while a non-confirming outcome applies no rewind and rests each source per the failure-path criterion below (a pause-first `running` source `paused`, every other source unchanged); a stale `expectedRunVersion` produces `expired` with no leg applied, and a `targetPosition` outside the validated rewind domain (non-integer, negative, current-or-future, naming no recorded boundary, or classified boundary-crossing against the run's newest current provider-side compaction per the criterion below) is rejected pre-dispatch with no leg applied.
- [ ] Rollback leg ordering is fail-closed end to end: the conversation leg applies first and the file leg last; a file-leg failure after a confirmed conversation rollback surfaces as a `degraded` outcome naming every file it did not put back while the run still lands `paused` at `targetPosition` with `run.rolled_back` appended (state follows the confirmed conversation leg); a conversation-leg failure after the internal pause leaves the run `paused` with no auto-resume and a `degraded` outcome naming the pause-only disposition — while the same failure from a waiting or terminal source leaves the source state standing with the outcome naming nothing applied (the waiting source keeps its pending block un-voided, the terminal source stays terminal); a terminal-source rollback that does not confirm the rewind leaves the run terminal with its working folder untouched; a confirmed-floor mismatch skips the file leg fail-closed with the event recording the confirmed position; a restore that fails partway names every file it did not put back, and a fresh restore to the same point puts those back; a dispatched-but-unconcluded rollback is reconciled by position-compare at recovery — completed forward or concluded, never blindly redispatched; an invalid or no-op driver-confirmed floor is treated as no-rewind failure, never an event; post-rollback re-execution captures snapshots under the new epoch's namespace, never colliding with a superseded epoch's ordinals; late pre-epoch non-lifecycle appends carry durable epoch attribution for replay-safe supersede marking; and a run that changed no file and a run whose working folder is gone complete conversation-only with that recorded on the outcome — a rootless re-opened run refusing `run.resume` with a typed error.
- [ ] Run-control authorization is owner-only and blind to what started a run: the session's owner passes the `Action::"intervene"` adjudication against a locally-hosted run **whatever started it** — for interventions and for the orchestration-layer `run.pause` / `run.resume` identically — with `initiatorId` and the run's origin never read as authorization inputs; a denied intervention settles `rejected`, and a denied `run.pause` / `run.resume` request is rejected untouched with no run-state mutation composed (the orchestration verbs hold no `InterventionType` membership and settle no `InterventionResult`). The grant is bounded by node trust, never a substitute for it ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)'s bound): every agent executes on its owner's machine (the credentials-never-travel invariant), so a run whose agent is hosted on another node takes the remote arm below — the hosting node's own approval authority is enforced as the approval leg, not voided by the local adjudication — and a locally-hosted run is by construction a run of the caller's own node's agents, adjudicated under the node-owner user principal the daemon itself binds on its local socket ([API Payload Contracts §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model)).
- [ ] Cross-node intervention is a request, never standing authority (the remote arm): when the target run's hosting node is not the caller's local node, the same adjudication **adds** the target-node-owner approval leg — an approval in the `tool_execution` category per [Spec-022](022-cross-node-dispatch-and-approval.md) — and the request is confined to Spec-022's dispatch lifecycle, in which the intervention capability handler executes only after a signed `allow` ApprovalRecord: the target daemon composes this spec's `Action::"intervene"` adjudication into its **pre-approval** Cedar evaluation point — the same step-5 evaluation that adjudicates Spec-022's own `Action::"dispatch::<capability>"` request — so an authorization-check failure terminates as the post-receipt `dispatch.rejected` **before any owner approval prompt surfaces**, never deferred to post-approval handler execution (whose faults Spec-022 classes as `dispatch.failed`); an approver's explicit refusal terminates as `dispatch.denied`, an approval still unresolved at caller-token expiry terminates as `dispatch.expired` — on every one of these the handler never runs, no intervention state is created or settled (no `InterventionResult` exists to reach `applied` or `degraded`), and no run mutation composes, a cross-node `run.pause` / `run.resume` request identically confined (the own-node `rejected` settlement in the local arm above is [Spec-022](022-cross-node-dispatch-and-approval.md)'s own-node out-of-scope carve-out, not this arm's); a local grant alone never clears the node-owner leg, and the leg fails closed by construction wherever no approval pipeline or cross-node dispatch surface exists to grant it — including before the run-control dispatch capability itself is registered (a named [Plan-003 §Preconditions](../plans/003-queue-steer-pause-resume.md#preconditions) prerequisite): an undeclared capability is rejected at intake before target-owner approval is ever requested per Spec-022's declared-capability rule, so an unregistered handler is unreachable, and an unobtainable approval is an absent approval.
- [ ] Rewind-target validation is compaction-boundary-aware and fails closed (2026-08-16 amendment): with no current `usage.context_compacted` row for the target run, every domain-admissible target stays admissible; a target at or above the newest current boundary's originating position is admitted unchanged, the compaction row staying current and out of the rewound tail — a target **equal** to that position included, since rewinding to the compaction's own boundary keeps the compaction rather than reversing it; a target strictly below it is rejected pre-dispatch with no leg applied and a machine-readable cause persisted on the durable intervention row, on the Codex and Claude legs identically, unless the target run's driver declares re-verified boundary-crossing rewind semantics; a current compaction row that resolves to no originating position at all — no stamp, no operation linkage, and no recoverable timeline slot, the shape a retention audit stub leaves behind — rejects **every** target of that run rather than being silently skipped; a compaction row already marked superseded by an earlier accepted rewind never gates a later one; and where a driver does declare the capability, its position translation anchors at the boundary's pre-compaction leaf only when every intervening address is a compaction-prelude address, degrading to the ordinary anchor off-pattern, bounded against a cyclic ancestor chain, with any resulting floor difference surfacing as the ordinary position-mismatch degrade rather than a silent divergence; the confirmed floor is reclassified at settlement against the then-current boundary set, a crossing conclusion settling `degraded` naming `boundary-diverged` — file leg skipped fail-closed, any staged replacement suppressed, run `paused` at the confirmed floor with the divergence cause persisted on the durable row; and `run.resume` refuses fail-closed, with a typed error, a run whose current position sits strictly below its newest current boundary (the post-settlement straggler backstop, making a boundary-diverged run non-resumable in V1 exactly like the rootless class).
- [ ] Atomic edit-and-resend is one intervention and preserves the caller's text in all three failure arms (2026-08-16 amendment): the composite rides the existing `rollback` intervention carrying `replacementSend` — one durable row, one `clientIdempotencyKey`, one `expectedRunVersion` guard, minting no new intervention type, wire method, event type, error code, or table (the `run.compaction_boundary_diverged` refusal is the compaction leg's shared resume backstop, not the composite's) — and is refused pre-dispatch, whole and with no leg applied, against a run holding a pending send — an accepted send not yet delivery-confirmed or an undrained queued send admitted before the composite — against a `targetPosition` whose boundary was not opened by a user-authored `user.message` of that run (bare rollback of such a boundary staying admissible), and against a non-resumable rootless target — a run whose execution context is released with no existing root, or whose execution context — live or already released — records a checkout root no longer on disk (a live one the confirmed rollback releases into that class; a terminal-source one arrives in it), where the promised next-resume delivery can never occur, while bare rollback of it stays admissible conversation-only; a fully-successful rewind (confirmed floor equal to the target, boundary-clear at settlement reclassification, file leg complete or legitimately conversation-only) **admits** the corrected message as a queue item **bound to the rewound run** (`queue_items.target_run_id` stamped at admission) in the same durable transaction that settles the intervention — the run still landing `paused` at the confirmed position with no auto-resume and no second driver-facing call, the item delivering into its bound run as that run's next provider send on `run.resume` (the pending-send guard having emptied the queue of older sends at admission), the drained turn executing under the admitting intervention caller's effective principal per [Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)'s extended rule — while a confirmed rewind whose replacement is suppressed or fails admission settles `degraded` carrying `resendDisposition: 'unapplied'` — **required** on the `resend-unapplied` arm, whose own shape identifies its request as composite, and which, where it displaces a completed file restore rather than following a skipped or refused one, reports that restore's own files put back and files skipped under the same never-silent contract a completed restore holds — both empty on the conversation-only branch, which ran no file leg and displaces nothing — naming `resend-unapplied` exactly when admission itself failed after a fully-successful rewind and the earlier-failing leg's disposition otherwise, with the run `paused` at the confirmed position and `run.rolled_back` appended; a dispatched-but-unconcluded composite reconciled at target drives the staged replacement send forward among its remaining legs rather than stranding it — admitting and settling in that same single transaction, so an unconcluded intervention proves no admission occurred and recovery never double-admits — and a replay of the same `clientIdempotencyKey` returns the recorded outcome rather than sending twice, with reuse adjudicated by decrypt-and-compare under the requester's live user key (an undecryptable stored body settling the reuse fail-closed as `intervention.idempotency_conflict`); the replacement text rides the user-keyed PII envelope on the durable intervention row (`interventions.pii_payload`, never plaintext `payload`) and is recoverable under the requester's key in every arm that reaches intervention creation (the cross-node pre-approval refusal creates no intervention state, and the caller-side surface that authored the text remains its holder); a refusal raised by any of the three structural guards names **which** guard refused on the closed-union `rejectionGuard` member of the `rejected` response — arm-scoped, schema-optional, producer-obligated, absent on every one of the **six** other refusal families a rollback reaches — beside the unchanged machine-readable `rejectionReason` (2026-09-06 amendment), so a per-guard remedy is rendered by an exhaustive switch over a closed union and never by a match against that sibling's contract-unenumerated cause vocabulary, the literal persisting on the intervention row (`interventions.rejection_guard`, vocabulary-closed and arm-bound by its `CHECK`) so that an idempotent replay of the same `clientIdempotencyKey` returns a `rejectionGuard` equal to the recorded one **across a daemon restart**, never omitted and never re-derived by re-evaluating the guards against a run that has since moved on; and superseded marking applies **solely** on the accepted `run.rolled_back` boundary — never on the composite's admission, its dispatch, or its replacement send — with the resend appending after the boundary in session append order, so no linkage field on either row is required to render the pair.

## Resolved Questions and V1 Scope Decisions

- One measurement is open and it blocks nothing: on Codex, whether `thread/revert` can be issued while a turn is still running, and in what order the interrupt and the revert must go, was not measured mid-turn (§Driver-Level Rollback Mechanics). The Claude leg raises no such question — its conversation-cut request carries an interrupt-if-running flag, so the cut ends the live turn itself. Until that measurement lands the Codex leg reaches a `running` source through the pause-first sub-step §Required Behavior already specifies for every rollback, which puts the interrupt ahead of the cut, so nothing waits on the answer.
- V1 decision: **a user reorders their own waiting messages, and what stays deferred is a priority attribute on the admission queue.** A message sent into a running turn waits as a row at the end of the transcript, and on hover or keyboard focus that row offers a grip that drags it — or the up and down arrows with the row focused — to move it in the stack, beside editing it back into the draft, removing it so nothing reaches the sidekick, and sending it now, which interrupts the turn, delivers that row first and lets the rest follow in order. Each driver realizes the move differently, because each holds the waiting message somewhere different: on the Claude driver the message has already gone to the provider, which holds it to the next tool boundary, so a reorder is a cancel of those rows and a resend in the new order; on the Codex driver the daemon holds the message itself and steers it at the tool boundary, so the order is the daemon's own right up to the moment it goes. Either way this is the **send order of one user's own waiting messages on one run**, applied by the driver at the next step boundary — not a priority attribute on the admission queue, which stays deferred: nothing ranks one run's or one channel's work ahead of another's, and admission itself stays canonical queue order. The first implementation uses canonical queue order plus explicit steer, pause, resume, interrupt, cancel, and — per the 2026-07-13 campaign B2 amendment (§Required Behavior) — rollback controls only (`cancel` restored to this enumeration 2026-09-01: it has been an `InterventionType` member since Tier 1 and was omitted here by erratum, which is why downstream text counted the set at five and called a would-be addition a "sixth"; the set is closed by enumeration, not by count). The 2026-08-16 amendment's edit-and-resend does **not** widen that set: it is an optional leg on the `rollback` control, adding no new control, and its compaction-boundary sibling narrows which rollback targets are admissible rather than adding a surface. The 2026-08-26 same-agent provider switch does not widen it either: `agent.configUpdate`'s `interruptAndSwitch` flag dispatches the **existing** `interrupt` intervention rather than minting a control, on the 2026-08-18 edit-affordance precedent ([Spec-014 §Same-Agent Provider Switch](014-multi-agent-channels-and-orchestration.md#same-agent-provider-switch), D-014-26).
