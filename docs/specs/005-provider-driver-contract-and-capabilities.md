## Purpose

Define the normalized driver boundary between the core runtime and provider-specific execution transports.

## Scope

This spec covers required driver operations, capability advertisement, normalized event shapes, and runtime binding persistence.

## Non-Goals

- UI behavior for every capability
- Provider-specific prompt tuning
- Provider commercial or billing concerns — **narrowed 2026-08-18.** Pricing, plan selection, invoicing, and what a provider charges remain out of scope. Two adjacent facts are **in** scope, because both are driver-contract surfaces rather than commercial ones: the typed provider usage-limit signal (§Fallback Behavior), which is a pacing fact the runtime must act on rather than a billing figure, and the provider-account identity a run is spawned against (§Interfaces And Contracts), which selects a credential environment. Neither carries a price, a rate, or an amount owed. What is spent and what it cost belong to `Spec-016 §Session Cost Receipt`; which account paid and under which billing mode belong to `Spec-029 §Billing mode`.

## Required Behavior

- Every provider integration must implement a normalized driver contract.
- Provider drivers must execute within a participant-owned or operator-owned runtime node governed by a local daemon. V1 must not depend on a shared hosted driver service as the execution authority.
- The driver contract must support create session, resume session, start run, interrupt run, `applyIntervention`, respond to interactive request, close session, and enumerate models or modes or both where available.
- The `applyIntervention` operation is a generic dispatcher that routes intervention requests (steer, interrupt, cancel) to the appropriate driver-specific handler based on the intervention type and the driver's declared capabilities. `cancel` maps to the `interrupted` terminal state in the run state machine — it is a user-initiated interruption. Drivers that do not support a given intervention type must return a `degraded` result, allowing the orchestration layer to fall back (e.g., steer degrades to queue + interrupt for providers without native steer support). The driver-level result vocabulary is exactly `applied | degraded`; `rejected` and `expired` are orchestration-layer verdicts rendered by the daemon's authorization and version-guard checks around driver dispatch and are never returned by a driver — the normative mapping onto the six-state intervention lifecycle lives in [Queue And Intervention Model §Driver Result To Lifecycle Mapping](../domain/queue-and-intervention-model.md#driver-result-to-lifecycle-mapping).
- The contract additionally defines capability-gated parity operations — `rollbackTo` (conversation rollback to a normalized session position on the run's live provider binding; gated on the `rollback` flag) and `setSessionGoal` / `clearSessionGoal` (session-goal injection; gated on `session_goals`) — plus a zero-turn `probeAuth` required of every driver: provider authentication state must be knowable without spending a billed turn. Dispatch of a capability-gated parity operation follows the same static/dynamic split as interventions ([Queue And Intervention Model](../domain/queue-and-intervention-model.md)): a call against a flag the driver does not declare is refused statically with `driver.capability_unsupported` before driver dispatch (these direct operations have no documented orchestration fallback), while `degraded` is the dynamic outcome of an invoked driver that could not deliver the operation natively and reports the fallback it took — never an opaque failure.
- Every intervention request carries a mandatory requester-generated `clientIdempotencyKey` (UUID) — generated by the participant client, or by the daemon’s origination path for system interventions (orchestration budget / idle / moderation interrupts per ADR-011), which reuses its synthesized key across its own retry loop. The daemon applies replay-or-conflict semantics — an identical retry returns the originally recorded outcome without re-dispatching the driver; reuse of a key with a differing payload is rejected as `intervention.idempotency_conflict` — following the converging idempotency-key practice ([Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests); the expired IETF draft [draft-ietf-httpapi-idempotency-key-header](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)). The key rides through `ApplyInterventionParams` so drivers can propagate it to provider-remote invocations that honor dedupe keys (the `compensable` pattern, §Tool Metadata).
- Every `getCapabilities` report must include `cliVersion` — a `DriverCliVersionReport` carrying the verbatim provider-reported version string (`raw`) and its parsed semantic version (`semver`). The daemon enforces a per-driver minimum-version floor mechanically at attach and refresh (semantic-version comparison against the configured floor; V1 shipped floors: Claude Code `2.1.198`, codex-cli `0.141.0` — the 2026-07-02 CLI-currency audit pair). An unparseable version report fails closed: the report cannot be constructed (`semver` is required, so unparsed-but-attached state is unrepresentable), the driver refuses attach, and the failure surfaces as `driver.cli_version_unparseable`. A version that parses cleanly but sits below the configured floor likewise refuses attach/refresh fail-closed, surfacing as `driver.cli_version_below_floor` (distinct from `version.floor_exceeded`, which governs client/event-envelope contract floors, not provider CLI installs).
- Every driver must implement `probeAuth` — a zero-turn authentication probe returning `DriverAuthProbeResult` (`authenticated | unauthenticated | indeterminate`). `indeterminate` (probe surface unavailable or unparseable) is treated as not authenticated for admission — fail closed — while remaining distinguishable so operators can separate probe health from credential state. Run admission against a driver that does not probe `authenticated` is refused as `driver.not_authenticated` before any turn is spent.
- The Codex driver must pin `approvalsReviewer: "user"` at session spawn so every approval routes through the daemon's approval pipeline ([Spec-012](012-approvals-permissions-and-trust-boundaries.md)); provider-side guardian / auto-review auto-adjudication is disabled by contract. The generated protocol's own default is already `user`, so the pin is defense-in-depth against a config/profile override — and guardian / auto-approval notifications normalize as observability rows, never as approval decisions.
- Spawn/turn parameters carry the parity surfaces: a session callback-tool registry (`SessionCallbackTool[]` — the daemon exposes a curated tool set into every run; Codex leg `dynamicTools` + the `item/tool/call` server request, Claude leg a daemon-hosted ephemeral MCP server via `--mcp-config`; every callback invocation flows through the daemon's approval pipeline per [Spec-012](012-approvals-permissions-and-trust-boundaries.md) and lands as ordinary `tool_activity` rows per [Spec-006](006-session-event-taxonomy-and-audit-log.md)), a `subagentPolicy { enabled, maxDepth, maxConcurrent, definitions[] }` pass-through under the single-supervisor invariant (the daemon is the only cross-session supervisor; orchestration semantics land in Spec-016 via campaign B6), and the run's `executionPosture` (shape owned by this spec and typed in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md); authorization and policy semantics in [Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior), campaign B20).
- Drivers must emit normalized runtime events rather than leaking provider-native event types into the session engine.
- Drivers must declare capability flags for at least `resume`, `steer`, `interactive_requests`, `mcp`, `tool_calls`, `reasoning_stream`, `model_mutation`, `structured_output`, `rollback`, `session_goals`, `callback_tools`, `subagents`, and `cost_cap`. A flag declares that the driver delivers the capability through its own mechanism at the driver boundary — natively or driver-emulated; **how** it delivers is recorded as a mechanism grade on the parity capability matrix (a capability delivered by the orchestration layer above the driver, like steer-for-Claude, keeps its driver flag `false`). The `pause` flag is intentionally excluded — no current provider implements native pause. Pause is an orchestration-layer construct (interrupt run, persist state, queue resume) that does not require driver support.
- Drivers must persist provider-owned resume handles separately from canonical session and run ids.
- The runtime must treat undeclared capabilities as unsupported.
- Drivers must declare a per-tool `idempotency_class ∈ {idempotent, compensable, manual_reconcile_only}` alongside their tool list. This metadata controls crash-recovery behavior for in-flight side-effecting tool calls; see [Spec-015 § Idempotency Protocol](015-persistence-recovery-and-replay.md#idempotency-protocol) for recovery semantics.
- **Provider-bound participant text reaches the model as prose, or the turn fails visibly (2026-08-25).** Text a participant authored — a run's opening content, a steer directive's content, and admitted queue content re-entering through run start — is data _for the model_, never an instruction to the provider's own client. Where a provider's programmatic input surface also parses client-side commands, a message whose first word is command-shaped is consumed by that parser and the participant's words never reach the model; the observed failure is silent, returning a zero-turn success rather than an error (Claude Code `2.1.245`, verified 2026-08-25). Every driver must therefore route provider-bound text through a single **outbound frame boundary**, and a driver whose provider command-parses that surface must neutralize command-shaped participant text there so the provider parses it as prose. The boundary and the tripwire below are **universal**; the transform itself is **grade-scoped** to the drivers whose mechanism grade requires it (§Parity Capability Mechanism Grades). A driver graded `native` on that row passes the author's bytes through unchanged — prepending a sentinel a provider does not need would alter text it would otherwise have delivered exactly. Because the grade is the behavioral input here rather than a bare record, **that row states the grade governing today, never the one a provider is expected to earn**: a `native` claim resting on any frontend other than the transport the driver actually drives is recorded `emulated` until a probe of that transport confirms it, and the confirming re-grade is an ordinary amendment. The default is therefore the transform and not its absence, because a spare newline on a prompt costs nothing and a skipped one costs the whole message. And the grade is a claim the tripwire keeps honest rather than one that is trusted: a `native` driver whose provider starts command-dispatching after an update trips exactly as an `emulated` one does, and the remedy is re-grading it, not discovering the loss from a user. **Command-shaped** is one predicate with one implementation shared by every driver, so two drivers can never classify the same message differently: the frame's first non-whitespace byte is `/` (`0x2F`), where **whitespace is exactly the six ASCII bytes** `0x09` (tab), `0x0A` (line feed), `0x0B` (vertical tab), `0x0C` (form feed), `0x0D` (carriage return), and `0x20` (space) — skipped from the frame's first byte until the first byte that is not one of them, which decides. Enumerating that set is load-bearing rather than pedantic: _whitespace_ is the one term in this predicate two drivers could read differently, and a byte-level rule may not appeal to a Unicode property without the decoding this rule forbids. A frame led by a non-ASCII whitespace character — a UTF-8 no-break space, say — is therefore **not** command-shaped here, and that residual is left to the tripwire deliberately rather than closed by guessing at a wider set: should a provider ever be observed trimming such bytes before its own command parse, the trip is loud, the turn fails visibly, and the remedy is widening this enumeration by amendment against an observation — where widening it today would trade a named residual for an unnamed one. It is deliberately that coarse. It is byte-level and locale-independent — it never decodes, normalizes, or case-folds — and it consults no list of known command names, because an unknown name is precisely the case that fails silently. It draws no distinction a provider might not draw: `/foo`, `/foo:bar` (the plugin-qualified command form), and the path-like `/etc/hosts` are all command-shaped, because the only cost of neutralizing prose is one invisible byte on the wire while the cost of missing a command is the whole message. A slash anywhere but the first non-whitespace position is not command-shaped. Neutralization is **transport-only**: it changes only the bytes on the provider wire, never the canonical text this repo persists, events, replays, rewinds to, or shows a participant, so an audit row and a rollback target carry exactly what the author typed. This is a **delivery-correctness** rule, not the provider-specific prompt tuning §Non-Goals excludes: the transform changes no word the author wrote, and it applies only where the alternative is the message not arriving at all. The V1 sentinel is a single leading newline — the smallest edit that defeats the parse. Should a provider build ever parse through it, the escalation ladder is ordered by decreasing invisibility and increasing honesty: leading newline → leading space → structural repositioning of the command-shaped word → a visible, documented prefix → a typed refusal. A driver never silently drops the message, and a driver that exhausts the ladder grades this capability `absent` and refuses command-shaped participant text loudly rather than delivering it mangled. Reaching a provider's own command surface _deliberately_ is a separate concern this spec does not open: the composer-level escape is [Spec-017](017-workflow-authoring-and-execution.md)'s C-18, which activates on provider-bound composer paths once this neutralization ships.
- **Neutralization is decided by a closed frame origin, and an unknown origin neutralizes (2026-08-25).** Every outbound provider frame declares exactly one origin — `participant_text` (neutralized), `driver_command` (a command the _driver itself_ composed from a typed daemon intent, routed verbatim and exempt from the tripwire below so the provider's own command surface stays reachable), or `system_narration` (daemon-composed prose, neutralized). An absent or unrecognized origin **neutralizes**: a frame nobody classified is far likelier to be participant text than a driver command, and neutralizing a command wrongly costs a visible no-op where skipping neutralization wrongly costs a silently swallowed turn. The discriminator is deliberately **not** a capability flag — an undeclared flag resolves through this section's undeclared-is-unsupported rule to "not neutralized", which is the fail-open polarity. V1 emits no `driver_command` frame: **no** capability this spec grades `emulated` for Claude is delivered through the provider's own command surface. The predicate is stated negatively on purpose — enumerating the delivery mechanisms in that set would oblige a re-derivation every time a row joins the table, and this amendment's own new row would already have falsified one. The arm exists so that a later capability leg realized through a provider's own command surface (`model_mutation` is the plausible first) has a declared route instead of an exemption cut into the neutralizer after the fact. `system_narration` — daemon-composed prose on the same channel — has nil V1 traffic for its own reasons, audited rather than assumed: the goal composition this spec grades `emulated` for Claude reaches the provider through system-prompt composition rather than through this boundary, and `respondToRequest` delivers a structured reply correlated to a `requestId` rather than a turn on the text-input channel. It is kept distinct from `participant_text` even though the two neutralize identically, because when the tripwire fires the frame record must say _whose_ words failed to arrive — a policy-composed answer ever delivered as text would otherwise be filed as the participant's.
- **The neutralizer's effect is verified at runtime, not assumed (2026-08-25).** A transform is a claim about a provider parser the daemon neither owns nor pins, and a provider update can change that parser between two runs of the same install. Each outbound frame therefore carries a daemon-minted correlation value, and the driver classifies the provider's response to that frame. **The classification asks for positive evidence of a model turn, never for a recognizable command dispatch.** The set of shapes in which a provider can say _I handled that as my own command_ is open, undocumented at the versions this repo pins, and free to grow with the next release, so a detector that enumerates it is stale on arrival and fails open — silently, in exactly the shape this rule exists to end. The set of shapes that evidence a model turn is closed, small, and already parsed by the normalizer to do its ordinary work. The burden is therefore inverted: a correlated frame that **settles** with no typed event attributing model output to it has tripped, whatever the provider called what it did instead. The classifier reads **typed fields of the provider's own response envelope** and never message prose, which §Pitfalls To Avoid forbids for the same localization and wording-drift reasons it forbids text-matched quota refusals; a response envelope whose shape the driver does not recognize therefore trips rather than passing, and a driver that would rather not trip on an unrecognized shape pins the turn-evidence discriminants for its provider instead of relaxing that polarity. Which typed fields those are is per-provider implementation work the driver records and re-probes, not a set this spec can enumerate: the pinned provider-wire references document no such discriminant at the versions this rule was authored against. One dispatch shape **is** named normatively, as the rule's conformance instance rather than as its definition — the **zero-turn synthetic reply**: a settled correlated frame whose response envelope carries a client-composed reply item, no model-turn attribution for that frame, and no token usage accounted to it. That is the shape observed first-party on Claude Code `2.1.245`, and the recorded transcript of it is [Plan-005](../plans/005-provider-driver-contract-and-capabilities.md) T3.18's **conformance fixture** — every driver's classifier must trip on it. Naming it does not narrow the rule to it: a frame that settles in any other shape without turn evidence trips just the same, so the fixture proves the detector present without becoming the enumeration this rule refuses to build. **A trip fails the run, and there is one landing for both paths.** The daemon emits the run's ordinary `run.failed` terminal carrying `failureCategory: 'provider failure'`, a `recoveryCondition` of `recovery-needed`, and a `providerFailureDetail` in **one fixed daemon-composed form**: the registered `driver.text_neutralization_failed` ([Error Contracts](../architecture/contracts/error-contracts.md)), one space byte (`0x20`), then `origin=` followed by one of `participant_text`, `system_narration`, or `unknown` — so `driver.text_neutralization_failed origin=participant_text` is the entire detail. Writing the form down is what makes _machine-readable_ true rather than claimed: a consumer reads the cause as the substring before the first space and the origin as the substring after `origin=`, and an origin the closed union does not name is recorded as the literal `unknown` rather than echoed, which keeps a string the daemon did not compose out of the audit log. `driver_command` can never appear, those frames being exempt. The form binds **this cause only** — `providerFailureDetail` stays free-form prose for the resume failure that introduced it ([API Payload Contracts](../architecture/contracts/api-payload-contracts.md)). That is the handoff §Fallback Behavior's resume failure already uses — a typed driver-side condition surfaced on the canonical run-lifecycle surface where consumers already subscribe — so the trip mints no driver event, no new result **status**, and no persisted column. It mints no state transition either: `starting -> failed` and `running -> failed` are both already declared ([Run State Machine §Complete Transition Table](../domain/run-state-machine.md#complete-transition-table)), and those are exactly the two states a provider-bound frame can be in flight in — a run's opening frame can settle before the `starting -> running` transition is recorded, and a steer targets a `running` run by definition. It is emphatically **not** a JSON-RPC error on either path, and the run-start path is the reason the landing had to be asynchronous at all: `startRun` is a daemon-internal lifecycle operation with no wire method behind it, and a run reaching it from the queue or from orchestration has **no caller waiting on a response** — the participant who authored the text may be offline, and a system-originated run has no participant at all. A synchronous refusal has nobody to refuse to. The run's own `run.failed` event is therefore the surface, delivered to whoever is subscribed whenever they subscribe, which is what an asynchronous run outcome means here. An intervention does have a caller, so it answers on its own result branch as well. That intervention settles `degraded` on the existing zero-effect arm — the frame was dispatched, which puts pre-dispatch `rejected` definitionally out of reach ([Queue And Intervention Model §Driver Result To Lifecycle Mapping](../domain/queue-and-intervention-model.md#driver-result-to-lifecycle-mapping)) — with no `fallbackAction`, because no fallback exists: re-sending the same text meets the same parser. It carries the cause **on that response**, through one additive-optional member the driver result envelope gains here: `refusalCode`, a **closed literal union** whose sole V1 member is `driver.text_neutralization_failed`. A closed union rather than a free-form string is the load-bearing choice — the envelope parses untrusted provider output, and a code the daemon selects from a fixed set can never smuggle provider-composed text into an audit record, so this member needs no length bounding and adds no free-form surface. The `status` vocabulary is untouched at `applied | degraded`, the envelope keeps `.strict()` — a **declared** optional key is not an unknown one, which is the only thing strictness rejects — and the daemon's intervention-result mapper reads it onto the caller's response. The member is **best-effort by construction, and the run terminal is the guarantee**: `refusalCode` is present only when the trip is classified before `applyIntervention` resolves. A driver must not hold that call open waiting for its correlated frame to settle — a healthy steer joins a model turn and settles when that turn ends, which can be minutes, so awaiting settlement would convert every ordinary intervention into a long poll and would make the neutralizer's own verification the slowest thing on the intervention path. The asymmetry is what makes the member worth having anyway: the tripped case is the fast one — a zero-turn synthetic reply settles immediately, well inside the call — so the classification is in hand exactly when there is something to report. A consumer that must not miss a trip subscribes to the run: `run.failed` is the surface on both paths and the only one a consumer may depend on, and no reader may treat an absent `refusalCode` as evidence that no trip occurred. Recording the cause twice, on the response and on the run terminal, is deliberate: the caller of a one-shot intervention should not have to subscribe to a run's event stream to learn why its text was not delivered, and the terminal is what a later reader replays. **A tripped intervention fails the run too, and that is worth arguing for, because the opposite reads as the kinder choice.** The tempting argument is that a misfired steer touched nothing, so failing the run destroys work the misfire never harmed — but the hazard is precisely that the provider _dispatched_ the frame, so it may have executed an unrecognized client-side action against the session state the run depends on, and a context clear or a model switch would leave every later turn running against a session this daemon still believes it understands. `recovery-needed` names that exactly: a human reconciles before the run continues. **The provider binding is quarantined with it.** Failing the run alone would not be enough — the run ends, but the provider process holding the possibly-mutated client-side state stays alive, and the next run admitted against that session would bind straight back to it. So the trip also **disposes the run's live provider binding**: the driver closes the provider session and the binding row is retired, an attach against a retired binding is refused with the same registered code, and returning to work means a fresh spawn — which is exactly what _operator restarts the session_ means mechanically. Disposal strands no ratified path. The one exit from a terminal state is a rollback intervention (`failed -> paused`), and that path never re-enters the binding it left: the terminal exit has already released the run's execution root, a terminal-source rollback re-acquires the root, and the run's live binding is repointed through `DriverRollbackResult.applied.bindingId` — the fork-composed arm that exists precisely because a rollback may return to a binding other than the one the run died on ([Run State Machine §Rollback Transitions](../domain/run-state-machine.md#rollback-transitions-campaign-b2)). A retired binding is the thing that must not be re-entered, and nothing ratified re-enters it. Disposal rather than a quarantine flag is the deliberate shape: this plan already rules that recovery state does not live on `runtime_bindings` (the `recovery_state` / `recovery_needed` prohibition), and a process that no longer exists cannot be re-bound by a caller that forgets to read a flag. The driver-level **status** vocabulary stays exactly `applied | degraded`; the one widening this rule makes anywhere on the driver contract is the additive-optional `refusalCode` member above, which no existing caller is required to read and which changes no shipped field's type. Frames of origin `driver_command` are exempt, a command dispatch being their intended outcome. A provider spawn flag claiming to disable command parsing may be set as defense in depth but never in place of the transform or the tripwire — it is the provider's promise rather than the daemon's guarantee, and in `2.1.245` the nearest such flag is described by the binary's own help as disabling skills, a scope that is not the input parse.

## Default Behavior

- Driver capability declarations are required at attach time and may be refreshed when provider state changes.
- Initial provider drivers are local-runtime-node integrations. They may call remote provider APIs or services, but driver control and execution authority remain attached to the local runtime node.
- Driver transport defaults to `stdio`. The Codex driver may additionally be configured — config-gated, off by default — to attach over `unix://` or `ws://` app-server listeners with bearer auth (`DriverTransportConfig`; the credential is held as a daemon-config reference, never inline). The Claude CLI exposes no local listener; remote Claude participation is cross-node dispatch per [Spec-024](024-cross-node-dispatch-and-approval.md) — recorded as the parity mechanism, not a driver transport.
- Unknown capability fields are ignored (tolerant reader). The declared `contractVersion` is a change-detection signal — the daemon records it at attach and compares it on refresh to detect contract drift and invalidate capability snapshots — not a negotiation surface: the daemon never version-gates its behavior on it, and additive contract evolution with tolerant reading replaces negotiated feature-unlocking.
- The runtime must only surface controls that correspond to supported capabilities for the active run.

## Fallback Behavior

- If a driver cannot resume a previously persisted handle, it must surface `provider failure` detail and a visible `recovery-needed` condition; it must not silently create a replacement provider session under the same canonical run. Recovery conditions form the closed `RecoveryCondition` set — `recovery-needed` (generic: operator reconciliation required) and `reauth-required` (the provider session or credential expired: detected mid-run via the provider's typed auth-failure signals or at resume/probe time; remediation is re-authenticating the provider CLI on the runtime node, after which recovery may retry). The named type is declared once in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) and referenced at every carrying surface.
- **Provider usage limits are a sibling axis, not a recovery condition (2026-08-18).** When a provider refuses or defers a turn because the bound account's plan allowance is exhausted, the driver surfaces a typed **provider usage-limit signal**, distinct from `RecoveryCondition` and never folded into it: a `recovery-needed` condition asks a human to reconcile, whereas a usage limit resolves on its own at a known boundary and asks the runtime to wait. The signal carries a **closed-set cause** and an **optional reset boundary**; the boundary carries its own provenance, distinguishing a value the provider stated from one the runtime derived, because a derived boundary may be wrong and a consumer that cannot tell will present a guess as a fact. Recognition is **typed-only**: a driver emits the signal solely from a structured provider event whose shape it can name, and MUST NOT infer a usage limit by matching message text, exit codes, or HTTP status alone. An unrecognized or unparseable shape yields **no signal** — the honest absence — rather than a synthesized one; a consumer reads that as "not known to be limited", never as "known not to be limited". A driver that cannot observe usage limits at all declares nothing here and is not emulated: this is the parity triad's degrade-honestly arm, and the pacing consumer's behavior without a signal is unchanged from today's.
- On successful resume the driver reports `sessionPosition` — its normalized monotonic position (turn/event ordinal) for the resumed provider session. The daemon compares it against the recorded position; reconciliation semantics (divergence halts for human decision) are Spec-015's, landing via campaign B5 per [ADR-017](../decisions/017-shared-event-sourcing-scope.md)'s local-log-authoritative ruling. A provider that silently returns a fresh session on resume (for example on a working-directory mismatch) is caught by this comparison rather than silently adopted.
- If a provider offers provider-native data that cannot be normalized safely, the runtime must store it as diagnostic metadata only, not as canonical domain state.
- If a driver does not support dynamic model or mode mutation, the runtime must require a new run or agent configuration rather than simulating mutation.
- If a requested integration path would require shared hosted execution outside the local runtime boundary, v1 must reject or mark that path unsupported rather than routing execution through the collaboration control plane.

The `status` union is unchanged, the envelope stays `.strict()`, and every existing caller keeps working without reading it.

  - `closeSession`
  - `listModels`
  - `listModes`
  - `getCapabilities`
  - `probeAuth` — zero-turn authentication probe (required of every driver)
- Required normalized event families:
  - run lifecycle
  - assistant output
  - tool activity
  - interactive request
  - artifact publication
  - usage or quota telemetry where available
- Normalization obligations bind at the driver's normalize boundary: usage/quota telemetry is provenance-stamped by the driver — it sets `windowSource` (`provider_reported | model_default | estimated`) and computes the `exceeded` headroom predicate at normalization ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — never deferring provenance or the derived predicate to consumers.
- **Provider-account identity is an additive-optional spawn input (2026-08-18).** Session-creation and resume parameters carry an **optional** provider-account identifier. Omitting it is a supported, unchanged path: the daemon resolves the provider's default account, and a caller written before this amendment behaves exactly as it did. The identifier is **opaque to the driver** — it selects a credential environment and is never parsed, decomposed, or used to locate credential material by the driver itself. The daemon constructs that environment and hands it to the spawn; a driver MUST NOT read ambient provider credentials from the operator's own environment or home directory when an account is bound, because doing so would silently execute against a different account than the one the run was admitted for, and the resulting spend would be attributed to an account that never paid it. The identifier is **server-resolved and server-stamped**: a client-supplied value is an input to resolution, never the recorded outcome. Resume rebinds to the account the run was originally admitted against rather than re-resolving the current default, so a default changed mid-session cannot silently move an in-flight run's billing. Registration, defaults, credential-home layout, validation, and concurrency posture are Spec-029's; this bullet is the whole of the driver-facing seam.

For each `false` in the matrix:

## Tool Metadata

Driver capabilities describe what the driver supports as a whole (e.g., `resume`, `steer`). Driver **tool metadata** is per-tool information the driver exposes for each tool in its catalog. The canonical V1 per-tool metadata field is `idempotency_class`, used by the daemon's two-phase command-receipt protocol during crash recovery.

### `idempotency_class`

| Value | Meaning |
| --- | --- |
| `idempotent` | Safe to re-execute on recovery. Either a pure read (`file.read`, `shell.stat`) or a write whose external target is server-side idempotent (for example `S3 PutObject` with `If-Match`). |
| `compensable` | Re-executable only when paired with a caller-supplied `dedupe_key` that the remote side honors (for example [Stripe idempotency keys](https://docs.stripe.com/api/idempotent_requests)). The driver is responsible for propagating `dedupe_key` to the remote invocation so that a duplicate request is rejected or treated as a no-op. |
| `manual_reconcile_only` | **Not** safe to re-execute automatically. Recovery halts the run with a `recovery-needed` condition (see §Fallback Behavior) and requires operator reconciliation. Two deterministic carve-outs — persisted MCP task-handle resolution and provably-never-dispatched auto-retry — are defined in the MCP floor paragraph below; every other receipt in this class halts. |

If a driver does not declare `idempotency_class` for a tool, the runtime MUST treat it as `manual_reconcile_only`. This is the conservative default and matches the existing rule that the runtime treats undeclared capabilities as unsupported.

An MCP-discovered tool is **always** `manual_reconcile_only`. The runtime MUST NOT derive `idempotency_class` from MCP `ToolAnnotations`: the MCP specification's current revision binds clients to treat tool annotations as untrusted unless they come from trusted servers ([MCP 2025-11-25 Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), MUST-strength) — and the MUST binds trust classification, not behavior derivation, so classes bind on the operator-managed assignment surface, never on annotation self-claims. The only upgrade path is the operator-governed assignment (MCP governance, [ADR-015](../decisions/015-v1-feature-scope-definition.md) feature #18 — governed by [Spec-028](./028-mcp-server-configuration-and-governance.md) §Tool-Level Overrides, landed 2026-07-22 via the campaign's B18 bundle: Cedar-gated, trusted-server-only, always audited). The consequence is stated outright: a `manual_reconcile_only` tool in flight at daemon crash halts the run's recovery with a `recovery-needed` condition, and the halted run blocks its co-participants' dependent work in that session until an operator reconciles. Two deterministic carve-outs (Part-B fail-closed follow-up, 2026-07-17) refine that recovery dispatch without weakening the floor — the trust rule is untouched, and a class still never derives from annotations. **(a) Durable task handle**: where the call was dispatched task-augmented under the experimental [MCP 2025-11-25 Tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks) utility and the receipt durably recorded the receiver-generated `taskId` from the task acceptance response (`CreateTaskResult` — the id exists only once the receiver accepts, so a crash before that response is durably stored leaves no handle and stays on the sent-but-unacked halt below), recovery resolves the receipt deterministically instead of halting: poll `tasks/get` to a terminal status (`completed | failed | cancelled`), then read the recorded outcome via `tasks/result` — the Tasks spec binds `tasks/result` to return exactly what the underlying request would have returned, so this is result retrieval, never re-execution; a task observed in `input_required` breaks the deterministic-resolution premise (it awaits interaction the recovery sweep cannot supply) and falls back to the floor's halt with the handle preserved for operator resolution, and a purged or expired task (receivers MAY delete after `ttl`) falls back the same way; retry-on-transient-poll-failure stays out of V1 while the utility is experimental upstream. **(b) Provably never dispatched**: a receipt whose send demonstrably never reached the remote side — connection refused, DNS resolution failure, or a recorded pre-send abort — is safe to auto-retry regardless of class: nothing executed, so there is nothing to reconcile. The sent-but-unacked window stays on the floor's halt — ambiguity is operator-owned. Recovery-side dispatch mirrors in [Spec-015 § Idempotency Protocol](015-persistence-recovery-and-replay.md#idempotency-protocol).

### Recovery Consequences

Recovery behavior for a receipt that was in-flight at daemon restart (Phase 2 started, Phase 3 not reached) is dispatched on `idempotency_class`. The runtime emits `tool.replayed` for an `idempotent` or `compensable` re-execution and `tool.skipped_during_recovery` for a halt; full semantics live in [Spec-015 § Idempotency Protocol](015-persistence-recovery-and-replay.md#idempotency-protocol), and event-type registration lives in [Spec-006](006-session-event-taxonomy-and-audit-log.md) (full taxonomy-row integration tracked in [BL-064](../archive/backlog-archive.md)).

## Example Flows

- `Example: A local Codex driver starts a session through its native transport, exposes resume and steer capability, and emits normalized run events into the daemon.`
- `Example: A local Claude driver calls a remote provider API from the participant's runtime node. The provider service is remote, but the canonical driver authority and policy enforcement remain local.`
- `Example: A user pauses a run. No driver supports native pause. The orchestration layer implements pause as: interrupt the active run, persist conversation history and run state to local SQLite, queue a resume. When the user resumes, a new turn is started with the full saved context. The driver only sees interruptRun followed later by startRun — it never needs to know about pause.`
- `Example: A user steers a Codex run. The orchestration layer calls applyIntervention(type: "steer", payload). The Codex driver supports steer natively via turn/steer and applies it. For a Claude run, applyIntervention returns degraded, and the orchestration layer falls back to queuing the steer content and interrupting the current turn.`
- `Example: A client retries a steer whose response was lost in transit. The retry carries the same clientIdempotencyKey; the daemon finds the persisted intervention row and returns the originally recorded outcome without dispatching the driver a second time. A different steer accidentally reusing that key is rejected as intervention.idempotency_conflict.`

## Implementation Notes

- Keep the contract small but explicit. The runtime should not need provider-name branches to answer common lifecycle questions.
- Contract versioning should allow additive capability expansion without breaking older drivers.
- Resume handle persistence belongs to the runtime binding layer, not the user-facing domain model.

## Pitfalls To Avoid

- Letting provider-native ids replace canonical ids
- Treating missing capability declarations as implicitly supported
- Making the session engine understand transport-specific details such as JSON-RPC framing or stdio protocol
- Deriving quota or rate-limit refusals by matching provider message text rather than the provider's typed wire signals — `reauth-required` in the closed `RecoveryCondition` set is already detected mid-run from the provider's typed auth-failure signals, and the pinned Codex surface carries rate limits as first-class typed data (`account/rateLimits/read` pull, `account/rateLimits/updated` push), so text-matching is a deliberate downgrade that breaks on provider wording changes and on localization
- Neutralizing command-shaped text with invisible or zero-width characters (`U+200B` zero-width space, `U+2060` word joiner, variation selectors, Unicode tag characters). That encoding is a live prompt-injection and data-exfiltration channel, so hardened pipelines strip or reject it — a neutralizer built on it fails open precisely where a hardened pipeline is present — and it alters the bytes the model reads while staying invisible to the human reviewing the diff. The sentinel must be a character a reviewer can see.
- Applying the neutralization anywhere upstream of the driver's outbound frame — at the client composer, at queue admission, or at event append. Text mutated before it is persisted is text the audit log no longer matches and a rewind no longer reproduces, and a second application would visibly double the sentinel; the transform belongs at the one boundary that is both after persistence and before the provider.

## Acceptance Criteria

- [ ] A new driver can be integrated without changing session or run domain semantics.
- [ ] Unsupported capabilities remain unavailable to the user and cannot be invoked accidentally.
- [ ] Driver recovery failure produces explicit `provider failure` detail and a `RecoveryCondition` (`recovery-needed` or `reauth-required`) rather than silent session replacement.
- [ ] An intervention retried with the same `clientIdempotencyKey` never applies twice: the retry returns the original outcome, and key reuse with a differing payload is rejected.
- [ ] A logged-out provider is detected by the zero-turn `probeAuth` before any billed turn is spent.
- [ ] A successful resume reports the driver's normalized `sessionPosition`; an unparseable CLI version or below-floor provider install refuses attach fail-closed.
- [ ] An in-flight MCP receipt with a persisted task handle resolves via `tasks/get` polling + `tasks/result` retrieval rather than halting (a purged/expired or `input_required` task falls back to the halt); a receipt provably never dispatched auto-retries; every other `manual_reconcile_only` receipt keeps the operator halt.
- [ ] Participant text whose first word is command-shaped reaches the model as prose on every provider-bound path, and a provider that dispatches such a frame as a command instead fails the turn visibly rather than recording a zero-turn success. Visibly means three things on both provider-bound paths: the run halts on its `run.failed` run-lifecycle event ([Spec-006 §Run Lifecycle](006-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)) carrying the registered cause beside a `recovery-needed` condition — the asynchronous outcome a queued or orchestration-started run surfaces through, no caller being present to answer; the run's provider binding is disposed, so no later run re-binds to a session whose client-side state may have been mutated; and an intervention caller additionally receives the cause on its own response via `DriverInterventionResult.refusalCode` whenever the trip is classified before that call resolves — a **best-effort** leg by construction, which is why the two preceding clauses, not this one, are what the criterion is met by.

## ADR Triggers

- If the runtime stops using a normalized driver interface, create or update `../decisions/005-provider-drivers-use-a-normalized-interface.md`.

## Resolved Questions and V1 Scope Decisions

- No blocking open questions remain for v1.
- V1 decision: driver capability and account-state declarations are refreshed **per runtime node on a bounded periodic cadence — 15 minutes in V1** — and may also be updated live where the provider pushes (e.g. Codex `account/rateLimits/updated` push alongside the `account/rateLimits/read` pull; the zero-turn `probeAuth` rides the same refresh). Correctness must not depend on push-only updates.
- V1 decision: the first implementation supports local-runtime-node drivers only. Shared hosted execution drivers are out of scope, even when a local driver talks to a remote provider API.
