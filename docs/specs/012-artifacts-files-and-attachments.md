## Purpose

Define the canonical handling of artifacts, file attachments, and immutable output payloads.

## Scope

This spec covers artifact types, attachment ingestion and its pipeline (a PDF's first page among its steps), covering part of a staged picture, storage expectations, manifests, how a session's artifacts are deleted with it and local content-addressed-storage (CAS) reclaim, the typed attachment-reference contract turn-scoped carriers use, and how every linked device of the user reads a session's artifacts from the machine that runs the session.

## Non-Goals

- Full UI preview rules
- Notification behavior for new artifacts
- Remote object-store implementation details

## Required Behavior

- The system must support immutable artifact publication with durable manifests.
- Supported artifact families must include at least:
  - file or attachment
  - diff
  - plan or summary
  - command or terminal output excerpt
  - design or generated preview output
- Attachment ingestion must produce stable artifact ids and provenance metadata.
- Attachment ingestion must run every payload through the pipeline of §Ingest Validation And Payload Bounds (V1) **before** the bytes are persisted or any manifest row is written. **Any file can be attached**: no type is refused, and nothing is rewritten. A file offered as a picture is checked by its bytes only to decide whether it goes to the provider as a picture, in a format that provider takes. How many files one message carries and how large a file may be are what the daemon and the provider accept, and the app sets no figure of its own; a file that does not fit is refused naming that file and the limit it hit.
- The daemon must **derive** an ingested payload's media type and byte size from the payload bytes themselves. A caller-declared `mediaType` or `sizeBytes` is **advisory input, never a trusted fact**: the derived values are what reach the manifest, the CAS key, and every downstream consumer.
- **Every picture reaches the provider as its original file.** A picture staged in the composer by attach, paste or drop, a picture staged from another device, and a picture file an agent wrote that the transcript or the inspector shows are kept, drawn and sent as their own bytes: nothing re-encodes them, strips their metadata or bounds their pixels before a decode. The file's own bytes decide only whether it goes to the provider as a picture, in a format that provider takes, or as a path. A picture a provider will not take, for example one too large, is refused in that provider's own words. The person's own file on disk and an agent's file in the working folder are never touched. A PDF reaches the screen only as a picture of its first page, drawn in a throwaway ingest worker, and the PDF itself goes to the agent unchanged. The step is §Ingest Validation And Payload Bounds (V1) step 2 and the ingest worker it names.
- No person deletes a single artifact, and no method deletes one. A session's artifacts are its record of what it made: each write to the same path is a new version kept with the time it was written, a later write never replaces an earlier one, and the session's inspector offers no delete. The artifacts are deleted with their session, when `Delete old data` removes it or `Erase all data` removes everything the service holds, with a defined disposition for shared CAS payloads and for derivative artifacts that name a deleted manifest as their `subject` (§Local Artifact Deletion And CAS Reclaim (V1)). Before Send, a person can take a staged attachment out of the draft, or cover part of a staged picture, which replaces it with its covered copy.
- Where a turn-scoped carrier references attachments (a steer, an intervention, a human-phase form submission), the reference must be a typed, ordered list of `ArtifactId` values — never an untyped payload blob and never an inline byte carrier. Ordering is caller-declared and preserved end to end, and an attachment the turn cannot deliver must degrade honestly with an explicit per-attachment diagnostic; silently dropping an attachment from a delivered turn is prohibited.
- An artifact is never altered in place. A summarized or redacted form of an artifact is a separate derivative artifact with its own manifest and provenance. The one partial redaction is covering part of a staged picture before Send (below), which replaces the staged attachment with its covered copy.
- Referencing a live workspace file is not sufficient for artifact immutability; the system must capture immutable artifact content or a content-addressed snapshot.
- **A session's artifacts live on the machine that runs the session.** The daemon there holds every artifact in its store, and every linked device of the user lists and reads them through Remote Control's method proxy, calling the same `artifact.list` and `artifact.read` the executing machine's own window calls (§Artifacts On Every Linked Device). No copy of an artifact is kept anywhere else, so an artifact is readable from another device whenever that device can reach the executing machine.
- **A chat session's own files are artifacts, and every write is a new version.** Every file and every folder a chat session writes into its managed workspace is an artifact in the store, and each write to the same path is a **new version** of that artifact, kept with the time it was written; a later write never replaces an earlier one. That store is the one list of what the chat made — what its files-written timeline row lists, what the file surface steps through, and what the session's artifact count counts.
- **A file is read where its session reads files, and is never edited here.** On a project session a file opens as what changed in it, scoped to that one file, in the review surface; on a chat session it opens in the file surface, because a chat keeps files rather than changes. The file surface shows the whole file as it stands in the version in view — every line, numbered, never capped, masked or folded — with a stepper carrying the previous version, which version of how many is in view, the next version, and when that version was written, opening on the newest version; beside them a compare control, drawn only where the version in view has one before it, redraws the body as the changes between those two versions. That is the only comparison a chat ever draws and it is never against a repository, so the surface carries no branch, no commit, no staging control, no base picker, no note gutter, no send strip and no door into the review surface. Its name line, carrying the file's path, draws at once; until the version in view has arrived the body reads `Loading the file…`, shown only after the short delay every loading state waits, and a read that fails reads `Could not load the file` with `Try again` at its right. A path written in a reply that names a real file of the session's own workspace opens the same way it opens from a row, wherever it stands in the text and whether or not it carries a line, while a path that names nothing, or names something outside that workspace, stays plain text. Nothing in this product edits a file: there is no editable buffer, so there is no save, no undo of a file's text, no dirty state, and no second writer in the folder the agent is working in — every file surface hands the path to the user's own editor and offers a copy of that path instead. The review surface does not open on a chat session at all; after a chat is converted to a project, the copied files are reviewable as ordinary changes.
- **A picture, a PDF or a drawn diagram opens in one quick look, drawn from what the store already holds** and never from a parse on the reading surface: the picture's own bytes and natural size, and for a PDF its first page as a generated preview together with its page count, both derived at ingest under the file-or-attachment and design-or-generated-preview families above. Where the preview cannot be made, the artifact stays valid and retrievable as raw content and the quick look shows the file's name alone rather than a broken picture. A picture named in a reply has its place reserved at the natural size the store holds for it before a byte of it arrives, so the text under it never moves; its bytes are fetched through the daemon as the reader reaches it, how many load at once and in total is bounded, and where one cannot be shown a named state is drawn in its place ([Spec-011 §Fallback Behavior](./011-live-timeline-visibility-and-reasoning-surfaces.md#fallback-behavior)). The quick look opens fitted to the reading column and carries the file's own name; a pinch or a modifier-held wheel zooms about the pointer, so the thing under the pointer stays under it, a drag pans a picture larger than the surface, and a double press or the home key returns it to the fitted size. Closing it forgets the zoom. It adds no control of its own — no zoom figure, no plus and minus, no arrows between pictures, no gallery — apart from a staged picture's `Cover part of it` (below), and a PDF's first page behaves the same way. A changed picture in the review surface opens the same quick look with the old picture beside the new one, each labeled, and alone where there is no earlier version.
- **A staged attachment answers by kind and is never removed by opening it.** Pressing a staged picture opens the quick look, pressing a staged file opens that file where the session reads files, and the attachment's own remove control stays the only way to unstage it; closing either surface from a staged attachment returns focus to the draft with the draft's text and the staged set unchanged.
- **A staged picture can have parts covered before Send.** The quick look over a picture that is staged and not yet sent carries one control at its foot, under the picture: `Cover part of it`. Pressing it turns the pointer into a crosshair, and the foot reads `Drag over what to hide.` with `Cancel` and `Done` at its right. The zoom and position hold where they were, so a person zooms first and then covers; while covering, a drag draws a box and never pans, and the wheel does not zoom. Each drag leaves a solid black box. `Done` sends the boxes, in picture pixels, to the ingest worker, which draws them into the pixels and writes the covered copy as a new artifact that replaces the attachment's; the quick look stays open on the covered copy, and the uncovered copy is then deleted from the store. `Cancel` leaves the attachment as it was. The provider receives only the covered copy: the hidden pixels are gone from it, not masked over, and the uncovered original never leaves the store. A sent picture's quick look has no control, because covering after Send cannot take back what the provider already has.
- **A finished plan is a session artifact.** Every plan an agent finishes is stored as an artifact of its session in the plan-or-summary family, kept across restarts and listed on reload and on every linked device of the user, carrying its own state — waiting, accepted, handed on, or open — which the daemon updates on the verdict the user gives ([Spec-010 §Interfaces And Contracts](./010-approvals-permissions-and-trust-boundaries.md#interfaces-and-contracts)); a session built from a hand-off lists its seed plan as accepted. The reader that opens a plan renders the stored text — the document as the timeline renders it, footer included — over the session, which keeps running underneath: a running command's clock keeps counting and new rows still land. It closes on a press outside it, on its own close control, on the escape key, and on a session switch, and closing changes nothing else.

## Default Behavior

- A newly staged attachment is stored in the session's artifact store on the machine that runs the session.
- Artifact manifests default to storing producer, session, run, type and created time.

## Fallback Behavior

- If the artifact payload is too large for inline timeline rendering, the timeline must show a manifest row and require explicit fetch for the payload.
- If preview generation fails, the artifact remains valid and retrievable as raw content.
- If an attachment named by a turn-scoped carrier cannot be resolved or delivered, the turn still proceeds and carries an explicit per-attachment unresolved marker in its declared position. The attachment is never silently omitted, and the marker names its cause, `deleted`: the manifest is gone, its payload reclaimed with it.

## Interfaces And Contracts

- `ArtifactPublish` must return artifact id and manifest metadata.
- `ArtifactRead` must return manifest plus retrievable payload handle or inline content where appropriate.
- `AttachmentIngest` must normalize names, media type, and size metadata, and must run the §Ingest Validation And Payload Bounds (V1) pipeline before persisting anything. Its declared `mediaType` / `sizeBytes` inputs are advisory; the response returns the **derived** values, so a caller that guessed wrong learns what was recorded rather than having its guess recorded. It is carried as the `AttachmentIngestInit` / `AttachmentIngestChunk` / `AttachmentIngestComplete` trio per that section's transport binding — a single JSON-RPC frame cannot carry a large file, so single-call ingest is not a wire shape this spec defines. Every call of the trio is **retry-safe against a lost response**: a replayed `AttachmentIngestChunk` is acknowledged without re-appending, and a replayed `AttachmentIngestComplete` replays its original response verbatim for as long as its stream's registry entry lives (§Ingest Validation And Payload Bounds (V1) stream protocol).
- Attachment references on turn-scoped carriers are typed as `ArtifactId[]` — an ordered list of ids into this spec's manifest space, each element the daemon-minted RFC 9562 UUID the manifest bullet below defines, so a carrier's element is refusable at the parse boundary rather than only at resolution time. No carrier accepts an untyped attachment element or an inline byte payload: bytes reach the system only through `AttachmentIngest`, which is where the validation pipeline binds. Element order is caller-declared and preserved; an unresolvable element degrades honestly per §Fallback Behavior rather than being dropped. The two driver-boundary carriers `SteerPayload.attachments` and the `InterventionRequestPayload` `steer` arm are typed `ArtifactId[]` by their owning plans; **no V1 carrier may be wired to deliver attachments over an untyped arm** — each arm's retyping is a prerequisite of the first delivery wiring through it, never an opportunistic follow-up.
- Artifact storage uses an OCI-inspired manifest envelope: `{id: ArtifactId, sessionId, runId, digest: SHA-256, size, artifactType, annotations, subject?, createdAt}`. An `ArtifactId` is a **UUID per [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562), minted by the daemon at manifest creation** — the registered daemon-assigned identifier encoding this space shares with `SessionId` and `RunId`. A minted id is **[UUIDv7](https://www.rfc-editor.org/rfc/rfc9562#section-5.7)**, whose Unix-millisecond timestamp in the leading 48 bits makes manifest ids time-ordered; **acceptance is deliberately wider than minting** — any form valid under [RFC 9562 §4](https://www.rfc-editor.org/rfc/rfc9562#section-4) parses, so a control-plane-provisioned v4 is admitted and the version and variant bits ([§4.1](https://www.rfc-editor.org/rfc/rfc9562#section-4.1), [§4.2](https://www.rfc-editor.org/rfc/rfc9562#section-4.2)) are what make that a decidable predicate rather than a vague allowance (§References — the `ArtifactId` encoding) — and it identifies the **manifest**, never its content: the payload's SHA-256 `digest` is carried separately in this same envelope, so two manifests over byte-identical payloads share a `digest` and never an `id`.
- `artifactType` is a discriminator: `"file"`, `"diff"`, `"summary"`, `"log"`, `"design"`, `"workflow_output"` — one value per family enumerated above (`summary` covers the plan/summary family) plus `workflow_output`, the Spec-015 workflow phase-output type ([Spec-015 §Output Mode Specification](./015-workflow-authoring-and-execution.md#output-mode-specification)).
- `subject` field enables artifact linking (e.g., a diff artifact referencing its parent run artifact).
- **Plan artifacts are written by the daemon, not by a client.** When a plan turn ends — the provider's plan-exit request arrives, or its plan item lands — the daemon writes that plan's text as an artifact of the session in the plan-or-summary family under a stable identifier, and updates that artifact's state when the user's verdict arrives: accepted on a build in the same session, handed on when the plan is handed to a fresh session, and left waiting while the verdict is outstanding ([Spec-010 §Interfaces And Contracts](./010-approvals-permissions-and-trust-boundaries.md#interfaces-and-contracts) owns the verdict itself). The list a session's artifact section shows is a projection of that store, and the plan reader renders the stored text.
- **A chat session's file versions are read through the same artifact space.** A read of one of those artifacts answers with the version in view and how many versions exist, so the file surface can step between them and compare a version with the one before it without a second store and without a comparison against a repository.
- `artifact.list {sessionId}` lists the session's artifacts: every plan the agent finished, with its first heading, its time and its state word, and, on a chat session, every file and folder the chat wrote with its versions; the reply carries the count the session's artifact section shows. The session screen reads it again on `artifact.published` rather than on a timer.
- `artifact.read {artifactId, version?}` returns the manifest, the version in view (the newest when none is named), how many versions exist and when the one in view was written, a picture's natural size, a PDF's first-page picture and page count, and the payload, in chunks when it is larger than one frame carries. It is a read: it never writes and never refuses a retry.
- Staging is the session's. `session.attachmentAdd {sessionId, items}` stages picked or dropped files by the token the main process's relay turns into a path, a pasted picture by the token minted for it, a Preview marks chip, or a tool server's resource; a path is accepted only from that relay or the command line, never from another device. Each item carries a client staging id, so `Try again` never stages twice; each file is copied into the store at staging time through §Ingest Validation And Payload Bounds (V1); and the reply is the whole staged set with a refusal per item not taken, naming the limit hit and how many were taken. `session.attachmentRemove {sessionId, artifactId}` unstages one attachment and returns the rest; removing one that is not staged returns the set unchanged. `session.attachmentCover {attachmentId, boxes: [{x, y, width, height}]}` covers part of a staged picture, the boxes in picture pixels, and returns the new attachment. The staged set is kept with the session beside its draft (`session.draftUpdate`), and `session.read` returns both on every device.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## Ingest Validation And Payload Bounds (V1)

The pipeline binds to the **trust boundary, not to a method name**: every caller-supplied payload that crosses the client↔daemon boundary runs this section's pipeline before anything persists, whichever interface carries it. Two interfaces carry such bytes. `AttachmentIngest` is the primary ingress and the only one that mints the `file` family. `ArtifactPublish` also accepts a caller `payload`, and a boundary-crossing publish runs the pipeline's three steps over its decoded payload — the type read from the bytes (step 1), a PDF's first page (step 2) and the CAS admission (step 3) — under the same decoded-byte accounting. A publish carries no filename member, and no publish-supplied string is ever a path component (step 3). Its single-call payload is bounded by the local transport's message ceiling (below), enforced on the **serialized frame** — so the only predictable raw ceiling is the `base64` arm's fixed 4/3 expansion, ≈3 MB of raw bytes; a `utf8` payload's serialized size is content-dependent, because `JSON.stringify` escaping of quotes, backslashes, and control characters can expand it 2–6×, so ≈4 MB of UTF-8 is the **no-escaping upper bound, never an allowance**, and a caller near the ceiling publishes `base64` for a predictable fit. An over-ceiling frame is refused at the transport before any body byte is buffered; V1 deliberately ships no chunked publish carrier — file bytes above the ceiling take the `AttachmentIngest` trio, and daemon- or engine-internal publishes never cross the wire, so they are unaffected — and a boundary-crossing publish declaring `artifactType: "file"` is **refused and directed to `AttachmentIngest`** rather than validated in a second place — one hardened ingress for file bytes, never two. Payloads produced by daemon- or engine-internal code paths (`diff`, `summary`, `log`, `design`, `workflow_output` from the run engine or daemon services) never cross the boundary: their media types come from the producing code path, and this section does not bind them.

**Transport binding and large payloads.** The local client↔daemon wire enforces a hard 4 MB message ceiling on the `Content-Length` declared by the frame header, **before the body is buffered** ([Spec-006 §Wire Format](./006-local-ipc-and-daemon-control.md#wire-format); shipped as [`local-ipc-gateway.ts#MAX_MESSAGE_BYTES`](../../packages/runtime-daemon/src/ipc/local-ipc-gateway.ts#MAX_MESSAGE_BYTES) — an oversized declaration closes the connection without materializing the payload), so no single request can hand the daemon an unbounded buffer. A file larger than one frame cannot arrive in one, so `AttachmentIngest` is carried as an **Init / Chunk / Complete trio**: `AttachmentIngestInit` declares the advisory metadata; each `AttachmentIngestChunk` appends to a daemon-spooled temporary file outside the CAS (bounded memory — chunks are written through, never accumulated in RAM), with every chunk's encoded frame respecting the Spec-006 ceiling; `AttachmentIngestComplete` runs the pipeline over the spooled bytes (the detector reads a bounded leading prefix), step 3's admitting CAS rename committing the payload as the pipeline's final successful act. An abandoned spool (crash or client disappearance mid-trio) is reaped by a daemon-local `mtime`-clocked reaper 48 h after its last write — no table, no daemon restart dependency. **The wire is JSON, so chunk bytes ride base64.** Spec-006's serialization is `JSON.stringify`/`JSON.parse` with no binary serialization, so no interface of this spec carries a binary field across the local boundary: an `AttachmentIngestChunk` chunk is an RFC 4648 §4 base64 string, and every payload-bearing member of this spec's local-wire interfaces is likewise a string — UTF-8 text verbatim or base64 under an explicit encoding discriminator. The per-chunk raw ceiling is `max_attachment_chunk_bytes` (§Bounds — fixed at 512 KiB): the 4/3 base64 expansion plus the JSON-RPC envelope fits the 4 MB frame ceiling by arithmetic (512 KiB × 4/3 ≈ 683 KiB), never by luck. Every byte bound in this section binds the **decoded** bytes — the spooled running count, the reservations, and `derivedSizeBytes` all count raw payload.

**Stream protocol: admission, sequencing, completion, and termination are contract, not implementation detail.** Six rules close the gaps a per-stream cap and an `mtime` reaper cannot see:

- **Admission is bounded in aggregate.** `AttachmentIngestInit` is refused with `artifact.ingest_capacity_exhausted` (429) — transient backpressure, retry later, no stream state created — when the count of open streams has reached `max_active_ingest_streams` or when the spool's volume, its free space read from the disk at admission, has no room for this declaration beside what the open streams have already reserved. Without the aggregate bound, a caller opening many large streams and never calling Complete holds spool disk hostage for the full reap TTL. A declaration the free disk cannot hold even with no other stream open can never admit, so waiting cannot help it: it is refused `artifact.too_large` (413), naming the file and the room the disk has, rather than given a 429 that promises a transience it does not have. No figure of the daemon's own caps one file. **Admission is a serialized reserve-then-install ledger, not a check followed by a write**: one critical section covers reading the open-stream count, the reserved-byte total and the volume's free space, testing the declaration against them, and installing the new registry entry carrying its reservation. Two concurrent Inits would otherwise each observe headroom and both admit, breaching `max_active_ingest_streams` or the disk's room by up to one maximal declaration per racing caller — a bound checked but not held is not a bound. **A refusal leaves zero state, and the zero is observable through admission rather than through the refused id**: a refused Init mints no `ingestId`, so there is nothing to probe with and this spec never fabricates one to make the check expressible. What is observable is the effect a leak would have on the _next_ caller — releasing one open stream after a count-bound refusal admits the following Init, and a declaration fitting the freed room admits after a reservation-arm refusal — so a leaked slot or reservation surfaces as a refusal that outlives its cause.
- **The declaration is a reservation, and the reservation is enforced.** A declared total reconciles downward at Complete (a smaller actual size resolves to the derived value — no refusal), but it is also the stream's spool reservation and per-stream ceiling: a chunk pushing the running decoded count past the Init-declared total is refused `artifact.too_large` (413) with the spool deleted. An unenforced declaration would make the admission arithmetic gameable — declare 1 MB, spool a gigabyte — so the byte the admission arithmetic counts is the byte the stream may write, no more.
- **Sequencing is replay-idempotent, and violation is terminal.** Chunks carry 0-based strictly-consecutive sequence numbers. The daemon retains the last acknowledged sequence number and the SHA-256 of the last appended chunk: an exact replay — same sequence, same bytes, the ordinary retry after a lost Chunk response — is **acknowledged idempotently without re-appending**, so a client-side retry is always safe. A same-sequence chunk with different bytes, a gap, or a regression terminates the stream: spool deleted, `ingestId` invalidated, the violating call and **every subsequent Chunk or Complete on a terminated, expired, or unknown `ingestId` — and every Chunk on a completed one** — refused with `artifact.ingest_stream_invalid` (409). The one carved exception is a replayed `Complete` on a **completed** stream whose completion record is still held, which replays that record's response verbatim rather than refusing (next rule). The two codes are the SDK's dispatch contract: 409 means restart from Init, 429 means retry later, and a transport-level failure means retry the same call — which replay idempotency makes lossless for every call of the trio, `Complete` included (next rule).
- **Completion is idempotent, because a lost response must not cost the caller its upload.** Replay idempotency above covers `Chunk`; `AttachmentIngestComplete` is the call whose response is the expensive one to lose — it carries the minted `artifactId` and the derived digest, name, media type, and size, and its work is the whole pipeline over the whole spool. A completion therefore writes a **completion record on that stream's own registry entry**: the response it returned, stamped with the digest the run committed. A `Complete` arriving on a stream that already holds one **replays that response verbatim** — same `artifactId`, same `contentHash` — running no pipeline step again and inserting no second manifest row, which is what makes the retry after a lost response lossless rather than merely safe. Completion still **releases the stream's reservation, its count slot, and its spool** at the moment it commits; what survives is the entry in a completed state holding only the record, so a completed stream can never pin `max_active_ingest_streams` or the reservation budget. `Complete` carries no member beyond the `ingestId` ([api-payload-contracts.md §Plan-011](../architecture/contracts/api-payload-contracts.md#plan-011--artifacts-files-and-attachments)), so a _divergent_ Complete on a completed stream has no wire form to take; the record is stamped with the committed digest regardless, and a stamp disagreeing with the entry's own committed state fails closed to `artifact.ingest_stream_invalid` (409) — defense in depth against a state a daemon-minted single-use `ingestId` makes unreachable, the same idiom as the Fetch step 5 multi-match arm, never a live path. The record **shares the registry entry's lifetime bounds exactly**: in-memory, dying with the process, and evicted with the entry at `max_ingest_stream_lifetime`. **Named residual:** past that bound a retried `Complete` receives the ordinary 409 and the caller re-ingests — CAS dedup stores the bytes once, so the cost is a **second manifest row over one payload**, never duplicated bytes and never a lost artifact. Retaining records longer would require a durable table, which this section deliberately does not mint for a transient.
- **Every call on one stream is single-flight, and eviction takes the same exclusion.** A `Chunk` is a read-modify-write over per-stream state — validate the sequence against the last acknowledged one, append to the spool, advance the running decoded count and the last-chunk digest, acknowledge — so two calls interleaving on one `ingestId` could both validate against the same last-acknowledged value and append twice (breaking the reservation arithmetic and the digest the replay check reads), or let a replay compare against half-updated state. Every call on one `ingestId` therefore executes inside a **critical section keyed by that `ingestId`**: concurrent calls on the same stream queue and run one at a time — the ordinary case being an original and its retry racing after a lost response — while calls on different streams never contend. The **reaper's eviction path takes the same exclusion**, or an over-lifetime sweep could delete a spool a `Chunk` is mid-append into, or release a reservation a `Complete` is mid-commit on; the sweep snapshots candidate entries under the admission ledger, releases it, then takes each candidate's own exclusion and re-checks the entry's state before evicting. So a stream is either being served or being evicted, never both. **Exclusion order is total and acyclic:** per-`ingestId` → the admission ledger → the per-`storage_path` CAS exclusion (§Local Artifact Deletion And CAS Reclaim (V1)). `Init` takes the ledger alone and no stream exclusion, so it introduces no back edge; `Complete` is the call that makes the order load-bearing, since it is the one holding a stream exclusion while releasing a reservation and then renaming into the CAS.
- **A live stream's lifetime is wall-clock-bounded.** The abandoned-spool reaper clocks `mtime`, and a hostile trickle of keep-alive chunks holds `mtime` young forever — so a stream is additionally bounded by `max_ingest_stream_lifetime` measured from Init — and enforcement does not wait for a call, because a silently-abandoned stream never makes one: every pass of the same daemon-local reaper cadence that owns abandoned-spool expiry and the orphan sweep evicts over-lifetime registry entries, terminating the stream, releasing its reservation and count slot, and deleting its spool, so sixteen abandoned streams cannot pin `max_active_ingest_streams` or their reserved room on the disk past the lifetime bound. An over-lifetime **completed** entry is evicted by the same pass, taking its completion record with it — it holds no reservation, count slot, or spool to release, having surrendered all three at commit, so its eviction bounds only how long a `Complete` stays replayable. A call on an over-lifetime stream that beats the sweep terminates it the same way (the same 409). The daemon-crash case needs nothing new, because the stream registry is in-memory — a stream dies with the process and its spool goes quiescent for the `mtime` reaper.

**Composer-staged payloads.** A picture pasted into a draft, and a file or a picture dropped onto the composer, stage as attachments through this same pipeline: the bytes are copied to the daemon at staging time and kept outside the checkout, several at once on a drop, while pasted **text** stays text in the draft and stages nothing. A picture stages as its original bytes and is never re-encoded or scaled; one the bound provider will not take, for example one too large, is refused in that provider's own words. A dropped **folder** is refused on the same ground the file picker refuses one: an agent reads a folder where it is, so a folder reaches it as a path rather than as bytes. Each refusal is one line beside the staged attachments naming the payload it refused, never a dialog, and where several were offered at once that same line says how many were taken, so nothing is dropped in silence. A payload still being copied says so on its own staged row, and a send waits for the copy to finish before the message goes, so a drop followed straight away by a send never loses the file.

**A file one session sends to another stages the same way.** The daemon's `session_send` takes paths the sending session can already read, copies them at send time, and stages them as the **receiving** session's own attachments, so they reach that session's model as paths it opens with its own file tools ([Spec-014 §Sessions Talking To Each Other](014-multi-agent-orchestration.md#sessions-talking-to-each-other)). Both message rows carry the file chips a sent turn's attachments carry. Nothing about the pipeline changes for them: the same steps run in the same order over the same decoded bytes, the same bounds hold, and the same refusals apply, each as the one line that names the payload it refused. No size or count bound of this app's stands beyond this pipeline's own, and the provider's own file-sending tool, switched off by its maker, is neither waited for nor mirrored.

**Every picture from outside the daemon is kept, drawn and sent as its original bytes.** Only those bytes are stored, in the artifact store, for the life of the session, and they go with it at purge. Claude Code receives the image content block built from them, and Codex receives `localImage {path}` naming the stored file. The console draws the original by decoding it straight to the size it is shown at (`createImageBitmap` with its resize options), so the window's memory follows the drawn size, never the file's; opening it full size decodes at the screen's size. Its picture budget counts each loaded picture at that decoded size ([Spec-021 §Pane kinds](./021-desktop-app-and-renderer.md#pane-kinds)). The file sent to the provider is untouched. Nothing is added on screen.

**A PDF reaches the screen only as a picture of its first page.** A throwaway ingest worker draws it. The worker is a child process the daemon starts for one file and ends after it, holding no key, no socket, no database handle and no session state; it reads the file's bytes on standard input and writes its output on standard output, so a crash or a hang in it is a refusal of that one file, never a fault in the daemon. A worker starts in 60 to 80 ms. One worker runs at a time and the next file waits for it, and each is admitted against the service's memory gate with a reservation of the file's bytes plus the output picture's pixels × 9 bytes plus 128 MiB, worked out before the worker starts. It opens the PDF with PDFium's WebAssembly build (`@hyzyla/pdfium`), reads its page count, draws page 1 at twice its own point size (a US Letter page is 1224 × 1584) and hands that bitmap to sharp, which writes a PNG. The PNG is stored as the PDF's generated preview, with the page count beside it. Only pixels leave the worker, so the PDF's scripts, forms, links, embedded files and fonts never reach a browsing context. A PDF the worker cannot open keeps the name-only quick look, and the PDF file itself goes to the agent unchanged.

**Covering part of a staged picture runs in the same kind of worker.** `session.attachmentCover` hands the worker the staged picture and the boxes, in picture pixels; the worker decodes it with only libvips' PNG, JPEG, GIF and WebP loaders, draws each box solid black into the pixels and writes the covered copy in the same format, and the daemon stores it as a new artifact that replaces the attachment, then deletes the uncovered copy through §Local Artifact Deletion And CAS Reclaim (V1). The covered copy names no `subject`, since the artifact it came from is deleted.

Any file can be attached, so no type list applies and nothing is refused for its type. The rule that carries over from upload guidance ([OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)) is **the server derives and never trusts**: the type and size recorded are read from the bytes, never taken from the caller, and no caller string becomes a path.

### Bounds

These bounds are fixed defaults the daemon ships; no setting changes them. None of them is a figure on how large one file may be or how many one message carries: those are what the daemon and the provider accept, and a refusal names the file and the limit it hit.

| Parameter | Value | Derivation |
| --- | --- | --- |
| `max_attachment_chunk_bytes` | 512 KiB | Largest raw chunk whose RFC 4648 base64 form plus JSON-RPC envelope fits Spec-006's 4 MB frame ceiling with headroom (512 KiB × 4/3 ≈ 683 KiB). |
| `max_active_ingest_streams` | 16 | Admission cap on concurrently open Init→Complete streams. The disk's free space, read at admission (§Stream protocol), is the binding constraint on bytes; the count bounds registry bookkeeping and refuses a pathological stream-open flood with an honest 429 rather than letting it exhaust file handles first. |
| `max_ingest_stream_lifetime` | 6 h | Wall-clock ceiling on one stream measured from Init: the abandoned-spool reaper clocks `mtime`, which a trickle of keep-alive chunks refreshes indefinitely, so live-stream tenure needs its own clock. It bounds a hostile hold on the spool's reserved room. |

### Pipeline (ordered)

1. **Read the type from the bytes.** The daemon derives the media type from the payload's own leading signature, reading a bounded leading prefix; the caller's declared `mediaType` is advisory. Nothing is refused for its type, and nothing is rewritten. The derived type decides two things only: whether a file offered as a picture goes to the provider as a picture, in a format that provider takes, or as a path; and the type the manifest records.
2. **Draw a PDF's first page.** A picture is stored as it came; a PDF goes to the ingest worker (above) for its first-page picture and is itself stored unchanged.
3. **Path validation, CAS address derivation, and admission.** The stored payload is keyed by its SHA-256 CAS address (§Implementation Notes), a server-derived name derived at this step, and **no caller-supplied string is ever a path component**. This discharges the cheat sheet's random-filename and path-traversal requirements — **structurally rather than by sanitization**: there is no caller-influenced path to traverse. The caller's original filename survives as manifest metadata only, length- and character-bounded before it is recorded, and is never used to open, create, or serve a file. **Admission lands here:** the CAS rename of that address commits the payload as a readable artifact, the pipeline's **final successful act**, with a PDF's first-page picture and page count committed beside it. A payload refused before this step never entered the CAS, so there is nothing to un-commit.

### Consumers, and what they may assume

A workflow's `files.ingest-artifacts` step pushes items through this pipeline unchanged and adds no validation path of its own: one pipeline, one place to harden.

The upload battery that consumers test against resolves here as follows. **Oversize** is what the daemon and the provider accept: a stream past its own declaration is refused at that chunk, and a picture the provider will not take is refused in its own words. **Mismatched `Content-Type`** refuses nothing: the type read from the bytes is recorded and the declaration is dropped. **Polyglot** is answered by the serving posture, not the detector: payloads are explicit-fetch downloads, never rendered inline as trusted markup, and the families the app does draw are drawn only as pictures — a picture by the console's sandboxed renderer, and a PDF's first page from what the ingest worker rendered to pixels (step 2) — so a second interpretation has no in-product execution surface. **Zip bomb** and **symlink traversal** — including the broken-fix class of [CVE-2025-66626](https://nvd.nist.gov/vuln/detail/CVE-2025-66626) — are not defended against so much as **made unreachable**: V1 never unpacks an archive (below), so no entry is ever extracted, no path is ever joined, and no symlink is ever followed. That is a stronger answer than a traversal check, and it is the reason the answer is stated rather than left to a validator.

### Scope limits, stated rather than implied

- **Reading the type from the bytes decides how a file is sent, never whether it is safe.** V1 ships the PDF's first page drawn to pixels, pictures drawn only in the console's sandboxed renderer, and no parser on any other outside file, and claims exactly that much.
- **V1 does not decompress or introspect archive interiors at ingest.** An archive is stored as opaque bytes under its own signature. This is a deliberate scope choice with a security dividend: not unpacking means the archive-entry-count and uncompressed-size class, and the zip-slip and symlink classes with it, have no reachable path here. It also means the type detector must not be pointed at container interiors — container-introspecting detectors have shipped decompression-bomb denial-of-service of their own.
- **Detection runs under a time and byte bound.** Signature detection is untrusted-input parsing and is treated as such: it reads a bounded leading prefix, and detection itself is bounded by a timeout, so a malformed payload that sends a parser into an unbounded loop fails the ingest rather than the daemon.
- **The daemon parses no outside file but a PDF's first page.** A picture is stored and sent as its original bytes and drawn only by the console's renderer, and a PDF reaches the screen only as its first page drawn to pixels in the ingest worker. Content-disarm-and-reconstruct of any format is not done, because the app opens no other outside file with a parser: text is shown as text, and everything else is stored unopened and handed to the agent as a file.

## Local Artifact Deletion And CAS Reclaim (V1)

A session's artifacts are deleted with the session. The one other deletion is the uncovered copy of a staged picture, which the cover replaces (§Required Behavior). No method deletes a single artifact, so this section governs those deletions: what becomes of a payload other manifests still name, and of a derivative whose source goes.

**Payload reclaim is refcounted, and the refcount is derived — not stored.** CAS dedup means several manifests can share one stored payload (§Implementation Notes: "keyed by SHA-256 for automatic deduplication"), so deleting a manifest must never delete bytes another manifest still names. The refcount for a stored payload is the number of surviving payload references to that storage key; reclaim is permitted **only** when that count reaches zero — that direction is absolute, bytes named by a surviving manifest are never unlinked — and initiates at zero, with completion eventual rather than instantaneous: a post-commit unlink that fails is left to the orphan sweep (below), so zero-referenced bytes may persist until the next sweep pass, never the reverse. Deriving the count from the existing reference rows rather than maintaining a counter column is deliberate: a stored counter is a second source of truth that drifts on every crash between the row write and the counter write, and drift in this direction destroys data.

**Reclaim is crash-safe by ordering, not by pretending one transaction spans two stores.** A SQLite transaction cannot make a filesystem unlink atomic with the row deletions it accompanies, so the direction of failure is chosen deliberately: the row-deletion transaction commits **first**, and the payload unlink runs **strictly after commit**. A crash between the two leaks bytes — an orphaned CAS entry referenced by no row — and never the reverse: no surviving manifest ever points at missing bytes. The leak is bounded and self-healing via an idempotent **orphan sweep** that unlinks CAS entries with zero payload-reference rows — run at daemon start **and periodically thereafter on the same daemon-local reaper cadence that owns abandoned-spool expiry** (a boot-only sweep leaves a failed reclaim's plaintext on disk for the lifetime of a long-running daemon). An ENOENT on the unlink path is success, so the sweep and a racing delete cannot fight, and re-running the sweep is always safe. The same sweep is the durable retry for a post-commit unlink that fails with a non-`ENOENT` error (`EACCES`, `EIO`): no tombstone row is minted, because the zero-reference predicate the sweep derives from the surviving rows **is** the durable reclaim record — the failed entry is simply an orphan the next pass retries. A session purge proves completion the same way: the sweep predicate over surviving rows, not a per-delete success bit.

**Reclaim is also concurrency-safe, by per-key exclusion — ordering alone is not.** Crash-safe ordering says nothing about a live writer: CAS dedup means a same-hash publish or ingest can land between a delete's commit and its post-commit unlink, observe the still-present CAS entry, insert a fresh payload reference to it — and then the unlink destroys bytes a surviving manifest names. The daemon is the CAS's only writer and reclaimer (single-process ownership), so the fix is an in-process critical section keyed by storage key: a writer holds the key's exclusion across its CAS existence check and payload-reference insert, and a reclaimer holds it across refcount derivation and unlink — **re-deriving the refcount inside the exclusion, after the row-deletion commit, and aborting the unlink on any count above zero** (a raced-in reference wins; the bytes stay). The boot-time orphan sweep takes the same per-key exclusion, so it is safe to run concurrently with the accepting surfaces rather than depending on startup ordering: a writer whose reference lands before the sweep's in-exclusion re-check saves the entry, and one arriving after the unlink misses the existence check and writes fresh bytes. Either interleaving ends with every manifest over present bytes; the exclusion removes the third.

**A derivative goes with its source, never after it.** Derivatives point at their source (§State And Data Implications), and a dangling `subject` would break the provenance chain that makes a redacted derivative auditable. Every derivative chain is confined to one session (below), so the purge deletes a derivative and its source in the same row-deletion transaction and never leaves one without the other. A staged picture is not yet part of any turn, so nothing derives from it, and the cover's deletion of the uncovered copy never meets a derivative. A derivative's `subject` is never nulled: that would silently convert a derivative into what looks like an original, destroying exactly the provenance the derivative-not-mutation rule exists to preserve.

**A derivative's `subject` is session-scoped, resolved at publish.** `ArtifactPublish` resolves a request's `subject` within the request's session only; an id that does not resolve there — including a manifest that exists in another session — is refused `artifact.not_found` (404), the same code as any unresolvable artifact reference, because outside the session's scope the manifest does not exist for this caller. The consequence is structural: every derivative chain is confined to one session, so the session-deletion sweep below never meets a foreign referent — its completeness is by construction, not by cross-session search.

**Session deletion disposes the session's artifacts with the session.** The service's one purge, `Delete old data` ([Spec-020 §Retention Policy](./020-data-retention-and-gdpr.md#retention-policy)), deletes each purged session's rows — its artifacts and their manifests among them — in one row-deletion transaction with SQLite's `secure_delete` on and a `TRUNCATE` checkpoint after commit ([Spec-020 §Ordering And Atomicity](./020-data-retention-and-gdpr.md#ordering-and-atomicity)), then reclaims every payload whose derived refcount reached zero, the unlinks running strictly after commit under the same crash-safe ordering, so a crash mid-sweep leaves rows consistent and at worst leaks payloads the orphan sweep reclaims. The artifact sweep is a session-keyed function the purge calls; nothing else deletes a session's artifacts but the cover's removal of the uncovered copy, archiving a session keeps them, and `Erase all data` removes the whole store with everything else the service holds. What the purge may never do is complete with the session's artifact payload bytes still in the CAS, because artifacts are session work product and their payloads are exactly the personal data a purge exists to destroy.

## Artifacts On Every Linked Device

A session's artifacts are held by the daemon on the machine that runs the session, in its store, and nowhere else. Every linked device of the user lists and reads them through Remote Control's method proxy ([Spec-027](./027-remote-control.md)), calling the same `artifact.list` and `artifact.read` the executing machine's own window calls, so a plan, a chat's file with its versions, a staged picture and a PDF's first page read the same on every device. No artifact payload is uploaded to a relay or copied to another device to be kept there, no per-device key wraps it, and an artifact is readable from another device whenever that device can reach the executing machine. A file staged from another device reaches the executing machine as bytes through the `AttachmentIngest` trio and passes §Ingest Validation And Payload Bounds (V1) there like any other.

## Failure modes (normative responses)

| Failure | Required response |
| --- | --- |
| The ingest worker crashes or hangs on a file | That one file is refused and the daemon keeps serving, because the worker is a separate process holding no key, socket, database handle or session state. |
| `AttachmentIngestInit` arrives while the open-stream count is at its bound or the spool's volume has no room for the declaration beside the open streams' reservations | Refuse with `artifact.ingest_capacity_exhausted` (429) — transient backpressure, retry later — with **no stream state created**: no `ingestId` is minted, no slot consumed, no reservation held, so releasing one open stream (or waiting out `max_ingest_stream_lifetime`) admits the next Init. Never silently queue, and never let the flood reach the filesystem (§Ingest Validation And Payload Bounds (V1) stream protocol). |
| Two `AttachmentIngestInit` calls arrive concurrently with one slot or one declaration's worth of free disk left | Exactly one admits; the other refuses `artifact.ingest_capacity_exhausted` (429). Admission is one serialized reserve-then-install section over the count and the reserved-byte total, so the bounds cannot be breached by two callers each observing the same headroom (§Ingest Validation And Payload Bounds (V1) stream protocol). |
| An ingest chunk repeats, gaps, or regresses its sequence — or any call arrives on a terminated, expired, or unknown `ingestId`, or a `Chunk` on a completed one | An exact replay of the last acknowledged chunk (same sequence, same bytes — the retry after a lost response) is acknowledged idempotently without re-appending. Every other violation refuses `artifact.ingest_stream_invalid` (409), terminating a live stream with its spool deleted — the terminal restart-from-Init signal, deliberately distinct from the transient 429 (§Ingest Validation And Payload Bounds (V1) stream protocol). |
| `AttachmentIngestComplete` is retried because its response was lost in transit | The retry **replays the original response verbatim** from the completion record on the stream's registry entry — same `artifactId`, same `contentHash` — re-running no pipeline step and inserting no second manifest row. Past `max_ingest_stream_lifetime` the entry and its record are gone, so the retry gets the ordinary `artifact.ingest_stream_invalid` (409) and a re-ingest costs a second manifest row over one CAS payload — never duplicated bytes (§Ingest Validation And Payload Bounds (V1) stream protocol). |
| Two calls on the **same** `ingestId` overlap — an original and its retry racing after a lost response | Both are served, one at a time: every call on one stream runs inside a critical section keyed by that `ingestId`, so sequence validation, spool append, running-count and digest update, and acknowledgment are atomic per call, and the second call observes fully-updated state (the replay path, not a double append). The reaper's eviction takes the same exclusion, so a stream is never served and evicted at once (§Ingest Validation And Payload Bounds (V1) stream protocol). |
| Attachment named by a turn-scoped carrier cannot be resolved or delivered | The turn proceeds and carries an explicit unresolved marker in that attachment's declared position naming its cause, `deleted` (the manifest is gone). Silently omitting it is prohibited (§Fallback Behavior). |

## State And Data Implications

- Artifact manifests are durable records and part of replayable session history.
- Payload storage may differ from manifest storage, but provenance must stay intact across both.
- Plan-011 owns the `artifact_manifests` table.
- Local payload reclaim carries **no counter column**. The refcount for a stored CAS payload is derived by counting the surviving payload-reference rows that name its storage key, and the bytes are reclaimed only at zero (§Local Artifact Deletion And CAS Reclaim (V1)). Adding a stored counter is rejected: it is a second source of truth that drifts on any crash between the reference write and the counter write, and drift in the decrementing direction deletes bytes another manifest still names.
- The ingest stream registry, its per-stream completion records, and the aggregate spool reservation are **in-memory daemon state, deliberately not tables**. A stream dies with the process — its spool goes quiescent for the `mtime` reaper, and a retried `AttachmentIngestComplete` after a restart takes the ordinary 409 restart-from-Init path. Making completion records durable would mint a table for a transient whose whole lifetime is bounded by `max_ingest_stream_lifetime`; the accepted cost is the named residual in §Ingest Validation And Payload Bounds (V1) — a second manifest row over one deduplicated CAS payload.
- Any redacted or summarized derivative must be a separate artifact with its own manifest and provenance rather than an in-place mutation of the original artifact.
- An outside picture is stored as its original bytes. A PDF's first-page picture and page count are stored beside the PDF. A covered picture is a new artifact naming no `subject`, and the uncovered copy it replaces is deleted.

## Implementation Notes

- Artifact immutability matters more than original path convenience.
- Content-addressable storage (CAS) is keyed by SHA-256 for automatic deduplication. CAS addressing also discharges the OWASP random-filename requirement structurally: no caller-supplied string is ever a path component, so there is no filename to sanitize on the storage path.
- Attachment manifests should stay small enough for routine timeline and replay use.
- Signature detection is a library choice, not a contract: the spec requires that the type be derived from the bytes and bounded in time, not that any particular detector be used. The implementing plan records the library-versus-hand-rolled decision with its version.
- **This spec's three in-process exclusions form one total, acyclic acquisition order**, all of them daemon-local because the daemon is the sole writer of the CAS, the spool, and its own manifest rows: **per-`ingestId`** (the stream single-flight section) → the **ingest admission ledger** (the open-stream count plus reserved-byte total) → **per-`storage_path`** (CAS reclaim and the same-hash write path). Acquiring in that order and never inverting it is the whole rule. Two shapes make it work rather than merely declare it: `AttachmentIngestInit` takes the ledger alone and no stream exclusion, so admission introduces no back edge from ledger to stream; and the lifetime reaper snapshots eviction candidates under the ledger, releases it, then takes each candidate's own `ingestId` exclusion and re-checks state before evicting, so the sweep never holds the ledger while waiting on a stream. `AttachmentIngestComplete` is the path that exercises the order end to end — stream exclusion held, reservation released against the ledger, then the step-3 CAS rename under the storage-key exclusion.

## Pitfalls To Avoid

- Treating a live filesystem path as an immutable artifact
- Requiring inline rendering for every artifact regardless of size
- Re-encoding, stripping or scaling a picture before it is stored, drawn or sent
- Covering a picture with an overlay or a flag instead of drawing the boxes into its pixels
- Rendering an outside PDF in a browsing context instead of drawing its first page to pixels in the worker
- Recording a caller-declared `mediaType` or `sizeBytes` on the manifest — the declared values are advisory input, and the derived values are the facts
- Pointing the type detector at an archive interior — container introspection is a decompression-bomb surface, and V1 deliberately does not unpack
- Maintaining a stored CAS refcount column instead of deriving the count from the surviving reference rows (a second source of truth whose drift deletes live bytes)
- Untyped attachment elements on turn-scoped carriers, or an attachment that a turn quietly drops when it cannot be delivered
- Refusing a retried `AttachmentIngestComplete` whose only fault is that the caller lost the first response — the completion record exists so the retry replays the original response instead of costing the caller a whole re-upload, and the opposite error is just as bad: re-running the pipeline and inserting a second manifest row on a stream that already completed
- Checking a shared byte budget outside the critical section that spends it (the ingest spool reservation) — concurrent callers each observe the same headroom and the bound is exceeded by one payload per racing caller, which is the denial-of-disk the budget exists to prevent
- Serving two calls on one `ingestId` concurrently — sequence validation, spool append, and running-count update are one read-modify-write, and interleaving them double-appends or compares a replay against half-updated state
- Letting the abandoned-stream reaper delete a spool or release a reservation without taking the same per-`ingestId` exclusion a live call holds — eviction racing an in-flight `Chunk` or `Complete` corrupts exactly the state the exclusion exists to protect
- Asserting "the refusal created no state" by probing an identifier the refusal never issued — a refused `AttachmentIngestInit` returns no `ingestId`, so the observable is whether the next Init admits, never a fabricated id

## Acceptance Criteria

- [ ] Attachment ingestion produces stable artifact ids and manifests.
- [ ] Artifacts remain readable and attributable after the producing run ends.
- [ ] Large artifacts can be represented in the timeline without forcing full inline payload rendering.
- [ ] A file of any type stages — an archive, an SVG and a file whose bytes name no type alike — and a file offered as a picture in a format the bound provider takes goes to it as a picture.
- [ ] A boundary-crossing `ArtifactPublish` payload runs the §Ingest Validation And Payload Bounds (V1) pipeline over its decoded bytes, and a boundary-crossing publish declaring `artifactType: "file"` is refused and directed to `AttachmentIngest` rather than validated in a second place.
- [ ] An `AttachmentIngest` abandoned mid-trio leaves only a spool file that the daemon-local `mtime`-clocked reaper removes at TTL; no manifest, CAS entry, or carrier state survives it.
- [ ] The manifest of an accepted payload records the **derived** media type and byte size, not the declared ones, and a declared `mediaType` that disagrees with the bytes refuses nothing.
- [ ] Every payload-bearing member of this spec's local-wire interfaces is a JSON string — base64 (RFC 4648) or UTF-8 under an explicit encoding discriminator, never a binary field — an `AttachmentIngestChunk` carrying `max_attachment_chunk_bytes` raw bytes fits the Spec-006 frame ceiling after base64 expansion, and every byte bound binds the decoded count.
- [ ] A boundary-crossing `ArtifactPublish` whose serialized frame overflows the Spec-006 ceiling is refused at the transport — the predictable raw ceiling is the `base64` arm's ≈3 MB (fixed 4/3 expansion), while a `utf8` payload's serialized size is content-dependent under JSON escaping, so an escape-heavy `utf8` payload well under 4 MB raw is still refused when its escaped form overflows — while a `utf8` publish and a `base64` publish of identical decoded content hash to one CAS entry (the daemon decodes before hashing).
- [ ] An `AttachmentIngestInit` arriving at the open-stream count bound or with no room on the spool's volume beside the open streams' reservations is refused with `artifact.ingest_capacity_exhausted` (429) and leaks neither a count slot nor a reservation — asserted through **admission**, never through an identifier the refusal did not issue: after a count-bound refusal, terminating one open stream admits the next Init, and after a reservation-arm refusal, an Init whose declaration fits the freed room admits. A chunk pushing a stream's running decoded count past its Init-declared total is refused with `artifact.too_large` (413) and the spool is deleted.
- [ ] Two `AttachmentIngestInit` calls dispatched concurrently against one remaining slot (or one declaration's worth of remaining free disk) admit exactly one and refuse the other with `artifact.ingest_capacity_exhausted` (429) — the open-stream count and reserved-byte total never exceed `max_active_ingest_streams` / the volume's free space at any observation point.
- [ ] An exact replay of the last acknowledged ingest chunk is acknowledged idempotently without double-appending (the spooled bytes are identical before and after the replay); a sequence gap, regression, or same-sequence different-bytes chunk terminates the stream, and every subsequent call on that `ingestId` — as on an expired or unknown one, and every `Chunk` on a completed one — is refused with `artifact.ingest_stream_invalid` (409).
- [ ] An `AttachmentIngestComplete` retried after its response was lost replays the original response verbatim — the same `artifactId` and `contentHash` — with the pipeline re-run zero times and exactly **one** manifest row over the payload; past `max_ingest_stream_lifetime` the same retry receives `artifact.ingest_stream_invalid` (409), and a caller that then re-ingests the identical bytes ends with one CAS entry and a second manifest row, never duplicated bytes.
- [ ] Two calls on one `ingestId` dispatched concurrently through the client gateway are serialized rather than interleaved: an original and its retry racing after a lost response leave the spool byte-identical to the single-call outcome, and the reaper cannot evict a stream while a call on it is in flight.
- [ ] An ingest stream older than `max_ingest_stream_lifetime` is terminated at its next call regardless of how recently a chunk arrived — and, absent any call, is evicted by the next reaper pass, which releases its reservation and count slot and deletes its spool, asserted by an `AttachmentIngestInit` refused at the count bound before the pass and admitted after it — so neither a trickle of keep-alive chunks nor silent abandonment holds spool capacity past the lifetime bound.
- [ ] `Delete old data` on a session whose artifact payload a kept session's manifest also names removes the purged session's manifest and leaves the payload; purging the last session naming that payload reclaims the bytes.
- [ ] `Delete old data` on a session holding a derivative and its source removes both in one transaction, and no manifest is left whose `subject` resolves nowhere.
- [ ] An `ArtifactPublish` whose `subject` names a manifest outside the request's session is refused with `artifact.not_found` (404) — subject resolution is session-scoped — so a session's deletion sweep never encounters a derivative whose `subject` resolves outside the session.
- [ ] A purge whose post-commit unlink fails with a non-`ENOENT` error completes, and a later pass of the periodic orphan sweep reclaims the entry without a daemon restart.
- [ ] A caller-attributable artifact — ingested via `AttachmentIngest` or published via a caller-attributable `ArtifactPublish` — records the device the request came from in `artifact_manifests.created_by` at insert; a daemon-produced artifact records NULL.
- [ ] `Delete old data` removes each purged session's artifacts and manifests in one row-deletion transaction, with `secure_delete` on and a `TRUNCATE` checkpoint after commit ([Spec-020 §Ordering And Atomicity](./020-data-retention-and-gdpr.md#ordering-and-atomicity)), and reclaims every payload whose derived refcount reached zero, unlinking strictly after commit.
- [ ] A simulated crash between a reclaim's row-deletion commit and its payload unlink leaves every surviving manifest readable and no manifest pointing at missing bytes; the orphaned payload is gone after the next daemon boot's orphan sweep.
- [ ] A same-hash publish racing a reclaim's post-commit unlink never yields a manifest over missing bytes: a reference inserted before the reclaimer's in-exclusion refcount re-check aborts the unlink, and a writer arriving after the unlink misses the existence check and stores fresh bytes — asserted in both interleavings, and for the boot sweep under the same per-key exclusion.
- [ ] Every turn-scoped attachment carrier types its attachment list as `ArtifactId[]`; an element the turn cannot resolve or deliver appears as an explicit unresolved marker in its declared position, naming the cause, and element order is preserved end to end.
- [ ] A 4032 × 3024 JPEG carrying a GPS position, an orientation tag and a camera make and model is stored, drawn and sent byte for byte as it was attached.
- [ ] A picture the bound provider will not take is refused in that provider's own words.
- [ ] An ingest worker killed mid-file refuses that one file and leaves the daemon serving, and no two workers run at once.
- [ ] A PDF's quick look shows page 1 drawn to pixels with its page count, no PDF byte reaches a browsing context, and the agent receives the PDF unchanged; a PDF the worker cannot open shows its name alone.
- [ ] `session.attachmentCover` on a staged picture returns a new attachment whose pixels under each box are black, the uncovered copy is gone from the store, and the provider receives only the covered bytes; a sent picture's quick look carries no cover control.
- [ ] Another linked device lists a session's artifacts and reads a chat file's versions from the executing machine through Remote Control's method proxy, and no artifact payload is kept on the relay.
- [ ] The file surface draws its name line at once, reads `Loading the file…` until the version in view arrives, and a failed read reads `Could not load the file` with `Try again`.

## Artifact Rules

- A session's artifacts stay on the machine that runs the session, and every linked device reads them there through Remote Control's method proxy; nothing is replicated, relayed or wrapped per device.
- An artifact is never redacted in place; a redacted or summarized form is a separate derivative artifact. The one partial redaction is the cover of a staged picture before Send, which writes the covered copy as a new artifact and deletes the uncovered one, so the provider receives only the covered pixels.
- Every picture from outside the daemon is kept, shown and sent as its original bytes, and a PDF reaches the screen only as its first page drawn to pixels in a throwaway worker.
- The `artifactType` discriminator takes these values — the five families above plus `workflow_output` ([Spec-015 §Output Mode Specification](./015-workflow-authoring-and-execution.md#output-mode-specification)). The typed union that carries them is in [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md).
- **Attachment ingest takes any file, and the server derives and never trusts.** §Ingest Validation And Payload Bounds (V1) reads each file's type from its bytes and records that, never the caller's declaration, and refuses nothing for its type: the derived type decides only whether a file offered as a picture goes to the provider as a picture and what the manifest records. How many files a message carries and how large one may be are what the daemon and the provider accept, with no figure of the app's own. Archive interiors are deliberately not introspected in V1, which removes the zip-slip and symlink classes from the reachable surface rather than defending against them.
- **No single-artifact delete; payload reclaim is a derived refcount; a derivative goes with its source.** A session's artifacts are its record of what it made, each write kept as a version, so no person deletes one and no method does: they go with their session through `Delete old data` or `Erase all data`, and the cover removes the uncovered copy of a staged picture. Two couplings are resolved rather than left implicit: the shared-CAS refcount is **derived from surviving reference rows, never a stored counter** (a counter is a second source of truth whose drift deletes live bytes); and a derivative is deleted with its source in the same transaction, never left behind with a nulled `subject`, which would silently convert it into an apparent original and destroy the provenance the derivative-not-mutation rule exists to preserve.
- **Turn-scoped attachment references are `ArtifactId[]`, ordered, with no silent drop.** This spec owns the **element type and the delivery contract** — an id into this spec's manifest space, caller-declared order preserved, and an undeliverable element surfacing as an explicit unresolved marker in its declared position rather than vanishing. The **carrier-side wire fields are not defined here**: those arms live in the driver-boundary contracts other plans own, and each arm's typing lands under its owning plan.

### Primary sources — the `ArtifactId` encoding (accessed 2026-09-08)

- [RFC 9562 — Universally Unique IDentifiers (UUIDs)](https://www.rfc-editor.org/rfc/rfc9562) — the normative definition this spec's `ArtifactId` accept set is stated against, superseding RFC 4122. [§4 UUID Format](https://www.rfc-editor.org/rfc/rfc9562#section-4) fixes the 128-bit layout and the ABNF for the "hex-and-dash" text form, and states that its hexadecimal characters may be "uppercase or lowercase" — which is why the accept set is case-insensitive rather than a lowercase convention; [§4.1 Variant Field](https://www.rfc-editor.org/rfc/rfc9562#section-4.1) and [§4.2 Version Field](https://www.rfc-editor.org/rfc/rfc9562#section-4.2) locate the variant and version bits (the version number in "the most significant 4 bits of octet 6"), which is what makes "any RFC 9562 form" a decidable predicate over a string rather than a vague allowance — a control-plane `gen_random_uuid()` v4 and a daemon-minted v7 differ only in those bits. The v4 half of that premise is PostgreSQL's own: [PostgreSQL §9.14 UUID Functions](https://www.postgresql.org/docs/current/functions-uuid.html) documents `gen_random_uuid()` as "Generates a version 4 (random) UUID" (and `uuid_extract_version()` on such a value "will return 4"), so the accept set's reason for admitting a version beyond the daemon's v7 is verifiable against the function's own documentation and not only against this repository.
- [RFC 9562 §5.7 — UUID Version 7](https://www.rfc-editor.org/rfc/rfc9562#section-5.7) — the version this spec requires the daemon to mint: "a time-ordered value field derived from the widely implemented and well-known Unix Epoch timestamp source", allocating "a Unix timestamp in milliseconds in the most significant 48 bits" with the remaining 74 bits random or, optionally, sub-millisecond-plus-counter for intra-millisecond monotonicity. The time-ordering property is the reason a minted manifest id is v7 rather than v4; acceptance is deliberately wider than minting, so this spec never refuses a well-formed id another RFC 9562 generator produced.
