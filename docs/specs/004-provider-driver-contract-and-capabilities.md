## Purpose

Define the normalized driver boundary between the core runtime and provider-specific execution transports.

## Scope

This spec covers required driver operations, capability advertisement and the grade of every operation on every driver, normalized event shapes, runtime binding persistence, the providers and every place that lists them, and the bridge to work a provider runs in its own cloud.

## Non-Goals

- UI behavior for every capability
- Provider-specific prompt tuning
- Provider commercial or billing concerns. Pricing, plan selection, invoicing, and what a provider charges remain out of scope. Two adjacent facts are **in** scope, because both are driver-contract surfaces rather than commercial ones: the typed provider usage-limit signal (§Fallback Behavior), which is a pacing fact the runtime must act on rather than a billing figure, and the provider-account identity a run is spawned against (§Interfaces And Contracts), which selects a credential environment. Neither carries a price, a rate, or an amount owed. What is spent and what it cost belong to [Spec-014 §Session Cost Receipt](./014-multi-agent-orchestration.md#session-cost-receipt); which account paid and under which billing mode belong to [Spec-026 §Billing mode](./026-provider-accounts-and-credential-homes.md#billing-mode).

## Required Behavior

- Every provider integration must implement a normalized driver contract.
- Provider drivers must execute within a user-owned or operator-owned runtime node governed by a local daemon. V1 must not depend on a shared hosted driver service as the execution authority.
- The driver contract must support create session, resume session, start run, interrupt run, `applyIntervention`, respond to interactive request, close session, and enumerate models or modes or both where available.
- The `applyIntervention` operation is a generic dispatcher that routes intervention requests (steer, interrupt, cancel) to the appropriate driver-specific handler based on the intervention type and the driver's declared capabilities. `cancel` maps to the `interrupted` terminal state in the run state machine — it is a user-initiated interruption. A driver that cannot deliver a given intervention type **at all** — neither through a provider verb of its own nor through the orchestration leg above it — must return a `degraded` result, allowing the orchestration layer to fall back to queue plus interrupt, and **neither V1 provider reaches that path** ([Spec-003 §Default Behavior](003-queue-steer-pause-resume.md#default-behavior), §Fallback Behavior below). **The test is delivery, not nativeness:** a driver whose capability flag is `false` because that capability is delivered above it still delivers the intervention, and reports `applied`. The driver-level result vocabulary is exactly `applied | degraded`; `rejected` and `expired` are orchestration-layer verdicts rendered by the daemon's authorization and version-guard checks around driver dispatch and are never returned by a driver — the normative mapping onto the six-state intervention lifecycle lives in [Queue And Intervention Model §Driver Result To Lifecycle Mapping](../domain/queue-and-intervention-model.md#driver-result-to-lifecycle-mapping).
- The contract additionally defines capability-gated parity operations — `rewindConversation` (the undo's conversation cut, made in place on the session's live runtime binding by the provider's own cut; gated on the `rollback` flag), `setSessionGoal` / `clearSessionGoal` (the provider's own goal for the agent it is sent to; gated on `session_goals`), `replayTranscript` (canonical-transcript reconstitution into a fresh provider session; gated on `transcript_replay`), and `forkConversation` (the provider leg of forking a session, serving [Spec-001](001-session-core.md)'s `session.fork`; gated on `session_fork`) — plus a zero-turn `probeAuth` required of every driver, since provider authentication state must be knowable without spending a billed turn. Dispatch of a capability-gated parity operation follows the same static/dynamic split as interventions ([Queue And Intervention Model](../domain/queue-and-intervention-model.md)): a call against a flag the driver does not declare is refused statically with `driver.capability_unsupported` before driver dispatch — with exceptions, each an undeclared arm with a named daemon-side fallback that settles `degraded` rather than refusing ([ADR-029 §Enumerated Gates And Fallbacks](../decisions/029-canonical-transcript-is-authoritative.md#enumerated-gates-and-fallbacks)): `replayTranscript`, on the hand-over brief (§The hand-over brief is the floor, and it is visibly a floor), and `forkConversation`, on the canonical transcript replayed into a second fresh session, the source left untouched; `rewindConversation` and the goal pair have no orchestration fallback and refuse — while `degraded` is the dynamic outcome of an invoked driver that could not deliver the operation natively and reports the fallback it took — never an opaque failure.
- Every intervention request carries a mandatory requester-generated `clientIdempotencyKey` (UUID) — generated by the user client, or by the daemon’s origination path for system interventions (orchestration budget and idle interrupts per ADR-011), which reuses its synthesized key across its own retry loop. The daemon applies replay-or-conflict semantics — an identical retry returns the originally recorded outcome without re-dispatching the driver; reuse of a key with a differing payload is rejected as `intervention.idempotency_conflict` — following the converging idempotency-key practice ([Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests); the expired IETF draft [draft-ietf-httpapi-idempotency-key-header](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)). The key rides through `ApplyInterventionParams` so drivers can propagate it to provider-remote invocations that honor dedupe keys (the `compensable` pattern, §Tool Metadata).
- Every `getCapabilities` report must include `cliVersion` — a `DriverCliVersionReport` carrying the verbatim provider-reported version string (`raw`) and its parsed semantic version (`semver`). The daemon enforces a per-driver minimum-version floor mechanically at attach and refresh (semantic-version comparison against the configured floor; V1 floors: Claude Code `2.1.234`, codex-cli `0.141.0` — set by this spec and mirrored by the nightly compatibility check's `floor` legs). An unparseable version report fails closed: the report cannot be constructed (`semver` is required, so unparsed-but-attached state is unrepresentable), the driver refuses attach, and the failure surfaces as `driver.cli_version_unparseable`. A version that parses cleanly but sits below the configured floor likewise refuses attach/refresh fail-closed, surfacing as `driver.cli_version_below_floor` (distinct from `version.floor_exceeded`, which governs client/event-envelope contract floors, not provider CLI installs).
- **The floor is this spec's to set; the pin is the reference family's to record.** They answer different questions — the floor is the oldest build the driver accepts, the pin is the newest build whose shapes were verified — and they move independently, so a re-pin records what was measured without raising what is supported. A governing document therefore **states a floor and cites a pin**: the floors above are values this spec sets, and every version number a spec or plan names for a _measured_ provider surface is a citation of [`claude.md`](../reference/provider-wire/claude.md) / [`codex.md`](../reference/provider-wire/codex.md) rather than a copy of one, because a copied pin is a value the next re-pin cannot reach.
- **A build at or above the floor is admitted, and a build above the pin is not a refusal condition.** The floor comparison is the whole of the version gate: at or above it the driver attaches, whether or not the build is one this corpus has measured. Newer-than-measured is the **expected** state rather than an exception — both vendors publish faster than any authoring pass can re-verify — so a driver that refused an untested build would refuse most of its own installed base within weeks. What an untested build changes is not admission but confidence: its capabilities are decided by the per-capability rule below rather than inherited from a table, and a surface that moved withdraws **that one capability**, never the session. This is the all-or-nothing-free policy the [provider-wire reference](../reference/provider-wire/README.md#versioning-and-pinning-policy) family states; the sentence here is its normative statement, and the two must not diverge.
- **Every optional capability is decided by a declared per-capability detection mechanism, and the report records how each flag was decided.** A flag declared from a static per-driver table is a claim about a build the table's author measured, not about the build that is running. Each flag on `GetCapabilitiesResult` therefore carries a **detection source** — a closed two-value `static | probed` — and each flag's mechanism is **declared per capability rather than assumed uniform**, because probeability is a property of the capability, not of the build. A probe is **admissible** only when it is all three of: **zero-turn** (it establishes availability without starting a model turn, and so is zero-billed); **non-mutating** (it changes no state the session owns — an operation whose defined effect is to _replace_ a set is not probeable by invoking it with an empty set, because the probe would perform the replacement); and **decisive at the granularity the capability is consumed at** (a capability whose contract depends on a parameter is not decided by the method's presence, so an enumeration that lists the method establishes the method and not the parameter). A flag with no admissible probe is declared `static` **by construction and by declaration** — the mechanism table names the conjunct that fails — and is left to its invocation-time refusal. `static` is therefore a stated property of a capability, never a silent fallback for a probe that was not written. Both providers expose such a channel at the pin (Verified 2026-08-26): the Claude control-request dispatcher answers an unknown subtype with a typed `Unsupported control request subtype: <name>` and a supported one with `success`, on the driver's own streaming-input transport and with no user message sent; the Codex app-server answers an unknown method with `-32600` **enumerating the accepted method set**, so one malformed request enumerates the surface. A probe is admissible only alongside a **negative control** — a deliberately unsupported name that must still be refused — because a probe that silently stopped probing reports every capability available. Failure is per capability: a probe that refuses withdraws exactly the flag it probed. Nothing is minted for this: an invocation against a withdrawn capability refuses as the already-registered `driver.capability_unsupported`, and a flag that moves `true` → `false` between two readings is written to the driver's stored capability snapshot, which is what the next read serves.
- **Registry membership is neither necessary nor sufficient for availability.** The reference family records the sufficiency half — a subtype present in a build's own registry can still be refused at call time. The **necessity** half is the sharper one: the `mcp_set_servers` control request answers `{ "subtype": "success", … }` at `2.1.234`, `2.1.245`, and `2.1.246` while appearing in **none** of those builds' censused subtype registries. A census is therefore a lower bound on availability exactly as a registry is an upper bound on it, and neither direction may decide a capability. What decides it is the flag's declared mechanism: an admissible probe's own classified answer where one exists, and the matrix reading the mechanism table declares otherwise. That measurement is authoring-time evidence, not a runtime mechanism: an empty `mcp_set_servers` would clear a live session's servers, so no probe issues it. It is also why `mcp_set_servers` is **not** a capability flag: it is a control-request subtype the driver sends only to install the session's own server set, right after start and after each resume, and no flag is decided by sending it.
- **The version a driver reports is the version that spawned.** The driver resolves the executable, spawns it, and reads the version **in-band from the running process** — Claude's `get_binary_version` control request returns that build's own `version` and `buildTime`; Codex's `initialize` result returns a `userAgent` **containing** the running `codex-cli` version — both zero-turn. The two readings are not symmetric, and the spec says so rather than papering over it: the Claude channel is structured (`{ version, buildTime }`), while the Codex channel is a **composite** string that also carries the caller's own client name and version, so a driver reading it MUST extract rather than adopt. Codex's structured alternative is not available to V1 — `server/diagnostics` is gated on the `experimentalApi` capability and, granted it, returns process gauges carrying no version at all (Verified 2026-08-26 at `0.149.1`) — so the composite `userAgent` is the only non-experimental in-band channel, and the extraction rule is a normative obligation on the driver rather than an implementation detail. A launcher symlink or wrapper is not an acceptable source: at this pin `claude --version` names the launcher's current build, which is measurably not the build a path-addressed spawn runs, and that divergence is how the reference file's own census target and `claude --version` came apart. One reading serves both consumers — it is what the floor comparison compares and what the run's `runtime_bindings` row records (`cli_version_raw` / `cli_version_semver`, with the resolved executable path on the daemon-owned `spawn_config` carrier) — so the recorded version can never describe a different install from the one that ran, and a replay reads what actually ran. No column is minted; both carriers already ship.
- **Provider auto-update is disabled in every driver-spawned child.** The daemon owns the spawn environment for every provider process, and every such environment sets that provider's documented auto-update opt-out — for Claude Code, `DISABLE_AUTOUPDATER=1` and `DISABLE_UPDATES=1` ([Claude wire reference](../reference/provider-wire/claude.md), presence-style gates). A build that replaces itself mid-session invalidates two things at once: the version recorded on the run's binding stops describing the process, and the capability snapshot the run was admitted against was probed from a binary that is no longer executing. Suppression is a correctness obligation, not hygiene. Where a provider documents no opt-out, the driver reaches the same guarantee by resolving and spawning an **exact build path** rather than a floating launcher; a driver that can do neither declares no `probed` flags, because it cannot promise the probed build is the running one.
- **The Codex posture rides the `permissions` profile, and `sandboxPolicy` is never sent.** Codex `turn/start` carries both a legacy `sandboxPolicy` and a preferred `permissions` profile selection, and the vendor's generated schema states they cannot be combined. Which member is even sendable is a property of the negotiated connection: on a **default** connection `permissions` is refused **by name** — `-32600 turn/start.permissions requires experimentalApi capability` — so the Codex driver's `initialize` carries the `experimentalApi` capability. At the levels below `yolo` the driver starts every conversation with `permissions: <that level's deny profile>` at `thread/start` and reads the profile back from `activePermissionProfile` on the `thread/start` and `thread/resume` replies and on `thread/settings/updated`, never from the legacy `sandbox` view, which does not show a profile's read-only folders; a reply naming no profile is refused as a start fault. It never sends `sandboxPolicy`: on an `experimentalApi` connection a `turn/start` carrying it is accepted and enforced, but `activePermissionProfile` reads back `null` and the level's read-only folders drop, and the two sent together are refused with `-32600` (measured at `codex-cli 0.156.0`). A profile named on a `turn/start` is a thread setting that holds for every later turn and across a restart, so the only per-turn `permissions` the driver sends are the ones plan mode derives (§Plan mode and the plan verdict). A per-turn `sandboxPolicy`, or a `permissions` the daemon did not derive, is a posture-affecting field the daemon did not derive — refused rather than passed through ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior) owns the daemon-side half). The removed `permissionProfile` field is not an option either: it refuses `-32602` on both connection kinds.
- Every driver must implement `probeAuth` — a zero-turn authentication probe returning `DriverAuthProbeResult` (`authenticated | unauthenticated | indeterminate`). `indeterminate` (probe surface unavailable or unparseable) is treated as not authenticated for admission — fail closed — while remaining distinguishable so operators can separate probe health from credential state. Run admission against a driver that does not probe `authenticated` is refused as `driver.not_authenticated` before any turn is spent.
- The Codex driver pins `approvalsReviewer: "user"` at `thread/start`, the moment a conversation is opened inside the account's service, at every permission level but Reviewed, so every approval routes through the daemon's approval pipeline ([Spec-010](010-approvals-permissions-and-trust-boundaries.md)). The generated protocol's own default is already `user`, so the pin is defense-in-depth against a config/profile override. Reviewed is Codex's own Approve for me: the conversation runs Codex's own automatic reviewer — `codex-auto-review` on a ChatGPT login and `gpt-5.6-luna` on an API key, Codex's own defaults — which approves routine work, blocks the rest and tells the agent why, and a block can be allowed once. The driver forwards what Codex does with it, a refusal in Codex's own words, and adds no reviewer of its own; the reviewer's requests are held with their exact tokens until the maintained price list prices its model. Every ask that reaches the daemon still takes the daemon's approval pipeline, and no reviewer notification ever settles one.
- **At Reviewed, both drivers capture a block by the provider's own reviewer, keep the provider's denial, and carry `Allow once` by the provider's own means.** Claude Code's reviewer is its auto-mode classifier: the driver registers Claude Code's `PermissionDenied` hook on the wire, which receives the blocked call's exact input, and reads the result's `permission_denials`. Codex's reviewer is `codex-auto-review`: the driver reads `item/autoApprovalReview/completed` with status `denied` or `timedOut`. Each block becomes one `approval.reviewer_denied` record ([Spec-010](010-approvals-permissions-and-trust-boundaries.md)) carrying the reviewer's reason in the provider's own words — Claude Code's denial reason, such as `[Data Exfiltration]`; Codex's review rationale — and the daemon keeps the provider's own denial with it, so an override still works after a restart. A block the provider does not let a person overrule is recorded as not overridable: Claude Code's block without a classifier verdict, and Codex's review that timed out. `approval.denialOverride` tells the agent it may try that one action again, and the daemon records the override as `approval.denial_overridden`: on Claude Code the driver sends the sentence Claude Code's own Recently denied list sends, `Permission granted for: <the action>. You may now retry this command if you would like.`; on Codex it calls `thread/approveGuardianDeniedAction` with the review Codex sent, as Codex's own `/approve` does, and Codex's reviewer still reviews the retry. The override reaches a running turn at once — a steer on Claude Code, Codex's own injection — and starts a turn when none is running, with that sentence as the turn's input on both; the sentence is the daemon's and is never drawn as the person's message. The agent decides whether to retry, and nothing runs by itself. When the reviewer blocks too often, each provider's own fallback runs and is forwarded: Codex interrupts the turn with its own warning, and Claude Code, after 3 blocks in a row or 20 in a session, asks instead, through the ordinary approval card.
- **The Codex driver's event normalizer maps Codex's reviewer warning and required review to `moderation.review_flagged`.** A `guardianWarning` is recorded with `signal: "review_warning"` and Codex's words as sent. An `autoApprovalReview/strictReviewRequired`, which carries no words, is recorded with `signal: "review_required"` and the sentence Codex's own app writes for it, `This request requires additional safety checks, some tool calls might take extra time`. The normalizer pairs each warning with the review Codex completes right after it and records none for a warning that reports an approval or one about an action the reviewer blocked, because a block's words land on the blocked action's own row. `item/autoApprovalReview/started` and `item/autoApprovalReview/completed` feed the block record above and never this event, and `turn/moderationMetadata`, a display hint with no words, goes to the daemon's log and to no session event. Claude Code sends no such signal.
- Spawn/turn parameters carry the parity surfaces: a session callback-tool registry (`SessionCallbackTool[]` — the daemon exposes a curated tool set into every run; reaching both legs as tools of the daemon's one MCP `url` entry per session — on Claude Code the one entry `--mcp-config` carries, on Codex a `url` entry in the conversation's `mcp_servers` table at `thread/start`, never Codex's `dynamicTools`; every callback invocation flows through the daemon's approval pipeline per [Spec-010](010-approvals-permissions-and-trust-boundaries.md) and lands as ordinary `tool_activity` rows per [Spec-005](005-session-event-taxonomy-and-audit-log.md)), a `subagentPolicy { enabled, maxDepth?, maxConcurrent?, definitions[] }` pass-through under the single-supervisor invariant (the daemon is the only cross-session supervisor; orchestration semantics land in [Spec-014](014-multi-agent-orchestration.md)), and the run's `executionPosture` (shape owned by this spec and typed in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md); authorization and policy semantics in [Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)).
- Drivers must emit normalized runtime events rather than leaking provider-native event types into the session engine.
- Drivers must declare capability flags for at least `resume`, `steer`, `interactive_requests`, `mcp`, `tool_calls`, `reasoning_stream`, `model_mutation`, `structured_output`, `rollback`, `session_goals`, `callback_tools`, `subagents`, `transcript_replay`, `context_compaction`, `provider_commands`, `output_speed`, and `session_fork`. A flag declares that the driver delivers the capability through its own mechanism at the driver boundary — natively or driver-emulated; **how** it delivers is recorded as a mechanism grade on the parity capability matrix (a capability delivered by the orchestration layer above the driver keeps its driver flag `false`). The `pause` flag is intentionally excluded — no current provider implements native pause. Pause is an orchestration-layer construct (interrupt run, persist state, queue resume) that does not require driver support.
- Drivers must persist provider-owned resume handles separately from canonical session and run ids.
- The runtime must treat undeclared capabilities as unsupported.
- Drivers must declare a per-tool `idempotency_class ∈ {idempotent, compensable, manual_reconcile_only}` alongside their tool list. This metadata controls crash-recovery behavior for in-flight side-effecting tool calls; see [Spec-013 § Idempotency Protocol](013-persistence-recovery-and-replay.md#idempotency-protocol) for recovery semantics.
- **Provider-bound user text reaches the model as prose, or the turn fails visibly.** Text a user authored — a run's opening content, a steer directive's content, and admitted queue content re-entering through run start — is data _for the model_, never an instruction to the provider's own client. Where a provider's programmatic input surface also parses client-side commands, a message whose first word is command-shaped is consumed by that parser and the user's words never reach the model; the observed failure is silent, returning a zero-turn success rather than an error (Claude Code `2.1.245`, verified 2026-08-25). Every driver must therefore route provider-bound text through a single **outbound frame boundary**, and a driver whose provider command-parses that surface must neutralize command-shaped user text there so the provider parses it as prose. The boundary and the tripwire below are **universal**; the transform itself is **grade-scoped** to the drivers whose mechanism grade requires it (§Parity Capability Mechanism Grades). A driver graded `native` on that row passes the author's bytes through unchanged — prepending a sentinel a provider does not need would alter text it would otherwise have delivered exactly. Because the grade is the behavioral input here rather than a bare record, **that row states the grade governing today, never the one a provider is expected to earn**: a `native` claim resting on any frontend other than the transport the driver actually drives is recorded `emulated` until a probe of that transport confirms it, and the confirming re-grade is an ordinary update. The default is therefore the transform and not its absence, because a spare newline on a prompt costs nothing and a skipped one costs the whole message. And the grade is a claim the tripwire keeps honest rather than one that is trusted: a `native` driver whose provider starts command-dispatching after an update trips exactly as an `emulated` one does, and the remedy is re-grading it, not discovering the loss from a user. **Command-shaped** is one predicate with one implementation shared by every driver, so two drivers can never classify the same message differently: the frame's first non-whitespace byte is `/` (`0x2F`), where **whitespace is exactly the six ASCII bytes** `0x09` (tab), `0x0A` (line feed), `0x0B` (vertical tab), `0x0C` (form feed), `0x0D` (carriage return), and `0x20` (space) — skipped from the frame's first byte until the first byte that is not one of them, which decides. Enumerating that set is load-bearing rather than pedantic: _whitespace_ is the one term in this predicate two drivers could read differently, and a byte-level rule may not appeal to a Unicode property without the decoding this rule forbids. A frame led by a non-ASCII whitespace character — a UTF-8 no-break space, say — is therefore **not** command-shaped here, and that residual is left to the tripwire deliberately rather than closed by guessing at a wider set: should a provider ever be observed trimming such bytes before its own command parse, the trip is loud, the turn fails visibly, and the remedy is widening this enumeration against an observation — where widening it today would trade a named residual for an unnamed one. It is deliberately that coarse. It is byte-level and locale-independent — it never decodes, normalizes, or case-folds — and it consults no list of known command names, because an unknown name is precisely the case that fails silently. It draws no distinction a provider might not draw: `/foo`, `/foo:bar` (the plugin-qualified command form), and the path-like `/etc/hosts` are all command-shaped, because the only cost of neutralizing prose is one invisible byte on the wire while the cost of missing a command is the whole message. A slash anywhere but the first non-whitespace position is not command-shaped. Neutralization is **transport-only**: it changes only the bytes on the provider wire, never the canonical text this repo persists, events, replays, rewinds to, or shows a user, so an audit row and a rollback target carry exactly what the author typed. This is a **delivery-correctness** rule, not the provider-specific prompt tuning §Non-Goals excludes: the transform changes no word the author wrote, and it applies only where the alternative is the message not arriving at all. The V1 sentinel is a single leading newline — the smallest edit that defeats the parse. Should a provider build ever parse through it, the escalation ladder is ordered by decreasing invisibility and increasing honesty: leading newline → leading space → structural repositioning of the command-shaped word → a visible, documented prefix → a typed refusal. A driver never silently drops the message, and a driver that exhausts the ladder grades this capability `absent` and refuses command-shaped user text loudly rather than delivering it mangled. Reaching a provider's own command surface _deliberately_ is a separate concern this spec does not open: the composer-level escape is [Spec-015](015-workflow-authoring-and-execution.md)'s C-18, which activates on provider-bound composer paths once this neutralization ships.
- **Neutralization is decided by a closed frame origin, and an unknown origin neutralizes.** Every outbound provider frame declares exactly one origin — `human_text` (neutralized), `driver_command` (a command routed verbatim and exempt from the tripwire below, so the provider's own command surface stays reachable), or `system_narration` (daemon-composed prose, neutralized). An absent or unrecognized origin **neutralizes**: a frame nobody classified is far likelier to be user text than a driver command, and neutralizing a command wrongly costs a visible no-op where skipping neutralization wrongly costs a silently swallowed turn. The discriminator is deliberately **not** a capability flag — an undeclared flag resolves through this section's undeclared-is-unsupported rule to "not neutralized", which is the fail-open polarity. **The `driver_command` arm has exactly two producer classes, and they are guarded differently because they claim different things.** The first is a command the **driver itself** composed from a typed daemon intent to realize a daemon operation — user-triggered context compaction and the goal on the Claude leg are the V1 cases, and a console word adapted onto a provider's own mechanism is the third (§The provider command and skill surface). Such a frame claims an effect, so it is guarded on both sides and both guards are obligations rather than advice: **before** dispatch, the command's literal name must be present in the provider's own enumerated command set for that session's binding (§The provider command and skill surface — an enumeration the driver already reads, which is what makes this checkable instead of a hardcoded string the next provider release can retire beneath), and **after** dispatch the operation completes only on the provider's own typed evidence that the command ran, never on the frame settling. A driver that can satisfy neither guard declares the capability `false` and refuses; it does not dispatch a command it cannot confirm. The second class is an enumerated command the **user** chose, forwarded verbatim so the provider's own client dispatches it. That frame claims nothing, so neither guard applies to it and neither is waived: it needs no presence check because the user picked it out of the enumeration itself, and it needs no evidence contract because the driver reports the provider's own answer and asserts no effect. What it must not do is report an effect, and a driver that synthesized a success for such a frame would commit exactly the error the tripwire exists to catch. `system_narration` — daemon-composed prose on the same channel — carries exactly **one** V1 producer, audited rather than assumed: the **hand-over brief** (§The hand-over brief is the floor, and it is visibly a floor), which is a turn on the text-input channel composed by the daemon, declares `system_narration` at the outbound frame boundary, and is neutralized like any other daemon-composed prose. The transcript file the daemon writes beside that brief is not a producer here at all: it is a file the new provider opens for itself, and no frame carries it. The one path that might look like a producer is not: `respondToRequest` delivers a structured reply correlated to a `requestId` rather than a turn on the text-input channel. No goal text reaches a provider as narration either: on the Claude leg the goal is the provider's own `/goal` command on a driver-composed `driver_command` frame, and no goal is ever composed into a system prompt. It is kept distinct from `human_text` even though the two neutralize identically, because when the tripwire fires the frame record must say _whose_ words failed to arrive — a policy-composed answer ever delivered as text would otherwise be filed as the user's.
- **The neutralizer's effect is verified at runtime, not assumed.** A transform is a claim about a provider parser the daemon neither owns nor pins, and a provider update can change that parser between two runs of the same install. Each outbound frame therefore carries a daemon-minted correlation value, and the driver classifies the provider's response to that frame. **The classification asks for positive evidence of a model turn, never for a recognizable command dispatch.** The set of shapes in which a provider can say _I handled that as my own command_ is open, undocumented at the versions this repo pins, and free to grow with the next release, so a detector that enumerates it is stale on arrival and fails open — silently, in exactly the shape this rule exists to end. The set of shapes that evidence a model turn is closed, small, and already parsed by the normalizer to do its ordinary work. The burden is therefore inverted: a correlated frame that **settles** with no typed event attributing model output to it has tripped, whatever the provider called what it did instead. The classifier reads **typed fields of the provider's own response envelope** and never message prose, which §Pitfalls To Avoid forbids for the same localization and wording-drift reasons it forbids text-matched quota refusals; a response envelope whose shape the driver does not recognize therefore trips rather than passing, and a driver that would rather not trip on an unrecognized shape pins the turn-evidence discriminants for its provider instead of relaxing that polarity. Which typed fields those are is per-provider implementation work the driver records and re-probes, not a set this spec can enumerate: the pinned provider-wire references document no such discriminant at the versions this rule was authored against. One dispatch shape **is** named normatively, as the rule's conformance instance rather than as its definition — the **zero-turn synthetic reply**: a settled correlated frame whose response envelope carries a client-composed reply item, no model-turn attribution for that frame, and no token usage accounted to it. That is the shape observed first-party on Claude Code `2.1.245`, and the recorded transcript of it is the **conformance fixture** every driver's classifier must trip on. Naming it does not narrow the rule to it: a frame that settles in any other shape without turn evidence trips just the same, so the fixture proves the detector present without becoming the enumeration this rule refuses to build. **A trip fails the run, and there is one landing for both paths.** The daemon emits the run's ordinary `run.failed` terminal carrying `failureCategory: 'provider failure'`, a `recoveryCondition` of `recovery-needed`, and a `providerFailureDetail` in **one fixed daemon-composed form**: the registered `driver.text_neutralization_failed` ([Error Contracts](../architecture/contracts/error-contracts.md)), one space byte (`0x20`), then `origin=` followed by one of `human_text`, `system_narration`, or `unknown` — so `driver.text_neutralization_failed origin=human_text` is the entire detail. Writing the form down is what makes _machine-readable_ true rather than claimed: a consumer reads the cause as the substring before the first space and the origin as the substring after `origin=`, and an origin the closed union does not name is recorded as the literal `unknown` rather than echoed, which keeps a string the daemon did not compose out of the audit log. `driver_command` can never appear, those frames being exempt. The form binds **this cause only** — `providerFailureDetail` stays free-form prose for the resume failure that introduced it ([API Payload Contracts](../architecture/contracts/api-payload-contracts.md)). That is the handoff §Fallback Behavior's resume failure already uses — a typed driver-side condition surfaced on the canonical run-lifecycle surface where consumers already subscribe — so the trip mints no driver event, no new result **status**, and no persisted column. It mints no state transition either: `starting -> failed` and `running -> failed` are both already declared ([Run State Machine §Complete Transition Table](../domain/run-state-machine.md#complete-transition-table)), and those are exactly the two states a provider-bound frame can be in flight in — a run's opening frame can settle before the `starting -> running` transition is recorded, and a steer targets a `running` run by definition. It is emphatically **not** a JSON-RPC error on either path, and the run-start path is the reason the landing had to be asynchronous at all: `startRun` is a daemon-internal lifecycle operation with no wire method behind it, and a run reaching it from the queue or from orchestration has **no caller waiting on a response** — the user who authored the text may be offline, and a system-originated run has no user at all. A synchronous refusal has nobody to refuse to. The run's own `run.failed` event is therefore the surface, delivered to whoever is subscribed whenever they subscribe, which is what an asynchronous run outcome means here. An intervention does have a caller, so it answers on its own result branch as well. That intervention settles `degraded` on the existing zero-effect arm — the frame was dispatched, which puts pre-dispatch `rejected` definitionally out of reach ([Queue And Intervention Model §Driver Result To Lifecycle Mapping](../domain/queue-and-intervention-model.md#driver-result-to-lifecycle-mapping)) — with no `fallbackAction`, because no fallback exists: re-sending the same text meets the same parser. It carries the cause **on that response**, through one additive-optional member the driver result envelope gains here: `refusalCode`, a **closed literal union** whose sole V1 member is `driver.text_neutralization_failed`. A closed union rather than a free-form string is the load-bearing choice — the envelope parses untrusted provider output, and a code the daemon selects from a fixed set can never smuggle provider-composed text into an audit record, so this member needs no length bounding and adds no free-form surface. The `status` vocabulary is untouched at `applied | degraded`, the envelope keeps `.strict()` — a **declared** optional key is not an unknown one, which is the only thing strictness rejects — and the daemon's intervention-result mapper reads it onto the caller's response. The member is **best-effort by construction, and the run terminal is the guarantee**: `refusalCode` is present only when the trip is classified before `applyIntervention` resolves. A driver must not hold that call open waiting for its correlated frame to settle — a healthy steer joins a model turn and settles when that turn ends, which can be minutes, so awaiting settlement would convert every ordinary intervention into a long poll and would make the neutralizer's own verification the slowest thing on the intervention path. The asymmetry is what makes the member worth having anyway: the tripped case is the fast one — a zero-turn synthetic reply settles immediately, well inside the call — so the classification is in hand exactly when there is something to report. A consumer that must not miss a trip subscribes to the run: `run.failed` is the surface on both paths and the only one a consumer may depend on, and no reader may treat an absent `refusalCode` as evidence that no trip occurred. Recording the cause twice, on the response and on the run terminal, is deliberate: the caller of a one-shot intervention should not have to subscribe to a run's event stream to learn why its text was not delivered, and the terminal is what a later reader replays. **A tripped intervention fails the run too, and that is worth arguing for, because the opposite reads as the kinder choice.** The tempting argument is that a misfired steer touched nothing, so failing the run destroys work the misfire never harmed — but the hazard is precisely that the provider _dispatched_ the frame, so it may have executed an unrecognized client-side action against the session state the run depends on, and a context clear or a model switch would leave every later turn running against a session this daemon still believes it understands. `recovery-needed` names that exactly: a human reconciles before the run continues. **The runtime binding is quarantined with it.** Failing the run alone would not be enough — the run ends, but the provider process holding the possibly-mutated client-side state stays alive, and the next run admitted against that session would bind straight back to it. So the trip also **disposes the run's live runtime binding**: the driver closes the provider session, which removes the process from the live provider-process registry, and returning to work means a fresh spawn — which is exactly what _operator restarts the session_ means mechanically. **Disposal is a process fact, not a row state, and deliberately so.** `runtime_bindings` carries no liveness column and must not gain one: the binding store returns every row for a run — superseded pre-relaunch history included — and rules that the **caller** owns the liveness intersection against the process supervisor's live provider-process registry before any fan-out or delivery, which is already what keeps a dead or superseded row from reaching a live leg. A disposed binding is therefore excluded from every such path by machinery the store already ships, with no flag for a caller to forget and no column for this rule to mint — and that is also why the refusal takes no attach-time arm: telling _disposed by this trip_ apart from _dead for any other reason_ at attach time would need exactly the persisted marker being refused, which is why [Error Contracts](../architecture/contracts/error-contracts.md) records this code as riding no error envelope on any path. The row itself survives as the history it is, holding the provider resume handle and the realized spawn configuration the audit record needs. **Disposal strands no specified path, because it creates no new state.** The trip leaves the run in `failed`, and `failed` has no exit. Two exits from a terminal state exist, each keeping the run id: a send into an `interrupted` run, which returns it to `running` with everything it knew, and a send into a finished child run's own steer box, which starts it again ([Run State Machine §Definitions](../domain/run-state-machine.md#definitions)). A run this trip failed reaches neither, and a terminal run with no live provider process is the **ordinary** case both already face: startup failure, resume failure, and an exited provider all end with the process gone. What a send resumes from — the canonical transcript, and the binding row's provider resume handle and realized spawn configuration — disposal keeps, because it ends the process and never the row. What must not be re-entered is the disposed **process**, and no caller can re-enter a process that no longer exists. The driver-level **status** vocabulary stays exactly `applied | degraded`; the one widening this rule makes anywhere on the driver contract is the additive-optional `refusalCode` member above, which no existing caller is required to read and which changes no shipped field's type. Frames of origin `driver_command` are exempt, a command dispatch being their intended outcome. A provider spawn flag claiming to disable command parsing may be set as defense in depth but never in place of the transform or the tripwire — it is the provider's promise rather than the daemon's guarantee, and in `2.1.245` the nearest such flag is described by the binary's own help as disabling skills, a scope that is not the input parse.

- **A provider session is a replay target, not an authority.** The daemon's canonical transcript is the authority for what a conversation contains ([ADR-029](../decisions/029-canonical-transcript-is-authoritative.md)); a provider's own stored session is a cache of it. Every provider-native continuity verb a driver uses — resume, rewind, fork — is an **optimization behind its capability flag**, and every one has a named daemon-side fallback that reconstitutes the conversation without it. No driver operation, and no capability built on one, may be specified such that its only path is a provider verb. A driver whose provider cannot be replayed into declares `transcript_replay: false` and runs on the hand-over brief floor; it does not fail to be a driver. A provider reopening its **own** conversation is the one case where the provider's verb is the good path rather than the optimization — it is the only one that loses nothing — and the fallbacks under it are the replay and then the brief, in that order.
- **A replay is verified by what the session answers, never by what the call returned.** Replay frames enter provider surfaces that perform no shape validation on them, so a success return proves only that bytes were accepted. `replayTranscript` therefore completes only after a **post-replay assertion**: the reconstituted session is probed and must answer consistently with the transcript's tail. A session that answers with zero turns, refuses, or contradicts the tail fails the operation — the driver reports the failure and the caller does not receive an `applied` result. This is the §Required Behavior text-neutrality tripwire's discipline applied to a second fail-open surface, and for the same reason: the layer above must not read a completed operation where none occurred.
- **What cannot be carried is declared at the operation that drops it.** Any operation that reconstitutes a session under a different provider, model, or account emits an explicit list of the facts it could not carry. Provider-private reasoning heads that list by construction ([ADR-029](../decisions/029-canonical-transcript-is-authoritative.md) Assumption 3: it is declared non-portable, not best-effort) — **visible reasoning summaries do carry, as plain text**, because they are user-visible and therefore already in the canonical record. An empty list is a positive assertion that nothing was dropped, so a driver that does not know what it lost may not emit one. Silence is never an admissible encoding of a loss.
- **A structurally invalid history is a permanent refusal, never a retry.** Where a provider rejects a request because the conversation it was given is structurally invalid — an unpaired tool call, a reasoning item the vendor's own rules forbid at that position — the rejection is **not transient**, because every subsequent request in that session re-sends the same history and is rejected identically. Retrying it is specified as a defect: it spends money, consumes the run's error budget, and cannot succeed. The driver classifies such a refusal permanent, disposes the run's runtime binding, and reconstitutes from the canonical transcript, which is the one record guaranteed not to carry the defect. This is the class the recovery ladder must **not** absorb into `recovery-needed`: a retryable transport fault and a poisoned history look alike from one attempt and differ absolutely from two.
- **Capability delivery follows one preference order, and refusal is a first-class arm.** Where a capability can be delivered by more than one mechanism, the driver takes the first that is available: **native** provider verb → **daemon-emulated** at the driver boundary → **MCP tool** exposed into the run → **prompt-injected** instruction → **typed refusal**. The order is by fidelity, and the last arm is deliberately a refusal rather than a silent no-op: a capability that cannot be delivered by any of the first four is reported unavailable, never claimed and dropped. §Parity Capability Mechanism Grades records which arm each shipped capability actually lands on, so the grade table is the evidence for this rule rather than a restatement of it.

- **Provider usage counters are cumulative, and what a driver emits is the per-turn delta.** Both pinned provider surfaces report usage as a **running total for the provider session** rather than a figure for the turn that just completed: the total resets at no turn boundary, at no context compaction, and on no resume (schema shape Verified first-party, runtime behavior Derived — see §References). A normalizer that forwards each reading as though it described one turn therefore re-counts every earlier turn on every later one, and the error compounds with conversation length — measured **22×** overstatement of session spend on a long thread. Because [Spec-014 §Session Cost Receipt](014-multi-agent-orchestration.md#session-cost-receipt) folds exactly these rows into the committed-spend figure this product bills and budgets against, the defect lands on money rather than on a display. So: a driver's usage emissions carry **per-axis deltas**, never the provider's cumulative counter. The base is **one register per provider thread and axis, advanced in stream order** as each declared-cumulative reading is consumed — a base is never a snapshot copied at turn dispatch, because two interleaved turns differencing against copies of the same starting value each re-count the interval the other already metered. Attribution is by **the turn the metered frame itself names** (the Codex usage notification carries the naming `turnId` on the frame — see §References), never by whichever turn is open at arrival: a usage frame for one turn routinely lands after the next turn has opened, and the stream-ordered base with named-turn attribution meters that late interval to its own turn instead of flooring it or crediting the newer turn — the same bind-at-dispatch discipline the turn-scoped effective principal already imposes on these same rows ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). Base establishment has exactly **two arms**. For a **fresh provider session — a replay-seeded one included — the base is zero and the first reading meters in full**: the provider's counter starts at zero, transcript injection spends nothing, and the first turn's large input is real billed spend that a zero-metered first reading would silently drop. For a **provider-native resume**, the base is **the daemon's own prior-emitted cumulative sum for that thread**, rebuilt from the canonical record ([ADR-029](../decisions/029-canonical-transcript-is-authoritative.md)) — never the first post-resume reading, which would forgive the entire first post-resume turn — so pre-resume spend is never re-metered and the first post-resume interval meters exactly the new spend. Where the wire declares a per-turn figure beside the cumulative one (the Codex breakdown's `last` beside its `total`), the driver consumes it as a **corroborating cross-check** — the derived interval is asserted equal to the declared figure for the naming turn, and a mismatch is recorded as a driver diagnostic — never as a substitute accountant, because the other pinned surface declares no per-turn figure and the declared figure's behavior across resume and compaction is unprobed. A context compaction does **not** re-base: the provider's cumulative counter is unaffected by it, and re-basing there would silently forgive every token spent before the boundary (a compaction's effect on the **window** reading is a separate matter, already specified). A declared-cumulative axis is monotonic non-decreasing within a session, so an observed decrease is a **falsified declaration, not a negative charge**: the emission is floored at zero and the floor-hit is recorded as a driver diagnostic — never emitted as negative spend, and never silently dropped.
- **Normalized token axes partition the turn; no token is counted twice.** Providers do not agree on whether cache-read tokens sit **inside** the input counter or **beside** it, and both pinned surfaces report a cached-input figure that is a component of their input figure (schema shape Verified first-party, runtime behavior Derived — see §References). A driver that forwards the two as siblings double-counts every cached token; one that forwards the input figure untouched prices cache reads at the uncached rate. The normalize boundary therefore emits a **partition**: the normalized input axis is **uncached input**, with any cached-read component subtracted there, and the normalized output axis is output. Containment is an **arithmetic-checked runtime property, never a schema assumption**: the vendor schema places the cached-input member beside the input member and proves nothing about nesting, so the driver subtracts only where the breakdown's own sum identity confirms the cached component sits inside the input figure, and where no identity holds it emits the input figure unsubtracted and records the failed identity as a driver diagnostic — a conservative overstatement surfaced for repair, never a silent understatement. Cache-read and cache-write remain **separate accounting axes inside the driver**, retained on its diagnostic band so the split is observable rather than discarded; the [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) payload registers no per-cache-axis member and this spec mints none — a declaration minted ahead of the consumer that reads it decays in silence, which is the reasoning §Capability discovery states for capability flags and which applies unchanged here. That is a **stated limit, not a silence**: a consumer needing the components separately is an ordinary `usage_telemetry` growth for Spec-005 to register, and the driver holds the values meanwhile. One consequence binds immediately — a driver that derives cost prices from the **provider's full breakdown**, the same reading it normalized from and at each component's own rate, never by re-multiplying the normalized axes, which are a telemetry partition and not a billing basis.
- **A provider connection carries more than one thread, and only the session's own thread projects.** Both pinned providers multiplex **child-thread** traffic — subagent, review, and compaction threads the provider spawns for itself — over the same connection that carries the session's own thread (schema shape Verified first-party, runtime behavior Derived — see §References; corroborated in-tree by a shipped third-party integration that surfaces Codex review, compaction, and thread-spawn children under a parent and hides memory-consolidation children outright). A normalizer that projects every frame it receives renders a child's assistant output and tool activity into the parent's timeline as though the parent produced them — a fabricated transcript — and it either double-counts or loses the child's spend. So: every inbound frame is first classified by its **family** against the pinned stream-surface census, and the routing obligation is **family-scoped**. A **thread-scoped** family routes by explicit thread identity read from the frame, and only frames carrying the session's own thread identity project into that session's timeline; a **connection- or account-scoped** family the census registers — the retry, rate-limit, and capability/initialization surfaces that structurally carry no thread identity — routes to its registered normalization without one, because demanding a member the frame's own shape excludes would quarantine every account-plane signal the corpus already consumes. A frame of an **unrecognized family** carrying no thread identity is still quarantined: the census is the discriminator, and an unlisted shape is never presumed connection-scoped. Thread identities enter the recognized set on a **registration path, ahead of the refusal rule**: the session's own thread registers at establishment, and a child identity registers from the provider's own **parent-linked announcement** — the Codex thread-start notification carrying the parent thread identity and a subagent source kind, the Claude subagent-start signal arriving in the parent's own stream with the parent linkage on it (see §References) — so recognition derives from the provider's declared lineage, never from arrival order. Routing is then **fail-closed** with two distinct held states, both bounded. A frame naming a thread that is **present but not yet registered** — child traffic racing its own announcement — enters a **pending-registration hold**: released into ordinary routing when the registration lands, shed with a recorded diagnostic when a declared timeout passes without one. A frame whose thread identity is **absent where its family requires one, or names a thread no registration path admits**, is **quarantined and reported as a driver diagnostic** — never projected, never silently dropped, and never attributed to the parent by arrival order or position. The quarantine is a diagnostic buffer rather than a queue awaiting delivery, and both it and the pending hold shed oldest-first under declared bounds rather than growing without limit. Two carve-outs bind **before suppression**. Usage counters are carved out first, so child spend is metered even though child content is not — spend the provider attributes to a subagent is attributed to that subagent on the already-registered (`runId`, `provider`, `subagentId`) triple, and spend on a provider-internal child that carries no subagent identity (a compaction or memory-consolidation thread) attributes to the **parent run at run scope**, which is what it is: real spend incurred on the session's behalf by machinery the user did not name. Neither arm invents a subagent and neither drops a token. Second, a child thread's **interactive requests** — tool-approval, permission, and input requests the provider raises from inside a child — are carved out and routed through the **same dispatch and approval pipeline as the parent run's**, answered on the child's own correlation identity: [Spec-014 §Provider-Native Subagents](014-multi-agent-orchestration.md#provider-native-subagents) requires exactly this ("subagent tool calls flow through the same approval pipeline as the parent run's; a subagent introduces no separate trust surface"), and suppressing the request with the transcript would not hide the child but hang it — the provider blocks awaiting an answer no layer will send. What suppression governs is the child's **transcript projection alone**. Child **lifecycle** reaches the timeline only through the already-registered `subagent.started` / `subagent.completed` kinds; a child thread's own frames are never a second lifecycle channel.

- **Context compaction is user-triggerable and never automatic.** A driver declaring `context_compaction` implements `compactContext`, which asks the provider to compact the bound session's own context on a user's explicit request. The runtime **never** triggers it on a threshold, a timer, or a heuristic: the [Spec-011 §Context Window and Usage Meters](011-live-timeline-visibility-and-reasoning-surfaces.md#context-window-and-usage-meters) hint stays informational, and this operation is a second thing beside it rather than the automation that bullet forbids. The operation **settles on the provider's own typed compaction evidence** — the frame that already produces the registered `usage.context_compacted` boundary — and never on the request being accepted, because both delivery mechanisms below can be accepted and then do nothing. It is capability-gated with no emulation arm: a driver that cannot compact declares `false` and refuses as `driver.capability_unsupported`. Prompt-injected self-summarization is **prohibited** as a substitute — it does not move the provider's own context window, so it would report success for work that did not happen, which §Capability delivery's typed-refusal arm exists precisely to prevent. Compaction moves no delta base (§Required Behavior's per-turn delta rule already states that a compaction is not a re-base point), and its boundary is what [Spec-003](003-queue-steer-pause-resume.md)'s compaction-boundary-aware rewind classifies against, unchanged.
- **An enumerated provider command belongs to the binding it was read from.** A driver declaring `provider_commands` implements `listProviderCommands`, and every entry it returns is bound to the `(driverName, providerAccountId)` pair the enumeration was read under. The binding is a **routing invariant**, not a label: an entry is offerable only to agents of that binding and dispatchable only through them. A command read from a Claude session must never be offered to, or sent through, a Codex agent — the two providers share a `/name` syntax and share nothing else, so a cross-provider dispatch is not a degraded call but a different command or none, and it refuses as `driver.capability_unsupported` rather than being attempted. The enumeration is a **live read held as driver-session state**: it is not persisted, not cached across sessions, and not folded into any projection, so a definition a user adds or removes between sessions is picked up by the next read rather than by an invalidation protocol this corpus would then have to own. Where a provider announces that its own set changed, the driver re-reads rather than patching its held copy.
- **The output-speed axis is declared by the provider, never inferred from a request.** A driver declaring `output_speed` reports the provider's own declared speed state and the provider's own reason when that state is not the requested one. Both pinned providers carry such an axis and each decides its own detection source and its own application boundary; neither is decided by a probe, because on both the reading that would decide the flag is a judgment rather than a decidable read (§Capability discovery), so the honest declaration is a static one from the driver's per-driver table. **The provider's declared state is the truth, and a request is not.** Where a provider accepts the driver's opt-in and its own account, plan or model then denies the mode, the declared state is what the driver reports — never the requested value, and never a synthesized success. The two values therefore have **two separate carriers and neither substitutes for the other**: the requested mode travels on the carrier its provider reads it from (the flag-settings request to the running process on Claude Code, sent again at every spawn and resume; the turn request on Codex; reconstructed on recovery from the durable spawn record), and the declared state travels back on whichever provider frame declares it, read live and stored in no column. A requested mode with no carrier would be committed to the agent row and never told to the process; a declared state written to a column would outlive the session that observed it. **A `false` cell would be a declaration about this contract's axis, not a census of the provider's wire.** A driver declares `output_speed: false` only where its provider supplies neither a level vocabulary a caller can read nor a declared-state read — and no V1 driver is in that position (§The output-speed axis).

- **An answer that will not fit the wire is refused, never truncated.** A provider-raised ask — a callback tool call, a permission or input request, an MCP elicitation — is answered back over the transport that carried it, and that transport bounds what one outbound frame may carry. Every driver that answers such asks MUST apply an explicit **outbound** frame bound; where the provider publishes no figure, the honest default is the bound that same transport already applies to that wire in the inbound direction, and the bound is measured on the **encoded** frame the write step will actually send rather than estimated from the composed object — an estimate being a second, disagreeing implementation of the serializer. Where a composed answer exceeds the bound, the driver MUST answer with that ask's **own refusal shape** carrying a bounded typed reason, and MUST NOT send a truncated answer: a truncated tool result is a wrong answer the model cannot distinguish from a complete one, where a refusal is an answer the model can act on. Two properties close the rule. The refusal reason is a **constant**, never a slice of what overflowed — a reason built from the oversized payload can overflow again, reintroducing by its own remedy the failure the bound exists to prevent — so the substitute fits by construction. And every attempt that does not reach the provider is **recorded**: an oversized answer, an unencodable one, and a rejected write each emit a driver diagnostic, so an ask this driver cannot answer is never _silently_ unanswered. A write rejection in particular may not be swallowed on the theory that the exit path reports it — the exit path records that the process died, not that a specific ask went unanswered, and a write can reject on a closed connection while the ask's caller is still waiting on an answer that will now never come.
- **A provider that ignored part of its own configuration is reported, in the provider's own words.** Codex logs one line as the process starts, `Invalid configuration; using defaults`, with the file's path, its line and its column, and runs every session on that install on its defaults for everything the file held; the driver reads that one line and hands the daemon the file name and the line number. Headless Claude Code drops a project or user settings file whole on bad JSON, drops one bad value, drops the tool-server file or one bad server, and says nothing on the wire: exit 0, empty stderr, nothing under `--debug`. The one place it is said is `claude doctor`, which prints an `Invalid settings` block naming the file and the rejected key, never a line, and exits 0 either way, so its stdout is the signal; the driver runs it in the session's project folder under the session's own credential home, once as the session starts and again when a settings file it watches changes, debounced because a run takes about a second, and beside the live session, since it runs no `SessionStart` hook. The file and the key are quoted from the report, never composed. A definition file with broken frontmatter is dropped and reported by nothing, `doctor` included, so it draws nothing until the provider reports it. A corrupt `.claude.json` is a launch error, exit 1 with the file and the parse error on stderr, and takes the launch-error path, never this report. These reports are the daemon's own `ProviderSettingsCheck`, which reaches the screen as `session.notice` of kind `settings_ignored`. The screen is the banner [Spec-021 §Console Design (Meridian)](./021-desktop-app-and-renderer.md#console-design-meridian) describes.
- **A long tool-server call moves to the background on both providers.** On Claude Code the driver starts the process with `CLAUDE_AUTO_BACKGROUND_TASKS=1`, so a tool-server call running past 120 seconds, or one running when a message arrives, moves to the background, and its notification wakes a turn when it ends. On Codex, which has no background move of its own, the daemon fronts every server a session reaches on its own route under the server's own name; past 120 seconds, or on a steer, the route answers the call with the same handle text Claude Code gives its model and offers the model the tools `task_output {task_id, wait_seconds?}` (the task's status and, once it ends, its result, waiting at most 10 seconds) and `task_stop {task_id}` (`tasks/cancel` for a task-augmented call, `notifications/cancelled` for a plain one), and delivers the result by `turn/steer` into a running turn or `turn/start` into an idle one. A task-augmented call's receipt records its task handle and a `delivered` flag, so a result that arrives after a daemon restart is delivered once; a plain call's state ends with the daemon, and its row reads `Stopped when the app restarted`. A server holding a sign-in Codex keeps for itself stays direct.
- **Codex's larger window is a second model row, and the driver sends `model_context_window` only to reach it.** Where a model's catalog row lists a `max_context_window` above its default window, the catalog read offers a second row of the same model carrying that larger window, its figure taken from the catalog, and choosing it makes the driver pass `model_context_window` equal to that maximum. That is the one value of `model_context_window` the driver ever sends, because any smaller value replaces Codex's own window; a model whose maximum equals its default has one row. The window a session shows is the figure read back, labeled `of <window>`.
- **An idle Claude Code session sleeps, and the next message wakes it by resume.** The driver keeps the set of work that would end with the process: the running background tasks from the last `background_tasks_changed` Claude Code reported, empty at each spawn, and the wake-ups (`ScheduleWakeup`'s `scheduledFor`) and session-only jobs (`CronCreate` until its last run or `CronDelete`) read from their tool results, because they are never in that set and die with the process even across a resume; a session holding one stays awake until two minutes after it fires. After 30 idle minutes, checked every 5 and again under the session's lock at the stop, the daemon stops the process of a Claude Code session it started while no turn, queued or untaken message, open approval or question, running background task, wake-up or session-only job, side question or voice call would end with it. The stop closes the process's input and waits for it to exit; Claude Code's own idle exit, `CLAUDE_CODE_EXIT_AFTER_STOP_DELAY`, is never set, because it exits with a wake-up pending and loses it. The next message — from the person, another session or a workflow step — wakes the session through `resumeSession` by the conversation's own id, on the same account, folder, settings and permission level, and is delivered once the process is ready (about 1.2 seconds, measured on Claude Code 2.1.283, with `SessionStart` run as `resume`). Nothing is shown. Codex is never slept, its conversations sharing one service per account, and a session the person runs in their own terminal is never stopped.

## Default Behavior

- Driver capability declarations are read at daemon start, before any page opens, and re-read on four triggers: a change to a provider's command path, the person's `Check again`, a provider process starting, and a model catalog going stale. There is no timer, and the reads stop at daemon shutdown. Readiness comes from the account's stored health ([Spec-026 §Credential-home health observation](026-provider-accounts-and-credential-homes.md#credential-home-health-observation)), with the zero-turn `probeAuth` as the instrument that reads it. A provider's push — Codex's `account/rateLimits/updated` beside the `account/rateLimits/read` pull — is taken live where it arrives, and correctness never depends on a push.
- Drivers run in the local daemon; V1 supports local-runtime-node drivers only. A driver may call remote provider APIs or services, but driver control and execution authority remain attached to the local runtime node, and the product runs no execution service of its own. Work a provider runs in its own cloud is that provider's, reached only through the provider's own verbs (§Interfaces And Contracts).
- Driver transport defaults to `stdio`. The Codex driver may additionally be configured — config-gated, off by default — to attach over `unix://` or `ws://` app-server listeners with bearer auth (`DriverTransportConfig`; the credential is held as a daemon-config reference, never inline). The Claude CLI exposes no local listener, so the Claude driver runs over `stdio` only; a session is driven from another device through Remote Control, which reaches the daemon and never a provider transport ([Spec-002](002-runtime-node-attach.md)).
- Unknown capability fields are ignored (tolerant reader). The declared `contractVersion` is a change-detection signal — the daemon records it at attach and compares it on refresh to detect contract drift and invalidate capability snapshots — not a negotiation surface: the daemon never version-gates its behavior on it, and additive contract evolution with tolerant reading replaces negotiated feature-unlocking.
- The runtime must only surface controls that correspond to supported capabilities for the active run.

## Fallback Behavior

- If a driver cannot resume a previously persisted handle, it must surface `provider failure` detail and a visible `recovery-needed` condition; it must not silently create a replacement provider session under the same canonical run. Recovery conditions form the closed `RecoveryCondition` set — `recovery-needed` (generic: operator reconciliation required) and `reauth-required` (the provider session or credential expired: detected mid-run via the provider's typed auth-failure signals or at resume/probe time; remediation is re-authenticating the provider CLI on the runtime node, after which recovery may retry). The named type is declared once in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) and referenced at every carrying surface.
- **Provider usage limits are a sibling axis, not a recovery condition.** When a provider refuses or defers a turn because the bound account's plan allowance is exhausted, the driver surfaces a typed **provider usage-limit signal**, distinct from `RecoveryCondition` and never folded into it: a `recovery-needed` condition asks a human to reconcile, whereas a usage limit resolves on its own at a known boundary and asks the runtime to wait. The signal carries a **closed-set cause** and an **optional reset boundary**; the boundary carries its own provenance, distinguishing a value the provider stated from one the runtime derived, because a derived boundary may be wrong and a consumer that cannot tell will present a guess as a fact. Recognition is **typed-only**: a driver emits the signal solely from a structured provider event whose shape it can name, and MUST NOT infer a usage limit by matching message text, exit codes, or HTTP status alone. An unrecognized or unparseable shape yields **no signal** — the honest absence — rather than a synthesized one; a consumer reads that as "not known to be limited", never as "known not to be limited". A driver that cannot observe usage limits at all declares nothing here and is not emulated: this is the parity triad's degrade-honestly arm, and the pacing consumer's behavior without a signal is unchanged from today's.
- On successful resume the driver reports `sessionPosition` — its normalized monotonic position (turn/event ordinal) for the resumed provider session. The daemon compares it against the recorded position; reconciliation semantics (divergence halts for human decision) are [Spec-013](013-persistence-recovery-and-replay.md)'s, per [ADR-017](../decisions/017-shared-event-sourcing-scope.md)'s local-log-authoritative ruling. A provider that silently returns a fresh session on resume (for example on a working-directory mismatch) is caught by this comparison rather than silently adopted.
- If a provider offers provider-native data that cannot be normalized safely, the runtime must store it as diagnostic metadata only, not as canonical domain state.
- If a driver does not support dynamic model or mode mutation, the runtime must require a new run or agent configuration rather than simulating mutation.
- If a requested integration path would require shared hosted execution outside the local runtime boundary, v1 must reject or mark that path unsupported rather than routing execution through the control plane.

Claude Code forks with `--resume-session-at` and `--fork-session`, Codex with `thread/fork` at an inclusive turn. It is never an undo; the session operation it serves is [Spec-001](001-session-core.md)'s fork, `session.fork`, and it is gated on `session_fork`, registered together with that caller.

The daemon supplies the condition and the target `bindingId` (+ `runId`), one call per live binding, and a later set replaces the active goal. The driver reads each ending from the provider — Codex's `thread/goal/updated` and `thread/goal/cleared`; on Claude Code the `Goal set` and `Goal cleared` stream lines, the `Stop hook feedback` user frame of an unmet check, the `goal_status` records Claude Code writes to its own session file for a met or impossible goal, and its `stop-hook-block-cap` notification — and never from hook frames, which Claude Code sends for no goal check. The goal model and its statuses are [Spec-014](014-multi-agent-orchestration.md)'s.

Input is the daemon-supplied canonical transcript projection and a target boundary; output is provider-shaped frames plus the **declared-loss list** for anything the target could not represent. Pure with respect to session state: exporting mutates nothing and starts no turn.
  - `replayTranscript` — reconstitute a conversation into a **fresh** provider session from exported frames (gated on `transcript_replay`). Returns only after the post-replay assertion passes; a driver whose provider refuses prior-turn content declares the flag `false` and the daemon falls back to the hand-over brief with the operation reported `degraded`. It is the **fallback** under `resumeSession` and not the ordinary path: a fresh process of the same provider reopens its own conversation first, and a replay is what happens when that reopen did not load, which is why a replayed conversation is reported as restarted rather than continued. Replay never re-mints tool-call identifiers (§Canonical Transcript Export And Replay) and never writes to the source session.

The summary is asked for in one shape on both providers: on Codex the copy answers the fixed template, and on Claude Code the driver runs the provider's own `/compact` on the copy carrying that template's instruction and returns what the provider said; where the copy's own summary is not readable the driver returns the fixed template instead and says which of the two it did, so the floor is inside the operation and there is no flag to decline it by. It returns the summary and the declared-loss list and never the message itself: the order of what follows the summary, and the plain transcript file written beside it, are the daemon's (§The hand-over brief is the floor, and it is visibly a floor). The copy answers one turn of its own, whose spend lands on the session's own account and is drawn as its own row; the live session starts no turn, and its conversation's bytes are unchanged across the composition.
  - `compactContext` — ask the provider to compact the bound session's own context (gated on `context_compaction`). Operates on an already-established session and starts no user turn. Settles only on the provider's typed compaction evidence, never on the request being accepted (§User-triggered context compaction). A driver declaring the flag `false` refuses as `driver.capability_unsupported`; nothing is emulated by prompt injection, because a prompt asking a model to summarize itself does not move the provider's own context window and would report success for work that did not happen. Its wait for that evidence is **bounded** and ends at whichever comes first of the driver's declared per-binding compaction bound or the run's runtime binding ceasing to be live; expiry settles `failed`, never `applied`, and a compaction frame arriving afterward is still normalized into `usage.context_compacted`. The result is a **discriminated union** on its settlement — `applied` carrying the boundary position (`null` where the provider's frame states none), `refused` where nothing was sent, `failed` where something was sent and no boundary was witnessed. Authorized by the identical `Action::"intervene"` adjudication the intervention path runs, on the run owning the named binding; no Cedar action and no error code is minted for it.
  - `listProviderCommands` — read the provider's own enumeration of native slash-commands and skills for the bound session (gated on `provider_commands`). A **live read** returning the enumeration as the driver observed it, held as driver-session state and discarded with the session; it is deliberately not a registry, not persisted, and not a projection the daemon folds. Every returned entry carries the `(driverName, providerAccountId)` binding it was read from (§The provider command and skill surface). The enumeration is both a discovery surface and the set a forwarded command must come from: an entry the console does not own is sent verbatim when a user selects it and settles on the provider's own answer, while a command the driver composes for a daemon operation is checked against this same enumeration before dispatch and settles on typed evidence (§The provider command and skill surface). Reading it requires an active session and nothing more. It is delivered as a per-binding **subscription** rather than a single reply: the first enumeration, then each replacement the provider pushes, whole — so a consumer is never handed a patch to apply, and a new provider process yields a new enumeration rather than an amended one. It reaches clients as `session.providerCommandsSubscribe`, the live `/` list: this enumeration plus the prompts each working tool server publishes, which on Codex — a provider that never asks a server for its prompts — the daemon lists and fetches through its own MCP client, over the connection that client already holds for the server, so listing prompts never starts a second copy of it.
- The driver-operation surface is the list above, read from the list rather than from a figure carried beside it.
- Required normalized event families:
  - run lifecycle
  - assistant output
  - tool activity
  - interactive request
  - artifact publication
  - usage or quota telemetry where available
- Normalization obligations bind at the driver's normalize boundary: usage/quota telemetry is provenance-stamped by the driver — it sets `windowSource` (`provider_reported | model_default | estimated`) and computes the `exceeded` headroom predicate at normalization ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — never deferring provenance or the derived predicate to consumers.
- **A session's provider also reports where its memory lives and which hooks it loaded, and both are per-session reads under the enumeration's own discipline.** They arrive on the transport the driver already establishes — the memory locations on the session handshake where the provider reports them, the hook set from the provider's own hook read where the provider has one — and are held for the session rather than stored. Two asymmetries are reported rather than smoothed over: Codex reports its loaded hooks through `hooks/list {cwds}`, which is in its stable request set, together with the entries it **skipped or warned about**, so a hook that did not load is named rather than silently missing, while Claude Code reports no hooks at all on the wire — for which the honest answer is the set of files hooks are read from, said to be files rather than presented as loaded hooks. And the provider's own memory switch applies **at once** on Codex (`thread/memoryMode/set`) and **at the next process start** on Claude Code, so a driver reports which of the two it is instead of implying an immediate effect it cannot deliver. A credential home's memory store belongs to the account bound to the run, never to the operator's own ambient provider directory ([Spec-026](026-provider-accounts-and-credential-homes.md)). The reads reach clients as `session.memoryRead` (the memory paths and the account's own store), `session.autoMemoryUpdate` (the provider's own memory switch) and `session.hookList` (each hook's key, event, handler type, command, matcher, timeout, source path, source, enabled, managed, hash and trust status, with the warnings and errors per folder); the daemon's own hooks are left out of that list.
- **The commands a run has running are a driver-boundary surface of their own, and the client-facing `command.*` namespace is where they reach a user.** A session carries a subscription to the set of commands the run has running — one entry per command with its output as it streams and the fact and manner of its ending — beside its operations: **stop a named running command**, **move a named running command to the background** where the provider offers that move, and **type into a named command that is waiting on its input**. The set is a subscription rather than a read because a command can outlive the turn that started it and wake the agent when it ends, so a consumer that polled would miss the ending it exists to show. It follows the provider's own pushes, with no timer: Claude Code's `background_tasks_changed`, and on Codex the command items, whose entry closes on the command's own `item/completed` and never on `turn/completed`, with one `thread/backgroundTerminals/list` read per attach. The client-facing names are `command.list` (the subscription, carrying `command.output` as live frames that are never stored), `command.stop`, `command.background` and `command.write`, and a command's ending is stored as the event `command.ended`, which settles its row after a reload — a command that outlives an interrupt included.
- **Stopping a command uses the provider's own per-task stop, and has one reported outcome.** Both pinned providers stop one command without ending the turn: Claude Code through `stop_task`, Codex through `thread/backgroundTerminals/terminate`. Where a provider offers no such stop, the daemon ends the process it launched. Either way the agent is told **which command was stopped**, in one short message, rather than being handed a bare failure to interpret: a model that learns only that something failed will retry it, which is the outcome a stop exists to prevent. Until the process is gone the run reports the command as still running, because a stop that has been asked for and a process that has ended are different facts and a consumer shows both.
- **Moving a command to the background is capability-shaped and absent rather than refused where the provider has no such move.** Claude Code lets a waiting command be released through its `background_tasks` control request, so its turn continues while the output keeps streaming; Codex has no mechanism for it and none is emulated, because faking it would mean the daemon continuing a turn the provider still considers blocked. A consumer offers the move only where the driver reports it, and a request against a driver without it refuses as `driver.capability_unsupported`.
- **Typing into a command an agent started works on both providers, through one daemon command wrapper.** The wrapper sits after each provider's permission decision and inside its sandbox, placed by each provider's own hook point: Claude Code is launched with `CLAUDE_CODE_SHELL_PREFIX` naming the wrapper, which runs hook commands and tool-server starts unchanged and treats only the Bash tool's command as a command; each Codex service runs Codex's own `codex exec-server` behind the daemon's pass-through relay, registered with `environment/add`, and every conversation starts, resumes and forks with `environments: [{environmentId, cwd}]`. The wrapper reports a command waiting on its input by the kernel's own signal; what the person types reaches the command through Codex's `process/write` on the executor or the wrapper's input pipe on Claude Code, and `End input` closes that input as end-of-file on a terminal would. Each provider is launched with `GIT_ASKPASS`, `SSH_ASKPASS` and `SSH_ASKPASS_REQUIRE=force` naming a daemon program, so a prompt that opens the terminal (`/dev/tty`) raises the same input line with the prompt's own words. A read waits for the person or `End input`, bounded only by the provider's and the runtime's own limits, and the waiting state is kept with the session, so it shows on every device.
- **Provider-account identity is an additive-optional spawn input.** Session-creation and resume parameters carry an **optional** provider-account identifier. Omitting it is a supported path: the daemon resolves the provider's current account. The identifier is **opaque to the driver** — it selects a credential environment and is never parsed, decomposed, or used to locate credential material by the driver itself. The daemon constructs that environment and hands it to the spawn; a driver MUST NOT read ambient provider credentials from the operator's own environment or home directory when an account is bound, because doing so would silently execute against a different account than the one the run was admitted for, and the resulting spend would be attributed to an account that never paid it. The identifier is **server-resolved and server-stamped**: a client-supplied value is an input to resolution, never the recorded outcome. Resume rebinds to the account the run was originally admitted against rather than re-resolving whichever account is current at resume time, so recovering a run never moves its billing as a side effect. The one act that does move a running session's account is the deliberate press on the provider surface, which moves every unpinned running session on that provider in place, from its next request ([Spec-026 §Moving a session to another account](026-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)): on Claude Code by `apply_flag_settings` pointing the running process at the new account's credential store, on Codex by handing the new account's tokens to the service the session already runs in. Only where a pinned build refuses that does the move fall back to a copy of the conversation file and the provider's own resume. Registration, defaults, credential-home layout, validation, and concurrency posture are Spec-026's; this bullet is the whole of the driver-facing seam.
- **Capability detection source rides the capability report.** Every flag `getCapabilities` reports carries a closed-literal `CapabilityDetectionSource` — `static` (declared from the driver's own per-driver table) or `probed` (decided against the installed build by a zero-turn probe). It is an **additive-optional**, **live-scoped**, report-only member of the **driver-side** read — present and total over the flag set on a live driver read, absent exactly when the wrapper was reconstructed from the durable capability cache, so its absence reads as _cache reconstruction_ rather than as _unknown provenance_ and a consumer needing provenance re-reads the driver. It rides `GetCapabilitiesResult` — registered on that wrapper beside `cliVersion` in [api-payload-contracts.md §Plan-004 — Provider Driver Contract (Internal Interface)](../architecture/contracts/api-payload-contracts.md#plan-004--provider-driver-contract-internal-interface) — and, exactly as the mechanism grades and `cliVersion` itself do, it stops there: this member does not reach the registered client-facing `driver.listCapabilities` payload, and a consumer that needs a flag's provenance reads it through the daemon rather than off that reply, per §Capability discovery. It is deliberately **not** persisted — `driver_capabilities` caches the flag values the change-detection compare reads, and provenance is a property of the reading rather than of the cached row, so no column and no CHECK widening is added. No operation is minted and no client-facing payload is widened **by this member**: what grows is the driver-side wrapper the daemon already reads, per §Capability discovery. (The sibling `outputSpeedLevels` on the same wrapper is deliberately the other way round — it is served to clients, because its reader is a user-facing control rather than a daemon consumer; §Provider Parameter Vocabularies states why the two differ.)
- **Usage-delta and thread-routing obligations bind at the same normalize boundary.** The per-turn delta derivation, the non-overlapping token partition, and the thread-identity routing of every inbound frame are normalization duties, discharged exactly where `windowSource` and `exceeded` already are — before an event reaches the session engine. A consumer never receives a cumulative counter to difference, an overlapping axis to reconcile, or a foreign-thread frame to filter, and none of the three may be deferred to one. The per-thread delta bases, the thread-identity registry, and the pending-registration hold are **driver-session state**: held for the life of the provider session and discarded with it, with each base re-established on resume from the daemon's own prior-emitted cumulative sum per §Required Behavior — never from the first post-resume reading.
- **Every driver declares the daemon's session-messaging tools at spawn and routes their calls to the daemon.** The operations a session uses to reach another session are `SendToSession {to, message, files}` and `ListSessions {}` — the daemon's, not a provider's — and they reach both providers the way every tool of the daemon's does: on the daemon's one MCP `url` entry per session, under the server name `sessions`, beside the workflow tools and the browser tools, and never through Codex's `dynamicTools`. Each provider prefixes them its own way — `mcp__sessions__SendToSession` on Claude Code. `files` names paths the sending session can read; the daemon stages them into the receiving session as that session's own attachments, so they arrive there as paths rather than as bytes the driver carries. The session's permission level gates them on Claude Code through `can_use_tool`, and on Codex the daemon applies the level itself under the entry's `approve` mode. A driver **forwards** the call and its arguments to the daemon and returns what the daemon answers; it never interprets the call, never reaches another session itself, and mints no wire method and no error code of its own ([Spec-014 §Sessions Talking To Each Other](014-multi-agent-orchestration.md#sessions-talking-to-each-other)). The session callback-tool registry rides the same entry, so each leg carries one declaration of daemon-served tools.
- **`maxStepsPerTurn` is a spawn parameter each leg realizes its own way.** Session-creation and resume parameters carry the bound on how many steps one turn may take, absent meaning unlimited, which is what both providers do on their own. The Claude leg realizes it as `--max-turns` at process start and the provider ends the turn itself at the number, which is why a change to a live session applies at that session's **next** turn, by a fresh spawn that reopens the provider's own conversation by its id — the parameter genuinely binds at process start on this leg. The Codex leg passes nothing through, that provider publishing no turn cap at all ([Codex wire reference §This provider publishes no turn cap](../reference/provider-wire/codex.md#this-provider-publishes-no-turn-cap)), so the bound is carried for the daemon's own count of the turn's steps with `turn/interrupt` sent at the number. Either way the **turn** ends and the run stays where it was; the bound is not a budget, mints no interrupt reason, and joins no stop condition ([Spec-003 §The Step Bound On A Turn](003-queue-steer-pause-resume.md#the-step-bound-on-a-turn)).
- **The Codex leg runs one service per account; the Claude leg runs one process per session.** The Codex driver does not spawn a process per conversation. The daemon runs one `codex app-server --listen unix://<the control socket in that account's Codex home>` per credential home and holds every conversation on that account inside it, as a websocket client of that socket — the same service a plain `codex` typed in a terminal joins by itself, the socket being per Codex home rather than per folder ([Codex wire reference §The shared `app-server` a terminal `codex` joins](../reference/provider-wire/codex.md#the-shared-app-server-a-terminal-codex-joins)). The managed-daemon form of that command is never the one started: its own subcommand set carries an updater that can replace the person's installed build mid-session, which is the very thing the auto-update opt-out above exists to prevent. Five conditions bind the driver. What a conversation owns — its working folder, its configuration and its tool servers — is passed at `thread/start` and never as a flag on the shared service, because a `-c` given at the service's start applies to every conversation the service holds; only what every conversation shares goes there: the daemon's hooks, `features.browser_use=false` so Codex's own browser tool stays off, and `thread_unload_delay_secs=5`. One service has one notification opt-out list and one process environment, so the list is the union of what every conversation needs and each event is routed by the `threadId` it carries; a fork loads into whichever service answered it; and on Windows the control socket's path fits within 108 bytes. A terminal session that joins runs its commands in the folder the person started it in ([codex.md §A second seat on the shared service](../reference/provider-wire/codex.md#a-second-seat-on-the-shared-service)). A change to a conversation the service already holds is applied where that provider honors it — its settings through `thread/settings/update`, its developer instructions appended, its base instructions only through a fork — from the conversation's next turn. And a service that dies, or answers `model/list` with a `-32600` asking for a restart, is started again by the daemon with every conversation in it resumed through that provider's own resume, the one on screen first; a service that dies three times within five minutes is left down until the person presses `Restart`. The account is the sharing key, never this runtime: a credential home is what a service is started on, so two accounts are two services and never one, and a switch of the current account hands the new account's tokens to the service the following sessions run in rather than moving them between services; only on the resume-path fallback does a conversation move to another account's service, and then only after the service it leaves has released it, so no conversation is held by two services at once. The Claude leg stays one process per session, that provider offering nothing else.
- **A session is spawned with exactly the tool servers switched on for it, declared through the provider's own means.** Nothing of this runtime's stands between the provider and that set. On Claude Code the process starts with `--strict-mcp-config`, so nothing the project or the account configures loads by itself; only the daemon's own `url` entry rides `--mcp-config`, and the driver adds the session's servers with `mcp_set_servers` right after start, sending the set again after each resume because it lives only in the process's memory. On Codex the set is the conversation's own configuration at `thread/start`: the whole `mcp_servers` table, each server a `url` entry on the daemon's route under its own name, enabled or not. A server that is switched off is never declared, so it costs the model no tool definitions. A switch flipped while the session runs is another `mcp_set_servers` call on Claude Code — the server's process ended and its tools gone from the next turn, or back the same way, with no restart and nothing written to disk — and reaches a Codex conversation at its next turn. `mcp_toggle` is never used, because it saves the switch for the whole project and leaves the server running.
- **A driver owns its transport, and every contract operation carries a grade on every driver.** The contract assumes no wire: Claude Code speaks `stream-json` with its control protocol over stdio, and Codex speaks JSON-RPC to one `codex app-server` per account. Every operation is graded `native`, `emulated`, `degraded` or `absent` on every driver (§Parity Capability Mechanism Grades); an emulated or degraded operation names its mechanism in the driver's capability record, and an absent one is refused with `driver.capability_unsupported`, never faked. The product's fallbacks are one set on every driver: a steer the provider cannot take mid-turn is held and delivered at the turn boundary; a pause holds the next turn at the boundary; an undo restores files from the daemon's own checkpoints and cuts the conversation only through the provider's own cut, so where a provider has no cut the files-only restore stands and the conversation half is refused. A provider's models come from its own list or its own configuration; its sign-in is one of three kinds — the provider handles it, the person signs in through the provider's own terminal flow, or a pasted key; and each account keeps its own home, named by the provider's own configuration-folder setting. **The providers are Claude Code and Codex.** The contracts' provider enumeration, the account table's check, the version-floor table and the tool-server governance union each list them, and the provider switch, the hand-over brief and import take any listed provider as source and target.
- **A session can send work to its provider's own cloud, and a cloud task shows only what the provider reports.** The daemon never executes the remote work; it calls the provider's own verbs under the session's account. On Codex, `codex cloud exec --env <environment> [--attempts N]` starts a task, `codex cloud list --json` and `codex cloud status` read its state — one list per environment a minute while a task is pending, none otherwise — `codex cloud diff` reads an attempt's diff, and `codex cloud apply` brings an attempt back after a file checkpoint through the daemon's checkpointer; the operation is `native` while the pinned build carries `codex cloud`. On Claude Code, `claude --cloud "<task>"` creates the cloud session; the CLI reads no status, so a task reads `Submitted` for its whole life, and bringing it back is `claude --teleport <id>` in a new worktree followed by the provider-session import, so the operation is `degraded`. A task needs a ChatGPT sign-in on Codex, a claude.ai Pro, Max or Team sign-in on Claude Code, and a GitHub remote on both. The client-facing names are `cloud.taskStart {sessionId, prompt, environment?, attempts?}`, `cloud.taskList {sessionId}` (live), `cloud.taskRead {taskId}`, `cloud.taskDiffRead {taskId, attempt?}` (Codex only) and `cloud.taskApply {taskId, attempt?}`, and the event `cloud.task_updated`, which carries only a state the provider reported. A cloud task stops nothing and holds nothing in the session.
- **Voice has its own operations.** `voice.dictationStart {sessionId}` (the mode is read from the machine's settings file, never sent), `voice.dictationWrite` (16 kHz 16-bit mono frames), `voice.dictationStop {cancel}` and `voice.dictationSubscribe` (the words in progress and settled, and a refusal) carry Claude Code's dictation; `voice.callStart {sessionId, offerSdp}` → `{answerSdp}`, `voice.callStop`, `voice.callSubscribe` and `voice.voiceList` carry Codex's call; and `voice.stateUpdate {sessionId | null}` with `voice.stateSubscribe` hold which session voice is on in, which the daemon keeps.
- **Every operation this spec owns is named with where its contract and its build live.** Client-facing, with method rows in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) and tasks in [Plan-004](../plans/004-provider-driver-contract-and-capabilities.md): `driver.listModels`, `driver.listModes`, `driver.listCapabilities`, `driver.compactContext`, `session.providerCommandsSubscribe`, `session.modeUpdate`, `session.sideQuestionAsk`, `session.reviewStart`, `session.memoryRead`, `session.autoMemoryUpdate`, `session.hookList`, `session.restart`, `command.list`, `command.stop`, `command.background`, `command.write`, the `cloud.*` set and the `voice.*` set. Built elsewhere on this spec's contract: `callbackTool.list` and the fixed `builtInTools` list `driver.listCapabilities` gains per driver, in [Plan-027](../plans/027-agent-definitions-and-peer-invocation.md); the provider page's `provider.list` and `provider.update`, whose home is [Spec-026](026-provider-accounts-and-credential-homes.md), in [Plan-026](../plans/026-provider-accounts-and-credential-homes.md). Daemon-side, crossing no client boundary and built in Plan-004 alone: the conversation cut, the Claude Code goal leg, the Codex hooks and their trust, the output-style answer, the shared Codex service a terminal session joins, the ignored-settings check (`ProviderSettingsCheck`, raising `session.notice` of kind `settings_ignored`), the transcript-retention setting, the idle sleep, the speech-service socket (`wss://api.anthropic.com/api/ws/speech_to_text/voice_stream`), the spoken answer on a Codex call, the background-call tools `task_output` and `task_stop`, and the provider leg of `Allow once` — capturing a block by the provider's own reviewer on both drivers and sending each provider's own retry — for `approval.denialOverride`, whose home is [Spec-010](010-approvals-permissions-and-trust-boundaries.md) and which [Plan-010](../plans/010-approvals-permissions-and-trust-boundaries.md) serves.

**What a driver sets on a process it starts, and what it reads back rather than assumes.**

- **Codex's hooks and their trust.** The daemon's Codex hooks ride `-c` at each account home's service start: a pre-tool hook, which reports a command and holds a call while the session is paused, and a post-tool hook. Their trust is written through `config/value/write` (`hooks.state`, the hook's `trusted_hash`, `upsert`) after `hooks/list`, at each service start and before any conversation starts, forks or resumes, because a trust write does not reach a conversation already loaded. A command Codex refused before sending its command item still gets its row from the hook pair, with no exit code, since the post payload carries none. The per-conversation trust bypass is never used. While the person has `Reach Codex sessions started in a terminal` on, the service on the person's own Codex folder carries the same hooks and writes their trust records into that folder's `config.toml` at service start, refreshing a record when its hook command changes and touching no other entry. The daemon does not otherwise modify the person's `~/.codex` configuration, except for the trust records its own terminal-session hooks need.
- **Codex's conversation flags.** Every conversation the daemon starts sets `features.default_mode_request_user_input` and `features.multi_agent_v2`.
- **Every provider figure is read, never hard-coded.** The window, the max window, the compaction point, the fixed start, the model list and the output-style names are read at creation and on every model change, under the session's own base URL: Claude Code's `get_context_usage`, and Codex's model catalog corrected by the first turn's `thread/tokenUsage/updated.modelContextWindow`. The figures of Claude models the session is not on are read at creation by one short control-only process on the same account home and base URL, about 5 seconds, with the window key removed.
- **Full model ids.** A driver passes a model's full id, never an alias, because Claude Code's plan mode runs the `haiku` alias as a different model; `set_model` sends a one-token check for an id that is not a built-in alias.
- **The daemon's own tools** reach both legs on its one MCP `url` entry per session (§Interfaces And Contracts).
- **Transcript retention.** Every Claude Code process the daemon starts carries `cleanupPeriodDays: 36500` in its `--settings`, so Claude Code's own cleanup never deletes a conversation a kept session resumes from, and `get_settings` is read back after each spawn, so a managed lower value is reported by `ProviderSettingsCheck` as `session.notice` of kind `settings_ignored` (§Required Behavior). At purge the session's provider files are removed from every account home it ran in, and Codex's `thread/delete` is sent for its conversation, never touching a terminal session's conversation in the person's own Codex folder.

### Fallback Behavior

For each `false` in the matrix:

- **Codex `reasoning_stream: false`**: reasoning surface shows "unavailable" in timeline UI. No degradation — reasoning simply isn't exposed.
- **Claude `steer: true`**: the driver delivers a steer by writing the message to the already-running process as a `stream-json` user message, which the provider holds until its next tool boundary and folds into the conversation there as a new user turn — the content joins the **same** run, with no interrupt and no second run, and the provider's own reason word for the fold is `absorbed_mid_turn` ([Spec-003 §Driver-Level Steer Mechanics](003-queue-steer-pause-resume.md#driver-level-steer-mechanics); the measurement behind it is recorded in [ADR-037](../decisions/037-claude-code-mods-are-an-optional-terminal-bridge.md)). The queue-plus-interrupt path is a generic fallback for a driver that can accept nothing mid-run, and **neither V1 provider reaches it** ([Spec-003 §Default Behavior](003-queue-steer-pause-resume.md#default-behavior)). A steer on this leg settles `applied`.
- **Claude `transcript_replay: false` (probe-declared)**: the only cell in this table whose `false` is decided at runtime rather than statically, and the only one with a daemon-side fallback — `replayTranscript` settles on the hand-over brief, reports `degraded`, and carries a non-empty declared-loss list rather than refusing (§The hand-over brief is the floor, and it is visibly a floor; [ADR-029 §Enumerated Gates And Fallbacks](../decisions/029-canonical-transcript-is-authoritative.md#enumerated-gates-and-fallbacks)). Never `applied`.

And for the `true` cell whose support is narrower than it reads:

- **`mcp: true` (both drivers)**: support is not visibility — the provider can invoke MCP server tools, but the daemon does not know the provider's MCP tool census from this flag. An MCP-discovered tool is **always** `manual_reconcile_only` unless an operator-governed assignment upgrades it (§Tool Metadata); the fallback for an unknown MCP tool census is the conservative default, never a class inferred from annotation self-claims.

This matrix is the initial V1 capability set. Drivers self-report capabilities via `getCapabilities()`. The matrix above documents expected V1 values; actual runtime values may differ as drivers evolve.

### Parity Capability Mechanism Grades

Boolean flags answer **whether** the driver delivers a capability; mechanism grades record **how** the system delivers it end-to-end (`native | emulated | degraded | absent`), generalizing the `mcp: true` honesty rule above. `degraded` delivers part of an operation and names what it leaves out. Grades are matrix/documentation truth for every row but one: the **provider-bound text neutrality** row is a normative behavioral input (§Required Behavior), so its cell states the grade governing today and re-grading it changes runtime behavior rather than only this table. Otherwise the wire declares driver-boundary booleans and the grade combines the driver leg with any daemon/orchestration leg. The grade token is always exactly one of those grades; a row may qualify it parenthetically (e.g. `native` (partial: …), `absent` (upstream-gated: …)) without widening the vocabulary. Per-provider mechanisms below are verified against the pinned binaries, Codex claims coming from the binary's own generated protocol schema rather than from a transcription of it.

The tier set is **runtime catalog data rather than schema** — a tier is three free-form strings — so the vocabulary is read per model exactly as `effortLevels` is, and the axis resolves to a **turn** boundary because the carrier is per-turn. Measured first-party at `codex-cli 0.155.1` on 2026-09-19: the catalog read published one tier on every model it returned, `{ id: "priority", name: "Fast", description: "1.5x speed, increased usage" }` (a `2x` description on one model) with a null catalog default, and the provider's own build carries the interactive toggle for the mode (`fast_mode`, stable in its own feature list). The flag is nonetheless **`static`**, and **decisiveness** is the conjunct that fails: reading a returned tier as an output-_speed_ tier is a semantic judgment over free-form strings rather than a decidable read, so the zero-turn catalog channel exists and still cannot decide the flag in either direction | `native` (declared, not probed) — the session handshake declares a fast-output state together with a reason when that state is not the requested one. Measured first-party at `2.1.251`: the reason **moved** between a bare launch and a launch carrying the documented opt-in, which is what establishes both that the opt-in is honored and that a second, account-scoped gate sits behind it (see §References). The flag is **`static`** here too and **zero-turn** is the conjunct that fails: the handshake that declares the state is emitted only as part of a turn-bearing exchange, so reading it is not zero-turn, and §Capability discovery's admissibility test is conjunctive. The mechanism is `apply_flag_settings {fastMode}` sent to the running process between turns, applying from the next run with no restart and no file written, and only models whose catalog entry carries `supportsFastMode: true` report fast output; a typed `/fast` declines under the programmatic transport, so the daemon applies it itself. The axis resolves to a **run** boundary |
| Provider cloud tasks | `native` while the pinned build carries `codex cloud` — `codex cloud exec`, `list --json`, `status`, `diff` and `apply`, run under the session's account; a task's state is the one Codex reports (`Pending`, `Ready`, `Applied` or `Failed` with Codex's own error) | `degraded` — `claude --cloud "<task>"` creates the cloud session and `claude --teleport <id>` brings it back into a new worktree for the provider-session import; the CLI has no status or list verb, so a task reads `Submitted` for its whole life, with a link to open it on claude.ai |

Some rows carry no boolean flag in V1, each for its own reason, and the difference is the point — a flag-less row is not one kind of gap. Voice has none because both V1 drivers deliver it and no caller branches on it: an account whose provider gives it no voice — on Claude Code an API-key or cloud-provider account — is refused `Voice isn't available on <account>.` by the voice operations themselves. Provider-bound text neutrality has none **by design** — the frame-origin discriminator is deliberately not a capability flag, an undeclared flag resolving fail-open through §Required Behavior's undeclared-is-unsupported rule. Provider cloud tasks are gated by this row's grade and by the account (§Interfaces And Contracts). Session fork is not among them: it carries `session_fork`, registered together with its caller, [Spec-001](001-session-core.md)'s `session.fork`, through the driver's `forkConversation`, and a driver that does not declare it takes [ADR-029 §Enumerated Gates And Fallbacks](../decisions/029-canonical-transcript-is-authoritative.md#enumerated-gates-and-fallbacks)'s fallback, the canonical transcript replayed into a second fresh session. `interactive_requests` is two-provider with distinct mechanisms: Claude via the `can_use_tool` control round-trip (`--permission-prompt-tool`); Codex via the native `item/tool/requestUserInput` server request plus `mcpServer/elicitation/request` MCP elicitation.

### Provider Parameter Vocabularies

**Effort vocabularies are per-model and provider-published, never per-provider.** The vocabulary a driver may offer for a model is the list that model publishes on the provider's own catalog read, carried verbatim on `ProviderModel.effortLevels`; **absent means the model exposes no effort selection at all**, which is a reading rather than an omission. A driver MUST NOT synthesize a level a model did not publish, and MUST NOT collapse the per-model lists into one provider-wide set — at both pins the lists disagree per model _within_ a single provider, so any provider-wide list is wrong for some model in the same reply. Each driver's **pinned declared catalog** is the answer for a composition that binds no live read; it is deliberately **not** a fallback for a read that failed, because serving a stale catalog under the appearance of a live one is exactly the confusion §Capability discovery's detection-source doctrine exists to prevent, so a bound read that fails propagates. Measured first-party zero-turn at both pins on 2026-08-30 (**Binary probe**, **Verified**): **Claude Code `2.1.251`** publishes `low | medium | high | xhigh | max` on `claude-opus-5[1m]`, `claude-fable-5`, and `claude-sonnet-5`, and publishes **no** effort surface on `claude-haiku-4-5-20251001` — the live instance of the absent-means-none reading. **codex-cli `0.150.1`** publishes **three** distinct lists across eight models and **no `minimal` anywhere**: `low | medium | high | xhigh | max | ultra` on `gpt-5.6-sol`, `gpt-5.6-terra`, and `gpt-daybreak-blue-latest`; `low | medium | high | xhigh | max` on `gpt-5.6-luna`, the one row carrying `max` without `ultra`; and `low | medium | high | xhigh` on `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini`, and `gpt-5.3-codex-spark`. Codex accepts per-turn model/effort/sandbox/approval overrides (`turn/start` params — the daemon surfaces per-turn posture via `StartRunParams.executionPosture`; other per-turn knobs ride `agentConfig`). **Claude binds neither model nor effort at spawn, and a change on either axis needs no respawn.** Both are reachable in the running process through the provider's own model and effort commands, which its client dispatches itself and answers without spending a turn; the change takes effect from the next turn. Measured first-party at Claude Code `2.1.275` on 2026-09-17 over the programmatic streaming-input transport this driver drives (**Binary probe**, **Verified** at the build measured): a model command sent as one user message answered `Set model to <model> for this session only` with zero turns and zero cost, emitted a **fresh session handshake naming the new model**, and the next ordinary turn ran on that model. The spawn parameters still carry the model and effort a fresh process starts on — a resume is a fresh spawn and re-realizes them — but they are the process's opening values rather than a binding for the session's life, so the daemon applies a mid-session change to the live process, the output speed included (§The output-speed axis), and reserves a reopen for the one surface that genuinely binds at process start, `--max-turns` carrying the step bound on that same leg (§Interfaces And Contracts).

**Output-speed vocabulary.** A driver declaring `output_speed` MUST publish that axis's value set as `GetCapabilitiesResult.outputSpeedLevels`, on the same capability read the flag travels on. The rule is the `effortLevels` rule and is stated for the same reason: a mutation validated against a set the caller cannot read is a control whose accepted values are undiscoverable, so [Spec-014 §The mutation surface](014-multi-agent-orchestration.md#the-mutation-surface) validates `outputSpeed` against this list and against no list written down here. **Where the set is published per model, that reading is the set; where it is not, the driver declares it statically.** Those are not two rules but one applied to two surfaces, and the choice is decided by what the provider publishes rather than by preference. The Codex leg publishes a tier list on each model row of its own catalog read, so its vocabulary is per-model and provider-published exactly as `effortLevels` is, and a model publishing no tier list exposes no speed selection at all. The Claude leg publishes no level set anywhere and its only reading costs a turn-bearing request, so its vocabulary is declared from the driver's per-driver table — the same table the flag comes from — because a vocabulary sourced by reading there would contradict the detection source of the flag it belongs to. The member is **client-visible** on both legs, unlike the sibling `detectionSource`: its reader is a user-facing control that has to offer the choice set, exactly as `effortLevels` reaches the client that renders the effort selector. Absent or empty, the axis is unsettable for that model and a mutation carrying it refuses fail-closed rather than forwarding a value no declaration admits.

### Plan mode and the plan verdict

Both drivers reach a planning posture natively, and neither leg degrades, so **no capability flag is minted for it** — a flag would be a gate nothing consults, which §Capability discovery forbids. What the contract owes is the binding, the held verdict and the plan's own text.

- **The mode is the provider's own planning posture, selected per turn.** On Claude Code it is the permission mode that plans without acting; on Codex it is the plan collaboration mode selected on the turn request. A driver sets it for the turns the session is in that mode and restores the session's ordinary posture when it leaves.
- **A plan turn cannot change a file, by construction rather than by the model's cooperation.** The Codex leg names the `:read-only` permissions profile on the plan turn's `turn/start` **whatever the session's permission level**, because that provider's plan mode changes the prompt and locks nothing; the profile persists on the thread and across a restart, so the first turn after `Build it` names the level's own profile on its `turn/start`, and the driver reads the profile back from `activePermissionProfile`. While a plan turn runs, the daemon declines every approval request Codex raises for an escalated command or a patch, since an accepted one would write during planning. The Claude leg's planning permission mode is itself the prohibition. A driver that could not hold that guarantee would be offering a mode whose whole promise is that nothing was changed.
- **The verdict is the user's, and the driver never answers it on a timer.** Claude Code asks to leave plan mode through a request it holds open, and that request is answered only when a verdict is given: a timeout would answer for the user, and the provider treats whatever comes back as the user's own decision. A driver that expired the request would manufacture consent to run.
- **The plan's text comes from the provider frame that carried it** — the held request on one leg, the plan item on the other — and never from a file read back off the disk. A provider may also write the plan to a file; that file is a by-product the driver may name, not the record it normalizes.
- **Two strings are fixed rather than composed per run.** Keeping on planning answers the held request with a refusal carrying one fixed sentence, `The person is still reviewing the plan. Stop and wait for their next message.`, so the model is never let out of the planning posture on its own. The seed that carries a plan into a fresh session is `Implement the following plan:`, a blank line, then the plan's own Markdown.
- **A plan reconstituted under another provider carries the plan and nothing else.** The seed is the same text in both directions and carries none of the writing session's skill, agent, command or tool-server names, no pointer into its transcript, and no provider's own dialog wording or preamble. This is the §Canonical Transcript Export And Replay declared-loss discipline applied to one artifact rather than a second rule: a name from one provider's namespace resolves to nothing in the other's, so carrying it across would seed a conversation with instructions the receiving provider cannot honor.

### The model catalog read

`listModels` returns the bound provider's whole catalog **as the provider returns it**, read at every process start and never carried from one process to the next: one entry per model in the provider's own order, each carrying its context window, the per-model effort vocabulary §Provider Parameter Vocabularies governs, and whether the model has fast output (Claude Code's `supportsFastMode`, a Codex model's `serviceTiers`). The client-facing `driver.listModels {sessionId}` serves both providers' catalogs, each under its own provider and the session's own provider first.

- **The driver filters nothing and this boundary holds no visibility policy.** There is no hide-list, allow-list or favourites set here and none is added. A model the bound account cannot run is **absent from the provider's own reading** rather than returned and marked unavailable, and that absence is the only thing that ever shortens the list.
- **Each row's window is read, never written down.** The window comes from the provider at creation and after every model change: Claude Code's `get_context_usage`, and Codex's model catalog corrected by the first turn's `thread/tokenUsage/updated.modelContextWindow`, which is the usable window, 95 % of the full one. A Claude Code `[1m]` variant, and a Codex model whose catalog row lists a `max_context_window` above its default, is a second row of the same model carrying the larger window (§Required Behavior). A row whose window has not arrived yet carries none rather than a placeholder figure.
- **Every model and speed the provider lists is offered the moment it is listed, priced or not.** A model or speed the maintained price list does not carry yet stays in the catalog exactly as the provider lists it, and its requests are held with their exact tokens until the list prices it; no provider pricing page is read as a second authority ([Spec-014 §Session Cost Receipt](014-multi-agent-orchestration.md#session-cost-receipt)).
- **The read is taken on the node that runs the session**, against that session's own bound account and the provider command that node resolved, so the catalog is what that machine can actually run rather than what the machine a client is watching from could.
- **Four settlements, and a failure never resolves to an empty catalog.** The read is pending, or it is a catalog, or it is a named failure the caller may retry, or it is a catalog the provider returned empty — four distinguishable outcomes, because "the provider offers nothing" and "the read did not settle" lead a user to different acts. A retry re-reads rather than serving the reading that failed.
- **A session bound to a model the catalog no longer offers keeps that model.** The read reports the binding's model as no longer offered beside the current catalog, and the run still starts: nothing silently rebinds a live session to another model and nothing refuses its turn. A withdrawn model is a fact to report, not a reason to fail.
- **A catalog reading is refreshed when it goes stale and re-read when the node's resolved provider command changes**, so a model that has left a catalog stops being offered and a command pointed at another build does not keep serving the old one's models.
- **A model from the other provider's catalog binds a session only through a switch.** Picking a model under the other provider's heading sets a switch for the end of the run ([Spec-014 §Same-Agent Provider Switch](014-multi-agent-orchestration.md#same-agent-provider-switch)); until it lands the session keeps running on the model it has, and no read here rebinds a session to another provider's model.

## Canonical Transcript Export And Replay

Under [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md), this section owns the driver-boundary contract for reconstituting a conversation; the capabilities that _invoke_ it — an undo's conversation fork ([Spec-003](003-queue-steer-pause-resume.md)), recovery ([Spec-013](013-persistence-recovery-and-replay.md)), and the same-agent provider switch ([Spec-014 §Same-Agent Provider Switch](014-multi-agent-orchestration.md#same-agent-provider-switch)) — each own their own trigger and their own settlement.

**Three operations sit at this boundary, and replay is not the first of them.** A conversation reaches a new process one of three ways, and which one applies is decided by what the new process is:

1. **The provider reopens its own conversation**, in a fresh process of the **same** provider, under the provider's own identifier. Nothing of the conversation is re-sent as text and nothing is lost. This is `resumeSession`, and both pinned providers do it across two **different** credential homes as well as inside one — a conversation file copied into another account's home, even a signed-out one, is found and loaded there ([Provider Wire Reference §claude](../reference/provider-wire/claude.md), [§codex](../reference/provider-wire/codex.md)), which is what makes the fallback for moving a session to another account — taken only where a pinned build refuses the in-place switch — a copy-and-resume rather than a replay ([Spec-026 §Moving a session to another account](026-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)).
2. **The canonical transcript is exported and replayed as text**, the pipeline the rest of this section specifies. It is the **fallback** for case 1 — a reopen that did not load — and it restarts what the conversation contains rather than continuing it, which is why it settles `degraded` and never `applied`.
3. **A hand-over brief is composed**, by `exportHandoverBrief` on a throwaway copy of the session. This is the whole of the cross-provider path, no vendor's resume verb accepting another vendor's conversation, and it is also the floor under case 2 (§The hand-over brief is the floor, and it is visibly a floor).

The three settle as the four continuity arms [Spec-014 §Continuity, and what is declared rather than dropped](014-multi-agent-orchestration.md#continuity-and-what-is-declared-rather-than-dropped) names, and no operation here chooses an arm: each reports what it did, and the caller maps it.

### The canonical transcript is a projection, never a store

The canonical transcript is **derived from the session event log on demand and rebuilt every turn**. It is not a table, not a file, and not a one-shot migration performed once at switch time. This is the whole reason ADR-029 rejected a separate durable transcript store: a second record of facts the log already holds must then be kept in step with it, which is the divergence problem the decision exists to eliminate, relocated inside the daemon. A consumer that caches a rendered transcript across turns is caching a projection whose source has moved.

Its content is bounded by [Spec-005](005-session-event-taxonomy-and-audit-log.md): the normalized event taxonomy is the complete set of facts a driver may report, and therefore the complete set the transcript can carry. Anything a provider held that never became an event is, by construction, not in the canonical record — which is what the declared-loss rule exists to surface.

### The transform pipeline is ordered, and the order is load-bearing

`exportTranscript` applies these steps in this sequence. Reordering them is a defect, not a style choice:

1. **Fold** the run's normalized events into ordered turns.
2. **Map identity.** Every tool call keeps a stable, bidirectional mapping between the canonical id and the id the target provider sees. Replay never re-mints a tool-call identifier and never reuses one across two distinct calls — the general form of this spec's standing prohibition on letting provider-native ids replace canonical ids (§Pitfalls To Avoid).
3. **Strip what is not portable**, and record each stripped class on the declared-loss list. Provider-private reasoning is stripped here, on **both** vendors' own stated rules: reasoning is tied to the model that produced it, and is reusable at most within one model family. Stripping is by the reasoning block's kind, not by a single type name — a filter that catches only the plain reasoning kind silently leaves its redacted sibling behind and breaks the multi-turn protocol. Visible reasoning summaries are **not** stripped; they carry as plain text, because they are user-visible and therefore already canonical.

   The strip is **unconditional**, including on a same-provider, same-model replay where a vendor's own reasoning signatures would in principle still validate. Carrying them would look like a free win and is not one: a signature is validated against the block's **position** as well as its bytes, so a replay that preserved them would owe an exact reproduction of block order and count — a second, provider-specific correctness contract layered underneath the canonical one, whose failures surface as opaque signature rejections rather than as declared losses. That is precisely the divergence [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md) exists to eliminate, so the pipeline declines the win and declares the loss.

   The strip is also why a switch is applied at a turn boundary **after the target model's last assistant turn has completed**: stale reasoning on _prior_ assistant turns is tolerated (a token cost), while modifying the _latest_ assistant turn's reasoning sequence is a hard refusal. The boundary default in [Spec-014 §Same-Agent Provider Switch](014-multi-agent-orchestration.md#same-agent-provider-switch) is therefore a correctness rule, not only a courtesy to work in flight.

4. **Repair pairing integrity**, strictly after the strip. A tool call whose result was removed, or whose result never existed because the turn was interrupted, receives a **synthetic error result** naming the interruption. It is never dropped, and it is never left unpaired: the target's injection surface performs no pairing validation, so an unpaired call is accepted silently and the reconstituted session then carries tool history that does not match what happened.
5. **Render** into the target's frame shapes, with every outbound frame declaring its origin per §Required Behavior's frame-origin discriminator — a replayed user turn is `human_text` and is neutralized exactly as a live one is.

Step 4 running before step 3 would repair pairs the strip then breaks. Step 2 running after step 5 would render ids the map has not yet fixed. The sequence is the contract.

### The hand-over brief is the floor, and it is visibly a floor

A switch to a **different** provider takes the brief always. A switch to a **fresh process of the same** provider takes it only where the reopen did not load and the transcript cannot be sent as text either — `transcript_replay` is `false`, the target refuses the frames, or the transcript exceeds the target's context window. Either way the daemon composes a **hand-over brief**: one message that stands in for the conversation, sent once, framed as continuing an existing conversation rather than as a new instruction.

**The summary inside it is the old provider's own, taken on a throwaway copy of the session.** It is asked for in one shape on both providers: on Codex the copy answers the fixed template, and on Claude Code the daemon runs the provider's own `/compact` on the copy carrying that template's instruction; where the copy's own summary is not readable, the copy answers the fixed template instead. The template states each decision the person made that still holds once, with what it applies to and its current value, and lists withdrawn values under their own heading, `Withdrawn, do not use`: the person's decisions, reversed ones included, travel in the summary, while the last two exchanges travel word for word for continuity of the work in hand. The copy is what keeps the live conversation out of it: composing a brief disturbs nothing the person is watching, and the live session's bytes are unchanged across the composition. What follows the summary in the message — the current diffs and branch read from disk at that moment, every earlier step as a one-line note with its output bodies left out, the last two exchanges word for word (the interim number below), and a reference to the whole old transcript, which the daemon writes as one plain file beside the brief for the new provider to open with its own file tools — is ordered by [Spec-014 §Continuity, and what is declared rather than dropped](014-multi-agent-orchestration.md#continuity-and-what-is-declared-rather-than-dropped). This section owns only what the driver boundary has to do to produce it. The transcript file is the **daemon's** write and not a driver operation, and nothing of its contents enters the message.

**Two things are stripped before it travels, and one is read rather than assumed.** The outgoing provider's own system prompt, its environment preamble and the instruction files it loaded are removed from the brief before it is sent: that provider's summary step reproduces them among the person's own messages, and carrying them would hand the incoming provider the outgoing one's standing context as though the person had written it. So are Claude Code's opening line saying the session is being continued, its pointer to its own session file (the throwaway copy's, deleted with it), its instruction to continue without asking the person anything, and its own compaction instruction where the summary's quote of the person's last message ends with it, because the brief names its own transcript file and frames the continuation itself. And because the same summary step can quote a tool's output back into its own text, the brief's list of what did **not** carry is read off the composed brief rather than assumed from what the composer meant to leave out.

Four properties are normative, and the last is the one implementations get wrong:

- **A budget expressed as a fraction of the target's context window**, not an absolute token count, so the same rule holds across models with different windows. It is the bound on how much of the conversation travels word for word, and it is the one tuning number in this mechanism. **Its interim setting is two exchanges**, measured 2026-09-21 over 25 hand-overs drawn from six short sessions — three tasks, both directions — at tails of two, five and ten: every planted decision arrived and was implemented at every tail size, because each provider's own summary step already carries the decisions the person stated in the words they used, and the ten-exchange brief ran about four-fifths larger for nothing that measurement could see. Two stands until a longer measurement moves it, and two cases are untested: a session long enough that the summary step starts compressing the person's own words, and a decision the person later reversed, which is the case a word-for-word tail should win.
- **A protected tail of the most recent tool exchanges that the budget may not evict**, and eviction operates on **whole exchanges**: a call and its result travel together, so a tight budget can never leave one half of an exchange in the brief and the other half out.
- **Once-only delivery, enforced by a _derived_ brief-identity key rather than by a durable claim.** The obvious design — a claim written before the send and released on failure — needs a durable owner, and there is none to give it: `runtime_bindings` is ruled out for recovery state, and no generic claim store exists in the local schema, so the claim would have to mint a table to hold one in-flight marker for something the event log already determines. The key is therefore **computed, not stored**: a deterministic function of the canonical transcript projection at the export log position and the target session's identity. Because that transcript is a projection rebuilt from the log rather than a store, the same switch yields the same key on any daemon and across any restart — the key is recoverable exactly when it is needed, and **no daemon-side claim row is persisted**. Derivation is only half of the mechanism, though, and the other half is what makes reconciliation possible at all: the key is also **carried on the brief itself**, as a visible marker in the sent prose — kept legible to the human reading the target conversation rather than hidden in an invisible or zero-width sentinel, which this spec prohibits outright — because a key that were derived and never sent would leave nothing in the target to match against. Derivation supplies the key without storing it locally; carriage supplies the value to compare it to; both legs are load-bearing and neither alone yields once-only delivery. **Every send reconciles first**: recompute the key and read the target session's own recent turns for it, treating a match as delivered. That makes the ambiguous send unremarkable rather than special — a timeout, a dropped connection, or a daemon restart between send and acknowledgment leaves the outcome unknown, and the unknown resolves exactly as the known cases do, by reading the target. Rollback-then-retry is not merely discouraged but **unrepresentable**, there being no claim to roll back, which is the point: releasing a claim on an ambiguous send is how the same brief gets sent twice. Where the target cannot be read back, nothing is sent and the operation settles on what did land, because a duplicated brief corrupts the conversation the user is watching while a missing one degrades it visibly. A reopen or a replay that carried the conversation **suppresses** the brief entirely rather than sending both. This diverges deliberately from the convergent prior art in §References, which pairs an atomic claim with rollback: that design is correct where a durable claim has an owner, and derivation is what stands in for the owner here.
- **Composed at the moment of the switch**, from the log as it then stands and from disk as it then is, rather than from a rendering pinned when the fallback was decided. The one part of it not drawn from the log is the old provider's own summary, which is taken once on the throwaway copy and is that provider's output rather than this daemon's projection.

These are not derived from first principles — they are the shape independent implementations converged on, and each property exists because its absence is a known defect (§References).

Every operation settled on the hand-over brief reports `degraded`, never `applied`, and carries the declared-loss list, and so does one settled on the fallback replay: both restart what the conversation contains rather than continuing it. A degraded settlement that renders identically to an applied one is a defect: the user is entitled to know that the conversation the model can see is a summary.

### Capability discovery

`getCapabilities` is the driver-side read for everything in §Per-Driver Capability Matrix and §Parity Capability Mechanism Grades, and it is the only source a caller may consult: a capability is available when the driver declares it, never when a method exists on the provider's wire. The two are not the same set — the pinned Codex surface carries a method that is present, callable, and upstream-deprecated, and the pinned Claude binary carries a flag string for a feature removed several versions earlier ([Claude wire reference §CLI / wire surface](../reference/provider-wire/claude.md#cli--wire-surface)). Presence is not availability.

The obligation runs in the other direction too: **a capability flag is minted together with the consumer that reads it, never ahead of one.** A declared flag is a promise a caller may plan against, so one gating a capability no surface in this corpus takes is a promise no code keeps — and it decays in silence, because the reader that would have caught it wrong never arrives. A capability the corpus does not yet consume is therefore recorded in prose with its fallback, and its flag is minted together with its first reader.

**Declaration is a reading of the installed build, not of a table.** §Required Behavior binds every flag carrying an **admissible** probe — zero-turn, non-mutating, and decisive at the granularity the capability is consumed at — to be `probed` and to carry that detection source on the report. The consequence for this section is that the two directions above are not symmetric in strength: presence is not availability, and **absence is not unavailability** either — a censused registry bounds availability from below, not above. So a driver may not resolve a flag from a version comparison or from a census, and it may not resolve from this spec's matrix any flag carrying an admissible probe; it resolves those by probing and classifying the answer. The matrix remains the resolution path for **every** flag the mechanism table **declares** non-probeable, each with its failing admissibility conjunct named — and that set is the large majority rather than a pair. Over this spec's flags across both drivers, the table's `probed` entries are these, and the rest are `static`. On the Codex leg they are `steer`, `session_goals`, `context_compaction`, and `provider_commands`, each decided by the accepted-method enumeration at the granularity its consumer calls it — and on the Claude leg it is `output_speed`, read off the fast-mode state the process's `initialize` reply reports before any turn. The Claude leg's other flags have no admissible probe, which is a measured finding rather than an omission: its one zero-turn control channel refuses the outbound-raised subtypes _by name_, so a refusal there is evidence about the inbound dispatcher and not about the capability. The corollary for §Acceptance Criteria is stated rather than left implicit: the negative control AC14 requires stays **declared and dormant** on a leg that declares no probe, and is armed on a leg that declares one; both legs declare one. Static entries fall into four failing-conjunct shapes and each names its own: `mcp` on **both** drivers fails **zero-turn and non-mutating together** (the only direct probe of it is invoking a tool, which costs a turn and performs the tool's own effect); Claude `model_mutation` fails **non-mutating** alone; Claude `context_compaction` and `provider_commands` fail **zero-turn**, their evidence riding a turn-bearing session handshake; and the rest fail **decisive-at-consumption-granularity**, the Codex `rollback` and `session_fork` boundaries among them, where the enumeration establishes the method and not the parameter. The set-replacing MCP server mutation is **not** among them, because it is not a capability flag at all — it is a control-request subtype no driver-side probe may issue, and its availability is the consuming plan's own reconcile answer. The matrix and the mechanism grades remain what the corpus plans against and what a refresh compares to; they are not what a running driver reads its own answer from.

The client-facing read of the flags is the already-registered `driver.listCapabilities`, and **no method is minted here**: it is one of the client-facing `driver.*` names [Plan-004 §Namespace](../plans/004-provider-driver-contract-and-capabilities.md) registers into the daemon IPC namespace [Spec-006](006-local-ipc-and-daemon-control.md) owns, and widening what `getCapabilities` reports widens what that read serves without changing its name. The console reads `driver.listModes`, `driver.listModels`, `driver.listCapabilities` and `driver.compactContext`, and the live `/` list reaches it as `session.providerCommandsSubscribe` (§Interfaces And Contracts). Each `driver.*` name is admitted by the governing principle that bounds it: every one operates on an already-existing session or run, and none establishes, restores, starts, or tears one down. `driver.listCapabilities` also carries each driver's fixed list of built-in tools, in words a person reads, for the allowlist picker. The mechanism grades are the driver-side read's: `getCapabilities` reports flags and grades alike, but the registered client-facing payload carries the flags, and a consumer that needs a grade reads it through the daemon rather than off that reply. The driver-side obligation — that `getCapabilities` reports both, re-read on §Default Behavior's triggers — is what this spec owns.

## Desktop Console Parity Surfaces

Capabilities the pinned provider consoles expose to their own interactive users, carried here so that a user working through this product has the same control as one working through the vendor's terminal. Context compaction, the provider command and skill surface and the output-speed axis are each capability-gated, and each mints its flag **together with the consumer that reads it** as §Capability discovery requires — the composer affordances and settings surfaces named per section below; voice carries no flag, both V1 drivers delivering it (§Parity Capability Mechanism Grades). None of them introduces an error code.

### User-triggered context compaction

`compactContext` compacts the bound session's provider-side context on a user's explicit request, and only on one. The distinction from the meter hint is the whole point of the operation: [Spec-011 §Context Window and Usage Meters](011-live-timeline-visibility-and-reasoning-surfaces.md#context-window-and-usage-meters) has always said the warning is informational and that compaction is not triggered automatically, and that statement is **unchanged and still normative**. Automation remains prohibited. What changes is that the user now has a control to reach for, which is a different thing from the system deciding on their behalf, and the two are stated separately so neither can be read as the other.

**Settlement is on evidence, never on acceptance.** Both delivery mechanisms — Codex's `thread/compact/start` and Claude's `/compact` — return before the work is done: the former answers an empty ack, the latter is a command frame whose settling says only that bytes were taken. So the operation completes on the provider's own typed compaction frame, the same frame that already produces the registered `usage.context_compacted` boundary. A driver that dispatches and cannot observe that frame reports the operation failed; it never reports a compaction it did not witness. A compaction moves **no** delta base (§Required Behavior's per-turn delta rule), and the boundary it produces is what [Spec-003](003-queue-steer-pause-resume.md)'s compaction-boundary-aware rewind classifies against — this operation gives that classifier a new way to be reached, not a new thing to classify.

**The wait for that evidence is bounded, and it has two terminals rather than one.** Settling on evidence is only safe if not-settling ends: a provider that acknowledges and then produces nothing would otherwise leave the operation — and the control the user is watching — open forever. So the wait ends at whichever comes first of the driver's **declared per-binding compaction bound** (the same declared-timeout shape the child-frame pending-registration hold already uses in §Required Behavior, and a per-driver declaration rather than a corpus constant because the two mechanisms do not take comparable time) and the run's **runtime binding ceasing to be live** — a process exit or a disposal, which is a positive observation that the evidence is never coming and should not be waited out. Expiry settles **`failed`**, never `applied`, and records a diagnostic naming which terminal ended it; the operation never reports a compaction it did not witness, which is the rule this bound protects rather than relaxes.

Bounding the **operation** does not bound the **boundary's record**, and conflating the two would lose data. A typed compaction frame arriving after the wait ended is normalized into `usage.context_compacted` exactly as an unsolicited provider-initiated compaction is — the driver has no privileged "this one was requested" path, and a late frame is indistinguishable from a spontaneous one at the point of normalization anyway. So no boundary escapes [Spec-003](003-queue-steer-pause-resume.md)'s rewind classifier because a timer expired, and the user's control is told the truth it had at settlement time. The consumer side follows from the same split: [Spec-011 §Context Window and Usage Meters](011-live-timeline-visibility-and-reasoning-surfaces.md#context-window-and-usage-meters)'s in-progress state clears on the **operation's** settlement, so the control cannot hang waiting for a frame that will arrive on its own schedule or not at all, while the meter itself moves on the boundary row whenever that row lands.

**Authorization is the intervention adjudication, reused rather than reinvented.** Compaction irreversibly mutates the bound run's provider-side context for every later turn of the session, so it is not a read and it is not ungated. A caller who is not an active user of the session is refused indistinguishably from a caller naming a session that does not exist — the registered `session.not_found`, whose description is already "does not exist or is not accessible" — so the operation is no session-existence oracle. A user is then adjudicated by the **identical `Action::"intervene"` evaluation** the intervention path runs, on the run that owns the named binding, reading the [Security Architecture §Permission Matrix](../architecture/security-architecture.md#permission-matrix) run-control row — whose subject names compaction, so the citation lands on a row that names the operation rather than on one a reader has to extend by inference; the matrix gains no row, which is the same claim as reusing the action. That reuse is the `run.pause` / `run.resume` precedent exactly: those are not interventions either, and they share this adjudication rather than minting their own. **No Cedar action is minted and no error code is minted** — compaction shares the adjudication, not the envelope, so [Spec-003](003-queue-steer-pause-resume.md)'s deliberately closed V1 control set is untouched and the driver error namespace does not move. The non-local hosting-node approval leg that adjudication also carries is unreachable here by construction rather than waived: a runtime binding this daemon holds is hosted on this node, so the resolved hosting node is always local. A denial settles on the operation's own **refusal arm** — the shape an authorization-rejected intervention already uses, riding its result's reason rather than a transport error — so a caller who reaches the control learns they may not, in the same channel as every other refusal this operation can produce.

**There is no emulation arm, and the absence is deliberate.** §Capability delivery's preference order ends in a typed refusal for exactly this shape of gap. Prompt-injecting an instruction to summarize the conversation would produce a plausible-looking assistant turn and move the provider's own context window not at all — spend incurred, meter unchanged, success reported. A driver that cannot compact declares `context_compaction: false` and refuses as `driver.capability_unsupported`, which the user can see and act on.

**The Claude leg composes a `driver_command` frame**, which is the driver-composed producer class §Required Behavior guards on both sides. Because that arm is exempt from the neutralization tripwire, this section supplies the guard that stands in the tripwire's place: the command's literal name is checked against the enumeration §The provider command and skill surface reads, for that session's own binding, **before** dispatch — so a provider release that retires the compaction command refuses at the check rather than silently sending prose the model never sees — and the typed evidence above is required **after** it. Both guards bind because this frame claims an effect the daemon then reports; a frame carrying a command the user chose out of the enumeration claims none and is reported as the provider answered it.

**Each provider's own compaction point is the knob, and a turn that cannot fit is cut back by the provider's own verb.** Claude Code's automatic compaction point is set with the `env` pair `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` through `apply_flag_settings {env}`, and Codex's with `model_auto_compact_token_limit`; the Codex bottom stop is taken from the first turn's own report, because a count taken before the turn runs 119 to 125 tokens under it. A turn too long for the window even after compaction — Claude Code's result with `is_error` and a `terminal_reason` of `prompt_too_long` or `blocking_limit`, Codex's `contextWindowExceeded` — is cut with the provider's own verb, `rewind_conversation` naming that message and the newest one sent, or `thread/revert`, and handed back to the person as a failed send. Claude Code's refill breaker, `rapid_refill_breaker`, which stops a turn whose context refilled right after each compaction, lands one row, `Stopped · the context refilled right after each compaction`, with no `Try again`. A failed compaction, `compact_result: "failed"` on Claude Code, lands no row of its own; one the person asked for says why.

### The provider command and skill surface

`listProviderCommands` reads the provider's own enumeration of native slash-commands and skills for the bound session and returns it as observed. Both pinned providers publish this over the transport the driver already establishes, which is what makes it a read of the session rather than a walk of the operator's home directory: enumerating by filesystem would see definitions the running provider has not loaded, miss the ones it loaded from elsewhere, and require the driver to model each vendor's discovery precedence — three ways to be wrong about a set the provider will happily state.

**The enumeration belongs to the live provider process, and it is delivered as a subscription rather than a single read.** On Claude Code it is the command set the process declares on its own session handshake, replaced **whole** by each change the provider pushes — each push carrying the full set with a description and an argument hint per name — so a held copy is never patched into. A new process brings a new handshake and a new set, and a new process is exactly what a new session and a change of account, model or working folder applied at a run boundary produce; a consumer therefore re-reads on the new binding rather than carrying the old set across it. On Codex the wire parses no command text at all, so that leg's enumeration is the skill set the provider lists, re-read whole on the provider's own change notification. **Commands and skills are one registry on the Claude leg**, and the enumeration is the provider's **user-invocable** set rather than its model-invocable one: measured first-party at Claude Code `2.1.270` on 2026-09-13 (**Binary probe**, **Verified** at the build measured), the declared set held command-file and skill entries side by side; a skill declaring itself not user-invocable was absent from that set while the model could still reach it; a skill declaring model invocation off was present in the set while absent from the model's own list; and argument substitution worked on the programmatic input path exactly as on the one-shot path. A driver therefore offers the set it was handed and derives no second set from it. The same measurement establishes why a definition's own fields are not round-tripped through the provider: unknown and foreign-namespaced front-matter keys are accepted and dropped with no signal on the wire, so a record of a definition is the daemon's to keep, never the provider's to hold.

**It is a live read, never a stored registry, and this is a design decision rather than an omission.** Nothing is persisted, nothing is cached across sessions, and no projection folds it. A stored copy would immediately need an invalidation protocol, a staleness policy, and a reconciliation path for a definition edited outside this product between two runs — machinery whose only purpose would be to re-derive what one read already gives. The direct consequence is that this capability **adds no table and no column**. Where a provider announces that its own set has changed, the driver re-reads rather than patching its held copy, so the held state is always a whole reading rather than an accumulation of edits.

**What is on disk is a separate record kept by a separate document, and neither derives the other.** This read answers what the bound provider process has loaded, per binding and as it was observed. The record of skills as files in folders — what exists on this machine, where each one came from, which providers can reach it, and what writing or editing one does — is [Spec-030 §Required Behavior](030-skills.md#required-behavior)'s, and it never claims that a provider loaded anything. The two disagree in both directions by design: a skill written on disk that the bound process has not loaded stands in that record and not in this enumeration, and an entry a provider declares from somewhere that record does not read stands here and not there. A consumer asking what a session can invoke right now reads this surface; one asking what the person has written reads that one.

**The routing invariant.** Every entry carries the `(driverName, providerAccountId)` binding it was read under, and that binding governs both directions of use: an entry is **offerable** only to agents of that binding, and **dispatchable** only through them. A command enumerated from a Claude session is never offered to a Codex agent and never sent through one. The invariant is not defensive tidiness — the two providers share a `/name` surface syntax and share no name space behind it, so a cross-provider dispatch is either a different command or no command, and both outcomes are worse than a refusal. A dispatch that would cross the binding refuses as `driver.capability_unsupported` rather than being attempted. The account half of the key is load-bearing on its own: two accounts of the same provider can carry different skill sets, so binding to the driver alone would offer one account's definitions to another's session. An agent may hold **several live bindings at once** — V1 admits concurrent runs and a switch applied at a run boundary leaves older runs on the binding they spawned under — so the read returns one enumeration **per live binding**, each carrying the run and the `(driverName, providerAccountId)` it was read under. Collapsing them into one list is prohibited for the same reason the invariant exists at all: a flattened list is a list whose entries have lost the binding that says where they may be used.

**A disabled entry is reported, not withheld.** Where the provider publishes an enabled/disabled distinction — the Codex skill surface does, the Claude handshake enumeration does not — the driver carries that declaration through **verbatim** and filters nothing: an enumeration with disabled entries silently dropped stops being the provider's own enumeration as observed, and leaves a consumer unable to tell a disabled command from one that does not exist. The flag governs **offerability** rather than presence: an entry declared disabled is not offerable and is surfaced as unavailable rather than advertised as runnable, because the bound provider will not execute it. Where the provider draws no such distinction the driver **synthesizes none** — absence means the surface has no notion of disabled, never a driver-assumed `true`.

**The enumeration reaches the user as one list, and the console's own words come first in it.** The consumer that reads this flag is the composer surface, which keys its command list on the **target agent's** driver and account — the routing invariant expressed as an interaction rather than as a second rule — and composes that list in a fixed order: the console's own words first, each with one line of help; then, on a provider whose enumeration carries commands, every enumerated word the console does not own, marked with the provider it came from; then every skill the session can reach, each marked with its origin; then the Sidekicks group, one row per saved agent, whose row inserts that provider's own way of naming an agent; then one group per working tool server, under that server's own name, holding the prompts that server publishes. A console word that takes a name completes that name from the same place the control that owns it reads its own choices, so the list never offers a value the control would refuse.

**Three classes of leading-`/` input, and the driver sends exactly one of them verbatim.** A word the console owns is pressed on the console's own control and is **never sent to the provider**; nothing reaches this contract for it. That ownership is what decides the class, and it is decided by **who holds the value**: where a provider's own command would change something a console control already holds — the model, the permission posture, the automatic-compaction bound — the console presses its own control instead of forwarding the word, because forwarding it would move the provider's state and leave the control reading the old value. A driver therefore never treats a value the daemon owns as provider-owned merely because the provider also has a command for it. A word the enumeration carries that the console does not own is **forwarded to the provider verbatim** on a `driver_command` frame, so the provider's own client dispatches it exactly as it would in that provider's terminal. Anything else is **sent as the user's own prose** on a `human_text` frame and neutralized as §Required Behavior requires, and the provider answers it as it would in its terminal — one provider's client replies that the command does not exist and spends a turn doing so, the other reads the words as prose. There is no literal-slash escape and no product-invented unknown-command refusal: a word no row matches is a word going to the provider, not a word being refused. **A forwarded command settles on what the provider answered and on nothing else.** The driver normalizes the provider's own reply, its usage and its turn count as it normalizes any other output, and asserts **no effect it did not witness** — which is the whole of the difference between this class and the one below. The pre-dispatch presence check and the post-dispatch typed-evidence requirement §Required Behavior places on the `driver_command` arm bind the frames the **driver itself composes** to realize a daemon operation, because there the daemon claims the effect; a frame carrying the user's own chosen word claims nothing and is reported as the provider answered it.

**A daemon operation may adapt a console word onto a provider's own mechanism, and each adaptation is verified once against the build it maps.** Where one console word means the same thing on both providers but reaches it differently — a code review is the V1 case, a native review operation on one provider and a bundled skill with a matching argument on the other — the driver composes that provider's own mechanism from a typed daemon intent rather than forwarding the console's word, and the mapping is checked against the installed build before it is used. Such a frame **is** driver-composed, so it carries both guards: the literal name is checked against this enumeration for that session's own binding before dispatch, so a provider release that retires the name refuses at the check rather than silently sending prose the model never sees; and the operation settles on the provider's own typed evidence after it. The compaction command is the other V1 case and takes the same shape.

**The console words the driver answers or adapts.** `/goal <condition>` addresses the agent it is sent to; `/goal clear` removes that agent's goal, and a later `/goal` replaces the active one. `/cd` into a worktree names a path in the daemon's execution-roots directory, never a `.worktrees/<name>` folder. `/output-style` keeps Claude Code's word on the list, and the daemon answers it with `apply_flag_settings {outputStyle}` so the change is that session's alone, never forwarding the word, whose provider command writes the project's `.claude/settings.local.json` and so every session in the project. The skills in the list come from the daemon's `skill.list`. `/review` of the staged set is Codex's `custom` review target told to review only `git diff --cached`, and on Claude Code a one-turn process on the session's account and model in a temporary worktree holding only the staged changes, removed afterwards. The aside, `/btw`, runs on a copy of the conversation: on Claude Code a second process started with `--resume` and `--fork-session` in plan mode, with the session's full model id and `--no-session-persistence`, its cost the fork's total less the parent's; on Codex `thread/fork` with `ephemeral: true`, `excludeTurns: true`, `permissions: ":read-only"` and `approvalPolicy: "never"`, never `sandbox`, the daemon checking that the reply's `activePermissionProfile` names `:read-only`, its cost the fork's own `last` figure. Its answer is stored as the event `session.side_question_answered`, carrying the question and the answer.

**Reading the enumeration requires an active session and nothing more.** It is a session-scoped read: a caller who is not an active user of the session is refused the registered `session.not_found` — one byte-identical refusal for a caller outside the session and for a session that does not exist, so the read discloses no session's existence. No Cedar action and no error code is minted for it.

**Reaching the Codex enumeration and the methods the console's words press needs the provider's own extended capability negotiated at handshake.** Measured first-party at `codex-cli 0.155.1` on 2026-09-19 (**Binary probe**, **Verified** at the build measured), five of the methods those words press — the thread-settings update, the two background-terminal verbs, the collaboration-mode list and the memory-mode set — answer only on a connection that asked for the provider's experimental capability at `initialize`, and are absent from the default schema generation while present in the extended one. So the driver negotiates that capability on every Codex connection and reads the extended generation when it checks a method's shape. That is a connection property rather than a capability flag: a method that answers only on an unasked-for connection would otherwise read as absent, which is the reading §Capability discovery's registry-bounds rule exists to prevent.

### The output-speed axis

`output_speed` declares that the provider offers a user-settable output-speed mode, and both pinned providers do — by different mechanisms, which is why this section states the axis once and then states each leg's carrier, boundary and reading separately. Claude Code takes `apply_flag_settings {fastMode}` from the driver between turns, applying from the next run with no restart and no file written, and declares the resulting state on its `initialize` reply before any turn and again on its own session handshake, with the provider's own reason when that state is not the one requested; only models whose catalog entry carries `supportsFastMode: true` report fast output, and a typed `/fast` declines under the programmatic transport, so the daemon applies it itself. Codex takes a service tier on thread establishment and again on each turn, publishes the tiers each model offers on its own catalog read, and declares the thread's current tier back on establishment and on its own settings-changed notification. A driver would declare `output_speed: false` only where its provider supplies neither a level vocabulary a caller can read nor a declared-state read; no V1 driver is in that position, so the axis has no `false` arm to fall back to at V1 and nothing is emulated onto the `model` / `effort` axis, because effort and speed are different claims and a control that silently retargets one onto the other misreports what the user chose.

**What each provider's surface carries.** On Codex: a per-turn service tier the caller sets, carried on thread establishment and on every turn request and documented by the provider as applying to that turn and the turns after it; a per-model tier catalog on the catalog read, each tier an identifier, a name and a description, beside a nullable catalog default that is the catalog's own default rather than the thread's current setting; and the thread's declared tier read back on the establishment reply and on the provider's own settings-changed notification. Measured first-party at `codex-cli 0.155.1` on 2026-09-19 (**Binary probe** and **Generated schema**, **Verified** at the build measured): the tier parameter is in the default non-experimental generation, so a connection that negotiated nothing extra can set it; the catalog read published one tier on every model it returned, `{ id: "priority", name: "Fast", description: "1.5x speed, increased usage" }`, with a `2x` description on one model and a null catalog default; and the provider's own build carries the interactive toggle for the mode in its command table and lists the feature behind it as stable. On Claude Code: `apply_flag_settings {fastMode}` sent between turns and applying from the next run, the catalog's per-model `supportsFastMode`, and a declared state plus a machine-readable reason on the `initialize` reply and again on the session handshake. **The tier set is runtime catalog data rather than schema on the Codex leg**, because a tier is three free-form strings — which tiers exist, and which of them is a speed tier, is a property of the catalog reading rather than of the wire's shape. That is the whole reason this flag stays `static` there.

**The declared state is the truth; the request is not.** On both legs the mode sits behind a gate the driver does not control — on Claude Code an account-scoped gate behind the settings opt-in the driver can supply, on Codex the tier list the model the session runs on actually publishes — and each provider reports which one is refusing. So the driver reports the provider's declared state and the provider's own reason, never the value it asked for: a user who turns the mode on and is denied by their plan, or who is on a model that offers no fast tier, sees that they were denied rather than a control that appears to have worked. The axis rides the existing `agent.configUpdate` boundary machinery rather than minting its own operation.

**The value set is published, not implied, and where it is published differs per leg.** A flag that says an axis exists does not say what may be put in it, and this contract deliberately names no speed values of its own — the vocabulary is the provider's. A driver declaring `output_speed` publishes that axis's value set as `outputSpeedLevels` on the same capability read the flag travels on, and [Spec-014 §The mutation surface](014-multi-agent-orchestration.md#the-mutation-surface) validates `outputSpeed` against that list and against no list written down here. **Where the provider publishes the set per model, that reading is the set** — the `effortLevels` rule, for the same reason and with the same consequence: at the Codex pin the tier list is a member of each model row, so a provider-wide list would be wrong for some model in the same reply, and a model publishing no tier list exposes no speed selection at all, which is a reading rather than an omission. **Where the provider publishes no per-model set and the driver's own opt-in is the whole axis, the set is statically declared** from the driver's per-driver table, as on the Claude leg, whose provider reports the mode's state but publishes no list of modes. Either way the member is **served to clients**, unlike the driver-side-only `detectionSource`, because the control that offers the choice lives in the renderer. Where the list is absent or empty the axis is unsettable for that model and a mutation carrying it refuses fail-closed; there is no arm in which an unvalidated speed value reaches a provider.

**The boundary is resolved from the carrier, per driver, and never assumed.** [Spec-014 §Same-Agent Provider Switch](014-multi-agent-orchestration.md#same-agent-provider-switch) resolves an axis's application boundary from the driver's declared mechanism: a per-turn override applies at a turn boundary, a spawn-bound one at a run boundary. The Claude leg's mechanism is `apply_flag_settings {fastMode}`, accepted between turns and applying from the next run, so a mutation resolves to a **`run`** boundary, surfaced through that section's `pending` arm naming the boundary it will apply at, and no process is restarted for it. The Codex leg's mechanism is the per-turn tier, so a mutation there resolves to a **`turn`** boundary and the next turn carries it. Stating this per leg is not a formality: every other provider axis on that mutation except `driverName` and `providerAccountId` is per-turn, so a reader who does not find each leg's boundary stated will assume one boundary for both.

**The requested mode reaches the provider on its own carrier, or it does not reach it at all.** On the Claude leg the requested mode is sent to the running process with `apply_flag_settings {fastMode}` between turns, and because a flag setting lives only in the process's memory, `CreateSessionParams` carries it and `ResumeSessionParams` re-realizes it — a resume is a fresh process, so every setting the create path applies must be applied again there or the resumed leg silently sheds it, exactly as a posture-less resume would relaunch unsandboxed. A per-turn mechanism is realized on each turn request, from the agent's accepted value, and a thread established mid-session carries it on the establishment call as well. Recovery holds no original request, so the value is reconstructed from the durable spawn record written at every spawn, as posture and output schema already are. Without a carrier an accepted switch would commit the agent's speed column, settle its terminal, and then run a provider process that was never told — every read built on that row asserting a mode the process is not running in, which is a false success this contract prohibits, merely produced one layer lower. The generic agent `config` blob is **not** that carrier and does not become one: it is opaque to the spawn path by construction, so a value placed there would be faithfully persisted and faithfully ignored.

**The declared state is read where the provider declares it, and is stored in no column.** On the Codex leg the establishment reply itself declares the thread's tier, and the provider's settings-changed notification declares it again on every change, so a binding carries an observation from establishment onward. On the Claude leg the process's `initialize` reply reports the declared state and its reason before any turn, and the session handshake reports it again with each turn-bearing exchange, so that binding too carries an observation from its spawn onward, replaced whenever a handshake reports a different state. A binding that is not live carries no observation, and that is distinct from a driver that declares no such axis. Every reader is absent-until-observed and none of those absences is ever rendered as the mode being off. The observation reaches clients as a **live-scoped** projection on the agent read model, beside the requested value and present only while the binding it was read on is live — its presence being the discriminator for "this was read from the provider", and its absence meaning nothing has been read yet or ever. Where an agent holds several live bindings at once, the projection is its **most recently established** one: that is the only binding whose establishment could have realized the requested value served beside it, so the pair compares like with like instead of setting a current request against an older leg's declaration. It is deliberately written to **no column**: the agent's speed column records the operator's accepted choice and the spawn record records what to re-realize, and an observation persisted into either would be a second and staler record of a fact the running session already holds — worse, it would let a mode that stopped being available across a restart keep reading as accepted. The declared value is carried **verbatim** rather than narrowed to the published vocabulary, because that vocabulary bounds what a caller may **request** while this is what the provider **reported**: a provider returning a state the vocabulary does not list is reporting a real state under version skew, and coercing it would fabricate the very reading this member exists to prevent. So a provider that accepts the request and then leaves the mode off is rendered as a requested value beside a differing declared one with the provider's own reason attached. That disagreement is **not a switch failure** and is not reported as one — the switch applied and the provider then declared something else — so [Spec-014 §The mutation surface](014-multi-agent-orchestration.md#the-mutation-surface)'s `output_speed_unavailable` keeps its narrower meaning: the mode could not be **requested** at all.

**Detection source is `probed` on Claude Code and `static` on Codex.** §Capability discovery admits a probe only where it is zero-turn, non-mutating, and decisive at consumption granularity, and a conjunctive test fails on one. On Claude Code all three hold: the process's `initialize` reply, which the driver reads at every spawn anyway, reports the fast-mode state and its reason before any turn — `off` with `sdk_opt_in_required` before the opt-in — and a state present there is the axis. On Codex a zero-turn, non-mutating channel bearing on the axis does exist, the catalog read, so the failing conjunct is **decisiveness**: a tier is three free-form strings, and reading a returned tier as an output-_speed_ tier is a semantic judgment rather than a decidable read, so the channel exists and still cannot decide the flag in either direction. The honest shape there is a static declaration from the driver's per-driver table, paired with a runtime read of the provider's own declared state on the session the driver was going to establish anyway. A driver that promoted the Codex leg to `probed` would claim an admissibility that leg does not have.

### Voice

`/voice` does on each provider what that provider's own `/voice` does, through the same service the provider's own clients use, and the person starts talking the same way on both. It is the console's own word, with no button, and names neither provider on screen.

- **Where it is on.** Voice is on in one session at a time on this machine: the one `/voice` was typed in, held by the daemon so every window and device showing that session shows the same, and off after the daemon restarts. `/voice` in another session moves it there and the first reads `Voice ended`; `/voice` again or `/voice off` ends it, and `/voice off` with voice already off reads `Voice is already off`. Only that session's message box hears, and nothing is recorded until Space is held or tapped. A Codex session typed in a terminal has no message box here, so voice never reaches it. In the command list `/voice` reads `Talk instead of typing in this session.`
- **How talking starts.** Hold Space to talk, or tap it after `/voice tap`; the mode is one for both providers, kept in this machine's settings file as `voice.mode` (`hold` or `tap`, default `hold`, the names Claude Code's own `voice.mode` uses).
- **On Claude Code it dictates.** The words appear at the caret as they are heard and stay unsent. The window captures the audio and hands 16 kHz frames to the daemon, which runs one socket per recording to Anthropic's speech service, `wss://api.anthropic.com/api/ws/speech_to_text/voice_stream`, exactly as Claude Code's own VS Code extension does, under the session's Claude sign-in; no other Claude Code session hears it.
- **On Codex it is Codex's own call.** A call starts at the first Space once voice is on, carries the session's earlier spoken exchange as `initialItems`, belongs to its one conversation even inside the shared Codex service — Codex keeps one voice-call manager per conversation and sends its events only to that conversation's listeners, so no other session here and no Codex session typed in a terminal hears the call — and is never a row of its own. A hold reaches the call only once Space is let go: it is played in at 1.5×, pitch kept, each pause cut to 0.2 seconds, so Codex hears one finished request; the window losing focus sends it as letting go does, and Escape drops it. A tap's open microphone stays live. Space while the voice talks silences it. `/voice settings` picks Codex's voice from Codex's own `v1` list, its default marked until a pick; the pick is kept in the machine's settings file as `voice.codexVoice` (a missing key reads as Codex's `defaultV1`), sent as `voice` on each call's `thread/realtime/start`, never written into Codex's configuration, and lands `Voice set to <voice> · from the next call`. A turn Codex's voice hands the agent draws everything a typed turn draws, its reasoning and commentary included, which Codex's own terminal hides.
- **Its refusals** are `Voice isn't available on <account>.` on an account its provider gives no voice, `Dictation couldn't be sent.` when the connection fails, and `Dictation couldn't sign in to <account>.` when the service refuses the account's sign-in. Credentials stay in the daemon.

## Tool Metadata

Driver capabilities describe what the driver supports as a whole (e.g., `resume`, `steer`). Driver **tool metadata** is per-tool information the driver exposes for each tool in its catalog. The canonical V1 per-tool metadata field is `idempotency_class`, used by the daemon's two-phase command-receipt protocol during crash recovery.

### `idempotency_class`

| Value | Meaning |
| --- | --- |
| `idempotent` | Safe to re-execute on recovery. Either a pure read (`file.read`, `shell.stat`) or a write whose external target is server-side idempotent (for example `S3 PutObject` with `If-Match`). |
| `compensable` | Re-executable only when paired with a caller-supplied `dedupe_key` that the remote side honors (for example [Stripe idempotency keys](https://docs.stripe.com/api/idempotent_requests)). The driver is responsible for propagating `dedupe_key` to the remote invocation so that a duplicate request is rejected or treated as a no-op. |
| `manual_reconcile_only` | **Not** safe to re-execute automatically. Recovery halts the run with a `recovery-needed` condition (see §Fallback Behavior) and requires operator reconciliation. Two deterministic carve-outs — persisted MCP task-handle resolution and provably-never-dispatched auto-retry — are defined in the MCP floor paragraph below; every other receipt in this class halts. |

If a driver does not declare `idempotency_class` for a tool, the runtime MUST treat it as `manual_reconcile_only`. This is the conservative default and matches the existing rule that the runtime treats undeclared capabilities as unsupported.

An MCP-discovered tool is **always** `manual_reconcile_only`. The runtime MUST NOT derive `idempotency_class` from MCP `ToolAnnotations`: the MCP specification's current revision binds clients to treat tool annotations as untrusted unless they come from trusted servers ([MCP 2025-11-25 Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), MUST-strength) — and the MUST binds trust classification, not behavior derivation, so classes bind on the operator-managed assignment surface, never on annotation self-claims. The only upgrade path is the operator-governed assignment ([ADR-015](../decisions/015-v1-feature-scope-definition.md), governed by [Spec-025](./025-mcp-server-configuration-and-governance.md) §Tool-Level Overrides: Cedar-gated, trusted-server-only, always audited). The consequence is stated outright: a `manual_reconcile_only` tool in flight at daemon crash halts the run's recovery with a `recovery-needed` condition, and the halted run blocks its co-users' dependent work in that session until an operator reconciles. Two deterministic carve-outs refine that recovery dispatch without weakening the floor — the trust rule is untouched, and a class still never derives from annotations. **(a) Durable task handle**: where the call was dispatched task-augmented under the experimental [MCP 2025-11-25 Tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks) utility and the receipt durably recorded the receiver-generated `taskId` from the task acceptance response (`CreateTaskResult` — the id exists only once the receiver accepts, so a crash before that response is durably stored leaves no handle and stays on the sent-but-unacked halt below), recovery resolves the receipt deterministically instead of halting: poll `tasks/get` to a terminal status (`completed | failed | cancelled`), then read the recorded outcome via `tasks/result` — the Tasks spec binds `tasks/result` to return exactly what the underlying request would have returned, so this is result retrieval, never re-execution; a task observed in `input_required` breaks the deterministic-resolution premise (it awaits interaction the recovery sweep cannot supply) and falls back to the floor's halt with the handle preserved for operator resolution, and a purged or expired task (receivers MAY delete after `ttl`) falls back the same way; polling follows Claude Code's own figures — every 2 seconds, or the server's `pollInterval` held between 100 milliseconds and 60 seconds, halting after 10 failed polls in a row with the handle kept. On Claude Code the provider runs the task itself and restores it on resume; on Codex, which has no MCP Tasks, every server is reached through the daemon's route, and the daemon's own MCP client makes the call task-augmented wherever the tool allows and owns the handle. A server started over stdio ends with the daemon, so its task is gone and its receipt stays on the halt. **(b) Provably never dispatched**: a receipt whose send demonstrably never reached the remote side — connection refused, DNS resolution failure, or a recorded pre-send abort — is safe to auto-retry regardless of class: nothing executed, so there is nothing to reconcile. The sent-but-unacked window stays on the floor's halt — ambiguity is operator-owned. Recovery-side dispatch mirrors in [Spec-013 § Idempotency Protocol](013-persistence-recovery-and-replay.md#idempotency-protocol).

### Recovery Consequences

Recovery behavior for a receipt that was in-flight at daemon restart (Phase 2 started, Phase 3 not reached) is dispatched on `idempotency_class`. The runtime emits `tool.replayed` for an `idempotent` or `compensable` re-execution and `tool.skipped_during_recovery` for a halt; full semantics live in [Spec-013 § Idempotency Protocol](013-persistence-recovery-and-replay.md#idempotency-protocol), and event-type registration lives in [Spec-005](005-session-event-taxonomy-and-audit-log.md).

## Example Flows

- `Example: A local Codex driver starts a session through its native transport, exposes resume and steer capability, and emits normalized run events into the daemon.`
- `Example: A local Claude driver calls a remote provider API from the user's runtime node. The provider service is remote, but the canonical driver authority and policy enforcement remain local.`
- `Example: A user pauses a run. No driver supports native pause. The orchestration layer implements pause as: interrupt the active run, persist conversation history and run state to local SQLite, queue a resume. When the user resumes, a new turn is started with the full saved context. The driver only sees interruptRun followed later by startRun — it never needs to know about pause.`
- `Example: A user steers a Codex run. The orchestration layer calls applyIntervention(type: "steer", payload). The Codex driver supports steer natively via turn/steer and applies it. For a Claude run, the driver writes the content to the running process, which folds it into the same run at its next tool boundary. A driver that can accept nothing mid-run returns degraded, and the orchestration layer falls back to queuing the steer content and interrupting the current turn.`
- `Example: A client retries a steer whose response was lost in transit. The retry carries the same clientIdempotencyKey; the daemon finds the persisted intervention row and returns the originally recorded outcome without dispatching the driver a second time. A different steer accidentally reusing that key is rejected as intervention.idempotency_conflict.`

## Implementation Notes

- Keep the contract small but explicit. The runtime should not need provider-name branches to answer common lifecycle questions.
- Contract versioning should allow additive capability expansion without breaking older drivers.
- Resume handle persistence belongs to the runtime binding layer, not the user-facing domain model.

## Pitfalls To Avoid

- Do not treat a version number as a capability answer. A version is admissible for one decision — whether the build is above the floor — and for nothing else. Deciding a feature from a version comparison lets a gate outlive its reason: a feature held behind a version floor stays held on builds the admission floor already guarantees, where a probe would say so on the first spawn.
- Do not read an accepted field as a harmless one. Codex accepts a per-turn `sandboxPolicy` on an `experimentalApi` connection and enforces it, but it wipes the named `permissions` profile — `activePermissionProfile` reads back `null` and the level's read-only folders drop — so the driver never sends it; where the wire accepts a field that would undo the derived posture, the daemon refuses it.
- Letting provider-native ids replace canonical ids
- Treating missing capability declarations as implicitly supported
- Making the session engine understand transport-specific details such as JSON-RPC framing or stdio protocol
- Deriving quota or rate-limit refusals by matching provider message text rather than the provider's typed wire signals — `reauth-required` in the closed `RecoveryCondition` set is already detected mid-run from the provider's typed auth-failure signals, and the pinned Codex surface carries rate limits as first-class typed data (`account/rateLimits/read` pull, `account/rateLimits/updated` push), so text-matching is a deliberate downgrade that breaks on provider wording changes and on localization
- Neutralizing command-shaped text with invisible or zero-width characters (`U+200B` zero-width space, `U+2060` word joiner, variation selectors, Unicode tag characters). That encoding is a live prompt-injection and data-exfiltration channel, so hardened pipelines strip or reject it — a neutralizer built on it fails open precisely where a hardened pipeline is present — and it alters the bytes the model reads while staying invisible to the human reviewing the diff. The sentinel must be a character a reviewer can see.
- Applying the neutralization anywhere upstream of the driver's outbound frame — at the client composer, at queue admission, or at event append. Text mutated before it is persisted is text the audit log no longer matches and a rewind no longer reproduces, and a second application would visibly double the sentinel; the transform belongs at the one boundary that is both after persistence and before the provider.

- Re-minting tool-call identifiers during a replay, or reusing one identifier for two distinct calls. The target's injection surface validates no pairing, so the mismatch is accepted silently and surfaces later as a conversation whose tool history contradicts the audit log.
- Stripping reasoning after repairing pairing integrity rather than before. The strip breaks pairs the repair has already fixed, and the resulting transcript is accepted without complaint.
- Treating a replay call's success return as evidence that the replay worked. The injection surfaces are untyped and fail open; only the post-replay assertion is evidence.
- Caching a rendered transcript across turns. The canonical transcript is a projection of a log that has moved; a cached render is a stale answer to a question whose source changed.
- Reading the provider's method list as its capability list. A method can be present, callable, and deprecated at the same pin, and a flag string can outlive the feature it named.

- Summing per-turn usage readings into a session total, or emitting a provider's cumulative counter as though it described a single turn. Both produce the same compounding overstatement, and the second is the easier mistake to make because the number looks entirely plausible on any one turn.
- Re-basing the usage delta at a context compaction, or differencing a late-arriving usage frame against whichever reading arrived most recently. The first forgives every token spent before the boundary; the second floors a real charge to zero and files the loss as a diagnostic. Neither is visible in the emitted row, which is why both are refused at the boundary rather than detected downstream.
- Copying a base snapshot at turn dispatch so each turn differences against its own opening reading. Two interleaved turns then each re-count the interval the other metered — the double-count is invisible per row and additive across rows. One stream-ordered base per thread and axis, with attribution by the frame's named turn, is the only shape that survives interleaving.
- Projecting a frame whose thread identity the driver could not read, or inferring the parent from arrival order. A multiplexed connection offers no positional guarantee, and the failure writes another thread's words into the user's transcript under the parent's name. The inverse over-rotation is also a defect: demanding a thread identity from a censused connection- or account-scoped family quarantines every retry and rate-limit signal the corpus consumes, and suppressing a child's interactive requests with its transcript hangs the child mid-tool-call — the routing rule is family-scoped and the request carve-out is mandatory, per §Required Behavior.

- Emulating context compaction by asking the model to summarize the conversation. The turn succeeds, the summary is plausible, spend is real, and the provider's context window is exactly where it was — a success report for work that did not happen, which is the failure the typed-refusal arm exists to prevent.
- Reporting a compaction because the request was accepted. Both pinned mechanisms answer before the work is done — one with an empty ack, one with a command frame that only settles — so acceptance is evidence of delivery and of nothing else.
- Hardcoding a provider's command name into a `driver_command` frame instead of checking it against the enumeration the driver reads. A retired command name dispatches as prose the model never sees, on the one frame arm the neutralization tripwire is exempt from — the two failures compose into a silent one.
- Persisting the provider command and skill enumeration, or folding it into a projection. A stored copy needs invalidation, staleness, and reconciliation machinery whose whole purpose is to re-derive what one live read already gives, and it adds durable state to a capability that needs none.
- Offering an enumerated command outside the `(driverName, providerAccountId)` it was read from — including the narrower mistake of keying on the driver alone, which offers one account's skills inside another account's session.
- Reporting the requested output-speed value rather than the provider's declared one. The mode sits behind a gate the driver does not control, so a request is a request; a toggle that appears to have worked when the plan refused it is a lie the user acts on.
- Truncating an oversized answer to a provider-raised ask so that it fits the wire, or building that ask's refusal reason out of the payload that overflowed. The first hands the model a wrong answer it cannot tell from a complete one; the second can overflow again and leave the ask unanswered by the very remedy meant to answer it.
- Swallowing the rejection of an answer write because the exit path reports it. The exit path reports that the process died, which is a different fact from a named ask going unanswered — a write can reject on a closed connection while the ask's caller is still waiting, and the exit record never names which ask that was.

## Acceptance Criteria

- [ ] A new driver can be integrated without changing session or run domain semantics.
- [ ] Unsupported capabilities remain unavailable to the user and cannot be invoked accidentally.
- [ ] Driver recovery failure produces explicit `provider failure` detail and a `RecoveryCondition` (`recovery-needed` or `reauth-required`) rather than silent session replacement.
- [ ] An intervention retried with the same `clientIdempotencyKey` never applies twice: the retry returns the original outcome, and key reuse with a differing payload is rejected.
- [ ] A logged-out provider is detected by the zero-turn `probeAuth` before any billed turn is spent.
- [ ] A successful resume reports the driver's normalized `sessionPosition`; an unparseable CLI version or below-floor provider install refuses attach fail-closed.
- [ ] An in-flight MCP receipt with a persisted task handle resolves via `tasks/get` polling + `tasks/result` retrieval rather than halting (a purged/expired or `input_required` task falls back to the halt); a receipt provably never dispatched auto-retries; every other `manual_reconcile_only` receipt keeps the operator halt.
- [ ] User text whose first word is command-shaped reaches the model as prose on every provider-bound path, and a provider that dispatches such a frame as a command instead fails the turn visibly rather than recording a zero-turn success. Visibly means three things on both provider-bound paths: the run halts on its `run.failed` run-lifecycle event ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)) carrying the registered cause beside a `recovery-needed` condition — the asynchronous outcome a queued or orchestration-started run surfaces through, no caller being present to answer; the run's runtime binding is disposed, so no later run re-binds to a session whose client-side state may have been mutated; and an intervention caller additionally receives the cause on its own response via `DriverInterventionResult.refusalCode` whenever the trip is classified before that call resolves — a **best-effort** leg by construction, which is why the two preceding clauses, not this one, are what the criterion is met by.
- [ ] A conversation reconstituted into a fresh provider session carries every user-visible fact the timeline shows for it, with stable tool-call identity and no unpaired tool call, and the operation reports `applied` only after the post-replay assertion passes.
- [ ] A driver declaring `transcript_replay: false`, a target that refuses the frames, and a transcript exceeding the target's context window all settle on the hand-over brief, report `degraded`, and carry a non-empty declared-loss list — none of the three reports `applied`.
- [ ] A hand-over brief is composed on a throwaway copy: the live session's conversation is byte-unchanged across the composition, the live session starts no turn, and a provider whose own summary is not readable yields the fixed template with the driver saying which arm it took.
- [ ] Provider-private reasoning appears in no exported transcript and is named on the declared-loss list of every operation that drops it, while visible reasoning summaries carry forward as plain text.
- [ ] Every capability a client can invoke is one `getCapabilities` declares; no client-reachable path is gated on the presence of a provider method alone.
- [ ] A provider build above the pin attaches and runs: every capability that still answers is kept, and only a capability whose probe refuses is withdrawn — no version above the floor refuses a session.
- [ ] Capability probes complete before the first billed turn and spend none, asserted at the provider transport: a probe run against a fresh session issues no turn-start and no user-message request, and its negative control is still refused.
- [ ] The version recorded on a run's binding is the version the spawned process reported in-band, and a driver-spawned child carries its provider's auto-update opt-out.
- [ ] The detection-mechanism table is total over each driver's flag set, every `static` entry names the admissibility conjunct that fails, and no probe mutates state the session owns — in particular no driver-side probe issues the set-replacing MCP server mutation.
- [ ] A Codex conversation's posture rides the `permissions` profile named at `thread/start` and read back from `activePermissionProfile`; `sandboxPolicy` is never sent, and a turn carrying a `sandboxPolicy` or a `permissions` the daemon did not derive is refused rather than sent.
- [ ] A provider session driven across many turns reports session spend equal to its newest cumulative reading minus the establishment base, not the sum of per-turn totals: every emitted usage row is a per-axis delta from the thread's single stream-ordered base, attributed to the turn the frame names — two interleaved turns re-sum exactly, with no interval counted twice — no normalized axis counts a cached token twice and an unconfirmed containment identity diagnoses rather than silently subtracting, a fresh session's first reading meters in full (a replay-seeded session included: seeding spends nothing and the first turn's spend is real), a provider-native resume meters nothing it already emitted (the base is the prior-emitted sum, never the first post-resume reading), and a wire-declared per-turn figure that disagrees with the derived interval is diagnosed, never substituted.
- [ ] A child-thread frame never appears in the parent session's timeline and its spend never disappears: a foreign thread identity is suppressed with a diagnostic; a censused connection- or account-scoped frame routes without a thread identity while an unrecognized family without one still quarantines; a child frame racing its own parent-linked announcement is held and then released on registration, and the hold's timeout sheds with a diagnostic; an absent or unrecognized identity is quarantined under a bounded buffer rather than projected; a child's interactive request reaches the approval pipeline and is answered on the child's own correlation rather than suppressed; subagent spend lands on the subagent's own attribution, provider-internal child spend lands on the parent run, and child lifecycle is visible only as `subagent.started` / `subagent.completed`.

- [ ] `compactContext` reports success only after the provider's own typed compaction frame is observed: a mechanism that returns an accepted ack and produces no compaction boundary settles as a failure, and no path reports a compaction the driver did not witness. No code path triggers compaction from a threshold, a timer, or a heuristic — the only trigger is an explicit user request. The wait for that evidence terminates on both of its bounds — the driver's declared per-binding bound and the binding ceasing to be live — settling `failed` in each case with a diagnostic naming which one ended it, while a compaction frame arriving after settlement is still normalized into a `usage.context_compacted` boundary, so no boundary is lost to an expired wait and no expired wait settles `applied`.
- [ ] A **driver-composed** `driver_command` frame is dispatched only after that command's literal name is found in the enumeration read for that session's own binding: with the name absent, the driver refuses rather than sending prose the provider will not act on. A frame carrying a command the user chose out of the enumeration is forwarded verbatim and settles on the provider's own answer, and no path reports an effect for it that the provider did not report.
- [ ] An entry returned by `listProviderCommands` is offerable only to agents of the `(driverName, providerAccountId)` it was read from, and dispatchable only through them: a Claude-enumerated command is neither offered to nor sent through a Codex agent, and a cross-binding dispatch refuses as `driver.capability_unsupported`. An enumerated entry the console does not own is forwarded verbatim when the user selects it and settles on the provider's own answer, and no path reports an effect the provider did not report. The enumeration is served from a live read: no table, column, or persisted projection holds it, and a definition changed between two sessions is picked up by the next read rather than by an invalidation path.
- [ ] The output-speed axis reports the provider's declared state and the provider's own reason when that state is not the requested one — a request the provider's account or settings gate refuses never surfaces as an enabled mode — and a driver declaring `output_speed: false` offers no speed control and emulates none onto the `model` / `effort` axis. A driver declaring `output_speed: true` publishes the axis's value set on the same capability read, that set reaches the client on both the live and the cache-reconstructed read, and a mutation carrying a value outside it — or carrying any value where the set is absent or empty — refuses fail-closed rather than forwarding the value to the provider. An accepted mode reaches the provider process: a fresh spawn and a resume both carry the requested value, and a resumed leg whose spawn record held one never relaunches at the provider's default. What the provider then declared is readable beside what was requested for as long as the binding is live, so a provider that accepts the opt-in and leaves the mode off is rendered as a disagreement with a reason rather than as an enabled mode or as a failed switch.
- [ ] Neither console-parity verb is reachable without session authorization, and neither mints a Cedar action or an error code to say so: a caller who is not the session's owner is refused indistinguishably from a caller naming a session that does not exist, that owner may read the command enumeration, and `compactContext` is refused for any other caller by the same `Action::"intervene"` adjudication the intervention path runs — the refusal arriving on the operation's own refusal arm, before the capability gate and before the driver is called.
- [ ] An answer larger than the driver's outbound frame bound reaches the provider as that ask's own refusal shape carrying a bounded constant reason, never as a truncated result or a prefix of itself, and every attempt that does not reach the provider — oversized, unencodable, or write-rejected — leaves a driver diagnostic behind rather than a silently unanswered ask.
