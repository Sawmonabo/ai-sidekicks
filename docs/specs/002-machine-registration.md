## Purpose

Define the runtime node, the backend's name for a machine that runs the daemon: how it registers with the control plane, how the person's other devices know whether it can be reached, what it reports about itself, which folders it can reach, and the shells a session opens on it, with the per-shell lease that decides which of the person's devices may type into each shell.

## Scope

This spec covers the machine's registration with the control plane, its reachability, the facts it reports on request, the list of folders it can reach, a session's shells, ordered writes to a shell, the per-shell device control lease, and the local-only fallback when the control plane cannot be reached.

## Non-Goals

- Driver-specific provider protocol details
- Detailed queue and run semantics
- Attaching a machine to a session, or putting a second machine behind one session. A session runs on the machine it was started on for its whole life; nothing moves it, copies it to another machine or dispatches its work elsewhere ([Spec-027 §One user, many devices, any number of machines](./027-remote-control.md#one-user-many-devices-any-number-of-machines)).
- A roster of machines per session, capability declarations as session events, and a version floor checked at attach. The version range between an app and a service is [Spec-027](./027-remote-control.md)'s and [Spec-021](./021-desktop-app-and-renderer.md)'s.
- Device linking, the account's statement chain and the encrypted channel, one per device and machine on the Noise Protocol Framework's `Noise_KK_25519_ChaChaPoly_SHA256`, which are [Spec-027](./027-remote-control.md)'s.

## Required Behavior

- **One machine, registered once, keyed by the machine and its owner.** The runtime node is a machine that runs the daemon. The daemon mints the machine's id (`node_id`) at its first start, together with the machine's identity key, and reads the machine's friendly name then: on macOS `scutil --get ComputerName`; on Linux `PRETTY_HOSTNAME` from `/etc/machine-info`, falling back to the static hostname; on Windows the DNS host name without its domain, which is what `os.hostname()` returns there, never `%COMPUTERNAME%`, which is the 15-byte uppercase NetBIOS name. On macOS the name is never `os.hostname()` (`Name-Mac-mini.local`). At its first connection to the control plane the machine registers (`runtimenode.register`) with its id, its public identity key, its name, its platform and its service version, under its owning user. The control plane accepts the registration only for a key enrolled to that user: `sidekicks sign-in`, run while the service is stopped, reads the identity key's public half itself and enrolls it with the control plane as this machine's key, and a removed machine that is linked again re-enrolls the new key it mints with its new `runtimenode.added`. The registration is keyed by the machine and that user and never by a session: the pair is what the person's other devices look the machine up by and what the control plane authorizes against. The id and key stay the same across restarts and reconnects. A Windows computer is one machine whichever side runs its service, a Windows install or a WSL 2 distribution, and a move between them keeps the id, the key and the registration.
- **Any number of machines, each session on one.** A person may have any number of machines. Each session runs on the machine it was started on for its whole life, and nothing moves it, copies it to another machine or dispatches its work elsewhere ([Spec-027 §One user, many devices, any number of machines](./027-remote-control.md#one-user-many-devices-any-number-of-machines)).
- **The machine's key.** The machine's identity key is the service's Ed25519 key, tagged `ed25519`, kept as its own item in the operating system's credential store ([ADR-020](../decisions/020-cli-identity-key-storage-custody.md)) and never leaving the machine. It is minted at the service's first start and again only when a removed machine is linked again. Every device pins it and refuses a machine that answers under a known id with a different key and no later `runtimenode.added` statement for that id behind it; those are the only ways the key changes, and an ended key is never trusted again ([Spec-027 §The encryption envelope](./027-remote-control.md#the-encryption-envelope)).
- **Rename and removal.** The person renames a machine (`runtimenode.rename`) and the new name is the one every device shows, in `Runs on <machine>` among other places. The name read at first start is only the default. The person removes a machine (`runtimenode.remove`), which posts a `runtimenode.removed` statement to the account's chain; its sessions stay on it, and the machine comes back only by being linked again, which first mints a new identity key under its same machine id, its store, sessions and id staying as they were ([Spec-027 §Device registration and revocation](./027-remote-control.md#device-registration-and-revocation)).
- **Reachable or not reachable, and nothing else.** A machine keeps one outbound connection to the relay while its service runs. It is reachable while that connection is up, and after 45 seconds without a frame it is not reachable, with the time it was last seen, read from the relay connection. There is no heartbeat, no liveness sweep, no degraded state and no second record of the same fact. The relay holds at most one live connection per machine key, so a new connection under the key closes the one before it. Two connections under one key that keep displacing each other, three times within a minute, mean the key is in two places: the newest connection still wins, and the relay flags the key. A machine's reachability is never written to a session's log and never rewrites the record of which machine ran a run. Besides reachability, the registration carries the service version, and the version range decides whether another device drives the machine or reads it only: each app accepts its own service version and the previous one ([Spec-027 §A machine that cannot be reached](./027-remote-control.md#a-machine-that-cannot-be-reached)).
- **A machine reports its own facts, and they are read rather than sampled.** A machine reports whether its service is running, when it started, its version, and how much of the machine's processor and memory the service is using. Those readings are taken on request — when Settings › Runtime opens, and again when the reader asks for a fresh one — and each carries the time it was taken, so a reader is never shown a figure without knowing how old it is; nothing samples them on a timer and no other surface derives them. On Settings › Runtime the service's own line reads `Running · started 3 hours ago · version 0.1.0`, with the processor and memory figures beside it, labeled `Processor` and `Memory` and each stamped with its time, `<percent>% · as of <time>` and `<size> · as of <time>` (as in `3% · as of 1:16 PM`), read again on `Check again`, under one line: `Everything above is read from the service and is not edited here.` While it loads it reads `Reading the background service…`, and a figure not read yet reads `Not read yet`. A service that does not answer is reported as not answering, `The background service is not answering.`, which is a different state from the person having no service at all, and the controls that act on it stay available rather than being withdrawn. A ceiling on the memory a tool process may use, `Memory cap for tool processes` (one size field, empty meaning no cap, a figure that is not a size refused under the field with the field left as it was), is a machine-level setting the service enforces wherever the operating system lets it, reports as unenforceable where it does not, and, when the ceiling stops a process, records against the session that owns it, naming the command and the figure.
- **The folders a machine can reach are a list, and a folder is removed only while nothing is working in it.** A machine reports the folders it can reach as one row each — a project's folder, and each worktree the app made beneath its project, marked `worktree` — under the heading `Folders this machine can reach`, and every row says what is using that folder, `2 sessions are using this folder.` or `Nothing is using it.`, beside its `Remove`. A project's folder can be removed while no agent is running anywhere in the project, and a worktree while none is running in it; while one is, the removal is refused, and its control is grayed with its title naming the running session, `Busy: <session> is running in it.` Removing a project's folder is the same act as deleting the project, detaching it (`repo.detach`), and leaves its sessions and the folder on disk; removing a worktree follows the worktree's own retire rule (`repo.worktreeRetire`). A chat's session workspace carries no removal: it is deleted only with its session. The surface that carries the list says, above the rows, when a folder can be removed: `A project's folder can be removed while no sidekick is running anywhere in the project, and a worktree while none is running in it.` With no folder mounted the list reads `No folders are mounted.` rather than drawing an empty table. On a Windows computer with WSL, a worktree whose folder is on the other side's disk carries one line on its row: `This folder is on another disk, so sidekicks read it more slowly.`
- **One control lease per shell.** Write access to one of a session's shells is an exclusive per-shell lease: a session may open as many shells as the machine can hold, each shell has a holder of its own, and exactly one writer holds a given shell at a time. Every take, every holder reading and every lease change names its shell through a terminal identifier, so this device may hold one shell while another of the person's devices, or a run's write path, holds another. The grain rests on that domain invariant, deliberately not on the sidecar wire: the PTY-host protocol's `session_id` is the sidecar-minted per-spawn PTY handle (`packages/runtime-daemon/src/pty/host/protocol.ts#SpawnResponse`), a machine-local namespace in which every shell and tool spawn gets its own id ([ADR-018 §Context](../decisions/018-windows-v1-tier-and-pty-sidecar.md#context)) — not the application `SessionId` — and the daemon's terminal-session leg owns the session → shell → PTY-handle mapping, applying each shell's lease check to the writes bound for that shell's handle (a provider process's own shell and its tool spawns are not terminal surfaces and sit outside the lease entirely).
- **Taking a shell.** `session.takeControl {sessionId, terminalId, outputSubscriptionId, force?}` takes one shell's lease for the calling connection, bound to `outputSubscriptionId`, that connection's own `pty.outputSubscribe` subscription to the shell: the pane the take was made from. A take or a write naming a subscription that is not the calling connection's own open subscription to that shell is refused with `pty.output_subscription_not_found`, so a hold is never bound to another connection's pane or to a pane on another shell. A request naming a shell its session does not have is refused with `pty.not_found`, so a terminal id never reaches another session's shell; the flow-control signal is the one exception, and naming such a shell there changes nothing, since it may race a closing shell. An uncontested take succeeds at once, with no approval hop. A take by the device already holding that shell is an idempotent success: the calling connection and subscription join the hold, the response names the caller as holder, and nothing broadcasts. A plain take while another device holds that shell is refused with `pty.control_held_by_other { holderDeviceId }`; the caller takes again after it sees the lease change, and there is no wait queue, no reservation and no grant on release.
- **The first input takes a free shell.** While nobody holds a shell, a device's first write to it takes that shell's lease for the connection it came on, bound to the output subscription the write names (`pty.write` names one, as a take does), and then lands, in one step at the daemon with no confirm, because nobody loses anything; the take broadcasts `pty.control_changed` with `reason: 'taken'` like any other, and of two devices writing at once exactly one takes it. A write from a connection the hold is bound to, through another of its panes' subscriptions to that shell, lands and binds that subscription to the hold too, with no broadcast, so typing in a pane keeps the hold through that pane as a take there would. Every other write — from a connection the shell's hold is not bound to, another connection of the holding device included until it takes the shell, or a run's to a shell it does not hold — is refused with `pty.control_not_held`, per shell, so a lease on one shell never authorizes a write to another, and the refused device's pane then reads `<device> holds the shell.` with `Take the shell`, its input refused and never silently dropped.
- **A forced take.** The forced form (`force: true`) moves a shell's lease off another of the person's devices with nothing from the holder, broadcasts the change with a reason naming the force, and leaves every other shell of the session untouched; the displaced device's next write is refused like any non-holder's, so it loses a half-typed line and nothing more. A connected but idle device therefore never blocks another: the forced take is the recourse, one shell at a time. **A forced take is refused while a run's command holds the shell**, with the same `pty.control_held_by_other`: the person stops that command from its row, or pauses or interrupts the run ([Spec-003 §Required Behavior](./003-queue-steer-pause-resume.md#required-behavior)), and the hold ends when the command ends or the run leaves `running`, whichever comes first. No take, forced or not, ever signals or stops the foreground process: the lease decides who writes next, enforced per write frame, so a handoff lands between frames.
- **There is no release.** No verb and no control gives a shell back. A run's hold ends with its command or the run, as the next item says; a device's lease ends only when another device takes it, when a forced take moves it, or when every binding it was taken through has ended, and an agent's command that takes it keeps it aside and hands it back, as the next item says. Each binding of a hold is a connection and the output subscription of the pane it took or wrote to the shell through; the connection ending or the subscription closing ends that binding, and the hold ends with its last, so a hold also ends when the output subscription it was taken through closes and nothing else binds it. Each further connection or pane of the device that takes a shell the device already holds, and each further pane of a bound connection that writes to it, joins the hold with a binding of its own: a device that drops off the network — a lid closed mid-command — gives its shells back by itself with nothing to press, and closing a pane gives back this device's leases on that pane's shells, which keep running, unless another of its panes took them too. A revoked device's channel is closed, which ends its connections and so its leases. When a connection ends, the daemon reads that end before the ends of the subscriptions it carried, so a hold that ends with the connection is released as a disconnect (`auto_released_disconnect`), and `auto_released_pane_closed` means a pane closed while its connection stayed open.
- **A run's hold lasts its command.** An agent's command takes a shell nobody holds, or one a device holds, while nothing is typed at its prompt (the agent's command checks this as it takes) and no command is still running in it, never by force. When it takes a device's hold, the daemon keeps that hold aside with its bindings, and a connection that ends or an output subscription that closes meanwhile leaves it. When an agent run's write path takes a shell for one of its commands, the daemon records the acquiring run on its lease record and names it as `holderRunId` on `pty.control_changed` and on the shell's holder reading, set while an agent's run holds the shell and absent while a device does; `holderDeviceId` stays the machine's own device identity, because every local writer on the machine resolves to it, and the agent's name comes from the run. The daemon releases that hold when the command it was taken for ends, broadcasting `reason: 'auto_released_command_ended'`, or on the run's first lifecycle transition out of `running` after the take — into `waiting_for_approval`, `waiting_for_input`, `paused` or a terminal state per the [Run State Machine](../domain/run-state-machine.md) — broadcasting `reason: 'auto_released_run_idle'`, whichever comes first. Either release hands the shell back to the hold kept aside, naming that device as the holder after the change, while one of its bindings is still open, so that device's body goes live again and every other device keeps `<device> holds the shell.`; with no hold kept aside, or none of its bindings open, nobody holds the shell, every device shows no line and a live body, and the first input takes it. So between an agent's commands the shell is the person's, a finished, blocked or paused agent never strands a shell, and the run's next command takes again. A hold one of the person's devices took carries no run, and no run transition releases it. A take by a different run on the same machine re-binds the record to that run and broadcasts `pty.control_changed` with `reason: 'taken'` and the new `holderRunId`, because the holder reading names the run's agent, so under concurrent runs ([Spec-014](./014-multi-agent-orchestration.md)) the record names the most recent acquiring run and keeps any device hold kept aside: a sibling's later idle transition or command end releases nothing, and when the recorded run's command ends or the run goes idle a still-running sibling's next command takes again, never a mid-command failure. A same-run retake for the same command and a device's idempotent self-take never rewrite the record and broadcast nothing; a same-run take for another command keeps the run and names that command as `holderCommandId`, broadcasting `pty.control_changed` with `reason: 'taken'`, so the holder reading always names the command that holds the shell.
- **The lease is not the agent-control surface.** A person who needs an agent's command stopped stops it from its row, and its end hands the shell back; pausing or interrupting the run hands the shell back while the command runs on; a lease contest never stands in for either.
- **Who holds a shell is shown to every device.** Each shell's live output opens with its holder, and every lease change broadcasts `pty.control_changed`, naming the shell, the new holder and the reason — `taken`, `taken_by_force`, `auto_released_disconnect`, `auto_released_pane_closed`, `auto_released_command_ended` or `auto_released_run_idle` ([Spec-005 §PTY Control](./005-session-event-taxonomy-and-audit-log.md#pty-control-session_lifecycle)). Every change of a shell's holder raises that shell's lease version by one, from 0 when the shell opens, and the daemon never gives a terminal id to a second shell, so one id's versions always count one shell's changes; the version rides `pty.control_changed`, the shell's `pty.list` entry and the scrollback frame that opens its output, and a device keeps whichever holder reading carries the higher version, so a change delivered after a newer listing never undoes it. A device learns its own id from `deviceId` on the connection handshake's reply and reads `holderRunId` beside the holder, so it tells apart "this device holds the shell", "another device holds the shell" and "a run holds the shell", naming the run's agent. The wire admits a write per connection while the screen reads the holder per device, and these agree because each device has exactly one client connection that can take a shell: the desktop's main process, whose windows share it. The CLI takes no shell. While nobody holds a shell, every device shows no lease line and a live body, since its first input takes the shell. Until a shell's holder has been read, that shell shows no lease line and a read-only body, so a device never types into a shell it may not hold. A `pty.control_changed` carrying any other reason, `released` or `auto_released_authorization_lost` among them, is a transition the device cannot read: it shows no holder for that shell and writes nothing to it until a transition it can read arrives.
- **Only the holder sizes a shell.** A resize (`pty.resize`) from a connection the shell's hold is not bound to is refused, with `pty.control_held_by_other` while another device or a run holds it and with `pty.control_not_held` while nobody does or its own device holds it through other connections. Other devices draw the shell at its own size, clipped or scaled, with no horizontal overflow; with no holder the last size stays, and after a take the shell fits the new holder's pane.
- **Closing a shell respects both holds.** Closing a shell (`pty.close {sessionId, terminalId, force?}`) ends it. It is refused with `pty.control_held_by_other` while a run's command holds the shell, whose hold ends when that command ends or is stopped from its row, or the run leaves `running`; while another device holds it the close is refused unless it carries `force: true`, which a client sends only after the person confirms in place.
- **Where the lease is enforced.** The lease is enforced at the daemon's terminal-write boundary, where the authenticated writer is known, and the daemon that owns the terminal is the only lease authority: the take is registered on the daemon's own transport and on nothing else. The writers at that boundary are the device beside the machine, the machine's own agent runs, which write as that same device identity (per-agent attribution rides the run and agent events, never the lease record), and another of the person's devices, whose take and whose writes both ride the same encrypted channel to the machine, with the device key that channel verified as the one identity for lease and writes ([Spec-027 §The encryption envelope](./027-remote-control.md#the-encryption-envelope)). The PTY-sidecar wire carries no lease: its `WriteRequest` frame (`packages/runtime-daemon/src/pty/host/protocol.ts#WriteRequest`) carries no holder field, because bytes that reach the sidecar are already lease-authorized (the sidecar's own `WriterUnavailable` write error is a process-level stream guard beneath this policy layer, not a lease surface). A lease carries no time bound and no fence issued by any other party.
- **Why exactly one writer.** Exactly one writer is deliberately stricter than the surveyed multi-editor grants — Warp's granted-Edit session sharing and Live Share's host-granted terminal read/write — on correctness grounds: a PTY has a single input stream, so concurrent writers interleave keystrokes into corrupted command lines, and the lease makes handoff explicit and instant instead. tmux's absent write lock and Replit's multi-writer shared shell are the unguarded counter-examples, and Devin's pause-before-takeover discipline for human-agent handoff is the ordering the run-scoped release mechanizes (§References).
- **A session's shells.** A terminal surface belongs to a project session: the machine starts the account's own login shell, read from the account's record at each open rather than from an environment variable or a value kept since the service started, so a shell changed with `chsh` is the one the next tab opens, as a login shell with its working directory the session's own tree, so that account's profile, aliases, prompt, version managers and tools are all present; where that login shell cannot be started, the machine falls back to the platform's own default shell and says so in one line above its prompt, naming the shell it could not start, the reason in plain words and the shell it runs instead (`Could not start /opt/homebrew/bin/fish (no such file), so this tab runs /bin/zsh.`), rather than failing quietly. Windows has no login shell, so a tab there starts the platform's default. A chat session, bound to a managed workspace and no repository, has no shell, and `pty.open` on one is refused with `pty.chat_unsupported`. A session's shells belong to that session and keep running whichever session a client happens to be showing; closing a terminal view ends none of them, a shell ends when it is closed or when its own program exits, and an exited shell keeps its record with the exit status rather than disappearing from a surface that was already showing it. The session's shells are one live list (`pty.list`): a terminal surface opened afterwards lists the shells the session still has and no others, a shell opened from another device arrives as a new tab, and a new shell (`pty.open`) is started only where the session has none or the person asks for one, so a session that already holds shells gains no extra one by being looked at. A session opens as many shells as the machine can hold; the only refusal is the machine's own, put into words, never a count kept anywhere else. The order of a session's shells is the daemon's (`pty.reorder`). Each shell is named by the title it sets for itself, and by the base name of the program it was started as until it sets one; no name is ever typed by a person. Quitting a client never ends a shell — the machine keeps every open shell running, so a server started in one is still serving after a relaunch. A shell drawn again, by another client or after a switch back or a restart, is sent its scrollback at the rows and columns it was last drawn at before its newest frame is written, so a running program's boxes and progress bars come back intact instead of rewrapped, and output already covered by that scrollback is not sent twice. Each shell keeps its last mebibyte of output as its scrollback window, bounded in bytes, and drops its oldest whole lines once it is full, so the scrollback starts at the first whole line; output no client is watching is held in the same window, and a single burst larger than the window keeps its tail.
- **A shell's output keeps pace with its slowest live reader, never its slowest reader.** Each connection reports, per shell, whether it has fallen behind (`session.setTerminalFlowControl {sessionId, terminalId, paused}`). The daemon pauses the shell's read only while every live watcher of that shell is behind; a single watcher that falls behind stops receiving output and catches up from the scrollback window, so it never freezes a healthy watcher, and a connection's behind state clears when it disconnects.
- **Writes to a shell are ordered and bounded.** Bytes reach a shell in the order they were sent: one write is in flight at a time and anything arriving while it is in flight rides the next one, so nothing between the keyboard and the shell can shuffle them. A backlog of resize requests collapses the same way, to the newest size only, so a shell is told the size a drag stopped at rather than every size it passed through. A paste of any size reaches the shell whole and in order: the machine writes it to the shell in pieces no larger than its own write bound, one after another, and nothing is refused or dropped. Where the program running in a shell has asked for pasted text to be marked as pasted (bracketed paste), the whole paste is wrapped in the start and end marks before it is split, so the program reads one paste and several lines arrive at the prompt as text instead of running themselves, and an end marker carried inside the pasted text is removed so it cannot close the wrapper early. Each of these bounds is the machine's and is enforced there; no client keeps a figure of its own.

## Default Behavior

- A machine registers once, at its service's first connection to the control plane, with the name read at first start as its default; after that only a rename changes the name. A Windows computer whose service runs in WSL 2 registers the Windows computer name as its default and its platform as the computer's (`Windows 11 24H2`), never the distribution's.
- A machine with no connection to the relay is not reachable; there is no state between reachable and not reachable.
- A new shell starts with no holder, and the first device to write to it takes it.
- A shell's scrollback window is 1 MiB of output.
- A shell's size is the size its holder last set, and with no holder the last size stays.

## Fallback Behavior

- If the control plane cannot be reached, the local daemon stays usable for `local-only` work on that machine, from the desktop app and the CLI beside it.
- If the machine cannot be reached, another device says so plainly and keeps what it last read; anything that needs the machine refuses and is retried by the person once it is back ([Spec-027 §A machine that cannot be reached](./027-remote-control.md#a-machine-that-cannot-be-reached)). Its sessions stay exactly where they are.
- If the machine's relay connection drops, it reconnects under the same id and key, and nothing about the sessions on it changes.
- If a shell cannot be started, the machine reports the cause in words and that shell's record reads as exited, taking no input, rather than the failure passing in silence. If the session's own tree has gone from disk, no shell of that session can be started at all, and the machine answers with that cause instead, because every shell of the session has lost its working directory.

## Interfaces And Contracts

- `runtimenode.register` — sent by the daemon at the machine's first connection to the control plane, carrying the machine's id, its public identity key with its algorithm tag, its name, its platform and its service version. The owning user is the caller's verified identity, never a value in the request body, and the call is accepted only when the key is the one enrolled to that user for this machine at `sidekicks sign-in` or when a removed machine is linked again; any other key is refused.
- `runtimenode.rename` and `runtimenode.remove` — the person's rename of a machine and its removal, the removal posting a `runtimenode.removed` statement ([Spec-027 §Interfaces And Contracts](./027-remote-control.md#interfaces-and-contracts)). `runtimenode.certificateChallengeSet` writes the DNS challenge record for a machine's shared-port certificate on the self-hosted relay ([Plan-025](../plans/025-remote-control.md)).
- Every `runtimenode.*` call is decided against the caller's verified identity, and every call that changes a row decides against that row read under lock in the same transaction as the change. A caller who does not own the machine is refused with one code, `runtimenode.permission_denied` (403), that never says whether the machine exists.
- The machine's facts are `daemon.status.read` ([Spec-006](./006-local-ipc-and-daemon-control.md)). The folder list is `repo.mountList`, removed through `repo.detach` for a project's folder and `repo.worktreeRetire {worktreeId, discard}` for a worktree ([Spec-007](./007-repo-attachment-and-workspace-binding.md)).
- A session's shells: `pty.list` (the live list), `pty.open`, `pty.close {sessionId, terminalId, force?}`, `pty.reorder`, `pty.outputSubscribe` (the scrollback at the last size, then the tail), `pty.write`, `pty.resize`, `pty.reportTerminalAppearance` (the console theme's colors, or the holding pane's colors and cell size, which a program's questions to its terminal are answered from), `session.setTerminalFlowControl {sessionId, terminalId, paused}`, and `session.takeControl {sessionId, terminalId, outputSubscriptionId, force?}` with its event `pty.control_changed`, which names the shell, the holder, the reason and the lease version. There is no release verb; a hold also ends when the output subscription it was taken through closes. The forced take is a member of the take's own request, not a second method, since it is the same act under a stronger precondition. All of them carry the shell's terminal identifier and are registered in the [Session Terminal-Control Method Registry](../architecture/contracts/remote-control-payloads.md#session-terminal-control-method-registry); refusals use the `### PTY` codes in [Error Contracts](../architecture/contracts/error-contracts.md), the forced take's refusal against a writing run's hold among them.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request and response schemas, and [Error Contracts](../architecture/contracts/error-contracts.md) for error codes.

## State And Data Implications

- The machine's registration is one durable row on the control plane: its id, its owning user, its public identity key with its algorithm tag, its name, its platform and its service version. The row holds only the current key, and a machine's key is never kept in `devices`: a key replaced when a removed machine is linked again is kept in the account's chain, in its `runtimenode.removed`; a statement an ended key signs afterward is refused, and it is never trusted again.
- Reachability is not stored: it is read from the machine's relay connection, and the relay writes a last-seen time.
- Each shell's lease lives only in the daemon that owns the terminal: the holding device with the connection and output subscription of each of its bindings, or, for a hold taken by an agent run's write path, the acquiring run, and the lease version. Its holder and version reach clients only on `pty.control_changed`, the shell's `pty.list` entry and the scrollback frame that opens its output, and it is in no control-plane table.
- A machine's reachability never rewrites the record of which machine ran a run.

## Example Flows

- `Example: The person installs the app on a Mac mini. Its service starts, mints the machine's id and key, and reads "Mac mini" as its name. The person stops it and runs sidekicks sign-in, which enrolls the key. When the service starts again, it registers at its first connection to the control plane, and the control plane accepts the enrolled key. On the phone, the machine's card reads Reachable.`
- `Example: The phone holds the shell in "Fix the token refresh". At the Mac, the person presses Take the shell and confirms; the phone loses its half-typed line and its pane now says the Mac holds the shell, while the build running in that shell carries on.`
- `Example: An agent's running command holds a shell. A forced take from the laptop is refused; the person pauses the run, the hold is released, and the laptop takes the shell.`

## Implementation Notes

- The machine's id, key and name are read once, at the daemon's first start, and the registration is sent at its first connection; nothing about the machine is session-scoped.
- The lease check runs per write frame at the terminal-write boundary, so a take lands between frames.
- The lease record lives with the terminal it guards; a connection's end or a closed output subscription releases a lease only when no other binding of the holding device's hold remains.

## Pitfalls To Avoid

- A second record of reachability beside the relay connection, such as a heartbeat table
- A registration keyed by a session
- A control that releases a shell, or a lease held per session rather than per shell
- A lease change that signals or stops the program running in the shell
- A count of shells kept anywhere but the machine

## Acceptance Criteria

- [ ] A machine registers at its first connection to the control plane with its id, key, name, platform and version, keyed by the machine and its owning user; a registration whose key is not the one enrolled to that user is refused; and a restart re-registers nothing and keeps the id and key.
- [ ] A machine whose relay connection has carried no frame for 45 seconds reads as not reachable with its last-seen time, and reads as reachable again when the connection returns, with no heartbeat anywhere.
- [ ] An uncontested `session.takeControl` for a named shell succeeds at once, `pty.control_changed` naming that shell is broadcast, and every other shell of the session keeps its own holder.
- [ ] A device's first write to a shell nobody holds takes that shell for its connection and the output subscription the write names, broadcasts `pty.control_changed` with `reason: 'taken'`, and lands; of two devices writing to a free shell at once exactly one takes it and the other's write is refused with `pty.control_not_held`; a second connection of the holding device that has not taken the shell is refused the same way, and so is a run's write to a shell it does not hold, and a lease held on one shell never authorizes a write to another; a bound connection's write through another of its panes' subscriptions to the shell binds that subscription, so the hold outlives the pane it was taken through; and a take or write naming a subscription that is not the calling connection's open subscription to that shell is refused with `pty.output_subscription_not_found`.
- [ ] A plain `session.takeControl` while another device holds that shell is refused with `pty.control_held_by_other` carrying `holderDeviceId`; after the holder's connection ends or a forced take moves the lease, the same take succeeds. No verb releases a shell.
- [ ] A forced take against another of the person's devices moves that shell's lease with nothing from the holder, broadcasts `pty.control_changed` with a reason naming the force, leaves the running program and every other shell untouched, and leaves the displaced device's next write refused; a forced take while a run's command holds the shell is refused with `pty.control_held_by_other`, and the run's hold ends only when that command ends or is stopped, or the run is paused or interrupted, handing the shell back.
- [ ] When the last of a shell's holding connections ends, that shell's lease is released (`pty.control_changed` with `reason: 'auto_released_disconnect'`), the next device to write to it takes it, and only the shells those connections held are freed; when a pane's output subscription closes, the holds bound to it alone are released (`reason: 'auto_released_pane_closed'`), the shells keep running, and a hold another subscription also took stands.
- [ ] A lease taken through an agent run's write path is released when the command it was taken for ends (`reason: 'auto_released_command_ended'`) or on that run's first transition out of `running` (`reason: 'auto_released_run_idle'`), whichever comes first; a take off a device's hold keeps that hold aside, and the release hands the shell back to it, naming that device as the holder, while one of its bindings is open, and to nobody once all of them have ended; a device's lease is otherwise untouched by run transitions; a take by a different run re-binds the record and broadcasts `pty.control_changed` with `reason: 'taken'` and the new `holderRunId`; a same-run take for another command broadcasts `reason: 'taken'` naming that command; a same-run retake for the same command or a device's self-take never rewrites it.
- [ ] `pty.open` on a chat session is refused with `pty.chat_unsupported` and starts no shell.
- [ ] A request naming another session's shell, or a terminal id no shell has, is refused with `pty.not_found` and leaves every shell as it was, and a flow-control call naming one changes nothing.
- [ ] Every change of a shell's holder raises its lease version by one, on `pty.control_changed` and on the shell's `pty.list` entry and scrollback frame.
- [ ] A resize from a connection the shell's hold is not bound to is refused with `pty.control_held_by_other` while another device or a run holds it and with `pty.control_not_held` while nobody does, and a close is refused while a run holds the shell and, while another device holds it, succeeds only with `force: true`.
- [ ] With two watchers of one shell, one behind and one live, the shell keeps running and the behind watcher catches up from the scrollback window; the shell's read pauses only when both are behind.
