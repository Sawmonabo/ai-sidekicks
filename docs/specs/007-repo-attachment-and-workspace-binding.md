## Purpose

Define how repositories are attached to the machine as projects, and how a session's workspace is bound to one of its places.

## Scope

This spec covers attaching a git repository as a project, cloning one from a URL, canonical root resolution, the project record and its actions, and binding a session's workspace. A folder that is not a git repository is not attached.

## Non-Goals

- Worktree lifecycle details
- PR creation policy
- Artifact rendering

## Required Behavior

- Attaching a repository must be an explicit action that creates the project's durable `RepoMount` on the machine. A mount belongs to the machine, not to one session: attach takes no session, the daemon stamps its own node on the mount and never takes one from the caller, and attach creates no default workspace. A new session in the project binds to the mount in the same step that creates the session, and converting a chat binds it through the workspace bind (§Interfaces And Contracts). Attaching a project grants both providers' project trust for that checkout — Codex's `projects.<path>.trust_level` override, written in the inline-table form, and Claude Code's own folder trust — and the attach confirm says so in one line.
- Attaching a project grants both providers' project trust for that checkout, since Codex reads project-level roles only from a trusted project, Claude Code runs project-level hooks only in a trusted folder, and an untrusted Codex project still loads its skills; the attach confirmation carries one line saying so. The Codex trust entry is written in its inline-table form, because the dotted form is accepted and does nothing.
- Repo attach must resolve and persist the canonical repository root — the MAIN checkout's working-tree root, identified by the repository's git common directory rather than by the top level of whatever working tree the supplied path sits in — not only the user-entered path (§Repo Identity And Common-Directory Keying (V1 Definition)).
- A repository is attached once per machine, and every session of that project binds to its one mount; the machine lists each folder once, with what is using it. Attaching a folder that is already a project switches the screen to that project, and the daemon refuses a second project record for the same origin.
- Workspace binding must be explicit and must resolve to one concrete execution root before a run begins.
- A project session's workspace is bound to one of two places: a worktree of its own or the project's checkout ([Spec-008 §Required Behavior](./008-worktree-lifecycle-and-execution-modes.md#required-behavior)). There is no read-only place and no disposable copy: how much a session may change is its permission level. Every project mount offers both places; a chat's managed workspace offers only its own root.
- The system must reject path traversal or workspace binding outside the declared local trust envelope.
- A folder that is not a git repository is refused at attach, in one line where the attach was asked for: `Could not attach: not a git repository`. A project is a repository, and a chat's own folder is one from its first byte.
- A session with no repository attached stands in its own daemon-managed workspace — the git-initialized folder the daemon owns, one per session, at the path [Spec-001 §Required Behavior](./001-session-core.md#required-behavior) spells under the daemon's own state directory, made by the daemon's managed-workspace service (`ManagedWorkspaceService.create`) in the same step that creates the chat, `session.create`, or forks one, `session.fork`, and registered as a mount whose managed origin names that one chat ([ADR-032](../decisions/032-two-session-shapes.md)) — and the session's own composer strip names that workspace, `Session workspace`, beside the attach action. The strip reads the label from the session's own shape (`chat` or `project`), a real field on the session record, never a guess from a path. The managed workspace is deleted whole when its session is purged, kept while the session is archived, and skipped by the archive sweep; it carries no `Remove` of its own. Attaching a repository is the strip's action and nothing implicit, and it makes the session a repository-bound session in place, with its identity and its history kept.
- Converting a session that started without a repository into a repository-bound one is one flow with three doors and one end. The doors are the attach action on the composer strip, a convert entry on the session's own row menu and on the session header's overflow menu — carried only on a session with no repository — and dragging that session's row onto a project's group in the session list. The flow opens in place above the composer's working line, carrying one line saying what will happen, a path field pre-filled from the door that opened it (empty from the strip and from the menus, the project's own path when the row was dropped on its group), and a cancel beside the confirm. Confirming copies the workspace's files into that repository and attaches it: the session's row moves into that project's group, its history stands, and the copied files are the first changes the review surface has to read.
- An attached repository is a PROJECT on every console surface, and a project carries a durable record beside its repo mount: a display name, the setup steps its worktrees run after preparation ([Spec-008 §Required Behavior](./008-worktree-lifecycle-and-execution-modes.md#required-behavior)), its own environment rows, its own branch-name pattern when one is set, and whether it is archived. The project's folder slug is fixed at attach. Renaming a project edits the display name alone: the folder on disk does not move, and neither does the project segment of any worktree path — the path a worktree was made at is derived from the slug fixed at attach, not from the display name, so every existing worktree stays exactly where it is and no session's working folder changes ([Spec-008 §Required Behavior](./008-worktree-lifecycle-and-execution-modes.md#required-behavior)).
- A project's own branch-name pattern overrides the machine's `Branch names` pattern for worktrees made in it afterward; it is empty unless set, is checked exactly as the machine's pattern is ([Spec-008 §Default Behavior](./008-worktree-lifecycle-and-execution-modes.md#default-behavior)), and is forgotten with the project's setup steps on delete.
- Archiving a project takes it out of the session list's grouping and moves its row to an archived group at the foot of the projects settings page carrying one action, unarchive. Its sessions are kept and come back with it. Archiving is reversible, which a detach is not — `detached` is terminal for a mount row (§Detach Semantics (V1 Definition)) — so an archived project is still attached and unarchiving restores its place in the list without re-attaching anything.
- A project's folder is in use only while live work uses it, and it has one removal act, the detach: the projects settings page's `Delete` and the runtime settings page's `Remove` on the project's folder are the same act under one rule. While an agent runs anywhere in the project the control is grayed with the title `Busy: <session> is running in it.`, the same words as a busy worktree's trash (§Detach Semantics (V1 Definition); [Spec-008 §Required Behavior](./008-worktree-lifecycle-and-execution-modes.md#required-behavior)), and nothing about the refusal stops that run. With nothing running it confirms in place in three plain lines, `Delete <project name>? Its sessions stay. The folder on disk stays. This cannot be undone.`, under `Cancel` and `Delete`. Confirming forgets the project record — display name, setup steps, environment rows and branch-name pattern — archives the project's sessions, which stay reachable, and detaches the repo mount under §Detach Semantics (V1 Definition); nothing on disk is touched.
- A worktree the app made is listed beneath its project's folder on the runtime settings page, marked `worktree`, and is removed only through the worktree removal ([Spec-008 §Interfaces And Contracts](./008-worktree-lifecycle-and-execution-modes.md#interfaces-and-contracts)), never the detach. A chat's session workspace carries no `Remove`: it goes only when its session is purged.
- The four project actions — rename, open the folder in the editor the general settings name, archive and delete — live on the project's own row on the projects settings page and nowhere else. The session list's project heading carries none of them: no menu, no overflow control, no hover control. Rename opens one field on the row, confirmed by a control that names the act rather than by a save, applied on Enter and abandoned on Escape; opening the folder names the editor and the folder before it acts and says in place that the folder was handed over.
- Every process the app starts carries the environment rows recorded for every project, and every process a project's sessions start additionally carries that project's own rows; a project row wins over an every-project row of the same name and says so where it is drawn. A row is one name and one value, added from a name field and a value field, edited where it sits, and removed one at a time; a list with no rows says what rows there would be for. No row in either list is a credential: a credential-shaped name is refused where it was typed (§Fallback Behavior), and no row carries a masked value or a sensitive mark. A name the app sets itself on the processes it starts, `DISABLE_AUTOUPDATER` among them, is refused at save with `The app sets this.` The name pattern, the credential shapes and the names the app sets are one shared rule, and the background service builds each process's environment from the same list. These rows reach a provider child as run-provisioned values inside the constructed-environment discipline, so a name reserved to the daemon — the credential-home variables — is discarded at construction rather than merged ([Spec-026 §Credential homes and the constructed environment](./026-provider-accounts-and-credential-homes.md#credential-homes-and-the-constructed-environment)).
- The projects settings page is the one list of attached projects: one row per project carrying its display name, its folder and how many sessions it holds, each row opening in place rather than navigating, the archived group at the foot, and, with nothing attached, one line saying no projects are attached and that one is attached from the sessions list.
- A repository can be cloned from a URL from the new-session picker's `Clone repository…`, which turns the picker's foot into one field, `Repository URL`, with one line under it naming where the clone goes (`Clones into ~/code/beacon`) and `Change…` beside it for this clone alone. The folder is the one the projects settings page's `Clone new repositories into` names, and while the person has not set it, the folder holding the most recently attached project, or the home folder when there is none; the picker and the settings page read that one answer. Only https and ssh URLs are cloned (git's short `host:owner/name` form counts as ssh); a URL that is neither reads `Only https and ssh URLs can be cloned.` and a destination that exists and is not empty reads `<folder> is already there and is not empty.`, both before anything is fetched: `repo.clone` is refused `repo.clone_refused`, with the reason `unsupported_address` or `destination_not_empty` ([Error Contracts §Repo](../architecture/contracts/error-contracts.md#repo)). A URL whose origin is already an attached project clones nothing and starts the session on that project.
- Pressing `Clone` starts the session at once as a project session on a project named for the repository, and the clone runs in place inside the composer card, where the worktree setup card runs: one head line, `Cloning <owner>/<name>`, git's own progress words under it and `Cancel`. Git clones the submodules too, under the same https-and-ssh rule. When git asks for a user name, a password or token, a key's passphrase, or whether to trust a host's key, the card grows one input line holding git's own question, masked for a password or a passphrase; the answer goes to git and nowhere else, and the app keeps no credential — the person's own git credential helper stores it, or not, as their git config says. A clone that fails keeps the card with git's own last error line, the URL in its field so a typo is fixed where it was typed, and `Clone`, which runs it again. `Cancel` stops git, removes the folder the clone made before the card offers `Clone` again, and reads `Clone canceled`; the session stays until the person closes it. When git finishes, the card reads `Cloned`, the project attaches exactly as `Open folder…` attaches a folder, and the session starts where the machine's default for a new project session says ([Spec-008 §Default Behavior](./008-worktree-lifecycle-and-execution-modes.md#default-behavior)).
- With Git LFS on the machine, the clone passes Git LFS's `filter.lfs.*` settings on the clone's own command line, so the large files arrive in the one checkout, and then runs `git lfs install --local` in the new repository, so later checkouts and every worktree the app makes fetch them too; the person's global git config is never written. Without Git LFS, when the cloned `.gitattributes` names `filter=lfs`, the card stays with `This repository keeps large files in Git LFS, which isn't installed on this Mac, so they arrived as placeholders. Install Git LFS, then press Get large files.` and a `Get large files` button, which runs `git lfs install --local` then `git lfs pull` in the new checkout once Git LFS is installed.
- The clone is one daemon command run as an argument list with the worktree service's git environment, only the https and ssh protocols allowed (the allow list reaches submodule fetches), and git's questions routed through the daemon's own askpass program. At most four progress updates a second reach the card, the latest winning and nothing queued, and the daemon holds one progress line per clone in memory while it runs; nothing polls and no temporary copy is made. A clone lost to a restart is found by its cloning mark, its partial folder removed and its failure reported; no clone event is kept.
- On the machine itself, `Open folder…` opens the platform's own folder chooser. On another device it lists the machine's folders in place: the folder in view and its folders by name, a folder that is a repository marked `repository`, a filter field, hidden folders left out unless shown, starting at the home folder of the account the service runs as; `Open this folder` on a folder that is not a repository reads `Could not attach: not a git repository`. The device acts only on folders the service listed, each named by a token the service keeps in memory for ten minutes, so no path string comes from another device.
- On a Windows computer with WSL, a project whose folder is on the other side's disk is accepted and its row carries one line, `This folder is on another disk, so sidekicks read it more slowly.`, naming no side; its git and file views refresh when the window takes focus and before each diff read, never on a timer. A folder picked in another distribution is refused in place with `The background service cannot reach this folder. Pick one under your home folder or on a drive.`

## Default Behavior

- Attaching a git repository creates the project's one repo mount and no workspace. A session's workspace is made when the session is created in the project, or when a chat is converted into it, in the place the session starts in: a worktree of its own, or the project's checkout rooted at the enclosing working tree of the attached path — the main checkout only when attach originates there (§Repo Identity And Common-Directory Keying (V1 Definition) surfaces both values for exactly this split).
- Repo metadata defaults to background refresh through daemon-owned git services.

## Fallback Behavior

- If a path is not a git repository, attach refuses it with `Could not attach: not a git repository`, said in place in the picker that asked; the project's header leaves the list again and nothing else is redrawn.
- If a folder picked on a Windows computer with WSL lies in another distribution, attach refuses it as unreachable, reading `The background service cannot reach this folder. Pick one under your home folder or on a drive.`
- If the daemon cannot make the place a session asked for, it says so where the session is and never substitutes the other place.
- If canonical root resolution fails, repo attach must fail explicitly rather than guessing; a supplied path that does not exist, and a path whose git metadata is present but unusable, are both resolution failures and must never be attributed to an ancestor repository (§Repo Identity And Common-Directory Keying (V1 Definition)).
- If a workspace path becomes unavailable after binding, the workspace transitions to `stale` and new write runs must be blocked until repair.
- If an environment row's name is credential-shaped — `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, or any name ending in `_TOKEN`, `_SECRET`, `_KEY` or `_PASSWORD` — the row is refused in place, in the list the name was typed into, reading `Credentials are not set here. Sign in to a provider on Providers, or add a workflow step's token in its Credential field.` ([Spec-026 §Non-interactive token registration](./026-provider-accounts-and-credential-homes.md#non-interactive-token-registration)); nothing is written and the rows stay exactly as they were. A name the app sets itself on the processes it starts is refused the same way with `The app sets this.` A name that is not an environment variable name — letters, digits and underscores, never starting with a digit — is refused the same way, in the same place.

## Interfaces And Contracts

- `RepoAttach` (`repo.attach`) takes a local path on the machine, or from another device a `folderToken` the folder list minted, in place of a path; it takes no session and no node, because the daemon stamps its own node on the mount. It makes the project's one mount and no workspace, keys the repository by its git common directory, refuses a folder that is not a git repository, refuses a folder in another WSL distribution as `repo.folder_unreachable`, and mints no second project record for an origin already attached. A finished attach records `repo.attached`, which is not a session event; another device sees the new project through the live project list.
- `RepoMountRead` (`repo.mountRead`) exposes one mount's canonical root, git metadata, current health, origin — `attached` for a project's folder, `managed` for a chat's workspace, `worktree` for a worktree the app made under its project — and what uses it.
- `repo.mountList` lists every folder the service can reach, each with what is using it and whether it is on the other side's disk of a WSL computer; each worktree the app made sits beneath its project's folder, origin `worktree`. A project folder's `Remove` is the detach, an app-made worktree's `Remove` is the worktree removal, and a chat's managed workspace carries no `Remove`. Repository identity stays the git common directory, and worktree folders and the daemon's private snapshot refs are namespaces of their own.
- `WorkspaceBind` (`repo.workspaceBind`) binds a converted chat's session to its project and to where it works — a worktree of its own or the project's checkout, `executionMode: "bound-root" | "provisioned-worktree"` — and admits the bound path to that session's trust envelope. A new session binds in the same step as `session.create`, whose `binding` names the project and the place. A session's workspace always references a repo mount; a workspace names a folder that attach already admitted.
- The project record's actions: `repo.projectList` (live: name, folder, session count, and whether an agent runs anywhere in the project, so `Delete` grays at once; each row also says whether its folder is on the other side's disk), `repo.projectRename`, `repo.projectArchive` and its undo `repo.projectReactivate`, `repo.projectSetupUpdate` (the setup steps as one draft: files to copy, commands to run in order, and the limit after which a step gives up, which the worktree setup reads, [Spec-008 §Required Behavior](./008-worktree-lifecycle-and-execution-modes.md#required-behavior)), `repo.projectEnvironmentUpdate` (the project's own environment rows, each checked by the shared environment-name rule), `repo.projectBranchPatternUpdate {projectId, pattern | null}` (`null` returns the project to the machine's pattern; a refusal writes nothing), and `repo.detach` for `Delete` and for the runtime page's `Remove`. `Open in editor` is the desktop's `native.openInEditor`. The every-project environment rows, the machine's branch-name pattern and `Clone new repositories into` are keys in the machine's settings file, written by the service.
- Cloning: `repo.cloneFolderRead {}` → `{folder, source: setting | lastProject | home}`, the one read the picker's `Clones into` line and the projects settings page share; `repo.clone {url, parentFolder?, projectId?}` → `{projectId}`, which creates the project record at once marked as cloning and ends in the daemon's ordinary attach, a `projectId` rerunning a failed or canceled clone of that project; `repo.cloneSubscribe {projectId}`, the card's phase, percent, a question waiting, the failure line and done; `repo.cloneAnswer {projectId, questionId, answer}`; `repo.cloneCancel {projectId}`; and `repo.largeFilesPull {projectId}`, whose progress and failure ride the clone's stream.
- `repo.folderList {folderToken?, filter?, showHidden?}` serves another device's `Open folder…`: the folder in view and up to 500 entries, each with a token the service mints for a folder it listed and keeps in memory for ten minutes, plus `more: true` when the filter would narrow more.
- Every project mount offers both places and a chat's workspace only its own root, so there is no execution-mode capabilities read.
- A workspace's state while its root is made ready, for either place, is `preparing`, recorded as `workspace.preparing`; the session state named `provisioning` is a different fact and keeps its name.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- Repo mount records must persist canonical root, the owning node the daemon stamps (its own, never the caller's), lifecycle state, origin, and the attach-time repository identity anchor (§Repo Identity And Common-Directory Keying (V1 Definition)'s persisted common directory). A mount is unique per machine by canonical root; it is never keyed by session.
- Workspace records must persist execution root, repo association, health, and the admitted bind origin (the bound-root carrier re-preparation never clears — the root a `bound-root` run works at).
- A project record persists its display name, the folder slug fixed at attach, setup steps, environment rows, its branch-name pattern when set, and whether it is archived; a project being cloned carries a cloning mark until the clone finishes or fails.
- The session record carries the session's shape, `chat` or `project`, as its own field.
- Repo health and git metadata belong to daemon-owned projection state rather than client cache.

## Example Flows

- `Example: A person attaches a repository from the new-session picker. The daemon resolves the canonical repo root and stores the project's one repo mount; the new session binds to it in the step that creates it, in a worktree of its own.`
- `Example: A session working in the project's checkout moves into a new worktree. The workspace stays the same session-bound concept, and the daemon prepares its execution root again in place before the next run starts.`
- `Example: A person picks a folder that is not a git repository. The picker says Could not attach: not a git repository in one line, and nothing is attached.`
- `Example: A person clones https://github.com/acme/beacon from the picker. The session starts at once, the clone runs in the composer card, git's password question appears as a masked line there, and when git finishes the project attaches and the session starts in a worktree of its own.`

## Execution Mode Transitions

When a session moves to another place — from the project's checkout into a worktree, from one worktree to another, or back to the checkout — its workspace is prepared again in place. The workspace ID remains the same; only the execution root changes.

State progression: `ready -> preparing -> ready`.

- The old execution root is released and the new one is made ready.
- This is NOT a new workspace. The `workspaces` row keeps its `id`; `execution_mode` and `fs_root` are updated, and `state` cycles through `preparing` before returning to `ready`.
- If the move fails (for example, the daemon cannot make the worktree), the workspace transitions to `stale` with an error detail recorded in the workspace's metadata. New write runs must be blocked until the workspace is repaired or the move is retried.

## Implementation Notes

- Repo attach should not assume that the user-selected path is already the repo root, nor that the working tree enclosing it is the repository's identity: a linked worktree's own top level is not its repository's main checkout root.
- Workspace binding must remain explicit even when a session has only one repo mount.
- A repo mount belongs to the machine whose daemon reaches its folder; the daemon stamps its own runtime node as the mount's owner, never one a caller names.

## Pitfalls To Avoid

- Treating a user-entered path as canonical without resolution, or treating the enclosing working tree's top level as the repository's identity
- Putting a session in a place the person did not choose, or falling back to the project's checkout when a worktree could not be made
- Allowing client-only workspace binding with no daemon validation

## Acceptance Criteria

- [ ] Attaching a repository yields a durable repo mount with canonical root metadata.
- [ ] One repository attached on a machine yields one repo mount, and any number of that project's sessions bind to it, each with its own workspace.
- [ ] Attaching a folder that is not a git repository is refused with `Could not attach: not a git repository` and attaches nothing.
- [ ] A clone from an https or ssh URL starts its session at once, shows git's progress and questions in the composer card, removes its partial folder on `Cancel`, and attaches the finished repository as `Open folder…` does.
- [ ] Attaching from a linked worktree and attaching from the same repository's main checkout resolve to one identical canonical root for every layout where git records the main working tree (the ordinary and submodule layouts — the `--separate-git-dir` layout's linked worktrees are the deliberate refusal arm of §Repo Identity And Common-Directory Keying (V1 Definition), with attach-from-the-main-checkout as the recovery and the worktree bindable through the registration arm), so N working trees of one repository yield ONE repo mount while each bound workspace keeps its own per-worktree execution root.
- [ ] A supplied path that does not exist, a path whose git metadata — at the path itself or at any directory strictly between it and the resolved working-tree top level — is present but unusable, a working tree whose registration is missing or does not name it back, a derived main-checkout root that fails its bidirectional verification with no lawful own-toplevel fallback (the linked worktree of a `--separate-git-dir` repository lands here), and a git pointer file that is not a regular file each fail repo attach explicitly rather than being attributed to an ancestor repository.
- [ ] A git-backed mount whose root's `.git` entry is moved or retargeted after attach refuses subsequent binds and run handoffs through the persisted-identity match and projects `identity_mismatch` — never `healthy` — on every subsequent health-reporting read until re-attach, while a mount whose canonical root cannot be probed at all projects `unreachable`, which takes precedence (§Repo Mount Health (V1 Definition)).

## Local Trust Envelope (V1 Definition)

For workspace binding, the declared local trust envelope of a session is the set of ADMITTED ROOTS of the repo mount the session is bound to: the mount's fully resolved canonical root, the working trees the mount's repository itself registers, and daemon-created execution roots admitted by provenance — the same union the defining rule below states in full. Envelope admission for user-supplied roots originates in the explicit `RepoAttach` action and reaches a session through its bind; no path enters the envelope implicitly.

- A workspace execution root is inside the envelope iff its fully resolved form (absolute, symlink-resolved, platform-normalized) is path-contained within an ADMITTED ROOT of the repo mount the session is bound to — the mount's fully resolved canonical root, a working tree the repository itself registers (admitted under the registration arm below), or a daemon-created execution root (admitted by provenance, below); the defining rule and the arms below are ONE contract, stated here so no admission exists that the definition does not name. Containment is path-component-boundary-aware (`/repo-evil` is not within `/repo`), case-folded on case-insensitive filesystems (Windows tier per [ADR-019](../decisions/019-windows-v1-tier-and-pty-sidecar.md)), and working-tree-boundary-aware: a candidate whose own enclosing working tree is NOT the admitted root it is tested against (a linked worktree NESTED beneath the canonical root is the concrete shape) is never admitted by lexical containment in that root; it is admitted only as, or within, a registered working tree through the registration arm — so de-registering a nested worktree removes it from the envelope exactly as it does a sibling one, and lexical containment can never resurrect it.
- `WorkspaceBind`'s optional `directory` carries two forms over the one existing string field — no schema change. A RELATIVE value is resolved against the mount's canonical root, exactly as shipped. An ABSOLUTE value is the wire form that names a registered working tree (or any other admitted root) — the only expressible form where no relative spelling exists at all, as for a worktree on another drive under the Windows tier ([ADR-019](../decisions/019-windows-v1-tier-and-pty-sidecar.md)). Both forms are admitted solely by post-symlink-resolution containment within an admitted root of the same mount — the canonical root, or a registered working tree admitted under the bullet below; `..` traversal, redirection, or symlink escape that resolves outside every admitted root is rejected with the typed `repo.outside_trust_envelope` error.
- The run-time boundary the approval policy governs — the session's own working folder under its permission level ([Spec-010 §Default Behavior](./010-approvals-permissions-and-trust-boundaries.md#default-behavior)) — is a separate authorization layer; it is not this spec's bind-time validation and is out of scope here.
- Daemon-created execution roots (Plan-008 worktrees under the daemon's execution-roots directory, keyed by the owning repo mount) are inside the envelope by construction: they are daemon-created derivatives of an admitted mount, never user-supplied paths, so the containment rule above governs user-supplied bind paths while daemon-created roots are admitted by provenance ([Spec-008 §State And Data Implications](./008-worktree-lifecycle-and-execution-modes.md#state-and-data-implications)).
- A mount's envelope is its canonical root PLUS the working-tree paths the repository itself registers. Because the canonical root is the main checkout's root (§Repo Identity And Common-Directory Keying (V1 Definition)), a linked worktree of that repository is generally NOT path-contained within it, so containment alone would reject binds to working trees the repository demonstrably owns. Each registered path is admitted only when it passes the same bidirectional-link and physical-containment screens resolution applies; registration is read from the repository at bind time and never cached, so a working tree git no longer registers is no longer in the envelope. Containment within an admitted registered working tree is then checked exactly as it is within the canonical root (the containment rule above), and a user-supplied path that is neither contained in the canonical root nor in an admitted registered working tree is rejected with `repo.outside_trust_envelope` as before. On the wire, a registered working tree is named by the ABSOLUTE form of `WorkspaceBind.directory` (the containment bullet above); no selector field is added. Leaving the envelope is additionally enforced at the next RUN boundary, not only at bind: run handoff re-verifies a user-supplied execution root's membership — canonical-root containment or currently-registered working tree — before work starts, and a root that no longer verifies blocks the run and transitions the workspace to `stale` with the typed error recorded (§Fallback Behavior's blocked-until-repair shape), so a worktree unregistered after bind cannot persist as a silently trusted root. This registration arm governs USER-SUPPLIED bind paths only; it does not narrow the provenance rule above. A daemon-created execution root stays admitted by provenance regardless of its registration state, because the daemon knows it created that root — so a daemon-created worktree whose registration git has pruned (the window between an external `git worktree prune` and the Plan-008 retirement sweep) remains in the envelope, is exempt from the run-boundary re-verification, and is retired by that sweep rather than being silently ejected from the envelope mid-run.

## Repo Mount Health (V1 Definition)

Repo mount health is the daemon-probed integrity of the mount's canonical root, exposed as a daemon-owned projection (`RepoMountHealth { status: "healthy" | "unreachable" | "identity_mismatch"; checkedAt: string }` — see [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) §Plan-007). `status` is `unreachable` when the canonical root is absent or unreadable at probe time — the verdict that takes precedence, because no further question can be asked of a root that cannot be probed; `identity_mismatch` when the root is reachable but the common directory re-derived from it no longer equals the attach-persisted identity anchor (`repo_mounts.metadata.commonDir` — §Repo Identity And Common-Directory Keying (V1 Definition)) — or cannot be re-derived at all, a removed or malformed `.git` entry under a reachable root being the same moved identity, an explicit verdict rather than an error escaping a health read — the health face of a post-attach `.git` move, removal, or retarget, standing on every subsequent health-reporting read until re-attach (the named recovery) — required because the mount's binds and runs are already refusing through the persisted-identity match, and a projection still answering `healthy` for a mount that can never bind again is a lying read model; and `healthy` when the root is reachable and the re-derived identity matches the anchor; `checkedAt` is the ISO-8601 instant of the probe that produced the verdict. Health is derived at read time (every health-reporting read surface probes synchronously — the on-read floor; the identity comparison is part of the probe wherever an anchor is persisted) and refreshed by the daemon-owned background metadata refresh (§Default Behavior); it is never persisted as a row column and is distinct from the lifecycle `state` axis (§State And Data Implications). A mount whose identity anchor is not yet persisted never projects `identity_mismatch`; the member requires an anchor to mismatch.

## Detach Semantics (V1 Definition)

`RepoDetach` must accept a repo mount id and transition the mount to `detached` without deleting the durable record (request/response shapes in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) §Plan-007).

- Detach is refused with `repo.detach_conflict` while an agent runs anywhere in the project, naming the running session; the screen draws it as `Busy: <session> is running in it.` Active work must finish or be canceled first, and the refusal never stops it. There is no force-detach in V1.
- Otherwise, detach transitions the mount to `detached` and archives all dependent workspaces (`workspaces.state -> 'archived'`), recording `repo.detached` — a project change, which is not a session event — plus one `workspace.archived` per dependent workspace (Spec-005 `session_lifecycle` taxonomy). Archived workspaces remain historically linked to completed runs. The same transaction revokes every remembered approval rule of the project, with `project_detached` ([Spec-010 §Fallback Behavior](./010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)). Dependent non-terminal worktree rows follow via the Plan-008 asynchronous retirement sweep ([Spec-008 §Fallback Behavior](./008-worktree-lifecycle-and-execution-modes.md#fallback-behavior) — retirement recorded and evented, metadata preserved).
- `detached` is terminal for the row: there is no `detached -> attached` transition. Re-attaching the same canonical root creates a NEW repo mount row (the active-mount uniqueness index constrains only `state = 'attached'` rows). Because the canonical root is the repository's main-checkout root (§Repo Identity And Common-Directory Keying (V1 Definition)), re-attaching from ANY working tree of a detached repository is a re-attach of that same canonical root and yields one new row for the repository, never one row per working tree.
- The console's detach doors are the project row's `Delete` on the projects settings page and `Remove` on the project's folder on the runtime settings page, one act under one rule (§Required Behavior): it confirms in place, forgets the project record, archives the project's sessions, and detaches the mount with the cascade above, carrying the same refusal while an agent runs anywhere in the project — there being no force-detach in V1. A worktree the app made is removed with the worktree removal, never the detach, and a chat's managed workspace goes only with its session's purge. There is no per-session detach control, and neither rename nor archive detaches: an archived project is still attached and comes back on unarchive, because archiving is reversible and this row's `detached` is not.

## Repo Identity And Common-Directory Keying (V1 Definition)

A repository's identity is its git COMMON directory, not the top level of whatever working tree the supplied path happens to sit in. Git gives one repository many working trees — one main checkout plus N linked worktrees — and they share exactly one common directory (normally the main checkout's own `.git` directory; a repository initialized with `--separate-git-dir` keeps it elsewhere, behind a `.git` pointer file — [git-init(1)](https://git-scm.com/docs/git-init)), which is why it is the only stable identity for that repository. The canonical root persisted on a repo mount is therefore the working-tree root of the MAIN checkout: the directory whose own `.git` entry resolves to that common directory. Attaching from a linked worktree resolves to that same main-checkout root, so N working trees of one repository resolve as ONE repo mount, and every daemon cache, filesystem watch, remote fetch, and throttle window keyed on repo identity is shared across them instead of duplicated per working tree.

- Identity keying does not move where work happens. A workspace's execution root (`workspaces.fs_root`) remains the per-working-tree path the user bound or the daemon created; only the repo-mount identity key (`repo_mounts.canonical_root`) collapses onto the main-checkout root. Resolution must therefore surface BOTH values — the repository identity and the enclosing working tree's own root — because attach persists the first and the default workspace of §Default Behavior roots at the second.
- The main-checkout root is DERIVED from git's own records, then VERIFIED — never assumed — and the derivation runs BEFORE any own-toplevel fallback, because the fallback is spoofable where the derivation is not: a planted `.git` pointer file naming a repository's common directory directly makes git report gitDir == commonDir with the planted holder as the top level, so an accept-own-toplevel-first rule would persist the planted directory as that repository's root. Candidate derivation, in order: when the common directory IS its parent's own `.git` entry — decided by SAME-FILE IDENTITY against the filesystem (the parent's `.git` child resolves to the same directory entry as the common directory), never by comparing name strings, because a `.GIT` spelling names the same entry wherever the filesystem folds case (default macOS, and the Windows tier per [ADR-019](../decisions/019-windows-v1-tier-and-pty-sidecar.md)) and no single string rule is right on both a case-folding and a case-sensitive volume, while the identity test is true exactly where the filesystem folds, with no per-platform table — the candidate is its parent (the ordinary layout); otherwise, when the common directory's own `config` records `core.worktree` (read file-scoped from `<commonDir>/config`, never via discovery), the candidate is that value resolved against the common directory — the submodule layout, whose module directory `<superproject>/.git/modules/<name>` has a non-`.git` basename yet genuinely records its working tree ([git-config(1)](https://git-scm.com/docs/git-config), [gitsubmodules(7)](https://git-scm.com/docs/gitsubmodules)). A candidate is accepted only when its own `.git` entry resolves back to that same common directory — a directory canonically equal to it, or a pointer file naming it. Only when NO candidate is derivable, or the derived candidate fails its back-check, does resolution consult the supplied tree: the supplied path's own git directory canonically equal to the common directory means the enclosing working tree is the repository's main working tree and the canonical root is that tree's own top level — the first-attach-defines-root arm a `--separate-git-dir` MAIN checkout takes, because git records no main-working-tree pointer for that layout (no `core.worktree` is written, and its own `git worktree list` reports the git directory itself as the main working tree — [git-worktree(1)](https://git-scm.com/docs/git-worktree)); anything else is refused with the typed root-resolution error, naming attach-from-the-main-checkout as the recovery — the linked worktree of a `--separate-git-dir` repository lands on exactly that refusal arm by design: identity for that repository is established by attaching its main checkout, after which the worktree binds through the registration arm of §Local Trust Envelope (V1 Definition) — which is why §Acceptance Criteria's one-identical-canonical-root criterion quantifies over the layouts where git records the main working tree, not over every working tree of every layout. Residual, named rather than hidden: for the `--separate-git-dir` layout git records no working-tree root at all, so a direct-to-common pointer-file holder is indistinguishable from the true main checkout at first attach; the working-tree membership screen (a supplied tree must canonically equal the derived canonical root or be a registered working tree) closes the spoof for every layout git does record, and the persisted-identity match below bounds the residual after attach.
- Because the active-mount uniqueness index is keyed on the canonical root (§State And Data Implications), attaching a second working tree of an already-attached repository is a re-attach of the SAME repository and is refused as already attached rather than admitted as a second mount. Uniqueness is additionally enforced on the identity itself: inside the attach transaction, the resolution's canonicalized common directory is compared against every active mount on this machine — each mount's persisted identity anchor, an absent anchor re-derived from that mount's canonical root and repaired in the same transaction (the anchor-repair rule below) — and equality refuses as already attached — the canonical-root index cannot see two mounts with DIFFERENT canonical roots and ONE common directory, exactly the pair the first-attach residual above would otherwise mint (a direct-to-common pointer-file holder attached beside the true main checkout), so the identity comparison bounds that residual to one active mount per repository. The check is service-level by design: the anchor lives in the metadata JSON column, where a unique index would demand a generated column for a value the daemon's single-writer attach transaction already compares race-free, and the canonical-root index stays as the structural backstop for the ordinary same-root shape. Binding that working tree is a workspace operation on the existing mount, not a second attach.
- The repository identity that resolution derives is PERSISTED at attach — `repo_mounts.metadata.commonDir`, the canonicalized common directory inside the existing metadata JSON column, no schema change — and every later re-derivation must MATCH it: workspace bind and the run-boundary re-verification re-derive the common directory from the mount's canonical root, and a value that no longer equals the attach-persisted one refuses with the typed root-resolution error and projects `identity_mismatch` per §Repo Mount Health (V1 Definition) on every subsequent health-reporting read rather than silently following the moved or retargeted `.git` entry, with re-attach as the named recovery. Without the persisted anchor, a post-attach retarget of the root's `.git` pointer file would walk every subsequent bind and run onto a different repository while the mount row still claims the old identity. An ABSENT anchor on a git-backed mount — a row attached before this contract — is REPAIRED at first contact rather than tolerated indefinitely: the first successful common-directory re-derivation after upgrade at a MUTATING seam — bind, the run-boundary re-verification, or the attach transaction's dedup comparison — persists the derived value as the mount's anchor; a health-reporting read NEVER writes it, because the wire read surfaces register `mutating: false` and an advertised pure read must stay one, so an unanchored row's health read simply has no identity question to ask until the first mutating contact repairs the anchor (a bounded, named window). First observation defines identity, so a retarget that PREdates the repair is undetectable by construction — nothing was recorded to contradict it — and stands as the named residual of the upgrade window; a re-derivation that fails while the anchor is still absent leaves the row unanchored and refuses the operation that needed it rather than guessing.
- Resolution must refuse a supplied path that does not exist instead of walking up from it. Walking up lexically from a deleted or never-created path attributes it to whatever repository happens to contain its parent — a dotfiles repository checked out at the user's home directory is enough to make that attribution wrong for essentially every path beneath it.
- Resolution must distinguish "no git metadata here" from "git metadata here is unusable", and must NOT lean on git to make that distinction: empirically (git 2.50.1), and confirmed at source in git's own `setup.c` (§References), git's own upward discovery hard-stops only on the unusable POINTER-FILE shape — a dangling or malformed `gitdir:` file fails discovery outright, because `read_gitfile_gently` classifies it as not-a-repository and the ascent loop in `setup_git_directory_gently_1` terminates on every gitfile error except the stat failure that means no `.git` entry exists at that level — while an unusable `.git` DIRECTORY at an ancestor draws no gitfile verdict at all and is silently skipped, the ancestor's own parent repository discovered instead, which is precisely how a damaged repository gets silently attributed to its parent repository. The daemon therefore enforces the stop itself: after git answers, the supplied path's OWN `.git` entry and every directory strictly BETWEEN it and the resolved working-tree top level are screened, and an entry that classifies as present but unreadable, malformed, or naming something that is not a usable git directory fails the attach explicitly — the at-the-path arm matters because git skips an unusable `.git` directory at the supplied path exactly as it skips one at an ancestor, and without it a supplied path sitting directly under its repository's top level (an empty strictly-between set) would sail past the screen wearing the exact damaged-metadata shape the acceptance criterion refuses. The boundary is the same on both resolution arms: when git finds no repository at all, only the supplied path's own entry is screened — a path whose own git metadata is unusable is refused, not classified as inside no repository, so the refusal never conflates with the no-repository fallback — and neither arm ever walks above git's answer. The screen is bounded and post-hoc — finitely many components below a root git already resolved, never a walk above it — so it can refuse a wrong answer but never manufacture a root, which keeps it compatible with the no-upward-walk rule above.
- A linked worktree is accepted as belonging to a repository only when git's link is BIDIRECTIONAL: the working tree's `.git` file names a git directory, AND that git directory's registration under `<common-dir>/worktrees/<name>/gitdir` names this working tree's own `.git` back. The registration must additionally be physically contained by the common directory it claims — the registered git directory's grandparent must canonically equal that common directory. A pointer file alone is attacker-writable and must never establish repository identity by itself.
- Every pointer file resolution reads — the working tree's `.git`, and the `commondir` / `gitdir` files under a git directory — must be opened WITHOUT blocking, validated as a REGULAR file by `fstat` on the OPENED descriptor, and read through that same descriptor under a fixed byte ceiling. A pre-open `stat` screen alone leaves a TOCTOU window: the checked path can be swapped for a FIFO or device node between check and open, and the open then blocks indefinitely and wedges the scan — the exact hazard the screen exists to prevent. Anchoring the regular-file check to the opened descriptor screens the object actually read, and reading through that descriptor bounds the bytes regardless of what pre-open metadata claimed.
- Both sides of every path comparison — bind containment, worktree-registration matching, and common-directory containment — must be canonicalized (symlink-resolved and absolutized) before they are compared. Comparing a canonicalized path against an uncanonicalized one produces false mismatches wherever the platform symlinks standard directories: on macOS `/tmp` is `/private/tmp`, so an uncanonicalized `/tmp/...` registration never equals its canonicalized peer and a legitimate worktree is refused.
- Each refusal above is a canonical-root resolution failure under §Fallback Behavior: attach fails explicitly with the typed root-resolution error rather than guessing a root. A path that is genuinely inside no repository is refused as not a git repository (§Fallback Behavior), carrying the root-resolution error's `not_a_repository` reason — a different reason from every refusal above, and the two must never be conflated, because reporting damaged repository metadata as "not a repository" hides the damage this section exists to surface.
