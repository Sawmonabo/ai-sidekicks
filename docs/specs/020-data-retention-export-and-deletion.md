## Purpose

Define how long the person's data is kept and how the person exports and deletes it, so that every copy of their data on a machine or in the control plane goes when they ask.

## Scope

This spec covers:

- Session data lifecycle beyond `archived` (the `purge_requested` state), and how long a kept session and its provider files last
- The data acts: deleting old sessions, exporting everything a machine keeps, erasing everything a machine keeps, and deleting the hosted account
- How deleting a session leaves nothing readable in the daemon's database, and where the daemon keeps its secrets

## Non-Goals

- Consent collection UX
- Cookie policy or browser-side tracking
- Third-party data processor agreements
- Billing data retention (governed separately)
- Anything that exists to govern an organization of other people: enterprise sign-on (OIDC and SAML), compliance mappings (SOC 2, ISO 27001, HIPAA, FedRAMP), HSM custody, WAF guidance, Helm charts, SLA support and multi-region sign-up discovery. The product serves one person.
- Server-side telemetry and usage analytics. The app collects none, and a crash report stays on the machine that crashed ([Spec-021 §Default Behavior](021-desktop-app-and-renderer.md#default-behavior)).

## Required Behavior

### Session States Beyond Archived

- The session lifecycle must include one additional state beyond `archived`: `purge_requested`.
- `purge_requested`: the person has pressed `Delete old data` and the session is among those it removes. The session row is locked against further modification while the purge deletes the files only this session names. The purge then deletes the row (§Ordering And Atomicity), so no state follows `purge_requested`: no row survives to hold one.
- Allowed transitions: `archived -> purge_requested` and `closed -> purge_requested`. Both `archived` and `closed` sessions may be purged. Purge is irreversible.

### Retention Policy

- A kept session holds its data, personal data included, until the person deletes it. Nothing deletes a session by age and nothing deletes one automatically ([ADR-037](../decisions/037-kept-sessions-keep-their-provider-files.md)).
- `Keep sessions for` on Settings › Runtime is the one bound over finished sessions, 90 days by default. It is the machine's own setting, set in one place on that machine and nowhere else. Past it a finished session is eligible for deletion, and eligible is not deleted: the control's line reads `After this, a finished session can be deleted. Nothing goes until Delete old data is pressed.`
- `Delete old data` is the only act that removes sessions and their logs, and its line on Runtime says so: `Removes sessions and their logs past their retention, while Erase all data removes everything the service holds.` It confirms in place: `Delete 14 archived sessions and their logs? Each chat's session workspace goes too; files in project folders stay. This cannot be undone.`, and, while backups are on, `Backups taken before this delete keep these sessions for up to four weeks.` It is the one purge, `daemon.retentionPurge` (§Interfaces And Contracts), and the service runs it on nothing but that press.
- The purge marks the session `purge_requested`, then deletes the files only this session names: its capture folder with its snapshot refs and its base pins, a chat's managed workspace whole, and the provider's own files for the session. Then it deletes the session's rows, its artifact manifests among them, in one transaction with SQLite's `secure_delete` on, so the freed pages hold nothing readable, and once the transaction commits it checkpoints the write-ahead log with `TRUNCATE`, so the log keeps no copy either ([§Erasure In The Daemon's Database](#erasure-in-the-daemons-database)). After that commit it unlinks each stored artifact payload that no surviving manifest names, and the orphan sweep reclaims one a crash leaves behind ([Spec-012 §Local Artifact Deletion And CAS Reclaim (V1)](012-artifacts-files-and-attachments.md#local-artifact-deletion-and-cas-reclaim-v1)).
- The provider's conversation file lasts as long as the session, because resuming a session reads the provider's own transcript. Every Claude Code process the daemon starts carries `"cleanupPeriodDays": 36500` in its `--settings` JSON, which outranks a repository's own settings files, and each account home's `settings.json` holds the same value for a process started there without the flag, so Claude Code's age sweep, which judges by file age across the whole home, never reaches a file. A managed policy that holds the value lower is read back from `get_settings` after each spawn and raised as the `session.notice` kind `settings_ignored`. Codex keeps a conversation until it is deleted.
- `Delete old data` removes, from every account home a session ran in, every file the provider keeps for that session: on Claude Code the conversation file with its subagent and tool-result files, its file history, session environment, todo and task lists, plan file and debug log; on Codex, `thread/delete`. A session typed in a terminal keeps its conversation in the person's own Codex folder, which the purge never touches.
- Only the diagnostic logs drop on their own, past `Keep diagnostic logs for`, 7 days by default; the bound takes any period and is not a switch that turns deletion on or off. It covers the service's own logs and, in each account home the app manages, what the provider writes there and never reads back for a session — its logs, telemetry, traces, shell snapshots and paste cache — by the provider build's own cleanup list minus what belongs to a session. Its sweep runs on the service's one scheduler.
- A worktree kept by `Discard and remove` is a project's file, not a session's: no retention bound reaches it, `Delete old data` never touches it, and it goes only when the person presses `Delete now` ([Spec-008](008-worktree-lifecycle-and-execution-modes.md)).
- The service may compact its own storage in the background — compress, repack, archive, move large bodies to compressed storage, rewrite its indexes — only when everything the app promises to show survives: the transcript in order, every system message, tool rows and their output that no deletion above removed, message identities and times, and the undo and fork points still kept. Compaction never removes anything a person could see, and it is never a retention mechanism.
- A workflow run's step data — what each step read and wrote — and its snapshots stay until the person deletes the run or its session ([Spec-015 §Execution semantics](015-workflow-authoring-and-execution.md#execution-semantics)). Files a workflow saved on purpose are never touched by either act.
- Deleting run data is always an explicit act — deleting one run from its own row, or deleting runs older than a chosen age — and runs through the one purge, `daemon.retentionPurge`. Each asks once, names what goes and that a `Keep` run stays, and neither can be undone.
- Every resolved secret value is redacted from logs, step payloads, and error messages before they are written, so a retained run record never holds the credential its step resolved.

### Provider Privacy Settings

- The person's own provider privacy settings follow into every account home the daemon manages. At each start the daemon reads Claude Code's `DISABLE_TELEMETRY`, `DISABLE_ERROR_REPORTING`, `DISABLE_FEEDBACK_COMMAND` and `CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY` from the person's own Claude Code settings and passes them through `--settings`, and reads Codex's `analytics.enabled` and `feedback.enabled` from the person's own Codex config and passes them through `-c`, as every provider setting is passed. It never writes them into a home, so a change the person makes in their own files reaches the next process the daemon starts.
- The keys are each provider's own: Claude Code's are documented in its [data usage](https://code.claude.com/docs/en/data-usage) page, and Codex's in its [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). There is no switch of the app's own for them.

### Erasure In The Daemon's Database

- Nothing in the daemon's database is encrypted by the app. The person's messages, every queued message's body and a steer's text sit in their rows as plain text, like every other column, and so does the machine-authored `content_payload`.
- Deleting a session deletes its rows with SQLite's `secure_delete` on, so the freed pages hold nothing readable, and the write-ahead log is checkpointed with `TRUNCATE` once the delete commits. This is how erasure works for the daemon's database: `Delete old data` erases one session this way, and `Erase all data` deletes the store whole ([§Erasure Paths](#erasure-paths) Path 1).

### Postgres (Control Plane) Deletion

- The hosted account's records in the control plane Postgres database are hard-deleted when the person deletes the account with `sidekicks delete-account`, over the control plane's `account.delete` ([§Erasure Paths](#erasure-paths) Path 2). Deleting the account signs this machine out and never erases a machine's local data: that is `Erase all data` alone.
- Where a surviving control-plane row carries an independent retention basis — a revoked access token's `revoked_jtis` entry, kept until its reap — the reference to the deleted user must be anonymized (the data-subject FK is nulled via `ON DELETE SET NULL` — see [§Erasure Paths](#erasure-paths) Path 2 FK-safety) rather than the row deleted, preserving the surviving record and its referential integrity while severing the user linkage.

### Data Export

- `Export all data` on Settings › Runtime writes everything this machine keeps for the person as a readable folder, and `sidekicks export-data <folder>` does the same from the command line with the service running. The row's line reads `Everything the app keeps, as a folder: sessions, files, sidekicks, workflows and accounts. No settings, passwords or tokens.`; `Export…` opens the platform's save dialog with the name `sidekicks-export-<date>`. While it runs it reads `Exporting · 312 of 1,204 sessions` with `Cancel`; when done, `Exported to <path> · 1.2 GB` with `Show in Finder` (`Show in Explorer` or `Show in folder` elsewhere) and the line `The export is not encrypted; keep it somewhere safe.`; a failure names its cause and offers `Try again`.
- The folder holds:
  - `sessions/<id>.jsonl`: every event of every session, one per line, in the canonical event shape — the person's words and the machine-authored bodies alike, with the at-rest bodies of `interventions` and `queue_items` ([Spec-003](003-queue-steer-pause-resume.md)), so text on a refused intervention or on a queue item canceled before it reached the transcript is exported too;
  - `files/<session id>/…`: each session's artifacts as the store holds them;
  - `sidekicks/`: agent definitions in their export form;
  - `workflows/`: workflows in their export form;
  - `accounts.json`: each provider account's name, provider and plan, with no credential;
  - `hosted-account.json`: when signed in to the hosted account, the control plane's `account.export` reply (the account record and its device list);
  - `README.txt`: what each folder is.
- It leaves out the settings values, every credential, pasted token, workflow secret and key, and the diagnostic logs.
- It streams one session at a time within 64 MiB of memory whatever the data's size, one export at a time, and needs no archive library. An export writes one line to the diagnostic log and no event.
- Because every session is exported whole, a mention of the person inside a machine-authored body is exported with the rest; no selector decides what reaches the folder.
- The export carries no separately computed spend tally: the session cost receipt is a read-time fold over the exported rows ([Spec-014 §Session Cost Receipt](014-multi-agent-orchestration.md#session-cost-receipt)), and a second tally would be the second accountant [Spec-014 §Cost Figure Display Consistency](014-multi-agent-orchestration.md#cost-figure-display-consistency) forbids.
- Export must run before `Erase all data`, which deletes everything the export reads.

## Default Behavior

- `Keep sessions for` is 90 days and `Keep diagnostic logs for` 7 days. A session becomes eligible for deletion once `Keep sessions for` has passed since it was archived or closed.
- No session is purged except by the person's `Delete old data`. The diagnostic logs are the only data the service drops on its own, past their bound.
- Backups are off until the person turns on `Back up automatically` ([Spec-013 §Backup Policy](013-persistence-and-recovery.md#backup-policy)).

## Fallback Behavior

- If a purge fails before its row-deletion transaction, the session row stays `purge_requested` and the failure is logged, to be retried.

## Interfaces And Contracts

The daemon verbs a Settings page calls are described with their shapes in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md); the command-line verbs, the control plane's account verbs and the provider-side steps are this spec's, each with the plan task that builds it.

- `daemon.retentionRead` reads the retention bounds and, on the same reply, the counts `Delete old data` would remove; there is no separate preview verb. Built in [Plan-005](../plans/005-local-ipc-and-daemon-control.md) Phase R1.
- `daemon.retentionUpdate` changes one bound. No bound covers a kept worktree. Built in Plan-005 Phase R1.
- `daemon.retentionPurge` is `Delete old data`, the one purge (§Retention Policy): it marks the session `purge_requested`, deletes the files only this session names (the capture folder with its snapshot refs and base pins, a chat's managed workspace, and the provider's files for the session), then runs the one transaction that deletes the session's rows from every table with a `session_id`, with `secure_delete` on, and appends its `event.compacted` receipt, with the `TRUNCATE` checkpoint after it, retried until it succeeds and run even when nothing was deleted, and after that commit unlinks the artifact payloads no surviving manifest names; the scheduler starts a backup run after it. No event of the session records the purge, because the purge deletes every row of the session; its one record is the `event.compacted` receipt on the sentinel session ([Spec-005 §Event Maintenance](005-session-event-taxonomy-and-audit-log.md#event-maintenance-event_maintenance)). Built in Plan-005 Phase R1; the erasure step is [Plan-019](../plans/019-data-retention-export-and-deletion.md) T19.3.1.
- The managed workspace is deleted whole inside the purge, through `ManagedWorkspaceService.delete`, and kept on archive, and the archive sweep skips a mount whose origin is managed. Built in [Plan-001](../plans/001-session-core.md) and [Plan-007](../plans/007-worktree-lifecycle-and-execution-modes.md), ordered before the rows' delete by Plan-019 T19.3.1.
- `daemon.dataExport {destination}` returns a job and `daemon.dataExportSubscribe` carries its progress; `destination` is the path the save dialog hands back, or the command line's folder. Built in Plan-019 T19.2.1; `sidekicks export-data <folder>` in Plan-005 Phase R3.
- `daemon.dataErase {}` is `Erase all data` (§Erasure Paths Path 1). Built in Plan-019 T19.2.2; `sidekicks erase-data`, refused while the service holds the data folder, in Plan-005 Phase R3.
- `sidekicks delete-account`, over the control plane's `account.delete`, deletes the hosted account (§Erasure Paths Path 2) and signs this machine out; `account.export` answers the export's `hosted-account.json`. Built in Plan-015 Phase 5, with the command-line verb in Plan-005 Phase R3.
- On the provider side, every Claude Code process the daemon starts carries `"cleanupPeriodDays": 36500` in its `--settings` JSON and each account home's `settings.json` holds it; a managed value below it is raised as the `session.notice` kind `settings_ignored`; at purge the provider's files for the session are removed, and a Codex session is deleted with `thread/delete`. Built in [Plan-003](../plans/003-provider-driver-contract-and-capabilities.md) and Plan-001.
- Every act here is the person's own. The daemon serves its verbs only to the person's own authenticated clients ([Spec-006](006-local-ipc-and-daemon-control.md)), and the control plane serves `account.delete` and `account.export` only to the signed-in account.

## State And Data Implications

- The `purge_requested` state extends the session state model defined in [Session Model](../domain/session-model.md).
- Deleting a session is permanent: with `secure_delete` on and the `TRUNCATE` checkpoint, its deleted rows leave nothing readable in the database file or its write-ahead log. This is by design.
- The daemon's secrets are not in its database: each is its own item in the operating system's credential store ([§Daemon Secrets](#daemon-secrets)).

## Daemon Secrets

The daemon keeps each secret as its own item in the operating system's credential store: through `@napi-rs/keyring` the login keychain on macOS and the Secret Service on Linux, and on Windows Credential Manager, through the service's Windows half and `windows-native-keyring-store`. Nothing in the daemon's database is encrypted by the app, and no secret is kept there.

**The items**: the machine's Remote Control identity key and its channel key; the hosted sign-in's refresh token and DPoP key; a pasted provider token ([§PII Data Map](#pii-data-map), the account-plane posture); a workflow secret; the notification web address and its signing secret; the mail password; and each tool server sign-in's refresh token and DPoP key ([ADR-038](../decisions/038-mcp-credential-custody.md)).

**Linux.** The daemon opens the Secret Service store explicitly, every item with `{linux: {store: "secret-service"}}`, because the binding falls back on its own to the kernel keyring when no Secret Service answers, and the kernel keyring is cleared at every restart; it is never used. When no Secret Service answers, the daemon keeps its items in one file, `secrets.json` in its own data folder, readable by this account alone (mode `0600`), as `gh` and Codex do. It never falls back silently: Settings › Runtime then shows one line under the service's own, `Secrets are kept unencrypted in <path>, readable by this account alone, because no Secret Service is running.`, `<path>` being that file, read from `daemon.status.read`'s `secretsFile`, and the line is absent on every other machine but a Mac whose secrets are in `secrets.json`, which reads it with its own cause (below): from the approved logged-out service's takeover until `sidekicks daemon uninstall` moves them back, including after that service is turned off in Login Items & Extensions, and never while the service waits for approval.

**macOS while the person is logged out.** Where `sidekicks daemon install --while-signed-out` has the app register its own system service ([Spec-006 §The service on a Mac while logged out](006-local-ipc-and-daemon-control.md#the-service-on-a-mac-while-logged-out)), that service runs the daemon from the Mac's start (with FileVault on, once the disk is unlocked), before login and after logout, and cannot reach the person's login keychain, because a process outside a user context has only the System keychain in its search list ([TN3137: On Mac keychains](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)). So once the service is approved and takes over, the daemon moves its own secrets to the same `secrets.json` file Linux uses, in its data folder, and each Claude Code sign-in it runs into that account's own `.credentials.json`, every file readable by this account alone (mode `0600`); a Codex sign-in is already its home's `auth.json`. Each item is written, read back and only then deleted from its source, and a move stopped partway finishes at the next start. The install says so in one line before it asks: `With this on, sign-ins and secrets are kept in files readable by this account alone, because a service that runs while you are logged out cannot reach the login keychain.` Settings › Runtime then shows the Linux line with its own cause, `Secrets are kept unencrypted in <path>, readable by this account alone, because the service runs while you are logged out.`, and once the service is turned off in Login Items & Extensions, until `sidekicks daemon uninstall` moves the secrets back, `Secrets are kept unencrypted in <path>, readable by this account alone, because the service was set up to run while you are logged out.`, `<path>` read from `daemon.status.read`'s `secretsFile`. `Erase all data` removes those files with everything else, and `sidekicks daemon uninstall` moves the secrets and sign-ins back into the login keychain.

**A locked store.** A credential store that is locked or unavailable refuses with its cause, `locked` or `unavailable`, as `workflow.secret_store_unavailable` carries it ([Error Contracts](../architecture/contracts/error-contracts.md)), because a keychain can still be locked on macOS and Windows; a secret the store cannot take is stored nowhere else. On Linux a missing Secret Service takes the file instead, and on a Mac the daemon's secrets are in `secrets.json` from the approved logged-out service's takeover until uninstall (above), so neither cause is raised there.

**Windows, native and WSL alike.** On both kinds of Windows computer each item is a Credential Manager generic credential at `CRED_PERSIST_LOCAL_MACHINE`, never `CRED_PERSIST_ENTERPRISE`, so it does not roam with the profile. Each is written and read in the service's Windows half, never in the daemon's own process, through `windows-native-keyring-store` 1.1.0 with `persistence=local`, because `@napi-rs/keyring` 2.1.0's Windows binding passes only the target and so writes every entry at Enterprise. The daemon's `WindowsCredentialStore` carries every call to the Windows half, over its channel while the service runs and one-shot while it does not (`sidekicks-windows-half.exe keystore get|set|delete <entry>`, reading and writing the item on stdin and stdout), because `sidekicks sign-in`, `sidekicks sign-out` and `sidekicks erase-data` need the credential store while the service is stopped; every unit that keeps an item on Windows goes through it. On a Windows computer whose service runs in WSL 2, the daemon inside the distribution keeps its items in Windows' Credential Manager through the Windows half, so a Windows computer has one place for secrets on either side; the Secret Service inside a WSL distribution is never used. A move between Windows and a distribution carries the store, and the items stay in Windows' Credential Manager for both sides.

**Backups, and a restore on another computer**:

- A backup is a plain copy of what it lists — the service's database, copied online; the machine's settings file; each chat session's workspace; each kept session's file checkpoint copies; each kept session's conversation files in every account home it ran in; and the agent memory folder ([Spec-013 §Backup Policy](013-persistence-and-recovery.md#backup-policy)) — and holds no credential.
- A restore on another computer reads it directly; the person then signs in to providers and links devices again. Restoring on the machine that wrote it needs nothing more. A Windows computer is one machine whichever side runs its service, so a backup made on one side restores on the other as a same-machine restore.
- A session removed by `Delete old data` leaves the backup mirror at the next run and stays only in database copies taken before the delete, until they age out (at most four weeks), and the delete's confirm says so ([Spec-013 §Backup Policy](013-persistence-and-recovery.md#backup-policy)).

## PII Data Map

The data map enumerates **every** PII-carrying path the data acts reach — `Delete old data` for one session, `Erase all data` for everything on the machine, `sidekicks delete-account` for the hosted account — and each path's **Removal** cell names the act that removes it, so no path is left out of the map (the provider-account plane's node-local surface goes when the person removes the registration). Exhaustive enumeration is required so the erasure paths in the next section have no gaps. Paths are grouped by durability tier.

**Durable tier (canonical audit log + control plane):**

| Table | Column | PII Type | Retention | Removal |
| --- | --- | --- | --- | --- |
| `session_events` (SQLite) | `payload` | The person's own words in the event payload: their messages, and the file paths and code snippets they wrote, in plain text like every other column | Session lifetime: until the person deletes the session with `Delete old data` | Deleted at purge with `secure_delete` on, with a `TRUNCATE` checkpoint after commit, so neither a freed page nor the write-ahead log keeps a readable copy; deleted with the store by `Erase all data` ([§Erasure Paths](#erasure-paths) Path 1) |
| `session_events` (SQLite) | `content_payload` | **Machine-authored** session content, not a data subject's authored text — the assistant message body, the reasoning-update body, and tool-call arguments / result / error bodies. It is mapped here **because it can quote a user**, not because a user wrote it: an assistant reply restates what was asked and a tool result can contain a file the user named. Plain text like every other column ([Local SQLite Schema §Session Events](../architecture/schemas/local-sqlite-schema.md#session-events-plan-001-extended-by-plans-004-012)); it carries no user linkage, so no per-person selector reaches it | Session lifetime: until the person deletes the session with `Delete old data`. Background compaction never removes it (§Retention Policy) | **Outside a per-person selector** — the artifact-payload posture below, applied unchanged. Erasure severs the person's **reach**, not the session's record of what its agents did |
| `interventions` (SQLite) | `payload` | User-authored intervention body: a steer's text, in plain text | Session lifetime: until the person deletes the session with `Delete old data` | Deleted at purge with `secure_delete` on and a `TRUNCATE` checkpoint after commit, as `session_events.payload` is; deleted with the store by `Erase all data` |
| `queue_items` (SQLite) | `payload` | Queued body — the follow-up message a user queues against an active run, or an orchestration-authored item's prompt (a workflow step's input, an orchestrated child-run prompt), which is the session's private content too — in plain text | Row lifetime: queue rows are durable and never deleted on drain (the row is canonical for audit, and is never evented), so the body persists until its session is deleted with `Delete old data` | Deleted at purge with `secure_delete` on and a `TRUNCATE` checkpoint after commit, in the same transaction as the session's events, so every copy of one send goes in a single act; deleted with the store by `Erase all data` |

| `runtime_nodes` (PG) | public key and algorithm, name, platform, service version, registered and last-connected times | The account's registered machines (identifier-class PII: each row names one of the person's machines) | Until the machine is removed, and at most account lifetime | DELETE row on account deletion (inside the Path-2 FK closure) |
| `trust_statements` (PG) | the signed statement | The account's append-only chain of trust statements (`device.linked`, `device.renamed`, `device.revoked`, `passkey.added`, `passkey.removed`, `runtimenode.added`, `runtimenode.renamed` and `runtimenode.removed`), each a few hundred bytes | Account lifetime | DELETE rows on account deletion (inside the Path-2 FK closure) |
| `refresh_token_families` (PG) | `user_id`, `cnf_jkt` | One row per live sign-in, holding its family's current token id and the key its tokens are bound to (identifier-class PII: each row names one of the user's signed-in machines) | Sign-in lifetime | DELETE row at sign-out, revocation or account deletion |

> **Artifact-payload posture.** Artifact manifests and their CAS payloads (`artifact_manifests` + `artifact_payload_refs`) are work product published into the person's own session and held on the machine that ran it, which lists them on every linked device. No person and no method deletes a single artifact: a session's artifacts go only with the session, through `Delete old data` or `Erase all data`. Before Send, covering part of a staged picture replaces the staged file with its covered copy, so the uncovered copy never enters the session. The manifest's nullable `created_by` stamp stays for the manifest's lifetime as the record of who made the artifact. `session_events.content_payload` follows the same rule: an assistant's reply and a tool's result are work product produced into the session, and go with the session, at purge through `Delete old data` or with the store through `Erase all data`. `payload` on the same rows holds every word the person wrote and goes the same way ([§Erasure Paths](#erasure-paths) Path 1).

> **Account-plane posture.** The provider-account registry holds **no credential material of any kind** — no token, no refresh token, no API key, no session cookie. Credentials live inside each account's own credential home, owned and written by the provider's tooling, and the daemon brokers refresh without ever holding the values ([Spec-025 §Credential homes and the constructed environment](025-provider-accounts-and-credential-homes.md#credential-homes-and-the-constructed-environment), [Spec-025 §Credential-refresh brokering](025-provider-accounts-and-credential-homes.md#credential-refresh-brokering)). **That absolute is bounded in one place.** [ADR-026](../decisions/026-provider-credential-custody-posture.md) D2 authorizes the daemon to hold exactly one class of credential material — a vendor-minted non-interactive token, supplied on one write-only wire input. **It is not a row in any table**, so this map's table-keyed rows are complete as written: the value is kept only in the operating system's credential store, one item keyed by account identity, as every daemon secret is ([§Daemon Secrets](#daemon-secrets)); a token the store cannot take is refused with one line per cause (`locked`, `unavailable`) and stored nowhere else, and `provider_accounts` records only that an account's **observed** mode is the token mode — a label, not the material. The deletion obligation is stated here rather than left implicit: **removing an account registration MUST delete that account's credential-store item** in the same operation, and `Erase all data` deletes every credential-store item the app made. A registry row removed while its token survived would leave live credential material on the machine with nothing left pointing at it — unattributable, out of reach of any later deletion, and invisible to every audit this map supports. The token is a credential and not personal data, so no session's purge reaches it and it appears in no export; its lifecycle obligation is destruction-with-its-account, and that is where it belongs. The registry's remaining columns are the machine's own configuration rather than session content: the recorded residual is `credential_home_path`, a local filesystem path that on most machines embeds the operating-system account name, kept on the machine under the same reading as the provider-reported identity row above and going with the same registration. Nothing in the account plane is relayed off the machine or uploaded to the control plane; `Export all data` writes each account's name, provider and plan to `accounts.json`, with no credential.

**Nothing is exported off the machine.** The app sends no telemetry and has no outbound telemetry sink: a crash report is built on the machine that crashed, stripped of personal data there, kept there and deleted with the diagnostic logs, and no workflow run is sent to an OpenTelemetry collector or any other exporter. Each provider's own telemetry export from the processes the daemon starts is received on one loopback port on this machine, read to price the requests a session's stream leaves out, and written to the service's own diagnostic logs, which drop it past `Keep diagnostic logs for`; none of it is forwarded to a telemetry destination the person set. ## Data Retention and Deletion Policy

This section states end-to-end coverage across both storage tiers ([ADR-037](../decisions/037-kept-sessions-keep-their-provider-files.md)).

- **Retention**: A kept session holds its personal data until the person deletes it; nothing deletes a session by age, and background compaction never removes anything a person could see. Past `Keep sessions for` a finished session is eligible for deletion, and eligible is not deleted.
- **The provider's own files**: Claude Code's age sweep never reaches a kept session's files, because every Claude Code process the daemon starts carries `"cleanupPeriodDays": 36500` and every account home the daemon manages holds the same value. `Delete old data` removes a purged session's provider files from every account home it ran in, Codex's through `thread/delete`. What a provider writes into those homes and never reads back goes past `Keep diagnostic logs for`.
- **Session purge**: `Delete old data` is the one purge. It marks the session `purge_requested`, deletes the files only this session names (its capture folder, snapshot refs and base pins, a chat's managed workspace and the provider's files), then, in one transaction, deletes the session's rows with `secure_delete` on, checkpointing with `TRUNCATE` after commit, and after that commit unlinks the artifact payloads no surviving manifest names ([§Ordering And Atomicity](#ordering-and-atomicity)). The session state `purge_requested` exists in the [Session Model](../domain/session-model.md) with transitions `archived -> purge_requested` and `closed -> purge_requested`. How each data act is recorded in the event log is [Spec-005 §Data Acts](005-session-event-taxonomy-and-audit-log.md#data-acts).
- **Data export**: `Export all data` writes every session's events, the files, agent definitions, workflows and provider accounts without credentials, and the hosted account's own export when signed in. Export must run before `Erase all data`.
- **Erasure of everything on the machine**: `Erase all data` stops every run and shell, signs each provider account out, revokes this machine's hosted refresh family, deletes every credential-store item the app made, deletes the data folder with the account homes it created, and starts again empty ([§Erasure Paths](#erasure-paths) Path 1). A disk backup taken earlier keeps what it held.
- **Deletion of the hosted account**: `sidekicks delete-account` hard-deletes the account's control-plane rows across the `REFERENCES users(id)` inbound-FK closure, severs the surviving references that carry an independent retention basis through `ON DELETE SET NULL`, and signs this machine out ([§Erasure Paths](#erasure-paths) Path 2). It never erases a machine.
- **Backups**: a deleted session leaves the backup mirror at the next run and stays only in database copies taken before the delete, until they age out at four weeks; the delete's confirm says so.

## Erasure Paths

Erasing a person's data spans three independent storage paths, each carried out by its own act and each complete on its own: Path 1 is `Erase all data` on a machine, Path 2 is `sidekicks delete-account` on the control plane, and Path 3 is the diagnostic tier's own bound. Neither act triggers the other: deleting the account never erases a machine, and erasing a machine never deletes the account. A person who wants both runs both, on each machine they keep. `sidekicks delete-account` is the one way to delete the hosted account. A person who has lost every machine installs the command-line tool on another computer, runs `sidekicks sign-in`, confirms the sign-in with their passkey on the device-code page in the browser, and runs `sidekicks delete-account`. The [Hosted Account Deletion Runbook](../operations/hosted-account-deletion-runbook.md) runs Path 2 by hand as a break-glass procedure, only when that path is genuinely impossible (for example, the owner has no passkey left to verify a sign-in); it is never a second way to delete an account.

**The provider account registry.** The daemon-local `provider_accounts` registry holds no credential material ([§PII Data Map](#pii-data-map) account-plane posture). Its personal data is the provider-reported identity, which goes when the person removes the registration and with the data folder on `Erase all data`.

### Path 1 — Everything on the machine (`Erase all data`)

**Mechanism.** `Erase all data`, from Settings › Runtime under the line `Removes everything this app keeps on this machine. Project folders stay.`, or `sidekicks erase-data`, confirms in place — `Erase everything this app keeps on this machine? Every session, file, sidekick, workflow and account sign-in goes. Project folders stay. Backups you made before keep their copy. This cannot be undone.`, with `Erase everything` and `Cancel` — and then, in order:

1. stops every run and shell, as Runtime's `Stop` does;
2. signs each provider account out through the provider's own sign-out: `claude auth logout` in each Claude Code account home, and `account/logout` on each Codex service;
3. revokes this machine's hosted refresh family, when signed in to the hosted account;
4. deletes every credential-store item the app made ([§Daemon Secrets](#daemon-secrets)): the machine's identity key and channel key, the hosted sign-in's refresh token and DPoP key, pasted tokens, workflow secrets, the web address and its signing secret, the mail password and each tool server's sign-in;
5. deletes the data folder, the account homes it created included;
6. starts again empty, and the app opens as on first launch.

`sidekicks erase-data` is refused while the service holds the data folder; on Windows its item deletion runs through the Windows half's one-shot verbs ([§Daemon Secrets](#daemon-secrets)).

**Scope.** Everything the app keeps on this machine: the database, the data folder, the account homes the app created and every credential-store item it made. Project folders and the person's own provider folders stay. A disk backup taken earlier keeps what it held; the erase claims no more than that. A single session's PII leaves earlier, with its rows, when the person deletes that session (§Retention Policy).

**Audit artifact.** None on the machine: an erase leaves no log to write into.

### Path 2 — Postgres PII rows (hard DELETE)

**Mechanism.** `sidekicks delete-account`, over the control plane's `account.delete`, deletes the hosted account. It first revokes every refresh family the account holds, so each is written to the denylist, then runs Path 2 in one Postgres transaction, and signs this machine out. Path 2 is exhaustive over the complete `REFERENCES users(id)` inbound-foreign-key closure in [shared-postgres-schema.md](../architecture/schemas/shared-postgres-schema.md) — not only the PII-content columns in the [§PII Data Map](#pii-data-map) durable tier, but **every** Postgres row that links to the deleted account. Per-table disposition by retention basis:

- **Hard DELETE** (no independent retention basis): `users` (Plan-015), `devices`, `runtime_nodes` and `trust_statements` (Plan-025 — the account's linked devices with their public keys and push addresses, its machines' registrations with their public keys and names, and the append-only signed chain of the account's trust statements; deleting them is safe at live-verification semantics, since every machine verifies the chain it keeps itself and no retained row re-verifies a signature by one of the account's keys after deletion), `webauthn_credentials` and `webauthn_challenges` (Plan-015 — enrolled passkeys and in-flight ceremony challenges; deleting them is safe at live-verification semantics, since a credential is verified at ceremony time and no retained row re-verifies one after deletion, and challenge rows self-expire within five minutes regardless), `refresh_token_families` (Plan-015 — one row per live sign-in, holding its family's current token id; revoking a family deletes its row, so none remains once `account.delete` has revoked the account's families, and the `user_id` reference cascades), `revoked_token_families` (Plan-015 — the account's revoked refresh-token families: a refresh token has no expiry of its own, lasting until sign-out or revocation, so a revoked family's row stays for the account's life and goes with it; once the account and the machine keys its tokens are bound to are deleted, none of its tokens can be traded).
- **Not in the closure: push.** The control plane holds no notification queue, filter or notification-preferences table. A push is sealed on the machine to the receiving device's push key — HPKE with X-Wing, and [RFC 8291](https://www.rfc-editor.org/rfc/rfc8291) for Web Push — and the relay adds only the person's own APNs, FCM or VAPID credentials and holds nothing that opens a notice; each machine decides per device before it sends (the device's switch, its kind, the session's mute, and no push while an app window is in front on any of the person's devices except a workflow's Notify step, which always sends). A push is a delivery, not a fact of the session, and nothing about it is written to any session log.
- **Anonymize-with-security-survival via `ON DELETE SET NULL`**: `revoked_jtis`, the revoked access tokens — the user hard-DELETE auto-nulls `user_id`, severing the data-subject linkage, while the key (`jti`, the table PRIMARY KEY — **not** `user_id`) is untouched and the row stays denied until its natural `expires_at + 24h` reap, a margin past the access token's short lifetime, so deletion does not resurrect a revoked access token within its remaining validity window. A revoked family's row in `revoked_token_families` has no natural expiry to reap at, because a refresh token has none: it stays for the account's life and is hard-DELETEd with the account (above). The control plane writes `revoked_token_families` on every revocation — a device revoked, the person signing out, a spent refresh token presented again, and the account deleted — and `revoked_jtis` for an access token revoked before its expiry. The refresh endpoint checks the family, and the control plane and the relay check the token id, on every request, each by primary key.

**FK-safety (the anonymize mechanism is `ON DELETE SET NULL`, not a tombstone row).** The one anonymize-class FK, `revoked_jtis.user_id`, references `users(id)` and must survive the hard-DELETE of the user it references. Because deletion hard-DELETEs the `users` row, an in-place rewrite to a non-user "tombstone identifier" would violate the FK, and a _reserved tombstone user row_ would leave a standing live identity on every surviving row that no later reader could tell apart from a real registration. The FK-safe mechanism is therefore `ON DELETE SET NULL`, and the FK is **nullable + `ON DELETE SET NULL`** in the control plane's one schema, where the control-plane account work adds the denylist ([Plan-015](../plans/015-hosted-account-and-identity.md) Phase 5), so the user hard-DELETE auto-nulls the reference DB-side; the closure is verifiable against [shared-postgres-schema.md](../architecture/schemas/shared-postgres-schema.md). The `jti` key survives the null because it is the PRIMARY KEY, not the FK. `revoked_token_families` is not in this class: its rows are hard-DELETEd with the account.

**Scope.** Exhaustive over the `REFERENCES users(id)` inbound-FK closure named in the Mechanism above — the closure is read from [shared-postgres-schema.md](../architecture/schemas/shared-postgres-schema.md), so it cannot drift behind a hand-maintained list. If any row fails its DELETE (foreign-key constraint, row lock, connection failure), the transaction rolls back, `account.delete` reports the failure, and no row is deleted.

**Audit artifact.** No event-log row is emitted per Postgres table. The account's revoked families are deleted with the account, and its revoked access-token entries are what survive of it, until their reap. Nothing is written to any machine's event log.

### Path 3 — Bounded-retention diagnostic buckets (age bound and erase)

**Mechanism.** Each diagnostic bucket listed in the [§PII Data Map](#pii-data-map) bounded-retention tier (`driver_raw_events`, `command_output`, `tool_traces`, `workflow_engine_events` and the service log, `logs/service-<start time>.log`) deletes a log file whole once it is past `Keep diagnostic logs for`, 7 days by default, on the service's one scheduler; the same bound drops what a provider writes into each account home and never reads back for a session. `Erase all data` deletes every file with the data folder. There is no per-person flush: the tier belongs to the one person whose machine it is, and it never outlives its bound.

**Scope.** Every file in the bounded-retention diagnostic tier, and the provider's own non-session files in each account home the app manages.

**Audit artifact.** None; a deleted diagnostic file is not a session fact.

### Ordering And Atomicity

Each act orders its own steps; no act spans two stores.

- **Session purge: the mark, the session's own files, the rows and the checkpoint, then the unreferenced payloads.** The session is marked `purge_requested` first, which locks its row. Then the files only this session names go: the capture folder with its snapshot refs and base pins, a chat's managed workspace, and the provider's files. Then the rows of every table with a `session_id` — drafts, queue items, workspaces, worktrees, run execution contexts and its artifact manifests among them — are deleted, and the `event.compacted` receipt appended, in one SQLite transaction with `secure_delete` on, so their freed pages hold nothing readable, and the write-ahead log is checkpointed with `TRUNCATE` once it commits, so the log keeps no copy of them; the checkpoint is retried until it succeeds, and runs even when nothing was deleted. A failure before that transaction leaves the row `purge_requested`, to be retried ([§Fallback Behavior](#fallback-behavior)). Stored artifact payloads go after the commit, and only those no surviving manifest names, because a payload deleted first could leave another session's manifest over missing bytes; one a crash leaves behind is reclaimed by the orphan sweep ([Spec-012 §Local Artifact Deletion And CAS Reclaim (V1)](012-artifacts-files-and-attachments.md#local-artifact-deletion-and-cas-reclaim-v1)).
- **Erase: work stops before secrets go, and secrets go before files.** Runs and shells stop first so nothing writes during the erase; provider sign-out and the hosted refresh family's revocation run while the service can still reach them; the app's credential-store items are deleted before the data folder.
- **Account deletion: revocation before rows.** The account's refresh families are revoked, and so written to the denylist, before Path 2's transaction deletes the account's rows, so no token outlives the account within its validity window.

Path 2 runs in one Postgres transaction and is idempotent: a DELETE of an already-deleted row affects zero rows. The erase is idempotent in the same sense: a step that finds its target already gone moves on.

## Example Flows

- `Example: A session was archived 91 days ago. It is eligible for deletion and nothing has removed it. The person opens Settings › Runtime and presses Delete old data, which confirms "Delete 14 archived sessions and their logs? Each chat's session workspace goes too; files in project folders stay. This cannot be undone." The purge marks each session purge_requested, deletes its capture folder, its managed workspace and its Claude Code conversation file in every account home it ran in, then deletes its rows with secure_delete on and checkpoints the write-ahead log.`
- `Example: A Claude Code session last used 400 days ago is resumed. Its conversation file is still in the account home, because every Claude Code process the daemon starts carries "cleanupPeriodDays": 36500, and the session continues where it stopped.`
- `Example: Before handing a laptop back, the person presses Export… under Export all data and writes sidekicks-export-2026-09-24 to an external drive, then presses Erase all data and Erase everything. The service stops its work, signs each provider account out, deletes its credential-store items and data, and starts again empty. Project folders are untouched.`
- `Example: The person runs sidekicks delete-account. The control plane revokes the account's refresh families, hard-deletes the account's rows, its revoked families among them, and nulls the user reference on the revoked access-token entries that survive to their reap, and this machine is signed out. Its sessions stay on it until the person deletes them or erases the machine.`

## Implementation Notes

- Every data act ships in V1, each built by the task §Interfaces And Contracts names: the session purge with `secure_delete` on and its `TRUNCATE` checkpoint, `Export all data`, `Erase all data`, `sidekicks delete-account`, and the token denylist written on every revocation.
- Every daemon secret is a credential-store item from the first build ([§Daemon Secrets](#daemon-secrets)).
- The data map of PII fields should be maintained as a living document alongside the data architecture.

## Pitfalls To Avoid

- Deleting a session's rows without `secure_delete` on, or without the `TRUNCATE` checkpoint after commit, which leaves its text readable in freed pages or the write-ahead log
- Assuming the hosted account's Postgres `DELETE` reaches a machine's SQLite event log; a machine's sessions go only with `Delete old data` or `Erase all data`
- Running `Erase all data` before the export (the export must happen first)
- Treating `purge_requested` as a terminal state instead of a transient processing state

## Acceptance Criteria

- [ ] Session state model includes the `purge_requested` state with its transitions from `archived` and `closed`, and no state after it: the purge's last step deletes the session's row.
- [ ] No session is deleted except by `Delete old data`: a finished session past `Keep sessions for` stays readable and resumable until the person deletes it.
- [ ] A Claude Code conversation file older than Claude Code's default cleanup period survives a new process's start in an account home the daemon manages, including under a repository whose own `.claude/settings.json` sets `cleanupPeriodDays` to 1; a managed value below 36500 raises `settings_ignored`.
- [ ] `Delete old data` marks each session `purge_requested`, removes the files only that session names — its capture folder, snapshot refs, base pins, managed workspace, and the provider's files from every account home it ran in (Codex through `thread/delete`) — then deletes its rows, its artifact manifests among them, in one transaction with `secure_delete` on, checkpointing with `TRUNCATE` after commit, and after that commit unlinks each artifact payload no surviving manifest names, the orphan sweep reclaiming one a crash leaves; a failure before that transaction leaves the row `purge_requested`, to be retried; a terminal session's conversation in the person's own Codex folder stays.
- [ ] The diagnostic tier and the provider's non-session files in each account home drop past `Keep diagnostic logs for`; no other data drops on its own.
- [ ] Nothing in the daemon's database is encrypted by the app: the person's messages, every queued message's body and a steer's text sit in plain columns.
- [ ] After `Delete old data`, a byte scan of the database file, its freed pages and its write-ahead log finds no plaintext of a deleted session's typed messages, queue item bodies, steer text or machine-authored bodies.
- [ ] `Export all data` writes every session's events with the files, agent definitions, workflows, provider accounts and the hosted account's export, and the folder holds no settings value, credential, token, workflow secret, key or diagnostic log.
- [ ] `Erase all data` runs its six steps in order, after which no credential-store item the app made remains, the data folder is gone, project folders are untouched, and the app opens as on first launch.
- [ ] Each daemon secret is its own credential-store item: in the login keychain on macOS, or, on a Mac from the approved logged-out service's takeover until `sidekicks daemon uninstall` moves them back, including after that service is turned off in Login Items & Extensions, and never while it waits for approval, in `secrets.json` in the data folder at mode `0600`, with each provider sign-in in its account's own sign-in file at mode `0600`; on Windows, native and WSL alike, a Credential Manager generic credential at `CRED_PERSIST_LOCAL_MACHINE` written by the Windows half; on Linux in the Secret Service, or, when no Secret Service answers, in one file in the data folder at mode `0600`, and never in the kernel keyring. A locked store refuses with its cause.
- [ ] A backup holds no credential, and a restore on another computer reads it directly.
- [ ] `sidekicks delete-account` revokes the account's refresh families, hard-deletes every row of the `REFERENCES users(id)` closure, the account's `refresh_token_families` and `revoked_token_families` rows included, leaves every `revoked_jtis` row with its key and `user_id` null until its `expires_at + 24h` reap, and leaves the machine's local data untouched.
- [ ] The anonymize-class FK `revoked_jtis.user_id` is nullable + `ON DELETE SET NULL` in the control plane's one schema.
