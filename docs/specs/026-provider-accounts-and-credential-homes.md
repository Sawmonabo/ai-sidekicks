## Purpose

An operator drives provider CLIs from more than one paid account: a personal subscription and a work seat, two organizations, a metered API key beside a plan-included subscription. V1 must let a runtime node hold several accounts per provider, choose which one pays for a given run, keep each account's credential material in its own isolated home so the accounts cannot corrupt one another, and report spend per account so that plan-included usage is never silently added to billed dollars.

This spec defines the **provider account** as a first-class node-local entity: how it is registered, how it is identified, how its credential home is constructed and validated, how a run selects one, and what the rest of the corpus may assume about it. Two surfaces elsewhere in the corpus already presuppose an account axis without defining it — the account-scoped provider-quota snapshot (`usage.rate_limit_update`, [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) and the per-phase park schedule that exists because "two parallel branches of one run may park concurrently against different provider accounts" ([Spec-015 §Provider-limit pacing and durable resumption (SA-40)](015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-40)). This spec is the canonical home those surfaces resolve against.

## Scope

- The provider-account registry: registration, listing, current-account selection, removal, and the account's durable fields.
- **Account identity** and **credential generation** — the two derivations other specs consume by name.
- Per-account isolated credential homes: construction, the environment discipline that reaches the provider child, validation at spawn, and the fail-closed refusal when a home is missing or husked.
- Per-provider current account plus the pins a saved agent definition and a workflow step carry, and the authorization posture of each.
- **Billing mode** (`subscription` / `metered` / `unknown`) as a recorded, displayed property.
- The concurrency posture for simultaneous runs on two accounts of one provider, specified through the parity triad with a named verification obligation and a degrade-honestly floor.
- Brokering the provider-initiated credential-refresh request within the bounded custody posture [ADR-028](../decisions/028-provider-credential-custody-posture.md) sets.
- **Brokered interactive sign-in** and the bounded **non-interactive token** registration path — the two legs ADR-028 authorizes, and the boundary that keeps everything else refused.
- The per-account **credential-home health observation** cadence, its opt-out, and the freshness horizons it renders.
- **Per-limit provider quota**: the limit identifier that keys an account's quota windows, and the durable per-account window registry that holds the newest reading of each.

## Non-Goals

- **Bounded token custody — one class, one input, and nothing else** (amended 2026-08-26 under [ADR-028](../decisions/028-provider-credential-custody-posture.md); this bullet previously stated an absolute, and the ADR is what authorizes replacing it). Credential material lives where each provider stores it, and the daemon still never logs, relays, or serves it: **no event, error, log, metric, or wire-read payload carries credential material, ever**. The single exception is ADR-028's D2 class — a vendor-minted non-interactive token, supplied by the operator on the `register` verb's dedicated write-only input, sealed through [ADR-021](../decisions/021-cli-identity-key-storage-custody.md)'s ladder, and injected only into the child environment of processes bound to that account. It is admitted **only** under the ADR's four conjunctive conditions (provider-minted through a documented subcommand; consumed through a provider-documented variable; carrying no refresh token, so possession mints no successors; supplied deliberately through the dedicated non-echoing input), and material failing any one of them is refused. What this spec principally adds remains a **location** discipline — which home a provider process reads and writes — and the custody claim it now makes is exactly this one and is bounded on its face.
- **No provider config-file ownership.** [Spec-025 §Non-Goals](025-mcp-server-configuration-and-governance.md#non-goals) keeps provider config files provider-owned and mutated only through each provider's sanctioned write mechanism. Choosing which home a provider process uses is a spawn-time environment decision and is **not** a write into a provider config file; this spec issues no such write and claims no ownership over the bytes inside a home.
- **No account provisioning or billing integration.** The daemon does not create provider accounts, purchase plans, read invoices, or call any vendor billing API. Billing mode is operator-declared or provider-observed, never fetched.
- **No control-plane account records.** Accounts and their spend are node-local. Nothing about a provider account is written to the control plane; the shared schema's permitted row classes do not admit them and this spec does not widen that set.
- **No first-run onboarding surface authored here.** The provider step of the first-run flow is authored by [Spec-023 §Provider Authentication (Group B)](023-first-run-onboarding.md#provider-authentication-group-b), which landed 2026-08-25; this spec supplies the registry that step registers into and the readiness derivation it reads (§Node provider readiness and the sign-in handoff), and still authors no onboarding UI, no walkthrough step, and no first-run trigger. The obligation that was deferred here is discharged, not dropped — [BL-154](../archive/backlog-archive.md) is `completed`.
- **No control-plane rate-limit policy.** Provider-side throttling is expressly a Non-Goal of [Spec-019](019-rate-limiting-policy.md); this spec's provider-quota surfaces do not belong there and do not amend it.

## Required Behavior

### The account registry

- A runtime node holds zero or more **provider accounts** per provider. Each is registered by the node operator with a provider and a credential home; the daemon mints the account's identity and records the registration durably.
- **An account is identified on every surface by the identity its own provider reports, and by nothing this product invents.** The identity is three fields read from the provider itself — the address it returns, the plan in the provider's own word, and the organisation where the plan carries one — and there is **no operator-typed display label**, no generated name, and no computed suffix anywhere. All three fields are part of the identity rather than decoration, because **one address can hold two accounts** of the same provider on different plans, and an identity of address alone could not tell them apart. Both pinned providers publish the three: Claude Code's own credential-status read reports the address, the subscription type and the organisation name, and the Codex sign-in token carries the address and the plan type. Where a provider reports no organisation, the identity is two fields; absence is not filled in.
- **Billing mode is the account row's one operator-authored field.** The provider-reported identity and the credential-home path are read-only: a surface that let either be typed over would let an operator relabel one account as another, and historical spend is keyed to identity.
- Registration is **node-owner authority** — the caller-owns-the-node model, the same authority class [Spec-025 §Non-Goals](025-mcp-server-configuration-and-governance.md#non-goals) uses for MCP governance. The predicate is ownership, never transport origin: the owning user reaches it identically from the machine itself and from any linked device, and a caller who does not own the node is **denied, never queued**.
- Exactly one account per provider MAY be marked the **default**, and that mark is the provider's **current** account — one fact under two words, the registry's and the operator surface's. It is what new sessions start on and what every unpinned running session on that provider moves to when it is pressed (§Moving a session to another account). Where a provider has accounts registered but none marked default, run admission for that provider refuses rather than guessing (§Fallback Behavior).
- Removing an account MUST NOT delete its credential home, MUST NOT run the provider's own sign-out, and MUST NOT be permitted while a run bound to that account is live. The home is operator-owned material; deregistration forgets the registry row, not the operator's credentials. **Running the provider's sign-out here would be a destructive side effect on material that is not this product's**: on at least one pinned leg signing out can end the login of the account being left, so an operator who merely wanted the row gone would find the credential gone too, and signing in again would be a full browser round trip rather than a re-registration. Ending a login is the separate, deliberate sign-out act (§Interfaces And Contracts), and the two are never folded into one.

### Account identity and credential generation

Two derivations are defined here because other specs consume them by name and none of them defines either.

- **Account identity** is the daemon-minted, opaque, immutable `accountId` recorded at registration. It is stable across credential rotation, re-authentication, a billing-mode correction, and default changes — it names _which account_, never _which credential_. It is never derived from a credential, an email address, a subscription identifier, or any path, so nothing about it leaks account material, and it is never reused after removal.
- **Credential generation** is a monotonically increasing integer stamped on the account row, starting at 1 at registration and incremented by the daemon at **every credential-home lifecycle transition it performs or observes**: a completed re-authentication, an operator-initiated home reset, and a transition of the account's probe result into or out of `authenticated` **as established by the deliberate probe verb or by validation at spawn**. A background health observation is deliberately not one of these: it writes the stored health pair and never bumps the generation, however its reading compares to the stored one (§Credential-home health observation) — [Spec-015 §Provider-limit pacing and durable resumption (SA-40)](./015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-40) keys parked work on `(accountId, credentialGeneration)`, so an observer that bumped on a transient fault would end an attention epoch for nothing. It names _which credential era_, so a consumer can tell "the same account, re-authenticated" from "the same account, unchanged" without inspecting credential material.

The pair `(accountId, credentialGeneration)` is the corpus's account-plane key. [Spec-015 §Provider-limit pacing and durable resumption (SA-40)](015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-40) composes its attention key from the provider, the account identity, and the credential generation held stable across the refusing dispatch — those two components are **these** derivations, and a re-authentication that bumps the generation therefore ends the old attention epoch rather than folding a repaired account's fresh refusals into the stale one. The account-scoped quota display (§Provider Quota Is Account-Scoped) and the cost receipt's paying-account column ([Spec-014 §Session Cost Receipt](014-multi-agent-channels-and-orchestration.md#session-cost-receipt)) consume the same `accountId`.

### Credential homes and the constructed environment

Each account owns an **isolated credential home** — a daemon-managed directory holding exactly that account's provider credential material, distinct from every other account's home and from the operator's own ambient provider configuration.

Isolation is the mechanism, and it exists for a specific failure: provider credential files are rewritten in place on token refresh, so two concurrent processes sharing one home can interleave writes and destroy a refresh token that only one of them holds the successor to. Separate homes give each account its own credential file and its own lock scope, so a refresh on one account cannot corrupt another. This is why homes are per-account and not per-provider.

The home reaches the provider child **inside the existing constructed-environment discipline** and never beside it. [Plan-004 §Phase 3 — Codex + Claude driver implementations](../plans/004-provider-driver-contract-and-capabilities.md#phase-3--codex--claude-driver-implementations) already requires that a provider child environment is **constructed, never inherited** — the child receives exactly the curated base plus the run-provisioned variables, with the effective credential policy's denied variables stripped at construction. This spec adds normative content to that regime rather than contradicting it:

- The provider **credential-home variables are a named, closed subset of the run-provisioned variables**, set by the daemon at spawn from the selected account's home and from nothing else. They are **reserved to the daemon**: the daemon is their sole writer, an inherited or caller-supplied value of a reserved name is discarded at construction rather than merged, and no session, run, workflow, execution posture, or MCP configuration surface may set one. Reserving these names is new normative content established here; it was not previously stated anywhere in the corpus.
- The Claude leg's existing rule — strip the provider's ambient variable family, supply configuration through the explicit settings flag rather than the operator's home — is **unchanged in kind**. The strip is of _inherited ambient_ values; the daemon then sets the reserved credential-home variable as a run-provisioned value. Stripping and provisioning are two stages of one construction, not a contradiction.
- The Codex leg's native environment policy, which inherits nothing and takes an explicit set, carries the reserved variable in that explicit set.
- **On the Claude leg the daemon also names the per-project folder the provider keeps its conversations under, and names it the same in every account's home.** That provider stores a session's conversation file at `<home>/projects/<project folder>/<session id>.jsonl`, and it derives the folder name from the working directory unless told otherwise. Two consequences make naming it load-bearing rather than tidy. First, moving a session between two accounts is a copy of that one file (§Moving a session to another account), and a folder name the daemon computes is a path the daemon can address, where a derived one is a path it would have to search for and could guess wrong on. Second, that folder is also where the provider keeps a project's automatic memory, so a name that varied would split one project's memory across directories. One name per project, the same in every home, set by the daemon at spawn like every other reserved variable.
- The reserved set is **per-provider and asymmetric**, and the asymmetry is a design constraint rather than an inconvenience to abstract away. Codex co-locates account identity and tokens in a single file under one platform-uniform home directory, relocated by one documented variable (`CODEX_HOME`). Claude Code splits the tuple across two stores — account identity in its own configuration file, tokens in a platform-dependent store (an OS keychain on macOS; a credentials file on Linux) — relocated by different variables with different scoping rules (`CLAUDE_CONFIG_DIR`, documented for its credential-file effect on Linux and Windows only, and a separate secure-storage variable that is undocumented). **No symmetric cross-provider abstraction is available**, and a design that assumes one will be correct on at most one provider. Each provider's concrete reserved set is pinned in the provider-wire reference and **re-verified against the pinned binary at implementation time**, per the reference family's regenerate-don't-transcribe and re-verify-at-authoring-time rules ([Provider Wire Reference §Versioning and pinning policy](../reference/provider-wire/README.md#versioning-and-pinning-policy)) — variable names move, and one of the two Claude variables has no vendor documentation to move with it.

- **The daemon sets a reserved variable to an absolute path or does not set it at all.** An empty-string value is not a permitted spelling of "unset". On the Claude leg an empty value is known to behave as unset _and_ to suppress the companion variable, collapsing a home partition that would otherwise have held — a failure that is both fail-open and silent. The daemon therefore never emits an empty reserved variable, and treats an empty value observed in a constructed environment as a construction defect rather than a default.

**Authentication must survive the constructed environment.** A provider process that reaches a home holding no usable credential is not authenticated, however well-formed its environment is. Two known hazards bound the design and are named rather than assumed:

- Provider minimal-startup modes can bypass the credential machinery entirely — the pinned Claude reference records that the minimal mode strips OAuth and keychain access ([Provider Wire Reference §Gaps recorded](../reference/provider-wire/claude.md#gaps-recorded), a **Provisional**-trust, design-census-sourced claim). A driver leg MUST NOT select such a mode for an account-bound spawn, and this constraint is a version floor/ceiling risk to re-check at each pin bump, not a routine flag choice.
- On platforms where provider credentials are held in an OS keychain rather than in the home directory, the keychain entry a provider addresses may be a function of its configured home. Where that holds, per-account homes give per-account keychain entries and isolation is preserved; where it does not, the home is not by itself an isolation boundary on that platform. **The daemon treats the keychain entry as opaque**: it never computes, derives, predicts, or addresses a provider's keychain entry name, and it never asserts partitioning by construction. Isolation on such a platform is established **empirically, by the capability probe** (§Concurrency Posture) observing that two accounts' homes yield independent authentication states — never by reasoning about how an entry name is built. The vendor documentation for the one provider that uses a keychain scopes its home variable's credential effect to the _other_ platforms, so a spec that asserted keychain partitioning would be asserting precisely what its source declines to say; and the entry-naming scheme, where it can be observed at all, is undocumented, version-fragile, and sensitive to inputs outside the daemon's control. Until the probe resolves, the degrade-honestly floor applies.
- **Measured on macOS at the pinned provider build, that keychain entry _is_ a function of the home**: the service name is the default one only for the default configuration home, and otherwise carries a suffix derived from the home the build salts with, so each home's login is its own ([Provider Wire Reference §Environment and update control](../reference/provider-wire/claude.md#environment-and-update-control)). The reading does not move the rule above — the daemon still addresses no entry and still establishes isolation by the probe rather than by construction — but it fixes one thing the daemon must not do: it **never sets the secure-storage variable for an account's home**, because that variable's honoured empty-string value collapses every home onto the default service name, and a home that borrowed another home's login would spend from an account nobody chose.

**Isolation does not make two sessions unreachable to each other.** A session running in one account's credential home is reachable from a session running in another **by its address, not by its name**: the daemon's own directory of its sessions and their addresses is what spans the homes, and it is the daemon — which runs both processes — that looks the address up and delivers the message ([Spec-014 §Sessions Talking To Each Other](014-multi-agent-channels-and-orchestration.md#sessions-talking-to-each-other)). No credential home is shared, mounted into another, or read to do it, and nothing about a message between two sessions touches either one's credential material. The address is the handle rather than the name for the same reason this section exists: each home keeps its own layout, down to the per-project folder a provider files conversations under (above), so a directory keyed on what each home calls things would have to reach inside the homes to build itself — which is the sharing this section forbids. The daemon knows both sessions because it started them, not because it read either home.

### Brokered interactive sign-in

Authorized by [ADR-028](../decisions/028-provider-credential-custody-posture.md) D1, and **not** custody: the daemon supplies a working directory and a process, and learns nothing.

- The daemon MAY **execute the provider's own first-party sign-in flow** for a registered account: it constructs the invocation itself, spawns the provider's binary **unmodified**, and pins that account's credential home through the reserved variables §Credential homes and the constructed environment already defines. Nothing is patched, and no built-in authentication method is removed, disabled, or restricted.
- **The daemon never reads the result.** It does not read, parse, copy, cache, relay, or persist the credential the flow writes. The credential is written by the provider's own tooling into the provider's own store inside that home, exactly as it would be had the operator run the command themselves. The broker has **no read path into the home at all** — this is a property of its shape, not a discipline its callers must observe.
- **What travels to the caller is a typed, validated whitelist — never the provider's raw output.** Exactly four fields may leave the broker: a verification URL, an optional device code, an opaque daemon-minted attempt identifier, and an optional attempt expiry. The daemon **parses** them out of the process stream and emits them as typed members; it never forwards a line of that stream verbatim, and any text it cannot parse into those fields is discarded rather than surfaced. This is what reconciles the broker with §Node provider readiness and the sign-in handoff's rule that provider sign-in output is never surfaced: that rule bars the **stream**, and it is narrowed here only to admit the three parsed fields, because a sign-in stream may also carry OAuth state, PKCE values, and credential fields that must never reach a client. The URL is validated against the provider's own documented verification host before it is emitted, so a compromised or unexpected stream cannot redirect the operator. The expiry is admitted under the same parse-and-validate discipline rather than as an exception to it — parsed to an RFC 3339 instant, required to be in the future and within the provider's documented attempt ceiling, and **omitted rather than surfaced** where it fails either test — and it is carried because an operator handed a device code with no visible bound will type a dead one; it is a bound on the attempt, never a provider state field. A provider arm that emits no parseable verification material cannot be brokered and is refused with a typed refusal naming the provider, rather than spawning a flow the operator cannot complete.
- **The verification material is emitted so the operator can finish the flow by hand.** The address is served as data the operator can read, select and copy, and is served whether or not the daemon also handed it to a browser — a browser that failed to open must not be a dead end, and an operator on a machine with no browser at all must still be able to complete a sign-in. Where the provider supplies a code, it travels with its own remaining life so an operator is not handed a code that has already died; an expired attempt says it expired rather than silently failing.
- **An attempt ends settled, never abandoned.** Every attempt reaches exactly one of completed, cancelled, expired or failed, and the failed arm carries a typed reason the surface can name together with the fact that starting again is the next act. An attempt left in neither a completed nor a failed state would leave an operator watching a flow that will never answer, and the single-attempt-per-account rule would then hold that account's sign-in shut.
- The flow is **cancellable by the attempt identifier**, and cancellation is a first-class outcome rather than an abandonment: a broker that could only be abandoned would leave a provider-side login slot occupied.
- **One brokered attempt per account at a time.** A second start against an account with one in flight is refused (§Fallback Behavior), because at least one pinned provider silently drops the previous attempt when a new one starts.
- Completion is **observed, not asserted**: the daemon learns the outcome from the provider's own completion signal, correlates it on the attempt identifier, and then takes an ordinary health observation (§Credential-home health observation) to establish the account's state. A completion reported as successful is not by itself a reading that the account is authenticated — only an observation is.
- Sign-in is **node-local operator authority**, in the same class as registration: a control-plane-relayed sign-in is denied, never queued.
- The **calling surface is the provider-management surface and its CLI parity verb**, deliberately **not** the first-run flow. [Spec-023 §Provider Authentication (Group B)](023-first-run-onboarding.md#provider-authentication-group-b) hands the operator the vendor's own invocation and re-probes, and this spec does **not** rewire it: that step's instruction to call the corresponding `providerAccount.*` verb excludes `providerAccount.login` and `providerAccount.loginCancel`. Onboarding stays a handoff so that a first run never depends on a brokered process the operator did not ask for.
- The **registry stays un-evented.** Completion reaches interested clients on a read-shaped subscription carrying a wire-only notification, never a durable session event and never an `EventEnvelope`: a node-local operator act on a node-local registry has no session to belong to, and minting a session event type for it would put node administration into a session's audit timeline.

### Non-interactive token registration

Authorized by [ADR-028](../decisions/028-provider-credential-custody-posture.md) D2. This is the one custody claim this spec makes, and it is bounded on its face.

- The `register` verb — **and no other verb, input, flag, configuration key, or environment variable** — MAY accept a provider-minted non-interactive token for the account being registered. The input is **write-only**: it is accepted, never returned, never echoed, never logged, never rendered, and never placed on any reply, event, error, metric, or diagnostic payload.
- Admission requires **all five** of ADR-028's conditions. The daemon does not mint, exchange, refresh, or derive credential material, and **never speaks a provider token endpoint**: a token arrives already minted by the provider's own tooling or it is refused.
- The supplied value is sealed through [ADR-021](../decisions/021-cli-identity-key-storage-custody.md)'s ratified ladder — OS keystore first, verified by write-probe-read-delete rather than assumed; encrypted daemon-owned file second; **loud refusal third, never a silent plaintext write**. Where the ladder refuses, registration refuses: an account is not registered in token mode on a host that cannot seal the token.
- **Availability is not durability, and the ladder's tier-1 probe only proves the first.** At least one platform's keystore binding falls back silently to an in-memory kernel keyring that is lost at reboot and publishes no way to ask which backend answered — so a write-probe-read-delete **passes** against a store that will be empty tomorrow, and the account would present an unexplained re-authentication demand rather than a storage fault. Where durability cannot be established, the daemon says so at registration and the operator chooses, rather than sealing into a store the daemon has not confirmed will still hold the value after a restart.
- **The sealed value is not written into the credential home.** §Non-Goals claims no ownership over the bytes inside a home, and daemon-owned bytes in provider-owned space would be indistinguishable to a later reader — and to the provider's own tooling. It lives in daemon-owned state keyed by `accountId`.
- It reaches the provider **only** as an environment variable, on exactly two invocations: the registration-time observation below, and — **only where ADR-028 condition 5 is met** — the child process of a run bound to that account, injected at the same single construction site that already assembles the child environment and applies the reserved-variable discipline. **Condition 5 is a fail-closed gate checked before anything is sealed, not a caveat:** a run child executes model-directed tools, so any command the model issues can read that child's environment. Until a provider leg is **observed** to strip the variable from the environments of the tool, shell, and subagent subprocesses it spawns, that leg **refuses token-mode registration outright** and the operator is routed to brokered sign-in instead. The refusal lands at registration rather than at run start deliberately: admitting an account whose token could never reach a run child would register something that stores `authenticated`, reports **ready**, and then refuses every run — the exact surface-versus-admission divergence §Node provider readiness and the sign-in handoff exists to prevent. Documentation asserting the strip is not observation. It is never exported to a shell, written to a file the provider does not own, or passed as a command-line argument — an argument vector is readable by any process running as the same user.
- An account registered this way records its **observed** authentication mode on its registry row rather than an assumed one, and the mode is what admits the class. The observation is made by a **registration-time status invocation**, spawned once as part of registration with the supplied token injected into that one child: a non-interactive, single-purpose invocation that runs no model-directed code and so is never itself the reason condition 5 refuses — the leg gate above is settled first, and this invocation runs only on a leg that has already admitted the class. Without it the class could never be admitted at all — the mode gates admission, spawn validation refuses an unobserved account, and the token would otherwise reach a child only on a run that admission has already refused. The registration transaction commits only if that invocation reports an authenticated mode; a mode the daemon has not observed is stored as absent, never as a default, and the registration is refused rather than left pending.
- The re-login horizon for a token-mode account is the provider's own fixed lifetime measured from the token's **issuance** time, which is not the registration time: a token is minted out of band and may be registered days or months later, so anchoring the horizon to registration would shift it forward by the token's pre-registration age and could tell the operator a credential is still good after it has expired. The horizon is therefore computed **only** from an issuance timestamp the daemon can obtain from the provider's own status surface or that the operator supplies explicitly; where neither exists the estimate is **null and rendered as unknown**, never defaulted to the registration time. It is **rendered as an expectation, never as fact** — the value is a property of the provider's issuance policy, which the daemon does not control and cannot verify.
- A **terminal authentication refusal on a token-mode account is not retryable and not refreshable**: the class carries no refresh token by construction, so there is no successor to mint. The account's stored reading moves to `reauth_required` and the remedy the surface names is to mint a fresh token at the provider and re-supply it — never a retry, and never a refresh attempt.
- **Re-supply targets the existing account and preserves its identity.** The register verb carries an optional `accountId`; supplied, it means _replace this account's sealed token_ rather than _create an account_, and the credential-accepting input census is unmoved at exactly one because no second verb, flag, or field is minted. Deregistering and registering again is **not** the remedy: registration daemon-mints a new immutable identity, so that path would discard the account and detach the spend, quota, and attention history keyed to it. A successful replacement bumps `credentialGeneration` — it is a new credential for the same account — re-runs the registration-time observation, and destroys the prior sealed value.
- **The registry row and the sealed value are two durability domains, so the lifecycle is an intent protocol rather than a claim of atomicity.** Requiring both to change in the _same operation_ would not make them atomic: SQLite and the OS keystore (or the encrypted file) commit independently, and a crash between them leaves either a live unreachable credential or a registered account with no token. Registration therefore **seals first, then commits the row**, so a crash strands a sealed value that no row references; removal **marks the row's intent first, then destroys the secret, then deletes the row**, so a crash strands a row already marked unusable. A reconciliation sweep at daemon start destroys every sealed value whose `accountId` matches no row and completes every row left marked for removal, and admission refuses any account whose row is intent-marked. Neither crash window can leave a usable credential the operator cannot see.
- **The fallback tier stores one secret per account, under a layout this spec names.** [ADR-021](../decisions/021-cli-identity-key-storage-custody.md)'s tier-2 fallback is a single ciphertext at one fixed path holding one identity key; it defines no keyed collection, so reusing it unchanged would leave the second token-mode account on a keystore-less host overwriting the first. Token-mode secrets therefore live one file per account, named by the daemon-minted opaque `accountId` under a dedicated token subdirectory, each sealed independently with ADR-021's parameters. Deletion enumerates by that filename, which is what makes the reconciliation sweep above able to find an orphan at all; the identity key's own path and format are untouched.

### Credential-refresh brokering

The pinned Codex surface includes a server request the provider sends **to the daemon** to refresh its authentication tokens (`account/chatgptAuthTokens/refresh`, [Provider Wire Reference §Server-requests](../reference/provider-wire/codex.md#server-requests--the-callback--interactive--approval-surface-codex--daemon)). **The daemon never enters the mode that sends it, and refuses the request.**

- **The request arrives only in the provider's external-authentication mode**, which is entered by an unstable login arm the vendor marks for its own internal use. Under the managed per-account credential home this spec builds on, the provider holds its own login inside that home and the request never arrives at all.
- **Answering it means handing the provider a token, not passing one through.** Its answer carries an access token, an account identifier and a plan type. So an implementation that "brokered" it would have to mint or hold credential material, which is the one thing the bounded-custody posture forbids outright (§Non-Goals, [ADR-028](../decisions/028-provider-credential-custody-posture.md)) — minting or exchanging credential material rather than receiving it already minted is a further ADR, not an implementation detail.
- **The daemon therefore answers with a refusal on every arrival, and entering external-authentication mode is prohibited.** A refusal is the honest answer: the request is asking for something the daemon does not have and must not obtain. A refusal arriving where none should is a defect in how the process was started, not a credential problem, and the refusal names it as such.
- **Nothing about a refusal is a credential-home lifecycle transition**, so it never bumps `credentialGeneration` (§Account identity and credential generation) and never moves an account's stored health reading. What renews a login is the provider's own code running inside its own home (§Credential-home health observation), and that renewal is likewise not a lifecycle transition: it is the provider keeping its own credential current in the place it keeps it, not a credential this product replaced.

### Selection at run start

- Every provider run resolves exactly one account **before spawn**: the account its saved agent definition or its workflow step pins, where one does, otherwise that provider's current account, the one marked default. Pinning is the only way a run's account is anything but the current one; no client supplies an account per run, and no session surface offers one (§Moving a session to another account).
- The resolved account is **stamped on the run and never changes under it**. It is stamped on the run's admission record as a path-independent server stamp (`admittedProviderAccountId`, [Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)) — never client-suppliable — and persisted through the binding's spawn-bound configuration record so that a resume or crash-relaunch re-realizes **the same account**. A resume MUST NOT silently rebind to a different account; where the original account can no longer be realized, the resume refuses fail-closed rather than paying from an account the caller never chose. What the stamp does **not** do is hold a session on an account after the operator has moved the provider's current account: the daemon ends the run at the next tool boundary and continues the work in a new run on the new account (§Moving a session to another account), so every run still carries exactly one account for its whole life and the boundary is one the daemon creates rather than one the operator waits for.
- **A workflow step that runs an agent resolves its account by this same rule, and per step rather than per run.** A step's own binding carries either the provider's default — meaning whichever account is marked default **at the moment the run starts**, resolved then rather than frozen when the workflow was authored — or one specific account chosen from the registry's own list, by the identity each provider reports. There is no separate paying-account control and no second account list: an account means nothing until the provider is known, and two controls setting one value can disagree. Resolution happens at **step launch, inside the daemon**, which is what lets two parallel branches of one run resolve different accounts of one provider and park independently against each one's limits; the resolved account is stamped on the step rather than on the run.
- **A step record stores the reference, never the value.** A step's provider parameter carries the account identifier, a credential parameter carries a reference into the secret store rather than a secret, and every value resolved at launch is redacted from logs and from step payloads before either is written. A workflow definition is a document an operator may export, import and hand to an agent to author, so a definition that could hold a resolved credential would carry it wherever the definition went.
- Account identity is **spawn-bound state**, so it travels the same data-leg path as the rest of the spawn-bound surface and is re-injected from the durable record on resume rather than re-requested from the client.

### Moving a session to another account

Changing which account a provider's work runs on is an act on the provider surface, not an act inside a session. Pressing an account there — or releasing the accounts cycling key on it — makes that account the provider's **current** account, and every running session on that provider that is not pinned to an account moves to it. The session surface reports which account a session is on and offers no switch of its own: one control setting one fact, on the page that owns the fact.

- **An idle session moves at once.** The daemon stops its provider process, copies the provider's own conversation file into the new account's credential home, and reopens the conversation there through **the provider's own resume**, against the same conversation identifier. Nothing of the conversation is re-sent as text. One faint collapsed row lands in the transcript at that point, `Switched to account <name>`, expanding to the account it came from and the time; `<name>` is the account as the Providers page lists it, the address the provider reports with the plan where one address holds two accounts, and nothing shorter, since an account carries no nickname.
- **A busy session moves at its next tool call.** The daemon holds the turn at the boundary the pause mechanism already holds at — after the step already in flight, by the provider's own hooks where it has them and by a boundary interrupt where it does not ([Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior)), interrupts the turn there, waits for the provider's own completion frame, copies the conversation file into the new account's home, resumes it there, and continues the same work in a new run on the new account. While it waits, the working line's state slot reads `switching to account <name>` and nothing longer. Its row expands to `turn continued` as well as the account and the time. The tool that was about to run does not run: the model plans again from a conversation that already holds every earlier step.
- **The boundary is the daemon's to create, and one tool call is the whole wait.** A run still carries one account for its whole life, so no turn is ever charged to two accounts and no provider's session file holds half a turn — but nothing waits for a run to end on its own, which across a long run is indistinguishable from being ignored.
- **Continuity is the provider's own resume across two credential homes, never a replay.** Both pinned providers find and load a conversation file copied into a different, even signed-out, credential home and resume it under the same identifier — measured on both legs at the pinned builds ([Provider Wire Reference §claude](../reference/provider-wire/claude.md), [§codex](../reference/provider-wire/codex.md)). A replay of the conversation as text is the **fallback** where the resume does not load, and it is reported as a restart rather than as a continuation: that row reads `Conversation restarted on account <name>`.
- **The conversation file follows the session, and the stale copy goes.** Each move copies the file forward into the home the session now runs in and removes the copy it came from, so a session moved back to an account it ran on before never resumes the older file.
- **A move never rewrites a credential, and it runs while the account being left is still valid.** Nothing about it touches a token, a keychain entry or a provider's own login: it copies one conversation file between two directories the daemon owns. Because the move is a copy-and-resume rather than a rescue, it is something the operator does while the old account still works.
- **A dead target refuses in place.** Where the account being moved to cannot be realized (§Validation at spawn — fail-closed), the move is refused with the target's own remedy — `account <name> · login expired · Sign in again` — and the session stays on the account it was on.
- **The session's cost keeps counting across the move, and the split lands as two account rows under one running total.** A turn split across two accounts is charged to both: the spend before the move stays under the account it ran on, the spend after it goes under the new one, and the session's receipt sums them into the same total (§State And Data Implications, [Spec-014 §The mutation surface](014-multi-agent-channels-and-orchestration.md#the-mutation-surface)). The accountant **re-baselines on the new process's own counters** at the resume, because a provider's cumulative figure restarts with its process: without a re-baseline the first turn on the new account would either double-count the conversation so far or read as zero. **The provider's own per-process figure never reaches the screen on either leg** — it is an input the accountant baselines against, not a number an operator is shown, and showing it would make a session look as though its spend had reset.
- **Pinned means pinned.** A saved agent definition or a workflow step set to a specific account stays on that account when the provider's current account moves ([Spec-027](027-agent-definitions-and-peer-invocation.md), [Spec-015](015-workflow-authoring-and-execution.md)). New sessions start on the current account.
- **A relaunch applies the same rule.** An unpinned session the daemon brings back after a restart, whose provider's current account is by then another one, moves like any other unpinned session: at once while idle, at its next tool call while busy. Its run re-realizes the account it was admitted against (§Selection at run start) only for the steps up to that boundary.

### Validation at spawn — fail-closed

- Before a provider process is spawned against an account, the daemon MUST validate that the account is registered, that its credential home exists, and that the driver's authentication probe reports `authenticated` for that home.
- Any other outcome **refuses the run before spawn**. A missing or husked home, an unregistered account, and an `indeterminate` probe are all refusals, never fallbacks: falling back to the default account, to the ambient operator configuration, or to an unauthenticated spawn would silently bill the wrong account or start work that cannot complete.
- This reuses the driver contract's existing authentication machinery rather than minting a parallel one. The probe is **required of every driver and is not capability-gated** — that posture is preserved exactly, and this spec adds no authentication capability flag. What it adds is the **scope** of the probe and of the daemon's cached authentication state: both become per-`(driver, account)` rather than per-driver, because a node with two accounts on one provider has two independent authentication states and a single per-driver record cannot represent them.

### Billing mode

- Every account records a **billing mode**: `subscription` (usage is included in a plan the operator already pays for), `metered` (usage accrues billed charges per token), or `unknown`.
- Billing mode is operator-declared at registration and may be corrected later; the daemon does not infer it from spend and does not fetch it from a vendor.
- **Every surfaced cost figure attributable to an account carries that account's billing mode.** Subscription-mode usage MUST NOT be presented as billed dollars without the label, and MUST NOT be silently summed with metered spend into a single unlabeled currency total. A total spanning more than one mode states that it does.
- **`unknown` is the honest-absence arm and is never resolved by guessing.** It means the operator has not declared how this account bills — not that the account is metered, and not that the figure is zero. A figure attributable to an `unknown`-mode account is labeled as undeclared and is subject to the same prohibition as a subscription figure: it is never presented as billed dollars, and never folded unlabeled into a currency total. The remedy is for the operator to correct the mode on the registration, which is why the mode is editable after registration rather than fixed at it.

  This rule is not a stylistic preference; it is the posture the provider itself publishes about its own figure. Anthropic's cost documentation states that the CLI's session cost block "is intended for API users", that subscribers "have usage included in their subscription, so the session cost figure isn't relevant for billing purposes", and — on the provenance of the number — that the figure is computed locally "from token counts priced at standard list rates", does not reflect promotional or contracted pricing, and "may differ from your actual bill" ([Claude Code costs](https://code.claude.com/docs/en/costs), accessed 2026-08-18; **Documented**). A locally-derived, list-rate figure presented as a subscriber's bill is wrong in the way the vendor explicitly warns about, and this spec's labeling requirement is what keeps that presentation from occurring. The same provenance caveat is why a cost figure is a **spend estimate for this node's usage**, never a statement about an operator's invoice, on either billing mode.

- **A figure that spans more than one billing mode says so.** Where a surface totals spend across an operator's accounts, that total states that it spans more than one mode rather than presenting one currency figure over accounts that do not bill alike. Per account the figure is carried with that account's own mode; across accounts the reading is the modes it covers, not an average of them. This is the positive half of the prohibition above: the rule bars an unlabeled sum, and this says what a labeled one looks like.
- Billing mode is **presentation and labeling only**. It is never an input to budget enforcement: the committed-spend fold ([Spec-014 §Cost Figure Display Consistency](014-multi-agent-channels-and-orchestration.md#cost-figure-display-consistency)) enforces the same ceiling arithmetic regardless of mode, for the same reason enforcement must not branch on cost provenance — one ceiling, no dual trust regimes.

### Provider quota is account-scoped

- A provider quota snapshot describes **an account's** standing with its provider, not a session's and not the node's. It spans every session that account's runs touch.
- The account-scoped quota event therefore **carries the account it describes** (`providerAccountId`, plus the credential generation observed with it). Before this spec the event was documented as account-scoped while carrying no account identifier, which left every consumer unable to attribute a snapshot to an account on a multi-account node; that gap is closed here.
- **An account's numbers live on the account surface and nowhere else, and no second usage screen is added beside it.** An account's quota standing and its spend are properties of the account, so the surface that lists accounts is where they are read. No session-scoped surface carries an account's quota windows or an account-wide spend figure: what a session shows is its own context reading and the spend attributable to its own work, which are different facts about a different subject, and putting an account's standing on a session surface would invite a reader to act on one session's figure as though it bounded the account. Spend and tokens **by day and by model** are drawn on the account surface, per account and summed across a provider's accounts, because the durable per-turn usage table those slices are group-bys over is what the accountant keeps (§State And Data Implications).
- The typed provider-limit signal the drivers normalize refusals into ([Spec-004 §Fallback Behavior](004-provider-driver-contract-and-capabilities.md#fallback-behavior)) is likewise account-scoped, and its consumers key on `(accountId, credentialGeneration)`.

### Credential-home health observation

The registry's stored reading is only as useful as it is fresh. A pull-on-read model — written by the deliberate probe verb and by spawn validation alone — would leave a node whose operator never probed and never ran serving a reading taken once and never revisited, and would leave an account nobody has used for weeks quietly signed out. A background observer therefore keeps every registered account's reading and its login current, and this subsection states precisely what it may and may not do.

- The observer is **homed in this spec's own plane**, not in [Spec-004](004-provider-driver-contract-and-capabilities.md)'s capability-refresh cadence. The two are different subjects — that one refreshes a driver's declared capabilities, this one observes an account's credential state — and CP-026-1 already places the per-`(driver, account)` scoping of cached authentication state on the driver-contract side. Nothing in Spec-004's contract is widened here.
- It runs **per registered account** on a fixed cadence, **default-on**, with a durable **per-account opt-out** so an operator can silence an account they are not using without deregistering it. The schedule is durable rather than an in-memory timer, so a daemon restart does not silently stop observing.
- **The observer reads with the provider's own code, inside the account's own home, and never touches a token itself.** The prohibition on calling a path documented to refresh proactively is **scoped to a shared home** and does not reach a per-account home. Its whole reason was a race between the daemon and the operator's own CLI holding one grant, and that race cannot occur in a directory the operator's CLI never opens: an account's home is daemon-owned, addressed by the reserved variable, and is never `~/.claude` or `~/.codex` (§Credential homes and the constructed environment). What stays absolutely prohibited is unchanged and is the real constraint: the daemon MUST NOT read, write, copy or transport credential material, MUST NOT speak a provider's token endpoint itself, and MUST NOT enter the Codex external-authentication mode (§Credential-refresh brokering). Renewal is the provider's own code running inside its own home, caused by asking that home a question it answers with a signed call.
- **What it reads is each provider's own limits surface, and neither read costs a model turn.** On the Codex leg the account-scoped rate-limit read (`account/rateLimits/read` with `excludeResetCreditDetails: true`, the flag the vendor's own comment scopes to background usage polls) returns every limit bucket for that account. On the Claude leg the `get_usage` control request answers in a short-lived headless process started in that home, **before any turn is sent**, and returns the short window, the weekly window and the weekly window per model. Both are measured on the pinned builds to answer with no model call and no spend ([Provider Wire Reference §claude](../reference/provider-wire/claude.md), [§codex](../reference/provider-wire/codex.md)).
- **On the Codex leg the read renews the login as a side effect, and that is the intent rather than a cost.** The read's own handler resolves the account's authentication first, and that resolution is where the provider applies its own renewal rule — within minutes of the short token's expiry, or when its last renewal is older than its own multi-day threshold. So one call both returns the limits and keeps the login alive, and an account nobody has used for weeks is still signed in. The rotation it spends is the provider's own, taken by the provider, inside the provider's own home, under the provider's own guard: before renewing it re-reads its file under its lock and skips when another process already renewed (§Concurrency Posture).
- **The cadence follows what each leg needs.** Claude every six hours per account; Codex every two days per account; and every five minutes per account while the operator is looking at the provider surface, which the daemon knows from the registry subscription being held rather than from any new signal. Single-flight per account, and **never while a turn is live on that account** — the exclusion §Credential-home health observation already carries, now load-bearing because the read reaches the provider rather than the filesystem. The cadence is **for accounts nobody is using**, which is why the live-turn exclusion costs no freshness.
- **A turn on any session refreshes that account's limits at once, without waiting for the cadence.** On the Codex leg the provider pushes its own rolling update with the turn (`account/rateLimits/updated`, the push half of the same surface the pull reads), so the daemon has only to record what arrives. On the Claude leg the daemon asks the live process itself for the same turn-free read at the **turn's end**, rather than starting a second process beside it: the process is already there, already signed in on that home, and already past the point where another call could disturb a turn. An account being worked on is therefore current at the end of every turn, and the cadence carries only the accounts nothing is running on.
- **An account whose freshness is switched off is read on neither cadence, and the deliberate probe still reads it.** The per-account opt-out stops every automatic read of that account — the background cadence and the while-the-surface-is-open cadence alike — without signing it out; the probe verb is the operator asking, and it always answers.
- **The local, no-network read stays, for the state a limits read does not report.** `claude auth status --json` on the Claude leg and the account read with refresh suppressed on the Codex leg both perform no network call and renew nothing; they are what reports which authentication mode a home is in, and what answers at all when the machine is offline. The two reads are different instruments for different facts and neither stands in for the other.
- **A renewal the provider performs inside its own home is not a credential-home lifecycle transition.** It does not bump `credentialGeneration` (§Account identity and credential generation). A generation bump ends an account's attention epoch and marks every quota reading before it as predating a change, and a routine two-day renewal changed nothing an operator or a consumer needs told about — bumping on it would end parked work's epoch ([Spec-015 §Provider-limit pacing and durable resumption (SA-40)](015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-40)) and stale every stored window, twice a week, for nothing. What it does move is the row's **last observed credential-refresh time**, which is the field this observation finally has a writer for.
- **The moment a window resets, the daemon spends one smallest turn on that account so the new window's clock starts then.** A provider counts a window from the first message in it, so while nobody is working the clock stands still and the reset an operator is waiting for arrives later than it had to. At each window's reset the daemon sends one short line to the smallest model in that provider's own catalog — `haiku` on the Claude leg — in a **throwaway process in that account's own credential home, outside every session**, and keeps nothing of it. It runs for **every window the account reports**, the short one and the weekly ones alike, on both legs. It is **on by default and switched off per account under the same freshness opt-out**, and never runs while that opt-out is off.
- **The limits read starts no window; the window start spends exactly one turn per window.** The two are deliberately different acts: the read is the one that must cost nothing, and this is the one that must cost something, because a window that has not been spent in has not begun. That turn lands in the per-turn usage table like any other, under the account that paid for it and with no session to attribute it to (§State And Data Implications), and it is drawn only where every turn is drawn — in that account's tokens for the day and the week, and in its spend where the provider reports a cost — never as a row of its own. Nothing announces the start: the limit row carries the new window's reset time at the next read.
- **A read that cannot be taken changes no reading and says so.** Where the machine is offline or the provider does not answer, the account keeps its last reading with the time it was taken and adds `could not read · 7:24 PM` beside it. No bar moves, no window is dropped, and nothing reads as zero used — an empty meter is a claim about an allowance the daemon did not observe.
- **The honest residual, stated rather than papered over.** The limits read establishes that the account's credential was accepted by the provider at the moment of the read, which is more than a local read establishes and still not a standing guarantee. A credential revoked between two reads reads as authenticated until the next read, a run, or a deliberate probe finds otherwise, and the surface carries **when the reading was taken** rather than presenting it as now (§Per-limit provider quota). What the read cannot do on the Claude leg is extend the login's own horizon: the vendor documents that only an interactive sign-in renews that, and its own status read carries no expiry field. So a Claude account asks to be signed in again at its horizon whatever the observer does, and the design's job is that the operator hears it from the provider surface with a one-press sign-in beside it — `Login expired · Sign in again`, from the structured authentication failure the read returns — and never from a session that died.
- The observer is a **third writer of the stored pair** — joining the deliberate probe verb and spawn validation — under the same rule §Validation at spawn and the contract registry already state: the row records observations, and every validation that actually observes an account's authentication state writes it back. **The generation-bump authority is not widened.** `credentialGeneration` still bumps only on the credential-home lifecycle transitions §Account identity and credential generation names, so a background observation is never by itself a lifecycle transition. This matters concretely: [Spec-015 §Provider-limit pacing and durable resumption (SA-40)](015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-40) keys parked work on `(accountId, credentialGeneration)`, and a transient observation failure that bumped the generation would end a parked-work attention epoch for nothing.
- Observation is **excluded against the account's own live work** and is single-flight per account: at most one observation per account at a time, and none while that account's credential home is being reset or a brokered sign-in is in flight against it.

### Per-limit provider quota

- An account's quota standing is **not one window**. The pinned Claude surface publishes several distinct limits at one time, **more than one of them over the same window length** ([Provider Wire Reference §claude](../reference/provider-wire/claude.md)), so a key of `(account, window length)` cannot hold them: one would overwrite another, and which survived would depend on arrival order.
- Quota readings are therefore keyed by **`(account, limit identifier)`**, with the window length carried as a property of the reading rather than as part of its key. A reading that names no limit identifier is the provider's single unnamed limit and takes the reserved identifier `default`, so a provider publishing one window needs no special case and the single-window shape is valid as the degenerate case.
- **Each leg's identifier is read from the carrier the provider actually populates.** On the Claude leg the windows come from the `get_usage` reply's `limits[]` list: each entry carries its own kind and, where it is scoped to a model, that model's **display name**, and the identifier is those two together — the per-model weekly window for one model is a different limit from the per-model weekly window for another, and from the account-wide weekly window over the same length. The flat per-model keys beside that list (`seven_day_opus`, `seven_day_sonnet`) **answer null and are not read**; a design keyed on them would render an empty per-model window for an account with real per-model usage. On the Codex leg the windows come from the reply's `rateLimitsByLimitId` map, whose keys are the provider's own metered limit identifiers.
- **A window is classified by its length in minutes, never by its position in the reply.** Each Codex limit identifier carries a primary and a secondary window, and the provider has moved a given window between those two positions; a reader that called the primary slot "the short window" would relabel every bar the day that moved. The reading carries the length the provider reported and the surface names the window from it. This is not in tension with the key above: the **key** is the limit identifier, and the **label** is read from the length — keying on the length is what collapses two limits into one, and reading a position as a meaning is what mislabels one.
- **Every reading carries when it was taken, and the surface shows it.** A percentage with no read time invites an operator to plan against a number that may be hours old, and on an idle account it will be. The read time stands in words beside the reading — `read 7:24 PM` — on every window; an account with no reading yet reads `not read yet` with no bar at all; and a reading the daemon could not refresh keeps its figure with `could not read · 7:24 PM` beside it (§Credential-home health observation).
- **A whole-account read marks itself complete, so a sparse push never prunes what it does not mention.** The deliberate probe and the observer's limits read both return every window the account has, and a reading set marked complete replaces the account's stored set. The providers' pushed updates are explicitly **sparse** — they carry the windows that moved and no others — so a pushed set is merged into the stored one and never treated as the whole truth. Without the distinction one sparse push would delete every window it happened not to name.
- The newest reading per key is held durably per account, and **the registry read is what delivers it**: `providerAccount.list` returns the stored windows alongside the accounts, so a client that connects after a reading was taken — or after a daemon restart — renders quota standing immediately instead of waiting for the next probe or run to produce one. The subscription remains a live tail and is deliberately not a snapshot replay; the read is the snapshot. Durability is what makes an account's quota visible on a node that has not run anything since restart. **A stored reading keeps the provenance it was observed under**: because the durable row is fed by both sanctioned sources, a window served from the registry may carry `source: 'run'` just as legitimately as `source: 'probe'`. Provenance is a property of the reading, not of the transport that delivers it, so a consumer must accept both values on a stored snapshot and must not infer provenance from the fact that a reading arrived on a read rather than on an event.
- **Newest wins, by observation time — except that a same-window reading never moves backward.** Where two readings key alike, the one with the later observation timestamp is current, and the source of the reading breaks ties only when the timestamps are equal. **The one exception is the same-window high-water guard**, which is the existing consumer rule and is retained here rather than contradicted: when the incoming reading matches the stored one on both `limitId` and `resetsAt`, a **lower** `usedPercent` is dropped, because usage rises monotonically inside one window. Without the guard a single erroneous or out-of-order low reading would overwrite the durable row and present a 90%-consumed account to a reconnecting client as 20%-consumed — the durability of one row per key is exactly what makes the unguarded overwrite destructive. Ordering by anything else — arrival, or a preference for one source — would let a stale reading mask real consumption.
- **A credential-home rebuild neither clears nor invalidates a reading, and deregistering the account takes every reading with it.** The two dispositions differ because the two facts differ: a quota window describes the **provider-side allowance**, which keeps running while a home sits empty and which the operator re-authenticates back into, so discarding the readings would destroy the pacing evidence the rebuild's own remedy depends on — whereas a reading has no meaning at all without the account it was read for. Each reading therefore records the credential generation it was observed under, exactly as the account-scoped quota event already carries one, and a reading whose generation is behind the account's current generation is rendered **stale rather than current**. This is the boundary between the two stored observations: a generation bump **invalidates** the stored health reading, which describes the home, and merely **ages** a quota reading, which does not.
- **A reading is delivered as three facts, and each is readable without a meter.** Every window carries the provider's own label for that limit, the share of it used, and when it resets. A surface may draw a meter, but nothing about a quota is legible only from a meter's length: the share and the reset time stand in words beside it, because a bar has no accessible reading of its own and a figure a reader cannot state is a figure they cannot act on.
- **A window that has reset reads as reset, not as its old figure.** The newest reading after a reset is the reset one, and a surface shows it as reset rather than holding the pre-reset share until something else moves. Together with the newest-wins rule above this closes both directions: a stale high reading never survives a reset, and a reset reading never loses to the older high one.
- **A reading taken before the account's credential generation changed is presented as predating it.** The reading itself survives the change — a provider-side allowance is not reset by a local credential rebuild, as the disposition rule below states — but it was observed under a generation that is over, so it is carried with that fact rather than as a current reading. A surface that showed it as current would invite an operator to plan against an allowance nothing has re-observed.
- **An account whose quota could not be read says so, and shows no meter.** An unreadable reading is not zero used: an empty meter is a claim about the allowance, and a surface that drew one would report a full allowance the daemon never observed. The absence is stated in words in the meter's place.
- Quota readings reach the registry from **two sanctioned sources and no others**: the account-scoped quota event carrying what a provider pushed during real traffic, and the deliberate limits read. The background health observer performs **that same limits read on its cadence** rather than a third kind of read (§Credential-home health observation), so it adds a caller and not a provenance: a reading it took is recorded under the same provenance an operator's own press produces. The two sources differ in completeness as well as in provenance, which is what the complete-set rule above turns on: a limits read describes an account's whole standing, and a pushed frame describes the windows that moved.

### Node provider readiness and the sign-in handoff

Readiness answers, ahead of any run, the question run admission will ask: **would a provider run for this provider be admitted on this node right now?** It exists because a node on which nobody has authenticated is otherwise indistinguishable from a healthy one until the first run refuses — the failure this spec's own first-run gap named.

- **Readiness is a derivation of the registry, never a second source of truth.** Per provider it is computed by the same resolution §Selection at run start and §Validation at spawn perform — resolve that provider's default account, then read that account's **stored health state** — and it is reported in the same vocabulary: two registry-shape arms mirroring the two resolution refusals (no account registered; accounts registered with no default), otherwise the resolved account's stored health state **verbatim**. The arm count is therefore not a design choice but a consequence: the health vocabulary's arms plus those two, and it widens only when one of them does. No other surface recomputes it. Two derivations of one predicate eventually disagree, and the one the operator is looking at is the one enforcing nothing.
- **Readiness is served from the stored observation, not from a fresh one.** What the registry row holds is the **stored outcome of the last validation** — the authentication probe's reading together with the credential-home observation taken at that same moment, which is exactly what the account's health state names. That distinction is load-bearing rather than pedantic: a missing-home reading is not something an authentication probe returns, so calling the stored value "the last probe result" would imply a live filesystem check at read time. There is none. Readiness reads the row, reports **when** that observation was taken, and performs no process spawn, no filesystem test, and no credential read of its own — so a surface may poll it. **Every validation that observes an account's authentication state writes the pair back**, and that set is exactly **four**: the deliberate per-account probe verb, the fail-closed validation §Validation at spawn performs, the **registration-time status invocation** §Non-interactive token registration performs (on first registration and again on re-supply), and the background health observer §Credential-home health observation homes. Nothing else writes it, and none of the four is optional — a stored value that recorded only _explicit probes_ would leave a node whose first run succeeded serving `indeterminate` forever while every run started fine, which is the same lie in the opposite direction from the one this section exists to prevent. The probe verb and the spawn validation apply §Account identity and credential generation's boundary rule in the same transaction as the health write, so a repaired or destroyed credential ends its attention epoch exactly when the observation that establishes it is recorded. The registration-time invocation establishes an account's **first** reading rather than crossing a boundary — at first registration the row is born at generation 1, and on re-supply the replacement has already bumped — so it writes the pair with no bump of its own. The observer deliberately does not either: it writes the reading and never bumps the generation, because ending a parked-work attention epoch on a transient fault is the harm that rule exists to produce only when a home genuinely changed. Readiness itself never writes: it is a reader of what those three wrote. The **read path applies no age test and has no `stale` arm**: the staleness ceiling in §Implementation Notes binds the probe caller's refresh obligation, not the reader, and the observation timestamp travels on the reply precisely so a caller may apply its own. Adding a read-path age test would be a second predicate — the thing this section exists to prevent — and would make a surface's rendering depend on when it happened to look.
- **Readiness authorizes nothing.** It is advisory. A ready reading is a statement about the last observation, not a grant; §Validation at spawn re-validates unconditionally and refuses on its own reading, whatever readiness last reported.
- **No surface reports a provider as authenticated on any reading other than the authenticated arm.** An `indeterminate` probe is not authenticated — and is not a sign-in failure either: it means the probe could not decide, and it is rendered as undetermined. The same rule bars manufacturing an authenticated claim out of a plan label, a subscription echo, a declared billing mode, or the existence of a home directory: none of those is evidence of a usable credential, and treating one as evidence produces a surface that tells the operator everything is fine while admission refuses.
- **Detection is credential-free and never authenticates.** Deriving readiness reads registry rows and the driver contract's existing zero-turn authentication probe. It never opens, parses, copies, or transmits credential material; it never computes a keychain entry name; and it never runs a provider sign-in command. The daemon does not sign an operator in as a side effect of looking.
- **The handoff discloses the remedy and stops.** On any non-authenticated arm the surface names what the operator must do. That is **several different actions, not one**, and the surface names the one that applies and no other: with nothing registered, register; with accounts registered and none default, choose a default — the daemon lists the candidates and refuses to elect one, because electing one would bind a run's spend to an account the operator never chose; with an account resolved whose credential home holds no credential at all, sign in against **that account's own home** to put one back in it; with an account resolved whose credential has stopped being accepted and whose **observed authentication mode is interactive**, the provider's own first-party sign-in against that account's home; and with one whose observed mode is the **non-interactive token** class, mint a fresh token at the provider and supply it, because such an account **cannot refresh itself** — so its remedy is never a retry and never a refresh, and the interactive remedy is never drawn on it. **The remedy is chosen by the account's observed mode, never offered as a menu**: an operator shown both remedies would try the one that cannot work. Only an arm that has resolved an account names a home, because only such an arm has one. The surface then hands the operator into that flow. Guidance naming a command or a filesystem location travels **in operator-facing message text only: never in an event payload, never in a relayed payload, and never in a log line**, the disclosure discipline `mcp.oauth_unsupported` and `mcp.config_scope_unsupported` already establish in [Error Contracts](../architecture/contracts/error-contracts.md). The client **displays** the invocation; it never executes it on the operator's behalf.
- **A refusal names the fault; readiness names the remedy.** A run refused on the account plane carries its typed refusal code and nothing more — the remedy is deliberately **not** copied onto the refusal, because a refusal envelope travels wherever errors travel and the disclosure rule below bars a credential home from every one of those places. A client that wants to offer the remedy after a refusal therefore **routes on the typed code and then reads readiness** for the provider concerned, on the same node-local, node-operator-authorized surface that composes it. This is not an extra hop grudgingly accepted: the refusal is a fact about one dispatch, readiness is the node's current state, and reading the second is what makes the offered remedy current rather than a snapshot of the moment something failed. Where the refused run was pinned to an account by its saved agent definition or its workflow step, the remedy the operator needs concerns **that** account, which the provider-default projection may not describe — the default may be perfectly healthy while the pinned account is the one signed out, and handing the operator a remedy for an account that is not broken is worse than handing them none. The readiness read is therefore **account-scopable**: a caller may pin the derivation to one named account instead of the provider's default, and the post-refusal path pins it to the account the refusal names whenever it names one. Pinning to an account that no longer exists refuses on the already-registered unknown-account code rather than falling back to the default, since a silent fallback is how the wrong-account remedy would come back.
- **The remedy travels on the readiness entry that obliges it, and nowhere else.** A surface required to display the remedy must be able to obtain it, and the only surface that can compose it correctly is the daemon: it alone knows which account resolution reached and which home that account holds. So the remedy rides the readiness entry — **schema-optional, producer-obligated**, on the [Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) `resendDisposition` precedent: the schema parses it optional, and the daemon's tested obligation is to populate it on every non-authenticated arm and omit it on the authenticated one. It is deliberately **not** a second RPC: a client that had to make one would render a state and a remedy fetched at two different moments, and the pair could disagree. Two consequences follow and are binding. First, the remedy is **derived at composition time and never stored**: no column holds it, so it cannot go stale against the row it describes. Second, the message-text-only rule above is what governs it — the remedy is operator-facing message text that happens to travel structured, so the same prohibition applies unchanged: it does not reach an event payload, a relayed payload, or a log line, and no refusal or telemetry surface echoes it. A registry read is node-local and node-operator-authorized, so disclosing a daemon-owned path to that caller crosses no boundary the credential home does not already cross.
- **No surface offers a credential refresh, and a refresh is visible only as a time moving.** A refresh the provider itself asks for is brokered by the daemon (§Credential-refresh brokering), which passes it through and stores nothing; the only trace it leaves on a surface is the account's last-observed-refresh time moving. A refresh control would offer an act the operator cannot usefully take — the daemon does not mint, exchange or derive credential material — and on a token account it would offer one that cannot exist at all.
- **Provider sign-in output is never surfaced.** Whatever a provider's sign-in process emits may carry OAuth state, PKCE values, or credential fields. It is not placed in an error payload, an event, or a log. A refusal reports that sign-in did not complete — not what the provider printed.
- **An honest limit, stated rather than papered over.** A credential-free probe reports what the provider CLI says about itself, and a signed-out first-party CLI can report a shape indistinguishable from a healthy account whose stored credential has since been destroyed. Readiness therefore **cannot promise a usable credential**: the authenticated arm is necessary, not sufficient. The compensating controls are the ones already specified — fail-closed validation at spawn (§Validation at spawn — fail-closed) and the per-account re-authentication remedy (§Fallback Behavior) — not a stronger predicate. Readiness must not be strengthened by reading credential bytes to break the tie: the bounded-custody posture (§Non-Goals) is not tradeable for a better banner — bounded custody admits one named input, not a credential read on this path.
- **A path is a hint, never a state.** Where a surface mentions an ambient operator configuration directory it does so from path existence alone, labels it a hint, and never renders it as an authentication state — on platforms where provider credentials live in an OS keychain the path carries no signal at all. Ambient configuration is never inherited, copied, or adopted as an account's home (§Credential homes and the constructed environment).

### Vendor authentication-policy constraints

The handoff above is a handoff, and not a login form, for reasons the vendor publishes. They are recorded here as normative constraints at **Documented** trust grade against the vendor's own policy page, so that a later contributor meets them as design constraints rather than re-opening them as UX preferences:

- **The provider binary runs unmodified.** The policy states that "The Claude Code binary must not be modified". The daemon spawns the vendor CLI as shipped, and patches nothing.
- **No built-in authentication method is removed, disabled, or restricted.** The policy states that customers "may not remove, disable, or restrict any authentication method built into it". A readiness surface therefore does not steer the operator toward one authentication method, and billing mode stays a label (§Billing mode) rather than becoming a gate on registration.
- **No credential custody or intermediation.** The policy states that developers "may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow". This is the rule that fixes the shape of the first-run surface: it offers registration and hands off, and **no field anywhere in the first-run flow accepts a provider token** — a statement [Spec-023 §Provider Authentication (Group B)](023-first-run-onboarding.md#provider-authentication-group-b) makes about that flow and which this amendment deliberately leaves true by excluding token supply from onboarding entirely. On this plane's wire the statement is now bounded rather than absolute (amended 2026-08-26): **exactly one input accepts credential material** — the `register` verb's write-only non-interactive-token member — and it is admitted only under [ADR-028](../decisions/028-provider-credential-custody-posture.md)'s four conjunctive conditions. Reversing the posture required an ADR rather than an amendment, and ADR-028 is that record; §ADR Triggers now names what still requires a further one. The clause's other half is satisfied structurally by the brokered leg: sign-in **does** complete through the vendor's own flow, in the vendor's unmodified binary, because that is literally what the daemon spawns.
- **Each operator authenticates with their own credential.** The policy requires that "Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential", billed to that end user. This **restates** the node-local posture already specified rather than adding a new prohibition: accounts and their credential homes are node-local (§Non-Goals, §State And Data Implications), so an account is the credential of the operator whose node holds it, and no shared or pooled provider credential exists that could be handed to anyone else.

## Default Behavior

- With exactly one account registered for a provider, that account is the default.
- A run pays from the account its saved agent definition or its workflow step pins, and from the provider's current account where neither pins one.
- Billing mode defaults to `unknown`, and `unknown` is displayed as `unknown` rather than assumed to be either mode.
- A newly registered account's credential generation is 1.
- Account selection is not a session-visible act: the default path emits no approval and no prompt.

## Fallback Behavior

- **No account registered for the provider.** Run admission refuses with a typed refusal naming the provider. V1 does not fall back to ambient operator credentials — an ambient fallback would make the paying account unknowable and would defeat the receipt.
- **Accounts registered, none marked current.** Refuse. Choosing arbitrarily would bill an account the operator did not choose, and the set is not orderable in a way the operator would recognize as a choice.
- **Selected account's home missing or husked.** Refuse fail-closed (§Validation at spawn). The operator's remedy is re-authentication against that home; the operator procedure is [Provider Failure Runbook §Provider Re-Authentication (Per Account)](../operations/provider-failure-runbook.md#provider-re-authentication-per-account).
- **Concurrent cross-account execution unavailable at the pinned binaries.** Serialize per provider account (§Concurrency Posture) rather than degrading to a shared home. A shared home is not a permitted fallback under any condition: it is the corruption case the isolation exists to prevent.
- **The operator cannot complete a sign-in where they are** (amended 2026-08-26 under [ADR-028](../decisions/028-provider-credential-custody-posture.md); the prior text terminated in a refusal, which left this state with no path to a working node). A headless or no-TTY environment, or a host with no reachable browser, cannot complete an in-place browser sign-in. The surface degrades in a stated order rather than refusing outright. **First**, where the provider publishes a device-code arm, the brokered sign-in returns the verification URL and user code and the operator completes the flow on any other device — no credential reaches the daemon, and this is the preferred arm on every provider that offers it. **Second**, where the provider publishes no device-code arm, the surface offers the non-interactive token path (§Non-interactive token registration) under ADR-028's D2 conditions. **Third**, where neither is available, the surface refuses to prompt, states which provider is not ready, and prints the out-of-band remedy — the account's credential home and the provider's own first-party sign-in invocation — for the operator to run where a browser exists. It still does **not** offer a general environment-variable credential override: an unbounded override accepts refresh tokens, session cookies, and interactively-minted credentials indistinguishably from the bounded class, which is the intermediation §Vendor authentication-policy constraints bars and which [ADR-028 §Alternatives, Option D](../decisions/028-provider-credential-custody-posture.md#option-d-general-environment-variable-credential-override-rejected) rejects on that ground.
- **A brokered sign-in is already in flight for this account.** Refuse the second start with a typed refusal naming the in-flight attempt, rather than starting it. At least one pinned provider holds exactly one active login slot and **silently drops the previous attempt** when a new one starts ([Provider Wire Reference §codex](../reference/provider-wire/codex.md)), so a permissive second start would strand an operator who is mid-flow on another device with no signal that their code had stopped working.
- **The health observer cannot decide.** Where the observation cannot be taken — the home is unreadable, the provider's own status surface answers nothing usable, or the observation times out — the stored reading is `indeterminate` and is **never** collapsed into `reauth_required`. The two have different remedies: `indeterminate` means look again, `reauth_required` means the operator must sign in. Conflating them nags an operator through a full sign-in over a transient fault, and §Validation at spawn already refuses on `indeterminate`, so nothing is gained by the collapse.
- **Provider reports a usage limit.** The run parks on the typed signal rather than consuming a retry ladder, per [Spec-015 §Provider-limit pacing and durable resumption (SA-40)](015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-40); the operator procedure is [Provider Failure Runbook §Provider Usage-Limit Outage](../operations/provider-failure-runbook.md#provider-usage-limit-outage).

## Concurrency Posture

Running two accounts of one provider **at the same time** is the design intent, and the mechanism that would make it work already exists in the corpus: one provider process per session, each on one account and each carrying one account for the lifetime of every run it serves ([ADR-033](../decisions/033-one-claude-process-per-session-one-codex-service-per-account.md)), and per-account isolated credential homes so those processes never share a credential file or a lock. Nothing in this spec's own machinery prevents it.

**Two processes of ours on one account's home tolerate each other, and the reason is the provider's own guard rather than anything of ours.** Two sessions on one account are two processes (ADR-033), so each provider has to tolerate its own neighbour inside one home, and the daemon's own reads add a third caller on the observer's cadence. On the Codex leg the provider re-reads its credential file under its own refresh lock **before** renewing and skips its renewal when another process got there first, which is what makes a second process on one home safe rather than merely likely to work. On the Claude leg the vendor documents that a token another session expired or rotated is refreshed and the request retried once. The daemon's own reads are single-flight per account on top of that, and never taken while a turn is live on the account (§Credential-home health observation), so the neighbours are two provider processes and not three. **The residual is narrow and named:** two processes renewing in the same instant, which the Codex guard cannot exclude because it is a re-read and not a mutual exclusion across processes. Where it happens the account's row reads `Login expired · Sign in again`, the registration and every stored reading stay, and the remedy is one press.

It is nevertheless a **hypothesis about the provider binaries, not a verified property of them**, and this spec declines to assert it as fact. The corpus's parity triad governs the gap:

- **Normalize — the normative contract.** Account selection at run start, one account per run, and per-account isolated homes are normative and unconditional. They hold whether or not concurrent cross-account execution is available, and no consumer of account identity depends on concurrency.
- **Verify — a named obligation, not an assumption.** [Plan-026 §Phase 3 — Credential homes and spawn binding](../plans/026-provider-accounts-and-credential-homes.md#phase-3--credential-homes-and-spawn-binding) carries a capability-probe task that establishes, against the pinned provider binaries, whether two accounts of one provider can execute concurrently with isolated homes without credential-file corruption, keychain collision, or single-flight refusal at the provider. It now **confirms** what both vendors document about keychain partitioning and what the Codex source shows about its refresh guard, rather than discovering either — but it stays an obligation, because a documented property and an observed one are not the same evidence and the entry name is not the daemon's to compute. Its outcome is recorded on the driver's declared capability surface, so the daemon reads a probed fact rather than a documented hope.
- **Degrade honestly — the floor.** Where the probe does not establish concurrency, the daemon **serializes per provider account**: runs bound to the same account queue behind one another, and runs bound to different accounts of the same provider serialize as well until the probe lifts them. Serialization is visible in run state rather than presented as slowness, and it is never relaxed by sharing a home.

Three engineering constraints are recorded as the reasons this is a probe rather than a deduction, each carried at its honest trust grade and attributed to the vendor that actually states it:

- **Credential-file refresh races — one vendor states the rule, the other is silent, and this spec does not launder the difference.** Codex publishes an imperative prohibition on sharing a credential file across concurrent execution and directs one file per runner or per serialized stream, and documents that a successful refresh writes new tokens back to that file, so a stale copy is superseded ([OpenAI Codex CI/CD authentication](https://learn.chatgpt.com/docs/auth/ci-cd-auth), accessed 2026-08-18; **Documented**). That is a citable, vendor-stated constraint and it is the direct basis for per-account isolation on the Codex leg. **Anthropic publishes no equivalent statement** — no rotation, locking, or concurrency rule appears in the Claude Code authentication or environment-variable references. The identical isolation requirement on the Claude leg is therefore **this project's conservative default**, adopted because the failure it prevents is unrecoverable and the vendor's silence is not evidence of safety. Neither vendor documents a file-locking mechanism; the documented safety model on the one leg that has one is exclusive access, not locking. Isolated homes remove the shared writer, which is the design's whole basis for expecting concurrency to work — but "no shared file" is a necessary condition, not a demonstrated sufficient one, which is exactly why the probe exists.
- **Config-home environment variables.** The reserved variables are the only channel by which a process is pointed at a home. If a provider resolves any credential state from a path that ignores that variable — or if a variable's documented effect is scoped to platforms other than the one in use — isolation is incomplete on that leg, and only a probe against the binary can tell.
- **Keychain entry derivation — documented on both legs, and still a probe.** Where credentials live in an OS keychain, isolation holds only if the entry a provider addresses varies with its configured home, and **both vendors state that it does**: Anthropic documents that the configured home keys the macOS keychain entry to that directory, so a process with a different home reads a different entry, and Codex derives its keyring key from a hash of its canonical home. The probe therefore **confirms** a documented property rather than discovering an unknown one — which lowers what is at stake in it and does not remove it, because the entry name is undocumented, version-fragile, and not the daemon's to compute (§Pitfalls To Avoid). Observe isolation; never derive it.

Neither vendor ships first-class multi-account support at the pinned versions. Codex's own issue tracker records that the CLI assumes a single account and that swapping the home directory is the acknowledged manual workaround, characterized there as tedious rather than as unsupported ([openai/codex#4432](https://github.com/openai/codex/issues/4432), open, accessed 2026-08-18; **Verified** as to the issue's text and state). That is corroboration for the mechanism this spec builds on — relocating the home is how the ecosystem does multi-account today — and simultaneously the reason the daemon must own the mechanism carefully rather than assume the provider will grow into it.

## Authorization Posture

Account operations split across two authority models, and the split is deliberate.

- **Registry mutation is node-operator authority, outside the session permission matrix.** Registering an account, removing one, changing a default, and resetting a credential home are node-local operator acts in the same class [Spec-025](025-mcp-server-configuration-and-governance.md) places MCP governance in: the caller who owns the node is authorized, a control-plane-relayed attempt is denied rather than queued, and no session-scoped authority grants any of them. No Cedar action is minted for these, and that absence is the deliberate answer rather than an omission — a session-scoped Cedar action would imply a relayed session call could reconfigure the node operator's paid accounts.
- **The registry read takes the node-operator gate as well, because of what it now discloses.** A list verb would ordinarily take a laxer gate than its mutating siblings, and before readiness that would have been right: account rows carry no credential material. The readiness projection changes the calculus — its remedy names a daemon-owned credential-home path and the provider's own sign-in invocation (§Node provider readiness and the sign-in handoff), and a filesystem location the daemon owns is not something a non-operator local caller is entitled to read merely because it arrived on a read verb. So the gate follows the disclosure rather than the verb's shape, and the whole namespace — read included — is node-operator authority. This is stated here rather than left implicit because the disclosure boundary the remedy relies on is exactly this gate: without it, the remedy's message-text-only discipline would be enforced against relayed surfaces while standing open to any local process that can reach the daemon socket.
- **Which account pays is chosen on the provider surface, not per run.** A run carries the account its definition or workflow step pins, or the provider's current one, and the daemon resolves it — so there is no per-run selection to authorize and no session-facing account act. Moving the current account is the provider surface's own verb (`providerAccount.setCurrent`) and is authorized there.

This split means the node operator alone decides which accounts exist, while policy decides who may spend from which of them.

## Interfaces And Contracts

- A node-local `providerAccount` wire namespace carries registry read and mutation, current-account selection, and the per-account authentication probe. Concrete method names, payload shapes, and the account-selection member on run creation are registered in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md).
- **Billing mode is the one operator-authored field on the row, and it is correctable in place.** A correction is a plain registry write: it does not touch the credential home, is not a credential-home lifecycle transition, and therefore does not bump `credentialGeneration`. Account identity — the address, plan and organisation the provider itself reports — the account's provider, and its credential-home path are **not** correctable, because each of those is what historical spend is keyed to or resolved through, and none of them is this product's to author. The correction path is required rather than convenient: since account identity is immutable and never re-derivable, an operator who could not correct a mis-declared billing mode would have to remove and re-register, minting a new identity and orphaning that account's spend history — so its absence would silently push operators into destroying their own cost record. It is also the mechanism the `unknown` billing mode is resolved through. The provider-reported identity fields are refreshed from the provider's own reading rather than edited, and their retention and erasure obligations are recorded in [Spec-020 §PII Data Map](020-data-retention-and-gdpr.md#pii-data-map).
- Run admission resolves the account from the run's pin or the provider's current account and stamps the result on the run's admission record ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)); it takes no account input from a caller.
- The account-scoped quota event carries account identity and credential generation ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)).
- The driver contract gains account-scoped authentication state and the typed provider-limit signal ([Spec-004 §Fallback Behavior](004-provider-driver-contract-and-capabilities.md#fallback-behavior)).
- The registry read reply carries, beside the accounts, a **per-provider readiness projection**: exactly one entry for each provider the request selects — never zero, never two — derived as §Node provider readiness and the sign-in handoff specifies and served from the stored last-probe result, with the timestamp of that observation. Its state vocabulary is registered in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) and widens only in lockstep with the account health vocabulary it embeds. **The namespace gains no verb**: readiness is an additive member on a reply that already exists.
- The brokered sign-in leg adds a **start** verb, a **cancel** verb, and a read-shaped **subscription** to the same node-local namespace. The subscription carries a wire-only notification and never an `EventEnvelope`, so the registry remains un-evented (§State And Data Implications) and no [Spec-005](005-session-event-taxonomy-and-audit-log.md) type is minted. Start returns the provider's verification material and an opaque attempt identifier; cancel takes that identifier and reports whether an attempt was cancelled or none matched.
- The `register` verb gains **one write-only member** carrying the [ADR-028](../decisions/028-provider-credential-custody-posture.md) D2 token class. It appears on no reply, and the namespace's no-credential-payload rule is otherwise unchanged: **exactly one input on this wire accepts credential material, and it is that one**.
- The registry row gains four durable fields — the observed authentication mode, the last observed credential-refresh time, the recorded sign-in time, and the per-account observation opt-out — each nullable where absence is honest and never defaulted into a value the daemon has not observed.
- The account-scoped quota event gains an **additive-optional limit identifier**, and the axis re-keys onto it (§Per-limit provider quota). Absent means the reserved `default` identifier, so no existing producer becomes invalid.
- **The namespace carries a sign-out verb, and sign-out is the credential-home reset rather than a registry mutation.** It ends the login the provider's own store holds inside that account's home and does nothing else: the registry row keeps its place, its identity, its billing mode, its quota readings and its spend history, and signing in again signs **that same account** back in rather than registering a second one. It is therefore a credential-home lifecycle transition and **bumps `credentialGeneration`**, which is what ends the account's prior attention epoch and marks every quota reading taken before it as predating the change (§Per-limit provider quota). It is deliberately not the removal verb and neither stands in for the other: removal forgets the registry row and leaves the home's bytes untouched, sign-out ends the login and leaves the row. It carries no credential material outward in either direction — the no-credential-payload rule is unchanged — and it is refused while a run bound to that account is live, on the same reasoning removal is.
- **Setting a provider's current account is one verb on this namespace, and it is the whole of the account switch.** `providerAccount.setCurrent` marks an account current for its provider and, in the same act, moves every running session on that provider that is not pinned to an account (§Moving a session to another account). There is no second verb, no per-session switch verb, and no pending-intent record: the verb's own reply names the account that is now current and the sessions the daemon is moving, and each session's move settles on that session's own timeline rather than on this reply. One control setting one fact is what keeps the two readings from disagreeing — a per-session switch beside a provider-wide current account would let a session sit on an account the provider surface says it is not on. A session's own surface reports which account it is on and offers no switch (§Moving a session to another account).
- **Copying an operator's own ambient memory store into an account's home is a one-time, operator-triggered operation on the namespace, `providerAccount.memoryImport`.** An operator whose provider memory lives in their own ambient provider directory can copy it **once** into a named account's home; the operation reports how many entries it copied, or that there was nothing to copy, and is offered no more for that account afterwards. The two stores are never joined and nothing is copied back: the ambient directory is the operator's and the home is the account's, and a continuing synchronization would make it impossible to say which store a running session read. This is an operator act on an account's own home rather than a claim of ownership over its bytes — the same boundary §Brokered interactive sign-in draws.
- The account half of the operator surface is the namespace above. Its **provider half is owed rather than registered**, and is listed here so it is built once: the path to that provider's command, with the re-check that follows a change to it; the switch that makes the provider available for new sessions; the bound on how many helper processes it may run at one time; the standing rules it holds on this machine, with the revoke beside each; the provider-level automatic-compaction bound; the read of Claude Code's current output style from the installed build, with the write that changes it; and the action that imports that provider's own existing conversations, with the stop it offers while it runs. These are provider-level rather than account-level, they belong to no account row, and no method is minted here for any of them.
- Refusal codes for the fail-closed paths are registered in [Error Contracts](../architecture/contracts/error-contracts.md).

## State And Data Implications

- One new node-local table, `provider_accounts`, holds the registry: account identity, provider, the provider-reported identity fields, credential-home path, billing mode, credential generation, default flag, and the **stored last-validation reading** — the account's health state together with the RFC 3339 timestamp of the observation it records, held as a nullable pair set and cleared together and NULL until a probe has ever been taken. That pair is the readiness projection's only source, which is what lets a registry read answer the admission question without spawning a provider process or opening a credential file (§Node provider readiness and the sign-in handoff). It is deliberately not `updated_at`: that column moves on any row mutation, so a billing-mode correction — the row's one operator-authored field — would read as a fresh authentication observation. DDL and constraints live in [Local SQLite Schema §Provider Account Tables (Plan-026)](../architecture/schemas/local-sqlite-schema.md#provider-account-tables-plan-026).
- **No control-plane table.** Provider accounts and their spend are node-local; nothing about them is written to the shared schema.
- **One durable per-turn usage projection, rebuilt from the events the accountant already folds.** The per-turn usage event ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) is the durable record of a turn's consumption, and this plane projects those events into a node-local table, `provider_account_usage_turns`, holding **one row per turn**: the time, the provider, the account identity, the credential generation observed with it, the session, the run, the model, the token counts (input, output, cache read, cache write, reasoning), and the cost with the provenance the three-tier derivation ladder already assigns it ([Spec-014 §Cost Derivation And Absent-Cost Semantics](014-multi-agent-channels-and-orchestration.md#cost-derivation-and-absent-cost-semantics)). It is **a projection and not a second accountant**: the same events feed it and feed the committed-spend fold, it is rebuilt on replay like every other projection, and every figure it answers is served through the one committed-spend accessor [Spec-014 §Cost Figure Display Consistency](014-multi-agent-channels-and-orchestration.md#cost-figure-display-consistency) names. What it adds over the fold is not a second arithmetic but an **axis**: the fold keeps running totals, and a total cannot be sliced by a day or a model it never kept. Rows are appended and never rewritten, and they are children of the registry, so an account's rows go when the account does. The session and the run are **absent** on a turn no session owns — the window-start turn is the one that spends outside every session (§Credential-home health observation) — so the account's own totals include it and no session's receipt does.
- **The account column is what makes the figures honest on a multi-account node, and the per-turn event must carry it.** Without it a provider's total silently pools every account, which is the failure mode of every tool surveyed on this ground. The event therefore carries the account it was charged to and the credential generation observed with it, exactly as the account-scoped quota event does (§Interfaces And Contracts).
- **The token counts are taken from the carrier that is complete on each leg.** On the Claude leg they come from the result frame's **per-model** usage block rather than its top-level one: the top-level block counts the outer loop only and undercounts as soon as helper conversations run, so a node reading it would under-report a session's real consumption. On the Codex leg the provider reports the five counts per turn and **no cost at all**. The row still carries whatever provenance the derivation ladder assigns it, because enforcement needs one number on one ladder — but the **account surface draws tokens only** for a provider that reports no cost of its own, `All accounts · today 18M tokens · tokens only`, rather than presenting a locally derived figure as that provider's spend. This is the same honesty rule §Billing mode states for a subscription figure, applied to the other axis: a number is labelled with where it came from, or it is not drawn as money.
- **What is drawn from it.** Per account: tokens and spend for the day, and, expanded, by day and by model. Per provider across its accounts: the same two figures summed over that provider's rows. Neither is assembled by a client from the other, and neither is assembled from per-session receipts. A figure spanning rows of more than one cost provenance **states that it does**, on the same rule a figure spanning more than one billing mode does — and the two labels are carried independently, because cost provenance says where a number came from and billing mode (§Billing mode) says how the account is paid for.
- A provider's own usage history, where it publishes one, is drawn **beside** this table as the vendor's figure with the vendor named, and is never reconciled into it: two accountants counting the same tokens differently is exactly what one source of truth exists to prevent.
- The provider-reported identity fields — the address, the plan and the organisation — are user-referencing data held on the row so an account can be named on a surface without a provider read, and they are refreshed from the provider's own reading rather than authored here. Their retention and erasure obligations are recorded in [Spec-020 §PII Data Map](020-data-retention-and-gdpr.md#pii-data-map). The credential-home path is a filesystem location, not credential material; no credential material is stored in this table or in any other.
- Credential generation is durable and monotonic per account; it is never reset, including across a home reset, so a stale consumer can always order two generations.
- A second node-local table, `provider_account_usage_windows`, holds the **newest quota reading per `(account, limit identifier)`** with its window length, observation time, and source. It is a child of the registry and is removed with its account. It carries no credential material and no user identity.
- **The sealed token is not a column.** The [ADR-028](../decisions/028-provider-credential-custody-posture.md) D2 value lives in the [ADR-021](../decisions/021-cli-identity-key-storage-custody.md) ladder's store keyed by account identity, not in `provider_accounts` and not in any other table. The registry records only that an account's **observed** mode is the token mode — a label, not the material — so the no-credential-column property of every table in this plane is preserved exactly.
- The observed authentication mode may reveal an account's provider-side email and organization where the provider's status surface reports them. Those are user-referencing data and their retention and erasure obligations are recorded in [Spec-020 §PII Data Map](020-data-retention-and-gdpr.md#pii-data-map) alongside the account's provider-reported identity.
- **The registry remains un-evented.** Nothing in this plane appends a durable session event, the brokered sign-in included; its completion travels a wire notification on a read-shaped subscription and reaches no session timeline.

## Example Flows

- `Example: An operator registers a personal subscription account and a work metered account for one provider, marks the personal one default, and starts a run whose definition pins no account — the personal account pays, and the run's admission record carries its account identity.`
- `Example: A saved agent definition pins the work account. A run started from that definition binds the work account, the daemon validates its home, probes it authenticated, spawns against that home, and the session cost receipt attributes the run's spend to the work account labeled metered.`
- `Example: The daemon crashes mid-run. On relaunch the binding's durable spawn-bound record re-realizes the same account; the home has since been logged out, the probe returns unauthenticated, and the resume refuses fail-closed rather than continuing on the default account.`
- `Example: A Codex process sends the daemon its token-refresh server request. The daemon refuses it, names the misconfiguration that produced it, stores nothing, and leaves the account's credential generation and stored health reading where they were — the provider keeps its own login inside its own home.`
- `Example: The provider reports a usage limit on the work account. The typed signal parks the phase with the account's identity and generation on the attention key; the personal account's runs are unaffected, because the fold key is account-scoped.`

## Implementation Notes

- The registry is small and node-local; a read-through cache is fine, but the authentication probe result is time-sensitive and must not be served stale past the driver contract's refresh cadence.
- The default flag is best enforced as a partial unique index rather than in application code, so two defaults for one provider are impossible by construction rather than by discipline.
- Credential-home paths must be validated as daemon-owned locations outside any repo working tree before they are written to the registry; a home inside a worktree would be captured by workspace lifecycle operations that have no business touching credentials.
- The reserved-variable set is the daemon's alone. The cleanest enforcement is to apply the reservation at the same construction site that already strips denied variables, so there is exactly one place where the child environment is assembled and exactly one place to audit.

## Pitfalls To Avoid

- **Do not treat the credential home as custody, and do not use it as one.** Pointing a provider at a directory is not storing its tokens, and a design that reads, copies, caches, or transports the material inside a home violates the posture even if it never persists it — that prohibition is unchanged. The 2026-08-26 amendment adds its converse: the one class of credential material the daemon may hold ([ADR-028](../decisions/028-provider-credential-custody-posture.md) D2) does **not** go into the home either. Daemon-owned bytes written into provider-owned space are indistinguishable from the provider's own to every later reader, the provider's tooling included. Seal it through the ADR-021 ladder in daemon-owned state.
- **Do not let an account fall back.** Every fallback in the account plane is a silent mis-billing. Refuse instead.
- **Do not key the account plane on the credential.** A rotated credential is the same account; an identity derived from credential material would fragment an account's history at every refresh and would leak account material into every payload carrying it.
- **Do not conflate the two "account identity" terms.** The control-plane user sense in the domain model is unrelated to this one.
- **Do not sum subscription and metered usage into an unlabeled dollar figure.** That is the single most misleading thing a multi-account cost surface can do.
- **Do not emit an empty reserved variable, and do not read one as a default — on either variable of a pair.** On at least one provider leg an empty value behaves as unset and silently returns the process to the shared credential entry, so the partition appears configured and is not. The hazard is **not one variable but two independent routes to the same collapse**: emptying the companion variable reaches it as directly as emptying the primary, and a filter that guards only the one everybody names is half a filter. Absent means absent; empty means defective; filter every reserved name at the single construction site, both halves of every pair.
- **Do not compute a provider's keychain entry name.** It is undocumented, version-fragile, and depends on inputs the daemon does not control. Observe isolation; never derive it.
- **Do not spawn an account-pinned provider binary older than the release that honors the pin.** The reserved credential-home variables are honored only from a specific provider release onward; an older binary ignores them and writes into the operator's **shared** home instead — so the spawn appears to succeed, the isolation silently does not exist, and two accounts cross-contaminate one credential store. The daemon establishes the binary's version before the first account-pinned spawn and refuses below the floor, because this failure is invisible at the moment it happens and only surfaces later as an account that mysteriously lost its login.
- **Do not let fail-closed spawn validation refuse an authentication method the vendor ships.** §Vendor authentication-policy constraints forbids removing, disabling, or restricting any built-in authentication method, and an account may legitimately be an API key, a third-party inference provider, or an externally-brokered credential rather than a subscription sign-in. Validation gates on whether the account's home is **authenticated**, never on which method authenticated it — which is exactly why the recorded mode is an observation with a tolerant unknown arm and not a gate.
- **Do not generalize one vendor's documented rule to the other.** Only one of the two providers publishes a concurrency constraint on its credential file. Adopting the same discipline on both is correct; attributing it to both is not.
- **Do not assume concurrency before the probe.** Shipping the concurrent path on the strength of the design's plausibility is exactly the failure the parity triad's verify leg exists to prevent.
- **Do not widen the driver capability set with an authentication flag.** The authentication probe is required of every driver by design; a flag would make it optional.
- **Do not let the daemon touch a credential, and do not let a per-account home be `~/.claude` or `~/.codex`.** The observer asks a provider a question inside a home the daemon owns and lets the provider's own code renew its own login there; the daemon reads no credential file, writes none, speaks no token endpoint, and never enters the Codex external-authentication mode. Pointed at the operator's own home the same read becomes the race the rotation rule exists to prevent — two holders of one grant, and a lost rotation ends their login. The isolation is what makes the read safe, so the read is never taken anywhere else.
- **Do not treat a provider path answering successfully as proof that credentials work.** At least one pinned path returns success while discarding the outcome of the refresh it was asked to perform, so a permanently-dead credential answers it cleanly. Liveness of the surface is not usability of the credential.
- **Do not key quota readings on the window length, and do not read a window's position as its meaning.** One pinned provider publishes several limits that share a window length; keying on the length collapses them and the survivor depends on arrival order, so the key is the limit identifier. The mirror error is the other way round: a provider has moved a given window between its primary and secondary slots, so a surface that labelled the primary slot as the short window would relabel every bar the day that moved. Key on the identifier; label from the length the provider reported.
- **Do not collapse `indeterminate` into `reauth_required`.** They have different remedies — look again versus sign in — and §Validation at spawn already refuses on `indeterminate`, so the collapse buys nothing and costs the operator a full sign-in over a transient fault.
- **Do not echo, log, or render the token input.** It is write-only on every surface, diagnostics included. A value that appears in a log line has been disclosed regardless of where it was sealed, and at least one upstream leg has shipped a fix for exactly this class — error strings that carried a token into a message the caller could read.

## Acceptance Criteria

- [ ] AC-1 — A node registers two accounts for one provider with distinct homes; both are listed under the identity each provider reports, exactly one is default, and a second default for the same provider is rejected by the schema.
- [ ] AC-2 — Account identity is stable across re-authentication, a billing-mode correction, and default changes; credential generation strictly increases at each credential-home lifecycle transition and never resets.
- [ ] AC-3 — A run whose definition pins no account binds the provider's current account; a run started from a definition or a workflow step that pins one binds the pinned account, and no client request can name either.
- [ ] AC-4 — The bound account is stamped on the run's admission record, is not client-suppliable, and is re-realized identically on resume from the durable spawn-bound record.
- [ ] AC-5 — A spawn against a missing home, a husked home, an unregistered account, or an `indeterminate` probe refuses before spawn with a typed refusal, and no provider process is created.
- [ ] AC-6 — The child environment for an account-bound spawn carries the reserved credential-home variable set by the daemon; a caller-supplied or inherited value of a reserved name is discarded rather than merged.
- [ ] AC-7 — The daemon starts no provider process in external-authentication mode on either leg, and a token-refresh server request arriving on any binding is **refused**: nothing is stored, no credential generation moves, no stored health reading moves, and the refusal names the misconfiguration rather than a credential fault.
- [ ] AC-8 — The account-scoped quota event carries account identity and credential generation, and a two-account node attributes each snapshot to the correct account.
- [ ] AC-9 — Every surfaced account-attributable cost figure carries its account's billing mode across all three values, and a total spanning more than one mode states that it does; a figure from a `subscription` or `unknown` account is never presented as billed dollars.
- [ ] AC-10 — With the capability probe unresolved or negative, runs bound to accounts of the same provider serialize, and no execution path shares a credential home.
- [ ] AC-11 — A node with no accounts reports the no-account arm for every provider it supports; registering one account and probing it authenticated moves that provider to the authenticated arm; and **a provider whose accounts include no default at all** reports the no-default arm. That third case is seeded directly — two accounts, neither flagged default — and **not** by adding a second account beside an existing default: registering a non-default account leaves the first account's default intact, so readiness correctly keeps resolving it, and asserting `no_default` there would require silently clearing a default and changing which account pays. The reply carries exactly one readiness entry per selected provider in every case.
- [ ] AC-12 — Deriving readiness spawns no provider process and reads no credential material: a registry read against a two-account node performs no authentication probe and opens no credential file, and the reply carries the timestamp of the **stored** observation rather than a fresh one.
- [ ] AC-13 — No surface reports a provider as authenticated on any reading other than the authenticated arm — `indeterminate` included — and a run bound to an account whose stored reading was authenticated still refuses at spawn once that home has been signed out.
- [ ] AC-15 — A brokered sign-in against a registered account spawns the provider's own unmodified binary with that account's home pinned, returns the provider-emitted verification material and an opaque attempt identifier, and completes without the daemon reading, copying, or persisting any credential; a second start against the same account while one is in flight is refused, and cancellation by attempt identifier releases the provider-side attempt.
- [ ] AC-16 — Sign-in completion reaches clients on the read-shaped subscription as a wire notification, appends no durable session event, and is followed by an ordinary health observation before the account is reported authenticated — a completion reported successful does not by itself move the stored reading.
- [ ] AC-17 — The `register` verb accepts a non-interactive token on its write-only member; the value is sealed through the ADR-021 ladder, never written into the credential home, never returned on any reply, and never present in any log line, error message, metric, or diagnostic dump. Registration refuses on a host where the ladder refuses, rather than falling back to a plaintext write.
- [ ] AC-18 — A token-mode registration against a provider leg with no recorded subprocess-strip observation is **refused at registration** (ADR-028 condition 5), creating no account and sealing nothing; on an admitting leg, a run bound to a token-mode account receives the token only in its own child process environment, never in an argument vector and never in a sibling account's environment; a terminal authentication refusal on such an account moves the stored reading to `reauth_required` and triggers no retry and no refresh attempt.
- [ ] AC-19 — The background observer runs per account on each leg's cadence, honours the per-account opt-out, is single-flight per account, takes no reading while a turn is live on that account, and **issues only the two reads this spec names** — that leg's limits read and its local status read. Across a full cycle: no credential file or keychain entry is read, written or copied by the daemon; no model turn is charged on either leg; every window the account has is stored with its read time; and on the Codex leg the account's own last-refresh marker **is permitted to move**, which is the renewal the cadence exists to cause, while `credentialGeneration` and every stored quota reading's generation stay where they were.
- [ ] AC-20 — An observation writes the stored health pair without bumping `credentialGeneration`, and a transient observation failure leaves parked work's `(accountId, credentialGeneration)` attention key intact.
- [ ] AC-21 — Quota readings for one account across distinct limits sharing one window length are held and rendered as distinct, keyed by limit identifier; a reading naming no limit identifier is stored under the reserved `default` identifier; where two readings key alike the later observation time wins, with the source breaking only exact ties; a per-model window is keyed from the model's display name on the leg that reports one and is **not** read from that leg's null flat keys; every window is labelled from its reported length rather than from its position in the reply; a complete reading set replaces the account's stored set while a sparse pushed update merges into it and prunes nothing; and every rendered window carries its read time.
- [ ] AC-22 — `providerAccount.setCurrent` on a provider with one idle and one busy unpinned session, and one session pinned to another account: the idle session's process is stopped and its conversation reopened in the new account's home through the provider's own resume under the same conversation identifier; the busy session is held at its next tool boundary, its turn interrupted there, its conversation resumed in the new account's home and the work continued in a **new run** stamped with the new account; the pinned session does not move; the conversation file is removed from the home it came from; no credential file, keychain entry or provider login is written anywhere in the sequence; and each moved session's timeline carries one row, `Switched to account <name>`, expanding to `turn continued` where a turn was in flight — or `Conversation restarted on account <name>` where the provider could not reopen its own conversation.
- [ ] AC-23 — `providerAccount.setCurrent` naming an account that fails spawn validation refuses in place: the current mark does not move, no session moves, and the refusal carries that account's own remedy.
- [ ] AC-24 — A turn on either leg appends exactly one per-turn usage row carrying the provider, the account, the credential generation observed with it, the session, the run, the model, the five token counts and the cost with the provenance the derivation ladder assigned it; a Claude row's tokens match the provider's per-model block on a turn that ran a helper conversation, and a Codex row carries no provider-supplied cost. A turn no session owns writes its row with the session and the run absent, and that row counts in the account's totals and in no session's receipt. The projection rebuilds identically from the event log on replay. Per-account, per-provider, by-day and by-model figures are group-bys over those rows served through the one committed-spend accessor, no surface re-sums them or derives one from another, and a figure spanning more than one cost provenance states that it does.
- [ ] AC-25 — Removing an account runs no provider sign-out: the account's credential home is byte-identical across the removal and the provider still reports that home as signed in; the row, its readings and its usage rows are gone; and removal is refused while a run bound to that account is live.
- [ ] AC-26 — A turn on a session refreshes that account's stored windows without the cadence firing: on the Codex leg from the provider's own rolling push recorded with the turn, and on the Claude leg from a turn-free `get_usage` sent to the session's **already-running** process at the turn's end, with no second process started and no model turn charged. An account whose freshness opt-out is off is refreshed by neither cadence, while the deliberate probe verb still reads it.
- [ ] AC-27 — At a reported window's reset the daemon spends **exactly one** turn on that account — one short message to the provider's smallest model, in a throwaway process in that account's own credential home holding no session — for every window the account reports on both legs; it appends exactly one per-turn usage row under that account with no session attributed; the limits read itself starts no window; and with the account's freshness opt-out off the reset spends nothing.
- [ ] AC-28 — A session moved between accounts mid-turn keeps one running total: the spend before the move is attributed to the account it ran on, the spend after it to the new one, the session's receipt carries both as account rows summing to that total, and the accountant re-baselines on the new process's own counters so no figure is double-counted and none reads as zero. The provider's per-process cumulative figure appears in no payload the operator's surfaces read.
- [ ] AC-14 — Guidance naming a credential home or a provider sign-in invocation appears only in operator-facing message text: no event payload, relayed payload, or log line carries a credential-home path, and no error payload carries provider sign-in output. The remedy member is present on every non-authenticated readiness entry and absent on the authenticated one — the producer obligation, asserted per arm — and it is composed at read time from the resolved account rather than read from any stored column.

## ADR Triggers

- Making provider accounts control-plane entities (shared across nodes, or synchronized) would cross the node-local boundary this spec asserts and require an ADR against the shared-schema invariant.
- **Discharged 2026-08-26 by [ADR-028](../decisions/028-provider-credential-custody-posture.md).** This trigger read: taking custody of provider credential material — storing, relaying, or serving it — would reverse the inherited no-token-custody posture and requires an ADR, not an amendment. It fired, and the ADR is the record. What it now governs is everything **outside** ADR-028's two bounded decisions: admitting a second class of credential material, accepting one on any input other than the `register` verb's, minting or exchanging credential material rather than receiving it already minted, speaking a provider token endpoint, or serving held material to any client. Each of those is a further ADR, not an amendment.
- Reading credential material out of a credential home — for any purpose, including a fact the registry could have recorded — would make the daemon a reader of provider-owned bytes and requires an ADR against §Pitfalls To Avoid.
- Adopting a shared credential home with application-level locking instead of per-account isolation would replace the mechanism this spec's concurrency posture rests on.

## Open Questions

- **Resolved 2026-08-25 — first-run provider authentication surfacing.** The gap this section recorded — a fresh install completing onboarding with no provider account registered and discovering it only when the first run refuses — is closed on this side by §Node provider readiness and the sign-in handoff and on the onboarding side by [Spec-023 §Provider Authentication (Group B)](023-first-run-onboarding.md#provider-authentication-group-b). [BL-154](../archive/backlog-archive.md) is `completed` and archived.
- **Open 2026-08-26 — no strip observation is scheduled, so the D2 token class ships dormant.** [ADR-028](../decisions/028-provider-credential-custody-posture.md) condition 5 admits the token class only on a provider leg with a **recorded first-party observation** that the provider strips the injected variable from the environments of the tool, shell, and subagent subprocesses it spawns. No such observation exists for either pinned leg, and **no task in this plan records one** — so §Non-interactive token registration is fully specified and, on today's evidence, refuses at registration everywhere. This is an absence of evidence rather than evidence of absence: a probe on either leg could satisfy the condition and switch the class on without any further amendment. It is carried here rather than folded into a task because assigning the probe is a scheduling decision, not a design one. The vehicle when it is assigned is the shape T3.3 already establishes — a named verification obligation against the pinned binaries with its own test file and the observed versions recorded alongside the result — and the observation must be **empirical**, since documentation asserting the strip is precisely what condition 5 refuses to accept.
- **Recorded 2026-08-26 — the bounded-custody residual is a named risk, not an open question.** Whether the vendor reads its own credential clause as barring [ADR-028](../decisions/028-provider-credential-custody-posture.md)'s D2 class is unresolved and cannot be resolved from this side. It is not carried here as an open question because it has an owner, a detection signal, and a pre-specified retreat in that ADR's §Failure Mode Analysis and §Assumptions Audit, and because D1 is specified to stand alone if D2 retreats. No open question remains on this spec.
