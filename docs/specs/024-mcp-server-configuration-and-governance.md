## Purpose

This spec defines V1 feature #15 ([ADR-014 §Decision](../decisions/014-v1-feature-scope-definition.md#decision)): how the local runtime daemon configures, governs, and observes **MCP servers** attached to the two provider CLIs (`claude` and `codex`). Each provider is an MCP client of its own. The daemon runs one MCP client of its own as well: it holds the real connection for every server it fronts — every server a Codex session reaches, and on both providers a server that demands proof-of-possession tokens — lists and reads a server's prompts for Codex, and serves the workflow MCP-tool step. What the daemon owns is the **governance layer** above those connections:

1. A **unified server inventory** — one normalized read model across both providers' divergent config surfaces.
2. **Configuration mutation** — add / update / remove / enable / disable servers at every scope on both providers, through each provider's own write mechanism where one exists and, where none does, through a format-preserving edit written only while the file is as the daemon last read it; never by blind config-file rewriting.
3. **Tool-level overrides** — per-(server, tool) enable/disable, approval-mode, and idempotency-class assignment, feeding the [Spec-004](./004-provider-driver-contract-and-capabilities.md) tool-metadata resolution layer.
4. **OAuth sign-in** — one daemon-held sign-in per server that needs one, used by both providers and by the daemon's own client, held and removed as [ADR-038](../decisions/038-mcp-credential-custody.md) records.
5. **Status observation** — normalizing both providers' server-status feeds onto the Spec-004 `McpServerStatus` enum, each transition sent live on `mcp.subscribe` and written to no log.
6. **Events** — every settled sign-in emits a canonical event in the `mcp_governance` category ([Spec-005 §MCP Governance (`mcp_governance`)](./005-session-event-taxonomy-and-audit-log.md#mcp-governance-mcp_governance).

## Scope

- The `mcp.*` IPC operation namespace on the daemon control surface, and the session operations over a session's own servers (`session.mcpServerList`, `session.mcpServerUpdate`, `session.mcpResourceList`).
- Normalized server inventory merging provider-declared config, live provider status, the daemon binding store, and the daemon override store.
- Provider-specific mutation engines at every scope: Claude Code's `claude mcp add-json --scope` writes plus live reconcile; the Codex user-config CRUD + reload pair, the daemon's own format-preserving edit of a project's `.codex/config.toml`, and the emulated Codex `local` scope.
- The `mcp_server_bindings`, `mcp_tool_overrides`, `mcp_mutation_receipts`, and `mcp_server_admitted_clients` SQLite tables (daemon-local, node-scoped).
- Every governance mutation is open to this machine's own client or any linked device, and no session, with no policy check and no ownership refusal.
- The `mcp.*` event types and their payloads, session binding, and sanitization rules.
- The daemon's own OAuth sign-in per server, its custody under [ADR-038](../decisions/038-mcp-credential-custody.md), and sign-out.
- The daemon's own MCP client and the route that fronts servers for Codex (and for a proof-of-possession server on Claude Code), with a long call moving to the background on both providers.
- A search of the public MCP Registry that fills the declaration form.

## Non-Goals

- **The daemon runs one MCP client of its own; a provider's own connections stay the provider's.** The client holds the real connection for every server the daemon fronts — every server a Codex session reaches, and on Claude Code only a server that demands proof-of-possession tokens (§Long tool calls and the fronted route) — and adds no governance of its own: the route applies the same overrides and approval a direct connection would. A server a provider reaches directly stays that provider's connection end to end. The daemon separately **hosts** an MCP server of its own: the callback-tool host of [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior), through which daemon-authored tools reach a run. That host sits outside this spec's governance model because the daemon authors it rather than the person declaring it: it is never override-governed, and its tools are governed by the specs that author them (Cedar authorization and the spec's own opt-in).
- **No credential custody beyond [ADR-038](../decisions/038-mcp-credential-custody.md).** The daemon holds MCP-server credentials exactly as that record states: one sign-in per server, the refresh token and any proof-of-possession signing key in the operating system's credential store under the daemon's own items, and access tokens only for provider processes it launched, through each provider's own header helper, and for its own client. It never reads or renews a sign-in the person's own Claude Code or Codex holds, and no credential reaches an event, error, log, read model, wire payload, or the renderer. Credential-bearing values in provider-owned config (env-var and header values) are handled **transiently in memory** only — by the provider's own write mechanism, by the `${VAR}` expansion of a Claude Code session's server set, and by the fronted route's connection — then discarded; they never reach storage, events, errors, logs, or any read model (§Implementation Notes — transient-secret handling). The node-local provider-account plane is [ADR-026](../decisions/026-provider-credential-custody-posture.md)'s and nothing here widens it.
- **No config-store ownership.** Provider config files (`~/.claude.json` scopes, `$CODEX_HOME/config.toml`, project-local `.codex/config.toml`, `.mcp.json`) remain provider-owned and are the source of truth the daemon observes, not a mirror it maintains. The daemon writes them through each provider's own mechanism where one exists — `claude mcp add-json --scope` on Claude Code, `config/value/write` / `config/batchWrite` for the Codex user file — and where none exists, a project's `.codex/config.toml`, through a format-preserving edit that keeps the file's comments and layout, is written only while the file is as the daemon last read it, and is read back through `config/read` before it counts (§Configuration Mutation).
- **No installing on the person's behalf.** A search of the public MCP Registry fills the declaration form; the person still adds the server and types every secret value, and the daemon keeps nothing from a search past the page.
- **No session-scoped permission-matrix extension.** Governance belongs to this machine's own client or any linked device, and no session, deliberately outside the session permission matrix ([Security Architecture §Permission Matrix](../architecture/security-architecture.md#permission-matrix)). The session-facing MCP surfaces are a session's own server list with its per-session switch, which only narrows what governance allows (§A session's own tool servers), the resource pick and the server prompts in the session's command list, and a server's request for input, which becomes the session's question card — none of them a governance mutation.

## Required Behavior

### Provider Capability Model

Both providers expose MCP configuration, status, and auth surfaces, but through structurally different mechanisms. Per the capability-parity principle (all provider capabilities integrate at V1; asymmetries are normalized, emulated, or degraded honestly — never silently dropped), the daemon binds to each mechanism natively and grades what each application path can deliver:

| Capability | Claude Code mechanism | Codex mechanism |
| --- | --- | --- |
| Declare servers for a session | `--strict-mcp-config`, so nothing the project or the account configures loads by itself; the session's servers sent with the `mcp_set_servers` control request right after start (about 0.1 s) and again after each resume, because the set lives only in the process's memory; only the daemon's own tool entry rides `--mcp-config`, which `mcp_set_servers` leaves in place | The conversation's own configuration at `thread/start`: the whole `mcp_servers` table, which replaces the service's table for that conversation, each server a `url` entry on the daemon's route under its own name and each enabled or not (§Long tool calls and the fronted route) |
| Change a live session's server set | Another full-set `mcp_set_servers` call, applied from the next turn — SDK `setMcpServers(servers)` returning `{added, removed, errors}`; streaming-input mode only | The conversation's per-server `enabled` flag, reaching it at its next turn where the provider honors it |
| Mutate durable config | `claude mcp add-json` / `claude mcp remove` with `--scope user`, `--scope project` (run from the project root; writes `<project>/.mcp.json`) or `--scope local` (writes the project's entry in `~/.claude.json`) — the provider's own store stays the durable home; the daemon never rewrites those bytes itself | `user`: `config/value/write` / `config/batchWrite` with `expected_version` optimistic concurrency on `$CODEX_HOME/config.toml`; `project`: the daemon's own format-preserving edit of `<project>/.codex/config.toml`, read back with `config/read`; `local`: emulated, an entry in the user file with `enabled = false` switched on per conversation in that project's sessions |
| Server status | Init census `mcp_servers[]` + `mcpServerStatus()` SDK query; `claude mcp list` glyphs (human CLI, no `--json`) | For a fronted server, the daemon's own client's connection to it; `mcpServerStatus/list` (ephemeral, cursored, `thread_id`-scopable) + `mcpServer/startupStatus/updated` notifications for the conversation's own leg |
| Per-server reconnect | SDK `reconnectMcpServer()` | The daemon's client reconnecting a fronted server; `mcpServer/refresh` |
| Enable/disable | The daemon's per-server enabled overlay decides whether the server is in the set sent with `mcp_set_servers` (Claude Code's configuration has no enabled field, and removal would destroy the declaration); `mcp_toggle` (`toggleMcpServer()`) is never used, because it saves the switch for the whole project and leaves the server running | `enabled` field write + reload; per conversation, the `enabled` flag in the `thread/start` table |
| Tool allow/deny + approval mode | Daemon-enforced (no native per-tool config field; the daemon's approval layer enforces overrides) | Native config fields: `enabled_tools` (allow), `disabled_tools` (deny, applied after allow), `default_tools_approval_mode` (`auto`\|`prompt`\|`writes`\|`approve`), `tools.<t>.approval_mode`; for a fronted server the daemon applies them on its route with the session's permission level |
| OAuth sign-in | The daemon's own sign-in (§OAuth Orchestration), handed to the process through `headersHelper`; for a server that admits only Claude Code's client, Claude Code's own flow (the `mcp_authenticate` control request) run in a credential folder the daemon makes for that sign-in | The daemon's own sign-in, handed to the process through `http_headers_helper` and used by the daemon's client for every fronted server; for a server that admits only Codex's client, `mcpServer/oauth/login` run in a throwaway home with `mcp_oauth_credentials_store = "file"` |
| Long tool call | `CLAUDE_AUTO_BACKGROUND_TASKS=1`: a call still running after 120 s, or one running when a message arrives, moves to the background, and the same switch moves a foreground helper to the background after 120 s; Claude Code runs MCP Tasks itself | No MCP Tasks and no backgrounding; the daemon's route answers a long call with a background handle and delivers the result (§Long tool calls and the fronted route) |
| Prompts | Claude Code lists a server's prompts itself | Codex never asks a server for its prompts; the daemon's client lists and reads them on the daemon's sign-in |
| Required-server gating | Not native; daemon surfaces failed servers via status | `required = true` ⇒ `thread/start` / `thread/resume` FAIL if the server cannot initialize |

Every mutation response MUST carry an **application grade** — `live_reconcile` (applied to the running session's live server set), `user_config_write` (persisted to the provider's own config store, effective for subsequent runs/threads), `next_run` (daemon-recorded governance state applied to the next session's server set), or `daemon_enforced` (enforced immediately at the daemon's own decision layer) — so callers know _when and where_ the change takes effect. Degradation is honest and typed, never silent: a Claude mutation that cannot reconcile live succeeds with the grade its durable path actually achieved, not an error and not a fake `live_reconcile`.

### Unified Inventory

- The daemon MUST expose one normalized inventory (`mcp.list` / `mcp.get`) merging four sources per server binding: (1) provider-declared configuration (parsed from the provider's own config surfaces), (2) live provider status normalized onto `McpServerStatus` (`unknown | starting | connected | needs-auth | failed` per [Spec-004](./004-provider-driver-contract-and-capabilities.md) — the api-payload `McpServerStatus` union), (3) the daemon binding row, (4) the daemon tool-override rows. Each entry carries a **redacted normalized config view** (`McpServerConfigView`) — transport, command/args, the **query-redacted URL** (scheme + host + path; the address is taken as typed and passed to the provider as typed, a user name or password in it included, and that user name and password and the query component are credential-equivalent write-only material, so neither is ever read back: the view serves the query **parameter names** instead, the same names-not-values discipline as env vars and headers), timeouts, `required`, `bearerTokenEnvVar`, the Codex auth references (`envHttpHeaders` — a header-name → env-var-**name** map — plus `oauthScopes` and `oauthResource`), and the **names** of env vars and headers, never their values — so `mcp.get` can read back what `mcp.upsertServer` wrote and the person can inspect provider state without the daemon ever serving credential material (`command`/`args` are process-visible strings the person authors, the same residual class as the identifiers in §Status Observation and Events).
- Server identity is the scope-qualified **binding** `(provider, scope, scopeRef, serverName)` — scope is `user` (Claude user scope in `~/.claude.json`; Codex `$CODEX_HOME/config.toml`), `project` (Claude `.mcp.json`; Codex `.codex/config.toml` in the project; `scopeRef` = the canonical project root), `local` (Claude's project-keyed private scope; on Codex the emulated scope — an entry in the user file switched on per conversation in that project's sessions, its name unique across that file; `scopeRef` = the canonical project root), or `plugin` (a server an installed plugin declares in its `.mcp.json`, read from the daemon's plugin home for that provider; `scopeRef` = the plugin's name); `scopeRef` is the empty string for `user`. A plugin's server is listed as `From plugin <name>` and joins a session only when switched on for it; its declaration belongs to the plugin and changes when the plugin is updated or removed. Two scopes legitimately declaring the same `serverName` with different configurations are **distinct bindings** with independent status and overrides — collapsing them would bleed overrides across configurations. The inventory MUST NOT merge same-named servers across providers or across scopes into one logical entry.
- Same-name shadowing across scopes is surfaced, not resolved away: both bindings appear in the inventory, and the provider's own scope precedence decides which one a session gets; the page names the copy a project does not use (§The MCP servers page). Every binding that is switched on joins a session's runs, at every scope on both providers: one the person added, and one that came with the repository; a server the person rejected in Claude Code stays out.
- Provider states outside the normalized enum map deterministically: Claude `pending` → `starting`; Claude `disabled` → `enabled: false` on the inventory entry with status from the last observation (or `unknown`); absence of any status source → `unknown`, honestly. Provider status feeds report server names, not bindings; the daemon MUST attribute each observation to the binding that is effective for the observing context (the set the daemon sent that session). For a server the daemon fronts, its own client holds the connection, so that client's connection is the observation; and because a server a provider reaches on a header helper reports `authStatus: unknown` on Codex, a server whose sign-in the daemon holds reads `needs-auth` from the daemon's own sign-in state.
- After the background service moves between Windows and a WSL distribution, a server whose command or arguments name a program on the side it left is kept as it was and reads `failed`, its entry carrying `failedReason: commandNotRunnable`; a bare command name such as `npx` is looked up on the new side. This is one member on the entry, not a new status.
- A config binding and a **live provider leg** are different grains: one binding can back several concurrent sessions' connections at once, and the Plan-003 status seam keys every session-feed observation by the runtime-binding leg (`sessionId` + the Plan-003 `bindingId`). The inventory MUST NOT collapse divergent leg states into one overwritten scalar: each entry exposes the per-leg observations (`legs[]` — leg identity, status, `observedAt`) alongside a deterministic top-level aggregate `status` — the most severe current live-leg status under the fixed severity order `failed > needs-auth > unknown > starting > connected` (`unknown` is a valid live-leg status — a leg whose observation source is lost; lost observability outranks states known healthy, but never a concrete failure), falling back to the newest node-probe observation when no live leg exists, and to `unknown` when there is no observation source at all. Legs are **live-session observations with a bounded lifecycle**: when a leg's backing runtime binding closes (session end, driver exit), the daemon retires the leg and recomputes the aggregate — a terminated session's last observation never pins the aggregate (a `failed` leg of a closed session does not hold the server at `failed` while every live session is `connected`); with no live legs remaining, the aggregate falls back per the order above. A leg is one running session's connection, so the page reads one line per running session that uses the server, never one per place.
- First observation of a binding the binding store has never seen MUST upsert its binding row — the anchor its enabled overlay and tool overrides hang from.

### Configuration Mutation

- Mutations (`mcp.upsertServer`, `mcp.removeServer`, `mcp.setEnabled`) target a binding and MUST route through the mechanism for its provider and scope, per the capability table above. `mcp.upsertServer` and `mcp.removeServer` take `scope` (`user` | `project` | `local`) and `scopeRef` (the project root) on both providers, and every one of those scopes is writable on both; a `plugin` binding takes `mcp.setEnabled` and tool overrides, and its declaration changes only with the plugin. **Upserts are read-modify-write over the provider's own declaration**: provider fields the normalized input does not model — or does not carry — are preserved, never erased (Codex user writes are field-granular `config/value` paths touching only carried fields; the project-file edit changes only that server's own table; the regenerated Claude declaration starts from the observed current one), so a typed read/edit round-trip can never silently destroy provider configuration outside the governed surface.
- **Every operation applies to a binding at any scope.** A Codex `project` binding is written through the daemon's own edit of the project's `.codex/config.toml`, its tool-override facets included (§Tool-Level Overrides).
- **A running session picks up a change without a restart, with one exception.** After a write the daemon sends Claude Code the reload request, so hooks, the tool-server file and output styles are live for the session's next turn, and a changed agent definition reaches the session by a `--resume` at its next idle moment, because the agents map Claude Code takes at start is fixed for the process's life; on the headless path that request does not apply a change to a plugin's tool server, so such a change lands at the provider's next start and the session's flow row says one is waiting. On Codex a skill is live at once, and a new or edited definition needs the lead's conversation forked on the running server with its history intact, the flow row reading that definitions were reloaded.
- **Validation precedes commitment.** Schema validation and every check that can fail the mutation outright run **before** the durable leg commits — `mcp.config_invalid` is exclusively a pre-commit refusal. Once the durable leg has committed, the mutation never converts to a thrown error: later per-leg live failures are reported inside the successful response (below), so a caller can never be induced to retry a mutation that already committed.
- **Claude, durable leg (unconditional):** every `mcp.upsertServer` / `mcp.removeServer` persists to the provider's own store at the binding's scope via Claude Code's own command (`claude mcp add-json <name> <json> --scope <scope>` / `claude mcp remove <name> --scope <scope>`, a `project` or `local` write run with the project root as the working folder) **before** the mutation is acknowledged — an acknowledged mutation survives daemon restart because the provider's store, not daemon memory, is the durable home. The daemon MUST verify the write took effect (re-read via `claude mcp get` / observation of that scope) before emitting the config event.
- **Claude, live leg (opportunistic):** in a streaming-input session (the live leg is selected by the outcome of the daemon's own full-desired-set `setMcpServers` call, never by a version comparison and never by a driver-side probe: Spec-004 declares this flag non-probeable because an empty-set probe would clear the session's servers, so the first full-set send **is** the detection and its refusal selects the fallback; streaming-input mode remains a reachability precondition), the daemon additionally applies the mutation live via `setMcpServers` and MUST reconcile the returned `{added, removed, errors}` against the requested delta. The call replaces the set the daemon last sent and leaves in place only what `--mcp-config` passed, which is the daemon's own tool entry; a plugin's servers are kept out by `--strict-mcp-config` and sent by the daemon like any other server switched on for the session — so the daemon MUST always send the full desired set, never a delta. The response grade reports the most immediate application achieved: `live_reconcile` when every attempted live leg applied (the durable leg having also completed), `user_config_write` otherwise.
- **Partial outcomes are typed, never masked.** Mutation responses carry `liveResults[]` — one entry per attempted live leg (`sessionId` + the Plan-003 runtime-binding leg key) with `outcome: 'applied' | 'failed'` and a sanitized per-leg error code on failure — so a durable-success/live-failure outcome is a **successful response** reporting `applied: 'user_config_write'` plus the failing legs, never a blanket success that hides the live failure and never an error that invites an unsafe retry of a committed write.
- **Claude, enabled overlay:** `mcp.setEnabled` for a Claude binding records the daemon's per-server enabled overlay (Claude Code's configuration has no enabled field; removal would destroy the declaration). The overlay decides whether the server is in the set each session is sent: at the next session start (grade `next_run`), and in running sessions through the next full-set `mcp_set_servers` call (grade `live_reconcile` when every attempted leg applied). `mcp_toggle` is never used: it saves the switch for the whole project, so later sessions start with the server off, and it leaves the server running.
- **Codex, `user`:** the daemon writes user-scope config via `config/batchWrite` (multi-field mutations MUST be batched — one version check, one reload) with `expected_version` from the immediately-preceding `config/read`; on `configVersionConflict` the daemon surfaces `mcp.config_write_conflict` and does not retry. After a successful write the daemon MUST trigger `config/mcpServer/reload` (or per-server `mcpServer/refresh` when scoped to one server). Grade `user_config_write`.
- **Codex, `project`:** Codex accepts config writes to the user file only, so the daemon edits `<project>/.codex/config.toml` itself, with a format-preserving TOML edit that keeps the file's comments and layout. The edit is written to a temporary file and renamed into place only if the file still hashes to what the daemon last read — otherwise `mcp.config_write_conflict`, nothing written — then read back with `config/read {cwd, includeLayers}`, whose project layer must list the server, and followed by `config/mcpServer/reload`. Grade `user_config_write`.
- **Codex, `local`:** Codex has no private per-project layer, so the daemon emulates one: it writes the server into the user file through `config/value/write` with `enabled = false`, and switches it on with the conversation's `enabled` flag at `thread/start` in each session whose project is that one. The name must be unique across the user file; a clash is refused with `mcp.config_invalid` before anything is written, naming the project that holds the other one. The daemon keeps one governance row per emulated binding and removes it with the server. Plain `codex` shows such an entry as switched off in every folder.
- **A `project` declaration is written as typed.** What the person types into a `project` server, values included, is written into the project's file in that provider's own format: `.mcp.json` through `claude mcp add-json --scope project`, and `.codex/config.toml` through the daemon's edit. A declaration may name a variable in place of a value. On Codex, `env_vars`, `env_http_headers` and `bearer_token_env_var` name the variables and Codex reads them itself. On Claude Code the file holds `${VAR}` or `${VAR:-default}`; because a session's servers arrive through the daemon's own `mcp_set_servers` call rather than Claude Code's load of `.mcp.json`, the daemon expands them from the session's spawn environment before sending and holds the expanded value only for that call.
- **Removing a binding ends the approval rules over its tools.** `mcp.removeServer` removes every approval rule whose subject is one of the binding's tools from the provider's file that holds it, in the same transaction, so no permission scoped to the server outlives it ([Spec-010 §Fallback Behavior](./010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).

### Tool-Level Overrides

- `mcp.setToolOverride` / `mcp.clearToolOverride` manage per-`(provider, scope, scopeRef, serverName, toolName)` rows carrying up to three optional facets: `enabled` (allow/deny), `approvalMode` (`auto | prompt | writes | approve` — the Codex-native vocabulary, adopted as the normalized set), `idempotencyClass` (`idempotent | compensable`; absence means the [Spec-004](./004-provider-driver-contract-and-capabilities.md) `manual_reconcile_only` floor). On the page each tool's row reads `On`; `Ask before running` with `Run without asking` · `Ask every time` · `Ask before it writes` · `Ask for approval`, one label per `approvalMode` value in that order; and `If a call is interrupted` with `Safe to run again` · `Can be undone` · `Leave it to a person`, reading `idempotent`, `compensable` and no `idempotencyClass` in that order. Each facet says whether its value is `The server's own` or `Set here`. The inventory entry carries this as `tools`: one reading per tool the server offers, each facet's value in force with its source (`server` or `override`), resolved by the daemon — an unset `approvalMode` reads the provider's default and an unset `idempotencyClass` reads `manual_reconcile_only` — so a client draws them and works none of them out. A facet under an override also carries `serverValue`, the server's own value a clear returns to, so picking `The server's own` sends `mcp.clearToolOverride` naming that one `facet`, and the other facets keep their values. An entry the provider does not use in a project carries `supersededIn`, the project roots where another binding of that name takes its place by the provider's own order, which the page reads as `Not used in <project>: its own <name> takes its place.`
- Enforcement is provider-graded, and the override response reports it **per facet** (see the payload contract): for Codex, `enabled`/`approvalMode` facets are materialized into the native config fields (`enabled_tools` / `disabled_tools` / `tools.<t>.approval_mode`) on write, in the file that holds the binding's declaration — the user file through `config/batchWrite`, a project's `.codex/config.toml` through the daemon's own edit (§Configuration Mutation) — grade `user_config_write`. The **first** facet materialization for a binding snapshots the pre-write native values of these fields as the binding's baseline, and `mcp.clearToolOverride` restores the cleared facet's portions from that baseline — clearing a binding's last facet restores the baseline verbatim and drops it, returning the fields to fully native ownership; a user's own pre-existing native entries always survive a set → clear round-trip; for Claude, the daemon enforces them at its own approval layer (Spec-010 evaluation sees the override before prompting) — grade `daemon_enforced`, effective immediately for subsequent evaluations. An override request MUST carry at least one facet — the request schema rejects a facet-less override at validation, mirroring the DDL's all-NULL row prohibition. The `idempotencyClass` facet is provider-independent and always `daemon_enforced`: it feeds the Spec-004 tool-metadata resolution layer, which its consumers read — consumers never read the override table directly. Override resolution is **binding-keyed**: the Spec-004 metadata layer resolves by `(driver_name, tool_name)`, which cannot disambiguate the same `serverName` bound in two scopes, so the override overlay widens the resolution input with the session's **effective server binding** for the tool's server (the binding in the set the daemon sent that session — the Codex `thread/start` table, the Claude Code `mcp_set_servers` set; the same attribution rule as §Unified Inventory status observations), carried through tool invocation and recovery-receipt resolution, and keys the lookup by the full binding plus `toolName` — two sessions resolving the same tool name from user- and project-scope bindings each get their own scope's override, never the other's.
- Idempotency-class assignment is the **only** governed path off the `manual_reconcile_only` floor ([Spec-004 §Tool Metadata](./004-provider-driver-contract-and-capabilities.md#tool-metadata)): initiated by the person.
- MCP tool **annotations** (`readOnlyHint`, `destructiveHint`, and the rest) are display-only: no daemon decision surface honors them. The MCP spec has a client treat a server's annotations as untrusted unless the server is trusted, and the daemon keeps no trusted-server record ([ADR-014 §References](../decisions/014-v1-feature-scope-definition.md#references)).

### Authorization

- Every non-read operation (`mcp.upsertServer`, `mcp.removeServer`, `mcp.setEnabled`, `mcp.setToolOverride`, `mcp.clearToolOverride`, `mcp.oauthLogin`, `mcp.oauthLogout`, `mcp.reconnect`) is open to this machine's own client or any linked device, and no session: the person's own edits pass no policy check and no ownership refusal. Read operations (`mcp.list`, `mcp.get`, the `mcp.subscribe` stream, and `mcp.registrySearch`) are readable by the person; `mcp.registrySearch` sends the person's search words to the public MCP Registry and nothing else, and writes nothing.
- **Governance mutations — and the receipted operational commands `mcp.oauthLogin` and `mcp.oauthLogout` — are idempotent to the caller (the Spec-004 `clientIdempotencyKey` discipline).** Every such request carries a mandatory requester-generated UUID `clientIdempotencyKey`. The daemon consults the durable `mcp_mutation_receipts` store: a retry with the same key returns the saved result, whatever the second request carries, with **no** provider call or store write (one representation exception: the `mcp.oauthLogin` receipt is stored and returned URL-free — §OAuth Orchestration). Receipts are **two-phase** (the Plan-012 `command_receipts` two-phase discipline): the daemon commits the receipt as a `pending` **intent** (key, operation) in its own transaction **before** any provider leg runs, then finalizes it (`committed`, response recorded) in the **same SQLite transaction** as the mutation's store writes — so the acknowledgment and the saved result are atomic at finalization, and both crash windows around the external provider side effect are closed: a crash before the provider leg leaves a pending intent with no provider effect (startup reconciliation verifies provider state and expires it), while a crash after a durable provider write but before finalization leaves a pending intent whose effect is durable — startup reconciliation observes the provider state, completes the store writes, and finalizes, late but exactly once. An identical-key retry that meets a pending intent drives reconciliation first, then returns the saved result; a lost IPC response or crash-window retry can re-drive only the provider leg (safe by construction: sanctioned provider writes are upserts, full-set replacements, or version-guarded), never a second acknowledgment. Receipts are retry-window dedup: `committed` rows older than 24 hours are pruned opportunistically on later mutation writes; `pending` intents are resolved at startup reconciliation, never silently pruned.
- Of the non-read operations, **the governance mutations** are `mcp.upsertServer`, `mcp.removeServer`, `mcp.setEnabled`, `mcp.setToolOverride` and `mcp.clearToolOverride`, whose receipt finalization and store writes commit in one transaction; none of them appends a governance event. The rest are **operational commands**. **`mcp.reconnect`** changes no daemon store and no provider config, so it carries no governance event — its observable effect is the status notices it induces (leg-addressable: a `bindingId` reconnects one leg, a `sessionId` that session's legs, neither every live leg), and a reconnect attempt that produces no status transition sends none (its failures surface as typed errors on the response). **`mcp.oauthLogin`** starts the daemon's sign-in, whose durable trace — `mcp.server_oauth_completed` — is **asynchronous by nature**: it cannot commit atomically with the launch acknowledgment, and an abandoned sign-in never completes, so the launch is receipted (idempotency) but deliberately not evented. The completion event is emitted **exactly once per completed sign-in** — the daemon's own callback, or the provider's flow finishing in the throwaway home — and an abandoned sign-in, or one ended by a newer attempt, leaves only its expiring receipt. **`mcp.oauthLogout`** removes the daemon's sign-in for the server and mints no event of its own: each leg that was connected on that sign-in sends its `needs-auth` status notice.
- No new approval _category_ is minted: governance mutations are not interactive approval requests, so the [api-payload `ApprovalCategory`](../architecture/contracts/api-payload-contracts.md#shared-enums) union is unchanged; no approval category is MCP-related, since a server's run-time elicitation becomes the session's question card.

### OAuth Orchestration

- **One sign-in per server, the daemon's own ([ADR-038](../decisions/038-mcp-credential-custody.md#decision)).** `mcp.oauthLogin` starts the daemon's own sign-in for that server, whatever kind of server it is, and returns the address of the sign-in page for the client to open. One sign-in and one consent serve the server's tools, resources and prompts on Claude Code and Codex alike, in every account. By default the daemon signs in as its own OAuth client: discovery from the server's protected-resource metadata, client registration by the server's metadata document or by dynamic registration, PKCE, and `resource` set to the server's address. A server whose entry names a client the server's owner issued (Codex's `oauth.client_id` and `oauth.callback_url`) is signed in as that client.
- **A server that admits only Claude Code's or Codex's own client** is signed in through that provider's own flow, run in a throwaway home the daemon makes for that sign-in: Codex's `mcpServer/oauth/login` with `mcp_oauth_credentials_store = "file"`, which needs no ChatGPT sign-in, or Claude Code's own flow in a credential folder of its own. The daemon takes the saved sign-in (the server, the issuer, the client id, the access and refresh tokens, the expiry) into its own item, deletes the home, renews the sign-in under that client id from then on, and hands it to each provider through its header helper like any other signed-in server; Claude Code reaches the server directly, and Codex on the daemon's route, which fronts every server a Codex session reaches (§Long tool calls and the fronted route). It learns which client a server admits before the browser opens wherever the server says so — a refused dynamic registration, or a refusal from the server's pushed-authorization endpoint. Where the server says nothing, the first sign-in opens with the daemon's own client, and when that one does not finish, the next attempt goes through the admitted provider's client. The daemon remembers which client each server admitted, so every later sign-in is one press.
- **A server that demands proof-of-possession (DPoP) tokens**, which neither provider can sign in to, is signed in by the daemon as its own client with a signing key made for that one sign-in — one key per server, never the machine's own control-plane key — kept in the operating system's credential store beside the refresh token. Because a header helper cannot carry a per-request proof, the daemon fronts that server for Claude Code and Codex alike and signs a fresh proof for every request.
- **How the sign-in reaches a provider.** The daemon keeps the refresh token in the operating system's credential store under its own item, never in a file, and renews it itself under the client id it was issued to. Each provider process the daemon launches carries a header helper for each signed-in server — Codex's `http_headers_helper`, Claude Code's `headersHelper` — that asks the daemon over its same-user local socket for a current access token and prints it as the `Authorization` header; the helper's command line carries only a server and session handle, never a credential. Each provider re-runs its helper by itself after a rejected token, so a renewal never reaches the person. The daemon's own MCP client uses the same sign-in to list and read the server's prompts for a Codex session and to hold the connection of every server it fronts. A provider process the daemon did not launch gets nothing. The daemon never reads or renews a sign-in held by the person's own Claude Code or Codex outside the app: a server replaces a public client's refresh token on every renewal, so a second party renewing it signs the first one out.
- **A new attempt ends the waiting one.** `mcp.oauthLogin` on a server whose sign-in is still waiting ends that wait and starts the next attempt, so a refusal page in the browser never holds the person until the flow's timeout.
- **Launch failures are errors; completion failures are events.** `mcp.oauth_flow_failed` is scoped to the **launch phase** — a failure to start the sign-in (discovery, registration, or the provider's own flow in its throwaway home), surfaced on the still-open `mcp.oauthLogin` call. Once the call has returned (the `authorizationUrl` handed to the caller), the JSON-RPC channel for that request is closed by definition, so an asynchronous completion failure is delivered as the completion outcome itself: `mcp.server_oauth_completed` with `outcome: 'failure'` and a sanitized `failureReason`, observable on the `mcp.subscribe` stream and reflected by the server's persisting `needs-auth` status. The daemon never fabricates a late JSON-RPC error for a completed call.
- **Sign-out.** `mcp.oauthLogout {serverId}` deletes the daemon's refresh token for that server, and its signing key where the server demands DPoP tokens, and stops answering the helpers for it, so each provider's next call to that server gets no token; the server reads `needs-auth` in every session on both providers until the next sign-in.
- Tokens, authorization codes, PKCE material and DPoP keys are held only as [ADR-038](../decisions/038-mcp-credential-custody.md#decision) records and are never logged, relayed, shown, or carried by any event, error, receipt, read model, or wire payload; the only durable trace on the governance stream is the `mcp.server_oauth_completed` event, whose payload carries the server identity and outcome, never credentials or URLs with embedded secrets. The idempotency receipt row for `mcp.oauthLogin` follows the same rule: the persisted response omits `authorizationUrl` **structurally** (launch URLs embed single-use PKCE state and are never durable), so an identical-key retry returns a URL-free acknowledgment — the sign-in is already started, completion arrives as the event, and a caller that never received the URL begins a new sign-in under a fresh key. **The launch URL has exactly one carrier: the `mcp.oauthLogin` reply, and no other surface.** It is absent from every durable and every broadcast destination — receipt rows, every event payload, the `mcp.subscribe` stream, errors beyond guidance text, and logs — which is the §Pitfalls destination list applied to this value rather than a carve-out of it, and it is what makes the rule mechanically checkable: one surface asserts presence and every other asserts absence. Each client then consumes it at **one destination and none other** — the CLI prints it as the login command's own **result**, on the stream that command's result belongs on, and the desktop opens it in the browser and holds it as transient render state that is written to no client-side storage, entered into no log, and dropped at settlement. A client that cannot show the URL cannot complete the sign-in at all, so withholding it there would not harden the launch phase but remove it. Tokens, authorization codes, and PKCE material stay prohibited at every one of those surfaces including the reply — the launch URL is a one-shot handle to the server's consent page, and it is the only member of this paragraph that any client ever sees.

### Status Observation and Events

The event type, `mcp_governance` category ([Spec-005 §MCP Governance (`mcp_governance`)](./005-session-event-taxonomy-and-audit-log.md#mcp-governance-mcp_governance)):

| Event | Emission point | Session binding |
| --- | --- | --- |
| `mcp.server_oauth_completed` | The daemon's sign-in settling (its own callback, or the provider's flow finishing in the throwaway home) | Sentinel-bound per [Spec-005 §Daemon-Scope Event Binding](./005-session-event-taxonomy-and-audit-log.md#daemon-scope-event-binding); `initiatingSessionId` when applicable |

- **A status change is a live notice, never an event.** A normalized status transition from either provider feed (Codex `mcpServer/startupStatus/updated` / `mcpServerStatus/list` deltas; Claude init census + `mcpServerStatus()` deltas) or from the daemon's own client for a server it fronts, including the transition to `needs-auth` a sign-out causes, is sent on `mcp.subscribe` as `{type: 'mcp.server_status_changed'}` with the binding's path-free audit ref, its status, and its `origin` (`session_feed` for a session's provider feed or a fronted connection serving that session, `node_probe` for an on-demand probe), and is written to no log. It is sent on transition only. The inventory keeps each leg's latest reading, so a surface that opens later reads it from `mcp.list`; no screen reads past status changes.
- Status observation is event-driven plus on-demand (`mcp.list` refresh); the daemon MUST NOT busy-poll provider status endpoints.
- **`mcp.subscribe` is the live governance stream.** `mcp.subscribe` is a long-lived subscription the person reads (the Plan-005 streaming primitive, the `session.subscribe` consumer shape) delivering each `mcp.server_oauth_completed` envelope as the daemon appends it and each status notice as the daemon sends it. It is live-tail with a **gap-free handshake, not a cursor**: a (re)connecting client opens `mcp.subscribe` first, then reads `mcp.list` — the subscribe acknowledgment precedes the stream's first delivery (the Plan-005 I-005-9 wire-ordering invariant), so registration is live before the snapshot read and an event concurrent with the snapshot arrives on the stream instead of falling between snapshot and subscription (re-observation is harmless — status notices and governance envelopes are re-entrant state updates; omission is impossible). Status keeps no history; sign-in completions remain in the sentinel session's log. The stream also carries a live notice after each edit to a binding, made from this machine or a linked device — an add, a change, a switch on or off, a tool override or a removal — `{type: 'mcp.server_config_changed'}` with the binding's provider, scope, scope reference and server name. The notice is sent live only and written to no session's log, so no audit record of an edit exists; a page showing that binding reads it again with `mcp.get`, and a removed one answers `mcp.server_not_found`. This is how the desktop MCP panel and `sidekicks mcp watch` observe governance without polling and without any per-session transcript merge (sentinel events never enter real sessions' streams — §Domain Dependencies).
- Every event payload and every notice is **credential-free and content-free by construction**: enums, scope identity, and sanitized failure reasons only — no config values, env-var values, header values, tokens, and none of the [Spec-020 §PII Data Map](./020-data-retention-export-and-deletion.md#pii-data-map) durable-tier PII classes (user messages, file paths, code snippets). `failureReason` fields pass the daemon's error-sanitization layer and MUST NOT echo config values or filesystem paths. Binding identity in payloads is the **path-free audit ref**, the binding's `provider`, `scope` and `serverName`: `scopeRef` — a user-specific filesystem path — never enters an event payload or a notice, and the raw path stays resolvable only through the node-local binding store. Status notices with `origin: 'session_feed'` additionally carry the observing leg's `bindingId` — the Plan-003 runtime-binding key, an opaque daemon-minted identifier — so a subscriber can attribute the transition to its `legs[]` entry when one binding backs several legs in the same session (absent on `node_probe` notices, which observe no leg).
- `serverName` / `toolName` are the deliberate residual: free-form identifiers the person or the provider chooses, `wireFreeFormString`-bounded, carried in the audit payload as **non-PII infrastructure identifiers** — the same classification as tool names in `tool_activity` events. The person CAN embed personal data in a name they choose; the identifiers age out of full payloads on the standard [Spec-005 §Event Compaction Policy](./005-session-event-taxonomy-and-audit-log.md#event-compaction-policy) lifecycle. No other free-form config-derived string may enter these payloads.

### The MCP servers page

The governance layer above faces the person by construction, and precisely so: **every** non-read operation is open to this machine's own client or any linked device, and no session; the **governance mutations** among them are receipted and append no event, while among the operational commands `mcp.reconnect` carries no dedicated governance event, `mcp.oauthLogin` is receipted and deliberately not evented, and `mcp.oauthLogout` is receipted and shows through the status notices it causes (§Required Behavior). It is reached through Settings › **MCP servers** in the desktop app. This section states what that surface is bound by; its composition sketch is [Spec-021 §Signature Feature Composition Sketches](021-desktop-app-and-renderer.md#signature-feature-composition-sketches); [Plan-022](../plans/022-mcp-server-configuration-and-governance.md) builds the page's components and their projection in the settings feature's MCP servers page folder (CP-022-5), and [Plan-020](../plans/020-desktop-app-and-renderer.md) owns the Settings frame and its page list, whose `mcp-servers` entry registers the page, and owns nothing inside that folder (CP-020-3).

- **It adds no surface.** The page composes the `mcp.*` operations §Interfaces And Contracts documents — the governance operations, `mcp.registrySearch` for `Browse servers`, and `mcp.oauthLogout` for `Sign out of this server` — and mints no operation, event type, or error code beyond them. A control that would need another new verb is not a control this page ships.
- **Its update channel is `mcp.subscribe`.** Status arrives on the live governance stream and is applied to the row it names, and an edit's notice makes the page read that one binding again, so a server added from a phone appears on an open page at once; the page does **not** poll `mcp.list` on a timer. §Status Observation and Events forbids the daemon to busy-poll provider status endpoints, and a surface that polled the daemon instead would reintroduce the same cost one layer up, with the daemon's own admission control no longer in the way.
- **It is a fail-closed projection of state, and it does not project eligibility at all.** The two are separate. **State** — connection status and per-leg observations, enablement, per-tool overrides and whether a tool's idempotency class is the native baseline or an override the person set — is rendered from what the daemon reports and recomputed **nowhere**. This is the sharpest rule here rather than a restatement of the general one: a tool's effective idempotency class is the daemon's resolution of the driver's floor and the person's own assignment, and the workflow inspector shows the same class read-only, so a renderer that derived one would be a second source of truth beside the person's assignment — and it would be the source no daemon path consults. **Eligibility is different**: no inventory entry and no event payload on this governance layer reports whether a given operation would be permitted for a given binding, and none is minted here, because a supplied eligibility flag would be exactly the daemon-side authorization re-expressed as a renderable field and would drift from the daemon's own decision. So the page projects none: every control is offered, the daemon adjudicates, and the typed refusal renders — which is the same rule as the bullet below, not a competing one. The **one** non-offer is a control whose required input is structurally absent from the entry the daemon served — on the degraded arm §Fallback Behavior serves when the binding store is unreachable, `tools` is absent outright and `enabled` survives only where the provider itself declares it, so the per-tool controls have nothing to act on, while every control whose input **did** arrive is offered exactly as on the normal arm — and that is absence of data rather than a judgment the renderer formed.
- **Configuration content splits three ways, and the split is what makes the page usable without making it a credential surface.** A page that rendered and collected nothing could not register a server at all, and `mcp.upsertServer` takes a declaration the person authors by design. **(1) Input.** The declaration form collects what that mutation accepts: transport, command, arguments, URL, timeouts, the required-server marker, environment-variable and header **names**, and the credential-bearing values the input shape admits. Those values are **write-only in the renderer as well as on the wire** — masked on entry, never read back, never held in serializable renderer state, cleared on submit — the Provider Accounts token-field discipline, applied here for the same reason: the wire rule protects the transport and this protects the screen. **(2) Read-back is exactly `McpServerConfigView` and nothing beyond it.** That view exists so `mcp.get` can serve back what `mcp.upsertServer` wrote — every non-secret field preserved, secret values structurally absent, names without values, the URL query-redacted, drawn under `Environment variables`, `Headers`, `Arguments`, `Address query` over the names of an address's query parameters, and `Token from the environment variable <NAME>` for an address server whose token is read from one — which is what supports an edit workflow without the daemon ever serving credential material. **(3) Never rendered.** Anything the daemon does not serve: environment-variable values, header values, tokens, URL query values. The page does not reach past the daemon to the provider's own config files, which remain the source of truth and are the daemon's to read. The governance **event** payloads stay credential-free and content-free by construction — that property is about the governance stream and is unchanged by anything this page collects or displays.
- **It is the one place a tool server is governed.** A tool server is added, removed, and governed here and nowhere else in the product. The page's sections carry the headings `Where it is set, and what each one reads` and `What each tool is allowed to do`, in sentence case as every Settings section heading is. The page is the server list beside the selected server's detail: the list gives each server its name, its provider, where it applies, in the provider's own terms — `All projects` (user scope), `This project · in the repo` (project scope) or `This project · not in the repo` (local scope), or for a server a plugin declared `From plugin <name>` — and its state. A name set in two places is never merged and never resolved by the page: both rows stand, and the copy a project does not use reads `Not used in <project>: its own <name> takes its place.`, by the order the provider documents — a project's private copy over its shared one, either over the `All projects` one. The page's note reads `The tool servers Claude Code and Codex connect to, and what each is allowed to do. Read live from the background service.` The detail gives, under `Running sessions`, one line per running session that uses the server, `<session> · <state word> · updated <age>`, the session named as the session list names it and never by an id — with none, `No running session uses this server.`, and a reading with no time drawn as its state word alone, `Unknown` carrying a state never reported — and then its controls, `On for runs` first, and with nothing selected it reads `Pick a server on the left to see what it is allowed to do.` The list's first read says it is reading (`Reading the server list…`), and a read that fails says so (`The server list could not be read.`) with `Try again`.
- **A server is added where it applies.** `Add a server` reads under one line `Register a tool server for a provider, in all projects or in one.` Its fields are `Name`, `Provider`, `Where it applies`, `How it runs` (`A command` / `An address`), `Command`, `Arguments`, `Address`, `Start-up timeout` and `Must start for a run to start`, under `A run does not begin until this server is up.`, then `Environment variables` and `Headers` as name-and-value pairs, each pair added by `Add`, which settles with `That name was added. Its value is held only long enough to send and is never read back.` Under the value fields: `Values are stored by the provider and are never shown here again. Type a new one to replace it.` The form is sent by `Add the server` and dropped by `Cancel`, and sending settles with `The server was sent to the background service. Every value typed here was cleared on submit.` `Where it applies` comes after the provider, with the same three choices; the last two add a `Project` chooser over the attached projects. Under Codex at `This project · not in the repo`, one line under the chooser reads `Plain codex shows this server as switched off.`
- **`Browse servers` searches the public MCP Registry.** It sits beside `Add a server`, searches only when the person types, and says under its field where the words go: `Searches the public MCP Registry. Anyone can publish there; check a server's source before adding it.` Each result reads its title or name, its description, its version, and whether it runs as a package or is reached at an address. Picking one opens the declaration form filled in — the name, how it runs with its command and arguments or its address, each environment variable's name and description with the required ones marked — and leaves every value and the add to the person.
- **Five words, one vocabulary.** A server's state is drawn in one of five words — `Connected`, `Starting`, `Needs sign-in`, `Failed`, `Unknown` — one word per `McpServerStatus` value. Every other surface that says what a tool server is doing uses those same five words read from this same inventory, the session composer's tool-server chip among them: it lists that session's servers, links here to manage them, and is the only place inside a session that names them. There is never a second inventory.
- **Every per-tool value says where it came from.** The three per-tool facets — whether the tool is on, whether it asks before running, and what happens if a call is interrupted — are each optional, each shown per tool, and each says whether the value in force is the server's own or one set here. The page works none of that out for itself.
- **Reconnect asks, and claims nothing.** Asking the provider to open the connection again is offered on the selected server whatever its state and is drawn first on one reading `Failed`. It writes nothing and changes no setting, and it says so: `This asks for the connection again. It changes nothing that is set here.`, then `Asking for the connection again…` while it runs. A try that moves no state reads `Nothing changed. The server is still Failed.` rather than reading as success.
- **Sign-in is one control and one consent, and leaves nothing behind.** `Sign in to this server` starts the daemon's own sign-in for that server (§OAuth Orchestration) — for every kind of server, one that admits only Claude Code's or Codex's own client and one that demands DPoP tokens included — and settles in place with `The sign-in for that server opened in the default browser.`, or reads `Sign-in did not finish.` It stays pressable while a sign-in waits: a press ends that wait and starts the next attempt. The address the flow opens with is held only while it is used, written to no storage and no log, and dropped when the sign-in settles. Once signed in, `Sign out of this server` stands where `Sign in to this server` stood; it forgets the sign-in at once, and the server then reads `Needs sign-in`.
- **A command that cannot run says so.** After the background service moves between Windows and a WSL distribution, a server whose command or arguments name a program on the side it left reads `Failed`, one of the state words, and its selected view carries one line: `Its command names a program the background service cannot run. Edit its command.` The line names no side.
- **A missing reading says it is missing.** Where the degraded arm leaves the per-tool controls without an input, the page says so in place — `Per-tool settings cannot be read right now. Those controls are not drawn because the reading they act on did not arrive; everything else on this page is offered exactly as usual.` — rather than leaving the absence unexplained. Where `On for runs` is missing too, the line names both: `` `On for runs` and the per-tool settings cannot be read right now. Those controls are not drawn because the reading they act on did not arrive; everything else on this page is offered exactly as usual. ``
- **A change says when it takes effect.** Every mutation the page sends settles in place with one line for the application grade it answered (§Configuration Mutation): `live_reconcile` reads `Applied to running sessions.`, `user_config_write` `Saved to <Provider>'s settings. New sessions use it.`, `next_run` `Saved. The next session uses it.`, and `daemon_enforced` `In force now.` While a change is on its way it reads `Sending…` under its control, only after the session's short delay, until it settles. Each live session the change failed on adds `<session> is still running with the old setting.`, the session named as the session list names it. No grade or outcome value reaches the screen.
- **Removing a server confirms in place.** `Remove <server>? It stops being offered to <Provider>. Nothing it wrote is touched.` under `Cancel` and `Remove`.
- **Nothing configurable is drawn as nothing.** A provider with no tool servers set up says so in words, one line per provider with none: `No tool servers are set up for Claude Code.` With both empty the lines stand in place of the list, and with one empty its line sits in quiet text at the list's foot. A server whose reading lists no tools reads `No tools listed for this server.` in place of its tool rows. An empty list is never drawn as though nothing could be configured.
- **One wire mutation per explicit action by the person, and refusals render.** No control batches, retries on the person's behalf, or pre-filters itself to hide an action the daemon would refuse. A refused action is refused before any write and the refusal is shown, because the person learning the rule from the system that enforces it is worth more than a control that quietly disappears — and a pre-filter would be a re-derivation of exactly the authorization this spec places in the daemon.

### Required-Server Semantics

- A Codex server with `required = true` that fails to initialize fails the thread start/resume; the daemon MUST map that failure onto the run-failure path with an actionable error naming the server, and send its `failed` status notice — the run failure is never silent or attributed to the provider generically.

### Long tool calls and the fronted route

A tool call that runs long moves to the background on both providers: after 120 s, or at once when a message arrives, the model is told the call keeps running under a task id and goes on working, and the result comes into the conversation when the call ends, starting a new turn if none is running.

- **Claude Code does it itself.** The daemon starts every Claude Code process with `CLAUDE_AUTO_BACKGROUND_TASKS=1`, so an MCP call still running after 120 s, or one running when a new message arrives, moves to the background: the model gets a tool result naming the task id and goes on, and when the call ends Claude Code's task notification starts a turn if none is running. Claude Code runs MCP Tasks itself and restores them on resume. The daemon reads `task_started` with `task_type: "mcp_task"` and the completion's `resource_links` off the stream and draws the call as a tool row that stays running until the task ends, and the notification as that row's result, never as a message from the person. The same switch moves a foreground helper to the background after 120 s. A plain call moved to the background ends with the process, and after a restart its row reads `Stopped when the app restarted`.
- **On Codex the daemon fronts every server it can reach.** Codex has no MCP Tasks and cannot move a call to the background, so the conversation's `thread/start` table carries every server as a `url` entry on the daemon's route under the server's own name, and the model sees the same server and tool names. The daemon's own MCP client holds the real connection: it starts a stdio server itself, one copy per conversation, as Codex would, or connects to an address, reading the declaration's environment and header values from the provider's config only for that connection.
- **The route answers a long call with a handle.** It answers a call normally when it ends within 120 s. Past 120 s, or when the daemon steers the conversation while the call runs, it answers Codex's pending call with Claude Code's own handle text — `Tool "<tool>" is still running after <N>s. It was moved to the background as task <id> and keeps running; you'll receive a notification with the result when it completes. You can keep working in the meantime. To stop it, call task_stop with task_id "<id>".` — and the call keeps running in the daemon's client. The route offers tools of its own:
  - `task_output {task_id, wait_seconds?}` returns the task's status and, once it ends, its result, waiting at most 10 s;
  - `task_stop {task_id}` cancels it: `tasks/cancel` for a task-augmented call, `notifications/cancelled` for a plain one.
- **Delivery.** When the call ends, the daemon delivers `MCP task <id> (<server>/<tool>) completed.` with the result — by `turn/steer` into a running turn, or `turn/start` into an idle conversation, and to a helper a Codex agent started, which takes no direct input, at its next tool call as added context from the daemon's post-tool hook, or as the continuation the helper-finish hook (`SubagentStop`) returns as it finishes — and draws it as the tool row's result. The client makes a call task-augmented wherever the tool allows one, writes the `taskId` to the command receipt before answering anything else, polls with Claude Code's figures (every 2 s by default, honoring the server's `pollInterval` held between 100 ms and 60 s, halting after 10 failures in a row with the handle kept), and marks the receipt `delivered` once the result is delivered, so a result that arrives after a daemon restart is delivered once. After a restart it resumes every receipt with a handle to a server reached at an address; a stdio server's task ends with the daemon.
- **What the route applies.** Codex's per-tool approval for a fronted server is applied on the route from the session's permission level and the server's `tools.<t>.approval_mode`. A request the server sends back is handed on: an elicitation becomes the session's question card, and a progress notice the row's progress line. A server behind a sign-in is fronted on the daemon's own sign-in (§OAuth Orchestration), including one whose sign-in the daemon took over from a provider's flow.
- **On Claude Code only a DPoP server is fronted.** Claude Code reaches a server that demands proof-of-possession tokens on the daemon's route, which signs a proof for every request, and a long call there takes the daemon's own MCP Tasks handling with Claude Code's figures.
- **The workflow MCP-tool step** calls a tool with MCP `tools/call` through the same client, task-augmented where the tool allows one.
- **Budget.** The route adds at most 5 ms to a fronted call against a direct one. While a call is in the background: one `tasks/get` per poll interval for a task-augmented call and nothing for a plain one; one model turn per delivery into an idle conversation. A fronted stdio server costs one copy of that server per Codex conversation (about 50 MB), the process Codex would otherwise start. At `Sandboxed` a wrapped server adds no Node process of its own: on Codex at most the native `codex sandbox` process, and on Claude Code the operating system's sandbox launcher and a share of the daemon's one network proxy; both are measured against the same server unwrapped when the wrap is built.

### A session's own tool servers

- **A session starts with exactly the servers switched on for it**, through the provider's own means (§Provider Capability Model), and a server that is off costs the model no tool definitions.
- **Its list is read, never recomputed.** `session.mcpServerList {sessionId}` is a live list of the servers the session was started with, each drawn from this spec's inventory: the working servers first by name alone, then the ones that are not working, each with `Needs sign-in` or `Failed` and the reason, the failed ones last; a server still starting, or one whose state is unknown, sits with the working ones until it says otherwise. The list carries no reconnect, no sign-in and no tool list; those are the MCP servers page's.
- **A per-session switch only narrows.** `session.mcpServerUpdate {sessionId, serverName, enabled}` turns one server off or on for this session alone: off stops the session offering that server's tools to the agent, so none of its definitions reach the model and none of its tokens are spent. Settings, every other session and every future session are untouched, and a new session starts with every server on. A switch applies at the next turn — on Claude Code another full-set `mcp_set_servers` call, which ends a switched-off server's process and removes its tools from the next turn with no restart and nothing written to disk; on Codex the conversation's `enabled` flag at its next turn — and one flipped mid-turn says so rather than changing anything under the run. The daemon keeps a session's switches with the session and sends its set again after each resume. The switch is not a governance mutation and emits no governance event.
- **At `Sandboxed`, the person's own tool servers run in the session's sandbox.** A stdio server the session starts at `Sandboxed` runs inside the same sandbox as the session's commands, through each provider's own sandbox engine: it writes only where those commands write — the worktree and the repository's git folder, whose `hooks` and `config` stay closed — the curated credential paths stay unreadable to it, and it reaches the hosts the person's own provider settings give those commands. On Codex the daemon's own client starts the server under Codex's own `codex sandbox --permission-profile <the session's profile> --cd <the worktree>`, run from `@openai/codex`'s native binary, so the per-repository profile the session runs under binds the server too, network included. On Claude Code the daemon links Anthropic's `@anthropic-ai/sandbox-runtime`, the library Claude Code's own sandbox is built on, as a library, never through its npm launcher, and each stdio entry it sends with `mcp_set_servers` runs the wrapped command the library returns: the session's writable roots and their closed paths, the curated credential paths denied for reading, and the hosts Claude Code itself would allow and deny — every settings source's `sandbox.network` domains merged with its `WebFetch(domain:…)` allow rules, managed sources alone where `allowManagedDomainsOnly` is set. The library's network proxy runs in the daemon, one for every wrapped server. A host outside those lists is refused with no card, since nothing asks at `Sandboxed`. A server at an address starts no process on the machine and is reached as at every level. The same rule holds for a workflow step that runs at `Sandboxed`, since a step runs at its run's level. A write the sandbox refuses fails that tool call with the server's own error, and one refused while the server starts shows as its `Failed` reason in the session's list. Where the wrap cannot start on the machine, the run is refused like any `Sandboxed` run whose sandbox cannot start ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)). Below `Sandboxed` nothing changes: the asking levels ask, and `YOLO` runs every server as the provider would.
- **Resources.** `session.mcpResourceList {sessionId, serverName}` lists what a working server offers, so the person can stage one in the composer's attachment row; on Codex the read goes through `mcpServer/resource/read`.
- **Prompts.** A working server's prompts appear as a group under its name in the session's command list, the provider-commands subscription [Spec-004](./004-provider-driver-contract-and-capabilities.md) owns; on Codex the daemon lists and reads them through its own client, on its own sign-in where the server needs one, over the connection that client already holds for the server, so listing prompts never starts a second copy of it.

## Default Behavior

- New servers are enabled per provider config, with no tool overrides (provider defaults + `manual_reconcile_only` idempotency floor).
- `mcp.list` serves the merged inventory from the most recent observations without forcing a provider round-trip; `refresh: true` forces one.
- Claude mutations attempt the live path on every installed build and settle the grade on the outcome of the daemon's own full-desired-set reconcile; callers never select the mechanism, only observe the returned grade.
- A status notice is sent on transition only — an unchanged status re-observation sends nothing.

## Fallback Behavior

- **A Claude Code session that refuses `mcp_set_servers`**: the daemon gives a session its tool servers with `mcp_set_servers` right after start, again after each resume, and after each change, never with `mcp_toggle` and never by restarting the session. A session that refuses the call (the CLI refuses control requests from a session it treats as cloud-hosted, and a non-streaming-input session cannot carry them at all) gets its servers no other way: each of that session's servers reads `Failed`, with the refusal as the server's reason, the way Settings › MCP servers draws a command the service cannot run. A configuration change made meanwhile is still written through `claude mcp add-json --scope` and answers with grade `user_config_write`; that session's live set does not change. The refusal is read from the call's own answer, never from a version comparison or a driver-side probe.
- **Codex write conflict:** a `configVersionConflict` surfaces `mcp.config_write_conflict` with both version tokens so the caller can re-inspect, with no retry: one press is one change.
- **Codex project file changed since it was read:** the edit is not renamed into place and the write refuses with `mcp.config_write_conflict`; the file is left as it was.
- **Status source unavailable** (provider down, or the status probe refused on the running build): inventory serves `unknown` with an `observedAt` timestamp; the daemon does not fabricate `connected`/`failed`.
- **Sign-in did not finish:** `mcp.server_oauth_completed` carries `outcome: 'failure'`, the server keeps reading `needs-auth`, and the next `mcp.oauthLogin` starts a new attempt — through the admitted provider's client where the daemon's own client was not admitted (§OAuth Orchestration).
- **Binding store unavailable** (storage failure): governance reads degrade to the **degraded entry arm** — a discriminated `bindingStoreUnavailable: true` variant whose store-dependent fields (`tools`, the Claude enabled overlay) are structurally absent rather than fabricated, with provider-observed fields (config view, status, legs) intact; all mutations fail closed.

## Interfaces And Contracts

- **IPC operations** (JSON-RPC per [ADR-009](../decisions/009-json-rpc-ipc-wire-format.md); registered in the Plan-005 `MethodRegistry` at Plan-022's tier per the `presence.*` late-namespace precedent): `mcp.list`, `mcp.get`, `mcp.subscribe`, `mcp.upsertServer`, `mcp.removeServer`, `mcp.setEnabled`, `mcp.setToolOverride`, `mcp.clearToolOverride`, `mcp.oauthLogin`, `mcp.oauthLogout {serverId}`, `mcp.reconnect`, and `mcp.registrySearch {query, cursor?}` answering `{servers, nextCursor?}` from the public MCP Registry's `GET /v0/servers?search=<query>&version=latest`, caching nothing past the page. Requests address the scope-qualified binding (`scopeRef` structurally required for `project`/`local` and forbidden for `user`, on both providers — a schema-level discriminated union, not a service-layer check); `mcp.upsertServer` and `mcp.removeServer` take `scope` and `scopeRef`; every governance mutation — and `mcp.oauthLogin` and `mcp.oauthLogout` — carries the mandatory `clientIdempotencyKey` (`mcp.reconnect` is unreceipted); `mcp.upsertServer` carries the fully-typed `McpServerConfigInput` union; mutation responses carry application grades (per-facet for overrides) plus per-leg `liveResults[]`; an entry reading `failed` because its command cannot run after a move carries `failedReason: commandNotRunnable`. Typed request/response mirrors live in [API Payload Contracts §Plan-022 — MCP Governance Contract Surfaces](../architecture/contracts/api-payload-contracts.md#plan-022--mcp-governance-contract-surfaces).
- **A session's servers** (§A session's own tool servers): `session.mcpServerList {sessionId}` (a live list; each row the server's name, binding, status with its reason, whether it is on for the session, and whether a switch waits for the next turn), `session.mcpServerUpdate {sessionId, serverName, enabled}`, and `session.mcpResourceList {sessionId, serverName}`; typed mirrors in the same api-payload section.
- **Tools the fronted route adds** (§Long tool calls and the fronted route): `task_output {task_id, wait_seconds?}` and `task_stop {task_id}`, visible to a Codex model and to a Claude Code model on a fronted DPoP server, never on screen.
- **Events and notices**: the `mcp.server_oauth_completed` type above and the two live notices on `mcp.subscribe` (`mcp.server_status_changed`, `mcp.server_config_changed`); payload mirrors in the same api-payload section; category registration in Spec-005; contracts-package registration via Plan-004 T1.9.
- **Errors**: the `mcp.*` code registry in [Error Contracts §MCP Governance](../architecture/contracts/error-contracts.md#mcp-governance) — the codes narrated across §Required Behavior plus `mcp.server_not_found` for the unknown-binding outcome every operation surface shares.

- **Versioning**: operation payloads follow [ADR-017](../decisions/017-cross-version-compatibility.md) cross-version compatibility rules; no provider version is compared or refused, and each capability is resolved by its own declared detection mechanism against the running build per the provider-wire trust model.

## State And Data Implications

- **New daemon-local tables** (node-scoped; DDL in [Local SQLite Schema §MCP Governance Tables (Plan-022)](../architecture/schemas/local-sqlite-schema.md#mcp-governance-tables-plan-022)): `mcp_server_bindings` (scope-qualified binding identity, an emulated Codex `local` binding among them, the native-tool baseline, and the Claude enabled overlay — no key material and no credential), `mcp_tool_overrides` (per-tool facets, FK-cascaded to the binding row), `mcp_mutation_receipts` (the idempotency receipt store — key, operation, saved response; pruned on age, never part of the audit trail), and `mcp_server_admitted_clients` (which client each signed-in server admitted — the daemon's own, Claude Code's or Codex's — kept once per provider and server name rather than on each binding, and kept after a sign-out, so every later sign-in is one press; not a credential).
- **No provider-config mirroring**: provider files remain the config source of truth at every scope — including for Claude, whose durable declarations live in the provider's own stores (written only through `claude mcp add-json --scope`) and whose session set is sent through `mcp_set_servers` from those declarations plus governance overlays, never an independent daemon-owned server set. The daemon persists only governance state (overlays, overrides, a session's own switches) and derives inventory on read; an acknowledged mutation survives daemon restart because the provider store holds it.
- **The operating system's credential store** holds, per signed-in server, the daemon's refresh token and, for a server that demands DPoP tokens, its signing key, each under an item the daemon created and removed with the sign-in ([ADR-038](../decisions/038-mcp-credential-custody.md)); on Windows, native and WSL alike, each is written through the service's Windows half at `CRED_PERSIST_LOCAL_MACHINE`, and none ever enters SQLite.
- **Events**: every settled sign-in appends through the Plan-004 `EventLogService` path and is rebuilt like every other category; status transitions are sent live and written to no log. Node-scoped events bind to the daemon-scope sentinel session per [Spec-005 §Daemon-Scope Event Binding](./005-session-event-taxonomy-and-audit-log.md#daemon-scope-event-binding).
- **Rebuild/recovery impact**: none. An idempotency class the person assigns says whether a call to the tool may safely be repeated, and recovery never branches on it: a daemon restart re-runs no command whatever its class ([Spec-013 §In-Flight Receipts After A Restart](./013-persistence-and-recovery.md#in-flight-receipts-after-a-restart)). Assignment stays the person's own act because it is the only path off the `manual_reconcile_only` floor.

## Example Flows

- `Example: live server add on Claude` — the person calls `mcp.upsertServer` (provider `claude`, scope `user`); the daemon persists the declaration via `claude mcp add-json linear <json> --scope user` and verifies the write; on a streaming-input session the daemon additionally computes the full desired named-server set and calls `setMcpServers` — that call is itself the availability answer, not a probe of it — reconciling `{added: ["linear"], removed: [], errors: []}`; it upserts the binding row for the `(claude, user, "", linear)` binding, sends the status notices (`starting` → `connected`), and returns the inventory entry with grade `live_reconcile`. Had that reconcile been refused, the same call would return `user_config_write` with the declaration already durable.
- `Example: Codex write conflict` — two of the person's devices race `mcp.setEnabled`; the second write's `expected_version` is stale, so it answers `mcp.config_write_conflict` with both version tokens and writes nothing; the page shows the refusal, and the person presses again against the new version.
- `Example: one sign-in, both providers` — the person presses `Sign in to this server` on `notion`; `mcp.oauthLogin` → the daemon discovers the server's authorization server, registers itself, and returns the sign-in page's address; the desktop opens it in the browser; the person consents once; the daemon's callback completes, the refresh token goes into the credential store under the daemon's own item, and the daemon emits `mcp.server_oauth_completed` (`outcome: 'success'`). A Claude Code session's `headersHelper` and a Codex session's fronted connection both get a current access token from the daemon, and each leg flips `needs-auth` → `connected`; the Codex session's command list gains the server's prompts. `mcp.oauthLogout` later deletes the token and every leg reads `needs-auth`.
- `Example: a server saved with the repository` — the person adds `postgres` for Claude Code at `This project · in the repo` for project `app`, typing its `DATABASE_URL` value, then adds it again for Codex, since each add registers a server for one provider; the daemon writes `app/.mcp.json` through `claude mcp add-json … --scope project` for the first and, for the second, edits `app/.codex/config.toml` in place, reads it back with `config/read`, and reloads; each file holds the value as typed. Sessions in `app` get the server; sessions elsewhere do not. A `.mcp.json` server that arrived with a pull joins the project's sessions like any other switched-on server.

## Implementation Notes

- **Re-verify at execution.** Every provider mechanism above is Verified at the versions the [provider-wire reference](../reference/provider-wire/README.md) records, or version-anchored beyond them (`mcp_set_servers` at `2.1.210` — an **upstream feature anchor**, far older than any build this project measured); Plan-022 code MUST check load-bearing shapes against the installed binaries before binding. Re-verification is **detection against the running build**, not a version comparison: [Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior) binds each capability to its own declared mechanism — a zero-turn, non-mutating, granularity-decisive probe where one is admissible, and a declared `static` reading naming the failing conjunct where none is — precisely because a version bounds availability from neither side. `mcp_set_servers` is not a capability flag at all — it is a control-request subtype no driver-side probe may issue — so its live answer comes from the reconcile itself, and a refusal there withdraws no flag.
- **Codex per-conversation configuration.** A conversation's `thread/start` configuration takes `mcp_servers`: a whole table replaces the service's table for that conversation, and the dotted form `mcp_servers.<name>` merges with it. The daemon sends the whole table, each server a `url` entry on its route, enabled or not — the per-session mechanism on Codex, never a flag on the shared service.
- **MCP revision watch.** The MCP 2026-07-28 revision restructures the protocol core (stateless core, Tasks → extension, Roots/Sampling/Logging deprecated); both providers will absorb it in their own releases. The governance layer binds to _provider surfaces_, so there the revision lands as provider-behavior changes caught by the re-verify rule; the daemon's own client takes it through its MCP client library, re-verified the same way.
- **The daemon's own MCP client** is `@modelcontextprotocol/client` 2.3.0, the one maintained MCP client that signs DPoP proofs; `@modelcontextprotocol/sdk` stays in the daemon only to host Playwright's tool server. The client implements the provider's `discoveryState` and `saveDiscoveryState`, which bind a sign-in's callback to its authorization server. It serves the fronted route, Codex's prompt list over the connection it already holds for the server, so listing prompts never starts a second copy of it, the workflow MCP-tool step and the recovery sweep of task handles.
- **Claude Code session set.** The daemon drives `claude mcp add-json` / `claude mcp remove` at the binding's `--scope` as the durable-write mechanism. Each session's process starts with `--strict-mcp-config`, so nothing the project, the account or a plugin configures loads by itself, and only the daemon's own tool entry rides `--mcp-config`; right after start the daemon sends the session's set with `mcp_set_servers`, built from every scope's switched-on bindings plus governance overlays, less the session's own switched-off servers and any server the person rejected in Claude Code, and sends it again after each resume, because the set lives only in the process's memory. Determinism means the session sees exactly the set the daemon sent, immune to mid-run ambient drift, while ambient edits (the person using the provider's own CLI directly) flow into the next send and the inventory. Because the daemon, not Claude Code's load of `.mcp.json`, supplies the set, Claude Code's own approval prompt for a repository's servers never runs, and `${VAR}` references in a `project` declaration are expanded by the daemon before sending (§Configuration Mutation).
- **Transient-secret handling.** The custody model for credential-bearing values in provider-owned files is transient-by-construction: parse the provider-owned file in memory, use the values for the one purpose that read them, discard — the values are never persisted, logged, served, or embedded in any payload.
- **The fronted connection's secrets.** To reach a server it fronts, the daemon starts it with the environment values its declaration holds, or connects with its headers, reading those values from the provider's config when it connects and holding them only in memory for that connection; they are never stored or logged. The same transient rule covers the `${VAR}` values the daemon expands for a Claude Code session's set, held only for that `mcp_set_servers` call.

## Pitfalls To Avoid

- **Writing the Codex project file blind.** Codex rejects project paths for its own config writes, so the daemon edits `.codex/config.toml` itself; an edit that is not format-preserving, not guarded by the file's hash, or not read back through `config/read` can destroy the repository's own comments or land a server Codex never loads.
- **Using `mcp_toggle`.** It saves "off" for the whole project, so later sessions start with the server off, and it leaves the server running; a switch is always another full-set `mcp_set_servers` call.
- **Renewing a sign-in someone else holds.** A server rotates a public client's refresh token on every renewal, so renewing a sign-in the person's own Claude Code or Codex holds signs that provider out; the daemon renews only sign-ins it holds.
- **Collapsing scope bindings.** Two scopes declaring the same `serverName` are different configurations with independent status and overrides; folding them into one node-global identity bleeds one scope's overrides into the other.
- **Honoring annotation self-claims.** A server saying `readOnlyHint: true` is data, not authorization; no decision surface reads annotations (the ADR-014 MUST — stable MCP-spec language since 2025-03-26).
- **Delta-sending `setMcpServers`.** The call replaces the full named-server set; sending a delta silently removes every unsent server. Always send the full desired set.
- **Treating `--help` as the capability census.** The Claude CLI's `--help` omits real flags; capability detection reads the pinned binary and the provider-wire reference, and treats `--help` as a lower bound ([Claude wire §The `--help` is non-authoritative rule](../reference/provider-wire/claude.md#the---help-is-non-authoritative-rule)).
- **Echoing secrets.** Config values, env vars, headers, tokens, authorization URLs, and URL query-string values never enter events, inventory reads, errors beyond guidance messages, or logs; `bearer_token_env_var` names an env var — the _name_ may appear in inventory, the _value_ is read only for a fronted connection and never stored or served; a server URL round-trips query-redacted (parameter names only — §Unified Inventory), and a user name or password in it, accepted as typed, never round-trips.
- **Erroring after the durable leg committed.** A mutation whose durable leg has committed MUST NOT surface a later live-leg failure as a JSON-RPC error — the caller would retry a write that already landed. Committed-then-degraded outcomes are successful responses with honest `applied` grades and per-leg `liveResults[]`; `mcp.config_invalid` exists strictly pre-commit.
- **Polling provider status.** Both providers push (notifications / feed emissions); polling is on-demand-only.

## Acceptance Criteria

- [ ] At `Sandboxed`, a person's own stdio tool server writes only where the session's commands write, cannot read a curated credential path, and reaches only the hosts the person's own provider settings give those commands — on both providers.
- [ ] `mcp.list` merges all four sources and round-trips both providers' declared servers with correct `(provider, scope, scopeRef, serverName)` binding separation — same-named servers in two scopes surface as distinct entries whose status and overrides never cross
- [ ] Claude mutation persists through `claude mcp add-json --scope <scope>` before acknowledgment and survives a daemon restart (the restarted daemon's inventory and the next session's `mcp_set_servers` set both contain it); on a reachable control channel the same call additionally applies live and returns grade `live_reconcile`, otherwise `user_config_write`
- [ ] Codex mutation writes user scope with `expected_version`, triggers reload, and surfaces `mcp.config_write_conflict` on a conflict with no retry
- [ ] A `project` write lands on both providers — `<project>/.mcp.json` through `claude mcp add-json --scope project` and `<project>/.codex/config.toml` through the daemon's edit with its comments and layout intact and its project layer listing the server on `config/read` — and a `local` write lands in the project's entry in `~/.claude.json` and, on Codex, as a switched-off user entry switched on only in that project's sessions; a Codex project file changed since the daemon read it refuses with `mcp.config_write_conflict`, file unchanged; a value typed at `project` scope lands in each file as typed, in that provider's format; an `enabled` or `approvalMode` facet on a Codex `project` binding lands in that project's `.codex/config.toml`
- [ ] Every switched-on binding joins a session's set at every scope — a `project` binding that came with the repository among them, present in the Claude Code `mcp_set_servers` set and enabled in the Codex `thread/start` table
- [ ] Binding refs are structurally valid at the schema layer: `scopeRef` rejected for `user` scope and required non-empty for `project`/`local` on both providers — each as a typed validation error, never a database constraint failure; the DDL CHECKs mirror the same rules as defense in depth
- [ ] No Claude Code process is ever sent `mcp_toggle`; a session switch reaches the process as a full-set `mcp_set_servers` call applied from the next turn, and a new session starts with every server on
- [ ] `mcp.get` returns the redacted `McpServerConfigView` round-tripping every non-secret field `mcp.upsertServer` accepted (transport, command/args, the query-redacted URL plus its query-parameter names, timeouts, `required`, `bearerTokenEnvVar`, the Codex auth references, env-var and header **names**) with zero secret values anywhere in the response, and an update leaves unmodeled provider fields byte-identical — a `?api_key=…` URL serves scheme + host + path with `api_key` listed by name and its value absent; per-leg `legs[]` surfaces divergent concurrent-session statuses that the top-level aggregate `status` ranks deterministically (`unknown` legs included, per the fixed order), each `session_feed` status notice carries its leg's `bindingId`, and a terminated session's leg retires — its last status (a `failed` included) no longer participates in the aggregate
- [ ] Retrying a governance mutation with the same `clientIdempotencyKey` returns the saved result, whatever the second request carries, with no second provider call or store write, verified across a daemon restart; a crash between the durable provider write and receipt finalization reconciles at startup (the store writes complete exactly once — late, never lost, never doubled); the `mcp.oauthLogin` receipt row and the acknowledgment it returns contain no `authorizationUrl`
- [ ] A Claude durable-success/live-failure mutation returns success with `applied: 'user_config_write'` and a per-leg `liveResults[]` failure entry — never a JSON-RPC error after the durable commit, and never an unreported live failure
- [ ] One `mcp.oauthLogin` and one consent let a Claude Code session (through `headersHelper`) and a Codex session (through the fronted connection) reach the server and list its prompts on Codex; a server that admits only one provider's client is signed in through that provider's flow in a throwaway home that is deleted afterward, and the daemon renews it under that client id; a DPoP server is reached from both providers with a proof on every request; `mcp.oauthLogout` deletes the refresh token (and the DPoP key) and every leg on both providers reads `needs-auth` on its next call; a sign-in held by the person's own provider outside the app is never read or renewed; no token, code, PKCE value or key appears on any event, error, log, receipt, read model, wire payload, renderer state or helper command line
- [ ] An asynchronous sign-in completion failure is delivered as `mcp.server_oauth_completed` with `outcome: 'failure'` on the `mcp.subscribe` stream (never a late JSON-RPC error); `mcp.oauth_flow_failed` remains reachable via a launch-phase failure; a second `mcp.oauthLogin` while a sign-in waits ends the first
- [ ] On Codex a fronted call past 120 s, or one running when the daemon steers the conversation, is answered with the handle text, `task_output` and `task_stop` work on it, its result is delivered once by `turn/steer` or `turn/start`, or on a Codex helper by the post-tool hook's added context or the `SubagentStop` continuation — once across a daemon restart for a task-augmented call — and the route adds at most 5 ms to a fronted call; on Claude Code a call past 120 s and a foreground helper past 120 s each move to the background under `CLAUDE_AUTO_BACKGROUND_TASKS=1`
- [ ] `mcp.registrySearch` returns results only for a typed query, fills the declaration form with names and no values, and keeps nothing past the page
- [ ] After a move between Windows and a WSL distribution, a server whose command names a program on the side the service left reads `failed` with `failedReason: commandNotRunnable`, and a bare command name is looked up on the new side
- [ ] The subscribe-then-list handshake is gap-free: an event appended between a subscriber's `mcp.subscribe` acknowledgment and its subsequent `mcp.list` read is delivered on the stream, and the stream delivers nothing appended before the acknowledgment
- [ ] First observation of an unknown server creates its binding row
- [ ] Removing a binding removes every approval rule over its tools from the provider's file that holds it, in the same transaction
- [ ] An `idempotencyClass` the person assigns reaches the Spec-004 tool-metadata resolution output; absent assignment resolves to `manual_reconcile_only`; resolution is binding-keyed — with the same `serverName` bound in two scopes, each session's invocation resolves its own effective binding's override, never the other scope's
- [ ] A Codex binding whose user config already carries native `enabled_tools` / `disabled_tools` / `tools.<t>.approval_mode` values survives an override set → clear round-trip with those native values restored from the baseline
- [ ] With the binding store unavailable, `mcp.list` / `mcp.get` serve the degraded entry arm (`bindingStoreUnavailable: true`; store-dependent fields structurally absent, provider-observed fields intact) and every governance mutation fails closed
- [ ] No governance mutation appends a governance event; status transitions are live notices written to no log, session-feed ones carrying the leg's `bindingId`; `mcp.server_oauth_completed` is emitted exactly once per observed flow completion — an abandoned flow emits nothing and leaves only its expiring receipt; `mcp.reconnect` emits no governance event beyond the status transitions it induces
- [ ] Event and error payloads contain no config values, tokens, env-var values, or unsanitized paths — raw `scopeRef` included: no event payload carries the path (schema-level test over every payload type and error code)
- [ ] Every `mcp.*` error code is reachable in integration tests and absent from success paths
- [ ] A governance mutation succeeds identically from this machine's own client over the local pipe and from a linked device over the relay, with no policy check and no ownership refusal
- [ ] The MCP servers page renders connection status and effective idempotency class wire-verbatim and recomputes none of them; it renders no **withheld** value — no environment-variable value, header value, URL query value, or token — while still rendering the daemon's redacted `McpServerConfigView` read-back, so the non-secret declaration (transport, command and arguments, timeouts, the required marker, names without values, the query-redacted URL) can be inspected and edited as §The MCP servers page's read-back split and Plan-022 T28.5.7 both require; it updates from `mcp.subscribe` rather than by polling; and each explicit action by the person produces exactly one wire mutation, with a daemon refusal rendered rather than pre-filtered away
