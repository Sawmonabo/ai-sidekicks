## Purpose

This spec defines V1 feature #15 ([ADR-014 §Decision](../decisions/014-v1-feature-scope-definition.md#decision)): how the local runtime daemon configures, governs, and observes **MCP servers** attached to each installed provider's CLI (today `claude` and `codex`). Each provider is an MCP client of its own. The daemon runs one MCP client of its own as well: it holds the real connection for every server it fronts — every server a Codex session reaches, and on Claude Code and Codex alike a server that demands proof-of-possession tokens — lists and reads a server's prompts for Codex, and serves the workflow MCP-tool step. What the daemon owns is the **governance layer** above those connections:

1. A **unified server inventory** — one normalized read model across the providers' divergent config surfaces.
2. **Configuration mutation** — add / update / remove / enable / disable servers at every scope on every provider, through each provider's own write mechanism where one exists and, where none does, through a format-preserving edit written only while the file is as the daemon last read it; never by blind config-file rewriting.
3. **Tool-level overrides** — per-(server, tool) enable/disable, approval-mode, and idempotency-class assignment, feeding the [Spec-004](./004-provider-driver-contract-and-capabilities.md) tool-metadata resolution layer.
4. **OAuth sign-in** — one daemon-held sign-in per server that needs one, used by every provider and by the daemon's own client, held and removed as [ADR-038](../decisions/038-mcp-credential-custody.md) records.
5. **Status observation** — normalizing each provider's server-status feed onto the Spec-004 `McpServerStatus` enum, each transition sent live on `mcp.subscribe` and written to no log.
6. **Events** — every settled sign-in emits a canonical event in the `mcpGovernance` category ([Spec-005 §MCP Governance (`mcpGovernance`)](./005-session-event-taxonomy-and-audit-log.md#mcp-governance-mcpgovernance).

## Scope

- The `mcp.*` IPC operation namespace on the daemon control surface, and the session operations over a session's own servers (`session.mcpServer.subscribe`, `session.mcpServer.enabled.update`, `mcp.resource.list`).
- Normalized server inventory merging provider-declared config, live provider status, the daemon binding store, and the daemon override store.
- Provider-specific mutation engines at every scope: Claude Code's `claude mcp add-json --scope` writes plus live reconcile; the Codex user-config CRUD + reload pair, the daemon's own format-preserving edit of a project's `.codex/config.toml`, and the emulated Codex `local` scope.
- The `mcp_server_bindings`, `mcp_tool_overrides`, `mcp_mutation_receipts`, and `mcp_server_admitted_clients` SQLite tables (daemon-local, machine-scoped).
- Every governance mutation is open to this machine's own client or any linked device, and no session, with no policy check and no ownership refusal.
- The `mcp.*` event types and their payloads, session binding, and sanitization rules.
- The daemon's own OAuth sign-in per server, its custody under [ADR-038](../decisions/038-mcp-credential-custody.md), and sign-out.
- The daemon's own MCP client and the route that fronts servers for Codex (and for a proof-of-possession server on Claude Code), with a long call moving to the background on Claude Code and on Codex.
- A search of the public MCP Registry that fills the declaration form.

## Non-Goals

- **The daemon runs one MCP client of its own; a provider's own connections stay the provider's.** The client holds the real connection for every server the daemon fronts — every server a Codex session reaches, and on Claude Code only a server that demands proof-of-possession tokens (§Long tool calls and the fronted route) — and adds no governance of its own: the route carries the server's overrides and approval fields to the provider and the provider decides, as it would on a direct connection (§Long tool calls and the fronted route). A server a provider reaches directly stays that provider's connection end to end. The daemon separately **hosts** an MCP server of its own: the callback-tool host of [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior), through which daemon-authored tools reach a run. That host sits outside this spec's governance model because the daemon authors it rather than the person declaring it: it is never override-governed, and its tools are governed by the specs that author them (Cedar authorization and the spec's own opt-in).
- **No credential custody beyond [ADR-038](../decisions/038-mcp-credential-custody.md).** The daemon holds MCP-server credentials exactly as that record states: one sign-in per server, the refresh token and any proof-of-possession signing key in the operating system's credential store under the daemon's own items, and access tokens only in its own memory, for its own client, which fronts every signed-in server for the provider processes it launched, so no provider holds one. It never reads or renews a sign-in the person's own Claude Code or Codex holds, and no credential reaches an event, error, log, read model, wire payload, or the renderer. Credential-bearing values in provider-owned config (env-var and header values) are handled **transiently in memory** only — by the provider's own write mechanism, by the `${VAR}` expansion of a Claude Code session's server set, and by the fronted route's connection — then discarded; they never reach storage, events, errors, logs, or any read model (§Implementation Notes — transient-secret handling). The machine-local provider-account plane is [ADR-026](../decisions/026-provider-credential-custody-posture.md)'s and nothing here widens it.
- **No config-store ownership.** Provider config files (`~/.claude.json` scopes, `$CODEX_HOME/config.toml`, project-local `.codex/config.toml`, `.mcp.json`) remain provider-owned and are the source of truth the daemon observes, not a mirror it maintains. The daemon writes them through each provider's own mechanism where one exists — `claude mcp add-json --scope` on Claude Code, `config/value/write` / `config/batchWrite` for the Codex user file — and where none exists, a project's `.codex/config.toml`, through a format-preserving edit that keeps the file's comments and layout, is written only while the file is as the daemon last read it, and is read back through `config/read` before it counts (§Configuration Mutation).
- **No installing on the person's behalf.** A search of the public MCP Registry fills the declaration form; the person still adds the server and types every secret value, and the daemon keeps nothing from a search past the page.
- **No session-scoped permission-matrix extension.** Governance belongs to this machine's own client or any linked device, and no session, deliberately outside the session permission matrix ([Security Architecture §Permission Matrix](../architecture/security-architecture.md#permission-matrix)). The session-facing MCP surfaces are a session's own server list with its per-session switch, which only narrows what governance allows (§A session's own tool servers), the resource pick and the server prompts in the session's command list, and a server's request for input, which becomes the session's question card — none of them a governance mutation.

## Required Behavior

### Provider Capability Model

Each provider exposes MCP configuration, status, and auth surfaces through mechanisms of its own, and each driver binds to its provider's: the table below names Claude Code's and Codex's, and a provider added brings its own column through its driver, while the shared governance layer names none. Which transports and declaration fields a provider takes is its driver's declaration, carried in `provider.list`, so the declaration form checks against it as the person types and the daemon checks the request again, refusing a transport or field the provider does not declare with `mcp.server.configInvalid` before anything is written. Per the capability-parity principle (all provider capabilities integrate at V1; asymmetries are normalized, emulated, or degraded honestly — never silently dropped), the daemon binds to each mechanism natively and grades what each application path can deliver:

| Capability | Claude Code mechanism | Codex mechanism |
| --- | --- | --- |
| Declare servers for a session | `--strict-mcp-config`, or the start the build's probe settles (§Implementation Notes), so nothing the project or the account configures loads by itself; the session's servers sent with the `mcp_set_servers` control request right after start (about 0.1 s) and again after each resume, because the set lives only in the process's memory; only the account's claude.ai connectors ride `--mcp-config`, which `mcp_set_servers` leaves in place, and the daemon's own tool server is an in-process server named in `initialize`'s `sdkMcpServers`, and every full-set `mcp_set_servers` send names it and every server the daemon fronts as `{"type": "sdk", "name": …}` entries, because Claude Code removes each in-process server a set leaves out (§Implementation Notes); on a machine whose organization deployed `managed-mcp.json`, neither flag (§Implementation Notes) | The conversation's own configuration at `thread/start`: the whole `mcp_servers` table, which replaces the service's table for that conversation, each server a `url` entry on the daemon's route under its own name and each enabled or not (§Long tool calls and the fronted route), the table also holding the daemon's own `sidekicks` and `sidekicks_hooks` entries, with the hook rows and their trust records in the same `config` ([Spec-026 §The definition registry](./026-agent-definitions-and-peer-invocation.md#the-definition-registry)) |
| Change a live session's server set | Another full-set `mcp_set_servers` call, applied from the next turn — SDK `setMcpServers(servers)` returning `{added, removed, errors}`; streaming-input mode only; each set names every in-process server, since one a set leaves out is removed | The conversation's per-server `enabled` flag, reaching it at its next turn where the provider honors it |
| Mutate durable config | `claude mcp add-json` / `claude mcp remove` with `--scope user`, `--scope project` (run from the project root; writes `<project>/.mcp.json`) or `--scope local` (writes the project's entry in `~/.claude.json`) — the provider's own store stays the durable home; the daemon never rewrites those bytes itself | `user`: `config/value/write` / `config/batchWrite` with `expected_version` optimistic concurrency on `$CODEX_HOME/config.toml`; `project`: the daemon's own format-preserving edit of `<project>/.codex/config.toml`, read back with `config/read`; `local`: emulated, an entry in the user file with `enabled = false` switched on per conversation in that project's sessions |
| Server status | Init census `mcp_servers[]` + `mcpServerStatus()` SDK query + the `mcp_set_servers` reply's `errors`, each a direct connection, and for an in-process server the daemon fronts, the daemon's own client's connection; for the machine probe, a probe process sent the bindings' set and asked `mcp_status` (§Default Behavior) | For a fronted server, the daemon's own client's connection to it; for the machine probe, `mcpServerStatus/list` on a probe thread (§Default Behavior) |
| Per-server reconnect | SDK `reconnectMcpServer()` | The daemon's client reconnecting the fronted server |
| Enable/disable | The daemon's per-server enabled overlay decides whether the server is in the set sent with `mcp_set_servers` (the daemon's own overlay, never Claude Code's `disabledMcpServers`, which `/mcp` writes for the whole project; removal would destroy the declaration); `mcp_toggle` (`toggleMcpServer()`) is never used, because it saves the switch for the whole project and leaves the server running | `enabled` field write + reload; per conversation, the `enabled` flag in the `thread/start` table |
| Tool allow/deny + approval mode | Daemon-enforced (no native per-tool config field; the daemon's approval layer enforces overrides) | Native config fields: `enabled_tools` (allow), `disabled_tools` (deny, applied after allow), `default_tools_approval_mode` (`auto`\|`prompt`\|`writes`\|`approve`), `tools.<t>.approval_mode`; for a fronted server they ride its `url` entry, which at `YOLO` carries `default_tools_approval_mode = "approve"` unless the binding sets its own, and Codex decides |
| OAuth sign-in | The daemon's own sign-in (§OAuth Orchestration), the server fronted by the daemon as an in-process (`type: "sdk"`) server; for a server that admits only Claude Code's client, Claude Code's own flow (the `mcp_authenticate` control request) run in a credential folder the daemon makes for that sign-in | The daemon's own sign-in, used by the daemon's client for every fronted server; for a server that admits only Codex's client, `mcpServer/oauth/login` run in a throwaway home with `mcp_oauth_credentials_store = "file"` |
| Long tool call | `CLAUDE_AUTO_BACKGROUND_TASKS=1`: a call still running after 120 s, or one running when a message arrives, moves to the background, and the same switch moves a foreground helper to the background after 120 s; Claude Code runs MCP Tasks itself | No MCP Tasks and no backgrounding; the daemon's route answers a long call with a background handle and delivers the result (§Long tool calls and the fronted route) |
| Prompts | Claude Code lists a server's prompts itself | Codex never asks a server for its prompts; the daemon's client lists and reads them on the daemon's sign-in |
| Required-server gating | Not native; daemon surfaces failed servers via status | `required = true` ⇒ `thread/start` / `thread/resume` FAIL if the server cannot initialize |

Every mutation response MUST carry an **application grade** — `liveReconcile` (applied to the running session's live server set), `userConfigWrite` (persisted to the provider's own config store, effective for subsequent runs/threads), `nextRun` (daemon-recorded governance state applied to the next session's server set), or `daemonEnforced` (enforced immediately at the daemon's own decision layer) — so callers know _when and where_ the change takes effect. Degradation is honest and typed, never silent: a Claude mutation that cannot reconcile live succeeds with the grade its durable path actually achieved, not an error and not a fake `liveReconcile`.

### Unified Inventory

- The daemon MUST expose one normalized inventory (`mcp.server.list` / `mcp.server.read`) merging four sources per server binding: (1) provider-declared configuration (parsed from the provider's own config surfaces), (2) live provider status normalized onto `McpServerStatus` (`unknown | starting | connected | needsAuth | failed` per [Spec-004](./004-provider-driver-contract-and-capabilities.md) — the api-payload `McpServerStatus` union), (3) the daemon binding row, (4) the daemon tool-override rows. Each entry carries a **redacted normalized config view** (`McpServerConfigView`) — transport, command/args, the **query-redacted URL** (scheme + host + path; the address is taken as typed and passed to the provider as typed, a user name or password in it included, and that user name and password and the query component are credential-equivalent write-only material, so neither is ever read back: the view serves the query **parameter names** instead, the same names-not-values discipline as env vars and headers), timeouts, `required`, `bearerTokenEnvVar`, the Codex auth references (`envHttpHeaders` — a header-name → env-var-**name** map — plus `oauthScopes` and `oauthResource`), and the **names** of env vars and headers, never their values — so `mcp.server.read` can read back what `mcp.server.upsert` wrote and the person can inspect provider state without the daemon ever serving credential material (`command`/`args` are process-visible strings the person authors, the same residual class as the identifiers in §Status Observation and Events).
- Server identity is the scope-qualified **binding** `(provider, scope, scopeRef, serverName)` — scope is `user` (Claude user scope in `~/.claude.json`; Codex `$CODEX_HOME/config.toml`), `project` (Claude `.mcp.json`; Codex `.codex/config.toml` in the project; `scopeRef` = the canonical project root), `local` (Claude's project-keyed private scope; on Codex the emulated scope — an entry in the user file switched on per conversation in that project's sessions, its name unique across that file; `scopeRef` = the canonical project root), `plugin` (a server an installed plugin declares in its `.mcp.json`, read from the daemon's plugin home for that provider; `scopeRef` = the plugin's name), and on Claude Code two scopes Claude Code brings itself: `connector` (a claude.ai connector, "automatically available in Claude Code" on a claude.ai subscription login; `scopeRef` = the provider account's id, since connectors are that account's own; `serverName` = the display name Claude Code reports, such as `claude.ai Slack`) and `managed` (a server the organization provides through `managedMcpServers`, which "ranks above all" scopes, or deploys in `managed-mcp.json`; no `scopeRef`, served with its address's host only, as Claude Code shows it) (<https://code.claude.com/docs/en/mcp>, §Use MCP servers from claude.ai and §Scope hierarchy and precedence; <https://code.claude.com/docs/en/managed-mcp>, §Provide servers through managed settings); `scopeRef` is the empty string for `user` and `managed`. On Codex, `managed` is a server an administrator layer declares: the two legacy managed files, which rank above the person's and the project's files, list as read-only `managed`; the `packagedDefaults`, `mdm`, `system` and `enterpriseManaged` layers, which rank below them, list as `managed` too, reading Codex's merged value, which Codex folds field by field, with `supersededIn` naming the person's or the project's settings file whose entry overrides them; the launch's own `sessionFlags` layer lists nothing. The per-conversation switches the daemon sends ride that `sessionFlags` layer, which ranks below the two legacy managed files, so a legacy file that sets a server's `enabled` itself wins over the daemon's switch for that server. A `connector` or `managed` binding is read-only: it takes no edit and no removal; its tool overrides, allow or deny per tool, stay available as on any server, and it is switched off or on per project, the daemon's own switch, kept in `mcp_project_server_switches` ([MCP Governance Tables](../architecture/schemas/local-sqlite-mcp-governance-tables.md)), as `/mcp` allows one per project. A plugin's server is listed as `From plugin <name>` and joins a session only when switched on for it; its declaration belongs to the plugin and changes when the plugin is updated or removed. Two scopes legitimately declaring the same `serverName` with different configurations are **distinct bindings** with independent status and overrides — collapsing them would bleed overrides across configurations. The inventory MUST NOT merge same-named servers across providers or across scopes into one logical entry.
- Same-name shadowing across scopes is surfaced, not resolved away: both bindings appear in the inventory, and the provider's own scope precedence decides which one a session gets; the page names the copy a project does not use (§The MCP servers page). Every binding that is switched on joins a session's runs, at every scope on every provider: one the person added, and one that came with the repository; a server the person rejected in Claude Code stays out, and so does one Claude Code's own `/mcp` switched off for that project: `/mcp` "records your choice per project in `~/.claude.json`" as `disabledMcpServers` (<https://code.claude.com/docs/en/mcp>, §Disable a server without removing it), which the daemon reads from the person's own `~/.claude.json`, and the entry carries `disabledIn`, those project roots, so the page reads `Off in <project>` beside its state, dimmed, once per project.
- Provider states outside the normalized enum map deterministically: Claude `pending` → `starting`; Claude `disabled`, and Codex's `disabled` for a server that conversation's configuration switches off, turn off that session's row in `session.mcpServer.subscribe` only: the leg keeps its last status but leaves the aggregate, and the inventory entry's `enabled` stays the binding's own switch (Codex's `enabled` from `config/read`, or the daemon's overlay for Claude Code and plugins); a Claude Code per-project off also shows in `disabledIn`, as above; absence of any status source → `unknown`, honestly. Provider status feeds report server names, not bindings; the daemon MUST attribute each observation to the binding that is effective for the observing context (the set the daemon sent that session). For a server the daemon fronts, its own client holds the connection, so that client's connection is the observation, and Codex's own status feed, which then observes the route, is not read for it; and a server whose sign-in the daemon holds reads `needsAuth` from the daemon's own sign-in state.
- On a Windows computer with WSL, a stdio server a provider starts for a session in a WSL 2 distribution runs in that distribution, and a bare command name such as `npx` is looked up there. A server whose command or arguments name a Windows program cannot run there: it is kept as it was and, for sessions in that distribution, reads `failed`, each such session's leg carrying `failedReason: commandNotRunnable`, the leg's session naming the distribution ([Spec-006 §The service on a Windows computer](./006-local-ipc-and-daemon-control.md#the-service-on-a-windows-computer)). This is one member on the leg, not a new status. A `project` or `local` binding's `scopeRef`, the root of `mcp.server.enabled.update`'s per-project switch, and each root `supersededIn` and `disabledIn` list carry `place?`, the WSL 2 distribution the root is in, its path in Linux form there, so one path in two distributions is two roots; `supersededIn` and `disabledIn` are unique lists of `{path, place?}`.
- A config binding and a **live provider leg** are different grains: one binding can back several concurrent sessions' connections at once, and the Plan-003 status seam keys every session-feed observation by the runtime-binding leg (`sessionId` + the Plan-003 `bindingId`). The inventory MUST NOT collapse divergent leg states into one overwritten scalar: each entry exposes the per-leg observations (`legs[]` — leg identity, status, `observedAt`) alongside a deterministic top-level aggregate `status` — the most severe current live-leg status under the fixed severity order `failed > needsAuth > unknown > starting > connected` (`unknown` is a valid live-leg status — a leg whose observation source is lost; lost observability outranks states known healthy, but never a concrete failure), falling back to the newest machine-probe observation when no live leg exists, and to `unknown` when there is no observation source at all. Legs are **live-session observations with a bounded lifecycle**: when a leg's backing runtime binding closes (session end, driver exit), the daemon retires the leg, recomputes the aggregate and sends `mcp.server.status.changed` with `origin: 'sessionEnded'`, the session and the leg, and the recomputed aggregate as `status`, so an open page drops that leg and reads nothing again — a terminated session's last observation never pins the aggregate (a `failed` leg of a closed session does not hold the server at `failed` while every live session is `connected`); with no live legs remaining, the aggregate falls back per the order above. A leg is one running session's connection, so the page reads one line per running session that uses the server, never one per place.
- First observation of a binding the binding store has never seen MUST upsert its binding row — the anchor its enabled overlay and tool overrides hang from.

### Configuration Mutation

- Mutations (`mcp.server.upsert`, `mcp.server.delete`, `mcp.server.enabled.update`) target a binding and MUST route through the mechanism for its provider and scope, per the capability table above. `mcp.server.upsert` and `mcp.server.delete` take `scope` (`user` | `project` | `local`) and `scopeRef` (the project root) on every provider, and every one of those scopes is writable on each; a `plugin` binding takes `mcp.server.enabled.update` and tool overrides, and its declaration changes only with the plugin. **Upserts are read-modify-write over the provider's own declaration**: provider fields the normalized input does not model — or does not carry — are preserved, never erased (Codex user writes are field-granular `config/value` paths touching only carried fields; the project-file edit changes only that server's own table; the regenerated Claude declaration starts from the observed current one), so a typed read/edit round-trip can never silently destroy provider configuration outside the governed surface.
- **Every operation applies to a binding at any scope.** A Codex `project` binding is written through the daemon's own edit of the project's `.codex/config.toml`, its tool-override facets included (§Tool-Level Overrides).
- **A running session picks up a change without a restart, with one exception.** After a write the daemon sends Claude Code the reload request, so hooks, the tool-server file and output styles are live for the session's next turn, and a changed agent definition reaches the session by a `--resume` at its next idle moment, because the agents map Claude Code takes at start is fixed for the process's life; on the headless path that request does not apply a change to a plugin's tool server, so such a change lands at the provider's next start and the session's flow row says one is waiting. On Codex a skill is live at once, and a new or edited definition needs the lead's conversation forked on the running server with its history intact, the flow row reading that definitions were reloaded.
- **Validation precedes commitment.** Schema validation and every check that can fail the mutation outright run **before** the durable leg commits — `mcp.server.configInvalid` is exclusively a pre-commit refusal. Once the durable leg has committed, the mutation never converts to a thrown error: later per-leg live failures are reported inside the successful response (below), so a caller can never be induced to retry a mutation that already committed.
- **Claude, durable leg (unconditional):** every `mcp.server.upsert` / `mcp.server.delete` persists to the provider's own store at the binding's scope via Claude Code's own command (`claude mcp add-json <name> <json> --scope <scope>` / `claude mcp remove <name> --scope <scope>`, a `project` or `local` write run with the project root as the working folder) **before** the mutation is acknowledged — an acknowledged mutation survives daemon restart because the provider's store, not daemon memory, is the durable home. The daemon MUST verify the write took effect (re-read via `claude mcp get` / observation of that scope) before emitting the config event.
- **Claude, live leg (opportunistic):** in a streaming-input session (the live leg is selected by the outcome of the daemon's own full-desired-set `setMcpServers` call, never by a version comparison and never by a driver-side probe: Spec-004 declares this flag non-probeable because an empty-set probe would clear the session's servers, so the first full-set send **is** the detection and its refusal selects the fallback; streaming-input mode remains a reachability precondition), the daemon additionally applies the mutation live via `setMcpServers` and MUST reconcile the returned `{added, removed, errors}` against the requested delta. The call replaces the set the daemon last sent and leaves in place only what `--mcp-config` passed, which is the account's claude.ai connectors, and removes each in-process server the set leaves out, so the full set names the `sidekicks` server and every fronted server as `sdk` entries; a plugin's servers are kept out by `--strict-mcp-config` and sent by the daemon like any other server switched on for the session — so the daemon MUST always send the full desired set, never a delta. The response grade reports the most immediate application achieved: `liveReconcile` when every attempted live leg applied (the durable leg having also completed), `userConfigWrite` otherwise.
- **Partial outcomes are typed, never masked.** Mutation responses carry `liveResults[]` — one entry per attempted live leg (`sessionId` + the Plan-003 runtime-binding leg key) with `outcome: 'applied' | 'failed'` and a sanitized per-leg error code on failure — so a durable-success/live-failure outcome is a **successful response** reporting `applied: 'userConfigWrite'` plus the failing legs, never a blanket success that hides the live failure and never an error that invites an unsafe retry of a committed write.
- **Claude, enabled overlay:** `mcp.server.enabled.update` for a Claude binding records the daemon's own per-server enabled overlay, never Claude Code's `disabledMcpServers`, which `/mcp` writes for the whole project; removal would destroy the declaration. The overlay decides whether the server is in the set each session is sent: at the next session start (grade `nextRun`), and in running sessions through the next full-set `mcp_set_servers` call (grade `liveReconcile` when every attempted leg applied). `mcp_toggle` is never used: it saves the switch for the whole project, so later sessions start with the server off, and it leaves the server running.
- **Codex, `user`:** the daemon writes user-scope config via `config/batchWrite` (multi-field mutations MUST be batched — one version check, one reload) with `expected_version` from the immediately-preceding `config/read`; on `configVersionConflict` the daemon surfaces `mcp.server.configWriteConflict` and does not retry. After a successful write the daemon MUST trigger `config/mcpServer/reload`; Codex has no per-server reload. Grade `userConfigWrite`.
- **Codex, `project`:** Codex accepts config writes to the user file only, so the daemon edits `<project>/.codex/config.toml` itself, with a format-preserving TOML edit that keeps the file's comments and layout. The edit is written to a temporary file and renamed into place only if the file still hashes to what the daemon last read — otherwise `mcp.server.configWriteConflict`, nothing written — then read back with `config/read {cwd, includeLayers}`, whose project layer must list the server, and followed by `config/mcpServer/reload`. Grade `userConfigWrite`.
- **Codex, `local`:** Codex has no private per-project layer, so the daemon emulates one: it writes the server into the user file through `config/value/write` with `enabled = false`, and switches it on with the conversation's `enabled` flag at `thread/start` in each session whose project is that one. The name must be unique across the user file; a clash is refused with `mcp.server.configInvalid` before anything is written, naming the project that holds the other one. The daemon keeps one governance row per emulated binding and removes it with the server. Plain `codex` shows such an entry as switched off in every folder.
- **A `project` declaration is written as typed.** What the person types into a `project` server, values included, is written into the project's file in that provider's own format: `.mcp.json` through `claude mcp add-json --scope project`, and `.codex/config.toml` through the daemon's edit. A declaration may name a variable in place of a value. On Codex, `env_vars`, `env_http_headers` and `bearer_token_env_var` name the variables and Codex reads them itself. On Claude Code the file holds `${VAR}` or `${VAR:-default}`; because a session's servers arrive through the daemon's own `mcp_set_servers` call rather than Claude Code's load of `.mcp.json`, the daemon expands them from the session's spawn environment before sending and holds the expanded value only for that call.
- **Removing a binding ends the approval rules over its tools.** `mcp.server.delete` removes every approval rule whose subject is one of the binding's tools from the provider's file that holds it, in the same transaction, so no permission scoped to the server outlives it ([Spec-010 §Fallback Behavior](./010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).

### Tool-Level Overrides

- `mcp.toolOverride.update` / `mcp.toolOverride.clear` manage per-`(provider, scope, scopeRef, serverName, toolName)` rows carrying up to three optional facets: `enabled` (allow/deny), `approvalMode` (`auto | prompt | writes | approve` — the Codex-native vocabulary, adopted as the normalized set), `idempotencyClass` (`idempotent | compensable`; absence means the [Spec-004](./004-provider-driver-contract-and-capabilities.md) `manualReconcileOnly` floor). On the page each tool's row reads `On`; `Ask before running` with `Run without asking` · `Ask every time` · `Ask before it writes` · `Ask for approval`, one label per `approvalMode` value in that order; and `If a call is interrupted` with `Safe to run again` · `Can be undone` · `Leave it to a person`, reading `idempotent`, `compensable` and no `idempotencyClass` in that order. Each facet says whether its value is `The server's own` or `Set here`. The inventory entry carries this as `tools`: one reading per tool the server offers, each facet's value in force with its source (`server` or `override`), resolved by the daemon — an unset `approvalMode` reads the provider's default and an unset `idempotencyClass` reads `manualReconcileOnly` — so a client draws them and works none of them out. A facet under an override also carries `serverValue`, the server's own value a clear returns to, so picking `The server's own` sends `mcp.toolOverride.clear` naming that one `facet`, and the other facets keep their values. An entry the provider does not use in a project carries `supersededIn`, the project roots where another binding of that name takes its place by the provider's own order, a plugin's server or a connector counting as the same server when it points at the same address or command (<https://code.claude.com/docs/en/mcp>, scope precedence), which the page reads as `Not used in <project>: its own <name> takes its place.`
- Enforcement is provider-graded, and the override response reports it **per facet** (see the payload contract): for Codex, `enabled`/`approvalMode` facets are materialized into the native config fields (`enabled_tools` / `disabled_tools` / `tools.<t>.approval_mode`) on write, in the file that holds the binding's declaration — the user file through `config/batchWrite`, a project's `.codex/config.toml` through the daemon's own edit (§Configuration Mutation) — grade `userConfigWrite`. The **first** facet materialization for a binding snapshots the pre-write native values of these fields as the binding's baseline, and `mcp.toolOverride.clear` restores the cleared facet's portions from that baseline — clearing a binding's last facet restores the baseline verbatim and drops it, returning the fields to fully native ownership; a user's own pre-existing native entries always survive a set → clear round-trip; for Claude, the daemon enforces them at its own approval layer (Spec-010 evaluation sees the override before prompting) — grade `daemonEnforced`, effective immediately for subsequent evaluations. An override request MUST carry at least one facet — the request schema rejects a facet-less override at validation, mirroring the DDL's all-NULL row prohibition. The `idempotencyClass` facet is provider-independent and always `daemonEnforced`: it feeds the Spec-004 tool-metadata resolution layer, which its consumers read — consumers never read the override table directly. Override resolution is **binding-keyed**: the Spec-004 metadata layer resolves by `(provider_name, tool_name)`, which cannot disambiguate the same `serverName` bound in two scopes, so the override overlay widens the resolution input with the session's **effective server binding** for the tool's server (the binding in the set the daemon sent that session — the Codex `thread/start` table, the Claude Code `mcp_set_servers` set; the same attribution rule as §Unified Inventory status observations), carried through tool invocation and recovery-receipt resolution, and keys the lookup by the full binding plus `toolName` — two sessions resolving the same tool name from user- and project-scope bindings each get their own scope's override, never the other's.
- Idempotency-class assignment is the **only** governed path off the `manualReconcileOnly` floor ([Spec-004 §Tool Metadata](./004-provider-driver-contract-and-capabilities.md#tool-metadata)): initiated by the person.
- MCP tool **annotations** (`readOnlyHint`, `destructiveHint`, and the rest) are display-only: no daemon decision surface honors them. The fronted route still passes each tool's annotations through unchanged, because Codex reads them itself to decide whether a call under `auto` asks, and a route that dropped them would make Codex ask even for a tool its server marks read-only ([Codex wire reference](../reference/provider-wire/codex.md#tool-server-approvals-approve-and-the-chatgpt-connectors)); passing a server's own words on to the provider is not the daemon honoring them. The MCP spec has a client treat a server's annotations as untrusted unless the server is trusted, and the daemon keeps no trusted-server record ([ADR-014 §References](../decisions/014-v1-feature-scope-definition.md#references)).

### Authorization

- Every non-read operation (`mcp.server.upsert`, `mcp.server.delete`, `mcp.server.enabled.update`, `mcp.toolOverride.update`, `mcp.toolOverride.clear`, `mcp.server.signIn`, `mcp.server.signOut`, `mcp.server.reconnect`) is open to this machine's own client or any linked device, and no session: the person's own edits pass no policy check and no ownership refusal. Read operations (`mcp.server.list`, `mcp.server.read`, the `mcp.subscribe` stream, and `mcp.registry.search`) are readable by the person; `mcp.registry.search` sends the person's search words to the public MCP Registry and nothing else, and writes nothing.
- **Governance mutations — and the receipted operational commands `mcp.server.signIn` and `mcp.server.signOut` — are idempotent to the caller (the Spec-004 `clientIdempotencyKey` discipline).** Every such request carries a mandatory requester-generated UUID `clientIdempotencyKey`. The daemon consults the durable `mcp_mutation_receipts` store: a retry with the same key returns the saved result, whatever the second request carries, with **no** provider call or store write (one representation exception: the `mcp.server.signIn` receipt is stored and returned URL-free — §OAuth Orchestration). Receipts are **two-phase** (the Plan-012 `command_receipts` two-phase discipline): the daemon commits the receipt as a `pending` **intent** (key, operation) in its own transaction **before** any provider leg runs, then finalizes it (`committed`, response recorded) in the **same SQLite transaction** as the mutation's store writes — so the acknowledgment and the saved result are atomic at finalization, and both crash windows around the external provider side effect are closed: a crash before the provider leg leaves a pending intent with no provider effect (startup reconciliation verifies provider state and expires it), while a crash after a durable provider write but before finalization leaves a pending intent whose effect is durable — startup reconciliation observes the provider state, completes the store writes, and finalizes, late but exactly once. An identical-key retry that meets a pending intent drives reconciliation first, then returns the saved result; a lost IPC response or crash-window retry can re-drive only the provider leg (safe by construction: sanctioned provider writes are upserts, full-set replacements, or version-guarded), never a second acknowledgment. Receipts are retry-window dedup: `committed` rows older than 24 hours are pruned opportunistically on later mutation writes; `pending` intents are resolved at startup reconciliation, never silently pruned.
- Of the non-read operations, **the governance mutations** are `mcp.server.upsert`, `mcp.server.delete`, `mcp.server.enabled.update`, `mcp.toolOverride.update` and `mcp.toolOverride.clear`, whose receipt finalization and store writes commit in one transaction; none of them appends a governance event. The rest are **operational commands**. **`mcp.server.reconnect`** changes no daemon store and no provider config, so it carries no governance event — its observable effect is the status notices it induces (leg-addressable: a `bindingId` reconnects one leg, a `sessionId` that session's legs, neither every live leg), and a reconnect attempt that produces no status transition sends none (its failures surface as typed errors on the response). **`mcp.server.signIn`** starts the daemon's sign-in, whose durable trace — `mcp.server.signIn.completed` — is **asynchronous by nature**: it cannot commit atomically with the launch acknowledgment, and an abandoned sign-in never completes, so the launch is receipted (idempotency) but deliberately not evented. The completion event is emitted **exactly once per completed sign-in** — the daemon's own callback, or the provider's flow finishing in the throwaway home — and an abandoned sign-in, or one ended by a newer attempt, leaves only its expiring receipt. **`mcp.server.signOut`** removes the daemon's sign-in for the server and mints no event of its own: each leg that was connected on that sign-in sends its `needsAuth` status notice.
- No new approval _category_ is minted: governance mutations are not interactive approval requests, so the [api-payload `ApprovalCategory`](../architecture/contracts/api-payload-contracts.md#shared-enums) union is unchanged; no approval category is MCP-specific: Codex's own approval of a tool-server call is a `toolExecution` ask, as Claude Code's ask for a tool-server tool is, and a server's own run-time elicitation becomes the session's question card.

### OAuth Orchestration

- **One sign-in per server, the daemon's own ([ADR-038](../decisions/038-mcp-credential-custody.md#decision)).** `mcp.server.signIn` starts the daemon's own sign-in for that server, whatever kind of server it is, and returns the address of the sign-in page for the client to open. One sign-in and one consent serve the server's tools, resources and prompts on Claude Code and Codex alike, in every account. By default the daemon signs in as its own OAuth client: discovery from the server's protected-resource metadata, client registration by the server's metadata document or by dynamic registration, PKCE, and `resource` set to the server's address. A server whose entry names a client the server's owner issued (Codex's `oauth.client_id` and `oauth.callback_url`) is signed in as that client. A server that publishes no sign-in route — no protected-resource or authorization-server metadata, or metadata the daemon cannot read — is refused on the open `mcp.server.signIn` call with `mcp.server.signInUnsupported`.
- **A server that admits only Claude Code's or Codex's own client** is signed in through that provider's own flow, run in a throwaway home the daemon makes for that sign-in: Codex's `mcpServer/oauth/login` with `mcp_oauth_credentials_store = "file"`, which needs no ChatGPT sign-in, or Claude Code's own flow in a credential folder of its own. The daemon takes the saved sign-in (the server, the issuer, the client id, the access and refresh tokens, the expiry) into its own item, deletes the home, renews the sign-in under that client id from then on, and fronts it for each provider like any other signed-in server (§Long tool calls and the fronted route). It learns which client a server admits before the browser opens wherever the server says so — a refused dynamic registration, or a refusal from the server's pushed-authorization endpoint. Where the server says nothing, the first sign-in opens with the daemon's own client, and when that one does not finish, the next attempt goes through the admitted provider's client. The daemon remembers which client each server admitted, so every later sign-in is one press.
- **A server that demands proof-of-possession (DPoP) tokens**, which neither Claude Code nor Codex can sign in to, is signed in by the daemon as its own client with a signing key made for that one sign-in — one key per server, never the machine's own control-plane key — kept in the operating system's credential store beside the refresh token. The daemon fronts it as it fronts every signed-in server, and signs a fresh proof for every request.
- **How the sign-in reaches a provider.** The daemon keeps the refresh token in the operating system's credential store under its own item, never in a file, and renews it itself under the client id it was issued to. It fronts every signed-in server for each provider process it launches and adds the token, and a DPoP proof where the server demands one, on the way out, so no provider process holds a token: on Claude Code as an in-process (`type: "sdk"`) server over the process's own control channel, on Codex as a `url` entry on the daemon's route (§Long tool calls and the fronted route). Fronting keeps the MCP allow and deny lists: an in-process server is beyond every MCP setting and `managed-mcp.json`, so the daemon applies `deniedMcpServers` and `allowedMcpServers`, the organization's and the person's, to each server's real address or command before fronting it, reading them as it reads a server sent as declared, and never fronts one they keep out; on a machine whose organization deployed `managed-mcp.json` the person's own servers do not apply ([Plan-022](../plans/022-mcp-server-configuration-and-governance.md) T22.2.1), so the daemon fronts none of them. A provider's own command that prints a request header is never used, because the provider runs it in a shell, where any command at the same place in the process tree can run it again and print a live token. A rejected token never reaches a provider as HTTP 401, which would start the provider's own sign-in: the daemon renews it, answers a call it cannot authorize with a tool error and sets the leg to `needsAuth` itself, so a renewal never reaches the person. The daemon's own MCP client uses the same sign-in to list and read the server's prompts for a Codex session and to hold the connection of every server it fronts. A provider process the daemon did not launch gets nothing. The daemon never reads or renews a sign-in held by the person's own Claude Code or Codex outside the app: a server replaces a public client's refresh token on every renewal, so a second party renewing it signs the first one out.
- **A new attempt ends the waiting one.** `mcp.server.signIn` on a server whose sign-in is still waiting ends that wait and starts the next attempt, so a refusal page in the browser never holds the person until the flow's timeout.
- **Launch failures are errors; completion failures are events.** `mcp.server.signInFailed` is scoped to the **launch phase** — a failure to start the sign-in (discovery, registration, or the provider's own flow in its throwaway home), surfaced on the still-open `mcp.server.signIn` call. Once the call has returned (the `authorizationUrl` handed to the caller), the JSON-RPC channel for that request is closed by definition, so an asynchronous completion failure is delivered as the completion outcome itself: `mcp.server.signIn.completed` with `outcome: 'failure'` and a sanitized `failureReason`, observable on the `mcp.subscribe` stream and reflected by the server's persisting `needsAuth` status. The daemon never fabricates a late JSON-RPC error for a completed call.
- **Sign-out.** `mcp.server.signOut {serverId}` deletes the daemon's refresh token for that server, and its signing key where the server demands DPoP tokens, and stops fronting it, so each provider's next call to that server fails; the server reads `needsAuth` in every session on every provider until the next sign-in.
- Tokens, authorization codes, PKCE material and DPoP keys are held only as [ADR-038](../decisions/038-mcp-credential-custody.md#decision) records and are never logged, relayed, shown, or carried by any event, error, receipt, read model, or wire payload; the only durable trace on the governance stream is the `mcp.server.signIn.completed` event, whose payload carries the server identity and outcome, never credentials or URLs with embedded secrets. The idempotency receipt row for `mcp.server.signIn` follows the same rule: the persisted response omits `authorizationUrl` **structurally** (launch URLs embed single-use PKCE state and are never durable), so an identical-key retry returns a URL-free acknowledgment — the sign-in is already started, completion arrives as the event, and a caller that never received the URL begins a new sign-in under a fresh key. **The launch URL has exactly one carrier: the `mcp.server.signIn` reply, and no other surface.** It is absent from every durable and every broadcast destination — receipt rows, every event payload, the `mcp.subscribe` stream, errors beyond guidance text, and logs — which is the §Pitfalls destination list applied to this value rather than a carve-out of it, and it is what makes the rule mechanically checkable: one surface asserts presence and every other asserts absence. Each client then consumes it at **one destination and none other** — the CLI prints it as the login command's own **result**, on the stream that command's result belongs on, and the desktop opens it in the browser and holds it as transient render state that is written to no client-side storage, entered into no log, and dropped at settlement. A client that cannot show the URL cannot complete the sign-in at all, so withholding it there would not harden the launch phase but remove it. Tokens, authorization codes, and PKCE material stay prohibited at every one of those surfaces including the reply — the launch URL is a one-shot handle to the server's consent page, and it is the only member of this paragraph that any client ever sees.

### Status Observation and Events

The event type, `mcpGovernance` category ([Spec-005 §MCP Governance (`mcpGovernance`)](./005-session-event-taxonomy-and-audit-log.md#mcp-governance-mcpgovernance)):

| Event | Emission point | Session binding |
| --- | --- | --- |
| `mcp.server.signIn.completed` | The daemon's sign-in settling (its own callback, or the provider's flow finishing in the throwaway home) | Sentinel-bound per [Spec-005 §Daemon-Scope Event Binding](./005-session-event-taxonomy-and-audit-log.md#daemon-scope-event-binding); `initiatingSessionId` when applicable |

- **A status change is a live notice, never an event.** A normalized status transition from a provider's feed (Codex `mcpServer/startupStatus/updated` / `mcpServerStatus/list` deltas; Claude init census + `mcpServerStatus()` deltas) or from the daemon's own client for a server it fronts, including the transition to `needsAuth` a sign-out causes, is sent on `mcp.subscribe` as `{type: 'mcp.server.status.changed'}` with the binding's path-free audit ref, its status, and its `origin` (`sessionFeed` for a session's provider feed or a fronted connection serving that session, `machineProbe` for an on-demand probe), and is written to no log. It is sent on transition only. The inventory keeps each leg's latest reading, so a surface that opens later reads it from `mcp.server.list`; no screen reads past status changes.
- Status observation is event-driven plus on-demand (`mcp.server.list` refresh); the daemon MUST NOT busy-poll provider status endpoints.
- **`mcp.subscribe` is the live governance stream.** `mcp.subscribe` is a long-lived subscription the person reads (the Plan-005 streaming primitive, the `session.event.subscribe` consumer shape) delivering each `mcp.server.signIn.completed` envelope as the daemon appends it and each status notice as the daemon sends it. It is live-tail with a **gap-free handshake, not a cursor**: a (re)connecting client opens `mcp.subscribe` first, then reads `mcp.server.list` — the subscribe acknowledgment precedes the stream's first delivery (the Plan-005 I-005-9 wire-ordering invariant), so registration is live before the snapshot read and an event concurrent with the snapshot arrives on the stream instead of falling between snapshot and subscription (re-observation is harmless — status notices and governance envelopes are re-entrant state updates; omission is impossible). Status keeps no history; sign-in completions remain in the sentinel session's log. The stream also carries a live notice after each edit to a binding, made from this machine or a linked device — an add, a change, a switch on or off, a tool override or a removal — `{type: 'mcp.server.config.changed'}` with the binding's provider, scope, scope reference and server name. The notice is sent live only and written to no session's log, so no audit record of an edit exists; a page showing that binding reads it again with `mcp.server.read`, and a removed one answers `mcp.server.notFound`. This is how the desktop MCP panel and `sidekicks mcp watch` observe governance without polling and without any per-session transcript merge (sentinel events never enter real sessions' streams — §Domain Dependencies).
- Every event payload and every notice is **credential-free and content-free by construction**: enums, scope identity, and sanitized failure reasons only — no config values, env-var values, header values, tokens, and none of the [Spec-020 §PII Data Map](./020-data-retention-export-and-deletion.md#pii-data-map) durable-tier PII classes (user messages, file paths, code snippets). `failureReason` fields pass the daemon's error-sanitization layer and MUST NOT echo config values or filesystem paths. Binding identity in payloads is the **path-free audit ref**, the binding's `provider`, `scope` and `serverName`: `scopeRef` — a user-specific filesystem path — never enters an event payload or a notice, and the raw path stays resolvable only through the machine-local binding store. Status notices with `origin: 'sessionFeed'` additionally carry the observing leg's `bindingId` — the Plan-003 runtime-binding key, an opaque daemon-minted identifier — so a subscriber can attribute the transition to its `legs[]` entry when one binding backs several legs in the same session (absent on `machineProbe` notices, which observe no leg).
- `serverName` / `toolName` are the deliberate residual: free-form identifiers the person or the provider chooses, `FreeFormText<MAX>`-bounded, carried in the audit payload as **non-PII infrastructure identifiers** — the same classification as tool names in `toolActivity` events. The person CAN embed personal data in a name they choose; the identifiers age out of full payloads on the standard [Spec-005 §Event Compaction Policy](./005-session-event-taxonomy-and-audit-log.md#event-compaction-policy) lifecycle. No other free-form config-derived string may enter these payloads.

### The MCP servers page

The governance layer above faces the person by construction, and precisely so: **every** non-read operation is open to this machine's own client or any linked device, and no session; the **governance mutations** among them are receipted and append no event, while among the operational commands `mcp.server.reconnect` carries no dedicated governance event, `mcp.server.signIn` is receipted and deliberately not evented, and `mcp.server.signOut` is receipted and shows through the status notices it causes (§Required Behavior). It is reached through Settings › **MCP servers** in the desktop app. This section states what that surface is bound by; its composition sketch is [Spec-021 §Signature Feature Composition Sketches](021-desktop-app-and-renderer.md#signature-feature-composition-sketches); [Plan-022](../plans/022-mcp-server-configuration-and-governance.md) builds the page's components and their projection in the settings feature's MCP servers page folder (CP-022-5), and [Plan-020](../plans/020-desktop-app-and-renderer.md) owns the Settings frame and its page list, whose `mcp-servers` entry registers the page, and owns nothing inside that folder (CP-020-3).

- **It adds no surface.** The page composes the `mcp.*` operations §Interfaces And Contracts documents — the governance operations, `mcp.registry.search` for `Browse servers`, and `mcp.server.signOut` for `Sign out of this server` — and mints no operation, event type, or error code beyond them. A control that would need another new verb is not a control this page ships.
- **Its update channel is `mcp.subscribe`.** Status arrives on the live governance stream and is applied to the row it names, and an edit's notice makes the page read that one binding again, so a server added from a phone appears on an open page at once; the page does **not** poll `mcp.server.list` on a timer. §Status Observation and Events forbids the daemon to busy-poll provider status endpoints, and a surface that polled the daemon instead would reintroduce the same cost one layer up, with the daemon's own admission control no longer in the way.
- **It is a fail-closed projection of state, and it does not project eligibility at all.** The two are separate. **State** — connection status and per-leg observations, enablement, per-tool overrides and whether a tool's idempotency class is the native baseline or an override the person set — is rendered from what the daemon reports and recomputed **nowhere**. This is the sharpest rule here rather than a restatement of the general one: a tool's effective idempotency class is the daemon's resolution of the driver's floor and the person's own assignment, and the workflow inspector shows the same class read-only, so a renderer that derived one would be a second source of truth beside the person's assignment — and it would be the source no daemon path consults. **Eligibility is different**: no inventory entry and no event payload on this governance layer reports whether a given operation would be permitted for a given binding, and none is minted here, because a supplied eligibility flag would be exactly the daemon-side authorization re-expressed as a renderable field and would drift from the daemon's own decision. So the page projects none: every control is offered, the daemon adjudicates, and the typed refusal renders — which is the same rule as the bullet below, not a competing one. The **one** non-offer is a control whose required input is structurally absent from the entry the daemon served — on the degraded arm §Fallback Behavior serves when the binding store is unreachable, `tools` is absent outright and `enabled` survives only where the provider itself declares it, so the per-tool controls have nothing to act on, while every control whose input **did** arrive is offered exactly as on the normal arm — and that is absence of data rather than a judgment the renderer formed.
- **Configuration content splits three ways, and the split is what makes the page usable without making it a credential surface.** A page that rendered and collected nothing could not register a server at all, and `mcp.server.upsert` takes a declaration the person authors by design. **(1) Input.** The declaration form collects what that mutation accepts: transport, command, arguments, URL, timeouts, the required-server marker, environment-variable and header **names**, and the credential-bearing values the input shape admits. Those values are **write-only in the renderer as well as on the wire** — masked on entry, never read back, never held in serializable renderer state, cleared on submit — the Provider Accounts token-field discipline, applied here for the same reason: the wire rule protects the transport and this protects the screen. **(2) Read-back is exactly `McpServerConfigView` and nothing beyond it.** That view exists so `mcp.server.read` can serve back what `mcp.server.upsert` wrote — every non-secret field preserved, secret values structurally absent, names without values, the URL query-redacted, drawn under `Environment variables`, `Headers`, `Arguments`, `Address query` over the names of an address's query parameters, and `Token from the environment variable <NAME>` for an address server whose token is read from one — which is what supports an edit workflow without the daemon ever serving credential material. **(3) Never rendered.** Anything the daemon does not serve: environment-variable values, header values, tokens, URL query values. The page does not reach past the daemon to the provider's own config files, which remain the source of truth and are the daemon's to read. The governance **event** payloads stay credential-free and content-free by construction — that property is about the governance stream and is unchanged by anything this page collects or displays.
- **It is the one place a tool server is governed.** A tool server is added, removed, and governed here and nowhere else in the product. The page's sections carry the headings `Where it is set, and what each one reads` and `What each tool is allowed to do`, in sentence case as every Settings section heading is. The page is the server list beside the selected server's detail: the list gives each server its name, its provider, where it applies, in the provider's own terms — `All projects` (user scope), `This project · in the repo` (project scope) or `This project · not in the repo` (local scope), or for a server a plugin declared `From plugin <name>` — and its state. A name set in two places is never merged and never resolved by the page: both rows stand, and the copy a project does not use reads `Not used in <project>: its own <name> takes its place.`, by the order the provider documents — a project's private copy over its shared one, either over the `All projects` one. The page's note reads `The tool servers Claude Code and Codex connect to, and what each is allowed to do. Read live from the background service.` The detail gives, under `Running sessions`, one line per running session that uses the server, `<session> · <state word> · updated <age>`, the session named as the session list names it, read from the `session.subscribe` subscription, and never by an id — with none, `No running session uses this server.`, and a reading with no time drawn as its state word alone, `Unknown` carrying a state never reported — and then its controls, `On for runs` first, and with nothing selected it reads `Pick a server on the left to see what it is allowed to do.` The list's first read says it is reading (`Reading the server list…`), and a read that fails says so (`The server list could not be read.`) with `Try again`.
- **A server is added where it applies.** `Add a server` reads under one line `Register a tool server for a provider, in all projects or in one.` Its fields are `Name`, `Provider`, `Where it applies`, `How it runs` (`A command` / `An address`), `Command`, `Arguments`, `Address`, `Start-up timeout` and `Must start for a run to start`, under `A run does not begin until this server is up.`, then `Environment variables` and `Headers` as name-and-value pairs, each pair added by `Add`, which settles with `That name was added. Its value is held only long enough to send and is never read back.` Under the value fields: `Values are stored by the provider and are never shown here again. Type a new one to replace it.` The form is sent by `Add the server` and dropped by `Cancel`, and sending settles with `The server was sent to the background service. Every value typed here was cleared on submit.` `Where it applies` comes after the provider, with the same three choices; the last two add a `Project` chooser over the attached projects. Under Codex at `This project · not in the repo`, one line under the chooser reads `Plain codex shows this server as switched off.`
- **`Browse servers` searches the public MCP Registry.** It sits beside `Add a server`, searches only when the person types, and says under its field where the words go: `Searches the public MCP Registry. Anyone can publish there; check a server's source before adding it.` Each result reads its title or name, its description, its version, and whether it runs as a package or is reached at an address. Picking one opens the declaration form filled in — the name, how it runs with its command and arguments or its address, each environment variable's name and description with the required ones marked — and leaves every value and the add to the person.
- **Five words, one vocabulary.** A server's state is drawn in one of five words — `Connected`, `Starting`, `Needs sign-in`, `Failed`, `Unknown` — one word per `McpServerStatus` value. Every other surface that says what a tool server is doing uses those same five words read from this same inventory, the session composer's tool-server chip among them: it lists that session's servers, links here to manage them, and is the only place inside a session that names them. There is never a second inventory.
- **Every per-tool value says where it came from.** The three per-tool facets — whether the tool is on, whether it asks before running, and what happens if a call is interrupted — are each optional, each shown per tool, and each says whether the value in force is the server's own or one set here. The page works none of that out for itself.
- **Reconnect asks, and claims nothing.** Asking the provider to open the connection again is offered on the selected server whatever its state and is drawn first on one reading `Failed`. It writes nothing and changes no setting, and it says so: `This asks for the connection again. It changes nothing that is set here.`, then `Asking for the connection again…` while it runs. A try that moves no state reads `Nothing changed. The server is still Failed.` rather than reading as success.
- **Sign-in is one control and one consent, and leaves nothing behind.** `Sign in to this server` starts the daemon's own sign-in for that server (§OAuth Orchestration) — for every kind of server, one that admits only Claude Code's or Codex's own client and one that demands DPoP tokens included — and settles in place with `The sign-in for that server opened in the default browser.`, or reads `Sign-in did not finish.` It stays pressable while a sign-in waits: a press ends that wait and starts the next attempt. The address the flow opens with is held only while it is used, written to no storage and no log, and dropped when the sign-in settles. Once signed in, `Sign out of this server` stands where `Sign in to this server` stood; it forgets the sign-in at once, and the server then reads `Needs sign-in`.
- **A command that cannot run says so.** On a Windows computer with WSL, a server whose command or arguments name a Windows program reads `Failed` for sessions in a distribution, one of the state words, and its selected view carries one line naming the distribution: `Its command names a Windows program, which cannot run in Ubuntu. Use the program's name without its folder.`
- **An organization's policy says so.** On a machine whose organization deployed `managed-mcp.json` (§Implementation Notes), the page reads one line: `This computer's MCP servers for Claude Code are set by an organization policy.` Where the service's own tools cannot load under that file, it reads `Claude Code can't start on this computer: an organization policy blocks the service's tools.`
- **What Claude Code brings itself is shown read-only.** Each Claude Code account's claude.ai connectors stand in a read-only group of their own, headed `claude.ai · <account name>` (`claude.ai · Work`, `claude.ai · Personal`), and a session gets the connectors of the account it runs on; the organization's servers stand in one read-only group, `Organization`. Each server is marked as `/mcp` marks it, in the five state words, with a switch per project and its tool overrides, and takes no edit and no removal. An account without a claude.ai subscription login has no `claude.ai` group at all, as Claude Code's own `/mcp` shows none, and no line stands in its place. A server switched off for a project — on this page, or in Claude Code's own `/mcp` — reads `Off in <project>` beside its state, dimmed, once per project.
- **A missing reading says it is missing.** Where the degraded arm leaves the per-tool controls without an input, the page says so in place — `Per-tool settings cannot be read right now. Those controls are not drawn because the reading they act on did not arrive; everything else on this page is offered exactly as usual.` — rather than leaving the absence unexplained. Where `On for runs` is missing too, the line names both: `` `On for runs` and the per-tool settings cannot be read right now. Those controls are not drawn because the reading they act on did not arrive; everything else on this page is offered exactly as usual. ``
- **A change says when it takes effect.** Every mutation the page sends settles in place with one line for the application grade it answered (§Configuration Mutation): `liveReconcile` reads `Applied to running sessions.`, `userConfigWrite` `Saved to <Provider>'s settings. New sessions use it.`, `nextRun` `Saved. The next session uses it.`, and `daemonEnforced` `In force now.` While a change is on its way it reads `Sending…` under its control, only after the session's short delay, until it settles. Each live session the change failed on adds `<session> is still running with the old setting.`, the session named as the session list names it; until the list names that session, its line is neither drawn nor announced. No grade or outcome value reaches the screen.
- **Removing a server confirms in place.** `Remove <server>? It stops being offered to <Provider>. Nothing it wrote is touched.` under `Cancel` and `Remove`.
- **Nothing configurable is drawn as nothing.** A provider with no tool servers set up says so in words, one line per provider with none: `No tool servers are set up for Claude Code.` With every provider empty the lines stand in place of the list, and otherwise each empty provider's line sits in quiet text at the list's foot. A server whose reading lists no tools reads `No tools listed for this server.` in place of its tool rows. An empty list is never drawn as though nothing could be configured.
- **One wire mutation per explicit action by the person, and refusals render.** No control batches, retries on the person's behalf, or pre-filters itself to hide an action the daemon would refuse. A refused action is refused before any write and the refusal is shown, because the person learning the rule from the system that enforces it is worth more than a control that quietly disappears — and a pre-filter would be a re-derivation of exactly the authorization this spec places in the daemon.

### Required-Server Semantics

- A Codex server with `required = true` that fails to initialize fails the thread start/resume; the daemon MUST map that failure onto the run-failure path with an actionable error naming the server, and send its `failed` status notice — the run failure is never silent or attributed to the provider generically.

### Long tool calls and the fronted route

A tool call that runs long moves to the background on Claude Code and on Codex alike: after 120 s, or at once when a message arrives, the model is told the call keeps running under a task id and goes on working, and the result comes into the conversation when the call ends, starting a new turn if none is running.

- **Claude Code does it itself.** The daemon starts every Claude Code process with `CLAUDE_AUTO_BACKGROUND_TASKS=1`, so an MCP call still running after 120 s, or one running when a new message arrives, moves to the background: the model gets a tool result naming the task id and goes on, and when the call ends Claude Code's task notification starts a turn if none is running. Claude Code runs MCP Tasks itself and restores them on resume. The daemon reads `task_started` with `task_type: "mcp_task"` and the completion's `resource_links` off the stream and draws the call as a tool row that stays running until the task ends, and the notification as that row's result, never as a message from the person. The same switch moves a foreground helper to the background after 120 s. A plain call moved to the background ends with the process, and after a restart its row reads `Stopped when the app restarted`.
- **On Codex the daemon fronts every server it can reach.** Codex has no MCP Tasks and cannot move a call to the background, so the conversation's `thread/start` table carries every server as a `url` entry on the daemon's route under the server's own name, and the model sees the same server and tool names. The daemon's own MCP client holds the real connection: it starts a stdio server itself, one copy per conversation, as Codex would, or connects to an address, reading the declaration's environment and header values from the provider's config only for that connection.
- **The route answers a long call with a handle.** It answers a call normally when it ends within 120 s. Past 120 s, or when the daemon holds a message for the conversation while the call runs, it answers Codex's pending call with Claude Code's own handle text — `Tool "<tool>" is still running after <N>s. It was moved to the background as task <id> and keeps running; you'll receive a notification with the result when it completes. You can keep working in the meantime. To stop it, call task_stop with task_id "<id>".` — which ends the call so the held message lands at the tool boundary that answer makes, and the call keeps running in the daemon's client. The route offers tools of its own:
  - `task_output {task_id, wait_seconds?}` returns the task's status and, once it ends, its result, waiting at most 10 s;
  - `task_stop {task_id}` cancels it: `tasks/cancel` for a task-augmented call, `notifications/cancelled` for a plain one.
- **Delivery.** When the call ends, the daemon delivers `MCP task <id> (<server>/<tool>) completed.` with the result — to a lead through the daemon's hold, handed over by `turn/steer` at the running turn's next tool boundary as every message is, or by `turn/start` into an idle one, and to a helper a Codex agent started, which takes no direct input, at its next tool call as added context from the daemon's post-tool hook, or as the continuation the helper-finish hook (`SubagentStop`) returns as it finishes — and draws it as the tool row's result. To a 2025-11-25 server the client makes a call task-augmented wherever the tool's `execution.taskSupport` allows one; to a 2026-07-28 server the server decides. The client writes the `taskId` to the command receipt before answering anything else, polls with Claude Code's figures (every 2 s by default, honoring the server's `pollIntervalMs` held between 250 ms and 30 s, halting after 5 failed polls in a row with the handle kept), and marks the receipt `delivered` once the result is delivered, so a result that arrives after a daemon restart is delivered once. After a restart it resumes every receipt with a handle to a server reached at an address; a stdio server's task ends with the daemon.
- **What the route passes through.** The route adds no approval of its own: Codex decides each call on a fronted server from the approval fields its `url` entry carries and the annotations the route passes through unchanged, and asks with its own approval, an elicitation marked `_meta.codex_approval_kind: "mcp_tool_call"`, which becomes the session's approval card. The entry carries the binding's own `default_tools_approval_mode` and `tools.<t>.approval_mode`; at `YOLO` it also carries `default_tools_approval_mode = "approve"` where the binding sets no default of its own, so a call runs unasked, as Claude Code in bypass permissions runs it, while a tool the person set to `prompt` or `writes` still asks. Codex's ChatGPT connectors, which follow Codex's `apps` table rather than any fronted entry, carry `apps._default.default_tools_approval_mode = "approve"` at `YOLO` the same way, and `"writes"` below it, so a connector tool not marked read-only asks, leaving any app, account or tool the person set. Codex takes these fields only when a conversation starts, so a move into or out of `YOLO` reaches a conversation at its next idle point, when the daemon unsubscribes and resumes it with the new fields. That is a gap on a conversation a terminal `codex` has joined: the daemon is not its only subscriber, so it stays loaded, Codex ignores the resume's fields with `config overrides were provided and ignored while running`, and the conversation keeps the approval fields it started with, so no mechanism applies a move across `YOLO` to it ([Codex wire reference](../reference/provider-wire/codex.md#tool-server-approvals-approve-and-the-chatgpt-connectors)). One difference stays: Claude Code still asks in bypass permissions before a tool marked `_meta["anthropic/requiresUserInteraction"]`, and Codex reads no such marker. A request the server sends back is handed on: a server's own elicitation becomes the session's question card, and a progress notice the row's progress line. A server behind a sign-in is fronted on the daemon's own sign-in (§OAuth Orchestration), including one whose sign-in the daemon took over from a provider's flow.
- **On Claude Code every signed-in server is fronted.** The daemon fronts only a server the MCP allow and deny lists let in, read against its real address or command (§OAuth Orchestration). Claude Code reaches a server behind the daemon's sign-in as an in-process (`type: "sdk"`) server the daemon names in every full-set `mcp_set_servers` send, since a set that leaves one out removes it, its messages carried by `mcp_message` on the process's own standard streams, with no port, no secret and no process to impersonate; the daemon's client holds the real connection and adds the token, and a DPoP proof for every request where the server demands one. Where a probe shows the in-process route lacks something a server needs, that server rides the daemon's loopback route instead, gated by the per-session secret and sent with `mcp_set_servers`, never on the command line. A long call on a fronted server takes the daemon's own MCP Tasks handling with Claude Code's figures, as on Codex, wherever the build's probe shows Claude Code does not run MCP Tasks and backgrounding over the route itself. A server no sign-in of the daemon's covers stays the server's own declaration, reached by Claude Code directly. In a WSL 2 distribution a fronted server is reached by kind: one at a web address is connected by the daemon on Windows, so the token never enters the distribution; a stdio server is started inside the distribution by its WSL server and carried over the channel; an address only the distribution reaches, its own `localhost`, is carried through the WSL server, which holds no token ([Spec-006 §The service on a Windows computer](./006-local-ipc-and-daemon-control.md#the-service-on-a-windows-computer)).
- **The workflow MCP-tool step** calls a tool with MCP `tools/call` through the same client, a task where the server's protocol version and the tool allow one, as above.
- **Budget.** The route adds at most 5 ms to a fronted call against a direct one. While a call is in the background: one `tasks/get` per poll interval for a task-augmented call and nothing for a plain one; one model turn per delivery into an idle conversation. A fronted stdio server costs one copy of that server per Codex conversation (about 50 MB), the process Codex would otherwise start. At `Sandboxed` a wrapped server adds, on Codex, at most the native `codex sandbox` process, and on Claude Code the operating system's sandbox launcher plus a share of one `bun` process per network list (55.8 MB at peak for two wrapped steps); both are measured against the same server unwrapped when the wrap is built.

### A session's own tool servers

- **A session starts with exactly the servers switched on for it**, through the provider's own means (§Provider Capability Model), and a server that is off costs the model no tool definitions.
- **Its list is read, never recomputed.** `session.mcpServer.subscribe {sessionId}` is a live list of the servers the session was started with, each drawn from this spec's inventory: the working servers first by name alone, then the ones that are not working, each with `Needs sign-in` or `Failed` and the reason, the failed ones last; a server still starting, or one whose state is unknown, sits with the working ones until it says otherwise. The list carries no reconnect, no sign-in and no tool list; those are the MCP servers page's.
- **A per-session switch only narrows.** `session.mcpServer.enabled.update {sessionId, serverName, enabled}` turns one server off or on for this session alone: off stops the session offering that server's tools to the agent, so none of its definitions reach the model and none of its tokens are spent. Settings, every other session and every future session are untouched, and a new session starts with every server on. A switch applies at the next turn — on Claude Code another full-set `mcp_set_servers` call, which ends a switched-off server's process and removes its tools from the next turn with no restart and nothing written to disk; on Codex the conversation's `enabled` flag at its next turn — and one flipped mid-turn says so rather than changing anything under the run. The daemon keeps a session's switches with the session and sends its set again after each resume. The switch is not a governance mutation and emits no governance event.
- **At `Sandboxed`, the person's own tool servers run in the session's sandbox.** A stdio server the session starts at `Sandboxed` runs inside the same sandbox as the session's commands, through each provider's own sandbox engine: it writes only where those commands write — the worktree and the repository's git folder, whose `hooks` and `config` stay closed — the curated credential paths stay unreadable to it, and it reaches the hosts the person's own provider settings give those commands. On Codex the daemon's own client starts the server under Codex's own `codex sandbox --permission-profile <the session's profile> --cd <the worktree>`, run from `@openai/codex`'s native binary, so the per-repository profile the session runs under binds the server too, network included. On Claude Code the daemon never links Anthropic's `@anthropic-ai/sandbox-runtime` 0.0.79, the library Claude Code's own sandbox is built on: a wrapped command comes from the library's `wrapWithSandbox` in a shared `bun` process, one per distinct network list (on Windows one per set of write folders), with `bun` fetched during first-run setup, and each stdio entry the daemon sends with `mcp_set_servers` runs the wrapped command it returns: the session's writable roots and their closed paths, the curated credential paths denied for reading, and the hosts Claude Code itself would allow and deny — every settings source's `sandbox.network` domains merged with its `WebFetch(domain:…)` allow rules, managed sources alone where `allowManagedDomainsOnly` is set. That `bun` process holds the library's network proxy for every wrapped server with its network list. A host outside those lists is refused with no card, since nothing asks at `Sandboxed`. A server at an address starts no process on the machine and is reached as at every level. The same rule holds for a workflow step that runs at `Sandboxed`, since a step runs at its run's level. A write the sandbox refuses fails that tool call with the server's own error, and one refused while the server starts shows as its `Failed` reason in the session's list. Where the wrap cannot start on the machine, the run is refused like any `Sandboxed` run whose sandbox cannot start ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)). Below `Sandboxed` nothing changes: the asking levels ask, and `YOLO` runs every server as the provider would.
- **Resources.** `mcp.resource.list {sessionId, serverName}` lists what a working server offers, so the person can stage one in the composer's attachment row; on Codex the read goes through `mcpServer/resource/read`.
- **Prompts.** A working server's prompts appear as a group under its name in the session's command list, the provider-commands subscription [Spec-004](./004-provider-driver-contract-and-capabilities.md) owns; on Codex the daemon lists and reads them through its own client, on its own sign-in where the server needs one, over the connection that client already holds for the server, so listing prompts never starts a second copy of it.

## Default Behavior

- New servers are enabled per provider config, with no tool overrides (provider defaults + `manualReconcileOnly` idempotency floor).
- `mcp.server.list` serves the merged inventory from the most recent observations without forcing a provider round-trip; `refresh: true` forces one, which for a binding with no live leg is the machine probe: on Claude Code a process in the project root that runs `initialize` and no turn, started with `--strict-mcp-config` (with neither flag on a machine whose organization manages MCP, §Implementation Notes), sent the bindings' set with `mcp_set_servers` and asked `mcp_status` (the SDK's `mcpServerStatus()`, carrying each server's status, error, scope, source and tools); on Codex an ephemeral `thread/start` in the project root on a connection of the probe's own, whose `mcp_servers` table switches each emulated `local` binding of that root on by name and adds each plugin server (the person's own and the project's servers load by Codex's own configuration, which merges the table field by field), asked `mcpServerStatus/list {threadId, serverName, detail: "toolsAndAuthOnly"}` once per server and then closed by dropping that connection: on the daemon's own Codex service for that home, which unloads the thread within 5 seconds, or, where the home has none or its service is Codex's own, on a service started for the probe that unloads the thread at once and stops when the read settles. One probe process per provider runs at a time, through the attached project roots in turn, and none bills a turn. `claude mcp list` is not read: it has no `--json` and lists the person's home's plugins rather than the daemon's plugin home.
- Claude mutations attempt the live path on every installed build and settle the grade on the outcome of the daemon's own full-desired-set reconcile; callers never select the mechanism, only observe the returned grade.
- A status notice is sent on transition only — an unchanged status re-observation sends nothing.

## Fallback Behavior

- **A Claude Code session that refuses `mcp_set_servers`**: the daemon gives a session its tool servers with `mcp_set_servers` right after start, again after each resume, and after each change, never with `mcp_toggle` and never by restarting the session. A session that refuses the call (the CLI refuses control requests from a session it treats as cloud-hosted, and a non-streaming-input session cannot carry them at all) gets its servers no other way: each of that session's servers reads `Failed`, with the refusal as the server's reason, the way Settings › MCP servers draws a command the service cannot run. A configuration change made meanwhile is still written through `claude mcp add-json --scope` and answers with grade `userConfigWrite`; that session's live set does not change. The refusal is read from the call's own answer, never from a version comparison or a driver-side probe.
- **Codex write conflict:** a `configVersionConflict` surfaces `mcp.server.configWriteConflict` with both version tokens so the caller can re-inspect, with no retry: one press is one change.
- **Codex project file changed since it was read:** the edit is not renamed into place and the write refuses with `mcp.server.configWriteConflict`; the file is left as it was.
- **Status source unavailable** (provider down, or the status probe refused on the running build): inventory serves `unknown` with an `observedAt` timestamp; the daemon does not fabricate `connected`/`failed`.
- **Sign-in did not finish:** `mcp.server.signIn.completed` carries `outcome: 'failure'`, the server keeps reading `needsAuth`, and the next `mcp.server.signIn` starts a new attempt — through the admitted provider's client where the daemon's own client was not admitted (§OAuth Orchestration).
- **Binding store unavailable** (storage failure): governance reads degrade to the **degraded entry arm** — a discriminated `bindingStoreUnavailable: true` variant whose store-dependent fields (`tools`, and `enabled` on a binding whose switch the daemon keeps as its enabled overlay) are structurally absent rather than fabricated, with provider-observed fields (config view, status, legs) intact; all mutations fail closed.

## Interfaces And Contracts

- **IPC operations** (JSON-RPC per [ADR-009](../decisions/009-json-rpc-ipc-wire-format.md); registered in the Plan-005 `MethodRegistry` at Plan-022's tier per the `presence.*` late-namespace precedent): `mcp.server.list`, `mcp.server.read`, `mcp.subscribe`, `mcp.server.upsert`, `mcp.server.delete`, `mcp.server.enabled.update`, `mcp.toolOverride.update`, `mcp.toolOverride.clear`, `mcp.server.signIn`, `mcp.server.signOut {serverId}`, `mcp.server.reconnect`, and `mcp.registry.search {query, cursor?}` answering `{servers, nextCursor?}` from the public MCP Registry's `GET /v0/servers?search=<query>&version=latest`, caching nothing past the page. Requests address the scope-qualified binding (`scopeRef` structurally required for `project`/`local` and forbidden for `user`, on every provider — a schema-level discriminated union, not a service-layer check); the binding's `provider` is the open `ProviderId`, checked against the registered drivers, and a request's declaration is checked against the transports and fields that provider's driver declares; `mcp.server.upsert` and `mcp.server.delete` take `scope` and `scopeRef`; every governance mutation — and `mcp.server.signIn` and `mcp.server.signOut` — carries the mandatory `clientIdempotencyKey` (`mcp.server.reconnect` is unreceipted); `mcp.server.upsert` carries the fully-typed `McpServerConfigInput` union; mutation responses carry application grades (per-facet for overrides) plus per-leg `liveResults[]`; an entry reading `failed` because its command names a Windows program a session in a WSL distribution cannot run carries `failedReason: commandNotRunnable`. Typed request/response mirrors live in [MCP Governance Payload Contracts §Plan-022 — MCP Governance Contract Surfaces](../architecture/contracts/mcp-governance-payloads.md#plan-022--mcp-governance-contract-surfaces).
- **A session's servers** (§A session's own tool servers): `session.mcpServer.subscribe {sessionId}` (a live list; each row the server's name, binding, status with its reason, whether it is on for the session, and whether a switch waits for the next turn), `session.mcpServer.enabled.update {sessionId, serverName, enabled}`, and `mcp.resource.list {sessionId, serverName}`; typed mirrors in the same api-payload section.
- **Tools the fronted route adds** (§Long tool calls and the fronted route): `task_output {task_id, wait_seconds?}` and `task_stop {task_id}`, visible to a Codex model and to a Claude Code model on a fronted DPoP server, never on screen.
- **Events and notices**: the `mcp.server.signIn.completed` type above and the two live notices on `mcp.subscribe` (`mcp.server.status.changed`, `mcp.server.config.changed`); payload mirrors in the same api-payload section; category registration in Spec-005; contracts-package registration via Plan-004 T1.9.
- **Errors**: the `mcp.*` code registry in [Error Contracts §MCP Governance](../architecture/contracts/error-contracts.md#mcp-governance) — the codes narrated across §Required Behavior (`mcp.server.signInUnsupported` among them) plus `mcp.server.notFound` for the unknown-binding outcome every operation surface shares.
- **Not built.** None of the following exists in code yet; each is built by the [Plan-022](../plans/022-mcp-server-configuration-and-governance.md) task named: `mcp.server.list` and `mcp.server.read` (Phase 2), `mcp.subscribe` (Phase 2), `mcp.server.upsert` and `mcp.server.delete` at every scope (Phase 3), `mcp.server.enabled.update` (Phase 3), `mcp.toolOverride.update` and `mcp.toolOverride.clear` (Phase 4), `mcp.registry.search` (Phase 3), `mcp.server.signIn` and `mcp.server.signOut` (Phase 5), `mcp.server.reconnect` (Phase 5), `failedReason: commandNotRunnable` (Phase 2), the session operations (Phase 5), the fronted route with `task_output` and `task_stop` (Phase 5), and the daemon's MCP client that the workflow MCP-tool step calls through (Phase 5).
- **Driver seam**: consumes the Spec-004 `onMcpServerStatus` producer seam (`McpServerStatusEmission` → `McpServerStatusUpdate`) as the session-scoped status source — this spec is the consumer that seam was built for.
- **Versioning**: operation payloads follow [ADR-017](../decisions/017-cross-version-compatibility.md) cross-version compatibility rules; no provider version is compared or refused, and each capability is resolved by its own declared detection mechanism against the running build per the provider-wire trust model.

## State And Data Implications

- **New daemon-local tables** (machine-scoped; DDL in [MCP Governance Tables (Plan-022)](../architecture/schemas/local-sqlite-mcp-governance-tables.md)): `mcp_server_bindings` (scope-qualified binding identity, an emulated Codex `local` binding among them, the native-tool baseline, and the Claude enabled overlay — no key material and no credential), `mcp_tool_overrides` (per-tool facets, FK-cascaded to the binding row), `mcp_mutation_receipts` (the idempotency receipt store — key, operation, saved response; pruned on age, never part of the audit trail), and `mcp_server_admitted_clients` (which client each signed-in server admitted — the daemon's own, Claude Code's or Codex's — kept once per provider and server name rather than on each binding, and kept after a sign-out, so every later sign-in is one press; not a credential).
- **No provider-config mirroring**: provider files remain the config source of truth at every scope — including for Claude, whose durable declarations live in the provider's own stores (written only through `claude mcp add-json --scope`) and whose session set is sent through `mcp_set_servers` from those declarations plus governance overlays, never an independent daemon-owned server set. The daemon persists only governance state (overlays, overrides, a session's own switches) and derives inventory on read; an acknowledged mutation survives daemon restart because the provider store holds it.
- **The operating system's credential store** holds, per signed-in server, the daemon's refresh token and, for a server that demands DPoP tokens, its signing key, each under an item the daemon created and removed with the sign-in ([ADR-038](../decisions/038-mcp-credential-custody.md)); on Windows, with or without WSL, each is written at `CRED_PERSIST_LOCAL_MACHINE`, in the service's own process through `sidekicks-platforms`, and none ever enters SQLite.
- **Events**: every settled sign-in appends through the Plan-004 `EventLogService` path and is rebuilt like every other category; status transitions are sent live and written to no log. Machine-scoped events bind to the daemon-scope sentinel session per [Spec-005 §Daemon-Scope Event Binding](./005-session-event-taxonomy-and-audit-log.md#daemon-scope-event-binding).
- **Rebuild/recovery impact**: none. An idempotency class the person assigns says whether a call to the tool may safely be repeated, and recovery never branches on it: a daemon restart re-runs no command whatever its class ([Spec-013 §In-Flight Receipts After A Restart](./013-persistence-and-recovery.md#in-flight-receipts-after-a-restart)). Assignment stays the person's own act because it is the only path off the `manualReconcileOnly` floor.

## Example Flows

- `Example: live server add on Claude` — the person calls `mcp.server.upsert` (provider `claude`, scope `user`); the daemon persists the declaration via `claude mcp add-json linear <json> --scope user` and verifies the write; on a streaming-input session the daemon additionally computes the full desired named-server set and calls `setMcpServers` — that call is itself the availability answer, not a probe of it — reconciling `{added: ["linear"], removed: [], errors: []}`; it upserts the binding row for the `(claude, user, "", linear)` binding, sends the status notices (`starting` → `connected`), and returns the inventory entry with grade `liveReconcile`. Had that reconcile been refused, the same call would return `userConfigWrite` with the declaration already durable.
- `Example: Codex write conflict` — two of the person's devices race `mcp.server.enabled.update`; the second write's `expected_version` is stale, so it answers `mcp.server.configWriteConflict` with both version tokens and writes nothing; the page shows the refusal, and the person presses again against the new version.
- `Example: one sign-in, both providers` — the person presses `Sign in to this server` on `notion`; `mcp.server.signIn` → the daemon discovers the server's authorization server, registers itself, and returns the sign-in page's address; the desktop opens it in the browser; the person consents once; the daemon's callback completes, the refresh token goes into the credential store under the daemon's own item, and the daemon emits `mcp.server.signIn.completed` (`outcome: 'success'`). The daemon's client connects with a current access token and fronts the server for a Claude Code session and a Codex session alike, and each leg flips `needsAuth` → `connected`; the Codex session's command list gains the server's prompts. `mcp.server.signOut` later deletes the token and every leg reads `needsAuth`.
- `Example: a server saved with the repository` — the person adds `postgres` for Claude Code at `This project · in the repo` for project `app`, typing its `DATABASE_URL` value, then adds it again for Codex, since each add registers a server for one provider; the daemon writes `app/.mcp.json` through `claude mcp add-json … --scope project` for the first and, for the second, edits `app/.codex/config.toml` in place, reads it back with `config/read`, and reloads; each file holds the value as typed. Sessions in `app` get the server; sessions elsewhere do not. A `.mcp.json` server that arrived with a pull joins the project's sessions like any other switched-on server.

## Implementation Notes

- **Re-verify at execution.** Every provider mechanism above is Verified at the versions the [provider-wire reference](../reference/provider-wire/README.md) records, or version-anchored beyond them (`mcp_set_servers` at `2.1.210` — an **upstream feature anchor**, far older than any build this project measured); Plan-022 code MUST check load-bearing shapes against the installed binaries before binding. Re-verification is **detection against the running build**, not a version comparison: [Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior) binds each capability to its own declared mechanism — a zero-turn, non-mutating, granularity-decisive probe where one is admissible, and a declared `static` reading naming the failing conjunct where none is — precisely because a version bounds availability from neither side. `mcp_set_servers` is not a capability flag at all — it is a control-request subtype no driver-side probe may issue — so its live answer comes from the reconcile itself, and a refusal there withdraws no flag.
- **Codex per-conversation configuration.** A conversation's `thread/start` configuration takes `mcp_servers`: a whole table replaces the service's table for that conversation, and the dotted form `mcp_servers.<name>` merges with it. The daemon sends the whole table, each server a `url` entry on its route, enabled or not — the per-session mechanism on Codex, never a flag on the shared service.
- **MCP revision watch.** The MCP 2026-07-28 revision restructures the protocol core (stateless core, Tasks → extension, Roots/Sampling/Logging deprecated); Claude Code and Codex will each absorb it in their own releases. The governance layer binds to _provider surfaces_, so there the revision lands as provider-behavior changes caught by the re-verify rule; the daemon's own client takes it through its MCP client library, re-verified the same way.
- **The daemon's own MCP client** is `rmcp` 3.5.1 with the service's bridge for 2025-11-25 tasks: task calls go out as `CustomRequest`s, polled through `tasks/result`, over the service's own `StreamableHttpClient` on `reqwest`, which signs a DPoP proof with `p256` on every request; a 2026-07-28 server is served through `rmcp`'s own types. `rmcp` also serves the daemon's shared `sidekicks` tool server, on which the browser tools are registered. The client runs each sign-in through `rmcp`'s `AuthorizationManager`, which binds the sign-in's callback to its authorization server. It serves the fronted route, Codex's prompt list over the connection it already holds for the server, so listing prompts never starts a second copy of it, the workflow MCP-tool step and the recovery sweep of task handles.
- **Claude Code session set.** The daemon drives `claude mcp add-json` / `claude mcp remove` at the binding's `--scope` as the durable-write mechanism. Each session's process starts with `--strict-mcp-config`, or as the build's probe below settles, so nothing the project, the account or a plugin configures loads by itself, and only the account's claude.ai connectors ride `--mcp-config`; the daemon's own tool server rides `initialize`'s `sdkMcpServers` as an in-process (`type: "sdk"`) server on every machine, its calls carried by `mcp_message`, so Claude Code holds no route secret, and where a probe shows that route lacks something the entry goes by `mcp_set_servers` in every full-set send, never `--mcp-config`; every full-set `mcp_set_servers` send names that server and every server the daemon fronts as `{"type": "sdk", "name": …}` entries, because Claude Code removes each in-process server a set leaves out, `initialize` covering the moments before the first send; right after start the daemon sends the session's set with `mcp_set_servers`, built from every scope's switched-on bindings plus governance overlays, less the session's own switched-off servers, any server the person rejected in Claude Code — a `disabledMcpjsonServers` entry in any of Claude Code's settings files (the person's, the project's, the project's local one, the managed one) or the project's entry in `~/.claude.json`, since "A `disabledMcpjsonServers` entry in any settings file still rejects the server" (<https://code.claude.com/docs/en/mcp>) — and any server Claude Code's own `/mcp` switched off for the project (`disabledMcpServers`), and sends it again after each resume, because the set lives only in the process's memory. Determinism means the session sees exactly the set the daemon sent, immune to mid-run ambient drift, while ambient edits (the person using the provider's own CLI directly) flow into the next send and the inventory. Because the daemon, not Claude Code's load of `.mcp.json`, supplies the set, Claude Code's own approval prompt for a repository's servers never runs, and `${VAR}` references in a `project` declaration are expanded by the daemon before sending (§Configuration Mutation).
- **A machine whose organization manages MCP.** Where an organization deployed `managed-mcp.json` — macOS `/Library/Application Support/ClaudeCode/managed-mcp.json`, Linux and WSL `/etc/claude-code/managed-mcp.json`, Windows `C:\Program Files\ClaudeCode\managed-mcp.json`, found through the daemon's operating-system interface — Claude Code exits at start when given `--mcp-config` or `--strict-mcp-config` (<https://code.claude.com/docs/en/managed-mcp>, §Servers passed with --mcp-config or --strict-mcp-config). The daemon starts Claude Code there with neither flag: the organization's servers load as Claude Code loads them, and the daemon's own tools ride as an in-process (`type: "sdk"`) server, which the file leaves to the app that started the session ("In-process servers that the app that started the session registers", <https://code.claude.com/docs/en/managed-mcp>, §Exclusive control with managed-mcp.json). The person's own servers and a session's per-server switch do not apply on that machine, and the MCP servers page says so in one line (§The MCP servers page). The claude.ai groups there list only the connectors Claude Code loads under the file, none unless an admin-controlled managed source sets `allowAllClaudeAiMcps: true` (<https://code.claude.com/docs/en/managed-mcp>, §Allow claude.ai connectors alongside the managed set), and an account with none has no group; `Organization` lists the file's servers and the `managedMcpServers` ones. A connector or organization server switched off for a project, on the page or by the project's `disabledMcpServers`, rides as a `deniedMcpServers` entry in the process's `--settings`, which merges from every scope and applies to the file's servers, provided servers and the allowed connectors (<https://code.claude.com/docs/en/managed-mcp>, §How allowlists and denylists apply to the managed set; <https://code.claude.com/docs/en/settings>). A probe confirms that an in-process server loads under the file before the build relies on it; if it does not, Claude Code is not run on that machine, and the line reads `Claude Code can't start on this computer: an organization policy blocks the service's tools.`
- **claude.ai connectors and the organization's servers in a session.** `--strict-mcp-config` "leaves provided servers out along with every other configured server" and uses only what `--mcp-config` passes (<https://code.claude.com/docs/en/managed-mcp>; <https://code.claude.com/docs/en/cli-reference>), so the daemon hands them to each Claude Code session itself while the session's own set stays exactly what it sends: each of the account's connectors as a `claudeai-proxy` entry on `--mcp-config`, because `mcp_set_servers` takes only stdio, sse, http and in-process entries, and each organization server as its own entry in the `mcp_set_servers` set, with Claude Code's precedence applied. The daemon reads them per account from a control-only Claude Code process started without `--strict-mcp-config` in an empty folder under the account home: its `mcp_status` names each connector and its `get_settings` carries `managedMcpServers` from every managed source. One left out of a project's sessions by `disabledMcpServers` or the page's per-project switch stays out; a connector's switch reaches a running session at its next start. A probe at build confirms a connector passed that way connects and an organization server passed in the set loads under the organization's allowlist; where either fails, the session starts without `--strict-mcp-config` so Claude Code loads both itself, with the person's own servers kept out by construction — none in the account home, installed plugins on `--plugin-dir-no-mcp`, the project's `.mcp.json` servers named in `disabledMcpjsonServers` in the process's `--settings` and sent with `mcp_set_servers` — and a connector or organization server switched off for the project in `deniedMcpServers` there. Connectors load only on a claude.ai subscription login, so an account signed in with an API key or a long-lived token has none (<https://code.claude.com/docs/en/mcp>, §Use MCP servers from claude.ai).
- **Transient-secret handling.** The custody model for credential-bearing values in provider-owned files is transient-by-construction: parse the provider-owned file in memory, use the values for the one purpose that read them, discard — the values are never persisted, logged, served, or embedded in any payload.
- **The fronted connection's secrets.** To reach a server it fronts, the daemon starts it with the environment values its declaration holds, or connects with its headers, reading those values from the provider's config when it connects and holding them only in memory for that connection; they are never stored or logged. The same transient rule covers the `${VAR}` values the daemon expands for a Claude Code session's set, held only for that `mcp_set_servers` call.

## Pitfalls To Avoid

- **Writing the Codex project file blind.** Codex rejects project paths for its own config writes, so the daemon edits `.codex/config.toml` itself; an edit that is not format-preserving, not guarded by the file's hash, or not read back through `config/read` can destroy the repository's own comments or land a server Codex never loads.
- **Using `mcp_toggle`.** It saves "off" for the whole project, so later sessions start with the server off, and it leaves the server running; a switch is always another full-set `mcp_set_servers` call.
- **Renewing a sign-in someone else holds.** A server rotates a public client's refresh token on every renewal, so renewing a sign-in the person's own Claude Code or Codex holds signs that provider out; the daemon renews only sign-ins it holds.
- **Collapsing scope bindings.** Two scopes declaring the same `serverName` are different configurations with independent status and overrides; folding them into one machine-wide identity bleeds one scope's overrides into the other.
- **Honoring annotation self-claims.** A server saying `readOnlyHint: true` is data, not authorization; no decision surface reads annotations (the ADR-014 MUST — stable MCP-spec language since 2025-03-26).
- **Delta-sending `setMcpServers`.** The call replaces the full named-server set; sending a delta silently removes every unsent server. Always send the full desired set.
- **Treating `--help` as the capability census.** The Claude CLI's `--help` omits real flags; capability detection reads the pinned binary and the provider-wire reference, and treats `--help` as a lower bound ([Claude wire §The `--help` is non-authoritative rule](../reference/provider-wire/claude.md#the---help-is-non-authoritative-rule)).
- **Echoing secrets.** Config values, env vars, headers, tokens, authorization URLs, and URL query-string values never enter events, inventory reads, errors beyond guidance messages, or logs; `bearer_token_env_var` names an env var — the _name_ may appear in inventory, the _value_ is read only for a fronted connection and never stored or served; a server URL round-trips query-redacted (parameter names only — §Unified Inventory), and a user name or password in it, accepted as typed, never round-trips.
- **Erroring after the durable leg committed.** A mutation whose durable leg has committed MUST NOT surface a later live-leg failure as a JSON-RPC error — the caller would retry a write that already landed. Committed-then-degraded outcomes are successful responses with honest `applied` grades and per-leg `liveResults[]`; `mcp.server.configInvalid` exists strictly pre-commit.
- **Polling provider status.** Claude Code and Codex both push (notifications / feed emissions); polling is on-demand-only.

## Acceptance Criteria

- [ ] At `Sandboxed`, a person's own stdio tool server writes only where the session's commands write, cannot read a curated credential path, and reaches only the hosts the person's own provider settings give those commands — on Claude Code and on Codex.
- [ ] `mcp.server.list` merges all four sources and round-trips every provider's declared servers with correct `(provider, scope, scopeRef, serverName)` binding separation — same-named servers in two scopes surface as distinct entries whose status and overrides never cross
- [ ] Claude mutation persists through `claude mcp add-json --scope <scope>` before acknowledgment and survives a daemon restart (the restarted daemon's inventory and the next session's `mcp_set_servers` set both contain it); on a reachable control channel the same call additionally applies live and returns grade `liveReconcile`, otherwise `userConfigWrite`

- [ ] The subscribe-then-list handshake is gap-free: an event appended between a subscriber's `mcp.subscribe` acknowledgment and its subsequent `mcp.server.list` read is delivered on the stream, and the stream delivers nothing appended before the acknowledgment
- [ ] First observation of an unknown server creates its binding row
- [ ] Removing a binding removes every approval rule over its tools from the provider's file that holds it, in the same transaction
- [ ] An `idempotencyClass` the person assigns reaches the Spec-004 tool-metadata resolution output; absent assignment resolves to `manualReconcileOnly`; resolution is binding-keyed — with the same `serverName` bound in two scopes, each session's invocation resolves its own effective binding's override, never the other scope's

- [ ] With the binding store unavailable, `mcp.server.list` / `mcp.server.read` serve the degraded entry arm (`bindingStoreUnavailable: true`; store-dependent fields structurally absent, provider-observed fields intact) and every governance mutation fails closed
