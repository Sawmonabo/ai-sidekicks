## Scope

## Required Behavior

- The user must be able to attach a local runtime node to an existing live session. **Caller authorization is a precondition on the whole `runtimenode.*` surface, not on attach alone (BL-141, [ADR-025](../decisions/025-runtime-node-control-plane-caller-authorization.md), ratified 2026-08-10).** The control plane MUST decide every `runtimenode.*` call against the caller's **verified** identity — never against a `userId` carried in the request body — and — for the four mutating procedures — against **persisted row state read under lock inside the same transaction as the mutation it authorizes**, so no ownership or attachment change can commit between the decision and the write; the mutation-free `runtimenode.roster` read instead folds its ownership predicate into the single `READ COMMITTED` statement that projects the roster — one snapshot, nothing to lock, no separate authorization phase (ADR-025 D7). The four mutating procedures require that the caller own the resolved `runtime_node_attachments` row **and** own the session; the control-plane-only `runtimenode.roster` query is session-scoped rather than row-scoped and requires session ownership alone, returning the faithful projection this section's §Interfaces contract pins (never a caller-filtered subset). Every non-permitted outcome — including "no such node" and "no such session" — returns one indistinguishable refusal per procedure, so the surface carries no attachment-existence or session-existence oracle; `detach` keeps its existing idempotent no-op only where no attachment is visible to the caller, and returns the same contracted `runtimenode.permission_denied` (403) the other four return for every non-permitted outcome, in [Error Contracts](../architecture/contracts/error-contracts.md#runtime-node). Presence is writable only through an owned active attachment: a heartbeat for a node the caller does not own writes nothing, closing the forgery path that would otherwise keep a foreign node advertised as live and defeat the §Default Behavior staleness sweep for it. Enforcement + tests ride [Plan-002](../plans/002-runtime-node-attach.md) T3.10–T3.12; the guard itself becomes production-live with no further Plan-002 code change when the control plane's PASETO validation lands and the host-wiring leg swaps the throwing `resolveCurrentUserId` for the verified principal ([ADR-010](../decisions/010-paseto-webauthn-mls-auth.md)).
- Attach must include node identity, declared capabilities, health, and trust context.
- The system must support multiple runtime nodes per session and multiple agents per runtime node.
- Runtime-node attach must not require session recreation.
- Runtime-node detach or offline state must not tear down the session by default.
- The control plane must coordinate runtime-node discovery and presence, but execution must remain local to the attached node.
- At attach, the control plane MUST verify the daemon's reported version against the session's `min_client_version` floor (declared in [Spec-001 §State And Data Implications](./001-session-core.md#state-and-data-implications)). A NULL floor permits all daemons. A daemon below the floor MUST be admitted in read-only state — the daemon remains joined and may read session state, but any subsequent **version-sensitive domain write** (e.g. a capability declaration via `capabilityupdate`) MUST return typed `VERSION_FLOOR_EXCEEDED` per [ADR-018 §Decision #4](../decisions/018-cross-version-compatibility.md#decision); **presence/liveness heartbeats are version-invariant and are EXEMPT** from this refusal — a below-floor node continues to heartbeat and report presence (the exemption holds only while the heartbeat payload stays version-invariant — revisit if a version-sensitive field is ever added to the heartbeat shape). Ejection MUST NOT be the response to a floor mismatch (graceful degradation, not ejection).
- **A node reports its own facts, and they are read rather than sampled.** A node reports whether it is running, when it started, its version, and how much of the machine's processor and memory it is using. Those readings are taken on request — when an operator surface opens, and again when the reader asks for a fresh one — and each carries the time it was taken, so a reader is never shown a figure without knowing how old it is; nothing samples them on a timer and no other surface derives them. A node that does not answer is reported as not answering, which is a different state from the user having no node at all, and the controls that act on it stay available rather than being withdrawn. A ceiling on the memory a tool process may use is a node-level setting the node enforces wherever the operating system lets it, reports as unenforceable where it does not, and, when the ceiling stops a process, records against the session that owns it, naming the command and the figure.
- **The folders a node can reach are a list, and a folder can only be removed while nothing is using it.** A node reports the folders it has been given to reach as one row each, and every row says what is using that folder — how many sessions are using it, or that nothing is — beside the control that removes it. Removing a folder is refused while a session is using it, and the refusal names how many sessions those are; the surface that carries the list says, above the rows, that a folder can only be removed while nothing is using it. With no folder mounted the list says so rather than drawing an empty table, and every other thing the node reports is read as it always is.
- **A shell's write lease.** Extending the same write-capability axis the version floor governs: write access to one of a session's shells is an **exclusive per-shell lease** — a session may open as many shells as the node can hold, each shell is a terminal surface of its own with a holder of its own, and exactly one writer may hold a given shell at a time. Per-shell is the pinned V1 grain: **a session exposes one terminal surface per shell it has open** — this clause is the normative statement of that cardinality, which no other corpus doc pins — so every take, every release and every holder reading names the shell it speaks for through a **terminal identifier**, and this device may hold one shell while another of the user's devices, or a run's write path, holds another. How many shells a session may open is the node's own limit, enforced daemon-side, and where the node can hold no more the refusal is the node's own answer put into words, never a count kept anywhere else. The grain rests on that domain invariant, deliberately not on the sidecar wire: the PTY-host protocol's `session_id` is the sidecar-minted per-spawn PTY handle (`packages/contracts/src/pty-host-protocol.ts#SpawnResponse`), a node-local namespace in which every shell and tool spawn gets its own id ([ADR-019 §Context](../decisions/019-windows-v1-tier-and-pty-sidecar.md#context)) — not the application `SessionId` — and the daemon's terminal-session leg owns the session → shell → PTY-handle mapping, applying each shell's lease check to the writes bound for that shell's handle (a node's other PTYs — a provider process's own shell and its tool spawns — are not terminal surfaces and sit outside the lease entirely). Holder identity is deliberately session-visible presence metadata, per shell — every linked device observes it through the `pty.control_changed` broadcast, which names the shell whose holder changed, and through the roster's `controlHolder`, which carries one entry per held shell: the same who-has-control visibility the surveyed grant-model surfaces expose. Release is holder-gated: only the device holding a shell frees that shell by release, so a holder's own cleanup is never refused (the forced take below transfers a lease rather than releasing it). `session.takeControl` acquires it and `session.releaseControl` frees it, each naming the shell through its terminal identifier (**first-acquire-holds**: an uncontested take succeeds immediately, no approval hop); while **no writer holds that shell's lease, writes to it are refused** (`pty.control_not_held` — fail-closed and per shell, so a lease held on one shell never authorizes a write to another and a writer claims each shell it writes to explicitly, never implicitly); a plain take while another device holds that shell is refused with `pty.control_held_by_other { holderDeviceId }` (handoff is explicit: the holder releases, the next writer takes — and deny-then-manual-retry is the complete V1 protocol: no wait queue, no reservation, no grant-on-release; the denied caller re-takes after observing the release via `pty.control_changed` or the roster, and a FIFO grant queue is a named deferral in §Resolved Questions); a **forced take** is the explicit override for a device holder, and every take and release carries the shell's terminal identifier alike: the forced form of the take moves that shell's lease off another of the user's devices without the holder releasing, broadcasts `pty.control_changed` with a reason naming the force, and leaves every other shell of the session untouched — the displaced device's next write is refused like any non-holder's, so it loses a half-typed line and nothing more. **A forced take is refused while the hold belongs to a run that is writing**, and the refusal is the same typed `pty.control_held_by_other`, no second code being minted for it: a run's writes are stopped by intervening on the run and never by a lease contest, so the recourse is `pause` or `interrupt` ([Spec-003 §Required Behavior](./003-queue-steer-pause-resume.md#required-behavior)) and the run-lifecycle auto-release below then frees that shell on the run's first transition out of `running`; a `session.releaseControl` by a non-holder is likewise refused with `pty.control_not_held` (release is not idempotent-success — it signals a caller-state bug); a `session.takeControl` by the device already holding that shell is by contrast **idempotent success** — the response names the caller as that shell's holder and no `pty.control_changed` broadcasts (no transition occurred); and the lease **auto-releases on holder disconnect** (the holder's presence/attachment drop frees it — no dead-holder lockout): a shell's lease belongs to the connection that took it, so a device dropping off the network — a lid closed mid-command — frees that shell's lease by itself with nothing to press, and a connection closing frees only the shells it was holding. **A second auto-release scopes agent-driven holds to their run's write burst:** when the in-process lease authority grants a take to an agent run's write path, it records the acquiring surface and run id on the daemon-local lease record (bookkeeping beside the projection sequence it already persists — never a wire field, never the coordination projection; the holder surface stays a device identifier, in the same string shape the presence registration carries), and it auto-releases that acquisition on the acquiring run's first lifecycle transition into any state other than `running` arriving after the acquisition (`waiting_for_approval`, `waiting_for_input`, `paused`, or a terminal state per the [Run State Machine](../domain/run-state-machine.md) — the run has stopped actively writing; broadcast `reason: 'auto_released_run_idle'`), so a finished, blocked, or paused agent never strands a shell behind a stale hold, and a resumed run's next write re-takes explicitly (first-acquire-holds — one more cheap, fail-closed acquisition, refused like any take if a remote-future holder has meanwhile taken control); a take from one of the user's devices carries no run binding and is untouched by run transitions — a device hold ends only by `session.releaseControl`, by another device's forced take, or by disconnect; and same-identity re-acquisition is surface-sensitive, because every local writer on the node resolves to the same holder identity and that grain cannot tell them apart: an agent-path take whose acquiring run differs from the recorded one **re-binds the tag to the new run** — a bookkeeping update on the daemon-local record, not a lease transition; the holder is unchanged and nothing broadcasts — so under concurrent runs on the same node (a supported [Spec-014](./014-multi-agent-channels-and-orchestration.md) multi-agent flow) the tag always names the most recent acquiring run and the release trigger tracks it: run B's first write re-takes and re-binds the tag, run A's later idle transition matches no recorded acquisition and releases nothing, and when the recorded run does go idle a still-writing sibling's next write frame simply re-takes (one more cheap, fail-closed acquisition — never a mid-burst hard failure for the sibling); an agent-path retake by the same recorded run and a client-path idempotent self-retake remain true no-ops that never rewrite the record — a burst-scoped hold survives a device holder's interleaved idempotent takes and still releases on its recorded run's transition (durable human intent is re-expressed by one explicit take after the auto-release). Two boundary rules complete the lease semantics: **the lease is not the agent-control surface** — a user who needs an agent's writes stopped intervenes on the run (pause / interrupt, [Spec-003 §Required Behavior](./003-queue-steer-pause-resume.md#required-behavior)) and the run-lifecycle auto-release then frees that shell, so a take/release contest never substitutes for a run intervention; and **no lease transition ever touches the foreground process** — the lease governs who may write next, enforced per write frame at the daemon boundary, so handoff lands between frames, never mid-frame, and taking, releasing, or force-clearing control neither signals nor terminates the running program (stopping the program is an explicit run intervention or terminal action, never a lease side-effect). Every transition broadcasts `pty.control_changed`, naming the shell and the reason ([Spec-005 census](./005-session-event-taxonomy-and-audit-log.md#pty-control-session_lifecycle)). Exactly-one-writer is deliberately stricter than the surveyed multi-editor grants — Warp's granted-Edit session sharing and Live Share's host-granted terminal read/write — on correctness grounds: a PTY exposes a single input stream, so concurrent writers interleave keystrokes into corrupted command lines — the lease makes handoff explicit and instant instead (the survey and tmux's absent-write-lock counter-example in §References; the strict end of the surveyed field agrees — Devin documents pause-before-takeover as its human↔agent handoff discipline, the ordering the run-scoped auto-release above mechanizes, and Replit's shared shell is multi-writer with no input governance, landing it beside tmux as the unguarded counter-example — §References). Enforcement sits at the **daemon terminal-write boundary**, where the authenticated writer identity is known from the execution context. In V1 the take, its forced form and the release are **daemon-transport-only** — registered on the daemon JSON-RPC surface with no control-plane tRPC leg: the terminal-owning daemon is the sole lease authority, and the corpus defines no control-plane→daemon command path that could forward a remote mutation to it ([ADR-008](../decisions/008-default-transports-and-relay-boundaries.md)'s relay is E2E peer connectivity, not a control-plane command channel), so a tRPC registration would place the mutation on a party that can neither adjudicate nor enforce it. The V1 writer identities at the boundary are exactly the identities whose bytes can reach a V1 terminal: the device co-located with the node (local socket — the registry's absent-actor binding) and the node's own agent runs, which bind to that **same device identity** (no wire hop; agents are session-scoped domain actors keyed by `AgentId` per [Spec-014](./014-multi-agent-channels-and-orchestration.md)'s agent surface, so no distinct agent holder exists — the user authorized those runs on their node, their PTY bytes exercise that authority, the holder surface stays that device identifier, a device-vs-own-agent take is the idempotent self-retake case rather than contention, and per-surface attribution rides the adjacent run/agent events on the timeline, not the lease record). Remote devices observe `controlHolder` — one entry per held shell — through the `runtimenode.roster` projection (fed by the daemon-called `runtimenode.leaseupdate` projection-sync mutation — the api-payload Terminal-Control registry's third row, landing with the same Plan-022 Phase 3B leg; producer-bound to the terminal-owning node's active attachment and monotonic per transition sequence, so a stale transport retry or a non-owning attached node cannot overwrite the projection — the registry carries the contract, under one constraint this clause pins normatively, because the projection must be able to reach the states the auto-releases above already require: **the no-dead-holder-lockout rule binds the projection's producer re-bind, not only the daemon-local lease record** — a successor terminal host's publish MUST be accepted once the recorded producer has stopped being a live terminal host, and since a crashed or powered-off host performs no detach, that producer's server-derived `offline` liveness verdict (the sweep-owned §Default Behavior threshold, read and never re-derived by the lease surface) is a sufficient departure signal alongside its attachment leaving the active set; without it the recorded producer stays a dead node forever and the roster can never advertise the true holder again. That constraint does not relocate lease authority — the terminal-owning daemon still adjudicates and enforces, and a refused publish costs projection freshness only); a remote take becomes possible only when a relay-borne terminal-write leg exists, and it MUST then ride the same E2E channel as the terminal bytes it gates, with the relay peer's PASETO-verified device identity as the principal — one authenticated identity for lease and writes by construction; the PTY-sidecar wire is untouched — its `WriteRequest` frame (`packages/contracts/src/pty-host-protocol.ts#WriteRequest`) deliberately carries no holder field, because bytes that reach the sidecar are already lease-authorized (the sidecar's own `WriterUnavailable` write-error is a process-level stream guard beneath this policy layer, not a lease surface). Implementation lands with Plan-022's Phase 3B terminal-session leg.
- **A session's shells.** A terminal surface belongs to a project session: the node starts the user's own `$SHELL` as a login shell with its working directory the session's own tree, so that account's profile, aliases, prompt, version managers and tools are all present; where `$SHELL` names nothing that can be started, the node falls back to the platform's own default shell and says so in words rather than failing quietly. A chat session, bound to a managed workspace and no repository, has no shell. A session's shells belong to that session and keep running whichever session a client happens to be showing; closing a terminal view ends none of them, a shell ends when it is closed or when its own program exits, and an exited shell keeps its record with the exit status rather than disappearing. Quitting a client never ends a shell — the node keeps every open shell running, so a server started in one is still serving after a relaunch. A shell drawn again, by another client or after a switch back or a restart, is replayed at the rows and columns it was last drawn at before its newest frame is written, so a running program's boxes and progress bars come back intact instead of rewrapped, and output already covered by that replay is not sent twice. Each shell keeps a bounded history of its output and drops its oldest lines once it is full; that bound is the node's own replay window, and output no client is watching is held under a bound of the same kind, oldest first, a single burst larger than the bound keeping its tail.
- **Writes to a shell are ordered and bounded.** Bytes reach a shell in the order they were sent: one write is in flight at a time and anything arriving while it is in flight rides the next one, so nothing between the keyboard and the shell can shuffle them. A backlog of resize requests collapses the same way, to the newest size only, so a shell is told the size a drag stopped at rather than every size it passed through. A single write larger than the node's own bound is refused rather than sent, and the refusal names its cause in words, so pasting a whole file into a shell says so instead of jamming the shell's input. Each of these bounds is the node's and is enforced there; no client keeps a figure of its own.

## Default Behavior

- Newly attached runtime nodes default to `online` only after capability declaration succeeds.
- Node capability exposure defaults to least privilege: only explicitly declared capabilities are schedulable.
- Runtime-node heartbeats default to `15s`, matching device-presence cadence unless overridden.
- A runtime node transitions to `degraded` when its most recent heartbeat (`runtime_node_presence.last_heartbeat_at`) is older than `30s` (≈ 2 missed `15s` beats) and to `offline` when older than `60s` (≈ 4 missed beats). The `30s` band between the two thresholds is deliberate hysteresis: a node whose heartbeats resume within it returns to `online` without ever passing through `offline`.
- These `degraded`/`offline` transitions are **server-derived and owned by the control plane** — never self-reported by the node. The control plane's heartbeat service evaluates `last_heartbeat_at` on a periodic staleness sweep and **records the transition on the coordination record** — the sweep-owned `runtime_node_presence.health_state` liveness axis, reconciled into the node's roster-visible state alongside `runtime_node_attachments.state` (per the `capabilityupdate` amendment above). (A silent or dead node sends nothing, so the demotion cannot be heartbeat-ingest-driven — it must be sweep-driven; and the wire health enum is `online | degraded` only, so a node can never report itself `offline`.) The timing guarantee is that a transition is **recorded within one sweep interval of a threshold crossing**; the sweep interval is an implementation choice of [Plan-002 T3.6](../plans/002-runtime-node-attach.md), set finer than the `15s` cadence to keep that bound tight. The control plane authors **no durable `runtime_node.*` session event** for these server-derived transitions in V1 — their durable emission is gated to V1.1 on the node-identity trust anchor ([ADR-017 §Server-Derived Runtime-Node Lifecycle Events](../decisions/017-shared-event-sourcing-scope.md#server-derived-runtime-node-lifecycle-events); §Amendment below).

> **Amendment (approved spec — 2026-06-03, BL-140 / PR #139).** The two thresholds and the sweep owner above were under-specified at original approval, which gave only the `15s` cadence; they are recorded here as canonical defaults rather than deferred to implementation, per [Plan-002 T3.6](../plans/002-runtime-node-attach.md). **Why `2→4` (balanced) over aggressive (`2→3`, `offline` at `45s`) or conservative (`3→6`, `offline` at `90s`):** `offline` is _reversible_ — it neither tears down the session (§Required Behavior) nor blocks reconnect under the same node identity (§Fallback Behavior) — so a false-positive `offline` is cheap, which argues against an over-conservative window; `60s` brackets the reversible Kubernetes node-`NotReady` grace (~40–50s, version-dependent), and the `30s` hysteresis band absorbs a single transient GC or network stall without UI flap. This mirrors the suspect-before-dead staging of SWIM and the reversible-`UNREACHABLE`-before-terminal-`DOWN` model of Akka's Φ-accrual detector (primary sources in §References).

>

>

## Fallback Behavior

- If attach completes but capability validation fails, the node must remain attached in `degraded` or `offline` state rather than being treated as healthy.
- If the control plane cannot broker cross-device visibility, the local daemon may remain usable for `local-only` execution on that machine.
- If a previously attached node disconnects, the session remains intact and the node may later reconnect under the same node identity.

## State And Data Implications

- Runtime-node records must be durable enough to support reconnect and audit.
- Capability declarations and trust posture changes must be emitted as session events. **(V1 scope clarified — §Amendment 2026-06-06: capability declarations are daemon-authored and ship in V1; the trust-posture `revoked` durable event is criterion-gated to V1.1 per [ADR-017 §Server-Derived Runtime-Node Lifecycle Events](../decisions/017-shared-event-sourcing-scope.md#server-derived-runtime-node-lifecycle-events).)**

> **Amendment (approved spec — 2026-06-06, Plan-002 Phase-3 lifecycle-event reconciliation).** The §Default Behavior treatment of the heartbeat sweep's server-derived `degraded` / `offline` transitions — corrected above from durable-event emission to a coordination-record write — and this section's MUST that "capability declarations and trust posture changes must be emitted as session events" are reconciled with accepted [ADR-017 §Server-Derived Runtime-Node Lifecycle Events](../decisions/017-shared-event-sourcing-scope.md#server-derived-runtime-node-lifecycle-events):
>
> - **Server-derived transitions** (heartbeat-staleness `degraded`, heartbeat-loss `offline`, authority-issued `revoked`) are recorded in V1 as **coordination records** (`runtime_node_presence.health_state` / `runtime_node_attachments.state`). V1 authors **no durable `runtime_node.*` session event** for them: the control plane has no event log and no roster-resolvable node-identity key (ADR-017 + ADR-010), a dead/untrusted node cannot self-report, and a peer never observes the liveness fact (heartbeats are control-plane-only), so it could only rubber-stamp the control plane's verdict — the forgeability ADR-017 §Node-Scope Anchor Witnessing names. This is the Kubernetes node-controller / SWIM / SPIFFE failure-detector model already cited in §References. Durable emission + the `degraded`/`revoked` payload schemas are **gated to V1.1** on the node-identity trust anchor (Plan-016 / Plan-002), forward-compatible with V2 MLS `external_senders` ([RFC 9420 §12.1.8](https://www.rfc-editor.org/rfc/rfc9420)).
> - **Capability declarations** (`capability_declared` / `capability_updated`) are **daemon-authored by the declaring node** (a live roster member) and satisfy the MUST in V1 (Plan-002 Phase 2). The **trust-posture (`revoked`) durable event** is the criterion-gated piece — V1's `runtime_node_attachments.state = revoked` coordination record carries the operational trust truth until the V1.1 node-identity anchor lets the control plane author the durable event soundly.
> - **`offline` the event still exists in V1** — authored daemon-side via explicit shutdown (detach, Plan-002 Phase 2); only the **sweep-derived** (heartbeat-loss) `offline` is the V1.1-gated durable-event path. The §Default Behavior coordination-column demotion (degraded/offline) and §Acceptance-Criteria distinguishability of a degraded/offline node from a healthy one are V1 behavior, satisfied by the coordination record.

## Implementation Notes

- Attach should be fast enough to feel interactive, but node health must not flip to healthy before capability validation completes.
- Node identity must be stable across reconnect if the same local daemon is reattaching.
- Scheduling logic must read node capability and health, not just attachment state.

## Pitfalls To Avoid

- Treating session ownership as automatic node trust
- Allowing implicit capability exposure on attach
- Destroying historical node provenance when a node reconnects

## Acceptance Criteria

- [ ] A user can attach a local runtime node to an already active session.
- [ ] A degraded or offline node remains distinguishable from a healthy online node.
- [ ] Multiple runtime nodes can coexist in one session without changing session identity.
- [ ] A daemon attaching with a version below the session's `min_client_version` is admitted in read-only state, surfaces typed `VERSION_FLOOR_EXCEEDED` on any subsequent version-sensitive domain write (e.g. a capability declaration via `capabilityupdate`), and is never ejected for the floor mismatch (per [ADR-018 §Decision #4](../decisions/018-cross-version-compatibility.md#decision)).
- [ ] An uncontested `session.takeControl` for a named shell succeeds immediately (first-acquire-holds), the roster projection's `controlHolder` carries that shell's new holder, and `pty.control_changed` naming that shell is broadcast; every other shell of the session keeps its own holder.
- [ ] A write to a shell while **no** writer holds that shell's lease is refused with typed `pty.control_not_held` (null-holder-refuses-writes) — writes never succeed implicitly, and a lease held on one shell never authorizes a write to another.
- [ ] A plain `session.takeControl` while another device holds that shell is refused with typed `pty.control_held_by_other` carrying `holderDeviceId`; after the holder's `session.releaseControl`, the same take succeeds (explicit handoff). The refusal is terminal for that attempt — V1 keeps no wait queue and no reservation; the denied caller retries after observing the release (`pty.control_changed` or the roster projection).
- [ ] A forced take against another of the user's devices moves that shell's lease with no release by the holder, broadcasts `pty.control_changed` with a reason naming the force, leaves the running foreground program and every other shell untouched, and leaves the displaced device's next write refused as any non-holder's is; a forced take while the hold belongs to a run that is writing is refused with the same typed `pty.control_held_by_other`, and the shell frees only when that run is paused or interrupted and its run-lifecycle auto-release fires.
- [ ] When a shell's lease holder disconnects, that shell's lease auto-releases (its `controlHolder` entry goes; `pty.control_changed` broadcasts for that shell with `reason: 'auto_released_disconnect'`), and subsequent writes to it are refused until a writer re-acquires; the disconnect frees only the shells that connection was holding.
- [ ] A lease acquired through an agent run's write path auto-releases on that run's first lifecycle transition into any state other than `running` after the acquisition (`pty.control_changed` broadcasts `reason: 'auto_released_run_idle'`); a lease taken from one of the user's devices is untouched by run transitions; an agent-path take from a different run on the same node re-binds the daemon-local acquisition record to the new run without any broadcast (holder unchanged), so the release trigger tracks the most recent acquiring run and a concurrent sibling run is never hard-failed mid-burst (its next write re-takes); and a same-run or client-path idempotent self-retake never rewrites the record (no transition occurred), so a burst-scoped hold still releases on its recorded run's transition.

## Resolved Questions and V1 Scope Decisions

- No blocking open questions remain for v1.
- V1 decision: a runtime node may participate in one active session at a time in v1. Multi-session sharing is deferred.
- **Present-but-idle device holder.** A connected-but-idle device does not block another of the user's devices: the forced take moves that shell's lease with no release by the holder, so V1's recourse is the forced take rather than waiting on a voluntary release or a disconnect, and it reaches one shell at a time. What stays refused is a hold that belongs to a run that is writing; there the recourse is a run intervention — pause or interrupt — after which the run-lifecycle auto-release frees that shell. FIFO lease grant to the next requester on release stays deferred and needs no tracker beyond this entry: with a forced take available there is nothing for a grant queue to solve for a device holder, and the run-side case auto-releases on the acquiring run's lifecycle per §Required Behavior.
