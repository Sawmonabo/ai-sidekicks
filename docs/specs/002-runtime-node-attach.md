## Purpose

Define how a user attaches one of their local runtime nodes to a live session.

## Scope

## Required Behavior

- The user must be able to attach a local runtime node to an existing live session. **Caller authorization is a precondition on the whole `runtimenode.*` surface, not on attach alone ([ADR-025](../decisions/025-runtime-node-control-plane-caller-authorization.md)).** The control plane MUST decide every `runtimenode.*` call against the caller's **verified** identity — never against a `userId` carried in the request body — and — for the four mutating procedures — against **persisted row state read under lock inside the same transaction as the mutation it authorizes**, so no ownership or attachment change can commit between the decision and the write; the mutation-free `runtimenode.roster` read instead folds its ownership predicate into the single `READ COMMITTED` statement that projects the roster — one snapshot, nothing to lock, no separate authorization phase. The four mutating procedures require that the caller own the resolved `runtime_node_attachments` row **and** own the session; the control-plane-only `runtimenode.roster` query is session-scoped rather than row-scoped and requires session ownership alone, returning the faithful projection this section's §Interfaces contract pins (never a caller-filtered subset). Every non-permitted outcome — including "no such node" and "no such session" — returns one indistinguishable refusal per procedure, so the surface carries no attachment-existence or session-existence oracle; `detach` keeps its existing idempotent no-op only where no attachment is visible to the caller, and returns the same contracted `runtimenode.permission_denied` (403) the other four return for every non-permitted outcome, in [Error Contracts](../architecture/contracts/error-contracts.md#runtime-node). Presence is writable only through an owned active attachment: a heartbeat for a node the caller does not own writes nothing, closing the forgery path that would otherwise keep a foreign node advertised as live and defeat the §Default Behavior staleness sweep for it. The verified caller identity is the principal the control plane's own authentication establishes ([ADR-010](../decisions/010-paseto-webauthn-mls-auth.md)).
- Attach must include node identity, declared capabilities, health, and trust context.
- The system must support multiple runtime nodes per session and multiple agents per runtime node.
- Runtime-node attach must not require session recreation.
- Runtime-node detach or offline state must not tear down the session by default.
- The control plane must coordinate runtime-node discovery and presence, but execution must remain local to the attached node.
- At attach, the control plane MUST verify the daemon's reported version against the session's `min_client_version` floor (declared in [Spec-001 §State And Data Implications](./001-session-core.md#state-and-data-implications)). A NULL floor permits all daemons. A daemon below the floor MUST be admitted in read-only state — the daemon remains joined and may read session state, but any subsequent **version-sensitive domain write** (e.g. a capability declaration via `capabilityupdate`) MUST return typed `VERSION_FLOOR_EXCEEDED` per [ADR-018 §Decision #4](../decisions/018-cross-version-compatibility.md#decision); **presence/liveness heartbeats are version-invariant and are EXEMPT** from this refusal — a below-floor node continues to heartbeat and report presence (the exemption holds only while the heartbeat payload stays version-invariant — revisit if a version-sensitive field is ever added to the heartbeat shape). Ejection MUST NOT be the response to a floor mismatch (graceful degradation, not ejection).
- **A node reports its own facts, and they are read rather than sampled.** A node reports whether it is running, when it started, its version, and how much of the machine's processor and memory it is using. Those readings are taken on request — when an operator surface opens, and again when the reader asks for a fresh one — and each carries the time it was taken, so a reader is never shown a figure without knowing how old it is; nothing samples them on a timer and no other surface derives them. A node that does not answer is reported as not answering, which is a different state from the user having no node at all, and the controls that act on it stay available rather than being withdrawn. A ceiling on the memory a tool process may use is a node-level setting the node enforces wherever the operating system lets it, reports as unenforceable where it does not, and, when the ceiling stops a process, records against the session that owns it, naming the command and the figure.
- **The folders a node can reach are a list, and a folder can only be removed while nothing is using it.** A node reports the folders it has been given to reach as one row each, and every row says what is using that folder — how many sessions are using it, or that nothing is — beside the control that removes it. Removing a folder is refused while a session is using it, and the refusal names how many sessions those are; the surface that carries the list says, above the rows, that a folder can only be removed while nothing is using it. With no folder mounted the list says so rather than drawing an empty table, and every other thing the node reports is read as it always is.
- **A shell's write lease.** Extending the same write-capability axis the version floor governs: write access to one of a session's shells is an **exclusive per-shell lease** — a session may open as many shells as the node can hold, each shell is a terminal surface of its own with a holder of its own, and exactly one writer may hold a given shell at a time. Per-shell is the V1 grain: **a session exposes one terminal surface per shell it has open**, so every take, every release and every holder reading names the shell it speaks for through a **terminal identifier**, and this device may hold one shell while another of the user's devices, or a run's write path, holds another. How many shells a session may open is the node's own limit, enforced daemon-side, and where the node can hold no more the refusal is the node's own answer put into words, never a count kept anywhere else. The grain rests on that domain invariant, deliberately not on the sidecar wire: the PTY-host protocol's `session_id` is the sidecar-minted per-spawn PTY handle (`packages/contracts/src/pty-host-protocol.ts#SpawnResponse`), a node-local namespace in which every shell and tool spawn gets its own id ([ADR-019 §Context](../decisions/019-windows-v1-tier-and-pty-sidecar.md#context)) — not the application `SessionId` — and the daemon's terminal-session leg owns the session → shell → PTY-handle mapping, applying each shell's lease check to the writes bound for that shell's handle (a node's other PTYs — a provider process's own shell and its tool spawns — are not terminal surfaces and sit outside the lease entirely). Holder identity is deliberately session-visible presence metadata, per shell — every linked device observes it through the `pty.control_changed` broadcast, which names the shell whose holder changed, and through the roster's `controlHolder`, which carries one entry per held shell: the same who-has-control visibility the surveyed grant-model surfaces expose. Release is holder-gated: only the device holding a shell frees that shell by release, so a holder's own cleanup is never refused (the forced take below transfers a lease rather than releasing it). `session.takeControl` acquires it and `session.releaseControl` frees it, each naming the shell through its terminal identifier (**first-acquire-holds**: an uncontested take succeeds immediately, no approval hop); while **no writer holds that shell's lease, writes to it are refused** (`pty.control_not_held` — fail-closed and per shell, so a lease held on one shell never authorizes a write to another and a writer claims each shell it writes to explicitly, never implicitly); a plain take while another device holds that shell is refused with `pty.control_held_by_other { holderDeviceId }` (handoff is explicit: the holder releases, the next writer takes — and deny-then-manual-retry is the complete V1 protocol: no wait queue, no reservation, no grant-on-release; the denied caller re-takes after observing the release via `pty.control_changed` or the roster, and a FIFO grant queue is a named deferral in §Resolved Questions); a **forced take** is the explicit override for a device holder, and every take and release carries the shell's terminal identifier alike: the forced form of the take moves that shell's lease off another of the user's devices without the holder releasing, broadcasts `pty.control_changed` with a reason naming the force, and leaves every other shell of the session untouched — the displaced device's next write is refused like any non-holder's, so it loses a half-typed line and nothing more. **A forced take is refused while the hold belongs to a run that is writing**, and the refusal is the same typed `pty.control_held_by_other`, no second code being minted for it: a run's writes are stopped by intervening on the run and never by a lease contest, so the recourse is `pause` or `interrupt` ([Spec-003 §Required Behavior](./003-queue-steer-pause-resume.md#required-behavior)) and the run-lifecycle auto-release below then frees that shell on the run's first transition out of `running`; a `session.releaseControl` by a non-holder is likewise refused with `pty.control_not_held` (release is not idempotent-success — it signals a caller-state bug); a `session.takeControl` by the device already holding that shell is by contrast **idempotent success** — the response names the caller as that shell's holder and no `pty.control_changed` broadcasts (no transition occurred); and the lease **auto-releases on holder disconnect** (the holder's presence/attachment drop frees it — no dead-holder lockout): a shell's lease belongs to the connection that took it, so a device dropping off the network — a lid closed mid-command — frees that shell's lease by itself with nothing to press, and a connection closing frees only the shells it was holding. **A second auto-release scopes agent-driven holds to their run's write burst:** when the in-process lease authority grants a take to an agent run's write path, it records the acquiring surface and run id on the daemon-local lease record (bookkeeping beside the projection sequence it already persists — never a wire field, never the coordination projection; the holder surface stays a device identifier, in the same string shape the presence registration carries), and it auto-releases that acquisition on the acquiring run's first lifecycle transition into any state other than `running` arriving after the acquisition (`waiting_for_approval`, `waiting_for_input`, `paused`, or a terminal state per the [Run State Machine](../domain/run-state-machine.md) — the run has stopped actively writing; broadcast `reason: 'auto_released_run_idle'`), so a finished, blocked, or paused agent never strands a shell behind a stale hold, and a resumed run's next write re-takes explicitly (first-acquire-holds — one more cheap, fail-closed acquisition, refused like any take if a remote-future holder has meanwhile taken control); a take from one of the user's devices carries no run binding and is untouched by run transitions — a device hold ends only by `session.releaseControl`, by another device's forced take, or by disconnect; and same-identity re-acquisition is surface-sensitive, because every local writer on the node resolves to the same holder identity and that grain cannot tell them apart: an agent-path take whose acquiring run differs from the recorded one **re-binds the tag to the new run** — a bookkeeping update on the daemon-local record, not a lease transition; the holder is unchanged and nothing broadcasts — so under concurrent runs on the same node (a supported [Spec-014](./014-multi-agent-channels-and-orchestration.md) multi-agent flow) the tag always names the most recent acquiring run and the release trigger tracks it: run B's first write re-takes and re-binds the tag, run A's later idle transition matches no recorded acquisition and releases nothing, and when the recorded run does go idle a still-writing sibling's next write frame simply re-takes (one more cheap, fail-closed acquisition — never a mid-burst hard failure for the sibling); an agent-path retake by the same recorded run and a client-path idempotent self-retake remain true no-ops that never rewrite the record — a burst-scoped hold survives a device holder's interleaved idempotent takes and still releases on its recorded run's transition (durable human intent is re-expressed by one explicit take after the auto-release). Two boundary rules complete the lease semantics: **the lease is not the agent-control surface** — a user who needs an agent's writes stopped intervenes on the run (pause / interrupt, [Spec-003 §Required Behavior](./003-queue-steer-pause-resume.md#required-behavior)) and the run-lifecycle auto-release then frees that shell, so a take/release contest never substitutes for a run intervention; and **no lease transition ever touches the foreground process** — the lease governs who may write next, enforced per write frame at the daemon boundary, so handoff lands between frames, never mid-frame, and taking, releasing, or force-clearing control neither signals nor terminates the running program (stopping the program is an explicit run intervention or terminal action, never a lease side-effect). Every transition broadcasts `pty.control_changed`, naming the shell and the reason ([Spec-005 §PTY Control](./005-session-event-taxonomy-and-audit-log.md#pty-control-session_lifecycle)). Exactly-one-writer is deliberately stricter than the surveyed multi-editor grants — Warp's granted-Edit session sharing and Live Share's host-granted terminal read/write — on correctness grounds: a PTY exposes a single input stream, so concurrent writers interleave keystrokes into corrupted command lines — the lease makes handoff explicit and instant instead (the survey and tmux's absent-write-lock counter-example in §References; the strict end of the surveyed field agrees — Devin documents pause-before-takeover as its human↔agent handoff discipline, the ordering the run-scoped auto-release above mechanizes, and Replit's shared shell is multi-writer with no input governance, landing it beside tmux as the unguarded counter-example — §References). Enforcement sits at the **daemon terminal-write boundary**, where the authenticated writer identity is known from the execution context. In V1 the take, its forced form and the release are **daemon-transport-only** — registered on the daemon JSON-RPC surface with no control-plane tRPC leg: the terminal-owning daemon is the sole lease authority, and the corpus defines no control-plane→daemon command path that could forward a remote mutation to it ([ADR-008](../decisions/008-default-transports-and-relay-boundaries.md)'s relay is E2E peer connectivity, not a control-plane command channel), so a tRPC registration would place the mutation on a party that can neither adjudicate nor enforce it. The writer identities at the boundary are the identities whose bytes can reach the terminal: the device beside the node (local socket — the registry's absent-actor binding) and the node's own agent runs, which bind to that **same device identity** (no wire hop; agents are session-scoped domain actors keyed by `AgentId` per [Spec-014](./014-multi-agent-channels-and-orchestration.md)'s agent surface, so no distinct agent holder exists — the user authorized those runs on their node, their PTY bytes exercise that authority, the holder surface stays that device identifier, a device-vs-own-agent take is the idempotent self-retake case rather than contention, and per-surface attribution rides the adjacent run/agent events on the timeline, not the lease record). Remote devices observe `controlHolder` — one entry per held shell — through the `runtimenode.roster` projection (fed by the daemon-called `runtimenode.leaseupdate` projection-sync mutation — producer-bound to the terminal-owning node's active attachment and monotonic per transition sequence, so a stale transport retry or a non-owning attached node cannot overwrite the projection — the registry carries the contract, under one constraint this clause pins normatively, because the projection must be able to reach the states the auto-releases above already require: **the no-dead-holder-lockout rule binds the projection's producer re-bind, not only the daemon-local lease record** — a successor terminal host's publish MUST be accepted once the recorded producer has stopped being a live terminal host, and since a crashed or powered-off host performs no detach, that producer's server-derived `offline` liveness verdict (the sweep-owned §Default Behavior threshold, read and never re-derived by the lease surface) is a sufficient departure signal alongside its attachment leaving the active set; without it the recorded producer stays a dead node forever and the roster can never advertise the true holder again. That constraint does not relocate lease authority — the terminal-owning daemon still adjudicates and enforces, and a refused publish costs projection freshness only); another of the person's devices holds a shell once the relay carries terminal writes, and that take rides the same end-to-end channel as the terminal bytes it gates, with the relay peer's PASETO-verified device identity as the principal — one authenticated identity for lease and writes by construction; the PTY-sidecar wire is untouched — its `WriteRequest` frame (`packages/contracts/src/pty-host-protocol.ts#WriteRequest`) deliberately carries no holder field, because bytes that reach the sidecar are already lease-authorized (the sidecar's own `WriterUnavailable` write-error is a process-level stream guard beneath this policy layer, not a lease surface). A lease carries no time bound and no authority-issued fence: a time-bounded lease would relocate authority to the control plane, which this section admits only for the relay-borne remote take that rides the terminal-byte channel.
- **A session's shells.** A terminal surface belongs to a project session: the node starts the user's own `$SHELL` as a login shell with its working directory the session's own tree, so that account's profile, aliases, prompt, version managers and tools are all present; where `$SHELL` names nothing that can be started, the node falls back to the platform's own default shell and says so in words rather than failing quietly. A chat session, bound to a managed workspace and no repository, has no shell. A session's shells belong to that session and keep running whichever session a client happens to be showing; closing a terminal view ends none of them, a shell ends when it is closed or when its own program exits, and an exited shell keeps its record with the exit status rather than disappearing from a surface that was already showing it. A terminal surface opened afterwards lists the shells the session still has and no others, and starts one only where the session has none, so a session that already holds shells gains no extra one by being looked at. Each shell is named by the title it sets for itself, and by the base name of the program it was started as until it sets one; no name is ever typed by a person. Quitting a client never ends a shell — the node keeps every open shell running, so a server started in one is still serving after a relaunch. A shell drawn again, by another client or after a switch back or a restart, is replayed at the rows and columns it was last drawn at before its newest frame is written, so a running program's boxes and progress bars come back intact instead of rewrapped, and output already covered by that replay is not sent twice. Each shell keeps a bounded history of its output and drops its oldest lines once it is full; that bound is the node's own replay window, and output no client is watching is held under a bound of the same kind, oldest first, a single burst larger than the bound keeping its tail.
- **Writes to a shell are ordered and bounded.** Bytes reach a shell in the order they were sent: one write is in flight at a time and anything arriving while it is in flight rides the next one, so nothing between the keyboard and the shell can shuffle them. A backlog of resize requests collapses the same way, to the newest size only, so a shell is told the size a drag stopped at rather than every size it passed through. A single write larger than the node's own bound is refused rather than sent, and the refusal names its cause in words, so pasting a whole file into a shell says so instead of jamming the shell's input. Where the program running in a shell has asked for pasted text to be marked as pasted, a paste is wrapped that way, so several lines arrive at the prompt as text instead of running themselves, and an end marker carried inside the pasted text is removed so it cannot close the wrapper early. Each of these bounds is the node's and is enforced there; no client keeps a figure of its own.

## Default Behavior

- Newly attached runtime nodes default to `online` only after capability declaration succeeds.
- Node capability exposure defaults to least privilege: only explicitly declared capabilities are schedulable.
- Runtime-node heartbeats default to `15s`, matching device-presence cadence unless overridden.
- A runtime node transitions to `degraded` when its most recent heartbeat (`runtime_node_presence.last_heartbeat_at`) is older than `30s` (≈ 2 missed `15s` beats) and to `offline` when older than `60s` (≈ 4 missed beats). The `30s` band between the two thresholds is deliberate hysteresis: a node whose heartbeats resume within it returns to `online` without ever passing through `offline`. The `2 → 4` staging is deliberate. `offline` is reversible — it neither tears down the session (§Required Behavior) nor blocks reconnect under the same node identity (§Fallback Behavior) — so a false-positive `offline` is cheap, which argues against a more conservative window; `60s` brackets the reversible Kubernetes node-`NotReady` grace (~40–50s, version-dependent), and the `30s` hysteresis band absorbs a single transient GC or network stall without UI flap. This mirrors the suspect-before-dead staging of SWIM and the reversible-`UNREACHABLE`-before-terminal-`DOWN` model of Akka's Φ-accrual detector (§References).
- These `degraded`/`offline` transitions are **server-derived and owned by the control plane** — never self-reported by the node. The control plane's heartbeat service evaluates `last_heartbeat_at` on a periodic staleness sweep and **records the transition on the coordination record** — the sweep-owned `runtime_node_presence.health_state` liveness axis, reconciled into the node's roster-visible state alongside `runtime_node_attachments.state`. (A silent or dead node sends nothing, so the demotion cannot be heartbeat-ingest-driven — it must be sweep-driven; and the wire health enum is `online | degraded` only, so a node can never report itself `offline`.) The timing guarantee is that a transition is **recorded within one sweep interval of a threshold crossing**; the sweep interval is an implementation choice, set finer than the `15s` cadence to keep that bound tight. The control plane authors **no durable `runtime_node.*` session event** for these server-derived transitions in V1 — their durable emission is gated to V1.1 on the node-identity trust anchor ([ADR-017 §Server-Derived Runtime-Node Lifecycle Events](../decisions/017-shared-event-sourcing-scope.md#server-derived-runtime-node-lifecycle-events)).
- `runtimenode.capabilityupdate` refreshes the control plane's discovery snapshot of a node's declared capabilities on its single active `runtime_node_attachments` row. This is coordination, not execution: the **daemon-side node-capability service remains the authoritative declarer**, so the operation MUST NOT drive `registering → online` — that transition requires a successful daemon-side capability declaration.
- A daemon MAY co-report a **capability-health** change through `capabilityupdate.healthChanges`, on the same self-reported-health axis `attach` and `heartbeat` carry — `online ↔ degraded` only, the two-value `RuntimeNodeHealthState`. A daemon reports only its _own_ capability-health and cannot assert `offline` or `revoked`; the request type makes both unrepresentable. **`offline` is liveness-death**: the control-plane sweep derives it from heartbeat staleness, or an explicit `detach` retires the node — never daemon-self-reported. **`revoked` is a trust decision an authority issues** about the node (the session, detach or admin path), never self-asserted. (Established practice: in Kubernetes the kubelet self-reports `Ready` while the node controller derives `Unknown`/NotReady from missed heartbeats; in SWIM/Lifeguard a node's self-reported health is an _input_ to the detector, not the failure verdict; zero-trust/SPIFFE revocation is authority-issued denial of trust, not subject-declared. §References.)
- Daemon-reported capability-health and sweep-derived liveness are **independent health axes with distinct owners**, so a node's roster-visible state **reconciles** both rather than collapsing into a single self-reported scalar two writers could race on, and a recovery on one axis never masks a degradation on the other. The storage backing each axis belongs to its writer. The control-plane operation writes **no** durable `runtime_node.*` event; the durable audit record is the daemon-side node-capability service's `runtime_node.capability_updated` emission, of which this snapshot refresh is the control-plane **projection**. Its `updatedAt` response field is the mutation-time server clock rather than a stored column (the canonical `runtime_node_attachments` schema carries only `attached_at`), and the response `state` is the server-derived liveness position the control plane owns (full `NodeState`).

## Fallback Behavior

- If attach completes but capability validation fails, the node must remain attached in `degraded` or `offline` state rather than being treated as healthy.
- If the control plane cannot broker cross-device visibility, the local daemon may remain usable for `local-only` execution on that machine.
- If a previously attached node disconnects, the session remains intact and the node may later reconnect under the same node identity.
- If a shell cannot be started, the node reports the cause in words and that shell's record reads as exited, taking no input, rather than the failure passing in silence. If the session's own tree has gone from disk, no shell of that session can be started at all, and the node answers with that cause instead, because every shell of the session has lost its working directory.

## Interfaces And Contracts

- `RuntimeNodeAttach` must include session id, user id, node id, capability declarations, and health metadata.
- `RuntimeNodeHeartbeat` must update presence and health.
- `RuntimeNodeCapabilityUpdate` must support capability additions, removals, and health changes.
- `RuntimeNodeDetach` must explicitly retire or disconnect a node from the session.
- `RuntimeNodeRoster` must return the session's full node roster — every `runtime_node_attachments` row for the session, both health axes carried verbatim — via the control-plane-only `runtimenode.roster` query.
- `session.takeControl` / `session.releaseControl` must acquire and free one shell's write lease per §Required Behavior, each carrying that shell's terminal identifier as a required member, and the take must carry the forced form as a member of its own request rather than as a second method, since it is the same act under a stronger precondition; all of it is registered in the [Session Terminal-Control Method Registry](../architecture/contracts/api-payload-contracts.md#session-terminal-control-method-registry). The roster read's response carries `controlHolder` as one entry per held shell — that shell's terminal identifier with the identifier of the device holding it, and no entry for a shell nothing holds — so control-plane-connected clients render each shell's lease from the same faithful projection (daemon-transport clients — including the local-only fallback — render it from the `pty.control_changed` stream, which names the shell whose holder changed and the reason for the change, and from the take/release mutation responses); refusals use the `### PTY` codes in [Error Contracts](../architecture/contracts/error-contracts.md), the forced take's refusal against a writing run's hold among them.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes — including `runtimenode.permission_denied` (403), the single uniform refusal the four mutating procedures and the `runtimenode.roster` read return for every non-permitted caller-authorization outcome per §Required Behavior — `detach` excepted only for a caller with no visible attachment, whose response stays the idempotent no-op ([ADR-025](../decisions/025-runtime-node-control-plane-caller-authorization.md)); `runtimenode.capabilityupdate_conflict` (409) carries its state-guard arm alone (a `registering` attachment cannot be driven `online` by the control plane), and a call with no active row takes the uniform refusal instead, so no arm discloses attachment existence.
- The roster read is the runtime-node namespace's only `query` — its four siblings are `mutation`s — and is **control-plane tRPC only**: the roster is control-plane-owned cross-node coordination state and a daemon knows only itself, so the read deliberately does not ride the dual daemon-JSON-RPC transport the four mutations share. Request `RuntimeNodeRosterRequest = { sessionId }`; response `RuntimeNodeRosterResponse = { nodes: RuntimeNodeRosterEntry[], controlHolder }`, where `controlHolder` carries one entry per held shell, keyed by that shell's terminal identifier and naming the device holding it in the same string shape the presence registration carries, and is empty while no shell of the session is held.
- **The roster read is a faithful projection.** It returns **every** `runtime_node_attachments` row for the session — all five `state` values verbatim (`registering | online | degraded | offline | revoked`), no server-side hiding — because a degraded or offline node must stay distinguishable from a healthy one, and the row count is bounded by distinct nodes ever attached (`UNIQUE(node_id, session_id)` per [shared-postgres-schema.md](../architecture/schemas/shared-postgres-schema.md)). Each `RuntimeNodeRosterEntry` carries **both health axes verbatim plus identity** — `nodeId`, `state` (the slot axis), `healthState` (the three-value `online | degraded | offline` sweep-owned liveness verdict) and `lastHeartbeatAt` (together the liveness axis, LEFT-JOINed from `runtime_node_presence` on `node_id` and **nullable**: no presence row exists until the node's first heartbeat), `readOnly`, `capabilities`, `clientVersion`, `attachedAt` — and **no collapsed health scalar**: reconciling the two axes is the client's render-time concern. The read **never derives staleness** — the heartbeat sweep is the single liveness-derivation writer. `readOnly` is **derived per row at read time** from the stored `client_version` against `sessions.min_client_version` (NULL floor → `false`), with semantics identical to the attach-time verdict, which is what the persisted `client_version` column exists for.
- The roster read **projects coordination records and authors no durable event**, so it does not collide with [ADR-017 §Server-Derived Runtime-Node Lifecycle Events](../decisions/017-shared-event-sourcing-scope.md#server-derived-runtime-node-lifecycle-events): that gate governs durable `runtime_node.*` **event authorship** for the server-derived transitions, not coordination-record reads.

## State And Data Implications

- Runtime-node records must be durable enough to support reconnect and audit.
- Capability declarations and trust posture changes must be emitted as session events. Capability declarations are daemon-authored and ship in V1; the trust-posture `revoked` durable event is gated to V1.1 per [ADR-017 §Server-Derived Runtime-Node Lifecycle Events](../decisions/017-shared-event-sourcing-scope.md#server-derived-runtime-node-lifecycle-events).
- Node health changes must not rewrite historical run provenance.
- **Server-derived transitions** (heartbeat-staleness `degraded`, heartbeat-loss `offline`, authority-issued `revoked`) are recorded in V1 as **coordination records** (`runtime_node_presence.health_state` / `runtime_node_attachments.state`). V1 authors **no durable `runtime_node.*` session event** for them: the control plane has no event log and no roster-resolvable node-identity key ([ADR-017](../decisions/017-shared-event-sourcing-scope.md) + [ADR-010](../decisions/010-paseto-webauthn-mls-auth.md)), a dead or untrusted node cannot self-report, and a peer never observes the liveness fact (heartbeats are control-plane-only), so a peer-authored event could only rubber-stamp the control plane's verdict. This is the Kubernetes node-controller / SWIM / SPIFFE failure-detector model cited in §References. Durable emission and the `degraded`/`revoked` payload schemas are **gated to V1.1** on the node-identity trust anchor, forward-compatible with V2 MLS `external_senders` ([RFC 9420 §12.1.8](https://www.rfc-editor.org/rfc/rfc9420)).
- **Capability declarations** (`capability_declared` / `capability_updated`) are **daemon-authored by the declaring node**, a live roster member, and satisfy the session-event requirement in V1. The **trust-posture (`revoked`) durable event** is the gated piece: V1's `runtime_node_attachments.state = revoked` coordination record carries the operational trust truth until the V1.1 node-identity anchor lets the control plane author the durable event soundly.
- **The `offline` event exists in V1**, authored daemon-side by explicit shutdown (`detach`); only the sweep-derived, heartbeat-loss `offline` is the V1.1-gated durable-event path. The coordination-column demotion to `degraded`/`offline` and a degraded or offline node staying distinguishable from a healthy one are V1 behavior, satisfied by the coordination record.

## Example Flows

- `Example: The user attaches a local runtime node that exposes Codex and Claude drivers to a live session, and later creates a reviewer agent on that node.`
- `Example: A node loses provider access and becomes degraded while the session stays active and readable from the user's other devices.`

## Implementation Notes

- Attach should be fast enough to feel interactive, but node health must not flip to healthy before capability validation completes.
- Node identity must be stable across reconnect if the same local daemon is reattaching.
- Scheduling logic must read node capability and health, not just attachment state.

## Pitfalls To Avoid

- Treating session ownership as automatic node trust
- Allowing implicit capability exposure on attach
- Destroying historical node provenance when a node reconnects

## Acceptance Criteria

- [ ] A user can attach a local runtime node to an already active session.
- [ ] A degraded or offline node remains distinguishable from a healthy online node.
- [ ] Multiple runtime nodes can coexist in one session without changing session identity.
- [ ] A daemon attaching with a version below the session's `min_client_version` is admitted in read-only state, surfaces typed `VERSION_FLOOR_EXCEEDED` on any subsequent version-sensitive domain write (e.g. a capability declaration via `capabilityupdate`), and is never ejected for the floor mismatch (per [ADR-018 §Decision #4](../decisions/018-cross-version-compatibility.md#decision)).
- [ ] An uncontested `session.takeControl` for a named shell succeeds immediately (first-acquire-holds), the roster projection's `controlHolder` carries that shell's new holder, and `pty.control_changed` naming that shell is broadcast; every other shell of the session keeps its own holder.
- [ ] A write to a shell while **no** writer holds that shell's lease is refused with typed `pty.control_not_held` (null-holder-refuses-writes) — writes never succeed implicitly, and a lease held on one shell never authorizes a write to another.
- [ ] A plain `session.takeControl` while another device holds that shell is refused with typed `pty.control_held_by_other` carrying `holderDeviceId`; after the holder's `session.releaseControl`, the same take succeeds (explicit handoff). The refusal is terminal for that attempt — V1 keeps no wait queue and no reservation; the denied caller retries after observing the release (`pty.control_changed` or the roster projection).
- [ ] A forced take against another of the user's devices moves that shell's lease with no release by the holder, broadcasts `pty.control_changed` with a reason naming the force, leaves the running foreground program and every other shell untouched, and leaves the displaced device's next write refused as any non-holder's is; a forced take while the hold belongs to a run that is writing is refused with the same typed `pty.control_held_by_other`, and the shell frees only when that run is paused or interrupted and its run-lifecycle auto-release fires.
- [ ] When a shell's lease holder disconnects, that shell's lease auto-releases (its `controlHolder` entry goes; `pty.control_changed` broadcasts for that shell with `reason: 'auto_released_disconnect'`), and subsequent writes to it are refused until a writer re-acquires; the disconnect frees only the shells that connection was holding.
- [ ] A lease acquired through an agent run's write path auto-releases on that run's first lifecycle transition into any state other than `running` after the acquisition (`pty.control_changed` broadcasts `reason: 'auto_released_run_idle'`); a lease taken from one of the user's devices is untouched by run transitions; an agent-path take from a different run on the same node re-binds the daemon-local acquisition record to the new run without any broadcast (holder unchanged), so the release trigger tracks the most recent acquiring run and a concurrent sibling run is never hard-failed mid-burst (its next write re-takes); and a same-run or client-path idempotent self-retake never rewrites the record (no transition occurred), so a burst-scoped hold still releases on its recorded run's transition.

## Resolved Questions and V1 Scope Decisions

- No blocking open questions remain for v1.
- V1 decision: a runtime node may participate in one active session at a time in v1. Multi-session sharing is deferred.
- **Present-but-idle device holder.** A connected-but-idle device does not block another of the user's devices: the forced take moves that shell's lease with no release by the holder, so V1's recourse is the forced take rather than waiting on a voluntary release or a disconnect, and it reaches one shell at a time. What stays refused is a hold that belongs to a run that is writing; there the recourse is a run intervention — pause or interrupt — after which the run-lifecycle auto-release frees that shell. FIFO lease grant to the next requester on release stays deferred and needs no tracker beyond this entry: with a forced take available there is nothing for a grant queue to solve for a device holder, and the run-side case auto-releases on the acquiring run's lifecycle per §Required Behavior.

  - [Kubernetes — Node Status](https://kubernetes.io/docs/reference/node/node-status/): the kubelet self-reports the `Ready` condition, but the node lifecycle controller sets it to `Unknown` when it "has not heard from the node in the last `node-monitor-grace-period`" — liveness-death is control-plane-derived, not self-asserted. (The closest direct analogue to a daemon that reports its own health while the control plane owns the `offline` verdict.)
  - [SWIM (Das, Gupta, Motivala, DSN 2002)](https://www.cs.cornell.edu/projects/Quicksilver/public_pdfs/SWIM.pdf) + [Lifeguard (Dadgar, Phillips, Currey, 2017)](https://arxiv.org/pdf/1707.00788): failure detection is detector-owned; a node's self-reported local health is an _input_ that improves detector accuracy, never the failure verdict itself.
  - [SPIFFE/SPIRE — zero-trust workload identity](https://github.com/spiffe/spiffe/blob/main/standards/SPIFFE_Federation.md): trust revocation is authority-issued (trust-bundle controlled / denial of further issuance), never declared by the subject workload — a node must not assert its own `revoked` status.
  - [Making illegal states unrepresentable (Wlaschin; principle attributed to Minsky)](https://fsharpforfunandprofit.com/posts/designing-with-types-making-illegal-states-unrepresentable/): encode the invariant in the type so invalid states cannot be constructed, rather than relying on runtime validation. The enforcement mechanism: `healthChanges.state` is the 2-value `RuntimeNodeHealthState`, so `offline`/`revoked` cannot be sent at all.
- Server-derived lifecycle-event authorship (§Default Behavior + §State And Data Implications) — prior art for recording a controller-derived liveness/trust transition as a coordination record rather than a node-authored durable event, the basis for V1 deferring durable `runtime_node.degraded`/`offline`/`revoked` emission to the V1.1 node-identity trust anchor:
  - [Kubernetes — Nodes (node controller & status conditions)](https://kubernetes.io/docs/concepts/architecture/nodes/): the node controller derives `NotReady`/`Unknown` from missed heartbeats and records it as a **status condition in the central coordination store (etcd)** — it does **not** author a signed per-observer "node failed" event into a distributed log. The direct analogue for V1 writing the server-derived transition to `runtime_node_presence.health_state` / `runtime_node_attachments.state` as a coordination record, with no durable session event until a sound authenticated authority (the V1.1 node-identity anchor) exists.
  - [RFC 9420 (MLS) §12.1.8 — External Proposals / `external_senders`](https://www.rfc-editor.org/rfc/rfc9420): the standards-track E2EE realization of the same authority model — a non-member authority _proposes_ a lifecycle change and group members _commit_ it — the V2 forward-compatible target once the control plane is an authenticated `external_senders` entity.
- Shared-terminal write-lease precedent survey (§Required Behavior) — the multi-editor grant models this spec's exactly-one-writer lease is deliberately stricter than, the counter-example confirming the unguarded-PTY failure mode, and the strict-discipline precedents the run-scoped auto-release mechanizes:
  - [VS Code Live Share — shared terminals](https://learn.microsoft.com/en-us/visualstudio/liveshare/use/share-server-visual-studio-code): shared terminals default read-only; the host explicitly grants read/write — write access to a shared terminal is a host-granted capability, never ambient.
  - [Warp — session sharing](https://docs.warp.dev/knowledge-and-collaboration/session-sharing/): joiners enter in View mode; Edit is a granted elevation — the same explicit-grant posture, on a commercial terminal whose multi-editor grant permits concurrent writers once granted.
  - [tmux(1)](https://man.openbsd.org/tmux): attached clients share one input stream with no built-in write lock (`attach -r` is voluntary read-only self-restraint) — concurrent writers interleave keystrokes into a single corrupted command line, the failure mode the exclusive lease exists to prevent.
  - [Devin — Session Tools (takeover)](https://docs.devin.ai/work-with-devin/devin-session-tools): "Make sure that Devin is paused before taking over the IDE to avoid simultaneous, conflicting changes" — the documented pause-before-takeover discipline for human↔agent handoff; `auto_released_run_idle` mechanizes that ordering (a paused, blocked, or finished agent frees the terminal, and a human stops an agent through a run intervention, never a lease race).
  - [Replit — Shell2 (2024-10)](https://replit.com/blog/shell2): shells stayed per-user for years ("Shells have remained specific to each user") with the workflow hazard named outright (joining a friend's session "without breaking my friend's workflow"), and sharing became an explicit join of a named session — separate-by-default confirming the shared-input-stream hazard; the joined session itself is multi-writer with no input governance ("multiple writers (each pane can listen to input and send to the same PTY)"), landing it beside tmux as the unguarded counter-example once sharing begins.
