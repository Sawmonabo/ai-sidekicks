## Purpose

Define the lifecycle of worktrees and the execution modes available for repo-bound runs.

## Scope

This spec covers `read-only`, `branch`, `worktree`, and `ephemeral clone` execution modes plus worktree creation, reuse, and retirement.

## Non-Goals

- PR preparation details
- Merge policy
- Diff artifact rendering

## Required Behavior

- Every repo-bound run must bind to exactly one canonical execution mode: `read-only`, `branch`, `worktree`, or `ephemeral clone`.
- Repo-bound coding runs must default to `worktree` execution mode when the repository supports worktrees.
- `read-only` mode must prohibit repo mutation and support inspection, review, and diagnostic tasks.
- `branch` mode must be an explicit writable override that uses an existing checkout with explicit branch context.
- Starting a writable worktree-mode run must create or reuse a valid worktree before execution begins.
- `ephemeral clone` mode must provision a disposable isolated clone before writable execution begins.
- The system must not silently fall back from intended worktree mode to mutating the main checkout.
- The system must not silently substitute one canonical execution mode for another when the requested mode is unavailable.
- Worktree lifecycle must support `creating`, `ready`, `dirty`, `merged`, `retired`, and `failed`.
- Reusing an existing worktree must be explicit and must preserve branch and provenance context.
- A session names the worktree it is standing in, and the branch that tree was cut off, on its own composer strip, and that one name holds for every surface the session opens — the conversation, the review pane, the terminal and the preview alike. No pane takes a branch label of its own. A session with no repository attached names no worktree and carries no worktree control at all.
- Moving between worktrees is the only way a session changes what it is working on: the folder a session stands in keeps the branch it was cut with for as long as the session is there, and the daemon never checks out, creates or switches a branch inside it. Another line of work is another tree.
- Choosing another tree while the session is idle moves it at once — same session, same history, new execution root — and the provider process reconnects there. Choosing one while a turn is running never refuses: the move is held as a pending intent, named on that tree's own row and on the strip, and applied at the run boundary. Re-targeting the tree the session is already in is the cancel, and a later request supersedes the pending one rather than queueing behind it.
- The control a session moves from has exactly three modes — the list, the create form, and an inline remove confirmation standing in the row's own place — and the list carries the repository root as a row of its own, so a session can stand in the main checkout as readily as in a worktree. It is as wide as its widest row reads at the current text size, so no row truncates. It offers no merge, no branch graph, no stash and no rebase; nothing in a session deletes or prunes a branch, and nothing in a session lists or creates a tag. Branch hygiene is a repository-wide chore done with the whole repository in front of the user, in the session's own terminal or on the hosting service's pages, and a session's list simply stops naming the branches that go.
- The worktree name on the strip opens that control and never the workspace inspector; the inspector stays reachable from the list's own details entry, from the session header's overflow menu and from its keyboard chord.
- Each row in the list carries the tree's name, the base it was cut off, how far ahead and how far behind its upstream it is, how many files are uncommitted, and which sessions are using it. A figure that is zero is left off rather than drawn as a zero. Unpushed means commits not reachable from any remote-tracking branch of that folder, and it is local knowledge.
- The list is re-read whenever a run starts or ends anywhere on the project, so every row's occupancy and every retirement control's reason stay true while the list is open; several such events arriving together are read once. A read that fails draws no rows at all — rather than rows whose occupancy the daemon could not verify — and says so in their place, while the repository-root row, the create entry and the details entry stand either way.
- While the session's own run is live every row in the list is inert and says why: once in the list's header, and again on each row, reaching assistive technology as a disabled row carrying its reason.
- A branch is minted with the folder that holds it. The create form takes a name and a base and cuts a new branch of that name off that base in its own worktree; there is no way to make a branch on its own, because a branch with no folder gives a session nowhere to stand. The suggested name is a fixed leading part and the session's own short identifier, neither of them editable, over a tail derived from the session's title, which is; only the tail is validated — against the shape `^[a-z0-9][a-z0-9._-]*$` and against the names already taken — and the create action stays inert with its reason until it validates. The form shows the path the tree will be made at — `~/.ai-sidekicks/worktrees/<project>/<name>`, under the daemon's own execution-roots directory and never inside the attached checkout — and the base list the daemon supplies, filtered as the user types.
- A base another worktree already has checked out is offered in that list greyed, naming the tree that holds it and pointing at that tree as the way to reach it, and it answers no press, because cutting a tree needs the checkout.
- Creating a tree acts on the press: the folder exists, the session is standing in it, and the strip names it before any message is sent. Nothing about creating a tree waits for a first turn.
- Carrying uncommitted work into a new tree stashes it, untracked files included, applies it on the new tree and drops the stash. It is refused unless the new base equals the branch the session is on, and a failure tears the new tree down, keeps the stash, and puts the command that recovers it in the error text.
- After the tree is provisioned the project's own setup steps run in place, in order, as part of provisioning: the steps are the user's own recorded list for that project — files to copy, commands to run in order, and a limit after which a step gives up ([Spec-007 §Required Behavior](./007-repo-attachment-and-workspace-binding.md#required-behavior)) — and the repository's own git hooks and setup scripts stay switched off throughout. No step raises an approval card, none waits on one, and no remembered approval rule is ever made from one.
- Those steps are edited as a draft on the project's own row on the projects settings page, and the provisioning report links there: two ordered lists and the limit, each list taking a new entry from its own field and each entry removable one at a time, a list with no entries saying so, nothing written until the draft is saved, and the unsaved state said in one line with a revert beside the save.
- Provisioning reports itself where the session is, in three stages — making the tree, running the project's steps, and warming the caches the session will read — naming the stage it is on, the step that failed with that step's own error and its output, and a retry that runs the failed step and the ones after it. A run that finishes clears itself; a failure stands until it is answered, and leaving the session and coming back shows it exactly as it stood.
- Retiring a worktree is refused while the directory is busy for any session, with the occupying session named, and for no other reason; it never stops a run. The confirmation names every risk in place — uncommitted files, unpushed commits, sessions attached, or that the tree is clean and unused — and the confirming action says it discards while there is something to lose. Retirement sweeps every session standing in that tree back to the repository root, clears any pending move pointing at it, and appends a flow row for each session that moved.
- A branch that changed outside the console is written back to the session's own record by the daemon, and every surface that names the branch follows it.

## Default Behavior

- Default branch naming pattern is `sidekicks/<session-short-id>/<task-slug>`.
- Default writable coding runs use one dedicated worktree per active task or branch context.
- `branch` mode and `ephemeral clone` mode are explicit selections or policy-driven overrides, not hidden defaults.
- Worktree retirement defaults to preserving metadata and artifacts even when filesystem cleanup later removes the checkout.
- Worktree or ephemeral-clone preparation must never execute repository-controlled code. The repository's own setup scripts are not run, and provisioning git invocations must neutralize hook execution at the invocation layer (e.g. an empty `core.hooksPath`), so cloning or adding a worktree on a hostile repository executes nothing the repository supplied. The steps that do run after provisioning are the project's own recorded list — the user's steps, not the repository's (§Required Behavior).

## Fallback Behavior

- If a repo does not support worktrees, the system may offer `ephemeral clone` or explicit `branch` mode where safe, but it must mark the selected mode distinctly from normal worktree mode.
- If worktree creation fails, the run must remain blocked in setup rather than mutating the main checkout.
- If ephemeral clone preparation fails, the run must remain blocked in setup unless an operator or user explicitly selects a different execution mode.
- "Blocked in setup" is a concrete run disposition: the run parks in the `starting` state with the typed preparation error surfaced; no `running` transition fires, the failure never silently mutates any checkout, and the parked run remains interruptible (cancel applies to `starting` runs, transitioning them to `interrupted`).
- If an intended reuse candidate is dirty or incompatible with the requested branch strategy, the system must require explicit user choice.
- Explicit reuse choice is candidate-anchored: the caller names the reuse candidate, and consent to bind a dirty candidate is a separate explicit acknowledgement — a candidate that becomes dirty between check and bind is refused rather than silently bound; a candidate incompatible with the requested branch strategy is never bindable.
- Preparing an execution root against a `stale` workspace must be refused with the typed stale error until the workspace is repaired (write-gate posture per Spec-007).
- When a repo mount detaches or an owning workspace archives, dependent non-terminal worktrees and ephemeral clones are retired by the daemon's asynchronous cleanup sweep — retirement is recorded and evented with metadata preserved; disk removal follows asynchronously. Retiring the clone backing a live `ephemeral clone`-mode workspace's current root returns that workspace to `provisioning` (awaiting the next per-run prepare); `stale` is reserved for fault paths ([Spec-007 §Ephemeral Clone Lifecycle](./007-repo-attachment-and-workspace-binding.md#ephemeral-clone-lifecycle)).
- If a repository requires setup commands before useful execution, they are recorded as the project's own setup steps and run as part of provisioning where the session can watch each step, its output and its failure (§Required Behavior) — never as a hidden execution-root side effect, and never as repository-controlled code the provisioning invokes.
- Moving between worktrees is never refused: while the session is idle the move applies at once, asked mid-turn it is held and applied at the run boundary, and while the session's own run is live the list's rows are inert with the reason stated rather than answering a press with a refusal.
- An invalid worktree name is answered on the create form's own error line, stating either the allowed shape or that the name is already taken, with the create action inert and its reason given while the editable tail is empty.
- A failed carry of uncommitted work into a new tree tears that tree down, keeps the stash, and puts the command that recovers it in the error text.
- A failed setup step stops provisioning at that step, names it, shows its own error and output, and offers a retry that runs it and the steps after it; the report stands until it is answered, across leaving the session and coming back.
- Retirement refused because the tree is occupied names the occupying session where the refusal is rendered (`worktree.retire_conflict`).

## Interfaces And Contracts

- `ExecutionModeSelect` must distinguish `read-only`, `branch`, `worktree`, and `ephemeral clone`. Selection records the canonical mode and transitions the workspace; it does not materialize per-task execution roots — materialization is `ExecutionRootPrepare`'s surface (read-only resolves synchronously at select; an explicit mode switch is exactly one selection mutation, never a client-sequenced select-then-prepare chain).
- `ExecutionRootPrepare` must create or bind the execution root required by the selected mode before a run enters `running`. Explicit worktree reuse rides this interface by naming the candidate worktree.
- `WorktreeReuseCheck` must report branch, cleanliness, and compatibility.
- `EphemeralClonePrepare` must report clone root, lifecycle, and cleanup policy.
- `EphemeralCloneDispose` must support explicit disposal of a prepared clone (the `manual` cleanup-policy arm and operator-driven cleanup).
- `WorktreeRetire` must record retirement even if filesystem deletion happens asynchronously.
- `WorktreeStatusRead` must expose the session's worktree and ephemeral-clone records — lifecycle state, branch, cleanup bookkeeping, and provenance — as a daemon-owned read surface.
- Clients reach this spec's surface under the `repo.*` wire namespace: execution-root preparation, the worktree reuse check, the worktree status read, worktree retirement, and the ephemeral-clone prepare and dispose.
- One worktree-candidate read serves, per candidate directory, how far ahead and how far behind its upstream the tree's branch is, how many files are uncommitted, and which sessions occupy it. Its figures are the daemon's background fetch's — run every few minutes while a session on the project is live, never pulling and never pruning, under the user's own git identity — so after a failed fetch the read returns the figures it had and the instant they were read, and a client draws them with that instant rather than refreshing on its own. It is the same read a worktree list re-reads on every run start and end (§Required Behavior).
- One ordered branch list is a daemon read, supplied in one order and drawn in it: the project's default branch first, then the branches this project's recent bases were picked from, most recent first, then the rest by the date of their newest commit. Each row carries its ahead and behind figures from the same background fetch and names the worktree holding that branch, or marks it as the project's default. The one list serves worktree creation and the review surface's base picker ([Spec-009 §Required Behavior](./009-gitflow-pr-and-diff-attribution.md#required-behavior)), so a branch is ordered and annotated once; filtering narrows what is drawn and never reorders it. Every figure and tag on a row is a fact: no branch row carries an action anywhere.
- Worktree creation and retirement each leave their record through the worktree lifecycle events the session event taxonomy already registers, and the sweep of sessions back to the repository root appends one `session.swept_to_repo_root` event per session it moved ([Spec-005](./005-session-event-taxonomy-and-audit-log.md)), so that row survives a reload; no further worktree or ephemeral-clone transition is evented (§Resolved Questions and V1 Scope Decisions).
- Tree staleness is a signal the daemon emits from watching a workspace's working folder; no client infers it. A working folder too large for the machine to watch is checked on a slow tick instead, the bound read from what the machine's own watch limit allows rather than a fixed number of folders, and the signal carries which of the two it came from so the surface showing it can say that a stale mark may be minutes late.

- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- Worktree records must persist branch name, owning repo mount, lifecycle state, and provenance to the creating session and run.
- Execution mode must be stored as run setup data: the daemon persists a per-run execution binding (run → workspace, mode, execution root, and any worktree / ephemeral clone / branch context involved) that survives the run for provenance.
- Branch context must be persisted for writable `branch`, `worktree`, and `ephemeral clone` runs. The branch-context record is a polymorphic carrier: worktree-mode rows reference the worktree, ephemeral-clone rows reference the clone, and branch-mode rows reference neither (the main checkout carries no Plan-008 root row).
- Dirty and merged state belong to daemon-owned workspace projections.
- A workspace whose execution root is handed to an active run is `busy` for the run's duration (one holding run at a time in V1); concurrent root handoff is refused with a typed busy error, and the workspace returns to `ready` when the holding run reaches a terminal state. The exclusivity is keyed on the NORMALIZED root — the workspace's persisted checkout root, the enclosing working-tree top level the snapshot service operates on (§Turn-Boundary Snapshots' applicability rule; derived at bind while the tree exists and rewritten when provisioning installs a new execution root, identity for daemon-provisioned worktrees and clones, which are top levels already — so independent provisioned roots never serialize against each other) — never on the bound path alone: two workspaces bound to disjoint subdirectories of one checkout normalize to one tree, and letting both hold active runs would hand each a whole-tree snapshot capture over the other's live state, so the second handoff refuses with the same typed busy error naming the holding run. The exclusivity is **node-scoped, by the shape of the comparison rather than by assumption**: the hold is decided by comparing normalized checkout roots across workspace records the deciding node owns — ownership resolved through each record's owning repo mount, the same owning-node key active-mount uniqueness binds canonical roots on — never across every record the local database happens to hold, because a workspace record carries no node marker of its own and a node's database lawfully holds records for other nodes' mounts (Spec-007 §State And Data Implications: the same absolute path on two different nodes is two distinct node-local filesystems, and both attach). Two nodes' identical absolute spellings of a checkout path therefore never enter one comparison set. No cross-node coordination is required to enforce this rule, and none is implied by it; a run on another node is never the holding run this refusal names.
- Daemon-provisioned execution roots (worktrees and ephemeral clones) live under the daemon's own execution-roots directory — a worktree at `~/.ai-sidekicks/worktrees/<project>/<name>`, the path the create form's hint shows — never inside the attached repository checkout; they are inside the session's trust envelope by construction ([Spec-007 §Local Trust Envelope (V1 Definition)](./007-repo-attachment-and-workspace-binding.md#local-trust-envelope-v1-definition)).

## Turn-Boundary Snapshots

At each turn boundary of a writable-mode run — turn completion is first-class via the `completionKind` carve on `run.completed` ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)) — the daemon records the worktree's project state as a snapshot ref. A snapshot **names a point to return to**; it is not a way to put files back. Every file restore reads from the daemon's per-session file checkpoint store ([Spec-013 §Required Behavior](013-persistence-recovery-and-replay.md#required-behavior)) — one mechanism, the same on both providers ([Spec-003 §Driver-Level Rollback Mechanics](003-queue-steer-pause-resume.md#driver-level-rollback-mechanics)) — and a restore aimed at a named snapshot of the session reads from that same store, the snapshot supplying the point to return to. Capture, the ref namespace it writes into, and the prune that removes a ref are the whole mechanism: nothing here checks a tree out, deletes a file on disk, or writes the repository index.

- **Scope:** tracked **and** untracked files; ignored **untracked** paths are deliberately excluded — ignore rules govern untracked files only, so a tracked file that happens to match `.gitignore` is recorded like any other tracked file (tracking wins over ignoring, git's own semantics) — and "ignored" means **project-declared** rules only: the in-tree `.gitignore` files, themselves recorded by the snapshot. Host-local ignore sources — `core.excludesFile` (user or global config) and `$GIT_DIR/info/exclude` — are deliberately never consulted: a developer's private ignore patterns are not project declarations, and an untracked project file matching one is still project state the snapshot must name on every host (confirmed on git 2.50.1: `git add -A` under a global exclude pattern or an `info/exclude` entry silently omits matching untracked files — which is why the capture pipeline below is plumbing with explicit exclusion flags rather than porcelain). **Submodule boundary:** snapshots operate at the superproject's gitlink level — the recorded tree carries each submodule's then-current commit OID (a `160000` gitlink entry, exactly what porcelain staging would record) — and capture never descends into a submodule worktree: a submodule is its own repository whose files never enter the superproject index, so interior modified and untracked state is outside what a snapshot names (confirmed on git 2.50.1: the superproject's untracked listing never reports interior files). Scoped that way, a snapshot never names derived state the project itself declares disposable (build artifacts, caches, `node_modules`), and per-turn snapshots never churn the object store with artifact trees.
- **Capture (temp-index recipe):** with `GIT_INDEX_FILE` pointing at a scratch index located **outside** the worktree, and one base OID resolved at entry (`<base>` = `git rev-parse HEAD`) reused for **both** the tree base and the recorded parent — so the snapshot stays self-consistent if `HEAD` moves mid-capture; symbolic `HEAD` at the two legs would re-resolve independently, recording an old-`HEAD` tree under a new-`HEAD` parent (confirmed on git 2.50.1) — `git read-tree <base>` → `git ls-files -co --exclude-per-directory=.gitignore -z | git -c core.autocrlf=false -c core.safecrlf=false -c core.attributesFile=/dev/null update-index --add --remove -z --stdin` (with `GIT_ATTR_NOSYSTEM=1` in the environment) → the untracked-embedded-repository normalization pass → `git write-tree` → `git -c i18n.commitEncoding=utf-8 commit-tree <written-tree> -p <base> -F -` → the create-only `git update-ref` of the Ref namespace bullet. The staging pipeline is the plumbing equivalent of `git add -A` — byte-identical trees under identical inputs, verified — with every exclusion and conversion input pinned: `-c` re-lists the temp index's seeded `<base>` paths so `--add --remove` re-stats each one, staging tracked modifications and deletions, while `-o --exclude-per-directory=.gitignore` lists untracked files honoring **in-tree `.gitignore` rules only**, the Scope bullet's project-declared boundary and the reason porcelain `git add -A` is not the pipeline (it also honors `core.excludesFile` and `$GIT_DIR/info/exclude`, with no off-switch). `core.autocrlf=false` pins check-in CRLF→LF conversion off — git's own default, a neutralize-by-pinning rather than a behavior choice — because a host `core.autocrlf=input` or `true` re-hashes CRLF worktree bytes to LF blobs, changing blob, tree and snapshot OIDs for identical worktree bytes (confirmed on git 2.50.1); `core.safecrlf=false` pins that same channel's **veto** off, since present-or-pinned-false stage the identical tree and what a host `core.safecrlf=true` adds is a fatal, which would turn whether a turn can be snapshotted at all into a host-config question; `core.attributesFile=/dev/null` and `GIT_ATTR_NOSYSTEM=1` take the user and system attribute files out of the conversion decision, while in-tree `.gitattributes` — a project declaration, checked in and identical on every host — stays deliberately honored. One host-local input has no config or environment off-switch, `$GIT_DIR/info/attributes`, and is declared out of contract: the daemon never writes it, and a host that adds conversion-changing rules there breaks its own snapshot-OID stability, nothing else. The commit leg is noninteractive and host-independent by construction: the fixed message is streamed on a stdin the daemon writes and closes, where an unmanaged stdin read hangs wherever the daemon leaves stdin open, and the daemon supplies `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` **and `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE`** — the turn-boundary instant at a fixed UTC offset — because without explicit ident environment `commit-tree` hard-fails (`Author identity unknown`) in passwd-less daemon and continuous-integration containers and silently stamps a passwd-derived operating-system ident elsewhere, which is both a machine-dependent snapshot OID and an identity leak into the object store, and because author and committer dates, timezone included, are commit-object fields and therefore OID inputs ([git-commit-tree](https://git-scm.com/docs/git-commit-tree) documents the stdin message read and the ident and date environment alike). The explicit `i18n.commitEncoding=utf-8` pin neutralizes repository and global config: set to anything but UTF-8 it writes an `encoding` header into the commit object, changing the snapshot OID for identical project state, while pinned UTF-8 is git's default and writes no header (confirmed on git 2.50.1; `commit.gpgsign` was likewise checked and is inert for this plumbing command). The message is **fixed** in the sense the determinism property needs: it is a pure function of **project state** — the fixed string plus state-derived sorted-JSON trailers streamed as further paragraphs — so two hosts capturing identical project state mint the same snapshot OID, skipped paths included, because a trailer's paths and their order are read out of the tree being captured. The out-of-worktree temp index also keeps snapshots from self-capturing index files: a worktree-resident scratch index would surface to the pipeline's own `ls-files -o` listing, and to `git status`, as stray untracked content. Capture failure is recorded on the capture diagnostic and **never blocks or fails the turn** — a snapshot is a name for a point, not a turn gate. `git stash create` was experimentally refuted for this job ([git-stash](https://git-scm.com/docs/git-stash): the `create` subcommand takes only a positional `[<message>]`, untracked support being a `push`-only flag): it captures tracked paths only, has no untracked option, and silently swallows `-u` as a commit message, so a stash-style snapshot would name turns minus every file they created.
- **Capture's embedded repositories and its two skip classes:** a non-ignored untracked embedded git repository lists as a single trailing-slash directory entry that `update-index --add` silently drops (both behaviors confirmed on git 2.50.1), so the normalization pass records each one as a `160000` gitlink via `git update-index --add --cacheinfo 160000,<embedded-HEAD>,<path>` — porcelain staging's own embedded-repository representation ([git-update-index](https://git-scm.com/docs/git-update-index) documents the `<mode>,<object>,<path>` cacheinfo form as a direct index insert; the `160000` gitlink is git's superproject submodule representation, [gitsubmodules](https://git-scm.com/docs/gitsubmodules); [git-add](https://git-scm.com/docs/git-add) documents embedded-repository staging and its warning via `--no-warn-embedded-repo`). Two classes cannot be recorded as a gitlink at all and are **skipped and enumerated in the capture diagnostic** rather than failing the capture: a commitless embedded repository (unborn `HEAD`), and one whose `HEAD` hex length disagrees with the superproject's object format (a sha1 repository under a sha256 superproject, or the mirror case). Skipping is the honest answer measured against what porcelain does with the same inputs on git 2.50.1: `git add -A` hard-fails the commitless class (`does not have a commit checked out`) and **fabricates** the gitlink OID for the mixed-format one, zero-padding a sha1 `HEAD` to 64 hex under a sha256 superproject and truncating a sha256 `HEAD` to 40 in the mirror case — against fabricate-or-fail, skip-and-enumerate degrades honestly, both classes reaching the diagnostic, neither silently dropped and neither invented. The snapshot commit's `Skipped-Embedded-Repositories:` trailer names those paths, written **only** when the list is non-empty so a capture that skipped nothing mints a byte-identical message and OID to the trailerless form; the trailer is the snapshot's own record that a path was skipped rather than absent, the tree holding no entry at it either way.
- **Capture in a sparse execution root:** a root is sparse exactly when `core.sparseCheckout` is true — the config bit alone, never conjoined with pattern-file existence — and the malformed state that predicate routes fail-closed: a truthy bit with the rules file deleted or unreadable takes the sparse arm and draws a typed capture refusal, never a not-sparse misclassification into the unpartitioned pipeline. Unpartitioned staging there would truncate the snapshot: the scratch index seeded from `<base>` carries no `skip-worktree` bits, so every out-of-cone path is listed, found absent from the pruned worktree, and dropped from the tree by `--remove` (confirmed on git 2.50.1), and the snapshot would then name a tree the project never had. Any sparse execution root is in scope — `branch` mode is the canonical exposure, its root being the user's own checkout, and `worktree` mode inherits it whenever the canonical mount is sparse, since `git worktree add` copies the current worktree's sparse-checkout patterns and worktree config into the new worktree ([git/git `53255916b7`](https://github.com/git/git/commit/53255916b7), shipped in git 2.36), while an ephemeral clone starts full, `git clone` copying objects and refs but never the source's config or sparse definition (measured) — and detection is root-keyed, so every mode routes through the same partitioning. Capture in a sparse root partitions both of its listings by the repository's own sparse-checkout definition, evaluated through git's own sparsity matcher: `git sparse-checkout check-rules` ([git-sparse-checkout](https://git-scm.com/docs/git-sparse-checkout); plumbing since git 2.41, [git/git `00408adeac`](https://github.com/git/git/commit/00408adeac)), run in the execution root against the worktree's live rules and mode with the candidate paths fed on stdin, output meaning in-cone. That is the availability floor and the only oracle: on older git the subcommand is absent and capture in a sparse root fails closed through its typed failure envelope rather than degrading to the unpartitioned pipeline, the matcher is fatal in a root with no sparse-checkout state (measured) so it runs only downstream of detection and never as the detector, and gitignore-semantics exclude machinery (`git ls-files -c -i --exclude-from=<pattern-file>`) was measured divergent — sparse patterns share gitignore syntax but not gitignore evaluation, which cannot re-include below an excluded parent ([gitignore](https://git-scm.com/docs/gitignore)), so a non-cone `/*` plus `!/a/b/` definition over-includes git's own out-of-cone `a/b/` subtree and the re-stat stream then drops it from the snapshot (both oracles measured on git 2.50.1). The in-cone side re-stats exactly as the pipeline above does, over a scratch index seeded from the **live index** rather than from `<base>`: the seed copy is taken from the per-root live index path resolved via `git rev-parse --git-path index` (a linked worktree's index lives under the main repository's `.git/worktrees/<id>/`, where a literal `.git/index.lock` fails against the gitfile or locks another worktree's index), under git's own index lock — the resolved path's sibling `<index>.lock` created exclusively and released without writing, because git prepares an index replacement at the lock path and renames it over the index, so an unlocked seed silently reads the pre-write index (measured on git 2.50.1) and omits racing staged state; acquisition contention retries briefly, then fails the capture typed. The live seed is what matches porcelain: porcelain updates no entry outside the cone ([git-add](https://git-scm.com/docs/git-add), `--sparse` being its opt-in), so out-of-cone cached entries persist at their live cached state and a `git add --sparse`-staged entry surviving a cone shrink reaches porcelain's tree, where a `<base>` seed was measured to revert it, and an out-of-cone unmerged entry fails `write-tree` typed exactly as porcelain refuses that index state. Out-of-cone untracked files are never added, and the boundary-time out-of-cone path set — untracked and intent-to-add paths alike, subtracted against the written tree on the listing's own bytes rather than on decoded strings, since two distinct on-disk paths can decode alike — is recorded on the snapshot commit's `Sparse-Boundary-Paths:` trailer, ordered after `Skipped-Embedded-Repositories:` wherever both are present since trailer bytes are OID inputs. That trailer is a sorted JSON string array whose strings are `latin1`-encoded, one code point per path byte, which makes it a record of bytes rather than of text and its order byte-lexicographic by construction: a decoded rendering collapses every invalid sequence onto one replacement character, so a path that is not valid UTF-8 could not be named honestly at all. A trailing-slash listing entry keeps its slash verbatim, because a directory git refused to descend is a directory capture could not enumerate. The trailer is written in a detected sparse root, an empty set spelling `[]`, and never in a non-sparse root, whose message bytes are what they were without the sparse pipeline. A snapshot of a sparse root is therefore a **full tree**, matching what `git add -A` stages there byte for byte under the pipeline's pinned exclusion and conversion inputs — the Scope bullet's host-local-ignore divergence standing unchanged in sparse roots, so a host-excluded in-cone untracked file is still deliberately recorded where porcelain would skip it — measured as byte-identical trees across cone, non-cone positive-pattern and non-cone negation fixtures, top-level and nested, in the clean sparse state, in the staged-out-of-cone state (`git add --sparse` then a cone shrink, where only the live-index seed matches porcelain's tree) and in the materialized-out-of-cone state alike, where porcelain keeps the index entry and refuses the on-disk edit because the cone is pattern-defined rather than `skip-worktree`-bit-defined, git clearing the bit the moment a path materializes while `git add -A` still refuses it. Sparseness stays a checkout-time projection, never a capture-time truncation, and the sparse evaluation stays structurally separate from the `.gitignore` exclusion pass — the sparsity matcher reads no gitignore source and the untracked listing keeps honoring in-tree `.gitignore` alone, so an ignored in-cone file is never swept into the stream (likewise measured). One scoped residual is recorded rather than closed, confined to out-of-cone **byte state**: content a user materialized on disk at a tracked out-of-cone path is outside what a snapshot names, capture recording the live cached state for such a path exactly as porcelain would. Implementation: [Plan-008](../plans/008-worktree-lifecycle-and-execution-modes.md) Phase 6 (T6.1, invariant I-008-24).
- **Ref namespace:** snapshot commits land under `refs/sidekicks/runs/<runId>/epoch-<E>/turn-<N>` — **never on `refs/heads/`** — so snapshots are invisible to branch history, PR preparation, and diff attribution by construction. `<E>` is the run's **execution epoch** ([Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) — `0` before any rollback, advanced with each **accepted `run.rolled_back`** — a confirmed conversation rewind, a position-mismatch rewind confirmed at the recorded floor included — regardless of what the file leg did, while an outcome with no confirmed rewind leaves it unchanged): same-run resurrection re-uses position ordinals, so a post-rollback re-execution's `turn-<N>` capture mints a **new** ref under its own `epoch-<E>` segment rather than resolving to the superseded epoch's tree. The closing `git update-ref --no-deref refs/sidekicks/runs/<runId>/epoch-<E>/turn-<N> <snapshot-commit> ""` is **create-only**: the trailing empty `<old-value>` is a compare-and-swap against ref absence (git refuses with `reference already exists` — confirmed on git 2.50.1), so a retried or duplicated capture of the same run, epoch and turn can never repoint an existing snapshot ref at later file state — the first successful write wins, and a capture retry that finds the ref already written treats it as idempotent success, returning the recorded OID. `--no-deref` is part of that spelling rather than decoration: git splits an update of a **symbolic** ref into an update of its referent and carries the must-not-exist check there with it, so an unflagged create against a dangling in-namespace symref plants an arbitrary branch at the snapshot commit and reports success (confirmed on git 2.50.1) — flagged, the write acts on the validated name itself and nothing outside the namespace moves. The same flag rides the retention prune's per-ref delete for the mirror reason: an unflagged `update-ref -d` resolves its compare-and-swap **through** a planted symref and deletes the branch it points at, exiting 0 and reporting a clean prune (likewise confirmed). Both directions of that channel are closed by the same flag, and neither guard substitutes for the other — the unflagged create mints a branch outside the namespace, the unflagged delete destroys one. [Spec-009](009-gitflow-pr-and-diff-attribution.md) is unaffected: its commits remain agent/user-authored and reviewable, and no Spec-009 surface changes.
- **Retention:** snapshot refs prune when the run's retention window closes (terminal state plus the configured window); the prune task lives with the run-retention owner. In `ephemeral clone` mode the refs live in the clone's own object store, so they additionally share the clone's disposal lifecycle (the configurable TTL below): a disposed clone takes its snapshot refs with it, and the points they named can no longer be named. The session's file checkpoints are unaffected, being held with the session outside the checkout ([Spec-013 §Required Behavior](013-persistence-recovery-and-replay.md#required-behavior)), so a restore anchored on one of the user's own messages stays available after disposal.
- **Applicability:** `worktree`, `branch`, and `ephemeral clone` writable modes; `read-only` runs snapshot nothing. In `branch` mode the execution root is the workspace's bound checkout — the user's own live working tree, main checkout or linked worktree, whichever the workspace bound (`workspaces.metadata.boundRoot`, which names the tree the workspace bound rather than the repository's canonical root — [Spec-007 §Repo Identity And Common-Directory Keying (V1 Definition)](./007-repo-attachment-and-workspace-binding.md#repo-identity-and-common-directory-keying-v1-definition)) — so a snapshot there names the state of a shared live checkout, branch mode's deliberately coarser isolation applying to what a snapshot records exactly as it does to execution. Capture's execution-root input is normalized to the enclosing working-tree **top level** at the snapshot service's entry: its `ls-files` legs are cwd-scoped, so an un-normalized nested execution root — a workspace bound at a subdirectory of its checkout — would record only the nested prefix, and the snapshot would name a narrower tree extent than the one the run is working in. The normalized top level is derived only while the bound directory exists — recorded at bind as the workspace's persisted checkout-root carrier (`workspaces.metadata.checkoutRoot`, beside `boundRoot`), rewritten whenever provisioning completion installs a new execution root, since a daemon-provisioned worktree or clone is its own top level, so the carrier always names the current checkout, the user's own for branch mode and the provisioned one otherwise. **How the recorded value reaches capture.** It is supplied, never looked up: the snapshot legs are pure callees that receive every root they operate on, so the normalized checkout root is captured per run into the run's execution-context record at run setup — while the tree exists and under a caller that knows which workspace the run is bound to — and is then handed to capture as an ordinary caller-resolved input, exactly as the execution root and execution mode already are. Capture, which by definition runs while the tree exists, re-verifies the supplied value against the live tree and fails the capture typed on disagreement. That widened extent is what the busy rule of §State And Data Implications keys on: run tenancy is exclusive per normalized checkout, never merely per bound subdirectory, so no two active runs ever share one enclosing working tree. A session that moves to another worktree is reprovisioned onto that tree — at once while the session is idle, and at the run boundary when the move was asked mid-turn (§Required Behavior) — and that provisioning completion rewrites the persisted checkout root exactly as any other does, so the value captured per run always names the tree the run actually ran in.

## Example Flows

- `Example: A user starts an implementation run. The daemon creates a dedicated worktree, binds the run to it, and only then starts provider execution.`
- `Example: The user opens the repo in read-only mode, inspects diffs, and cannot accidentally mutate the checkout.`
- `Example: A repository cannot use worktrees safely, so a user explicitly selects ephemeral clone mode and the daemon prepares a disposable clone for the writable run.`
- `Example: A later follow-up run explicitly reuses the same worktree because it targets the same branch and task lineage.`

## Implementation Notes

- Branch-name defaults should be deterministic and human-readable, but collision handling must be explicit.
- Worktree reuse is valuable, but the system should bias toward isolation over convenience.
- `branch` mode remains important for special maintenance tasks, but it must stay clearly non-default for mutable coding work.
- Repository bootstrap or setup commands should be modeled as explicit approved work, not as an implicit part of worktree creation.

## Pitfalls To Avoid

- Mutating the main checkout as a hidden fallback
- Treating worktree reuse as implicit magic
- Losing run provenance when a worktree is later retired

## Acceptance Criteria

- [ ] A writable coding run on a git repo defaults to worktree mode.
- [ ] The execution-mode contract distinguishes `read-only`, `branch`, `worktree`, and `ephemeral clone`.
- [ ] Worktree creation failure blocks the run instead of mutating the main checkout.
- [ ] Reused worktrees remain explicitly linked to branch and prior run context.

## Resolved Questions and V1 Scope Decisions

- No blocking open questions remain for v1.
- V1 decision: branch prefix and slugging rules are product-defined and locked for consistency in v1: `sidekicks/<session-short-id>/<task-slug>`, where `<session-short-id>` is the **last** 8 hex characters of the session UUID (hyphens stripped, lowercased — the low 32 of its random bits: the daemon mints RFC 9562 v7 ids, whose first 8 characters are the high bits of the millisecond timestamp and are shared by every id minted within one 65,536 ms window, so a first-8 short id collides across sessions on one repository) and `<task-slug>` is derived from the originating queue-item summary — lowercased, non-alphanumeric runs collapsed to `-`, trimmed of leading/trailing `-`, truncated to 40 characters at a `-` boundary — falling back to `run-<run-short-id>` (the last 8 hex of the run id, by the same rule) when no summary exists. User-configurable naming rules are deferred.
- V1 decision: branch-name collision handling is provenance-split. A caller-supplied branch name that collides with a live checkout is refused with the typed collision error — user intent is never silently adapted. A daemon-derived default name that collides takes the first free ordinal suffix (`-2`, `-3`, …) as part of the deterministic derivation rule; the chosen name is persisted and reported verbatim. Collision never implies implicit reuse: a fresh worktree on a suffixed name is created; explicit reuse remains the only reuse path.
- V1 decision: worktree base refs default to the repo mount's current HEAD branch; an explicit base ref may be supplied at preparation. Preparation against a detached-HEAD mount with no explicit base ref is refused rather than guessed.
- V1 decision: `branch` mode binds to the bound checkout's existing branch state and verifies it matches the requested branch context; the daemon never checks out, creates, or switches branches inside the BOUND checkout — the user's main checkout or linked worktree, per `workspaces.metadata.boundRoot` (a mismatch is a typed refusal; the prohibition names the BOUND checkout, the tree branch mode runs in, rather than the repository's main checkout).
- V1 decision: ephemeral-clone TTL is daemon configuration (default 24 hours per [Spec-007 §Ephemeral Clone Lifecycle](./007-repo-attachment-and-workspace-binding.md#ephemeral-clone-lifecycle)), not a wire parameter.
- V1 decision: worktree and ephemeral-clone state transitions are not separately evented in V1 beyond the worktree lifecycle events already registered in the Spec-005 taxonomy; the `failed` transition and all ephemeral-clone transitions surface through the owning workspace's lifecycle events (`workspace.stale` carries the failure detail) and the `WorktreeStatusRead` surface. The Spec-005 event-type registry stays closed.
- V1 decision: the repository's own setup scripts and git hooks never run during worktree or ephemeral-clone preparation. The steps that do run are the project's own recorded list, which runs as part of provisioning, in the session's view, and under no approval (§Required Behavior).
