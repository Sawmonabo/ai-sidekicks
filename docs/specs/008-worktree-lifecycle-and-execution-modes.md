## Purpose

Define the lifecycle of worktrees and the places a project session works in.

## Scope

This spec covers the two places a project session works in — a worktree of its own, `provisioned-worktree`, and the checkout the project already has, `bound-root` — plus worktree creation, moving between trees, removal, keeping a removed tree and putting it back, and the turn snapshots and command captures taken in a session's working folder. There is no disposable copy and no read-only place: how much a session may change is its permission level.

## Non-Goals

- PR preparation details
- Merge policy
- Diff artifact rendering

## Required Behavior

- Every repo-bound run works in exactly one of two places: `provisioned-worktree`, a worktree the daemon's worktree lifecycle made for the session or one it made earlier that the session moved into, or `bound-root`, the root already bound to the session's workspace — the project's checkout, main or linked, or a chat's managed workspace — at which the daemon makes nothing. A chat session is always `bound-root` on its own managed workspace and never gets a worktree.
- A new project session starts in a new worktree of its own unless the person chose the project's checkout when creating it; the machine's `Default checkout for a new project session` setting, `A new worktree` out of the box, decides the default and never overrides a choice made at creation.
- How much a session may change is its permission level ([Spec-010](./010-approvals-permissions-and-trust-boundaries.md)); a session at the `Read-only` level works in either place and changes nothing.
- The `bound-root` arm runs at the root the workspace bound (`workspaces.metadata.boundRoot`), never at the repository's canonical root, so a workspace bound at a linked worktree works in that tree.
- Starting a run in a `provisioned-worktree` workspace must have its worktree ready before execution begins.
- The system must not silently fall back from a worktree to the project's checkout, and must never put a session in a place the person did not choose.
- Worktree lifecycle must support `creating`, `ready`, `dirty`, `merged`, `retired`, and `failed`.
- A session can bind to any worktree git lists for the repository. One the person made binds as an existing checkout and is never stamped as one this daemon provisioned or reused; moving into one this daemon created preserves its branch and provenance context. Removing a worktree or deleting a branch stays limited to what the daemon's records say it made.
- Two sessions may work in one worktree, or in the project's checkout, at the same time: nothing holds a folder for one session's turn, and `Undo to here` puts back only its own session's changes, naming a file another session also changed as `also changed by <session>` and leaving it unless the person includes it.
- A session names the worktree it is standing in, and the branch that tree was cut off, on its own composer strip, and that one name holds for every surface the session opens — the conversation, the review pane, the terminal and the preview alike. No pane takes a branch label of its own. A session with no repository attached names no worktree and carries no worktree control at all.
- Moving between worktrees is the only way a session changes what it is working on: the folder a session stands in keeps the branch it was cut with for as long as the session is there, and the daemon never checks out, creates or switches a branch inside it. Another line of work is another tree.
- Choosing another tree while the session is idle moves it at once — same session, same history, new execution root — and the provider process reconnects there. Choosing one while a turn is running never refuses: the move is held as a pending intent, named on that tree's own row, `switching when this run ends` with a single `Cancel`, and on the strip, `<current> → <target> when this run ends`, and applied at the run boundary. Re-targeting the tree the session is already in is the cancel, and a later request supersedes the pending one rather than queueing behind it.
- The control a session moves from has exactly three modes — the list, the create form, and an inline remove confirmation standing in the row's own place — and the list carries the repository root as a row of its own, so a session can stand in the main checkout as readily as in a worktree. It is as wide as its widest row reads at the current text size, so no row truncates. It offers no merge, no branch graph, no stash and no rebase; nothing in a session deletes or prunes a branch, and nothing in a session lists or creates a tag. Branch hygiene is a repository-wide chore done with the whole repository in front of the user, in the session's own terminal or on the hosting service's pages, and a session's list simply stops naming the branches that go.
- The worktree name on the strip reads `<tree> off <base>`, the tree the session is in and the branch it was cut off, whatever pane is open. It opens that control and never the workspace inspector; the inspector stays reachable from the list's own details entry, from the session header's overflow menu and from its keyboard chord.
- Each row in the list carries the tree's name, the base it was cut off, how far ahead and how far behind its upstream it is, how many files are uncommitted, and which sessions are using it; the row's second line reads `↑<ahead>` then `↓<behind>`. A figure that is zero is left off rather than drawn as a zero. Unpushed means commits not reachable from any remote-tracking branch of that folder, and it is local knowledge.
- The list is re-read whenever a run starts or ends anywhere on the project, so every row's occupancy and every retirement control's reason stay true while the list is open; several such events arriving together are read once. A read that fails draws no rows at all — rather than rows whose occupancy the daemon could not verify — and says so in their place, `Could not read the worktrees`, while the repository-root row, the create entry and the details entry stand either way.
- While the session's own run is live every row in the list is inert and says why: once in the list's header, and again on each row, reaching assistive technology as a disabled row carrying its reason.
- A branch is minted with the folder that holds it. The create form takes a name and a base and cuts a new branch of that name off that base in its own worktree; there is no way to make a branch on its own, because a branch with no folder gives a session nowhere to stand. The suggested name is the project's branch-name pattern filled in (§Default Behavior): every part of it is fixed except the tail derived from the session's title, which is the one part the form edits. The tail is shaped as it is typed — capitals lowered, every character outside `a-z 0-9 . _ -` turned into a hyphen, a leading `.`, `_` or `-` dropped — so it always matches `^[a-z0-9][a-z0-9._-]*$`, and under the field the whole name shows as it will be made, `Will be created as <name>.` The whole name is checked by git's own branch-name rule (`git check-ref-format --branch`) and against every branch in the repository, including one that would hold it or sit inside it (`feature` beside `feature/x`), and a name git refuses shows git's own error line under the field (§Fallback Behavior), the create action staying inert until it passes. The suggestion never opens on a refusal: when its tail clashes it takes the next free `-2`, `-3`. The form shows the path the tree will be made at — `~/.ai-sidekicks/worktrees/<project>/<session-short-id>-<task-slug>/`, under the daemon's own execution-roots directory and never inside the attached checkout, `<project>` being the slug fixed at attach — and the base list the daemon supplies, filtered as the user types. The fixed parts, the suggested tail and the path hint come from the same daemon function that creates the tree and names its folder.
- A base another worktree already has checked out is offered in that list grayed, its hover title reading `Checked out in <worktree>. Pick that tree from the switcher.`, and it answers no press, because cutting a tree needs the checkout.
- `Create and move here` acts on the press: the folder exists, the session is standing in it, and the strip names it before any message is sent. The press is one execution-root preparation on the session's own workspace, which prepares that workspace again in place on the new tree; there is no separate create and move. Nothing about creating a tree waits for a first turn.
- Carrying uncommitted work into a new tree stashes it, untracked files included, applies it on the new tree and drops the stash. It is refused unless the new base equals the branch the session is on, and a failure tears the new tree down, keeps the stash, and puts the command that recovers it in the error text.
- After the tree is made the project's own setup steps run in place, in order, as part of preparation: the steps are the user's own recorded list for that project — files to copy, commands to run in order, and a limit after which a step gives up ([Spec-007 §Required Behavior](./007-repo-attachment-and-workspace-binding.md#required-behavior)). The steps and the service's own git calls run with the repository's own git config, its hooks included, and the repository's own setup scripts are not run. No step raises an approval card, none waits on one, and no approval rule is ever made from one.
- Those steps are edited as a draft on the project's own row on the projects settings page, and the preparation report links there: two ordered lists and the limit, each list taking a new entry from its own field and each entry removable one at a time, a list with no entries saying so, nothing written until the draft is saved, and the unsaved state said in one line with a revert beside the save.
- Preparation reports itself in place inside the composer card, in three stages — making the tree, running the project's steps, and a warm step — naming the stage it is on, the step that failed with that step's own error and its output, and a retry that runs the failed step and the ones after it. The warm step is one `git status` in the new tree while nothing else runs, then the tree's watches started (the working-folder watch and the git-folder watch), and the `@` file index only if the daemon keeps it live; the ship facts and the branch list cache nothing, so the warm step reads neither early. A run that finishes clears itself; a failure stands until it is answered, and leaving the session and coming back shows it exactly as it stood.
- Removing a worktree is refused while an agent is running in it, with the occupying session named, and for no other reason; it never stops a run. The confirmation names every risk in place — uncommitted files, ignored files (such as `.env`) that would be destroyed, unpushed commits, sessions attached, or `Clean and unused.` — and never reads `Clean and unused.` while ignored files would be destroyed. With something to lose the button reads `Discard and remove` and the risk line ends `A copy is kept until you delete it.`; the plain `Remove` removes nothing the risk line did not show, and when the tree changed since the risks were read the confirmation redraws them and removes nothing. Removal sweeps every session standing in that tree back to the repository root, clears any pending move pointing at it, and appends a flow row for each session that moved; that row carries `Put back` while the copy is kept. Before the tree is moved or deleted, the daemon ends the processes it started whose working folder is inside it: Terminal pane shells and project processes.
- `Discard and remove` keeps what it discards: the daemon moves the worktree's folder whole, by one rename, into the project's kept folder `~/.ai-sidekicks/worktrees/<project>/.removed/<name>-<removed id>/`, so tracked changes, untracked and ignored files, symbolic links, executable bits, empty folders, nested repositories and files of any size stay exactly as they were. Where the rename would cross a volume, which happens only when something is mounted inside the worktrees folder, the daemon copies instead (`cp -c -R` for APFS clones, a real copy elsewhere) and deletes the original only once the copy is complete. Before git's record of the worktree is pruned, it copies that record whole except `gitdir` and `commondir` (the index, `HEAD`, `ORIG_HEAD`, `logs/`, `refs/`, a sparse checkout's rules, the tree's own `config.worktree`, its submodules' git folders and any merge or rebase in progress), packs the objects the kept index names that HEAD's tree does not into the kept folder, and pins the commit the tree stood on, and every commit git's saved worktree state names, under `refs/sidekicks/removed/<removed id>/`; a locked record is unlocked first. After the press, the row's place reads `<name> removed · Put back` until the switcher closes. A plain `Remove`, sent only for a tree with nothing to lose, deletes it. Where the operating system refuses the rename because a program outside the app holds a file in the tree open, the discard is refused with `A program outside the app is using a file in this worktree.` and nothing is removed.
- Nothing deletes a kept worktree on its own — no age, no sweep and no `Delete old data`. It goes only when the person presses `Delete now` on the runtime settings page, which confirms in place, `Delete the kept copy of <name>? This cannot be undone.` The runtime settings page lists each kept worktree beneath its project's worktrees, `<name> · removed <date> · <size>`, with `Put back` and `Delete now`.
- `Put back` recreates the worktree at its own path, from the switcher's row, the swept sessions' flow row or the runtime settings page. The tree goes back on its own branch when that branch still points at the recorded commit (in a rebase, the recorded `orig-head`) and no other worktree holds it, and otherwise on `<branch>-restored` at the recorded commit, the result saying `Put back on <branch>-restored: <branch> has moved since.`; a taken name goes back as `<name>-restored`. It is refused, with its reason on the row, with `The project is no longer attached.`, `The repository is no longer at <path>.` or `A worktree named <name>-restored already exists.`; refused or not, the kept copy stays. A put-back tree does not move the swept sessions back; the person moves a session into it with the switcher.
- The worktrees the app made are listed on the runtime settings page beneath their project's folder, marked `worktree`, and each one's `Remove` is this removal.
- A branch that changed outside the console is written back to the session's own record by the daemon, and every surface that names the branch follows it.
- On a Windows computer with WSL, a worktree whose repository or folder is on the other side's disk is locked (`git worktree add --lock`, or `git worktree lock` after a move), so the other side's git, which sees its path as missing, never prunes it; new worktrees are made in the service's own home, on its own disk. When the service moves between Windows and the distribution, it reconnects every worktree with git's own `git worktree repair` from the main worktree, naming each linked worktree's new path, after the first good start on the new side, and locks each worktree now on the other side's disk. The service marks every such folder with `onOtherSideDisk: true` on its `repo.projectList` row (a project) or its `repo.mountList` row (a worktree), set from the folder's path form, and the folder refreshes its git and file views on window focus and before each diff read, never on a timer.

## Default Behavior

- A new worktree's branch is named by the machine's `Branch names` pattern, `sidekicks/{session}/{title}` until the person changes it, or by the project's own pattern when one is set: `{title}` is the tail derived from the session title and appears exactly once, and `{session}` is the session's short id (the last 8 hex characters of its id) and is optional. With the default pattern a tree's branch is `sidekicks/<session-short-id>/<task-slug>` and its folder `~/.ai-sidekicks/worktrees/<project>/<session-short-id>-<task-slug>/`, flat. A pattern applies to worktrees made afterward; a branch already made keeps its name, and the daemon knows the branches it made by its worktree records, never by their names. A pattern is refused in place with nothing written: `Put {title} in the name once.` when `{title}` is missing or repeated, and `Git does not accept this as a branch name.` when the filled-in name fails `git check-ref-format --branch`.
- A new project session starts in a new worktree of its own; the project's checkout is a place the person picks, at creation or in the switcher, never a hidden default.
- Worktree retirement defaults to preserving metadata and artifacts even when filesystem cleanup later removes the checkout.
- Worktree preparation runs with the repository's own git config: the daemon sets no `core.hooksPath` or `core.fsmonitor` override, so the repository's own git hooks run on the service's git calls as they do on the person's. The repository's own setup scripts are not run. The steps that do run after preparation are the project's own recorded list — the user's steps, not the repository's (§Required Behavior).

## Fallback Behavior

- If a worktree cannot be made in a repository, the session stays where it was and the failure is said where it is; the person may pick the project's checkout, which the daemon never picks for them.
- If worktree creation fails, the run must remain blocked in setup rather than mutating the main checkout.
- "Blocked in setup" is a concrete run disposition: the run parks in the `starting` state with the typed preparation error surfaced; no `running` transition fires, the failure never silently mutates any checkout, and the parked run remains interruptible (cancel applies to `starting` runs, transitioning them to `interrupted`).
- Moving into an existing worktree is the person's own pick of that tree's row in the switcher, which shows its uncommitted count and the sessions using it before the press; the pick is the explicit choice, and every worktree git lists for the repository is offered.
- Preparing an execution root against a `stale` workspace must be refused with the typed stale error until the workspace is repaired (write-gate posture per Spec-007).
- When a repo mount detaches or an owning workspace archives, dependent non-terminal worktrees are retired by the daemon's asynchronous cleanup sweep — retirement is recorded and evented with metadata preserved, and nothing on disk is touched: a worktree's folder is removed from disk only when `repo.worktreeRetire` retired it. The sweep skips a chat's managed workspace, which goes only with its session's purge.
- If a repository requires setup commands before useful execution, they are recorded as the project's own setup steps and run as part of preparation where the session can watch each step, its output and its failure (§Required Behavior) — never as a hidden execution-root side effect, and never as repository-controlled code the preparation invokes.
- Moving between worktrees is never refused: while the session is idle the move applies at once, asked mid-turn it is held and applied at the run boundary, and while the session's own run is live the list's rows are inert with the reason stated rather than answering a press with a refusal.
- A worktree name git refuses — by its branch-name rule, or because it clashes with a branch in the repository, one that would hold it or sit inside it included — is answered on the create form's own error line with git's error line exactly as git prints it, `fatal:` included (`fatal: 'x y' is not a valid branch name`, `fatal: a branch named 'feature/x' already exists`), and none of git's `hint:` lines, which advise its command line; the create action stays inert with that line given, and while the editable tail is empty.
- A failed carry of uncommitted work into a new tree tears that tree down, keeps the stash, and puts the command that recovers it in the error text.
- A failed setup step stops preparation at that step, names it, shows its own error and output, and offers a retry that runs it and the steps after it; the report stands until it is answered, across leaving the session and coming back.
- Removal refused because an agent is running in the tree names the occupying session where the refusal is rendered (`worktree.retire_conflict`, `reason: root_busy`); a plain `Remove` of a tree that changed since its risks were read is refused with `reason: has_changes` and the current risks, and the confirmation redraws them.

## Interfaces And Contracts

- A session's place is chosen in `session.create`'s `binding` for a new session and in `repo.workspaceBind` for a converted chat ([Spec-007 §Interfaces And Contracts](./007-repo-attachment-and-workspace-binding.md#interfaces-and-contracts)); `executionMode` is `"bound-root" | "provisioned-worktree"`.
- `ExecutionRootPrepare` (`repo.executionRootPrepare`, with `carryUncommitted`) makes the execution root a run needs ready before the run enters `running`: it creates the worktree at the path and on the branch the create function names, or binds the root already bound. `Create and move here` is one call on the session's own workspace, which prepares it again in place on the new tree. The daemon records the base it was given, which the branch list's recent-bases tier reads.
- `session.setWorkingFolder` moves a session into another tree; asked mid-turn it holds the move as a pending intent on the session's own record, applied at the run boundary, and re-targeting the tree the session is already in is the cancel.
- `WorktreeStatusRead` (`repo.worktreeStatusRead`, keyed by project) is the switcher's list: the repository-root row and each worktree with its base, ahead and behind figures, uncommitted count, the sessions using it, and `countsAsOf`, the instant its figures were read. Its figures are the daemon's background fetch's — run every few minutes while a session on the project is live, never pulling and never pruning, under the user's own git identity — so after a failed fetch the read returns the figures it had and the instant they were read, and a client draws them with that instant rather than refreshing on its own. It is the same read the list re-reads on every run start and end (§Required Behavior). It also returns the create form's fixed leading part, the suggested tail and the path hint, from the same daemon function that creates the tree and names its folder.
- `WorktreeRetire` (`repo.worktreeRetire {worktreeId, discard}`) records retirement even if filesystem deletion happens asynchronously. Ignored files count in its risk check. `discard: false` is the ordinary removal: if the tree has something to lose that the confirmation did not show, it is refused with `worktree.retire_conflict`, `reason: root_busy | has_changes`, carrying the current risks for `has_changes`. `discard: true` is sent only after the discard confirmation, keeps the tree (§Required Behavior), and its result carries `kept: {removedWorktreeId}`.
- `repo.removedWorktreeList {projectId?}` lists the kept worktrees, each `{removedWorktreeId, projectId, name, branch, headCommit, removedAt, sizeBytes, sizeReadAt}`, the size read once after the discard, off its path. `repo.worktreeRestore {removedWorktreeId}` → `{worktreeId, path, branch, onNewBranch}`, or a refusal with `reason`. `repo.removedWorktreeDelete {removedWorktreeId}` deletes the kept folder and its pins.
- `repo.worktreeSetupSubscribe` streams the setup card's stages and steps, each step's output and failure, and survives leaving the session; `repo.worktreeSetupRetry` runs the failed step and the ones after it. The steps are the ones the projects settings page stores.
- One ordered branch list is a daemon read (`repo.branchList`), supplied in one order and drawn in it: the project's default branch first, then the branches this project's recent bases were picked from, most recent first, then the rest by the date of their newest commit. Each row carries its ahead and behind figures from the same background fetch and names the worktree holding that branch, or marks it as the project's default. The one list serves worktree creation and the review surface's base picker ([Spec-009 §Required Behavior](./009-gitflow-pr-and-diff-attribution.md#required-behavior)), so a branch is ordered and annotated once; filtering narrows what is drawn and never reorders it. Every figure and tag on a row is a fact: no branch row carries an action anywhere. A base picked in the create form or the review surface is recorded by the daemon from the preparation's base and the diff read's base, so no verb of its own records it.
- Worktree creation and retirement each leave their record through `worktree.created` (carrying `restoredFrom` when a kept tree was put back) and `worktree.retired` (carrying `removedWorktreeId` when the tree was kept), and the sweep of sessions back to the repository root appends one `session.swept_to_repo_root` event per session it moved ([Spec-005](./005-session-event-taxonomy-and-audit-log.md)), so that row survives a reload. A failed setup is the setup card's own stream, never an event; `worktree.ready`, `worktree.dirty` and `worktree.merged` complete the worktree events. A branch that changed outside the console is recorded as `session.branch_changed`, which every surface naming the branch follows.
- Tree staleness is a signal the daemon emits from watching a workspace's working folder (`repo.workingTreeSubscribe`); no client infers it. A working folder too large for the machine to watch is checked on a slow tick instead, the bound read from what the machine's own watch limit allows rather than a fixed number of folders, and the signal carries which of the two it came from so the surface showing it can say that a stale mark may be minutes late.
- The background fetch that keeps the ahead and behind figures true, and sets `countsAsOf`, is daemon-internal, with no wire verb.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- Worktree records must persist branch name, owning repo mount, lifecycle state, and provenance to the creating session and run.
- The place must be stored as run setup data: the daemon persists a per-run execution binding (run → workspace, execution mode, execution root, and any worktree and branch context involved) that survives the run for provenance.
- Branch context must be persisted for every repo-bound run. The branch-context record references the worktree for a `provisioned-worktree` run and references none for a `bound-root` run (the bound checkout carries no Plan-007 root row).
- Dirty and merged state belong to daemon-owned workspace projections.
- No workspace is held for one run: two sessions' runs may work in one folder at once, as neither provider holds one. What keeps their work apart is the capture rule of §Turn-Boundary Snapshots — captures of one working folder run one at a time, across every session working in it — and the checkpoint store's per-session record of edits and command windows ([Spec-013 §Required Behavior](013-persistence-and-recovery.md#required-behavior)).
- Daemon-created execution roots live under the daemon's own execution-roots directory — a worktree at `~/.ai-sidekicks/worktrees/<project>/<session-short-id>-<task-slug>/`, flat, the path the create form's hint shows and the path `/cd` and `/worktree` name — never inside the attached repository checkout; they are inside the session's trust envelope by construction ([Spec-007 §Local Trust Envelope (V1 Definition)](./007-repo-attachment-and-workspace-binding.md#local-trust-envelope-v1-definition)). The folder is flat while the branch keeps its three parts, because git names a worktree's record after the folder's last part.
- A kept worktree is a record of its own beside the worktree records, holding the name, branch, recorded commit, removal time and read size, while its pins live under `refs/sidekicks/removed/<removed id>/` in the repository.

## Turn-Boundary Snapshots

At each turn boundary of a repo-bound run — turn completion is first-class via the `completionKind` carve on `run.completed` ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)) — the daemon records the working folder's project state as a snapshot, and around every command an agent or any of its children runs it takes a capture before and after. A snapshot **names a point to return to**; it is not a way to put files back. Every file restore reads from the daemon's per-session file checkpoint store ([Spec-013 §Required Behavior](013-persistence-and-recovery.md#required-behavior)) — one mechanism, the same on both providers ([Spec-003 §Driver-Level Rollback Mechanics](003-queue-steer-pause-resume.md#driver-level-rollback-mechanics)) — and a restore aimed at a named snapshot of the session reads from that same store, the snapshot supplying the point to return to. Capture, the capture folder it writes into, the ref namespace inside that folder, the pins it keeps in the repository and the prune that removes a ref are the whole mechanism: nothing here checks a tree out, deletes a file on disk, or writes the repository index.

- **Scope:** tracked **and** untracked files; ignored **untracked** paths are deliberately excluded — ignore rules govern untracked files only, so a tracked file that happens to match `.gitignore` is recorded like any other tracked file (tracking wins over ignoring, git's own semantics) — and "ignored" means **project-declared** rules only: the in-tree `.gitignore` files, themselves recorded by the snapshot. Host-local ignore sources — `core.excludesFile` (user or global config) and `$GIT_DIR/info/exclude` — are deliberately never consulted: a developer's private ignore patterns are not project declarations, and an untracked project file matching one is still project state the snapshot must name on every host (confirmed on git 2.50.1: `git add -A` under a global exclude pattern or an `info/exclude` entry silently omits matching untracked files — which is why the capture pipeline below is plumbing with explicit exclusion flags rather than porcelain). **Submodule boundary:** snapshots operate at the superproject's gitlink level — the recorded tree carries each submodule's then-current commit OID (a `160000` gitlink entry, exactly what porcelain staging would record) — and capture never descends into a submodule worktree: a submodule is its own repository whose files never enter the superproject index, so interior modified and untracked state is outside what a snapshot names (confirmed on git 2.50.1: the superproject's untracked listing never reports interior files). Scoped that way, a snapshot never names derived state the project itself declares disposable (build artifacts, caches, `node_modules`), and per-turn snapshots never churn the object store with artifact trees.
- **Where captures live:** each owner — a session, or a workflow run — has one capture folder, outside the checkout and never the person's `.git`. A capture is written with only `GIT_INDEX_FILE` (the owner's scratch index, seeded once from a copy of the repository's own index and kept between captures, so only what changed is hashed) and `GIT_OBJECT_DIRECTORY` (the capture folder) set — `git update-index -q --refresh`, the staging pipeline of the Capture bullet, `git write-tree --missing-ok` — so every blob and tree it changed lands in the capture folder. Diffs, before-images and the review surface read it with the repository's objects as an alternate. At the owner's first capture, and at any capture whose HEAD moved since the previous one, the objects HEAD's tree lacks are packed into the folder (`git rev-list --objects <tree> --not HEAD^{tree}` into `git pack-objects`), so a `git gc --prune=now` in the repository never takes one. Each kept snapshot pins the commit it stood on under `refs/sidekicks/base/<owner id>/` in the repository, one ref per distinct commit, naming only the person's own commit; nothing else is written into the person's `.git`, no object and no ref but those pins. The snapshot list is read from the folder (`session.snapshotList`).
- **Command captures:** around every command an agent or any of its children runs, the daemon captures the working folder twice, itself and outside every sandbox: before the command starts, holding the start until the capture is written, and when it ends, holding nothing. On Claude Code the daemon's command wrapper runs as `CLAUDE_CODE_SHELL_PREFIX`, after Claude Code's permission decision, and signals `starting`, waits for `go` and signals `exited`; on Codex the daemon's relay in front of `codex exec-server` holds an approved `process/start` until the before-capture is written and forwards `process/exited` at once. A service that does not acknowledge `starting` within 10 s, or a capture that fails, lets the command run uncovered, and the dry run names it `ran while the service could not capture it`. A command capture lists the turn snapshot's own listing plus the project's ignored files that sit outside an ignored folder (an `.env`, a `*.pem`), less the files over 10 MiB, which are shadowed by a copy-on-write clone instead and, on a volume that cannot clone, named `too large to keep`; the files changed by a command during which HEAD moved are named `changed by a git command that moved the branch`. Every path that differs between the two captures enters the checkpoint store as an ordinary copy ([Spec-013 §Required Behavior](013-persistence-and-recovery.md#required-behavior)). Captures of one working folder run one at a time, across every session working in it, so a command that starts while another's capture runs waits for it. Budget: before a command, at most 125 ms median (200 ms at the 99th percentile) on a 5,000-file checkout and at most 350 ms median (450 ms at the 99th percentile) on 50,000 files; after it, about 1.2 ms per changed file, off the agent's path.
- **Capture (scratch-index recipe):** with `GIT_INDEX_FILE` pointing at the owner's scratch index in its capture folder, **outside** the worktree, `GIT_OBJECT_DIRECTORY` naming that folder, and one base OID resolved at entry (`<base>` = `git rev-parse HEAD`) used as the recorded parent — resolved once so a `HEAD` that moves mid-capture cannot record an old-`HEAD` tree under a new-`HEAD` parent (confirmed on git 2.50.1) — `git update-index -q --refresh` → `git ls-files -co --exclude-per-directory=.gitignore -z | git -c core.autocrlf=false -c core.safecrlf=false -c core.attributesFile=/dev/null update-index --add --remove -z --stdin` (with `GIT_ATTR_NOSYSTEM=1` in the environment) → the untracked-embedded-repository normalization pass → `git write-tree --missing-ok` → `git -c i18n.commitEncoding=utf-8 commit-tree <written-tree> -p <base> -F -` → the create-only `git update-ref` of the Ref namespace bullet, inside the capture folder. The staging pipeline is the plumbing equivalent of `git add -A` — byte-identical trees under identical inputs, verified — with every exclusion and conversion input pinned: `-c` re-lists the scratch index's paths so `--add --remove` re-stats each one, staging tracked modifications and deletions, while `-o --exclude-per-directory=.gitignore` lists untracked files honoring **in-tree `.gitignore` rules only**, the Scope bullet's project-declared boundary and the reason porcelain `git add -A` is not the pipeline (it also honors `core.excludesFile` and `$GIT_DIR/info/exclude`, with no off-switch). `core.autocrlf=false` pins check-in CRLF→LF conversion off — git's own default, a neutralize-by-pinning rather than a behavior choice — because a host `core.autocrlf=input` or `true` re-hashes CRLF worktree bytes to LF blobs, changing blob, tree and snapshot OIDs for identical worktree bytes (confirmed on git 2.50.1); `core.safecrlf=false` pins that same channel's **veto** off, since present-or-pinned-false stage the identical tree and what a host `core.safecrlf=true` adds is a fatal, which would turn whether a turn can be snapshotted at all into a host-config question; `core.attributesFile=/dev/null` and `GIT_ATTR_NOSYSTEM=1` take the user and system attribute files out of the conversion decision, while in-tree `.gitattributes` — a project declaration, checked in and identical on every host — stays deliberately honored. One host-local input has no config or environment off-switch, `$GIT_DIR/info/attributes`, and is declared out of contract: the daemon never writes it, and a host that adds conversion-changing rules there breaks its own snapshot-OID stability, nothing else. The commit leg is noninteractive and host-independent by construction: the fixed message is streamed on a stdin the daemon writes and closes, where an unmanaged stdin read hangs wherever the daemon leaves stdin open, and the daemon supplies `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` **and `GIT_AUTHOR_DATE`/`GIT_COMMITTER_DATE`** — the turn-boundary instant at a fixed UTC offset — because without explicit ident environment `commit-tree` hard-fails (`Author identity unknown`) in passwd-less daemon and continuous-integration containers and silently stamps a passwd-derived operating-system ident elsewhere, which is both a machine-dependent snapshot OID and an identity leak into the object store, and because author and committer dates, timezone included, are commit-object fields and therefore OID inputs ([git-commit-tree](https://git-scm.com/docs/git-commit-tree) documents the stdin message read and the ident and date environment alike). The explicit `i18n.commitEncoding=utf-8` pin neutralizes repository and global config: set to anything but UTF-8 it writes an `encoding` header into the commit object, changing the snapshot OID for identical project state, while pinned UTF-8 is git's default and writes no header (confirmed on git 2.50.1; `commit.gpgsign` was likewise checked and is inert for this plumbing command). The message is **fixed** in the sense the determinism property needs: it is a pure function of **project state** — the fixed string plus state-derived sorted-JSON trailers streamed as further paragraphs — so two hosts capturing identical project state mint the same snapshot OID, skipped paths included, because a trailer's paths and their order are read out of the tree being captured. The out-of-worktree scratch index also keeps snapshots from self-capturing index files: a worktree-resident scratch index would surface to the pipeline's own `ls-files -o` listing, and to `git status`, as stray untracked content. Capture failure is recorded on the capture diagnostic and **never blocks or fails the turn** — a snapshot is a name for a point, not a turn gate. `git stash create` was experimentally refuted for this job ([git-stash](https://git-scm.com/docs/git-stash): the `create` subcommand takes only a positional `[<message>]`, untracked support being a `push`-only flag): it captures tracked paths only, has no untracked option, and silently swallows `-u` as a commit message, so a stash-style snapshot would name turns minus every file they created.
- **Capture's embedded repositories and its two skip classes:** a non-ignored untracked embedded git repository lists as a single trailing-slash directory entry that `update-index --add` silently drops (both behaviors confirmed on git 2.50.1), so the normalization pass records each one as a `160000` gitlink via `git update-index --add --cacheinfo 160000,<embedded-HEAD>,<path>` — porcelain staging's own embedded-repository representation ([git-update-index](https://git-scm.com/docs/git-update-index) documents the `<mode>,<object>,<path>` cacheinfo form as a direct index insert; the `160000` gitlink is git's superproject submodule representation, [gitsubmodules](https://git-scm.com/docs/gitsubmodules); [git-add](https://git-scm.com/docs/git-add) documents embedded-repository staging and its warning via `--no-warn-embedded-repo`). Two classes cannot be recorded as a gitlink at all and are **skipped and enumerated in the capture diagnostic** rather than failing the capture: a commitless embedded repository (unborn `HEAD`), and one whose `HEAD` hex length disagrees with the superproject's object format (a sha1 repository under a sha256 superproject, or the mirror case). Skipping is the honest answer measured against what porcelain does with the same inputs on git 2.50.1: `git add -A` hard-fails the commitless class (`does not have a commit checked out`) and **fabricates** the gitlink OID for the mixed-format one, zero-padding a sha1 `HEAD` to 64 hex under a sha256 superproject and truncating a sha256 `HEAD` to 40 in the mirror case — against fabricate-or-fail, skip-and-enumerate degrades honestly, both classes reaching the diagnostic, neither silently dropped and neither invented. The snapshot commit's `Skipped-Embedded-Repositories:` trailer names those paths, written **only** when the list is non-empty so a capture that skipped nothing mints a byte-identical message and OID to the trailerless form; the trailer is the snapshot's own record that a path was skipped rather than absent, the tree holding no entry at it either way.
- **Capture in a sparse execution root:** a root is sparse exactly when `core.sparseCheckout` is true — the config bit alone, never conjoined with pattern-file existence — and the malformed state that predicate routes fail-closed: a truthy bit with the rules file deleted or unreadable takes the sparse arm and draws a typed capture refusal, never a not-sparse misclassification into the unpartitioned pipeline. Unpartitioned staging there would truncate the snapshot: the scratch index seeded from `<base>` carries no `skip-worktree` bits, so every out-of-cone path is listed, found absent from the pruned worktree, and dropped from the tree by `--remove` (confirmed on git 2.50.1), and the snapshot would then name a tree the project never had. Any sparse execution root is in scope — `bound-root` is the canonical exposure, its root being the user's own checkout, and `provisioned-worktree` inherits it whenever the canonical mount is sparse, since `git worktree add` copies the current worktree's sparse-checkout patterns and worktree config into the new worktree ([git/git `53255916b7`](https://github.com/git/git/commit/53255916b7), shipped in git 2.36) — and detection is root-keyed, so both places route through the same partitioning. Capture in a sparse root partitions both of its listings by the repository's own sparse-checkout definition, evaluated through git's own sparsity matcher: `git sparse-checkout check-rules` ([git-sparse-checkout](https://git-scm.com/docs/git-sparse-checkout); plumbing since git 2.41, [git/git `00408adeac`](https://github.com/git/git/commit/00408adeac)), run in the execution root against the worktree's live rules and mode with the candidate paths fed on stdin, output meaning in-cone. That is the availability floor and the only oracle: on older git the subcommand is absent and capture in a sparse root fails closed through its typed failure envelope rather than degrading to the unpartitioned pipeline, the matcher is fatal in a root with no sparse-checkout state (measured) so it runs only downstream of detection and never as the detector, and gitignore-semantics exclude machinery (`git ls-files -c -i --exclude-from=<pattern-file>`) was measured divergent — sparse patterns share gitignore syntax but not gitignore evaluation, which cannot re-include below an excluded parent ([gitignore](https://git-scm.com/docs/gitignore)), so a non-cone `/*` plus `!/a/b/` definition over-includes git's own out-of-cone `a/b/` subtree and the re-stat stream then drops it from the snapshot (both oracles measured on git 2.50.1). The in-cone side re-stats exactly as the pipeline above does, over the owner's kept scratch index, whose one seed copy is taken from the per-root live index path resolved via `git rev-parse --git-path index` (a linked worktree's index lives under the main repository's `.git/worktrees/<id>/`, where a literal `.git/index.lock` fails against the gitfile or locks another worktree's index), under git's own index lock — the resolved path's sibling `<index>.lock` created exclusively and released without writing, because git prepares an index replacement at the lock path and renames it over the index, so an unlocked seed silently reads the pre-write index (measured on git 2.50.1) and omits racing staged state; acquisition contention retries briefly, then fails the capture typed. The live seed is what matches porcelain: porcelain updates no entry outside the cone ([git-add](https://git-scm.com/docs/git-add), `--sparse` being its opt-in), so out-of-cone cached entries persist at their live cached state and a `git add --sparse`-staged entry surviving a cone shrink reaches porcelain's tree, where a `<base>` seed was measured to revert it, and an out-of-cone unmerged entry fails `write-tree` typed exactly as porcelain refuses that index state. Out-of-cone untracked files are never added, and the boundary-time out-of-cone path set — untracked and intent-to-add paths alike, subtracted against the written tree on the listing's own bytes rather than on decoded strings, since two distinct on-disk paths can decode alike — is recorded on the snapshot commit's `Sparse-Boundary-Paths:` trailer, ordered after `Skipped-Embedded-Repositories:` wherever both are present since trailer bytes are OID inputs. That trailer is a sorted JSON string array whose strings are `latin1`-encoded, one code point per path byte, which makes it a record of bytes rather than of text and its order byte-lexicographic by construction: a decoded rendering collapses every invalid sequence onto one replacement character, so a path that is not valid UTF-8 could not be named honestly at all. A trailing-slash listing entry keeps its slash verbatim, because a directory git refused to descend is a directory capture could not enumerate. The trailer is written in a detected sparse root, an empty set spelling `[]`, and never in a non-sparse root, whose message bytes are what they were without the sparse pipeline. A snapshot of a sparse root is therefore a **full tree**, matching what `git add -A` stages there byte for byte under the pipeline's pinned exclusion and conversion inputs — the Scope bullet's host-local-ignore divergence standing unchanged in sparse roots, so a host-excluded in-cone untracked file is still deliberately recorded where porcelain would skip it — measured as byte-identical trees across cone, non-cone positive-pattern and non-cone negation fixtures, top-level and nested, in the clean sparse state, in the staged-out-of-cone state (`git add --sparse` then a cone shrink, where only the live-index seed matches porcelain's tree) and in the materialized-out-of-cone state alike, where porcelain keeps the index entry and refuses the on-disk edit because the cone is pattern-defined rather than `skip-worktree`-bit-defined, git clearing the bit the moment a path materializes while `git add -A` still refuses it. Sparseness stays a checkout-time projection, never a capture-time truncation, and the sparse evaluation stays structurally separate from the `.gitignore` exclusion pass — the sparsity matcher reads no gitignore source and the untracked listing keeps honoring in-tree `.gitignore` alone, so an ignored in-cone file is never swept into the stream (likewise measured). One scoped residual is recorded rather than closed, confined to out-of-cone **byte state**: content a user materialized on disk at a tracked out-of-cone path is outside what a snapshot names, capture recording the live cached state for such a path exactly as porcelain would. Implementation: [Plan-007](../plans/007-worktree-lifecycle-and-execution-modes.md) Phase 6 (T6.1, invariant I-007-19).
- **Ref namespace:** snapshot commits land under `refs/sidekicks/runs/<runId>/epoch-<E>/turn-<N>` inside the owner's capture folder — **never in the repository, never on `refs/heads/`** — so snapshots are invisible to branch history, pull requests, and diff attribution by construction. A workflow run's snapshot points use the same grammar in the run's own capture folder, keyed by the workflow run's id: `refs/sidekicks/runs/<workflowRunId>/epoch-<E>/start`, `…/pause-<N>` (its approval pauses, counted from 1) and `…/end`; the ref-name check admits these point names beside `turn-<N>`. `<E>` is the run's **execution epoch** ([Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) — `0` before any rollback, advanced with each **accepted `run.rolled_back`** — a confirmed conversation rewind, a position-mismatch rewind confirmed at the recorded floor included — regardless of what the file leg did, while an outcome with no confirmed rewind leaves it unchanged): same-run resurrection re-uses position ordinals, so a post-rollback re-execution's `turn-<N>` capture mints a **new** ref under its own `epoch-<E>` segment rather than resolving to the superseded epoch's tree. The closing `git update-ref --no-deref refs/sidekicks/runs/<runId>/epoch-<E>/turn-<N> <snapshot-commit> ""` is **create-only**: the trailing empty `<old-value>` is a compare-and-swap against ref absence (git refuses with `reference already exists` — confirmed on git 2.50.1), so a retried or duplicated capture of the same run, epoch and turn can never repoint an existing snapshot ref at later file state — the first successful write wins, and a capture retry that finds the ref already written treats it as idempotent success, returning the recorded OID. `--no-deref` is part of that spelling rather than decoration: git splits an update of a **symbolic** ref into an update of its referent and carries the must-not-exist check there with it, so an unflagged create against a dangling in-namespace symref plants an arbitrary branch at the snapshot commit and reports success (confirmed on git 2.50.1) — flagged, the write acts on the validated name itself and nothing outside the namespace moves. The same flag rides the retention prune's per-ref delete for the mirror reason: an unflagged `update-ref -d` resolves its compare-and-swap **through** a planted symref and deletes the branch it points at, exiting 0 and reporting a clean prune (likewise confirmed). Both directions of that channel are closed by the same flag, and neither guard substitutes for the other — the unflagged create mints a branch outside the namespace, the unflagged delete destroys one. [Spec-009](009-gitflow-pr-and-diff-attribution.md) is unaffected: its commits remain agent/user-authored and reviewable, and no Spec-009 surface changes.
- **Retention:** snapshot refs stay until the person deletes the run or its session, and nothing prunes them by age or on the edit or turn path; a workflow run's snapshots are never pruned while the run's record exists. The service's hourly sweep repacks the capture folder from its own objects only (`git rev-list --objects --missing=allow-any <kept refs>` into `git pack-objects --missing=allow-any`), never `git repack -l`, which drops a local copy the repository also holds, the very copy that protects a capture. The whole-session purge deletes the session's capture folder, its snapshot refs with it, and its pins. The session's file checkpoints are held with the session outside the checkout ([Spec-013 §Required Behavior](013-persistence-and-recovery.md#required-behavior)).
- **Applicability:** both places. In `bound-root` the execution root is the workspace's bound checkout — the user's own live working tree, main checkout or linked worktree, whichever the workspace bound (`workspaces.metadata.boundRoot`, which names the tree the workspace bound rather than the repository's canonical root — [Spec-007 §Repo Identity And Common-Directory Keying (V1 Definition)](./007-repo-attachment-and-workspace-binding.md#repo-identity-and-common-directory-keying-v1-definition)) — so a snapshot there names the state of a shared live checkout. Capture's execution-root input is normalized to the enclosing working-tree **top level** at the snapshot service's entry: its `ls-files` legs are cwd-scoped, so an un-normalized nested execution root — a workspace bound at a subdirectory of its checkout — would record only the nested prefix, and the snapshot would name a narrower tree extent than the one the run is working in. The normalized top level is derived only while the bound directory exists — recorded at bind as the workspace's persisted checkout-root carrier (`workspaces.metadata.checkoutRoot`, beside `boundRoot`), rewritten whenever a finished preparation installs a new execution root, since a daemon-created worktree is its own top level, so the carrier always names the current checkout, the user's own for `bound-root` and the daemon-created one otherwise. **How the recorded value reaches capture.** It is supplied, never looked up: the snapshot legs are pure callees that receive every root they operate on, so the normalized checkout root is captured per run into the run's execution-context record at run setup — while the tree exists and under a caller that knows which workspace the run is bound to — and is then handed to capture as an ordinary caller-resolved input, exactly as the execution root and execution mode already are. Capture, which by definition runs while the tree exists, re-verifies the supplied value against the live tree and fails the capture typed on disagreement. That widened extent is what the one-at-a-time capture rule keys on: captures are serialized per normalized checkout, never merely per bound subdirectory, so two sessions bound to subdirectories of one checkout never capture it at once. A session that moves to another worktree has its root prepared again on that tree — at once while the session is idle, and at the run boundary when the move was asked mid-turn (§Required Behavior) — and that finished preparation rewrites the persisted checkout root exactly as any other does, so the value captured per run always names the tree the run actually ran in.

## Example Flows

- `Example: A person starts a new project session. The daemon creates a worktree of its own on sidekicks/1a2b3c4d/fix-login-bug, runs the project's setup steps in the composer card, and only then starts provider execution.`
- `Example: A person starts a session in the project's checkout at the Read-only permission level, inspects diffs, and the agent changes nothing.`
- `Example: A person removes a worktree with an uncommitted .env in it. The confirmation reads Discard and remove, the tree is moved aside whole, and Put back later recreates it with the .env where it was.`
- `Example: A second session moves into the same worktree from the switcher. Both work there at once, and Undo to here in one puts back only what that session changed.`

## Implementation Notes

- Branch-name defaults should be deterministic and human-readable, but collision handling must be explicit.
- A new session gets a worktree of its own by default; moving into an existing tree or working in the checkout is the person's choice.
- Repository setup commands are the project's own recorded steps, run in place in the setup card under no approval; the repository's own setup scripts never run, and its git hooks run as its own git config says.

## Pitfalls To Avoid

- Mutating the main checkout as a hidden fallback
- Treating worktree reuse as implicit magic
- Losing run provenance when a worktree is later retired

## Acceptance Criteria

- [ ] A new project session starts in a worktree of its own unless the person chose the project's checkout.
- [ ] The execution-mode contract is `bound-root | provisioned-worktree`, and a chat session is always `bound-root`.
- [ ] `Discard and remove` keeps the tree whole, and `Put back` recreates it with its staged set, ignored files and HEAD identical.
- [ ] Two sessions run in one worktree at once, and each one's undo puts back only its own changes.
- [ ] Worktree creation failure blocks the run instead of mutating the main checkout.
- [ ] A worktree a session moved into remains linked to its branch and prior run context.

## Branch, Base And Preparation Rules

- A worktree's branch is the `Branch names` pattern filled in, `sidekicks/<session-short-id>/<task-slug>` under the default `sidekicks/{session}/{title}`, where `<session-short-id>` is the **last** 8 hex characters of the session UUID (hyphens stripped, lowercased — the low 32 of its random bits: the daemon mints RFC 9562 v7 ids, whose first 8 characters are the high bits of the millisecond timestamp and are shared by every id minted within one 65,536 ms window, so a first-8 short id collides across sessions on one repository) and `<task-slug>` is the tail derived from the session title or, before the session has a title, from its provisional title, the first words of the first message, read through the one function the session's naming uses. Every derived tail is shaped as it is typed (capitals lowered, every character outside `a-z 0-9 . _ -` turned into a hyphen, a leading `.`, `_` or `-` dropped), then repeated `-` and `.` collapse, a trailing `-`, `.` or `.lock` is trimmed, and it is cut at a word break near 40 characters, so it always matches `^[a-z0-9][a-z0-9._-]*$`: `fix the login redirect` gives `sidekicks/<session-short-id>/fix-the-login-redirect`. Only when no usable words remain does the tail fall back to `run-<run-short-id>` (the last 8 hex of the run id, by the same rule). A branch keeps its name when the session's title changes. A suggested tail that clashes takes the next free `-2`, `-3`. The pattern is the machine's, which the person can change and a project can override (§Default Behavior).
- Branch-name collision handling is provenance-split. A caller-supplied branch name that collides with a live checkout is refused with the typed collision error — user intent is never silently adapted. A daemon-derived default name that collides takes the first free ordinal suffix (`-2`, `-3`, …) as part of the deterministic derivation rule; the chosen name is persisted and reported verbatim. A collision never places a session in an existing worktree: a fresh worktree on a suffixed name is created.
- Worktree base refs default to the repo mount's current HEAD branch; an explicit base ref may be supplied at preparation. Preparation against a detached-HEAD mount with no explicit base ref is refused rather than guessed.
- `bound-root` binds to the bound checkout's branch as it stands; the daemon never checks out, creates, or switches branches inside the BOUND checkout — the user's main checkout or linked worktree, per `workspaces.metadata.boundRoot`. A branch that changed there outside the console is written back to the session's record (`session.branch_changed`) and never refused.
- Worktree state transitions are evented only by `worktree.created`, `worktree.ready`, `worktree.dirty`, `worktree.merged` and `worktree.retired`; a failed setup is the setup card's own stream (`repo.worktreeSetupSubscribe`) and is never an event, and the `failed` state is read through `WorktreeStatusRead`.
- The repository's own setup scripts never run during worktree preparation, and its git hooks run as its own git config says. The steps that do run are the project's own recorded list, which runs as part of preparation, in the session's view, and under no approval (§Required Behavior).
