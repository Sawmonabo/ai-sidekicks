## Purpose

This spec defines V1 feature #18 ([ADR-015 §Decision](../decisions/015-v1-feature-scope-definition.md#decision)): how the local runtime daemon configures, governs, and observes **MCP servers** attached to the two provider CLIs (`claude` and `codex`). Both providers are MCP _clients_ that own their MCP server connections; the daemon never joins the MCP wire. What the daemon owns is the **governance layer** above those connections:

1. A **unified server inventory** — one normalized read model across both providers' divergent config surfaces.
2. **Configuration mutation** — add / update / remove / enable / disable servers through each provider's sanctioned mechanism, never by blind config-file rewriting.
3. A **trust store** — operator-granted, config-hash-bound trust per server binding, untrusted by default, auto-revoked on config drift. This is the operator-managed trusted-server store that [ADR-015 §References](../decisions/015-v1-feature-scope-definition.md#references) binds MCP annotation trust to: the MCP spec requires clients to treat tool annotations as untrusted unless the server is trusted, and trust classification MUST bind on this store, never on annotation self-claims.
4. **Tool-level overrides** — per-(server, tool) enable/disable, approval-mode, and idempotency-class assignment, feeding the [Spec-005](./005-provider-driver-contract-and-capabilities.md) tool-metadata resolution layer.
5. **OAuth orchestration** — driving each provider's own login flow for servers that require it; the daemon never stores tokens.
6. **Status observation** — normalizing both providers' server-status feeds onto the Spec-005 `McpServerStatus` enum and the session event timeline.
7. **Audit** — every governance mutation and status transition emits a canonical event in the `mcp_governance` category ([Spec-006 §MCP Governance (`mcp_governance`)](./006-session-event-taxonomy-and-audit-log.md#mcp-governance-mcp_governance), 2026-07-22 B18 amendment).

## Scope

- The `mcp.*` IPC operation namespace (11 operations) on the daemon control surface.
- Normalized server inventory merging provider-declared config, live provider status, the daemon trust store, and the daemon override store.
- Provider-specific mutation engines: Claude's sanctioned user-scope CLI writes plus opportunistic live reconcile, and the Codex user-config CRUD + reload pair.
- The `mcp_server_trust`, `mcp_tool_overrides`, and `mcp_mutation_receipts` SQLite tables (daemon-local, node-scoped).
- Cedar-gated authorization for every governance mutation (node-operator scope).
- The five `mcp.*` event types and their payloads, session binding, and sanitization rules.
- OAuth login orchestration for both providers, including the honest degradation for flows a mode cannot run in-band.

## Non-Goals

- **No MCP protocol implementation.** The daemon is not an MCP client or server and does not proxy, intercept, or transform MCP traffic. Provider CLIs own their connections end to end.
- **No token custody.** OAuth tokens, bearer tokens, and API keys live where each provider stores them. The daemon never persists, logs, relays, or serves credential material, and event/error payloads never carry it. The bounded exception this posture explicitly allows: observation and sanctioned-write paths necessarily parse provider-owned config (which may embed env-var and header values) **transiently in memory** — that material is consumed only by canonicalization + keyed hashing (§Trust Governance) and the provider's own sanctioned write mechanism, then discarded; it never reaches storage, events, errors, logs, or any read model (see §Implementation Notes — transient-secret handling).
- **No config-store ownership.** Provider config files (`~/.claude.json` scopes, `$CODEX_HOME/config.toml`, project-local `.codex/config.toml`, `.mcp.json`) remain provider-owned; the daemon mutates them only through each provider's sanctioned write mechanism and treats them as the source of truth it observes, not a mirror it maintains.
- **No server marketplace, registry, or discovery.** V1 governs servers the operator declares; it does not fetch, recommend, or install them.
- **No remote governance mutation.** V1 authorizes only the node-local operator (the caller-owns-the-node model, [BL-141](../backlog.md)); control-plane-relayed mutation attempts are denied, not queued.
- **No session-role permission-matrix extension.** Governance is node-operator authority, deliberately outside the session-role matrix ([Security Architecture §Permission Matrix (Task 5.4)](../architecture/security-architecture.md#permission-matrix-task-54)); the only session-role-facing MCP surface remains `mcp_elicitation` approvals per Spec-012.
- **No non-user-scope config writes.** V1 observes project and local scopes read-only on both providers (Codex cwd-resolved `.codex/config.toml`; Claude `.mcp.json` and the project-keyed `local` scope); writes target user scope only (see §Fallback Behavior for the honest degradation).

## Required Behavior

### Provider Capability Model

Both providers expose MCP configuration, status, and auth surfaces, but through structurally different mechanisms. Per the capability-parity principle (all provider capabilities integrate at V1; asymmetries are normalized, emulated, or degraded honestly — never silently dropped), the daemon binds to each mechanism natively and grades what each application path can deliver:

| Capability | Claude Code mechanism | Codex mechanism |
| --- | --- | --- |
| Declare servers for a session | Per-run ephemeral config — `--mcp-config <file-or-inline-json>` + `--strict-mcp-config` — composed by the daemon as a snapshot of the observed user-scope declarations plus governance overlays (see §Configuration Mutation) | cwd-resolved project-local `.codex/config.toml` (trusted projects) layered over `$CODEX_HOME/config.toml` |
| Mutate a live session's server set | `mcp_set_servers` control request — SDK `setMcpServers(servers)` returning `{added, removed, errors}`; streaming-input mode only; version floor CLI `2.1.210` / SDK `0.3.166` | Not live per-thread; config write + `config/mcpServer/reload` applies to subsequent thread starts |
| Mutate durable config | Sanctioned CLI writes at user scope: `claude mcp add-json` / `claude mcp remove` with `--scope user` — the provider's own store stays the durable home; the daemon never rewrites `~/.claude.json` bytes directly | `config/value/write` / `config/batchWrite` with `expected_version` optimistic concurrency; user scope (`$CODEX_HOME/config.toml`) only |
| Server status | Init census `mcp_servers[]` + `mcpServerStatus()` SDK query; `claude mcp list` glyphs (human CLI, no `--json`) | `mcpServerStatus/list` (ephemeral, cursored, `thread_id`-scopable) + `mcpServer/startupStatus/updated` notifications |
| Per-server reconnect | SDK `reconnectMcpServer()` | `mcpServer/refresh` |
| Enable/disable | SDK `toggleMcpServer()` (live) + the daemon's per-server enabled overlay applied at next-run composition (user scope has no enabled field, and removal would destroy the declaration) | `enabled` field write + reload |
| Tool allow/deny + approval mode | Daemon-enforced (no native per-tool config field; the daemon's approval layer enforces overrides) | Native config fields: `enabled_tools` (allow), `disabled_tools` (deny, applied after allow), `default_tools_approval_mode` (`auto`\|`prompt`\|`writes`\|`approve`), `tools.<t>.approval_mode` |
| OAuth login | `claude mcp login <server>` (CLI ≥ `2.1.186`) / `/mcp` panel; no dedicated completion event — completion is observed as a status flip to `connected` | `codex mcp login <server>` and app-server `mcpServer/oauth/login` → `authorization_url`; completion notification `mcpServer/oauthLogin/completed` |
| Required-server gating | Not native; daemon surfaces failed servers via status | `required = true` ⇒ `thread/start` / `thread/resume` FAIL if the server cannot initialize |

Every mutation response MUST carry an **application grade** — `live_reconcile` (applied to the running session's live server set), `user_config_write` (persisted to the provider's own config store, effective for subsequent runs/threads), `next_run` (daemon-recorded governance state applied at the next run's composed config), or `daemon_enforced` (enforced immediately at the daemon's own decision layer) — so callers know _when and where_ the change takes effect. Degradation is honest and typed, never silent: a Claude mutation that cannot reconcile live succeeds with the grade its durable path actually achieved, not an error and not a fake `live_reconcile`.

### Unified Inventory

- The daemon MUST expose one normalized inventory (`mcp.list` / `mcp.get`) merging four sources per server binding: (1) provider-declared configuration (parsed from the provider's own config surfaces), (2) live provider status normalized onto `McpServerStatus` (`unknown | starting | connected | needs-auth | failed` per [Spec-005](./005-provider-driver-contract-and-capabilities.md) — the api-payload `McpServerStatus` union), (3) the daemon trust row, (4) the daemon tool-override rows. Each entry carries a **redacted normalized config view** (`McpServerConfigView`) — transport, command/args, the **query-redacted URL** (scheme + host + path; the query component is credential-equivalent write-only material — a `?api_key=…` credential passes no-userinfo validation, so query **values** never round-trip and the view serves the query **parameter names** instead, the same names-not-values discipline as env vars and headers), timeouts, `required`, `bearerTokenEnvVar`, the Codex auth references (`envHttpHeaders` — a header-name → env-var-**name** map — plus `oauthScopes` and `oauthResource`), and the **names** of env vars and headers, never their values — so `mcp.get` can read back what `mcp.upsertServer` wrote and an operator can inspect provider state without the daemon ever serving credential material (`command`/`args` are operator-authored process-visible strings, the same residual class as the identifiers in §Status Observation and Events; the full URL still feeds the base-config hash, so a query-string credential rotation drifts the hash like any semantic change).
- Server identity is the scope-qualified **binding** `(provider, scope, scopeRef, serverName)` — scope is `user` (Claude user scope in `~/.claude.json`; Codex `$CODEX_HOME/config.toml`), `project` (Claude `.mcp.json`; Codex cwd-resolved `.codex/config.toml`; `scopeRef` = the canonical project root), or `local` (Claude's project-keyed private scope; `scopeRef` = the keying directory; `scopeRef` is the empty string for `user`). Two scopes legitimately declaring the same `serverName` with different configurations are **distinct bindings** with independent status, trust rows, and overrides — collapsing them would make one scope's config drift-revoke trust granted to the other and bleed overrides across configurations. The inventory MUST NOT merge same-named servers across providers or across scopes into one logical entry — a merge would launder trust. Project/local entries additionally serve `scopeRefDigest` — the keyed audit-ref digest event payloads carry (§Status Observation and Events) — so governance events join to inventory entries without raw paths ever entering the audit trail.
- Same-name shadowing across scopes is surfaced, not resolved away: both bindings appear in the inventory, and each entry carries `effectiveInRuns` — whether that binding reaches provider runs (Codex `user` + `project`: `true`, the provider layers them natively with project winning per TOML layering; Claude `user`: `true` via the daemon's composed ephemeral config; Claude `project` + `local`: `false` in V1 — strict-mode composition deliberately excludes them, see §Implementation Notes).
- Provider states outside the normalized enum map deterministically: Claude `pending` → `starting`; Claude `disabled` → `enabled: false` on the inventory entry with status from the last observation (or `unknown`); absence of any status source → `unknown`, honestly. Provider status feeds report server names, not bindings; the daemon MUST attribute each observation to the binding that is effective for the observing context (the session's cwd for Codex feeds; the composed set for Claude feeds).
- A config binding and a **live provider leg** are different grains: one binding can back several concurrent sessions' connections at once, and the Plan-005 status seam keys every session-feed observation by the runtime-binding leg (`sessionId` + the Plan-005 `bindingId`). The inventory MUST NOT collapse divergent leg states into one overwritten scalar: each entry exposes the per-leg observations (`legs[]` — leg identity, status, `observedAt`) alongside a deterministic top-level aggregate `status` — the most severe current live-leg status under the fixed severity order `failed > needs-auth > unknown > starting > connected` (`unknown` is a valid live-leg status — a leg whose observation source is lost; lost observability outranks states known healthy, but never a concrete failure), falling back to the newest node-probe observation when no live leg exists, and to `unknown` when there is no observation source at all. Legs are **live-session observations with a bounded lifecycle**: when a leg's backing runtime binding closes (session end, driver exit), the daemon retires the leg and recomputes the aggregate — a terminated session's last observation never pins the aggregate (a `failed` leg of a closed session does not hold the server at `failed` while every live session is `connected`); with no live legs remaining, the aggregate falls back per the order above.
- First observation of a binding the trust store has never seen MUST upsert an untrusted trust row (`trusted = 0`) — observation creates the governance anchor; it never creates trust.

### Configuration Mutation

- Mutations (`mcp.upsertServer`, `mcp.removeServer`, `mcp.setEnabled`) target a binding and MUST route through the provider-native mechanism for the target provider, per the capability table above. The only provider-config-writable scope in V1 is `user` on both providers. **Upserts are read-modify-write over the provider's own declaration**: provider fields the normalized input does not model — or does not carry — are preserved, never erased (Codex writes are field-granular `config/value` paths touching only carried fields; the regenerated Claude declaration starts from the observed current one), so a typed read/edit round-trip can never silently destroy provider configuration outside the governed surface.
- **Scope applicability is per operation, not blanket.** `mcp.config_scope_unsupported` fires exactly when the requested operation requires a mechanism the target binding's scope cannot support in V1, with actionable guidance naming the file to edit; it never blocks governance that the daemon can genuinely deliver on a read-only scope: (1) the three config mutations above require a provider-config write — non-`user` scopes refuse on both providers (and `mcp.setEnabled` additionally refuses Claude `project`/`local` bindings because the enabled overlay materializes only through composition, which excludes them in V1); (2) `mcp.setTrust`, `mcp.setToolOverride`/`mcp.clearToolOverride`, `mcp.oauthLogin`, and `mcp.reconnect` apply to any binding that is **effective in runs** (Codex `user` + `project`; Claude `user`) — a Codex project binding is governable (trust, daemon-enforced override facets, OAuth, reconnect) precisely because its tools really run; (3) governance mutations targeting a binding that V1 never materializes into runs (Claude `project`/`local`, `effectiveInRuns: false`) refuse with `mcp.config_scope_unsupported` — accepting them would store governance state nothing can ever enforce; (4) override facets that can only materialize through a native config write (Codex `enabled`/`approvalMode`) refuse on Codex `project` bindings with guidance to edit the project file directly — the daemon has no interception point that could honestly enforce them (§Tool-Level Overrides).
- **Validation precedes commitment.** Schema validation and every check that can fail the mutation outright run **before** the durable leg commits — `mcp.config_invalid` is exclusively a pre-commit refusal. Once the durable leg has committed, the mutation never converts to a thrown error: later per-leg live failures are reported inside the successful response (below), so a caller can never be induced to retry a mutation that already committed.
- **Claude, durable leg (unconditional):** every `mcp.upsertServer` / `mcp.removeServer` persists to the provider's own user scope via the sanctioned CLI (`claude mcp add-json <name> <json> --scope user` / `claude mcp remove <name> --scope user`) **before** the mutation is acknowledged — an acknowledged mutation survives daemon restart because the provider's store, not daemon memory, is the durable home. The daemon MUST verify the write took effect (re-read via `claude mcp get` / user-scope observation) before emitting the config event.
- **Claude, live leg (opportunistic):** when the running CLI/SDK pair satisfies the version floor (capability-probed at driver spawn, not assumed from the pin) in a streaming-input session, the daemon additionally applies the mutation live via `setMcpServers` and MUST reconcile the returned `{added, removed, errors}` against the requested delta. The call replaces the named-server set but keeps unnamed plugin-provided servers — the daemon MUST always send the full desired named-server set, never a delta. The response grade reports the most immediate application achieved: `live_reconcile` when every attempted live leg applied (the durable leg having also completed), `user_config_write` otherwise.
- **Partial outcomes are typed, never masked.** Mutation responses carry `liveResults[]` — one entry per attempted live leg (`sessionId` + the Plan-005 runtime-binding leg key) with `outcome: 'applied' | 'failed'` and a sanitized per-leg error code on failure — so a durable-success/live-failure outcome is a **successful response** reporting `applied: 'user_config_write'` plus the failing legs, never a blanket success that hides the live failure and never an error that invites an unsafe retry of a committed write.
- **Claude, enabled overlay:** `mcp.setEnabled` for a Claude binding records the daemon's per-server enabled overlay (user scope has no enabled field; removal would destroy the declaration) — applied to the composed ephemeral config at the next run start (grade `next_run`) and live via `toggleMcpServer` when the capability probe allows (grade `live_reconcile`).
- **Codex:** the daemon writes user-scope config via `config/batchWrite` (multi-field mutations MUST be batched — one version check, one reload) with `expected_version` from the immediately-preceding `config/read`; on `configVersionConflict` the daemon MUST re-read and retry exactly once, then surface `mcp.config_write_conflict`. After a successful write the daemon MUST trigger `config/mcpServer/reload` (or per-server `mcpServer/refresh` when scoped to one server). Grade `user_config_write`.
- Every applied mutation MUST emit `mcp.server_config_changed` with the binding identity, change kind, application grade, and post-change config hash — except removals, whose payload carries `previousConfigHash` and no `configHash` (there is no post-removal config to hash; see the payload contract). The payload MUST NOT include config values (env vars, headers, URLs with embedded credentials, tokens).

### Trust Governance

- Trust is per binding `(provider, scope, scopeRef, serverName)`, granted and revoked only by the node operator via `mcp.setTrust`, Cedar-gated. Same-named bindings in different scopes carry independent trust — trust granted to the user-scope configuration never covers a project-scope configuration of the same name.
- A trust grant MUST bind to the binding's current **base-config hash**: `b3:`-prefixed BLAKE3 in **keyed mode** — the key is the binding's **config-hash subkey**, derived from the daemon-held MCP governance master key via BLAKE3 keyed-PRF over a purpose tag plus the canonical binding identity (32-byte node-local key material held **outside the database** — §Implementation Notes; deterministic, so the subkey is stable for the binding's life without storing any key beside the digest) — over the RFC 8785 JCS canonicalization of the normalized server config (the same canonical-bytes discipline as [Spec-006 §Integrity Protocol](./006-session-event-taxonomy-and-audit-log.md#integrity-protocol); keying is the deliberate deviation: the canonical input includes credential-bearing env-var and header **values** so their drift is detected, and the non-colocated per-binding key keeps the resulting hash — which travels in events, inventory reads, and the trust row itself — from being an offline-brute-forceable digest of low-entropy secrets even for an attacker holding the database file), computed **excluding the daemon-managed override-projection fields** (`enabled_tools` / `disabled_tools` / `tools.<t>.approval_mode` — the fields the daemon itself materializes for governed tool overrides, which carry their own Cedar-gated audit trail in the override store). Without the exclusion, the daemon's own governed override write would change the hash and revoke the very trust that authorized it. **The exclusion is hash-scope only, never drift-scope**: every drift evaluation on a trusted binding additionally reconciles the observed values of these fields against the **expected native state** — the binding's preserved **native-field baseline** overlaid with its materialized override facets. The baseline (the trust row's `native_tool_baseline_json`) is snapshotted from the observed native values at trust grant or at the binding's first facet materialization, whichever comes first — never silently refreshed while held, dropped only once the binding is untrusted with no materialized facets — and is what makes the expected state well-defined for the _ungoverned portions_ of these shared fields (an operator's own pre-existing `enabled_tools` entries) alongside the governed ones. Any divergence is out-of-band tool-governance drift, auto-revoking exactly like base-config drift; portions governed by materialized facets are re-asserted to the expected state (`mcp.tool_override_changed` per re-asserted facet) while ungoverned portions adopt the observed values — revoke, never undo the operator's own config, mirroring base-config drift semantics. A hand-edited `enabled_tools` broadening or approval-mode weakening therefore can never ride into a run under an unchanged base hash. (An untrusted binding's native tool fields are ungoverned provider config — observed and served in the config view, never trust-laundered.) Trust means "the operator trusts _this_ configuration", not the name.
- On any observation where a trusted binding's current base-config hash differs from the bound hash, the daemon MUST auto-revoke trust (`trusted = 0`, `revoked_reason = 'config_drift'`) before the changed config is used, and emit `mcp.server_trust_changed` with `reason: 'config_drift'`. Re-trusting after drift is an explicit operator action.
- **Run admission refreshes before trust-dependent state applies (the drift gate).** "Before the changed config is used" is enforced at run admission, not left to eventual observation: for every run/thread start or resume whose effective binding set is non-empty, the daemon MUST perform a fresh read of the provider config surfaces backing those bindings, recompute base-config hashes, and complete drift processing — auto-revocation **and** weakening neutralization, including Codex native-field reversion — before the provider process spawns or the thread starts. The Claude composed snapshot is generated **from** this post-drift-processing read; the Codex pre-start refresh completes before `thread/start` / `thread/resume` is issued. An operator who edits provider config out-of-band therefore can never launder a prior grant's trust-dependent annotations or weakened facets into a run ahead of drift detection. The admission service has **two registered call sites** (see Plan-028 CP-028-5): run/thread starts register through the Plan-004 `RunSetupGate` seam (`assertRunReady`, the CP-004-8 registration pattern), and **daemon-restart recovery** invokes the same service through the Plan-015 startup-attach admission seam — a vacuous-default gate on the recovery attach sequence that Plan-028's composition-root wiring fills — before any recovery adoption or cold-resume dispatch, so a config edit made while the daemon was down processes drift before any provider session re-attaches (before Plan-028 ships, the default is honestly vacuous: no trust store exists, so there is no drift to process).
- **Revocation neutralizes weakening (atomic):** whenever trust is revoked — operator revoke or drift auto-revoke — safety-weakening override facets for that binding stop applying in the same operation: daemon-enforced weakenings (Claude approval modes, idempotency-class assignments everywhere) are conditioned on current trust at resolution time and lapse immediately, and Codex-materialized native weakening fields MUST be rewritten to the **baseline-anchored safe state** — the preserved native-field baseline overlaid with the surviving safety-tightening facets, never an invented default — before the revocation returns, emitting `mcp.tool_override_changed` for each reverted facet. The trust event plus the per-facet reversion events are the revocation's **atomic event batch**: they append in the same transaction as the revocation itself, one batch exactly-once under the mutation's receipt (§Authorization). A revoked server never keeps a weakened posture it was granted while trusted.
- Trust consequences (the enforcement points other specs own but this store feeds):
  - MCP tool **annotations** (`readOnlyHint`, `destructiveHint`, etc.) are honored in daemon decision surfaces only for trusted servers, per the ADR-015 binding of the MCP spec's annotation-trust MUST. Untrusted servers' annotations are display-only.
  - **Safety-weakening tool overrides** require a trusted server — `mcp.trust_required` otherwise. The weakening set is: idempotency-class assignment off the floor; approval modes weaker than the provider default; and `enabled: true` — enabling a tool the effective provider configuration or a prior override disables **broadens the executable tool set**, which is capability expansion and therefore weakening, never neutral. Safety-tightening overrides (disable a tool, force `approve` mode) are allowed regardless of trust.

### Tool-Level Overrides

- `mcp.setToolOverride` / `mcp.clearToolOverride` manage per-`(provider, scope, scopeRef, serverName, toolName)` rows carrying up to three optional facets: `enabled` (allow/deny), `approvalMode` (`auto | prompt | writes | approve` — the Codex-native vocabulary, adopted as the normalized set), `idempotencyClass` (`idempotent | compensable`; absence means the [Spec-005](./005-provider-driver-contract-and-capabilities.md) `manual_reconcile_only` floor).
- Enforcement is provider-graded, and the override response reports it **per facet** (see the payload contract): for Codex, `enabled`/`approvalMode` facets are materialized into the native config fields (`enabled_tools` / `disabled_tools` / `tools.<t>.approval_mode`) on write — grade `user_config_write`, `user`-scope bindings only (on a Codex `project` binding these two facets refuse with `mcp.config_scope_unsupported` and edit-the-file guidance — the daemon has no interception point in the Codex tool path, so a "daemon-enforced" grade there would be a lie; the scope-applicability rule in §Configuration Mutation governs). The **first** facet materialization for a binding snapshots the pre-write native values of these fields as the binding's baseline (unless a trust grant already did — §Trust Governance), and `mcp.clearToolOverride` restores the cleared facet's portions from that baseline — clearing the last facet of an untrusted binding restores the baseline verbatim and drops it, returning the fields to fully native ownership; a user's own pre-existing native entries always survive a set → clear round-trip; for Claude, the daemon enforces them at its own approval layer (Spec-012 evaluation sees the override before prompting) — grade `daemon_enforced`, effective immediately for subsequent evaluations. An override request MUST carry at least one facet — the request schema rejects a facet-less override at validation, mirroring the DDL's all-NULL row prohibition. The `idempotencyClass` facet is provider-independent and always `daemon_enforced`: it feeds the Spec-005 tool-metadata resolution layer, which downstream consumers (recovery/replay per Spec-015) already read — consumers never read the override table directly. Override resolution is **binding-keyed**: the Spec-005 metadata layer resolves by `(driver_name, tool_name)`, which cannot disambiguate the same `serverName` bound in two scopes, so the override overlay widens the resolution input with the session's **effective server binding** for the tool's server (the binding the session's context makes effective — Codex cwd layering, Claude composed snapshot; the same attribution rule as §Unified Inventory status observations), carried through tool invocation and recovery-receipt resolution, and keys the lookup by the full binding plus `toolName` — two sessions resolving the same tool name from user- and project-scope bindings each get their own scope's override, never the other's. Safety-weakening facets are effective only while the binding's trust holds (see §Trust Governance — revocation neutralizes weakening).
- Idempotency-class assignment is the **only** governed path off the `manual_reconcile_only` floor ([Spec-005 §Tool Metadata](./005-provider-driver-contract-and-capabilities.md#tool-metadata)): operator-initiated, Cedar-gated, trusted-server-only, and always audited via `mcp.tool_override_changed`.
- Every override mutation emits `mcp.tool_override_changed` (set and clear alike).

### Authorization

- Every non-read operation (`mcp.upsertServer`, `mcp.removeServer`, `mcp.setEnabled`, `mcp.setTrust`, `mcp.setToolOverride`, `mcp.clearToolOverride`, `mcp.oauthLogin`, `mcp.reconnect` — eight of the eleven) MUST be authorized through the Plan-012 Cedar evaluation surface (`PermissionCheckService`) under a dedicated `mcp` Cedar action family before any provider call or store write. Read operations (`mcp.list`, `mcp.get`, and the `mcp.subscribe` stream) are operator-readable without a Cedar mutation check.
- **Governance mutations — and the receipted operational command `mcp.oauthLogin` — are idempotent to the caller (the Spec-005/B3 `clientIdempotencyKey` discipline, the intervention-surface precedent).** Every such request carries a mandatory requester-generated UUID `clientIdempotencyKey`. After the Cedar check, the daemon consults the durable `mcp_mutation_receipts` store: an identical retry (same key, same `b3:` keyed request digest — keyed under a **daemon-held node-local key stored outside the database**, never a value colocated with the receipt row, so a database copy alone cannot verify secret guesses offline; see the schema) replays the recorded response verbatim with **no** provider call, store write, or second event (one representation exception: the `mcp.oauthLogin` receipt is stored and replayed URL-free — §OAuth Orchestration); the same key with a differing digest refuses with `mcp.idempotency_conflict`, original mutation untouched. Receipts are **two-phase** (the Plan-015 `command_receipts` two-phase discipline): the daemon commits the receipt as a `pending` **intent** (key, operation, request digest) in its own transaction **before** any provider leg runs, then finalizes it (`committed`, response recorded) in the **same SQLite transaction** as the mutation's store writes and event append — so acknowledgment, audit event, and replay evidence are atomic at finalization, and both crash windows around the external provider side effect are closed: a crash before the provider leg leaves a pending intent with no provider effect (startup reconciliation verifies provider state and expires it), while a crash after a durable provider write but before finalization leaves a pending intent whose effect is durable — startup reconciliation observes the provider state, completes the store writes, appends the event, and finalizes, so the audit event lands late but exactly once, never lost. An identical-key retry that meets a pending intent drives reconciliation first, then replays; a lost IPC response or crash-window retry can re-drive only the provider leg (safe by construction: sanctioned provider writes are upserts, full-set replacements, or version-guarded), never a second acknowledgment or a second event. Receipts are retry-window dedup, not audit (events are the audit trail): `committed` rows older than 24 hours are pruned opportunistically on later mutation writes; `pending` intents are resolved at startup reconciliation, never silently pruned.
- Of the eight Cedar-gated operations, **six are governance mutations** bound by the one-event-set-per-mutation atomic audit invariant — `mcp.upsertServer`, `mcp.removeServer`, `mcp.setEnabled`, `mcp.setTrust`, `mcp.setToolOverride`, `mcp.clearToolOverride` — whose receipt finalization, store writes, and **defined event set** commit in one transaction: a single event for most mutations, and for `mcp.setTrust(false)` on a binding with materialized weakening facets the **revocation batch** — `mcp.server_trust_changed` plus one `mcp.tool_override_changed` per reverted facet (§Trust Governance) — all-or-nothing under the mutation's receipt, never re-emitted on replay. The remaining two are **operational commands outside that atomic invariant**. **`mcp.reconnect`** changes no daemon store and no provider config, so it carries no dedicated governance event — its observable effect is audited through the `mcp.server_status_changed` transitions it induces (leg-addressable: a `bindingId` reconnects one leg, a `sessionId` that session's legs, neither every live leg), and a reconnect attempt that produces no status transition intentionally leaves no governance-event row (the attempt is still Cedar-evaluated, and its failures surface as typed errors on the response). **`mcp.oauthLogin`** launches a provider flow whose durable trace — `mcp.server_oauth_completed` — is **provider-asynchronous by nature**: it cannot commit atomically with the launch acknowledgment, and an abandoned flow never completes, so the launch is receipted (idempotency) but deliberately not evented. The completion event is emitted **exactly once per observed completion** (Codex: the `mcpServer/oauthLogin/completed` notification; Claude: the on-transition status-flip rule, which dedups by construction); an abandoned or never-observed completion leaves only the expiring receipt, and an auth outcome the daemon misses (completion while the daemon is down) still surfaces as the server's next observed status transition — honest, never fabricated.
- The V1 principal model is **caller-owns-the-node**: only the node-local operator identity is authorized; callers arriving via control-plane relay receive `mcp.operator_scope_required`. The formalized remote-caller authorization model is [BL-141](../backlog.md)'s scope and a V1.1 ADR trigger, not a V1 surface.
- A Cedar deny returns `mcp.governance_denied`; authorization is evaluated before existence checks so the refusal is stable and does not leak inventory contents to unauthorized callers.
- No new approval _category_ is minted: governance mutations are direct Cedar authorization decisions, not interactive approval requests, so the [api-payload `ApprovalCategory`](../architecture/contracts/api-payload-contracts.md#shared-enums) union is unchanged; `mcp_elicitation` (run-time server elicitations) remains the only MCP-related approval category, owned by Spec-012.

### OAuth Orchestration

- `mcp.oauthLogin` starts the provider's own flow. Codex: app-server `mcpServer/oauth/login` — the daemon returns the provider's `authorization_url` to the caller, then observes `mcpServer/oauthLogin/completed` and emits `mcp.server_oauth_completed` with the outcome. Claude: interactive contexts route to `claude mcp login <server>`; the daemon observes completion as the server-status flip (there is no dedicated completion event on this provider) and emits `mcp.server_oauth_completed` on the flip.
- **Launch failures are errors; completion failures are events.** `mcp.oauth_flow_failed` is scoped to the **launch phase** — a provider-side failure to start the flow, surfaced on the still-open `mcp.oauthLogin` call. Once the call has returned (the `authorizationUrl` handed to the caller), the JSON-RPC channel for that request is closed by definition, so an asynchronous completion failure is delivered as the completion outcome itself: `mcp.server_oauth_completed` with `outcome: 'failure'` and a sanitized `failureReason`, observable on the `mcp.subscribe` stream and reflected by the server's persisting `needs-auth` status. The daemon never fabricates a late JSON-RPC error for a completed call.
- In a mode where the provider cannot run the flow in-band (Claude non-interactive), `mcp.oauthLogin` fails with `mcp.oauth_unsupported` and guidance naming the out-of-band command; the server's `needs-auth` status remains the visible state.
- The daemon MUST NOT store, log, or relay tokens, authorization codes, or PKCE material; the only durable trace is the `mcp.server_oauth_completed` event, whose payload carries the server identity and outcome, never credentials or URLs with embedded secrets. The idempotency receipt row for `mcp.oauthLogin` follows the same rule: the persisted response omits `authorizationUrl` **structurally** (launch URLs embed single-use PKCE state and are never durable), so an identical-key retry replays a URL-free acknowledgment — the flow is already launched, completion arrives as the event, and a caller that never received the URL begins a new login under a fresh key.

### Status Observation and Events

Five event types, `mcp_governance` category ([Spec-006 §MCP Governance (`mcp_governance`)](./006-session-event-taxonomy-and-audit-log.md#mcp-governance-mcp_governance)):

| Event | Emission point | Session binding |
| --- | --- | --- |
| `mcp.server_status_changed` | Normalized status transition from either provider feed (Codex `mcpServer/startupStatus/updated` / `mcpServerStatus/list` deltas; Claude init census + `mcpServerStatus()` deltas) | Per-event: the observing session's real `session_id` when the observation is a session-scoped provider feed; the daemon-scope sentinel for node-level probes |
| `mcp.server_config_changed` | Every applied configuration mutation | Sentinel-bound (node-scope) per [Spec-006 §Daemon-Scope Event Binding And Node-Scope Anchoring](./006-session-event-taxonomy-and-audit-log.md#daemon-scope-event-binding-and-node-scope-anchoring); `initiatingSessionId` in the payload when a session-scoped caller initiated |
| `mcp.server_trust_changed` | Trust grant, operator revoke, config-drift auto-revoke | Sentinel-bound; `initiatingSessionId` when applicable (absent on drift auto-revoke) |
| `mcp.tool_override_changed` | Override set / clear | Sentinel-bound; `initiatingSessionId` when applicable |
| `mcp.server_oauth_completed` | Provider flow completion (Codex notification; Claude status-flip observation) | Sentinel-bound; `initiatingSessionId` when applicable |

- Status observation is event-driven plus on-demand (`mcp.list` refresh); the daemon MUST NOT busy-poll provider status endpoints.
- **`mcp.subscribe` is the live governance stream.** The eleventh operation is a long-lived operator-readable subscription (the Plan-007 streaming primitive, the `session.subscribe` consumer shape) delivering every `mcp_governance` event envelope — sentinel-bound and session-bound alike — as the daemon appends it. It is live-tail with a **gap-free handshake, not a cursor**: a (re)connecting client opens `mcp.subscribe` first, then reads `mcp.list` — the subscribe acknowledgment precedes the stream's first delivery (the Plan-007 I-007-10 wire-ordering invariant), so registration is live before the snapshot read and an event concurrent with the snapshot arrives on the stream instead of falling between snapshot and subscription (re-observation is harmless — governance envelopes are re-entrant state updates; omission is impossible). History remains the locally-verified sentinel chain. This is how the desktop MCP panel and `ai-sidekicks mcp watch` observe governance without polling and without any per-session timeline merge (sentinel events never enter real sessions' streams — §Domain Dependencies).
- All five payloads are **credential-free and content-free by construction**: hashes, enums, scope identity, and sanitized failure reasons only — no config values, env-var values, header values, tokens, and none of the [Spec-022 §PII Data Map](./022-data-retention-and-gdpr.md#pii-data-map) durable-tier PII classes (user messages, file paths, code snippets). `failureReason` fields pass the daemon's error-sanitization layer and MUST NOT echo config values or filesystem paths. Binding identity in payloads is the **path-free audit ref**: `scopeRef` — a user-specific filesystem path — never enters an event payload; project/local variants carry `scopeRefDigest`, the `b3:`-prefixed keyed BLAKE3 (key = the binding's **scope-ref subkey** of the same daemon-held master key — derivable before any event fires and without any database row) of the canonical `scopeRef`, also served on inventory entries so operators join events to bindings; the raw path stays resolvable only through the node-local trust store. `mcp.server_status_changed` payloads with `origin: 'session_feed'` additionally carry the observing leg's `bindingId` — the Plan-005 runtime-binding key, an opaque daemon-minted identifier — so a subscriber can attribute the transition to its `legs[]` entry when one binding backs several legs in the same session (absent on `node_probe` rows, which observe no leg).
- `serverName` / `toolName` are the deliberate residual: operator- or provider-chosen free-form identifiers, `wireFreeFormString`-bounded, classified as **non-PII infrastructure identifiers** in the plaintext audit payload — the same classification as tool names in `tool_activity` events. An operator CAN embed personal data in a name they choose; the classification is recorded here (not silently assumed) so Plan-022's call-site PII classification pass over the event corpus inherits an explicit ruling with its rationale: governance provenance is unusable if server identity crypto-shreds with any single participant, and the identifiers age out of full payloads on the standard [Spec-006 §Event Compaction Policy](./006-session-event-taxonomy-and-audit-log.md#event-compaction-policy) lifecycle. No other free-form config-derived string may enter these payloads.

### Required-Server Semantics

- A Codex server with `required = true` that fails to initialize fails the thread start/resume; the daemon MUST map that failure onto the run-failure path with an actionable error naming the server, and emit `mcp.server_status_changed` (`failed`) for it — the run failure is never silent or attributed to the provider generically.

## Default Behavior

- New servers are enabled per provider config, **untrusted** in the daemon trust store, with no tool overrides (provider defaults + `manual_reconcile_only` idempotency floor).
- `mcp.list` serves the merged inventory from the most recent observations without forcing a provider round-trip; `refresh: true` forces one.
- Claude mutations prefer the live path whenever the capability probe says it exists; callers never select the mechanism, only observe the returned grade.
- Event emission is on-transition only — an unchanged status re-observation emits nothing.

## Fallback Behavior

- **Claude below the live-reconcile floor** (CLI < `2.1.210` or SDK < `0.3.166`, or a non-streaming-input session): config mutations complete through the durable user-scope leg alone, grade `user_config_write`; the enabled overlay applies at next-run composition, grade `next_run`.
- **Codex write conflict:** one silent re-read-and-retry; a second `configVersionConflict` surfaces `mcp.config_write_conflict` with both version tokens so the caller can re-inspect.
- **Scope-unsupported operation (either provider):** `mcp.config_scope_unsupported` per the §Configuration Mutation applicability rule — provider-config writes at non-`user` scopes, governance mutations on bindings V1 never materializes into runs, and native-write-only override facets on Codex `project` bindings — with the resolved config-file path in the _message guidance only_ (never in event payloads).
- **Status source unavailable** (provider down, probe unsupported at the running version): inventory serves `unknown` with an `observedAt` timestamp; the daemon does not fabricate `connected`/`failed`.
- **OAuth not runnable in-band:** `mcp.oauth_unsupported` + out-of-band guidance (see §OAuth Orchestration).
- **Trust store unavailable** (storage failure): governance reads degrade to the **degraded entry arm** — a discriminated `trustUnavailable: true` variant whose trust- and override-dependent fields (`trusted`, `configHash`, `toolOverrides`, the Claude enabled overlay) are structurally absent rather than fabricated, with provider-observed fields (config view, status, legs) intact — and `scopeRefDigest` still served: it derives from the daemon-held master key, not from any database row; all mutations fail closed.

## State And Data Implications

- **Three new daemon-local tables** (node-scoped; DDL in [Local SQLite Schema §MCP Governance Tables (Plan-028)](../architecture/schemas/local-sqlite-schema.md#mcp-governance-tables-plan-028)): `mcp_server_trust` (scope-qualified binding identity, `trusted`, the base-config `b3:`-hash binding, the native-tool baseline, grant/revoke provenance, and the Claude enabled overlay — no key material: every digest key derives from the daemon-held master key held outside the database), `mcp_tool_overrides` (per-tool facets, FK-cascaded to the trust row), and `mcp_mutation_receipts` (the idempotency receipt store — key, operation, request digest, replayed response; pruned on age, never part of the audit trail). SQLite census 52 → 55.
- **No provider-config mirroring**: provider files remain the config source of truth — including for Claude, whose durable declarations live in the provider's own user scope (written only via the sanctioned CLI) and whose per-run ephemeral config is a composed snapshot of that scope plus governance overlays, never an independent daemon-owned server set. The daemon persists only governance state (trust, overlays, overrides) and derives inventory on read; an acknowledged mutation survives daemon restart because the provider store holds it.
- **Events are the audit trail**: every mutation and transition appends through the Plan-006 `EventLogService` path — hash-chained, signed, replayable like every other category. Node-scoped events bind to the daemon-scope sentinel session per [Spec-006 §Daemon-Scope Event Binding And Node-Scope Anchoring](./006-session-event-taxonomy-and-audit-log.md#daemon-scope-event-binding-and-node-scope-anchoring).
- **Replay/recovery impact**: operator-assigned idempotency classes change what [Spec-015](./015-persistence-recovery-and-replay.md) recovery may safely replay — which is exactly why assignment is trusted-server-only, Cedar-gated, and audited.

## Example Flows

- `Example: live server add on Claude` — operator calls `mcp.upsertServer` (provider `claude`, scope `user`); the daemon persists the declaration via `claude mcp add-json linear <json> --scope user` and verifies the write; the capability probe says CLI `2.1.210+` streaming session, so the daemon additionally computes the full desired named-server set, calls `setMcpServers`, reconciles `{added: ["linear"], removed: [], errors: []}`; it upserts an untrusted trust row for the `(claude, user, "", linear)` binding, emits `mcp.server_config_changed` (grade `live_reconcile`) then `mcp.server_status_changed` (`starting` → `connected`), and returns the inventory entry with grade `live_reconcile`. Had the probe failed, the same call would return `user_config_write` with the declaration already durable.
- `Example: Codex write conflict` — two operators race `mcp.setEnabled`; the second write's `expected_version` is stale; the daemon re-reads, retries once against the new version, succeeds, triggers `config/mcpServer/reload`, emits `mcp.server_config_changed` (grade `user_config_write`).
- `Example: trust drift` — operator trusts `github` at hash `b3:abc…`; a later inventory refresh parses a changed `http_headers` block, hash now `b3:def…`; the daemon auto-revokes before use, emits `mcp.server_trust_changed` (`reason: 'config_drift'`), and the server's annotations stop informing approval decisions until re-trusted.
- `Example: OAuth on Codex` — `mcp.oauthLogin` → `mcpServer/oauth/login` → daemon returns `authorization_url`; operator completes in browser; `mcpServer/oauthLogin/completed` arrives; daemon emits `mcp.server_oauth_completed` (`outcome: 'success'`); next status observation flips `needs-auth` → `connected`.
- `Example: safety-weakening override denied` — operator sets `idempotencyClass: 'idempotent'` on a tool of an untrusted server; the daemon returns `mcp.trust_required` before any write; after `mcp.setTrust` grants trust, the same call succeeds and emits `mcp.tool_override_changed`.

## Implementation Notes

- **Re-verify at execution.** Every provider mechanism above is Verified at the provider-wire pins (`claude` `2.1.198`, `codex-cli 0.141.0`) or version-anchored beyond them (`mcp_set_servers` at `2.1.210`); Plan-028 code MUST re-verify load-bearing shapes against the then-installed binaries per [provider-wire README](../reference/provider-wire/README.md) before binding.
- **Codex generic thread-config map.** `ThreadStartParams` carries a generic `config` map whose MCP reach is unverified; if it can scope servers per-thread at execution time, it is an optimization _inside_ the same normalized surface (per-session scoping without user-config writes) — adopt behind the same interface, never as a new caller-visible mechanism. Recorded as the explicitly-deferred question in §Open Questions.
- **MCP revision watch.** The MCP 2026-07-28 revision (RC locked 2026-05-21) restructures the protocol core (stateless core, Tasks → extension, Roots/Sampling/Logging deprecated); both providers will absorb it in their own releases. This spec binds to _provider surfaces_, not the MCP wire, so the revision lands here only as provider-behavior changes caught by the re-verify rule.
- **Claude composition model.** The daemon drives `claude mcp add-json` / `claude mcp remove` at `--scope user` as the sanctioned durable-write mechanism, and declares each run's server set via ephemeral config (`--mcp-config` + `--strict-mcp-config`) composed as a **snapshot of the observed user scope plus governance overlays** at run start — built from the run-admission drift gate's fresh read (§Trust Governance), so composition never consumes a pre-drift-processing state — determinism means the session sees exactly the composed snapshot, immune to mid-run ambient drift, while ambient edits (operators using the human CLI directly) flow into the next composition and the inventory. Claude `project` (`.mcp.json`) and `local` scopes are observed read-only and deliberately **excluded from composition** in V1: strict-mode composition bypasses the provider's native project-file trust prompting, so auto-including them would launder project-file trust; their entries carry `effectiveInRuns: false`.
- **Config-hash normalization and transient-secret handling.** Hash inputs normalize the server config to the daemon's canonical shape (sorted keys via JCS, provider-native field names preserved) so cosmetic reordering does not flip hashes, but any semantic change to the base config (URL, headers, env, command, timeouts, `required`, auth) does — credential-bearing values included, so a rotated or tampered secret drifts the hash like any other semantic change. The daemon-managed override-projection fields are excluded per §Trust Governance — they are governed and audited through the override store, not the trust binding. The custody model for the credential-bearing input is transient-by-construction: parse the provider-owned file in memory, canonicalize, feed the keyed hash (the binding's derived config-hash subkey as the BLAKE3 key), discard — the values are never persisted, logged, served, or embedded in any payload, and the keyed digests are the only derived artifacts that survive — the base-config hash and the event-side `scopeRefDigest` alike. **Key custody is one artifact:** the daemon holds a single 32-byte **MCP governance master key** in a node-local key file beside its other node key material (the same custody class as the event-signing key), generated at first governance use and never entering SQLite; every digest key is a purpose- and binding-separated subkey derived from it via BLAKE3 keyed-PRF (the config-hash, scope-ref, and receipt-digest subkeys) — keyed mode takes exactly a 32-byte key, and keeping the key material out of the database is what makes every stored or served digest non-brute-forceable from a database copy or backup alone. Losing the master key is fail-closed by construction: no key, no comparable hash, no trust — re-granting re-binds under the regenerated key.

## Pitfalls To Avoid

- **Writing non-user scopes.** Codex upstream rejects project paths for config writes, and Claude project/local scopes are observed-only in V1; attempting either corrupts the parity story — surface `mcp.config_scope_unsupported` instead.
- **Collapsing scope bindings.** Two scopes declaring the same `serverName` are different configurations with independent status, trust, and overrides; folding them into one node-global identity makes legitimate per-scope configs look like config drift (trust ping-pong) and bleeds one scope's overrides into the other.
- **Trusting annotation self-claims.** A server saying `readOnlyHint: true` is data, not authorization; only the operator trust store admits annotations into decision surfaces (the ADR-015 MUST — stable MCP-spec language since 2025-03-26, not a recent strengthening).
- **Delta-sending `setMcpServers`.** The call replaces the full named-server set; sending a delta silently removes every unsent server. Always send the full desired set.
- **Treating `--help` as the capability census.** The Claude CLI's `--help` omits real flags; capability probes and the provider-wire reference are authoritative (the documented `--help`-non-authoritative rule).
- **Echoing secrets.** Config values, env vars, headers, tokens, authorization URLs, and URL query-string values never enter events, inventory reads, errors beyond guidance messages, or logs; `bearer_token_env_var` names an env var — the _name_ may appear in inventory, the _value_ never leaves the provider; a server URL round-trips query-redacted (parameter names only — §Unified Inventory).
- **Treating the hash exclusion as a drift exclusion.** The override-projection fields are excluded from the base-config hash so governed writes never self-revoke — not because they are unobserved; skipping their reconciliation against the baseline-anchored expected state would let an out-of-band `enabled_tools` broadening ride into a run under an unchanged hash (§Trust Governance).
- **Erroring after the durable leg committed.** A mutation whose durable leg has committed MUST NOT surface a later live-leg failure as a JSON-RPC error — the caller would retry a write that already landed. Committed-then-degraded outcomes are successful responses with honest `applied` grades and per-leg `liveResults[]`; `mcp.config_invalid` exists strictly pre-commit.
- **Conflating elicitation approval with governance authorization.** `mcp_elicitation` (Spec-012, session-scoped, interactive) and the `mcp` Cedar action family (this spec, node-scoped, non-interactive) are different layers; routing governance through interactive approvals would deadlock headless operation.
- **Polling provider status.** Both providers push (notifications / feed emissions); polling is on-demand-only.

## Acceptance Criteria

- [ ] `mcp.list` merges all four sources and round-trips both providers' declared servers with correct `(provider, scope, scopeRef, serverName)` binding separation — same-named servers in two scopes surface as distinct entries whose status, trust, and overrides never cross
- [ ] Claude mutation persists through the sanctioned user-scope CLI write before acknowledgment and survives a daemon restart (the restarted daemon's inventory and next composed run both contain it); above the version floor the same call additionally applies live and returns grade `live_reconcile`, below it `user_config_write`
- [ ] Codex mutation writes user scope with `expected_version`, retries a conflict exactly once, triggers reload, and surfaces `mcp.config_write_conflict` on double conflict
- [ ] Provider-config mutation attempts at non-`user` scopes (Codex project; Claude project/local) and governance mutations on non-effective bindings (Claude project/local) fail with `mcp.config_scope_unsupported`, target file byte-identical; on an effective Codex `project` binding, `mcp.setTrust` and the daemon-enforceable override facets (`idempotencyClass`) succeed while native-write-only facets (`enabled`/`approvalMode`) refuse with the same code
- [ ] Binding refs are structurally valid at the schema layer: `scopeRef` rejected for `user` scope, required non-empty for `project`/`local`, and `(codex, local)` rejected outright — each as a typed validation error, never a database constraint failure; the DDL CHECKs mirror the same rules as defense in depth
- [ ] `mcp.get` returns the redacted `McpServerConfigView` round-tripping every non-secret field `mcp.upsertServer` accepted (transport, command/args, the query-redacted URL plus its query-parameter names, timeouts, `required`, `bearerTokenEnvVar`, the Codex auth references, env-var and header **names**) with zero secret values anywhere in the response, and an update leaves unmodeled provider fields byte-identical — a `?api_key=…` URL serves scheme + host + path with `api_key` listed by name and its value absent; per-leg `legs[]` surfaces divergent concurrent-session statuses that the top-level aggregate `status` ranks deterministically (`unknown` legs included, per the fixed order), each `session_feed` status event carries its leg's `bindingId`, and a terminated session's leg retires — its last status (a `failed` included) no longer participates in the aggregate
- [ ] An out-of-band provider-config edit followed immediately by a run start is caught by the run-admission drift gate: revocation and weakening neutralization complete (events emitted, Codex native fields reverted) before the provider process spawns, and the run's config reflects the post-drift state — including a projection-field-only edit (`enabled_tools` / `disabled_tools` / `tools.<t>.approval_mode`) whose base-config hash is unchanged, and the daemon-restart variant: the same edit made while the daemon was down completes drift processing before startup recovery adopts or resumes any provider session
- [ ] Replaying a governance mutation with the same `clientIdempotencyKey` and identical request returns the recorded response with no second provider call, store write, or event; the same key with a differing request fails `mcp.idempotency_conflict` leaving the original untouched — both verified across a daemon restart; a crash between the durable provider write and receipt finalization reconciles at startup (the audit event appends exactly once — late, never lost, never doubled); the `mcp.oauthLogin` receipt row and its replayed acknowledgment contain no `authorizationUrl`
- [ ] A Claude durable-success/live-failure mutation returns success with `applied: 'user_config_write'` and a per-leg `liveResults[]` failure entry — never a JSON-RPC error after the durable commit, and never an unreported live failure
- [ ] `enabled: true` on a provider-disabled tool of an untrusted binding fails `mcp.trust_required`; the same override under trust applies and is neutralized on revocation like every weakening facet
- [ ] An asynchronous OAuth completion failure is delivered as `mcp.server_oauth_completed` with `outcome: 'failure'` on the `mcp.subscribe` stream (never a late JSON-RPC error); `mcp.oauth_flow_failed` remains reachable via a launch-phase failure
- [ ] The subscribe-then-list handshake is gap-free: an event appended between a subscriber's `mcp.subscribe` acknowledgment and its subsequent `mcp.list` read is delivered on the stream, and the stream delivers nothing appended before the acknowledgment
- [ ] First observation of an unknown server creates an untrusted trust row; no code path creates `trusted = 1` without an operator `mcp.setTrust`
- [ ] Base-config drift on a trusted binding auto-revokes before use and emits `mcp.server_trust_changed` with `reason: 'config_drift'`; a daemon-governed override write does NOT drift the hash, and revocation reverts Codex-materialized weakening fields in the same operation
- [ ] Safety-weakening overrides on untrusted servers fail with `mcp.trust_required`; safety-tightening overrides succeed regardless of trust; a weakening facet granted under trust stops resolving the moment trust is revoked
- [ ] Operator-assigned `idempotencyClass` reaches the Spec-005 tool-metadata resolution output; absent assignment resolves to `manual_reconcile_only`; resolution is binding-keyed — with the same `serverName` bound in two scopes, each session's invocation resolves its own effective binding's override, never the other scope's
- [ ] A Codex binding whose user config already carries native `enabled_tools` / `disabled_tools` / `tools.<t>.approval_mode` values survives an override set → clear round-trip with those native values restored from the baseline; revocation rewrites weakening fields to the baseline-anchored safe state, never to an invented default
- [ ] With the trust store unavailable, `mcp.list` / `mcp.get` serve the degraded entry arm (`trustUnavailable: true`; trust- and override-dependent fields structurally absent, provider-observed fields and the key-derived `scopeRefDigest` intact) and every governance mutation fails closed
- [ ] `mcp.removeServer` emits `mcp.server_config_changed` with `previousConfigHash` and no `configHash` — the removal payload validates against the schema without fabricating a post-removal hash
- [ ] Each of the six governance mutations emits its defined event set exactly once (single-event for most; a weakening-facet revocation's batch — the trust event plus its per-facet reversion events — appends all-or-nothing), with sentinel binding for node-scope events and real-session binding for session-feed status observations; `mcp.server_oauth_completed` is emitted exactly once per observed flow completion — an abandoned flow emits nothing and leaves only its expiring receipt; `mcp.reconnect` emits no governance event beyond the status transitions it induces
- [ ] Event and error payloads contain no config values, tokens, env-var values, or unsanitized paths — raw `scopeRef` included: project/local event payloads carry `scopeRefDigest`, never the path (schema-level test over all five payload types + ten error codes)
- [ ] All ten `mcp.*` error codes are reachable in integration tests and absent from success paths
- [ ] Remote (relay-originated) mutation attempts fail with `mcp.operator_scope_required` before any store or provider mutation

## ADR Triggers

- Remote governance mutation (control-plane-relayed operator actions) — requires the BL-141 caller-authorization model formalized as an ADR before any implementation.
- A third provider CLI joining the parity set — re-derives the capability table and may fork normalization decisions.
- Provider adoption of the MCP 2026-07-28 revision materially changing config/auth surfaces (e.g., Tasks-extension governance) — reference update plus re-derivation of the capability table.
- Any proposal to store credential material in the daemon — hard ADR gate; the no-custody posture is a deliberate one-way-door refusal.
