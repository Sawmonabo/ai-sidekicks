## Required Behavior

- A participant with active session membership must be able to attach a local runtime node to an existing live session.
- Runtime-node attach must be a separate step from membership acceptance.
- Attach must include node identity, declared capabilities, health, and trust context.
- The system must support multiple runtime nodes per session and multiple agents per runtime node.
- Runtime-node attach must not require session recreation.
- Runtime-node detach or offline state must not revoke session membership by default.
- The control plane must coordinate runtime-node discovery and presence, but execution must remain local to the attached node.
- At attach, the control plane MUST verify the daemon's reported version against the session's `min_client_version` floor (declared in [Spec-001 §State And Data Implications](./001-shared-session-core.md#state-and-data-implications)). A NULL floor permits all daemons. A daemon below the floor MUST be admitted in read-only state — the daemon remains joined and may read session state, but any subsequent **version-sensitive domain write** (e.g. a capability declaration via `capabilityupdate`) MUST return typed `VERSION_FLOOR_EXCEEDED` per [ADR-018 §Decision #4](../decisions/018-cross-version-compatibility.md); **presence/liveness heartbeats are version-invariant and are EXEMPT** from this refusal — a below-floor node continues to heartbeat and report presence (the exemption holds only while the heartbeat payload stays version-invariant — revisit if a version-sensitive field is ever added to the heartbeat shape). Ejection MUST NOT be the response to a floor mismatch (graceful degradation, not ejection).
- **Shared-terminal write lease (campaign B4, 2026-07-06).** Extending the same write-capability axis the version floor governs: write access to a session's shared terminal surface is an **exclusive per-session lease** — exactly one participant may hold terminal control at a time. Role authorization precedes lease state: `session.takeControl` is owner/collaborator-only per the [Security Architecture permission matrix](../architecture/security-architecture.md#permission-matrix-task-54) 'Take/release terminal control' row — a viewer's or runtime contributor's take is refused `pty.permission_denied` (403) before any lease-state comparison, so an unauthorized caller never learns holder identity; release is deliberately holder-gated rather than role-gated (only owner/collaborator roles can ever have acquired the lease, and during the demotion-signal propagation window a holder demoted mid-hold must still be able to relinquish — a role re-check there would refuse the holder's own cleanup exactly when it matters; once the demotion reaches the lease authority, the role-downgrade force-clear below has already freed the lease). `session.takeControl` acquires it (**first-acquire-holds**: an uncontested take succeeds immediately, no approval hop) and `session.releaseControl` frees it; while **no participant holds the lease, terminal writes are refused** (`pty.control_not_held` — fail-closed, a writer must take control explicitly, never implicitly); a take while another participant holds it is refused with `pty.control_held_by_other { holderParticipantId }` (handoff is explicit: the holder releases, the next writer takes); a `session.releaseControl` by a non-holder is likewise refused with `pty.control_not_held` (release is not idempotent-success — it signals a caller-state bug); a `session.takeControl` by the participant already holding the lease is by contrast **idempotent success** — the response names the caller as `controlHolder` and no `pty.control_changed` broadcasts (no transition occurred); and the lease **auto-releases on holder disconnect** (the holder's presence/attachment drop frees it — no dead-holder lockout) **and on holder role downgrade**: when a `membership.role_changed` ([Spec-006](./006-session-event-taxonomy-and-audit-log.md)) removes the current holder from the authorized set, the lease authority force-clears the lease as it applies the change (broadcast `reason: 'auto_released_role_downgrade'`), so revocation of write authority takes effect at signal arrival over the terminal-owning daemon's control-plane membership feed — the same propagation bound every membership-driven enforcement change carries — never waiting on the demoted holder's next disconnect or voluntary release. Every transition broadcasts `pty.control_changed` ([Spec-006 census](./006-session-event-taxonomy-and-audit-log.md#pty-control-session_lifecycle), registered by this amendment). Exactly-one-writer is deliberately stricter than the surveyed reference runtime's multi-editor grant on correctness grounds: a PTY exposes a single input stream, so concurrent writers interleave keystrokes into corrupted command lines — the lease makes handoff explicit and instant instead (precedent survey — Live Share's host-granted terminal write, Warp's View-default sharing, tmux's absent write lock — in §References). Enforcement sits at the **daemon terminal-write boundary**, where the authenticated participant identity is known from the execution context. In V1 the two methods are **daemon-transport-only** — registered on the daemon JSON-RPC surface with no control-plane tRPC leg: the terminal-owning daemon is the sole lease authority, and the corpus defines no control-plane→daemon command path that could forward a remote mutation to it ([ADR-008](../decisions/008-default-transports-and-relay-boundaries.md)'s relay is E2E peer connectivity, not a control-plane command channel), so a tRPC registration would place the mutation on a party that can neither adjudicate nor enforce it. The V1 writer identities at the boundary are exactly the identities whose bytes can reach a V1 terminal: the node-owner participant (local socket — the registry's absent-actor binding) and the node's own agent runs (daemon-internal participant identities, no wire hop). Remote participants observe `controlHolder` through the `runtimenode.roster` projection; a remote take becomes possible only when a relay-borne terminal-write leg exists, and it MUST then ride the same E2E channel as the terminal bytes it gates, with the relay peer's PASETO-verified participant identity as the principal — one authenticated identity for lease and writes by construction; the PTY-sidecar wire is untouched — its `WriteRequest` frame (`packages/contracts/src/pty-host-protocol.ts#WriteRequest`) deliberately carries no participant field, because bytes that reach the sidecar are already lease-authorized (the sidecar's own `WriterUnavailable` write-error is a process-level stream guard beneath this policy layer, not a participant-lease surface). Implementation lands with Plan-024's Phase 3B terminal-session leg via the campaign's Plan-024 bundle.

## Default Behavior

- Newly attached runtime nodes default to `online` only after capability declaration succeeds.
- Node capability exposure defaults to least privilege: only explicitly declared capabilities are schedulable.
- Runtime-node heartbeats default to `15s`, matching participant presence cadence unless overridden.
- A runtime node transitions to `degraded` when its most recent heartbeat (`runtime_node_presence.last_heartbeat_at`) is older than `30s` (≈ 2 missed `15s` beats) and to `offline` when older than `60s` (≈ 4 missed beats). The `30s` band between the two thresholds is deliberate hysteresis: a node whose heartbeats resume within it returns to `online` without ever passing through `offline`.
- These `degraded`/`offline` transitions are **server-derived and owned by the control plane** — never self-reported by the node. The control plane's heartbeat service evaluates `last_heartbeat_at` on a periodic staleness sweep and **records the transition on the coordination record** — the sweep-owned `runtime_node_presence.health_state` liveness axis, reconciled into the node's roster-visible state alongside `runtime_node_attachments.state` (per the `capabilityupdate` amendment above). (A silent or dead node sends nothing, so the demotion cannot be heartbeat-ingest-driven — it must be sweep-driven; and the wire health enum is `online | degraded` only, so a node can never report itself `offline`.) The timing guarantee is that a transition is **recorded within one sweep interval of a threshold crossing**; the sweep interval is an implementation choice of [Plan-003 T3.6](../plans/003-runtime-node-attach.md), set finer than the `15s` cadence to keep that bound tight. The control plane authors **no durable `runtime_node.*` session event** for these server-derived transitions in V1 — their durable emission is gated to V1.1 on the node-identity trust anchor ([ADR-017 §Server-Derived Runtime-Node Lifecycle Events](../decisions/017-shared-event-sourcing-scope.md#server-derived-runtime-node-lifecycle-events); §Amendment below).

> **Amendment (approved spec — 2026-06-03, BL-140 / PR #139).** The two thresholds and the sweep owner above were under-specified at original approval, which gave only the `15s` cadence; they are recorded here as canonical defaults rather than deferred to implementation, per [Plan-003 T3.6](../plans/003-runtime-node-attach.md). **Why `2→4` (balanced) over aggressive (`2→3`, `offline` at `45s`) or conservative (`3→6`, `offline` at `90s`):** `offline` is _reversible_ — it neither revokes session membership (§Required Behavior) nor blocks reconnect under the same node identity (§Fallback Behavior) — so a false-positive `offline` is cheap, which argues against an over-conservative window; `60s` brackets the reversible Kubernetes node-`NotReady` grace (~40–50s, version-dependent), and the `30s` hysteresis band absorbs a single transient GC or network stall without UI flap. This mirrors the suspect-before-dead staging of SWIM and the reversible-`UNREACHABLE`-before-terminal-`DOWN` model of Akka's Φ-accrual detector (primary sources in §References).

> **Amendment (approved spec — 2026-06-04, Plan-003 Phase-3 four-procedure reconciliation).** `runtimenode.capabilityupdate` — one of the four runtime-node control-plane **mutation** procedures in the [Runtime-Node Method-Name Registry](../architecture/contracts/api-payload-contracts.md) (a fifth registry entry — the control-plane-only `runtimenode.roster` **query** — joined 2026-06-09 per the §Interfaces And Contracts amendment, PR #150) — **refreshes the control-plane discovery snapshot** of a node's declared capabilities on its single active `runtime_node_attachments` row. This is coordination, not execution (line 52): the **daemon-side node-capability service remains the authoritative declarer**, so the operation MUST NOT drive `registering → online` (line 58 — that transition requires a successful daemon-side capability declaration; [Plan-003 §Invariants I-003-2](../plans/003-runtime-node-attach.md)).
>
> A daemon MAY co-report a **capability-health** change via `capabilityupdate.healthChanges`, and that signal travels the **same self-reported-health axis as `attach` and `heartbeat` — `online ↔ degraded` only** (the 2-value `RuntimeNodeHealthState` wire-health enum those two siblings already carry). A daemon self-reports only its _own_ capability-health (the §Fallback Behavior axis — capability-validation failure leaves the node `degraded`); it **cannot** assert `offline` or `revoked`. Those belong to other authorities and **will be made unrepresentable in the request type**: [Plan-003 T3.0](../plans/003-runtime-node-attach.md) **narrows** `healthChanges.state` to `RuntimeNodeHealthState` (down from the 5-value `NodeState`), flipping the canonical Zod schema and its `api-payload-contracts.md` wire-shape mirror in lockstep so the doc never leads the code. Once that narrowing lands the boundaries hold by construction rather than by runtime check:
>
> - **`offline` is liveness-death — server-effected**: the control-plane sweep derives it from heartbeat staleness (line 62), or an explicit `detach` retires the node (line 86) — never daemon-self-reported via `healthChanges`. (Established practice: in Kubernetes the kubelet self-reports `Ready`, but the node controller derives `Unknown`/NotReady from missed heartbeats; in SWIM/Lifeguard a node's self-reported health is an _input_ to the detector, not the failure verdict. §References.)
> - **`revoked` is a trust decision issued by an authority** _about_ the node (the session / detach / admin path), never self-asserted by the node. (Established practice: zero-trust / SPIFFE revocation is authority-issued denial of trust, not subject-declared. §References.)
>
> A daemon-reported capability-`degraded` and the sweep's staleness-`degraded`/`offline` are **independent health axes with distinct owners** (orthogonal to, not a violation of, the line-62 rule that liveness-`degraded`/`offline` is sweep-derived) — the daemon reports its own capability-health (`online ↔ degraded`); the control plane derives liveness from heartbeat age — so the node's effective roster state **reconciles** both axes, a recovery on one never masking a degradation on the other, rather than collapsing into a single self-reported scalar that two writers could race on (the self-reported-vs-derived separation Kubernetes draws between the kubelet's `Ready` self-report and the controller-derived node `Unknown`; §References); the storage backing each axis is owned by its writer — the staleness sweep ([Plan-003 T3.6](../plans/003-runtime-node-attach.md)), the capability-update service ([Plan-003 T3.9](../plans/003-runtime-node-attach.md)) — not pinned in this contract. The control-plane operation writes **no** durable `runtime_node.*` event (ADR-017 — the control plane has no event log); the durable **audit record** is the daemon-side node-capability service's authoritative `runtime_node.capability_updated` emission (the §State And Data Implications session-event for capability and trust-posture changes), of which this snapshot-refresh is the control-plane **projection** — so the audit trail is complete without a control-plane event, and its `updatedAt` response field is the mutation-time server clock, **not** a stored column (the canonical `runtime_node_attachments` schema carries only `attached_at`); the **response** `state` is the server-derived liveness position the control plane owns (full `NodeState`). **Why ratify now:** the [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md) registry listed `runtimenode.capabilityupdate` but typed `healthChanges.state` as the broad 5-value `NodeState` — inconsistent with the `online | degraded` self-report its `attach`/`heartbeat` siblings carry, and silent on the authority boundary. [Plan-003 T3.0 (contract narrowing) + T3.9 (service)](../plans/003-runtime-node-attach.md) implement it. **(Amended 2026-06-09, PR #150: the per-axis _storage_ above remains writer-owned and unpinned, but the read-side _projection_ of both axes is now pinned — the control-plane-only `runtimenode.roster` query carries `state` and `healthState` verbatim per axis with no collapsed scalar; see the roster amendment in §Interfaces And Contracts. Reconciliation remains the client's render-time concern.)**

## Fallback Behavior

- If attach completes but capability validation fails, the node must remain attached in `degraded` or `offline` state rather than being treated as healthy.
- If the control plane cannot broker collaborative visibility, the local daemon may remain usable for `local-only` execution on that participant machine.
- If a previously attached node disconnects, active membership remains intact and the node may later reconnect under the same node identity.

## Interfaces And Contracts

- `RuntimeNodeAttach` must include session id, participant id, node id, capability declarations, and health metadata.
- `RuntimeNodeHeartbeat` must update presence and health.
- `RuntimeNodeCapabilityUpdate` must support capability additions, removals, and health changes.
- `RuntimeNodeDetach` must explicitly retire or disconnect a node from the session.
- `RuntimeNodeRoster` must return the session's full node roster — every `runtime_node_attachments` row for the session, both health axes carried verbatim — via the control-plane-only `runtimenode.roster` query (pinned in the 2026-06-09 amendment below).
- `session.takeControl` / `session.releaseControl` (campaign B4) must acquire/free the shared-terminal write lease per §Required Behavior, registered in the [Session Terminal-Control Method Registry](../architecture/contracts/api-payload-contracts.md#session-terminal-control-method-registry-tier-3-campaign-b4); the roster read's response carries the current `controlHolder` (`ParticipantId | null`) so control-plane-connected clients render the lease from the same faithful projection (daemon-transport clients — including the local-only fallback — render it from the `pty.control_changed` stream and the take/release mutation responses); refusals use the `### PTY` codes in [Error Contracts](../architecture/contracts/error-contracts.md).
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- Runtime-node records must be durable enough to support reconnect and audit.
- Capability declarations and trust posture changes must be emitted as session events. **(V1 scope clarified — §Amendment 2026-06-06: capability declarations are daemon-authored and ship in V1; the trust-posture `revoked` durable event is criterion-gated to V1.1 per [ADR-017 §Server-Derived Runtime-Node Lifecycle Events](../decisions/017-shared-event-sourcing-scope.md#server-derived-runtime-node-lifecycle-events).)**
- Node health changes must not rewrite historical run provenance.

> **Amendment (approved spec — 2026-06-06, Plan-003 Phase-3 lifecycle-event reconciliation).** The §Default Behavior treatment of the heartbeat sweep's server-derived `degraded` / `offline` transitions — corrected above from durable-event emission to a coordination-record write — and this section's MUST that "capability declarations and trust posture changes must be emitted as session events" are reconciled with accepted [ADR-017 §Server-Derived Runtime-Node Lifecycle Events](../decisions/017-shared-event-sourcing-scope.md#server-derived-runtime-node-lifecycle-events):
>
> - **Server-derived transitions** (heartbeat-staleness `degraded`, heartbeat-loss `offline`, authority-issued `revoked`) are recorded in V1 as **coordination records** (`runtime_node_presence.health_state` / `runtime_node_attachments.state`). V1 authors **no durable `runtime_node.*` session event** for them: the control plane has no event log and no roster-resolvable node-identity key (ADR-017 + ADR-010), a dead/untrusted node cannot self-report, and a peer never observes the liveness fact (heartbeats are control-plane-only), so it could only rubber-stamp the control plane's verdict — the forgeability ADR-017 §Node-Scope Anchor Witnessing names. This is the Kubernetes node-controller / SWIM / SPIFFE failure-detector model already cited in §References. Durable emission + the `degraded`/`revoked` payload schemas are **gated to V1.1** on the node-identity trust anchor (Plan-018 / Plan-003), forward-compatible with V2 MLS `external_senders` ([RFC 9420 §12.1.8](https://www.rfc-editor.org/rfc/rfc9420)).
> - **Capability declarations** (`capability_declared` / `capability_updated`) are **daemon-authored by the declaring node** (a live roster member) and satisfy the MUST in V1 (Plan-003 Phase 2). The **trust-posture (`revoked`) durable event** is the criterion-gated piece — V1's `runtime_node_attachments.state = revoked` coordination record carries the operational trust truth until the V1.1 node-identity anchor lets the control plane author the durable event soundly.
> - **`offline` the event still exists in V1** — authored daemon-side via explicit shutdown (detach, Plan-003 Phase 2); only the **sweep-derived** (heartbeat-loss) `offline` is the V1.1-gated durable-event path. The §Default Behavior coordination-column demotion (degraded/offline) and §Acceptance-Criteria distinguishability of a degraded/offline node from a healthy one are V1 behavior, satisfied by the coordination record.

## Example Flows

- `Example: A participant joins a live session, attaches a local runtime node that exposes Codex and Claude drivers, and later creates a reviewer agent on that node.`
- `Example: A node loses provider access and becomes degraded while session membership remains active and readable by other participants.`

## Implementation Notes

- Attach should be fast enough to feel interactive, but node health must not flip to healthy before capability validation completes.
- Node identity must be stable across reconnect if the same local daemon is reattaching.
- Scheduling logic must read node capability and health, not just membership role.

## Pitfalls To Avoid

- Treating membership as automatic node trust
- Allowing implicit capability exposure on attach
- Destroying historical node provenance when a node reconnects

## Acceptance Criteria

- [ ] A participant can attach a local runtime node to an already active session.
- [ ] A degraded or offline node remains distinguishable from a healthy online node.
- [ ] Multiple runtime nodes can coexist in one session without changing session identity.
- [ ] A daemon attaching with a version below the session's `min_client_version` is admitted in read-only state, surfaces typed `VERSION_FLOOR_EXCEEDED` on any subsequent version-sensitive domain write (e.g. a capability declaration via `capabilityupdate`), and is never ejected for the floor mismatch (per [ADR-018 §Decision #4](../decisions/018-cross-version-compatibility.md)).
- [ ] An uncontested `session.takeControl` succeeds immediately (first-acquire-holds), the roster projection's `controlHolder` reflects the new holder, and `pty.control_changed` is broadcast.
- [ ] A terminal write while **no** participant holds the lease is refused with typed `pty.control_not_held` (null-holder-refuses-writes) — writes never succeed implicitly.
- [ ] A `session.takeControl` while another participant holds the lease is refused with typed `pty.control_held_by_other` carrying `holderParticipantId`; after the holder's `session.releaseControl`, the same take succeeds (explicit handoff).
- [ ] When the lease holder disconnects, the lease auto-releases (`controlHolder` returns to `null`, `pty.control_changed` broadcast), and subsequent writes are refused until a participant re-acquires.

- `capabilityupdate` capability-health authority model (2026-06-04 amendment, §Default Behavior) — least-privilege grounding for _the node self-reports its own capability-health; the system derives liveness-death; the trust authority issues revocation_, enforced by making `offline`/`revoked` unrepresentable in the daemon self-report type:
  - [Kubernetes — Node Status](https://kubernetes.io/docs/reference/node/node-status/): the kubelet self-reports the `Ready` condition, but the node lifecycle controller sets it to `Unknown` when it "has not heard from the node in the last `node-monitor-grace-period`" — liveness-death is control-plane-derived, not self-asserted. (The closest direct analogue to a daemon that reports its own health while the control plane owns the `offline` verdict.)
  - [SWIM (Das, Gupta, Motivala, DSN 2002)](https://www.cs.cornell.edu/projects/Quicksilver/public_pdfs/SWIM.pdf) + [Lifeguard (Dadgar, Phillips, Currey, 2017)](https://arxiv.org/pdf/1707.00788): failure detection is detector-owned; a node's self-reported local health is an _input_ that improves detector accuracy, never the failure verdict itself.
  - [SPIFFE/SPIRE — zero-trust workload identity](https://github.com/spiffe/spiffe/blob/main/standards/SPIFFE_Federation.md): trust revocation is authority-issued (trust-bundle controlled / denial of further issuance), never declared by the subject workload — a node must not assert its own `revoked` status.
  - [Making illegal states unrepresentable (Wlaschin; principle attributed to Minsky)](https://fsharpforfunandprofit.com/posts/designing-with-types-making-illegal-states-unrepresentable/): encode the invariant in the type so invalid states cannot be constructed, rather than relying on runtime validation. The enforcement mechanism: `healthChanges.state` is the 2-value `RuntimeNodeHealthState`, so `offline`/`revoked` cannot be sent at all.
- Server-derived lifecycle-event authorship (2026-06-06 amendment, §Required Behavior + §Default Behavior) — prior art for recording a controller-derived liveness/trust transition as a coordination record rather than a node-authored durable event, the basis for V1 deferring durable `runtime_node.degraded`/`offline`/`revoked` emission to the V1.1 node-identity trust anchor:
  - [Kubernetes — Nodes (node controller & status conditions)](https://kubernetes.io/docs/concepts/architecture/nodes/): the node controller derives `NotReady`/`Unknown` from missed heartbeats and records it as a **status condition in the central coordination store (etcd)** — it does **not** author a signed per-observer "node failed" event into a distributed log. The direct analogue for V1 writing the server-derived transition to `runtime_node_presence.health_state` / `runtime_node_attachments.state` as a coordination record, with no durable session event until a sound authenticated authority (the V1.1 node-identity anchor) exists.
  - [RFC 9420 (MLS) §12.1.8 — External Proposals / `external_senders`](https://www.rfc-editor.org/rfc/rfc9420): the standards-track E2EE realization of the same authority model — a non-member authority _proposes_ a lifecycle change and group members _commit_ it — the V2 forward-compatible target once the control plane is an authenticated `external_senders` entity.
- Shared-terminal write-lease precedent survey (campaign B4 amendment, §Required Behavior) — the multi-editor grant models this spec's exactly-one-writer lease is deliberately stricter than, and the counter-example confirming the unguarded-PTY failure mode:
  - [VS Code Live Share — shared terminals](https://learn.microsoft.com/en-us/visualstudio/liveshare/use/share-server-visual-studio-code): shared terminals default read-only; the host explicitly grants read/write — write access to a shared terminal is a host-granted capability, never ambient.
  - [Warp — session sharing](https://docs.warp.dev/knowledge-and-collaboration/session-sharing/): joiners enter in View mode; Edit is a granted elevation — the same explicit-grant posture, on a commercial terminal whose multi-editor grant permits concurrent writers once granted.
  - [tmux(1)](https://man.openbsd.org/tmux): attached clients share one input stream with no built-in write lock (`attach -r` is voluntary read-only self-restraint) — concurrent writers interleave keystrokes into a single corrupted command line, the failure mode the exclusive lease exists to prevent.
