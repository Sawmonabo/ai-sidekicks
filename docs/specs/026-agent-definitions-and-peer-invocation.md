## Purpose

An agent is configured once and used many times. Without a durable record, the configuration a user tuned — provider, model, effort, instructions, the tools it may reach, the account that pays for it — would exist nowhere except inside whichever session it was typed into. This spec defines the **agent definition**: a node-local, named, durable record of that configuration, and the rules by which the daemon resolves one when a run starts under it.

It also defines **peer invocation** — the one daemon-owned tool server by which a running agent reaches another agent, including one bound to the other provider. Peer invocation is the reason the definition registry must exist rather than merely being convenient: an agent naming the peer it wants needs a stable, node-local thing to name.

## Scope

- A definition is **authored content with a lifecycle** — created, edited, duplicated, exported, imported, deleted, and found by search — and it is kept at the top level, beside the surfaces that consume it: its own destination on the console's rail rather than a page of node configuration ([ADR-029](../decisions/029-five-rail-destinations.md)). A destination is where a person goes to make or use something; a configuration page configures the node or the app.
- The `agent_definitions` registry: its fields, its identity model, its uniqueness rules, its origins, and its node-local lifetime.
- The split between a definition's **core** — name, role, icon and accent, instructions, goal, tool allowlist, hooks, memory scope, turn cap — which is provider-agnostic, and its **bindings** — driver, model, paying account, effort — which are a plural axis, so one agent runs on either provider without being copied into a second definition.
- Resolution when a run starts: how the daemon resolves a definition, what it applies, what it echoes back, and what it refuses.
- Peer invocation: the one daemon-owned tool server and its verbs, how each provider's lead reaches them, their targeting rules, their authorization, and their cost and causation consequences.
- **One registry, read by every surface that chooses an agent** — a session's composer and the workflow builder's node alike. A surface holding a list of its own would be a second copy of one registry; the control that chooses belongs to the surface it sits on, and the registry it reads belongs here.
- The editing surfaces the desktop and CLI clients present for definitions: the library over the registry, the editor over one definition, and `Browse plugins`, the view over each provider's own plugin catalogs through which agents and skills made elsewhere are installed.

## Non-Goals

- **No new orchestration primitive.** A peer invocation creates an ordinary orchestration-admitted child run, and the child's link records that a bridge `run` call reached it, `reachedBy: "bridge_run"` ([Spec-014 §Interfaces And Contracts](./014-multi-agent-orchestration.md#interfaces-and-contracts)). Every [Spec-014 §Scheduler Limits](./014-multi-agent-orchestration.md#scheduler-limits) admission rule and every refusal code applies unchanged; this spec adds no run kind, no `reachedBy` value, and no scheduler rule.
- **No new approval category.** A bridge call is an ordinary tool call: it rides the existing `tool_execution` category through the existing approval pipeline, under the session's own permission level, so no `ApprovalCategory` value is added and the category enum of [Spec-010 §Required Behavior](./010-approvals-permissions-and-trust-boundaries.md#required-behavior) is unchanged. An invocation still lands as an ordinary `tool_activity` row.
- **No choice of machine.** A definition and a peer-invocation target live on the machine the session runs on. One machine executes a session, and where it runs is never a choice, so no request names a machine and no refusal exists for naming one.
- **No definition sync.** Definitions live in files on the machine that holds them. A linked device reads and edits them there through Remote Control, like every other screen, and no copy is kept on the control plane or on another machine.
- **No gallery of this product's own, and no discovery outside the providers' own catalogs.** Agents made elsewhere arrive only as plugins installed from each provider's own marketplaces in `Browse plugins` (§Browse plugins), and a plugin's agents are listed read-only beside the rest. Nothing else is fetched to fill the registry, and no catalog shared between people is listed, because the product has one person.
- **Nothing about driving a session from a linked device.** Remote Control ([Spec-027](./027-remote-control.md)) carries a linked device to this destination as it carries every other screen; this spec adds nothing to that path.
- **No new provider capability.** Effort, paying accounts, and tools are the axes the corpus already carries; a definition composes them and invents none.
- **No place of work.** A definition says who, never **where** or how carefully: it carries no repository, no checkout and no level. Whether a run works in a new worktree or in the checkout the project already has belongs to the session or the workflow run that uses the agent, which already decides it, so the record gains no column for either, no editing surface offers one, and an export carries nothing machine-local on this axis.
- **No skill attachment.** A definition does not list skills. Every skill available on the provider an agent runs on reaches it in the pack the daemon builds at session launch, so there is nothing to attach one at a time here; skills, their availability, and their files are [Spec-029](./029-skills.md)'s.
- **No workflow replacement.** A workflow remains the surface for multi-step authored orchestration (`Spec-015`). An agent definition configures _one_ agent; it declares no sequence, no gate, and no dependency edge.
- **No report-back channel beside the verbs' own answers.** The bridge's verbs answer on their own results — the agent's handle when it starts, its status and its output when a wait returns — and no verb mints a side channel by which an agent pushes state into the one that reached it. A caller that needs a structured answer asks for it on `run`, and `wait` returns that object as the output (§Peer invocation).

## Required Behavior

### The definition registry

- An **agent definition** is a node-local durable record in two parts. Its **core** is provider-agnostic and carries: a human `name`, a `description` that may be empty — the role line read under the name — an optional `icon`, an optional `accentHue`, `instructions` (the system-prompt text the agent runs under), an optional `goal`, an optional tool allowlist, the agent's **hooks**, an optional **memory scope**, an optional turn cap, and creation/update timestamps. Its **bindings** carry the provider axes: one default binding and any number of overrides, each binding naming a driver key, a model id, an optional provider-account reference, and an optional effort level.
- **The bindings are a plural axis, and the default is one of them rather than a fallback.** An override names a driver the definition has not already bound: an override's driver is unique within the definition and no override may repeat the default's driver, so at most one binding exists per driver and which binding answers for a driver is never ambiguous. An override is a whole binding in its own right and never "the default with some fields replaced" — no field of an override is inherited from the default. This is what lets one definition run on either provider without being copied into a second definition, and it is why the provider axes (driver, model, paying account, effort) are not top-level fields of the record.
- **`icon` and `accentHue` are two fields, not one**, and either may be absent: the icon is a glyph key from the console's own icon set, and the accent is one step of the console's twelve-step hue wheel. A definition that sets no icon is drawn with the generic agent glyph — the same picture the destination's own rail entry uses — and the accent is what tints that agent wherever it is shown, so one agent keeps one color across every surface that draws it.
- **A definition MAY carry a turn cap**: the number of turns the agent may take before it is stopped, with no value meaning no cap. The number means the same thing on both providers although only one enforces it — on the Claude leg it is that provider's own per-agent limit, `maxTurns` in the agent file, or `--max-turns`, and on the Codex leg, which publishes none, the daemon counts the agent's model rounds on the wire, and at the cap its pre-tool hook denies every further call with `You have reached your turn limit. Report what you completed and what remains.`, so the agent writes its report and its turn ends. The record carries it as `turnCap`. The daemon invents no cap of its own, and this is not a budget: the budgets and their ceilings are [Spec-014 §Budget Policies](./014-multi-agent-orchestration.md#budget-policies)'s.
- **Four origins, one registry.** A definition's file lives in one of four places, and all four are listed as one registry, each entry marked with which place it came from and whether it is global to the node or belongs to one project: this product's own folder (`~/.ai-sidekicks/agents/<name>.md`, and `<project>/.ai-sidekicks/agents/` for a project's own, committed with the repository), the Claude leg's own folder (`~/.claude/agents`, `<project>/.claude/agents`), the Codex leg's own folder (`~/.codex/agents`, `<project>/.codex/agents`), and a plugin's own folder, for an agent a plugin installed. A plugin's agent is read from the daemon's own plugin home for that provider (§Browse plugins), never from an account home, which holds no plugins; it is marked `plugin · <plugin name>` and is **read-only**, because its plugin decides it. The daemon watches all of them. A provider's own file is **edited in place, deleted when the person deletes that agent, and never written by this product otherwise**, and never gains a key its provider does not read; anything authored here is written only under this product's own folder, and a definition reaches a provider through the pack the daemon builds at session launch, in that provider's own format, so nothing is ever copied into another provider's folder. A project's own definition file, committed with the repository, never carries an account id: this machine's account choice for it is kept in the record beside the file, as the icon and accent are for a provider's own file. Items authored here are therefore visible inside this product's sessions only, and that is deliberate: making a bare provider terminal see them is not this product's job.
- **The record is the union of both providers' fields, and what a file cannot hold lives beside it.** A field a provider's file has no place for — the icon, the accent, and on a Codex file the hooks and the memory scope, which a Codex role file never reads — is stored in this node's own record attached to that file, and a reader is shown the merge: editing a provider-supported field writes the file, editing one of the others writes only the record. The attachment follows the file's name and location, so a file renamed or deleted outside this product leaves those fields **orphaned**, kept with the last path the file was known at, until they are reattached to a file — picked with the platform's file chooser, and accepted only while the record is orphaned — or discarded: never silently rewritten, never silently dropped. Where a provider cannot enforce an agent's tool allowlist itself — on the leg that has no allowlist, and on the Codex leg, whose role file discards its tool list — the daemon enforces it at spawn, so one rule covers definitions authored here and definitions authored by a provider alike.
- **The daemon reads every file itself** rather than trusting what a provider chose to load, because Claude Code drops a broken agent file silently. Each entry carries two facts beside its origin, each its own field and neither excluding the other: **switched off in its provider**, while the provider's own configuration turns the agent off, and **failed to load**, while its file does not load, with the reason. Neither fact hides the agent.
- Definition **identity is a daemon-minted opaque immutable `definitionId`**. `name` is a mutable human label and MUST NOT be used as an identity key on any wire request, stored reference, or audit row. Renaming a definition MUST NOT change its `definitionId`, and MUST NOT alter any agent already running from it.
- `name` MUST be unique within one origin and one scope under full Unicode case folding. Two definitions in one place differing only in letter case are the same handle to a human reading a picker, and admitting both would make the name a target the person cannot disambiguate. Across origins the same name is allowed: a provider's own `reviewer` sits beside this product's own `reviewer`, because a session names the packed one `sidekicks:reviewer`.
- The tool allowlist has three distinguishable states and the daemon MUST NOT collapse them: **absent** means the driver's default tool set, an **empty list** means no tools at all, and a **populated list** means exactly those tools. An absent allowlist and an empty one are opposite instructions.
- **The allowlist covers the provider's own built-in tools too**, beside the configured tool servers and the daemon's own callback tools, and the states keep exactly the meanings above over that wider catalog. The daemon realizes the list at spawn, where the allowlist is already enforced. On the Claude leg it becomes that provider's tool flags — `--tools`, or bare `--disallowedTools` names — and a pack entry's own `tools` list, where a **bare tool name** is what removes a tool's schema from the request — a scoped rule such as `Bash(git *)`, and any allow-form, leave the schema in place. On the Codex leg it becomes switches set per conversation — `features.shell_tool = false` and `web_search = "disabled"` — and a model running in its code-only mode sends no tool list at all, so on that model there is nothing for an allowlist to remove. Codex has no per-conversation switch for its patch tool, so a Codex list that leaves `apply_patch` out, _no tools_ included, is enforced at the call: the daemon's pre-tool hook refuses that tool, whether it is called directly or from a code cell, and any shell command naming it as a command word, with a reason naming the agent's tool list, and the conversation's developer instructions name the tools the agent lacks. The tool's schema stays in the request, a few hundred characters, so leaving it out would save almost nothing. A name the driver cannot realize is refused in place, naming the driver. A tool that has left the catalog is the one name resolution refuses as unrealizable, per §Fallback Behavior. There is deliberately **no provider-wide always-off list** anywhere in this corpus: a standing per-provider disabled set would be a second precedence layer over the allowlist, and a second answer to which tools a run gets.
- A definition carries **no permission level**. A level decides only what asks first, and it belongs to the session or the workflow run: every agent working in a session, the lead and every helper at any depth, on either provider and across the agent bridge, runs at that session's level, and every step of a workflow run runs at the run's level. What an agent can do at all is its tool allowlist: a reviewer with only reading tools cannot change a file at any level.
- **Hooks are authored here, on both providers.** A definition's hooks are handlers that run only while that agent works, on whichever provider runs it. Each names an event, a tool-name pattern for a tool event, and a handler — a command, an address, a tool, a prompt, or an agent — with that handler's value. The events offered are the ones the providers the definition binds fire: eleven fire on both, Claude Code alone fires two more and Codex alone one more, each listed with its on-screen words under §The editor. Every handler kind runs on both providers: native where the provider runs that kind, and built by the daemon from the provider's own pieces where it does not, as the next two items say. On Claude Code a finish hook on a helper becomes that provider's helper-finish event, as Claude Code does itself. Where hooks are kept follows the union rule: this product's own file holds them in its `hooks` key, a Claude Code agent's own file holds them in that file's `hooks` key, edited in place, and a Codex agent's hooks live in the record beside its file. Each is kept for as long as the agent exists, and nothing about an agent's hooks is written into a provider's own global configuration or the person's settings. The console's own pause hooks are the daemon's own, registered per session, and are never listed among an agent's hooks or written into an agent or a file.
- **How each provider runs an agent's hooks.** A Claude Code helper's hooks ride its entry in the agents map the daemon hands the process at start, and Claude Code runs them only while that helper works; hooks from that map run without the workspace-trust gate, and a project's agents come only from a project the person attached, which is trusted for both providers. A Claude Code agent that leads its own process — a bridged agent, a try-it run, a workflow's run-an-agent step — carries them in the settings the daemon passes when it starts the process, beside the console's own pause hooks. A Codex agent that is its own conversation carries them in that conversation's start configuration together with each hook's trust record, so they run trusted with nothing written to the person's configuration; the provider-wide trust bypass is never set, because it would also trust project hooks the person has not trusted, and the build checks each hook against Codex's own hook list, which must report it trusted. A Codex helper its lead starts cannot carry hooks in its role file, so the lead's configuration carries one gate row per event that any of the session's Codex helpers has a hook on: the gate is the app's own `sidekicks hook-gate` command, called by its absolute path because Codex runs it through the shell with no promise about the command path; it reads which helper fired, ends at once when that helper has no hook for the event and tool, and otherwise runs that helper's matching handlers in order, each as its kind runs on Codex — a tool handler called through the daemon's own MCP client, since the gate is a command hook — passing one hook's answer through unchanged and, with several, returning the first answer that blocks, else the last. The session file the gate reads holds only hook definitions, no secrets, lives in the daemon's folder for that session, and is deleted when the session ends. Each firing starts one gate process whatever the number of helpers, adds at most 100 ms before the handlers it runs, and holds no process between firings.
- **Each handler kind, per provider.** On Claude Code every kind is native: `command`, `http`, `mcp_tool`, `prompt` and `agent`. On Codex a command runs natively, and a tool runs natively as Codex's own tool hook (`mcp_tool`), except at session end, where Codex skips a tool hook, so there the daemon's command hook calls the tool through the daemon's own MCP client. An address is sent by the daemon's command hook. A prompt and an agent, which Codex declares and skips at load, are answered by the daemon's command hook, which asks Codex's own app server for the one-off answer or runs a short-lived Codex agent, and returns allow or block; the added time and cost of each firing are measured by the building unit before it ships. When Codex ships one of these kinds itself, the daemon learns it at start from what Codex reports, never from a version pin, and uses Codex's own.
- **One memory per agent, on both providers and every account.** An agent's memory is a folder of its own notes — a `MEMORY.md` index and the notes beside it — in one of four scopes: none; **all projects**, at `~/.ai-sidekicks/agent-memory/<name>/`, one folder of the daemon's own; **this project · in the repo**, at `<project>/.claude/agent-memory/<name>/`; or **this project · not in the repo**, at `<working folder>/.claude/agent-memory-local/<name>/`. These are Claude Code's own `user`, `project` and `local` scopes, stored as the memory scope, and `<name>` has every character outside letters, digits, `-` and `_` turned into `-`. On Claude Code, for a helper, the agent's memory key hands the folder to Claude Code's own memory, which reads the first 200 lines or 25 KB of `MEMORY.md` at start and lets the agent read and write the folder. Everywhere else — every Codex run, and a Claude Code agent that leads its own process — the daemon does the same by hand: it puts the same head of `MEMORY.md` and short memory instructions naming the folder into the agent's instructions, and makes the folder writable for the run; on Codex the conversation's permission profile gains one write entry for the memory folder of each agent in the session that has one, the lead's profile carrying its helpers' folders, and a helper's role file is rewritten when `MEMORY.md` changes so the next helper starts with the new head. A resumed Claude Code lead keeps the head it started with until its next compaction, because Claude Code's own `--system-prompt-snapshot` stays at its default, as a running Codex conversation keeps its `thread/start` instructions; the agent reads the folder itself for anything newer. Codex's own memory is not used: it is one global store, and it skips spawned agents.
- **The all-projects folder is one folder on every account.** Every Claude Code configuration home the daemon creates holds `agent-memory` as a link to `~/.ai-sidekicks/agent-memory/`, made when the home is created and checked before each start, so Claude Code's own user memory path is the one folder on every account. Claude Code asks permission for the agent's own reads and writes through that link, because it checks the link's target as well; the daemon answers those asks itself, allow and no card, when the file is a `.md` whose path lies in the agent-memory folder, at every level that asks, and at Sandboxed, where no ask is sent, the settings the daemon passes carry the same allowance as allow rules for both spellings of the folder. Each such answer costs under 10 ms of the daemon's time and none becomes an approval rule. Claude Code's own remote-memory folder setting (`CLAUDE_CODE_REMOTE_MEMORY_DIR`) is not used, because it would also move every session's own memory into that folder and join the session memories each account home keeps apart. Agent memory is shared across accounts on purpose, because it belongs to the agent, not the account; two sessions writing one note at once cannot silently lose an edit, because Claude Code's edit refuses a file that changed since it was read and Codex's patch fails when its context lines have moved.
- **An agent's memory is the one exception to asking.** At every permission level, Read-only included, an agent reads and writes its own memory folder without asking, on both providers. Memory follows Claude Code's own switch: with its automatic memory turned off (`autoMemoryEnabled` false, or `CLAUDE_CODE_DISABLE_AUTO_MEMORY` set), no agent memory is read or written on either provider. Notes stay in the folder of the chosen scope until the person deletes them; deleting an agent leaves its memory folder where it is, and the delete confirmation names that folder. The person's own terminal agent memory stays theirs, and no session loads it; the import from the person's own Claude Code home copies those agent folders into the all-projects folder once, never overwriting a file that exists, and counts them among the memories it imported. Where a session runs in a worktree of its own, notes kept out of the repo stay with that worktree on both providers, as Claude Code keeps them in the working folder: nothing copies them into the main checkout or into a new worktree, a discarded worktree is kept whole so putting it back brings its notes too, and they go only when the person deletes the kept copy.
- **The pack is how a definition reaches a provider.** On Claude Code the daemon hands every agent of the session pack to the process in the agents map of its `initialize` request, each under its namespaced name (`sidekicks:reviewer`, `sidekicks:codex-reviewer`) with every field of its record — description, instructions, tools and disallowed tools, model, effort, tool servers, hooks, turn cap and memory — and no `permissionMode`, so the agent runs at the session's level and is in the process's agent list from its first answer. The plugin folder the pack also passes carries skills only, because Claude Code ignores hooks and tool servers in a plugin's agent file while an agent in the agents map keeps both. On Codex the pack is role files passed through its configuration, with this product's skills as the plugin named `sidekicks`, and what a role file cannot carry — hooks, tool servers, sandbox and memory — rides the conversation's `thread/start` configuration. The person's own global and project files load as they always do, and the pack is one more source: on Claude Code its agents, in the agents map, rank above the person's files and its skills, in the plugin folder, below them; on Codex the pack ranks above them; and no override occurs, because the pack's names differ.
- Definitions live on the machine that holds their files. A linked device lists and edits them through Remote Control's method proxy, calling the same `agent.*` operations the machine's own window calls, and the daemon keeps no copy of a definition on the control plane or on another machine.

### The library

The library is the destination's list over the registry, and the one place a definition is created, duplicated, exported, imported, deleted, and found.

- **The header** carries the destination's title, the definition count, a search field, `Browse plugins`, `New sidekick`, and `Import`. `Export` is absent while the list is empty, loading, or refused, because there is nothing to select. The library answers at `#/sidekicks`, one definition at `#/sidekicks/<definitionId>`, a new one at `#/sidekicks/new`, and `Browse plugins` at `#/sidekicks/plugins`.
- **A card** carries the icon on a swatch tinted with the accent; the name; the role line clamped to one line; a chip row of provider and model, and effort read as one word of the console's single effort ladder; the tool-allowlist summary; the **origin mark**, naming which place the definition's file lives in and whether it is global or belongs to this project, a plugin's agent reading `plugin · <plugin name>`; and a meta line holding `Also on Codex` where a second provider is bound, `used by N workflows`, when it was last used, and the provider facts — `Off in Claude Code` or `Off in Codex` while the provider switches the agent off, and `Didn't load · <reason>` while its file fails to load, each drawn only while it holds and both drawn when both hold. Every card shares one shape: the chip row and the meta row keep their slots whether or not they have content, so a card always aligns with its neighbors. The whole card opens the editor, and `Duplicate`, `Export` and `Delete` sit on it; a plugin's agent carries no `Delete`, because its plugin is removed in `Browse plugins`.
- **Four read states are kept apart** — not loaded, refused, served empty, and rows. An empty registry shows one sentence, `No sidekicks yet — a sidekick is a set of instructions and a model binding you tune once and reuse in every session and workflow.`, and `New sidekick`, never a spinner and never a list. A read still in flight is its own state, distinct from empty: the loading note `Reading the sidekick registry…` with its skeletons, no cards, and the count reading `—`, the note appearing only after the 800 ms a session's first read waits before it shows a loading line. A refused read renders the refusal itself with `Try again` as one faint clickable word at the right end of its line — no box and no icon — and no rows.
- **An orphaned agent is set apart, never dropped.** An agent whose provider file was renamed or deleted outside this product leaves the grid for a group of its own after it, `File gone`, never among the live cards. Its card keeps what the record still holds — the icon on its accent swatch and the name — reads the last path its file was known at, and carries two acts: `Reattach…`, which opens the platform's file chooser, and `Discard`, which drops the record after asking in place.
- **Ordering** is by name under `Intl.Collator`, ties broken by the definition id, and it does not change while a delete is in flight. Exactly one alternative exists — **last used**, most recent first, never-used last, ties broken by the same name collation — switched from the caption itself, where `ordered by name` flips to `ordered by last used` and back, rather than from a menu, and remembered per user. The caption carries only that control, `N of M match` while a search narrows the list, and `Select all` while selecting.
- **Search** matches name, role, driver, model, and tool names; case-folded; substring; never fuzzy. A search matching nothing says so and leaves the search field focused.
- **Selecting is for export, and only after being asked for.** `Export` in the header starts it: a checkbox appears on every card, `Select all` appears beside the caption, and a bar at the foot reads `0 selected · Export · Cancel`, with its own `Export` disabled until something is ticked. A click ticks one and a shift-click ticks the range from the last tick; once every visible card is ticked the same control reads `Select none` and clears them; canceling or `Escape` leaves selecting and clears it. Outside selecting no checkbox and no `Select all` is anywhere, and the library looks exactly as it always does. Export from the bar writes the ticked definitions, one Markdown file each, into the folder the person picks; Export on a card writes that one definition's file. **Delete stays on the card, one at a time**, because its confirmation names that definition's running sessions and its workflow count, and a bulk delete would have to name them per definition; the selection bar carries no delete.
- **`New sidekick`** opens the editor empty, with a driver preselected only where the node has exactly one provider registered — otherwise nothing is guessed.
- **Duplicating** copies every field, bindings included, names the copy after the original (`<name> copy`, then `<name> copy 2`), and opens the editor on it.
- **Deleting is confirmed, never refused by the client.** The confirmation names the consequence: sessions already running the agent keep the configuration they were given, and the workflows that use it, counted once per workflow, will refuse at their next run; where the workflow store cannot be read the workflow clause is dropped rather than guessed. **An agent that came from a provider's own file is deleted with that file**: the daemon checks that the path is the provider's own agent file it read, deletes it, and drops the record beside it in the same act, and the confirmation names the path and says the provider loses the agent too, so its plain command line stops finding it, and on a project file that the change shows in the repository — Claude Code drops the agent from its next turn and Codex at its next helper start. The delete never only hides the agent in this product's record, because the provider would still load the file into every session. On an agent that keeps a memory the confirmation adds `Its memory stays in <folder>.`, and the folder stays. A delete the daemon refuses renders that refusal on the card and leaves the row in place.
- **Export and import.** An export writes one Markdown file per definition into a folder the person picks: the core, the icon and accent, the hooks and the memory scope, and every binding with the account left out. The notes in an agent's memory folder are never read into a file, so an imported agent starts with whatever the folder of its scope already holds on the importing machine. Both are daemon operations: the folder is picked with the platform's own dialog, and the client never holds its path. An import reads the definition files in the folder the person picks and **creates** definitions in the global scope, never overwriting one, suffixing a colliding name exactly as duplicating does, because the files carry nothing tied to one machine and a project is. An import takes every file in the folder that is an agent definition; any other file in the folder is skipped and listed once with its reason (`README.md · not an agent definition`), as Claude Code treats its own agents folder, and no import is refused whole for a file that is not a definition. An export whose file cannot be written is refused with the operating system's cause.
- **Keys.** The cards are one roving-index list: the arrows move a cursor, `Enter` opens, the delete key starts the two-step delete on the card, and `/` focuses search.

### The editor

The editor is one column and no wizard, over one definition, in this order: name, global or project (on a new agent only), role, icon and accent, instructions, goal, `Max turns`, tool allowlist, hooks, memory, skills, provider bindings, and a try-it panel in the side slot.

- **Instructions** is a field that grows with its text, with an **estimate** of its size under it, rendered with a visible `≈` and computed by a character heuristic — never by a tokenizer dependency, whose precision the number does not have.
- **`Max turns`** is one number field, empty meaning no cap, with one line under it saying that the agent stops at that many turns, that Claude Code enforces the cap itself, and that on Codex the daemon counts the turns on the wire and then refuses the agent's further tool calls so it reports what it finished.
- **Global or project** is drawn on a new agent only. It opens on `Global`, writing under `~/.ai-sidekicks/agents/`, with `This project · <name>` one press away, writing under that project's `.ai-sidekicks/agents/`, and it is held with its reason, `No project is attached`, while none is. The project it names is the one the person came from — the session's project when the destination was opened from a session, otherwise the project of the most recently focused session. An agent that already has a file keeps it where it is, so the control is not drawn on one.
- **Hooks** is a list under the tool allowlist, on every origin and both providers. Each row reads `<When> · <Matching> · <Run>`, and `Add a hook` opens one row in place with three fields: `When`, the event in plain words in the chooser and on the row alike, never the provider's event name, which stays on the wire and in the files; `Matching`, a tool-name pattern, drawn only for a tool event; and `Run` — `A command`, `An address`, `A tool`, `A prompt` or `A sidekick` — then that handler's value. `When` lists the events of the providers the agent's bindings name. On an agent bound to both providers, an event only one provider fires carries `Runs on Claude Code only` or `Runs on Codex only`; no `Run` choice carries such a line, because every handler kind runs on both providers. A change marks the editor dirty like any other field. The console's own pause hooks are never listed here. The words for each event, and the provider's event each stands for:

  | On screen                                   | Provider event      | Fired by         |
  | ------------------------------------------- | ------------------- | ---------------- |
  | `Before a tool runs`                        | `PreToolUse`        | both             |
  | `When a tool asks for permission`           | `PermissionRequest` | both             |
  | `After a tool runs`                         | `PostToolUse`       | both             |
  | `Before the context is compacted`           | `PreCompact`        | both             |
  | `After the context is compacted`            | `PostCompact`       | both             |
  | `When a session starts`                     | `SessionStart`      | both             |
  | `When a session ends`                       | `SessionEnd`        | both             |
  | `When a prompt is sent`                     | `UserPromptSubmit`  | both             |
  | `When a helper starts`                      | `SubagentStart`     | both             |
  | `When a helper finishes`                    | `SubagentStop`      | both             |
  | `When the sidekick finishes`                | `Stop`              | both             |
  | `When a notification is sent`               | `Notification`      | Claude Code only |
  | `When a tool server's question is answered` | `ElicitationResult` | Claude Code only |
  | `When the sidekick is interrupted`          | `interrupt`         | Codex only       |

- **Memory** is one choice of four — `None`, `All projects`, `This project · in the repo`, `This project · not in the repo` — with one line under it: `Notes this sidekick keeps for itself. It reads the first 200 lines when it starts.`
- **A plugin's agent** opens in the same editor, read-only: every field is drawn as its value with no control, the provider bindings and hooks included, under one line, `Installed by a plugin. Update or remove it in Browse plugins.`, where `Browse plugins` opens `#/sidekicks/plugins`. The header carries `All sidekicks` and the origin mark and no save, cancel or delete, and a try-it runs it like any saved agent.
- **The tool allowlist is three visibly different controls, never one empty list**: the driver's defaults, with nothing chosen; no tools, an explicit empty set; and exactly these, a checked set over the catalog. The catalog holds the configured tool servers, the daemon's own callback tools, and each driver's built-in tools in a group under that driver's name, below the servers — on Claude Code `Read`, `Edit`, `Write`, `Bash`, `Glob`, `Grep`, `WebFetch`, `WebSearch` and `Agent`, on Codex `shell`, `apply_patch` and `web_search`. Each row reads the **words for the tool** — `Web search`, `Run a sidekick`, `Apply a patch` — while the driver's own spelling is what is stored and what the daemon realizes at spawn, and the two facts about what an allowlist actually removes on each provider are stated with the control, because both are true and neither is obvious. On Codex a list that leaves out `Apply a patch`, _no tools_ included, saves and runs like any other, and the daemon refuses the tool when the agent calls it. A tool that has left the catalog keeps its unknown-but-still-stored rendering rather than being dropped.
- **Tool servers listed on an agent reach that agent alone, on both legs.** A Claude Code helper and an agent the bridge runs receive exactly the servers listed for them. A Codex helper inherits its lead's servers, so a server listed on it is added to the lead's session and granted to that helper alone by the daemon-fronted server at call time, which sees the calling thread on every call; the field states that.
- **Effort** reads as the console's one ladder everywhere — Low, Medium, High, Extra high, Max, Ultra — mapped one-to-one from the provider's own names (`low`, `medium`, `high`, `xhigh`, `max`, `ultra`), which are what is stored, and offering exactly the rungs the resolved model publishes. A model publishing no levels renders the effort row as the words `Not published by this model`, never an empty or disabled control. An effort stored for a model that no longer publishes it is shown with a warning and is never silently cleared.
- **Skills** takes no value. It states the rule and links out: every skill available on the provider an agent runs on is handed to it in the pack the daemon builds at launch, so nothing is attached here one at a time, and one link beside the field, `Open Skills`, opens the skills destination at `#/skills`, where availability, folders, and the files themselves are edited.
- **Provider bindings** render the default binding as a dependent chain — driver, then model, then paying account, then effort, each narrowing the next — followed by the overrides, each the same chain, each on a driver the definition has not already bound. The chain's driver axis reads `Provider` on screen, as every screen says it. The model row offers every model and speed the provider lists, the moment it lists it, priced or not. The control that adds an override is absent once every registered driver is bound, and removing an override never touches the default binding.
- On a definition whose file belongs to a provider, a field that provider does not understand — the icon, the accent — is saved in this node's own record beside the file and never written into it, and the editor says so under the field.
- A **goal** is a condition the agent is given to work toward, a command sent to that agent, never something a session is. Left empty, the agent starts with none: a session has no goal of its own for it to take.
- **The header** carries `All sidekicks` back to the library, the same origin mark the card carries, a count of unsaved changes while there are any, and the definition's name as the title. Delete is disabled until the definition has been saved once. Leaving the editor with unsaved changes asks first, and the dialog names the changed fields by the editor's own labels, `Changed: Name, Role`.
- **Leaving.** Saving is the only exit that keeps changes: canceling, and navigating away from the destination, ask first and name what would be lost. A save that would produce an identifier another agent already carries warns before it saves. Save and cancel both return to the library with focus restored to the card. Delete asks in place, with the same sentence the card uses. `Cmd/Ctrl+S` saves and `Escape` cancels through the unsaved-changes question.
- **A save reaches a running session with its conversation intact.** The daemon's watch sees the change, from any origin, and the provider learns of it the same way. On Claude Code, agents in the process's agents map are fixed for the life of the process, so the daemon waits for the session's next idle moment — no turn running and no background task of the process running — then stops the process and starts it again on `--resume <session id>` with the new `initialize` agents map; the conversation and its history carry over, several saves before that moment make one restart, and the restart costs about 1.6 s to the process's first answer and then a cold first reply. On Codex the daemon forks the lead's conversation with `thread/fork` on the running server with its history intact, the console rebinding the session to the new conversation so the person sees one continuous conversation. It never reopens the conversation with `thread/resume` for this, which brings back the history but not the new agent, never restarts the service, which would end every other conversation on it, and never archives the old conversation with `thread/archive`, which archives it and its whole subtree where the person can see them. A reopened conversation is cold, its first reply taking 1.5 to 4 s to start, so the lead's row shows it thinking at once. Nothing lingers: after the fork the daemon unsubscribes the old conversation, and Codex unloads it after the service's unload delay, which the daemon sets to 5 s when it starts the service, ending that conversation's stdio tool-server processes, about 54 MB each; between that unsubscribe and Codex's `thread/closed`, Codex refuses a reopen of the old conversation as closing, and the daemon retries after that notice and never shows the refusal; the daemon rewrites the hook gate's session file and re-passes the lead's hook gate rows and their trust records in the fork's configuration, so a helper's hooks keep firing. An idle or waiting lead is reloaded the moment the file is saved; a lead mid-turn waits until that turn finishes. On both providers one flow row reads `sidekicks reloaded`, stored as a session notice of kind `conversation_reloaded`. `/reload` in the composer, `session.definitionsReload`, presses the same refresh by hand, for an edit made outside a watched folder or when the person wants to be sure: it refreshes both providers' skills and plugins — on Claude Code through its own skill and plugin reloads, which on the headless path do not apply a plugin's tool-server change, so that change lands at the session's next start and the flow row says so while one is pending — and only when an agent definition changed restarts the Claude Code lead at its next idle moment and forks the Codex lead's conversation. A running agent keeps the values it was resolved with ([Plan-024 §I-024-2 — A run keeps the configuration it was resolved for, never a live view](../plans/024-agent-definitions-and-peer-invocation.md#i-024-2--a-run-keeps-the-configuration-it-was-resolved-for-never-a-live-view)), except the hooks of a bridged agent, a try-it run or a workflow's run-an-agent step, which ride its process's settings: an edit to them reaches that process by a resume at its next idle moment.
- **A rename keeps the definition id.** Every surface that draws the registry picks up the new label on its next list read; nothing re-points and nothing breaks.
- **Try it** runs the definition itself, given a message — never a simulation of how something else would call it. It is disabled until the definition has been saved once, and says so. It composes two ordinary operations and mints no verb of its own: start a **scratch session with no repository attached, whose lead is the definition under test**, then send one turn; the reply streams in the panel. Exactly **one scratch session per definition** is kept and reused, so repeated tries do not multiply sessions, and the console never silently deletes a session it created — the scratch session is named and left in the session list, where it can be found and closed. The provider, model, effort, and account the daemon resolved come back on that session's start, and that echo is where every surface that runs a definition reads the resolved binding from.
- **A live try-it run carries the same two controls a dispatched agent's own view carries** — `Pause · Interrupt` — beside its `Running…` button. Pause holds the run after the step under way and is pressed again to continue. Interrupt ends the turn, the panel reads `Interrupted · waiting`, the button reads `Try it` again, and the scratch session is kept so the next press reuses it. `Escape` interrupts a live run first, and only the next `Escape` starts the leave-the-editor path. The daemon picks the mechanism behind each word per provider, exactly as it does for a dispatched agent ([Spec-014 §Intervention Propagation](./014-multi-agent-orchestration.md#intervention-propagation)).

### Browse plugins

`Browse plugins` is one view at `#/sidekicks/plugins`, opened by `Browse plugins` in the library's header and in the Skills destination's header ([Spec-029](./029-skills.md)). It is how agents and skills made by others reach this product's sessions: through each provider's own plugin verbs, never a catalog of this product's own.

- **The catalogs.** The view lists each provider's catalog under that provider's heading, one row per plugin: its display name, its one-line description, its marketplace, what it carries (`6 sidekicks · 2 skills · 1 tool server`), and `Installed` or `Install` at the row's end. A search field, `Search plugins`, filters the list as the person types; the daemon filters, because neither provider's list verb takes a query. Each provider's official marketplace is there without adding it, and `Add a marketplace` takes a repository address or a folder through the provider's own verb. Under Codex the view lists what Codex's own `/plugins` lists for the account, with `Workspace` and `Shared with me` as their own sections.
- **One plugin.** Opening a row shows what the plugin carries, each item by name and description — a hook by its event's plain words — and its source: the marketplace and, for a plugin fetched from elsewhere, the repository and its commit.
- **Install and remove ask in place.** `Install` shows one line before it acts, `This plugin can run commands on this machine. Install only plugins you trust.`, with `Install` and `Cancel`; `Remove` confirms in place the same way.
- **Where plugins live.** A plugin is installed into a plugin home the daemon owns, one per provider, never into an account home and never into the person's own home: `~/.ai-sidekicks/plugins/claude/`, which every Claude Code plugin command runs with as its configuration home, and `~/.ai-sidekicks/plugins/codex/`, the home of a Codex service the daemon starts while the view is open and stops 60 s after it closes. Plugins sit there in the provider's own layout until removed, and the catalog is read when the view opens and held only while it is open.
- **What a plugin brings.** An installed plugin reaches every session of its provider, and its agents and skills are listed in this library and on the Skills destination marked `plugin · <plugin name>`, read-only (§The definition registry). On Claude Code the daemon passes each installed plugin's folder when it starts the process, and Claude Code loads it as it does in its own terminal, with the same limits: a plugin's agents carry no hooks, tool servers or permission mode. The plugin's tool servers stay out of the session under its strict tool-server configuration; the daemon reads them from the plugin, lists them on the MCP servers page as `From plugin <name>`, and sends a session only the ones switched on for it. On Codex the daemon hands the plugin's skills, tool servers and hooks to the conversation as pack items — tool servers fronted by the daemon's own route, hooks with their trust records — and Codex's own plugin loading is off in sessions: every Codex service the daemon starts on an account home runs with plugins disabled, which stops the curated catalog sync each home would otherwise make (about 88 MB) and leaves the home's own skills, hooks, tool servers and apps as they are; only the plugin home's own service runs with plugins on. An install or a removal reaches a live session as a saved agent does: on Claude Code by the resume at its next idle moment, on Codex by the fork (§The editor).
- **The person's own plugins.** A plugin the person installed in their own terminal is listed as `Installed in the terminal`, read without writing from each provider's own record of installed plugins, and `Use in Sidekicks` installs the same plugin, from the same marketplace, into the daemon's plugin home. The person's own home is never loaded into a session.
- **A Codex plugin's apps.** An app is a tool server the provider hosts, not a program on this machine, so a session reaches it through its account's ChatGPT sign-in, the daemon-handed one included, with plugin loading off. Linking an app to its service is kept on the account, so it is done once per account and holds in every session on it. A plugin's page lists its apps, each as an `App` row with one line per Codex account: the account's name, then `Connected` when that account's own service reads the app as accessible, otherwise `Connect <App>`, which opens the app's page on chatgpt.com in the browser, where the person links it while signed in as that account. The lines are read again when the window regains focus, and with one Codex account the row carries that account's state alone, with no name. Every account is shown because a session moves between accounts, and after a move to an account that has not linked an app the session loses that app's tools from its next request. An agent whose tool list leaves apps out starts its conversation with apps off by default and on for each app the list names. An API-key account carries no apps, and its rows read `Apps need a ChatGPT sign-in.`
- **Cost.** One catalog read per opening of the view and no background refresh. No process runs while the view is closed, apart from the Codex plugin home's service, which stops 60 s after it closes. Disk: the two catalogs, about 100 MB, in the daemon's plugin homes only, plus the installed plugins.

### Rules the library and the editor both obey

- **A save, an export, and an import each confirm with one short note that fades**, and nothing else on these surfaces reports success. The import's note reads `Imported <n> definitions` (`1 definition` for one), with one line under it per skipped file.
- **No wire identifier reaches either surface.** A refusal is rendered as words — its code and then its reason, in sentence case, the code first and the reason after — followed by the daemon's own message in plain words; a status, an event kind, and an enumerated value are read the same way. A tool and a policy action are shown by the label registered for them while the driver's or the policy's own spelling is what is stored, a hook event reads its plain words (`Before a tool runs`, never the provider's event name), and an unlabeled code falls back to its own words. Only what a person or an agent wrote, or would type, stays as written: model ids, file names and paths, commands, and prose.
- **The one user is never the named subject** of a row, a note, or a dialog on these surfaces, and no sentence of the product's own prose begins with `You`; the label is the thing and what happened to it, so the unsaved-changes question reads `Changed: Name, Role`. A definition's `instructions` are the person's own text and are outside that rule.
- **Every chrome size on these surfaces is derived from the current text size**, never a pixel constant — each width, floor, ceiling, padding, margin, gap, and grid track is as large as the content it must hold — so a larger text size grows the library, the cards, the editor, and its panels in one proportion, while the drawn marks (the hairlines, the corner radii, the icon boxes) stay as drawn. The same rule bounds the surfaces themselves: they fit the window they are given, full screen or any smaller size a desktop window reaches.

### Resolution when a run starts

- Any request that starts a run under an agent MAY name a definition instead of spelling out its axes — the session whose lead it is, the scratch session a try-it starts, a workflow step, and an agent named in a composer alike. The daemon resolves the definition and uses its fields as the configuration that run starts under.
- Request members that are explicitly present MUST override the definition's corresponding field, per field. The response MUST echo the **effective resolved configuration** — every field as actually applied — so a caller can never be left guessing which side of the merge won.
- **Resolution order is per field, and it has exactly three steps.** The resolved **driver** is the driver the request names, or the default binding's driver where the request names none. Each remaining provider axis then resolves in one order: an explicit value on the request, else the override for the resolved driver where the definition has one, else the default binding. Nothing falls through further, and no axis is ever composed from two bindings at once.
- **A model is never guessed.** A request naming a driver the definition neither defaults to nor overrides resolves **only if the request also supplies the model**; otherwise it refuses. Substituting a nearest model, or carrying another driver's model id across, would run something the definition never pinned and price it differently.
- **The caller sends only what it changed; the daemon performs resolution and answers with what it applied.** A request carries the definition reference plus exactly the axes explicitly overridden for this use. A client MAY show, per axis, where a value would come from — the caller's own override, this definition's binding, or the driver's default — as a preview beside the control that changes it; it MUST NOT compute the resolved configuration itself and MUST NOT present that preview as the applied result. The echo on the reply is the one place a resolved binding is read from, on every request that starts a run under a definition, and three requests carry it: the session start — the scratch session a try-it opens included, where the definition under test runs as that session's own lead — the workflow step's own record, and the composer's agent row. Each answers with the binding the daemon applied: the driver, the model, the effort, and the provider account.
- **An account entry that means the provider's current account follows the mark.** Wherever a caller chooses the paying account for one use of an agent, the `Default` entry at the top of that list means whichever account is the provider's current one when the run starts, and it follows the mark when the mark moves, exactly as a definition with no account reference does (§Default Behavior). Every other entry names an account by the identity its provider reports at sign-in.
- **Effort is validated at resolution, never at save.** An editing surface MAY warn that an effort stored on a binding is not among what the chosen model publishes, and MUST still save it: the vocabulary is per model and provider-published, so it moves under a stored value without the definition changing. The daemon validates at resolution against the resolved model's own published levels and refuses there (§Fallback Behavior); a model publishing none exposes no effort choice at all.
- **A run keeps the configuration it was given; only its label is read live.** The resolved values belong to the run from the moment it starts: editing or deleting the definition MUST NOT mutate, reconfigure, re-authorize, or revoke an agent already running from it, and MUST NOT affect any run in flight — which is exactly what the delete confirmation tells the person (§The library). A live reference would let an edit widen a running agent's tool allowlist or paying account without that widening ever passing the authorization that admitted the run. Presentation is the one exception and is resolved at the moment it is drawn: a running agent's displayed name, icon, and accent come from its definition, falling back to the agent's own name where the definition is gone, so a rename retitles a running agent mid-session while no edit changes what it may do.
- Resolution MUST fail closed. A definition naming a provider account that is no longer in this node's registry MUST refuse, and the refusal MUST name the definition and the unresolvable account; no agent is configured and no run starts. The test is **registry membership**, a definite fact the resolver owns — deliberately not whether the account is currently usable, which is authentication state that `Spec-025`'s live spawn probe is the authority on. Refusing here on a stored readiness reading would refuse a run the spawn gate would have admitted. The daemon MUST NOT silently fall back to the provider's default account — a pinned account that quietly becomes "whichever account is default now" is a spend and identity change the person did not ask for.
- The tool allowlist MUST be **enforced at spawn**, not merely recorded. If the resolved driver cannot realize the allowlist, resolution MUST refuse rather than spawning the agent unconstrained. An allowlist that is stored and not applied is worse than no allowlist, because it reports a restriction that does not hold.
- Deleting a definition MUST NOT be blocked by the agents already running from it, because a run no longer depends on the definition it resolved.

### Peer invocation

- **One bridge, six verbs.** The daemon serves a session exactly one tool server, named `sidekicks`, carrying six verbs: **run** a named agent, **message** one that is running, **wait** for its output, **stop** it, **close** it, and **list** what is running. The server is daemon-constructed and daemon-trusted, and it reaches both providers through the callback-tool registry [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior) defines, as tools of the daemon's shared Model Context Protocol (MCP) tool server `sidekicks` beside the session tools, through the one `url` entry each session carries — on the Claude leg in `--mcp-config`, on the Codex leg in the conversation's `mcp_servers` table at `thread/start`, never Codex's `dynamicTools` ([Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other)). The six verbs mirror what each provider already gives its own helpers, which is why one server serves both legs. This is the one place this product builds a bridge of its own, and it exists so that every saved agent reaches every lead: an agent bound to one provider is usable from a session running on the other.
- **The daemon runs the agent on its own provider.** It starts that provider's own unit of work — a thread on the Codex leg, a process on the Claude leg — applies the definition there, shows the agent under the one that reached it in the session's agent tree with a mark of which provider is running it, and returns its output like any helper's. Because the daemon owns that process it reads the agent's output word by word in both directions. Who owns the process decides how words arrive: every Codex agent and every agent the daemon runs itself streams word by word, and only a native Claude Code subagent, seen through its lead, lands whole messages ([Spec-014 §Provider-Native Subagents](./014-multi-agent-orchestration.md#provider-native-subagents)).
- **How each lead reaches the bridge.** On a Claude Code lead an agent bound to the other provider is an entry in the session pack whose **only** tools are the bridge's verbs; the lead's own tool list never holds those verbs, so the lead reaches the agent through that entry and nothing else, and that provider's own mention form (`@agent-sidekicks:<name>`) works on it as on any agent. That separation is load-bearing rather than tidy: with the verbs merely permitted on the lead itself, a lead told to run an agent called the verbs directly and started no helper at all, leaving nothing for the tree to draw. On a Codex lead the tool server itself is the interface — its own description lists every agent bound to the other provider by name and description, and the lead runs one by name. No stand-in role is planted on that leg: a Codex lead calls a tool it can see rather than spawning a role that would call it, and that provider has no per-role tool list to hide the verbs behind. Whatever the daemon needs a caller to do therefore belongs in the verbs' own descriptions and in what they return, because a lead that calls them itself never loads a stand-in's instructions.
- **`run` answers at once, and `wait` is bounded.** `run` returns the agent's handle immediately rather than blocking until the work is done, and `wait` returns within 10 seconds whatever the caller asked for — with the agent still running and what it has produced so far, or with the terminal it reached and its output. 10 seconds is also the longest a steer from the lead waits. A blocking wait would make the agent unsteerable by construction: on the Claude leg a helper reads what it is sent only at a tool round, so each bounded wait is the round that lets a steer land. The daemon caps the timeout itself rather than trusting the caller's.
- **Steer and stop from the row** reach the provider running the agent directly — a steer and an interrupt on its Codex thread, a message and an interrupt on its Claude Code process — and whoever reached it learns the outcome on its next wait and relays it without being told. **Steer from the lead** is native on both legs: a message to the helper on the Claude leg, the message verb on the Codex leg. **Stop from the lead** on the Claude leg is read by the daemon off the lead's own stream — the stop names the helper, and that helper's bridge calls carry its handle — and the daemon interrupts the underlying thread at once; on the Codex leg the lead calls the stop verb.
- **A run nobody is waiting on is closed.** Neither provider tells a tool server that its caller was stopped, so an agent whose caller has gone would otherwise run on, billed, with nobody reading it. The daemon therefore closes a run once its caller has had neither a wait in flight nor a turn running for 15 seconds, and interrupts what it was doing; a caller whose process exits has its runs closed at once, so an abandoned agent is interrupted within 25 seconds. The clock runs only while the caller has neither a wait in flight nor a turn running, never on the age of the last wait: the daemon drives every caller's turns, so a lead busy with its own command, or thinking long between two waits, keeps its run, and one long wait cannot mask an abandoned run, because the daemon caps every wait at 10 seconds rather than letting the caller choose. The caller is the agent that called `run` and holds the handle: on Claude Code the pack entry, which keeps a wait in flight until the answer comes, so the helper that started it may end first without closing the run; on Codex the agent itself, so one that ends its turn with no wait in flight has its run closed. Both figures live beside the bridge's argument schemas in the daemon's agents module, and the handler declares none of its own.
- **A run is finished when its whole span is.** A Claude Code lead starts its helpers in the background by default and can end its turn while a helper still runs, so a turn's end never means the work is done: a bridged Claude Code agent's run counts as finished only when its process has no turn running and no background task left, and its output is the last structured output of that span. The workflow's run-an-agent step reads a Claude Code run's end by the same rule.
- **State lives in the daemon, never in the tool-server process.** The handles, the provider-side thread and process identities, and what each agent has produced are the daemon's own. A provider restarts a tool server under a live session, and state held in that process is lost with it: measured, the restart lost the handles, the next wait answered that no such handle existed, and the agent's whole task was re-run from the start — a second billed turn nobody asked for.
- **The bridge's budget.** A cross-provider helper costs, only while it works, one conversation on its account's Codex service (1.8 to 3.0 MB a conversation, 53 to 61 MB for the whole service) or one Claude Code process (a peak of 182 MB); the bridge hop adds 1–3 ms, and the pack entry's own turns about 15 s on Claude Code.
- **A cross-provider agent keeps its conversation until the bridge closes it.** A message sent to one that has already finished continues the same conversation with its memory intact rather than opening a second one, so a follow-up costs one more turn rather than a whole repeat.
- **A typed result.** `run` takes an optional output schema, and the agent's final answer must fit it: on Claude Code the daemon passes it as the process's JSON-schema flag, and on Codex as the output schema on the conversation's turn start. `wait` then returns that object as the output, beside the status it already returns. On Claude Code the schema binds every turn of the process, not only the first, while Codex sets it per turn, so a follow-up `run` on Claude Code with a different schema, or with none, starts the agent's process again resuming its conversation with the new flag at its next idle moment, and the same schema keeps the process. A question the agent asks reaches the person as a question card, never the caller.
- **Which definitions cross the bridge**: a Claude Code file in a Codex session, a Codex file in a Claude Code session, and one of this product's own definitions only where its binding names the other provider — this product's own definitions are provider-agnostic and otherwise run natively on the session's own provider. Skills never cross: a skill is text a model reads, so one available only on the other provider is used from this side by running an agent that carries it ([Spec-029](./029-skills.md)).
- **An agent reached across the bridge carries the provider running it in its name** — `sidekicks:codex-reviewer` in a Claude Code session, `sidekicks:claude-reviewer` in a Codex session — so two files of the same name never collide, and nobody types either: choosing the row inserts the identifier. On a Claude Code session the row inserts `@agent-<name>` for one of Claude Code's own, `@agent-sidekicks:<name>` for one of this product's own and `@agent-sidekicks:codex-<name>` for a Codex-bound one; on a Codex session `<name>`, `sidekicks:<name>` and `sidekicks:claude-<name>`. A definition's name is written as one identifier — lower case, spaces and punctuation as single hyphens — wherever a provider takes one.
- **A helper at any depth reaches the bridge the same way its lead does**, an agent reached through the bridge included — on the Claude leg it starts the pack entry itself and can steer it, on the Codex leg it holds its lead's tools and calls the verbs directly. Neither provider lets an agent address its helper's helper; the person reaches any depth.
- **Every verb that names a target names an agent.** `run` names a saved definition by its `definitionId`; `message`, `wait`, `stop` and `close` name an agent already running in this session by the handle `run` returned; `list` names none. `run` may also carry a model and a reasoning effort for that run, as both providers' own spawn calls take them. A request naming a provider, an account or a node MUST be refused, because the agent's binding names them. The unit an agent addresses is another configured agent, not a vendor.
- The work the bridge starts is admitted through the ordinary orchestration pipeline and linked to the run that reached it, the link recording `reachedBy: "bridge_run"` ([Spec-014 §Interfaces And Contracts](./014-multi-agent-orchestration.md#interfaces-and-contracts)); this spec mints no run kind and no `reachedBy` value.
- **The controls a bridged agent carries are the ones every agent's own view carries** — pause and interrupt at the end of its own working line, and the steer box under its flow — and never a control on its row in a list. Pause on it is the same hold the daemon applies to any helper, its pre-tool hook holding the agent's next tool call on either leg, while its interrupt and steer reach its own conversation directly ([Spec-014 §Intervention Propagation](./014-multi-agent-orchestration.md#intervention-propagation)).
- Every invocation MUST be authorized as the tool call it is — through the session's existing approval pipeline, in the existing `tool_execution` category — MUST land as an ordinary `tool_activity` row, and MUST produce an agent visible in the session's agent tree like any other. There is no invisible peer invocation. The bridge's own verb spellings are plumbing and never reach a screen: a row says what the agent is doing, not which verb carried it.
- Refusals MUST be answered on the callback-tool result's existing arms — `denied` with the reason for an authorization or admission refusal, `failed` for an unknown target or schema-invalid arguments. No invocation is left unanswered, and no peer-invocation refusal is invented as a new error code.

### Availability and adjudication

- **The bridge is available in every session**, and the product adds no switch, cap, or enrollment of its own over it. Its verbs MUST be registered into the callback-tool registry at spawn **unconditionally**, and every invocation MUST be adjudicated at call time by the session's existing approval pipeline, in the existing `tool_execution` category, under the session's own permission level ([Spec-010 §Required Behavior](./010-approvals-permissions-and-trust-boundaries.md#required-behavior)). A bridge call is governed exactly as any other tool call in that session is: on a level that asks, it raises the same approval any tool call raises; an approval rule the provider keeps answers it without asking again; on a level that asks for nothing, nothing asks. The calling definition's tool allowlist is the only other filter, and nothing else gates it. Registration follows the landed `workflow_run` shape — registered at spawn, adjudicated per invocation — and is deliberately **not** state-gated: `callbackTools` rides only the session-creation and resume parameter shapes, and no live-registry mutation seam exists, so a registry filtered against anything that can move while the session runs could not change until the leg respawned. Per-call adjudication requires no such seam, and every change of what a session permits is effective on the next call.
- A definition's tool allowlist MUST filter this registry as it filters any other tool source. An agent whose definition carries an empty allowlist receives **none** of the bridge's verbs, and one naming an explicit set receives them only if that set names them. An allowlist that did not bind the daemon's own curated tools would report a restriction that is not in force.
- **A wait always settles.** A wait returns inside its own timeout whatever the agent's state is then, and a wait outstanding when the agent reaches a terminal state is settled by that terminal — one that fails, is canceled, or is interrupted answers with that state and whatever output it had produced, and one that finishes having produced nothing answers as finished-with-nothing rather than as an answer. The agent's run id does not exist before admission, so the waiter cannot subscribe ahead of it; the waiter MUST therefore **capture the run-lifecycle stream cursor before admitting the agent**, then subscribe and catch up from that captured cursor, settling from whichever source presents the terminal first. Subscribing merely before the verb _returns_ is insufficient and MUST NOT be relied on: a live subscription opened after admission never resends the terminal that landed in between, which is the one window this ordering closes. No invocation is left unanswered.

### Cost and causation

- A bridged agent's spend lands on **its own** paying account's row of the cost receipt and in its own per-agent figure, and is paid by **that agent's** provider account — an ordinary value of the receipt's existing per-account axis, and the reason a cross-provider agent's cost is legible at all: it runs on its own account, not on the lead's.
- A bridged agent's spend MUST NOT count toward the asking agent's own spend figure. [Spec-014 §Session Cost Receipt](./014-multi-agent-orchestration.md#session-cost-receipt) has no per-run rows, and the causal relationship between the two is carried by the existing parent/child run link, never by a receipt row.

## Default Behavior

- The bridge is present in every new session, and every call it carries raises whatever that session's permission level raises for any tool call — an approval on a level that asks, nothing on a level that asks for nothing. A session whose agents never reach for a peer behaves exactly as a session with no bridge.
- **An account reference on a definition is either pinned or current, and the two differ exactly when the provider's current account moves.** A definition that names a **specific** account is **pinned** to it: that account pays for every run under the definition, and it stays where it is pinned when a press on the provider surface makes another account current ([Spec-025 §Moving a session to another account](025-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)). A definition with **no** account reference follows the mark instead: it resolves to whichever account is the provider's current one when the run starts, and the resolved account is recorded with the run — so a run already going keeps the account it was admitted against, and a later move of the current account never silently re-points it. Those two are the whole of the choice an editing surface offers; there is no third state and nothing is resolved by guessing.
- A definition with no effort level resolves to the driver's default. A supplied effort is validated at resolution against the target model's driver-reported effort levels, never against a corpus-wide enumeration.
- A definition with no tool allowlist resolves to the driver's default tool set.
- A definition with no turn cap resolves to no cap; the daemon adds none of its own.
- A definition with no goal starts its agent with none.
- A definition with no memory scope keeps no memory, and one with no hooks runs none of its own.
- A caller that names no driver resolves the default binding's driver, and a caller that changes no axis sends no axis: an unchanged request is the definition, unmodified.

## Fallback Behavior

- **The registry is unreadable.** A run named by definition refuses; a run whose axes are spelled out in full is unaffected, so a storage fault on this table never blocks ordinary session work.
- **A definition pins a provider account that is no longer in the registry.** Resolution refuses with the `account_unavailable` arm, names the definition and the account, and starts nothing. An editing surface **marks the binding** and never rewrites it to the current account — a binding silently re-pointed is a change of who pays that nobody asked for. A binding that pins no account shows the current-account entry instead, meaning whichever account is current at the moment a run starts. The daemon MUST NOT fall back to the provider's current account. Account _readiness_ is deliberately **not** checked here: [Spec-025 §Node provider readiness and the sign-in handoff](./025-provider-accounts-and-credential-homes.md#node-provider-readiness-and-the-sign-in-handoff) makes the stored readiness projection advisory only, and the live probe the spawn path performs is the authentication check that decides. Refusing at resolution on a stored reading would refuse an agent that would have started.
- **A definition's model is no longer offered by its provider.** Resolution refuses with the `model_unavailable` arm and names the model. The daemon MUST NOT substitute a nearest-match model — silently running a different model than the one a definition pins changes both behavior and price.
- **A caller names a driver the definition neither defaults to nor overrides, and supplies no model.** The same `model_unavailable` arm answers, carrying the requested driver and **no** model, which reads as "this definition binds no model for that driver". The arm says that, and no new code is minted, because the unresolvable thing is still the model.
- **A definition's effort level is not supported by its model.** Resolution refuses with the `effort_unsupported` arm, naming the stored value and the supported set, rather than coercing to a neighboring level. An editing surface shows that same set with the stored value beside it, both in the words of the console's one effort ladder, so the person sees what is stored and what the model will take.
- **A definition's tool allowlist names a tool that has left the catalog.** Resolution refuses with the `allowlist_unrealizable` arm, names the unrealizable tools alongside the driver's supported set, and starts nothing; this is the one case that arm covers. The daemon MUST NOT spawn the agent with a silently narrowed allowlist, and MUST NOT spawn it unconstrained — either substitution reports a restriction that is not in force. The tool is likewise never dropped from a stored allowlist: it keeps an unknown-but-still-stored rendering until a person removes it.
- **A Codex agent's list leaves out the patch tool.** The list saves and the run starts like any other; when the agent calls `apply_patch`, directly, from a code cell, or as a shell command naming it, the daemon's pre-tool hook refuses the call with the reason `apply_patch is not in this agent's tool list; do not call it again.`, and the conversation's developer instructions already name the tools it lacks.
- **The tool catalog cannot be read in full.** The allowlist control renders its states over its three sources — the MCP catalog, each provider's own built-in tools, and the daemon's callback tools — and a source that has not been read is **shown as not read**, never as an empty set, rather than presenting a short catalog as the whole one. An empty catalog is never shown as an empty set: the two are opposite instructions here exactly as absent and empty are on the allowlist itself.
- **A definition's usage count or last-used time is unavailable.** Those lines are **absent** from a card rather than rendered as zero or never — an unavailable count and a count of none are different facts, and only one of them is a fact about the definition.
- **A provider's file is renamed or deleted outside this product.** The extras the record holds for it — the icon, the accent, and on a Codex file its hooks and memory scope — are shown as orphaned in the `File gone` group with the last path the file was known at, until they are reattached to a file or discarded; nothing is silently rewritten and nothing is silently dropped.
- **A provider's file does not load, or its provider switches it off.** The card stays in the library and says which, `Didn't load · <reason>` or `Off in Claude Code`, read from the daemon's own parse and the provider's own configuration rather than from what the provider chose to load; nothing hides the agent.
- **A binding names a provider this app doesn't run** (a hand-edited `provider: gemini`). The agent is shown, never hidden or refused at read; the read carries that binding with no provider and the name the file gave, kept apart from the chosen provider, so a binding's provider is only ever one the app runs. The card's provider chip reads `<name> · not supported here`, and the editor's provider row keeps showing the name with `This sidekick names <name>, which this app doesn't run. Use another provider instead?` under it and one `Use <provider>` button per provider installed on this machine; a press sets that provider and leaves the model blank until one is picked, and Save writes it to the file. An override naming such a provider gets the same line and buttons. Until a provider is picked, starting the agent, Try it included, is refused with the `provider_unsupported` arm, carrying the name the file gave, with that sentence as the daemon's message; no other provider runs in its place.
- **A change to a plugin's agent.** An update to it is refused with `agent.update_refused` (`reason: plugin_read_only`), because a plugin's agent is read-only; its card carries no delete, and its plugin is removed in `Browse plugins`.
- **An import skips a file.** A file in the picked folder that is not an agent definition is skipped and listed once in the import's answer with its reason, `README.md · not an agent definition`; every definition in the folder is still created.
- **An export cannot be written.** The export is refused with `agent.export_write_failed`, carrying the operating system's cause; no partial file is left as a success.
- **A Codex plugin's app the account has not linked.** Its `App` row in `Browse plugins` carries `Connect <App>` on that account's line; on an API-key account the row reads `Apps need a ChatGPT sign-in.`
- **A try-it run fails.** The panel keeps the scratch session, shows the refusal from whichever of the two operations failed — starting the scratch session, or sending the turn — and offers to retry that step alone, so a failed turn does not cost a new session and the resolved-binding echo is not lost.
- **A peer-invocation target names a definition that no longer exists.** The verb answers `failed` with the unresolvable target; no run is created.
- **A peer-invocation target resolves but the run refuses to start.** The verb answers `denied` carrying resolution's own reason, so the asking agent learns why rather than seeing an unexplained failure.
- **The approval seam is unavailable.** The whole callback-tool registry is withheld at spawn under the existing fail-closed availability rule of [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior), and the bridge goes with it — a withholding inherited from that rule rather than one this spec introduces; a stray invocation on an already-spawned leg is answered `denied`.
- **A bridged agent terminates without answering.** An outstanding wait is settled by that terminal state rather than left waiting or answered with a success the asking model would act on.

## Interfaces And Contracts

- Six daemon JSON-RPC operations in the `agent.*` namespace, carrying definition create / update / delete / list / export / import (`agent.definitionCreate`, `agent.definitionUpdate`, `agent.definitionDelete`, `agent.definitionList`, `agent.definitionExport`, `agent.definitionImport`), and one stream, `agent.definitionSubscribe`. All belong to the destination that owns the registry; the list is the one read a session's composer and the workflow node's chooser also make, and no session surface mutates a definition. Export and import are daemon operations because every definition in the folder is created in one daemon transaction, or none, a file that is not a definition being skipped and listed — and the client never holds a path: each takes the folder the platform's own dialog picked. Shapes and method strings are registered in [agent-definition-payloads.md §Plan-024 — Agent Definitions And Peer Invocation](../architecture/contracts/agent-definition-payloads.md#plan-024--agent-definitions-and-peer-invocation); every refusal on the definition and resolution paths this spec describes is typed in [error-contracts.md §Agent Definitions](../architecture/contracts/error-contracts.md#agent-definitions), whose codes are the ones for those paths — `agent.export_write_failed` (carrying the operating system's cause) and `agent.update_refused` (reason `plugin_read_only` or `not_orphaned`) among them — and an untyped or generic failure on any of them is a defect, not a fallback. Peer-invocation refusals are deliberately absent from that table: they ride the callback-tool result's `denied` / `failed` arms per §Required Behavior, and mint no code.
- **The record's shape, and what the operations carry.** The definition's four provider fields — driver, model, paying account, effort — are **not** top-level members: they are `bindings`, one default binding plus a list of overrides, and the stored row always carries the list, possibly empty. `icon`, `accentHue` and `turnCap` join the core as nullable members, and so do `hooks`, in the form an agent file's `hooks` key holds (`{ <Event>: [{ matcher?, hooks: [<handler>] }] }`), and `memoryScope` (`user`, `project` or `local`, null meaning none). The record carries no permission level. The create request carries `bindings` with `overrides` **optional**, which is the stored-versus-draft grammar this corpus already uses — a stored row materializes an inherited value as null, a draft expresses it by omission, and that difference is load-bearing — and it carries `scope`, `global` or one project. The update request replaces `bindings` and `hooks` **whole** and sets `memoryScope` as a value — a per-override patch grammar is not worth its wire for a bounded list that is always read together — is refused on a plugin's agent with `agent.update_refused` (`reason: plugin_read_only`), and also reattaches an orphaned record to a file, taking a picked-file token from the platform's chooser, accepted only while the record is orphaned and refused otherwise with `agent.update_refused` (`reason: not_orphaned`). Delete on a provider's own file deletes that file after checking it is the file the daemon read, together with the record beside it, in one act. Each list entry also carries `origin` (`ours`, `claude`, `codex` or `plugin`), `pluginName` on a plugin's agent, `scope` (`global` or `project`), `sourcePath`, `orphaned`, `disabledInProvider` and `loadError` with its reason — each its own field, not one exclusive state, typed with the contracts' existing types and no duplicate shape.
- A definition reference on every request that starts a run under an agent — additive-optional from the caller's side, so a request that spells its axes out in full is unchanged, while one carrying the reference need not respell the axes the definition supplies. The effective-resolved-configuration echo rides the response, and covers every field as actually applied, the system prompt and goal included; where the definition is bound plural, the echo carries the **resolved binding** in place of the folded axes. One echo serves every such request — the session whose lead the definition is, a scratch session started to try one out, a workflow step's own record, an agent named in a composer — so a resolved binding has exactly one home on the wire. The session start that a try-it makes, `session.create` with `leadDefinitionId` naming the definition, also carries the scratch mark `scratch: true`, and the session record names the definition it is the scratch session for in `scratchForDefinitionId`, which is how the one scratch session per definition is found again; no verb is minted for it.
- **The definition list is the one registry read, and every surface that chooses an agent draws its own rows from it.** A session's composer draws them as its own group of agent rows, and the workflow builder's node draws them in its chooser; an authoring agent that names an agent by name in a written workflow resolves against that same read, so a workflow written by hand and one written by an agent reach the same library. Each row a reader draws carries the identity fields only — the icon on its accent swatch, the name, the role line, and the origin mark — and not the card's chips. **This spec exports no chooser and no picker**: what choosing an agent fills in belongs to the surface that chose it — the provider's own invocation form inserted into a composer's draft, or a workflow node's agent reference with its binding left absent until an axis is changed for that node. A surface holding its own list of definitions would be a second copy of one registry. Every reader draws its rows in the library's current order — by name, or by last used once the person has switched the library to it (§The library) — so the agents a person reaches for rise to the top in the composer's group and the node's chooser too. `agent.definitionSubscribe` sends the whole list again each time it changes — a save, delete or import from any window, a provider's file added, changed or removed on disk as the daemon's watch sees it, or a plugin landing or leaving — so the library, the composer's group and a workflow node's chooser stay current in every open window without re-reading.
- **How many workflow definitions reference a definition, and when it was last used, are derived, never stored.** The daemon folds the current body of every workflow definition on the node, counting each param its node kind types `agent` ([Workflow Graph Model §Graph model](../domain/workflow-graph-model.md#graph-model--nodes-ports-and-edges-sa-29)) once per workflow, and `agent.definitionList` carries the fold beside the rows as `workflowUsage`, absent as a whole when the workflow store could not be read; a client never derives it. The card draws the line only above zero, and the delete confirmation reads the number fresh when it opens. `lastUsedAt` rides the same reply, derived the same way from the session runs and workflow runs that record the definition they were resolved from; it is absent where that cannot be read (§Fallback Behavior).
- One `SessionCallbackTool` registration per bridge verb, served through the existing callback-tool dispatch seam of [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior), and one pack entry per cross-provider agent on the Claude leg carrying those verbs and nothing else. `run` takes an optional output schema and `wait` returns the object as the output; the 10-second wait cap and the 15-second close figure sit beside the bridge's argument schema in the daemon's agents module, which only the daemon's tool server and a provider read, and the handler declares no figure of its own.
- **The allowlist's catalog comes from these reads.** `callbackTool.list` returns the daemon's callback tools, each entry carrying the label a person reads — the one label the picker and the transcript both draw, a tool without one falling back to its sentence-case words; it reads the registrations the callback-tool host dispatches, once their approval hookup is registered. `driver.listCapabilities` carries each provider's fixed list of built-in tools, and the MCP catalog is the configured servers' own read.
- **The plugin operations**, all serving `Browse plugins`: `plugin.catalogList` (a provider, an optional query and cursor, answering one entry per plugin with what it carries, whether it is installed, and whether it is installed in the person's own terminal), `plugin.read`, `plugin.install` and `plugin.uninstall` (each announcing `plugin.installed` or `plugin.uninstalled` when a plugin lands in or leaves a plugin home, which the daemon's origin reader and the session pack follow), `plugin.installedList`, `plugin.marketplaceAdd` and `plugin.marketplaceRemove`, and `plugin.appList` for a Codex plugin's apps and their link state on every Codex account. Each runs the provider's own plugin verb in the daemon's plugin home.
- No named Cedar action of this spec's own: editing a definition passes no policy check, and peer invocation registers none — a bridge call is an ordinary tool call and rides the `tool_execution` approval category already in the enumeration of [Spec-010 §Implementation Notes](./010-approvals-permissions-and-trust-boundaries.md#implementation-notes).
- No new session event type. Definition mutation appends nothing to the event log: it is node-local configuration rather than session history, and it reaches clients through `agent.definitionSubscribe`; the plugin notices are the daemon's own, not session history; every session-visible consequence of a peer invocation is already carried by the existing tool-activity and run-lifecycle events, and a save reaching a running session writes the session notice of kind `conversation_reloaded` that a conversation reload already writes.

## State And Data Implications

- **A definition is a file, and one node-local table is the registry over it.** The authored fields live in the definition's file — one of the origins of §Required Behavior, which the daemon watches — and one node-local table, owned by this spec's plan, holds the row the registry read answers from: identity, the origin, the scope and the file's path, the name fold, the bindings, the icon and accent, the instructions and goal, the tool allowlist, the hooks and memory scope, the turn cap, and the timestamps. The name fold is unique within one origin and scope. The row follows its file: a file this product wrote carries every field, so its row restates what the file says; a provider's own file carries only the fields that provider reads, so its row additionally holds what the file cannot (§Required Behavior, the union rule); a plugin's file lives in the daemon's plugin home and is never written. Editing a field the file can hold writes the file; editing one it cannot writes only the row; a file changed or removed outside this product is picked up by the watch, and the fields only the row holds show as orphaned until they are reattached to a file or discarded. The table is configuration, not session state: it is not events-canonical and is not rebuilt from the event log.
- **The bindings are one JSON column, not a child table.** The provider columns a single binding would have taken fold into one non-null `bindings` column holding the default and the overrides together, beside nullable columns for the icon and the accent. JSON rather than a second table because this corpus already carries bounded, always-read-together lists inline — the tool allowlist on this same table is the precedent — and a binding is never queried across definitions. The table is part of the daemon's one local schema, in this shape.
- **An agent's memory is files, never a table.** Each memory scope is a folder — the all-projects folder under `~/.ai-sidekicks/agent-memory/`, the project scopes at Claude Code's own paths inside the project — holding the agent's notes; the table stores only the scope. Every Claude Code configuration home the daemon creates links `agent-memory` to the all-projects folder. Deleting an agent leaves its memory folder in place.
- **Installed plugins live in the daemon's plugin homes**, `~/.ai-sidekicks/plugins/claude/` and `~/.ai-sidekicks/plugins/codex/`, in each provider's own layout: the two catalogs, about 100 MB, and the installed plugins. Nothing of a plugin is written into an account home or the person's own home.
- **Nothing this product knows is ever written into a provider's file.** A field a provider's file has no place for stays in the row, attached to the file by its name and location, and the file never gains a key its provider does not read.
- Export and import touch no table of their own: an export is one Markdown file per definition the person keeps, with the account left out and no memory contents, and an import is ordinary definition creates, applied in one daemon transaction.
- Starting a run under a definition writes the resolved values onto that run's own agent record. No foreign key binds an agent to the definition it was resolved from, because it does not depend on it after resolution.
- No control-plane impact: a linked device lists and edits definitions on this machine through Remote Control, like every other screen, and no copy of a definition is kept anywhere else.
- `instructions` and `goal` are text the person writes and are treated as ordinary node-local configuration content; they are never emitted into an event payload by definition mutation.

## Example Flows

- `Example: A user creates a definition named "reviewer" pinning a provider, a model, extra-high effort, review instructions, and an allowlist of read-only tools. Three later sessions name it in their composer; each run records the configuration it was resolved for.`
- `Example: The user edits "reviewer" to widen its tool allowlist. The two agents already running keep the narrower allowlist for the rest of their lives; the next run picks up the wider one.`
- `Example: A lead on one provider runs "reviewer", whose binding is for the other. The call raises the same approval any other tool call raises at that session's permission level. The daemon starts the reviewer on its own provider, the row appears under the lead with a mark of which provider is running it, the lead's wait returns the reviewer's answer, and the reviewer's spend appears on its own receipt row under its own paying account.`
- `Example: A lead runs a bridged agent and then stops waiting on it, with no turn of its own running. Fifteen seconds later the daemon closes the run and interrupts what it was doing, and the row says so.`
- `Example: The account a definition pins is removed. The next run under that definition refuses and names both the definition and the missing account; nothing starts and no current account is substituted.`

## Implementation Notes

- Because a run keeps the configuration it was given, the definition table is safe to edit under load: no reader of a running agent's configuration ever consults it.
- Because every invocation lands as an ordinary tool-activity row and an ordinary run, the session transcript is itself the record of which agent reached which peer and when — a capability that lets a running model start other runs is exactly the kind that should not be exercised invisibly.

## Pitfalls To Avoid

- **Do not make a running agent a live view of its definition.** It reads as a feature ("edit once, applies everywhere") and is an authorization hole: it widens a running agent's authority without an authorization act.
- **Do not treat `name` as an identifier.** A rename must not orphan references, and two identically-named definitions in different origins are unrelated records.
- **Do not conflate an absent tool allowlist with an empty one.** One means "the driver's defaults", the other means "nothing"; collapsing them either strips an agent of every tool or hands it all of them.
- **Do not give a definition a permission level.** The level is the session's or the workflow run's; a level on an agent would be a second precedence layer over its tool allowlist.
- **Do not fall back to the provider's current account when a pinned one is missing.** It converts a hard, legible refusal into a silent change of who pays and which identity acts.
- **Do not filter the bridge's verbs out of the registry by session state.** It reads as the safer choice and is not: the registry is composed at spawn only, so a filtered registry cannot reflect a change made while the session runs, and the person who narrows or widens what the session permits sees nothing happen. Adjudicate per call through the ordinary approval pipeline instead, and keep the refusal legible.
- **Do not hold a bridged agent's state in the tool-server process.** A provider restarts that process under a live session, and the agent's work is then silently re-run from the start on the next call.

## Acceptance Criteria

- [ ] A definition can be created, listed, updated, renamed, and deleted; `definitionId` is stable across every update including a rename.
- [ ] Creating a second definition in the same origin and scope whose name differs only in letter case is refused, including a pair differing only in a non-ASCII case mapping, and including two such creates issued concurrently — exactly one commits; a definition of this product's own may share a name with a provider's own.
- [ ] A run started under a `definitionId` matches the definition's configuration, and the response echoes the effective resolved configuration.
- [ ] A request carrying both a `definitionId` and an explicit field applies the explicit field for that field only, and echoes the merged result.
- [ ] Editing a definition leaves an agent already running from it byte-for-byte unchanged in configuration, and deleting the definition leaves it running.
- [ ] A run under a definition whose pinned provider account is absent refuses, names the definition and the account, starts nothing, and does not fall back to the provider's current account.
- [ ] A run under a definition whose tool allowlist the driver cannot realize refuses rather than spawning.
- [ ] A definition with an absent tool allowlist and one with an empty allowlist produce observably different spawns.
- [ ] Every bridge verb is present in a session's callback-tool registry, and every call is adjudicated at call time by the session's existing approval pipeline in the `tool_execution` category, a denial answering on the callback-tool result's `denied` arm.
- [ ] A bridge call on a permission level that asks raises the same approval a tool call raises, an approval rule answers the next one without asking again, and on a level that asks for nothing the call runs unprompted.
- [ ] An agent whose definition carries an empty tool allowlist receives none of the bridge's verbs.
- [ ] A peer invocation lands a `tool_activity` row and a run visible in the transcript.
- [ ] On a Claude Code lead, a cross-provider agent is reachable only through its pack entry: the lead's own tool list holds no bridge verb, and a lead told to run that agent produces a row in the tree rather than calling the verbs itself.
- [ ] On a Codex lead, the tool server's own description lists every cross-provider agent by name, and the lead runs one by name with no stand-in role planted.
- [ ] `run` returns a handle without waiting for the work, and every `wait` returns inside the daemon's own cap even while the agent runs on.
- [ ] A run whose caller has had neither a wait in flight nor a turn running for 15 seconds is closed and its provider-side work interrupted, a caller whose process exits has its runs closed at once, and every `wait` returns within 10 seconds whatever the caller asked for.
- [ ] Restarting the tool-server process under a live session loses no handle and re-runs no work: the next wait answers from the daemon's own state.
- [ ] A message to a bridged agent that has already finished continues the same conversation rather than starting a second one.
- [ ] Steer and stop from the row reach the provider running the agent, and the agent that reached it learns the outcome on its next wait.
- [ ] A denied invocation is answered `denied` on the already-running leg, with no respawn required and no registry rebuild.
- [ ] A wait outstanding on an agent that fails, is canceled, or finishes having produced nothing is settled by that terminal state rather than left waiting.
- [ ] A bridged agent's spend appears on its own paying account's row of the cost receipt and in its own per-agent figure, and the asking agent's own figure is unchanged.
- [ ] A bridge request naming a provider, an account or a node is refused, and a `run` carrying a model and a reasoning effort runs the named agent at them.
- [ ] Every refusal on the definition and resolution paths carries one of the registered `agent.*` definition codes, and none surfaces as a generic or untyped failure; every peer-invocation refusal arrives on a callback-tool result arm instead, carrying no code.
- [ ] A definition whose pinned account is registered but not currently authenticated resolves, and is refused by the spawn gate rather than by the resolver.
- [ ] The registry lists definitions from every origin, each with its origin, scope, file path and both provider facts; a plugin's agent is read-only and an update to it is refused.
- [ ] Deleting an agent from a provider's own file deletes that file and the record beside it, and the confirmation names the path.
- [ ] A provider's file renamed or deleted outside the product leaves its record in the `File gone` group, and reattaching it through a picked file is accepted only while it is orphaned.
- [ ] An agent's hooks of every handler kind run on both providers only while that agent works, and a Codex helper's hooks run through the gate.
- [ ] On Codex, an address, a prompt and an agent hook each run through the daemon's command hook and return allow or block, and a tool hook runs at session end through the daemon's own MCP client.
- [ ] An agent with the everywhere memory scope reads and writes the same folder on every account and both providers, at every permission level without asking.
- [ ] A saved agent reaches a running Claude Code session at its next idle moment and a running Codex session by a fork, each writing one reload row.
- [ ] On Codex, a list without the patch tool runs, and a call to that tool is refused with the reason naming the agent's tool list.
- [ ] A `run` that asks for an output schema gets that object back from `wait`.
- [ ] Installing a plugin in `Browse plugins` puts it in the daemon's plugin home, never an account home, and its agents and skills appear read-only marked with the plugin's name.
- [ ] Every open window's library, composer group and workflow chooser follow a definition change without re-reading.
