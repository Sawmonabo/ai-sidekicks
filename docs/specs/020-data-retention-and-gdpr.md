## Purpose

Define data retention, deletion, and GDPR compliance policy to ensure the system meets regulatory obligations for personal data protection while preserving non-PII audit capability.

## Scope

This spec covers:

- Session data lifecycle beyond `archived` (the `purge_requested` and `purged` states), and how long a kept session and its provider files last
- The data acts: deleting old sessions, exporting everything a machine keeps, erasing everything a machine keeps, rotating the keys, and deleting the hosted account
- Crypto-shredding, and the custody of the daemon master key every other key is sealed under
- Schema requirements for PII separation

## Non-Goals

- Consent collection UX
- Cookie policy or browser-side tracking
- Third-party data processor agreements
- Billing data retention (governed separately)
- Anything that exists to govern an organization of other people: enterprise sign-on (OIDC and SAML), compliance mappings (SOC 2, ISO 27001, HIPAA, FedRAMP), HSM custody, WAF guidance, Helm charts, SLA support and multi-region sign-up discovery. The product serves one person.
- Server-side telemetry and usage analytics. The app collects none, and a crash report stays on the machine that crashed ([Spec-021 §Default Behavior](021-desktop-app-and-renderer.md#default-behavior)).

## Required Behavior

### Session States Beyond Archived

- The session lifecycle must include two additional states beyond `archived`: `purge_requested` and `purged`.
- `purge_requested`: the person has pressed `Delete old data` and the session is among those it removes. The session is locked against further modification while purge processing is pending.
- `purged`: event payloads containing PII have been destroyed. Audit stubs (timestamps, event types, non-PII metadata) are retained.
- Allowed transitions: `archived -> purge_requested -> purged` and `closed -> purge_requested -> purged`. Both `archived` and `closed` sessions may be purged. Purge is irreversible. A `purged` session must not transition to any other state.

### Retention Policy

- A kept session holds its data, personal data included, until the person deletes it. Nothing deletes a session by age and nothing deletes one automatically ([ADR-039](../decisions/039-kept-sessions-keep-their-provider-files.md)).
- `Keep sessions for` on Settings › Runtime is the one bound over finished sessions, 90 days by default. It is the machine's own setting, set in one place on that machine and nowhere else. Past it a finished session is eligible for deletion, and eligible is not deleted: the control's line reads `After this, a finished session can be deleted. Nothing goes until Delete old data is pressed.`
- `Delete old data` is the only act that removes sessions and their logs, and its line on Runtime says so: `Removes sessions and their logs past their retention, while Erase all data removes everything the service holds.` It confirms in place: `Delete 14 archived sessions and their logs? Each chat's session workspace goes too; files in project folders stay. This cannot be undone.`, and, while backups are on, `Backups taken before this delete keep these sessions for up to four weeks.` It is the one purge, `daemon.retentionPurge` (§Interfaces And Contracts), and the service runs it on nothing but that press.
- The purge shreds first. In one transaction it overwrites the session's wrapped content key with zeros of the same length and then deletes that row, before the session's rows; once the transaction commits it checkpoints the write-ahead log with `TRUNCATE`, so neither the database file nor the log keeps a copy of the wrapped key. The person's own words and the machine-authored bodies alike are sealed under that key, so every body that stays on disk until SQLite reuses the page (the free list, the write-ahead log) is ciphertext whose key is gone, even to whoever holds the master key; no `secure_delete` pragma is set. After the transaction it reclaims the session's artifacts, deletes its capture folder with its snapshot refs and its base pins, deletes a chat's managed workspace whole, and removes the provider's own files for the session. The purge claims no more than that: provable destruction of the freed pages is never claimed.
- The provider's conversation file lasts as long as the session, because resuming a session reads the provider's own transcript. Every Claude Code process the daemon starts carries `"cleanupPeriodDays": 36500` in its `--settings` JSON, which outranks a repository's own settings files, and each account home's `settings.json` holds the same value for a process started there without the flag, so Claude Code's age sweep, which judges by file age across the whole home, never reaches a file. A managed policy that holds the value lower is read back from `get_settings` after each spawn and raised as the `session.notice` kind `settings_ignored`. Codex keeps a conversation until it is deleted.
- `Delete old data` removes, from every account home a session ran in, every file the provider keeps for that session: on Claude Code the conversation file with its subagent and tool-result files, its file history, session environment, todo and task lists, plan file and debug log; on Codex, `thread/delete`. A session typed in a terminal keeps its conversation in the person's own Codex folder, which the purge never touches.
- Two things drop on their own past a bound, and neither bound is a switch that turns deletion on or off: a workflow run's step data past `Keep run data for` (below), and the diagnostic logs past `Keep diagnostic logs for`, 7 days by default. Above 30 days the service records a warning about that setting. The diagnostic bound covers the service's own logs and, in each account home the app manages, what the provider writes there and never reads back for a session — its logs, telemetry, traces, shell snapshots and paste cache — by the pinned provider build's own cleanup list minus what belongs to a session, re-read on every pin move. Both sweeps run on the service's one scheduler.
- A worktree kept by `Discard and remove` is a project's file, not a session's: no retention bound reaches it, `Delete old data` never touches it, and it goes only when the person presses `Delete now` ([Spec-008](008-worktree-lifecycle-and-execution-modes.md)).
- The service may compact its own storage in the background — compress, repack, archive, move large bodies to compressed storage, rewrite its indexes — only when everything the app promises to show survives: the transcript in order, every system message, tool rows and their output that no deletion above removed, message identities and times, and the undo and fork points still kept. Compaction never removes anything a person could see, and it is never a retention mechanism.
- A workflow run's step data — what each step read and wrote — carries its own bound, 30 days by default, set beside the session window on the same machine and overridden by no workflow ([Spec-015 §Execution semantics](015-workflow-authoring-and-execution.md#execution-semantics)).
- The run-data bound covers step data alone. Past it the run still lists and still carries its status, its timings, and its summary, and its step panel reads that the data expired in place of the panels. Files a workflow saved on purpose are never touched by the bound.
- A run marked `Keep` holds its step data past the bound, and a run still waiting is never touched by it.
- Deleting run data is always an explicit act — deleting one run from its own row, or deleting runs older than a chosen age. Each asks once, names what goes and that a `Keep` run stays, and neither can be undone.
- Every resolved secret value is redacted from logs, step payloads, and error messages before they are written, so a retained run record never holds the credential its step resolved.

### Provider Privacy Settings

- The person's own provider privacy settings follow into every account home the daemon manages. At each start the daemon reads Claude Code's `DISABLE_TELEMETRY`, `DISABLE_ERROR_REPORTING`, `DISABLE_FEEDBACK_COMMAND` and `CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY` from the person's own Claude Code settings and passes them through `--settings`, and reads Codex's `analytics.enabled`, `feedback.enabled` and `otel.metrics_exporter` from the person's own Codex config and passes them through `-c`, as every provider setting is passed. It never writes them into a home, so a change the person makes in their own files reaches the next process the daemon starts.
- The keys are each provider's own: Claude Code's are documented in its [data usage](https://code.claude.com/docs/en/data-usage) page, and Codex's in its [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). There is no switch of the app's own for them.

### Crypto-shredding (SQLite Event Log)

- PII fields must be encrypted under the content key of the session they belong to, the same AES-256-GCM key that seals the session's machine-authored content, under an associated-data label of their own ([§PII Payload Column Pattern](#pii-payload-column-pattern)). This covers the person's own messages, queued sends and steer text.
- Session content keys must be stored in the separate `session_content_keys` table, not inline with event data, each wrapped under the daemon master key.
- Erasure must be accomplished by destroying the key material the PII fields are sealed under. `Delete old data` overwrites a session's wrapped content key with zeros and deletes it before the session's rows, checkpointing with `TRUNCATE` after commit, and `Erase all data` destroys every custody copy of the daemon master key, which wraps every session's content key, and then deletes the store. Once the key is gone, the encrypted PII fields are unrecoverable, including the bytes SQLite leaves in freed pages and the write-ahead log. No `secure_delete` pragma is set.
- Non-PII fields must remain in plaintext for audit and operational purposes.

### Postgres (Control Plane) Deletion

- The hosted account's records in the control plane Postgres database are hard-deleted when the person deletes the account with `sidekicks delete-account`, over the control plane's `account.delete` ([§Erasure Paths](#erasure-paths) Path 2). Deleting the account signs this machine out and never erases a machine's local data: that is `Erase all data` alone.
- Where a surviving control-plane row carries an independent retention basis — a revoked access token's `revoked_jtis` entry, kept until its reap — the reference to the deleted user must be anonymized (the data-subject FK is nulled via `ON DELETE SET NULL` — see [§Erasure Paths](#erasure-paths) Path 2 FK-safety) rather than the row deleted, preserving the surviving record and its referential integrity while severing the user linkage.

### Data Export

- `Export all data` on Settings › Runtime writes everything this machine keeps for the person as a readable folder, and `sidekicks export-data <folder>` does the same from the command line with the service running. The row's line reads `Everything this machine keeps for you, as a folder: sessions, files, sidekicks, workflows and accounts. Not your settings, and no passwords or tokens.`; `Export…` opens the platform's save dialog with the name `sidekicks-export-<date>`. While it runs it reads `Exporting · 312 of 1,204 sessions` with `Cancel`; when done, `Exported to <path> · 1.2 GB` with `Show in Finder` (`Show in Explorer` or `Show in folder` elsewhere) and the line `The export is not encrypted; keep it somewhere safe.`; a failure names its cause and offers `Try again`.
- The folder holds:
  - `sessions/<id>.jsonl`: every event of every session, decrypted under that session's content key, one per line, in the canonical event shape — the person's words and the machine-authored bodies alike, with the at-rest bodies of `interventions` and `queue_items` ([Spec-003](003-queue-steer-pause-resume.md)), so text on a refused intervention or on a queue item canceled before it reached the timeline is exported too;
  - `files/<session id>/…`: each session's artifacts as the store holds them;
  - `sidekicks/`: agent definitions in their export form;
  - `workflows/`: workflows in their export form;
  - `accounts.json`: each provider account's name, provider and plan, with no credential;
  - `hosted-account.json`: when signed in to the hosted account, the control plane's `account.export` reply (the account record, its device list and its `account_audit` rows);
  - `README.txt`: what each folder is.
- It leaves out the settings values, every credential, pasted token, workflow secret and key, and the diagnostic logs.
- It streams one session at a time within 64 MiB of memory whatever the data's size, one export at a time, and needs no archive library. An export writes one line to the diagnostic log and no event.
- Because every session is exported whole, a mention of the person inside a machine-authored body is exported with the rest; no selector decides what reaches the folder.
- The export carries no separately computed spend tally: the session cost receipt is a read-time fold over the exported rows ([Spec-014 §Session Cost Receipt](014-multi-agent-orchestration.md#session-cost-receipt)), and a second tally would be the second accountant [Spec-014 §Cost Figure Display Consistency](014-multi-agent-orchestration.md#cost-figure-display-consistency) forbids.
- Export must run before `Erase all data`, which destroys the keys every body is sealed under.

### Schema Requirements

- PII must be stored in a separate `pii_payload` column (encrypted) from day one. Non-PII must be stored in a `payload` column (plaintext).
- This separation is part of the daemon's one schema.

### Data Map Prerequisite

- A data map documenting all PII fields across both the SQLite event log and Postgres control plane must be produced before crypto-shredding logic is implemented. The PII data map is documented in the [PII Data Map](#pii-data-map) section below.

## Default Behavior

- `Keep sessions for` is 90 days, `Keep run data for` 30 days and `Keep diagnostic logs for` 7 days. A session becomes eligible for deletion once `Keep sessions for` has passed since it was archived or closed.
- No session is purged except by the person's `Delete old data`. Step data and the diagnostic logs are the only data the service drops on its own, each past its own bound.
- Backups are off until the person turns on `Back up automatically` ([Spec-013 §Backup Policy](013-persistence-recovery-and-replay.md#backup-policy)).

## Fallback Behavior

- If a session's content key cannot be opened during `Export all data` (the master key unavailable, the session's `session_content_keys` row missing, or its wrap failing to authenticate), the export must fail with an error that names the session and the cause rather than writing partially decrypted or corrupted data.
- If a purge operation fails midway, the session must remain in `purge_requested` state and the failure must be logged for retry. Partial purge must not leave the session in `purged` state.

## State And Data Implications

- The `purge_requested` and `purged` states extend the session state model defined in [Session Model](../domain/session-model.md).
- The event log keeps its keys in these tables: `session_content_keys`, one wrapped content key per session, and `master_keys`, the ids of the master keys in custody and which one is active ([§Daemon Master Key](#daemon-master-key)).
- Crypto-shredding means that once a key is deleted, historical PII in the event log is permanently unrecoverable. This is by design.
- Audit stubs in `purged` sessions provide a non-PII record that the session existed and what structural events occurred.

## PII Payload Column Pattern

Tables with PII in the SQLite event log use a dedicated encrypted column to separate PII from non-PII data:

- **Tables**: `session_events`, `interventions` and `queue_items` each carry a `pii_payload BLOB` column (see [Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md)).
- **Encryption**: **AES-256-GCM** under the session's content key, the key in `session_content_keys` that also seals the session's `content_payload`, with a random 96-bit nonce per write, stored as `iv || ciphertext || tag`, and AAD = `session_id || "ais.session-pii.v1" || row id`, where the row id is the event id, the intervention id or the queue item id, and an intervention's session is its target run's session. The AAD binds the ciphertext to its record, so it cannot be replayed onto another record, and the label keeps a row's PII ciphertext from authenticating as that row's `content_payload`, whose AAD is `session_id || event_id`. The label sits beside the wrap labels `ais.master-wrap.v1` and `ais.session-content-wrap.v1`.
- **Encryption flow**: PII fields (user messages, file paths, code snippets) are extracted from the event payload, encrypted under the session's content key and stored in `pii_payload`, by the same write path that seals `content_payload`. A queue item's body, a person's send or an orchestration-authored prompt, and a steer's text are sealed the same way into their rows. The main `payload` column contains only non-PII data (event type metadata, timestamps, structural references).
- **Content-key provisioning**: A session's content key is a **random 32-byte AES-256 key** generated by the platform CSPRNG at the session's first write that seals a body (an event's PII or content partition, a queue item's body or a steer's text), **not** derived from the person's credentials or any identity record. Its only persisted copy is `session_content_keys.encrypted_key_blob`, where it is envelope-encrypted (wrapped) under the daemon master key via XChaCha20-Poly1305 behind the master-key header, with AAD = the header followed by `session_id || "ais.session-content-wrap.v1" || key_version` (binding the wrap to the session, the key version and the master key that sealed it). Because the key is random with no derivation, destroying it is a true cryptographic erasure: no surviving secret — credential or identity record — can reconstruct it. `Delete old data` destroys one session's key by deleting its row before the session's rows, and `Erase all data` destroys every session's key at once by destroying every custody copy of the daemon master key ([§Erasure Paths](#erasure-paths) Path 1). This is the GDPR Article 17 crypto-shred precondition; a credential- or identity-derived key would survive the delete via its source secret and silently defeat erasure. Envelope encryption (a random DEK wrapped by a KEK) is the AWS KMS / Google Cloud KMS / Rails ActiveRecord Encryption consensus and the construction under which destroying the key, or the key that wraps it, is true erasure.
- **Tables that do NOT get `pii_payload`**: All Postgres control-plane tables. PII in Postgres is handled via access control and row-level deletion, not column-level encryption. The control plane is a trusted environment with its own access boundaries.

### Daemon Master Key

The daemon master key is the symmetric key under which every session's content key in `session_content_keys` and every secret the daemon keeps in its database, its private keys and its hosted refresh token, are wrapped. It opens unattended under the person's login: the service starts at login, comes back after a reboot and runs scheduled workflows with nobody present, so nothing asks for a touch or a passphrase at start, except on a machine with neither a security chip nor a keychain. Where the machine has a security chip, the key that opens the data day to day is bound to it, so a copied disk or data folder is unreadable on another machine.

**Custody ladder**, tried in order at first start and on every custody change:

1. **Hardware wrap**, where the machine has a security chip the service can use with no person present.
   - _macOS:_ a Secure Enclave P-256 key-agreement key made with CryptoKit. Its opaque handle (284 bytes) sits in the data folder, and the master key is wrapped to it: an ephemeral P-256 key, ECDH with the enclave key, HKDF-SHA-256, then AES-256-GCM. The enclave work runs in a small Swift helper process, `sidekicks-keywrap`, shipped per architecture, because a tampered handle crashes CryptoKit; a helper crash is a refusal, never a daemon fault. The helper needs no signing identity, entitlement or keychain entry: an ad-hoc-signed helper made the key in 53 ms and a second process unwrapped it in 9 to 20 ms. An Intel Mac without a T2 chip has no Secure Enclave and starts at the keychain tier.
   - _Windows:_ a user-scoped, non-exportable key with no PIN in the Microsoft Platform Crypto Provider ([`MS_PLATFORM_CRYPTO_PROVIDER`](https://learn.microsoft.com/en-us/windows/win32/api/ncrypt/nf-ncrypt-ncryptopenstorageprovider), the TPM key storage provider); the master key is wrapped and unwrapped with NCrypt.
   - _Linux:_ no hardware tier until a probe on a Linux machine with a TPM chooses between `systemd-creds` and the TPM2 software stack.
2. **Keychain.** The master key, already hardware-wrapped where tier 1 exists, is one entry, whose account is `master-key.<key id>`, in the login keychain or the Secret Service through `@napi-rs/keyring` 2.1.0, every entry opened with `{linux: {store: "secret-service"}}` so the kernel keyring, which empties at reboot, is never used. On Windows it is one Credential Manager generic credential at `CRED_PERSIST_LOCAL_MACHINE`, never `CRED_PERSIST_ENTERPRISE`, so it does not roam with the profile. Where both tiers exist both apply: reading the key needs this machine's chip and the person's unlocked login.
   - On Linux with lingering, the service can start before login while the keyring is locked. It then starts locked: a run that needs sealed content fails its step and offers `Retry from this step`, never waiting indefinitely, and the service reads the key again at each new run and each retry, so the first one after login succeeds.
3. **Passphrase file**, on a machine with neither: the master key sits in `daemon-master.<key id>.enc` in the data folder, the Argon2id file of [ADR-021 §Tier 3 — Argon2id passphrase file](../decisions/021-cli-identity-key-storage-custody.md#tier-3--argon2id-passphrase-file) (`@noble/hashes` Argon2id, m = 19456 KiB, t = 2, p = 1; XChaCha20-Poly1305 under the 50-byte header). The person chooses the passphrase at first start, with `sidekicks daemon install` or on Settings › Runtime's service line, which reads `Choose a passphrase for this machine's data` over a masked field. After each start the service is locked until the passphrase arrives through `daemon.unlock {passphrase}`: `sidekicks daemon unlock` reads it without echo and sends it over the daemon's socket, and the Runtime service line, reading `Running · locked until its passphrase is entered`, takes it in a masked field with `Unlock`. The passphrase is never kept, and the service stays unlocked while it runs.
4. **Refuse.** No tier works: the service does not start, and says why in `sidekicks daemon status`. It never falls back to a plaintext master or to a master held only in memory.

The master key is never written anywhere in the clear: it lives only in the hardware wrap, the keychain entry or the passphrase file, the iCloud Keychain item when that is on, wrapped in the recovery envelope when a recovery passphrase is set, and in locked memory while the service runs.

**Key ids and the master-key header**:

- Each placement of the master key in custody has a key id: 16 random bytes, written as 32 lowercase hex characters. The `master_keys` table records them: `key_id` (primary key), `state` (`active`, `incoming`, `outgoing` or `retired`; at most one row in each of `active`, `incoming` and `outgoing`, and one `retired` row for each older key a backup still names) and `created_at`. Outside a rotation exactly one row is `active`.
- Custody entries are named by key id: the keychain entry's account is `master-key.<key id>`, the passphrase file is `daemon-master.<key id>.enc`, and the iCloud Keychain backup item is labeled with the key id. The Secure Enclave or TPM key belongs to the machine, not to a master key, and is kept across rotations.
- Every blob sealed under the master key, each `session_content_keys` wrap and each `daemon_secrets` row's `sealed_secret`, begins with the master-key header: one format byte and the 16-byte id of the key that sealed it, ahead of the 24-byte nonce, the ciphertext and the tag. The header is bound into the AAD, which is the header followed by the blob's own AAD, so a blob cannot be relabeled to another key. A reader opens each blob with the key its header names, and so records, on every row, which key protects it.
- A write never commits under a retired key or one that only memory holds: it wraps under the key `master_keys` names `active`, and its transaction confirms that key is still `active` before it commits.

**Windows, native and WSL alike.** On both kinds of Windows computer each Windows step runs in the service's Windows half, never in the daemon's own process. The Windows half wraps and unwraps with NCrypt through Microsoft's `windows` crate, and writes Credential Manager at `CRED_PERSIST_LOCAL_MACHINE` through `windows-native-keyring-store` 1.1.0 with `persistence=local`, because `@napi-rs/keyring` 2.1.0's Windows binding passes only the target and so writes every entry at Enterprise. The tier-3 passphrase file sits in the Windows data folder, where a native daemon on that computer keeps it, and the Windows half reads it as it reads the keychain entry. The daemon's `WindowsHardwareKeyWrap` and `WindowsCredentialStore` carry every call to the Windows half, over its channel while the service runs and one-shot while it does not (`sidekicks-windows-half.exe keystore get|set|delete <entry>` and `keywrap wrap|unwrap`, reading and writing the key material on stdin and stdout), because `sidekicks sign-in`, `sidekicks db restore` and `sidekicks erase-data` run with the service stopped. The Windows half holds the master key only for the one unwrap and passes it over the channel; it never sees a key sealed under the master key: the identity key, the channel key, the MCP governance key, or the hosted account's DPoP key and refresh token. The Secret Service inside a WSL distribution is never used. Custody is the same whichever side runs the service and never moves: a move between Windows and a distribution carries the store, and the master key stays in Windows custody for both sides.

**One custody root.** Every other daemon key is sealed under the master key and stored in the daemon's database, in `daemon_secrets`, one row per secret keyed by its `purpose`, with its `key_id`, its `state` (`active` or `incoming`), its `public_key` where it has one and its `sealed_secret`: the machine's identity key and its channel key, the hosted account's DPoP key and refresh token, and the MCP governance key ([Spec-025 §Implementation Notes](./025-mcp-server-configuration-and-governance.md#implementation-notes)). The seal is XChaCha20-Poly1305 behind the master-key header, with the header followed by `purpose || row id || "ais.master-wrap.v1"` as its AAD. A tool server's sign-in is held apart, as [ADR-040](../decisions/040-mcp-credential-custody.md) records: its refresh token and, for a server that demands DPoP tokens, its signing key are items of their own in the operating system's credential store. The app's keychain entries are therefore the master key and the secrets that keep an entry of their own: the pasted provider tokens, the workflow secrets, the web address's signing secret, the mail password, and each tool server's sign-in items. On Windows every one of them, like the master key's, is a Credential Manager entry the Windows half writes at `CRED_PERSIST_LOCAL_MACHINE`; none is written at a roaming persistence, and none goes through `@napi-rs/keyring` there.

**In-memory handling**:

- Master key is allocated in memory locked with `sodium_mlock` (libsodium / sodium-native v5.1.0). This prevents swap-to-disk on all platforms and sets `MADV_DONTDUMP` on Linux.
- Master key is zeroed with `sodium_memzero` and unlocked with `sodium_munlock` on wipe events.
- Wipe events:
  - **Idle wipe**, on the hardware and keychain tiers only: default 15 minutes in which nothing is wrapped or unwrapped under the master key. Configurable via `daemon.master_key.idle_wipe_seconds` (minimum 60, no maximum). The next access reads the key again at the cost of one keychain read and one enclave or TPM unwrap, with no person involved; on Windows the read goes through the Windows half. The passphrase tier has no idle wipe, because an unlocked unattended service must stay unlocked.
  - **Shutdown wipe**: on `SIGTERM`, `SIGINT`, or orderly daemon shutdown. Wipe happens before closing SQLite handles so no encryption operation can execute during teardown.

**Rotation**:

- `sidekicks rotate-keys`, over `daemon.keyRotate`, replaces the master key in six steps:
  1. create a new master key and key id, in locked memory;
  2. write the new key's custody entry, named by its key id, on the highest custody tier that works, with its iCloud Keychain item when `Keep the backup key in iCloud Keychain` is on and its recovery envelope when a recovery passphrase is set, and verify each by reading it back and comparing it with the key in memory;
  3. insert the new key's `master_keys` row as `incoming`; the `active` row still names the old key, so the store records both ids;
  4. re-wrap every `session_content_keys` row, and re-seal every `daemon_secrets` row, under the new key, each blob's header naming the new key id, each content key's `key_version` rising by one and its `rotated_at` stamped;
  5. in the same `BEGIN EXCLUSIVE` transaction as step 4, mark the new key `active` and the old one `outgoing`, then commit;
  6. confirm that no blob's header names the outgoing key id, re-wrapping any that does, then delete the old key's recovery envelope and mark its `master_keys` row `retired`. A retired key's custody entry and its iCloud Keychain item stay until the last backup sealed with it ages out, so the machine that wrote a backup still opens it; the backup run that prunes that backup deletes them and the row ([Spec-013 §Backup Policy](013-persistence-recovery-and-replay.md#backup-policy)), and a retired key no backup names goes at once. Nothing is sealed under a retired key; it only opens a backup being restored.
- No row is ever committed under a key that existed only in memory: the new key's custody entry is written and verified (step 2) and the store names it (step 3) before anything is wrapped under it (step 4).
- The service keeps neither passphrase, so `sidekicks rotate-keys` reads, without echo, the machine's passphrase when the master key is on the passphrase-file tier and the recovery passphrase when one is set, as `sidekicks daemon unlock` reads one, and sends them with the request. The service checks each against what it already opens before step 1, and refuses the rotation, with nothing to undo, when one it needs is missing or wrong.
- At start the service finishes or undoes a rotation a crash interrupted, before it serves anything:

  | Crash after | What the store holds | What start does |
  | --- | --- | --- |
  | step 1 | nothing new | nothing: the new key existed only in memory, and nothing names it |
  | step 2 | a custody entry whose key id has no `master_keys` row | deletes that entry, with the iCloud Keychain item and recovery envelope step 2 wrote; the old key stays active (rolled back) |
  | step 3, or during step 4 | an `incoming` row; every blob still names the old key, because steps 4 and 5 commit together | reads the incoming key's entry: when it opens to a key, runs steps 4 to 6 (resumed); when it is missing or does not open, deletes the `incoming` row and whatever step 2 wrote, and the old key stays active (rolled back) |
  | step 5 | an `outgoing` row; every blob names the new key | runs step 6 |
  | step 6 | one `active` row, and a `retired` row for each older key a backup still names | nothing: a `retired` row is no rotation |

  Start finds a custody entry that has no row by listing the master key's entries, as `Erase all data` lists every entry the app made. A service whose custody is locked at start stays locked, and applies the table once custody opens. Every step is idempotent: one that finds its target already done moves on.

- A custody change, when a hardware key becomes available or the keychain becomes usable after the passphrase file (custody only moves up the ladder), runs the same six steps and the same table, except that step 1 mints no key: it gives the current key a new key id. The rows are re-wrapped so their headers name the new id, the new tier's entry is written and verified beside the old one before any row moves, and step 6 marks the old id `retired`: its entry on the old tier stays until the last backup sealed under that id ages out, and goes at once when no backup names it. The recovery envelope wraps the key's bytes whatever its id, so it stays as it is, and a custody change asks for nothing.
- Content keys are never regenerated. Each seals with AES-256-GCM and a random 96-bit nonce, and [NIST SP 800-38D](https://csrc.nist.gov/publications/detail/sp/800-38d/final) §8.3 bounds such a key at 2^32 seals, which one session's writes do not approach. The re-wrap leaves the content key as it is, and because its wrap AAD binds `key_version`, a wrapped blob cannot be replayed under another version or rolled back to an earlier wrap.
- Re-wrapping measured 42 µs a key (10,000 keys in 424.6 ms); steps 4 to 6, step 6's check included, stay within 2 s for 10,000 sessions.
- `rotate-keys` also mints a new identity key, and the old one is retired for good by the `runtimenode.key_rotated` statement the rotation records in the account's statement chain.
- A backup taken before a rotation is sealed with the old key, which stays in this machine's custody, `retired`, until the last backup sealed with it ages out (at most four weeks), so the machine that wrote the backup still opens it. On another computer it opens through the recovery envelope it carries, present when a recovery passphrase was set before it was taken, or through the old key id's iCloud Keychain item.
- There is no calendar rotation and no rotation on deletion: a purge deletes the session's own content key, and a rotation would delete nothing more.

**Backups, and a restore on another computer**:

- The master key is never in a backup. The key that opens the data day to day is bound to this machine's security chip where it has one, so it cannot leave the machine.
- Once the person sets `Recovery passphrase` on Runtime, the service wraps the master key under a key derived from that passphrase (Argon2id, with the passphrase file's parameters), and every backup after that carries the 98-byte wrapped envelope as its own file, which opens nothing alone. Nothing asks for the passphrase; it is stored nowhere, so a lost passphrase cannot be recovered. `Change…` wraps the key again, and backups taken before keep the envelope they were written with. A rotation makes the new key's envelope from the recovery passphrase it asks for. Every backup's manifest records the id of the master key it was sealed with, never the key.
- On a Mac, `Keep the backup key in iCloud Keychain`, off by default, puts the master key in the person's iCloud Keychain as one synchronizable data-protection keychain item labeled with that id, through `sidekicks-keywrap` under the app's own keychain access group. Turning it off deletes the item. A rotation or a custody change adds the new key id's item and keeps the old id's until the last backup sealed with it ages out.
- A restore on the machine that wrote the backup reads everything, because a rotation keeps the old key in custody until the last backup sealed with it ages out. The restore brings back the backup's `master_keys` table, whose `active` key opens the restored store; before the service starts on it, the restore adds a `retired` row for each other key in this machine's custody that a backup still names, so the keys the other backups need stay. On another computer the restore seeks the master key: on a Mac, iCloud Keychain first, with nothing asked; then the recovery passphrase against any backup in the folder that carries an envelope for that key. Once found, every backup sealed with that key opens, those taken before the passphrase was set included. A backup whose key neither way finds opens only on the computer that wrote it. A Windows computer is one machine whichever side runs its service, so a backup made on one side restores on the other as a same-machine restore.
- A session removed by `Delete old data` leaves the backup mirror at the next run and stays only in database copies taken before the delete, until they age out (at most four weeks), and the delete's confirm says so ([Spec-013 §Backup Policy](013-persistence-recovery-and-replay.md#backup-policy)).
- Backups the person makes with other tools: on macOS, exclude `~/Library/Keychains/` from Time Machine via `tmutil addexclusion`; on Linux with libsecret, exclude `~/.local/share/keyrings/` from home-directory backups. On Windows every entry's `CRED_PERSIST_LOCAL_MACHINE` keeps it out of File History and OneDrive Folder Backup roaming.

**Cross-reference to ADR-021**: [ADR-021](../decisions/021-cli-identity-key-storage-custody.md) records the same ladder — hardware wrap, keychain, passphrase file, refuse — for the machine's keys. The master key is the one key on it; every other daemon key except a tool server's sign-in items ([ADR-040](../decisions/040-mcp-credential-custody.md)) is sealed under the master key rather than holding a custody entry of its own, and the command line holds no key of its own, reaching the daemon on its machine through the socket.

**Resource budget**: one master-key read at each start and after each idle wipe, at most 100 ms and one short-lived helper process per read on macOS (measured: key made in 53.1 ms, unwrapped in 9.1 to 19.6 ms plus the helper's start; handle 284 bytes, wrapped master 125 bytes), one keychain read elsewhere, and one Argon2id derivation per unlock on the passphrase tier. The Windows TPM tier's cost is measured by its build task.

**Explicitly NOT claimed**:

- No HSM or FIPS 140-2 Level 3 hardware custody. Master key lives in general-purpose RAM while the service runs.
- No SGX, TrustZone, or equivalent trusted execution environment protection.
- The Secure Enclave wrap binds the master key to this Mac, not to the app: a second, different unsigned binary running as the same person unwrapped it (measured). It keeps a copied folder or disk image unreadable elsewhere; it does not stop code running as the same person on the same machine, which ADR-021 puts out of scope.
- No protection against a root-privileged attacker on the daemon host. If an attacker can read the daemon process's memory while the master key is unlocked, the master key is exposed.
- No protection against a weak passphrase on the passphrase-file tier or a weak recovery passphrase. Argon2id with OWASP 2026 parameters raises the cost of offline brute-force but does not prevent it for guessable passphrases.
- No crypto-agility for AEAD. XChaCha20-Poly1305 is fixed. Migration to a different AEAD requires re-wrapping every envelope.
- No master key shared across machines. Each machine has its own master key in its own custody; a person with several machines has one per machine.

> **Artifact-payload posture.** Artifact manifests and their CAS payloads (`artifact_manifests` + `artifact_payload_refs`) are work product published into the person's own session and held on the machine that ran it, which lists them on every linked device. No person and no method deletes a single artifact: a session's artifacts go only with the session, through `Delete old data` or `Erase all data`. Before Send, covering part of a staged picture replaces the staged file with its covered copy, so the uncovered copy never enters the session. The manifest's nullable `created_by` stamp stays for the manifest's lifetime as the record of who made the artifact. `session_events.content_payload` follows the same rule: an assistant's reply and a tool's result are work product produced into the session, sealed under the session's content key, and go with the session, at purge through `Delete old data`, which deletes that key first, or with the daemon master key through `Erase all data`. `pii_payload` on the same rows holds every word the person wrote and goes the same way ([§Erasure Paths](#erasure-paths) Path 1). `content_payload` and `pii_payload` partition one row's text by authorship.

> **User-reference posture.** A daemon-local SQLite column whose value is a bare `UserId` **referencing** the person — as distinct from a column carrying their content — is attribution, kept for its session's life under the same reading the `created_by` stamp above takes. The class comprises `interventions.admitting_principal_id` and `interventions.initiator_id` ([Spec-003](003-queue-steer-pause-resume.md)) and `approval_resolutions.approver_id` ([Spec-010](010-approvals-permissions-and-trust-boundaries.md)), each recording who authorized one durable act in the session. It goes with its session at purge through `Delete old data` and with the data folder on `Erase all data`; no act removes the reference alone, because the record that the act was authorized is the audit property the columns exist for. Only `admitting_principal_id` carries a map row above; the others are named here so the map's exhaustiveness claim reads correctly over the whole class rather than implying that unlisted siblings were overlooked. The Postgres analogue is not this posture: a control-plane user reference sits inside Path 2's inbound-FK closure and is hard-DELETEd or `SET NULL`ed there, because that closure is exhaustive over FK linkage by construction. These SQLite columns carry no FK to a Postgres table and are unreachable from it.

> **Account-plane posture.** The provider-account registry holds **no credential material of any kind** — no token, no refresh token, no API key, no session cookie. Credentials live inside each account's own credential home, owned and written by the provider's tooling, and the daemon brokers refresh without ever holding the values ([Spec-026 §Credential homes and the constructed environment](026-provider-accounts-and-credential-homes.md#credential-homes-and-the-constructed-environment), [Spec-026 §Credential-refresh brokering](026-provider-accounts-and-credential-homes.md#credential-refresh-brokering)). **That absolute is bounded in one place.** [ADR-028](../decisions/028-provider-credential-custody-posture.md) D2 authorizes the daemon to hold exactly one class of credential material — a vendor-minted non-interactive token, supplied on one write-only wire input. **It is not a row in any table**, so this map's table-keyed rows are complete as written: the value is kept only in the OS keychain, one entry keyed by account identity, opened with `{linux: {store: "secret-service"}}` and on Windows written by the Windows half at `CRED_PERSIST_LOCAL_MACHINE`; a token the keychain cannot take is refused with one line per cause (`locked`, `unavailable`) and stored nowhere else, and `provider_accounts` records only that an account's **observed** mode is the token mode — a label, not the material. The shredding obligation is stated here rather than left implicit: **removing an account registration MUST destroy that account's keychain entry** in the same operation, and `Erase all data` destroys every keychain entry the app made. A registry row removed while its sealed secret survived would leave live credential material on the machine with nothing left pointing at it — unattributable, unshreddable by any later request, and invisible to every audit this map supports. The token is a credential and not personal data, so no session's purge reaches it and it appears in no export; its lifecycle obligation is destruction-with-its-account, and that is where it belongs. The registry's remaining columns are the machine's own configuration rather than session content: the recorded residual is `credential_home_path`, a local filesystem path that on most machines embeds the operating-system account name, kept on the machine under the same reading as the provider-reported identity row above and going with the same registration. Nothing in the account plane is relayed off the machine or uploaded to the control plane; `Export all data` writes each account's name, provider and plan to `accounts.json`, with no credential.

The **PII Type** column above names what each bucket carries, not separate columns.

**Nothing is exported off the machine.** The app sends no telemetry and has no outbound telemetry sink: a crash report is built on the machine that crashed, stripped of personal data there, kept there and deleted with the diagnostic logs, and no workflow run is sent to an OpenTelemetry collector or any other exporter. Each provider's own telemetry export from the processes the daemon starts is received on one loopback port on this machine, read to price the requests a session's stream leaves out, and dropped; nothing of it is stored but the priced request.

## Data Retention and Deletion Policy

This section states end-to-end coverage across both storage tiers ([ADR-039](../decisions/039-kept-sessions-keep-their-provider-files.md)).

- **Retention**: A kept session holds its personal data until the person deletes it; nothing deletes a session by age, and background compaction never removes anything a person could see. Past `Keep sessions for` a finished session is eligible for deletion, and eligible is not deleted.
- **The provider's own files**: Claude Code's age sweep never reaches a kept session's files, because every Claude Code process the daemon starts carries `"cleanupPeriodDays": 36500` and every account home the daemon manages holds the same value. `Delete old data` removes a purged session's provider files from every account home it ran in, Codex's through `thread/delete`. What a provider writes into those homes and never reads back goes past `Keep diagnostic logs for`.
- **Session purge**: `Delete old data` is the one purge. In one transaction it overwrites the session's wrapped content key with zeros and deletes it before the session's rows, and checkpoints with `TRUNCATE` after commit ([§Ordering And Atomicity](#ordering-and-atomicity)); then it deletes its artifacts, capture folder, snapshot refs and base pins, a chat's managed workspace and the provider's files. Session states `purge_requested` and `purged` exist in the [Session Model](../domain/session-model.md) with transitions `archived -> purge_requested -> purged` and `closed -> purge_requested -> purged`, and the purge keeps the signed audit stub. How each data act is recorded in the event log is [Spec-005 §Data Acts](005-session-event-taxonomy-and-audit-log.md#data-acts).
- **Data export**: `Export all data` writes every session's events decrypted, the files, agent definitions, workflows and provider accounts without credentials, and the hosted account's own export when signed in. Export must run before `Erase all data`.
- **Erasure of everything on the machine**: `Erase all data` stops every run and shell, signs each provider account out, revokes this machine's hosted refresh family, destroys every custody copy of the master key and every keychain entry the app made, deletes the data folder with the account homes it created, and starts again empty ([§Erasure Paths](#erasure-paths) Path 1). A disk backup taken earlier keeps what it held.
- **Deletion of the hosted account**: `sidekicks delete-account` hard-deletes the account's control-plane rows across the `REFERENCES users(id)` inbound-FK closure, severs the surviving references that carry an independent retention basis through `ON DELETE SET NULL`, and signs this machine out ([§Erasure Paths](#erasure-paths) Path 2). It never erases a machine.
- **Backups**: a deleted session leaves the backup mirror at the next run and stays only in database copies taken before the delete, until they age out at four weeks; the delete's confirm says so.

## Erasure Paths

Erasing a person's data spans three independent storage paths, each carried out by its own act and each complete on its own: Path 1 is `Erase all data` on a machine, Path 2 is `sidekicks delete-account` on the control plane, and Path 3 is the diagnostic tier's own bound. Neither act triggers the other: deleting the account never erases a machine, and erasing a machine never deletes the account. A person who wants both runs both, on each machine they keep. `sidekicks delete-account` is the one way to delete the hosted account. A person who has lost every machine installs the command-line tool on another computer, runs `sidekicks sign-in`, confirms the sign-in with their passkey on the device-code page in the browser, and runs `sidekicks delete-account`. The [Hosted Account Deletion Runbook](../operations/hosted-account-deletion-runbook.md) runs Path 2 by hand as an operator break-glass procedure, only when that path is genuinely impossible (for example, the owner has no passkey left to verify a sign-in); it is never a second way to delete an account.

**The provider account registry.** The daemon-local `provider_accounts` registry holds no credential material ([§PII Data Map](#pii-data-map) account-plane posture). Its personal data is the provider-reported identity, which goes when the person removes the registration and with the data folder on `Erase all data`.

### Path 1 — SQLite `session_events.pii_payload` (crypto-shred)

**Mechanism.** `Erase all data`, from Settings › Runtime or `sidekicks erase-data`, confirms in place — `Erase everything this app keeps on this machine? Every session, file, sidekick, workflow and account sign-in goes, and the keys that could read them are destroyed. Project folders stay. Backups you made before keep their copy. This cannot be undone.`, with `Erase everything` and `Cancel` — and then, in order:

1. stops every run and shell, as Runtime's `Stop` does;
2. signs each provider account out through the provider's own sign-out: `claude auth logout` in each Claude Code account home, and `account/logout` on each Codex service;
3. revokes this machine's hosted refresh family, when signed in to the hosted account;
4. destroys the master key's hardware key where one exists, the custody entry of every key id in `master_keys`, every backup-key item in iCloud Keychain, and every keychain entry the app made (pasted tokens, workflow secrets, each tool server's sign-in, the web address's signing secret and the mail password);
5. deletes the data folder, the account homes it created included;
6. starts again empty, and the app opens as on first launch.

Destroying the master key is the crypto-shred: every row of `session_content_keys` is wrapped under it, and each session's content key seals both its `pii_payload` and its `content_payload`, so every body on the machine becomes unrecoverable even for bytes that survive in freed pages, before the folder itself is deleted. Each of those keys is random, never derived from a credential, so nothing that survives the erase can reconstruct one. `sidekicks erase-data` is refused while the service holds the data folder; on Windows its key destruction runs through the Windows half's one-shot verbs (§Daemon Master Key).

**Scope.** Everything the app keeps on this machine: the database, the data folder, the account homes the app created and every keychain entry it made. Project folders and the person's own provider folders stay. A disk backup taken earlier keeps what it held, and on another computer opens with the recovery passphrase that was set when it was taken; the erase claims no more than that. A single session's PII leaves earlier, with its rows and its content key, when the person deletes that session (§Retention Policy).

**Audit artifact.** None on the machine: an erase leaves no log to write into. The hosted account, when signed in, records the refresh family's revocation as an `account_audit` row.

### Path 2 — Postgres PII rows (hard DELETE)

**Mechanism.** `sidekicks delete-account`, over the control plane's `account.delete`, deletes the hosted account. It first revokes every refresh family the account holds, so each is written to the denylist, then runs Path 2 in one Postgres transaction, and signs this machine out. Path 2 is exhaustive over the complete `REFERENCES users(id)` inbound-foreign-key closure in [shared-postgres-schema.md](../architecture/schemas/shared-postgres-schema.md) — not only the PII-content columns in the [§PII Data Map](#pii-data-map) durable tier, but **every** Postgres row that links to the deleted account. Per-table disposition by retention basis:

- **Hard DELETE** (no independent retention basis): `users`, `identity_mappings` (Plan-016), `devices`, `runtime_nodes` and `trust_statements` (Plan-028 — the account's linked devices with their public keys and push addresses, its machines' registrations with their public keys and names, and the append-only signed chain of the account's trust statements; deleting them is safe at live-verification semantics, since every machine verifies the chain it keeps itself and no retained row re-verifies a signature by one of the account's keys after deletion), `webauthn_credentials` and `webauthn_challenges` (Plan-016 — enrolled passkeys and in-flight ceremony challenges; deleting them is safe at live-verification semantics, since a credential is verified at ceremony time and no retained row re-verifies one after deletion, and challenge rows self-expire within five minutes regardless), `account_audit` (Plan-016 — the account's audit rows, included in `account.export` and deleted with the account), `refresh_token_families` (Plan-016 — one row per live sign-in, holding its family's current token id; revoking a family deletes its row, so none remains once `account.delete` has revoked the account's families, and the `user_id` reference cascades), `revoked_token_families` (Plan-016 — the account's revoked refresh-token families: a refresh token has no expiry of its own, lasting until sign-out or revocation, so a revoked family's row stays for the account's life and goes with it; once the account and the machine keys its tokens are bound to are deleted, none of its tokens can be traded).
- **Not in the closure: push.** The control plane holds no notification queue, filter or notification-preferences table. A push is sealed on the machine to the receiving device's push key — HPKE with X-Wing, and [RFC 8291](https://www.rfc-editor.org/rfc/rfc8291) for Web Push — and the relay adds only the person's own APNs, FCM or VAPID credentials and holds nothing that opens a notice; each machine decides per device before it sends (the device's switch, its kind, the session's mute, and no push while an app window is in front on any of the person's devices except a workflow's Notify step, which always sends). A push is a delivery, not a fact of the session, and nothing about it is written to any session log.
- **Anonymize-with-security-survival via `ON DELETE SET NULL`**: `revoked_jtis`, the revoked access tokens — the user hard-DELETE auto-nulls `user_id`, severing the data-subject linkage, while the key (`jti`, the table PRIMARY KEY — **not** `user_id`) is untouched and the row stays denied until its natural `expires_at + 24h` reap, a margin past the access token's short lifetime, so deletion does not resurrect a revoked access token within its remaining validity window (the GDPR Art. 17(3) security/legal-obligation carve-out). A revoked family's row in `revoked_token_families` has no natural expiry to reap at, because a refresh token has none: it stays for the account's life and is hard-DELETEd with the account (above). The control plane writes `revoked_token_families` on every revocation — a device revoked, the person signing out, a spent refresh token presented again, and the account deleted — and `revoked_jtis` for an access token revoked before its expiry. The refresh endpoint checks the family, and the control plane and the relay check the token id, on every request, each by primary key.

**FK-safety (the anonymize mechanism is `ON DELETE SET NULL`, not a tombstone row).** The one anonymize-class FK, `revoked_jtis.user_id`, references `users(id)` and must survive the hard-DELETE of the user it references. Because deletion hard-DELETEs the `users` row, an in-place rewrite to a non-user "tombstone identifier" would violate the FK, and a _reserved tombstone user row_ would leave a standing live identity on every surviving row that no later reader could tell apart from a real registration. The FK-safe mechanism is therefore `ON DELETE SET NULL`, and the FK is **nullable + `ON DELETE SET NULL`** in the control plane's one schema, where the control-plane account work adds the denylist ([Plan-016](../plans/016-identity-and-user-state.md) Phase 5), so the user hard-DELETE auto-nulls the reference DB-side; the closure is verifiable against [shared-postgres-schema.md](../architecture/schemas/shared-postgres-schema.md). The `jti` key survives the null because it is the PRIMARY KEY, not the FK. `revoked_token_families` is not in this class: its rows are hard-DELETEd with the account.

**Scope.** Exhaustive over the `REFERENCES users(id)` inbound-FK closure named in the Mechanism above — the closure is read from [shared-postgres-schema.md](../architecture/schemas/shared-postgres-schema.md), so it cannot drift behind a hand-maintained list. If any row fails its DELETE (foreign-key constraint, row lock, connection failure), the transaction rolls back, `account.delete` reports the failure, and no row is deleted.

**Audit artifact.** No event-log row is emitted per Postgres table. The control plane appends an `account_audit` row for the deletion request in the same transaction as the request; the account's `account_audit` rows and revoked families are then deleted with the account, and its revoked access-token entries are what survive of it, until their reap. Nothing is written to any machine's event log.

### Path 3 — Bounded-retention diagnostic buckets (age bound and erase)

**Mechanism.** Each diagnostic table listed in the [§PII Data Map](#pii-data-map) bounded-retention tier (`driver_raw_events`, `command_output`, `tool_traces`) drops its rows past `Keep diagnostic logs for`, 7 days by default, on the service's one scheduler; the same bound drops what a provider writes into each account home and never reads back for a session. `Erase all data` deletes every table with the data folder. There is no per-person flush: the tier belongs to the one person whose machine it is, and it never outlives its bound.

The daemon MAY retain summary-only variants that never contained PII by construction per [Spec-018 §Required Behavior](018-observability-and-failure-recovery.md#required-behavior). Summary-only variants hold no personal data by construction, so the diagnostic bound does not apply to them.

**Scope.** Every row in the bounded-retention diagnostic tier, and the provider's own non-session files in each account home the app manages.

**Audit artifact.** None; a dropped diagnostic row is not a session fact.

### Ordering And Atomicity

Each act orders its own steps; no act spans two stores.

- **Session purge: key first.** The session's wrapped content key is overwritten with zeros in place and its row deleted before the session's rows, in one SQLite transaction, and the write-ahead log is checkpointed with `TRUNCATE` once it commits, so no moment exists in which the rows are gone and the key that reads their freed pages survives, and no freed page keeps the wrapped key. The artifacts, the capture folder, the managed workspace and the provider's files follow the transaction; a failure among them leaves the session `purge_requested` ([§Fallback Behavior](#fallback-behavior)).
- **Erase: work stops before keys go, and keys go before files.** Runs and shells stop first so nothing writes during the erase; provider sign-out and the hosted refresh family's revocation run while the service can still reach them; the master key's custody is destroyed before the data folder is deleted, so every byte the deletion leaves behind is already unreadable.
- **Account deletion: revocation before rows.** The account's refresh families are revoked, and so written to the denylist, before Path 2's transaction deletes the account's rows, so no token outlives the account within its validity window.

Path 2 runs in one Postgres transaction and is idempotent: a DELETE of an already-deleted row affects zero rows. The erase is idempotent in the same sense: a step that finds its target already gone moves on.

## Example Flows

- `Example: A session was archived 91 days ago. It is eligible for deletion and nothing has removed it. The person opens Settings › Runtime and presses Delete old data, which confirms "Delete 14 archived sessions and their logs? Each chat's session workspace goes too; files in project folders stay. This cannot be undone." The purge deletes each session's content key, then its rows, keeping the audit stub, then its capture folder, its managed workspace and its Claude Code conversation file in every account home it ran in.`
- `Example: A Claude Code session last used 400 days ago is resumed. Its conversation file is still in the account home, because every Claude Code process the daemon starts carries "cleanupPeriodDays": 36500, and the session continues where it stopped.`
- `Example: Before handing a laptop back, the person presses Export… under Export all data and writes sidekicks-export-2026-09-24 to an external drive, then presses Erase all data and Erase everything. The service stops its work, signs each provider account out, destroys its keys and data, and starts again empty. Project folders are untouched.`
- `Example: The person runs sidekicks delete-account. The control plane revokes the account's refresh families, hard-deletes the account's rows, its revoked families among them, and nulls the user reference on the revoked access-token entries that survive to their reap, and this machine is signed out. Its sessions stay on it until the person deletes them or erases the machine.`

## Implementation Notes

- Crypto-shredding and every data act ship in V1, each built by the task §Interfaces And Contracts names: the session purge with its key-first order, `Export all data`, `Erase all data`, `sidekicks rotate-keys`, `sidekicks delete-account`, and the token denylist written on every revocation. The `pii_payload` encrypted column on `session_events`, `interventions` and `queue_items`, the `session_content_keys` table and the `master_keys` table ship in the initial schema.
- The data map of PII fields should be maintained as a living document alongside the data architecture.
- AES-256-GCM key generation must use a cryptographically secure random source. Content keys are never regenerated; the master key rotates on `sidekicks rotate-keys` in the six steps of §Daemon Master Key and re-wraps them.

## Pitfalls To Avoid

- Storing PII and non-PII in the same column, making crypto-shredding impossible without destroying audit data
- Assuming `DELETE` on Postgres is sufficient for GDPR compliance without also addressing the SQLite event log
- Allowing data export after key deletion (the export must happen first)
- Treating `purge_requested` as a terminal state instead of a transient processing state
- Shipping without the `pii_payload` column

## Acceptance Criteria

- [ ] Session state model includes `purge_requested` and `purged` states with correct transitions, including the irreversibility invariant (a `purged` session cannot transition to any other state).
- [ ] No session is deleted except by `Delete old data`: a finished session past `Keep sessions for` stays readable and resumable until the person deletes it.
- [ ] A Claude Code conversation file older than Claude Code's default cleanup period survives a new process's start in an account home the daemon manages, including under a repository whose own `.claude/settings.json` sets `cleanupPeriodDays` to 1; a managed value below 36500 raises `settings_ignored`.
- [ ] `Delete old data` overwrites each session's wrapped content key with zeros and deletes it before its rows in one transaction, checkpoints with `TRUNCATE` after commit, keeps the audit stub, and removes the session's capture folder, snapshot refs, base pins, managed workspace, and the provider's files from every account home it ran in (Codex through `thread/delete`); a terminal session's conversation in the person's own Codex folder stays.
- [ ] The diagnostic tier and the provider's non-session files in each account home drop past `Keep diagnostic logs for`; step data drops past `Keep run data for`; no other data drops on its own.
- [ ] V1 schema includes the `pii_payload` (encrypted) column separate from `payload` (plaintext) on `session_events`, `interventions` and `queue_items`, sealed under the session's content key with the `ais.session-pii.v1` label, and the `session_content_keys` and `master_keys` tables; no per-user key table exists.
- [ ] After `Delete old data`, a byte scan of the database file, its freed pages and its write-ahead log finds no plaintext of a deleted session's typed messages, queue item bodies or steer text, and no copy of its wrapped content key.
- [ ] `Export all data` writes every session's events decrypted with the files, agent definitions, workflows, provider accounts and the hosted account's export, and the folder holds no settings value, credential, token, workflow secret, key or diagnostic log.
- [ ] `Erase all data` runs its six steps in order, after which no custody copy of the master key and no keychain entry the app made remains, the data folder is gone, project folders are untouched, and the app opens as on first launch.
- [ ] `sidekicks rotate-keys` runs the six steps of §Daemon Master Key: with the process killed after each step and during step 4, the next start resumes or rolls back as its table says, and every row opens under the key its header names. No blob is committed under a key whose custody entry was not first written and verified, and the old key's custody entry is deleted only after no header names it and the last backup sealed with it has aged out.
- [ ] A custody change runs the same steps with the current key under a new key id, and a backup taken before it still restores on another computer.
- [ ] The master key opens with no person present on a machine with a security chip or a keychain; on the passphrase-file tier the service stays locked until `daemon.unlock`; with no tier the service refuses to start and says why.
- [ ] `sidekicks delete-account` revokes the account's refresh families, hard-deletes every row of the `REFERENCES users(id)` closure, the account's `refresh_token_families` and `revoked_token_families` rows included, leaves every `revoked_jtis` row with its key and `user_id` null until its `expires_at + 24h` reap, and leaves the machine's local data untouched.
- [ ] The anonymize-class FK `revoked_jtis.user_id` is nullable + `ON DELETE SET NULL` in the control plane's one schema.
