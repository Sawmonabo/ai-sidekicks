## Purpose

This spec defines V1 feature #18 ([ADR-015 §Decision](../decisions/015-v1-feature-scope-definition.md#decision)): how the local runtime daemon configures, governs, and observes **MCP servers** attached to the two provider CLIs (`claude` and `codex`). Each provider is an MCP client of its own. The daemon runs one MCP client of its own as well: it holds the real connection for every server it fronts — every server a Codex session reaches, and on both providers a server that demands proof-of-possession tokens — lists and reads a server's prompts for Codex, and serves the workflow MCP-tool step. What the daemon owns is the **governance layer** above those connections:

1. A **unified server inventory** — one normalized read model across both providers' divergent config surfaces.
2. **Configuration mutation** — add / update / remove / enable / disable servers at every scope on both providers, through each provider's own write mechanism where one exists and, where none does, through a format-preserving edit written only while the file is as the daemon last read it; never by blind config-file rewriting.
3. A **trust store** — trust granted by the person, config-hash-bound, per server binding, untrusted by default, auto-revoked on config drift. This is the trusted-server store, managed by the person, that [ADR-015 §References](../decisions/015-v1-feature-scope-definition.md#references) binds MCP annotation trust to: the MCP spec requires clients to treat tool annotations as untrusted unless the server is trusted, and trust classification MUST bind on this store, never on annotation self-claims.
4. **Tool-level overrides** — per-(server, tool) enable/disable, approval-mode, and idempotency-class assignment, feeding the [Spec-004](./004-provider-driver-contract-and-capabilities.md) tool-metadata resolution layer.
5. **OAuth sign-in** — one daemon-held sign-in per server that needs one, used by both providers and by the daemon's own client, held and removed as [ADR-040](../decisions/040-mcp-credential-custody.md) records.
6. **Status observation** — normalizing both providers' server-status feeds onto the Spec-004 `McpServerStatus` enum and the session event timeline.
7. **Audit** — every governance mutation and status transition emits a canonical event in the `mcp_governance` category ([Spec-005 §MCP Governance (`mcp_governance`)](./005-session-event-taxonomy-and-audit-log.md#mcp-governance-mcp_governance).

## Scope

- The `mcp.*` IPC operation namespace on the daemon control surface, and the session operations over a session's own servers (`session.mcpServerList`, `session.mcpServerUpdate`, `session.mcpResourceList`).
- Normalized server inventory merging provider-declared config, live provider status, the daemon trust store, and the daemon override store.
- Provider-specific mutation engines at every scope: Claude Code's `claude mcp add-json --scope` writes plus live reconcile; the Codex user-config CRUD + reload pair, the daemon's own format-preserving edit of a project's `.codex/config.toml`, and the emulated Codex `local` scope.
- The `mcp_server_trust`, `mcp_tool_overrides`, `mcp_mutation_receipts`, and `mcp_server_admitted_clients` SQLite tables (daemon-local, node-scoped).
- Cedar-gated authorization for every governance mutation, open to this machine's own client or any linked device, and no session.
- The `mcp.*` event types and their payloads, session binding, and sanitization rules.
- The daemon's own OAuth sign-in per server, its custody under [ADR-040](../decisions/040-mcp-credential-custody.md), and sign-out.
- The daemon's own MCP client and the route that fronts servers for Codex (and for a proof-of-possession server on Claude Code), with a long call moving to the background on both providers.
- A search of the public MCP Registry that fills the declaration form.

## Non-Goals

- **The daemon runs one MCP client of its own; a provider's own connections stay the provider's.** The client holds the real connection for every server the daemon fronts — every server a Codex session reaches, and on Claude Code only a server that demands proof-of-possession tokens (§Long tool calls and the fronted route) — and adds no governance of its own: the route applies the same trust, overrides and approval a direct connection would. A server a provider reaches directly stays that provider's connection end to end. The daemon separately **hosts** an MCP server of its own: the callback-tool host of [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior), through which daemon-authored tools reach a run. That host sits outside this spec's governance model because the daemon authors it rather than the person declaring it: it is never trusted, drift-evaluated, or override-governed, and its tools are governed by the specs that author them (Cedar authorization and the spec's own opt-in), not by MCP trust.
- **No credential custody beyond [ADR-040](../decisions/040-mcp-credential-custody.md).** The daemon holds MCP-server credentials exactly as that record states: one sign-in per server, the refresh token and any proof-of-possession signing key in the operating system's credential store under the daemon's own items, and access tokens only for provider processes it launched, through each provider's own header helper, and for its own client. It never reads or renews a sign-in the person's own Claude Code or Codex holds, and no credential reaches an event, error, log, read model, wire payload, or the renderer. Credential-bearing values in provider-owned config (env-var and header values) are handled **transiently in memory** only — by canonicalization + keyed hashing (§Trust Governance), by the provider's own write mechanism, by the `${VAR}` expansion of a Claude Code session's server set, and by the fronted route's connection — then discarded; they never reach storage, events, errors, logs, or any read model (§Implementation Notes — transient-secret handling). The node-local provider-account plane is [ADR-028](../decisions/028-provider-credential-custody-posture.md)'s and nothing here widens it.
- **No config-store ownership.** Provider config files (`~/.claude.json` scopes, `$CODEX_HOME/config.toml`, project-local `.codex/config.toml`, `.mcp.json`) remain provider-owned and are the source of truth the daemon observes, not a mirror it maintains. The daemon writes them through each provider's own mechanism where one exists — `claude mcp add-json --scope` on Claude Code, `config/value/write` / `config/batchWrite` for the Codex user file — and where none exists, a project's `.codex/config.toml`, through a format-preserving edit that keeps the file's comments and layout, is written only while the file is as the daemon last read it, and is read back through `config/read` before it counts (§Configuration Mutation).
- **No installing on the person's behalf.** A search of the public MCP Registry fills the declaration form; the person still adds the server and types every secret value, a server found there starts untrusted like any other, and the daemon keeps nothing from a search past the page.
- **No governance by a caller who does not own the node.** V1 authorizes exactly the node's owner (the caller-owns-the-node model — §Authorization), reachable from any of that owner's linked devices; a caller who does not own the node is refused outright, never queued. Where the request arrived from is not an input to that decision — [Spec-028 §Parity by construction](./028-remote-control.md#parity-by-construction) makes a method that works on the machine and not from a linked device a transport defect, so a transport-origin test here would be one.
- **No session-scoped permission-matrix extension.** Governance belongs to this machine's own client or any linked device, and no session, deliberately outside the session permission matrix ([Security Architecture §Permission Matrix](../architecture/security-architecture.md#permission-matrix)). The session-facing MCP surfaces are a session's own server list with its per-session switch, which only narrows what governance allows (§A session's own tool servers), the resource pick and the server prompts in the session's command list, and a server's request for input, which becomes the session's question card — none of them a governance mutation.

## Required Behavior

### Provider Capability Model

Both providers expose MCP configuration, status, and auth surfaces, but through structurally different mechanisms. Per the capability-parity principle (all provider capabilities integrate at V1; asymmetries are normalized, emulated, or degraded honestly — never silently dropped), the daemon binds to each mechanism natively and grades what each application path can deliver:

| Capability | Claude Code mechanism | Codex mechanism |
| --- | --- | --- |
| Declare servers for a session | `--strict-mcp-config`, so nothing the project or the account configures loads by itself; the session's servers sent with the `mcp_set_servers` control request right after start (about 0.1 s) and again after each resume, because the set lives only in the process's memory; only the daemon's own tool entry rides `--mcp-config`, which `mcp_set_servers` leaves in place | The conversation's own configuration at `thread/start`: the whole `mcp_servers` table, which replaces the service's table for that conversation, each server a `url` entry on the daemon's route under its own name and each enabled or not (§Long tool calls and the fronted route) |
| Change a live session's server set | Another full-set `mcp_set_servers` call, applied from the next turn — SDK `setMcpServers(servers)` returning `{added, removed, errors}`; streaming-input mode only; SDK floor `0.3.166` | The conversation's per-server `enabled` flag, reaching it at its next turn where the provider honors it |
| Mutate durable config | `claude mcp add-json` / `claude mcp remove` with `--scope user`, `--scope project` (run from the project root; writes `<project>/.mcp.json`) or `--scope local` (writes the project's entry in `~/.claude.json`) — the provider's own store stays the durable home; the daemon never rewrites those bytes itself | `user`: `config/value/write` / `config/batchWrite` with `expected_version` optimistic concurrency on `$CODEX_HOME/config.toml`; `project`: the daemon's own format-preserving edit of `<project>/.codex/config.toml`, read back with `config/read`; `local`: emulated, an entry in the user file with `enabled = false` switched on per conversation in that project's sessions |
| Server status | Init census `mcp_servers[]` + `mcpServerStatus()` SDK query; `claude mcp list` glyphs (human CLI, no `--json`) | For a fronted server, the daemon's own client's connection to it; `mcpServerStatus/list` (ephemeral, cursored, `thread_id`-scopable) + `mcpServer/startupStatus/updated` notifications for the conversation's own leg |
| Per-server reconnect | SDK `reconnectMcpServer()` | The daemon's client reconnecting a fronted server; `mcpServer/refresh` |
| Enable/disable | The daemon's per-server enabled overlay decides whether the server is in the set sent with `mcp_set_servers` (Claude Code's configuration has no enabled field, and removal would destroy the declaration); `mcp_toggle` (`toggleMcpServer()`) is never used, because it saves the switch for the whole project and leaves the server running | `enabled` field write + reload; per conversation, the `enabled` flag in the `thread/start` table |
| Tool allow/deny + approval mode | Daemon-enforced (no native per-tool config field; the daemon's approval layer enforces overrides) | Native config fields: `enabled_tools` (allow), `disabled_tools` (deny, applied after allow), `default_tools_approval_mode` (`auto`\|`prompt`\|`writes`\|`approve`), `tools.<t>.approval_mode`; for a fronted server the daemon applies them on its route with the session's permission level |
| OAuth sign-in | The daemon's own sign-in (§OAuth Orchestration), handed to the process through `headersHelper`; for a server that admits only Claude Code's client, Claude Code's own flow (the `mcp_authenticate` control request) run in a credential folder the daemon makes for that sign-in | The daemon's own sign-in, handed to the process through `http_headers_helper` and used by the daemon's client for every fronted server; for a server that admits only Codex's client, `mcpServer/oauth/login` run in a throwaway home with `mcp_oauth_credentials_store = "file"` |
| Long tool call | `CLAUDE_AUTO_BACKGROUND_TASKS=1`: a call still running after 120 s, or one running when a message arrives, moves to the background; Claude Code runs MCP Tasks itself | No MCP Tasks and no backgrounding; the daemon's route answers a long call with a background handle and delivers the result (§Long tool calls and the fronted route) |
| Prompts | Claude Code lists a server's prompts itself | Codex never asks a server for its prompts; the daemon's client lists and reads them on the daemon's sign-in |
| Required-server gating | Not native; daemon surfaces failed servers via status | `required = true` ⇒ `thread/start` / `thread/resume` FAIL if the server cannot initialize |

Every mutation response MUST carry an **application grade** — `live_reconcile` (applied to the running session's live server set), `user_config_write` (persisted to the provider's own config store, effective for subsequent runs/threads), `next_run` (daemon-recorded governance state applied to the next session's server set), or `daemon_enforced` (enforced immediately at the daemon's own decision layer) — so callers know _when and where_ the change takes effect. Degradation is honest and typed, never silent: a Claude mutation that cannot reconcile live succeeds with the grade its durable path actually achieved, not an error and not a fake `live_reconcile`.

### Unified Inventory

- The daemon MUST expose one normalized inventory (`mcp.list` / `mcp.get`) merging four sources per server binding: (1) provider-declared configuration (parsed from the provider's own config surfaces), (2) live provider status normalized onto `McpServerStatus` (`unknown | starting | connected | needs-auth | failed` per [Spec-004](./004-provider-driver-contract-and-capabilities.md) — the api-payload `McpServerStatus` union), (3) the daemon trust row, (4) the daemon tool-override rows. Each entry carries a **redacted normalized config view** (`McpServerConfigView`) — transport, command/args, the **query-redacted URL** (scheme + host + path; the query component is credential-equivalent write-only material — a `?api_key=…` credential passes no-userinfo validation, so query **values** never round-trip and the view serves the query **parameter names** instead, the same names-not-values discipline as env vars and headers), timeouts, `required`, `bearerTokenEnvVar`, the Codex auth references (`envHttpHeaders` — a header-name → env-var-**name** map — plus `oauthScopes` and `oauthResource`), and the **names** of env vars and headers, never their values — so `mcp.get` can read back what `mcp.upsertServer` wrote and the person can inspect provider state without the daemon ever serving credential material (`command`/`args` are process-visible strings the person authors, the same residual class as the identifiers in §Status Observation and Events; the full URL still feeds the base-config hash, so a query-string credential rotation drifts the hash like any semantic change).
- Server identity is the scope-qualified **binding** `(provider, scope, scopeRef, serverName)` — scope is `user` (Claude user scope in `~/.claude.json`; Codex `$CODEX_HOME/config.toml`), `project` (Claude `.mcp.json`; Codex `.codex/config.toml` in the project; `scopeRef` = the canonical project root), or `local` (Claude's project-keyed private scope; on Codex the emulated scope — an entry in the user file switched on per conversation in that project's sessions, its name unique across that file; `scopeRef` = the canonical project root; `scopeRef` is the empty string for `user`). Two scopes legitimately declaring the same `serverName` with different configurations are **distinct bindings** with independent status, trust rows, and overrides — collapsing them would make one scope's config drift-revoke trust granted to the other and bleed overrides across configurations. The inventory MUST NOT merge same-named servers across providers or across scopes into one logical entry — a merge would launder trust. Project/local entries additionally serve `scopeRefDigest` — the keyed audit-ref digest event payloads carry (§Status Observation and Events) — so governance events join to inventory entries without raw paths ever entering the audit trail.
- Same-name shadowing across scopes is surfaced, not resolved away: both bindings appear in the inventory, and the provider's own scope precedence decides which one a session gets. Each entry carries `effectiveInRuns` — whether that binding reaches provider runs: `true` for every scope on both providers, except a `project` binding the daemon did not write (one that came with the repository), which reads `false` until the person trusts it and again after a drift auto-revoke until it is trusted again (§Trust Governance).
- Provider states outside the normalized enum map deterministically: Claude `pending` → `starting`; Claude `disabled` → `enabled: false` on the inventory entry with status from the last observation (or `unknown`); absence of any status source → `unknown`, honestly. Provider status feeds report server names, not bindings; the daemon MUST attribute each observation to the binding that is effective for the observing context (the set the daemon sent that session). For a server the daemon fronts, its own client holds the connection, so that client's connection is the observation; and because a server a provider reaches on a header helper reports `authStatus: unknown` on Codex, a server whose sign-in the daemon holds reads `needs-auth` from the daemon's own sign-in state.
- After the background service moves between Windows and a WSL distribution, a server whose command or arguments name a program on the side it left is kept as it was and reads `failed`, its entry carrying `failedReason: commandNotRunnable`; a bare command name such as `npx` is looked up on the new side. This is one member on the entry, not a new status.
- A config binding and a **live provider leg** are different grains: one binding can back several concurrent sessions' connections at once, and the Plan-004 status seam keys every session-feed observation by the runtime-binding leg (`sessionId` + the Plan-004 `bindingId`). The inventory MUST NOT collapse divergent leg states into one overwritten scalar: each entry exposes the per-leg observations (`legs[]` — leg identity, status, `observedAt`) alongside a deterministic top-level aggregate `status` — the most severe current live-leg status under the fixed severity order `failed > needs-auth > unknown > starting > connected` (`unknown` is a valid live-leg status — a leg whose observation source is lost; lost observability outranks states known healthy, but never a concrete failure), falling back to the newest node-probe observation when no live leg exists, and to `unknown` when there is no observation source at all. Legs are **live-session observations with a bounded lifecycle**: when a leg's backing runtime binding closes (session end, driver exit), the daemon retires the leg and recomputes the aggregate — a terminated session's last observation never pins the aggregate (a `failed` leg of a closed session does not hold the server at `failed` while every live session is `connected`); with no live legs remaining, the aggregate falls back per the order above.
- First observation of a binding the trust store has never seen MUST upsert an untrusted trust row (`trusted = 0`) — observation creates the governance anchor; it never creates trust.

### Configuration Mutation

- Mutations (`mcp.upsertServer`, `mcp.removeServer`, `mcp.setEnabled`) target a binding and MUST route through the mechanism for its provider and scope, per the capability table above. `mcp.upsertServer` and `mcp.removeServer` take `scope` (`user` | `project` | `local`) and `scopeRef` (the project root) on both providers, and every scope is writable on both. **Upserts are read-modify-write over the provider's own declaration**: provider fields the normalized input does not model — or does not carry — are preserved, never erased (Codex user writes are field-granular `config/value` paths touching only carried fields; the project-file edit changes only that server's own table; the regenerated Claude declaration starts from the observed current one), so a typed read/edit round-trip can never silently destroy provider configuration outside the governed surface.
- **Scope refusal is narrow.** `mcp.config_scope_unsupported` fires only for what no mechanism reaches: an `enabled` or `approvalMode` override facet on a Codex `project` binding, which would have to be written into the repository's own file on the person's behalf; the refusal's guidance names the file to edit (§Tool-Level Overrides). Every other operation applies to a binding at any scope.
- **A running session picks up a change without a restart, with one exception.** After a write the daemon sends Claude Code the reload request, so hooks, the tool-server file, definitions and output styles are live for the session's next turn; on the headless path that request does not apply a change to a plugin's tool server, so such a change lands at the provider's next start and the session's flow row says one is waiting. On Codex a skill is live at once, and a new or edited definition needs the lead's conversation forked on the running server with its history intact, the flow row reading that definitions were reloaded.
- **Validation precedes commitment.** Schema validation and every check that can fail the mutation outright run **before** the durable leg commits — `mcp.config_invalid` is exclusively a pre-commit refusal. Once the durable leg has committed, the mutation never converts to a thrown error: later per-leg live failures are reported inside the successful response (below), so a caller can never be induced to retry a mutation that already committed.
- **Claude, durable leg (unconditional):** every `mcp.upsertServer` / `mcp.removeServer` persists to the provider's own store at the binding's scope via Claude Code's own command (`claude mcp add-json <name> <json> --scope <scope>` / `claude mcp remove <name> --scope <scope>`, a `project` or `local` write run with the project root as the working folder) **before** the mutation is acknowledged — an acknowledged mutation survives daemon restart because the provider's store, not daemon memory, is the durable home. The daemon MUST verify the write took effect (re-read via `claude mcp get` / observation of that scope) before emitting the config event.
- **Claude, live leg (opportunistic):** in a streaming-input session (the live leg is selected by the outcome of the daemon's own full-desired-set `setMcpServers` call, never by a version comparison and never by a driver-side probe: Spec-004 declares this flag non-probeable because an empty-set probe would clear the session's servers, so the first full-set send **is** the detection and its refusal selects the fallback; the SDK floor and streaming-input mode remain reachability preconditions), the daemon additionally applies the mutation live via `setMcpServers` and MUST reconcile the returned `{added, removed, errors}` against the requested delta. The call replaces the set the daemon last sent and leaves in place only what `--mcp-config` passed, which is the daemon's own tool entry; a plugin's servers are kept out by `--strict-mcp-config` and sent by the daemon like any other server switched on for the session — so the daemon MUST always send the full desired set, never a delta. The response grade reports the most immediate application achieved: `live_reconcile` when every attempted live leg applied (the durable leg having also completed), `user_config_write` otherwise.
- **Partial outcomes are typed, never masked.** Mutation responses carry `liveResults[]` — one entry per attempted live leg (`sessionId` + the Plan-004 runtime-binding leg key) with `outcome: 'applied' | 'failed'` and a sanitized per-leg error code on failure — so a durable-success/live-failure outcome is a **successful response** reporting `applied: 'user_config_write'` plus the failing legs, never a blanket success that hides the live failure and never an error that invites an unsafe retry of a committed write.
- **Claude, enabled overlay:** `mcp.setEnabled` for a Claude binding records the daemon's per-server enabled overlay (Claude Code's configuration has no enabled field; removal would destroy the declaration). The overlay decides whether the server is in the set each session is sent: at the next session start (grade `next_run`), and in running sessions through the next full-set `mcp_set_servers` call (grade `live_reconcile` when every attempted leg applied). `mcp_toggle` is never used: it saves the switch for the whole project, so later sessions start with the server off, and it leaves the server running.
- **Codex, `user`:** the daemon writes user-scope config via `config/batchWrite` (multi-field mutations MUST be batched — one version check, one reload) with `expected_version` from the immediately-preceding `config/read`; on `configVersionConflict` the daemon MUST re-read and retry exactly once, then surface `mcp.config_write_conflict`. After a successful write the daemon MUST trigger `config/mcpServer/reload` (or per-server `mcpServer/refresh` when scoped to one server). Grade `user_config_write`.
- **Codex, `project`:** Codex accepts config writes to the user file only, so the daemon edits `<project>/.codex/config.toml` itself, with a format-preserving TOML edit that keeps the file's comments and layout. The edit is written to a temporary file and renamed into place only if the file still hashes to what the daemon last read — otherwise `mcp.config_write_conflict`, nothing written — then read back with `config/read {cwd, includeLayers}`, whose project layer must list the server, and followed by `config/mcpServer/reload`. Grade `user_config_write`.
- **Codex, `local`:** Codex has no private per-project layer, so the daemon emulates one: it writes the server into the user file through `config/value/write` with `enabled = false`, and switches it on with the conversation's `enabled` flag at `thread/start` in each session whose project is that one. The name must be unique across the user file; a clash is refused with `mcp.config_invalid` before anything is written, naming the project that holds the other one. The daemon keeps one governance row per emulated binding and removes it with the server. Plain `codex` shows such an entry as switched off in every folder.
- **A `project` declaration carries names only.** That file travels with the repository, so it takes environment-variable and header **names** and no values: a value in any value field is refused with `mcp.config_invalid` before anything is written. The server reads the value from the environment the provider starts in. On Codex, `env_vars`, `env_http_headers` and `bearer_token_env_var` name the variables and Codex reads them itself. On Claude Code the file holds `${VAR}` or `${VAR:-default}`; because a session's servers arrive through the daemon's own `mcp_set_servers` call rather than Claude Code's load of `.mcp.json`, the daemon expands them from the session's spawn environment before sending and holds the expanded value only for that call.
- **One change on the wire.** Each write, at any scope, is one governed mutation: the provider write, the recomputed base-config hash and `mcp.server_config_changed` commit together, so a server saved through the MCP servers page never trips the drift gate and never loses its trust to its own save.
- Every applied mutation MUST emit `mcp.server_config_changed` with the binding identity, change kind, application grade, and post-change config hash — except removals, whose payload carries `previousConfigHash` and no `configHash` (there is no post-removal config to hash; see the payload contract). The payload MUST NOT include config values (env vars, headers, URLs with embedded credentials, tokens).

### Trust Governance

- Trust is per binding `(provider, scope, scopeRef, serverName)`, granted and revoked only from this machine's own client or any linked device, and never from a session, via `mcp.setTrust`, Cedar-gated. Same-named bindings in different scopes carry independent trust — trust granted to the user-scope configuration never covers a project-scope configuration of the same name.
- A trust grant MUST bind to the binding's current **base-config hash**: `b3:`-prefixed BLAKE3 in **keyed mode** — the key is the binding's **config-hash subkey**, derived from the daemon-held MCP governance master key via BLAKE3 keyed-PRF over a purpose tag plus the canonical binding identity (32-byte key material the database holds only **sealed under the daemon master key** — §Implementation Notes; deterministic, so the subkey is stable for the binding's life without storing any key beside the digest) — over the RFC 8785 JCS canonicalization of the normalized server config (the daemon's one canonicalizer; keying is deliberate: the canonical input includes credential-bearing env-var and header **values** so their drift is detected, and the non-colocated per-binding key keeps the resulting hash — which travels in events, inventory reads, and the trust row itself — from being an offline-brute-forceable digest of low-entropy secrets even for an attacker holding the database file), computed **excluding the daemon-managed override-projection fields** (`enabled_tools` / `disabled_tools` / `tools.<t>.approval_mode` — the fields the daemon itself materializes for governed tool overrides, which carry their own Cedar-gated audit trail in the override store). Without the exclusion, the daemon's own governed override write would change the hash and revoke the very trust that authorized it. **The exclusion is hash-scope only, never drift-scope**: every drift evaluation on a trusted binding additionally reconciles the observed values of these fields against the **expected native state** — the binding's preserved **native-field baseline** overlaid with its materialized override facets. The baseline (the trust row's `native_tool_baseline_json`) is snapshotted from the observed native values at trust grant or at the binding's first facet materialization, whichever comes first — never silently refreshed while held, dropped only once the binding is untrusted with no materialized facets — and is what makes the expected state well-defined for the _ungoverned portions_ of these shared fields (the person's own pre-existing `enabled_tools` entries) alongside the governed ones. Any divergence is out-of-band tool-governance drift, auto-revoking exactly like base-config drift; portions governed by materialized facets are re-asserted to the expected state (`mcp.tool_override_changed` per re-asserted facet) while ungoverned portions adopt the observed values — revoke, never undo the person's own config, mirroring base-config drift semantics. A hand-edited `enabled_tools` broadening or approval-mode weakening therefore can never ride into a run under an unchanged base hash. (An untrusted binding's native tool fields are ungoverned provider config — observed and served in the config view, never trust-laundered.) Trust means "the person trusts _this_ configuration", not the name.
- On any observation where a trusted binding's current base-config hash differs from the bound hash, the daemon MUST auto-revoke trust (`trusted = 0`, `revoked_reason = 'config_drift'`) before the changed config is used, and emit `mcp.server_trust_changed` with `reason: 'config_drift'`. Re-trusting after drift is an explicit act by the person.
- **Run admission refreshes before trust-dependent state applies (the drift gate).** "Before the changed config is used" is enforced at run admission, not left to eventual observation: for every run/thread start or resume whose effective binding set is non-empty, the daemon MUST perform a fresh read of the provider config surfaces backing those bindings, recompute base-config hashes, and complete drift processing — auto-revocation **and** weakening neutralization, including Codex native-field reversion — before the provider process spawns or the thread starts. The Claude Code session set sent with `mcp_set_servers` is built **from** this post-drift-processing read; the Codex `thread/start` table is built from it before `thread/start` / `thread/resume` is issued. A person who edits provider config out-of-band therefore can never launder a prior grant's trust-dependent annotations or weakened facets into a run ahead of drift detection. The admission service is registered on each path that starts a provider session (see Plan-025 CP-025-5): run/thread starts register through the Plan-003 `RunSetupGate` seam (`assertRunReady`, the CP-003-8 registration pattern), and **daemon-restart recovery** invokes the same service through the Plan-013 startup-attach admission seam — a vacuous-default gate on the recovery attach sequence that Plan-025's composition-root wiring fills — before any recovery adoption or cold-resume dispatch, so a config edit made while the daemon was down processes drift before any provider session re-attaches (before Plan-025 ships, the default is honestly vacuous: no trust store exists, so there is no drift to process).
- **Revocation neutralizes weakening (atomic):** whenever trust is revoked — the person's revoke or a drift auto-revoke — safety-weakening override facets for that binding stop applying in the same operation: daemon-enforced weakenings (Claude approval modes, idempotency-class assignments everywhere) are conditioned on current trust at resolution time and lapse immediately, and Codex-materialized native weakening fields MUST be rewritten to the **baseline-anchored safe state** — the preserved native-field baseline overlaid with the surviving safety-tightening facets, never an invented default — before the revocation returns, emitting `mcp.tool_override_changed` for each reverted facet. The trust event plus the per-facet reversion events are the revocation's **atomic event batch**: they append in the same transaction as the revocation itself, one batch exactly-once under the mutation's receipt (§Authorization). A revoked server never keeps a weakened posture it was granted while trusted.
- **Revocation neutralizes the durable surface as well as the live one.** The bullet above conditions weakening on _current_ trust at resolution time, which settles every live decision — but the idempotency class is also **stamped** into a durable `command_receipts` row at accept time, and [Spec-013](./013-persistence-recovery-and-replay.md) recovery dispatches on that stamp with no session to re-resolve against. So a revocation MUST additionally rewrite every **non-terminal** receipt stamped with the revoked binding to the `manual_reconcile_only` floor, inside the revocation's own transaction. Without it a receipt stamped `compensable` under a trust revoked minutes later would be auto-compensated after a crash under an authority that no longer exists — the same governed-weakening-outliving-its-governance failure this section prevents, displaced in time. Recovery's contract is unchanged and deliberately so: it still dispatches on the stamped class, which this rule makes current rather than merely current-as-of-stamping. Receipts are matched by a **path-free keyed digest** of the binding tuple, never a stored filesystem path, and that digest excludes the config hash — a binding's config drifts while its identity does not, so a drift-triggered revocation must still match receipts stamped before the drift.

- Trust consequences (the enforcement points other specs own but this store feeds):
  - MCP tool **annotations** (`readOnlyHint`, `destructiveHint`, etc.) are honored in daemon decision surfaces only for trusted servers, per the ADR-015 binding of the MCP spec's annotation-trust MUST. Untrusted servers' annotations are display-only.
  - **Safety-weakening tool overrides** require a trusted server — `mcp.trust_required` otherwise. The weakening set is: idempotency-class assignment off the floor; approval modes weaker than the provider default; and `enabled: true` — enabling a tool the effective provider configuration or a prior override disables **broadens the executable tool set**, which is capability expansion and therefore weakening, never neutral. Safety-tightening overrides (disable a tool, force `approve` mode) are allowed regardless of trust.
  - **A `project` binding the daemon did not write joins runs only while trusted.** A server that came with the repository starts untrusted like every newly observed binding and joins a session's server set only once the person trusts it. On Claude Code the session's set is the daemon's own (`--strict-mcp-config` and `mcp_set_servers`), so Claude Code's approval prompt for a repository's `.mcp.json` never runs and the trust grant stands in for it; a server the person rejected in Claude Code (`disabledMcpjsonServers`) stays out. On Codex an untrusted one is switched off per conversation with `enabled = false` in the `thread/start` table. A drift auto-revoke takes it back out until it is trusted again. `user` and `local` bindings, and a `project` binding the daemon wrote, are written only by the person and join runs whether or not they are trusted.
  - **Withdrawn trust ends the approval rules over the binding's tools.** Withdrawing a binding's trust, by `mcp.setTrust` or by a drift auto-revoke, and removing the binding revoke every remembered approval rule whose subject is one of its tools, with `server_trust_withdrawn`, in the same transaction, so no permission granted under the old trusted identity outlives it ([Spec-010 §Fallback Behavior](./010-approvals-permissions-and-trust-boundaries.md#fallback-behavior)).

### Tool-Level Overrides

- `mcp.setToolOverride` / `mcp.clearToolOverride` manage per-`(provider, scope, scopeRef, serverName, toolName)` rows carrying up to three optional facets: `enabled` (allow/deny), `approvalMode` (`auto | prompt | writes | approve` — the Codex-native vocabulary, adopted as the normalized set), `idempotencyClass` (`idempotent | compensable`; absence means the [Spec-004](./004-provider-driver-contract-and-capabilities.md) `manual_reconcile_only` floor).
- Enforcement is provider-graded, and the override response reports it **per facet** (see the payload contract): for Codex, `enabled`/`approvalMode` facets are materialized into the native config fields (`enabled_tools` / `disabled_tools` / `tools.<t>.approval_mode`) on write — grade `user_config_write`, `user`-scope bindings only (on a Codex `project` binding these facets refuse with `mcp.config_scope_unsupported` and edit-the-file guidance — they would have to be written into the repository's own file on the person's behalf; the scope rule in §Configuration Mutation governs). The **first** facet materialization for a binding snapshots the pre-write native values of these fields as the binding's baseline (unless a trust grant already did — §Trust Governance), and `mcp.clearToolOverride` restores the cleared facet's portions from that baseline — clearing the last facet of an untrusted binding restores the baseline verbatim and drops it, returning the fields to fully native ownership; a user's own pre-existing native entries always survive a set → clear round-trip; for Claude, the daemon enforces them at its own approval layer (Spec-010 evaluation sees the override before prompting) — grade `daemon_enforced`, effective immediately for subsequent evaluations. An override request MUST carry at least one facet — the request schema rejects a facet-less override at validation, mirroring the DDL's all-NULL row prohibition. The `idempotencyClass` facet is provider-independent and always `daemon_enforced`: it feeds the Spec-004 tool-metadata resolution layer, which downstream consumers (recovery/replay per Spec-013) already read — consumers never read the override table directly. Override resolution is **binding-keyed**: the Spec-004 metadata layer resolves by `(driver_name, tool_name)`, which cannot disambiguate the same `serverName` bound in two scopes, so the override overlay widens the resolution input with the session's **effective server binding** for the tool's server (the binding in the set the daemon sent that session — the Codex `thread/start` table, the Claude Code `mcp_set_servers` set; the same attribution rule as §Unified Inventory status observations), carried through tool invocation and recovery-receipt resolution, and keys the lookup by the full binding plus `toolName` — two sessions resolving the same tool name from user- and project-scope bindings each get their own scope's override, never the other's. Safety-weakening facets are effective only while the binding's trust holds (see §Trust Governance — revocation neutralizes weakening).
- Idempotency-class assignment is the **only** governed path off the `manual_reconcile_only` floor ([Spec-004 §Tool Metadata](./004-provider-driver-contract-and-capabilities.md#tool-metadata)): initiated by the person, Cedar-gated, trusted-server-only, and always audited via `mcp.tool_override_changed`.
- Every override mutation emits `mcp.tool_override_changed` (set and clear alike).

### Authorization

- Every non-read operation (`mcp.upsertServer`, `mcp.removeServer`, `mcp.setEnabled`, `mcp.setTrust`, `mcp.setToolOverride`, `mcp.clearToolOverride`, `mcp.oauthLogin`, `mcp.oauthLogout`, `mcp.reconnect`) MUST be authorized through the Plan-010 Cedar evaluation surface (`PermissionCheckService`) under a dedicated set of `mcp` Cedar actions before any provider call or store write. Read operations (`mcp.list`, `mcp.get`, the `mcp.subscribe` stream, and `mcp.registrySearch`) are readable by the person without a Cedar mutation check; `mcp.registrySearch` sends the person's search words to the public MCP Registry and nothing else, and writes nothing.
- **Governance mutations — and the receipted operational commands `mcp.oauthLogin` and `mcp.oauthLogout` — are idempotent to the caller (the Spec-004 `clientIdempotencyKey` discipline).** Every such request carries a mandatory requester-generated UUID `clientIdempotencyKey`. After the Cedar check, the daemon consults the durable `mcp_mutation_receipts` store: an identical retry (same key, same `b3:` keyed request digest — keyed under a **daemon-held key the database holds only sealed under the daemon master key**, never a value colocated with the receipt row, so a database copy alone cannot verify secret guesses offline; see the schema) replays the recorded response verbatim with **no** provider call, store write, or second event (one representation exception: the `mcp.oauthLogin` receipt is stored and replayed URL-free — §OAuth Orchestration); the same key with a differing digest refuses with `mcp.idempotency_conflict`, original mutation untouched. Receipts are **two-phase** (the Plan-013 `command_receipts` two-phase discipline): the daemon commits the receipt as a `pending` **intent** (key, operation, request digest) in its own transaction **before** any provider leg runs, then finalizes it (`committed`, response recorded) in the **same SQLite transaction** as the mutation's store writes and event append — so acknowledgment, audit event, and replay evidence are atomic at finalization, and both crash windows around the external provider side effect are closed: a crash before the provider leg leaves a pending intent with no provider effect (startup reconciliation verifies provider state and expires it), while a crash after a durable provider write but before finalization leaves a pending intent whose effect is durable — startup reconciliation observes the provider state, completes the store writes, appends the event, and finalizes, so the audit event lands late but exactly once, never lost. An identical-key retry that meets a pending intent drives reconciliation first, then replays; a lost IPC response or crash-window retry can re-drive only the provider leg (safe by construction: sanctioned provider writes are upserts, full-set replacements, or version-guarded), never a second acknowledgment or a second event. Receipts are retry-window dedup, not audit (events are the audit trail): `committed` rows older than 24 hours are pruned opportunistically on later mutation writes; `pending` intents are resolved at startup reconciliation, never silently pruned.
- Of the Cedar-gated operations, **the governance mutations** are those bound by the one-event-set-per-mutation atomic audit invariant — `mcp.upsertServer`, `mcp.removeServer`, `mcp.setEnabled`, `mcp.setTrust`, `mcp.setToolOverride`, `mcp.clearToolOverride` — whose receipt finalization, store writes, and **defined event set** commit in one transaction: a single event for most mutations, and for `mcp.setTrust(false)` on a binding with materialized weakening facets the **revocation batch** — `mcp.server_trust_changed` plus one `mcp.tool_override_changed` per reverted facet (§Trust Governance) — all-or-nothing under the mutation's receipt, never re-emitted on replay. The rest are **operational commands outside that atomic invariant**. **`mcp.reconnect`** changes no daemon store and no provider config, so it carries no dedicated governance event — its observable effect is audited through the `mcp.server_status_changed` transitions it induces (leg-addressable: a `bindingId` reconnects one leg, a `sessionId` that session's legs, neither every live leg), and a reconnect attempt that produces no status transition intentionally leaves no governance-event row (the attempt is still Cedar-evaluated, and its failures surface as typed errors on the response). **`mcp.oauthLogin`** starts the daemon's sign-in, whose durable trace — `mcp.server_oauth_completed` — is **asynchronous by nature**: it cannot commit atomically with the launch acknowledgment, and an abandoned sign-in never completes, so the launch is receipted (idempotency) but deliberately not evented. The completion event is emitted **exactly once per completed sign-in** — the daemon's own callback, or the provider's flow finishing in the throwaway home — and an abandoned sign-in, or one ended by a newer attempt, leaves only its expiring receipt. **`mcp.oauthLogout`** removes the daemon's sign-in for the server and mints no event of its own: its trace is the `mcp.server_status_changed` transition to `needs-auth` on each leg that was connected on that sign-in.
- The V1 principal model is **caller-owns-the-node**, and the predicate is **ownership, never transport origin**: the daemon authorizes a governance operation when the authenticated caller owns this node, and refuses with `mcp.operator_scope_required` when it does not. A linked device of the owning user driving the node through the relay is the same principal as that user sitting at the machine and carries the same authority — [Spec-028 §Parity by construction](./028-remote-control.md#parity-by-construction) makes that the bar rather than a concession, so the daemon MUST NOT admit or refuse a governance operation on the basis of which transport carried it. The authenticated identity is resolved at the transport boundary before the operation is dispatched; what this spec authorizes against is that identity and the node's ownership record, nothing else.
- A Cedar deny returns `mcp.governance_denied`; authorization is evaluated before existence checks so the refusal is stable and does not leak inventory contents to unauthorized callers.
- No new approval _category_ is minted: governance mutations are direct Cedar authorization decisions, not interactive approval requests, so the [api-payload `ApprovalCategory`](../architecture/contracts/api-payload-contracts.md#shared-enums) union is unchanged; no approval category is MCP-related, since a server's run-time elicitation becomes the session's question card.

### OAuth Orchestration

- **One sign-in per server, the daemon's own ([ADR-040](../decisions/040-mcp-credential-custody.md#decision)).** `mcp.oauthLogin` starts the daemon's own sign-in for that server, whatever kind of server it is, and returns the address of the sign-in page for the client to open. One sign-in and one consent serve the server's tools, resources and prompts on Claude Code and Codex alike, in every account. By default the daemon signs in as its own OAuth client: discovery from the server's protected-resource metadata, client registration by the server's metadata document or by dynamic registration, PKCE, and `resource` set to the server's address. A server whose entry names a client the server's owner issued (Codex's `oauth.client_id` and `oauth.callback_url`) is signed in as that client.
- **A server that admits only Claude Code's or Codex's own client** is signed in through that provider's own flow, run in a throwaway home the daemon makes for that sign-in: Codex's `mcpServer/oauth/login` with `mcp_oauth_credentials_store = "file"`, which needs no ChatGPT sign-in, or Claude Code's own flow in a credential folder of its own. The daemon takes the saved sign-in (the server, the issuer, the client id, the access and refresh tokens, the expiry) into its own item, deletes the home, renews the sign-in under that client id from then on, and fronts the server for both providers (§Long tool calls and the fronted route). It learns which client a server admits before the browser opens wherever the server says so — a refused dynamic registration, or a refusal from the server's pushed-authorization endpoint. Where the server says nothing, the first sign-in opens with the daemon's own client, and when that one does not finish, the next attempt goes through the admitted provider's client. The daemon remembers which client each server admitted, so every later sign-in is one press.
- **A server that demands proof-of-possession (DPoP) tokens**, which neither provider can sign in to, is signed in by the daemon as its own client with a signing key made for that one sign-in — one key per server, never the machine's own control-plane key — kept in the operating system's credential store beside the refresh token. Because a header helper cannot carry a per-request proof, the daemon fronts that server for Claude Code and Codex alike and signs a fresh proof for every request.
- **How the sign-in reaches a provider.** The daemon keeps the refresh token in the operating system's credential store under its own item, never in a file, and renews it itself under the client id it was issued to. Each provider process the daemon launches carries a header helper for each signed-in server — Codex's `http_headers_helper`, Claude Code's `headersHelper` — that asks the daemon over its same-user local socket for a current access token and prints it as the `Authorization` header; the helper's command line carries only a server and session handle, never a credential. Each provider re-runs its helper by itself after a rejected token, so a renewal never reaches the person. The daemon's own MCP client uses the same sign-in to list and read the server's prompts for a Codex session and to hold the connection of every server it fronts. A provider process the daemon did not launch gets nothing. The daemon never reads or renews a sign-in held by the person's own Claude Code or Codex outside the app: a server replaces a public client's refresh token on every renewal, so a second party renewing it signs the first one out.
- **A new attempt ends the waiting one.** `mcp.oauthLogin` on a server whose sign-in is still waiting ends that wait and starts the next attempt, so a refusal page in the browser never holds the person until the flow's timeout.
- **Launch failures are errors; completion failures are events.** `mcp.oauth_flow_failed` is scoped to the **launch phase** — a failure to start the sign-in (discovery, registration, or the provider's own flow in its throwaway home), surfaced on the still-open `mcp.oauthLogin` call. Once the call has returned (the `authorizationUrl` handed to the caller), the JSON-RPC channel for that request is closed by definition, so an asynchronous completion failure is delivered as the completion outcome itself: `mcp.server_oauth_completed` with `outcome: 'failure'` and a sanitized `failureReason`, observable on the `mcp.subscribe` stream and reflected by the server's persisting `needs-auth` status. The daemon never fabricates a late JSON-RPC error for a completed call.
- **Sign-out.** `mcp.oauthLogout {serverId}` deletes the daemon's refresh token for that server, and its signing key where the server demands DPoP tokens, and stops answering the helpers for it, so each provider's next call to that server gets no token; the server reads `needs-auth` in every session on both providers until the next sign-in.
- Tokens, authorization codes, PKCE material and DPoP keys are held only as [ADR-040](../decisions/040-mcp-credential-custody.md#decision) records and are never logged, relayed, shown, or carried by any event, error, receipt, read model, or wire payload; the only durable trace on the governance stream is the `mcp.server_oauth_completed` event, whose payload carries the server identity and outcome, never credentials or URLs with embedded secrets. The idempotency receipt row for `mcp.oauthLogin` follows the same rule: the persisted response omits `authorizationUrl` **structurally** (launch URLs embed single-use PKCE state and are never durable), so an identical-key retry replays a URL-free acknowledgment — the sign-in is already started, completion arrives as the event, and a caller that never received the URL begins a new sign-in under a fresh key. **The launch URL has exactly one carrier: the `mcp.oauthLogin` reply, and no other surface.** It is absent from every durable and every broadcast destination — receipt rows, every event payload, the `mcp.subscribe` stream, errors beyond guidance text, and logs — which is the §Pitfalls destination list applied to this value rather than a carve-out of it, and it is what makes the rule mechanically checkable: one surface asserts presence and every other asserts absence. Each client then consumes it at **one destination and none other** — the CLI prints it as the login command's own **result**, on the stream that command's result belongs on, and the desktop opens it in the browser and holds it as transient render state that is written to no client-side storage, entered into no log, and dropped at settlement. A client that cannot show the URL cannot complete the sign-in at all, so withholding it there would not harden the launch phase but remove it. Tokens, authorization codes, and PKCE material stay prohibited at every one of those surfaces including the reply — the launch URL is a one-shot handle to the server's consent page, and it is the only member of this paragraph that any client ever sees.

### Status Observation and Events

Five event types, `mcp_governance` category ([Spec-005 §MCP Governance (`mcp_governance`)](./005-session-event-taxonomy-and-audit-log.md#mcp-governance-mcp_governance)):

| Event | Emission point | Session binding |
| --- | --- | --- |
| `mcp.server_status_changed` | Normalized status transition from either provider feed (Codex `mcpServer/startupStatus/updated` / `mcpServerStatus/list` deltas; Claude init census + `mcpServerStatus()` deltas) or from the daemon's own client for a server it fronts, including the transition to `needs-auth` a sign-out causes | Per-event: the observing session's real `session_id` when the observation is a session-scoped provider feed or a fronted connection serving that session; the daemon-scope sentinel for node-level probes |
| `mcp.server_config_changed` | Every applied configuration mutation | Sentinel-bound (node-scope) per [Spec-005 §Daemon-Scope Event Binding](./005-session-event-taxonomy-and-audit-log.md#daemon-scope-event-binding); `initiatingSessionId` in the payload when a session-scoped caller initiated |
| `mcp.server_trust_changed` | Trust grant, the person's revoke, config-drift auto-revoke | Sentinel-bound; `initiatingSessionId` when applicable (absent on drift auto-revoke) |
| `mcp.tool_override_changed` | Override set / clear | Sentinel-bound; `initiatingSessionId` when applicable |
| `mcp.server_oauth_completed` | The daemon's sign-in settling (its own callback, or the provider's flow finishing in the throwaway home) | Sentinel-bound; `initiatingSessionId` when applicable |

- Status observation is event-driven plus on-demand (`mcp.list` refresh); the daemon MUST NOT busy-poll provider status endpoints.
- **`mcp.subscribe` is the live governance stream.** `mcp.subscribe` is a long-lived subscription the person reads (the Plan-006 streaming primitive, the `session.subscribe` consumer shape) delivering every `mcp_governance` event envelope — sentinel-bound and session-bound alike — as the daemon appends it. It is live-tail with a **gap-free handshake, not a cursor**: a (re)connecting client opens `mcp.subscribe` first, then reads `mcp.list` — the subscribe acknowledgment precedes the stream's first delivery (the Plan-006 I-006-10 wire-ordering invariant), so registration is live before the snapshot read and an event concurrent with the snapshot arrives on the stream instead of falling between snapshot and subscription (re-observation is harmless — governance envelopes are re-entrant state updates; omission is impossible). History remains the sentinel session's log. This is how the desktop MCP panel and `sidekicks mcp watch` observe governance without polling and without any per-session timeline merge (sentinel events never enter real sessions' streams — §Domain Dependencies).
- All five payloads are **credential-free and content-free by construction**: hashes, enums, scope identity, and sanitized failure reasons only — no config values, env-var values, header values, tokens, and none of the [Spec-020 §PII Data Map](./020-data-retention-and-gdpr.md#pii-data-map) durable-tier PII classes (user messages, file paths, code snippets). `failureReason` fields pass the daemon's error-sanitization layer and MUST NOT echo config values or filesystem paths. Binding identity in payloads is the **path-free audit ref**: `scopeRef` — a user-specific filesystem path — never enters an event payload; project/local variants carry `scopeRefDigest`, the `b3:`-prefixed keyed BLAKE3 (key = the binding's **scope-ref subkey** of the same daemon-held master key — derivable before any event fires and without any trust row) of the canonical `scopeRef`, also served on inventory entries so a reader joins events to bindings; the raw path stays resolvable only through the node-local trust store. `mcp.server_status_changed` payloads with `origin: 'session_feed'` additionally carry the observing leg's `bindingId` — the Plan-004 runtime-binding key, an opaque daemon-minted identifier — so a subscriber can attribute the transition to its `legs[]` entry when one binding backs several legs in the same session (absent on `node_probe` rows, which observe no leg).
- `serverName` / `toolName` are the deliberate residual: free-form identifiers the person or the provider chooses, `wireFreeFormString`-bounded, classified as **non-PII infrastructure identifiers** in the plaintext audit payload — the same classification as tool names in `tool_activity` events. The person CAN embed personal data in a name they choose; the classification is recorded here (not silently assumed) so Plan-020's call-site PII classification pass over the event corpus inherits an explicit ruling with its rationale: governance provenance is unusable if server identity crypto-shreds with any single user, and the identifiers age out of full payloads on the standard [Spec-005 §Event Compaction Policy](./005-session-event-taxonomy-and-audit-log.md#event-compaction-policy) lifecycle. No other free-form config-derived string may enter these payloads.

### The MCP servers page

The governance layer above faces the person by construction, and precisely so: **every** non-read operation is Cedar-gated, open to this machine's own client or any linked device, and no session; the **governance mutations** among them are atomically audited under the one-event-set-per-mutation invariant, while the operational commands are not — `mcp.reconnect` carries no dedicated governance event, `mcp.oauthLogin` is receipted and deliberately not evented, and `mcp.oauthLogout` is receipted and traced by the status transitions it causes; and **trust is a gate on the safety-weakening subset rather than on mutation as such** — a first observation upserts an untrusted binding, `mcp.setTrust` is by definition reachable on one, and a safety-**tightening** override is admitted regardless of trust (§Required Behavior). Reading the layer as uniformly trusted-server-only would misdescribe what this page can do, since the person's first action on a newly-observed server is necessarily taken against an untrusted binding. It is reached through Settings › **MCP servers** in the desktop app. This section states what that surface is bound by; its composition sketch is [Spec-021 §Signature Feature Composition Sketches](021-desktop-app-and-renderer.md#signature-feature-composition-sketches), and the ownership split is the one: [Plan-025](../plans/025-mcp-server-configuration-and-governance.md) authors the page's components and their projection in its own renderer subtree (CP-025-8), and [Plan-021](../plans/021-desktop-app-and-renderer.md) mounts that subtree into the app and owns nothing inside it (CP-021-7).

- **It adds no surface.** The page composes the `mcp.*` operations §Interfaces And Contracts documents — the governance operations, `mcp.registrySearch` for `Browse servers`, and `mcp.oauthLogout` for `Sign out of this server` — and mints no operation, event type, or error code beyond them. A control that would need another new verb is not a control this page ships.
- **Its update channel is `mcp.subscribe`.** Status arrives on the live governance stream and is applied to the row it names; the page does **not** poll `mcp.list` on a timer. §Status Observation and Events forbids the daemon to busy-poll provider status endpoints, and a surface that polled the daemon instead would reintroduce the same cost one layer up, with the daemon's own admission control no longer in the way.
- **It is a fail-closed projection of state, and it does not project eligibility at all.** The two are separate. **State** — connection status and per-leg observations, trust state including a config-drift auto-revoke and its reason, enablement, per-tool overrides and whether a tool's idempotency class is the native baseline or an override the person set — is rendered from what the daemon reports and recomputed **nowhere**. This is the sharpest rule here rather than a restatement of the general one: idempotency classes the person assigns change what [Spec-013](013-persistence-recovery-and-replay.md) recovery may safely replay, so a renderer that derived an effective class would be a second source of truth for a recovery decision — and it would be the source no policy engine consults. **Eligibility is different**: no inventory entry and no event payload on this governance layer reports whether a given operation would be permitted for a given binding, and none is minted here, because a supplied eligibility flag would be exactly the daemon-side authorization re-expressed as a renderable field and would drift from the Cedar decision that actually governs. So the page projects none: every control is offered, the daemon adjudicates, and the typed refusal renders — which is the same rule as the bullet below, not a competing one. The **one** non-offer is a control whose required input is structurally absent from the entry the daemon served — on the degraded arm §Fallback Behavior serves when the trust store is unreachable, `trusted`, `configHash`, and `toolOverrides` are absent outright and `enabled` survives only where the provider itself declares it, so the trust and per-tool controls have nothing to act on, while every control whose input **did** arrive is offered exactly as on the normal arm — and that is absence of data rather than a judgment the renderer formed.
- **Configuration content splits three ways, and the split is what makes the page usable without making it a credential surface.** A page that rendered and collected nothing could not register a server at all, and `mcp.upsertServer` takes a declaration the person authors by design. **(1) Input.** The declaration form collects what that mutation accepts: transport, command, arguments, URL, timeouts, the required-server marker, environment-variable and header **names**, and the credential-bearing values the input shape admits. Those values are **write-only in the renderer as well as on the wire** — masked on entry, never read back, never held in serializable renderer state, cleared on submit — the Provider Accounts token-field discipline, applied here for the same reason: the wire rule protects the transport and this protects the screen. **(2) Read-back is exactly `McpServerConfigView` and nothing beyond it.** That view exists so `mcp.get` can serve back what `mcp.upsertServer` wrote — every non-secret field preserved, secret values structurally absent, names without values, the URL query-redacted — which is what supports an edit workflow without the daemon ever serving credential material. **(3) Never rendered.** Anything the daemon does not serve: environment-variable values, header values, tokens, URL query values. The page does not reach past the daemon to the provider's own config files, which remain the source of truth and are the daemon's to read. The five governance **event** payloads stay credential-free and content-free by construction — that property is about the audit stream and is unchanged by anything this page collects or displays.
- **It is the one place a tool server is governed.** A tool server is added, removed, trusted, and governed here and nowhere else in the product. The page is the server list beside the selected server's detail: the list gives each server its name, its provider, where it applies — `On this machine, in every project`, `In this project, saved with the repository`, or `In this project, on this machine only` — and its state; a name held in two places says so rather than being resolved away. The detail gives that server's per-connection readings and then its controls, and with nothing selected it says to pick a server on the left. The list's first read says it is reading (`Reading the server list…`), and a read that fails says so (`The server list could not be read.`) with `Try again`.
- **A server is added where it applies.** The declaration form takes `Where it applies` after the provider, with the same three choices; the last two add a chooser over the attached projects. At `In this project, saved with the repository` a value typed in any value field is refused in place before anything is written — `This file is saved in the repository, so values can't be stored in it. Name an environment variable instead.` — and the value fields are cleared. Under Codex at `In this project, on this machine only`, one line under the chooser reads `Plain codex shows this server as switched off.`
- **`Browse servers` searches the public MCP Registry.** It sits beside `Add a server`, searches only when the person types, and says under its field where the words go: `Searches the public MCP Registry. Anyone can publish there; check a server's source before adding it.` Each result reads its title or name, its description, its version, and whether it runs as a package or is reached at an address. Picking one opens the declaration form filled in — the name, how it runs with its command and arguments or its address, each environment variable's name and description with the required ones marked — and leaves every value and the add to the person; the server starts untrusted like any other.
- **Five words, one vocabulary.** A server's state is drawn in one of five words — `Connected`, `Starting`, `Needs sign-in`, `Failed`, `Not known yet` — one word per `McpServerStatus` value. Every other surface that says what a tool server is doing uses those same five words read from this same inventory, the session composer's tool-server chip among them: it lists that session's servers, links here to manage them, and is the only place inside a session that names them. There is never a second inventory.
- **Every per-tool value says where it came from.** The three per-tool facets — whether the tool is on, whether it asks before running, and what happens if a call is interrupted — are each optional, each shown per tool, and each says whether the value in force is the server's own or one set here. The page works none of that out for itself.
- **Reconnect asks, and claims nothing.** Asking the provider to open the connection again is offered on the selected server whatever its state and is drawn first on one reading `Failed`. It writes nothing and changes no setting, and it says so. A try that moves no state says that nothing changed rather than reading as success.
- **Sign-in is one control and one consent, and leaves nothing behind.** `Sign in to this server` starts the daemon's own sign-in for that server (§OAuth Orchestration) — for every kind of server, one that admits only Claude Code's or Codex's own client and one that demands DPoP tokens included — and settles in place when the page opens in the browser, or says the sign-in did not finish. It stays pressable while a sign-in waits: a press ends that wait and starts the next attempt. The address the flow opens with is held only while it is used, written to no storage and no log, and dropped when the sign-in settles. Once signed in, `Sign out of this server` stands where `Sign in to this server` stood; it forgets the sign-in at once, and the server then reads `Needs sign-in`.
- **A command that cannot run says so.** After the background service moves between Windows and a WSL distribution, a server whose command or arguments name a program on the side it left reads `Failed`, one of the state words, and its selected view carries one line: `Its command names a program the background service cannot run. Edit its command.` The line names no side.
- **A missing reading says it is missing.** Where the degraded arm leaves the trust and per-tool controls without an input, the page says so in place — those controls are not drawn because the reading they act on did not arrive, and everything else on the page is offered exactly as usual — rather than leaving the absence unexplained.
- **Nothing configurable is drawn as nothing.** A provider with no tool servers set up says so in words. An empty list is never drawn as though nothing could be configured.
- **One wire mutation per explicit action by the person, and refusals render.** No control batches, retries on the person's behalf, or pre-filters itself to hide an action the daemon would refuse. A safety-weakening override on an untrusted server is refused before any write and the refusal is shown, because the person learning the rule from the system that enforces it is worth more than a control that quietly disappears — and a pre-filter would be a re-derivation of exactly the authorization this spec places in the daemon.

### Required-Server Semantics

- A Codex server with `required = true` that fails to initialize fails the thread start/resume; the daemon MUST map that failure onto the run-failure path with an actionable error naming the server, and emit `mcp.server_status_changed` (`failed`) for it — the run failure is never silent or attributed to the provider generically.

### Long tool calls and the fronted route

A tool call that runs long moves to the background on both providers: after 120 s, or at once when a message arrives, the model is told the call keeps running under a task id and goes on working, and the result comes into the conversation when the call ends, starting a new turn if none is running.

- **Claude Code does it itself.** The daemon starts every Claude Code process with `CLAUDE_AUTO_BACKGROUND_TASKS=1`, so an MCP call still running after 120 s, or one running when a new message arrives, moves to the background: the model gets a tool result naming the task id and goes on, and when the call ends Claude Code's task notification starts a turn if none is running. Claude Code runs MCP Tasks itself and restores them on resume. The daemon draws the call as a tool row that stays running until the task ends, and the notification as that row's result, never as a message from the person. A plain call moved to the background ends with the process, and after a restart its row reads `Stopped when the app restarted`.
- **On Codex the daemon fronts every server it can reach.** Codex has no MCP Tasks and cannot move a call to the background, so the conversation's `thread/start` table carries every server as a `url` entry on the daemon's route under the server's own name, and the model sees the same server and tool names. The daemon's own MCP client holds the real connection: it starts a stdio server itself, one copy per conversation, as Codex would, or connects to an address, reading the declaration's environment and header values from the provider's config only for that connection.
- **The route answers a long call with a handle.** It answers a call normally when it ends within 120 s. Past 120 s, or when the daemon steers the conversation while the call runs, it answers Codex's pending call with Claude Code's own handle text — `Tool "<tool>" is still running after <N>s. It was moved to the background as task <id> and keeps running; you'll receive a notification with the result when it completes. You can keep working in the meantime. To stop it, call task_stop with task_id "<id>".` — and the call keeps running in the daemon's client. The route offers tools of its own:
  - `task_output {task_id, wait_seconds?}` returns the task's status and, once it ends, its result, waiting at most 10 s;
  - `task_stop {task_id}` cancels it: `tasks/cancel` for a task-augmented call, `notifications/cancelled` for a plain one.
- **Delivery.** When the call ends, the daemon delivers `MCP task <id> (<server>/<tool>) completed.` with the result — by `turn/steer` into a running turn, or `turn/start` into an idle conversation — and draws it as the tool row's result. The client makes a call task-augmented wherever the tool allows one, writes the `taskId` to the command receipt before answering anything else, polls with Claude Code's figures (every 2 s by default, honoring the server's `pollInterval` held between 100 ms and 60 s, halting after 10 failures in a row with the handle kept), and marks the receipt `delivered` once the result is delivered, so a result that arrives after a daemon restart is delivered once. After a restart it resumes every receipt with a handle to a server reached at an address; a stdio server's task ends with the daemon.
- **What the route applies.** Codex's per-tool approval for a fronted server is applied on the route from the session's permission level and the server's `tools.<t>.approval_mode`. A request the server sends back is handed on: an elicitation becomes the session's question card, and a progress notice the row's progress line. A server behind a sign-in is fronted on the daemon's own sign-in (§OAuth Orchestration), including one whose sign-in the daemon took over from a provider's flow.
- **On Claude Code only a DPoP server is fronted.** Claude Code reaches a server that demands proof-of-possession tokens on the daemon's route, which signs a proof for every request, and a long call there takes the daemon's own MCP Tasks handling with Claude Code's figures.
- **The workflow MCP-tool step** calls a tool with MCP `tools/call` through the same client, task-augmented where the tool allows one.
- **Budget.** The route adds at most 5 ms to a fronted call against a direct one. While a call is in the background: one `tasks/get` per poll interval for a task-augmented call and nothing for a plain one; one model turn per delivery into an idle conversation. A fronted stdio server costs one copy of that server per Codex conversation (about 50 MB), the process Codex would otherwise start.

### A session's own tool servers

- **A session starts with exactly the servers switched on for it**, through the provider's own means (§Provider Capability Model), and a server that is off costs the model no tool definitions.
- **Its list is read, never recomputed.** `session.mcpServerList {sessionId}` is a live list of the servers the session was started with, each drawn from this spec's inventory: the working servers first by name alone, then the ones that are not working, each with `Needs sign-in` or `Failed` and the reason, the failed ones last; a server still starting, or one whose state is not known yet, sits with the working ones until it says otherwise. The list carries no reconnect, no sign-in and no tool list; those are the MCP servers page's.
- **A per-session switch only narrows.** `session.mcpServerUpdate {sessionId, serverName, enabled}` turns one server off or on for this session alone: off stops the session offering that server's tools to the agent, so none of its definitions reach the model and none of its tokens are spent. Settings, every other session and every future session are untouched, and a new session starts with every server on. A switch applies at the next turn — on Claude Code another full-set `mcp_set_servers` call, which ends a switched-off server's process and removes its tools from the next turn with no restart and nothing written to disk; on Codex the conversation's `enabled` flag at its next turn — and one flipped mid-turn says so rather than changing anything under the run. The daemon keeps a session's switches with the session and sends its set again after each resume. The switch is not a governance mutation and emits no governance event.
- **Resources.** `session.mcpResourceList {sessionId, serverName}` lists what a working server offers, so the person can stage one in the composer's attachment row; on Codex the read goes through `mcpServer/resource/read`.
- **Prompts.** A working server's prompts appear as a group under its name in the session's command list, the provider-commands subscription [Spec-004](./004-provider-driver-contract-and-capabilities.md) owns; on Codex the daemon lists and reads them through its own client, on its own sign-in where the server needs one, over the connection that client already holds for the server, so listing prompts never starts a second copy of it.

## Default Behavior

- New servers are enabled per provider config, **untrusted** in the daemon trust store, with no tool overrides (provider defaults + `manual_reconcile_only` idempotency floor).
- `mcp.list` serves the merged inventory from the most recent observations without forcing a provider round-trip; `refresh: true` forces one.
- Claude mutations attempt the live path on every admitted build and settle the grade on the outcome of the daemon's own full-desired-set reconcile; callers never select the mechanism, only observe the returned grade.
- Event emission is on-transition only — an unchanged status re-observation emits nothing.

## Fallback Behavior

- **A Claude Code session that refuses `mcp_set_servers`**: the daemon gives a session its tool servers with `mcp_set_servers` right after start, again after each resume, and after each change, never with `mcp_toggle` and never by restarting the session. A session that refuses the call (the CLI refuses control requests from a session it treats as cloud-hosted, and a non-streaming-input session cannot carry them at all) gets its servers no other way: each of that session's servers reads `Failed`, with the refusal as the server's reason, the way Settings › MCP servers draws a command the service cannot run. A configuration change made meanwhile is still written through `claude mcp add-json --scope` and answers with grade `user_config_write`; that session's live set does not change. The refusal is read from the call's own answer, never from a version comparison or a driver-side probe.
- **Codex write conflict:** one silent re-read-and-retry; a second `configVersionConflict` surfaces `mcp.config_write_conflict` with both version tokens so the caller can re-inspect.
- **Scope-unsupported operation:** `mcp.config_scope_unsupported` only for an `enabled` or `approvalMode` override facet on a Codex `project` binding (§Configuration Mutation), with the resolved config-file path in the _message guidance only_ (never in event payloads).
- **Codex project file changed since it was read:** the edit is not renamed into place and the write refuses with `mcp.config_write_conflict`; the file is left as it was.
- **Status source unavailable** (provider down, or the status probe refused on the running build): inventory serves `unknown` with an `observedAt` timestamp; the daemon does not fabricate `connected`/`failed`.
- **Sign-in did not finish:** `mcp.server_oauth_completed` carries `outcome: 'failure'`, the server keeps reading `needs-auth`, and the next `mcp.oauthLogin` starts a new attempt — through the admitted provider's client where the daemon's own client was not admitted (§OAuth Orchestration).
- **Trust store unavailable** (storage failure): governance reads degrade to the **degraded entry arm** — a discriminated `trustUnavailable: true` variant whose trust- and override-dependent fields (`trusted`, `configHash`, `toolOverrides`, the Claude enabled overlay) are structurally absent rather than fabricated, with provider-observed fields (config view, status, legs) intact — and `scopeRefDigest` still served: it derives from the governance key, not from any trust-store row; all mutations fail closed.

## Interfaces And Contracts

- **IPC operations** (13, JSON-RPC per [ADR-009](../decisions/009-json-rpc-ipc-wire-format.md); registered in the Plan-006 `MethodRegistry` at Plan-025's tier per the `presence.*` late-namespace precedent): `mcp.list`, `mcp.get`, `mcp.subscribe`, `mcp.upsertServer`, `mcp.removeServer`, `mcp.setEnabled`, `mcp.setTrust`, `mcp.setToolOverride`, `mcp.clearToolOverride`, `mcp.oauthLogin`, `mcp.oauthLogout {serverId}`, `mcp.reconnect`, and `mcp.registrySearch {query, cursor?}` answering `{servers, nextCursor?}` from the public MCP Registry's `GET /v0/servers?search=<query>&version=latest`, caching nothing past the page. Requests address the scope-qualified binding (`scopeRef` structurally required for `project`/`local` and forbidden for `user`, on both providers — a schema-level discriminated union, not a service-layer check); `mcp.upsertServer` and `mcp.removeServer` take `scope` and `scopeRef`; every governance mutation — and `mcp.oauthLogin` and `mcp.oauthLogout` — carries the mandatory `clientIdempotencyKey` (`mcp.reconnect` is unreceipted); `mcp.upsertServer` carries the fully-typed `McpServerConfigInput` union; mutation responses carry application grades (per-facet for overrides) plus per-leg `liveResults[]`; an entry reading `failed` because its command cannot run after a move carries `failedReason: commandNotRunnable`. Typed request/response mirrors live in [API Payload Contracts §Plan-025 — MCP Governance Contract Surfaces](../architecture/contracts/api-payload-contracts.md#plan-025--mcp-governance-contract-surfaces).
- **A session's servers** (§A session's own tool servers): `session.mcpServerList {sessionId}` (a live list; each row the server's name, binding, status with its reason, whether it is on for the session, and whether a switch waits for the next turn), `session.mcpServerUpdate {sessionId, serverName, enabled}`, and `session.mcpResourceList {sessionId, serverName}`; typed mirrors in the same api-payload section.
- **Tools the fronted route adds** (§Long tool calls and the fronted route): `task_output {task_id, wait_seconds?}` and `task_stop {task_id}`, visible to a Codex model and to a Claude Code model on a fronted DPoP server, never on screen.
- **Events**: the `mcp.*` types above; payload mirrors in the same api-payload section; category registration in Spec-005; contracts-package registration via Plan-005 T1.10.
- **Errors**: the `mcp.*` code registry in [Error Contracts §MCP Governance](../architecture/contracts/error-contracts.md#mcp-governance) — the codes narrated across §Required Behavior plus `mcp.server_not_found` for the unknown-binding outcome every operation surface shares.
- **Not built.** None of the following exists in code yet; each is built by the [Plan-025](../plans/025-mcp-server-configuration-and-governance.md) task named: `mcp.list` and `mcp.get` (Phase 2), `mcp.subscribe` (Phase 2), `mcp.upsertServer` and `mcp.removeServer` at every scope (Phase 3), `mcp.setEnabled` (Phase 3), `mcp.setTrust` (Phase 4), `mcp.setToolOverride` and `mcp.clearToolOverride` (Phase 4), `mcp.registrySearch` (Phase 3), `mcp.oauthLogin` and `mcp.oauthLogout` (Phase 5), `mcp.reconnect` (Phase 5), `failedReason: commandNotRunnable` (Phase 2), the session operations (Phase 5), the fronted route with `task_output` and `task_stop` (Phase 5), and the daemon's MCP client that the workflow MCP-tool step calls through (Phase 5).
- **Driver seam**: consumes the Spec-004 `onMcpServerStatus` producer seam (`McpServerStatusEmission` → `McpServerStatusUpdate`) as the session-scoped status source — this spec is the consumer that seam was built for.
- **Versioning**: operation payloads follow [ADR-018](../decisions/018-cross-version-compatibility.md) cross-version compatibility rules; provider version floors are **version-compared** at driver spawn — that comparison is the admission gate and decides nothing else — while each capability is separately resolved by its own declared detection mechanism and re-verified against the then-installed binaries per the provider-wire trust model.

## State And Data Implications

- **New daemon-local tables** (node-scoped; DDL in [Local SQLite Schema §MCP Governance Tables (Plan-025)](../architecture/schemas/local-sqlite-schema.md#mcp-governance-tables-plan-025)): `mcp_server_trust` (scope-qualified binding identity, an emulated Codex `local` binding among them, `trusted`, the base-config `b3:`-hash binding, the native-tool baseline, grant/revoke provenance, whether the daemon wrote a `project` binding, and the Claude enabled overlay — no key material and no credential: every digest key derives from the governance key, which the database holds only sealed under the daemon master key), `mcp_tool_overrides` (per-tool facets, FK-cascaded to the trust row), `mcp_mutation_receipts` (the idempotency receipt store — key, operation, request digest, replayed response; pruned on age, never part of the audit trail), and `mcp_server_admitted_clients` (which client each signed-in server admitted — the daemon's own, Claude Code's or Codex's — kept once per provider and server name rather than on each binding, and kept after a sign-out, so every later sign-in is one press; not a credential).
- **No provider-config mirroring**: provider files remain the config source of truth at every scope — including for Claude, whose durable declarations live in the provider's own stores (written only through `claude mcp add-json --scope`) and whose session set is sent through `mcp_set_servers` from those declarations plus governance overlays, never an independent daemon-owned server set. The daemon persists only governance state (trust, overlays, overrides, a session's own switches) and derives inventory on read; an acknowledged mutation survives daemon restart because the provider store holds it.
- **The operating system's credential store** holds, per signed-in server, the daemon's refresh token and, for a server that demands DPoP tokens, its signing key, each under an item the daemon created and removed with the sign-in ([ADR-040](../decisions/040-mcp-credential-custody.md)), on Windows, native and WSL alike, through the service's Windows half at `CRED_PERSIST_LOCAL_MACHINE`; neither ever enters SQLite.
- **Events are the audit trail**: every mutation and transition appends through the Plan-005 `EventLogService` path and replays like every other category. Node-scoped events bind to the daemon-scope sentinel session per [Spec-005 §Daemon-Scope Event Binding](./005-session-event-taxonomy-and-audit-log.md#daemon-scope-event-binding).
- **Replay/recovery impact**: idempotency classes the person assigns change what [Spec-013](./013-persistence-recovery-and-replay.md) recovery may safely replay — which is exactly why assignment is trusted-server-only, Cedar-gated, and audited.

## Example Flows

- `Example: live server add on Claude` — the person calls `mcp.upsertServer` (provider `claude`, scope `user`); the daemon persists the declaration via `claude mcp add-json linear <json> --scope user` and verifies the write; on a streaming-input session the daemon additionally computes the full desired named-server set and calls `setMcpServers` — that call is itself the availability answer, not a probe of it — reconciling `{added: ["linear"], removed: [], errors: []}`; it upserts an untrusted trust row for the `(claude, user, "", linear)` binding, emits `mcp.server_config_changed` (grade `live_reconcile`) then `mcp.server_status_changed` (`starting` → `connected`), and returns the inventory entry with grade `live_reconcile`. Had that reconcile been refused, the same call would return `user_config_write` with the declaration already durable.
- `Example: Codex write conflict` — two of the person's devices race `mcp.setEnabled`; the second write's `expected_version` is stale; the daemon re-reads, retries once against the new version, succeeds, triggers `config/mcpServer/reload`, emits `mcp.server_config_changed` (grade `user_config_write`).
- `Example: trust drift` — the person trusts `github` at hash `b3:abc…`; a later inventory refresh parses a changed `http_headers` block, hash now `b3:def…`; the daemon auto-revokes before use, emits `mcp.server_trust_changed` (`reason: 'config_drift'`), and the server's annotations stop informing approval decisions until re-trusted.
- `Example: one sign-in, both providers` — the person presses `Sign in to this server` on `notion`; `mcp.oauthLogin` → the daemon discovers the server's authorization server, registers itself, and returns the sign-in page's address; the desktop opens it in the browser; the person consents once; the daemon's callback completes, the refresh token goes into the credential store under the daemon's own item, and the daemon emits `mcp.server_oauth_completed` (`outcome: 'success'`). A Claude Code session's `headersHelper` and a Codex session's fronted connection both get a current access token from the daemon, and each leg flips `needs-auth` → `connected`; the Codex session's command list gains the server's prompts. `mcp.oauthLogout` later deletes the token and every leg reads `needs-auth`.
- `Example: a server saved with the repository` — the person adds `postgres` for Claude Code at `In this project, saved with the repository` for project `app`, naming `DATABASE_URL` with no value, then adds it again for Codex, since each add registers a server for one provider; the daemon writes `app/.mcp.json` through `claude mcp add-json … --scope project` for the first and, for the second, edits `app/.codex/config.toml` in place, reads it back with `config/read`, and reloads; each write commits with its recomputed hash and `mcp.server_config_changed`. Sessions in `app` get the server; sessions elsewhere do not. A `.mcp.json` server that arrived with a pull starts untrusted and joins no session until the person trusts it.
- `Example: safety-weakening override denied` — the person sets `idempotencyClass: 'idempotent'` on a tool of an untrusted server; the daemon returns `mcp.trust_required` before any write; after `mcp.setTrust` grants trust, the same call succeeds and emits `mcp.tool_override_changed`.

## Implementation Notes

- **Re-verify at execution.** Every provider mechanism above is Verified at the pins the [provider-wire reference](../reference/provider-wire/README.md) records, or version-anchored beyond them (`mcp_set_servers` at `2.1.210` — an **upstream feature anchor**, unaffected by any re-pin, and one that now sits below the driver's admission floor); Plan-025 code MUST re-verify load-bearing shapes against the then-installed binaries per that README before binding. Re-verification is **detection against the running build**, not a version comparison: [Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior) binds each capability to its own declared mechanism — a zero-turn, non-mutating, granularity-decisive probe where one is admissible, and a declared `static` reading naming the failing conjunct where none is — precisely because a version bounds availability from neither side. `mcp_set_servers` is not a capability flag at all — it is a control-request subtype no driver-side probe may issue — so its live answer comes from the reconcile itself, and a refusal there withdraws no flag.
- **Codex per-conversation configuration.** A conversation's `thread/start` configuration takes `mcp_servers`: a whole table replaces the service's table for that conversation, and the dotted form `mcp_servers.<name>` merges with it. The daemon sends the whole table, each server a `url` entry on its route, enabled or not — the per-session mechanism on Codex, never a flag on the shared service.
- **MCP revision watch.** The MCP 2026-07-28 revision restructures the protocol core (stateless core, Tasks → extension, Roots/Sampling/Logging deprecated); both providers will absorb it in their own releases. The governance layer binds to _provider surfaces_, so there the revision lands as provider-behavior changes caught by the re-verify rule; the daemon's own client takes it through its MCP client library, re-verified the same way.
- **The daemon's own MCP client** is `@modelcontextprotocol/client` 2.1.0, the one maintained MCP client that signs DPoP proofs; `@modelcontextprotocol/sdk` stays in the daemon only to host Playwright's tool server. The client implements the provider's `discoveryState` and `saveDiscoveryState`, which bind a sign-in's callback to its authorization server. It serves the fronted route, Codex's prompt list over the connection it already holds for the server, so listing prompts never starts a second copy of it, the workflow MCP-tool step and the recovery sweep of task handles.
- **Claude Code session set.** The daemon drives `claude mcp add-json` / `claude mcp remove` at the binding's `--scope` as the durable-write mechanism. Each session's process starts with `--strict-mcp-config`, so nothing the project, the account or a plugin configures loads by itself, and only the daemon's own tool entry rides `--mcp-config`; right after start the daemon sends the session's set with `mcp_set_servers`, built from the run-admission drift gate's fresh read (§Trust Governance) — every scope's effective bindings plus governance overlays, a repository-borne `project` server only while trusted, less the session's own switched-off servers — and sends it again after each resume, because the set lives only in the process's memory. Determinism means the session sees exactly the set the daemon sent, immune to mid-run ambient drift, while ambient edits (the person using the provider's own CLI directly) flow into the next send and the inventory. Because the daemon, not Claude Code's load of `.mcp.json`, supplies the set, Claude Code's own approval prompt for a repository's servers never runs, which is why the trust grant stands in for it (§Trust Governance), and `${VAR}` references in a `project` declaration are expanded by the daemon before sending (§Configuration Mutation).
- **Config-hash normalization and transient-secret handling.** Hash inputs normalize the server config to the daemon's canonical shape (sorted keys via JCS, provider-native field names preserved) so cosmetic reordering does not flip hashes, but any semantic change to the base config (URL, headers, env, command, timeouts, `required`, auth) does — credential-bearing values included, so a rotated or tampered secret drifts the hash like any other semantic change. The daemon-managed override-projection fields are excluded per §Trust Governance — they are governed and audited through the override store, not the trust binding. The custody model for the credential-bearing input is transient-by-construction: parse the provider-owned file in memory, canonicalize, feed the keyed hash (the binding's derived config-hash subkey as the BLAKE3 key), discard — the values are never persisted, logged, served, or embedded in any payload, and the keyed digests are the only derived artifacts that survive — the base-config hash and the event-side `scopeRefDigest` alike. **Key custody is one artifact:** the daemon holds a single 32-byte **governance key**, generated at first governance use and sealed under the daemon master key in the daemon's database like every other daemon key, as the `daemon_secrets` row whose `purpose` is `mcp_governance`, in its `sealed_secret` column ([Spec-020 §Daemon Master Key](./020-data-retention-and-gdpr.md#daemon-master-key)), with no key file; every digest key is a purpose- and binding-separated subkey derived from it via BLAKE3 keyed-PRF (the config-hash, scope-ref, and receipt-digest subkeys) — keyed mode takes exactly a 32-byte key, and the key rests in the database only sealed under the daemon master key, which never enters the database, so no stored or served digest can be brute-forced from a database copy or backup alone. Losing the master key is fail-closed by construction: no key, no comparable hash, no trust — re-granting re-binds under the regenerated key.
- **The fronted connection's secrets.** To reach a server it fronts, the daemon starts it with the environment values its declaration holds, or connects with its headers, reading those values from the provider's config when it connects and holding them only in memory for that connection; they are never stored or logged. The same transient rule covers the `${VAR}` values the daemon expands for a Claude Code session's set, held only for that `mcp_set_servers` call.

## Pitfalls To Avoid

- **Writing the Codex project file blind.** Codex rejects project paths for its own config writes, so the daemon edits `.codex/config.toml` itself; an edit that is not format-preserving, not guarded by the file's hash, or not read back through `config/read` can destroy the repository's own comments or land a server Codex never loads.
- **Using `mcp_toggle`.** It saves "off" for the whole project, so later sessions start with the server off, and it leaves the server running; a switch is always another full-set `mcp_set_servers` call.
- **Renewing a sign-in someone else holds.** A server rotates a public client's refresh token on every renewal, so renewing a sign-in the person's own Claude Code or Codex holds signs that provider out; the daemon renews only sign-ins it holds.
- **Putting a value into a repository file.** A `project` declaration takes names only; a value typed there is refused before anything is written.
- **Collapsing scope bindings.** Two scopes declaring the same `serverName` are different configurations with independent status, trust, and overrides; folding them into one node-global identity makes legitimate per-scope configs look like config drift (trust ping-pong) and bleeds one scope's overrides into the other.
- **Trusting annotation self-claims.** A server saying `readOnlyHint: true` is data, not authorization; only the trust store the person manages admits annotations into decision surfaces (the ADR-015 MUST — stable MCP-spec language since 2025-03-26).
- **Delta-sending `setMcpServers`.** The call replaces the full named-server set; sending a delta silently removes every unsent server. Always send the full desired set.
- **Treating `--help` as the capability census.** The Claude CLI's `--help` omits real flags; capability detection and the provider-wire reference are authoritative (the documented `--help`-non-authoritative rule).
- **Echoing secrets.** Config values, env vars, headers, tokens, authorization URLs, and URL query-string values never enter events, inventory reads, errors beyond guidance messages, or logs; `bearer_token_env_var` names an env var — the _name_ may appear in inventory, the _value_ is read only for a fronted connection and never stored or served; a server URL round-trips query-redacted (parameter names only — §Unified Inventory).
- **Treating the hash exclusion as a drift exclusion.** The override-projection fields are excluded from the base-config hash so governed writes never self-revoke — not because they are unobserved; skipping their reconciliation against the baseline-anchored expected state would let an out-of-band `enabled_tools` broadening ride into a run under an unchanged hash (§Trust Governance).
- **Erroring after the durable leg committed.** A mutation whose durable leg has committed MUST NOT surface a later live-leg failure as a JSON-RPC error — the caller would retry a write that already landed. Committed-then-degraded outcomes are successful responses with honest `applied` grades and per-leg `liveResults[]`; `mcp.config_invalid` exists strictly pre-commit.
- **Conflating a server's request for input with governance authorization.** A tool server's elicitation (the session's question card, session-scoped, interactive) and the `mcp` Cedar actions (this spec, node-scoped, non-interactive) are different layers; routing governance through an interactive answer would deadlock headless operation.
- **Polling provider status.** Both providers push (notifications / feed emissions); polling is on-demand-only.

## Acceptance Criteria

- [ ] `mcp.list` merges all four sources and round-trips both providers' declared servers with correct `(provider, scope, scopeRef, serverName)` binding separation — same-named servers in two scopes surface as distinct entries whose status, trust, and overrides never cross
- [ ] Claude mutation persists through `claude mcp add-json --scope <scope>` before acknowledgment and survives a daemon restart (the restarted daemon's inventory and the next session's `mcp_set_servers` set both contain it); on a reachable control channel the same call additionally applies live and returns grade `live_reconcile`, otherwise `user_config_write`
- [ ] Codex mutation writes user scope with `expected_version`, retries a conflict exactly once, triggers reload, and surfaces `mcp.config_write_conflict` on double conflict
- [ ] A `project` write lands on both providers — `<project>/.mcp.json` through `claude mcp add-json --scope project` and `<project>/.codex/config.toml` through the daemon's edit with its comments and layout intact and its project layer listing the server on `config/read` — and a `local` write lands in the project's entry in `~/.claude.json` and, on Codex, as a switched-off user entry switched on only in that project's sessions; a Codex project file changed since the daemon read it refuses with `mcp.config_write_conflict`, file unchanged; a value typed at `project` scope refuses with `mcp.config_invalid`, both files unchanged; an `enabled` or `approvalMode` facet on a Codex `project` binding refuses with `mcp.config_scope_unsupported`, and nothing else refuses with that code
- [ ] A `project` binding that came with the repository joins no session's set while untrusted — absent from the Claude Code `mcp_set_servers` set and `enabled = false` in the Codex `thread/start` table — joins after `mcp.setTrust`, and leaves again on a drift auto-revoke; a server the person rejected in Claude Code stays out; a server the daemon wrote at any scope joins at once
- [ ] Binding refs are structurally valid at the schema layer: `scopeRef` rejected for `user` scope and required non-empty for `project`/`local` on both providers — each as a typed validation error, never a database constraint failure; the DDL CHECKs mirror the same rules as defense in depth
- [ ] No Claude Code process is ever sent `mcp_toggle`; a session switch reaches the process as a full-set `mcp_set_servers` call applied from the next turn, and a new session starts with every server on
- [ ] `mcp.get` returns the redacted `McpServerConfigView` round-tripping every non-secret field `mcp.upsertServer` accepted (transport, command/args, the query-redacted URL plus its query-parameter names, timeouts, `required`, `bearerTokenEnvVar`, the Codex auth references, env-var and header **names**) with zero secret values anywhere in the response, and an update leaves unmodeled provider fields byte-identical — a `?api_key=…` URL serves scheme + host + path with `api_key` listed by name and its value absent; per-leg `legs[]` surfaces divergent concurrent-session statuses that the top-level aggregate `status` ranks deterministically (`unknown` legs included, per the fixed order), each `session_feed` status event carries its leg's `bindingId`, and a terminated session's leg retires — its last status (a `failed` included) no longer participates in the aggregate
- [ ] An out-of-band provider-config edit followed immediately by a run start is caught by the run-admission drift gate: revocation and weakening neutralization complete (events emitted, Codex native fields reverted) before the provider process spawns, and the run's config reflects the post-drift state — including a projection-field-only edit (`enabled_tools` / `disabled_tools` / `tools.<t>.approval_mode`) whose base-config hash is unchanged, and the daemon-restart variant: the same edit made while the daemon was down completes drift processing before startup recovery adopts or resumes any provider session
- [ ] Replaying a governance mutation with the same `clientIdempotencyKey` and identical request returns the recorded response with no second provider call, store write, or event; the same key with a differing request fails `mcp.idempotency_conflict` leaving the original untouched — both verified across a daemon restart; a crash between the durable provider write and receipt finalization reconciles at startup (the audit event appends exactly once — late, never lost, never doubled); the `mcp.oauthLogin` receipt row and its replayed acknowledgment contain no `authorizationUrl`
- [ ] A Claude durable-success/live-failure mutation returns success with `applied: 'user_config_write'` and a per-leg `liveResults[]` failure entry — never a JSON-RPC error after the durable commit, and never an unreported live failure
- [ ] `enabled: true` on a provider-disabled tool of an untrusted binding fails `mcp.trust_required`; the same override under trust applies and is neutralized on revocation like every weakening facet
- [ ] One `mcp.oauthLogin` and one consent let a Claude Code session (through `headersHelper`) and a Codex session (through the fronted connection) reach the server and list its prompts on Codex; a server that admits only one provider's client is signed in through that provider's flow in a throwaway home that is deleted afterward, and the daemon renews it under that client id; a DPoP server is reached from both providers with a proof on every request; `mcp.oauthLogout` deletes the refresh token (and the DPoP key) and every leg on both providers reads `needs-auth` on its next call; a sign-in held by the person's own provider outside the app is never read or renewed; no token, code, PKCE value or key appears on any event, error, log, receipt, read model, wire payload, renderer state or helper command line
- [ ] An asynchronous sign-in completion failure is delivered as `mcp.server_oauth_completed` with `outcome: 'failure'` on the `mcp.subscribe` stream (never a late JSON-RPC error); `mcp.oauth_flow_failed` remains reachable via a launch-phase failure; a second `mcp.oauthLogin` while a sign-in waits ends the first
- [ ] On Codex a fronted call past 120 s, or one running when the daemon steers the conversation, is answered with the handle text, `task_output` and `task_stop` work on it, its result is delivered once by `turn/steer` or `turn/start` — once across a daemon restart for a task-augmented call — and the route adds at most 5 ms to a fronted call; on Claude Code a call past 120 s moves to the background under `CLAUDE_AUTO_BACKGROUND_TASKS=1`
- [ ] `mcp.registrySearch` returns results only for a typed query, fills the declaration form with names and no values, and keeps nothing past the page; a server added from it starts untrusted
- [ ] After a move between Windows and a WSL distribution, a server whose command names a program on the side the service left reads `failed` with `failedReason: commandNotRunnable`, and a bare command name is looked up on the new side
- [ ] The subscribe-then-list handshake is gap-free: an event appended between a subscriber's `mcp.subscribe` acknowledgment and its subsequent `mcp.list` read is delivered on the stream, and the stream delivers nothing appended before the acknowledgment
- [ ] First observation of an unknown server creates an untrusted trust row; no code path creates `trusted = 1` without the person's `mcp.setTrust`
- [ ] Base-config drift on a trusted binding auto-revokes before use and emits `mcp.server_trust_changed` with `reason: 'config_drift'`; a daemon-governed override write does NOT drift the hash, and revocation reverts Codex-materialized weakening fields in the same operation
- [ ] Safety-weakening overrides on untrusted servers fail with `mcp.trust_required`; safety-tightening overrides succeed regardless of trust; a weakening facet granted under trust stops resolving the moment trust is revoked
- [ ] An `idempotencyClass` the person assigns reaches the Spec-004 tool-metadata resolution output; absent assignment resolves to `manual_reconcile_only`; resolution is binding-keyed — with the same `serverName` bound in two scopes, each session's invocation resolves its own effective binding's override, never the other scope's
- [ ] A Codex binding whose user config already carries native `enabled_tools` / `disabled_tools` / `tools.<t>.approval_mode` values survives an override set → clear round-trip with those native values restored from the baseline; revocation rewrites weakening fields to the baseline-anchored safe state, never to an invented default
- [ ] With the trust store unavailable, `mcp.list` / `mcp.get` serve the degraded entry arm (`trustUnavailable: true`; trust- and override-dependent fields structurally absent, provider-observed fields and the key-derived `scopeRefDigest` intact) and every governance mutation fails closed
- [ ] `mcp.removeServer` emits `mcp.server_config_changed` with `previousConfigHash` and no `configHash` — the removal payload validates against the schema without fabricating a post-removal hash
- [ ] Each governance mutation emits its defined event set exactly once (single-event for most; a weakening-facet revocation's batch — the trust event plus its per-facet reversion events — appends all-or-nothing), with sentinel binding for node-scope events and real-session binding for session-feed status observations; `mcp.server_oauth_completed` is emitted exactly once per observed flow completion — an abandoned flow emits nothing and leaves only its expiring receipt; `mcp.reconnect` emits no governance event beyond the status transitions it induces
- [ ] Event and error payloads contain no config values, tokens, env-var values, or unsanitized paths — raw `scopeRef` included: project/local event payloads carry `scopeRefDigest`, never the path (schema-level test over every payload type and error code)
- [ ] Every `mcp.*` error code is reachable in integration tests and absent from success paths
- [ ] A mutation attempt by a caller who does not own this node fails with `mcp.operator_scope_required` before any store or provider mutation; the owner's own attempt succeeds identically over the local pipe and over the relay, so the same operation is never admitted on one transport and refused on the other
- [ ] The MCP servers page renders trust state, connection status, and effective idempotency class wire-verbatim and recomputes none of them; it renders no **withheld** value — no environment-variable value, header value, URL query value, or token — while still rendering the daemon's redacted `McpServerConfigView` read-back, so the non-secret declaration (transport, command and arguments, timeouts, the required marker, names without values, the query-redacted URL) can be inspected and edited as §The MCP servers page's read-back split and Plan-025 T28.5.7 both require; a criterion prohibiting configuration content as such would reject the edit workflow this page ships; it updates from `mcp.subscribe` rather than by polling; and each explicit action by the person produces exactly one wire mutation, with a daemon refusal rendered rather than pre-filtered away
