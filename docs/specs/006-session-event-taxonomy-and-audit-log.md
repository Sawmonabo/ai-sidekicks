## Required Behavior

- Every durable session-relevant change must emit a canonical event.
- Canonical events must include at least `eventId`, `sessionId`, `sequence`, `occurredAt`, `category`, `type`, `actor`, and correlation or causation metadata where applicable.
- The taxonomy must cover at least:
  - session lifecycle
  - invite and membership
  - participant and runtime-node presence
  - channel and agent lifecycle
  - run lifecycle
  - queue and intervention
  - approval requests and resolutions
  - repo, workspace, and worktree lifecycle
  - artifact and diff publication
- Events must be immutable after append.
- Ordering is **per-aggregate, not global** (B1): within a single run, event order is preserved, and tool events pair by `toolCallId` (the canonical Tool Activity **payload** field — `payload.toolCallId`; provider-native tool-call identifiers such as `tool_use_id` normalize into it); **no global causal-order guarantee exists across aggregates** — consumers MUST NOT infer cross-aggregate causality from interleaved positions across runs, channels, or sessions. The ingest-side bounded reorder buffer's parameters (bound, overflow = flush-in-arrival-order + diagnostic, pairing timeout) are the consuming plan's to name; this spec fixes only the guarantee's scope.
- Replay must support reading after a known cursor and reading bounded windows.

## Default Behavior

- Canonical event metadata is retained indefinitely unless an explicit retention policy supersedes it.
- Per-session event ordering is presented as a monotonically increasing sequence in session projections.
- High-volume payloads may be compacted, but their audit stub must preserve type, actor, timestamps, and provenance.

## Fallback Behavior

- If a client detects a live-stream gap, it must rehydrate from the canonical event log starting after the last acknowledged sequence.
- If full payload data has been compacted, the system must still return an audit-visible stub rather than pretending the event never existed.
- If a producer cannot emit a canonical event immediately, the related state change must not be considered committed.

### EventEnvelope Version Semantics

Full semantics of the `.version` field are specified in [ADR-018: Cross-Version Compatibility](../decisions/018-cross-version-compatibility.md). The binding contract summary:

> **Terminology note — "version stub" vs. "compaction stub":** This section uses "**version stub**" for the receiver-side artifact produced when an unknown-type event is preserved verbatim (full canonical bytes retained so the Ed25519 signature stays verifiable). This is structurally distinct from the "audit stub" form produced by §Event Compaction Policy below, which removes `payload`, `correlationId`, and `causationId` and replaces them with a `summary`. A version stub retains all canonical fields; a compaction stub does not. A version stub is only eligible for compaction once it has been re-interpreted at least once, per `ADR-018 §Decision` #11.

- **Format:** Semver string `"MAJOR.MINOR"` (no PATCH component on the wire). Integer form is not used.
- **Producer sets it:** The emitting daemon writes its own outgoing wire version at emit time. `.version` is never copied from a received event. Version stubs record their original received version in version-stub metadata, separate from `.version`.
- **Validation is two-sided:** The control plane validates at write time; receiving peers validate on parse. A receiver that cannot interpret a given `.version` MUST persist the event as a version stub rather than drop or crash.
- **Unknown MAJOR (same or higher than receiver's supported MAJOR):** Persist as version stub with full original canonical bytes; never dispatched to application handlers. The canonical row's `.version` field stays the producer's original — version-stubbing is a read-side behavior, not a rewrite. On upgrade, the upcaster chain transforms the stub to a typed event at dispatch time; the log row is never rewritten.
- **Unknown MINOR (same MAJOR, higher MINOR):** Event dispatches normally; unknown optional fields and unknown enum values within the payload are preserved verbatim for future upcasting. MINOR bumps MUST be additive-only per ADR-018.
- **MAJOR mismatch at session join:** Hard error with typed code. `VERSION_FLOOR_EXCEEDED` if client is below `session.min_client_version`; `VERSION_CEILING_EXCEEDED` if client is above the session's highest supported MAJOR. Errors carry a human-readable upgrade/downgrade path; join is rejected, client does not crash. Both codes MUST be registered in [Error Contracts](../architecture/contracts/error-contracts.md) before the first Plan-001 emitter lands.
- **Below-floor clients may READ but NOT WRITE.** A below-floor write attempt returns `VERSION_FLOOR_EXCEEDED` while the client remains joined in read-only state.
- **Immutability:** `.version` is set once at producer emit time and is part of the event's durable identity. It is never rewritten by upcasters, version-stub re-interpretation, or upgrade processes. This is load-bearing for the §Integrity Protocol hash-chain and signature invariants — the signed bytes include `.version`, so rewriting it would break all downstream verification.
- **Envelope version vs. event-type registry:** `.version` governs the envelope contract only. New event-type introductions are additive and MAY be allowed under the same envelope version if they follow the additive-only MINOR rule. V1 uses an accept-and-stub model for unknown types (each unknown type becomes a version stub on receipt); a central control-plane event-type registry is deferred to V1.1 per `ADR-018 §Alternatives Considered` Option C.

## Event Type Enumeration

This section enumerates every individual event type within each `EventCategory`. Each type is a string value for the `type` field of `EventEnvelope`. The payload fields listed are the category-specific fields carried inside the `payload` object; the envelope-level fields (`id`, `sessionId`, `sequence`, `occurredAt`, `category`, `actor`, `correlationId`, `causationId`, `version`) are always present and are not repeated here. One **cross-cutting payload field pair** spans categories (registered 2026-07-20 — the campaign-B9 CP-004-12 epoch-attribution carrier whose typed shape [Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior) delegates to this spec's plan bundle): `sourceEpoch?` — a nonnegative integer naming the **pre-rollback execution epoch** a late-appended **non-lifecycle** row is attributed to — with its companion `sourcePosition?` — a nonnegative integer naming the **normalized session position** (the turn-boundary vocabulary of Spec-004's `targetPosition`) that row occupies within its source epoch, registered because no run-scoped family's payload carries a native position key and the supersede cutoff (`turn > targetPosition`) cannot rank a late row against its epoch's surviving prefix without one — stamped **together** at ingestion by the run-engine's late-append leg (Plan-004 T3.11) — the pair from the straggler's **per-event operation association**, each provider-side operation recorded against the (epoch, turn) current when it opened, pre-fence (an association-less pre-epoch straggler falls back to the closed delivery generation's retained pair, a conservative always-superseding upper bound — [Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior)'s fence and generation-rotation semantics own the mechanics) — exactly when that cursor attributes the row to a superseded epoch (the atomic closed-pair `driver_ask.requested` + `driver_ask.canceled` late-append included), and absent on every current-epoch row — absence means current-epoch, the pair travels together with the row's `runId` (a stamped payload REQUIREs all three — the pairing rule below), and the stamp is never fabricated at read time. The field is admitted by the payload schemas of exactly the run-scoped families that late-append window covers — `assistant_output`, `tool_activity`, `usage_telemetry`, `artifact_publication`, and the `interactive_request` closed pair — and by no others (a `run_lifecycle` straggler is absorbed, never appended; non-run-scoped families carry no run epoch): every canonical `SessionEventSchema` payload branch of those five families **whose variant is run-scoped** — the payload carries `runId` — MUST admit the optional pair via the Plan-006 T1.9 composition helper, whose pairing refinement is schema-enforced (either stamp key present ⇒ both present and `runId` present), so a stamped row validates through the canonical read path and is never rejected at subscription or replay validation; variants without run attribution never admit it — the account-plane sentinel-bound `usage.rate_limit_update` (no `runId` — §Usage Telemetry) foremost — because an epoch stamp on a row with no run identity is unattributable by construction. The field lives inside `payload`, so it sits in the §Canonical Serialization Rules canonical bytes — signed, hash-chained, and shred-safe like any payload field, with **no envelope-level field added** (the canonical-set membership is unchanged) and no version bump: this registration precedes [ADR-018 §Reversibility Assessment](../decisions/018-cross-version-compatibility.md#reversibility-assessment)'s point of no return, which is an **emission event, not a code merge** — the project is pre-first-release with no production deployment, so no `"1.0"` envelope has been emitted in a non-test environment as of 2026-07-20 (shipped emitter code on `develop`, the Plan-003 runtime-node emitter included, does not cross it) — so the pair is part of the v1.0 baseline payload contract from first emit, exactly as the campaign's earlier baseline field registrations rode (`executionPosture`, the B1 terminal keys); the same fields added after that point would be a MINOR envelope bump per `ADR-018 §Decision` #8's new-optional-field rule composed with §EventEnvelope Version Semantics' higher-MINOR preservation, and Plan-006 T1.9 carries the matching conditional: crossed before it ships, the implementer takes the `"1.1"` bump with producer and golden-vector updates — and replays durably: the [Spec-004 §Driver-Level Rollback Mechanics](004-queue-steer-pause-resume.md#driver-level-rollback-mechanics) supersede projection consumes it for cross-epoch keying, and the audit-stub projection preserves it at compaction (§Compacted Event Format). Execution-epoch semantics — `0` before any rollback, advancing with each **accepted `run.rolled_back`** (a confirmed conversation rewind, regardless of the file-leg disposition) — are owned by [Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior) and [Run State Machine §Invariants](../domain/run-state-machine.md#invariants), not redefined here; the typed Zod shapes (`SourceEpochSchema` / `SourcePositionSchema`, the `SOURCE_EPOCH_PAYLOAD_KEY` / `SOURCE_POSITION_PAYLOAD_KEY` consts, and the pairing-refinement composition helper) are [Plan-006](../plans/006-session-event-taxonomy-and-audit-log.md) T1.9's, in `packages/contracts/src/event.ts`, mirrored in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md).

Re-reading the source definition at replay time is not the alternative: it may have been edited or deleted, which is the whole reason the columns are a snapshot. All four are **attach-time only** — `agent.configUpdate` carries no such member, so `agent.config_updated` needs no matching growth and none is added) so the `agents` projection is replay-complete and deterministic from the log alone (`state` is `'ready'` or `'configured'` per the domain lifecycle — [agent-channel-and-run-model.md §Lifecycle](../domain/agent-channel-and-run-model.md#lifecycle)); `agent.detached` carries `{sessionId, agentId, state: 'disabled', actor}`; `agent.config_updated` carries `{sessionId, agentId, name?, modelId?, defaultNodeId?: NodeId | null, config?, state?, actor, pendingSwitch?}` (changed fields only — `defaultNodeId` mirrors the request tri-state: absent = unchanged, `null` = the pin-clear (replay writes table `NULL` = any local attached node), value = rebound; `state?` present when a node rebind flipped `configured` ↔ `ready`). `pendingSwitch?` is the 2026-08-26 provider axis (D-016-26), additive-optional per [ADR-018](../decisions/018-cross-version-compatibility.md), and it carries that axis **as an intent rather than as a fact**, in the same `AgentProviderSwitchPending` shape the mutation's response returns: `{status: 'pending', switchId, appliesAt: 'turn_boundary' | 'run_boundary', interruptRequested, pendingAxes: {driverName?, providerAccountId?, modelId?, effort?, outputSpeed?}, replacedSwitchId?}`. `interruptRequested` is the caller's `interruptAndSwitch` arm made observable, and it is carried rather than re-derived because `appliesAt` does not imply it — a deferred switch and an interrupted one can both read `'turn_boundary'`, so a projector or a restarted daemon reading the boundary alone cannot tell which one owes an interrupt. One shape across the wire reply and this payload is what lets a client and a projector read the same record of the same intent; the durable `agents.pending_switch` slot is a **superset** of it, adding the two recovery-only members ([api-payload-contracts.md §Plan-016](../architecture/contracts/api-payload-contracts.md)) that no caller and no payload ever sees — the admitting principal, recorded under the §Authenticated Principal class rule because a switch settling after a restart has no request left to resolve an `actor` from, and the `'requested'` \| `'dispatched'` interrupt-dispatch progress that keeps recovery from firing a second interrupt at a run that already took one — and `pendingAxes` carries the **target values**, not merely the axis names, because an intent recording only which axes moved could not be applied at a boundary the caller is no longer waiting at. Every other top-level member of this payload is **effective at append**; the five provider axes are not, so they ride inside `pendingAxes` and are never also set at top level. The nesting is what makes the payload projectable rather than merely complete: a provider switch appends this event at **mutation**, so a projector reading a top-level `driverName?` as "the driver changed" would move the binding into the effective columns at a moment the switch has not happened — precisely the projection [Spec-016 §Same-Agent Provider Switch](./016-multi-agent-channels-and-orchestration.md#same-agent-provider-switch) forbids. Keyed on `pendingSwitch` instead, a projector writes the pending slot and touches no effective column, and the effective move is written by the **terminal**: `agent.provider_switched` carries the `to*` binding and clears the slot, `agent.provider_switch_failed` clears the slot and leaves the columns untouched. So this event is appended exactly once per switch, at mutation, and `agents` — pending promise included — stays rebuildable from the log alone. The pre-existing top-level `modelId?` is retained for pre-amendment history and is unset by post-amendment emitters, every model change now being boundary-scheduled; `agent.provider_switched` carries `{sessionId, agentId, switchId, fromDriverName, toDriverName, fromModelId, toModelId, fromProviderAccountId?, toProviderAccountId?, fromEffort?, toEffort?, fromOutputSpeed?, toOutputSpeed?, continuity: 'in_place' | 'replayed' | 'memo', declaredLosses: DeclaredLossKind[], actor}` (2026-08-26, D-016-26; the output-speed pair added 2026-08-29 with the fifth axis, on the same replay-completeness ground as the pair before it — the terminal is what writes the effective column, so a settled speed the log could not rebuild would leave `agents.output_speed` NULL on replay while the pending slot had already been cleared). The `to*` members record the value the switch **requested and committed**, which is that column's own content; what the new binding's provider then **declared** is a live reading and is deliberately not evented, an observation captured once being a second and staler record of a fact the running session already holds ([Spec-005 §The output-speed axis](./005-provider-driver-contract-and-capabilities.md#the-output-speed-axis)). It is emitted **in addition to** `agent.config_updated`, not instead of it: the config event records the mutation, this one records the continuity consequence, and a consumer that renders only the first is still correct about the agent's configuration. `switchId` is the daemon-minted correlator the mutation's response carried — as the pending acknowledgment's id on the deferred arm, as the settlement's own id on the immediate one — so a client that was told a switch was coming can match it to the terminal that settled it. `continuity` is closed at three values and is the wire's honest-degrade discriminator — `'in_place'` where a per-turn-override axis was carried into the next turn on the running process with nothing respawned and nothing replayed, `'replayed'` where the canonical transcript reached a fresh target session, `'memo'` where it could not and the bounded prose projection stood in ([Spec-005 §Canonical Transcript Export And Replay](./005-provider-driver-contract-and-capabilities.md#canonical-transcript-export-and-replay)); the first two are `applied` and only the last is `degraded`. `declaredLosses` is a **closed vocabulary, not free text** — V1 members `'provider_private_reasoning'`, `'context_truncated'`, `'tool_call_history_repaired'`, `'conversation_history_summarized'`, `'turn_content_unavailable'`, `'turn_content_truncated'` — and it is **required**, because an empty array is the positive assertion that nothing was dropped and an absent one would be indistinguishable from a driver that did not know. Requiredness is **arm-scoped** so that assertion keeps its meaning: `'in_place'` carries the empty array by rule, `'memo'` MUST be non-empty and MUST include `'conversation_history_summarized'`, and `'replayed'` may be either. The sixth member, **`'turn_content_truncated'`** (2026-08-30, the machine-authored prose amendment), is the second produced at pipeline step 1 (Fold) and the sibling of `'turn_content_unavailable'`: where that member names a logged turn whose body could not be **read**, this one names a logged turn whose body was **stored as a prefix** because it exceeded `CONTENT_PAYLOAD_PLAINTEXT_MAX` at append. It is minted rather than folded into `'context_truncated'`, whose own scope is the memo budget evicting whole exchanges and never halves — reusing it for a halved body would contradict the member it borrowed. It is likewise not `'turn_content_unavailable'`: a truncated turn **is** available, and reporting it unavailable would overstate the loss as surely as silence would understate it. Declaring it is [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md)'s declared-loss principle applied at the operation that drops the bytes; the prefix replays, and the reader is told it is a prefix. The `from*` members are the daemon's record of the binding being left, so the event is self-contained on replay and a reader never has to fold backwards to learn what changed. `agent.provider_switch_failed` carries `{sessionId, agentId, switchId, fromDriverName, fromModelId, fromProviderAccountId?, fromEffort?, attemptedDriverName?, attemptedModelId?, attemptedProviderAccountId?, attemptedEffort?, attemptedOutputSpeed?, reason: 'driver_unavailable' | 'model_unavailable' | 'effort_unavailable' | 'account_unavailable' | 'output_speed_unavailable' | 'interrupt_refused' | 'target_unstartable', actor}` (2026-08-26, D-016-26) and is the **sibling terminal** of the type above, not a variant of it: an accepted switch is recorded pending in the log at mutation on **both** arms, and the pending slot is cleared by a terminal rather than by a reply, so an application-time refusal reaching no event would leave a promise no replay can clear. It is therefore emitted on both arms — on the deferred one it is the only refusal that reaches anyone, the caller having since disconnected; on the immediate one it appends in addition to settling the held-open request as the `failed` disposition, because a reply is not a durable record and the projection cannot be rebuilt from one. Emitting it under the `switched` name instead was rejected — an event whose name asserts a switch occurred is the wrong record of one that did not. The `from*` members are unchanged by construction (a failed application moves nothing), the `attempted*` members name what was asked for, and `reason` is closed at seven members: widening it is an amendment. It deliberately does **not** reuse the `agent.provider_axis_invalid` `axis` discriminator (`driverName` | `modelId` | `effort` | `outputSpeed`, the request's own member names and a strict subset of the five-member axis union), and the two vocabularies are separate because they answer different questions: that error code answers a caller synchronously about a request that was never accepted and names the field to correct, while this reason explains why an **accepted** switch could not be honoured at a boundary the caller is not watching — a set that must also carry `account_unavailable`, `interrupt_refused`, and `target_unstartable`, none of which is a field of the request at all. One vocabulary spanning both would either drop those three arms or teach a client to render a fix-your-request hint for a failure no correction of the request would have avoided. A memo settlement is **not** a failure and never emits this type — it moved the agent and declared what came along; this type means the agent did not move at all. A superseded pending switch emits neither terminal, by the [Spec-016 §Same-Agent Provider Switch](./016-multi-agent-channels-and-orchestration.md#same-agent-provider-switch) supersession rule. The bootstrap `main` channel never emits `channel.created` — it is projected from the session itself (`deriveMainChannelId`, CP-002-7).

### Run Lifecycle (`run_lifecycle`)

One event per state from the [Run State Machine](../domain/run-state-machine.md)'s 9 canonical states, plus the forward (non-state) `run.rolled_back` event (B1).

Payload shape: `{sessionId, runId, runVersion, previousState, newState, channelId?, failureCategory?: RunFailureCategory, recoveryCondition?: RecoveryCondition ('recovery-needed' | 'reauth-required' — the named type per the campaign B3 hoist in the same API Payload Contracts mirror), recoverySpanClassification?: RecoverySpanClassification ('read_only' | 'idempotent_write' | 'irreversible' | 'unclassifiable' — the halted/diverged span's content classification, named type in the same contracts mirror; semantics per Spec-015 §Fallback Behavior, Part-B fail-closed follow-up 2026-07-17: audit metadata in V1, 'unclassifiable' handled exactly as 'irreversible'), trigger?: 'turn_limit' | 'budget_exhausted' | 'idle_timeout' | 'moderation_denied' | 'workflow_phase_cancelled' (the fifth value added 2026-08-11, Plan-016 D-016-23 — the canonical union matching the `run.interrupted` per-type row below and the api-payload §Plan-004 mirror; an event schema implemented from this owning shape admits the workflow cancellation event), completionKind?: 'turn' | 'task', intendedClose?: true, executionPosture?: ExecutionPosture}` — this state-transition shape governs the nine state events; `executionPosture?` (structural shape per the typed `RunStateChangeEvent.executionPosture?` mirror in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) — this bundle, the canonical in-corpus shape source; policy semantics per [Spec-012](./012-approvals-permissions-and-trust-boundaries.md), campaign B20 — PR #175, a named merge prerequisite for implementing posture semantics) is stamped only on `run.running` — the post-setup-gate spawn-success transition (Plan-004's gate seam admits `queued → starting`, then setup gates — Plan-010's execution-root gate among them — run **before** `driver.startRun`, so the resolved workspace root and effective posture are final only when `running` fires; a `run.starting` stamp would be premature) — recording the run's effective posture for audit, and is absent on every other transition (the audit-stub projection preserves `executionPosture` — and `credentialPolicyRef` when the payload carries it (present on the two sandboxed modes, absent under `mode: 'trusted'` per the Spec-012 execution-posture amendment, PR #175) — on posture-bearing `run.running` rows, §Compacted Event Format, so the boundary stays reconstructable after compaction); `run.rolled_back` is per-type (see its row) and carries no `previousState`/`newState`.

`runVersion` is the run aggregate's **any-run-progression counter** (Plan-004 D-004-1): it increments on every run progression — applied interventions included, not only the state transitions enumerated below — and is the optimistic-concurrency token the `expectedRunVersion` intervention guard compares against ([Spec-004 §Interfaces And Contracts](004-queue-steer-pause-resume.md#interfaces-and-contracts)). It is a **payload** field, distinct from the envelope-level `.version` (§EventEnvelope Version Semantics above): `.version` is the immutable semver wire-contract version bound into the Ed25519 signature, whereas `runVersion` is a mutable per-run counter carried inside `payload` — the two share the word "version" but are different contracts and must never be conflated. Because `runVersion` also advances on applied interventions that cause no state change (e.g. a native steer), the authoritative source of a run's current `runVersion` is the run-state read / `run.subscribeState` stream and the intervention / pause / resume responses, not the `run.*` event sequence alone. A no-state-change advance with **no per-type event of its own** (the native-steer case) is **not** broadcast as a discrete `run.*` event — there is no state transition to record ([Spec-004 §Driver-Level Steer Mechanics](004-queue-steer-pause-resume.md#driver-level-steer-mechanics)); the carved-out exception is the in-place rollback from `paused` (campaign B2), which also transitions no state but whose per-type `run.rolled_back` event (its row below) streams the fresh post-rollback `runVersion` — so a _non-intervening_ subscriber tracking `runVersion` off the event sequence may hold a stale comparand after a steer-like advance. Its next guarded intervention / pause / resume is then correctly rejected `expired` (the comparand genuinely _is_ stale — this is the optimistic-concurrency guard working, not a false rejection), whereupon it re-reads run-state for the fresh `runVersion` and retries: the reject → re-read → retry loop is the designed correction, and V1 adds **no** broadcast/read-model push for such no-per-type-event bumps. The _intervening_ caller never round-trips — its `RunControlAck` / `InterventionRequestResponse` / pause-resume ack carries the post-application `runVersion` directly (per [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md)).

**At-most-once terminal emission (B1).** For the three terminal types (`run.completed` / `run.interrupted` / `run.failed`), at most one terminal `run_lifecycle` event exists per `(runId, runVersion)`. The emitter owns the guarantee: the terminal guard + state swap + append execute under the per-session append lock with read-your-writes state, so a duplicate terminal attempt is rejected before append. A schema-level **partial unique index backstops** the emitter contract — `UNIQUE` on (`json_extract(payload, '$.runId')`, `json_extract(payload, '$.runVersion')`) `WHERE category = 'run_lifecycle' AND type IN ('run.completed', 'run.interrupted', 'run.failed')`, predicated on `session_events`'s real scalar `category` + `type` columns ([local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md)) — as a **fail-loud invariant detector**: an index violation surfaces a bug, never silently no-ops (an append-if-absent API remains rejected). The backstop index itself — and the projection-level CHECK below — ship with the campaign's B11 schema work (the append-lock bundle the design assigns them to), a named gate before any post-B1 terminal emitter treats the backstop as active; the schema mirror ([local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md)) gains the index DDL when that migration lands, and until then the emitter-side guard is the sole enforcement. Terminal payloads MUST carry non-null `runId` and `runVersion` (an emitter precondition, mirrored as that same projection-level CHECK): SQLite UNIQUE indexes treat NULLs as distinct, so a NULL key would silently bypass the backstop for exactly the malformed rows it exists to catch. The same NULL-bypass would reopen at compaction — §Event Compaction Policy replaces `payload` with the audit-stub projection — so the stub projection for terminal `run_lifecycle` rows MUST preserve `runId` + `runVersion`, keeping the index keyed for the row's whole retention life.

**Intended-close discriminator (B1).** A daemon-initiated `closeSession` produces a clean terminal: the terminal payload carries `intendedClose: true`, and consumers MUST NOT classify such a terminal as a crash. The field is absent on every other terminal path (natural completion, user cancel, failure), so its presence is the discriminator — orderly shutdown stays distinguishable from abnormal termination in the durable record.

Provider-initiated asks (B1) — the third `interactive_request` subfamily beside queue items and interventions: the provider CLI, mid-run, asks a human for something. Payload shape: `{sessionId, runId, askId, kind: 'permission' | 'input', toolName?, prompt?, input?, options?, expiresAt?, state: 'requested' | 'responded' | 'expired' | 'canceled'}` — for `kind: 'permission'` the payload MUST carry `input` (the normalized requested resource — command / path / tool arguments — the approval decision is about, so two same-tool asks are always distinguishable in audit) — post-amendment `driver_ask.requested` emitters MUST set `expiresAt` (ISO-8601: the bounded fail-closed deadline stamped at creation per [Spec-012 §Required Behavior](./012-approvals-permissions-and-trust-boundaries.md#required-behavior), Part-B fail-closed follow-up 2026-07-17; optionality is pre-amendment history only — enforced at the emission seam by the per-type refinement, campaign B13's `driverAskPayloadRefinementFor` (sibling of Plan-012 T1.1's `approvalFlowPayloadRefinementFor`): a post-amendment requested row without `expiresAt` fails the emission parse, never replay — and the other three states carry the requested row's deadline forward unchanged when they echo it) — `state` is the closed `DriverAskState` enum and MUST equal the emitting event type's suffix (denormalized so latest-row projections read one field; a mismatch is an emitter bug and fails loud, never repairs silently); `kind` discriminates permission-approval asks (Claude `can_use_tool` / `--permission-prompt-tool`) from structured-input asks (Codex `item/tool/requestUserInput` and MCP elicitation). Permission-kind asks route into the approval pipeline; input-kind asks route to the run's interactive surface. `options` (added 2026-08-29) is **additive-optional** and carries the closed choice set an input-kind ask offers, where the provider's own ask declares one — the Codex `item/tool/requestUserInput` and MCP-elicitation surfaces can, and the Claude control round-trip does not. It is produced at the **driver's normalize boundary** ([Spec-005](./005-provider-driver-contract-and-capabilities.md)) and never synthesized by a consumer, so its absence means the provider offered no choice set the driver's normalize boundary could represent, rather than that a represented one was lost in transit. The member is **bounded at that boundary and again in the payload schema** (2026-08-29) — a declared cardinality cap on the array and the same free-form-string bound the corpus's other untrusted provider strings carry on each option's `value` and `label` — because the set is provider- or MCP-authored and this is a durable canonical payload: unbounded, the 32 KiB canonical ceiling would be its first guard and an oversized but otherwise valid ask would fail at append, leaving a run waiting on an input card no one recorded. Bounded, the over-large set is dropped with a recorded driver diagnostic while the ask itself still arrives and its unconditional free-text arm still answers it — which is why the absence clause reads on representability rather than on the provider's intent. It is minted with its reader — the [Spec-013](./013-live-timeline-visibility-and-reasoning-surfaces.md) input-ask card, whose free-text answer arm is unconditional precisely because this member is optional, so an ask without it is still answerable. No event type is added and the taxonomy census does not move.

#### User Message Events

### Assistant Output (`assistant_output`)

Payload shape: `{sessionId, runId, channelId?, contentType?, contentLength?, contentTruncated?, contentCiphertextDigest?}`, with the message or reasoning **body itself** carried out-of-payload in `session_events.content_payload` (2026-08-30, the machine-authored prose amendment).

**The body has a durable home, and it is not `payload`.** `assistant.message` and `assistant.thinking_update` previously carried `contentLength?` and no body at all, which made these rows a record that an assistant spoke rather than a record of what it said — and left [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md)'s ruling that the canonical transcript is authoritative for the content of a provider session standing over a log holding none of it. The body now lands in the [`session_events.content_payload`](../architecture/schemas/local-sqlite-schema.md) envelope: sealed AES-256-GCM under the **session**-scoped content key, excluded from the canonical bytes exactly as `pii_payload` is, and committed to by the `contentCiphertextDigest` member (BLAKE3 over the ciphertext) that the signed `payload` carries in its place — so the signature binds the body without carrying it and survives the body's destruction. This is the same Encrypt-Then-Digest-Then-Sign order [Plan-006 §PII Columns](../plans/006-session-event-taxonomy-and-audit-log.md#pii-columns) already runs, applied to a second, differently-keyed column rather than duplicated.

`contentType?` and `contentLength?` keep their meanings and become the _stub-surviving_ description of a body that now exists: `contentLength` is the body's **pre-truncation** UTF-8 byte length, so a compacted stub still reports how much was said. `contentTruncated?` is present and `true` only on a row whose body exceeded `CONTENT_PAYLOAD_PLAINTEXT_MAX` and was stored as a codepoint-boundary prefix; absent means the stored body is complete. Both members are ordinary signed `payload` content and neither is a second copy of the prose.

| --------------------------- | ------------------------------------------------------------ |
| `assistant.message`         | The assistant has emitted a message to the session timeline. |
| `assistant.thinking_update` | The assistant has emitted a reasoning or thinking update.    |

### Cross-Node Dispatch (`cross_node_dispatch`)

Cross-participant runtime-dispatch lifecycle events produced by [Spec-024](./024-cross-node-dispatch-and-approval.md). Each dispatch crosses two daemons — the caller's and the target's — and each daemon appends the complementary events to its own local `session_events` log per [ADR-017](../decisions/017-shared-event-sourcing-scope.md); no shared Postgres event log exists for these events in V1. Payloads never carry full PASETO tokens or secret material — ApprovalRecord envelopes are referenced by `approvalRecordRef` pointing to the local `cross_node_dispatch_approvals` row, not embedded verbatim in events.

Base payload shape: `{sessionId, dispatchId, callerParticipantId, targetParticipantId, targetNodeId, capability, timestamp}`. Per-event payload extensions (on top of base):

- Pre-approval failure (`.rejected`): `+ {reason}` naming which step failed (invalid signature, expired token, body-hash mismatch, replay, undeclared capability, requested output schema unsupported by the executing driver — `output_schema_unsupported`, campaign B7 — or policy-engine error — plus the two `action_payload` canonicalization refusals the CP-006-3 obligation binds on Plan-027: an over-deep payload (`dispatch.payload_too_deep`) and an ill-formed one (`dispatch.payload_ill_formed`), which never collapse into one reason).
- Approval refusal (`.denied`): `+ {approvalRecordRef, reason?}` — signed deny envelope reference.
- Approval success (`.approved`, `.approval_observed`): `+ {approvalRecordRef}`.
- Execution success (`.executed`, `.completed`): `+ {approvalRecordRef, resultRef?}` — `resultRef` points to the local dispatch-result record; full result payload is not carried inline. The caller-side terminal observation (`.result_observed`) carries `+ {outcome: 'completed' | 'failed' | 'expired' | 'rejected', approvalRecordRef?, resultRef?, reason?}` — `outcome: 'completed'` is the result-delivery case (`resultRef` present); `'failed'` / `'expired'` record a relayed terminal-failure envelope (its `reason` carried through); `'rejected'` records either rejection observation — the synchronous `DispatchReceive` rejection ack, or the same relayed terminal-failure envelope carrying a **post-receipt** `dispatch.rejected` terminal (a Cedar-evaluation failure — class-rule deny outside the approval flow, or `policy_engine_error` — lands after intake validation passed and the ack returned `"received"`; intake failures — token, body binding, replay, capability — reject synchronously in the ack itself, per [Spec-024 §Interfaces And Contracts](./024-cross-node-dispatch-and-approval.md#interfaces-and-contracts) `DispatchTerminalNotice`) (campaign B7, 2026-07-13 — one caller-side observation event per **observed** target terminal, none for a terminal the caller never observes; `.denied` is observed via `.approval_observed`).
- Post-approval failure (`.failed`): `+ {approvalRecordRef, reason}`.
- Mid-flight timeout (`.expired`): `+ {reason: 'caller_token_expired' | 'execution_deadline'}`.
- Buffered delivery (`.result_buffered`): `+ {approvalRecordRef, bufferedUntil}`.
- UI-notification stage (`.approval_requested`): base only (UI surface resolves additional context via `dispatchId`).
- Intake stage (`.sent`, `.received`): base only.

Lifecycle discipline: five terminal events — `.rejected`, `.denied`, `.failed`, `.expired`, `.completed` — are the **only** events that terminate a dispatch's lifecycle. Exactly one fires per `dispatchId`. Intermediate events may fire in sequence before the terminal event. `.executed` is intermediate and fires **when the capability handler returns a result** — i.e., the handler itself completed without raising. Two valid post-`.executed` paths exist per `Spec-024 §Cross-Node Failure Semantics` ("capability handler fails during **or after** execution"): the normal success path `.executed` → `.completed` (result ready for emission), and the post-handler-failure path `.executed` → `.failed` (result-emission error or other post-handler runtime fault after the handler returned). A `.failed` terminal can _also_ fire without a prior `.executed` — if the handler itself raises before returning, the lifecycle goes straight to `.failed` with no intermediate `.executed`. Summary of valid success-path-ancestor lifecycles: (a) handler raises → `.failed`; (b) handler returns, post-handler step fails → `.executed` → `.failed`; (c) handler returns, result ready → `.executed` → `.completed`. The `.executed` / `.completed` split exists so audit reconstruction can distinguish (b) from (c) from a lost-terminal bug case (`.executed` recorded but no subsequent terminal in the log — the inter-step emit was lost or the daemon crashed mid-sequence). Result _delivery_ to the caller is tracked separately from lifecycle termination: live-delivered results produce caller-side `.result_observed` after target `.completed`; if the caller was detached at `.completed` time, the target appends `.result_buffered` (a post-terminal delivery annotation, **not** a lifecycle state) and later delivery on caller reconnect produces caller-side `.result_observed`. Campaign B7 (2026-07-13) widened `.result_observed` beyond result payloads to every caller-observed terminal outcome — a relayed `.failed`/`.expired` envelope or the `DispatchReceive` rejection ack appends it with the matching `outcome` discriminator — so each target terminal has exactly one caller-side observation event and the caller-local pending-dispatch window closes on observation (`Spec-024 §Cross-Node Failure Semantics`). The `.completed` / delivery separation exists because `Spec-024 §Execution And Result Emission` Example Flow 3 explicitly allows the success-path lifecycle to terminate at the target _before_ the caller reconnects and observes the result.

| Type | Side | Description (When Fired) |
| --- | --- | --- |
| `dispatch.sent` | caller | Caller daemon has transmitted the dispatch envelope via the relay's pairwise-encrypted channel. |
| `dispatch.received` | target | Target daemon has received the envelope and passed intake validation (token signature, RFC 8785 body-hash binding, replay guard, capability declared). Intermediate. |

This shape governs the three metered update types (`usage.token_count`, `usage.cost_update`, `usage.context_window_update`) only — with per-type requiredness on post-B1 emitters: `usage.cost_update` MUST set `costStatus` + `costSource` — and, on post-2026-08-26 emitters, `effectivePrincipal` (priced-vs-unpriced provenance is the row's purpose; `windowUsedTokens` / `windowMaxTokens` travel as a **pair** — a post-B1 emitter sets both or neither (a lone numerator or denominator is an emitter bug; the pair is absent only where the wire genuinely supplies no counts, e.g. a bare provider exceeded signal), and a counts-absent update is a provenance/`exceeded`-only signal whose consumers treat headroom as **unknown** — the headroom projection yields no ratio, no soft threshold fires on unknown (never a fabricated denominator), and unknown never satisfies a hard-action predicate — with the driver-computed `exceeded` flag as the deliberate carve-out: `exceeded: true` at `windowSource: 'provider_reported'` is a first-class terminal fact consumed directly, not a ratio to derive, and it authorizes the protective hard responses (interrupting the affected run, refusing further admission) on its own, so a provider that reports its window exhausted without counts is never answered more weakly than one that reports counts; what unknown never satisfies is a ratio-derived predicate (thresholds, projections, buffer arithmetic); the normative consumer line and the advisory auto-compaction safeguard it feeds live in [Spec-016 §Budget Policies](./016-multi-agent-channels-and-orchestration.md#budget-policies); optionality on those fields is pre-B1 history only; `usage.budget_warning` is per-type (see its row: `{sessionId, runId?, agentId?, budgetType, limitValue, observedValue, reason?, modelFamily?}` — `modelFamily` present whenever `reason: 'unpriced-model'`, so warnings key once per family and every blocked family is audit-visible, campaign B6); `usage.rate_limit_update` is per-type — exactly `{provider, providerAccountId, credentialGeneration, limitId?, windowMins, usedPercent, resetsAt?}`, keyed `(providerAccountId, limitId)` (its row below carries both re-keys and the `limitId`-absent `default` rule), with no `sessionId` in the payload (session binding happens at the envelope via the node-scope sentinel per §Daemon-Scope Event Binding And Node-Scope Anchoring). **Turn-scoped effective principal (2026-08-26).** The shared shape additionally carries `effectivePrincipal?: { kind: 'participant', participantId } | { kind: 'system' }` — the causing party for the turn the row meters, **required on `usage.cost_update`** for post-2026-08-26 emitters and unused by the other two metered types. It is **daemon-resolved and neither wire- nor driver-supplied**, and it is bound **at turn dispatch rather than read at emission**: the run engine mints an immutable per-turn scope at each turn boundary and the driver normalizer stamps the row from the scope of the turn whose stream produced it, so a `usage.cost_update` for one turn that lands after the next has opened still carries the principal of the turn it meters. Reading a mutable "current turn" at emission would misattribute exactly the late rows the receipt most needs to be right about. The scope is resolved from the [Spec-004 §Required Behavior](./004-queue-steer-pause-resume.md#required-behavior) admitting-principal rows — the intervener for a turn opened by a steer or an edit-and-resend, otherwise the participant who started the run, and the `system` arm where no participant caused it (a scheduled sweep, an idle-timeout settlement, a daemon-initiated recovery turn). Recording it **on the metered row itself** rather than deriving it later by ordering the row against turn-boundary events is what the [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) §Authenticated Principal class rule requires, and it is what makes [Spec-016 §Session Cost Receipt](./016-multi-agent-channels-and-orchestration.md#session-cost-receipt)'s per-caused-by axis a partition by construction: every unit of spend carries exactly one key. The two arms are closed and the participant reference is required exactly on the participant arm and absent on the system arm — the same discriminator discipline the `interventions.origin` CHECK enforces in storage, expressed here by the union's shape, since a wire payload has no table to constrain. Absence is pre-amendment history only, and the receipt's stated degrade covers it: an unstamped turn attributes to the run starter and is never guessed. **Per-turn delta semantics (2026-08-28).** The token members a `usage.token_count` row carries (`tokenCount`, `inputTokens`, `outputTokens`) are **per-turn figures, never cumulative counters**: a run- or session-scope total is obtained by summation over that scope's rows, and no consumer differences one row against another. The emitter discipline that makes the fold sound is [Spec-005 §Required Behavior](005-provider-driver-contract-and-capabilities.md#required-behavior)'s usage-delta rule (Plan-005 I-005-11) — the driver derives the per-turn figure from the provider's cumulative counters at its normalize boundary, so a cumulative reading never reaches this payload. No shipped emitter predates this semantics (Plan-005 T3.11 is unshipped), so there is no compatibility arm. The registered sum-fold consumer is the Plan-016 budget accountant (CP-016-9).

### Audit Integrity (`audit_integrity`)

Integrity-verification events recording the outcomes of hash-chain, Ed25519 signature, and Merkle-anchor checks per [§Integrity Protocol](#integrity-protocol) above. These events belong to a distinct category from `session_lifecycle` because they describe **the audit log's tamper-evidence state**, not a session's operational state — a single verification pass may cover events from many sessions, and a failure does not end a session but does halt replay.

**Invariant: audit-integrity events are never compacted, never shredded.** Compacting or shredding these events would defeat the integrity protocol — a verifier could not distinguish between "no failure occurred" and "the failure record was compacted." They are explicitly excluded from [§Event Compaction Policy](#event-compaction-policy) triggers and from the crypto-shred fan-out in [Spec-022 §Shred Fan-Out](./022-data-retention-and-gdpr.md#shred-fan-out).

Payload shape: `{sessionId, anchorId?, verifierNodeId}` (base). Per-event payload extensions called out inline. The `audit_integrity_failed` registrar arm takes a REDUCED base — `{sessionId, verifierNodeId}` — because `anchorId` is excluded from that arm outright rather than merely left absent (2026-08-03, PR #285 Codex round 2; the row's cell below carries the reasoning, and the two `runtime_node.capability_*` rows are the reduced-base precedent).

**Session binding.** `audit_integrity_verified` / `audit_integrity_failed` carry the real `session_id` of the verified range (or the sentinel when verifying the node-scope chain itself); `key_reuse_detected` is a node-level observation bound to the reserved sentinel `session_id` per [§Daemon-Scope Event Binding And Node-Scope Anchoring](#daemon-scope-event-binding-and-node-scope-anchoring). The `signing_key_slot_conflict` registrar arm (2026-08-01, PR #276) is a third case matching neither: no range was verified, yet the alarm is deliberately NOT node-scope-bound like `key_reuse_detected` — it carries the refused registration's real `session_id`, landing the row in the log whose verification the usurped slot breaks; `verifierNodeId` carries the refused daemon's own NodeId (the emitter naming itself — the node whose slot the conflict implicates), and `anchorId` is absent ALWAYS rather than merely at emission — this arm's schema REJECTS the member outright (scoped 2026-08-03, PR #285 Codex round 2, correcting a reading this sentence previously invited) — while the ROW still gains anchor coverage as any appended row does, once a subsequent anchor covers its range: coverage is a property of the range an anchor spans, never a reference the signed payload carries or could later acquire. Session binding's reach is scoped honestly (round 2, 2026-08-01): the row is signed with the refused daemon's LOCAL key, so a roster-resolving external verifier sees it fail as `signature_mismatch` exactly as it does every other row this daemon signs — the binding serves local replay and the anchor-covered post-repair forensic record, not externally-authenticatable testimony; the sixteenth-mode prose in the table below carries the full scoping and the open trust-path item.

| `audit_integrity_verified` | A read-side verifier has completed hash, signature, and anchor checks successfully over a range. Promoted from §Integrity Events with category corrected from `session_lifecycle` → `audit_integrity`. | base + `{treeSize, rootHash, fromSeq, toSeq, verifiedAt, signatureAlgorithm}` |

The four `anchor_missing_for_compacted_range` / `anchor_signature_invalid` / `stub_signature_invalid` / `stub_scalar_mismatch` modes are additive-MINOR extensions for the post-compaction integrity protocol per §Post-Compaction Integrity. The twelfth mode `signature_placeholder` (added 2026-07-26) is a further additive-MINOR extension: the row's `daemon_signature` is still the 64-zero-byte placeholder, so **no signature was ever produced** for it — it is deliberately distinct from `signature_mismatch`, and pairs with **`failurePath: 'signature'`** (the defect is in the signature column, the same path `signature_mismatch` takes; ratified 2026-07-26 so implementations mirror this assignment rather than infer one). §Integrity Protocol carries the fail-closed rule, the all-three-columns predicate, the check-ordering requirement, and why such a row is never retro-signed. The thirteenth mode `occurred_at_not_canonical` (amendment 2026-07-27, approved spec — added in response to a P1 review finding on PR #256 and recorded as a deliberate amendment, not a routine editorial change, on the 2026-05-28 precedent under §Post-Compaction Integrity) is a further additive-MINOR extension, and what it registers is a **coverage asymmetry rather than a new threat**: [Plan-006 §Invariants I-006-3-03](../plans/006-session-event-taxonomy-and-audit-log.md#invariants) check (c) already byte-compares a compacted row's `occurred_at` column against the SIGNED stub-projection bytes, so a post-compaction respelling of that column is caught there as `stub_scalar_mismatch` — while the live chain, which every row occupies for the whole of its pre-compaction life, carries no equivalent binding at all. Same column, same threat, same rationale, protected after compaction and unprotected before it; the exposure window is every row's entire uncompacted lifetime. The mechanism behind the asymmetry is that §Canonical Serialization Rules NORMALIZES exactly one canonical member, `occurredAt`, folding it to `YYYY-MM-DDTHH:MM:SS.sssZ`; every other member passes through byte-for-byte. That normalization is many-to-one, so `row_hash` and `daemon_signature` commit to the **instant**, never to the bytes sitting in the `occurred_at` column. An at-rest actor can therefore respell a stored `occurred_at` as any other spelling of the same instant — a `±HH:MM` offset in place of `Z`, a differing fractional-digit count — and BOTH the chain recomputation and the Ed25519 verification still pass, while the row silently drops out of every lexical `occurred_at` range scan. The verdict is deliberately NOT `hash_mismatch` and NOT `signature_mismatch`: on such a row the hash genuinely DOES match and the signature genuinely DOES verify, so either would report a falsehood — that nothing mismatched IS the finding. It pairs with **`failurePath: 'signature'`**, following the `stub_scalar_mismatch` assignment in [Security Architecture §Verification Rules](../architecture/security-architecture.md#verification-rules) rule 4 — the nearest sibling, a scalar-column defect that survives signature verification: `failurePath` names the verification GUARANTEE that failed, not the column the defect occupies, and the guarantee broken here is that the signature binds the stored bytes. Neither alternative fits — `'inclusion'` is the chain path, which passes, and `'consistency'` is the anchor path, which passes over the frozen `row_hash`; a fourth `failurePath` value is deliberately NOT minted, because this verdict routes to the same tamper-response owner `signature_mismatch` does. **The check is a read-side verifier duty performed with the pure, non-throwing predicate `isCanonicalOccurredAt` (`packages/runtime-daemon/src/events/canonicalizer.ts`) over the column bytes AS STORED — it is not part of `verifyRow`, which is handed already-canonicalized bytes and therefore never sees the stored spelling at all.** It is also UNCONDITIONAL: a green chain-and-signature verdict is exactly the state this attack produces, so a verifier MUST NOT gate the check behind a hash or signature failure. The one row it does NOT run on is a row the `signature_placeholder` precondition has already refused: that precondition's mandate to emit and STOP before any Ed25519 verification is unchanged and dominates, because a never-signed row has no signature binding to reason about — `signature_placeholder` stays the single reported verdict there. "Unconditional" therefore scopes to rows that reach verification, and forbids only the inverse error of skipping this check because the chain and the signature both came back green. It applies to `retention_class IS NULL` rows AND to `retention_class = 'audit_stub'` rows, and the two arms cover different halves of the compacted case. On a compacted row `stub_scalar_mismatch` catches a respelling performed AFTER compaction, because the signed projection is a fixed comparand; what it cannot catch is a spelling that was ALREADY non-canonical when the compactor signed that projection — §Compacted Event Format preserves the original timestamp verbatim, so such a spelling is baked into the signed bytes and byte-equals the column forever. This check closes that carried-forward case, and on a live row it is the only binding of any kind. **The two verdicts must not be unified under one name:** the compacted check holds signed projection bytes to compare against, so "mismatch" is accurate there, whereas the live path has no stored projection at all — the only available invariant is that the column IS in canonical form, and nothing mismatches — which is exactly why this mode is named `occurred_at_not_canonical` and not a `_mismatch` variant. The fourteenth mode `pii_ciphertext_digest_unbound` (amendment 2026-07-27, approved spec — added in response to a P1 review finding on PR #256 and recorded as a deliberate amendment, not a routine editorial change) is a further additive-MINOR extension closing the **same class** as the thirteenth, found by sweeping for it: a **signed-but-unchecked binding**, where the signature commits to a value that nothing ever compares against the column it stands for. §Canonical Serialization Rules deliberately excludes `pii_payload` from the canonical form and instead requires a `pii_ciphertext_digest` member — BLAKE3 over the ciphertext bytes — so that a Spec-022 crypto-shred cannot break the chain. That digest has been minted and signed since the codec shipped, and no verification rule ever recomputed it, so the ciphertext column carried no integrity binding at all: an at-rest substitution, truncation, or deletion of `pii_payload` left `row_hash` and `daemon_signature` both green. **Precedent — observer/monitor pattern (`key_reuse_detected`).** [Sigstore Security Model](https://docs.sigstore.dev/about/security/) (accessed 2026-04-19) states verbatim: _"users can detect any mis-issued certificates, either due to the CA acting maliciously or a compromised OIDC identity provider"_; _"Fulcio itself does not monitor the certificate transparency log; users are responsible for monitoring the log for unauthorized certificates issued to their identities"_; _"these certificates are useless unless they are published to the certificate transparency log, so such compromise can be detected."_ Our `key_reuse_detected` event is the local-daemon observer-pattern equivalent: a monitor process watching for Ed25519 public-key collisions across the daemon's signing-key stores — the same key under two identities — which violate the register-once `refuse_on_rotation` posture. ### Security Events (`security_events`)

Daemon-emitted events recording operator-facing security and data-protection posture transitions — fail-safe-default overrides and update-availability signals per [Spec-027 §Required Behavior](./027-self-host-secure-defaults.md#required-behavior), plus the daemon master-key custody source and the PII-split containment signal per [Spec-022](./022-data-retention-and-gdpr.md) (registered here at the Tier-5 readiness-audit swap, Plan-022 D-022-5). These events belong to a distinct category from `audit_integrity` (which records the audit log's tamper-evidence state) and from `event_maintenance` (which records operations on the event stream itself) because they describe **the daemon's security and data-protection posture** at process scope. Like those two infrastructure-state categories, security events fire at daemon scope across all sessions hosted on the node — they are not session-scoped. (These daemon-scope categories fire at process scope across all sessions, so they bind to a **reserved node-scope sentinel `session_id`** in the daemon-local `session_events` store: the local SQLite `session_id` is `TEXT NOT NULL` with **no** foreign key (see [local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md)), so a reserved sentinel value is admissible without a phantom `sessions` row. The sentinel is pinned to the **RFC 9562 §5.10 Max UUID** `ffffffff-ffff-ffff-ffff-ffffffffffff`: the wire-path `EventEnvelopeSchema` validates every `sessionId` with `SessionIdSchema` (`z.uuid()`, [`packages/contracts/src/session.ts`](../../packages/contracts/src/session.ts)) regardless of the local store's looser `TEXT` typing, so the sentinel **must** be a `z.uuid()`-admissible value or the two `daemon.*` events would be rejected before append/serialization — `z.uuid()` accepts the Max UUID (verified, Zod 4.3.6). The Max UUID is chosen over the Nil UUID deliberately: it is a standards-reserved sentinel distinguishable from an accidental nil/zero-init, and is structurally disjoint from the `gen_random_uuid()` v4 id space (version nibble `f`, not `4`), so it can never collide with a real session id. In the daemon-local store it forms its own monotonic-sequence + BLAKE3 hash-chain + anchor partition exactly as a real session id does — reusing the existing per-session machinery, not a new replay mechanism. This identical-partition property is **local-only**: the control-plane anchor _upload_ cannot accept the sentinel (`event_log_anchors.session_id` is a non-null FK to `sessions(id)`, which the sentinel is deliberately not), so node-scope (sentinel-partitioned) chains are witnessed **locally only** in V1 — their control-plane upload is a V1.1 extension gated on a node-identity trust anchor (see [§Daemon-Scope Event Binding And Node-Scope Anchoring](#daemon-scope-event-binding-and-node-scope-anchoring) and [ADR-017 §Node-Scope Anchor Witnessing](../decisions/017-shared-event-sourcing-scope.md#node-scope-anchor-witnessing-v1-local-only-v11-control-plane-upload)). The two Plan-022 `daemon.*` events registered above (`daemon.master_key_source`, `daemon.pii_split_ambiguous`) bind to this sentinel per [Plan-022 §Ratified Design Decisions D-022-8](../plans/022-data-retention-and-gdpr.md#ratified-design-decisions-tier-5-audit-2026-05-30). The cross-category binding rule for all daemon-scope events — `audit_integrity` (`key_reuse_detected`), `event_maintenance`, the daemon-startup `runtime_node_lifecycle` clock events, and the account-plane `usage.rate_limit_update` (`usage_telemetry`, B1) — is specified canonically in [§Daemon-Scope Event Binding And Node-Scope Anchoring](#daemon-scope-event-binding-and-node-scope-anchoring) below.)

### Event Maintenance (`event_maintenance`)

Daemon-level events recording operations on the event stream itself — schema migrations, compaction passes, and crypto-shred fan-out. These events belong to a distinct category from any session-scoped category because they describe **the event log as infrastructure**, not the session content it carries. One `event.compacted` event may compact thousands of prior events across multiple sessions; one `event.shredded` event spans every session a purged participant touched.

**Invariant: event-maintenance events are never compacted, never shredded.** Compacting a `schema.migrated` event would destroy the audit trail for a non-reversible schema change; shredding an `event.shredded` event would be self-referential and break the audit stub record of the shred. Like `audit_integrity` events, they are excluded from [§Event Compaction Policy](#event-compaction-policy) and from [Spec-022 §Shred Fan-Out](./022-data-retention-and-gdpr.md#shred-fan-out).

**Session binding.** These are daemon-scope events bound to the reserved sentinel `session_id` per [§Daemon-Scope Event Binding And Node-Scope Anchoring](#daemon-scope-event-binding-and-node-scope-anchoring) (an `event.compacted` scoped to one session's compaction MAY carry that session's id).

| `event.shredded` | A crypto-shred operation has cleared `pii_payload` ciphertext across the affected sessions per [Spec-022 §Crypto-shredding](./022-data-retention-and-gdpr.md#crypto-shredding-sqlite-event-log). ## Integrity Protocol

Canonical events are append-only AND tamper-evident. Every `session_events` row is chained to its predecessor via a BLAKE3 hash and signed by the emitting daemon with Ed25519 over the **same** canonical byte string. On a bounded cadence, a Merkle root over contiguous ranges is anchored to the control plane's `event_log_anchors` table as metadata only — the control plane does not store event payloads, consistent with [ADR-017 Shared Event-Sourcing Scope](../decisions/017-shared-event-sourcing-scope.md). Full protocol, including schema additions and verification order, is specified in [Security Architecture § Audit Log Integrity](../architecture/security-architecture.md#audit-log-integrity).

Tamper-evidence persists across compaction via a two-tier protocol: per-row chain + signature verification for uncompacted rows (`retention_class IS NULL`), and anchor-based range integrity for compacted rows (`retention_class = 'audit_stub'`). Per §Post-Compaction Integrity below, the compactor MUST force-fire and durably persist a covering Merkle anchor BEFORE stripping any row's canonical bytes — verifiers on compacted rows fall through to anchor-existence + anchor-signature checks instead of per-row recomputation.

**Placeholder signatures are refused, never retro-signed (amendment 2026-07-26, approved spec).** [Plan-001](../plans/001-shared-session-core.md) forward-declared the integrity columns with placeholder values — `prev_hash` / `row_hash` as 32 zero bytes and `daemon_signature` as **64** zero bytes (the column is `BLOB NOT NULL` with `CHECK(length(daemon_signature) = 64)`). A row still carrying the 64-zero-byte `daemon_signature` was written by a code path that predates the signer: no signature was ever produced for it, and there is nothing to verify. **The predicate is all three integrity columns, not the signature alone** — `prev_hash` and `row_hash` 32 zero bytes each AND `daemon_signature` 64 zero bytes, the exact trio the pre-signing path writes together and never a mix. Keying on `daemon_signature` by itself would also capture a genuinely TAMPERED row that merely happens to carry a zeroed signature, reporting an engineering bug where an attack occurred; requiring all three sends that row to the chain check, which reports it truthfully. Requiring `row_hash` is also what keeps a legitimate signed genesis row — zero `prev_hash` at `sequence = 0` — out of this branch. Verifiers MUST detect this case **before both the chain recomputation and the Ed25519 verification**, and MUST emit `audit_integrity_failed` with `failureMode: 'signature_placeholder'` and `failurePath: 'signature'` — a distinct twelfth enum value, additive-MINOR per [ADR-018 §Decision #8](../decisions/018-cross-version-compatibility.md#decision). Ordering before the CHAIN check is load-bearing, not stylistic: such a row's `row_hash` is 32 zero bytes and therefore fails the chain recomputation too, so a verifier that recomputes first both mislabels a never-signed row as a chain break and makes this precondition unreachable dead code. It MUST therefore never be reported as `hash_mismatch`, and it is deliberately NOT folded into `signature_mismatch`: a mismatch is evidence of possible tampering and warrants security incident response, whereas a placeholder is an engineering sequencing bug, and conflating the two pages the wrong on-call. No implementation may "repair" such a row by signing it with a current key. Signing old records with a later key is a published attack on exactly this class of log — Dörre and Ottenhues, [_Security Analysis of Forward Secure Log Sealing in Journald_](https://eprint.iacr.org/2023/867) (ACNS 2025), a real systemd vulnerability patched in v255, states verbatim: _"This check does not prevent old log messages from being signed with a newer key. An attacker can take a journal, remove seals, adjust log messages as desired, and re-create a seal with the current log sealing key."_ No conforming verifier detects the substitution after the fact, because raw Ed25519 verification per [RFC 8032](https://datatracker.ietf.org/doc/html/rfc8032) takes no time parameter at all and daemon signing keys are raw Ed25519 public keys with no X.509 validity windows per [Security Architecture §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature) ([ADR-010](../decisions/010-paseto-webauthn-mls-auth.md) governs CLI-identity and session-auth key custody, not daemon session signing keys). Key rotation cannot reintroduce the problem, because V1 specifies no daemon signing-key rotation ceremony at all: a session's daemon key is registered once and a registration presenting a different key is refused end-to-end per the same Security Architecture section, so no superseded-key epoch exists for a later key to re-seal. Recorded as a deliberate amendment to an approved spec (the 2026-05-28 precedent under §Post-Compaction Integrity), not a routine editorial change; it replaces the deleted T2.6 genesis-row backfill migration of [Plan-006](../plans/006-session-event-taxonomy-and-audit-log.md), whose full provenance is in that plan's Progress Log. (The rotation clause of this amendment originally asserted validity-window resolution for superseded keys and attributed daemon-key rotation to ADR-010; both were corrected to the no-rotation form above by the 2026-07-29 CP-006-7 re-vehicle, which pinned the register-once / different-key-refusal posture.)

### Canonical Serialization Rules

Both the `row_hash` input and the Ed25519-signed bytes are computed over the **same** canonical form. Two honest implementations that diverge here produce incompatible hashes and signatures for identical events, so the rules below are mandatory.

- Canonicalization standard: [RFC 8785 — JSON Canonicalization Scheme (JCS)](https://datatracker.ietf.org/doc/html/rfc8785). Re-used identically from [Spec-024 Cross-Node Dispatch And Approval](024-cross-node-dispatch-and-approval.md) so the daemon runs one canonicalization rule across integrity and dispatch.
- Hash function: [BLAKE3](https://github.com/BLAKE3-team/BLAKE3-specs/blob/master/blake3.pdf). Same digest used for Spec-024's `request_body_hash`.
- Signature scheme: [RFC 8032 §5.1 — Ed25519](https://datatracker.ietf.org/doc/html/rfc8032#section-5.1).
- Fields included (the canonical set; serialized order is mandated by RFC 8785 §3.2.3 UTF-16 code-unit lex-sort of member names, not the order listed here): `id`, `sessionId`, `sequence`, `occurredAt`, `category`, `type`, `actor`, `payload`, `correlationId`, `causationId`, `version`. RFC 8785's lex-sort is non-negotiable — it is what makes "two honest implementations" above produce byte-identical canonical forms; this list documents membership only. (One further member is conditional and local-only — `receivedFromNodeId`, present on received rows exclusively; see the received-row bullet below.)
- Fields with value `null` MUST be included (so "present-but-null" and "absent" are distinguishable after serialization).
- `occurredAt` MUST be RFC 3339 UTC with millisecond precision (`YYYY-MM-DDTHH:MM:SS.sssZ`) so ordering is byte-stable. It is the **one** canonical member that is NORMALIZED into that form rather than passed through byte-for-byte, and the normalization is many-to-one, so the hash and the signature commit to the instant and NOT to the spelling stored in the `occurred_at` column — the read-side `occurred_at_not_canonical` check at [§Audit Integrity (`audit_integrity`)](#audit-integrity-audit_integrity) is what enforces this MUST at rest (2026-07-27 amendment).
- `pii_payload` is NOT included in the canonical form. Events whose `pii_payload` column is non-NULL MUST embed a `pii_ciphertext_digest` field in `payload` — BLAKE3 over the ciphertext bytes of `pii_payload` — so a [Spec-022](022-data-retention-and-gdpr.md) crypto-shred of `pii_payload` does not break the hash chain. The digest sits inside the canonical bytes and is never shredded — and neither is the ciphertext column: [Spec-022 §Shred Fan-Out](022-data-retention-and-gdpr.md#shred-fan-out) Path 1 destroys the per-participant key and overwrites nothing, so the stored bytes still hash to the signed digest in BOTH retention states. That is what lets the digest-binding check in [Security Architecture §Verification Rules](../architecture/security-architecture.md#verification-rules) rule 2 run wherever `pii_payload` is non-NULL, with no shred-state carve-out (corrected 2026-07-27 — this bullet previously said shredding "clears only the ciphertext column"; scoped 2026-08-11 to origin-authored rows — a received row never legitimately holds the column, per the received-row provenance amendment in §Event Type Enumeration).
- Events whose `pii_payload` column is non-NULL MUST **also** embed a `pii_participant_id` field in `payload` — the participant whose content key sealed that ciphertext — so the signature binds the row's PII **owner** as well as its bytes. The owner stamp is INCLUDED where the ciphertext it names is EXCLUDED, and the asymmetry is deliberate rather than an inconsistency. Excluding `pii_payload` protects the shred: signed bytes derived from the PII partition would hand an attacker length and structure oracles over data the shred was meant to erase. The stamp is not that hazard — it is an identifier no shred erases, since [Spec-022 §Shred Fan-Out](022-data-retention-and-gdpr.md#shred-fan-out) Path 1 destroys the per-participant key and overwrites no column — and signing it discloses no new CLASS of datum, because `actor` is already a canonical member above and [Local SQLite Schema §Session Events](../architecture/schemas/local-sqlite-schema.md#session-events-plan-001-extended-by-plans-006-008-015) documents that column as `participant_id or agent_id or NULL for system`, so the canonical form has committed to signed participant identifiers since it shipped. The stamp is nonetheless NOT redundant with `actor`: `actor` names who EMITTED the row, the stamp names whose key SEALED the ciphertext, and the two diverge exactly where it matters — an agent-emitted or system-emitted row can still carry a participant's PII. What the binding buys is post-shred attribution. Once Path 1 destroys the key no decrypt can ever re-attribute the retained ciphertext, so the stamp becomes the SOLE surviving evidence of whose data the row held; a tampered stamp cannot stop that global key deletion, but it corrupts the SCOPE SELECTOR instead, falsifying the `affectedSessionIds[]` / `piiPayloadsCleared` an `event.shredded` event retains indefinitely as compliance evidence per [§Event Maintenance (`event_maintenance`)](#event-maintenance-event_maintenance). The read-side `pii_owner_stamp_unbound` check at [§Audit Integrity (`audit_integrity`)](#audit-integrity-audit_integrity) is what holds the row's durable stamp to this signed claim; the stamp column it compares against is `session_events.pii_participant_id`, created by [Plan-006](../plans/006-session-event-taxonomy-and-audit-log.md) T3.1's additive migration `0007-pii-participant-id.ts` and written by the append path from the same codec result that produced the ciphertext, so the check now compares two independent copies rather than re-reading one (2026-07-27 amendment; column landed 2026-08-04).
- `content_payload` is NOT included in the canonical form either, and for the same structural reason `pii_payload` is not (2026-08-30, the machine-authored prose amendment). Events whose `content_payload` column is non-NULL MUST embed a `contentCiphertextDigest` field in `payload` — BLAKE3 over the ciphertext bytes — so the signature binds the machine-authored body without carrying it, and survives that body's destruction at compaction. The parallel is deliberate but the columns are **not** interchangeable and the differences are the point: `content_payload` is sealed under a **session**-scoped key rather than a per-participant one, so it carries **no owner-stamp sibling** — `session_id` is already a canonical signed member, so the key's binding is committed by the canonical form as it stands and a second column would restate a fact the bytes already sign. This is why the durable home for machine-authored prose costs one column and not two, and why there is no `content_owner_stamp_unbound` check to pair with `pii_owner_stamp_unbound`: the stamp such a check would compare against does not exist, because it would be redundant rather than missing. The digest-binding check the [Security Architecture §Verification Rules](../architecture/security-architecture.md#verification-rules) run over `pii_ciphertext_digest` applies unchanged to this digest wherever `content_payload` is non-NULL — the retained ciphertext still hashes to the signed digest in both retention states, since nothing overwrites the column while the row is live. Unlike `pii_payload`, whose ciphertext outlives its key, this column's ciphertext is **removed** at compaction along with the payload that carries its digest, so the two disappear together and no post-compaction check straddles them.

- One canonical member is **local and conditional** (2026-08-11 received-row provenance amendment; created by [Plan-008](../plans/008-control-plane-relay-and-session-join.md)'s R4 backfill task): `receivedFromNodeId` — included in the canonical form **iff** the row's `session_events.received_from_node_id` column is non-NULL, i.e. the row was appended from another daemon's origin-signed bytes by the [Spec-008 §Peer History Backfill On Join (V1)](008-control-plane-relay-and-session-join.md#peer-history-backfill-on-join-v1) live-relay or backfill path, re-sequenced and re-signed under the local key — carrying the origin `NodeId` whose roster key verified the incoming bytes before append. Origin-authored rows never include the member, so every hash and signature produced before the receive path ships is byte-identical under this rule, and the member never travels the wire: backfill serves the **origin's** bytes (which cannot contain it) and the shipped `packages/contracts/src/event.ts` `EventEnvelope` is untouched — this is a canonicalization-input rule, not a wire field. Mirroring the durable column into the receiver-signed bytes is what makes the provenance marker tamper-evident with **no new verification mode**: clearing the column on a received row (to fake origin authorship, and with it backfill servability) or setting it on an origin row (to dodge the two PII binding checks it dispatches) changes the recomputed canonical bytes and fails the ordinary `signature_mismatch` check — for the row's **uncompacted** life, the only window in which the canonical bytes are recomputable at all. After compaction the original bytes are gone, so the binding deliberately transfers rather than lapses: §Compacted Event Format preserves the marker inside the signed stub projection as the conditional `receivedFromNodeId` stub field, and [Security Architecture §Verification Rules](../architecture/security-architecture.md#verification-rules) rule 4's scalar binding compares it against the durable column, so a post-compaction marker flip in either direction fails the existing `stub_scalar_mismatch` mode — still no new verification mode in either retention class. Rows exported for external verification MUST carry the column so the canonical form is reconstructible. Registered pre-first-release like the campaign-B9 pair in §Event Type Enumeration — no `"1.0"` envelope has been emitted in a non-test environment as of 2026-08-11 — so it is part of the v1.0 baseline canonicalization contract from first emit, with the same conditional Plan-006 T1.9 carries: were the point of no return crossed before the receive path ships, the implementer takes the MINOR bump with producer and golden-vector updates.
- The canonical form is **bounded**: `canonical_bytes(row)` MUST NOT exceed `EVENT_CANONICAL_BYTES_MAX = 32768` bytes (32 KiB; the exported constant lives beside `EVENT_ENVELOPE_SEQUENCE_MAX` in `packages/contracts/src/event.ts`), enforced at the sole append path — an oversized envelope is refused with the typed `daemon.event_canonical_bytes_exceeded` error ([Error Contracts §Daemon](../architecture/contracts/error-contracts.md#daemon), 400) before any row is written, never truncated and never silently accepted (2026-08-11 amendment, Codex PR #323 round 2). The bound is a **serviceability guarantee, not merely hygiene**: [Spec-008 §Peer History Backfill On Join (V1)](008-control-plane-relay-and-session-join.md#peer-history-backfill-on-join-v1) re-publishes canonical bytes base64-encoded inside a chunk riding one relay frame, and that spec's §Message Framing caps a frame at 64 KB with **one** AEAD envelope per frame and no reassembly protocol — so an unbounded canonical form would mint rows that can never legally travel the seam (base64 expands 4/3: a 32 KiB canonical payload encodes to ≈43.7 KiB, and with signature, origin, stub, anchor, and chunk members plus AEAD and framing overhead a maximal single-entry chunk stays ≈45 KiB, comfortably under the ceiling; the live relay path carries the smaller un-base64'd form and clears it a fortiori). The constant is **headroom over the catalog, not a constraint producers engineer around**: §Event Type Enumeration's payload shapes are metadata-shaped by construction — assistant output carries `contentType?` / `contentLength?` and never message text, tool activity carries no tool output, dispatch results ride `resultRef` with the full payload explicitly not carried inline, and artifact/diff content is content-addressed relay state ([Spec-014 §Cross-Node Artifact Relay (V1)](014-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1)), never event-carried — so unbounded content always rides behind a reference, and an append approaching the ceiling is a payload-design defect (bulk content inlined where a reference belongs), exactly the class the refusal exists to catch. The bound covers **both** payload-writing sites: the append path here, and the compactor's stub construction ([§Compacted Event Format](#compacted-event-format) — the projection replaces `payload` after this check has passed, so the stub bound is the companion this guarantee needs, 2026-08-12 round-3 amendment). Registered pre-first-release: no shipped test or fixture appends a payload within an order of magnitude of the bound, so nothing existing is invalidated; the shipped Plan-006 T3.1 append path and T3.2 compactor predate their checks and take them in the same immediate Plan-006 follow-up code PR as the anchor-claim preimage below (§Anchoring Cadence) — landed 2026-08-12, PR #324.

Verification is the inverse: recompute `canonical_bytes(row)`, recompute `BLAKE3(prev_hash || canonical_bytes(row))`, compare to the stored `row_hash`, and verify `daemon_signature` against the canonical bytes using the `NodeId`-resolved public key from the session participant roster (see Security Architecture § Audit Log Integrity for roster lookup semantics).

### Anchoring Cadence

Anchors fire on the earlier of `ANCHOR_INTERVAL_EVENTS = 1000` events or `ANCHOR_INTERVAL_SECONDS = 300` seconds since the previous anchor. The anchor payload is `(session_id, node_id, start_sequence, end_sequence, merkle_root, root_signature, anchored_at)` — metadata only — uploaded to the control plane's `event_log_anchors` table. **`root_signature` covers the anchor claim, not the root alone (2026-08-11 amendment, Codex PR #323 round 2):** Ed25519 under the daemon's session-scoped signing key over the UTF-8 bytes of the [RFC 8785](https://datatracker.ietf.org/doc/html/rfc8785) canonicalization of the five-member **anchor claim** object `{"endSequence", "merkleRoot", "nodeId", "sessionId", "startSequence"}` — `merkleRoot` in the base64 spelling the upload wire already carries, the sequences as JSON numbers, `sessionId` / `nodeId` as their wire strings. The coordinates that make a root _meaningful_ — whose log, which span — are thereby inside the signature rather than beside it: a signature over `merkle_root` alone leaves `start_sequence` / `end_sequence` / `node_id` / `session_id` rewritable by whoever stores or carries the record, so any span-coverage test a consumer runs against unsigned coordinates is vacuous (the defect surfaced by [Spec-008 §Peer History Backfill On Join (V1)](008-control-plane-relay-and-session-join.md#peer-history-backfill-on-join-v1)'s carried-anchor verification, where a malicious carrier could relabel an authentic root onto an arbitrary range). No cross-protocol confusion arises under the shared per-session key: the claim's five-member set is disjoint from every event canonical form (§Canonical Serialization Rules requires `id` / `category` / `type` members no anchor claim carries) and from every stub projection, so no anchor-claim byte string is also a valid signed-event or signed-stub byte string. `anchored_at` stays outside the claim deliberately — it is a receipt timestamp, not an integrity coordinate. Amended pre-first-release with **no production anchors in existence** — the same signed-format freedom the 2026-08-04 §2.1.1 gloss repair exercised; the shipped [Plan-006](../plans/006-session-event-taxonomy-and-audit-log.md) T3.3 signer signs the root alone as of this amendment and takes the preimage update in the immediate Plan-006 follow-up code PR (landed 2026-08-12, PR #324), before any anchor reaches production. Node-scope (sentinel-partitioned) chains are an exception in V1 — see [§Daemon-Scope Event Binding And Node-Scope Anchoring](#daemon-scope-event-binding-and-node-scope-anchoring) below.

### Daemon-Scope Event Binding And Node-Scope Anchoring

Not every event describes activity inside a session. Some describe the **daemon process itself** — its security posture, its event-stream maintenance, its startup clock state. These **daemon-scope** events carry no real session context, yet every `session_events` row needs a `session_id` to partition its hash chain and anchor range.

**Binding rule (event-level).** An event is emitted with `session_id` set to the reserved sentinel **iff it has no single owning session** — either because its payload carries no real session context (**daemon-scope**), or because it spans a participant's entire cross-session footprint and so has no one owning session (**participant-scope**; the sessions it touches, when it names them, live in the payload, never in the `session_id`). The discriminator is the event, not the category — a category may contain both shapes. The sentinel-bound set is:

- every `security_events` type — `security.default.override`, `security.update.available`, `daemon.master_key_source`, `daemon.pii_split_ambiguous`;
- every `event_maintenance` type — `schema.migrated`, `event.compacted`, `event.shredded` (an `event.compacted` scoped to a single session's compaction MAY instead carry that session's id);
- `key_reuse_detected` (category `audit_integrity`) — a node-level key-collision observation, distinct both from `audit_integrity_verified` / `audit_integrity_failed`, which carry the real `session_id` of the range they verified (or the sentinel when they verify the node-scope chain itself), and from `audit_integrity_failed`'s `signing_key_slot_conflict` registrar arm (2026-08-01, PR #276) — a second contrast, NOT a member of this sentinel-bound set: it verified no range yet satisfies the owning-session criterion above by carrying the refused registration's real `session_id`, never the sentinel, per [§Audit Integrity](#audit-integrity-audit_integrity)'s Session binding;
- the daemon-startup clock events `session.clock_unsynced` / `session.clock_corrected` (category `runtime_node_lifecycle`) — distinct from `runtime_node.*`, which describe a node's attachment to a specific session and carry that `session_id`;
- `usage.rate_limit_update` (category `usage_telemetry`, B1) — an account-scoped provider-quota snapshot spanning every session the account's runs touch, so it has no single owning session; the other seven `usage_telemetry` types carry the real `sessionId` of the run or session they meter;
- the four node-scope `mcp_governance` types (B18) — `mcp.server_config_changed`, `mcp.server_trust_changed`, `mcp.tool_override_changed`, `mcp.server_oauth_completed` — node-operator governance actions against daemon trust/override stores and provider config surfaces, with no single owning session (a session-scoped initiator lives in the payload as `initiatingSessionId?`, never in the row's `session_id`); the fifth type, `mcp.server_status_changed`, binds **per-event** (the `event.compacted` dual-binding precedent): a session-scoped provider-feed observation carries that session's real `session_id`, a node-level probe binds to the sentinel ([§MCP Governance](#mcp-governance-mcp_governance); [Spec-028](./028-mcp-server-configuration-and-governance.md));
- every `participant_lifecycle` type — `participant.exported`, `participant.purge_requested`, `participant.purged`, `participant.tokens_revoked_all`, `participant.device_reset` — which describe the **participant entity itself** (account-level existence and keyring state), not its role in any one session ([§Participant Lifecycle](#participant-lifecycle-participant_lifecycle)): a single such event spans every session the participant touched, so it has no one owning `session_id` (participant-scope). When the event names affected sessions they live in the **payload** (`participant.purged.affectedSessionIds[]`), never in the row's `session_id` — the event is not hidden: it anchors in the daemon's sentinel-partitioned node-scope chain exactly like any daemon-scope event, and `affectedSessionIds[]` cross-references the touched sessions for audit. Emitted once per participant action (aggregate), not once per affected session.

**Sentinel constant.** The sentinel is the RFC 9562 §5.10 **Max UUID** `ffffffff-ffff-ffff-ffff-ffffffffffff`, applied uniformly across **all** daemon-scope bindings — not only the two Plan-022 `daemon.*` events that first reserved it. Its rationale (`z.uuid()`-admissibility on the wire path, deliberate disjointness from the `gen_random_uuid()` v4 id space, FK-free admissibility in the `TEXT NOT NULL` local `session_id`) is detailed in [§Security Events](#security-events-security_events).

**Node-scope anchoring is local-only in V1.** A sentinel-partitioned chain forms its own monotonic-sequence + BLAKE3 hash-chain + Merkle-anchor partition exactly as a real session does, reusing the per-session machinery — not a new replay mechanism. In V1 that witness is **local only**: the chain is signed and anchored on the emitting daemon (the local Merkle root durably held in [`pending_anchor_uploads`](../architecture/schemas/local-sqlite-schema.md)) and verified by a **local** reader using the daemon's **public verification key** — the public half of the daemon's own anchor-signing keypair, resolved locally and **not** from a participant roster (a sessionless node-scope chain has no roster entry, per reason (2) below); an audit reader needs only this public key, never custody of the private signing key that could forge the chain. It is **not** uploaded to the control plane, for two reasons: (1) the sentinel cannot satisfy the non-null `session_id` FK on [`event_log_anchors`](../architecture/schemas/shared-postgres-schema.md); and (2) the control-plane verification path resolves the anchor-signing key from the **session participant roster** ([Security Architecture §Audit Log Integrity](../architecture/security-architecture.md#audit-log-integrity)), in which a sessionless chain has no entry. Local tamper-evidence is sound against every adversary except one holding the daemon's own **signing (private) key** — which is exactly the boundary control-plane witnessing addresses.

**Control-plane witnessing of node-scope chains is a V1.1 extension** ([ADR-017 §Node-Scope Anchor Witnessing](../decisions/017-shared-event-sourcing-scope.md#node-scope-anchor-witnessing-v1-local-only-v11-control-plane-upload)), gated on a non-forgeable **node-identity** trust anchor + resolution surface (a daemon/node identity key registered control-plane-side, owned by Plan-018 / Plan-003). V1's secure-defaults obligation is operator-visible _local_ audit-visibility ([Spec-027 §Required Behavior](./027-self-host-secure-defaults.md#required-behavior)), which the local witness satisfies; remote tamper-evidence against a malicious local operator is the V1.1 hardening, and it cannot be made sound without that node identity — a self-provisioned node key signing its own posture history is forgeable by the very operator it would attest against.

### Integrity Events

The `audit_integrity_verified` and `audit_integrity_failed` event types are fully enumerated under [§Audit Integrity](#audit-integrity-audit_integrity) below with category `audit_integrity`. `audit_integrity_failed` halts replay at the affected row and must be surfaced to operators. The prior interim registration under category `session_lifecycle` is superseded — integrity events describe the audit log's tamper-evidence state, not a session's operational state.

## Event Compaction Policy

Compaction reduces storage and event volume by replacing full event payloads with lightweight audit stubs. Any one of the following triggers initiates compaction:

| Trigger | Threshold | Description |
| --- | --- | --- |
| Event count | 50,000 events per session | Oldest events beyond this are compaction candidates |
| Event age | 90 days | Events older than 90 days are compaction candidates |
| Storage threshold | 500 MB per session SQLite | When session DB exceeds this, compact oldest events first |

Compaction runs as a background daemon task during idle periods. It never runs during active runs.

### Retention Windows

| Retention Class | Retained | Compacted |
| --- | --- | --- |
| Audit stubs | Indefinitely | Never — audit stubs are the compacted form |
| Full event payloads | Until any ONE §Event Compaction Policy trigger names the event a candidate | Replaced by audit stubs |
| PII payloads | Per GDPR policy (Spec-022) | Crypto-shredded independently of compaction |
| Reasoning content | 7 days (detailed) / indefinitely (summary) | Detailed reasoning compacted; durable summary retained |

**The triggers are independent, never a joint floor (clarified 2026-08-04).** Each trigger's candidate set is its own §Event Compaction Policy Description column, and a pass compacts their **union** — an event becomes compactable as soon as ONE trigger names it. The Full-event-payloads row above previously read "90 days or 50K events (whichever is more generous)", which, taken as a per-row conjunction over both windows, promised the opposite: a session under 50,000 events would retain full payloads past 90 days indefinitely. That reading is inadmissible on two independent grounds. First, it contradicts [Spec-022 §Data Retention and Deletion Policy](./022-data-retention-and-gdpr.md#data-retention-and-deletion-policy), which records as **verified** that "the event compaction policy (Spec-006) compacts events older than 90 days", and on which that spec's 90-day `session_events.pii_payload` retention entry depends — under the conjunctive reading a low-volume session retains full PII indefinitely, which Spec-022 makes an ADR-triggering exception rather than the default. Second, it would make the age trigger dead code for every session, its candidate set being a strict subset of the count trigger's, contradicting §Event Compaction Policy's own "Any one of the following triggers initiates compaction". The Description columns are the normative statement of what each trigger may destroy; this table summarizes retention classes, not trigger arithmetic.

### Compacted Event Format

An audit stub retains the fields below — and, for **every run-scoped row** (its source payload carries `runId`), that `runId` plus, when the rollback-attribution source resolves one at compaction, the row's originating `originPosition` (the [Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior) uncompacted-rewind-span check's detection keys); for a row attributed to a superseded epoch/turn (its source payload carries the cross-cutting `sourceEpoch` stamp, or the attribution is established at compaction time for a rolled-back run's rewound tail — §Event Type Enumeration and the compaction paragraph below), the `sourceEpoch` + `sourcePosition` pair together with that `runId`; and, for an accepted `run.rolled_back` boundary row, the `runId` + `runVersion` + `targetPosition` rewind cutoff; for a **received** row (`received_from_node_id` non-NULL), that marker as `receivedFromNodeId`; and, for any row whose source payload carries a `channelId` binding, that `channelId` (both 2026-08-11, the received-row provenance amendment's change 4) — each preserved verbatim inside the stub projection per the compaction paragraph below:

```
{
  id: string,           // original event ID preserved
  sessionId: SessionId,
  sequence: number,     // original sequence preserved
  occurredAt: string,   // original timestamp preserved
  category: EventCategory,
  type: string,         // original type preserved
  runId?: RunId,        // REQUIRED on every run-scoped row (campaign B9): backstop-index key on terminal run_lifecycle + posture-bearing run.running rows, rollback-boundary key on accepted run.rolled_back rows, epoch key on sourceEpoch-stamped rows, rewind-span detection key on every other run-scoped row (with originPosition when resolved — the compaction paragraph below)
  runVersion?: number,  // REQUIRED on terminal run_lifecycle rows and posture-bearing run.running rows (the keys survive compaction — §Run Lifecycle), and on accepted run.rolled_back rows (campaign B9)
  executionPosture?: ExecutionPosture, // REQUIRED on posture-bearing run.running rows — the audit boundary survives compaction
  credentialPolicyRef?: string, // preserved when the source run.running payload carries it — present on the two sandboxed modes, absent under mode:'trusted' per the Spec-012 execution-posture amendment (PR #175); NOT unconditionally required alongside executionPosture, since a mode:'trusted' row carries executionPosture but no credential ref (the stub neither requires nor fabricates one)
  channelId?: ChannelId, // preserved verbatim iff the source payload carries one (2026-08-11 received-row provenance amendment, change 4): keeps the Spec-008 serving-side channel-entitlement predicate resolvable on compacted rows — absence means the source payload carried none, unrestricted by construction
  receivedFromNodeId?: NodeId, // present iff session_events.received_from_node_id is non-NULL (2026-08-11, change 4): binds the provenance marker into the signed stub bytes; the §Post-Compaction Integrity scalar binding compares it against the durable column (stub_scalar_mismatch on divergence)
  actor: string | null,
  compactedAt: string,  // when compaction occurred
  retentionClass: 'audit_stub',
  summary: string       // human-readable one-line summary
}
```

At compaction the `payload` column is **replaced** (not nulled — the column is `NOT NULL`) by the JCS-canonicalized audit-stub projection above; `pii_payload`, `pii_participant_id`, `content_payload`, `correlationId`, and `causationId` are removed (set NULL). **`content_payload` joins that list rather than sitting beside it** (2026-08-30, the machine-authored prose amendment): the audit stub is a non-PII, non-content commitment, and a surviving machine-authored body would outlive the payload describing it exactly as a surviving `pii_payload` would. Its `contentCiphertextDigest` needs **no stub field of its own** and is deliberately given none — the digest lives inside the live `payload`, which this same sentence **replaces** wholesale, and the stub's field set is a closed enumeration. Stating that disposition rather than leaving it implicit is the lesson of the 2026-07-27 owner-stamp amendment two paragraphs below, applied at mint time instead of retroactively. The `summary` field is generated at compaction time from the original payload, and the compactor MUST hold the serialized projection to the same `EVENT_CANONICAL_BYTES_MAX` bound the append path enforces ([§Canonical Serialization Rules](#canonical-serialization-rules)) by truncating the `summary` it mints **before** signing (2026-08-12 amendment, Codex PR #323 round 3): the projection replaces `payload` after the append-time check has already passed, `summary` is locally generated prose rather than signed origin content — the one member the bound may lawfully shorten: every other member is either origin or attribution content the stub exists to preserve (the row scalars, the preserved payload members, the compaction-time attribution stamps) or a fixed-width local stamp with nothing to shorten (`compactedAt`, `retentionClass`) — and an unbounded stub would be permanently unservable at entry granularity under [Spec-008 §Peer History Backfill On Join (V1)](008-control-plane-relay-and-session-join.md#peer-history-backfill-on-join-v1)'s no-fragmentation frame budget — the same serviceability guarantee the append ceiling exists for, which a bound enforced at only one of the two payload-writing sites would not actually give. When truncation cannot hold the bound — the projection still oversized with its `summary` emptied, reachable only for a row written before the ceiling existed or outside the ceiling-enforced append path, whose preserved members the projection copies verbatim — the compactor MUST refuse to stub the row rather than shorten preserved members or sign a stub no relay frame can carry: the row stays live and uncompacted, and the refusal is surfaced on the pass result (2026-08-12 clarification, PR #324 — the fail-closed residual the MUST-hold above entails). For terminal `run_lifecycle` rows (`run.completed` / `run.interrupted` / `run.failed`) the projection additionally preserves the original payload's `runId` + `runVersion` (B1) — the at-most-once-terminal backstop index (§Run Lifecycle) is keyed on those payload fields, and compacting them away would re-admit duplicate terminals as indexed NULLs. For accepted `run.rolled_back` rows — non-terminal lifecycle, the epoch boundary — the projection additionally preserves the original payload's `runId` + `runVersion` + `targetPosition` (campaign B9, the CP-004-12 registration): the [Spec-004 §Driver-Level Rollback Mechanics](004-queue-steer-pause-resume.md#driver-level-rollback-mechanics) supersede projection rebuilds each epoch's rewind cutoff from the boundary event, so compacting the cutoff away would strand every stale-epoch row's marking — a projection rebuild after both the boundary row and its stale rows are compacted must still produce the marks. For a row whose source payload carries a `channelId` binding, the projection preserves it verbatim (2026-08-11 received-row provenance amendment, change 4): [Spec-008 §Peer History Backfill On Join (V1)](008-control-plane-relay-and-session-join.md#peer-history-backfill-on-join-v1)'s serving-side channel-entitlement predicate reads the binding after compaction, and without preservation every compacted channel-bound row would resolve as an unresolvable binding and fail closed at selection — withholding exactly the stubs the anchor-plus-stub serving path exists to serve. For a **received** row (`received_from_node_id` non-NULL) the projection carries `receivedFromNodeId` mirroring the durable column (same change), so the possession bound and the [§ Post-Compaction Integrity](#post-compaction-integrity) scalar binding keep the provenance marker tamper-evident after the original canonical bytes are gone. The compactor then writes a per-row **`stub_signature`** — an Ed25519 signature over the **exact canonical byte string it stores in `payload`** (the RFC 8785 JCS serialization of the audit-stub projection) using the daemon's session signing key. **Sign-exact-bytes invariant:** the compactor signs the identical byte string it persists to `payload`, with no re-serialization between signing and storing; consequently a verifier authenticates the stub by checking `stub_signature` **directly over the stored `payload` bytes** — it never re-canonicalizes or reconstructs the projection from the scalar columns (`compactedAt` and `summary` are not columns; they exist only inside the stored projection). See [§ Post-Compaction Integrity](#post-compaction-integrity). The replay and renderer contracts read this stub from `payload` and MUST surface it with `retentionClass: 'audit_stub'` (never a silent omission) per [§ Replay Interaction with Compacted Regions](#replay-interaction-with-compacted-regions). For **every run-scoped row** — any row whose source payload carries `runId` — the projection preserves that `runId` (read directly from the payload, so the rule holds under the vacuous attribution default below) and, when the rollback-attribution source resolves one, the row's originating position as **`originPosition`** (a stub-projection field like the pair below, its key pinned by Plan-006 T1.9's `ORIGIN_POSITION_STUB_KEY`): these are the [Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior) uncompacted-rewind-span check's detection keys — without them an ordinary current row compacted before any rollback loses its run identity and position, a later rollback across it becomes undetectable at admission, and the row is stranded unattributable (a position-less stub of the target run is therefore itself a standing refusal: written before rollback support, its position is unknowable). For any row whose source payload carries the cross-cutting `sourceEpoch` epoch-attribution field (§Event Type Enumeration — the 2026-07-20 CP-004-12 registration), the projection preserves the `sourceEpoch` + `sourcePosition` pair — together with the stamped row's `runId` (epochs and positions are run-local and the supersede cutoff reads run identity, epoch, and position, so a stamp without them is unattributable) — exactly as it preserves the posture fields above — inside the stored stub projection bytes, so `stub_signature` covers it — keeping a compacted stale-epoch row attributed to its source epoch on replay (the [Spec-004 §Driver-Level Rollback Mechanics](004-queue-steer-pause-resume.md#driver-level-rollback-mechanics) supersede projection reads it after compaction; a stub-projection field, not a scalar column, so the [§ Post-Compaction Integrity](#post-compaction-integrity) scalar-binding check is unaffected). Conversely, a **rolled-back run's ordinary rewound-tail row** — live and unstamped when written, attributed to a superseded epoch/turn only because a later accepted `run.rolled_back` rewound past it — receives the same `sourceEpoch` + `sourcePosition` + `runId` triple **stamped into its stub at compaction time**: compaction is the moment in-stream derivability is destroyed, so the projection freezes exactly what a rebuild can no longer derive (the rule that already mints `summary` at compaction), while a row attributed current takes no stamp — absence keeps meaning current. The attribution is supplied through the Plan-006-owned rollback-attribution interface that the [Spec-004 §Driver-Level Rollback Mechanics](004-queue-steer-pause-resume.md#driver-level-rollback-mechanics) supersede projection implements and the consuming plan wires in at the daemon composition root, replacing the vacuous default exactly as the PII codec seam is wired (constructor-injected; until that implementation lands no accepted `run.rolled_back` can exist, so the default is vacuous); the interface answers three ways — _current_ (no stamp; the answer carries the row's resolved originating position for `originPosition` when the implementation can supply it — the vacuous default supplies none), _superseded_ (stamp the triple), or _defer_ (a dispatched-but-unconcluded rollback's rewind span covers the row — [Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior)'s admission serialization — so the row stays live this pass and is re-examined after the intervention concludes). With the [Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior) uncompacted-rewind-span precondition refusing any rollback across already-compacted history, every row a supersede mark must reach stays attributable for the log's whole retention life: ingestion stamps cover late arrivals, compaction-time stamps cover the marked tail, and the boundary row's preserved cutoff covers the rebuild.

**PII owner stamp — the compacted disposition (2026-07-27 amendment).** The stub projection above carries no `pii_participant_id`, so the signed owner-stamp CLAIM that [§Canonical Serialization Rules](#canonical-serialization-rules) requires on every PII-bearing row does not survive compaction: `payload` is replaced wholesale by that fixed field set, and the field set has no PII members. The disposition this amendment sets for the other half is that the compactor clears the row's durable stamp alongside `pii_payload`, on two grounds — the stamp and the ciphertext are the two halves of one PII partition, and [Spec-022 §Shred Fan-Out](./022-data-retention-and-gdpr.md#shred-fan-out) Path 1 scopes itself to rows whose `pii_payload` is non-NULL, so once the ciphertext is destroyed outright the stamp has no remaining consumer. **That disposition is now landed and confirmed (2026-08-04).** [Plan-006](../plans/006-session-event-taxonomy-and-audit-log.md) T3.1's additive migration `0007-pii-participant-id.ts` created the column, and T3.2's compactor clears it in the same stub-write statement that NULLs `pii_payload` — so `pii_participant_id` now stands in the removal list above rather than only here, which is the follow-on amendment this paragraph reserved. Had the column instead been RETAINED on compacted rows, the `pii_owner_stamp_unbound` check at [§Audit Integrity (`audit_integrity`)](#audit-integrity-audit_integrity) would report every compacted row unbound — a present stamp beside an absent claim is that check's tamper signal and must NOT be softened into a pass to accommodate compaction — and its CALLER would have had to scope it to `retention_class IS NULL` instead, the way the digest check is scoped out of `verifyRow`.

### Post-Compaction Integrity

Once an event is compacted to an audit stub, the daemon discards the original `payload` content, `correlationId`, and `causationId`. The row's `daemon_signature` and `row_hash` commit to canonical bytes derived from those (now-discarded) fields, so per-row recomputation **against the original** is no longer possible. Two complementary commitments preserve integrity instead: (1) a covering Merkle **anchor** witnesses that the original pre-compaction range existed and was internally consistent at anchor time; (2) a per-row **`stub_signature`** authenticates the surviving audit-stub bytes against post-compaction tampering. The anchor is the external (control-plane-witnessed) proof of original existence; the `stub_signature` is the at-rest proof that the visible stub is the daemon's genuine compaction output. Both are required — neither alone is sufficient (the anchor cannot detect a tampered stub, and a `stub_signature` alone cannot prove the original range was not fabricated wholesale).

**Anchor-before-compaction protocol (load-bearing).** Before mutating any row's payload in a range `[start_sequence, end_sequence]`, the compactor MUST:

1. Verify that a **covering** Merkle anchor exists for the range — one whose `[start_sequence, end_sequence]` spans the entire to-be-compacted range, i.e. `anchor.start_sequence ≤ range_start AND anchor.end_sequence ≥ range_end` (a single-anchor coverage test, NOT an exact-`start_sequence` match) — in the local `pending_anchor_uploads` queue OR already durably persisted to the control-plane's `event_log_anchors` table.
2. If no covering anchor exists, force-fire one — compute `merkle_root = BLAKE3-merkle(row_hash for row in range)` using the pre-existing anchoring path (the leaves are the rows' frozen `row_hash` values — the **same** leaf basis the cadence anchor commits via `MerkleAnchorService.onEventAppended({…rowHash})` and the verifier recomputes per [Security architecture §Audit Log Integrity](../architecture/security-architecture.md#audit-log-integrity) Rule 3, NOT `canonical_bytes`: the canonical bytes are discarded at compaction, so a `canonical_bytes`-leaved root could never be reproduced at verify time, whereas `row_hash` is frozen by the I-006-3-03 chain-commitment-frozen invariant and survives; RFC 9162 §2.1.1 MTH — leaves are `HASH(0x00 || row_hash)`, interior nodes `HASH(0x01 || left || right)`, the list splitting at the largest power of two below its length), sign the anchor claim with the daemon's Ed25519 key ([§Anchoring Cadence](#anchoring-cadence) — coordinates and root together, per the 2026-08-11 amendment), and queue for upload.
3. Wait for the anchor row to land in `pending_anchor_uploads` with a durable monotonic sequence (does NOT require successful control-plane upload — the local queue's durable ordering plus daemon signature is sufficient, since the queue's `UNIQUE(session_id, node_id, start_sequence, end_sequence)` makes re-anchoring the **same** range after partition recovery idempotent while still letting a wider covering anchor that shares a `start_sequence` coexist — the step-1 coverage test, not an exact-`start_sequence` match, decides whether a force-fire is needed).
4. For each row in the range, build the audit-stub projection (the field set in [§ Compacted Event Format](#compacted-event-format)) and serialize it **once** to its canonical byte string `B = canonical_bytes(stub)` (RFC 8785 JCS), then compute `stub_signature = Ed25519-sign(B, daemon_signing_key)`. Because `B` includes the row's `id` and `sequence`, the signature is bound to the specific row and cannot be replayed onto another. `B` itself — not a re-serialization of it — is the value step 5 stores in `payload`.
5. ONLY THEN mutate the rows in one transaction: **replace** `payload` with the exact canonical byte string `B` from step 4 (the column is `NOT NULL`; persisting `B` verbatim — never a re-serialization — is load-bearing so that checking `stub_signature` over the stored bytes at verify time is sound); set `correlation_id` / `causation_id` / `pii_payload` / `pii_participant_id` to NULL; set `retention_class = 'audit_stub'`; write the `stub_signature` from step 4.

The compactor MUST refuse to proceed with payload mutation if step 1 returns false and step 2 fails. Chain-commitment columns (`prev_hash`, `row_hash`, `daemon_signature`, `participant_signature`, `monotonic_ns`, `version`) are NEVER mutated — they remain frozen as the commitment to the pre-compaction state, even though per-row recomputation against the (now-stub) `payload` would fail.

**Verifier semantics on compacted rows.** For rows with `retention_class = 'audit_stub'`, the verifier runs **three** checks (all must pass):

- _Original-existence (anchor) check._ Per-row chain recomputation against the original is **skipped** — those bytes are unrecoverable. The verifier instead reads the covering anchor from `pending_anchor_uploads` (local) or `event_log_anchors` (control-plane) and verifies its daemon Ed25519 `root_signature` over the anchor claim ([§Anchoring Cadence](#anchoring-cadence) — coordinates and root together per the 2026-08-11 amendment, so a stored record whose span or log identity was relabeled fails here rather than passing a coverage test on unsigned coordinates). Anchor absent → `audit_integrity_failed` with `failureMode: 'anchor_missing_for_compacted_range'`. Anchor present but `root_signature` verification fails → `failureMode: 'anchor_signature_invalid'`.
- _Stub-authenticity (stub_signature) check._ The verifier checks `stub_signature` **directly over the canonical byte string stored in `payload`** — the exact bytes the compactor signed and persisted (step 5) — using the same `NodeId`-resolved daemon Ed25519 public key from the participant roster. It does **not** re-canonicalize the stub or reconstruct it from the scalar columns (`compactedAt` and `summary` are not columns; they live only inside the stored projection): verifying the stored bytes verbatim is strictly stronger (it catches **any** byte-level edit, not only semantic ones) and avoids a JCS round-trip at verify time. A `stub_signature` that is absent OR fails to verify on an `audit_stub` row → `audit_integrity_failed` with `failureMode: 'stub_signature_invalid'` (the signature is REQUIRED on every compacted row; its absence is a verification failure, never a skip).
- _Scalar-binding check._ The surviving scalar columns on the `audit_stub` row (`id`, `session_id`, `sequence`, `occurred_at`, `category`, `type`, `actor`) are a denormalized cache that SQL filters (`idx_session_events_type`) and envelope reconstruction read — they are NOT covered by `stub_signature`, which signs only the `payload` projection bytes. The verifier therefore decodes the projection from the just-verified `payload` bytes and asserts each scalar column **byte-equals** its projection counterpart (column `occurred_at` ↔ field `occurredAt`, `session_id` ↔ `sessionId`, and so on; `compactedAt` and `summary` have no scalar column and are exempt), plus the conditional provenance binding the 2026-08-11 received-row amendment added: `received_from_node_id` non-NULL ⇔ projection member `receivedFromNodeId` present and equal, both-absent a pass — with the received-as-stub class dispatched per the paragraph below, whose projection **lacks** the member by construction. Any divergence → `audit_integrity_failed` with `failureMode: 'stub_scalar_mismatch'`. Without it an actor with at-rest DB write access could edit a scalar column (e.g. `actor`, `type`) while leaving `payload` intact: `stub_signature` and the anchor over the frozen `row_hash` would both still verify, yet a filter or reconstruction reading the scalar column would surface the forged value. The signed `payload` projection is the authoritative source for a compacted row's envelope fields — the scalar columns are trustworthy only once this check passes.

A range verifies only when every compacted row passes all three checks. For mixed ranges (some uncompacted, some `audit_stub`), the verifier performs per-row chain recomputation on the uncompacted prefix and the three compacted-row checks on the compacted suffix; all must pass for the range as a whole to verify.

**Received-as-stub rows dispatch the three checks (2026-08-12 amendment, Codex PR #323 round 3).** A [Spec-008 §Peer History Backfill On Join (V1)](008-control-plane-relay-and-session-join.md#peer-history-backfill-on-join-v1) joiner appends an **origin-compacted** stub with the origin's projection bytes stored verbatim as `payload`, the origin's `stub_signature` retained, `received_from_node_id` stamped, and a fresh local `sequence` — a fourth row shape the three checks above must not misread. The class is **self-discriminating**: `received_from_node_id` is non-NULL while the stored projection carries **no** `receivedFromNodeId` member (an origin-authored projection never had one; a received row the **local** compactor stubs later carries the member and stays on the ordinary checks under the local key). On this class: the _stub-authenticity_ check resolves the verification key through the **marker** — the origin `NodeId`'s roster key, the same resolution rule received full rows use at their receive boundary — over the stored verbatim bytes as always; the _scalar-binding_ check exempts exactly two bindings, `sequence` (the projection's member is the **origin's** log coordinate inside signed bytes; the column is the local append position) and the provenance binding above (member absent by construction), and enforces every other column unchanged; and the _original-existence_ check is satisfied **at the receive boundary** by the entry-carried, origin-signed covering anchor Spec-008 requires and verifies before append — consumed there like a received full row's origin signature, since no local store holds foreign anchors and the origin's control-plane upload is asynchronous — after which the joiner's own chain binds the row, so the anchor arm is not re-required at rest on this class. Every cross-class flip an at-rest writer can attempt breaks a signature: clearing the marker sends the row to the local-key check, which the origin-signed bytes fail; planting a marker on a locally-compacted stub sends it to an origin key its locally-signed bytes fail; stripping or editing the projection member breaks whichever `stub_signature` covered it — fail-closed in all arms, no new `failureMode` value needed.

**Tamper-evidence guarantees post-compaction (threat model).** The threat is an actor with write access to the at-rest SQLite database but WITHOUT the daemon's sealed signing key (the daemon itself is the trusted compaction authority). Against that actor:

- _Edit the visible stub_ (`summary`, `actor`, …) inside `payload`: the modified `payload` bytes no longer match `stub_signature` → `stub_signature_invalid`. (This is the gap the prior anchor-only design missed: the anchor commits to the original `row_hash`, not to the post-compaction stub bytes.)
- _Edit a surviving scalar column_ (`actor`, `type`, `category`, `occurred_at`) while leaving `payload` intact: the scalar no longer equals the signed projection → `stub_scalar_mismatch`. Both `stub_signature` over `payload` and the anchor over the frozen `row_hash` still verify, so the scalar-binding check is the only thing that catches a forged value surfaced through a filter or envelope reconstruction.
- _Replay a valid stub+signature from another row_: the canonical bytes bind `id` + `sequence`, so a row-A signature fails to verify against row-B bytes → `stub_signature_invalid`.
- _Strip the `stub_signature`_ to dodge the check: a NULL `stub_signature` on an `audit_stub` row is itself a failure → `stub_signature_invalid`.
- _Flip `retention_class` `'audit_stub'` → NULL_ to force the row down the live-chain path: per-row recomputation then runs over the current (stub) `payload`, which does not match the frozen `row_hash` → `hash_mismatch`.
- _Flip `retention_class` NULL → `'audit_stub'`_ on a live row to dodge per-row checks: the row has no covering compaction anchor (`anchor_missing_for_compacted_range`) and no `stub_signature` (`stub_signature_invalid`).

Anchors remain immutable once queued (the durable `pending_anchor_uploads` queue plus the control-plane `event_log_anchors` table hold two independent copies of the signed commitment), so the original-existence proof is independently durable. Stub authenticity is now asserted at **per-row** granularity by `stub_signature`, not merely at anchor-presence granularity.

The four `failureMode` enum values added for the post-compaction protocol (`'anchor_missing_for_compacted_range'`, `'anchor_signature_invalid'`, `'stub_signature_invalid'`, `'stub_scalar_mismatch'`) are additive-MINOR extensions to the canonical 7-value enum at [§Audit Integrity (`audit_integrity`)](#audit-integrity-audit_integrity) per [ADR-018 §Decision #8](../decisions/018-cross-version-compatibility.md#decision) (MINOR additive enum-value extension is sanctioned), taking the enum to 11 values as of that amendment — 12 as of the 2026-07-26 `signature_placeholder` amendment recorded under §Integrity Protocol, and **15 values** today, after the three 2026-07-27 amendments (`occurred_at_not_canonical`, then `pii_ciphertext_digest_unbound`, then `pii_owner_stamp_unbound`) recorded in the `audit_integrity_failed` row's own description (the canonical list is the `audit_integrity_failed` row at [§Audit Integrity (`audit_integrity`)](#audit-integrity-audit_integrity), not this arithmetic). **Security amendment (approved spec):** the `stub_signature` per-row commitment was added 2026-05-28 in response to a P1 review finding (PR #124) that the prior anchor-only post-compaction design left the visible stub bytes unauthenticated. A follow-on P1 finding the same date (PR #124 round-5) showed the surviving scalar columns (`category`, `type`, `actor`, `occurred_at`) remained unbound to `stub_signature` — a forged scalar could survive verification — so the per-row **scalar-binding check** above was added (`stub_scalar_mismatch`). The 2026-07-26 and 2026-07-27 additions followed the same route: each was a P1 review finding on an approved spec (`signature_placeholder` on PR #256, then `occurred_at_not_canonical`, `pii_ciphertext_digest_unbound`, and `pii_owner_stamp_unbound` on the same PR), and the last three are one class found three times — a signature committing to a value nothing compared back, first for the stored `occurred_at` spelling, then for the `pii_payload` ciphertext, then for that ciphertext's owner stamp, each successive one found by sweeping for the class the previous exposed. All are recorded here as deliberate amendments to an approved spec, not routine editorial changes; the 2026-05-28 pair is the standing precedent that this route does not require a status flip.

### Replay Interaction with Compacted Regions

- Replay from compacted regions returns audit stubs, not full events.
- The replay cursor tracks whether a session has compacted regions.
- Projection rebuild from compacted regions uses the audit stub summary — this produces a degraded but functional timeline.
- If a projection requires full event data (e.g., to rebuild approval state), and that data has been compacted, the projection enters `degraded` state and surfaces a warning.
- Clients can detect compacted regions via the `retentionClass: 'audit_stub'` field and render them as summarized timeline segments.
- See [Spec-015](015-persistence-recovery-and-replay.md) for full replay and recovery semantics.

## State And Data Implications

- Canonical events are the source of truth for replay and audit.
- Read projections may be rebuilt from canonical events.
- Command receipts or equivalent idempotency markers are required for safe replay of side-effecting command paths.

## Example Flows

- `Example: A run starts, emits tool activity, requests approval, publishes a diff artifact, and completes. Each change becomes a canonical session event with causation and actor metadata.`
- `Example: A participant reconnects after missing events and requests replay after the last acknowledged session sequence.`

## Implementation Notes

- Keep the event taxonomy stable and additive; avoid repurposing old types with new semantics.
- Treat provider-native diagnostic events as separate from canonical business events unless they are normalized.
- Replay must be safe for both operators and user-facing timeline projections.

## Pitfalls To Avoid

- Using final assistant text as the only historical source
- Mutating or deleting canonical events in normal operation
- Leaving approval or intervention decisions out of the audit log

## Acceptance Criteria

- [ ] Every run lifecycle transition results in one or more canonical session events.
- [ ] A client can recover missed state by replaying events after its last known cursor.
- [ ] Approval, membership, and artifact changes are visible in audit history even after payload compaction.
- [ ] Post-compaction range integrity is preserved via the anchor-before-compaction protocol: every compacted range has a covering Merkle anchor with valid daemon signature, and a verifier that observes an `audit_stub` row WITHOUT a covering anchor emits `audit_integrity_failed` with `failureMode: 'anchor_missing_for_compacted_range'`.
- [ ] Post-compaction stub authenticity is preserved per-row: every `audit_stub` row carries a `stub_signature` (Ed25519 over its canonical stub bytes), and a verifier that observes a tampered, replayed, or missing `stub_signature` on an `audit_stub` row emits `audit_integrity_failed` with `failureMode: 'stub_signature_invalid'`.
- [ ] Post-compaction scalar binding is enforced per-row: a verifier that observes an `audit_stub` row whose surviving scalar columns (`category`, `type`, `actor`, `occurred_at` — and, since the 2026-08-11 received-row provenance amendment, `received_from_node_id` against the conditional `receivedFromNodeId` stub field, column non-NULL ⇔ member present and equal) diverge from the signed `payload` projection emits `audit_integrity_failed` with `failureMode: 'stub_scalar_mismatch'`.
- [ ] Unsigned rows fail closed and are never retro-signed: a verifier that observes a row whose three integrity columns ALL still hold the zero-fill placeholder (`prev_hash` / `row_hash` 32 zero bytes each, `daemon_signature` 64 zero bytes) emits `audit_integrity_failed` with `failureMode: 'signature_placeholder'` and `failurePath: 'signature'` — checked before both the chain recomputation and Ed25519 verification, never reported as `hash_mismatch` or `signature_mismatch`, and never repaired by signing the row with a current key. A row whose chain columns are intact but whose signature is zeroed is NOT this case and keeps its ordinary verdict.
- [ ] The stored `occurred_at` spelling is bound at rest: a verifier that observes a row whose `occurred_at` column is not the canonical `YYYY-MM-DDTHH:MM:SS.sssZ` form emits `audit_integrity_failed` with `failureMode: 'occurred_at_not_canonical'` and `failurePath: 'signature'`. The check runs UNCONDITIONALLY on every row — live and `audit_stub` alike — and is never gated behind a hash or signature failure, because a row carrying a respelled-but-equal-instant `occurred_at` passes both the chain recomputation and the Ed25519 verification; a green `verifyRow` verdict is the state this defect produces, not a licence to skip. The sole row exempted is one the `signature_placeholder` precondition has already refused and stopped on, whose single verdict is unchanged.
- [ ] The PII ciphertext column is bound by the signature that covers its digest: a verifier that observes a row where `pii_payload` and the signed `pii_ciphertext_digest` disagree emits `audit_integrity_failed` with `failureMode: 'pii_ciphertext_digest_unbound'` and `failurePath: 'signature'`. "Disagree" covers all three defective states — stored bytes whose BLAKE3 differs from the digest, stored bytes with no digest at all (violating the non-NULL MUST in §Canonical Serialization Rules), and a digest whose ciphertext has been removed at rest. The check runs as a POSTcondition of the signature verification, never before it, because the digest is only trustworthy once the bytes carrying it have verified; it is unconditional wherever `pii_payload` is non-NULL, including on crypto-shredded rows, whose ciphertext Spec-022 Path 1 retains intact. A row with neither ciphertext nor digest passes — that is an ordinary no-PII row or a compacted stub. On a **received** row (`received_from_node_id` non-NULL) the check takes the 2026-08-11 amendment's require-absent arm instead of the compare: `pii_payload` MUST be NULL, and a planted ciphertext is reported under this same mode rather than compared against the carried origin digest.
- [ ] The PII owner stamp is bound by the signature that covers it: a verifier that observes a row whose durable participant-id stamp and signed `pii_participant_id` claim disagree emits `audit_integrity_failed` with `failureMode: 'pii_owner_stamp_unbound'` and `failurePath: 'signature'`. "Disagree" covers all three defective states — a stamp differing from the signed claim, a stamp with no claim at all (violating the non-NULL MUST in §Canonical Serialization Rules), and a claim whose stamp has been cleared at rest. Like the digest check it runs as a POSTcondition of the signature verification, never before it, because the claim lives inside the bytes that verification authenticates; a row carrying neither stamp nor claim passes, that being an ordinary no-PII row. It is deliberately NOT discharged by the digest check: the digest binds WHICH bytes the row holds, the stamp binds WHOSE data they are, and after a Spec-022 Path 1 shred destroys the key the stamp is the only answer to the second question that survives. The stamp column the check reads against is added by Plan-006 T3.1, which also confirms §Compacted Event Format's disposition that compaction clears it; should T3.1 instead retain it on compacted rows, the check is scoped by its caller to `retention_class IS NULL` rather than softened into a pass. On a **received** row (`received_from_node_id` non-NULL) the check takes the 2026-08-11 amendment's require-absent arm instead of the compare: the stamp column MUST be NULL, and a planted stamp is reported under this same mode rather than compared against the carried origin claim.
