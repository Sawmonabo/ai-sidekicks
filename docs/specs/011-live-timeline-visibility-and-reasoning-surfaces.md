## Purpose

Define the user-facing contract for live timeline visibility, background work surfacing, and reasoning disclosure.

## Scope

This spec covers the canonical timeline read model, child-run visibility, reasoning surfaces, and replay-aware live updates.

## Non-Goals

- Notification rules
- Artifact storage internals
- Provider-specific reasoning formats

## Required Behavior

- The system must expose one live timeline per session or channel view built from canonical events.
- Timeline rows must cover at least messages, handoffs, run state changes, tool activity, approval events, interventions, artifacts, and child-run activity.
- Background runs and child runs must be visible in the primary session experience, even when details are lazy-loaded.
- Reasoning surfaces must be normalized and policy-aware; unavailable or redacted reasoning must still produce a visible reason surface.
- Durable reasoning surfaces must be limited to normalized reasoning summaries, state transitions, tool-intent or tool-result summaries, and policy-redaction markers. Provider-native detailed reasoning is not guaranteed durable.
- Live delivery must support replay catch-up so clients can recover missing timeline state.
- **Superseded-turn rendering (campaign B9, CP-003-13 — 2026-07-20).** Rolled-back (superseded) turns remain in the timeline and MUST render distinctly from current rows — an explicit superseded treatment, never dropped and never re-rendered as current ([Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) owns the supersede semantics; marks are epoch-scoped, so a re-executed turn reusing a superseded ordinal renders current). The marking reaches the surface on two legs with one outcome: `TimelineRead` and replay rows carry a projection-computed `superseded` marker (sourced from the Plan-003 supersede projection's exported `supersededTurns(runId)` read — the CP-003-13 seam), and on the live stream the accepted `run.rolled_back` boundary entry (§Timeline Entry Types) — delivered to every filtered subscription whose filter admits any of the affected run's rows (projection-resolved visibility, never the event's optional channel field) — instructs the client to apply the same treatment to that run's **already-delivered** rows whose carried run position exceeds the carried rewind cutoff (run-scoped rows expose their run identity, projection-resolved originating run position, and execution epoch as typed row fields required together — a partial attribution row fails schema validation, never a silently incomparable cached row; the session event sequence is never a run position, and the boundary entry is a typed arm of the discriminated row union the read and subscribe surfaces return: its payload is validated into the `run.rolled_back` event shape at projection, so the cutoff is never read through an untyped cast) — an idempotent rule across multi-rollback sequences (a row already superseded re-marks as a no-op), with each newly-marked row's marker being just the boundary's cutoff against the row's own exposed identity — identical to the replay-computed marker by construction, a previously-current row's first remover being that boundary, so a subscriber that joined from a bounded window after earlier rollbacks marks its cached rows without recovering epochs from reused ordinals whose delivery-order scoping needs no epoch tag, because every row delivered **after** the boundary arrives with its marker already projection-computed: a late pre-rollback straggler appends pre-marked exactly when its stamped attribution ranks it above the run's effective cutoff for its epoch — the minimum rewind cutoff among accepted rollbacks at its epoch or later in the run's lineage, since a later rollback that rewinds below an earlier retained prefix supersedes the inherited rows — and current when it ranks into the run's surviving history ([Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior); the CP-003-12 `sourcePosition` companion exists precisely for this ranking) — and a new-epoch row appends unmarked — so live and replay views converge on identical marking. A compacted superseded row keeps the treatment: its audit stub renders with both the compaction placeholder and the superseded marker (stub-preserved attribution — [Spec-005 §Compacted Event Format](005-session-event-taxonomy-and-audit-log.md#compacted-event-format)).
- **The timeline is one continuous flow.** No card, no panel and no framed container stands around any turn. Role is carried by asymmetry alone: the user's words render in a tinted, right-aligned bubble sized to its own text — no width cap, so a short message sits well inside the column and a long one grows to the column's edge — and the sidekick's words render as flat prose with no bubble. There is no left-and-right alternation, no avatar, no name label, no role eyebrow, no fixed clock column, no per-turn border, no scrubber, and no seen-or-read mark of any kind, there being one person here and nobody for such a mark to tell ([ADR-034](../decisions/034-transcript-is-one-flow.md) holds the reasons). Every row sits in one centred column whose width every row in the flow reads, and one gap — derived from the reading line rather than chosen, so it moves with the text size — sets the distance between any two consecutive rows whatever those rows are, no row kind carrying a margin of its own. The flow offers exactly two position aids and no third: a rail whose ticks lead to the moments that need a person, and one control that returns the reader to the live tail.
- **A reply's time is its own foot, not a row.** The foot carries the reply's time stamp and a copy action, is drawn the moment the reply has something to read so a time never stands over an empty answer, and stays for the rest of the turn. A user turn's actions — copy, fork, edit, undo to here — and its time are revealed on hover or on focus inside the bubble. Where the day changes between two rows, one quiet line between them reads that date in the machine's own clock format; it is a label and leads nowhere, so it is not a way of moving about the flow. There is no unread line and no typing indicator.
- **Every state-changing act appends a row.** Goal set and cleared, context compacted, worktree created, moved and removed, committed, pushed, pull request opened, review posted, an interrupt, a restore, a plan accepted or handed to a fresh session, and fork provenance. An act row names the act and never the actor. A product command that does work of its own appends one; a product command that presses a control appends whatever that control's own press appends, which for most controls is nothing.
- **A provider notice lands as one act row** — the notice in words on the row, with its reason and what to do about it on faint lines beneath — drawn in the colour reserved for "a person is needed" only where one is, and in the flow's ordinary quiet otherwise.
- **Grouping comes from the daemon's own run boundaries** in a session's flow, while a child run's view groups consecutive tool, diff and output rows at render time. A notification landing between the calls of a run joins that run rather than ending it and is counted in the group's header; one with no call before it in the run stands on its own. A message the wire delivered in two pieces is rejoined where grouping is decided, before anything is drawn, so the timeline shows one message with one time and one copy.
- **Success is shown by absence; only failure is marked.** A call that succeeded carries no tick, no "done" and no colour of its own. Failure is derived from the run's own durable record, so a restart replays the same answer and a run that failed still reads failed the next morning: there is no stored failure flag and nothing for anyone to clear. A failed call carries one line saying why — the reason in plain words, with the code the tool returned beside it, rendered as words wherever words exist for it — and a failed command's reason line carries its exit code and the last lines the command printed with colour codes removed, the rest of the output staying in the call's body. A call the **user declined** is not marked as a failure and never in the colour that means a person is needed: it reads as a failed row whose reason says `Declined`. A run group's header carries the same mark and a failure count whenever any call in it failed, and names the call now running while one runs, in its folded and its open state alike; a declined call is not counted there either.
- **A reasoning surface renders as a three-line tail.** It shows the last three lines and clips the head — a tail, never an ellipsis — with a count at its head saying how many lines the tail hides, and it renders the reasoning's own emphasis, monospace and links as real runs, the links not being pressable. One press opens the whole reasoning in place and a second folds it back to the tail; while the thought is still arriving the opened text keeps growing and nothing is shown twice. Where the provider kept no reasoning, the row says so rather than opening on nothing — that is the visible unavailability reason this spec requires, in its ordinary form.
- **Code is coloured once, in the daemon, and every surface paints the spans it is handed.** Code in the timeline — a code block in a reply, a diff under a tool row, a file opened from a row — carries the colour spans the daemon computed for that file and cached against what the file holds, painted as classes that read the theme's own code tokens rather than as colours written onto elements, so a theme or scheme change repaints the same spans and nothing is ever coloured twice; a language nobody recognises stays plain with no round trip ([ADR-035](../decisions/035-one-syntax-colourer-in-the-daemon.md)). A block still being written keeps the colours it already has — the lines that arrived stay coloured and only the line still arriving is plain until it lands — and a block redrawn after a theme change starts from the colours it had rather than flashing back to plain. Command output keeps the colour the program itself wrote, mapped into the one terminal colour vocabulary this product carries so a line reads the same in a tool row as in a shell, with bold, italic and underline kept, a code naming a colour outside that vocabulary mapped to its nearest entry rather than dropped, background colours not drawn — a washed line is the diff's own mark — and cursor and screen-control sequences removed.
- **A tool row names the provider's own verb for the tool**, never a name this product holds in a list of its own, so a tool the provider added yesterday reads under its own name today. The one mapped verb is a notebook cell edit, drawn as an edit on the notebook's path with the cell it touched as a chip beside the path and that cell's own changed lines under the row, because the provider's word there names the file kind rather than the act. A command row reads the command the sidekick wrote with the provider's shell wrapper stripped — in a truncated row too — while the whole invocation stays in the call's body. A tool-server call reads the label that tool registers for a person to read, never the server's dotted name and never its arguments bracketed after it; the call's own arguments sit in the body under the row, each named and laid out by what it is.
- **A path a call names is a link to the file it names**, on every row whose verb names a file, in a session's flow and in a child's view alike; a command's row carries none. The path's whole text stays in the row's hover title, which is how a truncated one is read in full, and a line, or a line and column, the call named is carried on the path. Opening it opens the file where that session reads files ([Spec-012 §Required Behavior](./012-artifacts-files-and-attachments.md#required-behavior)), scrolled to the line the call named.
- **Nothing folds itself.** Every run group and every foldable call is open at rest, live or long settled; a run never closes when it ends and a call never closes when its output lands, and a fold is only ever where the user put it. A group's header is its own fold control, sits in the tab order, and reports its open state to assistive technology; a call with a body under it folds on its own row while its one summary line stays; and a call whose whole output is that summary line, or that has no output at all, offers no fold, no press and no tab stop, because a control that opens something is drawn only where there is something to open. Whether a call is folded, and whatever body it has already fetched, belong to the call rather than to the element drawn for it: a row scrolled out of the drawn window and back is in the state the user left it in and does not fetch its body a second time. The reasoning tail is the same three lines whether the thought is running or settled. One pair of commands folds and unfolds every run group of the session at once and sets exactly the state a header press sets, so a group's control can never disagree with the group.
- **A large body arrives only when its control is pressed**, never because the reader scrolled past it: the control names the size before the press, says so while the read is out, and offers the press again when the read fails. The same holds for a patch the daemon did not send with the row — such a call looks exactly like one whose patch travelled, and one read covers every missing file in that call.
- **No row re-runs the call it records.** A tool runs when the sidekick calls it; running one again is asked of the sidekick in the message box, and the sidekick's own row is the record of what happened.
- **The working line carries the turn's own live data.** It is drawn only while it has something to say — the activity, the state after a pause or an interrupt, or the connection state — and is absent on an idle session and while a plan waits for its verdict. Its data is: the **action words**, which say what the sidekick is doing right now (`Running pnpm test`, `Editing <path>`, `Writing the summary`, `Waiting for approval`, `Waiting for your answer`, `Compacting…`, `Retrying…`), hold the last step's words while reasoning streams between steps, read `Thinking` before a turn's first step has landed, and stay after a pause or an interrupt; the turn's **elapsed clock**; the **token figure**, the tokens received this turn, marked with a downward arrow and stepped from the provider's own usage frames once per model round rather than per word, starting at zero when the turn starts, holding across a pause, and muting with the clock after a stop; the **state word**, one reading at a time and absent together with its separator when there is none — `Thinking` while reasoning streams between steps, `Pausing` then `Paused`, and `Interrupted` followed by what is still outstanding (sidekicks still running, a command still running, or waiting); the **tasks word**, `N of M tasks` while the turn has a task list; and the **count of questions** the sidekick did not wait for while any are unanswered. From the press of send until the turn starts the action words read `Sending…` with no clock and no token figure beside them. No live token figure stands anywhere else in the product and no message carries one. A child run's line carries the same data without the token figure, because a child's own head already carries its tokens and its spend, and its state word additionally reads `Done` or `Stopped` once the child is over. No reading ever moves the clock backwards.
- **The task list is the provider's own list**, read from the sidekick's task-list tool calls on Claude Code and from the plan-update stream on Codex, which the daemon enables for every session because that provider leaves it off. It is shown in the sidekick's own order with each item's state — done, in progress, not started — and it is never merged with the list of running commands, never a row in the timeline and never a section in an inspector; opening either list closes the other, so one is open at a time. The tasks word leaves after an interrupt and returns with the next turn's list.
- **A plan renders as one full-width document in the flow**, at the timeline's own content width: an accent rail down its left and every heading, numbered step, nested list, code block and table as the sidekick wrote them, nothing folded and nothing summarised, never inside a bubble and never inside a card. Its footer says that nothing was changed, and names the plan file where the provider wrote one. The reply's own foot with its copy follows it as after any reply, and the working line is hidden while the plan waits. Lines selected inside a plan can be quoted into the draft through one control that rises at the selection's end and goes when the selection is cleared; a plan carries no comments and nothing is anchored to it. The verdict itself is an approval-pipeline decision ([Spec-010 §Interfaces And Contracts](./010-approvals-permissions-and-trust-boundaries.md#interfaces-and-contracts)), and a revised plan lands as a second full-width document.

## Default Behavior

- Timeline rows default to chronological order from oldest to newest within the current view.
- **Nothing is collapsed at rest.** Every run group and every foldable call opens as it arrives and stays as the user left it (§Required Behavior). What bounds a large payload is a **cut**, not a fold: a long diff, a long command output and a long pasted message are each drawn to a height derived from the visible flow and the current text size, faded at the cut, with the rest one press away and the control that opens it naming what it will bring.
- Child-run activity defaults to summarized rows with explicit expansion for detailed inspection.
- If provider reasoning is available and permitted, the system may render a structured reasoning surface tied to the relevant run or message row.
- Detailed provider-native reasoning defaults to ephemeral rendering or bounded diagnostic retention only when policy allows it; it is not part of the durable canonical timeline contract.
- **Streaming reveals prose word by word at the pace the words arrive, with no lead-in.** A reply's first word is on screen the moment the runtime has it; the reveal catches up at no more than twice the arriving pace when the wire runs ahead, and it keeps draining after the turn closes so nothing is left unshown. It breaks on word boundaries, so a long word arrives whole, and arriving text changes only its opacity, so a line filling in never reflows the lines above it and nothing that has settled shifts. Coming back to a session draws everything that arrived while the user was away as settled text at full strength with no reveal; only words arriving from that moment on animate. There is one rendering of a reply and no setting that turns streaming off — a machine set to reduced motion resolves a stream straight to the full text, which is the one case such a setting would have served.
- **Markdown that has only half arrived is drawn as what it is becoming**: a code fence is framed from its first line, a half-typed link is held as its text until its target lands, a half-typed picture or footnote mark draws nothing, and emphasis whose closer has not arrived is mended for display rather than showing its marks. The text underneath stays exactly what arrived, so a copy and a search still read the truth. A reply still arriving is split at its last settled block, so the blocks before it are never re-read and a selection crossing the split survives it.
- **One ticker advances every live figure on the screen**, beating once a second, which is the finest figure any of them shows; there is no per-row interval. A live elapsed figure and a finished duration share one cell in one colour, and a figure that finishes freezes in place rather than being replaced. Live figures under a minute read in whole seconds and at or above a minute as minutes and seconds. The figure is never tinted — not while waiting, not while running — and a session row's status dot never blinks, a live elapsed figure being what says the sidekick is working. Every elapsed reading lives in the model and is never read back out of the page, so a re-render never resets a clock.
- **The flow follows its own tail only while the reader is near it.** A scroll away from the bottom releases the follow at once, however small the scroll, and it re-engages when the reader returns to within a couple of line heights of the bottom or presses the control that jumps to the live tail — the one control that returns the reader there, drawn only while the follow is released and nothing drawn over the flow. A selection being dragged inside the flow suspends the follow for as long as the button is held, so a reply arriving underneath never pulls the words out from under the pointer. While the follow is on, the flow glides after arriving text rather than jumping; a layout correction is not arriving text and is placed at once — a picture that typesets late, a row that remeasures, a reflow at a new width — as is everything on a machine set to reduced motion.
- **Motion runs only where something changes under the reader's eye** — a fold opening, a row arriving, the follow gliding. It is armed by the change itself rather than by scrolling past it, and a change in a region that is out of view is placed at once instead; reduced motion removes every animation and transition without exception.
- **History loads in stretches, never all at once.** Only the rows near the window are drawn, with a band above and below kept ready so a fast scroll never shows blank space where rows have not drawn yet. At the top of what is loaded, one line offers the stretch before it, and a wheel, an arrow key or an upward drag made at the very top asks for it too; older history also comes in on its own as the reader nears the top, one stretch per gesture so a fling cannot pull in a whole day, and how much comes in is a stretch of the screen's own height rather than a count of rows. Newer rows page in as the reader nears the bottom of a window opened in the middle of a long session, so a reader who landed on a search hit reads forward rather than reloading. In every case the reading position stays where it was.
- **Rows leave memory in cuts, and a cut never takes a row someone is reading.** Old rows are released in cuts that never take a row that is on screen and never take the row under the reader — a cut that would is refused — and never take the rows an open child-run view is showing, or its parent's. A session the user has opened before mounts at the heights its rows really had, so the reading place lands where it belongs instead of drifting as each row measures itself, a row with no remembered height taking an estimate for its kind until it measures.
- **Every way of reaching one row takes the same path** — a tick on the rail, a search match, a review note, a notification: the row is loaded if it is not on the page, the run group holding it is opened first, the flow lands on it, and it is marked briefly by opacity alone so the mark survives reduced motion. A row that is no longer there says so in one line instead of moving the page.
- **One selection runs across every kind of row** — prose, a message, a list, a table cell, a tool row, an act row — and survives both the rows around it leaving the drawn window and the reply still arriving underneath it: text that is still streaming only ever grows, and no block a selection touches is redrawn while it touches it. A chunk of arriving output adds its new lines and touches nothing already drawn.

## Fallback Behavior

- If live delivery gaps occur, the client must request replay from the canonical event source.
- If detailed reasoning or tool payload is unavailable or policy-restricted, the timeline must show a placeholder row with the reason for unavailability.
- If a child-run detail fetch fails, the summary row remains visible and marked incomplete rather than disappearing. The mark is **explicit and required**, never inferred from a low event count: it names a **cause** from the closed set `detail_fetch_failed` (this daemon's own expansion read failed) / `compacted` (the rows were compacted away), together with the time that cause was observed, because the first is transient and the second terminal and a consumer's right response differs between them. On the incomplete arm the summary's event count is a **lower bound** — what the daemon holds, not the child run's total.
- If detailed reasoning has been compacted or was never retained, the durable reasoning summary or policy placeholder remains the canonical visible surface.
- If a dispatch is refused, the timeline appends one row naming the cause. A refusal is never swallowed and never leaves the flow silent.
- If a provider imposes a limit mid-turn, the working line carries it and the flow carries one act row for it, never a banner and never a modal: on Claude Code the action words read `Retrying…` in place of the verb while the retries run, then `<Provider> did not answer · Try again` if they give out; on Codex the line reads `Limit reached · resets at <time> · Try again`.
- If a turn is interrupted while a command it started is still running, the working line's state word says so — `Interrupted · a command still running` — until the daemon has ended the process, and that command's row settles as stopped then and never before. A pause reads `Pausing · a command still running` and waits for it the same way.
- If a call's patch or a call's whole output was not delivered with the row, the row looks exactly like one whose payload travelled and its place says it is loading while the read is out; a read that failed says so where the content would sit and offers the press again, one read covering every missing file of that call.
- If a picture cannot be shown, its place is still reserved at the size the daemon holds for that file and a named state is drawn where the picture would be — loading, unavailable, or refused — rather than a blank. A block that cannot be drawn shows its own source with one line above it saying it could not be drawn and why.
- If a superseded row's payload has been compacted, the stub placeholder retains the superseded treatment — compaction never launders a rewound row back to current. A vacuous-attribution-era legacy stub (its position unknowable) renders the compaction placeholder alone, exempt from marking by construction — a run carrying one can never admit a rollback ([Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior)'s standing refusal), so no marker can ever apply to it.

## Timeline Entry Types

> These timeline entry types are projection-layer constructs derived from canonical session events (see [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)). They do not create new event types.

### Flow Row Kinds

The flow renders these kinds and no others. Each is a row in the one column of §Required Behavior, one gap apart from its neighbours.

- **Act row** — a hairline rule either side, the act's own name, its text capped at about half the row, and a tabular time stamp.
- **User turn** — the tinted, right-aligned bubble with its own revealed actions. A message past twelve of its own lines is clipped to twelve, with a control at its foot reading the message's real line count; one press opens the whole message, takes the control with it, and holds the bubble's place on the screen so the rows above do not move. A message inside twelve lines is drawn whole and carries no control. The edit action puts the words into the draft and marks the row as being edited, its bubble saying how many turns after it would be superseded; a resend marks that row and every row after it superseded and draws a line under the bubble saying it was re-asked below.
- **Sidekick prose** — flat prose wrapping at the column's edge, followed by the reply's own foot.
- **Reasoning tail** — a glyph, a verb column as wide as the longest verb it must hold, and the three-line tail filled from the bottom.
- **Run group** — a header carrying a per-verb count over a rail that every call in the group hangs off, indented by the group's own step. The header is the group's fold control.
- **Tool row** — a glyph, the same verb column as the reasoning tail, a body carrying the target with its chips and its added-and-deleted counts, a status slot, and a right-aligned duration. A run of reads standing next to each other in one run draws as one read row listing every file, each a link, a file read twice appearing once; the row's single status mark follows the newest member still running and then the newest that failed, while the group's header still counts every read.
- **Output row** — indented to the body column, with a prefix and a summary, a good result in the success colour.
- **Running command** — the tool row with its duration live and its output growing line by line as it arrives; the row keeps its place while later rows land below it. Its own stop control sits at the row's right, in the row's own text rather than as an icon, and on a provider that waits on a command the row alone also carries a control that moves the command to the background — absent, not disabled, on a provider without that ability. Stopping leaves a stopped line in the output, freezes the timer, and appends one act row carrying the short note the daemon sent the sidekick, never a bare failure. Output is shown in a tail window derived from the visible flow, with the rest one press away and a copy lifting the whole output rather than the lines on screen; where the provider says the command is waiting for typed input the row grows one input line under its output, what is typed going to the command through the provider's own write path and the output carrying on beneath it. A command that outlives the turn stays a live row across turns. While a call's output is not there yet its body says so in its own words, and a read of the output that failed says that instead.
- **Diff block** — one block per file a call changed, each with its own counts and its own door into the review surface, and no wrapper around the set; two files of the same name each keep their own block. Added and removed lines are washed by background alone with the sign in its own one-character cell, a quiet gutter carries the new file's line numbers, a removed line keeps the number it had, a paired removal and addition mark their differing words with a stronger wash, and skipped lines of the file stand as a quiet separator that opens nothing in the flow. A long line wraps under the code rather than under the sign, so no diff scrolls sideways. The block is cut at a height the flow derives and its footer reads how many of how many lines are drawn, beside a control that opens the whole diff in place, a copy of that file's whole patch, and the door into the review surface; a diff inside the cut is drawn whole and its footer drops the open-all control alone. Past as many file blocks as a couple of screens hold, a call's remaining files fold into one footer naming how many more files changed and how many changed in total.
- **Dispatch block** — a run group holding the session's own dispatches, its header naming how many sidekicks were dispatched and how many more by them, and in tree order one item per child, a child that dispatched sidekicks of its own carrying a fold of its own and a box holding its descendants.
- **Streaming prose** — the prose row while it streams, the text already shown and the text still pending drawn as their own spans.
- **Files-written row** — a chat session only: the one list of what the chat made, every artifact in its store with its folders, each file openable ([Spec-012 §Required Behavior](./012-artifacts-files-and-attachments.md#required-behavior)).
- **Workflow progress row** — one flat row for a run this session started: the run's name, its status, its elapsed time, and a way into the run; it updates in place until the run ends.
- **Workflow results row** — the same row once the run ends: name, status, duration, a one-line summary of what came out, and the run's attachments as file rows in that same shape, with no cost figure. It is an ordinary message the session's sidekick reads on its next turn.
- **Aside row** — the answer to a question asked of a throwaway read-only copy of the session, landing in the flow at the point it was asked, in the flow's quiet type, saying on its first line that it is a side question and not part of this conversation, with the question and its answer beneath and a copy and a fork at its foot. It is never an overlay and never part of the session's own history.
- **Child-only rows** — inside a child run's view, the child's own note row and act rows for a steer and an interrupt; a pause and a continue append no row.

The approval card, the question card and the plan verdict card are **not** flow rows: they are raised in the composer area ([Spec-010 §Required Behavior](./010-approvals-permissions-and-trust-boundaries.md#required-behavior) and §`driver_ask` below), while the plan document itself is a flow row of its own (§Required Behavior).

### `handoff`

Agent-to-agent and user-to-agent handoffs rendered as discrete timeline rows, visually distinct from normal messages.

- **Payload**: `{fromActor: string, toActor: string, reason?: string, channelId?: ChannelId}`
- A `handoff` entry is emitted when:
  - Orchestration transfers a run between agents.
  - A user explicitly delegates to an agent.
  - An agent spawns a child run on a different node.

### `driver_ask`

A provider-initiated **input**-kind ask, rendered as one actionable question card in the session's composer area, where an approval card sits. Permission-kind asks are **not** rendered here — they normalize into the canonical approval model and ride the approvals surface ([Spec-010](010-approvals-permissions-and-trust-boundaries.md)), and this section changes that routing in no way. The `kind` discriminator on the event is what selects between the two surfaces, so exactly one of them renders any given ask and neither has to guess.

- **Source events**: the three `driver_ask.*` types ([Spec-005 §Driver Ask Events](005-session-event-taxonomy-and-audit-log.md#driver-ask-events)), filtered to `kind: 'input'`.
- **The card.** An eyebrow reading `Question`, the sidekick's own short header as a chip beside it, the question itself as the title, and the sidekick's heading as the summary line only where it sent one. Under them the option rows, each carrying a mark, its label, its description, and a number key on the first nine. The row the sidekick recommended stays where the sidekick put it — first, which is how both providers are asked to write it — and is marked as recommended, with the provider's own parenthetical suffix stripped so the mark is made once. A dashed `Something else…` row with a text field is **always last**, on every ask with or without options: a provider that declares no closed choice set is the ordinary case on at least one driver, and a card offering only options would leave such an ask unanswerable while its run sits blocked. Where both are present the options are a shortcut into the same answer, not a different one.
- **Answering.** Number keys pick a row, the arrows move between rows, and Enter presses the primary button; a pick never advances the card by itself. The buttons are `Skip`, `Back` — absent on the first page — and `Next`, which reads `Answer` on the last page and on a single question. The marks are boxes, and several picks go back together, on every Codex question and on a Claude Code question that carries the several-answers flag; they are single-choice marks otherwise.
- **Several questions page one at a time**, with the count of where the card stands beside its eyebrow, `Back` and `Next`, and `Answer` on the last page. Picks and typed text survive paging in both directions, every answer goes back together when the last page is answered, and `Skip` leaves that page's question unanswered and moves on.
- **Two arms exist only where the provider supplies them.** A preview column beside the option rows is drawn only where Claude Code attached previews to the options, and it follows the focused row; Codex questions never show one. A masked field with no option rows is drawn only where Codex marked the question secret; the value is never written into the timeline, and the user's turn afterwards records that a secret was answered. Claude Code questions never show that field.
- **The answer lands as one ordinary user turn**, not as a card that stays. Answering — or skipping a single question — hides the card and appends one turn carrying, per question, the question's own text as a faint quoted line with the answer beneath it at full strength: the picked labels joined with commas, the typed text, that it was skipped, or that a secret was answered. The turn is drawn settled at once, having been held while the sidekick waited. The sidekick then resumes, the working line returns to its verb, and the session leaves the group waiting on a person. That turn is the record, and the question cannot be answered twice.
- **A question the sidekick did not wait for is a message, never a card.** On the one provider that emits them, it renders as the sidekick's own message with option rows under it, joins no attention group, and is counted on the working line while it is unanswered. Pressing a row sends the quoted question and that row's label as one message, which lands as a pending row while the turn runs, the row then reading as chosen and the rows settling; typing in the composer answers it just as well. Pressing the working line's count opens the question card in its usual place on those questions, oldest first and paged, while the sidekick keeps working and the working line keeps its verb and clock; answering sends one message per question and the count drops, the control leaving at zero, while dismissing the card leaves the count where it was. Pending rows survive a pause: rows pending when the sidekick stops to ask, or to seek an approval, stay pending in place and land at the sidekick's next step once the answer resumes the turn.
- **A tool server's question is answered on this same card**, drawn in this product's own controls — text fields, one pick and several picks — with the server named beside the eyebrow the way a sidekick's short header is. The server never draws a surface of its own inside the card, and a question that would hand the user off to a web address to finish elsewhere is refused with one line saying so rather than followed.
- **The card carries no clock and never settles itself.** The daemon holds the provider's request open with no timer, rebuilds the card on reload and on every linked device of the user, and lets the first answer settle it everywhere; a device that was showing the card closes it with one line saying it was answered elsewhere. Besides the answer, the only thing that closes an open question is the end of the turn holding it: an interrupted turn cancels it, and the cancellation is recorded. The question itself never runs out of time ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)). `responded` and `canceled` each render from their own `driver_ask.*` row — the delivered answer for the first, the cancellation for the second — and the renderer derives **no** terminal state of its own, on this spec's standing wire-verbatim discipline. That matters more here than on a status row: a card carries nothing counting down, so it can never show a close the daemon has not recorded.
- **Answer dispatch** is one resolve call on the question record (§Interfaces And Contracts), carrying per question the picked labels, the typed text, the secret — which is never stored — or a skip. The daemon is what shapes that into each provider's own answer: on Claude Code the held request is answered with the ask's input unchanged plus the answers keyed by question text, the annotations and the response and nothing else; on Codex the picked labels, the typed text, or an empty list per question identifier, with the daemon writing the question record itself because that provider emits no item for it.
- **Unrecognized values render rather than vanish**: an option shape or a state value this spec does not enumerate is shown as itself, so a later member is never silently invisible.

Run-state subtypes are rendering types that map from underlying run lifecycle events. They exist so the timeline can render distinct visual treatments without inspecting raw event payloads.

## Context Window and Usage Meters

The session composer area must always display a context-window meter reflecting the current provider conversation state.

- **Fields**:
  - `usagePercent` (0-100): current context window consumption as a percentage of the provider limit.
  - `tokenCount`: combined input + output token count for the active conversation.
  - `maxTokens`: the provider's context window limit for the active model.
- **The meter is one figure and one meter, and it is never coloured**: a ring carrying the share of the window in use, with a faint notch on its arc at the compaction bound and a hover that reads the current percentage together with that bound. It is also a control: pressing it opens the compaction controls in place above it — `Compact now` over a slider reading `Compact automatically at <bound>% · of <window size>` — with no overlay, closing on Escape or a press elsewhere. There is no compaction chip anywhere in the composer area.
- **Compaction at the bound is the provider's own, and it is automatic; compaction on request is the user's.** The bound is a setting rather than a warning: the default is set once per provider and mapped onto that provider's own compaction knob, where it moves between 50 and 95 per cent of the window in steps of five; a session may hold a bound of its own behind the meter — anywhere from 10 to 95 per cent, on every window size — which applies from the next turn and carries a mark saying it belongs to this session until it matches the provider's default again; it belongs to that session alone, and the next session opened on the project starts from the provider default once more. The ceiling is 95 per cent on both controls, because a compaction needs room left over to write its summary and take the next turn. Nothing else in this product initiates a compaction: there is no second threshold, no timer and no heuristic, and no surface reshapes a conversation on its own initiative.
- **Visibility**: the context-window meter is always visible in the session composer area regardless of usage level.
- **The user-initiated trigger is a different act with a different actor** from the bound: the user decides, and the system does what it was asked. It is the compaction controls' `Compact now`, and the product command that compacts at once without opening them.
  - It is **capability-gated** on the bound driver's `context_compaction` flag ([Spec-004 §User-triggered context compaction](004-provider-driver-contract-and-capabilities.md#user-triggered-context-compaction)) and is **absent** where the flag is `false` — not present-and-disabled, because a disabled control asserts that the capability exists and is momentarily unavailable, which would be false. It is offered at every usage level rather than unlocking at a threshold: a user who wants a clean context before a long task should not have to fill one first.
  - **It dispatches the already-minted `driver.compactContext`** and renders **only** from what comes back through the event stream. A dispatch shows an in-progress state; the completed state renders on the `usage.context_compacted` row, and the meter's own new reading arrives on the ordinary `usage.context_window_update` path with no special case. The renderer never treats the request's acceptance as a compaction, and never redraws the meter from a value it predicted — both provider mechanisms answer before the work is done, so a surface that trusted the acknowledgment would show a compaction that had not happened. A refusal renders as a refusal. **The in-progress state clears on the operation's own settlement, not on the boundary row.** The two are separate moments and conflating them would hang the control: the daemon's compaction wait is bounded and can settle `failed` — an expired wait, a lost binding, a provider error — with no boundary row ever arriving ([Spec-004 §User-triggered context compaction](004-provider-driver-contract-and-capabilities.md#user-triggered-context-compaction)). So the in-progress state ends when the call settles, in **every** arm, and the settlement's own reason renders where it is not `applied`; the **completed** state still renders only on the `usage.context_compacted` row, unchanged. The two rules compose without conflict because they answer different questions — whether the request is still outstanding, and whether a compaction actually happened — and a late boundary row arriving after a `failed` settlement moves the meter exactly as a compaction the provider began on its own would, which is what it is indistinguishable from at the point it is normalized.
- **Update mechanism**: the meter is updated via `usage.context_window_update` events from the canonical event stream (see [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)).
- **What is in the context is read per provider and never computed here.** Beside the meter, a session's inspector carries a context section: one head line reading the tokens in the window against the window size together with the percentage the meter shows, then one row per bucket, each a name on the left and a right-aligned token figure. On a Claude Code session the rows are that provider's own buckets in its own order, named in this product's words — the system prompt, its system tools, the tool servers' tools, custom sidekicks, memory files, skills, the messages, the compaction buffer, and free space — with a bucket the provider defers rendered dimmed and left out of the head line's used figure, and a bucket the provider reports named parts for unfolding into rows of its own when pressed, every other row being inert. On a Codex session the rows are that provider's only split — cached input, input, output, reasoning — and one note line under them reads exactly `Codex reports totals, not what is in them.`; on a Claude Code session that line is absent rather than empty.
- **One read per provider feeds the meter and that section alike**, so the two can never disagree. On Claude Code it is the provider's own context report: the model, the total, the window size, the percentage, and the named categories with the kind the provider marks each one — used, deferred, buffer or free — together with the tool, memory-file, sidekick and skill lists that sit behind them. On Codex it is the thread's token-usage update: the total, cached input, input, output and reasoning against the model's context window, because that provider exposes no category split on any surface it has. A provider that reports no split gets the honest note line rather than a derived figure. The section is a list of figures and never a graph, and no value in it overflows its own width: a long one truncates and carries a hover title.
- **Compaction boundary and superseded marking.** A **provider-side** context compaction is recorded as a `usage.context_compacted` row ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — a different thing from the daemon retention pass's `event.compacted` audit stubs that §Required Behavior's superseded-turn bullet already covers, whether the provider reached the bound on its own or the user asked for it. Two consequences follow: the row is run-scoped, so it takes §Required Behavior's superseded treatment on exactly the same terms as every other run-scoped row, with no exemption; and this meter, which reflects the **current** provider conversation state, therefore stops reading a superseded compaction marker as the run's live compaction state. [Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) additionally treats the newest current such row as a **rewind boundary** and refuses any target below it, so in V1 no accepted rewind supersedes one and the case does not arise; the consistency stated here is what keeps the two surfaces aligned wherever a driver's re-verified boundary-crossing semantics later makes it reachable.

### Rate-Limit Display

A rate-limit indicator shows the remaining provider quota **of one named provider account, for one named limit**. The figure is an account-plane fact, never a session-level or per-run one, and it must never be rendered as either.

- **Two sanctioned Sources, and no third** (amended 2026-08-26). **(a)** The `usage.rate_limit_update` event on the canonical event stream ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)), emitted from real traffic. **(b)** The **newest stored reading** in the daemon's per-account quota-window registry ([Spec-026 §Per-limit provider quota](026-provider-accounts-and-credential-homes.md#per-limit-provider-quota)), carried on the provider-account read and its subscription. **A stored reading keeps the provenance it was observed under, not the transport that delivered it**: the registry is fed by both the real-traffic event and the deliberate probe, so a window served from it may carry `source: 'run'` exactly as legitimately as `source: 'probe'`. A consumer accepts both on a stored snapshot and never infers provenance from the fact that a reading arrived on a read rather than on the event stream. The second Source exists because the first is only available to a client that was connected when the traffic happened: a renderer opened after a reading was taken, or after a restart, would otherwise show nothing and be unable to distinguish that from a healthy account. **Precedence between them is by observation time, not by source**: newest `observedAt` per `(providerAccountId, limitId)` wins, and `source` breaks **only exact ties**. Preferring one source outright would let a stale reading mask real consumption. A stored reading additionally carries the credential generation it was observed under, and a reading whose generation is behind the account's current generation is rendered **stale rather than current** rather than dropped — a credential-home rebuild does not stop the provider-side window the reading describes ([Spec-026 §Per-limit provider quota](026-provider-accounts-and-credential-homes.md#per-limit-provider-quota)).
- **Neither Source is an HTTP response header.** The indicator is not extracted from any control-plane response header — the control plane's own rate limiting meters this product's API, which is a different quota from the provider's and must not be displayed in its place.
- **Fields** (as carried by the event, plus the account identity added by [Spec-026 §Provider quota is account-scoped](026-provider-accounts-and-credential-homes.md#provider-quota-is-account-scoped)):
  - `provider`: the provider whose quota window this reading describes.
  - `providerAccountId` and the credential generation observed with it: together the `(accountId, credentialGeneration)` account-plane key of the account the reading belongs to (see [Spec-026 §Account identity and credential generation](026-provider-accounts-and-credential-homes.md#account-identity-and-credential-generation)).
  - `limitId` (optional on the wire, defaulted on read): the provider's own identifier for **which** limit this reading describes. **This is the reading's key, together with the account** — absent means the reserved identifier `default`. It is required here because a single account may stand against several limits at once: the pinned Claude surface publishes five, of which **three share a 10080-minute window**, so a surface keyed on the window length would render one weekly limit as the operator's weekly standing and silently drop the other two, with the survivor decided by arrival order.
  - `windowMins`: the length of the provider quota window this reading describes. A **property of the reading, not part of its key** — two limits of one account may share a length.
  - `usedPercent` (0-100): the fraction of that window's quota consumed.
  - `resetsAt` (optional): ISO-8601 timestamp when the window resets, present only when the provider supplied one.
- **No absolute counts**: the carrier reports a percentage, not request or token counts. The surface must render the percentage it was given and must not synthesize a `remaining` or `limit` figure, which is not derivable from a percentage alone.
- **No run to join through**: the event carries no `runId`. Quota is consumed by an account across every run and every session that account executes, so there is no run whose row could supply the account — which is exactly why the event carries the account identity directly rather than leaving it to a join.
- **Account labeling is mandatory**: every rendered quota figure must be labeled with the account it describes, using that account's operator-chosen display label ([Spec-026 §The account registry](026-provider-accounts-and-credential-homes.md#the-account-registry)). A node may hold several accounts for one provider, and each has its own independent quota; an unlabeled or merged meter would show an operator a healthy quota while the account actually executing their run is exhausted. Readings for different accounts are never summed, averaged, or otherwise collapsed into one figure.
- **Limit labeling is mandatory on the same grounds, and readings are never collapsed across limits** (added 2026-08-26): where the provider publishes a display label for a limit it is rendered, and where it does not the limit identifier is rendered verbatim. **Every consumer obligation on this display applies per `(providerAccountId, limitId)` and never across limits** — including the drop-a-lower-reading rule, which now requires the same `limitId` as well as the same `resetsAt` before a decrease may be discarded. Two limits of one account move independently, so a comparison spanning them was never meaningful, and collapsing them would reproduce inside one account exactly the harm the account-labeling rule prevents across accounts.
- **Threshold coloring**, computed from the remaining share (`100 - usedPercent`) of the account's window:
  - Green: >50% remaining.
  - Yellow: 20-50% remaining.
  - Red: <20% remaining.
- **Reset timing**: when the indicator is visible and the reading carried a `resetsAt`, it displays a countdown to that time. A reset time is never estimated or fabricated when the provider did not supply one.
- **Visibility**: the indicator is shown for **any `(account, limit)` pair** whose remaining quota is below 50%, and hidden while that pair is healthy. An account standing against several limits may therefore show several indicators, or one, or none, independently.
- **What absence means, restated (amended 2026-08-26 — the second Source widened it, and the widening is not cosmetic).** Absence of an indicator has never been an affirmative statement that quota is healthy, and it is now less of one than before: it means no constraining reading is held for that pair, and there are **three** distinct ways for that to be true — the pair is genuinely healthy; no reading has ever been taken from either sanctioned Source; or this home is **not plan-limited at all**, which the provider itself reports for API-key and third-party-inference sessions where plan limits are simply not a concept. A surface that rendered "no limits reported" as "healthy" would misreport both of the last two. **Silencing the background health observer is deliberately not on this list**: [Spec-026 §Per-limit provider quota](026-provider-accounts-and-credential-homes.md#per-limit-provider-quota) admits exactly two quota Sources and excludes that observer by name, because reading quota on the pinned Codex leg traverses a path documented to refresh proactively. Listing the opt-out as a quota-absence cause would both misattribute the absence and invite an implementation to satisfy the explanation by having the observer fetch quota — the one thing its no-refresh invariant forbids. Where the daemon knows which of the three applies, the surface may say so; where it does not, it says nothing rather than guessing.
- **Update mechanism**: readings are keyed by `(providerAccountId, limitId)`, exactly as the event registers them ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) — re-keyed 2026-08-18 from `(provider, windowMins)` to `(providerAccountId, windowMins)`, closing the collision **across** two registered accounts of one provider, and again 2026-08-26 to `(providerAccountId, limitId)`, closing the collision **within** one account that the previous key still admitted), so a reading is held per account and per limit rather than once per node and is updated as later readings for that same pair arrive. A reading observed under a credential generation that the account has since moved past is stale and must not be shown as the account's current quota.
- **Node-local, and deliberately not symmetric with the session cost receipt**: the quota event binds to the reserved node-scope sentinel rather than to a session, and is excluded from control-plane anchor upload and from peer history backfill ([Spec-005 §Daemon-Scope Event Binding And Node-Scope Anchoring](005-session-event-taxonomy-and-audit-log.md#daemon-scope-event-binding-and-node-scope-anchoring)). A user therefore sees quota only for accounts registered on their own node, and never for the accounts of a peer executing in the same session. This does **not** generalize to spend: the session cost receipt ([Spec-014 §Session Cost Receipt](014-multi-agent-channels-and-orchestration.md#session-cost-receipt)) is session-wide, because the usage events it folds are session-scoped and relay to peers normally. A reader must not assume the two surfaces share a reach — one meters an account on this machine, the other meters a session across every machine in it.

## Interfaces And Contracts

- `TimelineRead` must support bounded windows and cursor-based continuation.
- `TimelineSubscribe` must support live append plus replay recovery.
- `ReasoningSurfaceRead` must identify availability status and policy reason when content is withheld.
- `ChildRunExpand` must read detailed activity for a summarized child-run row.
- `ReasoningSurfaceRead` and `ChildRunExpand` must support the same cursor-based continuation `TimelineRead` does: each takes an optional after-cursor, and each answers with an explicit more-to-come flag so that an over-large result is a page the caller can continue rather than a refusal or a silent truncation.
- Every page a read returns must fit in one transport message body. The substrate's limit ([Spec-006 §Wire Format](006-local-ipc-and-daemon-control.md#wire-format)) is absolute and an oversized response closes the connection rather than failing the request, so the bound is stated on the **encoded size of the page** and checked once per reply — never on a row count alone, which cannot bound a page whose per-row text fields and opaque payload are bounded independently of it. A producer fills a page until the row ceiling or the byte budget trips, whichever comes first, and reports the remainder as a continuation.
- A page that reports more to come must carry the cursor that continues it **and at least one entry**. A page promising more and delivering none advances nothing while reading like progress: the caller obeys the contract, re-asks from the same cursor, receives the same answer, and loops. The byte budget above therefore bounds **aggregation** and never bounds a page below one entry — where the first candidate alone exceeds it, the producer pages that entry rather than reporting an empty page, and the reply is refused for its size at the response boundary, which names the offending member instead of leaving a caller to loop on an unconsumed cursor. A terminal page may carry a cursor and is never required to, so a caller moving from a completed read to a live subscription has an after-cursor wherever the daemon has one; a terminal page may also be **empty**, which is the honest answer to a continuation whose cursor already sat at the end and to a filtered read that matched nothing.
- A page must be internally consistent with the header it carries: its entries never move backwards in sequence, and every run-scoped entry of a child-run expansion belongs to the run the response names.
- **Every reply and every emission is scoped to the request that asked for it, and answers the question it asked.** A timeline read returns rows of the requested session only; a child-run expansion names the requested run; a live subscription carries rows of the subscribed session only. One further reply is judged against the request rather than against itself: an `available` reasoning surface carrying **no entries** is the correct answer to a continuation whose cursor already sat at the end of the surface, and a defect on a **first** read, where it renders as a surface that exists and shows nothing — indistinguishable from the unavailable state while asserting the opposite, the state collapse the availability vocabulary exists to prevent. A producer with nothing to serve at all must answer with the state that is true. A third is judged the same way: a page may not exceed the **window the caller asked for**, which is the request's own row limit where it named one and the default ceiling where it did not — a response schema can bound a page only at the default, so a read for ten rows answering with the maximum is otherwise well-formed, and a client sizing a viewport, a budget, or a render pass from its own request is handed more with nothing on the reply saying so. None of this can be a schema rule — a response schema never sees the request — so it is enforced where both are in hand, at the daemon's method binder, on the caller's own parsed request. A cross-scope reply is a **daemon** failure and never a client one: the caller asked a well-formed question, the answer is well-formed, and it correlates to the caller's own request id, so nothing downstream can tell it apart from a correct answer. A cross-scope emission is refused before it is written rather than reported, because the acknowledgement it would ride behind has already settled and a notification frame carries no error channel.
- **A row is filed under a run wherever the corpus says it belongs to one, and it may not say so twice differently.** Whether a row is run-scoped is decided by three tests and not by its category alone: a category closed on the run-scoped side, a canonical event type whose registered payload names a run in every form ([Spec-005 §Event Type Enumeration](005-session-event-taxonomy-and-audit-log.md#event-type-enumeration)), or — for the types whose run identity is registered optional, which no type-level test can decide — the row's own payload naming one. A row answering any of the three while carrying the attribution-free kind is refused, because it would be reachable by no run filter and permanently current under rollback projection. Where a projection echoes the canonical origin keys into the payload, they must agree with the row's own attribution — under **either** registered spelling of run identity, since the intervention family names its run `targetRunId` and a rule reading only `runId` would leave every intervention row free to be filed under one run while naming another; echoing stays optional, and disagreement is refused.
- **The turn's live figures are their own subscriptions, one per session.** `turn.usage` carries the tokens received this turn, folded from the provider's own usage frames — Claude Code's message-delta and result usage, Codex's token-usage update — and `turn.tasks` carries the turn's task list, folded from the agent's task-list tool calls on Claude Code and from the plan-update stream on Codex, which the daemon enables per session. The reasoning state the working line's state word reads arrives on the turn's own stream rather than as a third subscription. None of the three is derived on the client: a figure the provider did not report is absent rather than estimated.
- **A sidekick's question is one record with one answer.** The held provider request — Claude Code's user-question tool request, Codex's user-input request — becomes one question record the surface renders, carrying the sidekick's header, the question, its options, the several-answers, preview and secret flags, and the page count. It is answered by one call, `question.resolve`, carrying per question the picked labels, the typed text, the secret — which is never stored — or a skip. There is no verb by which a client asks a question: a question exists because a provider stopped its turn to ask one, so the record is the daemon's to write and the client's only move on it is the answer. The user's answering turn is written as an ordinary message record with any secret masked, and a question the provider does not wait on is the message item it already is. A question is an attention entry exactly as an approval is, and the daemon holds the provider's request open until the record is resolved, rebuilding it on reload and on every linked device of the user (§`driver_ask`).
- `ReasoningSurfaceRead`'s policy decision is evaluated against the **daemon-resolved calling principal** carried on the dispatch context, and the request carries no principal member of its own. A body field naming a user would be metadata the authorization never reads ([api-payload-contracts.md §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model)), and the request schema is strict, so one supplied is refused rather than stripped — a stripped member would let a caller believe it had scoped the read. A read dispatched with no resolved principal is **refused**, never answered against a default identity: a placeholder is indistinguishable from a real caller to the policy check, which would turn a fail-closed read into a fail-open one.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- Timeline rows are read projections, not canonical events themselves.
- Reasoning disclosure decisions must be traceable to policy and artifact visibility state.
- Child-run summaries and detail windows must preserve provenance to parent run and producing runtime node.
- Durable timeline reasoning rows must remain reconstructible from canonical summaries and policy markers even when detailed reasoning payloads are unavailable.
- Superseded marking is projection-derived, never stored ad hoc: provenance traces through the Plan-003 supersede projection to the accepted `run.rolled_back` boundary event (its run and carried rewind cutoff) plus the projection-derived source epoch, and survives projection rebuilds and compaction ([Spec-005 §Compacted Event Format](005-session-event-taxonomy-and-audit-log.md#compacted-event-format)).

## Example Flows

- `Example: A session timeline shows a run start, command execution, approval request, diff artifact publication, and completion, all as ordered timeline rows.`
- `Example: A background reviewer run appears as a summarized child-run row that can later be expanded to show findings.`
- `Example: A provider emits detailed reasoning during a run. The timeline stores a durable reasoning summary and policy marker, while the detailed payload remains ephemeral or subject to bounded diagnostic retention.`

## Implementation Notes

- Timeline virtualization or pagination is allowed, but it must not alter canonical ordering.
- Redacted reasoning should still be visible as an event that something was intentionally withheld.
- Live timeline and replay logic should share the same projection schema.

## Pitfalls To Avoid

- Hiding child-run work because it happened in the background
- Flattening every structured event into plain chat text
- Rendering reasoning as if it were always available and safe to show
- Dropping rewound turns from the timeline instead of rendering them superseded — the authoritative log never truncates ([Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior))
- Re-rendering superseded output as current after replay, a projection rebuild, or compaction — or marking a re-executed turn that reuses a superseded ordinal (marks are epoch-scoped)
- Applying that treatment optimistically — truncating, removing, or renumbering rendered rows when an edit-and-resend intervention is _admitted_ or _dispatched_ rather than when its accepted `run.rolled_back` boundary entry appends (2026-08-16, a restatement of the rule above rather than a new obligation: the boundary entry is the only thing that applies the treatment, and a composite whose conversation leg never confirms rewinds nothing at all, so an optimistic edit would drop history the run still holds — [Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) owns the rule, and dimming the affected rows while the intervention is in flight is a permitted affordance)

## Acceptance Criteria

- [ ] A client can see live run, approval, artifact, and child-run activity in the session's live view.
- [ ] Missing live updates can be recovered through replay without rebuilding state from free-form text.
- [ ] Reasoning surfaces clearly distinguish available, unavailable, and policy-redacted cases.
- [ ] Handoff and run-state entries render as distinct timeline rows with appropriate visual treatment.
- [ ] Rolled-back turns render with the distinct superseded treatment identically on live delivery (the `run.rolled_back` boundary entry's already-delivered-rows rule keyed on each row's exposed run position and epoch against the boundary's typed cutoff — delivered to every filtered subscription admitting the run's rows, the live marker identical to replay by construction — plus attribution-ranked late stragglers — pre-marked above the run's effective lineage-minimum cutoff for their epoch, current within the surviving history, a later rollback below an earlier retained prefix superseding the inherited rows), `TimelineRead` windows, and replay recovery; a re-executed turn reusing a superseded ordinal renders current; and a compacted superseded row composes the stub placeholder with the superseded marker.
- [ ] An input-kind driver ask renders an answerable card with the ask's prompt, a free-text answer arm present on **every** such card, and its structured options additionally where the ask carries them; a permission-kind ask renders on the approvals surface and never as this card.
- [ ] An input-ask card carries no clock of its own and never settles itself: it waits until it is answered, its answered and cancelled states each render from the corresponding `driver_ask.*` row, and an answer lands as one ordinary user turn quoting each question with its answer beneath it.
- [ ] The composer offers a compaction control exactly where the bound driver declares `context_compaction`, absent rather than disabled otherwise, and the completed state renders only on the `usage.context_compacted` row — never on the dispatch being accepted. The control's in-progress state clears on the call's own settlement in every arm — a settled failure leaves no control waiting — while a boundary row arriving after that settlement still moves the meter. The only automatic compaction is the provider's own at the bound the meter's notch shows, and no other threshold, timer or heuristic initiates one.
- [ ] Every timeline read answers within one transport message body: an over-large result comes back as a page carrying an explicit more-to-come flag and the cursor that continues it, never as a dropped connection and never as a truncation the caller cannot detect. A returned page's entries do not move backwards in sequence, and a child-run expansion's run-scoped entries all belong to the run the response names.
