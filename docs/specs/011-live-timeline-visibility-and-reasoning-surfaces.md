## Purpose

Define the user-facing contract for live timeline visibility, background work surfacing, and reasoning disclosure.

## Scope

This spec covers the canonical timeline read model, child-run visibility, reasoning surfaces, and replay-aware live updates.

## Non-Goals

- Notification rules
- Artifact storage internals
- Provider-specific reasoning formats

## Required Behavior

- The system must expose one live timeline per session, built from canonical events.
- Timeline rows must cover at least messages, run state changes, tool activity, approval events, interventions, artifacts, and child-run activity.
- Background runs and child runs must be visible in the primary session experience, even when details are lazy-loaded.
- Reasoning surfaces must be normalized, and no policy check withholds reasoning: every reasoning text the provider supplies is shown whole. Reasoning the provider kept back itself (Claude Code's `redacted_thinking`, Codex's encrypted reasoning) or never kept must still produce a visible reason surface.
- **Every reasoning text the provider supplies is shown and kept whole.** Thinking reaches the flow on every session, and no switch or setting controls it, because each provider already sends the fullest reasoning it gives: on Claude Code the driver sends `set_max_thinking_tokens {thinking_display: "summarized"}`, with no budget key, at every start and after every model change, because without it a headless session's thinking arrives with no text; on Codex every conversation sets `model_reasoning_summary = "auto"`, which asks for the most detailed summary the model supports and which a model without one drops silently. Whether the model thinks, and how much, stays with the model and the session's reasoning effort, and a model that produces no reasoning shows no reasoning row. Neither provider's API returns a model's own full reasoning, so what each supplies is the record: it is shown whole and kept whole in the session's history, as the reasoning events of its turn, for as long as the session's events are kept, never trimmed or rewritten. A reasoning text longer than one entry holds (16,384 characters) is kept as consecutive entries in order and read back as one; nothing is cut. There is no per-session reasoning control, no `Explain as you go` switch, which would be the model narrating in its reply rather than its reasoning, and no `detailed` summary switch, which reads no richer than `auto`. `Generate`, the one-turn utility that writes a commit or pull-request text, keeps thinking off.
- Live delivery must support replay catch-up so clients can recover missing timeline state.
- **The daemon feeds the timeline in batched frames and never waits on a screen.** A session's events are coalesced into frames whose size and cadence [Spec-006 §Required Behavior](006-local-ipc-and-daemon-control.md#required-behavior) sets, the window opening on the first event so nothing waits longer than it; every frame carries changes rather than the whole timeline, and every change carries its cursor. A client that falls behind is dropped for rather than waited on: the very next frame that fits carries the gap flag, and that client repairs from the daemon's record by cursor, re-opening the session's own stream (`session.subscribe`) with `afterCursor` at the last position it kept — one stream per session, never a second stream of the same history — and taking a snapshot read in place of a fill past a gap of 1,024 events, so a timeline on screen is never silently short. A client that fell behind and has caught up on its queue is sent one frame with no changes, carrying the drop mark and the newest cursor, so a session that goes quiet right after a drop still tells that client it is behind. The frame itself is [Spec-006 §Wire Format](006-local-ipc-and-daemon-control.md#wire-format)'s. On the page a row grows only at its tail: settled text is never re-rendered and only the growing row is re-measured, and the list keeps its retained window, pages back against a cursor, and takes the list library's own end anchor and follow-on-append, turning the browser's own scroll anchoring off while it follows.
- **Superseded-turn rendering.** Rolled-back (superseded) turns remain in the timeline and MUST render distinctly from current rows — an explicit superseded treatment, never dropped and never re-rendered as current ([Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) owns the supersede semantics; marks are epoch-scoped, so a re-executed turn reusing a superseded ordinal renders current). The marking reaches the surface on two legs with one outcome: `TimelineRead` and replay rows carry a projection-computed `superseded` marker (sourced from the Plan-003 supersede projection's exported `supersededTurns(runId)` read — the CP-003-13 seam), and on the live stream the accepted `run.rolled_back` boundary entry (§Timeline Entry Types) — delivered to every filtered subscription whose filter admits any of the affected run's rows (projection-resolved visibility) — instructs the client to apply the same treatment to that run's **already-delivered** rows whose carried run position exceeds the carried rewind cutoff (run-scoped rows expose their run identity, projection-resolved originating run position, and execution epoch as typed row fields required together — a partial attribution row fails schema validation, never a silently incomparable cached row; the session event sequence is never a run position, and the boundary entry is a typed arm of the discriminated row union the read and subscribe surfaces return: its payload is validated into the `run.rolled_back` event shape at projection, so the cutoff is never read through an untyped cast) — an idempotent rule across multi-rollback sequences (a row already superseded re-marks as a no-op), with each newly-marked row's marker being just the boundary's cutoff against the row's own exposed identity — identical to the replay-computed marker by construction, a previously-current row's first remover being that boundary, so a subscriber that joined from a bounded window after earlier rollbacks marks its cached rows without recovering epochs from reused ordinals whose delivery-order scoping needs no epoch tag, because every row delivered **after** the boundary arrives with its marker already projection-computed: a late pre-rollback straggler appends pre-marked exactly when its stamped attribution ranks it above the run's effective cutoff for its epoch — the minimum rewind cutoff among accepted rollbacks at its epoch or later in the run's lineage, since a later rollback that rewinds below an earlier retained prefix supersedes the inherited rows — and current when it ranks into the run's surviving history ([Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior); the CP-003-12 `sourcePosition` companion exists precisely for this ranking) — and a new-epoch row appends unmarked — so live and replay views converge on identical marking.
- **The timeline is one continuous flow.** No card, no panel and no framed container stands around any turn. Role is carried by asymmetry alone: the user's words render in a tinted, right-aligned bubble sized to its own text — no width cap, so a short message sits well inside the column and a long one grows to the column's edge — and the agent's words render as flat prose with no bubble. There is no left-and-right alternation, no avatar, no name label, no role eyebrow, no fixed clock column, no per-turn border, no scrubber, and no seen-or-read mark of any kind, there being one person here and nobody for such a mark to tell ([ADR-034](../decisions/034-transcript-is-one-flow.md) holds the reasons). Every row sits in one centered column whose width every row in the flow reads, and one gap — derived from the reading line rather than chosen, so it moves with the text size — sets the distance between any two consecutive rows whatever those rows are, no row kind carrying a margin of its own. The flow offers exactly two position aids: a rail whose ticks lead to the moments that need a person, and one control that returns the reader to the live tail.
- **A reply's time is its own foot, not a row.** The foot carries the reply's time stamp and a copy action, is drawn the moment the reply has something to read so a time never stands over an empty answer, and stays for the rest of the turn. A user turn's actions — copy, fork, edit, undo to here — and its time are revealed on hover or on focus inside the bubble. Where the day changes between two rows, one quiet line between them reads that date in the machine's own clock format; it is a label and leads nowhere, so it is not a way of moving about the flow. There is no unread line and no typing indicator.
- **Every state-changing act appends a system message.** A goal set, updated, completed or cleared, context compacted, worktree created, moved and removed, committed, pushed, pulled, pull request opened, review posted, an interrupt, a restore, a plan accepted or handed to a fresh session, and fork provenance. One system-message kind draws every one-line row the app writes, and a system message names the act and never the actor. A product command that does work of its own appends one; a product command that presses a control appends whatever that control's own press appends, which for most controls is nothing.
- **A provider notice lands as one system message** — the notice in words on the row, with its reason and what to do about it on faint lines beneath — drawn in the color reserved for "a person is needed" only where one is, and in the flow's ordinary quiet otherwise. Codex's warnings and deprecations are the exception, as in Codex's own app: they never enter the flow and are counted on the working line.
- **A provider build the app cannot work with is a banner under the header, never a row**, because it is true of the whole session rather than of a moment in it: `<Provider> <version> is too old · this app needs <version> or newer · Open Providers ×`. A build that changed under a running session takes the same banner, `<Provider> updated · <old version> → <new version> · Restart the session ×`, and the running turn is untouched until the session is restarted. Both name both builds, and each carries its own dismiss.
- **The window says once that it is catching up.** While the window repairs a hole in what it received, or a read it depends on has failed, one line directly under the session header, where the header's banners sit, says so, and nothing else on the screen repeats it: no second notice for missing entries and no note of how the repair is made. It reads `Catching up…` while the repair runs; it appears only once the repair has run 0.4 s and, once shown, stays at least 0.4 s so it never flickers, and it goes when the missing entries have arrived. A repair read that fails turns it to `Couldn't catch up · Try again`; `Try again` reads again, and so does the window's own refresh on focus and on reconnect, since the screen never polls. No technical cause is shown on screen; the cause goes to the window's diagnostic capture.
- **Grouping comes from the daemon's own run boundaries** in a session's flow, while a child run's view groups consecutive tool, diff and output rows at render time. A notification landing between the calls of a run joins that run rather than ending it and is counted in the group's header; one with no call before it in the run stands on its own. A message the wire delivered in two pieces is rejoined where grouping is decided, before anything is drawn, so the timeline shows one message with one time and one copy.
- **Success is shown by absence; only failure is marked.** A call that succeeded carries no tick, no "done" and no color of its own. Failure is derived from the run's own durable record, so a restart replays the same answer and a run that failed still reads failed the next morning: there is no stored failure flag and nothing for anyone to clear. A failed call carries one line saying why — the reason in plain words, with the code the tool returned beside it, rendered as words wherever words exist for it — and a failed command's reason line carries its exit code and the last lines the command printed with color codes removed and kept to one line, the rest of the output staying in the call's body. On Codex, a command the sandbox refuses before Codex sends its command item still gets its row, drawn from the daemon's pre-tool and post-tool hooks paired by call id: a call the hooks report with no item by the end of the turn reads `Blocked by the sandbox`, with the command's last output line as its reason line and no exit code, because the hook carries none; a command that has its item keeps the item's exit code. At the `Reviewed` level, an action the provider's own reviewer blocks keeps its row too: a failed row whose reason line reads `Blocked · <the reviewer's reason>` in the provider's own words — Claude Code's denial reason, such as `[Data Exfiltration]`, or Codex's review rationale — with one button beside it, `Allow once`. Pressing it tells the agent it may try that one action again; the row then reads `Allowed once` and the button goes, the failed mark staying because the blocked call never ran and `Allowed once` drawn in the secondary text color rather than the failure color, and the agent decides whether to retry, so nothing runs by itself. A block the provider does not let a person overrule has no button: Claude Code's block without a classifier verdict, and Codex's review that timed out. The button stays until it is pressed or the session ends, holds across a restart, and a press on one screen settles it on every screen ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)). A call the **user declined** is not marked as a failure and never in the color that means a person is needed: it reads as a failed row whose reason says `Declined`. A run group's header carries the same mark and a failure count whenever any call in it failed, and names the call now running while one runs, in its folded and its open state alike; a declined call is not counted there either, nor a block by the provider's own reviewer.
- **A reasoning surface renders as a three-line tail.** It shows the last three lines and clips the head — a tail, never an ellipsis — with a count at its head saying how many lines the tail hides, and it renders the reasoning's own emphasis, monospace and links as real runs, the links not being pressable. One press opens the whole reasoning in place and a second folds it back to the tail; while the thought is still arriving the opened text keeps growing and nothing is shown twice. Where the provider kept no reasoning, the row says so rather than opening on nothing — that is the visible unavailability reason this spec requires, in its ordinary form.
- **Code is colored once, in the daemon, and every surface paints the spans it is handed.** Code in the timeline — a code block in a reply, a diff under a tool row, a file opened from a row — carries the color spans the daemon computed for that file and cached against what the file holds, painted as classes that read the theme's own code tokens rather than as colors written onto elements, so a theme or scheme change repaints the same spans and nothing is ever colored twice; a language nobody recognizes stays plain with no round trip ([ADR-035](../decisions/035-one-syntax-colorer-in-the-daemon.md)). A block still being written keeps the colors it already has — the lines that arrived stay colored and only the line still arriving is plain until it lands — and a block redrawn after a theme change starts from the colors it had rather than flashing back to plain. Command output keeps the color the program itself wrote, mapped into the one terminal color vocabulary this product carries so a line reads the same in a tool row as in a shell, with bold, italic and underline kept, a code naming a color outside that vocabulary mapped to its nearest entry rather than dropped, background colors not drawn — a washed line is the diff's own mark — and cursor and screen-control sequences removed.
- **A tool row names the provider's own verb for the tool**, never a name this product holds in a list of its own, so a tool the provider added yesterday reads under its own name today. The one mapped verb is a notebook cell edit, drawn as an edit on the notebook's path with the cell it touched as a chip beside the path and that cell's own changed lines under the row, because the provider's word there names the file kind rather than the act. A command row reads the command the agent wrote with the provider's shell wrapper stripped — in a truncated row too — while the whole invocation stays in the call's body. A tool-server call reads the label that tool registers for a person to read, never the server's dotted name and never its arguments bracketed after it; the call's own arguments sit in the body under the row, each named and laid out by what it is. A skill's answer arrives as the agent's own reply and carries no second author — no attribution line over it, no second glyph, and nothing naming the skill as a speaker — because a skill is text the agent read and the agent's own rows are the record of what it did with it.
- **A Claude Code advisor call is an ordinary tool row**: the verb `advisor` and, in the body, the advisor's model by its display name (`Fable 5.1`), live while the advisor works, with its duration. Its output row is Claude Code's own line, `└ Advisor has reviewed the conversation and will apply the feedback`. When the advice arrives readable (`advisor_result`, from an older advisor), the row takes a chevron and the advice sits under it, folded at rest, the one tool row folded at rest; a sealed result (`advisor_redacted_result`, from every advisor that pairs with Opus 5 and 5.5, Sonnet 5.5, Fable and Mythos) has nothing under it and takes no chevron. A refusal's output row reads `Advisor declined to advise on this request`, with the provider's explanation folded under it when one is sent; an error reads `Advisor unavailable · <the reason in words>`, never the wire's code. The advisor's spend is priced at its own model and counted in the account's row in Cost ([Spec-014 §Session Cost Receipt](014-multi-agent-orchestration.md#session-cost-receipt)). The advisor's thinking is never sent on any model, so no row shows it, and the agent is not asked to repeat the advice.
- **A path a call names is a link to the file it names**, on every row whose verb names a file, in a session's flow and in a child's view alike; a command's row carries none. The path's whole text stays in the row's hover title, which is how a truncated one is read in full, and a line, or a line and column, the call named is carried on the path. Opening it opens the file where that session reads files ([Spec-012 §Required Behavior](./012-artifacts-files-and-attachments.md#required-behavior)), scrolled to the line the call named.
- **Nothing folds itself.** Every run group and every foldable call is open at rest, live or long settled, except an advisor call's readable advice, which is folded at rest; a run never closes when it ends and a call never closes when its output lands, and a fold is only ever where the user put it. A group's header is its own fold control, sits in the tab order, and reports its open state to assistive technology; a call with a body under it folds on its own row while its one summary line stays; and a call whose whole output is that summary line, or that has no output at all, offers no fold, no press and no tab stop, because a control that opens something is drawn only where there is something to open. Whether a call is folded, and whatever body it has already fetched, belong to the call rather than to the element drawn for it: a row scrolled out of the drawn window and back is in the state the user left it in and does not fetch its body a second time. The reasoning tail is the same three lines whether the thought is running or settled. One pair of commands folds and unfolds every run group of the session at once and sets exactly the state a header press sets, so a group's control can never disagree with the group.
- **A large body arrives only when its control is pressed**, never because the reader scrolled past it: the control names the size before the press, says so while the read is out, and offers the press again when the read fails. The same holds for a patch the daemon did not send with the row — such a call looks exactly like one whose patch traveled, and one read covers every missing file in that call.
- **No row re-runs the call it records.** A tool runs when the agent calls it; running one again is asked of the agent in the message box, and the agent's own row is the record of what happened.
- **The working line carries the turn's own live data.** It is drawn only while it has something to say — the activity, the state after a pause or an interrupt, the connection state, or a Codex warning count — and is absent on an idle session that has none of these and while a plan waits for its verdict. Its data is: the **action words**, which say what the agent is doing right now (`Running pnpm test`, `Editing <path>`, `Writing the summary`, `Revising the plan`, `Waiting for approval`, `Waiting for your answer`, `Compacting…`, `Retrying…`, and on Codex `Giving this request a little extra thought` while Codex holds the turn for a safety check, the clock still running, until Codex clears the hold or the reply starts), hold the last step's words while reasoning streams between steps, read `Thinking` before a turn's first step has landed, and stay after a pause or an interrupt; while any command is running those words are pressable and open, in place, the list of what is running — one entry per command in the order they started, each carrying the command's name, its own live clock and its own stop, a press on a name taking the reader to that command's row, and a live tail of that command's output beneath it — a window onto those rows and never a second copy of their output, which goes when the last command ends, the line itself never counting commands; the turn's **elapsed clock**; the **token figure**, the tokens received this turn, marked with a downward arrow: the provider's own output count for each model round, summed across the turn and stepped once per round rather than per word — Claude Code's final message delta of the round, Codex's `last` output figure on its token-usage update — with reasoning already inside it and never added again, never Claude Code's result `iterations` figure, which holds only the last round, and never a difference of Codex's running totals; it starts at zero when the turn starts, holding across a pause, and muting with the clock after a stop; the **state word**, one reading at a time and absent together with its separator when there is none — `Thinking` while reasoning streams between steps, `Pausing` then `Paused`, and `Interrupted` followed by what is still outstanding — `· N sidekicks still running`, `· a command still running`, or `· waiting` — and, while a switch waits, which one it is switching to — `switching to Codex` or `switching to Claude` while a provider switch waits for the end of the run — a switch that lands in place, an account switch among them, drawing no waiting words; the **tasks word**, `N of M tasks` while the turn has a task list; the **count of questions** the agent did not wait for while any are unanswered; and the **warnings word**, `⚠ 1 warning` or `⚠ N warnings`, while the session's Codex has reported one or more warnings or deprecations, drawn also while no turn runs. Pressing the warnings word opens a small list above the line under the word, the way the action words open the running commands: one row per warning, newest last, Codex's own words with its source (`Warning` or `Deprecation`) and the time, a deprecation's details under its summary, the same words twice making one row; Escape or a press outside closes it. The count is the session's, survives a reload and is never cleared by reading. Codex's settings warning is the ignored-settings banner, its reviewer's warning is a `Review warning` row, and the warning it sends right after a model switch in the same turn is the sentence on that switch's `Model switched` row, so none of them is counted and the switch's words show once; a Claude Code session never carries the word. While Codex holds a turn for a safety check and names a faster model, the line also carries `Retry with a faster model` after the warnings word, with Codex's own sentence `If you'd rather not wait, retry with a faster model. It may be less capable of handling complex requests.` as its hover title; with no faster model named the word is absent. Pressing it asks first: the line's words give way to `Stop and retry on <model>? · Stop and retry · Keep waiting`, the model named as the catalog writes it, and `Keep waiting` or Escape puts the line back; the question and the word go by themselves when the reply starts or Codex clears the check. `Stop and retry` sends the intervention `run.intervene` {type: `faster_model_retry`, targetRunId, expectedRunVersion, clientIdempotencyKey, expectedTurnId, model}: the daemon interrupts the turn, forks the conversation to just before it and sends the same message again on the faster model in the same session. The message is not drawn a second time, rows the stopped attempt already drew stay, and the model change draws no row. A retry that fails puts the message back in the composer with Codex's words, `Failed to retry with a faster model: <reason>`. From the press of send until the turn starts the action words read `Sending…` with no clock and no token figure beside them. No live token figure stands anywhere else in the product and no message carries one. A child run's line carries the same data without the token figure, because a child's own head already carries its tokens and its spend, and its state word additionally reads `Done` or `Stopped` once the child is over. No reading ever moves the clock backwards.
- **The task list is the provider's own list**, read from the agent's task-list tool calls on Claude Code and from the plan-update stream on Codex, which the daemon enables for every session because that provider leaves it off. It is shown in the agent's own order with each item's state — done, in progress, not started — and it is never merged with the list of running commands, never a row in the timeline and never a section in an inspector; opening either list closes the other, so one is open at a time. The tasks word leaves after an interrupt and returns with the next turn's list.
- **A plan renders as one full-width document in the flow**, at the timeline's own content width: an accent rail down its left and every heading, numbered step, nested list, code block and table as the agent wrote them, nothing folded and nothing summarized, never inside a bubble and never inside a card. Its footer says that nothing was changed, and names the plan file where the provider wrote one. The reply's own foot with its copy follows it as after any reply, and the working line is hidden while the plan waits. Lines selected inside a plan can be quoted into the draft through one control that rises at the selection's end and goes when the selection is cleared; a plan carries no comments and nothing is anchored to it. The verdict itself is an approval-pipeline decision ([Spec-010 §Interfaces And Contracts](./010-approvals-permissions-and-trust-boundaries.md#interfaces-and-contracts)), and a revised plan lands as a second full-width document.

## Default Behavior

- Timeline rows default to chronological order from oldest to newest within the current view.
- **Nothing is collapsed at rest.** Every run group and every foldable call but an advisor call's readable advice opens as it arrives and stays as the user left it (§Required Behavior). What bounds a large payload is a **cut**, not a fold: a long diff, a long command output and a long pasted message are each drawn to a height derived from the visible flow and the current text size, faded at the cut, with the rest one press away and the control that opens it naming what it will bring.
- Child-run activity defaults to summarized rows with explicit expansion for detailed inspection.
- Reasoning the provider supplies renders as the reasoning tail (§Required Behavior), tied to the run and the turn it belongs to; where the provider kept it back itself, a placeholder renders in its place.
- Reasoning has one retention: the reasoning events of its turn, kept whole for as long as the session's events are kept, and read back whole by a reload and by a copy of the row.
- **Streaming reveals prose word by word at the pace the words arrive, with no lead-in.** A reply's first word is on screen the moment the runtime has it. The pace is measured from the wire itself and counted in words, a word being one word-like segment of the platform's word segmenter in the reply's language with the spaces and punctuation after it: each arrival interval is clamped at 250 ms, or 1,000 ms when one update carries more than ten words, so one pause does not crater the estimate, and the rate is held between 40 and 2,000 words a second. The reveal runs in two gears with hysteresis under the frame budget, counted in characters: the normal gear reveals at the pace the words arrive, and a catch-up gear takes over once the backlog reaches eight lines, as laid out at the current width, or 120 ms of staleness and gives way again only after 250 ms of calm, so the text never drifts behind the wire and never dumps a backlog at once. It keeps draining after the turn closes, at no less than 80 words a second, so nothing is left unshown. It breaks on word boundaries, so a long word arrives whole, and arriving text changes only its opacity, so a line filling in never reflows the lines above it and nothing that has settled shifts. Coming back to a session draws everything that arrived while the user was away as settled text at full strength with no reveal; only words arriving from that moment on animate. There is one rendering of a reply and no setting that turns streaming off — the reveal engine reads the machine's own reduced-motion setting rather than leaving it to the stylesheet, so on a machine set to reduced motion the text lands as it arrives with no reveal animation at all, which is the one case such a setting would have served.
- **Markdown that has only half arrived is drawn as what it is becoming**: a code fence is framed from its first line, a half-typed link is held as its text until its target lands, a half-typed picture or footnote mark draws nothing, and emphasis whose closer has not arrived is mended for display rather than showing its marks. The text underneath stays exactly what arrived, so a copy and a search still read the truth. A reply still arriving is split at its last settled block, so the blocks before it are never re-read and a selection crossing the split survives it.
- **One ticker advances every live figure on the screen**, beating once a second, which is the finest figure any of them shows; there is no per-row interval. A live elapsed figure and a finished duration share one cell in one color, and a figure that finishes freezes in place rather than being replaced. Live figures under a minute read in whole seconds and at or above a minute as minutes and seconds. The figure is never tinted — not while waiting, not while running — and a session row's status dot never blinks, a live elapsed figure being what says the agent is working. Every elapsed reading lives in the model and is never read back out of the page, so a re-render never resets a clock.
- **The flow follows its own tail only while the reader is near it.** A scroll away from the bottom releases the follow at once, however small the scroll, and it re-engages when the reader returns to within a couple of line heights of the bottom or presses the control that jumps to the live tail — the one control that returns the reader there, drawn only while the follow is released and nothing drawn over the flow. A selection being dragged inside the flow suspends the follow for as long as the button is held, so a reply arriving underneath never pulls the words out from under the pointer. While the follow is on, the flow glides after arriving text rather than jumping; a layout correction is not arriving text and is placed at once — a picture that typesets late, a row that remeasures, a reflow at a new width — as is everything on a machine set to reduced motion.
- **Motion runs only where something changes under the reader's eye** — a fold opening, a row arriving, the follow gliding. It is armed by the change itself rather than by scrolling past it, and a change in a region that is out of view is placed at once instead; reduced motion removes every animation and transition without exception.
- **History loads in stretches, never all at once.** Only the rows near the window are drawn, with a band above and below kept ready so a fast scroll never shows blank space where rows have not drawn yet. At the top of what is loaded, one line offers the stretch before it, and a wheel, an arrow key or an upward drag made at the very top asks for it too; older history also comes in on its own, the next stretch asked for once the reader is within about two screen heights of the top of what is loaded, one stretch per gesture so a fling cannot pull in a whole day. A session opens with the screen the reader lands on and about two screen heights above it already loaded. A stretch is about three screen heights of rows, read from the window's own height rather than a count of rows, and one read is also bounded by its size, so a run of very large tool outputs cannot stall it. History reaches back to the session's first message, the part before any compaction included, read from the daemon's own record, which keeps every event, and never from a provider's files; the window holds a bounded share of it, letting rows far from the reading position go and reading them again when the reader returns. A stretch that fails to load leaves one line at the top of the loaded history, `Couldn't load earlier messages · Try again`, and `Try again` reads it again. The build measures this against a budget: at a normal reading pace the next stretch lands before the reader reaches the top, and a session paints first no later than it would without the look-ahead. Newer rows page in as the reader nears the bottom of a window opened in the middle of a long session, so a reader who landed on a search hit reads forward rather than reloading. In every case the reading position stays where it was.
- **Rows leave memory in cuts, and a cut never takes a row someone is reading.** Old rows are released in cuts that never take a row that is on screen and never take the row under the reader — a cut that would is refused — and never take the rows an open child-run view is showing, or its parent's. A session the user has opened before mounts at the heights its rows really had, so the reading place lands where it belongs instead of drifting as each row measures itself, a row with no remembered height taking an estimate for its kind until it measures.
- **Every way of reaching one row takes the same path** — a tick on the rail, a search match, a review note, a notification: the row is loaded if it is not on the page, the run group holding it is opened first, the flow lands on it, and it is marked briefly by opacity alone so the mark survives reduced motion. A row that is no longer there says so in one line instead of moving the page.
- **One selection runs across every kind of row** — prose, a message, a list, a table cell, a tool row, a system message — and survives both the rows around it leaving the drawn window and the reply still arriving underneath it: text that is still streaming only ever grows, and no block a selection touches is redrawn while it touches it. A chunk of arriving output adds its new lines and touches nothing already drawn.

## Fallback Behavior

- If live delivery drops for a client, the gap flag on the next frame says so, and that client must re-open `session.subscribe` after the last position it kept rather than wait for the loss to reveal itself.
- If the provider kept reasoning back itself, or a tool payload cannot be read, the timeline must show a placeholder in its place with the reason.
- If a child-run detail fetch fails, the summary row remains visible and marked incomplete rather than disappearing. The mark is **explicit and required**, never inferred from a low event count: it names its **cause**, `detail_fetch_failed` (this daemon's own expansion read failed), together with the time that cause was observed, so a consumer can tell a read worth retrying from a complete summary. On the incomplete arm the summary's event count is a **lower bound** — what the daemon holds, not the child run's total.
- If the provider kept no reasoning for a stretch of thinking, the reasoning row says so rather than opening on nothing. Reasoning the provider did supply is never compacted away, trimmed or withheld, and the placeholder stands only where the provider kept reasoning back itself.
- If a dispatch is refused, the timeline appends one row naming the cause. A refusal is never swallowed and never leaves the flow silent.
- If a provider imposes a limit mid-turn, the working line carries it and the flow carries one system message for it, never a banner and never a modal: on Claude Code the action words read `Retrying…` in place of the verb while the retries run, then `<Provider> did not answer · Try again` if they give out; on Codex the line reads `Limit reached · resets at <time> · Try again`.
- If a turn is interrupted while a command it started is still running, the working line's state word says so — `Interrupted · a command still running` — until the daemon has ended the process, and that command's row settles as stopped then and never before. A pause reads `Pausing · a command still running` and waits for it the same way.
- If a call's patch or a call's whole output was not delivered with the row, the row looks exactly like one whose payload traveled and its place says it is loading while the read is out; a read that failed says so where the content would sit and offers the press again, one read covering every missing file of that call.
- If a picture cannot be shown, its place is still reserved at the size the daemon holds for that file and a named state is drawn where the picture would be — loading, unavailable, or refused — rather than a blank. A block that cannot be drawn shows its own source with one line above it saying it could not be drawn and why.

## Timeline Entry Types

> These timeline entry types are projection-layer constructs derived from canonical session events (see [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)). They do not create new event types.

### Flow Row Kinds

The flow renders these kinds, folded from a list of events. An event outside that list draws nothing on screen — no row and no notice — and the app may record it in its diagnostics log. Each kind is a row in the one column of §Required Behavior, one gap apart from its neighbors.

- **System message** — the one kind that draws every one-line row the app writes: a hairline rule either side, the act's own name, its text capped at about half the row, except a `Review warning` or a `Model switched`, whose words from the provider wrap across the row so the sentence is read whole, and a tabular time stamp. A goal shows here and nowhere else — no goal card, no header item, no sidebar section and no session label — each change one system message drawn from the goal's events: `Goal set` when a goal is set with none active, `Goal updated` when a later `/goal` replaces it, `Goal completed` when its status becomes complete, and `Goal cleared`. A goal that stops unmet carries its status and the provider's reason on its row — Codex's blocked or limit statuses, Claude Code's `Goal impossible` — and two more rows are Claude Code's while its goal stays active, stored as the session's notice kinds: `Goal not met · still active` when the turn ended at Claude Code's own cap on unmet checks in a row, and `Goal check did not finish · still active` when a check ran past Claude Code's fixed 30-second limit. A tool process the memory cap on this machine stops appends one, naming the command and the figure it was stopped at, so a process that went is read as a limit doing its work rather than as a failure with no cause. Claude Code's refill breaker, which ends a turn whose own tool output refilled the context to the compaction point three times in a row, each within three model calls of the compaction before it, appends one where the turn stopped, marked in red as the failure it is, `Stopped · the context refilled right after each compaction`, with nothing to press and no `Try again`, because the same turn would refill it the same way; the next message runs normally. A compaction the provider attempts and fails appends none: the working line returns to its verb and the context meter keeps its figure, because the provider tries again at the next turn. When Codex's own reviewer, at the `Reviewed` level, warns about something or requires a closer review in a Codex session, the flow gains one system message with no control, showing what Codex's own app shows: `Review warning · <Codex's words>` carries Codex's warning exactly as Codex sent it — `Review warning · Automatic approval review rejected too many approval requests for this turn (3 consecutive, 3 in the last 50 reviews); interrupting the turn.` — and `Review required · This request requires additional safety checks, some tool calls might take extra time` marks a required review, which carries no words, with the sentence Codex's own app writes for it. A warning that reports an approval draws nothing, as in Codex's own app, and a warning about an action the reviewer blocked draws nothing of its own, because its words are on that action's row (§Required Behavior). Each row is drawn from one `moderation.review_flagged` event, which is on the list the flow folds and carries which of the two it is and the words the row shows. Codex's moderation metadata on a turn, a display hint with no words that Codex's own app does not draw, draws nothing and stays in the daemon's log. Codex's `warning` and `deprecationNotice` draw no row either: each is recorded as a `session.notice` of kind `provider_warning` and counted on the working line ([Spec-005 §Session Lifecycle](005-session-event-taxonomy-and-audit-log.md#session-lifecycle-session_lifecycle)). Nor does Codex's hold of a turn for a safety check, `model/safetyBuffering/updated`: it reaches the screen only as the live event `run.safety_buffering_updated` on `run.subscribeState`, which puts Codex's own sentence in the working line's action words and is not kept ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)). A Claude Code session draws none of these rows, because Claude Code sends no such signal. When the provider's safety check, an unavailable or blocked model, or a credits choice moves a turn onto another model and the turn goes on, one system message lands, `Model switched · <the provider's own sentence>`, or `Model switched · <from> to <to>` when the provider sends no sentence; under it a reason line reads the provider's explanation verbatim when it sends one, and otherwise the cause in words — `Safety check · cybersecurity`, `Safety check · biology`, `Safety check`, `Model unavailable`, `Model blocked` or `Out of credits` — never the wire's code, a Codex reroute for high-risk cyber activity reading `Safety check · cybersecurity`. The provider's safety category picks the words: `cyber` reads `Safety check · cybersecurity`, `bio` reads `Safety check · biology`, and any other category or none reads `Safety check`. The composer's model chip reads the model really running: a switch that holds for one turn leaves it on the chosen model, a switch that holds for the rest of the session moves it and the chosen model stands for the next session, and a switch that moved only a subagent's, a side question's or a background fork's response lands its message where that response is drawn and leaves the chip where it is. Codex's reroute is per request, so it leaves the chip too. Nothing is added to the notifications, because nothing waits on the person. The row is drawn from one `usage.model_rerouted` event, its `scope` saying which of the three the switch is ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). When the provider's safety check refuses a turn and no other model can take it, the turn ends with one failed row, `Refused · <the provider's own sentence>`, or `Refused · <the refusing model>` when the provider sends no sentence, carrying the same reason line, with nothing to press: sending the same words again meets the same check, and editing and resending the refused message is the move. The row is drawn from the run's `run.failed` with `failureCategory: 'refused'` ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)). When Claude Code's safety check refuses a turn and names a fallback model, Claude Code asks, as its own app does, whether to retry on that model or edit the message, and the same `Refused · <sentence>` row, under the same reason line, carries two choices, `Edit message` (ghost) then `Retry on <fallback model>` (primary). The turn waits on the person: the session is a `Waiting on you` entry in the bell ([Spec-017 §Required Behavior](017-notifications-and-attention-model.md#required-behavior)), the row is rebuilt on reload and on every linked device, and the first answer settles it everywhere. `Retry on <fallback model>` answers `retry_fallback`, and the turn goes on on that model, its switch drawn as the `Model switched` message above from what Claude Code sends. `Edit message` answers `edit_prompt`: the turn ends refused and the message returns to the composer to be reworded, as a failed faster-model retry returns it. `Interrupt`, or a message sent while the choice waits, answers `cancelled`, Claude Code's own default, and the row stays `Refused` with no choices. The messages Claude Code names as already streamed for the refused answer leave the flow when the choice is answered, whichever it is, never when it arrives. The choices are drawn from `run.refusal_choice_requested`, answered through `run.refusalChoiceResolve` and settled by `run.refusal_choice_resolved` ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)). After `edit_prompt` or `cancelled` the run ends `run.failed` with `failureCategory: 'refused'`, and the settled row keeps the sentence the choice carried: it takes its sentence from `run.refusal_choice_requested`, and the refusal that follows, whose own sentence is empty, does not replace it. Codex has no such choice.
- **User turn** — the tinted, right-aligned bubble with its own revealed actions. A message past twelve of its own lines is clipped to twelve, with a control at its foot reading the message's real line count; one press opens the whole message, takes the control with it, and holds the bubble's place on the screen so the rows above do not move. A message inside twelve lines is drawn whole and carries no control. The edit action puts the words into the draft and marks the row as being edited, its bubble saying how many turns after it would be superseded; a resend marks that row and every row after it superseded and draws a line under the bubble saying it was re-asked below.
- **Agent prose** — flat prose wrapping at the column's edge, followed by the reply's own foot.
- **Reasoning tail** — a glyph, a verb column as wide as the longest verb it must hold, and the three-line tail filled from the bottom.
- **Run group** — a header carrying a per-verb count over a rail that every call in the group hangs off, indented by the group's own step. The header is the group's fold control. A long run draws only a window of its calls: a line stands at each edge of that window saying how many calls lie earlier and how many later, each opening the next stretch, and calls landing above what is on screen leave the reading position where it was.
- **Tool row** — a glyph, the same verb column as the reasoning tail, a body carrying the target with its chips and its added-and-deleted counts, a status slot, and a right-aligned duration. A run of reads standing next to each other in one run draws as one read row listing every file, each a link, a file read twice appearing once; the row's single status mark follows the newest member still running and then the newest that failed, while the group's header still counts every read.
- **Output row** — indented to the body column, with a prefix and a summary, a good result in the success color. A call that both changed files and printed output draws both — its diff blocks on the run's rail and its output row beneath them, each visible at once, with nothing switching between them.
- **Running command** — the tool row with its duration live and its output growing line by line as it arrives; the row keeps its place while later rows land below it. Its own stop control sits at the row's right, in the row's own text rather than as an icon, and on a provider that waits on a command the row alone also carries a control that moves the command to the background — absent, not disabled, on a provider without that ability. Stopping leaves a stopped line in the output, freezes the timer, and appends one system message carrying the short note the daemon sent the agent, never a bare failure. Output is shown in a tail window a quarter of the visible flow high at the current text size, with the rest one press away and a copy lifting the whole output rather than the lines on screen; where the provider says the command is waiting for typed input the row grows one input line under its output, what is typed going to the command through the provider's own write path and the output carrying on beneath it. A command that outlives the turn stays a live row across turns. While a call's output is not there yet its body says so in its own words, and a read of the output that failed says that instead. Nothing here chooses foreground or background for a command, forces a wait, sets a time limit of its own, or shows a command's processor or memory use.
- **Diff block** — one block per file a call changed, each with its own counts and its own door into the review surface, and no wrapper around the set; two files of the same name each keep their own block. Added and removed lines are washed by background alone with the sign in its own one-character cell, a quiet gutter carries the new file's line numbers, a removed line keeps the number it had, a paired removal and addition mark their differing words with a stronger wash, and skipped lines of the file stand as a quiet separator that opens nothing in the flow. A long line wraps under the code rather than under the sign, so no diff scrolls sideways. The block draws as many rows as a third of the visible flow holds at the current text size, cut there, and its footer reads how many of how many lines are drawn, beside a control that opens the whole diff in place, a copy of that file's whole patch, and the door into the review surface, which scopes that surface to this one file, selects it and lands at its top; a diff inside the cut is drawn whole and its footer drops the open-all control alone. Past as many file blocks as a couple of screens hold, a call's remaining files fold into one footer naming how many more files changed and how many changed in total.
- **Dispatch block** — a run group holding the session's own dispatches, its header naming how many agents were dispatched and how many more by them, and in tree order one item per child, a child that dispatched agents of its own carrying a fold of its own and a box holding its descendants.
- **Streaming prose** — the prose row while it streams, the text already shown and the text still pending drawn as their own spans.
- **Files-written row** — a chat session only: the one list of what the chat made, every artifact in its store with its folders, each file openable ([Spec-012 §Required Behavior](./012-artifacts-files-and-attachments.md#required-behavior)).
- **Workflow progress row** — one flat row for a run this session started: the run's name, its status, its elapsed time, and a way into the run; it updates in place until the run ends.
- **Workflow results row** — the same row once the run ends: name, status, duration, a one-line summary of what came out, and the run's attachments as file rows in that same shape, with no cost figure. It is an ordinary message the session's agent reads on its next turn.
- **Aside row** — the answer to a question asked of a throwaway read-only copy of the session, landing in the flow at the point it was asked, in the flow's quiet type, saying on its first line that it is a side question and not part of this conversation, with the question and its answer beneath and a copy and a fork at its foot. It is never an overlay and never part of the session's own history.
- **Child-only rows** — inside a child run's view, the child's own note row and system messages for a steer and an interrupt; a pause and a continue append no row. A child run is drawn as a child: a row in its parent's transcript, its entry in the agent list and its own view show the agent tree, its provider and model, and `via <agent>` where it was a peer call; no row, label or tag names how it was reached. A provider's own subagent is a child run like any other: the provider driver records it when the provider reports it starting and stopping, so it appears in the agent tree.

The approval card, the question card and the plan verdict card are **not** flow rows: they are raised in the composer area ([Spec-010 §Required Behavior](./010-approvals-permissions-and-trust-boundaries.md#required-behavior) and §An Agent's Question below), while the plan document itself is a flow row of its own (§Required Behavior).

**The rows that belong to sessions talking to each other are each one of the kinds above rather than a kind of its own.** A send and an arrival are each a **Tool row** in the ordinary tool-row shape, drawn the same way on both sides: the verb `Message`, the other session as the target, the send's state in the trailing cell, and, where the message carried files, the same file chips a sent turn's attachments draw, on both rows — the arrival's row sitting where the message was folded into that turn. A send is an ordinary tool call under the sending session's own permission level, so at a level that asks its row waits on the ordinary approval card and at `Sandboxed` and `YOLO` nothing asks; what the message causes follows the receiving session's own level. It is the one tool row whose verb is the console's own word rather than the provider's name for the tool, and what each state reads is [Spec-021 §The session screen](021-desktop-app-and-renderer.md#the-session-screen)'s. The rest are **system messages**, and **none of them is a failure**: `Turn interrupted · exchange with builder ended · 2 messages not delivered`, where an interrupt ended a live exchange on both sides; `Step limit reached · 40 · Continue`, where a turn reached the person's own step bound — the one of these that carries a press, `Continue` carrying that same turn on rather than starting a new one; and `3 messages waiting · paused` on a paused session, which opens to the list of what is waiting and goes as the continue delivers them in the order they arrived ([Spec-014 §Sessions Talking To Each Other](014-multi-agent-orchestration.md#sessions-talking-to-each-other), [Spec-003 §The Step Bound On A Turn](003-queue-steer-pause-resume.md#the-step-bound-on-a-turn)).

### An Agent's Question

An agent's question — Claude Code's held user-question request, Codex's user-input request — rendered as one actionable question card in the session's composer area, where an approval card sits. A permission request is **not** rendered here: it is an approval and rides the approvals surface ([Spec-010](010-approvals-permissions-and-trust-boundaries.md)), and this section changes that routing in no way. A question and an approval are different records, so exactly one surface renders any request and neither has to guess.

- **Source**: the question record, `question.asked` ([Spec-005 §An Agent's Question](005-session-event-taxonomy-and-audit-log.md#an-agents-question)); the answer is written as an ordinary message record.
- **The card.** An eyebrow reading `Question`, the agent's own short header as a chip beside it, the question itself as the title, and the agent's heading as the summary line only where it sent one. Under them the option rows, each carrying a mark, its label, its description, and a number key on the first nine. The row the agent recommended stays where the agent put it — first, which is how both providers are asked to write it — and is marked as recommended, with the provider's own parenthetical suffix stripped so the mark is made once. A dashed `Something else…` row with a text field is **always last**, on every ask with or without options: a provider that declares no closed choice set is the ordinary case on at least one driver, and a card offering only options would leave such an ask unanswerable while its run sits blocked. Where both are present the options are a shortcut into the same answer, not a different one.
- **Answering.** Number keys pick a row, the arrows move between rows, and Enter presses the primary button; a pick never advances the card by itself. The buttons are `Skip`, `Back` — absent on the first page — and `Next`, which reads `Answer` on the last page and on a single question. The marks are boxes, and several picks go back together, on every Codex question and on a Claude Code question that carries the several-answers flag; they are single-choice marks otherwise.
- **Several questions page one at a time**, with the count of where the card stands beside its eyebrow, `Back` and `Next`, and `Answer` on the last page. Picks and typed text survive paging in both directions, every answer goes back together when the last page is answered, and `Skip` leaves that page's question unanswered and moves on.
- **Two arms exist only where the provider supplies them.** A preview column beside the option rows is drawn only where Claude Code attached previews to the options, and it follows the focused row; Codex questions never show one. A masked field with no option rows is drawn only where Codex marked the question secret; the value is never written into the timeline, and the user's turn afterwards records that a secret was answered. Claude Code questions never show that field.
- **The answer lands as one ordinary user turn**, not as a card that stays. Answering — or skipping a single question — hides the card and appends one turn carrying, per question, the question's own text as a faint quoted line with the answer beneath it at full strength: the picked labels joined with commas, the typed text, that it was skipped, or that a secret was answered. The turn is drawn settled at once, having been held while the agent waited. The agent then resumes, the working line returns to its verb, and the session leaves the group waiting on a person. That turn is the record, and the question cannot be answered twice.
- **A question the agent did not wait for is a message, never a card.** On the one provider that emits them, it renders as the agent's own message with option rows under it, joins no attention group, and is counted on the working line while it is unanswered. Pressing a row sends the quoted question and that row's label as one message, which lands as a pending row while the turn runs, the row then reading as chosen and the rows settling; typing in the composer answers it just as well. Pressing the working line's count opens the question card in its usual place on those questions, oldest first and paged, while the agent keeps working and the working line keeps its verb and clock; answering sends one message per question and the count drops, the control leaving at zero, while dismissing the card leaves the count where it was. Pending rows survive a pause: rows pending when the agent stops to ask, or to seek an approval, stay pending in place and land at the agent's next step once the answer resumes the turn.
- **A tool server's question is answered on this same card**, drawn in this product's own controls — text fields, one pick and several picks — with the server named beside the eyebrow the way an agent's short header is. The server never draws a surface of its own inside the card, and a question that would hand the user off to a web address to finish elsewhere is refused with one line saying so rather than followed.
- **The card carries no clock and never settles itself.** The daemon holds the provider's request open with no timer, rebuilds the card on reload and on every linked device of the user, and lets the first answer settle it everywhere; a device that was showing the card closes it with one line saying it was answered elsewhere. Besides the answer, the only thing that closes an open question is the end of the turn holding it: an interrupted turn cancels it, and the cancellation is recorded. The question itself never runs out of time ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)). The card closes when its attention entry resolves ([Spec-017](017-notifications-and-attention-model.md)), for an answer from any device and for an interrupted turn alike, and the renderer derives **no** close of its own, on this spec's standing wire-verbatim discipline. That matters more here than on a status row: a card carries nothing counting down, so it can never show a close the daemon has not recorded.
- **Answer dispatch** is one resolve call on the question record (§Interfaces And Contracts), carrying per question the picked labels, the typed text, the secret — which is never stored — or a skip. The daemon is what shapes that into each provider's own answer: on Claude Code the held request is answered with the ask's input unchanged plus the answers keyed by question text, the annotations and the response and nothing else; on Codex the picked labels, the typed text, or an empty list per question identifier, with the daemon writing the question record itself because that provider emits no item for it.
- **A workflow step waiting on this session asks on this same card**, and the run's page is a second door onto the same wait ([Spec-015 §Execution semantics](015-workflow-authoring-and-execution.md#execution-semantics)). The workflow's name sits beside the eyebrow as the chip, where an agent's short header or a tool server's name sits, so the question never reads as the agent's. A wait for a chat reply carries its question with the free-text row alone — a plain field with no `Something else…` label — and `Answer` as its one button, dimmed while the field is empty, with no `Skip`; it otherwise ends only at the step's timeout or with the run. A chain's question sits on the session of the chain's first run and reads `Summarize folder has started 100 runs from its 2:00 AM start. Keep going?`, with no option rows and its two answers as the card's buttons, a quiet `Stop them all` then the primary `Keep going`. While either waits, the session is one of the moments waiting on the person. The first answer through either door settles the wait everywhere, and the card becomes its one-line receipt with no way back — `Answered at 2:14 PM`, `Kept going at 100 runs`, `Stopped at 100 runs`, or `Timed out at 6:00 AM` when the step's timeout comes first — which stays in the card's place until the person sends their next message or another card takes the place. Nothing lands in the transcript: the answer goes to the run, not to the agent, and the run's page keeps the record.
- **Unrecognized values render rather than vanish**: an option shape or a state value this spec does not enumerate is shown as itself, so a later member is never silently invisible.

### Run-State Subtypes

Run-state subtypes are rendering types that map from underlying run lifecycle events. They exist so the timeline can render distinct visual treatments without inspecting raw event payloads.

| Entry Type | Rendered As | Source Condition |
| --- | --- | --- |
| `run.paused` | Status row with pause icon | Run transitions to `paused` state |
| `run.resumed` | Status row with resume icon | Run transitions from `paused` to `running` |
| `run.blocked` | Status row with block indicator | Run enters `waiting_for_approval` or `waiting_for_input` |
| `run.unblocked` | Status row with unblock indicator | Approval or input resolves the block |
| `run.rolled_back` | Status row with rewind indicator; the run's already-delivered rows above the carried rewind cutoff take the superseded treatment (§Required Behavior) | Accepted rollback rewinds the run — the forward `run.rolled_back` event ([Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior)) |
| `agent.provider_binding_changed` | **One faint collapsed system message**, never a message row and never a block, drawn only when the event's `from` and `to` bindings differ in provider or account; an event whose bindings differ only in model, effort or speed settles in place and draws no row. A provider switch reads `Switched to Codex` and, when `declaredLosses` is non-empty, how the conversation continued and what did not carry over — `· continued from a brief · 3 things did not carry over` — opening to the declared losses named in plain words, beside the faint `Hand-over brief · <the provider that wrote it>` row that opens to the brief. An account switch reads `Switched to account <name>` and opens to the account it came from, the account it went to and the time. A switch that carried everything renders the same single line without a loss clause; it does not render as a warning, because nothing was lost. Both continuity arms render the same one line and differ only in that clause: `'in_place'` carries none and `'brief'` carries it. The row is rendered from the event payload's `from` and `to` bindings, the account the run landed on and `declaredLosses` **verbatim** — the renderer derives nothing, on this spec's standing wire-verbatim discipline, and in particular does not infer loss from the presence of a switch, nor a difference in treatment from which of the arms produced the row, the mechanism being a detail and not something the user is asked to act on | The `agent.provider_binding_changed` event ([Spec-005 §Agent Lifecycle](005-session-event-taxonomy-and-audit-log.md#agent-lifecycle-session_lifecycle); [Spec-014 §Same-Agent Provider Switch](014-multi-agent-orchestration.md#same-agent-provider-switch)) |
| `agent.provider_binding_change_failed` | **One system message**, the only trace of a switch that failed after it was accepted: the switch never lands, the agent stays on the binding and the account it had, the waiting words leave the working line, and the success row is not drawn. It names the attempted switch and the `reason` in plain words — `Switch to Codex failed · <reason>`, or `Switch to account <name> failed · login expired · Sign in again` — with `Sign in again` offered only where `accountState` is `reauth_required`. An in-place account switch whose login then fails at the next request draws the same message, and the daemon hands the previous account back. There is no banner, toast, dialog or standing error. It never reads as a switch — the user asked for a change that did not happen, and a row that implied otherwise would be worse than none. The reason is rendered from the payload verbatim, an unrecognized value showing the value itself rather than being dropped, so a later member is never silently invisible | The `agent.provider_binding_change_failed` event ([Spec-005 §Agent Lifecycle](005-session-event-taxonomy-and-audit-log.md#agent-lifecycle-session_lifecycle); [Spec-014 §Same-Agent Provider Switch](014-multi-agent-orchestration.md#same-agent-provider-switch)) |

## Context Window and Usage Meters

The session composer area must always display a context-window meter reflecting the current provider conversation state.

- **Fields**, as `session.contextSubscribe` streams them (§Interfaces And Contracts) and `usage.context_window_update` records them ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)):
  - `windowUsedTokens`: the tokens in the window, as the provider reports them.
  - `windowMaxTokens`: the window of the session's model, read from the provider.
  - `windowSource`: where the window figure came from.
  - `exceeded`: whether the conversation has outgrown the window.
  - the breakdown: Claude Code's named categories, which this section's inspector rows read; Codex reports totals only.
  - The share of the window in use, which the ring draws, is the provider's own percentage on Claude Code and `windowUsedTokens` over `windowMaxTokens` on Codex.
- **The meter is one figure and one meter, and it is never colored**: a ring carrying the share of the window in use, with a faint notch on its arc at the compaction bound and a hover that reads the current percentage together with that bound, `Context 41% · compacts at 80%`. It is also a control: pressing it opens the compaction controls in place above it — `Compact now` over a slider reading `Compact automatically at <bound>% · of <window>`, the window being the model's own figure — with no overlay, closing on Escape or a press elsewhere. There is no compaction chip anywhere in the composer area.
- **Compaction at the bound is the provider's own, and it is automatic; compaction on request is the user's.** The bound is a setting rather than a warning, and every figure behind it is read from the provider and never hard-coded. **The default** is set once per provider in Settings as `Compact automatically at <N>% full`, mapped onto that provider's own knob and moving in steps of five between the lowest bottom stop and the highest top stop that provider's models report; where it falls outside a session's own stops, that session reads it at the nearer stop, unmarked. **The session's own bound** is the slider behind the meter: it applies from the next turn, carries a mark saying it belongs to this session until it matches the default again, belongs to that session alone, and the next session opened on the project starts from the default once more. Its range is derived for the session from the provider's live figures, read at creation and on every model change: the top stop at the provider's own compaction point on this window, with no fixed cap of this product's own — on Codex, which clamps every limit at 90 per cent of the window, that is 90 per cent — and the bottom stop at the session's fixed start, what the session loads before any message, plus a tenth of the window, rounded up. `/autocompact <size>` moves the slider to the nearest per cent of the session model's window and `/autocompact auto` returns it to the default; a value outside the session's stops presses nothing and draws one system message saying what the word accepts.
  - **Claude Code's knob** is the `env` pair `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, set at spawn and through `apply_flag_settings {env}`. The daemon sets the window key when the provider's context report gives the model's compaction source as `auto`, even at the model's own point, because without it such a model does not compact early at all, and whenever the slider leaves the model's own point; at the model's own point with a model-default source it leaves the key unset, because a window set that way also turns off Claude Code's special case for models with a native 1M window. The window key alone sets every point from 67,000 tokens up; below that the percentage key reaches, its point computed from the reply reserve and the constant read at creation. On a model change the daemon removes the key, reads the new model, and sets the key again where needed. Every figure is read under the session's own base URL, because a proxy changes them.
  - **Codex's knob** is `model_auto_compact_token_limit`, per conversation, which fires before a turn and mid-turn between requests. No Codex request reports a session's fixed start, which depends on its tools, tool servers, agents, memory and skills: until the session's first usage report the popover shows the current bound and the top stop, the slider stays inactive, and one line under it reads `The range opens after the first reply, once Codex reports what this session loads.`; after that report the bottom stop is counted from that turn's actual input.
  - **Three figures no request reports are read from the installed provider**, never guessed: Claude Code's reply reserve and its constant, from two context reads in the short control-only process the daemon runs at session creation; its output-style descriptions, from `/output-style` with no argument in the same process; and Codex's resolved compaction point, from Codex's own trace in a calibration service run against a local stand-in endpoint, keyed by the Codex version, the model and the offered window.
  - Nothing else in this product initiates a compaction: there is no second threshold, no timer and no heuristic, and no surface reshapes a conversation on its own initiative.
- **Visibility**: the context-window meter is always visible in the session composer area regardless of usage level.
- **The user-initiated trigger is a different act with a different actor** from the bound: the user decides, and the system does what it was asked. It is the compaction controls' `Compact now`, and the product command that compacts at once without opening them.
  - It is **capability-gated** on the bound driver's `context_compaction` flag ([Spec-004 §User-triggered context compaction](004-provider-driver-contract-and-capabilities.md#user-triggered-context-compaction)) and is **absent** where the flag is `false` — not present-and-disabled, because a disabled control asserts that the capability exists and is momentarily unavailable, which would be false. It is offered at every usage level rather than unlocking at a threshold: a user who wants a clean context before a long task should not have to fill one first.
  - **It dispatches the already-minted `driver.compactContext`** and renders **only** from what comes back through the event stream. A dispatch shows an in-progress state; the completed state renders on the `usage.context_compacted` row, and the meter's own new reading arrives on the ordinary `usage.context_window_update` path with no special case. The renderer never treats the request's acceptance as a compaction, and never redraws the meter from a value it predicted — both provider mechanisms answer before the work is done, so a surface that trusted the acknowledgment would show a compaction that had not happened. A refusal renders as a refusal. **The in-progress state clears on the operation's own settlement, not on the boundary row.** The two are separate moments and conflating them would hang the control: the daemon's compaction wait is bounded and can settle `failed` — an expired wait, a lost binding, a provider error — with no boundary row ever arriving ([Spec-004 §User-triggered context compaction](004-provider-driver-contract-and-capabilities.md#user-triggered-context-compaction)). So the in-progress state ends when the call settles, in **every** arm, and the settlement's own reason renders where it is not `applied`; the **completed** state still renders only on the `usage.context_compacted` row, unchanged. The two rules compose without conflict because they answer different questions — whether the request is still outstanding, and whether a compaction actually happened — and a late boundary row arriving after a `failed` settlement moves the meter exactly as a compaction the provider began on its own would, which is what it is indistinguishable from at the point it is normalized.
  - **A compaction that fails lands no row.** The working line returns to its verb and the ring keeps its figure, because the provider tries again at the next turn. When the person asked for it, the one line beside the message box says why — `Compaction didn't run — the conversation is too short to compact`, or the provider's other reason in words — and is cleared by the next keystroke. A turn that cannot fit even after compaction is cut with the provider's own verb and handed back as a failed send, its words back in the composer and the system message `Send failed · Too long for this session's context window` in the flow.
- **Update mechanism**: the meter and the inspector's context section read one stream, `session.contextSubscribe` (§Interfaces And Contracts), whose readings the daemon also records as `usage.context_window_update` ([Spec-005](005-session-event-taxonomy-and-audit-log.md)); a completed compaction arrives as the `usage.context_compacted` row on the session's own stream.
- **What is in the context is read per provider and never computed here.** Beside the meter, a session's inspector carries a context section: one head line reading the tokens in the window against the window size together with the percentage the meter shows, then one row per bucket, each a name on the left and a right-aligned token figure. On a Claude Code session the rows are that provider's own buckets in its own order, named in this product's words — the system prompt, its system tools, the tool servers' tools, custom agents, memory files, skills, the messages, the compaction buffer, and free space — with a bucket the provider defers rendered dimmed and left out of the head line's used figure, and a bucket the provider reports named parts for unfolding into rows of its own when pressed, every other row being inert. On a Codex session the rows are that provider's only split — cached input, input, output, reasoning — and one note line under them reads exactly `Codex reports totals, not what is in them.`; on a Claude Code session that line is absent rather than empty.
- **One read per provider feeds the meter and that section alike**, so the two can never disagree. On Claude Code it is the provider's own context report: the model, the total, the window size, the percentage, and the named categories with the kind the provider marks each one — used, deferred, buffer or free — together with the tool, memory-file, agent and skill lists that sit behind them. On Codex it is the thread's token-usage update: the total, cached input, input, output and reasoning against the model's context window, because that provider exposes no category split on any surface it has. A provider that reports no split gets the honest note line rather than a derived figure. The section is a list of figures and never a graph, and no value in it overflows its own width: a long one truncates and carries a hover title.
- **The window is a fact of the model, read from the provider.** Every provider figure — the window, the larger window a model offers, the compaction point, the fixed start, the model list and the output-style names — is read when the session is created and on every model change, under the session's own base URL, and is never hard-coded: on Claude Code from its own context report, on Codex from its model catalog, corrected by the first turn's usage report, whose window is the usable one, 95 per cent of the full window, and reflects an override. The Claude models the session is not on are read at creation by one short control-only process on the same account home and base URL, taking about five seconds, with a one-token check per model id that is not a built-in alias. Where Codex's catalog lists a larger window for a model than its default, the model picker carries a second row for that model with the larger window, `GPT-5.6 Luna · 872K` beside `GPT-5.6 Luna · 272K`, and choosing it makes the daemon pass `model_context_window` equal to that maximum — the one value it ever passes, because any smaller value replaces Codex's own window. A model whose maximum equals its default has one row.
- **Every cost figure is the cost.** The session's cost receipt ([Spec-014 §Session Cost Receipt](014-multi-agent-orchestration.md#session-cost-receipt)) and every figure read from it carry dollars, never `est.`, `tokens only`, `unpriced` or unknown, and a session that has spent nothing reads `$0.00`. Where the provider reports no price of its own, the daemon prices from its price table, a live copy of LiteLLM's MIT-licensed model price list, fetched when the daemon starts, once an hour while it runs, and at once on first sight of a model or a speed the held copy lacks; the newest copy that passes its schema is kept, and each release carries one for a first start that cannot fetch. A model is found by its exact id and never priced as a neighbor of its family; a request is priced once, when it completes, and never repriced; no table is kept by hand. Every model and speed a provider lists is offered the moment it lists it, priced or not, and a request on one the list does not price yet is held with its exact tokens and joins every figure when a later copy prices it. A Codex request costs (input − cached − cache writes) × the input rate + cached × the cached-input rate + cache writes × the cache-write rate + output × the output rate, because Codex's input count already holds the cached and the cache-write tokens; every rate is the price list's own for that model, its long-context rate when that request's input passes the size the list names for it and its Fast rate when the conversation runs Fast; reasoning is already inside output and is never added, and a turn costs the sum of its requests. A subscription figure is the same tokens priced exactly at the published per-token rates. A total adds every row and never counts a budget's reservation.
- **Compaction boundary and superseded marking.** A **provider-side** context compaction, whether the provider reached the bound on its own or the user asked for it, is recorded as a `usage.context_compacted` row ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). Two consequences follow: the row is run-scoped, so it takes §Required Behavior's superseded treatment on exactly the same terms as every other run-scoped row, with no exemption; and this meter, which reflects the **current** provider conversation state, therefore stops reading a superseded compaction marker as the run's live compaction state. An undo may return to a point before the last compaction ([Spec-003 §Driver-Level Rollback Mechanics](003-queue-steer-pause-resume.md#driver-level-rollback-mechanics)), and that undo is what supersedes a compaction row.

### Rate-Limit Display

A provider quota reading describes **one named provider account, for one named limit**, and it is drawn in one place: on that account in Settings › Providers, one row per limit, as [Spec-026 §Per-limit provider quota](026-provider-accounts-and-credential-homes.md#per-limit-provider-quota) states. The session screen carries no quota figure — none beside the context ring, none in a footer under the rail or the session list, and no account-wide total — and a limit that binds mid-turn reaches the session only as the working line's words and one system message (§Fallback Behavior). The figure is an account-plane fact, never a session-level or per-run one, and it must never be rendered as either.

- **The display reads exactly two Sources.** **(a)** The `usage.rate_limit_update` event on the canonical event stream ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)), emitted from real traffic. **(b)** The **newest stored reading** in the daemon's per-account quota-window registry ([Spec-026 §Per-limit provider quota](026-provider-accounts-and-credential-homes.md#per-limit-provider-quota)), carried on the provider-account read and its subscription. **A stored reading keeps the provenance it was observed under, not the transport that delivered it**: the registry is fed by both the real-traffic event and the deliberate probe, so a window served from it may carry `source: 'run'` exactly as legitimately as `source: 'probe'`. A consumer accepts both on a stored snapshot and never infers provenance from the fact that a reading arrived on a read rather than on the event stream. The second Source exists because the first is only available to a client that was connected when the traffic happened: a renderer opened after a reading was taken, or after a restart, would otherwise show nothing and be unable to distinguish that from a healthy account. **Precedence between them is by observation time, not by source**: newest `observedAt` per `(providerAccountId, limitId)` wins, and `source` breaks **only exact ties**. Preferring one source outright would let a stale reading mask real consumption. A stored reading additionally carries the credential generation it was observed under, and a reading whose generation is behind the account's current generation is rendered **stale rather than current** rather than dropped — a credential-home rebuild does not stop the provider-side window the reading describes ([Spec-026 §Per-limit provider quota](026-provider-accounts-and-credential-homes.md#per-limit-provider-quota)).
- **Neither Source is an HTTP response header.** The indicator is not extracted from any control-plane response header — the control plane's own rate limiting meters this product's API, which is a different quota from the provider's and must not be displayed in its place.
- **Fields** (as carried by the event, plus the account identity added by [Spec-026 §Provider quota is account-scoped](026-provider-accounts-and-credential-homes.md#provider-quota-is-account-scoped)):
  - `provider`: the provider whose quota window this reading describes.
  - `providerAccountId` and the credential generation observed with it: together the `(accountId, credentialGeneration)` account-plane key of the account the reading belongs to (see [Spec-026 §Account identity and credential generation](026-provider-accounts-and-credential-homes.md#account-identity-and-credential-generation)).
  - `limitId` (optional on the wire, defaulted on read): the provider's own identifier for **which** limit this reading describes. **This is the reading's key, together with the account** — absent means the reserved identifier `default`. It is required here because a single account may stand against several limits at once: the pinned Claude surface publishes five, of which **three share a 10080-minute window**, so a surface keyed on the window length would render one weekly limit as the person's weekly standing and silently drop the other two, with the survivor decided by arrival order.
  - `windowMins`: the length of the provider quota window this reading describes. A **property of the reading, not part of its key** — two limits of one account may share a length.
  - `usedPercent` (0-100): the fraction of that window's quota consumed.
  - `resetsAt` (optional): ISO-8601 timestamp when the window resets, present only when the provider supplied one.
- **No absolute counts**: the carrier reports a percentage, not request or token counts. The surface must render the percentage it was given and must not synthesize a `remaining` or `limit` figure, which is not derivable from a percentage alone.
- **No run to join through**: the event carries no `runId`. Quota is consumed by an account across every run and every session that account executes, so there is no run whose row could supply the account — which is exactly why the event carries the account identity directly rather than leaving it to a join.
- **Account labeling is mandatory**: every rendered quota figure must be labeled with the account it describes, by the identity [Spec-026 §The account registry](026-provider-accounts-and-credential-homes.md#the-account-registry) gives it — the address, plan and organization its provider reports, or the name the person gave an account added by a pasted token or key. This machine may hold several accounts for one provider, and each has its own independent quota; an unlabeled or merged figure would show the person a healthy quota while the account actually executing their run is exhausted. Readings for different accounts are never summed, averaged, or otherwise collapsed into one figure.
- **Limit labeling is mandatory on the same grounds, and readings are never collapsed across limits**: where the provider publishes a display label for a limit it is rendered, and where it does not the limit identifier is rendered verbatim. **Every consumer obligation on this display applies per `(providerAccountId, limitId)` and never across limits** — including the drop-a-lower-reading rule, which requires the same `limitId` as well as the same `resetsAt` before a decrease may be discarded. Two limits of one account move independently, so a comparison spanning them is never meaningful, and collapsing them would reproduce inside one account exactly the harm the account-labeling rule prevents across accounts.
- **Each limit is one row on its account**: the limit's own label, a bar filled to what has been used, the share used in words and, where the reading carried a `resetsAt`, when the window resets — `Weekly limit`, a bar at 62 per cent, `62% used`, `resets Friday 3:00 PM`. A window the provider reports for one model is its own row beside the general ones, `Weekly · Fable`. Nothing is read off the bar alone. A window that has reset reads an empty bar with `Reset · 0% used`. A reset time is never estimated or fabricated when the provider did not supply one.
- **Every pair with a reading is drawn**, healthy or not, so an account standing against several limits shows several rows. Under the rows one line says when they were read, `read 7:24 PM`, or `from its last turn · 7:24 PM` where the figures came from the account's own last turn rather than a read of its own; a reading taken under an older credential generation carries one line under the rows, `From before this account's credential changed`.
- **What absence means.** An account with no limit rows is not an affirmative statement that its quota is healthy, and there are two distinct ways for that to be true: no reading has ever been taken from either sanctioned Source, which reads `Not read yet` with no bar; or this home is **not plan-limited at all**, which the provider itself reports for API-key and third-party-inference sessions where plan limits are simply not a concept, so a Codex API key's account draws no limit rows. A surface that rendered either as healthy would misreport it.
- **Update mechanism**: readings are keyed by `(providerAccountId, limitId)`, exactly as the event registers them ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). The key carries both members because a key without the account collides **across** two registered accounts of one provider and a key without the limit collides **within** one account; a reading is therefore held per account and per limit rather than once per node and is updated as later readings for that same pair arrive. A reading observed under a credential generation that the account has since moved past is stale and must not be shown as the account's current quota.
- **Account-scoped, and deliberately not symmetric with the session cost receipt**: the quota event binds to the reserved node-scope sentinel rather than to a session and is not uploaded to the control plane ([Spec-005 §Daemon-Scope Event Binding](005-session-event-taxonomy-and-audit-log.md#daemon-scope-event-binding)), so a user sees quota for the accounts registered on this machine. This does **not** generalize to spend: the session cost receipt ([Spec-014 §Session Cost Receipt](014-multi-agent-orchestration.md#session-cost-receipt)) is per session, because the usage events it folds are session-scoped. A reader must not assume the two surfaces share a reach — one meters an account across every session it runs, the other meters one session.

## Interfaces And Contracts

- `TimelineRead` must support bounded windows and cursor-based continuation.
- Live rows arrive on the session's one stream, `session.subscribe`; a client that fell behind resumes it with `afterCursor` at its kept position. There is no second timeline stream.
- `ReasoningSurfaceRead` must identify availability status.
- `ChildRunExpand` must read detailed activity for a summarized child-run row.
- On the wire these are `timeline.read`, `timeline.reasoningSurfaceRead` and `timeline.childRunExpand`; `session.subscribe` delivers the session's events in the batched frames §Required Behavior describes. `timeline.reasoningSurfaceRead` reads every reasoning text whole: a text kept as consecutive 16,384-character entries is returned as one. `timeline.childRunExpand` reads a child's rows on demand, a finished child's stored record included.
- `timeline.bodyRead {sessionId, rowId}` reads a row's large body or whole output, only when its control is pressed; the row id is the event id. It answers `{available: true, content}` or `{available: false, reason}`, the reason saying why the body cannot be read, such as the loss of the key that sealed it. It is refused with `session.not_found` for a session id the daemon does not hold, and a row id the session does not hold is refused as not found.
- `timeline.patchRead {sessionId, toolCallId}` reads every patch a call did not carry, in one read, answering `{files: [{path, patch} | {path, unavailable: reason}]}`. The call's row names the patches it left out, `omittedPatches: [{path, size}]`, so it looks exactly like a row whose patches traveled.
- `timeline.search {sessionId, query}` searches the whole of one session's own rows, loaded or not, answering `{hits}` with every hit in the session's own order, each carrying its row's cursor, the line the match sits in and the matched ranges, so the find box counts the whole session; a hit takes the reader to its row by the one path every way of reaching a row takes (§Default Behavior), loading the history it sits in only when the person steps to it. It is refused with `session.not_found` for a session id the daemon does not hold.
- `ReasoningSurfaceRead` and `ChildRunExpand` must support the same cursor-based continuation `TimelineRead` does: each takes an optional after-cursor, and each answers with an explicit more-to-come flag so that an over-large result is a page the caller can continue rather than a refusal or a silent truncation.
- Every page a read returns must fit in one transport message body. The substrate's limit ([Spec-006 §Wire Format](006-local-ipc-and-daemon-control.md#wire-format)) is absolute and an oversized response closes the connection rather than failing the request, so the bound is stated on the **encoded size of the page** and checked once per reply, against the page's own byte budget, which keeps today's page size, stays under the transport limit and is never sized against it — never on a row count alone, which cannot bound a page whose per-row text fields and opaque payload are bounded independently of it. A producer fills a page until the row ceiling or the byte budget trips, whichever comes first, and reports the remainder as a continuation.
- A page that reports more to come must carry the cursor that continues it **and at least one entry**. A page promising more and delivering none advances nothing while reading like progress: the caller obeys the contract, re-asks from the same cursor, receives the same answer, and loops. The byte budget above therefore bounds **aggregation** and never bounds a page below one entry — where the first candidate alone exceeds it, the producer pages that entry rather than reporting an empty page, and the reply is refused for its size at the response boundary, which names the offending member instead of leaving a caller to loop on an unconsumed cursor. A terminal page may carry a cursor and is never required to, so a caller moving from a completed read to a live subscription has an after-cursor wherever the daemon has one; a terminal page may also be **empty**, which is the honest answer to a continuation whose cursor already sat at the end and to a filtered read that matched nothing.
- A page must be internally consistent with the header it carries: its entries never move backwards in sequence, and every run-scoped entry of a child-run expansion belongs to the run the response names.
- **Every reply and every emission is scoped to the request that asked for it, and answers the question it asked.** A timeline read returns rows of the requested session only; a child-run expansion names the requested run; a live subscription carries rows of the subscribed session only. One further reply is judged against the request rather than against itself: an `available` reasoning surface carrying **no entries** is the correct answer to a continuation whose cursor already sat at the end of the surface, and a defect on a **first** read, where it renders as a surface that exists and shows nothing — indistinguishable from the unavailable state while asserting the opposite, the state collapse the availability vocabulary exists to prevent. A producer with nothing to serve at all must answer with the state that is true. A third is judged the same way: a page may not exceed the **window the caller asked for**, which is the request's own row limit where it named one and the default ceiling where it did not — a response schema can bound a page only at the default, so a read for ten rows answering with the maximum is otherwise well-formed, and a client sizing a viewport, a budget, or a render pass from its own request is handed more with nothing on the reply saying so. None of this can be a schema rule — a response schema never sees the request — so it is enforced where both are in hand, at the daemon's method binder, on the caller's own parsed request. A cross-scope reply is a **daemon** failure and never a client one: the caller asked a well-formed question, the answer is well-formed, and it correlates to the caller's own request id, so nothing downstream can tell it apart from a correct answer. A cross-scope emission is refused before it is written rather than reported, because the acknowledgment it would ride behind has already settled and a notification frame carries no error channel.
- **A row is filed under a run wherever the corpus says it belongs to one, and it may not say so twice differently.** Whether a row is run-scoped is decided by three tests and not by its category alone: a category closed on the run-scoped side, a canonical event type whose registered payload names a run in every form ([Spec-005 §Event Type Enumeration](005-session-event-taxonomy-and-audit-log.md#event-type-enumeration)), or — for the types whose run identity is registered optional, which no type-level test can decide — the row's own payload naming one. A row answering any of the three while carrying the attribution-free kind is refused, because it would be reachable by no run filter and permanently current under rollback projection. Where a projection echoes the canonical origin keys into the payload, they must agree with the row's own attribution — under **either** registered spelling of run identity, since the intervention family names its run `targetRunId` and a rule reading only `runId` would leave every intervention row free to be filed under one run while naming another; echoing stays optional, and disagreement is refused.
- **The turn's live figures are their own subscriptions, one per running turn of a session.** Each takes `{sessionId, runId}` and is refused with `session.not_found` for a session id the daemon does not hold and with `run.not_found` for a run it does not hold; neither is stored as an event. `turn.usage` streams `{runId, turnId, tokensReceived}`, cumulative for the turn: the provider's own output count for each model round, summed — Claude Code's final message delta of the round, Codex's `last` output on its token-usage update — with reasoning already inside it and never added again, never Claude Code's result `iterations` figure and never a difference of Codex's running totals. `turn.tasks` streams the whole task list on every change, folded from the agent's task-list tool calls on Claude Code and from the plan-update stream on Codex, which the daemon enables per session, never drawn as a message. The reasoning state the working line's state word reads arrives on the turn's own stream rather than as a third subscription. Codex's hold of a turn for a safety check arrives as the live event `run.safety_buffering_updated {sessionId, runId, turnId, active, fasterModel?}` on the run's own state stream, `run.subscribeState`, which the daemon never stores, so a re-opened session does not replay it. None of the three is derived on the client: a figure the provider did not report is absent rather than estimated.
- **An agent's question is one record with one answer.** The held provider request — Claude Code's user-question tool request, Codex's user-input request — becomes one question record the surface renders, stored as the event `question.asked` ([Spec-005 §An Agent's Question](005-session-event-taxonomy-and-audit-log.md#an-agents-question)) and carrying the agent's header, the question, its options, the several-answers, preview and secret flags, and the page count. On Codex the user-input request routes here whatever the provider's experimental-API setting says, and every Codex conversation sets `features.default_mode_request_user_input = true`, so the request reaches it outside plan mode too. It is answered by one call, `question.resolve {questionId, answers}`, carrying per question the picked labels, the typed text, the secret — which is never stored — or a skip, and answering `{questionId, state: answered | canceled}`; a list that does not answer every question is refused, and a second call reads the state rather than answering again. There is no verb by which a client asks a question: a question exists because a provider stopped its turn to ask one, so the record is the daemon's to write and the client's only move on it is the answer. The user's answering turn is written as an ordinary message record with any secret masked, and a question the provider does not wait on is the message item it already is. A question is an attention entry exactly as an approval is, and the daemon holds the provider's request open until the record is resolved, rebuilding it on reload and on every linked device of the user (§An Agent's Question).
- **What fills the context is one stream.** `session.contextSubscribe {sessionId}` streams the readings the meter and the inspector's context section both draw — the tokens in the window, the window, where the window figure came from, whether the window is exceeded, and on Claude Code the named breakdown — from Claude Code's own context report and from Codex's model catalog corrected by the first turn's usage report (§Context Window and Usage Meters). It is refused with `session.not_found` for a session id the daemon does not hold.
- **The session's own compaction bound** is set by `session.autoCompactUpdate {sessionId, percent}`, answered `{sessionId, percent}`: a set, stored with the session and applied to the provider's own knob from the next turn, and refused outside the session's derived stops; the next session starts from the Settings default. `Compact now` and `/compact` dispatch `driver.compactContext {sessionId, runId}` ([Spec-004 §User-triggered context compaction](004-provider-driver-contract-and-capabilities.md#user-triggered-context-compaction)), whose completion is the `usage.context_compacted` row.
- **A side question** is `session.sideQuestionAsk {sessionId, question}`, answered at once with `{asideId}`; the answer lands later, at the point where it was asked, as the event `session.side_question_answered` carrying the question and the answer, which draws the aside row. It runs on a throwaway copy that is read-only by construction — on Codex `thread/fork {ephemeral: true, excludeTurns: true, sandbox: "read-only", approvalPolicy: "never"}` with no goal-continuation flag, on Claude Code a second process in plan mode on a copy of the conversation, passing the session's full model id and `--no-session-persistence` — so the aside never enters the session's history, and its cost goes to the session's account. It is refused for a session with no conversation yet and where the provider cannot run one.
- `ReasoningSurfaceRead` runs no policy check and carries no principal member: every caller reads the same reasoning, and the request schema is strict, so a member naming a user is refused rather than stripped.

## State And Data Implications

- Timeline rows are read projections, not canonical events themselves.
- Child-run summaries and detail windows must preserve provenance to the parent run.
- Reasoning rows are read back from the reasoning events of their turn, whole, for as long as the session's events are kept; a text kept as consecutive entries is read back as one.
- Superseded marking is projection-derived, never stored ad hoc: provenance traces through the Plan-003 supersede projection to the accepted `run.rolled_back` boundary event (its run and carried rewind cutoff) plus the projection-derived source epoch, and survives projection rebuilds.

## Example Flows

- `Example: A session timeline shows a run start, command execution, approval request, artifact publication, and completion, all as ordered timeline rows.`
- `Example: A background reviewer run appears as a summarized child-run row that can later be expanded to show findings.`
- `Example: A provider sends reasoning during a run. The timeline shows it as the reasoning tail as it arrives and keeps the whole text as the reasoning events of that turn; a reload, or a copy of the row, reads the same text back whole.`

## Implementation Notes

- Timeline virtualization or pagination is allowed, but it must not alter canonical ordering.
- Reasoning the provider kept back should still be visible as a row saying so.
- Live timeline and replay logic should share the same projection schema.

## Pitfalls To Avoid

- Hiding child-run work because it happened in the background
- Flattening every structured event into plain chat text
- Rendering reasoning as if it were always available and safe to show
- Dropping rewound turns from the timeline instead of rendering them superseded — the authoritative log never truncates ([Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior))
- Re-rendering superseded output as current after replay or a projection rebuild — or marking a re-executed turn that reuses a superseded ordinal (marks are epoch-scoped)
- Applying that treatment optimistically — truncating, removing, or renumbering rendered rows when an undo or an edit and resend starts rather than when its accepted `run.rolled_back` boundary entry appends (the boundary entry is the only thing that applies the treatment, and a cut that fails rewinds nothing, so an optimistic edit would drop history the run still holds — [Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) owns the rule; while the call is in flight the turns it will supersede dim and stay readable and pressable)

## Acceptance Criteria

- [ ] A client can see live run, approval, artifact, and child-run activity in the session's live view.
- [ ] Missing live updates can be recovered through replay without rebuilding state from free-form text.
- [ ] Reasoning surfaces clearly distinguish available and unavailable cases.
- [ ] Run-state entries render as distinct timeline rows with appropriate visual treatment.
- [ ] Rolled-back turns render with the distinct superseded treatment identically on live delivery (the `run.rolled_back` boundary entry's already-delivered-rows rule keyed on each row's exposed run position and epoch against the boundary's typed cutoff — delivered to every filtered subscription admitting the run's rows, the live marker identical to replay by construction — plus attribution-ranked late stragglers — pre-marked above the run's effective lineage-minimum cutoff for their epoch, current within the surviving history, a later rollback below an earlier retained prefix superseding the inherited rows), `TimelineRead` windows, and replay recovery; and a re-executed turn reusing a superseded ordinal renders current.
- [ ] An agent's question renders an answerable card with the question, a free-text answer arm present on **every** such card, and its options additionally where the question carries them; a permission request renders on the approvals surface and never as this card.
- [ ] A question card carries no clock of its own and never settles itself: it waits until it is answered, it closes when its attention entry resolves, and an answer lands as one ordinary user turn quoting each question with its answer beneath it.
- [ ] The composer offers a compaction control exactly where the bound driver declares `context_compaction`, absent rather than disabled otherwise, and the completed state renders only on the `usage.context_compacted` row — never on the dispatch being accepted. The control's in-progress state clears on the call's own settlement in every arm — a settled failure leaves no control waiting — while a boundary row arriving after that settlement still moves the meter. The only automatic compaction is the provider's own at the bound the meter's notch shows, and no other threshold, timer or heuristic initiates one.
- [ ] Every timeline read answers within one transport message body: an over-large result comes back as a page carrying an explicit more-to-come flag and the cursor that continues it, never as a dropped connection and never as a truncation the caller cannot detect. A returned page's entries do not move backwards in sequence, and a child-run expansion's run-scoped entries all belong to the run the response names.
