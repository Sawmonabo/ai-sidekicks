## Purpose

Define the canonical handling of artifacts, file attachments, and immutable output payloads.

## Scope

This spec covers artifact types, attachment ingestion and its validation pipeline, storage expectations, manifests, visibility, artifact deletion and local content-addressed-storage (CAS) reclaim, the typed attachment-reference contract turn-scoped carriers use, and the cross-node artifact relay (payload availability across nodes, including while the publishing node is offline).

## Non-Goals

- Full UI preview rules
- Notification behavior for new artifacts
- Remote object-store implementation details

## Required Behavior

- The system must support immutable artifact publication with durable manifests.
- Supported artifact families must include at least:
  - file or attachment
  - diff
  - plan or summary
  - command or terminal output excerpt
  - design or generated preview output
- Attachment ingestion must produce stable artifact ids and provenance metadata.
- Attachment ingestion must run every accepted payload through the validation pipeline of §Ingest Validation And Payload Bounds (V1) **before** the bytes are persisted or any manifest row is written: bounded size, bounded per-carrier count, an allow-listed media type, and a magic-byte check reconciling the declared type against the payload's own leading signature. A payload that fails any bound is refused or quarantined — never persisted as a normal artifact and never silently accepted.
- The daemon must **derive** an ingested payload's media type and byte size from the payload bytes themselves. A caller-declared `mediaType` or `sizeBytes` is **advisory input, never a trusted fact**: it is reconciled against the derived values, and the derived values are what reach the manifest, the CAS key, and every downstream consumer.
- Artifact deletion must exist as an explicit operation (`ArtifactDelete`, §Local Artifact Deletion And CAS Reclaim (V1)) with a defined disposition for shared CAS payloads, for derivative artifacts that name the deleted manifest as their `subject`, and for a live relay pin over the same content.
- Where a turn-scoped carrier references attachments (a steer, an intervention, a human-phase form submission), the reference must be a typed, ordered list of `ArtifactId` values — never an untyped payload blob and never an inline byte carrier. Ordering is caller-declared and preserved end to end, and an attachment the turn cannot deliver must degrade honestly with an explicit per-attachment diagnostic; silently dropping an attachment from a delivered turn is prohibited.
- Artifact visibility must be explicit and must distinguish `local-only` from shared-visible artifacts.
- V1 artifact visibility must remain class-based and policy-based. Participant-specific partial redaction is out of scope for the first implementation.
- Referencing a live workspace file is not sufficient for artifact immutability; the system must capture immutable artifact content or a content-addressed snapshot.
- A shared-visible artifact within the relay size cap must be fetchable by session participants on other nodes **while the publishing node is offline** (eager relay pin at publish — see §Cross-Node Artifact Relay (V1)). **Threat-model scope (2026-08-08) — the relay is untrusted for content, trusted for storage.** Confidentiality and integrity hold **against the relay itself**: it stores only ciphertext and wrapped CEKs, and the signed chunk manifest means it cannot substitute bytes undetectably. **Availability cannot**: it necessarily assumes an operational relay that keeps and serves the bytes it accepted, and is not guaranteed against relay deletion, loss, or refusal to serve — that is the trusted-for-storage half of the split, not a defect this spec can close. Against everything outside the relay, availability holds for non-members and for every other participant, but is **not** guaranteed against a **compromised node inside the fetching participant's own trust domain**, which can forge a delivery ack and drive premature refcount-zero GC. V1 defines no node-identity credential to bind against ([security-architecture.md §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature)); the closure for that leg is the [cross-plan-dependencies.md §V1.1+ Cross-Plan Extensions](../architecture/cross-plan-dependencies.md#v11-cross-plan-extensions) Plan-014 row.
- Relay-held payloads must be ciphertext under a per-artifact content-encryption key (CEK) wrapped once per intended recipient **node** (each participant node holds its own durable artifact-encryption key, so every node unwraps independently); the relay must never hold key material sufficient to decrypt.
- Cross-node payload fetch must be authenticated and bound to the fetching `(participant, node)` pair; capability URLs (secret-in-URL fetch) are prohibited.
- Chunk integrity and whole-payload integrity must be verified against the signed publish-event manifest; any mismatch must fail loudly — never silently-wrong bytes.

## Default Behavior

- Newly uploaded attachments default to local artifact storage with visibility derived from session policy.
- Artifact manifests default to storing producer, session, run, type, created time, and visibility class.
- Shared replication defaults to opt-in or policy-driven behavior rather than automatic blind sharing of all local outputs.
- If an artifact should not be visible to all recipients of a shared-visible class, the default v1 behavior is to keep it `local-only` or publish a separate derived artifact under a different visibility class rather than partially redact the original in place.
- Shared-visible artifacts within `max_artifact_relay_bytes` default to eager relay pin at publish; retention defaults to the `default` tier (7-day TTL) unless the publisher selects another named tier.

## Fallback Behavior

- If shared replication is unavailable, the artifact may remain `local-only` with manifest status `pending_replication` or equivalent.
- If the artifact payload is too large for inline timeline rendering, the timeline must show a manifest row and require explicit fetch for the payload.
- If preview generation fails, the artifact remains valid and retrievable as raw content.
- If current policy does not allow sharing the full payload, the system must retain the original artifact under its current visibility class and may publish a separate redacted or summarized derivative artifact instead of mutating the original.
- If an artifact exceeds `max_artifact_relay_bytes`, or the session/participant relay quota is exhausted, the artifact is not relay-pinned: it stays publisher-local with an explicit degraded manifest status ("unavailable while the publisher is offline") — honest degradation, never silent unavailability.
- If an ingested payload fails the magic-byte reconciliation or the media-type allow-list, the ingest is refused and the bytes are **quarantined** rather than stored as a normal artifact: held in an isolated, non-served location outside the CAS under a server-generated name, referenced by no manifest, reachable by no `ArtifactRead`, reaped at `ingest_quarantine_ttl`, and bounded in aggregate by `ingest_quarantine_max_bytes` (oldest evicted first). Quarantine is the fallback for a payload the pipeline cannot classify as safe, not a delivery path.
- If an attachment named by a turn-scoped carrier cannot be resolved or delivered, the turn still proceeds and carries an explicit per-attachment unresolved marker in its declared position. The attachment is never silently omitted, and the marker names which member of the closed cause union applies: `deleted` (the manifest is gone), `local_only_remote` (`local-only` visibility rendered on a remote node), or — for a shared artifact whose payload is not remotely deliverable — the manifest's **own non-`pinned` replication status carried verbatim**: `pending_replication`, `over_cap`, `quota_exceeded`, or `expired` (2026-08-17, PR #341 round 3 — the earlier three-member union forced every relay lifecycle state into `over_cap`'s nearest fit, reporting a false cause for a pending, quota-exhausted, or TTL-expired blob whose remedies all differ; the replication-status arm reuses the `replicationStatus` tokens exactly, so the marker can never disagree with the manifest it describes). **The arm reads the persisted status, which is what makes each of its members reachable** (2026-08-17, ingest-protocol hardening amendment): the marker is rendered from the reading node's own `artifact_manifests` row — never recomputed from live relay state the renderer cannot observe — so a cause is reportable exactly when some writer has recorded it. `pending_replication`, `over_cap`, and `quota_exceeded` are written by the publish path on the publishing node and reach every recipient through manifest-first replication; `expired` is written by the **fetching** node, on either fetch-path refusal that establishes the payload is no longer obtainable from the relay — `artifact.relay_expired` (410) or `artifact.no_access_key` (404), against a row still reading `pinned` — per §Fetch (authenticated; relay-served in V1), where the 404 arm's dominance and the deliberate widening of what `expired` names are set out. Without that writer the `expired` member would name a status no row ever carries — and, worse than an unused token, an attachment made undeliverable by relay expiry would hand the marker renderer a still-`pinned` manifest that matches **no** member of a closed union.

## Interfaces And Contracts

- `ArtifactPublish` must return artifact id and manifest metadata.
- `ArtifactRead` must return manifest plus retrievable payload handle or inline content where appropriate.
- `ArtifactVisibilityUpdate` must require policy and authorization checks.
- `AttachmentIngest` must normalize names, media type, and size metadata, and must run the §Ingest Validation And Payload Bounds (V1) pipeline before persisting anything. Its declared `mediaType` / `sizeBytes` inputs are advisory; the response returns the **derived** values, so a caller that guessed wrong learns the reconciled truth rather than having its guess recorded. It is carried as the `AttachmentIngestInit` / `AttachmentIngestChunk` / `AttachmentIngestComplete` trio per that section's transport binding — a single JSON-RPC frame cannot carry the size cap, so single-call ingest is not a wire shape this spec defines. Every call of the trio is **retry-safe against a lost response**: a replayed `AttachmentIngestChunk` is acknowledged without re-appending, and a replayed `AttachmentIngestComplete` replays its original response verbatim for as long as its stream's registry entry lives (§Ingest Validation And Payload Bounds (V1) stream protocol — 2026-08-17, ingest-protocol hardening amendment).
- `ArtifactDelete` must delete one manifest by id under policy and authorization checks, and must resolve — never leave implicit — the three couplings of §Local Artifact Deletion And CAS Reclaim (V1): the shared CAS payload's refcount, any derivative manifest naming the deleted manifest as its `subject`, and a live relay pin over the same content.
- Attachment references on turn-scoped carriers are typed as `ArtifactId[]` — an ordered list of ids into this spec's manifest space. No carrier accepts an untyped attachment element or an inline byte payload: bytes reach the system only through `AttachmentIngest`, which is where the validation pipeline binds. Element order is caller-declared and preserved; an unresolvable element degrades honestly per §Fallback Behavior rather than being dropped. The two pre-existing driver-boundary carriers (`SteerPayload.attachments` and the `InterventionRequestPayload` `steer` arm) predate this rule as `unknown[]` and retype under their owning plans (registered as Plan-014 CP-014-7); **no V1 carrier may be wired to deliver attachments over an untyped arm** — each arm's retyping is a prerequisite of the first delivery wiring through it, never an opportunistic follow-up.
- Artifact storage uses an OCI-inspired manifest envelope: `{id: ArtifactId, sessionId, runId, digest: SHA-256, size, artifactType, annotations, subject?, createdAt}`.
- `artifactType` is a discriminator: `"file"`, `"diff"`, `"summary"`, `"log"`, `"design"`, `"workflow_output"` — one value per family enumerated above (`summary` covers the plan/summary family) plus `workflow_output`, the Spec-017 workflow phase-output type (`Spec-017 §Output Mode Specification`).
- `subject` field enables artifact linking (e.g., a diff artifact referencing its parent run artifact).
- Cross-node relay methods (additive; see §Cross-Node Artifact Relay (V1)): `ArtifactUploadInit` / `ArtifactUploadChunk` / `ArtifactUploadComplete` (resumable ciphertext-chunk upload to the relay blob store; the received-set is discoverable so an interrupted publisher resumes without re-sending), and `ArtifactFetchAuthorize` (mints a `(participant, node)`-scoped, DPoP-bound, short-lived fetch token — 5–15 min expiry — against session membership) + per-chunk authenticated GETs, then `ArtifactFetchComplete` (the post-verification delivery ack).
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## Ingest Validation And Payload Bounds (V1)

The pipeline binds to the **trust boundary, not to a method name**: every caller-supplied payload that crosses the client↔daemon boundary runs this section's pipeline before anything persists, whichever interface carries it. Two interfaces carry such bytes. `AttachmentIngest` is the primary ingress and the only one that mints the `file` family. `ArtifactPublish` also accepts a caller `payload`, and a boundary-crossing publish runs the pipeline's **content gates over its decoded payload** — steps 3–4 (signature sniff + declared-vs-derived reconciliation), the media-type leg of step 5, step 6's undetermined-signature closure, and steps 7–8 — under the same decoded-byte accounting. The extension leg of step 5 binds filename-bearing ingest only and is **structurally vacuous** for a publish, which carries no filename member: nothing is refused for lacking one, and nothing smuggles past it either, because no publish-supplied string is ever a path component (step 7). Stated per gate rather than as "the same pipeline" (2026-08-17, PR #341 rounds 3–4): a gate whose input does not exist on the shape cannot execute, so the publish-side scope is enumerated instead of overclaimed. Its single-call payload is bounded by the local transport's message ceiling (below), enforced on the **serialized frame** — so the only predictable raw ceiling is the `base64` arm's fixed 4/3 expansion, ≈700 KiB of raw bytes; a `utf8` payload's serialized size is content-dependent, because `JSON.stringify` escaping of quotes, backslashes, and control characters can expand it 2–6×, so ≈1 MB of UTF-8 is the **no-escaping upper bound, never an allowance**, and a caller near the ceiling publishes `base64` for a predictable fit (round 4 corrected the round-2 numerics, which read as a raw-byte guarantee the escape-heavy case does not meet). An over-ceiling frame is refused at the transport before any body byte is buffered; V1 deliberately ships no chunked publish carrier — file bytes above the ceiling take the `AttachmentIngest` trio, and daemon- or engine-internal publishes never cross the wire, so they are unaffected — and a boundary-crossing publish declaring `artifactType: "file"` is **refused and directed to `AttachmentIngest`** rather than validated in a second place — one hardened ingress for file bytes, never two. Payloads produced by daemon- or engine-internal code paths (`diff`, `summary`, `log`, `design`, `workflow_output` from the run engine or daemon services) never cross the boundary: their media types come from the producing code path, and this section does not bind them.

**Transport binding and large payloads.** The local client↔daemon wire enforces a hard 1 MB message ceiling on the `Content-Length` declared by the frame header, **before the body is buffered** ([Spec-007 §Wire Format](./007-local-ipc-and-daemon-control.md#wire-format); shipped as [`local-ipc-gateway.ts#MAX_MESSAGE_BYTES`](../../packages/runtime-daemon/src/ipc/local-ipc-gateway.ts#MAX_MESSAGE_BYTES) — an oversized declaration closes the connection without materializing the payload). The daemon-memory exhaustion this section's step 1 guards against is therefore closed structurally at the transport for any single frame; no request can hand the daemon an unbounded buffer. The functional consequence is normative rather than left to discovery: a payload approaching `max_attachment_ingest_bytes` (default 100 MB) cannot arrive in one frame, so `AttachmentIngest` is carried as an **Init / Chunk / Complete trio** (the §Cross-Node Artifact Relay (V1) upload-leg shape applied to the local boundary): `AttachmentIngestInit` declares the advisory metadata and is refused `artifact.too_large` (413) up front when the declared size exceeds the cap; each `AttachmentIngestChunk` appends to a daemon-spooled temporary file outside the CAS (bounded memory — chunks are written through, never accumulated in RAM), with every chunk's encoded frame respecting the Spec-007 ceiling and the running byte count refused at the cap the moment it is exceeded, deleting the spool (an over-cap stream is refused garbage, not a classified threat — quarantine is reserved for payloads that fail steps 3–8); `AttachmentIngestComplete` runs steps 3–8 over the spooled bytes (the detector reads a bounded leading prefix), step 8's admitting CAS rename committing the payload as the pipeline's final successful act. An abandoned spool (crash or client disappearance mid-trio) is reaped by the same daemon-local `mtime`-clocked reaper that owns quarantine, under the same TTL class — no table, no daemon restart dependency. **The wire is JSON, so chunk bytes ride base64.** Spec-007's serialization is `JSON.stringify`/`JSON.parse` with no binary serialization, so no interface of this spec carries a binary field across the local boundary (2026-08-17, PR #341 round 2): an `AttachmentIngestChunk` chunk is an RFC 4648 §4 base64 string, and every payload-bearing member of this spec's local-wire interfaces is likewise a string — UTF-8 text verbatim or base64 under an explicit encoding discriminator. The per-chunk raw ceiling is `max_attachment_chunk_bytes` (§Bounds — fixed at 512 KiB): the 4/3 base64 expansion plus the JSON-RPC envelope fits the 1 MB frame ceiling by arithmetic (512 KiB × 4/3 ≈ 683 KiB), never by luck. Every byte bound in this section binds the **decoded** bytes — the spooled running count, the caps, and `derivedSizeBytes` all count raw payload, the same plaintext unit the relay quota table binds.

**Stream protocol: admission, sequencing, completion, and termination are contract, not implementation detail** (2026-08-17, PR #341 round 4; extended the same day by the ingest-protocol hardening amendment, which added the completion-record and single-flight rules and made admission a serialized ledger — re-deriving the count from four rules to six). Six rules close the gaps a per-stream cap and an `mtime` reaper cannot see:

- **Admission is bounded in aggregate.** `AttachmentIngestInit` is refused with `artifact.ingest_capacity_exhausted` (429) — transient backpressure, retry later, no stream state created — when the count of open streams has reached `max_active_ingest_streams` or when the sum of open streams' declared totals plus this declaration would exceed `ingest_spool_max_bytes`. Without the aggregate bound, a caller opening many just-under-cap streams and never calling Complete holds spool disk hostage for the full reap TTL; quarantine already carries the equivalent aggregate cap for exactly this attack, and in-flight spools get the same discipline. **Admission is a serialized reserve-then-install ledger, not a check followed by a write** (2026-08-17, ingest-protocol hardening amendment): one critical section covers reading the open-stream count and the reserved-byte total, testing both against their bounds, and installing the new registry entry carrying its reservation. Two concurrent Inits would otherwise each observe headroom and both admit, breaching `max_active_ingest_streams` or `ingest_spool_max_bytes` by up to one maximal declaration per racing caller — a bound checked but not held is not a bound. **A refusal leaves zero state, and the zero is observable through admission rather than through the refused id**: a refused Init mints no `ingestId`, so there is nothing to probe with and this spec never fabricates one to make the check expressible. What is observable is the effect a leak would have on the _next_ caller — releasing one open stream after a count-bound refusal admits the following Init, and a declaration fitting the freed budget admits after a reservation-arm refusal — so a leaked slot or reservation surfaces as a refusal that outlives its cause.
- **The declaration is a reservation, and the reservation is enforced.** A declared total below the cap is never refused at Init and still reconciles downward at Complete (a smaller actual size resolves to the derived value — no refusal), but it is also the stream's spool reservation and per-stream ceiling: a chunk pushing the running decoded count past the Init-declared total is refused `artifact.too_large` (413) with the spool deleted. An unenforced declaration would make the aggregate budget gameable — declare 1 MB, spool 100 MB — so the byte the admission arithmetic counts is the byte the stream may write, no more.
- **Sequencing is replay-idempotent, and violation is terminal.** Chunks carry 0-based strictly-consecutive sequence numbers. The daemon retains the last acknowledged sequence number and the SHA-256 of the last appended chunk: an exact replay — same sequence, same bytes, the ordinary retry after a lost Chunk response — is **acknowledged idempotently without re-appending**, so a client-side retry is always safe. A same-sequence chunk with different bytes, a gap, or a regression terminates the stream: spool deleted, `ingestId` invalidated, the violating call and **every subsequent Chunk or Complete on a terminated, expired, or unknown `ingestId` — and every Chunk on a completed one** — refused with `artifact.ingest_stream_invalid` (409). The one carved exception is a replayed `Complete` on a **completed** stream whose completion record is still held, which replays that record's response verbatim rather than refusing (next rule; 2026-08-17, ingest-protocol hardening amendment). The two codes are the SDK's dispatch contract: 409 means restart from Init, 429 means retry later, and a transport-level failure means retry the same call — which replay idempotency makes lossless for every call of the trio, `Complete` included (next rule).
- **Completion is idempotent, because a lost response must not cost the caller its upload** (2026-08-17, ingest-protocol hardening amendment). Replay idempotency above covers `Chunk`; `AttachmentIngestComplete` is the call whose response is the expensive one to lose — it carries the minted `artifactId` and the derived digest, name, media type, and size, and its work is steps 3–8 over the whole spool. A completion therefore writes a **completion record on that stream's own registry entry**: the response it returned, stamped with the digest the run committed. A `Complete` arriving on a stream that already holds one **replays that response verbatim** — same `artifactId`, same `contentHash` — running no pipeline step again and inserting no second manifest row, which is what makes the retry after a lost response lossless rather than merely safe. Completion still **releases the stream's reservation, its count slot, and its spool** at the moment it commits; what survives is the entry in a completed state holding only the record, so a completed stream can never pin `max_active_ingest_streams` or the reservation budget. `Complete` carries no member beyond the `ingestId` ([api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md#plan-014--artifacts-files-and-attachments)), so a _divergent_ Complete on a completed stream has no wire form to take; the record is stamped with the committed digest regardless, and a stamp disagreeing with the entry's own committed state fails closed to `artifact.ingest_stream_invalid` (409) — defence in depth against a state a daemon-minted single-use `ingestId` makes unreachable, the same idiom as the Fetch step 5 multi-match arm, never a live path. The record **shares the registry entry's lifetime bounds exactly**: in-memory, dying with the process, and evicted with the entry at `max_ingest_stream_lifetime`. **Named residual:** past that bound a retried `Complete` receives the ordinary 409 and the caller re-ingests — CAS dedup stores the bytes once, so the cost is a **second manifest row over one payload**, never duplicated bytes and never a lost artifact. Retaining records longer would require a durable table, which this section deliberately does not mint for a transient.
- **Every call on one stream is single-flight, and eviction takes the same exclusion** (2026-08-17, ingest-protocol hardening amendment). A `Chunk` is a read-modify-write over per-stream state — validate the sequence against the last acknowledged one, append to the spool, advance the running decoded count and the last-chunk digest, acknowledge — so two calls interleaving on one `ingestId` could both validate against the same last-acknowledged value and append twice (breaking the reservation arithmetic and the digest the replay check reads), or let a replay compare against half-updated state. Every call on one `ingestId` therefore executes inside a **critical section keyed by that `ingestId`**: concurrent calls on the same stream queue and run one at a time — the ordinary case being an original and its retry racing after a lost response — while calls on different streams never contend. The **reaper's eviction path takes the same exclusion**, or an over-lifetime sweep could delete a spool a `Chunk` is mid-append into, or release a reservation a `Complete` is mid-commit on; the sweep snapshots candidate entries under the admission ledger, releases it, then takes each candidate's own exclusion and re-checks the entry's state before evicting. So a stream is either being served or being evicted, never both. **Exclusion order is total and acyclic:** per-`ingestId` → the admission ledger → at most one of the per-`storage_path` CAS exclusion (§Local Artifact Deletion And CAS Reclaim (V1)) or the quarantine-directory exclusion (step 9), which are never both held. `Init` takes the ledger alone and no stream exclusion, so it introduces no back edge; `Complete` is the call that makes the order load-bearing, since it is the one holding a stream exclusion while releasing a reservation and then renaming into the CAS.
- **A live stream's lifetime is wall-clock-bounded.** The abandoned-spool reaper clocks `mtime`, and a hostile trickle of keep-alive chunks holds `mtime` young forever — so a stream is additionally bounded by `max_ingest_stream_lifetime` measured from Init — and enforcement does not wait for a call, because a silently-abandoned stream never makes one: every pass of the same daemon-local reaper cadence that owns quarantine expiry and the orphan sweep evicts over-lifetime registry entries, terminating the stream, releasing its reservation and count slot, and deleting its spool, so sixteen abandoned streams cannot pin `max_active_ingest_streams` or the reservation budget past the lifetime bound. An over-lifetime **completed** entry is evicted by the same pass, taking its completion record with it — it holds no reservation, count slot, or spool to release, having surrendered all three at commit, so its eviction bounds only how long a `Complete` stays replayable (2026-08-17, ingest-protocol hardening amendment). A call on an over-lifetime stream that beats the sweep terminates it the same way (the same 409). The daemon-crash case needs nothing new, because the stream registry is in-memory — a stream dies with the process and its spool goes quiescent for the `mtime` reaper.

Because those six families span images, text diffs, log excerpts, and workflow outputs, a strict image allow-list — the shape most upload guidance assumes — would be **wrong here**. The two rules that do transfer, and that this section makes normative, are **the server derives and never trusts** and **bound before persist**. Guidance base: [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) and [OWASP ASVS 5.0.0 §V5 File Handling](https://github.com/OWASP/ASVS/blob/v5.0.0_release/5.0/en/0x14-V5-File-Handling.md) — the cheat sheet is the source for allow-listing, `Content-Type` distrust, signature validation, and filename handling; **ASVS is the source for the count caps**, which the cheat sheet does not cover at all (its only limits text bounds upload _size_ and download _request rate_).

Satisfies ASVS 5.2.4's per-user file-count leg; the byte half is `per_participant_relay_bytes` in §Size, quota, retention (normative defaults; operator-tunable). |
| `ingest_quarantine_ttl` | 48 h | 24–72 h | Matches `incomplete_upload_ttl` — the same "failed transient, reap it" class. |
| `ingest_quarantine_max_bytes` | 1 GB | 100 MB – 10 GB | Aggregate cap on the quarantine directory (2026-08-17, PR #341 round 2): without it, a caller repeatedly submitting just-under-cap payloads that fail steps 3–8 fills the daemon's disk with refused bytes for the full TTL — a denial-of-service the per-payload cap alone cannot see. Floor = one maximally-sized refusal always fits at defaults; eviction is oldest-`mtime`-first (step 9). |
| `max_attachment_chunk_bytes` | 512 KiB | fixed (wire-derived) | Largest raw chunk whose RFC 4648 base64 form plus JSON-RPC envelope fits Spec-007's 1 MB frame ceiling with headroom (512 KiB × 4/3 ≈ 683 KiB; 2026-08-17, PR #341 round 2). Deliberately **not** operator-tunable — the frame ceiling it derives from is not. |
| `max_active_ingest_streams` | 16 | 1 – 128 | Admission cap on concurrently open Init→Complete streams (2026-08-17, PR #341 round 4). At defaults the byte budget below is the binding constraint; the count bounds registry bookkeeping and refuses a pathological stream-open flood with an honest 429 rather than letting it exhaust file handles first. |
| `ingest_spool_max_bytes` | 2 GB | 200 MB – 20 GB | Aggregate reservation budget across all open ingest spools (2026-08-17, PR #341 round 4): Init reserves its declared total against this budget, and the per-stream declared-total ceiling (§Stream protocol) is what makes the reservation arithmetic honest. The in-flight analog of `ingest_quarantine_max_bytes` — without it, many just-under-cap never-completed streams exhaust disk for the full reap TTL. Floor = 2 × one maximally-sized stream at the default per-stream cap, so a maximal ingest always admits beside another in flight — and the relation is normative across the ranges, not a defaults-only accident: `ingest_spool_max_bytes` ≥ 2 × `max_attachment_ingest_bytes`, checked at config load, because an operator raising the per-stream cap over a low budget would turn every maximal Init into a **permanent** `artifact.ingest_capacity_exhausted` — a 429 whose contract promises transience — so the misconfiguration is refused at load, never discovered as an un-retryable retry-later. |
| `max_ingest_stream_lifetime` | 6 h | 1 – 24 h | Wall-clock ceiling on one stream measured from Init (2026-08-17, PR #341 round 4): the abandoned-spool reaper clocks `mtime`, which a trickle of keep-alive chunks refreshes indefinitely, so live-stream tenure needs its own clock. Derivation: a maximal 100 MB payload on a slow 50 KiB/s uplink completes in ≈35 min; 6 h is an order of magnitude of headroom while still bounding a hostile hold on the spool budget. |

`max_attachments_per_carrier` binds the **carrier**, not `AttachmentIngest`: an ingest stream carries exactly one payload end to end — however many chunks deliver it — and has no count to cap, so the bound is enforced on every typed `ArtifactId[]` carrier (§Interfaces And Contracts) at the point the carrier is accepted. Stating it on the ingest stream would be unenforceable there.

**Default allow-list (normative; the step-5 gate's shipped configuration).** Deny-by-default with no shipped list would reject every attachment out of the box, and leaving the list to each deployment would make admission behavior incompatible across them — so the default is stated here and shipped value-for-value in `ingest-limits.ts` (2026-08-17, PR #341 round 2). The **signature-exempt textual subset** (admitted via step 6's UTF-8-proof branch): `text/plain` (`.txt`, `.log`), `text/markdown` (`.md`, `.markdown`), `text/csv` (`.csv`), `application/json` (`.json`), `application/yaml` (`.yaml`, `.yml`), `text/xml` (`.xml` — stored as opaque bytes, never parsed server-side, so the XXE class has no reachable path), and `text/x-diff` (`.diff`, `.patch`). The **signature-verified binary set**: `image/png` (`.png`), `image/jpeg` (`.jpg`, `.jpeg`), `image/gif` (`.gif`), `image/webp` (`.webp`), `application/pdf` (`.pdf`), `application/zip` (`.zip`), and `application/gzip` (`.gz`, `.tgz` — archives stored opaque per §Scope limits). `image/svg+xml` is **deliberately absent from the default**: it is the one image type that is also a scriptable document (the cheat sheet's named XSS carrier), and its exclusion is a recorded decision an operator may reverse, not an oversight. Operators may **widen or narrow**: the deployment owns its risk posture, and an override **replaces the list wholesale** — no merge semantics, so the effective list is always exactly what the operator (or this default) states.

### Pipeline (ordered; each step is a gate, not a hint)

1. **Size cap — bound the bytes first.** Refuse a payload exceeding `max_attachment_ingest_bytes` with `artifact.too_large` (413) **before** reading it into memory or invoking any parser. The bound binds three times, earliest first: the transport's 1 MB frame ceiling refuses an oversized declaration before any body byte is buffered (§Transport binding above — the structural leg); `AttachmentIngestInit` refuses a declared total above the cap before a chunk is accepted; and the spooled running count refuses at the cap during accumulation regardless of what Init declared. This ordering is load-bearing, not stylistic: signature detection is itself untrusted-input parsing, and bounding first is what keeps a malformed payload from reaching it.
2. **Count cap.** Refuse a carrier exceeding `max_attachments_per_carrier` with `artifact.too_many_attachments` (413) at carrier acceptance, before any element is **bound or delivered**. The cap is a carrier-integrity bound, not a retroactive ingest bound: the carrier names already-minted `ArtifactId`s, so refusal leaves no partial carrier state — no attachment binding, no delivery, no marker — while artifacts minted by earlier `AttachmentIngest` calls are unaffected and simply follow their own lifecycle (§Local Artifact Deletion And CAS Reclaim (V1), session sweep included). They are session artifacts, not orphans.
3. **Magic-byte sniff — derive the type from the bytes.** Determine the media type from the payload's own leading signature. The caller's declared `mediaType` is a hint used only to _narrow_ the expected signature — never to widen acceptance, and never recorded when it disagrees with the derived value.
4. **Reconcile declared against derived.** A declared type that contradicts the derived type is a refusal (`artifact.unsupported_media_type`, 415), not a silent correction — an attacker-declared type that the server quietly "fixes" is exactly the double-extension and `Content-Type`-spoof class the cheat sheet names. A declared type absent altogether is fine; the derived value stands.
5. **Extension and media-type allow-list.** Both the filename extension (after full decoding, so a double extension or an embedded null byte cannot smuggle one past) and the derived media type must be allow-listed, and the two must agree. The allow-list is **deny-by-default** and ships the normative default of §Bounds (operator-overridable, wholesale); block-listing is prohibited, per the cheat sheet's "blocking specific extensions is a weak protection method on its own."
6. **Undetermined signature — the fail-open to close.** Signature detection cannot classify most free-form text formats, so an undetermined result is **not** evidence of safety. A payload whose signature is undetermined is accepted only when its declared type is in the allow-list's explicitly marked **signature-exempt** subset (the text formats the operator has chosen to accept) **and** the bytes pass a UTF-8 well-formedness check; otherwise it is refused. Treating "detector returned nothing" as "nothing wrong" is prohibited. **The classification rule for this branch is stated rather than implied**, because bytes alone cannot distinguish textual subtypes: what the bytes prove is UTF-8 well-formedness, and the recorded media type is the **declared subtype, admitted under the exemption** — valid only inside the signature-exempt subset and only with an agreeing extension (step 5). The manifest and `derivedMediaType` carry that admitted value; the claim this section makes for the branch is "allow-list-bounded declaration over byte-proven UTF-8", never "subtype derived from the payload".
7. **Path validation + CAS address derivation.** The stored payload is keyed by its SHA-256 CAS address (§Implementation Notes) — a server-derived name, derived at this step; the rename that commits the payload under it into the CAS is **step 8's admitting act**, never this step's, so bytes do not enter the CAS ahead of the final gate — and **no caller-supplied string is ever a path component**. This discharges the cheat sheet's random-filename and path-traversal requirements — and ASVS 5.3.2's "use internally generated or trusted data instead of user-submitted filenames" — **structurally rather than by sanitization**: there is no caller-influenced path to traverse. The caller's original filename survives as manifest metadata only, length- and character-bounded before it is recorded, and is never used to open, create, or serve a file.
8. **Antivirus hook.** The pipeline exposes a **scanner seam** at this point, after the payload is bounded and typed and before it is committed as a readable artifact. V1 ships the seam and its refusal path, **not a bundled scanner**: the default configuration is no scanner, and an operator that configures one gets a verdict that either admits the payload or refuses it with `artifact.scanner_rejected` (422) and routes the bytes to step 9 — its own code (2026-08-17, PR #341 round 2), because the payload's type was allow-listed and reconciled before the seam ran, so reporting a content verdict as `artifact.unsupported_media_type` would misdirect the remedy. This is deliberately a hook rather than an engine — bundling a scanner is a deployment and licensing decision this spec does not make — and it is what lets a deployment satisfy ASVS 5.4.3 without the spec pretending V1 scans anything by default. **Admission itself lands here** (2026-08-17, PR #341 round 2): on an admitting verdict — or in the default no-scanner configuration, where the seam is a pass-through — the CAS rename of the step-7-derived address commits the payload as a readable artifact, the pipeline's **final successful act**. A rejecting verdict therefore routes bytes that never entered the CAS to step 9, with nothing to un-commit — which is what makes this step's before-commit clause and step 9's outside-the-CAS rule literally true for a scanner refusal.
9. **Quarantine on failure**, per §Fallback Behavior: bytes that failed steps 3–8 are held outside the CAS, referenced by no manifest, unreachable via `ArtifactRead`, and reaped at `ingest_quarantine_ttl`. The quarantine location is a daemon-local directory outside every served path, and the TTL clock is the quarantined file's own filesystem `mtime` — deliberately **not** a database row. **Quarantine entries are stored under server-generated names** — the payload's content digest, or a random identifier when hashing is what failed — extending step 7's no-caller-string-in-any-path-component rule to the quarantine writer (2026-08-17, PR #341 round 2): a traversal-shaped or null-byte filename that fails step 5 reaches quarantine as bytes, never as a path, and the caller's original filename is **not persisted with quarantined bytes at all** — nothing references quarantine by design, and the refusal response already told the caller what was refused. The directory is additionally bounded in aggregate by `ingest_quarantine_max_bytes` (§Bounds): a new entry that would breach the cap first evicts existing entries oldest-`mtime`-first until it fits, and one that cannot fit even into an emptied quarantine is deleted rather than held — the refusal outcome is identical either way; only forensic retention degrades, and it degrades against the oldest evidence first. **Admission to the directory is serialized as reserve-then-install, because the cap is a shared budget and a shared budget cannot be checked outside the mutation that spends it** (2026-08-17, ingest-protocol hardening amendment): one critical section keyed by the quarantine directory covers measuring the current aggregate size, evicting oldest-`mtime`-first until the incoming entry fits, reserving that entry's byte count, and installing its bytes. Concurrent content refusals otherwise each measure headroom before any of them writes, and the directory overshoots `ingest_quarantine_max_bytes` by up to one payload per racing refusal — at the default per-payload cap, precisely the unbounded-disk outcome the aggregate cap exists to prevent, and reachable by an attacker who simply submits refusable payloads in parallel rather than in series. The reaper's TTL pass takes the same exclusion, so a reap cannot delete an entry mid-install or race the eviction loop's own accounting; the reservation is released when the install completes, since the installed file's size is thereafter what a measurement sees. Serialization is affordable here because quarantine is the refusal path — it is never on the accepted-ingest hot path, and a content refusal has no latency budget worth protecting. A quarantined payload's defining property is that nothing references it; minting a table to track it would contradict that property, put a durable record of attacker-supplied metadata in the local schema, and move the local-schema census for a transient. The reaper is therefore a directory scan over `mtime`, and it is owned by the same daemon-local component that writes the quarantine — **not** by the relay's control-plane TTL sweep, which governs pinned blobs on the other side of the node boundary and never sees this directory. **Named residual:** an `mtime` an operation perturbs (a copy, a restore, an image rebuild) resets a quarantined payload's apparent age and delays its reap — and, because eviction orders by the same clock, mis-ages it in the eviction queue, so a touched entry can outlive genuinely newer evidence. This is an availability-of-disk-space and forensic-retention-order cost, never a confidentiality one — the bytes remain outside the CAS, referenced by no manifest, and unreachable via `ArtifactRead` for as long as they persist — and it is the accepted side of the trade against keeping a durable, queryable record of attacker-supplied metadata in the local schema.

### Consumers, and what they may assume

[Spec-017](./017-workflow-authoring-and-execution.md) human-phase uploads consume this pipeline unchanged and reimplement no part of it (Spec-017 I6). Its seven named legs map onto the steps above one-to-one: size cap (1), extension allow-list (5), magic-byte sniff (3), storage rename (8 — the admitting act), path validation (7), antivirus hook (8), quarantine-on-fail (9). A consumer adding a second validation path of its own is the defect this mapping exists to prevent — one pipeline, one place to harden.

The upload battery that consumers test against resolves here as follows. **Oversize** fails step 1. **Mismatched `Content-Type`** fails step 4. **Polyglot** is answered honestly rather than overclaimed: steps 4–5 refuse every declaration/derivation/extension **disagreement**, which is the smuggling half of the class — but a polyglot crafted so its leading signature, declaration, and extension all agree passes both steps while remaining parseable as a second format, and signature checking cannot exclude it (§Scope limits below: necessary, not sufficient). V1's defense for the agreement-consistent polyglot is the serving posture, not the detector: payloads are explicit-fetch downloads, never rendered inline as trusted markup, so a second interpretation has no in-product execution surface — and the step-8 scanner seam is where an operator adds content inspection. Format-specific validation joins under the same §Scope limits criterion as image rewriting (the first inline-rendered family). **Zip bomb** and **symlink traversal** — including the broken-fix class of [CVE-2025-66626](https://nvd.nist.gov/vuln/detail/CVE-2025-66626) — are not defended against so much as **made unreachable**: V1 never unpacks an archive (below), so no entry is ever extracted, no path is ever joined, and no symlink is ever followed. That is a stronger answer than a traversal check, and it is the reason the answer is stated rather than left to a validator.

### Scope limits, stated rather than implied

- **Magic-byte verification is necessary, not sufficient.** The cheat sheet is explicit — signature checking "should not be used on its own, as bypassing it is pretty common and easy" — and ASVS 5.2.2 lists it as one member of a set that also includes image rewriting and format-specific validation. V1 ships bounds, reconciliation, the allow-list, and the scanner seam, and claims exactly that much.
- **V1 does not decompress or introspect archive interiors at ingest.** An archive is stored as opaque bytes under its own signature. This is a deliberate scope choice with a security dividend: not unpacking means the ASVS 5.2.3 archive-entry-count and uncompressed-size class, and the zip-slip and symlink classes with it, have no reachable path here. It also means the type detector must not be pointed at container interiors — container-introspecting detectors have shipped decompression-bomb denial-of-service of their own.
- **Detection runs under a time and byte bound.** Signature detection is untrusted-input parsing and is treated as such: the size cap of step 1 applies before it, and detection itself is bounded by a timeout, so a malformed payload that sends a parser into an unbounded loop fails the ingest rather than the daemon.
- **Image rewriting, content-disarm-and-reconstruct, and pixel-flood limits (ASVS 5.2.6) are V1 non-goals**, and V1 ships **no default antivirus engine** — step 8 is a seam, not an implementation. They are named here so their absence is a recorded decision rather than an oversight. The criterion for pulling any of them into a later version is the first artifact family that is rendered inline in a browsing context without a download step — until then the payload is served as an explicit fetch, never executed or rendered as trusted markup.

## Local Artifact Deletion And CAS Reclaim (V1)

`ArtifactDelete` deletes one manifest by id. It is the local-storage counterpart of §Delete (refcount + TTL + crypto-shred), which governs the **relay** copy only; the two are separate lifecycles over the same content and this section does not restate the relay half.

**Payload reclaim is refcounted, and the refcount is derived — not stored.** CAS dedup means several manifests can share one stored payload (§Implementation Notes: "keyed by SHA-256 for automatic deduplication"), so deleting a manifest must never delete bytes another manifest still names. The refcount for a stored payload is the number of surviving payload references to that storage key; reclaim is permitted **only** when that count reaches zero — that direction is absolute, bytes named by a surviving manifest are never unlinked — and initiates at zero, with completion eventual rather than instantaneous: a post-commit unlink that fails degrades to the sweep-owned `reclaim_pending` disposition (below), so zero-referenced bytes may persist until the next sweep pass, never the reverse. Deriving the count from the existing reference rows rather than maintaining a counter column is deliberate: a stored counter is a second source of truth that drifts on every crash between the row write and the counter write, and drift in this direction destroys data.

**Reclaim is crash-safe by ordering, not by pretending one transaction spans two stores.** A SQLite transaction cannot make a filesystem unlink atomic with the row deletions it accompanies, so the direction of failure is chosen deliberately: the row-deletion transaction commits **first**, and the payload unlink runs **strictly after commit**. A crash between the two leaks bytes — an orphaned CAS entry referenced by no row — and never the reverse: no surviving manifest ever points at missing bytes. The leak is bounded and self-healing via an idempotent **orphan sweep** that unlinks CAS entries with zero payload-reference rows — run at daemon start **and periodically thereafter on the same daemon-local reaper cadence that owns quarantine expiry** (2026-08-17, PR #341 round 4: a boot-only sweep leaves a failed reclaim's plaintext on disk for the lifetime of a long-running daemon). An ENOENT on the unlink path is success, so the sweep and a racing delete cannot fight, and re-running the sweep is always safe. The same sweep is the durable retry for a post-commit unlink that fails with a non-`ENOENT` error (`EACCES`, `EIO`): no tombstone row is minted, because the zero-reference predicate the sweep derives from the surviving rows **is** the durable reclaim record — the failed entry is simply an orphan the next pass retries — and the delete response reports the disposition honestly (`payloadDisposition: "reclaim_pending"`, [api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md#plan-014--artifacts-files-and-attachments)) rather than claiming a reclaim that did not happen. A session purge proves completion the same way: the sweep predicate over surviving rows, not a per-delete success bit.

**Reclaim is also concurrency-safe, by per-key exclusion — ordering alone is not** (2026-08-17, PR #341 round 2). Crash-safe ordering says nothing about a live writer: CAS dedup means a same-hash publish or ingest can land between a delete's commit and its post-commit unlink, observe the still-present CAS entry, insert a fresh payload reference to it — and then the unlink destroys bytes a surviving manifest names. The daemon is the CAS's only writer and reclaimer (single-process ownership), so the fix is an in-process critical section keyed by storage key: a writer holds the key's exclusion across its CAS existence check and payload-reference insert, and a reclaimer holds it across refcount derivation and unlink — **re-deriving the refcount inside the exclusion, after the row-deletion commit, and aborting the unlink on any count above zero** (a raced-in reference wins; the bytes stay). The boot-time orphan sweep takes the same per-key exclusion, so it is safe to run concurrently with the accepting surfaces rather than depending on startup ordering: a writer whose reference lands before the sweep's in-exclusion re-check saves the entry, and one arriving after the unlink misses the existence check and writes fresh bytes. Either interleaving ends with every manifest over present bytes; the exclusion removes the third.

**Deleting a manifest that is another artifact's `subject` is refused.** Derivatives point at their source (§State And Data Implications), and a dangling `subject` would break the provenance chain that makes a redacted derivative auditable. The refusal names the referencing manifests so the caller can delete the derivatives first, or keep the source — **bounded** (2026-08-17, PR #341 round 3): the details list carries at most the first 50 referencing ids ordered ascending by artifact id (deterministic across retries) plus the total count, because an unboundedly-derived source must not make its own 409 undeliverable by overflowing the transport's 1 MB frame; the full set remains enumerable via the read path. Nulling the derivative's `subject` is rejected as the alternative: it silently converts a derivative into what looks like an original, destroying exactly the provenance the derivative-not-mutation rule exists to preserve.

**A derivative's `subject` is session-scoped, resolved at publish** (2026-08-17, PR #341 round 2). `ArtifactPublish` resolves a request's `subject` within the request's session only; an id that does not resolve there — including a manifest that exists in another session — is refused `artifact.not_found` (404), the same code as any unresolvable artifact reference, because outside the session's scope the manifest does not exist for this caller. The consequence is structural: every derivative chain is confined to one session, so the `artifact.delete_blocked` referencing set never crosses sessions and the session-deletion sweep below never meets a foreign referent — its completeness is by construction, not by cross-session search.

**A live relay pin blocks nothing and is not orphaned.** The relay copy's lifecycle is refcount-plus-TTL on the relay side; deleting the local manifest deletes the publisher-retained `relay_cek_ciphertext` with it (the [Spec-022](./022-data-retention-and-gdpr.md) artifact-payload posture already states the retained CEK "dies with the manifest row"). The consequence is normative and must be stated rather than discovered: after a local delete, **the publisher can no longer re-publish that artifact** — the re-wrap source is gone — so the late-join `artifact.no_access_key` remedy is unavailable for it. Already-pinned recipients are unaffected and fetch normally until the blob's own refcount-zero or TTL. `ArtifactDelete` must surface this consequence rather than deleting silently — and the signal is grounded in **local state alone** (2026-08-17, PR #341 round 3): the response reports that the delete destroyed a retained re-wrap capability (the manifest's `relay_cek_ciphertext` existed and died with the row), named `rePublishForeclosed` on the wire, **not** a claim that a relay pin is currently live — whether the relay still holds the blob is the relay's own refcount/TTL lifecycle, which the daemon neither tracks after publish nor queries at delete time, so a member spelled "pin lost" would assert a truth the daemon cannot derive once the relay has GC'd or expired the blob.

**Session deletion disposes local artifacts with the session.** Deleting a session deletes its `local-only` artifacts and their manifests in one row-deletion transaction, then reclaims every payload whose derived refcount reached zero — the unlinks running strictly after commit under the same crash-safe ordering, so a crash mid-sweep leaves rows consistent and at worst leaks payloads the boot sweep reclaims. Shared-visible artifacts follow the same local path; their relay copies are governed by §Delete (refcount + TTL + crypto-shred) and are not deleted by this operation. Participant erasure is a different sweep with a different key and is unchanged by this section (§Delete step 9). **The trigger is stated honestly rather than implied** (2026-08-17, PR #341 round 2): no V1 operation deletes or purges a session — archive/close retains data, participant erasure is the different sweep above, and the one documented session-data-disposal operation, session purge ([Spec-022 §Interfaces And Contracts](022-data-retention-and-gdpr.md#interfaces-and-contracts): `POST /sessions/{id}/purge`, `archived → purge_requested → purged`), is V1.1 by Plan-022's documented deferral, its `gdpr.sessionPurge` stub reserved in V1 — so this sweep lands as a callable, session-keyed function with no V1 production caller, exercised by its own tests (the same deliberately caller-dormant shape as the carrier validator, recorded rather than discovered). Plan-014 registers **CP-014-8** binding that V1.1 purge handler — the named first caller — to wire this sweep as its artifact leg as a precondition of shipping, instead of re-discovering it. Whether the artifact leg deletes manifests outright or first reduces them to non-PII stub rows is that implementation's adjudication under Spec-022's audit-stub retention; what it may not do is complete with the session's artifact payload bytes still in the CAS, because artifacts are session work product and their payloads are exactly the PII-bearing class purge exists to destroy.

## Cross-Node Artifact Relay (V1)

Shared-visible artifacts are fetchable from any participating node **even while the publishing node is offline**. This is a V1 required property ([ADR-015 amendment 2026-07-08](../decisions/015-v1-feature-scope-definition.md#amendment-2026-07-08-v11-deferred-features-3--2-cross-node-shared-artifacts-pulled-into-v1) — cross-node shared artifacts pulled forward from V1.1), **scoped 2026-08-08 to an honest-node threat model**: because V1 ships no node-identity credential, this availability property is guaranteed only against parties outside the participant's own trust domain — a **compromised node of the same participant** can forge a delivery ack and drive premature GC (Fetch step 6), and can attest an attacker-held artifact key under a sibling's `node_id`, locking the honest sibling out of artifacts it is entitled to (Publish step 3). **Both residuals are availability- and attribution-class, not confidentiality** (reclassified 2026-08-08): an attached sibling is already an intended recipient under its own attested key, so neither residual widens plaintext reach. Neither is remediable in V1, neither weakens the cross-participant guarantees, and both close on the §V1.1+ Cross-Plan Extensions Plan-014 row. Manifest-first replication is unchanged; the payload leg is an **eagerly pinned relay store-and-forward of chunked, participant-encrypted, digest-addressed ciphertext**. Publisher-online-only fetch is rejected (fails the offline-availability property); lazy cache-on-miss relay population is rejected (a blob no remote peer fetched before the publisher went offline is simply unavailable — the Matrix remote-media-cache gap). The relay is trusted to hold bytes, never to read them: it stores ciphertext and wrapped keys only — the same trust model as the existing E2E-encrypted event relay ([ADR-010](../decisions/010-paseto-webauthn-mls-auth.md)).

### Publish (eager pin)

1. The publishing daemon generates a random per-artifact **content-encryption key (CEK)** and encrypts the payload with XChaCha20-Poly1305 — the existing relay payload cipher — under a **derived, never random, nonce** (a versioned domain-separated hash of the plaintext CAS digest): the CEK is single-use so nonce determinism is safe (and accidental CEK reuse across different plaintexts derives different nonces, so no keystream reuse), and it makes encryption **reproducible** — the publisher can reconstruct byte-identical ciphertext, chunks, and digests from the CAS plaintext plus the retained CEK (below), which is what lets a re-publish after the relay copy was GC'd re-upload the same digest and re-emit identical signed-manifest content. AEAD is normative but **not sufficient**: a non-committing cipher (e.g. AES-CTR) admits multi-plaintext key substitution by a malicious sender (the Matrix "Missing Salamanders" class), and ChaCha20-Poly1305-family AEADs are themselves **not key-committing** — one ciphertext can authenticate under two different keys ([Len et al., partitioning oracles, USENIX Security 2021](https://www.usenix.org/conference/usenixsecurity21/presentation/len); [Albertini et al., USENIX Security 2022](https://www.usenix.org/conference/usenixsecurity22/presentation/albertini)). The publish therefore also derives a **key commitment** — `cekCommitment = SHA-256("ais/artifact-cek-commit/v1" ‖ CEK)` — carried in the signed manifest (step 2); every recipient MUST verify their unwrapped CEK against it **before decrypting** (step 6), so one relay ciphertext commits every recipient to one CEK — and, with the post-decrypt CAS check, to one plaintext. The publishing daemon **retains the CEK locally** — master-key-wrapped on the manifest row (`relay_cek_ciphertext`, [Spec-022](./022-data-retention-and-gdpr.md) custody) — for the artifact's shareable lifetime: re-publish (step 3) re-wraps this same CEK for new recipients, since the pinned ciphertext is under it and the relay holds only recipient-wrapped copies. The retained copy is deliberately **not** a per-participant erasure target — it sits sealed beside the CAS plaintext it encrypts and grants nothing the publishing machine does not already hold; it dies with the manifest row (artifact deletion) or with the daemon master key (the [Spec-022 §PII Data Map](./022-data-retention-and-gdpr.md#pii-data-map) artifact-payload posture).
2. The ciphertext is split into fixed **8 MiB chunks** (`artifact_relay_chunk_bytes`); each chunk is SHA-256-hashed. The daemon builds a **signed chunk manifest** — ordered `{index, ciphertextChunkSha256, size}` rows plus the whole-payload plaintext SHA-256 (the CAS digest already in the artifact manifest), the whole-ciphertext SHA-256, and the `cekCommitment` (step 1) — carried inside the signed, E2E-encrypted `artifact.published` event. Binding the digests to the signed event (blob → event, not merely blob → itself) means a malicious relay cannot substitute a different-but-internally-consistent blob.
3. The CEK is **wrapped once per intended recipient node** — to each attested **durable artifact-encryption X25519 public key**, never to the session-ephemeral X25519 keys (those are zeroed at session end per [ADR-010](../decisions/010-paseto-webauthn-mls-auth.md), so a CEK wrapped to them would be orphaned by any recipient restart and the offline-fetch guarantee would fail exactly when it matters). Each participant node generates its artifact-encryption keypair **at its first session attach** (once per node — the key is durable across sessions; lazy at-first-fetch generation is prohibited, because a node attached at publish time but never yet needing a key would silently fall out of the wrapped-key set and be demoted to the late-join path, voiding the offline guarantee for a node that was present), holds the private half under the [Spec-022](./022-data-retention-and-gdpr.md) daemon master-key custody (the daemon-local `artifact_encryption_keys` store), and announces the public half as an **artifact-key attestation** — signed by the participant's long-term Ed25519 identity key over `session_id ‖ node_id ‖ artifact_public_key` — sent **as part of joining the relay-crypto layer, immediately after the ADR-010 pairwise handshake with each peer** (attestation is a join-sequence obligation, not a lazy exchange: any node whose attach completed before a publish is in that publish's recipient set, the publishing node itself excepted; only a genuinely concurrent attach-vs-publish race falls to late-join semantics), carried as an **application-level payload inside the existing pairwise ciphertext envelope** ([Spec-008 §Relay Connection Lifecycle](./008-control-plane-relay-and-session-join.md#relay-connection-lifecycle) frame structure — no new frame message type, no `SessionKeyBundle` change; the relay still forwards opaque ciphertext and learns nothing). Publishers cache **the latest attestation per `(participant, node)`** — never a session-frozen first-seen snapshot: **rotation immediately re-attests the new active key to every session peer over the same pairwise channels** (the identical signed-attestation payload; the channel is ordered and authenticated, so last-received-wins per sender is sound, and every reconnect handshake re-exchanges current attestations before the reconnecting peer can publish). An unattested or signature-invalid peer key is never wrapped to. **Attestation binds to the participant, not the node (scoped 2026-08-08):** the verifier's check is that the attestation is signed by _a_ long-term Ed25519 identity key registered to that participant — and a participant may have **several**. Each workstation independently runs its own custody ladder and holds **its own** identity key, registered separately with the control plane, so one participant carries multiple `bound` identities ([trust-and-identity.md §Edge Cases](../domain/trust-and-identity.md#edge-cases) "Multiple workstations under the same participant"; [ADR-021](../decisions/021-cli-identity-key-storage-custody.md) for the per-workstation CLI ladder — no private key is ever shared or copied between nodes). Nothing binds the **signing identity** to the `node_id` being attested, which is merely a signed-over field with no node credential behind it. So **any participant-authorized registered identity** — including one on a compromised node of that participant — can attest an attacker-held X25519 key under a _sibling_ node's `node_id`, and, since publishers accept the latest attestation per `(participant, node)` regardless of which of the participant's identities signed it, later publishes wrap that node's CEK to a key the attacker holds. **The harm is availability and attestation integrity, not confidentiality** (reclassified 2026-08-08; an earlier draft called it a confidentiality exposure and was wrong): an _attached_ sibling is already in the intended-recipient set above — the publisher's other nodes are ordinary recipients — so it already holds that artifact's CEK under its **own legitimate** attested key, and the spoof buys it **no plaintext it did not already have**. Plaintext reach by an attached, authorized node of the participant is **participant-granularity sharing working as designed** (visibility is class-based, per §Required Behavior; no node-scoped visibility is defined anywhere in V1) — a compromised-endpoint problem, not a protocol residual. What the spoof does cost is **(a) victim-node lockout** — the victim's recipient row now carries a CEK wrapped to a key that node does not hold, so the honest node cannot decrypt an artifact it is entitled to — and **(b) corrupted attestation and delivery attribution**. Cross-participant confidentiality is untouched: forging the attestation requires an identity key registered to that participant. Closure is the [cross-plan-dependencies.md §V1.1+ Cross-Plan Extensions](../architecture/cross-plan-dependencies.md#v11-cross-plan-extensions) Plan-014 row, which restores **attestation integrity** (binding the signer to the `node_id` it attests) — deliberately **not** node-level content exclusion, which no named V1.1 primitive defines. Re-attestation is what keeps the retired-key purge rule sound against late wraps: attestations and uploads ride the same session relay connection, so a publisher that can reach the relay has either already received the re-attestation or is racing it by transport-scale seconds — without it, a stale session-lifetime cache could mint fresh recipient rows under a retired thumbprint arbitrarily late, and their TTL would outlive the key's purge bound (see Rotation below). The wrapped-key set — one entry per attested `(participant, node)`, each carrying the wrapping key's **thumbprint** so the fetching daemon selects the right private key after restart or rotation — is **uploaded to the relay with the blob**, becoming the `artifact_relay_recipients` rows — the wrapped CEKs' **only** store; each participant's wrapped CEK is returned to them by `ArtifactFetchAuthorize` (step 5). **Within one `(ciphertext_digest, participant_id)` the key thumbprint is unique**, enforced by a relay-side uniqueness constraint on `(ciphertext_digest, participant_id, key_thumbprint)`. This is what makes a thumbprint a usable mint selector at step 5 — it makes thumbprint→node injective inside the caller's own rows — and it is satisfied by construction in every honest case: each node generates its own artifact-encryption keypair and no private key is ever shared or copied between nodes ([trust-and-identity.md §Edge Cases](../domain/trust-and-identity.md#edge-cases)), so two of a participant's nodes cannot legitimately present one thumbprint. The **one** state that violates it is the attestation spoof already named in this step — an attacker-held key attested under a sibling's `node_id` while the attacker's own honest row carries the same key. Its disposition is normative: the relay validates the declared recipient entries for a duplicate `(participant, thumbprint)` **before writing any row**, drops **both** colliding entries fail-closed (the relay cannot adjudicate which is the honest node, and guessing would complete the lockout the spoof is attempting), pins the blob for every non-colliding recipient, and returns the dropped entries to the publisher as an explicit per-entry rejection so the conflict surfaces rather than vanishing. The affected nodes then see `artifact.no_access_key` (404) with its documented re-publish remedy. **Failing the whole publish is rejected**: it would hand any participant-authorized identity a denial-of-publish primitive over every subsequent artifact in the session — strictly worse than the availability residual it would purport to address. The constraint is therefore a hardening with an enumerated failure response, and the uniqueness index is the durable backstop behind a check the write path already makes. **The screen covers surviving rows, not the submitted set alone** (2026-08-17, PR #341 round 2): an incoming entry can also collide with a row an **earlier** publish left at rest — most plainly a re-pin adding an entry for one node whose thumbprint already tags a surviving, undelivered row for a sibling node, the at-rest face of the same spoof (an honest collision is impossible: keys are generated per node and never shared). The disposition is asymmetric by design: the **incoming entry alone is rejected, per-entry** — reported to the publisher exactly like an intra-set drop — and the surviving row is untouched, because that row is a standing prior grant whose deletion would hand any participant-authorized identity a revocation primitive over the victim's existing access, converting an attempted lockout into an achieved one. The intra-set both-drop rule deliberately does not transfer: there the relay faces two unproven entries and cannot adjudicate; here it faces one unproven entry against one standing grant. The publish still never fails, and the index stays the arbiter at write time — a violation surfacing at the write itself (a concurrent publish racing the screen) resolves to the same per-entry rejection, never a transaction abort surfaced as a failed publish. **Re-pinning after rotation UPDATEs in place, never inserts:** the recipient row is keyed `(ciphertext_digest, participant_id, node_id)`, so a re-publish to a node that has rotated writes the new `wrapped_cek` and `key_thumbprint` onto that node's existing row (an upsert on the primary key). An insert would violate the primary key, and a second row for the same node would violate the per-node delivery refcount of I-014-7. The retained retired key (Rotation, below) therefore covers exactly the rows no re-publish has touched — which is precisely the set whose blobs are still pinned under it. The set deliberately does **not** ride the durable `artifact.published` event — a deliberate divergence from the Signal/WhatsApp/Wire key-in-event precedent: the event log is immutable, replayable session history, so an event-carried key set could never be crypto-shredded, while the relay row is the participant's one erasable key-access record — exactly what makes the CP-014-2 hard-DELETE a true shred. The event carries the signed `cekCommitment`, never the keys. The relay never sees the CEK or plaintext (wrapped keys are opaque to it); one stored blob serves every participant, and each participant's access is independently revocable by crypto-shred (envelope-encryption precedent: AWS KMS data keys; one-ciphertext-plus-per-recipient-key precedent: Wire/Signal attachment fan-out). The **intended-recipient set is the attested `(participant, node)` set at publish time, minus the publishing node itself** — the publishing node holds the plaintext and never fetches, so a self-row could never ack and would hold every blob's refcount hostage to full TTL, silently defeating the store-until-delivered economics; the publisher's **other** nodes are ordinary recipients. The set is membership-epoch-scoped decryptability, the same boundary the pairwise-encrypted event log gives late joiners (they cannot decrypt pre-join events either — the event-log half of that boundary now carries its own peer re-publication leg, [Spec-008 §Peer History Backfill On Join (V1)](./008-control-plane-relay-and-session-join.md#peer-history-backfill-on-join-v1), which generalizes this section's **publisher-scoped** re-publish mechanism to the session event stream — there the originating daemon is likewise the only party that can re-serve an event, because a receiver's re-sequencing puts the event outside the origin's signature; cross-reference only — nothing in this section's artifact contract changes) and the deliberate posture of group-messaging protocols generally ([MLS RFC 9420](https://www.rfc-editor.org/rfc/rfc9420): new members cannot read pre-join ciphertext). A member or node joining after publish gains access via publisher **re-publish** while online — `ArtifactUploadInit` on an already-pinned digest is an idempotent CAS re-pin that adds recipient rows without re-uploading chunks **and refreshes the blob's TTL lease** (step 4; a blob already refcount- or TTL-GC'd re-uploads **byte-identically** from the CAS plaintext + the retained CEK — step 1's derived nonce makes re-encryption reproducible, so the re-publish remedy works even after the relay copy is gone), **paired with a re-emitted `artifact.published` event into the current membership epoch** carrying the identical signed manifest content (idempotent by digest): relay recipient rows alone are never an access grant, because the verification material — `chunkManifest`, `cekCommitment` — rides E2E events and the joiner cannot decrypt the pre-join original — and until then sees an explicit no-access-key state — the reserved `artifact.no_access_key` (404) error-contract row, deliberately distinct from `artifact.fetch_unauthorized` (403) so clients surface the re-publish remedy rather than an auth failure — never a silent one. Relay-held wrapped CEKs are deliberately **not** forward-secret against artifact-key compromise (durable availability cannot ride restart-zeroed keys); the exposure is bounded by the TTL ceiling (30 d), refcount GC, and crypto-shred. **Rotation retires, never replaces:** a rotated-out artifact key is retained (keyed by its thumbprint, marked retired, never used for new wraps) until every relay row wrapped to that thumbprint is delivered or TTL-expired, because a within-TTL blob pinned to the retired key must stay fetchable while the publisher is offline. That predicate is deliberately **not** evaluated by asking the relay: the daemon purges a retired key at `retired_at + 30 d + a 48 h skew margin` — the `extended`-tier TTL ceiling bounds how long any row wrapped to it can outlive retirement on the **relay's** clock, and the margin absorbs daemon-vs-relay clock skew (a fast local clock must never purge a key whose blob the relay still serves), so a purely local clock rule is sound: it over-retains at worst and never strands a live blob. The rule's second leg is **no late wraps**: rotation re-attestation (above) confines any wrap to the retired thumbprint to the seconds-scale race around `retired_at`, so every row bearing it TTL-expires within the purge bound — a guarantee a session-frozen attestation cache could not give. Erasure still destroys the participant's active and retired keys together (Spec-022 Path 1).
4. The daemon **eagerly uploads** the ciphertext chunks to the relay blob store at publish time — when the intended-recipient set is non-empty; a publish with no intended recipients (a solo session: no attested peer node beyond the publishing one) uploads nothing and the manifest stays `pending_replication`, because there is nothing to replicate and a zero-row pinned blob would be vacuously delivered — the explicit re-publish toward the first actual recipient performs the initial pin (init on an unknown digest is simply the first upload) — (`ArtifactUploadInit` — carrying the **relay-visible lifecycle envelope** as authenticated plaintext: ciphertext digest, size, chunk size/count, `retentionTier`, and the wrapped-CEK recipient entries, because the relay cannot enforce quotas, chunk accounting, or tier TTLs blind — then chunk PUTs → `ArtifactUploadComplete`, whose finalize re-hashes the assembled ciphertext and refuses the pin unless it equals the init-declared **ciphertext digest** (the relay's CAS key — the whole-ciphertext SHA-256 of step 2; the plaintext CAS digest never reaches the relay and is not computable from ciphertext) — the CAS key is verified, never trusted, so `replicationStatus` cannot reach `pinned` over a corrupt store; resumable via received-set discovery; on an already-pinned digest, upload-init is an idempotent re-pin that re-verifies the stored copy's digest before short-circuiting — a damaged-at-rest copy is discarded and the upload proceeds fresh, making re-publish the repair path for relay-side corruption too — adds recipient rows, and **re-anchors the blob's `expires_at` to now + the declared retention tier's TTL** (a re-pin is a fresh grant of the same bytes; without the lease refresh, a re-publish near expiry could hand a late joiner a current-epoch event and wrapped CEK for a blob that TTL-dies before their fetch, silently voiding the `artifact.no_access_key` remedy) — the relay half of the re-publish path, which step 3 pairs with the re-emitted signed-manifest event). Eager pin at publish is what converts offline availability from best-effort to a guarantee.

### Fetch (authenticated; relay-served in V1)

5. A participant fetches via `ArtifactFetchAuthorize` — an **authenticated, `(participant, node)`-scoped, DPoP-bound ([RFC 9449](https://datatracker.ietf.org/doc/html/rfc9449)), short-lived (5–15 min) fetch token** minted against session membership. The **node half of the scope is not a client-supplied body field** — and a DPoP `cnf`/JWK-thumbprint is proof-of-possession material, not an identity, so the thumbprint alone cannot name a node. The binding is made at **mint time**, the standard RFC 9449 §5 flow: the control plane stamps `(participant, node)` into the token as **issuer-signed claims** — never a request-body node identifier — and sets the `cnf` confirmation claim to the key demonstrated in that call's DPoP proof. **The node-resolution mechanism is a key-thumbprint fetch selector** (deferred 2026-08-08; first specified 2026-08-12 as a server-minted `attachmentId` by the Plan-014 relay-scope readiness-audit delta; **re-specified 2026-08-16** as the thumbprint selector below, because the `attachmentId` form owed a daemon-side carrier that no V1 surface supplied): where the calling participant has exactly one attached node for the session, resolution from attach state is well-defined; where it has **two or more**, `sub` names only the participant, `cnf` is possession material rather than an identity, and no raw node identifier in the request body may disambiguate. So the caller presents **the set of artifact-encryption key thumbprints it holds** — the thumbprints of its own durable `artifact_encryption_keys` rows, a set rather than a single value because rotation retires rather than replaces and a daemon legitimately holds an active key plus any retired keys still covering undelivered blobs. The issuer resolves the recipient rows matching `ciphertext_digest` = the digest under fetch, `participant_id` = the authenticated `sub`, and `key_thumbprint` ∈ the presented set — and requires **exactly one**. **On exactly one row**, the issuer derives `node_id` **from that row**, never from caller input, then corroborates an active-state `runtime_node_attachments` row for that `node_id` **with `participant_id` = the authenticated `sub`, in the blob's own `session_id`** — all three legs in one predicate — before minting. The participant leg is load-bearing, not redundant (added 2026-08-17, PR #341 round 2): the attestation-spoofing residual means a recipient row's attested `node_id` can name **another participant's** attached node, and a node-and-session-only check would corroborate that row and mint a token whose `(participant, node)` claims describe no attachment that exists — the participant leg makes such a row fail corroboration instead. The predicate remains strictly stronger than membership alone (the attachments table is unique on `(node_id, session_id)` and carries `participant_id`), and membership is verified separately. **On zero rows**, `artifact.no_access_key` (404): an authenticated member with no wrapped CEK for this digest, exactly the post-publish-joiner state whose remedy is a publisher re-publish. **On exactly one row whose derived node holds no active attachment in the blob's session**, the corroboration fails and the mint is refused with `artifact.fetch_unauthorized` (403) — deliberately **not** `artifact.no_access_key`, because the caller holds a wrapped CEK and a re-publish remedies nothing; the remedy is re-attaching the node, a state the fetching daemon observes in its own attach lifecycle. **On two or more rows**, `artifact.fetch_unauthorized` (403), refused fail-closed and never silently narrowed to one — this arm is **defense in depth against a state Publish step 3's uniqueness constraint makes unreachable**, not a live path, since within one `(digest, participant)` the thumbprint is unique and a multi-match can only mean the constraint was bypassed or a partial write survived; refusing is the only safe response, because choosing among the candidates is precisely the guess that completes an attestation-spoof lockout. The node half therefore stays **issuer-derived and never caller-supplied**, and I-014-10 is unchanged: the selector picks among the caller's own rows and the issuer derives the value. **What the selector is not** — and this is the debit to state plainly rather than let a reader assume otherwise — a thumbprint is a public key's fingerprint, not a secret: presenting it proves nothing and grants nothing. Authorization is carried entirely by the authenticated `sub`, session membership, the DPoP proof, and the `participant_id` equality in the resolution predicate; the thumbprint set only **disambiguates among rows the caller is already entitled to**, and a caller presenting a thumbprint from another participant's row simply matches nothing, because `participant_id` is pinned to `sub` inside the same predicate. **Why this selector and not the alternatives:** the daemon already holds its own thumbprints durably in `artifact_encryption_keys` — a table it owns, on its own disk, surviving restart — so the selector needs no delivery machinery and no carrier, which is exactly what the `attachmentId` form could not say (the attach response returns to the client while the mint's caller is the daemon, and the renderer→daemon delivery path was deleted 2026-08-11). A pure issuer-side identity lookup was rejected because it is the mechanism V1 does not have — there is no node-identity credential to look up. Roster re-derivation was rejected because it reintroduces the same ambiguity one level up: a participant's roster names several nodes and nothing selects among them. The daemon's own `nodeId` as a request field remains a viable fallback shape but is strictly weaker — it is a raw caller-supplied node identity, the one thing I-014-10 prohibits — and is recorded as the fallback rather than the choice. Mint-time authorization is in any case **participant-granular, not node-granular** (scoped 2026-08-08; the prior wording — the issuer resolves `node_id` from "the authenticated node-attach context" — over-claimed a mechanism V1 does not ship: `ArtifactFetchAuthorize` is a control-plane route whose access token carries `sub` and `cnf` and no node claim, and **V1 defines no node-identity credential** per [security-architecture.md §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature)), so a same-participant sibling daemon obtaining a token for another of that participant's nodes is not cryptographically excludable — the same bound the Plan-006 T4.10 registrar resolves at, whose closure is the [cross-plan-dependencies.md §5 V1.1+ Cross-Plan Extensions](../architecture/cross-plan-dependencies.md#v11-cross-plan-extensions) Plan-018/Plan-003 node-identity leg. The residual is **not confined to delivery attribution** (corrected 2026-08-08 — an earlier draft of this clause wrongly narrowed it that way). It has two reachable harms, both bounded to a compromised node inside the participant's own trust domain and both **unremediable in V1** — and both are **availability- and attribution-class, never confidentiality** (reclassified 2026-08-08): the **forged ack** of Fetch step 6, which drives premature refcount-zero GC, and the **attestation spoof** of Publish step 3, which redirects a sibling's future CEK wraps to an attacker-held key and thereby **locks that honest sibling out**. Neither widens plaintext reach, because an attached sibling is already an intended recipient holding the CEK under its own attested key; plaintext reach by an authorized node is participant-granularity sharing working as designed. The relay thereafter reads the scope from the signed claims and verifies possession against `cnf` on every chunk GET and ack — no standing thumbprint→node registry to maintain, rotate, or garbage-collect. Node-scoping is load-bearing rather than cosmetic: recipient rows are keyed `(digest, participant, node)`, so a merely participant-scoped token could neither select the right wrapped CEK for a participant running several nodes nor attribute a delivery ack to the node that actually fetched — one node's ack would clear a sibling node's row and defeat the per-node refcount (I-014-7). The authorize response returns **the wrapped CEK on the single row the selector resolved** (whose only store is the relay, step 3), together with that row's `key_thumbprint`, so the fetching daemon knows which of its own private keys to unwrap with — including after a restart or a rotation, where the answer may be a retired key. Row selection happens on the **request** path, at mint time, by the thumbprint predicate above; the response does not re-select. Selection and delivery name the same row by construction, which is the point of requiring exactly one match. Then follow per-chunk authenticated GETs, resumable. Capability URLs are prohibited: they leak via logs/referrers/history, offer no per-participant revocation, and are the abuse surface that shut down Firefox Send; Matrix retrofitted authenticated media (MSC3916) for the same reasons. Authenticated fetch additionally provides per-participant quota attribution and a GDPR access-audit trail.
6. Each chunk is verified against the signed manifest **on arrival** (a bad chunk is rejected and re-requested without discarding verified chunks); the unwrapped CEK is verified against the signed `cekCommitment` **before decrypt**; after reassembly and decrypt, the whole-payload CAS digest is verified end-to-end. The integrity split is honest about the trust boundary: the chunk manifest and `cekCommitment` live inside the signed E2E payload the relay never parses, so **all chunk-level, key-commitment, and plaintext verification is recipient-side** (this step); the relay's only integrity duty is digest-level and keyless — verifying the assembled ciphertext against the init-declared **ciphertext digest** (its CAS key; the plaintext CAS digest never reaches it) at upload finalize (step 4) — it holds no per-chunk hashes and polices nothing at fetch time beyond serving stored bytes. Only then does the fetching node send an **authenticated `ArtifactFetchComplete` acknowledgement** — the relay MUST NOT infer delivery from the last chunk GET, because verification, decrypt, and the CAS check all happen client-side afterwards: a GET-inferred `delivered_at` could delete the last relay copy before the recipient detects a bad CEK, a digest mismatch, or crashes mid-verify. The ack is the sole writer of `delivered_at` (it also releases the grace lease); an un-acked fetch leaves the row undelivered and the blob lives to its TTL — the deliberate trade (a leaked blob until TTL is recoverable; a prematurely GC'd one is not). The ack **names no row**: the relay resolves the target `(ciphertext_digest, participant_id, node_id)` from the digest under fetch plus the token's own `(participant, node)` claims (step 5), never from a caller-supplied node identifier — otherwise any node could mark its siblings delivered and drive the blob to refcount-zero GC while they still need it. That closes the buggy-node and cross-participant cases outright. It does **not** close the **compromised same-participant node** (scoped 2026-08-08): step 5's mint is participant-granular, and the ack carries no evidence that the CEK was ever unwrapped or the payload verified, so a sibling holding a token minted under another of that participant's nodes can ack that node's row without fetching anything. If that clears the blob's last outstanding row, refcount-zero GC deletes it while the honest node still needs it. The honest node then sees `artifact.no_access_key` — its recipient row cascades away with the blob — but that error's documented remedy is a **publisher re-publish**, which is unavailable in precisely the publisher-offline case the availability guarantee exists for. V1 cannot prevent the forged ack (no node-identity credential exists to bind the ack to), so §Required Behavior scopes the guarantee instead; the closure is the §V1.1+ Cross-Plan Extensions Plan-014 row. The ack is **idempotent**: re-acking an already-delivered row sets nothing and returns success, so a recipient whose ack response was lost in transit safely retries.
7. **Direct-first fetch** (device-to-device when the publisher is reachable, relay as fallback) is criterion-gated to V1.x as [ADR-015 C4](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments): it requires a direct daemon-to-daemon transport V1 does not ship (cross-node traffic is relay-mediated per [Spec-024](./024-cross-node-dispatch-and-approval.md)). The wire format below already carries both paths (`replicationStatus` pin states, digest addressing), so the direct leg lands additively.

**A relay payload this node can no longer fetch is written back to the local manifest, not merely reported to the caller** (2026-08-17, ingest-protocol hardening amendment). Two fetch-path refusals establish that fact, and **both** drive the write-back: `artifact.relay_expired` (410) — at the `ArtifactFetchAuthorize` mint, at a per-chunk GET, or on a resume after eviction mid-fetch — and `artifact.no_access_key` (404) at the mint. On either, for a digest whose manifest row on **its own node** currently reads `replicationStatus: "pinned"`, the fetching daemon transitions that row to `"expired"` in the same pass, before surfacing the error. The 410 arm is scoped to the code rather than to the mint deliberately: a resume-path 410 is the _same_ fact about the same blob, and scoping the write-back to the mint alone would leave a `pinned` row beside a dead blob — the exact state this rule exists to eliminate.

**The 404 arm is not optional, because which code a fetching node meets depends on which lifecycle path removed its access.** Two of the three GC paths in step 8 destroy the recipient row rather than leave an expired blob behind: refcount-zero delete and watermark eviction remove the blob, and `artifact_relay_recipients` cascades from it — step 6 states the consequence outright, that the honest node "sees `artifact.no_access_key` — its recipient row cascades away with the blob." A fetch against a digest whose recipient row is gone resolves **zero** rows in the step-5 selector and is refused 404, never 410. So a write-back scoped to the 410 alone would leave every cascade-path loss carrying the state this rule exists to eliminate: a still-`pinned` row whose payload is unfetchable, matching no member of a closed union. Scoping the rule to the **fact** — this node can no longer obtain the payload — rather than to one code is also what makes it robust to a disposition this spec has not pinned: whether the hourly TTL sweep _retains_ the blob row at `state = 'expired'` (which is why that value exists in the blob-state set, and what lets the mid-fetch row above promise a 410 rather than a bare 404) or _deletes_ it like the other two GC paths (which step 8's "GC'd at … TTL expiry" reads as). The two readings put a post-TTL fetch on different codes, so a code-scoped rule would be right under one and broken under the other. A fact-scoped rule is right under both, and the ambiguity is therefore not load-bearing here — but it remains a real gap in the relay lifecycle description, flagged rather than silently settled by this amendment — tracked as [BL-152](../backlog.md) — since resolving it would change what the relay is contracted to serve after a TTL sweep.

**What the 404 arm costs, stated plainly rather than left for a reader to discover.** `artifact.no_access_key` has **three** producers the fetching node cannot distinguish, all of them resolving zero rows in the same step-5 selector: a GC'd blob it genuinely was a recipient of; the post-publish-joiner state where it never held a recipient row at all (step 5); and the thumbprint-collision case where both colliding entries were dropped fail-closed before any row was written (Publish step 3). All three can leave a local row reading `pinned` — the joiner's and the dropped node's because the publisher's manifest replicated carrying the status it held at publish — and all three carry the **same** remedy, a publisher re-publish while online. The write-back therefore treats them alike, and `expired` is to be read as _this node cannot obtain the payload from the relay; the remedy is a re-publish_ rather than narrowly as _the TTL elapsed_. Minting a separate union member for the joiner case was rejected on its merits and not merely on amendment scope: the distinction is **unobservable at the point of writing** — the refused node has no evidence of which producer refused it — so a distinct member would encode a fact its own writer cannot establish, while every member of this union is required to be both reachable and cause-true. Three properties make the write sound. It needs **no coordination**: a node's daemon is the only writer of its own `artifact_manifests` rows, so this is a local single-writer update, and every recipient node holds such a row because replication is manifest-first (§Resolved Questions and V1 Scope Decisions; the §Example Flows `over_cap` case has remote participants reading `replicationStatus` off exactly that row). It needs **no schema growth**: `expired` is already in the column's closed value set (§Wire-format additivity), which until now had no writer on the recipient side — the relay's TTL sweep and watermark eviction run on the other side of the node boundary and emit no event, so a recipient could observe expiry only by fetching. And it is **idempotent and non-latching**: writing `expired` over `expired` changes nothing, only a `pinned` row is transitioned (a row already carrying `pending_replication`, `over_cap`, or `quota_exceeded` was never pinned and is left alone), and a later publisher re-publish re-pins and re-emits the manifest, returning the row to `pinned` through the ordinary manifest path — so the status tracks live availability rather than latching on first failure. The publishing node's own row is untouched by this rule, since the publisher holds the plaintext and never fetches (Publish step 3). The consumer this grounds is the §Fallback Behavior unresolved-attachment marker, whose `expired` cause reads the persisted status and would otherwise name a value no row ever carries.

### Delete (refcount + TTL + crypto-shred)

8. The relay tracks per-recipient delivery at **`(participant, node)` granularity** — each intended-recipient node of a participant counts separately (the publishing node itself takes no row, step 3), so a participant's second device that has not yet fetched keeps the blob alive (delivery is never truncated by the same participant's first device fetching). A row becomes delivered only on that node's authenticated `ArtifactFetchComplete` ack (step 6), never on a chunk GET. The blob and its wrapped CEKs are GC'd at **refcount → 0 (every `(participant, node)` recipient row acked) or TTL expiry, whichever comes first**, with a **grace lease**: GC must not evict a blob while a known intended recipient has an in-flight resumable fetch. GC is asynchronous — hourly TTL sweep, immediate refcount-zero delete, and eviction at 90% of `node_relay_storage_max` (already-delivered / nearest-TTL blobs first) — never synchronous on the write path.
9. Participant erasure (the [Spec-022](./022-data-retention-and-gdpr.md) surface): crypto-shred the participant's key material — their daemon-local `artifact_encryption_keys` row on every node they run (Spec-022 Path 1, the durable artifact key's only copy) — and hard-DELETE their wrapped-CEK rows across **all their nodes** (Spec-022 Path 2); the relay rows are the wrapped CEKs' only copies, never the event (they can no longer derive the CEK), delete the shared blob at refcount-zero or TTL, emit an audit event, and fan out to every relay node holding the blob. The publisher-retained `relay_cek_ciphertext` is deliberately **not** in this sweep: the artifact — manifest and CAS plaintext — is session work-product that survives participant erasure (the [Spec-022 §PII Data Map](./022-data-retention-and-gdpr.md#pii-data-map) artifact-payload posture), and a sealed CEK beside the plaintext it encrypts grants nothing; the erased participant's reach is what the key and recipient-row shreds sever. The relay copy is a TTL-bounded transient buffer of ciphertext, not a system of record — the publisher's CAS is. The erasure posture combines NIST SP 800-88 Cryptographic Erase, GDPR Art 5(1)(e) storage limitation, and the CJEU _EDPS v SRB_ recipient-relative reading; stated honestly it is **defensible under the conditions in §State And Data Implications, not a settled EDPB position** — the spec claims "minimal-risk pseudonymised data plus a genuine crypto-shred + TTL erasure mechanism," never "the relay stores no personal data."

### Size, quota, retention (normative defaults; operator-tunable)

| Parameter | Default | Range | Precedent |
| --- | --- | --- | --- |
| `artifact_relay_chunk_bytes` | 8 MiB (fixed; content-defined chunking is pointless on ciphertext) | 5 MiB floor (S3 part minimum) | AWS CLI `multipart_chunksize` |
| `max_artifact_relay_bytes` | 100 MB | 50 MB – 1 GB | Synapse `max_upload_size` 50 MB; Bitwarden Send 500 MB |
| `per_session_relay_bytes` | 1 GB | operator-set | WeTransfer free tier; IPFS `StorageMax` |
| `per_participant_relay_bytes` | 250 MB | operator-set | WeTransfer per-user norms |
| `node_relay_storage_max` | 10 GB | operator-set | IPFS `StorageMax` default |
| `artifact_relay_ttl` (`default` tier) | 7 days | 24 h – 30 d (named tiers: `volatile` 24 h / `default` 7 d / `extended` 30 d) | Bitwarden Send 7 d default, 30 d max; WhatsApp 30 d undelivered; Signal ~45 d transit |
| `incomplete_upload_ttl` | 48 h | 24–72 h | tus `Upload-Expires`; S3 `AbortIncompleteMultipartUpload` |

**Every byte parameter in this table binds the plaintext byte count** (2026-08-17, PR #341 round 2 — the unit shared with `max_attachment_ingest_bytes`, which is what makes "relay-pinnable by construction" exact at the boundary): the relay enforces the declared plaintext size at upload init and re-verifies at finalize that the assembled ciphertext does not exceed it by more than the bounded AEAD envelope overhead (per-chunk tag + nonce — a constant under 0.01% at the fixed 8 MiB chunk, XChaCha20-Poly1305 being length-preserving otherwise); that overhead is operator storage headroom, never quota spend, so `per_session_relay_bytes` / `max_artifact_relay_bytes` = 10 is exact rather than approximate. Retention is a small named tier set, not a free-form TTL, so relays reason about lifecycle uniformly. Over-quota or over-rate upload receives `429 Too Many Requests` + `Retry-After` per [Spec-021](./021-rate-limiting-policy.md), whose registry carries the six relay request-rate rows (`artifact.upload.init`, `artifact.upload.chunk`, `artifact.upload.complete`, `artifact.fetch.authorize`, `artifact.fetch.chunk`, `artifact.fetch.complete`); the byte/storage quotas above are enforced at the relay blob store and are Spec-014-owned. Self-host operators tune down (shorter TTL, smaller quotas) — steady-state footprint is "in-flight undelivered artifacts," not "all artifacts ever" (the Signal/WhatsApp store-until-delivered economics). The blob store's backing engine stays an implementation detail per §Non-Goals; the 8 MiB chunk maps 1:1 onto an S3 multipart part, so S3-compatible object stores are a natural fit without being mandated.

### Failure modes (normative responses)

| Failure | Required response |
| --- | --- |
| Publisher offline at fetch time | The relay serves the eagerly pinned copy — availability is independent of publisher reachability (the core case). **Scoped 2026-08-08:** honest-node threat model only — a compromised node of the fetching participant can forge the Fetch step 6 ack and GC the blob out from under its sibling, with no offline remedy; V1 has no node credential to prevent it (§V1.1+ Cross-Plan Extensions Plan-014 row). |
| Over-cap artifact | Not relay-pinned; publisher-local with explicit degraded manifest status ("unavailable while the publisher is offline"). Never silent. |
| Relay full / quota exceeded | Upload backpressure `429` + `Retry-After`; watermark eviction (90% of `node_relay_storage_max`, delivered/nearest-TTL first); publish degrades to publisher-local with the explicit degraded status. |
| Digest mismatch on fetch | Reject the chunk on arrival and re-request it; verify the whole payload post-decrypt; persistent mismatch surfaces a loud integrity error — never silently-wrong bytes. Persistent mismatch across recipients means the relay's stored copy itself is damaged: publisher re-publish repairs it, because re-pin re-verifies the stored digest and replaces a corrupt copy (Publish step 4). |
| Recipient crashes after the last chunk GET, before verifying | No `ArtifactFetchComplete` ack is sent, so the row stays undelivered and the blob survives to TTL; the recipient re-fetches and re-verifies. Delivery is never inferred from transport. |
| Recipient rotates its artifact key with a pinned blob still live | The retired key is retained (thumbprint-selected) until every relay row wrapped to it is delivered or TTL-expired, so the offline-fetch guarantee survives rotation; new wraps use the active key. |
| TTL expiry / eviction mid-fetch | Resume returns an explicit expired/unavailable error — `artifact.relay_expired` (410), never a bare 404; the participant re-requests via re-publish (or the C4 direct leg once shipped). The grace lease prevents eviction during a known in-flight fetch. The fetching daemon additionally transitions its own manifest row `pinned` → `expired` in the same pass, on the mint, chunk-GET, and resume arms alike, so the local status stops claiming a pin the relay no longer holds (§Fetch — 2026-08-17, ingest-protocol hardening amendment). Where a GC path instead removes the blob row — refcount-zero delete and watermark eviction both do — the recipient rows cascade with it (step 6) and a later fetch is refused the typed `artifact.no_access_key` (404), never a _bare_ 404; the zero-row row below carries that arm of the same write-back. |
| Publisher dies mid-upload | Chunks are independent; the publisher resumes via received-set discovery on reconnect. Orphaned incomplete uploads are reaped at `incomplete_upload_ttl`. |
| Participant erased mid-life | Immediate crypto-shred + wrapped-CEK drop for that participant; blob GC at refcount-zero/TTL; audit event; fan-out to all relay nodes. |
| Malicious or curious relay operator | Sees ciphertext, wrapped keys, and metadata (sizes, timing, participant identities, retention tier) — never plaintext or the CEK. Same trust model as the untrusted relays of magic-wormhole / croc / Syncthing. |
| Abuse (malware/phishing distribution) | No public URL surface — fetch is authenticated-participant-only (closing Firefox Send's fatal gap); revocation rides session membership; denial-of-storage is bounded by the quota envelope. |
| Ingest payload's derived type contradicts the declared type, or is not allow-listed | Refuse with `artifact.unsupported_media_type` (415) and quarantine the bytes; never silently correct the declared type, and never persist a manifest for the refused payload (§Ingest Validation And Payload Bounds (V1) steps 4–5). |
| Ingest payload's signature is undetermined | Accept only if the declared type is in the allow-list's signature-exempt subset **and** the bytes are well-formed UTF-8; otherwise refuse with `artifact.unsupported_media_type` (415) and quarantine. An undetermined signature is never read as an absence of risk. |
| Operator-configured scanner rejects an otherwise-admissible payload | Refuse with `artifact.scanner_rejected` (422) and quarantine per step 9 — never `artifact.unsupported_media_type`, whose media-type remedy would misdirect a content verdict (§Ingest Validation And Payload Bounds (V1) step 8). The default no-scanner configuration never produces this refusal. |
| Carrier names more attachments than `max_attachments_per_carrier` | Refuse the carrier with `artifact.too_many_attachments` (413) at carrier acceptance, before any element is bound or delivered — refusal leaves no partial carrier state. Artifacts already minted by earlier `AttachmentIngest` calls are unaffected and follow their own lifecycle; they are session artifacts, not orphans (§Ingest Validation And Payload Bounds (V1) step 2). |
| `AttachmentIngestInit` arrives while the open-stream count or the aggregate spool reservation budget is exhausted | Refuse with `artifact.ingest_capacity_exhausted` (429) — transient backpressure, retry later — with **no stream state created**: no `ingestId` is minted, no slot consumed, no reservation held, so releasing one open stream (or waiting out `max_ingest_stream_lifetime`) admits the next Init. Never silently queue, and never let the flood reach the filesystem (§Ingest Validation And Payload Bounds (V1) stream protocol). |
| Two `AttachmentIngestInit` calls arrive concurrently with one slot or one declaration's worth of reservation budget left | Exactly one admits; the other refuses `artifact.ingest_capacity_exhausted` (429). Admission is one serialized reserve-then-install section over the count and the reserved-byte total, so the bounds cannot be breached by two callers each observing the same headroom (§Ingest Validation And Payload Bounds (V1) stream protocol — 2026-08-17, ingest-protocol hardening amendment). |
| An ingest chunk repeats, gaps, or regresses its sequence — or any call arrives on a terminated, expired, or unknown `ingestId`, or a `Chunk` on a completed one | An exact replay of the last acknowledged chunk (same sequence, same bytes — the retry after a lost response) is acknowledged idempotently without re-appending. Every other violation refuses `artifact.ingest_stream_invalid` (409), terminating a live stream with its spool deleted — the terminal restart-from-Init signal, deliberately distinct from the transient 429 (§Ingest Validation And Payload Bounds (V1) stream protocol). |
| `AttachmentIngestComplete` is retried because its response was lost in transit | The retry **replays the original response verbatim** from the completion record on the stream's registry entry — same `artifactId`, same `contentHash` — re-running no pipeline step and inserting no second manifest row. Past `max_ingest_stream_lifetime` the entry and its record are gone, so the retry gets the ordinary `artifact.ingest_stream_invalid` (409) and a re-ingest costs a second manifest row over one CAS payload — never duplicated bytes (§Ingest Validation And Payload Bounds (V1) stream protocol — 2026-08-17, ingest-protocol hardening amendment). |
| Two calls on the **same** `ingestId` overlap — an original and its retry racing after a lost response | Both are served, one at a time: every call on one stream runs inside a critical section keyed by that `ingestId`, so sequence validation, spool append, running-count and digest update, and acknowledgement are atomic per call, and the second call observes fully-updated state (the replay path, not a double append). The reaper's eviction takes the same exclusion, so a stream is never served and evicted at once (§Ingest Validation And Payload Bounds (V1) stream protocol — 2026-08-17, ingest-protocol hardening amendment). |
| Several ingests fail content validation at once with quarantine near `ingest_quarantine_max_bytes` | Each admission is serialized reserve-then-install under the quarantine directory's own exclusion — measure, evict oldest-`mtime`-first, reserve, install — so the aggregate cap holds under concurrency instead of overshooting by one payload per racing refusal. Every payload is still refused with its own code; only forensic retention degrades, oldest evidence first (§Ingest Validation And Payload Bounds (V1) step 9 — 2026-08-17, ingest-protocol hardening amendment). |
| Fetch mint resolves exactly one recipient row, but the derived node has no active attachment **by the authenticated participant** in the blob's session — detached, or attested under a foreign `node_id` | `artifact.fetch_unauthorized` (403): the caller holds a grant but is not attached where the blob lives, so re-publish remedies nothing — re-attaching the node does (Fetch step 5). |
| Two recipient entries in one publish share a key thumbprint for the same participant | Drop **both** entries fail-closed before any row is written, pin the blob for every non-colliding recipient, and return the dropped entries to the publisher as an explicit per-entry rejection. Never fail the whole publish — that would be a denial-of-publish primitive. The affected nodes see `artifact.no_access_key` (404) with its re-publish remedy (Publish step 3). |
| A publish's incoming recipient entry shares a key thumbprint with a **surviving** row for the same participant on a different node | Reject the **incoming entry only**, per-entry, reported to the publisher like an intra-set drop; the surviving row — a standing grant — is never deleted or displaced, and the publish never fails. A write-time uniqueness violation that outruns the screen resolves to the same per-entry rejection (Publish step 3). |
| Fetch mint's thumbprint selector matches zero rows, or matches two or more | Zero is `artifact.no_access_key` (404) — the post-publish-joiner state, and equally the deleted-blob state (recipient rows cascade with the blob at refcount-zero delete or watermark eviction, step 6) and the fail-closed thumbprint-collision drop (Publish step 3); the three are indistinguishable to the refused node and share the re-publish remedy, so a zero-row refusal against a local row still reading `pinned` also drives that row to `expired` (§Fetch — 2026-08-17, ingest-protocol hardening amendment). Two or more is `artifact.fetch_unauthorized` (403), refused fail-closed and never narrowed to one; it is unreachable given the Publish step 3 uniqueness constraint, so reaching it means the constraint was bypassed (Fetch step 5). |
| `ArtifactDelete` targets a manifest that another manifest names as its `subject` | Refuse with `artifact.delete_blocked` (409), naming the referencing manifests — at most the first 50 ids ascending plus the total count, so the refusal always fits the transport frame (2026-08-17, PR #341 round 3). Nulling the derivative's `subject` is prohibited — it would silently convert a derivative into an apparent original and destroy the provenance chain (§Local Artifact Deletion And CAS Reclaim (V1)). |
| `ArtifactDelete` by a caller the permission matrix does not authorize | Refuse with `artifact.delete_forbidden` (403) **before any mutation**: the owner role may delete any session artifact, a collaborator only artifacts they produced — the own-artifacts scope evaluated against `artifact_manifests.created_by`, the publishing caller stamped at insert, NULL when the daemon itself produced the artifact with no attributable caller, and evaluated fail-closed: a NULL stamp matches no collaborator, so only the owner role deletes a daemon-produced artifact — runtime contributors and viewers never ([security-architecture.md §Permission Matrix (Task 5.4)](../architecture/security-architecture.md#permission-matrix-task-54)). The target manifest, its payload references, and the CAS bytes are unchanged by the refusal. |
| `ArtifactDelete` targets a manifest carrying a retained `relay_cek_ciphertext` | Delete proceeds and takes the retained CEK with it, but the operation must surface the consequence rather than delete silently: the response reports `rePublishForeclosed` — grounded in the destroyed local CEK alone, never in relay liveness the daemon cannot derive (2026-08-17, PR #341 round 3) — because re-publish for that artifact becomes impossible, so the late-join `artifact.no_access_key` remedy is no longer available for it. Any still-pinned recipients fetch normally until the blob's own refcount-zero or TTL. |
| Attachment named by a turn-scoped carrier cannot be resolved or delivered | The turn proceeds and carries an explicit unresolved marker in that attachment's declared position, naming the cause from the closed union — `deleted`, `local_only_remote`, or the manifest's own non-`pinned` replication status carried verbatim (`pending_replication`, `over_cap`, `quota_exceeded`, `expired`; 2026-08-17, PR #341 round 3). The replication-status arm reads the **persisted** row on the rendering node, never live relay state; its `expired` value is written there by that node's own fetch path on either `artifact.relay_expired` (410) or a zero-row `artifact.no_access_key` (404) against a still-`pinned` row — §Fetch (2026-08-17, ingest-protocol hardening amendment). Silently omitting it is prohibited (§Fallback Behavior). |

### Wire-format additivity

The `artifact.published` event gains additive, schema-versioned fields (old clients ignore unknown fields): `ciphertextDigest`, `chunkSize`, `chunkCount`, `chunkManifest` (or `manifestDigest` when the manifest is fetched out-of-band), `cekCommitment` (the signed key-commitment binding — wrapped CEKs are relay-held per-recipient state returned by `ArtifactFetchAuthorize`, never event-carried), and `retentionTier`. The pin state rides the **existing** `ArtifactManifest.replicationStatus?` field, whose value set is refined to `pending_replication | pinned | over_cap | quota_exceeded | expired` — this is the "deferred owner refinement" the Tier-7 audit's A-014-3 anticipated for that column (the values are now spec-named, so the schema CHECK lands with them). The content-integrity fields ride inside the existing signed, E2E-encrypted payload — the relay never parses them; the **lifecycle envelope** (`retentionTier` plus size/chunk accounting) is deliberately relay-visible at `ArtifactUploadInit` (step 4 — the relay cannot enforce TTLs and quotas blind) and is mirrored inside the signed payload, so a relay that tampers with the tier is evident to every recipient (declared tier vs relay-reported expiry). Digests are multihash-prefixed (`sha256:…`) so a future hash migration is additive. Event lifecycle and blob lifecycle are independent: the `artifact.published` event may outlive the relay blob; the event carries the digest, so a re-publish re-pins and re-associates — and re-emits the event into the current membership epoch (identical signed manifest content, idempotent by digest), because pre-join events are undecryptable to late joiners and a wrapped CEK is unverifiable without the signed manifest.

## State And Data Implications

- Artifact manifests are durable records and part of replayable session history.
- Payload storage may differ from manifest storage, but provenance must stay intact across both.
- Artifact visibility changes must be auditable.
- Plan-014 owns the `artifact_manifests` table. Plan-011's `diff_artifacts` references manifests via foreign key.
- Local payload reclaim carries **no counter column**. The refcount for a stored CAS payload is derived by counting the surviving payload-reference rows that name its storage key, and the bytes are reclaimed only at zero (§Local Artifact Deletion And CAS Reclaim (V1)). Adding a stored counter is rejected: it is a second source of truth that drifts on any crash between the reference write and the counter write, and drift in the decrementing direction deletes bytes another manifest still names.
- Every node participating in a shared artifact holds **its own** `artifact_manifests` row (replication is manifest-first), and that row's `replicationStatus` is the **persisted** value the unresolved-attachment marker reads — never a status recomputed at render time from state the renderer cannot observe. The node's daemon is that row's only writer, which is what lets the fetch path record a relay `artifact.relay_expired` (410) as `expired` there (§Fetch) instead of reporting the expiry and forgetting it. No table or column is added: `expired` is already in the column's closed value set, and this amendment supplies the writer it lacked (2026-08-17, ingest-protocol hardening amendment).
- The ingest stream registry, its per-stream completion records, and the aggregate spool reservation are **in-memory daemon state, deliberately not tables**. A stream dies with the process — its spool goes quiescent for the `mtime` reaper, and a retried `AttachmentIngestComplete` after a restart takes the ordinary 409 restart-from-Init path. Making completion records durable would mint a table for a transient whose whole lifetime is bounded by `max_ingest_stream_lifetime`, and would move the local-schema census for it; the accepted cost is the named residual in §Ingest Validation And Payload Bounds (V1) — a second manifest row over one deduplicated CAS payload.
- The relay recipient set carries a **uniqueness constraint on `(ciphertext_digest, participant_id, key_thumbprint)`** — an index, not a table, so no table census moves. It makes thumbprint→node injective within one participant's rows for one blob, which is what makes the Fetch step 5 mint selector resolvable, and it makes the attestation-spoof duplicate a pre-write refusal rather than a silent lockout — the screen covering the submitted set and the surviving rows alike, with the incoming entry alone rejected in the surviving-row case (Publish step 3). It composes with the existing `(ciphertext_digest, participant_id, node_id)` primary key rather than replacing it: the primary key bounds rows per node, the new index bounds rows per key.
- Any redacted or summarized shareable derivative must be a separate artifact with its own manifest and provenance rather than an in-place mutation of the original artifact.
- The relay blob store adds control-plane state (Plan-014 CREATEs; see the [ownership map](../architecture/cross-plan-dependencies.md)): blob metadata (ciphertext digest, size, chunk set, TTL/retention tier, pin state), the per-`(participant, node)` wrapped-CEK set (wrapped to durable artifact-encryption keys; the private halves live daemon-local in `artifact_encryption_keys` under Spec-022 master-key custody), per-recipient delivery refcounts with grace leases, and per-session/per-participant quota accounting. The wrapped-CEK rows reference participants, which adds a row to the [Spec-022](./022-data-retention-and-gdpr.md) CP-022-6 erasure fan-out closure — Plan-014 owes the Path-2 reciprocal.
- GDPR conditions that must hold for the crypto-shred posture (each an engineering requirement, not advice): encryption is applied before bytes reach the relay; key isolation is per-participant; key destruction is complete and irreversible **including backups** — and because Postgres PITR/WAL archiving is database-wide, "excluding rows from backup" is not a real mechanism: either the control-plane backup/PITR retention window is bounded at or below the erasure SLA (≤ the 30 d relay-TTL ceiling), or the wrapped-CEK envelopes are stored under a separately-destroyable KEK so a restored backup yields unusable ciphertext (the [Spec-022 §Daemon Master Key](./022-data-retention-and-gdpr.md#daemon-master-key) custody precedent; the daemon-local artifact-key store inherits that backup-exclusion posture wholesale) — the known failure class remains deleting client keys while server ciphertext outlives an unwired delete path; TTL is bounded; shred and deletion are audited without logging plaintext or keys; a hosted relay operates under an Art 28 processor DPA; erasure fans out to every relay node.

## Example Flows

- `Example: A participant uploads a design reference image, which becomes an immutable attachment artifact visible to the session.`
- `Example: A run publishes a diff artifact and a terminal-output artifact. The timeline shows both manifests, but the large terminal payload requires explicit expansion.`
- `Example: A local-only artifact contains sensitive machine-specific data. The participant keeps the original artifact local and publishes a separate summarized artifact for shared discussion instead of partially redacting the original artifact in place.`
- `Example: A participant on node A publishes a 40 MB design bundle as shared-visible and closes the laptop. The relay already holds the encrypted chunks (eager pin at publish); a participant on node B fetches, verifies each chunk against the signed manifest, unwraps their CEK, decrypts, and verifies the CAS digest — with node A offline throughout. After the last intended recipient fetches, the relay copy is GC'd.`
- `Example: A participant publishes a 2 GB dataset. It exceeds the relay cap, so it is not pinned; the manifest replicates with replicationStatus "over_cap" and remote participants see an explicit "unavailable while the publisher is offline" status instead of a silent failure.`

## Implementation Notes

- Artifact immutability matters more than original path convenience.
- Content-addressable storage (CAS) is keyed by SHA-256 for automatic deduplication. CAS addressing also discharges the OWASP random-filename requirement structurally: no caller-supplied string is ever a path component, so there is no filename to sanitize on the storage path.
- Attachment manifests should stay small enough for routine timeline and replay use.
- Signature detection is a library choice, not a contract: the spec requires that the type be derived from the bytes and bounded in time, not that any particular detector be used. The implementing plan records the library-versus-hand-rolled decision with its version.
- **This spec's four in-process exclusions form one total, acyclic acquisition order** (2026-08-17, ingest-protocol hardening amendment), all of them daemon-local because the daemon is the sole writer of the CAS, the spool, the quarantine directory, and its own manifest rows: **per-`ingestId`** (the stream single-flight section) → the **ingest admission ledger** (the open-stream count plus reserved-byte total) → at most one of **per-`storage_path`** (CAS reclaim and the same-hash write path) or the **quarantine directory**, which no path holds together. Acquiring in that order and never inverting it is the whole rule. Two shapes make it work rather than merely declare it: `AttachmentIngestInit` takes the ledger alone and no stream exclusion, so admission introduces no back edge from ledger to stream; and the lifetime reaper snapshots eviction candidates under the ledger, releases it, then takes each candidate's own `ingestId` exclusion and re-checks state before evicting, so the sweep never holds the ledger while waiting on a stream. `AttachmentIngestComplete` is the path that exercises the order end to end — stream exclusion held, reservation released against the ledger, then the step-8 CAS rename under the storage-key exclusion.

## Pitfalls To Avoid

- Treating a live filesystem path as an immutable artifact
- Auto-sharing local artifacts with no visibility classification
- Requiring inline rendering for every artifact regardless of size
- Capability URLs for payload fetch (secret-in-URL: leaks via logs/referrers/history, no per-participant revocation — the Firefox Send failure; fetch is authenticated-participant-only)
- A non-committing encryption posture for relay payloads — a non-AEAD cipher (AES-CTR-class) admits multi-plaintext key substitution ("Missing Salamanders"), and an AEAD alone is still not key-committing (the partitioning-oracle class); the design requires AEAD **plus** the signed `cekCommitment`
- Lazy cache-on-miss relay population presented as offline availability (it is best-effort, not a guarantee — the pin must be eager at publish)
- Synchronous GC on the upload/fetch path (GC is background: TTL sweep + refcount-zero delete + watermark eviction)
- Recording a caller-declared `mediaType` or `sizeBytes` on the manifest — the declared values are advisory input to be reconciled, and the derived values are the facts
- Reading an undetermined signature as "nothing detected, therefore safe" — the fail-open that a signature-based pipeline invites and that the signature-exempt allow-list subset exists to close
- Silently correcting a declared media type that the derived type contradicts (the double-extension and `Content-Type`-spoof class), instead of refusing
- Pointing the type detector at an archive interior — container introspection is a decompression-bomb surface, and V1 deliberately does not unpack
- Maintaining a stored CAS refcount column instead of deriving the count from the surviving reference rows (a second source of truth whose drift deletes live bytes)
- Untyped attachment elements on turn-scoped carriers, or an attachment that a turn quietly drops when it cannot be delivered
- Failing an entire publish because one recipient entry collided — a per-entry drop is the honest response; whole-publish failure hands an attacker a denial-of-publish primitive
- Refusing a retried `AttachmentIngestComplete` whose only fault is that the caller lost the first response — the completion record exists so the retry replays the original response instead of costing the caller a whole re-upload, and the opposite error is just as bad: re-running steps 3–8 and inserting a second manifest row on a stream that already completed
- Checking a shared byte budget outside the critical section that spends it (the quarantine directory's aggregate cap, the ingest spool reservation) — concurrent callers each observe the same headroom and the bound is exceeded by one payload per racing caller, which is the denial-of-disk the cap was added to prevent
- Serving two calls on one `ingestId` concurrently — sequence validation, spool append, and running-count update are one read-modify-write, and interleaving them double-appends or compares a replay against half-updated state
- Letting the abandoned-stream reaper delete a spool or release a reservation without taking the same per-`ingestId` exclusion a live call holds — eviction racing an in-flight `Chunk` or `Complete` corrupts exactly the state the exclusion exists to protect
- Reporting a relay `artifact.relay_expired` (410) to the caller without recording it on the local manifest — the row then claims a pin the relay no longer holds, and the closed unresolved-marker cause union has no member matching a still-`pinned` manifest whose payload is unavailable
- Recording that write-back on the 410 **only**, and so missing every loss that arrives as a 404 instead: refcount-zero delete and watermark eviction remove the blob row, its recipient rows cascade with it, and the later fetch resolves zero rows — a typed `artifact.no_access_key`, not a 410. A 410-only write-back leaves those cases carrying the very still-`pinned` row the previous bullet prohibits
- Asserting "the refusal created no state" by probing an identifier the refusal never issued — a refused `AttachmentIngestInit` returns no `ingestId`, so the observable is whether the next Init admits, never a fabricated id

## Acceptance Criteria

- [ ] Attachment ingestion produces stable artifact ids and manifests.
- [ ] Artifacts remain readable and attributable after the producing run ends.
- [ ] Large artifacts can be represented in the timeline without forcing full inline payload rendering.
- [ ] A shared-visible artifact within the relay cap published on node A is fetchable on node B while node A is offline — asserted **given an operational relay that serves the bytes it accepted** (availability cannot be asserted against relay deletion, loss, or refusal; against the relay this spec asserts confidentiality and integrity only), and asserted against non-members and other participants; **not** asserted against a compromised node of node B's own participant (2026-08-08 threat-model scope, §Required Behavior).
- [ ] The relay stores only ciphertext and per-`(participant, node)` wrapped CEKs; no relay-side material suffices to decrypt.
- [ ] Payload fetch requires an authenticated, `(participant, node)`-scoped, DPoP-bound authorization; non-member and unauthenticated fetches are refused.
- [ ] A corrupted chunk is rejected on arrival and re-requested; the whole-payload digest is verified post-decrypt; persistent mismatch surfaces a loud integrity error.
- [ ] Over-cap and over-quota artifacts surface the explicit degraded status (`replicationStatus`) rather than failing silently.
- [ ] Participant erasure crypto-shreds that participant's wrapped-CEK rows across all their nodes, the blob is GC'd at refcount-zero or TTL, and an audit event is emitted.
- [ ] A recipient daemon restarted (or its session ended) between publish and fetch still unwraps its relay-held CEK — CEKs are wrapped to durable artifact-encryption keys, never to session-ephemeral X25519 keys.
- [ ] A participant or node joining the session after publish receives the explicit `artifact.no_access_key` error (distinct from `artifact.fetch_unauthorized`; never a silent failure) and gains access when the online publisher re-publishes — idempotent re-pin adding recipient rows, **refreshing the blob's TTL lease** (a re-pin near expiry re-anchors `expires_at`, so the joiner's fetch window is the full tier TTL), **plus a re-emitted current-epoch `artifact.published` event**, so the joiner's fetch verifies end-to-end against the re-emitted signed manifest.
- [ ] Artifact-key generation and attestation happen at node attach (join-sequence obligation, never lazily at first fetch): every node whose attach completed before a publish — other than the publishing node itself, which holds the plaintext and takes no recipient row — appears in that publish's wrapped-key recipient set, with the publishing daemon stopped afterward.
- [ ] `delivered_at` advances only on an authenticated `ArtifactFetchComplete` ack sent after chunk, commitment, and CAS verification succeed; a recipient that crashes after its last chunk GET leaves the blob intact until TTL.
- [ ] The relay resolves the acked recipient row from the fetch token's own `(participant, node)` claims, never from a caller-supplied node identifier, and a replayed ack is an idempotent no-op. **Scoped 2026-08-08:** the sibling-delivery bar this enforces is that a node presenting a token minted for itself cannot ack another row — a **compromised** node of the same participant still can, because the mint is participant-granular and the ack proves no unwrap (Fetch steps 5–6); that case is the named V1 residual, not a criterion V1 meets.
- [ ] A node that rotated its artifact-encryption key still fetches and unwraps a blob pinned to the retired key while the publisher is offline, until that blob is delivered or TTL-expired — asserted under the same threat-model scope as the offline-fetch row above (operational relay; not against a compromised node of that participant).
- [ ] Rotation re-attests the new active key to session peers immediately: a publish by a connected peer after the rotation wraps to the new key, while a publish racing the in-flight re-attestation wraps to the retired key and remains fetchable until delivered or TTL-expired — never past the retired key's local purge bound.
- [ ] A fetch mint by a participant running two attached nodes resolves to the node whose presented key thumbprint matches its own recipient row, derives `node_id` from that row rather than from any caller field, and corroborates its own active-state node attachment — the derived node, the authenticated participant, the blob's session — before minting.
- [ ] A fetch mint presenting a thumbprint that matches no row for the authenticated participant receives `artifact.no_access_key` (404), and one whose predicate matches two or more rows is refused with `artifact.fetch_unauthorized` (403) rather than narrowed to a single candidate.
- [ ] A publish whose declared recipient entries contain two entries sharing one key thumbprint for one participant drops both fail-closed before writing, pins for every other recipient, and reports the dropped entries to the publisher; the publish itself does not fail.
- [ ] A publish whose incoming recipient entry collides with a **surviving** recipient row for the same participant on a different node rejects that entry alone — reported to the publisher — leaves the surviving row untouched, pins for every other recipient, and does not fail the publish.
- [ ] A re-publish to a node that rotated its artifact-encryption key updates that node's existing recipient row in place — new wrapped CEK and new thumbprint — rather than inserting a second row for the same node.
- [ ] An ingested payload exceeding `max_attachment_ingest_bytes` is refused with `artifact.too_large` (413) before any parser reads it — at Init when declared, and at the spooled running count when not — and a carrier exceeding `max_attachments_per_carrier` is refused with `artifact.too_many_attachments` (413) at carrier acceptance, before any element is bound or delivered, leaving no partial carrier state.
- [ ] A boundary-crossing `ArtifactPublish` payload runs the §Ingest Validation And Payload Bounds (V1) content gates over its decoded bytes — steps 3–4, the media-type leg of step 5, step 6, and steps 7–8, with the extension leg structurally vacuous because no publish shape carries a filename member — and a boundary-crossing publish declaring `artifactType: "file"` is refused and directed to `AttachmentIngest` rather than validated in a second place.
- [ ] An `AttachmentIngest` abandoned mid-trio leaves only a spool file that the daemon-local `mtime`-clocked reaper removes at TTL; no manifest, CAS entry, or carrier state survives it.
- [ ] An ingested payload whose derived media type contradicts its declared `mediaType` is refused with `artifact.unsupported_media_type` (415) and quarantined — never silently corrected — and the manifest of an accepted payload records the **derived** media type and byte size, not the declared ones.
- [ ] An ingested payload whose signature cannot be determined is accepted only when its declared type is in the allow-list's signature-exempt subset and the bytes are well-formed UTF-8; otherwise it is refused and quarantined.
- [ ] Quarantined bytes are referenced by no manifest, are unreachable via `ArtifactRead`, and are reaped at `ingest_quarantine_ttl` by a daemon-local reaper clocked off the quarantined file's own `mtime` — a quarantined payload older than the TTL is gone from disk, and one younger than it is not.
- [ ] Quarantine entries are stored under server-generated names — no caller-supplied string is a path component of a quarantined file — and the directory's aggregate size never exceeds `ingest_quarantine_max_bytes`: a new entry evicts oldest-`mtime`-first until it fits, and the eviction removes older entries before younger ones. The bound holds under **concurrent** content refusals as well as serial ones: several refusable payloads submitted in parallel against a near-full quarantine leave the directory at or below `ingest_quarantine_max_bytes`, not one payload above it per racing refusal.
- [ ] A configured step-8 scanner's rejecting verdict refuses the ingest with `artifact.scanner_rejected` (422) and quarantines the bytes, leaving **zero CAS entries** — the admitting rename is the same step's success arm and never ran; the default no-scanner configuration admits the same payload without producing that refusal.
- [ ] Every payload-bearing member of this spec's local-wire interfaces is a JSON string — base64 (RFC 4648) or UTF-8 under an explicit encoding discriminator, never a binary field — an `AttachmentIngestChunk` carrying `max_attachment_chunk_bytes` raw bytes fits the Spec-007 frame ceiling after base64 expansion, and every byte bound binds the decoded count.
- [ ] A boundary-crossing `ArtifactPublish` whose serialized frame overflows the Spec-007 ceiling is refused at the transport — the predictable raw ceiling is the `base64` arm's ≈700 KiB (fixed 4/3 expansion), while a `utf8` payload's serialized size is content-dependent under JSON escaping, so an escape-heavy `utf8` payload well under 1 MB raw is still refused when its escaped form overflows — while a `utf8` publish and a `base64` publish of identical decoded content hash to one CAS entry (the daemon decodes before hashing).
- [ ] An `AttachmentIngestInit` arriving at the open-stream count bound or the aggregate spool-reservation budget is refused with `artifact.ingest_capacity_exhausted` (429) and leaks neither a count slot nor a reservation — asserted through **admission**, never through an identifier the refusal did not issue: after a count-bound refusal, terminating one open stream admits the next Init, and after a reservation-arm refusal, an Init whose declaration fits the freed budget admits. A chunk pushing a stream's running decoded count past its Init-declared total is refused with `artifact.too_large` (413) and the spool is deleted.
- [ ] Two `AttachmentIngestInit` calls dispatched concurrently against one remaining slot (or one declaration's worth of remaining reservation budget) admit exactly one and refuse the other with `artifact.ingest_capacity_exhausted` (429) — the open-stream count and reserved-byte total never exceed `max_active_ingest_streams` / `ingest_spool_max_bytes` at any observation point.
- [ ] An exact replay of the last acknowledged ingest chunk is acknowledged idempotently without double-appending (the spooled bytes are identical before and after the replay); a sequence gap, regression, or same-sequence different-bytes chunk terminates the stream, and every subsequent call on that `ingestId` — as on an expired or unknown one, and every `Chunk` on a completed one — is refused with `artifact.ingest_stream_invalid` (409).
- [ ] An `AttachmentIngestComplete` retried after its response was lost replays the original response verbatim — the same `artifactId` and `contentHash` — with the pipeline re-run zero times and exactly **one** manifest row over the payload; past `max_ingest_stream_lifetime` the same retry receives `artifact.ingest_stream_invalid` (409), and a caller that then re-ingests the identical bytes ends with one CAS entry and a second manifest row, never duplicated bytes.
- [ ] Two calls on one `ingestId` dispatched concurrently through the client gateway are serialized rather than interleaved: an original and its retry racing after a lost response leave the spool byte-identical to the single-call outcome, and the reaper cannot evict a stream while a call on it is in flight.
- [ ] An ingest stream older than `max_ingest_stream_lifetime` is terminated at its next call regardless of how recently a chunk arrived — and, absent any call, is evicted by the next reaper pass, which releases its reservation and count slot and deletes its spool, asserted by an `AttachmentIngestInit` refused at the count bound before the pass and admitted after it — so neither a trickle of keep-alive chunks nor silent abandonment holds spool capacity past the lifetime bound.
- [ ] A configuration declaring `ingest_spool_max_bytes` below 2 × `max_attachment_ingest_bytes` is refused at config load — never accepted into a running daemon where every maximal Init would refuse `artifact.ingest_capacity_exhausted` permanently.
- [ ] `ArtifactDelete` on a manifest whose CAS payload is shared with another manifest deletes the manifest and leaves the payload; deleting the last manifest naming that payload reclaims the bytes.
- [ ] `ArtifactDelete` on a manifest that another manifest names as its `subject` is refused with `artifact.delete_blocked` (409) and names the referencing manifests — at most the first 50 ids in ascending order plus the total count, so the refusal frame always fits the transport ceiling; no derivative is ever left with a dangling `subject`.
- [ ] An `ArtifactPublish` whose `subject` names a manifest outside the request's session is refused with `artifact.not_found` (404) — subject resolution is session-scoped — so a session's deletion sweep never encounters a derivative whose `subject` resolves outside the session.
- [ ] `ArtifactDelete` by a caller outside the permission-matrix Delete rule — including a collaborator targeting a manifest whose `created_by` names another participant or is NULL (daemon-produced, so owner-only under the fail-closed scope) — is refused with `artifact.delete_forbidden` (403) before any mutation; the target manifest, its payload references, and the CAS bytes are unchanged by the refusal.
- [ ] `ArtifactDelete` on a manifest carrying a retained `relay_cek_ciphertext` reports `rePublishForeclosed` — derived from the deleted row's retained CEK alone, with no relay round-trip — rather than deleting silently, and any still-pinned recipients continue to fetch until the blob's own refcount-zero or TTL.
- [ ] A delete whose post-commit unlink fails with a non-`ENOENT` error reports `payloadDisposition: "reclaim_pending"`, and a later pass of the periodic orphan sweep reclaims the entry without a daemon restart.
- [ ] A collaborator-produced artifact — ingested via `AttachmentIngest` or published via a caller-attributable `ArtifactPublish` — records that caller in `artifact_manifests.created_by` at insert and is deletable by its creator under the permission-matrix Delete rule; a daemon-produced artifact records NULL and stays owner-only.
- [ ] An unresolved-attachment marker for a shared artifact carries the manifest's own non-`pinned` replication status as its cause — a `quota_exceeded` manifest yields a `quota_exceeded` marker and an `expired` one an `expired` marker, never a nearest-fit `over_cap`.
- [ ] A fetch that meets `artifact.relay_expired` (410) **or a zero-row `artifact.no_access_key` (404)** transitions the **fetching** node's own manifest row from `pinned` to `expired` before the error surfaces — asserted on the `ArtifactFetchAuthorize` mint arm, on a mid-fetch resume arm, and on the zero-row arm left by a cascading blob deletion alike — so an unresolved-attachment marker rendered afterwards reports the `expired` cause from the persisted row rather than meeting a still-`pinned` manifest that matches no member of the closed union. A row already carrying a degraded status is left unchanged, and a publisher re-publish that re-pins returns the row to `pinned`, so the status tracks availability instead of latching.
- [ ] Session deletion removes the session's local artifacts and manifests and reclaims every payload whose derived refcount reached zero — one row-deletion transaction, unlinks strictly after commit — without touching relay copies.
- [ ] A simulated crash between a reclaim's row-deletion commit and its payload unlink leaves every surviving manifest readable and no manifest pointing at missing bytes; the orphaned payload is gone after the next daemon boot's orphan sweep.
- [ ] A same-hash publish racing a reclaim's post-commit unlink never yields a manifest over missing bytes: a reference inserted before the reclaimer's in-exclusion refcount re-check aborts the unlink, and a writer arriving after the unlink misses the existence check and stores fresh bytes — asserted in both interleavings, and for the boot sweep under the same per-key exclusion.
- [ ] A fetch mint that resolves exactly one recipient row for a node with no active attachment by the authenticated participant in the blob's session — detached, or another participant's node — is refused with `artifact.fetch_unauthorized` (403), never `artifact.no_access_key`.
- [ ] Every turn-scoped attachment carrier types its attachment list as `ArtifactId[]`; an element the turn cannot resolve or deliver appears as an explicit unresolved marker in its declared position, naming the cause, and element order is preserved end to end.

## Resolved Questions and V1 Scope Decisions

- No blocking open questions remain for v1.
- V1 decision: shared artifact replication is manifest-first with deferred payload transfer. Small-payload synchronous optimization does not change the external contract in v1. (Clarified 2026-07-08: "deferred payload transfer" means the payload is decoupled from event delivery and fetched explicitly — it does NOT mean cross-node payload availability is V1.1-deferred. The payload leg is the §Cross-Node Artifact Relay (V1) eager pin + authenticated fetch.)
- V1 decision (2026-07-08 scope pull-forward, [ADR-015 amendment](../decisions/015-v1-feature-scope-definition.md#amendment-2026-07-08-v11-deferred-features-3--2-cross-node-shared-artifacts-pulled-into-v1)): cross-node payload availability while the publisher is offline is a V1 guarantee, delivered by eager relay pin at publish. Direct-first fetch is criterion-gated (ADR-015 C4) on a shipped direct daemon transport; the V1 wire format already carries both paths.
- V1 decision (2026-07-08): retention is a named tier set (`volatile` 24 h / `default` 7 d / `extended` 30 d), not free-form TTLs; relay deletion triggers are refcount-zero and TTL, whichever comes first, with a grace lease for in-flight fetches.
- V1 decision: participant-specific fine-grained artifact redaction is out of scope for v1. Visibility remains class-based, and any redacted shareable form must be published as a separate derivative artifact.
- V1 decision (2026-07-09, Codex round-2): artifact CEKs wrap to **durable per-`(participant, node)` artifact-encryption X25519 keys** (daemon-generated; private halves under Spec-022 master-key custody in the daemon-local `artifact_encryption_keys` table; public halves distributed as Ed25519-identity-signed attestations over the established pairwise relay channels). Wrapping to the ADR-010 session-ephemeral X25519 keys is prohibited — they are zeroed at session end, which would orphan every relay-held CEK on restart and silently void the offline-fetch guarantee. The recipient set is the attested `(participant, node)` set at publish time; late join heals via publisher-online re-publish; post-quantum hybrid wrapping (PQXDH-class) is a named non-goal for V1 — the MLS (RFC 9420) V1.1 upgrade path is where the key-agreement layer evolves.
- V1 decision (2026-07-09, Codex round-4): artifact-key rotation **retires rather than replaces** — the daemon-local store keeps retired keys by thumbprint until every relay row wrapped to them is delivered or TTL-expired (30 d ceiling), so rotation never strands a within-TTL pinned blob behind an offline publisher. Erasure destroys active and retired keys together. The retention predicate is evaluated locally as `retired_at + 30 d + a 48 h skew margin` (the tier ceiling bounds it on the relay clock; the margin absorbs daemon-vs-relay skew), never by querying the relay.
- V1 decision (2026-07-09, Codex rounds 5–6; mechanism scoped 2026-08-08): the relay fetch token is **`(participant, node)`-scoped**, the binding made at mint per RFC 9449 §5 — the issuer stamps `(participant, node)` as issuer-signed claims, and sets `cnf` from that call's DPoP proof (a bare `cnf`/jkt thumbprint is possession material, not an identity, so no thumbprint→node registry exists to maintain). Participant-only scoping was insufficient once recipient rows became per-node: the relay could neither select the correct wrapped CEK for a multi-node participant nor safely attribute an `ArtifactFetchComplete` ack, and a caller-supplied node id would let one compromised node mark its siblings delivered. The ack is idempotent, so a lost ack response is retry-safe. **2026-08-08 scoping** (extends the Plan-014 relay-scope readiness-audit delta, which pins the issuer-integration seam): the round 5–6 wording said the issuer resolves `node_id` from "the authenticated node-attach context", which named a mechanism V1 does not supply — **V1 defines no node-identity credential** ([security-architecture.md §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature)), so the mint authorizes at **participant granularity**, the same bound the Plan-006 T4.10 registrar resolves at. What survives verbatim is the wire property this decision bought: the node half's **value** is issuer-derived from the caller's own attach-state rows, never a trusted caller-supplied raw node identity (narrowed 2026-08-08: a validated opaque selector over the caller's own attachment rows stays permissible — the issuer still derives the value and refuses any row not owned by the authenticated `sub`). The §Acceptance Criteria clause "one node of a participant cannot mark a sibling node delivered" accordingly holds of the relay's ack-row resolution given a token minted for that node, and that criterion is now scoped in place. The **compromised** same-participant node is the named V1 residual, and it is **not** bounded to delivery attribution — an earlier draft of this note said so and was wrong. It costs **availability and attestation integrity**, on two legs: the forged ack (premature refcount-zero GC with no offline remedy, Fetch step 6), and the artifact-key attestation spoof, which redirects a sibling's later CEK wraps to an attacker-held key and **locks that honest sibling out** of artifacts it is entitled to (Publish step 3). A second draft called the latter a **confidentiality** residual; that too was wrong and is retracted — an attached sibling is already an intended recipient holding the CEK under its own attested key, so the spoof widens no plaintext reach, and plaintext reach by an authorized node is participant-granularity sharing working as designed. §Required Behavior and the two §Acceptance Criteria rows carry the matching threat-model scope. The closure for both is the [cross-plan-dependencies.md §5 V1.1+ Cross-Plan Extensions](../architecture/cross-plan-dependencies.md#v11-cross-plan-extensions) Plan-018/Plan-003 node-identity leg.
- V1 decision (2026-07-09, Codex round-6): `ArtifactUploadComplete` carries its own Spec-021 registry row (`artifact.upload.complete` — the sixth relay row; the finalization that lets `replicationStatus` reach `pinned` cannot be the one relay method outside the rate-limit surface), and the late-join no-access-key state is a **reserved error contract** — `artifact.no_access_key` (404), distinct from `artifact.fetch_unauthorized` (403), so clients can surface the publisher-re-publish remedy instead of misreporting an auth failure.
- V1 decision (2026-07-09, Codex round-7): artifact-key generation and attestation are **join-sequence obligations** — the keypair is generated at the node's first session attach (durable across sessions) and the attestation is sent immediately after the ADR-010 pairwise handshake with each peer, never lazily at first fetch. Lazy generation would silently demote an attached-but-never-yet-fetching node to the late-join `artifact.no_access_key` path, voiding the offline guarantee for a node that was present at publish; with eager attestation, only a genuinely concurrent attach-vs-publish race falls to late-join semantics.
- V1 decision (2026-07-09, Codex round-8): relay-side integrity is **digest-level only** — the signed chunk manifest and `cekCommitment` are E2E payload the relay never parses, so per-chunk, key-commitment, and plaintext verification are exclusively recipient-side; the relay's one keyless check is re-hashing the assembled ciphertext against the init-declared ciphertext digest — its CAS key; the plaintext CAS digest never reaches the relay (terminology tightened 2026-07-09, round 11) — at `ArtifactUploadComplete` (nothing pins unverified), and a re-pin re-verifies the stored copy before short-circuiting — so publisher re-publish also repairs at-rest corruption, closing the healing loop that recipients-detect-only verification would otherwise leave open.
- V1 decision (2026-07-09, Codex round-9): rotation is a **re-attestation event** — the rotating node immediately re-attests its new active key to every session peer over the pairwise channels (identical signed-attestation payload; the ordered, authenticated channel makes last-received-wins sound), and publisher caches hold the **latest** attestation per `(participant, node)`, never a session-frozen snapshot. Without this, a stale cache could wrap fresh CEKs to a retired thumbprint arbitrarily late in a long session, minting relay rows whose TTL outlives the retired key's local purge bound — the recipient would purge the only private key while an undelivered blob still needed it. With it, late wraps are confined to a seconds-scale race the existing 48 h purge margin absorbs.
- V1 decision (2026-07-09, Codex round-9): late-join re-publish **pairs the relay re-pin with a re-emitted `artifact.published` event in the current membership epoch** (identical signed manifest content — idempotent by digest). Relay recipient rows alone are never an access grant: the `chunkManifest` and `cekCommitment` verification material rides E2E events, and pre-join events are undecryptable by design — a joiner holding only a wrapped CEK could fetch bytes but never verify them.
- V1 decision (2026-07-09, self-review hardening): the publishing daemon **retains each relay-bound artifact's CEK locally** — master-key-wrapped `relay_cek_ciphertext` on the manifest row (Spec-022 custody) — because re-publish re-wraps this same CEK for new recipients and the relay holds only recipient-wrapped copies; without local retention the publisher could not extend late-join access except by re-encrypting and re-uploading under a fresh key. The retained copy is not a per-participant erasure target — it dies with the manifest row or the daemon master key (the `Spec-022 §PII Data Map` artifact-payload posture).
- V1 decision (2026-07-09, self-review hardening): the intended-recipient set **excludes the publishing node itself** — it holds the plaintext and never fetches, so a self-row could never ack and would hold every blob at full TTL, silently defeating the store-until-delivered refcount economics; the publisher's other nodes are ordinary recipients.
- V1 decision (2026-07-09, self-review hardening): a publish whose intended-recipient set is empty (a solo session) **uploads nothing** — the manifest stays `pending_replication` and the explicit re-publish toward the first attested peer performs the initial pin. Uploading to nobody is pure cost ending in a vacuously-delivered zero-row blob; skipping preserves both the GC economics and the membership-epoch boundary (no automatic share-forward on join).
- V1 decision (2026-07-09, Codex round-11): a successful re-pin **refreshes the blob's TTL lease** — `expires_at` re-anchors to now + the declared tier's TTL, because a re-pin is a fresh grant of the same bytes (quota-attributed and rate-limited like any upload-init): without it, a late-join re-publish near the original expiry could mint recipient rows and a current-epoch event for a blob the hourly sweep deletes before the joiner fetches, silently voiding the `artifact.no_access_key` remedy. Same round, terminology precision: the relay finalize verifies against the init-declared **ciphertext digest** (its CAS key) — the plaintext CAS digest never reaches the relay — and `relay_cek_ciphertext` is retained from the first **relay-bound** publish (including a solo-session publish that uploads nothing), never only at pin time, or the empty-set re-publish path could not honor the same-CEK contract.
- V1 decision (2026-07-09, Codex round-4): delivery is **acknowledgement-driven**, not transport-inferred — an authenticated `ArtifactFetchComplete` (a fifth Spec-021 relay registry row) sent after chunk + `cekCommitment` + CAS verification is the sole writer of `delivered_at`, so refcount GC can never delete the last relay copy before the recipient has verifiably decrypted it. An un-acked fetch leaves the blob to its TTL (a recoverable leak) rather than risking an unrecoverable premature delete.
- V1 decision (2026-07-09, Codex round-2): the crypto-shred backup posture names its two real mechanisms — a control-plane backup/PITR retention window bounded ≤ the erasure SLA (30 d relay-TTL ceiling), or wrapped-CEK envelopes under a separately-destroyable KEK (`Spec-022 §Daemon Master Key` precedent) — because Postgres PITR/WAL archiving is database-wide and cannot exclude rows.
- V1 decision (2026-07-09, Codex round-2): `retentionTier` and size/chunk accounting form the **relay-visible lifecycle envelope**, carried as authenticated plaintext on `ArtifactUploadInit` and mirrored inside the signed E2EE payload (tier tampering is recipient-evident); only the content-integrity fields are relay-opaque.
- V1 decision (Tier-7 NS-19 audit): the `artifactType` discriminator is closed to six values — the five families above plus `workflow_output` (`Spec-017 §Output Mode Specification`). The Required-Behavior families list admits "at least" the five, so `workflow_output` is an additive sixth discriminator value, not a families-list rewrite; the closed typed union is the contract in [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md). Content-only amendment — Spec-014 stays `approved`.
- **2026-08-12 — relay-scope readiness-audit delta (restoring).** The Plan-014 targeted delta audited this section's contract surface against every corpus row consuming it and restored both files `review → approved` in one swap. Three dispositions are recorded here because they bear on this spec's own reading: (1) the envelope-interior application-payload discriminator that Publish step 3's artifact-key attestation rides is **Plan-008-owned and now ratified** — this spec and Spec-008 both place message families inside the one pairwise envelope while refusing a new frame message type, and the delta ratified a discriminated union over a required `kind` tag with a consumer registration seam (Plan-014 D-014-5 / CP-014-4 ⇄ Plan-008 CP-008-16), through which this spec's attestation registers as `artifact_key_attestation`; nothing in this section's wire contract changes, and Spec-008's body was not edited; (2) the fetch-authorization node selector adopts a validated opaque selector over the caller's own attachment rows — the server-minted `attachmentId` — so the node half stays issuer-derived, the multi-node deferral in Fetch step 5 is discharged, and no wire field of this spec is committed by the choice beyond that selector; (3) the size/quota/retention defaults in this section are the normative source and gain an owned typed surface under Plan-014 for CP-014-3's operator-tunability obligation — the values here are unchanged.

- **2026-08-17 — V1 decision (ingest-protocol hardening amendment): completion is idempotent, both ingest byte ledgers are serialized, each stream is single-flight, and the `expired` marker cause gets the writer it was missing.** Five accepted findings (Codex PR #341 round 5) against the stream protocol this spec authored the same day, all folded into the sections that own them, none of them adding an interface, a wire member, an error code, a table, or a column. **(1) `AttachmentIngestComplete` is retry-idempotent.** The trio's dispatch contract already promised that a transport failure means "retry the same call", and that promise was true only of `Chunk`: a lost `Complete` response left the caller holding a completed stream it could not name and a 100 MB upload it would have to repeat. A completion record on the stream's registry entry — the returned response, stamped with the committed digest — makes the retry replay verbatim. Its scope is deliberately one carved exception to terminal invalidation, not a general relaxation: a `Chunk` on a completed stream is still a 409, and the record shares the entry's in-memory lifetime, so the residual past `max_ingest_stream_lifetime` is a second manifest row over one deduplicated payload rather than lost bytes. A durable record was rejected — it would mint a table for a transient whose lifetime is already bounded. The brief for this leg described the record as "keyed by `ingestId` + declared digest"; `AttachmentIngestCompleteRequest` carries only the `ingestId`, so a _divergent_ Complete has no wire form and the digest is recorded as a **stamp verified against the entry's own committed state** — a fail-closed defence-in-depth check in the Fetch step 5 multi-match idiom, not a live discriminator, and no new wire member. **(2) Both ingest byte ledgers reserve before they install.** The quarantine aggregate cap and the aggregate spool reservation were each specified as a bound to test, with nothing saying the test and the spend are one section — the classic check-then-act on a shared budget, breachable by one payload per racing caller by submitting in parallel instead of in series. Serializing quarantine admission alone was rejected as an asymmetry: the spool ledger is the identical race, so admission became a serialized reserve-then-install section in the same amendment. **(3) Each stream is single-flight, and the reaper takes the same exclusion.** Sequence validation, spool append, running-count and digest advance, and acknowledgement are one read-modify-write; the reaper's eviction path had no exclusion at all and could delete a spool mid-append. Both are closed by a critical section keyed by `ingestId`, and §Implementation Notes now states this spec's whole exclusion order — per-`ingestId` → the admission ledger → at most one of per-`storage_path` or the quarantine directory — as one total acyclic order rather than three unrelated locks. **(4) The `expired` unresolved-marker cause has a writer.** The round-3 fold widened the cause union to carry the manifest's `replicationStatus` verbatim, but no surface wrote `expired` to a local manifest: the relay's TTL sweep and eviction run past the node boundary and emit no event, so a recipient's row sat at `pinned` forever and an expiry-blocked attachment matched **no** member of a closed union. The fetching daemon now writes `pinned` → `expired` on **either** fetch-path refusal that establishes the payload is no longer obtainable — `artifact.relay_expired` (410), scoped to the code rather than to the mint so the resume arm cannot leave the defect in place, **and** a zero-row `artifact.no_access_key` (404) — as a local single-writer update on a value the column already permits. The 404 arm was added on the same day's review of this very leg, and without it the rule would have missed a whole class of losses: refcount-zero delete and watermark eviction remove the blob row and `artifact_relay_recipients` cascades from it (Fetch step 6), so those fetches resolve zero rows and are refused 404 rather than 410. Binding the rule to the fact rather than to one code also makes it independent of a disposition this spec leaves open — whether the hourly TTL sweep retains the blob row at `state = 'expired'` or deletes it like the other GC paths — which is flagged in §Fetch as a genuine gap rather than settled here (tracked as [BL-152](../backlog.md)). The debit is that `no_access_key` has three indistinguishable producers (GC'd blob, post-publish joiner, fail-closed thumbprint-collision drop), so `expired` is deliberately widened to mean _this node cannot obtain the payload; the remedy is a re-publish_; a separate union member for the joiner case was rejected because the distinction is unobservable to the node doing the writing. **(5) The Init-refusal zero-state criterion became runnable.** Its prior form asserted "no stream state created" by sending a `Chunk` on the refused id, which an Init refusal never issues — an unrunnable assertion needing a fabricated identifier. It is replaced by two admission probes: after a count-bound refusal, terminating one stream admits the next Init; after a reservation-arm refusal, a fitting declaration admits. A leaked slot or reservation then shows up as a refusal that outlives its cause, with no invented id and no new wire field.

- [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) — the allow-list-not-block-list rule ("blocking specific extensions is a weak protection method on its own"), `Content-Type` distrust ("provided by the user, and as such cannot be trusted, as it is trivial to spoof"), the named extension bypasses (double extensions, null bytes, home-grown regex), the random-filename storage rule, and the explicit insufficiency of signature checking alone ("This should not be used on its own, as bypassing it is pretty common and easy"). **Its limits text bounds upload size and download request rate only — it specifies no per-request file-count cap**, which is why the count cap below cites ASVS instead.
- [OWASP ASVS 5.0.0 §V5 File Handling](https://github.com/OWASP/ASVS/blob/v5.0.0_release/5.0/en/0x14-V5-File-Handling.md) (released 2025-05-30) — **5.2.1** size bounded to what the application can process without denial of service; **5.2.2** extension-match paired with content verification, naming magic bytes as one member of a set that also includes image rewriting and format-specific libraries; **5.2.3** and **5.2.4**, the two requirements that actually specify a "maximum number of files" (archive-entry count before decompression, and a per-user file-count quota) — the source for `max_attachments_per_carrier`; **5.3.2** internally generated file paths rather than user-submitted filenames; **5.2.6** pixel-flood limits and **5.4.3** antivirus scanning, both recorded above as named V1 non-goals.
- [CERT IDS04-J — Safely extract files from ZipInputStream](https://wiki.sei.cmu.edu/confluence/display/java/IDS04-J.+Safely+extract+files+from+ZipInputStream) — the decompression-bomb accounting the cheat sheet links; cited for the class V1 avoids outright by not unpacking archives at ingest.
