## Purpose

Define the approval model, permission scopes, and trust boundaries for execution in shared sessions.

## Scope

This spec covers approval requests, approval scopes, remembered grants, and the distinction between session membership and local execution trust.

## Non-Goals

- Transport protocol details
- Notification policy

## Required Behavior

- The system must distinguish:
  - session membership authorization
  - runtime-node trust
  - run-level approval policy
  - tool- and resource-level permission grants
- The membership role model must distinguish at least `viewer`, `collaborator`, `runtime contributor`, and `owner`. **Run-control interventions** — `steer`, `interrupt`, `cancel`, and `rollback`, the canonical intervention types of [Spec-004 §Interfaces And Contracts](./004-queue-steer-pause-resume.md#interfaces-and-contracts), together with the orchestration-layer `run.pause` / `run.resume` mutations, which are governed identically — are authorized by **session write access, not run authorship**: any participant holding `collaborator` or `owner` may intervene on any run in the session, including runs authored by another participant and runs targeting another participant's agent. Within the intervention authorization path, run authorship is audit metadata and never an authorization input — the same rule [ADR-011](../decisions/011-generic-intervention-dispatch.md) applies to `initiatorId`. This grant is **bounded by the node-trust rule below**: where the target run executes on **another participant's runtime node**, the intervention is admitted only under that node owner's authority — an approval in the `tool_execution` category per [Spec-024](./024-cross-node-dispatch-and-approval.md)'s dispatch rules — never under session role alone, so cross-node steering is a request, never standing authority. Authorization to **direct** a run is distinct from executing **as** its initiator: a turn opened by an accepted `steer` executes under the **steering participant's** effective Cedar principal — resolved from the verified caller identity the daemon admitted the steer under (the PASETO `sub` that authorized the intervention, durably recorded on the accepted intervention), never from any client-supplied actor field, which stays informational per [ADR-011](../decisions/011-generic-intervention-dispatch.md) — and never the run initiator's, so the sensitive actions a steered turn produces adjudicate against the director's own policy and remembered rules, and one participant's remembered grant never authorizes another participant's direction. Where a single turn's input composes contributions from more than one participant, each sensitive action in that turn adjudicates under **every** contributing principal and applies only when all pass — a fail-closed conjunction, with any required approval asked rather than skipped. Turns opened by the run's own continuation or by the initiator's inputs keep the run-initiator principal unchanged.
- Sensitive actions must require approval or prior grant according to policy. This includes at least destructive git operations, out-of-boundary file writes, unrestricted network access, and high-risk tool execution.
- The canonical approval category enum is:
  - `tool_execution` — tool call approval
  - `file_write` — out-of-boundary file writes
  - `network_access` — unrestricted network
  - `destructive_git` — force push, branch delete
  - `user_input` — freeform questions from agent
  - `plan_approval` — proposed plan review
  - `mcp_elicitation` — MCP server input
  - `gate` — workflow phase gate
  - `human_phase_contribution` — phase-level human contribution (Spec-017 `human` phase submission; SA-12 addition per BL-097 Wave-1 synthesis)
- Approval requests must record requester, target scope, requested capability, and expiry where applicable.
- Approval resolution must record approver, decision, and effective scope.
- Membership in a shared session must not imply authority to execute on another participant's machine.
- `runtime contributor` role may allow a participant to attach their own runtime nodes, but it must not imply authority over another participant's node.
- A participant's own runtime node may be trusted as the default execution host for that participant within its local daemon policy envelope, but that trust must not bypass approval rules for out-of-envelope or high-risk actions.
- Driver-native permission flows must be normalized into the canonical approval model. Provider-initiated mid-run asks normalized this way ([Spec-006 §Driver Ask Events](./006-session-event-taxonomy-and-audit-log.md#driver-ask-events)) are **bounded and fail-closed** (Part-B fail-closed follow-up, 2026-07-17): every pending ask carries a concrete expiry deadline stamped at creation (`expiresAt` on the `driver_ask.requested` payload — audit-visible, never an implicit daemon-internal timer); the wait is modeled **timer-OR-answer, whichever first**, with the deadline persisted durably so a daemon restart neither loses nor indefinitely extends a pending ask (restart re-arms from the stored deadline; replay-stable) — the surveyed orchestration-engine discipline ([Temporal human-in-the-loop approvals](https://temporal.io/blog/human-in-the-loop-approvals) models the wait as a durable timer racing the answer, consulted 2026-07-12) — and expiry **never auto-approves**: silence is a denial, never a grant, at every tier and posture (the surveyed bounded-approval systems cancel or reject on timeout — GitHub deployment approvals auto-cancel at their 30-day bound ([GitHub Actions deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), consulted 2026-07-12) — none grants on silence). On expiry the ask resolves to its typed per-kind outcome (§Resolved Questions and V1 Scope Decisions) and the emitted `driver_ask.expired` row closes it; an ask raised by a provider-native subagent ([Spec-016 §Provider-Native Subagents](./016-multi-agent-channels-and-orchestration.md#provider-native-subagents)) follows the same expiry path — it surfaces on the session's approval/interactive surface and times out like any other ask, never silently stalling its parent run. Expiry and idle-reaping are **decoupled but coordinated**: any liveness exemption the orchestration layer grants a run for its pending ask (the pending-blocking-work hard-skip from the idle sweep) MUST end the moment the ask expires or resolves, returning the run to the ordinary idle path — an unanswered ask is therefore a bounded wait, never a designed-in leak that shields a zombie session from reaping indefinitely.

> **Amendment (approved spec — 2026-07-02, capability-enhancement campaign B20).** Required Behavior gains a canonical **execution posture** — a provider-uniform authorization input layered onto the trust distinction above (session membership authorization, runtime-node trust, run-level approval policy, tool- and resource-level permission grants) — and specifies how driver-native sandbox and permission flows normalize into it, extending the driver-normalization obligation immediately above. It also pins the authorization rule for daemon-registered session callback tools. No section is renamed or removed; the additions are the bullets below.

- Each run carries an **execution posture**: `executionPosture { mode: 'trusted' | 'workspace-sandboxed' | 'readonly-sandboxed', networkAccess: 'none' | 'allowed-domains' | 'full', allowedDomains?: string[], writableRoots: string[], profileName?: string, credentialPolicyRef?: string }`. `credentialPolicyRef` is a **content-addressed reference** to the daemon's curated credential-policy artifact in effect: `"sha256:<hex>"` over the [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) JCS-canonicalized artifact document `{schemaVersion: 1, denyPaths: string[], denyEnvVars: string[], envNameMatch: 'case-sensitive' | 'case-insensitive'}` — where `denyPaths` holds the **daemon-expanded canonical absolute effective paths** at policy-resolution time (tilde and environment references expanded, symlinks resolved, platform case/relative components normalized), never raw config strings like `~/.ssh`, and `denyEnvVars` holds environment-variable names **canonicalized to the host's environment-name case semantics** at that same resolution time — a host whose process environment matches names case-insensitively folds each name to a single canonical spelling (so `GITHUB_TOKEN` and `github_token` collapse to one entry), a case-sensitive host keeps them verbatim, and the daemon spawn-env strip matches under those same host rules — with the host's matching mode itself recorded as **`envNameMatch`** in the hashed document, because canonicalizing the names is not sufficient: a case-insensitive host strips **every** spelling of a curated name while a case-sensitive host strips only the exact one, so two hosts sharing a `denyEnvVars` list but differing in match mode enforce **different** effective boundaries and MUST therefore carry **different** refs (with `envNameMatch` hashed, ref equality means the same denied set _and_ the same strip rule) — so a curated secret cannot survive under an alternate spelling and ref equality still means effective-boundary equality **across** hosts, not only within one (this env-name predicate is deliberately distinct from the filesystem case-normalization governing `denyPaths`: a host may fold filesystem paths yet still distinguish env-var names, or the reverse) — and the daemon **lexicographically sorts and dedupes both arrays before hashing** (RFC 8785 canonicalizes object members, not array order — unsorted arrays would give order-dependent refs), so ref equality means effective-boundary equality across hosts and homes (the raw curated list is daemon configuration; the artifact records what it resolved to for this run) — REQUIRED on both sandboxed modes so auditors can reconstruct exactly which credentials were denied/scrubbed for this run without embedding the raw (installation-revealing) list in the audit log. Content addressing makes the artifact immutable and self-deduplicating by construction (identical policy ⇒ identical ref; two runs carrying the same ref carried the same policy), and the ref can never dangle: the daemon persists the artifact row **write-ahead** — before the first posture stamp that cites it (the same ordering discipline as ADR-019's spawn-intent registry) — and retains it at least as long as any run event citing it (compaction/shred follow the audit-stub retention class). Storage is daemon SQLite; the table's CREATE lands with the campaign B13 code lane that implements posture stamping (the pattern B1 set for the terminal-backstop index shipping with B11's schema work). The API Payload Contracts mirror gains this field with this bundle. `allowedDomains` is meaningful only with `networkAccess: 'allowed-domains'` and holds exact hostnames or leading-`*.` wildcard patterns — hostname-matched, per the domain-fronting caveat below. `writableRoots` holds absolute paths; the daemon canonicalizes each root (symlink-resolved real path; relative paths rejected) before the posture enters Cedar evaluation, so policy always compares canonical paths, never raw input. The posture is a **Cedar authorization input**, not merely a spawn-time knob: policy MAY require a minimum posture per trust level (a less-trusted context cannot select a weaker sandbox than policy allows), evaluated inside the same principal-action-resource-context decision as every other approval category. **Minimum-posture comparison is per-axis, never cross-axis**: strictness is defined independently on each axis — `mode`: `trusted` < `workspace-sandboxed` < `readonly-sandboxed`; `networkAccess`: `'full'` < `'allowed-domains'` < `'none'` (tier-level; between two `'allowed-domains'` postures policy MAY additionally require a domain-subset relation, computed daemon-side under canonical host-pattern rules — hostnames normalize to lowercase punycode FQDNs with no scheme / port / trailing dot; patterns are exact FQDNs or single-form wildcards `*.suffix`; exact ⊆ exact iff equal, exact ⊆ `*.suffix` iff the host is a **proper** subdomain of `suffix` (the bare suffix is not covered — list it exactly), `*.s1` ⊆ `*.s2` iff `s1` equals or is a proper subdomain suffix of `s2`, a wildcard is never ⊆ an exact, list A ⊆ list B iff every pattern in A is contained by some pattern in B, and any other pattern form is incomparable — floor unsatisfied, fail closed (the daemon computes the subset verdict and passes it to Cedar as context; Cedar never re-implements pattern math)); `writableRoots`: compared by **canonical path containment**, not literal array membership — a caller's roots satisfy a floor iff **every** canonical caller root is contained by (equals or is a descendant of) some canonical floor root, exactly parallel to the intra-`'allowed-domains'` subdomain-subset above, so a `workspace-sandboxed` caller narrowing a `["/repo"]` floor to `["/repo/src"]` writes a strictly smaller effective set and **satisfies** the floor rather than being rejected for choosing a safer posture. The two non-sandboxed modes are the well-defined endpoints of that containment: `readonly-sandboxed` writes nothing (∅, contained by every floor, so it satisfies **any** roots floor and is never rejected for choosing a safer posture), while `trusted`'s canonical `[]` denotes _no write limit_ (the unconstrained set — the flip noted below), so a `trusted` caller satisfies only a `trusted` floor, a `trusted` floor is satisfied by every posture, and a `trusted` caller failing a sandboxed floor is rejected on the `mode` axis, never admitted by misreading its `[]` as 'nothing writable' — and a posture satisfies a floor iff **every** axis independently meets its floor, so cross-axis trade-offs (for example `readonly-sandboxed` + `'full'` network versus `workspace-sandboxed` + an allow-list) are incomparable by construction and never substitute for one another. `profileName` resolves to **daemon-side posture presets** so that named profiles are provider-uniform rather than references into a provider's own profile store. **Cross-field invariants (fail closed)**: the daemon validates the posture object before it enters Cedar evaluation or spawn — `networkAccess: 'allowed-domains'` requires a present, non-empty `allowedDomains` (and `allowedDomains` MUST be absent under `'none'` / `'full'`); `mode: 'readonly-sandboxed'` requires `writableRoots: []`; `mode: 'trusted'` (no OS-sandbox enforcement) MUST be **supplied** as `networkAccess: 'full'` + `writableRoots: []` — the canonical form denoting no OS-enforced constraint, so no posture record implies a constraint nothing enforces; any other combination under `mode: 'trusted'` is a violating combination and is **rejected** like every other cross-field violation — the daemon never rewrites a restrictive request into the permissive canonical form — and symmetrically with the `allowedDomains` clause above, `writableRoots` is meaningful only in the two sandboxed modes: under `mode: 'trusted'` the canonical `[]` denotes _no OS-enforced write constraint_ (unconstrained), the opposite of the same value under `readonly-sandboxed` (nothing writable), so audit reconstruction MUST read `writableRoots` in conjunction with `mode`, never in isolation. The same record-equals-enforced-boundary discipline governs `credentialPolicyRef`: a curated credential policy is in effect only as part of a **sandboxed** posture's realization (the Claude leg supplies the deny-list under its sandboxed-posture settings; the Codex leg maps `denyPaths` into the sandbox permission profile — a `mode: 'trusted'` run has no sandbox to realize), so the ref is present on the two sandboxed modes and MUST be **absent** under `mode: 'trusted'`, whose canonical form records no enforced credential constraint just as it records no network or write constraint; a `credentialPolicyRef` present under `mode: 'trusted'` would imply an enforced credential boundary nothing applies and is **rejected** exactly like every other cross-field violation (the run is refused, never silently normalized). A violating combination is **rejected** — the run is refused, never silently normalized into a permissive state — so implementations cannot diverge on whether an ambiguous posture is invalid, deny-all, or permissive.
- The **effective posture is recorded on the run's `run.running` event** — the post-setup-gate spawn-success transition: Plan-004's gate seam admits `queued → starting`, then setup gates (Plan-010's execution-root gate among them) run **before** `driver.startRun`, so the resolved workspace root, shared-`.git` allowance, and preset-resolved profile are final only when `running` fires — a `run.starting` stamp would be premature or wrong. The `executionPosture?` carrier field registers with [Spec-006 §Run Lifecycle](./006-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)'s run-state payload (2026-07-02 campaign B1 amendment item (11), PR #173 — a named merge prerequisite of this bundle; the typed wire mirror rides `RunStateChangeEvent.executionPosture?` in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), and **this bundle extends that mirror with `credentialPolicyRef` as a merge-blocking step of its own merge series** — the field is spec'd here first, the mirror gains it before this bundle lands) — so the audit trail records the **complete effective posture object**, never a named-fields subset — and it survives compaction: the Spec-006 audit-stub projection preserves the `executionPosture` object on posture-bearing `run.running` rows — including `credentialPolicyRef` **whenever it is present**, i.e. on the two sandboxed modes (a `mode: 'trusted'` row carries no ref, matching the absent-under-`trusted` invariant above, so the stub neither requires nor fabricates one) (B1 stub contract), so the boundary stays reconstructable after the payload compacts — including `allowedDomains` whenever `networkAccess: 'allowed-domains'` (the allow-list _is_ the security boundary in that mode; reviewers MUST be able to reconstruct exactly which hosts were reachable) and `profileName` whenever the posture was preset-resolved.
- Driver-native sandbox and permission flows are normalized into this canonical posture, with the realization recorded per driver:
  - **Codex leg** — `native`: built-in permission profiles (`:read-only`, `:workspace`, `:danger-full-access`) plus named `[permissions.<name>]` profiles resolved via `default_permissions` ([Codex permissions docs](https://developers.openai.com/codex/permissions), fetched 2026-07-02), plus per-turn `sandboxPolicy` on `turn/start` (app-server schema, regenerated at `codex-cli 0.141.0` — provider-wire reference `docs/reference/provider-wire/codex.md`, campaign B19 — PR #176, a named merge prerequisite of this bundle). **Legacy-settings conflict fails closed**: per the same permissions docs, legacy `sandbox_mode` / `sandbox_workspace_write` config keys (or a `--sandbox` flag) shadow `default_permissions`, so the driver MUST NOT pass `--sandbox`, MUST override those legacy keys in every config layer it controls when realizing a posture, and MUST refuse the run when a loaded config still carries them un-overridden — a run is never recorded under a posture Codex does not actually enforce. The same whole-config verification binds named profiles: profiles resolve through Codex's normal config-layer model (a higher-precedence layer can add or replace entries in a same-named `[permissions.<name>]` profile — same permissions docs), so the daemon writes its generated profile at the highest-precedence layer it controls under a daemon-unique profile name and verifies the fully-resolved effective profile equals the posture-derived configuration exactly; any residual widener from another layer (extra workspace roots, network domains, Unix-socket or local-binding allowances) refuses the run. Built-in profile aliases are audited at the same bar: the built-in `:workspace` profile also allows writes to **system temp directories** beyond the workspace roots (same permissions docs), so the daemon-generated profile either suppresses the temp allowance where the config surface can express that, or the recorded posture's `writableRoots` MUST include the effective temp roots — and the same profile keeps `.git/`, `.codex/`, and `.agents/` under each workspace root **read-only** ([Codex agent-approvals docs](https://developers.openai.com/codex/agent-approvals-security), fetched 2026-07-05 — the built-in protection is recursive, and where `<workspace-root>/.git` is a **pointer file** the resolved external gitdir it names is protected too), exclusions the recorded roots carry as **normative semantics** exactly like the Claude shared-`.git` leg: non-command write surfaces are Cedar-denied on `<workspace-root>/.git/**` (including the gitdir resolved behind a pointer-`.git`), `<workspace-root>/.codex/**`, and `<workspace-root>/.agents/**`, and posture realization verifies the generated profile preserves every read-only rule — the audit record always equals the enforced boundary, never a subset of it. The stamp binds **every turn, not one spawn moment**: `turn/start` accepts optional per-turn overrides for posture-affecting fields — `cwd`, the **legacy** `sandboxPolicy`, the **preferred** `permissions` profile-selection, and `approvalPolicy` — each carried as an optional field that persists for the turn ([app-server docs](https://developers.openai.com/codex/app-server), fetched 2026-07-03; the field inventory is pinned in the provider-wire reference `docs/reference/provider-wire/codex.md`, campaign B19). The daemon therefore derives **every** posture-affecting turn field from the stamped posture and refuses any turn carrying a posture-affecting field it did not itself so derive: a turn whose `cwd`, `sandboxPolicy`, `permissions`, `approvalPolicy`, `approvalsReviewer`, or any field the app-server later adds to this posture-affecting class diverges from the posture-derived value is **refused**, never silently started wider than the `run.running` record (a posture change is a new run, not a turn override). This closes by principle rather than by field enumeration, and it explicitly binds `approvalsReviewer` — which `turn/start` also accepts as an optional per-turn override (`TurnStartParams`, provider-wire reference `docs/reference/provider-wire/codex.md`, campaign B19): the driver pins it to `"user"` and the daemon refuses any turn supplying a divergent reviewer, so a later turn cannot reroute approval adjudication to an `auto_review` / guardian path that bypasses the Cedar pipeline. `approvalPolicy` (which actions require approval) and `approvalsReviewer` (who adjudicates) are distinct posture-affecting fields, each derived and verified in its own right. The Claude leg has no symmetric per-turn escape: its sandbox and permission posture are applied at process launch through the daemon-controlled settings surface (the isolated `--settings` payload realized per the Claude-leg description below) and the sandboxing docs define no `turn/start`-equivalent per-turn override, so there is no per-turn widening surface to verify there. And because Codex permission profiles govern **sandboxed local commands** while MCP / app-connector / browser / computer-use surfaces ride separate controls (same permissions docs), the Codex leg carries the same non-command binding the Claude leg's non-Bash rule establishes: network-capable non-command surfaces are denied outright under `networkAccess: 'none'` and Cedar-gated against `allowedDomains` under `'allowed-domains'`, write-capable ones are Cedar-gated against `writableRoots`, and any surface the daemon cannot bind to the posture is disabled for the run **before** the posture is stamped — the recorded posture covers the whole tool boundary, not only sandboxed commands. The stamped `credentialPolicyRef` binds on this leg too, not only on Claude's: `denyEnvVars` are enforced by the provider-neutral daemon spawn-env strip (the daemon owns the spawn environment for every provider process) with Codex `shell_environment_policy` (`inherit: "none"` + explicit `set`) as the native defense-in-depth layer beneath it; `denyPaths` map into the daemon-generated permission profile's filesystem deny rules (the permissions surface governs local-command filesystem access — same permissions docs) with the resolved profile verified to carry every curated deny, non-command read surfaces Cedar-gated against the same canonical deny paths exactly as the Claude leg's non-Bash rule — and a posture whose resolved Codex configuration cannot express a curated deny is refused rather than stamped with a credential policy its tools do not enforce.
  - **Claude leg** — `native-partial` (Bash-tool-scoped): the OS-level Bash-tool sandbox (macOS Seatbelt / Linux bubblewrap) is settings-driven and headless-enforceable ([Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing), fetched 2026-07-02; `sandbox.credentials` requires ≥ 2.1.187). Sandboxed postures set `sandbox.enabled`, `failIfUnavailable: true` (fail-closed if the sandbox cannot initialize), and `allowUnsandboxedCommands: false` (removing the unsandboxed-retry escape hatch); `filesystem.allowWrite` maps to `writableRoots` and `network.allowedDomains` to `networkAccess` — and because the sandbox prompts on an unallowed host and an approval **adds that host for the session** (same sandboxing docs), fixed postures (`'none'` / `'allowed-domains'`) MUST disable prompt-widening: managed-domain lockdown (`allowManagedDomainsOnly`) where the daemon controls managed-settings delivery, else sandbox traffic routes through a **daemon-owned proxy** (`network.httpProxyPort` / `socksProxyPort` — same sandboxing docs) that enforces the posture allowlist without prompting, so the reachable set cannot grow past the `run.running` stamp; and because `sandbox.credentials` ships **no** built-in denies, the daemon supplies a **curated default credential deny-list** (for example `~/.ssh`, `~/.aws`) — and because `sandbox.credentials` binds **sandboxed Bash commands only** (same sandboxing docs), the same curated paths are mirrored as permission-rule `Read` denies for the non-Bash read surface (Read-tool and read-capable MCP invocations are denied / Cedar-gated against the same list) and secret environment variables are bound by the layer the daemon owns outright: the daemon **strips every curated secret env var from the provider-process spawn environment itself**, with `sandbox.credentials` env unsets (sandboxed Bash only — same sandboxing docs) and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` (Anthropic / cloud-provider names only) as defense-in-depth beneath it — spawn-env removal is what binds arbitrary curated names (for example `GITHUB_TOKEN` / `NPM_TOKEN`) for daemon-hosted MCP and every other non-Bash subprocess — so no posture is recorded with a credential boundary its non-Bash tools do not enforce. Under `readonly-sandboxed` the effective Bash write surface MUST resolve to empty: the sandbox docs give Bash commands **default** write access to the current working directory and the session temp directory (with `filesystem.allowWrite` only _adding_ paths), so the daemon's posture realization denies those defaults (read-only working-directory realization plus temp isolation, or the vendor deny knob where one exists) and verifies the resolved write surface is empty — a posture whose defaults cannot be suppressed is not realizable natively and the run is refused rather than audited `readonly-sandboxed` with `writableRoots: []` while the cwd stays writable. Linked git worktrees get the same audit treatment: when the working directory is a linked worktree the sandbox additionally allows writes to the main repository's shared `.git` directory (`hooks/` and `config` stay denied — same sandboxing docs), and because the daemon executes worktree-first ([ADR-006](../decisions/006-worktree-first-execution-mode.md)) this allowance is live on essentially every run — under `workspace-sandboxed` the recorded `writableRoots` MUST include that shared `.git` directory, whose entry carries the vendor-fixed exclusions as **normative semantics of the recorded root** — `hooks/` and `config` inside it are denied for every write path, so the permission-rule scoping for non-Bash tools MUST apply the same exclusions (Edit/Write-class denied and write-capable MCP Cedar-denied on `<shared-.git>/hooks/**` and `<shared-.git>/config`), keeping record-plus-semantics exactly equal to the enforced boundary on Bash and non-Bash paths alike; under `readonly-sandboxed` it is part of the write surface the daemon verifies resolves to empty. Sandboxed postures additionally pin `excludedCommands: []` in the daemon-controlled settings payload and launch against the daemon's isolated `--settings` surface: `excludedCommands` merges **additively** from every settings scope and excluded commands run **outside** the sandbox ([Claude Code settings docs](https://code.claude.com/docs/en/settings), fetched 2026-07-02), so a run whose effective configuration still carries excluded commands is not recorded as `workspace-sandboxed` / `readonly-sandboxed` — fail closed. The same check covers the **whole resolved sandbox configuration**, not only excluded commands: `--settings` merges with file-based scopes and array-valued settings **concatenate** across scopes (same settings docs), so a user / project / managed layer can widen `filesystem.allowWrite`, `network.allowedDomains`, Unix-socket allowances (`allowUnixSockets`), macOS `allowAppleEvents` (which removes code-execution isolation per those docs), or the isolation-weakening booleans (`enableWeakerNestedSandbox` / `enableWeakerNetworkIsolation` — each considerably weakens the boundary per those docs) beyond the posture; the driver therefore verifies the run's fully-resolved effective sandbox configuration is **exactly** the posture-derived configuration and refuses the run on any residual widener from another scope — the recorded `writableRoots` / `networkAccess` / `allowedDomains` are always the enforced boundary, never a subset of it. Non-Bash tools (Read / Edit / MCP) ride the permission system rather than the OS sandbox, so per-tool coverage is legible from the posture semantics themselves — the mechanism split (OS sandbox for Bash; permission system for non-Bash) is a property of the posture contract, graded in the Spec-005 capability matrix (campaign B3), never a per-run stamp — and a `mode` label never implies uniform OS enforcement where the Claude leg is Bash-scoped — and precisely because of that split, sandboxed postures MUST bind the **non-Bash write surface** through the permission system: under `readonly-sandboxed` the daemon-controlled settings deny file-mutation tools (Edit/Write-class) outright and write-capable MCP tools are Cedar-gated against `writableRoots` (the empty set denies all); under `workspace-sandboxed` file-mutation tool invocations are permission-scoped to `writableRoots`. The same binding covers the **non-Bash network surface**: the OS sandbox's network controls are Bash-scoped, so under `networkAccess: 'none'` the daemon-controlled permission rules deny network-capable non-Bash tools (WebFetch-class, network-capable MCP tools) outright, and under `'allowed-domains'` their invocations are Cedar-gated against the same `allowedDomains` list. A run whose resolved permission rules leave any write path — or any reachable network surface — broader than the posture is not recorded under that posture: the recorded `mode` and `networkAccess` bind every path, Bash and non-Bash alike.
- Three boundary facts the posture semantics encode:
  - In-session subagents run in the parent process and **inherit the parent's OS sandbox configuration**, so the sandbox floor covers a run's subagents automatically — no subagent sandbox-escape at the OS layer ([sandboxing docs §Scope](https://code.claude.com/docs/en/sandboxing), fetched 2026-07-02). The **non-sandbox** permission surface is not inherited by default, however: a Claude `AgentDefinition` carries its own `permissionMode`, `tools`, and `mcpServers` ([Agent SDK permissions docs](https://code.claude.com/docs/en/agent-sdk/permissions), fetched 2026-07-05 — per-subagent override is force-suppressed only when the parent runs `bypassPermissions` / `acceptEdits` / `auto`), so absent binding a subagent could be launched with broader non-Bash Edit / MCP / network access than the stamped posture allows. The daemon therefore **derives every hosted subagent definition from the run's posture** — the `--agents` payload is daemon-controlled, exactly like the `--settings` surface — bounding each subagent's `permissionMode` / `tools` / `mcpServers` to the posture and Cedar-gating them identically to the parent's non-Bash surface; any subagent definition the daemon cannot so bound is **disabled for the run before the posture is stamped**, so the recorded posture covers subagents at the permission layer, not only the sandbox layer.
  - The Claude sandbox is **unavailable on native Windows** (WSL2 only, per the same sandboxing docs) — and a host that cannot fully realize a sandboxed posture (native-Windows Claude leg, missing Linux sandbox dependencies, any partially-realizable knob) **refuses the run**: a sandboxed posture is stamped only when fully realized, never stamped degraded, so one `workspace-sandboxed` record always means the same enforced boundary on every host. Per-knob realization _vocabulary_ (`native` / `native-partial` / emulated) lives in the Spec-005 capability matrix (campaign B3), not on the run stamp ([ADR-019](../decisions/019-windows-v1-tier-and-pty-sidecar.md)-adjacent).
  - The network allow-list matches client-supplied hostnames without TLS inspection, so **broad domain allows are domain-fronting-weak** (the sandboxing docs' own §Security-limitations warning); posture presets prefer narrow allow-lists.
- The daemon's command policy carries a **provider-supervisor deny** covering the full background-agent surface: the subcommands `claude agents` / `claude daemon` / `codex cloud` plus Claude's background-agent entrypoints (`--bg`, `/background`), with the daemon additionally pinning `disableAgentView: true` in its controlled settings — the vendor knob that turns off `claude agents`, `--bg`, `/background`, and the on-demand supervisor in one switch, equivalently `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` in the spawn environment ([Claude Code settings docs](https://code.claude.com/docs/en/settings), fetched 2026-07-02) — enforced for **every effective posture** — preset-resolved via `profileName` or supplied inline — so an inline posture cannot bypass it and no preset may omit it. This is the residual-vector control behind the single-supervisor invariant (the daemon is the only cross-session supervisor — [Spec-016 §Provider-Native Subagents](016-multi-agent-channels-and-orchestration.md#provider-native-subagents), landed 2026-07-06 via campaign B6; the command-policy deny itself is enforceable standalone).
- **Callback-tool authorization.** Every daemon-registered session callback tool — the daemon-hosted tool registry exposed into a run, whose shape is defined in [Spec-005](./005-provider-driver-contract-and-capabilities.md) by the campaign's B3 amendment (a named merge prerequisite for implementing this bullet) — is Cedar-governed identically to provider tools, and its invocations land as `tool_activity` records; no callback tool bypasses the approval pipeline.

## Default Behavior

- Default grant scope is `request_only`.
- Session-wide remembered approval rules are `off` by default and must require explicit user opt-in. Remembered approval rules are allow-rules only in V1: a remembered-scope request is valid only on an `approved` decision (`ApprovalResolve` rejects a rejected-decision remember request with a typed error); deny-by-default remains the policy engine's job, not the remembered-rule store's. (Tier-6 audit.)
- File and tool permissions default to the bound workspace or node trust envelope; out-of-boundary access requires explicit approval.
- Network access defaults to denied unless the active policy or approval explicitly allows it.
- A participant's own attached runtime node defaults to trusted for running work on that participant's machine inside the node's declared trust envelope, but it does not grant ambient authority to other participants and does not waive explicit approval for sensitive escalation.

## Fallback Behavior

- If a driver cannot expose granular permission requests, the daemon must enforce an equal or stricter approval boundary at the local execution layer.
- If approval state cannot be durably persisted, the sensitive action must not proceed.
- If a remembered approval rule becomes invalid because membership or node trust changed, the system must revoke it before the next use.
- If node ownership or trust provenance cannot be established confidently, the daemon must treat the node as requiring strict per-request approval for sensitive actions rather than assuming own-node trust.

## Interfaces And Contracts

- `ApprovalRequestCreate` must include category, scope, requested resource, and expiry policy.
- `ApprovalResolve` must include approver, decision, optional remembered-scope request, and audit metadata. The Cedar `principal` for authorization is the verified PASETO `sub` of the caller; the `approver` field in the request body is informational/routing metadata and is rejected when it disagrees with the verified `sub`. See [API Payload Contracts §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model). On the local daemon socket — which carries no PASETO principal per the linked local-daemon model — the `approver` body field is optional: when absent, the daemon records its node-owner participant binding as the approver; when present, it is cross-checked against that binding and rejected on mismatch (`auth.principal_mismatch`). The resolution record always carries the recorded approver. (Tier-6 audit.)
- `PermissionCheck` must run inside the local daemon before executing a sensitive local action.
- `ApprovalProjectionRead` must surface pending and historical approval state to participants authorized to see it.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- Approval requests and resolutions must be durable and replayable.
- Remembered approval rules require explicit revocation paths and audit history.
- Changes to membership or runtime-node trust must be able to invalidate dependent approval rules.

## Example Flows

- `Example: An agent requests write permission outside the bound worktree. A participant approves the request for this run only, and the decision is recorded with explicit path scope.`
- `Example: A participant with collaborator role has chat access in a shared session but cannot approve execution on another participant's runtime node because they lack the required trust scope.`
- `Example: A participant attaches their own runtime node to a shared session and starts a run on that node. Execution is allowed within the node's default trust envelope, but a later unrestricted network request still produces an explicit approval prompt.`

## Implementation Notes

- Approval UX may present grouped requests, but canonical approval records must remain granular enough for audit.
- Remembered approval scopes should be explicit enums, not free-form client labels.
- Trust changes must propagate into approval evaluation immediately.
- Policy evaluation uses Cedar (CNCF sandbox). V1 runs `@cedar-policy/cedar-wasm` in-process over a build-embedded, signature-verified compiled policy set authored from YAML policy sources (compiled at package build; verified against the pinned operator key on every daemon start, fail-closed — Plan-012 D-012-9). V1.1 changes the policy SOURCE only (build-embedded → runtime-delivered signed policy bundles, criterion-gated per ADR-012); the evaluator does not change. Cedar's principal-action-resource-context model maps to: principal = participant, action = the approval category for decisions that traverse the approval pipeline, or a named operation action for authorizations that do not (`Action::"intervene"` on the target `Run` for run control per [Spec-004 §Interfaces And Contracts](./004-queue-steer-pause-resume.md#interfaces-and-contracts); `Action::"dispatch::<capability>"` per [Spec-024](./024-cross-node-dispatch-and-approval.md)), resource = target (file, tool, network, run, runtime node, etc.), context = session state — a run's hosting node included, which is what makes §Required Behavior's node-trust bound evaluable. Policy artifact signing, verification, and operator key lifecycle are governed by [ADR-012 §Policy Chain of Custody](../decisions/012-cedar-approval-policy-engine.md#policy-chain-of-custody); operational procedures are in [Cedar Policy Signing And Rotation](../operations/cedar-policy-signing-and-rotation.md).

## Pitfalls To Avoid

- Treating membership as equivalent to local execution trust
- Storing remembered approvals with no revocation model
- Allowing provider-specific permission semantics to leak into canonical docs

## Acceptance Criteria

- [ ] Sensitive local actions require explicit approval or prior valid grant.
- [ ] Session membership alone cannot authorize execution on another participant's node.
- [ ] Approval records survive replay and clearly show who granted what scope.

## Resolved Questions and V1 Scope Decisions

- No blocking open questions remain for v1.
- V1 decision: organization-level stricter policy overrides are out of scope. V1 uses product-default policy with local daemon enforcement and explicit per-request approvals.
- V1 decision: own-node trust in v1 is envelope-bound, not blanket. A participant's own runtime node is the default execution host for that participant, but sensitive actions outside the node's normal trust envelope still require explicit approval and no own-node attachment grants authority over another participant's machine.
- V1 decision (Part-B fail-closed follow-up, 2026-07-17): **bounded ask-expiry with per-kind fail-closed outcomes.** A `kind: 'permission'` ask expires to **auto-deny, deny-and-continue**: the daemon delivers a structured denial through the provider's native deny path — the agent adapts or ends its turn cleanly; never a session kill, never a fabricated approval — and the corresponding approval-pipeline request resolves through the registered `approval.expired` event ([Spec-006 §Approval Flow](./006-session-event-taxonomy-and-audit-log.md#approval-flow-approval_flow) — an expired request grants nothing), carrying **one shared deadline**: the pipeline request's `expiryAt` equals the ask's `expiresAt`, stamped once at creation, so `approval.expired` and `driver_ask.expired` are two registered surfaces of the same passage, never two divergent timers; the passage is also **replay-atomic**: an expiry's sibling effects — for a permission ask the `approval.expired` resolution together with `driver_ask.expired` and the native-path denial, for an input ask `driver_ask.expired` together with the park transition below — commit as one unit under the session append lock, and daemon startup reconciliation deterministically derives a missing sibling effect from the persisted (`ask_id`, `expiry_at`) pair, so a crash between effects never strands a resolved approval against a still-pending native ask or a closed input ask against a still-waiting run (crash-after-first-effect tests ride the implementing B13/B9 tasks) — and the association between the two surfaces is itself **persisted at creation**: the normalizer-minted pipeline request records the originating `askId` (carried on `approval.requested` — `ApprovalFlowEventPayload.askId` in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md); never client-suppliable: the public `ApprovalRequestCreateRequest` deliberately carries no `askId` and its strict schema refuses a smuggled one — a caller-forged association could route another ask's outcome or expiry to the wrong native ask — so the normalizer supplies the association daemon-internally at the approval-service seam — and persisted onto the `approval_requests` projection's `ask_id` column with its unique partial routing index and ask-implies-deadline CHECK — exactly one approval row per native ask, and never an association without its shared deadline (an invariant enforced at emission too: the approval-flow payload refinement refuses an `askId`-bearing `approval.requested` lacking `expiryAt` before it becomes durable, so the projection CHECK is the replay-side backstop, never the first line of defense), so a normalizer retry or replay re-mint collides instead of duplicating — rebuilt from the event at replay, per [Local SQLite Schema §Approval Tables](../architecture/schemas/local-sqlite-schema.md#approval-tables-plan-012)), so with multiple in-flight permission asks on one run — and across daemon restart or event replay — the daemon reconstructs exactly which native ask a pipeline outcome or shared-deadline expiry must deny; ask↔approval routing is never inferred from timing or a one-pending-ask assumption. A `kind: 'input'` ask expires to **park-resumable**: no input is ever fabricated (fail-closed), the ask closes as expired, and the run parks in its ordinary resumable paused state via the `waiting_for_input → paused` transition this amendment adds to the canonical run-state machine ([run-state-machine.md](../domain/run-state-machine.md) — previously legal only for rollback), driven by the daemon's ask-expiry path on `driver_ask.expired` and deliberately NOT the CP-004-9/CP-012-5 approval-outcome seam: that seam's expired outcomes continue-with-refusal back to `running`, which is correct for approval-pipeline categories — an expired permission ask's deny-and-continue rides exactly that seam — but a driver input ask never traverses the approval pipeline ([Spec-006 §Driver Ask Events](./006-session-event-taxonomy-and-audit-log.md#driver-ask-events) routes input-kind asks to the run's interactive surface), so its expiry must take the park edge and a run is never returned to `running` with no input delivered — a deliberate, owner-visible persisted state subject to normal session retention, not an active run holding a liveness exemption (resume re-engages the provider, which may re-raise the ask; the persisted-session defer pattern is the surveyed precedent — [Claude Agent SDK, handling approvals and user input](https://code.claude.com/docs/en/agent-sdk/user-input), consulted 2026-07-12). V1 default expiry: **4 hours** for `permission` asks, **24 hours** for `input` asks — policy-configurable per daemon under a **fail-closed floor**: durations may be tuned but expiry can never be disabled (no wait-forever configuration exists), and the timers are durable per §Required Behavior ([Temporal timers, timeouts, and the art of waiting](https://temporal.io/blog/timers-timeouts-and-the-art-of-waiting-in-temporal), consulted 2026-07-12 — a timer that dies with the process is not a bound). Risk-tiered refinement of these defaults (shorter low-risk / longer high-risk windows, reminder and second-approver escalation affordances) is the campaign B13 approval-policy-content surface, bounded by the same floor and the same never-auto-approve invariant.
