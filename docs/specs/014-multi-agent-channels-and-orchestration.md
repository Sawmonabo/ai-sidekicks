## Purpose

Define how multiple agents collaborate inside a session and how their channels and run relationships are represented.

## Scope

This spec covers channel creation, parent-child run linkage, cross-agent collaboration, and background helper activity — including session goals, cost derivation for budget enforcement, and the orchestration-level governance of provider-native in-session subagents (campaign B6).

## Non-Goals

- Workflow authoring syntax
- Defining provider-native subagent APIs — the `subagentPolicy` and driver-op shapes are [Spec-004](004-provider-driver-contract-and-capabilities.md)'s; this spec governs only their orchestration use (§Provider-Native Subagents, campaign B6)
- Notification policy

## Required Behavior

- A session must support multiple active agents at once.
- Agents may collaborate through one or more channels inside the same session.
- Cross-agent communication **inside one session** must use canonical channel publication, artifact references, approvals, or persisted run linkage, and V1 adds no direct run-to-run messaging primitive between agents of the same session. Reaching **another session** is a different act with its own surface (§Sessions Talking To Each Other), and it is not a channel.
- Parent-child run relationships must be durable and auditable.
- Internal helper runs must remain distinguishable from user-visible agents while still appearing in canonical history.
- Per-agent model, driver, and runtime-node selection must be allowed within one session.
- Orchestration must remain valid even when a driver has no native subagent concept.

### Sessions Talking To Each Other

A session reaches another session through **one tool the daemon serves to both providers**: `SendToSession {to, message, files}`, with `ListSessions {}` beside it naming every session of the person's on either provider and whether each is working or idle. That tool is the only path between two sessions, so a message draws the same pair of rows whichever provider sits at either end.

**`to` is a name, and `files` are paths.** `to` is the other session's name as `ListSessions` prints it and never an address: the daemon holds the directory of its sessions and resolves the name to whatever that session is actually reached by, so no model ever handles a socket path. `files` is optional — a list of paths the sending session can already read, which the daemon copies at send time and stages into the **receiving** session as that session's own attachments, through the ingest pipeline every other attachment takes ([Spec-012 §Ingest Validation And Payload Bounds (V1)](012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1)), so they arrive there as paths the receiving model opens with its own file tools on either provider. Both rows carry the file chips a sent turn's own attachments carry, and this runtime sets no bound of its own beyond that pipeline's. The daemon reads each path as the person's own user at send time, and a path that does not exist or cannot be read fails the call with that path named in the tool result rather than arriving as an empty attachment. Nothing gates it a second time: the receiving session runs as the same person on the same machine and could open that path itself, so a second check would refuse nothing it can already reach. The provider's own file-sending tool is neither waited for nor mirrored: its maker keeps it switched off for every session behind a server flag, so nothing here rests on it, and this path stands unchanged the day it turns on — and because that tool is not on this path at all, the size and count bounds its own build carries never apply to a message's `files` ([provider-wire reference, claude.md](../reference/provider-wire/claude.md)).

**How the tool is declared.** On a Claude Code session the daemon declares it as an in-process tool server in that session's `initialize` control request; a call arrives as the `mcp_message` control round trip and is answered on that same channel, and the session's permission level is applied through `can_use_tool` — the levels that ask raise the ordinary approval card, and the two that answer for themselves allow. On a Codex conversation it is declared as a dynamic tool on `thread/start`; a call arrives as `item/tool/call` and is answered with its result, and because that provider asks nothing for a dynamic tool the daemon applies the same level rule itself before routing. A send is an ordinary tool call under the **sending** session's own permission level and nothing in this runtime gates it beyond that; what the message then causes is gated by the **receiving** session's own level, exactly as words typed there would be.

**A session starts with exactly the tool servers switched on for it.** The daemon starts that set and no other, and declares it through each provider's own means with nothing of this runtime's in between: on Claude Code as the `--mcp-config` set together with `--strict-mcp-config`, so the session reads that set and no other tool-server configuration on the machine; on Codex as the conversation's own configuration at `thread/start`, each server enabled or not. A server that is switched off is never declared, so it costs the model no tool definitions at all, and a switch flipped while the session is running reaches Claude Code when its process is next reopened and Codex at its next turn.

**How a message is delivered.** Into a Claude Code session it is one user frame written to that session's own address, carrying the true sending session's name, so that provider's own repeat and flood protections apply with the provider's own numbers ([provider-wire reference, claude.md](../reference/provider-wire/claude.md)). Into a Codex conversation it is `turn/start` carrying the tool output where the conversation is idle, and `turn/steer` where a turn is running, which folds it in at the next message boundary. A busy session is reached on either provider, and the message lands inside the turn that is running rather than waiting for the next one.

**A reply is read off the receiving session's own record.** One provider routes a peer-prompted turn's answer back to nobody at all — the writer is told nothing and no connection is made to the address the sender declared — so the answer exists only on that session's own record, and the daemon reads it there ([provider-wire reference, claude.md §A message from another session arrives on the session's own address](../reference/provider-wire/claude.md#a-message-from-another-session-arrives-on-the-sessions-own-address)). Which record depends on who started the session and on nothing else. For a session this product started it is the daemon's own stream, which it can read because it is the daemon that runs that process. For a Claude Code session the person typed in their own terminal it is that provider's own transcript file, whose folder and name the provider's live-session registry gives, read only from the daemon's own message onward: the record of the arriving message carries the id it came in with and the answer is chained back to that record, so a reply is paired to the message it answers, and a line lands within a quarter second of the moment it carries ([provider-wire reference, claude.md §A reply comes back when the message asks for one, and the transcript pairs it to its prompt](../reference/provider-wire/claude.md#a-reply-comes-back-when-the-message-asks-for-one-and-the-transcript-pairs-it-to-its-prompt), measured 2026-09-21 at `2.1.278`). So the reply a row shows is what that session actually said. Nothing is added to the message to make this work — no instruction line asking for an answer, and no tool call asked of a session in the person's own terminal — and the daemon's own inbox is the `from` address on every delivery, so a reply a far model chooses to send of its own accord lands there too and is drawn as the same one row rather than a second. That is why `replied` is a reading rather than a return value, and why `not delivered` is a reading too: it is that registry's own status for the session going idle with no record of the message.

**What the daemon keeps.** A directory of its sessions and their addresses, looked up at send time so nothing dies with a provider process. An exchange table naming who is talking to whom and how many messages the two have traded since the person last wrote in either; that count travels into the message the receiving model reads, as a fact and not a limit. And, for a paused session, a queue of everything addressed to it, delivered one at a time in arrival order when it continues.

**The daemon's queue is what keeps a message out of a paused session, and it is the only thing that does.** A pause on this product's own boundary is a hold inside the provider's tool callback: a frame written to that session's address during the hold is not read while the hold lasts, and it is not lost either — it lands a few milliseconds after the held tool's own result and folds into that same turn, and the model acts on it in the same answer. The hold puts nothing on the wire, so from outside a held session is indistinguishable from an idle one ([provider-wire reference, claude.md](../reference/provider-wire/claude.md)). Two consequences follow. The daemon never writes to a paused session's address in the first place, which is what makes `queued, builder is paused` an honest reading rather than a guess about the provider. And a session in the person's own terminal, writing straight to a paused session's address with no daemon in the middle, is read when the hold releases rather than held out — the queue is the daemon's, not the provider's.

**A provider's own send to another session is closed.** The daemon registers a `PreToolUse` hook on Claude Code's `SendMessage` — declared in that session's `initialize` request and answered over the wire the way the pause hooks are, so none of it is a script on disk — which denies a send whose target is another session and answers the model `send with SendToSession`, so a message between two sessions cannot take a second path or draw a second shape. It judges the target from the call's `to` alone: an address (`uds:` or `bridge:`), or a name that is a session in the daemon's own directory or in that provider's live-session registry (`sessions/<pid>.json` under its config folder), is denied, and a `\\.\pipe\` name is an address here exactly as that provider's own target resolver reads it ([provider-wire reference, claude.md §A message from another session arrives on the session's own address](../reference/provider-wire/claude.md#a-message-from-another-session-arrives-on-the-sessions-own-address)); any other name is one of the session's own subagents or teammates, and that call goes through untouched. The two sets cannot overlap, because the daemon never names a session as seventeen lowercase hexadecimal characters, which is the shape a subagent's id takes.

**The hook answers in the one form that hands the model the reason alone.** Its answer is the JSON decision — `permissionDecision` `deny` with `permissionDecisionReason` `send with SendToSession` — and nothing else. The other form the provider accepts, a refusal carried as an error, is not used: the model then reads the reason wrapped in an error naming this product's own file path, which tells it about our plumbing instead of about the tool it should have called ([provider-wire reference, claude.md](../reference/provider-wire/claude.md)). Either way the refused call stays **on the record** — the turn's own list of permission denials carries it with its full input — and that record, not an absence, is what the sending session's row reads when it says a send never happened.

**An interrupt reaches both ends.** Interrupting a session that is in an exchange ends the turn here and the turn there and empties the queue between them, because one press on one side would otherwise leave the other side free to wake it again. This is the one place an intervention reaches past the session it was aimed at, and it reaches exactly one further session — the one on the other end of the exchange — by the pair the exchange table already holds; it is a fan-out of ordinary interrupts, one per run, and not a cascade primitive (§Intervention Propagation). Each transcript records what the interrupt reached, including how many messages were not delivered.

**Nothing in this runtime bounds how many messages two sessions trade.** Each provider's own limits flow in with that provider's own numbers, and the one bound the person can set is `Max steps per turn` ([Spec-003 §The Step Bound On A Turn](003-queue-steer-pause-resume.md#the-step-bound-on-a-turn)), which is unlimited until they set a number.

**A session the person started in their own terminal reaches these sessions two ways, and the first needs nothing installed.** Every session has an address, offered on screen as `Copy address`; a Claude Code session in the person's terminal writes to it, and the message arrives as that provider's own peer delivery, which the daemon reads off the receiving session's stream and draws as the same row. An optional Claude Code plugin, built after this surface and never required, additionally gives such terminal sessions `SendToSession` and `ListSessions` by name and hands a peer delivery to the daemon before the model reads it; with the plugin absent, switched off or failing, the address and the stream frame are the behaviour, so nothing in the daemon depends on it ([ADR-037](../decisions/037-claude-code-mods-are-an-optional-terminal-bridge.md)).

**A Codex session the person typed in a terminal is reached through one shared Codex service.** That provider gives a session no address of its own, so the only way in is a Codex service the daemon runs on the person's **own** Codex folder, which a plain `codex` typed in a terminal joins by itself. The daemon runs that service while the Codex switch `Reach Codex sessions started in a terminal` is on, and it is on by default; the switch sits under Codex alone, because the mechanism is that provider's alone ([Spec-021 §The surface set](021-desktop-shell-and-renderer.md#the-surface-set)). A session that joins the service is in the daemon's directory, has a row in the sessions list, and is messaged like any session through the one tool. Three limits hold, because both the folder and the process are the person's rather than the daemon's: the daemon never writes into that folder, it never moves such a session between accounts, and it stops the service only when the switch goes off **and** no terminal session is still inside it.

**What the daemon starts, and what joins it.** The service is `codex app-server --listen unix://<the Codex home's control socket>` and never `codex app-server daemon start`, whose subcommand set carries an updater that can replace the person's install mid-work; it speaks websocket over that socket ([provider-wire reference, codex.md](../reference/provider-wire/codex.md)). A plain `codex` joins whatever is listening there whichever folder it was typed in — the socket is per Codex home, not per folder — while `codex -c …`, `codex -p …` and `codex exec` each run alone and never appear in the list. Killing the service kills no terminal session: a session whose service comes back within about five seconds reconnects by itself, and one whose service has been away about twenty-four seconds has given up and answers nothing further, its transcript intact and reachable by `codex resume <thread id>`. Three consequences for the daemon. The service comes back on the same socket **before anything else** when the daemon restarts, so a session inside the reconnect window never notices. The daemon's own stop confirmation names the terminal Codex sessions that are inside the service, because stopping it is what strands them ([Spec-006 §Required Behavior](006-local-ipc-and-daemon-control.md#required-behavior)). And a session that was stranded says so on its own row rather than reading as idle ([Spec-021 §The surface set](021-desktop-shell-and-renderer.md#the-surface-set)).

**One service per Codex account, not one per person.** The service on the person's own Codex folder is the same mechanism, under the limits above: every Codex conversation on one account runs inside one service in that account's own Codex home, because the socket is per Codex home and a credential home is what a service is started on, so two accounts are two services and the account is the sharing key ([provider-wire reference, codex.md §The shared `app-server` a terminal `codex` joins](../reference/provider-wire/codex.md#the-shared-app-server-a-terminal-codex-joins), measured 2026-09-21 at `0.155.1`). Claude Code stays one process per session, that provider offering nothing else ([Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior)). Four conditions come with the sharing. A conversation's folder, its configuration and its tool servers are its own, passed at `thread/start` and never as a flag on the service that holds it — for a conversation the daemon starts; a terminal session that joins takes the service's own folder, measured 2026-09-21 ([codex.md §A second seat on the shared service](../reference/provider-wire/codex.md#a-second-seat-on-the-shared-service)), so the folder the daemon starts a service in is load-bearing until the provider carries the joining client's folder. A change to a conversation the service already holds — its configuration, its base instructions, its developer instructions — is applied where that provider honours it, at the conversation's next turn, and is measured against the running build before it is relied on. A conversation moves to another account only after the account it leaves has released it: the daemon unsubscribes it there, waits for that provider's own unload, and only then resumes the copied file in the new account's service, so no conversation is ever held by two services at once ([Spec-026 §Moving a session to another account](026-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)). And a service that dies is started again by the daemon with every conversation in it resumed through that provider's own resume, each such session carrying one faint row in its transcript that says so.

**Windows puts the daemon on the providers' side of the boundary.** A Claude Code session's inbox is a Unix socket on macOS and Linux and a named pipe on native Windows, and the two halves of one Windows computer cannot see each other: a daemon on native Windows and sessions inside WSL 2 reach neither each other's inboxes nor each other's session registries. So the daemon runs on the same side as the providers it drives, and a shell on the other side reaches it over loopback, which WSL forwards by default ([Spec-006 §Fallback Behavior](006-local-ipc-and-daemon-control.md#fallback-behavior)). The Codex legs are the same on every platform by construction: the daemon holds the seat on every Codex process it starts or joins, so a Codex session of ours sends and receives the same way on macOS, Linux, WSL 2 and native Windows, and a terminal Codex session is reached through the shared service wherever that service listens — `turn/start` on its thread when it is idle, `turn/steer` when it is busy, its reply the thread's own events on the daemon's seat. That seat was measured on 2026-09-21 ([codex.md §A second seat on the shared service](../reference/provider-wire/codex.md#a-second-seat-on-the-shared-service)): the daemon's seat sees a joined terminal's thread the moment the terminal connects; the thread's turn and item events reach the seat only once it has resumed that thread, which leaves the terminal undisturbed, while lifecycle notifications reach every seat unasked; a `turn/start` from the seat runs and the terminal shows the message and the reply as its own rows; and a `turn/steer` folds into the running turn, as a `turn/start` on a busy thread also does, so the steer's `expectedTurnId` is the one race-free form. The same measurement leaves this leg three open obligations, each owed a measurement or a rule before the terminal-Codex rows in this section are built: nothing on that wire says a terminal has quit — its thread stays loaded and a turn on it still runs — so the daemon needs a liveness source that is not the service; a terminal that joins the shared service runs its shell commands in the folder the service was started in rather than the folder the person typed `codex` in; and where an approval request goes when two seats hold one thread is unmeasured. Nothing in this section has been measured on Windows, for either provider: the Claude Code probes owed there are the named-pipe delivery, the registry read and the deny rule; the Codex probes are the service's listen form on native Windows (`--listen unix://` or a pipe), the plain `codex` join and `codex resume`; and for both, the WSL 2 split above.

**Every message is two rows and nothing else.** The sending session's transcript carries one row for the send and the receiving session's one row for the arrival, both of them the ordinary tool events the transcript already folds — so a message mints no row kind, and nothing of a message is persisted beyond those events ([Spec-021 §The surface set](021-desktop-shell-and-renderer.md#the-surface-set)).

## Default Behavior

- Default collaboration mode is explicit: new child runs are created only by user request, by workflow definition, or by an agent's own tool call through the cross-provider bridge of [Spec-027 §Required Behavior](./027-agent-definitions-and-peer-invocation.md#required-behavior) — a provider's own in-session subagent starts no canonical child run and so sits outside this rule (§Provider-Native Subagents). The third arm does not weaken the default, and is admitted here rather than treated as an exception to it: such a call is adjudicated at call time under the session's permission level exactly as any other tool call in that session is, so no child run of this origin can exist that the session's own level does not admit. Every other constraint in this section applies to such a child unchanged: it is subject to the budgets of §Budget Policies and the approval pipeline at whatever depth it sits, and it publishes into the parent timeline like any other child.
- Child-run output defaults to publishing a summarized row into the parent session timeline, with expandable detail.
- A collaboration channel belongs to the session that created it and is visible across that session unless later restricted by policy.
- The runtime adds no depth limit of its own to delegation. A child run may create child runs of its own, and those may create their own; how deep agents may nest is the provider's own limit under the person's own provider settings, and where a provider refuses a level, its refusal is shown in its own words. Every other rule binds at every level: the budgets of §Budget Policies, the approval pipeline, and the visibility rules of §Provider-Native Subagents.
- Concurrent child runs are allowed, and the runtime adds no count limit of its own on how many a session may have. How many agents a provider will run at once is that provider's own limit under the person's own provider settings; where a provider refuses, its refusal is shown in its own words.

## Fallback Behavior

- If a driver does not support native subagent creation, the runtime must model delegated work as separate runs with explicit linkage and channel context.
- If child-run detail loading fails, the summary row remains available and marked incomplete.
- If channel-specific delivery is unavailable, output falls back to the session's default visible channel with preserved provenance. (Tier-5 audit, A-014-18: "unavailable" = the target channel is archived at publication time, or its row is missing at projection time; "preserved provenance" = the event payload keeps the original `channelId` while the projection re-homes display to the main channel.)
- If child-run creation is refused, the runtime must reject the request with the explicit reason rather than silently dropping it or starting work it did not admit.
- **A send to another session that did not land says which thing happened, and never more than happened** (§Sessions Talking To Each Other). `refused: <reason>` carries the provider's own words where the provider refused it — a target that has ended, a message past that provider's own size bound, a declined approval on the sending side. `not delivered` is the receiving session finishing its turn and going idle without the message ever appearing on its stream, which is how a silent drop by the receiving provider's own repeat or flood protection is reported; it is never reported as delivery. `held by builder` is the receiving session's own inbound setting holding the message, opening to that session's own words, and nothing in this runtime approves it. `queued, builder is paused` is the daemon holding it for a paused session, which the continue delivers in arrival order. The sending row rests at `sent` until one of those is known, so a state is a fact the daemon observed rather than an acknowledgement of the write, and every state after `sent` reaches the sending model once as one short note telling it not to send again straight away.

## Interfaces And Contracts

- `ChannelCreate` must create a session-scoped communication surface. Channel lifecycle mutations (`ChannelMute` / `ChannelUnmute` / `ChannelArchive`) and a daemon-native roster read (`ChannelRosterRead`, carrying per-channel config + arbitration state and each entry's channel kind) complete the channel surface (Tier-5 audit, D-014-6/D-014-12).
- **Channel-directory publication (2026-08-11, D-014-22):** every channel-lifecycle transition a daemon accepts — `channel.created` / `channel.muted` / `channel.unmuted` / `channel.archived` — is additionally **published to the control-plane channel directory**: minimal channel metadata only (`channelId`, `sessionId`, the triggering event's `lifecycleEventKind` — added 2026-08-11, PR #322 Codex round 1, so the ingest can identify a creation under arbitrary reordering — `name?`, `state`, and `kind`), never message content, over an idempotent control-plane ingest mutation. **The directory has a single owner end to end:** [Plan-014](../plans/014-multi-agent-channels-and-orchestration.md) owns the daemon-side producer, the ingest mutation's wire contract, the `session_channel_directory` backing store ([Shared Postgres Schema §Session Channel Directory (Plan-014)](../architecture/schemas/shared-postgres-schema.md#session-channel-directory-plan-014)), and the `ChannelList` read path alike — one plan, so the fold below is specified and built by the same hand that publishes into it. Publication is **at-least-once and never blocking**: the daemon-local channel operation commits first and never fails, rolls back, or waits on directory acknowledgment (the daemon is the machine-local execution authority per ADR-001/ADR-003) — the origin daemon publishes after its durable event append and retries until acknowledged, and every daemon re-publishes the channel set of the sessions it hosts on startup and on relay reconnect. Re-publication is safe by construction: each publication is a pure function of the durable channel-lifecycle event and carries the corpus's origin-ordering keys — `originNodeId` + `originSeq` **server-stamped on the lifecycle payload itself** ([Spec-005 §Channel and Agent Lifecycle](005-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle), amended alongside this bullet — the goal-payload `producingNodeId` idiom), so the keys survive relay re-sequencing in every holder's durable copy and a non-origin republisher reproduces them exactly, with envelope `occurredAt` + `id` for the cross-origin comparator (the §Session Goals two-stage register precedent; a publication derived from a pre-extension event whose payload lacks the keys carries no origin keys on the wire and folds via the ingest's single envelope-ordered legacy slot, never binding disclosure) — so the control-plane upsert is a deterministic **per-origin candidate-retention fold** (redesigned 2026-08-11, PR #322 Codex round 1 — a single-winner comparator mixing a same-origin sequence branch with a cross-origin timestamp branch is order-dependent when an origin clock steps backward): the ingest retains one candidate per origin (same-origin `originSeq`-max) and resolves visible state from the retained set, so replicas that have received the same publication set converge to the same directory state regardless of delivery order or duplication (the state-based merge and its strong-eventual-consistency property per Preguiça, _Conflict-free Replicated Data Types: An Overview_, [arXiv:1806.10254](https://arxiv.org/abs/1806.10254) — §References), and a replayed or delayed publication converges instead of regressing directory state. The fold additionally honors lifecycle terminality (PR #321 Codex round 2): `archived` is terminal in the channel lifecycle (no transition leaves it — D-014-12), so it **latches** — a directory row's state is `archived` iff any publication ever carried it, and a delayed or replayed mute/unmute straggler can never resurrect an archived row — while non-terminal resolution takes the `(occurredAt, id)`-lexicographic-max retained candidate (residual: cross-origin resolution is wall-clock and skew-prone, so a cross-node mute/unmute race can transiently order wrong until both publications land, bounded by [Spec-013](013-persistence-recovery-and-replay.md)'s clock discipline; the HLC upgrade is the V1.1 path per ADR-017/BL-076, the same seam the §Session Goals register names — same-origin causality stays exact via `originSeq`, which is why the counter is retained rather than demoted to a timestamp tiebreak). The terminal latch governs the **`state` axis only**, and the create-once disclosure binding below governs `kind` + `name` on an independent axis — so when at-least-once delivery lands the `channel.archived` publication before the `channel.created` one, the later-arriving creation publication still binds the disclosure-bearing fields on the already-terminal row without reviving its state, and an archived channel is never left permanently kind-unresolvable (PR #321 round 2). Because the publication derives from the event rather than from private daemon state, any daemon holding the relayed event MAY re-publish it (healing a permanently offline origin) without divergence — but healing is **existence-and-ordering only, never disclosure-widening**: the relay re-signs relayed history under the receiving daemon's key, so a non-origin publisher has no origin-authenticated evidence for the metadata it forwards, and the control-plane ingest binds the disclosure-bearing fields (`kind` and the user-supplied `name` — the latter joined 2026-08-11 so a GDPR-cleared name can never rebind from a redelivered or sweep publication) **create-once** (PR #321 Codex round 2 — a per-publication caller check alone would let any authenticated daemon later re-declare a channel's kind by publishing fresh metadata under its own origin claim): they are honored only from the channel's **creation publication** — the publication whose `lifecycleEventKind` is `channel.created` (carried on the wire, since the resulting `state` alone cannot distinguish a creation from an unmute under the promised reordering — PR #322 Codex round 1) and whose authenticated caller identity matches its payload's `originNodeId` — and are immutable in the directory thereafter, no later publication (origin-authenticated included) altering them, with conflicting origin-authenticated creation claims for the same `channelId` collapsed to the unresolvable-kind disposition below; a non-origin (healing) publication keeps the row's existence, state, and ordering alive but its kind is treated as unresolvable and the entry is omitted, so a compromised daemon cannot relabel another origin's channel (its forgeries land as omitted placeholders at worst). The recorded V1 residual is the insider case — the daemon that originates a channel declares that channel's metadata at creation, so a compromised origin can mis-declare only its own channels — and the V1.1 hardening seam is an origin-signed event envelope the control plane verifies against the registered node key, binding the creation claim cryptographically rather than by transport authentication. **Staleness fails closed, never open:** until a channel's publication lands, the control-plane `ChannelList` simply does not list it — and an entry whose kind the projection cannot resolve is omitted (the control-plane projection) — so a delayed publication can briefly under-list a channel but never lists one on facts it could not verify. **What the control plane learns is a deliberate, scoped disclosure:** the directory holds channel existence metadata only, protected under [Spec-020](020-data-retention-and-gdpr.md)'s Postgres posture (access control plus row-level deletion) — and because the directory durably holds a user-supplied `name?`, **routing that table and that column into Spec-020's PII data map and its erasure closure is a named, non-optional leg of the store itself**: the ingest does not go live until that erasure routing has landed, so no publication can ever flow into a store outside the erasure fan-out; channel **content** never reaches the control plane (it transits the relay E2E-sealed per [Spec-028](./028-remote-control.md)). The control plane's `ChannelList` read is precisely what this publication feeds, so a device listing a session's channels reads them server-side instead of failing open on an absent source.
- **Per-channel turn budget (2026-08-11, D-014-23 — the A-015-07 provider leg):** `ChannelConfig` carries `turnsPerAgent?` — an optional positive integer overriding, for that channel alone, the session's per-agent consecutive-turn limit (§Budget Policies turn-limit row; `session_budgets.turn_limit_per_agent`, which exists only where the person set one). Absent means the session value applies, and where the person set none the channel carries no turn limit either. Counting semantics and the enforcement site are unchanged (the D-014-8 per-(channel, agent) consecutive counter with interleave reset, enforced by the turn-policy arbiter): at the effective limit the run completes with `trigger: 'turn_limit'` and same-agent admission into that channel refuses until an interleaving turn — any other agent's turn in the channel, or the user's, the universal counter reset, available with no mutation surface. The D-014-8 owner-raise lever reaches only channels with no override (`orchestration.budgetUpdate` on `turn_limit_per_agent`): an **overridden channel's limit is create-time-fixed**, because `ChannelConfig` is uniformly immutable after create in V1 — no post-create channel-config mutation exists on any member, deliberately, since mid-flight policy mutation would invalidate the arbiter's admission-time assumptions — so the override pins the channel for its lifetime and a post-create override mutation (`channel.configUpdate`, with its events-canonical `channel.config_updated` companion) is the named V1.1 seam per §Resolved Questions and V1 Scope Decisions. The first consumer is Spec-015's phase-owned OWN channels, which set it at channel create (`turns_per_agent`, indicative max 20). It is a per-channel override of the existing turn budget, **not a fourth budget** — the §Budget Policies three-budget table is unchanged.
- **Agent surface (Tier-5 audit, A-014-2; provider axis added 2026-08-26, D-014-26):** Plan-014 owns the V1 agent identity surface satisfying §Required Behavior's per-agent model/driver/node selection — `AgentConfigUpdate` / `AgentList`, with the agent persona `{name, driverName, modelId, defaultNodeId?, config?, providerAccountId?, effort?}` durable via `agent.*` events ([Spec-005 §Channel and Agent Lifecycle](005-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle)). There is no attach or detach verb: a session's main agent is the one it starts with, and every other agent in the session arrives because that one delegated to it or because the user named one in the composer. **No event exists whose only job is to create an agent record, so every row in the `agents` projection is born from the durable record of that agent's own start.** The session's main agent is born with the session: `session.created` carries its id together with the binding and configuration the daemon resolved for it, and that event is its row's creating record ([Spec-005 §Session Lifecycle](005-session-event-taxonomy-and-audit-log.md#session-lifecycle-session_lifecycle)). An agent a run starts under an agent definition — the run a peer invocation admits included — is born from that run's own `run.queued` record, which names the agent and carries what admission resolved for it ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)). The three `agent.*` events only ever move a row one of those two records created. A provider's own in-session subagent has no row in `agents` at all: it is not a canonical child run and holds no persona of its own, and it is visible through the registered `subagent.started` / `subagent.completed` pair and through the daemon's own tree index (§Provider-Native Subagents). `OrchestrationRunCreate.targetAgentId` resolves against this surface; an unknown or not-ready agent is a typed refusal.
- `OrchestrationRunCreate` must allow parent linkage, target agent, target node, and target channel.
- `OrchestrationRunCreate` failure must surface an explicit typed rejection carrying its own reason, never a silent drop.
- `ChildRunLinkRead` must expose parent-child relationships.
- `InternalRunFlag` must distinguish internal helper work from user-facing agents.
- **Link-type semantics (Tier-5 audit, D-014-17):** `spawn` — parent-initiated helper whose output returns to the parent's channel context; `delegate` — bounded task published to its own target channel; `handoff` — the parent transfers its continuation to the child and completes. The type is caller-declared (`linkType`, default `spawn`) and durable in the run linkage.
- **Budget surface (Tier-5 audit, D-014-5):** session budget limits are readable and owner-adjustable via `OrchestrationBudgetRead` / `OrchestrationBudgetUpdate`. Both answer with the same budget state, whose cost members carry the committed-spend decomposition governed by §Cost Figure Display Consistency (D-014-24) — a read and an update reply report the same number at the same fold state.
- **The surface a session's agent view reads:** `orchestration.runCreate` to dispatch, `orchestration.childRunLinkRead` for the parent-child links, `orchestration.budgetRead` for the session's limits and the committed-spend decomposition §Cost Figure Display Consistency governs, and `orchestration.costReceiptRead` for the receipt §Session Cost Receipt mints — whose per-paying-account axis is what a session's own cost detail draws — beside the agent surface's `agent.configUpdate` / `agent.list`. The events that surface folds are the two `subagent.*` tool-activity rows (§Provider-Native Subagents) and `orchestration.rejected` (§Scheduler Limits). No caller on it re-folds a cost figure or re-assembles a tree from the rows it holds.
- **The session's agent tree is a daemon-owned index.** The daemon builds, per session, a parent-to-child index of every agent in a run's tree, read from the provider's own stream — on the Claude leg the task-started frame and the parent call id it carries, on the Codex leg the agent's turn-started frame — and **persists** it, because neither provider lists its subagents back on resume: after a daemon restart every agent is re-attached by the id the daemon stored at dispatch (the task id on one leg, the thread id on the other) and its rows replay from the provider's own record. That index is the single source of the tree every client draws, of every fan-out count (§Provider-Native Subagents), of the run ids the three subtree sweeps iterate (§Intervention Propagation), and of the key by which a pause or an interrupt is routed to one agent rather than another — the agent id on the Claude leg, absent on a run's own calls, and the turn id on the Codex leg, whose session id is always the root's. **The durable handle for an agent is its run, its provider, and its own id together, never a bare agent id**, because neither provider mints ids unique outside the process that made them. Two consequences bind the daemon: it never sends the Claude leg's conversation reset to a session whose agents it means to keep — that reset leaves every settled agent's transcript on disk while making the provider refuse every resume of it, and nothing recovers them — and on the Codex leg an agent its parent shut down or evicted is reopened by its thread id.
- **The session-to-session tool is two operations the daemon serves to the providers, not a method of this runtime's own wire** (§Sessions Talking To Each Other). `SendToSession {to, message, files}` answers with the session it reached and one state: `sent` when the call returned, and then, as the daemon learns it, `delivered`, `queued`, `held`, `refused` carrying the provider's own reason, or `not delivered`. `ListSessions {}` answers with one entry per session of the person's — that session's name, its provider, its account, and whether it is working or idle — drawn from the daemon's own directory rather than from either provider's listing, which is what lets one entry name a session on the other provider. `files` names paths the sending session can read; the daemon copies them at send time and stages them into the receiving session as that session's own attachments, so they arrive as paths rather than as bytes on the wire. Because both are tools a provider's model calls, neither is registered in a method-name registry, neither mints an error code, and a refusal is the provider's own words carried on the result. What the screen draws from them rides surfaces that already exist: the exchange line on a session's row and a sent row's later states come over the run-state subscription, and the rows themselves are the ordinary tool events.

## State And Data Implications

- Channel and run-link records must be durable and replayable.
- Parent-child linkage must survive recovery and replay.
- Internal helper visibility must be policy-aware but never silently omitted from audit history.
- The channel record additionally carries its channel kind, an additive field on the record itself. This introduces **no new persistence table**.
- Because channel records are events-canonical projections, the channel kind must ride the channel-creation event payload and not the row alone — a channel whose kind could not be rebuilt from the event log would break the durable-and-replayable guarantee above. (The [Spec-005 §Channel and Agent Lifecycle](005-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle) enumeration carries the matching additive-optional `kind?` payload member as of 2026-08-11.)
- The agent record additionally carries its provider account, its reasoning effort, its output-speed mode (2026-08-29), and any switch still pending against it (2026-08-26, D-014-26, §Same-Agent Provider Switch). All four are additive columns on the **unshipped** `agents` `CREATE` ([Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md)) rather than fields inside the opaque `config` blob, because each is validated against driver-reported vocabularies or read by surfaces outside the driver — the account by the [Spec-026](026-provider-accounts-and-credential-homes.md) spawn gate, the effort by the switch's own refusal check, the speed mode by the spawn that has to realize it, the pending intent by the boundary hook and by `agent.list`. No table is added and no migration ordinal is consumed. Like the channel kind above, all four must ride the record that creates the agent's row and every `agent.*` payload that moves them, never the row alone, or an agent's provider binding — and the promise that a deferred switch is still coming — would not survive replay.
- The pending column holds **one** intent or none, which is what makes the one-pending-per-agent rule structural rather than advisory, and it holds the **pending** binding only: the effective binding stays in the account, model, driver, and effort columns and moves into them at application, so a projection read never shows a switch that has not happened yet. It is cleared by whichever terminal event settles the switch, and by a superseding mutation, so a stale intent is unrepresentable.
- The switch introduces **no daemon-side state beyond those four columns**: the canonical transcript it replays is a projection rebuilt from the session event log, never a stored artifact ([Spec-004 §Canonical Transcript Export And Replay](004-provider-driver-contract-and-capabilities.md#canonical-transcript-export-and-replay)), and the declared-loss list is carried on the `agent.provider_switched` event rather than retained separately.
- The channel-directory publication (D-014-22, §Interfaces And Contracts) introduces **no daemon-side state**: no new SQLite table and no acknowledgment ledger — the startup/reconnect re-publication sweep derives entirely from the durable channel-lifecycle events, whose payloads carry the server-stamped origin-ordering keys themselves ([Spec-005 §Channel and Agent Lifecycle](005-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle), 2026-08-11), so the sweep reconstructs complete publications with no side-state. The directory's backing store is the control-plane `session_channel_directory` table ([Shared Postgres Schema §Session Channel Directory (Plan-014)](../architecture/schemas/shared-postgres-schema.md#session-channel-directory-plan-014)) — owned by the same plan as the producer, but a control-plane table, so it is outside this spec's **daemon** data model and moves no daemon table census.
- **What sessions talking to each other add to the data model is three pieces of daemon state and no record of a message** (§Sessions Talking To Each Other). The **session directory** — each session of this daemon's, its provider, its credential home and its current address — is derived from the sessions the daemon hosts and is rebuilt when it starts, so it holds nothing a restart cannot re-read and an address that moved with a restarted provider process is looked up again rather than remembered. The **exchange table** (the pair, and the count since the person last wrote in either session) and the **paused queue** (every message addressed to a paused session, in arrival order) are durable, session-scoped daemon state held with the session, because a daemon restart mid-exchange must deliver what it was holding and must not forget which two sessions were talking; a message whose state was `sent` and never seen is re-checked against the receiving session's own rows when the daemon comes back, and settles at `not delivered` where it is still absent. **A message itself persists nothing of its own**: the send and the arrival are the ordinary tool events of the two sessions' event logs, so no message table, no message row and no new event type exists for one, and the states a sent row walks through are read off those events and the run-state the daemon already holds.

## Turn Policies

| Policy | Behavior | Default |
| --- | --- | --- |
| `free-form` | Any user may send at any time; addressed agent turns admit in arrival order with no turn-taking constraint | Yes (default) |
| `round-robin` | Agents take turns in a fixed order | No |
| `request-based` | Agents speak only when explicitly addressed | No |

Tier-5 audit ratifications (D-014-19): a `round-robin` channel requires a non-empty agent order in its channel config at create time (validation refusal otherwise); the fixed order is that config value, and the next-due cursor derives from the durable run-admission sequence (no separate cursor store). `request-based` is **structurally satisfied in V1**: every agent run is explicitly created (§Default Behavior — a child run is created by user request, by workflow definition, or by an agent's own tool call, and in every case by an explicit addressing act; no agent speaks unaddressed), so every agent turn already carries an explicit addresser and admission adds no check beyond `free-form`. The policy value is accepted and recorded; dedicated request-addressing primitives become meaningful only when agent-initiated communication arrives (V2, with conclusion detection). Turn-policy enforcement governs **agent** runs; the user is never turn-blocked.

**Activation is addressing-gated under every turn policy in V1** (2026-08-03 product-vision reconciliation — the ratified activation invariant: agents act when mentioned or dispatched, never on their own initiative). An agent produces a turn only in response to an explicit addressing act directed at that agent; a channel message addressing no agent admits **no** agent turn, under `free-form` exactly as under `request-based`. Turn policy therefore governs the **ordering** of admitted agent turns and never governs whether an unaddressed agent may activate — the `free-form` and `request-based` rows above are ordering variants of one activation rule, which is why `request-based` remains structurally satisfied (D-014-19) rather than being the only addressing-gated policy. The V1 addressing act is `OrchestrationRunCreate` naming a `targetAgentId` (§Interfaces And Contracts); a client-surface `@mention` is sugar that resolves to that act and introduces no new wire contract. **An agent-authored channel message is never an addressing act in V1** — agents do not activate agents through channel speech; runs are created only by user request or workflow definition (§Default Behavior). That rule bounds activation **inside a channel** and is not a bound on how much two sessions say to each other: a message from another session is not channel speech, it starts a turn where it lands, and nothing in this runtime bounds how many two sessions trade — each provider's own limits flow in with its own numbers and the one bound the person can set is `Max steps per turn` (§Sessions Talking To Each Other). This pin structurally resolves the case the surveyed platforms leave undefined — a plain unaddressed reply in a thread where several agents are live admits **zero** agent turns rather than an implementation-defined subset: mention-gating is the surveyed default for channel-resident bots ([Microsoft Teams: channel and group conversations](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/channel-and-group-conversations), accessed 2026-08-03), and the reference Slack-resident assistant likewise filters other bots' replies while leaving the multi-agent unaddressed-reply case explicitly undefined ([Claude in Slack — when Claude responds](https://claude.com/docs/claude-tag/users/when-claude-responds), accessed 2026-08-03; public beta at that date). Agent-initiated speech remains V2, arriving with conclusion detection (§Stop Conditions).

## Budget Policies

| Budget Type            | Description                              | Default |
| ---------------------- | ---------------------------------------- | ------- |
| Token limit per run    | Max input+output tokens for a single run | None    |
| Cost limit per session | Max estimated cost across all runs       | None    |
| Turn limit per agent   | Max consecutive turns an agent can take  | None    |

Every budget in this table exists only where the person sets one. The default is none, and with none set nothing warns, interrupts or refuses on that budget — the runtime adds no ceiling the providers do not have. A budget the person did set is a hard ceiling. The daemon emits `usage.budget_warning` events (the registered [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) name for the warning this paragraph previously called `usage_warning` — Tier-5 audit, A-014-6) at 80% of any budget limit the person set, once per (scope, budget-type) crossing — and additionally, off-threshold, on the unpriced-model condition per §Cost Derivation And Absent-Cost Semantics, keyed once per (scope, budget-type, **modelFamily**) with the family carried on the payload so each newly-blocked family is separately audit-visible (campaign B6) — and issues an `interrupt` intervention via the generic dispatcher ([ADR-011](../decisions/011-generic-intervention-dispatch.md)) at 100%. Per-run token ceilings interrupt the specific offending run with `reason: budget_exhausted`; the per-agent turn limit is a stop condition, not a budget interrupt — at the limit the run **completes** with `trigger: 'turn_limit'` per §Stop Conditions (D-014-8). A session cost ceiling interrupts all active runs in the session and blocks further queue admission until the person raises or clears the limit (via `OrchestrationBudgetUpdate` — D-014-5). Context-window headroom is deliberately **not a fourth budget** (Part-B fail-closed follow-up, 2026-07-17): the three-budget table above stays the closed set, and orchestration consumers read the `usage.context_window_update` headroom signal — `windowUsedTokens` / `windowMaxTokens`, provenance-graded by `windowSource`, with the driver-computed `exceeded` predicate ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — advisorily, on a **hard-vs-soft line keyed to provenance**: `estimated`- and `model_default`-grade headroom may drive only reversible, soft responses (surface a warning, advise the owner, pre-warm the advisory auto-compaction safeguard named in §Resolved Questions and V1 Scope Decisions — invoking compaction itself mutates the live conversation and rides the hard side of this line, per that section), while any costly or irreversible action taken because of headroom (interrupting a run, refusing admission) requires `windowSource: 'provider_reported'` **with both window counts present** — or the provider-reported `exceeded: true` terminal flag, a reported fact rather than a derived ratio, which authorizes those protective actions directly so a counts-absent exhausted window is never answered more weakly than a counted one (a counts-absent, non-exceeded update carries no headroom fact to act on — the pair rule in [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — a hard action never fires off an estimated count, both because vendor token counts are documented as estimates even from the vendor's own counting endpoint and because current-generation tokenizers produce approximately 30 percent more tokens for the same text than earlier models ("The same input text produces approximately 30 percent more tokens than on earlier models … Recount prompts against the model you plan to use" — [Anthropic token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting), accessed 2026-07-12; re-verified 2026-07-17), so a window number derived from a stale pre-4.7 tokenizer assumption materially under-counts — `model_default`-grade values are tokenizer-fragile rather than merely stale; the surveyed field draws the same line — context thresholds are "automatic safeguards rather than hard stops" ([GitHub Copilot CLI context management](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/context-management), accessed 2026-07-12) — and the only hard context bound anywhere in the stack remains the provider's own real window ceiling. Conclusion detection (agent determines task is complete) remains V2.

### Cost Derivation And Absent-Cost Semantics

Session cost enforcement resolves every usage event's cost through three tiers (campaign B6). Tier (a): provider-emitted cost is consumed whenever the CLI wire supplies it, sanity-bounded — non-negative, finite, and below the configured absurdity ceiling (daemon configuration `costSanityCeilingCents`, default 10000 — a single usage event claiming ≥ $100 is rejected to tier-(b) derivation with the divergence diagnostic) (the ceiling is parameterized in the owning implementation task, not fixed here); gross divergence between an emitted cost and a derivable estimate emits a diagnostic rather than silently trusting either value (known provider over-reporting precedent). Tier (b): otherwise the daemon derives cost as token counts × the local per-model-family pricing table, with family-prefix fallback for point releases; a static local table is the ecosystem-standard mechanism, and its staleness is bounded because tier (a) takes precedence whenever the wire supplies cost. Two classification rules bound tier (b) at its table edges (Part-B fail-closed follow-up, 2026-07-17). **Explicit-$0 carve-out**: tier-(c) fail-closed applies to _unknown_ pricing only — a table entry whose price the operator explicitly set to zero (a genuinely-free local or on-prem family, e.g. an Ollama-served model) is a real price, so the family is **priced-at-zero**: admission proceeds normally, its rows emit `costCents: 0` with `costStatus: 'priced'` and ordinary `derived_*` provenance, and enforcement runs the same ceiling arithmetic as any priced family (contributing zero) — never the unpriced block; unknown-vs-explicitly-free is exactly the distinction the ecosystem's reference gateway added when it moved unmapped-model enforcement to fail-closed ([BerriAI/litellm#24949](https://github.com/BerriAI/litellm/pull/24949), accessed 2026-07-12), and without it tier (c) would false-halt every free/local model — the precise failure fail-open postures exist to avoid. **Prefix-resolves-concrete rule**: the family-prefix fallback must resolve to a concrete, explicitly-set price — a prefix hit whose matched entry carries no operator-set price (absent, or zero only via defaulting the operator never wrote) classifies the family **unpriced → tier (c), never free**: a prefix/wildcard match silently pricing at $0 is a shipped-bug class in that same gateway ([BerriAI/litellm#22609](https://github.com/BerriAI/litellm/issues/22609), accessed 2026-07-12), so the pricing-table shape MUST keep "explicitly zero" and "price absent" structurally distinct (an explicit value versus an absent field — the shape is parameterized in the owning implementation task, like the sanity ceiling above), never encoding unknown as 0. Derivation is **emit-once**: the derived value persists on the emitted `usage.cost_update` row (`costCents`, `costSource: 'derived_*'`), and replay folds those persisted row values plus the worst-case terminal debits of native-cap unpriced runs, rebuilt from their `run.queued` cap stamps (their rows are costless by design — folding rows alone would resurrect their headroom) — it never re-derives historical usage against the current table — so a pricing-table update re-prices nothing retroactively (it applies to future usage only, the same future-admissions-only idiom as `unpricedFamilyCaps`) and `observedCostCents`, warnings, and admission blocks are replay-stable. Admission preempts this tier where it can see it coming: run admission resolves the model family (the same as-of-admission resolution that stamps `admittedModelFamily`) against the pricing table, and an unpriced family admits only under a native-cap reservation — on a capless leg it **refuses at admission** (`orchestration.budget_exhausted`, `reason: 'driver_capless'`) before any queueing or spend, so the first unpriced run never starts unbounded. The mid-run path below remains only for coverage lost after admission (a pricing-table change while the run is in flight). Tier (c): otherwise the run is **budget-indeterminate and the daemon fails closed** — it emits `usage.budget_warning` with `reason: 'unpriced-model'` ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry), campaign B1) — schema-valid under the registered payload: `budgetType: 'session_cost'`, `limitValue` = the configured session cost limit, `observedValue` = the committed spend observed so far (priced cost + worst-case terminal debits of prior unpriced runs + active reservations (`reservedCostCents`) of still-running native-cap admissions; possibly 0 — the live unpriced usage itself is exactly what cannot be observed) — interrupts per the enforcement paragraph above, and blocks further queue admission for the unpriced model family session-wide (the admission refusal reuses `orchestration.budget_exhausted` with `reason: 'unpriced-model'` + `modelFamily` in `data.fields`, [Error Contracts](../architecture/contracts/error-contracts.md)).

The unpriced block — admission refusal and mid-run interrupt alike — lifts only by explicit owner action (degrade honestly, never fail open): a pricing-table update covering the family (an operator config/deploy action — the table is static local daemon configuration per the tier text above, not a session RPC; the universal escape, and the **only** one for legs without a native cap) — or, **on provider legs with a native hard budget cap only** (Claude `--max-budget-usd` at the pinned version), an owner-supplied hard USD bound under which runs proceed unpriced-but-USD-bounded with the unpriced status surfaced (their `usage.cost_update` rows carry `costStatus: 'unpriced'`, `costSource: 'unpriced_native_cap'`, `costCents` absent — the Spec-005 provenance vocabulary admits the capped-unpriced case first-class) on every affected run (supplied per model family via `OrchestrationBudgetUpdate.unpricedFamilyCaps` — one entry per family, duplicates rejected at validation; a run whose model set spans several unpriced families admits under the MINIMUM of their entries — the run-wide provider stop cannot honor per-family sub-budgets, so the conservative bound is the only safe single cap — persisted with session budgets and replayed like any budget change — the wire/state contract lives in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), this bundle). The escape reserves, never exempts: admitting a run under a family cap **reserves the full per-run cap against the session ceiling** — admission requires `observedCostCents + reservedCostCents + hardCapUsdCents ≤ costLimitCents` wherever the person set a session cost limit (with none set there is no ceiling to reserve against and cost refuses nothing), else the queue refuses with the ordinary `orchestration.budget_exhausted` (whose `observedValue` then carries committed spend: observed cost including unpriced terminal debits, plus active reservations); at the run's terminal state the reservation **converts to a worst-case charge, never back to headroom**: the admitted cap moves from `reservedCostCents` into `observedCostCents` as an unpriced debit (the actual spend is unknowable by construction, so the full cap is what the ledger records — serial unpriced runs therefore consume the ceiling cumulatively exactly like priced work, and a session can never launder unbounded spend through admit-finish-repeat), the reserved amount **snapshots at admission onto the run's `run.queued` admission record** (`admittedUnpricedCapCents` — a server-stamped sibling of `effectiveRunConfig`, deliberately not an `OrchestrationRunConfig` member so a run-create request can never inject it; persisted per D-014-5), so later `unpricedFamilyCaps` updates apply to future admissions only and can never retro-shrink an active run's reservation and restart/replay rebuilds reservations and debits from the server-stamped `run.queued` records alone, the admitted cap **wires through to the driver** on the run params (`StartRunParams.admittedCostCapCents` — realized as the native cap on cap-capable legs, Claude `--max-budget-usd`, per [Spec-004](004-provider-driver-contract-and-capabilities.md)'s params; a leg that binds caps at spawn realizes it at session boundaries per the posture precedent) so the local reservation is always backed by the provider-side hard stop, and admission is daemon-serialized so reserve-then-admit is race-free, and the 80% warning threshold evaluates the same committed-spend sum; a capless leg (Codex at the pinned version — its `token_budget` is upstream-under-development) stays fail-closed until its pricing-table entry lands, so its named escape is the pricing-table path. A Day-0 model family therefore never silently runs unbounded and never hard-blocks without a named escape. Enforcement MUST NOT branch on `costSource`: provider-emitted and daemon-derived cost feed one ceiling with no dual trust regimes — the `costStatus`/`costSource` provenance mirrors ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) are observability, not policy inputs. The surveyed reference runtime's fail-open zero-cost terminal is the one surveyed posture explicitly not ported. Currency (2026-07-06): the tier-(b) table seeds from the current vendor model catalogs — Claude Sonnet 5 / Fable 5 families and Codex `gpt-5.5` / `gpt-5.4` / `gpt-5.3-codex-spark` ([Anthropic model overview](https://docs.anthropic.com/en/docs/about-claude/models/overview), [OpenAI models](https://platform.openai.com/docs/models), both accessed 2026-07-06) — and the Claude per-run `--max-budget-usd` cap ([provider-wire reference, claude.md](../reference/provider-wire/claude.md), version-pinned) is wired as defense-in-depth beneath this accountant, never as the accountant. Codex's caplessness is auditable from the pinned wire surface ([provider-wire reference, codex.md](../reference/provider-wire/codex.md) — no budget-cap parameter exists at the pin); upstream work on a `token_budget` config was observed at survey time (2026-07-02) but is not pinned and confers nothing here. The three-budget table above and the §Stop Conditions closed set (D-014-8) are unchanged by this subsection. The provider-side hard stop also survives recovery: resume/relaunch re-threads the admitted cap from the durable `run.queued` payload into `ResumeSessionParams.admittedCostCapCents`, and reservation is gated on the leg's `cost_cap` driver capability (Spec-004 matrix) — a capless leg refuses fail-closed (`reason: 'driver_capless'`), never reserves-without-enforcement. The cap rides every provider-process entry point — spawn (`CreateSessionParams`, where Claude binds `--max-budget-usd`), run start (`StartRunParams`), and resume (`ResumeSessionParams`) — so no capless window exists between admission and enforcement; and on a spawn-bound leg a native-cap run **starts only inside a provider session spawned with the matching cap**: an existing uncapped (or differently-capped) process forces a capped relaunch at the session boundary before `startRun` dispatches (the posture-relaunch precedent), never a start inside an uncapped process.

### Cost Figure Display Consistency

Every cost figure this spec's surfaces expose derives from the **same committed-spend fold the accountant enforces against** — the fold specified in §Cost Derivation And Absent-Cost Semantics above: persisted priced row cost, plus the worst-case terminal debits of unpriced native-cap runs rebuilt from their `run.queued` cap stamps, plus the active reservations of still-running native-cap admissions. Three rules bind (2026-08-17, D-014-24).

**(a) One fold, never a second accountant.** A surfaced session-level or run-level cost figure is **supplied by** the accountant that enforces, never recomputed beside it. Summing the runs visible in a run list is expressly not a permitted derivation, and no surface may maintain an independently-folded total for presentation. The three committed-spend figures V1 actually surfaces are therefore the same number at the same fold state: the `OrchestrationBudgetState.committedSpendCents` member — one figure, not two, because the budget read and the budget update answer with that same state type and are served from the same accessor — and the `observedValue` the daemon stamps on a **session-cost** `usage.budget_warning` — the `budgetType: 'session_cost'` member of that event's three-value union ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — both already defined as committed spend by the tier-(c) and escape paragraphs above, and that cross-surface equality is **asserted**, not assumed (I-014-24 at [Plan-014 §Invariants](../plans/014-multi-agent-channels-and-orchestration.md#invariants), asserted by T2.5 at [Plan-014 §Phase 2 — Daemon orchestration services](../plans/014-multi-agent-channels-and-orchestration.md#phase-2--daemon-orchestration-services)). The third is the `observedValue` a session-cost `orchestration.budget_exhausted` refusal stamps in its `data.fields` ([error-contracts.md §Orchestration](../architecture/contracts/error-contracts.md#orchestration)): the admission predicate that refuses reads `committedSpendCents` from the same accessor, and the refusal stamps exactly the value the predicate read, so the refused caller is shown the enforced number too — three surfaces, one accessor, one value (the PR #343 Codex round-3 fold). The warning-side equality is scoped to that event's session-cost member alone: a `run_tokens` warning stamps a token count and an `agent_turns` warning a turn count, neither of which is a cost figure and neither of which this subsection governs. The read response's other cost members are components of that number rather than independent totals — the identities in clause (c) pin each of them to it, so there is exactly one total on the surface and no second one to drift. The failure this forecloses was observed in the campaign's reference-runtime parity survey (2026-08-12; a first-party field observation, recorded inline per the amendment header's provenance note): the surveyed overview listed each root run with only that run's own ledger cost while the spend of delegated work landed on the children those runs called, so a large multi-run campaign displayed at a small fraction of its true cost — a display fold that had silently drifted from the number the ledger held. V1's structure already bounds the drift class (every child run carries a receipt row of its own at whatever depth it sits, under the per-run partition of §Session Cost Receipt, in-session subagent usage rolls into the parent run's own budget per §Provider-Native Subagents, and the session ceiling folds everything), which is why the residue is this display-side rule rather than a re-derivation of the fold itself.

**Where a cost figure may stand is closed too.** On a session's own surface money appears in exactly two places: the session's cost detail, which reads the receipt's per-paying-account axis, and the spend carried against each agent in the session's agent list. Nowhere else — not beside the context-window reading, which stays a context reading and its compaction control; not in a footer under the session list or the destination rail; and no billing period, no per-model split, and no account-wide total anywhere on a session's surface. Account-level figures — an account's usage windows, its lifetime spend with its billing-mode label, and any total across accounts — belong to the provider-account surfaces [Spec-026](026-provider-accounts-and-credential-homes.md) owns, and no second usage surface is added beside those. The division is not cosmetic: a quota describes an account's standing with its provider rather than a session's spending, and the receipt is session-wide while provider quota is node-local (§Session Cost Receipt).

**(b) A per-run figure declares its aggregation scope.** Any surfaced run-level cost figure states whether it is **run-only** or **run-plus-children-plus-in-session-subagents**; an undeclared per-run figure is exactly the ambiguity the surveyed overview shipped. **Every per-run cost figure V1 exposes is a session cost receipt row (§Session Cost Receipt), and every one of them declares `run-only`**. One source, drawn wherever it is useful: the console draws those rows in two places — the session's cost detail and the spend carried against each agent in the session's agent list — and neither is a second fold, because both are served from the accountant's single accessor per clause (a). Where an agent in that list is an in-session subagent it has no receipt row of its own, and the figure carried against it is the **subagent-attributed part** of its run's row, supplied by the daemon from the same persisted usage rows the fold reads — those rows already carry the subagent attribution (§Provider-Native Subagents) — so it is a decomposition of an existing row under clause (c)'s discipline and never a total of its own; the run's row stays `run-only` and continues to include it. The declaration is uniform because the receipt lists every run of the session as its own row: a delegated child run appears beside its parent rather than inside it, so summing the rows double-counts nothing and no row silently absorbs another's spend. In-session subagent usage is the one thing a `run-only` row does include, because [Spec-014 §Provider-Native Subagents](./014-multi-agent-channels-and-orchestration.md#provider-native-subagents) already rolls it into the parent run's own budget — it is not delegation to a separate run and has no row of its own to be counted twice from. Every child run has a receipt row of its own at whatever depth it sits, and the parent-child links the receipt reads say which row belongs under which, so the parent-plus-children reading is always recoverable from the rows the receipt already shows, which is why V1 needs no second scope label. This clause is therefore **verified positively**: the assertion is that every run-level figure the receipt emits carries the `run-only` declaration, and that no surface presents a per-run figure the receipt did not supply (I-014-24 at [Plan-014 §Invariants](../plans/014-multi-agent-channels-and-orchestration.md#invariants), extended in the same amendment). The forward obligation on any plan that grows a further cost-displaying surface is registered as CP-014-16 at [Plan-014 §Cross-Plan Obligations](../plans/014-multi-agent-channels-and-orchestration.md#cross-plan-obligations).

**(d) A token figure declares its scope too.** The one-fold rule of clause (a) is **cost-scoped and stays that way**: the token axis deliberately carries two folds — the per-run enforced token budget (`tokenLimit`, the ceiling admission and interrupt act on) and the conversation-scoped token count the composer meter displays — and that divergence is intentional and reconciled at the auto-compaction safeguard in §Budget Policies. Nothing here collapses them. What does bind, as the token-axis analogue of clause (b), is the declaration: **any surfaced token figure states which of the two it is** — per-run enforced budget, or conversation-scoped observed count. The concrete case this closes is a rendered `run_tokens` budget warning, whose `observedValue` is a per-run token figure that no rule previously governed and that reads, beside a conversation-scoped meter, as though the two were the same quantity. Declaring the scope is the whole obligation; no fold changes, no surface is added, and no figure moves.

**(c) Provenance rides the figure, supplied by the wire.** Where unpriced-run debits or active reservations contribute to a surfaced total, the presentation carries that fact, and the **daemon reply** supplies it rather than the client inferring it — a renderer computing provenance from component fields would violate Plan-014's zero-client-derivation rule (I-014-19), and an SDK doing so its marshal-never-derive rule (I-014-16) — both rows at [Plan-014 §Invariants](../plans/014-multi-agent-channels-and-orchestration.md#invariants). The budget state therefore decomposes the number it already reported, on the `orchestration.budgetRead` and `orchestration.budgetUpdate` replies alike ([API Payload Contracts](../architecture/contracts/api-payload-contracts.md), this bundle): `observedPricedCostCents` (the exact priced leg), `observedUnpricedDebitCents` (the worst-case terminal-debit leg), `committedSpendCents` (the sum enforcement compares against the ceiling), and an **aggregate `costStatus`** reusing the row-level [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) vocabulary with aggregate semantics defined here: `'priced'` when the total is exact — no unpriced debit contributes, no active reservation contributes, and the session's persisted history records no mid-run tier-(c) classification (§Cost Derivation And Absent-Cost Semantics: pricing coverage lost after admission, whose in-flight unpriced usage is unobservable by construction and enters no leg of the fold) — and `'unpriced'` when any of the three holds. The third condition replays from a durable trace exactly as the debits do: the mid-run classification's persisted `usage.budget_warning` (`reason: 'unpriced-model'`) **carries the interrupted run's `runId`** — required on that emission path, the same per-path requiredness discipline Spec-005 states for `modelFamily` on that event's optional members — while an admission-time family refusal precedes any run and stamps no `runId`, so the residue key is precisely the run-stamped warning and never the admission-time block. The once-per-`(scope, budget-type, modelFamily)` emission latch that warning dedups on is **epoch-scoped, never lifetime-scoped**: the explicit owner action that lifts a family's unpriced block re-arms the latch for that family, so a family refused runless at admission, repaired by a pricing-table update, re-admitted, and then classified tier-(c) mid-run emits a **second** warning — the run-stamped row the residue condition keys on — rather than being silenced by the spent key of the admission-time row (the PR #343 Codex round-2 fold). Torn-append crash windows do not defeat the key: the tier-(c) classification is a deterministic function of persisted state — the unpriceable usage row, the absent cap stamp, and the pricing table's persisted emit-once derivations — and the replay-rebuilt accountant re-runs it, so a daemon that crashed after appending the unpriceable row but before appending the warning re-classifies that row at rebuild and appends the missing run-stamped warning then, or, where a table repair has since restored coverage, prices the row into the observed leg — either way the rebuilt fold is honest: the spend is observed or the residue is recorded, never neither (the PR #343 Codex round-3 fold). Two identities hold at every fold state: `observedPricedCostCents + observedUnpricedDebitCents === observedCostCents`, and `observedCostCents + reservedCostCents === committedSpendCents`. This is a **decomposition of the existing number, not new arithmetic** — the two observed legs are precisely the two folds `observedCostCents` was already rebuilt from, so the decomposition is replay-stable for the same reason the fold is. The aggregate `costStatus` is observability exactly as its row-level sibling is: enforcement reads `committedSpendCents` and **MUST NOT** branch on it, per the no-dual-trust-regimes rule above.

**The total is not a lower bound.** The surveyed runtime's pricing fold counts its unpriced rows, so its total can honestly label itself a lower bound; this spec's unpriced runs are instead charged their **full admitted cap** as a worst-case debit at terminal state. The committed-spend figure is therefore exact for priced usage, worst-case for unpriced native-cap usage, and forward-looking for the reservations of runs still in flight — with exactly one exclusion: the in-flight usage of a mid-run tier-(c) classification (pricing coverage lost after admission) is unobservable by construction and enters no leg of the fold, bounded by that path's immediate interrupt and surfaced — never silently absorbed — by the aggregate `costStatus` turning `'unpriced'` per clause (c). A surface MUST NOT label the figure a lower bound, because the label is wrong in both directions: the worst-case cap debits make it **over**-state settled spend by the unconsumed remainder of the caps already charged, and, when the mid-run residue is present, it additionally omits spend no fold can observe — a bound label in either direction claims knowledge the accountant does not have. What the figure always is, is the enforced number, which is exactly what clause (a) requires a surface to show, with clause (c)'s provenance riding it.

This subsection mints no event type, no wire method, no error code, and no table, and adds no budget: the three-budget table above stays the closed set it was, and the §Stop Conditions closed set (D-014-8) is unchanged.

### Session Cost Receipt

Added 2026-08-18. Every session carries a **cost receipt**: a collapsed line showing the session total, which expands into a detailed transcript of what that total is made of. The collapsed line is the committed-spend figure clause (a) already governs — the same number, from the same accessor, with no second fold behind it. The receipt is what makes that number answerable rather than merely correct: an operator who sees a session cost and cannot find out what caused it has a figure, not an account.

**The transcript is a decomposition, never a re-fold.** This is the same move clause (c) makes for the priced/unpriced axis, applied to the two axes below, and it is bound by the same discipline: the accountant that enforces is the accountant that answers, the decomposition members are components of the number it already reported, and identities pin every part to the whole. A presentation-side re-aggregation — summing rows the client can see, or maintaining a parallel tally of its own — is expressly forbidden by clause (a) and is not made permissible by being a detail view. Concretely, the receipt decomposes committed spend along two axes:

- **Per run.** One row per run of the session, each declaring `run-only` per clause (b). A delegated child run gets its own row beside its parent rather than being folded into it.
- **Per paying provider account.** Each row carries the account that paid ([Spec-026 §Selection at run start](026-provider-accounts-and-credential-homes.md#selection-at-run-start)) and that account's billing mode, under the labeling rule at [Spec-026 §Billing mode](026-provider-accounts-and-credential-homes.md#billing-mode): plan-included usage is never presented as billed dollars without its label, and a total spanning both billing modes states that it does.

Two identities hold at every fold state, and they are the receipt's whole correctness argument: the per-run rows sum to the session's committed spend, and the per-paying-account rows sum to it as well. Each axis is a **partition** — every unit of committed spend appears in exactly one row of each axis, which is why either axis totals to the same number and why neither can quietly omit or duplicate a contribution. The unpriced and reserved legs decompose along these axes exactly as they do along clause (c)'s, so a receipt row carries the same aggregate `costStatus` vocabulary and the same provenance obligation as the session figure: the receipt never invents an honesty marker of its own, and in particular **never labels any figure a lower bound**, for the reason the not-a-lower-bound rule already gives — worst-case cap debits make committed spend over-state settled spend, so the label would be wrong in both directions at the row level exactly as it is at the session level.

**Derivation is fold-of-persisted-rows, exactly as enforcement is.** The receipt re-uses the emit-once ladder in §Cost Derivation And Absent-Cost Semantics without amending it: it folds the persisted `usage.cost_update` row values plus the worst-case terminal debits of native-cap unpriced runs plus active reservations, and it **never re-prices anything at read time**. A pricing-table update re-prices no history for the receipt any more than it does for enforcement, so a receipt rendered twice at the same fold state renders identically, and a receipt is replay-stable for precisely the reason the accountant is. The attribution axes add keys to the fold; they do not add arithmetic.

**Cross-machine behavior, stated honestly.** The receipt folds the session's own usage events, and those events travel the ordinary session event relay: the seven session-scoped `usage_telemetry` types carry the real `sessionId` of the run or session they meter ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)), so a session spanning two runtime nodes yields one receipt covering both, and a joining peer's backfill recovers the spend history it is entitled to. One usage type is deliberately **not** part of this: `usage.rate_limit_update` is account-plane, binds to the reserved node-scope sentinel rather than to a session, and sentinel-bound rows are excluded from peer history backfill and are witnessed locally only in V1. The consequence is stated rather than papered over — **provider quota display is node-local, while the cost receipt is session-wide.** Those are different scopes for good reasons (a quota describes an account's standing with its provider, not a session's spending), and no V1 surface presents the account-plane quota as though it were session state.

This subsection mints no event type, no table, and no budget. It mints one read surface (registered in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md)) whose every figure is served from the same committed-spend accessor as the budget read, and the paying-account axis it reads is supplied by [Spec-026](026-provider-accounts-and-credential-homes.md).

## Stop Conditions

| Condition | Trigger | Behavior |
| --- | --- | --- |
| Turn limit reached | Agent exceeds turn limit | Run completes with `turn_limit` metadata |
| Budget exhausted | Token or cost limit exceeded | Run interrupted with `budget_exhausted` reason |
| Explicit stop | User sends stop command | Run interrupted via cancel intervention |
| Idle timeout | No activity for a window the person set; none is set by default | Run interrupted with `idle_timeout` reason |
| Workflow phase cancelled | The run's owning workflow phase terminates its in-flight channel work ([Spec-015](015-workflow-authoring-and-execution.md) SA-9 `REQUEST_CANCEL` / `TERMINATE` cascade — added 2026-08-11, D-014-23) | Run interrupted with `workflow_phase_cancelled` reason |

Conclusion detection (agent determines task is complete) is V2.

Tier-5 audit definitions (D-014-8): a **turn** is one completed assistant-output cycle attributed to a (channel, agent) pair; the consecutive-turn counter resets when a different agent (or the user) takes an interleaving turn in the same channel. At the turn limit the run completes with `trigger: 'turn_limit'` and further same-agent admission into that channel is refused with explicit limit detail until an interleaving turn occurs or the person raises or clears the limit (the change is `orchestration.budgetUpdate` on the session's `turn_limit_per_agent` and reaches only channels with no override — a channel carrying a `turnsPerAgent` override is create-time-fixed and recovers by interleave alone, §Interfaces And Contracts, D-014-23). **Activity** for the idle timeout is any appended session event whose payload carries the run's id; the idle sweep is a daemon-owned per-run timer armed only where the person set an idle window for that run — with none set no timer runs and a quiet run is never interrupted — and an armed timer is subject to two cross-spec exemptions: while a run's work item has a pending outbound cross-node dispatch the sweep hard-skips **that dispatch-initiating run** — such waits are locally event-quiet by construction and bounded by the dispatch's own caller-local expiry window ([Spec-022 §Required Behavior](022-cross-node-dispatch-and-approval.md#required-behavior), campaign B7); and a run in a blocking state (`waiting_for_input` / `waiting_for_approval`) is likewise hard-skipped while the state holds. **A wait for a person never expires**: an approval, a plan card and a question stand until they are answered, and the only things that end one are the answer itself, an interrupt of the run, a move to a permission level that never asks — which answers an open card and lets the blocked row run — and the provider process ending. The exemption therefore ends when the block ends, returning the run to ordinary idle semantics; a pre-turn moderation gate is not one of these waits and keeps its own denial path (`moderation_denied`), being a check the daemon makes rather than a card a person answers — per Spec-010's decoupled-but-coordinated rule ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior), [run-state-machine.md §Invariants](../domain/run-state-machine.md#invariants)), while the startup-reconciliation divergence halt — `waiting_for_input` carrying `recovery-needed`, backed by no pending ask or approval — is a designed human-action halt the sweep never times out: it exits only by human recovery action and surfaces on the recovery status channels ([Spec-013 §Fallback Behavior](013-persistence-recovery-and-replay.md#fallback-behavior), campaign B5/B14). Unrelated runs in the same session keep ordinary idle semantics under both exemptions. The four system-interrupt reasons (`budget_exhausted`, `idle_timeout`, `moderation_denied`, `workflow_phase_cancelled` — the fourth added 2026-08-11, D-014-23: minted by this spec, invoked only by the workflow engine's SA-9 phase-termination cascade ([Spec-015](015-workflow-authoring-and-execution.md)/Plan-015, which names the member and never authors it) through the same in-process system-intervention entrypoint as the other three, D-014-7) form a closed set carried on the interrupt intervention.

## Intervention Propagation

Interventions use the generic dispatcher defined by [Spec-003](../specs/003-queue-steer-pause-resume.md) and [ADR-011](../decisions/011-generic-intervention-dispatch.md). Spec-014 introduces no new intervention verbs.

- A pause, interrupt, or steer applied to a parent run does not auto-cascade to its child runs. Each child run is an independent intervention target. The same holds at every level of the in-session agent tree (§Provider-Native Subagents): interrupting one agent reaches that agent and nothing else — the agents it dispatched keep working, and whatever dispatched it keeps working. Continuing a paused agent likewise continues that agent alone.
- Propagating an intervention across a parent/child subtree requires the caller to submit one intervention per run. This preserves Spec-003's audit property that every run-state transition corresponds to a distinct `InterventionResult` record.
- A steer applied to a parent run does not inject content into child-run conversations — child runs receive steer content only when the steer is targeted at the child run's id.
- Child runs accept the same run-control surface as standalone runs — steer and interrupt via `applyIntervention`, pause/resume via the orchestration-layer `run.pause` / `run.resume` verbs (Spec-003; the driver never needs to know about pause). Driver capability semantics (Spec-003's steer degradation, for example) apply uniformly. **Every live agent in the in-session tree takes that same surface, at any depth, whatever dispatched it and whichever provider runs it**; the daemon owns the mechanism behind each control per provider (Spec-003) and no difference in mechanism reaches the caller or the screen.
- **A per-agent pause is never a process freeze.** Both providers run their subagents inside the run's own provider process, so freezing one agent at the process level would freeze the run and its siblings with it; a process freeze stays available only as a whole-session pause. An agent's pause is therefore a hold the daemon places on that agent's own next step, and it is lossless: the agent waits without spending, and the hold ends only by an answer — continued, or steered with the user's own words.
- **An interrupt leaves nothing running behind it.** Interrupting an agent ends the command that agent had in flight as well as its own turn — on the Claude leg the hold on its next step together with the end of its running command, on the Codex leg that provider's own terminal verbs for the same purpose — so no command outlives the agent that started it. The agent then waits for a steer rather than disappearing, and a steer starts it again with everything it knew.
- **An intervention must not reach what it was not aimed at.** An interrupt of a run never collaterally ends an agent that run dispatched: on the Claude leg the daemon moves a foreground agent to the background over the provider's own background request before it interrupts the run, so the interrupt spares that agent exactly as it spares every background one; on the Codex leg every agent already runs on its own thread and what blocks the run is its own wait, so nothing is needed. The daemon additionally declares the provider's per-task stop affordance so that an ordinary interrupt cannot sweep up background subagents.
- **The interventions that do reach a whole subtree are fan-outs, never a cascade primitive.** Exactly three reach more than one agent: a session-wide interrupt, a stop of everything running in the session's agent tree, and an undo's stop of the agents started after its point. Each is **one ordinary intervention per run id**, taken from the daemon's own parent-to-child index at every depth (§Interfaces And Contracts) — so Spec-003's audit property is preserved exactly as the bullet above requires, and the count a confirmation states is that index's count rather than a client's. None of the three is relayed through the run that dispatched the tree, because no provider's lead can stop its own subtree: the Claude leg's stop tool refuses a grandchild as another agent's, and the Codex leg publishes no stop-all verb at all.
- **One intervention crosses a session boundary, and only one.** Interrupting a session that is trading messages with another session ends the turn on both, because the other side's next message would otherwise wake this one straight back up (§Sessions Talking To Each Other). It reaches exactly the session on the other end of that exchange, named by the pair the daemon's exchange table already holds, and never a third; it is the same fan-out shape as the three sweeps above — one ordinary interrupt per run, each landing its own `InterventionResult` — and no new intervention verb is minted for it.
- A subtree-wide **atomic** propagation — one call that cancels a parent and all its descendants as a single transition, with one result — is a new ADR rather than a payload field addition, consistent with ADR-011's Type-1 reversibility stance. The three sweeps above are deliberately not that: each dispatches an ordinary intervention per run and each run lands its own `InterventionResult`, so a partially-refused sweep is legible rather than atomic-and-silent.

## Moderation Hooks

- Pre-turn approval: before an agent's output is committed to the timeline, an approval gate can require human review.
- Post-turn review: after output is committed, a review flag marks it for human inspection (non-blocking).
- Both hooks integrate with the approval system (Plan-010): category `gate` for pre-turn, informational event for post-turn.
- V1 default: no moderation hooks enabled. Opt-in per channel.

Tier-5 audit ratification (D-014-10): the pre-turn gate point is `PermissionCheckService.check({category: 'gate'})` evaluated at the turn boundary **before** the turn's `assistant_output` event is appended; pending output buffers in memory while the run blocks per the standard approval-blocking flow, a denial discards the buffered output and system-cancels the run with `reason: moderation_denied`, and an approval appends it unchanged. The post-turn informational event is the registered `moderation.review_flagged` ([Spec-005 §Approval Flow](005-session-event-taxonomy-and-audit-log.md#approval-flow-approval_flow)).

## Session Goals

- A session MAY carry one structured goal (campaign B6): `goal: { text: string }` — the structured object [Spec-005 §Session Lifecycle](005-session-event-taxonomy-and-audit-log.md#session-lifecycle-session_lifecycle) binds to `session.goal_updated.goal` (campaign B1). The single required member is `text` — bounded free-form (1–4096 characters, non-blank, NUL-rejected; the repo's standard free-form wire guards) since it persists into the event log and injects into provider prompts; extending the shape requires a spec revision, and an update without a goal is malformed rather than an implicit clear (clearing is the distinct operation).
- Set and clear are RPC operations, authorized as the session's user like every other session mutation (`SessionGoalUpdate` / `SessionGoalClear`, following this spec's `OrchestrationBudgetUpdate` naming precedent; wire shapes `SessionGoalUpdateRequest` / `SessionGoalClearRequest` + the `session.goalUpdate` / `session.goalClear` method rows live in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), this bundle); an accepted operation emits the registered `session.goal_updated` / `session.goal_cleared` event carrying the same canonical value the RPC supplied, so RPC and durable event serialize identically. A goal change is not a run-state transition.
- Goal state derives from the event log as a projection — there is no separate goal store; the current goal is whatever the latest goal event says.
- Provider delivery (parity triad, campaign B6): the Codex leg is native (`thread/goal/*`); the Claude leg is emulated — the daemon stores the goal and injects it via system-prompt composition on turn start and resume. Delivery to a live run rides the [Spec-004](004-provider-driver-contract-and-capabilities.md) driver operations — whose exported code-contract mirror (`setSessionGoal` / `clearSessionGoal` methods + `DriverGoalResult` in `packages/contracts`) lands with [Plan-004](../plans/004-provider-driver-contract-and-capabilities.md)'s driver phases via the campaign's Plan-004 bundle, so the live-delivery requirement is code-dispatchable only after that mirror (adding required interface methods in this doc bundle would break existing `ProviderDriver` implementors) — (`setSessionGoal` / `clearSessionGoal`), whose `goalText` is rendered from `goal.text`; the mechanism grade (`native | emulated`) is recorded in the Spec-004 capability matrix (`session_goals`). With multiple active provider legs, delivery is **all-or-nothing**: the mutation fans out to every active binding, `session.goal_updated` / `session.goal_cleared` commits only after all of them ack — an ack means `DriverGoalResult.status: 'applied'`; a `degraded` result is **not** an ack and takes the refusal path (revert + typed error) unless the degraded fallback is itself a verified apply committed by the daemon (the Claude emulated leg's daemon-owned staging is exactly that). Goal changes are **turn-boundary-effective on every leg**: a native ack and an emulated stage both mean the goal durably governs the _next_ turn or resume — an in-flight provider turn completes under the prior prompt on all legs alike, so the committed `session.goal_*` event records the mutation without claiming a mid-turn prompt swap (there is no divergence to reconcile, only the defined boundary). And the fan-out target set is race-free by serialization: **run/binding admission for a session with an in-flight goal intent waits for intent convergence** (the same daemon-serialized session admission that makes budget reserve-then-admit race-free), so no binding can appear between target-set enumeration and the event append; and "live" is the process supervisor's judgment, not the store's — `runtime_bindings` persists no liveness by design (a persisted flag would claim live across a daemon crash), the supervisor's process ↔ binding map names each active run's CURRENT binding, and superseded rows from earlier relaunches never enter the target set — and any refusal or failure durably marks the refusing leg `failed` before compensation begins (so crash replay continues the revert instead of re-issuing a doomed mutation), then re-asserts the prior goal on every non-failed leg — acked and pending alike, since a pending leg's in-flight call may have applied without acking (goal set is last-write-wins, making revert exact) — deletes the dispatch intent **only after every non-failed leg's re-assertion has acked** (a failed or unconverged revert keeps the intent durable with that leg still unconverged; the revert retries immediately and on startup replay; every leg of an unconverged intent is **turn-gated**, applying and compensating alike — mid-apply, an acked leg holds its next turn until the append/delete transaction commits (its provider already carries the new goal, and a turn before convergence would run under a goal the durable log might never record); during compensation, the goal-at-turn-dispatch precondition re-applies the projected prior goal to an acked-unreverted leg before any turn dispatches — so no leg ever runs a turn under an uncommitted goal; and further goal mutations for the session stay refused — one in-flight mutation per session, whether the prior intent is still applying or compensating, surfaced as the registered `session.goal_mutation_in_flight` conflict — until convergence). On the success path the `session.goal_*` append and the intent delete commit in **one daemon-SQLite transaction** (both tables are daemon-local), so a committed event with a live intent — and therefore a double-apply on replay — is unrepresentable. Startup reconciliation is idempotent by re-assertion (goal set/clear is last-write-wins): an interrupted apply re-issues the mutation to **every** leg, acked included (acked is advisory across a restart — a restarted provider may have lost a not-yet-appended goal); a failed intent re-asserts the **prior** goal on every leg, pending included (an in-flight call may have applied without acking), and surfaces `session.goal_delivery_failed` — the durable log and every live leg agree at each turn boundary (per the turn-boundary-effective rule above, an in-flight turn completing under the prior prompt is the defined semantic, not divergence); a binding that terminates before its dispatch resolves simply leaves the target set (a dead leg needs no delivery and can never strand the mutation); legs attaching later receive the current goal at attach/resume via their parity mechanism, and a newly admitted leg in an already-goaled session receives the projected goal **before its first turn** (the same goal-at-turn-dispatch precondition, applied at leg start by the admission/start path). Cross-node sessions follow this spec's AP partition model (availability over consistency; local daemons own their attached runs): the synchronous all-or-nothing barrier binds the legs owned by the mutating daemon; legs on other runtime nodes converge through the relayed event log — each owning daemon applies the projected goal to its local legs with the same intent/retry machinery, and **applies it before dispatching any further turn to a leg** (goal-at-turn-dispatch precondition), so no leg starts a turn under a goal staler than its own node's replayed event log. On the mutating node that is the committed goal immediately; on a remote node, legs MAY run turns under the prior goal while the relayed event is delayed or partitioned away — the deliberate AP posture (remote runs continue locally; convergence is bounded by [Spec-022](022-cross-node-dispatch-and-approval.md)'s reconnect/replay, never by a cross-node lock) — and the precondition applies the relayed goal before the first turn after it arrives. The one-in-flight serialization above is likewise **per-node**: the intent table is daemon-local, so `session.goal_mutation_in_flight` refuses concurrent mutations only among callers of the same daemon, and mutations accepted on different nodes while the relay is delayed or partitioned are NOT mutually refused — they converge as a **last-writer-wins register**. Every daemon's goal projection folds `session.goal_updated` / `session.goal_cleared` in **two stages**: within one origin daemon, its own append order is authoritative — the origin's latest goal event by the **server-stamped payload keys `originNodeId` + `originSeq`** (the accepting daemon's per-session append sequence over the session's goal events — class-scoped: the 2026-08-11-amended channel-lifecycle payloads carry a sibling counter of their own and no consumer compares `originSeq` across event classes, per Spec-005 (PR #321 round 2) — durable on every goal payload per Spec-005, because a receiving daemon re-sequences relayed events under its own local `sequence` per ADR-017 and origin order would otherwise be unrecoverable), per [Spec-013](013-persistence-recovery-and-replay.md)'s within-daemon ordering rule (`occurred_at` is display/audit data and never orders same-daemon events, so a wall-clock step between two serial local mutations can never invert them) — and only BETWEEN different origins' latest candidates does the cross-origin comparator apply: envelope `occurredAt`, tie-broken by envelope `id` (the best V1 cross-daemon primitive — HLC is the V1.1 upgrade path per ADR-017/BL-076). The fold is a pure function of the event set, so once both events replay everywhere, every node settles on the same final goal (cross-node wall-clock skew is bounded by Spec-013's clock discipline, and a skew-misordered CONCURRENT write costs at most a goal overwrite between two mutations that raced anyway — never divergence), and the goal-at-turn-dispatch precondition applies the converged winner before each leg's next turn. A control-plane lease or lock on goal mutation is deliberately rejected: goal mutation stays available under partition — the same availability-over-consistency trade-off the cross-node AP model above already commits to.

## Same-Agent Provider Switch

Added 2026-08-26 (D-014-26) under [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md). An agent's provider is an **axis of its configuration**, not a fact fixed when its session started. A user may move a conversation from one provider to another — or to a different model, or a different reasoning effort — without losing the conversation or starting a second agent.

**Which account pays is not an axis of this mutation.** An account belongs to its provider, and the control that changes which account a provider's work runs on is the provider surface's own ([Spec-026 §Moving a session to another account](026-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)): pressing an account there makes it that provider's current account and moves every running session on that provider that is not pinned to one. A per-session account switch beside it would let a session sit on an account the provider surface says it is not on, so this mutation carries no account member and mints no account refusal.

**Where the provider switch is picked.** The session composer's **model control** lists both providers' models under two headings, `Claude Code` and `Codex`, and picking a model under the other provider's heading is how a provider switch is asked for. There is no separate provider picker: the model and the provider that runs it are one choice, and two controls setting one binding would let them disagree. Picking again replaces the pending pick; picking the current provider's model back cancels it. While a pick is pending the working line's state slot reads `switching to Codex` or `switching to Claude` and the control itself keeps reading the model.

### The mutation surface

`AgentConfigUpdate` carries the provider-axis members beside the persona members it already had, every one **additive-optional**, and the set is re-derived by listing rather than counted: `driverName?`, `modelId?`, `effort?`, and `outputSpeed?`. The axes a run is started with carry `providerAccountId?` and `effort?` and deliberately **not** `outputSpeed?`: an agent is not born with a speed mode, and fixing one at the start would put a resolved axis on the `agents` row for a preference no authorization decision reads. **`providerAccountId` is a run-start input and not a member of this mutation** — which account pays is the provider surface's control, per the paragraph above — so the agent row still records the account a run resolved and this update never moves it. An omitted member is unchanged, not reset — the same additive-optional discipline [ADR-018](../decisions/018-cross-version-compatibility.md) binds everywhere else. There is correspondingly **no clear**: V1 offers no operation returning a provider axis to a driver default. `driverName` and `modelId` could not be cleared in any case — an agent always has both — and clearing `effort` would need a third request state this surface deliberately does not carry, since "omitted means unchanged" is uniform here and a member that sometimes meant "reset" would make every omission ambiguous. The consequence is load-bearing downstream rather than merely tidy: the pending intent is stored as a two-state record of moved axes and their targets ([§State And Data Implications](#state-and-data-implications)), and a clear would have to widen that record to the `defaultNodeId` tri-state in the same amendment that minted it.

`effort` is first-class here rather than buried in the opaque `config` blob because it is validated, surfaced, and switched like `modelId` is: it is per-model, and the valid set is the target model's `effortLevels` as reported by the driver ([Spec-004 §Provider Parameter Vocabularies](004-provider-driver-contract-and-capabilities.md#provider-parameter-vocabularies)), not a corpus-wide enum. A value outside that set is refused rather than clamped, because a silently-lowered effort is a silently different agent.

`outputSpeed` is validated the same way, against a vocabulary the driver **publishes before the axis is offered** rather than one this spec names: `GetCapabilitiesResult.outputSpeedLevels`, present exactly where the `output_speed` flag is `true` and reaching clients on the same capability read the flag itself travels on ([Spec-004 §Provider Parameter Vocabularies](004-provider-driver-contract-and-capabilities.md#provider-parameter-vocabularies)). Publishing it is not optional politeness — a mutation validated against an unpublished set is a control whose accepted values no caller can discover, so the composer would have to guess and the daemon would have to refuse the guesses. Where the vocabulary is absent or empty the axis is **unsettable** and the mutation refuses `agent.provider_axis_invalid` fail-closed, which is the same answer an unrecognized value gets: an unsettable axis and an invalid value are both "this value will not be applied", and splitting them would tell a caller which providers are mid-rollout. An accepted value lands, at application, in the agent row's own provider-axis column beside the account and the effort ([§State And Data Implications](#state-and-data-implications)) — `NULL` until a switch sets one, which is what "an agent is not born with a speed mode" looks like as a starting state rather than as a member fixed when the run started. That column is the **requested** mode and is what the agent read model returns for the axis; what the provider then **declared** is a separate, live-scoped observation served beside it from the live binding and stored nowhere ([Spec-004 §The output-speed axis](004-provider-driver-contract-and-capabilities.md#the-output-speed-axis)). Keeping them as two members rather than folding the observation into the column is what lets a caller see a mode that was accepted here and refused by the provider's own account gate — a single value would have to choose which of the two facts to lose. It is a column and not a key in the opaque `config` blob for the reason the paragraph above gives for `effort`, and for one more: the application transaction commits the effective binding into those columns in the same act as clearing the pending slot, so an axis with a durable pending home and no durable effective one would apply once and silently revert at the next restart.

### Application timing, and why the boundary depends on the axis

A switch applies **at the next boundary the target axis permits**, and the two boundaries are not interchangeable.

An axis the target driver accepts as a **per-turn override** applies at the next **turn boundary**: the running provider process carries the change into its next turn, nothing is respawned, and no transcript is replayed. Codex accepts per-turn `model` and `effort` overrides on `turn/start` ([Spec-004 §Provider Parameter Vocabularies](004-provider-driver-contract-and-capabilities.md#provider-parameter-vocabularies)).

**`modelId` is a turn-boundary axis on the Claude leg too: that provider does not bind the model at spawn.** A long-lived Claude Code session changes model **in process**. Measured on Claude Code 2.1.275 (2026-09-17) over a persistent streaming session: the provider's own `/model <name>` command answers `Set model to <name> for this session only`, costs no model turn and no money, and emits a fresh session-initialization frame whose model is the new one; the next ordinary turn in that same session runs on the new model, and the session's own context report reads it back. The daemon therefore **MUST NOT respawn a provider process for a model change** — a respawn would throw away a live conversation, and force a transcript replay and its declared losses, to buy a change the running process already accepts. A model-only switch on this leg settles `in_place` with an empty declared-loss list, exactly as a model-only switch on the other leg does.

An axis that is **spawn-bound** applies at the next **run boundary**, because realizing it requires a new provider process. `driverName` is spawn-bound on every driver — a different vendor is a different binary. `effort` is spawn-bound on a driver that binds it at spawn instead of per turn (same Spec-004 section). `modelId` is in this group on neither driver, per the paragraph above. `outputSpeed` is spawn-bound on the one driver that declares the `output_speed` flag at all: [Spec-004 §The output-speed axis](004-provider-driver-contract-and-capabilities.md#the-output-speed-axis) binds the axis to that provider's **spawn-time settings opt-in** — the mechanism whose effect was measured — rather than to the interactive command the same provider also publishes, whose programmatic effect was not, so this axis resolves to a **`run`** boundary. Its settlement is then the ordinary spawn-bound one and needs no vocabulary of its own: the fresh process reopens the provider's own conversation, so the switch settles `resumed`, or `replayed` where that reopen did not load, and never `in_place` — moving a settings flag rather than the model makes the reconstitution no smaller, because the same conversation still has to arrive. It is stated rather than left to the reader because it is the minority case on this mutation, and a probe confirming the command's effect would re-home it to a turn boundary by ordinary amendment on the same read-the-vocabulary rule. Which group an axis falls in is therefore **read from the target driver's declared vocabulary, never assumed**: the same `effort` mutation is a turn-boundary change on one provider and a run-boundary change on another, and a daemon that guessed would either respawn needlessly or promise an immediacy the provider will not honor. The model axis is the worked example of the cost of guessing: read from the vocabulary it is a turn-boundary change on both legs, and a daemon that assumed otherwise would respawn a process, replay a transcript, and declare losses for a change no provider required any of that for.

A turn already in flight completes on the binding that started it in either case — interrupting it would abandon work the user is watching and would truncate the very transcript a spawn-bound switch then has to replay.

Mutation and application are therefore **two moments**. The mutation's own response acknowledges a **pending** switch and names the boundary it will apply at; `agent.provider_switched` is emitted at **application**, and it is what carries the settlement and the declared losses. This is the shape §Session Goals already uses for turn-boundary-effective delivery — the committed event records the mutation without claiming a mid-turn swap — and it is the only shape available here, since a spawn-bound switch cannot know what replay dropped until the replay happens.

**A pending switch is durable, and it is singular.** An acknowledgment that survives only in daemon memory is a promise a restart silently breaks: the caller has been told the switch will happen, the boundary arrives, and nothing does. So the pending intent is written **before** the acknowledgment returns and lives on the agent record itself ([§State And Data Implications](#state-and-data-implications)) — a daemon-minted `switchId`, the boundary it resolved, and the axes it moves. It rides `agent.config_updated` on that event's own `pendingSwitch` member, with the provider axes travelling **inside** it rather than beside it, so the append that records an intent can never be read as the binding having moved ([Spec-005 §Channel and Agent Lifecycle](005-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle)); the pending state therefore rebuilds from the log alone rather than from a side store, and daemon startup **re-arms** it: a restart resumes waiting for the boundary rather than dropping the intent. What it does not do is re-validate optimistically — the application-time re-validation below runs on the re-armed path exactly as on the live one.

Exactly **one** switch is pending per agent, and that singularity is the ordering rule rather than a queue: a second provider-axis update while one is pending **supersedes** it, last writer wins, and the superseded intent never reaches a terminal event. Queuing would be worse in the way that matters — a user who changes their mind twice would watch their first choice apply, run a turn, and then be replaced by their second. The superseding acknowledgment names the id it displaced, so the caller is told a supersession happened rather than left to infer it from an event that never arrives. Because the intent lives in a single slot on the agent row, the exclusion is structural: two concurrent mutations serialize on the same row under the daemon's session-mutation path, and the loser is a supersession, never a lost write. Supersession binds the **application** as well, not only the mutation. A superseded switch may still be in flight — its boundary hook armed, its interrupt dispatched, its target session perhaps already spawned — so every application step is guarded by a compare-and-set on `switchId`: the applying coordinator re-reads the pending slot **inside the same transaction that commits the binding**, proceeds only if the slot still holds its own id, and otherwise abandons the application entirely, emitting **no** terminal and clearing **no** slot. That is exactly what the rule above already promises — a superseded intent never reaches a terminal event — and it is what stops a stale application from erasing the switch that displaced it. Without the guard the last writer would win the mutation and then lose the application: switch B lands in the slot, switch A's boundary arrives, and A writes its own binding and clears B's promise.

The immediate arm is `interruptAndSwitch: true`, and the run-boundary group is why it exists: without it a spawn-bound switch waits for the run to end on its own, which across a long run is indistinguishable from being ignored. It **dispatches the existing `interrupt` intervention** and then applies at the boundary that interrupt creates — collapsing the two moments into one, the only case in which the mutation response can carry the settlement itself rather than a pending acknowledgment — and the only arm that holds its request open across the boundary in order to do so. Collapsing them does not skip the durability step: the pending intent is written before the interrupt is dispatched here exactly as on the deferred arm, and cleared when the settlement commits. **What the durable record must additionally carry is that an interrupt is owed at all**, and how far it got — the boundary alone cannot say, since a deferred switch and an interrupted one can both resolve to `turn_boundary`. So the slot records `interruptRequested` beside the boundary and, on this arm, an interrupt-dispatch progress marker advanced from `requested` to `dispatched` by its **own** durable write once the intervention is accepted. Recovery reads exactly that: a re-armed switch marked `requested` **redispatches** the interrupt, and one marked `dispatched` reconciles against the run rather than interrupting it a second time. Without the marker a restart would re-arm an immediate switch as though it were a deferred one and wait for a boundary nothing is going to produce — the crash would not cost the caller their answer, it would cost them the switch. A crash in between therefore costs the caller their answer and nothing else — the intent is re-armed at startup, the owed interrupt is redispatched, and the switch still applies — because an arm that waits for its own settlement is precisely the arm where losing the answer must not also lose the switch; the price of a crash between the two durable writes is one idempotent redispatch. That window is short but real, and keeping it real is what keeps the append honest: a client watching the session observes the same `agent.config_updated`-then-terminal pair on both arms, so the projection rebuilt from the log alone never has to know which arm produced it. It is an entry point into a control the corpus already has, not a new run control, so [Spec-003](003-queue-steer-pause-resume.md)'s V1 control set stays closed — the 2026-08-18 edit-affordance precedent, where the renderer's edit action dispatches the existing `rollback` intervention. Two consequences follow from that reuse and are deliberate: the interrupt is authorized as `Action::"intervene"` on the target run, and it settles through the ordinary intervention path, so a refused interrupt refuses the switch rather than leaving the agent half-moved.

Because that arm holds its request open until the switch settles, its response must express **every** settlement the boundary can reach, not only the good one. The mutation's response is therefore a four-arm discriminated union ([api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md)): `pending` on the deferred arm, and `applied`, `degraded`, or `failed` on the immediate one. `degraded` is not a judgment a client makes — it is a **total mapping** from the settlement's own continuity: `applied` exactly when the conversation arrived whole (`in_place` or `resumed`) and `degraded` exactly when it did not (`brief` or `replayed`), so the honest-degrade rule §Continuity states and [Spec-005](005-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle) restates for the terminal event is carried by the wire's own discriminator rather than re-derived by every renderer. `failed` carries the same closed `reason` vocabulary as `agent.provider_switch_failed` — one vocabulary across both surfaces — and is a **result rather than an error**, because the switch was accepted, the `switchId` was minted, and `agent.config_updated` was already appended: the mutation succeeded and only the application did not. A refusal reached **before** acceptance is the synchronous `agent.provider_axis_invalid` error instead, and mints no id and appends no event. A failing immediate arm still emits the terminal: the pending slot is cleared by a terminal and never by a reply, so an arm that answered its caller and appended nothing would leave a promise no replay could clear.

### Continuity, and what is declared rather than dropped

Continuity depends on whether the new process belongs to the same provider, and the two cases use different mechanisms because the providers make different things possible.

**Same provider, new process.** A spawn-bound axis that is not the provider itself — `outputSpeed`, or `effort` on a driver that binds it at spawn — reaches a fresh process of the same provider, in the same credential home, over the same conversation. That provider **reopens its own conversation** by its own identifier, so nothing of the conversation is re-sent as text and nothing is lost. Canonical-transcript replay ([Spec-004 §Canonical Transcript Export And Replay](004-provider-driver-contract-and-capabilities.md#canonical-transcript-export-and-replay)) is the **fallback** where that reopen does not load, and it is reported as the conversation having been restarted rather than continued.

**A different provider: a hand-over brief.** No vendor's resume verb accepts another vendor's conversation, which is the case [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md) was triggered by. The new provider is therefore started from a **hand-over brief**, and replaying the whole conversation as text is deliberately **not** what a provider switch does: it is the most expensive thing to send and not the thing that helps most. The brief is built on a **throwaway copy of the old session, never the live one**, so nothing about producing it disturbs the conversation the person is watching. Where the old provider has its own summarizing command the daemon runs it on that copy and reads the summary; where the old provider's own summary is not readable the copy answers a fixed template instead.

The first message the new provider receives is that brief, and then, in this order:

- the **current diffs and the branch**, read from disk at that moment rather than taken from anything remembered;
- **every earlier step as a one-line note** — what the step was and how it ended, such as a command and that it failed with two failing tests — with the output bodies left out;
- the **last exchanges word for word**. How many travel verbatim is one tuning number and the only one in this mechanism; it is bounded as a share of the new model's context window rather than as an absolute count, and its interim setting is the last **two** exchanges, measured rather than asserted ([Spec-004 §The hand-over brief is the floor, and it is visibly a floor](004-provider-driver-contract-and-capabilities.md#the-hand-over-brief-is-the-floor-and-it-is-visibly-a-floor));
- and a **reference to the whole old transcript**, which the daemon writes as one plain file beside the brief. Nothing of it is pushed into the message: the new provider opens and reads whatever part of it it wants, on demand, with its own file tools. This is what makes leaving the conversation out of the message affordable — the expensive thing is not sent, and it is still reachable. That file lives in the daemon's own storage for that session, outside the working folder and outside either provider's own home, is named in the brief by its absolute path, and is kept as long as the session is and removed with it. Nothing about the file is a line on screen: the transcript's two rows are the brief and the switch, and the file is not a third.

**What never travels, on any switch:** the model's private reasoning, which both vendors make unusable outside their own product; tool calls as live calls, which arrive as history and never as work in flight; the old provider's own skill and command names, which name nothing on the new provider; and the old provider's own system prompt, its environment preamble and the instruction files it loaded, which that provider's own summary step reproduces among the person's messages and which the daemon strips out of the brief before it travels. Nothing is written into the other vendor's own directories at any point.

**Switching back reopens the old provider's own conversation.** A session that moves from one provider to another and back does not start a third conversation: the daemon reopens the first provider's own session by the identifier it kept, and hands it a brief of what happened while it was away, composed the same way. That is what makes a switch a move rather than a fork.

Three consequences are stated rather than discovered:

- **Every switch MUST be assumed to lose the provider-side prompt cache.** No vendor publishes a cache-scoping contract this corpus can hold them to, so the rule is stated in the safe direction rather than in the precise one: the daemon assumes the miss, prices the switch as if the miss occurs, and tells the user so. Being wrong in this direction over-warns and over-reserves; being wrong in the other direction bills a user for a cost the affordance told them they would not pay. No axis is exempt — an effort-only change on an otherwise-identical binding is assumed to miss like any other, because the assumption costs an unneeded warning and the exemption would cost real money. A vendor that publishes a scoping contract at Verified grade re-opens this by ordinary amendment; until one does, the conservative rule stands.
- **What did not carry is declared at application, and the person reads it.** The declared-loss list rides the `agent.provider_switched` event, and an **empty list is a positive assertion that nothing was dropped** — a driver that does not know what it lost may not emit one. A turn-boundary switch moves nothing and so drops nothing: its list is empty by construction, and that emptiness is the same positive assertion, not an absence of information. A same-provider reopen likewise drops nothing. A provider switch always drops something, and the transcript says how much: two faint single lines at the point the run ended, collapsed until pressed — `Hand-over brief · Claude Code` and, under it, `Switched to Codex · continued from a brief · 3 things did not carry over`, the second expanding to the named list. What composing the brief cost is counted where every other figure for the account that wrote it is counted (§Session Cost Receipt) and is never a line of its own on either row.
- **A switch whose conversation did not arrive whole settles `degraded`, never `applied`.** A provider switch is always in that class, because a brief is not the conversation, and so is a same-provider reopen that fell back to replaying the transcript as text. The switch still happens; the user is told what the new process can see. A turn-boundary switch has nothing to reconstitute and settles `applied`, and so does a reopen that loaded.

  The settlement therefore names **which mechanism carried the conversation**, because they are four different acts and not degrees of one. `in_place` is the running process carrying a per-turn override into its next turn: nothing was respawned, nothing was reconstituted, and its declared-loss list is empty **by rule**, not by luck. `resumed` is a fresh process of the same provider reopening its own conversation by its own identifier: the conversation arrived whole, so this list is empty by rule too. `brief` is a different provider started from a hand-over brief, and its list is **required non-empty** and must name the summarization itself, since a brief settlement whose list said nothing would be claiming that a summary costs nothing. `replayed` is the fallback: a same-provider reopen did not load, and the canonical transcript was sent as text instead, which restarts the conversation rather than continuing it — its list is required non-empty for the same reason. `in_place` and `resumed` are `applied`; `brief` and `replayed` are `degraded`. Collapsing any pair would force one of the lies the wire must not tell: that a reopen was a summary, that a summary was a reopen, or that an empty loss list has stopped meaning "nothing was dropped".

### Refusals are fail-closed and precede any spend

A switch is refused, before any turn is started on the target, when the named driver is not registered on the hosting node, when the named model is not in the target driver's `listModels`, or when the named effort is not in that model's `effortLevels`. Because application may be deferred to a later boundary, that validation runs **twice** — at mutation, so the caller learns immediately rather than at a boundary it is not watching, and again at application, so an axis de-registered in the interval refuses the application and leaves the agent on its current binding rather than realizing a configuration the node can no longer honor. The account arm defers to [Spec-026](026-provider-accounts-and-credential-homes.md)'s registry and its fail-closed spawn gate ([Plan-026](../plans/026-provider-accounts-and-credential-homes.md) I-026-3) as the authority — the readiness projection on the account read is advisory and is not consulted as a gate here — and the registry being node-local is what bounds this surface: a caller can only name an account the operator already registered on that node.

**A refusal at application is an event, because no caller is there to receive an error.** The mutation-time arm answers the caller synchronously with `agent.provider_axis_invalid`, and that is the whole story only when the two moments coincide. Where application is deferred, the caller has already been acknowledged and disconnected, so a re-validation failure that produced only a log line would leave a pending switch that resolves into silence — the user waits at a boundary that has already passed. Every deferred switch therefore reaches **exactly one terminal event**: `agent.provider_switched` on the arm that applied, or `agent.provider_switch_failed` ([Spec-005 §Channel and Agent Lifecycle](005-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle)) on the arm that did not, both carrying the `switchId` the acknowledgment named. The failure event carries a closed reason — which axis went unhonourable, or that the target could not be started at all — clears the pending intent, and leaves the agent on its current binding, which is the same fail-closed outcome the paragraph above requires and is now the outcome a client can render. A refused `interrupt` on the immediate arm settles the same way: the switch is abandoned with a reason rather than left half-moved. The single exception is supersession — a pending switch replaced by a later one emits no terminal of its own, and the superseding acknowledgment names it instead, because two terminals for what the user experienced as one change of mind would be a worse record than none.

A degraded settlement is **not** a failure and never takes this path: a provider switch settles `agent.provider_switched` with `continuity: 'brief'`, and a reopen that did not load settles it with `continuity: 'replayed'`, each with a non-empty loss list. The distinction is exactly whether the agent moved. A degraded settlement moved it and told the truth about what came along; a failed application did not move it at all.

Authorization does not move with the axis. The mutation authorizes exactly as every other `AgentConfigUpdate` member already does — as the session's user under [Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior) — and the immediate arm's interrupt authorizes as `Action::"intervene"` on the target run, an action that spec's named-operation-action enumeration already carries. No third authorization is minted and none is owed: naming a driver or a model confers no spend authority the caller did not already hold, because causing execution on the hosting node is bounded by the unchanged node-trust rule, and the drivers a caller can name are exactly the ones registered on that node. Choosing among them is a configuration choice inside a boundary already authorized, not a new grant — which is why [Spec-010](010-approvals-permissions-and-trust-boundaries.md)'s named-operation-action enumeration does not grow here. Which **account** pays is authorized on its own plane, where its control lives ([Spec-026 §Authorization Posture](026-provider-accounts-and-credential-homes.md#authorization-posture)).

### Identity, attribution, and what does not move

The agent keeps its `agentId`, its name, its channel membership, its run linkage, and its place in every projection built on those. A switch is a change of execution binding.

§Session Cost Receipt therefore keeps both partition axes **unchanged in shape**. The per-run axis keys on runs, which are already per-binding. The per-paying-account axis already keys on each run's `admittedProviderAccountId`, and **one run carrying one account for its whole life** is what keeps that key exact — the account move ends the run at the next tool boundary and continues the work in a new run, rather than moving the account under a run that is already stamped ([Spec-026 §Moving a session to another account](026-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)) — so a session whose provider's current account moved mid-way yields two `byAccount` rows summing to the same session total: the axis reporting a real split, not a new arithmetic. Both partition identities in §Session Cost Receipt hold across a switch for exactly that reason, and this section adds no key, no fold, and no repricing.

## Provider-Native Subagents

- **Single-supervisor invariant (campaign B6): the daemon is the only cross-session supervisor.** A run MAY use its provider's in-session subagents (Claude `--agents` / Task tool; Codex `multi_agent` / `[agents]`) under the `subagentPolicy` the daemon passes through — the policy shape (`{enabled, maxDepth?, maxConcurrent?, definitions[]}` — both limit members carrying the person's own provider setting where they have set one, the daemon setting none of its own and clamping nothing) is owned by [Spec-004](004-provider-driver-contract-and-capabilities.md) and its API Payload Contracts mirror.
- Budget roll-up: subagent usage aggregates into the run's own budgets — the §Budget Policies accountant sees it through the run's `usage` events, so subagents provide no budget escape hatch. Derived pricing resolves **per usage row**: a row wire-attributed to a model outside the run's admitted family keys off THAT model's family — the attribution rides the durable [Spec-005](005-session-event-taxonomy-and-audit-log.md) B6 usage-row fields `modelId?` / `modelFamily?` / `subagentId?`, populated by the driver normalizer from wire attribution (per-model usage maps; subagent-scoped usage pairing on the subagent triple; the normalizer duty lands with the campaign's Plan-004 bundle's normalizer tasks) — falling back to `admittedModelFamily` when the wire carries no attribution. A differently-modeled subagent is thus never priced under its parent's rates when the wire attributes it; and because the spawn screen above already requires every subagent-definition family to be priced or native-cap-covered at admission, an attribution-less row can at worst mis-allocate between two PRICED families' rates — it can never miss an unpriced-family block. And the admission-preemption rule above extends to spawn: `subagentPolicy.definitions[]` models resolve against the pricing table at spawn, and a definition naming an unpriced-family model on a capless leg is refused fail-closed (same `driver_capless` vocabulary) unless a native-cap reservation covers the run — coverage is **per-family across the run's whole model set** (parent + every subagent definition): each unpriced family needs its own `unpricedFamilyCaps` entry, and since the provider hard stop is run-wide, the single stamped `admittedUnpricedCapCents` is the **minimum** of those entries (run-wide spend ≤ every family's owner bound — deterministic and safe; an unpriced family with no entry refuses per the spawn screen) ([Spec-005 §Tool Activity](005-session-event-taxonomy-and-audit-log.md#tool-activity-tool_activity) records the same aggregation rule on `subagent.completed`, campaign B1).
- Approval flow-through: subagent tool calls flow through the same approval pipeline as the parent run's (Plan-010); a subagent introduces no separate trust surface.
- Timeline normalization: subagent lifecycle lands as the registered `tool_activity` rows `subagent.started` / `subagent.completed` (campaign B1), provider-attributed and pairing on the (`runId`, `provider`, `subagentId`) triple.
- In-session subagents execute beneath a single run and are not canonical child runs; cross-run delegation is governed by §Default Behavior, which sets no depth limit of its own either.
- **The runtime adds no depth cap to the in-session tree.** An agent dispatched inside a run may dispatch agents of its own, and those may dispatch again; how deep that tree may go is the provider's own limit under the person's own provider settings — the daemon sets no depth of its own, passes the person's value through on `subagentPolicy.maxDepth`, and clamps nothing — and where the provider refuses a level, its refusal is shown in its own words. Cross-run delegation carries no depth limit of the runtime's either (§Default Behavior), so this is not an exception to it. Every rule in this section — budget roll-up, approval flow-through, timeline normalization — binds at every level of that tree, not only the first, so spend and approvals reach the run through however many levels stand between.
- **The daemon owns the tree, and every count over it.** The tree a client draws is the daemon's own parent-to-child index for the session (§Interfaces And Contracts), never an arrangement a client infers from the rows it happens to hold. A fan-out count — the agents one dispatch made, how many more their own dispatches made, how many are live — is supplied by the daemon for the same reason: a client may hold only part of the tree, and a count folded from a partial list would understate the work. One list holds every agent the session produced, an in-session subagent and a peer-invoked child run alike, each under whatever dispatched it; the two kinds differ in what they are (§Interfaces And Contracts, the link types) and not in whether they are visible.
- **A dispatched agent is visible in exactly three places, all fed from that one source:** a row in the transcript where its dispatch happened, a row in the session's agent list, and its own view. The dispatch's own row in the transcript counts what it made and, while the dispatching agent is waiting on them, carries that wait as live state beside the count and drops those words in place when the wait ends — one place for the wait, never a second group and never a separate waiting row.
- **What a row states.** Every agent row names the model it runs on and its reasoning effort as one word, whether the dispatch chose them or it inherited them from the session, so a row never goes quiet about what it is running on; where the agent was reached by a peer invocation the row additionally names which agent was asked. Each row carries, under the name, the tools it has used, its tokens, its spend and its duration — figures that read live while it runs and settle in place when it finishes, and that are never dropped to save room. An activity line says what the agent is doing and **stays** when it finishes, with its result beneath it: the last thing it was doing still stands above what it came back with. The list is one tree in the order the work happened; a finished agent keeps its place under whatever dispatched it and can be collapsed away as a set, never re-ordered.
- **An agent's name, icon, and colour are resolved for display from the definition it was made from** — through the definition reference its agent record carries — and fall back to the agent's own name where that definition is gone. This is presentation only: the rule that a run keeps the configuration it was resolved for ([Spec-027 §Resolution when a run starts](./027-agent-definitions-and-peer-invocation.md#resolution-when-a-run-starts)) governs configuration and authority, not the label, so renaming a definition retitles a running agent mid-session while editing its tools changes nothing it may do.
- **What no row states.** No row, head, or note says how an agent was made, or by what mechanism a control reaches it — the provider's spawn machinery is an implementation fact and never surfaces. No dependency graph is drawn over the tree.
- **An agent's own view is the session's own rendering at one level down** — its working line, its grouped tool runs, its diffs, its command output, its reasoning, its prose, an approval inline, and a steer box — and it keeps its own scroll position and its own folded runs, per agent, so reading one never moves another or the session behind it. Its head carries the one-line ask it was dispatched with and the whole ancestry back to the session, each ancestor reachable from it. Its rows are fetched on demand, once: any agent in the tree opens, including one whose rows were never in the window a client holds. A finished agent's view is read from the record the daemon stored when it finished and opens at the beginning of that record; where the stored record cannot be read the view follows the agent's own live document instead, so a finished agent always opens. A view with no rows says **which** fact that is — nothing produced yet, or rows still being fetched — and never draws an empty body for either.
- **An agent with agents under it can be folded**, and folding replaces their rows with one line carrying how many are under it, counting their own, and what the live one is doing (`3 sidekicks · docs-sweep editing … · 1 more running`, `2 sidekicks · done`). An agent with nothing under it offers no fold. Nothing folds itself, and a fold outlives a redraw.
- **Every failure is named on the agent that had it, and never swallowed.** An agent that failed says so on its result line with the reason after it, and that is the only mark a row takes — one that finished carries no mark at all. A record that cannot be read says so in one line where the rows would be, naming the cause, and never draws a partial transcript in its place. An agent whose dispatcher is missing from the record says so and draws at the root of the tree rather than under a guess.
- **An agent's own limit is read from the agent, never from the lead.** A provider turn limit settles the agent with its partial result, and a send into its steer box continues it with its context. A provider error may kill an agent while the run that dispatched it reports success, so the reason is read from the agent's own update — a lead's success is not evidence that the agent it dispatched succeeded.
- **A capability the provider refuses is learned from the refusal and remembered for that agent** — never read from an experimental opt-in surface, and never assumed from the provider's documentation.
- **The provider's own subagent view stays switched off.** The tree, the rows, and each agent's view are built from the messages the daemon already routes, so one rendering serves both providers and neither provider's own presentation competes with it.
- The CLIs' own out-of-session supervisors (`claude agents` / `claude daemon`, `--bg` / `/background`, Codex cloud) stay disabled inside daemon-managed runs. This is the parity implementation of "background agents" — the daemon's orchestration layer IS the manager — not a capability rejection. Enforcement is layered: the daemon owns spawn argv and configuration and never enables those surfaces; the command-policy provider-supervisor deny applies for every effective posture ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior), campaign B20); and the Bash-sandbox/permission layer is the residual control against model-initiated supervisor spawns. The invariant is scoped to daemon-configured supervision.
- Concurrency: `maxConcurrent` is Codex's own `agents.max_concurrent_threads_per_session` setting. It is optional, it carries the person's own Codex value where they set one, and it is passed through on the Codex leg alone. Claude Code has no such setting, so the Claude leg sends nothing for it and the daemon holds nothing back: no subagent is serialized, queued or delayed at the daemon's boundary, and how many subagents run at once on that leg is whatever the provider does. Where a provider refuses a spawn under a concurrency limit of its own, its refusal is shown in the provider's words. A subagent's usage debits the supervising run's budgets however many ran alongside it (no escape hatch).

## Scheduler Limits

The runtime adds no count limit of its own: not on how many channels a session runs at once, not on how many orchestration runs may be pending, not on how many children a run may have, and not on how many items a channel or a session may queue. How many agents a provider will run at once, and how deep they may nest, is that provider's own limit under the person's own provider settings; where a provider refuses, its refusal is shown in its own words. What a session may spend is its budget, which the person sets (§Budget Policies).

Admission still refuses on the budgets and the turn policy the person set, and on the state of what a run targets — the session's cost ceiling, an agent's consecutive-turn limit, a target node that is not local, an archived channel, an agent that is not ready. Every such refusal is enforced at create-time admission with zero residue (no run row, no queue item survives a refusal), is a typed error carrying its own detail, and is recorded durably by the daemon via `orchestration.rejected` ([Spec-005 §Channel Arbitration](005-session-event-taxonomy-and-audit-log.md#channel-arbitration-channel_arbitration)). The budget limits live in the session budget surface and are owner-adjustable (D-014-5).

## Partition And Reconnect Behavior

Multi-agent sessions span multiple runtime nodes; partition behavior inherits from [Spec-002](../specs/002-runtime-node-attach.md) and [Spec-013](../specs/013-persistence-recovery-and-replay.md). Spec-014 adds only the turn-arbitration and channel-visibility rules specific to multi-agent semantics.

- When a node loses its relay connection, the control plane marks it `offline` per Spec-002. The node's session attachment is preserved and it may reconnect under the same node identity.
- Child runs on the offline node continue locally if the node can still reach its provider; events buffer against the node's local audit log ([Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)) until relay catch-up via Spec-013 replay.
- Parent-channel views on connected nodes show the offline node's runs in an `unreachable` state with the last-known state preserved from the event cursor. `unreachable` is a visibility outcome, not a run-state transition — it is distinct from the run-level `paused` state defined in Spec-003.
- Turn-policy arbitration degrades by policy:
  - `free-form`: unaffected; addressed turns for the remaining reachable agents continue to admit in arrival order (activation stays addressing-gated per §Turn Policies — partition changes ordering availability, never the activation rule).
  - `round-robin`: if the next agent is on an unreachable node, arbitration pauses the channel and emits an `arbitration.paused` event (with `arbitration.resumed` on reconnect). Arbitration must not silently skip the unreachable agent (which would let a disconnected agent miss its turn without record) and must not auto-fail-over to free-form without explicit operator action. `arbitration.paused` and `arbitration.resumed` are registered in the [Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md) canonical event taxonomy under the `channel_arbitration` category (BL-084, completed 2026-04-18).
  - `request-based`: unaffected on the sender side; responders on unreachable nodes do not consume their turn, and the addressing act is not delivered — it is refused on the sender side with the node named, never left pending against a clock.
- On reconnect, buffered events catch up via Spec-013 replay and any arbitration pause resolves automatically once the canonical ordering is restored.
- Runs that cannot be resumed because provider-session state was lost transition to `failed` per Spec-013; they must not reappear as a new run.
- The control plane does not enforce cross-node consensus on turn arbitration. Local daemons own their attached runs; cross-node ordering is eventually consistent through the event log. A round-robin channel with two agents on two partitioned node-halves may briefly see divergent local views; Spec-013 replay reconciles on reconnect. Availability over consistency (AP) is the explicit trade-off for the orchestration surface.

## Implementation Notes

- Keep orchestration semantics provider-agnostic and session-scoped.
- Channel creation should be lightweight, but channel identity must remain durable enough for audit and replay.
- Internal helper runs should be discoverable without overwhelming the default UI.

## Pitfalls To Avoid

- Treating multi-agent orchestration as only a UI grouping trick
- Hiding child-run provenance
- Assuming provider-native spawn semantics are universal

## Acceptance Criteria

- [ ] A session can host multiple concurrent agents and channels.
- [ ] Parent-child run relationships remain visible after replay and reconnect.
- [ ] Delegated work remains possible even on drivers without native subagent APIs.
- [ ] Every surfaced cost figure equals the committed-spend fold the accountant enforces against, and carries its provenance from the wire.

- [ ] An agent whose provider, model, or effort is changed keeps its `agentId`, its channel membership, and its run linkage, and the conversation continues rather than restarting; so does an agent whose provider's current account moved under it.
- [ ] A switch requested without `interruptAndSwitch` leaves an in-flight turn to complete on its original binding and takes effect at the next boundary its target axes permit — a **run** boundary whenever `driverName` moves, a **turn** boundary only where every moved axis is a per-turn override on the target driver, and the widest of the two on a multi-axis update; the immediate arm dispatches the existing `interrupt` intervention and mints no new run control. The mutation carries no account member at all, and a caller that supplies one is refused rather than served.
- [ ] A switch naming an unregistered driver, a model absent from the target driver's `listModels`, or an effort absent from that model's `effortLevels` is refused before any turn is started on the target.
- [ ] A provider switch settles `degraded` with `continuity: 'brief'` and a non-empty declared-loss list, never `applied`: the brief is built on a throwaway copy with the live session untouched, the first message to the new provider carries the brief then the current diffs and branch then every earlier step as a one-line note then the last exchanges verbatim then a reference to the whole old transcript, which exists as one plain readable file beside the brief whose contents are in no part of the message, no private reasoning and no live tool call and no old-provider skill or command name is in it, and the transcript carries **exactly** the two rows naming the brief and the switch with a count of what did not carry over — the transcript file gets no row of its own. A same-provider spawn-bound switch settles `applied` with `continuity: 'resumed'` and an empty list where the provider reopened its own conversation, and `degraded` with `continuity: 'replayed'` where it did not.
- [ ] After the provider's current account moves under a live session, the session cost receipt's `byAccount` rows still sum to the session total, and no run is stamped with two accounts.
- [ ] Switching a session to another provider and back reopens the first provider's own conversation by the identifier it kept, with a brief of what happened while it was away, rather than starting a third conversation.
- [ ] An `outputSpeed` mutation is acknowledged `pending` naming a **`run`** boundary and applies at the next run rather than the next turn; the same mutation against a driver declaring `output_speed: false` refuses before anything is spent and is never satisfied by changing `effort` instead.

- [ ] A Claude Code session and a Codex session each reach the other through `SendToSession`, in both directions, and each exchange draws one row in the sending transcript and one in the receiving one; the receiving row sits where the message was folded into that turn rather than at the turn's end, and a session that was busy when the message arrived shows it inside the turn that was running.
- [ ] `ListSessions` names sessions on **both** providers, including one the sending provider's own listing cannot see, each with whether it is working or idle.
- [ ] A Claude Code session's own `SendMessage` aimed at another session is denied by the daemon's hook, the model reads `send with SendToSession`, and the same tool aimed at one of that session's own agents still works.
- [ ] A message the receiving provider dropped silently reads `not delivered` once that session goes idle and never reads `delivered`; a message a paused session was addressed with reads `queued, builder is paused`, waits, and is delivered on the continue in arrival order.
- [ ] Interrupting either session of a live exchange ends both turns, empties the queue between them, and lands one row in each transcript naming how many messages were not delivered.
- [ ] No message table, message row or message event type exists: the only durable record of an exchange is the two sessions' ordinary tool events, while the exchange table and the paused queue survive a daemon restart and the restarted daemon delivers what it was holding.
- [ ] A Claude Code session the person started in their own terminal reaches a hosted session by that session's address, with no plugin installed, and the arrival draws the same row a tool send draws.
- [ ] With no step bound set, two sessions trade a long exchange to its own end: no count, cap, throttle or refusal of this runtime's ends it, and the only limits that fire are the receiving provider's own, reported in that provider's own words. With a bound set, the turn ends at the number and `Continue` — or the next arriving message — carries the same turn on rather than starting a run.

## Resolved Questions and V1 Scope Decisions

- No blocking open questions remain for v1.
- V1 decision: channel-level permission restrictions are deferred. A new channel is visible across its session and carries the session's visibility policy in the first implementation.
- V1 decision: **inside one session** channels are the only canonical communication boundary between agents and runs, and no direct run-to-run messaging primitive is added between agents of the same session. **Between two sessions** the boundary is the one tool the daemon serves to both providers (§Sessions Talking To Each Other): a message there is an ordinary tool call on the sending side and an ordinary tool row on both, never a channel, and it carries none of a channel's turn policy, moderation or roster.
- V1 decision: the runtime adds no depth ceiling of its own to canonical delegation. A child run may create child runs of its own; how deep agents nest is the provider's own limit under the person's own provider settings, a provider's refusal is shown in its own words, and every budget, approval, and visibility rule binds at every level rather than at the first alone.
- V1 decision: concurrent child runs are allowed, and v1 imposes no numeric ceiling of its own on them. How many a provider will run at once is that provider's own limit under the person's own provider settings, and admission refuses only on the budgets and turn policy the person set and on the state of what a run targets (§Scheduler Limits).
- V1 decision (campaign B6, R8): realtime/voice channels are **reserved behind the R8 capability gate** — the upstream Codex realtime feature flag is still under development, a named external gate surfaced to the owner. The reservation binds to the gate, not to the provisional wire shape: per [ADR-015](../decisions/015-v1-feature-scope-definition.md)'s feature #23 note the `thread/realtime/*` shapes are present in the Codex app-server's **default** generated schema, and the gate that withholds them is **not** in that schema (corrected 2026-08-26; re-verified at the `0.150.1` pin 2026-08-28): measurement at both the floor and the pin shows the default and `--experimental` `ServerNotification` unions are **identical**, so nothing is gated off at the schema layer at all. The gate is `should_skip_notification_for_connection`, a **runtime** filter that silently drops every experimental notification — the eleven `thread/realtime/*` among them (eight at the 2026-08-26 measurement; the `0.150.1` pin hop added `thread/realtime/item/started`, `thread/realtime/item/completed`, and `thread/realtime/item/transcript/delta` beside them, likewise experimental-gated) — for any connection that did not set `initialize.capabilities.experimentalApi`, with no error and no deprecation notice ([Codex wire reference](../reference/provider-wire/codex.md)). Two consequences the old framing hid: the shapes cannot be feature-detected by generating the schema, and an activating driver must opt in at `initialize` before a single realtime notification will arrive. The re-verification obligation stands and is now specific — probe the runtime gate against the then-installed binary, never re-read the generated union. Spec-014 defines no channel media-type enumeration and none is invented for the reservation; no channel-model change lands until the upstream flag stabilizes. The paired event-census reservation (the reserved `realtime_*` family) is [Spec-005](005-session-event-taxonomy-and-audit-log.md)'s (campaign B1); the scope entry is V1 feature #23 per [ADR-015](../decisions/015-v1-feature-scope-definition.md).
- V1 decision (Part-B fail-closed follow-up, 2026-07-17): **auto-compaction is a named advisory safeguard — a tracked affordance, never a forced interrupt.** The context-window hard budget stays rejected (§Budget Policies: headroom is not a fourth budget), and the future orchestrator-run compaction lever is scoped now so it cannot later land as a stop: when a run's headroom climbs past a soft threshold the orchestrator MAY surface and pre-arm provider-native conversation compaction — that advisory surfacing is the soft, reversible response even `estimated`-grade headroom may drive under the §Budget Policies hard-vs-soft line, whose human-facing sibling is the V1-shipped composer-meter compaction hint (which stays purely informational — [Spec-011 §Context Window and Usage Meters](011-live-timeline-visibility-and-reasoning-surfaces.md#context-window-and-usage-meters); this entry scopes the future machine-facing counterpart) — while **invoking** compaction mutates the live provider conversation and is graded accordingly: invocation fires only on `provider_reported`-grade signal (both window counts present, or the `exceeded: true` terminal flag), never off an estimate — and its implementation binds three invariants. **Buffer-for-compaction**: the trigger MUST sit far enough below the window ceiling that the compaction call itself still has room to run — too-full-to-compact is a documented field deadlock ([anthropics/claude-code#25620](https://github.com/anthropics/claude-code/issues/25620), accessed 2026-07-12), and surveyed runtimes hold triggers near ~75-85% usage with an explicit reserve partly for this reason ([GitHub Copilot CLI context management](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/context-management) keeps a ~20% buffer and names its thresholds "automatic safeguards rather than hard stops", accessed 2026-07-12). **Recoverable originals**: the lever summarizes the provider conversation only, never the session record — the canonical event log ([Spec-005](005-session-event-taxonomy-and-audit-log.md)) keeps the full pre-compaction history under its own retention rules, so dropped detail stays re-derivable as a record; recoverability is an audit and re-derivation guarantee, deliberately not a live-conversation undo — neither provider wire exposes a compaction-restore operation, which is exactly why invocation rides the hard side of the provenance line above. **Capability-gated invocation**: daemon-invoked compaction exists only behind a capability-gated driver compaction operation, and the V1 provider-driver contract (`ProviderDriver`, `packages/contracts/src/provider-driver.ts`) deliberately ships none — so in V1 the daemon never invokes compaction: the shipped safeguard surface is buffer maintenance plus advisory surfacing, and provider-native auto-compaction runs under the provider's own authoritative accounting (the provider compacts on its own counts, never on our estimate); the invocation lever activates only when that driver operation lands. The surveyed 2026 provider surfaces ship compaction first-class (client-side auto-compact in the provider CLIs; server-side as the Messages API `compact_20260112` context edit — [Anthropic compaction](https://platform.claude.com/docs/en/build-with-claude/compaction), accessed 2026-07-12), so the lever composes with provider machinery rather than inventing summarization; which mechanism each driver leg binds is an implementation-plan concern, deliberately not fixed here.
- V1 decision (2026-08-11, D-014-22): **full channel-directory publication — every channel is published to the control-plane channel directory** (§Interfaces And Contracts). Ratified by the product owner over the alternative of no control-plane directory at all, which would strand the control plane's `ChannelList` on the synthesized `main` alone, so a device other than the one that created a channel could not list it. **The directory has one owner: Plan-014 builds all of it** — the daemon-side producer, the ingest mutation, the `session_channel_directory` store, and the `ChannelList` read path. A split owner was the earlier shape and is rejected here: the convergence fold is the whole correctness argument, and specifying the producer in one plan while another builds the ingest that folds its publications puts one contract across two build boundaries for no gain, since the daemon-to-control-plane call is an ordinary client call either way. Two legs ride the store beyond the wire contract (both §Interfaces And Contracts, PR #321 Codex rounds 1–2): the Spec-020 PII-map + erasure routing for the directory rows, which the ingest does not go live without, and the origin-authentication rule under which disclosure-bearing fields bind create-once from the channel's origin-authenticated creation publication and are immutable thereafter (healing publications are existence-and-ordering only). The disclosure boundary is stated in §Interfaces And Contracts: the control plane learns channel existence metadata, never content.
- V1 decision (2026-08-11, D-014-23): **Plan-014 owns the OWN-channel turn-budget provider and the workflow interrupt reason** — discharging [Plan-015](../plans/015-workflow-authoring-and-execution.md)'s A-015-07/A-015-14 upstream ruling that both live on this spec's surfaces and Plan-015 consumes them, authoring neither. `ChannelConfig.turnsPerAgent` is the per-channel override of the per-agent turn limit (§Interfaces And Contracts; the bare-channel comparator stays the session default, 50), and `workflow_phase_cancelled` is the fourth `InterruptReason` member (§Stop Conditions), the mechanism the SA-9 `REQUEST_CANCEL` / `TERMINATE` policies invoke. Neither adds a budget: the three-budget table is the closed set it was. A ruling folded into this decision (PR #321 Codex round 1): `ChannelConfig` — the override included — is **uniformly create-time-immutable in V1**; no post-create channel-config mutation exists on any member, so an overridden channel recovers from its limit by the interleaving-turn reset alone (available to every member with no mutation surface) while the owner-raise lever reaches only channels at the session default. The post-create override mutation — `channel.configUpdate` admitting `turnsPerAgent` set/raise/clear, with an events-canonical `channel.config_updated` companion so the channels projection stays replay-complete — is the named V1.1 seam, gated on a demand criterion: field evidence of overridden channels wedging where an interleaving turn is not a viable recovery (e.g. single-agent automation channels no human monitors). Widening V1 with it was considered and rejected: it would mint the first post-create config mutability on a surface that is otherwise uniformly create-time-fixed (an inconsistency inviting mid-flight arbiter-assumption drift) and mint an event type against a census three plans pin, for a recovery the interleave already provides.
- V1 decision (2026-08-17, D-014-24): **the displayed cost and the enforced cost are one fold** — every surfaced cost figure is supplied by the accountant that enforces, never recomputed beside it (§Cost Figure Display Consistency). Three alternatives were considered and rejected. A **display-side sum over the visible run list** is the surveyed failure mode itself — it renders whatever the list happens to show, which under any delegation is less than what the ledger holds. A **second fold maintained for presentation** drifts by construction: two accountants over the same events diverge the moment one gains a case the other lacks, and the divergence is invisible precisely because both look authoritative. **Labelling the total a lower bound** is correct for a row-counting fold and wrong for this one, which charges an unpriced run its full admitted cap, so the label would understate the spec's own conservatism and invite a compensating second estimate — and where the mid-run tier-(c) residue of §Cost Figure Display Consistency clause (c) is present the total is a bound in neither direction, which is why non-exactness surfaces through the aggregate `costStatus`, never through a bound label. No budget is added and no number changes: the decomposition members report the legs the fold was already rebuilt from, and the three-budget table stays the closed set it was.

## V1 Readiness Review (BL-042, 2026-04-17)

Review against the V1 quality bar declared by [ADR-015](../decisions/015-v1-feature-scope-definition.md) §Thesis. Findings:

- **Turn policy defaults** — `free-form` is the explicit default. Round-robin and request-based are documented alternatives with deterministic triggers. No "configurable without default" surfaces remain.
- **Budget policies** — Each of the three budgets exists only where the person sets one, and with none set nothing warns, interrupts or refuses. A budget the person did set is a hard ceiling enforced by intervention dispatch: soft warning at 80%, hard interrupt at 100%.
- **Stop conditions** — Four named conditions (turn limit, budget exhausted, explicit stop, idle timeout) with deterministic triggers. An idle timeout exists only where the person sets one. Conclusion detection deferred to V2.
- **Moderation / approval hooks** — Pre-turn (category `gate`) and post-turn (informational) hooks integrate with [Plan-010](../plans/010-approvals-permissions-and-trust-boundaries.md) approval categories. Opt-in per channel is the V1 default.
- **Turn arbitration under partition** — Named partition behavior added: `round-robin` pauses arbitration when the next agent is on an unreachable node with explicit `arbitration.paused` / `arbitration.resumed` events (registration in Spec-005 is a Plan-014 precondition — tracked as BL-084); `free-form` and `request-based` degrade gracefully. Reconnect semantics align with Spec-002 node-identity continuation and Spec-013 replay. Eventually-consistent cross-node ordering is the accepted trade-off (AP over CP for the orchestration surface).
- **ADR-011 intervention dispatch** — Non-cascading propagation clarified; no new intervention verbs introduced; subtree-wide cascade would be a new ADR, not a Spec-014 edit.

Behavioral change: budget enforcement posture (advisory → hard ceiling). No blocking changes required to ADR-011, Spec-003, Spec-010, or the approval policy surface. Turn arbitration pause is an orchestration-layer visibility state distinct from run-level `paused`, consistent with Spec-003's discrimination of waiting states.
