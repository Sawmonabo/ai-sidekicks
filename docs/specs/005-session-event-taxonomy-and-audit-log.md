## Purpose

Define the canonical event envelope and taxonomy used for rebuilds, audit, and live projections.

## Scope

This spec covers event categories, required event fields, ordering, catch-up, rebuilds, and audit retention requirements.

## Non-Goals

- Full UI rendering rules for the transcript
- Metrics-only observability details
- Storage engine implementation details

## Required Behavior

- Every durable session-relevant change must emit a canonical event.
- Canonical events must include at least `eventId`, `sessionId`, `sequence`, `occurredAt`, `category`, `type`, `actor`, and correlation or causation metadata where applicable.
- The taxonomy must cover at least:
  - session lifecycle
  - agent lifecycle
  - run lifecycle
  - queue and intervention
  - approval requests and resolutions
  - repo, workspace, and worktree lifecycle
  - artifact and diff publication
- Events must be immutable after append.
- Ordering is **per-aggregate, not global**: within a single run, event order is preserved, and tool events pair by `toolCallId` (the canonical Tool Activity **payload** field — `payload.toolCallId`; provider-native tool-call identifiers such as `tool_use_id` normalize into it); **no global causal-order guarantee exists across aggregates** — consumers MUST NOT infer cross-aggregate causality from interleaved positions across runs or sessions. The ingest-side bounded reorder buffer's parameters (bound, overflow = flush-in-arrival-order + diagnostic, pairing timeout) are the consuming plan's to name; this spec fixes only the guarantee's scope.
- The log must support reading after a known cursor and reading bounded windows.

## Default Behavior

- Canonical event metadata is retained indefinitely unless an explicit retention policy supersedes it.
- Per-session event ordering is presented as a monotonically increasing sequence in session projections.
- Background work never removes anything the transcript draws. It may compress, repack, archive, move large bodies and rewrite indexes, and only when the transcript's order, its system messages, its tool rows and output, message identities and times, and the kept undo and fork anchors all survive. A session's events are deleted only when the person deletes the session, whole sessions at a time, and the deletion removes the session's rows (§Event Compaction Policy).

## Fallback Behavior

- If a client detects a live-stream gap, it must rehydrate from the canonical event log starting after the last acknowledged sequence.
- If a producer cannot emit a canonical event immediately, the related state change must not be considered committed.

## Interfaces And Contracts

- `EventEnvelope` must be versioned.
- A screen reads a session's events through one stream per session, `session.subscribe`, and through no other event method: it catches up from the screen's cursor, then follows the live append-only tail, batched by the daemon into one frame per 16 ms or per 50 events, whichever comes first, each frame carrying only changes, each with its cursor. The daemon never waits for a screen: a screen that falls behind is dropped for and told so on the next frame that fits, and repairs itself from the log by cursor. When a screen that fell behind has caught up on its queue, the daemon sends it one frame with no changes, carrying the drop mark and the newest cursor, so a session that goes quiet right after a drop still tells the screen it is behind.
- The daemon's own reads of the log are internal, never methods a screen calls: the read after a cursor returns ordered events plus the next cursor, and the window read returns a bounded historical window for rebuilds and inspection.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

### EventEnvelope Version Semantics

Full semantics of the `.version` field are specified in [ADR-017: Cross-Version Compatibility](../decisions/017-cross-version-compatibility.md). The binding contract summary:

> **Terminology note — "version stub":** This section uses "**version stub**" for the receiver-side artifact produced when an unknown-type event is preserved verbatim (full canonical bytes retained, so an upgraded receiver can interpret it later). A version stub retains all canonical fields.

- **Format:** Semver string `"MAJOR.MINOR"` (no PATCH component on the wire). Integer form is not used.
- **Producer sets it:** The emitting daemon writes its own outgoing wire version at emit time. `.version` is never copied from a received event. Version stubs record their original received version in version-stub metadata, separate from `.version`.
- **Validation is two-sided:** The control plane validates at write time; receiving peers validate on parse. A receiver that cannot interpret a given `.version` MUST persist the event as a version stub rather than drop or crash.
- **Unknown MAJOR (same or higher than receiver's supported MAJOR):** Persist as version stub with full original canonical bytes; never dispatched to application handlers. The canonical row's `.version` field stays the producer's original — version-stubbing is a read-side behavior, not a rewrite. On upgrade, a receiver that knows the type reads the stub's preserved canonical bytes as that typed event at dispatch time; no converter runs and the log row is never rewritten.
- **Unknown MINOR (same MAJOR, higher MINOR):** Event dispatches normally; unknown optional fields and unknown enum values within the payload are preserved verbatim. MINOR bumps MUST be additive-only per ADR-017.
- **Version range at the connection handshake, never at join or write:** An app outside its service's version range is refused once, at the connection handshake: the service answers with `DaemonHelloAck { compatible: false, reason }`, `reason` being `version.floor_exceeded` (the app is older than the service accepts) or `version.ceiling_exceeded` (the app is newer than the service knows), and the app draws that machine read-only and names the side that is behind. A session carries no version floor of its own, and no write, join or envelope read carries a typed version error ([ADR-017 §Decision](../decisions/017-cross-version-compatibility.md#decision) #3, #4, #10).
- **Immutability:** `.version` is set once at producer emit time and is part of the event's durable identity. It is never rewritten, by a version stub or by an upgrade.
- **Envelope version vs. event-type registry:** `.version` governs the envelope contract only. New event-type introductions are additive and MAY be allowed under the same envelope version if they follow the additive-only MINOR rule. V1 uses an accept-and-stub model for unknown types (each unknown type becomes a version stub on receipt); the event union in `packages/contracts` is the registry, and no central event-type registry exists, because the app talks only to its own service version and the one before it.

### Canonical Form

An event's canonical bytes are the [RFC 8785 — JSON Canonicalization Scheme (JCS)](https://datatracker.ietf.org/doc/html/rfc8785) serialization of its envelope members `id`, `sessionId`, `sequence`, `occurredAt`, `category`, `type`, `actor`, `payload`, `correlationId`, `causationId` and `version`, in the member order RFC 8785 §3.2.3 sets, with `null`-valued members included. `content_payload` is a column beside the envelope and is not part of them. `occurredAt` is RFC 3339 UTC with millisecond precision (`YYYY-MM-DDTHH:MM:SS.sssZ`), so ordering is byte-stable.

An event append is never refused for size. §Event Type Enumeration's payload shapes are metadata-shaped by construction — assistant output carries `contentType?` / `contentLength?` and never message text, tool activity carries no tool output, and artifact and diff content is held in the artifact store on the session's machine and read from other devices through Remote Control ([Spec-012 §Artifacts On Every Linked Device](012-artifacts-files-and-attachments.md#artifacts-on-every-linked-device)), never event-carried — so bulk content rides behind a reference, and a long text the log does hold is kept whole as consecutive entries.

## Event Type Enumeration

This section enumerates every individual event type within each `EventCategory`. Each type is a string value for the `type` field of `EventEnvelope`. The payload fields listed are the category-specific fields carried inside the `payload` object; the envelope-level fields (`id`, `sessionId`, `sequence`, `occurredAt`, `category`, `actor`, `correlationId`, `causationId`, `version`) are always present and are not repeated here. One **cross-cutting payload field pair** spans categories (the epoch-attribution carrier whose typed shape [Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) delegates to this spec): `sourceEpoch?` — a nonnegative integer naming the **pre-rollback execution epoch** a late-appended **non-lifecycle** row is attributed to — with its companion `sourcePosition?` — a nonnegative integer naming the **normalized session position** (the turn-boundary vocabulary of `run.rolled_back`'s `targetPosition`, §Run Lifecycle) that row occupies within its source epoch, registered because no run-scoped category's payload carries a native position key and the supersede cutoff (`turn > targetPosition`) cannot rank a late row against its epoch's surviving prefix without one — stamped **together** at ingestion by the run-engine's late-append leg (Plan-002 T3.10) — the pair from the straggler's **per-event operation association**, each provider-side operation recorded against the (epoch, turn) current when it opened, pre-fence (an association-less pre-epoch straggler falls back to the closed delivery generation's retained pair, a conservative always-superseding upper bound — [Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior)'s fence and generation-rotation semantics own the mechanics) — exactly when that cursor attributes the row to a superseded epoch, and absent on every current-epoch row — absence means current-epoch, the pair travels together with the row's `runId` (a stamped payload REQUIREs all three — the pairing rule below), and the stamp is never fabricated at read time. The field is admitted by the payload schemas of exactly the run-scoped categories that late-append window covers — `assistant_output`, `tool_activity`, `usage_telemetry` and `artifact_publication` — and by no others (a `run_lifecycle` straggler is absorbed, never appended, and so is a provider permission ask from the execution before a cut, which opens no pending approval; non-run-scoped categories carry no run epoch): every canonical `SessionEventSchema` payload branch of those four categories **whose variant is run-scoped** — the payload carries `runId` — MUST admit the optional pair via the Plan-004 T1.8 composition helper, whose pairing refinement is schema-enforced (either stamp key present ⇒ both present and `runId` present), so a stamped row validates through the canonical read path and is never rejected at subscription or rebuild validation; variants without run attribution never admit it — the account-scoped sentinel-bound `usage.rate_limit_update` (no `runId` — §Usage Telemetry) foremost — because an epoch stamp on a row with no run identity is unattributable by construction. The field lives inside `payload`, and no envelope-level field carries it, so the canonical set is the one §Canonical Form names: the pair is part of the v1.0 baseline payload contract from first emit, as the other baseline payload fields are (`executionPosture`, the terminal keys), and it survives a rebuild: the [Spec-003 §Driver-Level Rollback Mechanics](003-queue-steer-pause-resume.md#driver-level-rollback-mechanics) supersede projection consumes it for cross-epoch keying. Execution-epoch semantics — `0` before any rollback, advancing with each **accepted `run.rolled_back`** (a confirmed conversation rewind, regardless of the file-leg disposition) — are owned by [Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) and [Run State Machine §Invariants](../domain/run-state-machine.md#invariants), not redefined here; the typed Zod shapes (`SourceEpochSchema` / `SourcePositionSchema`, the `SOURCE_EPOCH_PAYLOAD_KEY` / `SOURCE_POSITION_PAYLOAD_KEY` consts, and the pairing-refinement composition helper) are [Plan-004](../plans/004-session-event-taxonomy-and-audit-log.md) T1.8's, in `packages/contracts/src/event/envelope.ts`, mirrored in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md).

### Session Lifecycle (`session_lifecycle`)

Payload shape: `{sessionId, previousState?, newState, actor?}`; the goal events carry per-type payloads — `session.goal_updated` carries the goal and its status (`{sessionId, agentId, goal, status, reason?, actor}` — a goal is a command sent to one agent, never what the session is, so `agentId` names the agent it was sent to; `goal` is the condition that agent works toward, whose exact shape is owned by the [Spec-014 §Session Goals](014-multi-agent-orchestration.md#session-goals) contract, and the event carries the same canonical value the accepted `session.goalUpdate` supplied, so RPC and durable event serialize identically; `status` is a union — `active`, `paused`, `blocked`, `usage-limited`, `budget-limited`, `complete`, `impossible` — whose `complete` and `impossible` members are final; `reason` carries the provider's own reason where it gives one, and `impossible`, which only Claude Code sends, always carries it), `session.goal_cleared` ends a goal and carries none (`{sessionId, agentId, actor}`; clearing is the distinct operation and never a status, so an update without a goal is malformed rather than an implicit clear). Each goal change is drawn only as one transcript system message; no goal text is ever put into a system prompt. A goal change is not a state transition. `session.created` carries a per-type payload of its own, because a session has exactly one main agent and that agent is born with the session rather than joined to it later: `{sessionId, mainAgent: {agentId, definitionId?, name, driverName, modelId, providerAccountId, effort?, toolAllowlist?, instructions?, goal?, state}, actor?}`. Every member of `mainAgent` is a value the **daemon** resolved when it started the session — the binding it resolved (driver, model, provider account, effort), the three axes the daemon itself reads (tool allowlist, instructions, goal), `definitionId` where a saved agent definition was named ([Spec-026 §Resolution when a run starts](./026-agent-definitions-and-peer-invocation.md#resolution-when-a-run-starts)), and the resolved agent `state` — and the event carries the same resolved values the session-create reply echoes, so wire and durable record serialize identically, exactly as the goal events do. This is the **creating record** of that agent's row in the `agents` projection ([Spec-014 §Interfaces And Contracts](014-multi-agent-orchestration.md#interfaces-and-contracts)): no attach event exists, so the `agent.*` types of §Agent Lifecycle only ever mutate a row this payload brought into being, and a projector that ignored it could not rebuild one.

### Agent Lifecycle (`session_lifecycle`)

Payload shapes are per-type, because one shared shape could not rebuild the `agents` projection. A switch of an agent's provider binding appends nothing when it is accepted. The pending switch is written to the agent row's own `pending_switch` column before the acknowledgment returns, and `agent.list` reads it back as `pendingSwitch` in the same `AgentBindingSwitchPending` shape the mutation's response returns ([Spec-014 §Same-Agent Provider Switch](./014-multi-agent-orchestration.md#same-agent-provider-switch)). No event records the pending switch, so no projector can read one as a change of binding before it lands. The effective move is written by the **terminal**: `agent.provider_binding_changed` carries the `to` binding and clears `pending_switch`, `agent.provider_binding_change_failed` clears `pending_switch` and leaves the columns untouched. So a switch appends exactly one event, at settlement, and the `agents` binding columns stay rebuildable from the log alone. `agent.provider_binding_changed` carries the session, the agent, `switchId`, `actor`, `from` and `to` — each a whole `AgentProviderBinding` `{driverName, modelId, providerAccountId, effort, outputSpeed?}`, where a `providerAccountId` of `null` means the binding follows the provider's current account — the account the run landed on, as a member of its own, `continuity: 'in_place' | 'brief'`, and `declaredLosses: DeclaredLossKind[]`. Whole bindings on both sides are what keep the log complete for a rebuild: the terminal writes the effective columns, so a settled member the log could not rebuild — the output speed among them — would leave its column NULL after a rebuild while `pending_switch` had already been cleared. **The account the run landed on is recorded apart from the binding's own account.** A change of driver ends the run and starts a new one on the new provider's current account, so the account the agent row carries does move; keeping the landed account beside `to.providerAccountId` rather than writing it into it means an agent that follows the current account is never silently pinned to the account it happened to land on. Moving an account on purpose is `providerAccount.setCurrent` on the provider surface; `agent.configUpdate` never asks for one. An account move settles in place (`continuity: 'in_place'`) at the session's next request, interrupting nothing. A change of model, effort or speed alone settles in place too and the screen draws no row for it: a row is drawn only for a provider or an account switch. The `to` binding records the value the switch **requested and committed**, which is that column's own content; what the new binding's provider then **declared** is a live reading and is deliberately not evented, an observation captured once being a second and staler record of a fact the running session already holds ([Spec-004 §The output-speed axis](./004-provider-driver-contract-and-capabilities.md#the-output-speed-axis)). `switchId` is the daemon-minted correlator the mutation's response carried — as the pending acknowledgment's id on the deferred arm, as the settlement's own id on the immediate one — so a client that was told a switch was coming can match it to the terminal that settled it. `continuity` is `'in_place'` or `'brief'`, the wire's honest-degrade discriminator, each naming a different act that carried the conversation rather than a degree of one: `'in_place'` where a per-turn-override axis or an account was carried on the **running** process, nothing respawned and nothing reconstituted; and `'brief'` where a **different** provider was started from a hand-over brief — the old provider's own summary taken on a throwaway copy of the session, with a reference to the whole old transcript written beside it as one plain file the new provider reads on demand. `'in_place'` is `applied`; `'brief'` is `degraded` and is never rendered as an ordinary success. `declaredLosses` is a list of named losses, **never free text** — its members are `'provider_private_reasoning'`, `'context_truncated'`, `'tool_call_history_repaired'`, `'conversation_history_summarized'`, `'helper_conversations'`, `'tool_output_bodies'`, `'live_tool_calls'`, `'provider_skill_and_command_names'`, `'turn_content_unavailable'`, enumerated in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), which is where the union lives — and it is **required**, because an empty array is the positive assertion that nothing was dropped and an absent one would be indistinguishable from a driver that did not know. Requiredness is **arm-scoped** so that assertion keeps its meaning: `'in_place'` carries the empty array by rule, nothing having been reconstituted; `'brief'` MUST be non-empty and MUST include `'conversation_history_summarized'` together with `'provider_private_reasoning'`. The `from` binding is the daemon's record of the binding being left, so the event is self-contained on a rebuild and a reader never has to fold backwards to learn what changed. `agent.provider_binding_change_failed` carries the session, the agent, `switchId`, `actor`, `from`, `attempted` (the binding asked for, its account included), `reason: 'driver_unavailable' | 'model_unavailable' | 'effort_unavailable' | 'output_speed_unavailable' | 'interrupt_refused' | 'target_unstartable' | 'account_unavailable'`, and, with `account_unavailable`, `accountState: 'reauth_required' | 'home_missing' | 'indeterminate' | 'not_registered'`, and is the **sibling terminal** of the type above, not a variant of it: an accepted switch is written to `pending_switch` on **both** arms, and that column is cleared by a terminal rather than by a reply, so an application-time refusal that appended no event would leave the promise standing with no record of why it was not kept. It is therefore emitted on both arms — on the deferred one it is the only refusal that reaches anyone, the caller having since disconnected; on the immediate one it appends in addition to settling the held-open request as the `failed` disposition, because a reply is not a durable record and the projection cannot be rebuilt from one. It is never emitted under the success name, because an event whose name asserts a switch landed is the wrong record of one that did not. The `from` binding is unchanged by construction (a failed application moves nothing), `attempted` names what was asked for, its account included, so a switch that could not reach its account says which one. A switch that fails after it was accepted never lands: the previous binding and account stay active, the success row is not drawn, and the transcript gains one system message naming the attempted switch and its reason — `Switch to Codex failed · <reason>`, or `Switch to account <name> failed · login expired · Sign in again`, with `Sign in again` only when `accountState` is `reauth_required`. No banner, toast, dialog or standing error is raised. It deliberately does **not** reuse the `agent.provider_axis_invalid` `axis` discriminator (`driverName` | `modelId` | `effort` | `outputSpeed`, the request's own member names and the whole of the axis union), and the two vocabularies are separate because they answer different questions: that error code answers a caller synchronously about a request that was never accepted and names the field to correct, while this reason explains why an **accepted** switch could not be honored at a boundary the caller is not watching — a set that must also carry `interrupt_refused`, `target_unstartable` and `account_unavailable`, none of which is a field of the request at all. One vocabulary spanning both would either drop those three arms or teach a client to render a fix-your-request hint for a failure no correction of the request would have avoided. A degraded settlement — a hand-over brief — is **not** a failure and never emits this type: it moved the agent and declared what came along, while this type means the agent did not move at all. A superseded pending switch emits neither terminal, by the [Spec-014 §Same-Agent Provider Switch](./014-multi-agent-orchestration.md#same-agent-provider-switch) supersession rule.

| Type | Description |
| --- | --- |
| `agent.provider_binding_changed` | A switch of an agent's provider binding — its provider, model, account, effort or output speed — landed, and the conversation was carried across. Its identity and run linkage are unchanged — this records a change of binding, never a new agent. A change of model, effort or speed alone settles in place, and the screen draws a row only for a provider or an account switch. |
| `agent.provider_binding_change_failed` | A switch accepted as pending could not be applied at its boundary, and the agent stayed on its previous binding and account. Emitted on **both** arms whenever an ACCEPTED switch fails at application: `pending_switch` is cleared by a terminal and never by a reply, so an immediate-arm failure emitting nothing would leave the promise standing with no record of why it was not kept — that arm additionally settles its held-open request as the `failed` disposition. The transcript gains one system message naming the attempted switch and its reason. A refusal reached BEFORE acceptance is a different thing entirely: it mints no `switchId`, writes no pending switch, and refuses synchronously with `agent.provider_axis_invalid`. Exactly one of this type and `agent.provider_binding_changed` terminates every pending switch that is not superseded. |

### Run Lifecycle (`run_lifecycle`)

One event per canonical state of the [Run State Machine](../domain/run-state-machine.md), plus the forward (non-state) `run.rolled_back` event.

Payload shape: `{sessionId, runId, runVersion, previousState, newState, failureCategory?: RunFailureCategory, failureCause?: {cause, origin, model, sentence?, explanation?, safetyCategory?} (the typed failure cause, present only on a run.failed, whose first member is the refusal, `cause: 'refused'`; origin is 'provider' where the driver normalized the provider's own cause and 'daemon' where the app's own refusal or failure ended the run), recoveryCondition?: RecoveryCondition ('recovery-needed' | 'reauth-required' — the named type in the API Payload Contracts mirror), processExit?: {exitCode?, signal?, outputTail} (present only on a run.failed whose provider process ended on its own under the turn: the exit code or the signal, and the last lines the process printed), trigger?: 'step_limit' | 'spend_limit' | 'token_limit' | 'workflow_phase_canceled' (the canonical union matching the `run.interrupted` per-type row below and the api-payload §Plan-002 mirror), completionKind?: 'turn' | 'task', intendedClose?: true, executionPosture?: ExecutionPosture}` — this state-transition shape governs the state events, `run.queued` through `run.failed` in the table below; `executionPosture?` (structural shape per the typed `RunStateChangeEvent.executionPosture?` mirror in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) — the canonical in-corpus shape source; policy semantics per [Spec-010](./010-approvals-permissions-and-trust-boundaries.md)) is stamped only on `run.running` — the post-setup-gate spawn-success transition (Plan-002's gate seam admits `queued → starting`, then setup gates — Plan-007's execution-root gate among them — run **before** `driver.startRun`, so the resolved workspace root and effective posture are final only when `running` fires; a `run.starting` stamp would be premature) — recording the run's effective posture for audit, and is absent on every other transition; `run.rolled_back` is per-type (see its row) and carries no `previousState`/`newState`.

`runVersion` is the run aggregate's **any-run-progression counter** (Plan-002 D-002-1): it increments on every run progression — applied interventions included, not only the state transitions enumerated below — and is the optimistic-concurrency token the `expectedRunVersion` intervention guard compares against ([Spec-003 §Interfaces And Contracts](003-queue-steer-pause-resume.md#interfaces-and-contracts)). It is a **payload** field, distinct from the envelope-level `.version` (§EventEnvelope Version Semantics above): `.version` is the immutable semver wire-contract version, whereas `runVersion` is a mutable per-run counter carried inside `payload` — the two share the word "version" but are different contracts and must never be conflated. Because `runVersion` also advances on applied interventions that cause no state change (e.g. a native steer), the authoritative source of a run's current `runVersion` is the run-state read / `run.subscribeState` stream and the intervention / pause / resume responses, not the `run.*` event sequence alone. A no-state-change advance with **no per-type event of its own** (the native-steer case) is **not** broadcast as a discrete `run.*` event — there is no state transition to record ([Spec-003 §Driver-Level Steer Mechanics](003-queue-steer-pause-resume.md#driver-level-steer-mechanics)); the carved-out exception is the in-place rollback from `paused`, which also transitions no state but whose per-type `run.rolled_back` event (its row below) streams the fresh post-rollback `runVersion` — so a _non-intervening_ subscriber tracking `runVersion` off the event sequence may hold a stale comparand after a steer-like advance. Its next guarded intervention / pause / resume is then correctly rejected `expired` (the comparand genuinely _is_ stale — this is the optimistic-concurrency guard working, not a false rejection), whereupon it re-reads run-state for the fresh `runVersion` and retries: the reject → re-read → retry loop is the designed correction, and V1 adds **no** broadcast/read-model push for such no-per-type-event bumps. The _intervening_ caller never round-trips — its `RunControlAck` / `InterventionRequestResponse` / pause-resume ack carries the post-application `runVersion` directly (per [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md)).

**At-most-once terminal emission.** For the four terminal types (`run.completed` / `run.interrupted` / `run.stopped` / `run.failed`), at most one terminal `run_lifecycle` event exists per `(runId, runVersion)`. The emitter owns the guarantee: the terminal guard + state swap + append execute under the per-session append lock with read-your-writes state, so a duplicate terminal attempt is rejected before append. A schema-level **partial unique index backstops** the emitter contract — `UNIQUE` on (`json_extract(payload, '$.runId')`, `json_extract(payload, '$.runVersion')`) `WHERE category = 'run_lifecycle' AND type IN ('run.completed', 'run.interrupted', 'run.stopped', 'run.failed')`, predicated on `session_events`'s real scalar `category` + `type` columns ([local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md)) — as a **fail-loud invariant detector**: an index violation surfaces a bug, never silently no-ops (there is no append-if-absent API). The schema mirror ([local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md)) carries the index DDL beside the projection-level CHECK below. Terminal payloads MUST carry non-null `runId` and `runVersion` (an emitter precondition, mirrored as that same projection-level CHECK): SQLite UNIQUE indexes treat NULLs as distinct, so a NULL key would silently bypass the backstop for exactly the malformed rows it exists to catch.

**Intended-close discriminator.** A daemon-initiated `closeSession` produces a clean terminal: the terminal payload carries `intendedClose: true`, and consumers MUST NOT classify such a terminal as a crash. The field is absent on every other terminal path (natural completion, the person's interrupt, failure), so its presence is the discriminator — orderly shutdown stays distinguishable from abnormal termination in the durable record.

#### User Message Events

The durable user-message row — the third set of `interactive_request` events beside queue items and interventions: a user's message into the session becomes first-class transcript history, not merely queue metadata. Payload shape: `{sessionId, queueItemId?, runId?, actor, deviceId?, message, origin?: 'voice', answersQuestionId?}` — `message` is the user-authored text, `origin: 'voice'` marks the words a Codex voice call heard (§Voice), `answersQuestionId` names the question a message answers (§An Agent's Question) and is absent on every other message, and `deviceId` is the device the message was sent from, the device the connection carries, present wherever one of the person's devices sent it; the transcript draws no device mark ([Spec-027 §Answering from another device](./027-remote-control.md#answering-from-another-device)). The answer to an agent's question is written as this row (§An Agent's Question), so it names the device that answered.

| Type | Description |
| --- | --- |
| `user.message` | A user message was accepted into the session. The provider-side `user_text` echo correlates into this row as delivery confirmation; audit reads and rebuilds reconstruct the human side of the conversation from these rows. |

#### An Agent's Question

The fourth set of `interactive_request` events: an agent stops mid-turn to ask the person something, and the daemon turns either provider's held request — a Claude Code question request, a Codex user-input request — into **one** record the screen renders; a tool server's question (an MCP elicitation) becomes the same record, the server named where the agent's short header stands. Payload shape: `{sessionId, runId, questionId, isAgentWaiting, pageCount, questions: [{header?, text, heading?, options: [{label, description?, preview?}], severalAnswers, secret}]}` — `isAgentWaiting` is `false` only for a question the agent does not wait for (below) and `true` for every held request; `pageCount` is how many questions the record carries and `questions` carries them all, so paging through them needs no second read and typed text survives paging in both directions; `header` is the agent's own short label for the ask and `heading` its own summary line, each present only where the provider sent one; `preview` is present only where the provider attached one to an option, which one provider does and the other does not; `severalAnswers` is the provider's own reading of whether a question takes more than one answer, never a console default; and `secret` marks a question answered into a masked field, whose value is **never stored** — it reaches no event payload, no artifact and no projection.

**A question is held open with no timer.** It stands until it is answered, is rebuilt on a reload and on the person's other devices, and the first answer settles it everywhere. One call answers every page, carrying per question exactly one of: the labels picked, typed text, the secret, or a skip. The person's turn is then written as an ordinary `user.message` row with the secret masked, so the answer is in the conversation where a reader expects it rather than in a second record. A question the agent does **not** wait for — Codex's `agentMessage` item carrying `questions` with `delivery: "async"` — is this record too, written with `isAgentWaiting: false` and without moving the run, which keeps running. That answer is one ordinary `user.message` whose text is the question quoted and then the answer. Every answer's `user.message` carries the question's id as `answersQuestionId`, and that is the question's answered mark: a question the agent does not wait for reads unanswered until the agent has taken the queue item carrying its answering message ([Plan-002](../plans/002-queue-steer-pause-resume.md)'s queue), and answered from then on, so its count drops on every device; an answer withdrawn before the agent takes it leaves the question unanswered.

| Type | Description |
| --- | --- |
| `question.asked` | An agent asked the person one or more questions mid-turn, and the record the screen renders was created. Payload `{questionId, sessionId, runId?, waitId?, isAgentWaiting, pageCount, questions[]}`: `questions[]` is the agent's free text and the options it offers. |

> See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed payload definitions.

### Approval Flow (`approval_flow`)

Payload shape: `{sessionId, runId?, approvalRequestId?, askId?, category: ApprovalCategory, scope, requestedBy?, resourceDescriptor?, effectiveScope?, deviceId?, nodeId?, rememberedScope?, ruleId?, invalidationTrigger?}` — `runId`/`approvalRequestId` are absent on `approval.rule_revoked` (no in-flight request); `requestedBy`/`resourceDescriptor` are present on `approval.requested`, which also carries `askId` when the request originates from a provider permission ask (the daemon's own id for the ask, a ULID, the provider's request id staying delivery routing state; required at the normalizer seam and persisted onto the `approval_requests` projection's `ask_id` column, so outcome routing to the native ask survives restart and rebuild — [Spec-010 §Required Behavior](./010-approvals-permissions-and-trust-boundaries.md#required-behavior)) and `effectiveScope` + `deviceId` on the resolution events — `deviceId` being the device whose answer landed, present wherever one of the person's devices answered ([Spec-027 §Answering from another device](./027-remote-control.md#answering-from-another-device)), and `approval.remembered` carries the rule the answer handed to the provider (the answering `deviceId`, bound `nodeId`, binding = `rememberedScope`/`runId`, origin resolution via `approvalRequestId`) together with the rule's **sense** on `rememberedScope` — allow or block, a blocking rule refusing its subject outright with no card raised until the rule is replaced. The provider keeps the rule and answers by it at every level that asks; the daemon keeps no rule store, and these events are the session's own record of its answers, which the daemon lists and carries across a restart of the provider's process ([Spec-010 §Default Behavior](./010-approvals-permissions-and-trust-boundaries.md#default-behavior)). So the logged events alone rebuild the daemon's approval projection byte-equal; `ruleId` is present on `approval.remembered` / `approval.rule_revoked`; `invalidationTrigger` is present on `approval.rule_revoked`. `moderation.review_flagged`, `approval.reviewer_denied` and `approval.denial_overridden` carry payloads of their own, stated in their rows, and the `plan.*` types carry theirs in the paragraph after the table.

| `approval.canceled` | An approval request was canceled because its run was interrupted, because its run ended before resolution, because its session closed before resolution ([Plan-009](../plans/009-approvals-permissions-and-trust-boundaries.md)'s sweep), its originating provider ask was retracted, because an undo (`session.restore`) cut the turn that raised it ([Spec-003 §Required Behavior](./003-queue-steer-pause-resume.md#required-behavior)), or because the resume position-compare halted its run for reconciliation, settling the pending approval as moot ([Spec-013 §Fallback Behavior](./013-persistence-and-recovery.md#fallback-behavior)). |

**A provider's permission ask is recorded once, as an approval.** Claude Code's `can_use_tool` control request for any tool but its question tool, and each of Codex's approval requests, is `approval.requested` carrying the daemon's own `askId` for it, kept in the `approval_requests` projection's `ask_id` column so the answer reaches the provider across a restart; `approval.approved`, `approval.rejected` and `approval.canceled` end it, and it has no second record. The answer's delivery to the provider is in the daemon's log only, never an event. A structured question — Claude Code's question tool, Codex's `item/tool/requestUserInput`, or a tool server's question (an MCP elicitation) — is not a permission ask: it becomes the question record of §An Agent's Question.

**An approval waits until it is answered.** No approval request carries a deadline and none expires: the card stands until the person answers it, until the run it blocks is interrupted, or until the provider process ends — the last two arriving as `approval.canceled`. Moving the session to a permission level that never asks answers an open card as allowed, recorded as `approval.approved`, and its blocked row runs; a later ask at that level raises no card, and moving back to a level that asks asks again.

**The plan record and its outcome.** A plan turn ends with a held provider request on one leg and a completed plan item on the other, and the daemon turns either into **one** plan record the screen renders and one call answers — a plan card being an attention entry exactly as an approval is, which is why the three types live in this category rather than in one of their own. `plan.proposed` carries `{sessionId, runId, planId, title, text, stepCount, fileCount, planFilePath?}`: `title` is the plan's first heading and `text` its prose as the agent wrote it, taken from the held request or the plan item and never read off the disk; the two counts are the daemon's own reading of the plan — its top-level steps and the files it names — and are what the card's summary line states; `planFilePath` is present only where the provider wrote the plan as a file, which one provider does and the other does not, so its absence means there is no file rather than that the path is unknown. The verdict is one of three — `keep`, `build`, `fresh` — and only two of them append: `keep` appends nothing and leaves the provider in plan mode, a revised plan minting a new record; `build` appends `plan.accepted` `{sessionId, planId, deviceId}`, the run continuing in this session; and `fresh` appends `plan.handed_off` `{sessionId, planId, freshSessionId, deviceId}`, naming the session minted on the same project and worktree and seeded with the plan, the verdict itself carrying the provider and the level of the session to mint — the account is neither, a minted session running on its provider's current account the way every session does. Both outcome rows exist so the system messages survive a reload, and each names the device whose verdict landed (`deviceId`). The plan record is held open with no timer, is rebuilt on a reload and on the person's other devices, and the first verdict settles it everywhere.

### Repo, Workspace, and Worktree Lifecycle (`session_lifecycle`)

Payload shape: `{sessionId, repoMountId?, workspaceId?, worktreeId?, state, actor?}`. A project's own attach and detach are not session events: another device sees a new project through the project list's owner, never through a session's log. `worktree.created` additionally carries `restoredFrom?` — the id of the kept copy it was put back from, present only on a put-back — and `worktree.retired` carries `removedWorktreeId?`, present only when `Discard and remove` kept the tree: the folder moved whole into `worktrees/<project>/.removed/`, git's per-worktree record copied, the staged objects packed and the commit pinned, kept until the person presses `Delete now`, with no automatic deletion. A put-back is recorded as that `worktree.created`, so no further event type exists for it. `session.branch_changed` carries a per-type payload — `{sessionId, repoMountId, worktreeId: string | null, branch: string | null, previousBranch}` — appended once for each session working in a folder whose branch changed outside the app, so every surface follows the session's record. `session.swept_to_repo_root` carries a per-type payload — `{sessionId, repoMountId, worktreeId, pendingMoveCleared?: true}` — because a sweep is not a state transition: it records that this session's working folder became the repository root because the worktree it was attached to was removed, `worktreeId` names the removed tree, and `pendingMoveCleared` is present only where the same removal cleared a pending move that pointed at that tree (absent otherwise, the presence-discriminator idiom `intendedClose` uses). One event is appended per session the removal moved, so the flow row for each moved session survives a reload.

### Artifact and Diff Publication (`artifact_publication`)

Payload shape: `{sessionId, artifactId?, runId?, diffArtifactId?, state}`. The contracts-package payload schemas for `artifact.*` events MUST be non-strict — unknown-key passthrough — so a known event type carrying an additive field is tolerated rather than rejected; a `.strict()` artifact payload schema is an [ADR-017](../decisions/017-cross-version-compatibility.md) MINOR-compatibility defect, because unknown-type stubbing never applies to a known type. No artifact content is event-carried: a session's artifacts are held in the artifact store on the machine that runs the session, and the person's other devices read them there through Remote Control ([Spec-012 §Artifacts On Every Linked Device](./012-artifacts-files-and-attachments.md#artifacts-on-every-linked-device)).

`git.settled` carries a per-type payload — `{sessionId, runId?, cause: 'committed' | 'pushed' | 'pulled' | 'pull_request_opened' | 'review_posted', commitId?, branch?, requestNumber?, requestUrl?, verdict?}` — one settlement record for the acts that move a session's work between this machine's working folder and its hosting service, so those rows survive a reload. `cause` is one of the values above, and each cause carries exactly the reference its row names: the commit's identifier for `committed`, the branch for `pushed`, the branch and the commit it brought in for `pulled`, the request's number plus its address on the hosting service for `pull_request_opened`, and the request's number plus the review's verdict for `review_posted` — a posted review whose verdict is comment-only reads `Commented on PR #12`. `runId` is present where an agent performed the act as an ordinary tool call and absent where the person pressed the control.

### Assistant Output (`assistant_output`)

Payload shape: `{sessionId, runId?, contentType?, contentLength?, origin?: 'voice'}`, with the message or reasoning **body itself** carried out-of-payload in `session_events.content_payload`; `origin: 'voice'` marks the answer a Codex voice call spoke (§Voice), absent on every other message. `runId` is present on every row but a voice call's answer, which carries `origin: 'voice'` and no `runId` because the call's answer comes outside any run of the agent's.

**The body has a durable home, and it is not `payload`.** A row recording that an assistant spoke but not what it said would leave [ADR-027](../decisions/027-canonical-transcript-is-authoritative.md)'s ruling that the canonical transcript is authoritative for the content of a provider session standing over a log holding none of it. The body lands in the [`session_events.content_payload`](../architecture/schemas/local-sqlite-schema.md) column, stored plain and kept out of `payload` and out of the canonical bytes. A body of 1 KiB or more is compressed with raw deflate at level 6 before it is written, and the encoding is recorded in the payload; a smaller body is stored as it is. Compression happens here, at write time.

**The body is a separate typed projection; it is never merged back into `payload`**. The payload shapes above deliberately declare **no** body member, and the `SessionEventSchema` variants that implement them are strict — which is what lets a driver normalizer resolve these types as envelope-constructible in the first place. A read path that spliced the body into `payload` would therefore have exactly three options, all wrong: add an undeclared key and fail strict validation, loosen the schema and give up the constructibility check, or change the shape of an event that is immutable once appended. Reading instead produces a **`HydratedSessionEvent`** — a distinct read-side type pairing the unmutated event with a `content` member that is a closed two-arm union: an **available** arm carrying the plaintext body together with the `contentLength` the payload already carries, or an **unavailable** arm, for a row whose column is NULL because it never had a body. The stored event and the hydrated view are two types precisely so that the two can never be confused at a call site: the canonical transcript fold consumes the hydrated projection, and the stored event is never rewritten. The unavailable arm is also where `'turn_content_unavailable'` gets its truth value, rather than a fold inferring loss from an absent key.

`contentType?` and `contentLength?` describe the body: `contentLength` is its UTF-8 byte length. Both members are ordinary `payload` content and neither is a second copy of the prose.

| Type                        | Description                                                    |
| --------------------------- | -------------------------------------------------------------- |
| `assistant.message`         | The assistant has emitted a message to the session transcript. |
| `assistant.thinking_update` | The assistant has emitted a reasoning or thinking update.      |

### Usage Telemetry (`usage_telemetry`)

Payload shape: `{sessionId, runId?, tokenCount?, inputTokens?, outputTokens?, cacheReadTokens?, cacheWriteTokens?, reasoningTokens?, providerAccountId?, credentialGeneration?, costUsdMicros?, windowUsedTokens?, windowMaxTokens?, windowSource?: 'provider_reported' | 'model_default', exceeded?: boolean}` (`windowSource` + `exceeded` mirror context-window provenance); the shape also carries the wire-attribution carriers `modelId?: string` and `subagentId?: string` — populated by the driver normalizer when the provider attributes usage below run scope (per-model usage maps; subagent-scoped usage pairing on the (`runId`, `provider`, `subagentId`) triple), absent when the wire attributes only at run scope — so pricing keys a differently-modeled subagent's rows at its own model ([Spec-014 §Provider-Native Subagents](./014-multi-agent-orchestration.md#provider-native-subagents))). This shape governs the three metered update types (`usage.token_count`, `usage.cost_update`, `usage.context_window_update`) only — with per-type requiredness: `usage.cost_update` MUST set `costUsdMicros` (`costUsdMicros` is the request's figure in integer micro-dollars, priced once when it completes and never repriced; a request held for a price carries it once a fetch prices it — [Spec-014 §Cost Derivation And Absent-Cost Semantics](./014-multi-agent-orchestration.md#cost-derivation-and-absent-cost-semantics)) and `usage.context_window_update` MUST set `windowSource` + `exceeded` (where the window figures came from, and whether the provider's own reading shows the conversation past the window, which the driver sets at normalization and never estimates), which the context ring and the inspector's Context section read; `windowUsedTokens` / `windowMaxTokens` travel as a **pair** — an emitter sets both or neither (a lone numerator or denominator is an emitter bug; the pair is absent only where the wire genuinely supplies no counts, e.g. a bare provider exceeded signal), and a counts-absent update leaves the window figures unknown, never filled with a fabricated denominator; `usage.rate_limit_update` is per-type — exactly `{provider, providerAccountId, credentialGeneration, limitId?, windowMins, usedPercent, resetsAt?}`, keyed `(providerAccountId, limitId)` (its row below carries both re-keys and the `limitId`-absent `default` rule), with no `sessionId` in the payload (session binding happens at the envelope via the node-scope sentinel per §Daemon-Scope Event Binding). **Per-turn delta semantics.** The token members a `usage.token_count` row carries (`tokenCount`, `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens`, `reasoningTokens`) are **per-turn figures, never cumulative counters**: a run- or session-scope total is obtained by summation over that scope's rows, and no consumer differences one row against another. The emitter discipline that makes the fold sound is [Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior)'s usage-delta rule — the driver derives the per-turn figure from the provider's cumulative counters at its normalize boundary, so a cumulative reading never reaches this payload. The sum-fold consumer is the budget accountant ([Plan-013](../plans/013-multi-agent-orchestration.md)). **The account that paid, and the three counts a per-turn row could not otherwise carry.** `usage.token_count` additionally carries `providerAccountId` and `credentialGeneration` — the account the turn was charged to, and the credential generation observed with it, spelled exactly as the account-scoped `usage.rate_limit_update` below spells them — and `cacheReadTokens?` / `cacheWriteTokens?` / `reasoningTokens?` beside `inputTokens?` and `outputTokens?`. All five are additive-optional under [ADR-017](../decisions/017-cross-version-compatibility.md); the account pair is **required on emitters of this type** and unused by the other two metered types, while the three counts are present exactly where the provider's own per-turn carrier names them and absent otherwise — absent meaning the provider reported none, never zero. Without the pair a provider's figures silently pool every account registered for it, which is the failure the account axis exists to prevent; without the counts, three of the five token figures the per-turn usage projection reads have no source at all ([Spec-025 §State And Data Implications](025-provider-accounts-and-credential-homes.md#state-and-data-implications)). The account is **daemon-resolved and server-stamped** from the run's own admission record rather than from anything the wire reported, on the same rule `run.queued`'s `admittedProviderAccountId` follows: a provider reports tokens, never who is paying for them. **A turn no session owns carries the account and no session.** The window-start turn [Spec-025 §Credential-home health observation](025-provider-accounts-and-credential-homes.md#credential-home-health-observation) spends on an account outside every session is metered by this type with `runId` **absent** and the envelope bound to the reserved node-scope sentinel `session_id` per [§Daemon-Scope Event Binding](#daemon-scope-event-binding) — the binding `usage.rate_limit_update` already takes for an account-scoped fact with no owning session — so that turn counts in the account's own totals and in no session's receipt. No second event type is minted for it: the fact is a turn's consumption, and this type is the carrier for a turn's consumption.

| Type | Description |
| --- | --- |
| `usage.token_count` | A per-turn token consumption figure has been recorded for a run; run- and session-scope totals fold by summation over rows. |
| `usage.cost_update` | A cost accumulation update has been recorded: one priced request, priced from the session's stream or, for a request the provider leaves out of the stream, from the provider's own telemetry export on this machine ([Spec-014 §Cost Derivation And Absent-Cost Semantics](./014-multi-agent-orchestration.md#cost-derivation-and-absent-cost-semantics)). It is never a transcript row. |
| `usage.context_window_update` | The context window reading changed significantly: `windowUsedTokens` and `windowMaxTokens` as a pair, with `windowSource` and `exceeded`. The screen's context read, `session.contextSubscribe`, serves this same reading as `{used, window, windowSource, exceeded, breakdown?}` — `used` and `window` are these two counts under the read's own names, and `breakdown` is Claude Code's own category report or, on a Codex session, Codex's only split — cached input, input, output and reasoning — from the thread's `thread/tokenUsage/updated`, the same read that feeds the ring — so the meter and the inspector's context section never disagree. |
| `usage.rate_limit_update` | An account-scoped provider-quota snapshot: payload `{provider, providerAccountId, credentialGeneration, limitId?, windowMins, usedPercent, resetsAt?}`, keyed by `(providerAccountId, limitId)` (the account half keeps two registered accounts of one provider from colliding: keyed on the provider alone, one account's exhaustion overwrites the other's reading and the person is shown a healthy quota while the account actually executing is spent. `credentialGeneration` makes a reading taken before a re-authentication detectable as stale rather than silently current. This is the one usage kind carrying account identity **directly**, because provider quota is account-scoped and has no run to join through; `usage.token_count` carries the same pair for the per-turn usage projection's account axis. `limitId` is additive-optional and absent means the reserved identifier `default`: the account alone still collides **within** one account, because one pinned provider publishes several distinct limits at a time and more than one of them can share a window length, so keying on the length would retain one of them by arrival order. `windowMins` stays on the payload as a property of the reading rather than part of its identity), carrying **no `runId`** — account-scoped, not run-scoped; a display/quota reading only, never an input to a security or admission decision. Consumer obligations (staleness defenses): an empty snapshot is a no-op; `windowMins <= 0` is dropped; **every obligation below applies per `(providerAccountId, limitId)` and never across limits** — two limits of one account move independently, so a comparison spanning them is meaningless; a lower-`usedPercent` reading is dropped **only when window identity is confirmed** (same `limitId` **and** same `resetsAt`) — usage climbs monotonically within a window, but when `resetsAt` is absent on either reading the window boundary is unknowable and the **newest reading wins**: a post-reset low reading is otherwise indistinguishable from a stale same-window decrease, pinning the display at the prior window's high-water mark; fail-open to freshest data, since a transient stale decrease self-corrects on the next snapshot. |
| `usage.api_retry` | A transient provider API retry was observed mid-run (the normalized `api_retry` kind plus its typed-error enum — capability-bearing: mid-run authentication/billing/rate-limit trouble becomes detectable instead of vanishing into silence). Per-type payload: `{sessionId, runId?, provider, errorKind, retryDelayMs?, attempt?}` — `errorKind` is the normalized typed-error enum value carried from the wire (the Claude `api_retry` enum as that provider publishes it; other providers normalize into the same vocabulary). |
| `usage.context_compacted` | The provider compacted the run's context window (the normalized `compact_boundary` kind) — **distinct from `event.compacted`** (§Event Maintenance), the record a session's deletion writes: this is the provider shrinking its own conversation context, and no stored event changes. Per-type payload: `{sessionId, runId, provider, preCompactionTokens?, postCompactionTokens?, summary?}`. `summary` is the summary the provider kept of the compacted conversation, in the provider's own words and unchanged, which the `Context compacted` row opens to ([Spec-011 §Required Behavior](011-transcript-and-reasoning.md#required-behavior)); it is absent where the provider kept none, and the row then has nothing to open. A compaction replaces the run's last used-tokens reading with `postCompactionTokens` when present, and leaves it unknown until the next `usage.context_window_update` otherwise. |
| `usage.model_rerouted` | The provider moved a turn onto another model and the turn went on (the normalized `model_rerouted` kind). Claude Code's `model_refusal_fallback`, `model_fallback` and `model_consent_fallback` and Codex's `model/rerouted` each normalize into it, and it draws one `Model switched` system message ([Spec-011 §Flow Row Kinds](./011-transcript-and-reasoning.md#flow-row-kinds)). Per-type payload: `{sessionId, runId, agentId?, fromModel, toModel, scope: 'turn' \| 'session' \| 'local', sentence?, explanation?, cause: 'safety' \| 'model_unavailable' \| 'model_blocked' \| 'out_of_credits', safetyCategory?}`. `scope` says how far the switch reaches: `turn` for one turn, `session` for the rest of the session, `local` for only a subagent's, a side question's or a background fork's response. The frames map onto it: Claude Code's `model_refusal_fallback` is `cause: 'safety'` with the frame's own `scope` (`local` stays `local`, absent reads `session`); `model_fallback` is `scope: 'turn'`, with `cause: 'model_blocked'` for its `model_blocked` trigger and `'model_unavailable'` for every other trigger; `model_consent_fallback` is `scope: 'session'`, `cause: 'out_of_credits'`; Codex's `model/rerouted` is `scope: 'turn'` (Codex keeps the requested model and compares each response's model against it, so the switch is per request), `cause: 'safety'`, `safetyCategory: 'cyber'`. On Claude Code `fromModel` and `toModel` are the frame's `original_model` and `fallback_model`, `sentence` is its `content` when that is not empty, `explanation` its `api_refusal_explanation`, and `safetyCategory` its `api_refusal_category`, an open string; on Codex `sentence` is the `warning` notification Codex sends right after `model/rerouted` in the same turn, recorded only here and never as a `session.notice` of kind `provider_warning`, because it is this row's sentence and its words show once. A request the reroute names is priced at the model it ran on, `toModel`, and held until the price table prices that model, never at the model it was sent to. Consumer obligation: the `BudgetAccountant` prices the run's requests after the reroute boundary at `toModel` where a usage row carries no per-row `modelId` (per-row attribution, when the wire supplies it, always wins). |

**Session binding.** `usage.token_count` / `usage.cost_update` / `usage.context_window_update` — and `usage.api_retry` / `usage.context_compacted` / `usage.model_rerouted` — carry the real `sessionId` of the run or session they meter; `usage.rate_limit_update` is account-scoped with no single owning session and binds to the reserved node-scope sentinel `session_id` per [§Daemon-Scope Event Binding](#daemon-scope-event-binding). The one `usage.token_count` row with no session — the window-start turn, above — binds to that same sentinel for the same reason and is the only row of this type that does.

### Recovery Events (`recovery_events`)

Daemon-startup recovery lifecycle events producing the durable record of projection rebuild, binding restoration, and in-flight run disposition per [Spec-013 §Required Behavior](./013-persistence-and-recovery.md#required-behavior). These events belong to their own category rather than `run_lifecycle` because a single recovery cycle may touch zero, one, or many runs across multiple sessions, and the category scope is **the daemon's recovery pass**, not any one run.

### Data Acts

The person's data acts ship in V1, and none is a category of events of its own. A session's purge is the daemon's one purge path. No event of the session records it, because the purge deletes every row of the session; its one record is the `event.compacted` receipt on the sentinel session (§Event Maintenance). It deletes the session's rows after the files only that session names, with SQLite's `secure_delete` on, so the freed pages hold nothing readable, and checkpoints the write-ahead log with `TRUNCATE` once the delete commits, and stored artifact payloads no surviving manifest names are unlinked after that commit ([Spec-020 §Ordering And Atomicity](./020-data-retention-and-gdpr.md#ordering-and-atomicity)). `Export all data` writes a readable folder that holds no settings, credentials or keys, and records one line in the diagnostic log rather than an event. `Erase all data` stops all work, signs the providers out, deletes the app's credential-store items and the store, and restarts the service empty, leaving no log to write into. `sidekicks delete-account` is the one way to delete the hosted account, through the control plane from a signed-in machine; and the revocation denylist is written on every revocation ([Spec-020](./020-data-retention-and-gdpr.md)). A lost or stolen device is revoked one at a time, recorded as the control plane's `device.revoked` (§Device And Machine List (control plane)), never as a session event; the daemon holds no WebAuthn credential to reset.

**Why a deleted session leaves nothing readable.** A person who deletes a session expects it gone, not hidden. A session purge deletes the session's rows with SQLite's `secure_delete` on, which overwrites deleted content with zeros ([SQLite — PRAGMA secure_delete](https://www.sqlite.org/pragma.html#pragma_secure_delete)), and checkpoints the write-ahead log with `TRUNCATE` once the delete commits, so neither the database file nor its log keeps a readable copy, and nothing of the session is hashed and kept.

### Security Events (`security_events`)

Daemon-emitted events recording the security and data-protection posture transitions the person is shown — a pinned relay's refused key per [Spec-027 §Interfaces And Contracts](./027-remote-control.md#interfaces-and-contracts). These events belong to a distinct category from `event_maintenance` (which records operations on the event stream itself) because they describe **the daemon's security and data-protection posture** at process scope. Like that infrastructure-state category, security events fire at daemon scope across all sessions hosted on the node — they are not session-scoped. (These daemon-scope categories fire at process scope across all sessions, so they bind to a **reserved node-scope sentinel `session_id`** in the daemon-local `session_events` store: the local SQLite `session_id` is `TEXT NOT NULL` with **no** foreign key (see [local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md)), so a reserved sentinel value is admissible without a phantom `sessions` row. The sentinel is pinned to the **RFC 9562 §5.10 Max UUID** `ffffffff-ffff-ffff-ffff-ffffffffffff`: the wire-path `EventEnvelopeSchema` validates every `sessionId` with `packages/contracts/src/session/session.ts#SessionIdSchema`, whose validator is the `packages/contracts/src/internal/branded.ts#brandedUuidIdSchema` factory's own `RFC_9562_TEXT_FORM` predicate regardless of the local store's looser `TEXT` typing, so the sentinel **must** be a value that predicate admits or these events would be rejected before append/serialization — the predicate admits the Max UUID by name, beside the general form and the Nil UUID, and matches case-insensitively, so the sentinel is emitted lowercase as a canonical-form convention rather than as a parse requirement. The Max UUID is chosen over the Nil UUID deliberately: it is a standards-reserved sentinel distinguishable from an accidental nil/zero-init, and is structurally disjoint from the `gen_random_uuid()` v4 id space (version nibble `f`, not `4`), so it can never collide with a real session id. In the daemon-local store it forms its own monotonic-sequence partition exactly as a real session id does — reusing the existing per-session machinery, not a new mechanism. Every event of this category binds to this sentinel. The cross-category binding rule for all daemon-scope events — `event_maintenance` and the account-scoped `usage.rate_limit_update` (`usage_telemetry`) — is specified canonically in [§Daemon-Scope Event Binding](#daemon-scope-event-binding) below.)

Payload shape: `{nodeId, occurredAt}` (base). Per-event payload extensions called out inline.

| Type | Description | Payload Extension |
| --- | --- | --- |
| `relay.pin_refused` | A pinned relay presented a key other than the one pinned when it was linked, and the daemon refused the connection with `relay.spki_mismatch` (412). Only a relay whose certificate does not chain to a root the operating system trusts has its key pinned; a publicly trusted relay is checked by the platform's certificate validation and its host name and never records this event. Each prefix is the first 8 bytes of its key hash, never a token. `sidekicks daemon status` names the refusal, and `sidekicks relay repin --force` accepts the new key ([Spec-027 §Interfaces And Contracts](./027-remote-control.md#interfaces-and-contracts)). | base + `{relayHost, pinnedSpkiPrefix, presentedSpkiPrefix}` |

### Voice

Voice stores no event type of its own. On a Claude Code session `/voice` is dictation into the composer; on a Codex session it is Codex's own realtime call. Both travel as calls and subscription frames on the `voice.*` wire — `voice.dictationStart`, `voice.dictationWrite`, `voice.dictationStop` and `voice.dictationSubscribe` for dictation; `voice.callStart`, `voice.callStop` and `voice.callSubscribe` for a call; `voice.voiceList` for Codex's voices — and none of them is appended to the log. The words a person dictates reach the log only as the ordinary `user.message` they send. On a Codex call, what the call hears of the person is recorded as their `user.message` when Codex sends `thread/realtime/transcript/done {role: "user"}`, and the voice's answer, `transcript/done {role: "assistant"}`, as an `assistant.message`, each carrying `origin: 'voice'`; the answer draws under the spoken message in the flow's quiet style, and a later call in the session starts with that spoken exchange, read from these records, as `initialItems`. The Codex driver routes the other `thread/realtime/*` notifications by `threadId` to the call's subscription and persists none of them, and a session's call minutes count on its `Voice` cost row ([Spec-004](./004-provider-driver-contract-and-capabilities.md)).

### Daemon-Scope Event Binding

Not every event describes activity inside a session. Some describe the **daemon process itself** — its security posture and its event-stream maintenance. These **daemon-scope** events carry no real session context, yet every `session_events` row needs a `session_id` to partition its sequence.

**Binding rule (event-level).** An event is emitted with `session_id` set to the reserved sentinel **iff it has no single owning session** — either because its payload carries no real session context (**daemon-scope**), or because it spans a user's entire cross-session footprint and so has no one owning session (**user-scope**; the sessions it touches, when it names them, live in the payload, never in the `session_id`). The discriminator is the event, not the category — a category may contain both shapes. The sentinel-bound set is:

- every `security_events` type — `relay.pin_refused`;
- every `event_maintenance` type — `event.compacted`, `backup.completed`, `backup.failed`, `backup.restored`;
- `usage.rate_limit_update` (category `usage_telemetry`) — an account-scoped provider-quota snapshot spanning every session the account's runs touch, so it has no single owning session; the other `usage_telemetry` types carry the real `sessionId` of the run or session they meter;
- the `mcp_governance` type `mcp.server_oauth_completed` — a server's sign-in, with no single owning session (a session-scoped initiator lives in the payload as `initiatingSessionId?`, never in the row's `session_id`) ([§MCP Governance](#mcp-governance-mcp_governance); [Spec-024](./024-mcp-server-configuration-and-governance.md)).

**Sentinel constant.** The sentinel is the RFC 9562 §5.10 **Max UUID** `ffffffff-ffff-ffff-ffff-ffffffffffff`, applied uniformly across **all** daemon-scope bindings. Its rationale (admissibility under the branded-id validator on the wire path, deliberate disjointness from the `gen_random_uuid()` v4 id space, FK-free admissibility in the `TEXT NOT NULL` local `session_id`) is detailed in [§Security Events](#security-events-security_events).

## Event Compaction Policy

Background compaction is lossless to the product. Background work may compress, repack, archive, move large bodies and rewrite indexes, and only when the transcript's order, its system messages, its tool rows and the output no deletion removed, message identities and times, and the kept undo and fork anchors all survive. Nothing that runs in the background removes anything a person could see, and nothing picks rows to destroy by count, age or size.

One service scheduler runs every background job, each with a cadence, a condition and a budget, and never runs two at once ([Spec-006 §Required Behavior](./006-local-ipc-and-daemon-control.md#required-behavior)). Of its jobs, this one touches the event store:

| Job | Cadence | Runs when | What it does |
| --- | --- | --- | --- |
| Repack the file | After each `Delete old data` | No turn running | Runs `wal_checkpoint(TRUNCATE)`, then `VACUUM`, measured before and after as `page_count × page_size` and `freelist_count` |

**The only deletion is the person's.** A session's events are deleted only by `Delete old data` (`daemon.retentionPurge`), which removes chosen archived or closed sessions whole. For each session it removes, it deletes the session's rows with SQLite's `secure_delete` on, so the freed pages hold nothing readable, checkpoints the write-ahead log with `TRUNCATE` once the delete commits ([Spec-020 §Ordering And Atomicity](./020-data-retention-and-gdpr.md#ordering-and-atomicity)), and records one `event.compacted` receipt on the sentinel session.

**Large bodies shrink at write time.** A body of 1 KiB or more is compressed with raw deflate at level 6 before it is written, the encoding recorded in the payload ([§Assistant Output](#assistant-output-assistant_output)); nothing rewrites a body afterward.

### Retention Windows

| Retention Class | Retained |
| --- | --- |
| Full event payloads | Until the person deletes the session (`Delete old data`), which deletes them with it |
| Reasoning content | Whole, for as long as the session is kept; it goes with its session |

**A kept session keeps its data.** Nothing expires a session's events by age, count or size: a session holds its full payloads, its personal data and its reasoning until the person deletes it, and deletion takes whole sessions. [Spec-020 §Data Retention and Deletion Policy](./020-data-retention-and-gdpr.md#data-retention-and-deletion-policy) owns the retention rules for personal data.

## State And Data Implications

- Canonical events are the source of truth for rebuilds and audit.
- Read projections may be rebuilt from canonical events.
- Command receipts or equivalent idempotency markers are required so a retried side-effecting command returns the saved result.

## Example Flows

- `Example: A run starts, emits tool activity, requests approval, publishes an artifact, and completes. Each change becomes a canonical session event with causation and actor metadata.`
- `Example: A user reconnects after missing events and requests catch-up after the last acknowledged session sequence.`

## Implementation Notes

- Keep the event taxonomy stable and additive; avoid repurposing old types with new semantics.
- Treat provider-native diagnostic events as separate from canonical business events unless they are normalized.
- A projection rebuild must be safe both for the person's audit reads and for user-facing transcript projections.

## Pitfalls To Avoid

- Using final assistant text as the only historical source
- Mutating or deleting canonical events in normal operation
- Leaving approval or intervention decisions out of the audit log

## Acceptance Criteria

- [ ] Every run lifecycle transition results in one or more canonical session events.
- [ ] A client can recover missed state by catching up from its last known cursor.
- [ ] Approval and artifact changes stay whole in a kept session's log: background work never removes them, and only deleting the session removes them.

## Design Decisions

- Session sequence numbers are assigned by the authoritative session-visible append path at write time. Projection merge must preserve those numbers and must not invent them later.
