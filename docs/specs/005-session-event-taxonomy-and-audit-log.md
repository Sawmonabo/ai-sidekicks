## Purpose

Define the canonical event envelope and taxonomy used for replay, audit, and live projections.

## Scope

This spec covers event categories, required event fields, ordering, replay, and audit retention requirements.

## Non-Goals

- Full UI rendering rules for the timeline
- Metrics-only observability details
- Storage engine implementation details

## Required Behavior

- Every durable session-relevant change must emit a canonical event.
- Canonical events must include at least `eventId`, `sessionId`, `sequence`, `occurredAt`, `category`, `type`, `actor`, and correlation or causation metadata where applicable.
- The taxonomy must cover at least:
  - session lifecycle
  - agent lifecycle
  - run lifecycle
  - queue and intervention
  - approval requests and resolutions
  - repo, workspace, and worktree lifecycle
  - artifact and diff publication
- Events must be immutable after append.
- Ordering is **per-aggregate, not global**: within a single run, event order is preserved, and tool events pair by `toolCallId` (the canonical Tool Activity **payload** field — `payload.toolCallId`; provider-native tool-call identifiers such as `tool_use_id` normalize into it); **no global causal-order guarantee exists across aggregates** — consumers MUST NOT infer cross-aggregate causality from interleaved positions across runs or sessions. The ingest-side bounded reorder buffer's parameters (bound, overflow = flush-in-arrival-order + diagnostic, pairing timeout) are the consuming plan's to name; this spec fixes only the guarantee's scope.
- Replay must support reading after a known cursor and reading bounded windows.

## Default Behavior

- Canonical event metadata is retained indefinitely unless an explicit retention policy supersedes it.
- Per-session event ordering is presented as a monotonically increasing sequence in session projections.
- Background work never removes anything the transcript draws. It may compress, repack, archive, move large bodies and rewrite indexes, and only when the transcript's order, its system messages, its tool rows and output, message identities and times, and the kept undo and fork anchors all survive. A session's events are deleted only when the person deletes the session, whole sessions at a time, and the audit stubs that deletion leaves preserve type, actor, timestamps, and provenance (§Event Compaction Policy).

## Fallback Behavior

- If a client detects a live-stream gap, it must rehydrate from the canonical event log starting after the last acknowledged sequence.
- If a row's full payload was replaced by an audit stub when its session was deleted, the system must still return that audit-visible stub rather than pretending the event never existed.
- If a producer cannot emit a canonical event immediately, the related state change must not be considered committed.

## Interfaces And Contracts

- `EventEnvelope` must be versioned.
- `EventReadAfterCursor` must return ordered events plus next replay cursor.
- `EventReadWindow` must support bounded historical windows for replay and inspection.
- `EventSubscription` must expose live append-only delivery together with replay catch-up semantics. The screen's session stream (`session.subscribe`) is that replay followed by the live tail, batched by the daemon into one frame per 16 ms or per 50 events, whichever comes first, each frame carrying only changes, each with its cursor. The daemon never waits for a screen: a screen that falls behind is dropped for and told so on the next frame that fits, and repairs itself from the log by cursor. When a screen that fell behind has caught up on its queue, the daemon sends it one frame with no changes, carrying the drop mark and the newest cursor, so a session that goes quiet right after a drop still tells the screen it is behind.

### EventEnvelope Version Semantics

Full semantics of the `.version` field are specified in [ADR-018: Cross-Version Compatibility](../decisions/018-cross-version-compatibility.md). The binding contract summary:

> **Terminology note — "version stub" vs. "audit stub":** This section uses "**version stub**" for the receiver-side artifact produced when an unknown-type event is preserved verbatim (full canonical bytes retained so the Ed25519 signature stays verifiable). This is structurally distinct from the "audit stub" a session's deletion writes (§Event Compaction Policy below), which removes `payload`, `correlationId`, and `causationId` and replaces them with a `summary`. A version stub retains all canonical fields; an audit stub does not. A version stub is stubbed only once it has been re-interpreted at least once, per [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #11.

- **Format:** Semver string `"MAJOR.MINOR"` (no PATCH component on the wire). Integer form is not used.
- **Producer sets it:** The emitting daemon writes its own outgoing wire version at emit time. `.version` is never copied from a received event. Version stubs record their original received version in version-stub metadata, separate from `.version`.
- **Validation is two-sided:** The control plane validates at write time; receiving peers validate on parse. A receiver that cannot interpret a given `.version` MUST persist the event as a version stub rather than drop or crash.
- **Unknown MAJOR (same or higher than receiver's supported MAJOR):** Persist as version stub with full original canonical bytes; never dispatched to application handlers. The canonical row's `.version` field stays the producer's original — version-stubbing is a read-side behavior, not a rewrite. On upgrade, the upcaster chain transforms the stub to a typed event at dispatch time; the log row is never rewritten.
- **Unknown MINOR (same MAJOR, higher MINOR):** Event dispatches normally; unknown optional fields and unknown enum values within the payload are preserved verbatim for future upcasting. MINOR bumps MUST be additive-only per ADR-018.
- **Version range at the connection handshake, never at join or write:** An app outside its service's version range is refused once, at the connection handshake: the service answers with `DaemonHelloAck { compatible: false, reason }`, `reason` being `version.floor_exceeded` (the app is older than the service accepts) or `version.ceiling_exceeded` (the app is newer than the service knows), and the app draws that machine read-only and names the side that is behind. A session carries no version floor of its own, and no write, join or envelope read carries a typed version error ([ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #3, #4, #10).
- **Immutability:** `.version` is set once at producer emit time and is part of the event's durable identity. It is never rewritten by upcasters, version-stub re-interpretation, or upgrade processes. This is load-bearing for the §Integrity Protocol hash-chain and signature invariants — the signed bytes include `.version`, so rewriting it would break all downstream verification.
- **Envelope version vs. event-type registry:** `.version` governs the envelope contract only. New event-type introductions are additive and MAY be allowed under the same envelope version if they follow the additive-only MINOR rule. V1 uses an accept-and-stub model for unknown types (each unknown type becomes a version stub on receipt); the event union in `packages/contracts` is the registry, and no central event-type registry exists, because the app talks only to its own service version and the one before it.

## Event Type Enumeration

This section enumerates every individual event type within each `EventCategory`. Each type is a string value for the `type` field of `EventEnvelope`. The payload fields listed are the category-specific fields carried inside the `payload` object; the envelope-level fields (`id`, `sessionId`, `sequence`, `occurredAt`, `category`, `actor`, `correlationId`, `causationId`, `version`) are always present and are not repeated here. One **cross-cutting payload field pair** spans categories (the epoch-attribution carrier whose typed shape [Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) delegates to this spec): `sourceEpoch?` — a nonnegative integer naming the **pre-rollback execution epoch** a late-appended **non-lifecycle** row is attributed to — with its companion `sourcePosition?` — a nonnegative integer naming the **normalized session position** (the turn-boundary vocabulary of `run.rolled_back`'s `targetPosition`, §Run Lifecycle) that row occupies within its source epoch, registered because no run-scoped family's payload carries a native position key and the supersede cutoff (`turn > targetPosition`) cannot rank a late row against its epoch's surviving prefix without one — stamped **together** at ingestion by the run-engine's late-append leg (Plan-003 T3.11) — the pair from the straggler's **per-event operation association**, each provider-side operation recorded against the (epoch, turn) current when it opened, pre-fence (an association-less pre-epoch straggler falls back to the closed delivery generation's retained pair, a conservative always-superseding upper bound — [Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior)'s fence and generation-rotation semantics own the mechanics) — exactly when that cursor attributes the row to a superseded epoch (the atomic closed-pair `driver_ask.requested` + `driver_ask.canceled` late-append included), and absent on every current-epoch row — absence means current-epoch, the pair travels together with the row's `runId` (a stamped payload REQUIREs all three — the pairing rule below), and the stamp is never fabricated at read time. The field is admitted by the payload schemas of exactly the run-scoped families that late-append window covers — `assistant_output`, `tool_activity`, `usage_telemetry`, `artifact_publication`, and the `interactive_request` closed pair — and by no others (a `run_lifecycle` straggler is absorbed, never appended; non-run-scoped families carry no run epoch): every canonical `SessionEventSchema` payload branch of those five families **whose variant is run-scoped** — the payload carries `runId` — MUST admit the optional pair via the Plan-005 T1.9 composition helper, whose pairing refinement is schema-enforced (either stamp key present ⇒ both present and `runId` present), so a stamped row validates through the canonical read path and is never rejected at subscription or replay validation; variants without run attribution never admit it — the account-plane sentinel-bound `usage.rate_limit_update` (no `runId` — §Usage Telemetry) foremost — because an epoch stamp on a row with no run identity is unattributable by construction. The field lives inside `payload`, so it sits in the §Canonical Serialization Rules canonical bytes — signed and hash-chained like any payload field, with **no envelope-level field added** (the canonical-set membership is unchanged) and no version bump: the pair sits before [ADR-018 §Reversibility Assessment](../decisions/018-cross-version-compatibility.md#reversibility-assessment)'s point of no return, which is an **emission event, not a code merge** — the project is pre-first-release with no production deployment, so no `"1.0"` envelope has been emitted outside a test environment — so the pair is part of the v1.0 baseline payload contract from first emit, as the other baseline payload fields are (`executionPosture`, the terminal keys); the same fields added after that point would be a MINOR envelope bump per [ADR-018 §Decision](../decisions/018-cross-version-compatibility.md#decision) #8's new-optional-field rule composed with §EventEnvelope Version Semantics' higher-MINOR preservation, and [Plan-005](../plans/005-session-event-taxonomy-and-audit-log.md) carries the matching conditional: crossed before it ships, the implementer takes the `"1.1"` bump with producer and golden-vector updates — and replays durably: the [Spec-003 §Driver-Level Rollback Mechanics](003-queue-steer-pause-resume.md#driver-level-rollback-mechanics) supersede projection consumes it for cross-epoch keying, and the audit stub a session's deletion writes preserves it (§Compacted Event Format). Execution-epoch semantics — `0` before any rollback, advancing with each **accepted `run.rolled_back`** (a confirmed conversation rewind, regardless of the file-leg disposition) — are owned by [Spec-003 §Required Behavior](003-queue-steer-pause-resume.md#required-behavior) and [Run State Machine §Invariants](../domain/run-state-machine.md#invariants), not redefined here; the typed Zod shapes (`SourceEpochSchema` / `SourcePositionSchema`, the `SOURCE_EPOCH_PAYLOAD_KEY` / `SOURCE_POSITION_PAYLOAD_KEY` consts, and the pairing-refinement composition helper) are [Plan-005](../plans/005-session-event-taxonomy-and-audit-log.md) T1.9's, in `packages/contracts/src/event.ts`, mirrored in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md).

### Session Lifecycle (`session_lifecycle`)

Payload shape: `{sessionId, previousState?, newState, actor?}`; the goal events carry per-type payloads — `session.goal_updated` carries the goal and its status (`{sessionId, agentId, goal, status, reason?, actor}` — a goal is a command sent to one agent, never what the session is, so `agentId` names the agent it was sent to; `goal` is the condition that agent works toward, whose exact shape is owned by the [Spec-014 §Session Goals](014-multi-agent-orchestration.md#session-goals) contract, and the event carries the same canonical value the accepted `session.goalUpdate` supplied, so RPC and durable event serialize identically; `status` is a union — `active`, `paused`, `blocked`, `usage-limited`, `budget-limited`, `complete`, `impossible` — whose `complete` and `impossible` members are final; `reason` carries the provider's own reason where it gives one, and `impossible`, which only Claude Code sends, always carries it), `session.goal_cleared` ends a goal and carries none (`{sessionId, agentId, actor}`; clearing is the distinct operation and never a status, so an update without a goal is malformed rather than an implicit clear). Each goal change is drawn only as one transcript system message; no goal text is ever put into a system prompt. A goal change is not a state transition. `session.created` carries a per-type payload of its own, because a session has exactly one main agent and that agent is born with the session rather than joined to it later: `{sessionId, mainAgent: {agentId, definitionId?, name, driverName, modelId, providerAccountId, effort?, executionPostureMode?, toolAllowlist?, instructions?, goal?, state}, actor?}`. Every member of `mainAgent` is a value the **daemon** resolved when it started the session — the binding it resolved (driver, model, provider account, effort), the four axes the daemon itself reads (posture mode, tool allowlist, instructions, goal), `definitionId` where a saved agent definition was named ([Spec-027 §Resolution when a run starts](./027-agent-definitions-and-peer-invocation.md#resolution-when-a-run-starts)), and the resolved agent `state` — and the event carries the same resolved values the session-create reply echoes, so wire and durable record serialize identically, exactly as the goal events do. This is the **creating record** of that agent's row in the `agents` projection ([Spec-014 §Interfaces And Contracts](014-multi-agent-orchestration.md#interfaces-and-contracts)): no attach event exists, so the `agent.*` types of §Agent Lifecycle only ever mutate a row this payload brought into being, and a projector that ignored it could not rebuild one.

### Agent Lifecycle (`session_lifecycle`)

Payload shapes are per-type, because one shared shape could not rebuild the `agents` projection on replay. A switch of an agent's provider binding appends nothing when it is accepted. The pending switch is written to the agent row's own pending slot before the acknowledgment returns, and `agent.list` reads it back as `pendingSwitch` in the same `AgentBindingSwitchPending` shape the mutation's response returns ([Spec-014 §Same-Agent Provider Switch](./014-multi-agent-orchestration.md#same-agent-provider-switch)). No event records the pending switch, so no projector can read one as a change of binding before it lands. The effective move is written by the **terminal**: `agent.provider_binding_changed` carries the `to` binding and clears the slot, `agent.provider_binding_change_failed` clears the slot and leaves the columns untouched. So a switch appends exactly one event, at settlement, and the `agents` binding columns stay rebuildable from the log alone. `agent.provider_binding_changed` carries the session, the agent, `switchId`, `actor`, `from` and `to` — each a whole `AgentProviderBinding` `{driverName, modelId, providerAccountId, effort, outputSpeed?}`, where a `providerAccountId` of `null` means the binding follows the provider's current account — the account the run landed on, as a member of its own, `continuity: 'in_place' | 'resumed' | 'brief' | 'replayed'`, `declaredLosses: DeclaredLossKind[]`, and `turnContinued`. Whole bindings on both sides are what keep the log complete on replay: the terminal writes the effective columns, so a settled member the log could not rebuild — the output speed among them — would leave its column NULL on replay while the pending slot had already been cleared. **The account the run landed on is recorded apart from the binding's own account.** A change of driver ends the run and starts a new one on the new provider's current account, so the account the agent row carries does move; keeping the landed account beside `to.providerAccountId` rather than writing it into it means an agent that follows the current account is never silently pinned to the account it happened to land on. Moving an account on purpose is `providerAccount.setCurrent` on the provider surface; `agent.configUpdate` never asks for one. `turnContinued` is `true` only on the resume-path fallback, where a `continue` is sent to carry the interrupted turn on. A change of model, effort or speed alone settles in place (`continuity: 'in_place'`) and the screen draws no row for it: a row is drawn only for a provider or an account switch. The `to` binding records the value the switch **requested and committed**, which is that column's own content; what the new binding's provider then **declared** is a live reading and is deliberately not evented, an observation captured once being a second and staler record of a fact the running session already holds ([Spec-004 §The output-speed axis](./004-provider-driver-contract-and-capabilities.md#the-output-speed-axis)). `switchId` is the daemon-minted correlator the mutation's response carried — as the pending acknowledgment's id on the deferred arm, as the settlement's own id on the immediate one — so a client that was told a switch was coming can match it to the terminal that settled it. `continuity` is closed at four values and is the wire's honest-degrade discriminator, naming which of four different acts carried the conversation rather than degrees of one: `'in_place'` where a per-turn-override axis was carried into the next turn on the **running** process, nothing respawned and nothing reconstituted; `'resumed'` where a fresh process of the **same** provider reopened its **own** conversation under the provider's own identifier, so the conversation arrived whole; `'brief'` where a **different** provider was started from a hand-over brief — the old provider's own summary taken on a throwaway copy of the session, with a reference to the whole old transcript written beside it as one plain file the new provider reads on demand; and `'replayed'` where a same-provider reopen did not load and the canonical transcript was sent as text instead, which restarts the conversation rather than continuing it ([Spec-004 §Canonical Transcript Export And Replay](./004-provider-driver-contract-and-capabilities.md#canonical-transcript-export-and-replay)). `'in_place'` and `'resumed'` are `applied`; `'brief'` and `'replayed'` are `degraded`, and neither is rendered as an ordinary success. `declaredLosses` is a **closed vocabulary, not free text** — V1 members `'provider_private_reasoning'`, `'context_truncated'`, `'tool_call_history_repaired'`, `'conversation_history_summarized'`, `'conversation_history_restarted'`, `'helper_conversations'`, `'tool_output_bodies'`, `'live_tool_calls'`, `'provider_skill_and_command_names'`, `'turn_content_unavailable'`, `'turn_content_truncated'`, enumerated in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), which is where the union lives — and it is **required**, because an empty array is the positive assertion that nothing was dropped and an absent one would be indistinguishable from a driver that did not know. Requiredness is **arm-scoped** so that assertion keeps its meaning: `'in_place'` and `'resumed'` carry the empty array by rule, nothing having been reconstituted on either; `'brief'` MUST be non-empty and MUST include `'conversation_history_summarized'` together with `'provider_private_reasoning'`; and `'replayed'` MUST be non-empty and MUST include `'conversation_history_restarted'`, since a fallback that restarts the conversation and claimed no loss would be claiming the restart was free. The sixth member, **`'turn_content_truncated'`**, is the second produced at pipeline step 1 (Fold) and the sibling of `'turn_content_unavailable'`: where that member names a logged turn whose body could not be **read**, this one names a logged turn whose body was **stored as a prefix** because it exceeded `CONTENT_PAYLOAD_PLAINTEXT_MAX` at append. It is minted rather than folded into `'context_truncated'`, whose own scope is the hand-over brief's verbatim budget evicting whole exchanges and never halves — reusing it for a halved body would contradict the member it borrowed. It is likewise not `'turn_content_unavailable'`: a truncated turn **is** available, and reporting it unavailable would overstate the loss as surely as silence would understate it. Declaring it is [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md)'s declared-loss principle applied at the operation that drops the bytes; the prefix replays, and the reader is told it is a prefix. The `from` binding is the daemon's record of the binding being left, so the event is self-contained on replay and a reader never has to fold backwards to learn what changed. `agent.provider_binding_change_failed` carries the session, the agent, `switchId`, `actor`, `from`, `attempted` (the binding asked for, its account included), `reason: 'driver_unavailable' | 'model_unavailable' | 'effort_unavailable' | 'output_speed_unavailable' | 'interrupt_refused' | 'target_unstartable' | 'account_unavailable'`, and, with `account_unavailable`, `accountState: 'reauth_required' | 'home_missing' | 'indeterminate' | 'not_registered'`, and is the **sibling terminal** of the type above, not a variant of it: an accepted switch is written to the pending slot on **both** arms, and the slot is cleared by a terminal rather than by a reply, so an application-time refusal that appended no event would leave the promise standing with no record of why it was not kept. It is therefore emitted on both arms — on the deferred one it is the only refusal that reaches anyone, the caller having since disconnected; on the immediate one it appends in addition to settling the held-open request as the `failed` disposition, because a reply is not a durable record and the projection cannot be rebuilt from one. It is never emitted under the success name, because an event whose name asserts a switch landed is the wrong record of one that did not. The `from` binding is unchanged by construction (a failed application moves nothing), `attempted` names what was asked for, its account included, so a switch that could not reach its account says which one. A switch that fails after it was accepted never lands: the previous binding and account stay active, the success row is not drawn, and the transcript gains one system message naming the attempted switch and its reason — `Switch to Codex failed · <reason>`, or `Switch to account <name> failed · login expired · Sign in again`, with `Sign in again` only when `accountState` is `reauth_required`. No banner, toast, dialog or standing error is raised. It deliberately does **not** reuse the `agent.provider_axis_invalid` `axis` discriminator (`driverName` | `modelId` | `effort` | `outputSpeed`, the request's own member names and the whole of the axis union), and the two vocabularies are separate because they answer different questions: that error code answers a caller synchronously about a request that was never accepted and names the field to correct, while this reason explains why an **accepted** switch could not be honoured at a boundary the caller is not watching — a set that must also carry `interrupt_refused`, `target_unstartable` and `account_unavailable`, none of which is a field of the request at all. One vocabulary spanning both would either drop those three arms or teach a client to render a fix-your-request hint for a failure no correction of the request would have avoided. A degraded settlement — a hand-over brief, or a fallback replay — is **not** a failure and never emits this type: it moved the agent and declared what came along, while this type means the agent did not move at all. A superseded pending switch emits neither terminal, by the [Spec-014 §Same-Agent Provider Switch](./014-multi-agent-orchestration.md#same-agent-provider-switch) supersession rule.

| Type | Description |
| --- | --- |
| `agent.provider_binding_changed` | A switch of an agent's provider binding — its provider, model, account, effort or output speed — landed, and the conversation was carried across. Its identity and run linkage are unchanged — this records a change of binding, never a new agent. A change of model, effort or speed alone settles in place, and the screen draws a row only for a provider or an account switch. |
| `agent.provider_binding_change_failed` | A switch accepted as pending could not be applied at its boundary, and the agent stayed on its previous binding and account. Emitted on **both** arms whenever an ACCEPTED switch fails at application: the pending slot is cleared by a terminal and never by a reply, so an immediate-arm failure emitting nothing would leave the promise standing with no record of why it was not kept — that arm additionally settles its held-open request as the `failed` disposition. The transcript gains one system message naming the attempted switch and its reason. A refusal reached BEFORE acceptance is a different thing entirely: it mints no `switchId`, writes no pending switch, and refuses synchronously with `agent.provider_axis_invalid`. Exactly one of this type and `agent.provider_binding_changed` terminates every pending switch that is not superseded. |

### Run Lifecycle (`run_lifecycle`)

One event per state from the [Run State Machine](../domain/run-state-machine.md)'s 10 canonical states, plus the forward (non-state) `run.rolled_back` event.

Payload shape: `{sessionId, runId, runVersion, previousState, newState, failureCategory?: RunFailureCategory, recoveryCondition?: RecoveryCondition ('recovery-needed' | 'reauth-required' — the named type in the API Payload Contracts mirror), recoverySpanClassification?: RecoverySpanClassification ('read_only' | 'idempotent_write' | 'irreversible' | 'unclassifiable' — the halted/diverged span's content classification, named type in the same contracts mirror; semantics per Spec-013 §Fallback Behavior: audit metadata in V1, 'unclassifiable' handled exactly as 'irreversible'), trigger?: 'turn_limit' | 'budget_exhausted' | 'idle_timeout' (the canonical union matching the `run.interrupted` per-type row below and the api-payload §Plan-003 mirror), completionKind?: 'turn' | 'task', intendedClose?: true, executionPosture?: ExecutionPosture}` — this state-transition shape governs the ten state events; `executionPosture?` (structural shape per the typed `RunStateChangeEvent.executionPosture?` mirror in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) — the canonical in-corpus shape source; policy semantics per [Spec-010](./010-approvals-permissions-and-trust-boundaries.md)) is stamped only on `run.running` — the post-setup-gate spawn-success transition (Plan-003's gate seam admits `queued → starting`, then setup gates — Plan-008's execution-root gate among them — run **before** `driver.startRun`, so the resolved workspace root and effective posture are final only when `running` fires; a `run.starting` stamp would be premature) — recording the run's effective posture for audit, and is absent on every other transition (the audit-stub projection preserves `executionPosture` — and `credentialPolicyRef`, which every posture-bearing row carries per Spec-010 — on posture-bearing `run.running` rows, §Compacted Event Format, so the boundary stays reconstructable after compaction); `run.rolled_back` is per-type (see its row) and carries no `previousState`/`newState`.

`runVersion` is the run aggregate's **any-run-progression counter** (Plan-003 D-003-1): it increments on every run progression — applied interventions included, not only the state transitions enumerated below — and is the optimistic-concurrency token the `expectedRunVersion` intervention guard compares against ([Spec-003 §Interfaces And Contracts](003-queue-steer-pause-resume.md#interfaces-and-contracts)). It is a **payload** field, distinct from the envelope-level `.version` (§EventEnvelope Version Semantics above): `.version` is the immutable semver wire-contract version bound into the Ed25519 signature, whereas `runVersion` is a mutable per-run counter carried inside `payload` — the two share the word "version" but are different contracts and must never be conflated. Because `runVersion` also advances on applied interventions that cause no state change (e.g. a native steer), the authoritative source of a run's current `runVersion` is the run-state read / `run.subscribeState` stream and the intervention / pause / resume responses, not the `run.*` event sequence alone. A no-state-change advance with **no per-type event of its own** (the native-steer case) is **not** broadcast as a discrete `run.*` event — there is no state transition to record ([Spec-003 §Driver-Level Steer Mechanics](003-queue-steer-pause-resume.md#driver-level-steer-mechanics)); the carved-out exception is the in-place rollback from `paused`, which also transitions no state but whose per-type `run.rolled_back` event (its row below) streams the fresh post-rollback `runVersion` — so a _non-intervening_ subscriber tracking `runVersion` off the event sequence may hold a stale comparand after a steer-like advance. Its next guarded intervention / pause / resume is then correctly rejected `expired` (the comparand genuinely _is_ stale — this is the optimistic-concurrency guard working, not a false rejection), whereupon it re-reads run-state for the fresh `runVersion` and retries: the reject → re-read → retry loop is the designed correction, and V1 adds **no** broadcast/read-model push for such no-per-type-event bumps. The _intervening_ caller never round-trips — its `RunControlAck` / `InterventionRequestResponse` / pause-resume ack carries the post-application `runVersion` directly (per [api-payload-contracts.md](../architecture/contracts/api-payload-contracts.md)).

**At-most-once terminal emission.** For the three terminal types (`run.completed` / `run.interrupted` / `run.failed`), at most one terminal `run_lifecycle` event exists per `(runId, runVersion)`. The emitter owns the guarantee: the terminal guard + state swap + append execute under the per-session append lock with read-your-writes state, so a duplicate terminal attempt is rejected before append. A schema-level **partial unique index backstops** the emitter contract — `UNIQUE` on (`json_extract(payload, '$.runId')`, `json_extract(payload, '$.runVersion')`) `WHERE category = 'run_lifecycle' AND type IN ('run.completed', 'run.interrupted', 'run.failed')`, predicated on `session_events`'s real scalar `category` + `type` columns ([local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md)) — as a **fail-loud invariant detector**: an index violation surfaces a bug, never silently no-ops (an append-if-absent API remains rejected). The schema mirror ([local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md)) carries the index DDL beside the projection-level CHECK below. Terminal payloads MUST carry non-null `runId` and `runVersion` (an emitter precondition, mirrored as that same projection-level CHECK): SQLite UNIQUE indexes treat NULLs as distinct, so a NULL key would silently bypass the backstop for exactly the malformed rows it exists to catch. The same NULL-bypass would reopen when a session's deletion stubs the row — §Event Compaction Policy replaces `payload` with the audit-stub projection — so the stub projection for terminal `run_lifecycle` rows MUST preserve `runId` + `runVersion`, keeping the index keyed for the row's whole retention life.

**Intended-close discriminator.** A daemon-initiated `closeSession` produces a clean terminal: the terminal payload carries `intendedClose: true`, and consumers MUST NOT classify such a terminal as a crash. The field is absent on every other terminal path (natural completion, user cancel, failure), so its presence is the discriminator — orderly shutdown stays distinguishable from abnormal termination in the durable record.

#### Driver Ask Events

Provider-initiated permission asks — the third `interactive_request` subfamily beside queue items and interventions: the provider CLI, mid-run, asks the person whether it may act. Payload shape: `{sessionId, runId, askId, toolName?, prompt?, input, state: 'requested' | 'responded' | 'canceled'}` — the payload MUST carry `input` (the normalized requested resource — command / path / tool arguments — the approval decision is about, so two same-tool asks are always distinguishable in audit). **An ask carries no deadline and never expires**: it stands until it is answered, and the only things that end one are the answer itself, an interrupt of the run, and the provider process ending, the last two arriving as `driver_ask.canceled`. A move to a permission level that never asks is an answer, not an end: it answers an open permission ask as allowed, recorded as `driver_ask.responded`, and the blocked row runs. `state` is the closed `DriverAskState` enum and MUST equal the emitting event type's suffix (denormalized so latest-row projections read one field; a mismatch is an emitter bug and fails loud, never repairs silently); A driver ask is Claude Code's `can_use_tool` control request for any tool but its question tool, or one of Codex's approval requests, and it routes into the approval pipeline. A structured question — Claude Code's question tool, Codex's `item/tool/requestUserInput`, or a tool server's question (an MCP elicitation) — is not a driver ask: it becomes the question record of §An Agent's Question.

| Type | Description |
| --- | --- |
| `driver_ask.requested` | The provider has asked mid-run for permission to act. |
| `driver_ask.responded` | A user (or policy) answered the ask and the response was delivered to the provider. Payload additionally carries `{response}` — the delivered permission decision — so replay and audit can reconstruct what unblocked the run. |
| `driver_ask.canceled` | The ask was withdrawn — the provider retracted it, the run was interrupted, the run ended first, the session closed first ([Plan-010](../plans/010-approvals-permissions-and-trust-boundaries.md)'s sweep), an undo (`session.restore`) cut the turn that raised it ([Spec-003 §Required Behavior](./003-queue-steer-pause-resume.md#required-behavior)), or the resume position-compare halted the run for reconciliation, settling the superseded ask as moot ([Spec-013 §Fallback Behavior](./013-persistence-recovery-and-replay.md#fallback-behavior)). |

#### User Message Events

The durable user-message row — the fourth `interactive_request` subfamily beside queue items, interventions, and driver asks: a user's message into the session becomes first-class timeline history, not merely queue metadata. Emission is owned by the **queue-submit surface** ([Plan-003](../plans/003-queue-steer-pause-resume.md)): the accepting daemon appends the row when it accepts the send. The `user_text` wire echo from the provider **correlates** into this row via `correlationId` as delivery confirmation — the echo never appends a second row. Payload shape: `{sessionId, queueItemId?, runId?, actor, deviceId?, message}` — `message` is the user-authored text (PII-bearing at this call site; the call-site splitter routes it through `pii_payload`), and `deviceId` is the device the message was sent from, verified at append against that device's signature and present wherever one of the person's devices sent it; the transcript draws no device mark ([Spec-028 §Answering from another device](./028-remote-control.md#answering-from-another-device)). The answer to an agent's question is written as this row (§An Agent's Question), so it names the device that answered.

| Type | Description |
| --- | --- |
| `user.message` | A user message was accepted into the session. The provider-side `user_text` echo correlates into this row as delivery confirmation; audit and replay reconstruct the human side of the conversation from these rows. |

#### An Agent's Question

The fifth `interactive_request` subfamily: an agent stops mid-turn to ask the person something, and the daemon turns either provider's held request — a Claude Code question request, a Codex user-input request — into **one** record the screen renders; a tool server's question (an MCP elicitation) becomes the same record, the server named where the agent's short header stands. Payload shape: `{sessionId, runId, questionId, pageCount, questions: [{header?, text, heading?, options: [{label, description?, preview?}], severalAnswers, secret}]}` — `pageCount` is how many questions the record carries and `questions` carries them all, so paging through them needs no second read and typed text survives paging in both directions; `header` is the agent's own short label for the ask and `heading` its own summary line, each present only where the provider sent one; `preview` is present only where the provider attached one to an option, which one provider does and the other does not; `severalAnswers` is the provider's own reading of whether a question takes more than one answer, never a console default; and `secret` marks a question answered into a masked field, whose value is **never stored** — it reaches no event payload, no artifact and no projection.

**A question is held open with no timer.** It stands until it is answered, is rebuilt on a reload and on the person's other devices, and the first answer settles it everywhere. One call answers every page, carrying per question exactly one of: the labels picked, typed text, the secret, or a skip. The person's turn is then written as an ordinary `user.message` row with the secret masked, so the answer is in the conversation where a reader expects it rather than in a second record. A provider's **non-waiting** question is not this record at all: it is the message item it already is, answered as an ordinary message.

| Type | Description |
| --- | --- |
| `question.asked` | An agent asked the person one or more questions mid-turn, and the record the screen renders was created. |

The Codex driver's event normalizer maps only these Codex signals to it: a `guardianWarning` (`signal: "review_warning"`), which it pairs with the review Codex completes right after it and records for no warning that reports an approval or that is about an action the reviewer blocked, whose words land on that action's own row (`approval.reviewer_denied`); and an `autoApprovalReview/strictReviewRequired` (`signal: "review_required"`). Codex's `turn/moderationMetadata`, a display hint with no words, is never this event and stays in the daemon's log. **An approval waits until it is answered.** No approval request carries a deadline and none expires: the card stands until the person answers it, until the run it blocks is interrupted, or until the provider process ends — the last two arriving as `approval.canceled`. Moving the session to a permission level that never asks answers an open card as allowed, recorded as `approval.approved`, and its blocked row runs; a later ask at that level raises no card, and moving back to a level that asks asks again.

**The plan record and its outcome.** A plan turn ends with a held provider request on one leg and a completed plan item on the other, and the daemon turns either into **one** plan record the screen renders and one call answers — a plan card being an attention entry exactly as an approval is, which is why the three types live in this category rather than in one of their own. `plan.proposed` carries `{sessionId, runId, planId, title, text, stepCount, fileCount, planFilePath?}`: `title` is the plan's first heading and `text` its prose as the agent wrote it, taken from the held request or the plan item and never read off the disk; the two counts are the daemon's own reading of the plan — its top-level steps and the files it names — and are what the card's summary line states; `planFilePath` is present only where the provider wrote the plan as a file, which one provider does and the other does not, so its absence means there is no file rather than that the path is unknown. The verdict is one of three — `keep`, `build`, `fresh` — and only two of them append: `keep` appends nothing and leaves the provider in plan mode, a revised plan minting a new record; `build` appends `plan.accepted` `{sessionId, planId, deviceId}`, the run continuing in this session; and `fresh` appends `plan.handed_off` `{sessionId, planId, freshSessionId, deviceId}`, naming the session minted on the same project and worktree and seeded with the plan, the verdict itself carrying the provider and the level of the session to mint — the account is neither, a minted session running on its provider's current account the way every session does. Both outcome rows exist so the system messages survive a reload, and each names the device whose verdict landed (`deviceId`). The plan record is held open with no timer, is rebuilt on a reload and on the person's other devices, and the first verdict settles it everywhere.

### Assistant Output (`assistant_output`)

Payload shape: `{sessionId, runId, contentType?, contentLength?, contentTruncated?, contentCiphertextDigest?}`, with the message or reasoning **body itself** carried out-of-payload in `session_events.content_payload`.

**The body has a durable home, and it is not `payload`.** A row recording that an assistant spoke but not what it said would leave [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md)'s ruling that the canonical transcript is authoritative for the content of a provider session standing over a log holding none of it. The body lands in the [`session_events.content_payload`](../architecture/schemas/local-sqlite-schema.md) envelope: sealed AES-256-GCM under the **session**-scoped content key, excluded from the canonical bytes exactly as `pii_payload` is, and committed to by the `contentCiphertextDigest` member (BLAKE3 over the ciphertext) that the signed `payload` carries in its place — so the signature binds the body without carrying it and survives the body's destruction. This is the same Encrypt-Then-Digest-Then-Sign order the PII column runs, applied to a second, differently-keyed column rather than duplicated. A body of 1 KiB or more is compressed with raw deflate at level 6 before it is sealed, and the encoding is recorded in the signed payload; a smaller body is sealed as it is. Compression happens here, at write time, because sealed ciphertext does not compress and rewriting a sealed body would break the digest the signature binds.

**The decrypted body is a separate typed projection; it is never merged back into `payload`**. The payload shapes above deliberately declare **no** body member, and the `SessionEventSchema` variants that implement them are strict — which is what lets a driver normalizer resolve these types as envelope-constructible in the first place. A read path that spliced the decrypted body into `payload` would therefore have exactly three options, all wrong: add an undeclared key and fail strict validation, loosen the schema and give up the constructibility check, or change the apparent shape of bytes that have already been verified against a signature. Reading instead produces a **`HydratedSessionEvent`** — a distinct read-side type pairing the verified, unmutated event with a `content` member that is a closed two-arm union: an **available** arm carrying the plaintext body together with the `contentLength` and `contentTruncated` the payload already signed, or an **unavailable** arm carrying the reason (column NULL, key unavailable, digest unbound, or the row replaced by a stub when its session was deleted). The signed event and the hydrated view are two types precisely so that _signed_ and _hydrated_ can never be confused at a call site: the canonical transcript fold consumes the hydrated projection, while every integrity check continues to run over the untouched event. The unavailable arm is also where `'turn_content_unavailable'` gets its truth value, rather than a fold inferring loss from an absent key.

`contentType?` and `contentLength?` keep their meanings and become the _stub-surviving_ description of a body that now exists: `contentLength` is the body's **pre-truncation** UTF-8 byte length, so the audit stub a deleted session leaves still reports how much was said. `contentTruncated?` is present and `true` only on a row whose body exceeded `CONTENT_PAYLOAD_PLAINTEXT_MAX` and was stored as a codepoint-boundary prefix; absent means the stored body is complete. Both members are ordinary signed `payload` content and neither is a second copy of the prose.

| Type                        | Description                                                  |
| --------------------------- | ------------------------------------------------------------ |
| `assistant.message`         | The assistant has emitted a message to the session timeline. |
| `assistant.thinking_update` | The assistant has emitted a reasoning or thinking update.    |

> See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed payload definitions.

### Usage Telemetry (`usage_telemetry`)

Payload shape: `{sessionId, runId?, tokenCount?, inputTokens?, outputTokens?, cacheReadTokens?, cacheWriteTokens?, reasoningTokens?, providerAccountId?, credentialGeneration?, costUsdMicros?, windowUsedTokens?, windowMaxTokens?, windowSource?: 'provider_reported' | 'model_default' | 'estimated', exceeded?: boolean}` (`windowSource` + `exceeded` mirror context-window provenance); the shape also carries the wire-attribution carriers `modelId?: string` and `subagentId?: string` — populated by the driver normalizer when the provider attributes usage below run scope (per-model usage maps; subagent-scoped usage pairing on the (`runId`, `provider`, `subagentId`) triple), absent when the wire attributes only at run scope — so pricing keys a differently-modeled subagent's rows at its own model ([Spec-014 §Provider-Native Subagents](./014-multi-agent-orchestration.md#provider-native-subagents))). This shape governs the three metered update types (`usage.token_count`, `usage.cost_update`, `usage.context_window_update`) only — with per-type requiredness: `usage.cost_update` MUST set `costUsdMicros` and `effectivePrincipal` (`costUsdMicros` is the request's figure in integer micro-dollars, priced once when it completes and never repriced; a request held for a price carries it once a fetch prices it — [Spec-014 §Cost Derivation And Absent-Cost Semantics](./014-multi-agent-orchestration.md#cost-derivation-and-absent-cost-semantics)) and `usage.context_window_update` MUST set `windowSource` + `exceeded` (authoritative-vs-estimated provenance and the headroom signal Plan-014's budget consumers depend on) — and consumption of that signal is provenance-keyed: `estimated`- and `model_default`-grade headroom drives only reversible, soft responses, while any costly or irreversible action keyed on headroom requires `windowSource: 'provider_reported'` with both counts present — or the provider-reported `exceeded: true` terminal flag, per the carve-out below; `windowUsedTokens` / `windowMaxTokens` travel as a **pair** — an emitter sets both or neither (a lone numerator or denominator is an emitter bug; the pair is absent only where the wire genuinely supplies no counts, e.g. a bare provider exceeded signal), and a counts-absent update is a provenance/`exceeded`-only signal whose consumers treat headroom as **unknown** — the headroom projection yields no ratio, no soft threshold fires on unknown (never a fabricated denominator), and unknown never satisfies a hard-action predicate — with the driver-computed `exceeded` flag as the deliberate carve-out: `exceeded: true` at `windowSource: 'provider_reported'` is a first-class terminal fact consumed directly, not a ratio to derive, and it authorizes the protective hard responses (interrupting the affected run, refusing further admission) on its own, so a provider that reports its window exhausted without counts is never answered more weakly than one that reports counts; what unknown never satisfies is a ratio-derived predicate (thresholds, projections, buffer arithmetic); the normative consumer line and the advisory auto-compaction safeguard it feeds live in [Spec-014 §Budget Policies](./014-multi-agent-orchestration.md#budget-policies); `usage.budget_warning` is per-type (see its row: `{sessionId, runId?, agentId?, budgetType, limitValue, observedValue}`); `usage.rate_limit_update` is per-type — exactly `{provider, providerAccountId, credentialGeneration, limitId?, windowMins, usedPercent, resetsAt?}`, keyed `(providerAccountId, limitId)` (its row below carries both re-keys and the `limitId`-absent `default` rule), with no `sessionId` in the payload (session binding happens at the envelope via the node-scope sentinel per §Daemon-Scope Event Binding And Node-Scope Anchoring). **Turn-scoped effective principal.** The shared shape additionally carries `effectivePrincipal?: { kind: 'user', userId } | { kind: 'system' }` — the causing party for the turn the row meters, **required on `usage.cost_update`** and unused by the other two metered types. It is **daemon-resolved and neither wire- nor driver-supplied**, and it is bound **at turn dispatch rather than read at emission**: the run engine mints an immutable per-turn scope at each turn boundary and the driver normalizer stamps the row from the scope of the turn whose stream produced it, so a `usage.cost_update` for one turn that lands after the next has opened still carries the principal of the turn it meters. Reading a mutable "current turn" at emission would misattribute exactly the late rows the receipt most needs to be right about. The scope is resolved from the [Spec-003 §Required Behavior](./003-queue-steer-pause-resume.md#required-behavior) admitting-principal rows — the intervener for a turn opened by a steer or an edit-and-resend, otherwise the user who started the run, and the `system` arm where no user caused it (a scheduled sweep, an idle-timeout settlement, a daemon-initiated recovery turn). Recording it **on the metered row itself** rather than deriving it later by ordering the row against turn-boundary events is what the [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) §Authenticated Principal class rule requires, and it is what makes the attribution a recorded fact rather than one a reader reconstructs: every unit of spend carries exactly one key. The two arms are closed and the user reference is required exactly on the user arm and absent on the system arm — the same discriminator discipline the `interventions.origin` CHECK enforces in storage, expressed here by the union's shape, since a wire payload has no table to constrain. The receipt's stated degrade covers an unstamped turn: it attributes to the run starter and is never guessed. **Per-turn delta semantics.** The token members a `usage.token_count` row carries (`tokenCount`, `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens`, `reasoningTokens`) are **per-turn figures, never cumulative counters**: a run- or session-scope total is obtained by summation over that scope's rows, and no consumer differences one row against another. The emitter discipline that makes the fold sound is [Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior)'s usage-delta rule — the driver derives the per-turn figure from the provider's cumulative counters at its normalize boundary, so a cumulative reading never reaches this payload. The sum-fold consumer is the budget accountant ([Plan-014](../plans/014-multi-agent-orchestration.md)). **The account that paid, and the three counts a per-turn row could not otherwise carry.** `usage.token_count` additionally carries `providerAccountId` and `credentialGeneration` — the account the turn was charged to, and the credential generation observed with it, spelled exactly as the account-scoped `usage.rate_limit_update` below spells them — and `cacheReadTokens?` / `cacheWriteTokens?` / `reasoningTokens?` beside `inputTokens?` and `outputTokens?`. All five are additive-optional under [ADR-018](../decisions/018-cross-version-compatibility.md); the account pair is **required on emitters of this type** and unused by the other two metered types, while the three counts are present exactly where the provider's own per-turn carrier names them and absent otherwise — absent meaning the provider reported none, never zero. Without the pair a provider's figures silently pool every account registered for it, which is the failure the account axis exists to prevent; without the counts, three of the five token figures the per-turn usage projection reads have no source at all ([Spec-026 §State And Data Implications](026-provider-accounts-and-credential-homes.md#state-and-data-implications)). The account is **daemon-resolved and server-stamped** from the run's own admission record rather than from anything the wire reported, on the same rule `run.queued`'s `admittedProviderAccountId` follows: a provider reports tokens, never who is paying for them. **A turn no session owns carries the account and no session.** The window-start turn [Spec-026 §Credential-home health observation](026-provider-accounts-and-credential-homes.md#credential-home-health-observation) spends on an account outside every session is metered by this type with `runId` **absent** and the envelope bound to the reserved node-scope sentinel `session_id` per [§Daemon-Scope Event Binding And Node-Scope Anchoring](#daemon-scope-event-binding-and-node-scope-anchoring) — the binding `usage.rate_limit_update` already takes for an account-plane fact with no owning session — so that turn counts in the account's own totals and in no session's receipt. No second event type is minted for it: the fact is a turn's consumption, and this type is the carrier for a turn's consumption.

### Data Acts

The person's data acts ship in V1, and none is a category of events of its own. A session's purge is the daemon's one purge path, recorded as `session.purge_requested` and `session.purged` (§Session Lifecycle), and it deletes the session's content key before its rows, overwritten with zeros first and with a `TRUNCATE` checkpoint after commit ([Spec-020 §Ordering And Atomicity](./020-data-retention-and-gdpr.md#ordering-and-atomicity)), so whatever stays on disk until its pages are reused is ciphertext whose key has been deleted. `Export all data` writes a readable folder that holds no settings, credentials or keys, and records one line in the diagnostic log rather than an event. `Erase all data` stops all work, signs the providers out, destroys the keys and the data, and restarts the service empty, leaving no log to write into. `sidekicks delete-account` is the one way to delete the hosted account, through the control plane from a signed-in machine; `sidekicks rotate-keys` replaces the master key crash-safely, re-wrapping every key under the new one in the transaction that makes it active; and the revocation denylist is written on every revocation ([Spec-020](./020-data-retention-and-gdpr.md)). A lost or stolen device is revoked one at a time, recorded as the control plane's `device.revoked` (§Device And Machine List (control plane)), never as a session event; the daemon holds no WebAuthn credential to reset.

**Precedent.** GDPR Article 17 names the right verbatim as _"Right to erasure ('right to be forgotten')"_ ([EUR-Lex GDPR consolidated 2016/679](https://eur-lex.europa.eu/eli/reg/2016/679/oj), Article 17(1), accessed 2026-04-19). [NIST SP 800-88 Rev. 2 — Guidelines for Media Sanitization](https://csrc.nist.gov/pubs/sp/800/88/r2/final) (final, Sept 26, 2025, accessed 2026-04-19) introduces _"Cryptographic Erasure (CE) that leverages encryption and key management"_ as a distinct sanitization category alongside "Clear" and "Destroy" — a session purge, which deletes the session's content key before its rows, and `Erase all data`, which destroys the keys, are CE-category operations. [EDPB CEF Report on the right of erasure (Feb 18, 2026)](https://www.edpb.europa.eu/our-work-tools/our-documents/other/coordinated-enforcement-action-implementation-right-erasure_en) (accessed 2026-04-19) flags anonymization-as-substitute as a common misapplication; CE with `pii_ciphertext_digest` preserved in the signed canonical bytes avoids that pattern because the ciphertext itself is destroyed rather than hashed-then-nulled.

### Audit Integrity (`audit_integrity`)

Integrity-verification events recording the outcomes of hash-chain, Ed25519 signature, and Merkle-anchor checks per [§Integrity Protocol](#integrity-protocol) above. These events belong to a distinct category from `session_lifecycle` because they describe **the audit log's tamper-evidence state**, not a session's operational state — a single verification pass may cover events from many sessions, and a failure does not end a session but does halt replay.

**Invariant: audit-integrity events are never stubbed.** Stubbing these events would defeat the integrity protocol — a verifier could not distinguish between "no failure occurred" and "the failure record was stubbed away." They are explicitly excluded from the stubs a session's deletion writes ([§Event Compaction Policy](#event-compaction-policy)); only `Erase all data`, which deletes the whole store, removes them ([Spec-020 §Erasure Paths](./020-data-retention-and-gdpr.md#erasure-paths) Path 1).

**A session that fails its integrity check stops taking events.** A session whose record fails its integrity check, or whose signing key is found in reuse, takes no new events, as the append gate already refuses them, and says so where the person acts: the composer's Send refuses with `This session's record failed its integrity check, so nothing more can be added to it.`, and one system message lands with the time. The session can still be read, forked from its last verified point, and deleted. The daemon's loopback `/metrics` carries `audit_integrity_failed_total{scope}`, `key_reuse_detected_total` and a gauge of the last full verification time, held in daemon memory and reset at a restart, and `sidekicks daemon status` prints one line per halted session. No screen lists audit events.

Payload shape: `{sessionId, anchorId?, verifierNodeId}` (base). Per-event payload extensions called out inline. The `audit_integrity_failed` registrar arm takes a REDUCED base — `{sessionId, verifierNodeId}` — because `anchorId` is excluded from that arm outright rather than merely left absent (the row's cell below carries the reasoning).

**Session binding.** `audit_integrity_verified` / `audit_integrity_failed` carry the real `session_id` of the verified range (or the sentinel when verifying the node-scope chain itself); `key_reuse_detected` is a node-level observation bound to the reserved sentinel `session_id` per [§Daemon-Scope Event Binding And Node-Scope Anchoring](#daemon-scope-event-binding-and-node-scope-anchoring). The `signing_key_slot_conflict` registrar arm is a third case matching neither: no range was verified, yet the alarm is deliberately NOT node-scope-bound like `key_reuse_detected` — it carries the refused registration's real `session_id`, landing the row in the log whose verification the usurped slot breaks; `verifierNodeId` carries the refused daemon's own NodeId (the emitter naming itself — the node whose slot the conflict implicates), and `anchorId` is absent ALWAYS rather than merely at emission — this arm's schema REJECTS the member outright — while the ROW still gains anchor coverage as any appended row does, once a subsequent anchor covers its range: coverage is a property of the range an anchor spans, never a reference the signed payload carries or could later acquire. Session binding's reach is scoped honestly: the row is signed with the refused daemon's LOCAL key, so a roster-resolving external verifier sees it fail as `signature_mismatch` exactly as it does every other row this daemon signs — the binding serves local replay and the anchor-covered post-repair forensic record, not externally-authenticatable testimony; the `signing_key_slot_conflict` prose in the table below carries the full scoping and the open trust-path item.

The four `anchor_missing_for_compacted_range` / `anchor_signature_invalid` / `stub_signature_invalid` / `stub_scalar_mismatch` modes are additive-MINOR extensions for the post-compaction integrity protocol per §Post-Compaction Integrity. The twelfth mode `signature_placeholder` is a further additive-MINOR extension: the row's `daemon_signature` is still the 64-zero-byte placeholder, so **no signature was ever produced** for it — it is deliberately distinct from `signature_mismatch`, and pairs with **`failurePath: 'signature'`** (the defect is in the signature column, the same path `signature_mismatch` takes, so implementations mirror this assignment rather than infer one). §Integrity Protocol carries the fail-closed rule, the all-three-columns predicate, the check-ordering requirement, and why such a row is never retro-signed. The thirteenth mode `occurred_at_not_canonical` is a further additive-MINOR extension, and what it registers is a **coverage asymmetry rather than a new threat**: [Plan-005 §Invariants I-005-3-03](../plans/005-session-event-taxonomy-and-audit-log.md#invariants) check (c) already byte-compares a compacted row's `occurred_at` column against the SIGNED stub-projection bytes, so a post-compaction respelling of that column is caught there as `stub_scalar_mismatch` — while the live chain, which every row occupies for the whole of its pre-compaction life, carries no equivalent binding at all. Same column, same threat, same rationale, protected after compaction and unprotected before it; the exposure window is every row's entire uncompacted lifetime. The mechanism behind the asymmetry is that §Canonical Serialization Rules NORMALIZES exactly one canonical member, `occurredAt`, folding it to `YYYY-MM-DDTHH:MM:SS.sssZ`; every other member passes through byte-for-byte. That normalization is many-to-one, so `row_hash` and `daemon_signature` commit to the **instant**, never to the bytes sitting in the `occurred_at` column. An at-rest actor can therefore respell a stored `occurred_at` as any other spelling of the same instant — a `±HH:MM` offset in place of `Z`, a differing fractional-digit count — and BOTH the chain recomputation and the Ed25519 verification still pass, while the row silently drops out of every lexical `occurred_at` range scan. The verdict is deliberately NOT `hash_mismatch` and NOT `signature_mismatch`: on such a row the hash genuinely DOES match and the signature genuinely DOES verify, so either would report a falsehood — that nothing mismatched IS the finding. It pairs with **`failurePath: 'signature'`**, following the `stub_scalar_mismatch` assignment in [Security Architecture §Verification Rules](../architecture/security-architecture.md#verification-rules) rule 4 — the nearest sibling, a scalar-column defect that survives signature verification: `failurePath` names the verification GUARANTEE that failed, not the column the defect occupies, and the guarantee broken here is that the signature binds the stored bytes. Neither alternative fits — `'inclusion'` is the chain path, which passes, and `'consistency'` is the anchor path, which passes over the frozen `row_hash`; a fourth `failurePath` value is deliberately NOT minted, because this verdict routes to the same tamper-response owner `signature_mismatch` does. **The check is a read-side verifier duty performed with the pure, non-throwing predicate `isCanonicalOccurredAt` (`packages/runtime-daemon/src/events/canonicalizer.ts`) over the column bytes AS STORED — it is not part of `verifyRow`, which is handed already-canonicalized bytes and therefore never sees the stored spelling at all.** It is also UNCONDITIONAL: a green chain-and-signature verdict is exactly the state this attack produces, so a verifier MUST NOT gate the check behind a hash or signature failure. The one row it does NOT run on is a row the `signature_placeholder` precondition has already refused: that precondition's mandate to emit and STOP before any Ed25519 verification is unchanged and dominates, because a never-signed row has no signature binding to reason about — `signature_placeholder` stays the single reported verdict there. "Unconditional" therefore scopes to rows that reach verification, and forbids only the inverse error of skipping this check because the chain and the signature both came back green. It applies to `retention_class IS NULL` rows AND to `retention_class = 'audit_stub'` rows, and the two arms cover different halves of the compacted case. On a compacted row `stub_scalar_mismatch` catches a respelling performed AFTER compaction, because the signed projection is a fixed comparand; what it cannot catch is a spelling that was ALREADY non-canonical when the session's deletion signed that projection — §Compacted Event Format preserves the original timestamp verbatim, so such a spelling is baked into the signed bytes and byte-equals the column forever. This check closes that carried-forward case, and on a live row it is the only binding of any kind. **The two verdicts must not be unified under one name:** the compacted check holds signed projection bytes to compare against, so "mismatch" is accurate there, whereas the live path has no stored projection at all — the only available invariant is that the column IS in canonical form, and nothing mismatches — which is exactly why this mode is named `occurred_at_not_canonical` and not a `_mismatch` variant. The fourteenth mode `pii_ciphertext_digest_unbound` is a further additive-MINOR extension closing the **same class** as the thirteenth, found by sweeping for it: a **signed-but-unchecked binding**, where the signature commits to a value that nothing ever compares against the column it stands for. §Canonical Serialization Rules deliberately excludes `pii_payload` from the canonical form and instead requires a `pii_ciphertext_digest` member — BLAKE3 over the ciphertext bytes — so that the signed bytes commit to the ciphertext without carrying it. That digest has been minted and signed since the codec shipped, and no verification rule ever recomputed it, so the ciphertext column carried no integrity binding at all: an at-rest substitution, truncation, or deletion of `pii_payload` left `row_hash` and `daemon_signature` both green. The check is the pure, total, never-throwing predicate `isCiphertextDigestBound` (`packages/runtime-daemon/src/events/pii-indirection.ts`), deliberately sited beside the mint so the two cannot drift apart again, and it is a **POSTcondition of the signature check rather than a precondition** — the digest lives inside the signed bytes, so it is worth trusting only once Ed25519 verification has passed (contrast the two column-SHAPE preconditions, which are pure form tests and run first). It decides four states and needs no caller-side guard: ciphertext present with a digest → recompute and compare; both absent → bound (an ordinary no-PII row, or a compacted stub); ciphertext present with NO digest → unbound, violating this section's non-NULL MUST; and digest present with the ciphertext GONE → unbound, which is the state worth naming, because a signed digest with nothing under it means the column was emptied AFTER signing and the signature still verifies green over a commitment that outlived its subject. A legitimately compacted row never lands there — §Compacted Event Format sets `pii_payload` NULL and replaces `payload` with a stub projection carrying no digest, so it lands in the both-absent state. No other row state needs a carve-out: a session's deletion removes its content key and leaves only its stubs, whose `pii_payload` is NULL, and `Erase all data` destroys the master key and deletes the store ([Spec-020 §Erasure Paths](./020-data-retention-and-gdpr.md#erasure-paths) Path 1), so no row keeps ciphertext its key can no longer open, and the check is unconditional wherever `pii_payload` is non-NULL. As with the thirteenth mode the verdict is deliberately NOT `hash_mismatch` and NOT `signature_mismatch` — the hash genuinely matches and the signature genuinely verifies — and it pairs with **`failurePath: 'signature'`**, naming the guarantee that broke (the signature's commitment to the ciphertext) rather than the column the defect occupies. It is named `_unbound` rather than `_mismatch` for the reason the thirteenth is: two of its four states are absences, where nothing mismatches. The registrar mode `signing_key_slot_conflict` is a further additive-MINOR extension, and it widens the EMITTER set rather than the verifier's check list: it is appended not by a read-side verifier but by the daemon-side registrar's conflict handler, when `runtimenode.signingkeyregister` refuses this daemon's OWN `(session_id, node_id)` slot with the typed different-key 409. Under the register-once / no-rotation posture that refusal at the GENUINE daemon is an integrity alarm, not a caller bug: the slot permanently holds a key this daemon never minted — either a same-user sibling daemon registered first (the registration authorization resolves at user granularity, so V1 cannot rule this out) or this daemon's own key store was lost and re-minted — and no rotation ceremony exists to repair it. Appending it durably makes the usurped slot session-visible and anchor-covered. (The scope is stated honestly. External verifiers are never unaware of the usurpation: it makes every row this daemon signs fail their roster-resolved verification per [Security Architecture §Verification Rules](../architecture/security-architecture.md#verification-rules), the alarm row included — so the alarm reaches that audience only as one more `signature_mismatch`, never as authenticated slot-conflict testimony. What the durable append adds over a log line is a locally-verifiable diagnosis on the emitting daemon's own chain, a tamper-evident anchor-covered forensic record whose authentication completes once the refused daemon's true key is established out-of-band, and operator surfacing. An independently verifiable trust path for the conflict — one not resting on the very key the roster refused — is out of scope: the wholesale roster-resolved mismatch IS the external signal, and the durable row is the locally-verifiable, anchor-covered forensic record whose authentication completes out-of-band. Witnessing of this kind exists so that other people can trust one operator's record against that operator, and this product has one user, who is both the operator and the only reader.) It pairs with **`failurePath: 'signature'`** — the guarantee broken is the roster's binding of this node's signature key; `offendingSeq` is absent (no row is implicated) and `detail` names the refused registration's `(session_id, node_id)` pair. **Its payload arm is likewise its own**: the Merkle triple (`treeSize`, `expectedRootHash`, `observedRootHash`) describes a verified range, and this mode's emitter verified none — requiring the triple here would force the registrar to fabricate roots for a tree it never walked — so the Payload Extension is a union DISCRIMINATED on `failureMode`: the read-side verifier modes REQUIRE the triple exactly as before — **every one** of them, the count read by listing the enum's members rather than carried forward — and the `signing_key_slot_conflict` arm carries `failureMode`, `failurePath: 'signature'`, and `detail` only. The reduced base follows one rule: where a base member cannot mean on a given row what the base says it means, the row drops the member rather than carrying it vacuously. **Precedent — production chain + message surface.** [AWS CloudTrail Log File Integrity Validation — Digest File Structure](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-digest-file-structure.html) and [AWS CloudTrail `validate-logs` CLI](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-cli.html) (both accessed 2026-04-19) publish 15 verbatim digest-file JSON fields including `previousDigestHashValue`, `previousDigestHashAlgorithm`, `previousDigestSignature`, `digestSignatureAlgorithm`, `digestPublicKeyFingerprint`, and per-log-file `hashValue` / `hashAlgorithm`. CloudTrail's `validate-logs` CLI emits verbatim message strings including `"valid"`, `"INVALID: has been moved from its original location"`, `"INVALID: invalid format"`, `"INVALID: not found"`, `"INVALID: public key not found for fingerprint <fingerprint>"`, `"INVALID: signature verification failed"`, `"INVALID: hash value doesn't match"` — these map to our `failureMode` enum's `log_file_*` and hash/signature variants.

**Precedent — observer/monitor pattern (`key_reuse_detected`).** [Sigstore Security Model](https://docs.sigstore.dev/about/security/) (accessed 2026-04-19) states verbatim: _"users can detect any mis-issued certificates, either due to the CA acting maliciously or a compromised OIDC identity provider"_; _"Fulcio itself does not monitor the certificate transparency log; users are responsible for monitoring the log for unauthorized certificates issued to their identities"_; _"these certificates are useless unless they are published to the certificate transparency log, so such compromise can be detected."_ Our `key_reuse_detected` event is the local-daemon observer-pattern equivalent: a monitor process watching for Ed25519 public-key collisions across the daemon's signing-key stores — the same key under two identities — which no registration, rotation included, may produce. (The event log is the trigger for a sweep, not its evidence: the canonical field set carries no `NodeId` and no key material, per §Canonical Serialization Rules.)

**Negative precedent.** [Google Cloud Audit Logs Overview](https://docs.cloud.google.com/logging/docs/audit) (Last updated 2026-04-17 UTC, accessed 2026-04-19) states verbatim: _"Log entries written by Cloud Audit Logs are immutable."_ — and publishes no hash-chain, signed-log, or cryptographic integrity verification mechanism. Our `audit_integrity_*` events intentionally exceed GCP Audit Logs' model; the RFC 9162 + CloudTrail composition is the operationally-mature precedent.

### Security Events (`security_events`)

Daemon-emitted events recording operator-facing security and data-protection posture transitions — fail-safe-default overrides and update-availability signals per [Spec-024 §Required Behavior](./024-self-host-secure-defaults.md#required-behavior), plus the daemon master-key custody source and the PII-split containment signal per [Spec-020](./020-data-retention-and-gdpr.md), and a pinned relay's refused key per [Spec-028 §Interfaces And Contracts](./028-remote-control.md#interfaces-and-contracts). These events belong to a distinct category from `audit_integrity` (which records the audit log's tamper-evidence state) and from `event_maintenance` (which records operations on the event stream itself) because they describe **the daemon's security and data-protection posture** at process scope. Like those two infrastructure-state categories, security events fire at daemon scope across all sessions hosted on the node — they are not session-scoped. (These daemon-scope categories fire at process scope across all sessions, so they bind to a **reserved node-scope sentinel `session_id`** in the daemon-local `session_events` store: the local SQLite `session_id` is `TEXT NOT NULL` with **no** foreign key (see [local-sqlite-schema.md](../architecture/schemas/local-sqlite-schema.md)), so a reserved sentinel value is admissible without a phantom `sessions` row. The sentinel is pinned to the **RFC 9562 §5.10 Max UUID** `ffffffff-ffff-ffff-ffff-ffffffffffff`: the wire-path `EventEnvelopeSchema` validates every `sessionId` with `packages/contracts/src/session.ts#SessionIdSchema`, whose validator is the `packages/contracts/src/internal/branded.ts#brandedUuidIdSchema` factory's own `RFC_9562_TEXT_FORM` predicate regardless of the local store's looser `TEXT` typing, so the sentinel **must** be a value that predicate admits or these events would be rejected before append/serialization — the Max UUID is one of its three alternatives, and every alternative matches case-insensitively, so the sentinel is emitted lowercase as a canonical-form convention rather than as a parse requirement. The Max UUID is chosen over the Nil UUID deliberately: it is a standards-reserved sentinel distinguishable from an accidental nil/zero-init, and is structurally disjoint from the `gen_random_uuid()` v4 id space (version nibble `f`, not `4`), so it can never collide with a real session id. In the daemon-local store it forms its own monotonic-sequence + BLAKE3 hash-chain + anchor partition exactly as a real session id does — reusing the existing per-session machinery, not a new replay mechanism. This identical-partition property is **local-only**: node-scope (sentinel-partitioned) chains are witnessed **locally only**, and control-plane witnessing is out of scope for one user ([ADR-017 §Node-Scope Anchor Witnessing (Local Only)](../decisions/017-shared-event-sourcing-scope.md#node-scope-anchor-witnessing-local-only); [§Daemon-Scope Event Binding And Node-Scope Anchoring](#daemon-scope-event-binding-and-node-scope-anchoring)). Every event of this category binds to this sentinel, `relay.pin_refused` included. The cross-category binding rule for all daemon-scope events — `audit_integrity` (`key_reuse_detected`), `event_maintenance`, the daemon-startup `runtime_node_lifecycle` clock events, and the account-plane `usage.rate_limit_update` (`usage_telemetry`) — is specified canonically in [§Daemon-Scope Event Binding And Node-Scope Anchoring](#daemon-scope-event-binding-and-node-scope-anchoring) below.)

**Invariant: exactly-once-per-active-override emission for `security.default.override`.** Per [Plan-006 §Invariants I-006-4](../plans/006-local-ipc-and-daemon-control.md#invariants), each active override emits exactly one `security.default.override` event per process startup, never per request. Multi-override scenarios emit one event per distinct override.

Payload shape: `{nodeId, occurredAt}` (base). Per-event payload extensions called out inline.

| Type | Description | Payload Extension |
| --- | --- | --- |
| `security.default.override` | An operator opt-in override of a fail-safe default has been activated for this daemon process. ### Event Maintenance (`event_maintenance`)

Daemon-level events recording operations on the event store itself — the stubs a session's deletion writes and the store's backups. These events belong to a distinct category from any session-scoped category because they describe **the event log as infrastructure**, not the session content it carries. One `event.compacted` event records one deletion across every session it removed.

**Invariant: event-maintenance events are never stubbed.** Stubbing an `event.compacted` event would destroy the record of the deletion it describes. Like `audit_integrity` events, they are excluded from the stubs a session's deletion writes ([§Event Compaction Policy](#event-compaction-policy)).

Payload shape: `{nodeId, operationId, occurredAt}` (base). Per-event payload extensions called out inline.

**Session binding.** These are daemon-scope events bound to the reserved sentinel `session_id` per [§Daemon-Scope Event Binding And Node-Scope Anchoring](#daemon-scope-event-binding-and-node-scope-anchoring). `event.compacted` is no exception: the sessions a deletion removes are the ones whose partitions it stubs, so its record lives on the sentinel partition and names the removed sessions in its payload.

| Type | Description | Payload Extension |
| --- | --- | --- |
| `event.compacted` | A session deletion (`Delete old data`) replaced the full payloads of the sessions it removed with audit stubs per [§Compacted Event Format](#compacted-event-format), after the anchor-before-stub protocol of [§Post-Compaction Integrity](#post-compaction-integrity), and deleted each session's content key first (overwritten with zeros, then deleted, with a `TRUNCATE` checkpoint after commit; [Spec-020 §Ordering And Atomicity](./020-data-retention-and-gdpr.md#ordering-and-atomicity)). It is the only record of stubbing: no background work writes one. It names the sessions removed and the range stubbed in each. | base + the removed sessions with the stubbed range of each (`fromSeq`, `toSeq`) |
| `backup.completed` | A backup of the service's store finished — `Back up now`, or the daily run the person turned on: the database copied online, the machine's settings file, each chat session's workspace, the agent memory folder, and each kept session's checkpoint copies and conversation files ([Spec-013 §Backup Policy](./013-persistence-recovery-and-replay.md#backup-policy)). | base |
| `backup.failed` | A backup run failed; the backups already made are kept, and the next run tries again. | base |
| `backup.restored` | A backup was restored into the service's store. | base |

**Precedent — `event.compacted`.** Range endpoints `fromSeq` / `toSeq` mirror RFC 9162's `tree_size_1` / `tree_size_2` from `ConsistencyProofDataV2`. No upstream event literally named `event.compacted` records a whole-session deletion; the field set is composed from §Compacted Event Format and §Post-Compaction Integrity.

Payload shapes are per-type (see the table).

### MCP Governance (`mcp_governance`)

### Workflow Lifecycle (`workflow_lifecycle`)

Durable records of one workflow run's own life, emitted by the workflow engine ([Spec-015 §Event envelope and category split](./015-workflow-authoring-and-execution.md#event-envelope-and-category-split-sa-18) owns the emission points and payload semantics; this section owns the event-type registration). ## Integrity Protocol

Canonical events are append-only AND tamper-evident. Every `session_events` row is chained to its predecessor via a BLAKE3 hash and signed by the emitting daemon with Ed25519 over the **same** canonical byte string. On a bounded cadence, a Merkle root over contiguous ranges is anchored to the control plane's `event_log_anchors` table as metadata only — the control plane does not store event payloads, consistent with [ADR-017 Shared Event-Sourcing Scope](../decisions/017-shared-event-sourcing-scope.md). Full protocol, including schema additions and verification order, is specified in [Security Architecture § Audit Log Integrity](../architecture/security-architecture.md#audit-log-integrity).

Tamper-evidence persists across the stubs a session's deletion writes via a two-tier protocol: per-row chain + signature verification for rows that were never stubbed (`retention_class IS NULL`), and anchor-based range integrity for stubbed rows (`retention_class = 'audit_stub'`). Per §Post-Compaction Integrity below, the deletion MUST force-fire and durably persist a covering Merkle anchor BEFORE stripping any row's canonical bytes — verifiers on stubbed rows fall through to anchor-existence + anchor-signature checks instead of per-row recomputation. A kept session never has a stubbed row, so every row of it stays on the per-row check.

**Placeholder signatures are refused, never retro-signed.** The integrity columns carry placeholder values — `prev_hash` / `row_hash` as 32 zero bytes and `daemon_signature` as **64** zero bytes (the column is `BLOB NOT NULL` with `CHECK(length(daemon_signature) = 64)`). A row still carrying the 64-zero-byte `daemon_signature` was written by a code path that predates the signer: no signature was ever produced for it, and there is nothing to verify. **The predicate is all three integrity columns, not the signature alone** — `prev_hash` and `row_hash` 32 zero bytes each AND `daemon_signature` 64 zero bytes, the exact trio the pre-signing path writes together and never a mix. Keying on `daemon_signature` by itself would also capture a genuinely TAMPERED row that merely happens to carry a zeroed signature, reporting an engineering bug where an attack occurred; requiring all three sends that row to the chain check, which reports it truthfully. Requiring `row_hash` is also what keeps a legitimate signed genesis row — zero `prev_hash` at `sequence = 0` — out of this branch. Verifiers MUST detect this case **before both the chain recomputation and the Ed25519 verification**, and MUST emit `audit_integrity_failed` with `failureMode: 'signature_placeholder'` and `failurePath: 'signature'` — a distinct twelfth enum value, additive-MINOR per [ADR-018 §Decision #8](../decisions/018-cross-version-compatibility.md#decision). Ordering before the CHAIN check is load-bearing, not stylistic: such a row's `row_hash` is 32 zero bytes and therefore fails the chain recomputation too, so a verifier that recomputes first both mislabels a never-signed row as a chain break and makes this precondition unreachable dead code. It MUST therefore never be reported as `hash_mismatch`, and it is deliberately NOT folded into `signature_mismatch`: a mismatch is evidence of possible tampering and warrants security incident response, whereas a placeholder is an engineering sequencing bug, and conflating the two pages the wrong on-call. No implementation may "repair" such a row by signing it with a current key. Signing old records with a later key is a published attack on exactly this class of log — Dörre and Ottenhues, [_Security Analysis of Forward Secure Log Sealing in Journald_](https://eprint.iacr.org/2023/867) (ACNS 2025), a real systemd vulnerability patched in v255, states verbatim: _"This check does not prevent old log messages from being signed with a newer key. An attacker can take a journal, remove seals, adjust log messages as desired, and re-create a seal with the current log sealing key."_ No conforming verifier detects the substitution after the fact, because raw Ed25519 verification per [RFC 8032](https://datatracker.ietf.org/doc/html/rfc8032) takes no time parameter at all and daemon signing keys are raw Ed25519 public keys with no X.509 validity windows per [Security Architecture §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature) ([ADR-010](../decisions/010-tokens-passkeys-and-the-remote-channel.md) governs CLI-identity and session-auth key custody, not daemon session signing keys). Key rotation cannot reintroduce the problem, because V1 specifies no daemon signing-key rotation ceremony at all: a session's daemon key is registered once and a registration presenting a different key is refused end-to-end per the same Security Architecture section, so no superseded-key epoch exists for a later key to re-seal.

### Canonical Serialization Rules

Both the `row_hash` input and the Ed25519-signed bytes are computed over the **same** canonical form. Two honest implementations that diverge here produce incompatible hashes and signatures for identical events, so the rules below are mandatory.

- Canonicalization standard: [RFC 8785 — JSON Canonicalization Scheme (JCS)](https://datatracker.ietf.org/doc/html/rfc8785).
- Hash function: [BLAKE3](https://github.com/BLAKE3-team/BLAKE3-specs/blob/master/blake3.pdf).
- Signature scheme: [RFC 8032 §5.1 — Ed25519](https://datatracker.ietf.org/doc/html/rfc8032#section-5.1).
- Fields included (the canonical set; serialized order is mandated by RFC 8785 §3.2.3 UTF-16 code-unit lex-sort of member names, not the order listed here): `id`, `sessionId`, `sequence`, `occurredAt`, `category`, `type`, `actor`, `payload`, `correlationId`, `causationId`, `version`. RFC 8785's lex-sort is non-negotiable — it is what makes "two honest implementations" above produce byte-identical canonical forms; this list documents membership only.
- Fields with value `null` MUST be included (so "present-but-null" and "absent" are distinguishable after serialization).
- `occurredAt` MUST be RFC 3339 UTC with millisecond precision (`YYYY-MM-DDTHH:MM:SS.sssZ`) so ordering is byte-stable. It is the **one** canonical member that is NORMALIZED into that form rather than passed through byte-for-byte, and the normalization is many-to-one, so the hash and the signature commit to the instant and NOT to the spelling stored in the `occurred_at` column — the read-side `occurred_at_not_canonical` check at [§Audit Integrity (`audit_integrity`)](#audit-integrity-audit_integrity) is what enforces this MUST at rest.
- `pii_payload` is NOT included in the canonical form. Events whose `pii_payload` column is non-NULL MUST embed a `pii_ciphertext_digest` field in `payload` — BLAKE3 over the ciphertext bytes of `pii_payload` — so the signed bytes commit to the ciphertext without carrying it. The digest sits inside the canonical bytes, and the stored ciphertext of a live row hashes to it, which is what lets the digest-binding check in [Security Architecture §Verification Rules](../architecture/security-architecture.md#verification-rules) rule 2 run wherever `pii_payload` is non-NULL. No row keeps ciphertext whose key is gone: a session's deletion removes its content key and stubs its rows with `pii_payload` NULL (§Compacted Event Format), and `Erase all data` destroys the master key and deletes the store ([Spec-020 §Erasure Paths](020-data-retention-and-gdpr.md#erasure-paths) Path 1), so the check needs no carve-out for a shredded row.
- The PII partition is sealed under the session's content key — the same random 32-byte AES-256 key in `session_content_keys` that seals `content_payload` below — with AES-256-GCM, a random 96-bit IV per write, and associated data `session_id || "ais.session-pii.v1" || event_id` ([Spec-020 §PII Payload Column Pattern](020-data-retention-and-gdpr.md#pii-payload-column-pattern)). The label keeps the partitions apart under one key: `content_payload`'s associated data is `session_id || event_id`, so without it a row's `pii_payload` ciphertext would authenticate as that row's `content_payload`. `session_id` is already a canonical signed member, so the canonical form as it stands commits to the key that sealed the row, and no owner member is signed beside the digest; who emitted the row is the signed `actor`.
- `content_payload` is NOT included in the canonical form either, and for the same structural reason `pii_payload` is not. Events whose `content_payload` column is non-NULL MUST embed a `contentCiphertextDigest` field in `payload` — BLAKE3 over the ciphertext bytes — so the signature binds the machine-authored body without carrying it, and survives that body's destruction when the session is deleted. The parallel is deliberate, and the partitions share one key: `content_payload` is sealed under the same session content key as `pii_payload`, under its own associated data `session_id || event_id`, and carries no owner member for the same reason the PII partition carries none — `session_id` is already a canonical signed member, so the key's binding is committed by the canonical form as it stands. What differs is authorship: this column holds what the machine wrote, the PII partition what the person wrote, and each is committed to by its own digest. **The digest is enforced by its own verification mode, not by the PII one.** The shipped binding predicate is hard-wired to the `pii_ciphertext_digest` payload key and the `pii_payload` column, so it can neither read nor vouch for this pair; without a mode of its own, a `content_payload` replaced or removed after signing would leave the row's signature green while decryption merely reported the body unavailable — silently converting at-rest tampering into an ordinary transcript-loss condition, which is precisely the confusion `'turn_content_unavailable'` must not absorb. This spec therefore mints **its own** verification mode, `content_ciphertext_digest_unbound`, as an exact structural sibling of the fourteenth: the same four-state compare over (digest present/absent × column present/absent), fail-closed on a column value it cannot digest. Every row in a session's log is authored by the one runtime node bound to that session, so the compare has exactly one arm and no provenance dispatch. It is a verifier `failureMode` and **not** a wire error code — no [error-contracts.md](../architecture/contracts/error-contracts.md) row is added, exactly as `pii_ciphertext_digest_unbound` adds none. Like `pii_payload`'s, this column's ciphertext is **removed** when a session's deletion stubs the row, along with the payload that carries its digest, so the two disappear together and no post-compaction check straddles them.
- The canonical form is **bounded**: `canonical_bytes(row)` MUST NOT exceed `EVENT_CANONICAL_BYTES_MAX = 32768` bytes (32 KiB; the exported constant lives beside `EVENT_ENVELOPE_SEQUENCE_MAX` in `packages/contracts/src/event.ts`), enforced at the sole append path — an oversized envelope is refused with the typed `daemon.event_canonical_bytes_exceeded` error ([Error Contracts §Daemon](../architecture/contracts/error-contracts.md#daemon), 400) before any row is written, never truncated and never silently accepted. The bound is a **payload-design guarantee**, and the constant is **headroom over the catalog rather than a constraint producers engineer around**: §Event Type Enumeration's payload shapes are metadata-shaped by construction — assistant output carries `contentType?` / `contentLength?` and never message text, tool activity carries no tool output, and artifact and diff content is held in the artifact store on the session's machine and read from other devices through Remote Control ([Spec-012 §Artifacts On Every Linked Device](012-artifacts-files-and-attachments.md#artifacts-on-every-linked-device)), never event-carried — so unbounded content always rides behind a reference, and an append approaching the ceiling is a payload-design defect (bulk content inlined where a reference belongs), exactly the class the refusal exists to catch. The bound covers **both** payload-writing sites: the append path here, and the stub construction a session's deletion runs ([§Compacted Event Format](#compacted-event-format) — the projection replaces `payload` after this check has passed, so the stub bound is the companion this guarantee needs).

Verification is the inverse: recompute `canonical_bytes(row)`, recompute `BLAKE3(prev_hash || canonical_bytes(row))`, compare to the stored `row_hash`, and verify `daemon_signature` against the canonical bytes using the `NodeId`-resolved public key from the session verification-key roster (see Security Architecture § Audit Log Integrity for roster lookup semantics).

### Anchoring Cadence

Anchors fire on the earlier of `ANCHOR_INTERVAL_EVENTS = 1000` events or `ANCHOR_INTERVAL_SECONDS = 300` seconds since the previous anchor. The anchor payload is `(session_id, node_id, start_sequence, end_sequence, merkle_root, root_signature, anchored_at)` — metadata only — uploaded to the control plane's `event_log_anchors` table. **`root_signature` covers the anchor claim, not the root alone:** Ed25519 under the daemon's session-scoped signing key over the UTF-8 bytes of the [RFC 8785](https://datatracker.ietf.org/doc/html/rfc8785) canonicalization of the five-member **anchor claim** object `{"endSequence", "merkleRoot", "nodeId", "sessionId", "startSequence"}` — `merkleRoot` in the base64 spelling the upload wire already carries, the sequences as JSON numbers, `sessionId` / `nodeId` as their wire strings. The coordinates that make a root _meaningful_ — whose log, which span — are thereby inside the signature rather than beside it: a signature over `merkle_root` alone leaves `start_sequence` / `end_sequence` / `node_id` / `session_id` rewritable by whoever stores or carries the record — the control plane that stores the anchor upload, or any later exporter — so any span-coverage test a consumer runs against unsigned coordinates is vacuous. No cross-protocol confusion arises under the shared per-session key: the claim's five-member set is disjoint from every event canonical form (§Canonical Serialization Rules requires `id` / `category` / `type` members no anchor claim carries) and from every stub projection, so no anchor-claim byte string is also a valid signed-event or signed-stub byte string. `anchored_at` stays outside the claim deliberately — it is a receipt timestamp, not an integrity coordinate. Node-scope (sentinel-partitioned) chains are an exception in V1 — see [§Daemon-Scope Event Binding And Node-Scope Anchoring](#daemon-scope-event-binding-and-node-scope-anchoring) below.

### Daemon-Scope Event Binding And Node-Scope Anchoring

Not every event describes activity inside a session. Some describe the **daemon process itself** — its security posture, its event-stream maintenance, its startup clock state. These **daemon-scope** events carry no real session context, yet every `session_events` row needs a `session_id` to partition its hash chain and anchor range.

**Binding rule (event-level).** An event is emitted with `session_id` set to the reserved sentinel **iff it has no single owning session** — either because its payload carries no real session context (**daemon-scope**), or because it spans a user's entire cross-session footprint and so has no one owning session (**user-scope**; the sessions it touches, when it names them, live in the payload, never in the `session_id`). The discriminator is the event, not the category — a category may contain both shapes. The sentinel-bound set is:

- every `security_events` type — `security.default.override`, `security.update.available`, `daemon.master_key_source`, `relay.pin_refused`, `daemon.pii_split_ambiguous`;
- every `event_maintenance` type — `event.compacted`, `backup.completed`, `backup.failed`, `backup.restored`;
- `key_reuse_detected` (category `audit_integrity`) — a node-level key-collision observation, distinct both from `audit_integrity_verified` / `audit_integrity_failed`, which carry the real `session_id` of the range they verified (or the sentinel when they verify the node-scope chain itself), and from `audit_integrity_failed`'s `signing_key_slot_conflict` registrar arm — a second contrast, NOT a member of this sentinel-bound set: it verified no range yet satisfies the owning-session criterion above by carrying the refused registration's real `session_id`, never the sentinel, per [§Audit Integrity](#audit-integrity-audit_integrity)'s Session binding;
- the daemon-startup clock events `session.clock_unsynced` / `session.clock_corrected` (category `runtime_node_lifecycle`, whose only events they are);
- `usage.rate_limit_update` (category `usage_telemetry`) — an account-scoped provider-quota snapshot spanning every session the account's runs touch, so it has no single owning session; the other seven `usage_telemetry` types carry the real `sessionId` of the run or session they meter;
- the four node-scope `mcp_governance` types — `mcp.server_config_changed`, `mcp.server_trust_changed`, `mcp.tool_override_changed`, `mcp.server_oauth_completed` — governance acts of this machine's own client or any linked device against daemon trust/override stores and provider config surfaces, with no single owning session (a session-scoped initiator lives in the payload as `initiatingSessionId?`, never in the row's `session_id`); the fifth type, `mcp.server_status_changed`, binds **per-event**: a session-scoped provider-feed observation carries that session's real `session_id`, a node-level probe binds to the sentinel ([§MCP Governance](#mcp-governance-mcp_governance); [Spec-025](./025-mcp-server-configuration-and-governance.md));

**Sentinel constant.** The sentinel is the RFC 9562 §5.10 **Max UUID** `ffffffff-ffff-ffff-ffff-ffffffffffff`, applied uniformly across **all** daemon-scope bindings — not only the two `daemon.*` events that first reserved it. Its rationale (admissibility under the branded-id validator on the wire path, deliberate disjointness from the `gen_random_uuid()` v4 id space, FK-free admissibility in the `TEXT NOT NULL` local `session_id`) is detailed in [§Security Events](#security-events-security_events).

**Node-scope anchoring is local-only in V1.** A sentinel-partitioned chain forms its own monotonic-sequence + BLAKE3 hash-chain + Merkle-anchor partition exactly as a real session does, reusing the per-session machinery — not a new replay mechanism. In V1 that witness is **local only**: the chain is signed and anchored on the emitting daemon (the local Merkle root durably held in [`pending_anchor_uploads`](../architecture/schemas/local-sqlite-schema.md)) and verified by a **local** reader using the daemon's **public verification key** — the public half of the daemon's own anchor-signing keypair, resolved locally and **not** from the session verification-key roster (a sessionless node-scope chain has no roster entry, per reason (2) below); an audit reader needs only this public key, never custody of the private signing key that could forge the chain. It is **not** uploaded to the control plane: control-plane witnessing is out of scope for one user ([ADR-017 §Node-Scope Anchor Witnessing (Local Only)](../decisions/017-shared-event-sourcing-scope.md#node-scope-anchor-witnessing-local-only)), and the control-plane verification path resolves the anchor-signing key from the **session verification-key roster** ([Security Architecture §Audit Log Integrity](../architecture/security-architecture.md#audit-log-integrity)), in which a sessionless chain has no entry. Local tamper-evidence is sound against every adversary except one holding the daemon's own **signing (private) key**.

**Control-plane witnessing of node-scope chains is out of scope** ([ADR-017 §Node-Scope Anchor Witnessing (Local Only)](../decisions/017-shared-event-sourcing-scope.md#node-scope-anchor-witnessing-local-only)). Witnessing exists so that other people can trust one operator's log against that operator; this product has one user, who is both the operator and the only reader, so the local witness is the whole design. V1's secure-defaults obligation is _local_ audit-visibility to the person ([Spec-024 §Required Behavior](./024-self-host-secure-defaults.md#required-behavior)), which the local witness satisfies.

### Integrity Events

The `audit_integrity_verified` and `audit_integrity_failed` event types are fully enumerated under [§Audit Integrity](#audit-integrity-audit_integrity) below with category `audit_integrity`. `audit_integrity_failed` halts replay at the affected row and must be surfaced to operators. Their category is `audit_integrity` rather than `session_lifecycle`, because integrity events describe the audit log's tamper-evidence state, not a session's operational state.

## Event Compaction Policy

Background compaction is lossless to the product. Background work may compress, repack, archive, move large bodies and rewrite indexes, and only when the transcript's order, its system messages, its tool rows and the output no deletion removed, message identities and times, and the kept undo and fork anchors all survive. Nothing that runs in the background removes anything a person could see, and nothing picks rows to destroy by count, age or size.

One service scheduler runs every background job, each with a cadence, a condition and a budget, and never runs two at once ([Spec-006 §Required Behavior](./006-local-ipc-and-daemon-control.md#required-behavior)). Of its jobs, these touch the event store:

| Job | Cadence | Runs when | What it does |
| --- | --- | --- | --- |
| Retire unused content keys | Hourly | No deletion running | Deletes the wrapped session content keys no stored body uses, in one indexed pass; no row a person can see changes |
| Repack the file | After each `Delete old data` | No turn running | Runs `wal_checkpoint(TRUNCATE)`, then `VACUUM`, measured before and after as `page_count × page_size` and `freelist_count` |

**The only deletion is the person's.** A session's events are deleted only by `Delete old data` (`daemon.retentionPurge`), which removes chosen archived or closed sessions whole. That deletion is what writes audit stubs: for each session it removes, it deletes the session's content key first (overwritten with zeros, then deleted, with a `TRUNCATE` checkpoint after commit; [Spec-020 §Ordering And Atomicity](./020-data-retention-and-gdpr.md#ordering-and-atomicity)), then replaces every row's payload with the stub of [§Compacted Event Format](#compacted-event-format) after the anchor-before-stub protocol of [§Post-Compaction Integrity](#post-compaction-integrity), and records one `event.compacted` receipt on the sentinel session. `audit_integrity` and `event_maintenance` rows are never stubbed. Because the deletion runs only on archived or closed sessions, no live session ever holds a stub.

**Large bodies shrink at write time.** A body of 1 KiB or more is compressed with raw deflate at level 6 before it is sealed, the encoding recorded in the signed payload ([§Assistant Output](#assistant-output-assistant_output)); nothing rewrites a body afterward.

### Retention Windows

| Retention Class | Retained | Stubbed |
| --- | --- | --- |
| Audit stubs | Indefinitely | Never — audit stubs are the stubbed form |
| Full event payloads | Until the person deletes the session (`Delete old data`) | Replaced by audit stubs when that deletion removes the session |
| PII payloads | Until the session is deleted, or until `Erase all data` destroys the master key and deletes the store under [Spec-020](./020-data-retention-and-gdpr.md) | Removed with the session's content key when its deletion stubs the row |
| Reasoning content | Whole, for as long as the session is kept | Never on its own; it goes with its session |

**A kept session keeps its data.** Nothing expires a session's events by age, count or size: a session holds its full payloads, its personal data and its reasoning until the person deletes it, and deletion takes whole sessions. [Spec-020 §Data Retention and Deletion Policy](./020-data-retention-and-gdpr.md#data-retention-and-deletion-policy) owns the retention rules for personal data.

### Compacted Event Format

An audit stub retains the fields below — and, for **every run-scoped row** (its source payload carries `runId`), that `runId`; for a row whose source payload carries the cross-cutting `sourceEpoch` stamp (§Event Type Enumeration), the `sourceEpoch` + `sourcePosition` pair together with that `runId`; and, for an accepted `run.rolled_back` boundary row, the `runId` + `runVersion` + `targetPosition` rewind cutoff — each copied verbatim from the source payload into the stub projection per the paragraph below. Only a session's deletion writes a stub (§Event Compaction Policy):

```
{
  id: string,           // original event ID preserved
  sessionId: SessionId,
  sequence: number,     // original sequence preserved
  occurredAt: string,   // original timestamp preserved
  category: EventCategory,
  type: string,         // original type preserved
  runId?: RunId,        // REQUIRED on every run-scoped row: backstop-index key on terminal run_lifecycle + posture-bearing run.running rows, rollback-boundary key on accepted run.rolled_back rows, epoch key on sourceEpoch-stamped rows
  runVersion?: number,  // REQUIRED on terminal run_lifecycle rows and posture-bearing run.running rows (the keys survive stubbing — §Run Lifecycle), and on accepted run.rolled_back rows
  executionPosture?: ExecutionPosture, // REQUIRED on posture-bearing run.running rows — the audit boundary survives stubbing
  credentialPolicyRef: string, // REQUIRED on posture-bearing run.running rows beside executionPosture — what the daemon handed the provider to deny, per Spec-010; the stub never fabricates one
  contentLength?: number,   // preserved verbatim iff the source payload carries one: the PRE-truncation body length, so a stubbed row still reports how much the machine said
  contentTruncated?: boolean, // preserved verbatim iff the source payload carries one: keeps 'turn_content_truncated' reportable after the body itself is gone; the contentCiphertextDigest deliberately does NOT survive — it commits to bytes the deletion destroys
  actor: string | null,
  compactedAt: string,  // when the session's deletion stubbed the row
  retentionClass: 'audit_stub',
  summary: string       // human-readable one-line summary
}
```

When a session's deletion stubs a row, the `payload` column is **replaced** (not nulled — the column is `NOT NULL`) by the JCS-canonicalized audit-stub projection above; `pii_payload`, `content_payload`, `correlationId`, and `causationId` are removed (set NULL). **`content_payload` joins that list rather than sitting beside it**: the audit stub is a non-PII, non-content commitment, and a surviving machine-authored body would outlive the payload describing it exactly as a surviving `pii_payload` would. Its `contentCiphertextDigest` needs **no stub field of its own** and is deliberately given none — the digest lives inside the live `payload`, which this same step **replaces** wholesale, and a commitment to bytes this same act destroys verifies nothing. Its **descriptive** siblings are treated the opposite way and for the same reason: the projection preserves `contentLength` and `contentTruncated` verbatim whenever the source payload carries them, because an audit stub exists to record _what_ was destroyed — how much the machine said and whether the log ever held all of it — and a hash of the destroyed bytes is not its business. Both are stub-projection members, not durable columns, so the [§ Post-Compaction Integrity](#post-compaction-integrity) scalar binding is untouched. The `summary` field is generated when the row is stubbed, from the original payload, and the deletion MUST hold the serialized projection to the same `EVENT_CANONICAL_BYTES_MAX` bound the append path enforces ([§Canonical Serialization Rules](#canonical-serialization-rules)) by truncating the `summary` it mints **before** signing: `summary` is locally generated prose rather than signed origin content, the one member the bound may lawfully shorten, every other member being either origin content the stub exists to preserve or a fixed-width local stamp (`compactedAt`, `retentionClass`). When truncation cannot hold the bound — the projection still oversized with its `summary` emptied, reachable only for a row written before the ceiling existed or outside the ceiling-enforced append path — the deletion MUST refuse to stub the row rather than shorten preserved members, and reports the refusal on its result. A bound enforced at only one of the two payload-writing sites would not give the guarantee the append ceiling exists for. For terminal `run_lifecycle` rows (`run.completed` / `run.interrupted` / `run.failed`) the projection preserves the original payload's `runId` + `runVersion` — the at-most-once-terminal backstop index (§Run Lifecycle) is keyed on those payload fields, and stubbing them away would re-admit duplicate terminals as indexed NULLs. For accepted `run.rolled_back` rows the projection preserves `runId` + `runVersion` + `targetPosition`, and for a row whose source payload carries the cross-cutting `sourceEpoch` field (§Event Type Enumeration) it preserves the `sourceEpoch` + `sourcePosition` + `runId` triple; each is copied from the source payload and nothing is stamped when the row is stubbed. The deletion then writes a per-row **`stub_signature`** — an Ed25519 signature over the **exact canonical byte string it stores in `payload`** (the RFC 8785 JCS serialization of the audit-stub projection) using the daemon's session signing key. **Sign-exact-bytes invariant:** the deletion signs the identical byte string it persists to `payload`, with no re-serialization between signing and storing; consequently a verifier authenticates the stub by checking `stub_signature` **directly over the stored `payload` bytes** — it never re-canonicalizes or reconstructs the projection from the scalar columns (`compactedAt` and `summary` are not columns; they exist only inside the stored projection). See [§ Post-Compaction Integrity](#post-compaction-integrity). A replay of a deleted session's retained rows reads this stub from `payload` and MUST return it with `retentionClass: 'audit_stub'` (never a silent omission) per [§ Replay Interaction with Compacted Regions](#replay-interaction-with-compacted-regions).

### Post-Compaction Integrity

Once a session's deletion stubs an event, the daemon discards the original `payload` content, `correlationId`, and `causationId`. The row's `daemon_signature` and `row_hash` commit to canonical bytes derived from those (now-discarded) fields, so per-row recomputation **against the original** is no longer possible. Two complementary commitments preserve integrity instead: (1) a covering Merkle **anchor** witnesses that the original pre-compaction range existed and was internally consistent at anchor time; (2) a per-row **`stub_signature`** authenticates the surviving audit-stub bytes against post-compaction tampering. The anchor is the external (control-plane-witnessed) proof of original existence; the `stub_signature` is the at-rest proof that the visible stub is the daemon's genuine compaction output. Both are required — neither alone is sufficient (the anchor cannot detect a tampered stub, and a `stub_signature` alone cannot prove the original range was not fabricated wholesale).

**Anchor-before-stub protocol (load-bearing).** Before mutating any row's payload in a range `[start_sequence, end_sequence]`, a session's deletion MUST:

1. Verify that a **covering** Merkle anchor exists for the range — one whose `[start_sequence, end_sequence]` spans the entire to-be-compacted range, i.e. `anchor.start_sequence ≤ range_start AND anchor.end_sequence ≥ range_end` (a single-anchor coverage test, NOT an exact-`start_sequence` match) — in the local `pending_anchor_uploads` queue OR already durably persisted to the control-plane's `event_log_anchors` table.
2. If no covering anchor exists, force-fire one — compute `merkle_root = BLAKE3-merkle(row_hash for row in range)` using the pre-existing anchoring path (the leaves are the rows' frozen `row_hash` values — the **same** leaf basis the cadence anchor commits via `MerkleAnchorService.onEventAppended({…rowHash})` and the verifier recomputes per [Security architecture §Audit Log Integrity](../architecture/security-architecture.md#audit-log-integrity) Rule 3, NOT `canonical_bytes`: the canonical bytes are discarded when a session's deletion stubs the row, so a `canonical_bytes`-leaved root could never be reproduced at verify time, whereas `row_hash` is frozen by the I-005-3-03 chain-commitment-frozen invariant and survives; RFC 9162 §2.1.1 MTH — leaves are `HASH(0x00 || row_hash)`, interior nodes `HASH(0x01 || left || right)`, the list splitting at the largest power of two below its length), sign the anchor claim with the daemon's Ed25519 key ([§Anchoring Cadence](#anchoring-cadence) — coordinates and root together), and queue for upload.
3. Wait for the anchor row to land in `pending_anchor_uploads` with a durable monotonic sequence (does NOT require successful control-plane upload — the local queue's durable ordering plus daemon signature is sufficient, since the queue's `UNIQUE(session_id, node_id, start_sequence, end_sequence)` makes re-anchoring the **same** range after partition recovery idempotent while still letting a wider covering anchor that shares a `start_sequence` coexist — the step-1 coverage test, not an exact-`start_sequence` match, decides whether a force-fire is needed).
4. For each row in the range, build the audit-stub projection (the field set in [§ Compacted Event Format](#compacted-event-format)) and serialize it **once** to its canonical byte string `B = canonical_bytes(stub)` (RFC 8785 JCS), then compute `stub_signature = Ed25519-sign(B, daemon_signing_key)`. Because `B` includes the row's `id` and `sequence`, the signature is bound to the specific row and cannot be replayed onto another. `B` itself — not a re-serialization of it — is the value step 5 stores in `payload`.
5. ONLY THEN mutate the rows in one transaction: **replace** `payload` with the exact canonical byte string `B` from step 4 (the column is `NOT NULL`; persisting `B` verbatim — never a re-serialization — is load-bearing so that checking `stub_signature` over the stored bytes at verify time is sound); set `correlation_id` / `causation_id` / `pii_payload` / `content_payload` to NULL; set `retention_class = 'audit_stub'`; write the `stub_signature` from step 4.

The deletion MUST refuse to proceed with payload mutation if step 1 returns false and step 2 fails. Chain-commitment columns (`prev_hash`, `row_hash`, `daemon_signature`, `monotonic_ns`, `version`) are NEVER mutated — they remain frozen as the commitment to the pre-compaction state, even though per-row recomputation against the (now-stub) `payload` would fail.

**Verifier semantics on compacted rows.** For rows with `retention_class = 'audit_stub'`, the verifier runs **three** checks (all must pass):

- _Original-existence (anchor) check._ Per-row chain recomputation against the original is **skipped** — those bytes are unrecoverable. The verifier instead reads the covering anchor from `pending_anchor_uploads` (local) or `event_log_anchors` (control-plane) and verifies its daemon Ed25519 `root_signature` over the anchor claim ([§Anchoring Cadence](#anchoring-cadence) — coordinates and root together, so a stored record whose span or log identity was relabeled fails here rather than passing a coverage test on unsigned coordinates). Anchor absent → `audit_integrity_failed` with `failureMode: 'anchor_missing_for_compacted_range'`. Anchor present but `root_signature` verification fails → `failureMode: 'anchor_signature_invalid'`.
- _Stub-authenticity (stub_signature) check._ The verifier checks `stub_signature` **directly over the canonical byte string stored in `payload`** — the exact bytes the deletion signed and persisted (step 5) — using the same `NodeId`-resolved daemon Ed25519 public key from the session verification-key roster. It does **not** re-canonicalize the stub or reconstruct it from the scalar columns (`compactedAt` and `summary` are not columns; they live only inside the stored projection): verifying the stored bytes verbatim is strictly stronger (it catches **any** byte-level edit, not only semantic ones) and avoids a JCS round-trip at verify time. A `stub_signature` that is absent OR fails to verify on an `audit_stub` row → `audit_integrity_failed` with `failureMode: 'stub_signature_invalid'` (the signature is REQUIRED on every compacted row; its absence is a verification failure, never a skip).
- _Scalar-binding check._ The surviving scalar columns on the `audit_stub` row (`id`, `session_id`, `sequence`, `occurred_at`, `category`, `type`, `actor`) are a denormalized cache that SQL filters (`idx_session_events_type`) and envelope reconstruction read — they are NOT covered by `stub_signature`, which signs only the `payload` projection bytes. The verifier therefore decodes the projection from the just-verified `payload` bytes and asserts each scalar column **byte-equals** its projection counterpart (column `occurred_at` ↔ field `occurredAt`, `session_id` ↔ `sessionId`, and so on; `compactedAt` and `summary` have no scalar column and are exempt). Any divergence → `audit_integrity_failed` with `failureMode: 'stub_scalar_mismatch'`. Without it an actor with at-rest DB write access could edit a scalar column (e.g. `actor`, `type`) while leaving `payload` intact: `stub_signature` and the anchor over the frozen `row_hash` would both still verify, yet a filter or reconstruction reading the scalar column would surface the forged value. The signed `payload` projection is the authoritative source for a compacted row's envelope fields — the scalar columns are trustworthy only once this check passes.

A range verifies only when every compacted row passes all three checks. For mixed ranges (some uncompacted, some `audit_stub`), the verifier performs per-row chain recomputation on the uncompacted prefix and the three compacted-row checks on the compacted suffix; all must pass for the range as a whole to verify.

**Tamper-evidence guarantees post-compaction (threat model).** The threat is an actor with write access to the at-rest SQLite database but WITHOUT the daemon's sealed signing key (the daemon itself is the trusted authority that writes stubs). Against that actor:

- _Edit the visible stub_ (`summary`, `actor`, …) inside `payload`: the modified `payload` bytes no longer match `stub_signature` → `stub_signature_invalid`. (The anchor alone cannot catch this: it commits to the original `row_hash`, not to the post-compaction stub bytes.)
- _Edit a surviving scalar column_ (`actor`, `type`, `category`, `occurred_at`) while leaving `payload` intact: the scalar no longer equals the signed projection → `stub_scalar_mismatch`. Both `stub_signature` over `payload` and the anchor over the frozen `row_hash` still verify, so the scalar-binding check is the only thing that catches a forged value surfaced through a filter or envelope reconstruction.
- _Replay a valid stub+signature from another row_: the canonical bytes bind `id` + `sequence`, so a row-A signature fails to verify against row-B bytes → `stub_signature_invalid`.
- _Strip the `stub_signature`_ to dodge the check: a NULL `stub_signature` on an `audit_stub` row is itself a failure → `stub_signature_invalid`.
- _Flip `retention_class` `'audit_stub'` → NULL_ to force the row down the live-chain path: per-row recomputation then runs over the current (stub) `payload`, which does not match the frozen `row_hash` → `hash_mismatch`.
- _Flip `retention_class` NULL → `'audit_stub'`_ on a live row to dodge per-row checks: the row has no covering compaction anchor (`anchor_missing_for_compacted_range`) and no `stub_signature` (`stub_signature_invalid`).

Anchors remain immutable once queued (the durable `pending_anchor_uploads` queue plus the control-plane `event_log_anchors` table hold two independent copies of the signed commitment), so the original-existence proof is independently durable. Stub authenticity is now asserted at **per-row** granularity by `stub_signature`, not merely at anchor-presence granularity.

The four `failureMode` enum values the post-compaction protocol adds (`'anchor_missing_for_compacted_range'`, `'anchor_signature_invalid'`, `'stub_signature_invalid'`, `'stub_scalar_mismatch'`) are additive-MINOR extensions per [ADR-018 §Decision #8](../decisions/018-cross-version-compatibility.md#decision), which sanctions additive enum-value extension. The canonical list of modes is the `audit_integrity_failed` row at [§Audit Integrity (`audit_integrity`)](#audit-integrity-audit_integrity) and is read from there rather than counted here. The per-row `stub_signature` and the scalar-binding check exist for the two gaps an anchor-only design leaves: the visible stub bytes would be unauthenticated, and the surviving scalar columns would stay unbound to any signature, so a forged scalar could survive verification.

### Replay Interaction with Compacted Regions

- Only a session's deletion writes audit stubs, and it runs only on archived or closed sessions it then removes, so no live session and no transcript on screen ever holds a stub.
- A replay of a deleted session's retained rows — an audit read, never a transcript — returns audit stubs, not full events, each marked `retentionClass: 'audit_stub'` and never silently omitted.
- See [Spec-013](013-persistence-recovery-and-replay.md) for full replay and recovery semantics.

## State And Data Implications

- Canonical events are the source of truth for replay and audit.
- Read projections may be rebuilt from canonical events.
- Command receipts or equivalent idempotency markers are required for safe replay of side-effecting command paths.

## Example Flows

- `Example: A run starts, emits tool activity, requests approval, publishes a diff artifact, and completes. Each change becomes a canonical session event with causation and actor metadata.`
- `Example: A user reconnects after missing events and requests replay after the last acknowledged session sequence.`

## Implementation Notes

- Keep the event taxonomy stable and additive; avoid repurposing old types with new semantics.
- Treat provider-native diagnostic events as separate from canonical business events unless they are normalized.
- Replay must be safe for both operators and user-facing timeline projections.

## Pitfalls To Avoid

- Using final assistant text as the only historical source
- Mutating or deleting canonical events in normal operation
- Leaving approval or intervention decisions out of the audit log

## Acceptance Criteria

- [ ] Every run lifecycle transition results in one or more canonical session events.
- [ ] A client can recover missed state by replaying events after its last known cursor.
- [ ] Approval and artifact changes stay whole in a kept session's log: background work never removes them, and only deleting the session replaces them with audit stubs.
- [ ] Stubbed-range integrity is preserved via the anchor-before-stub protocol: every range a session's deletion stubs has a covering Merkle anchor with valid daemon signature, and a verifier that observes an `audit_stub` row WITHOUT a covering anchor emits `audit_integrity_failed` with `failureMode: 'anchor_missing_for_compacted_range'`.
- [ ] Post-compaction stub authenticity is preserved per-row: every `audit_stub` row carries a `stub_signature` (Ed25519 over its canonical stub bytes), and a verifier that observes a tampered, replayed, or missing `stub_signature` on an `audit_stub` row emits `audit_integrity_failed` with `failureMode: 'stub_signature_invalid'`.
- [ ] Post-compaction scalar binding is enforced per-row: a verifier that observes an `audit_stub` row whose surviving scalar columns (`category`, `type`, `actor`, `occurred_at`) diverge from the signed `payload` projection emits `audit_integrity_failed` with `failureMode: 'stub_scalar_mismatch'`.
- [ ] Unsigned rows fail closed and are never retro-signed: a verifier that observes a row whose three integrity columns ALL still hold the zero-fill placeholder (`prev_hash` / `row_hash` 32 zero bytes each, `daemon_signature` 64 zero bytes) emits `audit_integrity_failed` with `failureMode: 'signature_placeholder'` and `failurePath: 'signature'` — checked before both the chain recomputation and Ed25519 verification, never reported as `hash_mismatch` or `signature_mismatch`, and never repaired by signing the row with a current key. A row whose chain columns are intact but whose signature is zeroed is NOT this case and keeps its ordinary verdict.
- [ ] The stored `occurred_at` spelling is bound at rest: a verifier that observes a row whose `occurred_at` column is not the canonical `YYYY-MM-DDTHH:MM:SS.sssZ` form emits `audit_integrity_failed` with `failureMode: 'occurred_at_not_canonical'` and `failurePath: 'signature'`. The check runs UNCONDITIONALLY on every row — live and `audit_stub` alike — and is never gated behind a hash or signature failure, because a row carrying a respelled-but-equal-instant `occurred_at` passes both the chain recomputation and the Ed25519 verification; a green `verifyRow` verdict is the state this defect produces, not a licence to skip. The sole row exempted is one the `signature_placeholder` precondition has already refused and stopped on, whose single verdict is unchanged.
- [ ] The PII ciphertext column is bound by the signature that covers its digest: a verifier that observes a row where `pii_payload` and the signed `pii_ciphertext_digest` disagree emits `audit_integrity_failed` with `failureMode: 'pii_ciphertext_digest_unbound'` and `failurePath: 'signature'`. "Disagree" covers all three defective states — stored bytes whose BLAKE3 differs from the digest, stored bytes with no digest at all (violating the non-NULL MUST in §Canonical Serialization Rules), and a digest whose ciphertext has been removed at rest. The check runs as a POSTcondition of the signature verification, never before it, because the digest is only trustworthy once the bytes carrying it have verified; it is unconditional wherever `pii_payload` is non-NULL. After a session's deletion no row of that session keeps a non-NULL `pii_payload`: its stubs land in the both-absent state and pass, and `Erase all data` leaves no row at all. A row with neither ciphertext nor digest passes — that is an ordinary no-PII row or a compacted stub.
- [ ] The machine-authored content ciphertext is bound by the signature that covers its digest: a verifier that observes a row where `content_payload` and the signed `contentCiphertextDigest` disagree — stored bytes whose BLAKE3 differs from the digest, stored bytes with no digest, or a digest with the column gone — emits `audit_integrity_failed` with `failureMode: 'content_ciphertext_digest_unbound'` and `failurePath: 'signature'`, fail-closed on a column value it cannot digest. Negative coverage is explicit: a replaced ciphertext and a digest-with-column-missing row each fail.

## Design Decisions

- Session sequence numbers are assigned by the authoritative session-visible append path at write time. Projection merge must preserve those numbers and must not invent them later.
