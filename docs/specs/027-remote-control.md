## Purpose

One user, many linked devices, each session executing on one of the user's machines, of which there may be any number; any device can do everything the desktop can, including read the transcript, send, steer, stop, approve, drive agents, view the diff, use the terminal, and reach every screen. No other people.

## Scope

Remote Control covers the whole path from a device that is not the machine a session runs on to that session, and the parity bar that path must meet. A device gets all of:

- read the live transcript and session history
- send a message
- steer a run in flight
- stop a run
- answer an approval, a question or a plan
- configure and drive agents
- view the diff
- open and use the terminal
- reach every screen: the sessions list, Sidekicks, Skills, Workflows and Settings

The mechanism is device linking recorded in the account's signed statement chain, an encrypted channel between each device and each machine through the person's own relay, a method proxy from the device to the machine, push sealed on the machine, and the device recorded on each event it sends.

## Non-Goals

- **Other people in a session.** A session belongs to one user. Remote Control adds devices, not people, and nothing here admits a second account to a session.
- **A second machine behind one session.** A session runs on the machine it was started on for its whole life. Nothing moves it, copies it to another machine or dispatches its work elsewhere.
- **A relay that serves other people.** The relay is the person's own, deployed in their own Cloudflare account or on their own server.
- **Frontend.** The screens named below are the contract the frontend will build against. No screen work belongs to this spec; Plan-025 Phase 7 owns it and starts only after the phases under it have merged.

## Required Behavior

### One user, many devices, any number of machines

A session has exactly one owner, and that owner is the user. Every device is a client of that same account — a phone, the web client in a browser, the desktop app on another computer. A device drives sessions; it executes nothing. A machine is a computer whose background service runs sessions, and a person may have any number of them, a Mac mini at home and a MacBook that also runs sessions, say. Each session has exactly one owning machine, the one it was started on, which executes it for its whole life; it is never moved or silently migrated. A computer that runs the service is one machine under one name, whether or not its desktop app is also used to drive another machine: the desktop app there acts with the machine's own key, so it is never listed twice. A Windows computer is one machine whichever side runs its service, a Windows install or a WSL 2 distribution, and a move between the two keeps its key and its registration, so no device links it again. Its name defaults to the Windows computer name at its first registration only, after which `Rename` alone sets it, and its platform string is the computer's (`Windows 11 24H2 · version 0.1.0`), never the distribution's. Where its Claude Code and Codex live in WSL 2, that one service is the daemon in the distribution plus the service's Windows half, started by a per-user logon task through one attached `wsl.exe` and reached locally through one per-user named pipe, the same pipe a native Windows service serves ([Spec-006](./006-local-ipc-and-daemon-control.md)).

- **One machine in view.** With two or more machines, every device shows one machine at a time. The head of the sessions list carries the machine in view; its list names each machine, with `This machine` and `Not reachable`, and picking one changes every screen to that machine and opens the session last in view there, or else its first row. Devices is the same on every machine. With one machine the switch is absent.
- **Where a device starts.** A device opens on the machine it last had in view; the desktop app on a machine opens on its own machine.
- **A new session runs on the machine in view.** The new-session picker offers no machine, because the switch above it already chose one.
- **One bell across machines.** The bell's count is the sum of what is waiting on every machine, as last read for one that is not reachable, so it always equals the lines the bell holds, and with two or more machines each line ends with its machine's name.
- **A session's address on several machines.** A device asks each machine it can reach whether it holds the session and opens it there; if none does, it says `That session is not here.`
- **Usage and spend are the machine's.** Settings › Providers shows the accounts, windows and spend of the machine in view; no figure is summed across machines.

A device holds one encrypted channel to every machine it can reach while its app is open, reads each machine's waiting items for the bell and sends its presence on each; only the machine in view serves the screens. Each machine runs its own Claude Code and Codex, signed in to the accounts on its own Providers page, and a provider never learns that another machine exists.

### Device registration and revocation

Everything that decides which of the person's things can drive their sessions is one Settings page, `Devices`, the last page, after Runtime (`#/settings/devices`, `#/settings/devices/<id>`). It is set up once and visited rarely, so the rail keeps its destinations. Its body is Remote Control's, contributed to the Settings page list through the settings page registry. On the machine itself, with no device linked yet, the page is still present: it is where the first device is linked. No other Settings page lists a device or a passkey.

- **Four sections, one column.** `Machines` (`Computers that run sessions.`), `Devices` (`Phones and browsers you've linked to reach sessions remotely.`), `Passkeys` (`Sign in on a new phone or browser with a face scan, fingerprint or screen lock, with no other device needed.`) and `Shared ports on <machine>` (§Shared ports), each opening with its one line. A section with nothing in it shows its line and its act alone. A card's acts are on the card; nothing opens beside it.
- **A machine card** shows the machine's name, `This machine` on the one this console runs on, its platform and service version (`macOS 15.6 · version 0.1.0`), `Reachable` or `Not reachable · last seen 2 hours ago`, `Rename` in place — one field a screen reader names `Machine name`, where Enter commits and Escape cancels — `Keep this Mac awake for other devices` (`Keep this computer awake for other devices` on Windows and Linux), off by default, under `Only while it is plugged in. Closing the lid still puts it to sleep.`, and `Remove`. Removing asks in place, `Remove <machine>? Linked devices stop reaching it. Its sessions stay on it.` under `Cancel` and `Remove`, which takes focus; Escape cancels. The machine this console runs on is removed the same way. Removing a machine stops every port it shares and closes every forward open on it, and the machine comes back only by being linked again, as a new computer joins: it first mints a new identity key under its same machine id, and its store, sessions and id stay as they were.
- **A device card** shows the device's name, its platform and app version (`iPhone · iOS app 1.4.0`, `Chrome on Windows · web`), `Connected now` or `Last seen 12 min ago`, `Linked <date>`, `This device` on the one in the person's hand, `Rename` in place — one field a screen reader names `Device name`, working as a machine's does — and `Revoke`, confirmed in place: `Revoke <device>? It is signed out everywhere and cannot link again.` under `Cancel` and `Revoke`, which takes focus; Escape cancels. A device that a since-revoked device linked reads `Linked from <device>, which you revoked. Revoke it if that device was lost.` on its card: revoking a device leaves linked every device it linked before, so this line is how a device a thief linked before the revoke is found. A revoked device moves to a `Revoked` group at the bottom with `Forget`, which removes the card; there is no restore, because a revoked key never links again. While a machine has not yet heard of a revoke, the card reads `<machine> drops it when it next connects.` The group is absent when empty.
- **Presence is on the cards and nowhere else.** `Connected now` is whether the device holds a relay connection this moment, and `Last seen` is the end of its last one. Nothing in a session names which devices are connected, a message carries no device mark, and there is no connected-devices banner.
- **Linking, on the device already in use.** `Link a device` gives way, in place, to a code to scan, which a screen reader names `QR code to link a device`, the same link as text in a read-only field a screen reader names `Link for the new device`, with `Copy link` (which reads `Copied` for the one transient duration of [Spec-021 §Meridian, the design language](021-desktop-app-and-renderer.md#meridian-the-design-language)), `Scan this code with the new device, or open this link on it.`, `Expires in 4:52` counting down, and `Cancel`. The link lasts 5 minutes and is good once. It opens on any device: in the phone app it goes straight to the next step; in a browser it opens the web client there. When the countdown reaches zero the block gives way to `Link a device` again. Once the new device has read it, both screens show `Check that both screens show the same number.` over six digits in three pairs (`48 21 07`), with `It matches` and `It doesn't match`. `It matches` links the device, and the card appears under `Devices`. `It doesn't match` ends the attempt: `Nothing was linked. Make a new link to try again.` An expired or used link reads `This link has expired. Make a new one on a device you have already linked.`
- **Linking, on the new device.** A phone app with nothing linked, and the web client, open on one screen with `Scan code` (in a browser only where it can read the camera) and `Paste link`, and `Sign in with a passkey` once a passkey exists. After the link is read, the new device shows the same six digits under `Confirm on <device>.` and waits; when the linking device confirms, it opens on the sessions list of the machine in view.
- **The six digits.** The link carries a fresh 32-byte linking secret in its fragment, which is never sent to the control plane. Both sides compute the six digits from that secret, both devices' keys and the list of machine keys, so a thief who redeems a pasted link first makes the two screens disagree.
- **One link reaches every machine.** A device linked from any machine or device is trusted by every machine that trusts the one that linked it. A new computer joins the same way, with no limit on how many: its service's console is the new device in the ceremony, and once it is linked, it trusts every device and machine the linking one trusts, and they trust it.
- **Passkeys, the owner's way in beside the link.** `Passkeys` lists each passkey with the platform that holds it and `Added <date>`, with `Remove`, confirmed in place: `Remove the <platform> passkey? It can no longer link a new device.` under `Cancel` and `Remove passkey`, which takes focus; Escape cancels. On the last passkey the question adds `New devices will need a link from one you already use.` Once removed, the row gives way to `Passkey removed. You can also delete it from <platform>.`, because a site cannot delete the key on the person's device. Each time the web client and the phone apps sign in, they tell their platform which passkeys still count — the WebAuthn Signal API's `PublicKeyCredential.signalAllAcceptedCredentials`, the iPhone app's `ASCredentialUpdater.reportAllAcceptedPublicKeyCredentials` and Android Credential Manager's `SignalAllAcceptedCredentialIdsRequest` — so the platform stops offering a removed passkey where it supports the signal (Chrome and Edge 132 and later, Safari and iOS 26 and later; not Firefox). Apple's 26 releases carry an open fault in this signal that can remove another account's passkey on the same site where that account keeps a password beside it; it cannot reach this product, whose one owner has one account and never a password here. `Add a passkey` is present in the web client and the phone apps and absent in the desktop app, which carries no WebAuthn. A passkey lets a browser or phone link itself with no other device at hand: `Sign in with a passkey` on the new device, the platform's own passkey sheet, then the same six digits shown on the new device alone for the record. A passkey added from a device that is later revoked is flagged on its row: `Added from <device>, which you revoked. Remove it if that device was lost.`
- **One name everywhere.** A device's or machine's name is the one every other device shows: on its card, in `<device> holds the shell.`, in `Runs on <machine>`, in `Answered on <device>` and in the relay block. A rename reaches every device, and every machine the next time it connects. A rename left empty keeps the name it had.
- **Nothing reads a log back.** The chain's statements are kept because the machines verify them, and they are never shown as an activity list.
- **The command line.** `sidekicks devices` prints the machines and the devices as the cards do. `sidekicks devices link` prints the link, draws the code in the terminal with the countdown, then the six digits and `Do both screens show 48 21 07? [y/N]`. `sidekicks devices rename <name-or-id> <new name>`, `sidekicks devices revoke <name-or-id>` (asking `Revoke <device>? [y/N]` unless `--yes`) and `sidekicks devices forget <name-or-id>` complete it; each has `--json`. A machine run only from the command line links and revokes this way, with its own key.
- **The account's statement chain.** The account's trust is an append-only chain of signed statements the control plane keeps, each naming the hash of the one before it: `device.linked`, `device.renamed`, `device.revoked`, `passkey.added`, `passkey.removed`, `runtimenode.added`, `runtimenode.renamed` and `runtimenode.removed`, each signed by a machine key, a device key or a passkey. Each kind names a fact, subject first and past tense, a machine by the backend's word for it, and the control plane's event that announces a statement carries its kind as its name. The person's first machine opens the chain with a `runtimenode.added` it signs itself, and every later machine joins by linking, which records its `runtimenode.added` signed by the device or machine that links it. Every machine verifies the chain itself and trusts a key only when a path of `runtimenode.added`, `device.linked` and `passkey.added` statements reaches it from its own machine key, each signed while its signer was still trusted at that point in the chain. A `device.revoked`, `runtimenode.removed` or `passkey.removed` ends the key it names at that point: a statement that key signs afterward is refused, and what it signed before stands, so every device, machine and passkey it added stays trusted, flagged on its card or row where a revoked device added it. An ended key is never trusted again. A link is a fact of the account, never of a session. The control plane's own view of who may use the relay serves only against spam and cost; a machine's refusal in the handshake is what protects the sessions.
- **Withholding is caught.** Every channel open carries the head of the chain each side holds. A machine that sees a newer head from any device fetches the missing statements, so a control plane that withholds a revoke from one machine is caught at the next connection of any honest device. The revoking device also sends its statement over its own channel to every machine it can reach.

### Parity by construction

The client SDK swaps its local pipe for the relay. Every surface already speaks the SDK, so a device gets parity because the transport underneath changed, not because each screen was re-implemented for remote use. The consequence is the bar: a method that works over the local pipe and not over the relay is a defect in the transport, never a feature a device does not have. Parity is proven by running one suite against both transports rather than by enumerating screens.

### What another device shows and does

Parity is the transport's job; the rules below are what follows from the screen being somewhere else, and they hold on every client.

- **Preview is a live picture, never a local page.** The preview pane on another device shows the page on the machine that runs it: a frame stream the service produces on whichever host runs the page, carried over the relay, with no debug port opened on either host. Mouse presses, moves and releases, the wheel, keys and touches are forwarded back and every frame is acknowledged as it is applied — an unacknowledged frame stalls Chromium's own screencast queue after three frames (measured on Chromium 152), so the acknowledgment is part of the contract rather than an optimization. Focus emulation stays on, because a page fully covered or behind the lock screen gives frames only with it. On a touch screen, touches reach the page as touch events with touch emulation off, a pinch zooms the picture on the device, up to three times, and a two-finger drag pans the zoomed picture, neither of them sent to the page, whose visual zoom is kept at (1, 1); `Type` on the Preview line, present only where the pointer is coarse, raises the soft keyboard; a machine that is lost reads `<machine> is not reachable.` with `Try again` in the pane. The address line reads `Runs on <machine>`, the page is never presented as a local one, and the stream runs only while that device has the pane open. One subscription carries the frame stream, the input channel and the page's right-click menu — `preview.screencastSubscribe` — and it exists for another device alone: the machine's own preview never goes through it.
- **The page's right-click menu is drawn on the device.** A right-click on the live picture, a long press on a touch screen, the menu key or Shift+F10, wherever the browser engine turns it into a right-click menu, opens Preview's own page menu on the device with the console's own menu component, from what the service reads in an isolated world of its own in each frame of the page: the link under the press, whether it landed in a field that takes text, and the selected text, none in a password field. Where the page canceled the menu to draw its own, the service, which reads that too, sends nothing and only the page's menu shows. `Back`, `Forward`, `Reload`, `Select all` and the field's edits go to the machine; `Copy`, `Cut`, `Copy link` and `Paste` use the device's own clipboard and never the machine's, a paste arriving as typing, and a clipboard the device refuses reads `Could not copy` or `Could not paste` on the pane's refusal line; `Open in the default browser` opens on the device, a `localhost` address only through a shared port and only on a host that can open one ([§Shared ports](#shared-ports)); and `Inspect` is absent, because the page's developer tools open only inside the machine's own pane. A right-click another device or an agent sends opens no menu on the machine's screen.
- **A mark means the same thing wherever it was drawn.** Marks drawn on the live picture carry the same element references — the page snapshot's reference and its box — as marks drawn on the machine itself, so the agent receives the same attachment either way.
- **A browser act names its machine.** An agent's browser act driven from another device names the machine it ran on in its transcript row.
- **An attachment is copied to the machine that will read it.** A file or photo picked with Attach on another device is copied to the daemon when it is staged and held with the session, so its chip, its `×`, and Send behave exactly as they do on the machine, and the agent is handed a path on that machine.
- **The shell says who holds it.** While another of the user's devices holds a shell's control lease, a device sees a lease line over a read-only body naming that device. While nobody holds a shell, every device shows no line and a live body, and the first device to type into it takes it, after which every other device reads `<device> holds the shell.` and its input is refused. Taking the shell moves it to this device behind one in-place confirm, and the handoff lands between write frames, so the running program is untouched and the displaced device loses only a half-typed line. A hold that belongs to an agent's running command is never takeable that way; that line offers stopping the run instead ([Spec-002 §Required Behavior](002-machine-registration.md#required-behavior)).
- **A local address is the machine's address.** A localhost link in the transcript or in tool output opens in the preview pane, and from another device that row names the machine running the server. Opening the real server on another device is a shared port (§Shared ports), kept beside Preview.
- **`Open folder…` lists the machine's folders in place.** On another device, `Open folder…` reads `Folders on <machine>` over the path as pressable segments, lists the folders in the one in view with `repository` beside each git repository, and ends with `Open this folder`; `Show hidden folders` shows the hidden ones, and a folder that is not a repository says `Could not attach: not a git repository` in place. Each entry carries its path, and the device sends the path of the folder it was shown. On the machine itself `Open folder…` opens the platform's own chooser.
- **What only the machine can do is absent elsewhere.** `Open in editor`, `Reveal in Finder` and `Open in terminal` act on the machine's own desktop, so they are absent on another device.
- **A provider sign-in comes to the device.** `Sign in` on Settings › Providers starts the provider's own sign-in on the machine, and its verification address and code come to the device holding the screen, where the address opens in that device's browser.
- **Settings from another device.** All ten pages are present. Appearance, Keyboard, Notifications and General's first block (the install's facts, its update block and `Keep crash reports`) are the device's own, and their opening line ends `Kept on this device.`; on a phone app the update block reads `This app is updated by installing a new build.`, and on the web client `This page is the version the relay serves.` General's second block (the new-session switch, both keep-awake switches, the editor and the default checkout), Providers, MCP servers, Projects, Browser and Runtime are the machine's, ending `Kept on <machine>.` Devices is the account's, the same list everywhere. General's opening line reads `What this install is and how it updates itself, kept on this device, and what a new session starts from, kept on <machine>.` On the machine itself each page's opening line reads as its page defines it. The service is the one writer of the machine's settings file, because a phone's change can reach the machine only through the service and a machine run from the command line has no main process: the main process and every other device write through one service verb, the service writes atomically, and every console window reads through the service's live read.
- **Voice from another device.** `/voice` works as on the machine, with the device in hand as the microphone. On a Claude Code session the device sends dictation's audio to the machine over the channel as 16 kHz 16-bit mono in 100 ms frames, 600 a minute, and the machine's daemon holds the Claude sign-in and the socket to Anthropic's speech service; the words come back the same way. On a Codex session the device is the call's WebRTC peer: its offer and Codex's answer pass through the machine, and the call's audio flows between the device and OpenAI. On a touch screen, holding the dimmed Send circle is the hold on both providers, and tap mode works as on the machine; on Codex the device closes the call's microphone on its own side unless the hold or a tap has opened it; on a phone, voice ends when the app leaves the screen: `Voice ended · the app left the screen`.
- **Quitting the app never takes the machine away.** The service outlives the desktop app; a quit leaves it, every run and every shell running, so the person's other devices keep reaching the machine. Only Settings › Runtime `Stop` or `sidekicks daemon stop` ends it.
- **Back dismisses, and never interrupts.** On a client with a hardware back gesture, Back dismisses the topmost surface — the same ladder the escape key walks — and stops short of the work: it never interrupts a turn, because a swipe is not the deliberate press the escape key is. The desktop has no back-gesture rule.
- **The relay's own state is a printed fact**, carried by the daemon's status command rather than by any screen: while a relay is configured, `sidekicks daemon status` gains one block — each linked device by name, connected or not, the age of the last frame out and the last frame in, the reconnect count and the rejected-frame count — in its text output and in `--json` alike ([Spec-006 §Required Behavior](006-local-ipc-and-daemon-control.md#required-behavior)).

### The phone and web clients

The whole console runs on a phone or in any browser, driving the sessions on the person's machines: the sessions list and a session's transcript; send, steer and stop; approvals, questions and plans; the terminal, Preview's live picture and Review; Sidekicks, Skills, Workflows and Settings, its Devices page included.

- **One front end in three more hosts.** The phone apps and the web client run the console's own front end, the same code the desktop runs; only the platform bridge differs. The bridge is the front end's `PlatformBridge`, one typed interface with three implementations: Electron's preload on the desktop, the browser's in the web client, and Capacitor's in the phone apps. A member a host cannot serve is absent from that host's bridge, so its control is absent from the screen, never drawn and refused. The front end reaches a machine over the relay; on the machine itself the desktop app keeps its local pipe. The front end runs in WebKit as well as Chromium.
- **The version range.** The web client is the control plane's release, and between it and each machine the version range applies exactly as between the desktop app and its service: each accepts its own version and the previous one, and outside that range the console is read-only, with the working line naming the side that is behind. A phone app whose host, its native code and platform bridge, is outside a machine's version range shows that machine read-only the same way.
- **Every screen folds.** Sessions, Sidekicks, Skills, Workflows and Settings each show their list, then their detail, one at a time once the window is too narrow for both; Devices is already one column. A detail's header begins with one back control naming the level above it: `‹ Sessions`, `‹ Sidekicks`, `‹ Skills`, `‹ Workflows`, `‹ Settings`, and `‹ <session title>` over a pane. The rail stays a rail: in one column it is drawn beside each screen's list level and is absent on a detail level, never a bottom bar.
- **Coarse pointers everywhere.** Targets grow to a fingertip, what hover reveals stands at rest, and every act a drag performs has a press that does the same, on the Workflows canvas too.
- **The phone terminal key row.** Where the pointer is coarse and the soft keyboard is up while a shell has focus, one row of keys sits directly above the keyboard: `esc`, `tab`, `ctrl`, `alt`; `←` `↑` `↓` `→`; `|`, `/`, `~`, `-`. `ctrl` and `alt` apply to the next key pressed and then release, so `ctrl` then `c` sends Ctrl+C. The row scrolls sideways where it does not fit and goes when the keyboard goes. With a hardware keyboard attached the row is absent and the chords answer as on the desktop. A shell whose lease another device holds shows the lease line and no row. The keys follow the default extra-keys rows of Termux, a terminal app for Android.
- **Back.** Android's Back, the iPhone app's edge swipe and a browser's back button or gesture all dismiss the topmost surface in the order Escape dismisses it: an open menu, list or card; an open pane; the session, for the list; any other screen, for Sessions. On Android, Back on the sessions list leaves the app as the platform does. Back never interrupts a turn, never clears a draft, never opens the rewind menu and never closes an editor with changes; where the next Escape would do any of those, Back takes the next step of the list instead. In the phone apps, the shell turns the platform's gesture into one marked dismissal the front end routes only to dismiss acts. In the web client, a back navigation that arrives while a menu, list or card is open closes it and puts the address back.
- **Two hops, two lines.** On a device that is not the machine, the working line says which hop is down: this device off the network (`Connection lost`, `Reconnecting…` or `Not connected.`, with `Retry`), or this device connected but the machine not (`<machine> is not reachable` where the action words stand, `Reconnecting…` while the relay still waits for it, and `Retry`). Before the machine first answers, the boot card reads `<machine> is not answering.` with `Retry`, and the working line arms only after the machine has answered once since the app opened.
- **The phone's cover.** The phone apps raise a cover whenever the app leaves the foreground and lower it on the platform's own biometric check, with the phone's passcode as the fallback. The cover shows the app's name and nothing else, so the app switcher never shows a transcript. The web client draws no cover: a browser tab cannot ask for the platform's check before it paints.
- **Staying current.** The web client is always the control plane's release. A phone app gets each linked machine's console from that machine: the machine serves its console bundle over the end-to-end channel with the list of its files and each one's SHA-256; the bundle is checked file by file against that list, which catches a partial or corrupt transfer and nothing more, since the channel already proves the machine; and it is staged for the next start, one bundle per machine, so a phone linked to two machines at different versions opens each with its own. Only the shared console assets come from the machine; each host's own native code and its platform bridge ship with that host and are never downloaded from a machine.
- **The hosts, in the order they are built.** First the web client, with a web app manifest so it can be added to the Home Screen, a service worker for Web Push, and its device key as a non-extractable WebCrypto key in IndexedDB. On an iPhone it is the whole phone client until the iPhone app exists: Web Push reaches an iPhone only for a web app added to the Home Screen, and a Safari tab that is not added can lose its storage, and with it the device key, after seven days without use, so the web client offers adding it to the Home Screen once a device is linked, and a lost key is replaced by linking again or by a passkey. Second the Android app, a Capacitor shell with its device key in the Android Keystore, FCM for push, Back, the scan, the cover and an in-app page view for shared ports. Last the iPhone app ([Spec-028](028-connect-an-ios-app-and-drive-control.md)): the one front end in a Capacitor shell, never a second app in SwiftUI, native only where the phone must do something a page cannot.
- **The person's own accounts.** Both phone apps are built from the repository and signed under the person's own Apple and Google developer accounts, and their push goes through the person's own APNs key and Firebase project; the project's release carries the build and the steps, and never a signing identity or push credential of its own.
- **Nothing from a session is kept on a device** beyond what the front end holds in memory while it runs; the transcript is read from the machine each time. A device keeps its key, the machine keys it trusts, its appearance record and keyboard map, its notification settings and the last machine in view.

### Notifications on another device

When a session on a machine starts waiting on the person, finishes or fails, or a workflow's Notify step fires, the phone shows the same notification the desktop would: the session's name and its state, never what was said, even when the app has not run for hours. Tapping it opens that session. When the moment moves on, the notification is replaced in place or withdrawn. Apple, Google, the browser's push service and the control plane carry the notice without being able to read it.

- **One set of moments, three ways out.** Every notification on every device comes from the machine's own waiting items, and each machine posts to each linked device in exactly one way at a time: a device with a live connection and an app window in front gets nothing posted, because the bell shows it; a device with a live connection and no window in front posts the operating system's notification itself; a device with no live connection gets a push. The kinds, the text, the stable id, replacing in place and withdrawal are the same on every path ([Spec-017](017-notifications-and-attention-model.md)).
- **What each push says.** The session's or run's name, the state (`Waiting on you`, `Finished`, `Failed`, or the Notify step's own text) and, when the person has two or more machines, the machine's name: `Nightly bump · Waiting on you · mac-mini`. Tapping it opens that session through its address on the machine that sent it, and one machine's notifications are grouped under its name where the platform groups them.
- **Each device's own switches.** Settings › Notifications on each device holds that device's switches and kinds, kept on that device. The device hands them to every machine it links with, on every connection and whenever one changes, and each machine keeps the copy it was last handed only to decide before it sends, because a pushed notification cannot be dropped after it arrives on an iPhone or in a browser without being shown. The copy is never edited on the machine, and a device that is not connected keeps the switches it last handed over.
- **Mute is the session's.** A muted session's `Finished` and `Failed` never push to any device, its `Waiting on you` always does, and the phone's row draws the same bell-off mark from `session.list`'s `muted`.
- **Quiet while the person is at a console.** No push, and no notification a background device posts, goes out while an app window is in front on any of the person's devices; an explicit workflow Notify step always goes out.
- **What "in front" means.** A device's presence says whether an app window is in front on that device, the same fact the desktop reads to decide whether it posts a banner. A window behind a locked or sleeping screen is not in front: the desktop reads the operating system's lock, unlock, suspend and resume events and the idle state's `locked` where the platform reports it, and the phone apps and the web client read the page's own visibility. On Linux, where the lock is not reported, a locked screen with the app in front still reads as in front. Each device sends its presence on each machine connection it holds, when it changes and otherwise every 15 seconds; a machine keeps the last one per device in memory only and sets no limit of its own on how often one arrives, and a device whose connection has closed counts as not in front.
- **Replaced and withdrawn.** Every push carries the moment's stable id as its collapse id (APNs' `apns-collapse-id`, FCM's collapse key and notification tag, Web Push's `Topic` header and the notification's `tag`), so `Finished` replaces `Waiting on you` in place. When a moment resolves with nothing to replace it, withdrawal is best effort by platform: on Android a sealed data message removes it at once; on the iPhone at most one background push per resolved `Waiting on you`, which Apple may hold back, and the app removes resolved notifications the next time it opens; in the web client the service worker closes resolved notifications whenever it runs, on the next push and when the page next opens, and a push without a notification is never sent, because Safari revokes the subscription for it.
- **The count on the app icon.** Where the device's own `Show a count on the app icon` is on, each push carries the count waiting on the person, summed across machines on the device: the iPhone's extension sets the badge; the web client uses the Badging API where the browser has it; Android shows what its launcher shows for the app's notifications.
- **How a push is made.** The sender is the machine. For each linked device it applies, in order, that device's `Notify me outside the app`, its kind switch, the session's mute and the quiet rule, then chooses the path. For a push it seals the notice on the machine to the device's push key — HPKE with X-Wing, and RFC 8291 for Web Push — so a 256-byte notice travels as 1,856 bytes no one on the path can open. The relay adds only the person's own APNs, FCM or VAPID credentials and holds nothing that opens a notice. `Waiting on you` and a Notify step go at high priority, `Finished` and `Failed` at normal priority, and every push expires after 24 hours. There is no control-plane queue, filter or notification-preferences table. On the iPhone the notification's text before the extension opens it is the fallback `A session changed. Open the app to see it.`, shown only if decryption fails. A push is a delivery, not a fact of the session: nothing is written to any session log.

### Answering from another device

Every one of the person's devices can answer an approval, a question or a plan. It is the same card in the composer, and the first answer settles it everywhere.

- **Every device answers.** The card is drawn on every device that has the session open, with the same buttons, and any of them answers. The machine holds each request open with no timer, so the card is rebuilt on a device that opens the session later or reconnects.
- **Answered elsewhere.** When another device's answer settles it, a device showing the card closes it and draws `Answered on <device>` in the card's place for as long as the session stays open there. It is faint, raises nothing that reads as an error, and is not a message in the transcript. On the machine's own console, answers from the machine read `Answered on <machine>`. A second answer arriving a moment later is refused as already settled, and its device draws the same line.
- **A card that cannot be answered here, now.** It is drawn with its title, command and summary, and one line in place of its buttons, which are absent, not grayed: `<machine> is not reachable, so this can be answered once it is back.`, showing the last card the device received and rebuilt from the machine's own state once it is reachable; or, outside the machine's version range, `This app is behind <machine>. Update it to answer here.` with the app's own update press, or `<machine> is behind this app. Update its background service to answer here.` with Runtime's `Update the background service`. When the reason clears, the line goes and the buttons return.
- **No device is limited by grant.** There is no per-device permission, no view-only device and no approval right: every linked device reads and acts on everything. A device that should not act is revoked.
- **Which device answered.** The channel's handshake proves which device holds each connection, and the machine records that connection's device on every event the device sends, so the resolution event carries the answering device's id. No device signs the events it sends. The screen names the device only in `Answered on <device>`: a message and an answer carry no device mark in the transcript. The hold is the daemon's on both providers — Claude Code's `can_use_tool` control request, Codex's held approval and question requests — so which device answers never reaches Claude Code or Codex.

### Shared ports

The person chooses which of a machine's dev-server ports their other devices may open as if the server ran on them. Preview stays the live picture; a shared port is for what a picture cannot do, such as running the app in the phone's own browser engine at the phone's own size, or pointing another tool on the laptop at the server.

- **The list, on the machine in view.** It is on the Devices page under `Shared ports on <machine>`, with one line: `Ports other devices can open as if the server ran on them. Preview shows the page either way.` Each row is the port with what the machine knows of it — `5173 · Vite · Listening`, or `5173 · Waiting for something to listen` before a server starts — and `Stop sharing`, which takes effect at once and closes every forward open on it. Under the rows is one number field, with `Share`; `Share a port` is its visible label and its name for a screen reader; `That is not a port number.` and `Port 5173 is already shared.` are said under the field, and nothing changes. The list is edited from any device. While the machine in view is not on the Machines list, the section is absent.
- **Opening a shared port on another device.** The desktop app on another computer listens on `localhost:<port>` there while it runs and the port stays shared, and the row reads `localhost:5173 on this computer`, with `Open` opening that address in the computer's own browser; a port already taken there is replaced by the next free one, and the row says so: `localhost:5174 on this computer (5173 was in use)`. The phone apps' `Open in the app` opens `http://localhost:<port>` in the app's own full-screen page view, backed by a listener inside the app that runs only while that view is open. The web client's `Open` opens the port at its own address in a new tab.
- **The web client's address, only on the self-hosted relay.** A browser tab cannot listen on a port, so the web client opens a shared port at `https://<port>-<machine label>.<relay's domain>/`. The relay passes the connection through by its server name to the machine, which holds that name's certificate and ends TLS itself, so the control plane never decrypts it. `Open` first fetches a one-time ticket over the encrypted channel, good for 60 seconds, which the machine trades for a cookie scoped to that address (`HttpOnly`, `Secure`, `SameSite=Lax`), living until the port stops being shared or the device is revoked; any request without it gets a plain 404. The machine rewrites the `Host` header to `localhost:<port>` on the way in, so a dev server that answers only `localhost` answers. A page that sends itself to `localhost`, a sign-in callback for one, leaves the tab. The Workers relay cannot pass TLS through, and TLS is never ended at Cloudflare, so on it the web client's row reads `This relay cannot pass a port through. Open it from the desktop or phone app.` in place of `Open`: a true gap of the Workers relay.
- **Only listed ports, only loopback.** The machine forwards only to a port on the list, and only to its own loopback (`127.0.0.1` and `::1`); a forward to any other port, host or address is refused. The list exists because a forward puts the server on another device's loopback, where every program on that device can reach it; it is a choice made once per port, not a gate on the person, and every one of their devices may open every shared port.
- **Under it.** Each TCP connection the device's listener accepts becomes one byte stream on the device's encrypted channel, which the machine connects to its loopback port. The streams share the channel with the terminal's and use the same backpressure and bounded buffers, so plain HTTP, WebSockets and HTTP/2 all pass. Preview opens no listening port on either host with one exception: on a Windows computer whose service runs in WSL, where WSL cannot carry a dev server's port to Windows, the service's Windows half carries it on a Windows loopback port of its own, bound to this machine only, which any program on this machine can reach. A shared port there connects to the distribution's own loopback, where the dev servers run. The agent's browser tools act on Preview's page on the machine, never on a shared port.

### The encryption envelope

Traffic is end-to-end encrypted between each of the user's devices and each of the user's machines. The control plane carries ciphertext and forwards it; it does not hold the keys, cannot read a frame, and stores no plaintext.

**Keys.** Every machine has one identity key, the service's Ed25519 key. The machine's id is minted at the service's first start; the identity key is minted under that id in the credential store, at that same first start, and again only when a removed machine is linked again. The key is kept in the operating system's credential store as its own item, through `@napi-rs/keyring` on macOS and Linux and on Windows through the service's Windows half at `CRED_PERSIST_LOCAL_MACHINE` ([ADR-020](../decisions/020-cli-identity-key-storage-custody.md)), and never leaves the machine; a move between Windows and a WSL 2 distribution carries the store, while the key's item stays in Windows' Credential Manager for both sides, so the key and every device's pin stay as they were. A phone or browser has its own identity key, made on the device and never exported: P-256 in the iPhone's Secure Enclave, in the Android Keystore (StrongBox where there is one), and a non-extractable WebCrypto key in the web client. Every public key carries its algorithm (`p256` or `ed25519`), and a key with an unknown tag is refused.

**A device pins each machine's key.** A device keeps every machine key its chain trusts and checks it in every handshake. A machine that answers under a known id with a different key, and no later `runtimenode.added` statement for that id behind it, is refused outright, with no way to continue past it: `<machine> is using a new key, so it was not connected. If you reinstalled it, remove it on Devices and link it again.` A removed machine that is linked again first mints a new identity key under its same machine id, and its new `runtimenode.added` moves every device's pin for that id; from that point a statement the old key signs is refused, what it signed before stands, and the old key is never trusted again. The control plane keeps only the machine's current key, on its `runtime_nodes` row.

**The channel.** A channel joins one device and one machine and carries every session and screen on that machine. When the device is the desktop app on another machine, that end is its own machine: its service holds the channel and its keys, and the app reaches the other machine through it, so the main process holds no key. It is the Noise Protocol Framework's `Noise_KK_25519_ChaChaPoly_SHA256` handshake and transport, a published, formally analyzed protocol, with no construction of the product's own: nothing is designed here beyond choosing the pattern and the rekey schedule ([ADR-010](../decisions/010-tokens-passkeys-and-the-remote-channel.md)).

- **Why `KK`.** After linking, each end already knows the other's static key: the device holds the machine's key from its chain, and the machine holds the device's. A handshake from a key the chain does not hold fails, with nothing to click past.
- **Channel keys.** Noise's curves are 25519 and 448, and the Secure Enclave holds only P-256, so every device and machine keeps an X25519 channel key beside its identity key: the machine's kept in the credential store as its own item, like its identity key; on the phones in the Keychain and the Android Keystore's wrapped storage; in the web client a non-extractable WebCrypto X25519 key. The channel key's public half is certified by the identity key in the same `device.linked` or `runtimenode.added` statement that trusts it, so the chain stays the one record of trust.
- **Rekeying.** A fresh handshake runs on every connection and every 10 minutes on a long one, inside the channel, on the connection's profile, and the old keys are erased: traffic before a rekey stays closed to anyone who later takes a device's or machine's memory, and someone who took the channel's keys without the static key loses the channel at the next rekey.
- **Profiles.** A channel profile is one full Noise protocol name, and there is exactly one, `Noise_KK_25519_ChaChaPoly_SHA256`. The connection's first frame, before any handshake message, carries the channel version and the profiles the connecting device runs, in its order of preference; the machine answers with the first of them it also runs, or closes the connection with `channel.no_common_profile` when it runs none, with nothing to fall back to. Both ends put that offer and answer, byte for byte, into the handshake's prologue, as the Noise specification provides for negotiation data, so a relay that dropped or reordered a profile makes the handshake fail on both ends. With one profile, the negotiation takes it or refuses: nothing weaker is offered.
- **Not post-quantum.** The handshake's X25519 exchange is not post-quantum: someone who records a channel's traffic today could open it once a large enough quantum computer exists, and nothing in the classical channel protects against that. No reviewed hybrid profile of Noise exists yet; the one in progress, `Noise_XXhfs_25519+MLKEM768_ChaChaPoly_SHA256`, is an open working draft with no formal analysis ([libp2p/specs#727](https://github.com/libp2p/specs/pull/727)). The channel ships no draft and no second, TLS-based connection. Moving to the hybrid `KK` profile, once its specification is finished and reviewed for production use, joins as a second profile in the same first frame, ahead of the classical one, on the same channel keys and frames, and a machine stops accepting the classical profile once every device linked to it offers the hybrid one.

**What the relay sees.** The device id and machine id at connection, the channel version and the profile the connection took, frame sizes and times; never a method, a name or a byte of a session. The relay is a live forwarder, not a mailbox: it holds a frame only for as long as the connection carrying it, and nothing survives both ends disconnecting.

**Relay access.** Negotiation hands a device a relay endpoint and a short-lived connect token bound to that device and that machine, never to a session; a token replayed for another device or machine is refused, and an expired one is refused. The relay holds at most one live connection per device key and one per machine key: a new connection under a key closes the one before it, so a phone moving from Wi-Fi to cellular reconnects cleanly. Two connections that keep displacing each other, three times within a minute, mean the key is in two places: the newest connection still wins, the relay flags the key, and that device's card reads `Seen in two places at once. Revoke it if you did not expect this.`

**Budget.** The relay forwards each device's frames as fast as the machine drains them; frames and bytes either way are bounded by the channel's per-connection backpressure.

**The relay's own key.** A relay whose certificate chains to a root the operating system trusts is checked by the platform's certificate validation and its host name. Only a relay without a publicly trusted certificate has its key pinned when it is linked; a pinned relay whose key changed is refused and recorded (`relay.pin_refused`), `sidekicks daemon status` prints `refused: the relay's key does not match the one pinned when it was linked`, and `sidekicks relay repin --force` with the new hash pasted sends the daemon `relay.repin {spkiHash}`, which accepts the new key, or refuses and changes nothing when the hash does not match the key the relay presents. The machine-key pin above holds on either relay, whatever its certificate.

### A machine that cannot be reached

A machine is reachable while its service holds its relay connection, and after 45 seconds without a frame it reads `Not reachable · last seen <when>`, read from the relay connection, with no heartbeat table and nothing written to a session's log ([Spec-002 §Required Behavior](002-machine-registration.md#required-behavior)). A device then says so plainly — `<machine> is not reachable`, with `Retry` — rather than appearing to work. A session on a machine that cannot be reached stays in the list exactly as it was: no row dims, grays, moves or leaves it. Nothing is queued on the control plane, so there is no backlog to drain when the machine returns and no illusion that a message sent into a dark session will be delivered later. What the device already holds stays readable; a card waiting on the person shows why it cannot be answered now; anything that needs the machine refuses and is retried by the person once the machine is back.

## Interfaces And Contracts

Described here, not schematized; the shapes belong to Plan-025 and the contracts.

- **The device registry and the chain.** On the control plane, one durable row per linked device: its id, its name, its kind and platform, when it was linked, when it was last seen (written by the relay at most once a minute), its public identity key with its algorithm tag, its push address, and whether it has been revoked; one `runtime_nodes` row per machine, the machine's registration with its current identity key ([Spec-002](002-machine-registration.md)), a machine's key never kept in the device registry; and the account's statement chain, in `trust_statements`. Each machine keeps its own verified copy of the chain and the devices it trusts, with each device's notification switches and push keys. The registry and the chain are the single answer to "which devices can act as me".
- **`device.*` methods.** `device.list` (a live read of the machines, devices and passkeys with each one's connected state and last-seen time), `device.linkStart`, `device.linkRedeem`, `device.link`, `device.linkCancel`, `device.rename`, `device.revoke`, `device.forget`, `device.statementList {after}` and `device.pushAddressSet {platform, address}`, on the control plane; `device.statementApply {statements}`, `device.trustedList` and `device.notificationSettingsSet`, on each machine over the channel. Reachable from any non-revoked device, and from the CLI.
- **The desktop app's control-plane calls.** The background service takes the desktop app's calls as `controlPlane.call {procedure, input}` on its local socket, its schema in `packages/contracts/src/device.ts` beside the procedures it forwards, attaching the hosted account's access token and signing each request's DPoP proof; `procedure` is one of `device.list`, `device.linkStart`, `device.linkRedeem`, `device.link`, `device.linkCancel`, `device.rename`, `device.revoke`, `device.forget`, `device.statementList`, `device.pushAddressSet`, `runtimenode.rename` and `runtimenode.remove`; relay negotiation or any other procedure is refused.
- **`runtimenode.*` methods.** `runtimenode.register`, `runtimenode.rename`, `runtimenode.remove` (posting `runtimenode.removed`) and `runtimenode.certificateChallengeSet` ([Spec-002 §Interfaces And Contracts](002-machine-registration.md#interfaces-and-contracts)).
- **Events on the device list.** Each statement is announced by an event that carries its kind as its name — `device.linked`, `device.renamed`, `device.revoked`, `passkey.added`, `passkey.removed`, `runtimenode.added`, `runtimenode.renamed` and `runtimenode.removed` — beside `device.forgotten` and `runtimenode.registered`, all carried by the `device.list` live read; event-driven, with no polling.
- **Push.** `push.send`, the machine's sealed notice handed to the relay with the device's push address; the relay adds the person's own APNs, FCM or VAPID credentials and stores nothing about the notice.
- **Presence.** Each device sends `presence.heartbeat`, carrying `PresenceHeartbeat`, on each machine connection it holds, when `appVisible` changes and otherwise every 15 seconds; `appVisible` means an app window is in front on that device. The machine keeps the last heartbeat per device in memory only; the relay sees only encrypted frames. `presence.read {}` and `presence.subscribe {}` report the devices connected to this machine and whether an app window is in front on each, with no session id.
- **Shared ports.** `preview.portShareList` (a live read), `preview.portShareAdd {port}`, `preview.portShareRemove {port}`, `preview.portTunnelOpen {port}` and `preview.portTunnelClose` (one byte stream per accepted TCP connection, at most 256 KB buffered each way), and `preview.portTicketIssue {port}` for the web client's address.
- **The live picture.** `preview.screencastSubscribe`.
- **Folders on another device.** `repo.folderList {path?, filter?, showHidden?}`, answering with each entry's path, and `repo.attach {localPath}` with the path of the folder the device was shown.
- **The channel's first frame.** `{channelVersion, profiles}`, answered `{profile}` or closed with `channel.no_common_profile`.
- **Relay refusals.** `relay.pin_refused {relayHost, pinnedSpkiPrefix, presentedSpkiPrefix}`, recorded on the daemon's own service session, and `relay.spki_mismatch` (412); each prefix is the first 8 bytes of its hash. The recovery is `relay.repin {spkiHash}`, a bare verb on the `relay` root, sent by `sidekicks relay repin --force`.
- **The Devices page.** The registry rendered in Settings: the machine, device and passkey cards, linking on both sides and the shared-ports list (§Device registration and revocation, §Shared ports).
- **The command line.** `sidekicks devices` with `link`, `rename`, `revoke` and `forget`; `sidekicks relay repin --force`; and the relay block of `sidekicks daemon status`, the `relay` field of `daemon.status.read`.

## Fallback Behavior

- A machine cannot be reached: the device reports it as not reachable, reads stay available from what the device already has, and writes refuse rather than queue.
- The relay cannot be reached but the device is the desktop app on the same machine: it uses the local pipe and keeps working.
- A device's connection drops: its card reads `Last seen <when>` from the end of that connection, read from the relay connection with no heartbeat, and on reconnect it runs a fresh handshake and resumes every stream from its last event, with no gap.
- A device has been revoked: its channel is closed, its next call takes a terminal refusal, not a retry loop, and its screen says it was revoked.
- A machine answers with a key the device has not pinned and no rotation statement behind it: the device refuses the connection, with no way past it.
