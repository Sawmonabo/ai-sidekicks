## Purpose

Define how multiple agents collaborate inside a session and how their run relationships are represented.

## Scope

This spec covers parent-child run linkage, cross-agent collaboration, and background helper activity — including session goals, cost derivation for budget enforcement, and the orchestration-level governance of provider-native in-session subagents.

## Non-Goals

- Workflow authoring syntax
- Defining provider-native subagent APIs — the `subagentPolicy` and driver-op shapes are [Spec-004](004-provider-driver-contract-and-capabilities.md)'s; this spec governs only their orchestration use (§Provider-Native Subagents)
- Notification policy

## Required Behavior

- A session must support multiple active agents at once.
- Agents collaborate inside the session itself: orchestration runs, the agents they run and their child runs all live in the session.
- Cross-agent communication **inside one session** must use persisted run linkage, the session timeline child runs publish into, artifact references, or approvals, and V1 adds no direct run-to-run messaging primitive between agents of the same session. Reaching **another session** is a different act with its own surface (§Sessions Talking To Each Other).
- Parent-child run relationships must be durable and auditable.
- Internal helper runs must remain distinguishable from user-visible agents while still appearing in canonical history.
- Per-agent model and driver selection must be allowed within one session; every agent runs on the machine that runs the session.
- Orchestration must remain valid even when a driver has no native subagent concept.

### Sessions Talking To Each Other

A session reaches another session through **one tool the daemon serves to both providers**: `SendToSession {to, message, files}`, with `ListSessions {}` beside it naming every session of the person's on either provider — a Codex session the person typed in a terminal included, while its terminal is open — and whether each is working or idle. Both ride the daemon's one MCP `url` entry for that session, on the daemon's own tool route, under the server and namespace name `sessions`, in the providers' own casing. That tool is the only path between two sessions, so a message draws the same pair of rows whichever provider sits at either end.

**`to` is a name, and `files` are paths.** `to` is the other session's name as `ListSessions` prints it and never an address: the daemon holds the directory of its sessions and resolves the name to whatever that session is actually reached by, so no model ever handles a socket path. `files` is optional — a list of paths the sending session can already read, which the daemon copies at send time and stages into the **receiving** session as that session's own attachments, through the ingest pipeline every other attachment takes ([Spec-012 §Ingest Validation And Payload Bounds (V1)](012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1)), so they arrive there as paths the receiving model opens with its own file tools on either provider. Both rows carry the file chips a sent turn's own attachments carry, and this runtime sets no bound of its own beyond that pipeline's. The daemon reads each path as the person's own user at send time, and a path that does not exist or cannot be read fails the call with that path named in the tool result rather than arriving as an empty attachment. Nothing gates it a second time: the receiving session runs as the same person on the same machine and could open that path itself, so a second check would refuse nothing it can already reach. The provider's own file-sending tool is neither waited for nor mirrored: its maker keeps it switched off for every session behind a server flag, so nothing here rests on it, and this path stands unchanged the day it turns on — and because that tool is not on this path at all, the size and count bounds its own build carries never apply to a message's `files` ([provider-wire reference, claude.md](../reference/provider-wire/claude.md)).

**A message carries what the tool's three fields carry — the sender's own words and the files it names — and nothing else.** Never a transcript and never a context window, so two sessions in an exchange see each other's finished answers the way two people do rather than reading over each other's shoulders. Context moves only where something is converted — a session changing provider, or a plan handed to a session running on the other one — and there it moves as the hand-over brief rather than as a message (§Same-Agent Provider Switch).

**How the tool is declared.** Every session the daemon starts carries one MCP `url` entry pointing at the daemon's own tool route, and the operations are served there — never as a tool server inside Claude Code's own process and never as a Codex dynamic tool. A Claude Code session's model reads the tool as `mcp__sessions__SendToSession`, and a Codex conversation's reads the same `sessions` namespace with the tool beside it. A send is an ordinary tool call under the **sending** session's own permission level: the levels that ask raise the ordinary approval card, `Sandboxed` and `YOLO` ask nothing, and no switch, setting or cap of this runtime's gates it. The level applies on Claude Code through `can_use_tool`; on Codex the entry carries `default_tools_approval_mode = "approve"` and a `tool_timeout_sec`, so that provider asks nothing and the daemon applies the same level rule itself before routing. What the message then causes in the **receiving** session follows that session's own level, exactly as words typed there would.

**A session starts with exactly the tool servers switched on for it.** The daemon starts that set and no other, and declares it through each provider's own means: on Claude Code as the `--mcp-config` set together with `--strict-mcp-config`, so the session reads that set and no other tool-server configuration on the machine; on Codex as the conversation's own `mcp_servers` configuration at `thread/start`, each switched-on server a `url` entry on the daemon's route under its own name, with the daemon's own MCP client holding the real connection (§Provider-Native Subagents). A server that is switched off is never declared, so it costs the model no tool definitions at all, and a switch flipped while the session is running reaches Claude Code when its process is next reopened and Codex at its next turn.

**How a message is delivered.** Into a Claude Code session it is one user frame written to that session's own address, carrying the true sending session's name, so that provider's own repeat and flood protections apply with the provider's own numbers ([provider-wire reference, claude.md](../reference/provider-wire/claude.md)). Into a Codex conversation it is `turn/start` carrying the message where the conversation is idle, and `turn/steer` where a turn is running, which folds it in at the next message boundary. A busy session is reached on either provider, and the message lands inside the turn that is running rather than waiting for the next one. The daemon starts every Claude Code session of its own with inbound session messages accepted, so a message to a session of this runtime's is never held for that reason; a `held` answer arises only on a session the person started in their own terminal, where that session's own inbound setting rules.

**A reply is read off the receiving session's own record.** One provider routes a peer-prompted turn's answer back to nobody at all — the writer is told nothing and no connection is made to the address the sender declared — so the answer exists only on that session's own record, and the daemon reads it there ([provider-wire reference, claude.md §A message from another session arrives on the session's own address](../reference/provider-wire/claude.md#a-message-from-another-session-arrives-on-the-sessions-own-address)). Which record depends on who started the session and on nothing else. For a session this product started it is the daemon's own stream, which it can read because it is the daemon that runs that process. For a Claude Code session the person typed in their own terminal it is that provider's own transcript file, whose folder and name the provider's live-session registry gives, read only from the daemon's own message onward: the record of the arriving message carries the id it came in with and the answer is chained back to that record, so a reply is paired to the message it answers, and a line lands within a quarter second of the moment it carries ([provider-wire reference, claude.md §A reply comes back when the message asks for one, and the transcript pairs it to its prompt](../reference/provider-wire/claude.md#a-reply-comes-back-when-the-message-asks-for-one-and-the-transcript-pairs-it-to-its-prompt), measured 2026-09-21 at `2.1.278`). So the reply a row shows is what that session actually said. Nothing is added to the message to make this work — no instruction line asking for an answer, and no tool call asked of a session in the person's own terminal — and the daemon's own inbox is the `from` address on every delivery, so a reply a far model chooses to send of its own accord lands there too and is drawn as the same one row rather than a second. That is why `replied` is a reading rather than a return value, and why `not delivered` is a reading too: it is that registry's own status for the session going idle with no record of the message.

**What the daemon keeps.** A directory of its sessions and their addresses, looked up at send time so nothing dies with a provider process. An exchange table naming who is talking to whom and how many messages the two have traded since the person last wrote in either; that count travels into the message the receiving model reads, as a fact and not a limit. And, for a paused session, a queue of everything addressed to it, delivered one at a time in arrival order when it continues.

**The daemon's queue is what keeps a message out of a paused session, and it is the only thing that does.** A pause on this product's own boundary is a hold inside the provider's tool callback: a frame written to that session's address during the hold is not read while the hold lasts, and it is not lost either — it lands a few milliseconds after the held tool's own result and folds into that same turn, and the model acts on it in the same answer. The hold puts nothing on the wire, so from outside a held session is indistinguishable from an idle one ([provider-wire reference, claude.md](../reference/provider-wire/claude.md)). Two consequences follow. The daemon never writes to a paused session's address in the first place, which is what makes `queued, builder is paused` an honest reading rather than a guess about the provider. And a session in the person's own terminal, writing straight to a paused session's address with no daemon in the middle, is read when the hold releases rather than held out — the queue is the daemon's, not the provider's.

**A provider's own send to another session is closed.** The daemon registers a `PreToolUse` hook on Claude Code's `SendMessage` — declared in that session's `initialize` request and answered over the wire the way the pause hooks are, so none of it is a script on disk — which denies a send whose target is another session and answers the model `send with SendToSession`, so a message between two sessions cannot take a second path or draw a second shape. It judges the target from the call's `to` alone: an address (`uds:` or `bridge:`), or a name that is a session in the daemon's own directory or in that provider's live-session registry (`sessions/<pid>.json` under its config folder), is denied, and a `\\.\pipe\` name is an address here exactly as that provider's own target resolver reads it ([provider-wire reference, claude.md §A message from another session arrives on the session's own address](../reference/provider-wire/claude.md#a-message-from-another-session-arrives-on-the-sessions-own-address)); any other name is one of the session's own subagents or teammates, and that call goes through untouched. The two sets cannot overlap, because the daemon never names a session as seventeen lowercase hexadecimal characters, which is the shape a subagent's id takes.

**The hook answers in the one form that hands the model the reason alone.** Its answer is the JSON decision — `permissionDecision` `deny` with `permissionDecisionReason` `send with SendToSession` — and nothing else. The other form the provider accepts, a refusal carried as an error, is not used: the model then reads the reason wrapped in an error naming this product's own file path, which tells it about our plumbing instead of about the tool it should have called ([provider-wire reference, claude.md](../reference/provider-wire/claude.md)). Either way the refused call stays **on the record** — the turn's own list of permission denials carries it with its full input — and that record, not an absence, is what the sending session's row reads when it says a send never happened.

**An interrupt reaches both ends.** Interrupting a session that is in an exchange ends the turn here and the turn there and empties the queue between them, because one press on one side would otherwise leave the other side free to wake it again. This is the one place an intervention reaches past the session it was aimed at, and it reaches exactly one further session — the one on the other end of the exchange — by the pair the exchange table already holds; it is a fan-out of ordinary interrupts, one per run, and not a cascade primitive (§Intervention Propagation). Each transcript records what the interrupt reached, including how many messages were not delivered.

**Nothing in this runtime bounds how many messages two sessions trade.** Each provider's own limits flow in with that provider's own numbers, and the one bound the person can set is `Max steps per turn` ([Spec-003 §The Step Bound On A Turn](003-queue-steer-pause-resume.md#the-step-bound-on-a-turn)), which is `Unlimited` on both providers until they set a number — on Settings › Runtime for every session, with a per-session override (§Interfaces And Contracts). Claude Code is passed `--max-turns` only when a number is set, and a change reaches a running session by reopening it by id at its next turn; on Codex the daemon counts the turn's steps itself and sends `turn/interrupt` at the number. A turn that reaches the bound ends there with `run.step_limit_reached` carrying the count, drawn with `Continue`, whose press carries the turn on, as a message arriving from another session also does.

**A session the person started in their own terminal reaches these sessions two ways, and the first needs nothing installed.** Every session has an address, offered on screen as `Copy address`; a Claude Code session in the person's terminal writes to it, and the message arrives as that provider's own peer delivery, which the daemon reads off the receiving session's stream and draws as the same row. An optional Claude Code plugin, built after this surface and never required, additionally gives such terminal sessions `SendToSession` and `ListSessions` by name and hands a peer delivery to the daemon before the model reads it; with the plugin absent, switched off or failing, the address and the stream frame are the behavior, so nothing in the daemon depends on it ([ADR-037](../decisions/037-claude-code-mods-are-an-optional-terminal-bridge.md)).

**A Codex session the person typed in a terminal is reached through one shared Codex service.** That provider gives a session no address of its own, so the only way in is a Codex service the daemon runs on the person's **own** Codex folder, which a plain `codex` typed in a terminal joins by itself. The daemon runs that service while the Codex switch `Reach Codex sessions started in a terminal` is on, and it is on by default; the switch sits under Codex alone, because the mechanism is that provider's alone ([Spec-021 §The surface set](021-desktop-app-and-renderer.md#the-surface-set)). A session that joins the service is in the daemon's directory and is reached by the agents, not by the person from here: `ListSessions` names it while its terminal is open, with `Codex` as its provider and whether it is working or idle, and `SendToSession` delivers to it as to any session, each exchange drawing its rows in the sending session and the exchange line on that session's row. It has no row in the sessions list, no heading of its own, no window and no screen here; the person reads it and types in it in their own terminal. Three limits hold, because both the folder and the process are the person's rather than the daemon's. The daemon writes nothing into that folder's configuration except the trust records its own terminal-session hooks need: when the service starts, before any conversation loads, it writes trust for exactly its pre-tool hook — which reports a command, carries the pause and refuses a tool the agent lacks — and its post-tool hook, through Codex's own `config/value/write` into that folder's `config.toml`, refreshes a record when a hook's command changes, and never cleans, rewrites or reorders any other entry, so those hooks reach a session the person started in a terminal as they reach ours; Codex keys a trust record by the hook's position rather than its command, so where the person also passes their own `-c` hooks to a `codex` process on that folder, each side's trust write marks the other's hooks modified until they are trusted again. It never moves such a session between accounts. And it stops the service only when the switch goes off **and** no terminal session is still inside it.

**What the daemon starts, and what joins it.** The service is `codex app-server --listen unix://<the Codex home's control socket>` — `app-server-control/app-server-control.sock` under that home — and never `codex app-server daemon start`, whose subcommand set carries an updater that can replace the person's install mid-work; it speaks websocket over that socket, so the daemon holds a websocket seat on it rather than a byte stream ([provider-wire reference, codex.md](../reference/provider-wire/codex.md)). A plain `codex` joins whatever is listening there whichever folder it was typed in — the socket is per Codex home, not per folder — while `codex -c …`, `codex -p …` and `codex exec` each run alone and never appear in the directory. Killing the service kills no terminal session: a session whose service comes back within about five seconds reconnects by itself, and one whose service has been away about twenty-four seconds has given up and answers nothing further, its transcript intact and reachable by `codex resume <thread id>`. Three consequences for the daemon. The service comes back on the same socket **before anything else** when the daemon restarts, so a session inside the reconnect window never notices. The daemon's own stop confirmation names the terminal Codex sessions that are inside the service, because stopping it is what strands them ([Spec-006 §Required Behavior](006-local-ipc-and-daemon-control.md#required-behavior)). And a session that was stranded is read as not reachable: `ListSessions` says so, and a send to it reads `not delivered` on the sending session's exchange row, whose second line is the reason, `Reopen it in your terminal: codex resume <thread id>`, with no `Retry`, since sending again cannot reach it.

**One service per Codex account, not one per person.** The service on the person's own Codex folder is the same mechanism, under the limits above: every Codex conversation on one account runs inside one service in that account's own Codex home, because the socket is per Codex home and a credential home is what a service is started on, so two accounts are two services and the account is the sharing key ([provider-wire reference, codex.md §The shared `app-server` a terminal `codex` joins](../reference/provider-wire/codex.md#the-shared-app-server-a-terminal-codex-joins)). Every session that follows the provider's current account runs in the one service the daemon keeps for the current account, and a session pinned to an account runs in that account's own service. Claude Code stays one process per session, that provider offering nothing else ([Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior)). Four conditions come with the sharing. A conversation's folder, its configuration and its tool servers are its own, passed at `thread/start` and never as a flag on the service that holds it; a terminal session that joins runs its commands in the folder the person typed `codex` in, which `thread/started` names as the conversation's `cwd`, whatever folder the service itself runs in. A change to a conversation the service already holds — its configuration, its base instructions, its developer instructions — is applied where that provider honors it, at the conversation's next turn, and is measured against the running build before it is relied on. And a service that dies is started again by the daemon with every conversation in it resumed through that provider's own resume, each such session carrying one faint row in its transcript that says so.

**Windows puts the daemon on the providers' side of the boundary.** A Claude Code session's inbox is a Unix socket on macOS and Linux and a named pipe on native Windows, and the daemon's own inbox there is a named pipe too, so delivery, a session's address, `Copy address`, the provider's own brakes and the hook's target rule are the same on every platform and only the address object changes. The two halves of one Windows computer cannot see each other: a daemon on native Windows and sessions inside WSL 2 reach neither each other's inboxes nor each other's session registries. So the daemon runs on the same side as the providers it drives. On a Windows computer whose Claude Code and Codex live in WSL 2, the background service runs in that distribution as the daemon together with the service's Windows half — one service per computer, started by a per-user logon task that keeps one attached `wsl.exe` — and the desktop app and the command line on Windows reach that daemon over one per-user named pipe, the same one a daemon on native Windows serves, carried by the Windows half and failing closed at the server and the client ([Spec-006 §Fallback Behavior](006-local-ipc-and-daemon-control.md#fallback-behavior)). The Codex legs are the same on every platform by construction: the daemon holds the seat on every Codex process it starts or joins, so a Codex session of ours sends and receives the same way on macOS, Linux, WSL 2 and native Windows, and a terminal Codex session is reached through the shared service wherever that service listens — `turn/start` on its thread when it is idle, `turn/steer` when it is busy, its reply the thread's own events on the daemon's seat ([codex.md §A second seat on the shared service](../reference/provider-wire/codex.md#a-second-seat-on-the-shared-service)). The seat sees a joined terminal's thread the moment the terminal connects; lifecycle notifications reach every seat unasked, while a thread's turn and item events reach the seat only once it has resumed that thread with `excludeTurns: true`, which leaves the terminal undisturbed; a `turn/start` from the seat runs and the terminal shows the message and the reply as its own rows; and a `turn/steer` carrying `expectedTurnId` folds into the running turn, which is the one race-free form. The seat resumes and subscribes to a terminal's conversation only for an exchange it sends and lets go when that exchange ends, and never while `thread/backgroundTerminals/list` shows a command of that conversation still running, because unloading a conversation kills a command it is running. How long a terminal Codex session stays in `ListSessions` is read off the service: the daemon starts it with `thread_unload_delay_secs` set to five seconds, and once neither the terminal nor the seat holds the conversation and no turn or command is running, the service sends `thread/closed`, about five seconds after the terminal quits; a terminal closed mid-turn or mid-command reads working until that work ends. Where an approval request goes when two seats hold one thread is measured before that row is drawn. Nothing in this section has been measured on Windows, for either provider: the Claude Code probes owed there are the named-pipe delivery, the registry read and the deny rule; the Codex probes are the service's listen form on native Windows (`--listen unix://` or a pipe), the plain `codex` join and `codex resume`; and for both, the WSL 2 split above.

**Every message is two rows and nothing else.** The sending session's transcript carries one row for the send and the receiving session's one row for the arrival, both of them the ordinary tool events the transcript already folds — so a message mints no row kind, and nothing of a message is persisted beyond those events ([Spec-021 §The surface set](021-desktop-app-and-renderer.md#the-surface-set)).

**The person writes to another session from the composer.** A draft that begins with a session's `@name` is addressed to that session: it is one Send, carried by `run.queueCreate` with an addressee member `to` naming the session ([Spec-003 §Interfaces And Contracts](003-queue-steer-pause-resume.md#interfaces-and-contracts)), and the daemon routes it there, where it arrives as that session's own row rather than starting a turn on this one. A session's `@name` later in a message to this session's own agent stays a mention.

## Default Behavior

- Default collaboration mode is explicit: new child runs are created only by user request, by workflow definition, or by an agent's own tool call through the cross-provider bridge of [Spec-027 §Required Behavior](./027-agent-definitions-and-peer-invocation.md#required-behavior) — a provider's own in-session subagent starts no canonical child run and so sits outside this rule (§Provider-Native Subagents). The third arm does not weaken the default, and is admitted here rather than treated as an exception to it: such a call is adjudicated at call time under the session's permission level exactly as any other tool call in that session is, so no child run of this origin can exist that the session's own level does not admit. Every other constraint in this section applies to such a child unchanged: it is subject to the budgets of §Budget Policies and the approval pipeline at whatever depth it sits, and it publishes into the parent timeline like any other child.
- Child-run output defaults to publishing a summarized row into the parent session timeline, with expandable detail.
- Orchestration runs, the agents they run and their child runs belong to the session that holds them and are visible across that session.
- The runtime adds no depth limit of its own to delegation. A child run may create child runs of its own, and those may create their own; how deep agents may nest is the provider's own limit under the person's own provider settings, and where a provider refuses a level, its refusal is shown in its own words. Every other rule binds at every level: the budgets of §Budget Policies, the approval pipeline, and the visibility rules of §Provider-Native Subagents.
- Concurrent child runs are allowed, and the runtime adds no count limit of its own on how many a session may have. How many agents a provider will run at once is that provider's own limit under the person's own provider settings; where a provider refuses, its refusal is shown in its own words.

## Fallback Behavior

- If a driver does not support native subagent creation, the runtime must model delegated work as separate runs with explicit linkage in the parent's session.
- If child-run detail loading fails, the summary row remains available and marked incomplete.
- If child-run creation is refused, the runtime must reject the request with the explicit reason rather than silently dropping it or starting work it did not admit.
- **A send to another session that did not land says which thing happened, and never more than happened** (§Sessions Talking To Each Other). `refused: <reason>` carries the provider's own words where the provider refused it — a target that has ended, a message past that provider's own size bound, a declined approval on the sending side. `not delivered` is the receiving session finishing its turn and going idle without the message ever appearing on its stream, which is how a silent drop by the receiving provider's own repeat or flood protection is reported; it is never reported as delivery. `held by builder` is the receiving session's own inbound setting holding the message, opening to that session's own words, and nothing in this runtime approves it. `queued, builder is paused` is the daemon holding it for a paused session, which the continue delivers in arrival order. The sending row rests at `sent` until one of those is known, so a state is a fact the daemon observed rather than an acknowledgment of the write, and every state after `sent` reaches the sending model once as one short note telling it not to send again straight away.

## Interfaces And Contracts

- **Agent surface:** Plan-014 owns the V1 agent identity surface satisfying §Required Behavior's per-agent model/driver selection — `agent.configUpdate` / `agent.list`, the agent's provider binding durable on the records below and the provider-binding events ([Spec-005 §Agent Lifecycle](005-session-event-taxonomy-and-audit-log.md#agent-lifecycle-session_lifecycle)). `agent.list` is a live list — the list, then each change, as `session.list` is — and each entry carries the agent's provider binding, the definition it was resolved from, which provider runs it, its place in the session's agent tree, and any switch still pending against it, so `switching to …` survives a reload and reaches another device. There is no attach or detach verb: a session's main agent is the one it starts with, and every other agent in the session arrives because that one delegated to it or because the user named one in the composer — a row in the composer's `/` list, which writes that agent's name in its provider's own form into a message to the main agent. The main agent's provider runs it: as the provider's own subagent when the definition runs on that provider (§Provider-Native Subagents), or, when it is bound to the other provider, as a run the cross-provider bridge's `run` verb admits. No console control calls `orchestration.runCreate`. **No event exists whose only job is to create an agent record, so every row in the `agents` projection is born from the durable record of that agent's own start.** The session's main agent is born with the session: `session.created` carries its id together with the binding and configuration the daemon resolved for it, and that event is its row's creating record ([Spec-005 §Session Lifecycle](005-session-event-taxonomy-and-audit-log.md#session-lifecycle-session_lifecycle)). An agent a run starts under an agent definition — the run a peer invocation admits included — is born from that run's own `run.queued` record, which names the agent and carries what admission resolved for it ([Spec-005 §Run Lifecycle](005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)). The provider-binding events only ever settle a row one of those records created (§Same-Agent Provider Switch). A provider's own in-session subagent has no row in `agents` at all: it is not a canonical child run and holds no persona of its own, and it is visible through the registered `subagent.started` / `subagent.completed` pair and through the daemon's own tree index (§Provider-Native Subagents). `OrchestrationRunCreate`'s agent target resolves against this surface; an unknown or not-ready agent is a typed refusal.
- `OrchestrationRunCreate` must allow parent linkage and a target; the run lives in the caller's session. The target is either a live agent (`{targetAgentId}`) or a saved agent definition that has no live agent yet (`{targetDefinitionId}`), so a lead or a workflow's `agent.run` step can start a saved definition. No console control calls it; its callers are the cross-provider bridge's `run` verb ([Spec-027 §Required Behavior](./027-agent-definitions-and-peer-invocation.md#required-behavior)) and a workflow's `agent.run` step.
- `OrchestrationRunCreate` failure must surface an explicit typed rejection carrying its own reason, never a silent drop.
- `ChildRunLinkRead` (`orchestration.childRunLinkRead`) must expose parent-child relationships for the whole session: it is a read of the daemon's own agent tree index at every depth, and each agent's entry carries its head facts — model, effort, the agent that was asked where it was a peer call (`via <agent>`), tokens, spend, start time and its ancestry — beside the counts the session's agent list draws: how many are live, how many in all, and how many are waiting.
- `InternalRunFlag` must distinguish internal helper work from user-facing agents.
- **How a child was reached:** a child's link to its parent records `reachedBy` — `provider_subagent`, the provider's own subagent, `bridge_run`, a bridge `run` call, or `workflow_step`, a workflow's `agent.run` step — durable in the run linkage, beside the agent the child runs, which is the agent that was asked. A `provider_subagent` link is written by the provider driver: Claude Code's subagent start and stop notifications and Codex's collaborating-agent events each add or close the run-link row for that subagent, so a provider's own subagents appear in the agent tree like any other child. However it was reached, a child appears in exactly three places, all fed by one source: a row in its parent's transcript where the dispatch happened, a row in the session's agent list, and its own child view. `reachedBy` is internal data: no screen, label or tag shows it or any word for how a child was reached; the screen shows the agent tree, each child's provider and model, and `via <agent>` naming the agent that was asked where the child was a peer call.
- **Budget surface:** session budget limits are readable and owner-adjustable via `OrchestrationBudgetRead` / `OrchestrationBudgetUpdate`. Both answer with the same budget state: the session's committed spend governed by §Cost Figure Display Consistency, and a per-agent axis carrying, for every member of the session's tree — a provider's own helper included — its own spend and its spend with the spend of every member under it routed up the parent chain at any depth, every amount in integer micro-dollars — a read and an update reply report the same number at the same fold state.
- **The surface a session's agent view reads:** `orchestration.runCreate` to dispatch, `orchestration.childRunLinkRead` for the parent-child links, `orchestration.budgetRead` for the session's limits, its committed spend and each agent's spend (§Cost Figure Display Consistency), and `orchestration.costReceiptRead` for the receipt §Session Cost Receipt mints, which the inspector's `Cost` section draws by provider and account, beside the agent surface's `agent.configUpdate` / `agent.list`. The events that surface folds are the `subagent.*` tool-activity rows (§Provider-Native Subagents), the provider-binding events (§Same-Agent Provider Switch) and `orchestration.rejected` (§Scheduler Limits). No caller on it re-folds a cost figure or re-assembles a tree from the rows it holds.
- **The session's agent tree is a daemon-owned index.** The daemon builds, per session, a parent-to-child index of every agent in a run's tree, read from the provider's own stream — on the Claude leg the task-started frame and the parent call id it carries, on the Codex leg the agent's turn-started frame — and **persists** it — one record per agent keyed by its run, its provider and its own id, holding the task id or thread id, the parent call or thread, and its state, written when the agent starts and when it finishes, and written by the daemon alone — because neither provider lists its subagents back on resume: after a daemon restart every agent is re-attached by the id the daemon stored at dispatch (the task id on one leg, the thread id on the other) and its rows replay from the provider's own record. That index is the single source of the tree every client draws, of every fan-out count (§Provider-Native Subagents), of the run ids the subtree sweeps iterate (§Intervention Propagation), and of the key by which a pause or an interrupt is routed to one agent rather than another — the agent id on the Claude leg, absent on a run's own calls, and the turn id on the Codex leg, whose session id is always the root's. **The durable handle for an agent is its run, its provider, and its own id together, never a bare agent id**, because neither provider mints ids unique outside the process that made them. Two consequences bind the daemon: it never sends the Claude leg's conversation reset to a session whose agents it means to keep — that reset leaves every settled agent's transcript on disk while making the provider refuse every resume of it, and nothing recovers them — and on the Codex leg an agent its parent shut down or evicted is reopened by its thread id.
- **The session-to-session tool is two operations the daemon serves to the providers, not a method of this runtime's own wire** (§Sessions Talking To Each Other). Both ride the session's one MCP `url` entry on the daemon's tool route, under the server and namespace `sessions`. `SendToSession {to, message, files}` answers with the session it reached and one state: `sent` when the call returned, and then, as the daemon learns it, `delivered`, `queued`, `held`, `refused` carrying the provider's own reason, or `not delivered`. `ListSessions {}` answers with one entry per session of the person's — that session's name, its provider, its account, and whether it is working, idle or not reachable, a Codex session the person typed in a terminal included while its terminal is open — drawn from the daemon's own directory rather than from either provider's listing, which is what lets one entry name a session on the other provider. `files` names paths the sending session can read; the daemon copies them at send time and stages them into the receiving session as that session's own attachments, so they arrive as paths rather than as bytes on the wire. A `SendToSession` call is an ordinary tool call under the sending session's own permission level — the levels that ask raise the ordinary approval card, `Sandboxed` and `YOLO` ask nothing, and no gate of this runtime's own applies — and what the message causes follows the receiving session's own level. Because both are tools a provider's model calls, neither is registered in a method-name registry, neither mints an error code, and a refusal is the provider's own words carried on the result. What the screen draws from them rides surfaces that already exist: the exchange line on a session's row is the peer's name with the count on that session's `session.list` entry, and a sent row's later states come over the run-state subscription, and the rows themselves are the ordinary tool events.
- **A provider switch settles as `agent.provider_binding_changed` or `agent.provider_binding_change_failed`** (§Same-Agent Provider Switch). `agent.provider_binding_changed` records that it landed: the session, the agent, the switch id, the actor, the binding it moved `from` and `to` (each with its account), the account the run landed on — kept apart from the binding's own account field, so an agent that follows its provider's current account is never pinned by a switch — the `continuity` that carried the conversation (`in_place` or `brief`), and the declared losses. `agent.provider_binding_change_failed` records that a switch accepted earlier did not land: the session, the agent, the switch id, the actor, the binding it stayed on (`from`), the binding it `attempted` (with its account), a `reason` — `driver_unavailable`, `model_unavailable`, `effort_unavailable`, `output_speed_unavailable`, `interrupt_refused`, `target_unstartable` or `account_unavailable` — and, with `account_unavailable`, the account's state: `reauth_required`, `home_missing`, `indeterminate` or `not_registered`. A change of model, effort or speed alone settles in place and draws no row.
- **`session.maxStepsUpdate {sessionId, maxStepsPerTurn}`** sets this session's own `Max steps per turn` over the Settings › Runtime value: a number, or `null` to follow that value again. It answers `{sessionId, maxStepsPerTurn?}`, is kept with the session's console state, refuses a value below 1, refuses a session id the daemon does not hold with `session.not_found` and keeps nothing, and is the owner's alone. Reaching the bound is [Spec-003](003-queue-steer-pause-resume.md#the-step-bound-on-a-turn)'s `run.step_limit_reached` (§Sessions Talking To Each Other).
- **`session.terminalProviderSessionList {}`** names the Codex sessions typed in a terminal that are inside the shared Codex service: `{sessions: [{name, threadId, state}]}`, `state` one of `working`, `idle` or `unreachable`, read off the same directory entries `ListSessions` names, so the agents and the Runtime settings page read one fact. It is read when a confirmation that would stop the service opens and while an update waits on those sessions, and nothing samples it on a timer; while `Reach Codex sessions started in a terminal` is off it is empty ([Spec-006 §Required Behavior](006-local-ipc-and-daemon-control.md#required-behavior)).
- **Every method that takes a `sessionId`** — the goal verbs, `session.maxStepsUpdate`, `orchestration.costReceiptRead`, `orchestration.runCreate`, `orchestration.budgetRead`, `orchestration.budgetUpdate`, `orchestration.childRunLinkRead` and `agent.list` among them — refuses a session id the daemon does not hold with `session.not_found` and appends nothing.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas (§Plan-014 — including the typed `OrchestrationRunConfig` shape and the `OrchestrationBudgetState` spend members — the session's committed spend and each agent's spend, in integer micro-dollars, carried on the budget read and update replies alike, specified in §Cost Figure Display Consistency below).
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes (§Orchestration / §Agent).

## State And Data Implications

- Run-link records must be durable and replayable.
- Parent-child linkage must survive recovery and replay.
- Internal helper visibility must be policy-aware but never silently omitted from audit history.
- The agent record additionally carries its provider account, its reasoning effort, its output-speed mode, and any switch still pending against it (§Same-Agent Provider Switch). These are columns on the `agents` table ([Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md)), because each is validated against driver-reported vocabularies or read outside the driver — the account by the [Spec-026](026-provider-accounts-and-credential-homes.md) spawn gate, the effort by the switch's own refusal check, the speed mode by the provider leg that applies it, the pending switch by the boundary hook and by `agent.list`. No table is added. The binding columns ride the record that creates the agent's row and the `agent.provider_binding_changed` event that moves them, never the row alone, so an agent's provider binding survives replay.
- The pending column holds **one** switch or none, which is what makes the one-pending-per-agent rule structural rather than advisory, and it holds the **pending** binding only: the effective binding stays in the account, model, driver, effort and speed columns and moves into them when the switch lands, so a projection read never shows a switch that has not happened yet. It is the one column of the row that is daemon state rather than a projection of the event log, because no event records a switch being asked for: it is written before the acknowledgment returns, returned on `agent.list` as `pendingSwitch` so `switching to …` survives a reload, re-armed at daemon startup, and cleared in the same transaction as whichever terminal event settles the switch, or overwritten by a superseding one, so a stale intent is unrepresentable.
- The switch introduces **no daemon-side state beyond those columns**: the canonical transcript it replays is a projection rebuilt from the session event log, never a stored artifact ([Spec-004 §Canonical Transcript Export And Replay](004-provider-driver-contract-and-capabilities.md#canonical-transcript-export-and-replay)), and the declared-loss list is carried on the `agent.provider_binding_changed` event rather than retained separately. A provider switch has the daemon write the old conversation's whole transcript as one plain file beside the hand-over brief, in the daemon's own storage for that session, outside the working folder and outside either provider's home, kept as long as the session is and removed with it (§Continuity, and what is declared rather than dropped).
- Spend is stored in integer micro-dollars on the daemon's per-turn usage rows — per turn, account and model, the tokens and the cost — written when the turn's last request is priced and never repriced. A request on a model the price table does not price yet is stored with its exact tokens and model, marked held, so it survives a restart, and it joins the figures when a fetch prices it (§Cost Derivation And Absent-Cost Semantics).
- **What sessions talking to each other add to the data model is daemon state and no record of a message** (§Sessions Talking To Each Other). The **session directory** — each session of this daemon's, its provider, its credential home and its current address, and each Codex session typed in a terminal that the shared service holds — is derived from the sessions the daemon hosts and from that service, and is rebuilt when it starts, so it holds nothing a restart cannot re-read and an address that moved with a restarted provider process is looked up again rather than remembered. The **exchange table** (the pair, and the count since the person last wrote in either session) and the **paused queue** (every message addressed to a paused session, in arrival order) are durable, session-scoped daemon state held with the session, because a daemon restart mid-exchange must deliver what it was holding and must not forget which two sessions were talking; a message whose state was `sent` and never seen is re-checked against the receiving session's own rows when the daemon comes back, and settles at `not delivered` where it is still absent. **A message itself persists nothing of its own**: the send and the arrival are the ordinary tool events of the two sessions' event logs, so no message table, no message row and no new event type exists for one, and the states a sent row walks through are read off those events and the run-state the daemon already holds.

## Addressing

**Activation is addressing-gated**: an agent acts when addressed, never on its own initiative. A plain message the person writes in the session is the main agent's turn, through the session's ordinary queue ([Spec-003 §Interfaces And Contracts](003-queue-steer-pause-resume.md#interfaces-and-contracts)); every other agent in the session takes a turn only in response to an explicit addressing act directed at it, so a plain message in a session where several agents are live starts exactly one turn, the main agent's, and never some subset of the others. The addressing acts are the person naming an agent in the composer (the `/` list writes the provider's own form for that agent into a message to the main agent, so the act rides the main agent's turn and needs no wire route of its own), a workflow definition's step, and an agent's own tool call through the cross-provider bridge (§Default Behavior); on the orchestration path the act is `OrchestrationRunCreate` naming its target (§Interfaces And Contracts). **What an agent writes is never an addressing act**: an agent starts another agent only through its own tool call, never by naming it in its output. That rule bounds activation inside a session and is not a bound on how much two sessions say to each other: a message from another session starts a turn where it lands, and nothing in this runtime bounds how many two sessions trade — each provider's own limits flow in with its own numbers and the one bound the person can set is `Max steps per turn` (§Sessions Talking To Each Other).

## Budget Policies

| Budget Type | Description | Default |
| --- | --- | --- |
| Spend limit | Dollars for the whole session, across every provider and account it uses | `Unlimited` |
| Tokens per run | Input and output tokens together for one run | `Unlimited` |

**Both limits are unlimited by default and exist only where the person sets one.** Settings › Runtime carries `Spend limit` and `Tokens per run` beside `Max steps per turn`, each reading `Unlimited`: what every new session starts from. The inspector's `Cost` section carries the session's own two rows at its foot, after `Max steps` and in its shape, `Spend limit · Unlimited` and `Tokens per run · Unlimited`; typing a number sets it for that session, and an empty field is `Unlimited`. With no limit set nothing warns, stops or refuses on it — the runtime adds no ceiling the providers do not have. **Both are held by the daemon's own spend count**, the committed-spend fold §Cost Figure Display Consistency defines, the same count the inspector's `Cost` section reads, on both providers. The daemon passes neither provider's own budget: Claude Code's `--max-budget-usd` is not passed, and Codex's own budget stop is per session tree — one child crossing it fails the child, the lead's wait and the lead's turn in the same instant, so a budget set there would draw as one cause behind several rows, while the daemon's own count is held per run from the daemon's own tree on either provider. **The daemon stops both providers itself, at the first usage report past a limit**, so one request can overshoot a limit slightly. The daemon emits `usage.budget_warning` events (the registered [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) name for this warning) at 80% of any limit the person set, once per (scope, budget-type) crossing, and issues an `interrupt` intervention via the generic dispatcher ([ADR-011](../decisions/011-generic-intervention-dispatch.md)) when a limit is passed, with `reason: budget_exhausted`.

**A reached limit lands as one system-message row**, written by the app itself like `Step limit reached`, and never as a banner, a modal or a composer refusal; nothing appears while a limit is unlimited or not reached:

- **`Spend limit reached · $20.00 · Raise limit`** (for a $20.00 limit): every running turn in the session stops, lead and helpers, as an interrupt does, and one row lands in the lead's transcript. A message sent while the limit stands still lands in the transcript, no turn starts, and the same row lands under it; the draft is never lost.
- **`Token limit reached · 500K · Raise limit`** (for a 500K limit): that run ends. The next message starts a new run with a fresh count. A helper's run is its own: a helper that reaches it stops alone, its child row reading `stopped · token limit reached`, and the lead goes on.
- **`Raise limit`** opens the inspector's field; saving a higher number carries the stopped turn or run on, as `Continue` does for the step limit.

Context-window headroom is deliberately **not a budget**: orchestration consumers read the `usage.context_window_update` headroom signal — `windowUsedTokens` / `windowMaxTokens`, provenance-graded by `windowSource`, with the driver-computed `exceeded` predicate ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — advisorily, on a **hard-vs-soft line keyed to provenance**: `estimated`- and `model_default`-grade headroom may drive only reversible, soft responses (surface a warning, advise the owner — compaction itself is the provider's own, at the point the person sets, per §Design Decisions), while any costly or irreversible action taken because of headroom (interrupting a run, refusing admission) requires `windowSource: 'provider_reported'` **with both window counts present** — or the provider-reported `exceeded: true` terminal flag, a reported fact rather than a derived ratio, which authorizes those protective actions directly so a counts-absent exhausted window is never answered more weakly than a counted one (a counts-absent, non-exceeded update carries no headroom fact to act on — the pair rule in [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — a hard action never fires off an estimated count, both because vendor token counts are documented as estimates even from the vendor's own counting endpoint and because current-generation tokenizers produce approximately 30 percent more tokens for the same text than earlier models ("The same input text produces approximately 30 percent more tokens than on earlier models … Recount prompts against the model you plan to use" — [Anthropic token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting), accessed 2026-07-12), so a window number derived from a stale pre-4.7 tokenizer assumption materially under-counts — `model_default`-grade values are tokenizer-fragile rather than merely stale; the surveyed field draws the same line — context thresholds are "automatic safeguards rather than hard stops" ([GitHub Copilot CLI context management](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/context-management), accessed 2026-07-12) — and the only hard context bound anywhere in the stack remains the provider's own real window ceiling.

### Cost Derivation And Absent-Cost Semantics

Every request a session makes is priced once, when it completes, and its figure is stored and never repriced; a later price change applies to later requests only. Two sources give the figure. **Claude Code prices its own requests**, so the daemon takes Claude Code's figure: the running `costUSD` it reports per model in `modelUsage` on each `result`, counted from the last one taken, for every model whose `costBasis` reads `list` (a list price Claude Code found in its own catalog or in the prices Anthropic sends it at start) or `managed` (an organization's own price, set in its managed settings). A model whose `costBasis` reads `unknown` is one Claude Code priced at its default model's rate because it found no price, and for that model the daemon prices each `assistant` message's `usage` itself from the price table — input, the five-minute and one-hour cache writes, cache reads and output, at the Fast rate when the message ran Fast and at the table's US-only multiplier when its `inference_geo` reads `us`. **Codex reports tokens and never a price**, so the daemon prices each Codex request from the price table, from the `last` figure of `thread/tokenUsage/updated`, which Codex sends once per request: a request costs (`inputTokens` − `cachedInputTokens` − `cacheWriteInputTokens`) × the input rate + `cachedInputTokens` × the cached-input rate + `cacheWriteInputTokens` × the cache-write rate + `outputTokens` × the output rate, because Codex's `inputTokens` already holds the cached and the cache-write tokens. Every rate is the table's own for that model — its long-context rates when the request's input passes the size the table names for them, its Fast rates when the thread's service tier is Fast — and the daemon holds none of those numbers itself; reasoning is already inside output and is never added. A frame whose `total` did not grow past the last `total` the daemon took on that thread repeats the request before it and is not priced again; a fork's first baseline is its parent's `total` at the fork, and a resumed thread's is the `total` the daemon stored for it. A turn's cost is the sum of its requests, compaction requests included. On a subscription plan the figure is the same tokens priced exactly at the provider's published per-token rates: on Claude Code, Claude Code's own list-price figure; on Codex, each request at the model's standard rates with its cache writes at the input rate and never the long-context rates, and at the Fast rates on Fast.

**The price table is a live copy of a maintained public price list, never a table kept by hand.** The daemon reads LiteLLM's model price list (MIT), which carries per model the input, cached-input, cache-write, one-hour cache-write, output, long-context and Fast rates of both providers' models. It fetches the list when it starts, once an hour while it runs, and at once whenever a provider lists a model or a speed the copy it holds lacks, each time asking only for a newer copy than the one it holds; it keeps the newest copy that passes its schema, and each release carries a copy for a first start that cannot fetch. A model is found by its exact id and never priced as a neighbor of its family. Every model and speed a provider lists is offered the moment the provider lists it, priced or not. A request on a model or speed the list does not price yet — a new model, a server-side reroute, an overridden reviewer, or Codex's `codex-auto-review` reviewer on a ChatGPT sign-in — is stored with its exact tokens as held, and the next fetch that carries its model prices it, when it joins every figure; until then its spend is in no figure, and nothing marks the figure for it.

**The requests a provider leaves out of the session's stream still count.** Codex's automatic reviewer, a Codex `/review`'s sub-agent and Claude Code's auto-mode check never reach the stream, so the daemon reads them from each provider's own telemetry export on this machine, prices each at its own model from the price table and records it as spend on its session under the account that ran it, as the same `usage.cost_update` spend event stream-priced requests write ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)), so the inspector's `Cost` section counts it; it is never a transcript row; a request on a streamed thread is priced from the stream alone, so nothing is counted twice. A Codex aside costs its fork's own last figure, because a fork's running total starts at its parent's; a Claude Code aside costs its process's total less the parent's cost, which that total includes once the parent has exited. A session that changes account keeps one set of figures, split at the switch: requests before it count to the account they ran on and requests after it to the new one. Spend is held in integer micro-dollars on the wire and in storage. A spend limit the person set is enforced against the sum of the priced requests (§Budget Policies); nothing is reserved in advance, and no model is refused or interrupted for lacking a price.

### Cost Figure Display Consistency

Every cost figure this spec's surfaces expose derives from the **same committed-spend fold the accountant enforces against** — the sum of the session's priced requests, specified in §Cost Derivation And Absent-Cost Semantics above. Four rules bind.

**(a) One fold, never a second accountant.** A surfaced session-level or run-level cost figure is **supplied by** the accountant that enforces, never recomputed beside it. Summing the runs visible in a run list is expressly not a permitted derivation, and no surface may maintain an independently-folded total for presentation. The three committed-spend figures V1 actually surfaces are therefore the same number at the same fold state: the `OrchestrationBudgetState` committed-spend member — one figure, not two, because the budget read and the budget update answer with that same state type and are served from the same accessor — and the `observedValue` the daemon stamps on a **session-cost** `usage.budget_warning` — the `budgetType: 'session_cost'` member of that event's union ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — both defined as committed spend, and that cross-surface equality is **asserted**, not assumed ([Plan-014 §Invariants](../plans/014-multi-agent-orchestration.md#invariants)). The third is the `observedValue` a session-cost `orchestration.budget_exhausted` refusal stamps in its `data.fields` ([error-contracts.md §Orchestration](../architecture/contracts/error-contracts.md#orchestration)): the admission predicate that refuses reads the committed spend from the same accessor, and the refusal stamps exactly the value the predicate read, so the refused caller is shown the enforced number too — three surfaces, one accessor, one value. The warning-side equality is scoped to that event's session-cost member alone: a `run_tokens` warning stamps a token count, which is not a cost figure and which this subsection does not govern. The read response's per-agent figures are parts of that number rather than independent totals, so there is exactly one total on the surface and no second one to drift. The failure this forecloses: an overview that lists each root run with only that run's own ledger cost, while the spend of delegated work lands on the children those runs called, displays a large multi-run campaign at a small fraction of its true cost — a display fold silently drifted from the number the ledger holds. V1's structure already bounds the drift class (every agent's spend is routed up the parent chain at whatever depth it sits, in-session subagent usage rolls into the parent run's own budget per §Provider-Native Subagents, and the session ceiling folds everything), which is why the residue is this display-side rule rather than a re-derivation of the fold itself.

On a session's own surface money appears in exactly two places: the inspector's `Cost` section, which reads the receipt by provider and account, and the spend carried against each agent in the session's agent list. Nowhere else — not beside the context-window reading, which stays a context reading and its compaction popover; not in a footer under the session list or the destination rail; and no billing period, no per-model split, and no account-wide total anywhere on a session's surface. Account-level figures — an account's usage windows, its lifetime spend with its billing-mode label, and any total across accounts — belong to the provider-account surfaces [Spec-026](026-provider-accounts-and-credential-homes.md) owns. The division is not cosmetic: a quota describes an account's standing with its provider rather than a session's spending.

**(b) A per-agent figure is the agent's own spend and its subtree's.** The spend carried against each agent in the session's agent list is the budget read's per-agent axis, `agentSpend`: `ownUsdMicros`, what the agent's own requests cost, and `subtreeUsdMicros`, that plus the spend of every agent under it, routed up the parent chain at any depth, both supplied by the daemon from the same usage rows the fold reads, never assembled by a client. Both are carried because one unnamed figure is exactly the ambiguity of an overview that shows each root at its own cost while delegated spend lands on its children. Where an agent in that list is an in-session subagent, its figure is the subagent-attributed part of its run's spend, which those usage rows already carry (§Provider-Native Subagents), so it is a part of an existing figure and never a total of its own. The inspector's `Cost` section carries no per-run, per-turn or per-agent line at all; it is the receipt by provider and account (§Session Cost Receipt). This clause is **verified positively**: every per-agent entry the daemon serves carries both figures, and no surface presents a per-agent figure the daemon did not supply ([Plan-014 §Invariants](../plans/014-multi-agent-orchestration.md#invariants)). Every cost-displaying surface reads the same accessor, as CP-014-16 at [Plan-014 §Cross-Plan Obligations](../plans/014-multi-agent-orchestration.md#cross-plan-obligations).

**(d) A token figure declares its scope too.** The one-fold rule of clause (a) is **cost-scoped**: the token axis deliberately carries two folds — the per-run enforced token budget (`tokenLimit`, the ceiling admission and interrupt act on) and the conversation-scoped token count the composer's context ring displays — and that divergence is intentional and reconciled at the auto-compaction safeguard in §Budget Policies. Nothing here collapses them. What does bind, as the token-axis analogue of clause (b), is the declaration: **any surfaced token figure states which of the two it is** — per-run enforced budget, or conversation-scoped observed count. The concrete case this closes is a rendered `run_tokens` budget warning, whose `observedValue` is a per-run token figure that no other rule governs and that reads, beside the context ring's conversation-scoped count, as though the two were the same quantity. Declaring the scope is the whole obligation.

**(c) A figure carries no mark, and money reads one way.** Every figure is the cost: no `est.`, no `tokens only`, no `unpriced` and no unknown on any surface, because there is one figure and it is the enforced one; a session that has spent nothing reads `$0.00`. Every dollar figure on every surface reads one way on both providers: `$`, then the amount in US dollars with a period for the decimals and commas between thousands, two decimals above $0.50 and four at $0.50 or below, rounded half up once from the stored micro-dollars, in tabular figures, with no `≈`, `~`, `≥` or `<`; a total is summed from the stored amounts and rounded once, never summed from rounded rows. **A session's voice calls add up on one cost row**, `Voice`, then the calls' minutes, then dollars, under its provider's header after that provider's account rows, counting toward `Subtotal` and `Total`: the calls' length from each call's start to its close, at the voice model's per-minute price, held with its seconds while the price list does not carry the model and joining the totals when a fetch prices it. On a ChatGPT sign-in the minutes are part of the plan: the row is their list-price value and nothing is billed, as with every figure on a plan account, and what a call draws from the plan's usage windows shows the way a turn's does. The turns a call hands to the agent cost what any turn costs.

**The total is the enforced number and states no bound.** It is exact for every priced request and carries no label saying otherwise. The one spend it cannot show is a request held for a price (§Cost Derivation And Absent-Cost Semantics), which joins the total when a fetch prices it; nothing reserved in advance ever enters it.

This subsection mints no event type, no wire method, no error code, and no table, and adds no budget.

### Session Cost Receipt

Every session carries a **cost receipt**, which the inspector's `Cost` section draws: a faint header per provider the session spent on, in the order the session first spent on it with the session's own provider first; under it one row per account that provider spent on, named as the session's Account fact names it, then its tokens, then its dollars; the `Voice` row of §Cost Figure Display Consistency under its provider; a `Subtotal` where a provider holds two or more rows; then `Total`, and after it the rows that are not figures, the session's own `Max steps per turn`, `Spend limit` and `Tokens per run`. The total is the committed-spend figure clause (a) already governs — the same number, from the same accessor, with no second fold behind it. The receipt is what makes that number answerable rather than merely correct: a person who sees a session cost and cannot find out what caused it has a figure, not an account.

**The receipt is a decomposition, never a re-fold.** The accountant that enforces is the accountant that answers, the receipt's rows are components of the number it already reported, and identities pin every part to the whole. A presentation-side re-aggregation — summing rows the client can see, or maintaining a parallel tally of its own — is expressly forbidden by clause (a) and is not made permissible by being a detail view. Concretely, the receipt decomposes committed spend by provider and then by account:

- **Per provider.** One group per provider the session spent on, in first-spent order, each with a subtotal the daemon computes; the client sums nothing.
- **Per account.** One row per account that provider spent on (`{provider, account, billingMode, tokens, usdMicros}`, the amount in integer micro-dollars), the account named exactly as the Account fact names it — the address, the plan in the provider's own word, and the organization where the plan carries one — and carrying that account's billing mode (`subscription`, `metered` or `unknown`), which labels the figure and never changes how it is derived. A turn split across two accounts by an account switch lands as two rows, the requests before the switch under the account they ran on and those after it under the new one. A request the stream left out lands under the account that ran it, and the hand-over brief's cost under the account that wrote it.

Two identities hold at every fold state, and they are the receipt's whole correctness argument: each provider's account rows, its voice row included, sum to its subtotal, and the subtotals sum to the session's committed spend. The axis is a **partition** — every unit of committed spend appears in exactly one row — which is why the rows total to the same number and why none can quietly omit or duplicate a contribution. A receipt row carries no mark of its own, for the reason clause (c) gives.

**Derivation is fold-of-persisted-rows, exactly as enforcement is.** The receipt folds the priced usage rows, each stored in integer micro-dollars when its request completed, and it **never re-prices anything at read time**. A price-table update re-prices no history for the receipt any more than it does for enforcement, so a receipt rendered twice at the same fold state renders identically, and a receipt is replay-stable for precisely the reason the accountant is.

This subsection mints no event type, no table, and no budget. It mints one read surface, `orchestration.costReceiptRead {sessionId}` (registered in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md)), answering the providers in first-spent order, each with its account rows, its voice row and its subtotal, then the total, every amount in integer micro-dollars and every figure served from the same committed-spend accessor as the budget read. It refuses a session id the daemon does not hold with `session.not_found` and appends nothing. The account each row names is supplied by [Spec-026](026-provider-accounts-and-credential-homes.md).

## Stop Conditions

| Condition | Trigger | Behavior |
| --- | --- | --- |
| Spend limit reached | The session's spend passes its spend limit | Every running turn in the session interrupted with `budget_exhausted` reason; `Spend limit reached` row |
| Token limit reached | A run's tokens pass its token limit | Run interrupted with `budget_exhausted` reason; `Token limit reached` row |
| Explicit stop | User sends stop command | Run interrupted via cancel intervention |

**A wait for a person never expires**: an approval, a plan card and a question stand until they are answered, and the only things that end one are the answer itself, an interrupt of the run, a move to a permission level that never asks — which answers an open card and lets the blocked row run — and the provider process ending ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior), [run-state-machine.md §Invariants](../domain/run-state-machine.md#invariants)). The startup-reconciliation divergence halt — `waiting_for_input` carrying `recovery-needed`, backed by no pending ask or approval — is a designed human-action halt: it exits only by human recovery action and surfaces in the recovery status ([Spec-013 §Fallback Behavior](013-persistence-recovery-and-replay.md#fallback-behavior)). The system-interrupt reason `budget_exhausted` is carried on the interrupt intervention.

## Intervention Propagation

Interventions use the generic dispatcher defined by [Spec-003](../specs/003-queue-steer-pause-resume.md) and [ADR-011](../decisions/011-generic-intervention-dispatch.md). Spec-014 introduces no new intervention verbs.

- A pause, interrupt, or steer applied to a parent run does not auto-cascade to its child runs. Each child run is an independent intervention target. The same holds at every level of the in-session agent tree (§Provider-Native Subagents): interrupting one agent reaches that agent and nothing else — the agents it dispatched keep working, and whatever dispatched it keeps working. Continuing a paused agent likewise continues that agent alone.
- Propagating an intervention across a parent/child subtree requires the caller to submit one intervention per run. This preserves Spec-003's audit property that every run-state transition corresponds to a distinct `InterventionResult` record.
- A steer applied to a parent run does not inject content into child-run conversations — child runs receive steer content only when the steer is targeted at the child run's id.
- Child runs accept the same run-control surface as standalone runs — steer and interrupt via `applyIntervention`, pause/resume via the orchestration-layer `run.pause` / `run.resume` verbs (Spec-003; the driver never needs to know about pause). Driver capability semantics (Spec-003's steer degradation, for example) apply uniformly. **Every live agent in the in-session tree takes that same surface, at any depth, whatever dispatched it and whichever provider runs it**; the daemon owns the mechanism behind each control per provider (Spec-003) and no difference in mechanism reaches the caller or the screen.
- **A per-agent pause is never a process freeze.** Both providers run their subagents inside the run's own provider process, so freezing one agent at the process level would freeze the run and its siblings with it; a process freeze stays available only as a whole-session pause. An agent's pause is therefore a hold the daemon places on that agent's own next step, and it is lossless: the agent waits without spending, and the hold ends only by an answer — continued, or steered with the user's own words.
- **An interrupt leaves nothing running behind it.** Interrupting an agent ends the command that agent had in flight as well as its own turn — for a helper on either leg the hold on its next step together with the end of its running command, ended on the Codex leg by that provider's own terminal verbs, and for a Codex lead its turn interrupt together with those same verbs — so no command outlives the agent that started it. The agent then waits for a steer rather than disappearing, and a steer starts it again with everything it knew.
- **An intervention must not reach what it was not aimed at.** An interrupt of a run never collaterally ends an agent that run dispatched: on the Claude leg the daemon moves a foreground agent to the background over the provider's own background request before it interrupts the run, so the interrupt spares that agent exactly as it spares every background one; on the Codex leg every agent already runs on its own thread and what blocks the run is its own wait, so nothing is needed. The daemon additionally declares the provider's per-task stop affordance so that an ordinary interrupt cannot sweep up background subagents.
- **The interventions that do reach a whole subtree are fan-outs, never a cascade primitive.** Exactly three reach more than one agent: a session-wide interrupt, a stop of everything running in the session's agent tree, and an undo's stop of the agents started after its point. The stop of everything running is `run.childrenStop {runId}` ([Spec-003](../specs/003-queue-steer-pause-resume.md) owns the verb): one call, which the daemon answers by walking its own index at every depth and stopping each agent in turn, reporting a failure per agent; `Interrupt everything` is the session's own interrupt together with that stop. Each is **one ordinary intervention per run id**, taken from the daemon's own parent-to-child index at every depth (§Interfaces And Contracts) — so Spec-003's audit property is preserved exactly as the bullet above requires, and the count a confirmation states is that index's count rather than a client's. None of the three is relayed through the run that dispatched the tree, because no provider's lead can stop its own subtree: the Claude leg's stop tool refuses a grandchild as another agent's, and the Codex leg publishes no stop-all verb at all.
- **One intervention crosses a session boundary, and only one.** Interrupting a session that is trading messages with another session ends the turn on both, because the other side's next message would otherwise wake this one straight back up (§Sessions Talking To Each Other). It reaches exactly the session on the other end of that exchange, named by the pair the daemon's exchange table already holds, and never a third; it is the same fan-out shape as the three sweeps above — one ordinary interrupt per run, each landing its own `InterventionResult` — and no new intervention verb is minted for it.
- **What a session-wide stop leaves behind differs by provider, and the difference is the provider's own.** On the Claude leg the agents such a stop reaches are stopped for good — that provider refuses every later message to an agent the person stopped — so one of them takes no steer and is never started again. That is the one exception to an interrupted agent waiting for a steer, and it is scoped to a stop that reaches the session's whole agent tree: on the Codex leg the same press interrupts them instead, so each waits for a steer exactly as any singly-interrupted agent does. The record of the stop says which of the two happened rather than carrying one word for both.
- There is no subtree-wide **atomic** propagation — one call that cancels a parent and all its descendants as a single transition, with one result. The three sweeps above each dispatch an ordinary intervention per run and each run lands its own `InterventionResult`, so a partially-refused sweep is legible rather than atomic-and-silent.

## Session Goals

- A goal is a command sent to one agent in a session, never what the session is. `/goal <condition>` gives the agent it is sent to a condition to work toward; the provider checks it each time the agent would stop, and the agent keeps working until the condition is met, the goal is cleared, or it stops unmet. A later `/goal` replaces the active goal and `/goal clear` removes it. A session may have no goal, one, or several over its life, and nothing names, labels or groups a session by its goal.
- `session.goalUpdate {sessionId, agentId, goal}` sets or replaces the goal of the agent it names and answers with the goal it set; the goal is not blank and carries no NUL, with no length cap of the app's own: a goal past the provider's own limit is refused in the provider's words. `session.goalClear {sessionId, agentId}` clears it, answers `{sessionId}`, and succeeds when no goal is set, as Codex does. Both are the session owner's alone — an agent may not call them — and each refuses a session id the daemon does not hold with `session.not_found`, appending nothing, and, where the agent's provider cannot carry a goal, `driver.capability_unsupported`; a later write wins. Wire shapes live in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md). `session.goal_updated` carries the goal and its status, one union — `active`, `paused`, `blocked`, `usage-limited`, `budget-limited`, `complete`, `impossible` — of which `complete` and `impossible` are final; only Claude Code sends `impossible`, and it carries the provider's reason. `session.goal_cleared` ends a goal, and clearing is never a status ([Spec-005 §Session Lifecycle](005-session-event-taxonomy-and-audit-log.md#session-lifecycle-session_lifecycle)). Goal state is a projection of those events, with no separate goal store, and a goal change is not a run-state transition.
- The transcript is the only place a goal shows. Each change is one system message derived from those events: `Goal set` (an update when no goal is active), `Goal updated`, `Goal completed` (the status becomes `complete`), `Goal cleared`. A goal that stops unmet shows its status and the provider's reason on its row: Codex's `blocked` or a limit status, Claude Code's `Goal impossible`. Two more rows are Claude Code's, stored as `session.notice` kinds while the goal stays active: `goal_not_met` (`Goal not met · still active`, the turn ended at Claude Code's own cap on unmet checks in a row) and `goal_check_unfinished` (`Goal check did not finish · still active`, a check ran past Claude Code's fixed 30-second limit). There is no goal card, no header item, no sidebar section and no session label.
- Each provider carries the goal itself, and the daemon reads every ending from what the provider writes. **Codex** has `thread/goal/set`, `thread/goal/get` and `thread/goal/clear`, and sends `thread/goal/updated` — the whole goal with a status of `active`, `paused`, `blocked`, `usageLimited`, `budgetLimited` or `complete` — and `thread/goal/cleared`, which the daemon maps to the session events. **Claude Code** has its own `/goal <condition>` and `/goal clear`, sent as user messages, and its driver declares the capability (`session_goals: true`). Set and clear reach the stream as `Goal set: <condition>` and `Goal cleared: <condition>`. An unmet check arrives as a `Stop hook feedback: [<condition>]: <reason>` user frame, and the turn goes on. Met and impossible reach only Claude Code's own session file, as `goal_status` records the daemon follows: met is `met: true` without `sentinel`, and the goal clears; a clear writes `met: true` with `sentinel: true`, which is how a clear is told from a completion; impossible is `met: false, failed: true` with the reason, the goal clears, and nothing reaches the stream. Capped: after Claude Code's own cap on unmet checks in a row, a `system` notification with the key `stop-hook-block-cap`, then a `result` with empty text, and the goal stays active. A check that could not finish writes no record and no frame and delays the turn's `result` by the 30-second limit; the daemon reads it from a `result` with the goal active, no interrupt, no cap notice and a subtype other than `error_max_turns`, and the goal stays active. The daemon never reads a goal outcome from hook frames, because Claude Code sends none for the goal check, and a turn the session's step bound ended (`error_max_turns`) is that bound's own row, never a goal outcome. No goal text is ever put into a system prompt: nothing gives every agent a standing sentence.

## Same-Agent Provider Switch

Under [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md), an agent's provider is an **axis of its configuration**, not a fact fixed when its session started. What a switch changes is the agent's **provider binding**, `AgentProviderBinding`: its driver, its model, its provider account (none means it follows that provider's current account), its reasoning effort and, where the provider has one, its output speed. A user may move a conversation from one provider to another — or to a different model, a different reasoning effort or a different speed — without losing the conversation or starting a second agent. The request keeps the word switch: a pending switch, a switch id.

**Which account pays is a field of the binding, moved from the provider surface.** An account belongs to its provider, and the control that changes which account a provider's work runs on is the provider surface's own ([Spec-026 §Moving a session to another account](026-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)): pressing an account there makes it that provider's current account and moves every running session on that provider that is not pinned to one. A per-session account switch beside it would let a session sit on an account the provider surface says it is not on, so the mutation below carries no account member. An account move settles through the same events a provider switch does and fails the same way: a move that fails after it was accepted keeps the account the session had (§Refusals are fail-closed and precede any spend).

**Where the provider switch is picked.** The session composer's **model control** lists both providers' models under two headings, `Claude Code` and `Codex`, and picking a model under the other provider's heading is how a provider switch is asked for. There is no separate provider picker: the model and the provider that runs it are one choice, and two controls setting one binding would let them disagree. Picking again replaces the pending pick; picking the current provider's model back cancels it. While a pick is pending the working line's state slot reads `switching to Codex` or `switching to Claude` and the control itself keeps reading the model.

### The mutation surface

`agent.configUpdate {agentId, modelId?, effort?, outputSpeed?, driverName?, interruptAndSwitch?}` carries the binding's axes, every one **additive-optional**, and never the account: **`providerAccountId` is a run-start input and a field the provider surface moves**, per the paragraph above, so the agent row records the account a run resolved and this update never moves it. The axes a run is started with carry `providerAccountId?` and `effort?` and deliberately **not** `outputSpeed?`: an agent is not born with a speed mode. An omitted member is unchanged, not reset — the same additive-optional discipline [ADR-018](../decisions/018-cross-version-compatibility.md) binds everywhere else. There is correspondingly **no clear**: no operation returns a provider axis to a driver default. `driverName` and `modelId` could not be cleared in any case — an agent always has both — and clearing `effort` would need a third request state this surface deliberately does not carry, since "omitted means unchanged" is uniform here and a member that sometimes meant "reset" would make every omission ambiguous. The answer is `pending`, `applied`, `degraded` or `failed`, with the switch's id; a refusal before acceptance is `agent.provider_axis_invalid`, or `driver.capability_unsupported` for an axis the target driver does not have; and every application step is a compare-and-set on that id.

`effort` is a first-class axis because it is validated, surfaced, and switched like `modelId` is: it is per-model, and the valid set is the target model's `effortLevels` as reported by the driver ([Spec-004 §Provider Parameter Vocabularies](004-provider-driver-contract-and-capabilities.md#provider-parameter-vocabularies)), not a corpus-wide enum. A value outside that set is refused rather than clamped, because a silently-lowered effort is a silently different agent.

`outputSpeed` is validated the same way, against a vocabulary the driver **publishes before the axis is offered** rather than one this spec names: `GetCapabilitiesResult.outputSpeedLevels`, present exactly where the `output_speed` flag is `true` and reaching clients on the same capability read the flag itself travels on ([Spec-004 §Provider Parameter Vocabularies](004-provider-driver-contract-and-capabilities.md#provider-parameter-vocabularies)). Publishing it is not optional politeness — a mutation validated against an unpublished set is a control whose accepted values no caller can discover, so the composer would have to guess and the daemon would have to refuse the guesses. A driver whose `output_speed` flag is `false` has no such axis, and the mutation refuses `driver.capability_unsupported` before anything is spent, never emulating speed onto `effort`. Where the flag is `true` and the vocabulary is absent or empty the axis is **unsettable** and the mutation refuses `agent.provider_axis_invalid` fail-closed, which is the same answer an unrecognized value gets: an unsettable axis and an invalid value are both "this value will not be applied", and splitting them would tell a caller which providers are mid-rollout. An accepted value lands, at application, in the agent row's own provider-axis column beside the account and the effort ([§State And Data Implications](#state-and-data-implications)) — `NULL` until a switch sets one, which is what "an agent is not born with a speed mode" looks like as a starting state rather than as a member fixed when the run started. That column is the **requested** mode and is what the agent read model returns for the axis; what the provider then **declared** is a separate, live-scoped observation served beside it from the live binding and stored nowhere ([Spec-004 §The output-speed axis](004-provider-driver-contract-and-capabilities.md#the-output-speed-axis)). Keeping them as separate members rather than folding the observation into the column is what lets a caller see a mode that was accepted here and refused by the provider's own account gate — a single value would have to choose which of the two facts to lose. It is a column for the reason the paragraph above gives for `effort`, and for one more: the application transaction commits the effective binding into those columns in the same act as clearing the pending column, so an axis with a durable pending home and no durable effective one would apply once and silently revert at the next restart.

### Application timing, and why the boundary depends on the axis

A switch applies **at the next boundary the target axis permits**, and the two boundaries are not interchangeable.

An axis the target driver accepts **between turns** applies at the next **turn boundary**: the running provider process carries the change into its next turn, nothing is respawned, and no transcript is replayed. Codex takes the model, the effort and the service tier that carries its speed on each `turn/start` ([Spec-004 §Provider Parameter Vocabularies](004-provider-driver-contract-and-capabilities.md#provider-parameter-vocabularies)); Claude Code takes the model through its own `/model` command, the effort through `/effort` from the next turn, and the speed through `apply_flag_settings {fastMode}` between turns, from the next run, with no restart and no file written.

**`modelId` is a turn-boundary axis on the Claude leg too: that provider does not bind the model at spawn.** A long-lived Claude Code session changes model **in process**. Measured on Claude Code 2.1.275 (2026-09-17) over a persistent streaming session: the provider's own `/model <name>` command answers `Set model to <name> for this session only`, costs no model turn and no money, and emits a fresh session-initialization frame whose model is the new one; the next ordinary turn in that same session runs on the new model, and the session's own context report reads it back. The daemon therefore **MUST NOT respawn a provider process for a model change** — a respawn would throw away a live conversation, and force a transcript replay and its declared losses, to buy a change the running process already accepts. A model-only switch on this leg settles `in_place` with an empty declared-loss list, exactly as a model-only switch on the other leg does.

An axis that is **spawn-bound** applies at the next **run boundary**, because realizing it requires a new provider process. Only `driverName` is spawn-bound: a different vendor is a different binary. Model, effort and speed are in this group on neither driver, per the paragraphs above, so a change of any of them alone settles `in_place` with an empty declared-loss list and draws no row. Which group an axis falls in is still **read from the target driver's declared vocabulary, never assumed**: a daemon that guessed would either respawn needlessly or promise an immediacy the provider will not honor, and the model axis is the worked example of the cost of guessing — a daemon that assumed a model change needed a new process would respawn it, replay a transcript and declare losses for a change no provider required any of that for. A pick under the other provider's heading therefore sets a switch for the end of the run and changes nothing under it.

A turn already in flight completes on the binding that started it in either case — interrupting it would abandon work the user is watching and would truncate the very transcript a spawn-bound switch then has to replay.

Mutation and application are therefore **two moments**. The mutation's own response acknowledges a **pending** switch and names the boundary it will apply at; `agent.provider_binding_changed` is emitted at **application**, and it is what carries the settlement and the declared losses — the only shape available here, since a provider switch cannot know what did not carry until the hand-over brief is written.

**A pending switch is durable, and it is singular.** An acknowledgment that survives only in daemon memory is a promise a restart silently breaks: the caller has been told the switch will happen, the boundary arrives, and nothing does. So the pending switch is written to the agent record's own pending column **before** the acknowledgment returns ([§State And Data Implications](#state-and-data-implications)) — a daemon-minted `switchId`, the boundary it resolved, and the binding it moves to — and `agent.list` returns it as `pendingSwitch`, so the working line's `switching to …` survives a reload and reaches another device. No event records a switch being asked for, so a pending switch can never be read as the binding having moved; daemon startup **re-arms** it from that column, and a restart resumes waiting for the boundary rather than dropping the switch. What it does not do is re-validate optimistically — the application-time re-validation below runs on the re-armed path exactly as on the live one.

Exactly **one** switch is pending per agent, and that singularity is the ordering rule rather than a queue: a second provider-axis update while one is pending **supersedes** it, last writer wins, and the superseded intent never reaches a terminal event. Queuing would be worse in the way that matters — a user who changes their mind twice would watch their first choice apply, run a turn, and then be replaced by their second. The superseding acknowledgment names the id it displaced, so the caller is told a supersession happened rather than left to infer it from an event that never arrives. A pick that returns to the binding the agent is already on — the current provider's model picked back — cancels the pending switch: the column clears, nothing lands, and no terminal is emitted, as with any supersession. Because the intent lives in a single column on the agent row, the exclusion is structural: two concurrent mutations serialize on the same row under the daemon's session-mutation path, and the loser is a supersession, never a lost write. Supersession binds the **application** as well, not only the mutation. A superseded switch may still be in flight — its boundary hook armed, its interrupt dispatched, its target session perhaps already spawned — so every application step is guarded by a compare-and-set on `switchId`: the applying coordinator re-reads the pending column **inside the same transaction that commits the binding**, proceeds only if the column still holds its own id, and otherwise abandons the application entirely, emitting **no** terminal and clearing **no** pending switch. That is exactly what the rule above already promises — a superseded intent never reaches a terminal event — and it is what stops a stale application from erasing the switch that displaced it. Without the guard the last writer would win the mutation and then lose the application: switch B lands in the column, switch A's boundary arrives, and A writes its own binding and clears B's promise.

The immediate arm is `interruptAndSwitch: true`, and the run-boundary group is why it exists: without it a spawn-bound switch waits for the run to end on its own, which across a long run is indistinguishable from being ignored. It **dispatches the existing `interrupt` intervention** and then applies at the boundary that interrupt creates — collapsing the two moments into one, the only case in which the mutation response can carry the settlement itself rather than a pending acknowledgment — and the only arm that holds its request open across the boundary in order to do so. Collapsing them does not skip the durability step: the pending intent is written before the interrupt is dispatched here exactly as on the deferred arm, and cleared when the settlement commits. **What the durable record must additionally carry is that an interrupt is owed at all**, and how far it got — the boundary alone cannot say, since a deferred switch and an interrupted one can both resolve to `turn_boundary`. So the column records `interruptRequested` beside the boundary and, on this arm, an interrupt-dispatch progress marker advanced from `requested` to `dispatched` by its **own** durable write once the intervention is accepted. Recovery reads exactly that: a re-armed switch marked `requested` **redispatches** the interrupt, and one marked `dispatched` reconciles against the run rather than interrupting it a second time. Without the marker a restart would re-arm an immediate switch as though it were a deferred one and wait for a boundary nothing is going to produce — the crash would not cost the caller their answer, it would cost them the switch. A crash in between therefore costs the caller their answer and nothing else — the intent is re-armed at startup, the owed interrupt is redispatched, and the switch still applies — because an arm that waits for its own settlement is precisely the arm where losing the answer must not also lose the switch; the price of a crash between the two durable writes is one idempotent redispatch. That window is short but real, and keeping it real is what keeps the record honest: a client watching the session sees the same pending switch and then the same terminal on both arms, so nothing downstream has to know which arm produced it. It is an entry point into a control the corpus already has, not a new run control, so [Spec-003](003-queue-steer-pause-resume.md)'s V1 control set is unchanged. Two consequences follow from that reuse and are deliberate: the interrupt is authorized as `Action::"intervene"` on the target run, and it settles through the ordinary intervention path, so a refused interrupt refuses the switch rather than leaving the agent half-moved.

Because that arm holds its request open until the switch settles, its response must express **every** settlement the boundary can reach, not only the good one. The mutation's response is therefore a discriminated union ([api-payload-contracts.md §Plan-014](../architecture/contracts/api-payload-contracts.md)): `pending` on the deferred arm, and `applied`, `degraded`, or `failed` on the immediate one. `degraded` is not a judgment a client makes — it is a **total mapping** from the settlement's own continuity: `applied` exactly when the conversation arrived whole (`in_place`) and `degraded` exactly when it did not (`brief`), so the honest-degrade rule §Continuity states and [Spec-005](005-session-event-taxonomy-and-audit-log.md#agent-lifecycle-session_lifecycle) restates for the terminal event is carried by the wire's own discriminator rather than re-derived by every renderer. `failed` carries the same `reason` vocabulary as `agent.provider_binding_change_failed` — one vocabulary across both surfaces — and is a **result rather than an error**, because the switch was accepted, the `switchId` was minted, and the pending switch was already written: the mutation succeeded and only the application did not. A refusal reached **before** acceptance is the synchronous `agent.provider_axis_invalid` or `driver.capability_unsupported` error instead, and mints no id and writes nothing. A failing immediate arm still emits the terminal: the pending column is cleared by a terminal and never by a reply, so an arm that answered its caller and appended nothing would leave a promise nothing could clear.

### Continuity, and what is declared rather than dropped

Continuity depends on whether the provider changes, and the two cases use different mechanisms because the providers make different things possible.

**Same provider: the running process.** No change inside one provider starts a new process. A model, effort or speed change and an account move are each carried on the running process and settle `in_place`: the account moves at the session's next request on every supported version, a running tool finishing and never repeated, nothing interrupted, and the conversation and its reasoning staying where they are ([Spec-026 §Moving a session to another account](026-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)).

**A different provider: a hand-over brief.** No vendor's resume verb accepts another vendor's conversation ([ADR-029](../decisions/029-canonical-transcript-is-authoritative.md)). The new provider is therefore started from a **hand-over brief** (the daemon's `HandOverBrief`), and replaying the whole conversation as text is deliberately **not** what a provider switch does: it is the most expensive thing to send and not the thing that helps most. The brief is built on a **throwaway copy of the old session, never the live one**, so nothing about producing it disturbs the conversation the person is watching, and it is the driver's own operation, `exportHandoverBrief` ([Spec-004 §The hand-over brief is the floor, and it is visibly a floor](004-provider-driver-contract-and-capabilities.md#the-hand-over-brief-is-the-floor-and-it-is-visibly-a-floor)). The person's decisions, reversed ones included, travel in the old provider's own summary, asked for in one shape on both providers: Codex answers a fixed template, and on Claude Code `/compact` on the throwaway copy carries that template's instruction. The summary states each decision that still holds once, with what it applies to and its current value (`strict-mode option name: strictKeys`), and lists withdrawn values under their own heading, `Withdrawn, do not use`.

The first message the new provider receives is that brief, and then, in this order:

- the **current diffs and the branch**, read from disk at that moment rather than taken from anything remembered;
- **every earlier step as a one-line note** — what the step was and how it ended, such as a command and that it failed with two failing tests — with the output bodies left out;
- the **last two exchanges word for word**, for continuity of the work in hand ([Spec-004 §The hand-over brief is the floor, and it is visibly a floor](004-provider-driver-contract-and-capabilities.md#the-hand-over-brief-is-the-floor-and-it-is-visibly-a-floor));
- and a **reference to the whole old transcript**, which the daemon writes as one plain file beside the brief. Nothing of it is pushed into the message: the new provider opens and reads whatever part of it it wants, on demand, with its own file tools. This is what makes leaving the conversation out of the message affordable — the expensive thing is not sent, and it is still reachable. That file lives in the daemon's own storage for that session, outside the working folder and outside either provider's own home, is named in the brief by its absolute path, and is kept as long as the session is and removed with it. Nothing about the file is a line on screen: the transcript's two rows are the brief and the switch, and the file is not a third.

**What never travels, on any switch:** the model's private reasoning, which both vendors make unusable outside their own product; tool calls as live calls, which arrive as history and never as work in flight; and the old provider's own skill and command names, which name nothing on the new provider. The daemon also strips from the old provider's summary, before the brief travels, what that summary step reproduces or adds: the old provider's own system prompt, its environment preamble and the instruction files it loaded, and from Claude Code's summary its opening line saying the session is being continued, its pointer to its own session file (the throwaway copy's, deleted with it), its instruction to continue without asking the person anything, and its own compaction instruction where the summary's quote of the person's last message ends with it (`CRITICAL: Respond with TEXT ONLY. Do NOT call any tools.`), because the brief names its own transcript file and frames the continuation itself. Because the summary can quote a tool's output, the list of what did not carry names what the message actually left out, read from the brief, never what a rule says is out of reach. Nothing is written into the other vendor's own directories at any point.

**Switching back reopens the old provider's own conversation.** A session that moves from one provider to another and back does not start a third conversation: the daemon reopens the first provider's own session by the identifier it kept, and hands it a brief of what happened while it was away, composed the same way. That is what makes a switch a move rather than a fork.

Three consequences are stated rather than discovered:

- **What did not carry is declared at application, and the person reads it.** The declared-loss list rides the `agent.provider_binding_changed` event, and an **empty list is a positive assertion that nothing was dropped** — a driver that does not know what it lost may not emit one. A turn-boundary switch moves nothing and so drops nothing: its list is empty by construction, and that emptiness is the same positive assertion, not an absence of information. An account move likewise drops nothing. A provider switch always drops something, and the transcript says how much: two faint single lines at the point the run ended, collapsed until pressed — `Hand-over brief · Claude Code`, which opens to the brief, and, under it, `Switched to Codex · continued from a brief · 3 things did not carry over`, which opens to the named list. What composing the brief cost is added to the inspector's `Cost` row for the account that wrote it and is never a line of its own on either row.
- **A switch whose conversation did not arrive whole settles `degraded`, never `applied`.** A provider switch is always in that class, because a brief is not the conversation. The switch still happens; the user is told what the new process can see. A turn-boundary switch and an account move have nothing to reconstitute and settle `applied`.

  The settlement therefore names **which mechanism carried the conversation**, because they are two different acts and not degrees of one. `in_place` is the running process carrying a per-turn override into its next turn, or an account into its next request: nothing was respawned, nothing was reconstituted, and its declared-loss list is empty **by rule**, not by luck. `brief` is a different provider started from a hand-over brief, and its list is **required non-empty** and must name the summarization itself, since a brief settlement whose list said nothing would be claiming that a summary costs nothing. `in_place` is `applied`; `brief` is `degraded`. Collapsing the pair would force one of the lies the wire must not tell: that a summary was the conversation, or that an empty loss list has stopped meaning "nothing was dropped".

### Refusals are fail-closed and precede any spend

A switch is refused, before any turn is started on the target, when the named driver is not registered on the machine that runs the session, when the named model is not in the target driver's `listModels`, when the named effort is not in that model's `effortLevels`, or when the named speed is not in the driver's published `outputSpeedLevels`. Because application may be deferred to a later boundary, that validation runs **twice** — at mutation, so the caller learns immediately rather than at a boundary it is not watching, and again at application, so an axis de-registered in the interval refuses the application and leaves the agent on its current binding rather than realizing a configuration the machine can no longer honor. The account arm defers to [Spec-026](026-provider-accounts-and-credential-homes.md)'s registry and its fail-closed spawn gate ([Plan-026](../plans/026-provider-accounts-and-credential-homes.md)) as the authority — the readiness projection on the account read is advisory and is not consulted as a gate here — and the registry being the machine's own is what bounds this surface: a caller can only name an account the person already signed in on that machine.

**A refusal at application is an event, because no caller is there to receive an error.** The mutation-time arm answers the caller synchronously with `agent.provider_axis_invalid`, and that is the whole story only when the two moments coincide. Where application is deferred, the caller has already been acknowledged and disconnected, so a re-validation failure that produced only a log line would leave a pending switch that resolves into silence — the user waits at a boundary that has already passed. Every deferred switch therefore reaches **exactly one terminal event**: `agent.provider_binding_changed` on the arm that applied, or `agent.provider_binding_change_failed` ([Spec-005 §Agent Lifecycle](005-session-event-taxonomy-and-audit-log.md#agent-lifecycle-session_lifecycle)) on the arm that did not, both carrying the `switchId` the acknowledgment named. The failure event carries a reason — `driver_unavailable`, `model_unavailable`, `effort_unavailable`, `output_speed_unavailable`, `interrupt_refused`, `target_unstartable`, or `account_unavailable` with the account's state (`reauth_required`, `home_missing`, `indeterminate` or `not_registered`) — clears the pending switch, and leaves the agent on the binding and account it had. A refused `interrupt` on the immediate arm settles the same way: the switch is abandoned with a reason rather than left half-moved. The single exception is supersession — a pending switch replaced by a later one emits no terminal of its own, and the superseding acknowledgment names it instead, because two terminals for what the user experienced as one change of mind would be a worse record than none.

**A switch that fails after it was accepted never lands, and says so once.** The session stays on the provider and account it had, the working line's `switching to …` words leave, the success row is not drawn, and the transcript gains one system message naming the switch it tried and the reason: `Switch to Codex failed · <reason>`, or `Switch to account <name> failed · login expired · Sign in again`, with `Sign in again` offered only where the account's state is `reauth_required`. There is no banner, toast, dialog or standing error.

A degraded settlement is **not** a failure and never takes this path: a provider switch settles `agent.provider_binding_changed` with `continuity: 'brief'` and a non-empty loss list. The distinction is exactly whether the agent moved. A degraded settlement moved it and told the truth about what came along; a failed application did not move it at all.

Authorization does not move with the axis. The mutation authorizes exactly as every other `AgentConfigUpdate` member already does — as the session's user under [Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior) — and the immediate arm's interrupt authorizes as `Action::"intervene"` on the target run, an action that spec's named-operation-action enumeration already carries. No further authorization is needed: naming a driver or a model confers no spend authority the caller did not already hold, because the caller may already cause execution on the machine that runs the session, and the drivers it can name are exactly the ones registered there. Choosing among them is a configuration choice inside a boundary already authorized, not a new grant — which is why [Spec-010](010-approvals-permissions-and-trust-boundaries.md)'s named-operation-action enumeration does not grow here. Which **account** pays is authorized separately, by the control that moves it ([Spec-026 §Authorization Posture](026-provider-accounts-and-credential-homes.md#authorization-posture)).

### Identity, attribution, and what does not move

The agent keeps its `agentId`, its name, its run linkage, and its place in every projection built on those. A switch is a change of the agent's provider binding and of nothing else.

§Session Cost Receipt therefore keeps its axis **unchanged in shape**. The receipt keys each request on the account it ran on, so a session whose provider's current account moved mid-way — in place at the acknowledgment of the move — yields two account rows summing to the same session total, the requests before the move under the account they ran on and those after it under the new one: the axis reporting a real split, not a new arithmetic. The partition identities in §Session Cost Receipt hold across a switch for exactly that reason, and this section adds no key, no fold, and no repricing.

## Provider-Native Subagents

- **Single-supervisor invariant: the daemon is the only cross-session supervisor.** A run MAY use its provider's in-session subagents (Claude `--agents` / Task tool; Codex `multi_agent` / `[agents]`) under the `subagentPolicy` the daemon passes through — the policy shape (`{enabled, maxDepth?, maxConcurrent?, definitions[]}` — both limit members carrying the person's own provider setting where they have set one, the daemon setting none of its own and clamping nothing) is owned by [Spec-004](004-provider-driver-contract-and-capabilities.md) and its API Payload Contracts mirror.
- Budget roll-up: subagent spend counts toward the session's spend limit — the §Budget Policies spend count sees it through the run's `usage` events, so subagents provide no budget escape hatch — and a helper's tokens count against its own run's token limit. Each usage row is priced at the exact model it ran on: the attribution rides the durable [Spec-005](005-session-event-taxonomy-and-audit-log.md) usage-row fields `modelId?` / `subagentId?`, populated by the driver normalizer from wire attribution (per-model usage maps; subagent-scoped usage pairing on the subagent triple; the normalizer duty lands with [Plan-004](../plans/004-provider-driver-contract-and-capabilities.md)'s normalizer work), and a row the wire does not attribute is priced at the run's own model. A differently-modeled subagent is thus never priced at its parent's rates, and a model the price table does not price yet is held like any other request (§Cost Derivation And Absent-Cost Semantics) ([Spec-005 §Tool Activity](005-session-event-taxonomy-and-audit-log.md#tool-activity-tool_activity) records the same aggregation rule on `subagent.completed`).
- Approval flow-through: subagent tool calls flow through the same approval pipeline as the parent run's (Plan-010); a subagent introduces no separate trust surface.
- Timeline normalization: subagent lifecycle lands as the registered `tool_activity` rows `subagent.started` / `subagent.completed`, provider-attributed and pairing on the (`runId`, `provider`, `subagentId`) triple.
- A provider's own in-session subagent runs beneath its parent's run and is recorded as a child with a `provider_subagent` link, written by the provider driver when the provider reports it starting and stopping, so it appears in the agent tree; cross-run delegation is governed by §Default Behavior, which sets no depth limit of its own either.
- **The runtime adds no depth cap to the in-session tree.** An agent dispatched inside a run may dispatch agents of its own, and those may dispatch again; how deep that tree may go is the provider's own limit under the person's own provider settings — the daemon sets no depth of its own, passes the person's value through on `subagentPolicy.maxDepth`, and clamps nothing — and where the provider refuses a level, its refusal is shown in its own words. Cross-run delegation carries no depth limit of the runtime's either (§Default Behavior), so this is not an exception to it. Every rule in this section — budget roll-up, approval flow-through, timeline normalization — binds at every level of that tree, not only the first, so spend and approvals reach the run through however many levels stand between.
- **The daemon owns the tree, and every count over it.** The tree a client draws is the daemon's own parent-to-child index for the session (§Interfaces And Contracts), never an arrangement a client infers from the rows it happens to hold. A fan-out count — the agents one dispatch made, how many more their own dispatches made, how many are live — is supplied by the daemon for the same reason: a client may hold only part of the tree, and a count folded from a partial list would understate the work. One list holds every agent the session produced, an in-session subagent and a peer-invoked child run alike, each under whatever dispatched it; the two kinds differ in what they are (§Interfaces And Contracts, how a child was reached) and not in whether they are visible.
- **A dispatched agent is visible in exactly three places, all fed from that one source:** a row in the transcript where its dispatch happened, a row in the session's agent list, and its own view. The dispatch's own row in the transcript counts what it made and, while the dispatching agent is waiting on them, carries that wait as live state beside the count and drops those words in place when the wait ends — one place for the wait, never a second group and never a separate waiting row.
- **What a row states.** Every agent row names the model it runs on and its reasoning effort as one word, whether the dispatch chose them or it inherited them from the session, so a row never goes quiet about what it is running on; where the agent was reached by a peer invocation the row additionally names which agent was asked. Each row carries, under the name, the tools it has used, its tokens, its spend and its duration — figures that read live while it runs and settle in place when it finishes, and that are never dropped to save room. An activity line says what the agent is doing and **stays** when it finishes, with its result beneath it: the last thing it was doing still stands above what it came back with. The list is one tree in the order the work happened; a finished agent keeps its place under whatever dispatched it and can be collapsed away as a set, never re-ordered.
- **An agent's name, icon, and color are resolved for display from the definition it was made from** — through the definition reference its agent record carries — and fall back to the agent's own name where that definition is gone. This is presentation only: the rule that a run keeps the configuration it was resolved for ([Spec-027 §Resolution when a run starts](./027-agent-definitions-and-peer-invocation.md#resolution-when-a-run-starts)) governs configuration and authority, not the label, so renaming a definition retitles a running agent mid-session while editing its tools changes nothing it may do.
- **What no row states.** No row, head, or note says how an agent was made, or by what mechanism a control reaches it — the provider's spawn machinery is an implementation fact and never surfaces. No dependency graph is drawn over the tree.
- **An agent's own view is the session's own rendering at one level down** — its working line, its grouped tool runs, its diffs, its command output, its reasoning, its prose, an approval inline, and a steer box — and it keeps its own scroll position and its own folded runs, per agent, so reading one never moves another or the session behind it. Its head carries the one-line ask it was dispatched with and the whole ancestry back to the session, each ancestor reachable from it. Its rows are fetched on demand, once: any agent in the tree opens, including one whose rows were never in the window a client holds. A finished agent's view is read from the record the daemon stored when it finished and opens at the beginning of that record; where the stored record cannot be read the view follows the agent's own live document instead, so a finished agent always opens. A view with no rows says **which** fact that is — nothing produced yet, or rows still being fetched — and never draws an empty body for either.
- **An agent with agents under it can be folded**, and folding replaces their rows with one line carrying how many are under it, counting their own, and what the live one is doing (`3 sidekicks · docs-sweep editing … · 1 more running`, `2 sidekicks · done`). An agent with nothing under it offers no fold. Nothing folds itself, and a fold outlives a redraw.
- **Every failure is named on the agent that had it, and never swallowed.** An agent that failed says so on its result line with the reason after it, and that is the only mark a row takes — one that finished carries no mark at all. A record that cannot be read says so in one line where the rows would be, naming the cause, and never draws a partial transcript in its place. An agent whose dispatcher is missing from the record says so and draws at the root of the tree rather than under a guess.
- **An agent's own limit is read from the agent, never from the lead.** A provider turn limit settles the agent with its partial result, and a send into its steer box continues it with its context. A provider error may kill an agent while the run that dispatched it reports success, so the reason is read from the agent's own update — a lead's success is not evidence that the agent it dispatched succeeded.
- **A capability the provider refuses is learned from the refusal and remembered for that agent** — never read from an experimental opt-in surface, and never assumed from the provider's documentation.
- **The provider's own subagent view stays switched off.** The tree, the rows, and each agent's view are built from the messages the daemon already routes, so one rendering serves both providers and neither provider's own presentation competes with it.
- **Inside a session the app runs, an agent's `claude agents`, `claude daemon` and `claude --bg` are refused by the command policy, and Claude Code's switch that turns them off (`disableAgentView`) stays pinned**, because such work would run outside the session's agent tree, outside `Stop` and `Interrupt`, and off the session's receipt ([Spec-010 §Required Behavior](010-approvals-permissions-and-trust-boundaries.md#required-behavior)). Claude Code used in the person's own terminal is untouched.
- Concurrency: `maxConcurrent` is the person's `Helpers at once` for that provider. It is optional, and empty is no limit; `0` withholds the provider's helper tool. On the Codex leg a number above zero is passed as Codex's own `agents.max_concurrent_threads_per_session`. Claude Code has no such setting, so on that leg, for a number above zero, the daemon's pre-tool hook on the Agent tool holds a new helper's start until one of that session's running helpers finishes. Where a provider refuses a spawn under a concurrency limit of its own, its refusal is shown in the provider's words. A subagent's spend counts toward the session's spend limit however many ran alongside it (no escape hatch).
- **A Codex helper's tool servers and turn limit are the daemon's to carry.** A Codex helper inherits the lead's tool servers exactly; a server listed on such an agent is added to the lead's session and granted to that helper alone by the daemon-fronted server, which sees the calling thread on every call. On a Codex session the daemon fronts every tool server it can reach: each is a `url` entry on the daemon's route, and the daemon's own MCP client holds the real connection, on the daemon's own sign-in where the server needs one — which is also how it lists and reads a server's prompts for a Codex session, and how it answers a call running past 120 seconds with a handle rather than holding the turn. A Codex helper's max turns is enforced by the daemon counting the helper's model rounds on the wire: at the cap the daemon's pre-tool hook denies every further call with `You have reached your turn limit. Report what you completed and what remains.`, so the helper writes its report and its turn ends, and the lead's wait returns it; the count re-arms on the helper's next turn.

## Scheduler Limits

The runtime adds no count limit of its own: not on how many orchestration runs may be pending, not on how many children a run may have, and not on how many items a session may queue. How many agents run at once is the person's `Helpers at once` for that provider (§Provider-Native Subagents), and how deep they may nest is that provider's own limit under the person's own provider settings; where a provider refuses, its refusal is shown in its own words. What a session may spend is its spend limit, which the person sets (§Budget Policies).

Admission still refuses on the spend limit the person set, and on the state of what a run targets: while a reached spend limit stands, a message lands in the transcript, no turn starts, and the `Spend limit reached` row lands under it. Every such refusal is enforced at create-time admission with zero residue (no run row, no queue item survives a refusal), is a typed error carrying its own detail, and is recorded durably by the daemon via `orchestration.rejected` ([Spec-005 §Orchestration Admission](005-session-event-taxonomy-and-audit-log.md#orchestration-admission-orchestration_admission)). The limits live in the session budget surface and are owner-adjustable.

## Partition And Reconnect Behavior

Every agent of a session runs on the machine that runs the session, so a partition separates that machine from the user's other devices, never one agent from another. How the machine is reached, and when it counts as not reachable, belongs to [Spec-002](../specs/002-runtime-node-attach.md); catch-up belongs to [Spec-013](../specs/013-persistence-recovery-and-replay.md).

- When the machine loses its relay connection, its runs keep going wherever it can still reach its providers, and their events stay in its local audit log ([Spec-005](../specs/005-session-event-taxonomy-and-audit-log.md)).
- Another device shows the machine not reachable, with the time it was last seen, and keeps each of its runs at the last-known state preserved from the event cursor. Not reachable is the machine's state, read from its relay connection; it is not a run-state transition, it is distinct from the run-level `paused` state defined in Spec-003, and no run carries a reachability field of its own.
- On reconnect, the device catches up through Spec-013 replay.
- Run ordering needs no cross-machine consensus, because one machine orders every run of the session.

## Implementation Notes

- Keep orchestration semantics provider-agnostic and session-scoped.
- Internal helper runs should be discoverable without overwhelming the default UI.

## Pitfalls To Avoid

- Treating multi-agent orchestration as only a UI grouping trick
- Hiding child-run provenance
- Assuming provider-native spawn semantics are universal

## Acceptance Criteria

- [ ] A session can host multiple concurrent agents.
- [ ] Parent-child run relationships remain visible after replay and reconnect.
- [ ] Delegated work remains possible even on drivers without native subagent APIs.
- [ ] Every surfaced cost figure equals the committed-spend fold the accountant enforces against, and carries no mark.

- [ ] An agent whose provider, model, or effort is changed keeps its `agentId` and its run linkage, and the conversation continues rather than restarting; so does an agent whose provider's current account moved under it.
- [ ] A switch requested without `interruptAndSwitch` leaves an in-flight turn to complete on its original binding and takes effect at the next boundary its target axes permit — a **run** boundary whenever `driverName` moves, a **turn** boundary only where every moved axis is a per-turn override on the target driver, and the widest of the two on a multi-axis update; the immediate arm dispatches the existing `interrupt` intervention and mints no new run control. The mutation carries no account member at all, and a caller that supplies one is refused rather than served.
- [ ] A switch naming an unregistered driver, a model absent from the target driver's `listModels`, or an effort absent from that model's `effortLevels` is refused before any turn is started on the target.
- [ ] A provider switch settles `degraded` with `continuity: 'brief'` and a non-empty declared-loss list, never `applied`: the brief is built on a throwaway copy with the live session untouched, the first message to the new provider carries the brief then the current diffs and branch then every earlier step as a one-line note then the last exchanges verbatim then a reference to the whole old transcript, which exists as one plain readable file beside the brief whose contents are in no part of the message, no private reasoning and no live tool call and no old-provider skill or command name is in it, and the transcript carries **exactly** the two rows naming the brief and the switch with a count of what did not carry over — the transcript file gets no row of its own. An account move settles `applied` with `continuity: 'in_place'` and an empty list.
- [ ] After the provider's current account moves under a live session, the session cost receipt shows the requests before the move under the old account and those after it under the new one, and its account rows still sum to the session total.
- [ ] Switching a session to another provider and back reopens the first provider's own conversation by the identifier it kept, with a brief of what happened while it was away, rather than starting a third conversation.
- [ ] A change of model, effort or `outputSpeed` alone settles in place with an empty declared-loss list, respawns nothing and draws no row; an `outputSpeed` mutation against a driver that has no output-speed axis refuses before anything is spent and is never satisfied by changing `effort` instead.
- [ ] A switch that fails after it was accepted leaves the agent on the binding and account it had, draws no success row, and adds exactly one system message naming the attempted switch and its reason, with `Sign in again` only when the account's state is `reauth_required`.

- [ ] A Claude Code session and a Codex session each reach the other through `SendToSession`, in both directions, and each exchange draws one row in the sending transcript and one in the receiving one; the receiving row sits where the message was folded into that turn rather than at the turn's end, and a session that was busy when the message arrived shows it inside the turn that was running.
- [ ] A `SendToSession` call raises the ordinary approval card at a level that asks and asks nothing at `Sandboxed` and `YOLO`, with no gate of this runtime's own, and what the message causes in the receiving session follows that session's own level.
- [ ] `ListSessions` names sessions on **both** providers, including one the sending provider's own listing cannot see, each with whether it is working or idle.
- [ ] A Claude Code session's own `SendMessage` aimed at another session is denied by the daemon's hook, the model reads `send with SendToSession`, and the same tool aimed at one of that session's own agents still works.
- [ ] A message the receiving provider dropped silently reads `not delivered` once that session goes idle and never reads `delivered`; a message a paused session was addressed with reads `queued, builder is paused`, waits, and is delivered on the continue in arrival order.
- [ ] Interrupting either session of a live exchange ends both turns, empties the queue between them, and lands one row in each transcript naming how many messages were not delivered.
- [ ] No message table, message row or message event type exists: the only durable record of an exchange is the two sessions' ordinary tool events, while the exchange table and the paused queue survive a daemon restart and the restarted daemon delivers what it was holding.
- [ ] A Claude Code session the person started in their own terminal reaches a hosted session by that session's address, with no plugin installed, and the arrival draws the same row a tool send draws.
- [ ] With no step bound set, two sessions trade a long exchange to its own end: no count, cap, throttle or refusal of this runtime's ends it, and the only limits that fire are the receiving provider's own, reported in that provider's own words. With a bound set, the turn ends at the number and `Continue` — or the next arriving message — carries the same turn on rather than starting a run.

## Design Decisions

- V1 decision: **inside one session** agents communicate through run linkage, the session timeline their child runs publish into, artifact references and approvals, and no direct run-to-run messaging primitive is added between agents of the same session. **Between two sessions** the boundary is the one tool the daemon serves to both providers (§Sessions Talking To Each Other): a message there is an ordinary tool call on the sending side and an ordinary tool row on both.
- V1 decision: the runtime adds no depth ceiling of its own to canonical delegation. A child run may create child runs of its own; how deep agents nest is the provider's own limit under the person's own provider settings, a provider's refusal is shown in its own words, and every budget, approval, and visibility rule binds at every level rather than at the first alone.
- V1 decision: concurrent child runs are allowed, and v1 imposes no numeric ceiling of its own on them. How many a provider will run at once is that provider's own limit under the person's own provider settings, and admission refuses only on the budgets the person set and on the state of what a run targets (§Scheduler Limits).
- V1 decision: **voice ships.** `/voice` is a console word on both providers and does what each provider's own `/voice` does: on a Claude Code session it dictates into the composer, the daemon running its own socket to Anthropic's speech service for each recording; on a Codex session it runs Codex's own realtime voice call, the app window the call's WebRTC peer, the daemon passing the window's offer in `thread/realtime/start`, returning the answer `thread/realtime/sdp` carries, routing the `thread/realtime/*` notifications by `threadId`, and sending `thread/realtime/stop` when voice is turned off or moves. Codex sends those notifications only to a connection that set `initialize.capabilities.experimentalApi` and drops them silently for any other, so the daemon opts in at `initialize`, and the check against a new Codex build probes that runtime behavior rather than reading the generated schema ([Codex wire reference](../reference/provider-wire/codex.md)). On both providers talking starts the same way, by holding Space or, after `/voice tap`, tapping it; a hold on Codex reaches the call only once Space is let go, played in at 1.5× with the pitch kept and each pause cut to 0.2 s. A voice call adds no media type, and its cost is the `Voice` row of §Cost Figure Display Consistency. The provider legs are [Spec-004](004-provider-driver-contract-and-capabilities.md)'s, the composer's capture is [Spec-021](021-desktop-app-and-renderer.md)'s, and the scope entry is [ADR-015](../decisions/015-v1-feature-scope-definition.md)'s.
- V1 decision: **compaction is the provider's own, run at the point the person sets — a safeguard, never a stop.** Context-window headroom is not a budget (§Budget Policies). Each provider compacts on its own authoritative counts, never on our estimate: the daemon maps the person's per-provider default (`Compact automatically at <N>% full`) and each session's own bound onto the provider's own knob — Claude Code's `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`, Codex's `model_auto_compact_token_limit` — and `Compact now` or `/compact` runs the provider's own compaction at once ([Spec-011 §Context Window and Usage Meters](011-live-timeline-visibility-and-reasoning-surfaces.md#context-window-and-usage-meters)). A context that no longer fits is a compaction on both providers, never an error. Two invariants bind it. **Room to compact**: the highest bound the person can set is the provider's own compaction point on the session's window, so the compaction call itself always has room to run — too-full-to-compact is a documented field deadlock ([anthropics/claude-code#25620](https://github.com/anthropics/claude-code/issues/25620), accessed 2026-07-12), and surveyed runtimes hold their triggers below the ceiling with an explicit reserve partly for this reason ([GitHub Copilot CLI context management](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/context-management) keeps a ~20% buffer and names its thresholds "automatic safeguards rather than hard stops", accessed 2026-07-12). **Recoverable originals**: compaction summarizes the provider conversation only, never the session record — the canonical event log ([Spec-005](005-session-event-taxonomy-and-audit-log.md)) keeps the full pre-compaction history under its own retention rules, so dropped detail stays re-derivable as a record; that is an audit and re-derivation guarantee, not a live-conversation undo, since neither provider wire exposes a compaction-restore operation. The surveyed 2026 provider surfaces ship compaction first-class (client-side auto-compact in the provider CLIs; server-side as the Messages API `compact_20260112` context edit — [Anthropic compaction](https://platform.claude.com/docs/en/build-with-claude/compaction), accessed 2026-07-12), so the product composes with the provider's machinery rather than inventing summarization.
- V1 decision: **the displayed cost and the enforced cost are one fold** — every surfaced cost figure is supplied by the accountant that enforces, never recomputed beside it (§Cost Figure Display Consistency). A display-side sum over the visible run list renders whatever the list happens to show, which under any delegation is less than what the ledger holds; a second fold maintained for presentation drifts by construction, because two accountants over the same events diverge the moment one gains a case the other lacks; and a mark on the figure — an estimate, a bound, `unpriced` — would claim a doubt the accountant does not have, since every figure is the provider's own or the price table's. No budget is added and no number changes.
