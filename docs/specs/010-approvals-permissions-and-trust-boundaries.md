## Purpose

Define the approval model, permission scopes, and trust boundaries for execution in a session.

## Scope

This spec covers approval requests, approval scopes, remembered grants, and the distinction between session authorization and local execution trust.

- Transport protocol details
- Notification policy

## Required Behavior

- The system must distinguish:
  - runtime-node trust
  - run-level approval policy
  - tool- and resource-level permission grants
- **Run-control interventions** — `steer`, `interrupt`, `cancel`, and `rollback`, the canonical intervention types of [Spec-003 §Interfaces And Contracts](./003-queue-steer-pause-resume.md#interfaces-and-contracts), together with the orchestration-layer `run.pause` / `run.resume` mutations, which are governed identically — are authorized as the session's user, **never by run authorship**: the user may intervene on any run in the session, including a run an agent started on its own initiative and a run targeting a sidekick the user did not launch by hand. Within the intervention authorization path, run authorship is audit metadata and never an authorization input — the same rule [ADR-011](../decisions/011-generic-intervention-dispatch.md) applies to `initiatorId`. This grant is **bounded by the node-trust rule below**: where the target run executes on a runtime node outside the local daemon's own trust envelope, the intervention is admitted only under that node owner's authority — an approval in the `tool_execution` category per [Spec-022](./022-cross-node-dispatch-and-approval.md)'s dispatch rules — so cross-node steering is a request, never standing authority. Authorization to **direct** a run is distinct from executing **as** its initiator: a turn opened by an accepted `steer` executes under the **user's** effective Cedar principal — resolved from the verified caller identity the daemon admitted the steer under (the PASETO `sub` that authorized the intervention, durably recorded on the accepted intervention), never from any client-supplied actor field, which stays informational per [ADR-011](../decisions/011-generic-intervention-dispatch.md) — so the sensitive actions a steered turn produces adjudicate against the user's own policy and remembered rules rather than against whatever opened the run. The same rule binds every intervention-opened turn, not steer alone: a turn opened by an admitted **run-bound replacement send** — [Spec-003 §Required Behavior](./003-queue-steer-pause-resume.md#required-behavior)'s edit-and-resend composite, V1's only run-bound producer — executes under the **admitting intervention caller's** effective principal, resolved from the same durably-recorded verified identity on the accepted intervention, so a corrected prompt the user authored never executes under an authority the run happened to carry. Turns opened by the run's own continuation, and interventions the daemon itself admits on the `system` arm, keep the run-initiator principal unchanged.
- Sensitive actions must require approval or prior grant according to policy. This includes at least destructive git operations, out-of-boundary file writes, unrestricted network access, and high-risk tool execution.
- The canonical approval category enum is:
  - `tool_execution` — tool call approval
  - `file_write` — out-of-boundary file writes
  - `network_access` — unrestricted network
  - `destructive_git` — force push, branch delete
  - `user_input` — freeform questions from agent
  - `plan_approval` — proposed plan review
  - `mcp_elicitation` — MCP server input
  - `gate` — workflow phase gate
  - `human_phase_contribution` — phase-level human contribution (Spec-015 `human` phase submission; SA-12 addition per BL-097 Wave-1 synthesis)
- Approval requests must record requester, target scope, and requested capability.
- Approval resolution must record approver, decision, and effective scope.
- Access to a session must not imply authority to execute on a machine the session does not already trust.
- The user's own runtime node may be trusted as the default execution host within its local daemon policy envelope, but that trust must not bypass approval rules for out-of-envelope or high-risk actions.
- Driver-native permission flows must be normalized into the canonical approval model. A provider-initiated mid-run ask normalized this way ([Spec-005 §Driver Ask Events](./005-session-event-taxonomy-and-audit-log.md#driver-ask-events)) **waits until it is answered**. No deadline is stamped on it, no timer runs beside it, and nothing settles it on elapsed time: a countdown would turn a decision into a race and make the outcome a choice the product had taken on the user's behalf, and silence is never read as a grant. The wait is durable rather than bounded — the pending ask and the blocking state it puts the run into are persisted, rebuilt from the event log after a daemon restart, and still waiting afterwards. An ask raised by a provider-native subagent ([Spec-014 §Provider-Native Subagents](./014-multi-agent-channels-and-orchestration.md#provider-native-subagents)) takes the same path: it surfaces on the session's approval and interactive surface and waits there like any other ask, never silently stalling its parent run. **Both providers hold their side of that wait without a ceiling**, measured 2026-09-21. Claude Code 2.1.278 held an unanswered `can_use_tool` permission request on its stream-json control channel for 900 seconds in one run and 1,500 seconds in another, sending no cancel frame either time; the answer was accepted at 904 and 1,504 seconds and the tool then ran. Codex 0.155.1 held an unanswered `item/commandExecution/requestApproval` for 1,503 seconds with no frame of any kind in between, then took the acceptance, resolved the request, ran the command and completed the turn. One neighbouring provider surface does impose a ceiling, and it is not this one: an unanswered Claude Code hook callback is cancelled by that command-line tool at 600 seconds unless the matcher registered for it carries a `timeout` of its own, and the cancelled call is reported to the model as a tool that did not run — which is why the daemon sets that timeout itself wherever it holds a callback open ([Spec-003 §Required Behavior](./003-queue-steer-pause-resume.md#required-behavior)) rather than letting a person's decision expire. A run holding an open ask keeps its liveness exemption from the idle sweep for as long as the ask stands; the exemption ends the moment the ask is answered or is closed with the run that raised it, and the run rejoins the ordinary idle path there.

- **The approval surface is one card in the session's composer area.** An approval is raised there and nowhere else — never a modal, never a toast, never a free-standing timeline card, never a notification of its own — and exactly one is shown at a time: a queue of waiting approvals is worked one item at a time, the card carrying its place in that queue beside its eyebrow (`1 of 3`) while more than one waits and carrying no count at all while one does. The card pushes the conversation up rather than covering it. There is no countdown, no "approve all", no per-approval keyboard accelerator, and no cancel-the-turn action beside it. Amber on this surface means, and only means, that a person is needed.
- **The card says exactly what is being asked.** An eyebrow, a title and a summary line name the ask. One reason line under the summary carries the provider's own words for why this particular action stopped, with control characters and terminal escape sequences stripped before it is shown and the line absent rather than empty where the provider sent none. The subject of the ask is shown whole in a fixed-width block — the command for a command, the path for a read or a write, the text for an input — which wraps rather than cutting and, past a height derived from the card, scrolls inside itself while the card keeps its answers in reach.
- **Three answers in one fixed order — decline, allow-and-remember, allow once** — the last being the primary. The remembering answer states its own scope in its label: the session, and the subject the daemon derived from the ask (a command's program and first subcommand, a network request's host, a written file's name), with the project offered as a second scope (§Default Behavior). Where the provider marks an ask as one that must not carry a standing allow, that middle answer is **absent rather than disabled** and nothing takes its place; the remaining two keep their order and the primary stays last.
- **A decline may carry a reason.** Choosing to decline opens one optional line on the card; whatever is typed there is delivered to the sidekick through the provider's own refusal field, and an empty line sends a bare decline. That line is the only thing the press adds, and the decline then resolves in place like any other answer.
- **The subject may be corrected before the ask is answered.** The command or path the card shows is editable in place, and the edited text is what goes back with the answer and what the audit record shows as having run. There is no raw form of the call on the card and no fourth answer.
- **Resolution is in place, with no banner.** An allow hides the card, un-waits the blocked call — whose elapsed clock resumes where it stood rather than restarting — and lets the run carry on, the result landing when it settles. A decline hides the card, the blocked call's row reads `Declined` where its result would sit, and the session leaves the group of sessions waiting on a person. An allow also marks the session's review data stale, because work the user has not seen may now have landed.
- **An approval raised by a child run is the parent's approval.** It is answered on the parent session's own card, through one approval pipeline and one trust boundary; a child's own view offers the same answers, by position in the same row of three, and mints no second answer surface. Walking from a child to the approval brings that card into view rather than drawing a second control beside the child.
- **Only the three most careful permission levels ask at all.** A session runs at one of five permission levels, most careful to least: `Read-only`, `Ask`, `Reviewed`, `Sandboxed`, `YOLO`. An approval card exists at the first three. At `Sandboxed` and `YOLO` the daemon answers every ask itself under the level's own posture — moving the level there answers an open card and lets its blocked row run, a later ask raises no card, and moving back to a level that asks asks again.
- **The card carries no clock and never settles itself.** The daemon holds the request open with no timer, rebuilds the card on reload and on every linked device of the user, and lets the first answer settle it everywhere; a device that was showing the card closes it with one line saying it was answered elsewhere, raising nothing that reads as an error. Four things close an open card and nothing else does: the person's answer; an interrupt of the run that raised it, which cancels the approval with the run and records the cancellation; a move of the session's permission level to one that never asks, where the daemon answers the open card itself under that level's posture and lets its blocked row run; and the provider process ending on its own, which takes the approval it was holding with it ([Spec-018 §Required Behavior](./018-observability-and-failure-recovery.md#required-behavior)). Elapsed time is not on that list — the card is exactly where it was left, however long that is.
- **A plan awaiting its verdict takes the same card in the same place.** Its eyebrow reads `Plan`, its title is the plan's first heading, and its summary counts the plan's top-level steps and the files it names and says that nothing has changed yet; it carries exactly three answers in one fixed order — keep planning, build in a fresh session, build it — and nothing else: no permission row, because the session's permission level already holds that choice and the card never asks it twice, no text box, because the composer is the text box, no provider name and no dialog. Keeping on planning hides the card and appends nothing, the next message being ordinary feedback in plan mode, and the card returns with new counts when a revised plan lands. Building appends one act row, restores the level's own posture, and lets the same session carry on with its history. Handing the plan to a fresh session appends an act row that leads to the new session and leaves the planning session's history intact. While the card is up, the session is one of those waiting on a person, exactly as one blocked on an approval is.
- **A denied lead sidekick is told why, in this product's own words.** The denial that keeps a lead away from a child run the user paused carries one fixed sentence as its reason and never anything the user typed: `The person paused this sidekick from the console. It will not take messages on any channel until they resume it. Do not retry another way; continue with what you can, or wait.` It is the same sentence on every provider and on every tool that could reach that paused child — denying one such tool leaves the others open, so each of them carries it — and it is never drawn on screen, because it is a wire string the lead reads: a refusal with no reason reads to the lead as a broken harness, while a sentence naming who paused the child and why reads as the environment it is. The steer channel is untouched: on a held child the user's own typed words are still the denial reason, and the child still reads them as its instruction.

> **Amendment (approved spec — 2026-07-02, capability-enhancement campaign B20).** Required Behavior gains a canonical **execution posture** — a provider-uniform authorization input layered onto the trust distinction above (runtime-node trust, run-level approval policy, tool- and resource-level permission grants) — and specifies how driver-native sandbox and permission flows normalize into it, extending the driver-normalization obligation immediately above. It also pins the authorization rule for daemon-registered session callback tools. No section is renamed or removed; the additions are the bullets below.

- Each run carries an **execution posture**: `executionPosture { mode: 'readonly' | 'ask' | 'reviewed' | 'sandboxed' | 'yolo', networkAccess: 'none' | 'allowed-domains' | 'full', allowedDomains?: string[], writableRoots: string[], profileName?: string, credentialPolicyRef?: string }`. Its `mode` is the session's **permission level** — the same five words the level control offers, most careful to least, and the only posture vocabulary in the product. **How a level maps to the sandbox and network posture the driver applies.** The three most careful levels ask, and each is realized as the provider's own asking mode: `readonly` reads on its own and asks before any change (Claude Code's manual mode restricted to reads; Codex's Read Only), `ask` edits files on its own and asks before running a command (Claude Code's accept-edits; Codex's Ask for approval), and `reviewed` lets the provider's own automatic check approve routine work and asks on the rest (Claude Code's auto mode; Codex's Approve for me). The two least careful levels never ask, so an enforced boundary stands where the card would have: `sandboxed` runs the provider's own sandbox with writes confined to the worktree (Claude Code's don't-ask with its Bash sandbox on; Codex's workspace-write with approvals off), and `yolo` enforces no limit at all — commits, pushes and opening a pull request all run unasked (Claude Code's bypass permissions; Codex's Full Access). The provider's own name for a mode never reaches a screen; it is a driver-realization detail this section records. A level the bound session, account and model cannot actually run is not offered at all, and a saved sidekick asking for one the session cannot give runs one step **more** careful and says so, never looser than asked. `credentialPolicyRef` is a **content-addressed reference** to the daemon's curated credential-policy artifact in effect: `"sha256:<hex>"` over the [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) JCS-canonicalized artifact document `{schemaVersion: 1, denyPaths: string[], denyEnvVars: string[], envNameMatch: 'case-sensitive' | 'case-insensitive'}` — where `denyPaths` holds the **daemon-expanded canonical absolute effective paths** at policy-resolution time (tilde and environment references expanded, symlinks resolved, platform case/relative components normalized), never raw config strings like `~/.ssh`, and `denyEnvVars` holds environment-variable names **canonicalized to the host's environment-name case semantics** at that same resolution time — a host whose process environment matches names case-insensitively folds each name to a single canonical spelling (so `GITHUB_TOKEN` and `github_token` collapse to one entry), a case-sensitive host keeps them verbatim, and the daemon spawn-env strip matches under those same host rules — with the host's matching mode itself recorded as **`envNameMatch`** in the hashed document, because canonicalizing the names is not sufficient: a case-insensitive host strips **every** spelling of a curated name while a case-sensitive host strips only the exact one, so two hosts sharing a `denyEnvVars` list but differing in match mode enforce **different** effective boundaries and MUST therefore carry **different** refs (with `envNameMatch` hashed, ref equality means the same denied set _and_ the same strip rule) — so a curated secret cannot survive under an alternate spelling and ref equality still means effective-boundary equality **across** hosts, not only within one (this env-name predicate is deliberately distinct from the filesystem case-normalization governing `denyPaths`: a host may fold filesystem paths yet still distinguish env-var names, or the reverse) — and the daemon **lexicographically sorts and dedupes both arrays before hashing** (RFC 8785 canonicalizes object members, not array order — unsorted arrays would give order-dependent refs), so ref equality means effective-boundary equality across hosts and homes (the raw curated list is daemon configuration; the artifact records what it resolved to for this run) — REQUIRED on every run so auditors can reconstruct exactly which credential paths and variables the daemon handed the provider to deny for this run without embedding the raw (installation-revealing) list in the audit log. Content addressing makes the artifact immutable and self-deduplicating by construction (identical policy ⇒ identical ref; two runs carrying the same ref carried the same policy), and the ref can never dangle: the daemon persists the artifact row **write-ahead** — before the first posture stamp that cites it (the same ordering discipline as ADR-019's spawn-intent registry) — and retains it at least as long as any run event citing it (compaction/shred follow the audit-stub retention class). Storage is daemon SQLite; the table's CREATE lands with the campaign B13 code lane that implements posture stamping (the pattern B1 set for the terminal-backstop index shipping with B11's schema work). The API Payload Contracts mirror gains this field with this bundle. `allowedDomains` is meaningful only with `networkAccess: 'allowed-domains'` and holds exact hostnames or leading-`*.` wildcard patterns — hostname-matched, per the domain-fronting caveat below. `writableRoots` holds absolute paths; the daemon canonicalizes each root (symlink-resolved real path; relative paths rejected) before the posture enters Cedar evaluation, so policy always compares canonical paths, never raw input. The posture is a **Cedar authorization input**, not merely a spawn-time knob: policy MAY require a minimum posture per trust level (a less-trusted context cannot select a weaker sandbox than policy allows), evaluated inside the same principal-action-resource-context decision as every other approval category. **Minimum-posture comparison is per-axis, never cross-axis**: strictness is defined independently on each axis — `mode` takes the level order, least careful to most: `yolo` < `sandboxed` < `reviewed` < `ask` < `readonly`; `networkAccess`: `'full'` < `'allowed-domains'` < `'none'` (tier-level; between two `'allowed-domains'` postures policy MAY additionally require a domain-subset relation, computed daemon-side under canonical host-pattern rules — hostnames normalize to lowercase punycode FQDNs with no scheme / port / trailing dot; patterns are exact FQDNs or single-form wildcards `*.suffix`; exact ⊆ exact iff equal, exact ⊆ `*.suffix` iff the host is a **proper** subdomain of `suffix` (the bare suffix is not covered — list it exactly), `*.s1` ⊆ `*.s2` iff `s1` equals or is a proper subdomain suffix of `s2`, a wildcard is never ⊆ an exact, list A ⊆ list B iff every pattern in A is contained by some pattern in B, and any other pattern form is incomparable — floor unsatisfied, fail closed (the daemon computes the subset verdict and passes it to Cedar as context; Cedar never re-implements pattern math)); `writableRoots`: compared by **canonical path containment**, not literal array membership — a caller's roots satisfy a floor iff **every** canonical caller root is contained by (equals or is a descendant of) some canonical floor root, exactly parallel to the intra-`'allowed-domains'` subdomain-subset above, so a `sandboxed` caller narrowing a `["/repo"]` floor to `["/repo/src"]` writes a strictly smaller effective set and **satisfies** the floor rather than being rejected for choosing a safer posture. The two ends of the level order are the well-defined endpoints of that containment: `readonly` writes nothing (∅, contained by every floor, so it satisfies **any** roots floor and is never rejected for choosing a safer posture), while `yolo`'s canonical `[]` denotes _no write limit_ (the unconstrained set — the flip noted below), so a `yolo` caller satisfies only a `yolo` floor, a `yolo` floor is satisfied by every posture, and a `yolo` caller failing a lower floor is rejected on the `mode` axis, never admitted by misreading its `[]` as 'nothing writable' — and a posture satisfies a floor iff **every** axis independently meets its floor, so cross-axis trade-offs (for example `readonly` + `'full'` network versus `sandboxed` + an allow-list) are incomparable by construction and never substitute for one another. `profileName` resolves to **daemon-side posture presets** so that named profiles are provider-uniform rather than references into a provider's own profile store. **Cross-field invariants (fail closed)**: the daemon validates the posture object before it enters Cedar evaluation or spawn — `networkAccess: 'allowed-domains'` requires a present, non-empty `allowedDomains` (and `allowedDomains` MUST be absent under `'none'` / `'full'`); `mode: 'readonly'` requires `writableRoots: []`, because that level asks before any change; `mode: 'yolo'` (no OS-sandbox enforcement) MUST be **supplied** as `networkAccess: 'full'` + `writableRoots: []` — the canonical form denoting no OS-enforced constraint, so no posture record implies a constraint nothing enforces; any other combination under `mode: 'yolo'` is a violating combination and is **rejected** like every other cross-field violation — the daemon never rewrites a restrictive request into the permissive canonical form — and symmetrically with the `allowedDomains` clause above, `writableRoots` is meaningful only on the four levels below `yolo`: under `mode: 'yolo'` the canonical `[]` denotes _no OS-enforced write constraint_ (unconstrained), the opposite of the same value under `readonly` (nothing writable), so audit reconstruction MUST read `writableRoots` in conjunction with `mode`, never in isolation. `credentialPolicyRef` does not vary with the level: the curated credential policy is handed to the provider in the provider's own form on every run, and what enforces it is the provider's own rule, never a second mechanism of the daemon's. On the Claude leg the curated paths are permission-rule denies, which Claude Code applies in every permission mode, bypass permissions included ([Claude Code permission modes docs](https://code.claude.com/docs/en/permission-modes), fetched 2026-09-21), so they hold on all five levels; the provider's own caveat holds with them — a deny rule covers Claude Code's file tools and the file commands it recognizes in the shell, and not a subprocess that opens a file itself, which only the `sandboxed` level's OS sandbox closes. On the Codex leg the curated paths are filesystem denies in the permission profile, which the platform sandbox enforces ([Codex permissions docs](https://developers.openai.com/codex/permissions), fetched 2026-09-21), so they hold on the four levels below `yolo`; `yolo` is Codex's Full Access, which runs no sandbox, so under it no path is denied, exactly as Codex behaves outside this product. The curated variables are stripped from the spawn environment on every level on both legs. The ref therefore records what the daemon handed over, and an audit reads it together with the provider and `mode`, never in isolation. A violating combination is **rejected** — the run is refused, never silently normalized into a permissive state — so implementations cannot diverge on whether an ambiguous posture is invalid, deny-all, or permissive.
- The **effective posture is recorded on the run's `run.running` event** — the post-setup-gate spawn-success transition: Plan-003's gate seam admits `queued → starting`, then setup gates (Plan-008's execution-root gate among them) run **before** `driver.startRun`, so the resolved workspace root, shared-`.git` allowance, and preset-resolved profile are final only when `running` fires — a `run.starting` stamp would be premature or wrong. The `executionPosture?` carrier field registers with [Spec-005 §Run Lifecycle](./005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)'s run-state payload (2026-07-02 campaign B1 amendment item (11), PR #173 — a named merge prerequisite of this bundle; the typed wire mirror rides `RunStateChangeEvent.executionPosture?` in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), and **this bundle extends that mirror with `credentialPolicyRef` as a merge-blocking step of its own merge series** — the field is spec'd here first, the mirror gains it before this bundle lands) — so the audit trail records the **complete effective posture object**, never a named-fields subset — and it survives compaction: the Spec-005 audit-stub projection preserves the `executionPosture` object on posture-bearing `run.running` rows — including `credentialPolicyRef`, which every posture-bearing row carries (B1 stub contract), so the boundary stays reconstructable after the payload compacts — including `allowedDomains` whenever `networkAccess: 'allowed-domains'` (the allow-list _is_ the security boundary in that mode; reviewers MUST be able to reconstruct exactly which hosts were reachable) and `profileName` whenever the posture was preset-resolved.
- Driver-native sandbox and permission flows are normalized into this canonical posture, with the realization recorded per driver:
  - **Codex leg** — `native`: built-in permission profiles (`:read-only`, `:workspace`, `:danger-full-access`) plus named `[permissions.<name>]` profiles resolved via `default_permissions` ([Codex permissions docs](https://developers.openai.com/codex/permissions), fetched 2026-07-02), plus per-turn `sandboxPolicy` on `turn/start` (app-server schema, regenerated at the pin the provider-wire reference `docs/reference/provider-wire/codex.md` records, campaign B19 — PR #176, a named merge prerequisite of this bundle; `0.141.0` is that file's supported floor rather than its pin). **Legacy-settings conflict fails closed**: per the same permissions docs, legacy `sandbox_mode` / `sandbox_workspace_write` config keys (or a `--sandbox` flag) shadow `default_permissions`, so the driver MUST NOT pass `--sandbox`, MUST override those legacy keys in every config layer it controls when realizing a posture, and MUST refuse the run when a loaded config still carries them un-overridden — a run is never recorded under a posture Codex does not actually enforce. The same whole-config verification binds named profiles: profiles resolve through Codex's normal config-layer model (a higher-precedence layer can add or replace entries in a same-named `[permissions.<name>]` profile — same permissions docs), so the daemon writes its generated profile at the highest-precedence layer it controls under a daemon-unique profile name and verifies the fully-resolved effective profile equals the posture-derived configuration exactly; any residual widener from another layer (extra workspace roots, network domains, Unix-socket or local-binding allowances) refuses the run. Built-in profile aliases are audited at the same bar: the built-in `:workspace` profile also allows writes to **system temp directories** beyond the workspace roots (same permissions docs), so the daemon-generated profile either suppresses the temp allowance where the config surface can express that, or the recorded posture's `writableRoots` MUST include the effective temp roots — and the same profile keeps `.git/`, `.codex/`, and `.agents/` under each workspace root **read-only** ([Codex agent-approvals docs](https://developers.openai.com/codex/agent-approvals-security), fetched 2026-07-05 — the built-in protection is recursive, and where `<workspace-root>/.git` is a **pointer file** the resolved external gitdir it names is protected too), exclusions the recorded roots carry as **normative semantics** exactly like the Claude shared-`.git` leg: non-command write surfaces are Cedar-denied on `<workspace-root>/.git/**` (including the gitdir resolved behind a pointer-`.git`), `<workspace-root>/.codex/**`, and `<workspace-root>/.agents/**`, and posture realization verifies the generated profile preserves every read-only rule — the audit record always equals the enforced boundary, never a subset of it. The stamp binds **every turn, not one spawn moment**: `turn/start` accepts optional per-turn overrides for posture-affecting fields — `cwd`, the **legacy** `sandboxPolicy`, the **preferred** `permissions` profile-selection, and `approvalPolicy` — each carried as an optional field that persists for the turn ([app-server docs](https://developers.openai.com/codex/app-server), fetched 2026-07-03; the field inventory is pinned in the provider-wire reference `docs/reference/provider-wire/codex.md`, campaign B19). The daemon therefore derives **every** posture-affecting turn field from the stamped posture and refuses any turn carrying a posture-affecting field it did not itself so derive: a turn whose `cwd`, `sandboxPolicy`, `permissions`, `approvalPolicy`, `approvalsReviewer`, or any field the app-server later adds to this posture-affecting class diverges from the posture-derived value is **refused**, never silently started wider than the `run.running` record (a posture change is a new run, not a turn override). **Where that class contains a mutually-exclusive pair, deriving "every" field means deriving exactly one of them (2026-08-26).** `sandboxPolicy` (legacy) and `permissions` (preferred profile selection) are documented as un-combinable, and two measurements at `codex-cli 0.149.1` make the distinction load-bearing rather than stylistic: on a **default** app-server connection `permissions` is refused by name (`-32600 turn/start.permissions requires experimentalApi capability`) while `sandboxPolicy` deserializes, so which member is sendable is a property of the negotiated connection; and on an `experimentalApi` connection the two sent **together** are **not** refused at request validation, so the vendor's documented exclusivity is unenforced at the wire and sending both would select an unspecified precedence rather than error. The daemon therefore derives and realizes **exactly one** member — V1 realizing the non-experimental `sandboxPolicy`, since a posture write must not rest on a field behind an experimental gate even though the Codex driver opts into that gate for its interactive-request leg — and the **un-realized** member is itself a posture-affecting field the daemon did not derive, so a turn carrying it is refused rather than forwarded. The removed `permissionProfile` field is not a third option (it refuses `-32602` on both connection kinds). [Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior) owns the driver-boundary half, including the trigger that re-decides which member V1 realizes: `permissions` arriving in the default generation. This closes by principle rather than by field enumeration, and it explicitly binds `approvalsReviewer` — which `turn/start` also accepts as an optional per-turn override (`TurnStartParams`, provider-wire reference `docs/reference/provider-wire/codex.md`, campaign B19): the driver pins it to `"user"` and the daemon refuses any turn supplying a divergent reviewer, so a later turn cannot reroute approval adjudication to an `auto_review` / guardian path that bypasses the Cedar pipeline. `approvalPolicy` (which actions require approval) and `approvalsReviewer` (who adjudicates) are distinct posture-affecting fields, each derived and verified in its own right. The Claude leg has no symmetric per-turn escape: its sandbox and permission posture are applied at process launch through the daemon-controlled settings surface (the isolated `--settings` payload realized per the Claude-leg description below) and the sandboxing docs define no `turn/start`-equivalent per-turn override, so there is no per-turn widening surface to verify there. And because Codex permission profiles govern **sandboxed local commands** while MCP / app-connector / browser / computer-use surfaces ride separate controls (same permissions docs), the Codex leg carries the same non-command binding the Claude leg's non-Bash rule establishes: network-capable non-command surfaces are denied outright under `networkAccess: 'none'` and Cedar-gated against `allowedDomains` under `'allowed-domains'`, write-capable ones are Cedar-gated against `writableRoots`, and any surface the daemon cannot bind to the posture is disabled for the run **before** the posture is stamped — the recorded posture covers the whole tool boundary, not only sandboxed commands. The stamped `credentialPolicyRef` binds on this leg too, not only on Claude's: `denyEnvVars` are enforced by the provider-neutral daemon spawn-env strip (the daemon owns the spawn environment for every provider process) with Codex `shell_environment_policy` (`inherit: "none"` + explicit `set`) as the native defense-in-depth layer beneath it; `denyPaths` map into the daemon-generated permission profile's filesystem deny rules (the permissions surface governs local-command filesystem access — same permissions docs) with the resolved profile verified to carry every curated deny, non-command read surfaces Cedar-gated against the same canonical deny paths exactly as the Claude leg's non-Bash rule — and on the four levels below `yolo` a posture whose resolved Codex configuration cannot express a curated deny is refused rather than run; under `yolo` Codex runs Full Access with no profile, and no path deny applies.
  - **Claude leg** — `native-partial` (Bash-tool-scoped): the OS-level Bash-tool sandbox (macOS Seatbelt / Linux bubblewrap) is settings-driven and headless-enforceable ([Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing), fetched 2026-07-02; `sandbox.credentials` requires ≥ 2.1.187). A sandboxed realization sets `sandbox.enabled`, `failIfUnavailable: true` (fail-closed if the sandbox cannot initialize), and `allowUnsandboxedCommands: false` (removing the unsandboxed-retry escape hatch); `filesystem.allowWrite` maps to `writableRoots` and `network.allowedDomains` to `networkAccess` — and because the sandbox prompts on an unallowed host and an approval **adds that host for the session** (same sandboxing docs), fixed postures (`'none'` / `'allowed-domains'`) MUST disable prompt-widening: managed-domain lockdown (`allowManagedDomainsOnly`) where the daemon controls managed-settings delivery, else sandbox traffic routes through a **daemon-owned proxy** (`network.httpProxyPort` / `socksProxyPort` — same sandboxing docs) that enforces the posture allowlist without prompting, so the reachable set cannot grow past the `run.running` stamp; and because `sandbox.credentials` ships **no** built-in denies, the daemon supplies a **curated default credential deny-list** (for example `~/.ssh`, `~/.aws`) — and because `sandbox.credentials` binds **sandboxed Bash commands only** (same sandboxing docs), the same curated paths are mirrored as permission-rule `Read` denies for the non-Bash read surface (Read-tool and read-capable MCP invocations are denied / Cedar-gated against the same list) and secret environment variables are bound by the layer the daemon owns outright: the daemon **strips every curated secret env var from the provider-process spawn environment itself**, with `sandbox.credentials` env unsets (sandboxed Bash only — same sandboxing docs) and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` (Anthropic / cloud-provider names only) as defense-in-depth beneath it — spawn-env removal is what binds arbitrary curated names (for example `GITHUB_TOKEN` / `NPM_TOKEN`) for daemon-hosted MCP and every other non-Bash subprocess — so no posture is recorded with a credential boundary its non-Bash tools do not enforce. Under `readonly` the effective Bash write surface MUST resolve to empty: the sandbox docs give Bash commands **default** write access to the current working directory and the session temp directory (with `filesystem.allowWrite` only _adding_ paths), so the daemon's posture realization denies those defaults (read-only working-directory realization plus temp isolation, or the vendor deny knob where one exists) and verifies the resolved write surface is empty — a posture whose defaults cannot be suppressed is not realizable natively and the run is refused rather than audited `readonly` with `writableRoots: []` while the cwd stays writable. Linked git worktrees get the same audit treatment: when the working directory is a linked worktree the sandbox additionally allows writes to the main repository's shared `.git` directory (`hooks/` and `config` stay denied — same sandboxing docs), and because the daemon executes worktree-first ([ADR-006](../decisions/006-worktree-first-execution-mode.md)) this allowance is live on essentially every run — under any level that writes inside the workspace (`ask`, `reviewed`, `sandboxed`) the recorded `writableRoots` MUST include that shared `.git` directory, whose entry carries the vendor-fixed exclusions as **normative semantics of the recorded root** — `hooks/` and `config` inside it are denied for every write path, so the permission-rule scoping for non-Bash tools MUST apply the same exclusions (Edit/Write-class denied and write-capable MCP Cedar-denied on `<shared-.git>/hooks/**` and `<shared-.git>/config`), keeping record-plus-semantics exactly equal to the enforced boundary on Bash and non-Bash paths alike; under `readonly` it is part of the write surface the daemon verifies resolves to empty. A sandboxed realization additionally pins `excludedCommands: []` in the daemon-controlled settings payload and launch against the daemon's isolated `--settings` surface: `excludedCommands` merges **additively** from every settings scope and excluded commands run **outside** the sandbox ([Claude Code settings docs](https://code.claude.com/docs/en/settings), fetched 2026-07-02), so a run whose effective configuration still carries excluded commands is not recorded under a sandboxed level — fail closed. The same check covers the **whole resolved sandbox configuration**, not only excluded commands: `--settings` merges with file-based scopes and array-valued settings **concatenate** across scopes (same settings docs), so a user / project / managed layer can widen `filesystem.allowWrite`, `network.allowedDomains`, Unix-socket allowances (`allowUnixSockets`), macOS `allowAppleEvents` (which removes code-execution isolation per those docs), or the isolation-weakening booleans (`enableWeakerNestedSandbox` / `enableWeakerNetworkIsolation` — each considerably weakens the boundary per those docs) beyond the posture; the driver therefore verifies the run's fully-resolved effective sandbox configuration is **exactly** the posture-derived configuration and refuses the run on any residual widener from another scope — the recorded `writableRoots` / `networkAccess` / `allowedDomains` are always the enforced boundary, never a subset of it. Non-Bash tools (Read / Edit / MCP) ride the permission system rather than the OS sandbox, so per-tool coverage is legible from the posture semantics themselves — the mechanism split (OS sandbox for Bash; permission system for non-Bash) is a property of the posture contract, graded in the Spec-004 capability matrix (campaign B3), never a per-run stamp — and a `mode` label never implies uniform OS enforcement where the Claude leg is Bash-scoped — and precisely because of that split, a sandboxed realization MUST bind the **non-Bash write surface** through the permission system: under `readonly` the daemon-controlled settings deny file-mutation tools (Edit/Write-class) outright and write-capable MCP tools are Cedar-gated against `writableRoots` (the empty set denies all); under a workspace-writing level file-mutation tool invocations are permission-scoped to `writableRoots`. The same binding covers the **non-Bash network surface**: the OS sandbox's network controls are Bash-scoped, so under `networkAccess: 'none'` the daemon-controlled permission rules deny network-capable non-Bash tools (WebFetch-class, network-capable MCP tools) outright, and under `'allowed-domains'` their invocations are Cedar-gated against the same `allowedDomains` list. A run whose resolved permission rules leave any write path — or any reachable network surface — broader than the posture is not recorded under that posture: the recorded `mode` and `networkAccess` bind every path, Bash and non-Bash alike.
- Three boundary facts the posture semantics encode:
  - In-session subagents run in the parent process and **inherit the parent's OS sandbox configuration**, so the sandbox floor covers a run's subagents automatically — no subagent sandbox-escape at the OS layer ([sandboxing docs §Scope](https://code.claude.com/docs/en/sandboxing), fetched 2026-07-02). The **non-sandbox** permission surface is not inherited by default, however: an entry in Claude Code's `--agents` flag carries its own `permissionMode`, `tools`, and `mcpServers` ([Agent SDK permissions docs](https://code.claude.com/docs/en/agent-sdk/permissions), fetched 2026-07-05 — per-subagent override is force-suppressed only when the parent runs `bypassPermissions` / `acceptEdits` / `auto`), so absent binding a subagent could be launched with broader non-Bash Edit / MCP / network access than the stamped posture allows. The daemon therefore **derives every hosted subagent definition from the run's posture** — the `--agents` payload is daemon-controlled, exactly like the `--settings` surface — bounding each subagent's `permissionMode` / `tools` / `mcpServers` to the posture and Cedar-gating them identically to the parent's non-Bash surface; any subagent definition the daemon cannot so bound is **disabled for the run before the posture is stamped**, so the recorded posture covers subagents at the permission layer, not only the sandbox layer.
  - The Claude sandbox is **unavailable on native Windows** (WSL2 only, per the same sandboxing docs) — and a host that cannot fully realize a sandboxed posture (native-Windows Claude leg, missing Linux sandbox dependencies, any partially-realizable knob) **refuses the run**: a sandboxed level is stamped only when fully realized, never stamped degraded, so one `sandboxed` record always means the same enforced boundary on every host — which is also why `Sandboxed` is absent from the level control on a host that cannot realize it, rather than offered and quietly weakened. Per-knob realization _vocabulary_ (`native` / `native-partial` / emulated) lives in the Spec-004 capability matrix (campaign B3), not on the run stamp ([ADR-019](../decisions/019-windows-v1-tier-and-pty-sidecar.md)-adjacent).
  - The network allow-list matches client-supplied hostnames without TLS inspection, so **broad domain allows are domain-fronting-weak** (the sandboxing docs' own §Security-limitations warning); posture presets prefer narrow allow-lists.
- The daemon's command policy carries a **provider-supervisor deny** covering the full background-agent surface: the subcommands `claude agents` / `claude daemon` / `codex cloud` plus Claude's background-agent entrypoints (`--bg`, `/background`), with the daemon additionally pinning `disableAgentView: true` in its controlled settings — the vendor knob that turns off `claude agents`, `--bg`, `/background`, and the on-demand supervisor in one switch, equivalently `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` in the spawn environment ([Claude Code settings docs](https://code.claude.com/docs/en/settings), fetched 2026-07-02) — enforced for **every effective posture** — preset-resolved via `profileName` or supplied inline — so an inline posture cannot bypass it and no preset may omit it. This is the residual-vector control behind the single-supervisor invariant (the daemon is the only cross-session supervisor — [Spec-014 §Provider-Native Subagents](014-multi-agent-channels-and-orchestration.md#provider-native-subagents), landed 2026-07-06 via campaign B6; the command-policy deny itself is enforceable standalone).
- **Callback-tool authorization.** Every daemon-registered session callback tool — the daemon-hosted tool registry exposed into a run, whose shape is defined in [Spec-004](./004-provider-driver-contract-and-capabilities.md) by the campaign's B3 amendment (a named merge prerequisite for implementing this bullet) — is Cedar-governed identically to provider tools, and its invocations land as `tool_activity` records; no callback tool bypasses the approval pipeline.

## Default Behavior

- Default grant scope is `request_only`.
- Session-wide remembered approval rules are `off` by default and must require explicit user opt-in: a rule exists only where the user pressed the answer that records one.
- **A remembered rule is an allow or a block, never allow alone.** An allow is recorded from an approved decision, on the remembering answer's own press. A block is recorded from a declined **network** ask alone, whose decline offers `Block <host> this session` with the project on the same second scope; a later request to that host is then refused by the daemon with no card at all, and its row reads `Declined` where the result would sit. A command's decline and a file's decline keep their single press and record nothing. A block and an allow over the same subject cannot both stand — recording one replaces the other — and the answer's label always says which is in force. `ApprovalResolve` rejects any other remembered-scope request with a typed error; deny-by-default remains the policy engine's job, not the remembered-rule store's.
- **A remembered rule carries the permission level it was made at and the scope it was made for.** The daemon evaluates it ahead of the level's own default and only at that level or a less careful one: at a more careful level the card asks again with the same label, and pressing it re-scopes the rule to the level now in force. The scope is the session or the project — the session from the answer's own face, the project from its second scope — and a project rule is written where the session's own provider writes its durable rules, so the same rule holds for that provider outside this product too.
- File and tool permissions default to the bound workspace or node trust envelope; out-of-boundary access requires explicit approval.
- Network access defaults to denied unless the active policy or approval explicitly allows it.
- The user's own attached runtime node defaults to trusted for running work on that machine inside the node's declared trust envelope, but it does not waive explicit approval for sensitive escalation.

## Fallback Behavior

- If a driver cannot expose granular permission requests, the daemon must enforce an equal or stricter approval boundary at the local execution layer.
- If approval state cannot be durably persisted, the sensitive action must not proceed.
- If a remembered approval rule becomes invalid because node trust changed, the system must revoke it before the next use.
- If node ownership or trust provenance cannot be established confidently, the daemon must treat the node as requiring strict per-request approval for sensitive actions rather than assuming own-node trust.

## Interfaces And Contracts

- `ApprovalRequestCreate` must include category, scope, and requested resource. It carries no deadline: a request a person answers waits until it is answered. The one category no person answers is `gate`, the pre-turn moderation check the daemon makes for itself; it keeps its own denial path and settles on the daemon's own verdict rather than on a card left standing ([Spec-014 §Stop Conditions](./014-multi-agent-channels-and-orchestration.md#stop-conditions)).
- `ApprovalResolve` must include approver, decision, optional remembered-scope request, and audit metadata. The Cedar `principal` for authorization is the verified PASETO `sub` of the caller; the `approver` field in the request body is informational/routing metadata and is rejected when it disagrees with the verified `sub`. See [API Payload Contracts §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model). On the local daemon socket — which carries no PASETO principal per the linked local-daemon model — the `approver` body field is optional: when absent, the daemon records its node-owner user binding as the approver; when present, it is cross-checked against that binding and rejected on mismatch (`auth.principal_mismatch`). The resolution record always carries the recorded approver. (Tier-5 audit.)
- `PermissionCheck` must run inside the local daemon before executing a sensitive local action.
- `ApprovalProjectionRead` must surface pending and historical approval state to the session's authorized surfaces.
- The remembered rules have their own read and their own revocation on the same namespace: one list of the rules in force for a session and its project, and one revoke by rule identifier. `ApprovalResolve` carries the remembered scope and the daemon-derived subject together with the decision, and the rule is stored with the permission level it was made at (§Default Behavior). A resolution, a rule's creation and its revocation are each recorded on the approval-flow events [Spec-005 §Approval Flow](./005-session-event-taxonomy-and-audit-log.md#approval-flow-approval_flow) registers, so a reload and every other linked device rebuild the same pending card and the same rule list from the log rather than from client memory.
- **Plan mode, the plan record, and the plan verdict.** Plan mode is a per-turn setting the daemon derives and realizes on the bound driver: Claude Code's `plan` permission mode, and on Codex the plan-mode field on the turn start together with a read-only sandbox for that turn, because that provider's plan mode changes the prompt and locks nothing. What the provider then holds open — Claude Code's held plan-exit request, or Codex's completed plan item — becomes **one** plan record, whose text is taken from that request or that item and never read off the disk. The record is answered by one call carrying a verdict of `keep`, `build` or `fresh`: `keep` returns the provider to planning with nothing appended, `build` restores the level's own posture and lets the same session build, and `fresh` carries the provider, the account and the permission level of the session to be minted and returns that session's identifier. One event family records the outcome — the plan accepted, and the plan handed off to a fresh session — so both acts survive a reload. A proposed plan is an approval-pipeline decision in the `plan_approval` category and an attention entry exactly as an approval is: the request is held open until a verdict arrives, is never answered on a timer, is rebuilt on reload and on every linked device, and the first verdict settles it everywhere.
- **The session callback tools that reach a workflow are authorized by named Cedar action, never by tool name.** The read tools — kinds, list, read, runs, run read, step read and validate — are gated on the session itself. Authoring a workflow, updating one, setting its schedule, enabling or disabling it, and posting a run's results back into a chat all take `Action::"workflow::author"`. Running a workflow or executing one of its nodes takes `Action::"workflow::start"`; cancelling a run takes `Action::"workflow::cancel"`; resuming one takes `Action::"workflow::resume"` ([Spec-015 §Chat-Invoked Start and Start Authorization](./015-workflow-authoring-and-execution.md#chat-invoked-start-and-start-authorization) owns the tools themselves). Each of them registers the way every other daemon-hosted callback tool does — a JSON-schema input, an approval category, and an activity record on every invocation — and each stays withheld from a run until its approval seam is registered. No callback tool accepts a session or a channel as an argument: the daemon derives it from the invoking turn's channel context and validates it there, so a forged channel cannot be reached.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

- Approval requests and resolutions must be durable and replayable.

- Changes to runtime-node trust must be able to invalidate dependent approval rules.

## Implementation Notes

- Approval UX may present grouped requests, but canonical approval records must remain granular enough for audit.
- Remembered approval scopes should be explicit enums, not free-form client labels.
- Trust changes must propagate into approval evaluation immediately.
- Policy evaluation uses Cedar (CNCF sandbox). V1 runs `@cedar-policy/cedar-wasm` in-process over a build-embedded, signature-verified compiled policy set authored from YAML policy sources (compiled at package build; verified against the pinned operator key on every daemon start, fail-closed — Plan-010 D-010-9). V1.1 changes the policy SOURCE only (build-embedded → runtime-delivered signed policy bundles, criterion-gated per ADR-012); the evaluator does not change. Cedar's principal-action-resource-context model maps to: principal = user, action = the approval category for decisions that traverse the approval pipeline, or a named operation action for authorizations that do not (`Action::"intervene"` on the target `Run` for run control per [Spec-003 §Interfaces And Contracts](./003-queue-steer-pause-resume.md#interfaces-and-contracts); `Action::"dispatch::<capability>"` per [Spec-022](./022-cross-node-dispatch-and-approval.md); `Action::"workflow::start"` on the target workflow for a chat-borne start per [Spec-015 §Start authorization (SA-39)](./015-workflow-authoring-and-execution.md#start-authorization-sa-39), whose principal is the daemon-resolved authoring user of the admitting-principal carrier class below — the schema registration and the carrier are owned here, the adjudication call-site by Plan-015; and `Action::"workflow::cancel"` and `Action::"workflow::resume"` on the target workflow **run** per [Spec-015 §Operator run control (SA-45)](./015-workflow-authoring-and-execution.md#operator-run-control-sa-45), likewise registered here with their adjudication call-sites at Plan-015 T5.14; and `Action::"workflow::author"` on the target workflow for the write half of the callback-tool surface — authoring, updating, schedule-setting, enabling and disabling, and posting a run's results into a chat (§Interfaces And Contracts) — four separate workflow actions rather than one, because authoring changes what a workflow will do, start creates work, cancel destroys it, and resume commits further spend against a provider account, so a single action would make a grant of "may start a workflow" silently carry "may cancel anyone's" or "may rewrite the workflow itself"; these two depend on no carrier, operator controls being invoked from surfaces whose principal the transport already resolves); and `Action::"agent::invoke"` and `Action::"agent::manage"` per [Spec-027 §Required Behavior](./027-agent-definitions-and-peer-invocation.md#required-behavior), registered here with their adjudication call-sites at Plan-027 — again two actions rather than one, separating who may turn peer invocation **on** for a session (`agent::manage`) from who may **use** it once on (`agent::invoke`, checked on the target `Session` at every invocation, with the session's projected peer-invocation enablement flag supplied as Cedar **context** — that flag is the projection of the `session.peer_invocation_set` event and never a `remembered_approval_rules` row, which cannot represent a named-operation action at all, since its category column is closed over the approval-pipeline categories and its rows must reference an approval resolution), so that a principal trusted to exercise a capability is not thereby trusted to enable it. The two actions are the whole registration; `agent::manage` simply resolves two resource descriptors — the node-scoped resource for creating, editing, deleting, and listing the node's sidekick definitions, which carry no session id, and the named `Session` for the enablement act), resource = target (file, tool, network, run, runtime node, etc.), context = session state — a run's hosting node included, which is what makes §Required Behavior's node-trust bound evaluable. Policy artifact signing, verification, and operator key lifecycle are governed by [ADR-012 §Policy Chain of Custody](../decisions/012-cedar-approval-policy-engine.md#policy-chain-of-custody); operational procedures are in [Cedar Policy Signing And Rotation](../operations/cedar-policy-signing-and-rotation.md).

## Pitfalls To Avoid

- Treating session access as equivalent to local execution trust
- Storing remembered approvals with no revocation model
- Allowing provider-specific permission semantics to leak into canonical docs

## Acceptance Criteria

- [ ] Sensitive local actions require explicit approval or prior valid grant.
- [ ] Session access alone cannot authorize execution on a runtime node the session does not already trust.
- [ ] Approval records survive replay and clearly show who granted what scope.

## Resolved Questions and V1 Scope Decisions

- Two measurements are open and neither blocks v1. The provider-hold evidence in §Required Behavior runs to about twenty-five minutes on each provider; a hold of several hours has not been measured on either. Nor has a hold that spans a provider process restart — what either provider does with a request it was holding when its process is replaced is unknown. Neither changes what this section requires: silence is never a grant, and the daemon holds the card and rebuilds it from the event log, so a provider that dropped a held request could at worst produce an answer it then refuses, never an action taken without one.
- V1 decision: organization-level stricter policy overrides are out of scope. V1 uses product-default policy with local daemon enforcement and explicit per-request approvals.
- V1 decision: own-node trust in v1 is envelope-bound, not blanket. The user's own runtime node is the default execution host, but sensitive actions outside the node's normal trust envelope still require explicit approval.
- V1 decision: **a driver ask waits until it is answered, and no request a person answers carries a deadline.** A `kind: 'permission'` ask is normalized into the approval pipeline and its run stays blocked on it; a `kind: 'input'` ask never traverses the approval pipeline — [Spec-005 §Driver Ask Events](./005-session-event-taxonomy-and-audit-log.md#driver-ask-events) routes input-kind asks to the run's interactive surface — and its run stays `waiting_for_input` until the answer arrives. No input is ever fabricated and no silence is ever read as a grant, at any tier and any permission level. The pairing between a permission ask and the pipeline request minted for it is **persisted at creation** and is never client-suppliable: the normalizer-minted request records the originating `askId` (carried on `approval.requested` — `ApprovalFlowEventPayload.askId` in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md); the public `ApprovalRequestCreateRequest` deliberately carries no `askId` and its strict schema refuses a smuggled one, because a caller-forged association could route another ask's outcome to the wrong native ask), and the association is persisted onto the `approval_requests` projection's `ask_id` column under a unique partial routing index — exactly one approval row per native ask, so a normalizer retry or a replay re-mint collides instead of duplicating — and it is rebuilt from the event at replay ([Local SQLite Schema §Approval Tables](../architecture/schemas/local-sqlite-schema.md#approval-tables-plan-010)). With several permission asks in flight on one run, and across a daemon restart or an event replay, the daemon therefore reconstructs exactly which native ask a pipeline outcome must answer; ask-to-approval routing is never inferred from timing or from a one-pending-ask assumption. A cross-node dispatch is the one place where a deadline still governs an approval, and what bounds it is the caller's own credential rather than a decision timer: the dispatch ends with the lifetime of the caller token that authorized it, because executing past that point would be unauthorized ([Spec-022](./022-cross-node-dispatch-and-approval.md)).
