## Purpose

Define the approval model, permission scopes, and trust boundaries for execution in a session.

## Scope

This spec covers approval requests, approval scopes, the rules an approval hands to the providers, and the distinction between the session's permission level, its approval rules and the trust given per project.

## Non-Goals

- Identity-provider implementation details
- Transport protocol details
- Notification policy
- Organization-level policy that overrides the product's own rules. Approval runs on the product's default policy, enforced by the local daemon, with an explicit answer for each request.

## Required Behavior

- The system must distinguish:
  - the session's permission level, which decides whether anything asks at all
  - approval rules, kept by the providers, which answer an ask for one subject at the session's or the project's scope
  - trust, which is given per project and never per machine
- **Run-control interventions** — `steer` and `interrupt`, the intervention types of [Spec-003 §Interfaces And Contracts](./003-queue-steer-pause-resume.md#interfaces-and-contracts), and `faster_model_retry`, Codex's retry on a faster model ([Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior)), which is made of an interrupt and a resend of the same message, together with the orchestration-layer `run.pause` / `run.resume` mutations, which are governed identically — are authorized as the session's user, **never by run authorship**: the user may intervene on any run in the session, including a run an agent started on its own initiative and a run targeting an agent the user did not launch by hand. Within the intervention authorization path, run authorship is audit metadata and never an authorization input, as [ADR-011](../decisions/011-generic-intervention-dispatch.md) rules for every intervention. A run executes on the one machine that holds its session, and nothing dispatches a session's work to another machine, so every intervention reaches a run on that machine, whichever of the user's linked devices sent it. An accepted intervention records the device it came from — the machine's own screen or a linked device's channel — never a person. Every turn, whatever opened it — a message, a steer, the resend of an edit (a member of the person's own `session.restore` call, [Spec-003 §Interfaces And Contracts](./003-queue-steer-pause-resume.md#interfaces-and-contracts)) or the run's own continuation — adjudicates its sensitive actions against the session's permission level and its approval rules, with the one user as the Cedar principal.
- What asks is decided by the session's level, which is the provider's own asking mode underneath. Every ask a provider raises reaches the person's approval card, except the few the daemon answers itself in plain code: the refusal of `claude agents`, `claude daemon` and `claude --bg`; the allow of an agent's own memory-folder `.md` file at `readonly`, `ask` and `reviewed`; and Codex's answers where Codex has no command of its own (a subject the session allowed, after a restart; a host blocked for the session; exactly the command or file change a person edited and approved on the card). The daemon also raises its own card before a workflow's command step and full-tier Code step at those three levels. The app's own Cedar rules decide only the app's own tools: workflows, messaging other sessions and the browser.
- The canonical approval category enum is:
  - `tool_execution` — tool call approval
  - `file_write` — out-of-boundary file writes
  - `network_access` — unrestricted network
  - `destructive_git` — force push, branch delete
  - `plan_approval` — proposed plan review
  - `gate` — workflow gate
- Approval requests must record requester, target scope, and requested capability.
- Approval resolution must record the answering device, decision, and effective scope.
- A session runs on the machine it was started on for its whole life; nothing moves it, copies it to another machine or dispatches its work elsewhere. A linked device that opens the session answers and steers it on that machine, under the same permission level and the same rules as the machine's own screen.
- Trust is given per project, never per machine. Attaching a project trusts it for both providers, so their project-level agents, skills and hooks work there; a tool server joins a session's runs when it is switched on. Neither answers an ask: the session's level and its approval rules still decide every sensitive action.
- Driver-native permission flows must be normalized into the canonical approval model. A provider-initiated mid-run permission ask normalized this way, recorded once as an approval ([Spec-005 §Approval Flow (approval_flow)](./005-session-event-taxonomy-and-audit-log.md#approval-flow-approval_flow)), **waits until it is answered**. No deadline is stamped on it, no timer runs beside it, and nothing settles it on elapsed time: a countdown would turn a decision into a race and make the outcome a choice the product had taken on the user's behalf, and silence is never read as a grant. The wait is durable rather than bounded — the pending ask and the blocking state it puts the run into are persisted, rebuilt from the event log after a daemon restart, and still waiting afterwards. An ask raised by a provider-native subagent ([Spec-014 §Provider-Native Subagents](./014-multi-agent-orchestration.md#provider-native-subagents)) takes the same path: it surfaces on the session's approval and interactive surface and waits there like any other ask, never silently stalling its parent run. **Both providers hold their side of that wait without a ceiling**, measured 2026-09-21. Claude Code 2.1.278 held an unanswered `can_use_tool` permission request on its stream-json control channel for 900 seconds in one run and 1,500 seconds in another, sending no cancel frame either time; the answer was accepted at 904 and 1,504 seconds and the tool then ran. Codex 0.155.1 held an unanswered `item/commandExecution/requestApproval` for 1,503 seconds with no frame of any kind in between, then took the acceptance, resolved the request, ran the command and completed the turn. One neighboring provider surface does impose a ceiling, and it is not this one: an unanswered Claude Code hook callback is canceled by that command-line tool at 600 seconds unless the matcher registered for it carries a `timeout` of its own, and the canceled call is reported to the model as a tool that did not run — which is why the daemon sets that timeout itself wherever it holds a callback open ([Spec-003 §Required Behavior](./003-queue-steer-pause-resume.md#required-behavior)) rather than letting a person's decision expire.
- **A permission ask waits until it is answered, and no request a person answers carries a deadline.** A provider's permission ask is normalized into the approval pipeline and its run stays blocked on it. A structured question an agent asks mid-turn is not a permission ask — it is the one question record of [Spec-005 §An Agent's Question](./005-session-event-taxonomy-and-audit-log.md#an-agents-question), answered on the question card and never through the approval pipeline. No answer is ever fabricated and no silence is ever read as a grant, at any tier and any permission level. The pairing between a permission ask and the pipeline request minted for it is **persisted at creation** and is never client-suppliable: the normalizer-minted request records the originating `askId` (carried on `approval.requested` — `ApprovalFlowEventPayload.askId` in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md); the daemon's own `ApprovalRequestCreateRequest` deliberately carries no `askId` and its strict schema refuses a smuggled one, because a forged association could route another ask's outcome to the wrong native ask), and the association is persisted onto the `approval_requests` projection's `ask_id` column under a unique partial routing index — exactly one approval row per native ask, so a normalizer retry or a replay re-mint collides instead of duplicating — and it is rebuilt from the event at replay ([Local SQLite Schema §Approval Tables](../architecture/schemas/local-sqlite-schema.md#approval-tables-plan-009)). With several permission asks in flight on one run, and across a daemon restart or an event replay, the daemon therefore reconstructs exactly which native ask a pipeline outcome must answer; ask-to-approval routing is never inferred from timing or from a one-pending-ask assumption.

- **The approval surface is one card in the session's composer area.** An approval is raised there and nowhere else — never a modal, never a toast, never a free-standing transcript card, never a notification of its own — and exactly one is shown at a time: a queue of waiting approvals is worked one item at a time, the card carrying its place in that queue beside its eyebrow (`1 of 3`) while more than one waits and carrying no count at all while one does. The card pushes the conversation up rather than covering it. There is no countdown, no "approve all", no per-approval keyboard accelerator, and no cancel-the-turn action beside it. Amber on this surface means, and only means, that a person is needed.
- **The card says exactly what is being asked.** An eyebrow, a title and a summary line name the ask. One reason line under the summary carries the provider's own words for why this particular action stopped, with control characters and terminal escape sequences stripped before it is shown and the line absent rather than empty where the provider sent none. The subject of the ask is shown whole in a fixed-width block — the command for a command, the path for a read or a write, the text for an input — which wraps rather than cutting and, past a height derived from the card, scrolls inside itself while the card keeps its answers in reach.
- **Three answers in one fixed order — decline, always allow, allow once** — the last being the primary. The always-allow answer states its own scope in its label: the session, and the subject the daemon derived from the ask (a command's program and first subcommand, a network request's host, a written file's name), with the project offered as a second scope (§Default Behavior). Where the provider marks an ask as one that must not carry a standing allow, that middle answer is **absent rather than disabled** and nothing takes its place; the remaining two keep their order and the primary stays last.
- **An ask to send input to a command that is already running** reads `Send input to <the running command>`, naming the command as its row does, with `Terminal input in the <worktree> worktree` under it and the input whole in the fixed-width block, labeled `Terminal input`. It takes no standing allow, so the card draws `Decline` and `Approve once` alone: `Approve once` lets that one input through, and `Decline` refuses it, the agent is told so, and the command keeps running. Codex raises this ask before the agent types into a command it runs with extra permissions (its command ask with `kind: "writeStdin"`, whose `itemId` is that command's own item); there the input is not editable, because Codex takes no changed input back. The person's own typing into a terminal never raises this card.
- **A decline may carry a reason.** Choosing to decline opens one optional line on the card; whatever is typed there is delivered to the agent through the provider's own refusal field — on Codex, whose answer carries only the decision, the daemon answers `decline` and then sends the typed words into the same turn with `turn/steer` — and an empty line sends a bare decline. That line is the only thing the press adds, and the decline then resolves in place like any other answer.
- **The subject may be corrected before the ask is answered.** The command or path the card shows is editable in place, and the edited text is what goes back with the answer and what the audit record shows as having run. There is no raw form of the call on the card and no fourth answer. On Codex, whose answer takes no changed command or path, the daemon answers `decline`, sends `turn/steer` asking the agent to run the changed command or use the changed path instead, and answers Codex's ask for exactly that command or change `accept` itself.
- **Resolution is in place, with no banner.** An allow hides the card, un-waits the blocked call — whose elapsed clock resumes where it stood rather than restarting — and lets the run carry on, the result landing when it settles. A decline hides the card, the blocked call's row reads `Declined` where its result would sit, and the session leaves the group of sessions waiting on a person. An allow also marks the session's review data stale, because work the user has not seen may now have landed.
- **An approval raised by a child run is the parent's approval.** It is answered on the parent session's own card, through one approval pipeline and one trust boundary; a child's own view offers the same answers, by position in the same row of three, and mints no second answer surface. Walking from a child to the approval brings that card into view rather than drawing a second control beside the child.
- **Only the three most careful permission levels ask at all.** A session runs at one of five permission levels, most careful to least: `Read-only`, `Ask`, `Reviewed`, `Sandboxed`, `YOLO`. An approval card exists at the first three. At `Read-only` and `Ask` the person answers it. At `Reviewed` the provider's own reviewer answers every ask it sees, in the person's place, and the daemon never answers in the reviewer's place, so a card shows there only for an ask no reviewer answered: Claude Code's own fallback, after 3 blocks in a row or 20 in a session; a card already open when the level moved to `Reviewed`, which stays open for the person; a Codex ask raised in the turn the level moved in, since Codex takes a new level from its next turn; and an ask the daemon raises itself, such as a workflow's command step. At `Sandboxed` and `YOLO` the daemon answers every ask itself under the level's own posture — moving the level there answers an open card and lets its blocked row run, a later ask raises no card, and moving back to a level that asks asks again.
- **At `Reviewed`, a block by the provider's own reviewer can be allowed once.** When the reviewer — Claude Code's auto-mode classifier, Codex's `codex-auto-review` — blocks an action, the call keeps its row in the flow, a failed row whose reason line reads `Blocked · <the reviewer's reason>` in the provider's own words (Claude Code's denial reason, such as `[Data Exfiltration]`; Codex's review rationale), with one button beside it, `Allow once`. Pressing it tells the agent it may try that one action again, by the provider's own means: on Claude Code the daemon sends the sentence Claude Code's own Recently denied list sends, `Permission granted for: <the action>. You may now retry this command if you would like.`; on Codex it calls `thread/approveGuardianDeniedAction` with the denial Codex sent, and Codex's reviewer still reviews the retry. It reaches a running turn at once and starts a turn when none is running, with that sentence as its input; the sentence is the daemon's and is never drawn as the person's message. The row then reads `Allowed once` and the button goes; the agent decides whether to retry, and nothing runs by itself. A block the provider does not let a person overrule has no button: Claude Code's block without a classifier verdict, and Codex's review that timed out. The button stays until it is pressed or the session ends and holds across a restart, because the daemon keeps the provider's own denial with the block's record; a press on one screen settles it on every screen, and a press on a block already allowed is answered with the settled row. The daemon records the block as `approval.reviewer_denied` and the press, made through `approval.denialOverride {sessionId, denialId}`, as `approval.denial_overridden` ([Spec-005 §Approval Flow](./005-session-event-taxonomy-and-audit-log.md#approval-flow-approval_flow)); both drivers capture the block, Claude Code through its `PermissionDenied` hook and the result's `permission_denials`, Codex through `item/autoApprovalReview/completed` ([Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior)). A block raises no card and settles no approval request. When the reviewer blocks too often, each provider's own fallback runs and is forwarded: Codex interrupts the turn with its own warning, drawn as a `Review warning` row, and Claude Code, after 3 blocks in a row or 20 in a session, asks instead, through the ordinary approval card. Codex's other reviewer signals draw what Codex's own app draws: a `guardianWarning` is one `Review warning · <Codex's words>` row, none for a warning that reports an approval or is about an action the reviewer blocked; a wordless `strictReviewRequired` is `Review required · This request requires additional safety checks, some tool calls might take extra time`; `turn/moderationMetadata` draws nothing and stays in the daemon's log.
- **A question is not an ask, and the question card exists at every level.** An agent's mid-turn question ([Spec-005 §An Agent's Question](./005-session-event-taxonomy-and-audit-log.md#an-agents-question) `question.asked`) is raised at all five levels. On Claude Code the daemon declares the permission host at every level, since a headless session offers the question tool only while one is declared; at the four levels where the question arrives as a permission request the card is raised from that request, and at `Sandboxed`, where the provider refuses the question tool in-process and no allow or ask rule re-arms it, the daemon's session-registered `PreToolUse` hook on that tool carries the question out and the answer back, keyed by each question's text. The daemon's own tools at `Sandboxed` run through the same hook after the daemon's level check, never through a standing allow rule, which would run them with no check on the path. The hook's matcher is a regular expression, so one entry covers the daemon's whole tool server; the hook echoes the question whole, because a partial input is refused; it answers allow or deny only, since an ask falls to the level's own deny; and the provider's sandbox settings beside `dontAsk` change none of this — a shell command runs without a prompt, the operating system refuses a write outside the working folder, and an allow rule still runs a daemon-hosted tool.
- **The card carries no clock and never settles itself, and every linked device answers it.** The daemon holds the request open with no timer and rebuilds the card on reload and on every one of the user's linked devices that has the session open, with the same answers; an approval, a question and a plan card are each answered from any of them, and the first answer settles it everywhere. A device that was showing the card closes it and draws `Answered on <device>` in the card's place for as long as the session stays open there — faint, raising nothing that reads as an error, and adding nothing to the transcript; on the machine's own screen an answer from the machine reads `Answered on <machine>`. A second answer arriving a moment later is refused as already settled, and its device draws the same line. A device that cannot answer right now draws the card with its title, subject and summary and one line in place of its answers, which return when the reason clears: `<machine> is not reachable, so this can be answered once it is back.` while the machine is unreachable, and `This app is behind <machine>. Update it to answer here.` or `<machine> is behind this app. Update its background service to answer here.` while the two are outside each other's version range. No device is limited by grant: there is no per-device permission, no view-only device and no approval right, and a device that should not act is revoked ([Spec-027 §Required Behavior](./027-remote-control.md#required-behavior)). No device signs the events it sends: the channel's handshake proves the device, and the resolution event carries the answering device's id, taken from the connection the answer arrived on; the hold is the daemon's on both providers, so which device answered never reaches the provider. Four things close an open card and nothing else does: the person's answer; an interrupt of the run that raised it, which cancels the approval with the run and records the cancellation; a move of the session's permission level to one that never asks, where the daemon answers the open card itself under that level's posture and lets its blocked row run; and the provider process ending on its own, which takes the approval it was holding with it ([Spec-018 §Required Behavior](./018-observability-and-failure-recovery.md#required-behavior)). Elapsed time is not on that list — the card is exactly where it was left, however long that is.
- **A plan awaiting its verdict takes the same card in the same place.** Its eyebrow reads `Plan`, its title is the plan's first heading, and its summary counts the plan's top-level steps and the files it names and says that nothing has changed yet; it carries exactly three answers in one fixed order — keep planning, build in a fresh session, build it — and nothing else: no permission row, because the session's permission level already holds that choice and the card never asks it twice, no text box, because the composer is the text box, no provider name and no dialog. Keeping on planning hides the card and appends nothing, the next message being ordinary feedback in plan mode, and the card returns with new counts when a revised plan lands. Building appends one system message, restores the level's own posture, and lets the same session carry on with its history. Handing the plan to a fresh session appends a system message that leads to the new session and leaves the planning session's history intact. While the card is up, the session is one of those waiting on a person, exactly as one blocked on an approval is.
- **A denied lead agent is told why, in this product's own words.** The denial that keeps a lead away from a child run the user interrupted carries one fixed sentence as its reason and never anything the user typed: `The person paused this agent from the console. It will not take messages on any channel until they resume it. Do not retry another way; continue with what you can, or wait.` It is the same sentence on every provider and on every tool that could reach that interrupted child — Claude Code's `SendMessage`, and Codex's `collaborationspawn_agent`, `collaborationsend_message`, `collaborationfollowup_task` and `collaborationwait_agent` — because denying one such tool leaves the others open, so each of them carries it; and it is never drawn on screen, because it is a wire string the lead reads: a refusal with no reason reads to the lead as a broken harness, while a sentence naming who paused the child and why reads as the environment it is. The steer channel is untouched: on a held child the user's own typed words are still the denial reason, and the child still reads them as its instruction.
- **The daemon's own Codex hooks are passed at each service start and trusted before any conversation loads.** On Codex the daemon's hooks — the pre-tool hook, which reports a command, carries the pause, refuses a tool the conversation's agent lacks and holds a call a revoked provider rule would have allowed until the person answers, and the post-tool hook — are passed with `-c` when the Codex service starts, in each account home the app manages, and are never written into a file. Codex runs no untrusted hook, so at each service start, before any conversation starts, forks or resumes, the daemon reads `hooks/list` and records trust for exactly those hooks through Codex's `config/value/write`, and refreshes a record when its hook command changes; a trust write does not reach a conversation already loaded. A hook that times out fails open, so the pre-tool hook's `-c` entry carries an explicit `timeout` of a day, as on Claude Code, since Codex sets no ceiling on a hook's timeout, with `features.code_mode.default_exec_yield_time_ms` at the same hold so a code-mode model's cell stays open while its call is held; a hold ends only by an answer, allow or deny, never by the hook ending. A command the sandbox refuses before Codex sends its command item still gets its row, drawn from the hooks paired by call id; when a hook reports a call with no item by the end of the turn, the row reads `Blocked by the sandbox` with the command's last output line as its reason and no exit code, because the hook carries none. While Settings › Providers › Codex's `Reach Codex sessions started in a terminal` is on, the same hooks and the pause reach a Codex session the person typed in a terminal, through the one Codex service the daemon runs on the person's own Codex folder; there the daemon writes only its own hooks' trust records into that folder's `config.toml` and does not otherwise modify the person's Codex configuration.
- Each run carries an **execution posture**: `executionPosture { mode: 'readonly' | 'ask' | 'reviewed' | 'sandboxed' | 'yolo', writableRoots: string[], credentialPolicyRef: string }`. Its `mode` is the session's **permission level** — the same five words the level control offers, most careful to least, and the only posture vocabulary in the product. **How a level maps to the sandbox the driver applies.** The three most careful levels ask, and each is realized as the provider's own asking mode: `readonly` reads on its own and asks before any change (Claude Code's manual mode restricted to reads; Codex's Read Only), `ask` edits files on its own and asks before running a command (Claude Code's accept-edits; Codex's Ask for approval), and `reviewed` lets the provider's own reviewer approve routine work, block the rest and tell the agent why, and a block can be allowed once (Claude Code's auto mode; Codex's Approve for me). `reviewed` is offered on a Codex ChatGPT login as on any Codex session, and the app forwards whatever Codex does with it: Codex runs its own reviewer, `codex-auto-review`, on the person's plan, and if Codex refuses the level or asks for something the account lacks, the level stays where it was and Codex's own words land in the session as the refusal. A warning or a required review from that reviewer lands as one system message in Codex's words, `Review warning · <Codex's words>` or `Review required · This request requires additional safety checks, some tool calls might take extra time`, recorded as `moderation.review_flagged`; Claude Code sends none. The app never hides the level on a guess and never swaps in a reviewer of its own. The two least careful levels never ask, so an enforced boundary stands where the card would have: `sandboxed` runs the provider's own sandbox with writes confined to the worktree and the repository's git folder, whose `hooks` and `config` stay closed (Claude Code's don't-ask with its Bash sandbox on; on Codex a permission profile the daemon builds for the session's repository on top of workspace-write, with approvals off), and the person's own stdio tool servers run inside that same sandbox ([Spec-024 §A session's own tool servers](024-mcp-server-configuration-and-governance.md#a-sessions-own-tool-servers)), and `yolo` enforces no limit at all — commits, pushes and opening a pull request all run unasked (Claude Code's bypass permissions; Codex's Full Access). No level sends Codex `approval_policy = "untrusted"`, though the pinned Codex accepts it ([Codex wire reference §Breaking type changes from earlier builds](../reference/provider-wire/codex.md#breaking-type-changes-from-earlier-builds)); each level takes the Codex mode named above. The posture carries no network setting: on both providers the network is the person's own provider settings, and the daemon neither opens nor restricts it. The provider's own name for a mode never reaches a screen; it is a driver-realization detail this section records. The five levels are one list in the contracts, `readonly`, `ask`, `reviewed`, `sandboxed`, `yolo`. An agent definition carries no level and no cap of its own: the lead and every helper at any depth, on either provider and across the agent bridge, run at the session's level, and what an agent can do at all is its tool allowlist. A level the bound session, account and model cannot actually run is not offered at all. A session made from another, by `Fork` or by `Build in a fresh session` on either provider, starts at its source session's level. The five levels map to both providers; the only gaps are an account's or a platform's — `Reviewed` on a Claude Code account whose plan lacks auto mode, read from each model's `supportsAutoMode` in Claude Code's `initialize` reply on that account and never from a list of plan names, `Sandboxed` on Claude Code on native Windows — and where the other provider cannot give a fresh session's source level, nothing is blocked and nothing is lowered on its own: in the `Fresh session with` list that provider's row carries the line `<Level> isn't available on this <Provider> account` (or, where the gap is the platform's, `<Level> isn't available on <Provider> on Windows`), and picking it opens the level list in place with that provider's levels, the nearest more careful one marked; the person picks a level and the fresh session starts at it. A running session is the one case that moves on its own: when its provider's current account changes to one that cannot run its level — `Reviewed` on a Claude Code account whose plan lacks auto mode — it moves with the rest and runs at `Ask`, the nearest more careful level; one row of the app's own reads `Reviewed isn't available on this Claude Code account`, stored as the `session.notice` kind `level_unavailable`, the level chip opens the level list as always, and nothing is blocked ([Spec-025 §Moving a session to another account](025-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)). Every other new session starts at `YOLO`. An agent's own memory folder is the one exception at every level: the agent reads and writes it without asking on both providers, and at `readonly`, `ask` and `reviewed` the daemon answers an agent's ask for a `.md` file in that folder `allow` itself, with no card and no rule. `credentialPolicyRef` is a plain reference naming the daemon's curated credential deny list the run was handed: its `denyPaths`, which the daemon expands to canonical absolute paths when it resolves the policy (tilde and environment references expanded, symlinks resolved, platform case and relative components normalized), never raw config strings like `~/.ssh`, and its `denyEnvVars`, which the spawn-environment strip matches under the host's own environment-name case rules, so a curated secret cannot survive under an alternate spelling. The typed wire mirror carries the reference beside the posture it belongs to. `writableRoots` holds absolute paths; the daemon canonicalizes each root (symlink-resolved real path; relative paths rejected) before the posture enters Cedar evaluation, so policy always compares canonical paths, never raw input. The posture is a **Cedar authorization input**, not merely a spawn-time knob: the run's effective posture rides the context of every Cedar decision about the app's own tools, inside the same principal-action-resource-context evaluation as every approval category. **Cross-field invariants (fail closed)**: the daemon validates the posture object before it enters Cedar evaluation or spawn — `mode: 'readonly'` requires `writableRoots: []`, because that level asks before any change; `mode: 'yolo'` (no OS-sandbox enforcement) MUST be **supplied** as `writableRoots: []` — the canonical form denoting no OS-enforced constraint, so no posture record implies a constraint nothing enforces; any other combination under `mode: 'yolo'` is a violating combination and is **rejected** like every other cross-field violation — the daemon never rewrites a restrictive request into the permissive canonical form — and `writableRoots` is meaningful only on the four levels below `yolo`: under `mode: 'yolo'` the canonical `[]` denotes _no OS-enforced write constraint_ (unconstrained), the opposite of the same value under `readonly` (nothing writable), so `writableRoots` is always read together with `mode`, never in isolation. `credentialPolicyRef` does not vary with the level: the curated credential policy is handed to the provider in the provider's own form on every run, and what enforces it is the provider's own rule, never a second mechanism of the daemon's. The curated set is not the only boundary that holds: **the deny rules the person has already set in that provider's own configuration**, global and project, go on holding inside this product because the provider enforces them itself, and the daemon never copies them into its own set. The daemon reads them, applying the provider's own precedence where the same subject appears in both, only to show every protected path with its source — the daemon's own credential set, the person's global provider configuration, or that project's — on the Providers page, so nothing is refused invisibly. The reference names the daemon's own set, however the person's own rules read. On the Claude leg the curated paths are permission-rule denies, which Claude Code applies in every permission mode, bypass permissions included ([Claude Code permission modes docs](https://code.claude.com/docs/en/permission-modes), fetched 2026-09-21), so they hold on all five levels; the provider's own caveat holds with them — a deny rule covers Claude Code's file tools and the file commands it recognizes in the shell, and not a subprocess that opens a file itself, which only the `sandboxed` level's OS sandbox closes. On the Codex leg the curated paths are filesystem denies in the permission profile, which the platform sandbox enforces ([Codex permissions docs](https://developers.openai.com/codex/permissions), fetched 2026-09-21), so they hold on the four levels below `yolo`; `yolo` is Codex's Full Access, which runs no sandbox, so under it no path is denied, exactly as Codex behaves outside this product. The curated variables are stripped from the spawn environment on every level on both legs. The reference therefore records what the daemon handed over, read together with the provider and `mode`, never in isolation. A violating combination is **rejected** — the run is refused, never silently normalized into a permissive state — so implementations cannot diverge on whether an ambiguous posture is invalid, deny-all, or permissive.
- The **effective posture is recorded on the run's `run.running` event** — the post-setup-gate spawn-success transition: Plan-002's gate seam admits `queued → starting`, then setup gates (Plan-007's execution-root gate among them) run **before** `driver.startRun`, so the resolved workspace root and shared-`.git` allowance are final only when `running` fires — a `run.starting` stamp would be premature or wrong. The `executionPosture?` carrier field registers with [Spec-005 §Run Lifecycle](./005-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle)'s run-state payload — the typed wire mirror rides `RunStateChangeEvent.executionPosture?` in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), `credentialPolicyRef` among its members — so the record carries the **complete effective posture object**, never a named-fields subset — `credentialPolicyRef` on every posture-bearing row — and compaction, which is lossless, keeps it whole.
- Driver-native sandbox and permission flows are normalized into this canonical posture, with the realization recorded per driver:
  - **Codex leg** — `native`: built-in permission profiles (`:read-only`, `:workspace`, `:danger-full-access`) plus named `[permissions.<name>]` profiles resolved via `default_permissions` ([Codex permissions docs](https://developers.openai.com/codex/permissions), fetched 2026-07-02), passed as the thread's `permissions` at `thread/start` (app-server schema, regenerated at the pin the provider-wire reference `docs/reference/provider-wire/codex.md` records). **Legacy settings**: per the same permissions docs, legacy `sandbox_mode` / `sandbox_workspace_write` config keys (or a `--sandbox` flag) shadow `default_permissions`, so the driver never passes `--sandbox` and overrides those legacy keys in every config layer it controls when realizing a posture. Named profiles resolve through Codex's normal config-layer model (a higher-precedence layer can add or replace entries in a same-named `[permissions.<name>]` profile — same permissions docs), so the daemon writes its generated profile at the highest-precedence layer it controls under a daemon-unique profile name; what the person's own config layers add passes through as Codex applies it, and no run is refused over them. Built-in profile aliases are realized exactly: the built-in `:workspace` profile also allows writes to **system temp directories** beyond the workspace roots (same permissions docs), so the daemon-generated profile either suppresses the temp allowance where the config surface can express that, or the recorded posture's `writableRoots` MUST include the effective temp roots — and at `sandboxed` the profile is one the daemon builds for the session's repository, a per-repository permission profile: the worktree and the repository's git folder are writable (for a linked worktree, its common git folder, named by its absolute path), while that folder's `hooks` and `config`, and a worktree's `.git` pointer, stay read-only, so an agent's commit lands without asking and no agent can plant a hook or repoint `core.hooksPath`. At `readonly`, `ask` and `reviewed` the built-in protection keeps `.git/` under each workspace root read-only, recursively, and where `<workspace-root>/.git` is a **pointer file** the resolved external gitdir it names is protected too; at every level below `yolo`, `.codex/` and `.agents/` under each workspace root stay read-only ([Codex agent-approvals docs](https://developers.openai.com/codex/agent-approvals-security), fetched 2026-07-05). The recorded roots carry these exclusions as **normative semantics** exactly like the Claude shared-`.git` leg: Codex holds its own file-change tool to the same profile: a patch to a path the level's profile keeps read-only — at `sandboxed` the git folder's `hooks/**` and `config` and the worktree's `.git` pointer, and at every level below `yolo` `<workspace-root>/.codex/**` and `<workspace-root>/.agents/**` — raises `item/fileChange/requestApproval`, which reaches the person's card at `readonly` and `ask`, Codex's own reviewer at `reviewed`, and is refused at `sandboxed`, where approvals are off; posture realization verifies the generated profile preserves every read-only rule — the audit record always equals the enforced boundary, never a subset of it. Once any permission profile is defined, `default_permissions` is set too, or the app-server exits at start. The stamp binds **every turn, not one spawn moment**: `turn/start` accepts optional per-turn overrides for posture-affecting fields — `cwd`, the **legacy** `sandboxPolicy`, the **preferred** `permissions` profile-selection, and `approvalPolicy` — each carried as an optional field that persists for the turn ([app-server docs](https://developers.openai.com/codex/app-server), fetched 2026-07-03; the field inventory is pinned in the provider-wire reference `docs/reference/provider-wire/codex.md`). The daemon therefore derives **every** posture-affecting turn field from the stamped posture and refuses any turn carrying a posture-affecting field it did not itself so derive: a turn whose `cwd`, `sandboxPolicy`, `permissions`, `approvalPolicy`, `approvalsReviewer`, or any field the app-server later adds to this posture-affecting class diverges from the posture-derived value is **refused**, never silently started wider than the `run.running` record (a level move reaches a loaded conversation through `thread/settings/update` from its next turn, never as a turn override). **The posture rides the `permissions` profile, never `sandbox`.** At the levels below `yolo` the daemon starts every thread with `permissions: <that level's deny profile>` — extending `:read-only` or `:workspace` for the built-in levels, and the per-repository profile at `sandboxed` — and never with `sandbox` or a per-turn `sandboxPolicy`, because a thread started with `sandbox: "workspace-write"` ignores the profile's denies even when `default_permissions` names the profile (measured). The daemon reads `activePermissionProfile` on the thread's reply, never its `sandbox` field, which hides the read-only folders, and a thread whose reply names no profile is refused as a start fault. The daemon's `initialize` carries the `experimentalApi` capability, which a default connection lacks (a default connection refuses `permissions` by name, `-32600 turn/start.permissions requires experimentalApi capability`, measured at `codex-cli 0.149.1`). The posture is set at `thread/start`. The only per-turn `permissions` the daemon sends are ones it derives itself: `:read-only` on a Codex plan turn, and the level's own profile on the first turn after `Build it` (the plan-mode bullet in §Interfaces And Contracts); a per-turn `sandboxPolicy`, or a `permissions` the daemon did not derive, is refused rather than forwarded. The daemon never sends `sandboxPolicy`, because it wipes the named profile: `activePermissionProfile` reads back `null` and the level's read-only folders drop (measured at Codex 0.156.0), and since 0.156.0 sending the two together is refused with `-32600`. The removed `permissionProfile` field is not an option either (it refuses `-32602` on both connection kinds). [Spec-004 §Required Behavior](004-provider-driver-contract-and-capabilities.md#required-behavior) owns the driver-boundary half. This closes by principle rather than by field enumeration, and it binds `approvalsReviewer` — which `turn/start` also accepts as an optional per-turn override (`TurnStartParams`, provider-wire reference `docs/reference/provider-wire/codex.md`): the driver sets it from the level — Codex's own automatic reviewer at `reviewed`, which is what that level means, and `"user"` at every other level — and the daemon refuses any turn supplying a reviewer the level did not derive, so no turn reroutes adjudication away from what the level says. `approvalPolicy` (which actions require approval) and `approvalsReviewer` (who adjudicates) are distinct posture-affecting fields, each derived and verified in its own right. The Claude leg has no symmetric per-turn escape: its sandbox and permission posture are applied at process launch through the daemon-controlled settings surface (the isolated `--settings` payload realized per the Claude-leg description below) and the sandboxing docs define no `turn/start`-equivalent per-turn override, so there is no per-turn widening surface to verify there. And because Codex permission profiles govern **sandboxed local commands** while MCP / app-connector / browser / computer-use surfaces ride separate controls (same permissions docs), each of those rides Codex's own control at the session's level: the file-change tool is held to the profile as above; every tool server the session reaches is fronted on the daemon's tool route, where Codex's per-tool approval is applied from the session's level and the server's `tools.<t>.approval_mode`, so a call asks where Codex would and the ask reaches the person's card, while the daemon's own `sidekicks` entry carries `default_tools_approval_mode = "approve"` and its tools take their Cedar actions; the agent's Tool allowlist switches Codex's built-in tools per conversation (`features.shell_tool`, `web_search`); and any surface the daemon cannot bind this way is disabled for the run **before** the posture is stamped — the recorded posture covers the whole tool boundary, not only sandboxed commands. As on the Claude leg, the daemon adds no network rule of its own: the network is the person's own Codex settings. The stamped `credentialPolicyRef` binds on this leg too, not only on Claude's: `denyEnvVars` are enforced by the provider-neutral daemon spawn-env strip (the daemon owns the spawn environment for every provider process) with Codex `shell_environment_policy` (`inherit: "none"` + explicit `set`) as the native defense-in-depth layer beneath it; `denyPaths` map into the daemon-generated permission profile's filesystem deny rules (the permissions surface governs local-command filesystem access — same permissions docs) with the resolved profile verified to carry every curated deny — the provider's own denies are the whole path binding, and the daemon builds no check beside them — and on the four levels below `yolo` a posture whose resolved Codex configuration cannot express a curated deny is refused rather than run; under `yolo` Codex runs Full Access with no profile, and no path deny applies.
  - **Claude leg** — `native-partial` (Bash-tool-scoped): the OS-level Bash-tool sandbox (macOS Seatbelt / Linux bubblewrap) is settings-driven and headless-enforceable ([Claude Code sandboxing docs](https://code.claude.com/docs/en/sandboxing), fetched 2026-07-02; `sandbox.credentials` requires ≥ 2.1.187). A sandboxed realization sets `sandbox.enabled` and `failIfUnavailable: true` (fail-closed if the sandbox cannot initialize), and leaves `allowUnsandboxedCommands` to the person's own setting; `filesystem.allowWrite` maps to `writableRoots`. The daemon writes no `network.allowedDomains` into Claude Code's settings: the network is open only as far as the person's own Claude Code settings allow — their own domain allowlist — and a host the sandbox prompts for reaches the person as Claude Code's own ask. **On every level, sandboxed or not, the daemon supplies the curated default credential deny-list** `credentialPolicyRef` records (for example `~/.ssh`, `~/.aws`): `sandbox.credentials` ships **no** built-in denies, and because `sandbox.credentials` binds **sandboxed Bash commands only** (same sandboxing docs), the same curated paths are passed as Claude Code permission `Read` deny rules, which Claude Code applies to its own file-reading tools in every mode, bypass permissions included, and the daemon builds no check beside them; and secret environment variables are bound by the layer the daemon owns outright: the daemon **strips every curated secret env var from the provider-process spawn environment itself**, with `sandbox.credentials` env unsets (sandboxed Bash only — same sandboxing docs) as defense-in-depth beneath it, and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` never set, because it forces the permission mode to `default` — spawn-env removal is what binds arbitrary curated names (for example `GITHUB_TOKEN` / `NPM_TOKEN`) for daemon-hosted MCP and every other non-Bash subprocess — so no posture is recorded with a credential boundary its non-Bash tools do not enforce. The Bash sandbox runs at `sandboxed` alone: the three asking levels are Claude Code's asking modes with the sandbox off, so at `readonly` a command that would change anything runs only once the person allows it, and `writableRoots: []` records that nothing writes unasked. At `sandboxed` the sandbox docs give Bash commands **default** write access to the current working directory and the session temp directory (with `filesystem.allowWrite` only _adding_ paths), which the recorded `writableRoots` carry. Linked git worktrees get the same audit treatment: when the working directory is a linked worktree the sandbox additionally allows writes to the main repository's shared `.git` directory (`hooks/` and `config` stay denied — same sandboxing docs), and because the daemon executes worktree-first ([ADR-006](../decisions/006-worktree-first-execution-mode.md)) this allowance is live on essentially every `sandboxed` run, so there the recorded `writableRoots` MUST include that shared `.git` directory, whose entry carries the vendor-fixed exclusions as **normative semantics of the recorded root** — `hooks/` and `config` inside it are denied for every write path, so the permission-rule scoping for non-Bash tools MUST apply the same exclusions (an `Edit` deny on `<shared-.git>/hooks/**` and `<shared-.git>/config` among the protected-path denies the session's flag settings carry, which Claude Code applies to every file-editing tool in every mode), keeping record-plus-semantics exactly equal to the enforced boundary on Bash and non-Bash paths alike. A sandboxed realization additionally pins `excludedCommands: []` in the daemon-controlled settings payload and launches against the daemon's isolated `--settings` surface. `--settings` merges with file-based scopes, and array-valued settings such as `excludedCommands` and `filesystem.allowWrite` **concatenate** across scopes ([Claude Code settings docs](https://code.claude.com/docs/en/settings), fetched 2026-07-02), so what the person's own user, project or managed layers add passes through as Claude Code applies it, and no run is refused over them. Non-Bash tools (Read / Edit / MCP) ride the permission system rather than the OS sandbox, so per-tool coverage is legible from the posture semantics themselves — the mechanism split (OS sandbox for Bash; permission system for non-Bash) is a property of the posture contract, graded in the Spec-004 capability matrix, never a per-run stamp — and a `mode` label never implies uniform OS enforcement where the Claude leg is Bash-scoped — and precisely because of that split, **the Claude leg MUST bind the non-Bash write surface on every level** through the permission system: under `readonly` Claude Code's manual mode asks before every file-mutation tool (Edit/Write-class) and every tool-server tool the person's own rules do not allow, and each ask reaches the person's card; under a workspace-writing level file-mutation tool invocations are permission-scoped to `writableRoots`. The **non-Bash network surface** — WebFetch-class and network-capable MCP tools — is left, like the Bash network, to the person's own Claude Code settings: the daemon adds no network deny of its own. The one place the daemon carries those settings itself is a person's own stdio tool server at `sandboxed`, which runs under the hosts Claude Code would allow and deny, through the sandbox library's proxy in the daemon ([Spec-024 §A session's own tool servers](024-mcp-server-configuration-and-governance.md#a-sessions-own-tool-servers)). The recorded `mode` binds every path the daemon's own rules reach, Bash and non-Bash alike; the person's own `permissions` in Claude Code's user, project and project-local settings files are not checked against the posture and apply as Claude Code applies them.
- Two boundary facts the posture semantics encode:
  - In-session subagents run in the parent process and **inherit the parent's OS sandbox configuration**, so the sandbox floor covers a run's subagents automatically — no subagent sandbox-escape at the OS layer ([sandboxing docs §Scope](https://code.claude.com/docs/en/sandboxing), fetched 2026-07-02). The **non-sandbox** permission surface is not inherited by default, however: an agent in the `agents` map of Claude Code's `initialize` request carries its own `permissionMode`, `tools`, and `mcpServers` ([Agent SDK permissions docs](https://code.claude.com/docs/en/agent-sdk/permissions), fetched 2026-07-05 — per-subagent override is force-suppressed only when the parent runs `bypassPermissions` / `acceptEdits` / `auto`), so absent binding a subagent could be launched with broader non-Bash Edit / MCP / network access than the stamped posture allows. The daemon therefore **derives every hosted subagent definition from the run's posture** — the `initialize` agents map is daemon-controlled, exactly like the `--settings` surface — carrying no `permissionMode` in any entry, so every helper runs at the session's level, and bounding each subagent's `tools` / `mcpServers` to what its agent's Tool allowlist grants, so a helper holds no tool its definition does not, and every call it makes is answered under the session's own mode and permission rules exactly as the parent's are; any subagent definition the daemon cannot so bound is **disabled for the run before the posture is stamped**, so the recorded posture covers subagents at the permission layer, not only the sandbox layer.
  - The Claude sandbox is **unavailable on native Windows** (WSL2 only, per the same sandboxing docs) — and a host that cannot fully realize a sandboxed posture (native-Windows Claude leg, missing Linux sandbox dependencies, any partially-realizable knob) **refuses the run**: a sandboxed level is stamped only when fully realized, never stamped degraded, so one `sandboxed` record always means the same enforced boundary on every host — which is also why `Sandboxed` is absent from the level control on a host that cannot realize it, rather than offered and quietly weakened. Per-knob realization _vocabulary_ (`native` / `native-partial` / emulated) lives in the Spec-004 capability matrix, not on the run stamp ([ADR-018](../decisions/018-windows-v1-tier-and-pty-sidecar.md)-adjacent).
- Inside a session the app runs, an agent's `claude agents`, `claude daemon` and `claude --bg` are refused by the daemon's own plain-code answer to the provider's ask, and Claude Code's own switch that turns them off stays pinned: `disableAgentView: true` in the daemon's controlled settings, equivalently `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` in the spawn environment ([Claude Code settings docs](https://code.claude.com/docs/en/settings), fetched 2026-07-02), which also turns off `/background` and the on-demand supervisor, set for every effective posture. Such work would run outside the session's agent tree, outside `Stop` and `Interrupt`, and off the session's receipt. Claude Code used in the person's own terminal is untouched.
- **Callback-tool authorization.** Every daemon-registered session callback tool — the daemon-hosted tool registry exposed into a run, whose shape is defined in [Spec-004](./004-provider-driver-contract-and-capabilities.md) — is one of the app's own tools, so the app's own Cedar rules decide it, and its invocations land as `tool_activity` records; no callback tool bypasses the approval pipeline.

## Default Behavior

- Default grant scope is `request_only`.
- A new session starts at `YOLO` — Claude Code's `bypassPermissions`, Codex's Full Access: no approvals and no sandbox — whatever the last session was left on and whatever Claude Code's own default mode is. The permission level is never remembered from one session to the next, and the person picks another level for that session from the level control.
- Approval rules are off by default and need the person's own act: a rule exists only where the person pressed the answer that hands one to the provider.
- **An approval rule is an allow or a block, never allow alone.** An allow comes from an approved decision, on the always-allow answer's own press. A block comes from a declined **network** ask alone, whose decline offers `Block <host> this session` with the project on the same second scope; a later request to that host is then refused with no card at all, and its row reads `Declined` where the result would sit. A command's decline and a file's decline keep their single press and make no rule. A block and an allow over the same subject cannot both stand — making one replaces the other — and the answer's label always says which is in force. `ApprovalResolve` rejects any other rule request with a typed error; deny-by-default remains the policy engine's job.
- **The providers keep the card's rules; the daemon keeps no rule store.** A rule holds at every level that asks, whatever level it was made at, because the provider answers by it, and each rule is one provider's. Its scope is the session or the project — the session from the answer's own face, the project from its second scope. The session's own answers, which its record already holds, are what the daemon lists and carries across a restart of the provider's process.
  - **Claude Code, session:** the session's allow and deny lists are the flag settings of its process, set by `apply_flag_settings {permissions}` as the card is answered, each call carrying the whole allow and deny lists — the card's session rules, the memory-folder allows the daemon passes at `Sandboxed` and the protected-path denies — and carried at launch by `--settings`; a grant, a revoke and a host block (a `WebFetch(domain:<host>)` deny, which the sandbox honors) each apply from the next call (measured on Claude Code 2.1.286).
  - **Claude Code, project:** an allow's answer carries the rule with `destination: "localSettings"`, so Claude Code writes it to the project's `.claude/settings.local.json`; a decline drops any rule it carries, so the daemon writes a project block's `WebFetch(domain:<host>)` deny into that file itself; a rule added to or removed from that file applies from the next call.
  - **Codex, session:** an allow is `acceptForSession`. Codex has no list, no revoke and no session block, so the daemon's own tool hook holds the next call on a subject taken back and raises its card again; the daemon declines Codex's later asks for a host blocked for the session; and after a restart it answers `acceptForSession` itself on a subject the session allowed. The hook runs before Codex's own approval for commands, file edits and tool-server calls (read from Codex 0.159.2's source); the unit that builds it measures that a held call on a subject Codex already allowed is refused when the person declines.
  - **Codex, project:** the daemon writes the rule as a `prefix_rule`, or a host's as a `network_rule`, into the project's `.codex/rules/sidekicks.rules`, which Codex reads, network rules included, in conversations started after it (an attached project is trusted), and answers the ask `acceptForSession` so the current conversation does not ask again. When it writes that file it adds that one path to the repository's `.git/info/exclude`, which git never commits, so the rule stays on this machine as Claude Code's `.claude/settings.local.json` does; the person's tracked `.gitignore` is never touched.
  - **A card the daemon raises itself**, not on a provider's ask (a workflow's command step), offers `Always allow <subject> this session` and no `Always in this project`: that rule is kept with the session's own answers in its record, honored by the daemon itself, and listed with the session's rules in the inspector.
- File and tool permissions default to the session's own working folder — its worktree or the project's checkout — under the session's permission level; access outside it requires an explicit approval or an approval rule.
- Network access goes as far as the person's own provider settings allow — off on Codex unless their own profile sets `network.enabled = true`, and the person's own domain allowlist on Claude Code. The daemon adds no network list or preset of its own, and a host a provider asks for reaches the person's card; at `sandboxed` a person's own stdio tool server reaches the hosts the person's own settings give, through a proxy in the daemon, and a host outside them is refused with no card, since nothing asks at that level ([Spec-024 §A session's own tool servers](024-mcp-server-configuration-and-governance.md#a-sessions-own-tool-servers)).
- An attached project is trusted for both providers from the moment it is attached, and a switched-on tool server joins a session's runs. Neither waives an ask: sensitive escalation still needs the level's own consent, an approval rule or a person's answer.

## Fallback Behavior

- If a driver cannot expose granular permission requests, the daemon must enforce an equal or stricter approval boundary at the local execution layer.
- If approval state cannot be durably persisted, the sensitive action must not proceed.
- A rule ends on `Revoke`; a session rule also ends with its session, which is the provider's own session; and a rule over a tool server's tool is removed from the provider's file that holds it when that server is removed. A project's rules live in the project's own folder and stay with it. A session rule's revoke applies from the next call on both providers, so the next ask on that subject raises its card again: Claude Code drops it from the session's flag settings, and on Codex the daemon's hook holds the next call on that subject. A project rule's revoke removes it from the provider's file and applies as that provider follows its own files: `Applies from the next tool call.` under Claude Code, `Applies to conversations started after this.` under Codex.
- If an input the decision needs — the machine's owning user or the session's working-folder roots — cannot be resolved, the daemon treats the sensitive action as needing a per-request approval rather than assuming it is inside the boundary.

## Interfaces And Contracts

- `ApprovalRequestCreate` must include category, scope, and requested resource. It carries no deadline: a request a person answers waits until it is answered. The daemon raises it itself, from a provider's callback — Claude Code's permission request, Codex's approval request, a daemon-hosted tool's invocation — and no screen calls it, so it is an in-process call with no registered method and its schema is the daemon's own.
- `ApprovalResolve` must include decision, an optional rule request, and audit metadata. The Cedar `principal` for authorization is the machine's owning user, the one user the daemon serves. The resolution record carries the answering device's id, taken from the connection the answer arrived on — the machine's own screen or a linked device's channel — never from the request body. It also carries the decline's optional reason line, delivered to the agent through Claude Code's refusal field, or on Codex by `turn/steer` after the decline; the subject as the person corrected it on the card, which is what runs and what the audit record shows; and a client resolution id that the resulting approval event echoes, so a device can tell its own answer from another's: the device whose answer settled it draws no line, and every other device showing the card draws `Answered on <device>`. The first answer settles the request; a later one is refused as already settled (`approval.already_resolved`). The resolution event carries the answering device's id.
- `PermissionCheck` must run inside the local daemon before executing a sensitive local action.
- `ApprovalProjectionRead` must surface pending and historical approval state to the session's authorized surfaces. The composer's card reads the session's pending requests through it and shows them one at a time, held open with no timer; the daemon's own `askId` never reaches a client.
- The rules in force on a session have their own read and their own revocation on the same namespace. `approval.ruleList` lists them, the session's own and its project's alike, read from where the providers keep them — Claude Code's `list_permission_rules`, Codex's project rule files and the session's own answers — each with its sense (allow or block), its subject and its scope; `approval.ruleRevoke` revokes one, removing it where the provider keeps it. `ApprovalResolve` carries the rule's scope — `session` or `project` — with its sense and the daemon-derived subject, together with the decision: the sense agrees with the decision, a block is accepted only on a network ask, and the daemon re-derives the subject and refuses an echoed subject that differs. Every standing rule on the machine, in every account home and attached project, is read and revoked on Settings › Providers through `provider.standingRuleList` and `provider.standingRuleRevoke` ([Spec-025](./025-provider-accounts-and-credential-homes.md)), from the same files. A resolution, a rule's creation and its revocation are each recorded on the approval-flow events [Spec-005 §Approval Flow](./005-session-event-taxonomy-and-audit-log.md#approval-flow-approval_flow) registers, so a reload and every other linked device rebuild the same pending card from the log rather than from client memory.
- **Plan mode, the plan record, and the plan verdict.** Plan mode is the composer's `Build` / `Plan` mode, set by `session.modeUpdate {sessionId, mode: 'build' | 'plan'}` and realized per turn on the bound driver: Claude Code's `plan` permission mode, and on Codex the plan-mode field on the plan turn's `turn/start` together with the `:read-only` permissions profile on that same `turn/start`, because that provider's plan mode changes the prompt and locks nothing. `sandboxPolicy` is never sent, because it wipes the named profile. The profile persists on the thread and across a restart, so the first turn after `Build it` names the level's own profile on its `turn/start`, and the daemon reads the profile back from `activePermissionProfile` on `thread/start`, `thread/resume` and `thread/settings/updated`. While a plan turn runs, the daemon declines every approval request Codex raises for an escalated command or a patch, because the plan turn is read-only whatever the level. Plan is a mode, never a permission level, and under it the level still governs what the plan may read. What the provider then holds open — Claude Code's held plan-exit request, or Codex's completed plan item — becomes **one** plan record, `plan.proposed`, whose text is taken from that request or that item and never read off the disk. The record is answered by one call, `plan.resolve`, carrying a verdict of `keep`, `build` or `fresh`: `keep` returns the provider to planning with nothing appended, `build` restores the level's own posture and lets the same session build, and `fresh` carries the provider of the session to be minted, which runs on that provider's default account at the level the verdict names — the planning session's, or the one the person picked where that provider cannot give it — and returns that session's identifier; a level that provider, its account or the model cannot run is refused with `session.permission_level_unavailable`, naming the level, and no session is minted. A second answer reads back the record's state rather than failing. The `plan.*` events join the approval-flow events: `plan.proposed` records the plan, and `plan.accepted` and `plan.handed_off` record the outcome, so both acts survive a reload. A proposed plan is an approval-pipeline decision in the `plan_approval` category and an attention entry exactly as an approval is: the request is held open until a verdict arrives, is never answered on a timer, is rebuilt on reload and on every linked device, and the first verdict settles it everywhere.
- **The session callback tools that reach a workflow are authorized by named Cedar action, never by tool name.** The read tools — kinds, list, read, runs, run read, step read and validate — are gated on the session itself. Authoring a workflow, updating one, setting its schedule, enabling or disabling it, and posting a run's results back into a chat all take `Action::"workflow::author"`. Running a workflow or executing one of its nodes takes `Action::"workflow::start"`; canceling a run takes `Action::"workflow::cancel"`; resuming one takes `Action::"workflow::resume"` ([Spec-015 §Chat-Invoked Start and Start Authorization](./015-workflow-authoring-and-execution.md#chat-invoked-start-and-start-authorization) owns the tools themselves). Each of them registers the way every other daemon-hosted callback tool does — a JSON-schema input, an approval category, and an activity record on every invocation — and each stays withheld from a run until its approval seam is registered. No callback tool takes the session it acts on as an argument: the daemon derives it from the connection the invocation arrives on and validates it there, so a forged session cannot be reached.
- **The permission level's own call.** The level control sets the session's level with `session.permissionLevelUpdate {sessionId, level: 'readonly' | 'ask' | 'reviewed' | 'sandboxed' | 'yolo'}`, returning the level now in force; the same level again is a no-op, a level the session's provider, account or model cannot run is refused with `session.permission_level_unavailable`, naming the level, and a move to a level that never asks answers the open card as §Required Behavior says.
- **`Allow once`'s own call.** `Allow once` on a block by the provider's own reviewer at `reviewed` is `approval.denialOverride {sessionId, denialId}`, returning the settled override `{sessionId, denialId, overriddenAt}`; a press on a block already allowed is answered with the same settled override and sends the provider nothing, and a press on a block the provider does not let a person overrule, or whose session has ended, is refused.
- `approval.requestCreate`, `approval.resolve`, `approval.projectionRead`, `approval.ruleList`, `approval.ruleRevoke`, `approval.denialOverride`, `plan.resolve` and `session.permissionLevelUpdate` are built by [Plan-009](../plans/009-approvals-permissions-and-trust-boundaries.md), and `session.modeUpdate` by [Plan-003](../plans/003-provider-driver-contract-and-capabilities.md); every one but `approval.requestCreate` is a registered method the app calls on the daemon. `approval.requestCreate` is the daemon's own in-process call: it has no registered method and no client method, and its schema is the daemon's.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- Approval requests and resolutions must be durable and replayable.
- Approval rules require explicit revocation paths and audit history.
- The daemon stores no rule: a session's rules are its provider's session state, carried by the session's own answers, and a project's rules are the provider's own files in the project's folder.

## Example Flows

- `Example: An agent at Ask asks to write a file outside the session's worktree. The user presses Approve once, the write runs, and the decision is recorded with the exact path; no rule is kept, so the next write outside the worktree asks again.`
- `Example: A session at Ask edits files in its worktree without asking, then an agent asks to reach api.example.com. The user opens Decline's arrow and takes Block api.example.com this session; the ask is declined, and every later request to that host in the session is refused by the daemon with no card, its row reading Declined, until the rule is revoked in the inspector's rules section.`

## Implementation Notes

- Approval UX may present grouped requests, but canonical approval records must remain granular enough for audit.
- Rule scopes are explicit enums (`session`, `project`), not free-form client labels.
- Trust changes must propagate into approval evaluation immediately.
- Policy evaluation uses Cedar (CNCF sandbox), run in-process by `@cedar-policy/cedar-wasm`; the built-in rules are `.cedar` files in the service's own source, compiled into the service with it and changed only by an app update ([ADR-012](../decisions/012-cedar-approval-policy-engine.md)). The rules decide only the app's own tools — workflows, messaging other sessions and the browser; a provider's own ask gets one of the designed plain-code answers or the person's card, never a Cedar decision. Cedar's principal-action-resource-context model maps to: principal = user, action = the approval category for decisions that traverse the approval pipeline, or a named operation action for authorizations that do not (`Action::"intervene"` on the target `Run` for run control per [Spec-003 §Interfaces And Contracts](./003-queue-steer-pause-resume.md#interfaces-and-contracts); `Action::"workflow::start"` on the target workflow for an agent's start and each run a trigger fires per [Spec-015 §Start authorization (SA-37)](./015-workflow-authoring-and-execution.md#start-authorization-sa-37), whose principal is the one user, resolved by the daemon — the schema registration is owned here, the adjudication call-site by Plan-014; and `Action::"workflow::cancel"` and `Action::"workflow::resume"` on the target workflow **run** per [Spec-015 §Run control (SA-43)](./015-workflow-authoring-and-execution.md#run-control-sa-43), likewise registered here with their adjudication call-sites at Plan-014 T5.22; and `Action::"workflow::author"` on the target workflow for the write half of the callback-tool surface — authoring, updating, schedule-setting, enabling and disabling, and posting a run's results into a chat (§Interfaces And Contracts) — four separate workflow actions rather than one, because authoring changes what a workflow will do, start creates work, cancel destroys it, and resume commits further spend against a provider account), resource = target (file, tool, network, run, project, tool server, etc.), context = session state, with the trust of the project and of the tool server an action touches. Arming a trigger is judged under `workflow::author`, and each run a trigger fires is judged under `workflow::start` when it fires, with the person recorded as its starter. The person's own edits on the app's screens — agent definitions, tool-server settings — pass no policy check. **Running** a saved agent from inside a session is no named action at all: a call on the cross-provider bridge is an ordinary tool call, so it is adjudicated through the approval pipeline under the existing `tool_execution` category at the session's own permission level — the asking levels raise the same card any tool call raises, an approval rule can answer it, and the levels that never ask never ask for this either.

## Pitfalls To Avoid

- Treating session access as equivalent to local execution trust
- Making an approval rule with no revocation path
- Allowing provider-specific permission semantics to leak into canonical docs

## Acceptance Criteria

- [ ] Sensitive local actions require explicit approval or prior valid grant.
- [ ] Every sensitive action is decided by the session's permission level, an approval rule or a person's answer, never by which of the user's devices the session was opened on, and the session's work runs only on the machine it was started on.
- [ ] Approval records survive replay and clearly show which device answered and what scope it granted.

## Open Questions

- Two measurements are open and neither blocks v1. The provider-hold evidence in §Required Behavior runs to about twenty-five minutes on each provider; a hold of several hours has not been measured on either. Nor has a hold that spans a provider process restart — what either provider does with a request it was holding when its process is replaced is unknown. Neither changes what this section requires: silence is never a grant, and the daemon holds the card and rebuilds it from the event log, so a provider that dropped a held request could at worst produce an answer it then refuses, never an action taken without one.
