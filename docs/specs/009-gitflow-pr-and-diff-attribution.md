## Purpose

Define the branch, PR, and diff-attribution behavior for repo-bound coding runs.

## Scope

This spec covers the branch context a project session works against, the diff the daemon reads for it and how that diff is attributed per file and per turn, how an agent's commits are attributed through a git trailer, and the review surface that reads a diff and ships it: how a diff is read, the comparisons it offers, the ship actions of commit, push, pull and open a request, the text Generate writes for them, the review notes and verdicts it carries to the hosting service, and the hosting sites it reaches, GitHub and GitLab, each through its own installed, signed-in command-line tool.

## Non-Goals

- A review workflow of the console's own: the surface carries the hosting service's threads and verdicts and invents no review state beside them
- Git hosting vendor-specific features
- Merge automation policy

## Required Behavior

- Every run in a project session executes against an explicit branch context, in whichever of the session's two places it works: a worktree of its own (`provisioned-worktree`) or the project's checkout (`bound-root`) ([Spec-008 §Required Behavior](./008-worktree-lifecycle-and-execution-modes.md#required-behavior)).
- The git engine tracks the base branch, the head branch and the worktree association of each project session's working folder.
- Attribution is per file and per turn in the diff, and per commit in the history, never per line. The diff read names, for each file, the newest turn that changed it, read from the session's file checkpoint store ([Spec-013](./013-persistence-and-recovery.md)); a file changed outside any turn carries no turn rather than a guessed one. A commit names the agent that made it only from its own `Agent-Run` trailer; a commit without one is the person's.
- An agent's commit carries `Agent-Run: <run-id>`, the authoritative attribution, written by the daemon's own git hook and never by the provider. On git 2.54 or later the hook is set in configuration through `GIT_CONFIG_COUNT`; on older git it is a `core.hooksPath` folder that forwards every hook name to the repository's own hooks — the repository's `core.hooksPath` first, else `.git/hooks` — so the person's own hooks still run. The hook adds the trailer with `git interpret-trailers --if-exists addIfDifferent` and reads the run from a per-session marker in the provider's environment: set at spawn on Claude Code, and through the conversation's `shell_environment_policy.set` on Codex, where `CODEX_THREAD_ID` also names the thread. The person's own commits and the session terminal therefore never get the trailer, and a commit made with `git -c core.hooksPath=…` carries none and reads as the person's.
- `Agent-Run` is the only trailer the daemon writes: it adds no co-author trailer, invents no identity and impersonates no one. A co-author trailer carrying a provider's address appears only where that provider itself writes or documents one. Claude Code writes its own co-author trailer by default, and a Claude agent's commit keeps it. Codex sends the model its own co-author instruction only when the person's commit-attribution setting in their OpenAI account is on — off by default, and always off when Codex signs in with an API key — so a Codex agent's commit carries `Agent-Run`, and Codex's own trailer only with that setting on. This spec describes any such address in words and never spells one.
- The daemon notices an agent's own commit and push without reading the agent's calls. It keeps one watch per git folder — the tree's own git folder and the shared refs area, each found with `git rev-parse --git-path` — as change signals only, then asks git; it never reads ref files (under reftable there are none), and every background read passes `--no-optional-locks`. A commit's run comes from its `Agent-Run` trailer, never from whichever run was live when HEAD moved. A push is read from the remote-tracking reflog's `update by push` entry and settles with cause `pushed`, carrying no run, because the record names the act and not the actor; a fetch changes only the ahead and behind figures. A finished `gh pr create` or `glab mr create` tool call re-reads the pull request.
- A pull request's base and head come from the recorded branch context, never from the currently selected client tab. The pull-request form opens with the values the ship-facts read supplies — the base, the proposed title and description, and whether the request carries its own push — and there is no separate preparation step, record or wire verb.
- A commit, push, pull or pull-request act the user takes states exactly what it will run before it runs: `Commit` and `Open pull request` open a form carrying the values the act will use, `Push` and `Pull` act on the press with no form, and the exact commands — built by the same daemon code that runs the act, so the two cannot drift — sit under an `Exact commands` fold beneath the confirming control, never in a modal, ticking off in place as each one finishes. While a run is live in the session, `Commit`, `Push`, `Open pull request` and `Pull` each wait with the reason in its own hover title, `Wait for the run to finish`, and answer again once the run ends. An agent's own commit, push and pull-request calls are ordinary tool calls governed by the session's approval policy ([Spec-010 §Required Behavior](./010-approvals-permissions-and-trust-boundaries.md#required-behavior)); git is never gated a second time and no proposal block is drawn for it.
- **The review surface is one pane, never a route.** Review is the diff pane with a ship strip and a pull-request tab composed on top: never a modal, never a route, never a second kind of pane. It opens wide enough to read a diff's two halves side by side, never narrows past the point one half still reads at, resizes from its own edge and can take the whole column, and its sub-line names the two ends of the comparison, the file count and the totals, `<head> → <base> · N files · +A −D`. It renders what the daemon reports, computes no git state of its own, and paints the syntax spans the daemon hands it rather than coloring anything itself. In its chrome, the header carries the file-list fold, the split-view toggle, the reload, the control that moves the pane into its own window, the full-width toggle and the close, with the commit picker following the sub-line on the branch and pull-request comparisons, and the scope row carries the comparisons below — `Changes` with its file count, `Branch` with its commit count, and `Pull request` with `#<n>` — plus the `Notes` tab, with the held count, while any note is held — no word-wrap toggle, no whitespace toggle, no separate checks panel.
- **Review never opens on a chat session.** A chat keeps files rather than changes: its review control is drawn at every moment and inert at every moment with the reason in its own tooltip, the chord that opens Review does nothing there however many files the chat has written, and what it wrote is read in the file pane instead. Converting the chat into a project session, which copies its files into the project's repository ([Spec-007 §Required Behavior](./007-repo-attachment-and-workspace-binding.md#required-behavior)), is what makes Review able to open on it, on the copied files as new changes.
- **Three comparisons, one at a time.** The uncommitted work with its file count; the branch's commits against the recorded base with their count; and the pull request, carrying its number, or reading `No pull request yet` and answering no press. Where the branch carries more than one request the tab reads `PRs` with the count — `PRs · 2` for two — and lists them, the newest open one standing first. Each comparison's empty line names the comparison it answered rather than the pane — `No uncommitted changes`, `No changes against <base>`, `No pull request yet` — and a comparison still loading says so in that same place without blanking what is already drawn.
- **The base is read, never checked out.** The base picker draws the one ordered branch list the daemon supplies ([Spec-008 §Interfaces And Contracts](./008-worktree-lifecycle-and-execution-modes.md#interfaces-and-contracts)) and refuses nothing, because a diff base is read and never checked out. Typed text narrows the list, the arrow keys move through what is left, Enter takes the selection and relabels the control, Escape closes the menu with the base where it was, nothing matching draws one inert line, `No matching branches`, while keeping what was typed, and a list longer than the menu can hold draws what fits and says how many of how many it is showing, `Showing <N> of <M> branches`. The picker opens on the project's default branch and never on the branch being compared: where the default IS that branch it opens on `main` or `master` if either is in the list, and otherwise on the first branch in the list that is not the current one. A base the user picked stands for as long as that branch is still in the list.
- **Every comparison reads as a file list beside a diff, and the commit picker narrows the branch and pull-request comparisons to one commit.** The branch comparison's body is the file list and the diff over the commits this session is responsible for against the recorded base, and the pull-request comparison's carries the same over the request's commits beside the request's own content; both follow the uncommitted comparison's fold, filter, width and divider rules (§The Diff Read). On those two comparisons the pane header carries a commit picker reading `All commits`, whose list holds `All commits` and then one row per commit of the comparison: the short identifier, the subject, when the commit landed, written in the machine's own clock ([Spec-021 §Meridian, the design language](021-desktop-app-and-renderer.md#meridian-the-design-language)), and the maker's mark — where an agent made the commit that agent's swatch and name, or the robot mark for the session's own agent, and nothing where the user made it. The short identifier is git's own abbreviation (`git rev-parse --short`), never a fixed count; pressing it copies the full identifier and it reads `Copied` for a moment before going back to the identifier, or `Could not copy` in the same place for the same moment when the copy fails. The identifier in the flow's `Committed · …` system message copies the same way. The identifier and the rest of the row are two controls side by side, never one inside the other, each reached on its own by the keyboard: pressing the identifier copies and narrows nothing, and picking the rest of the row narrows both the file list and the diff, with their counts, to that one commit, exactly one at a time, the picker then closing and reading that commit's short identifier and subject, and the row reading pressed when the picker opens again; `All commits` restores the full range and clears the pressed row, and switching comparison or reloading restores it too. There is no author column and no date column, because one person's name on every row says nothing, and the console draws no repository history at all — no lane graph, no column chooser, no branch-tips overview, no fold of a branch's run of commits, no paging row, no commit search. Repository history is read in the session's own terminal or on the hosting service's own pages.
- **The pull-request comparison reads the request, and never guesses at it.** Its header carries the state beside the two facts the hosting read supplies — whether the request can merge or its branches conflict, `can merge` or `conflicts`, and its review decision in plain words, `changes requested`, `approved` or `review required` — each absent rather than guessed while the service has not settled it, and neither of them a control. Reviewers are listed one to a row under the heading `Reviews` with each latest verdict in plain words, those who have been asked but have not answered standing under `Review requested`, and with no verdict at all the heading is absent and the comparison reads `No review yet`. Beside that request content the comparison draws the file list and the diff of the request's commits, which the commit picker narrows as on the branch comparison. The description is a card folded under the header whenever the comparison opens, showing its first line beside the word `Description`, opening and folding again on a press, and drawn not at all where the request has no description. The request's number is the door to its page on the hosting service: a press opens that address in the system browser, the way any address outside this machine opens, and it is drawn only while the daemon has supplied the address.
- **Attribution in the review surface is per file and per turn, never per line.** Each file row shows the turn that changed it as a short word beside its counts, `turn <n>`, reading the newest turn that touched that file, while the row's hover title stays the file path; a commit row carries the mark and name of the agent that made it. No gutter carries per-line authorship and no file row takes a color bar for who changed it; a commit's agent is read from its `Agent-Run` trailer, not from the pane's chrome.
- **A review note is a draft the daemon holds.** Notes are held by the daemon and scoped to the session, so a half-written review reaches the user's other devices; typed unsent text is never put in window storage. A held note is a card under its line carrying the file and line it points at, a one-line quote of that line, its own words, and an edit and a delete drawn plainly and at all times rather than on hover; it carries no reply and no resolve. Each note records the comparison it was written on — the scope, the base, the head commit or the working file's blob id, and the request's number where there is one — with the side, the line and the first line of a range, so pressing it walks to the comparison that holds it. A note left on the removed side of a rename cites the old path, so its line number still means something. A note whose line no longer exists in the diff is marked stranded and kept — still readable, editable and deletable — and is left out of any review posted to the hosting service; a note on uncommitted lines is left out of a post the same way, since the hosting service has no such line.
- **A held note leaves in exactly three ways.** Composed into the draft as a steer: one message opening with `Address these review notes:`, each note located by its file and line, focus moved to the draft, the notes cleared, and nothing sent — the message stays an ordinary user turn, since it already names every file and line the notes touched. Posted as one pull-request review under exactly one verdict. Or discarded. While any note is held it is one chip in the composer's attachment row reading `1 note` or `<N> notes`, drawn beside any attached file rather than in place of it; pressing it opens the review surface on its `Notes` tab, which carries the count and lists each note by its file and line with the send control beneath, offering `Steer the sidekick` or `Post to PR review` with the verdicts `Comment`, `Approve` and `Request changes`, and each entry there takes the reader to that line in the diff. The chip's own dismissal, the same `×` a file chip carries, discards the notes behind one question asked in place on the chip, `Discard <N> notes?` with `Cancel` and `Discard`. The count clears on those three things and on nothing else, so it can never stand for notes that are gone.
- **A post that partly failed says what did not go.** The send strip names the file and line of the note that failed and why, the notes that did post are marked sent and are never offered again, and the notes behind the failure stay held; a second press posts only what is still held.
- **The ship strip is read off the state, never remembered.** One sentence above the buttons says where the branch stands and what happens next — `<n> commits ahead of <base> · <n> files uncommitted`, `Pushed · no pull request` — and it is present in every state, including the one that offers no action. One next action follows from the state: uncommitted work commits, an unpushed branch pushes, a pushed branch with no request opens one, and otherwise none is offered. One alternate stands beside it, and for as long as the branch is behind its base that alternate is a pull, in place of whatever the state would otherwise have offered there; it goes the moment the branch is level, and it never displaces the next action, so a behind branch with uncommitted files still offers the commit first. The commit action is absent for as long as a merge, a rebase or a bisect is half-finished, and the state line names which one is open and the exact command that ends it — `A rebase is in progress — run git rebase --continue in the terminal.` — that pending operation being the daemon's fact like every other.
- **Committing takes the whole working folder.** There is no staging surface: nothing selects files, hunks or lines, the commit form says how many changed files it will sweep in, `Commits all <N> changed files`, and the fold beneath the button shows the add that sweeps them before the commit runs. Splitting a commit is done in the session's own terminal. The commit form's subject label carries a live count of its characters against 72, the figure alone turning amber past it; it is a reading and never a limit — the field takes a subject of any length, the confirming control stays live, and nothing is refused, truncated or rewritten — and no other field carries one.
- **Generate is a fresh one-turn process.** Generate on the commit form writes the subject and body, and on the pull-request form the title and description, from the whole working folder's diff, the branch name and the recent commit subjects. It runs in a fresh one-turn process on the session's own provider and account that carries no conversation, on the model with the lowest input rate in the price table among those the provider lists for the account and does not hide, the lowest output rate breaking a tie; a model the price table does not price has no rate and is never the one chosen. It runs at the lowest effort with thinking off, read-only, in a folder outside the repository. A failure reads in the provider's own words and never falls back to the other provider; what it writes is editable, and pressing again rewrites it.
- **Pushing and opening a request.** A pull-request action carries its own push only when the branch has never left this machine; nothing else is folded in. Opening a request takes the base branch, whether it is a draft, its reviewers and its labels. The strip offers no amend and no force push — rewriting pushed history is done in the session's own terminal, and the strip re-reads the state when it is — and no merge: merge is out of scope, and the pane says so in the hosting service's own vocabulary rather than hiding the gap, `Merge from <hosting service> when checks are green.` Stacked requests and restore-from-review do not exist. A push and a pull each act on press with no form, each command under the same fold, and a pull runs under the user's own git identity; it acts on the branch this session is on, in the folder in front of the reader, and a tree elsewhere that has fallen behind is reached by moving to it. The behind figure the strip reads is the daemon's background fetch's, never a fetch of its own.
- **Every act leaves a record where the session can see it.** A commit, a push, a pull, an opened request and a posted review each append one system message to the session's own flow naming the act and never the actor — `Committed · <short id> · <subject>`, `Pushed`, `Pulled`, `PR #12 opened`, `PR #12 approved`, `Changes requested on PR #12`, and `Commented on PR #12` for a review that is comments only — and their outcomes are recorded by one settlement event, `git.settled`, so those messages survive a reload. Every push leaves the machine under the user's own hosting-tool identity whether the user pressed or an agent ran it, and an agent's commit carries the `Agent-Run` trailer, so the history says who wrote it outside the console too. A result that arrives after the form it came from has closed, or after the surface was pointed at another session, updates nothing on screen — the act still happened and its message still stands. Each act asks the daemon for a fresh read the moment it finishes rather than waiting on the next watch tick, so the next action offered is true the instant the act lands, and a read that comes back for a session the surface has since left is dropped.
- **Nothing is swapped out from under the reader.** Tree staleness is a signal the daemon emits from watching the working folder ([Spec-008 §Interfaces And Contracts](./008-worktree-lifecycle-and-execution-modes.md#interfaces-and-contracts)) — the pane never infers it, and where the working folder is too large for the machine to watch the daemon checks it on a slow tick instead, which the reload button's hover title says, `Checked every few minutes on this repo`, so a mark slow to arrive is never read as a tree that never changed — and it shows as a reload mark titled `Tree changed — reload`; a pull request that has gained commits past the head the pane loaded raises the same mark titled `Pull request moved on — reload`, held against that request so switching requests never raises it falsely. The diff is re-read only when the reader presses reload. A reload puts the line that was at the top of the pane back at the top of the pane however much the content above it grew or shrank, redraws only the files whose content actually changed, and changes nothing at all when the result is identical. A rebuild the reader caused — folding a file, opening a note — moves nothing.
- **The pull-request tab re-reads itself, and only itself.** While it is the comparison in view it re-reads the request's state and its threads on a cadence — often enough to be current, less often once the request is settled — so the state and the thread counts change under the reader as the hosting service reports them. The patch is never re-read or swapped with them.
- **Threads and checks.** A posted note is a hosting thread sitting at the line it is about, taking that thread's own `Reply` and `Resolve` and `Send to the sidekick`, which sends it to the agent; resolving it flips its state and drops the unresolved count. An unresolved thread stands open with its replies and its actions, and a resolved or outdated one folds to a single line at its anchor naming who left it, its state and how many replies it holds. Pressing a thread takes the reader to its line: the comparison that holds it, the file unfolded, the thread opened and the line brought into view and flashed; a thread with no line in the diff opens at its own card instead. The pull-request tab has no time-ordered feed — threads under the `Conversation` heading with the unresolved count, commits in the commit picker, verdicts in the review rows, and nothing gathering the three into a stream — and the only free-standing body the surface offers is the summary that goes with a review verdict. A failing check opens its raw log at its end, because the useful part of a build log is the last of it, drawing only the lines on screen however long it is and saying above them how much was left out, `Showing the last part of a <size> log`; the log carries exactly two controls, `Send failure to the sidekick`, which sends the failure to the agent, and `Open in browser`, which opens that check's own page on the hosting service in the system browser, and there is no save-to-file.
- **The surface never resolves a conflict.** It never draws a conflicted file, takes no side over another, edits nothing in place and marks nothing resolved: a half-finished merge or rebase is named on the state line with the command that ends it, and the conflicted file itself is read in the editor or in the session's own terminal.

## Default Behavior

- The default pull-request base is the session's recorded base branch, in either place the session works.
- Where the branch carries more than one request, the newest open one stands first, in the header's request word and in the pull-request comparison.

## Fallback Behavior

- Where the daemon cannot say which turn changed a file, the file carries no turn; where a commit has no `Agent-Run` trailer, it carries no agent. Nothing is attributed by guess.
- Where no installed, signed-in hosting tool answers for the repository's host, the diff, the commit, the push and the pull still work and the pull-request half of the surface stays dark; where the daemon cannot say which service it is, the pull-request wording stands.
- A read the review surface depends on that fails in a way that can be retried is retried once, after a fixed 100 ms in the daemon, git's own lock-retry window, before anything reaches the screen; no figure on screen depends on that pause. A failure that survives the retry is named in one line at the top of the pane saying which read it was — `Could not read the branch list` — with `Try again` at its right, and the diff already drawn stays exactly where it is until the new content is ready; the line goes when the read succeeds.
- A git read that failed is never rendered as an absent fact. The state line says which read it was and offers the try-again, and the strip's action buttons stay absent until the facts are back, because a button drawn on a fact the daemon does not have is the one thing the strip must never do.
- A command a strip action runs that fails is marked as failed in the fold that showed it, keeps a try-again that runs it again from where it stopped, and lands its cause as a row in the session's flow either way, so the record survives the pane.
- A pull-request read that fails backs off — the wait growing from seconds towards minutes until one succeeds — and the last state that was read stays on screen through every failure, so the tab never blanks.
- With no diff to draw the surface has four answers: a clean tree reads `nothing to review`; a pane whose subject is gone closes itself and says so in one line; a read slow enough to be waited on reads `Reading changes…` where the diff would be, so a fast read never flickers; and a failed read reads `Could not read the working folder`, with `Try again` beside it.
- A file the surface cannot draw says why as text in the body where the file would have been, in the console's own words and naming the cause — `binary — contents not shown`, `Permission denied`, `Not a regular file` — with the file's header above it unchanged, so its path, its counts and its open-in-editor control still work. A reason may be repeated in a tooltip but is never only in one.
- A failure while drawing the diff shows one short line in the body, `Could not show this change`, in place of whatever was there, and never replaces a diff that is already readable.
- While a run is live every control that would reach the agent waits, with the reason in its own hover title: Review's three send controls — the notes tab's send, a thread's `Send to the sidekick` and the check log's `Send failure to the sidekick` — read `Send from the chat box while the sidekick is working`, and the strip's acts read `Wait for the run to finish`.

## Interfaces And Contracts

- Clients reach this spec's surface under the `gitflow.*` wire namespace: its verbs, each keyed by the session (`{sessionId}`) except a running act's progress, keyed by the act, and the host verbs, which belong to the machine; the daemon maps each session to its working folder. Their refusals are the codes `packages/contracts/src/gitflow/` registers with them, each with its reason list ([error-contracts.md §Gitflow](../architecture/contracts/error-contracts.md#gitflow)).
  - `gitflow.branchContextRead` — the ship facts: the head, the recorded base, the default branch, the upstream, the uncommitted file count, how far ahead of and behind the base the branch is, the unpushed commits, whether the branch has never left this machine, a half-finished merge, rebase or bisect with the command that ends it, the branch's requests (number, address, state, whether it can merge, review decision; the newest open one first), the hosting service's name and its request word — pull request or merge request — and everything the pull-request form opens with: its proposed base, title and description, and whether it carries its own push. It is re-read after every act, on `git.settled` and on the tree-staleness signal. A failed read names which read failed, after one retry inside the daemon.
  - `gitflow.diffRead {sessionId, scope, base?, commitId?, changeRequestNumber?}` — one comparison's diff (`changes`, `branch` or `change_request`) as [§The Diff Read](#the-diff-read) fixes it, with the commits of the branch and pull-request scopes, which a `commitId` narrows to one: each commit's short identifier, subject, time landed, and the agent that made it where one did. A `workflowRun` arm diffs two of a workflow run's snapshot points, read from the run's own capture folder with the repository's objects as an alternate, and serves the run view: this list and diff with no scope row, base picker, notes or ship strip, each file marked with the step that changed it, the mark reading the step's name alone in the list and in the file's diff header, its accessible name `Changed by the <step name> step`, per file and never per line, reading `Loading the changes…` until the diff has been read, `Could not load the changes` with `Try again` where the read fails, and `This run changed no files` when nothing changed.
  - `gitflow.gitActionPreview {sessionId, act, formValues}` → `{commands}` — the exact commands an act will run, before the press, built by the same daemon code that runs the act.
  - `gitflow.gitActionExecute` — the person's acts: commit (subject and body), push, pull, and open a request (base, title, description, draft, reviewers, labels). A `retryFromCommand` field runs a failed act again from the command that failed. It returns the act's id and its commands and records `git.settled`; a command that fails is a failed step in the act's progress, not an error reply.
  - `gitflow.gitActionSubscribe {actId}` — a running act's progress, catching up and then following: each command pending, running, done or failed, with its output scrubbed of credentials.
  - `gitflow.commitMessageGenerate` → `{subject, body}` and `gitflow.changeRequestTextGenerate` → `{title, description}` — Generate's reads; a failure is refused with the provider's own words.
  - `gitflow.changeRequestSubscribe {sessionId, depth: summary | full}` — the live read of the branch's requests. `summary` carries the state, whether it can merge and the review decision, and feeds the header's request word; `full` adds each reviewer's latest verdict, the reviewers asked who have not answered, the description, the address, the author and whether the signed-in identity authored it, the threads with their anchors, states and replies, the checks, and the head commit, for the pull-request comparison. Each frame carries when it was read and when a read last failed; a failed read is a frame field, never an error.
  - `gitflow.reviewerList` and `gitflow.labelList` — the reviewers and labels the pull-request form offers.
  - `gitflow.reviewSubmit {sessionId, changeRequestNumber, verdict, body?}` — posts the held notes as one review under one verdict (comment, approve or request changes) with its optional summary, and answers with the notes posted and each note that failed with its reason; a second press posts only what is still held. It reads the notes from the daemon's store and never takes note text off the wire.
  - `gitflow.threadResolve` and `gitflow.threadReply` — resolve a hosting thread, and reply in one. Resolving a thread already resolved succeeds.
  - `gitflow.checkLogRead` — a failing check's log: its tail, whether it was cut and how much it holds, and the address of the check's own page on the hosting service.
  - `gitflow.hostList`, `gitflow.hostAdd {host}` and `gitflow.hostRemove` — the self-hosted hosts ([§Hosting Sites](#hosting-sites)).
- `repo.*` reads serve the review surface beside them: `repo.branchList`, the one ordered branch list ([Spec-008 §Interfaces And Contracts](./008-worktree-lifecycle-and-execution-modes.md#interfaces-and-contracts)), and `repo.fileRead`, which reads a working-tree file that is not in the diff and the lines inside a collapsed gap. A gap read takes `{path, blobId, side}`. A committed side is read with `git cat-file blob`, exact and never stale. A working-tree side is read from disk only while `git hash-object` (without `-w`) still matches its blob id, and otherwise answers `stale`, which the surface shows as the reload mark. A pull request's head is fetched locally before its lines are read.
- Held review notes are `session.*` verbs over the daemon's session-scoped store beside the session's composer draft, the store that carries them to the user's other devices: `session.reviewNoteAdd` (the client mints the note's id, so the same id makes one note; the note records its comparison `{scope, base, headCommitId | workingTreeBlobId, requestNumber?}` with its `side`, `line` and `startLine?`), `session.reviewNoteUpdate` (a posted note is refused, since it is a hosting thread now), `session.reviewNoteRemove {noteIds}` (an array, so the chip's discard and a steer each clear every note in one act), and `session.reviewNoteList`, live, each note carrying `stranded` recomputed against its comparison.
- One settlement event, `git.settled`, records the acts that left this machine, so their system messages survive a reload. Its causes are `committed`, `pushed`, `pulled` (`{branch, commitId}`), `pull_request_opened` and `review_posted` (`{requestNumber, verdict}`), and each cause carries exactly the reference its message names: the commit's identifier, the branch, the pulled branch and commit, the request's number with its address on the hosting service, and the reviewed request's number with the verdict. The run is present only when an agent's own tool call made a commit; a push carries none. A `review_posted` whose verdict is comment-only reads `Commented on PR #12`. The session event taxonomy registers the type and its payload ([Spec-005](./005-session-event-taxonomy-and-audit-log.md)); no preparation or submission event stands beside it.
- The hosting service is reached through the daemon's internal `GitHostingAdapter` ([§Git Hosting Adapter](#git-hosting-adapter)), never through a wire method of its own.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- The recorded base, head and worktree association live in the session's branch context, which [Spec-008](./008-worktree-lifecycle-and-execution-modes.md) owns. Every other ship and pull-request fact is read live from git and the hosting service and never stored: the daemon keeps one watch and one in-memory cache per working folder, shared by every session working there, and answers each session's ship-facts read from its folder's cache.
- The diff is a read, re-read on the reader's press, and keeps no record of its own; its per-file turn comes from the session's file checkpoint store.
- The durable record of each act is its `git.settled` event in the session's log.
- Held review notes are rows in the daemon's session-scoped store, in the one local schema, and never in window storage.
- The registered self-hosted hosts, each with the kind of the tool that answered for it, are kept by the daemon.

## The Diff Read

The review surface's diff is a read the daemon answers each time it is asked (`gitflow.diffRead`), retried once inside the daemon and re-read on the reader's press. It mints no artifact and writes no row.

What a diff carries, per file, is the daemon's answer and never the client's inference:

- One word for what happened — `added`, `deleted`, `renamed`, mode changed — carried on the file's row and on its header, a rename's header reading `renamed from <old path>` while its row reads `renamed`, never by color alone, and said once rather than repeated as a separate notice row above the file's changes. A file git reports as a copy reads added: the source stays where it was and the copy is a new path, so no other word is drawn for it. A file that was only edited carries no word.
- That file's own added and removed counts, and the newest turn that touched it.
- A file the agent edited more than once in one turn reaches the surface as ONE file: the daemon composes the edits into a single patch with true line numbers and one pair of counts, and the surface draws one row and one body for that path.
- A changed binary file is marked binary, and the surface writes that its contents are not shown where its lines would be; the file keeps its row, its header and its word, and counts that are zero because there are no lines are left off rather than drawn as zeros. Pressing a changed picture's row opens the quick look with the old picture beside the new one, each at its natural size inside the column and labeled `before` and `after` under it; a picture with no earlier version opens alone.
- A diff reaches the surface whole: the daemon never cuts a patch at a size.
- Every untracked file the repository does not ignore appears in the uncommitted comparison as a new file, its lines as additions and its counts in the totals, read from the repository's status without ever touching the index.
- A rename carries the path the file had before, so a note anchored on the removed side still means something.
- Each file carries git's blob id for each side, taken from `git diff --full-index`, which gives the working file's hash as the right-hand id; the gap read and a note's comparison name a side by it.
- Where a file is unreadable the file carries the cause — permission denied, not a regular file — and keeps its row and header. Size is never a cause.

How a diff is read is fixed by this spec, so every surface reading one reads it the same way:

- Every file folds to its header, and a folded file keeps its whole header — the path, its counts, and its open-in-editor and copy-path controls — so it still says what changed and still opens. The fold control is the chevron each file header starts with, a real button whose accessible name reads `Fold <path>` while the file is open and `Unfold <path>` while it is folded; it tells assistive technology whether the file is open, and Enter and Space press it as a pointer does. Each file's header stays pinned at the top of the diff column while its body scrolls under it.
- There is no capped body and no row limit: a file is either folded to its header or shown whole, its rows built only as they scroll into view however long it is, and a folded file contributes no rows at all. Files that are noise start folded — lockfiles, generated files, and any file longer than the surface can show at once — and a fold or unfold by hand stands over that from then on. There is no second control that lifts a shortened body, because no body is shortened.
- One toggle folds every file: it sits in the scope row immediately to the left of the base picker, a glyph with a tooltip and no word on it, and it reads as pressed only while every file in the loaded diff is folded, re-reading itself when a single file is folded or unfolded by hand. Which files are folded is remembered per session and per file on this device and laid back over the diff whenever the surface opens on that session again — after a reload, after closing and reopening the surface, and after a session switch; a file no longer in the diff drops out of that memory, and the fold-all toggle re-reads itself from what came back.
- A collapsed gap between two changes opens a step at a time in the direction asked for, one screenful per press, with only the arrow the file's shape allows; a gap one step covers has no arrows and opens whole on a single press, and each press leaves the reading position where it was. The patch's technical range line is never drawn: the gap expander stands where one would, saying in words how many unchanged lines are hidden.
- Split view pairs runs of removed and added lines into one grid row so the halves cannot drift, and the left half carries no gutter and no notes, so a note has exactly one home. Where a removed line is paired with its added line the part that actually changed carries a stronger wash of the row's own color, snapped out to whole words; the pair is left plainly washed when the two lines are the same, when either is very long, or when most of the line changed, so a rewritten line is never painted end to end.
- A file's line-number columns are as wide as that file's largest line number reads at the current text size and never narrower than two figures, both halves of split view sized the same way from the same file, so a number never spills into the code. A file with no newline at its end says so in one quiet row under its last line, `No newline at end of file`, spanning both halves as one row in split view rather than stranding it on one side.
- A line wider than the surface wraps at word boundaries with its continuations hung past the first row, so nothing is ever clipped and the diff never scrolls sideways; there is no wrap toggle.
- The file list is as wide as the longest path in the current list reads at the current text size, capped at 30 % of the pane so a deep path cannot eat into the diff, sized from its own drag edge and remembered at the width it is left at. It folds itself when the pane is narrower than the column plus one readable diff, `28rem`, and comes back at its derived width when the pane widens past that, while a fold made by hand with the header's control stands until it is undone by hand, so the two never fight.
- The header's file-list toggle folds the list away and the diff takes the whole pane width; the selected file, the filter and the diff's scroll survive the fold either way, and the choice holds across sessions as the split-view choice does. The toggle is absent, not disabled, wherever there is no list to hide: while no file has changed in the comparison in view.
- The file list is flat while every row fits the column at once and groups under faint folder headings the moment it does not, one heading per run of files, a folder holding a single child merged into one heading; the switch is read from how many rows the column can show at the current text size, never from a fixed number of files, and the filter, the selection and the diff's scroll are untouched by it. One filter box matches anywhere in a path, so an extension narrows the list as readily as a name does, and no second control filters it. In a path the folder is dimmed and truncates from its left while the file name keeps the row's own weight and never shrinks.
- The gutter control that opens a note is drawn on the row under the pointer, on the row that holds keyboard focus, and on every row from the start on a screen whose pointer cannot hover.
- Coloring arrives in two passes and the surface never computes it: a first pass is taken from the hunk's own lines the moment the file opens, and the whole file's spans replace it when they arrive, so a string that opens above the hunk corrects itself without the lines moving.

## Git Hosting Adapter

**Decision:** The hosting sites are GitHub and GitLab, each reached through its own installed, signed-in command-line tool: `gh` for GitHub and `glab` for GitLab, one adapter per kind behind one interface.

**Rationale:**

- Each tool is maintained by its site and covers what the review surface needs: opening a request, reading its state, reviews, threads and checks, posting a review, replying in and resolving a thread, and reading a check's log.
- Each tool carries the person's own sign-in, so the daemon holds no hosting token and every act leaves the machine under the person's own identity, whether the person pressed or an agent ran it.
- The adapter wraps the tool rather than calling the site's API with a token of its own, and never scrapes a tool's human-readable output: where a subcommand prints no structured output, the adapter goes through the tool's own API passthrough (`gh api`, `gh api graphql`).

### GitHostingAdapter Interface

The adapter uses host-agnostic naming (`ChangeRequest` rather than `PullRequest`), so one interface serves both sites and callers never name either.

| Operation | Description | On GitHub (`gh`) |
| --- | --- | --- |
| `createChangeRequest(params)` | Opens a request. Params: `baseBranch`, `headBranch`, `title`, `description`, `draft`, `reviewers`, `labels`. | `gh pr create` (`--base`, `--draft`, `--reviewer`, `--label`) + `gh pr view <created-url> --json number,url` |
| `listChangeRequests(params)` | Lists the requests on a branch, newest first. | `gh pr list` |
| `getChangeRequestStatus(params)` | Returns everything the request's reader needs (below). | `gh pr view --json …`, plus `gh api graphql` for the threads |
| `submitReview(params)` | Posts one review under exactly one verdict — comment, approve or request changes — with its line-anchored notes and an optional summary, naming each note that failed. | `gh api graphql`: a pending review, one `addPullRequestReviewThread` per note, then `submitPullRequestReview` |
| `resolveThread(params)` | Marks one review thread resolved. | `gh api graphql` (`resolveReviewThread`) |
| `replyToThread(params)` | Replies in one review thread. | `gh api graphql` (`addPullRequestReviewThreadReply`) |
| `readCheckLog(params)` | Returns a failing check's log tail and the address of the check's own page. | `gh api` |
| `listReviewers(params)` | Lists the people and teams a request can ask for review. | `gh api` |
| `listLabels(params)` | Lists the repository's labels. | `gh api` |

On GitLab each operation goes through `glab` with the same parameters and the same structured results, opening a request with `glab mr create`. Every operation takes the session's repository and returns a structured result, never raw tool output. `createChangeRequest` on GitHub runs `gh pr create`, which prints only the new request's address, and then resolves the structured handle by passing that address to `gh pr view <created-url> --json number,url` — never a bare `gh pr view`, which resolves the current branch's request rather than the one just created on an arbitrary `headBranch`. The adapter never scrapes a tool's human-readable output.

A review is posted as a pending review, then one thread per note, then submitted, so a post that fails part-way can name the note that failed and a second press posts only what is still held. On GitHub each note is `addPullRequestReviewThread` on the pending review, and `submitPullRequestReview` then takes the pending review's id (or the request's id), a required `event` (`APPROVE`, `COMMENT` or `REQUEST_CHANGES`) and the optional summary as `body`, and returns the submitted review; a pending review can be deleted before it is submitted ([GitHub GraphQL: pulls](https://docs.github.com/en/graphql/reference/pulls)). The REST create-review call is never used: it is all or none, so one comment on a line outside the diff refuses the whole call with 422 `Line could not be resolved` and leaves no review, no comment and no pending draft ([GitHub REST: pull request reviews](https://docs.github.com/en/rest/pulls/reviews)). `gh pr review` carries only a review body, with no per-line notes, and resolving or replying in a thread has no `gh pr` subcommand, so all of them go through the tool's GraphQL passthrough.

`getChangeRequestStatus` returns everything a reader needs to judge a request without leaving the console: its state and whether it is a draft, whether it can merge or its branches conflict, its review decision in plain words, each reviewer's latest verdict and the reviewers who have been asked but have not answered, its description body, its own web address on the service, who authored it and whether the signed-in identity did, its threads with each one's file, line, side, state (open, resolved or outdated), author and replies, its checks with each one's name, status and page, and its head commit. On GitHub the request's own facts are `gh pr view --json` fields (`isDraft`, `mergeable`, `reviewDecision`, `latestReviews`, `reviewRequests`, `body`, `url`, `author`, `statusCheckRollup`, `headRefOid`) and the threads are the request's `reviewThreads` through `gh api graphql`, which also answers `viewerDidAuthor` (checked on gh 2.101.0). A fact the service has not settled yet comes back absent rather than guessed, and a surface renders each of these as a fact rather than as a control.

The author field is load-bearing for one refusal: a hosting service refuses an approval on a request the signed-in identity authored. The approve verdict therefore keeps its fixed place beside comment and request-changes and is offered disabled on the user's own request, with that reason given in its own tooltip, which reads exactly `The forge refuses a self-approval: this pull request is your own.`, while the other two stay live and post exactly as they otherwise do. This is the one place on the review surface where a control is disabled rather than absent.

The adapter also reports the vocabulary the host uses, and one session's surfaces all speak it: where a host calls them pull requests the strip reads `Open pull request`, the comparison `Pull request` and the number carries `#`; where a host calls them merge requests the same places read `Open merge request` and `Merge request` and the number carries `!`. Where the adapter cannot say which service it is, the pull-request wording stands. This is what host-agnostic `ChangeRequest` naming buys — the interface never changes, only the words a surface prints.

### Hosting Sites

The adapter answers for GitHub and GitLab, on their public sites and on self-hosted hosts. The site a repository lives on is read from its remote. A self-hosted host is registered by name on the machine's Settings (`gitflow.hostAdd {host}`), so it lights the pull-request half of Review; the host is one name and there is no kind to pick: the daemon asks each installed tool, `gh` and `glab`, whether it answers for that host signed in, and keeps the kind, GitHub or GitLab, of the one that does. A name that does not parse is refused in place with `That is not a host name.`; a host no installed, signed-in tool answers for is refused with `<host> didn't answer as GitHub or GitLab. Sign in to it with gh or glab, then add it again.`; either way nothing is saved. `gitflow.hostList` lists the registered hosts and `gitflow.hostRemove` removes one.

A request is kept current only while someone is looking at it. While the session's header is on screen its request word follows the site through a conditional request every 60 s — an unchanged answer, `304 Not Modified`, costs no rate-limit quota ([GitHub REST: best practices, conditional requests](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests)) — and reads again at once after the person's own git and pull-request acts and after each event that changes the request. The pull-request comparison re-reads the request's state and threads while it is in view, every 60 s while the request is open and every five minutes once it is merged or closed; a read that fails waits one second, then 1.6 times longer each time up to two minutes, with a fifth either way of jitter, waits longer whenever the service names a time, and waits at least a minute after a rate limit that names none, keeping the last state on screen through every failure. With nothing subscribed, nothing asks the host.

The adapter's typed interface is the daemon's own, in its gitflow module (`packages/runtime-daemon/src/gitflow/`, which Plan-008 builds); only the `gitflow.*` method shapes are wire contracts.

## Example Flows

- `Example: An agent edits files in the session's worktree and commits them with a git command. The daemon's hook adds the Agent-Run trailer, the watch sees HEAD move, the Branch tab's commit picker lists the commit with the agent's mark, and the flow gains Committed · a1b2c3d · Add the login form. The person presses Open pull request; the form opens on the recorded base with the proposed title and description, the exact commands show under the fold, and the flow gains PR #484 opened.`
- `Example: The person edits a file in the session terminal between turns. The diff read shows the file with no turn beside its counts, and a commit made there carries no trailer and reads as the person's.`

## Implementation Notes

- A file's turn and a commit's agent are facts the daemon supplies, never inferred in the surface.
- The ship facts and the diff are separate reads: the facts follow the per-folder watch, and the diff is re-read only on the reader's press.
- Head or base branch changes after worktree creation must be explicit updates to the stored branch context.

## Pitfalls To Avoid

- Marking a file with a turn that did not change it, or a commit with an agent that did not make it
- Inferring PR base or head from transient client state
- Running a git act whose exact commands the person was not shown first
- Asking the hosting service while nothing on screen is subscribed to its answer

## Acceptance Criteria

- [ ] Every run in a project session, in its own worktree or in the project's checkout, has an explicit branch context.
- [ ] An agent's commit carries exactly one trailer the daemon wrote, `Agent-Run: <run-id>`; the person's commits, the session terminal's commits and a commit made with `git -c core.hooksPath=…` carry none.
- [ ] The diff names each file's newest turn and nothing for a file changed outside a turn; a commit shows an agent only where its trailer names one.
- [ ] The commands a preview shows are the commands the act runs.
- [ ] The pull-request form opens on the recorded base with the values the ship-facts read supplies, with no preparation record.
- [ ] A posted review that fails part-way names the failed note, marks the posted notes sent, and a second press posts only what is still held; a stranded note and a note on uncommitted lines are never posted.
- [ ] A self-hosted GitHub or GitLab host is added by name, and a malformed name and an unanswered host are each refused with their own line and save nothing.
- [ ] With no subscriber, the daemon sends no request to the hosting service.
