## Purpose

An agent is configured once and used many times. Without a durable record, the configuration a user tuned — provider, model, effort, instructions, the tools it may reach, the account that pays for it — would exist nowhere except inside whichever session it was typed into. This spec defines the **agent definition**: a node-local, named, durable record of that configuration, and the rules by which the daemon resolves one when a run starts under it.

It also defines **peer invocation** — the one daemon-owned tool server by which a running agent reaches another agent, including one bound to the other provider. Peer invocation is the reason the definition registry must exist rather than merely being convenient: an agent naming the peer it wants needs a stable, node-local thing to name.

## Scope

- A definition is **authored content with a lifecycle** — created, edited, duplicated, exported, imported, deleted, and found by search — and it is kept at the top level, beside the surfaces that consume it: its own destination on the console's rail rather than a page of node configuration ([ADR-031](../decisions/031-five-rail-destinations.md)). A destination is where a person goes to make or use something; a configuration page configures the node or the shell.
- The `agent_definitions` registry: its fields, its identity model, its uniqueness rules, and its node-local lifetime.
- The split between a definition's **core** — name, role, icon and accent, instructions, goal, execution posture, tool allowlist, turn cap — which is provider-agnostic, and its **bindings** — driver, model, paying account, effort — which are a plural axis, so one agent runs on either provider without being copied into a second definition.
- Resolution when a run starts: how the daemon resolves a definition, what it applies, what it echoes back, and what it refuses.
- Peer invocation: the one daemon-owned tool server and its six verbs, how each provider's lead reaches them, their targeting rules, their authorization, and their cost and causation consequences.
- **One registry, read by every surface that chooses an agent** — a session's composer and the workflow builder's node alike. A surface holding a list of its own would be a second copy of one registry; the control that chooses belongs to the surface it sits on, and the registry it reads belongs here.
- The editing surfaces the desktop and CLI clients present for definitions: the library over the registry, and the editor over one definition.

## Non-Goals

- **No new orchestration primitive.** A peer invocation creates an ordinary orchestration-admitted child run. Every [Spec-014 §Scheduler Limits](./014-multi-agent-channels-and-orchestration.md#scheduler-limits) admission rule, every link type, and every refusal code applies unchanged; this spec adds no run kind, no link type, and no scheduler rule.
- **No new approval category.** A bridge call is an ordinary tool call: it rides the existing `tool_execution` category through the existing approval pipeline, under the session's own permission level, so no `ApprovalCategory` value is added and the nine-member category enum of [Spec-010 §Required Behavior](./010-approvals-permissions-and-trust-boundaries.md#required-behavior) is unchanged. An invocation still lands as an ordinary `tool_activity` row.
- **No cross-node targeting.** A definition and a peer-invocation target are node-local. Cross-node dispatch remains `Spec-022`'s; a target resolving to a non-local node refuses under the existing `orchestration.node_not_local`.
- **No definition sharing or sync.** Definitions live on the node that owns them and are never relayed, published to the control plane, or carried in a session join. Two nodes that both hold a definition named `reviewer` hold two unrelated records.
- **No marketplace, no template gallery, and no discovery of definitions authored elsewhere.** The registry holds what this node's files hold; there is no catalogue to browse and nothing is fetched to fill it.
- **Nothing about driving a session from a linked device.** The registry is node-local and no part of this spec crosses that boundary; a linked device reads a session, never this node's definition files.
- **No new provider capability.** Effort, execution posture, paying accounts, and tools are the axes the corpus already carries; a definition composes them and invents none.
- **No place of work.** A definition says who and how carefully, never **where**: beyond its execution posture it carries no repository and no worktree execution mode. Those belong to the session or the workflow run that uses the agent, which already decide them — [Spec-008](./008-worktree-lifecycle-and-execution-modes.md) binds exactly one execution mode to every repo-bound run — so the record gains no column for either, no editing surface offers one, and an export carries nothing machine-local on this axis.
- **No skill attachment.** A definition does not list skills. Every skill available on the provider an agent runs on reaches it in the pack the daemon builds at session launch, so there is nothing to attach one at a time here; skills, their availability, and their files are [Spec-030](./030-skills.md)'s.
- **No workflow replacement.** A workflow phase remains the surface for multi-step authored orchestration (`Spec-015`). An agent definition configures _one_ agent; it declares no sequence, no gate, and no dependency edge.
- **No structured report-back channel beyond the tool result.** The bridge's verbs answer on their own results — the agent's handle when it starts, its status and its output when a wait returns; no verb mints a side channel by which an agent pushes structured state into the one that reached it.

## Required Behavior

### The definition registry

- An **agent definition** is a node-local durable record in two parts. Its **core** is provider-agnostic and carries: a human `name`, a `description` that may be empty — the role line read under the name — an optional `icon`, an optional `accentHue`, an optional execution-posture **mode**, `instructions` (the system-prompt text the agent runs under), an optional `goal`, an optional tool allowlist, an optional turn cap, and creation/update timestamps. Its **bindings** carry the provider axes: one default binding and any number of overrides, each binding naming a driver key, a model id, an optional provider-account reference, and an optional effort level.
- **The bindings are a plural axis, and the default is one of them rather than a fallback.** An override names a driver the definition has not already bound: an override's driver is unique within the definition and no override may repeat the default's driver, so at most one binding exists per driver and which binding answers for a driver is never ambiguous. An override is a whole binding in its own right and never "the default with some fields replaced" — no field of an override is inherited from the default. This is what lets one definition run on either provider without being copied into a second definition, and it is why the four provider axes are not top-level fields of the record.
- **`icon` and `accentHue` are two fields, not one**, and either may be absent: the icon is a glyph key from the console's own icon set, and the accent is one step of the console's twelve-step hue wheel. A definition that sets no icon is drawn with the generic agent glyph — the same picture the destination's own rail entry uses — and the accent is what tints that agent wherever it is shown, so one agent keeps one colour across every surface that draws it.
- **A definition MAY carry a turn cap**: the number of turns the agent may take before it is stopped, with no value meaning no cap. The number means the same thing on both providers although only one enforces it — on the Claude leg it is that provider's own per-agent limit, and on the Codex leg, which publishes none, the daemon counts the agent's rounds on the wire, interrupts at the cap, and then lets exactly one wrap-up turn run. The daemon invents no cap of its own, and this is not a budget: the budgets and their ceilings are [Spec-014 §Budget Policies](./014-multi-agent-channels-and-orchestration.md#budget-policies)'s.
- **Three origins, one registry.** A definition's file lives in one of three places, and all three are listed as one registry, each entry marked with which place it came from and whether it is global to the node or belongs to one project: this product's own folder (`~/.ai-sidekicks/agents/<name>.md`, and `<project>/.ai-sidekicks/agents/` for a project's own, committed with the repository), the Claude leg's own folder (`~/.claude/agents`, `<project>/.claude/agents`), and the Codex leg's own folder (`~/.codex/agents`, `<project>/.codex/agents`). The daemon watches all of them. A provider's own file is **edited in place and never written by this product otherwise**, and never gains a key its provider does not read; anything authored here is written only under this product's own folder, and a definition reaches a provider through the pack the daemon builds at session launch, in that provider's own format, so nothing is ever copied into another provider's folder.
- **The record is the union of both providers' fields, and what a file cannot hold lives beside it.** A field a provider's file has no place for — the icon, the accent — is stored in this node's own record attached to that file, and a reader is shown the merge: editing a provider-supported field writes the file, editing one of the others writes only the record. The attachment follows the file's name and location, so a file renamed or deleted outside this product leaves those fields **orphaned** until they are reattached to a file or discarded — never silently rewritten, never silently dropped. Where a provider cannot enforce a core field itself — a tool allowlist on the leg that has none, a sandbox posture on the other — the daemon enforces it at spawn, so one rule covers definitions authored here and definitions authored by a provider alike.
- Definition **identity is a daemon-minted opaque immutable `definitionId`**. `name` is a mutable human label and MUST NOT be used as an identity key on any wire request, stored reference, or audit row. Renaming a definition MUST NOT change its `definitionId`, and MUST NOT alter any agent already running from it.
- `name` MUST be unique per node under case-insensitive comparison. Two definitions differing only in letter case are the same handle to a human reading a picker, and admitting both would make the name a target no operator can disambiguate.
- The tool allowlist has three distinguishable states and the daemon MUST NOT collapse them: **absent** means the driver's default tool set, an **empty list** means no tools at all, and a **populated list** means exactly those tools. An absent allowlist and an empty one are opposite instructions.
- **The allowlist covers the provider's own built-in tools too**, beside the configured tool servers and the daemon's own callback tools, and the three states keep exactly the meanings above over that wider catalogue. The daemon realizes the list at spawn, where the allowlist is already enforced: on the Claude leg as that provider's tool flags, where a **bare tool name** is what removes a tool's schema from the request — a scoped rule such as `Bash(git *)`, and any allow-form, leave the schema in place — and on the Codex leg as that provider's own feature and tool keys, where a model running in its code-only mode sends no tool list at all, so on that model there is nothing for an allowlist to remove. A name the resolved driver cannot realize is refused in place, naming the driver, per §Fallback Behavior. There is deliberately **no provider-wide always-off list** anywhere in this corpus: a standing per-provider disabled set would be a third precedence layer over posture and allowlist, and a second answer to which tools a run gets.
- A definition stores the execution-posture **mode** only — never a composed `ExecutionPosture`. The mode is one of the corpus's five permission levels — `readonly`, `ask`, `reviewed`, `sandboxed`, `yolo` — or absent, which means the posture of the session or run the agent is used in. Plan is not among them: that is a session's own mode, not a property of an agent. The daemon composes the full posture when the run starts, from that mode plus the session's live credential policy. Storing a composed posture would let a definition pin a content-addressed `credentialPolicyRef` that has since been superseded, so a definition edited once could re-grant a trust decision the session has since narrowed.
- Definitions are node-local. The daemon MUST NOT relay, publish, or otherwise transmit a definition to the control plane or to a peer node.

### The library

The library is the destination's list over the registry, and the one place a definition is created, duplicated, exported, imported, deleted, and found.

- **The header** carries the destination's title, the definition count, a search field, `New sidekick`, and `Import`. `Export` is absent while the list is empty, loading, or refused, because there is nothing to select. The library answers at `#/sidekicks`, one definition at `#/sidekicks/<definitionId>`, and a new one at `#/sidekicks/new`.
- **A card** carries the icon on a swatch tinted with the accent; the name; the role line clamped to one line; a chip row of provider and model, effort read as one word of the console's single effort ladder, and posture; the tool-allowlist summary; the **origin mark**, naming which of the three places the definition's file lives in and whether it is global or belongs to this project; and a meta line holding `Also on Codex` where a second provider is bound, `used by N workflows`, and when it was last used. Every card shares one shape: the chip row and the meta row keep their slots whether or not they have content, so a card always aligns with its neighbours. The whole card opens the editor, and `Duplicate`, `Export` and `Delete` sit on it.
- **Four read states are kept apart** — not loaded, refused, served empty, and rows. An empty registry shows one sentence and `New sidekick`, never a spinner and never a list. A read still in flight is its own state, distinct from empty. A refused read renders the refusal itself with `Try again` as one faint clickable word at the right end of its line — no box and no icon — and no rows.
- **Ordering** is by name under `Intl.Collator`, ties broken by the definition id, and it does not change while a delete is in flight. Exactly one alternative exists — **last used**, most recent first, never-used last, ties broken by the same name collation — switched from the caption itself, where `ordered by name` flips to `ordered by last used` and back, rather than from a menu, and remembered per user. The caption carries only that control, `N of M match` while a search narrows the list, and `Select all` while selecting.
- **Search** matches name, role, driver, model, and tool names; case-folded; substring; never fuzzy. A search matching nothing says so and leaves the search field focused.
- **Selecting is for export, and only after being asked for.** `Export` in the header starts it: a checkbox appears on every card, `Select all` appears beside the caption, and a bar at the foot reads `0 selected · Export · Cancel`, with its own `Export` disabled until something is ticked. A click ticks one and a shift-click ticks the range from the last tick; once every visible card is ticked the same control reads `Select none` and clears them; cancelling or `Escape` leaves selecting and clears it. Outside selecting no checkbox and no `Select all` is anywhere, and the library looks exactly as it always does. Export from the bar writes one file holding the ticked definitions; Export on a card writes that one definition. **Delete stays on the card, one at a time**, because its confirmation names that definition's running sessions and its workflow count, and a bulk delete would have to name them per definition; the selection bar carries no delete.
- **`New sidekick`** opens the editor empty, with a driver preselected only where the node has exactly one provider registered — otherwise nothing is guessed.
- **Duplicating** copies every field, bindings included, names the copy after the original (`<name> copy`, then `<name> copy 2`), and opens the editor on it.
- **Deleting is confirmed, never refused by the client.** The confirmation names the consequence: sessions already running the agent keep the configuration they were given, and the workflow nodes that reference it will refuse at their next run. A delete the daemon refuses renders that refusal on the card and leaves the row in place.
- **Export and import.** An export is one file holding one or many definitions: the core, the icon and accent, and every binding with its **provider-account reference cleared**, plus a schema marker; the file itself says the accounts were cleared. An import **creates** definitions and never overwrites one, suffixing a colliding name exactly as duplicating does. A file whose schema marker is unknown is refused whole, and no partial import is applied.
- **Keys.** The cards are one roving-index list: the arrows move a cursor, `Enter` opens, the delete key starts the two-step delete on the card, and `/` focuses search.

### The editor

The editor is one column and no wizard, over one definition, in this order: name, role, icon and accent, instructions, goal, `Max turns` beside the read-only provider badges, execution posture, tool allowlist, skills, provider bindings, and a try-it panel in the side slot.

- **Instructions** is a field that grows with its text, with an **estimate** of its size under it, rendered with a visible `≈` and computed by a character heuristic — never by a tokenizer dependency, whose precision the number does not have.
- **`Max turns`** is one number field, empty meaning no cap, with one line under it saying that the agent stops at that many turns and gets one wrap-up turn, that Claude Code enforces the cap itself, and that on Codex the daemon counts the turns on the wire.
- Beside it, and only on a definition whose file is the Claude leg's own, two read-only badges under `From this sidekick's file` name what that file declares and this editor does not author — `Hooks · <the hooks the file declares>` and `Memory · <scope>`. Neither carries a control — they are edited in the file. The console's own session-level hooks are registered per session over the wire, are never shown here, and are never written into a file.
- **Execution posture** offers the session default and the five permission levels in one fixed order, in the same words a session's composer shows — Read-only, Ask, Reviewed, Sandboxed, YOLO. A provider's own mode name never appears, and Plan is not offered: that is a session's mode.
- **The tool allowlist is three visibly different controls, never one empty list**: the driver's defaults, with nothing chosen; no tools, an explicit empty set; and exactly these, a checked set over the catalogue. The catalogue holds the configured tool servers, the daemon's own callback tools, and each driver's built-in tools in a group under that driver's name. Each row reads the **words for the tool** while the driver's own spelling is what is stored and what the daemon realizes at spawn, and the two facts about what an allowlist actually removes on each provider are stated with the control, because both are true and neither is obvious. A tool that has left the catalogue keeps its unknown-but-still-stored rendering rather than being dropped.
- **Effort** reads as the console's one ladder everywhere — Minimal, Low, Medium, High, Extra high, Max — mapped one-to-one from the provider's own names, which are what is stored. A model publishing no levels renders the effort row as the words `Not published by this model`, never an empty or disabled control. An effort stored for a model that no longer publishes it is shown with a warning and is never silently cleared.
- **Skills** takes no value. It states the rule and links out: every skill available on the provider an agent runs on is handed to it in the pack the daemon builds at launch, so nothing is attached here one at a time, and one link beside the field, `Open Skills`, opens the skills destination at `#/skills`, where availability, folders, and the files themselves are edited.
- **Provider bindings** render the default binding as a dependent chain — driver, then model, then paying account, then effort, each narrowing the next — followed by the overrides, each the same chain, each on a driver the definition has not already bound. The control that adds an override is absent once every registered driver is bound, and removing an override never touches the default binding.
- On a definition whose file belongs to a provider, a field that provider does not understand — the icon, the accent — is saved in this node's own record beside the file and never written into it, and the editor says so under the field.
- A **goal** left empty means the agent takes the goal of the session or run it is used in.
- **The header** carries `All sidekicks` back to the library, the same origin mark the card carries, a count of unsaved changes while there are any, and the definition's name as the title. Delete is disabled until the definition has been saved once.
- **Leaving.** Saving is the only exit that keeps changes: cancelling, and navigating away from the destination, ask first and name what would be lost. Save and cancel both return to the library with focus restored to the card. Delete asks in place, with the same sentence the card uses. `Cmd/Ctrl+S` saves and `Escape` cancels through the unsaved-changes question.
- **A rename keeps the definition id.** Every surface that draws the registry picks up the new label on its next list read; nothing re-points and nothing breaks.
- **Try it** runs the definition itself, given a message — never a simulation of how something else would call it. It is disabled until the definition has been saved once, and says so. It composes two ordinary operations and mints no verb of its own: start a **scratch session with no repository attached, whose lead is the definition under test**, then send one turn; the reply streams in the panel. Exactly **one scratch session per definition** is kept and reused, so repeated tries do not multiply sessions, and the console never silently deletes a session it created — the scratch session is named and left in the session list, where it can be found and closed. The provider, model, effort, and account the daemon resolved come back on that session's start, and that echo is where every surface that runs a definition reads the resolved binding from.
- **A live try-it run carries the same two controls a dispatched agent's own view carries** — `Pause · Interrupt` — beside its `Running…` button. Pause holds the run after the step under way and is pressed again to continue. Interrupt ends the turn, the panel reads `Interrupted · waiting`, the button reads `Try it` again, and the scratch session is kept so the next press reuses it. `Escape` interrupts a live run first, and only the next `Escape` starts the leave-the-editor path. The daemon picks the mechanism behind each word per provider, exactly as it does for a dispatched agent ([Spec-014 §Intervention Propagation](./014-multi-agent-channels-and-orchestration.md#intervention-propagation)).

### Rules the library and the editor both obey

- **A save, an export, and an import each confirm with one short note that fades**, and nothing else on these surfaces reports success.
- **No wire identifier reaches either surface.** A refusal is rendered as words — its code and then its reason, in sentence case, the code first and the reason after — followed by the daemon's own message in plain words; a status, an event kind, and an enumerated value are read the same way. A tool and a policy action are shown by the label registered for them while the driver's or the policy's own spelling is what is stored, and an unlabelled code falls back to its own words. Only what a person or an agent wrote, or would type, stays as written: model ids, file names and paths, commands, and prose.
- **The one user is never the named subject** of a row, a note, or a dialog on these surfaces, and no sentence of the product's own prose begins with `You`; the label is the thing and what happened to it, so the unsaved-changes question reads `Changed: Name, Role`. A definition's `instructions` are the person's own text and are outside that rule.
- **Every chrome size on these surfaces is derived from the current text size**, never a pixel constant — each width, floor, ceiling, padding, margin, gap, and grid track is as large as the content it must hold — so a larger text size grows the library, the cards, the editor, and its panels in one proportion, while the drawn marks (the hairlines, the corner radii, the icon boxes) stay as drawn. The same rule bounds the surfaces themselves: they fit the window they are given, full screen or any smaller size a desktop window reaches.

### Resolution when a run starts

- Any request that starts a run under an agent MAY name a definition instead of spelling out its axes — the session whose lead it is, the scratch session a try-it starts, a workflow step, and an agent named in a composer alike. The daemon resolves the definition and uses its fields as the configuration that run starts under.
- Request members that are explicitly present MUST override the definition's corresponding field, per field. The response MUST echo the **effective resolved configuration** — every field as actually applied — so a caller can never be left guessing which side of the merge won.
- **Resolution order is per field, and it has exactly three steps.** The resolved **driver** is the driver the request names, or the default binding's driver where the request names none. Each remaining provider axis then resolves in one order: an explicit value on the request, else the override for the resolved driver where the definition has one, else the default binding. Nothing falls through further, and no axis is ever composed from two bindings at once.
- **A model is never guessed.** A request naming a driver the definition neither defaults to nor overrides resolves **only if the request also supplies the model**; otherwise it refuses. Substituting a nearest model, or carrying another driver's model id across, would run something the definition never pinned and price it differently.
- **The caller sends only what it changed; the daemon performs resolution and answers with what it applied.** A request carries the definition reference plus exactly the axes explicitly overridden for this use. A client MAY show, per axis, where a value would come from — the caller's own override, this definition's binding, or the driver's default — as a preview beside the control that changes it; it MUST NOT compute the resolved configuration itself and MUST NOT present that preview as the applied result. The echo on the reply is the one place a resolved binding is read from, on every request that starts a run under a definition, and three requests carry it: the session start — the scratch session a try-it opens included, where the definition under test runs as that session's own lead — the workflow step's own record, and the composer's agent row. Each answers with the binding the daemon applied: the driver, the model, the effort, and the provider account.
- **Effort is validated at resolution, never at save.** An editing surface MAY warn that an effort stored on a binding is not among what the chosen model publishes, and MUST still save it: the vocabulary is per model and provider-published, so it moves under a stored value without the definition changing. The daemon validates at resolution against the resolved model's own published levels and refuses there (§Fallback Behavior); a model publishing none exposes no effort choice at all.
- **A run keeps the configuration it was given; only its label is read live.** The resolved values belong to the run from the moment it starts: editing or deleting the definition MUST NOT mutate, reconfigure, re-authorize, or revoke an agent already running from it, and MUST NOT affect any run in flight — which is exactly what the delete confirmation tells the person (§The library). A live reference would let an edit widen a running agent's tool allowlist, posture, or paying account without that widening ever passing the authorization that admitted the run. Presentation is the one exception and is resolved at the moment it is drawn: a running agent's displayed name, icon, and accent come from its definition, falling back to the agent's own name where the definition is gone, so a rename retitles a running agent mid-session while no edit changes what it may do.
- Resolution MUST fail closed. A definition naming a provider account that is no longer in this node's registry MUST refuse, and the refusal MUST name the definition and the unresolvable account; no agent is configured and no run starts. The test is **registry membership**, a definite fact the resolver owns — deliberately not whether the account is currently usable, which is authentication state that `Spec-026`'s live spawn probe is the authority on. Refusing here on a stored readiness reading would refuse a run the spawn gate would have admitted. The daemon MUST NOT silently fall back to the provider's default account — a pinned account that quietly becomes "whichever account is default now" is a spend and identity change the operator did not ask for.
- The tool allowlist MUST be **enforced at spawn**, not merely recorded. If the resolved driver cannot realize the allowlist, resolution MUST refuse rather than spawning the agent unconstrained. An allowlist that is stored and not applied is worse than no allowlist, because it reports a restriction that does not hold.
- Deleting a definition MUST NOT be blocked by the agents already running from it, because a run no longer depends on the definition it resolved.

### Peer invocation

- **One bridge, six verbs.** The daemon serves a session exactly one tool server, carrying six verbs: **run** a named agent, **message** one that is running, **wait** for its output, **stop** it, **close** it, and **list** what is running. The server is daemon-constructed and daemon-trusted, and it reaches both providers through the callback-tool registry [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior) defines — the Codex leg as a function-form dynamic tool, the Claude leg through the daemon-hosted ephemeral Model Context Protocol (MCP) server. The six verbs mirror what each provider already gives its own helpers, which is why one server serves both legs. This is the one place this product builds a bridge of its own, and it exists so that every saved agent reaches every lead: an agent bound to one provider is usable from a session running on the other.
- **The daemon runs the agent on its own provider.** It starts that provider's own unit of work — a thread on the Codex leg, a process on the Claude leg — applies the definition there, shows the agent under the one that reached it in the session's agent tree with a mark of which provider is running it, and returns its output like any helper's. Because the daemon owns that process it reads the agent's output word by word in both directions; a provider's own in-session helper, seen through its lead, arrives as whole messages instead ([Spec-014 §Provider-Native Subagents](./014-multi-agent-channels-and-orchestration.md#provider-native-subagents)).
- **How each lead reaches the bridge.** On a Claude Code lead an agent bound to the other provider is an entry in the session pack whose **only** tools are the bridge's verbs; the lead's own tool list never holds those verbs, so the lead reaches the agent through that entry and nothing else, and that provider's own mention form (`@agent-sidekicks:<name>`) works on it as on any agent. That separation is load-bearing rather than tidy: with the verbs merely permitted on the lead itself, a lead told to run an agent called the verbs directly and started no helper at all, leaving nothing for the tree to draw. On a Codex lead the tool server itself is the interface — its own description lists every agent bound to the other provider by name and description, and the lead runs one by name. No stand-in role is planted on that leg: a Codex lead calls a tool it can see rather than spawning a role that would call it, and that provider has no per-role tool list to hide the verbs behind. Whatever the daemon needs a caller to do therefore belongs in the verbs' own descriptions and in what they return, because a lead that calls them itself never loads a stand-in's instructions.
- **`run` answers at once, and `wait` is bounded.** `run` returns the agent's handle immediately rather than blocking until the work is done, and `wait` always returns inside its own timeout — with the agent still running and what it has produced so far, or with the terminal it reached and its output. A blocking wait would make the agent unsteerable by construction: on the Claude leg a helper reads what it is sent only at a tool round, so each bounded wait is the round that lets a steer land. The daemon caps the timeout itself rather than trusting the caller's.
- **Steer and stop from the row** reach the provider running the agent directly — a steer and an interrupt on its Codex thread, a message and an interrupt on its Claude Code process — and whoever reached it learns the outcome on its next wait and relays it without being told. **Steer from the lead** is native on both legs: a message to the helper on the Claude leg, the message verb on the Codex leg. **Stop from the lead** on the Claude leg is read by the daemon off the lead's own stream — the stop names the helper, and that helper's bridge calls carry its handle — and the daemon interrupts the underlying thread at once; on the Codex leg the lead calls the stop verb.
- **A run nobody waits on is closed on the poll interval.** Neither provider tells a tool server that its caller was stopped, so an agent whose caller has gone would otherwise run on, billed, with nobody reading it. The daemon therefore closes any run no wait has arrived for within one poll interval and interrupts what it was doing. The clock is the gap between one wait **returning** and the next **arriving**, never the age of the last wait: one long wait would otherwise keep the clock fresh for its whole duration and mask an abandoned run completely — measured, a caller-chosen thirty-second wait hid the abandonment and the sweep never fired, which is also why the daemon caps the wait timeout rather than the caller.
- **State lives in the daemon, never in the tool-server process.** The handles, the provider-side thread and process identities, and what each agent has produced are the daemon's own. A provider restarts a tool server under a live session, and state held in that process is lost with it: measured, the restart lost the handles, the next wait answered that no such handle existed, and the agent's whole task was re-run from the start — a second billed turn nobody asked for.
- **A cross-provider agent keeps its conversation until the bridge closes it.** A message sent to one that has already finished continues the same conversation with its memory intact rather than opening a second one, so a follow-up costs one more turn rather than a whole repeat.
- **Which definitions cross the bridge**: a Claude Code file in a Codex session, a Codex file in a Claude Code session, and one of this product's own definitions only where its binding names the other provider — this product's own definitions are provider-agnostic and otherwise run natively on the session's own provider. Skills never cross: a skill is text a model reads, so one available only on the other provider is used from this side by running an agent that carries it ([Spec-030](./030-skills.md)).
- **An agent reached across the bridge carries the provider running it in its name** — `sidekicks:codex-reviewer` in a Claude Code session, `sidekicks:claude-reviewer` in a Codex session — so two files of the same name never collide, and nobody types either: choosing the row inserts the identifier.
- **An agent reached through the bridge reaches it the same way its lead does** — on the Claude leg it starts the pack entry itself and can steer it, on the Codex leg it holds its lead's tools and calls the verbs directly.
- **Every verb that names a target names an agent.** `run` names a saved definition by its `definitionId`; `message`, `wait`, `stop` and `close` name an agent already running in this session by the handle `run` returned; `list` names none. A request naming a provider, a model, or an account rather than an agent MUST be refused. The unit an agent addresses is another configured agent, not a vendor.
- The work the bridge starts is admitted through the ordinary orchestration pipeline and linked to the run that reached it under the existing link types; this spec mints no run kind and no link type.
- **The controls a bridged agent carries are the ones every agent's own view carries** — pause and interrupt at the end of its own working line, and the steer box under its flow — and never a control on its row in a list. Pause on it is the same hold the daemon applies to any agent on that provider: the hold on its next tool callback on the Claude leg, the boundary interrupt on its Codex thread ([Spec-014 §Intervention Propagation](./014-multi-agent-channels-and-orchestration.md#intervention-propagation)).
- Every invocation MUST be authorized as the tool call it is — through the session's existing approval pipeline, in the existing `tool_execution` category — MUST land as an ordinary `tool_activity` row, and MUST produce an agent visible in the session's agent tree like any other. There is no invisible peer invocation. The bridge's own verb spellings are plumbing and never reach a screen: a row says what the agent is doing, not which verb carried it.
- Refusals MUST be answered on the callback-tool result's existing arms — `denied` with the reason for an authorization or admission refusal, `failed` for an unknown target or schema-invalid arguments. No invocation is left unanswered, and no peer-invocation refusal is invented as a new error code.

### Availability and adjudication

- **The bridge is available in every session**, and the product adds no switch, cap, or enrolment of its own over it. Its verbs MUST be registered into the callback-tool registry at spawn **unconditionally**, and every invocation MUST be adjudicated at call time by the session's existing approval pipeline, in the existing `tool_execution` category, under the session's own permission level ([Spec-010 §Required Behavior](./010-approvals-permissions-and-trust-boundaries.md#required-behavior)). A bridge call is governed exactly as any other tool call in that session is: on a level that asks, it raises the same approval any tool call raises; a remembered rule answers it without asking again; on a level that asks for nothing, nothing asks. The calling definition's tool allowlist is the only other filter, and nothing else gates it. Registration follows the landed `workflow_start` shape — registered at spawn, adjudicated per invocation — and is deliberately **not** state-gated: `callbackTools` rides only the session-creation and resume parameter shapes, and no live-registry mutation seam exists, so a registry filtered against anything that can move while the session runs could not change until the leg respawned. Per-call adjudication requires no such seam, and every change of what a session permits is effective on the next call.
- A definition's tool allowlist MUST filter this registry as it filters any other tool source. An agent whose definition carries an empty allowlist receives **none** of the bridge's verbs, and one naming an explicit set receives them only if that set names them. An allowlist that did not bind the daemon's own curated tools would report a restriction that is not in force.
- **A wait always settles.** A wait returns inside its own timeout whatever the agent's state is then, and a wait outstanding when the agent reaches a terminal state is settled by that terminal — one that fails, is cancelled, or is interrupted answers with that state and whatever output it had produced, and one that finishes having produced nothing answers as finished-with-nothing rather than as an answer. The agent's run id does not exist before admission, so the waiter cannot subscribe ahead of it; the waiter MUST therefore **capture the run-lifecycle stream cursor before admitting the agent**, then subscribe and replay forward from that captured cursor, settling from whichever source presents the terminal first. Subscribing merely before the verb _returns_ is insufficient and MUST NOT be relied on: a live subscription opened after admission never replays the terminal that landed in between, which is the one window this ordering closes. No invocation is left unanswered.

### Cost and causation

- A bridged agent's spend lands on **its own** cost-receipt row and is paid by **that agent's** provider account — an ordinary value of the receipt's existing per-account axis, and the reason a cross-provider agent's cost is legible at all: it runs on its own account, not on the lead's.
- The receipt MUST NOT roll a bridged agent's spend into the row of the run that reached it. [Spec-014 §Session Cost Receipt](./014-multi-agent-channels-and-orchestration.md#session-cost-receipt)'s per-run partition stays run-scoped, and the causal relationship between the two is carried by the existing parent/child run link, which the receipt reads and never re-folds.

## Default Behavior

- The bridge is present in every new session, and every call it carries raises whatever that session's permission level raises for any tool call — an approval on a level that asks, nothing on a level that asks for nothing. A session whose agents never reach for a peer behaves exactly as a session predating this spec.
- **An account reference on a definition is either pinned or current, and the two differ exactly when the provider's current account moves.** A definition that names a **specific** account is **pinned** to it: that account pays for every run under the definition, and it stays where it is pinned when a press on the provider surface makes another account current ([Spec-026 §Moving a session to another account](026-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)). A definition with **no** account reference follows the mark instead: it resolves to whichever account is the provider's current one when the run starts, and the resolved account is recorded with the run — so a run already going keeps the account it was admitted against, and a later move of the current account never silently re-points it. Those two are the whole of the choice an editing surface offers; there is no third state and nothing is resolved by guessing.
- A definition with no effort level resolves to the driver's default. A supplied effort is validated at resolution against the target model's driver-reported effort levels, never against a corpus-wide enumeration.
- A definition with no execution-posture mode resolves to the session's default posture.
- A definition with no tool allowlist resolves to the driver's default tool set.
- A definition with no turn cap resolves to no cap; the daemon adds none of its own.
- A definition with no goal resolves to the goal of the session or run it is used in.
- A caller that names no driver resolves the default binding's driver, and a caller that changes no axis sends no axis: an unchanged request is the definition, unmodified.

## Fallback Behavior

- **The registry is unreadable.** A run named by definition refuses; a run whose axes are spelled out in full is unaffected, so a storage fault on this table never blocks ordinary session work.
- **A definition pins a provider account that is no longer in the registry.** Resolution refuses with the `account_unavailable` arm, names the definition and the account, and starts nothing. An editing surface **marks the binding** and never rewrites it to the current account — a binding silently re-pointed is a change of who pays that nobody asked for. A binding that pins no account shows the current-account entry instead, meaning whichever account is current at the moment a run starts. The daemon MUST NOT fall back to the provider's current account. Account _readiness_ is deliberately **not** checked here: [Spec-026 §Node provider readiness and the sign-in handoff](./026-provider-accounts-and-credential-homes.md#node-provider-readiness-and-the-sign-in-handoff) makes the stored readiness projection advisory only, and the authoritative authentication check is the live probe the spawn path performs. Refusing at resolution on a stored reading would refuse an agent that would have started.
- **A definition's model is no longer offered by its provider.** Resolution refuses with the `model_unavailable` arm and names the model. The daemon MUST NOT substitute a nearest-match model — silently running a different model than the one a definition pins changes both behavior and price.
- **A caller names a driver the definition neither defaults to nor overrides, and supplies no model.** The same `model_unavailable` arm answers, carrying the requested driver and **no** model, which reads as "this definition binds no model for that driver". The arm is widened to say that rather than a new code being minted, because the unresolvable thing is still the model.
- **A definition's effort level is not supported by its model.** Resolution refuses with the `effort_unsupported` arm, naming the stored value and the supported set, rather than coercing to a neighbouring level. An editing surface shows that same set with the stored value beside it, both in the words of the console's one effort ladder, so the person sees what is stored and what the model will take.
- **A definition's tool allowlist cannot be realized by the resolved driver.** Resolution refuses with the `allowlist_unrealizable` arm, names the unrealizable tools alongside the driver's supported set, and starts nothing. The daemon MUST NOT spawn the agent with a silently narrowed allowlist, and MUST NOT spawn it unconstrained — either substitution reports a restriction that is not in force. A tool that has left the catalogue is likewise never dropped from a stored allowlist: it keeps an unknown-but-still-stored rendering until a person removes it.
- **The tool catalogue cannot be read in full.** The allowlist control renders its three states over the part of the catalogue it can read and **says which part it cannot list**, rather than presenting a short catalogue as the whole one. An empty catalogue is never shown as an empty set: the two are opposite instructions here exactly as absent and empty are on the allowlist itself.
- **A definition's usage count or last-used time is unavailable.** Those lines are **absent** from a card rather than rendered as zero or never — an unavailable count and a count of none are different facts, and only one of them is a fact about the definition.
- **A try-it run fails.** The panel keeps the scratch session, shows the refusal from whichever of the two operations failed — starting the scratch session, or sending the turn — and offers to retry that step alone, so a failed turn does not cost a new session and the resolved-binding echo is not lost.
- **A peer-invocation target names a definition that no longer exists.** The verb answers `failed` with the unresolvable target; no run is created.
- **A peer-invocation target resolves but the run refuses to start.** The verb answers `denied` carrying resolution's own reason, so the asking agent learns why rather than seeing an unexplained failure.
- **The approval seam is unavailable.** The whole callback-tool registry is withheld at spawn under the existing fail-closed availability rule of [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior), and the bridge goes with it — a withholding inherited from that rule rather than one this spec introduces; a stray invocation on an already-spawned leg is answered `denied`.
- **A bridged agent terminates without answering.** An outstanding wait is settled by that terminal state rather than left waiting or answered with a success the asking model would act on.

## Interfaces And Contracts

- Four daemon JSON-RPC operations in the `agent.*` namespace, carrying definition create / update / delete / list. All four belong to the destination that owns the registry; the list is the one read a session's composer also makes, and no session surface mutates a definition. Shapes and method strings are registered in [api-payload-contracts.md §Plan-027 — Agent Definitions And Peer Invocation](../architecture/contracts/api-payload-contracts.md#plan-027--agent-definitions-and-peer-invocation); every definition-plane and resolution-plane refusal this spec describes is typed in [error-contracts.md §Agent Definitions](../architecture/contracts/error-contracts.md#agent-definitions), whose five codes are the closed set for those paths — an untyped or generic failure on any of them is a defect, not a fallback. Peer-invocation refusals are deliberately absent from that table: they ride the callback-tool result's `denied` / `failed` arms per §Required Behavior, and mint no code.
- **The record's shape, and what the four pairs carry.** The definition's four provider fields — driver, model, paying account, effort — are **not** top-level members: they are `bindings`, one default binding plus a list of overrides, and the stored row always carries the list, possibly empty. `icon` and `accentHue` join the core as nullable members. The create request carries `bindings` with `overrides` **optional**, which is the stored-versus-draft grammar this corpus already uses — a stored row materializes an inherited value as null, a draft expresses it by omission, and that difference is load-bearing. The update request replaces `bindings` **whole**: a per-override patch grammar is not worth its wire for a bounded list that is always read together. **No verb is minted for any of this — the definition plane stays at four pairs.**
- A definition reference on every request that starts a run under an agent — additive-optional from the caller's side, so a request that spells its axes out in full is unchanged, while one carrying the reference need not respell the axes the definition supplies. The effective-resolved-configuration echo rides the response, and covers every field as actually applied, the system prompt and goal included; where the definition is bound plural, the echo carries the **resolved binding** in place of the folded axes. One echo serves every such request — the session whose lead the definition is, a scratch session started to try one out, a workflow step's own record, an agent named in a composer — so a resolved binding has exactly one home on the wire.
- **The definition list is the one registry read, and every surface that chooses an agent draws its own rows from it.** A session's composer draws them as its own group of agent rows, and the workflow builder's node draws them in its chooser; an authoring agent that names an agent by name in a written workflow resolves against that same read, so a workflow written by hand and one written by an agent reach the same library. Each row a reader draws carries the identity fields only — the icon on its accent swatch, the name, the role line, and the origin mark — and not the card's chips. **This spec exports no chooser and no picker**: what choosing an agent fills in belongs to the surface that chose it — the provider's own invocation form inserted into a composer's draft, or a workflow node's agent reference with its binding left absent until an axis is changed for that node. A surface holding its own list of definitions would be a second copy of one registry.
- **Two figures a card shows have no contract behind them yet**: how many workflow definitions reference a definition — the workflow document carries no agent reference to count — and which run most recently resolved one. Neither is derived by a client in the meantime; both lines are simply absent (§Fallback Behavior).
- One `SessionCallbackTool` registration per bridge verb — six — served through the existing callback-tool dispatch seam of [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior), and one pack entry per cross-provider agent on the Claude leg carrying those verbs and nothing else.
- One named Cedar action — `Action::"agent::manage"`, for authoring the node's definitions — registered in the enumeration of [Spec-010 §Implementation Notes](./010-approvals-permissions-and-trust-boundaries.md#implementation-notes). Peer invocation registers none: a bridge call is an ordinary tool call and rides the `tool_execution` approval category already in that spec's enum.
- No new event type. Definition mutation emits nothing: it is node-local configuration rather than session history, and every session-visible consequence of a peer invocation is already carried by the existing tool-activity and run-lifecycle events.

## State And Data Implications

- **A definition is a file, and one node-local table is the registry over it.** The authored fields live in the definition's file — one of the three origins of §Required Behavior, which the daemon watches — and one node-local table, owned by this spec's plan, holds the row the registry read answers from: identity, the name fold, the bindings, the icon and accent, the posture mode, the instructions and goal, the tool allowlist, the turn cap, and the timestamps. The row follows its file: a file this product wrote carries every field, so its row restates what the file says; a provider's own file carries only the fields that provider reads, so its row additionally holds what the file cannot (§Required Behavior, the union rule). Editing a field the file can hold writes the file; editing one it cannot writes only the row; a file changed or removed outside this product is picked up by the watch, and the fields only the row holds show as orphaned until they are reattached to a file or discarded. The table is configuration, not session state: it is not events-canonical, is not replayed, and is not rebuilt from the event log.
- **The bindings are one JSON column, not a child table.** The four provider columns a single binding would have taken fold into one non-null `bindings` column holding the default and the overrides together, beside nullable columns for the icon and the accent. JSON rather than a second table because this corpus already carries bounded, always-read-together lists inline — the tool allowlist on this same table is the precedent — and a binding is never queried across definitions. The table has not shipped, so this consumes no migration ordinal and moves no table census; the definitions table is created in its final shape rather than created and then migrated.
- **Nothing this product knows is ever written into a provider's file.** A field a provider's file has no place for stays in the row, attached to the file by its name and location, and the file never gains a key its provider does not read.
- Export and import touch no table of their own: an export is a file the person keeps, with every provider-account reference cleared, and an import is ordinary definition creates.
- Starting a run under a definition writes the resolved values onto that run's own agent record. No foreign key binds an agent to the definition it was resolved from, because it does not depend on it after resolution.
- No relay, control-plane, or export impact: definitions never leave the node.
- `instructions` and `goal` are operator-authored text and are treated as ordinary node-local configuration content; they are never emitted into an event payload by definition mutation.

## Example Flows

- `Example: A user creates a definition named "reviewer" pinning a provider, a model, extra-high effort, a read-only posture, review instructions, and an allowlist of read-only tools. Three later sessions name it in their composer; each run records the configuration it was resolved for.`
- `Example: The user edits "reviewer" to widen its tool allowlist. The two agents already running keep the narrower allowlist for the rest of their lives; the next run picks up the wider one.`
- `Example: A lead on one provider runs "reviewer", whose binding is for the other. The call raises the same approval any other tool call raises at that session's permission level. The daemon starts the reviewer on its own provider, the row appears under the lead with a mark of which provider is running it, the lead's wait returns the reviewer's answer, and the reviewer's spend appears on its own receipt row under its own paying account.`
- `Example: Nobody waits on a bridged agent for longer than one poll interval. The daemon closes the run and interrupts what it was doing, and the row says so.`
- `Example: The account a definition pins is removed. The next run under that definition refuses and names both the definition and the missing account; nothing starts and no current account is substituted.`

## Implementation Notes

- The registry is a natural home for later work this spec deliberately does not do — definition versioning, sharing across nodes, and per-definition budget ceilings are all expressible as additive columns rather than as reshapes.
- Because a run keeps the configuration it was given, the definition table is safe to edit under load: no reader of a running agent's configuration ever consults it.
- Because every invocation lands as an ordinary tool-activity row and an ordinary run, the session timeline is itself the record of which agent reached which peer and when — a capability that lets a running model start other runs is exactly the kind that should not be exercised invisibly.

## Pitfalls To Avoid

- **Do not make a running agent a live view of its definition.** It reads as a feature ("edit once, applies everywhere") and is an authorization hole: it widens a running agent's authority without an authorization act.
- **Do not treat `name` as an identifier.** A rename must not orphan references, and two nodes' identically-named definitions are unrelated records.
- **Do not conflate an absent tool allowlist with an empty one.** One means "the driver's defaults", the other means "nothing"; collapsing them either strips an agent of every tool or hands it all of them.
- **Do not store a composed execution posture in a definition.** Posture carries content-addressed policy references that are meaningful only against the session that composed them.
- **Do not fall back to the provider's current account when a pinned one is missing.** It converts a hard, legible refusal into a silent change of who pays and which identity acts.
- **Do not filter the bridge's verbs out of the registry by session state.** It reads as the safer choice and is not: the registry is composed at spawn only, so a filtered registry cannot reflect a change made while the session runs, and an operator who narrows or widens what the session permits sees nothing happen. Adjudicate per call through the ordinary approval pipeline instead, and keep the refusal legible.
- **Do not hold a bridged agent's state in the tool-server process.** A provider restarts that process under a live session, and the agent's work is then silently re-run from the start on the next call.

## Acceptance Criteria

- [ ] A definition can be created, listed, updated, renamed, and deleted; `definitionId` is stable across every update including a rename.
- [ ] Creating a second definition whose name differs only in letter case is refused, including a pair differing only in a non-ASCII case mapping, and including two such creates issued concurrently — exactly one commits.
- [ ] A run started under a `definitionId` matches the definition's configuration, and the response echoes the effective resolved configuration.
- [ ] A request carrying both a `definitionId` and an explicit field applies the explicit field for that field only, and echoes the merged result.
- [ ] Editing a definition leaves an agent already running from it byte-for-byte unchanged in configuration, and deleting the definition leaves it running.
- [ ] A run under a definition whose pinned provider account is absent refuses, names the definition and the account, starts nothing, and does not fall back to the provider's current account.
- [ ] A run under a definition whose tool allowlist the driver cannot realize refuses rather than spawning.
- [ ] A definition with an absent tool allowlist and one with an empty allowlist produce observably different spawns.
- [ ] All six bridge verbs are present in a session's callback-tool registry, and every call is adjudicated at call time by the session's existing approval pipeline in the `tool_execution` category, a denial answering on the callback-tool result's `denied` arm.
- [ ] A bridge call on a permission level that asks raises the same approval a tool call raises, a remembered rule answers the next one without asking again, and on a level that asks for nothing the call runs unprompted.
- [ ] An agent whose definition carries an empty tool allowlist receives none of the bridge's verbs.
- [ ] A peer invocation lands a `tool_activity` row and a timeline-visible run.
- [ ] On a Claude Code lead, a cross-provider agent is reachable only through its pack entry: the lead's own tool list holds no bridge verb, and a lead told to run that agent produces a row in the tree rather than calling the verbs itself.
- [ ] On a Codex lead, the tool server's own description lists every cross-provider agent by name, and the lead runs one by name with no stand-in role planted.
- [ ] `run` returns a handle without waiting for the work, and every `wait` returns inside the daemon's own cap even while the agent runs on.
- [ ] A run no wait has arrived for within one poll interval is closed and its provider-side work interrupted; a single long wait does not postpone that sweep.
- [ ] Restarting the tool-server process under a live session loses no handle and re-runs no work: the next wait answers from the daemon's own state.
- [ ] A message to a bridged agent that has already finished continues the same conversation rather than starting a second one.
- [ ] Steer and stop from the row reach the provider running the agent, and the agent that reached it learns the outcome on its next wait.
- [ ] A denied invocation is answered `denied` on the already-running leg, with no respawn required and no registry rebuild.
- [ ] A wait outstanding on an agent that fails, is cancelled, or finishes having produced nothing is settled by that terminal state rather than left waiting.
- [ ] A bridged agent's spend appears on its own cost-receipt row under its own paying account, and the row of the run that reached it is unchanged.
- [ ] Targeting a provider or a model rather than an agent is refused.
- [ ] Every refusal on the definition and resolution paths carries one of the five registered definition-plane `agent.*` codes, and none surfaces as a generic or untyped failure; every peer-invocation refusal arrives on a callback-tool result arm instead, carrying no code.
- [ ] A definition whose pinned account is registered but not currently authenticated resolves, and is refused by the spawn gate rather than by the resolver.

## ADR Triggers

- Making a running agent a live reference to its definition, or otherwise allowing a definition edit to change a running agent's authority, is an authorization-model change and requires an ADR.
- Sharing, syncing, or relaying definitions between nodes crosses this spec's node-local boundary and requires an ADR covering trust and provenance of a definition authored elsewhere.
- Minting a report-back channel by which a bridged agent pushes structured state into the run that reached it, beyond what the bridge's verbs return, adds an inter-run data path and requires an ADR.

- [Model Context Protocol specification, revision `2026-07-28`](https://modelcontextprotocol.io/specification/2026-07-28/) ([schema.ts](https://github.com/modelcontextprotocol/specification/blob/main/schema/2026-07-28/schema.ts)) — the revision the Claude leg's daemon-hosted server speaks. Two of its §Security and Trust & Safety rules are load-bearing here and are honoured rather than assumed: tool annotations "should be considered untrusted, unless obtained from a trusted server", which is why the bridge is daemon-constructed and daemon-trusted and is never sourced from a governed third-party binding; and "Hosts must obtain explicit user consent before invoking any tool", which the session's own approval pipeline supplies: the person sets the permission level, every bridge call raises the approval that level raises for any other tool call in the session, and the bridge adds no consent mechanism of its own beside it (§Availability and adjudication).
- MCP **elicitation** is a _client_ feature in that revision — a server-initiated request for information from the user — and is deliberately unused by the bridge: a peer invocation reaches another **agent**, never the human, so routing it through elicitation would put a second question in front of the user on a path whose one authorization is the approval the session's permission level already raises.
