## Purpose

Define the typed local control surface used by the desktop app's main process and the CLI to communicate with the local daemon. Renderer-originated traffic reaches the daemon through the main process via the preload bridge per [Spec-021 §Trust Stance](./021-desktop-app-and-renderer.md#trust-stance) — the renderer is not a direct daemon client.

## Scope

This spec covers transport choice, version negotiation, request and stream semantics, and daemon supervision controls.

## Non-Goals

- Remote relay transport
- Provider-driver internal protocols
- UI rendering behavior
- Network reachability configuration. There is no local-network switch, no private-network join, no coordination-server field, no approval link and no address to copy on this surface: how a machine is reached is the layer beneath it, and the only thing the product says about reachability here is whether the daemon is running. Beside the port a workflow started by a web request listens on, no other listening figure is set here either — no domain and no command to update one, no certificate or key path, and no check of a certificate — and that port is the one address this surface sets. The ports a person shares with their other devices are set on the Devices page ([Spec-027](./027-remote-control.md)), not here.
- Reading the diagnostic record back. This surface writes that record and never serves it back as a list: the diagnostic controls say what is written and where it is written, and no read here renders the contents — no recent-activity fold, no credential-attempt list, no audit view, no log viewer, and no viewer for the raw provider messages, which are written to the folder its switch names and read only by whoever opens that folder. The diagnostic controls are the whole of diagnostics; there is no diagnostics page of its own.
- A browser client of the local daemon. The desktop app and the CLI are its only local clients; the web client and the phone apps reach a machine only over the relay ([Spec-027](./027-remote-control.md)).

## Required Behavior

- The desktop app's main process and the CLI must use one shared typed client SDK. Renderer-originated traffic is brokered by the main process via the preload bridge per [Spec-021 §Trust Stance](./021-desktop-app-and-renderer.md#trust-stance) and reaches the daemon as JSON-RPC traffic the main process originates.
- The CLI must be treated as a first-class local client and the first delivery track for the typed daemon contract.
- **The service log is the daemon's own file.** The daemon writes each service-log line — a reading that failed, a shell that hung at start, a drain's result — to its standard error and to `logs/service-<start time>.log` in its data folder, a file it opens at start, readable by the person alone. Once standard error's reader is gone, the lines go to the file alone, and the file says so once; a file that cannot be opened leaves standard error carrying the log, which says so once. Neither stops the daemon. Whoever started it — the desktop app with its standard streams detached, the CLI, the per-user service, the Windows half — needs to capture nothing for the log to be kept. The file is a diagnostic log, deleted whole once past `Keep diagnostic logs for` and with the data folder by `Erase all data` ([Spec-018 §Required Behavior](018-observability-and-failure-recovery.md#required-behavior)).
- The local daemon must expose a typed request-response and subscription contract for session, run, repo, artifact, settings, and daemon lifecycle operations.
- A subscription delivers changes in frames rather than one message per change: at most 50 events or 16 ms of them to a frame, whichever comes first, the window opening on the first event so nothing waits longer than it, and every change in a frame carrying its own cursor. A consumer that falls behind is not waited for. The daemon drops for it, marks the gap on the next frame that fits, and the consumer repairs by reading again from its cursor — taking a snapshot read past the gap where the gap is further back than the record can fill — so a consumer is never silently short and a slow reader never holds the daemon up. When a consumer that fell behind has caught up on its queue, the daemon sends it one frame with no changes, carrying the drop mark and the newest cursor, so a subscription that goes quiet right after a drop still tells its consumer that it is behind. [Plan-005 §Phase 2D](../plans/005-local-ipc-and-daemon-control.md#phase-2d--substrate-supplement-the-subscription-frame-is-batched-carries-changes-only-and-never-waits-for-a-consumer) builds the frame.
- The default local IPC transport must be OS-local:
  - Unix domain socket on Unix-like platforms
  - named pipe on Windows
- **A stop is answered at once and bounded on both sides.** The service answers `daemon.stop` at once and then waits at most its drain bound for the writes already in flight, beside its terminal drain. The caller — main, the CLI or the Windows half — waits at most 10 seconds for `daemon.flush`, sends the stop and counts the drain bound from that send; a daemon still running after it gets SIGTERM and, 2 seconds later, SIGKILL. A stop that goes unanswered gets SIGTERM at once and SIGKILL once the drain bound and 2 seconds have passed, so a hung service never holds the caller.
- **The socket path has a hard length limit, so the daemon's run directory is short by design.** A Unix domain socket address is a fixed-size field in the operating system's own structure — the `sun_path` field of `sockaddr_un`, 104 bytes on macOS, 108 on Linux (`unix(7)`, read 2026-09-21) — and it is not a path the platform will truncate or redirect: a path past the limit simply cannot be bound. The failure is also badly reported by at least one client library above it, which surfaces it as a malformed address rather than as a length, so a caller reading the message looks for a typo in a path that is spelled correctly. The daemon therefore keeps its run directory short enough that the socket fits with room for the file name, and where it is handed a longer one it **refuses to bind and says the path is too long for a socket on this platform**, naming the limit and the length it was given, rather than passing the platform's own message through.
- Local IPC must support protocol version negotiation before mutating operations are accepted.
- The desktop app's main process must be able to start, supervise and reconnect to the daemon, and it stops or restarts it only when the person presses `Stop` or `Restart`. The daemon is never the app's child process: main spawns it detached, or, where a detached process does not outlive the app, starts the per-user service the install registered; on a Windows computer whose service runs in WSL, starting it is running its per-user task (§The service on a Windows computer). Main checks the link with `daemon.ping` only after 5 seconds with no frame from the daemon, and after 20 seconds with no frame counts the link as dead and reconnects.
- The daemon must resolve the calling connection's device from the transport and make it available to every handler it dispatches, so a write records the device it came from. Nothing checks ownership: no handler authorizes a read or a write by a person's identity. The device is a dispatch-context fact and never a wire field, so no request schema gains a member for it and a caller-supplied one is never trusted.
- The daemon outlives its clients. Quitting the desktop app flushes the daemon (`daemon.flush`) and nothing more: the service, every session, every run and every shell on that machine keep running, and the app reattaches to them when it opens again. Only Runtime's `Stop` and `Restart`, and the CLI's `sidekicks daemon stop` and `restart`, end work in flight. No surface explains this, and no surface claims where the work runs.
- `sidekicks daemon status` must report whether the daemon is up, since when, and which workspace it holds, in its text output and in `--json` alike. While a relay is configured it carries one further block: each linked device by name, whether it is connected, the age of the last frame out and of the last frame in, the reconnect count and the rejected-frame count. With no relay configured the block is absent — never printed empty and never printed disabled. Its fields follow the relay wire [Spec-027](./027-remote-control.md) defines, and the block adds no command, no exit-code path, and nothing to any screen.
- The CLI must be able to run the daemon as a background service of the person's own account — `sidekicks daemon install`, `uninstall`, `start`, `stop`, `restart` and `status` — and `sidekicks daemon install` alone installs and starts it, so a machine with no desktop is running after a single line. `uninstall` removes whatever the install registered and keeps the person's data. On every platform the service comes back after a reboot. Whether it keeps running after the person logs out depends on the platform:
  - **macOS:** a per-user login agent, which starts at login and stops at logout.
  - **Linux:** a user service, and the install turns lingering on (`loginctl enable-linger`, which systemd's own polkit policy allows with no password from any session, SSH included; with no polkit daemon running the install refuses and says so), so the service keeps running after logout, while the Secret Service keeps the service's credential-store items locked until the person logs in again ([Spec-020 §Daemon Secrets](./020-data-retention-and-gdpr.md#daemon-secrets)).
  - **Windows:** the service starts at login by default, and `sidekicks daemon install --while-signed-out` adds the administrator-installed service, which keeps it running while the person is signed out. On a Windows computer whose service runs in WSL the same flag means the same thing through a different mechanism (§The service on a Windows computer).
- At each start on macOS, on Linux and inside a WSL distribution, the daemon runs the person's login shell once, with no input and a 5-second deadline, and keeps the environment it prints between two markers as the base every provider's environment is built from, so proxy, certificate and locale settings are there with no terminal open and a provider installed after the install is found. A shell that misses the deadline or prints no markers is ended, the start goes on with the account's default environment, and the service log says why; the service never waits on a shell. A stop that arrives during the start ends the shell too, and the daemon stops as soon as it has started, without writing its ready line. Inside a distribution, provider binaries under the Windows drive mounts are ignored: a Windows `claude` or `node` reached through `appendWindowsPath` fails with Claude Code's documented "exec: node: not found". On Windows the service starts with the account's own environment.
- A session that cannot start because its provider is not installed where the service runs is refused with one flow row naming that provider, which opens Settings › Providers on that provider's section, on every platform; the row is drawn from the session notice of kind `provider_missing`, and [Plan-001](../plans/001-session-core.md)'s session start owns the refusal.
- `sidekicks self-update` checks for a newer release of the background service and applies it down the same path Settings › Runtime's `Update the background service` uses, so the app and the CLI can never disagree about which version is current. It updates the service only and says that the app updates from General. Like that button, it waits for running work to finish, naming it, rather than stopping it. On an install a package manager made, it replaces no file behind that manager and names the manager's own update command instead. `sidekicks self-update --check` only reports: it exits `0` when this machine is up to date, `100` when an update is waiting and `1` when it could not check; a crash also exits `1`, so `1` never means an update is waiting.
- Signing in to and out of the product's hosted account is one CLI verb each, `sidekicks sign-in` and `sidekicks sign-out`, and either is refused while the daemon holds the data directory, naming `sidekicks daemon stop` or Runtime's `Stop`. The daemon holds the data directory through an exclusive SQLite lock on a small lock file, taken at start and held for its whole life; both verbs try that lock without waiting, so the refusal is immediate. What signing in means — the ceremony, the credential it produces and the state it leaves behind — belongs to [Spec-016 §Required Behavior](./016-hosted-account-and-identity.md#required-behavior); what this surface owes is the verbs and that refusal.
- Machine-wide daemon configuration is read and written through this surface, one place per value and no second one: how long diagnostic logs are kept, how long finished sessions are kept, the port a workflow started by a web request listens on, the time limit after which a run is ended, how many runs one start may lead to before the next one waits for the person, the memory cap for tool processes, `Max steps per turn`, `Spend limit`, `Tokens per run`, the package caches' limit, and the two diagnostic switches — recording traces, and recording raw provider messages, which names the folder it writes to. Several carry a shape of their own: the run limit is no limit by default and is otherwise `30 minutes`, `1 hour`, `4 hours`, `12 hours` or `24 hours`; the run count one start may lead to is `100 runs` by default and is otherwise `25 runs`, `500 runs`, `2,000 runs` or `Never ask`; the memory cap is empty until a size is given, and empty means no cap; `Max steps per turn` reads `Unlimited` by default, which is what both providers do on their own, and carries one line saying what the number bounds and that a session can set its own number in its inspector; empty is `Unlimited` and a number of 1 or more is that many, and anything else, `0` included, is refused under the field with `1 or more, or empty for unlimited` — a number typed here governs sessions started later and reaches a session already running at its next turn, and `Unlimited` puts the providers' own behavior back, what the bound does and how each provider realizes it being [Spec-003 §The Step Bound On A Turn](./003-queue-steer-pause-resume.md#the-step-bound-on-a-turn)'s and the per-session override's own write being [Spec-001 §Interfaces And Contracts](./001-session-core.md#interfaces-and-contracts)'s; `Spend limit`, in dollars for a whole session, and `Tokens per run` each read `Unlimited` by default and are what every new session starts from, a session setting its own in its inspector, what each limit does being [Spec-014 §Budget Policies](./014-multi-agent-orchestration.md#budget-policies)'s; the package caches' limit reads `Unlimited` by default, under which the daemon never clears a cache on its own, and otherwise takes a size, what the caches hold and when they are cleared being [Spec-015](./015-workflow-authoring-and-execution.md)'s; and both diagnostic switches are off until they are turned on. Each value's own policy belongs to the spec that owns it: the diagnostic-log bound to [Spec-018 §PII in Diagnostics](./018-observability-and-failure-recovery.md#pii-in-diagnostics), the finished-session bound to [Spec-020 §Retention Policy](./020-data-retention-and-gdpr.md#retention-policy). What this surface owes is that the value is set in one place, that a value the operating system will not let the daemon enforce says so where it is set, and that a refused value — something that is not a port, something that is not a size — is refused in place with nothing written and the field left as it was; a port already taken is answered the same way, saying that nothing is listening, and the daemon never moves to another port of its own. [Plan-005 §Phase R1](../plans/005-local-ipc-and-daemon-control.md#phase-r1--namespace-handlers) builds the configuration and retention verbs.
- One of the two retention bounds acts on its own and one does not. Past its bound the daemon drops its own diagnostic logs; that control sets only how long, and it is not a switch that turns deletion on or off. A workflow run's step data and its snapshots stay until the person deletes the run or its session. A finished session is never removed on its own: its bound only makes it eligible, and it goes only through `Delete old data`, the one operation on this surface that deletes sessions, which asks first, names what goes and what stays, and cannot be undone ([Spec-020 §Required Behavior](./020-data-retention-and-gdpr.md#required-behavior)). Setting a value deletes nothing at the moment it is set, and no bound reaches a worktree the person kept, which goes only on that worktree's own `Delete now`. Every job the service runs in the background — that expiry, backups, the package caches' limit, the update check — runs on its one scheduler, never on a timer of its own. The retention verbs are this surface's, built with the rest of the service's control surface.
- The folders this machine can reach are read and changed through this surface: the list, each folder's row with what is using it, and each worktree the app made listed beneath its project's folder and marked `worktree` — marked when the app makes it, so a worktree the person made is never claimed. Removing a project's folder is the Projects page's delete under the same rule: refused while an agent runs anywhere in the project, naming the running session ([Spec-002 §Required Behavior](./002-machine-registration.md#required-behavior)). Removing a worktree the app made follows the worktree's own removal rules through `repo.worktreeRetire {worktreeId, discard}`. Beneath its project's worktrees, each worktree kept by `Discard and remove` has one row with its size, `Put back`, which recreates the worktree at its own path, and `Delete now`, the only act that deletes it ([Spec-008](./008-worktree-lifecycle-and-execution-modes.md)). A chat's session workspace has no removal of its own: it goes whole only when its session is deleted through `Delete old data`. A read with no folder mounted answers an empty list rather than an error, and the surface showing it says so rather than drawing an empty table.
- **What the daemon brings back first.** Where a shared Codex service was running — the provider's own `codex app-server --listen unix://<control socket>`, which terminal Codex sessions join ([Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other)) — the daemon starts that service again on the same socket before anything else it restores, so a terminal Codex session attached to it reattaches by itself — a session whose service is back within about five seconds reconnects on its own, and one is given up on at about twenty-four — and never notices the restart ([Codex wire reference §The shared `app-server` a terminal `codex` joins](../reference/provider-wire/codex.md#the-shared-app-server-a-terminal-codex-joins), measured 2026-09-21 at `0.155.1`). A session that has been without its service for longer than that window has given up and is not recovered by the daemon at all: it is the person's own process, and what brings it back is the provider's own resume ([Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other)). The restart order is [Plan-005 §Phase R1](../plans/005-local-ipc-and-daemon-control.md#phase-r1--namespace-handlers)'s, the shared service itself [Plan-003](../plans/003-provider-driver-contract-and-capabilities.md)'s.
- The daemon's own supervision facts are read by the surface that shows them and edited nowhere: whether it is running and since when, its version, and how much of the machine's processor and memory it is using — each reading stamped with the time it was taken and taken again only when it is asked for, never sampled on a timer. Until the first read answers, the surface says it is reading, and a figure not read yet says so rather than showing a number. On a Windows computer whose service runs in WSL, the processor and memory figures are the service's own processes and nothing else; the WSL virtual machine is not counted (§The service on a Windows computer).
- Stop and restart are the two supervised controls; each confirms before it acts and each says that work in flight on this machine stops. Where terminal Codex sessions are inside the shared Codex service, the stop confirmation adds one line counting them, read through `session.terminalProviderSessionList`, and says how to use one again, because stopping the service strands them until the person runs the provider's own resume ([Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other)). The restart confirmation names none: the restart brings the shared service back first, within its window, and they reconnect on their own.
- The daemon is updated separately from the desktop app, and an update never stops work. While any session, workflow run or terminal Codex session is working, the update waits and names that work on one line, its parts joined by `·` — the sessions and runs by their titles, at most three, then `and N more`, then the terminal Codex sessions as a count — and each title opens its session or run so it can be finished or stopped from there. It offers a cancel while it waits and until the app asks the old service to stop, since a cancel after that request cannot be honored. It shows the step it is on and settles by naming the version it came from and the one it reached, or both versions and the reason where it rolled back, or that this machine is already at the newest version. The stop, restart and status verbs are [Plan-005 §Phase R1](../plans/005-local-ipc-and-daemon-control.md#phase-r1--namespace-handlers)'s; the update's steps, wait, cancel and outcome are the service's update path ([Plan-005](../plans/005-local-ipc-and-daemon-control.md) T-005r-3-6), one module both clients import, which Runtime drives through the main process ([Plan-020](../plans/020-desktop-app-and-renderer.md) T-020r-4-1) and `sidekicks self-update` drives from the command line.
- While any agent works and the machine's keep-awake switch `keepAwakeWhileAgentWorks` is on (it is off by default and lives in the machine's settings file), the daemon holds the machine and its screen awake through each platform's own tool, tied to the daemon's own process: `caffeinate -d -i -w <daemon pid>` on macOS; on Linux `systemd-inhibit --what=sleep:idle --mode=block` held until the daemon exits, plus the screen saver's inhibit, `org.freedesktop.ScreenSaver.Inhibit`, held on the daemon's own session bus connection and released when that connection closes; on Windows the service's Windows half calls `SetThreadExecutionState` and holds it for as long as its channel to the daemon is open. The hold outlives a quit of the app and ends when the service stops. The second keep-awake switch in the same file, `keepAwakeForOtherDevices`, also off by default, holds the machine awake while it is on and the machine is on power ([Spec-027](./027-remote-control.md)). No platform's hold stops a sleep the person asks for, such as closing the lid, and each switch says so.
- `sidekicks open <address>` hands a `sidekicks://` address to the running app, or to the app the platform starts for it, through the platform's own link handler, and calls no daemon method. The address is checked by the one `sidekicks://` parser that the app's `Copy link` and its link handler also use; anything else is refused with a usage line.

### The service on a Windows computer

On a Windows computer a person may keep Claude Code and Codex inside a WSL 2 distribution, such as Ubuntu, rather than on Windows. The background service then runs where they are. The decision and its alternatives are [ADR-039](../decisions/039-the-service-on-wsl-2.md).

- **One service per computer, on the providers' side.** The service runs on Windows or inside one WSL 2 distribution, never both. At first launch it is placed with no question: where both providers are found, else where one is, else on Windows; a WSL 1 distribution is never chosen, and between two WSL distributions that tie, the one WSL marks as its default wins once and the choice is then kept. Where the place it lands on has neither provider, the service starts there all the same, and the flow row a session that cannot start for that reason draws, its `provider_missing` notice carrying `placeHasNeitherProvider`, reads `Choose where Claude Code and Codex are installed` and opens Providers' place row. The place is changed on Settings › Providers, or with `sidekicks daemon install --windows` or `--wsl <distro>` and `sidekicks daemon move --windows` or `--wsl <distro>`, which name the place because the place is their subject. Settings › Providers is the only screen that names a side or a distribution, and only where the place is its subject; every other line says what failed and what to do, and where the way out is a WSL setting it names that setting, never the side the service runs on.
- **Discovery.** WSL is present when `%SystemRoot%\System32\wsl.exe` exists (`Sysnative` for a 32-bit caller), and every run uses that absolute path. `wsl.exe -l -v` lists the distributions, decoded as UTF-16LE, under a 5-second deadline; WSL 1 rows are shown and marked as needing WSL 2, and Docker's and Rancher's own distributions are hidden. A distribution's providers, with their versions, and its C library are found by one run of the person's login shell inside it, which ignores anything under the Windows drive mounts; the Windows half's `scan` runs it in every WSL 2 distribution at once when the place list opens and once at first launch, for the placement, never on a timer. A musl-based distribution such as Alpine is listed like any other. Discovery and the install into a distribution are the Windows half's, run one-shot by main and the CLI before any service exists, so discovery has one implementation.
- **Two processes on WSL.** Inside a distribution the service is the daemon, the same Linux runtime a Linux computer runs, and the service's Windows half, a small native Windows program that holds WSL open, serves Windows clients their named pipe, keeps the service's credential-store items in Windows' Credential Manager, and does the Windows-only jobs while the app is quit. On native Windows the daemon runs the same Windows half as its own child (`--daemon-child`), so every Windows-only job has one implementation on both kinds of Windows computer. The Windows half is never named on screen.
- **Start and lifetime on WSL.** A per-user logon task, `\AI Sidekicks\Background service`, registered by `sidekicks daemon install` at the person's normal privilege, runs the Windows half; the Windows half runs `wsl.exe --cd ~ -d <distro> --exec <home>/.ai-sidekicks/runtime/sha256-<digest>/bin/sidekicks-daemon --windows-half-stdio`, created suspended and with no window inside a Job that ends `wsl.exe` when the Windows half ends and lets every Windows program started through interop leave, so a window an agent opened survives a service stop. The daemon is ready when its ready line arrives within 10 seconds. Its standard error is drained and thrown away for the process's whole life, so the pipe never fills — the daemon writes its own service log file; its standard output carries only the ready line and then the channel. That one attached `wsl.exe` keeps the distribution and the WSL virtual machine running for the service's whole life; the person's `.wslconfig` is never edited. A daemon that exits unexpectedly is started again with the supervisor's backoff (100 ms, 300 ms, 1 s, 3 s, 10 s); after the fifth failure the Windows half stops trying and records the error word for word. A daemon whose input ends or whose output write fails stops itself, because killing `wsl.exe` sends it no signal. A stop is `daemon.flush`, then `daemon.stop`, then a wait of up to the service's drain bound (4 seconds: 2 for its terminals, 2 for the terminal host) for the daemon's process inside the distribution to exit, and only if it still runs the terminate signal to it, then a kill 2 seconds later; never `wsl --terminate` or `wsl --shutdown`, which would take the person's own work with it. Only one daemon runs per person at a time: every start, the native Windows start included, takes the per-user mutex `Global\ai-sidekicks-service-<user SID>`, created with a user-only access list, where `ERROR_ACCESS_DENIED` on its create means another program holds the name, as on the pipe; and a move stops the old side before the new one starts.
- **Sign-out.** A WSL instance ends with the Windows session that made it, so a service the logon task started stops when the person signs out: the Windows half answers Windows' end-of-session query at once, sends `DaemonStop`, waits about 4 seconds inside the 5 Windows allows, and exits. The stop is crash-safe on its own, because every SQLite commit is already durable and a turn in flight resumes from the provider's own conversation file at the next start. The task starts the service again at the next sign-in.
- **Running while signed out.** `sidekicks daemon install --while-signed-out` adds a second task, `\AI Sidekicks\Background service (signed out)`, set to run whether the person is signed in or not, triggered at logon and at startup, and restarting on failure like the logon task. Its password is typed into Task Scheduler's own prompt and kept there; the app never reads, stores or passes it. Whichever instance of the Windows half holds the mutex is the service; the logon task's instance then takes the desktop role (`--desktop`), connecting over the pipe to post and withdraw banners, and ends with the session. While the person is signed out, a moment that would post a banner reaches the phone by push and waits for the desktop role to post it at the next sign-in. When the Windows password changes, Task Scheduler's copy no longer works: at the next sign-in the logon task's instance runs the service itself and Runtime reads `The background service no longer runs while you are signed out, because your Windows password changed. Run sidekicks daemon install --while-signed-out again.` This ships only if a Windows machine shows that such a task holds WSL, Credential Manager, the pipe, keep-awake and the wake timer with no one signed in; if it cannot, the flag refuses on a WSL computer, naming the way that works (the providers installed on Windows, `sidekicks daemon move --windows`, then the flag again), and Runtime reads `On this computer the background service runs only while you are signed in to it.`, naming no side. On native Windows the same flag adds the administrator-installed service.
- **Reaching the daemon from Windows.** Windows clients reach the daemon through one per-user named pipe, `\\.\pipe\ai-sidekicks-<user SID>`, the same on both kinds of Windows computer, so a client never needs to know the side. The server fails closed: it creates the pipe with an access list that grants the person alone, refuses remote clients (`PIPE_REJECT_REMOTE_CLIENTS`), and creates the first instance with `FILE_FLAG_FIRST_PIPE_INSTANCE`, treating `ERROR_ACCESS_DENIED` there as another program holding its name — it refuses to serve, records why and exits. It also checks each accepted client's process belongs to the person. The client fails closed: main and the Windows CLI open the pipe at identification level (`SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`) through the client SDK and check that the pipe's owner is the person before writing a byte. On WSL each accepted client is one stream on one HTTP/2 channel over the attached `wsl.exe`'s standard input and output, handed to the same connection handler a Unix-socket client gets. The daemon still demands its token first: on Windows the token is `%LOCALAPPDATA%\ai-sidekicks\run\daemon.token`, written with a user-only access list at every daemon start and read by clients at every connect. The service binds no TCP port for its clients on either side, so the OS-local default above holds and no loopback is involved.
- **Dropped files on WSL.** Files dropped on the composer are staged to the daemon as bytes ([Spec-012 §Ingest Validation And Payload Bounds (V1)](./012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1)), so no path crosses: where the service runs inside a WSL 2 distribution, the main process reads the file behind the dropped file's token and stages its bytes; everywhere else the dropped file reaches the daemon by its path token.
- **Why it cannot start.** Every `wsl.exe` the Windows half starts has a deadline (10 seconds to start the service, 5 to list, 30 to check a distribution's providers). After two missed deadlines with no success between them it marks WSL as not responding and starts no more until the machine wakes or an hour passes. It writes `%LOCALAPPDATA%\ai-sidekicks\run\service-status.json` when its state changes, never on a timer. When the pipe is absent, main and the Windows CLI check the mutex and read that file, so Runtime and `sidekicks daemon status` say why the service cannot start instead of `The background service is not answering.`, in lines that name no side: WSL not responding, `The background service cannot start. Restarting Windows brings it back.`; restarts used up, `The background service stopped and could not start again. Restarting Windows usually brings it back.`, with the error it gave under it, word for word; the place gone, `The background service cannot start because the Claude Code and Codex it used are no longer on this computer. Choose where they are installed in Settings › Providers, then restore your latest backup here.`, whose act opens Providers' place row; and its connection name taken by another program, `The background service cannot start because another program on this computer is using its connection. Restarting Windows usually clears it.` Where the mutex is free the Windows half is gone, so main runs the task at once and says `Starting the background service…` meanwhile.
- **Uninstall on WSL** stops the service and removes both tasks, the Windows half's folders, the runtime folders and the `sidekicks` link in the distribution, the token and status files and the place record, and keeps the store, the account homes, the agent memory, the worktrees, the backups and the credential entries, as uninstall does everywhere.
- **Moving to the other side.** Picking another place confirms in place, under `Cancel` and `Move`: `Use the Claude Code and Codex in Ubuntu? The background service restarts there, so work in flight stops. Your sessions, sidekicks and what they remember, workflows, settings and signed-in accounts come along. Project folders stay where they are.` Two lines are added only where they apply: Stop's count of the terminal Codex sessions inside the shared Codex service, and `2 tool servers run a Windows program and need setting up again in Ubuntu.` when a tool server's command or arguments name a program on the side the service leaves. Once confirmed, or on `sidekicks daemon move`, the move installs the new side while the old one runs, stops the old one as `Stop` does, copies the move set, rewrites its paths, starts the new side, reconnects worktrees and settles. The switches that write into the person's own provider files follow the service: with the terminal-plugin switch on, its plugin and setting are removed from the old side's Claude Code and added on the new side's where Claude Code is installed there, and the shared Codex service runs on the new side's own Codex folder. The move set is the database, the machine settings file, each chat session's workspace, each kept session's checkpoint copies, the agent memory folder, and every account home whole; each account's sign-in file is moved, never copied, and only after the old side has fully stopped, so two live copies never exist. The new side's account homes are written into fresh folders, so no credential from an earlier stay on that side survives a move back. Project folders, worktrees, each workflow version's code folder, the package caches, the credential-store items in Windows' Credential Manager and backups stay where they are. A data path crosses with `wslpath`; a program path never crosses and reads as broken in place. Worktrees are repaired with git's own `git worktree repair` after the new side's first good start and locked when they sit on the other side's disk. The progress is one row over a bar on Providers: `Installing in Ubuntu` · `Stopping the background service` · `Copying your work · 1.2 GB of 3.4 GB` · `Starting in Ubuntu` · `Reconnecting worktrees`; `Cancel` holds until the old side is asked to stop. A settled move reads `Your sidekicks now use the Claude Code and Codex in Ubuntu.` A failure before the settle puts everything back — each account's newest sign-in file first — and starts the old side, and the row reads `The move did not finish: <reason>. Nothing changed; your sidekicks still use the ones on Windows.` with `Try again`. If part of the undo fails, the line says what was not put back instead of `Nothing changed`, still naming the side in use: `The move did not finish: <reason>. Your sidekicks still use the ones on Windows, but 2 worktrees could not be reconnected; Runtime lists them.`, with the same `Try again`, and those rows carry git's own reason. The machine's identity key and channel key stay in Windows' Credential Manager and its registration rides the store, so the computer stays one machine and linked devices reconnect with no new link.
- **Backups on WSL** default to the Windows home's `.ai-sidekicks\backups`, reached from the distribution through the drive mount, because unregistering or resetting the distribution deletes its disk with the store on it. A backup made on one side restores on the other.
- **The Linux runtime on Windows.** The Windows installers carry the Linux runtime archives, glibc and musl, for the installer's architecture, as the standalone Node.js bundle a Linux machine downloads. The service installs the archive for the distribution's C library into `~/.ai-sidekicks/runtime/sha256-<digest>/`, keeping the current folder and the one before it. Compatibility is the `DaemonHello` negotiation, not identical bytes; an app carrying a newer runtime than the one running shows Runtime's `Update the background service`, which waits for running work; if a new runtime sends no ready line within 10 seconds or fails the handshake, the Windows half starts the previous folder again and the update names both versions and the reason.

## Wire Format

- The wire format is JSON-RPC 2.0 with LSP-style Content-Length framing (not newline-delimited). Each message is preceded by `Content-Length: <byte-count>\r\n\r\n`.
- Maximum message size: 4 MB, sized to the largest request the connection carries plus its envelope (a message at Codex's own limit). It is the transport's bound, never an on-screen limit.
- Maximum request `id` size: 256 bytes once JSON-encoded. The `id` is opaque to the substrate and echoed verbatim, which makes it the one member of a response the caller sizes; an id past the bound is refused as `-32600 Invalid Request` **before dispatch**, and the refusal — like every error frame for an envelope whose id could not be recovered — carries `id: null` rather than echoing the offending value, per JSON-RPC 2.0 §5. Refusing the request is the only place the rule can be enforced: an oversized **response** cannot carry its own error, so the alternative is a closed connection on a request the daemon accepted.
- Every request (except health checks) must include a `protocolVersion` field carrying an ISO 8601 date-string in `YYYY-MM-DD` form (per [API Payload Contracts](../architecture/contracts/api-payload-contracts.md)).
- Serialization: JSON via `JSON.stringify`/`JSON.parse`. No binary serialization.
- The client SDK in `packages/client-sdk/` wraps JSON-RPC in a thin typed Zod layer, following the MCP TypeScript SDK pattern.

## Default Behavior

- Desktop app default is auto-connect to the local daemon through OS-local IPC.
- If the daemon is not running, the desktop app's main process starts it — a detached spawn, the per-user service the install registered, or on a WSL computer the per-user task — under one cover that reads `Starting the background service…`, before the renderer gives up.
- CLI default is connect to the same typed local daemon contract rather than reimplement daemon logic inline.
- The first implementation release of the local control surface is CLI-first, with the desktop app's main process consuming the same stabilized contract afterward. The renderer consumes the preload bridge API per [Spec-021 §Trust Stance](./021-desktop-app-and-renderer.md#trust-stance), not this daemon contract directly.

## Fallback Behavior

- If version negotiation fails, read-only compatibility may continue, but mutating operations must be blocked until versions are compatible. Each app accepts its own service version and the one before it. Outside that window the console is read-only, and the session's working line names in words the side that is behind — the background service or the app — with a press that opens its fix: the service's update on Settings › Runtime or the app's update on General.
- If the daemon cannot be started automatically, the client must return actionable status instead of hanging.
- While the daemon is unreachable or reconnecting, the client retries and says so in exactly one place rather than hanging, and it offers an explicit retry. Nothing already read is emptied, dimmed, or disabled: a list that could not be refreshed says only that, a draft keeps its text, and no open surface closes. The reading arms only once the daemon has answered at least once since the client started, so a client started into an outage reports a daemon that would not start rather than a connection that was lost. In the console that one place is the session's working line ([Spec-018 §Required Behavior](./018-observability-and-failure-recovery.md#required-behavior)).

## Interfaces And Contracts

- `DaemonHello` and `DaemonHelloAck` must perform version negotiation. The reply carries `deviceId`, the connecting device's own id, so a client can tell its own hold on a shell from another device's.
- `DaemonStatusRead` (`daemon.status.read`), `DaemonStop` (`daemon.stop`) and `DaemonRestart` (`daemon.restart`) must exist as IPC methods. Daemon **start** is not one: a stopped daemon has no IPC server to receive a call, so starting is a process launch — `sidekicks daemon start`, or the desktop app's main process per §Default Behavior, spawning the daemon detached, starting the per-user service the install registered, or on a WSL computer running the per-user task — which then awaits `DaemonHelloAck`. See [Plan-005 §Phase R1](../plans/005-local-ipc-and-daemon-control.md#phase-r1--namespace-handlers) for the methods and [§Phase R3](../plans/005-local-ipc-and-daemon-control.md#phase-r3--client-delivery) for the CLI's start.
- `LocalSubscriptionConsumer<T>` must support event streams that catch up, then follow, where appropriate.
- `DaemonStatusRead` must carry everything a status surface prints, in one response rather than several reads: whether the daemon is up, since when (`startedAt`), the workspace it holds, its `version`, and its processor use (`{percent, readAt}`) and memory use (`{residentBytes, readAt}`), each `null` until it has been read, and `secretsFile`, the path of the file it keeps its secrets in, present only on Linux where no Secret Service answers ([Spec-020 §Daemon Secrets](./020-data-retention-and-gdpr.md#daemon-secrets)) — plus, while a relay is configured, the per-device relay block §Required Behavior describes, its counts running since the service started. It also carries a relay pin the daemon refused. The CLI's text output and its `--json` output are two renderings of that one response.
- The desktop app's main process exposes the daemon's typed surface to its renderer as one generic call and one generic subscribe rather than a bridge member per verb, so a method the daemon registers reaches the renderer with no new bridge member added; the renderer still holds no daemon connection of its own per [Spec-021 §Trust Stance](./021-desktop-app-and-renderer.md#trust-stance). The web client and the phone apps run the same front end through the same bridge interface, implemented over the relay ([Spec-027](./027-remote-control.md)); a member that host cannot serve is absent there rather than refusing.
- The service's own control surface, each verb once and none a second place a value already set here can be set. Each is a [Plan-005](../plans/005-local-ipc-and-daemon-control.md) task unless another plan is named.
  - `daemon.flush` — the main process's quit call: the daemon writes what it holds and stops nothing.
  - `daemon.ping` — the main process's liveness check, sent only after 5 seconds with no frame from the daemon; after 20 seconds with no frame the link counts as dead.
  - `daemon.retentionRead` — the retention bounds, with the counts `Delete old data` would remove on the same reply; `daemon.retentionUpdate` changes one bound; `daemon.retentionPurge` is `Delete old data`, the one purge, which deletes each session's rows with SQLite's `secure_delete` on, so the freed pages hold nothing readable, checkpoints the write-ahead log with `TRUNCATE` once the delete commits ([Spec-020 §Required Behavior](./020-data-retention-and-gdpr.md#required-behavior)), and starts a backup run once it is done.
  - `daemon.configRead` and `daemon.configUpdate` — the listener port, the run limit, `workflowChainAskAfterRuns` (a number of runs, or `null` for `Never ask`), `Max steps per turn`, `Spend limit`, `Tokens per run`, the tool memory cap, the package caches' limit (`null` for `Unlimited`), and the diagnostic switches, one member changed per call.
  - `daemon.packageCacheRead` → `{bun: {bytes, readAt}, uv: {bytes, readAt}}`, read only when asked, and `daemon.packageCacheClear {cache: bun | uv | all}`, answered with the new reading; what the caches hold and when a limit clears one are [Spec-015](./015-workflow-authoring-and-execution.md)'s, and [Plan-014](../plans/014-workflow-authoring-and-execution.md) builds them.
  - `session.terminalProviderSessionList {}` → `{sessions: TerminalProviderSession[]}`, each `{provider, name, threadId, state: working | idle | unreachable}` — the provider sessions a person typed in a terminal, inside that provider's shared service, read when the stop confirmation opens and while an update waits; [Spec-014](./014-multi-agent-orchestration.md)'s, built by [Plan-013](../plans/013-multi-agent-orchestration.md).
  - The update, on the main process's own supervisor bridge rather than the daemon: `daemon.requestUpdate()`, `daemon.cancelUpdate()` and `daemon.subscribeUpdate(handler)`, whose deliveries carry `step` (`checking | downloading | verifying | waiting | restarting`), `percent` while `downloading` (0 to 100, the bytes received against the release's size), `waitingOn` (the named work while it waits), `cancelable` (false once main has asked the old service to stop) and, at the end, `outcome` (`landed` or `rolled-back` with both versions, the latter with its reason, or `already-newest`). They run in main because the daemon refuses to replace its own program while connections are open. [Plan-020](../plans/020-desktop-app-and-renderer.md) builds them.
  - The command line: `sidekicks daemon install` (with `--while-signed-out`), `uninstall`, `start`, `stop`, `restart` and `status`; `sidekicks sign-in` and `sign-out`; `sidekicks self-update` (with `--check`); `sidekicks open <address>`.
  - The daemon's own processor and memory readings, and the read that takes them again, ride the status read above rather than a verb of their own.
- The service's backups, crash reports and data acts. Each is a [Plan-005](../plans/005-local-ipc-and-daemon-control.md) task, and what each act does to the data is the named spec's.
  - `daemon.backupRead` → the last run, the folder, the total size, and each backup with its time, its size and the app version that wrote it; `daemon.backupStart` runs one now. The daily run is off until the person turns it on, runs on the service's scheduler at the first moment of the day with no turn running, and never stops or delays work. Each run ends in `backup.completed` or `backup.failed`, and a restore in `backup.restored`, on the daemon's own sentinel session. What a backup holds and how long copies are kept is [Spec-013 §Backup Policy](./013-persistence-and-recovery.md#backup-policy)'s.
  - `daemon.crashList` reads the crash reports this machine keeps, from `sidekicks crash list` and from a linked device. Reports never leave the machine that crashed; each holds the process type, both versions, the platform and the crashing thread's stack as module names and offsets, with file paths cut to their names and session ids replaced by stable hashes, and goes with the diagnostic logs.
  - The command line's data verbs, each doing what its Settings action does: `sidekicks export-data <folder>`, which runs with the service running; `sidekicks erase-data` and `sidekicks db restore <backup>`, each refused while the service holds the data directory, as sign-in is; `sidekicks delete-account`, over the control plane's `account.delete`, which signs this machine out and leaves its local data to `Erase all data`; and `sidekicks relay repin --force` with the new hash pasted, sent to the daemon as `relay.repin {spkiHash}`, the recovery a refused relay pin names; the daemon refuses and changes nothing when the hash does not match the key the relay presents. Their effects are [Spec-020](./020-data-retention-and-gdpr.md)'s, [Spec-013 §Backup Policy](./013-persistence-and-recovery.md#backup-policy)'s and [Spec-027](./027-remote-control.md)'s. `sidekicks delete-account` is the one way to delete the hosted account: a person who has lost every machine installs the command-line tool on another computer, runs `sidekicks sign-in` there, confirms it with a passkey on the device-code page, and runs `sidekicks delete-account`. The SQL in the [Hosted Account Deletion Runbook](../operations/hosted-account-deletion-runbook.md) is a break-glass procedure the person runs on their own relay, used only when they have no passkey left to verify a sign-in.
- On a Windows computer (§The service on a Windows computer). [Plan-005 §Phase R4](../plans/005-local-ipc-and-daemon-control.md#phase-r4--the-service-on-wsl-2) builds them.
  - The places, on the main process's supervisor bridge, because the list must answer before any service exists: `daemon.listPlaces()` → `ServicePlace[]`, each `{place: windows | {distro}, inUse, wslVersion?, libc?, claude: {version} | null, codex: {version} | null, reading: read | checking | failed {reason}}`, and `daemon.subscribePlaces(handler)`, whose first delivery is the list as it stands and which then delivers each place's reading as it lands. Absent on macOS and Linux.
  - The move, on the same bridge, because the service cannot move itself: `daemon.requestMove(place)`; `daemon.cancelMove()`, honored until the old service is asked to stop; `daemon.subscribeMove(handler)` → `{step: installing | stopping | copying {bytesDone, bytesTotal} | starting | reconnecting}`, then `moved` or `failed {reason, notRestored?: {worktrees}}`. The daemon's copy, path rewrite, worktree repair and undo run once on the Linux side of the move before its first start, as `sidekicks-daemon --take-in <from>`.
  - The `daemon.status` topic the main process publishes to its windows gains `cannotStart {reason: wslNotResponding | restartsExhausted {error} | placeGone | connectionNameTaken}`, read from the status file when the pipe is absent, and `whileSignedOut: on | off | passwordOutOfDate | notOffered`.
  - The command line: `sidekicks daemon install --windows` or `--wsl <distro>`; `sidekicks daemon move --windows` or `--wsl <distro>`, confirming in the terminal; `sidekicks daemon install --while-signed-out`. With interop off inside a distribution, a verb that must reach Windows prints `This terminal cannot start Windows programs, so sidekicks cannot do this from here. Run it from a Windows terminal, or turn WSL interop back on.` and exits nonzero; verbs that only talk to a running daemon keep working over the Unix socket. Inside a distribution, `daemon start` and `daemon install` run the Windows task through interop (`schtasks.exe /run`), and when the service is on Windows the in-distribution CLI hands the whole command to the Windows CLI through interop, so the same line works in either terminal.
  - The Windows half's start arguments: `--windows-half-stdio` on the daemon it starts inside a distribution, `--daemon-child` when a native daemon starts it, `--desktop` for the logon task's instance while the signed-out task holds the service. The daemon's ready line on standard output is `<prefix>{protocolVersion, pid}` and carries no token.
  - The channel between the daemon and the Windows half is HTTP/2 over that standard input and output: `node:http2`'s `performServerHandshake` on the daemon's side, the `h2` crate on the Windows half's, with `maxSessionMemory` 128 MB and the matching send buffer on each end, a stream flow window of 1 MiB and a connection window of 16 MiB. One long-lived control stream, opened first by the Windows half, carries its verbs both ways: `keystore.get`, `keystore.set`, `keystore.delete`, `banner.post`, `banner.withdraw`, `awake.hold`, `awake.release`, `wake.set`, `power.report`, `portOwner.read`, `portCarry.open {port, family} → {windowsPort}`, `portCarry.close {port}`, `scan` (the provider check in every WSL 2 distribution: `claude` and `codex` with their versions, and the C library, for the place list and the first-launch placement) and `status.report`; each pipe client and each carried port connection is a stream of its own beside it.
  - The credential store while the service is stopped runs the same code one-shot: `sidekicks-windows-half.exe keystore get | set | delete <entry>`, with the secret on standard input and output. Discovery — WSL's presence, the distribution list, and `scan`, each distribution's providers with their versions and its C library — and the install into a distribution run one-shot from the same binary, by main and the CLI, before any service exists.
- The typed client SDK must expose the same semantic surface to the desktop app's main process and the CLI. The renderer consumes a narrower preload bridge API per [Spec-021 §Trust Stance](./021-desktop-app-and-renderer.md#trust-stance), not this SDK directly.

- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- Client cache must not become the daemon's state store.
- Daemon supervision state may live in the desktop app's main process, but daemon runtime truth remains in daemon-owned persistence and projections.
- Version compatibility decisions must be visible to clients and logs.

## Example Flows

- `Example: The desktop app opens while the daemon is not running. The main process starts the daemon as the person's own background service, never as its child, negotiates protocol version via the typed client SDK, and then exposes renderer-accessible capabilities via the preload bridge per Spec-021 §Trust Stance; the renderer is not a direct daemon client. Quitting the app later calls daemon.flush and leaves the daemon and its work running.`
- `Example: The CLI requests a run-state subscription through the same client SDK and receives canonical updates without duplicating daemon logic.`

## Implementation Notes

- Keep IPC semantics typed and narrow. Avoid renderer-driven arbitrary shell escape hatches.
- Local IPC choice is a security boundary, not merely a performance choice.
- Treat the CLI as the contract proving ground for daemon control behavior, not as a disposable wrapper around desktop-only logic.

## Pitfalls To Avoid

- Giving renderer code direct untyped native execution access
- Allowing silent version skew for mutating operations
- Reimplementing daemon state transitions in the CLI
