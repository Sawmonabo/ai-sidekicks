## Purpose

Define the typed local control surface used by the desktop app's client helper and the CLI to communicate with the local daemon. Renderer-originated traffic travels over a `MessagePort` that main hands the page through the preload, to the client helper, which carries it on its own daemon connection per [Spec-021 §Trust Stance](./021-desktop-app-and-renderer.md#trust-stance) — the renderer is not a direct daemon client.

## Scope

This spec covers transport choice, version negotiation, request and stream semantics, and daemon supervision controls.

## Non-Goals

- Remote channel transport
- Provider-driver internal protocols
- UI rendering behavior
- Network reachability configuration. There is no local-network switch, no private-network join, no coordination-server field, no approval link and no address to copy on this surface: how a machine is reached is the layer beneath it, and the only thing the product says about reachability here is whether the daemon is running. Beside the port a workflow started by a web request listens on, no other listening figure is set here either — no domain and no command to update one, no certificate or key path, and no check of a certificate — and that port is the one address this surface sets. The ports a person shares with their other devices are set on the Devices page ([Spec-027](./027-remote-control.md)), not here.
- Reading the diagnostic record back. This surface writes that record and never serves it back as a list: the diagnostic controls say what is written and where it is written, and no read here renders the contents — no recent-activity fold, no credential-attempt list, no audit view, no log viewer, and no viewer for the raw provider messages, which are written to the folder its switch names and read only by whoever opens that folder. The diagnostic controls are the whole of diagnostics; there is no diagnostics page of its own.
- A browser client of the local daemon. The desktop app and the CLI are its only local clients; the web client and the iPhone app reach a machine over their end-to-end channel ([Spec-027](./027-remote-control.md)).

## Required Behavior

- The desktop app and the CLI must use one typed client, `sidekicks-client`; the desktop runs it in its client helper, an Electron `utilityProcess`. Renderer-originated traffic travels over a `MessagePort` that main hands the page through the preload, to the client helper, which checks it against its method allowlist per [Spec-021 §Trust Stance](./021-desktop-app-and-renderer.md#trust-stance) and carries it to the daemon over its own connection; main's own daemon calls reach the helper over `parentPort`.
- The CLI must be treated as a first-class local client and the first delivery track for the typed daemon contract.
- **The service log is the daemon's own file.** The daemon writes each service-log line — a reading that failed, a shell that hung at start, a drain's result — to its standard error and to `logs/service-<time begun>.log` in its data folder, a file it opens at start and begins anew each day and at 16 MiB, so a service that runs for weeks keeps day-sized files, each readable by the person alone. Once standard error's reader is gone, the lines go to the file alone, and the file says so once; a file that cannot be opened leaves standard error carrying the log, which says so once. Neither stops the daemon. Whoever started it — the desktop app with its standard streams detached, the CLI, the per-user service — needs to capture nothing for the log to be kept. The file is a diagnostic log, deleted whole once past `Keep diagnostic logs for` and with the data folder by `Erase all data` ([Spec-018 §Required Behavior](018-observability-and-failure-recovery.md#required-behavior)).
- The local daemon must expose a typed request-response and subscription contract for session, run, repo, artifact, settings, and daemon lifecycle operations.
- A subscription delivers changes in frames rather than one message per change. The first change after a quiet spell, one with no frame sent in the last 16 ms, goes out at once in a frame of its own and opens no window; what follows is coalesced into one frame per 16 ms or 50 events, whichever comes first, so nothing waits longer than one window, and every change in a frame carries its own cursor. A consumer that falls behind is not waited for and loses nothing: a subscription holds only its place, never a queue, nothing is dropped for it, and it sends its next frame when its lane has credit. A feed over a stored record (session events, the transcript, run history) reads that frame from the record at its cursor. A subscription more than 1,024 events or 1 MB of events behind the record's head when its next frame is read is sent one frame with no changes that says it is behind and carries the head cursor; its consumer takes one snapshot read instead of every change, and the stream carries on from the head. A catch-up never moves the reader: the row a reader who scrolled away is reading stays where it is, and a reader at the live tail lands on the new tail. A feed over a current state (a run's status, a list, the settings) sends the newest value; a shell's output reads from the shell's scrollback, and a watcher further behind than the scrollback redraws from it; a page's screencast sends the newest image once the last is acknowledged; an upload is taken a chunk at a time as each is written. So a slow reader never holds the daemon up and never grows its memory, however many subscriptions are open. A connection holds at most 10,000 open subscriptions, a backstop against a client that opens them in a loop: a subscribe call past it is refused with `connection.subscription.limitReached` and may be sent again once one closes. A connection also holds at most 100 calls in flight (`MAX_CALLS_IN_FLIGHT`, a figure that changes only with a new dated `protocolVersion`): a client holds any further call and sends it, in order, as an answer frees a slot, settles a cancel for a call it still holds without sending it, and sends a subscription cancel, a stop or a `terminal.write` past the cap, since none of them takes a slot: the daemon answers a subscription cancel and a stop without waiting on any call, and a shell's writes are bounded by that shell's own window ([Spec-002 §Required Behavior](./002-machine-registration.md#required-behavior)); a call past the cap reaches the daemon only through a client fault and is refused at once with `connection.call.limitReached`, nothing run and nothing retried. Every other lane is opened only after a call the receiver admitted, so a peer that opens lanes past the 10,000-subscription bound is misframed and its connection is closed. [Plan-005 §Phase 2D](../plans/005-local-ipc-and-daemon-control.md#phase-2d--substrate-supplement-the-subscription-frame-is-batched-carries-changes-only-and-never-waits-for-a-consumer) builds the frame.
- The default local IPC transport must be OS-local:
  - Unix domain socket on Unix-like platforms
  - named pipe on Windows
- **A stop is answered at once and bounded on both sides.** The service answers `daemon.stop` at once and then waits at most its drain bound for the writes already in flight, beside its terminal drain. The caller — main or the CLI — waits at most 10 seconds for `daemon.flush`, sends the stop and counts the drain bound from that send; a daemon still running after it gets SIGTERM and, 2 seconds later, SIGKILL. A stop that goes unanswered gets SIGTERM at once and SIGKILL once the drain bound and 2 seconds have passed, so a hung service never holds the caller.
- **The socket path has a hard length limit, so the daemon's run directory is short by design.** A Unix domain socket address is a fixed-size field in the operating system's own structure — the `sun_path` field of `sockaddr_un`, 104 bytes on macOS, 108 on Linux (`unix(7)`, read 2026-09-21) — and it is not a path the platform will truncate or redirect: a path past the limit simply cannot be bound. The failure is also badly reported by at least one client library above it, which surfaces it as a malformed address rather than as a length, so a caller reading the message looks for a typo in a path that is spelled correctly. The daemon therefore keeps its run directory short enough that the socket fits with room for the file name, and where it is handed a longer one it **refuses to bind and says the path is too long for a socket on this platform**, naming the limit and the length it was given, rather than passing the platform's own message through.
- Local IPC must support protocol version negotiation before mutating operations are accepted.
- The desktop app's main process must be able to start and supervise the daemon, and it stops or restarts it only when the person presses `Stop` or `Restart`. The daemon is never the app's child process: on macOS an installed app registers the per-user login agent with macOS's service manager and launchd starts it, on Windows main runs the per-user logon task, so Task Scheduler is its parent (§The service on a Windows computer); and elsewhere main spawns it detached, or, where a detached process does not outlive the app, starts the per-user service the install registered. The client helper checks the link with `daemon.ping` only after 5 seconds with no frame from the daemon, after 20 seconds with no frame counts the link as dead and reconnects, and reports the link's state to main.
- The daemon must resolve the calling connection's device from the transport and make it available to every handler it dispatches, so a write records the device it came from. Nothing checks ownership: no handler authorizes a read or a write by a person's identity. The device is a dispatch-context fact and never a wire field, so no request schema gains a member for it and a caller-supplied one is never trusted.
- The daemon outlives its clients. Quitting the desktop app flushes the daemon (`daemon.flush`) and nothing more: the service, every session, every run and every shell on that machine keep running, and the app reattaches to them when it opens again. Only Runtime's `Stop` and `Restart`, and the CLI's `sidekicks daemon stop` and `restart`, end work in flight. No surface explains this, and no surface claims where the work runs.
- `sidekicks daemon status` must report whether the daemon is up, since when, and which workspace it holds, in its text output and in `--json` alike. While a relay is configured it carries one further block: each linked device by name, whether it is connected, the path its channel takes (`direct (local network)`, `direct (internet)` or `relay`), the age of the last frame out and of the last frame in, the reconnect count and the rejected-frame count, as `iPhone · connected · direct (local network) · out 0.4 s · in 0.2 s · reconnects 1 · rejected 0`; `--json` carries the path as its wire value, `directLocalNetwork`, `directInternet` or `relay`. With no relay configured the block is absent — never printed empty and never printed disabled. Its fields follow the relay wire [Spec-027](./027-remote-control.md) defines, and the block adds no command, no exit-code path, and nothing to any screen.
- The CLI must be able to run the daemon as a background service of the person's own account — `sidekicks daemon install`, `uninstall`, `start`, `stop`, `restart` and `status` — and `sidekicks daemon install` alone installs and starts it, so a machine with no desktop is running after a single line. `uninstall` removes whatever the install registered and keeps the person's data. Where the desktop app's own registration already runs the service, `sidekicks daemon install` writes nothing, prints `The app already runs the background service on this computer. See it with sidekicks daemon status.` and exits `0`, the same line on every platform, the operating-system interface reporting only who owns the service, the app's registration or none ([Command Line Interface Guidelines](https://github.com/cli-guidelines/cli-guidelines/blob/main/README.md): a brief success that suggests the next command). On every platform the service comes back after a reboot. Whether it keeps running after the person logs out depends on the platform:
  - **macOS:** a per-user login agent, which starts at login and stops at logout, because launchd sends `SIGTERM` to every user agent it started when the person logs out ([Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)); one launchd label serves it on a Mac — with the app installed the app's own registration owns it (`SMAppService.agent`), and without the app `sidekicks daemon install` writes the per-user agent under `~/Library/LaunchAgents`, which the app boots out and deletes before it registers its own; while it runs, provider sign-ins and secrets are kept in the person's login keychain. A person who needs the service running while logged out adds `sidekicks daemon install --while-signed-out`, which installs a system service itself, as a property list in `/Library/LaunchDaemons` behind one administrator password, the old way, because macOS's service manager registers a system service only for a notarized app; the property list names the person's account, so launchd itself runs the daemon as the person and no program of ours runs as root; the daemon is the app's, or on a Mac with only the command line the command line's own copy, so that Mac keeps the service running too. That system service replaces the login agent: it runs the daemon as the person from the Mac's start (with FileVault on, once the disk is unlocked), before they log in, while they are logged in and after they log out, so there is one service and no handover. A system service cannot reach the person's login keychain, so once the service is installed and takes over, the daemon moves its own secrets to `secrets.json` in its data folder and each provider sign-in it runs into that account's own sign-in file, every file readable by this account alone (mode `0600`) ([Spec-020 §Daemon Secrets](./020-data-retention-export-and-deletion.md#daemon-secrets)), and the install says so in one line before it asks: `With this on, sign-ins and secrets are kept in files readable by this account alone, because a service that runs while you are logged out cannot reach the login keychain.` `sidekicks daemon uninstall` removes the system service behind the same administrator password, moves the secrets and sign-ins back into the login keychain, and puts the login agent back. The flag ships only if a Mac shows that the system service keeps Claude Code and Codex signed in from those files, runs their turns, reads projects in Desktop, Documents and Downloads, and reaches devices on the local network while the person is logged out ([macOS Service Probes](../operations/macos-service-probes.md)); otherwise it refuses on macOS with `This Mac cannot keep the background service running while you are logged out: <cause>.`, the cause the one the probe found, and nothing changes. Where the system service is turned off in Login Items & Extensions after the install, Runtime reads `The background service no longer runs while you are logged out, because it is turned off in Login Items & Extensions. Turn it on in System Settings › General › Login Items & Extensions, under App Background Activity.` ([Change Login Items & Extensions settings on Mac](https://support.apple.com/guide/mac-help/change-login-items-extensions-settings-mtusr003/mac)) How each step runs and every cause a Mac refuses with are §The service on a Mac while logged out.
  - **Linux:** a user service, and the install turns lingering on (`loginctl enable-linger`, which systemd's own polkit policy allows with no password from any session, SSH included; with no polkit daemon running the install refuses and says so), so the service keeps running after logout, while the Secret Service keeps the service's credential-store items locked until the person logs in again ([Spec-020 §Daemon Secrets](./020-data-retention-export-and-deletion.md#daemon-secrets)).
  - **Windows:** a per-user logon task starts the service at login and it stops at sign-out, and `sidekicks daemon install --while-signed-out` adds the signed-out task of §The service on a Windows computer, which keeps it running while the person is signed out.
- At each start on macOS and on Linux the daemon, and inside a WSL distribution its WSL server, runs the person's login shell once, with no input and a 5-second deadline, and keeps the environment it prints between two markers as the base every provider's environment is built from, so proxy, certificate and locale settings are there with no terminal open and a provider installed after the install is found. A shell that misses the deadline or prints no markers is ended, the start goes on with the account's default environment — its home, its shell, its user name as `USER` and `LOGNAME`, the default search path `/usr/bin:/bin` and, on macOS, its own temporary folder as `TMPDIR` (read with `getconf DARWIN_USER_TEMP_DIR`, and left out with one log line when that read fails) — and the service log says why; the service never waits on a shell. A stop that arrives during the start ends the shell too, and the daemon stops as soon as it has started, without writing its ready line. Inside a distribution, provider binaries under the Windows drive mounts are ignored: a Windows `claude` or `node` reached through `appendWindowsPath` fails with Claude Code's documented "exec: node: not found". On Windows the service starts with the account's own environment.
- A session that cannot start because its provider is not installed where the session runs is refused with one flow row naming that provider, and on a Windows computer with a WSL 2 distribution its place, which opens Settings › Providers on that provider's section, on every platform; the row is drawn from the session notice of kind `providerMissing`, and [Plan-001](../plans/001-session-core.md)'s session start owns the refusal.
- `sidekicks daemon update` checks for a newer release of the background service and applies it down the same path Settings › Runtime's `Update the background service` uses, so the app and the CLI can never disagree about which version is current. It updates the service only and says that the app updates from General. Like that button, it waits for running work to finish, naming it, rather than stopping it. On an install a package manager made, it replaces no file behind that manager and names the manager's own update command instead. `sidekicks daemon update --check` only reports: it exits `0` when this machine is up to date, `100` when an update is waiting and `1` when it could not check; a crash exits `70`, like any other failure, so only `100` means an update is waiting.
- Signing in to and out of the product's hosted account is one CLI verb each, `sidekicks account login` and `sidekicks account logout`, and both always go through the background service, which runs the sign-in and keeps its keys and tokens; nothing asks the service to stop. With the service stopped, each verb starts it first, as the desktop app does, then acts through it. `sidekicks account login` opens the sign-in address in this computer's browser and prints it too, reading `Opening the sign-in page in the default browser…` and then `Signed in as <name>.`; where no browser can reach this computer (an SSH session, Linux with no display, WSL with interop off) or with `--no-browser`, it prints `Open this address in any browser, sign in, then paste the code it shows:` beside the address and takes the pasted code. A sign-in that does not finish prints `Sign-in did not finish.` with its reason under it, and an expired one `The sign-in page expired.`, the same words Devices shows; Ctrl-C cancels the attempt and prints nothing, as Devices' `Cancel` shows no line. `sidekicks account logout` deletes the machine's DPoP key first, so no token it holds can be traded again, then revokes the refresh-token family ([RFC 7009](https://www.rfc-editor.org/rfc/rfc7009)) once the relay is reachable. The service holds an exclusive lock on a small lock file beside its store, `daemon.lock`, for its whole life, through the standard library's `File::try_lock` (`flock` on macOS and Linux, `LockFileEx` on Windows), and writes its process number beside it. The lock is freed the moment its holder dies, and the standard library opens the file close-on-exec on macOS and Linux and not inheritable on Windows, so no process the service starts holds it. A second service started on the same store retries the lock for a moment, since a child between fork and exec briefly shares its open file, then is refused with `The background service is already running (process 4182).`, naming the holder's process number. What signing in means — the ceremony, the credential it produces and the state it leaves behind — belongs to [Spec-016 §Required Behavior](./016-hosted-account-and-identity.md#required-behavior); what this surface owes is the verbs and the service methods they call.
- Ctrl-C in a terminal stops only that `sidekicks` command: the background service, every session and every workflow keep running, the command cancels only what it waited on (`sidekicks account login` cancels its sign-in), and it ends the way a Ctrl-C does, so a script running it stops too.
- Machine-wide daemon configuration is read and written through this surface, one place per value and no second one: how long diagnostic logs are kept, how long finished sessions are kept, the port a workflow started by a web request listens on, the time limit after which a run is ended, how many runs one start may lead to before the next one waits for the person, the memory cap for tool processes, `Max steps per turn`, `Spend limit`, `Tokens per run`, the package caches' limit, and the two diagnostic switches — recording traces, and recording raw provider messages, which names the folder it writes to. Several carry a shape of their own: the run limit is no limit by default and is otherwise `30 minutes`, `1 hour`, `4 hours`, `12 hours` or `24 hours`; the run count one start may lead to is `100 runs` by default and is otherwise `25 runs`, `500 runs`, `2,000 runs` or `Never ask`; the memory cap is empty until a size is given, and empty means no cap; `Max steps per turn` reads `Unlimited` by default, which is what each provider does on its own, and carries one line saying what the number bounds and that a session can set its own number in its inspector; empty is `Unlimited` and a number of 1 or more is that many, and anything else, `0` included, is refused under the field with `1 or more, or empty for unlimited` — a number typed here governs sessions started later and reaches a session already running at its next turn, and `Unlimited` puts the providers' own behavior back, what the bound does and how each provider realizes it being [Spec-003 §The Step Bound On A Turn](./003-queue-steer-pause-resume.md#the-step-bound-on-a-turn)'s and the per-session override's own write being [Spec-001 §Interfaces And Contracts](./001-session-core.md#interfaces-and-contracts)'s; `Spend limit`, in dollars for a whole session, and `Tokens per run` each read `Unlimited` by default and are what every new session starts from, a session setting its own in its inspector, what each limit does being [Spec-014 §Budget Policies](./014-multi-agent-orchestration.md#budget-policies)'s; the package caches' limit reads `Unlimited` by default, under which the daemon never clears a cache on its own, and otherwise takes a size, what the caches hold and when they are cleared being [Spec-015](./015-workflow-authoring-and-execution.md)'s; and both diagnostic switches are off until they are turned on. Each value's own policy belongs to the spec that owns it: the diagnostic-log bound to [Spec-018 §PII in Diagnostics](./018-observability-and-failure-recovery.md#pii-in-diagnostics), the finished-session bound to [Spec-020 §Retention Policy](./020-data-retention-export-and-deletion.md#retention-policy). What this surface owes is that the value is set in one place, that a value the operating system will not let the daemon enforce says so where it is set, and that a refused value — something that is not a port, something that is not a size — is refused in place with nothing written and the field left as it was; a port already taken is saved, the listener then listening on nothing and saying so where the port is set and in place of every address it would serve, and the daemon never moves to another port of its own. [Plan-005 §Phase R1](../plans/005-local-ipc-and-daemon-control.md#phase-r1--namespace-handlers) builds the configuration and retention verbs.
- One of the two retention bounds acts on its own and one does not. Past its bound the daemon drops its own diagnostic logs; that control sets only how long, and it is not a switch that turns deletion on or off. A workflow run's step data and its snapshots stay until the person deletes the run or its session. A finished session is never removed on its own: its bound only makes it eligible, and it goes only through `Delete old data`, the one operation on this surface that deletes sessions, which asks first, names what goes and what stays, and cannot be undone ([Spec-020 §Required Behavior](./020-data-retention-export-and-deletion.md#required-behavior)). Setting a value deletes nothing at the moment it is set, and no bound reaches a worktree the person kept, which goes only on that worktree's own `Delete now`. Every job the service runs in the background — that expiry, backups, the package caches' limit, the update check — runs on its one scheduler, never on a timer of its own. The retention verbs are this surface's, built with the rest of the service's control surface.
- The folders this machine can reach are read and changed through this surface: the list, each folder's row with what is using it, and each worktree the app made listed beneath its project's folder and marked `worktree` — marked when the app makes it, so a worktree the person made is never claimed. Removing a project's folder is the Projects page's delete under the same rule: refused while an agent runs anywhere in the project, naming the running session ([Spec-002 §Required Behavior](./002-machine-registration.md#required-behavior)). Removing a worktree the app made follows the worktree's own removal rules through `worktree.retire {worktreeId, discard}`. Beneath its project's worktrees, each worktree kept by `Discard and remove` has one row with its size, `Put back`, which recreates the worktree at its own path, and `Delete now`, the only act that deletes it ([Spec-008](./008-worktree-lifecycle-and-execution-modes.md)). A chat's session workspace has no removal of its own: it goes whole only when its session is deleted through `Delete old data`. A read with no folder mounted answers an empty list rather than an error, and the surface showing it says so rather than drawing an empty table.
- **What the daemon connects to first.** Where a shared Codex service was running — the provider's own `codex app-server --listen unix://<control socket>`, which terminal Codex sessions join ([Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other)) — that service runs apart from the daemon, so the daemon's restart leaves it running and the daemon finds it again by connecting before anything else it restores, and a terminal Codex session attached to it never notices the restart; a terminal session that loses its service reconnects on its own for up to 120 seconds ([Codex wire reference §The shared `app-server` a terminal `codex` joins](../reference/provider-wire/codex.md#the-shared-app-server-a-terminal-codex-joins), measured 2026-10-07 at `0.161.0`). A session that has been without its service for longer than that window has given up and is not recovered by the daemon at all: it is the person's own process, and what brings it back is the provider's own resume ([Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other)). The restart order is [Plan-005 §Phase R1](../plans/005-local-ipc-and-daemon-control.md#phase-r1--namespace-handlers)'s, the shared service itself [Plan-003](../plans/003-provider-driver-contract-and-capabilities.md)'s.
- The daemon's own supervision facts are read by the surface that shows them and edited nowhere: whether it is running and since when, its version, and how much of the machine's processor and memory it is using — each reading stamped with the time it was taken and taken again only when it is asked for, never sampled on a timer. Until the first read answers, the surface says it is reading, and a figure not read yet says so rather than showing a number. On a Windows computer with work in a WSL distribution, the processor and memory figures are the service's own processes and nothing else, each WSL server and its processes among them; the WSL virtual machine is not counted (§The service on a Windows computer).
- Stop and restart are the two supervised controls; each confirms before it acts and each says that work in flight stops. Where terminal Codex sessions are inside the shared Codex service, the stop confirmation adds one line counting them, read through `provider.terminalSession.list`, and says how to use one again, because stopping the service strands them until the person runs the provider's own resume ([Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other)). The restart confirmation names none: the restart leaves the shared service running, so they stay attached.
- The daemon is updated separately from the desktop app, and an update never stops work. While any session, workflow run or terminal Codex session is working, the update waits and names that work on one line, its parts joined by `·` — the sessions and runs by their titles, at most three, then `and N more`, then the terminal Codex sessions as a count — and each title opens its session or run so it can be finished or stopped from there. It offers a cancel while it waits and until the app asks the old service to stop, since a cancel after that request cannot be honored. It shows the step it is on and settles by naming the version it came from and the one it reached, or both versions and the reason where it rolled back, or that this machine is already at the newest version. The stop, restart and status verbs are [Plan-005 §Phase R1](../plans/005-local-ipc-and-daemon-control.md#phase-r1--namespace-handlers)'s; the update's steps, wait, cancel and outcome are the service's update path ([Plan-005](../plans/005-local-ipc-and-daemon-control.md) T-005r-3-6), one module both clients import, which Runtime drives through the main process ([Plan-020](../plans/020-desktop-app-and-renderer.md) T-020r-4-1) and `sidekicks daemon update` drives from the command line.
- **The runtime settings page's words.** The page's note reads `The background service that runs sidekicks, the folders it can reach, what it keeps, and the port it listens on.` The service's own line reads its state, how long ago it started and its version, `Running · started <age> · version <version>`, with one line under it, `Everything above is read from the service and is not edited here.` `Restart or stop it` sits under `Both stop whatever is in flight.`; `Restart` confirms in place with `Restart the background service? Work in flight stops.` and `Stop` with `Stop the background service? Work in flight stops, and nothing new starts until it is running again.`, adding, where terminal Codex sessions are inside the shared Codex service, `<N> Codex sessions in a terminal will disconnect. To use one again, run codex resume in its terminal.` (`1 Codex session` for one). `Update the background service` sits under `The app and the service are updated separately.`, and on a machine already up to date it settles as `The background service is already at its newest version.` `Folders this computer can reach` sits under `A project's folder can be removed while no sidekick is running anywhere in the project, and a worktree while none is running in it.`; each row says what is using it, `2 sessions are using this folder.` or `Nothing is using it.`, a kept worktree's row reads `<name> · removed <date> · <size>`, and with no folder mounted the list reads `No folders are mounted.` `Package cache` sits under `Packages workflow steps download, kept so each is fetched once. Clearing them never breaks a step already installed.`; `Cache limit`'s other choice, `Custom…`, opens one size field, refused with `That is not a size.`; `Current usage` reads each cache's size, then the total and the time it was read, and is read again on `Check again`; `Clear Bun cache` confirms in place with `Clear the Bun package cache? Steps already installed keep working; a version not yet installed downloads its packages again.`, `Clear uv cache` the same with `uv`, and `Clear all caches` with `Clear both package caches? Steps already installed keep working; a version not yet installed downloads its packages again.`; a clear waiting on an install reads `Waiting for an install to finish…`. `Port workflows listen on` sits under `A workflow started by a web request listens here. Changing the port changes every one of those addresses.`, a taken port reads `Port <port> is already taken, so nothing is listening. Pick another port.` and something that is not a port reads `That is not a port number.` `Ask me after one start leads to` has no line on the page, its tooltip reading `When runs that start other runs — Execute workflow, error and session-event triggers — have started this many from one start, the next one waits for you.`; `Stop a run after` has none either, its tooltip reading `Ends a run that has been working longer than this and marks it timed out. Time a run spends waiting on you does not count, and the workflow's schedule keeps firing.`; and `Max steps per turn` sits under `How many steps a sidekick may take in one turn before it stops and asks you to continue. Unlimited is what each provider does on its own. A session can set its own number in its inspector.`
- While any agent works and the machine's keep-awake switch `keepAwakeWhileAgentWorks` is on (it is off by default and lives in the machine's settings file), the daemon holds the machine and its screen awake with `keepawake` 0.6.1 built with `.display(true).idle(true)`, never `.sleep(true)`, its guard created and dropped on one thread made for the hold, tied to the daemon's own process: on macOS a power assertion the daemon's own process holds, which macOS releases when that process ends; on Linux logind's idle `block` lock (`Inhibit("idle", …, "block")` on the system bus, its file descriptor held by the daemon so the lock ends with the process) and the screen saver's inhibit (`org.freedesktop.ScreenSaver.Inhibit`, held on the daemon's own session bus connection and released when that connection closes), both of which `keepawake` takes, and no `sleep` lock, since a `sleep` lock in block mode inhibits "system suspend and hibernation requested by (unprivileged) users", so it would block a suspend the person requests ([systemd, Inhibitor Locks](https://systemd.io/INHIBITOR_LOCKS/)); on Windows the daemon holds `SetThreadExecutionState` in its own process through `sidekicks-platforms`, and a sleep blocker inside a WSL distribution holds nothing on Windows. The hold outlives a quit of the app and ends when the service stops. The second keep-awake switch in the same file, `keepAwakeForOtherDevices`, also off by default, holds the machine awake while it is on and the machine is on power ([Spec-027](./027-remote-control.md)). No platform's hold stops a sleep the person asks for, such as closing the lid, and each switch says so.
- `sidekicks open <address>` hands a `sidekicks://` address to the running app, or to the app the platform starts for it, through the platform's own link handler, and calls no daemon method. The address is checked by the one `sidekicks://` parser that the app's `Copy link` and its link handler also use; anything else is refused with a usage line.

### The service on a Windows computer

On a Windows computer the background service is one native Windows program, whether or not WSL is installed. A person may keep projects inside a WSL 2 distribution, such as Ubuntu, and install Claude Code or Codex there; a session runs where its project folder is, and for work in a distribution the service starts that distribution's WSL server. The decision and its alternatives are [ADR-039](../decisions/039-sessions-in-wsl-2-distributions.md).

- **One service per computer, native on Windows.** The service is the native daemon on every Windows computer: the per-user logon task, the per-user pipe, Credential Manager, keep-awake, the wake timer and banners, each in its own process through `sidekicks-platforms`. The machine's identity, the store and the relay connection are the daemon's own, so the computer is one machine with one key ([Spec-027](./027-remote-control.md)), and a Devices card reads this computer's operating system. The service itself is never placed on screen.
- **Where a session runs.** The folder decides, with no override. A drive path, `C:\code\beacon`, runs on Windows, and so does `/mnt/c/code/beacon` given from inside a distribution, kept as `C:\code\beacon` (`wslpath -w`); `\\wsl.localhost\Ubuntu\home\me\x`, `\\wsl$\Ubuntu\…`, or a Linux path given from the in-distribution CLI or a session in Ubuntu, runs in Ubuntu, kept as `/home/me/x`. A folder in a WSL 1 distribution is refused in place, `Ubuntu-18.04 runs on WSL 1. Convert it to WSL 2 or pick another folder.`, with `wsl --set-version Ubuntu-18.04 2` under it as text; a path in a distribution not on this computer is refused in place, `No WSL distribution named Kali is on this computer.` The project record keeps its place and its path in that place's own form. A session's place is written on it at creation from its project and never rewritten: a fork, a resume, a provider switch, an account switch and a restore keep it, and nothing moves a session between places, as nothing moves one between machines. A chat has no folder: its managed workspace is made on Windows when its provider is installed there, otherwise in the distribution where it is installed, WSL's default distribution first, then by name. A run nobody is watching takes its workflow's project's place, or the chat rule when the workflow has no project. A worktree is made on its project's side, by git in that place ([Spec-008](./008-worktree-lifecycle-and-execution-modes.md)). No session ever works on another place's disk. A session whose provider is not installed in its place lands one flow row naming the place, `Claude Code is not installed in Ubuntu.` with `Install in Ubuntu`, which opens Providers on that provider's `Ubuntu (WSL)` row, or, for a Windows folder, `Claude Code is not installed on Windows.` with `Install on Windows`, which opens that provider's `Windows` row. The first session in a distribution installs the runtime there and starts its WSL server under the session's own starting state, the working line every session start shows, with no cover and no step of its own.
- **On screen.** No group word, "place" or "side", appears on screen. A folder in a distribution reads as the distribution's name and its Linux path, `Ubuntu · ~/code/beacon`, and a Windows folder as its drive path alone. A label beside `Windows` reads `Ubuntu (WSL)`; a sentence reads "on Windows" and "in Ubuntu". A distribution is named exactly as `wsl -l` prints it, and the word is "distribution". On a Windows computer with at least one WSL 2 distribution, each provider's section on Settings › Providers draws one `Command` row per place ([Spec-025 §Machine provider readiness and the sign-in handoff](./025-provider-accounts-and-credential-homes.md#machine-provider-readiness-and-the-sign-in-handoff)); everywhere else it draws one row and names no place.
- **No WSL work at first launch.** The app starts the native service under its one cover, and no distribution is listed, booted or installed into until a session or Settings › Providers needs one.
- **Discovery.** WSL is present when `wsl.exe` exists in the system folder as Windows reports it (`FOLDERID_System`), and every run uses that absolute path, since a search-path lookup can be hijacked. `wsl.exe -l -v` lists the distributions, decoded as UTF-16LE with or without a byte-order mark, under a 5-second deadline; an empty answer with exit code 0 is read again through the daemon's pseudo console, because a piped list can come back empty. WSL 1 rows are shown dimmed with `Needs WSL 2`, Docker's and Rancher's own distributions are hidden, and WSL's undocumented registry key is not read. A running distribution is told from a stopped one by the daemon's own record of the WSL servers it runs and, for the rest, by one `wsl.exe -l --running` per Providers page open, which boots nothing. A distribution's providers, with their versions, and its C library are found by one run of the person's login shell inside it, ignoring anything under the Windows drive mounts, under a 30-second deadline: its WSL server answers while it runs, and otherwise a one-shot run on `Check` or `Check again` does, which starts a stopped distribution. A musl-based distribution such as Alpine is listed like any other.
- **The WSL server.** One runs inside each WSL 2 distribution that has work: `sidekicks-daemon wsl`, a helper mode of the shipped Linux `sidekicks-daemon`, started and stopped by the daemon and never named on screen. It owns, inside its distribution, the provider processes of sessions there, their standard streams carried as channel streams; terminals, through `sidekicks-terminal`'s PTY in the person's login shell; git and worktrees; file reads, folder listings, writes of staged attachments and file watching with inotify on that distribution's own disk; the local endpoints providers and hooks dial, each with its gate (its Unix socket for the in-distribution CLI and the `hook provider` hooks of that place's terminal Codex service, mode `0600`, under the caller check and the daemon token; the terminal bridge's HTTP socket, under the caller check and the token as `Authorization: Bearer`; the `sidekicks` tool server's loopback port, which Codex's hook rows reach too, under each session's secret; the command channel's folders, each conversation's own, each party known by the public key read from `/proc/<pid>/cmdline`; Codex's pass-through relay, under its own bearer token; and the inboxes it serves for Claude Code sessions, each a socket of mode `0600` with no caller check, as Claude Code's own inbox is, [Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other)); every program a provider there starts on the daemon's behalf (`hook provider`, which runs a Codex helper's own command handlers and dials nothing, and on that place's terminal Codex service runs the daemon's two hooks, dialing the server's Unix socket under the caller check's one admission for it, the command wrapper, the askpass program, and Codex's `codex exec-server` from that place's Codex); the tool servers the daemon fronts for a session there that only the distribution can reach: a stdio server, which it starts there and carries over the channel, and an address on the distribution's own `localhost`, which it carries, while the daemon connects a server at a web address itself on Windows, so the token never enters the distribution and the WSL server holds none; workflow steps, shell commands and armed file-watch triggers of runs whose session is there; the providers' own global agent and skill folders there; dev-server listener discovery and the far end of each carried connection; and the login-shell capture at its start and the provider lookup in its distribution. It never owns the store, credentials, the scheduler and its timers, the relay connection, the approval engine or the account registry, and it holds no secret at rest: a token a provider needs reaches the process as an environment value or a provider request the daemon sends through the channel. The daemon sends each process, terminal, file operation and watch through one interface chosen by the session's place, so session, git, terminal, workflow and provider code never ask which system they run on.
- **Starting a WSL server.** The first time a distribution needs its server after that distribution started, the daemon makes the private mount ([Spec-025 §Credential homes and the constructed environment](./025-provider-accounts-and-credential-homes.md#credential-homes-and-the-constructed-environment)) with a one-shot `wsl.exe -d <distro> -u root --exec mount …`, unless it is already there. It then runs the system folder's `wsl.exe` (the folder as Windows reports it) as `wsl.exe --cd ~ -d <distro> --exec <home>/.ai-sidekicks/runtime/sha256-<digest>/bin/sidekicks-daemon wsl`, `<home>` being the runtime row's absolute path, since `--exec` runs no Linux shell and passes a `~` through literally, so the person's shell and its rc files never re-read the server's arguments. The process is created suspended and with no window, placed in the daemon's Job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`, then resumed: kill-on-close ends `wsl.exe` if the daemon dies, and silent breakaway lets every Windows program started through interop, such as an editor window an agent opened, survive a server stop, restart, update or crash. Killing `wsl.exe` only closes the server's standard streams and sends it no signal, so the server stops itself on end of input or a failed output write. Its standard error is drained and thrown away for the process's whole life, the server writing its log lines to the daemon over the channel; its standard output carries the ready line, `<prefix>{protocolVersion, pid}` with no token, within 10 seconds for a running distribution and within the measured cold-start figure from a stopped virtual machine, and then the channel. Anything before the prefix is `wsl.exe`'s own launch message, shown word for word under the failure line. Only the daemon runs `wsl.exe` on a Windows computer; main, the Windows CLI and the `banners` instance never do, except under the signed-out fallback below, because WSL binds a user's whole WSL to the Windows session that first reached it.
- **The channel.** One HTTP/2 channel over that `wsl.exe`'s standard input and output, never a link per connection: a link per connection costs a process pair each, and after a sleep a new `wsl.exe` can hang until a reboot. One control stream, opened first, carries the daemon's requests and the server's reports; one stream each carries a provider process's standard streams, a PTY, a file read or listing, a watch, a carried connection, and each local client of the server's endpoints. The daemon treats the channel as its own child's standard streams. Every local client of the server's endpoints still sends the daemon token as its first message; the server writes the token's copy into its run folder at each start. Because that copy is readable by every process of the person, the server's Unix socket and its terminal bridge's HTTP socket also make the daemon socket's caller check, the bridge socket taking the token as `Authorization: Bearer <token>` as the daemon's second socket does, refusing a caller that descends from the WSL server or runs through that place's terminal Codex service, with the exceptions and the one `hook provider` admission the daemon's socket makes; the check pins the caller with `SO_PEERPIDFD` and each parent with `pidfd_open`, the server reads the process at the other end of each Codex service socket in the distribution the daemon dials and holds it while the socket is open, and the server sets `PR_SET_CHILD_SUBREAPER` and reaps the orphans that reach it and calls `prctl(PR_SET_DUMPABLE, 0)` at its start, so another process of the person's cannot read its memory, as the daemon does on Linux ([Security Architecture §Local Daemon Authentication](../architecture/security-architecture.md#local-daemon-authentication)).
- **A WSL server's lifetime.** A distribution has work while a session's provider process runs there (a Claude Code process until it sleeps, or the account's Codex service there while any Codex session there exists), that place's terminal Codex service runs, an account's five-minute read runs there, a terminal, running command or workflow step is open there, an armed file-watch trigger watches a root there, an open session view needs its watches, a Preview carry or shared port leads into it, a backup or restore is copying its part, or a client of its endpoints is connected. The server exits 10 minutes after the last of that work ends, closing its standard output first so `wsl.exe` cannot hang at teardown; WSL then stops the distribution after 15 seconds and the virtual machine after 60. The attached `wsl.exe` is what keeps the distribution up meanwhile, and the person's `.wslconfig` is never edited. A normal stop is a stop request on the control stream, after which the server ends its processes as `Stop` does, closes its standard output and exits within the service's drain bound (4 seconds); only if it still runs does the daemon send `wsl.exe -d <distro> --exec kill -TERM <pid>`, and `kill -KILL` 2 seconds later; never `wsl --terminate` or `wsl --shutdown`, which would take the person's own terminals and work with them. A server whose input ends or whose output write fails treats the daemon as gone and stops cleanly. A server that exits unexpectedly — the person's own `wsl --shutdown`, a WSL update — takes its provider processes with it; the daemon starts it again with the supervisor's backoff (100 ms, 300 ms, 1 s, 3 s, 10 s) when work needs it, and each session resumes from its provider's own conversation file. Windows sessions are never touched.
- **A stuck WSL.** Every `wsl.exe` the daemon starts has a deadline and is killed through its Job when it misses it: 10 seconds to start a server in a running distribution, the measured cold-start figure from a stopped virtual machine, 5 seconds for the list, 30 for a provider check, and the runtime's copy by its size. After two missed deadlines with no success between them the daemon marks WSL as not answering and starts no more `wsl.exe`, trying again once after each wake and once an hour. Each session in any distribution then reads one flow row, `WSL is not answering. Restarting Windows brings it back.`; after five failed restarts of one server, each session in that distribution reads `Ubuntu stopped and could not start again. Restarting Windows usually brings it back.`, with the error it gave under it, word for word. Windows sessions are touched by neither, and a distribution's failures are its sessions' lines, never the service's.
- **Sleep and wake.** The daemon's own sleep and wake are the native ones. A WSL server's link that ended across a sleep is a server that ended: after the wake the daemon starts it again under the deadlines above and the sessions resume from the providers' own files. No scheduler runs inside WSL.
- **A distribution's failures.** A stopped distribution starts with its WSL server, since WSL boots a stopped distribution for any `wsl.exe -d`. A removed one (`wsl --unregister`, or a reset) leaves each of its sessions one flow row, `Ubuntu is no longer on this computer, so this session cannot run.`, and its project row on Projects `Ubuntu is no longer on this computer.` with `Remove`; the store and every transcript are untouched, and its runtime row is dropped. Its provider conversation files and account homes went with its disk, so its sessions run again only once a backup holding that distribution's part is restored onto a distribution of the same name. With WSL uninstalled, the per-place rows are not drawn and sessions in distributions read the removed line. A WSL update stops every distribution and the server restarts when work needs it; it never touches Windows sessions or the service. Interop turned off in a distribution does not touch the daemon, which reaches the server from Windows; it limits only the in-distribution CLI and the terminal pane.
- **Start at login.** Main or the CLI runs the per-user task `\AI Sidekicks\Background service`, so the service's parent is Task Scheduler and never the app. The task has a logon trigger, runs `sidekicks-daemon` at the person's normal privilege, never with highest privileges, so the pipe it creates is owned by the person, and restarts the daemon if it fails, Task Scheduler's smallest restart interval being 1 minute. `sidekicks daemon install` registers it and `uninstall` removes it. Before any start the daemon takes the per-user mutex `Global\ai-sidekicks-service-<user SID>`, created with a user-only access list, so an instance in another Windows session and one started at sign-in never both run; `ERROR_ACCESS_DENIED` on its create means another program holds the name, as on the pipe. The mutex is also how main and the CLI tell whether the service is alive, since it is released the moment its holder dies.
- **Sign-out.** A service the logon task started in the person's own session stops at sign-out, within the 5 seconds Windows gives a program with no visible window. The daemon keeps a hidden top-level window, not a message-only one, which receives no broadcasts; on `WM_QUERYENDSESSION` it answers `TRUE` at once and never calls `ShutdownBlockReasonCreate`; on `WM_ENDSESSION` it stops its WSL servers, flushes what it can and returns within about 4 seconds. The stop is crash-safe on its own, because it may not finish: every SQLite commit is already durable, and a turn in flight resumes from the provider's own conversation file at the next start. The task starts the service again at the next sign-in.
- **Running while signed out.** `sidekicks daemon install --while-signed-out`, from either kind of terminal, adds a second task, `\AI Sidekicks\Background service (signed out)`, set to run whether the person is signed in or not, triggered at logon and at startup, and restarting on failure like the logon task; it runs the daemon in its own logon, so Windows sessions keep running through a sign-out. Its password is typed into Task Scheduler's own prompt (`schtasks /create … /ru <user>` with no `/rp`) and kept there; the app never reads, stores or passes it. A task kept with a password loads the person's profile, so Credential Manager answers. Sessions in a distribution run while the person is signed out where that task's daemon reaches WSL with no one signed in, through `C:\Program Files\WSL\wsl.exe`, and where the daemon's Windows session was the first to reach WSL; where the person's own terminal reached WSL first, that sign-out ends the WSL work once and the daemon starts the WSL servers again in its own session, the turns resuming from the providers' files. Where the task's daemon cannot reach WSL, the logon task's `banners` instance starts each WSL server's `wsl.exe` in the person's session and relays its channel to the daemon over the pipe, so sessions in WSL run whenever the person is signed in and wait while they are signed out, and Runtime reads under the service's own line `Sessions in WSL wait while you are signed out of Windows.` Whichever instance takes the mutex is the service; with the signed-out task added, the logon task's instance finds the mutex held and runs as `sidekicks-daemon banners`, connecting to the service over the pipe to post and withdraw banners in the person's session, and ends with the session. Keep-awake and the wake timer stay with the service. While the person is signed out, a moment that would post a banner reaches the phone by push and waits for the `banners` instance at the next sign-in. When the Windows password changes, Task Scheduler's copy no longer runs the task: at the next sign-in the logon task's instance finds no service, takes the mutex and runs the service, and Runtime reads `The background service no longer runs while you are signed out, because the Windows password changed. Run sidekicks daemon install --while-signed-out again.`, the daemon reading the signed-out task's last result at each start. `sidekicks daemon uninstall` removes the signed-out task with the logon task.
- **Reaching the daemon.** Windows clients reach the daemon through one per-user named pipe, `\\.\pipe\ai-sidekicks-<user SID>`. The server fails closed: the daemon creates the pipe through `sidekicks-platforms`' pipe code (tokio's `ServerOptions` with `first_pipe_instance` and `reject_remote_clients`) with an access list that grants the person alone on every instance, refuses remote clients (`PIPE_REJECT_REMOTE_CLIENTS`), and creates the first instance with `FILE_FLAG_FIRST_PIPE_INSTANCE`, treating `ERROR_ACCESS_DENIED` there as another program holding its name: it refuses to serve, records why, releases the mutex and exits nonzero, so the task tries again a minute later. It also checks that each accepted client's process belongs to the person and refuses one whose parent chain descends from a process the service started or runs through a Codex service the daemon dials, as the daemon's socket does, a parent that cannot be opened or that started later than its child ending the chain the way the system's first process ends it elsewhere, since Windows never moves a process to a new parent, and hands each connection to the same connection handler a Unix-socket connection gets. The client fails closed: the desktop's client helper and the Windows CLI open the pipe at identification level (`SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`) through `sidekicks-client`, which uses `sidekicks-platforms`' pipe code, and before writing a byte check that the process serving the pipe runs as the person; a wrong user or any failed call closes the handle and refuses. The daemon still demands its token first: the token is `%LOCALAPPDATA%\ai-sidekicks\run\daemon.token`, written with a user-only access list at every daemon start and read by clients at every connect. Inside a distribution, the in-distribution `sidekicks` dials its WSL server's Unix socket (mode `0600`, token); with no server running it asks the daemon to start one by running the Windows CLI through interop with a verb naming `$WSL_DISTRO_NAME`. `daemon install`, `uninstall`, `start`, `stop` and `data erase`, and `account login` or `account logout` while the service is stopped, hand the whole command to the Windows CLI through interop, so the same line works in either terminal; with interop off, a verb that must reach Windows prints `This terminal cannot start Windows programs, so sidekicks cannot do this from here. Run it from a Windows terminal, or turn WSL interop back on.` and exits nonzero, while verbs over a running WSL server keep working. The service binds no TCP port for its clients, so the OS-local default above holds and no loopback is involved; inside a distribution, each endpoint the WSL server serves keeps the gate named under the WSL server above, its `sidekicks` tool server's loopback port gated by each session's secret, since other distributions share the virtual machine's network.
- **Why the service cannot start.** The daemon writes `%LOCALAPPDATA%\ai-sidekicks\run\service-status.json`, beside the token, when its start fails, never on a timer. When the pipe is absent, main and the Windows CLI read that file, so Runtime and `sidekicks daemon status` say why instead of `The background service is not answering.`: its connection's name taken by another program, `The background service cannot start because another program on this computer is using its connection. Restarting Windows usually clears it.` Main and the CLI check the mutex rather than judging the file by its age: where it is free no service runs, so main runs the task at once rather than waiting for Task Scheduler's one-minute restart and says `Starting the background service…` meanwhile.
- **Paths.** The daemon translates paths: `sidekicks-platforms` for the `\\wsl.localhost\<distro>\…` and `\\wsl$\<distro>\…` forms, and `wslpath` run in the WSL server for the rest; main never builds a Linux path, and the renderer holds only `FilePathRef` tokens. `Open folder…` is the Windows folder dialog, where a distribution's folders are reached at `\\wsl.localhost\<distro>\`. Files dropped on the composer are staged to the daemon as bytes ([Spec-012 §Ingest Validation And Payload Bounds (V1)](./012-artifacts-files-and-attachments.md#ingest-validation-and-payload-bounds-v1)), so no path crosses, and the WSL server writes them for a session in a distribution. A Linux name with `:` or another character Windows forbids appears remapped from Windows, and a path Windows hands back with a remapped name, such as a folder picked through `\\wsl.localhost\`, is put back to its Linux spelling by WSL's own escape table, which `sidekicks-platforms`' `distribution_of` applies. `Show in File Explorer` takes the Windows form the daemon returns, and for such a name selects its parent folder. An editor opens a distribution's folder in its WSL form: VS Code with `code --remote wsl+<distro> <linux path>` and its forks, such as Cursor, through their own commands in the same form, Zed with `--wsl <user>@<distro>`, and every other editor with the `\\wsl.localhost\` path. A terminal in a distribution's session runs through the WSL server's PTY in the person's login shell, with a Linux working folder.
- **Runtime's figure, status and uninstall.** Runtime's processor and memory figures are the service's own processes and nothing else: the daemon's process tree on Windows plus, for each running WSL server, its `wsl.exe` and its process tree read inside the distribution; the WSL virtual machine is not counted and no line for it is drawn. `sidekicks daemon status` adds a `WSL` block, one line per distribution with a WSL server running or a session in it: `Ubuntu: running · 3 sessions`, `Debian: stopped · 1 session`, `Arch: not answering since 2:14 PM`. `sidekicks daemon uninstall`, from either kind of terminal, stops the service, then removes the logon task and the signed-out task where it was added, the token and status files under `%LOCALAPPDATA%\ai-sidekicks\run\`, and, in each distribution with a runtime row, after the private mount is unmounted, the runtime folders `~/.ai-sidekicks/runtime/` and the link `~/.local/bin/sidekicks`, through a one-shot `wsl.exe --exec`, starting a stopped distribution once for it. It keeps the store, the account homes, the agent memory, the worktrees, the backups and the Credential Manager entries, as uninstall does everywhere; `Erase all data` removes those, each distribution's `~/.ai-sidekicks/` included, worktrees aside.
- **Backups.** The store is on Windows, so `Back up to` defaults to the Windows home's `.ai-sidekicks\backups`, and each backup also holds each distribution's part ([Spec-013 §Backup Policy](./013-persistence-and-recovery.md#backup-policy)).
- **The Linux runtime on Windows.** The Windows installers carry the Linux runtime archives for the installer's architecture, the Linux release's own Rust builds: `sidekicks-daemon`, with SQLite compiled in and the PTY inside it, and `sidekicks`, for glibc and for musl, each archive with its SHA-256. The musl `sidekicks-daemon` is the dynamic build with `libgcc_s.so.1` and `libpdfium.so` beside it, because a static musl program cannot load PDFium, and the musl `sidekicks` is one static program, since it loads no PDFium. The runtime is shipped rather than downloaded at first use, so the first WSL session works offline. The first time anything needs it in a distribution — a session, `Install in <place>`, or `Use Sidekicks in terminal Claude Code` turned on for that place — the daemon resolves `$HOME` there, translates the archive's Windows path with `wslpath -u` inside the distribution, extracts the archive for the distribution's C library into a temporary folder, renames it to `~/.ai-sidekicks/runtime/sha256-<digest>/` and links `~/.local/bin/sidekicks` to its CLI. The archive is copied through the drive mount, or through `\\wsl.localhost\<distro>\` with drive mounts off, never through `wsl.exe`'s standard input. Each distribution's installed runtime (version, digest, the resolved home) is a row in the daemon's store, read before a start, cleared before a folder is replaced and written after a start succeeds, so a failed install is never taken for a good one; the current folder and the one before it stay. The WSL server is the daemon's own release, so no version is negotiated between them and a server from another release is never started: a service update replaces the archives with the daemon, each distribution's runtime is replaced at its server's next start, and if the new folder's server sends no ready line within the start deadline, the daemon starts the previous folder once and the update names both versions and the reason. A runtime replaced by an update rewrites a session's command wrapper, askpass and `hook provider` paths at the session's next start, and the terminal Codex service's at its next start.

### The service on a Mac while logged out

On a Mac, `sidekicks daemon install --while-signed-out` swaps the per-user login agent for a system service, which keeps the daemon running while the person is logged out (§Required Behavior). It is installed the old way: a property list in `/Library/LaunchDaemons`, the folder of "System-wide daemons provided by the administrator" (`launchd.plist(5)`), put there behind one administrator password. Apple's service manager registers a system service only for a notarized app ("Apps that contain LaunchDaemons must be notarized", `SMAppService.h` in the macOS 27.0 SDK), which the app is not, while a property list in that folder "will continue to be bootstrapped without explicit approval in System Settings since writing to /Library is protected with filesystem permissions" (the same header). Every step below is the macOS form of the service's operating-system interface, so no shared code holds it.

- **Who may turn it on, and when it refuses.** The command installs the service itself; the app need not be running. It runs one `osascript -e 'do shell script "…" with administrator privileges'`, the one-shot route Apple's developer support names for a product outside the notarized path ([BSD Privilege Escalation on macOS](https://developer.apple.com/forums/thread/708765)), which asks for an administrator's password on the Mac's screen, writes the property list and starts the service with `launchctl bootstrap system`. The property list names the daemon the login agent runs: the one that comes with the app where the app is installed, and otherwise the command line's own copy ([Plan-005](../plans/005-local-ipc-and-daemon-control.md) T-005r-3-4), so a Mac with only the command line turns it on the same way. The command refuses with `This Mac cannot keep the background service running while you are logged out: <cause>.`, changing nothing, for each cause it finds, each named in plain words:
  - the build this Mac runs carries the refusal, because a probe that decides the flag ([macOS Service Probes](../operations/macos-service-probes.md)) did not pass: the cause that probe found, among them `This Mac cannot keep the background service running while you are logged out: macOS keeps it from reading projects in Desktop, Documents or Downloads.` and `This Mac cannot keep the background service running while you are logged out: macOS keeps it from reaching devices on the local network.` (below);
  - this account has no session at the Mac's screen, where the administrator prompt is drawn, as when the command runs over SSH with no one logged in: `This Mac cannot keep the background service running while you are logged out: turning it on needs this account logged in at the Mac's screen. Log in at this Mac, then run the command again.`;
  - another account on this Mac already has it on, because the Mac has one such service: `This Mac cannot keep the background service running while you are logged out: another account on this Mac already has it on. Run sidekicks daemon uninstall from that account first.`;
  - the prompt is canceled: `This Mac cannot keep the background service running while you are logged out: the administrator password was not given.`;
  - the install fails: `This Mac cannot keep the background service running while you are logged out: macOS did not install it (<macOS's own message>).`
- **Nothing to approve.** Once the password is given, launchd runs the service at once and at every start after, with no approval in System Settings, so `whileSignedOut` goes from `off` to `on` once the service has taken over (below).
- **Runs as the person, with no program of ours as root.** The property list names the person's account in `UserName`, "the user to run the job as", a key honored only for a service in the system domain (`launchd.plist(5)`), and leaves `GroupName` unset, so "the group will be set to the primary group of the user", and `InitGroups` at its default, so launchd sets the account's group list with `initgroups(3)` (the same page). launchd makes the switch itself: only the root launchd may `setuid(2)` to another user, which is why `UserName` is honored for system services alone ([launchd-dev: UserName ignored on per-user LaunchAgents](https://web.archive.org/web/20240914195733/https://lists.macosforge.org/pipermail/launchd-dev/2007-December/000104.html)). So the property list names the daemon itself and launchd starts it as the person; Apple's launchd engineer called a system service per account, run as that account through `UserName`, "the next best alternative" while a user agent cannot start at boot ([launchd-dev: User Deamon](https://web.archive.org/web/20240915010707/https://lists.macosforge.org/pipermail/launchd-dev/2007-November/000079.html)). The account is the one that ran the command: the command reads its own account's name before it asks for the password and the install writes that name into the property list, so nothing hands the account over later, and another account's install finds the service by its property list's `UserName`. The property list is owned by root and writable by no other account, because "All system-wide daemons (LaunchDaemons) must be owned by root. Configuration files must disallow group and world writes … as allowing writability to a launchd configuration file allows one to specify which executable will be launched" (`launchctl(1)`); the daemon it names runs with the person's own rights, so where it lives needs no such rule. Where the app is installed, the property list also carries `AssociatedBundleIdentifiers` with the app's bundle identifier, as `launchd.plist(5)` asks of an app that installs a legacy property list, which ties it to the app in the Login Items list of System Settings; without the app it carries none, and neither that page nor Apple's Login Items guides say what the list then shows for it, so the probes record it ([macOS Service Probes](../operations/macos-service-probes.md)). The property list starts the daemon with an argument saying it is the system service, which tells the daemon to keep its secrets and sign-ins in files and to take over from the login agent (below).
- **What macOS may withhold from a service run as a person.** launchd switches the account a system service runs as but not the rest of what macOS checks, so Apple's developer support says "Running a `launchd` daemon as a real user tends to cause weird problems", that if it "hits a MAC check — for example, it tries to access the Desktop folder — it's completely unclear as to what'll actually happen", and advises that background code run as a real user be set up "as a `launchd` agent" ([Local Network Permissions - launchd service running as non-root user](https://developer.apple.com/forums/thread/772178)); a user agent stops at logout (§Required Behavior), so it cannot keep the daemon running while the person is logged out. In the same thread a system service run as a user could not reach the local network until `UserName` was removed. The probes decide both: logged out and logged in, the service must read and write a project in Desktop, Documents and Downloads and reach a device on the local network, and a failure ships the flag as the refusal with that cause (above).
- **Taking over from the login agent.** Once installed, launchd starts the daemon as the person, as the system service. It asks the login agent's daemon, which is still running in the person's login session where the login keychain can be reached, to move the secrets and sign-ins into their files (below), remove the login agent and stop, and then serves; from then on it is the only service, at login, at logout and across restarts.
- **Moving into the files and back, with nothing lost.** Each item is written at its destination, read back, and only then deleted from where it was, and a record in the data folder notes each item's step, so a move stopped partway, by a crash or a power cut, finishes at the next start in the same direction and never deletes an item whose copy did not read back. Into the files: the daemon's own secrets go into `secrets.json` ([Spec-020 §Daemon Secrets](./020-data-retention-export-and-deletion.md#daemon-secrets)), and each Claude Code account's sign-in goes from its keychain entry into that account's `.credentials.json`, the file Claude Code keeps a login in whenever the keychain rejects its write ([Claude Code §Credential management](https://code.claude.com/docs/en/authentication#credential-management)); that move is the named exception in [ADR-026](../decisions/026-provider-credential-custody-posture.md). A Codex account's sign-in is already a file: Codex keeps it in `auth.json` in the account's home, its default store ([Codex `defaults.toml`](https://github.com/openai/codex/blob/main/codex-rs/config/defaults.toml)), and the daemon starts every Codex process of an account home with `-c cli_auth_credentials_store="file"`, an override every Codex subcommand takes ([Codex `config_override.rs`](https://github.com/openai/codex/blob/main/codex-rs/utils/cli/src/config_override.rs)), so a Codex sign-in never moves. Back: the same items, the other way, and each file is deleted once its items read back from the keychain.
- **A new sign-in, and a renewal, while the service runs.** The provider writes each one itself, and the daemon writes neither. A process outside a user context has only the System keychain in its search list ([TN3137: On Mac keychains](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains)), so Claude Code's keychain write is rejected and it keeps the login in `.credentials.json` at mode `0600` ([Claude Code §Credential management](https://code.claude.com/docs/en/authentication#credential-management)); Codex writes `auth.json` at mode `0600` in its file store ([Codex `auth/storage.rs`](https://github.com/openai/codex/blob/main/codex-rs/login/src/auth/storage.rs)). The probes confirm both for a fresh sign-in and for a renewal.
- **Turned off in Login Items & Extensions.** When an administrator turns the service off in System Settings › General › Login Items & Extensions ([Change Login Items & Extensions settings on Mac](https://support.apple.com/guide/mac-help/change-login-items-extensions-settings-mtusr003/mac)), launchd stops starting it, and `SMAppService.statusForLegacyURL`, which Apple gives apps "unable to adopt the new daemon and agent packaging guidelines but still want to know when a user disables its legacy daemons or agents", reports `requiresApproval` for its property list, the status "returned if the user revokes consent for the service to run in System Settings" (`SMAppService.h` in the macOS 27.0 SDK). With no approval before the install, that status means only that it was turned off, and `whileSignedOut` reads `turnedOffInLoginItems`. While the person is logged in, the app starts the daemon as its login agent, as it does when it finds none running, and the secrets and sign-ins stay in their files, so Runtime's secrets line reads `Secrets are kept unencrypted in <path>, readable by this account alone, because the service was set up to run while you are logged out.` in place of the `…because the service runs while you are logged out.` it reads while the service runs. The app's main process reads that status, as the macOS form of its operating-system interface, when it starts and each time it becomes the active app, because the person turns the service on or off in System Settings and comes back; never on a timer. Without the app, `sidekicks daemon status` reads it, in the macOS form of the command line's operating-system interface, and prints the same turned-off line. `SMAppService.h` calls the call one "intended for apps" and says "Apps that use SMAppService APIs must be code signed", but not whether a process outside an app may make it, so the probes check it from the command line ([macOS Service Probes](../operations/macos-service-probes.md)).
- **Uninstall.** `sidekicks daemon uninstall` removes the service itself behind the same one administrator password: `launchctl bootout` stops it, and the property list is deleted. The login agent is put back and started in the person's login session, and its daemon moves the secrets and sign-ins back into the login keychain before it serves anything. The move back needs the login keychain unlocked, so once items are in the files, over SSH while the person is logged out or with the keychain locked, the command changes nothing and reads `The sign-ins and secrets cannot go back into the login keychain while it is locked. Log in at this Mac, then run sidekicks daemon uninstall again.`
- **What is not logging out.** Closing the lid, sleep, locking the screen and fast user switching are not logging out: the person stays logged in, as fast user switching keeps more than one user logged in at the same time ([Switch quickly between users on Mac](https://support.apple.com/guide/mac-help/switch-quickly-between-users-mchlp2439/mac)), so the login agent keeps running through each and nothing moves to the files. A sleeping Mac runs nothing until it wakes, whichever service it has.
- **FileVault.** With FileVault on, the disk is unlocked with an account's login password at startup ([Protect data on your Mac with FileVault](https://support.apple.com/guide/mac-help/protect-data-on-your-mac-with-filevault-mh11785/mac)), so after a restart the system service starts once the disk is unlocked, not before.

## Wire Format

- The wire format is JSON-RPC 2.0 messages in one frame codec, the same bytes on the local socket and inside each message of the encrypted channel (not newline-delimited). Each frame is a 10-byte header (`kind`, `flags`, `lane`, `length`, big-endian) and a chunk of at most 65,509 bytes; a message is one lane's chunks up to the one flagged `END`: a 4-byte JSON length, one JSON-RPC 2.0 message in UTF-8, then any byte attachments, each after its 4-byte length and referenced once from the JSON as `{"$bytes": <index>}`.
- The daemon reads each message as it arrives, before any count: no call that takes a slot, response or `$/cancelRequest` waits behind slotless calls still running. A subscription cancel and a stop each hold one of `MAX_CALLS_IN_FLIGHT` running counts until its reply holds its place among the replies waiting to be sent; one that finds no count free waits, in arrival order behind any other that waits, with its credit unreturned, while every later message is still taken. A `terminal.write` takes no count, since its shell's own window bounds it ([Spec-002 §Required Behavior](./002-machine-registration.md#required-behavior)). At most 100 replies to messages that take no slot wait unsent; past that the daemon takes no further message until one is sent, though it still reads every frame.
- Maximum message size: 7 MiB of JSON (`MAX_MESSAGE_BYTES`), sized to the largest request the connection carries: a send at Codex's own limit, 2^20 characters counted in characters, at up to 6 bytes each once JSON-escaped, plus 1 MiB for its envelope. A message's attachments are capped at their own 4 MiB. It is the transport's bound, never an on-screen limit.
- Maximum request `id` size: 256 bytes once JSON-encoded. The `id` is opaque to the substrate and echoed verbatim, which makes it the one member of a response the caller sizes; an id past the bound is refused as `-32600 Invalid Request` **before dispatch**, and the refusal — like every error frame for an envelope whose id could not be recovered — carries `id: null` rather than echoing the offending value, per JSON-RPC 2.0 §5. Refusing the request is the only place the rule can be enforced: an oversized **response** cannot carry its own error, so the alternative is a closed connection on a request the daemon accepted.
- Every request (except health checks) must include a `protocolVersion` field carrying an ISO 8601 date-string in `YYYY-MM-DD` form (per [API Payload Contracts](../architecture/contracts/api-payload-contracts.md)); the daemon checks it once per request, at its one admission site. A notification or response that carries `protocolVersion` is no message and is refused `-32600` with `id: null`.
- A client notification other than `$/cancelRequest` is dropped, never answered (JSON-RPC 2.0 §4.1). A client response or error response is refused `-32600 Invalid Request`, under its id when that id is within the bound and `id: null` otherwise.
- Serialization: JSON through serde, decoded and checked against the method table's serde types and garde checks before dispatch. A method's params are one JSON object whose members go by name; params by position (a JSON array, which JSON-RPC 2.0 also allows) are refused as `-32602` `request.paramsInvalid` before dispatch. Bulk bytes ride as attachments beside the JSON, never base64; there is no other binary serialization.
- The client in `crates/sidekicks-client` wraps JSON-RPC in typed methods drawn from the contracts' method table, decoding each reply with serde and garde; the CLI links it, and the desktop loads it through its Node-API package, `packages/client-sdk`, in a helper process.

## Default Behavior

- Desktop app default is auto-connect to the local daemon through OS-local IPC.
- If the daemon is not running, the desktop app's main process starts it — a detached spawn, the per-user service the install registered, or on Windows the per-user logon task — under one cover that reads `Starting the background service…`, before the renderer gives up.
- CLI default is connect to the same typed local daemon contract rather than reimplement daemon logic inline.
- The first implementation release of the local control surface is CLI-first, with the desktop app's client helper consuming the same stabilized contract afterward. The renderer consumes the bridge API over the client helper's port per [Spec-021 §Trust Stance](./021-desktop-app-and-renderer.md#trust-stance), not this daemon contract directly.

## Fallback Behavior

- If version negotiation fails, read-only compatibility may continue, but mutating operations must be blocked until versions are compatible. Each app accepts its own service version and the one before it. Outside that window the console is read-only, and the session's working line names in words the side that is behind — the background service or the app — with a press that opens its fix: the service's update on Settings › Runtime or the app's update on General.
- If the daemon cannot be started automatically, the client must return actionable status instead of hanging.
- From an SSH session while this account has no session at the Mac's screen, `sidekicks daemon install --while-signed-out` cannot install the system service, whose administrator password is asked at the Mac's screen, so it refuses with `This Mac cannot keep the background service running while you are logged out: <cause>.` and the cause in plain words, `This Mac cannot keep the background service running while you are logged out: turning it on needs this account logged in at the Mac's screen. Log in at this Mac, then run the command again.`, and nothing changes; the login agent keeps running as before (§The service on a Mac while logged out).
- While the daemon is unreachable or reconnecting, the client retries and says so in exactly one place rather than hanging, and it offers an explicit retry. Nothing already read is emptied, dimmed, or disabled: a list that could not be refreshed says only that, a draft keeps its text, and no open surface closes. The reading arms only once the daemon has answered at least once since the client started, so a client started into an outage reports a daemon that would not start rather than a connection that was lost. In the console that one place is the session's working line ([Spec-018 §Required Behavior](./018-observability-and-failure-recovery.md#required-behavior)). The client opens a lost link again after each wait of `LINK_REOPEN_BACKOFF_MS`, its last wait repeated, for `LINK_REOPEN_WINDOW` from the loss, each attempt's handshake held to `HANDSHAKE_DEADLINE`, all in `crates/sidekicks-client/src/daemon_connection.rs`; it reads as reconnecting for the whole window, and once the window passes with every attempt failed it is down until the explicit retry.

## Interfaces And Contracts

- `ConnectionInitializeRequest` and `ConnectionInitializeResponse` must perform version negotiation. The reply carries `deviceId`, the connecting device's own id, so a client can tell its own hold on a shell from another device's.
- `DaemonStatusRead` (`daemon.status.read`), `DaemonStop` (`daemon.stop`) and `DaemonRestart` (`daemon.restart`) must exist as IPC methods. Daemon **start** is not one: a stopped daemon has no IPC server to receive a call, so starting is a process launch — `sidekicks daemon start`, or the desktop app's main process per §Default Behavior, spawning the daemon detached, starting the per-user service the install registered, or on Windows running the per-user logon task — which then awaits `ConnectionInitializeResponse`. See [Plan-005 §Phase R1](../plans/005-local-ipc-and-daemon-control.md#phase-r1--namespace-handlers) for the methods and [§Phase R3](../plans/005-local-ipc-and-daemon-control.md#phase-r3--client-delivery) for the CLI's start.
- `Subscription<T>` must support event streams that catch up, then follow, where appropriate.
- `DaemonStatusRead` must carry everything a status surface prints, in one response rather than several reads: whether the daemon is up, since when (`startedAt`), the workspace it holds, its `version`, and its processor use (`{percent, readAt}`) and memory use (`{residentBytes, readAt}`), each `null` until it has been read, and `secretsFile`, the path of the file it keeps its secrets in, present only on Linux where no Secret Service answers and on a Mac while its secrets are in `secrets.json`, from the logged-out service's takeover until `sidekicks daemon uninstall` moves them back, including after that service is turned off in Login Items & Extensions ([Spec-020 §Daemon Secrets](./020-data-retention-export-and-deletion.md#daemon-secrets)) — plus `wakeHelper`, the `ProviderWakeHelperState` (`installed | notInstalled {reason} | turnedOff | missing`, one closed set for the helper) reading `installed`, `turnedOff` or `missing`, the machine's one wake helper, present on macOS and Linux while any account's `Wake this computer for it` is on, `turnedOff` macOS's alone ([Spec-025 §Required Behavior](./025-provider-accounts-and-credential-homes.md#required-behavior)), plus, while a relay is configured, the per-device relay block §Required Behavior describes, its counts running since the service started. It also carries a relay pin the daemon refused. The CLI's text output and its `--json` output are two renderings of that one response.
- The desktop app exposes the daemon's typed surface to its renderer, over the client helper's port, as one generic call and one generic subscribe rather than a bridge member per verb, so a method the daemon registers reaches the renderer with no new bridge member added; the renderer still holds no daemon connection of its own per [Spec-021 §Trust Stance](./021-desktop-app-and-renderer.md#trust-stance). The web client and the iPhone app run the same front end through the same bridge interface, implemented over their end-to-end channel ([Spec-027](./027-remote-control.md)); a member that host cannot serve is absent there rather than refusing.
- The service's own control surface, each verb once and none a second place a value already set here can be set. Each is a [Plan-005](../plans/005-local-ipc-and-daemon-control.md) task unless another plan is named.
  - `daemon.flush` — the main process's quit call: the daemon writes what it holds and stops nothing.
  - `daemon.ping` — the client helper's liveness check, sent only after 5 seconds with no frame from the daemon; after 20 seconds with no frame the link counts as dead, and the helper reports the link's state to main.
  - `daemon.retention.read` — the retention bounds, with the counts `Delete old data` would remove on the same reply; `daemon.retention.update` changes one bound; `daemon.retention.subscribe` sends the bounds first and then each change, which the main process's own log and an open Runtime page follow; `daemon.retention.purge` is `Delete old data`, the one purge, which deletes each session's rows with SQLite's `secure_delete` on, so the freed pages hold nothing readable, checkpoints the write-ahead log with `TRUNCATE` once the delete commits ([Spec-020 §Required Behavior](./020-data-retention-export-and-deletion.md#required-behavior)), and, when it removed a session while `Back up automatically` is on, starts a backup run once it is done.
  - `daemon.config.read` and `daemon.config.update` — the listener port, the run limit, `workflowChainAskAfterRuns` (a number of runs, or `null` for `Never ask`), `Max steps per turn`, `Spend limit`, `Tokens per run`, the tool memory cap, the package caches' limit (`null` for `Unlimited`), and the diagnostic switches, one member changed per call.
  - `daemon.packageCache.list` → `{bun: {bytes, readAt}, uv: {bytes, readAt}}`, read only when asked, and `daemon.packageCache.clear {cache: bun | uv | all}`, answered with the new reading; what the caches hold and when a limit clears one are [Spec-015](./015-workflow-authoring-and-execution.md)'s, and [Plan-014](../plans/014-workflow-authoring-and-execution.md) builds them.
  - `provider.terminalSession.list {}` → `{sessions: TerminalProviderSession[]}`, each `{provider, name, threadId, state: working | idle | unreachable}` — the provider sessions a person typed in a terminal, inside that provider's shared service, read when the stop confirmation opens and while an update waits; [Spec-014](./014-multi-agent-orchestration.md)'s, built by [Plan-013](../plans/013-multi-agent-orchestration.md).
  - The update, on the main process's own supervisor bridge rather than the daemon: `daemon.requestUpdate()`, `daemon.cancelUpdate()` and `daemon.subscribeUpdate(handler)`, whose deliveries carry `step` (`checking | downloading | verifying | waiting | restarting`), `percent` while `downloading` (0 to 100, the bytes received against the release's size), `waitingOn` (the named work while it waits), `cancelable` (false once main has asked the old service to stop) and, at the end, `outcome` (`landed` or `rolledBack` with both versions, the latter with its reason, or `alreadyNewest`). They run in main because the daemon refuses to replace its own program while connections are open. [Plan-020](../plans/020-desktop-app-and-renderer.md) builds them.
  - The command line: `sidekicks daemon install` (with `--while-signed-out`), `uninstall`, `start`, `stop`, `restart` and `status`; `sidekicks account login` (with `--no-browser`) and `account logout`, over the service's `account.signIn`, `account.signIn.subscribe`, `account.signInAttempt.cancel`, `account.signInCode.submit` (the pasted code, the command line's alone) and `account.signOut`; `sidekicks daemon update` (with `--check`); `sidekicks open <address>`.
  - The daemon's own processor and memory readings, and the read that takes them again, ride the status read above rather than a verb of their own.
  - On Windows and macOS, the `daemon.status` topic the main process publishes to its windows carries `whileSignedOut: on | off | passwordOutOfDate | wslSessionsWait | notOffered | turnedOffInLoginItems`, whether the service keeps running while the person is signed out: `passwordOutOfDate` and `wslSessionsWait` are Windows' (§The service on a Windows computer), `wslSessionsWait` where the signed-out service cannot reach WSL, so sessions in WSL wait while the person is signed out and Runtime reads `Sessions in WSL wait while you are signed out of Windows.`; `notOffered` is a Mac's where the flag refused, which draws no Runtime line; and `turnedOffInLoginItems` is macOS's, the system service `--while-signed-out` installed and turned off in Login Items & Extensions since; the old way of installing it has no approval to wait for, so no value says it waits (§The service on a Mac while logged out). Absent on Linux.
- The service's backups, crash reports and data acts. Each is a [Plan-005](../plans/005-local-ipc-and-daemon-control.md) task, and what each act does to the data is the named spec's.
  - `daemon.backup.read` → the last run, the folder, the total size, and each backup with its time, its size and the app version that wrote it; `daemon.backup.start` runs one now. The daily run is off until the person turns it on, runs on the service's scheduler at the first moment of the day with no turn running, and never stops or delays work. Each run ends in `daemon.backup.completed` or `daemon.backup.failed`, and a restore in `daemon.backup.restored`, on the daemon's own sentinel session, written by the `database restore` mode into the restored database before the service starts. What a backup holds and how long copies are kept is [Spec-013 §Backup Policy](./013-persistence-and-recovery.md#backup-policy)'s.
  - `daemon.crashReport.list` reads the crash reports this machine keeps, from `sidekicks crash list` and from a linked device. Reports never leave the machine that crashed; each holds the process type, both versions, the platform and the crashing thread's stack as module names and offsets, with file paths cut to their names and session ids replaced by stable hashes, and goes with the diagnostic logs.
  - The command line's data verbs, each doing what its Settings action does: `sidekicks data export <folder>`, which runs with the service running; `sidekicks data erase` and `sidekicks data restore <backup>`, each refused while the service holds the data directory; `sidekicks account delete`, over the control plane's `account.delete`, which signs this machine out and leaves its local data to `Erase all data`; and `sidekicks relay repin --force` with the new hash pasted, sent to the daemon as `relay.repin {spkiHash}`, the recovery a refused relay pin names; the daemon refuses and changes nothing when the hash does not match the key the relay presents. Their effects are [Spec-020](./020-data-retention-export-and-deletion.md)'s, [Spec-013 §Backup Policy](./013-persistence-and-recovery.md#backup-policy)'s and [Spec-027](./027-remote-control.md)'s. `sidekicks account delete` is the one way to delete the hosted account: a person who has lost every machine installs the command-line tool on another computer, runs `sidekicks account login` there, signs in with a passkey on the sign-in page, and runs `sidekicks account delete`. The SQL in the [Hosted Account Deletion Runbook](../operations/hosted-account-deletion-runbook.md) is a break-glass procedure the person runs on their own relay, used only when they have no passkey left to verify a sign-in.
- On a Windows computer (§The service on a Windows computer). [Plan-005](../plans/005-local-ipc-and-daemon-control.md) Phase R4 builds them.
  - The place a session, a project and a provider reading carry, `Place`: `"windows"`, or `{distro}` (`WindowsPlace` and `WslPlace`), written on a session at creation and never changed. Absent on macOS and Linux. Work runs only in a WSL 2 distribution; a WSL 1 one appears only as a provider's `Command` row that reads `Needs WSL 2` (`{state: "distributionNeedsWsl2"}`).
  - Attaching a folder refuses one in a WSL 1 distribution with `repoMount.distributionNeedsWsl2` and one in a distribution not on this computer with `repoMount.distributionNotFound`.
  - The session notices: `providerMissing` carries `place` on a Windows computer with a WSL 2 distribution; `distributionRemoved {sessionId, distro}`, `wslNotAnswering {sessionId}` and `distributionRestartFailed {sessionId, distro, error?}` draw the flow rows of §The service on a Windows computer.
  - The `daemon.status` topic the main process publishes to its windows gains `cannotStart {reason: connectionNameTaken | turnedOffInLoginItems}`: `connectionNameTaken` is Windows', read from the status file when the pipe is absent, beside the `whileSignedOut` above; `turnedOffInLoginItems` is macOS's, read from the login agent's `requires-approval` registration status, Runtime and the boot card reading `The background service cannot start because it is turned off in Login Items. Turn it on in System Settings, then it starts on its own.` with `Open Login Items`. `DaemonStatusRead` carries the `WSL` block `sidekicks daemon status` prints, one entry per distribution with a WSL server running or a session in it: running, stopped or not answering since a time, and its session count.
  - The command line: `sidekicks daemon install --while-signed-out`; the in-distribution `sidekicks`, which dials its WSL server's Unix socket and hands `daemon install`, `uninstall`, `start`, `stop` and `data erase`, and `account login` or `account logout` while the service is stopped, to the Windows CLI through interop, printing the interop-off line and exiting nonzero where it cannot.
  - The daemon's helper modes: `sidekicks-daemon wsl`, the WSL server, whose ready line on standard output is `<prefix>{protocolVersion, pid}` and carries no token; and `sidekicks-daemon banners`, the logon task's instance while the signed-out task holds the service.
  - The channel between the daemon and a WSL server is HTTP/2 over that `wsl.exe`'s standard input and output: `h2` 0.4.20 on tokio on both ends, the daemon the client, every writer sending through the stream's granted capacity, with a stream flow window of 1 MiB and a connection window of 16 MiB on both ends. Three `h2` defaults are set on purpose, since both ends are ours: the small-DATA-frame budget, which closes the whole connection with `ENHANCE_YOUR_CALM` when spent, is raised so a terminal's stream of small output frames never trips it, and the WSL server coalesces a PTY's reads while its stream waits for capacity; the local error-reset limit (1,024 by default) is lifted, because its count never resets over a channel that lives for days; and nothing pings at idle, since `h2` has no keepalive: a PING goes out only when a call passes its deadline, and no answer within 5 seconds ends the channel and the daemon starts the server again. A standard handle that is not a console is relayed raw both ways; where a WSL build does not carry binary intact, the channel carries its frames base64-encoded on the same link.
  - The credential store while the service is stopped: the Windows CLI calls `sidekicks-platforms`' credential code itself, and the in-distribution CLI hands the command to it through interop.
- The typed client SDK must expose the same semantic surface to the desktop app's client helper and the CLI. The renderer consumes a narrower bridge API, over the client helper's port and its method allowlist, per [Spec-021 §Trust Stance](./021-desktop-app-and-renderer.md#trust-stance), not this SDK directly.

## State And Data Implications

- Client cache must not become the daemon's state store.
- Daemon supervision state may live in the desktop app's main process, but daemon runtime truth remains in daemon-owned persistence and projections.
- Version compatibility decisions must be visible to clients and logs.

## Example Flows

- `Example: The desktop app opens while the daemon is not running. The main process starts the daemon as the person's own background service, never as its child; its client helper negotiates protocol version through sidekicks-client, and main then exposes renderer-accessible capabilities via the preload bridge and the client helper's port per Spec-021 §Trust Stance; the renderer is not a direct daemon client. Quitting the app later calls daemon.flush and leaves the daemon and its work running.`
- `Example: The CLI requests a run-state subscription through the same client SDK and receives canonical updates without duplicating daemon logic.`

## Implementation Notes

- Keep IPC semantics typed and narrow. Avoid renderer-driven arbitrary shell escape hatches.
- Local IPC choice is a security boundary, not merely a performance choice.
- Treat the CLI as the contract proving ground for daemon control behavior, not as a disposable wrapper around desktop-only logic.

## Pitfalls To Avoid

- Giving renderer code direct untyped native execution access
- Allowing silent version skew for mutating operations
- Reimplementing daemon state transitions in the CLI

## Acceptance Criteria

- [ ] The desktop app's client helper and the CLI share one typed daemon client surface; the renderer consumes the bridge API over the client helper's port per [Spec-021 §Trust Stance](./021-desktop-app-and-renderer.md#trust-stance), not this daemon contract directly.
- [ ] The daemon can be started, pinged, and subscribed to through local IPC.
- [ ] Version mismatch blocks unsafe mutation while keeping status visibility available.
- [ ] **AC-N1** (`session.create`) — handler accepts a valid request envelope and returns a `SessionRead`-shape result with a stable `sessionId` (per [Spec-001 §Interfaces And Contracts](./001-session-core.md#interfaces-and-contracts)); a malformed payload rejects with `-32602 InvalidParams` and the handler closure is never invoked (per [I-005-6](../plans/005-local-ipc-and-daemon-control.md), schema-validates-before-dispatch). Verified directly by Plan-005 Phase 3 test IDs `W-005p-3-T1` + `W-005p-3-T2` (a malformed payload is refused `-32602` before the handler runs, I-005-6); `W-005p-3-T2` lives in the tests of `crates/sidekicks-daemon/src/ipc/registry.rs`, `W-005p-3-T1` lands with the session service it round-trips through, and both are grep-discoverable in [Plan-005 §Phase 3 test plan](../plans/005-local-ipc-and-daemon-control.md).
- [ ] **AC-N2** (`session.read`) — handler returns a `SessionRead`-shape result for a known session id (per [Spec-001 §Interfaces And Contracts](./001-session-core.md#interfaces-and-contracts)). The unknown-id rejection wire-shape is the domain refusal number `-31000` + `data.type: "session.notFound"` + `data.category: "notFound"` per [error-contracts.md §JSON-RPC Wire Mapping](../architecture/contracts/error-contracts.md#json-rpc-wire-mapping) + [Plan-005 §Invariants I-005-7](../plans/005-local-ipc-and-daemon-control.md#invariants) (every registered domain refusal answers `-31000`, its dotted-namespace code riding as `data.type` and its category as `data.category` in the two-layer envelope; an id that resolves to nothing is such a refusal, never `-32602`), implemented via `SessionNotFoundError` at `crates/sidekicks-daemon/src/ipc/session_errors.rs` and its `map_json_rpc_error` discriminator branch at `crates/sidekicks-daemon/src/ipc/jsonrpc_error_mapping.rs`. Wire shape inherits [Spec-001 §Required Behavior](./001-session-core.md#required-behavior). Structural invariants (I-005-5 duplicate-registration rejection at register-time + I-005-6 schema-validates-before-dispatch) inherit via the shared `router.register` substrate, proven by Plan-005 Phase 3 test ID `W-005p-3-T5`; the per-method binding lives at `crates/sidekicks-daemon/src/ipc/handlers/session/read.rs`. Verified directly by Plan-005 Phase 3 test ID `W-005p-3-T8` (a known id is read, and an unknown id is refused `-31000` with `data.type: "session.notFound"`); lives in the tests of `crates/sidekicks-daemon/src/ipc/handlers/session/read.rs`.
- [ ] **AC-N3** (`session.event.subscribe`) — handler returns the subscribe-init envelope (`{ subscriptionId }`) BEFORE the first catch-up notification per [I-005-9](../plans/005-local-ipc-and-daemon-control.md) (subscribe-init response precedes the first notification frame); the client-side `Subscription<EventEnvelope>` is a `futures::Stream` per [CP-005-3](../plans/005-local-ipc-and-daemon-control.md) (typed JSON-RPC client transport cross-plan obligation); a subscription's end releases its feed on every path per [I-005-10](../plans/005-local-ipc-and-daemon-control.md). Verified directly by Plan-005 Phase 3 test IDs `W-005p-3-T3` (subscribe round-trip + cancel idempotency) + `W-005p-3-T6` (the daemon writer's response-before-notify ordering: no chunk of a subscription's lane is written before the `END` chunk of its subscribe response) + `W-005p-3-T7` (client-side registration of the subscription before its response is handed on). T3 + T6 live in the tests of `crates/sidekicks-daemon/src/ipc/handlers/session/event_subscribe.rs`; T7 lives in the client's integration tests in `crates/sidekicks-client/tests/it/`.
- [ ] A request whose `id` exceeds the §Wire Format bound is refused as `-32600 Invalid Request` before the handler runs, the refusal carries `id: null` rather than the offending value, and the connection stays open — the request fails, not the session. Stated as [I-005-20](../plans/005-local-ipc-and-daemon-control.md); verified by the oversized-id test of `crates/sidekicks-daemon/src/ipc/local_gateway/tests/requests.rs`, which covers the one id gate's refusal and carries an under-bound id as its negative control.
- [ ] On macOS, `sidekicks daemon install --while-signed-out` prints `With this on, sign-ins and secrets are kept in files readable by this account alone, because a service that runs while you are logged out cannot reach the login keychain.` before it asks, and refuses with `This Mac cannot keep the background service running while you are logged out: <cause>.` and its cause, changing nothing, from a session with no screen, where another account has it on, where the administrator password is not given, and where macOS refuses the install.
- [ ] On a Mac, the system service's property list in `/Library/LaunchDaemons` names the account that ran the install in `UserName` and the daemon the login agent runs, the command line's own copy on a Mac with only the command line, and the daemon it starts runs as that account, with no process of ours running as root.
- [ ] Once the administrator password installs the system service, the daemon's secrets are in `secrets.json` and each Claude Code sign-in in its account's `.credentials.json`, each at mode `0600`, and none is left in the login keychain; a move stopped partway finishes at the next start with nothing lost.
- [ ] `sidekicks daemon uninstall` on a Mac puts every secret and sign-in back into the login keychain, deletes the files and puts the login agent back, and with items in the files and the login keychain locked it changes nothing and reads `The sign-ins and secrets cannot go back into the login keychain while it is locked. Log in at this Mac, then run sidekicks daemon uninstall again.`
- [ ] A dispatched handler reads the calling connection's device from its dispatch context, and a write records it. Stated as [I-005-19](../plans/005-local-ipc-and-daemon-control.md); verified by [Plan-005](../plans/005-local-ipc-and-daemon-control.md) Phase 2B task `T-005p-2B-1`.
