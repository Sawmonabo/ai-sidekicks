## Purpose

Define how multiple agents collaborate inside a session and how their channels and run relationships are represented.

## Scope

This spec covers channel creation, parent-child run linkage, cross-agent collaboration, and background helper activity — including session goals, cost derivation for budget enforcement, and the orchestration-level governance of provider-native in-session subagents (campaign B6).

## Non-Goals

- Workflow authoring syntax
- Defining provider-native subagent APIs — the `subagentPolicy` and driver-op shapes are [Spec-005](005-provider-driver-contract-and-capabilities.md)'s; this spec governs only their orchestration use (§Provider-Native Subagents, campaign B6)
- Notification policy

## Required Behavior

- A session must support multiple active agents at once.
- Agents may collaborate through one or more channels inside the same session.
- Cross-agent communication must use canonical channel publication, artifact references, approvals, or persisted run linkage. V1 must not depend on a separate direct run-to-run messaging primitive.
- Parent-child run relationships must be durable and auditable.
- Internal helper runs must remain distinguishable from user-visible agents while still appearing in canonical history.
- Per-agent model, driver, and runtime-node selection must be allowed within one session.
- Orchestration must remain valid even when a driver has no native subagent concept.

## Default Behavior

- Default collaboration mode is explicit: new child runs are created only by user request or workflow definition.
- Child-run output defaults to publishing a summarized row into the parent session timeline, with expandable detail.
- New non-direct collaboration channels default to inheriting session membership unless later restricted by policy. A `direct` channel is the single V1 exception: its membership is the immutable two-human pair fixed at creation (§Interfaces And Contracts).
- V1 delegation defaults to one parent-child layer. A child run is not allowed to create another child run under the canonical first-release contract.
- Concurrent child runs are allowed, but admission remains subject to explicit runtime scheduler limits rather than unbounded fan-out.

## Fallback Behavior

- If a driver does not support native subagent creation, the runtime must model delegated work as separate runs with explicit linkage and channel context.
- If child-run detail loading fails, the summary row remains available and marked incomplete.
- If channel-specific delivery is unavailable, output falls back to the session's default visible channel with preserved provenance. (Tier-6 audit, A-016-18: "unavailable" = the target channel is archived at publication time, or its row is missing at projection time; "preserved provenance" = the event payload keeps the original `channelId` while the projection re-homes display to the main channel.)
- **Delivery fallback never widens audience** (2026-08-03 vision reconciliation): the re-homing above applies only to `participants`-audience channels. Content from an audience-restricted channel (`humans-only`, and therefore every `direct` channel) is never re-homed to the main channel or to any other `participants` channel — an undeliverable message there fails visibly to its sender instead, because re-homing would hand agent-excluded content to every agent in the session (§Interfaces And Contracts).
- If child-run creation would exceed the supported delegation depth, the runtime must reject the request with explicit limit detail and must not create hidden background work.
- If child-run creation would exceed the active-child scheduler limit, the runtime must reject the request with explicit capacity detail rather than silently dropping or auto-spawning overflow work.

## Interfaces And Contracts

- `ChannelCreate` must create a session-scoped communication surface. Channel lifecycle mutations (`ChannelMute` / `ChannelUnmute` / `ChannelArchive`) and a daemon-native roster read (`ChannelRosterRead`, carrying per-channel config + arbitration state — and, since the 2026-08-03 amendment (D-016-21), each entry's channel kind with a `direct` entry's member pair, the read-back of the create-side fields below) complete the channel surface (Tier-6 audit, D-016-6/D-016-12).
- **Channel audience (2026-08-03 vision reconciliation, D-016-21):** `ChannelConfig` carries an `audience` member — `participants` (default: humans and agents, the pre-amendment behavior) or `humans-only` (agents are never given the channel's content as context). Audience is a **normative daemon obligation, not renderer etiquette**: each daemon MUST exclude every `humans-only` channel's content from every prompt, context window, tool result, and artifact it assembles for any agent, **regardless of which participant owns that agent** — including when the agent's own owner is a member of that channel ([vision.md §The Collaboration Model](../vision.md): "each daemon scopes which channels its agents are given as context — audience is a runtime-enforced contract, not etiquette"). Read scope is the privileged grant and is separate from act scope: an agent addressable in a session gains no read access to that session's `humans-only` channels. Audience is expressible only on an explicitly created channel: the bootstrap `main` channel has no channel row and emits no `channel.created` (§State And Data Implications), so it carries no `ChannelConfig` — its audience is always `participants` and is never restrictable, leaving the one channel every session has with no unspecified case. The surveyed platforms draw the same split — Discord separates message delivery (`GUILD_MESSAGES`) from the privileged `MESSAGE_CONTENT` intent that makes content readable ([Discord Gateway events](https://docs.discord.com/developers/events/gateway)), and Slack scopes an app's mention delivery (`app_mention`) separately from channel-history read ([Slack `app_mention` event](https://docs.slack.dev/reference/events/app_mention)); both accessed 2026-08-03.
- **Direct channels (2026-08-03 vision reconciliation, D-016-21):** `ChannelCreate` accepts a `direct` channel kind — a two-human direct-message channel whose member pair is fixed at creation and immutable thereafter (no add, no remove, no widen). On this kind `audience` is `humans-only` **by construction and immutable**: the daemon forces the value, refuses any create supplying a conflicting one, and admits no mutation that would widen it — so `audience` is not caller-settable on a `direct` channel. The agent-turn members of `ChannelConfig` are refused on this kind under the same fail-closed disposition: `turnPolicy`, `roundRobinOrder`, and `moderation` all govern agent turns on a channel that admits no agents, and `round-robin` is structurally unsatisfiable here because its create validation requires a non-empty agent order (§Turn Policies) — a `direct` create supplying any of the three is refused rather than silently carrying inert configuration. A `direct` channel is omitted from this spec's own roster surface for non-members: `ChannelRosterRead` omits it for any caller outside the pair — the daemon half of a deliberately two-surface non-disclosure property whose control-plane half is [Spec-002 §Interfaces And Contracts](002-invite-membership-and-presence.md#interfaces-and-contracts)'s matching `ChannelList` per-caller omission (amended 2026-08-03 alongside this spec; Plan-002 I-002-6). Each surface's filter belongs to the plan that owns that surface, and only together do the two close a `direct` channel's existence metadata across V1's channel-enumeration surfaces — neither closes it alone. Non-direct channels keep open session-wide membership in V1 per §Resolved Questions and V1 Scope Decisions. Confidentiality from **non-member humans** is a distinct, relay-layer property this spec depends on rather than defines — defined in [Spec-008 §Per-Channel Recipient Scoping (V1)](008-control-plane-relay-and-session-join.md#per-channel-recipient-scoping-v1) (amended 2026-08-03 alongside this spec): a membership-restricted channel's events are sealed to the channel member set intersected with the session's current recipient set, and are never served on peer history backfill outside that set.
- **Agent surface (Tier-6 audit, A-016-2):** Plan-016 owns the V1 agent identity surface satisfying §Required Behavior's per-agent model/driver/node selection — `AgentAttach` / `AgentDetach` / `AgentConfigUpdate` / `AgentList`, with the agent persona `{name, driverName, modelId, defaultNodeId?, config?}` durable via `agent.*` events ([Spec-006 §Channel and Agent Lifecycle](006-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle)). `OrchestrationRunCreate.targetAgentId` resolves against this surface; an unknown or detached agent is a typed refusal.
- `OrchestrationRunCreate` must allow parent linkage, target agent, target node, and target channel.
- `OrchestrationRunCreate` failure must surface explicit limit or policy rejection when depth or active-child bounds are exceeded.
- `ChildRunLinkRead` must expose parent-child relationships.
- `InternalRunFlag` must distinguish internal helper work from user-facing agents.
- **Link-type semantics (Tier-6 audit, D-016-17):** `spawn` — parent-initiated helper whose output returns to the parent's channel context; `delegate` — bounded task published to its own target channel; `handoff` — the parent transfers its continuation to the child and completes. The type is caller-declared (`linkType`, default `spawn`) and durable in the run linkage.
- **Budget surface (Tier-6 audit, D-016-5):** session budget/scheduler limits are readable and owner-adjustable via `OrchestrationBudgetRead` / `OrchestrationBudgetUpdate`.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas (§Plan-016 — including the typed `ChannelConfig` / `OrchestrationRunConfig` shapes that replace the former untyped config placeholders, D-016-4; the `ChannelConfig.audience` member, the `ChannelCreate` channel-kind + member-pair fields, and the matching `ChannelRosterRead` per-entry kind + member-pair read-back members landed there alongside this spec's 2026-08-03 amendment, D-016-21).
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes (§Channel / §Orchestration / §Agent).

## State And Data Implications

- Channel and run-link records must be durable and replayable.
- Parent-child linkage must survive recovery and replay.
- Internal helper visibility must be policy-aware but never silently omitted from audit history.
- The channel record additionally carries its audience configuration, its channel kind, and — for a `direct` channel — its immutable two-human member pair (2026-08-03 vision reconciliation, D-016-21). `audience` rides the existing typed `ChannelConfig` value; the kind and the member pair are additive fields on the channel record itself. This introduces **no new persistence table**: the member pair is fixed-arity by construction, so it needs no membership relation of its own.
- Because channel records are events-canonical projections, the channel kind and the member pair must ride the channel-creation event payload and not the row alone — a channel whose kind or pair could not be rebuilt from the event log would break the durable-and-replayable guarantee above and silently widen audience on replay.

## Turn Policies

| Policy | Behavior | Default |
| --- | --- | --- |
| `free-form` | Any participant may send at any time; addressed agent turns admit in arrival order with no turn-taking constraint | Yes (default) |
| `round-robin` | Agents take turns in a fixed order | No |
| `request-based` | Agents speak only when explicitly addressed | No |

Tier-6 audit ratifications (D-016-19): a `round-robin` channel requires a non-empty agent order in its channel config at create time (validation refusal otherwise); the fixed order is that config value, and the next-due cursor derives from the durable run-admission sequence (no separate cursor store). `request-based` is **structurally satisfied in V1**: every agent run is explicitly created (§Default Behavior — child runs only by user request or workflow definition; no agent-initiated speech exists in V1), so every agent turn already carries an explicit addresser and admission adds no check beyond `free-form`. The policy value is accepted and recorded; dedicated request-addressing primitives become meaningful only when agent-initiated communication arrives (V2, with conclusion detection). Turn-policy enforcement governs **agent** runs; human participants are never turn-blocked.

**Activation is addressing-gated under every turn policy in V1** (2026-08-03 vision reconciliation — [vision.md §The Collaboration Model](../vision.md)'s ratified activation invariant: agents "act when mentioned or dispatched — never by interjecting into human-to-human exchanges"). An agent produces a turn only in response to an explicit addressing act directed at that agent; a channel message addressing no agent admits **no** agent turn, under `free-form` exactly as under `request-based`. Turn policy therefore governs the **ordering** of admitted agent turns and never governs whether an unaddressed agent may activate — the `free-form` and `request-based` rows above are ordering variants of one activation rule, which is why `request-based` remains structurally satisfied (D-016-19) rather than being the only addressing-gated policy. The V1 addressing act is `OrchestrationRunCreate` naming a `targetAgentId` (§Interfaces And Contracts); a client-surface `@mention` is sugar that resolves to that act and introduces no new wire contract. **An agent-authored channel message is never an addressing act in V1** — agents do not activate agents through channel speech; runs are created only by user request or workflow definition (§Default Behavior), which is also the V1 loop-prevention bound. This pin structurally resolves the case the surveyed platforms leave undefined — a plain unaddressed reply in a thread where several agents are live admits **zero** agent turns rather than an implementation-defined subset: mention-gating is the surveyed default for channel-resident bots ([Microsoft Teams: channel and group conversations](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/channel-and-group-conversations), accessed 2026-08-03), and the reference Slack-resident assistant likewise filters other bots' replies while leaving the multi-agent unaddressed-reply case explicitly undefined ([Claude in Slack — when Claude responds](https://claude.com/docs/claude-tag/users/when-claude-responds), accessed 2026-08-03; public beta at that date). Agent-initiated speech remains V2, arriving with conclusion detection (§Stop Conditions).

Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — advisorily, on a **hard-vs-soft line keyed to provenance**: `estimated`- and `model_default`-grade headroom which authorizes those protective actions directly so a counts-absent exhausted window is never answered more weakly than a counted one (a counts-absent, non-exceeded update carries no headroom fact to act on — the pair rule in [Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — a hard action never fires off an estimated count, both because vendor token counts are documented as estimates even from the vendor's own counting endpoint and because current-generation tokenizers produce approximately 30 percent more tokens for the same text than earlier models ("The same input text produces approximately 30 percent more tokens than on earlier models … Recount prompts against the model you plan to use" — [Anthropic token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting), accessed 2026-07-12; re-verified 2026-07-17), so a window number derived from a stale pre-4.7 tokenizer assumption materially under-counts — `model_default`-grade values are tokenizer-fragile rather than merely stale; the surveyed field draws the same line — context thresholds are "automatic safeguards rather than hard stops" ([GitHub Copilot CLI context management](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/context-management), accessed 2026-07-12) — and the only hard context bound anywhere in the stack remains the provider's own real window ceiling. Conclusion detection (agent determines task is complete) remains V2.

### Cost Derivation And Absent-Cost Semantics

Session cost enforcement resolves every usage event's cost through three tiers (campaign B6). Tier (a): provider-emitted cost is consumed whenever the CLI wire supplies it, sanity-bounded — non-negative, finite, and below the configured absurdity ceiling (daemon configuration `costSanityCeilingCents`, default 10000 — a single usage event claiming ≥ $100 is rejected to tier-(b) derivation with the divergence diagnostic) (the ceiling is parameterized in the owning implementation task, not fixed here); gross divergence between an emitted cost and a derivable estimate emits a diagnostic rather than silently trusting either value (known provider over-reporting precedent). Tier (b): otherwise the daemon derives cost as token counts × the local per-model-family pricing table, with family-prefix fallback for point releases; a static local table is the ecosystem-standard mechanism, and its staleness is bounded because tier (a) takes precedence whenever the wire supplies cost. Two classification rules bound tier (b) at its table edges (Part-B fail-closed follow-up, 2026-07-17). **Explicit-$0 carve-out**: tier-(c) fail-closed applies to _unknown_ pricing only — a table entry whose price the operator explicitly set to zero (a genuinely-free local or on-prem family, e.g. an Ollama-served model) is a real price, so the family is **priced-at-zero**: admission proceeds normally, its rows emit `costCents: 0` with `costStatus: 'priced'` and ordinary `derived_*` provenance, and enforcement runs the same ceiling arithmetic as any priced family (contributing zero) — never the unpriced block; unknown-vs-explicitly-free is exactly the distinction the ecosystem's reference gateway added when it moved unmapped-model enforcement to fail-closed ([BerriAI/litellm#24949](https://github.com/BerriAI/litellm/pull/24949), accessed 2026-07-12), and without it tier (c) would false-halt every free/local model — the precise failure fail-open postures exist to avoid. **Prefix-resolves-concrete rule**: the family-prefix fallback must resolve to a concrete, explicitly-set price — a prefix hit whose matched entry carries no operator-set price (absent, or zero only via defaulting the operator never wrote) classifies the family **unpriced → tier (c), never free**: a prefix/wildcard match silently pricing at $0 is a shipped-bug class in that same gateway ([BerriAI/litellm#22609](https://github.com/BerriAI/litellm/issues/22609), accessed 2026-07-12), so the pricing-table shape MUST keep "explicitly zero" and "price absent" structurally distinct (an explicit value versus an absent field — the shape is parameterized in the owning implementation task, like the sanity ceiling above), never encoding unknown as 0. Derivation is **emit-once**: the derived value persists on the emitted `usage.cost_update` row (`costCents`, `costSource: 'derived_*'`), and replay folds those persisted row values plus the worst-case terminal debits of native-cap unpriced runs, rebuilt from their `run.queued` cap stamps (their rows are costless by design — folding rows alone would resurrect their headroom) — it never re-derives historical usage against the current table — so a pricing-table update re-prices nothing retroactively (it applies to future usage only, the same future-admissions-only idiom as `unpricedFamilyCaps`) and `observedCostCents`, warnings, and admission blocks are replay-stable. Admission preempts this tier where it can see it coming: run admission resolves the model family (the same as-of-admission resolution that stamps `admittedModelFamily`) against the pricing table, and an unpriced family admits only under a native-cap reservation — on a capless leg it **refuses at admission** (`orchestration.budget_exhausted`, `reason: 'driver_capless'`) before any queueing or spend, so the first unpriced run never starts unbounded. The mid-run path below remains only for coverage lost after admission (a pricing-table change while the run is in flight). Tier (c): otherwise the run is **budget-indeterminate and the daemon fails closed** — it emits `usage.budget_warning` with `reason: 'unpriced-model'` ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry), campaign B1) — schema-valid under the registered payload: `budgetType: 'session_cost'`, `limitValue` = the configured session cost limit, `observedValue` = the committed spend observed so far (priced cost + worst-case terminal debits of prior unpriced runs + active reservations (`reservedCostCents`) of still-running native-cap admissions; possibly 0 — the live unpriced usage itself is exactly what cannot be observed) — interrupts per the enforcement paragraph above, and blocks further queue admission for the unpriced model family session-wide (the admission refusal reuses `orchestration.budget_exhausted` with `reason: 'unpriced-model'` + `modelFamily` in `data.fields`, [Error Contracts](../architecture/contracts/error-contracts.md)).

The unpriced block — admission refusal and mid-run interrupt alike — lifts only by explicit owner action (degrade honestly, never fail open): a pricing-table update covering the family (an operator config/deploy action — the table is static local daemon configuration per the tier text above, not a session RPC; the universal escape, and the **only** one for legs without a native cap) — or, **on provider legs with a native hard budget cap only** (Claude `--max-budget-usd` at the pinned version), an owner-supplied hard USD bound under which runs proceed unpriced-but-USD-bounded with the unpriced status surfaced (their `usage.cost_update` rows carry `costStatus: 'unpriced'`, `costSource: 'unpriced_native_cap'`, `costCents` absent — the Spec-006 provenance vocabulary admits the capped-unpriced case first-class) on every affected run (supplied per model family via `OrchestrationBudgetUpdate.unpricedFamilyCaps` — one entry per family, duplicates rejected at validation; a run whose model set spans several unpriced families admits under the MINIMUM of their entries — the run-wide provider stop cannot honor per-family sub-budgets, so the conservative bound is the only safe single cap — persisted with session budgets and replayed like any budget change — the wire/state contract lives in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), this bundle). The escape reserves, never exempts: admitting a run under a family cap **reserves the full per-run cap against the session ceiling** — admission requires `observedCostCents + reservedCostCents + hardCapUsdCents ≤ costLimitCents`, else the queue refuses with the ordinary `orchestration.budget_exhausted` (whose `observedValue` then carries committed spend: observed cost including unpriced terminal debits, plus active reservations); at the run's terminal state the reservation **converts to a worst-case charge, never back to headroom**: the admitted cap moves from `reservedCostCents` into `observedCostCents` as an unpriced debit (the actual spend is unknowable by construction, so the full cap is what the ledger records — serial unpriced runs therefore consume the ceiling cumulatively exactly like priced work, and a session can never launder unbounded spend through admit-finish-repeat), the reserved amount **snapshots at admission onto the run's `run.queued` admission record** (`admittedUnpricedCapCents` — a server-stamped sibling of `effectiveRunConfig`, deliberately not an `OrchestrationRunConfig` member so a run-create request can never inject it; persisted per D-016-5), so later `unpricedFamilyCaps` updates apply to future admissions only and can never retro-shrink an active run's reservation and restart/replay rebuilds reservations and debits from the server-stamped `run.queued` records alone, the admitted cap **wires through to the driver** on the run params (`StartRunParams.admittedCostCapCents` — realized as the native cap on cap-capable legs, Claude `--max-budget-usd`, per [Spec-005](005-provider-driver-contract-and-capabilities.md)'s params; a leg that binds caps at spawn realizes it at session boundaries per the posture precedent) so the local reservation is always backed by the provider-side hard stop, and admission is daemon-serialized so reserve-then-admit is race-free, and the 80% warning threshold evaluates the same committed-spend sum; a capless leg (Codex at the pinned version — its `token_budget` is upstream-under-development) stays fail-closed until its pricing-table entry lands, so its named escape is the pricing-table path. A Day-0 model family therefore never silently runs unbounded and never hard-blocks without a named escape. Enforcement MUST NOT branch on `costSource`: provider-emitted and daemon-derived cost feed one ceiling with no dual trust regimes — the `costStatus`/`costSource` provenance mirrors ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) are observability, not policy inputs. The surveyed reference runtime's fail-open zero-cost terminal is the one surveyed posture explicitly not ported. Currency (2026-07-06): the tier-(b) table seeds from the current vendor model catalogs — Claude Sonnet 5 / Fable 5 families and Codex `gpt-5.5` / `gpt-5.4` / `gpt-5.3-codex-spark` ([Anthropic model overview](https://docs.anthropic.com/en/docs/about-claude/models/overview), [OpenAI models](https://platform.openai.com/docs/models), both accessed 2026-07-06) — and the Claude per-run `--max-budget-usd` cap ([provider-wire reference, claude.md](../reference/provider-wire/claude.md), version-pinned) is wired as defense-in-depth beneath this accountant, never as the accountant. Codex's caplessness is auditable from the pinned wire surface ([provider-wire reference, codex.md](../reference/provider-wire/codex.md) — no budget-cap parameter exists at the pin); upstream work on a `token_budget` config was observed at survey time (2026-07-02) but is not pinned and confers nothing here. The three-budget table above and the §Stop Conditions closed set (D-016-8) are unchanged by this subsection. The provider-side hard stop also survives recovery: resume/relaunch re-threads the admitted cap from the durable `run.queued` payload into `ResumeSessionParams.admittedCostCapCents`, and reservation is gated on the leg's `cost_cap` driver capability (Spec-005 matrix) — a capless leg refuses fail-closed (`reason: 'driver_capless'`), never reserves-without-enforcement. The cap rides every provider-process entry point — spawn (`CreateSessionParams`, where Claude binds `--max-budget-usd`), run start (`StartRunParams`), and resume (`ResumeSessionParams`) — so no capless window exists between admission and enforcement; and on a spawn-bound leg a native-cap run **starts only inside a provider session spawned with the matching cap**: an existing uncapped (or differently-capped) process forces a capped relaunch at the session boundary before `startRun` dispatches (the posture-relaunch precedent), never a start inside an uncapped process.

## Stop Conditions

| Condition | Trigger | Behavior |
| --- | --- | --- |
| Turn limit reached | Agent exceeds turn limit | Run completes with `turn_limit` metadata |
| Budget exhausted | Token or cost limit exceeded | Run interrupted with `budget_exhausted` reason |
| Explicit stop | User sends stop command | Run interrupted via cancel intervention |
| Idle timeout | No activity for configurable duration (default: 5 min) | Run interrupted with `idle_timeout` reason |

Conclusion detection (agent determines task is complete) is V2.

Tier-6 audit definitions (D-016-8): a **turn** is one completed assistant-output cycle attributed to a (channel, agent) pair; the consecutive-turn counter resets when a different agent (or a human participant) takes an interleaving turn in the same channel. At the turn limit the run completes with `trigger: 'turn_limit'` and further same-agent admission into that channel is refused with explicit limit detail until an interleaving turn occurs or the owner raises the limit. **Activity** for the idle timeout is any appended session event whose payload carries the run's id; the idle sweep is a daemon-owned per-run timer (default 300000 ms, per-run configurable), subject to two cross-spec exemptions: while a run's work item has a pending outbound cross-node dispatch the sweep hard-skips **that dispatch-initiating run** — such waits are locally event-quiet by construction and bounded by the dispatch's own caller-local expiry window ([Spec-024 §Required Behavior](024-cross-node-dispatch-and-approval.md#required-behavior), campaign B7); and a run in a blocking state (`waiting_for_input` / `waiting_for_approval`) is likewise hard-skipped while the state holds — for pending-work-backed blocking (a provider ask or a pipeline approval block) the exemption is expiry-bounded by the pending work's own deadline — every run-blocking ask or approval request carries one at creation (asks stamp `expiresAt` per Spec-012's ask-side bounded-wait contract; run-blocking approval mints stamp `expiryAt`, concretizing that contract's "expiry where applicable" requirement across the approval side — the mint mechanism landing with Plan-012's run-blocking mint rule, campaign B15) — ending the moment it expires or resolves and returning the run to ordinary idle semantics — or, for a denied or expired pre-turn moderation gate, exiting terminally (`moderation_denied`; expiry is denial per Spec-012's silence-is-denial rule) — per Spec-012's decoupled-but-coordinated rule ([Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior), [run-state-machine.md §Invariants](../domain/run-state-machine.md#invariants), campaign B13/B15), while the startup-reconciliation divergence halt — `waiting_for_input` carrying `recovery-needed`, backed by no pending ask or approval — is a designed human-action halt the sweep never times out: it exits only by human recovery action and surfaces on the recovery status channels ([Spec-015 §Fallback Behavior](015-persistence-recovery-and-replay.md#fallback-behavior), campaign B5/B14). Unrelated runs in the same session keep ordinary idle semantics under both exemptions. The three system-interrupt reasons (`budget_exhausted`, `idle_timeout`, `moderation_denied`) form a closed set carried on the interrupt intervention.

## Intervention Propagation

Interventions use the generic dispatcher defined by [Spec-004](../specs/004-queue-steer-pause-resume.md) and [ADR-011](../decisions/011-generic-intervention-dispatch.md). Spec-016 introduces no new intervention verbs.

- A pause, interrupt, or steer applied to a parent run does not auto-cascade to its child runs. Each child run is an independent intervention target.
- Propagating an intervention across a parent/child subtree requires the caller to submit one intervention per run. This preserves Spec-004's audit property that every run-state transition corresponds to a distinct `InterventionResult` record.
- A steer applied to a parent run does not inject content into child-run conversations — child runs receive steer content only when the steer is targeted at the child run's id.
- Child runs accept the same run-control surface as standalone runs — steer and interrupt via `applyIntervention`, pause/resume via the orchestration-layer `run.pause` / `run.resume` verbs (Spec-004; the driver never needs to know about pause). Driver capability semantics (Spec-004's steer degradation, for example) apply uniformly.
- If a future requirement demands subtree-wide propagation (e.g., "cancel this parent and all its descendants atomically"), that is a new ADR rather than a payload field addition, consistent with ADR-011's Type-1 reversibility stance.

## Moderation Hooks

- Pre-turn approval: before an agent's output is committed to the timeline, an approval gate can require human review.
- Post-turn review: after output is committed, a review flag marks it for human inspection (non-blocking).
- Both hooks integrate with the approval system (Plan-012): category `gate` for pre-turn, informational event for post-turn.
- V1 default: no moderation hooks enabled. Opt-in per channel.

Tier-6 audit ratification (D-016-10): the pre-turn gate point is `PermissionCheckService.check({category: 'gate'})` evaluated at the turn boundary **before** the turn's `assistant_output` event is appended; pending output buffers in memory while the run blocks per the standard approval-blocking flow, a denial discards the buffered output and system-cancels the run with `reason: moderation_denied`, and an approval appends it unchanged. The post-turn informational event is the registered `moderation.review_flagged` ([Spec-006 §Approval Flow](006-session-event-taxonomy-and-audit-log.md#approval-flow-approval_flow)).

## Session Goals

- A session MAY carry one structured goal (campaign B6): `goal: { text: string }` — the structured object [Spec-006 §Session Lifecycle](006-session-event-taxonomy-and-audit-log.md#session-lifecycle-session_lifecycle) binds to `session.goal_updated.goal` (campaign B1). The single required member is `text` — bounded free-form (1–4096 characters, non-blank, NUL-rejected; the repo's standard free-form wire guards) since it persists into the event log and injects into provider prompts; extending the shape requires a spec revision, and an update without a goal is malformed rather than an implicit clear (clearing is the distinct operation).
- Set and clear are owner/collaborator RPC operations — viewers and runtime contributors are read-only for goal mutation, per the [Security Architecture](../architecture/security-architecture.md) role matrix (`SessionGoalUpdate` / `SessionGoalClear`, following this spec's `OrchestrationBudgetUpdate` naming precedent; wire shapes `SessionGoalUpdateRequest` / `SessionGoalClearRequest` + the `session.goalUpdate` / `session.goalClear` method rows live in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), this bundle); an accepted operation emits the registered `session.goal_updated` / `session.goal_cleared` event carrying the same canonical value the RPC supplied, so RPC and durable event serialize identically. A goal change is not a run-state transition.
- Goal state derives from the event log as a projection — there is no separate goal store; the current goal is whatever the latest goal event says.
- Provider delivery (parity triad, campaign B6): the Codex leg is native (`thread/goal/*`); the Claude leg is emulated — the daemon stores the goal and injects it via system-prompt composition on turn start and resume. Delivery to a live run rides the [Spec-005](005-provider-driver-contract-and-capabilities.md) driver operations — whose exported code-contract mirror (`setSessionGoal` / `clearSessionGoal` methods + `DriverGoalResult` in `packages/contracts`) lands with [Plan-005](../plans/005-provider-driver-contract-and-capabilities.md)'s driver phases via the campaign's Plan-005 bundle, so the live-delivery requirement is code-dispatchable only after that mirror (adding required interface methods in this doc bundle would break existing `ProviderDriver` implementors) — (`setSessionGoal` / `clearSessionGoal`), whose `goalText` is rendered from `goal.text`; the mechanism grade (`native | emulated`) is recorded in the Spec-005 capability matrix (`session_goals`). With multiple active provider legs, delivery is **all-or-nothing**: the mutation fans out to every active binding, `session.goal_updated` / `session.goal_cleared` commits only after all of them ack — an ack means `DriverGoalResult.status: 'applied'`; a `degraded` result is **not** an ack and takes the refusal path (revert + typed error) unless the degraded fallback is itself a verified apply committed by the daemon (the Claude emulated leg's daemon-owned staging is exactly that). Goal changes are **turn-boundary-effective on every leg**: a native ack and an emulated stage both mean the goal durably governs the _next_ turn or resume — an in-flight provider turn completes under the prior prompt on all legs alike, so the committed `session.goal_*` event records the mutation without claiming a mid-turn prompt swap (there is no divergence to reconcile, only the defined boundary). And the fan-out target set is race-free by serialization: **run/binding admission for a session with an in-flight goal intent waits for intent convergence** (the same daemon-serialized session admission that makes budget reserve-then-admit race-free), so no binding can appear between target-set enumeration and the event append; and "live" is the process supervisor's judgment, not the store's — `runtime_bindings` persists no liveness by design (a persisted flag would claim live across a daemon crash), the supervisor's process ↔ binding map names each active run's CURRENT binding, and superseded rows from earlier relaunches never enter the target set — and any refusal or failure durably marks the refusing leg `failed` before compensation begins (so crash replay continues the revert instead of re-issuing a doomed mutation), then re-asserts the prior goal on every non-failed leg — acked and pending alike, since a pending leg's in-flight call may have applied without acking (goal set is last-write-wins, making revert exact) — deletes the dispatch intent **only after every non-failed leg's re-assertion has acked** (a failed or unconverged revert keeps the intent durable with that leg still unconverged; the revert retries immediately and on startup replay; every leg of an unconverged intent is **turn-gated**, applying and compensating alike — mid-apply, an acked leg holds its next turn until the append/delete transaction commits (its provider already carries the new goal, and a turn before convergence would run under a goal the durable log might never record); during compensation, the goal-at-turn-dispatch precondition re-applies the projected prior goal to an acked-unreverted leg before any turn dispatches — so no leg ever runs a turn under an uncommitted goal; and further goal mutations for the session stay refused — one in-flight mutation per session, whether the prior intent is still applying or compensating, surfaced as the registered `session.goal_mutation_in_flight` conflict — until convergence). On the success path the `session.goal_*` append and the intent delete commit in **one daemon-SQLite transaction** (both tables are daemon-local), so a committed event with a live intent — and therefore a double-apply on replay — is unrepresentable. Startup reconciliation is idempotent by re-assertion (goal set/clear is last-write-wins): an interrupted apply re-issues the mutation to **every** leg, acked included (acked is advisory across a restart — a restarted provider may have lost a not-yet-appended goal); a failed intent re-asserts the **prior** goal on every leg, pending included (an in-flight call may have applied without acking), and surfaces `session.goal_delivery_failed` — the durable log and every live leg agree at each turn boundary (per the turn-boundary-effective rule above, an in-flight turn completing under the prior prompt is the defined semantic, not divergence); a binding that terminates before its dispatch resolves simply leaves the target set (a dead leg needs no delivery and can never strand the mutation); legs attaching later receive the current goal at attach/resume via their parity mechanism, and a newly admitted leg in an already-goaled session receives the projected goal **before its first turn** (the same goal-at-turn-dispatch precondition, applied at leg start by the admission/start path). Cross-node sessions follow this spec's AP partition model (availability over consistency; local daemons own their attached runs): the synchronous all-or-nothing barrier binds the legs owned by the mutating daemon; legs on other runtime nodes converge through the relayed event log — each owning daemon applies the projected goal to its local legs with the same intent/retry machinery, and **applies it before dispatching any further turn to a leg** (goal-at-turn-dispatch precondition), so no leg starts a turn under a goal staler than its own node's replayed event log. On the mutating node that is the committed goal immediately; on a remote node, legs MAY run turns under the prior goal while the relayed event is delayed or partitioned away — the deliberate AP posture (remote runs continue locally; convergence is bounded by [Spec-024](024-cross-node-dispatch-and-approval.md)'s reconnect/replay, never by a cross-node lock) — and the precondition applies the relayed goal before the first turn after it arrives. The one-in-flight serialization above is likewise **per-node**: the intent table is daemon-local, so `session.goal_mutation_in_flight` refuses concurrent mutations only among callers of the same daemon, and mutations accepted on different nodes while the relay is delayed or partitioned are NOT mutually refused — they converge as a **last-writer-wins register**. Every daemon's goal projection folds `session.goal_updated` / `session.goal_cleared` in **two stages**: within one origin daemon, its own append order is authoritative — the origin's latest goal event by the **server-stamped payload keys `originNodeId` + `originSeq`** (the accepting daemon's per-session append sequence, durable on every goal payload per Spec-006, because a receiving daemon re-sequences relayed events under its own local `sequence` per ADR-017 and origin order would otherwise be unrecoverable), per [Spec-015](015-persistence-recovery-and-replay.md)'s within-daemon ordering rule (`occurred_at` is display/audit data and never orders same-daemon events, so a wall-clock step between two serial local mutations can never invert them) — and only BETWEEN different origins' latest candidates does the cross-origin comparator apply: envelope `occurredAt`, tie-broken by envelope `id` (the best V1 cross-daemon primitive — HLC is the V1.1 upgrade path per ADR-017/BL-076). The fold is a pure function of the event set, so once both events replay everywhere, every node settles on the same final goal (cross-node wall-clock skew is bounded by Spec-015's clock discipline, and a skew-misordered CONCURRENT write costs at most a goal overwrite between two mutations that raced anyway — never divergence), and the goal-at-turn-dispatch precondition applies the converged winner before each leg's next turn. A control-plane lease or lock on goal mutation is deliberately rejected: goal mutation stays available under partition — the same availability-over-consistency trade-off the cross-node AP model above already commits to.

## Provider-Native Subagents

- **Single-supervisor invariant (campaign B6): the daemon is the only cross-session supervisor.** A run MAY use its provider's in-session subagents (Claude `--agents` / Task tool; Codex `multi_agent` / `[agents]`) under the `subagentPolicy` the daemon passes through — the policy shape (`{enabled, maxDepth, maxConcurrent, definitions[]}`) is owned by [Spec-005](005-provider-driver-contract-and-capabilities.md) and its API Payload Contracts mirror.
- Budget roll-up: subagent usage aggregates into the run's own budgets — the §Budget Policies accountant sees it through the run's `usage` events, so subagents provide no budget escape hatch. Derived pricing resolves **per usage row**: a row wire-attributed to a model outside the run's admitted family keys off THAT model's family — the attribution rides the durable [Spec-006](006-session-event-taxonomy-and-audit-log.md) B6 usage-row fields `modelId?` / `modelFamily?` / `subagentId?`, populated by the driver normalizer from wire attribution (per-model usage maps; subagent-scoped usage pairing on the subagent triple; the normalizer duty lands with the campaign's Plan-005 bundle's normalizer tasks) — falling back to `admittedModelFamily` when the wire carries no attribution. A differently-modeled subagent is thus never priced under its parent's rates when the wire attributes it; and because the spawn screen above already requires every subagent-definition family to be priced or native-cap-covered at admission, an attribution-less row can at worst mis-allocate between two PRICED families' rates — it can never miss an unpriced-family block. And the admission-preemption rule above extends to spawn: `subagentPolicy.definitions[]` models resolve against the pricing table at spawn, and a definition naming an unpriced-family model on a capless leg is refused fail-closed (same `driver_capless` vocabulary) unless a native-cap reservation covers the run — coverage is **per-family across the run's whole model set** (parent + every subagent definition): each unpriced family needs its own `unpricedFamilyCaps` entry, and since the provider hard stop is run-wide, the single stamped `admittedUnpricedCapCents` is the **minimum** of those entries (run-wide spend ≤ every family's owner bound — deterministic and safe; an unpriced family with no entry refuses per the spawn screen) ([Spec-006 §Tool Activity](006-session-event-taxonomy-and-audit-log.md#tool-activity-tool_activity) records the same aggregation rule on `subagent.completed`, campaign B1).
- Approval flow-through: subagent tool calls flow through the same approval pipeline as the parent run's (Plan-012); a subagent introduces no separate trust surface.
- Timeline normalization: subagent lifecycle lands as the registered `tool_activity` rows `subagent.started` / `subagent.completed` (campaign B1), provider-attributed and pairing on the (`runId`, `provider`, `subagentId`) triple.
- In-session subagents execute beneath a single run and are not canonical child runs — the §Resolved Questions one-parent-child-layer delegation decision governs cross-run delegation and is unchanged by this section.
- The CLIs' own out-of-session supervisors (`claude agents` / `claude daemon`, `--bg` / `/background`, Codex cloud) stay disabled inside daemon-managed runs. This is the parity implementation of "background agents" — the daemon's orchestration layer IS the manager — not a capability rejection. Enforcement is layered: the daemon owns spawn argv and configuration and never enables those surfaces; the command-policy provider-supervisor deny applies for every effective posture ([Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior), campaign B20); and the Bash-sandbox/permission layer is the residual control against model-initiated supervisor spawns. The invariant is scoped to daemon-configured supervision.
- Concurrency: `maxConcurrent` enforces natively on the Codex leg. The Claude leg's spawn-side cap is docs-silent, so the daemon **enforces at its own boundary instead of trusting the provider**: subagent tool calls already route through the daemon's approval/execution pipeline keyed by the (`runId`, `provider`, `subagentId`) triple, and beyond-cap subagents serialize there — held at their next daemon-mediated call until a slot frees, never failed — keeping effective concurrency at or under `maxConcurrent` for all daemon-mediated work. Provider-internal reasoning by an excess subagent cannot be blocked from outside; it still debits the supervising run's budgets (no escape hatch, bounded by budget/idle limits), the breach diagnostic remains as the observability signal, and a leg that cannot mediate subagent tool calls keeps subagents disabled at spawn (fail-safe). Mechanism grades per the Spec-005 capability matrix: native vs boundary-serialized.

## Scheduler Limits

| Limit | Default |
| --- | --- |
| Max concurrent channels executing | 5 per session |
| Max queue depth per channel | 25 items (subject to Spec-001 per-session queue depth of 100) |
| Max pending orchestration runs | 10 per session |
| Max active children per parent run | 5 (daemon default — Tier-6 audit, D-016-11; not a product-wide ceiling per §Resolved Questions: the value is session-configurable via `OrchestrationBudgetUpdate`) |

Tier-6 audit semantics (D-016-11): a channel is **executing** when ≥1 run targeting it is in `starting` / `running` / `waiting_for_input` / `waiting_for_approval`; a **pending orchestration run** is an orchestration-created run in `queued`; a child is **active** for the active-child bound when in any of those four states or `queued`. All limits are enforced at create-time admission with zero residue (no run row, no queue item survives a refusal), the refusal is a typed error with explicit limit detail, and the daemon records it durably via `orchestration.rejected` ([Spec-006 §Channel Arbitration](006-session-event-taxonomy-and-audit-log.md#channel-arbitration-channel_arbitration)). All scheduler limits live with the budget limits in the session budget surface and are owner-adjustable (D-016-5).

## Partition And Reconnect Behavior

Multi-agent sessions span multiple runtime nodes; partition behavior inherits from [Spec-003](../specs/003-runtime-node-attach.md) and [Spec-015](../specs/015-persistence-recovery-and-replay.md). Spec-016 adds only the turn-arbitration and channel-visibility rules specific to multi-agent semantics.

- When a node loses its relay connection, the control plane marks it `offline` per Spec-003. Session membership is preserved and the node may reconnect under the same node identity.
- Child runs on the offline node continue locally if the node can still reach its provider; events buffer against the node's local audit log ([Spec-006](../specs/006-session-event-taxonomy-and-audit-log.md)) until relay catch-up via Spec-015 replay.
- Parent-channel views on connected nodes show the offline node's runs in an `unreachable` state with the last-known state preserved from the event cursor. `unreachable` is a visibility outcome, not a run-state transition — it is distinct from the run-level `paused` state defined in Spec-004.
- Turn-policy arbitration degrades by policy:
  - `free-form`: unaffected; addressed turns for the remaining reachable agents continue to admit in arrival order (activation stays addressing-gated per §Turn Policies — partition changes ordering availability, never the activation rule).
  - `round-robin`: if the next agent is on an unreachable node, arbitration pauses the channel and emits an `arbitration.paused` event (with `arbitration.resumed` on reconnect). Arbitration must not silently skip the unreachable agent (which would let a disconnected participant miss their turn without record) and must not auto-fail-over to free-form without explicit operator action. `arbitration.paused` and `arbitration.resumed` are registered in the [Spec-006](../specs/006-session-event-taxonomy-and-audit-log.md) canonical event taxonomy under the `channel_arbitration` category (BL-084, completed 2026-04-18).
  - `request-based`: unaffected on the sender side; responders on unreachable nodes do not consume their turn and the request expires per its normal timeout.
- On reconnect, buffered events catch up via Spec-015 replay and any arbitration pause resolves automatically once the canonical ordering is restored.
- Runs that cannot be resumed because provider-session state was lost transition to `failed` per Spec-015; they must not reappear as a new run.
- The control plane does not enforce cross-node consensus on turn arbitration. Local daemons own their attached runs; cross-node ordering is eventually consistent through the event log. A round-robin channel with two agents on two partitioned node-halves may briefly see divergent local views; Spec-015 replay reconciles on reconnect. Availability over consistency (AP) is the explicit trade-off for the collaboration surface.

## Implementation Notes

- Keep orchestration semantics provider-agnostic and session-scoped.
- Channel creation should be lightweight, but channel identity must remain durable enough for audit and replay.
- Internal helper runs should be discoverable without overwhelming the default UI.

## Pitfalls To Avoid

- Treating multi-agent orchestration as only a UI grouping trick
- Hiding child-run provenance
- Assuming provider-native spawn semantics are universal

## Acceptance Criteria

- [ ] A session can host multiple concurrent agents and channels.
- [ ] Parent-child run relationships remain visible after replay and reconnect.
- [ ] Delegated work remains possible even on drivers without native subagent APIs.

## Resolved Questions and V1 Scope Decisions

- No blocking open questions remain for v1.
- V1 decision (narrowed 2026-08-03 — see the channel-audience entry below): channel-level permission restrictions are deferred **for non-direct channels**. A new non-direct channel inherits session membership and visibility policy in the first implementation.
- V1 decision: channels are the only canonical communication boundary between agents and runs. Direct run-to-run messaging is out of scope for the first implementation. (Unchanged by the 2026-08-03 amendment: the `direct` channel kind is a **channel** between two humans, not a run-to-run messaging primitive — it rides the same canonical boundary this decision names.)
- V1 decision: canonical nested delegation depth is one parent-child layer in v1. Deeper delegation requires a future spec revision.
- V1 decision: concurrent child runs are allowed, but v1 does not impose one product-wide numeric ceiling. Each runtime scheduler must expose bounded active-child admission behavior and explicit limit rejection.
- V1 decision (campaign B6, R8): realtime/voice channels are **reserved behind the R8 capability gate** — the upstream Codex realtime feature flag is still under development, a named external gate surfaced to the owner. The reservation binds to the gate, not to the provisional wire shape: per [ADR-015](../decisions/015-v1-feature-scope-definition.md)'s feature #23 note the `thread/realtime/*` shapes were re-verified against the then-installed binary at authoring time (2026-07-06: installed `codex --version` = `codex-cli 0.141.0`, byte-identical to the provider-wire pin, so the pinned receipt IS the then-installed evidence — present but feature-gated OFF), and the same re-verification MUST be repeated against the then-installed binary before any future activation. Spec-016 defines no channel media-type enumeration and none is invented for the reservation; no channel-model change lands until the upstream flag stabilizes. The paired event-census reservation (the reserved `realtime_*` family) is [Spec-006](006-session-event-taxonomy-and-audit-log.md)'s (campaign B1); the scope entry is V1 feature #23 per [ADR-015](../decisions/015-v1-feature-scope-definition.md).
- V1 decision (Part-B fail-closed follow-up, 2026-07-17): **auto-compaction is a named advisory safeguard — a tracked affordance, never a forced interrupt.** The context-window hard budget stays rejected (§Budget Policies: headroom is not a fourth budget), and the future orchestrator-run compaction lever is scoped now so it cannot later land as a stop: when a run's headroom climbs past a soft threshold the orchestrator MAY surface and pre-arm provider-native conversation compaction — that advisory surfacing is the soft, reversible response even `estimated`-grade headroom may drive under the §Budget Policies hard-vs-soft line, whose human-facing sibling is the V1-shipped composer-meter compaction hint (which stays purely informational — [Spec-013 §Context Window and Usage Meters](013-live-timeline-visibility-and-reasoning-surfaces.md#context-window-and-usage-meters); this entry scopes the future machine-facing counterpart) — while **invoking** compaction mutates the live provider conversation and is graded accordingly: invocation fires only on `provider_reported`-grade signal (both window counts present, or the `exceeded: true` terminal flag), never off an estimate — and its implementation binds three invariants. **Buffer-for-compaction**: the trigger MUST sit far enough below the window ceiling that the compaction call itself still has room to run — too-full-to-compact is a documented field deadlock ([anthropics/claude-code#25620](https://github.com/anthropics/claude-code/issues/25620), accessed 2026-07-12), and surveyed runtimes hold triggers near ~75-85% usage with an explicit reserve partly for this reason ([GitHub Copilot CLI context management](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/context-management) keeps a ~20% buffer and names its thresholds "automatic safeguards rather than hard stops", accessed 2026-07-12). **Recoverable originals**: the lever summarizes the provider conversation only, never the session record — the canonical event log ([Spec-006](006-session-event-taxonomy-and-audit-log.md)) keeps the full pre-compaction history under its own retention rules, so dropped detail stays re-derivable as a record; recoverability is an audit and re-derivation guarantee, deliberately not a live-conversation undo — neither provider wire exposes a compaction-restore operation, which is exactly why invocation rides the hard side of the provenance line above. **Capability-gated invocation**: daemon-invoked compaction exists only behind a capability-gated driver compaction operation, and the V1 provider-driver contract (`ProviderDriver`, `packages/contracts/src/provider-driver.ts`) deliberately ships none — so in V1 the daemon never invokes compaction: the shipped safeguard surface is buffer maintenance plus advisory surfacing, and provider-native auto-compaction runs under the provider's own authoritative accounting (the provider compacts on its own counts, never on our estimate); the invocation lever activates only when that driver operation lands. The surveyed 2026 provider surfaces ship compaction first-class (client-side auto-compact in the provider CLIs; server-side as the Messages API `compact_20260112` context edit — [Anthropic compaction](https://platform.claude.com/docs/en/build-with-claude/compaction), accessed 2026-07-12), so the lever composes with provider machinery rather than inventing summarization; which mechanism each driver leg binds is an implementation-plan concern, deliberately not fixed here.
- V1 decision (2026-08-03 vision reconciliation, D-016-21): **channel audience and two-human direct channels are un-deferred into V1 — scoped, not a general channel-permission model.** The ratified product vision commits V1 to "humans-only side channels and direct messages whose content agents are never given as context" ([vision.md §The Collaboration Model](../vision.md)), so exactly two surfaces leave the deferral above: the `ChannelConfig.audience` member (`participants` default \| `humans-only`) and the `direct` two-human channel kind, both specified in §Interfaces And Contracts. Everything the deferral otherwise covered stays deferred — no per-participant channel ACLs, no agent-scoped read grants, no membership mutation on non-direct channels, no channel-visibility policy language beyond audience. Enforcement is a daemon obligation at **agent-context assembly** rather than a renderer or relay concern, because that assembler is the single choke point every prompt, tool result, and artifact passes through on the machine that owns the agent; renderer-side hiding would leave the excluded content inside the model's window, which is precisely the failure the vision's runtime-enforced-contract wording rules out. Two consequences are stated where they bind rather than here: audience survives delivery fallback (§Fallback Behavior — re-homing never widens it), and the kind and member pair are event-carried so replay cannot widen audience (§State And Data Implications). A `direct` channel's confidentiality from **non-member humans** is deliberately **not** established by this entry: it is a relay-layer property this spec consumes, defined in [Spec-008 §Per-Channel Recipient Scoping (V1)](008-control-plane-relay-and-session-join.md#per-channel-recipient-scoping-v1) (amended 2026-08-03 alongside this spec).

## V1 Readiness Review (BL-042, 2026-04-17)

Review against the V1 quality bar declared by [ADR-015](../decisions/015-v1-feature-scope-definition.md) §Thesis. Findings:

- **Turn policy defaults** — `free-form` is the explicit default. Round-robin and request-based are documented alternatives with deterministic triggers. No "configurable without default" surfaces remain.
- **Budget policy defaults** — Named defaults for per-run token (100,000), per-session cost ($10.00), and per-agent turn (50) limits. V1 enforcement tightened from advisory to hard ceiling via intervention dispatch during this review. Soft warning at 80%, hard interrupt at 100%.
- **Stop conditions** — Four named conditions (turn limit, budget exhausted, explicit stop, idle timeout) with deterministic triggers. Idle timeout default is 5 minutes. Conclusion detection deferred to V2.
- **Moderation / approval hooks** — Pre-turn (category `gate`) and post-turn (informational) hooks integrate with [Plan-012](../plans/012-approvals-permissions-and-trust-boundaries.md) approval categories. Opt-in per channel is the V1 default.
- **Turn arbitration under partition** — Named partition behavior added: `round-robin` pauses arbitration when the next agent is on an unreachable node with explicit `arbitration.paused` / `arbitration.resumed` events (registration in Spec-006 is a Plan-016 precondition — tracked as BL-084); `free-form` and `request-based` degrade gracefully. Reconnect semantics align with Spec-003 node-identity continuation and Spec-015 replay. Eventually-consistent cross-node ordering is the accepted trade-off (AP over CP for the collaboration surface).
- **ADR-011 intervention dispatch** — Non-cascading propagation clarified; no new intervention verbs introduced; subtree-wide cascade would be a new ADR, not a Spec-016 edit.

Behavioral change: budget enforcement posture (advisory → hard ceiling). No blocking changes required to ADR-011, Spec-004, Spec-012, or the approval policy surface. Turn arbitration pause is an orchestration-layer visibility state distinct from run-level `paused`, consistent with Spec-004's discrimination of waiting states.
