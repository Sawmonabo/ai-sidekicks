## Purpose

Define how multiple agents collaborate inside a session and how their channels and run relationships are represented.

## Scope

This spec covers channel creation, parent-child run linkage, cross-agent collaboration, and background helper activity — including session goals, cost derivation for budget enforcement, and the orchestration-level governance of provider-native in-session subagents (campaign B6).

## Non-Goals

- Workflow authoring syntax
- Defining provider-native subagent APIs — the `subagentPolicy` and driver-op shapes are [Spec-005](005-provider-driver-contract-and-capabilities.md)'s; this spec governs only their orchestration use (§Provider-Native Subagents, campaign B6)
- Notification policy

## Required Behavior

- A session must support multiple active agents at once.
- Agents may collaborate through one or more channels inside the same session.
- Cross-agent communication must use canonical channel publication, artifact references, approvals, or persisted run linkage. V1 must not depend on a separate direct run-to-run messaging primitive.
- Parent-child run relationships must be durable and auditable.
- Internal helper runs must remain distinguishable from user-visible agents while still appearing in canonical history.
- Per-agent model, driver, and runtime-node selection must be allowed within one session.
- Orchestration must remain valid even when a driver has no native subagent concept.

## Default Behavior

- Default collaboration mode is explicit: new child runs are created only by user request, by workflow definition, or by a peer-invocation tool call inside a session where a participant has explicitly turned peer invocation on ([Spec-030 §Required Behavior](./030-sidekick-definitions-and-peer-invocation.md#required-behavior)). The third arm does not weaken the default, and is admitted here rather than treated as an exception to it: a session that has not turned peer invocation on refuses every peer-invocation call at adjudication, so no child run of this origin can exist without the opt-in, and that opt-in **is** the user request — made once for the session instead of once per child run. Every other constraint in this section applies to a peer-invoked child unchanged: it is one parent-child layer deep, it is subject to the scheduler limits below, and it publishes into the parent timeline like any other child.
- Child-run output defaults to publishing a summarized row into the parent session timeline, with expandable detail.
- New non-direct collaboration channels default to inheriting session membership unless later restricted by policy. A `direct` channel is the single V1 exception: its membership is the immutable two-human pair fixed at creation (§Interfaces And Contracts).
- V1 delegation defaults to one parent-child layer. A child run is not allowed to create another child run under the canonical first-release contract.
- Concurrent child runs are allowed, but admission remains subject to explicit runtime scheduler limits rather than unbounded fan-out.

## Fallback Behavior

- If a driver does not support native subagent creation, the runtime must model delegated work as separate runs with explicit linkage and channel context.
- If child-run detail loading fails, the summary row remains available and marked incomplete.
- If channel-specific delivery is unavailable, output falls back to the session's default visible channel with preserved provenance. (Tier-6 audit, A-016-18: "unavailable" = the target channel is archived at publication time, or its row is missing at projection time; "preserved provenance" = the event payload keeps the original `channelId` while the projection re-homes display to the main channel.)
- **Delivery fallback never widens audience** (2026-08-03 vision reconciliation): the re-homing above applies only to `participants`-audience channels. Content from an audience-restricted channel (`humans-only`, and therefore every `direct` channel) is never re-homed to the main channel or to any other `participants` channel — an undeliverable message there fails visibly to its sender instead, because re-homing would hand agent-excluded content to every agent in the session (§Interfaces And Contracts).
- If child-run creation would exceed the supported delegation depth, the runtime must reject the request with explicit limit detail and must not create hidden background work.
- If child-run creation would exceed the active-child scheduler limit, the runtime must reject the request with explicit capacity detail rather than silently dropping or auto-spawning overflow work.

## Interfaces And Contracts

- `ChannelCreate` must create a session-scoped communication surface. Channel lifecycle mutations (`ChannelMute` / `ChannelUnmute` / `ChannelArchive`) and a daemon-native roster read (`ChannelRosterRead`, carrying per-channel config + arbitration state — and, since the 2026-08-03 amendment (D-016-21), each entry's channel kind with a `direct` entry's member pair, the read-back of the create-side fields below) complete the channel surface (Tier-6 audit, D-016-6/D-016-12).
- **Channel audience (2026-08-03 vision reconciliation, D-016-21):** `ChannelConfig` carries an `audience` member — `participants` (default: humans and agents, the pre-amendment behavior) or `humans-only` (agents are never given the channel's content as context). Audience is a **normative daemon obligation, not renderer etiquette**: each daemon MUST exclude every `humans-only` channel's content from every prompt, context window, tool result, and artifact it assembles for any agent, **regardless of which participant owns that agent** — including when the agent's own owner is a member of that channel ([vision.md §The Collaboration Model](../vision.md): "each daemon scopes which channels its agents are given as context — audience is a runtime-enforced contract, not etiquette"). Read scope is the privileged grant and is separate from act scope: an agent addressable in a session gains no read access to that session's `humans-only` channels. Audience is expressible only on an explicitly created channel: the bootstrap `main` channel has no channel row and emits no `channel.created` (§State And Data Implications), so it carries no `ChannelConfig` — its audience is always `participants` and is never restrictable, leaving the one channel every session has with no unspecified case. The surveyed platforms draw the same split — Discord separates message delivery (`GUILD_MESSAGES`) from the privileged `MESSAGE_CONTENT` intent that makes content readable ([Discord Gateway events](https://docs.discord.com/developers/events/gateway)), and Slack scopes an app's mention delivery (`app_mention`) separately from channel-history read ([Slack `app_mention` event](https://docs.slack.dev/reference/events/app_mention)); both accessed 2026-08-03.
- **Direct channels (2026-08-03 vision reconciliation, D-016-21):** `ChannelCreate` accepts a `direct` channel kind — a two-human direct-message channel whose member pair is fixed at creation and immutable thereafter (no add, no remove, no widen). Create is admitted only when the authenticated creator is one of the two named members and both members resolve to active human session participants — a create naming a pair the creator is outside, an unknown participant, or a non-human member is refused. Membership defines the write set, not only the read set: every write to a `direct` channel — message publication and the lifecycle mutations (`ChannelMute` / `ChannelUnmute` / `ChannelArchive`) — is admitted only from an authenticated pair member and refused fail-closed for every other caller, the session `owner` included; relay recipient scoping bounds who can read ([Spec-008 §Per-Channel Recipient Scoping (V1)](008-control-plane-relay-and-session-join.md#per-channel-recipient-scoping-v1)), and this gate is the daemon-side bound on who can write, since a caller whose daemon never holds the channel's ciphertext can still reach the wire surface. One publish path is refused outright rather than pair-gated: sharing an artifact into a `direct` channel — an artifact publication or attachment addressed into it — is a typed refusal, because [Spec-014 §Cross-Node Artifact Relay (V1)](014-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1) wraps an artifact's content key to the session-wide attested set with no channel narrowing, so admitting it would hand a decryptable key to every non-member daemon; the durable artifact-channel binding with member-intersected key wrapping is the named V1.1 extension ([Spec-008 §Resolved Questions and V1 Scope Decisions](008-control-plane-relay-and-session-join.md#resolved-questions-and-v1-scope-decisions) records the seam). On this kind `audience` is `humans-only` **by construction and immutable**: the daemon forces the value, refuses any create supplying a conflicting one, and admits no mutation that would widen it — so `audience` is not caller-settable on a `direct` channel. The agent-turn members of `ChannelConfig` are refused on this kind under the same fail-closed disposition: `turnPolicy`, `roundRobinOrder`, `moderation`, and `turnsPerAgent` (the fourth member, added 2026-08-11 — D-016-23) all govern agent turns on a channel that admits no agents, and `round-robin` is structurally unsatisfiable here because its create validation requires a non-empty agent order (§Turn Policies) — a `direct` create supplying any of the four is refused rather than silently carrying inert configuration. A `direct` channel is omitted from this spec's own roster surface for non-members: `ChannelRosterRead` omits it for any caller outside the pair — the daemon half of a deliberately two-surface non-disclosure property whose control-plane half is [Spec-002 §Interfaces And Contracts](002-invite-membership-and-presence.md#interfaces-and-contracts)'s matching `ChannelList` per-caller omission (amended 2026-08-03 alongside this spec; Plan-002 I-002-6) — a filter whose server-side kind + member-pair source is the channel-directory publication bullet below (D-016-22, 2026-08-11). Each surface's filter belongs to the plan that owns that surface, and only together do the two close a `direct` channel's existence metadata across V1's channel-enumeration surfaces — neither closes it alone. The non-enumeration presence vector — a `direct` channel's id riding `focusedChannelId` or a typing indicator through the control-plane presence channel, which bypasses the relay recipient filter — is closed sender-side by [Spec-002 §Default Behavior](002-invite-membership-and-presence.md#default-behavior)'s suppression rule (2026-08-03), the third leg of the same property. Non-direct channels keep open session-wide membership in V1 per §Resolved Questions and V1 Scope Decisions. Confidentiality from **non-member humans** is a distinct, relay-layer property this spec depends on rather than defines — defined in [Spec-008 §Per-Channel Recipient Scoping (V1)](008-control-plane-relay-and-session-join.md#per-channel-recipient-scoping-v1) (amended 2026-08-03 alongside this spec): a membership-restricted channel's events are sealed to the channel member set intersected with the session's current recipient set, and are never served on peer history backfill outside that set.
- **Channel-directory publication (2026-08-11, D-016-22):** every channel-lifecycle transition a daemon accepts — `channel.created` / `channel.muted` / `channel.unmuted` / `channel.archived` — is additionally **published to the control-plane channel directory**: minimal channel metadata only (`channelId`, `sessionId`, the triggering event's `lifecycleEventKind` — added 2026-08-11, PR #322 Codex round 1, so the ingest can identify a creation under arbitrary reordering — `name?`, `state`, `kind`, and — for a `direct` channel — the canonicalized member pair), never message content, over an idempotent control-plane ingest mutation whose wire contract, backing store, and `ChannelList` read path are [Plan-002](../plans/002-invite-membership-and-presence.md)-owned surfaces on the CP-002-7 edge (owed by Plan-002's own targeted readiness-audit delta; this spec owns only the producer obligation). Publication is **at-least-once and never blocking**: the daemon-local channel operation commits first and never fails, rolls back, or waits on directory acknowledgment (the daemon is the machine-local execution authority per ADR-001/ADR-003) — the origin daemon publishes after its durable event append and retries until acknowledged, and every daemon re-publishes the channel set of the sessions it hosts on startup and on relay reconnect. Re-publication is safe by construction: each publication is a pure function of the durable channel-lifecycle event and carries the corpus's origin-ordering keys — `originNodeId` + `originSeq` **server-stamped on the lifecycle payload itself** ([Spec-006 §Channel and Agent Lifecycle](006-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle), amended alongside this bullet — the goal-payload `producingNodeId` idiom), so the keys survive relay re-sequencing in every member's durable copy and a non-origin republisher reproduces them exactly, with envelope `occurredAt` + `id` for the cross-origin comparator (the §Session Goals two-stage register precedent; a publication derived from a pre-extension event whose payload lacks the keys carries no origin keys on the wire and folds via the ingest's single envelope-ordered legacy slot, never binding disclosure) — so the Plan-002-owned upsert is a deterministic **per-origin candidate-retention fold** (redesigned 2026-08-11, PR #322 Codex round 1 — a single-winner comparator mixing a same-origin sequence branch with a cross-origin timestamp branch is order-dependent when an origin clock steps backward): the ingest retains one candidate per origin (same-origin `originSeq`-max) and resolves visible state from the retained set, so replicas that have received the same publication set converge to the same directory state regardless of delivery order or duplication (the state-based merge and its strong-eventual-consistency property per Preguiça, _Conflict-free Replicated Data Types: An Overview_, [arXiv:1806.10254](https://arxiv.org/abs/1806.10254) — §References), and a replayed or delayed publication converges instead of regressing directory state. The fold additionally honors lifecycle terminality (PR #321 Codex round 2): `archived` is terminal in the channel lifecycle (no transition leaves it — D-016-12), so it **latches** — a directory row's state is `archived` iff any publication ever carried it, and a delayed or replayed mute/unmute straggler can never resurrect an archived row — while non-terminal resolution takes the `(occurredAt, id)`-lexicographic-max retained candidate (residual: cross-origin resolution is wall-clock and skew-prone, so a cross-node mute/unmute race can transiently order wrong until both publications land, bounded by [Spec-015](015-persistence-recovery-and-replay.md)'s clock discipline; the HLC upgrade is the V1.1 path per ADR-017/BL-076, the same seam the §Session Goals register names — same-origin causality stays exact via `originSeq`, which is why the counter is retained rather than demoted to a timestamp tiebreak). The terminal latch governs the **`state` axis only**, and the create-once disclosure binding below governs `kind` + `memberPair` + `name` on an independent axis — so when at-least-once delivery lands the `channel.archived` publication before the `channel.created` one, the later-arriving creation publication still binds the disclosure-bearing fields on the already-terminal row without reviving its state, and an archived `participants` channel is never left permanently kind-unresolvable (PR #321 round 2). Because the publication derives from the event rather than from private daemon state, any member daemon holding the relayed event MAY re-publish it (healing a permanently offline origin) without divergence — but healing is **existence-and-ordering only, never disclosure-widening**: the relay re-signs relayed history under the receiving daemon's key ([Spec-008 §Peer History Backfill On Join (V1)](008-control-plane-relay-and-session-join.md#peer-history-backfill-on-join-v1)), so a non-origin publisher has no origin-authenticated evidence for the metadata it forwards, and the Plan-002-owned ingest binds the disclosure-bearing fields (`kind`, `memberPair`, and the user-supplied `name` — the third member joined 2026-08-11 so a GDPR-cleared name can never rebind from a redelivered or sweep publication) **create-once** (PR #321 Codex round 2 — a per-publication caller check alone would let any authenticated daemon later re-declare a channel's kind by publishing fresh metadata under its own origin claim): they are honored only from the channel's **creation publication** — the publication whose `lifecycleEventKind` is `channel.created` (carried on the wire, since the resulting `state` alone cannot distinguish a creation from an unmute under the promised reordering — PR #322 Codex round 1) and whose authenticated caller identity matches its payload's `originNodeId` — and are immutable in the directory thereafter, no later publication (origin-authenticated included) altering them, with conflicting origin-authenticated creation claims for the same `channelId` collapsed to the unresolvable-kind disposition below; a non-origin (healing) publication keeps the row's existence, state, and ordering alive but its kind is treated as unresolvable, taking the same omit-as-`direct` collapse, so a compromised member daemon can neither relabel another origin's `direct` channel as listable nor fabricate a disclosed pair (its forgeries land as non-disclosed placeholders at worst). The recorded V1 residual is the insider case — the daemon that originates a channel declares that channel's metadata at creation, so a compromised origin can mis-declare only its own channels — and the V1.1 hardening seam is an origin-signed event envelope the control plane verifies against the registered node key, binding the creation claim cryptographically rather than by transport authentication. **Staleness fails closed, never open:** until a channel's publication lands, the control-plane `ChannelList` simply does not list it — and an entry whose kind the projection cannot resolve is omitted as if `direct` (Plan-002 T3.6) — so a delayed publication can briefly under-disclose a `participants` channel but can never over-disclose a `direct` one. **What the control plane learns is a deliberate, scoped disclosure:** the directory holds channel existence metadata — including, for a `direct` channel, which two humans share it — the same membership-metadata class the control plane already holds in `session_memberships`, protected under [Spec-022](022-data-retention-and-gdpr.md)'s Postgres posture (access control plus row-level deletion) — and because the directory will durably hold a user-supplied `name?` and, for `direct` channels, both participant identifiers, **routing the directory table and those columns into Spec-022's PII data map and its participant-erasure closure is a named, non-optional leg of the Plan-002 carrier delta**: the carrier is not registered (and Plan-016's carrier box stays unchecked, holding the producer task) until that erasure routing lands, so no publication can flow into a store outside the erasure fan-out; channel **content** never reaches the control plane (it transits the relay E2E-sealed per [Spec-008](008-control-plane-relay-and-session-join.md)), and the three-leg `direct`-channel non-disclosure property above binds **non-member participants**, not the control plane itself — the `ChannelList` per-caller filter (I-002-6) is precisely what this publication feeds, so the filter can evaluate kind and membership server-side instead of failing open on an absent source.
- **Per-channel turn budget (2026-08-11, D-016-23 — the A-017-07 provider leg):** `ChannelConfig` carries `turnsPerAgent?` — an optional positive integer overriding, for that channel alone, the session's per-agent consecutive-turn limit (§Budget Policies turn-limit row; `session_budgets.turn_limit_per_agent`, default 50). Absent means the session value applies — the "bare-channel 50" comparator [Spec-017 §Default Behavior](017-workflow-authoring-and-execution.md#default-behavior) names. Counting semantics and the enforcement site are unchanged (the D-016-8 per-(channel, agent) consecutive counter with interleave reset, enforced by the turn-policy arbiter): at the effective limit the run completes with `trigger: 'turn_limit'` and same-agent admission into that channel refuses until an interleaving turn — any other agent's or any human participant's turn in the channel, the universal counter reset, available to every member with no mutation surface. The D-016-8 owner-raise lever reaches only channels at the session default (`orchestration.budgetUpdate` on `turn_limit_per_agent`): an **overridden channel's limit is create-time-fixed**, because `ChannelConfig` is uniformly immutable after create in V1 — no post-create channel-config mutation exists on any member, deliberately, since mid-flight policy mutation would invalidate the arbiter's admission-time assumptions — so the override pins the channel for its lifetime and a post-create override mutation (`channel.configUpdate`, with its events-canonical `channel.config_updated` companion) is the named V1.1 seam per §Resolved Questions and V1 Scope Decisions. The first consumer is Spec-017's phase-owned OWN channels, which set it at channel create (`turns_per_agent`, indicative max 20); a `direct` channel refuses it with the other agent-turn members (above). It is a per-channel override of the existing turn budget, **not a fourth budget** — the §Budget Policies three-budget table is unchanged.
- **Agent surface (Tier-6 audit, A-016-2; provider axis added 2026-08-26, D-016-26):** Plan-016 owns the V1 agent identity surface satisfying §Required Behavior's per-agent model/driver/node selection — `AgentAttach` / `AgentDetach` / `AgentConfigUpdate` / `AgentList`, with the agent persona `{name, driverName, modelId, defaultNodeId?, config?, providerAccountId?, effort?}` durable via `agent.*` events ([Spec-006 §Channel and Agent Lifecycle](006-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle)). `OrchestrationRunCreate.targetAgentId` resolves against this surface; an unknown or detached agent is a typed refusal.

The type is caller-declared (`linkType`, default `spawn`) and durable in the run linkage.

## State And Data Implications

- Channel and run-link records must be durable and replayable.
- Parent-child linkage must survive recovery and replay.
- Internal helper visibility must be policy-aware but never silently omitted from audit history.
- The channel record additionally carries its audience configuration, its channel kind, and — for a `direct` channel — its immutable two-human member pair (2026-08-03 vision reconciliation, D-016-21). `audience` rides the existing typed `ChannelConfig` value; the kind and the member pair are additive fields on the channel record itself. This introduces **no new persistence table**: the member pair is fixed-arity by construction, so it needs no membership relation of its own.
- Because channel records are events-canonical projections, the channel kind and the member pair must ride the channel-creation event payload and not the row alone — a channel whose kind or pair could not be rebuilt from the event log would break the durable-and-replayable guarantee above and silently widen audience on replay. (The [Spec-006 §Channel and Agent Lifecycle](006-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle) enumeration carries the matching additive-optional `kind?` + `memberPair?` payload members as of 2026-08-11.)
- The agent record additionally carries its provider account, its reasoning effort, its output-speed mode (2026-08-29), and any switch still pending against it (2026-08-26, D-016-26, §Same-Agent Provider Switch). All four are additive columns on the **unshipped** `agents` `CREATE` ([Local SQLite Schema](../architecture/schemas/local-sqlite-schema.md)) rather than fields inside the opaque `config` blob, because each is validated against driver-reported vocabularies or read by surfaces outside the driver — the account by the [Spec-029](029-provider-accounts-and-credential-homes.md) spawn gate, the effort by the switch's own refusal check, the speed mode by the spawn that has to realize it, the pending intent by the boundary hook and by `agent.list`. No table is added and no migration ordinal is consumed. Like the channel kind and member pair above, all four must ride the `agent.*` event payloads and not the row alone, or an agent's provider binding — and the promise that a deferred switch is still coming — would not survive replay.
- The pending column holds **one** intent or none, which is what makes the one-pending-per-agent rule structural rather than advisory, and it holds the **pending** binding only: the effective binding stays in the account, model, driver, and effort columns and moves into them at application, so a projection read never shows a switch that has not happened yet. It is cleared by whichever terminal event settles the switch, and by a superseding mutation, so a stale intent is unrepresentable.
- The switch introduces **no daemon-side state beyond those four columns**: the canonical transcript it replays is a projection rebuilt from the session event log, never a stored artifact ([Spec-005 §Canonical Transcript Export And Replay](005-provider-driver-contract-and-capabilities.md#canonical-transcript-export-and-replay)), and the declared-loss list is carried on the `agent.provider_switched` event rather than retained separately.
- The channel-directory publication (D-016-22, §Interfaces And Contracts) introduces **no daemon-side state**: no new SQLite table and no acknowledgment ledger — the startup/reconnect re-publication sweep derives entirely from the durable channel-lifecycle events, whose payloads carry the server-stamped origin-ordering keys themselves ([Spec-006 §Channel and Agent Lifecycle](006-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle), 2026-08-11), so the sweep reconstructs complete publications with no side-state, and the directory's backing store is a [Plan-002](../plans/002-invite-membership-and-presence.md)-owned control-plane surface, not part of this spec's daemon data model.

## Turn Policies

| Policy | Behavior | Default |
| --- | --- | --- |
| `free-form` | Any participant may send at any time; addressed agent turns admit in arrival order with no turn-taking constraint | Yes (default) |
| `round-robin` | Agents take turns in a fixed order | No |
| `request-based` | Agents speak only when explicitly addressed | No |

Tier-6 audit ratifications (D-016-19): a `round-robin` channel requires a non-empty agent order in its channel config at create time (validation refusal otherwise); the fixed order is that config value, and the next-due cursor derives from the durable run-admission sequence (no separate cursor store). `request-based` is **structurally satisfied in V1**: every agent run is explicitly created (§Default Behavior — child runs only by user request or workflow definition; no agent-initiated speech exists in V1), so every agent turn already carries an explicit addresser and admission adds no check beyond `free-form`. The policy value is accepted and recorded; dedicated request-addressing primitives become meaningful only when agent-initiated communication arrives (V2, with conclusion detection). Turn-policy enforcement governs **agent** runs; human participants are never turn-blocked.

**Activation is addressing-gated under every turn policy in V1** (2026-08-03 vision reconciliation — [vision.md §The Collaboration Model](../vision.md)'s ratified activation invariant: agents "act when mentioned or dispatched — never by interjecting into human-to-human exchanges"). An agent produces a turn only in response to an explicit addressing act directed at that agent; a channel message addressing no agent admits **no** agent turn, under `free-form` exactly as under `request-based`. Turn policy therefore governs the **ordering** of admitted agent turns and never governs whether an unaddressed agent may activate — the `free-form` and `request-based` rows above are ordering variants of one activation rule, which is why `request-based` remains structurally satisfied (D-016-19) rather than being the only addressing-gated policy. The V1 addressing act is `OrchestrationRunCreate` naming a `targetAgentId` (§Interfaces And Contracts); a client-surface `@mention` is sugar that resolves to that act and introduces no new wire contract. **An agent-authored channel message is never an addressing act in V1** — agents do not activate agents through channel speech; runs are created only by user request or workflow definition (§Default Behavior), which is also the V1 loop-prevention bound. This pin structurally resolves the case the surveyed platforms leave undefined — a plain unaddressed reply in a thread where several agents are live admits **zero** agent turns rather than an implementation-defined subset: mention-gating is the surveyed default for channel-resident bots ([Microsoft Teams: channel and group conversations](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/channel-and-group-conversations), accessed 2026-08-03), and the reference Slack-resident assistant likewise filters other bots' replies while leaving the multi-agent unaddressed-reply case explicitly undefined ([Claude in Slack — when Claude responds](https://claude.com/docs/claude-tag/users/when-claude-responds), accessed 2026-08-03; public beta at that date). Agent-initiated speech remains V2, arriving with conclusion detection (§Stop Conditions).

## Budget Policies

| Budget Type            | Description                              | Default Limit |
| ---------------------- | ---------------------------------------- | ------------- |
| Token limit per run    | Max input+output tokens for a single run | 100,000       |
| Cost limit per session | Max estimated cost across all runs       | $10.00        |
| Turn limit per agent   | Max consecutive turns an agent can take  | 50            |

V1 budget enforcement is a hard ceiling, tightened from advisory during the 2026-04-17 V1-readiness review (Spec-016 was authored 2026-04-14, predating ADR-015's V1 quality bar declaration by three days, so the original advisory posture no longer matches the V1 gate). The daemon emits `usage.budget_warning` events (the registered [Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) name for the warning this paragraph previously called `usage_warning` — Tier-6 audit, A-016-6) at 80% of any budget limit, once per (scope, budget-type) crossing — and additionally, off-threshold, on the unpriced-model condition per §Cost Derivation And Absent-Cost Semantics, keyed once per (scope, budget-type, **modelFamily**) with the family carried on the payload so each newly-blocked family is separately audit-visible (campaign B6) — and issues an `interrupt` intervention via the generic dispatcher ([ADR-011](../decisions/011-generic-intervention-dispatch.md)) at 100%. Per-run token ceilings interrupt the specific offending run with `reason: budget_exhausted`; the per-agent turn limit is a stop condition, not a budget interrupt — at the limit the run **completes** with `trigger: 'turn_limit'` per §Stop Conditions (D-016-8). Session-level cost ceilings interrupt all active runs in the session and block further queue admission until the session owner raises the limit ("session admin" resolved to the session `owner` role — the only administrative role in the V1 model (`packages/contracts/src/session.ts`); raise via `OrchestrationBudgetUpdate`, owner-only — Tier-6 audit, D-016-5). Context-window headroom is deliberately **not a fourth budget** (Part-B fail-closed follow-up, 2026-07-17): the three-budget table above stays the closed set, and orchestration consumers read the `usage.context_window_update` headroom signal — `windowUsedTokens` / `windowMaxTokens`, provenance-graded by `windowSource`, with the driver-computed `exceeded` predicate ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — advisorily, on a **hard-vs-soft line keyed to provenance**: `estimated`- and `model_default`-grade headroom may drive only reversible, soft responses (surface a warning, advise the owner, pre-warm the advisory auto-compaction safeguard named in §Resolved Questions and V1 Scope Decisions — invoking compaction itself mutates the live conversation and rides the hard side of this line, per that section), while any costly or irreversible action taken because of headroom (interrupting a run, refusing admission) requires `windowSource: 'provider_reported'` **with both window counts present** — or the provider-reported `exceeded: true` terminal flag, a reported fact rather than a derived ratio, which authorizes those protective actions directly so a counts-absent exhausted window is never answered more weakly than a counted one (a counts-absent, non-exceeded update carries no headroom fact to act on — the pair rule in [Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — a hard action never fires off an estimated count, both because vendor token counts are documented as estimates even from the vendor's own counting endpoint and because current-generation tokenizers produce approximately 30 percent more tokens for the same text than earlier models ("The same input text produces approximately 30 percent more tokens than on earlier models … Recount prompts against the model you plan to use" — [Anthropic token counting](https://platform.claude.com/docs/en/build-with-claude/token-counting), accessed 2026-07-12; re-verified 2026-07-17), so a window number derived from a stale pre-4.7 tokenizer assumption materially under-counts — `model_default`-grade values are tokenizer-fragile rather than merely stale; the surveyed field draws the same line — context thresholds are "automatic safeguards rather than hard stops" ([GitHub Copilot CLI context management](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/context-management), accessed 2026-07-12) — and the only hard context bound anywhere in the stack remains the provider's own real window ceiling. Conclusion detection (agent determines task is complete) remains V2.

### Cost Derivation And Absent-Cost Semantics

Session cost enforcement resolves every usage event's cost through three tiers (campaign B6). Tier (a): provider-emitted cost is consumed whenever the CLI wire supplies it, sanity-bounded — non-negative, finite, and below the configured absurdity ceiling (daemon configuration `costSanityCeilingCents`, default 10000 — a single usage event claiming ≥ $100 is rejected to tier-(b) derivation with the divergence diagnostic) (the ceiling is parameterized in the owning implementation task, not fixed here); gross divergence between an emitted cost and a derivable estimate emits a diagnostic rather than silently trusting either value (known provider over-reporting precedent). Tier (b): otherwise the daemon derives cost as token counts × the local per-model-family pricing table, with family-prefix fallback for point releases; a static local table is the ecosystem-standard mechanism, and its staleness is bounded because tier (a) takes precedence whenever the wire supplies cost. Two classification rules bound tier (b) at its table edges (Part-B fail-closed follow-up, 2026-07-17). **Explicit-$0 carve-out**: tier-(c) fail-closed applies to _unknown_ pricing only — a table entry whose price the operator explicitly set to zero (a genuinely-free local or on-prem family, e.g. an Ollama-served model) is a real price, so the family is **priced-at-zero**: admission proceeds normally, its rows emit `costCents: 0` with `costStatus: 'priced'` and ordinary `derived_*` provenance, and enforcement runs the same ceiling arithmetic as any priced family (contributing zero) — never the unpriced block; unknown-vs-explicitly-free is exactly the distinction the ecosystem's reference gateway added when it moved unmapped-model enforcement to fail-closed ([BerriAI/litellm#24949](https://github.com/BerriAI/litellm/pull/24949), accessed 2026-07-12), and without it tier (c) would false-halt every free/local model — the precise failure fail-open postures exist to avoid. **Prefix-resolves-concrete rule**: the family-prefix fallback must resolve to a concrete, explicitly-set price — a prefix hit whose matched entry carries no operator-set price (absent, or zero only via defaulting the operator never wrote) classifies the family **unpriced → tier (c), never free**: a prefix/wildcard match silently pricing at $0 is a shipped-bug class in that same gateway ([BerriAI/litellm#22609](https://github.com/BerriAI/litellm/issues/22609), accessed 2026-07-12), so the pricing-table shape MUST keep "explicitly zero" and "price absent" structurally distinct (an explicit value versus an absent field — the shape is parameterized in the owning implementation task, like the sanity ceiling above), never encoding unknown as 0. Derivation is **emit-once**: the derived value persists on the emitted `usage.cost_update` row (`costCents`, `costSource: 'derived_*'`), and replay folds those persisted row values plus the worst-case terminal debits of native-cap unpriced runs, rebuilt from their `run.queued` cap stamps (their rows are costless by design — folding rows alone would resurrect their headroom) — it never re-derives historical usage against the current table — so a pricing-table update re-prices nothing retroactively (it applies to future usage only, the same future-admissions-only idiom as `unpricedFamilyCaps`) and `observedCostCents`, warnings, and admission blocks are replay-stable. Admission preempts this tier where it can see it coming: run admission resolves the model family (the same as-of-admission resolution that stamps `admittedModelFamily`) against the pricing table, and an unpriced family admits only under a native-cap reservation — on a capless leg it **refuses at admission** (`orchestration.budget_exhausted`, `reason: 'driver_capless'`) before any queueing or spend, so the first unpriced run never starts unbounded. The mid-run path below remains only for coverage lost after admission (a pricing-table change while the run is in flight). Tier (c): otherwise the run is **budget-indeterminate and the daemon fails closed** — it emits `usage.budget_warning` with `reason: 'unpriced-model'` ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry), campaign B1) — schema-valid under the registered payload: `budgetType: 'session_cost'`, `limitValue` = the configured session cost limit, `observedValue` = the committed spend observed so far (priced cost + worst-case terminal debits of prior unpriced runs + active reservations (`reservedCostCents`) of still-running native-cap admissions; possibly 0 — the live unpriced usage itself is exactly what cannot be observed) — interrupts per the enforcement paragraph above, and blocks further queue admission for the unpriced model family session-wide (the admission refusal reuses `orchestration.budget_exhausted` with `reason: 'unpriced-model'` + `modelFamily` in `data.fields`, [Error Contracts](../architecture/contracts/error-contracts.md)).

The unpriced block — admission refusal and mid-run interrupt alike — lifts only by explicit owner action (degrade honestly, never fail open): a pricing-table update covering the family (an operator config/deploy action — the table is static local daemon configuration per the tier text above, not a session RPC; the universal escape, and the **only** one for legs without a native cap) — or, **on provider legs with a native hard budget cap only** (Claude `--max-budget-usd` at the pinned version), an owner-supplied hard USD bound under which runs proceed unpriced-but-USD-bounded with the unpriced status surfaced (their `usage.cost_update` rows carry `costStatus: 'unpriced'`, `costSource: 'unpriced_native_cap'`, `costCents` absent — the Spec-006 provenance vocabulary admits the capped-unpriced case first-class) on every affected run (supplied per model family via `OrchestrationBudgetUpdate.unpricedFamilyCaps` — one entry per family, duplicates rejected at validation; a run whose model set spans several unpriced families admits under the MINIMUM of their entries — the run-wide provider stop cannot honor per-family sub-budgets, so the conservative bound is the only safe single cap — persisted with session budgets and replayed like any budget change — the wire/state contract lives in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), this bundle). The escape reserves, never exempts: admitting a run under a family cap **reserves the full per-run cap against the session ceiling** — admission requires `observedCostCents + reservedCostCents + hardCapUsdCents ≤ costLimitCents`, else the queue refuses with the ordinary `orchestration.budget_exhausted` (whose `observedValue` then carries committed spend: observed cost including unpriced terminal debits, plus active reservations); at the run's terminal state the reservation **converts to a worst-case charge, never back to headroom**: the admitted cap moves from `reservedCostCents` into `observedCostCents` as an unpriced debit (the actual spend is unknowable by construction, so the full cap is what the ledger records — serial unpriced runs therefore consume the ceiling cumulatively exactly like priced work, and a session can never launder unbounded spend through admit-finish-repeat), the reserved amount **snapshots at admission onto the run's `run.queued` admission record** (`admittedUnpricedCapCents` — a server-stamped sibling of `effectiveRunConfig`, deliberately not an `OrchestrationRunConfig` member so a run-create request can never inject it; persisted per D-016-5), so later `unpricedFamilyCaps` updates apply to future admissions only and can never retro-shrink an active run's reservation and restart/replay rebuilds reservations and debits from the server-stamped `run.queued` records alone, the admitted cap **wires through to the driver** on the run params (`StartRunParams.admittedCostCapCents` — realized as the native cap on cap-capable legs, Claude `--max-budget-usd`, per [Spec-005](005-provider-driver-contract-and-capabilities.md)'s params; a leg that binds caps at spawn realizes it at session boundaries per the posture precedent) so the local reservation is always backed by the provider-side hard stop, and admission is daemon-serialized so reserve-then-admit is race-free, and the 80% warning threshold evaluates the same committed-spend sum; a capless leg (Codex at the pinned version — its `token_budget` is upstream-under-development) stays fail-closed until its pricing-table entry lands, so its named escape is the pricing-table path. A Day-0 model family therefore never silently runs unbounded and never hard-blocks without a named escape. Enforcement MUST NOT branch on `costSource`: provider-emitted and daemon-derived cost feed one ceiling with no dual trust regimes — the `costStatus`/`costSource` provenance mirrors ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) are observability, not policy inputs. The surveyed reference runtime's fail-open zero-cost terminal is the one surveyed posture explicitly not ported. Currency (2026-07-06): the tier-(b) table seeds from the current vendor model catalogs — Claude Sonnet 5 / Fable 5 families and Codex `gpt-5.5` / `gpt-5.4` / `gpt-5.3-codex-spark` ([Anthropic model overview](https://docs.anthropic.com/en/docs/about-claude/models/overview), [OpenAI models](https://platform.openai.com/docs/models), both accessed 2026-07-06) — and the Claude per-run `--max-budget-usd` cap ([provider-wire reference, claude.md](../reference/provider-wire/claude.md), version-pinned) is wired as defense-in-depth beneath this accountant, never as the accountant. Codex's caplessness is auditable from the pinned wire surface ([provider-wire reference, codex.md](../reference/provider-wire/codex.md) — no budget-cap parameter exists at the pin); upstream work on a `token_budget` config was observed at survey time (2026-07-02) but is not pinned and confers nothing here. The three-budget table above and the §Stop Conditions closed set (D-016-8) are unchanged by this subsection. The provider-side hard stop also survives recovery: resume/relaunch re-threads the admitted cap from the durable `run.queued` payload into `ResumeSessionParams.admittedCostCapCents`, and reservation is gated on the leg's `cost_cap` driver capability (Spec-005 matrix) — a capless leg refuses fail-closed (`reason: 'driver_capless'`), never reserves-without-enforcement. The cap rides every provider-process entry point — spawn (`CreateSessionParams`, where Claude binds `--max-budget-usd`), run start (`StartRunParams`), and resume (`ResumeSessionParams`) — so no capless window exists between admission and enforcement; and on a spawn-bound leg a native-cap run **starts only inside a provider session spawned with the matching cap**: an existing uncapped (or differently-capped) process forces a capped relaunch at the session boundary before `startRun` dispatches (the posture-relaunch precedent), never a start inside an uncapped process.

### Cost Figure Display Consistency

Every cost figure this spec's surfaces expose derives from the **same committed-spend fold the accountant enforces against** — the fold specified in §Cost Derivation And Absent-Cost Semantics above: persisted priced row cost, plus the worst-case terminal debits of unpriced native-cap runs rebuilt from their `run.queued` cap stamps, plus the active reservations of still-running native-cap admissions. Three rules bind (2026-08-17, D-016-24).

**(a) One fold, never a second accountant.** A surfaced session-level or run-level cost figure is **supplied by** the accountant that enforces, never recomputed beside it. Summing the runs visible in a run list is expressly not a permitted derivation, and no surface may maintain an independently-folded total for presentation. The three committed-spend figures V1 actually surfaces are therefore the same number at the same fold state: the `OrchestrationBudgetState.committedSpendCents` member — one figure, not two, because the budget read and the budget update answer with that same state type and are served from the same accessor — and the `observedValue` the daemon stamps on a **session-cost** `usage.budget_warning` — the `budgetType: 'session_cost'` member of that event's three-value union ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)) — both already defined as committed spend by the tier-(c) and escape paragraphs above, and that cross-surface equality is **asserted**, not assumed (I-016-24 at `Plan-016 §Invariants`, asserted by T2.5 at `Plan-016 §Phase 2 — Daemon orchestration services`). The third is the `observedValue` a session-cost `orchestration.budget_exhausted` refusal stamps in its `data.fields` ([error-contracts.md §Orchestration](../architecture/contracts/error-contracts.md#orchestration)): the admission predicate that refuses reads `committedSpendCents` from the same accessor, and the refusal stamps exactly the value the predicate read, so the refused caller is shown the enforced number too — three surfaces, one accessor, one value (the PR #343 Codex round-3 fold). The warning-side equality is scoped to that event's session-cost member alone: a `run_tokens` warning stamps a token count and an `agent_turns` warning a turn count, neither of which is a cost figure and neither of which this subsection governs. The read response's other cost members are components of that number rather than independent totals — the identities in clause (c) pin each of them to it, so there is exactly one total on the surface and no second one to drift. The failure this forecloses was observed in the campaign's reference-runtime parity survey (2026-08-12; a first-party field observation, recorded inline per the amendment header's provenance note): the surveyed overview listed each root run with only that run's own ledger cost while the spend of delegated work landed on the children those runs called, so a large multi-run campaign displayed at a small fraction of its true cost — a display fold that had silently drifted from the number the ledger held. V1's structure already bounds the drift class (canonical delegation depth is one parent-child layer per §Resolved Questions and V1 Scope Decisions, in-session subagent usage rolls into the parent run's own budget per §Provider-Native Subagents, and the session ceiling folds everything), which is why the residue is this display-side rule rather than a re-derivation of the fold itself.

**(b) A per-run figure declares its aggregation scope.** Any surfaced run-level cost figure states whether it is **run-only** or **run-plus-children-plus-in-session-subagents**; an undeclared per-run figure is exactly the ambiguity the surveyed overview shipped. **V1 exposes per-run cost figures on exactly one surface — the session cost receipt (§Session Cost Receipt) — and every one of them declares `run-only`** (2026-08-18). The declaration is uniform because the receipt lists every run of the session as its own row: a delegated child run appears beside its parent rather than inside it, so summing the rows double-counts nothing and no row silently absorbs another's spend. In-session subagent usage is the one thing a `run-only` row does include, because `Spec-016 §Provider-Native Subagents` already rolls it into the parent run's own budget — it is not delegation to a separate run and has no row of its own to be counted twice from. Canonical delegation depth is one parent-child layer (§Resolved Questions and V1 Scope Decisions), so the parent-plus-children reading is always recoverable from the rows the receipt already shows, which is why V1 needs no second scope label. This clause is therefore **verified positively** from 2026-08-18: the assertion is that every run-level figure the receipt emits carries the `run-only` declaration and that no other V1 surface emits one (I-016-24 at `Plan-016 §Invariants`, extended in the same amendment). The forward obligation on any plan that grows a further cost-displaying surface is registered as CP-016-16 at `Plan-016 §Cross-Plan Obligations`.

**(d) A token figure declares its scope too.** The one-fold rule of clause (a) is **cost-scoped and stays that way**: the token axis deliberately carries two folds — the per-run enforced token budget (`tokenLimit`, the ceiling admission and interrupt act on) and the conversation-scoped token count the composer meter displays — and that divergence is intentional and reconciled at the auto-compaction safeguard in §Budget Policies. Nothing here collapses them. What does bind, as the token-axis analogue of clause (b), is the declaration: **any surfaced token figure states which of the two it is** — per-run enforced budget, or conversation-scoped observed count. The concrete case this closes is a rendered `run_tokens` budget warning, whose `observedValue` is a per-run token figure that no rule previously governed and that reads, beside a conversation-scoped meter, as though the two were the same quantity. Declaring the scope is the whole obligation; no fold changes, no surface is added, and no figure moves.

**(c) Provenance rides the figure, supplied by the wire.** Where unpriced-run debits or active reservations contribute to a surfaced total, the presentation carries that fact, and the **daemon reply** supplies it rather than the client inferring it — a renderer computing provenance from component fields would violate Plan-016's zero-client-derivation rule (I-016-19), and an SDK doing so its marshal-never-derive rule (I-016-16) — both rows at `Plan-016 §Invariants`. The budget state therefore decomposes the number it already reported, on the `orchestration.budgetRead` and `orchestration.budgetUpdate` replies alike ([API Payload Contracts](../architecture/contracts/api-payload-contracts.md), this bundle): `observedPricedCostCents` (the exact priced leg), `observedUnpricedDebitCents` (the worst-case terminal-debit leg), `committedSpendCents` (the sum enforcement compares against the ceiling), and an **aggregate `costStatus`** reusing the row-level [Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) vocabulary with aggregate semantics defined here: `'priced'` when the total is exact — no unpriced debit contributes, no active reservation contributes, and the session's persisted history records no mid-run tier-(c) classification (§Cost Derivation And Absent-Cost Semantics: pricing coverage lost after admission, whose in-flight unpriced usage is unobservable by construction and enters no leg of the fold) — and `'unpriced'` when any of the three holds. The third condition replays from a durable trace exactly as the debits do: the mid-run classification's persisted `usage.budget_warning` (`reason: 'unpriced-model'`) **carries the interrupted run's `runId`** — required on that emission path, the same per-path requiredness discipline Spec-006 states for `modelFamily` on that event's optional members — while an admission-time family refusal precedes any run and stamps no `runId`, so the residue key is precisely the run-stamped warning and never the admission-time block. The once-per-`(scope, budget-type, modelFamily)` emission latch that warning dedups on is **epoch-scoped, never lifetime-scoped**: the explicit owner action that lifts a family's unpriced block re-arms the latch for that family, so a family refused runless at admission, repaired by a pricing-table update, re-admitted, and then classified tier-(c) mid-run emits a **second** warning — the run-stamped row the residue condition keys on — rather than being silenced by the spent key of the admission-time row (the PR #343 Codex round-2 fold). Torn-append crash windows do not defeat the key: the tier-(c) classification is a deterministic function of persisted state — the unpriceable usage row, the absent cap stamp, and the pricing table's persisted emit-once derivations — and the replay-rebuilt accountant re-runs it, so a daemon that crashed after appending the unpriceable row but before appending the warning re-classifies that row at rebuild and appends the missing run-stamped warning then, or, where a table repair has since restored coverage, prices the row into the observed leg — either way the rebuilt fold is honest: the spend is observed or the residue is recorded, never neither (the PR #343 Codex round-3 fold). Two identities hold at every fold state: `observedPricedCostCents + observedUnpricedDebitCents === observedCostCents`, and `observedCostCents + reservedCostCents === committedSpendCents`. This is a **decomposition of the existing number, not new arithmetic** — the two observed legs are precisely the two folds `observedCostCents` was already rebuilt from, so the decomposition is replay-stable for the same reason the fold is. The aggregate `costStatus` is observability exactly as its row-level sibling is: enforcement reads `committedSpendCents` and **MUST NOT** branch on it, per the no-dual-trust-regimes rule above.

**The total is not a lower bound.** The surveyed runtime's pricing fold counts its unpriced rows, so its total can honestly label itself a lower bound; this spec's unpriced runs are instead charged their **full admitted cap** as a worst-case debit at terminal state. The committed-spend figure is therefore exact for priced usage, worst-case for unpriced native-cap usage, and forward-looking for the reservations of runs still in flight — with exactly one exclusion: the in-flight usage of a mid-run tier-(c) classification (pricing coverage lost after admission) is unobservable by construction and enters no leg of the fold, bounded by that path's immediate interrupt and surfaced — never silently absorbed — by the aggregate `costStatus` turning `'unpriced'` per clause (c). A surface MUST NOT label the figure a lower bound, because the label is wrong in both directions: the worst-case cap debits make it **over**-state settled spend by the unconsumed remainder of the caps already charged, and, when the mid-run residue is present, it additionally omits spend no fold can observe — a bound label in either direction claims knowledge the accountant does not have. What the figure always is, is the enforced number, which is exactly what clause (a) requires a surface to show, with clause (c)'s provenance riding it.

This subsection mints no event type, no wire method, no error code, and no table, and adds no budget: the three-budget table above stays the closed set it was, and the §Stop Conditions closed set (D-016-8) is unchanged.

### Session Cost Receipt

Added 2026-08-18. Every session carries a **cost receipt**: a collapsed line showing the session total, which expands into a detailed transcript of what that total is made of. The collapsed line is the committed-spend figure clause (a) already governs — the same number, from the same accessor, with no second fold behind it. The receipt is what makes that number answerable rather than merely correct: an operator who sees a session cost and cannot find out what caused it has a figure, not an account.

**The transcript is a decomposition, never a re-fold.** This is the same move clause (c) makes for the priced/unpriced axis, applied to two further axes, and it is bound by the same discipline: the accountant that enforces is the accountant that answers, the decomposition members are components of the number it already reported, and identities pin every part to the whole. A presentation-side re-aggregation — summing rows the client can see, or maintaining a parallel per-participant tally — is expressly forbidden by clause (a) and is not made permissible by being a detail view. Concretely, the receipt decomposes committed spend along three axes:

- **Per run.** One row per run of the session, each declaring `run-only` per clause (b). A delegated child run gets its own row beside its parent rather than being folded into it.
- **Per caused-by party.** Each unit of spend attributes to the participant who caused it, or to **system** where no participant did — a scheduled sweep, an idle-timeout settlement, or a daemon-initiated recovery turn. A run created by a peer-invocation tool call attributes to the effective principal of the **turn that made the call** — that turn's principal is already resolved and stamped when the call is issued, so the attribution is settled at child-creation time rather than by a later lookup, and a subsequent steer of the asking run never retroactively re-attributes a child already created. Causation chains through the parent/child run link, and the once-per-session enablement grant is the participant act that admitted the chain, so such spend stays inside the per-participant split rather than falling to the system arm. The system arm exists so that unattributable spend is named rather than silently distributed across participants or dropped from the split.
- **Per paying provider account.** Each row carries the account that paid ([Spec-029 §Selection at run start](029-provider-accounts-and-credential-homes.md#selection-at-run-start)) and that account's billing mode, under the labeling rule at [Spec-029 §Billing mode](029-provider-accounts-and-credential-homes.md#billing-mode): plan-included usage is never presented as billed dollars without its label, and a total spanning both billing modes states that it does.

Two identities hold at every fold state, and they are the receipt's whole correctness argument: the per-run rows sum to the session's committed spend, and the per-caused-by rows sum to it as well. Each axis is a **partition** — every unit of committed spend appears in exactly one row of each axis, which is why either axis totals to the same number and why neither can quietly omit or duplicate a contribution. The unpriced and reserved legs decompose along these axes exactly as they do along clause (c)'s, so a receipt row carries the same aggregate `costStatus` vocabulary and the same provenance obligation as the session figure: the receipt never invents an honesty marker of its own, and in particular **never labels any figure a lower bound**, for the reason the not-a-lower-bound rule already gives — worst-case cap debits make committed spend over-state settled spend, so the label would be wrong in both directions at the row level exactly as it is at the session level.

**Per-turn billing attribution.** Within a run, spend attributes to **the participant who started the run** by default, and to **the intervener** for a turn they steered or whose message they edited and resent. The rule follows causation rather than ownership: a run someone else steers is spend that person caused, and attributing it to the original starter would make the receipt misreport exactly the multi-participant case it exists to illuminate. Attribution keys on the turn-scoped effective principal — the admitting-principal stamp registered by CP-004-14 and the [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) §Authenticated Principal class rule — and not on run ownership, which cannot express a mid-run change of causing party. **Since 2026-08-26 that key rides the metered row itself**: every `usage.cost_update` carries the daemon-resolved effective principal for the turn it meters ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)), so the fold reads a group key off each row rather than joining it out of event history by ordering — which is what makes this axis a partition by construction rather than by argument, and what makes it replay-stable for the same reason the class rule gives. Where that stamp is absent for a turn — pre-amendment history only — the turn attributes to the run starter and the receipt does not guess.

**Derivation is fold-of-persisted-rows, exactly as enforcement is.** The receipt re-uses the emit-once ladder in §Cost Derivation And Absent-Cost Semantics without amending it: it folds the persisted `usage.cost_update` row values plus the worst-case terminal debits of native-cap unpriced runs plus active reservations, and it **never re-prices anything at read time**. A pricing-table update re-prices no history for the receipt any more than it does for enforcement, so a receipt rendered twice at the same fold state renders identically, and a receipt is replay-stable for precisely the reason the accountant is. The attribution axes add keys to the fold; they do not add arithmetic.

**Cross-machine behavior, stated honestly.** The receipt folds the session's own usage events, and those events travel the ordinary session event relay: the seven session-scoped `usage_telemetry` types carry the real `sessionId` of the run or session they meter ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)), so a session spanning two runtime nodes yields one receipt covering both, and a joining peer's backfill recovers the spend history it is entitled to. One usage type is deliberately **not** part of this: `usage.rate_limit_update` is account-plane, binds to the reserved node-scope sentinel rather than to a session, and sentinel-bound rows are excluded from peer history backfill and are witnessed locally only in V1. The consequence is stated rather than papered over — **provider quota display is node-local, while the cost receipt is session-wide.** Those are different scopes for good reasons (a quota describes an account's standing with its provider, not a session's spending), and no V1 surface presents the account-plane quota as though it were session state.

This subsection mints no event type, no table, and no budget. It mints one read surface (registered in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md)) whose every figure is served from the same committed-spend accessor as the budget read, and the account and caused-by axes it reads are supplied by [Spec-029](029-provider-accounts-and-credential-homes.md) and by the turn-scoped effective principal respectively.

## Stop Conditions

| Condition | Trigger | Behavior |
| --- | --- | --- |
| Turn limit reached | Agent exceeds turn limit | Run completes with `turn_limit` metadata |
| Budget exhausted | Token or cost limit exceeded | Run interrupted with `budget_exhausted` reason |
| Explicit stop | User sends stop command | Run interrupted via cancel intervention |
| Idle timeout | No activity for configurable duration (default: 5 min) | Run interrupted with `idle_timeout` reason |
| Workflow phase cancelled | The run's owning workflow phase terminates its in-flight channel work ([Spec-017](017-workflow-authoring-and-execution.md) SA-9 `REQUEST_CANCEL` / `TERMINATE` cascade — added 2026-08-11, D-016-23) | Run interrupted with `workflow_phase_cancelled` reason |

Conclusion detection (agent determines task is complete) is V2.

Tier-6 audit definitions (D-016-8): a **turn** is one completed assistant-output cycle attributed to a (channel, agent) pair; the consecutive-turn counter resets when a different agent (or a human participant) takes an interleaving turn in the same channel. At the turn limit the run completes with `trigger: 'turn_limit'` and further same-agent admission into that channel is refused with explicit limit detail until an interleaving turn occurs or the owner raises the limit (the raise is `orchestration.budgetUpdate` on the session's `turn_limit_per_agent` and reaches only channels at the session default — a channel carrying a `turnsPerAgent` override is create-time-fixed and recovers by interleave alone, §Interfaces And Contracts, D-016-23). **Activity** for the idle timeout is any appended session event whose payload carries the run's id; the idle sweep is a daemon-owned per-run timer (default 300000 ms, per-run configurable), subject to two cross-spec exemptions: while a run's work item has a pending outbound cross-node dispatch the sweep hard-skips **that dispatch-initiating run** — such waits are locally event-quiet by construction and bounded by the dispatch's own caller-local expiry window ([Spec-024 §Required Behavior](024-cross-node-dispatch-and-approval.md#required-behavior), campaign B7); and a run in a blocking state (`waiting_for_input` / `waiting_for_approval`) is likewise hard-skipped while the state holds — for pending-work-backed blocking (a provider ask or a pipeline approval block) the exemption is expiry-bounded by the pending work's own deadline — every run-blocking ask or approval request carries one at creation (asks stamp `expiresAt` per Spec-012's ask-side bounded-wait contract; run-blocking approval mints stamp `expiryAt`, concretizing that contract's "expiry where applicable" requirement across the approval side — the mint mechanism landing with Plan-012's run-blocking mint rule, campaign B15) — ending the moment it expires or resolves and returning the run to ordinary idle semantics — or, for a denied or expired pre-turn moderation gate, exiting terminally (`moderation_denied`; expiry is denial per Spec-012's silence-is-denial rule) — per Spec-012's decoupled-but-coordinated rule ([Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior), [run-state-machine.md §Invariants](../domain/run-state-machine.md#invariants), campaign B13/B15), while the startup-reconciliation divergence halt — `waiting_for_input` carrying `recovery-needed`, backed by no pending ask or approval — is a designed human-action halt the sweep never times out: it exits only by human recovery action and surfaces on the recovery status channels ([Spec-015 §Fallback Behavior](015-persistence-recovery-and-replay.md#fallback-behavior), campaign B5/B14). Unrelated runs in the same session keep ordinary idle semantics under both exemptions. The four system-interrupt reasons (`budget_exhausted`, `idle_timeout`, `moderation_denied`, `workflow_phase_cancelled` — the fourth added 2026-08-11, D-016-23: minted by this spec, invoked only by the workflow engine's SA-9 phase-termination cascade ([Spec-017](017-workflow-authoring-and-execution.md)/Plan-017, which names the member and never authors it) through the same in-process system-intervention entrypoint as the other three, D-016-7) form a closed set carried on the interrupt intervention.

## Intervention Propagation

Interventions use the generic dispatcher defined by [Spec-004](../specs/004-queue-steer-pause-resume.md) and [ADR-011](../decisions/011-generic-intervention-dispatch.md). Spec-016 introduces no new intervention verbs.

- A pause, interrupt, or steer applied to a parent run does not auto-cascade to its child runs. Each child run is an independent intervention target.
- Propagating an intervention across a parent/child subtree requires the caller to submit one intervention per run. This preserves Spec-004's audit property that every run-state transition corresponds to a distinct `InterventionResult` record.
- A steer applied to a parent run does not inject content into child-run conversations — child runs receive steer content only when the steer is targeted at the child run's id.
- Child runs accept the same run-control surface as standalone runs — steer and interrupt via `applyIntervention`, pause/resume via the orchestration-layer `run.pause` / `run.resume` verbs (Spec-004; the driver never needs to know about pause). Driver capability semantics (Spec-004's steer degradation, for example) apply uniformly.
- If a future requirement demands subtree-wide propagation (e.g., "cancel this parent and all its descendants atomically"), that is a new ADR rather than a payload field addition, consistent with ADR-011's Type-1 reversibility stance.

## Moderation Hooks

- Pre-turn approval: before an agent's output is committed to the timeline, an approval gate can require human review.
- Post-turn review: after output is committed, a review flag marks it for human inspection (non-blocking).
- Both hooks integrate with the approval system (Plan-012): category `gate` for pre-turn, informational event for post-turn.
- V1 default: no moderation hooks enabled. Opt-in per channel.

Tier-6 audit ratification (D-016-10): the pre-turn gate point is `PermissionCheckService.check({category: 'gate'})` evaluated at the turn boundary **before** the turn's `assistant_output` event is appended; pending output buffers in memory while the run blocks per the standard approval-blocking flow, a denial discards the buffered output and system-cancels the run with `reason: moderation_denied`, and an approval appends it unchanged. The post-turn informational event is the registered `moderation.review_flagged` ([Spec-006 §Approval Flow](006-session-event-taxonomy-and-audit-log.md#approval-flow-approval_flow)).

## Session Goals

- A session MAY carry one structured goal (campaign B6): `goal: { text: string }` — the structured object [Spec-006 §Session Lifecycle](006-session-event-taxonomy-and-audit-log.md#session-lifecycle-session_lifecycle) binds to `session.goal_updated.goal` (campaign B1). The single required member is `text` — bounded free-form (1–4096 characters, non-blank, NUL-rejected; the repo's standard free-form wire guards) since it persists into the event log and injects into provider prompts; extending the shape requires a spec revision, and an update without a goal is malformed rather than an implicit clear (clearing is the distinct operation).
- Set and clear are owner/collaborator RPC operations — viewers and runtime contributors are read-only for goal mutation, per the [Security Architecture](../architecture/security-architecture.md) role matrix (`SessionGoalUpdate` / `SessionGoalClear`, following this spec's `OrchestrationBudgetUpdate` naming precedent; wire shapes `SessionGoalUpdateRequest` / `SessionGoalClearRequest` + the `session.goalUpdate` / `session.goalClear` method rows live in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md), this bundle); an accepted operation emits the registered `session.goal_updated` / `session.goal_cleared` event carrying the same canonical value the RPC supplied, so RPC and durable event serialize identically. A goal change is not a run-state transition.
- Goal state derives from the event log as a projection — there is no separate goal store; the current goal is whatever the latest goal event says.
- Provider delivery (parity triad, campaign B6): the Codex leg is native (`thread/goal/*`); the Claude leg is emulated — the daemon stores the goal and injects it via system-prompt composition on turn start and resume. Delivery to a live run rides the [Spec-005](005-provider-driver-contract-and-capabilities.md) driver operations — whose exported code-contract mirror (`setSessionGoal` / `clearSessionGoal` methods + `DriverGoalResult` in `packages/contracts`) lands with [Plan-005](../plans/005-provider-driver-contract-and-capabilities.md)'s driver phases via the campaign's Plan-005 bundle, so the live-delivery requirement is code-dispatchable only after that mirror (adding required interface methods in this doc bundle would break existing `ProviderDriver` implementors) — (`setSessionGoal` / `clearSessionGoal`), whose `goalText` is rendered from `goal.text`; the mechanism grade (`native | emulated`) is recorded in the Spec-005 capability matrix (`session_goals`). With multiple active provider legs, delivery is **all-or-nothing**: the mutation fans out to every active binding, `session.goal_updated` / `session.goal_cleared` commits only after all of them ack — an ack means `DriverGoalResult.status: 'applied'`; a `degraded` result is **not** an ack and takes the refusal path (revert + typed error) unless the degraded fallback is itself a verified apply committed by the daemon (the Claude emulated leg's daemon-owned staging is exactly that). Goal changes are **turn-boundary-effective on every leg**: a native ack and an emulated stage both mean the goal durably governs the _next_ turn or resume — an in-flight provider turn completes under the prior prompt on all legs alike, so the committed `session.goal_*` event records the mutation without claiming a mid-turn prompt swap (there is no divergence to reconcile, only the defined boundary). And the fan-out target set is race-free by serialization: **run/binding admission for a session with an in-flight goal intent waits for intent convergence** (the same daemon-serialized session admission that makes budget reserve-then-admit race-free), so no binding can appear between target-set enumeration and the event append; and "live" is the process supervisor's judgment, not the store's — `runtime_bindings` persists no liveness by design (a persisted flag would claim live across a daemon crash), the supervisor's process ↔ binding map names each active run's CURRENT binding, and superseded rows from earlier relaunches never enter the target set — and any refusal or failure durably marks the refusing leg `failed` before compensation begins (so crash replay continues the revert instead of re-issuing a doomed mutation), then re-asserts the prior goal on every non-failed leg — acked and pending alike, since a pending leg's in-flight call may have applied without acking (goal set is last-write-wins, making revert exact) — deletes the dispatch intent **only after every non-failed leg's re-assertion has acked** (a failed or unconverged revert keeps the intent durable with that leg still unconverged; the revert retries immediately and on startup replay; every leg of an unconverged intent is **turn-gated**, applying and compensating alike — mid-apply, an acked leg holds its next turn until the append/delete transaction commits (its provider already carries the new goal, and a turn before convergence would run under a goal the durable log might never record); during compensation, the goal-at-turn-dispatch precondition re-applies the projected prior goal to an acked-unreverted leg before any turn dispatches — so no leg ever runs a turn under an uncommitted goal; and further goal mutations for the session stay refused — one in-flight mutation per session, whether the prior intent is still applying or compensating, surfaced as the registered `session.goal_mutation_in_flight` conflict — until convergence). On the success path the `session.goal_*` append and the intent delete commit in **one daemon-SQLite transaction** (both tables are daemon-local), so a committed event with a live intent — and therefore a double-apply on replay — is unrepresentable. Startup reconciliation is idempotent by re-assertion (goal set/clear is last-write-wins): an interrupted apply re-issues the mutation to **every** leg, acked included (acked is advisory across a restart — a restarted provider may have lost a not-yet-appended goal); a failed intent re-asserts the **prior** goal on every leg, pending included (an in-flight call may have applied without acking), and surfaces `session.goal_delivery_failed` — the durable log and every live leg agree at each turn boundary (per the turn-boundary-effective rule above, an in-flight turn completing under the prior prompt is the defined semantic, not divergence); a binding that terminates before its dispatch resolves simply leaves the target set (a dead leg needs no delivery and can never strand the mutation); legs attaching later receive the current goal at attach/resume via their parity mechanism, and a newly admitted leg in an already-goaled session receives the projected goal **before its first turn** (the same goal-at-turn-dispatch precondition, applied at leg start by the admission/start path). Cross-node sessions follow this spec's AP partition model (availability over consistency; local daemons own their attached runs): the synchronous all-or-nothing barrier binds the legs owned by the mutating daemon; legs on other runtime nodes converge through the relayed event log — each owning daemon applies the projected goal to its local legs with the same intent/retry machinery, and **applies it before dispatching any further turn to a leg** (goal-at-turn-dispatch precondition), so no leg starts a turn under a goal staler than its own node's replayed event log. On the mutating node that is the committed goal immediately; on a remote node, legs MAY run turns under the prior goal while the relayed event is delayed or partitioned away — the deliberate AP posture (remote runs continue locally; convergence is bounded by [Spec-024](024-cross-node-dispatch-and-approval.md)'s reconnect/replay, never by a cross-node lock) — and the precondition applies the relayed goal before the first turn after it arrives. The one-in-flight serialization above is likewise **per-node**: the intent table is daemon-local, so `session.goal_mutation_in_flight` refuses concurrent mutations only among callers of the same daemon, and mutations accepted on different nodes while the relay is delayed or partitioned are NOT mutually refused — they converge as a **last-writer-wins register**. Every daemon's goal projection folds `session.goal_updated` / `session.goal_cleared` in **two stages**: within one origin daemon, its own append order is authoritative — the origin's latest goal event by the **server-stamped payload keys `originNodeId` + `originSeq`** (the accepting daemon's per-session append sequence over the session's goal events — class-scoped: the 2026-08-11-amended channel-lifecycle payloads carry a sibling counter of their own and no consumer compares `originSeq` across event classes, per Spec-006 (PR #321 round 2) — durable on every goal payload per Spec-006, because a receiving daemon re-sequences relayed events under its own local `sequence` per ADR-017 and origin order would otherwise be unrecoverable), per [Spec-015](015-persistence-recovery-and-replay.md)'s within-daemon ordering rule (`occurred_at` is display/audit data and never orders same-daemon events, so a wall-clock step between two serial local mutations can never invert them) — and only BETWEEN different origins' latest candidates does the cross-origin comparator apply: envelope `occurredAt`, tie-broken by envelope `id` (the best V1 cross-daemon primitive — HLC is the V1.1 upgrade path per ADR-017/BL-076). The fold is a pure function of the event set, so once both events replay everywhere, every node settles on the same final goal (cross-node wall-clock skew is bounded by Spec-015's clock discipline, and a skew-misordered CONCURRENT write costs at most a goal overwrite between two mutations that raced anyway — never divergence), and the goal-at-turn-dispatch precondition applies the converged winner before each leg's next turn. A control-plane lease or lock on goal mutation is deliberately rejected: goal mutation stays available under partition — the same availability-over-consistency trade-off the cross-node AP model above already commits to.

## Same-Agent Provider Switch

Added 2026-08-26 (D-016-26) under [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md). An agent's provider is an **axis of its configuration**, not a fact fixed at attach. A participant may move a conversation from one provider to another — or to a different account of the same provider, a different model, or a different reasoning effort — without detaching the agent, losing the conversation, or starting a second one.

### The mutation surface

`AgentConfigUpdate` carries five provider-axis members beside the persona members it already had, every one **additive-optional**: `driverName?`, `providerAccountId?`, `modelId?` (pre-existing), `effort?`, and `outputSpeed?` (added 2026-08-29 — the count is re-derived by listing rather than incremented). `AgentAttach` carries `providerAccountId?` and `effort?` and deliberately **not** `outputSpeed?`: an agent is not born with a speed mode, and adding it there would put a fifth attach-time snapshot axis on the `agents` row for a preference no attach-time authorization decision reads. An omitted member is unchanged, not reset — the same additive-optional discipline [ADR-018](../decisions/018-cross-version-compatibility.md) binds everywhere else, and a caller written before this amendment behaves exactly as it did. There is correspondingly **no clear**: V1 offers no operation returning a provider axis to a driver default. `driverName` and `modelId` could not be cleared in any case — an agent always has both — and clearing `providerAccountId` or `effort` would need a third request state this surface deliberately does not carry, since "omitted means unchanged" is uniform here and a member that sometimes meant "reset" would make every omission ambiguous. The consequence is load-bearing downstream rather than merely tidy: the pending intent is stored as a two-state record of moved axes and their targets ([§State And Data Implications](#state-and-data-implications)), and a clear would have to widen that record to the `defaultNodeId` tri-state in the same amendment that minted it.

`effort` is first-class here rather than buried in the opaque `config` blob because it is validated, surfaced, and switched like `modelId` is: it is per-model, and the valid set is the target model's `effortLevels` as reported by the driver ([Spec-005 §Provider Parameter Vocabularies](005-provider-driver-contract-and-capabilities.md#provider-parameter-vocabularies)), not a corpus-wide enum. A value outside that set is refused rather than clamped, because a silently-lowered effort is a silently different agent.

`outputSpeed` is validated the same way, against a vocabulary the driver **publishes before the axis is offered** rather than one this spec names: `GetCapabilitiesResult.outputSpeedLevels`, present exactly where the `output_speed` flag is `true` and reaching clients on the same capability read the flag itself travels on ([Spec-005 §Provider Parameter Vocabularies](005-provider-driver-contract-and-capabilities.md#provider-parameter-vocabularies)). Publishing it is not optional politeness — a mutation validated against an unpublished set is a control whose accepted values no caller can discover, so the composer would have to guess and the daemon would have to refuse the guesses. Where the vocabulary is absent or empty the axis is **unsettable** and the mutation refuses `agent.provider_axis_invalid` fail-closed, which is the same answer an unrecognized value gets: an unsettable axis and an invalid value are both "this value will not be applied", and splitting them would tell a caller which providers are mid-rollout. An accepted value lands, at application, in the agent row's own provider-axis column beside the account and the effort ([§State And Data Implications](#state-and-data-implications)) — `NULL` until a switch sets one, which is what "an agent is not born with a speed mode" looks like as a starting state rather than as an attach-time member. That column is the **requested** mode and is what the agent read model returns for the axis; what the provider then **declared** is a separate, live-scoped observation served beside it from the live binding and stored nowhere ([Spec-005 §The output-speed axis](005-provider-driver-contract-and-capabilities.md#the-output-speed-axis)). Keeping them as two members rather than folding the observation into the column is what lets a caller see a mode that was accepted here and refused by the provider's own account gate — a single value would have to choose which of the two facts to lose. It is a column and not a key in the opaque `config` blob for the reason the paragraph above gives for `effort`, and for one more: the application transaction commits the effective binding into those columns in the same act as clearing the pending slot, so an axis with a durable pending home and no durable effective one would apply once and silently revert at the next restart.

### Application timing, and why the boundary depends on the axis

A switch applies **at the next boundary the target axis permits**, and the two boundaries are not interchangeable.

An axis the target driver accepts as a **per-turn override** applies at the next **turn boundary**: the running provider process carries the change into its next turn, nothing is respawned, and no transcript is replayed. Codex accepts per-turn `model` and `effort` overrides on `turn/start` ([Spec-005 §Provider Parameter Vocabularies](005-provider-driver-contract-and-capabilities.md#provider-parameter-vocabularies)).

An axis that is **spawn-bound** applies at the next **run boundary**, because realizing it requires a new provider process. `driverName` and `providerAccountId` are spawn-bound on every driver — a different vendor is a different binary, and [Spec-029 §Selection at run start](029-provider-accounts-and-credential-homes.md#selection-at-run-start) binds a run's account for the run's lifetime and forbids a resume silently rebinding it, a rule this section preserves rather than carves out. `modelId` and `effort` are spawn-bound on a driver that binds them at spawn instead of per turn, which the Claude leg does (same Spec-005 section). `outputSpeed` (2026-08-29) is spawn-bound on the one driver that declares the `output_speed` flag at all: [Spec-005 §The output-speed axis](005-provider-driver-contract-and-capabilities.md#the-output-speed-axis) binds the axis to that provider's **spawn-time settings opt-in** — the mechanism whose effect was measured — rather than to the interactive command the same provider also publishes, whose programmatic effect was not, so this axis resolves to a **`run`** boundary. Its settlement is then the ordinary spawn-bound one and needs no vocabulary of its own: the fresh process is reached by the canonical transcript, so the switch settles `replayed`, or `memo` where the replay could not be made, and never `in_place` — moving a settings flag rather than the model makes the reconstitution no smaller, because the same conversation still has to arrive. It is stated rather than left to the reader because it is the minority case on this mutation, and a probe confirming the command's effect would re-home it to a turn boundary by ordinary amendment on the same read-the-vocabulary rule. Which group an axis falls in is therefore **read from the target driver's declared vocabulary, never assumed**: the same `modelId` mutation is a turn-boundary change on one provider and a run-boundary change on another, and a daemon that guessed would either respawn needlessly or promise an immediacy the provider will not honor.

A turn already in flight completes on the binding that started it in either case — interrupting it would abandon work the participant is watching and would truncate the very transcript a spawn-bound switch then has to replay.

Mutation and application are therefore **two moments**. The mutation's own response acknowledges a **pending** switch and names the boundary it will apply at; `agent.provider_switched` is emitted at **application**, and it is what carries the settlement and the declared losses. This is the shape §Session Goals already uses for turn-boundary-effective delivery — the committed event records the mutation without claiming a mid-turn swap — and it is the only shape available here, since a spawn-bound switch cannot know what replay dropped until the replay happens.

**A pending switch is durable, and it is singular.** An acknowledgment that survives only in daemon memory is a promise a restart silently breaks: the caller has been told the switch will happen, the boundary arrives, and nothing does. So the pending intent is written **before** the acknowledgment returns and lives on the agent record itself ([§State And Data Implications](#state-and-data-implications)) — a daemon-minted `switchId`, the boundary it resolved, and the axes it moves. It rides `agent.config_updated` on that event's own `pendingSwitch` member, with the five provider axes travelling **inside** it rather than beside it, so the append that records an intent can never be read as the binding having moved ([Spec-006 §Channel and Agent Lifecycle](006-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle)); the pending state therefore rebuilds from the log alone rather than from a side store, and daemon startup **re-arms** it: a restart resumes waiting for the boundary rather than dropping the intent. What it does not do is re-validate optimistically — the application-time re-validation below runs on the re-armed path exactly as on the live one.

Exactly **one** switch is pending per agent, and that singularity is the ordering rule rather than a queue: a second provider-axis update while one is pending **supersedes** it, last writer wins, and the superseded intent never reaches a terminal event. Queuing would be worse in the way that matters — a participant who changes their mind twice would watch their first choice apply, run a turn, and then be replaced by their second. The superseding acknowledgment names the id it displaced, so the caller is told a supersession happened rather than left to infer it from an event that never arrives. Because the intent lives in a single slot on the agent row, the exclusion is structural: two concurrent mutations serialize on the same row under the daemon's session-mutation path, and the loser is a supersession, never a lost write. Supersession binds the **application** as well, not only the mutation. A superseded switch may still be in flight — its boundary hook armed, its interrupt dispatched, its target session perhaps already spawned — so every application step is guarded by a compare-and-set on `switchId`: the applying coordinator re-reads the pending slot **inside the same transaction that commits the binding**, proceeds only if the slot still holds its own id, and otherwise abandons the application entirely, emitting **no** terminal and clearing **no** slot. That is exactly what the rule above already promises — a superseded intent never reaches a terminal event — and it is what stops a stale application from erasing the switch that displaced it. Without the guard the last writer would win the mutation and then lose the application: switch B lands in the slot, switch A's boundary arrives, and A writes its own binding and clears B's promise.

The immediate arm is `interruptAndSwitch: true`, and the run-boundary group is why it exists: without it a spawn-bound switch waits for the run to end on its own, which across a long run is indistinguishable from being ignored. It **dispatches the existing `interrupt` intervention** and then applies at the boundary that interrupt creates — collapsing the two moments into one, the only case in which the mutation response can carry the settlement itself rather than a pending acknowledgment — and the only arm that holds its request open across the boundary in order to do so. Collapsing them does not skip the durability step: the pending intent is written before the interrupt is dispatched here exactly as on the deferred arm, and cleared when the settlement commits. **What the durable record must additionally carry is that an interrupt is owed at all**, and how far it got — the boundary alone cannot say, since a deferred switch and an interrupted one can both resolve to `turn_boundary`. So the slot records `interruptRequested` beside the boundary and, on this arm, an interrupt-dispatch progress marker advanced from `requested` to `dispatched` by its **own** durable write once the intervention is accepted. Recovery reads exactly that: a re-armed switch marked `requested` **redispatches** the interrupt, and one marked `dispatched` reconciles against the run rather than interrupting it a second time. Without the marker a restart would re-arm an immediate switch as though it were a deferred one and wait for a boundary nothing is going to produce — the crash would not cost the caller their answer, it would cost them the switch. A crash in between therefore costs the caller their answer and nothing else — the intent is re-armed at startup, the owed interrupt is redispatched, and the switch still applies — because an arm that waits for its own settlement is precisely the arm where losing the answer must not also lose the switch; the price of a crash between the two durable writes is one idempotent redispatch. That window is short but real, and keeping it real is what keeps the append honest: a client watching the session observes the same `agent.config_updated`-then-terminal pair on both arms, so the projection rebuilt from the log alone never has to know which arm produced it. It is an entry point into a control the corpus already has, not a sixth run control, so [Spec-004](004-queue-steer-pause-resume.md)'s V1 control set stays closed — the 2026-08-18 edit-affordance precedent, where the renderer's edit action dispatches the existing `rollback` intervention. Two consequences follow from that reuse and are deliberate: the interrupt is authorized as `Action::"intervene"` on the target run, and it settles through the ordinary intervention path, so a refused interrupt refuses the switch rather than leaving the agent half-moved.

Because that arm holds its request open until the switch settles, its response must express **every** settlement the boundary can reach, not only the good one. The mutation's response is therefore a four-arm discriminated union ([api-payload-contracts.md §Plan-016](../architecture/contracts/api-payload-contracts.md)): `pending` on the deferred arm, and `applied`, `degraded`, or `failed` on the immediate one. `degraded` is not a judgment a client makes — it is a **total mapping** from the settlement's own continuity, `degraded` exactly when continuity is `memo` and `applied` exactly when it is `in_place` or `replayed`, so the honest-degrade rule §Continuity states and [Spec-006](006-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle) restates for the terminal event is carried by the wire's own discriminator rather than re-derived by every renderer. `failed` carries the same closed seven-member `reason` vocabulary as `agent.provider_switch_failed` — one vocabulary across both surfaces — and is a **result rather than an error**, because the switch was accepted, the `switchId` was minted, and `agent.config_updated` was already appended: the mutation succeeded and only the application did not. A refusal reached **before** acceptance is the synchronous `agent.provider_axis_invalid` error instead, and mints no id and appends no event. A failing immediate arm still emits the terminal: the pending slot is cleared by a terminal and never by a reply, so an arm that answered its caller and appended nothing would leave a promise no replay could clear.

### Continuity, and what is declared rather than dropped

Continuity across a switch is canonical-transcript replay ([Spec-005 §Canonical Transcript Export And Replay](005-provider-driver-contract-and-capabilities.md#canonical-transcript-export-and-replay)). There is no provider-native path and there never will be — no vendor's resume verb accepts another vendor's session — which is the case [ADR-029](../decisions/029-canonical-transcript-is-authoritative.md) was triggered by.

Three consequences are stated rather than discovered:

- **Every switch MUST be assumed to lose the provider-side prompt cache.** No vendor publishes a cache-scoping contract this corpus can hold them to, so the rule is stated in the safe direction rather than in the precise one: the daemon assumes the miss, prices the switch as if the miss occurs, and tells the participant so. Being wrong in this direction over-warns and over-reserves; being wrong in the other direction bills a participant for a cost the affordance told them they would not pay. No axis is exempt — an effort-only change on an otherwise-identical binding is assumed to miss like any other, because the assumption costs an unneeded warning and the exemption would cost real money. A vendor that publishes a scoping contract at Verified grade re-opens this by ordinary amendment; until one does, the conservative rule stands.
- **What replay cannot carry is declared at application.** Provider-private reasoning heads that list by construction; visible reasoning summaries carry forward as plain text. The declared-loss list rides the `agent.provider_switched` event, and an **empty list is a positive assertion that nothing was dropped** — a driver that does not know what it lost may not emit one. A turn-boundary switch replays nothing and so drops nothing: its list is empty by construction, and that emptiness is the same positive assertion, not an absence of information.
- **A spawn-bound switch that cannot replay settles `degraded`, never `applied`.** Where the target declares `transcript_replay: false`, refuses the frames, or cannot fit the transcript, the daemon falls back to the memo projection and the switch reports `degraded` with the losses named. The switch still happens; the participant is told what the new provider can see. A turn-boundary switch has no replay to fail and settles `applied`.

  The settlement therefore has **three** continuity arms and not two, because a turn-boundary switch is not a degenerate replay — it is a different act. `in_place` is the running process carrying a per-turn override into its next turn: nothing was respawned, nothing was replayed, and its declared-loss list is empty **by rule**, not by luck. `replayed` is the canonical transcript reaching a fresh target session, and its list may be empty or not. `memo` is the floor, and its list is **required non-empty** and must name the summarization itself, since a memo settlement whose list said nothing would be claiming that replacing verbatim history with prose cost nothing. `in_place` and `replayed` are both `applied`; only `memo` is `degraded`. Collapsing `in_place` into `replayed` would force one of the two lies the wire must not tell: either an unreplayed switch reports a replay, or an empty loss list stops meaning "nothing was dropped".

### Refusals are fail-closed and precede any spend

A switch is refused, before any turn is started on the target, when the named driver is not registered on the hosting node, when the named provider account is not registered there, when the named model is not in the target driver's `listModels`, or when the named effort is not in that model's `effortLevels`. Because application may be deferred to a later boundary, that validation runs **twice** — at mutation, so the caller learns immediately rather than at a boundary it is not watching, and again at application, so an axis de-registered in the interval refuses the application and leaves the agent on its current binding rather than realizing a configuration the node can no longer honor. The account arm defers to [Spec-029](029-provider-accounts-and-credential-homes.md)'s registry and its fail-closed spawn gate ([Plan-029](../plans/029-provider-accounts-and-credential-homes.md) I-029-3) as the authority — the readiness projection on the account read is advisory and is not consulted as a gate here — and the registry being node-local is what bounds this surface: a caller can only name an account the operator already registered on that node.

**A refusal at application is an event, because no caller is there to receive an error.** The mutation-time arm answers the caller synchronously with `agent.provider_axis_invalid` (or, for the account axis, the account plane's own refusal), and that is the whole story only when the two moments coincide. Where application is deferred, the caller has already been acknowledged and disconnected, so a re-validation failure that produced only a log line would leave a pending switch that resolves into silence — the participant waits at a boundary that has already passed. Every deferred switch therefore reaches **exactly one terminal event**: `agent.provider_switched` on the arm that applied, or `agent.provider_switch_failed` ([Spec-006 §Channel and Agent Lifecycle](006-session-event-taxonomy-and-audit-log.md#channel-and-agent-lifecycle-session_lifecycle)) on the arm that did not, both carrying the `switchId` the acknowledgment named. The failure event carries a closed reason — which axis went unhonourable, or that the target could not be started at all — clears the pending intent, and leaves the agent on its current binding, which is the same fail-closed outcome the paragraph above requires and is now the outcome a client can render. A refused `interrupt` on the immediate arm settles the same way: the switch is abandoned with a reason rather than left half-moved. The single exception is supersession — a pending switch replaced by a later one emits no terminal of its own, and the superseding acknowledgment names it instead, because two terminals for what the participant experienced as one change of mind would be a worse record than none.

The memo floor is **not** a failure and never takes this path: a replay the target refuses settles `agent.provider_switched` with `continuity: 'memo'` and a non-empty loss list. The distinction is exactly whether the agent moved. A memo settlement moved it and told the truth about what came along; a failed application did not move it at all.

Authorization does not move with the axis. The mutation authorizes exactly as every other `AgentConfigUpdate` member already does — on session write access under [Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior)'s membership-role model — and the immediate arm's interrupt authorizes as `Action::"intervene"` on the target run, an action that spec's named-operation-action enumeration already carries. No third authorization is minted and none is owed: naming an account confers no spend authority the caller did not already hold, because causing execution on the hosting node is bounded by the unchanged node-trust rule, and the accounts a caller can name are exactly the ones that node's operator registered. Choosing among them is a configuration choice inside a boundary already authorized, not a new grant — which is why [Spec-012](012-approvals-permissions-and-trust-boundaries.md)'s named-operation-action enumeration does not grow here and that spec does not flip with this amendment.

### Identity, attribution, and what does not move

The agent keeps its `agentId`, its name, its channel membership, its run linkage, and its place in every projection built on those. A switch is a change of execution binding.

§Session Cost Receipt therefore keeps all three partition axes **unchanged in shape**. The per-run axis keys on runs, which are already per-binding. The per-caused-by axis keys on the turn-scoped effective principal, which a provider switch does not touch — switching provider does not change who caused the spend. The per-paying-account axis already keys on each run's `admittedProviderAccountId`, and the account axis applying at a **run** boundary is what keeps that key exact — every run carries one account for its whole life, exactly as [Spec-029 §Selection at run start](029-provider-accounts-and-credential-homes.md#selection-at-run-start) requires — so a session whose agent switched accounts mid-way yields two `byAccount` rows summing to the same session total: the axis reporting a real split, not a new arithmetic. Both partition identities in §Session Cost Receipt hold across a switch for exactly that reason, and this section adds no key, no fold, and no repricing.

## Provider-Native Subagents

- **Single-supervisor invariant (campaign B6): the daemon is the only cross-session supervisor.** A run MAY use its provider's in-session subagents (Claude `--agents` / Task tool; Codex `multi_agent` / `[agents]`) under the `subagentPolicy` the daemon passes through — the policy shape (`{enabled, maxDepth, maxConcurrent, definitions[]}`) is owned by [Spec-005](005-provider-driver-contract-and-capabilities.md) and its API Payload Contracts mirror.
- Budget roll-up: subagent usage aggregates into the run's own budgets — the §Budget Policies accountant sees it through the run's `usage` events, so subagents provide no budget escape hatch. Derived pricing resolves **per usage row**: a row wire-attributed to a model outside the run's admitted family keys off THAT model's family — the attribution rides the durable [Spec-006](006-session-event-taxonomy-and-audit-log.md) B6 usage-row fields `modelId?` / `modelFamily?` / `subagentId?`, populated by the driver normalizer from wire attribution (per-model usage maps; subagent-scoped usage pairing on the subagent triple; the normalizer duty lands with the campaign's Plan-005 bundle's normalizer tasks) — falling back to `admittedModelFamily` when the wire carries no attribution. A differently-modeled subagent is thus never priced under its parent's rates when the wire attributes it; and because the spawn screen above already requires every subagent-definition family to be priced or native-cap-covered at admission, an attribution-less row can at worst mis-allocate between two PRICED families' rates — it can never miss an unpriced-family block. And the admission-preemption rule above extends to spawn: `subagentPolicy.definitions[]` models resolve against the pricing table at spawn, and a definition naming an unpriced-family model on a capless leg is refused fail-closed (same `driver_capless` vocabulary) unless a native-cap reservation covers the run — coverage is **per-family across the run's whole model set** (parent + every subagent definition): each unpriced family needs its own `unpricedFamilyCaps` entry, and since the provider hard stop is run-wide, the single stamped `admittedUnpricedCapCents` is the **minimum** of those entries (run-wide spend ≤ every family's owner bound — deterministic and safe; an unpriced family with no entry refuses per the spawn screen) ([Spec-006 §Tool Activity](006-session-event-taxonomy-and-audit-log.md#tool-activity-tool_activity) records the same aggregation rule on `subagent.completed`, campaign B1).
- Approval flow-through: subagent tool calls flow through the same approval pipeline as the parent run's (Plan-012); a subagent introduces no separate trust surface.
- Timeline normalization: subagent lifecycle lands as the registered `tool_activity` rows `subagent.started` / `subagent.completed` (campaign B1), provider-attributed and pairing on the (`runId`, `provider`, `subagentId`) triple.
- In-session subagents execute beneath a single run and are not canonical child runs — the §Resolved Questions one-parent-child-layer delegation decision governs cross-run delegation and is unchanged by this section.
- The CLIs' own out-of-session supervisors (`claude agents` / `claude daemon`, `--bg` / `/background`, Codex cloud) stay disabled inside daemon-managed runs. This is the parity implementation of "background agents" — the daemon's orchestration layer IS the manager — not a capability rejection. Enforcement is layered: the daemon owns spawn argv and configuration and never enables those surfaces; the command-policy provider-supervisor deny applies for every effective posture ([Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior), campaign B20); and the Bash-sandbox/permission layer is the residual control against model-initiated supervisor spawns. The invariant is scoped to daemon-configured supervision.
- Concurrency: `maxConcurrent` enforces natively on the Codex leg. The Claude leg's spawn-side cap is docs-silent, so the daemon **enforces at its own boundary instead of trusting the provider**: subagent tool calls already route through the daemon's approval/execution pipeline keyed by the (`runId`, `provider`, `subagentId`) triple, and beyond-cap subagents serialize there — held at their next daemon-mediated call until a slot frees, never failed — keeping effective concurrency at or under `maxConcurrent` for all daemon-mediated work. Provider-internal reasoning by an excess subagent cannot be blocked from outside; it still debits the supervising run's budgets (no escape hatch, bounded by budget/idle limits), the breach diagnostic remains as the observability signal, and a leg that cannot mediate subagent tool calls keeps subagents disabled at spawn (fail-safe). Mechanism grades per the Spec-005 capability matrix: native vs boundary-serialized.

## Scheduler Limits

| Limit | Default |
| --- | --- |
| Max concurrent channels executing | 5 per session |
| Max queue depth per channel | 25 items (subject to Spec-001 per-session queue depth of 100) |
| Max pending orchestration runs | 10 per session |
| Max active children per parent run | 5 (daemon default — Tier-6 audit, D-016-11; not a product-wide ceiling per §Resolved Questions: the value is session-configurable via `OrchestrationBudgetUpdate`) |

Tier-6 audit semantics (D-016-11): a channel is **executing** when ≥1 run targeting it is in `starting` / `running` / `waiting_for_input` / `waiting_for_approval`; a **pending orchestration run** is an orchestration-created run in `queued`; a child is **active** for the active-child bound when in any of those four states or `queued`. All limits are enforced at create-time admission with zero residue (no run row, no queue item survives a refusal), the refusal is a typed error with explicit limit detail, and the daemon records it durably via `orchestration.rejected` ([Spec-006 §Channel Arbitration](006-session-event-taxonomy-and-audit-log.md#channel-arbitration-channel_arbitration)). All scheduler limits live with the budget limits in the session budget surface and are owner-adjustable (D-016-5).

## Partition And Reconnect Behavior

Multi-agent sessions span multiple runtime nodes; partition behavior inherits from [Spec-003](../specs/003-runtime-node-attach.md) and [Spec-015](../specs/015-persistence-recovery-and-replay.md). Spec-016 adds only the turn-arbitration and channel-visibility rules specific to multi-agent semantics.

- When a node loses its relay connection, the control plane marks it `offline` per Spec-003. Session membership is preserved and the node may reconnect under the same node identity.
- Child runs on the offline node continue locally if the node can still reach its provider; events buffer against the node's local audit log ([Spec-006](../specs/006-session-event-taxonomy-and-audit-log.md)) until relay catch-up via Spec-015 replay.
- Parent-channel views on connected nodes show the offline node's runs in an `unreachable` state with the last-known state preserved from the event cursor. `unreachable` is a visibility outcome, not a run-state transition — it is distinct from the run-level `paused` state defined in Spec-004.
- Turn-policy arbitration degrades by policy:
  - `free-form`: unaffected; addressed turns for the remaining reachable agents continue to admit in arrival order (activation stays addressing-gated per §Turn Policies — partition changes ordering availability, never the activation rule).
  - `round-robin`: if the next agent is on an unreachable node, arbitration pauses the channel and emits an `arbitration.paused` event (with `arbitration.resumed` on reconnect). Arbitration must not silently skip the unreachable agent (which would let a disconnected participant miss their turn without record) and must not auto-fail-over to free-form without explicit operator action. `arbitration.paused` and `arbitration.resumed` are registered in the [Spec-006](../specs/006-session-event-taxonomy-and-audit-log.md) canonical event taxonomy under the `channel_arbitration` category (BL-084, completed 2026-04-18).
  - `request-based`: unaffected on the sender side; responders on unreachable nodes do not consume their turn and the request expires per its normal timeout.
- On reconnect, buffered events catch up via Spec-015 replay and any arbitration pause resolves automatically once the canonical ordering is restored.
- Runs that cannot be resumed because provider-session state was lost transition to `failed` per Spec-015; they must not reappear as a new run.
- The control plane does not enforce cross-node consensus on turn arbitration. Local daemons own their attached runs; cross-node ordering is eventually consistent through the event log. A round-robin channel with two agents on two partitioned node-halves may briefly see divergent local views; Spec-015 replay reconciles on reconnect. Availability over consistency (AP) is the explicit trade-off for the collaboration surface.

## Implementation Notes

- Keep orchestration semantics provider-agnostic and session-scoped.
- Channel creation should be lightweight, but channel identity must remain durable enough for audit and replay.
- Internal helper runs should be discoverable without overwhelming the default UI.

## Pitfalls To Avoid

- Treating multi-agent orchestration as only a UI grouping trick
- Hiding child-run provenance
- Assuming provider-native spawn semantics are universal

## Acceptance Criteria

- [ ] A session can host multiple concurrent agents and channels.
- [ ] Parent-child run relationships remain visible after replay and reconnect.
- [ ] Delegated work remains possible even on drivers without native subagent APIs.
- [ ] Every surfaced cost figure equals the committed-spend fold the accountant enforces against, and carries its provenance from the wire.

- [ ] An agent whose provider, account, model, or effort is changed keeps its `agentId`, its channel membership, and its run linkage, and the conversation continues rather than restarting.
- [ ] A switch requested without `interruptAndSwitch` leaves an in-flight turn to complete on its original binding and takes effect at the next boundary its target axes permit — a **run** boundary whenever `driverName` or `providerAccountId` moves, a **turn** boundary only where every moved axis is a per-turn override on the target driver, and the widest of the two on a multi-axis update; the immediate arm dispatches the existing `interrupt` intervention and mints no new run control.
- [ ] A switch naming an unregistered driver, an unregistered provider account, a model absent from the target driver's `listModels`, or an effort absent from that model's `effortLevels` is refused before any turn is started on the target.
- [ ] A switch whose target cannot be replayed into settles `degraded` with a non-empty declared-loss list, never `applied`, and the participant is told what the new provider can see.
- [ ] After a mid-session account switch, the session cost receipt's `byAccount` rows still sum to the session total, and the per-caused-by rows are unchanged by the switch.
- [ ] An `outputSpeed` mutation is acknowledged `pending` naming a **`run`** boundary and applies at the next run rather than the next turn; the same mutation against a driver declaring `output_speed: false` refuses before anything is spent and is never satisfied by changing `effort` instead.

Three alternatives were considered and rejected. A **display-side sum over the visible run list** is the surveyed failure mode itself — it renders whatever the list happens to show, which under any delegation is less than what the ledger holds. A **second fold maintained for presentation** drifts by construction: two accountants over the same events diverge the moment one gains a case the other lacks, and the divergence is invisible precisely because both look authoritative. **Labelling the total a lower bound** is correct for a row-counting fold and wrong for this one, which charges an unpriced run its full admitted cap, so the label would understate the spec's own conservatism and invite a compensating second estimate — and where the mid-run tier-(c) residue of §Cost Figure Display Consistency clause (c) is present the total is a bound in neither direction, which is why non-exactness surfaces through the aggregate `costStatus`, never through a bound label. No budget is added and no number changes: the decomposition members report the legs the fold was already rebuilt from, and the three-budget table stays the closed set it was.

## V1 Readiness Review (BL-042, 2026-04-17)

Review against the V1 quality bar declared by [ADR-015](../decisions/015-v1-feature-scope-definition.md) §Thesis. Findings:

- **Turn policy defaults** — `free-form` is the explicit default. Round-robin and request-based are documented alternatives with deterministic triggers. No "configurable without default" surfaces remain.
- **Budget policy defaults** — Named defaults for per-run token (100,000), per-session cost ($10.00), and per-agent turn (50) limits. V1 enforcement tightened from advisory to hard ceiling via intervention dispatch during this review. Soft warning at 80%, hard interrupt at 100%.
- **Stop conditions** — Four named conditions (turn limit, budget exhausted, explicit stop, idle timeout) with deterministic triggers. Idle timeout default is 5 minutes. Conclusion detection deferred to V2.
- **Moderation / approval hooks** — Pre-turn (category `gate`) and post-turn (informational) hooks integrate with [Plan-012](../plans/012-approvals-permissions-and-trust-boundaries.md) approval categories. Opt-in per channel is the V1 default.
- **Turn arbitration under partition** — Named partition behavior added: `round-robin` pauses arbitration when the next agent is on an unreachable node with explicit `arbitration.paused` / `arbitration.resumed` events (registration in Spec-006 is a Plan-016 precondition — tracked as BL-084); `free-form` and `request-based` degrade gracefully. Reconnect semantics align with Spec-003 node-identity continuation and Spec-015 replay. Eventually-consistent cross-node ordering is the accepted trade-off (AP over CP for the collaboration surface).
- **ADR-011 intervention dispatch** — Non-cascading propagation clarified; no new intervention verbs introduced; subtree-wide cascade would be a new ADR, not a Spec-016 edit.

Behavioral change: budget enforcement posture (advisory → hard ceiling). No blocking changes required to ADR-011, Spec-004, Spec-012, or the approval policy surface. Turn arbitration pause is an orchestration-layer visibility state distinct from run-level `paused`, consistent with Spec-004's discrimination of waiting states.
