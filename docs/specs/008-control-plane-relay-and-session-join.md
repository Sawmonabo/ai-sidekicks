## Purpose

Define how participants authenticate, join shared sessions, and use relay-assisted connectivity without moving execution into the control plane.

## Required Behavior

- Shared session join must require authenticated membership verification.
- A participant must be able to join a live session before attaching any runtime node.
- The control plane must provide session directory, invite resolution, presence registration, and relay coordination.
- Relay coordination must not grant the control plane arbitrary execution authority over participant nodes.
- A participant changing between direct and relay connectivity must remain attached to the same session identity when membership is still valid.
- The control plane must track presence for both participants and runtime nodes, even when relay is not currently in use.
- A participant joining a live session must be able to reconstruct the part of that session's prior history it is **entitled** to from its **peers'** local event logs. The control plane stores no session events ([ADR-017](../decisions/017-shared-event-sourcing-scope.md)) and pre-join relay ciphertext is undecryptable to a new member, so peer re-publication is the only V1 path and it is normative, not best-effort — see §Peer History Backfill On Join (V1).
- Backfilled history must be verified against its **originating** daemon's signature before it is appended, must be served only from origin-signed bytes (never a re-signed received copy), must be scoped to the joining participant's entitlement — session membership, and channel membership wherever a channel restricts it — and must surface an explicit pending state naming every source that has not answered and every roster origin no answer has claimed.
- Relay traffic for an event scoped to a **membership-restricted** channel must be addressed only to that channel's members, never to the full session recipient set, so a non-member participant's daemon never receives the ciphertext at all. V1's one membership-restricting kind is [Spec-016](./016-multi-agent-channels-and-orchestration.md)'s `direct` two-human channel — see §Per-Channel Recipient Scoping (V1), which also states what this does **not** guarantee.

## Control-Plane Transport Protocol

The control plane uses a dual-transport architecture per [ADR-014](../decisions/014-trpc-control-plane-api.md):

- **tRPC v11** for request-response operations and SSE subscriptions.
- **WebSocket (JSON-RPC 2.0)** for bidirectional collaboration channels.

**tRPC (request-response) handles:**

- Session CRUD (create, read, update, archive)
- Membership management (add, remove, role changes)
- Invite lifecycle (create, revoke, accept)
- Approval operations (request, resolve, escalate)
- Artifact metadata (publish, query, reference) — artifact ciphertext chunk upload/fetch (resumable chunk PUTs + authenticated per-chunk GETs) rides the [Spec-014 §Cross-Node Artifact Relay (V1)](./014-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1) blob-store surface, owned by Spec-014 and not restated here
- Relay negotiation (`negotiateRelay` — returns the relay endpoint + short-lived `connectionToken`; the subsequent WSS binary frame exchange is separate, per §Relay Negotiation)
- Health checks

**SSE (via tRPC subscriptions) handles:**

- Event streaming (session timeline, run output)
- Run state updates (started, paused, resumed, completed, failed)
- Notification delivery (mentions, approval requests, membership changes)

**WebSocket (JSON-RPC 2.0) handles:**

- Presence sync (heartbeats, cursor position, active/idle state)
- Live collaboration events (typing indicators, shared editing state)

**Relay WSS (binary wire frames — §Message Framing) handles:**

- Relay message exchange (end-to-end encrypted collaboration traffic; V1 pairwise X25519 + XChaCha20-Poly1305, V1.1+ MLS — see §Relay Encryption) — negotiation rides tRPC request/response (ADR-014), the connection authenticates via `Sec-WebSocket-Protocol` at WSS upgrade (§Connection Lifecycle), and every frame on the connection is a §Message Framing binary frame, never JSON-RPC (2026-07-02 ADR-009/ADR-014 correction)

### Client SDK Implementation Guidance

**Desktop renderer:**

- Uses tRPC client with React Query integration for typed queries and mutations.
- SSE subscription (via tRPC `subscription`) for live timeline updates and notifications.
- WebSocket connection for presence sync and collaboration events.

**CLI:**

- Uses tRPC client (vanilla, no React Query) for typed queries and mutations.
- SSE for event tailing (run output, session timeline).
- WebSocket for presence is optional -- CLI may skip live presence when non-interactive.

**Shared contract surface:**

- Both clients import types from `packages/contracts/` -- no codegen needed (tRPC router type inference).

**Connection lifecycle:**

- tRPC client reuses HTTP/2 connections; connection pooling is handled by the runtime (Node.js `fetch` or browser).
- WebSocket reconnects with exponential backoff (initial 1s, max 30s, jitter).
- SSE auto-reconnects via the EventSource spec (`Last-Event-ID` header for resumption).

## Relay Encryption

V1 relay encryption is defined by [ADR-010](../decisions/010-paseto-webauthn-mls-auth.md); the properties summarized here are authoritative for V1 implementation.

**V1 cipher suite (pairwise X25519 ECDH + XChaCha20-Poly1305):**

- Libraries: `@noble/curves` (X25519; audited by Cure53, Kudelski Security, and Trail of Bits) and `@noble/ciphers` (XChaCha20-Poly1305; audited by Cure53).
- Each participant generates an **ephemeral X25519 key pair per session** (not per message); these are zeroed when the session ends. A long-term **Ed25519 identity key** signs the ephemeral X25519 public key, binding the session key exchange to the participant's control-plane-registered identity. CLI at-rest storage of this long-term Ed25519 identity key is specified by [ADR-021](../decisions/021-cli-identity-key-storage-custody.md); desktop clients derive the key from a WebAuthn PRF ceremony per [ADR-010](../decisions/010-paseto-webauthn-mls-auth.md).
- The control plane distributes signed `SessionKeyBundle` entries (`{ephemeral_x25519_public, ed25519_identity_public, signature}`). A compromised control plane cannot forge valid Ed25519 signatures.
- Session keys are derived via HKDF-SHA256 (RFC 5869) from the ECDH shared secret: `sessionKey = HKDF-SHA256(shared, salt=session_id, info="ai-sidekicks/v1/pairwise", length=32)`.
- Each message is encrypted per-recipient with a fresh 24-byte random nonce; the AEAD associated data binds the recipient's principal identifier **and** the per-sender monotonic sequence number (`recipient_id ‖ seq`), yielding per-recipient `(sender_ephemeral, recipient_id, seq, nonce, ciphertext+tag)` envelopes. `sender_ephemeral` is the sender's session ephemeral X25519 public key (the same value carried in its `SessionKeyBundle`), included in the clear as the recipient's **key-selection handle**: the recipient looks up the pairwise key it derived from that ephemeral (the per-pair derived-keys map is keyed by exactly this value) and the AEAD tag verifies **only** under that key, so a relay-mislabeled `sender_ephemeral` selects the wrong key and fails the tag. Authenticity follows from key-selection **because the key is pairwise** — held only by the two endpoints, so a valid tag under it proves the peer sent it (the Olm/Signal Double Ratchet property), unlike Megolm's _group_ key, where key-selection is non-authenticating and a separate Ed25519 signature is required. The cleartext handle itself follows the Megolm session-id lookup idiom — carried in the clear, never trusted as a sender claim (MSC3700). `sender_ephemeral` is therefore **not** bound into the associated data, which stays `recipient_id ‖ seq`. The `seq` is carried in the envelope in the clear so the receiver can reconstruct the associated data, but it is authenticated by the AEAD tag — a tampered `seq` fails verification (the DTLS/QUIC/Noise sequence-in-clear-authenticated-as-AAD idiom). Recipients reject any frame whose `seq` is ≤ the last accepted for that sender (resolved via `sender_ephemeral`), providing replay protection within a session.
- Properties: **session-granularity forward secrecy** (ephemeral X25519 discarded at session end), zero-knowledge relay. Post-compromise security and per-message ratcheting are V1.1 properties delivered by the MLS upgrade (see below).
- **Participant cap:** V1 pairwise sessions are limited to ≤ 10 active participants to bound the N² per-message fan-out cost.
- Wire format: 4-byte length prefix + 1-byte message type (pairwise ciphertext envelope vs relay control) + payload.
- Connection authentication: PASETO v4 tokens.
- WebSocket Hibernation: relay DOs sleep between messages for cost efficiency.

**V1.1+ upgrade path (MLS, RFC 9420):**

MLS via an audited implementation (OpenMLS, mls-rs, or a post-audit TypeScript implementation) is the planned V1.1 relay encryption layer, adding post-compromise security and O(log N) group rekeying. MLS ships behind a feature flag and is promoted to the default cipher once all three promotion gates in [ADR-010 §Success Criteria](../decisions/010-paseto-webauthn-mls-auth.md#success-criteria) pass (external audit, interop testing, production soak). The V1 pairwise layer continues to serve sessions whose participants have not yet adopted V1.1. KeyPackage distribution, group-add/remove, and welcome-message flows will be specified in the V1.1 relay spec revision once implementation selection lands.

## Relay Connection Lifecycle

1. **Connect**: Client establishes a WSS connection to the relay endpoint. The endpoint URL is provided by the control plane via `RelayNegotiationResponse`.
2. **Authenticate**: Client presents a PASETO v4.public token in the WebSocket handshake via the `Sec-WebSocket-Protocol` header as two subprotocol values — `paseto-v4, <base64url(token)>`: the first value names the auth scheme (which the relay echoes back as the negotiated subprotocol), the second carries the base64url-encoded token. (Browsers cannot set custom WebSocket headers, so the bearer token rides in the subprotocol header — the established Kubernetes apiserver idiom, [kubernetes/kubernetes#47740](https://github.com/kubernetes/kubernetes/pull/47740); base64url-encoding keeps the value within the RFC 7230 `token` grammar the subprotocol field requires, independent of token format.) The relay reads the second value, base64url-decodes it, validates the token, and establishes the session-scoped channel.
3. **Session Key Establishment**: The client generates an ephemeral X25519 key pair, signs the public key with its long-term Ed25519 identity key, and posts the resulting `SessionKeyBundle` to the control plane. The control plane verifies the Ed25519 signature, publishes the bundle to other session participants, and returns their bundles. The client derives per-pair session keys via HKDF-SHA256 from each X25519 ECDH shared secret and caches them for the session's lifetime.
4. **Message Exchange**: All message payloads are encrypted per-recipient under the derived pairwise session keys. The recipient set is the session's current recipient set, **narrowed** for an event scoped to a membership-restricted channel per §Per-Channel Recipient Scoping (V1). The relay sees only opaque per-recipient ciphertext envelopes and forwards them without inspection.
5. **Graceful Close**: The client notifies the control plane that the session has ended, zeroes its ephemeral X25519 secret key and derived session keys in memory, and closes the WebSocket connection. The control plane discards the participant's `SessionKeyBundle`.
6. **Reconnect**: The client re-authenticates with a fresh PASETO token, fetches any missed messages via the control plane, and (if its ephemeral X25519 material is still resident) resumes using the same session keys. If the client restarted between sessions, it generates a new ephemeral X25519 key pair and re-establishes session keys as in step 3.

### Message Framing

- **Wire format**: WebSocket binary frames.
- **Frame structure**: `[4-byte big-endian length][1-byte message type][payload]`. V1 payload is a pairwise ciphertext envelope (`{sender_ephemeral, recipient_id, seq, nonce, ciphertext+tag}`) — `sender_ephemeral` is the sender's 32-byte session ephemeral X25519 public key, the recipient's O(1) key-selection handle into its cached pairwise-key map (sender authenticity follows from which key verifies the tag, so `sender_ephemeral` is **not** AEAD-bound; the associated data stays `recipient_id ‖ seq`). The `seq` is the per-sender monotonic sequence (8-byte big-endian) bound into the AEAD associated data and carried in the clear for receiver reconstruction. Both `sender_ephemeral` and `seq` live inside the opaque `[payload]`, not in the frame header — the R1 frame codec wraps the envelope without inspecting it. V1.1+ payload (MLS) is an MLSCiphertext structure.
- **Maximum frame size**: 64 KB. Messages larger than 64 KB must be chunked at the application layer before encryption. The 4-byte length prefix counts the 1-byte message type + payload, and the codec enforces the 64 KB cap on the frame consistently on encode and decode.
- **Heartbeat**: WebSocket ping/pong at 30-second intervals for keepalive. If no pong is received within 60 seconds, the client must treat the connection as dead and begin reconnect.

### Session Membership Management (V1 Pairwise)

- **Session creation**: The first participant posts a `SessionKeyBundle` (ephemeral X25519 public key signed by the long-term Ed25519 identity key) to the control plane. No group state is maintained beyond the set of active `SessionKeyBundle` entries.
- **Member addition**: The joining participant posts its own `SessionKeyBundle`. Existing members fetch the new bundle, verify the Ed25519 signature, and derive a pairwise session key with the new member via X25519 + HKDF-SHA256.
- **Member removal**: When a participant leaves (or is removed for policy reasons), the control plane discards that participant's `SessionKeyBundle`. Remaining participants drop the per-pair session keys that reference the removed participant. Because there is no shared group key, no rekey is required on removal — future messages are simply not addressed to the removed participant.
- **Key rotation**: Session keys rotate at session boundary. Long-running sessions that require intra-session key rotation must end and restart the session (acceptable trade-off for V1; V1.1+ MLS adds automatic mid-session rekeying via `Update`/`Commit`).

### Per-Channel Recipient Scoping (V1)

The fan-out above addresses the **session's current recipient set** — the participants whose `SessionKeyBundle` entries are admitted at send time, distributed as the server-attested `DistributedSessionKeyBundle` records §Trust Properties describes. That set is what makes the membership epoch meaningful: a participant admitted later cannot read earlier traffic because no envelope was ever sealed to it. A channel that **restricts membership** narrows the set further, and this section defines by how much. It exists because [Spec-016 §Interfaces And Contracts](./016-multi-agent-channels-and-orchestration.md#interfaces-and-contracts)'s `direct` two-human channel names confidentiality from non-member **humans** as "a distinct, relay-layer property this spec depends on rather than defines" — defined here.

**The predicate is structural, never an event-type list.** A session event is channel-scoped when its `payload` carries a `channelId` binding; the binding lives in the payload because the envelope's canonical top-level member set is closed ([Spec-006 §Canonical Serialization Rules](./006-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules)), so scoping adds no envelope member and could not. The rule keys on the **channel record that binding resolves to**, never on the event's `type`: every type [Spec-006](./006-session-event-taxonomy-and-audit-log.md) gives a `channelId` payload member is covered by construction, and a type that gains one later is covered the day it does. An enumerated list would have to be re-derived on every taxonomy addition and would fail **open** on the one it missed — the wrong direction for a confidentiality rule.

**Membership restriction is not audience.** V1 has exactly one membership-restricting kind: [Spec-016](./016-multi-agent-channels-and-orchestration.md)'s `direct` channel, whose two-human member pair is fixed at creation and immutable thereafter. `humans-only` **audience** is a different restriction on a different axis — it withholds content from **agents**, not from participants, and a `humans-only` channel that is not `direct` still inherits full session membership, so every member's daemon legitimately holds its plaintext. Recipient scoping therefore keys on the `direct` kind's member pair and never on `audience`.

**The rule.** For a channel-scoped event on a membership-restricted channel, the origin daemon derives the envelope recipient set as **the channel's member set intersected with the session's current recipient set**, and seals one envelope per member of that intersection — never one per session recipient. A non-member's daemon receives no ciphertext for that event at all; the withholding is at addressing time, not a decrypt-side check, so there is nothing for a non-member to attempt and no ciphertext for it to retain against a future key compromise. Both sides of the intersection are `ParticipantId`-keyed — the channel's member pair is two humans, and `recipient_id` is a peer `ParticipantId` (§Message Framing, §Trust Properties) — so the intersection is well-typed without a second identity mapping.

**Composition with the membership epoch.** The intersection is a further narrowing **on top of** the epoch-current recipient set, never a replacement for it: an event reaches a participant only if it is both a channel member and in the recipient set at send time. The two narrowings compose in one direction only. For a `direct` channel the pair is immutable, so no epoch transition can ever **widen** that channel's recipients — a later joiner enters the session's recipient set but never the pair, and the intersection is unchanged by its arrival, which is exactly the property a general channel-membership model would not have. Departure narrows further (a departed pair member leaves the recipient set), the safe direction.

**Totality, and the one refusal.** The predicate is total over a session's channels. The bootstrap `main` channel has no channel row and emits no `channel.created` ([Spec-016 §State And Data Implications](./016-multi-agent-channels-and-orchestration.md#state-and-data-implications)), so it resolves structurally from its session-derived identity, is unrestricted by construction, and is never an unresolvable binding — a `main`-bound event takes the full recipient set, and the one channel every session has carries no unspecified case. What remains is a `channelId` the origin cannot resolve at all, which on this path is a **producer invariant violation** rather than an operational state: the origin authored the row it is publishing and holds the channel record it projected. That case is **fail-closed — publication is refused, never widened to the unscoped set** — because a wrong narrowing is a delivery failure the sender observes and retries, while a wrong widening is a disclosure no later action recalls. It mints no error code: it is an internal producer bug, not a wire outcome a peer negotiates.

**Backfill applies the same predicate at a different point.** A `HistoryBackfillChunk` is addressed to the requesting joiner alone, so the leg that needs scoping there is **selection**, not addressing: a source never _serves_ an event of a membership-restricted channel to a requester outside that channel's member set — normative in §Peer History Backfill On Join (V1) alongside the sentinel-bound-row and `pii_payload` exclusions, since the immutable pair reduces it to never serving a `direct` channel's events outside that pair. It mints no new terminal coverage gap: every event of a `direct` channel is authored by one of the two pair members, so within the pair the channel's history stays fully re-servable by its origins, exactly like any other span.

**Named residual: this scopes daemons, not agents.** Recipient scoping withholds ciphertext from **non-member humans' daemons** — that, and nothing more. A member's own daemon holds the channel's plaintext by design, so no cryptographic property here prevents that daemon from placing the content into an agent's context; agent exclusion is the separate normative daemon obligation [Spec-016 §Interfaces And Contracts](./016-multi-agent-channels-and-orchestration.md#interfaces-and-contracts) places at **agent-context assembly**, discharged through the single audience-filter seam [Plan-016 §Cross-Plan Obligations](../plans/016-multi-agent-channels-and-orchestration.md#cross-plan-obligations) registers as CP-016-14. The two properties are complementary and neither substitutes for the other: encryption keeps a non-member's daemon from ever holding the bytes; the daemon obligation keeps a member's own agents from being handed bytes that daemon does hold. A reader who takes recipient scoping for the agent-exclusion mechanism has the trust boundary wrong — and on a `humans-only` channel that is not `direct`, where every member daemon holds plaintext by design, the daemon obligation is doing **all** of the work.

**No new mechanism.** Scoping changes which recipients an envelope is sealed to and nothing else: no new transport, no new frame message type, no `SessionKeyBundle` or `DistributedSessionKeyBundle` change, no new table, no new error code. The channel kind and a `direct` channel's member pair are already durable on the channel record and event-carried so replay cannot widen audience ([Spec-016 §State And Data Implications](./016-multi-agent-channels-and-orchestration.md#state-and-data-implications)), so the origin derives the scoped set from state it already projects — and a replaying daemon derives the same set, because the inputs are event-carried rather than reconstructed from live membership.

### Group Management (V1.1+ MLS — Planned)

### Relay Negotiation

The control plane provides the following via `RelayNegotiationResponse`:

| Field | Value |
| --- | --- |
| Relay endpoint URL | WSS URL for the relay endpoint. The verifier MUST be able to recover the connection's `sessionId` from this URL **out-of-band from the connect-token** (the implicit-assertion requirement below): the hosted topology satisfies this via session-sharding (the relay Durable Object _is_ the session), and a non-session-sharded verifier — the self-hostable single-process relay (Plan-025) — satisfies it by minting the endpoint with `sessionId` as a path segment (`wss://<host>/relay/<sessionId>`). |
| Transport protocol | `websocket` |
| Connection token | Short-lived PASETO v4.public token (TTL: 300 seconds) |
| Session ID | The session's identifier, used as HKDF salt during session-key derivation |
| Cipher suite version | `v1/pairwise` for V1; a V1.1+ client may indicate MLS capability and the control plane returns the negotiated suite |

**V1 connection-token claim shape:** The `connectionToken` is a PASETO `v4.public` capability minted by the control plane's relay-negotiation issuer (signing custody is Plan-018's; the relay broker only verifies) and presented at the relay WSS upgrade. It carries these registered claims:

- `iss` — the relay-negotiation issuer identity;
- `sub` — the authenticated `ParticipantId` the negotiation was performed for;
- `aud` — `relay-connect`, distinguishing it from endpoint-authentication tokens;
- `exp` — a 300-second expiry matching the connection-token TTL above;
- `sessionId` and `nodeId` — the negotiated channel the token authorizes.

The negotiated `sessionId` is **additionally bound as the PASETO v4 implicit assertion** at both mint and verify: the relay WSS handshake supplies its own session's `sessionId` as the implicit assertion, so a token minted for one session **fails verification cryptographically** when replayed against another — the binding is carried by the signature, not by a claim comparison a verifier could forget to perform. `sessionId` is the sole implicit-assertion component because it is the only value the verifier independently holds at the upgrade — the hosted relay Durable Object is session-sharded, so it knows its own `sessionId`, and a non-sharded verifier (the self-hostable single-process relay, Plan-025) recovers the same `sessionId` from the relay-endpoint URL path segment the control plane minted (the `RelayNegotiationResponse` relay-endpoint URL, §Relay Negotiation), out-of-band from the token either way; `nodeId` and `sub` arrive only inside the token — it is the single credential the client presents (carried in `Sec-WebSocket-Protocol`, nothing else) — so they remain signed claims the verifier reads from the verified token and adopts as the connection's identity. The handshake refuses the upgrade unless `aud == relay-connect`, `exp` is unexpired, the implicit-assertion `sessionId` matches the verifier's own session, and `sub` and `nodeId` are present. The 300-second TTL bounds bearer replay within a session; binding the token to a proof-of-possession key is a V1.1 hardening that ships alongside MLS.

**V1 SessionKeyBundle requirements:**

- Ephemeral X25519 public key (32 bytes)
- Long-term Ed25519 identity public key (32 bytes)
- Ed25519 signature over the concatenation of session ID and ephemeral X25519 public key
- Bundle lifetime: the session's lifetime. Each new session requires a fresh ephemeral X25519 key pair.

Clients must post a fresh `SessionKeyBundle` to the control plane before requesting relay negotiation. Reused ephemeral X25519 public keys across distinct sessions must be rejected by the control plane.

**V1.1+ KeyPackage requirements (planned, ships with MLS upgrade):**

- Signing key: Ed25519
- Init key: X25519
- Cipher suite: `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`

### Trust Properties

**Threat model**: The relay operator is honest-but-curious. The relay can observe metadata (who connects, when, message sizes) but cannot read message content.

**Trust anchors**: Participant identity is established via control plane authentication. In V1, each participant's long-term Ed25519 identity key signs its per-session ephemeral X25519 public key; the control plane verifies each signature before distributing the `SessionKeyBundle` to other participants, and any bundle whose Ed25519 signing key is not bound to a registered participant identity — or whose admission-resolved owner is not the authenticated caller posting it — is rejected. In V1.1+, the same identity-binding applies to MLS KeyPackages.

The control plane distributes admitted bundles as `DistributedSessionKeyBundle` records, each pairing a `SessionKeyBundle` with the **server-attested** `ParticipantId` of its owner — the identity the control plane authenticated at bundle admission, carried alongside the bundle rather than inside the client-signed `SessionKeyBundle` (which has no participant field). This lets a recipient map a relay `recipient_id` (a peer `ParticipantId`) to that peer's ephemeral X25519 public key and derive the pairwise key. The `ParticipantId` is never client-asserted: because a bundle whose admission-resolved owner is not the authenticated caller is rejected (above), the distributed record's identity is the control plane's attestation, not a self-claim.

**V1 guarantees:**

- **Session-granularity forward secrecy** -- past session keys become undecryptable after the session ends, because the ephemeral X25519 material is zeroed. Compromise of the long-term Ed25519 identity key does not reveal past session keys.
- **Zero-knowledge relay** -- the relay sees only opaque per-recipient ciphertext and cannot read, forge, or replay messages. Per-sender monotonic sequence numbers — carried in the envelope and bound into AEAD associated data — provide in-session replay protection; the recipient resolves which per-sender counter and pairwise key apply via the `sender_ephemeral` handle (only the true sender's key verifies the tag, so the handle cannot be spoofed into accepting a forged sender). The relay forwards `sender_ephemeral`, `seq`, `nonce`, and `ciphertext+tag` opaquely (it routes on `recipient_id` alone) and learns nothing about the sender beyond what the connection already reveals — the per-session ephemeral is unlinkable across sessions.
- **Membership-restricted channel confidentiality** -- an event scoped to a membership-restricted channel is sealed only to that channel's members, so a session participant outside the channel never receives the ciphertext (§Per-Channel Recipient Scoping (V1)). In V1 the restricting kind is [Spec-016](./016-multi-agent-channels-and-orchestration.md)'s `direct` two-human channel, whose immutable pair means no later membership change widens the set.

**V1.1+ additional guarantees (delivered by MLS upgrade):**

- **Per-message forward secrecy** via tree-based key ratcheting.
- **Post-compromise security** -- a compromised member can be removed and the group re-keyed, restoring confidentiality for future messages.

**Non-guarantees (V1 and V1.1+)**: The relay CAN perform traffic analysis (timing, message sizes, connection patterns). Metadata protection is out of scope for V1. Post-compromise security and per-message forward secrecy are V1.1+ properties, not V1. **Recipient scoping is not agent exclusion**: it bounds which _daemons_ hold a channel's plaintext and says nothing about what a member's own daemon does with plaintext it legitimately holds — keeping a channel's content out of agent context is [Spec-016](./016-multi-agent-channels-and-orchestration.md)'s daemon obligation at agent-context assembly, not a property of this layer (§Per-Channel Recipient Scoping (V1)). Channel-membership metadata is likewise unprotected from the **relay operator**: the relay routes on `recipient_id`, so a narrowed fan-out is observable as a narrowed fan-out, and a membership-restricted channel's existence is operator-inferable from that traffic pattern alone — the operator's channel signal is traffic-shaped, not row-shaped, since the [shared Postgres schema](../architecture/schemas/shared-postgres-schema.md) defines no channel table. To a non-member **participant**, though, a `direct` channel's existence is no longer observable through the control-plane channel projection: [Spec-002 §Interfaces And Contracts](./002-invite-membership-and-presence.md#interfaces-and-contracts) (amended 2026-08-03) omits it entirely for any caller outside its member pair — the control-plane half of the two-surface non-disclosure property whose daemon half is [Spec-016 §Interfaces And Contracts](./016-multi-agent-channels-and-orchestration.md#interfaces-and-contracts)'s `ChannelRosterRead` omission, a metadata property those surfaces own; this layer seals content, not metadata.

## Peer History Backfill On Join (V1)

A member who joins mid-session cannot read the session's prior history from any surface this spec previously contracted. V1 event logs are per-daemon ([ADR-017](../decisions/017-shared-event-sourcing-scope.md) Option B), so the control plane holds no session events to hand over; the relay is zero-knowledge (§Trust Properties), so it holds only ciphertext; and that ciphertext was addressed to the recipient set that existed when it was sent, so a participant who was not in that set cannot decrypt it — the same membership-epoch boundary [Spec-014 §Cross-Node Artifact Relay (V1)](./014-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1) records for artifacts, and the deliberate posture of group-messaging protocols generally ([MLS RFC 9420](https://www.rfc-editor.org/rfc/rfc9420): new members cannot read pre-join ciphertext). Absent this section a joiner would see an empty timeline. **Peers close the gap by re-publishing**, which is Spec-014's re-publication mechanism generalized from artifacts to the session event stream.

A participant can be outside an event's recipient set for **two independent reasons** under this spec, and they resolve oppositely. The **membership epoch** just described is an accident of when the participant joined — that is the gap this section repairs. **Channel non-membership** (§Per-Channel Recipient Scoping (V1)) is deliberate and permanent: an event scoped to a membership-restricted channel was never addressed to non-members, and backfill **preserves** that rather than repairing it — the entitlement rules below carry the predicate onto the serving side so re-publication cannot become the leak the live path refuses.

**No new transport, no new store.** Backfill rides the established pairwise relay channel as an **application-level payload inside the existing pairwise ciphertext envelope** (§Message Framing frame structure — no new frame message type, no `SessionKeyBundle` change; the relay still forwards opaque ciphertext and learns nothing), exactly as Spec-014's artifact-key attestations do. Sources read their existing per-daemon `session_events` log; the joiner appends into its own. No control-plane table and no daemon-local table is added.

**Trigger and sources: each member's daemon serves the origin-signed rows it holds.** On the joiner's **relay admission** — its posted `SessionKeyBundle` admitted to the session's current recipient set (the member-addition step above), the point from which peers seal live envelopes to it, not the accepted `SessionJoin` alone, since events published in the interval between join acceptance and bundle admission are still addressed to the pre-admission set — the joining daemon issues a `HistoryBackfillRequest` naming the session, and **every current member's daemon answers with the rows for which it holds origin-signed canonical bytes**, serving only a requester already in its live recipient set: because a source answers with its full holdings at answer time (below) and everything it publishes after that moment is addressed to a set that already contains the requester, no row falls between the snapshot and the live stream. That possession bound is forced by the integrity protocol, not chosen by policy: `sequence` is a member of the canonical set ([Spec-006 §Canonical Serialization Rules](./006-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules)), and [ADR-017 §Decision](../decisions/017-shared-event-sourcing-scope.md#decision) has each receiving daemon append relayed events **under its own per-session `sequence`** — so a daemon's received copy of a peer's event is canonically a different row, signed by the receiver, and relayed traffic never yields origin-signed bytes to re-publish. (The possession bound's durable selector is the `received_from_node_id` provenance column the 2026-08-11 [Spec-006 §Canonical Serialization Rules](./006-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules) received-row amendment added to the local [`session_events`](../architecture/schemas/local-sqlite-schema.md#session-events-plan-001-extended-by-plans-006-008-015) shape: `NULL` marks an origin-authored, servable row; non-NULL marks a received, re-signed, unservable one.) Origin-signed bytes exist only where an origin daemon's own log lives: for almost every daemon that is exactly the rows it authored itself, and for a daemon whose member migrated it from a predecessor `NodeId` — its carried-forward store — additionally the predecessor's rows, which it serves as **transport, never authorship**: those rows still verify only under the origin `NodeId`'s roster key, and serving them re-signs nothing. Letting a peer serve its received copies would mean letting it **re-sign** history, and a member that may re-sign may fabricate rows whose `actor` names someone else; refusing that is what keeps attribution meaningful across the seam. Every event has exactly one origin daemon, so the union of origin-signed holdings over reachable members is the joiner's **entitled** history — every row it may hold, and no more, since each source applies the entitlement rules below to what it serves — the same federated gather [ADR-017 §Negative (accepted trade-offs)](../decisions/017-shared-event-sourcing-scope.md#negative-accepted-trade-offs) already prescribes for cross-participant audit, performed by the joiner instead of an operator. No peer is designated and no durable coverage registry exists; each response instead **declares the origin `NodeId`s it serves for** — its own always, a predecessor's only as §Failure honesty below credits it — and those per-response claims are the only coverage bookkeeping V1 keeps.

**A request names the session, not a cursor.** V1 mints no cross-daemon sequence to cursor against ([ADR-017 §Negative (accepted trade-offs)](../decisions/017-shared-event-sourcing-scope.md#negative-accepted-trade-offs)), and a source's own `sequence` does not survive the seam (it is re-assigned on append, above), so the joiner cannot durably name "the span I lack" in any origin's terms. A source therefore answers with its full origin-signed holdings for the session and the joiner discards what it already holds — safe and cheap because append is idempotent on `id` (§Convergence below). The joiner recovers from restart by re-requesting, never by persisting a cursor it could not reconstruct.

**Every joiner has a local daemon; runtime-node attach is not a precondition.** §Required Behavior's join-before-attach rule separates membership from **execution**, not from daemon presence: both V1 client paths reach a session only through their local daemon ([Spec-007 §Purpose](./007-local-ipc-and-daemon-control.md#purpose)), and [ADR-017 §Decision](../decisions/017-shared-event-sourcing-scope.md#decision) gives **each receiving daemon** its own `session_events` log for cross-participant traffic — a member's log, not an executor's. What attach adds is execution capability plus publication of the attaching daemon's **own** signing public key to the roster; neither is needed to request, verify, or append backfill, because the joiner resolves **other** daemons' roster entries to verify and signs its own appended rows with the session-scoped keypair every daemon holds locally ([`daemon_signing_keys`](../architecture/schemas/local-sqlite-schema.md#audit-log-crypto-tables-plan-006) — the degenerate `NodeId` = self arm of the same resolution rule). A joiner that never attaches still **authors**: a member's durable rows do not wait on execution — [Spec-006 §User Message Events](./006-session-event-taxonomy-and-audit-log.md#user-message-events)'s `user.message` is appended by the accepting daemon when it accepts the send, attach or no attach — so a chat-only member's daemon is a genuine origin with history to serve. **Named gap (Codex PR #284 round 3; closed 2026-08-11):** the registration path was attach-bound as specified 2026-08-01–2026-08-11 — the write landed producer-bound to a live attachment row — while [Security Architecture §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature) states the at-join-time registration contract this section's verification depends on, so a never-attached member's origin would have held no roster key, its authored history degrading on the unrostered-origin arm (§Failure honesty below): refused fail-closed by every verifier, named as unverifiable, never silently absorbed. The admission-time registration decoupling — registration keyed on membership admission, with the daemon-held credential as producer binding and no attachment row required ([API Payload Contracts §Signing-Key Registration Method Registry](../architecture/contracts/api-payload-contracts.md#signing-key-registration-method-registry-tier-4-plan-006-t410)) — landed 2026-08-11 via Plan-008's restoring targeted readiness-audit delta jointly with the Plan-006-owned T4.10 registration surface, before backfill ships as this pin required: every member daemon now registers at admission, chat-only members included, and the unrostered-origin arm remains the degrade for a node registered under no roster key (pre-roster software), not a structural gap for unattached members.

**Payload: the origin's bytes, never a re-authored event.** Each `HistoryBackfillChunk` carries, per event, the **originating** daemon's RFC 8785 canonical bytes ([Spec-006 §Canonical Serialization Rules](./006-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules)), that daemon's `daemon_signature` over exactly those bytes, and the origin `NodeId` the signature resolves under. **Re-publication is transport, never authorship: a backfilling daemon never re-signs another daemon's event and never re-canonicalizes what it serves.** A history span routinely exceeds the 64 KB frame ceiling, so chunks MUST be split at the application layer before encryption per §Message Framing; the frame codec is unchanged. Because a response therefore spans multiple chunks — and an entitled-empty one carries none of substance — **completion is declared, never inferred**: the requester mints a per-request correlation identifier on the `HistoryBackfillRequest`, every chunk of the response echoes it and carries its ordinal, and the response terminates in an authenticated terminal marker declaring the total entry count, an empty entitled set answering as a single zero-entry terminal chunk — so "answered" is a checkable property (terminal marker received and every declared ordinal held), a dropped tail leaves the source outstanding rather than silently accepted, and a multi-chunk response is never mistaken for several. The correlation identifier serves completion accounting only, never convergence: deduplication stays keyed on the event `id` alone (§Convergence below).

**Integrity: verify before append.** The joiner MUST verify each backfilled event's `daemon_signature` against the **origin `NodeId`'s** Ed25519 public key resolved from the session participant roster ([Security Architecture §Per-Event Daemon Signature](../architecture/security-architecture.md#per-event-daemon-signature) — the register-once `daemon_signing_public_keys` roster that section already names "peer daemon verifying relayed events" as a consumer of) **before** appending it. This is the verification path a peer daemon already runs on relayed live events; backfill is that path deferred, not a second one. A chunk entry whose signature does not verify is **refused — never appended** — and surfaces `audit_integrity_failed` per [Spec-006 §Integrity Protocol](./006-session-event-taxonomy-and-audit-log.md#integrity-protocol). Re-publication therefore cannot launder tampered history: a peer that edits what it re-publishes produces bytes that fail under the origin's key, and it cannot re-seal them, because it does not hold the origin daemon's session signing key and V1 ships no signing-key rotation ceremony under which a later key could re-sign an old record (the retro-signing attack class [Spec-006 §Integrity Protocol](./006-session-event-taxonomy-and-audit-log.md#integrity-protocol) refuses).

Append then follows [ADR-017](../decisions/017-shared-event-sourcing-scope.md)'s cross-participant receive semantics unchanged — **validate, then append to the local log with the receiving daemon's own per-session `sequence`**, its own `prev_hash` / `row_hash` chain, and its own signature. The origin signature is verification-time evidence, and it is **unretainable** rather than merely unretained: `sequence` sits inside the signed canonical bytes ([Spec-006 §Canonical Serialization Rules](./006-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules)), so re-sequencing yields a different byte string that the origin's key cannot cover, and the local [`session_events`](../architecture/schemas/local-sqlite-schema.md#session-events-plan-001-extended-by-plans-006-008-015) shape carries no foreign-origin signature slot to keep the original in. This one fact is the root of the whole section — it is why a peer cannot re-publish another daemon's rows, why verification happens before append rather than at read time, and why the residual below exists. **Named residual:** once appended, the joiner's chain attests its own _receipt_, not the origin's _authorship_ — precisely the property live relayed events already have, and precisely why cross-participant audit stays federated ([ADR-017 §Negative (accepted trade-offs)](../decisions/017-shared-event-sourcing-scope.md#negative-accepted-trade-offs)). Backfill neither widens nor narrows that residual.

A source that has compacted part of the requested span re-publishes the **audit stub** it holds with that stub's `stub_signature`, verified on the anchor-plus-stub path of [Spec-006 §Post-Compaction Integrity](./006-session-event-taxonomy-and-audit-log.md#post-compaction-integrity). A source never reconstructs a full row it no longer holds.

**Entitlement: the joined session's history the requester may hold, and nothing else.** A source re-publishes only rows whose `session_id` is the session in which the joiner holds active membership. Four exclusions are normative and closed:

- **Sentinel-bound rows are never backfilled.** Daemon-scope and participant-scope events bind to the reserved Max UUID sentinel ([Spec-006 §Daemon-Scope Event Binding And Node-Scope Anchoring](./006-session-event-taxonomy-and-audit-log.md#daemon-scope-event-binding-and-node-scope-anchoring)) precisely because they have no owning session — they are the source daemon's own security posture, event-stream maintenance, and account-level participant history. They are outside every joiner's entitlement by construction, and a backfill selector keyed on "rows in this daemon's log" rather than "rows of this session" would ship them.
- **The `pii_payload` column is never backfilled.** It is excluded from the canonical form by design ([Spec-006 §Canonical Serialization Rules](./006-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules)), so omitting it costs the joiner **nothing** in verifiability — the origin signature verifies over bytes that never contained it. Shipping it, by contrast, would fan a partition sealed under another participant's content key ([Spec-022 §Shred Fan-Out](./022-data-retention-and-gdpr.md#shred-fan-out)) out to a member who holds neither that key nor any part of its erasure path. The signed `pii_ciphertext_digest` and `pii_participant_id` members stay inside the canonical payload, so the joiner's row is explicit about the partition it does not hold rather than silently appearing PII-free. **Named verifier conflict (2026-08-03; closed 2026-08-11):** [Spec-006 §Integrity Protocol](./006-session-event-taxonomy-and-audit-log.md#integrity-protocol)'s fourteenth verification mode `pii_ciphertext_digest_unbound` classifies digest-present-with-`pii_payload`-gone as unbound → `audit_integrity_failed` — and a backfilled PII-bearing row lands in exactly that state on the joiner by this exclusion's own design, as does every **live-relayed** PII-bearing row on its receiving daemon (the same never-held-ciphertext shape — a latent, pre-existing member of the class that this exclusion makes unavoidable to confront). The resolution is a durable received-row provenance marker that origin-scopes the fourth state — ciphertext-gone is an integrity signal only where the ciphertext was ever held, the origin — but that amends the fourteenth mode's four-state matrix in the approved [Spec-006](./006-session-event-taxonomy-and-audit-log.md), so this spec does not restate it; the concrete mechanism — the `received_from_node_id` column with both PII binding modes (the fourteenth and its owner-stamp sibling) origin-scoped at their callers — landed 2026-08-11 as the [Spec-006 §Canonical Serialization Rules](./006-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules) received-row provenance amendment (Spec-006 flip-and-restored `approved` in the same swap), carried by Plan-008's restoring targeted readiness-audit delta's backfill task T-008r-4-14 before backfill ships, as this pin required — a verifier now classifies a received PII-bearing row on the origin-scoped arm, never as tampered.
- **No other session's rows.** Membership in one session entitles a joiner to that session's history only; a source daemon holding several sessions' logs scopes every response by `session_id`.
- **No membership-restricted channel's rows outside that channel.** A source never serves an event scoped to a membership-restricted channel to a requester outside that channel's member set — the serving-side half of §Per-Channel Recipient Scoping (V1), applying the same structural predicate (a `payload`-carried `channelId` resolving to a restricting channel record) at **selection** time rather than at addressing time, because a chunk is addressed to the requester alone and carries no second recipient set to narrow. Since V1's one restricting kind is [Spec-016](./016-multi-agent-channels-and-orchestration.md)'s `direct` channel with an immutable pair, this reduces to: a `direct` channel's events are served only to the two humans in that pair. It is a **fail-closed** selector — a `channelId` the source cannot resolve withholds the row rather than serving it, the same disposition the live path takes and for the same reason. Omitting the row is not a refusal of the request: unentitled rows are silently absent, exactly as sentinel-bound rows and `pii_payload` bytes are, so no new response state or error code is owed.

Within the joined session the entitlement is **role-independent but not membership-independent**: every canonical join mode — `viewer`, `collaborator`, `runtime contributor` ([Spec-002 §Required Behavior](./002-invite-membership-and-presence.md#required-behavior)) — reads the same timeline, so backfill is never narrowed by **role**. The one narrowing that operates inside a session is the fourth exclusion's **channel membership**, which applies identically to every role including the session `owner` — an administrative role in the session is not membership in a `direct` channel, and V1 mints no override that would make it one.

**Convergence.** Repeated deliveries converge because append is idempotent on the event's **canonical identity** — the `id` field, which is both a member of the signed canonical set and the local `session_events` primary key. Because origin-signed holdings are never duplicated across members (§Trigger and sources — an origin's log lives with one member's daemon), two _different_ peers never offer the same event; duplicates come from the retry paths this section requires — a re-request after restart, after a partial failure, or on a peer's presence transition. A source serves one representation per `id` per response — the full row where it still holds one, else the audit stub (above) — and deduplication is plain **first-delivery-wins on `id`**: a delivery whose `id` the joiner already holds is discarded rather than appended, whichever representation either delivery carries, because — the load-bearing direction — **no appended row is ever rewritten**: supersession would rewrite a committed row mid-chain, and the joiner's own `prev_hash` / `row_hash` chain over appended rows (above) forbids exactly that. The compaction race this dissolves rather than tie-breaks: a re-request can race the origin's own compaction, so a pre-compaction full row and a post-compaction stub for the same `id` can both be in flight — but a source never reconstructs a full row it no longer holds (above), so a stub is only ever served after the compaction it records, and whichever representation is appended first stands: a pinned stub is the accurate record of what its source now holds, verifiable on the anchor-plus-stub path (above), and a pinned full row is the richer representation the source held at serve time. Neither outcome supersedes a committed append, and picking one involves no correlation state: the request-scoped correlation identifier (§Payload above) serves completion accounting only, while dedup keys on `id` alone, which the signed canonical bytes already carry.

**Ordering is reconstruction, not canonical read.** The backfilled log is the joiner's own view — the union of what its peers retained **and it was entitled to receive** — and never a ground-truth session timeline; divergent views across participants are an expected property, not a defect ([ADR-017 §Negative (accepted trade-offs)](../decisions/017-shared-event-sourcing-scope.md#negative-accepted-trade-offs)). Consumers ordering backfilled rows against locally-originated ones use wall-clock `occurredAt` plus origin-participant tiebreakers, never the origin's `sequence` — it arrives inside the origin's canonical bytes, but it is that daemon's own log position, comparable only within that log and never the joiner's row order. `run.rolled_back` rows backfill like any other event, so the joiner's projection computes superseded-turn marks itself from the boundary it receives ([Spec-013 §Required Behavior](./013-live-timeline-visibility-and-reasoning-surfaces.md#required-behavior)); backfill mints no second marking channel.

**Failure honesty: coverage is expressed over origins and sources, not over spans.** A joiner cannot enumerate events it has never seen, so "which span is missing" is not a question it can answer — but "which origin's history no source has claimed" is, and it is kept on **two axes**. The **origin axis**: the joiner enumerates the session's origin `NodeId`s from the register-once [`daemon_signing_public_keys` roster](../architecture/security-architecture.md#per-event-daemon-signature) — exactly the set whose rows it could verify at all, though not provably every author: a node that attached under pre-roster software registered no key ([Shared Postgres Schema §Daemon Signing Public Keys (Plan-006 — Verification-Key Roster)](../architecture/schemas/shared-postgres-schema.md#daemon-signing-public-keys-plan-006--verification-key-roster) names that absent-row state its honest degrade), such an origin is invisible to this axis, and any row of its a source served would be refused fail-closed at verification with no roster key to resolve (§Integrity: verify before append), so an unrostered origin's history is unverifiable everywhere rather than silently absorbed, and coverage is a completeness claim over **verifiable** origins only — and each origin is either **claimed** by some answered response (§Trigger and sources — a response declares the origins it serves for) or **unclaimed**. A response's claim over its **own** `NodeId` is credited on answer, empty or not; a claim over any **other** origin — the migrated-predecessor case — is credited only when the response actually carries at least one row or stub verifying under that origin's roster key, because an empty foreign claim is not evidence of possession and crediting it would let one member silently retire another's history from coverage. The **member axis** drives requests and retries: the joiner enumerates the session's **current** members from the membership state returned at join (§Default Behavior) — and only them: the record retains `suspended` and `revoked` rows rather than deleting them ([Shared Postgres Schema §Sessions and Membership (Plan-001, Plan-002)](../architecture/schemas/shared-postgres-schema.md#sessions-and-membership-plan-001-plan-002)), but a departed member's daemon is not a requestable source and never enters this axis — holding it outstanding would pin `pending_backfill` forever on a peer that can never answer — and what a departed member uniquely held is exactly what the origin axis preserves: its origin `NodeId` stays enumerable from the register-once roster and resolves on the unclaimed-origin arms below. Each current member is either an answered source or an outstanding one. While any origin is unclaimed or any source is outstanding the timeline carries the explicit **`pending_backfill`** state **naming them**, surfaced to the client and **never** rendered as an empty or complete history.

**Answered is answered, even when the answer is empty — and answered is a declared, checkable state.** A source is answered when its response's terminal marker has arrived and every declared chunk ordinal is held (§Payload above), never when some chunk merely arrived — so a dropped tail leaves the source outstanding rather than silently accepted. A source whose entitled set for this requester is empty — it authored nothing in the session, or authored only rows the exclusions above withhold — answers as the single zero-entry terminal chunk, is not outstanding, and its **own** origin is credited as claimed. Coverage is a claim that every source **responded** and every verifiable origin found a claimant, never a claim that the joiner holds everything its sources hold; the entitlement narrowings are therefore invisible to coverage by construction, and a `direct` channel a joiner is not in produces no perpetual pending state for the daemons that are. **The one deliberate asymmetry is the empty foreign claim** (§Failure honesty above): a migrated daemon whose predecessor-origin holdings are entirely withheld by the exclusions cannot evidence possession without serving a withheld row — which entitlement forbids — so that predecessor origin stays unclaimed for this requester and resolves on the terminal arm below. That is fail-honest over-reporting: the joiner is told an origin went unserved when what it is owed from that origin may be nothing, and V1 accepts naming too much over either alternative — trusting an unevidenced claim (one member silently retiring another's history) or leaking a withheld row as proof of possession.

The state has two arms, distinguished because they resolve differently. On the member axis an **outstanding current member** — offline, failing, or refusing — is transient: it clears when that peer returns and serves what it holds, and the joiner re-requests on peer presence transitions. On the origin axis an **unclaimed origin** is transient while any current member is still outstanding — the member yet to answer may hold and claim it — and **terminal once every current member has answered without claiming it**: its origin-signed bytes are then held by no reachable member, the departed member whose store was carried nowhere being the canonical instance (above), so that origin stays named until a shared ordered log or an MLS-era group re-publication story lands ([ADR-017 §Alternatives Considered](../decisions/017-shared-event-sourcing-scope.md#alternatives-considered)). Collapsing either arm into a complete-looking timeline would be the defect; naming both is the contract. This is the [Spec-014 §Cross-Node Artifact Relay (V1)](./014-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1) posture applied to history — that section gives a joiner without access the reserved `artifact.no_access_key` state rather than a silent failure, so that clients surface the remedy instead of misreporting.

The typed code `session.history_backfill_unavailable` names the **response-level** failure — a source that received a request and cannot serve it — and so feeds the transient arm only; the joiner's coverage state is `pending_backfill`, never this code, and the terminal arm has no response to carry a code at all. It is **reserved here** and was registered 2026-08-11 in [Error Contracts §Session](../architecture/contracts/error-contracts.md#session) (HTTP 503) by Plan-008's backfill task T-008r-4-14, the OD-008r-1 registration shape.

## Default Behavior

- Session join defaults to direct control-plane API and event-stream attachment.
- Relay is used only when required by topology or reachability constraints.
- The control plane returns session metadata, membership state, and live replay cursors as part of successful join.
- Peer history backfill starts automatically on relay admission: once the joiner's `SessionKeyBundle` is admitted to the session's recipient set following the accepted join, the joiner requests, and each current member's daemon serves the origin-signed rows it holds **that the requester is entitled to** (§Peer History Backfill On Join (V1)). The control plane does not participate beyond membership and presence — it holds no session events to serve.
- Relay fan-out defaults to the session's current recipient set. An event scoped to a membership-restricted channel is narrowed to that channel's members instead (§Per-Channel Recipient Scoping (V1)); no channel opts in, since the narrowing follows from the channel's kind, and a channel restricting no membership — including the bootstrap `main` channel — is never narrowed.

## Fallback Behavior

- If the control plane is unavailable, existing `local-only` sessions remain usable on their local nodes, but new shared-session join and invite actions must fail explicitly.
- If relay setup fails, the join remains valid but remote live connectivity may remain degraded until an alternate path succeeds.
- If a client switches connectivity path while within the reconnect grace window, the same participant presence should be re-associated rather than duplicated when possible.
- If any source has not answered a backfill request — a current member offline, failing, refusing, or whose response never completed (no terminal marker, or a declared ordinal missing) — or any roster origin remains unclaimed by the answers received, the joiner surfaces the explicit `pending_backfill` state naming them and re-requests as peers return, never an empty timeline presented as a complete one; a member who has left the session surfaces here through its unclaimed origin, never as an outstanding source. A departed member's origin stays named permanently in V1 once every current member has answered without claiming it, since origin-signed copies of its rows then exist on no reachable daemon (§Peer History Backfill On Join (V1)).
- If a backfilled event fails verification against its originating daemon's roster-resolved key, it is refused rather than appended, and the failure surfaces as `audit_integrity_failed`; the joiner continues requesting the remaining span from other peers.
- If a source withholds rows because the requester is outside a membership-restricted channel, that is **not** a degraded state: the rows are silently absent, the source counts as answered even when it serves nothing, and no `pending_backfill` entry, error code, or client-visible gap marker is produced (§Peer History Backfill On Join (V1)). Surfacing the withholding would disclose the channel's traffic pattern to exactly the participant the scoping excludes. The one corner where a `pending_backfill` entry coexists with withholding is the empty foreign claim (§Peer History Backfill On Join (V1)): a predecessor origin whose holdings are entirely withheld stays named as unclaimed, but the entry is **cause-opaque** — the joiner cannot distinguish it from an uncarried store or a permanently offline member, so no traffic pattern is disclosed.
- If an origin daemon cannot resolve the channel a publishable event binds to, it refuses the publication rather than falling back to the unscoped session recipient set (§Per-Channel Recipient Scoping (V1)) — a producer invariant violation surfaced as a local failure, never a wider fan-out.

## Interfaces And Contracts

- `SessionJoin` must require authenticated identity and valid membership or invite acceptance.
- `RelayNegotiation` must return only the information needed to establish remote session connectivity.
- `PresenceRegister` must exist independently of runtime-node attach.
- `SessionResumeAfterReconnect` must accept a prior participant or client identity handle where applicable.
- `HistoryBackfillRequest` must name the session — never a cross-daemon span, which V1 defines no sequence for — and must carry no authority beyond the requester's own active membership: a source authorizes on the requester's own membership — in the named session for the response as a whole, and additionally in each membership-restricted channel whose rows it would otherwise include — never on the request's self-description. The request gains no channel selector: scoping is applied by the source to what it serves, not requested by the joiner. It carries a requester-minted correlation identifier that the response's chunks echo for completion accounting (§Peer History Backfill On Join (V1)); the identifier confers no authority and never keys deduplication.
- `HistoryBackfillChunk` must carry, per event, the origin daemon's canonical bytes, that daemon's `daemon_signature` over them, and the origin `NodeId`, split under the §Message Framing frame ceiling. It must carry only events for which the responding daemon holds **origin-signed** canonical bytes — its own authored rows, plus a predecessor `NodeId`'s rows where its member's store was carried forward — and a response must declare the origin `NodeId`s it serves for; it must never carry re-signed or re-canonicalized events, sentinel-bound rows, `pii_payload` bytes, rows from any session other than the requested one, or rows scoped to a membership-restricted channel the requester is not a member of (§Peer History Backfill On Join (V1)). Each chunk must echo the request's correlation identifier and carry its ordinal, and each response must terminate in an authenticated terminal marker declaring the response's total entry count — an empty entitled set answers as a single zero-entry terminal chunk — so completion is declared on the wire rather than inferred from silence.
- Relay message publication must derive its per-recipient envelope set from the published event itself: the session's current recipient set, intersected with the channel's member set when the event's `payload` channel binding resolves to a membership-restricted channel (§Per-Channel Recipient Scoping (V1)). This adds no wire method, no frame message type, and no envelope member — it constrains which envelopes a sender produces, leaving the frame codec, the relay, and the receiving path unchanged.
- Both backfill payload types are typed in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) rather than in this spec — landed 2026-08-11 by Plan-008's backfill task T-008r-4-14 as `HistoryBackfillRequest` / `HistoryBackfillEntry` / `HistoryBackfillChunk` (relay application payloads inside the pairwise ciphertext envelope; no method registration on either transport) — the same registration shape their companion `session.history_backfill_unavailable` code takes in [Error Contracts §Session](../architecture/contracts/error-contracts.md#session), registered the same day.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- Control-plane join emits membership and presence events into session history.
- Relay negotiation state may be ephemeral, but successful join and presence changes must be durably represented.
- Control-plane metadata must not become the local source of truth for run execution state.
- Peer history backfill adds **no store**: a source reads its existing per-daemon `session_events` log — whose `received_from_node_id` provenance column (the 2026-08-11 [Spec-006 §Canonical Serialization Rules](./006-session-event-taxonomy-and-audit-log.md#canonical-serialization-rules) amendment; a column on the existing log, not a new store) is the durable serving selector — and the joiner appends into its own with its own sequence and hash chain ([ADR-017](../decisions/017-shared-event-sourcing-scope.md)), stamping that column on each backfill-appended row exactly as on a live-relayed one. Backfill coverage — which sources have answered and which roster origins remain unclaimed under `pending_backfill` — is derived in-session state, not a durable table: a restarting joiner re-requests and discards by `id` rather than resuming a persisted cursor, which is why no cursor column is owed (§Peer History Backfill On Join (V1)).
- Per-channel recipient scoping adds **no store and no column**: both its inputs — the channel kind and a `direct` channel's immutable member pair — are already durable on the channel record and event-carried ([Spec-016 §State And Data Implications](./016-multi-agent-channels-and-orchestration.md#state-and-data-implications)), and the derived recipient set is per-publication, held only for the fan-out that produced it (§Per-Channel Recipient Scoping (V1)). Because the inputs are event-carried, a daemon rebuilding projection from its log derives the same recipient set it derived live, so replay cannot widen a past narrowing.

## Example Flows

- `Example: A participant accepts an invite, authenticates to the control plane, joins a live session, and reads the existing timeline before deciding whether to attach a runtime node.`
- `Example: A participant loses direct connectivity and falls back to relay coordination while remaining in the same session and retaining the same membership.`
- `Example: A colleague accepts an invite mid-session and joins; on its relay admission their daemon requests history backfill, each current member re-publishes the origin-signed rows it holds that the joiner is entitled to, the joiner verifies every event against its originating daemon's roster-resolved key, appends the union under its own sequence, and renders the recovered timeline — which omits, by design, the events of any direct channel the joiner is not a member of.`
- `Example: A participant joins while every peer daemon is offline; the timeline shows an explicit pending-backfill state naming every unanswered source rather than an empty history, and fills in as each peer reconnects and serves the origin-signed rows it holds that the joiner may hold.`
- `Example: Two humans open a direct channel in a five-participant session; each message there is sealed only to that pair, so the other three participants' daemons never receive the ciphertext and a later joiner is never served it — while neither human's own agents see the content either, which is the daemon's separate audience obligation rather than an effect of the encryption.`

## Implementation Notes

- Join and relay should be separate sub-protocols. Joining a session is a membership action; relay is a connectivity action.
- Control-plane session join responses should be small and replay-oriented, not giant state dumps.
- Presence should be resilient to brief network path flips.

## Pitfalls To Avoid

- Treating relay connectivity as proof of execution authority
- Binding session identity to a specific transport path
- Making runtime-node attach a prerequisite for reading or discussing in a session

## Acceptance Criteria

- [ ] A participant can authenticate and join a live session without restarting active runs.
- [ ] Switching between direct and relay connectivity does not create a second session identity.
- [ ] Control-plane services never become the execution authority for local repo and tool actions.
- [ ] A participant joining a live session recovers its **entitled** prior history from its peers, with every backfilled event served from origin-signed bytes and verified against its **originating** daemon's roster-resolved key before append; sentinel-bound rows, `pii_payload` bytes, and events of a membership-restricted channel the requester is not a member of never present in any chunk; and an explicit pending-backfill state naming every unanswered source — the source axis holding the session's **current** members only, a departed member never enumerable as a source while its events stay covered on the roster-origin axis — and every unclaimed roster origin, where **answered** is the declared completion state (the source's terminal entry-count marker received and every declared chunk ordinal held): a source serving zero **entitled** rows answers with a single zero-entry terminal chunk, while a response missing its terminal marker or any declared ordinal leaves its source unanswered — never a silently empty timeline.
- [ ] An event scoped to a membership-restricted channel reaches that channel's members and no one else: a session participant outside the channel receives no envelope for it on the live path and is served none of it on backfill, while a member receives and is served it normally.

## Resolved Questions and V1 Scope Decisions

- No blocking open questions remain for v1.
- V1 decision: direct control-plane connectivity is required for admin and join-establishment flows. Relay is a secondary connectivity path for session participation after direct control-plane join succeeds.
- V1 decision (2026-08-03): late-joiner history is backfilled by **peers**, never by the control plane. [ADR-017](../decisions/017-shared-event-sourcing-scope.md) Option B leaves the control plane with no session events to serve and the zero-knowledge relay with no plaintext, so peer re-publication is not one option among several — it is the only one V1's trust model admits. The mechanism is the [Spec-014 §Cross-Node Artifact Relay (V1)](./014-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1) membership-epoch re-publication shape generalized to the event stream (§Peer History Backfill On Join (V1)); it adds no transport, no frame message type, and no table. The degraded state's typed code `session.history_backfill_unavailable` is reserved here and registered in [Error Contracts](../architecture/contracts/error-contracts.md) by Plan-008's backfill task — the OD-008r-1 registration shape, not minted in this spec.
- V1 decision (2026-08-03): **a daemon backfills only origin-signed rows — its own authored rows, plus a predecessor `NodeId`'s where its member's store was carried forward — never a re-signed received copy.** Re-sequencing on append puts `sequence` — a signed canonical member — outside the origin's signature, so a relayed copy is re-signed by its receiver and unservable, and admitting re-signed copies would let any member author history attributed to another participant; possession of origin-signed bytes is therefore the serving capability, and verification always resolves the origin `NodeId`'s roster key. The accepted cost is recorded in §Peer History Backfill On Join (V1): an origin whose origin-signed bytes no reachable member holds does not recover in V1 and stays `pending_backfill` rather than being rendered as complete. Closing it needs the shared ordered log ([ADR-017 §Alternatives Considered](../decisions/017-shared-event-sourcing-scope.md#alternatives-considered)) or an MLS-era group re-publication story — both V1.1.
- V1 decision (2026-08-03): **per-channel recipient scoping is defined here, and it keys on channel membership rather than on audience.** [Spec-016 §Resolved Questions and V1 Scope Decisions](./016-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions) (D-016-21) names the property as a dependency it consumes; this spec supplies it (§Per-Channel Recipient Scoping (V1)). An event scoped to a membership-restricted channel — V1's one such kind is the `direct` two-human channel, whose member pair is immutable — is sealed to that channel's member set intersected with the session's current recipient set, and is never served on backfill to a requester outside that set. The predicate is **structural** (a `payload`-carried `channelId` resolving to a restricting channel record) rather than an enumerated event-type list, so a later taxonomy addition cannot fall outside it silently, and an unresolvable binding fails **closed** on both paths — refusing publication on the live path, withholding the row on the serving path. It composes with the membership epoch as a further narrowing rather than a replacement, and mints no transport, frame message type, envelope member, table, or error code. **Its limit is deliberate and named**: it bounds which _daemons_ hold the plaintext and does not enforce agent exclusion, which remains [Spec-016](./016-multi-agent-channels-and-orchestration.md)'s daemon obligation at agent-context assembly — on a `humans-only` channel that is not `direct`, membership is session-wide and that obligation is the entire mechanism. A second named limit is the **artifact key path**: this event-envelope predicate does not govern [Spec-014 §Cross-Node Artifact Relay (V1)](./014-artifacts-files-and-attachments.md#cross-node-artifact-relay-v1)'s content-key wrapping, which fans an artifact's key to the session-wide attested set with no channel narrowing — so V1 refuses artifact sharing into a membership-restricted channel outright, fail-closed at the publish path ([Spec-016 §Interfaces And Contracts](./016-multi-agent-channels-and-orchestration.md#interfaces-and-contracts)'s `direct`-channel rule), and a durable artifact-channel binding with member-intersected key wrapping is the named V1.1 extension.
- V1 non-goal (2026-08-03): a joiner's backfilled log is **not** a canonical session timeline, and V1 mints no cross-daemon canonical ordering for it. Replay stays reconstruction per [ADR-017 §Negative (accepted trade-offs)](../decisions/017-shared-event-sourcing-scope.md#negative-accepted-trade-offs); a single ordered cross-participant history rides that ADR's Option A V1.1 candidate, gated on the [ADR-010](../decisions/010-paseto-webauthn-mls-auth.md) MLS promotion gates. Retaining the origin daemon's signature on a backfilled row — so a joiner's own log carries origin-authorship evidence rather than receipt evidence — is likewise deferred: it needs a foreign-origin signature slot the V1 local schema does not have.
