## Purpose

Define the lifecycle of worktrees and the execution modes available for repo-bound runs.

## Scope

This spec covers `read-only`, `branch`, `worktree`, and `ephemeral clone` execution modes plus worktree creation, reuse, and retirement.

## Non-Goals

- PR preparation details
- Merge policy
- Diff artifact rendering

## Required Behavior

- Every repo-bound run must bind to exactly one canonical execution mode: `read-only`, `branch`, `worktree`, or `ephemeral clone`.
- Repo-bound coding runs must default to `worktree` execution mode when the repository supports worktrees.
- `read-only` mode must prohibit repo mutation and support inspection, review, and diagnostic tasks.
- `branch` mode must be an explicit writable override that uses an existing checkout with explicit branch context.
- Starting a writable worktree-mode run must create or reuse a valid worktree before execution begins.
- `ephemeral clone` mode must provision a disposable isolated clone before writable execution begins.
- The system must not silently fall back from intended worktree mode to mutating the main checkout.
- The system must not silently substitute one canonical execution mode for another when the requested mode is unavailable.
- Worktree lifecycle must support `creating`, `ready`, `dirty`, `merged`, `retired`, and `failed`.
- Reusing an existing worktree must be explicit and must preserve branch and provenance context.

## Default Behavior

- Default branch naming pattern is `sidekicks/<session-short-id>/<task-slug>`.
- Default writable coding runs use one dedicated worktree per active task or branch context.
- `branch` mode and `ephemeral clone` mode are explicit selections or policy-driven overrides, not hidden defaults.
- Worktree retirement defaults to preserving metadata and artifacts even when filesystem cleanup later removes the checkout.
- Worktree or ephemeral-clone preparation must not automatically execute repository setup scripts in v1. This includes repository-controlled git hooks: provisioning git invocations must neutralize hook execution at the invocation layer (e.g. an empty `core.hooksPath`), so cloning or adding a worktree on a hostile repository executes no repository-controlled code.

## Fallback Behavior

- If a repo does not support worktrees, the system may offer `ephemeral clone` or explicit `branch` mode where safe, but it must mark the selected mode distinctly from normal worktree mode.
- If worktree creation fails, the run must remain blocked in setup rather than mutating the main checkout.
- If ephemeral clone preparation fails, the run must remain blocked in setup unless an operator or participant explicitly selects a different execution mode.
- "Blocked in setup" is a concrete run disposition: the run parks in the `starting` state with the typed preparation error surfaced; no `running` transition fires, the failure never silently mutates any checkout, and the parked run remains interruptible (cancel applies to `starting` runs, transitioning them to `interrupted`).
- If an intended reuse candidate is dirty or incompatible with the requested branch strategy, the system must require explicit user choice.
- Explicit reuse choice is candidate-anchored: the caller names the reuse candidate, and consent to bind a dirty candidate is a separate explicit acknowledgement — a candidate that becomes dirty between check and bind is refused rather than silently bound; a candidate incompatible with the requested branch strategy is never bindable.
- Preparing an execution root against a `stale` workspace must be refused with the typed stale error until the workspace is repaired (write-gate posture per Spec-009).
- When a repo mount detaches or an owning workspace archives, dependent non-terminal worktrees and ephemeral clones are retired by the daemon's asynchronous cleanup sweep — retirement is recorded and evented with metadata preserved; disk removal follows asynchronously. Retiring the clone backing a live `ephemeral clone`-mode workspace's current root returns that workspace to `provisioning` (awaiting the next per-run prepare); `stale` is reserved for fault paths (`Spec-009 §Ephemeral Clone Lifecycle`).
- If a repository requires setup commands before useful execution, v1 must surface them as explicit follow-on actions or workflow steps rather than hidden execution-root side effects.

## Interfaces And Contracts

- `ExecutionModeSelect` must distinguish `read-only`, `branch`, `worktree`, and `ephemeral clone`. Selection records the canonical mode and transitions the workspace; it does not materialize per-task execution roots — materialization is `ExecutionRootPrepare`'s surface (read-only resolves synchronously at select; an explicit mode switch is exactly one selection mutation, never a client-sequenced select-then-prepare chain).
- `ExecutionRootPrepare` must create or bind the execution root required by the selected mode before a run enters `running`. Explicit worktree reuse rides this interface by naming the candidate worktree.
- `WorktreeReuseCheck` must report branch, cleanliness, and compatibility.
- `EphemeralClonePrepare` must report clone root, lifecycle, and cleanup policy.
- `EphemeralCloneDispose` must support explicit disposal of a prepared clone (the `manual` cleanup-policy arm and operator-driven cleanup).
- `WorktreeRetire` must record retirement even if filesystem deletion happens asynchronously.
- `WorktreeStatusRead` must expose the session's worktree and ephemeral-clone records — lifecycle state, branch, cleanup bookkeeping, and provenance — as a daemon-owned read surface.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- Worktree records must persist branch name, owning repo mount, lifecycle state, and provenance to the creating session and run.
- Execution mode must be stored as run setup data: the daemon persists a per-run execution binding (run → workspace, mode, execution root, and any worktree / ephemeral clone / branch context involved) that survives the run for provenance.
- Branch context must be persisted for writable `branch`, `worktree`, and `ephemeral clone` runs. The branch-context record is a polymorphic carrier: worktree-mode rows reference the worktree, ephemeral-clone rows reference the clone, and branch-mode rows reference neither (the main checkout carries no Plan-010 root row).
- Dirty and merged state belong to daemon-owned workspace projections.
- A workspace whose execution root is handed to an active run is `busy` for the run's duration (one holding run at a time in V1); concurrent root handoff is refused with a typed busy error, and the workspace returns to `ready` when the holding run reaches a terminal state.
- Daemon-provisioned execution roots (worktrees and ephemeral clones) live under the daemon's own execution-roots directory, never inside the attached repository checkout; they are inside the session's trust envelope by construction (`Spec-009 §Local Trust Envelope (V1 Definition)`).

## Turn-Boundary Snapshots

At each turn boundary of a writable-mode run — turn completion is first-class via the `completionKind` carve on `run.completed` ([Spec-006 §Run Lifecycle](006-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle), campaign B1) — the daemon records the worktree's project state as a snapshot ref (campaign B21). This is the mechanism the run time-travel file-restore leg consumes (the `rollback` intervention — [Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior), campaign B2 — under [ADR-017](../decisions/017-shared-event-sourcing-scope.md)'s forward `run.rolled_back` ruling).

- **Scope:** tracked **and** untracked files; ignored **untracked** paths are deliberately excluded on both the capture and restore legs — ignore rules govern untracked files only, so a tracked file that happens to match `.gitignore` is captured and restored like any other tracked file (tracking wins over ignoring, git's own semantics) — and "ignored" means **project-declared** rules only: the in-tree `.gitignore` files, themselves captured by the snapshot. Host-local ignore sources — `core.excludesFile` (user/global config) and `$GIT_DIR/info/exclude` — are deliberately never consulted on either leg: a developer's private ignore patterns are not project declarations, and an untracked project file matching one is still project state that must survive snapshot/restore on every host (empirically confirmed on git 2.50.1: `git add -A` under a global exclude pattern or an `info/exclude` entry silently omits matching untracked files — exactly why the Capture bullet's staging pipeline is plumbing with explicit exclusion flags, not porcelain). The capture pipeline's `--exclude-per-directory=.gitignore` skips ignored untracked paths, and the restore's untracked-delete pass (same flag; ignored paths are never deletion candidates) preserves them on disk — with one deliberate exception: an ignored untracked path that **collides** with a path tracked in the snapshot (a tracked file deleted during the turn and replaced by ignored content at the same path) is overwritten when `git read-tree --reset -u` re-materializes the snapshot's tracked content there — the removal happens on the read-tree leg ([git-read-tree](https://git-scm.com/docs/git-read-tree): `-u` updates working-tree files with the reset result), out of the delete pass's ignored-path-preserving reach. Restore wins by design — re-materializing snapshot-tracked content is the operation's purpose — and the restore result enumerates every overwritten colliding path, so the loss is observable, never silent. **Colliding** is three measured shapes rather than the exact-path case alone, because `read-tree --reset -u` replaces a whole obstructing file or directory rather than merging around it (each shape measured on git 2.50.1, the checkout exiting 0 while taking the ignored content with it): the snapshot tracks a file **at** the ignored path; an ancestor of the ignored path is a snapshot-tracked **file**, so the directory beneath it is removed whole; or the ignored path is an ancestor **directory** of a snapshot-tracked path, so the ignored file sitting there is unlinked to make room. In every shape the enumerated path is the **ignored** one — the content being destroyed, never the snapshot path that displaced it — ancestry is tested segment-wise (`foo` collides with `foo/a`, never with `foobar/a`), and a sibling never collides (ignored `foo/b` beside snapshot-tracked `foo/a` shares a directory the checkout merely populates). An ignored **embedded repository**, which the untracked listing spells with a trailing slash, is enumerated under its slash-stripped name through the first two shapes only: a directory is destroyed only by a file at or above its path, and is merged into with its payload and its `.git` intact when the snapshot holds only paths beneath it. A snapshot `160000` gitlink writes no file bytes, so the first two shapes never fire at a gitlink path, but the checkout does need a directory at that path and along the way to it, so the third shape enumerates an ignored **file** unlinked at a gitlink's own path or at an ancestor of one. Two dispositions therefore ride the divergence enumeration rather than the collision one, both measured: an ignored **directory** at a gitlink's path is not destroyed at all (the checkout leaves it, its payload and its `.git` untouched, so there is no overwrite to report — a divergent embedded `HEAD` there surfaces as a divergent gitlink, and an agreeing one is reported nowhere because nothing moved), and ignored content merely **beneath** a materialized gitlink directory is neither enumerated nor deleted — the checkout's side of the same submodule boundary the untracked-delete pass meets from its listing. The per-shape measurements are recorded once at the daemon service's prospective-effects derivation site rather than restated here. **Submodule boundary:** snapshots operate at the superproject's gitlink level — the captured tree records each submodule's then-current commit OID (a `160000` gitlink entry, exactly what porcelain staging would record), and neither capture nor restore descends into submodule worktrees: a submodule is its own repository whose files never enter the superproject index, so interior modified/untracked state is outside the snapshot/restore contract (empirically confirmed on git 2.50.1: interior dirty and untracked files survive a restore untouched, and the superproject's untracked listing never reports them), the restore pins `-c submodule.recurse=false` so host config cannot widen the operation across that boundary, and the restore result enumerates each submodule path whose gitlink diverges from the snapshot — a turn that moved a submodule's HEAD is reported, never silently half-restored. Scoped to non-colliding superproject paths, the guarantee stands: rollback never deletes derived state the project itself declares disposable (build artifacts, caches, `node_modules`), and per-turn snapshots never churn the object store with artifact trees. The files/conversation coherence guarantee therefore covers project-declared superproject state (tracked + non-ignored untracked) only.

The closing `git update-ref --no-deref refs/sidekicks/runs/<runId>/epoch-<E>/turn-<N> <snapshot-commit> ""` is **create-only**: the trailing empty `<old-value>` is a compare-and-swap against ref absence (git refuses with `reference already exists` — empirically confirmed on git 2.50.1), so a retried or duplicated capture of the same run/epoch/turn can never repoint an existing snapshot ref at later file state — the first successful write wins, and a capture retry that finds the ref already written treats it as idempotent success, returning the recorded OID (idempotence is per-epoch: a post-rollback execution's identical ordinal mints a fresh ref under its own `epoch-<E>` segment — the Ref namespace bullet below). `--no-deref` is part of that spelling rather than decoration: git splits an update of a **symbolic** ref into an update of its referent and carries the must-not-exist check there with it, so an unflagged create against a dangling in-namespace symref plants an arbitrary branch at the snapshot commit and reports success (empirically confirmed on git 2.50.1) — flagged, the write acts on the validated name itself and nothing outside the namespace moves. The same flag rides the retention prune's per-ref delete for the mirror reason: an unflagged `update-ref -d` resolves its compare-and-swap **through** a planted symref and deletes the branch it points at, exiting 0 and reporting a clean prune (likewise confirmed). Both directions of that channel are therefore closed by the same flag, and neither guard substitutes for the other — the unflagged create mints a branch outside the namespace, the unflagged delete destroys one. The out-of-worktree temp index also keeps snapshots from self-capturing index files — a worktree-resident scratch index would surface to the capture pipeline's `ls-files -o` listing, the restore's untracked-delete pass, and `git status` as stray untracked content (the restore legs always operate on the real index, which lives under `.git/` outside the worktree).
- **Ref namespace:** snapshot commits land under `refs/sidekicks/runs/<runId>/epoch-<E>/turn-<N>` — **never on `refs/heads/`** — so snapshots are invisible to branch history, PR preparation, and diff attribution by construction. `<E>` is the run's **execution epoch** ([Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior), campaign B2 — `0` before any rollback, advanced with each **accepted `run.rolled_back`** — a confirmed conversation rewind, a position-mismatch rewind confirmed at the recorded floor and the same-position recovery's convergence no-op included — regardless of the file-leg disposition, while an outcome with no confirmed rewind leaves it unchanged): same-run resurrection re-uses position ordinals, so a post-rollback re-execution's `turn-<N>` capture must mint a **new** ref rather than hit the superseded epoch's create-only ref and silently resolve to the wrong tree — the create-only duplicate-capture idempotence below is therefore **per-epoch**. Restore target resolution walks the current lineage: a rollback to position `P` resolves the snapshot from the newest epoch whose recorded range contains `P`, an epoch inheriting the prefix at or below its rewind base from its parent epoch (implementation: the campaign's Plan-010 bundle). [Spec-011](011-gitflow-pr-and-diff-attribution.md) is explicitly unaffected: its commits remain agent/user-authored and reviewable; no Spec-011 surface changes.
- **Restore:** `git -c core.autocrlf=false -c core.eol=lf -c submodule.recurse=false -c core.attributesFile=/dev/null read-tree --reset -u <verified-snapshot-OID>` (with `GIT_ATTR_NOSYSTEM=1` in the environment — the same conversion pins as capture: a host `core.autocrlf=true` would smudge LF blobs to CRLF worktree bytes on checkout, and a user/system attributes file (`*.txt eol=crlf`) reaches the same smudge path through the attribute machinery, restoring different bytes than were captured, while in-tree `.gitattributes` — a project declaration inside the restored tree — stays deliberately honored, so attribute-affected paths restore to git-canonical worktree form; `core.eol=lf` pins **which** line ending that smudge path writes for an in-tree `text` path, and the `core.autocrlf` pin is what makes it load-bearing — a host `core.autocrlf=true` writes CRLF whatever `core.eol` says, and only under the pin does the checkout follow `core.eol` at all, at which point an unpinned host `core.eol=crlf` restores CRLF for content captured as LF (all measured on git 2.50.1); `lf` rather than `native`, because `native` is the host's own answer by definition and would restore CRLF on Windows for LF-captured bytes, and the check-in leg deliberately omits the knob because staging under either value produces the identical tree OID (the `text` attribute's clean filter normalizes on the way in regardless); the recurse pin keeps a host `submodule.recurse=true` from carrying the checkout across the Scope bullet's submodule boundary; and `<verified-snapshot-OID>` is the operand deliberately: this leg is issued against the **snapshot commit OID that target resolution verified**, never against a mutable ref name re-read at application time, so the object the precondition was checked against and the tree-ish actually applied can never be two different commits — the OID spelling upholds this row's requirement, which is about which tree lands in the worktree, more exactly than a name does) **followed by an untracked-delete pass on the same pinned exclusion pipeline as capture** — `git ls-files -o --exclude-per-directory=.gitignore -z` lists post-snapshot untracked content honoring in-tree `.gitignore` rules only (host ignore sources cannot shield post-snapshot files from deletion, symmetric with capture, which never consulted them either); the daemon unlinks each listed file, recursively removes entries reported with a trailing slash (directories git does not descend into — e.g. a nested repository the turn created; `ls-files -o` reports such a directory as `nested/`, empirically confirmed, the same class `clean -ffd`'s second `-f` existed for), and prunes directories the deletions empty — a bare checkout-from-ref leaves post-snapshot files on disk (empirically confirmed), recreating exactly the files/conversation incoherence rollback exists to prevent — **with the delete pass repeated to a fixpoint (re-run until a pass deletes nothing)**: the untracked listing honors ignore rules that post-snapshot untracked ignore files themselves supply, so a turn-created untracked `.gitignore` ignoring a turn-created directory shields that directory through the very pass that deletes the `.gitignore`, leaving the directory behind as non-ignored post-snapshot content — a single pass is insufficient (empirically confirmed on the pinned listing itself: pass one removes only the `.gitignore`, pass two removes the un-hidden directory; termination is guaranteed because every non-final pass strictly shrinks the untracked set and deleting files never adds ignore rules). **Skipped embedded repositories are exempt from that pass.** The restore reads the snapshot commit's `Skipped-Embedded-Repositories:` trailer back before mutating anything — failing closed on an undecodable trailer at the enumeration-derivation step, ahead of every write — and exempts each recorded path and its subtree, matched at segment boundaries, from deletion. Without the exemption the pass destroys exactly what capture could not record: the snapshot tree holds no entry at a skipped path, so the listing reads it as post-snapshot content and the trailing-slash rule removes the repository recursively (empirically confirmed for both skip classes). Both fixpoint termination checks operate on the **deletable** subset for the same reason — a check over the raw listing would never converge while a preserved repository keeps reappearing in it. An embedded repository the turn **created** is absent from the trailer and is still deleted, which is the contract rather than an exception to it: the discriminator is capture-time knowledge, not what sits on disk at restore time. The preserved set is reported on the restore's diagnostic channel rather than on the restore result, whose shape is frozen for the rollback consumer ([Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior)). The fixpoint cannot over-delete: at delete time the index still holds the snapshot tree — tracked **and** captured-untracked files, their `.gitignore`s included — so every snapshot file is index-tracked and only post-snapshot untracked content is ever a deletion candidate, with snapshot-declared ignored paths (`node_modules`, build artifacts) protected in every pass — **closed by `git read-tree --reset <verified-HEAD-OID>` (index-only, no `-u`)**: the `-u` leg leaves the real index at the snapshot tree, so every captured-untracked file would otherwise surface as a staged addition against `HEAD`; resetting the index back to `HEAD` returns those files to untracked status and tracked edits to ordinary unstaged modifications, worktree bytes untouched (empirically confirmed — no fabricated staged intent survives a restore). `<verified-HEAD-OID>` is the operand here for the same check-then-act reason as the destructive leg: the literal name would let the precondition check and this command see different commits if `HEAD` moved between them, and naming the OID the check verified removes that window — a closer satisfaction of this row's own requirement, which is about where the index lands, not about which spelling reaches it. **Object-interpretation legs additionally pin `-c core.useReplaceRefs=false`.** A hostile or leftover `refs/replace/<oid>` substitutes one object for another transparently, so an unpinned read of a recorded id — the destructive checkout, the delete pass's snapshot-tree listing, the lineage parent read, the trailer read, the capture's index seed — resolves **through** the replacement while every precondition still passes on the unreplaced ids (empirically confirmed on git 2.50.1: the listing enumerates the substituted tree's paths and the checkout writes its bytes, exit 0). The pin is scoped to legs that interpret an object **id**, never to ref **resolution**: ref reads and the `HEAD` observation are measured unaffected, and the closing index reset deliberately **honors** the setting instead, because porcelain is redirected identically there — pinning it would leave the index disagreeing with what every other git command in that worktree calls `HEAD`, surfacing as fabricated staged modifications, the precise failure the reset exists to prevent. Restore additionally carries a **fail-closed precondition**: the current `HEAD` must equal the resolved snapshot commit's recorded first parent (`<verified-snapshot-OID>^` — pinned by the capture recipe's `-p <base>`; the check and the checkout name the same object by construction). If branch history has advanced past the snapshot — a reviewed [Spec-011](011-gitflow-pr-and-diff-attribution.md) commit/push action landing after that turn, or any other commit reaching the execution root — the restore is refused with a typed refusal rather than applied: reading the older snapshot tree against the newer `HEAD` would leave the later commit in branch history while anti-diffing its files into the worktree as unstaged modifications — fabricated edit intent of exactly the kind the index-reset leg exists to prevent. Rewinding or reverting branch commits is deliberately outside this recipe: committed history is Spec-011's reviewable surface. **Ruling recorded (campaign B2, [Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior)):** the standing refusal is the contract — Spec-004 validates this precondition pre-dispatch, and a refusal **rejects the whole rollback intervention with no leg applied** (neither conversation nor files move; rewind/revert of post-snapshot commits stays outside the contract), and the precondition check plus restore run under **exclusive tenancy of the execution root** — a terminal-source rollback first re-acquires the root through the single-holder handoff above (the terminal exit had returned the workspace to `ready`), and a root `busy` under another run refuses the whole intervention identically, per the same Spec-004 contract. File restore is available exactly while `HEAD` is unmoved since capture, never a silent partial restore; a mid-flight `HEAD` advance discovered at restore time (after a confirmed conversation rollback) surfaces as a `degraded` intervention outcome naming the partial state, per the same Spec-004 ruling. A mid-sequence restore failure is likewise a **distinct disposition** — `files-partially-restored`, naming the failed command and carrying the **same two never-silent enumerations as a completed restore** (overwritten colliding ignored paths; divergent submodule gitlinks), covering **every effect applied before the failure — the failing command's own partial writes included**: `read-tree -u` updates the working tree as it applies, not transactionally, so a `read-tree` failing on a later path (a required smudge filter erroring there) has already overwritten an earlier colliding ignored path — empirically confirmed on git 2.50.1, exit 128 with the collision overwrite on disk — required and empty-when-none — and empty on two distinct readings, so **both empty never means nothing was mutated**: a failure before any mutation carries both empty, and so does a failure after a checkout that rewrote the whole worktree, whenever the snapshot tree held no colliding ignored path and no gitlink at all; the two enumerations are effect **classes**, not a census of everything the sequence touched, and the failed step is what names how far it got — never collapsed into files-unrestored: the sequence mutates incrementally, so a late failure leaves earlier effects on disk, and hiding that would mask file loss or fabricated staged state; the sequence is **convergent by construction** — every command drives toward the declarative snapshot-tree target, so re-running the `read-tree --reset -u` leg, the fixpoint delete, and the index close is safe — though convergence is a property of the **commands**, not a promise that recovery always succeeds: a fresh rollback re-enters through the same non-mutating target resolution, and two shapes are terminal there, an index-close failure reached under a `HEAD` that has since moved (the fail-closed precondition refuses from then on) and any failed step whose snapshot ref the retention prune has since removed (resolution refuses it as absent, with no OID left to freeze); recovery is otherwise a fresh rollback to the same target re-running the restore to its fixpoint, and the run retains its exclusive root hold across the partial state — a half-restored tree is never released to another holder, per the same Spec-004 ruling. **Target resolution freezes the target.** Resolution records the snapshot's commit **OID** and every mutating leg downstream names that OID, so a retention prune deleting the snapshot ref **inside** the resolve→application window cannot starve the checkout: the commit object outlives its last name until `gc` reclaims it, and the restore completes normally. The split is two-sided and deliberate — a prune landing **before** resolution draws the ordinary typed refusal with nothing applied; one landing **after** it applies the correct tree — and it composes into a third shape worth stating: the deletion costs nothing until some unrelated step fails, at which point that partial restore is terminal for its target, because the fresh rollback's resolution now finds no ref. The ref named on a restore result is therefore a correlation handle, not a live one.
- **Retention:** snapshot refs prune when the run's retention window closes (terminal state + the configured window); the prune task lives with the run-retention owner. In `ephemeral clone` mode the refs live in the clone's own object store, so they additionally share the clone's disposal lifecycle (the configurable TTL below) — disposal is not a retention violation; there is no clone left to restore into. The interaction with post-terminal rollback belonged to the campaign's rollback legs (the Spec-004 rollback-semantics bundle and [Plan-010](../plans/010-worktree-lifecycle-and-execution-modes.md)'s file-restore leg): an `on_run_complete` cleanup disposes the clone — and with it these refs — while the run's rollback retention may still be open, so the open question was whether clone disposal defers to the rollback-retention window, the refs relocate outside the disposable clone, or a disposed-clone run's rollback proceeds conversation-only. **Ruling recorded (campaign B2, [Spec-004 §Required Behavior](004-queue-steer-pause-resume.md#required-behavior)):** disposal is not deferred and refs do not relocate — a disposed clone takes its snapshot refs with it, and any later rollback of that run proceeds **conversation-only** with the file-leg disposition recorded on the intervention outcome; file restore is available exactly as long as the clone is.
- **Applicability:** `worktree`, `branch`, and `ephemeral clone` writable modes (`ephemeral clone` subject to the Retention bullet's disposal interaction — snapshot refs share the clone's lifecycle, so file restore ends at clone disposal); `read-only` runs snapshot nothing. In `branch` mode the execution root is the shared main checkout, so a restore operates on that shared checkout — its post-snapshot untracked (non-ignored) files are discarded like any other rollback effect; branch mode's deliberately coarser isolation applies to restore exactly as it does to execution.

## Example Flows

- `Example: A user starts an implementation run. The daemon creates a dedicated worktree, binds the run to it, and only then starts provider execution.`
- `Example: A reviewer opens the repo in read-only mode, inspects diffs, and cannot accidentally mutate the checkout.`
- `Example: A repository cannot use worktrees safely, so a participant explicitly selects ephemeral clone mode and the daemon prepares a disposable clone for the writable run.`
- `Example: A later follow-up run explicitly reuses the same worktree because it targets the same branch and task lineage.`

## Implementation Notes

- Branch-name defaults should be deterministic and human-readable, but collision handling must be explicit.
- Worktree reuse is valuable, but the system should bias toward isolation over convenience.
- `branch` mode remains important for special maintenance tasks, but it must stay clearly non-default for mutable coding work.
- Repository bootstrap or setup commands should be modeled as explicit approved work, not as an implicit part of worktree creation.

## Pitfalls To Avoid

- Mutating the main checkout as a hidden fallback
- Treating worktree reuse as implicit magic
- Losing run provenance when a worktree is later retired

## Acceptance Criteria

- [ ] A writable coding run on a git repo defaults to worktree mode.
- [ ] The execution-mode contract distinguishes `read-only`, `branch`, `worktree`, and `ephemeral clone`.
- [ ] Worktree creation failure blocks the run instead of mutating the main checkout.
- [ ] Reused worktrees remain explicitly linked to branch and prior run context.
