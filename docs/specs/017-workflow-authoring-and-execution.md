## Purpose

Define how reusable workflows are authored, versioned, and executed inside sessions. V1 ships the full workflow engine: four phase types (`single-agent`, `multi-agent`, `automated`, `human`), four gate types, parallel phase execution with named resource pools, and durable state with append-only hash-chained approval history. The engine plugs into existing daemon primitives (Spec-016 channels, Spec-012 approvals, Spec-014 artifacts, Spec-006 events, Spec-015 recovery) — workflow execution does not duplicate them.

## Scope

This spec covers:

- Workflow authoring as YAML definitions + typed TypeScript SDK (no bespoke DSL per C-1)
- Workflow versioning (immutable-by-version with content-hash identity)
- Phase execution for all four phase types
- Workflow-level gates (four gate types)
- Parallel phase execution with named resource pools and bounded iteration
- Append-only hash-chained approval history (C-13 / I7)
- Workflow event taxonomy (new Spec-006 categories + event types)
- Durable phase state persisted via Spec-015 (SQLite + WAL)
- Replay-determinism contract
- Visual node-graph authoring of workflow definitions, and the canonical file form definitions export to and import from (§Visual Workflow Builder)

## Non-Goals

- General-purpose external workflow engines (no Temporal, Restate, Argo binding at V1)
- Marketplace or distribution semantics for workflow templates — publishing, importing from outside the daemon, or any cross-machine sync of definitions. Narrowed 2026-08-10 (Tier-8 audit) rather than deleted: the ratified `shared` scope value adds daemon-local cross-project **reuse**, which is a visibility breadth, not distribution. A `shared` definition never leaves the daemon that stores it, so this Non-Goal stands with its subject stated precisely. Definition portability between machines at V1 is therefore the operator-driven file form of §Definition file form — export and import (C-17) — a file an operator moves, never a service that moves it.
- Pixel-level UI design for the workflow editor. V1 ships the visual builder surface specified in §Visual Workflow Builder — its node taxonomy, port and connection rules, refusal set, layout-persistence tier, and scope semantics are normative here; visual styling, theming, and interaction polish beyond those rules stay out of the spec and are implementation choices. (Amended 2026-08-10, Tier-8 audit: the prior bullet scoped out "full UI design for workflow editors" wholesale, which the visual-builder amendment contradicts.)
- `BIND` multi-phase channel reuse — criterion-gated V1.1 commitment per [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments). V1 ships `ownership: OWN` only; `BIND` lands only if three named criteria are satisfied (see Interfaces And Contracts §Multi-agent).
- Default timeout for `human` phase — required typed opt-in in V1 per BL-097 D1. Default-timeout + escalate-to-paging deferred to V1.x under notification-routing criterion per `ADR-015 §V1.1 Criterion-Gated Commitments`.
- **Cross-run campaign memory and durable wake-coalescing delivery — criterion-gated V1.1 (deferred 2026-08-16).** V1 ships the _fold_: §Provider-limit pacing and durable resumption (SA-40) groups concurrently parked runs by their park's provider-account attention key, so one provider-account outage presents as one attention record rather than one per parked run. V1 does **not** ship the durable delivery-settlement substrate that fold could be built into — a per-watcher generation record with a claim / queue / deliver compare-and-set lifecycle, crash-time claim reclamation across daemon restart, and campaign-scoped memory carrying attention state across separate runs of the same recurring workflow. The V1 fold is a grouping over the run aggregate's own projection state and crosses no aggregate boundary; the deferred substrate is durable cross-run state with its own lifecycle, which is a different thing wearing the same word. Until all three criteria below hold, V1's honest behavior is the fold plus the per-run park cause of §Park integrity and cancellability (SA-42) — every parked run stays individually visible and individually resumable, and nothing claims to have notified anyone. Three named criteria gate the V1.1 ship decision and all three must hold; this is a criterion-gated commitment, not an intention:
  - **Criterion 1 — an outbound delivery channel exists to settle against.** Notification routing ships (the same gate `ADR-015 §V1.1 Criterion-Gated Commitments` already names for the `human`-phase default timeout). A delivery-settlement protocol is unbuildable while there is no delivery to settle: at V1 the attention record is read from a surface, never pushed to one, so "delivered" has no observable moment.
  - **Criterion 2 — a measured insufficiency of the V1 fold.** At least three recorded occasions in a 30-day rolling window where one provider-account outage parked five or more runs **and** the single V1 attention record was observed insufficient, in that an operator inspected the parked runs individually rather than acting on the record. The two halves are evidenced differently, and stating which is which is part of the criterion. The **scale half** is machine-derivable: §Engine event record (SA-43) captures every park with its attention key and correlation keys, so counting outages that parked five or more runs is a read over records V1 already writes. The **insufficiency half** is an operator-attested finding, not a derived one — SA-43 records engine decisions, never client reads, and V1 mints no operator control surface whose usage could be observed (the recorded residual of §Park integrity and cancellability (SA-42)) — so evaluating it means recording the attestation when the occasion happens, not building observation machinery beforehand.
  - **Criterion 3 — a written cross-run ownership contract.** The substrate spans runs and outlives any one of them, so before it ships a contract must name the watcher identity a generation keys on, the exact edge that advances a generation, the crash-reclaim rule, and which plan owns the durable rows — the four questions the V1 fold does not have to answer because it never leaves the run. Absent that contract, cross-run coalescing state has no one-writer owner, which `cross-plan-dependencies.md` §2 forbids.
- Daemon-side draft autosave for `human` phase forms — V1 ships with client-side localStorage / IndexedDB only (SA-28 / Pass G §10.3). Daemon-side form-state table ships empty at V1.
- Cross-phase discussion channels (V2): agents from different phases collaborating in shared channels.
- OpenTelemetry workflow semantic conventions — OTel GenAI semconv is not yet ratified as of 2026-04-22 ([OpenTelemetry GenAI Observability Blog 2025](https://opentelemetry.io/blog/2025/ai-agent-observability/)); V1 ships on CloudEvents + Spec-006 envelope and adopts OTel semconv additively when ratified under [ADR-018](../decisions/018-cross-version-compatibility.md) MINOR rules.
- SQLite STRICT tables adoption (criterion-gated V1.x deferral per Wave 2 §4.1 — cross-plan policy change; Plan-017 schema uses repo's existing TEXT-column convention).
- Mutation testing in CI (criterion-gated V1.x deferral per Wave 2 §4.2 — V1 PR budget already at 30 min).
- Execution-model enum (`local | queued | remote`) — C-11 commitment is local-only at V1 (Airflow executors and n8n `own` mode precedent: every system that enumerated execution models at V1 had to break-remove entries later).

## Required Behavior

### Authoring + versioning

- Workflows must be authored as explicit phase definitions with stable ids and versioned structure.
- Workflow authoring format: YAML definitions + typed TypeScript SDK. **No bespoke DSL** (no CUE, no HCL, no custom expression language) — C-1 commitment. DSL lock-in cost is precedent-heavy: Dagger maintained its CUE SDK as primary authoring language from Jan 2022 (v0.1.0) through Dec 2023, then ended CUE SDK support after a year of dual-maintenance against multi-language SDKs, citing that "engineers...want to write code in a language they already know. Learning a brand new language, however powerful, is simply not what they're looking for" ([Dagger — Ending Support for the Dagger CUE SDK, 2023](https://dagger.io/blog/ending-cue-support/); [Solomon Hykes on Changelog #550, 2023](https://changelog.com/podcast/550)); GitHub Actions migrated off HCL to YAML under breaking-change pressure ([GitHub Actions HCL→YAML deprecation, 2019](https://github.blog/changelog/2019-09-17-github-actions-will-stop-running-workflows-written-in-hcl/)).
- Workflow definition files must carry an explicit schema version marker (e.g., `ai-sidekicks-schema: 1.0`). Daemon must support compat mode for reading older-marker files (SA-14 / C-8 — Temporal's Version Sets → Build IDs retrofit is the precedent cost avoided here).
- Workflow definitions must be stored as first-class durable definition and version records. Artifact publication may represent workflow exports or summaries, but it must not be the canonical source of workflow definition truth.
- `WorkflowDefinitionCreate` must run a DFS three-color cycle check against the phase graph and reject invalid definitions with a typed error. Graph stays acyclic at definition time; `go-back-to` is a state-reset operation, not a cyclic edge. The graph the check runs over is the one the definition declares: the per-phase `dependsOn` predecessor lists when the definition carries them, the phase array's sequential chain when every phase omits them (§Graph model — nodes, ports, and edges (SA-32)).

### Execution semantics

- V1 ships all four phase types: `single-agent`, `multi-agent`, `automated`, `human`.
- V1 ships all four gate types: `auto-continue`, `quality-checks`, `human-approval`, `done`.
- V1 ships parallel phase execution with named per-resource-pool backpressure (SA-3). The executor tick loop uses a Kahn-style ready-set admission over the phase DAG; ready-set processing bounded by `max_concurrent_phases` (daemon-global default 4) as final backstop.
- Iteration must be bounded by three counters:
  - Per-phase `max_retries` (default 3).
  - Workflow-run-level `max_phase_transitions` (default 100) — hard-fails the run with `failure_reason='RUN_ITERATION_LIMIT'` (SA-1; G §10.6 resolved).
  - Workflow-run wall-clock `max_duration` (default 24h) — hard-fails run on deadline (SA-2).
- Resource pools for V1 (SA-3):
  - `pty_slots` — capacity `min(8, cpu_count * 2)`, tunable per daemon config.
  - `agent_memory_mb` — capacity `daemon_budget - overhead ≈ 192 MB`; per-`single-agent` phase default reservation 100 MB (pessimistic). Tripwire: >15% phase-launch attempts blocked on `agent_memory_mb` in a 2-week rolling window triggers V1.1 calibration.
  - Pull-based admission in executor tick.
- `PhaseResourceNeed` model on phase definition: `{pool: string, amount: number}[]`. Multiple pool reservations must all be available at admit time.
- Parallel execution must specify `ParallelJoinPolicy` (SA-4): `'fail-fast' | 'all-settled' | 'any-success'`. Default `fail-fast`. Sibling cancellation on `fail-fast` must be recorded at a deterministic synchronous tick checkpoint — never in async callbacks (prevents the non-determinism class documented in Temporal Java SDK #902).
- `priority?: number` on phase definition drives ready-set ordering; FIFO tiebreaker (SA-5). Airflow-style priority weight deferred to V1.1 if tripwire warrants.
- All phase execution routes through existing `OrchestrationRunCreate` per Spec-016/017 constraints.
- A workflow phase may create runs, request approvals, emit artifacts, or block on participant input.
- Workflow execution must remain visible in the session timeline and must preserve per-phase provenance.
- Phase outputs must be durable, addressable after workflow completion, **and immutable once written** (SA-16 / C-9). Accumulator patterns build on top (e.g., a `collect` phase reads N upstream outputs and emits a new output). Retry creates a new phase-run identity and a new output row — never overwrites. The GitHub Actions Artifact v3→v4 mutability-forced migration is the precedent ([GitHub Actions — v3 artifact deprecation notice, 2024-04-16](https://github.blog/changelog/2024-04-16-deprecation-notice-v3-of-the-artifact-actions/)).
- Workflow execution must be resumable after daemon restart or client reconnect.

### Provider-limit pacing and durable resumption (SA-40)

Added 2026-08-16 (workflow-hardening amendment). A provider account that has spent its usage allowance refuses work. V1 treats that refusal as a **first-class park** — neither an execution failure nor a transient to be retried — because retrying into a spent account converts one refusal into a burned retry budget and then a false `failed` verdict on work the engine never got to try.

**C-19 — recognition is typed, and only typed.** The engine recognizes a usage-limit refusal from the driver's **normalized typed signal alone**. It MUST NOT recognize one from message text, provider prose, an error string, a rate-limit window's name, or a model id. Text-matching a refusal is forbidden for the reason Spec-005 gives for the driver boundary generally: prose is not a contract, it changes without a version bump, and a matcher that silently stops matching turns a park into a burned retry ladder with no signal that anything changed.

Three facts about the shipped driver surface fix what "typed" means here, and the third is a gap this amendment declares rather than fills.

- **The precedent for typed recognition.** [Spec-005 §Fallback Behavior](005-provider-driver-contract-and-capabilities.md#fallback-behavior) establishes the class: recovery conditions form a closed `RecoveryCondition` set whose `reauth-required` member is detected "mid-run via the provider's typed auth-failure signals", never by reading a message. A usage-limit refusal is the same class of fact — a provider-account state the driver observes and normalizes — and is recognized the same way.
- **The stamping discipline the carrier must follow, which is not the same as the field it stamps.** [Spec-005 §Interfaces And Contracts](005-provider-driver-contract-and-capabilities.md#interfaces-and-contracts) binds normalization at the driver boundary: the driver stamps `windowSource` (`provider_reported | model_default | estimated`) and computes the `exceeded` headroom predicate at normalization, "never deferring provenance or the derived predicate to consumers." This amendment adopts that **discipline** — provenance is stamped where the fact is normalized, never inferred by a consumer — and deliberately does **not** reuse that field. `windowSource` is the provenance of a **context-window headroom** reading ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)); a spent usage allowance is a different fact, and a context-window provenance stamp says nothing about whether a quota reset boundary is real.
- **The carrier does not yet exist, and this spec does not mint it.** No shipped surface carries a typed usage-limit refusal: `RecoveryCondition` is closed at `recovery-needed | reauth-required` and no registered driver error code names one. Spec-017 therefore **requires** the signal and states what it must carry — a closed-set cause identifying the refusal as a spent usage allowance, and, where the provider reported one, a reset boundary carrying its own provenance stamp on the `windowSource` model — while leaving the type's name and declaration site to Spec-005 and Plan-005, which own the driver vocabulary (one-writer). The shape must be a **sibling axis, not a widening of `RecoveryCondition`**: [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) already refused that widening once, minting `RecoverySpanClassification` beside `RecoveryCondition` because "the two axes answer different questions, and conflating them would overload operator-remediation routing." A usage-limit park needs no operator at all, so folding it into a set whose every member means _a human must act_ would misroute all of them.

**What the engine deliberately does not consume.** The account-plane `usage.rate_limit_update` snapshot — payload `{provider, providerAccountId, credentialGeneration, limitId?, windowMins, usedPercent, resetsAt?}`, keyed `(providerAccountId, limitId)` (erratum corrected 2026-08-26: this restatement was written before the 2026-08-18 account re-key and the 2026-08-26 per-limit re-key and had carried the pre-account shape; the sentence's point is unaffected, since what the engine declines to consume is the snapshot, not any particular member of it) — is the nearest existing surface and is **not** an input to any rule in this section. [Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) scopes it as "a display/quota surface only, kept off the security/admission plane"; its `resetsAt` carries no provenance stamp; and its own consumer obligations are staleness defenses that resolve **fail-open to the freshest reading**. Arming an execution schedule off a display surface that is licensed to be stale and stamps no provenance would be precisely the guess the arming rule below refuses to make. It stays what it is: a quota display.

**The carrier landed 2026-08-18; this section is reachable.** The typed provider usage-limit signal this section depends on is minted at [Spec-005 §Fallback Behavior](005-provider-driver-contract-and-capabilities.md#fallback-behavior) as a sibling axis beside `RecoveryCondition` — typed-only recognition, a closed-set cause, an optional provenance-stamped reset boundary — so the park, the schedule, and the attention fold activate together as specified. What does **not** change is the prohibition that accompanied the wait: a provider or shape the driver cannot name emits no signal, that silence means _not known to be limited_ rather than _known not to be limited_, and it is never closed by reading message text. The supply cadence the carrier will ride is already fixed: [Spec-005 §Resolved Questions and V1 Scope Decisions](005-provider-driver-contract-and-capabilities.md#resolved-questions-and-v1-scope-decisions)'s bounded 15-minute per-runtime-node refresh with optional provider push (the Codex `account/rateLimits/updated` push alongside the `account/rateLimits/read` pull), and correctness here does not depend on the push arm.

**A recognized refusal parks immediately, and spends no ladder.** The phase suspends on the refusal itself. The park:

- consumes **no** `max_retries` attempt and mints **no** new `phaseRunId` — a park is not an attempt, and the resumed turn is the same attempt continuing;
- increments **no** `max_phase_transitions` counter — no phase boundary was crossed;
- happens **even when no reset window was reported**. A missing window changes only whether a schedule is armed (below); it never changes whether the run parks, and it never licenses one more attempt "to see". The refusal is itself the proof.

`max_duration` is the one bound a park does not stop: SA-2 defines it as workflow-run **wall-clock**, and a park is elapsed time. The deadline therefore stays authoritative over every rule below.

**A durable resume schedule, armed only where a boundary is real.** Where the typed refusal carries a reset boundary whose own provenance the driver stamped **provider-reported**, the engine arms `autoResumeAt` — a **durable value on the parked phase's persisted state, never an in-memory timeout** — and the run resumes itself when the window opens. The value is per-phase, not per-run: parallel branches of one run may park concurrently against different provider accounts with different reset boundaries (§Graph model — nodes, ports, and edges (SA-32)), and a single run-level schedule could hold only one of them — delaying or stranding the sibling. Where that provenance is the driver's default or its estimate, or where no boundary was reported at all, **no schedule is armed**: those values are the driver's honest admission that the number is a guess, and scheduling against a guess either fires into a still-spent account or holds a run that could have run. The gate is not invented here — [Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) already fixes the rule for the whole corpus: estimated- and default-grade readings drive only reversible, soft responses, while "any costly or irreversible action keyed on headroom" requires provider-reported provenance. Holding a run asleep against a wall-clock instant is such an action. A parked run with no schedule is a normal, fully-visible, fully-resumable park — not a stuck one (§Park integrity and cancellability (SA-42)).

The schedule obeys five rules:

1. **Jitter is derived and scaled, never modular.** The armed instant is the reported boundary plus a jitter offset spanning a bounded window (V1: 0–120 seconds), computed by **scaling** a fixed-width prefix of the run's own derived digest across that span — `offset = span × prefix / 2^width` — so a wave of runs parked by one outage does not resume in a thundering herd. A modulus is forbidden: when the span exceeds the operand's range the modulus never wraps, so the spread silently collapses to a fraction of its declared width while every bound assertion still passes. The offset is a pure function of `workflowRunId`, so §Deterministic identity (SA-21) replay reproduces the same instant and the projection rebuild reconstructs the same row.
2. **The armed instant — and the park's attention key, where one was computed — are carried by the suspension event.** The engine writes both into the event payload before it is projected, so the durable columns are a function of the log and §Truth vs projection vs ephemeral (SA-25)'s rebuild-from-events rule holds without a special case.
3. **The deadline wins.** A schedule that would fall at or after the run's `max_duration` deadline is **not armed at all**; the run parks unscheduled and hard-fails at its deadline with `failure_reason` preserved, per §Fallback Behavior. The boot sweep applies the same rule, so a restart never resurrects a run past its deadline.
4. **Restart re-arms; it never fires inline.** On daemon start the sweep re-arms every schedule from its durable row **after** projection rebuild completes, and a past-due instant is re-armed at a short bounded delay rather than fired during rebuild — a timer that races the rebuild is deciding what the run is while the answer is still being computed. A durable value the sweep cannot decode is **quarantined, never fatal**: the run is left parked and unscheduled — a normal, fully resumable state — and the undecodable value is recorded in §Engine event record (SA-43) rather than raised as a wiring error. An engine that refuses to boot, or that parks every run at a configuration fault, because one row it wrote itself is no longer decodable has converted a single bad row into a total outage.
5. **Every exit clears it.** Every transition out of the park — the phase resuming, or the run being cancelled, failing, or completing — clears the parked phase's durable value and any armed timer, in the same unit of work as the transition. A cleared schedule is unarmed, not merely ignored.

**Firing re-checks, and an early resume is safe.** When the schedule fires, the engine re-checks that the run is still parked and still resumable, then makes a **real provider attempt**. If the account is still limited, the attempt receives another typed refusal and the run re-parks honestly against whatever boundary is now in force. Resuming too early therefore costs exactly one refused attempt and converges on the true unblock; it can never leave a run unrunnable.

**A fire that does not move the run is not an exit.** Rule 5's clear is keyed on the run _transitioning out of the park_, not on the timer having fired. Where a fire re-checks and then fails to transition the run — the engine is shutting down, the phase cannot be re-dispatched yet, the write loses a race — the durable value **stays armed** and re-arms at a bounded delay. Clearing on a fire that did not move the run is the worst available outcome: the run is left parked with its only route forward deleted, and nothing has recorded that it is stranded.

**One attention record per outage, and it is never an availability lock.** A single spent account can refuse many concurrently running workflows at once. Each affected run parks independently, on its own state, with its own cause — but the engine stamps each park with an **attention key** identifying the outage rather than the run: the provider, the account identity, and the credential generation held stable across the refusing dispatch. Runs sharing an attention key present as **one** attention record, so a wide refusal storm surfaces once rather than once per run. Three constraints keep this a fold rather than a mechanism:

- **A mixed failure is never folded.** A set of concurrently failed siblings collapses into one usage-limit attention record only if every one of them carries the same non-null attention key. Folding a genuine non-usage failure behind a familiar outage would make the only record an operator sees actively misleading — the "protection that isn't" class §Loud-errors discipline (C-12) forbids.
- **The record never gates anything.** Starting, resuming, retrying, and firing a schedule MUST NOT consult it, and it MUST NOT interrupt work already running. It is a correlation for presentation, not a lock on availability: a credential rotation or a quiet reset must never be able to leave a run unstartable because a record says an account was once spent. Any transition back to running invalidates a not-yet-surfaced record for that key, so a later refusal surfaces again rather than being suppressed by a stale one.
- **The fold fails open, and only toward more noise.** Where the correlation cannot be computed — the key is unavailable, the read fails, the account identity is ambiguous — the affected run surfaces **its own** attention record rather than none, and the refusal never reverts to a retry. Duplicated notifications are a cost. A refusal quietly rehabilitated into one more attempt against a spent account, or a park nobody is told about, are failures — so the only direction the fold is permitted to fail in is the loud one.

Durable cross-run memory of attention state — a per-watcher generation with a claim / deliver settlement lifecycle, its crash-reclaim rule, and campaign-scoped carry-over between separate runs — is explicitly **not** V1 (§Non-Goals, criterion-gated V1.1).

### Frozen-definition repair (SA-41)

Added 2026-08-16 (workflow-hardening amendment). §Fallback Behavior freezes a running instance on the version it started with, which is correct and load-bearing for replay — and which means a run parked against a defect in its own frozen definition has no route forward: the definition has been fixed, the run cannot see the fix, and the only remaining action is to abandon it and lose every completed phase output.

V1 therefore provides one governed repair: **an operator resuming a parked run may re-pin it to the definition's current version**, as an explicit, separately-requested action on the resume. The repair is bounded by six rules:

- **Explicit, never implicit.** Re-pinning happens only when the resuming operator asks for it by name. An ordinary resume always continues on the pinned version, unchanged. No timer, no schedule, no automatic recovery path ever re-pins — auto-resumption (SA-40) resumes the frozen version and nothing else.
- **Only while parked.** A running instance is never re-pinned. The frozen-version rule of §Fallback Behavior is unconditional for a run that is executing.
- **Only where no attempt of the run is in flight.** Parked is necessary but not sufficient. A re-pin takes effect only where the resume's next act is to **enter a phase fresh** — and, because the pin is run-level, only where **no other non-terminal phase of the run holds an in-flight attempt either**: parallel branches park independently (§Graph model — nodes, ports, and edges (SA-32)), and a parked sibling mid-attempt will continue that attempt later, so a re-pin admitted through one branch's fresh entry would still swap the definition under the sibling's already-dispatched work. Requested on a park whose resume **continues an in-flight attempt**, or while any parked sibling holds one, it is refused, loudly and typed, naming the blocking attempt and the explicit fresh-entry action that would discard it. The two arms are **one refusal point, not two**: the predicate is single — _some attempt of the run is still in flight_ — evaluated run-wide, and which phase holds the attempt changes what the refusal names, never what it is; the A-017-15 census counts it once, the same one-failure treatment the version-accountability rule below gives its two detection arms. The usage-limit park of §Provider-limit pacing and durable resumption (SA-40) is exactly the in-flight case by construction — it mints no new `phaseRunId` and its resumed turn is the same attempt continuing — so a bare re-pin there is always refused. Swapping the definition under an attempt whose work was already dispatched from the frozen bytes is incoherent rather than merely risky: the in-flight units were launched from a version the run would no longer be pinned to, so neither those units' inputs nor the outputs they return could be explained by the version the run's own record names. Refusing is the honest form of the boundary — quietly continuing on the frozen version would repair nothing while reporting success, and quietly re-pinning mid-attempt is the unreadable-history failure the audit rule below forbids. And the failure mode is concrete: an operator who fixes a parked phase's prompt and resumes expects the fix to have taken effect — absent this explicit boundary, the run re-renders the frozen prompt into an identical park with nothing telling the operator why, as many times as they retry.
- **Audited, in the log.** The repair is recorded as an additive-optional member on the `workflow.resumed` payload naming the version the run left and the version it joined — an additive MINOR payload bump under [ADR-018](../decisions/018-cross-version-compatibility.md), the same discipline the SA-26 dual anchor rides. No new event type is minted, and the projected run row stays a function of the log per §Truth vs projection vs ephemeral (SA-25). A silent re-pin is forbidden outright: it would make a run's own history unreadable, since the definition its early phases executed would no longer be recoverable from the run.
- **Completed work is preserved, never re-run.** Phase outputs are immutable (SA-16) and a repair rewrites none of them. The repair mints no new attempt for a completed phase and resets no counter — `max_retries`, `max_phase_transitions`, and the `max_duration` deadline all carry over exactly as they stood.
- **Refused when it would strand the run's own record.** The re-pin is refused, loudly and typed, when the target version does not contain every phase id whose outputs the run already holds, or when the target version's declared topology would leave a completed phase unreachable. Both are the same failure: a run whose record names phases its definition no longer contains cannot be replayed, verified, or explained. Refusal leaves the run parked and unchanged, on its original pinned version.

### Park integrity and cancellability (SA-42)

Added 2026-08-16 (workflow-hardening amendment). Two properties make a park a state an operator can act on rather than a hole a run falls into.

**Every park carries a bounded, engine-authored cause.** A suspended phase records a typed `parkReason` and a human-readable `parkCause`:

- `parkReason` is a closed union — at V1, `waiting-human` (the existing §Session timeline surfacing value) and `provider-usage-limited` (SA-40). Widening it is an additive MINOR bump under [ADR-018](../decisions/018-cross-version-compatibility.md) and moves the domain-lockstep pin, never a comment.
- `parkCause` is the engine's own sentence about why this run is waiting and, where a schedule is armed, **the instant it holds** — so the time named in the cause and the time in the durable schedule are one value read from one place, not two values that can drift.
- The cause is **bounded at 8 KiB, truncated at a UTF-8 code-point boundary with a visible truncation marker**. A durable, operator-facing, engine-authored string with no bound is an unbounded write on the projection tier.
- All four park fields — the two record fields here and SA-40's armed instant and attention key — are carried by the suspension event's payload and projected from it, so §Truth vs projection vs ephemeral (SA-25)'s byte-equal rebuild holds.
- The cause is **never** written into a phase output, an artifact, or an agent-visible context. Engine prose delivered through a model-output channel is read as something a model said, which makes the engine's own diagnosis indistinguishable from generated content — and phase outputs are immutable truth (SA-16), so an engine sentence written there is unretractable.

**A parked run is always cancellable.** Cancellation is a legal transition into the `cancelled` run status from **every** suspended or waiting state, without precondition and without waiting for anything:

- It is **pure bookkeeping and therefore cannot block**. A parked run holds no resource-pool reservation (pool state is ephemeral and re-requested — §Truth vs projection vs ephemeral (SA-25)) and no live phase process, so there is nothing to drain, interrupt, or wait on. A cancel that could be refused, queued, or made to wait for a provider window would reintroduce exactly the stuck state this rule exists to remove.
- It **clears the durable resume schedule** in the same unit of work, so a cancelled run can never be resurrected by a timer armed before it was cancelled.
- It **preserves the record**. The parked phase-state row's state, its `parkReason`, its `parkCause`, and every completed phase output survive cancellation untouched — they are the account of why a human was asked and what the run had achieved, and losing them at cancel would make cancelling the operation that destroys the evidence. The phase's **live** fields — the armed instant and the attention key — are instead cleared by the same cancel per SA-40 rule 5: record and live state sit on one row and part ways at exactly this boundary.

**Recorded residual — closed 2026-08-18.** V1 ships the rules above as engine state-machine rules, and the operator control surface that invokes them is now minted, as the separate deliberate contract addition this paragraph called for. The gate it named, [BL-151](../archive/backlog-archive.md), is `completed`; §Operator run control (SA-45) below is the landed surface, and §Park surfacing on the read model (SA-44) is what makes the state it acts on legible. The structural constraint this paragraph fixed in advance held exactly as written: the operation set and the run-cancelled lifecycle event minted **together**, because a durable cancellation the log cannot reconstruct would break §Truth vs projection vs ephemeral (SA-25) — a projection rebuild would replay the last `workflow.phase_suspended` payload, restore its schedule and attention key, and resurrect a run the operator cancelled. The auto-resume path of SA-40 was never part of the residual: it is engine-internal and needs no wire producer. What moved at the closure, and nothing else: the wire registry eleven → **thirteen** rows and §Event types (SA-19) 23 → **24** types across the same five categories. The nine-table schema is unchanged — the four park columns and the `cancelled` run status the surface reads and writes have been on disk since the workflow-hardening amendment.

### Park surfacing on the read model (SA-44)

A parked phase MUST be renderable from **one** `workflow.runRead` response — no timeline replay, no second call, no client-side reconstruction from event history. The park is the state an operator is most likely to be looking at and least able to explain from a status word alone, so the read model carries its reason rather than deferring to the log.

- **Four members, additive-optional.** `PhaseState` carries `parkReason`, `parkCause`, `autoResumeAt`, and `parkAttentionKey`, mirroring the four per-phase park columns. All four are additive-OPTIONAL per [ADR-018](../decisions/018-cross-version-compatibility.md) on an already-published shape; readers MUST tolerate their absence, which is also what an older daemon emits.
- **Live, not record — the rule that makes them readable.** The projection **columns** are a durable record that survives resume and cancellation (SA-42's preserve-the-record rule depends on exactly that). The wire **members** are a live view of it: a daemon emits them for precisely those phases parked at the moment the response is built, and emits none of them for a phase that is not — including a phase that parked earlier in the run and has since resumed, whose columns still hold the record. The wire therefore gives a stronger guarantee than the columns do, deliberately.
- **`parkReason` is the wire discriminator.** Because emission is live-scoped, its presence means _this phase is parked now_ and its absence means _it is not_. `parkCause` is present whenever `parkReason` is — SA-42 requires a parked phase to always carry one. `autoResumeAt` and `parkAttentionKey` are present only where the park armed them (an SA-40 park whose provider reported a reset boundary); their absence **narrows** the park to the unscheduled, operator-resumable kind rather than denying it.
- **The phase-run status union is NOT widened.** `PhaseState.state` stays the five values of §Phase-Type and Gate-Type Taxonomy. This is the reason the liveness rule is required rather than convenient: the coarse union carries no `suspended` arm, so a reader given only column mirrors could not separate a phase still waiting on a human form from one that already resumed past that wait. Widening the union instead would move the domain-lockstep pin, the conformance row that checks it, and every reader switching on five values — a breaking-shaped change to avoid a problem one producer rule solves.
- **Per-phase, never per-run.** SA-32 branches park independently against different provider accounts, so a run-level park field could hold only one of them. `WorkflowRunReadResponse` grows no park member of its own; the run's `suspended` status says _something is parked_ and the phase states say _what and why_.
- **No new disclosure.** `parkCause` is engine-authored and bounded by I-017-21 and reaches no phase output, artifact, or agent-visible context. Surfacing it on a read a session member is already entitled to make adds no recipient.
- **Accepted consequence: a finished run shows no park members.** The liveness rule is exhaustive, so a run that resumed, completed, failed, or was cancelled emits none of the four on any phase — including a phase whose `park_reason` and `park_cause` columns still hold the record SA-42 deliberately preserves. This is intended, not an oversight: the wire members answer _why is this parked now_, and asking _why was this parked once_ is a history question the timeline answers, since every park emitted `workflow.phase_suspended` carrying the same cause. A cancelled run additionally carries its cancellation reason on `failureReason`. If a post-hoc park summary is later wanted on the read model it is a separate additive member with its own name, never a loosening of this rule — a member that sometimes means _now_ and sometimes means _once_ is the ambiguity this rule exists to remove.

### Operator run control (SA-45)

The engine rules of SA-40 through SA-42 are reachable over the wire through exactly two operations. Both are operator actions on a run, both are authorized as named Cedar operation actions, and both refuse through registered codes.

- **Two operations, not three.** `workflow.runCancel` cancels a run. `workflow.runResume` resumes a parked run and carries the SA-41 re-pin as an **optional member of the resume request**, not as an operation of its own — SA-41 defines the repair only as an action on a resume, so a separate operation would admit the re-pin-without-resume shape that section refuses. The wire registry moves eleven → thirteen.
- **Cancel and its event mint together.** A run reaches the `cancelled` status durably only by appending `workflow.cancelled` in the **same unit of work** as the status write. This is not a logging convention: without it a projection rebuild would replay the last `workflow.phase_suspended` payload and resurrect a run the operator cancelled (SA-25). `workflow.cancelled` joins the `workflow_lifecycle` category, taking it 6 → 7 types and the taxonomy 23 → 24 across the same five categories. Its payload carries the operator's supplied `reason`, bounded exactly as `parkCause` is.
- **`workflow.cancelled` clears the live park fields of the whole run — a projector rule, not only an engine rule.** On applying `workflow.cancelled` the projector sets `park_reason`, `park_cause`, `auto_resume_at`, and `park_attention_key` to `NULL` on **every** phase row of that run, and does so from the event alone. Stating this only as an engine rule would leave the invariant unverifiable against the artifact it quantifies over: a rebuild that replays `workflow.phase_suspended` and then a `workflow.cancelled` carrying nothing but a reason has no other instruction that would clear what the suspension set, so the rebuilt row would carry an armed schedule for a run that is over. The rule is deliberately **run-scoped and unconditional** rather than payload-enumerated — a workflow with parallel branches can hold several parked phases at once, and a payload that listed them would have to enumerate them correctly to stay byte-equal, adding a way to be wrong for no gain. Every phase of a cancelled run is unparked by construction, so clearing all of them is the same write as clearing the right ones.
- **Cancel is unconditional on a parked run, idempotent on a cancelled one, and refused on a finished one.** SA-42's without-precondition rule is unchanged and is why no code names a refused cancellation of a parked run. A second cancel of an already-`cancelled` run replays the original event's identity rather than writing again — a retried operator action must not cost a clear answer. A cancel against a run that reached `completed` or `failed` refuses `workflow.run_not_cancellable`, because answering "cancelled" for a run that ran to completion would misinform the operator about what their action did.
- **Resume requires a park, and does not require the schedule to have elapsed.** A resume against an unparked run refuses `workflow.resume_not_parked` — distinct from `workflow.repair_not_parked`, which refuses the re-pin leg, so an operator can tell whether dropping the re-pin would have worked. Resuming **ahead of** an armed `autoResumeAt` is permitted and needs no override flag: the armed instant is advisory pacing derived from what a provider reported, and the worst outcome is that the account is still spent and the phase re-parks, emitting its own `workflow.phase_suspended`. That re-park is a legal response, not a refusal, and is visible in the timeline and on the next read.
- **Authorization is a named operation action, not an approval category.** `workflow.runCancel` adjudicates `Action::"workflow::cancel"` and `workflow.runResume` adjudicates `Action::"workflow::resume"`, each on the target workflow run, through the same `PermissionCheckService` seam SA-39 uses for `Action::"workflow::start"`. They are **separate actions from start and from each other**: start creates work, cancel destroys it, and resume commits further spend against a provider account — one action covering all three would make "may start a workflow" silently mean "may cancel anyone's". A denial refuses `workflow.control_denied`, naming which action was denied, since the two are separately grantable. Registering both actions in the Cedar schema is Plan-012 surface, not Plan-017's; until it lands, both operations fail closed for every principal but the node owner, the same shape SA-39 already ships for start.
- **Refusals are total.** Every refusal above leaves run status, phase rows, armed schedules, and phase outputs byte-identical to their pre-request state. Resolution and validation complete before any write.

### Loud-errors discipline (C-12)

- Unknown integration name, missing required input, typo in expression, unknown phase reference, unknown resource pool, unknown approver principal — all must fail loudly at `WorkflowDefinitionCreate` or at phase launch. Silent no-ops forbidden by default. n8n 1.0 had to break silent-error-passing behavior users had built on — the V1 chance to avoid that is now.
- Workflow step outputs referenced by downstream phases must resolve at definition time (by shape) and at execution time (by presence). Missing-output is never silently coerced to empty string.

## Default Behavior

- Workflow phases default to sequential execution unless the definition explicitly marks safe parallelism. When explicitly parallel, default `ParallelJoinPolicy` is `fail-fast`.
- Each `single-agent` / `automated` phase defaults to one primary target channel and one primary producing run.
- `multi-agent` phase defaults to `ownership: OWN` — V1 default and only value (SA-6).
- `multi-agent` phase-owned channel defaults differ from bare-channel defaults on four axes (SA-8 / Pass B §3.3):
  - `turn_policy: round-robin` (bare-channel default `free-form`)
  - `turns_per_agent`: formula-bounded, indicative max 20 (bare-channel 50)
  - `membership`: phase-targeted agents only (bare-channel: session membership)
  - `moderation`: `off` for `auto-continue` / `done` / `human-approval` gates; `post-turn informational` for `quality-checks` gate
  - All other bare-channel defaults (token budget, cost limit, idle timeout, scheduler limits, partition behavior) unchanged.
- `multi-agent` channel termination defaults to `CLOSE_WITH_RECORDS_PRESERVED` on phase completion (SA-9). This inverts Temporal's `TERMINATE` default because the workflow engine inherits channel transcripts as phase-output source material. Phase failure drives `REQUEST_CANCEL` with 30-second grace period. Retry creates a new channel per iteration (prevents BIND-like cross-iteration state leak).
- Workflow definitions default to immutable-by-version: editing a workflow creates a new version rather than mutating a running definition in place.
- Workflow definition reads default to the canonical persisted definition record for the requested scope and version rather than to an artifact manifest.
- `human` phase forms default to primitive-type JSON schema fields (`text` / `long_text` / `number` / `integer` / `boolean` / `enum`) plus optional `artifact` field referencing a Plan-014 pre-uploaded `ArtifactId`. No in-form file upload — uploads are out-of-band via Plan-014 (SA-10; Pass C §3.2).

## Fallback Behavior

- If a later phase depends on unavailable capabilities, the workflow must pause in a blocked state instead of silently skipping the phase.
- If a workflow definition changes while an older version is running, the running instance must continue on the version it started with.
- If a phase output is large or unavailable inline, the workflow timeline must link to a durable artifact reference instead of dropping the output.
- If a `multi-agent` phase's channel fails to create (resource exhaustion, moderation-backend unavailable), phase admission blocks until preconditions are met or `max_duration` deadline fires.
- If a `human` phase is claimed by one participant and then abandoned, optimistic-concurrency must allow re-claim on next open (SA-10; Pass C §3.2). Assignment model: implicit claim on first open; optimistic-concurrency reject on submit if version mismatch.
- If `RUN_ITERATION_LIMIT` or `max_duration` fires mid-run, the workflow moves to `failed` with `failure_reason` preserved; all completed phase outputs remain addressable. `max_duration` continues to elapse while a run is parked (SA-2 measures wall-clock), so a parked run reaching its deadline fails there rather than resuming — and no resume schedule is ever armed past it (§Provider-limit pacing and durable resumption (SA-40)).
- If a provider refuses a phase's work with a typed usage-limit signal, the phase parks rather than failing and rather than retrying: the retry ladder is not entered, no attempt is consumed, and the run stays fully visible and resumable with a stated cause (§Provider-limit pacing and durable resumption (SA-40); §Park integrity and cancellability (SA-42)). A refusal carrying no provider-reported reset boundary parks with no schedule — an unscheduled park, never a silent one.
- If a resume — scheduled or operator-invoked — reaches a provider that is still refusing, the run re-parks against the boundary now in force rather than failing or looping. An early resume costs exactly one refused attempt.
- If a parked run's frozen definition is the reason it is parked, the operator may resume it onto the definition's current version as an explicit, audited re-pin at a resume that **enters a phase fresh**, which the engine refuses in each of three cases — a run that is not parked at all, a target version that cannot account for the phases the run has already completed, and a repair requested while any of the run's attempts is still in flight — the resuming phase continuing one, or a parked parallel sibling holding one (§Frozen-definition repair (SA-41)). Absent that request, the run resumes on its pinned version unchanged.

## Interfaces And Contracts

### Core SDK and persistence contracts

- `WorkflowDefinitionCreate` must persist phase definitions and version metadata with schema version marker (C-8). Persisted phase definitions embed the declared topology — each phase's `dependsOn` predecessor list and, on a join phase, its `parallelJoinPolicy` (§Graph model — nodes, ports, and edges (SA-32)) — so the stored body is the complete executable graph and no edge lives outside it.
- `WorkflowDefinitionCreate` with target scope `shared` — direct authoring, file import, and the §Definition scope in the builder (SA-36) promotion alike, which all ride the one operation — must adjudicate the daemon's operator-scope authorization through the Plan-012 Cedar evaluation surface (`PermissionCheckService`) against the daemon-resolved node-owner participant identity before any row is written, the same boundary Spec-028 §Authorization applies to governance mutations. A principal that does not resolve to the node owner is refused with a typed error, the check fails closed while the identity-resolution seam is unwired, and a refusal never silently downgrades the request to a narrower scope.
- `WorkflowDefinitionRead` must return the canonical definition record and selected version metadata for the requested scope.
- `WorkflowDefinitionList` must enumerate the definitions visible to a caller, resolving scope most-specific-first — the caller's session, then its project, then the daemon's `shared` tier — and deduping on `(scope, scopeRef, contentHash)` (added 2026-08-10 by the Tier-8 plan-readiness audit). Enumeration is not optional polish: every other operation here addresses a definition by an id the caller must already hold, so without it a definition that is not already known cannot be reached at all, and the `session` / `project` / `shared` breadth the same amendment ratified would be unobservable.
- `WorkflowRunStart` must bind a workflow version to a session and create phase execution state.
- Definition/execution entity separation: `WorkflowPhaseId` identifies a phase in the definition (static); `PhaseRunId` identifies a specific execution (with iteration number, status, timestamps). `PhaseRunId` is deterministically generated as `BLAKE3(workflowRunId || phaseDefinitionId || attemptNumber)` (SA-21 — see State And Data Implications).
- `PhaseOutputRead` must expose durable phase outputs and artifact references.
- `WorkflowGateResolve` must resolve workflow-scoped approvals or participant questions; gate resolution rows are append-only hash-chained per §State And Data Implications.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

### Workflow gate scope vs channel gate scope (SA-7)

Workflow gates (`WorkflowGateResolve`) and channel moderation gates (Spec-016 per-turn) share the Plan-012 approval backend but are **temporally disjoint** (Pass B §3.2):

- Channel-level gates fire per-turn with `scope: channel`.
- `WorkflowGateResolve` fires at phase boundary with `scope: workflow-phase`.
- Pending channel gates **block** phase transition to `completed`. A phase cannot complete while its owned channel has an unresolved moderation gate.

### Multi-agent phase — `ownership: OWN` at V1 (SA-6, SA-8, SA-9)

`multi-agent` phase at V1 supports `ownership: OWN` only:

- Phase B receives phase A's channel transcript as read-only context via SDK ergonomic `inheritContext: { from: "previous_phase" }`.
- Retry creates a new channel per iteration — never reuses a phase-owned channel across attempts.
- `BIND` (multi-phase channel reuse) is committed to V1.1 under three named criteria in [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments): (a) ≥3 production reports of OWN+transcript-inheritance insufficient, (b) concrete failure case documented, (c) BIND lifecycle contract addressing the five ambiguities recorded canonically in `ADR-015 §V1.1 Criterion-Gated Commitments`.
- Modern multi-agent composition convergence (2025–2026) is **state-passing, not handle-binding**: Temporal Child Workflows + Signals ([Temporal — Child Workflows](https://docs.temporal.io/develop/typescript/child-workflows)), LangGraph `Command(goto, state)` ([LangGraph multi-agent handoff](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)), AutoGen `HandoffMessage` ([AutoGen Teams](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)), OpenAI Assistants API Threads removal ([OpenAI Assistants deprecation, Threads removal 2026-08-26](https://platform.openai.com/docs/assistants/migration)). Airflow SubDAG — the closest BIND analogue — was deprecated in 2.x because its shared-scope ambiguity took 3+ years to patch ([Airflow — Deprecate SubDags in Favor of TaskGroups, #12292](https://github.com/apache/airflow/issues/12292)).

### Human phase — `HumanPhaseConfig` (SA-10, SA-11, SA-12)

Human-phase authoring uses the `HumanPhaseConfig` type:

```typescript
type HumanPhaseConfig = {
  prompt: string;
  inputSchema: JSONSchema7; // primitive-type fields + optional artifact ref
  assignees?: ParticipantRef[];
  dueAt?: Duration;
  timeout: "none" | Duration; // REQUIRED — no default; author must opt in
  timeoutBehavior?: "fail" | "continue" | "escalate"; // default 'fail'
};
```

- `timeout` is **required** at the SDK-type level — no field-default footgun (Wave 1 §5.1 SDK ergonomic safeguard). Author must type either `"none"` (no deadline; session timeline shows `waiting-human` until resolved) or an explicit `Duration`.
- Three independent durable-execution engines converge on no-default-timeout: [Temporal Workflow Execution Timeouts](https://docs.temporal.io/encyclopedia/detecting-workflow-failures) default ∞, [Argo — Suspending Workflows](https://argo-workflows.readthedocs.io/en/latest/walk-through/suspending/) with `{}` = indefinite suspend, [Camunda 8 User Task dueDate](https://docs.camunda.io/docs/components/modeler/bpmn/user-tasks/) optional/expression-based. This is modern durable-execution convention across independent implementations — not one-camp disagreement.
- `timeoutBehavior: 'escalate'` emits the `workflow.human_phase_escalated` telemetry event only at V1 (SA-11). No paging primitive exists; default-timeout is reconsidered V1.x once notification routing ships (see [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments)).
- `human` phase uses the new Spec-012 approval category `human_phase_contribution` (SA-12). See [Spec-012 Approvals](../specs/012-approvals-permissions-and-trust-boundaries.md).
- Deep-link URL: `/session/:sid/workflow/:rid/phase/:pid`. Client-side autosave via localStorage / IndexedDB keyed on `(phaseRunId, participantId)` — daemon-side draft persistence deferred V1.x.

### Adapter contract (SA-15)

- First-party adapters (Codex, Claude, MCP tool adapters, channel surfaces) ship as separately-versioned packages under `@ai-sidekicks/adapter-*`. Core exposes an adapter contract via `packages/contracts/`. No `src/adapters/` folder inside core (C-6).
- Adapter-bundling precedent cost: Airflow `airflow.contrib` was force-split into 61 provider packages in the 2.0 release ([Airflow 2.0 providers](https://airflow.apache.org/docs/apache-airflow-providers/)).

### External tool references — content-addressed (C-7)

- External tool references in workflow definitions (e.g., `codex@v1.2.3#sha256=...`) must be content-addressed with hash pins. Mutable tags must not be trusted for externally-referenced definitions.
- This closes the [tj-actions/changed-files CVE-2025-30066](https://nvd.nist.gov/vuln/detail/CVE-2025-30066) retroactive-tag-repointing class (23,000 repositories compromised by a single upstream tag repointing).

### Secrets — by reference only (C-15)

- Secrets are referenced via `secret://<scope>/<name>` and resolved at phase-launch into environment variables, stdin, or a named-file file descriptor — **never argv**. Logging redaction is defense-in-depth, not primary control. Closes the argv-exposure vector documented in CVE-2025-30066 (runner memory dumped to logs via argv).

## State And Data Implications

### Truth vs projection vs ephemeral (SA-25)

Workflow state separates into three tiers (Pass G §1, §8):

- **Truth (immutable, source-of-truth):** `workflow_definitions` (content-hashed), `workflow_versions`, `phase_outputs`, `workflow_gate_resolutions` (hash-chained). These, together with `session_events` (Spec-006), are authoritative. Daemon must be able to rebuild everything else from them.
- **Projection (rebuildable):** `workflow_runs`, `workflow_phase_states`, `parallel_join_state`, `workflow_channels` — rebuildable via a `ProjectionRebuild` path owned by Plan-015 ([Temporal — Custom persistence layer, 2024](https://temporal.io/blog/higher-throughput-and-lower-latency-temporal-clouds-custom-persistence-layer)).
- **Ephemeral:** pool reservation state is not persisted — re-requested on daemon restart; no runtime pool-counts rows (G §10.7 resolved).

The park-and-resume state added 2026-08-16 stays inside this split rather than beside it: the durable `autoResumeAt` schedule, its `parkAttentionKey` fold key, and the `parkReason` / `parkCause` record all sit on the phase-state projection — per-phase, because SA-32 parallel branches park independently and a run-level value could hold only one park (§Provider-limit pacing and durable resumption (SA-40); §Park integrity and cancellability (SA-42)). All four are **projection**, not truth, and every one of them is carried by the event that produced it — the suspension event for all four park fields, the `workflow.resumed` event for a repair's version re-pin — so the rebuild-byte-equal-from-`session_events` rule holds with no exception and no schedule survives a rebuild that the log does not contain. None of the four is a new table; the 9-table census below is unchanged.

Workflow definitions, versions, and phase outputs must be durable and replayable. Workflow and run histories must remain cross-linked for audit and replay. Optional workflow exports, previews, or summaries may be published as artifacts, but those artifacts are derivative views and must not replace the canonical definition store. Running workflows require phase-state persistence separate from UI state.

Plan-017 specifies the concrete 9-table SQLite schema (SA-24 lands there — implementation detail, not spec contract).

Canvas layout is deliberately **none of the three tiers** and therefore holds no daemon storage at V1: it is not truth (it is mutable per author), it is not a projection (it is not rebuildable from `session_events`), and it is not run-ephemeral (it must outlive a run). It is client-local, per §Canvas layout is not definition bytes (SA-35).

### Deterministic identity (SA-21)

`PhaseRunId` generator: `BLAKE3(workflowRunId || phaseDefinitionId || attemptNumber)`. **Derivation is total (clarified 2026-08-10, Tier-8 plan-readiness audit):** every bit of the identifier is a function of that preimage and none of it comes from a clock or an entropy source — so a `phaseRunId` is **not a ULID**, whose leading 48 bits are a millisecond timestamp the preimage cannot produce. Implementation surfaces that typed the column as a ULID were describing a shape this rule forbids; the audit corrected them and left the identifier's concrete text rendering open (see §Open Questions), because choosing a rendering is a design decision rather than an audit finding. Any ratified rendering must stay a pure function of the digest. Replay reproduces the same `phaseRunId` sequence; random ULIDs are forbidden for `phaseRunId`. Replay uses `session_events` + immutable truth tables as authority; projection tables rebuild via `ProjectionRebuild` ([Temporal Encyclopedia — Event History](https://docs.temporal.io/encyclopedia/event-history); [Bitovi — Replay Testing in Temporal](https://www.bitovi.com/blog/replay-testing-to-avoid-non-determinism-in-temporal-workflows)).

### Hash-chain scheme (SA-26, SA-27)

- Approval history is append-only, per-`workflow_run_id` flat hash chain (C-13 / I7), anchored to Spec-006's existing scheme: **BLAKE3** digest, Ed25519 signature, RFC 8785 JSON Canonicalization Scheme. No new SHA-256 approval-chain scheme. Dual-anchored: each `workflow_gate_resolutions` row also has a corresponding `session_events` row whose payload carries the `row_hash` — the pre-ordered-log pattern from [Google Trillian](https://google.github.io/trillian/docs/TransparentLogging.html) at smaller scale.
- Flat chain (not a Merkle tree) is appropriate at V1 write volume per [Crosby & Wallach, Efficient Data Structures for Tamper-Evident Logging (USENIX 2009)](https://static.usenix.org/event/sec09/tech/full_papers/crosby.pdf) and [AuditableLLM, MDPI Electronics 2025](https://www.mdpi.com/2079-9292/15/1/56).
- **Dual-hash algorithm (SA-27):** BLAKE3 for daemon-internal identity (workflow-definition content hash, `phaseRunId` derivation, approval-chain row digest). SHA-256 reserved for Plan-014 artifact-manifest content hashes where ecosystem interop matters. This is deliberate — different algorithms for different scopes, not an oversight.
- Write amplification: ~42 KB / 110 writes per 10-phase workflow; fits within 2–3 Spec-015 batches under `synchronous=FULL` WAL mode ([SQLite — Write-Ahead Logging](https://www.sqlite.org/wal.html)).

### Ship-empty tables (SA-28)

`human_phase_form_state` ships in V1 as an **empty schema** (reserved for V1.x daemon-side draft autosave). Zero migration cost when autosave feature lands; zero runtime cost while unused. Clients resume drafts from their own localStorage / IndexedDB per Pass C §3.2 until daemon-side drafts ship V1.x. Canvas layout for the visual builder persists on this same client-local tier and for the same reason — see §Canvas layout is not definition bytes (SA-35). Neither is daemon state at V1.

### I/O format invariants (C-5)

Workflow state, step inputs/outputs, captures: **JSON-only**. No pickle, no YAML-with-`!!python/object`, no eval-of-user-expression. Airflow XCom's pickle default enabled a direct RCE path, disabled in 2.0 ([Airflow — Turn off pickling of XCom by default in 2.0, #9606](https://github.com/apache/airflow/issues/9606)).

### Engine event record (SA-43)

Added 2026-08-16 (workflow-hardening amendment). The engine keeps a **maintainer-facing record of its own decisions**, and it is **always on** — there is no enable flag, no verbosity level, and no per-run opt-in.

The always-on rule is the whole point and is not a convenience: a run parks once. By the time anyone knows a park needs explaining, the decision that produced it has already happened, and there is no second chance to have turned the log on. A record that must be enabled before the event it explains is a record that is off exactly when it matters. The cost of the alternative is paid once, in bounded storage; the cost of this alternative is paid every time, in an unreconstructable incident.

**What it is not.** The record is **non-canonical** and MUST NOT become the only account of anything. The canonical account of a run stays `session_events` plus the immutable truth tables (§Truth vs projection vs ephemeral (SA-25)); the operator-facing account of a park stays the `parkCause` of §Park integrity and cancellability (SA-42). Nothing in replay, verification, projection rebuild, or audit may read this record, and its expiry must degrade diagnosis, never correctness.

**What it carries.** Engine decisions and the typed values they were made from: phase admission verdicts and pool-wait entries, state transitions, gate resolutions, park decisions with their typed `parkReason`, schedule arm and clear events with the instant armed, resume attempts and their outcomes, and typed refusal codes. Every record carries the correlation keys — `workflowRunId`, `phaseRunId`, `attemptNumber`, and a monotonic per-run sequence — so a single run's decision history is reconstructable by filtering. The requirement is per-run **correlation**, not per-run storage: the physical layout (one file per day, per run, or per daemon; rotation and compaction policy) is the observability owner's choice and is deliberately not fixed here. The line format is newline-delimited JSON — one complete object per line, inside the JSON-only constraint of §I/O format invariants (C-5) — so a record truncated by a crash costs its last line rather than its whole file.

**Dispatch and outcome are two records, and the wording is part of the contract.** A record written before the work it describes states an **intent** — that the engine is dispatching a resume onto a session, never that a turn is running on it — and is paired with a second record stating that work's outcome. The pairing is what makes absence diagnostic: a dispatch with no outcome beside it is itself the finding, and where the step between them wedges it is the only signal there is. One record phrased as a completed fact for work that had not started yet reads, to an operator watching a run that then hangs, as the exact opposite of what happened. The prose in every record is engine-authored, never model output.

**What it must not carry.** No secret material, ever, in any encoding (§Secrets — by reference only (C-15) and its SA-13 I4 invariant apply here exactly as they apply to argv, logs, and artifacts). No raw provider prompt or completion text: where a decision was made from a provider signal, the record carries the **typed** value the driver normalized — the park reason, the window provenance — never the payload it was normalized from. This keeps the record a decision log rather than a second, unredacted transcript.

**Ownership.** This record is a **non-canonical bounded-retention diagnostic payload class**, which is [Spec-020 §Required Behavior](020-observability-and-failure-recovery.md#required-behavior)'s declared tier — "non-canonical observability payloads … must use explicit bounded retention separate from canonical event and failure-detail retention" — and [Spec-020 §PII in Diagnostics](020-observability-and-failure-recovery.md#pii-in-diagnostics) owns that tier's discipline: the ≤ 7-day default TTL, the `retention_policy_override` warning past 30 days, and mandatory inclusion in the [Spec-022 §Shred Fan-Out](022-data-retention-and-gdpr.md#shred-fan-out) Path-3 fan-out. Spec-017 **requires** the record and specifies its content, correlation keys, and always-on rule; Spec-020 and Plan-020 **own** the bucket, its retention, and its shred leg, and register it alongside the diagnostic buckets already enumerated there. This spec authors no bucket, no TTL, and no shred path — the one-writer discipline `cross-plan-dependencies.md` §1 imposes.

## Example Flows

- **Sequential with human gate.** A workflow runs `analyze → plan → implement → review`, pausing between `plan` and `implement` for a human-approval gate.
- **Version-immutable edit.** A workflow is edited after one instance has already started. The running instance continues on the old version while new runs use the new version.
- **Definition-as-artifact export (derivative view).** A project-scoped workflow definition is exported as a review artifact for discussion. Later workflow execution still binds to the canonical persisted definition version rather than to the artifact copy.
- **Parallel with `all-settled`.** A research workflow spawns `{pass-a, pass-b, pass-c, pass-d, pass-e}` in parallel under `ParallelJoinPolicy: all-settled`. Any pass that fails emits `workflow.phase_failed`; siblings continue; the workflow enters its synthesis phase once all five settle (pass or fail).
- **Multi-agent OWN.** A `deliberate` multi-agent phase spawns a phase-owned channel with three agents under `turn_policy: round-robin`, `turns_per_agent: 15`. The channel produces a conclusion artifact which becomes phase output. Phase completes; channel closes with `CLOSE_WITH_RECORDS_PRESERVED`. The next phase receives the transcript via `inheritContext: { from: "previous_phase" }`.
- **Human phase with escalation.** A `validate` human phase with `timeout: {days: 3}`, `timeoutBehavior: 'escalate'`, `inputSchema: {decision: enum['approve','reject'], notes: long_text}`. The participant opens the deep-link `/session/:sid/workflow/:rid/phase/:pid`, drafts a reply (localStorage autosave), submits. Gate resolves with `scope: workflow-phase`. If timeout fires before submit, the workflow emits `workflow.human_phase_escalated` telemetry event — no paging at V1 (deferred per `ADR-015 §V1.1 Criterion-Gated Commitments` until notification routing ships).

## Quality-Check Model

- Retry targets: the phase that produced the output, or a specific earlier phase (configured per gate).
- Max retries: configurable per gate (default 3).
- Quality-check failure behavior: `block` (halt workflow), `warn` (continue with flag), `skip` (bypass gate).
- Quality checks are evaluated by a dedicated agent or automated script — not by the same agent that produced the output.

## Output Mode Specification

- V1: structured JSON with artifact references. Each phase produces `{artifacts: ArtifactId[], summary: string, metadata: Record<string, unknown>}`.
- V2 (deferred): conversation markdown, channel transcripts, rich media as first-class output types.
- Phase outputs are stored as artifacts (Plan-014) with `artifactType: 'workflow_output'`.

## Discussion Integration Path

- **V1:** `single-agent` phases run one agent in one channel. `multi-agent` phases spawn phase-owned channels (`ownership: OWN`) where agents discuss before producing output; the channel's conclusion becomes phase output.
- **V1.1 (criterion-gated):** `ownership: BIND` — multi-phase channel reuse. Contingent on three criteria in [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments). See Interfaces And Contracts §Multi-agent.
- **V2 (deferred):** cross-phase discussion channels — agents from different phases collaborate in shared channels.

## Workflow Timeline Integration

### Event envelope and category split (SA-18)

All workflow events land as payloads inside the existing Spec-006 `EventEnvelope` — **no new envelope schema**. `causationId` on the envelope carries parent-event relationships; `workflow_run_id` / `phase_run_id` are payload fields. This is an additive MINOR envelope bump under [ADR-018](../decisions/018-cross-version-compatibility.md) discipline.

V1 introduces **5 new Spec-006 categories** (not one monolithic `workflow_lifecycle`):

- `workflow_lifecycle`
- `workflow_phase_lifecycle`
- `workflow_parallel_coordination`
- `workflow_channel_coordination`
- `workflow_gate_resolution`

Scope-of-query split matches Spec-006's existing `run_lifecycle` / `approval_flow` pattern. No collision with existing `presence.*`, `run.*`, `approval.*`, `channel.*`, `recovery.*` categories.

Reverse-DNS `workflow.*` namespace convention follows [CloudEvents Specification v1.0.2 `type` attribute](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#type).

### Event types (SA-19) — 24 types under `workflow.*`

- **`workflow_lifecycle` (7):** `workflow.created`, `workflow.started`, `workflow.gated`, `workflow.failed`, `workflow.completed`, `workflow.resumed` (payload extended 2026-08-16 with an additive-optional version re-pin member naming the version a repaired run left and the one it joined — §Frozen-definition repair (SA-41); additive MINOR under [ADR-018](../decisions/018-cross-version-compatibility.md)), `workflow.cancelled` (**new 2026-08-18** — the canonical record of an operator cancellation, carrying the operator-supplied `reason` bounded exactly as `parkCause` is. Minted **together** with `workflow.runCancel` per §Operator run control (SA-45): the status write and this append share one unit of work, without which a projection rebuild would replay the last `workflow.phase_suspended` payload and resurrect a cancelled run (SA-25). This is the only type minted since the taxonomy was declared at 23, and the category count stays at five)
- **`workflow_phase_lifecycle` (12):** `workflow.phase_admitted` (new; resource-pool admission), `workflow.phase_waiting_on_pool` (diagnostic), `workflow.phase_started`, `workflow.phase_progressed`, `workflow.phase_cancelling`, `workflow.phase_failed` (extended with `cancellation_reason: 'sibling_failure' | null`), `workflow.phase_retried`, `workflow.phase_suspended` (payload extended 2026-08-16: its `reason` union widens from the single `waiting-human` value to `waiting-human \| provider-usage-limited`, and the payload carries the bounded `parkCause` plus, where one is armed, the durable `autoResumeAt` instant and, where one was computed, the `parkAttentionKey` fold key — §Park integrity and cancellability (SA-42); additive MINOR under [ADR-018](../decisions/018-cross-version-compatibility.md), so no new type is minted and this list stays at twelve), `workflow.phase_resumed`, `workflow.phase_completed`, `workflow.human_phase_claimed` (informational), `workflow.human_phase_escalated` (telemetry-only at V1 per SA-11; no `nextAction` pre-declaration — additive-field discipline per ADR-018)
- **`workflow_parallel_coordination` (1):** `workflow.parallel_join_cancellation` (sibling cancel driven by `ParallelJoinPolicy`)
- **`workflow_channel_coordination` (3):** `workflow.channel_created_for_phase`, `workflow.channel_closed_with_records_preserved`, `workflow.channel_terminated_forcibly`
- **`workflow_gate_resolution` (1):** `workflow.gate_resolved` — carries `scope: channel | workflow-phase` + `outcome`. The base payload is extended at the persistence layer with `gate_resolution_id` + `row_hash` fields to realize the `session_events` dual-anchor (SA-26). No separate chain-advance event — the gate-resolved event carries the chain extension. Payload additions are additive MINOR bumps under [ADR-018](../decisions/018-cross-version-compatibility.md).

### Ordering invariants (SA-20)

Load-bearing event-sequence rules ([Temporal Events Reference](https://docs.temporal.io/references/events), [Temporal — Events and Event History](https://docs.temporal.io/workflow-execution/event)):

- `workflow.phase_admitted` precedes `workflow.phase_started` (resource-pool admission required first).
- `workflow.phase_cancelling` precedes `workflow.phase_failed` whenever `cancellation_reason != null`.
- `workflow.gate_resolved` with `scope: workflow-phase` precedes the subsequent `workflow.phase_started`.
- `workflow.channel_created_for_phase` precedes any events with matching `channelId`.
- Parallel cancellation fires one coordinator event (`workflow.parallel_join_cancellation`) + per-sibling event chains at deterministic tick-boundary — never mid-callback.
- (Added 2026-08-16.) `workflow.phase_suspended` precedes every `workflow.phase_resumed` carrying the same `phase_run_id`, and a `workflow.resumed` carrying the SA-41 version re-pin member is preceded by a `workflow.phase_suspended` for that run — a repair is only ever expressible on a parked run, so a re-pin with no preceding park is a malformed sequence rather than an unusual one.

### Cadence (SA-22, SA-23)

- `workflow.phase_progressed` cadence is phase-type-specific:
  - `single-agent` / `automated`: emit on turn completion + tool-invocation boundary.
  - `multi-agent`: emit on channel-turn boundary + 25 / 50 / 75% of `turns_per_agent` budget milestones.
  - `human`: emit on form-section save + claim / re-claim.
- `workflow.phase_waiting_on_pool` cadence: emit on entry-to-blocked-state + 30-second intervals while blocked (tripwire-configurable), carrying `waitingSinceSeq` for reader correlation. Pass G stores aggregate `totalPoolWaitMs` on phase row — not per-wait rows (G §10.1 resolved).
- `workflow.resumed` payload carries structured `resumptionPoint: {activePhaseRunIds, pendingGates}` for reader-reconstruction speed (aligns with low-cardinality naming per [OpenTelemetry SemConv for Events](https://opentelemetry.io/docs/specs/semconv/general/events/); [n8n Workflow Executions](https://docs.n8n.io/workflows/executions/) provides durable-resume prior art).

### Session timeline surfacing

- Workflow phases appear as distinct sections in the session timeline (Spec-013).
- Retry iterations appear as sub-entries within the phase section.
- `workflow.phase_suspended` with `reason: 'waiting-human'` is a first-class surfaced event; session UI surfaces pending-human count prominently (Pass C §5.1 mitigation for no-default-timeout UX cost).
- (Added 2026-08-16.) `workflow.phase_suspended` with `reason: 'provider-usage-limited'` is surfaced with the same first-class weight, rendering the park's `parkCause` and, where one is armed, the instant the run resumes itself — the same instant the durable schedule holds, read from the payload rather than recomputed. Concurrently parked runs sharing an attention key render as one entry with its affected-run count, never as one entry per run (§Provider-limit pacing and durable resumption (SA-40)); a run parked with no schedule renders as parked-awaiting-resume rather than as scheduled, because a client that invents a time the engine did not arm is the display half of the same guess SA-40 refuses to make.

## Phase-Type and Gate-Type Taxonomy

Phase types (V1):

| Type | Description |
| --- | --- |
| `single-agent` | One agent executes the phase autonomously in one channel |
| `multi-agent` | Phase-owned channel (`ownership: OWN`) — multiple agents deliberate, conclusion becomes phase output |
| `automated` | No agent — executes a script or validation check |
| `human` | Human participant completes a form; submission becomes phase output |

Gate types (V1):

| Gate Type | Behavior | Failure Behavior |
| --- | --- | --- |
| `auto-continue` | Phase completes, next phase starts automatically | N/A (no gate check) |
| `quality-checks` | Automated quality check runs on phase output | Configurable: block / warn / skip. Retry: re-run phase up to `max_retries`. |
| `human-approval` | Human must approve phase output before continuing | Block until approved. Reject: retry or stop (configurable). |
| `done` | Terminal gate — marks workflow as complete | N/A |

Failure behaviors: `retry`, `go-back-to`, `stop`. Phase run statuses: `pending`, `running`, `completed`, `failed`, `skipped`. Gate result statuses: `passed`, `failed`, `waiting-human`.

## Visual Workflow Builder

V1 ships a visual, node-graph authoring surface for workflow definitions alongside the file and SDK authoring paths. The builder is an **authoring and visualization surface over the execution model defined above** — it introduces no execution semantics, no scheduling behavior, and no node kind the phase model cannot already express. Every graph the builder can produce serializes to the same `PhaseDefinition` sequence a hand-authored definition produces, and the daemon accepts it through the same `workflow.definitionCreate` path with the same validation. See [ADR-026](../decisions/026-visual-node-graph-workflow-authoring.md).

### Graph model — nodes, ports, and edges (SA-32)

The persisted node set is **exactly the phase set plus one entry node**. Nothing else is a node.

| Node kind | Persisted as | Count | Notes |
| --- | --- | --- | --- |
| Phase node | one `PhaseDefinition` in the definition's phase sequence | one per phase | Carries the phase's declared type — `single-agent`, `multi-agent`, `automated`, `human` — from §Phase-Type and Gate-Type Taxonomy. The node's visual class is that type; there is no fifth phase type and the builder cannot mint one. |
| Entry node | not a phase; a definition-level `entry` record | exactly one, mandatory | Names how a run of this definition begins. It never enters the phase sequence, never receives a phase run id, and never produces a phase-state row. |

Everything else an author manipulates on the canvas is a **property of a phase node**, edited in that node's inspector and rendered on the node as a badge or attached affordance — never an independent node with its own identity:

- **Gate** — the phase's gate type (`auto-continue`, `quality-checks`, `human-approval`, `done`). Rendered on the phase node's outgoing edge shoulder. A gate is not a node; promoting it to one would require a node kind the phase-type domain does not contain and would put a second writer on the phase-state row.
- **Agent assignment** — the agents a `single-agent` or `multi-agent` phase runs, rendered as avatars inside the phase node. A `multi-agent` phase's agents are the members of that phase's OWN channel; they are not separate graph nodes, because they have no independent position in the phase sequence.
- **Tool / action binding** — see §Tool bindings are references, never inline policy (SA-34) below.
- **Human-form definition** — a `human` phase's form config, edited in the inspector.

**Edges.** A single edge kind exists: the **sequence edge**, meaning "when the source phase's gate resolves to continue, the target phase becomes eligible." Fan-out from one phase node to several targets is the graph spelling of the existing within-phase-boundary parallel construct and carries the definition's `ParallelJoinPolicy` on the join, exactly as a hand-authored definition does. Ports are typed by construction: a phase node exposes one inbound port and one gate-qualified outbound port; the entry node exposes an outbound port only and has no inbound port.

Sequence edges persist **in the canonical definition body**, as each phase's optional `dependsOn` predecessor list — the ids of the phases whose gates must resolve to continue before this phase becomes eligible. An empty list marks an entry-node successor. The field is all-or-none across a definition: when every phase omits it, the order of the phase array declares the sequential chain of §Default Behavior and the stored bytes stay exactly what the author submitted — the daemon never materializes the lists; supplying the field on some phases but not others is refused server-side alongside the SA-33 rules. Fan-out is one phase id appearing in more than one `dependsOn` list; a join is a phase whose list carries more than one id, and that phase carries the fan-out's `ParallelJoinPolicy` as its `parallelJoinPolicy` value — required exactly there and refused on any non-join phase, with the §Default Behavior `fail-fast` default supplied by the authoring surfaces (the builder and the SDK write it into the definition they emit; the wire and the store never default it). The daemon therefore executes the declared topology from the stored body alone, and the builder round-trips it with no out-of-band edge store.

**`go-back-to` is not an edge.** §Required Behavior states it is a state-reset operation, not a cyclic edge, and `workflow.definitionCreate` runs a cycle check that would reject the cyclic spelling. The builder therefore renders a phase's `go-back-to` target as an **annotation on the phase node** (a labelled back-reference), never as a drawn connection, and the connection layer refuses any attempt to draw one. A builder that drew it would emit definitions the daemon rejects on every save.

### Graph shapes that are refused (SA-33)

The builder refuses these at **edit time** — a connection that would produce one cannot be completed, and a definition that already contains one cannot be saved:

1. **Any cycle** among phase nodes, including a self-edge. Mirrors the definition-create cycle check.
2. **An orphan phase** — a phase node not reachable from the entry node by sequence edges.
3. **Zero phase nodes.** A definition must contain at least one phase.
4. **Zero or more than one entry node in the graph.** The refusal is on the graph and on the stored definition, which always carry exactly one entry record — it is **not** a wire-level requirement: a `workflow.definitionCreate` request may omit the entry record, because `manual` is the only V1 start mode and the daemon materializes it (§Entry node and the V1 trigger surface (SA-37)). A request carrying an entry record with an unrecognized start mode still refuses.
5. **Any edge whose target is the entry node.**
6. **A `done`-gated phase with an outgoing sequence edge** — `done` terminates; an outgoing edge would assert a successor the engine will never run.
7. **A fan-out whose branches carry no join policy**, or whose branches converge on more than one join point.

**Edit-time validation mirrors the daemon check; it never replaces it (SA-33).** Every rule above is re-evaluated server-side at `workflow.definitionCreate`, and the daemon's answer is authoritative. A client that skips, weakens, or predates a rule produces a **refusal**, not a persisted definition — the fail-closed direction. Refusals surface as the typed codes registered in [error-contracts.md](../architecture/contracts/error-contracts.md) §Workflow; the builder mints no error surface of its own, and until the pending §Workflow extension lands, an unregistered condition refuses under the existing codes rather than inventing one, per §Loud-errors discipline (C-12).

### Tool bindings are references, never inline policy (SA-34)

A phase node may bind tools. The binding a definition persists is a **reference only**: the scope-qualified binding identity plus a tool name, resolved at phase launch through the [Spec-005](../specs/005-provider-driver-contract-and-capabilities.md) §Tool Metadata layer that [Spec-028](../specs/028-mcp-server-configuration-and-governance.md) §Tool-Level Overrides feeds.

A workflow definition **MUST NOT** carry any governance facet inline. Specifically, a tool binding in a definition carries no `enabled`, no `approvalMode`, and no `idempotencyClass` value — those three facets are node-operator surface, set only through the Spec-028 override operations, Cedar-gated per [Spec-028](../specs/028-mcp-server-configuration-and-governance.md) §Authorization, and independent per binding scope. A definition that carried them would let a workflow author grant themselves an approval posture the operator never granted, and would let a definition exported from one machine silently import a weakened posture onto another. The builder's inspector therefore **displays** the effective facets read-only, sourced live from the governance surface, and offers no control that writes them.

Trust is likewise not a definition concern: an untrusted binding refuses at launch under the Spec-028 trust rules, and the builder shows that state rather than overriding it. This is a distinct mechanism from the content-addressed external-tool pin of §External tool references — content-addressed (C-7): that pin governs a fetched tool artifact's bytes, while a tool binding's identity and trust are governed by the binding's own keyed base-config hash. Neither substitutes for the other.

### Canvas layout is not definition bytes (SA-35)

The **canonical definition** is the JCS-canonicalized JSON body the BLAKE3 content hash already covers. Canvas geometry — node coordinates, viewport pan and zoom, collapse state, and any other purely visual attribute — is **excluded from that body** and from the hash preimage. Dragging a node changes no byte of the definition, mints no content hash, and creates no version. This exclusion is **hash-scope only, never semantics-scope**: nothing that affects execution may be moved into the layout channel to escape hashing, and every field the engine reads stays inside the hashed body.

Layout persists **client-local**, on the same tier and by the same mechanism as `human` phase form drafts in §Ship-empty tables (SA-28) — browser-local storage in the renderer, with no daemon write and no table. The choice is forced by §Truth vs projection vs ephemeral (SA-25): `workflow_versions` is immutable truth, so a mutable per-author geometry cannot live there; a new mutable table would be neither truth nor a projection rebuildable from `session_events`, which is a tier SA-25 does not define; and eventing geometry would enlarge the workflow event taxonomy for data no execution path reads.

Layout is nonetheless **portable**, because the file form of §Definition file form — export and import (C-17) carries it as an optional top-level section outside the hashed body. A definition opened with no layout available — freshly imported, authored through the CLI or SDK, or opened on a second machine — renders through a **deterministic topological auto-layout** derived from the phase sequence, so a definition is never unopenable and two authors opening the same layout-less definition see the same arrangement.

### Definition scope in the builder (SA-36)

The builder loads and saves at all three scopes of §Resolved Questions and V1 Scope Decisions.

- **Loading** lists definitions visible from the current context — the session's own, its project's, and the daemon's `shared` tier — grouped by scope, with the resolution order (`session`, then `project`, then `shared`) shown so an author can see which definition a run would pick.
- **Saving at `session` or `project` scope** creates a new immutable version of that definition, exactly as today.
- **Saving an edit to a `shared` definition is copy-on-write, never edit-in-place.** Opening a `shared` definition and editing it produces a **new definition at the editing context's scope** (`project` by default, `session` if there is no project context), carrying the shared definition's content hash as its parent content hash so provenance is recorded in the existing version-chain field. The `shared` original is untouched.

  Copy-on-write is required, not preferred. Definition rows are immutable by construction — the definitions table deliberately carries no updated-at column — so "editing in place" would mean appending a version to the shared definition, which silently repoints **every project on the daemon** that resolves it, with no signal at any consuming project and no way for a consumer to pin. Copy-on-write keeps the blast radius of an edit equal to the scope the editor is standing in, which is the same containment principle that makes two same-scope-name MCP bindings distinct entries rather than a merge.

- **Promotion `project → shared` is an explicit, separately-invoked operator action**, never an implicit consequence of saving. It creates the definition at `shared` scope from the promoted version's exact bytes. "Operator" is enforced, not honorific: promotion rides `workflow.definitionCreate` at `shared` scope and therefore clears the same operator-scope authorization every `shared`-target create clears (§Core SDK and persistence contracts) — the boundary keys on the target scope, never on the invoking gesture, so no route into `shared` bypasses it.

### Entry node and the V1 trigger surface (SA-37)

Every definition has exactly one entry node, which records **how a run begins**. At V1 the entry node's start mode has exactly one value: **manual** — a run begins when a participant starts it through `workflow.runStart` or the CLI.

The entry node is shipped as a **structurally extensible single-value record, not a union with unhonored arms**. No `schedule`, `event`, or `webhook` arm is declared, because §Non-Goals records the C-11 precedent for exactly this shape — an enum whose arms outran the engine had to be break-removed later — and §Loud-errors discipline (C-12) forbids a surface that looks like a capability and silently is not. When a firing engine ships, its start mode is an additive-MINOR extension under [ADR-018](../decisions/018-cross-version-compatibility.md), and the run row's existing creator field already distinguishes a participant-initiated run from a trigger-initiated one, so the persistence hook is in place without declaring the arm early.

### Definition file form — export and import (C-17)

A workflow definition has one canonical file form, and it is the YAML the authoring commitment already names, carrying the schema-version marker the versioning commitment already requires. **No second schema dialect exists**: the file is the definition, and its canonical bytes are the JCS-canonicalized JSON of the parsed document — which is precisely the existing hash preimage, so a definition's content hash is identical whether it arrived through the builder, the SDK, or a file.

The document has exactly two top-level parts:

1. The **definition body** — the hashed, canonical part. Everything the engine reads.
2. An **optional `layout` section** — canvas geometry, outside the hashed body. An importer that does not understand it, or a consumer that does not want it, ignores it and loses nothing executable. A CLI-authored file omits it entirely.

Round-tripping is closed in both directions: builder → file → CLI → daemon and CLI → file → builder produce the same definition body bytes and therefore the same content hash. Export is a serialization of an existing read; import is a submission through the ordinary definition-create path with the ordinary validation, so an imported definition is subject to every refusal rule above and to the ordinary tool-governance resolution — an import can never carry governance state with it.

## Chat-Invoked Start and Start Authorization

Governed by [ADR-027](../decisions/027-chat-invoked-workflow-start.md). This section adds start **callers**, never start **modes**: §Entry node and the V1 trigger surface (SA-37) is unchanged, the entry node still records exactly `manual`, and every surface below resolves to the existing `workflow.runStart` operation — the shape `Spec-016 §Turn Policies` already establishes for chat-typed affordances, where a client-surface `@mention` is sugar resolving to a typed operation and introduces no new wire contract.

### Chat-start surface (SA-38)

Three chat-adjacent callers exist at V1, and all three collapse onto one start semantics:

1. **The registered `/workflow` command.** The session composer registers exactly one command root, `workflow`, with exactly one V1 verb, `start`: `/workflow start <name>`. The argument is a definition name; the client resolves it through the same most-specific-first scope walk as every other name resolution (`session`, then `project`, then `shared` — §Resolved Questions and V1 Scope Decisions), and autocomplete enumerates candidates via `workflow.definitionList` — the existing scope-filtered operation, so enumeration discloses nothing the caller could not already list (I-017-13 holds by construction). Verb additions are additive-MINOR; no verb is ever repurposed (the SA-17 rename-cost precedent).
2. **The composer affordance.** A visible composer control enumerates startable definitions by name over the same `workflow.definitionList` call; selecting one issues the same start. The command is the accelerator; the affordance is the discoverable surface — two entrances, one operation.
3. **The agent leg — the `workflow_start` callback tool.** Agents start workflows only through the daemon-curated `workflow_start` session callback tool, the first concrete `SessionCallbackTool` in the corpus. The tool takes a definition name plus an optional scope qualifier, resolves through the same scope walk, and issues the same start under SA-39 adjudication; the invocation lands as an ordinary `tool_activity` row. While the daemon's `approval.requestCreate` seam is unregistered, the callback-tool registry is withheld at spawn and a stray invocation is answered `denied` — the agent leg is **born-withheld**, and that is the shipped state until CP-005-7's activation; nothing on this surface bypasses or weakens that contract.

A start issued from a channel carries the originating channel as an additive-optional `channelId` on `WorkflowRunStartRequest` — provenance and progress-surface binding only. It is not an input to the SA-39 role adjudication, but it is **daemon-validated before it binds a surface** — after the SA-39 role adjudication admits the start: the daemon requires the resolved starting participant to be a member of the named channel and refuses `workflow.start_denied` otherwise, so a forged `channelId` can neither surface run progress into nor inject a progress card into a channel the starter cannot see. On the agent leg the field is never tool-supplied — the `workflow_start` input schema carries no channel field — the daemon derives the originating channel from the invoking turn's channel context, leaves it absent when the invoking turn is not channel-scoped, and runs the same membership validation on the derived value. The run's timeline presence in a validated channel follows §Session timeline surfacing; a client renders the run's live progress against the channel the start named.

An agent-authored channel message is never a command. The command grammar exists at the human composer only, and channel text activates nothing (`Spec-016 §Turn Policies` — activation is addressing-gated), so the literal text `/workflow start x` inside any channel message is inert prose twice over.

### Command interception — the reserved `/` prefix (C-18)

Leading-`/` input in the session composer is **command namespace, owned by the runtime**:

- A registered command is intercepted and executed by the client. The text never composes into a channel message, an agent context, or a provider turn — under any path, including steer-through-composer surfaces that share the input box.
- Unrecognized leading-`/` input **refuses loudly** at the composer with the unknown-command form (§Loud-errors discipline (C-12)), **naming the `//` escape**, and is likewise never forwarded. Silent fall-through to prose is forbidden: the reference provider CLIs dispatch leading-`/` user text as their own commands, so forwarding it would hand the input to a command layer outside this system's governance — the rule is collision-forced, not stylistic.
- **The escape.** On the channel-message path, composer input beginning `//` is ordinary text: the composer strips exactly one leading `/` and sends the remainder, so `//etc/hosts — what does this line do?` sends the message `/etc/hosts — what does this line do?` — inert downstream, since channel activation is addressing-gated. The escape is the sole path by which composer-originated leading-slash text is ever sent. On provider-bound composer paths (steer-through-composer), the escape is **not yet active**: every leading-`/` input — `//`-escaped included — keeps the loud refusal, not because the hazard is still open — `Spec-005 §Required Behavior`'s driver-boundary neutralization closes it, and an escaped `//etc/hosts …` arrives as `/etc/hosts …`, which that predicate neutralizes — but because activating the escape is composer work no task yet authors, and shipping an escape into a path whose neutralization has not merged would re-open the hazard for exactly as long as the two are out of step; the refusal on those paths tells the user that slash-prefixed text cannot be sent there yet — user-facing copy never carries an internal tracking id; this spec names the gate — and the escape activates there via a Plan-017/Plan-023 composer follow-up once the driver-boundary neutralization ships — `Spec-005 §Required Behavior` settles that behavior and [Plan-005](../plans/005-provider-driver-contract-and-capabilities.md) T3.18 builds it. **This rule records that follow-up as its own downstream consumer** (2026-08-25): the gate it formerly named was an open backlog item, and an archived item records nothing forward, so the record lives here. Stated without softening, because a reader must not mistake a recorded gate for scheduled work: **no Plan-017 or Plan-023 task authors this activation yet.** T3.18's merge satisfies the gate but changes no composer code, so the refusal on provider-bound composer paths stands — correctly, and indefinitely — until that task is authored and ships. This sentence is the surface that holds it.
- The namespaces never overlap: `@` is addressing (**who** — resolving to `OrchestrationRunCreate` per `Spec-016 §Turn Policies`); `/` is commands (**what** — resolving to typed operations). A definition name occupies argument position only (`/workflow start <name>`), so no workflow name can ever collide with a command verb.

**Recorded residual — contract settled 2026-08-25, code pending.** This rule governs the composer path. The steer and queue-submit paths carry free text into provider turns and are Spec-004 / Spec-005 / Spec-006 surface; neutralizing leading-`/` text at the driver boundary is now settled contract in `Spec-005 §Required Behavior` — transport-only neutralization at the driver's outbound frame boundary, a closed frame-origin discriminator whose unknown arm neutralizes, and a runtime tripwire that fails the turn rather than letting a provider's zero-turn success be recorded as a completed one — which supersedes the backlog item that formerly tracked it. The spawn-with-command-dispatch-disabled variant that item also floated is **rejected** there: a provider flag is the provider's promise, not the daemon's guarantee, and may be set only as defense in depth. Until [Plan-005](../plans/005-provider-driver-contract-and-capabilities.md) T3.18's code merges, chat-borne workflow start is collision-proof by interception, the composer's provider-bound paths refuse all leading-`/` input (the escape above stays inactive there, so the composer never produces provider-bound slash text), and steered and queued free text arriving from non-composer surfaces retains the provider-dispatch hazard: a bounded, named residual, not a silent one.

### Start authorization (SA-39)

Starting a workflow run is adjudicated **per start** as the named Cedar operation action `Action::"workflow::start"`, in the `Spec-012` named-operation-action shape (the `Action::"intervene"` and `Action::"dispatch::<capability>"` precedents) — deliberately **not** a tenth approval category. A start traverses no approval pipeline, mints no approval row, and is never remembered: remembered grants key on approval category, so a category-shaped grant would silently cover every definition on the daemon — the wrong width for a per-definition operation. Role defaults, mirrored as one row in the security-architecture Permission Matrix:

| Role                  | Start workflow runs |
| --------------------- | ------------------- |
| `owner`               | Yes                 |
| `collaborator`        | Yes                 |
| `runtime contributor` | No                  |
| `viewer`              | No                  |

One rule governs humans and agents: the CLI path, the desktop path, the chat surfaces of SA-38, and the `workflow_start` callback tool all adjudicate the same action. The agent leg's principal is the invoking turn's effective principal under the Spec-012 actor-axis rules — consumed here, authored there.

**Principal resolution.** On the local daemon socket every JSON-RPC caller binds to the daemon's recorded node-owner participant (the transport rule the contract doc records), so the local CLI and desktop paths collapse to the node-owner and the matrix row discriminates only on identity-carrying paths. The chat-borne start is the first per-participant start surface: its authoring participant MUST arrive as a **daemon-resolved value — the transport-authenticated participant — never a client-supplied body field** (the admitting-principal-carrier class). Until the Spec-012/Plan-012 carrier registration lands (a Tier-6 targeted delta, gated by a named Plan-017 §Preconditions box), a chat-borne start resolves only the node-owner principal and **every other chat-borne start refuses** — fail-closed, with the refusal below, and with the CLI, desktop, and affordance node-owner paths unaffected.

**Refusal.** A denied start — matrix denial, unresolvable chat-borne principal, or a `channelId` naming a channel the resolved starting participant is not a member of (SA-38's membership validation) — refuses with `workflow.start_denied`, registered in `error-contracts.md` §Workflow as the first landed entry of the extension A-017-15 already owes. The arms are ordered and their disclosure is scoped: the role adjudication runs first and may refuse with a role-level message — the matrix is public surface, so naming the role leaks nothing — and the SA-38 membership validation runs second, only for a start the matrix admits, with its non-member and nonexistent-channel outcomes collapsed into one byte-identical message, so a denied caller learns no channel-membership or channel-existence fact (the `runtimenode.permission_denied` shape: one code, distinct messages where nothing leaks, collapse exactly where a distinction would). No other code is minted on this surface, preserving the no-unregistered-codes constraint of §Loud-errors discipline (C-12).

**Cedar registration is upstream surface.** The action literal and the chat-borne carrier are registered by the Spec-012/Plan-012 targeted delta; this spec names the semantics and consumes the adjudication (`PermissionCheckService`), authoring no Cedar schema entry — the one-writer discipline `cross-plan-dependencies.md` imposes.

## Implementation Notes

- Workflow authoring belongs in the product surface, but workflow execution still uses the same run, approval, and artifact primitives as free-form sessions.
- Version immutability simplifies replay and support.
- Phase-level parallelism remains explicit and bounded — no implicit concurrency.
- Persistence uses a LangGraph-inspired checkpoint pattern on the existing SQLite store (Spec-015), with the normalized-tables-over-JSON-blob decision documented in State And Data Implications. No external workflow engines (Temporal, Restate) — contradicts ADR-002 (local-first). V1 ships ahead of OpenTelemetry workflow semantic conventions and adopts OTel semconv additively when ratified.
- One execution model at V1 per C-11: local daemon runs workflows locally. Do not ship a `local | queued | remote` enum at V1.

## Pitfalls To Avoid

### Structural pitfalls

- Mutating running workflow definitions in place.
- Hiding workflow phase outputs outside the session timeline.
- Treating workflow pause as a UI-only banner with no durable execution state.
- Using mutable tags instead of content-addressed pins for external tool references — directly opens the CVE-2025-30066 class.
- Absorbing `BIND` multi-phase channel reuse into V1 without the three ADR-015 criteria being met — engineering risk budget is documented in Pass B §3.1.
- Recording sibling cancellation in async callbacks instead of at a deterministic synchronous tick checkpoint — reintroduces the non-determinism class observed in Temporal Java SDK #902.
- Collapsing `user_input` approval / `human-approval` gate / `human` phase into two categories — the three-way split is load-bearing (Pass C §2).
- Recognizing a provider usage-limit refusal by matching message text, an error string, a rate-limit window name, or a model id. Prose is not a contract; it changes without a version bump, and a matcher that silently stops matching converts a park into a burned retry ladder and then a false `failed` verdict, with no signal that anything changed (C-19).
- Holding a resume schedule in an in-memory timeout. A timeout is lost at the exact moment it is most needed — a daemon restart — and a run whose only route forward died with the process is stuck without anything having recorded that it is.
- Computing resume jitter with a modulus. When the intended span exceeds the operand's range the modulus never wraps, so the real spread collapses to a fraction of the declared width while every bound assertion still passes — the test proves the value is inside the window and proves nothing about the distribution.
- Arming a schedule from a window whose provenance is `model_default` or `estimated`. Those values are the driver's honest statement that the number is a guess; scheduling against a guess either fires into a still-spent account or holds a run that could have run, and both look like the engine knew something it did not.
- Letting the attention record gate work. A correlation record consulted by start, resume, or retry becomes an availability lock, and a stale one then makes a run unstartable after the account has quietly recovered — the "protection that isn't" class of C-12 in its most expensive form.
- Writing the engine's park cause into a phase output, an artifact, or an agent-visible context. Engine prose arriving through a model-output channel reads as something a model said, and a phase output is immutable truth (SA-16), so the sentence is unretractable once written.
- Re-pinning a run's frozen definition version silently, or as a side effect of an ordinary resume. A run whose early phases executed a definition no longer recoverable from the run cannot be replayed, verified, or explained.
- Re-pinning while any attempt of the run is in flight — the resume **continuing one** rather than entering a phase fresh, or a re-pin admitted through one branch's fresh entry while a parked parallel sibling still holds one — the same class as the silent re-pin above, reached by a caller who asked explicitly. The units already dispatched were launched from bytes the run would no longer be pinned to, so neither the attempt's inputs nor the outputs it returns remain explainable by the version the run's record names, and the operator who asked for a repair is told it succeeded over a run that repaired nothing.
- Clearing a durable resume schedule because its timer fired, rather than because the run left the park. A fire that re-checked and then failed to transition the run leaves a parked run whose only route forward has been deleted, with nothing recording that it is stranded.

### Security invariants (non-conformant if violated) — SA-13 / Pass E §4

Engine implementations violating any of the following are **non-conformant**. Each invariant is a testable contract requirement; concrete CVE-reproducer corpora and test categories are specified in [Plan-017 §Testing](../plans/017-workflow-authoring-and-execution.md) (SA-29, SA-30, SA-31 — implementation detail, not spec surface).

- **I1 — argv-only execution.** The engine **MUST NOT** accept a shell-string command form for user-templated content. No `shell=true`, no `/bin/sh -c "..."` over author-controlled fields. All commands execute via argv-list spawn only. Closes [GitHub Actions — Script-injection guidance](https://docs.github.com/en/actions/concepts/security/script-injections), [n8n CVE-2025-68613 (CVSS 9.9)](https://github.com/n8n-io/n8n/security/advisories/GHSA-v98v-ff95-f3cp), and [Airflow CVE-2024-39877](https://nvd.nist.gov/vuln/detail/CVE-2024-39877) in one architectural choice.
- **I2 — typed substitution; no templating over author-controlled fields.** The engine **MUST NOT** evaluate Jinja2, `${...}`, `{{}}`-eval, or any Turing-complete expression language over workflow-definition strings. Parameter substitution is a closed, non-Turing-complete lookup grammar with a whitelist. Closes the template-injection class.
- **I3 — typed approver capability.** The engine **MUST NOT** treat approver permission as a submitter string or as "whoever has `Read`". Approver principal is a typed capability bound to an identity (Spec-012). Admin override is a distinct audited capability. Anti-pattern: Jenkins Pipeline Input Step historically approved on `Item/Read` (CVE-2017-1000108, fixed in plugin 2.8 on 2017-08-07) and still silently bypasses the `submitter` allow-list for holders of `Jenkins.ADMINISTER` with no audit emission ([Jenkins SECURITY-576 advisory, 2017-08-07](https://www.jenkins.io/security/advisory/2017-08-07/); [`InputStepExecution.java` `canSettle()`](https://github.com/jenkinsci/pipeline-input-step-plugin/blob/master/src/main/java/org/jenkinsci/plugins/workflow/support/steps/input/InputStepExecution.java); [JENKINS-56016 Won't Fix](https://issues.jenkins.io/browse/JENKINS-56016)).
- **I4 — secrets by reference only.** The engine **MUST NOT** accept inline secret material in workflow definitions. Secrets are referenced as `secret://<scope>/<name>` and resolved at phase-launch into env / stdin / named-file fd — never argv. Logging redaction is defense-in-depth on top, not primary control. Closes [tj-actions/changed-files CVE-2025-30066](https://nvd.nist.gov/vuln/detail/CVE-2025-30066) runner-memory-via-argv class. The redaction-is-defense-in-depth stance is motivated by [Airflow secret masker issue #54540](https://github.com/apache/airflow/issues/54540) Vault masking regression (Airflow 3.0.0-3.0.4).
- **I5 — content-addressed external references.** The engine **MUST NOT** resolve external tool references by mutable tag. References carry hash pins (`codex@v1.2.3#sha256=...`). Closes CVE-2025-30066 retroactive-tag-repointing class.
- **I6 — OWASP File Upload minimums on human-phase uploads.** The engine **MUST** enforce size cap, extension allowlist, magic-byte sniff, storage rename, path validate, AV hook, quarantine-on-fail per [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html). Closes [Argo CVE-2025-66626](https://www.endorlabs.com/learn/when-a-broken-fix-leads-to-rce-how-we-found-cve-2025-66626-in-argo) symlink-traversal-via-broken-fix class.
- **I7 — append-only hash-chained approval history.** The engine **MUST NOT** permit mutation of `workflow_gate_resolutions` rows. Workflow-definition edits are a separate audit entry. Replays use at-execution-time policy — not current definition ([Crosby & Wallach USENIX 2009](https://static.usenix.org/event/sec09/tech/full_papers/crosby.pdf); [AuditableLLM MDPI 2025](https://www.mdpi.com/2079-9292/15/1/56); Temporal's Event History is the reference pattern).
- **I1–I7 testability.** Every invariant has ≥1 test that fails when the invariant is violated. Test categories and CVE-reproducer corpora are specified in Plan-017 §Testing (SA-30).

### Terminology discipline (SA-17 / C-12)

- Use **"workflow"** (not pipeline / flow), **"phase"** (not stage / task), **"artifact"** (not output / capture when persisted), **"step"** reserved for intra-phase operations if any.
- Airflow Datasets→Assets, SubDAG→TaskGroup, execution_date→logical_date terminology churn is the precedent for cost of late rename ([Airflow — Upgrading to Airflow 3](https://airflow.apache.org/docs/apache-airflow/stable/installation/upgrading_to_airflow3.html)).

## Acceptance Criteria

- [ ] Workflows can be authored as versioned phase definitions with schema version marker; cycle-check rejects invalid definitions at author time.
- [ ] All four phase types execute: `single-agent`, `multi-agent` (`OWN` only), `automated`, `human`.
- [ ] All four gate types resolve correctly, with channel gates blocking phase transition per temporally-disjoint contract (SA-7).
- [ ] Workflow runs survive reconnect and daemon restart with phase state intact; replay reproduces deterministic `phaseRunId` sequence (SA-21).
- [ ] Parallel phase execution honors `ParallelJoinPolicy`; `fail-fast` cancels siblings at deterministic tick boundary (SA-4).
- [ ] Resource-pool admission (`pty_slots`, `agent_memory_mb`) blocks phase launch when pool saturated; tripwire events fire.
- [ ] `RUN_ITERATION_LIMIT` / `max_duration` / `max_retries` bounds all hard-fail with preserved `failure_reason` (SA-1, SA-2).
- [ ] Workflow phase outputs are addressable after workflow completion; retries produce new output rows (immutability preserved — SA-16).
- [ ] Human-phase `HumanPhaseConfig.timeout` is typed `'none' | Duration` with no field-level default (SA-10).
- [ ] Human-phase uploads enforce OWASP File Upload minimums; CVE-2025-66626 regression battery passes (I6).
- [ ] Approval history hash chain verifies on replay; tamper-detection tests pass (I7 regression battery).
- [ ] Security regression battery covers I1–I7 invariants with CVE-reproducer corpora (test surface lands in Plan-017 §Testing per SA-30).
- [ ] All 24 workflow event types emit in the Spec-006 envelope with correct ordering invariants; Pass F ordering-invariant tests pass.
- [ ] A parked phase is renderable from one `workflow.runRead` response, and a phase that resumed past an earlier park carries no park members on that response (§Park surfacing on the read model (SA-44)).
- [ ] A cancelled run's status and its cleared live park columns rebuild from the log alone, with `workflow.cancelled` as the sole durable producer of the `cancelled` status (§Operator run control (SA-45)).
- [ ] Secrets referenced via `secret://...` never appear in argv, logs, or artifacts (canary-secret regression — I4).
- [ ] The registered `/workflow start` command intercepts at the composer; unrecognized leading-`/` composer input refuses loudly, naming the `//` escape; command-namespace input never reaches a channel message or provider turn; the `//` escape is the sole path by which composer-originated leading-slash text is sent — as ordinary channel prose with one escape character stripped — and provider-bound composer paths refuse all leading-`/` input, escaped included, until the composer change activating the escape on those paths is authored and ships — Plan-005 T3.18's driver-boundary neutralization is that change's precondition, not its substitute, so T3.18 merging does not by itself lift this refusal (C-18).
- [ ] Every start path — CLI, desktop, chat command, composer affordance, `workflow_start` callback tool — adjudicates `Action::"workflow::start"`; a matrix-denied principal, an unresolvable chat-borne principal, and a `channelId` naming a channel the resolved starter is not a member of each refuse with `workflow.start_denied` — role adjudication first, membership validation only for a matrix-admitted start (SA-39, SA-38).
- [ ] The `workflow_start` callback tool is withheld at spawn while the `approval.requestCreate` seam is unregistered; a stray invocation answers `denied`, never `completed` and never silence (SA-38).
- [ ] A usage-limit refusal is recognized from the typed driver signal alone and never from message text; it parks the phase immediately, consumes no `max_retries` attempt, mints no new `phaseRunId`, and increments no `max_phase_transitions` — including when no reset window was reported (SA-40, C-19).
- [ ] A durable `autoResumeAt` is armed only where the typed refusal's reset boundary is stamped provider-reported, is jitter-offset by a scaled — never modular — pure function of `workflowRunId` that replay reproduces, survives daemon restart via a post-rebuild re-arm, is never armed at or past the run's `max_duration` deadline, and is cleared by every transition out of the park (SA-40).
- [ ] Concurrently parked runs sharing a provider-account attention key present as one attention record; a mixed set of failures is never folded into a usage-limit record; and no start, resume, retry, or schedule fire consults the record — a run stays startable after its account recovers (SA-40).
- [ ] Every parked run is cancellable from every waiting state without precondition or wait, cancellation clears the durable schedule in the same unit of work, and the parked phase-state row with its `parkReason`, bounded `parkCause`, and completed outputs survives the cancel intact (SA-42).
- [ ] An operator resuming a parked run may re-pin it to the definition's current version explicitly; the re-pin is recorded on `workflow.resumed`, never fires from a timer or an ordinary resume, never re-runs or rewrites a completed phase output, and refuses at each of its three refusal points — a run that is not parked, a repair requested while any of the run's attempts is still in flight (the resuming phase continuing one rather than entering fresh, or a parked parallel sibling holding one), and a target version that cannot account for the phases the run already completed (SA-41).
- [ ] The engine event record is on for every run with no flag to turn it on, carries `workflowRunId` / `phaseRunId` / `attemptNumber` / sequence on every record, carries no secret material and no raw provider prompt or completion text, and is read by no replay, verification, projection-rebuild, or audit path — its expiry degrades diagnosis only (SA-43).

## Open Questions

Backfilled 2026-08-10 by the Tier-8 plan-readiness audit (A-017-12). Questions this spec settled are recorded below in §Resolved Questions and V1 Scope Decisions — including the OWN-channel `turns_per_agent` provider question, opened here 2026-08-10 and discharged 2026-08-11 by the Spec-016/Plan-016 restoring delta (PR #321, NS-56; moved below per the settled-questions rule, PR #321 Codex round 2). The first entry here is open against **another** spec, not against this one; the second is open against this spec but is narrow — it asks how a value this spec already constrains is rendered, not what the value must be. No entry gates a Required Behavior row: §Deterministic identity (SA-21) is satisfied by any rendering that stays a pure function of the digest, so the determinism row holds irrespective of which rendering is ratified. Criterion 2 of the runbook `§Spec-Status Promotion Gate` is therefore satisfied by deferral with a named vehicle rather than by resolution.

- **Where the 24 `workflow.*` event types and their five categories are registered** (23 until 2026-08-18, when `workflow.cancelled` joined `workflow_lifecycle` with the operator-recovery surface; the registration this question tracks is still owed and now owes one more literal). §Workflow Timeline Integration enumerates them, but `Spec-006 §Event Type Summary` — the owning registry — carries no `workflow` category. Deferred to a combined Spec-006/Plan-006 targeted readiness-audit delta, following the ratified `mcp_governance` registration precedent; registration moves the summary rows, the marker-governed in-band total, and Plan-006's prose census in one PR. Tracked plan-side as `Plan-017 §Upstream-Tier Amendments Required` and gated by a named Precondition box on every Plan-017 phase.
- **How a derived `phaseRunId` is rendered into its text form.** §Deterministic identity (SA-21) fixes the preimage and, as of the 2026-08-10 clarification, fixes that the identifier is totally derived — but not the encoding of the digest into the column's stored characters. The obvious candidate, "ULID-shaped so the column type is unchanged," is not self-consistent as usually stated: Crockford base32 carries 5 bits per character, so a 26-character rendering spans 130 bits, and a ULID reaches 26 characters by padding its 128 bits and constraining the leading character — a rendering rule that must be written down rather than assumed. The audit deliberately did **not** choose: picking an encoding is a design decision of the same class as the scope domain, and the identifier is a durable primary key, so the choice is one-way. Deferred to lead ratification and a targeted Spec-017/Plan-017 delta, which must state the digest function's output width, the truncation or padding rule, the alphabet, and whether any leading-character constraint applies. Until it lands, implementation surfaces must describe the column as a derived opaque identifier and must not call it a ULID.

## Resolved Questions and V1 Scope Decisions

- **V1 scope per [ADR-015 amendment 2026-04-22](../decisions/015-v1-feature-scope-definition.md) (BL-097 resolution).** Full workflow engine ships at V1 (the then-17-feature V1 — workflow promoted from V1.1-deferred to V1; V1 subsequently grew to 23 features per the ADR-015 amendment of 2026-07-02, which does not affect this promotion). Two workflow-scoped V1.1 criterion-gated commitments documented in `ADR-015 §V1.1 Criterion-Gated Commitments`: (1) `BIND` multi-phase channel reuse (3 criteria); (2) `human`-phase default timeout once notification routing ships (1 criterion). (The ADR section gained a third, non-workflow commitment — the automated GDPR erasure endpoint, 2026-07-08 per BL-139 — and a fourth, also non-workflow — direct-first artifact fetch, C4, 2026-07-08 with the cross-node artifact pull-forward; neither affects this spec.)
- **V1 decision (BL-097 D1, Wave 1 §5.1):** no default timeout on `human` phase. Required typed opt-in `timeout: 'none' | Duration`. Revisit V1.x once notification routing ships. Rationale: three durable-execution engines (Temporal ∞, Argo `{}`, Camunda 8 expression-based) converge on no-default-timeout as modern convention; the `7d+escalate` alternative is illusory at V1 because no paging primitive exists — escalate fires telemetry-only, creating the "telemetry-that-looks-like-protection" silent-failure class (violates C-12).
- **V1 decision (BL-097 D2, Wave 1 §5.2):** `multi-agent` phase ships `ownership: OWN` only; `BIND` is criterion-gated V1.1. Rationale: modern multi-agent composition (2025–2026) is state-passing (Temporal Child Workflows, LangGraph `Command(goto, state)`, AutoGen `HandoffMessage`), not handle-binding. BIND adds 5 state-machine invariants on top of OWN's 3 (retry↔BIND, abandon↔BIND, gate-scoping lattice, membership snapshot timing, termination authority); Airflow SubDAG's lifecycle bugs took 3+ years to patch before deprecation. OWN-only→V1.1 BIND is additive (non-breaking); OWN+BIND at V1→V1.1 revision is breaking.
- **V1 decision (amended 2026-08-10, Tier-8 plan-readiness audit):** the workflow-definition scope domain is three-valued — `session` \| `project` \| `shared`. `session` binds a definition to its authoring session; `project` spans the sessions of one project; `shared` is the cross-project tier, a definition authored once and reusable by any project on the same daemon. All three resolve out of the same local definition store: no additional table and no synchronization path. Scope identity is carried by a `scope_ref` value alongside `scope`, in the shape `Spec-028 §Unified Inventory` already uses for scope-qualified bindings — the authoring session id at `session`, the canonical repository root at `project`, the empty string at `shared` — and definition dedupe keys on `(scope, scope_ref, contentHash)` so one definition stored at a scope is one record regardless of which session submitted it. Resolution at run start walks the tiers most-specific-first — `session`, then `project`, then `shared` — with **no merging across tiers**: two definitions of the same name at two scopes are two distinct definitions, exactly as two same-named MCP bindings in two scopes are distinct entries. Widening `scope` alone would not be storable: `project` would name no project, and a dedupe key rooted in the authoring session would split a `shared` definition into one record per submitting session. `workflow_definitions.session_id` keeps recording the authoring session at every scope, so provenance survives the widening. `shared` widens **visibility and reuse breadth only** — it is not publication, not a marketplace, and not cross-machine sync; global workflow libraries and any distribution of definitions beyond the storing daemon remain out of scope per §Non-Goals. The `channel` scope value that appeared on the contract doc and the SQLite DDL before this amendment was never specified here and is struck: a channel-scoped definition has no defined visibility semantics and would have collided with the Spec-016 `direct` channel kind, whose audience is server-forced `humans-only`.
- **V1 decision:** workflow definitions are canonical durable definition records, not canonical artifacts. Artifact publication is allowed only for derivative exports, previews, or summaries.
- **V1 decision:** one execution model (local) at V1 per C-11. No `local | queued | remote` enum at V1.
- **V1 decision (2026-08-11, discharged upstream — PR #321, NS-56; Plan-016 D-016-23):** the surface providing the OWN channel's `turns_per_agent` budget — opened as a 2026-08-10 audit question (A-017-07): §Interfaces And Contracts specifies the budget and §Workflow Timeline Integration emits progress at 25 / 50 / 75% of it, but no Spec-016 `ChannelConfig` field, `workflow_channels` column, or Spec-016 default supplied a value, and the "bare-channel 50" comparator had no bare-channel default to compare against. Ratified resolution, landed by the Spec-016/Plan-016 restoring readiness-audit delta: [Spec-016 §Interfaces And Contracts](016-multi-agent-channels-and-orchestration.md#interfaces-and-contracts) carries `ChannelConfig.turnsPerAgent` (optional positive integer; absent = the session default, so the bare-channel-50 comparator now has its default; create-time-fixed like every `ChannelConfig` member) and [Spec-016 §Stop Conditions](016-multi-agent-channels-and-orchestration.md#stop-conditions) carries the `InterruptReason` member `workflow_phase_cancelled` — the mechanism the SA-9 `REQUEST_CANCEL` and `TERMINATE` policies invoke. Plan-016 owns both (D-016-23); this spec's engine sets the former at OWN-channel creation and names the latter in its cascade, authoring neither. Plan-017's A-017-07 §Preconditions box is checked, and the cancel arms carry no upstream provider block (entry moved from §Open Questions at discharge — PR #321 Codex round 2).
- **V1 decision (2026-08-11, chat-start amendment; [ADR-027](../decisions/027-chat-invoked-workflow-start.md)):** workflows are chat-invocable through three callers of `workflow.runStart` — the intercepted `/workflow start <name>` command, the composer affordance, and the `workflow_start` callback tool — under the reserved-`/` interception rule (C-18), with start authorization as the named Cedar operation action `Action::"workflow::start"` (owner/collaborator Yes; runtime contributor/viewer No; never an approval category, never remembered; chat-borne principal daemon-resolved, fail-closed until the Tier-6 carrier delta). Rejected shapes and the full antithesis are recorded in ADR-027 §Alternatives Considered: workflows are never `@`-addressable pseudo-participants (`@` is addressing, `/` is commands), and no tenth approval category is minted.
- **V1 decision (2026-08-16, workflow-hardening amendment):** a workflow run's park is a first-class, durable, explicable state rather than a failure or a retry. Four rules are ratified for V1. **(1) Typed recognition, immediate park (SA-40, C-19).** A provider usage-limit refusal is recognized from a typed driver signal alone — never from message text, prose, a window name, or a model id — and parks the phase at once without entering the retry ladder, even when no reset window was reported. That carrier is **not yet shipped** and this spec does not mint it: it is owed by Spec-005 and Plan-005 as a sibling axis beside `RecoveryCondition`, and until it registers, a quota refusal travels the ordinary failure path and none of this section is reachable — the honest fail-closed V1 state. **(2) A durable schedule where a boundary is real (SA-40).** Where the typed refusal's reset boundary is stamped provider-reported, the parked phase arms a durable `autoResumeAt` value (never an in-memory timeout) with scaled, run-id-derived jitter and the run resumes itself across daemon restart; where that provenance is a default, an estimate, or absent, no schedule is armed and the park is unscheduled rather than invented. The account-plane `usage.rate_limit_update` display snapshot is deliberately not consumed by any of this. The `max_duration` deadline stays authoritative over any armed instant. Concurrently parked runs fold onto one provider-account attention record, which never gates start, resume, or retry. **(3) Repair and cancellability (SA-41, SA-42).** An operator may resume a parked run onto the definition's current version explicitly and audited, at a resume that enters a phase fresh — refused at three points: where the run is not parked at all, where the target version cannot account for phases the run already completed, and where any of the run's attempts is still in flight — the resuming phase continuing one, or a parked parallel sibling holding one — because a definition swapped under units already dispatched from the frozen bytes explains neither their inputs nor their outputs; and a parked run is always cancellable from every waiting state, carrying a bounded engine-authored park cause that never reaches a phase output or an agent-visible context. **(4) An always-on engine event record (SA-43)** on the Plan-020-owned bounded-retention diagnostic tier, non-canonical and read by no correctness path — always on because a run parks once and there is no second chance to have turned the log on. Rejected shape, recorded rather than assumed: a schedule armed from any reported window regardless of provenance. It was rejected because a window the driver marked `estimated` is a guess, and a run held on a guess is indistinguishable, to every reader, from a run held on a fact. Deferred rather than scoped: cross-run campaign memory and the durable wake-coalescing delivery substrate, criterion-gated to V1.1 under the three named criteria of §Non-Goals.
