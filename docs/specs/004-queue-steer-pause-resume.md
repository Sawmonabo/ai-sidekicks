## Required Behavior

- Follow-up work created while a run is active must be stored as persisted queue items unless the user explicitly requests steer and the target run supports it.
- `pause` is an orchestration-layer construct: the daemon interrupts the active run, persists conversation history and run state, and queues a resume event. The resulting `paused` state must not mean queue-drain suspension or blocked waiting.
- `resume` must return a `paused` run to active execution with the same run id.
- `interrupt` must transition a run directly to `interrupted`. Interruption is a synchronous or near-synchronous provider call with no intermediate state.
- Waiting for approval or input must remain `waiting_for_approval` or `waiting_for_input`, not `paused`.
- Every intervention outcome must be visible in the canonical event stream.
- Queue items must support cancellation before admission.
- **Post-interrupt late-event absorption (campaign B2, P1-8).** A provider **run-lifecycle** event — a run-state-transition report — that arrives for a run already in a terminal state (`completed`, `interrupted`, `failed`) is **absorbed, never appended**: a terminal-class straggler routes into the at-most-once terminal emitter ([Spec-006 §Run Lifecycle](006-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle) emission contract, campaign B1) and no-ops there; a non-terminal lifecycle straggler is dropped from the lifecycle path entirely and recorded only as a `run.late_event.absorbed` **diagnostic non-event** on the daemon's telemetry (an OTel log record per [Observability Architecture](../architecture/observability-architecture.md) — never a `session_events` row), with no state transition and no `runVersion` advance. Absorption also keys on **execution epoch**, not current run state alone (the epoch is the interval between accepted `run.rolled_back` rewinds — a confirmed conversation rewind advances it regardless of the file-leg disposition — [Run State Machine §Invariants](../domain/run-state-machine.md#invariants)): a run-lifecycle event sourced from the pre-rollback execution that arrives after a rollback has re-opened the run in `paused` is absorbed identically even though the run is no longer terminal — the Spec-006 `(runId, runVersion)` at-most-once key cannot catch these (rollback advanced `runVersion`), so appending one would record a stale terminal against the new epoch or force an illegal transition. The epoch attribution is concrete and needs no wire token: run-lifecycle events are attributed per **binding** — a superseded (fork-repointed) binding's deliveries are entirely pre-epoch, and on an in-place binding the driver's `rollbackTo` confirmation is an **in-stream fence** (the driver owns one serialized provider connection, which totally orders the confirmation against event delivery) — so the driver quiesces pre-rollback lifecycle delivery once `rollbackTo` resolves, and the daemon's per-binding cursor — an **(epoch, position) pair** whose position component advances at each turn boundary observed in the binding's ordered delivery and freezes at the fence or at repointing (a fork-superseded binding's deliveries are entirely pre-epoch at its frozen pair) — absorbs any straggler that slips through (§Driver-Level Rollback Mechanics). For the pause-first composite the absorption window opens **earlier than the fence**: from the moment the composite issues its internal interrupt, run-lifecycle events sourced from the interrupted execution are the pause's expected echo — consumed by the pause application exactly as the client pause path consumes its own interrupt's echo, or absorbed as above, never routed as spontaneous transitions — so a late `run.interrupted` arriving after the internal pause but before the `rollbackTo` confirmation cannot re-terminalize the mid-composite run or release its root (the rollback bullet below). Absorption is scoped to the run-lifecycle family: non-lifecycle provider events arriving in the same window — usage telemetry above all, plus assistant output, tool activity, and artifact publication — append normally under their own families' rules (late usage telemetry must still reach the cost ledger; absorption never drops billable usage) — but never epoch-blind: a non-lifecycle row the per-binding cursor attributes to a pre-rollback epoch appends **carrying that attribution durably** (the daemon stamps the source-epoch linkage onto the appended row at ingestion — the pair **from the straggler's operation association**: the run engine records each provider-side operation (tool call, message item, artifact production) against the **(epoch, turn) current when it opened**, in-stream and pre-fence, and the straggler's correlation key resolves that recorded pair — re-executed turns reuse ordinals, so the association must carry the epoch alongside the turn, and delivery order bounds only the _emission_ turn, so a content-asynchronous straggler (a long-running tool's progress, a delayed usage aggregate, a late-completing artifact upload) must rank by its _operation's_ opening pair, not the last-observed boundary. Binding lineage differs by mechanism without changing the value source, and **the 2026-08-26 Codex rebinding collapses V1 onto one arm of that rule**: a fork-superseded binding freezes wholesale — every delivery is pre-epoch at its retained (epoch, position) pair — and **both V1 drivers are now fork-superseded**, Claude by `--resume-session-at` + `--fork-session` and Codex by `thread/fork` at an inclusive `lastTurnId`, which mints a new thread and re-points the run's live binding in the same operation. The rule's other arm — an **in-place** rollback **rotating the binding's delivery generation at the fence**, the confirmation closing the pre-rollback generation while post-fence deliveries open the new epoch at the confirmed floor, so one provider binding spans epochs with per-generation attribution — is retained as mechanism-generic contract for a future in-place driver and **has no V1 instance**; it is not machinery V1 builds or tests. A straggler with no resolvable operation linkage takes the retained pre-rollback generation's pair — in V1 always the superseded fork binding wholesale, since every V1 rewind supersedes its binding; on a hypothetical in-place binding a post-fence delivery would instead be current by the in-stream fence's total order — a conservative upper bound strictly above its epoch's rewind cutoff (that generation closed at the run's then-current position, and admission requires the target strictly below it), so an unattributable pre-epoch straggler is always superseded with its epoch, never resurfacing as current — never a read-time guess and never the post-rollback run's current position; append-time knowledge is never discarded), so replayed projections mark it superseded exactly like the in-time rows of the epoch it belongs to and stale output can never resurface as current timeline state (the typed stamp shape is owned by the campaign's Plan-006 bundle — registered 2026-07-20 as the cross-cutting `sourceEpoch` + `sourcePosition` payload pair, [Spec-006 §Event Type Enumeration](006-session-event-taxonomy-and-audit-log.md#event-type-enumeration); §Driver-Level Rollback Mechanics' supersede projection consumes it). The near-synchronous interrupt hedge above is the _reason_ the window exists — a provider may emit briefly after the daemon records the terminal; canonical-stream visibility of the intervention outcome is satisfied by the terminal event itself, and absorption adds no second visible outcome.
- **Rollback intervention (campaign B2 — R8 run time-travel, V1 feature #19 per [ADR-015](../decisions/015-v1-feature-scope-definition.md)).** `rollback` is a first-class intervention type on the existing generic dispatch: `applyIntervention('rollback', {targetPosition})`, carrying the same mandatory fail-closed `expectedRunVersion` guard and mandatory `clientIdempotencyKey` as every intervention (§Interfaces And Contracts) — a rollback racing a progressing run expires exactly like a stale steer. `targetPosition` is the **normalized session position** (a `number`, the [Spec-005](005-provider-driver-contract-and-capabilities.md) `rollbackTo` position vocabulary) identifying the turn boundary to rewind to — **domain-validated fail-closed at admission**: an integer ≥ 0 naming a turn boundary recorded in this run's history **strictly below the run's current position**; non-integer, negative, current, future, or boundary-less values are rejected pre-dispatch with no leg applied (the wire arm carries the matching runtime bound — [API Payload Contracts](../architecture/contracts/api-payload-contracts.md)) — with exactly one carve-out: a target **equal to the current position** is admissible when the run's recorded rollback outcome at that position left the file leg incomplete (`files-unrestored`, `files-partially-restored`, or the position-mismatch skip) — the **file-leg recovery path**, whose conversation leg no-ops by absolute-position convergence and whose restore re-runs to the fixpoint; the accepted intervention's value serializes onto the forward `run.rolled_back` event ([Spec-006 §Run Lifecycle](006-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle) per-type row — this contract is that row's named structural-type owner), identically on the confirmed path (the confirmed-floor rule below). **State-gated:** legal from `paused`, `waiting_for_approval`, `waiting_for_input`, and the three terminal states; a `running` target is first brought to `paused` via the existing orchestration-layer pause path (interrupt + persist), and rollback applies from `paused` — the pause-first path is scoped to a **bare** rollback, a rollback carrying the 2026-08-16 amendment's `replacementSend` leg refusing a `running` target outright instead (§Required Behavior's edit-and-resend bullet) — the pause is an **unguarded internal sub-step of the atomic rollback application**, not a client `run.pause` request: it queues **no resume event** (the client pause path's queued resume is not part of the sub-step — rollback lands and stays `paused`, and a surviving marker would re-run the pre-rollback continuation), **every fail-closed pre-dispatch validation — the target-position domain check, the compaction-boundary classification (the 2026-08-16 amendment's bullet below), the Spec-010 restore precondition, the uncompacted-rewind-span check, execution-root tenancy, the capability check — completes at admission, before the pause sub-step** (a refused rollback of a `running` run leaves it running, untouched — pausing first and then refusing would itself be a leg applied), the intervention's `expectedRunVersion` guard is evaluated **exactly once, at admission**, against the caller-observed pre-pause `runVersion` (the internal pause's own progression cannot expire the very intervention that initiated it), and the intervention response returns the post-composition `runVersion`; rollback is the **only** path out of a terminal state ([Run State Machine §Rollback Transitions](../domain/run-state-machine.md#rollback-transitions-campaign-b2), this bundle). A rollback from a waiting state voids the pending block — the awaited approval or input request is canceled as moot when the turn that raised it is rewound, the void applying **exactly on the confirmed conversation rewind, never at admission or dispatch**: a conversation leg that fails or confirms no rewind leaves the block pending and the run in its waiting state, per the no-rewind path below (the approval reaches `approval.canceled`, a driver ask reaches `driver_ask.canceled` — Spec-006's existing terminals; the void mints no new event type). A concurrent resolution racing the rollback serializes on the run's progression: a resolution that applies first advances `runVersion`, so the in-flight rollback correctly expires; a rollback that applies first cancels the block, and the late resolution finds a canceled request and no-ops. A queued resume pending against the target run at application time is voided the same way — canceled as moot, because the position it would resume from has been rewound — under the same progression-serialized race rule. **Same-run resurrection, not fork-new-run:** budgets, supersede-marking, and the `expectedRunVersion` guard are all run-scoped; a fork would orphan all three. Re-executed turns reuse position ordinals, which is why snapshot identity is **epoch-namespaced** — the post-rollback execution's turn-6 capture must never collide with (or silently resolve to) the superseded epoch's turn-6 tree ([Spec-010 §Turn-Boundary Snapshots](010-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots), this bundle's ruling; implemented by the campaign's Plan-010 bundle). Modeled as a **forward** `run.rolled_back` event on the authoritative log ([ADR-017 Decision Log, 2026-07-02](../decisions/017-shared-event-sourcing-scope.md#decision-log)): the log never truncates or rewrites, and rolled-back turns remain queryable history **marked superseded by projection**. Successful rollback lands the run in `paused` at the rewound position. Leg ordering is **fail-closed**: the file-leg restore precondition ([Spec-010 §Turn-Boundary Snapshots](010-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots) — current `HEAD` must equal the snapshot's recorded first parent) is validated pre-dispatch, and a refusal rejects the whole intervention with no leg applied (this records the post-snapshot-commit ruling Spec-010's Restore bullet defers to this bundle: standing refusal, never rewind/revert of reviewable Spec-011 history and never a silent partial restore); the **rewind span must be live** — every row of the target run the position cutoff would mark superseded (the rewound tail strictly above `targetPosition`) is uncompacted at admission, and a rollback whose rewind span intersects already-compacted history is refused whole (the same standing-refusal class: compaction irreversibly replaced those rows' payloads with audit stubs, destroying the per-row attribution the supersede projection needs — [Spec-006 §Compacted Event Format](006-session-event-taxonomy-and-audit-log.md#compacted-event-format) — while rows at or below the target compact freely, staying current and taking no mark), with detection reading the stubs' preserved run identity: every audit stub of a run-scoped row preserves its `runId`, plus its originating position when the rollback-attribution source resolved one at compaction — [Spec-006 §Compacted Event Format](006-session-event-taxonomy-and-audit-log.md#compacted-event-format)'s `originPosition` — so the span check counts the target run's **unstamped** stubs strictly above `targetPosition`, or position-less (a stub written before rollback support shipped, whose position is unknowable), as span intersections, while `sourceEpoch`-stamped stubs are already attributed and never block; and the check is **not check-then-forget**: the span check and the write-ahead intervention row's durability are atomic under the session's append serialization (the per-session append lock), and from that durability until the intervention concludes the span is **compaction-deferred** — the compactor's per-row attribution answers _defer_ for rows a dispatched-but-unconcluded rollback's span covers (leaving them live for a later pass; the durable intervention row survives restart, so the deferral holds across a crash until the [Spec-015](015-persistence-recovery-and-replay.md) reconciliation concludes the row) and its per-row attribute-and-stub runs under the same lock — so idle compaction can neither stub the rewound tail in the admission-to-boundary window (no accepted boundary exists yet for compaction-time stamping, so those stubs would be stranded unattributable) nor race the span check over a row mid-stub; the file leg additionally requires **exclusive tenancy of the execution root** — a terminal-source rollback first re-acquires the workspace root through the [Spec-010 §State And Data Implications](010-worktree-lifecycle-and-execution-modes.md#state-and-data-implications) single-holder handoff (the terminal exit had returned the workspace to `ready`, so another run may hold or acquire the root), a root `busy` under another run is a standing refusal of the same whole-rejection class (retriable once the root frees — never a restore into another run's live working tree), and the precondition check plus restore then run under the re-acquired exclusive hold, closing the check-then-restore window (non-terminal sources still hold their root; no re-acquisition step); the conversation leg (the driver's capability-gated `rollbackTo` parity operation, campaign B3) applies next — **a conversation-leg failure ends the intervention with no file mutation and never auto-resumes**: when the driver reports `degraded` or the reconciliation rule below concludes no rewind occurred, the intervention ends `degraded` with the disposition naming exactly what applied — the internal pause for a `running` source (the run stays `paused` at its pre-rollback position with `runVersion` reflecting the pause; an implicit resume would re-run the very continuation the caller asked to rewind away from — recovery is a fresh rollback, now from `paused`, or an explicit `run.resume`), nothing for every other source (dispatch occurred, so pre-dispatch `rejected` is definitionally unavailable — [Queue And Intervention Model §Driver Result To Lifecycle Mapping](../domain/queue-and-intervention-model.md#driver-result-to-lifecycle-mapping)) — and **a terminal-source composite releases its re-acquired root on every path that does not confirm the conversation rewind**: the run stays terminal, the workspace returns to `ready`, and the execution context's release marker is restored (the hold is retained exactly when the run re-opens — a rule over the file leg's re-acquired hold alone: a conversation-only branch never re-acquires, so a vanished-checkout re-open stays released — [Run State Machine §Rollback Transitions](../domain/run-state-machine.md#rollback-transitions-campaign-b2)); once the driver confirms, the daemon **validates the driver-confirmed floor equals `targetPosition` before the file leg** (`DriverRollbackResult.applied.sessionPosition` — §Driver-Level Rollback Mechanics) — the confirmed floor is untrusted driver output and first passes the **same domain validation as the request target**: an invalid report (non-integer, negative, unrecorded boundary) or a no-op report (equal to the pre-rollback position) is treated as a no-rewind conversation-leg failure per the path above, minting no `run.rolled_back` and superseding nothing — with the file-leg recovery path excepted, because there the carve-out-admitted target legitimately equals the current position, so the driver's convergence no-op (`sessionPosition == targetPosition`, no movement) IS the confirmed floor: the composite proceeds to the fixpoint restore and the forward event emits at the confirmed position (the no-rewind branch applies only when the driver fails to confirm that floor); then, on a valid-but-different confirmed position (mismatch) the file leg is skipped fail-closed (never a restore against a boundary the conversation is not at), the run follows conversation truth — `paused` at the **confirmed** position — the intervention ends `degraded` naming the position-mismatch disposition (requested vs confirmed), and the forward event records the confirmed position (the event never lies about where the run landed) — and the confirmed floor additionally passes the settlement-time compaction-boundary reclassification (the compaction bullet below): a `boundary-diverged` conclusion degrades the same way, file leg skipped fail-closed, run at conversation truth; the file leg restores last, and a file-leg failure after a confirmed conversation rollback is surfaced as a **`degraded`** intervention outcome naming the partial state — two distinct dispositions, never collapsed: `files-unrestored` (the restore never started) and `files-partially-restored` (the multi-command restore failed mid-sequence, the failed step named; the sequence is convergent, so a fresh rollback to the same `targetPosition` re-runs it to the full-restoration fixpoint, and the run retains its exclusive root hold across the partial state — a half-restored tree is never handed to another run — [Spec-010 §Turn-Boundary Snapshots](010-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)) — never `applied`, which would hide the file-leg failure ([Queue And Intervention Model](../domain/queue-and-intervention-model.md): `degraded` is the lifecycle's partial-effect terminal, and `failed` is not an intervention state). The run-state consequence follows the **conversation leg**: once that leg is confirmed, the run's authoritative position has rewound, so the run lands `paused` at `targetPosition` and the forward `run.rolled_back` event is appended **even when the file leg then fails** — recording anything else would silently diverge the daemon's recorded position from the provider's. Replaying the same `clientIdempotencyKey` returns the recorded partial outcome (replay-or-conflict — never a re-execution); recovery is a **fresh** rollback intervention to the same `targetPosition`, which re-runs both legs. **Dispatch ambiguity is reconciled, never guessed**: the accepted intervention row is durable **before** driver dispatch (the `interventions` table's lifecycle state is the write-ahead dispatch-intent marker), and neither provider protocol offers a rollback dedupe key — the provider-boundary idempotency mechanism is **absolute-position targeting**: `rollbackTo` addresses an absolute normalized position, never a relative drop-count on the daemon's wire, so a retry after an unconfirmed attempt converges instead of double-rewinding (§Driver-Level Rollback Mechanics — the Codex driver resolves `targetPosition` to the boundary turn id at each dispatch, so a re-dispatch names the same boundary rather than recomputing a delta; the Claude driver re-composes from the still-bound pre-fork binding, minting a fresh binding at the same target and orphaning, never re-executing, any unacknowledged earlier fork). On daemon restart — or a driver throw/timeout leaving the attempt unconfirmed — every rollback row dispatched-but-unconcluded is reconciled by the [Spec-015](015-persistence-recovery-and-replay.md) resume position-compare **before anything else touches the run**: a provider position at `targetPosition` (or a discovered post-fork binding at it) completes the intervention forward — remaining legs (the recorded `replacementSend` among them wherever the 2026-08-16 amendment's composite staged one, never left unsent), durable outcome, `run.rolled_back`, binding repoint; an unchanged provider position concludes it by the no-rewind path above — with the file-leg recovery intervention reconciled as **at-target**: its carve-out-admitted target equals the pre-dispatch position, so at-target and unchanged coincide by construction, and reconciliation takes the completion branch (remaining legs re-run to the restore fixpoint, durable outcome, forward event at the confirmed position), never the no-rewind conclusion that would strand the partially-restored tree the recovery exists to finish; only after reconciliation is redispatch legal, converging by the same absolute-position rule. Runs whose mode snapshots nothing (`read-only`) and runs whose execution root no longer exists — an ephemeral clone past disposal, a worktree retired by the cleanup sweep — roll back **conversation-only** per Spec-010 §Retention/§Applicability, with the outcome recording the file-leg disposition; a run whose live execution context records a checkout root that no longer exists on disk (nothing left to restore into) takes the same conversation-only path, and the confirmed rollback **releases** that context atomically with the re-open, recording the vanished-checkout disposal cause — converging the arm into this released rootless class rather than minting a third conversation-only class, so the non-resumable rule below governs it structurally (Codex PR #346 round 2; a non-confirming conversation leg releases nothing, and a terminal-source run whose recorded checkout root is gone takes the same branch with its context **already released** — the file-leg-scoped re-acquisition below never fires on a conversation-only branch, so its original release record stands — classified by the same recorded-checkout-root existence check) ([Plan-004](../plans/004-queue-steer-pause-resume.md)'s rollback tasks — campaign B9 — own the typed outcome detail); a **rootless** run re-opened this way is **non-resumable**: `run.resume` against a run whose execution context is released with no existing root is refused with a typed error — nothing recreates a disposed clone or retired worktree, and re-execution takes a fresh run on the same branch through normal admission — so the rolled-back history is queryable and correct without ever activating a run against a nonexistent root ([Run State Machine §Rollback Transitions](../domain/run-state-machine.md#rollback-transitions-campaign-b2)).
- **Compaction-boundary-aware rewind targeting (2026-08-16 amendment).** Rewind-target validation is **compaction-boundary-aware**, and the boundary in question is the **provider's context-window compaction** — never the daemon's audit-log retention compaction. The two are distinct mechanisms with distinct rewind consequences and must not be conflated: the retention pass replaces this system's own event payloads with audit stubs and is governed by the uncompacted-rewind-span check above ([Spec-006 §Compacted Event Format](006-session-event-taxonomy-and-audit-log.md#compacted-event-format)), while a provider-side compaction rewrites the **provider's** live conversation context in place and is recorded here as a `usage.context_compacted` row ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). Let **B** be the greatest originating position among the target run's `usage.context_compacted` rows that are **current** — not already marked superseded by an earlier accepted rewind, so a boundary a prior rollback rewound past never gates a later one. That currency filter is stated for correctness, not because V1 reaches it: while every driver keeps the refusal below, no accepted rewind can supersede a compaction row — a boundary-clear target leaves the row at or below `targetPosition`, and the supersede cutoff marks only `turn > targetPosition`, so both the strictly-above and the equal arm leave it current — and the filter therefore becomes live exactly when a driver's re-verified boundary-crossing semantics does. B is resolved through the same operation-association rule that ranks every content-asynchronous straggler (the absorption bullet above) — the stamped originating position on a late row, the payload's operation linkage on an in-time one, and the row's own timeline slot only as the linkage-less fallback that rule already carries — never as a bare append-order read taken in preference to association. The distinction is **precision, not safety**: no row is ever appended before the operation it reports, so a slot-ranked boundary can only sit at or above the true one, and a slot-ranked B therefore over-refuses and can never silently admit a crossing target. Association is nonetheless required first, because that over-refusal would deny every legitimate rewind across the span between a compaction's originating turn and its late delivery — precisely the span a long-running turn makes widest. Classification is three-valued and **fails closed**:
  - **No boundary.** The run has no current `usage.context_compacted` row, and every target the domain check admits stays admissible. This is the V1 default: no V1 driver ships a compaction operation, so a boundary arises only from provider-native auto-compaction ([Spec-016 §Resolved Questions and V1 Scope Decisions](016-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions)).
  - **Boundary-clear** — `targetPosition` at or above B. The rewound tail lies strictly above the target, so the compaction row is not in it, the row stays current, and the provider legitimately keeps its compacted context: recorded state and provider state agree. The ordinary path applies unchanged. This deliberately includes a target **equal** to B — rewinding to the compaction's own turn boundary keeps the compaction, it does not reverse it.
  - **Boundary-crossing** — `targetPosition` strictly below B, **or** a current `usage.context_compacted` row the association rule resolves to no originating position at all — no stamp, no operation linkage, and no recoverable timeline slot. A row that resolves only through the linkage-less slot fallback is **not** in this arm: it ranks, conservatively and at or above its true position, and is classified on that rank like any other. The supersede cutoff would mark the compaction row rewound, asserting the compaction is undone, while no provider wire offers a compaction-restore operation ([Spec-016 §Resolved Questions and V1 Scope Decisions](016-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions): "neither provider wire exposes a compaction-restore operation" — the recoverability that section grants is an audit and re-derivation guarantee, deliberately not a live-conversation undo), and what a provider rewind actually reconstructs across its own compaction boundary — pre-compaction context, or the compacted summary alone — is exactly the question §Driver-Level Rollback Mechanics leaves open: the Claude leg's probe record already names it explicitly for a fork, and that section's compaction-boundary anchoring rule scopes the ADR-017 re-verification it owes to what **each** provider's rewind reconstructs across its own boundary, so neither leg is verified. Such a target is **refused whole, fail-closed, pre-dispatch**, with no leg applied and a machine-readable cause persisted on the durable intervention row — the same standing-refusal class as the uncompacted-rewind-span check, and for the same reason: admitting it would leave the rendered timeline asserting one context state while the provider holds another. A position-less compaction row classifies as crossing for **every** target of that run, because evidence of a compaction that cannot be proven to sit at or below the target must be treated as sitting above it — exactly as the span check treats a position-less audit stub as a span intersection.

  The classification is **provider-agnostic**, binding both legs identically, because it is a property of compaction being a context rewrite rather than of either wire's rewind mechanism: the Codex leg drops turns, which does not un-compact a rewrite the provider has already applied to its own transcript, and the Claude leg forks at a message address whose reconstructed context across a boundary is unverified. The refusal is **liftable, not permanent**: a driver whose declared capabilities carry re-verified boundary-crossing rewind semantics — verified against the then-installed binary under the same ADR-017 row that governs both rewind mechanisms — admits crossing targets on its own legs, and every other driver keeps the refusal. V1 registers no such capability member: the [Spec-005](005-provider-driver-contract-and-capabilities.md) capability surface carries no boundary-crossing-rewind declaration, so V1 classification reads **no capability input** and the refusal is unconditional on every driver — the lift is a named future Spec-005 amendment that registers the member, never a latent runtime branch waiting on a declaration no shipped driver can make. It follows that "undo the compaction" is not expressible as any admissible target in V1: it is definitionally the boundary-crossing class, never something a target at or above B achieves.

  **Classification is two-point: admission and settlement.** Admission classifies the requested target against the boundary set current at admission; the boundary set can move before the driver's `rollbackTo` confirmation — a `usage.context_compacted` row emitted pre-rewind but delivered late, or one emitted between admission and dispatch — and the in-stream fence bounds exactly how far: the driver's serialized provider connection totally orders event delivery against the `rollbackTo` confirmation (the absorption bullet above), so every boundary row the provider emitted before the rewind is delivered by the time the confirmation arrives. The confirmed floor is therefore **reclassified at settlement against the then-current boundary set** — the same three-valued classification, its third arm now actionable-degraded rather than refusable, because dispatch has happened and no wire un-rewinds: a confirmed floor the settlement classification finds strictly below the then-newest current B settles the intervention **`degraded`** naming the **`boundary-diverged`** disposition — the file leg is skipped fail-closed, a staged `replacementSend` is suppressed (`resendDisposition: 'unapplied'`), the run follows conversation truth `paused` at the confirmed floor, and the forward `run.rolled_back` records the confirmed position with the divergence cause persisted on the durable row. The settled outcome names **both** sides of that comparison — the confirmed floor and the boundary it diverged from — with one narrowing (2026-08-25): where the then-current boundary set's newest row is **position-less** (the unknowable-position shape admission rejects outright, arriving here only between admission and the driver's confirmation), the outcome names the confirmed floor beside an explicitly **null** comparand rather than omitting the member, so a divergence is never reported as an unstated cause and the absent-member reading stays unavailable to a parser. **`run.resume` then holds the line:** resume against a run whose current position sits strictly below the newest current B refuses fail-closed with a typed error — the same standing-refusal family as the rootless-resume refusal, and the backstop for the one window settlement cannot see: a boundary row whose content-asynchronous delivery lags past settlement (the absorption bullet's long-tool span). A boundary-diverged run is therefore **non-resumable in V1** exactly as the rootless class is — its history stays queryable and correct, re-execution takes a fresh run on the same branch through normal admission, and the refusal lifts with the same future capability amendment that lifts the crossing-target refusal (no rollback can move the run forward to clear the boundary — targets sit strictly below the current position by the domain check — so the resume refusal is the class's terminal shape, not a recoverable degrade). The file-leg recovery path cannot re-enter this class either: a recovery composite's equal-target re-issue classifies at admission against the same boundary set and is refused pre-dispatch, its target now sitting strictly below the newest B — consistent rather than a gap, because the divergence settlement skipped the file leg fail-closed, so no half-restored tree exists for recovery to finish.

- **Atomic edit-and-resend (2026-08-16 amendment).** Correcting a previously-sent user message — editing its text and re-dispatching it — is an **optional replacement-send leg on the `rollback` intervention above**, never a new intervention type, wire method, or event type: `applyIntervention('rollback', {targetPosition, replacementSend})`, where `replacementSend` carries the corrected message body. The whole operation is **one intervention**: one durable `interventions` row, one `clientIdempotencyKey`, one `expectedRunVersion` guard evaluated once at admission, one application under the session's append serialization — the same atomicity the pause-first composite already holds, extended by one leg rather than forked into a second mechanism. Every rule the rollback bullet states applies unchanged: the target-position domain check, the compaction-boundary classification, the Spec-010 restore precondition, the uncompacted-rewind-span check, execution-root tenancy, the capability check, confirmed-floor validation, epoch advance, supersede-by-projection, and write-ahead dispatch reconciliation. Five additions are specific to the replacement leg.

  **The replacement leg admits; it does not dispatch — and it admits run-bound.** On a fully-successful rewind (the admission condition below) the corrected message is admitted as a durable queue item against the rewound run through the ordinary participant-send path (the `user.message` row plus queue admission — admission in the participant-send sense of durable acceptance into the queue: the row persists in queue-state **`queued`**, reaching the queue-state `admitted`'s run-bound arm only at the `run.resume` drain's delivery), and the queue item is **durably bound to that run**: admission stamps `queue_items.target_run_id` with the rewound run's id, and a run-bound item is **delivered into its bound run as that run's next provider send on its next `run.resume`** — never converted into a new run, which is what admission means for an unbound follow-up item ([Queue And Intervention Model §State Model](../domain/queue-and-intervention-model.md#state-model) carries both admitted-state arms). The binding is composite-internal in V1: `QueueItemCreate` mints no run-bound items — `target_run_id` is stamped solely by this leg's admission (and by its reconciliation completion), so the queue wire request shape is unchanged. The run lands `paused` at the confirmed position exactly as a bare rollback does — **no auto-resume**, and no second driver-facing call: the composite's only driver contact remains the conversation leg (plus the internal interrupt on the pause-first path a replacement send never takes). The admission and the intervention's terminal settlement commit in **one durable transaction** — the queue item, its `user.message` row, and the intervention's outcome are a single atomic write, never two (the failure-taxonomy bullet below carries the crash consequence). **Admission is conditioned on the composite's other legs, fail-closed:** the replacement admits **only** when the confirmed floor **equals** `targetPosition` (a position-mismatch degrade suppresses it — a corrected message must never be delivered after a boundary the caller did not authorize it to follow), the settlement-time boundary reclassification concludes boundary-clear (a `boundary-diverged` degrade — the compaction bullet above — suppresses it), **and** the file leg completed or the run's mode legitimately takes the conversation-only branch (a `files-unrestored` / `files-partially-restored` degrade suppresses it — delivering the corrected prompt into a half-restored tree would execute the caller's intent against state the rewind never produced); a suppressed replacement stays recoverable on the durable intervention row, and the caller's recovery is the file-leg recovery path re-issued **with the replacement leg re-attached** — guard (ii) is clean, since suppression admitted nothing. Every composite settlement that reaches a terminal result additionally reports the resend outcome **structurally**: the rollback outcome detail carries a `resendDisposition` member (`'admitted'` | `'unapplied'`) — **schema-optional on the wire, producer-obligated at settlement**: with a single exception no member of a rollback result identifies its request as composite (`replacementSend` is request-side and the result does not echo it), so requiredness is not expressible at the strict-parse boundary; the schema parses the member optional on every rollback result **except the composite-only `resend-unapplied` degraded arm — the exception, and the counterexample to that premise, since a bare rollback can never settle there: on that arm requiredness IS expressible, so the schema REQUIREs the member (`'unapplied'`, its only admissible value) rather than admitting a settlement that omits the very leg the disposition exists to report** (2026-08-25 narrowing) — and the daemon's tested producer obligation is that a composite settlement always populates it and a bare rollback settlement never does — so a caller reads the resend outcome from a typed member rather than parsing a disposition taxonomy whose primary job is naming the earliest-failing leg — in V1 the value is determined by the terminal state (`applied` ⇒ `'admitted'`, every `degraded` arm ⇒ `'unapplied'`), and it is carried structurally anyway so the resend outcome stays typed if the admission-condition arms ever widen. The drained replacement's turn additionally executes under the **admitting intervention caller's** effective principal — [Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior)'s turn-scoped effective-principal rule, extended 2026-08-17 to the run-bound replacement send as its intervention-opened arm, durably recorded via the admitting-principal carrier that [Plan-012 §Preconditions](../plans/012-approvals-permissions-and-trust-boundaries.md#preconditions)' carrier box registers — because a corrected prompt authored by an intervening collaborator must not execute with the run initiator's authority. The queued replacement drains on the next `run.resume` of its bound run — necessarily as the **next** send, because guard (ii) below refuses the composite while any earlier pending send exists on the target run: at admission the rewound run's queue holds no older send to deliver first, so the resend-next ordering is enforced by refusal at the gate rather than by a queue-priority mechanism V1 explicitly defers (§Resolved Questions' queue-priority deferral). "Resend" therefore guarantees the corrected message is durably re-submitted and will be delivered next in order — never that it is already on the provider wire when the intervention settles. Anything else would contradict the rollback bullet's two standing rules (a confirmed rollback lands `paused`; the composite never auto-resumes) for the sake of one leg.

  **The caller's text is durable before anything destructive runs — and it rides the PII envelope, never the plaintext payload.** (The 2026-08-18 amendment generalizes this paragraph's split to **every** participant-authored intervention body — steer directive text included, per the at-rest-split bullet below — of which the `replacementSend` body specified here is the composite's instance; the mechanism, the erasure parity, the retention bound, and the export leg are identical for each.) The accepted intervention row is durable **before** driver dispatch (the rollback bullet's write-ahead dispatch-intent marker), and the `replacementSend` body is persisted **on that row through the same participant-keyed PII split the ordinary `user.message` path applies** ([Spec-006](006-session-event-taxonomy-and-audit-log.md)'s `splitPii` discipline, Plan-006's `PiiEncryptor` seam): the corrected text encrypts into the row's PII-bearing field (`interventions.pii_payload`, stamped `interventions.pii_participant_id` = the requesting participant), while the plaintext `interventions.payload` carries only the non-PII rollback members and the replacement leg's presence — a participant message body never lands plaintext at rest here when the event path it replaces would have encrypted it. Erasure parity is structural, not procedural: crypto-shred is participant-key deletion (Plan-022 Path 1), so the key deletion that shreds the `user.message` event copy shreds this copy identically — no second erasure path exists to forget. The corrected text therefore survives every failure arm including a daemon crash mid-composite, recoverable under the requester's live participant key. V1 has no daemon-side composer-draft surface to stage it in — daemon-side draft persistence is deferred past V1 and `human_phase_form_state` ships empty ([Spec-017 §State And Data Implications](017-workflow-authoring-and-execution.md#state-and-data-implications)) — which is precisely why the intervention row, already the reconciliation source, carries it. The copy is retention-bounded and export-registered like the event copy it mirrors ([Spec-022 §PII Data Map](022-data-retention-and-gdpr.md#pii-data-map) carries the row): past the [Spec-022](022-data-retention-and-gdpr.md) 90-day full-retention bound the daemon's retention pass NULLs `interventions.pii_payload` while retaining the non-PII intervention audit record for the row's lifetime — a plain NULL-out, safe here where the `session_events` copy must instead compact to an audit stub, because no digest, signature, or anchor binding attaches to the intervention row's ciphertext — and the participant data-subject export (`GET /participants/{id}/export`) includes the decrypted replacement-send bodies of intervention rows stamped with the participant, since text that exists only on a refused or suppressed intervention row is still that participant's authored content.

  **Four structural refusal guards, each fail-closed at admission, pre-dispatch, and whole-intervention.** (i) **No active turn.** The pause-first path does **not** extend to a replacement send: a `running` target is refused outright rather than paused first, because the message being replaced is still being answered, and silently pausing a live turn to rewrite its prompt substitutes an edit for a decision the caller never made. Bare rollback keeps pause-first unchanged; this carve-out is scoped to the replacement leg. (ii) **No pending send.** A run holding **any earlier pending send** refuses the composite, in either of its two forms: an accepted send whose provider delivery is not yet confirmed — the window between the admitted `user.message` row and the provider's `user_text` wire echo folding into it as delivery confirmation, where the target cannot be validated against a turn boundary the provider has not yet acknowledged — or an **undrained queued send** admitted before the composite, which ordinary FIFO would deliver ahead of the replacement and thereby make the corrected message not the next send, the very promise the leg exists to keep. Front-inserting the replacement ahead of the older item is not an admissible fix: that is a queue-priority override, which V1 explicitly defers (§Resolved Questions' queue-priority deferral). The pending-send order is not the composite's to reorder — the caller's remedy is to cancel the queued items (`QueueItemCancel`) or let them drain, then re-issue; the queued-send arm of this refusal lifts if and when V1.1 priority overrides land. (iii) **A participant-authored target of this run.** `targetPosition` must name a turn boundary opened by a participant-authored `user.message` of the target run; a boundary opened by any other origin has no participant send to replace. An orchestration-authored boundary — a workflow phase's input or an orchestrated child run's ([Spec-016](016-multi-agent-channels-and-orchestration.md), [Spec-017](017-workflow-authoring-and-execution.md)) — therefore refuses the composite, since rewriting one would rewrite a phase input outside the workflow's own authoring surface. Bare rollback of such a boundary stays admissible; only the replacement leg is refused. (iv) **A resumable target.** The leg's whole promise is delivery on the bound run's next `run.resume`, so a target run that can never resume is refused: the rollback bullet's **rootless** class — a run whose execution context is released with no existing root (a disposed ephemeral clone, a retired worktree), which that bullet already marks non-resumable with a typed refusal, together with an execution context — live, which the confirmed rollback itself releases into that class, or already released, a terminal source arriving in it — whose recorded checkout root no longer exists on disk (admitting its replacement would settle a send onto a run the same settlement just made — or found — non-resumable — Codex PR #346 round 2) — could hold a queued replacement only as a dead letter, so the composite refuses it whole rather than admitting a send no resume will ever drain. Bare rollback of a rootless run stays admissible (conversation-only, queryable history); only the replacement leg is refused — and the caller's path to re-execution is the one the rollback bullet already names: a fresh run on the same branch through normal admission, carrying the corrected text as its input. **Which guard refused is reported structurally (2026-09-06 amendment).** A refusal raised by any of the four settles `rejected` carrying, beside the machine-readable `rejectionReason` cause, the **closed-union `rejectionGuard`** member naming the guard — `'no-active-turn'` | `'no-pending-send'` | `'participant-authored-target'` | `'resumable-target'`, the four names above kebab-cased with the leading article dropped, each naming the condition its guard requires rather than restating the failure. The member is **arm-scoped** (the `rollback` `rejected` arm, never the shared response base, since only a composite raises these guards) and, within that arm, **schema-optional and producer-obligated** exactly as `resendDisposition` is and for the same reason — no member of a `rejected` response identifies its request as composite, so requiredness is not expressible at the strict-parse boundary — with the daemon's tested obligation being that a guard refusal always populates it and every other refusal family never does — the **eight** [Queue And Intervention Model §Intervention State Transition Table](../domain/queue-and-intervention-model.md#intervention-state-transition-table) admits for a rollback: capability, authorization, target-position domain, compaction-boundary, incompatible target run state, the Spec-010 restore precondition, uncompacted-rewind-span, and execution-root `busy`. `rejectionReason` is unchanged: the typed member exists so a client renders a per-guard remedy by an **exhaustive** switch, which its sibling's open vocabulary cannot support at any amount of care. A fifth guard is an amendment of this paragraph and of that union together, never a free string; and the union is a wire vocabulary only — the eligibility predicate stays the daemon's, and any client-side projection of it remains fail-closed and never a second source of eligibility truth. **The literal is durable, so the replay contract holds across a restart.** The daemon persists the refusing guard on the intervention's own row beside the machine-readable cause, and an idempotent replay of the same `clientIdempotencyKey` returns a `rejectionGuard` **equal to the recorded one** — a daemon restart between the refusal and the replay included. It is stated because it does not follow from the sibling: the recorded outcome of a `rejected` intervention is reconstructed from the durable row (the wire contract carries no `result` on that state), and `rejectionReason`'s vocabulary is open and unenumerated, so the literal cannot be recovered from it without the match against an unpublished value set this member abolishes. A replay may therefore never omit the member, and may never re-derive it by re-evaluating the guards — the run has moved on, and re-evaluation would answer about the run's state now rather than about the refusal that was recorded.

  **The failure taxonomy is three-valued, and the caller's text is recoverable in every arm that reaches intervention creation.** **Refused** — any pre-dispatch validation fails: nothing dispatched, no leg applied, the intervention settles `rejected` (or `expired` on a guard mismatch), and the caller still holds its own text. One refusal family settles with **no intervention row at all**: a cross-node composite denied by the target owner's approval or rejected by the pre-approval role check is refused before intervention creation (§Interfaces And Contracts' cross-node rule — no intervention state, no `InterventionResult`), so the durable-row guarantees of this bullet do not attach there; the refusal returns on the wire and the caller-side surface that authored the text (the CLI invocation, the composer) remains its holder. **Committed-then-failed** — the conversation rewind is confirmed but the replacement send is not admitted, in either of two shapes: an admission-condition suppression (the admits-paragraph above — the disposition then names the earlier-failing leg, precedence following leg order: `boundary-diverged`, then position-mismatch, then the file-leg arms), or an admission that itself fails after a fully-successful rewind — the **`resend-unapplied`** disposition, reserved for exactly that arm — which is therefore the one degraded disposition that **displaces a completed file restore** rather than following a file leg that was skipped fail-closed or refused pre-mutation, so it reports that restore with the same two REQUIRED enumerations `files-restored` carries (`overwrittenIgnoredPaths` and `divergentGitlinks`, present-and-empty when nothing was overwritten or diverged — including on the conversation-only branch, the reading two empty arrays already carry on `files-restored`), keeping [Spec-010 §Turn-Boundary Snapshots](010-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)' never-silent mandate intact across the displacement (2026-08-25 narrowing). Either way the intervention settles `degraded` carrying `resendDisposition: 'unapplied'`, the run lands `paused` at the confirmed position with `run.rolled_back` appended exactly as a bare rollback does (run state follows the confirmed conversation leg), and the text stays recoverable on the durable intervention row under the requester's participant key. **Transport-lost** — the outcome is unknown to the caller through a driver throw, timeout, or daemon restart: the existing write-ahead reconciliation resolves it, and the [Spec-015](015-persistence-recovery-and-replay.md) position-compare's completion branch drives the staged `replacementSend` forward among the remaining legs — concluding a confirmed rewind without re-dispatching it would strand the very text this leg exists to preserve. The completion branch admits and settles in the **same single transaction** the live path uses, which is what makes recovery crash-idempotent: an intervention observed unconcluded at restart **proves** no admission occurred (the two outcomes cannot diverge — there is no window between an admitted replacement and an unsettled intervention for a crash to land in), so reconciliation never re-admits a message the run already holds, and replaying the same `clientIdempotencyKey` returns the recorded outcome rather than sending twice.

  **Superseded marking applies solely on the accepted `run.rolled_back` boundary.** It is driven by that event's confirmed position and by nothing else — not by the composite's admission, not by its dispatch, and not by the replacement send. A client MAY dim the turns a pending composite would rewind, and MUST NOT remove or renumber them before the boundary appends: a composite whose conversation leg does not confirm applies no rewind at all (the no-rewind path above), so an optimistic truncation would delete history the run still holds (§Implementation Notes' optimistic-affordance rule). Because the replacement send appends **after** the boundary in the session's append order, a consumer observes rewind-then-resend from ordering alone, and the composite needs no linkage field on either row to be rendered correctly.

- **Every accepted intervention durably records the principal that admitted it (2026-08-18 amendment).** The daemon resolves the caller's **transport-authenticated** identity at acceptance and persists it on the intervention row, alongside a daemon-resolved `origin` discriminator naming which admission path produced the row. Resolution follows the three mechanisms the approval pipeline's shipped approver identity already uses ([Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior)): the daemon's node-owner participant identity on the local socket, the verified PASETO `sub` on authenticated surfaces, and `caller_token.sub` on the [Spec-024](024-cross-node-dispatch-and-approval.md) cross-node arm. The wire `initiatorId` is **never** the source — it stays routing/audit metadata per [ADR-011](../decisions/011-generic-intervention-dispatch.md), and a request whose body actor disagrees with the verified identity is refused through the existing `auth.principal_mismatch` error, never trusted and never silently normalized. `origin` is `'participant'` for a request admitted over an identity-carrying transport and `'system'` for the in-process orchestration entrypoint that sits below the wire authorization boundary and carries no participant at all; the principal is **required exactly on the participant arm and forbidden on the system arm**, enforced as a storage constraint so a participant-origin row can never persist unidentified and a system-origin row can never smuggle an identity in. The discriminator is resolved, not inferred: a client-supplied `initiatorId`'s absence is not evidence of a system admission. Recording the principal on the row — rather than reconstructing it later from run history — is what makes it **replay-stable**, since a run accumulates interventions over its life and history offers no single answer to which one authorized a given unit of work. A queue item admitted by an intervention carries a **row-anchored linkage** to that intervention for the same reason, so its drain resolves one admitting row rather than scanning a history. Producers write the stamp inside the transaction that accepts the intervention — for the edit-and-resend composite, the single durable transaction that already commits the admission and the settlement together, never a second write that a crash could separate. Consumers are the authorization path: a turn opened by an accepted intervention adjudicates under the recorded principal ([Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior)'s turn-scoped resolution, covering both the steer-opened and replacement-send-opened arms), and an unresolved principal adjudicates as a **deny**, never as the run initiator.
- **Participant-authored queue-item bodies rest encrypted, exactly as intervention bodies do (2026-08-18 amendment).** A queue item's participant-authored send body is persisted through the same participant-keyed PII split this spec already specifies for intervention bodies: the text encrypts into the item's PII-bearing field under the authoring participant's key with that participant stamped as the owner, while the plaintext payload retains only the non-PII members. Before this rule the queue row held the body in plaintext while the `user.message` event copy of the same text was already encrypted — one send, two at-rest copies, one of them unprotected and, worse, unreachable by erasure: no column on the queue row named a participant, so the [Spec-022](022-data-retention-and-gdpr.md) fan-out had no selector for the table at all. The owner stamp **is** that selector, and same-key parity makes erasure structural: the one participant-key deletion that shreds the event copy shreds the queue copy in the same act, with no second erasure path to forget. Content authored by orchestration rather than by a participant — a workflow phase input, an orchestrated child-run prompt — stays plaintext with both fields unset: it is session work product rather than participant PII, and the system admission path holds no participant key to encrypt under. Queue rows remain **durable and never-evented**, drained but never deleted and canonical for audit and replay; this rule changes what a row stores at rest, not its lifecycle. Queryability is unaffected because every field admission and drain select on — state, priority, run binding, channel, session — is its own column and none of them is content.

## Default Behavior

- The default follow-up behavior while a run is active is `queue`.
- Queue ordering default is FIFO within the target scheduling scope.
- If a driver does not support steer natively, the intervention must be rejected or degraded to a new queue item. Pause does not require driver support — it is an orchestration-layer run-control mutation (`run.pause` / `run.resume`), handled entirely by the daemon (interrupt + persist + queue a resume) and **not** dispatched through the driver-facing `applyIntervention` path that steer/interrupt/cancel follow ([ADR-011](../decisions/011-generic-intervention-dispatch.md); the driver never needs to know about pause — see [Queue And Intervention Model](../domain/queue-and-intervention-model.md)).

## Fallback Behavior

- If `steer` is requested against a run that cannot accept it, the system must either reject the intervention or explicitly degrade it to a new queue item.
- If a paused run cannot be resumed because driver state is lost, the system must transition it through recovery logic and then to `failed` or `interrupted`; it must not pretend the same run resumed.
- If queue persistence is temporarily unavailable, the system must reject new queue creation rather than silently storing queue state only in client memory.

## Interfaces And Contracts

- `QueueItemCreate`, `QueueItemList`, and `QueueItemCancel` must operate against runtime-owned durable state.
- `InterventionRequest` must include target run id, intervention type, and a **mandatory** version guard (`expectedRunVersion`). The guard is **fail-closed**: the comparand is required on every intervention, and an absent comparand is **rejected**, never applied — an optional guard would let a caller bypass stale-replay protection by omitting the field (Plan-004 D-004-2). `expectedRunVersion` is compared against the target run's `runVersion` — an **any-run-progression counter** that increments on every run progression, applied interventions included (not only `run.*` state-machine transitions), so two steers racing on a still-`running` run cannot both pass undetected (Plan-004 D-004-1). `runVersion` is the run aggregate's optimistic-concurrency token, distinct from the immutable `EventEnvelope.version` wire-contract field ([Spec-006 §EventEnvelope Version Semantics](006-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics)). Payload fields vary by type: `steer` includes `expectedTurnId`, `content`, and optional `attachments`; `interrupt` and `cancel` include optional `reason`; `rollback` (campaign B2) includes a **mandatory** `targetPosition` — the normalized session position (a `number`, [Spec-005](005-provider-driver-contract-and-capabilities.md) `RollbackToParams.position` vocabulary) of the turn boundary to rewind to — plus an **optional** `replacementSend` (2026-08-16 amendment) carrying the corrected message body of the atomic edit-and-resend composite (§Required Behavior): absent on a bare rollback, and its presence is exactly what selects the composite's four additional refusal guards, its admission-conditioned resend with the structural `resendDisposition` result member, and its `resend-unapplied` disposition, so no separate discriminator is required. The matching optional member on the wire union's `rollback` arm is a named [Plan-004 §Preconditions](../plans/004-queue-steer-pause-resume.md#preconditions) merge prerequisite against [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) rather than an edit carried by this amendment (registered 2026-08-25 as that arm's optional `replacementSend` member — [API Payload Contracts §Plan-004 — Queue Steer Pause Resume](../architecture/contracts/api-payload-contracts.md#plan-004--queue-steer-pause-resume) — so the named prerequisite box now reads `- [x]` and this sentence records a discharged obligation rather than an outstanding one; the V1 control set is unwidened, and the three narrowings that registration surfaced — the `resend-unapplied` arm's REQUIRED `resendDisposition`, that arm's two displaced never-silent restore enumerations, and the nullable settlement comparand — are folded into §Required Behavior above under the 2026-08-25 amendment blockquote, with both Status rows flipping and restoring `approved` in that same swap). Every intervention request additionally carries a **mandatory** requester-generated `clientIdempotencyKey` (UUID) — the second, orthogonal guard ([Spec-005 §Required Behavior](005-provider-driver-contract-and-capabilities.md#required-behavior), campaign B3): `expectedRunVersion` defeats stale replays of outdated intent, the key defeats duplicate applications of the same intent (replay-or-conflict, `intervention.idempotency_conflict`). The replay-or-conflict body comparison is **PII-safe by construction** on the composite: whether a reused key carries the same or a differing `replacementSend` body is decided by decrypting the stored envelope under the requester's live participant key (the injected `PiiEncryptor` seam) and comparing plaintexts — never by comparing ciphertexts (the envelope is nonce-randomized, so equal plaintexts encrypt unequal) and never by persisting a plaintext digest beside the envelope (a retained digest of erased text would survive [Spec-022](022-data-retention-and-gdpr.md) Path-1 crypto-shred as a guessing oracle) — and a stored body rendered undecryptable by participant-key shred settles the reuse fail-closed as `intervention.idempotency_conflict` ([Queue And Intervention Model](../domain/queue-and-intervention-model.md) owns the canonical rule). See [Queue And Intervention Model](../domain/queue-and-intervention-model.md) for canonical payload shapes.
- `InterventionResult` must distinguish the 6 canonical intervention states: `requested`, `accepted`, `applied`, `rejected`, `degraded`, and `expired`. A version guard mismatch produces `expired`. An authorization failure produces `rejected`.
- Intervention dispatch uses `applyIntervention` (see [Spec-005](../specs/005-provider-driver-contract-and-capabilities.md) and [ADR-011](../decisions/011-generic-intervention-dispatch.md)), which routes to the appropriate driver-specific handler based on intervention type and declared capabilities. The Cedar `principal` for authorizing an intervention is the caller's verified participant identity: the verified PASETO `sub` on every identity-carrying transport (control-plane, relay, and the cross-node dispatch path, where the target binds the principal to the verified `caller_token.sub` per [Spec-024](024-cross-node-dispatch-and-approval.md)'s envelope rules), and — on the daemon's local socket, which carries no PASETO token — the daemon's node-owner participant binding resolved through the Plan-018-gated credential/identity provider seam (a named [Plan-004 §Preconditions](../plans/004-queue-steer-pause-resume.md#preconditions) prerequisite); `initiatorId` and any body-level actor fields are informational only. See [API Payload Contracts §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model). The Cedar **action** for a run-control intervention is `Action::"intervene"` on the target `Run` resource, with the run's **hosting node** carried in the request context. Authorization is evaluated against session membership role — never against run authorship — so a participant holding `collaborator` or `owner` may intervene on a run another participant authored ([Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior) owns the rule); a non-local hosting node **adds** the target-node-owner approval requirement (an approval in the `tool_execution` category per [Spec-024](024-cross-node-dispatch-and-approval.md)) rather than substituting for the role check, so cross-node intervention is a request, never standing authority. The same adjudication governs the orchestration-layer `run.pause` / `run.resume` run-control mutations even though they never ride `applyIntervention` (they are daemon-handled orchestration verbs holding no `InterventionType` membership): their handlers evaluate the identical `Action::"intervene"` request — same `Run` resource, same hosting-node context, same role-not-authorship rule, same cross-node node-owner approval leg — before composing any run-state mutation, per [Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior)'s governed-identically rule, so the dispatch-path split is transport plumbing, never an authorization boundary.
- **Rollback routing (campaign B2).** `rollback` is a full intervention on the client→daemon wire — the `InterventionRequestPayload` union in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) carries a `rollback` member, and the request flows through the same authorization, `expectedRunVersion` guard, idempotency ledger, and `InterventionResult` lifecycle as every other type. At the driver boundary it does **not** ride `ApplyInterventionParams`: the conversation leg dispatches through the driver's dedicated, capability-gated `rollbackTo` parity operation ([Spec-005 §Interfaces And Contracts](005-provider-driver-contract-and-capabilities.md#interfaces-and-contracts), campaign B3) — `RollbackToParams {sessionId, position, bindingId}` returning `DriverRollbackResult` (`applied {sessionPosition, bindingId?}` | `degraded {fallbackAction?}`). The `bindingId` leg key is **daemon-resolved at dispatch** — run→bindings is 1:many, so the daemon names the run's live provider binding exactly as it does for goal delivery; client rollback payloads never carry it (clients address the run), and a fork-composed rollback repoints the live binding via the result's `bindingId`. The optional `replacementSend` of the 2026-08-16 amendment's edit-and-resend composite never crosses this boundary at all: it is daemon-held state — persisted on the write-ahead intervention row through the participant-keyed PII envelope (§Required Behavior's at-rest split), then admitted through the ordinary participant-send path once the conversation rewind confirms — so `RollbackToParams` is unchanged by the composite and the driver leg cannot distinguish a bare rollback from one carrying an edit ([Queue And Intervention Model §Field-Level Consistency](../domain/queue-and-intervention-model.md#field-level-consistency) carries the same non-forwarding rule). A driver whose capabilities do not declare rollback support produces a **static refusal** (`driver.capability_unsupported`, the [Queue And Intervention Model §Driver Result To Lifecycle Mapping](../domain/queue-and-intervention-model.md#driver-result-to-lifecycle-mapping) no-documented-fallback carve-out) — there is no orchestration-layer emulation, because a synthesized rollback (replaying a truncated history into a fresh run) would violate same-run resurrection and silently fork budgets and supersede-marking.
- See [Queue And Intervention Model](../domain/queue-and-intervention-model.md) § Boundary: Interventions vs Interactive Requests for the steer/respondToRequest distinction.
- `RunStateChange` events must reflect the canonical state machine defined in `../domain/run-state-machine.md`.

## State And Data Implications

- Queue items require durable storage and ordering metadata.
- Interventions require durable audit records even when they fail.
- Blocked states must remain associated with the same run id and same event lineage.
- **Intervention audit records carry an identity, not just an outcome (2026-08-18 amendment).** The durable intervention record must hold the daemon-resolved admitting principal and the `origin` discriminator beside the outcome fields, with the storage layer enforcing that the two agree — principal present exactly on the participant arm. A queue item admitted by an intervention must hold a durable reference to that intervention row, so the drained turn's authority is resolvable from the item alone. Neither field is client-writable.

  **The resolved authority is published per turn, not left to be re-derived (2026-08-26).** Recording the admitting principal on the intervention row makes the authority _resolvable_; it does not make it _reachable_ by a consumer that meters a turn rather than admitting one. At every turn boundary the run engine opens, it therefore resolves that turn's effective principal — the admitting participant of the intervention that opened the turn (a steer, or a rollback carrying `replacementSend`), otherwise the participant who started the run, otherwise the `system` arm where no participant caused it — and publishes it as an **immutable per-turn scope** on the run's execution context, where the driver's usage normalizer reads it and carries it onto the metered row ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). Per-turn and immutable are both load-bearing: the normalizer stamps from the scope **bound to the turn whose stream produced the frame**, never from a mutable "current turn" read when the frame arrives, because a metered row for one turn routinely lands after the next turn has opened and a read-at-emission stamp would attribute that spend to whoever caused the following turn. A published scope is never mutated; a new turn mints a new one. The resolution rule itself is unchanged and stays owned by [Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior); what this adds is the obligation to publish it, so that no downstream fold has to recover the identity by ordering metered rows against turn-boundary events — the derivation the [api-payload-contracts.md §Authenticated Principal](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model) class rule forbids. The value is published and never emitted by this spec's surface: it mints no event, no column, and no wire member here.

- **Both durable tables store participant-authored bodies encrypted and owner-stamped (2026-08-18 amendment).** Intervention rows and queue rows each require a participant-keyed ciphertext field and a participant owner stamp beside their plaintext payloads. The owner stamp is what makes each table addressable by the [Spec-022](022-data-retention-and-gdpr.md) erasure and export paths; a table holding participant content with no participant column is not erasable, which is the defect this closes for queue items. Both fields are nullable — orchestration-authored rows legitimately carry neither.

## Driver-Level Steer Mechanics

- **Codex driver**: native `turn/steer` API — content is injected mid-conversation as a new user turn. The active generation is interrupted and the model continues from the steer content.
- **Claude driver**: no native steer support — degrades to queue + interrupt. The orchestration layer: (1) interrupts the active run (transitioning it to `interrupted`), (2) creates a new queue item with the steer content, (3) admits the queue item as a new run. The conversation history is preserved.
- **Generic driver fallback**: same as Claude (queue + interrupt).

### Steer Content Injection Point

- For native steer (Codex): content appears as a new user message in the conversation, immediately after the point of interruption. The model sees it as if the user sent a follow-up.
- For degraded steer (queue + interrupt): content becomes the initial message of the new run. Previous conversation history is loaded from the session event log.
- In both cases: steer content is marked with `source: 'steer'` in the event payload so the timeline can distinguish it from normal user messages.

The typed payload shapes for steer, interrupt, cancel, and rollback interventions are defined in [Queue And Intervention Model](../domain/queue-and-intervention-model.md) and verified against API contracts in that document's Field-Level Consistency section.

## Driver-Level Rollback Mechanics

- **Codex driver**: native, and **rebound 2026-08-26** from `thread/rollback` to `thread/fork` at an inclusive `lastTurnId` boundary. The re-verification this bullet previously deferred has been performed and the answer changed the binding: the deprecation now lives in the generated type itself, so `thread/rollback` is not a method V1 may build on (primary source: [Codex Wire Reference §`thread/rollback`](../reference/provider-wire/codex.md#threadrollback--session-time-travel-conversation-leg), with the successor recorded in the same file). Neither verb reverts local file changes — file restore is always the daemon's leg, below. The mechanism change is real, not cosmetic: a fork mints a **new thread**, so the driver resolves the daemon's absolute `targetPosition` to a **boundary turn id** rather than to a drop-count and re-points the run's live provider binding at the forked thread in the same operation, leaving the pre-rewind thread intact and unreferenced. Retry convergence is thereby structural rather than arithmetic — re-forking from the same boundary is idempotent where a repeated drop-count would compound (§Required Behavior's reconciliation rule). The driver-side contract is [Spec-005 §Parity Capability Mechanism Grades](005-provider-driver-contract-and-capabilities.md#parity-capability-mechanism-grades); the [ADR-017 Decision Log](../decisions/017-shared-event-sourcing-scope.md#decision-log) MUST is discharged for this leg.
- **Claude driver**: native composed — `--resume-session-at <message-uuid>` + `--fork-session`, with the driver running `--replay-user-messages` so message-UUID rewind targets appear on the wire; the driver owns the normalized-position → message-UUID translation. `--resume-session-at` is binary-probe-only — absent from the live CLI reference; the probe record and docs-gap analysis are checked in at [Claude Code Wire Reference §Gaps recorded](../reference/provider-wire/claude.md#gaps-recorded), version-pinned with provenance in that doc — and MUST equally be re-verified against the then-installed binary before load-bearing use (same ADR-017 row), that re-verification covering one question the probe record leaves open — what a fork carries across a provider-side context-compaction boundary (whether the forked session reconstructs pre-compaction context or resumes from the compacted summary alone), the case a rewind target older than a compaction boundary lands in. The provider-level fork is **beneath the binding, not a run fork**: the daemon's run aggregate persists (same run id, same `runVersion` lineage, same budgets) and the driver mints a new binding for the same run — the established relaunch pattern ([Spec-005](005-provider-driver-contract-and-capabilities.md) `DriverResumeResult.bindingId`), **registered through the same runtime-binding write seam before the result returns**: the new binding row (provider-owned `resume_handle` + runtime metadata, the `runtime_bindings` model) is durable before `applied` is reported, and `applied.bindingId?` is the store-minted surrogate of that registered row — never itself a resume handle — so a repointed run remains `resumeSession`-able across a daemon restart; the daemon persists the surrogate as the run's live binding so every later per-binding operation (goal delivery, resume, steer) targets the post-fork session, never the dead pre-fork one; under the 2026-08-26 Codex rebinding both V1 legs mint one, so the field is present on each — it stays optional for a future in-place mechanism, not for either shipped leg. A retried compose after an unconfirmed attempt operates on the still-bound pre-fork binding and mints a fresh binding at the same target — an unacknowledged earlier fork is orphaned provider-side, never re-executed, because no daemon binding ever points at it (§Required Behavior's reconciliation rule). §Required Behavior's same-run resurrection invariant holds.
- **File restore** is the daemon's turn-snapshot git leg ([Spec-010 §Turn-Boundary Snapshots](010-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots), campaign B21) — never the driver's, on either provider.
- **Confirmed floor**: `DriverRollbackResult`'s `applied` variant carries a REQUIRED driver-confirmed `sessionPosition` — the new authoritative recovery floor consumed by the [Spec-015](015-persistence-recovery-and-replay.md) resume position-compare (campaign B5/B14) — plus the optional `bindingId` above (present exactly when the mechanism minted a new binding). A successful rollback without a confirmed floor is structurally inexpressible, and the daemon validates the confirmed floor **equals the requested `targetPosition` before the file leg**, after first applying the same domain validation as the request target (an invalid or no-op confirmed floor is a no-rewind failure — never an event — except the file-leg recovery convergence, where the no-op confirmation at the carve-out-admitted current-position target is the confirmed floor and the restore proceeds; §Required Behavior) — a valid-but-different floor skips the restore fail-closed and ends the intervention `degraded` naming the position-mismatch disposition, with the forward event recording the confirmed position (§Required Behavior). Resolving `applied` also **quiesces the pre-rollback stream**: after `rollbackTo` resolves, the driver delivers no further run-lifecycle events from the pre-rollback execution on the run's binding (a superseded pre-fork binding delivers nothing at all) — implementable without a wire token because the driver owns one serialized provider connection, so the `rollbackTo` confirmation is an in-stream fence ordering the epoch boundary against event delivery; any straggler that slips through is absorbed by §Required Behavior's execution-epoch gate, never appended.
- **Timeline presentation**: rolled-back turns are never deleted from `session_events`; projections mark them superseded (turn > post-rollback position of the accepted `run.rolled_back` event) so clients render the rewound history distinctly rather than dropping it. Late pre-epoch non-lifecycle appends carry §Required Behavior's durable epoch stamp (the `sourceEpoch` + `sourcePosition` carrier pair, [Spec-006 §Event Type Enumeration](006-session-event-taxonomy-and-audit-log.md#event-type-enumeration)), so replay ranks them with their source epoch — never by append order — and the supersede marking survives projection rebuilds.
- **Compaction-boundary anchoring (2026-08-16 amendment).** Wherever a driver's declared capabilities admit a boundary-crossing rewind at all (§Required Behavior's compaction-boundary classification), that driver's normalized-position → provider-address translation MUST anchor at the boundary's **pre-compaction** leaf, not at whatever address the post-compaction prelude chain resolves to. The failure this closes is one of ordering, not arithmetic: a provider-side compaction writes its effects — the boundary marker, the generated summary, and any caveat the provider injects — as ancestors of the invoking turn's own echo, so a translation that anchors on that echo's immediate parent lands **inside** the compaction's own prelude and hands the provider its compacted context back, while this system has already marked the boundary rewound. This spec binds the anchoring rule directly — its authority is the ordering hazard just stated, not any external implementation, and each driver's conformance is established by the ADR-017 re-verification against the then-installed provider binary that this section already owes (the first-party evidence path; the 2026-08-12 reference-runtime parity survey's first-party observation of the same hazard corroborates the shape but is not its source of authority): anchor at the last address preceding the boundary, taken **only** when every intervening address between the requested target and the boundary is a compaction-prelude address; where the chain is off-pattern, degrade to the ordinary anchor rather than guessing; and bound the ancestor walk so a malformed or cyclic chain cannot spin the translation. The daemon never re-derives a target from the driver's anchoring — the driver reports whatever floor it actually reached and §Required Behavior's confirmed-floor validation adjudicates it unchanged, so an anchoring that lands anywhere other than the accepted `targetPosition` surfaces as the ordinary position-mismatch degrade rather than as a silent divergence. Until the ADR-017 re-verification this section owes settles what each provider's rewind reconstructs across its own compaction boundary, no V1 driver declares the capability and the classification refuses every boundary-crossing target: this rule is the contract that re-verification is verifying **against**, not a claim that either wire already satisfies it.

## Implementation Notes

- Queueing and intervention logic must live in the daemon or equivalent runtime authority, not in the currently open client.
- UI affordances may be optimistic, but canonical run state changes must come from runtime truth.
- Capability-aware controls are required so unsupported operations do not masquerade as working.
- Pause is an orchestration-layer construct. The daemon interrupts the active run, persists conversation history and run state to local SQLite, and queues a resume. The driver never needs to know about pause.

## Pitfalls To Avoid

- Using client memory as the queue of record
- Calling reread or reattach semantics `resume`
- Treating waiting states as paused states
- Appending a late provider run-lifecycle event to a terminal run's timeline (the absorption rule exists precisely for this window) — or, inversely, absorbing non-lifecycle events the rule never covered (late usage telemetry is billable and must append) — or keying absorption on current run state alone, which misses pre-rollback stragglers arriving after a rollback re-opened the run (the epoch gate exists for exactly that arrival order)
- Treating rollback as log truncation — the authoritative log never truncates; rollback is a forward `run.rolled_back` event plus projection-level supersede marking
- Conflating the daemon's audit-log retention compaction with the provider's context-window compaction — they are different mechanisms with different rewind consequences, gated by different checks (the uncompacted-rewind-span check and the compaction-boundary classification respectively), and a rewind cleared by one is not thereby cleared by the other
- Reading a compaction boundary off the arrival slot of its `usage.context_compacted` row without first attempting operation association — the error direction is conservative rather than unsafe (nothing is appended before the operation it reports, so a slot-ranked boundary sits at or above the true one), which is exactly why the mistake survives testing: it never admits a crossing rewind, it silently refuses every legitimate one in the span between the compaction's originating turn and its late delivery. Reading the same conservatism the other way is the genuinely unsafe twin — concluding that because slot-ranking cannot admit a crossing target, an unresolvable row may be skipped rather than refused
- Truncating or renumbering the rendered timeline when an edit-and-resend composite is admitted or dispatched rather than when its `run.rolled_back` boundary is appended — a composite whose conversation leg never confirms applies no rewind at all, so the optimistic truncation would delete history the run still holds
- Admitting the replacement send after a degraded arm — a position-mismatch, `boundary-diverged`, or file-leg-failed settlement must suppress the resend (`resendDisposition: 'unapplied'`), never deliver the corrected message after a boundary, or into a tree, the caller did not authorize it to follow
- Comparing idempotency-key reuse bodies by ciphertext or by a persisted plaintext digest — the PII envelope is nonce-randomized, so ciphertext comparison always conflicts, and a retained digest of erased text survives crypto-shred as a guessing oracle; the only admissible comparison is decrypt-and-compare under the requester's live key, failing closed to `intervention.idempotency_conflict` when the key is shredded

## Acceptance Criteria

- [ ] Follow-up work while a run is active is durably queued by default.
- [ ] Pause (orchestration-layer interrupt + persist + queue resume) and resume operate on the same run id and same run history.
- [ ] Unsupported intervention requests result in explicit `degraded` or `rejected` outcomes rather than silent behavior changes.
- [ ] A provider run-lifecycle event arriving for a run already terminal never appends a `session_events` row and never advances `runVersion`: a terminal-class straggler no-ops in the at-most-once terminal emitter; a non-terminal lifecycle straggler surfaces only as the `run.late_event.absorbed` OTel diagnostic; a run-lifecycle event sourced from the pre-rollback execution epoch, arriving after a rollback re-opened the run, is absorbed identically — never appended against the new epoch; and during a pause-first rollback composite, run-lifecycle events sourced from the internally-interrupted execution — arriving after the pause, before the `rollbackTo` confirmation — are consumed or absorbed, never re-terminalizing the mid-composite run. Non-lifecycle provider events in the same window (usage telemetry foremost) still append under their own families' rules.
- [ ] A `rollback` intervention from every legal source state — `paused`, `waiting_for_approval`, `waiting_for_input`, each terminal state, and `running` via the pause-first path (guard evaluated once at admission against the pre-pause `runVersion`; every fail-closed pre-dispatch validation precedes the internal pause — a refusal leaves the run running — and the pause queues no resume event) — lands the run, **on a conversation-leg-confirmed rewind**, in `paused` at the confirmed position — `targetPosition` on the equal-floor path, the driver-confirmed floor on a position-mismatch degrade (the failure-path criterion below; the event never lies about the landing position) — with a forward `run.rolled_back` event appended (plus the `run.paused` state event for state-changing sources; in-place from `paused` emits only `run.rolled_back`; a waiting source's pending block is voided — canceled as moot — exactly on that confirmation, never before it) and prior turns marked superseded by projection, while a non-confirming outcome applies no rewind and rests each source per the failure-path criterion below (a pause-first `running` source `paused`, every other source unchanged); a stale `expectedRunVersion` produces `expired` with no leg applied, and a `targetPosition` outside the validated rewind domain (non-integer, negative, current-or-future, naming no recorded boundary, or classified boundary-crossing against the run's newest current provider-side compaction per the criterion below) is rejected pre-dispatch with no leg applied — current-position targets admissible solely as file-leg recovery of a recorded incomplete restore.
- [ ] Rollback leg ordering is fail-closed end to end: a [Spec-010](010-worktree-lifecycle-and-execution-modes.md) file-leg precondition refusal rejects the whole intervention with no leg applied, as does a terminal-source rollback whose execution root cannot be exclusively re-acquired because another run holds it; a file-leg failure after a confirmed conversation rollback surfaces as a `degraded` outcome naming the partial state while the run still lands `paused` at `targetPosition` with `run.rolled_back` appended (state follows the confirmed conversation leg); a conversation-leg failure after the internal pause leaves the run `paused` with no auto-resume and a `degraded` outcome naming the pause-only disposition — while the same failure from a waiting or terminal source leaves the source state standing with the outcome naming nothing applied (the waiting source keeps its pending block un-voided, the terminal source stays terminal); a terminal-source composite that does not confirm the rewind releases its re-acquired root (workspace `ready`, execution-context release marker restored); a confirmed-floor mismatch skips the file leg fail-closed with the event recording the confirmed position; a mid-sequence restore failure surfaces the distinct `files-partially-restored` disposition with the run retaining its root hold; a dispatched-but-unconcluded rollback is reconciled by position-compare at recovery — completed forward or concluded, never blindly redispatched, with a dispatched-but-unconcluded same-position recovery reconciling as at-target (completed forward to the restore fixpoint, never concluded no-rewind); an invalid or no-op driver-confirmed floor is treated as no-rewind failure, never an event — the file-leg recovery convergence excepted (its no-op confirmation at the carve-out-admitted current-position target is the confirmed floor, and the restore re-runs to the fixpoint); post-rollback re-execution captures snapshots under the new epoch's namespace, never colliding with a superseded epoch's ordinals; late pre-epoch non-lifecycle appends carry durable epoch attribution for replay-safe supersede marking; and `read-only` and disposed-ephemeral-clone runs complete conversation-only with the file-leg disposition recorded on the outcome — a rootless re-opened run refusing `run.resume` with a typed error.
- [ ] Run-control authorization is role-based and authorship-blind (the local arm of the 2026-08-03 cross-user rule): a caller holding a session write-access role (`owner` or `collaborator` per the [Security Architecture §Permission Matrix](../architecture/security-architecture.md#permission-matrix-task-54) run-control row) passes the `Action::"intervene"` adjudication against a locally-hosted run **another participant authored** — for interventions and for the orchestration-layer `run.pause` / `run.resume` identically — with `initiatorId`, the run's creating participant, and the target agent's owner never read as authorization inputs; a caller whose role carries no session write access (`runtime contributor`, `viewer`) is denied — a denied intervention settles `rejected`, and a denied `run.pause` / `run.resume` request is rejected untouched with no run-state mutation composed (the orchestration verbs hold no `InterventionType` membership and settle no `InterventionResult`). The role grant is bounded by node trust, never a substitute for it ([Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior)'s bound): every agent executes on its owner's machine ([vision.md §The Collaboration Model](../vision.md#the-collaboration-model)'s credentials-never-travel invariant), so a run targeting **another participant's agent** is hosted on that participant's node and takes the remote arm below — the owner's-approval-policy authority the vision's steering rule names ("granted by that owner's approval policy, never by membership alone") is enforced as the hosting-node approval leg, not voided by the role check — and a locally-hosted run is by construction a run of the caller's own node's agents, adjudicated under the node-owner participant principal the daemon itself binds on its local socket ([API Payload Contracts §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model)).
- [ ] Cross-node intervention is a request, never standing authority (the remote arm): when the target run's hosting node is not the caller's local node, the same adjudication **adds** the target-node-owner approval leg — an approval in the `tool_execution` category per [Spec-024](024-cross-node-dispatch-and-approval.md) — and the request is confined to Spec-024's dispatch lifecycle, in which the intervention capability handler executes only after a signed `allow` ApprovalRecord: the target daemon composes this spec's `Action::"intervene"` adjudication into its **pre-approval** Cedar evaluation point — the same step-5 evaluation that adjudicates Spec-024's own `Action::"dispatch::<capability>"` request — so a role-check failure terminates as the post-receipt `dispatch.rejected` **before any owner approval prompt surfaces**, never deferred to post-approval handler execution (whose faults Spec-024 classes as `dispatch.failed`); an approver's explicit refusal terminates as `dispatch.denied`, an approval still unresolved at caller-token expiry terminates as `dispatch.expired` — on every one of these the handler never runs, no intervention state is created or settled (no `InterventionResult` exists to reach `applied` or `degraded`), and no run mutation composes, a cross-node `run.pause` / `run.resume` request identically confined (the own-node `rejected` settlement in the local arm above is [Spec-024](024-cross-node-dispatch-and-approval.md)'s own-node out-of-scope carve-out, not this arm's); session write access alone never clears the node-owner leg, and the leg fails closed by construction wherever no approval pipeline or cross-node dispatch surface exists to grant it — including before the run-control dispatch capability itself is registered (a named [Plan-004 §Preconditions](../plans/004-queue-steer-pause-resume.md#preconditions) prerequisite): an undeclared capability is rejected at intake before target-owner approval is ever requested per Spec-024's declared-capability rule, so an unregistered handler is unreachable, and an unobtainable approval is an absent approval.
- [ ] Rewind-target validation is compaction-boundary-aware and fails closed (2026-08-16 amendment): with no current `usage.context_compacted` row for the target run, every domain-admissible target stays admissible; a target at or above the newest current boundary's originating position is admitted unchanged, the compaction row staying current and out of the rewound tail — a target **equal** to that position included, since rewinding to the compaction's own boundary keeps the compaction rather than reversing it; a target strictly below it is rejected pre-dispatch with no leg applied and a machine-readable cause persisted on the durable intervention row, on the Codex and Claude legs identically, unless the target run's driver declares re-verified boundary-crossing rewind semantics; a current compaction row that resolves to no originating position at all — no stamp, no operation linkage, and no recoverable timeline slot, the shape a retention audit stub leaves behind — rejects **every** target of that run rather than being silently skipped; a compaction row already marked superseded by an earlier accepted rewind never gates a later one; and where a driver does declare the capability, its position translation anchors at the boundary's pre-compaction leaf only when every intervening address is a compaction-prelude address, degrading to the ordinary anchor off-pattern, bounded against a cyclic ancestor chain, with any resulting floor difference surfacing as the ordinary position-mismatch degrade rather than a silent divergence; the confirmed floor is reclassified at settlement against the then-current boundary set, a crossing conclusion settling `degraded` naming `boundary-diverged` — file leg skipped fail-closed, any staged replacement suppressed, run `paused` at the confirmed floor with the divergence cause persisted on the durable row; and `run.resume` refuses fail-closed, with a typed error, a run whose current position sits strictly below its newest current boundary (the post-settlement straggler backstop, making a boundary-diverged run non-resumable in V1 exactly like the rootless class).
- [ ] Atomic edit-and-resend is one intervention and preserves the caller's text in all three failure arms (2026-08-16 amendment): the composite rides the existing `rollback` intervention carrying `replacementSend` — one durable row, one `clientIdempotencyKey`, one `expectedRunVersion` guard, minting no new intervention type, wire method, event type, error code, or table (the `run.compaction_boundary_diverged` refusal is the compaction leg's shared resume backstop, not the composite's) — and is refused pre-dispatch, whole and with no leg applied, against a `running` target (the pause-first path does not extend to the replacement leg, while bare rollback keeps it), against a run holding a pending send — an accepted send not yet delivery-confirmed or an undrained queued send admitted before the composite — against a `targetPosition` whose boundary was not opened by a participant-authored `user.message` of that run (bare rollback of such a boundary staying admissible), and against a non-resumable rootless target — a run whose execution context is released with no existing root, or whose execution context — live or already released — records a checkout root no longer on disk (a live one the confirmed rollback releases into that class; a terminal-source one arrives in it), where the promised next-resume delivery can never occur, while bare rollback of it stays admissible conversation-only; a fully-successful rewind (confirmed floor equal to the target, boundary-clear at settlement reclassification, file leg complete or legitimately conversation-only) **admits** the corrected message as a queue item **bound to the rewound run** (`queue_items.target_run_id` stamped at admission) in the same durable transaction that settles the intervention — the run still landing `paused` at the confirmed position with no auto-resume and no second driver-facing call, the item delivering into its bound run as that run's next provider send on `run.resume` (the pending-send guard having emptied the queue of older sends at admission), the drained turn executing under the admitting intervention caller's effective principal per [Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior)'s extended rule — while a confirmed rewind whose replacement is suppressed or fails admission settles `degraded` carrying `resendDisposition: 'unapplied'` — **required** on the `resend-unapplied` arm, whose own shape identifies its request as composite, and which, where it displaces a completed file restore rather than following a skipped or refused one, carries that restore's `overwrittenIgnoredPaths` and `divergentGitlinks` under the same never-silent contract `files-restored` holds — both present-and-empty on the conversation-only branch, which ran no file leg and displaces nothing (2026-08-25 narrowing) — naming `resend-unapplied` exactly when admission itself failed after a fully-successful rewind and the earlier-failing leg's disposition otherwise, with the run `paused` at the confirmed position and `run.rolled_back` appended; a dispatched-but-unconcluded composite reconciled at target drives the staged replacement send forward among its remaining legs rather than stranding it — admitting and settling in that same single transaction, so an unconcluded intervention proves no admission occurred and recovery never double-admits — and a replay of the same `clientIdempotencyKey` returns the recorded outcome rather than sending twice, with reuse adjudicated by decrypt-and-compare under the requester's live participant key (an undecryptable stored body settling the reuse fail-closed as `intervention.idempotency_conflict`); the replacement text rides the participant-keyed PII envelope on the durable intervention row (`interventions.pii_payload`, never plaintext `payload`) and is recoverable under the requester's key in every arm that reaches intervention creation (the cross-node pre-approval refusal creates no intervention state, and the caller-side surface that authored the text remains its holder); a refusal raised by any of the four structural guards names **which** guard refused on the closed-union `rejectionGuard` member of the `rejected` response — arm-scoped, schema-optional, producer-obligated, absent on every one of the **eight** other refusal families a rollback reaches — beside the unchanged machine-readable `rejectionReason` (2026-09-06 amendment), so a per-guard remedy is rendered by an exhaustive switch over a closed union and never by a match against that sibling's contract-unenumerated cause vocabulary, the literal persisting on the intervention row (`interventions.rejection_guard`, vocabulary-closed and arm-bound by its `CHECK`) so that an idempotent replay of the same `clientIdempotencyKey` returns a `rejectionGuard` equal to the recorded one **across a daemon restart**, never omitted and never re-derived by re-evaluating the guards against a run that has since moved on; and superseded marking applies **solely** on the accepted `run.rolled_back` boundary — never on the composite's admission, its dispatch, or its replacement send — with the resend appending after the boundary in session append order, so no linkage field on either row is required to render the pair.

## Resolved Questions and V1 Scope Decisions

- No blocking open questions remain for v1.
- V1 decision: queue priority overrides are deferred. The first implementation uses canonical queue order plus explicit steer, pause, resume, interrupt, cancel, and — per the 2026-07-13 campaign B2 amendment (§Required Behavior) — rollback controls only (`cancel` restored to this enumeration 2026-09-01: it has been an `InterventionType` member since Tier 1 and was omitted here by erratum, which is why downstream text counted the set at five and called a would-be addition a "sixth"; the set is closed by enumeration, not by count). The 2026-08-16 amendment's edit-and-resend does **not** widen that set: it is an optional leg on the `rollback` control, adding no new control, and its compaction-boundary sibling narrows which rollback targets are admissible rather than adding a surface. The 2026-08-26 same-agent provider switch does not widen it either: `agent.configUpdate`'s `interruptAndSwitch` flag dispatches the **existing** `interrupt` intervention rather than minting a control, on the 2026-08-18 edit-affordance precedent ([Spec-016 §Same-Agent Provider Switch](016-multi-agent-channels-and-orchestration.md#same-agent-provider-switch), D-016-26).
