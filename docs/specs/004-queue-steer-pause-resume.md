## Purpose

Define the canonical control semantics for queued work, active-run steering, pause and resume, and interrupt behavior.

## Scope

## Required Behavior

- Follow-up work created while a run is active must be stored as persisted queue items unless the user explicitly requests steer and the target run supports it.
- `pause` is an orchestration-layer construct: the daemon interrupts the active run, persists conversation history and run state, and queues a resume event. The resulting `paused` state must not mean queue-drain suspension or blocked waiting.
- `resume` must return a `paused` run to active execution with the same run id.
- `interrupt` must transition a run directly to `interrupted`. Interruption is a synchronous or near-synchronous provider call with no intermediate state.
- Waiting for approval or input must remain `waiting_for_approval` or `waiting_for_input`, not `paused`.
- Every intervention outcome must be visible in the canonical event stream.
- Queue items must support cancellation before admission.
- **Post-interrupt late-event absorption (campaign B2, P1-8).** A provider **run-lifecycle** event — a run-state-transition report — that arrives for a run already in a terminal state (`completed`, `interrupted`, `failed`) is **absorbed, never appended**: a terminal-class straggler routes into the at-most-once terminal emitter ([Spec-006 §Run Lifecycle](006-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle) emission contract, campaign B1) and no-ops there; a non-terminal lifecycle straggler is dropped from the lifecycle path entirely and recorded only as a `run.late_event.absorbed` **diagnostic non-event** on the daemon's telemetry (an OTel log record per [Observability Architecture](../architecture/observability-architecture.md) — never a `session_events` row), with no state transition and no `runVersion` advance. Absorption also keys on **execution epoch**, not current run state alone (the epoch is the interval between accepted `run.rolled_back` rewinds — a confirmed conversation rewind advances it regardless of the file-leg disposition — [Run State Machine §Invariants](../domain/run-state-machine.md#invariants)): a run-lifecycle event sourced from the pre-rollback execution that arrives after a rollback has re-opened the run in `paused` is absorbed identically even though the run is no longer terminal — the Spec-006 `(runId, runVersion)` at-most-once key cannot catch these (rollback advanced `runVersion`), so appending one would record a stale terminal against the new epoch or force an illegal transition. The epoch attribution is concrete and needs no wire token: run-lifecycle events are attributed per **binding** — a superseded (fork-repointed) binding's deliveries are entirely pre-epoch, and on an in-place binding the driver's `rollbackTo` confirmation is an **in-stream fence** (the driver owns one serialized provider connection, which totally orders the confirmation against event delivery) — so the driver quiesces pre-rollback lifecycle delivery once `rollbackTo` resolves, and the daemon's per-binding cursor — an **(epoch, position) pair** whose position component advances at each turn boundary observed in the binding's ordered delivery and freezes at the fence or at repointing (a fork-superseded binding's deliveries are entirely pre-epoch at its frozen pair) — absorbs any straggler that slips through (§Driver-Level Rollback Mechanics). For the pause-first composite the absorption window opens **earlier than the fence**: from the moment the composite issues its internal interrupt, run-lifecycle events sourced from the interrupted execution are the pause's expected echo — consumed by the pause application exactly as the client pause path consumes its own interrupt's echo, or absorbed as above, never routed as spontaneous transitions — so a late `run.interrupted` arriving after the internal pause but before the `rollbackTo` confirmation cannot re-terminalize the mid-composite run or release its root (the rollback bullet below). Absorption is scoped to the run-lifecycle family: non-lifecycle provider events arriving in the same window — usage telemetry above all, plus assistant output, tool activity, and artifact publication — append normally under their own families' rules (late usage telemetry must still reach the cost ledger; absorption never drops billable usage) — but never epoch-blind: a non-lifecycle row the per-binding cursor attributes to a pre-rollback epoch appends **carrying that attribution durably** (the daemon stamps the source-epoch linkage onto the appended row at ingestion — the pair **from the straggler's operation association**: the run engine records each provider-side operation (tool call, message item, artifact production) against the **(epoch, turn) current when it opened**, in-stream and pre-fence, and the straggler's correlation key resolves that recorded pair — re-executed turns reuse ordinals, so the association must carry the epoch alongside the turn, and delivery order bounds only the _emission_ turn, so a content-asynchronous straggler (a long-running tool's progress, a delayed usage aggregate, a late-completing artifact upload) must rank by its _operation's_ opening pair, not the last-observed boundary. Binding lineage differs by mechanism without changing the value source: a fork-superseded binding (Claude) freezes wholesale — every delivery is pre-epoch at its retained (epoch, position) pair — while an in-place rollback (Codex) **rotates the binding's delivery generation at the fence**: the confirmation closes the pre-rollback generation, retaining its pair, and post-fence deliveries open the new epoch at the confirmed floor, so one provider binding spans epochs with per-generation attribution. A straggler with no resolvable operation linkage takes the retained pre-rollback generation's pair — reachable only where the delivery itself is attributable pre-epoch without content linkage: the superseded fork binding wholesale, never an in-place binding's post-fence delivery, which the in-stream fence's total order makes current — a conservative upper bound strictly above its epoch's rewind cutoff (that generation closed at the run's then-current position, and admission requires the target strictly below it), so an unattributable pre-epoch straggler is always superseded with its epoch, never resurfacing as current — never a read-time guess and never the post-rollback run's current position; append-time knowledge is never discarded), so replayed projections mark it superseded exactly like the in-time rows of the epoch it belongs to and stale output can never resurface as current timeline state (the typed stamp shape is owned by the campaign's Plan-006 bundle — registered 2026-07-20 as the cross-cutting `sourceEpoch` + `sourcePosition` payload pair, [Spec-006 §Event Type Enumeration](006-session-event-taxonomy-and-audit-log.md#event-type-enumeration); §Driver-Level Rollback Mechanics' supersede projection consumes it). The near-synchronous interrupt hedge above is the _reason_ the window exists — a provider may emit briefly after the daemon records the terminal; canonical-stream visibility of the intervention outcome is satisfied by the terminal event itself, and absorption adds no second visible outcome.
- **Rollback intervention (campaign B2 — R8 run time-travel, V1 feature #19 per [ADR-015](../decisions/015-v1-feature-scope-definition.md)).** `rollback` is a first-class intervention type on the existing generic dispatch: `applyIntervention('rollback', {targetPosition})`, carrying the same mandatory fail-closed `expectedRunVersion` guard and mandatory `clientIdempotencyKey` as every intervention (§Interfaces And Contracts) — a rollback racing a progressing run expires exactly like a stale steer. `targetPosition` is the **normalized session position** (a `number`, the [Spec-005](005-provider-driver-contract-and-capabilities.md) `rollbackTo` position vocabulary) identifying the turn boundary to rewind to — **domain-validated fail-closed at admission**: an integer ≥ 0 naming a turn boundary recorded in this run's history **strictly below the run's current position**; non-integer, negative, current, future, or boundary-less values are rejected pre-dispatch with no leg applied (the wire arm carries the matching runtime bound — [API Payload Contracts](../architecture/contracts/api-payload-contracts.md)) — with exactly one carve-out: a target **equal to the current position** is admissible when the run's recorded rollback outcome at that position left the file leg incomplete (`files-unrestored`, `files-partially-restored`, or the position-mismatch skip) — the **file-leg recovery path**, whose conversation leg no-ops by absolute-position convergence and whose restore re-runs to the fixpoint; the accepted intervention's value serializes onto the forward `run.rolled_back` event ([Spec-006 §Run Lifecycle](006-session-event-taxonomy-and-audit-log.md#run-lifecycle-run_lifecycle) per-type row — this contract is that row's named structural-type owner), identically on the confirmed path (the confirmed-floor rule below). **State-gated:** legal from `paused`, `waiting_for_approval`, `waiting_for_input`, and the three terminal states; a `running` target is first brought to `paused` via the existing orchestration-layer pause path (interrupt + persist), and rollback applies from `paused` — the pause-first path is scoped to a **bare** rollback, a rollback carrying the 2026-08-16 amendment's `replacementSend` leg refusing a `running` target outright instead (§Required Behavior's edit-and-resend bullet) — the pause is an **unguarded internal sub-step of the atomic rollback application**, not a client `run.pause` request: it queues **no resume event** (the client pause path's queued resume is not part of the sub-step — rollback lands and stays `paused`, and a surviving marker would re-run the pre-rollback continuation), **every fail-closed pre-dispatch validation — the target-position domain check, the compaction-boundary classification (the 2026-08-16 amendment's bullet below), the Spec-010 restore precondition, the uncompacted-rewind-span check, execution-root tenancy, the capability check — completes at admission, before the pause sub-step** (a refused rollback of a `running` run leaves it running, untouched — pausing first and then refusing would itself be a leg applied), the intervention's `expectedRunVersion` guard is evaluated **exactly once, at admission**, against the caller-observed pre-pause `runVersion` (the internal pause's own progression cannot expire the very intervention that initiated it), and the intervention response returns the post-composition `runVersion`; rollback is the **only** path out of a terminal state ([Run State Machine §Rollback Transitions](../domain/run-state-machine.md#rollback-transitions-campaign-b2), this bundle). A rollback from a waiting state voids the pending block — the awaited approval or input request is canceled as moot when the turn that raised it is rewound, the void applying **exactly on the confirmed conversation rewind, never at admission or dispatch**: a conversation leg that fails or confirms no rewind leaves the block pending and the run in its waiting state, per the no-rewind path below (the approval reaches `approval.canceled`, a driver ask reaches `driver_ask.canceled` — Spec-006's existing terminals; the void mints no new event type). A concurrent resolution racing the rollback serializes on the run's progression: a resolution that applies first advances `runVersion`, so the in-flight rollback correctly expires; a rollback that applies first cancels the block, and the late resolution finds a canceled request and no-ops. A queued resume pending against the target run at application time is voided the same way — canceled as moot, because the position it would resume from has been rewound — under the same progression-serialized race rule. **Same-run resurrection, not fork-new-run:** budgets, supersede-marking, and the `expectedRunVersion` guard are all run-scoped; a fork would orphan all three. Re-executed turns reuse position ordinals, which is why snapshot identity is **epoch-namespaced** — the post-rollback execution's turn-6 capture must never collide with (or silently resolve to) the superseded epoch's turn-6 tree ([Spec-010 §Turn-Boundary Snapshots](010-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots), this bundle's ruling; implemented by the campaign's Plan-010 bundle). Modeled as a **forward** `run.rolled_back` event on the authoritative log ([ADR-017 Decision Log, 2026-07-02](../decisions/017-shared-event-sourcing-scope.md#decision-log)): the log never truncates or rewrites, and rolled-back turns remain queryable history **marked superseded by projection**. Successful rollback lands the run in `paused` at the rewound position. Leg ordering is **fail-closed**: the file-leg restore precondition ([Spec-010 §Turn-Boundary Snapshots](010-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots) — current `HEAD` must equal the snapshot's recorded first parent) is validated pre-dispatch, and a refusal rejects the whole intervention with no leg applied (this records the post-snapshot-commit ruling Spec-010's Restore bullet defers to this bundle: standing refusal, never rewind/revert of reviewable Spec-011 history and never a silent partial restore); the **rewind span must be live** — every row of the target run the position cutoff would mark superseded (the rewound tail strictly above `targetPosition`) is uncompacted at admission, and a rollback whose rewind span intersects already-compacted history is refused whole (the same standing-refusal class: compaction irreversibly replaced those rows' payloads with audit stubs, destroying the per-row attribution the supersede projection needs — [Spec-006 §Compacted Event Format](006-session-event-taxonomy-and-audit-log.md#compacted-event-format) — while rows at or below the target compact freely, staying current and taking no mark), with detection reading the stubs' preserved run identity: every audit stub of a run-scoped row preserves its `runId`, plus its originating position when the rollback-attribution source resolved one at compaction — [Spec-006 §Compacted Event Format](006-session-event-taxonomy-and-audit-log.md#compacted-event-format)'s `originPosition` — so the span check counts the target run's **unstamped** stubs strictly above `targetPosition`, or position-less (a stub written before rollback support shipped, whose position is unknowable), as span intersections, while `sourceEpoch`-stamped stubs are already attributed and never block; and the check is **not check-then-forget**: the span check and the write-ahead intervention row's durability are atomic under the session's append serialization (the per-session append lock), and from that durability until the intervention concludes the span is **compaction-deferred** — the compactor's per-row attribution answers _defer_ for rows a dispatched-but-unconcluded rollback's span covers (leaving them live for a later pass; the durable intervention row survives restart, so the deferral holds across a crash until the [Spec-015](015-persistence-recovery-and-replay.md) reconciliation concludes the row) and its per-row attribute-and-stub runs under the same lock — so idle compaction can neither stub the rewound tail in the admission-to-boundary window (no accepted boundary exists yet for compaction-time stamping, so those stubs would be stranded unattributable) nor race the span check over a row mid-stub; the file leg additionally requires **exclusive tenancy of the execution root** — a terminal-source rollback first re-acquires the workspace root through the [Spec-010 §State And Data Implications](010-worktree-lifecycle-and-execution-modes.md#state-and-data-implications) single-holder handoff (the terminal exit had returned the workspace to `ready`, so another run may hold or acquire the root), a root `busy` under another run is a standing refusal of the same whole-rejection class (retriable once the root frees — never a restore into another run's live working tree), and the precondition check plus restore then run under the re-acquired exclusive hold, closing the check-then-restore window (non-terminal sources still hold their root; no re-acquisition step); the conversation leg (the driver's capability-gated `rollbackTo` parity operation, campaign B3) applies next — **a conversation-leg failure ends the intervention with no file mutation and never auto-resumes**: when the driver reports `degraded` or the reconciliation rule below concludes no rewind occurred, the intervention ends `degraded` with the disposition naming exactly what applied — the internal pause for a `running` source (the run stays `paused` at its pre-rollback position with `runVersion` reflecting the pause; an implicit resume would re-run the very continuation the caller asked to rewind away from — recovery is a fresh rollback, now from `paused`, or an explicit `run.resume`), nothing for every other source (dispatch occurred, so pre-dispatch `rejected` is definitionally unavailable — [Queue And Intervention Model §Driver Result To Lifecycle Mapping](../domain/queue-and-intervention-model.md#driver-result-to-lifecycle-mapping)) — and **a terminal-source composite releases its re-acquired root on every path that does not confirm the conversation rewind**: the run stays terminal, the workspace returns to `ready`, and the execution context's release marker is restored (the hold is retained exactly when the run re-opens — [Run State Machine §Rollback Transitions](../domain/run-state-machine.md#rollback-transitions-campaign-b2)); once the driver confirms, the daemon **validates the driver-confirmed floor equals `targetPosition` before the file leg** (`DriverRollbackResult.applied.sessionPosition` — §Driver-Level Rollback Mechanics) — the confirmed floor is untrusted driver output and first passes the **same domain validation as the request target**: an invalid report (non-integer, negative, unrecorded boundary) or a no-op report (equal to the pre-rollback position) is treated as a no-rewind conversation-leg failure per the path above, minting no `run.rolled_back` and superseding nothing — with the file-leg recovery path excepted, because there the carve-out-admitted target legitimately equals the current position, so the driver's convergence no-op (`sessionPosition == targetPosition`, no movement) IS the confirmed floor: the composite proceeds to the fixpoint restore and the forward event emits at the confirmed position (the no-rewind branch applies only when the driver fails to confirm that floor); then, on a valid-but-different confirmed position (mismatch) the file leg is skipped fail-closed (never a restore against a boundary the conversation is not at), the run follows conversation truth — `paused` at the **confirmed** position — the intervention ends `degraded` naming the position-mismatch disposition (requested vs confirmed), and the forward event records the confirmed position (the event never lies about where the run landed); the file leg restores last, and a file-leg failure after a confirmed conversation rollback is surfaced as a **`degraded`** intervention outcome naming the partial state — two distinct dispositions, never collapsed: `files-unrestored` (the restore never started) and `files-partially-restored` (the multi-command restore failed mid-sequence, the failed step named; the sequence is convergent, so a fresh rollback to the same `targetPosition` re-runs it to the full-restoration fixpoint, and the run retains its exclusive root hold across the partial state — a half-restored tree is never handed to another run — [Spec-010 §Turn-Boundary Snapshots](010-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots)) — never `applied`, which would hide the file-leg failure ([Queue And Intervention Model](../domain/queue-and-intervention-model.md): `degraded` is the lifecycle's partial-effect terminal, and `failed` is not an intervention state). The run-state consequence follows the **conversation leg**: once that leg is confirmed, the run's authoritative position has rewound, so the run lands `paused` at `targetPosition` and the forward `run.rolled_back` event is appended **even when the file leg then fails** — recording anything else would silently diverge the daemon's recorded position from the provider's. Replaying the same `clientIdempotencyKey` returns the recorded partial outcome (replay-or-conflict — never a re-execution); recovery is a **fresh** rollback intervention to the same `targetPosition`, which re-runs both legs. **Dispatch ambiguity is reconciled, never guessed**: the accepted intervention row is durable **before** driver dispatch (the `interventions` table's lifecycle state is the write-ahead dispatch-intent marker), and neither provider protocol offers a rollback dedupe key — the provider-boundary idempotency mechanism is **absolute-position targeting**: `rollbackTo` addresses an absolute normalized position, never a relative drop-count on the daemon's wire, so a retry after an unconfirmed attempt converges instead of double-rewinding (§Driver-Level Rollback Mechanics — the Codex driver re-derives the drop-count from the provider's current position at each dispatch; the Claude driver re-composes from the still-bound pre-fork binding, minting a fresh binding at the same target and orphaning, never re-executing, any unacknowledged earlier fork). On daemon restart — or a driver throw/timeout leaving the attempt unconfirmed — every rollback row dispatched-but-unconcluded is reconciled by the [Spec-015](015-persistence-recovery-and-replay.md) resume position-compare **before anything else touches the run**: a provider position at `targetPosition` (or a discovered post-fork binding at it) completes the intervention forward — remaining legs (the recorded `replacementSend` among them wherever the 2026-08-16 amendment's composite staged one, never left unsent), durable outcome, `run.rolled_back`, binding repoint; an unchanged provider position concludes it by the no-rewind path above — with the file-leg recovery intervention reconciled as **at-target**: its carve-out-admitted target equals the pre-dispatch position, so at-target and unchanged coincide by construction, and reconciliation takes the completion branch (remaining legs re-run to the restore fixpoint, durable outcome, forward event at the confirmed position), never the no-rewind conclusion that would strand the partially-restored tree the recovery exists to finish; only after reconciliation is redispatch legal, converging by the same absolute-position rule. Runs whose mode snapshots nothing (`read-only`) and runs whose execution root no longer exists — an ephemeral clone past disposal, a worktree retired by the cleanup sweep — roll back **conversation-only** per Spec-010 §Retention/§Applicability, with the outcome recording the file-leg disposition ([Plan-004](../plans/004-queue-steer-pause-resume.md)'s rollback tasks — campaign B9 — own the typed outcome detail); a **rootless** run re-opened this way is **non-resumable**: `run.resume` against a run whose execution context is released with no existing root is refused with a typed error — nothing recreates a disposed clone or retired worktree, and re-execution takes a fresh run on the same branch through normal admission — so the rolled-back history is queryable and correct without ever activating a run against a nonexistent root ([Run State Machine §Rollback Transitions](../domain/run-state-machine.md#rollback-transitions-campaign-b2)).
- **Compaction-boundary-aware rewind targeting (2026-08-16 amendment).** Rewind-target validation is **compaction-boundary-aware**, and the boundary in question is the **provider's context-window compaction** — never the daemon's audit-log retention compaction. The two are distinct mechanisms with distinct rewind consequences and must not be conflated: the retention pass replaces this system's own event payloads with audit stubs and is governed by the uncompacted-rewind-span check above ([Spec-006 §Compacted Event Format](006-session-event-taxonomy-and-audit-log.md#compacted-event-format)), while a provider-side compaction rewrites the **provider's** live conversation context in place and is recorded here as a `usage.context_compacted` row ([Spec-006 §Usage Telemetry](006-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)). Let **B** be the greatest originating position among the target run's `usage.context_compacted` rows that are **current** — not already marked superseded by an earlier accepted rewind, so a boundary a prior rollback rewound past never gates a later one. That currency filter is stated for correctness, not because V1 reaches it: while every driver keeps the refusal below, no accepted rewind can supersede a compaction row — a boundary-clear target leaves the row at or below `targetPosition`, and the supersede cutoff marks only `turn > targetPosition`, so both the strictly-above and the equal arm leave it current — and the filter therefore becomes live exactly when a driver's re-verified boundary-crossing semantics does. B is resolved through the same operation-association rule that ranks every content-asynchronous straggler (the absorption bullet above) — the stamped originating position on a late row, the payload's operation linkage on an in-time one, and the row's own timeline slot only as the linkage-less fallback that rule already carries — never as a bare append-order read taken in preference to association. The distinction is **precision, not safety**: no row is ever appended before the operation it reports, so a slot-ranked boundary can only sit at or above the true one, and a slot-ranked B therefore over-refuses and can never silently admit a crossing target. Association is nonetheless required first, because that over-refusal would deny every legitimate rewind across the span between a compaction's originating turn and its late delivery — precisely the span a long-running turn makes widest. Classification is three-valued and **fails closed**:
  - **No boundary.** The run has no current `usage.context_compacted` row, and every target the domain check admits stays admissible. This is the V1 default: no V1 driver ships a compaction operation, so a boundary arises only from provider-native auto-compaction ([Spec-016 §Resolved Questions and V1 Scope Decisions](016-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions)).
  - **Boundary-clear** — `targetPosition` at or above B. The rewound tail lies strictly above the target, so the compaction row is not in it, the row stays current, and the provider legitimately keeps its compacted context: recorded state and provider state agree. The ordinary path applies unchanged. This deliberately includes a target **equal** to B — rewinding to the compaction's own turn boundary keeps the compaction, it does not reverse it.
  - **Boundary-crossing** — `targetPosition` strictly below B, **or** a current `usage.context_compacted` row the association rule resolves to no originating position at all — no stamp, no operation linkage, and no recoverable timeline slot. A row that resolves only through the linkage-less slot fallback is **not** in this arm: it ranks, conservatively and at or above its true position, and is classified on that rank like any other. The supersede cutoff would mark the compaction row rewound, asserting the compaction is undone, while no provider wire offers a compaction-restore operation ([Spec-016 §Resolved Questions and V1 Scope Decisions](016-multi-agent-channels-and-orchestration.md#resolved-questions-and-v1-scope-decisions): "neither provider wire exposes a compaction-restore operation" — the recoverability that section grants is an audit and re-derivation guarantee, deliberately not a live-conversation undo), and what a provider rewind actually reconstructs across its own compaction boundary — pre-compaction context, or the compacted summary alone — is exactly the question §Driver-Level Rollback Mechanics leaves open: the Claude leg's probe record already names it explicitly for a fork, and that section's compaction-boundary anchoring rule scopes the ADR-017 re-verification it owes to what **each** provider's rewind reconstructs across its own boundary, so neither leg is verified. Such a target is **refused whole, fail-closed, pre-dispatch**, with no leg applied and a machine-readable cause persisted on the durable intervention row — the same standing-refusal class as the uncompacted-rewind-span check, and for the same reason: admitting it would leave the rendered timeline asserting one context state while the provider holds another. A position-less compaction row classifies as crossing for **every** target of that run, because evidence of a compaction that cannot be proven to sit at or below the target must be treated as sitting above it — exactly as the span check treats a position-less audit stub as a span intersection.

  The classification is **provider-agnostic**, binding both legs identically, because it is a property of compaction being a context rewrite rather than of either wire's rewind mechanism: the Codex leg drops turns, which does not un-compact a rewrite the provider has already applied to its own transcript, and the Claude leg forks at a message address whose reconstructed context across a boundary is unverified. The refusal is **liftable, not permanent**: a driver whose declared capabilities carry re-verified boundary-crossing rewind semantics — verified against the then-installed binary under the same ADR-017 row that governs both rewind mechanisms — admits crossing targets on its own legs, and every other driver keeps the refusal. It follows that "undo the compaction" is not expressible as any admissible target in V1: it is definitionally the boundary-crossing class, never something a target at or above B achieves.

- **Atomic edit-and-resend (2026-08-16 amendment).** Correcting a previously-sent user message — editing its text and re-dispatching it — is an **optional replacement-send leg on the `rollback` intervention above**, never a new intervention type, wire method, or event type: `applyIntervention('rollback', {targetPosition, replacementSend})`, where `replacementSend` carries the corrected message body. The whole operation is **one intervention**: one durable `interventions` row, one `clientIdempotencyKey`, one `expectedRunVersion` guard evaluated once at admission, one application under the session's append serialization — the same atomicity the pause-first composite already holds, extended by one leg rather than forked into a second mechanism. Every rule the rollback bullet states applies unchanged: the target-position domain check, the compaction-boundary classification, the Spec-010 restore precondition, the uncompacted-rewind-span check, execution-root tenancy, the capability check, confirmed-floor validation, epoch advance, supersede-by-projection, and write-ahead dispatch reconciliation. Five additions are specific to the replacement leg.

  **The replacement leg admits; it does not dispatch.** On a confirmed rewind the corrected message is admitted as a durable queue item against the rewound run through the ordinary participant-send path (the `user.message` row plus queue admission), and the run lands `paused` at the confirmed position exactly as a bare rollback does — **no auto-resume**, and no second driver-facing call: the composite's only driver contact remains the conversation leg (plus the internal interrupt on the pause-first path a replacement send never takes). The queued replacement drains on the next `run.resume` under ordinary FIFO admission, which is this spec's own default for follow-up work. "Resend" therefore guarantees the corrected message is durably re-submitted and will be delivered in order — never that it is already on the provider wire when the intervention settles. Anything else would contradict the rollback bullet's two standing rules (a confirmed rollback lands `paused`; the composite never auto-resumes) for the sake of one leg.

  **The caller's text is durable before anything destructive runs.** The accepted intervention row is durable **before** driver dispatch (the rollback bullet's write-ahead dispatch-intent marker), and `replacementSend` is persisted **on that row**, so the corrected text survives every failure arm including a daemon crash mid-composite. V1 has no daemon-side composer-draft surface to stage it in — daemon-side draft persistence is deferred past V1 and `human_phase_form_state` ships empty ([Spec-017 §State And Data Implications](017-workflow-authoring-and-execution.md#state-and-data-implications)) — which is precisely why the intervention row, already the reconciliation source, carries it.

  **Three structural refusal guards, each fail-closed at admission, pre-dispatch, and whole-intervention.** (i) **No active turn.** The pause-first path does **not** extend to a replacement send: a `running` target is refused outright rather than paused first, because the message being replaced is still being answered, and silently pausing a live turn to rewrite its prompt substitutes an edit for a decision the caller never made. Bare rollback keeps pause-first unchanged; this carve-out is scoped to the replacement leg. (ii) **No unconfirmed send.** A run holding an accepted send whose provider delivery is not yet confirmed — the window between the admitted `user.message` row and the provider's `user_text` wire echo folding into it as delivery confirmation — refuses the composite, because the target cannot be validated against a turn boundary the provider has not yet acknowledged, and the pending-send order is not the composite's to reorder. (iii) **A participant-authored target of this run.** `targetPosition` must name a turn boundary opened by a participant-authored `user.message` of the target run; a boundary opened by any other origin has no participant send to replace. An orchestration-authored boundary — a workflow phase's input or an orchestrated child run's ([Spec-016](016-multi-agent-channels-and-orchestration.md), [Spec-017](017-workflow-authoring-and-execution.md)) — therefore refuses the composite, since rewriting one would rewrite a phase input outside the workflow's own authoring surface. Bare rollback of such a boundary stays admissible; only the replacement leg is refused.

  **The failure taxonomy is three-valued, and the caller's text is recoverable in every arm.** **Refused** — any pre-dispatch validation fails: nothing dispatched, no leg applied, the intervention settles `rejected` (or `expired` on a guard mismatch), and the caller still holds its own text. **Committed-then-failed** — the conversation rewind is confirmed but the replacement send is not admitted: the intervention settles `degraded` naming the **`resend-unapplied`** disposition, the run lands `paused` at the confirmed position with `run.rolled_back` appended exactly as a bare rollback does (run state follows the confirmed conversation leg), and the text stays readable on the durable intervention row. **Transport-lost** — the outcome is unknown to the caller through a driver throw, timeout, or daemon restart: the existing write-ahead reconciliation resolves it, and the [Spec-015](015-persistence-recovery-and-replay.md) position-compare's completion branch drives the staged `replacementSend` forward among the remaining legs — concluding a confirmed rewind without re-dispatching it would strand the very text this leg exists to preserve — while replaying the same `clientIdempotencyKey` returns the recorded outcome rather than sending twice.

  **Superseded marking applies solely on the accepted `run.rolled_back` boundary.** It is driven by that event's confirmed position and by nothing else — not by the composite's admission, not by its dispatch, and not by the replacement send. A client MAY dim the turns a pending composite would rewind, and MUST NOT remove or renumber them before the boundary appends: a composite whose conversation leg does not confirm applies no rewind at all (the no-rewind path above), so an optimistic truncation would delete history the run still holds (§Implementation Notes' optimistic-affordance rule). Because the replacement send appends **after** the boundary in the session's append order, a consumer observes rewind-then-resend from ordering alone, and the composite needs no linkage field on either row to be rendered correctly.

## Default Behavior

- The default follow-up behavior while a run is active is `queue`.
- Queue ordering default is FIFO within the target scheduling scope.
- If a driver does not support steer natively, the intervention must be rejected or degraded to a new queue item. Pause does not require driver support — it is an orchestration-layer run-control mutation (`run.pause` / `run.resume`), handled entirely by the daemon (interrupt + persist + queue a resume) and **not** dispatched through the driver-facing `applyIntervention` path that steer/interrupt/cancel follow ([ADR-011](../decisions/011-generic-intervention-dispatch.md); the driver never needs to know about pause — see [Queue And Intervention Model](../domain/queue-and-intervention-model.md)).

## Fallback Behavior

- If `steer` is requested against a run that cannot accept it, the system must either reject the intervention or explicitly degrade it to a new queue item.
- If a paused run cannot be resumed because driver state is lost, the system must transition it through recovery logic and then to `failed` or `interrupted`; it must not pretend the same run resumed.
- If queue persistence is temporarily unavailable, the system must reject new queue creation rather than silently storing queue state only in client memory.

## Interfaces And Contracts

- `QueueItemCreate`, `QueueItemList`, and `QueueItemCancel` must operate against runtime-owned durable state.
- `InterventionRequest` must include target run id, intervention type, and a **mandatory** version guard (`expectedRunVersion`). The guard is **fail-closed**: the comparand is required on every intervention, and an absent comparand is **rejected**, never applied — an optional guard would let a caller bypass stale-replay protection by omitting the field (Plan-004 D-004-2). `expectedRunVersion` is compared against the target run's `runVersion` — an **any-run-progression counter** that increments on every run progression, applied interventions included (not only `run.*` state-machine transitions), so two steers racing on a still-`running` run cannot both pass undetected (Plan-004 D-004-1). `runVersion` is the run aggregate's optimistic-concurrency token, distinct from the immutable `EventEnvelope.version` wire-contract field ([Spec-006 §EventEnvelope Version Semantics](006-session-event-taxonomy-and-audit-log.md#eventenvelope-version-semantics)). Payload fields vary by type: `steer` includes `expectedTurnId`, `content`, and optional `attachments`; `interrupt` and `cancel` include optional `reason`; `rollback` (campaign B2) includes a **mandatory** `targetPosition` — the normalized session position (a `number`, [Spec-005](005-provider-driver-contract-and-capabilities.md) `RollbackToParams.position` vocabulary) of the turn boundary to rewind to — plus an **optional** `replacementSend` (2026-08-16 amendment) carrying the corrected message body of the atomic edit-and-resend composite (§Required Behavior): absent on a bare rollback, and its presence is exactly what selects the composite's three additional refusal guards and its `resend-unapplied` disposition, so no separate discriminator is required. The matching optional member on the wire union's `rollback` arm is a named [Plan-004 §Preconditions](../plans/004-queue-steer-pause-resume.md#preconditions) merge prerequisite against [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) rather than an edit carried by this amendment. Every intervention request additionally carries a **mandatory** requester-generated `clientIdempotencyKey` (UUID) — the second, orthogonal guard ([Spec-005 §Required Behavior](005-provider-driver-contract-and-capabilities.md#required-behavior), campaign B3): `expectedRunVersion` defeats stale replays of outdated intent, the key defeats duplicate applications of the same intent (replay-or-conflict, `intervention.idempotency_conflict`). See [Queue And Intervention Model](../domain/queue-and-intervention-model.md) for canonical payload shapes.
- `InterventionResult` must distinguish the 6 canonical intervention states: `requested`, `accepted`, `applied`, `rejected`, `degraded`, and `expired`. A version guard mismatch produces `expired`. An authorization failure produces `rejected`.
- Intervention dispatch uses `applyIntervention` (see [Spec-005](../specs/005-provider-driver-contract-and-capabilities.md) and [ADR-011](../decisions/011-generic-intervention-dispatch.md)), which routes to the appropriate driver-specific handler based on intervention type and declared capabilities. The Cedar `principal` for authorizing an intervention is the caller's verified participant identity: the verified PASETO `sub` on every identity-carrying transport (control-plane, relay, and the cross-node dispatch path, where the target binds the principal to the verified `caller_token.sub` per [Spec-024](024-cross-node-dispatch-and-approval.md)'s envelope rules), and — on the daemon's local socket, which carries no PASETO token — the daemon's node-owner participant binding resolved through the Plan-018-gated credential/identity provider seam (a named [Plan-004 §Preconditions](../plans/004-queue-steer-pause-resume.md#preconditions) prerequisite); `initiatorId` and any body-level actor fields are informational only. See [API Payload Contracts §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model). The Cedar **action** for a run-control intervention is `Action::"intervene"` on the target `Run` resource, with the run's **hosting node** carried in the request context. Authorization is evaluated against session membership role — never against run authorship — so a participant holding `collaborator` or `owner` may intervene on a run another participant authored ([Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior) owns the rule); a non-local hosting node **adds** the target-node-owner approval requirement (an approval in the `tool_execution` category per [Spec-024](024-cross-node-dispatch-and-approval.md)) rather than substituting for the role check, so cross-node intervention is a request, never standing authority. The same adjudication governs the orchestration-layer `run.pause` / `run.resume` run-control mutations even though they never ride `applyIntervention` (they are daemon-handled orchestration verbs holding no `InterventionType` membership): their handlers evaluate the identical `Action::"intervene"` request — same `Run` resource, same hosting-node context, same role-not-authorship rule, same cross-node node-owner approval leg — before composing any run-state mutation, per [Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior)'s governed-identically rule, so the dispatch-path split is transport plumbing, never an authorization boundary.
- **Rollback routing (campaign B2).** `rollback` is a full intervention on the client→daemon wire — the `InterventionRequestPayload` union in [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) carries a `rollback` member, and the request flows through the same authorization, `expectedRunVersion` guard, idempotency ledger, and `InterventionResult` lifecycle as every other type. At the driver boundary it does **not** ride `ApplyInterventionParams`: the conversation leg dispatches through the driver's dedicated, capability-gated `rollbackTo` parity operation ([Spec-005 §Interfaces And Contracts](005-provider-driver-contract-and-capabilities.md#interfaces-and-contracts), campaign B3) — `RollbackToParams {sessionId, position, bindingId}` returning `DriverRollbackResult` (`applied {sessionPosition, bindingId?}` | `degraded {fallbackAction?}`). The `bindingId` leg key is **daemon-resolved at dispatch** — run→bindings is 1:many, so the daemon names the run's live provider binding exactly as it does for goal delivery; client rollback payloads never carry it (clients address the run), and a fork-composed rollback repoints the live binding via the result's `bindingId`. The optional `replacementSend` of the 2026-08-16 amendment's edit-and-resend composite never crosses this boundary at all: it is daemon-held state — persisted on the write-ahead intervention row, then re-admitted through the ordinary participant-send path once the conversation rewind confirms — so `RollbackToParams` is unchanged by the composite and the driver leg cannot distinguish a bare rollback from one carrying an edit ([Queue And Intervention Model §Field-Level Consistency](../domain/queue-and-intervention-model.md#field-level-consistency) carries the same non-forwarding rule). ## Driver-Level Steer Mechanics

- **Codex driver**: native `turn/steer` API — content is injected mid-conversation as a new user turn. The active generation is interrupted and the model continues from the steer content.
- **Claude driver**: no native steer support — degrades to queue + interrupt. The orchestration layer: (1) interrupts the active run (transitioning it to `interrupted`), (2) creates a new queue item with the steer content, (3) admits the queue item as a new run. The conversation history is preserved.
- **Generic driver fallback**: same as Claude (queue + interrupt).

### Steer Content Injection Point

- For native steer (Codex): content appears as a new user message in the conversation, immediately after the point of interruption. The model sees it as if the user sent a follow-up.
- For degraded steer (queue + interrupt): content becomes the initial message of the new run. Previous conversation history is loaded from the session event log.
- In both cases: steer content is marked with `source: 'steer'` in the event payload so the timeline can distinguish it from normal user messages.

The typed payload shapes for steer, interrupt, cancel, and rollback interventions are defined in [Queue And Intervention Model](../domain/queue-and-intervention-model.md) and verified against API contracts in that document's Field-Level Consistency section.

## Driver-Level Rollback Mechanics

- **Codex driver**: native `thread/rollback` (drop-N-turns; primary source: [Codex Wire Reference §`thread/rollback`](../reference/provider-wire/codex.md#threadrollback--session-time-travel-conversation-leg), schema-pinned at `codex-cli 0.141.0` with generation receipts in that doc's §Provenance). The protocol schema itself notes it does not revert local file changes — file restore is always the daemon's leg, below. The driver translates the daemon's absolute `targetPosition` into the drop-count **from the provider's current position at each dispatch**, so a retried `rollbackTo` after an unconfirmed attempt converges rather than double-rewinding (§Required Behavior's reconciliation rule). `thread/rollback` is upstream-deprecated beyond the `0.141.0` pin (the deprecation verification is recorded in the same reference section): [Plan-005](../plans/005-provider-driver-contract-and-capabilities.md)/[Plan-010](../plans/010-worktree-lifecycle-and-execution-modes.md) MUST re-verify the method or its replacement against the then-installed binary before driver code lands ([ADR-017 Decision Log, 2026-07-02](../decisions/017-shared-event-sourcing-scope.md#decision-log)).
- **Claude driver**: native composed — `--resume-session-at <message-uuid>` + `--fork-session`, with the driver running `--replay-user-messages` so message-UUID rewind targets appear on the wire; the driver owns the normalized-position → message-UUID translation. `--resume-session-at` is binary-probe-only — absent from the live CLI reference; the probe record and docs-gap analysis are checked in at [Claude Code Wire Reference §Gaps recorded](../reference/provider-wire/claude.md#gaps-recorded), version-pinned with provenance in that doc — and MUST equally be re-verified against the then-installed binary before load-bearing use (same ADR-017 row), that re-verification covering one question the probe record leaves open — what a fork carries across a provider-side context-compaction boundary (whether the forked session reconstructs pre-compaction context or resumes from the compacted summary alone), the case a rewind target older than a compaction boundary lands in. The provider-level fork is **beneath the binding, not a run fork**: the daemon's run aggregate persists (same run id, same `runVersion` lineage, same budgets) and the driver mints a new binding for the same run — the established relaunch pattern ([Spec-005](005-provider-driver-contract-and-capabilities.md) `DriverResumeResult.bindingId`), **registered through the same runtime-binding write seam before the result returns**: the new binding row (provider-owned `resume_handle` + runtime metadata, the `runtime_bindings` model) is durable before `applied` is reported, and `applied.bindingId?` is the store-minted surrogate of that registered row — never itself a resume handle — so a repointed run remains `resumeSession`-able across a daemon restart; the daemon persists the surrogate as the run's live binding so every later per-binding operation (goal delivery, resume, steer) targets the post-fork session, never the dead pre-fork one; the field is absent on an in-place rollback (Codex). A retried compose after an unconfirmed attempt operates on the still-bound pre-fork binding and mints a fresh binding at the same target — an unacknowledged earlier fork is orphaned provider-side, never re-executed, because no daemon binding ever points at it (§Required Behavior's reconciliation rule). §Required Behavior's same-run resurrection invariant holds.
- **File restore** is the daemon's turn-snapshot git leg ([Spec-010 §Turn-Boundary Snapshots](010-worktree-lifecycle-and-execution-modes.md#turn-boundary-snapshots), campaign B21) — never the driver's, on either provider.
- **Confirmed floor**: `DriverRollbackResult`'s `applied` variant carries a REQUIRED driver-confirmed `sessionPosition` — the new authoritative recovery floor consumed by the [Spec-015](015-persistence-recovery-and-replay.md) resume position-compare (campaign B5/B14) — plus the optional `bindingId` above (present exactly when the mechanism minted a new binding). A successful rollback without a confirmed floor is structurally inexpressible, and the daemon validates the confirmed floor **equals the requested `targetPosition` before the file leg**, after first applying the same domain validation as the request target (an invalid or no-op confirmed floor is a no-rewind failure — never an event — except the file-leg recovery convergence, where the no-op confirmation at the carve-out-admitted current-position target is the confirmed floor and the restore proceeds; §Required Behavior) — a valid-but-different floor skips the restore fail-closed and ends the intervention `degraded` naming the position-mismatch disposition, with the forward event recording the confirmed position (§Required Behavior). Resolving `applied` also **quiesces the pre-rollback stream**: after `rollbackTo` resolves, the driver delivers no further run-lifecycle events from the pre-rollback execution on the run's binding (a superseded pre-fork binding delivers nothing at all) — implementable without a wire token because the driver owns one serialized provider connection, so the `rollbackTo` confirmation is an in-stream fence ordering the epoch boundary against event delivery; any straggler that slips through is absorbed by §Required Behavior's execution-epoch gate, never appended.
- **Timeline presentation**: rolled-back turns are never deleted from `session_events`; projections mark them superseded (turn > post-rollback position of the accepted `run.rolled_back` event) so clients render the rewound history distinctly rather than dropping it. Late pre-epoch non-lifecycle appends carry §Required Behavior's durable epoch stamp (the `sourceEpoch` + `sourcePosition` carrier pair, [Spec-006 §Event Type Enumeration](006-session-event-taxonomy-and-audit-log.md#event-type-enumeration)), so replay ranks them with their source epoch — never by append order — and the supersede marking survives projection rebuilds.
- **Compaction-boundary anchoring (2026-08-16 amendment).** Wherever a driver's declared capabilities admit a boundary-crossing rewind at all (§Required Behavior's compaction-boundary classification), that driver's normalized-position → provider-address translation MUST anchor at the boundary's **pre-compaction** leaf, not at whatever address the post-compaction prelude chain resolves to. The failure this closes is one of ordering, not arithmetic: a provider-side compaction writes its effects — the boundary marker, the generated summary, and any caveat the provider injects — as ancestors of the invoking turn's own echo, so a translation that anchors on that echo's immediate parent lands **inside** the compaction's own prelude and hands the provider its compacted context back, while this system has already marked the boundary rewound. The surveyed reference runtime's fix is the shape to bind: anchor at the last address preceding the boundary, taken **only** when every intervening address between the requested target and the boundary is a compaction-prelude address; where the chain is off-pattern, degrade to the ordinary anchor rather than guessing; and bound the ancestor walk so a malformed or cyclic chain cannot spin the translation. The daemon never re-derives a target from the driver's anchoring — the driver reports whatever floor it actually reached and §Required Behavior's confirmed-floor validation adjudicates it unchanged, so an anchoring that lands anywhere other than the accepted `targetPosition` surfaces as the ordinary position-mismatch degrade rather than as a silent divergence. Until the ADR-017 re-verification this section owes settles what each provider's rewind reconstructs across its own compaction boundary, no V1 driver declares the capability and the classification refuses every boundary-crossing target: this rule is the contract that re-verification is verifying **against**, not a claim that either wire already satisfies it.

## Implementation Notes

- Queueing and intervention logic must live in the daemon or equivalent runtime authority, not in the currently open client.
- UI affordances may be optimistic, but canonical run state changes must come from runtime truth.
- Capability-aware controls are required so unsupported operations do not masquerade as working.
- Pause is an orchestration-layer construct. The daemon interrupts the active run, persists conversation history and run state to local SQLite, and queues a resume. The driver never needs to know about pause.

## Pitfalls To Avoid

- Using client memory as the queue of record
- Calling reread or reattach semantics `resume`
- Treating waiting states as paused states
- Appending a late provider run-lifecycle event to a terminal run's timeline (the absorption rule exists precisely for this window) — or, inversely, absorbing non-lifecycle events the rule never covered (late usage telemetry is billable and must append) — or keying absorption on current run state alone, which misses pre-rollback stragglers arriving after a rollback re-opened the run (the epoch gate exists for exactly that arrival order)
- Treating rollback as log truncation — the authoritative log never truncates; rollback is a forward `run.rolled_back` event plus projection-level supersede marking
- Conflating the daemon's audit-log retention compaction with the provider's context-window compaction — they are different mechanisms with different rewind consequences, gated by different checks (the uncompacted-rewind-span check and the compaction-boundary classification respectively), and a rewind cleared by one is not thereby cleared by the other
- Reading a compaction boundary off the arrival slot of its `usage.context_compacted` row without first attempting operation association — the error direction is conservative rather than unsafe (nothing is appended before the operation it reports, so a slot-ranked boundary sits at or above the true one), which is exactly why the mistake survives testing: it never admits a crossing rewind, it silently refuses every legitimate one in the span between the compaction's originating turn and its late delivery. Reading the same conservatism the other way is the genuinely unsafe twin — concluding that because slot-ranking cannot admit a crossing target, an unresolvable row may be skipped rather than refused
- Truncating or renumbering the rendered timeline when an edit-and-resend composite is admitted or dispatched rather than when its `run.rolled_back` boundary is appended — a composite whose conversation leg never confirms applies no rewind at all, so the optimistic truncation would delete history the run still holds

## Acceptance Criteria

- [ ] Follow-up work while a run is active is durably queued by default.
- [ ] Pause (orchestration-layer interrupt + persist + queue resume) and resume operate on the same run id and same run history.
- [ ] Unsupported intervention requests result in explicit `degraded` or `rejected` outcomes rather than silent behavior changes.
- [ ] A provider run-lifecycle event arriving for a run already terminal never appends a `session_events` row and never advances `runVersion`: a terminal-class straggler no-ops in the at-most-once terminal emitter; a non-terminal lifecycle straggler surfaces only as the `run.late_event.absorbed` OTel diagnostic; a run-lifecycle event sourced from the pre-rollback execution epoch, arriving after a rollback re-opened the run, is absorbed identically — never appended against the new epoch; and during a pause-first rollback composite, run-lifecycle events sourced from the internally-interrupted execution — arriving after the pause, before the `rollbackTo` confirmation — are consumed or absorbed, never re-terminalizing the mid-composite run. Non-lifecycle provider events in the same window (usage telemetry foremost) still append under their own families' rules.
- [ ] A `rollback` intervention from every legal source state — `paused`, `waiting_for_approval`, `waiting_for_input`, each terminal state, and `running` via the pause-first path (guard evaluated once at admission against the pre-pause `runVersion`; every fail-closed pre-dispatch validation precedes the internal pause — a refusal leaves the run running — and the pause queues no resume event) — lands the run, **on a conversation-leg-confirmed rewind**, in `paused` at the confirmed position — `targetPosition` on the equal-floor path, the driver-confirmed floor on a position-mismatch degrade (the failure-path criterion below; the event never lies about the landing position) — with a forward `run.rolled_back` event appended (plus the `run.paused` state event for state-changing sources; in-place from `paused` emits only `run.rolled_back`; a waiting source's pending block is voided — canceled as moot — exactly on that confirmation, never before it) and prior turns marked superseded by projection, while a non-confirming outcome applies no rewind and rests each source per the failure-path criterion below (a pause-first `running` source `paused`, every other source unchanged); a stale `expectedRunVersion` produces `expired` with no leg applied, and a `targetPosition` outside the validated rewind domain (non-integer, negative, current-or-future, naming no recorded boundary, or classified boundary-crossing against the run's newest current provider-side compaction per the criterion below) is rejected pre-dispatch with no leg applied — current-position targets admissible solely as file-leg recovery of a recorded incomplete restore.
- [ ] Rollback leg ordering is fail-closed end to end: a [Spec-010](010-worktree-lifecycle-and-execution-modes.md) file-leg precondition refusal rejects the whole intervention with no leg applied, as does a terminal-source rollback whose execution root cannot be exclusively re-acquired because another run holds it; a file-leg failure after a confirmed conversation rollback surfaces as a `degraded` outcome naming the partial state while the run still lands `paused` at `targetPosition` with `run.rolled_back` appended (state follows the confirmed conversation leg); a conversation-leg failure after the internal pause leaves the run `paused` with no auto-resume and a `degraded` outcome naming the pause-only disposition — while the same failure from a waiting or terminal source leaves the source state standing with the outcome naming nothing applied (the waiting source keeps its pending block un-voided, the terminal source stays terminal); a terminal-source composite that does not confirm the rewind releases its re-acquired root (workspace `ready`, execution-context release marker restored); a confirmed-floor mismatch skips the file leg fail-closed with the event recording the confirmed position; a mid-sequence restore failure surfaces the distinct `files-partially-restored` disposition with the run retaining its root hold; a dispatched-but-unconcluded rollback is reconciled by position-compare at recovery — completed forward or concluded, never blindly redispatched, with a dispatched-but-unconcluded same-position recovery reconciling as at-target (completed forward to the restore fixpoint, never concluded no-rewind); an invalid or no-op driver-confirmed floor is treated as no-rewind failure, never an event — the file-leg recovery convergence excepted (its no-op confirmation at the carve-out-admitted current-position target is the confirmed floor, and the restore re-runs to the fixpoint); post-rollback re-execution captures snapshots under the new epoch's namespace, never colliding with a superseded epoch's ordinals; late pre-epoch non-lifecycle appends carry durable epoch attribution for replay-safe supersede marking; and `read-only` and disposed-ephemeral-clone runs complete conversation-only with the file-leg disposition recorded on the outcome — a rootless re-opened run refusing `run.resume` with a typed error.
- [ ] Run-control authorization is role-based and authorship-blind (the local arm of the 2026-08-03 cross-user rule): a caller holding a session write-access role (`owner` or `collaborator` per the [Security Architecture §Permission Matrix](../architecture/security-architecture.md#permission-matrix-task-54) run-control row) passes the `Action::"intervene"` adjudication against a locally-hosted run **another participant authored** — for interventions and for the orchestration-layer `run.pause` / `run.resume` identically — with `initiatorId`, the run's creating participant, and the target agent's owner never read as authorization inputs; a caller whose role carries no session write access (`runtime contributor`, `viewer`) is denied — a denied intervention settles `rejected`, and a denied `run.pause` / `run.resume` request is rejected untouched with no run-state mutation composed (the orchestration verbs hold no `InterventionType` membership and settle no `InterventionResult`). The role grant is bounded by node trust, never a substitute for it ([Spec-012 §Required Behavior](012-approvals-permissions-and-trust-boundaries.md#required-behavior)'s bound): every agent executes on its owner's machine ([vision.md §The Collaboration Model](../vision.md#the-collaboration-model)'s credentials-never-travel invariant), so a run targeting **another participant's agent** is hosted on that participant's node and takes the remote arm below — the owner's-approval-policy authority the vision's steering rule names ("granted by that owner's approval policy, never by membership alone") is enforced as the hosting-node approval leg, not voided by the role check — and a locally-hosted run is by construction a run of the caller's own node's agents, adjudicated under the node-owner participant principal the daemon itself binds on its local socket ([API Payload Contracts §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model)).
- [ ] Cross-node intervention is a request, never standing authority (the remote arm): when the target run's hosting node is not the caller's local node, the same adjudication **adds** the target-node-owner approval leg — an approval in the `tool_execution` category per [Spec-024](024-cross-node-dispatch-and-approval.md) — and the request is confined to Spec-024's dispatch lifecycle, in which the intervention capability handler executes only after a signed `allow` ApprovalRecord: the target daemon composes this spec's `Action::"intervene"` adjudication into its **pre-approval** Cedar evaluation point — the same step-5 evaluation that adjudicates Spec-024's own `Action::"dispatch::<capability>"` request — so a role-check failure terminates as the post-receipt `dispatch.rejected` **before any owner approval prompt surfaces**, never deferred to post-approval handler execution (whose faults Spec-024 classes as `dispatch.failed`); an approver's explicit refusal terminates as `dispatch.denied`, an approval still unresolved at caller-token expiry terminates as `dispatch.expired` — on every one of these the handler never runs, no intervention state is created or settled (no `InterventionResult` exists to reach `applied` or `degraded`), and no run mutation composes, a cross-node `run.pause` / `run.resume` request identically confined (the own-node `rejected` settlement in the local arm above is [Spec-024](024-cross-node-dispatch-and-approval.md)'s own-node out-of-scope carve-out, not this arm's); session write access alone never clears the node-owner leg, and the leg fails closed by construction wherever no approval pipeline or cross-node dispatch surface exists to grant it — including before the run-control dispatch capability itself is registered (a named [Plan-004 §Preconditions](../plans/004-queue-steer-pause-resume.md#preconditions) prerequisite): an undeclared capability is rejected at intake before target-owner approval is ever requested per Spec-024's declared-capability rule, so an unregistered handler is unreachable, and an unobtainable approval is an absent approval.
- [ ] Rewind-target validation is compaction-boundary-aware and fails closed (2026-08-16 amendment): with no current `usage.context_compacted` row for the target run, every domain-admissible target stays admissible; a target at or above the newest current boundary's originating position is admitted unchanged, the compaction row staying current and out of the rewound tail — a target **equal** to that position included, since rewinding to the compaction's own boundary keeps the compaction rather than reversing it; a target strictly below it is rejected pre-dispatch with no leg applied and a machine-readable cause persisted on the durable intervention row, on the Codex and Claude legs identically, unless the target run's driver declares re-verified boundary-crossing rewind semantics; a current compaction row that resolves to no originating position at all — no stamp, no operation linkage, and no recoverable timeline slot, the shape a retention audit stub leaves behind — rejects **every** target of that run rather than being silently skipped; a compaction row already marked superseded by an earlier accepted rewind never gates a later one; and where a driver does declare the capability, its position translation anchors at the boundary's pre-compaction leaf only when every intervening address is a compaction-prelude address, degrading to the ordinary anchor off-pattern, bounded against a cyclic ancestor chain, with any resulting floor difference surfacing as the ordinary position-mismatch degrade rather than a silent divergence.
- [ ] Atomic edit-and-resend is one intervention and preserves the caller's text in all three failure arms (2026-08-16 amendment): the composite rides the existing `rollback` intervention carrying `replacementSend` — one durable row, one `clientIdempotencyKey`, one `expectedRunVersion` guard, minting no new intervention type, wire method, event type, error code, or table — and is refused pre-dispatch, whole and with no leg applied, against a `running` target (the pause-first path does not extend to the replacement leg, while bare rollback keeps it), against a run holding an accepted-but-undelivered send, and against a `targetPosition` whose boundary was not opened by a participant-authored `user.message` of that run (bare rollback of such a boundary staying admissible); a confirmed rewind **admits** the corrected message as a queue item on the rewound run — the run still landing `paused` at the confirmed position with no auto-resume and no second driver-facing call, the item draining on the next `run.resume` under ordinary FIFO admission — while a confirmed rewind whose replacement is not admitted settles `degraded` naming `resend-unapplied`, with the run `paused` at the confirmed position and `run.rolled_back` appended; a dispatched-but-unconcluded composite reconciled at target drives the staged replacement send forward among its remaining legs rather than stranding it, and a replay of the same `clientIdempotencyKey` returns the recorded outcome rather than sending twice; the replacement text is readable on the durable intervention row in every arm; and superseded marking applies **solely** on the accepted `run.rolled_back` boundary — never on the composite's admission, its dispatch, or its replacement send — with the resend appending after the boundary in session append order, so no linkage field on either row is required to render the pair.

- No blocking open questions remain for v1.
