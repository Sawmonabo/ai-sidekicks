## Purpose

Define how reusable workflows are authored, versioned, and executed inside sessions. V1 ships the full workflow engine: four phase types (`single-agent`, `multi-agent`, `automated`, `human`), four gate types, parallel phase execution with named resource pools, and durable state with append-only hash-chained approval history. The engine plugs into existing daemon primitives (Spec-014 channels, Spec-010 approvals, Spec-012 artifacts, Spec-005 events, Spec-013 recovery) — workflow execution does not duplicate them.

## Scope

This spec covers:

- A visual, node-graph builder on a canvas, whose sidekick steps run on the user's own provider accounts and their own sidekick definitions
- Workflow authoring as one node-shaped document plus a typed TypeScript SDK (no bespoke DSL per C-1), and the canonical file form definitions export to and import from (§Definition file form — export and import (C-17))
- Workflow versioning (immutable-by-version with content-hash identity)
- The V1 node catalog — forty-one kinds across eight categories (§Phase-Type and Gate-Type Taxonomy) — and the four phase types whose node kinds delegate to the existing run, approval and form machinery at run time
- Phase execution for all four phase types
- Workflow-level gates (four gate types)
- The full V1 trigger set — manual, schedule, file change, loopback webhook, session event, chat, sub-workflow and error — with every arm honoured at ship time (§Entry node and the V1 trigger surface (SA-37))
- Parallel phase execution with named resource pools and bounded iteration
- Append-only hash-chained approval history (C-13 / I7)
- Workflow event taxonomy (new Spec-005 categories + event types)
- Durable phase state persisted via Spec-013 (SQLite + WAL)
- Replay-determinism contract
- Workflows as first-class objects of session chat in both directions: from a message, the user or a sidekick can list, read, create, edit, fix, run, schedule, cancel, resume, enable and disable a workflow and fetch a run's results
- A run history that keeps every step's input, output, logs, timing, cost and error, inspectable per step and re-runnable from any step

## Non-Goals

- General-purpose external workflow engines (no Temporal, Restate, Argo binding at V1)
- Marketplace or distribution semantics for workflow templates — publishing, importing from outside the daemon, or any cross-machine sync of definitions. Narrowed 2026-08-10 (Tier-7 audit) rather than deleted: the ratified `shared` scope value adds daemon-local cross-project **reuse**, which is a visibility breadth, not distribution. A `shared` definition never leaves the daemon that stores it, so this Non-Goal stands with its subject stated precisely. Definition portability between machines at V1 is therefore the operator-driven file form of §Definition file form — export and import (C-17) — a file an operator moves, never a service that moves it.
- Queue mode and worker pools. The engine is one process inside the daemon; the run record stays serializable, so splitting work onto a worker stays possible later without changing what a run is.
- External binary storage as a configured tier. A payload too large to sit inline becomes an artifact through the existing ingest pipeline, and an item's binary reference keeps that escape hatch open.
- Declarative node authoring for HTTP-shaped kinds — the second authoring style n8n offers, where a node declares its requests and operations as data rather than executing them. One imperative executor per kind is enough.
- A second spelling of anything the expression surface already has: no legacy node-indexed or item-indexed lookups, no second query language beside the expression language of §Expressions, no `continueOnFail` beside `onError`, and no second execution order. One spelling of each.
- The SQL-query merge mode, and an expression-extension library that adds methods to built-in types.
- Pixel-level UI design for the workflow editor. V1 ships the visual builder surface specified in §Visual Workflow Builder — its node taxonomy, port and connection rules, refusal set, layout tier, and scope semantics are normative here; type scale, colour, spacing and motion are the console's own design-token surface and are not fixed in this spec.
- `BIND` multi-phase channel reuse — criterion-gated V1.1 commitment per [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments). V1 ships `ownership: OWN` only; `BIND` lands only if three named criteria are satisfied (see Interfaces And Contracts §Multi-agent).
- Default timeout for `human` phase — required typed opt-in in V1 per BL-097 D1. Default-timeout + escalate-to-paging deferred to V1.x under notification-routing criterion per [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments).
- **Cross-run campaign memory and durable wake-coalescing delivery — criterion-gated V1.1 (deferred 2026-08-16).** V1 ships the _fold_: §Provider-limit pacing and durable resumption (SA-40) groups concurrently parked runs by their park's provider-account attention key, so one provider-account outage presents as one attention record rather than one per parked run. V1 does **not** ship the durable delivery-settlement substrate that fold could be built into — a per-watcher generation record with a claim / queue / deliver compare-and-set lifecycle, crash-time claim reclamation across daemon restart, and campaign-scoped memory carrying attention state across separate runs of the same recurring workflow. The V1 fold is a grouping over the run aggregate's own projection state and crosses no aggregate boundary; the deferred substrate is durable cross-run state with its own lifecycle, which is a different thing wearing the same word. Until all three criteria below hold, V1's honest behavior is the fold plus the per-run park cause of §Park integrity and cancellability (SA-42) — every parked run stays individually visible and individually resumable, and nothing claims to have notified anyone. Three named criteria gate the V1.1 ship decision and all three must hold; this is a criterion-gated commitment, not an intention:
  - **Criterion 1 — an outbound delivery channel exists to settle against.** Notification routing ships (the same gate [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments) already names for the `human`-phase default timeout). A delivery-settlement protocol is unbuildable while there is no delivery to settle: at V1 the attention record is read from a surface, never pushed to one, so "delivered" has no observable moment.
  - **Criterion 2 — a measured insufficiency of the V1 fold.** At least three recorded occasions in a 30-day rolling window where one provider-account outage parked five or more runs **and** the single V1 attention record was observed insufficient, in that an operator inspected the parked runs individually rather than acting on the record. The two halves are evidenced differently, and stating which is which is part of the criterion. The **scale half** is machine-derivable: §Engine event record (SA-43) captures every park with its attention key and correlation keys, so counting outages that parked five or more runs is a read over records V1 already writes. The **insufficiency half** is an operator-attested finding, not a derived one — SA-43 records engine decisions, never client reads, and V1 mints no operator control surface whose usage could be observed (the recorded residual of §Park integrity and cancellability (SA-42)) — so evaluating it means recording the attestation when the occasion happens, not building observation machinery beforehand.
  - **Criterion 3 — a written cross-run ownership contract.** The substrate spans runs and outlives any one of them, so before it ships a contract must name the watcher identity a generation keys on, the exact edge that advances a generation, the crash-reclaim rule, and which plan owns the durable rows — the four questions the V1 fold does not have to answer because it never leaves the run. Absent that contract, cross-run coalescing state has no one-writer owner, which the corpus's one-writer ownership discipline forbids.
- Cross-phase discussion channels (V2): agents from different phases collaborating in shared channels.
- OpenTelemetry workflow semantic conventions — OTel GenAI semconv is not yet ratified as of 2026-04-22 ([OpenTelemetry GenAI Observability Blog 2025](https://opentelemetry.io/blog/2025/ai-agent-observability/)); V1 ships on CloudEvents + Spec-005 envelope and adopts OTel semconv additively when ratified under [ADR-018](../decisions/018-cross-version-compatibility.md) MINOR rules.
- SQLite STRICT tables adoption (criterion-gated V1.x deferral per Wave 2 §4.1 — cross-plan policy change; Plan-015 schema uses repo's existing TEXT-column convention).
- Mutation testing in CI (criterion-gated V1.x deferral per Wave 2 §4.2 — V1 PR budget already at 30 min).
- Execution-model enum (`local | queued | remote`) — C-11 commitment is local-only at V1 (Airflow executors and n8n `own` mode precedent: every system that enumerated execution models at V1 had to break-remove entries later).

Three layers own the surface, and each owns one thing:

- **The shared contracts** define the document, items, node kinds, run and step records, events and method schemas as the single source both other layers read.
- **The daemon** owns definitions, runs, the engine, expression evaluation, the node-kind registry, the triggers, the scheduler, the sidekick tools and the request handlers.
- **The renderer** owns the three tabs — Builder, Workflows and Runs — the builder's own draft store, the canvas, the palette, the inspector, the catalog, the run detail and the chat verbs.

The renderer parses on every read and the daemon validates on every write. Where both evaluate the same rule, the daemon's answer is authoritative and the client's edit-time check is a mirror of it, never a replacement for it.

## Required Behavior

### Authoring + versioning

- Workflows must be authored as one explicit node document with stable node ids and versioned structure.
- Workflow authoring format: that document plus a typed TypeScript SDK. **No bespoke DSL** (no CUE, no HCL, no custom expression language) — C-1 commitment. DSL lock-in cost is precedent-heavy: Dagger maintained its CUE SDK as primary authoring language from Jan 2022 (v0.1.0) through Dec 2023, then ended CUE SDK support after a year of dual-maintenance against multi-language SDKs, citing that "engineers...want to write code in a language they already know. Learning a brand new language, however powerful, is simply not what they're looking for" ([Dagger — Ending Support for the Dagger CUE SDK, 2023](https://dagger.io/blog/ending-cue-support/); [Solomon Hykes on Changelog #550, 2023](https://changelog.com/podcast/550)); GitHub Actions migrated off HCL to YAML under breaking-change pressure ([GitHub Actions HCL→YAML deprecation, 2019](https://github.blog/changelog/2019-09-17-github-actions-will-stop-running-workflows-written-in-hcl/)).
- Workflow definition files must carry an explicit schema version marker — the document's own `schemaVersion` field, whose V1 value is `2`. Daemon must support compat mode for reading older-marker files (SA-14 / C-8 — Temporal's Version Sets → Build IDs retrofit is the precedent cost avoided here).
- Workflow definitions must be stored as first-class durable definition and version records. Artifact publication may represent workflow exports or summaries, but it must not be the canonical source of workflow definition truth.
- `WorkflowDefinitionCreate` must run a DFS three-color cycle check against the node graph and reject invalid definitions with a typed error. The graph the check runs over is the one the document declares — its edge list, each entry naming a source node and handle and a target node and handle (§Graph model — nodes, ports, and edges (SA-32)) — and it walks the `main` edges only. It exempts exactly one shape: an edge whose target is a loop node's own input, because closing a loop body is the loop rather than a cycle. `go-back-to` stays a state-reset operation and never a drawn edge.

**Saving is one act, and it always writes a version.**

- Save stays unavailable until the draft differs from the version it was loaded from, and it answers the platform's save chord.
- Save writes a new immutable version and never mutates an existing one.
- Saving an edit to a `shared`-scope definition creates a new definition at the editing context's scope carrying the original's content hash as its parent, and leaves the original untouched (§Definition scope in the builder (SA-36)).
- The scope choice lives in one small panel anchored directly under the Save button, holding the scope control, the version line and Cancel and Save, with nothing dimmed behind it. That panel is the only place scope appears while authoring; nothing about scope stands on the canvas.
- Run now against a dirty draft asks to save first and runs the version it saved, never unsaved bytes.
- Closing the builder with unsaved changes asks once, and the draft survives a reload.
- A save the daemon refuses leaves the draft intact and lists every refusal in the validation strip below the canvas.
- The validation strip's unsaved-changes row counts the nodes that differ from the saved version with a verb that agrees — `Unsaved changes · 1 node differs from version 7.` — and a draft that has never been saved says so rather than naming a version it does not have: `Unsaved changes · never saved, 1 node to save.` The prompt on leaving reads the same line.
- What is hashed is a fixed field list — name, description, trigger, nodes, edges — canonicalized with a recursive key sort, JCS-serialized and BLAKE3'd. Content fields only, so ids, timestamps and runtime state never produce a spurious conflict, and the layout and pinned-data sections sit outside the preimage (§Canvas layout is not definition bytes (SA-35)).

**Versions are readable where the workflow is authored.** The builder's toolbar carries a version readout, and opening it opens a Versions panel beside the canvas listing the workflow's versions newest first, each with when it was saved, who saved it — the user, or the sidekick that did — and a one-line count derived from the structural diff ("2 nodes changed, 1 edge added"). Selecting an older version shows its difference against the current one on the canvas itself: changed nodes marked, added edges in the success colour, removed edges dimmed, and the inspector showing the selected node's old and new params side by side. The panel offers two acts: **Restore**, which saves a new version identical to the selected one and rewrites no history, and **Show runs**, which filters the Runs tab to the runs pinned to that version. A run row's pinned-version chip opens the same panel with that version selected. The diff is computed in the daemon over the hashed body only, so a node's position never counts as a change and every reader — the panel and a sidekick reading a version's changes alike — gets one answer.

### Execution semantics

- V1 ships all four phase types: `single-agent`, `multi-agent`, `automated`, `human`.
- V1 ships all four gate types: `auto-continue`, `quality-checks`, `human-approval`, `done`.
- V1 ships parallel phase execution with named per-resource-pool backpressure (SA-3). The executor tick loop uses a Kahn-style ready-set admission over the phase DAG; ready-set processing bounded by `max_concurrent_phases` (daemon-global default 4) as final backstop.
- Iteration must be bounded by three counters:
  - Per-phase `max_retries` (default 3).
  - Workflow-run-level `max_phase_transitions` (default 100) — hard-fails the run with `failure_reason='RUN_ITERATION_LIMIT'` (SA-1).
  - Workflow-run wall-clock `max_duration`, which is **unset by default** and comes from one console-wide control, `Stop a run after`, on the Runtime settings page. Where it is set, a run that has been working longer than that ends as failed and timed out, with `failure_reason` preserved (SA-2); time the run spent waiting on a person does not count against it, while a park on a spent provider account does, because the bound is wall-clock (§Provider-limit pacing and durable resumption (SA-40)). A timed-out run never touches the workflow's schedule, which fires again as planned. There is no per-workflow cap and no document field for one; the two node kinds that execute something — the sidekick run and the shell command — carry their own `Timeout` param instead, empty by default, meaning none.
- Resource pools for V1 (SA-3):
  - `pty_slots` — capacity `min(8, cpu_count * 2)`, tunable per daemon config.
  - `agent_memory_mb` — capacity `daemon_budget - overhead ≈ 192 MB`; per-`single-agent` phase default reservation 100 MB (pessimistic). Tripwire: >15% phase-launch attempts blocked on `agent_memory_mb` in a 2-week rolling window triggers V1.1 calibration.
  - Pull-based admission in executor tick.
- `PhaseResourceNeed` model on phase definition: `{pool: string, amount: number}[]`. Multiple pool reservations must all be available at admit time.
- Parallel execution must specify `ParallelJoinPolicy` (SA-4): `'fail-fast' | 'all-settled' | 'any-success'`. Default `fail-fast`. Sibling cancellation on `fail-fast` must be recorded at a deterministic synchronous tick checkpoint — never in async callbacks (prevents the non-determinism class documented in Temporal Java SDK #902).
- `priority?: number` on phase definition drives ready-set ordering; FIFO tiebreaker (SA-5). Airflow-style priority weight deferred to V1.1 if tripwire warrants.
- All phase execution routes through existing `OrchestrationRunCreate` per Spec-014/015 constraints.
- A workflow phase may create runs, request approvals, emit artifacts, or block on user input.
- Workflow execution must remain visible in the session timeline and must preserve per-phase provenance.
- Phase outputs must be durable, addressable after workflow completion, **and immutable once written** (SA-16 / C-9). Accumulator patterns build on top (e.g., a `collect` phase reads N upstream outputs and emits a new output). Retry creates a new phase-run identity and a new output row — never overwrites. The GitHub Actions Artifact v3→v4 mutability-forced migration is the precedent ([GitHub Actions — v3 artifact deprecation notice, 2024-04-16](https://github.blog/changelog/2024-04-16-deprecation-notice-v3-of-the-artifact-actions/)).
- Workflow execution must be resumable after daemon restart or client reconnect.

**How the engine walks the graph.** The daemon owns the run. A topological scheduler walks the edge list depth-first, sorting a node's siblings by that node's own explicit `order` value, so moving a node on the canvas never changes what the run does. A node runs when all of its `main` inputs are settled. A node with more than one `main` input parks in a per-(node, run index) partial-input buffer until every input slot is filled. A node whose input carries no items is skipped unless it is marked to always output data. A disabled node passes its input straight to its output. A loop node keeps its remaining items in per-node run context and is closed by the author wiring the loop body's last node back into it, which re-executes it under a new run index — which is why a step record is an array per node and why the expression surface exposes a run index at all.

**What a run and a step record keep.** A run record carries its id, the definition and version it is pinned to, the session it lives in, its status, its mode, its trigger record, who or what started it, when it started and finished, and its error where it failed. One step record exists per node attempt, carrying: the run id and node id, the attempt number, a per-run monotonic `executionIndex`, the source array naming for each input the edge that actually fed it and which run of the source produced it, the status, the timings, three payload references — input, output and log — the cost receipt where a provider was billed, and the typed error where it failed. The `executionIndex` gives a faithful "what happened when" list for a branching run, and the source array is what lets a run's detail say that this run of a merge consumed run 3 of the loop. One structure is what makes a branching run renderable, partial re-execution expressible and staleness computable.

**A run's own state.** Run statuses are a closed list: `new`, `running`, `waiting`, `succeeded`, `failed`, `cancelled`, `crashed`, and nothing else is ever displayed. Modes are `manual`, `trigger`, `webhook`, `chat`, `agent` (a sidekick's own tool call), `retry` and `sub-workflow`. What started a run is one of: the user, a schedule, chat, a sidekick, a webhook, a file event, or a parent workflow.

**Crash sweep and waiting.** On daemon start, runs left in `new` or `running`, and runs in states no longer decidable, are swept to `crashed`; a run in `waiting` is never swept and never pruned, so a parked approval survives a restart and rehydrates. A node that suspends stores a resume token on the run, sets the wait deadline where one exists, offloads its run data, and resumes on the matching resolution or timer. The approval node, the form node and the wait-for-a-chat-reply node all ride that one mechanism, so a paused run is one state rather than three.

**Every step boundary is an event.** A step's start, finish or failure emits its event into the session event log (§Event types (SA-19)), so the Runs tab and the session's own record are one truth rather than two.

**A partial run decides what to skip from a dirty-node lattice** computed over the last run's step data:

- Editing a node's params marks that node.
- Inserting or deleting a node marks the following node.
- Adding a connection marks its destination.
- Disabling a node marks the next node.
- Any dirty node inside a loop marks the loop head.
- Pinning or unpinning marks the nodes it affects.

"Run from here" then executes the target's ancestors plus the target, reusing clean step data and re-executing only what is dirty; "Run this node" is the single-node case of the same call and uses pinned or prior input. The lattice lives in the builder's own draft store for display, and the filtered run is computed by the daemon, whose answer is authoritative.

**Pinned data makes an offline authoring loop possible.** A node's pinned items live on the document outside the hashed body, so pinning creates no version. Pinned data is honoured only in a manual run and ignored by every trigger-started run. A node may be pinned only where it has a single `main` output and its items carry no binary payload. Unpinning is offered as a banner link at the top of the node's Output panel. A run's detail offers "Copy this run into the builder", which loads the run's document version and pins the run's data onto the first node — which is what carries a production failure back into the builder as data to author against.

**Run data is kept in three tiers.**

1. The run rows — status, timings, trigger, the one-line summary — are kept until the user deletes them. They are the history list.
2. Step data — each step's input, output and log, whether inline under the payload cap or spilled into an artifact above it — is kept for the run-data bound [Spec-020 §Retention Policy](./020-data-retention-and-gdpr.md#retention-policy) sets, which nothing overrides per workflow; the control that sets it is the machine-local settings surface of [Spec-006 §Required Behavior](./006-local-ipc-and-daemon-control.md#required-behavior), one place per value. Past the bound the run still lists and still carries its status, timings and summary, and its step panel reads that the data expired in place of its panels. A run the user marked **Keep** holds its step data past the bound, and a run in `waiting` is never touched.
3. Files a workflow saved on purpose, through the save-as-artifact kind, are the user's work product and are never auto-deleted.

Deleting is asked for once and is never undone: the Runs tab carries **Delete run** as a run row's one action and **Delete runs older than…** above the list, each naming what goes and saying that a run marked Keep stays and a run waiting on a person is never touched. Deleting a workflow soft-deletes it and leaves its runs readable against their pinned versions.

**Redaction happens before the first write.** Every secret value resolved for a step is added to the run's redaction set before any log line, step payload or error message is written, so no resolved secret is ever stored (§Secrets — by reference only (C-15)).

### Expressions

A param's value is either a literal or an expression string in the form `={{ … }}`, where the leading `=` is the marker — so a literal string that happens to contain braces is unambiguous.

The binding namespace is closed and is the whole of it: `$json`, `$input.all()` / `.first()` / `.last()` / `.item`, `$('<label>')` with `.all()` / `.first()` / `.last()` / `.item` / `.params`, `$runIndex`, `$itemIndex`, `$now`, `$today`, `$env` (allow-listed names only), `$vars`, `$run { id, startedAt, trigger }`, `$workflow { id, name }`, and `$secrets("<scope>/<name>")`, which resolves at run time and is redacted from every log line. A reference by label resolves through an id index, so renaming a node is a metadata edit and never a graph-wide rewrite.

Two tiers exist and the document says which is which:

- **Expressions** are evaluated in the daemon only, per item, with an explicit item index, by a sandboxed-by-construction evaluator with no host access — the JSONata library, with the binding namespace registered as its own variables and functions. One evaluation is budgeted at 5 ms and aborts when it exceeds it; an evaluation over budget refuses with a registered code rather than running on.
- **Programs** live in the Code node and nowhere else, on the WebAssembly interpreter of §Implementation Notes, with a memory budget and a deadline. A document a sidekick wrote or an import carried therefore never becomes executable text on the host under either tier.

Every secret value an expression resolves is added to the run's redaction set before the first log line of that step is written.

### Provider-limit pacing and durable resumption (SA-40)

Added 2026-08-16 (workflow-hardening amendment). A provider account that has spent its usage allowance refuses work. V1 treats that refusal as a **first-class park** — neither an execution failure nor a transient to be retried — because retrying into a spent account converts one refusal into a burned retry budget and then a false `failed` verdict on work the engine never got to try.

**C-19 — recognition is typed, and only typed.** The engine recognizes a usage-limit refusal from the driver's **normalized typed signal alone**. It MUST NOT recognize one from message text, provider prose, an error string, a rate-limit window's name, or a model id. Text-matching a refusal is forbidden for the reason Spec-004 gives for the driver boundary generally: prose is not a contract, it changes without a version bump, and a matcher that silently stops matching turns a park into a burned retry ladder with no signal that anything changed.

Three facts about the shipped driver surface fix what "typed" means here, and the third is a gap this amendment declares rather than fills.

- **The precedent for typed recognition.** [Spec-004 §Fallback Behavior](004-provider-driver-contract-and-capabilities.md#fallback-behavior) establishes the class: recovery conditions form a closed `RecoveryCondition` set whose `reauth-required` member is detected "mid-run via the provider's typed auth-failure signals", never by reading a message. A usage-limit refusal is the same class of fact — a provider-account state the driver observes and normalizes — and is recognized the same way.
- **The stamping discipline the carrier must follow, which is not the same as the field it stamps.** [Spec-004 §Interfaces And Contracts](004-provider-driver-contract-and-capabilities.md#interfaces-and-contracts) binds normalization at the driver boundary: the driver stamps `windowSource` (`provider_reported | model_default | estimated`) and computes the `exceeded` headroom predicate at normalization, "never deferring provenance or the derived predicate to consumers." This amendment adopts that **discipline** — provenance is stamped where the fact is normalized, never inferred by a consumer — and deliberately does **not** reuse that field. `windowSource` is the provenance of a **context-window headroom** reading ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)); a spent usage allowance is a different fact, and a context-window provenance stamp says nothing about whether a quota reset boundary is real.
- **The carrier does not yet exist, and this spec does not mint it.** No shipped surface carries a typed usage-limit refusal: `RecoveryCondition` is closed at `recovery-needed | reauth-required` and no registered driver error code names one. Spec-015 therefore **requires** the signal and states what it must carry — a closed-set cause identifying the refusal as a spent usage allowance, and, where the provider reported one, a reset boundary carrying its own provenance stamp on the `windowSource` model — while leaving the type's name and declaration site to Spec-004 and Plan-004, which own the driver vocabulary (one-writer). The shape must be a **sibling axis, not a widening of `RecoveryCondition`**: [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) already refused that widening once, minting `RecoverySpanClassification` beside `RecoveryCondition` because "the two axes answer different questions, and conflating them would overload operator-remediation routing." A usage-limit park needs no operator at all, so folding it into a set whose every member means _a human must act_ would misroute all of them.

**What the engine deliberately does not consume.** The account-plane `usage.rate_limit_update` snapshot — payload `{provider, providerAccountId, credentialGeneration, limitId?, windowMins, usedPercent, resetsAt?}`, keyed `(providerAccountId, limitId)` (erratum corrected 2026-08-26: this restatement was written before the 2026-08-18 account re-key and the 2026-08-26 per-limit re-key and had carried the pre-account shape; the sentence's point is unaffected, since what the engine declines to consume is the snapshot, not any particular member of it) — is the nearest existing surface and is **not** an input to any rule in this section. [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) scopes it as "a display/quota surface only, kept off the security/admission plane"; its `resetsAt` carries no provenance stamp; and its own consumer obligations are staleness defenses that resolve **fail-open to the freshest reading**. Arming an execution schedule off a display surface that is licensed to be stale and stamps no provenance would be precisely the guess the arming rule below refuses to make. It stays what it is: a quota display.

**The carrier landed 2026-08-18; this section is reachable.** The typed provider usage-limit signal this section depends on is minted at [Spec-004 §Fallback Behavior](004-provider-driver-contract-and-capabilities.md#fallback-behavior) as a sibling axis beside `RecoveryCondition` — typed-only recognition, a closed-set cause, an optional provenance-stamped reset boundary — so the park, the schedule, and the attention fold activate together as specified. What does **not** change is the prohibition that accompanied the wait: a provider or shape the driver cannot name emits no signal, that silence means _not known to be limited_ rather than _known not to be limited_, and it is never closed by reading message text. The supply cadence the carrier will ride is already fixed: [Spec-004 §Resolved Questions and V1 Scope Decisions](004-provider-driver-contract-and-capabilities.md#resolved-questions-and-v1-scope-decisions)'s bounded 15-minute per-runtime-node refresh with optional provider push (the Codex `account/rateLimits/updated` push alongside the `account/rateLimits/read` pull), and correctness here does not depend on the push arm.

**A recognized refusal parks immediately, and spends no ladder.** The phase suspends on the refusal itself. The park:

- consumes **no** `max_retries` attempt and mints **no** new `phaseRunId` — a park is not an attempt, and the resumed turn is the same attempt continuing;
- increments **no** `max_phase_transitions` counter — no phase boundary was crossed;
- happens **even when no reset window was reported**. A missing window changes only whether a schedule is armed (below); it never changes whether the run parks, and it never licenses one more attempt "to see". The refusal is itself the proof.

`max_duration` is the one bound a park does not stop: SA-2 defines it as workflow-run **wall-clock**, and a park is elapsed time. The deadline therefore stays authoritative over every rule below.

**A durable resume schedule, armed only where a boundary is real.** Where the typed refusal carries a reset boundary whose own provenance the driver stamped **provider-reported**, the engine arms `autoResumeAt` — a **durable value on the parked phase's persisted state, never an in-memory timeout** — and the run resumes itself when the window opens. The value is per-phase, not per-run: parallel branches of one run may park concurrently against different provider accounts with different reset boundaries (§Graph model — nodes, ports, and edges (SA-32)), and a single run-level schedule could hold only one of them — delaying or stranding the sibling. Where that provenance is the driver's default or its estimate, or where no boundary was reported at all, **no schedule is armed**: those values are the driver's honest admission that the number is a guess, and scheduling against a guess either fires into a still-spent account or holds a run that could have run. The gate is not invented here — [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) already fixes the rule for the whole corpus: estimated- and default-grade readings drive only reversible, soft responses, while "any costly or irreversible action keyed on headroom" requires provider-reported provenance. Holding a run asleep against a wall-clock instant is such an action. A parked run with no schedule is a normal, fully-visible, fully-resumable park — not a stuck one (§Park integrity and cancellability (SA-42)).

The schedule obeys five rules:

1. **Jitter is derived and scaled, never modular.** The armed instant is the reported boundary plus a jitter offset spanning a bounded window (V1: 0–120 seconds), computed by **scaling** a fixed-width prefix of the run's own derived digest across that span — `offset = span × prefix / 2^width` — so a wave of runs parked by one outage does not resume in a thundering herd. A modulus is forbidden: when the span exceeds the operand's range the modulus never wraps, so the spread silently collapses to a fraction of its declared width while every bound assertion still passes. The offset is a pure function of `workflowRunId`, so §Deterministic identity (SA-21) replay reproduces the same instant and the projection rebuild reconstructs the same row.
2. **The armed instant — and the park's attention key, where one was computed — are carried by the suspension event.** The engine writes both into the event payload before it is projected, so the durable columns are a function of the log and §Truth vs projection vs ephemeral (SA-25)'s rebuild-from-events rule holds without a special case.
3. **The deadline wins.** A schedule that would fall at or after the run's `max_duration` deadline is **not armed at all**; the run parks unscheduled and hard-fails at its deadline with `failure_reason` preserved, per §Fallback Behavior. The boot sweep applies the same rule, so a restart never resurrects a run past its deadline.
4. **Restart re-arms; it never fires inline.** On daemon start the sweep re-arms every schedule from its durable row **after** projection rebuild completes, and a past-due instant is re-armed at a short bounded delay rather than fired during rebuild — a timer that races the rebuild is deciding what the run is while the answer is still being computed. A durable value the sweep cannot decode is **quarantined, never fatal**: the run is left parked and unscheduled — a normal, fully resumable state — and the undecodable value is recorded in §Engine event record (SA-43) rather than raised as a wiring error. An engine that refuses to boot, or that parks every run at a configuration fault, because one row it wrote itself is no longer decodable has converted a single bad row into a total outage.
5. **Every exit clears it.** Every transition out of the park — the phase resuming, or the run being cancelled, failing, or completing — clears the parked phase's durable value and any armed timer, in the same unit of work as the transition. A cleared schedule is unarmed, not merely ignored.

**Firing re-checks, and an early resume is safe.** When the schedule fires, the engine re-checks that the run is still parked and still resumable, then makes a **real provider attempt**. If the account is still limited, the attempt receives another typed refusal and the run re-parks honestly against whatever boundary is now in force. Resuming too early therefore costs exactly one refused attempt and converges on the true unblock; it can never leave a run unrunnable.

**A fire that does not move the run is not an exit.** Rule 5's clear is keyed on the run _transitioning out of the park_, not on the timer having fired. Where a fire re-checks and then fails to transition the run — the engine is shutting down, the phase cannot be re-dispatched yet, the write loses a race — the durable value **stays armed** and re-arms at a bounded delay. Clearing on a fire that did not move the run is the worst available outcome: the run is left parked with its only route forward deleted, and nothing has recorded that it is stranded.

**One attention record per outage, and it is never an availability lock.** A single spent account can refuse many concurrently running workflows at once. Each affected run parks independently, on its own state, with its own cause — but the engine stamps each park with an **attention key** identifying the outage rather than the run: the provider, the account identity, and the credential generation held stable across the refusing dispatch. Runs sharing an attention key present as **one** attention record, so a wide refusal storm surfaces once rather than once per run. Three constraints keep this a fold rather than a mechanism:

- **A mixed failure is never folded.** A set of concurrently failed siblings collapses into one usage-limit attention record only if every one of them carries the same non-null attention key. Folding a genuine non-usage failure behind a familiar outage would make the only record an operator sees actively misleading — the "protection that isn't" class §Loud-errors discipline (C-12) forbids.
- **The record never gates anything.** Starting, resuming, retrying, and firing a schedule MUST NOT consult it, and it MUST NOT interrupt work already running. It is a correlation for presentation, not a lock on availability: a credential rotation or a quiet reset must never be able to leave a run unstartable because a record says an account was once spent. Any transition back to running invalidates a not-yet-surfaced record for that key, so a later refusal surfaces again rather than being suppressed by a stale one.
- **The fold fails open, and only toward more noise.** Where the correlation cannot be computed — the key is unavailable, the read fails, the account identity is ambiguous — the affected run surfaces **its own** attention record rather than none, and the refusal never reverts to a retry. Duplicated notifications are a cost. A refusal quietly rehabilitated into one more attempt against a spent account, or a park nobody is told about, are failures — so the only direction the fold is permitted to fail in is the loud one.

Durable cross-run memory of attention state — a per-watcher generation with a claim / deliver settlement lifecycle, its crash-reclaim rule, and campaign-scoped carry-over between separate runs — is explicitly **not** V1 (§Non-Goals, criterion-gated V1.1).

### Frozen-definition repair (SA-41)

Added 2026-08-16 (workflow-hardening amendment). §Fallback Behavior freezes a running instance on the version it started with, which is correct and load-bearing for replay — and which means a run parked against a defect in its own frozen definition has no route forward: the definition has been fixed, the run cannot see the fix, and the only remaining action is to abandon it and lose every completed phase output.

V1 therefore provides one governed repair: **an operator resuming a parked run may re-pin it to the definition's current version**, as an explicit, separately-requested action on the resume. The repair is bounded by six rules:

- **Explicit, never implicit.** Re-pinning happens only when the resuming operator asks for it by name. An ordinary resume always continues on the pinned version, unchanged. No timer, no schedule, no automatic recovery path ever re-pins — auto-resumption (SA-40) resumes the frozen version and nothing else.
- **Only while parked.** A running instance is never re-pinned. The frozen-version rule of §Fallback Behavior is unconditional for a run that is executing.
- **Only where no attempt of the run is in flight.** Parked is necessary but not sufficient. A re-pin takes effect only where the resume's next act is to **enter a phase fresh** — and, because the pin is run-level, only where **no other non-terminal phase of the run holds an in-flight attempt either**: parallel branches park independently (§Graph model — nodes, ports, and edges (SA-32)), and a parked sibling mid-attempt will continue that attempt later, so a re-pin admitted through one branch's fresh entry would still swap the definition under the sibling's already-dispatched work. Requested on a park whose resume **continues an in-flight attempt**, or while any parked sibling holds one, it is refused, loudly and typed, naming the blocking attempt and the explicit fresh-entry action that would discard it. The two arms are **one refusal point, not two**: the predicate is single — _some attempt of the run is still in flight_ — evaluated run-wide, and which phase holds the attempt changes what the refusal names, never what it is; the A-015-15 census counts it once, the same one-failure treatment the version-accountability rule below gives its two detection arms. The usage-limit park of §Provider-limit pacing and durable resumption (SA-40) is exactly the in-flight case by construction — it mints no new `phaseRunId` and its resumed turn is the same attempt continuing — so a bare re-pin there is always refused. Swapping the definition under an attempt whose work was already dispatched from the frozen bytes is incoherent rather than merely risky: the in-flight units were launched from a version the run would no longer be pinned to, so neither those units' inputs nor the outputs they return could be explained by the version the run's own record names. Refusing is the honest form of the boundary — quietly continuing on the frozen version would repair nothing while reporting success, and quietly re-pinning mid-attempt is the unreadable-history failure the audit rule below forbids. And the failure mode is concrete: an operator who fixes a parked phase's prompt and resumes expects the fix to have taken effect — absent this explicit boundary, the run re-renders the frozen prompt into an identical park with nothing telling the operator why, as many times as they retry.
- **Audited, in the log.** The repair is recorded as an additive-optional member on the `workflow.resumed` payload naming the version the run left and the version it joined — an additive MINOR payload bump under [ADR-018](../decisions/018-cross-version-compatibility.md), the same discipline the SA-26 dual anchor rides. No new event type is minted, and the projected run row stays a function of the log per §Truth vs projection vs ephemeral (SA-25). A silent re-pin is forbidden outright: it would make a run's own history unreadable, since the definition its early phases executed would no longer be recoverable from the run.
- **Completed work is preserved, never re-run.** Phase outputs are immutable (SA-16) and a repair rewrites none of them. The repair mints no new attempt for a completed phase and resets no counter — `max_retries`, `max_phase_transitions`, and the `max_duration` deadline all carry over exactly as they stood.
- **Refused when it would strand the run's own record.** The re-pin is refused, loudly and typed, when the target version does not contain every phase id whose outputs the run already holds, or when the target version's declared topology would leave a completed phase unreachable. Both are the same failure: a run whose record names phases its definition no longer contains cannot be replayed, verified, or explained. Refusal leaves the run parked and unchanged, on its original pinned version.

### Park integrity and cancellability (SA-42)

Added 2026-08-16 (workflow-hardening amendment). Two properties make a park a state an operator can act on rather than a hole a run falls into.

**Every park carries a bounded, engine-authored cause.** A suspended phase records a typed `parkReason` and a human-readable `parkCause`:

- `parkReason` is a closed union — at V1, `waiting-human` (the existing §Session timeline surfacing value) and `provider-usage-limited` (SA-40). Widening it is an additive MINOR bump under [ADR-018](../decisions/018-cross-version-compatibility.md) and moves the domain-lockstep pin, never a comment.
- `parkCause` is the engine's own sentence about why this run is waiting and, where a schedule is armed, **the instant it holds** — so the time named in the cause and the time in the durable schedule are one value read from one place, not two values that can drift.
- The cause is **bounded at 8 KiB, truncated at a UTF-8 code-point boundary with a visible truncation marker**. A durable, operator-facing, engine-authored string with no bound is an unbounded write on the projection tier.
- All four park fields — the two record fields here and SA-40's armed instant and attention key — are carried by the suspension event's payload and projected from it, so §Truth vs projection vs ephemeral (SA-25)'s byte-equal rebuild holds.
- The cause is **never** written into a phase output, an artifact, or an agent-visible context. Engine prose delivered through a model-output channel is read as something a model said, which makes the engine's own diagnosis indistinguishable from generated content — and phase outputs are immutable truth (SA-16), so an engine sentence written there is unretractable.

**A parked run is always cancellable.** Cancellation is a legal transition into the `cancelled` run status from **every** suspended or waiting state, without precondition and without waiting for anything:

- It is **pure bookkeeping and therefore cannot block**. A parked run holds no resource-pool reservation (pool state is ephemeral and re-requested — §Truth vs projection vs ephemeral (SA-25)) and no live phase process, so there is nothing to drain, interrupt, or wait on. A cancel that could be refused, queued, or made to wait for a provider window would reintroduce exactly the stuck state this rule exists to remove.
- It **clears the durable resume schedule** in the same unit of work, so a cancelled run can never be resurrected by a timer armed before it was cancelled.
- It **preserves the record**. The parked phase-state row's state, its `parkReason`, its `parkCause`, and every completed phase output survive cancellation untouched — they are the account of why a human was asked and what the run had achieved, and losing them at cancel would make cancelling the operation that destroys the evidence. The phase's **live** fields — the armed instant and the attention key — are instead cleared by the same cancel per SA-40 rule 5: record and live state sit on one row and part ways at exactly this boundary.

**Recorded residual — closed 2026-08-18.** V1 ships the rules above as engine state-machine rules, and the operator control surface that invokes them is now minted, as the separate deliberate contract addition this paragraph called for. The gate it named, [BL-151](../archive/backlog-archive.md), is `completed`; §Operator run control (SA-45) below is the landed surface, and §Park surfacing on the read model (SA-44) is what makes the state it acts on legible. The structural constraint this paragraph fixed in advance held exactly as written: the operation set and the run-cancelled lifecycle event minted **together**, because a durable cancellation the log cannot reconstruct would break §Truth vs projection vs ephemeral (SA-25) — a projection rebuild would replay the last `workflow.phase_suspended` payload, restore its schedule and attention key, and resurrect a run the operator cancelled. The auto-resume path of SA-40 was never part of the residual: it is engine-internal and needs no wire producer. What moved at the closure, and nothing else: the wire registry eleven → **thirteen** rows and §Event types (SA-19) 23 → **24** types across the same five categories. The nine-table schema is unchanged — the four park columns and the `cancelled` run status the surface reads and writes have been on disk since the workflow-hardening amendment.

### Park surfacing on the read model (SA-44)

A parked phase MUST be renderable from **one** `workflow.runRead` response — no timeline replay, no second call, no client-side reconstruction from event history. The park is the state an operator is most likely to be looking at and least able to explain from a status word alone, so the read model carries its reason rather than deferring to the log.

- **Four members, additive-optional.** `PhaseState` carries `parkReason`, `parkCause`, `autoResumeAt`, and `parkAttentionKey`, mirroring the four per-phase park columns. All four are additive-OPTIONAL per [ADR-018](../decisions/018-cross-version-compatibility.md) on an already-published shape; readers MUST tolerate their absence, which is also what an older daemon emits.
- **Live, not record — the rule that makes them readable.** The projection **columns** are a durable record that survives resume and cancellation (SA-42's preserve-the-record rule depends on exactly that). The wire **members** are a live view of it: a daemon emits them for precisely those phases parked at the moment the response is built, and emits none of them for a phase that is not — including a phase that parked earlier in the run and has since resumed, whose columns still hold the record. The wire therefore gives a stronger guarantee than the columns do, deliberately.
- **`parkReason` is the wire discriminator.** Because emission is live-scoped, its presence means _this phase is parked now_ and its absence means _it is not_. `parkCause` is present whenever `parkReason` is — SA-42 requires a parked phase to always carry one. `autoResumeAt` and `parkAttentionKey` are present only where the park armed them (an SA-40 park whose provider reported a reset boundary); their absence **narrows** the park to the unscheduled, operator-resumable kind rather than denying it.
- **The phase-run status union is NOT widened.** `PhaseState.state` stays the five values of §Phase-Type and Gate-Type Taxonomy. This is the reason the liveness rule is required rather than convenient: the coarse union carries no `suspended` arm, so a reader given only column mirrors could not separate a phase still waiting on a human form from one that already resumed past that wait. Widening the union instead would move the domain-lockstep pin, the conformance row that checks it, and every reader switching on five values — a breaking-shaped change to avoid a problem one producer rule solves.
- **Per-phase, never per-run.** SA-32 branches park independently against different provider accounts, so a run-level park field could hold only one of them. `WorkflowRunReadResponse` grows no park member of its own; the run's `waiting` status says _something is parked_ and the phase states say _what and why_.
- **No new disclosure.** `parkCause` is engine-authored and bounded by I-015-21 and reaches no phase output, artifact, or agent-visible context. Surfacing it on a read the caller is already entitled to make adds no recipient.
- **Accepted consequence: a finished run shows no park members.** The liveness rule is exhaustive, so a run that resumed, succeeded, failed, or was cancelled emits none of the four on any phase — including a phase whose `park_reason` and `park_cause` columns still hold the record SA-42 deliberately preserves. This is intended, not an oversight: the wire members answer _why is this parked now_, and asking _why was this parked once_ is a history question the timeline answers, since every park emitted `workflow.phase_suspended` carrying the same cause. A cancelled run additionally carries its cancellation reason on `failureReason`. If a post-hoc park summary is later wanted on the read model it is a separate additive member with its own name, never a loosening of this rule — a member that sometimes means _now_ and sometimes means _once_ is the ambiguity this rule exists to remove.

### Operator run control (SA-45)

The engine rules of SA-40 through SA-42 are reachable over the wire through exactly two operations. Both are operator actions on a run, both are authorized as named Cedar operation actions, and both refuse through registered codes.

- **Two operations over one run, not three.** `workflow.runCancel` cancels a run. `workflow.runResume` resumes a parked run and carries the SA-41 re-pin as an **optional member of the resume request**, not as an operation of its own — SA-41 defines the repair only as an action on a resume, so a separate operation would admit the re-pin-without-resume shape that section refuses. Fixing a failed step in a fresh session is not a third one either: it opens a session and changes nothing about the run (§Workflow Timeline Integration).
- **Cancel and its event mint together.** A run reaches the `cancelled` status durably only by appending `workflow.cancelled` in the **same unit of work** as the status write. This is not a logging convention: without it a projection rebuild would replay the last `workflow.phase_suspended` payload and resurrect a run the operator cancelled (SA-25). `workflow.cancelled` is a member of the `workflow_lifecycle` category, and its payload carries the operator's supplied `reason`, bounded exactly as `parkCause` is.
- **`workflow.cancelled` clears the live park fields of the whole run — a projector rule, not only an engine rule.** On applying `workflow.cancelled` the projector sets `park_reason`, `park_cause`, `auto_resume_at`, and `park_attention_key` to `NULL` on **every** phase row of that run, and does so from the event alone. Stating this only as an engine rule would leave the invariant unverifiable against the artifact it quantifies over: a rebuild that replays `workflow.phase_suspended` and then a `workflow.cancelled` carrying nothing but a reason has no other instruction that would clear what the suspension set, so the rebuilt row would carry an armed schedule for a run that is over. The rule is deliberately **run-scoped and unconditional** rather than payload-enumerated — a workflow with parallel branches can hold several parked phases at once, and a payload that listed them would have to enumerate them correctly to stay byte-equal, adding a way to be wrong for no gain. Every phase of a cancelled run is unparked by construction, so clearing all of them is the same write as clearing the right ones.
- **Cancel is unconditional on a parked run, idempotent on a cancelled one, and refused on a finished one.** SA-42's without-precondition rule is unchanged and is why no code names a refused cancellation of a parked run. A second cancel of an already-`cancelled` run replays the original event's identity rather than writing again — a retried operator action must not cost a clear answer. A cancel against a run that reached `succeeded` or `failed` refuses `workflow.run_not_cancellable`, because answering "cancelled" for a run that ran to completion would misinform the operator about what their action did.
- **Resume requires a park, and does not require the schedule to have elapsed.** A resume against an unparked run refuses `workflow.resume_not_parked` — distinct from `workflow.repair_not_parked`, which refuses the re-pin leg, so an operator can tell whether dropping the re-pin would have worked. Resuming **ahead of** an armed `autoResumeAt` is permitted and needs no override flag: the armed instant is advisory pacing derived from what a provider reported, and the worst outcome is that the account is still spent and the phase re-parks, emitting its own `workflow.phase_suspended`. That re-park is a legal response, not a refusal, and is visible in the timeline and on the next read.
- **Authorization is a named operation action, not an approval category.** `workflow.runCancel` adjudicates `Action::"workflow::cancel"` and `workflow.runResume` adjudicates `Action::"workflow::resume"`, each on the target workflow run, through the same `PermissionCheckService` seam SA-39 uses for `Action::"workflow::start"`. They are **separate actions from start and from each other**: start creates work, cancel destroys it, and resume commits further spend against a provider account — one action covering all three would make "may start a workflow" silently mean "may cancel a run already committing spend". A denial refuses `workflow.control_denied`, naming which action was denied, since the two are separately grantable. Registering both actions in the Cedar schema is Plan-010 surface, not Plan-015's; until it lands, both operations fail closed for every principal but the node owner, the same shape SA-39 already ships for start.
- **Refusals are total.** Every refusal above leaves run status, phase rows, armed schedules, and phase outputs byte-identical to their pre-request state. Resolution and validation complete before any write.

**A third operation addresses no run at all: the hold on starting.** One switch, **Pause new runs**, holds every new start — a schedule fire, a webhook, a file event, a chat verb, a sidekick's own run tool and Run now alike, because it is a hold on starting and not a filter on triggers — while a run already going finishes untouched. The switch's own words carry the count of what is waiting, `Pause new runs · 3 waiting`, and switching it off starts what waited, in the order it arrived. The hold is one state per daemon over its whole scheduler, not a property of a workflow: the enabled toggle arms and disarms one workflow's triggers and stays that way until someone changes it back, while this holds every workflow's starts at once and is meant to be switched back the same minute. One method sets the hold and answers with how many starts are waiting, and the hold and its count also ride the run subscription, so every open surface reads one truth rather than its own guess.

**The queue of runs that need a person is walked, not hunted for.** One control, **Next waiting (N)**, opens the next run that is waiting on a person, and pressing it again once that one is dealt with opens the one after it. It takes them from the top of the list down, so the walk and the table agree about which one is next, and the filters above the list never narrow it, because it is the queue of what needs the person rather than a view of the table. N reads how many such runs there are other than the one open, so from the list it reads the whole queue and from a run's own page it reads how many others are still owed an answer. A run waiting on an account rather than on a person — parked on a spent provider account, with its own resume instant — is never in it, because nobody can answer that one. With none left the control stays in place, disabled, reading `Nothing waiting`, rather than disappearing: a control that comes and goes as runs arrive moves everything beside it under the pointer just as someone reaches for it.

**A run has four acts and each keeps its place.** `Re-run`, `Cancel` and `Resume` stand in the run's header and `Retry from this step` in a step's own panel. Each keeps its place whatever state the run is in, and a state that does not allow it refuses in words that say why rather than the control quietly not being there. Cancel is available on a running or waiting run and replays idempotently on an already-cancelled one; Resume is available on a parked run; retry-from-step re-runs that step and its descendants with the prior run's data pinned upstream. The builder carries the same acts where the author is looking: its one run control reads `Run now` at rest and `Cancel` while the run it started is live — the same outline style, no stop glyph and no red — and the announcement reads `Run cancelled`. A workflow run is cancelled, never interrupted, because nothing steers it, and one word covers the act wherever it is taken.

### Loud-errors discipline (C-12)

- Unknown integration name, missing required input, typo in expression, unknown node reference, unknown resource pool, unknown approver principal — all must fail loudly at `WorkflowDefinitionCreate` or at phase launch. Silent no-ops forbidden by default. n8n 1.0 had to break silent-error-passing behavior users had built on — the V1 chance to avoid that is now.
- Workflow step outputs referenced by downstream nodes must resolve at definition time (by shape) and at execution time (by presence). Missing-output is never silently coerced to empty string.

**One spelling of failure per node.** A node carries `onError` with exactly three dispositions — `stop`, `continue`, `continue-error-output` — the third materializing a real `error` output handle the failed items route to. Beside it sits `retry { maxTries, waitMs }`, and the engine clamps both: the clamps are the engine's and are never trusted from the document, because anything user-editable that costs money needs its bound held somewhere the author cannot edit. There is no second error setting and no `continueOnFail`. An error may also ride a single item, so one item of a batch can fail while the rest succeed.

**One spelling of failure per run.** A run observes cooperative cancellation through an abort signal every executor can see, obeys the optional run cap of §Execution semantics, and can be failed on purpose by a stop-with-error node, so a deliberate failure is a visible element of the graph rather than a hidden setting. Every failure lands in the session event log and on the node itself; the error trigger that fires when another workflow fails is sugar on top of that record, never the primary channel.

**Advisories are not errors.** A step may attach non-fatal hints — an unwired branch that dropped items, a deprecated param, a truncated output — and they render as a strip above the step's output rather than as a failure, so the one red treatment keeps meaning one thing.

## Default Behavior

- Workflow phases default to sequential execution unless the definition explicitly marks safe parallelism. When explicitly parallel, default `ParallelJoinPolicy` is `fail-fast`.
- Each `single-agent` / `automated` phase defaults to one primary target channel and one primary producing run.
- `multi-agent` phase defaults to `ownership: OWN` — V1 default and only value (SA-6).
- `multi-agent` phase-owned channel defaults differ from bare-channel defaults on four axes (SA-8 / Pass B §3.3):
  - `turn_policy: round-robin` (bare-channel default `free-form`)
  - `turns_per_agent`: formula-bounded, indicative max 20 (bare-channel 50)
  - `membership`: phase-targeted agents only (bare-channel: all session agents)
  - `moderation`: `off` for `auto-continue` / `done` / `human-approval` gates; `post-turn informational` for `quality-checks` gate
  - All other bare-channel defaults (token budget, cost limit, idle timeout, scheduler limits, partition behavior) unchanged.
- `multi-agent` channel termination defaults to `CLOSE_WITH_RECORDS_PRESERVED` on phase completion (SA-9). This inverts Temporal's `TERMINATE` default because the workflow engine inherits channel transcripts as phase-output source material. Phase failure drives `REQUEST_CANCEL` with 30-second grace period. Retry creates a new channel per iteration (prevents BIND-like cross-iteration state leak).
- Workflow definitions default to immutable-by-version: editing a workflow creates a new version rather than mutating a running definition in place.
- Workflow definition reads default to the canonical persisted definition record for the requested scope and version rather than to an artifact manifest.
- `human` phase forms default to primitive-type JSON schema fields (`text` / `long_text` / `number` / `integer` / `boolean` / `enum`) plus optional `artifact` field referencing a Plan-012 pre-uploaded `ArtifactId`. No in-form file upload — uploads are out-of-band via Plan-012 (SA-10; Pass C §3.2).

## Fallback Behavior

- If a later phase depends on unavailable capabilities, the workflow must pause in a blocked state instead of silently skipping the phase.
- If a workflow definition changes while an older version is running, the running instance must continue on the version it started with.
- If a phase output is large or unavailable inline, the workflow timeline must link to a durable artifact reference instead of dropping the output.
- If a `multi-agent` phase's channel fails to create (resource exhaustion, moderation-backend unavailable), phase admission blocks until preconditions are met or the run's `max_duration` deadline fires.
- If a `human` phase is claimed by one user and then abandoned, optimistic-concurrency must allow re-claim on next open (SA-10). Assignment model: implicit claim on first open; optimistic-concurrency reject on submit if version mismatch.
- If `RUN_ITERATION_LIMIT` or a set `max_duration` fires mid-run, the workflow moves to `failed` with `failure_reason` preserved; all completed phase outputs remain addressable. A set `max_duration` continues to elapse while a run is parked on a provider account (SA-2 measures wall-clock), so a parked run reaching its deadline fails there rather than resuming — and no resume schedule is ever armed past it (§Provider-limit pacing and durable resumption (SA-40)).
- If a provider refuses a phase's work with a typed usage-limit signal, the phase parks rather than failing and rather than retrying: the retry ladder is not entered, no attempt is consumed, and the run stays fully visible and resumable with a stated cause (§Provider-limit pacing and durable resumption (SA-40); §Park integrity and cancellability (SA-42)). A refusal carrying no provider-reported reset boundary parks with no schedule — an unscheduled park, never a silent one. The Runs tab renders it as parked with its cause and, where one is armed, the instant it will resume itself; a park with no armed instant renders as awaiting resume rather than inventing a time, and the resume then happens without the user acting.
- If a resume — scheduled or operator-invoked — reaches a provider that is still refusing, the run re-parks against the boundary now in force rather than failing or looping. An early resume costs exactly one refused attempt.
- If a parked run's frozen definition is the reason it is parked, the operator may resume it onto the definition's current version as an explicit, audited re-pin at a resume that **enters a phase fresh**, which the engine refuses in each of three cases — a run that is not parked at all, a target version that cannot account for the phases the run has already completed, and a repair requested while any of the run's attempts is still in flight — the resuming phase continuing one, or a parked parallel sibling holding one (§Frozen-definition repair (SA-41)). Absent that request, the run resumes on its pinned version unchanged.

**Refusals the builder can compute locally land in the validation strip**, one row each, each clicking through to the node it names: a cycle, an orphan node, a document with no nodes, a missing or duplicate trigger, an edge into the trigger, a terminal node with an outgoing edge, a missing required param, an expression that does not parse, an expression naming a node that no longer exists, and a capability edge into a node that has no capability input.

**A refusal from the daemon is rendered on the nodes it names** and leaves the draft editable. The registered codes are used as they stand — the definition-not-found, invalid-transition and gate-closed codes; the start-denied code for a denied or unresolvable start and for a session the starter cannot see; the control-denied, not-cancellable and not-parked codes for the operator controls; and the three re-pin codes for a repair the run's state forbids. The refusal points this surface adds — an unarmable trigger, a webhook token mismatch, a Code node over its memory or time budget, an expression evaluation over budget, and an import whose schema version is unknown — each land with a registered code in the same change as the refusal itself, and none ships unregistered (§Loud-errors discipline (C-12)).

**A failed step is legible where it failed.** The node carries the first line of its error and its failing item index, the run's status is `failed`, and the run's detail opens on that step's error. A step whose node routes its failed items to an error handle instead continues the run down that branch.

**A missed fire is one of two things and the run says which.** A schedule whose fire was missed because the daemon was down either skips the occurrence or catches up exactly once, per that schedule's own policy, and the run's trigger record records which happened.

**An operation that is not live on the wire yet answers the console's own unavailability refusal**, and every surface renders that absence rather than a control that looks available and does nothing.

- `WorkflowDefinitionCreate` must persist the document and version metadata with its schema version marker (C-8). The stored body embeds the whole declared topology — the node list and the edge list (§Graph model — nodes, ports, and edges (SA-32)) — so the stored bytes are the complete executable graph and no edge lives outside them.
- `WorkflowDefinitionCreate` with target scope `shared` — direct authoring, file import, and the §Definition scope in the builder (SA-36) promotion alike, which all ride the one operation — must adjudicate the daemon's operator-scope authorization through the Plan-010 Cedar evaluation surface (`PermissionCheckService`) against the daemon-resolved node-owner user identity before any row is written, the same boundary Spec-025 §Authorization applies to governance mutations. A principal that does not resolve to the node owner is refused with a typed error, the check fails closed while the identity-resolution seam is unwired, and a refusal never silently downgrades the request to a narrower scope.
- `WorkflowDefinitionRead` must return the canonical definition record and selected version metadata for the requested scope.
- `WorkflowDefinitionList` must enumerate the definitions visible to a caller, resolving scope most-specific-first — the caller's session, then its project, then the daemon's `shared` tier — and deduping on `(scope, scopeRef, contentHash)`. Enumeration is not optional polish: every other operation here addresses a definition by an id the caller must already hold, so without it a definition that is not already known cannot be reached at all, and the `session` / `project` / `shared` breadth would be unobservable.
- `WorkflowRunStart` must bind a workflow version to a session and create phase execution state.
- Definition/execution entity separation: `WorkflowPhaseId` identifies a phase in the definition (static), and because a phase is one of the document's nodes (§Graph model — nodes, ports, and edges (SA-32)) it is that node's id, so a phase's state row and the step rows of the same node are keyed by one string; `PhaseRunId` identifies a specific execution (with iteration number, status, timestamps). `PhaseRunId` is deterministically generated as `BLAKE3(workflowRunId || phaseDefinitionId || attemptNumber)` (SA-21 — see State And Data Implications).
- `PhaseOutputRead` must expose durable phase outputs and artifact references.
- `WorkflowGateResolve` must resolve workflow-scoped approvals or user questions; gate resolution rows are append-only hash-chained per §State And Data Implications.
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

**One declarative description per node kind is the whole contract.** A kind declares its id and category, the name a person reads and the one line under it, its icon, any palette search aliases, its input and output handle specs, its param specs, the one-line summary it computes from its params, whether it executes once per item, the credentials it needs, and its capabilities — whether it is cancellable, whether it is resumable, and whether its side effects are none, local or external. That one description drives the parameter form, the canvas ports, the palette entry, the node's summary line and the validation; everything else is a generic renderer over it.

- A handle spec carries its id, its label, its type — `main` for items or `tool` for a capability — and optionally how many connections it accepts and whether it is required. A kind's output set may be a function of its params rather than a fixed list; the one kind that needs it is the switch, and the canvas re-registers a node's internals immediately after any param write that changes the set.
- A param spec carries its id, its label, its type, whether it is required, its default, its help line, its options, and the sibling-param values under which it is shown. The type is one of a closed list: text of one line or many, number, boolean, single or multiple choice, JSON, expression, path, glob, cron, secret, sidekick, an MCP tool, a session, or a channel; a collection param holds a list of nested param specs and may repeat. `provider-account` is deliberately not a member: an account means nothing until the provider is known, and the one kind that needs both reads them from the sidekick it names (§Multi-agent phase — `ownership: OWN` at V1 (SA-6, SA-8, SA-9)).
- The shown-when rule is the whole conditional-form engine; a param whose condition is unsatisfied is hidden, not disabled.
- An executor is one function: it takes a step context plus one array of items per input handle and returns one array of items per output handle, an empty array meaning that branch is dead.
- One registry is the only list of kinds, `workflow.kindList` serializes it, the palette renders it, and a sidekick reads it before authoring. A kind's version is written into the node once at insert and never migrated: a kind ships its implementations side by side and the loader resolves the exact one the document names, so a saved workflow never needs a migration pass.

### Workflow gate scope vs channel gate scope (SA-7)

Workflow gates (`WorkflowGateResolve`) and channel moderation gates (Spec-014 per-turn) share the Plan-010 approval backend but are **temporally disjoint** (Pass B §3.2):

- Channel-level gates fire per-turn with `scope: channel`.
- `WorkflowGateResolve` fires at phase boundary with `scope: workflow-phase`.
- Pending channel gates **block** phase transition to `completed`. A phase cannot complete while its owned channel has an unresolved moderation gate.

### Multi-agent phase — `ownership: OWN` at V1 (SA-6, SA-8, SA-9)

`multi-agent` phase at V1 supports `ownership: OWN` only:

- Phase B receives phase A's channel transcript as read-only context via SDK ergonomic `inheritContext: { from: "previous_phase" }`.
- Retry creates a new channel per iteration — never reuses a phase-owned channel across attempts.
- `BIND` (multi-phase channel reuse) is committed to V1.1 under three named criteria in [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments): (a) ≥3 production reports of OWN+transcript-inheritance insufficient, (b) concrete failure case documented, (c) BIND lifecycle contract addressing the five ambiguities recorded canonically in [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments).
- Modern multi-agent composition convergence (2025–2026) is **state-passing, not handle-binding**: Temporal Child Workflows + Signals ([Temporal — Child Workflows](https://docs.temporal.io/develop/typescript/child-workflows)), LangGraph `Command(goto, state)` ([LangGraph multi-agent handoff](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)), AutoGen `HandoffMessage` ([AutoGen Teams](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)), OpenAI Assistants API Threads removal ([OpenAI Assistants deprecation, Threads removal 2026-08-26](https://platform.openai.com/docs/assistants/migration)). Airflow SubDAG — the closest BIND analogue — was deprecated in 2.x because its shared-scope ambiguity took 3+ years to patch ([Airflow — Deprecate SubDags in Favor of TaskGroups, #12292](https://github.com/apache/airflow/issues/12292)).

**A step that runs a sidekick is a first-class run, not a thin model call.** It has a provider account, a sidekick definition, a posture, a tool allowlist, approvals, a cost receipt and park-and-resume, because it is the same pipeline a session's own run uses. Which sidekick runs it, and which account pays, are **params on the node**, never wired sub-nodes:

- The node's one chooser is the sidekick. It is a popover over the sidekick definition list the sidekick library owns — the same list the session composer's own sidekick group draws — and it carries one entry at the top, **General**, meaning the provider's own sidekick with no saved definition, with every saved sidekick following.
- Once General or a sidekick is chosen, four rows stand under it — **Provider**, **Model**, **Effort** and **Account** — prefilled from the sidekick's saved setup for that provider, or from the defaults for General, and each changeable for this node alone. A changed row is marked as the author's own and carries a reset back to the sidekick's value.
- Provider lists both providers. Model lists that provider's models and stands blank, and must be chosen, where the sidekick has no setup saved for that provider: a model is never guessed. Effort offers the one ladder the console uses everywhere — Minimal, Low, Medium, High, Extra high, Max — narrowed to what the chosen model publishes, reading `Not set` where the sidekick saved none and `Not published by this model` where the model publishes no ladder at all. Account lists that provider's accounts exactly as the accounts page lists them, each by the identity the provider itself reports at sign-in, with its billing and default marks, plus one `Default` entry at the top meaning whichever account is marked default when the run starts; never a label of ours, no invented names and no computed suffixes.
- With General chosen the same four rows show, prefilled from the defaults: Provider preselects the first provider, in the accounts page's order, that has an account marked default, and stands blank where none has one; Model reads that provider's default model; Effort is not set; Account reads `Default`.
- The node stores the chosen sidekick plus only the rows the author changed. A node whose rows all read the sidekick's own values stores no binding at all — except General, whose provider always travels, because no global default provider exists to fall back on — and nothing a node changes is ever written back to the sidekick's own definition.
- There is no second account control and no provider-accounts list on the node: the account means something only once the provider is known, and two controls setting one value can disagree.
- The chooser and the node's own rows read the definition list on every read. A sidekick renamed in the library shows its new name on the node at the next read, and one deleted on this machine clears the node's choice with a one-line notice and never sends an id it can no longer see.
- The node's name is `Run a sidekick`, and the on-screen word for the provider is **Provider**, never driver: `driver` is the adapter's name in code, on the wire and in specs only.

### Human phase — `HumanPhaseConfig` (SA-10, SA-11, SA-12)

Human-phase authoring uses the `HumanPhaseConfig` type:

```typescript
type HumanPhaseConfig = {
  prompt: string;
  inputSchema: JSONSchema7; // primitive-type fields + optional artifact ref
  dueAt?: Duration;
  timeout: "none" | Duration; // REQUIRED — no default; author must opt in
  timeoutBehavior?: "fail" | "continue" | "escalate"; // default 'fail'
};
```

- `timeout` is **required** at the SDK-type level — no field-default footgun (Wave 1 §5.1 SDK ergonomic safeguard). Author must type either `"none"` (no deadline; session timeline shows `waiting-human` until resolved) or an explicit `Duration`.
- Three independent durable-execution engines converge on no-default-timeout: [Temporal Workflow Execution Timeouts](https://docs.temporal.io/encyclopedia/detecting-workflow-failures) default ∞, [Argo — Suspending Workflows](https://argo-workflows.readthedocs.io/en/latest/walk-through/suspending/) with `{}` = indefinite suspend, [Camunda 8 User Task dueDate](https://docs.camunda.io/docs/components/modeler/bpmn/user-tasks/) optional/expression-based. This is modern durable-execution convention across independent implementations — not one-camp disagreement.
- `timeoutBehavior: 'escalate'` emits the `workflow.human_phase_escalated` telemetry event only at V1 (SA-11). No paging primitive exists; default-timeout is reconsidered V1.x once notification routing ships (see [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments)).
- `human` phase uses the new Spec-010 approval category `human_phase_contribution` (SA-12). See [Spec-010 Approvals](../specs/010-approvals-permissions-and-trust-boundaries.md).
- Deep-link URL: `/session/:sid/workflow/:rid/phase/:pid`. A draft is autosaved to the daemon through `workflow.humanFormDraftSave`, one draft per phase run and person, so a half-filled form survives a reload; nothing typed is written to window storage.

### Adapter contract (SA-15)

- First-party adapters (Codex, Claude, MCP tool adapters, channel surfaces) ship as separately-versioned packages under `@ai-sidekicks/adapter-*`. Core exposes an adapter contract via `packages/contracts/`. No `src/adapters/` folder inside core (C-6).
- Adapter-bundling precedent cost: Airflow `airflow.contrib` was force-split into 61 provider packages in the 2.0 release ([Airflow 2.0 providers](https://airflow.apache.org/docs/apache-airflow-providers/)).

### External tool references — content-addressed (C-7)

- External tool references in workflow definitions (e.g., `codex@v1.2.3#sha256=...`) must be content-addressed with hash pins. Mutable tags must not be trusted for externally-referenced definitions.
- This closes the [tj-actions/changed-files CVE-2025-30066](https://nvd.nist.gov/vuln/detail/CVE-2025-30066) retroactive-tag-repointing class (23,000 repositories compromised by a single upstream tag repointing).

### Secrets — by reference only (C-15)

- Secrets are referenced via `secret://<scope>/<name>` and resolved at phase-launch into environment variables, stdin, or a named-file file descriptor — **never argv**. Logging redaction is defense-in-depth, not primary control. Closes the argv-exposure vector documented in CVE-2025-30066 (runner memory dumped to logs via argv).
- A node never stores a secret, an account credential, or a governance decision. A credential param carries a `secret://` reference; a provider param carries a provider-account id; a tool param carries a scope-qualified binding identity.
- Resolution happens at step launch, inside the daemon. The step record stores the reference and never the value, and every resolved secret is redacted from that step's logs, payloads and error messages before any of them is written.

## State And Data Implications

**The document.** A workflow is one JSON document, and its canonical bytes are the JCS canonicalization of the hashed field list, BLAKE3'd (§Authoring + versioning). It carries:

- `schemaVersion`, whose V1 value is `2`;
- `name` and an optional `description`;
- `trigger` — exactly one node, of a kind in the trigger category;
- `nodes` — everything else;
- `edges`, each one `{ id, source, sourceHandle, target, targetHandle }`;
- `layout`, optional and **outside** the hashed body: a position per node, an optional viewport, and the sticky notes;
- `pinData`, optional and outside the hashed body: an item array per node id.

A node carries its id, its kind, the kind version written at insert, its display name, its sibling `order`, its params, and optionally whether it is disabled, its notes, its `onError` disposition, its `retry` bounds, whether it executes once over the whole input, and whether it always outputs data.

**The document holds no settings block**, because each concern one would carry has a home of its own: what a failure does is set on the node that failed, how long step data is kept and how long a run may work are the two controls on the console's Runtime settings page, and the clock a schedule reads is a param on the schedule trigger itself.

**The tables.** Thirteen tables hold the surface. Nine are the schema the workflow engine already specifies — `workflow_definitions`, `workflow_versions`, `workflow_runs`, `workflow_phase_states`, `phase_outputs`, `workflow_gate_resolutions`, `parallel_join_state`, `workflow_channels`, `human_phase_form_state` — with `workflow_definitions` and `workflow_versions` carrying the document body as the hash preimage and a layout column beside it, because layout is outside the hash (§Canvas layout is not definition bytes (SA-35)). Four are added:

| Table | Holds |
| --- | --- |
| `workflow_steps` | One row per step attempt: run id, node id, attempt, execution index, the source array, status, timings, the three payload references, cost, error. |
| `workflow_triggers` | One row per armed trigger: workflow id, node id, kind, config hash, next fire, last fire, whether it is enabled. |
| `workflow_webhook_tokens` | One row per workflow that has a webhook trigger: the token hash, when it was created, when it was last used. |
| `workflow_node_state` | The per-(workflow, node) key-value store that holds trigger cursor state, so no mutable field lives on the document. |

A payload over 64 KiB becomes an artifact and the step row keeps the reference; below the cap it is inline JSON on the step row.

### Truth vs projection vs ephemeral (SA-25)

Workflow state separates into three tiers:

- **Truth (source-of-truth):** `workflow_definitions` (content-hashed), `workflow_versions`, `phase_outputs`, `workflow_gate_resolutions` (hash-chained). These, together with `session_events` (Spec-005), are authoritative. Daemon must be able to rebuild everything else from them. Three of the four added tables join this tier as **mutable** truth rather than immutable truth: the armed-trigger rows, the webhook token rows and the per-(workflow, node) key-value store are facts about what this machine is armed to do next, which no event history can reconstruct — the durable row is the truth and the in-process timer is only a cache over it, re-armed from the row after a restart (§Entry node and the V1 trigger surface (SA-37)).
- **Projection (rebuildable):** `workflow_runs`, `workflow_phase_states`, `workflow_steps`, `parallel_join_state`, `workflow_channels` — rebuildable via a `ProjectionRebuild` path owned by Plan-013 ([Temporal — Custom persistence layer, 2024](https://temporal.io/blog/higher-throughput-and-lower-latency-temporal-clouds-custom-persistence-layer)). The per-step record is a projection over the events the run, approval and form pipelines already emit, which is what keeps one step's history a function of the log rather than a second account of it.
- **Ephemeral:** pool reservation state is not persisted — re-requested on daemon restart; no runtime pool-counts rows.

The park-and-resume state stays inside this split rather than beside it: the durable `autoResumeAt` schedule, its `parkAttentionKey` fold key, and the `parkReason` / `parkCause` record all sit on the phase-state projection — per-phase, because parallel branches park independently and a run-level value could hold only one park (§Provider-limit pacing and durable resumption (SA-40); §Park integrity and cancellability (SA-42)). All four are **projection**, not truth, and every one of them is carried by the event that produced it — the suspension event for all four park fields, the `workflow.resumed` event for a repair's version re-pin — so the rebuild-byte-equal-from-`session_events` rule holds with no exception and no schedule survives a rebuild that the log does not contain.

Workflow definitions, versions, and phase outputs must be durable and replayable. Workflow and run histories must remain cross-linked for audit and replay. Optional workflow exports, previews, or summaries may be published as artifacts, but those artifacts are derivative views and must not replace the canonical definition store. Running workflows require phase-state persistence separate from UI state.

Plan-015 specifies the concrete SQLite schema (SA-24 lands there — implementation detail, not spec contract).

Canvas layout is not a fourth tier: it rides the definition document's own `layout` section, outside the hashed body, persisted in a column beside the definition body, per §Canvas layout is not definition bytes (SA-35). It is mutable per author and changes no byte the engine reads, which is why it neither mints a version nor enters a rebuild.

### Deterministic identity (SA-21)

`PhaseRunId` generator: `BLAKE3(workflowRunId || phaseDefinitionId || attemptNumber)`. **Derivation is total (clarified 2026-08-10, Tier-7 plan-readiness audit):** every bit of the identifier is a function of that preimage and none of it comes from a clock or an entropy source — so a `phaseRunId` is **not a ULID**, whose leading 48 bits are a millisecond timestamp the preimage cannot produce. Implementation surfaces that typed the column as a ULID were describing a shape this rule forbids; the audit corrected them and left the identifier's concrete text rendering open (see §Open Questions), because choosing a rendering is a design decision rather than an audit finding. Any ratified rendering must stay a pure function of the digest. Replay reproduces the same `phaseRunId` sequence; random ULIDs are forbidden for `phaseRunId`. Replay uses `session_events` + immutable truth tables as authority; projection tables rebuild via `ProjectionRebuild` ([Temporal Encyclopedia — Event History](https://docs.temporal.io/encyclopedia/event-history); [Bitovi — Replay Testing in Temporal](https://www.bitovi.com/blog/replay-testing-to-avoid-non-determinism-in-temporal-workflows)).

### Hash-chain scheme (SA-26, SA-27)

- Approval history is append-only, per-`workflow_run_id` flat hash chain (C-13 / I7), anchored to Spec-005's existing scheme: **BLAKE3** digest, Ed25519 signature, RFC 8785 JSON Canonicalization Scheme. No new SHA-256 approval-chain scheme. Dual-anchored: each `workflow_gate_resolutions` row also has a corresponding `session_events` row whose payload carries the `row_hash` — the pre-ordered-log pattern from [Google Trillian](https://google.github.io/trillian/docs/TransparentLogging.html) at smaller scale.
- Flat chain (not a Merkle tree) is appropriate at V1 write volume per [Crosby & Wallach, Efficient Data Structures for Tamper-Evident Logging (USENIX 2009)](https://static.usenix.org/event/sec09/tech/full_papers/crosby.pdf) and [AuditableLLM, MDPI Electronics 2025](https://www.mdpi.com/2079-9292/15/1/56).
- **Dual-hash algorithm (SA-27):** BLAKE3 for daemon-internal identity (workflow-definition content hash, `phaseRunId` derivation, approval-chain row digest). SHA-256 reserved for Plan-012 artifact-manifest content hashes where ecosystem interop matters. This is deliberate — different algorithms for different scopes, not an oversight.
- Write amplification: ~42 KB / 110 writes per 10-phase workflow; fits within 2–3 Spec-013 batches under `synchronous=FULL` WAL mode ([SQLite — Write-Ahead Logging](https://www.sqlite.org/wal.html)).

### Human form drafts (SA-28)

No workflow table ships empty. `human_phase_form_state` carries the human form kind's drafts from V1: the form activates `workflow.humanFormDraftSave`, each autosave bumps the row's own draft version, and a half-filled form is restored from the daemon rather than from the window. A client resumes no draft from browser-local storage, because typed unsent text is never put there.

### I/O format invariants (C-5)

Workflow state, step inputs and outputs, and captures are **JSON-only**. No pickle, no YAML carrying language-native object tags, and no evaluation of document text on the host — a program runs only inside the Code node's sandbox (§Expressions). Airflow XCom's pickle default enabled a direct RCE path, disabled in 2.0 ([Airflow — Turn off pickling of XCom by default in 2.0, #9606](https://github.com/apache/airflow/issues/9606)).

**Data between nodes is always an array of items.** An item carries its JSON body, an optional map of binary references, an optional record of which input item it came from, and an optional error of its own. A node executes once over all the items of its input, or once per item where its kind declares that, and returns one array of items per output handle — an empty array meaning that branch is dead. A binary reference is an artifact id plus its media type, file name and size: bytes never travel inside a run record.

**Item lineage is what makes a cross-branch reference resolve.** The record of which input item an output came from is what lets an expression naming an upstream node resolve to the input item a given output derived from, across a branch and a merge. The engine fills it automatically for one-to-one, one-to-many and equal-count transforms, and for the empty item a node marked to always output data emits; a kind that genuinely mints or collapses items sets it itself. Two failure modes are first-class typed errors shown in the inspector rather than thrown at the user as a stack trace: lineage missing from an upstream node, and an ambiguous backward walk after a collapse, whose message names taking the first item, the last item, or one item by index as the fixes.

**A step's payloads are inline while they are small.** A step's input, output and log sit inline on the step row under a 64 KiB cap; above it each becomes an artifact through the existing ingest pipeline and the step row keeps the reference. The panel that shows a payload says which of the two it is reading. An artifact is already readable by a sidekick in chat with the same read the user uses, so a step's input and output are addressable from a message and the run row stays small.

### Engine event record (SA-43)

Added 2026-08-16 (workflow-hardening amendment). The engine keeps a **maintainer-facing record of its own decisions**, and it is **always on** — there is no enable flag, no verbosity level, and no per-run opt-in.

The always-on rule is the whole point and is not a convenience: a run parks once. By the time anyone knows a park needs explaining, the decision that produced it has already happened, and there is no second chance to have turned the log on. A record that must be enabled before the event it explains is a record that is off exactly when it matters. The cost of the alternative is paid once, in bounded storage; the cost of this alternative is paid every time, in an unreconstructable incident.

**What it is not.** The record is **non-canonical** and MUST NOT become the only account of anything. The canonical account of a run stays `session_events` plus the immutable truth tables (§Truth vs projection vs ephemeral (SA-25)); the operator-facing account of a park stays the `parkCause` of §Park integrity and cancellability (SA-42). It is also not the run's own step history: what a person reads about a run — each step's input, output and log, its timings, its cost, its typed error, its execution index and the edge that actually fed it — is the per-step projection of §Truth vs projection vs ephemeral (SA-25), and re-running a run or retrying it from one step reads that record, never this one. Nothing in replay, verification, projection rebuild, or audit may read this record, and its expiry must degrade diagnosis, never correctness.

**What it carries.** Engine decisions and the typed values they were made from: phase admission verdicts and pool-wait entries, state transitions, gate resolutions, park decisions with their typed `parkReason`, schedule arm and clear events with the instant armed, resume attempts and their outcomes, and typed refusal codes. Every record carries the correlation keys — `workflowRunId`, `phaseRunId`, `attemptNumber`, and a monotonic per-run sequence — so a single run's decision history is reconstructable by filtering. The requirement is per-run **correlation**, not per-run storage: the physical layout (one file per day, per run, or per daemon; rotation and compaction policy) is the observability owner's choice and is deliberately not fixed here. The line format is newline-delimited JSON — one complete object per line, inside the JSON-only constraint of §I/O format invariants (C-5) — so a record truncated by a crash costs its last line rather than its whole file.

**Dispatch and outcome are two records, and the wording is part of the contract.** A record written before the work it describes states an **intent** — that the engine is dispatching a resume onto a session, never that a turn is running on it — and is paired with a second record stating that work's outcome. The pairing is what makes absence diagnostic: a dispatch with no outcome beside it is itself the finding, and where the step between them wedges it is the only signal there is. One record phrased as a completed fact for work that had not started yet reads, to an operator watching a run that then hangs, as the exact opposite of what happened. The prose in every record is engine-authored, never model output.

**What it must not carry.** No secret material, ever, in any encoding (§Secrets — by reference only (C-15) and its SA-13 I4 invariant apply here exactly as they apply to argv, logs, and artifacts). No raw provider prompt or completion text: where a decision was made from a provider signal, the record carries the **typed** value the driver normalized — the park reason, the window provenance — never the payload it was normalized from. This keeps the record a decision log rather than a second, unredacted transcript.

**Ownership.** This record is a **non-canonical bounded-retention diagnostic payload class**, which is [Spec-018 §Required Behavior](018-observability-and-failure-recovery.md#required-behavior)'s declared tier — "non-canonical observability payloads … must use explicit bounded retention separate from canonical event and failure-detail retention" — and [Spec-018 §PII in Diagnostics](018-observability-and-failure-recovery.md#pii-in-diagnostics) owns that tier's discipline: the ≤ 7-day default TTL, the `retention_policy_override` warning past 30 days, and mandatory inclusion in the [Spec-020 §Shred Fan-Out](020-data-retention-and-gdpr.md#shred-fan-out) Path-3 fan-out. Spec-015 **requires** the record and specifies its content, correlation keys, and always-on rule; Spec-018 and Plan-018 **own** the bucket, its retention, and its shred leg, and register it alongside the diagnostic buckets already enumerated there. This spec authors no bucket, no TTL, and no shred path — the one-writer discipline this corpus imposes.

## Example Flows

- **Sequential with human gate.** A workflow runs `analyze → plan → implement → review`, pausing between `plan` and `implement` for a human-approval gate.
- **Version-immutable edit.** A workflow is edited after one instance has already started. The running instance continues on the old version while new runs use the new version.
- **Definition-as-artifact export (derivative view).** A project-scoped workflow definition is exported as a review artifact. Later workflow execution still binds to the canonical persisted definition version rather than to the artifact copy.
- **Parallel with `all-settled`.** A research workflow spawns `{pass-a, pass-b, pass-c, pass-d, pass-e}` in parallel under `ParallelJoinPolicy: all-settled`. Any pass that fails emits `workflow.phase_failed`; siblings continue; the workflow enters its synthesis phase once all five settle (pass or fail).
- **Multi-agent OWN.** A `deliberate` multi-agent phase spawns a phase-owned channel with three agents under `turn_policy: round-robin`, `turns_per_agent: 15`. The channel produces a conclusion artifact which becomes phase output. Phase completes; channel closes with `CLOSE_WITH_RECORDS_PRESERVED`. The next phase receives the transcript via `inheritContext: { from: "previous_phase" }`.
- **Human phase with escalation.** A `validate` human phase with `timeout: {days: 3}`, `timeoutBehavior: 'escalate'`, `inputSchema: {decision: enum['approve','reject'], notes: long_text}`. The user opens the deep-link `/session/:sid/workflow/:rid/phase/:pid`, drafts a reply (localStorage autosave), submits. Gate resolves with `scope: workflow-phase`. If timeout fires before submit, the workflow emits `workflow.human_phase_escalated` telemetry event — no paging at V1 (deferred per [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments) until notification routing ships).

## Quality-Check Model

- Retry targets: the phase that produced the output, or a specific earlier phase (configured per gate).
- Max retries: configurable per gate (default 3).
- Quality-check failure behavior: `block` (halt workflow), `warn` (continue with flag), `skip` (bypass gate).
- Quality checks are evaluated by a dedicated agent or automated script — not by the same agent that produced the output.

## Output Mode Specification

- V1: structured JSON with artifact references. Each phase produces `{artifacts: ArtifactId[], summary: string, metadata: Record<string, unknown>}`.
- V2 (deferred): conversation markdown, channel transcripts, rich media as first-class output types.
- Phase outputs are stored as artifacts (Plan-012) with `artifactType: 'workflow_output'`.

## Discussion Integration Path

- **V1:** `single-agent` phases run one sidekick in one channel. `multi-agent` phases spawn phase-owned channels (`ownership: OWN`) where several sidekicks discuss before producing output; the channel's conclusion becomes phase output.
- **V1.1 (criterion-gated):** `ownership: BIND` — multi-phase channel reuse. Contingent on three criteria in [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments). See Interfaces And Contracts §Multi-agent.
- **V2 (deferred):** cross-phase discussion channels — sidekicks from different phases collaborate in shared channels.

**A run's results reach exactly one session: the one that asked for the run.** The session where the user typed the run verb, or whose own sidekick started the run through its run tool, receives one flat transcript row when the run ends — the workflow's name, the run's status, its duration, a one-line summary of what came out, its attachments as that session's own file rows, and a link to the run; no cost figure. It is an ordinary message, which the sidekicks in that session read on their next turn. While the run is live the same session carries one progress row, updating in place until the run ends and then becoming the results row; it links to the run's page and nothing is pinned.

**Nothing posts into a session that did not ask.** There is no post-to-chat node and no method that takes a target session: the results verb pulls a run's results into the current session on demand, and the results-posting tool does the same for the invoking sidekick's own session, the daemon deriving that session from the invoking turn. A schedule's results live in the runs list, and a workflow that needs a sidekick to act on its results starts its own session with a task.

## Workflow Timeline Integration

**Runs are two levels: the list of runs, and one run's page.** Nothing keeps a trail of where the reader has been and no control walks one backwards.

**The list.** One row per run, newest first, reading in order: the workflow's name, the status chip, the trigger, who or what started it, when it started, how long it took, how many steps it ran, and what it cost with the account that paid, where a provider was billed. A row that was never billed carries no money figure and names no account. While a run is going, its step cell says where the run is and what it is doing — `4 of 9 · run tests` — off the same subscription that moves its status and its duration; the row never grows a second line, and the cell goes back to the finished step count when the run ends. The list updates live through one subscription rather than one per row. Four filters narrow it — workflow, status, trigger and date range — and nothing else; they narrow the table alone, and a set of them matching nothing gives way to a note in their own words, `No run matches Failed in the last 7 days.`, carrying one **Clear filters** button. The four filters are kept on this device and come back the way they were left, read and written defensively so the tab renders correctly when that store is empty or throws; nothing else about the tab is kept — not which run was open, not where the reader had read to. Every run the surface shows belongs to the daemon that ran it, and a run reached from another device is that same run driven from a distance; no run ever leaves the list because of the device it is being read on. One row action, **Delete run**, asks once and names what goes; above the list, **Delete runs older than…** names how many runs would go and says that a run marked Keep stays and a run waiting on a person is never touched. No row carries a selection control and nothing else acts across the list.

**Runs waiting on a person stand in their own section above the table**, oldest first, one line each: the workflow's name, what it is waiting on, and how long it has waited. The entries for runs parked on a spent provider account keep their place at the top of that section, folded to one entry per outage with its affected-run count. The filters never narrow the section, and the table below keeps its newest-first order and every run it lists. The section stands whether or not anything is waiting: with nothing waiting it reads `Nothing waiting`, and where this sitting has answered runs it says so beside it — `Nothing waiting · you answered 4 runs this morning` — counting only what has been answered since the surface was opened.

**A run's page is three things: a header, the run graph, and a step panel** that opens beside the graph when a step is picked. Everything the run has to say is in one of the three, and picking a step replaces what the panel holds rather than making the page longer.

- The header carries status, timings, trigger, who started it, cost, the pinned version, and links to the source workflow and — where a message started the run — to that message. It opens with two lines: what happened, then what it needs, both composed from the run's status and, where it is parked, its cause — `The test step failed twice` over `Fix it and press Resume, or cancel the run` — so every kind of stop is written in plain words and none is kept by hand. A run still going says that it is running and that nothing is needed, and a parked run's cause is read in the first of those two lines and nowhere else on the page.
- A run that has finished carries one control more in that header, **Open in Review**, which opens the console's one difference surface on the run's own branch. A run still going carries none, and this page draws no difference of its own.
- While a run is going, one line sits at the foot of the header, directly above the graph, saying where the run is: which step is live and its place in the run, what is blocking it, the instant it resumes itself where one is armed, and what it has spent so far — `Step 4 of 9 · waiting on your approval · $0.42 so far`. Only a blocker that needs a person is marked. A run that has finished carries no such line.
- The graph is the workflow's own canvas, read-only: every node where the builder put it, coloured by that step's state, and every edge carrying the count of items that went through it. Nothing on it can be moved, connected or deleted, and no second drawing of a run exists. It opens placed on the step that is live and follows it as the run moves; a scroll, a drag or a key stops the follow and nothing starts it again by itself, and once the view has drifted a small `now` chip stands at the canvas's corner, which slides the view back and follows again. The chip is drawn only while pressing it would move the view.
- Picking a step opens the **step panel** on Output, or on Error where the step failed. The panel has Input, Output, Logs, Cost and Error tabs, each with a table and a JSON view, item counts, the item pairing, `Copy as JSON` and `Open as artifact`. The table view draws a payload by its type: a binary field draws as the file it names — `pr-4821.patch · text/x-patch · 14 KB` — in place of its reference, and a markdown string draws as the formatted text it is; the JSON view keeps both exactly as they were stored. The panel says whether a payload was read inline or from an artifact, and it shows the executed source edge, so a step fed by run 3 of a loop says so. Cost renders only where a provider was billed, and names the paying account.
- A step whose data is past the retention bound reads that it expired in place of its panels. Beside the panel's own controls sit **Keep**, which holds this run's step data past the bound, and pinning this output as the builder's test data. There is no send-to-chat action anywhere on the page: results reach a session only from inside that session (§Discussion Integration Path).
- A sub-workflow step links through to the child run. A run whose definition version was deleted still opens, because a run pins its version.
- Every clock figure is written the way the machine's own clock writes it — `Mon 8:30 AM EDT`, `Yesterday 7:48 PM` — and an instant inside an item's own data stays exactly as it was written, like a log line or a path. A duration is written the way the rest of the surface writes one — `6 m 41 s`, `38 s` — and only a duration under a second is written in milliseconds, `4 ms`; a raw millisecond figure for a step that took minutes never reaches the screen.
- A run that ended before its last step quotes why from the latest attempt's own cause, read from the provider's frame and never from an earlier attempt: a turn the daemon itself interrupted is marked as the daemon's, a provider's own turn limit is its own reason, and a provider that gave out after its retries is the cause on either provider. A run parked by a spent account still renders its park cause and its resume instant.

**A step blocked on an approval is answered where it blocks.** Its panel carries **Reject** and **Approve** beside **Open in Review**, and answers the approval there — in the words the approvals surface uses, through the same pipeline and the same Cedar check — so the person already looking at the step that is blocking never has to leave it to unblock it. The run leaves `waiting` and resumes down the branch that was chosen. Answering replaces all three controls with a one-line past-tense receipt in the machine's own clock, `Approved at 2:14 PM`, with no way back from it — no undo, no re-answer, no second press — and the run's own actions are what act next. Every act a person takes on a run once — approve, reject, answer, restart, discard, merge, open a pull request — leaves that same receipt in place of its controls.

**A failed step is fixed in a fresh session, never inside the step's own.** A run parked on a failed step carries one action no other step's panel does, `Fix in a fresh session`. It prepends a new session on that step's own project and checkout and switches to it: its first turn carries the step's name, the input the step ran on and the output it failed with, under a footer naming the run and the step with a link back, plus a second link to the step's own session for reading. The step's session is read from and never written to — no message, no steer and no act reaches it — so the run's record stays the run's record and a resumed step never carries messages as context it was never meant to have. **Resume** then reruns the step from its original input against the fixed checkout and the rest of the run follows. Once such a session exists the run's page links it, beside the links to the source workflow and the starting message, for the life of the run. That link is the one route into a step's session anywhere on this surface: a run's page never opens the session its steps ran in, because the step's transcript is the run's own record and is read in the step panel. Nothing else new is offered on a parked run: no takeover, no detach, and no third operator operation beside cancel and resume (§Operator run control (SA-45)).

### Event envelope and category split (SA-18)

All workflow events land as payloads inside the existing Spec-005 `EventEnvelope` — **no new envelope schema**. `causationId` on the envelope carries parent-event relationships; `workflow_run_id` / `phase_run_id` are payload fields. This is an additive MINOR envelope bump under [ADR-018](../decisions/018-cross-version-compatibility.md) discipline.

V1 introduces **5 new Spec-005 categories** (not one monolithic `workflow_lifecycle`):

- `workflow_lifecycle`
- `workflow_phase_lifecycle`
- `workflow_parallel_coordination`
- `workflow_channel_coordination`
- `workflow_gate_resolution`

Scope-of-query split matches Spec-005's existing `run_lifecycle` / `approval_flow` pattern. No collision with existing `presence.*`, `run.*`, `approval.*`, `channel.*`, `recovery.*` categories.

Reverse-DNS `workflow.*` namespace convention follows [CloudEvents Specification v1.0.2 `type` attribute](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#type).

### Event types (SA-19) — 34 types under `workflow.*`

- **`workflow_lifecycle` (13):** `workflow.created`, `workflow.started`, `workflow.gated`, `workflow.failed`, `workflow.completed`, `workflow.resumed` (its payload carries an additive-optional version re-pin member naming the version a repaired run left and the one it joined — §Frozen-definition repair (SA-41); additive MINOR under [ADR-018](../decisions/018-cross-version-compatibility.md)), `workflow.cancelled` (the canonical record of an operator cancellation, carrying the operator-supplied `reason` bounded exactly as `parkCause` is, and minted **together** with `workflow.runCancel` per §Operator run control (SA-45): the status write and this append share one unit of work, without which a projection rebuild would replay the last `workflow.phase_suspended` payload and resurrect a cancelled run (SA-25)), `workflow.run_waiting`, `workflow.schedule_armed`, `workflow.schedule_fired`, `workflow.trigger_armed`, `workflow.trigger_fired`, `workflow.results_posted`
- **`workflow_phase_lifecycle` (16):** `workflow.phase_admitted` (resource-pool admission), `workflow.phase_waiting_on_pool` (diagnostic), `workflow.phase_started`, `workflow.phase_progressed`, `workflow.phase_cancelling`, `workflow.phase_failed` (carries `cancellation_reason: 'sibling_failure' | null`), `workflow.phase_retried`, `workflow.phase_suspended` (its `reason` union is `waiting-human | provider-usage-limited`, and the payload carries the bounded `parkCause` plus, where one is armed, the durable `autoResumeAt` instant and, where one was computed, the `parkAttentionKey` fold key — §Park integrity and cancellability (SA-42)), `workflow.phase_resumed`, `workflow.phase_completed`, `workflow.human_phase_claimed` (informational), `workflow.human_phase_escalated` (telemetry-only at V1 per SA-11; no `nextAction` pre-declaration — additive-field discipline per ADR-018), `workflow.step_started`, `workflow.step_finished`, `workflow.step_failed`, `workflow.step_skipped`
- **`workflow_parallel_coordination` (1):** `workflow.parallel_join_cancellation` (sibling cancel driven by `ParallelJoinPolicy`)
- **`workflow_channel_coordination` (3):** `workflow.channel_created_for_phase`, `workflow.channel_closed_with_records_preserved`, `workflow.channel_terminated_forcibly`
- **`workflow_gate_resolution` (1):** `workflow.gate_resolved` — carries `scope: channel | workflow-phase` + `outcome`. The base payload is extended at the persistence layer with `gate_resolution_id` + `row_hash` fields to realize the `session_events` dual-anchor (SA-26). No separate chain-advance event — the gate-resolved event carries the chain extension. Payload additions are additive MINOR bumps under [ADR-018](../decisions/018-cross-version-compatibility.md).

The four step events are what make a run's own step history a function of the log: each step boundary emits one, so the runs surface and the session's record are one truth rather than two (§Truth vs projection vs ephemeral (SA-25)).

### Ordering invariants (SA-20)

Load-bearing event-sequence rules ([Temporal Events Reference](https://docs.temporal.io/references/events), [Temporal — Events and Event History](https://docs.temporal.io/workflow-execution/event)):

- `workflow.phase_admitted` precedes `workflow.phase_started` (resource-pool admission required first).
- `workflow.phase_cancelling` precedes `workflow.phase_failed` whenever `cancellation_reason != null`.
- `workflow.gate_resolved` with `scope: workflow-phase` precedes the subsequent `workflow.phase_started`.
- `workflow.channel_created_for_phase` precedes any events with matching `channelId`.
- Parallel cancellation fires one coordinator event (`workflow.parallel_join_cancellation`) + per-sibling event chains at deterministic tick-boundary — never mid-callback.
- `workflow.phase_suspended` precedes every `workflow.phase_resumed` carrying the same `phase_run_id`, and a `workflow.resumed` carrying the SA-41 version re-pin member is preceded by a `workflow.phase_suspended` for that run — a repair is only ever expressible on a parked run, so a re-pin with no preceding park is a malformed sequence rather than an unusual one.
- `workflow.step_started` precedes the `workflow.step_finished` or `workflow.step_failed` that carries the same step identity.
- `workflow.run_waiting` precedes every resume of the same run.
- `workflow.schedule_fired` precedes the `workflow.started` it caused.
- `workflow.results_posted` follows the terminal status of the run it names.

### Cadence (SA-22, SA-23)

- `workflow.phase_progressed` cadence is phase-type-specific:
  - `single-agent` / `automated`: emit on turn completion + tool-invocation boundary.
  - `multi-agent`: emit on channel-turn boundary + 25 / 50 / 75% of `turns_per_agent` budget milestones.
  - `human`: emit on form-section save + claim / re-claim.
- `workflow.phase_waiting_on_pool` cadence: emit on entry-to-blocked-state + 30-second intervals while blocked (tripwire-configurable), carrying `waitingSinceSeq` for reader correlation. Pass G stores aggregate `totalPoolWaitMs` on phase row — not per-wait rows (G §10.1 resolved).
- `workflow.resumed` payload carries structured `resumptionPoint: {activePhaseRunIds, pendingGates}` for reader-reconstruction speed (aligns with low-cardinality naming per [OpenTelemetry SemConv for Events](https://opentelemetry.io/docs/specs/semconv/general/events/); [n8n Workflow Executions](https://docs.n8n.io/workflows/executions/) provides durable-resume prior art).

### Session timeline surfacing

- Workflow phases appear as distinct sections in the session timeline (Spec-011).
- Retry iterations appear as sub-entries within the phase section.
- `workflow.phase_suspended` with `reason: 'waiting-human'` is a first-class surfaced event; session UI surfaces pending-human count prominently.
- `workflow.phase_suspended` with `reason: 'provider-usage-limited'` is surfaced with the same first-class weight, rendering the park's `parkCause` and, where one is armed, the instant the run resumes itself — the same instant the durable schedule holds, read from the payload rather than recomputed. Concurrently parked runs sharing an attention key render as one entry with its affected-run count, never as one entry per run (§Provider-limit pacing and durable resumption (SA-40)); a run parked with no schedule renders as parked-awaiting-resume rather than as scheduled, because a client that invents a time the engine did not arm is the display half of the same guess SA-40 refuses to make.

**Every run lives in a session, and the run record names it.** Three rules place it:

1. A run started from a chat — a workflow verb typed there, or that session's own sidekick starting it through its run tool — lives in that session.
2. A run nobody is watching — a schedule, a webhook, a file event, or Run now from the Workflows tab — lives in **one session the workflow owns**, created on its first unattended run and reused by every later one, named after the workflow and listed once among the sessions. A five-minute schedule is therefore one session entry, not two hundred and eighty-eight a day.
3. A sub-workflow call runs the child **inside the parent's session**. The child keeps its own run record carrying its parent's id, so the runs list shows it, links it to the parent, and applies retry-from-step and the step-data retention bound to it as to any run; its steps' channels and events land in the parent's session, so there is one place to open, and pause, resume and cancel on the parent cover the child.

## Visual Workflow Builder

V1 ships a visual, node-graph authoring surface for workflow definitions alongside the file and SDK authoring paths. Every graph the builder can produce is a document the daemon accepts through the same `workflow.definitionCreate` path with the same validation, and the saved bytes are what the author drew, so a round trip through export, a sidekick's edit or the version chain shows the workflow the author built. See [ADR-026](../decisions/026-visual-node-graph-workflow-authoring.md).

The destination has one header and three tabs. The header carries the screen's title, the tabs — **Builder**, **Workflows** and **Runs**, the last two each carrying the count of what it lists, read from the data on first paint and after, so a person landing on the Builder reads the same number as a person landing on the tab — and at its right one actions menu holding `New workflow`, `Import…` and `Ask a sidekick to build one`.

**The builder is three columns**: a palette as wide as its widest kind row reads at the current text size, the canvas, and an inspector as wide as its widest param label and field pair. A toolbar sits above the canvas and a validation strip below it. The inspector opens when a node is selected and closes at its own step in this surface's Escape order, keeping every edit it holds.

**The palette** lists every kind the runtime offers, grouped by the eight categories, each row carrying an icon, the name a person reads and the one line under it, searchable by name, description and alias. Rows drag onto the canvas and click to add at the viewport's centre. It is docked, never a modal, and it is drawn from `workflow.kindList`, so a kind added in the daemon appears with no renderer change. Placing the Code node opens an editable code body in the inspector, so a program is typed there and nowhere else.

**The canvas flows left to right and is fully controlled.** Its nodes and edges derive from the document draft held in the builder's own store, and every change the canvas reports becomes a document mutation, so the store and not the canvas library is the source of the bytes that get serialized. Nodes drag, multi-select, delete, connect by dragging from an output handle to an input handle, reconnect, and copy and paste as a JSON fragment. `tool` handles sit on a node's bottom edge and `main` handles left and right. The canvas draws background dots, its own zoom controls and `Add a note` at the bottom left, the minimap at the bottom right, and a run bar across its top while a run is live; `Run now` and `Tidy up` stay in the toolbar. The canvas library's attribution mark stands at the canvas's corner, on the builder and on a run's read-only graph alike, and is never hidden.

**Canvas interactions.**

- Dragging a node updates its layout entry and nothing else; the hashed body is untouched. A drag is coalesced into one undo entry at drag end, not one per pointer move.
- Dragging from an output handle to an input handle creates an edge; releasing on empty canvas opens the palette at that point, pre-filtered to the kinds whose matching handle accepts the dragged type.
- An existing edge reconnects by dragging either end; dropping a reconnected end on empty canvas deletes it. The mid-point `+` on an edge inserts a chosen kind between the two endpoints and rewires both sides, and the edge under the pointer raises to the top of the drawing so its own controls are never covered where edges overlap.
- Backspace or Delete removes the selection, and removing a node removes its edges. Shift adds to the selection, a plain drag on empty canvas rubber-band-selects, and the platform select-all chord selects every node and every note. Pan is the wheel, a space-drag or a middle-drag.
- Undo and redo are document snapshots in the builder's store, capped at 200 entries and bound to the platform undo chord and its shifted form.
- Copy serializes the selected nodes and the edges between them as a JSON fragment; paste re-ids them and offsets them by two grid steps, so a fragment pasted from a chat message lands as real nodes, visibly beside what it was copied from. Nodes snap to the canvas grid.
- `Tidy up` re-runs the layout engine over the whole document and writes the result into the layout section as one undo entry.
- Double-clicking a node's name renames it in place; the rename touches no edge and no expression, because every edge and every expression resolves through the node's id.
- Arrow keys nudge the focused node one grid step and Shift with an arrow moves it four. The console's own keybinding service owns that binding, because the canvas library's keyboard handling is switched off here so a second live announcer is never created; every structural change — a node added, connected, deleted, or changing run state — is announced through the console's single announcer instead.
- Param editing happens in the inspector and never inside a node, so a keystroke re-renders one panel rather than the graph, and a document over roughly 150 nodes renders only the elements in view.

**A node draws its kind icon, its name, and the one-line summary its kind computes from its params.** A disabled node renders greyed with struck-through edges, and the engine passes its input straight to its output. During a run a node carries a state ring — idle, running, succeeded, failed, waiting or skipped — and after one it carries the item count of its first output. A node whose last run's data is stale carries a staleness marker distinct from the success ring, and a node with pinned data carries a pin marker and is not executed in a manual run. A failed node carries a red outline and the first line of its error, and clicking it opens the inspector on Error. A node with a capability input renders those handles on its bottom edge, visually distinct from data handles. Each kind has one node width — wide enough for that kind's icon, its name and its count at the default text size — so first paint is complete and the layout pass needs no measurement; a failed node grows by the one line of error it must carry. A loop node draws both of its ways out before any run: a `done` edge onward and a `loop` edge back into its body, each labelled where it leaves the node, and each carrying the count of items that went through it while a run is circling.

**One edge type draws every connection**: a bezier path with an arrow head, a mid-point `+`, a delete affordance on hover, a branch label near the source handle — `true`, `false`, `error`, `loop`, `done`, `approved`, `rejected` — and, while a run flows through it, an animated state and an item count.

**The inspector** opens with a header carrying the node's kind, its name, its enable toggle and delete. Below it: a Parameters panel rendered generically from the kind's param specs, each param shown or hidden by its sibling-value condition; a Settings section for the error disposition, the retry bounds, execute-once, always-output-data, a fork's branch `Order`, and the node's notes; and three data panels over the last run's data for that node — **Input**, **Output** and **Schema**.

- Any param toggles between a fixed value and an expression, and typing `=` into an empty param activates expression mode. An expression field previews its resolved value against the current item of the last run, live, with the failure reason where it cannot resolve. Dragging a field from Input or Schema into an expression param writes the expression that reads it.
- Output offers table, JSON and schema views with an item count, a search box and pagination, plus a pin button, `Copy as JSON`, the per-type renderers for binary and markdown payloads, the advisory hints strip, and a run-info block. Its JSON view is editable, and saving it pins that data onto the node. Schema is the field tree, and it is what a sidekick-authored expression is checked against in the validation strip.
- Governance facets on a tool binding render read-only with their source named, and no control in the inspector writes them (§Tool bindings are references, never inline policy (SA-34)).
- A kind whose handle set depends on its params re-registers the node's internals immediately after the param write that changed the set.
- The sidekick param opens the node's own chooser: a popover over the sidekick definition list, its header reading `Run as` over a search field, with **General** at the top of the list. Typing narrows the list by name, the arrows move a cursor through what is shown, Enter or a click chooses and the choice applies to the node at once, and Escape closes it without choosing. The cursor sits on the row the node already holds wherever that row is shown, else on the first row, and a search matching nothing says so. What the node stores is §Multi-agent phase — `ownership: OWN` at V1 (SA-6, SA-8, SA-9).
- A node's notes are one field in that Settings section, read by whoever opens the workflow. Nothing carries a note from one run to the next: what one run should tell the next is written into the workflow's own state, where the engine can read it.
- A trigger node's panel carries three things under its params that no other node's does: the overlap choice, the last skipped fire where there is one, and, for a webhook, its address (§Entry node and the V1 trigger surface (SA-37)).

**The toolbar** carries the workflow's name, inline-editable; Save; Run now, which reads `Cancel` while the run it started is live; a schedule pill reading off or the next fire; a version readout that opens the Versions panel; Tidy up; Export; Import; Undo and Redo; and at its right New workflow and a zoom readout.

**The validation strip** is a bottom bar listing unsaved changes, unreachable nodes, missing required params, invalid expressions and refused shapes, each row clicking through to the node it names.

**The builder's empty state is a trigger picker over the canvas**, asking how the workflow should start and listing the eight trigger kinds with one line each: "Pick a trigger — every workflow has exactly one. Place anything else from the palette and this steps aside; the strip below then says the trigger is still owed." Choosing a card places the trigger; placing any other kind from the palette steps the picker aside and leaves the validation strip to say the trigger is owed.

**While a run is live the canvas is a run overlay**: nodes carry their step states, edges carry item counts, and clicking a node opens the inspector on that step's Output.

**One Escape order covers this surface**, one step per press, the topmost open surface first, a surface that is not open skipped, and nothing a person typed discarded: an open menu, popover or confirm; the composer's command list; text in a focused search box; the inspector, its edits kept; the versions pane; a run's step panel; a run's page, back to the runs list; the canvas selection. A field whose Escape already means something keeps it — an inline node rename reverts the name and leaves the field, a search box with text in it clears — and the order does not also run for that press, while a box already empty lets the press fall through to the next step. Two acts here answer to a chord of their own, opening the next run that needs a person and pressing the main answer the open run's blocking step offers, and one more opens this destination from anywhere; all three are ordinary rebindable rows on the console's keyboard settings and are inert while a text field has focus.

**The Workflows tab is a table, one row per saved workflow**: name, trigger kind, schedule with its next fire and — where one happened — the last fire skipped because a run was still going, an enabled toggle, the last run's status and relative time, the run count, and updated-at. Under the name sits the row's second line, the definition's scope and its tags — `Project scope · review`. Rows sort by updated-at descending by default and every column sorts. Row actions are Run now, Edit, Duplicate, Export and Delete: Run now starts the row's latest saved version and opens the new run's page, after the inputs panel where the workflow declares any; Duplicate creates a new definition at the same scope with " copy" appended and opens it in the builder; Delete asks once, names how many runs will keep their pinned versions, and is not undoable. A filter row above the table carries a search box and chips for enabled, has schedule, failed last run, tag and scope, with `Import` and `New workflow` at its right; the failed-last-run chip narrows to workflows whose most recent terminal run failed, and the tag chip to one tag. There are no scope groups, no resolution-order sentence and no promote button (§Definition scope in the builder (SA-36)). With nothing saved the tab reads one sentence saying what a workflow is — `A workflow is a set of steps that runs on a schedule, a webhook or a command.` — over `New workflow` and `Ask a sidekick to build one`, the second opening the session composer pre-filled with the create verb, and offers nothing else. A filter that matches nothing is a different thing from a catalog that holds nothing: the table gives way to a note in the filter's own words — `No workflow matches "review" with Enabled on.` — carrying one `Clear filters` button, and the never-built empty state with its two buttons stands only when the catalog itself holds nothing.

### Graph model — nodes, ports, and edges (SA-32)

**Every kind in the catalog is a first-class node.** The document is node-shaped end to end: what the author drew is what is stored, and nothing is compiled into a different shape at save time.

| Node kind | Persisted as | Count | Notes |
| --- | --- | --- | --- |
| Trigger node | the document's own `trigger` slot | exactly one, mandatory | Names how a run of this definition begins (§Entry node and the V1 trigger surface (SA-37)). It never enters the phase sequence, never receives a phase run id and never produces a phase-state row. |
| Every other kind | one entry in the document's `nodes` list | one per node | Carries its kind, the kind version written at insert, its params and its `order`. The four phase types are four of those kinds; their executors delegate at run time to the existing run, approval and form machinery (§Implementation Notes). |

A node's params carry **references** — a sidekick definition, a provider account, a tool binding identity, a secret reference — and never a nested node, which is why the sidekick and the paying account are params rather than wired sub-nodes (§Multi-agent phase — `ownership: OWN` at V1 (SA-6, SA-8, SA-9)). A phase node's gate type stays a property of that node, rendered on its outgoing edge shoulder rather than drawn as an element of its own.

**Two handle types exist, and no more.** `main` carries items between nodes. `tool` carries a capability: an MCP-tool node, a callback-tool node or another sidekick wired into a sidekick node's `tool` input becomes callable by that sidekick, unbounded in cardinality. `provider_account`, `gate` and `repo` are reserved names, not V1 wire values, and each of those three stays a param.

A handle is identified by one string of the form `"<mode>/<type>/<index>"` — `inputs/main/0`, `outputs/main/1`, `inputs/tool/0` — parsed tolerantly, falling back to the first main output. One handle primitive therefore renders both data ports and capability ports, and a branch index and connection type are recoverable from the stored edge alone.

**Edges are keyed by node id, never by node name.** A name is a mutable label; every edge, every expression index and every step record resolves through the id, so a rename is a metadata edit rather than a graph-wide rewrite. An edge is stored as its own id plus the source node and handle and the target node and handle, in the document's `edges` list, so the stored bytes are the complete executable graph and no edge lives outside them.

**Which sibling runs first is a number, not a position.** Each node carries an explicit integer `order`, defaulted from the order the nodes were added and edited on the node itself, so moving a node on the canvas never changes what the run does. One traversal ships; there is no second execution order.

**`go-back-to` is not an edge.** §Required Behavior states it is a state-reset operation, not a cyclic edge, and `workflow.definitionCreate` runs a cycle check that would reject the cyclic spelling. The builder therefore renders a phase's `go-back-to` target as a labelled back-reference on the node, never as a drawn connection, and the connection layer refuses any attempt to draw one. Iterating over items is a different thing and is drawable: it is the loop kind, whose body wires back into its own input.

### Graph shapes that are refused (SA-33)

The builder refuses these at **edit time** — a connection that would produce one cannot be completed, and a document that already contains one cannot be saved:

1. **A self-edge.**
2. **Any cycle** among `main` handles, walking the outgoers from the target. The one exempt shape is an edge whose target is a loop node's own input, because closing a loop body is the loop rather than a cycle.
3. **A handle-type mismatch**: `main` never connects to `tool`.
4. **A second edge into an input handle that accepts one.**
5. **Any edge whose target is the trigger node.**
6. **An edge out of a terminal kind** — a terminal kind ends the run, and an outgoing edge would assert a successor the engine will never reach. A `done`-gated phase is the same case.
7. **A fan-out whose branches carry no join policy**, or whose branches converge on more than one join point.
8. **An orphan node** — one not reachable from the trigger by `main` edges — and **a document with no nodes**, or with no trigger or more than one.

A refusal during a drag is shown as a red connection line plus a one-line reason in the validation strip — never a toast, and never an edge that is created and then removed.

**Edit-time validation mirrors the daemon check; it never replaces it.** Every rule above is re-evaluated server-side at `workflow.definitionCreate`, and the daemon's answer is authoritative. A client that skips, weakens, or predates a rule produces a **refusal**, not a persisted definition — the fail-closed direction. Refusals surface as the typed codes registered in [error-contracts.md](../architecture/contracts/error-contracts.md) §Workflow; the builder mints no error surface of its own, and until the pending §Workflow extension lands, an unregistered condition refuses under the existing codes rather than inventing one, per §Loud-errors discipline (C-12).

### Tool bindings are references, never inline policy (SA-34)

A phase node may bind tools. The binding a definition persists is a **reference only**: the scope-qualified binding identity plus a tool name, resolved at phase launch through the [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md) §Tool Metadata layer that [Spec-025](../specs/025-mcp-server-configuration-and-governance.md) §Tool-Level Overrides feeds.

A workflow definition **MUST NOT** carry any governance facet inline. Specifically, a tool binding in a definition carries no `enabled`, no `approvalMode`, and no `idempotencyClass` value — those three facets are node-operator surface, set only through the Spec-025 override operations, Cedar-gated per [Spec-025](../specs/025-mcp-server-configuration-and-governance.md) §Authorization, and independent per binding scope. A definition that carried them would let a workflow author grant themselves an approval posture the operator never granted, and would let a definition exported from one machine silently import a weakened posture onto another. The builder's inspector therefore **displays** the effective facets read-only, sourced live from the governance surface, and offers no control that writes them.

Trust is likewise not a definition concern: an untrusted binding refuses at launch under the Spec-025 trust rules, and the builder shows that state rather than overriding it. This is a distinct mechanism from the content-addressed external-tool pin of §External tool references — content-addressed (C-7): that pin governs a fetched tool artifact's bytes, while a tool binding's identity and trust are governed by the binding's own keyed base-config hash. Neither substitutes for the other.

### Canvas layout is not definition bytes (SA-35)

The **canonical definition** is the JCS-canonicalized JSON body the BLAKE3 content hash already covers. Canvas geometry — each node's coordinates, the viewport's pan and zoom, the sticky notes, and any other purely visual attribute — is **excluded from that body** and from the hash preimage, and so is a node's pinned data. Dragging a node or pinning an output changes no byte of the definition, mints no content hash and creates no version. This exclusion is **hash-scope only, never semantics-scope**: nothing that affects execution may be moved into the layout channel to escape hashing, and every field the engine reads stays inside the hashed body.

Layout is nonetheless **persisted and portable**, because it is part of the document rather than a client's private note. It lives in the document's own `layout` section and is stored in a column beside the definition body, and the file form of §Definition file form — export and import (C-17) carries it as an optional top-level section outside the hashed body. A workflow a sidekick authored or a user exported therefore carries its picture with it instead of arriving as an arrangement a machine invented.

Where a document does arrive with no layout — written through the SDK, the CLI or a sidekick — it is laid out **deterministically, left to right**, by the same layered layout library in the daemon and in the renderer, so a definition is never unopenable, opens the same way twice, and looks the same wherever it is opened (§Implementation Notes).

### Definition scope in the builder (SA-36)

The builder loads and saves at all three scopes of §Resolved Questions and V1 Scope Decisions, and the storage model is unchanged. What the surface shows of it is deliberately narrow: **scope is one control in the Save panel, one chip in the catalog's filter row, and one line on a workflow's own row.** There is no scope group, no resolution-order sentence, no copy-on-write banner and no Promote button on either the builder or the Workflows tab.

- **Loading** lists the definitions visible from the current context — the session's own, its project's, and the daemon's `shared` tier — as one list. Resolution still walks `session`, then `project`, then `shared`, most-specific-first, and that is what a run picks.
- **Saving at `session` or `project` scope** creates a new immutable version of that definition.
- **Saving an edit to a `shared` definition is copy-on-write, never edit-in-place.** Opening a `shared` definition and editing it produces a **new definition at the editing context's scope** (`project` by default, `session` if there is no project context), carrying the shared definition's content hash as its parent content hash so provenance is recorded in the existing version-chain field. The `shared` original is untouched, and the Save panel says so in one line before the save.

  Copy-on-write is required, not preferred. Definition rows are immutable by construction — the definitions table deliberately carries no updated-at column — so "editing in place" would mean appending a version to the shared definition, which silently repoints **every project on the daemon** that resolves it, with no signal at any consuming project and no way for a consumer to pin. Copy-on-write keeps the blast radius of an edit equal to the scope the editor is standing in, which is the same containment principle that makes two same-scope-name MCP bindings distinct entries rather than a merge.

- **Promotion `project → shared` is an explicit, separately-invoked action**, never an implicit consequence of saving. It creates the definition at `shared` scope from the promoted version's exact bytes, riding `workflow.definitionCreate` at `shared` scope and therefore clearing the same authorization every `shared`-target create clears (§Core SDK and persistence contracts) — the boundary keys on the target scope, never on the invoking gesture, so no route into `shared` bypasses it.

### Entry node and the V1 trigger surface (SA-37)

Every definition has exactly one entry node — its trigger — and that node records **how a run begins**. V1 ships eight kinds, and every arm is honoured at ship time; none is declared and left unwired.

| Kind | How a run begins |
| --- | --- |
| `trigger.manual` | Run now in the builder or on a workflow's row, the chat run verb, or a sidekick's own run tool. |
| `trigger.schedule` | Cron or every-N, in the trigger's own timezone, with a missed-fire policy of skip or catch-up-once. |
| `trigger.file-watch` | A path, a set of globs and the event kinds to honour, debounced 250 ms. |
| `trigger.webhook` | The daemon's loopback listener, with a per-workflow bearer token and a response mode of immediate or on-finish. |
| `trigger.session-event` | An event-type filter over the session log — a run finished, an approval resolved, an artifact published. |
| `trigger.chat` | A message in a session (§Chat-start surface (SA-38)). |
| `trigger.sub-workflow` | The entry point an Execute-a-workflow node calls, taking the parent's items in and handing the child's terminal items back, the child's run carrying its parent's id. |
| `trigger.error` | Any other workflow failing, receiving that run's id, its error and its last node. |

**A workflow is either enabled or not.** Enabling arms every trigger it declares; disabling disarms all of them, and the workflow stays that way until someone changes it back. A workflow with no trigger that can arm cannot be enabled, and the toggle says so rather than silently accepting. The enabled toggle on a workflow's row acts immediately and reverts visibly where the daemon refuses it.

**Arming is durable; the timer is only a cache.** Each armed trigger holds its own row — kind, config hash, next fire, last fire, whether it is enabled — and the in-process timer is a cache over that row. On daemon start, after the projection rebuild completes, every enabled workflow re-arms from its rows. A fired occurrence carries a dedup key of the workflow, the node and the scheduled instant, so neither a restart nor a double-arm can fire twice. Trigger cursor state lives in the daemon's per-(workflow, node) key-value store and never on the document, so the document stays hashable and safe to edit.

**Two policies decide what a fire does, and they answer different questions.**

- The **missed-fire** policy is per schedule and covers a fire that arrived while the daemon was down: skip the occurrence, or catch up exactly once. The run's trigger record says which happened.
- The **overlap** policy covers a fire arriving while a run of the same workflow is still going. It is one control on the trigger that fires — the schedule node's and the webhook node's alike, because every workflow has exactly one trigger — named **While a run is going**, with three values: **Skip**, the default, where no run is created and the workflow's row and that trigger's own panel show the skipped time and the run that was still going (`3:00 AM skipped · the 2:00 AM run was still going`), so a skip is visible without widening the run status list; **Wait, then run once**, where the next run starts when the current one finishes and several fires that arrived meanwhile collapse into one; and **Run alongside**, where a second run starts regardless. A start a person or a sidekick asked for always starts, because someone asked. File-watch is already debounced, and a loop's sub-workflow calls are sequential by the loop.

Editing a schedule writes a new version and re-arms the trigger only after a successful save. A workflow's own row and the builder's toolbar both read the schedule as off or as the next fire, written in the trigger's timezone and in the machine's own clock.

**One webhook address per workflow, on one port for the machine.** The daemon's loopback listener binds a single configured port — the default one constant chosen from a range no common developer tool uses — and the console's settings hold the one control that changes it. A workflow's address is therefore `http://127.0.0.1:<port>/hooks/<workflow>` and changes only when the user changes the port. The webhook trigger's own panel shows the full address under an **Address** heading with `Copy the address` beside it, and under both the line "One port for every workflow on this machine, set in Settings. The address changes only when you change the port." Where the port is already held at daemon start the listener does not start and nothing moves: settings show the port and that it is in use, and every webhook trigger shows the same reason in place of its address — "Port 7391 is in use, so the listener did not start and this workflow has no address. Change the port in Settings and the address comes back unchanged." — with no address and no copy control while that stands. No ephemeral port, and no silent move to the next free one.

**A workflow declares the inputs it asks for on its trigger**: each one named, typed, and carrying the value it starts on. Run now on a workflow that declares any opens a small panel under the control with one labelled field per input, drawn from its type — a checkbox for a yes or no, a list for a choice, a folder picker for a path, a box otherwise — seeded from those values, with the ones that may be left alone marked `(optional)`. Run starts the latest saved version with what was filled in, and a required field left empty says so in place while the panel stays open. A workflow that declares no inputs starts on the press.

**Two daemon dependencies carry this surface** and are recorded with the rest in §Implementation Notes: `croner` computes a schedule's next fire in its timezone, and the file-watch trigger uses Node's own recursive `fs.watch` on the pinned Node line with `picomatch` filtering the globs. The durable next-fire row remains the truth in both cases; neither library holds state that outlives the process.

### Definition file form — export and import (C-17)

A workflow definition has one canonical file form, and it is the file the authoring commitment already names, carrying the schema-version marker the versioning commitment already requires. **No second schema dialect exists**: the file is the definition, and its canonical bytes are the JCS-canonicalized JSON of the parsed document — which is precisely the existing hash preimage, so a definition's content hash is identical whether it arrived through the builder, the SDK, or a file.

The document has exactly two top-level parts:

1. The **definition body** — the hashed, canonical part. Everything the engine reads.
2. An **optional `layout` section** — the canvas geometry, outside the hashed body. An importer that does not understand it, or a consumer that does not want it, ignores it and loses nothing executable. A file written through the CLI or the SDK omits it entirely, and the document it produces is laid out deterministically when it is opened (§Canvas layout is not definition bytes (SA-35)).

Export serializes the current version to that one form, body plus the optional layout section. Import submits the parsed body through the ordinary create path with the ordinary validation, so an imported definition is subject to every refusal rule above and to the ordinary tool-governance resolution — an import can never carry governance state with it, and an import whose schema version is unknown refuses with its registered code rather than being read optimistically. Round-tripping is closed in both directions: builder → file → CLI → daemon and CLI → file → builder produce the same definition body bytes and therefore the same content hash.

## Chat-Invoked Start and Start Authorization

Governed by [ADR-027](../decisions/027-chat-invoked-workflow-start.md). Workflows are first-class objects of session chat in both directions: the user reaches them through one command root, and a sidekick reaches them through a curated set of callback tools. Every caller resolves to the typed operations of §Interfaces And Contracts and introduces no wire contract of its own — the shape [Spec-014 §Turn Policies](./014-multi-agent-channels-and-orchestration.md#turn-policies) already establishes for chat-typed affordances.

**Sixteen callback tools, each with a policy action.** A sidekick that builds or fixes a workflow needs to read the catalog, read a definition, validate one, read a run and read a step; a half set makes it guess. Each tool registers exactly as the first one did: a JSON-schema input, an approval category, and an activity record on every invocation. A sidekick's own tool allowlist decides which of the sixteen that sidekick holds.

| Tool | Adjudicated as |
| --- | --- |
| `workflow_kinds`, `workflow_list`, `workflow_read`, `workflow_runs`, `workflow_run_read`, `workflow_step_read`, `workflow_validate` | reads, gated on the session itself |
| `workflow_create`, `workflow_update`, `workflow_schedule_set`, `workflow_enable` (which takes the enabled flag, so it serves both the enable and the disable verb) | `Action::"workflow::author"` |
| `workflow_run`, `workflow_node_execute` | `Action::"workflow::start"` |
| `workflow_cancel` | `Action::"workflow::cancel"` |
| `workflow_resume` | `Action::"workflow::resume"` |
| `workflow_results_post` | `Action::"workflow::author"`, with the session derived from the invoking turn and never tool-supplied |

`workflow_results_post` never takes a session or a channel as an argument: the daemon derives it from the invoking turn's own context and validates it, so a forged target cannot be reached (§Discussion Integration Path). Registering each action in the Cedar schema is Spec-010 and Plan-010 surface, not this spec's; while the daemon's `approval.requestCreate` seam is unregistered the callback-tool registry is withheld at spawn and a stray invocation is answered `denied`, and that is the shipped state until its activation.

### Chat-start surface (SA-38)

**One command root, thirteen verbs.** The session composer registers exactly one root, `workflow`, and under it: `run`, `list`, `runs`, `results`, `open`, `create`, `edit`, `fix`, `schedule`, `cancel`, `resume`, `enable` and `disable`. One root is what keeps the command namespace collision-free, and verbs are additive under it; no verb is ever repurposed. Typing `/` in the composer lists the console's commands with `/workflow` among them, and typing `/workflow ` lists the thirteen verbs with one line of help each.

- A verb's name argument autocompletes over the definitions the caller can already see, through `workflow.definitionList`, and resolves most-specific-first — the session's own, then its project's, then the daemon's `shared` tier — so enumeration discloses nothing the caller could not already list.
- Ten of the verbs are direct calls to the operations of §Interfaces And Contracts. Three — `create`, `edit` and `fix` — are not: they compose a message to the session's current sidekick carrying the instruction plus a structured hint naming the intent and, where one exists, the definition, so the sidekick knows to reach for its own workflow tools. The reply lands as an ordinary chat message carrying a definition row or a results row.
- An unrecognized verb lands one flow row reading what the word takes. It presses nothing and never composes into a message.
- A sidekick's tool call that Cedar denies is answered denied and lands as an activity record, and the chat shows that refusal rather than a silent failure.
- Interception is total for the console's own words: `/workflow` and its verbs are executed by the client and never reach a channel message, a sidekick's context or a provider turn, on any path. Leading-`/` text the console does not own is not the runtime's to hold (§Command interception — the reserved `/` prefix (C-18)).

**No surface here shows internal code syntax.** Every error code, refusal reason, status, event kind and enum value renders as words in sentence case, so a wire pair like `sidekick.resolution_refused · account_unavailable` reads "Sidekick resolution refused · Account unavailable" and `workflow.start_denied` reads "Workflow start denied", each followed by the daemon's message in plain words. Tool names, policy actions and node kinds are wire spelling too: each daemon tool and each policy action registers the label a person reads — `workflow_results_post` reads "Post workflow results", and a refusal under `Action::"workflow::author"` reads "Needs permission to author workflows" — and the inspector's kind chip shows a kind's display name and version, never its id. An unlabelled code falls back to its own sentence-case words. Only what a person or a sidekick wrote or would type stays as written: model ids, file names and paths, commands, diffs, log output and prose. A parser's or a runtime's own error text is a code message and never reaches the screen — an import that does not parse says what is wrong in plain words and names the line.

### Command interception — the reserved `/` prefix (C-18)

Leading-`/` input in the session composer sorts into three classes, and exactly one of them belongs to the runtime. Which class a word falls into is decided by **who holds the value it would change** ([Spec-004 §The provider command and skill surface](./004-provider-driver-contract-and-capabilities.md#the-provider-command-and-skill-surface) fixes the three and this rule consumes them):

- **A word the console owns is intercepted and executed by the client**, pressing the console control that owns the value or doing the console's own work through the daemon. The text never composes into a channel message, a sidekick's context, or a provider turn — under any path, including the steer-through-composer surfaces that share the input box. A provider's own command for something a console control already holds is not forwarded either, because forwarding it would move the provider's state and leave the control reading the old value. `/workflow` and its verbs are console words, which is what makes a chat-borne start collision-proof by construction rather than by convention.
- **A word the bound provider's own enumeration carries that the console does not own is forwarded to that provider exactly as typed**, so the provider's own client dispatches it as it would in that provider's terminal. It is offered in the command list marked with the provider it came from, it is offerable and dispatchable only through the binding it was read under, and the runtime asserts no effect it did not witness.
- **Anything else is sent as the user's own prose**, with no press and no console message, neutralized at the driver's outbound frame boundary as [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior) requires, and the provider answers it as it would in its terminal: one provider's client replies that the command does not exist and spends a turn doing so, the other reads the words as prose. **There is no literal-slash escape and no unknown-command refusal of the product's own invention** — a word no row matches is a word going to the provider, not a word being refused.
- A console word whose argument its own control cannot take — a name the control does not offer, a value outside its range — answers with one flow row saying what the word accepts and presses nothing. It is never forwarded as text instead.
- The namespaces never overlap: `@` is addressing (**who** — resolving to `OrchestrationRunCreate` per [Spec-014 §Turn Policies](./014-multi-agent-channels-and-orchestration.md#turn-policies)); `/` is commands (**what** — resolving to typed operations). A definition name occupies argument position only (`/workflow <verb> <name>`), so no workflow name can ever collide with a command verb.

**The prose class rests on the driver boundary, and that code is still owed.** Neutralizing leading-`/` text where it is carried as prose is settled contract in [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior) — transport-only neutralization at the driver's outbound frame boundary, a closed frame-origin discriminator whose unknown arm neutralizes, and a runtime tripwire that fails the turn rather than letting a provider's zero-turn success be recorded as a completed one — and [Plan-004](../plans/004-provider-driver-contract-and-capabilities.md) T3.18 builds it. The same boundary governs the steer and queue paths, which carry free text into provider turns from outside the composer. Until that code merges, chat-borne workflow start is collision-proof by interception, and free text arriving from non-composer surfaces retains the provider-dispatch hazard: a bounded, named residual, not a silent one. The spawn-with-command-dispatch-disabled variant is rejected there: a provider flag is the provider's promise, not the daemon's guarantee, and may be set only as defense in depth.

### Start authorization (SA-39)

Starting a workflow run is adjudicated **per start** as the named Cedar operation action `Action::"workflow::start"`, in the `Spec-010` named-operation-action shape (the `Action::"intervene"` and `Action::"dispatch::<capability>"` precedents) — deliberately **not** a tenth approval category. A start traverses no approval pipeline, mints no approval row, and is never remembered: remembered grants key on approval category, so a category-shaped grant would silently cover every definition on the daemon — the wrong width for a per-definition operation. The default, mirrored as one row in the security-architecture Permission Matrix: the user may start workflow runs from any linked device, and a sidekick may start one only through its curated `workflow_run` callback tool under the same adjudication.

One rule governs the user and their sidekicks: the CLI path, the desktop path, the chat surfaces of SA-38, and the `workflow_run` callback tool all adjudicate the same action. A sidekick's principal is the invoking turn's effective principal under the Spec-010 actor-axis rules — consumed here, authored there.

**Principal resolution.** On the local daemon socket every JSON-RPC caller binds to the daemon's recorded node-owner user (the transport rule the contract doc records), so the local CLI and desktop paths collapse to the node-owner and the matrix row discriminates only on identity-carrying paths. The chat-borne start is the first per-user start surface: its authoring user MUST arrive as a **daemon-resolved value — the transport-authenticated user — never a client-supplied body field** (the admitting-principal-carrier class). Until the Spec-010/Plan-010 carrier registration lands (a Tier-5 targeted delta, gated by a named Plan-015 §Preconditions box), a chat-borne start resolves only the node-owner principal and **every other chat-borne start refuses** — fail-closed, with the refusal below, and with the CLI, desktop, and affordance node-owner paths unaffected.

**Refusal.** A denied start — a principal the matrix does not admit, an unresolvable chat-borne principal, or a `channelId` naming a channel the resolved starter cannot see (SA-38's channel validation) — refuses with `workflow.start_denied`, registered in `error-contracts.md` §Workflow as the first landed entry of the extension A-015-15 already owes. The arms are ordered and their disclosure is scoped: the principal adjudication runs first and may refuse with a message naming the denied action — the matrix is public surface, so naming it leaks nothing — and the SA-38 channel validation runs second, only for a start the matrix admits, with its not-visible and nonexistent-channel outcomes collapsed into one byte-identical message, so a denied caller — an agent leg above all — learns no channel-visibility or channel-existence fact (the `runtimenode.permission_denied` shape: one code, distinct messages where nothing leaks, collapse exactly where a distinction would). No other code is minted on this surface, preserving the no-unregistered-codes constraint of §Loud-errors discipline (C-12).

**Cedar registration is upstream surface.** The action literal and the chat-borne carrier are registered by the Spec-010/Plan-010 targeted delta; this spec names the semantics and consumes the adjudication (`PermissionCheckService`), authoring no Cedar schema entry — the one-writer discipline this corpus imposes.

## Implementation Notes

- Workflow authoring belongs in the product surface, but workflow execution still uses the same run, approval, and artifact primitives as free-form sessions.
- Version immutability simplifies replay and support.
- Phase-level parallelism remains explicit and bounded — no implicit concurrency.
- Persistence uses a LangGraph-inspired checkpoint pattern on the existing SQLite store (Spec-013), with the normalized-tables-over-JSON-blob decision documented in State And Data Implications. No external workflow engines (Temporal, Restate) — contradicts ADR-002 (local execution). V1 ships ahead of OpenTelemetry workflow semantic conventions and adopts OTel semconv additively when ratified.
- One execution model at V1 per C-11: local daemon runs workflows locally. Do not ship a `local | queued | remote` enum at V1.

**The four phase kinds compile down at run time, not at save time**, which is what keeps the document node-shaped end to end. Their executors reimplement nothing:

- The run-a-sidekick kind calls the existing run admission with the definition id from its sidekick param, and with the provider account, posture and tool allowlist resolved from that definition under any per-node binding override.
- The sidekick-team kind opens a phase-owned channel through the existing orchestration path.
- The approval kind raises a request through the existing approval pipeline and its Cedar check.
- The form kind writes through the existing form-state store.

The park-and-resume rules for provider limits apply to these steps unchanged, so a spent account parks the step and the run resumes itself when the account recovers (§Provider-limit pacing and durable resumption (SA-40)). The step record is a projection over the events those pipelines already emit.

## Pitfalls To Avoid

### Structural pitfalls

- Mutating running workflow definitions in place.
- Hiding workflow phase outputs outside the session timeline.
- Treating workflow pause as a UI-only banner with no durable execution state.
- Using mutable tags instead of content-addressed pins for external tool references — directly opens the CVE-2025-30066 class.
- Absorbing `BIND` multi-phase channel reuse into V1 without the three ADR-015 criteria being met — engineering risk budget is documented in Pass B §3.1.
- Recording sibling cancellation in async callbacks instead of at a deterministic synchronous tick checkpoint — reintroduces the non-determinism class observed in Temporal Java SDK #902.
- Collapsing `user_input` approval / `human-approval` gate / `human` phase into two categories — the three-way split is load-bearing (Pass C §2).
- Recognizing a provider usage-limit refusal by matching message text, an error string, a rate-limit window name, or a model id. Prose is not a contract; it changes without a version bump, and a matcher that silently stops matching converts a park into a burned retry ladder and then a false `failed` verdict, with no signal that anything changed (C-19).
- Holding a resume schedule in an in-memory timeout. A timeout is lost at the exact moment it is most needed — a daemon restart — and a run whose only route forward died with the process is stuck without anything having recorded that it is.
- Computing resume jitter with a modulus. When the intended span exceeds the operand's range the modulus never wraps, so the real spread collapses to a fraction of the declared width while every bound assertion still passes — the test proves the value is inside the window and proves nothing about the distribution.
- Arming a schedule from a window whose provenance is `model_default` or `estimated`. Those values are the driver's honest statement that the number is a guess; scheduling against a guess either fires into a still-spent account or holds a run that could have run, and both look like the engine knew something it did not.
- Letting the attention record gate work. A correlation record consulted by start, resume, or retry becomes an availability lock, and a stale one then makes a run unstartable after the account has quietly recovered — the "protection that isn't" class of C-12 in its most expensive form.
- Writing the engine's park cause into a phase output, an artifact, or an agent-visible context. Engine prose arriving through a model-output channel reads as something a model said, and a phase output is immutable truth (SA-16), so the sentence is unretractable once written.
- Re-pinning a run's frozen definition version silently, or as a side effect of an ordinary resume. A run whose early phases executed a definition no longer recoverable from the run cannot be replayed, verified, or explained.
- Re-pinning while any attempt of the run is in flight — the resume **continuing one** rather than entering a phase fresh, or a re-pin admitted through one branch's fresh entry while a parked parallel sibling still holds one — the same class as the silent re-pin above, reached by a caller who asked explicitly. The units already dispatched were launched from bytes the run would no longer be pinned to, so neither the attempt's inputs nor the outputs it returns remain explainable by the version the run's record names, and the operator who asked for a repair is told it succeeded over a run that repaired nothing.
- Clearing a durable resume schedule because its timer fired, rather than because the run left the park. A fire that re-checked and then failed to transition the run leaves a parked run whose only route forward has been deleted, with nothing recording that it is stranded.

### Security invariants (non-conformant if violated) — SA-13 / Pass E §4

Engine implementations violating any of the following are **non-conformant**. Each invariant is a testable contract requirement; concrete CVE-reproducer corpora and test categories are specified in [Plan-015 §Testing](../plans/015-workflow-authoring-and-execution.md) (SA-29, SA-30, SA-31 — implementation detail, not spec surface).

- **I1 — argv-only execution.** The engine **MUST NOT** accept a shell-string command form for user-templated content. No `shell=true`, no `/bin/sh -c "..."` over author-controlled fields. All commands execute via argv-list spawn only. Closes [GitHub Actions — Script-injection guidance](https://docs.github.com/en/actions/concepts/security/script-injections), [n8n CVE-2025-68613 (CVSS 9.9)](https://github.com/n8n-io/n8n/security/advisories/GHSA-v98v-ff95-f3cp), and [Airflow CVE-2024-39877](https://nvd.nist.gov/vuln/detail/CVE-2024-39877) in one architectural choice.
- **I2 — two evaluation tiers, both sandboxed, and no templating on the host.** The engine **MUST NOT** hand a workflow-definition string to a host template engine or to any host evaluator — no Jinja2, no `${...}` interpolation, no `eval` of document text, and no expression that can reach a host API. Document text is evaluated in exactly two places: an expression, by the sandboxed-by-construction evaluator of §Expressions, over a closed binding namespace, per item, in the daemon, under a per-evaluation time budget that aborts; and a program, inside the Code node's WebAssembly sandbox, under a memory budget and a deadline, with nothing bound into it that it was not given. Anything else is the template-injection class this invariant closes.
- **I3 — typed approver capability.** The engine **MUST NOT** treat approver permission as a submitter string or as "whoever has `Read`". Approver principal is a typed capability bound to an identity (Spec-010). Admin override is a distinct audited capability. Anti-pattern: Jenkins Pipeline Input Step historically approved on `Item/Read` (CVE-2017-1000108, fixed in plugin 2.8 on 2017-08-07) and still silently bypasses the `submitter` allow-list for holders of `Jenkins.ADMINISTER` with no audit emission ([Jenkins SECURITY-576 advisory, 2017-08-07](https://www.jenkins.io/security/advisory/2017-08-07); [`InputStepExecution.java` `canSettle`](https://github.com/jenkinsci/pipeline-input-step-plugin/blob/master/src/main/java/org/jenkinsci/plugins/workflow/support/steps/input/InputStepExecution.java); [JENKI16 Won't Fix](https://issues.jenkins.io/browse/JENKI16)).
- **I4 — secrets by reference only.** The engine **MUST NOT** accept inline secret material in workflow definitions. Secrets are referenced as `secret://<scope>/<name>` and resolved at phase-launch into env / stdin / named-file fd — never argv. Logging redaction is defense-in-depth on top, not primary control. Closes [tj-actions/changed-files CVE-2025-30066](https://nvd.nist.gov/vuln/detail/CVE-2025-30066) runner-memory-via-argv class. The redaction-is-defense-in-depth stance is motivated by [Airflow secret masker issue #54540](https://github.com/apache/airflow/issues/54540) Vault masking regression (Airflow 3.0.0-3.0.4).
- **I5 — content-addressed external references.** The engine **MUST NOT** resolve external tool references by mutable tag. References carry hash pins (`codex@v1.2.3#sha256=...`). Closes CVE-2025-30066 retroactive-tag-repointing class.
- **I6 — OWASP File Upload minimums on human-phase uploads.** The engine **MUST** enforce size cap, extension allowlist, magic-byte sniff, storage rename, path validate, AV hook, quarantine-on-fail per [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html). Closes [Argo CVE-2025-66626](https://www.endorlabs.com/learn/when-a-broken-fix-leads-to-rce-how-we-found-cve-2025-66626-in-argo) symlink-traversal-via-broken-fix class.
- **I7 — append-only hash-chained approval history.** The engine **MUST NOT** permit mutation of `workflow_gate_resolutions` rows. Workflow-definition edits are a separate audit entry. Replays use at-execution-time policy — not current definition ([Crosby & Wallach USENIX 2009](https://static.usenix.org/event/sec09/tech/full_papers/crosby.pdf); [AuditableLLM MDPI 2025](https://www.mdpi.com/2079-9292/15/1/56); Temporal's Event History is the reference pattern).
- **I1–I7 testability.** Every invariant has ≥1 test that fails when the invariant is violated. Test categories and CVE-reproducer corpora are specified in Plan-015 §Testing (SA-30).

### Terminology discipline (SA-17 / C-12)

- Use **"workflow"** (not pipeline / flow), **"phase"** (not stage / task), **"artifact"** (not output / capture when persisted), **"step"** reserved for intra-phase operations if any.
- Airflow Datasets→Assets, SubDAG→TaskGroup, execution_date→logical_date terminology churn is the precedent for cost of late rename ([Airflow — Upgrading to Airflow 3](https://airflow.apache.org/docs/apache-airflow/stable/installation/upgrading_to_airflow3.html)).

## Acceptance Criteria

- [ ] Workflows can be authored as versioned phase definitions with schema version marker; cycle-check rejects invalid definitions at author time.
- [ ] All four phase types execute: `single-agent`, `multi-agent` (`OWN` only), `automated`, `human`.
- [ ] All four gate types resolve correctly, with channel gates blocking phase transition per temporally-disjoint contract (SA-7).
- [ ] Workflow runs survive reconnect and daemon restart with phase state intact; replay reproduces deterministic `phaseRunId` sequence (SA-21).
- [ ] Parallel phase execution honors `ParallelJoinPolicy`; `fail-fast` cancels siblings at deterministic tick boundary (SA-4).
- [ ] Resource-pool admission (`pty_slots`, `agent_memory_mb`) blocks phase launch when pool saturated; tripwire events fire.
- [ ] `RUN_ITERATION_LIMIT` / `max_duration` / `max_retries` bounds all hard-fail with preserved `failure_reason` (SA-1, SA-2).
- [ ] Workflow phase outputs are addressable after workflow completion; retries produce new output rows (immutability preserved — SA-16).
- [ ] Human-phase `HumanPhaseConfig.timeout` is typed `'none' | Duration` with no field-level default (SA-10).
- [ ] Human-phase uploads enforce OWASP File Upload minimums; CVE-2025-66626 regression battery passes (I6).
- [ ] Approval history hash chain verifies on replay; tamper-detection tests pass (I7 regression battery).
- [ ] Security regression battery covers I1–I7 invariants with CVE-reproducer corpora (test surface lands in Plan-015 §Testing per SA-30).
- [ ] All 34 workflow event types emit in the Spec-005 envelope with correct ordering invariants; Pass F ordering-invariant tests pass.
- [ ] A parked phase is renderable from one `workflow.runRead` response, and a phase that resumed past an earlier park carries no park members on that response (§Park surfacing on the read model (SA-44)).
- [ ] A cancelled run's status and its cleared live park columns rebuild from the log alone, with `workflow.cancelled` as the sole durable producer of the `cancelled` status (§Operator run control (SA-45)).
- [ ] Secrets referenced via `secret://...` never appear in argv, logs, or artifacts (canary-secret regression — I4).
- [ ] The registered `/workflow start` command intercepts at the composer; unrecognized leading-`/` composer input refuses loudly, naming the `//` escape; command-namespace input never reaches a channel message or provider turn; the `//` escape is the sole path by which composer-originated leading-slash text is sent — as ordinary channel prose with one escape character stripped — and provider-bound composer paths refuse all leading-`/` input, escaped included, until the composer change activating the escape on those paths is authored and ships — Plan-004 T3.18's driver-boundary neutralization is that change's precondition, not its substitute, so T3.18 merging does not by itself lift this refusal (C-18).
- [ ] Every start path — CLI, desktop, chat command, composer affordance, `workflow_run` callback tool — adjudicates `Action::"workflow::start"`; a matrix-denied principal, an unresolvable chat-borne principal, and a `channelId` naming a channel the resolved starter cannot see each refuse with `workflow.start_denied` — principal adjudication first, channel validation only for a matrix-admitted start (SA-39, SA-38).
- [ ] Every workflow callback tool is withheld at spawn while the `approval.requestCreate` seam is unregistered; a stray invocation answers `denied`, never `completed` and never silence (SA-38).
- [ ] A usage-limit refusal is recognized from the typed driver signal alone and never from message text; it parks the phase immediately, consumes no `max_retries` attempt, mints no new `phaseRunId`, and increments no `max_phase_transitions` — including when no reset window was reported (SA-40, C-19).
- [ ] A durable `autoResumeAt` is armed only where the typed refusal's reset boundary is stamped provider-reported, is jitter-offset by a scaled — never modular — pure function of `workflowRunId` that replay reproduces, survives daemon restart via a post-rebuild re-arm, is never armed at or past the run's `max_duration` deadline, and is cleared by every transition out of the park (SA-40).
- [ ] Concurrently parked runs sharing a provider-account attention key present as one attention record; a mixed set of failures is never folded into a usage-limit record; and no start, resume, retry, or schedule fire consults the record — a run stays startable after its account recovers (SA-40).
- [ ] Every parked run is cancellable from every waiting state without precondition or wait, cancellation clears the durable schedule in the same unit of work, and the parked phase-state row with its `parkReason`, bounded `parkCause`, and completed outputs survives the cancel intact (SA-42).
- [ ] An operator resuming a parked run may re-pin it to the definition's current version explicitly; the re-pin is recorded on `workflow.resumed`, never fires from a timer or an ordinary resume, never re-runs or rewrites a completed phase output, and refuses at each of its three refusal points — a run that is not parked, a repair requested while any of the run's attempts is still in flight (the resuming phase continuing one rather than entering fresh, or a parked parallel sibling holding one), and a target version that cannot account for the phases the run already completed (SA-41).
- [ ] The engine event record is on for every run with no flag to turn it on, carries `workflowRunId` / `phaseRunId` / `attemptNumber` / sequence on every record, carries no secret material and no raw provider prompt or completion text, and is read by no replay, verification, projection-rebuild, or audit path — its expiry degrades diagnosis only (SA-43).

## Open Questions

Backfilled 2026-08-10 by the Tier-7 plan-readiness audit (A-015-12). Questions this spec settled are recorded below in §Resolved Questions and V1 Scope Decisions — including the OWN-channel `turns_per_agent` provider question, opened here 2026-08-10 and discharged 2026-08-11 by the Spec-014/Plan-014 restoring delta (PR #321; moved below per the settled-questions rule, PR #321 Codex round 2). The first entry here is open against **another** spec, not against this one; the second is open against this spec but is narrow — it asks how a value this spec already constrains is rendered, not what the value must be. No entry gates a Required Behavior row: §Deterministic identity (SA-21) is satisfied by any rendering that stays a pure function of the digest, so the determinism row holds irrespective of which rendering is ratified. Criterion 2 of the runbook `§Spec-Status Promotion Gate` is therefore satisfied by deferral with a named vehicle rather than by resolution.

- **Where the 34 `workflow.*` event types and their five categories are registered.** §Workflow Timeline Integration enumerates them, but [Spec-005 §Event Type Summary](./005-session-event-taxonomy-and-audit-log.md#event-type-summary) — the owning registry — carries no `workflow` category. Deferred to a combined Spec-005/Plan-005 amendment, following the `mcp_governance` registration precedent; registration moves the summary rows, the marker-governed in-band total, and Plan-005's census in one change. Tracked plan-side as [Plan-015 §Upstream-Tier Amendments Required](../plans/015-workflow-authoring-and-execution.md#upstream-tier-amendments-required) and gated by a named Precondition box on every Plan-015 phase.
- **How a derived `phaseRunId` is rendered into its text form.** §Deterministic identity (SA-21) fixes the preimage and, as of the 2026-08-10 clarification, fixes that the identifier is totally derived — but not the encoding of the digest into the column's stored characters. The obvious candidate, "ULID-shaped so the column type is unchanged," is not self-consistent as usually stated: Crockford base32 carries 5 bits per character, so a 26-character rendering spans 130 bits, and a ULID reaches 26 characters by padding its 128 bits and constraining the leading character — a rendering rule that must be written down rather than assumed. The audit deliberately did **not** choose: picking an encoding is a design decision of the same class as the scope domain, and the identifier is a durable primary key, so the choice is one-way. Deferred to lead ratification and a targeted Spec-015/Plan-015 delta, which must state the digest function's output width, the truncation or padding rule, the alphabet, and whether any leading-character constraint applies. Until it lands, implementation surfaces must describe the column as a derived opaque identifier and must not call it a ULID.

## Resolved Questions and V1 Scope Decisions

- **V1 scope per [ADR-015 amendment 2026-04-22](../decisions/015-v1-feature-scope-definition.md) (BL-097 resolution).** Full workflow engine ships at V1 (the then-17-feature V1 — workflow promoted from V1.1-deferred to V1; V1 subsequently grew to 23 features per the ADR-015 amendment of 2026-07-02, which does not affect this promotion). Two workflow-scoped V1.1 criterion-gated commitments documented in [ADR-015 §V1.1 Criterion-Gated Commitments](../decisions/015-v1-feature-scope-definition.md#v11-criterion-gated-commitments): (1) `BIND` multi-phase channel reuse (3 criteria); (2) `human`-phase default timeout once notification routing ships (1 criterion). (The ADR section gained a third, non-workflow commitment — the automated GDPR erasure endpoint, 2026-07-08 per BL-139 — and a fourth, also non-workflow — direct-first artifact fetch, C4, 2026-07-08 with the cross-node artifact pull-forward; neither affects this spec.)
- **V1 decision (BL-097 D1, Wave 1 §5.1):** no default timeout on `human` phase. Required typed opt-in `timeout: 'none' | Duration`. Revisit V1.x once notification routing ships. Rationale: three durable-execution engines (Temporal ∞, Argo `{}`, Camunda 8 expression-based) converge on no-default-timeout as modern convention; the `7d+escalate` alternative is illusory at V1 because no paging primitive exists — escalate fires telemetry-only, creating the "telemetry-that-looks-like-protection" silent-failure class (violates C-12).
- **V1 decision (BL-097 D2, Wave 1 §5.2):** `multi-agent` phase ships `ownership: OWN` only; `BIND` is criterion-gated V1.1. Rationale: modern multi-agent composition (2025–2026) is state-passing (Temporal Child Workflows, LangGraph `Command(goto, state)`, AutoGen `HandoffMessage`), not handle-binding. BIND adds 5 state-machine invariants on top of OWN's 3 (retry↔BIND, abandon↔BIND, gate-scoping lattice, membership snapshot timing, termination authority); Airflow SubDAG's lifecycle bugs took 3+ years to patch before deprecation. OWN-only→V1.1 BIND is additive (non-breaking); OWN+BIND at V1→V1.1 revision is breaking.
- **V1 decision (amended 2026-08-10, Tier-7 plan-readiness audit):** the workflow-definition scope domain is three-valued — `session` \| `project` \| `shared`. `session` binds a definition to its authoring session; `project` spans the sessions of one project; `shared` is the cross-project tier, a definition authored once and reusable by any project on the same daemon. All three resolve out of the same local definition store: no additional table and no synchronization path. Scope identity is carried by a `scope_ref` value alongside `scope`, in the shape [Spec-025 §Unified Inventory](./025-mcp-server-configuration-and-governance.md#unified-inventory) already uses for scope-qualified bindings — the authoring session id at `session`, the canonical repository root at `project`, the empty string at `shared` — and definition dedupe keys on `(scope, scope_ref, contentHash)` so one definition stored at a scope is one record regardless of which session submitted it. Resolution at run start walks the tiers most-specific-first — `session`, then `project`, then `shared` — with **no merging across tiers**: two definitions of the same name at two scopes are two distinct definitions, exactly as two same-named MCP bindings in two scopes are distinct entries. Widening `scope` alone would not be storable: `project` would name no project, and a dedupe key rooted in the authoring session would split a `shared` definition into one record per submitting session. `workflow_definitions.session_id` keeps recording the authoring session at every scope, so provenance survives the widening. `shared` widens **visibility and reuse breadth only** — it is not publication, not a marketplace, and not cross-machine sync; global workflow libraries and any distribution of definitions beyond the storing daemon remain out of scope per §Non-Goals. The `channel` scope value that appeared on the contract doc and the SQLite DDL before this amendment was never specified here and is struck: a channel-scoped definition has no defined visibility semantics.
- **V1 decision:** workflow definitions are canonical durable definition records, not canonical artifacts. Artifact publication is allowed only for derivative exports, previews, or summaries.
- **V1 decision:** one execution model (local) at V1 per C-11. No `local | queued | remote` enum at V1.
- **V1 decision (2026-08-11, discharged upstream — PR #321; Plan-014 D-014-23):** the surface providing the OWN channel's `turns_per_agent` budget — opened as a 2026-08-10 audit question (A-015-07): §Interfaces And Contracts specifies the budget and §Workflow Timeline Integration emits progress at 25 / 50 / 75% of it, but no Spec-014 `ChannelConfig` field, `workflow_channels` column, or Spec-014 default supplied a value, and the "bare-channel 50" comparator had no bare-channel default to compare against. Ratified resolution, landed by the Spec-014/Plan-014 restoring readiness-audit delta: [Spec-014 §Interfaces And Contracts](014-multi-agent-channels-and-orchestration.md#interfaces-and-contracts) carries `ChannelConfig.turnsPerAgent` (optional positive integer; absent = the session default, so the bare-channel-50 comparator now has its default; create-time-fixed like every `ChannelConfig` member) and [Spec-014 §Stop Conditions](014-multi-agent-channels-and-orchestration.md#stop-conditions) carries the `InterruptReason` member `workflow_phase_cancelled` — the mechanism the SA-9 `REQUEST_CANCEL` and `TERMINATE` policies invoke. Plan-014 owns both (D-014-23); this spec's engine sets the former at OWN-channel creation and names the latter in its cascade, authoring neither. Plan-015's A-015-07 §Preconditions box is checked, and the cancel arms carry no upstream provider block (entry moved from §Open Questions at discharge — PR #321 Codex round 2).
- **V1 decision (2026-08-11, chat-start amendment; [ADR-027](../decisions/027-chat-invoked-workflow-start.md)):** workflows are chat-invocable through three callers of `workflow.runStart` — the intercepted `/workflow start <name>` command, the composer affordance, and the `workflow_start` callback tool — under the reserved-`/` interception rule (C-18), with start authorization as the named Cedar operation action `Action::"workflow::start"` (never an approval category, never remembered; chat-borne principal daemon-resolved, fail-closed until the Tier-5 carrier delta). Rejected shapes and the full antithesis are recorded in ADR-027 §Alternatives Considered: workflows are never `@`-addressable pseudo-users (`@` is addressing, `/` is commands), and no tenth approval category is minted.
- **V1 decision (2026-08-16, workflow-hardening amendment):** a workflow run's park is a first-class, durable, explicable state rather than a failure or a retry. Four rules are ratified for V1. **(1) Typed recognition, immediate park (SA-40, C-19).** A provider usage-limit refusal is recognized from a typed driver signal alone — never from message text, prose, a window name, or a model id — and parks the phase at once without entering the retry ladder, even when no reset window was reported. That carrier is **not yet shipped** and this spec does not mint it: it is owed by Spec-004 and Plan-004 as a sibling axis beside `RecoveryCondition`, and until it registers, a quota refusal travels the ordinary failure path and none of this section is reachable — the honest fail-closed V1 state. **(2) A durable schedule where a boundary is real (SA-40).** Where the typed refusal's reset boundary is stamped provider-reported, the parked phase arms a durable `autoResumeAt` value (never an in-memory timeout) with scaled, run-id-derived jitter and the run resumes itself across daemon restart; where that provenance is a default, an estimate, or absent, no schedule is armed and the park is unscheduled rather than invented. The account-plane `usage.rate_limit_update` display snapshot is deliberately not consumed by any of this. The `max_duration` deadline stays authoritative over any armed instant. Concurrently parked runs fold onto one provider-account attention record, which never gates start, resume, or retry. **(3) Repair and cancellability (SA-41, SA-42).** An operator may resume a parked run onto the definition's current version explicitly and audited, at a resume that enters a phase fresh — refused at three points: where the run is not parked at all, where the target version cannot account for phases the run already completed, and where any of the run's attempts is still in flight — the resuming phase continuing one, or a parked parallel sibling holding one — because a definition swapped under units already dispatched from the frozen bytes explains neither their inputs nor their outputs; and a parked run is always cancellable from every waiting state, carrying a bounded engine-authored park cause that never reaches a phase output or an agent-visible context. **(4) An always-on engine event record (SA-43)** on the Plan-018-owned bounded-retention diagnostic tier, non-canonical and read by no correctness path — always on because a run parks once and there is no second chance to have turned the log on. Rejected shape, recorded rather than assumed: a schedule armed from any reported window regardless of provenance. It was rejected because a window the driver marked `estimated` is a guess, and a run held on a guess is indistinguishable, to every reader, from a run held on a fact. Deferred rather than scoped: cross-run campaign memory and the durable wake-coalescing delivery substrate, criterion-gated to V1.1 under the three named criteria of §Non-Goals.
