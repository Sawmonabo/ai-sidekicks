## Purpose

Define how reusable workflows are authored, versioned, and executed inside sessions. V1 ships the full workflow engine: the node catalog, whose agent and person kinds delegate to the existing run, orchestration, approval and form machinery, parallel steps admitted by a memory gate, and durable state with append-only approval history. The engine plugs into existing daemon primitives (Spec-014 orchestration runs, Spec-010 approvals, Spec-012 artifacts, Spec-005 events, Spec-013 recovery) — workflow execution does not duplicate them.

## Scope

This spec covers:

- A visual, node-graph builder on a canvas, whose agent steps run on the user's own provider accounts and their own agent definitions
- Workflow authoring as one node-shaped document plus a typed TypeScript SDK (no bespoke DSL per C-1), and the canonical file form definitions export to and import from (§Definition file form — export and import (C-17))
- Workflow versioning (immutable-by-version with content-hash identity)
- The V1 node catalog (§Node-Kind Taxonomy) — among them the kinds that run an agent or ask a person, `agent.run`, `agent.multi-agent`, `human.approval` and `human.form`, whose executors delegate to the existing run, orchestration, approval and form machinery at run time
- Step execution for every node kind, a failure on a node handled by its own `onError` and clamped `retry`
- Steps that wait on a person — an approval, a form or a chat reply — on one wait mechanism
- The full V1 trigger set — manual, schedule, file change, loopback webhook, session event, chat, sub-workflow and error — with every arm honored at ship time (§Entry node and the V1 trigger surface (SA-37))
- Parallel step execution with memory-gated admission and bounded iteration
- Append-only approval history (C-13 / I7)
- Workflow event taxonomy (new Spec-005 categories + event types)
- Durable step state persisted via Spec-013 (SQLite + WAL)
- Replay-determinism contract
- Workflows as first-class objects of session chat in both directions: from a message, the user or an agent can list, read, create, edit, fix, run, schedule, cancel, resume, enable and disable a workflow and fetch a run's results
- A run history that keeps every step's input, output, logs, timing, cost and error, inspectable per step and re-runnable from any step

## Non-Goals

- General-purpose external workflow engines (no Temporal, Restate, Argo binding at V1)
- Marketplace or distribution semantics for workflow templates — publishing, importing from outside the daemon, or any cross-machine sync of definitions. The `shared` scope value adds daemon-local cross-project **reuse**, which is a visibility breadth, not distribution. A `shared` definition never leaves the daemon that stores it, so this Non-Goal stands with its subject stated precisely. Definition portability between machines at V1 is therefore the file form of §Definition file form — export and import (C-17) — a file the person moves, never a service that moves it.
- Queue mode and worker pools. The engine is one process inside the daemon. A quick Code step, and an expression whose reachable data includes an artifact, runs on a `worker_threads` thread of its own, started for that step and ended with it (§Implementation Notes); such a thread runs one step and is not a worker. The run record stays serializable, so what a run is never depends on where a step ran.
- External binary storage as a configured tier. A payload too large to sit inline becomes an artifact through the existing ingest pipeline, and an item's binary reference keeps that escape hatch open.
- Declarative node authoring for HTTP-shaped kinds — the second authoring style n8n offers, where a node declares its requests and operations as data, with `routing`, `requestDefaults` and `requestOperations`, rather than executing them. One imperative executor per kind is enough.
- A second spelling of anything the expression surface already has: no legacy node-indexed or item-indexed lookups, no second query language beside the expression language of §Expressions, no `continueOnFail` beside `onError`, and no second execution order. One spelling of each.
- The SQL-query merge mode, and an expression-extension library that adds methods to built-in types.
- Pixel-level UI design for the workflow editor. V1 ships the visual builder surface specified in §Visual Workflow Builder — its node taxonomy, port and connection rules, refusal set, layout tier, and scope semantics are normative here; type scale, color, spacing and motion are the console's own design-token surface and are not fixed in this spec.
- A default `Timeout` on a step that waits on a person, and any reminder after the first. The kinds that wait on a person carry a `Timeout` that is empty by default, meaning the step waits until it is answered (§Human steps — `HumanStepConfig` (SA-10, SA-11, SA-12)). The start of the wait is its one escalation: `Waiting on you` is posted once and never again while the step waits, because the bell keeps counting it on every device until it is answered.
- **A durable cross-run delivery substrate.** One spent provider account is heard about once, through the fold of §Provider-limit pacing and durable resumption (SA-40), which groups concurrently parked runs by their account's attention key; every parked run stays individually visible and individually resumable (§Park integrity and cancelability (SA-42)). No claim, delivery record or attention state is carried from one run to the next. The only values one run leaves the next are the ones a `Set variables` step keeps with `Keep for later runs` (§Node-Kind Taxonomy).
- An OpenTelemetry exporter. A run's page, its step panel and the event record are its whole trace; no run is sent to an OpenTelemetry collector or any other exporter.
- Execution-model enum (`local | queued | remote`) — C-11 commitment is local-only at V1 (Airflow executors and n8n `own` mode precedent: every system that enumerated execution models at V1 had to break-remove entries later).

Three layers own the surface, and each owns one thing:

- **The shared contracts** define the document, items, node kinds, run and step records, events and method schemas as the single source both other layers read.
- **The daemon** owns definitions, runs, the engine, expression evaluation, the node-kind registry, the triggers, the scheduler, the agent tools and the request handlers.
- **The renderer** owns the three tabs — Builder, Workflows and Runs — the builder's own draft store, the canvas, the palette, the inspector, the catalog, the run detail and the chat verbs.

The renderer parses on every read and the daemon validates on every write. Where both evaluate the same rule, the daemon's answer is authoritative and the client's edit-time check is a mirror of it, never a replacement for it.

## Required Behavior

### Authoring + versioning

- Workflows must be authored as one explicit node document with stable node ids and versioned structure.
- Workflow authoring format: that document plus a typed TypeScript SDK. **No bespoke DSL** (no CUE, no HCL, no custom expression language) — C-1 commitment. DSL lock-in cost is precedent-heavy: Dagger maintained its CUE SDK as primary authoring language from Jan 2022 (v0.1.0) through Dec 2023, then ended CUE SDK support after a year of dual-maintenance against multi-language SDKs, citing that "engineers...want to write code in a language they already know. Learning a brand new language, however powerful, is simply not what they're looking for" ([Dagger — Ending Support for the Dagger CUE SDK, 2023](https://dagger.io/blog/ending-cue-support/); [Solomon Hykes on Changelog #550, 2023](https://changelog.com/podcast/550)); GitHub Actions migrated off HCL to YAML under breaking-change pressure ([GitHub Actions HCL→YAML deprecation, 2019](https://github.blog/changelog/2019-09-17-github-actions-will-stop-running-workflows-written-in-hcl/)).
- Workflow definition files must carry an explicit schema version marker — the document's own `schemaVersion` field, whose V1 value is `2`. Daemon must support compat mode for reading older-marker files (SA-14 / C-8 — Temporal's Version Sets → Build IDs retrofit is the precedent cost avoided here).
- Workflow definitions must be stored as first-class durable definition and version records. Artifact publication may represent workflow exports or summaries, but it must not be the canonical source of workflow definition truth.
- `WorkflowDefinitionCreate` must run a DFS three-color cycle check against the node graph and reject invalid definitions with a typed error. The graph the check runs over is the one the document declares — its edge list, each entry naming a source node and handle and a target node and handle (§Graph model — nodes, ports, and edges (SA-32)) — and it walks the `main` edges only. It exempts exactly one shape: an edge whose target is a loop node's own input, because closing a loop body is the loop rather than a cycle.

**Saving is one act, and it always writes a version.**

- Save stays unavailable until the draft differs from the version it was loaded from, and it answers the platform's save chord.
- Save writes a new immutable version and never mutates an existing one.
- Saving an edit to a `shared`-scope definition creates a new definition at the editing context's scope carrying the original's content hash as its parent, and leaves the original untouched (§Definition scope in the builder (SA-36)).
- The scope choice lives in one small panel anchored directly under the Save button, holding the scope control, the version line and Cancel and Save, with nothing dimmed behind it. That panel is the only place scope appears while authoring; nothing about scope stands on the canvas.
- Run now against a dirty draft asks to save first and runs the version it saved, never unsaved bytes. Run this node and Run from here follow the same rule: the same save prompt, then the version just saved.
- Closing the builder with unsaved changes asks once, and the draft survives a reload.
- A save the daemon refuses leaves the draft intact and lists every refusal in the validation strip below the canvas.
- The validation strip's unsaved-changes row counts the nodes that differ from the saved version with a verb that agrees — `Unsaved changes · 1 node differs from version 7.` — and a draft that has never been saved says so rather than naming a version it does not have: `Unsaved changes · never saved, 1 node to save.` The prompt on leaving reads the same line.
- What is hashed is a fixed field list — name, description, trigger, nodes, edges — canonicalized with a recursive key sort, JCS-serialized and BLAKE3'd. Content fields only, so ids, timestamps and runtime state never produce a spurious conflict, and the layout and pinned-data sections sit outside the preimage (§Canvas layout is not definition bytes (SA-35)). Where a surface shows that hash it shows it short: the `b3:` prefix and eight hex characters.

**Versions are readable where the workflow is authored.** The builder's toolbar carries a version readout, and opening it opens a Versions panel beside the canvas listing the workflow's versions newest first, each with when it was saved, who saved it — the user, or the agent that did — and a one-line count derived from the structural diff ("2 nodes changed, 1 edge added"). The panel's heading and count draw at once; until the versions have been read the list reads `Loading the versions…` after the session's short delay, a read that fails reads `Could not load the versions` with `Try again`, and a workflow never saved reads `This workflow has never been saved, so it has no versions yet.` Selecting an older version shows its difference against the current one on the canvas itself: changed nodes marked, added edges in the success color, removed edges dimmed, and the inspector showing the selected node's old and new params side by side. The panel offers two acts: **Restore**, which saves a new version identical to the selected one and rewrites no history, and **Show runs**, which opens the Runs tab with its workflow filter set to this workflow and narrows it to the runs pinned to that version, the version standing as one removable chip in the filter row that is never kept. The `version vN pinned` chip in the header of a run's own page opens the same panel with that version selected; the rows of the runs table carry no version chip. The diff is computed in the daemon over the hashed body only, so a node's position never counts as a change and every reader — the panel and an agent reading a version's changes alike — gets one answer.

### Execution semantics

- V1 ships every node kind of the catalog (§Node-Kind Taxonomy). The kinds that run an agent or ask a person — `agent.run`, `agent.multi-agent`, `human.approval` and `human.form` — delegate at run time to the existing run, orchestration, approval and form machinery; there is no separate phase type and no gate type. An approval is a `human.approval` node with `approved` and `rejected` outputs.
- V1 ships parallel steps with memory-gated admission (SA-3). The executor's tick admits from one line of ready steps, and no fixed count bounds how many run: a step starts while the machine has room for it.
- Iteration must be bounded by three rules:
  - Per-step `max_retries`: each node's `retry.maxTries`, clamped by the engine (default 3).
  - Runs that start runs form a chain, and the chain's count bounds it (SA-1; §Entry node and the V1 trigger surface (SA-37)). When a chain has started as many runs as `Ask me after one start leads to` on the Runtime settings page allows — 100 by default — its next start waits for the person's answer. Within one run nothing repeats without bound: every cycle other than a loop closed back into `Loop over items` is refused at save, and that loop is bounded by its items.
  - A run's wall-clock bound, `max_duration`, is the console-wide `Stop a run after` value on the Runtime settings page: **unset by default**, one value for every run, and never a column on a run. Where it is set, a run that has been working longer than that ends as `failed · timed out` (`workflow.step_timed_out`, cause `run_cap`), with `failure_reason` preserved (SA-2); time the run spent waiting on a person does not count against it, while a park on a spent provider account does, because the bound is wall-clock (§Provider-limit pacing and durable resumption (SA-40)). A timed-out run never touches the workflow's schedule, which fires again as planned. There is no per-workflow cap and no document field for one; the node kinds that execute something or wait on a person carry their own `Timeout` param instead — the agent run, the shell command and the human kinds empty by default, meaning none, and the Code node 5 s by default.
- Admission (SA-3) is one memory gate, and memory is the only real pool behind it:
  - Capacity is read fresh on every tick from `process.availableMemory()`, which on macOS sums free, inactive and purgeable pages from Node 24.16.0 on (on Node 22 it returns free pages alone, the same number as `os.freemem()`), so the daemon and the CLI run on Node 24.16 or later. From the reading the gate takes a headroom of 20 % of physical memory, at least 1 GiB, and the reservation of every step it has admitted and not yet finished, because the reading shows only part of what a new process takes, and late.
  - A step's reservation is its kind's starting figure per provider until that workflow node has run, and then the peak the node reached on this machine, so the figure calibrates itself where it runs. A quick Code step's reservation is its own memory budget, plus 32 MiB for its thread, plus nine times the size of its input.
  - A step whose size is an estimate — a provider's process, a `bun` or Python step — starts at least 1.5 s after the last such start, so its effect is visible before the gate grants another; a quick step starts as soon as it fits, because its reservation is a bound it cannot pass.
  - At least one step is always admitted, so a machine under memory pressure makes progress instead of deadlocking.
  - A step waiting on a person — an approval, a form, a wait for a reply — or parked on a spent provider account holds no reservation while it waits.
  - Ready steps wait in one line in the order they became ready, across every run, and siblings that become ready together join it in their `order` (SA-5). The gate weighs only the step at the head of the line, and a step behind it never starts first, so a large reservation is never passed over by smaller ones; when nothing is running, the head is admitted whatever its size. No step, node or workflow carries a priority or a weight: the person's levers are `Pause new runs`, cancel, and the trigger's overlap choice.
  - A step the gate is holding reads `waiting-memory` on its node and starts itself when room appears.
  - Nothing else bounds what runs: there is no maximum step count, no terminal slot pool, and no limit of the engine's own on what an agent step may do or how long it may run.
- A fan-in joins through a `flow.merge` node, whose mode decides the join (SA-4): `append`, `combine-by-field`, `combine-by-position`, `choose-branch` or `first-to-arrive`. `First to arrive` passes on the first input to succeed and cancels the branches still running.
- When a run ends failed or canceled — a step whose `onError` is `stop`, a `flow.stop-error`, the run cap or a person's `Cancel` — every sibling branch still running is canceled through the executors' cooperative abort, and its steps read `canceled`, so nothing the run started acts after the run has ended. A canceled branch counts as settled only after its last edit has reported and the daemon has read the checkout from disk, never from the tool's own result: on both providers an interrupt does not stop an edit already under way, an edit leaves the whole file or none, and a tool result can report a write as rejected while the whole file is on disk. A sibling cancellation is recorded at a deterministic synchronous tick checkpoint — never in async callbacks (prevents the non-determinism class documented in Temporal Java SDK #902).
- An agent step creates runs only through the existing run admission (`agent.run`) or `orchestration.runCreate` (`agent.multi-agent`).
- A workflow step may create runs, request approvals, emit artifacts, or wait on a person.
- Workflow execution must remain visible in the session timeline and must preserve per-step provenance.
- Step outputs must be durable, addressable after workflow completion, **and immutable once written** (SA-16 / C-9). Accumulator patterns build on top (e.g., a `collect` step reads N upstream outputs and emits a new output). A retry is a new attempt, with its own `stepRunId` and its own output — never an overwrite. The GitHub Actions Artifact v3→v4 mutability-forced migration is the precedent ([GitHub Actions — v3 artifact deprecation notice, 2024-04-16](https://github.blog/changelog/2024-04-16-deprecation-notice-v3-of-the-artifact-actions/)).
- Workflow execution must be resumable after daemon restart or client reconnect.

**How the engine walks the graph.** The daemon owns the run. A topological scheduler walks the edge list depth-first, sorting a node's siblings by that node's own explicit `order` value, so moving a node on the canvas never changes what the run does. A node runs when all of its `main` inputs are settled. A node with more than one `main` input parks in a per-(node, run index) partial-input buffer until every input slot is filled. A node whose input carries no items is skipped unless it is marked to always output data. A disabled node passes its input straight to its output. A loop node keeps its remaining items in per-node run context and is closed by the author wiring the loop body's last node back into it, which re-executes it under a new run index — which is why a step record is an array per node and why the expression surface exposes a run index at all.

**What a run and a step record keep.** A run record carries its id, the definition and version it is pinned to, the session it lives in, the execution context it runs in (§Interfaces And Contracts), the first run of its chain, its status, its mode, its trigger record, who or what started it, when it started and finished, and its error where it failed. One step record exists per node attempt, carrying: the run id and node id, the attempt number, a per-run monotonic `executionIndex`, the source array naming for each input the edge that actually fed it and which run of the source produced it, the status, the timings, the payload references — input, output and log — the cost receipt where a provider was billed, the typed error where it failed, and the instant a step waiting on a person gives up where its `Timeout` is set. The `executionIndex` gives a faithful "what happened when" list for a branching run, and the source array is what lets a run's detail say that this run of a merge consumed run 3 of the loop. One structure is what makes a branching run renderable, partial re-execution expressible and staleness computable.

**A run's own state.** Run statuses are `new`, `running`, `waiting`, `succeeded`, `failed`, `canceled`, `crashed`, and nothing else is ever displayed. Step statuses are `pending`, `running`, `waiting`, `waiting-memory` (held by the memory gate before it starts), `succeeded`, `failed`, `skipped` and `canceled` (a step that was running or waiting when its run ended failed or canceled). A `waiting` step carries its cause — `approval`, `form` or `reply` when it waits on a person, `chain` when an `Execute workflow` step's child is held behind its chain's question, `account` when it is parked on a spent provider account — and, where one is armed, the instant it resumes itself. A step cut by a time limit — its own `Timeout`, its deadline or the run cap — reads `failed · timed out` (`workflow.step_timed_out`). Modes are `manual`, `trigger`, `webhook`, `chat`, `agent` (an agent's own tool call), `retry` and `sub-workflow`. What started a run is one of: the user, a schedule, chat, an agent, a webhook, a file event, or a parent workflow.

**Crash sweep and waiting.** On daemon start, runs left in `new` or `running`, and runs in states no longer decidable, are swept to `crashed`; a run in `waiting` is never swept and never pruned, so a parked approval survives a restart and rehydrates. A node that suspends stores a resume token on the run under a durable `waitId` that ties the wait to its run, its step and its session, sets the wait deadline where one exists, offloads its run data, and resumes on the matching resolution or timer. The approval node, the form node and the wait-for-a-chat-reply node all ride that one mechanism, so a paused run is one state rather than three. A step that waits on a person asks on the session's own question card, with the workflow's name as the card's chip, and the run's page is a second door onto the same question; the first answer, through either door, settles the wait everywhere at once, and every other message in the session stays an ordinary message. The answer is tied to the question by its `waitId`, never to whichever message arrives first, because two runs of one workflow can wait in the same session, a child run waits in its parent's session, and a person's next message there may be meant for the agent. The start of a wait on a person is its escalation: the bell counts it and `Waiting on you` is posted on every device the person uses, once. The deadline a set `Timeout` arms is written on the step's row when the step starts waiting and is the truth; the in-process timer is a cache over it, re-armed from the row when the daemon starts, so a deadline that passed while the daemon was stopped or the machine slept fires at once on start or wake (§Human steps — `HumanStepConfig` (SA-10, SA-11, SA-12)).

**Every step boundary is an event.** A step's start, finish, failure, cancellation or skip emits `workflow.step_started`, `workflow.step_finished`, `workflow.step_failed`, `workflow.step_canceled` or `workflow.step_skipped` into the session event log (§Event types (SA-19)), so the Runs tab and the session's own record are one truth rather than two. The engine commits the step rows one turn of its loop started or settled in one transaction, never a commit per row, and hands that turn's events to the event log as one batch under Spec-013's batched transactions (50 events or 10 ms to a transaction). Twenty steps starting and finishing together cost 1.3 to 2.3 ms of the daemon's time in one transaction, against up to 12.3 ms one by one. There is no write rate limit, because nothing the engine can emit outruns the store: a sustained 10,000 step boundaries cost 17 to 19 µs each.

**A quick step runs on a thread of its own.** The engine is one process. A quick Code step runs on a `worker_threads` thread started for that step and ended with it, because on the daemon's own thread one ordinary step delays the session frame by 26 to 38 ms and a runaway stops every session for its whole deadline. An expression whose reachable data includes an artifact runs its evaluations on a thread the same way (§Expressions). A step ends when its deadline passes, when its run ends or when the person cancels: the interpreter's interrupt handler reads a shared cancel flag, and a thread that has not answered 250 ms later is ended with `terminate()`. Each thread's JavaScript heap is capped with `resourceLimits`, so a defect in the step's host ends that thread and never grows the daemon; a thread that ends without an answer fails its step with `workflow.step_thread_failed` (§Implementation Notes).

**A partial run decides what to skip from a dirty-node lattice** computed over the last run's step data:

- Editing a node's params marks that node.
- Inserting or deleting a node marks the following node.
- Adding a connection marks its destination.
- Disabling a node marks the next node.
- Any dirty node inside a loop marks the loop head.
- Pinning or unpinning marks the nodes it affects.

"Run from here" then executes the target's ancestors plus the target, reusing clean step data and re-executing only what is dirty; "Run this node" is the single-node case of the same call and uses pinned or prior input. The lattice lives in the builder's own draft store for display, and the filtered run is computed by the daemon, whose answer is authoritative.

**Pinned data makes an offline authoring loop possible.** A node's pinned items live on the document outside the hashed body, so pinning creates no version. Pinned data is honored only in a manual run and ignored by every trigger-started run. A node may be pinned only where it has a single `main` output and its items carry no binary payload. Unpinning is offered as a banner link at the top of the node's Output panel. A run's detail offers "Copy this run into the builder", which loads the run's document version and pins the run's data onto the first node — which is what carries a production failure back into the builder as data to author against.

**Run data is kept in three tiers.**

1. The run rows — status, timings, trigger, the one-line summary — are kept until the user deletes them. They are the history list.
2. Step data — each step's input, output and log, whether inline under the payload cap or spilled into an artifact above it — is kept for the run-data bound [Spec-020 §Retention Policy](./020-data-retention-and-gdpr.md#retention-policy) sets, which nothing overrides per workflow; the control that sets it is the machine-local settings surface of [Spec-006 §Required Behavior](./006-local-ipc-and-daemon-control.md#required-behavior), one place per value. Past the bound the run still lists and still carries its status, timings and summary, and its step panel reads that the data expired in place of its panels. A run the user marked **Keep** holds its step data past the bound, and a run in `waiting` is never touched. The sweep that expires step data is one job on the service's one scheduler, which runs every background job at its own cadence, under its own condition and budget, and never two at once. It never deletes a session, a workflow's own session included: the one way a session is deleted is `Delete old data`.
3. Files a workflow saved on purpose, through the save-as-artifact kind, are the user's work product and are never auto-deleted.

Deleting is asked for once and is never undone: the Runs tab carries **Delete run** as a run row's one action and **Delete runs older than…** above the list, each naming what goes and saying that a run marked Keep stays and a run waiting on a person is never touched. `Delete run` on a run that is `new`, `running` or `waiting` is refused in place with `Cancel it first.` (`workflow.run_not_deletable`) and nothing is deleted; `Cancel` is offered on every one of those runs. Deleting a run removes its step data, its snapshot capture folder and the pins that folder holds. Deleting a workflow soft-deletes it and leaves its runs readable against their pinned versions.

**Redaction happens before the first write.** Every secret value resolved for a step is added to the run's redaction set before any log line, step payload or error message is written, so no resolved secret is ever stored (§Secrets — by reference only (C-15)).

### Expressions

A param's value is either a literal or an expression string in the form `={{ … }}`, where the leading `=` is the marker — so a literal string that happens to contain braces is unambiguous.

The bindings an expression can name are these: `$json`, `$input.all()` / `.first()` / `.last()` / `.item`, `$('<label>')` with `.all()` / `.first()` / `.last()` / `.item` / `.params`, `$runIndex`, `$itemIndex`, `$now`, `$today`, `$env` (allow-listed names only), `$vars`, `$run { id, startedAt, trigger }` and `$workflow { id, name }`. No expression resolves a secret: a secret reaches a step only through a field its kind marks sensitive (§Secrets — by reference only (C-15)), and an expression that names one is refused at save. A reference by label resolves through an id index, so renaming a node is a metadata edit and never a graph-wide rewrite. `$vars.<name>` reads the value this run set for that name with `Set variables`, and where this run has not set it, the value kept by the latest run that kept it; a name nobody set reads as absent. Two runs going at once each read what was kept when they read it, and the one whose step finishes last is what the next run reads.

Two tiers exist and the document says which is which:

- **Expressions** are evaluated in the daemon only, per item, with an explicit item index, by a sandboxed-by-construction evaluator with no host access — the JSONata library, with the binding namespace registered as its own variables and functions. One evaluation is budgeted at 5 ms and aborts when it exceeds it; an evaluation over budget refuses with a registered code rather than running on. An evaluation whose reachable data is all inline — the node's input and every earlier output it names, each under the 64 KiB inline cap — runs on the daemon's thread, and the engine yields after every 4 ms of evaluation, so a node with many items never holds the session frame. Where any of that data is an artifact, the node's evaluations run on a thread of their own, as a quick step does, because one native call inside JSONata over a large value cannot be cut by its timeout (`$string` over 200,000 rows took 45 to 49 ms). A regular expression runs on `re2js`, a linear-time engine, through JSONata's own `RegexEngine` option, so no pattern takes time exponential in its input; a pattern that engine cannot run — a backreference or a lookaround — is refused at save with the finding `expression_regex_unsupported`, and a program that needs one uses a Code step, whose interpreter has JavaScript's own regular expressions under the step's deadline.
- **Programs** live in the Code node and nowhere else, on the WebAssembly interpreter of §Implementation Notes, with a memory budget and a deadline. A document an agent wrote or an import carried therefore never becomes executable text on the host under either tier.

An expression's live preview in the inspector never resolves a secret: a sensitive field previews the secret's name, never its value.

### Provider-limit pacing and durable resumption (SA-40)

A provider account that has spent its usage allowance refuses work. V1 treats that refusal as a **first-class park** — neither an execution failure nor a transient to be retried — because retrying into a spent account converts one refusal into a burned retry budget and then a false `failed` verdict on work the engine never got to try.

**C-19 — recognition is typed, and only typed.** The engine recognizes a usage-limit refusal from the driver's **normalized typed signal alone**. It MUST NOT recognize one from message text, provider prose, an error string, a rate-limit window's name, or a model id. Text-matching a refusal is forbidden for the reason Spec-004 gives for the driver boundary generally: prose is not a contract, it changes without a version bump, and a matcher that silently stops matching turns a park into a burned retry ladder with no signal that anything changed.

Three facts about the driver surface fix what "typed" means here.

- **The precedent for typed recognition.** [Spec-004 §Fallback Behavior](004-provider-driver-contract-and-capabilities.md#fallback-behavior) establishes the class: recovery conditions form the `RecoveryCondition` set, whose `reauth-required` member is detected "mid-run via the provider's typed auth-failure signals", never by reading a message. A usage-limit refusal is the same class of fact — a provider-account state the driver observes and normalizes — and is recognized the same way.
- **The stamping discipline the carrier must follow, which is not the same as the field it stamps.** [Spec-004 §Interfaces And Contracts](004-provider-driver-contract-and-capabilities.md#interfaces-and-contracts) binds normalization at the driver boundary: the driver stamps `windowSource` (`provider_reported | model_default | estimated`) and computes the `exceeded` headroom predicate at normalization, "never deferring provenance or the derived predicate to consumers." This spec adopts that **discipline** — provenance is stamped where the fact is normalized, never inferred by a consumer — and deliberately does **not** reuse that field. `windowSource` is the provenance of a **context-window headroom** reading ([Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry)); a spent usage allowance is a different fact, and a context-window provenance stamp says nothing about whether a quota reset boundary is real.
- **The carrier is Spec-004's to declare, not this spec's.** `RecoveryCondition` carries only `recovery-needed | reauth-required` and names no spent allowance. Spec-015 therefore **requires** the signal and states what it must carry — a typed cause identifying the refusal as a spent usage allowance, and, where the provider reported one, a reset boundary carrying its own provenance stamp on the `windowSource` model — while leaving the type's name and declaration site to Spec-004 and Plan-004, which own the driver vocabulary (one-writer). The shape must be a **sibling axis, not a widening of `RecoveryCondition`**: [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) keeps `RecoverySpanClassification` beside `RecoveryCondition` for the same reason: the two axes answer different questions, and conflating them would misroute what a person must fix. A usage-limit park needs no one to act at all, so folding it into a set whose every member means _a human must act_ would misroute all of them.

**What the engine deliberately does not consume.** The account-plane `usage.rate_limit_update` snapshot — payload `{provider, providerAccountId, credentialGeneration, limitId?, windowMins, usedPercent, resetsAt?}`, keyed `(providerAccountId, limitId)` — is the nearest existing surface and is **not** an input to any rule in this section. [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) scopes it to display and quota only, kept out of security and admission decisions; its `resetsAt` carries no provenance stamp; and its own consumer obligations are staleness defenses that resolve **fail-open to the freshest reading**. Arming an execution schedule off a display surface that is licensed to be stale and stamps no provenance would be precisely the guess the arming rule below refuses to make. It stays what it is: a quota display.

**Spec-004 mints the carrier.** The typed provider usage-limit signal this section depends on is minted at [Spec-004 §Fallback Behavior](004-provider-driver-contract-and-capabilities.md#fallback-behavior) as a sibling axis beside `RecoveryCondition` — typed-only recognition, an enumerated cause, an optional provenance-stamped reset boundary. The prohibition stands alongside it: a provider or shape the driver cannot name emits no signal, that silence means _not known to be limited_ rather than _known not to be limited_, and it is never closed by reading message text. The reads the carrier rides are fixed at [Spec-004 §Default Behavior](004-provider-driver-contract-and-capabilities.md#default-behavior): at daemon start and on its triggers, with no timer, and a provider's push taken live where it arrives (the Codex `account/rateLimits/updated` push beside the `account/rateLimits/read` pull); correctness here does not depend on the push.

**A recognized refusal parks immediately, and spends no ladder.** The step suspends on the refusal itself. The park:

- consumes **no** `max_retries` attempt and mints **no** new `stepRunId` — a park is not an attempt, and the resumed turn is the same attempt continuing;
- starts **no** run and adds nothing to its chain's count — a park is not a start;
- happens **even when no reset window was reported**. A missing window changes only whether a schedule is armed (below); it never changes whether the run parks, and it never licenses one more attempt "to see". The refusal is itself the proof.

`max_duration` is the one bound a park does not stop: SA-2 defines it as workflow-run **wall-clock**, and a park is elapsed time. The deadline therefore stays authoritative over every rule below.

**A durable resume schedule, armed only where a boundary is real.** Where the typed refusal carries a reset boundary whose own provenance the driver stamped **provider-reported**, the engine arms `resumeAt` — a **durable value on the parked step's persisted state, never an in-memory timeout** — and the run resumes itself when the window opens. The value is per-step, not per-run: parallel branches of one run may park concurrently against different provider accounts with different reset boundaries (§Graph model — nodes, ports, and edges (SA-32)), and a single run-level schedule could hold only one of them — delaying or stranding the sibling. Where that provenance is the driver's default or its estimate, or where no boundary was reported at all, **no schedule is armed**: those values are the driver's honest admission that the number is a guess, and scheduling against a guess either fires into a still-spent account or holds a run that could have run. The gate is Spec-005's: [Spec-005 §Usage Telemetry](005-session-event-taxonomy-and-audit-log.md#usage-telemetry-usage_telemetry) sets the rule: estimated- and default-grade readings drive only reversible, soft responses, while "any costly or irreversible action keyed on headroom" requires provider-reported provenance. Holding a run asleep against a wall-clock instant is such an action. A parked run with no schedule is a normal, fully-visible, fully-resumable park — not a stuck one (§Park integrity and cancelability (SA-42)).

The schedule obeys five rules:

1. **Jitter is derived and scaled, never modular.** The armed instant is the reported boundary plus a jitter offset spanning a bounded window (V1: 0–120 seconds), computed by **scaling** a fixed-width prefix of the run's own derived digest across that span — `offset = span × prefix / 2^width` — so a wave of runs parked by one outage does not resume in a thundering herd. A modulus is forbidden: when the span exceeds the operand's range the modulus never wraps, so the spread silently collapses to a fraction of its declared width while every bound assertion still passes. The offset is a pure function of `workflowRunId`, so §Deterministic identity (SA-21) replay reproduces the same instant and the projection rebuild reconstructs the same row.
2. **The armed instant — and the park's attention key, where one was computed — are carried by the suspension event.** The engine writes both into the event payload before it is projected, so the durable columns are a function of the log and §Truth vs projection vs ephemeral (SA-25)'s rebuild-from-events rule holds without a special case.
3. **The deadline wins.** A schedule that would fall at or after the run's `max_duration` deadline is **not armed at all**; the run parks unscheduled and hard-fails at its deadline with `failure_reason` preserved, per §Fallback Behavior. The boot sweep applies the same rule, so a restart never resurrects a run past its deadline.
4. **Restart re-arms; it never fires inline.** On daemon start the sweep re-arms every schedule from its durable row **after** projection rebuild completes, and a past-due instant is re-armed at a short bounded delay rather than fired during rebuild — a timer that races the rebuild is deciding what the run is while the answer is still being computed. A durable value the sweep cannot decode is **quarantined, never fatal**: the run is left parked and unscheduled — a normal, fully resumable state — and the undecodable value is recorded in §Engine event record (SA-43) rather than raised as a wiring error. An engine that refuses to boot, or that parks every run at a configuration fault, because one row it wrote itself is no longer decodable has converted a single bad row into a total outage.
5. **Every exit clears it.** Every transition out of the park — the step resuming, or the run being canceled, failing, or completing — clears the parked step's durable value and any armed timer, in the same unit of work as the transition. A cleared schedule is unarmed, not merely ignored.

**Firing re-checks, and an early resume is safe.** When the schedule fires, the engine re-checks that the run is still parked and still resumable, then makes a **real provider attempt**. If the account is still limited, the attempt receives another typed refusal and the run re-parks honestly against whatever boundary is now in force. Resuming too early therefore costs exactly one refused attempt and converges on the true unblock; it can never leave a run unrunnable.

**A fire that does not move the run is not an exit.** Rule 5's clear is keyed on the run _transitioning out of the park_, not on the timer having fired. Where a fire re-checks and then fails to transition the run — the engine is shutting down, the step cannot be re-dispatched yet, the write loses a race — the durable value **stays armed** and re-arms at a bounded delay. Clearing on a fire that did not move the run is the worst available outcome: the run is left parked with its only route forward deleted, and nothing has recorded that it is stranded.

**One attention record per outage, and it is never an availability lock.** A single spent account can refuse many concurrently running workflows at once. Each affected run parks independently, on its own state, with its own cause — but the engine stamps each park with an **attention key** identifying the outage rather than the run: the provider, the account identity, and the credential generation held stable across the refusing dispatch. Runs sharing an attention key present as **one** attention record, so a wide refusal storm surfaces once rather than once per run. Three constraints keep this a fold rather than a mechanism:

- **A mixed failure is never folded.** A set of concurrently failed siblings collapses into one usage-limit attention record only if every one of them carries the same non-null attention key. Folding a genuine non-usage failure behind a familiar outage would make the only record the person sees actively misleading — the "protection that isn't" class §Loud-errors discipline (C-12) forbids.
- **The record never gates anything.** Starting, resuming, retrying, and firing a schedule MUST NOT consult it, and it MUST NOT interrupt work already running. It is a correlation for presentation, not a lock on availability: a credential rotation or a quiet reset must never be able to leave a run unstartable because a record says an account was once spent. Any transition back to running invalidates a not-yet-surfaced record for that key, so a later refusal surfaces again rather than being suppressed by a stale one.
- **The fold fails open, and only toward more noise.** Where the correlation cannot be computed — the key is unavailable, the read fails, the account identity is ambiguous — the affected run surfaces **its own** attention record rather than none, and the refusal never reverts to a retry. Duplicated notifications are a cost. A refusal quietly rehabilitated into one more attempt against a spent account, or a park nobody is told about, are failures — so the only direction the fold is permitted to fail in is the loud one.

No attention state crosses from one run to another: there is no per-watcher generation, claim or delivery record, and no campaign-scoped carry-over between separate runs (§Non-Goals). The only values one run leaves the next are the ones a `Set variables` step keeps with `Keep for later runs`, off by default: on, the values the step writes are also kept for the workflow when the step succeeds, one entry per name, replacing that name's earlier value, and a later run reads them through `$vars` (§Expressions). A kept value is at most 64 KiB, and a larger one fails the step with `workflow.kept_value_too_large`, carrying the name and the size. Kept values belong to the workflow, not to a version: saving, restoring or duplicating a version leaves them, a duplicate starts with none, deleting the workflow deletes them, and `Clear kept values` (`workflow.keptVarsClear`) clears them after asking once and naming what goes.

### Frozen-definition repair (SA-41)

§Fallback Behavior freezes a running instance on the version it started with, which is correct and load-bearing for replay — and which means a run parked against a defect in its own frozen definition has no route forward: the definition has been fixed, the run cannot see the fix, and the only remaining action is to abandon it and lose every completed step output.

V1 therefore provides one governed repair: **the person resuming a parked run may re-pin it to the definition's current version**, as an explicit, separately-requested action on the resume. The repair is bounded by six rules:

- **Explicit, never implicit.** Re-pinning happens only when the person resuming asks for it by name. An ordinary resume always continues on the pinned version, unchanged. No timer, no schedule, no automatic recovery path ever re-pins — auto-resumption (SA-40) resumes the frozen version and nothing else.
- **Only while parked.** A running instance is never re-pinned. The frozen-version rule of §Fallback Behavior is unconditional for a run that is executing.
- **Only where no attempt of the run is in flight.** Parked is necessary but not sufficient. A re-pin takes effect only where the resume's next act is to **enter a step fresh** — and, because the pin is run-level, only where **no other non-terminal step of the run holds an in-flight attempt either**: parallel branches park independently (§Graph model — nodes, ports, and edges (SA-32)), and a parked sibling mid-attempt will continue that attempt later, so a re-pin admitted through one branch's fresh entry would still swap the definition under the sibling's already-dispatched work. Requested on a park whose resume **continues an in-flight attempt**, or while any parked sibling holds one, it is refused, loudly and typed, naming the blocking attempt and the explicit fresh-entry action that would discard it. The arms are **one refusal point, not two**: the predicate is single — _some attempt of the run is still in flight_ — evaluated run-wide, and which step holds the attempt changes what the refusal names, never what it is, the same one-failure treatment the version-accountability rule below gives its detection arms. The usage-limit park of §Provider-limit pacing and durable resumption (SA-40) is exactly the in-flight case by construction — it mints no new `stepRunId` and its resumed turn is the same attempt continuing — so a bare re-pin there is always refused. Swapping the definition under an attempt whose work was already dispatched from the frozen bytes is incoherent rather than merely risky: the in-flight units were launched from a version the run would no longer be pinned to, so neither those units' inputs nor the outputs they return could be explained by the version the run's own record names. Refusing is the honest form of the boundary — quietly continuing on the frozen version would repair nothing while reporting success, and quietly re-pinning mid-attempt is the unreadable-history failure the audit rule below forbids. And the failure mode is concrete: a person who fixes a parked step's prompt and resumes expects the fix to have taken effect — absent this explicit boundary, the run re-renders the frozen prompt into an identical park with nothing telling them why, as many times as they retry.
- **Audited, in the log.** The repair is recorded as an optional member on the `workflow.resumed` payload naming the version the run left and the version it joined — an additive MINOR change under [ADR-018](../decisions/018-cross-version-compatibility.md). No new event type is minted, and the projected run row stays a function of the log per §Truth vs projection vs ephemeral (SA-25). A silent re-pin is forbidden outright: it would make a run's own history unreadable, since the definition its early steps executed would no longer be recoverable from the run.
- **Completed work is preserved, never re-run.** Step outputs are immutable (SA-16) and a repair rewrites none of them. The repair mints no new attempt for a completed step and resets no counter — `max_retries`, the chain's count, and the `max_duration` deadline all carry over exactly as they stood.
- **Refused when it would strand the run's own record.** The re-pin is refused, loudly and typed, when the target version does not contain every node id whose outputs the run already holds, or when the target version's declared topology would leave a completed step unreachable. Both are the same failure: a run whose record names steps its definition no longer contains cannot be replayed, verified, or explained. Refusal leaves the run parked and unchanged, on its original pinned version.

### Park integrity and cancelability (SA-42)

Two properties make a park a state the person can act on rather than a hole a run falls into.

**Every park carries a bounded, engine-authored cause.** A suspended step records a typed `parkReason` and a human-readable `parkCause`:

- `parkReason` is `waiting-human` (the §Session timeline surfacing value) or `provider-usage-limited` (SA-40), and the daemon refuses any other value.
- `parkCause` is the engine's own sentence about why this run is waiting and, where a schedule is armed, **the instant it holds** — so the time named in the cause and the time in the durable schedule are one value read from one place, not two values that can drift.
- The cause is **bounded at 8 KiB, truncated at a UTF-8 code-point boundary with a visible truncation marker**. A durable, person-facing, engine-authored string with no bound is an unbounded write on the projection tier.
- All four park fields — the two record fields here and SA-40's armed instant and attention key — are carried by the suspension event's payload and projected from it, so §Truth vs projection vs ephemeral (SA-25)'s byte-equal rebuild holds.
- The cause is **never** written into a step output, an artifact, or an agent-visible context. Engine prose delivered through a model-output channel is read as something a model said, which makes the engine's own diagnosis indistinguishable from generated content — and step outputs are immutable truth (SA-16), so an engine sentence written there is unretractable.

**A parked run is always cancelable.** Cancellation is a legal transition into the `canceled` run status from **every** suspended or waiting state, without precondition and without waiting for anything:

- It is **pure bookkeeping and therefore cannot block**. A parked run holds no resource-pool reservation (pool state is ephemeral and re-requested — §Truth vs projection vs ephemeral (SA-25)) and no live step process, so there is nothing to drain, interrupt, or wait on. A cancel that could be refused, queued, or made to wait for a provider window would reintroduce exactly the stuck state this rule exists to remove.
- It **clears the durable resume schedule** in the same unit of work, so a canceled run can never be resurrected by a timer armed before it was canceled.
- It **preserves the record**. The parked step row's state, its `parkReason`, its `parkCause`, and every completed step output survive cancellation untouched — they are the account of why a human was asked and what the run had achieved, and losing them at cancel would make canceling the operation that destroys the evidence. The step's **live** fields — the armed instant and the attention key — are instead cleared by the same cancel per SA-40 rule 5: record and live state sit on one row and part ways at exactly this boundary.

**The operator control surface is §Operator run control (SA-45)**, and §Park surfacing on the read model (SA-44) is what makes the state it acts on legible. Its operation set and the run-canceled lifecycle event mint **together**, because a durable cancellation the log cannot reconstruct would break §Truth vs projection vs ephemeral (SA-25) — a projection rebuild would replay the last `workflow.phase_suspended` payload, restore its schedule and attention key, and resurrect a run the person canceled. The auto-resume path of SA-40 needs no wire producer of its own: it is engine-internal.

### Park surfacing on the read model (SA-44)

A parked step MUST be renderable from **one** `workflow.runRead` response — no timeline replay, no second call, no client-side reconstruction from event history. The park is the state the person is most likely to be looking at and least able to explain from a status word alone, so the read model carries its reason rather than deferring to the log.

- **Additive-optional members.** `WorkflowStep` carries `parkReason`, `parkCause`, `resumeAt`, and `parkAttentionKey`, mirroring the per-step park columns. All of them are optional, an additive MINOR change under [ADR-018](../decisions/018-cross-version-compatibility.md): readers MUST tolerate their absence.
- **Live, not record — the rule that makes them readable.** The projection **columns** are a durable record that survives resume and cancellation (SA-42's preserve-the-record rule depends on exactly that). The wire **members** are a live view of it: a daemon emits them for precisely those steps parked at the moment the response is built, and emits none of them for a step that is not — including a step that parked earlier in the run and has since resumed, whose columns still hold the record. The wire therefore gives a stronger guarantee than the columns do, deliberately.
- **`parkReason` is the wire discriminator.** Because emission is live-scoped, its presence means _this step is parked now_ and its absence means _it is not_. `parkCause` is present whenever `parkReason` is — SA-42 requires a parked step to always carry one. `resumeAt` and `parkAttentionKey` are present only where the park armed them (an SA-40 park whose provider reported a reset boundary); their absence **narrows** the park to the unscheduled kind a person resumes rather than denying it.
- **The step status list is not widened for a park.** `WorkflowStep.status` is the step-status list of §Execution semantics: a parked step reads `waiting` with its wait cause, and the park members add why and until when. This is the reason the liveness rule is required rather than convenient: a reader given only column mirrors could not separate a step still parked from one that already resumed past that park.
- **Per-step, never per-run.** SA-32 branches park independently against different provider accounts, so a run-level park field could hold only one of them. `WorkflowRunReadResponse` grows no park member of its own; the run's `waiting` status says _something is parked_ and the step states say _what and why_.
- **No new disclosure.** `parkCause` is engine-authored, bounded by SA-42's 8 KiB cause bound, and reaches no step output, artifact, or agent-visible context. Surfacing it on a read the caller is already entitled to make adds no recipient.
- **Accepted consequence: a finished run shows no park members.** The liveness rule is exhaustive, so a run that resumed, succeeded, failed, or was canceled emits no park member on any step — including a step whose `park_reason` and `park_cause` columns still hold the record SA-42 deliberately preserves. This is intended, not an oversight: the wire members answer _why is this parked now_, and asking _why was this parked once_ is a history question the timeline answers, since every park emitted `workflow.phase_suspended` carrying the same cause. A canceled run additionally carries its cancellation reason on `failureReason`. A park member always means _parked now_, never _parked once_: a member that sometimes means _now_ and sometimes means _once_ is the ambiguity this rule exists to remove.

### Operator run control (SA-45)

The engine rules of SA-40 through SA-42 are reachable over the wire through exactly two operations. Both are operator actions on a run, both are authorized as named Cedar operation actions, and both refuse through registered codes.

- **Two operations over one run, not three.** `workflow.runCancel` cancels a run. `workflow.runResume` resumes a parked run and carries the SA-41 re-pin as an **optional member of the resume request**, not as an operation of its own — SA-41 defines the repair only as an action on a resume, so a separate operation would admit the re-pin-without-resume shape that section refuses. Fixing a failed step in a fresh session is not a third one either: it opens a session and changes nothing about the run (§Workflow Timeline Integration).
- **Cancel and its event mint together.** A run reaches the `canceled` status durably only by appending `workflow.canceled` in the **same unit of work** as the status write. This is not a logging convention: without it a projection rebuild would replay the last `workflow.phase_suspended` payload and resurrect a run the person canceled (SA-25). `workflow.canceled` is a member of the `workflow_lifecycle` category, and its payload carries the supplied `reason`, bounded exactly as `parkCause` is.
- **`workflow.canceled` clears the live park fields of the whole run — a projector rule, not only an engine rule.** On applying `workflow.canceled` the projector sets `park_reason`, `park_cause`, `resume_at`, and `park_attention_key` to `NULL` on **every** step row of that run, and does so from the event alone. Stating this only as an engine rule would leave the invariant unverifiable against the artifact it quantifies over: a rebuild that replays `workflow.phase_suspended` and then a `workflow.canceled` carrying nothing but a reason has no other instruction that would clear what the suspension set, so the rebuilt row would carry an armed schedule for a run that is over. The rule is deliberately **run-scoped and unconditional** rather than payload-enumerated — a workflow with parallel branches can hold several parked steps at once, and a payload that listed them would have to enumerate them correctly to stay byte-equal, adding a way to be wrong for no gain. Every step of a canceled run is unparked by construction, so clearing all of them is the same write as clearing the right ones.
- **Cancel is unconditional on a parked run, idempotent on a canceled one, and refused on a finished one.** SA-42's without-precondition rule is unchanged and is why no code names a refused cancellation of a parked run. A second cancel of an already-`canceled` run replays the original event's identity rather than writing again — a retried operator action must not cost a clear answer. A cancel against a run that reached `succeeded` or `failed` refuses `workflow.run_not_cancelable`, because answering "canceled" for a run that ran to completion would misinform the person about what their action did.
- **Resume requires a park, and does not require the schedule to have elapsed.** A resume against an unparked run refuses `workflow.resume_not_parked` — distinct from `workflow.repair_not_parked`, which refuses the re-pin leg, so the person can tell whether dropping the re-pin would have worked. Resuming **ahead of** an armed `resumeAt` is permitted and needs no override flag: the armed instant is advisory pacing derived from what a provider reported, and the worst outcome is that the account is still spent and the step re-parks, emitting its own `workflow.phase_suspended`. That re-park is a legal response, not a refusal, and is visible in the timeline and on the next read.
- **Authorization is a named operation action, not an approval category.** `workflow.runCancel` adjudicates `Action::"workflow::cancel"` and `workflow.runResume` adjudicates `Action::"workflow::resume"`, each on the target workflow run, through the same `PermissionCheckService` seam SA-39 uses for `Action::"workflow::start"`. They are **separate actions from start and from each other**: start creates work, cancel destroys it, and resume commits further spend against a provider account — one action covering all three would make "may start a workflow" silently mean "may cancel a run already committing spend". A denial refuses `workflow.control_denied`, naming which action was denied, since the two are separately grantable. Both actions sit beside `Action::"workflow::start"` in [Spec-010 §Implementation Notes](./010-approvals-permissions-and-trust-boundaries.md#implementation-notes)' named-operation-action enumeration, which Plan-010 registers; this spec consumes the adjudication and authors no Cedar schema entry.
- **Refusals are total.** Every refusal above leaves run status, step rows, armed schedules, and step outputs byte-identical to their pre-request state. Resolution and validation complete before any write.

Every run has one address inside the window, `#/workflows/runs/<runId>` under `#/workflows/runs` under `#/workflows`, and one outside it, `sidekicks://workflow-run/<runId>`, which the OS notification's click, `Open run` on a chat row and a fix session's footer link all use; an unknown id opens the run list with one line, `That run is not here.`; the address carries no step segment and nothing about it is persisted ([Spec-021 §Main Process Responsibilities](./021-desktop-app-and-renderer.md#main-process-responsibilities)).

**A third operation addresses no run at all: the hold on starting.** One switch, **Pause new runs**, holds every new start — a schedule fire, a webhook, a file event, a chat verb, an agent's own run tool and Run now alike, because it is a hold on starting and not a filter on triggers — while a run already going finishes untouched. The switch's own words carry the count of what is waiting, `Pause new runs · 3 waiting`, and switching it off starts what waited, in the order it arrived. The hold is one state per daemon over its whole scheduler, not a property of a workflow: the enabled toggle arms and disarms one workflow's triggers and stays that way until someone changes it back, while this holds every workflow's starts at once and is meant to be switched back the same minute. One method sets the hold and answers with how many starts are waiting, and the hold and its count also ride the run subscription, so every open surface reads one truth rather than its own guess.

**The queue of runs that need a person is walked, not hunted for.** One control, **Next waiting (N)**, opens the next run that is waiting on a person, and pressing it again once that one is dealt with opens the one after it. It takes them from the top of the list down, so the walk and the table agree about which one is next, and the filters above the list never narrow it, because it is the queue of what needs the person rather than a view of the table. N reads how many such runs there are other than the one open, so from the list it reads the whole queue and from a run's own page it reads how many others are still owed an answer. A run waiting on an account rather than on a person — parked on a spent provider account, with its own resume instant — is never in it, because nobody can answer that one. With none left the control stays in place, disabled, reading `Nothing waiting`, rather than disappearing: a control that comes and goes as runs arrive moves everything beside it under the pointer just as someone reaches for it.

**A run has four acts and each keeps its place.** `Re-run`, `Cancel` and `Resume` stand in the run's header and `Retry from this step` in a step's own panel. Each keeps its place whatever state the run is in, and a state that does not allow it refuses in words that say why rather than the control quietly not being there. Cancel is available on a `new`, `running` or `waiting` run, refuses on a terminal one with a reason, and replays idempotently on an already-canceled one; canceling a run cancels every sibling branch it still has running (§Execution semantics). Resume is available on a parked run; retry-from-step re-runs that step and its descendants with the prior run's data pinned upstream. `Delete run` on a `new`, `running` or `waiting` run is refused in place with `Cancel it first.` (`workflow.run_not_deletable`). The builder carries the same acts where the author is looking: its one run control reads `Run now` at rest and `Cancel` while the run it started is live — the same outline style, no stop glyph and no red — and the announcement reads `Run canceled`. A workflow run is canceled, never interrupted, because nothing steers it, and one word covers the act wherever it is taken.

### Loud-errors discipline (C-12)

- Unknown integration name, missing required input, typo in expression, unknown node reference, unknown resource pool, unknown approver principal — all must fail loudly at `WorkflowDefinitionCreate` or at step launch. Silent no-ops forbidden by default. n8n 1.0 had to break silent-error-passing behavior users had built on; failing loudly from the first release leaves no such behavior to break.
- Workflow step outputs referenced by downstream nodes must resolve at definition time (by shape) and at execution time (by presence). Missing-output is never silently coerced to empty string.

**One spelling of failure per node.** A node carries `onError` with exactly three dispositions — `stop`, `continue`, `continue-error-output` — the third materializing a real `error` output handle the failed items route to. Beside it sits `retry { maxTries, waitMs }`, and the engine clamps both: the clamps are the engine's and are never trusted from the document, because anything user-editable that costs money needs its bound held somewhere the author cannot edit. There is no second error setting and no `continueOnFail`. An error may also ride a single item, so one item of a batch can fail while the rest succeed.

**One spelling of failure per run.** A run observes cooperative cancellation through an abort signal every executor can see, obeys the optional run cap of §Execution semantics, and can be failed on purpose by a stop-with-error node, so a deliberate failure is a visible element of the graph rather than a hidden setting. Every failure lands in the session event log and on the node itself; the error trigger that fires when another workflow fails is sugar on top of that record, never the primary channel.

**Advisories are not errors.** A step may attach non-fatal hints — an unwired branch that dropped items, a deprecated param, a truncated output — and they render as a strip above the step's output rather than as a failure, so the one red treatment keeps meaning one thing.

## Default Behavior

- A node runs when all its `main` inputs are settled, and siblings start in their explicit `order`; branches run in parallel as the memory gate admits them. A join is a `flow.merge` node, whose mode is set on the node; no other node carries a join policy.
- Each `agent.run` step starts one primary producing run, in the run's session.
- An `agent.multi-agent` step runs a lead and its helpers in the run's session through the orchestration path (§Agent steps (SA-6, SA-8, SA-9)). When its run ends failed or canceled, the lead and its helpers are canceled with every other running branch (§Execution semantics).
- Workflow definitions default to immutable-by-version: editing a workflow creates a new version rather than mutating a running definition in place.
- Workflow definition reads default to the canonical persisted definition record for the requested scope and version rather than to an artifact manifest.
- A `human.form` step's fields default to primitive-type JSON schema fields (`text` / `long_text` / `number` / `integer` / `boolean` / `enum` / `path`). A form has no artifact field and no in-form upload: a location is a `path` field, which the person fills through the platform's own file chooser (SA-10).

## Fallback Behavior

- If a step needs a capability that is unavailable when it runs, it fails with its typed error and its node's `onError` decides what follows; a step is never silently skipped, and a run has no blocked state.
- If a workflow definition changes while an older version is running, the running instance must continue on the version it started with.
- If a step output is large or unavailable inline, the workflow timeline must link to a durable artifact reference instead of dropping the output.
- If the provider's sandbox cannot start for a full-tier Code node or a `developer.shell` node while the run's posture is `sandboxed`, the step refuses with `workflow.sandbox_unavailable`, carrying `provider: claude-code | codex` and `detail`, the wrapper's own error; the node says so, and the run takes the node's own error disposition from there. It never falls back to running the program unsandboxed, and no looser posture is substituted for the one the run holds (I2). On Linux both sandboxes need unprivileged user namespaces, and Claude Code's also needs the system `bwrap`, `socat` and `ripgrep`; Debian 11 and later allow them. Ubuntu 24.04 allows them too, but on a desktop install AppArmor strips every capability inside a namespace made by a program with no profile of its own (`kernel.apparmor_restrict_unprivileged_userns = 1`, set at boot by the `apparmor` package every desktop install brings), and no profile Ubuntu loads names `/usr/bin/bwrap` or Codex's own `bwrap`. Lifting it takes root — a sysctl file that sets the value to 0, a profile granting `userns` to the exact program path, or enabling the one `bwrap` profile, which ships disabled in the optional `apparmor-profiles` package — so until the person does one of them, such a step refuses there.
- If a step's sensitive field names a secret the keychain does not hold, the step fails with `workflow.secret_not_found`, which carries only `reference`, reading `The secret project/github-read is not on this machine.` over `Add it in the step's Credential field, then press Retry from this step.` If the keychain is locked or unavailable, the step fails with `workflow.secret_store_unavailable`, carrying `cause: locked | unavailable`, names the cause and offers `Retry from this step`. The step never waits on the keychain indefinitely and never falls back to a plaintext value ([ADR-038](../decisions/038-workflow-secrets-in-the-os-keychain.md)).
- If a full-tier Code step names a package that does not resolve, names one package at two versions in two imports, or is saved with no network, the save is refused on that node with `workflow.definition_refused` and one `code_packages_unresolved` finding whose `detail` is `bun`'s or `uv`'s own error naming the package; the validation strip lists it and the draft is kept.
- If a full-tier Code step's install cannot finish, the step fails with `workflow.code_install_failed`. Below 1 GiB free on the volume that holds the code folder the install does not start, and a no-space error from `bun` or `uv` stops it and removes the partly written folder; both carry `reason: disk_space` and read `Not enough disk space to install this step's packages: 640 MB free. Free up space or clear the package caches in Settings › Runtime, then retry.` The daemon never clears a package cache to make room. Any other install error, a lock that no longer matches its step included, carries `reason: tool_error` and `detail`, `bun`'s or `uv`'s own error.
- If the machine has no room for any ready step's reservation, one step is admitted anyway and the rest keep waiting, each carrying `workflow.phase_waiting_on_pool` and reading `Waiting for memory` where its node is drawn — waiting is the engine's answer to memory pressure, never a refusal.
- If one form is open in two windows or on two devices, a submit carrying a stale form revision refuses with `workflow.revision_stale` and the form reloads its saved draft; an answer that arrives after the step stopped waiting — answered elsewhere, or past its `Timeout` — refuses with `workflow.step_not_waiting` (SA-10).
- If a set `max_duration` fires mid-run, the run ends as `failed · timed out` (`workflow.step_timed_out`, cause `run_cap`) with `failure_reason` preserved; all completed step outputs remain addressable. A set `max_duration` continues to elapse while a run is parked on a provider account (SA-2 measures wall-clock), so a parked run reaching its deadline fails there rather than resuming — and no resume schedule is ever armed past it (§Provider-limit pacing and durable resumption (SA-40)). A chain that reaches its count does not fail: its next start waits for the person's answer (§Entry node and the V1 trigger surface (SA-37)).
- If a provider refuses a step's work with a typed usage-limit signal, the step parks rather than failing and rather than retrying: the retry ladder is not entered, no attempt is consumed, and the run stays fully visible and resumable with a stated cause (§Provider-limit pacing and durable resumption (SA-40); §Park integrity and cancelability (SA-42)). A refusal carrying no provider-reported reset boundary parks with no schedule — an unscheduled park, never a silent one. The Runs tab renders it as parked with its cause and, where one is armed, the instant it will resume itself; a park with no armed instant renders as awaiting resume rather than inventing a time, and the resume then happens without the user acting.
- If a resume — scheduled or asked for by the person — reaches a provider that is still refusing, the run re-parks against the boundary now in force rather than failing or looping. An early resume costs exactly one refused attempt.
- If a parked run's frozen definition is the reason it is parked, the person may resume it onto the definition's current version as an explicit, audited re-pin at a resume that **enters a step fresh**, which the engine refuses in each of these cases — a run that is not parked at all, a target version that cannot account for the steps the run has already completed, and a repair requested while any of the run's attempts is still in flight — the resuming step continuing one, or a parked parallel sibling holding one (§Frozen-definition repair (SA-41)). Absent that request, the run resumes on its pinned version unchanged.

**Refusals the builder can compute locally land in the validation strip**, one row each, each clicking through to the node it names: a cycle, an orphan node, a document with no nodes, a missing or duplicate trigger, an edge into the trigger, a terminal node with an outgoing edge, a missing required param, an expression that does not parse, an expression naming a node that no longer exists, and a capability edge into a node that has no capability input.

**A refusal from the daemon is rendered on the nodes it names** and leaves the draft editable. The registered codes are used as they stand — the definition-not-found and gate-closed codes; the start-denied code for a denied or unresolvable start and for a session the starter cannot see; the control-denied, not-cancelable and not-parked codes for the operator controls; and the re-pin codes for a repair the run's state forbids. Every other refusal point carries its own code in the registry's `<root>.<noun>_<condition>` form, and none ships unregistered (§Loud-errors discipline (C-12)). A state refusal is 409, well-formed input the daemon cannot act on is 422, and findings ride the error as an extension list:

- `workflow.definition_refused` (422) carries `findings: [{rule, nodeIds, detail?}]`, the whole list, for a document the daemon's re-check refuses; `detail` is set only on `code_packages_unresolved`, where it is `bun`'s or `uv`'s own error naming the package. The finding rules are `cycle`, `orphan`, `empty_document`, `trigger_missing`, `trigger_duplicate`, `edge_into_trigger`, `edge_out_of_terminal`, `param_missing`, `expression_unparsable`, `expression_unknown_node`, `expression_regex_unsupported`, `tool_edge_without_tool_input`, `handle_type_unknown`, `content_hash_mismatch`, `scope_ref_invalid`, `governance_inline`, `unknown_key`, `secret_outside_sensitive_field` and `code_packages_unresolved`.
- `workflow.operator_required` (403) for `shared` saved by a principal that is not the node owner; `workflow.revision_stale` (409) for a stale form revision; `workflow.version_stale` (409) for a stale definition version; `workflow.step_not_waiting` (409) for a form submitted, an approval answered or a form read on a step no longer waiting; `workflow.retry_unavailable` (409) with `reason: step_data_expired | source_running`; `workflow.run_not_deletable` (409) for `Delete run` on a `new`, `running` or `waiting` run, reading `Cancel it first.`; and `workflow.invalid_transition` (409) for a run or step move its state does not allow, such as retrying a step that did not fail or reading results from an unfinished run.
- The engine and the listener: `workflow.trigger_unarmable` (a trigger that cannot be armed), `workflow.webhook_token_mismatch` (a webhook call with the wrong token, or any call while no token exists), `workflow.code_over_budget` (a Code node over its memory or time budget), `workflow.code_install_failed` (`reason: disk_space | tool_error`, `detail`), `workflow.expression_over_budget` (an expression evaluation over its budget) and `workflow.import_schema_unknown` (an import whose schema version is unknown).
- The step failures: `workflow.step_thread_failed` (`reason: out_of_memory | start_timeout | exited`), `workflow.sandbox_unavailable` (`provider`, `detail`), `workflow.step_timed_out` (`cause: step_timeout | run_cap` and the limit, reading `failed · timed out`) and `workflow.kept_value_too_large` (the name and the size). Each rides the step's `error` on its row and the `workflow.step_failed` event, for the life of the run record.
- The secrets: `workflow.secret_not_found` (`reference`), `workflow.secret_store_unavailable` (`cause: locked | unavailable`) and `workflow.secret_name_invalid` (`reason: pattern | taken`); the first two fail the step and offer `Retry from this step`.

**A failed step is legible where it failed.** The node carries the first line of its error and its failing item index, the run's status is `failed`, and the run's detail opens on that step's error. A step whose node routes its failed items to an error handle instead continues the run down that branch.

**A missed fire is one of two things and the run says which.** A schedule whose fire was missed because the daemon was down either skips the occurrence or catches up exactly once, per that schedule's own policy, and the run's trigger record records which happened.

**Until a method is live on the wire it is a build gap.** No client refuses on its behalf, and a control whose method is not live is absent, not disabled, under the console's standing rule and its named exceptions ([Spec-021 §Rules every console surface obeys](./021-desktop-app-and-renderer.md#rules-every-console-surface-obeys)).

**How the agent tools reach a provider.** The agent tools (§Chat-Invoked Start and Start Authorization) reach both providers on one MCP server per session: a `url` entry on the daemon's tool route, carrying the route's own secret and admitted from this machine only. The entry starts no process per conversation.

- On Codex the entry carries `default_tools_approval_mode = "approve"`, so the daemon applies each tool's Cedar action and the session's level itself, and a `tool_timeout_sec` above the longest bounded wait; every fork re-passes it. A helper Codex spawns inherits the entry; `-c mcp_servers={}` and `-c plugins={}` do not clear an account home's own servers and plugins.
- On Claude Code the server's `timeout` sits above the longest bounded wait.
- The route answers a request's headers at once and then streams, sending progress at least every 60 s during a wait. It answers a long call with a handle that is waited on in bounded polls, and it ends its own work when Codex's tool timeout passes, because Codex sends no cancel. It answers Codex's OAuth-discovery `GET /.well-known/…` requests, a `GET` on the tool path (405) and the closing `DELETE` per session. A call is tied to its conversation by the provider's `_meta`: Codex puts `threadId` (a helper's call adds `parent_thread_id`, a fork's `forked_from_thread_id`), and Claude Code puts `claudecode/toolUseId`, which its stream ties to the helper through `parent_tool_use_id`.

**Waits.** A wait's durable `waitId` ties it to its run, its step and its session. A wait for a chat reply rides the session's own question card as `question.asked` carrying the `waitId`, answered by `question.resolve`; an approval or a form resolves through `workflow.gateResolve` or `workflow.humanFormSubmit` from whichever door the person answered at, and the first answer settles the wait at both (§Execution semantics).

**A run's execution context and snapshot points.** A run in a project session records its execution context in one `run_execution_contexts` row — the workspace, the execution mode, the root, the worktree and the repository's git common folder — and the run record references it. The daemon pins a snapshot of the run's checkout when the run starts, at each approval pause and when it ends, through the turn-snapshot service's `captureTurnSnapshot` (`packages/runtime-daemon/src/git/`), as the points `start`, `pause-<N>` and `end` under that service's one private grammar, `refs/sidekicks/runs/<id>/epoch-<E>/<point>`, with its create-only writes and ref-name checks; each re-execution opens the next epoch. The refs live inside the run's own capture folder and never in the person's repository, and each point pins the person's own commit it stood on, one ref per distinct commit under `refs/sidekicks/base/<workflowRunId>/` in the repository. The service's window-based prune never removes a run's snapshots while the run's record exists, and deleting the record deletes the capture folder and its pins. A chat run has no execution context row and no `Open in Review`. A capture fault at the start fails the run before its first step, naming the cause; a later fault fills `point_capture_error`, and `Open in Review` stays and says why it cannot open. A session that moves while a run is paused leaves the steps on the recorded root, and a step whose root is gone fails, naming the cause. A snapshot takes about 0.1 s on a 5,000-file checkout.

**One capture folder for every git capture.** Every git capture the daemon takes — a capture before and after each step it spawns or calls, a turn snapshot, a run's points — is written into its owner's own capture folder, a session's or a workflow run's, with only `GIT_INDEX_FILE` and `GIT_OBJECT_DIRECTORY` set and no alternate, and read with the repository's objects as an alternate. No capture object enters the person's `.git`, and no ref but the base pins, because a capture holds ignored files such as `.env`.

### Core SDK and persistence contracts

- `WorkflowDefinitionCreate` must persist the document and version metadata with its schema version marker (C-8). The stored body embeds the whole declared topology — the node list and the edge list (§Graph model — nodes, ports, and edges (SA-32)) — so the stored bytes are the complete executable graph and no edge lives outside them.
- `WorkflowDefinitionCreate` with target scope `shared` — direct authoring, file import, and the §Definition scope in the builder (SA-36) promotion alike, which all ride the one operation — must adjudicate the daemon's operator-scope authorization through the Plan-010 Cedar evaluation surface (`PermissionCheckService`) against the daemon-resolved node-owner user identity before any row is written, the same boundary Spec-025 §Authorization applies to governance mutations. A principal that does not resolve to the node owner is refused with a typed error, the check fails closed where that identity does not resolve, and a refusal never silently downgrades the request to a narrower scope.
- `WorkflowDefinitionRead` must return the canonical definition record and selected version metadata for the requested scope.
- `WorkflowDefinitionList` must enumerate the definitions visible to a caller, resolving scope most-specific-first — the caller's session, then its project, then the daemon's `shared` tier — and deduping on `(scope, scopeRef, contentHash)`. Enumeration is not optional polish: every other operation here addresses a definition by an id the caller must already hold, so without it a definition that is not already known cannot be reached at all, and the `session` / `project` / `shared` breadth would be unobservable.
- `WorkflowRunStart` must bind a workflow version to a session and create step execution state.
- Definition/execution entity separation: `WorkflowNodeId` names a node in the definition (static) — it is that node's id (§Graph model — nodes, ports, and edges (SA-32)), so a node and every step record of it are keyed by one string; `StepRunId` identifies one attempt of that node (with attempt number, status, timestamps). `StepRunId` is deterministically generated as `BLAKE3(workflowRunId || nodeId || attemptNumber)` (SA-21 — see State And Data Implications).
- `StepOutputList` must expose the agent and human steps' durable output summaries and artifact references; a step's full input, output or log comes only from `StepRead`.
- `WorkflowGateResolve` must resolve workflow-scoped approvals or user questions; gate resolution rows are append-only, recorded in `workflow_gate_resolutions` (§Truth vs projection vs ephemeral (SA-25)).
- See [API Payload Contracts](../architecture/contracts/api-payload-contracts.md) for typed request/response schemas.
- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

**One declarative description per node kind is the whole contract.** A kind declares its id and category, the name a person reads and the one line under it, its icon, any palette search aliases, its input and output handle specs, its param specs, the one-line summary it computes from its params, whether it executes once per item, and its capabilities — whether it is cancelable, whether it is resumable, and whether its side effects are none, local or external. That one description drives the parameter form, the canvas ports, the palette entry, the node's summary line and the validation; everything else is a generic renderer over it.

- A handle spec carries its id, its label, its type — `main` for items or `tool` for a capability — and optionally how many connections it accepts and whether it is required. A kind's output set may be a function of its params rather than a fixed list; the one kind that needs it is the switch, and the canvas re-registers a node's internals immediately after any param write that changes the set.
- A param spec carries its id, its label, its type, whether it is required, whether it is sensitive, its default, its help line, its options, and the sibling-param values under which it is shown. The type is text of one line or many, number, boolean, single or multiple choice, JSON, expression, path, glob, cron, secret, agent, an MCP tool, or a session; a collection param holds a list of nested param specs and may repeat. A sensitive param is the only place a `secret://` reference resolves: the step's Credential field and an HTTP step's auth and headers are sensitive, and a reference in any other param is refused at save (`secret_outside_sensitive_field`). `provider-account` is deliberately not a member: an account means nothing until the provider is known, and the one kind that needs both reads them from the agent it names (§Agent steps (SA-6, SA-8, SA-9)).
- The shown-when rule is the whole conditional-form engine; a param whose condition is unsatisfied is hidden, not disabled.
- An executor is one function: it takes a step context plus one array of items per input handle and returns one array of items per output handle, an empty array meaning that branch is dead.
- One registry is the only list of kinds, `workflow.kindList` serializes it, the palette renders it, and an agent reads it before authoring. A kind's version is written into the node once at insert and never migrated: a kind ships its implementations side by side and the loader resolves the exact one the document names, so a saved workflow never needs a migration pass.

### Workflow gate scope (SA-7)

Workflow gates (`WorkflowGateResolve`) share the Plan-010 approval backend with every other approval in the session. A workflow gate's scope is the run's session. There are two gate kinds, told apart by whether the resolution names a node. A `human.approval` gate is a `human.approval` step's question, and its resolution names that step's node by `nodeId`; a `chain` gate is a chain's question (§Entry node and the V1 trigger surface (SA-37)), and its resolution names no node. Each resolution is keyed by the run and carries no `stepRunId`. A form step is not a gate: its answer goes through `workflow.humanFormSubmit` and becomes the step's output. A gate's answer is a session event, `workflow.gate_resolved`, and the answering device is recorded by its id.

### Agent steps (SA-6, SA-8, SA-9)

An `agent.multi-agent` step runs a lead and its helpers in the run's session through the orchestration path, `orchestration.runCreate` ([Spec-014 §Addressing](./014-multi-agent-orchestration.md#addressing)).

- A later step reads an earlier step's output through the ordinary item bindings (`$('<label>')`, §Expressions), never through a transcript handle.
- A retry starts a new orchestration run for the new attempt and never reuses the earlier attempt's.
- Composition is state-passing, not handle-binding, which is where independent engines converged in 2025–2026: Temporal Child Workflows + Signals ([Temporal — Child Workflows](https://docs.temporal.io/develop/typescript/child-workflows)), LangGraph `Command(goto, state)` ([LangGraph multi-agent handoff](https://langchain-ai.github.io/langgraph/concepts/multi_agent/)), AutoGen `HandoffMessage` ([AutoGen Teams](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)), OpenAI Assistants API Threads removal ([OpenAI Assistants deprecation, Threads removal 2026-08-26](https://platform.openai.com/docs/assistants/migration)). Airflow SubDAG, the closest handle-binding analogue, was deprecated in 2.x because its shared-scope ambiguity took 3+ years to patch ([Airflow — Deprecate SubDags in Favor of TaskGroups, #12292](https://github.com/apache/airflow/issues/12292)).

**A step that runs an agent is a first-class run, not a thin model call.** It has a provider account, an agent definition, a posture, a tool allowlist, approvals, a cost receipt and park-and-resume, because it is the same pipeline a session's own run uses. Which agent runs it, and which account pays, are **params on the node**, never wired sub-nodes:

- The node's one chooser is the agent. It is a popover over the app-wide agent definition list the desktop keeps current from the daemon — the same list the agent library and the session composer's own `Sidekicks` group draw — and it carries one entry at the top, **General**, meaning the provider's own agent with no saved definition, with every saved agent following.
- Once General or an agent is chosen, four rows stand under it — **Provider**, **Model**, **Effort** and **Account** — prefilled from the agent's saved setup for that provider, or from the defaults for General, and each changeable for this node alone. A changed row is marked `you` and carries a reset back to the agent's value.
- Provider lists both providers. Model offers every model and every speed the provider lists, the moment it lists them, whether or not a price is known yet, and stands blank, and must be chosen, where the agent has no setup saved for that provider: a model is never guessed. Effort offers the one ladder the console uses everywhere — Minimal, Low, Medium, High, Extra high, Max — narrowed to what the chosen model publishes, reading `Not set` where the agent saved none and `Not published by this model` where the model publishes no ladder at all. Account lists that provider's accounts exactly as the accounts page lists them, each by the identity the provider itself reports at sign-in — its email, its plan in the provider's own word, and its organization where the plan carries one — with its billing chip and, on the account marked default, the `Default` chip; an account added by a pasted token or an API key, which the provider names nowhere, reads the name the person gave it beside the credential's kind (`Work · Codex API key`). One `Default` entry stands at the top of the list. No label of ours, no invented names and no computed suffixes. **The two choices are what pinning means here, and they differ when the default mark moves.** Naming a specific account **pins the step to it**: that account pays every time the step runs, and it stays where it is pinned when `Set as default` on the Providers page moves the default mark to another account ([Spec-026 §Moving a session to another account](026-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)). The `Default` entry pins nothing: the step resolves to whichever account carries the default mark when the run starts, so it follows the mark as it moves. A step never resolves to an account by guessing.
- With General chosen the same four rows show, prefilled from the defaults: Provider preselects the first provider, in the accounts page's order, that has a default account, and stands blank where none has one; Model reads that provider's default model; Effort is not set; Account reads `Default`.
- The node stores the chosen agent plus only the rows the author changed. A node whose rows all read the agent's own values stores no binding at all — except General, whose provider always travels, because no global default provider exists to fall back on — and nothing a node changes is ever written back to the agent's own definition.
- There is no second account control and no provider-accounts list on the node: the account means something only once the provider is known, and two controls setting one value can disagree.
- The chooser and the node's own rows read the definition list on every read. An agent renamed in the library shows its new name on the node at the next read, and one deleted on this machine clears the node's choice in the open draft with a one-line notice, writes nothing to the stored document until the author saves (a saved clear would mint a version and silently move the library's usage count), and never sends an id it can no longer see.
- The node's name is `Run a sidekick`, and the on-screen word for the provider is **Provider**, never driver: `driver` is the adapter's name in code, on the wire and in specs only.

### Human steps — `HumanStepConfig` (SA-10, SA-11, SA-12)

A human step is authored with the `HumanStepConfig` type, the params of the kinds that wait on a person — `human.approval`, `human.form` and `human.wait-for-chat-reply`:

```typescript
type HumanStepConfig = {
  prompt: string;
  inputSchema: JSONSchema7; // primitive-type fields; a location is a `path` field
  timeout?: Duration; // empty by default: the step waits until it is answered
};
```

- `timeout` is **empty by default**, meaning the step waits until it is answered. Set, it arms the wait's deadline: the instant is written on the step's row when the step starts waiting and is the truth, and the in-process timer is a cache over it, re-armed from the row when the daemon starts, so a deadline that passed while the daemon was stopped or the machine slept fires at once on start or wake. At the deadline the wait ends: the step fails with `workflow.step_timed_out`, cause `step_timeout`, and the node's own `onError` decides what follows — `stop` fails the run, `continue` passes the step's input on, and `continue-error-output` sends it down the error handle. The deadline is also checked when an answer arrives, so an answer after the instant is refused with `workflow.step_not_waiting` even if the timer has not run yet, and one answer or the deadline, whichever is first, settles the wait everywhere. Time a step waits never counts against the run cap.
- Three independent durable-execution engines converge on no default timeout: [Temporal Workflow Execution Timeouts](https://docs.temporal.io/encyclopedia/detecting-workflow-failures) default ∞, [Argo — Suspending Workflows](https://argo-workflows.readthedocs.io/en/latest/walk-through/suspending/) with `{}` = indefinite suspend, [Camunda 8 User Task dueDate](https://docs.camunda.io/docs/components/modeler/bpmn/user-tasks/) optional/expression-based. This is modern durable-execution convention across independent implementations — not one-camp disagreement.
- The start of a wait on a person is its one escalation (SA-11): the bell counts it and `Waiting on you` is posted on every device the person uses, once, and never again while the step waits, because the bell keeps counting it on every device until it is answered. A step that reaches its `Timeout` replaces its controls, in the step panel and on the session's question card alike, with a one-line receipt, `Timed out at 6:00 AM`, which has no way back; the `Waiting on you` banner and the bell's count for it are taken down; the run's header reads the cause in its first line, `The approval step timed out`; and where the run failed, `Retry from this step` waits for the person again from the same input. A step with no `Timeout` shows no end, and one with a `Timeout` names the instant it gives up in the run's live line, in the machine's own clock — `Step 4 of 9 · waiting on your approval until 6:00 AM · $0.4213 so far` — never a countdown.
- A human step's submission uses the Spec-010 approval category `human_step_contribution` (SA-12). See [Spec-010 Approvals](../specs/010-approvals-permissions-and-trust-boundaries.md).
- A step waiting on a person opens at its run's own address, `#/workflows/runs/<runId>`, on the waiting step's panel. A form is answered in that step panel: the node's prompt over one field per entry of its input schema, drawn by the same generic form renderer the inspector uses, and `Submit`. Until the form has been read the panel reads `Loading the form…` after the session's short delay, and a read that fails reads `Could not load the form` with `Try again`. What is typed is saved to the daemon as it is typed, through `workflow.humanFormDraftSave`, one draft per waiting form, so a half-filled form survives a reload and nothing typed is written to window storage. `Submit` resumes the run and replaces the form with the receipt `Answered at 2:14 PM`. A run waiting on a form is one of the runs `Next waiting (N)` walks.
- A form has no artifact field and no in-form upload: a location is a `path` field, which the person fills through the platform's own file chooser.

### Provider drivers (SA-15)

- The provider drivers (Codex, Claude) are built inside the daemon, under `packages/runtime-daemon/src/provider/drivers/`, and a workflow reaches MCP tools through the daemon's one MCP client, so there is no adapter package and no adapter contract. No `src/adapters/` folder inside core (C-6).

### External tool references — content-addressed (C-7)

- External tool references in workflow definitions (e.g., `codex@v1.2.3#sha256=...`) must be content-addressed with hash pins. Mutable tags must not be trusted for externally-referenced definitions.
- This closes the [tj-actions/changed-files CVE-2025-30066](https://nvd.nist.gov/vuln/detail/CVE-2025-30066) retroactive-tag-repointing class (23,000 repositories compromised by a single upstream tag repointing).

### Secrets — by reference only (C-15)

- Secrets are referenced via `secret://<scope>/<name>` and resolved at step launch into environment variables, stdin, or a named-file file descriptor — **never argv**. Logging redaction is defense-in-depth, not primary control. Closes the argv-exposure vector documented in CVE-2025-30066 (runner memory dumped to logs via argv).
- A node never stores a secret, an account credential, or a governance decision. A credential param carries a `secret://` reference; a provider param carries a provider-account id; a tool param carries a scope-qualified binding identity.
- A secret resolves only in a field its kind marks sensitive — the step's Credential field, and an HTTP step's auth and headers — and a `secret://` reference anywhere else is refused at save; no expression resolves one (§Expressions). HTTP auth sends `Authorization: Bearer <value>`. The live preview never resolves a secret.
- A secret's value is sealed in the operating system's keychain and never written to the document, the step record or a log ([ADR-038](../decisions/038-workflow-secrets-in-the-os-keychain.md)). Its scope is `project` or `shared`, never a session, and its name is lowercase letters, digits and hyphens, starting with a letter or digit, at most 64 characters: `secret://project/github-read`. A name that breaks the pattern, or is already taken in its scope, is refused with `workflow.secret_name_invalid`, carrying `reason: pattern | taken`.
- The step's Credential field is a chooser listing this project's secrets and the shared ones by name — a shared workflow's step, the shared ones only — read through `workflow.secretList`, with `New secret` (`workflow.secretCreate`), and `Replace value` (`workflow.secretReplace`) and `Delete` (`workflow.secretDelete`) on each row. Nothing on Settings holds secrets. The value field is write-only: masked on entry, never read back, cleared on submit, and no verb returns the value or carries it on a reply, event, log or error.
- Resolution happens at step launch, inside the daemon. The step record stores the reference and never the value, and every resolved secret is redacted from that step's logs, payloads and error messages before any of them is written. A secret the keychain does not hold, or a keychain that is locked or unavailable, fails the step and offers `Retry from this step` (§Fallback Behavior). The authoring and run-start policy checks see which secrets a version uses.

## State And Data Implications

**The document.** A workflow is one JSON document, and its canonical bytes are the JCS canonicalization of the hashed field list, BLAKE3'd (§Authoring + versioning). It carries:

- `schemaVersion`, whose V1 value is `2`;
- `name` and an optional `description`;
- `trigger` — exactly one node, of a kind in the trigger category;
- `nodes` — everything else;
- `edges`, each one `{ id, source, sourceHandle, target, targetHandle }`;
- `layout`, optional and **outside** the hashed body: a position per node, an optional viewport, and the sticky notes;
- `pinData`, optional and outside the hashed body: an item array per node id.

A node carries its id, its kind, the kind version written at insert, its display name, its sibling `order`, its params, and optionally whether it is disabled, its notes, its `onError` disposition, its `retry` bounds, whether it executes once over the whole input, and whether it always outputs data.

**The document holds no settings block**, because each concern one would carry has a home of its own: what a failure does is set on the node that failed, how long step data is kept and how long a run may work are the two controls on the console's Runtime settings page, and the clock a schedule reads is a param on the schedule trigger itself.

**The tables.** Of the tables that hold the surface, these carry over from the schema the workflow engine specifies — `workflow_definitions`, `workflow_versions`, `workflow_runs`, `workflow_gate_resolutions` and `human_phase_form_state`, the last keyed by run and node and holding a form step's draft — with `workflow_definitions` and `workflow_versions` carrying the document body as the hash preimage and a layout column beside it, because layout is outside the hash (§Canvas layout is not definition bytes (SA-35)). `workflow_runs` carries the run's `sessionId` and columns for runs that start runs: on each run's row, the chain's first run (`chain_root_run_id`, its own id for a first run) and whether an error trigger joined the chain (`chain_from_error`); on the first run's row, the count of runs the chain has started (`chain_run_count`, incremented in the transaction that creates each run) and whether the person answered `Keep going` (`chain_kept_going`). They are kept for the life of the run records, and the chain's question is a row of `workflow_gate_resolutions`, like any approval's, so a chain needs no table of its own. A run's execution context is one row in `run_execution_contexts` (§Interfaces And Contracts). These are added:

| Table | Holds |
| --- | --- |
| `workflow_steps` | One row per step attempt: run id, node id, attempt, execution index, the source array, status, timings, the payload references, cost, error, and `wait_deadline_at`, the instant a step waiting on a person gives up, set only where its `Timeout` is. |
| `workflow_triggers` | One row per armed trigger: workflow id, node id, kind, config hash, next fire, last fire, whether it is enabled. |
| `workflow_webhook_tokens` | One row per workflow that has a webhook trigger: the token hash, when it was created, when it was last used. |
| `workflow_node_state` | The per-(workflow, node) key-value store that holds trigger cursor state, so no mutable field lives on the document, and the values `Keep for later runs` keeps: one entry per (workflow, name), with the value, the run that kept it and when, kept until cleared or the workflow is deleted. |
| `workflow_secrets` | One row per secret: its daemon-minted id, scope, scope reference and name, with no value column; the value is in the operating system's keychain ([ADR-038](../decisions/038-workflow-secrets-in-the-os-keychain.md)). |

Step records live in `workflow_steps`, one row per step attempt; there is no join-state table, because a `flow.merge` node's mode decides a join. A step's written paths live in the daemon's memory only, 1 s past its after-capture. Every table is `STRICT` — its columns typed `INTEGER`, `REAL`, `TEXT`, `BLOB` or `ANY`, with JSON stored as `TEXT` — as every table in the daemon's collapsed SQLite schema is.

A payload over 64 KiB becomes an artifact and the step row keeps the reference; below the cap it is inline JSON on the step row.

**Scope.** The workflow-definition scope domain is `session` \| `project` \| `shared`. `session` binds a definition to its authoring session; `project` spans the sessions of one project; `shared` is the cross-project tier, a definition authored once and reusable by any project on the same daemon. Every scope resolves out of the same local definition store: no additional table and no synchronization path. Scope identity is carried by a `scope_ref` value alongside `scope`, in the shape [Spec-025 §Unified Inventory](./025-mcp-server-configuration-and-governance.md#unified-inventory) already uses for scope-qualified bindings — the authoring session id at `session`, the project record's id at `project`, the empty string at `shared` — and definition dedupe keys on `(scope, scope_ref, contentHash)` so one definition stored at a scope is one record regardless of which session submitted it. Resolution at run start walks the tiers most-specific-first — `session`, then `project`, then `shared` — with **no merging across tiers**: two definitions of the same name at two scopes are two distinct definitions, exactly as two same-named MCP bindings in two scopes are distinct entries. A `scope` without its `scope_ref` would not be storable: `project` would name no project, and a dedupe key rooted in the authoring session would split a `shared` definition into one record per submitting session. `workflow_definitions.session_id` records the authoring session at every scope, so provenance is kept at every scope. `shared` widens **visibility and reuse breadth only** — it is not publication, not a marketplace, and not cross-machine sync; global workflow libraries and any distribution of definitions beyond the storing daemon remain out of scope per §Non-Goals.

**Definitions are records, not artifacts.** A workflow definition is a canonical durable definition record, not a canonical artifact. Artifact publication is allowed only for derivative exports, previews, or summaries.

### Truth vs projection vs ephemeral (SA-25)

Workflow state separates into three tiers:

- **Truth (source-of-truth):** `workflow_definitions` (content-hashed), `workflow_versions`, `workflow_gate_resolutions`, and each step's payloads once written — the inline JSON or the artifact its step row references, immutable, a retry writing a new attempt rather than overwriting (SA-16). These, together with `session_events` (Spec-005), are authoritative. Daemon must be able to rebuild everything else from them. Some of the added tables join this tier as **mutable** truth rather than immutable truth: the armed-trigger rows, the webhook token rows, the per-(workflow, node) key-value store and the secret records are facts about what this machine is armed to do next and what it holds, which no event history can reconstruct — the durable row is the truth and the in-process timer is only a cache over it, re-armed from the row after a restart (§Entry node and the V1 trigger surface (SA-37)).
- **Projection (rebuildable):** `workflow_runs` and `workflow_steps` — rebuildable via a `ProjectionRebuild` path owned by Plan-013 ([Temporal — Custom persistence layer, 2024](https://temporal.io/blog/higher-throughput-and-lower-latency-temporal-clouds-custom-persistence-layer)). The per-step record is a projection over the events the run, approval and form pipelines already emit, which is what keeps one step's history a function of the log rather than a second account of it.
- **Ephemeral:** memory reservation state is not persisted — re-requested on daemon restart; no runtime pool-counts rows.

The park-and-resume state stays inside this split rather than beside it: the durable `resumeAt` schedule, its `parkAttentionKey` fold key, and the `parkReason` / `parkCause` record all sit on the step projection — per step, because parallel branches park independently and a run-level value could hold only one park (§Provider-limit pacing and durable resumption (SA-40); §Park integrity and cancelability (SA-42)). All of them are **projection**, not truth, and every one of them is carried by the event that produced it — the suspension event for every park field, the `workflow.resumed` event for a repair's version re-pin — so the rebuild-byte-equal-from-`session_events` rule holds with no exception and no schedule survives a rebuild that the log does not contain.

Workflow definitions, versions, and step outputs must be durable and replayable. Workflow and run histories must remain cross-linked for audit and replay. Optional workflow exports, previews, or summaries may be published as artifacts, but those artifacts are derivative views and must not replace the canonical definition store. Running workflows require step-state persistence separate from UI state.

Plan-015 specifies the concrete SQLite schema (SA-24 lands there — implementation detail, not spec contract).

Canvas layout is not a fourth tier: it rides the definition document's own `layout` section, outside the hashed body, persisted in a column beside the definition body, per §Canvas layout is not definition bytes (SA-35). It is mutable per author and changes no byte the engine reads, which is why it neither mints a version nor enters a rebuild.

### Deterministic identity (SA-21)

`StepRunId` generator: `BLAKE3(workflowRunId || nodeId || attemptNumber)`. **Derivation is total:** every bit of the identifier is a function of that preimage and none of it comes from a clock or an entropy source — so a `stepRunId` is **not a ULID**, whose leading 48 bits are a millisecond timestamp the preimage cannot produce. The identifier's concrete text rendering is left open (see §Open Questions), because choosing a rendering is a design decision; any rendering must stay a pure function of the digest. Replay reproduces the same `stepRunId` sequence; random ULIDs are forbidden for `stepRunId`. Replay uses `session_events` + immutable truth tables as authority; projection tables rebuild via `ProjectionRebuild` ([Temporal Encyclopedia — Event History](https://docs.temporal.io/encyclopedia/event-history); [Bitovi — Replay Testing in Temporal](https://www.bitovi.com/blog/replay-testing-to-avoid-non-determinism-in-temporal-workflows)).

**Two hash algorithms (SA-27).** BLAKE3 is the daemon-internal identity hash: the workflow-definition content hash and the `stepRunId` derivation. SHA-256 stays Plan-012's artifact-manifest content hash, where ecosystem interop matters. The split is deliberate — different algorithms for different scopes, not an oversight.

### Human form drafts (SA-28)

No workflow table ships empty. `human_phase_form_state` carries the human form kind's drafts from V1: the form activates `workflow.humanFormDraftSave`, each autosave bumps the row's own draft version, and a half-filled form is restored from the daemon rather than from the window. A client resumes no draft from browser-local storage, because typed unsent text is never put there.

### I/O format invariants (C-5)

Workflow state, step inputs and outputs, and captures are **JSON-only**. No pickle, no YAML carrying language-native object tags, and no evaluation of document text on the host — a program runs only inside a boundary the interpreter or the operating system enforces (I2). Airflow XCom's pickle default enabled a direct RCE path, disabled in 2.0 ([Airflow — Turn off pickling of XCom by default in 2.0, #9606](https://github.com/apache/airflow/issues/9606)).

**Data between nodes is always an array of items.** An item carries its JSON body, an optional map of binary references, an optional record of which input item it came from, and an optional error of its own. A node executes once over all the items of its input, or once per item where its kind declares that, and returns one array of items per output handle — an empty array meaning that branch is dead. A binary reference is an artifact id plus its media type, file name and size: bytes never travel inside a run record.

**Item lineage is what makes a cross-branch reference resolve.** The record of which input item an output came from is what lets an expression naming an upstream node resolve to the input item a given output derived from, across a branch and a merge. The engine fills it automatically for one-to-one, one-to-many and equal-count transforms, and for the empty item a node marked to always output data emits; a kind that genuinely mints or collapses items sets it itself. Two failure modes are first-class typed errors shown in the inspector rather than thrown at the user as a stack trace: lineage missing from an upstream node, and an ambiguous backward walk after a collapse, whose message names taking the first item, the last item, or one item by index as the fixes.

**A step's payloads are inline while they are small.** A step's input, output and log sit inline on the step row under a 64 KiB cap; above it each becomes an artifact through the existing ingest pipeline and the step row keeps the reference. The panel that shows a payload says which of the two it is reading. An artifact is already readable by an agent in chat with the same read the user uses, so a step's input and output are addressable from a message and the run row stays small.

### Engine event record (SA-43)

The engine keeps a **maintainer-facing record of its own decisions**, and it is **always on** — there is no enable flag, no verbosity level, and no per-run opt-in.

The always-on rule is the whole point and is not a convenience: a run parks once. By the time anyone knows a park needs explaining, the decision that produced it has already happened, and there is no second chance to have turned the log on. A record that must be enabled before the event it explains is a record that is off exactly when it matters. The cost of the alternative is paid once, in bounded storage; the cost of this alternative is paid every time, in an unreconstructable incident.

**What it is not.** The record is **non-canonical** and MUST NOT become the only account of anything. The canonical account of a run stays `session_events` plus the immutable truth tables (§Truth vs projection vs ephemeral (SA-25)); the person-facing account of a park stays the `parkCause` of §Park integrity and cancelability (SA-42). It is also not the run's own step history: what a person reads about a run — each step's input, output and log, its timings, its cost, its typed error, its execution index and the edge that actually fed it — is the per-step projection of §Truth vs projection vs ephemeral (SA-25), and re-running a run or retrying it from one step reads that record, never this one. Nothing in replay, verification, projection rebuild, or audit may read this record, and its expiry must degrade diagnosis, never correctness.

**What it carries.** Engine decisions and the typed values they were made from: step admission verdicts and pool-wait entries, state transitions, gate resolutions, park decisions with their typed `parkReason`, schedule arm and clear events with the instant armed, resume attempts and their outcomes, and typed refusal codes. Every record carries the correlation keys — `workflowRunId`, `stepRunId`, `attemptNumber`, and a monotonic per-run sequence — so a single run's decision history is reconstructable by filtering. The requirement is per-run **correlation**, not per-run storage: the physical layout (one file per day, per run, or per daemon; rotation and compaction policy) is the observability owner's choice and is deliberately not fixed here. The line format is newline-delimited JSON — one complete object per line, inside the JSON-only constraint of §I/O format invariants (C-5) — so a record truncated by a crash costs its last line rather than its whole file.

**Dispatch and outcome are two records, and the wording is part of the contract.** A record written before the work it describes states an **intent** — that the engine is dispatching a resume onto a session, never that a turn is running on it — and is paired with a second record stating that work's outcome. The pairing is what makes absence diagnostic: a dispatch with no outcome beside it is itself the finding, and where the step between them wedges it is the only signal there is. One record phrased as a completed fact for work that had not started yet reads, to a person watching a run that then hangs, as the exact opposite of what happened. The prose in every record is engine-authored, never model output.

**What it must not carry.** No secret material, ever, in any encoding (§Secrets — by reference only (C-15) and its SA-13 I4 invariant apply here exactly as they apply to argv, logs, and artifacts). No raw provider prompt or completion text: where a decision was made from a provider signal, the record carries the **typed** value the driver normalized — the park reason, the window provenance — never the payload it was normalized from. This keeps the record a decision log rather than a second, unredacted transcript.

**Ownership.** This record is a **non-canonical bounded-retention diagnostic payload class**, which is [Spec-018 §Required Behavior](018-observability-and-failure-recovery.md#required-behavior)'s declared tier — "non-canonical observability payloads … must use explicit bounded retention separate from canonical event and failure-detail retention" — and [Spec-018 §PII in Diagnostics](018-observability-and-failure-recovery.md#pii-in-diagnostics) owns that tier's discipline: the ≤ 7-day default TTL, the `retention_policy_override` warning past 30 days, and mandatory inclusion in the [Spec-020 §Erasure Paths](020-data-retention-and-gdpr.md#erasure-paths) Path 3. Spec-015 **requires** the record and specifies its content, correlation keys, and always-on rule; Spec-018 and Plan-018 **own** the bucket, its retention, and its erasure path, and register it alongside the diagnostic buckets already enumerated there. This spec authors no bucket, no TTL, and no erasure path.

## Example Flows

- **Sequential with an approval.** A workflow runs `analyze → plan → implement → review`, with a `human.approval` step between `plan` and `implement`.
- **Version-immutable edit.** A workflow is edited after one instance has already started. The running instance continues on the old version while new runs use the new version.
- **Definition-as-artifact export (derivative view).** A project-scoped workflow definition is exported as a review artifact. Later workflow execution still binds to the canonical persisted definition version rather than to the artifact copy.
- **Parallel with a merge.** A research workflow fans out to `{pass-a, pass-b, pass-c, pass-d, pass-e}`, which join at a `flow.merge` node in `append` mode. A pass whose node's `onError` is `continue` passes its input on when it fails, so its siblings continue and the synthesis step runs once all five settle; a pass whose `onError` is `stop` ends the run failed and cancels the four still running.
- **Multi-agent.** A `deliberate` multi-agent step runs a lead and two helpers in the run's session through the orchestration path. What that orchestration run returns is the step's output, and the next step reads it through `$('deliberate').item`.
- **Human step with a timeout.** A `validate` form step with `Timeout` set to three days, `inputSchema: {decision: enum['approve','reject'], notes: long_text}`, and `onError` set to `continue-error-output`. The person opens the run from `Next waiting (N)` or from the session's question card, drafts a reply in the step panel (saved to the daemon as it is typed, per SA-28) and submits; the submission becomes the step's output, and no gate is resolved, because a form step is not a gate. If the deadline passes first, the step fails with `workflow.step_timed_out`, cause `step_timeout`, its controls become `Timed out at 6:00 AM`, and the run continues down the node's error handle.

## Output Mode Specification

- V1: a step's output is an array of items, each carrying JSON and, where it holds a file, a binary reference to an artifact — the artifact's id with its media type, file name and size; bytes never travel inside a run record.
- A step payload over 64 KiB is stored as an artifact (Plan-012) with `artifactType: 'workflow_output'`, and the step row keeps its reference; a smaller payload is inline JSON on the step row.

## Discussion Integration Path

- An `agent.run` step runs one agent in the run's session. An `agent.multi-agent` step runs a lead and its helpers in the run's session through the orchestration path (§Agent steps (SA-6, SA-8, SA-9)).

**A run's results reach exactly one session: the one that asked for the run.** The session where the user typed the run verb, or whose own agent started the run through its run tool, receives one flat transcript row when the run ends — the workflow's name, the run's status, its duration, a one-line summary of what came out, its attachments as that session's own file rows, and a link to the run; no cost figure. It is an ordinary message, which the agents in that session read on their next turn. While the run is live the same session carries one progress row, updating in place until the run ends and then becoming the results row; it links to the run's page and nothing is pinned.

**Nothing posts into a session that did not ask.** There is no post-to-chat node and no method that takes a target session: the results verb pulls a run's results into the current session on demand, sending the session it was typed in, which the daemon checks is the caller's own, and the results-posting tool does the same for the invoking agent's own session, taking no session at all — the daemon derives it from the invoking turn. A schedule's results live in the runs list, and a workflow that needs an agent to act on its results starts its own session with a task.

## Workflow Timeline Integration

**Runs are two levels: the list of runs, and one run's page.** Nothing keeps a trail of where the reader has been and no control walks one backwards.

**The list.** One row per run, newest first, reading in order: the workflow's name, the status chip, the trigger, who or what started it, when it started, how long it took, how many steps it ran, and what it cost with the account that paid. A row that spent nothing reads `$0.00` and names no account. While a run is going, its step cell says where the run is and what it is doing — `4 of 9 · run tests` — off the same subscription that moves its status and its duration; the row never grows a second line, and the cell goes back to the finished step count when the run ends. The list updates live through one subscription rather than one per row. Four filters narrow it — workflow, status, trigger and date range — and nothing else; they narrow the table alone, and a set of them matching nothing gives way to a note in their own words, `No run matches Failed in the last 7 days.`, carrying one **Clear filters** button. The one narrowing beside them is the version `Show runs` hands in from the Versions panel: it stands as one removable chip in the filter row, is never kept, and `Clear filters` clears it. The four filters are kept on this device and come back the way they were left, read and written defensively so the tab renders correctly when that store is empty or throws; nothing else about the tab is kept — not which run was open, not where the reader had read to. With no run at all and no filter on, the list reads `No runs yet` over `A run appears here the moment a workflow starts.` The rows carry no version chip. Every run the surface shows belongs to the daemon that ran it, and a run reached from another device is that same run driven from a distance; no run ever leaves the list because of the device it is being read on. One row action, **Delete run**, asks once and names what goes, and on a `new`, `running` or `waiting` run it is refused in place with `Cancel it first.`; above the list, **Delete runs older than…** names how many runs would go and says that a run marked Keep stays and a run waiting on a person is never touched. No row carries a selection control and nothing else acts across the list.

**Runs waiting on a person stand in their own section above the table**, oldest first, one line each: the workflow's name, what it is waiting on, and how long it has waited. The entries for runs parked on a spent provider account keep their place at the top of that section, folded to one entry per outage with its affected-run count. The filters never narrow the section, and the table below keeps its newest-first order and every run it lists. The section stands whether or not anything is waiting: with nothing waiting it reads `Nothing waiting`, and where this sitting has answered runs it says so beside it — `Nothing waiting · you answered 4 runs this morning` — counting only what has been answered since the surface was opened.

**A run's page is three things: a header, the run graph, and a step panel** that opens beside the graph when a step is picked. Everything the run has to say is in one of the three, and picking a step replaces what the panel holds rather than making the page longer. While a run's page is being read the runs strip stays drawn and the page reads `Loading this run…` after the session's short delay; a read that fails reads `Could not load this run` with `Try again`.

- The header carries status, timings, trigger, who started it, cost, the `version vN pinned` chip — which opens the Versions panel with that version selected — and links to the source workflow and — where a message started the run — to that message. A run that joined a chain names the chain's first run among those facts, beside who started it: `Started by Summarize folder · 2:00 AM`, linking to that run. It opens with two lines: what happened, then what it needs, both composed from the run's status and, where it is parked, its cause — `The test step failed twice` over `Fix it and press Resume, or cancel the run` — so every kind of stop is written in plain words and none is kept by hand. A run still going says that it is running and that nothing is needed, and a parked run's cause is read in the first of those two lines and nowhere else on the page.
- A run that has finished carries one control more in that header, **Open in Review**, which opens the console's one difference surface on the run's own snapshots, from the run's start to its end. A run has no branch of its own, so what the run wrote is read where every other difference is read, the session screen's Review pane, as the branch comparison's file list and diff with no scope row, base picker, notes or ship strip, reading `This run changed no files` when nothing changed; edits others made in the same checkout between two snapshots show too, each file marked with the step that changed it, and `Open in editor` on a file shows only while that file still exists in the recorded folder. A run still going carries none, and this page draws no difference of its own.
- While a run is going, one line sits at the foot of the header, directly above the graph, saying where the run is: which step is live and its place in the run, what is blocking it, the instant it resumes itself where one is armed, and what it has spent so far — `Step 4 of 9 · waiting on your approval · $0.4213 so far`. Only a blocker that needs a person is marked, and it is marked amber. A run that has finished carries no such line.
- The graph is the workflow's own canvas, read-only: every node where the builder put it, colored by that step's state, and every edge carrying the count of items that went through it. A step the memory gate is holding carries its own quiet hold ring and reads `Waiting for memory`, never the amber that marks a step waiting on a person, and nothing about it reads as a failure; a step parked on a spent account reads `waiting` with its cause and, where one is armed, the instant it resumes itself. Nothing on the graph can be moved, connected or deleted, and no second drawing of a run exists. It opens placed on the step that is live and follows it as the run moves; a scroll, a drag or a key stops the follow and nothing starts it again by itself, and once the view has drifted a small `now` chip stands at the canvas's corner, which slides the view back and follows again. The chip is drawn only while pressing it would move the view.
- Picking a step opens the **step panel** on Output, or on Error where the step failed. The panel has Input, Output, Logs, Cost and Error tabs, each with a table and a JSON view, item counts, the item pairing, `Copy as JSON` and `Open as artifact`; it reads a step's payloads through `workflow.stepRead`; `workflow.stepOutputList` serves the command line and the SDK. The table view draws a payload by its type: a binary field draws as the file it names — `pr-4821.patch · text/x-patch · 14 KB` — in place of its reference, and a markdown string draws as the formatted text it is; the JSON view keeps both exactly as they were stored. The panel says whether a payload was read inline or from an artifact, and it shows the executed source edge, so a step fed by run 3 of a loop says so. Cost renders on every step and every run as the cost itself, with no mark, priced as the session's cost rows are, and names the paying account; a step or run that spent nothing reads `$0.00` and names none. Every figure reads in the one money format: `$`, then the amount in US dollars with a period for the decimals and commas between thousands, two decimals above $0.50 and four at $0.50 or below, rounded half up from the stored amount, in tabular figures, with no prefix, suffix or mark; a run's cost is summed from its steps' stored amounts and rounded once, never from rounded rows — a four-request step reads `$0.0018` and a long run `$11.60`.
- A step whose data is past the retention bound reads that it expired in place of its panels. Beside the panel's own controls sit **Keep**, which holds this run's step data past the bound, and pinning this output as the builder's test data. There is no send-to-chat action anywhere on the page: results reach a session only from inside that session (§Discussion Integration Path).
- A sub-workflow step links through to the child run. A run whose definition version was deleted still opens, because a run pins its version.
- Every clock figure is written the way the machine's own clock writes it — `Mon 8:30 AM EDT`, `Yesterday 7:48 PM` — and an instant inside an item's own data stays exactly as it was written, like a log line or a path. A duration is written the way the rest of the surface writes one — `6 m 41 s`, `38 s` — and only a duration under a second is written in milliseconds, `4 ms`; a raw millisecond figure for a step that took minutes never reaches the screen.
- A run that ended before its last step quotes why from the latest attempt's own cause, read from the provider's frame and never from an earlier attempt: a turn the daemon itself interrupted is marked as the daemon's, a provider's own turn limit is its own reason, and a provider that gave out after its retries is the cause on either provider. A run parked by a spent account still renders its park cause and its resume instant.

**A step blocked on an approval is answered where it blocks.** Its panel carries **Reject** and **Approve** beside **Open in Review**, and answers the approval there — in the words the approvals surface uses, through the same pipeline and the same Cedar check — so the person already looking at the step that is blocking never has to leave it to unblock it. The run leaves `waiting` and resumes down the branch that was chosen. Answering replaces all three controls with a one-line past-tense receipt in the machine's own clock, `Approved at 2:14 PM`, with no way back from it — no undo, no re-answer, no second press — and the run's own actions are what act next. Every act a person takes on a run once — approve, reject, answer, restart, discard, merge, open a pull request — leaves that same receipt in place of its controls.

**A step waiting on a form or on a chat reply is answered the same way, at either of two doors.** A form is answered in the step panel (§Human steps — `HumanStepConfig` (SA-10, SA-11, SA-12)). A step waiting for a chat reply raises the session's own question card, with the workflow's name as its chip, its free-text row alone and `Answer`, and no `Skip`; its step panel carries the same question with the same row. The two doors are one wait, tied to it by its `waitId`: the first answer, through either door, settles the wait everywhere at once and replaces both with the receipt `Answered at 2:14 PM`, and the receipt stays until the next message or card. Every other message in the session stays an ordinary message. A run waiting on a reply is one of the runs `Next waiting (N)` walks. `Open in Review` in an approval step's panel opens Review from the run's start to that pause.

**A failed step is fixed in a fresh session, never inside the step's own.** A run parked on a failed step carries one action no other step's panel does, `Fix in a fresh session`. It prepends a new session on that step's own project and checkout and switches to it: its first turn carries the step's name, the input the step ran on and the output it failed with, under a footer naming the run and the step with a link back, plus a second link to the step's own session for reading. The step's session is read from and never written to — no message, no steer and no act reaches it — so the run's record stays the run's record and a resumed step never carries messages as context it was never meant to have. **Resume** then reruns the step from its original input against the fixed checkout and the rest of the run follows. Once such a session exists the run's page links it, beside the links to the source workflow and the starting message, for the life of the run. That link is the one route into a step's session anywhere on this surface: a run's page never opens the session its steps ran in, because the step's transcript is the run's own record and is read in the step panel. Nothing else new is offered on a parked run: no takeover, no detach, and no third operator operation beside cancel and resume (§Operator run control (SA-45)).

### Event envelope and category split (SA-18)

All workflow events land as payloads inside the existing Spec-005 `EventEnvelope` — **no new envelope schema**. `causationId` on the envelope carries parent-event relationships; `workflow_run_id` / `step_run_id` are payload fields. This is an additive MINOR envelope bump under [ADR-018](../decisions/018-cross-version-compatibility.md) discipline.

V1 introduces **new Spec-005 categories** (not one monolithic `workflow_lifecycle`):

- `workflow_lifecycle`
- `workflow_phase_lifecycle`
- `workflow_parallel_coordination`
- `workflow_gate_resolution`

Scope-of-query split matches Spec-005's existing `run_lifecycle` / `approval_flow` pattern. No collision with existing `presence.*`, `run.*`, `approval.*`, `recovery.*` categories.

Reverse-DNS `workflow.*` namespace convention follows [CloudEvents Specification v1.0.2 `type` attribute](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#type).

### Event types (SA-19)

- **`workflow_lifecycle` (13):** `workflow.created`, `workflow.started`, `workflow.gated`, `workflow.failed`, `workflow.completed`, `workflow.resumed` (its payload carries an additive-optional version re-pin member naming the version a repaired run left and the one it joined — §Frozen-definition repair (SA-41); additive MINOR under [ADR-018](../decisions/018-cross-version-compatibility.md)), `workflow.canceled` (the canonical record of a cancellation, carrying the supplied `reason` bounded exactly as `parkCause` is, and minted **together** with `workflow.runCancel` per §Operator run control (SA-45): the status write and this append share one unit of work, without which a projection rebuild would replay the last `workflow.phase_suspended` payload and resurrect a canceled run (SA-25)), `workflow.run_waiting`, `workflow.schedule_armed`, `workflow.schedule_fired`, `workflow.trigger_armed`, `workflow.trigger_fired`, `workflow.results_posted`
- **`workflow_phase_lifecycle` (17):** `workflow.phase_admitted` (resource-pool admission), `workflow.phase_waiting_on_pool` (diagnostic), `workflow.phase_started`, `workflow.phase_progressed`, `workflow.phase_canceling`, `workflow.phase_failed` (carries `cancellation_reason: 'sibling_failure' | null`), `workflow.phase_retried`, `workflow.phase_suspended` (its `reason` union is `waiting-human | provider-usage-limited`, and the payload carries the bounded `parkCause` plus, where one is armed, the durable `resumeAt` instant and, where one was computed, the `parkAttentionKey` fold key — §Park integrity and cancelability (SA-42)), `workflow.phase_resumed`, `workflow.phase_completed`, `workflow.human_phase_claimed` (informational), `workflow.human_phase_escalated` (telemetry-only at V1 per SA-11; no `nextAction` pre-declaration — additive-field discipline per ADR-018), `workflow.step_started`, `workflow.step_finished`, `workflow.step_failed`, `workflow.step_canceled` (a step that was running or waiting when its run ended failed or canceled, or a branch `First to arrive` canceled), `workflow.step_skipped`
- **`workflow_parallel_coordination` (1):** `workflow.parallel_join_cancellation` (the coordinator event when a run that ends failed or canceled, or a `First to arrive` merge, cancels running sibling branches)
- **`workflow_gate_resolution` (1):** `workflow.gate_resolved` — carries `nodeId` for a `human.approval` gate and none for a chain's question, `outcome` (`approved` or `rejected`), `deviceId`, the answering device's id, and `gateResolutionId`, the id of the `workflow_gate_resolutions` row it records; it is keyed by the run and carries no `stepRunId`. Payload additions are additive MINOR bumps under [ADR-018](../decisions/018-cross-version-compatibility.md).

The step events are what make a run's own step history a function of the log: each step boundary emits one, so the runs surface and the session's record are one truth rather than two (§Truth vs projection vs ephemeral (SA-25)). The events one turn of the engine's loop emits are handed to the event log as one batch, in the same transaction as the step rows they describe (§Execution semantics). Each type is also listed under its category in [Spec-005 §Event Type Enumeration](./005-session-event-taxonomy-and-audit-log.md#event-type-enumeration).

**Where the `workflow.*` event types and their categories are registered.** [Spec-005 §Event Type Summary](./005-session-event-taxonomy-and-audit-log.md#event-type-summary) — the owning registry — carries the workflow categories. §Workflow Timeline Integration here enumerates the type literals themselves and registers none of them.

### Ordering invariants (SA-20)

Load-bearing event-sequence rules ([Temporal Events Reference](https://docs.temporal.io/references/events), [Temporal — Events and Event History](https://docs.temporal.io/workflow-execution/event)):

- `workflow.phase_admitted` precedes `workflow.phase_started` (resource-pool admission required first).
- `workflow.phase_canceling` precedes `workflow.phase_failed` whenever `cancellation_reason != null`.
- `workflow.gate_resolved` precedes the next `workflow.phase_started`.
- Parallel cancellation fires one coordinator event (`workflow.parallel_join_cancellation`) + per-sibling event chains at deterministic tick-boundary — never mid-callback.
- `workflow.phase_suspended` precedes every `workflow.phase_resumed` carrying the same `step_run_id`, and a `workflow.resumed` carrying the SA-41 version re-pin member is preceded by a `workflow.phase_suspended` for that run — a repair is only ever expressible on a parked run, so a re-pin with no preceding park is a malformed sequence rather than an unusual one.
- `workflow.step_started` precedes the `workflow.step_finished`, `workflow.step_failed` or `workflow.step_canceled` that carries the same step identity.
- `workflow.run_waiting` precedes every resume of the same run.
- `workflow.schedule_fired` precedes the `workflow.started` it caused.
- `workflow.results_posted` follows the terminal status of the run it names.

### Cadence (SA-22, SA-23)

- `workflow.phase_progressed` cadence depends on the node kind:
  - `agent.run`: emit on turn completion + tool-invocation boundary.
  - `multi-agent`: emit on each turn completion of the lead or a helper + tool-invocation boundary.
  - `human`: emit on each form-draft save.
- `workflow.phase_waiting_on_pool` cadence: emit on entry-to-blocked-state + 30-second intervals while blocked, carrying `waitingSinceSeq` for reader correlation. Aggregate `totalPoolWaitMs` is stored on the step row — not per-wait rows.
- `workflow.resumed` payload carries structured `resumptionPoint: {activeStepRunIds, pendingGates}` for reader-reconstruction speed (aligns with low-cardinality naming per [OpenTelemetry SemConv for Events](https://opentelemetry.io/docs/specs/semconv/general/events/); [n8n Workflow Executions](https://docs.n8n.io/workflows/executions/) provides durable-resume prior art).

### Session timeline surfacing

- A run's steps appear as distinct sections in the session timeline (Spec-011).
- Retry attempts appear as sub-entries within their step's section.
- `workflow.phase_suspended` with `reason: 'waiting-human'` is a first-class surfaced event; session UI surfaces pending-human count prominently.
- `workflow.phase_suspended` with `reason: 'provider-usage-limited'` is surfaced with the same first-class weight, rendering the park's `parkCause` and, where one is armed, the instant the run resumes itself — the same instant the durable schedule holds, read from the payload rather than recomputed. Concurrently parked runs sharing an attention key render as one entry with its affected-run count, never as one entry per run (§Provider-limit pacing and durable resumption (SA-40)); a run parked with no schedule renders as parked-awaiting-resume rather than as scheduled, because a client that invents a time the engine did not arm is the display half of the same guess SA-40 refuses to make.

**Every run lives in a session, and the run record names it.** Three rules place it:

1. A run started from a chat — a workflow verb typed there, or that session's own agent starting it through its run tool — lives in that session.
2. A run nobody is watching — a schedule, a webhook, a file event, or Run now from the Workflows tab — lives in **one session the workflow owns**, created on its first unattended run and reused by every later one, named after the workflow and listed once among the sessions. A five-minute schedule is therefore one session entry, not two hundred and eighty-eight a day.
3. A sub-workflow call runs the child **inside the parent's session**. The child keeps its own run record carrying its parent's id, so the runs list shows it, links it to the parent, and applies retry-from-step and the step-data retention bound to it as to any run; its steps' runs and events land in the parent's session, so there is one place to open, and pause, resume and cancel on the parent cover the child.

## Node-Kind Taxonomy

**Every kind the runtime offers is a node, and a run executes nodes as steps.** The kinds that run an agent or ask a person — `agent.run`, `agent.multi-agent`, `human.approval` and `human.form` — are nodes like any other; their executors reimplement nothing and delegate at run time to the existing run, orchestration, approval and form machinery (§Implementation Notes). There is no separate phase type and no gate type: an approval is a `human.approval` node with `approved` and `rejected` outputs, a step follows the one before it along an edge, and a run ends when its last steps settle.

What a failure does is the failing node's `onError` — `stop`, `continue` or `continue-error-output` — beside its `retry` bounds, which the engine clamps (§Loud-errors discipline (C-12)). Step statuses are the list of §Execution semantics.

The catalog is built in the order a kind unblocks an end-to-end scenario: `trigger.manual`, `trigger.schedule`, `agent.run`, `human.approval`, `files.read`, `developer.shell`, `flow.if`, `output.save-artifact`, `developer.http`, `developer.mcp-tool`, `flow.loop-items`, `flow.merge`, `flow.set-vars`, `files.write`, `files.parse`, `files.template`, `files.ingest-artifacts`, `browser.open`, `browser.extract`, `developer.git`, `developer.repo-diff`, `developer.run-tests`, `developer.code`, `human.form`, `flow.wait`, `flow.switch`, `trigger.file-watch`, `trigger.webhook`, `trigger.session-event`, `trigger.chat`, `flow.execute-workflow`, `trigger.sub-workflow`, `trigger.error`, `flow.stop-error`, `output.notify`, `output.write-summary`, `browser.screenshot`, `browser.act`, `agent.ask-question`, `agent.multi-agent`, `human.wait-for-chat-reply`.

**Key shapes.** `flow.if` has two `main` outputs named true and false. `flow.switch` derives its output count from its rules. `flow.loop-items` has outputs named done and loop, in that order, and its body's last node wires back into its input. `flow.merge` has N inputs and one output, with append, combine-by-field, combine-by-position, choose-branch and first-to-arrive modes; `First to arrive` passes on the first input to succeed and cancels the branches still running. `flow.set-vars` carries `Keep for later runs`, off by default: on, the values the step writes are also kept for the workflow when the step succeeds, one entry per name, replacing that name's earlier value, read by later runs through `$vars` (§Provider-limit pacing and durable resumption (SA-40)); the node shows, under its params, what is kept now — each name, its value and the run that kept it — with `Clear kept values`. `human.approval` has approved and rejected outputs on the wait mechanism. `agent.run` has one `main` input, one `main` output, an unbounded `tool` input, and params for the definition, the per-node binding, the prompt, an optional output schema and an optional timeout, where the definition is absent for General and the binding holds only the rows the author changed (§Agent steps (SA-6, SA-8, SA-9)). `developer.mcp-tool` and `developer.code` both expose a `tool` output, so either can be wired into an agent node. A sticky note is a kind with no handles and a resize affordance, added from the canvas controls rather than the palette.

**The Code node's two tiers, and the one boundary a program runs inside.** The quick tier is the default and starts no process: the WebAssembly interpreter of §Implementation Notes, on a thread of its own, held to a memory budget and a deadline (256 MiB and 5 s by default, settable), for shaping items, with no packages and nothing of the host bound into it. The full tier runs a real child process — JavaScript and TypeScript under `bun`, Python in an environment `uv` builds — and a step names its packages in its own code: JavaScript and TypeScript in the import line, with or without a version (`import { camelCase } from "lodash-es@4.17.21"`), and Python in the script's inline metadata block (`# /// script` … `dependencies = [...]`). Locking and installing happen behind save and run; there is no install screen.

- **Packages are locked when a version is saved.** Every version write — Save, Restore, Duplicate and import — locks each Code node whose code differs from the version it was written from, or that carries no lock; every other node carries its lock forward, so a restored version installs the packages it ran with, and a Duplicate or an import that changes no code needs no network. An export carries each node's lock. For JavaScript and TypeScript the daemon reads the step's import specifiers with bun's own transpiler (`Bun.Transpiler.scanImports`), leaves out relative paths and Node's and bun's built-in modules, writes a `package.json` naming each package at the version its import gives or at `latest`, and runs `bun install --lockfile-only`; two imports that name one package at different versions refuse the save. For Python it runs `uv lock --script`; the first Python save on a machine also installs the Python `uv` manages into the daemon's folder, shared by every step. A bare import locks to the newest release at save, and a script with no `requires-python` locks for the newest Python. The version's row holds the step and its lock, and a lock made on one system installs on another.
- **A run installs from the lock and never resolves again.** At a version's first run on a machine the daemon writes the step, its lock and its `package.json` from the version's row into that version's code folder, `~/.ai-sidekicks/workflow-code/<version>/<node>/`, and installs there as a plain process with the network on, outside the sandbox: `bun install --frozen-lockfile`, which puts `node_modules` beside the step, or `uv export --script --locked` into hashed requirements, `uv venv` on the managed Python the lock's `requires-python` allows, and `uv pip sync --require-hashes` into the folder's own `.venv`. Later runs of that version reuse the folder, and their install only checks it. Installs into one folder run one at a time; a second run of the same version waits for the first one's install. Packages come from one cache per tool in the daemon's folder, so a package version is fetched once for every workflow. Install scripts run as bun's default trust list allows them, and a source-only Python package is built here. A version's code folders are removed once a newer version of its workflow is saved and no run of it is live, and a later run of that version rebuilds them from its row.
- **The step runs with the worktree as its working folder.** JavaScript and TypeScript run as `bun --config=<the daemon's own empty bunfig.toml> --no-env-file --preload <unpin preload> <code folder>/step.ts`: the daemon names the file `step.ts` or `step.js`, and the preload, shipped with the daemon, rewrites each versioned specifier in an import position (`from`, `import`, `import(`, `require(`) to its bare name before bun resolves it, so the lock supplies the version; any other string is left alone. `--config` and `--no-env-file` keep the worktree's own files out of the step: without them bun runs the preloads a worktree's `bunfig.toml` names and loads its `.env` into `process.env`, which Python never does. A step reads a secret through a sensitive field (§Secrets — by reference only (C-15)), never from a file in the worktree. Python runs as `<code folder>/.venv/bin/python <code folder>/step.py` with `PYTHONDONTWRITEBYTECODE=1`, with no `uv` at run. A step's temporary files go to its run's own folder, `~/.ai-sidekicks/workflow-runs/<run>/<node>/tmp`, which is removed when the step ends, so nothing but the step's own output lands in the worktree. Both folders sit in the daemon's folder and never under `/tmp`, because on Linux Codex's `/tmp` deny hides all of `/tmp`, a grant for one folder included.
- **The package caches are disposable, and the person bounds them.** A version's code folder lasts until its own removal above; the two caches only speed installs up. Clearing one never breaks an installed folder, because an install copies each file out of the cache (a clone on macOS, a hard link on Linux) and a later run's check reads only the folder. `Cache limit` under `Package cache` on the Runtime settings page reads `Unlimited` by default, and then the daemon never clears a cache on its own; with a size set, after each successful install the daemon reads that tool's cache and clears it when it is larger, never the other tool's. `Clear Bun cache`, `Clear uv cache` and `Clear all caches` clear on request. A clear never touches a code folder or the managed Python, which every installed `.venv` runs on. Installs and a clear of one cache run one at a time: a clear waits for the installs using that cache, and an install waits for a clear. The daemon never clears a cache to make room for an install (§Fallback Behavior).

The full tier and `developer.shell` both run at the **run's permission level** ([Spec-010 §Required Behavior](./010-approvals-permissions-and-trust-boundaries.md#required-behavior)), exactly as a command an agent runs does: the asking levels ask before the step runs; `sandboxed` runs the step inside the provider's own sandbox — Claude Code's through `@anthropic-ai/sandbox-runtime` linked as a library, Codex's through `codex sandbox` under a named permission profile, run from `@openai/codex`'s native binary — with writes confined to the worktree and the step's own temporary folder; `yolo` runs it with no sandbox. Codex's profile extends `:workspace` with `filesystem."/tmp" = "deny"` and `filesystem."<temporary folder>" = "write"`, and Codex starts with `TMPDIR` set to that folder, because `:workspace` alone leaves `/tmp` and whatever `TMPDIR` Codex starts with writable. Claude Code's sandbox takes `allowWrite: ["<worktree>", "<temporary folder>"]` and `denyWrite: ["/tmp/claude", "/private/tmp/claude", "~/.npm/_logs", "~/.claude/debug"]` and starts with `CLAUDE_CODE_TMPDIR` set to that folder, because it otherwise keeps its own `/tmp/claude` and `~/.npm/_logs` writable. The code folders and the shared caches are read from inside and never written. The network reaches only what the person's own provider settings allow — off on Codex unless their profile enables it, and their own domain allowlist on Claude Code — except that on Linux Codex's run profile carries `network = { enabled = true }`, because with the network off Codex's Linux sandbox refuses bun's writes to a child process's pipes. The engine builds no sandbox of its own, and at `sandboxed` a sandbox that cannot start refuses the step rather than running it unprotected (§Fallback Behavior).

**The browser kinds run in the session's own managed browser** — the desktop's page host where a desktop is open on the executing machine, otherwise the daemon's headless browser, both driven through one path — Playwright over the Chrome DevTools Protocol, which reaches the desktop's page views through the daemon's relay, with no listening debug port on either host — and sharing the one saved site-data set. A run's page is the same page a person sees in the session's preview surface; nothing browser-shaped is created per step.

## Visual Workflow Builder

V1 ships a visual, node-graph authoring surface for workflow definitions alongside the file and SDK authoring paths. Every graph the builder can produce is a document the daemon accepts through the same `workflow.definitionCreate` path with the same validation, and the saved bytes are what the author drew, so a round trip through export, an agent's edit or the version chain shows the workflow the author built. See [ADR-026](../decisions/026-visual-node-graph-workflow-authoring.md).

The destination has one header and three tabs. The header carries the screen's title, the tabs — **Builder**, **Workflows** and **Runs**, the last two each carrying the count of what it lists, read from the data on first paint and after, so a person landing on the Builder reads the same number as a person landing on the tab — and at its right one actions menu holding `New workflow`, `Import…` and `Ask a sidekick to build one`.

**The builder is three columns**: a palette as wide as its widest kind row reads at the current text size, the canvas, and an inspector as wide as its widest param label and field pair. A toolbar sits above the canvas and a validation strip below it. The inspector opens when a node is selected and closes at its own step in this surface's Escape order, keeping every edit it holds.

**The palette** lists every kind the runtime offers, grouped by category, each row carrying an icon, the name a person reads and the one line under it, searchable by name, description and alias. Rows drag onto the canvas and click to add at the viewport's center. It is docked, never a modal, and it is drawn from `workflow.kindList`, so a kind added in the daemon appears with no renderer change. Placing the Code node opens an editable code body in the inspector, so a program is typed there and nowhere else.

**The canvas flows left to right and is fully controlled.** Its nodes and edges derive from the document draft held in the builder's own store, and every change the canvas reports becomes a document mutation, so the store and not the canvas library is the source of the bytes that get serialized. Nodes drag, multi-select, delete, connect by dragging from an output handle to an input handle, reconnect, and copy and paste as a JSON fragment. A `tool` input sits on a node's bottom edge, a `tool` output on its top edge, and `main` handles left and right. The canvas draws background dots, its own zoom controls and `Add a note` at the bottom left, the minimap at the bottom right, and a run bar across its top while a run is live; `Run now` and `Tidy up` stay in the toolbar. The canvas library's attribution mark stands at the canvas's corner, on the builder and on a run's read-only graph alike, and is never hidden.

**Canvas interactions.**

- Dragging a node updates its layout entry and nothing else; the hashed body is untouched. A drag is coalesced into one undo entry at drag end, not one per pointer move.
- Dragging from an output handle to an input handle creates an edge; releasing on empty canvas opens the palette at that point, pre-filtered to the kinds whose matching handle accepts the dragged type.
- An existing edge reconnects by dragging either end; dropping a reconnected end on empty canvas deletes it. The mid-point `+` on an edge inserts a chosen kind between the two endpoints and rewires both sides, and the edge under the pointer raises to the top of the drawing so its own controls are never covered where edges overlap.
- Backspace or Delete removes the selection, and removing a node removes its edges. Shift adds to the selection, a plain drag on empty canvas rubber-band-selects, and the platform select-all chord selects every node and every note. Pan is the wheel, a space-drag or a middle-drag.
- Undo and redo are document snapshots in the builder's store, capped at 200 entries and bound to the platform undo chord and its shifted form.
- Copy serializes the selected nodes and the edges between them as a JSON fragment; paste re-ids them and offsets them by two grid steps, so a fragment pasted from a chat message lands as real nodes, visibly beside what it was copied from. Nodes snap to the canvas grid.
- `Tidy up` re-runs the layout engine over the whole document and writes the result into the layout section as one undo entry.
- Double-clicking a node's name renames it in place; the rename touches no edge and no expression, because every edge and every expression resolves through the node's id.
- Arrow keys nudge the focused node one grid step and Shift with an arrow moves it four. The console's own keybinding service owns that binding, because the canvas library's keyboard handling is switched off here so a second live announcer is never created; every structural change — a node added, connected, deleted, or changing run state — is announced through the console's single announcer instead.
- Param editing happens in the inspector and never inside a node, so a keystroke re-renders one panel rather than the graph, and a document over roughly 150 nodes renders only the elements in view.

**A node draws its kind icon, its name, and the one-line summary its kind computes from its params.** A disabled node renders grayed with struck-through edges, and the engine passes its input straight to its output. During a run a node carries a state ring — idle, running, succeeded, failed, waiting, waiting for memory, skipped or canceled — and after one it carries the item count of its first output. A node whose last run's data is stale carries a staleness marker distinct from the success ring, and a node with pinned data carries a pin marker and is not executed in a manual run. A failed node carries a red outline and the first line of its error, and clicking it opens the inspector on Error. A node with a capability input renders those handles on its bottom edge, visually distinct from data handles, and a node that offers a capability — the MCP-tool kind and the Code kind — puts that output handle on its top edge, so a capability never leaves a node where its items do. A node in the agent category draws the one generic mark that stands for an agent, as the rows of that node's own chooser do, and a saved agent's own icon stands in its place on a chooser row where it sets one; no other generic mark on this surface ever stands for an agent. Each kind has one node width — wide enough for that kind's icon, its name and its count at the default text size — so first paint is complete and the layout pass needs no measurement; a failed node grows by the one line of error it must carry. A loop node draws both of its ways out before any run: a `done` edge onward and a `loop` edge back into its body, each labeled where it leaves the node, and each carrying the count of items that went through it while a run is circling. The ring is amber only on a step waiting on a person — an approval, a form or a reply — and never on a step held for memory or parked on a spent account; a step held for memory carries its own quiet hold ring and reads `Waiting for memory`.

**One edge type draws every connection**: a bezier path with an arrow head, a mid-point `+`, a delete affordance on hover, a branch label near the source handle — `true`, `false`, `error`, `loop`, `done`, `approved`, `rejected` — and, while a run flows through it, an animated state and an item count.

**The inspector** opens with a header carrying the node's kind, its name, its enable toggle and delete. Below it: a Parameters panel rendered generically from the kind's param specs, each param shown or hidden by its sibling-value condition; a Settings section for the error disposition, the retry bounds, execute-once, always-output-data, a fork's branch `Order`, and the node's notes; and three data panels over the last run's data for that node — **Input**, **Output** and **Schema**.

- Any param toggles between a fixed value and an expression, and typing `=` into an empty param activates expression mode. An expression field previews its resolved value against the current item of the last run, live, with the failure reason where it cannot resolve; a sensitive field previews the secret's name, never its value. Dragging a field from Input or Schema into an expression param writes the expression that reads it.
- Output offers table, JSON and schema views with an item count, a search box and pagination, plus a pin button, `Copy as JSON`, the per-type renderers for binary and markdown payloads, the advisory hints strip, and a run-info block. Its JSON view is editable, and saving it pins that data onto the node. Schema is the field tree, and it is what an agent-authored expression is checked against in the validation strip.
- Governance facets on a tool binding render read-only with their source named, and no control in the inspector writes them (§Tool bindings are references, never inline policy (SA-34)).
- A kind whose handle set depends on its params re-registers the node's internals immediately after the param write that changed the set.
- The Code node's tier is one control offering two words — `Quick` for shaping items, with no packages and no reach outside the interpreter, and `Full` for a program that names the packages it needs in its own first lines. Nothing else about the node changes with the choice: the code body, the input and output panels and the timeout read the same either way.
- The agent param opens the node's own chooser: a popover over the agent definition list, its header reading `Run as` over a search field, with **General** at the top of the list. Typing narrows the list by name, the arrows move a cursor through what is shown, Enter or a click chooses and the choice applies to the node at once, and Escape closes it without choosing. The cursor sits on the row the node already holds wherever that row is shown, else on the first row, and a search matching nothing says so. What the node stores is §Agent steps (SA-6, SA-8, SA-9).
- A node's notes are one field in that Settings section, read by whoever opens the workflow. Nothing carries a note from one run to the next: what one run should tell the next is written into the workflow's own state, where the engine can read it.
- A trigger node's panel carries three things under its params that no other node's does: the overlap choice, the last skipped fire where there is one, and, for a webhook, its address (§Entry node and the V1 trigger surface (SA-37)).

**The toolbar** carries the workflow's name, inline-editable; Save; Run now, which reads `Cancel` while the run it started is live; a schedule pill reading off or the next fire; a version readout that opens the Versions panel; Tidy up; Export; Import; Undo and Redo; and at its right New workflow and a zoom readout.

**The validation strip** is a bottom bar listing unsaved changes, unreachable nodes, missing required params, invalid expressions, refused shapes and a Code node's packages that do not resolve, each row clicking through to the node it names.

**The builder's empty state is a trigger picker over the canvas**, asking how the workflow should start and listing the trigger kinds with one line each: "Pick a trigger — every workflow has exactly one. Place anything else from the palette and this steps aside; the strip below then says the trigger is still owed." Choosing a card places the trigger; placing any other kind from the palette steps the picker aside and leaves the validation strip to say the trigger is owed. While a saved workflow is being read the canvas reads `Loading this workflow…` after the session's short delay, and a read that fails reads `Could not load this workflow` with `Try again`; a new workflow reads neither, because it opens on the trigger picker.

**While a run is live the canvas is a run overlay**: nodes carry their step states, edges carry item counts, and clicking a node opens the inspector on that step's Output.

**One Escape order covers this surface**, one step per press, the topmost open surface first, a surface that is not open skipped, and nothing a person typed discarded: an open menu, popover or confirm; the composer's command list; text in a focused search box; the inspector, its edits kept; the versions pane; a run's step panel; a run's page, back to the runs list; the canvas selection. A field whose Escape already means something keeps it — an inline node rename reverts the name and leaves the field, a search box with text in it clears — and the order does not also run for that press, while a box already empty lets the press fall through to the next step. Two acts here answer to a chord of their own, opening the next run that needs a person and pressing the main answer the open run's blocking step offers, and one more opens this destination from anywhere; all three are ordinary rebindable rows on the console's keyboard settings and are inert while a text field has focus. ### Graph model — nodes, ports, and edges (SA-32)

**Every kind in the catalog is a first-class node.** The document is node-shaped end to end: what the author drew is what is stored, and nothing is compiled into a different shape at save time.

| Node kind | Persisted as | Count | Notes |
| --- | --- | --- | --- |
| Trigger node | the document's own `trigger` slot | exactly one, mandatory | Names how a run of this definition begins (§Entry node and the V1 trigger surface (SA-37)). It never runs as a step: it receives no `stepRunId` and leaves no step record. |
| Every other kind | one entry in the document's `nodes` list | one per node | Carries its kind, the kind version written at insert, its params and its `order`. Among them, the kinds that run an agent or ask a person delegate at run time to the existing run, orchestration, approval and form machinery (§Implementation Notes). |

A node's params carry **references** — an agent definition, a provider account, a tool binding identity, a secret reference — and never a nested node, which is why the agent and the paying account are params rather than wired sub-nodes (§Agent steps (SA-6, SA-8, SA-9)).

**A handle is `main` or `tool`.** `main` carries items between nodes. `tool` carries a capability: an MCP-tool node, a callback-tool node or another agent wired into an agent node's `tool` input becomes callable by that agent, unbounded in cardinality, through each provider's own mechanism: on Claude Code the wired nodes' servers join the agent's set through `mcp_set_servers` at start and after each resume, the process started with `--strict-mcp-config`, and on Codex each is an `mcp_servers.<id>` entry in the conversation's `thread/start` configuration. There is no reserved third type: the account that pays, an approval and the repository each already have one home — the account is the `Account` row under the node's agent, an approval is the `human.approval` node, and the repository is the run's recorded folder or the `path` a git node names — and a handle would be a second control setting the same value.

A handle is identified by one string of the form `"<mode>/<type>/<index>"` — `inputs/main/0`, `outputs/main/1`, `inputs/tool/0` — parsed tolerantly: a string whose type is neither `main` nor `tool` parses as `main`, so a document still opens, and is refused at save with the finding `handle_type_unknown`. One handle primitive therefore renders both data ports and capability ports, and a branch index and connection type are recoverable from the stored edge alone.

**Edges are keyed by node id, never by node name.** A name is a mutable label; every edge, every expression index and every step record resolves through the id, so a rename is a metadata edit rather than a graph-wide rewrite. An edge is stored as its own id plus the source node and handle and the target node and handle, in the document's `edges` list, so the stored bytes are the complete executable graph and no edge lives outside them.

**Which sibling runs first is a number, not a position.** Each node carries an explicit integer `order`, defaulted from the order the nodes were added and edited on the node itself, so moving a node on the canvas never changes what the run does. One traversal ships; there is no second execution order.

### Graph shapes that are refused (SA-33)

The builder refuses these at **edit time** — a connection that would produce one cannot be completed, and a document that already contains one cannot be saved:

1. **A self-edge.**
2. **Any cycle** among `main` handles, walking the outgoers from the target. The one exempt shape is an edge whose target is a loop node's own input, because closing a loop body is the loop rather than a cycle.
3. **A handle-type mismatch**: `main` never connects to `tool`.
4. **A second edge into an input handle that accepts one.**
5. **Any edge whose target is the trigger node.**
6. **An edge out of a terminal kind** — a terminal kind ends the run, and an outgoing edge would assert a successor the engine will never reach.
7. **A `tool` edge into a node that has no `tool` input.**
8. **An orphan node** — one not reachable from the trigger by `main` edges — and **a document with no nodes**, or with no trigger or more than one.

A refusal during a drag is shown as a red connection line plus a one-line reason in the validation strip — never a toast, and never an edge that is created and then removed.

**Edit-time validation mirrors the daemon check; it never replaces it.** Every rule above is re-evaluated server-side at `workflow.definitionCreate`, and the daemon's answer is authoritative. A client that skips, weakens, or predates a rule produces a **refusal**, not a persisted definition — the fail-closed direction. Refusals surface as `workflow.definition_refused` with its finding list (§Fallback Behavior), registered in [error-contracts.md](../architecture/contracts/error-contracts.md) §Workflow; the builder mints no error surface of its own (§Loud-errors discipline (C-12)).

### Tool bindings are references, never inline policy (SA-34)

A node may bind tools. The binding a definition persists is a **reference only**: the scope-qualified binding identity plus a tool name, resolved at step launch through the [Spec-004](../specs/004-provider-driver-contract-and-capabilities.md) §Tool Metadata layer that [Spec-025](../specs/025-mcp-server-configuration-and-governance.md) §Tool-Level Overrides feeds.

A workflow definition **MUST NOT** carry any governance facet inline. Specifically, a tool binding in a definition carries no `enabled`, no `approvalMode`, and no `idempotencyClass` value — those three facets are set only through the Spec-025 override operations, from this machine's own client or any linked device and never from a session, Cedar-gated per [Spec-025](../specs/025-mcp-server-configuration-and-governance.md) §Authorization, and independent per binding scope. A definition that carried them would let a workflow author grant themselves an approval posture the person never granted, and would let a definition exported from one machine silently import a weakened posture onto another. The builder's inspector therefore **displays** the effective facets read-only, sourced live from the governance surface, and offers no control that writes them.

Trust is likewise not a definition concern: an untrusted binding refuses at launch under the Spec-025 trust rules, and the builder shows that state rather than overriding it. This is a distinct mechanism from the content-addressed external-tool pin of §External tool references — content-addressed (C-7): that pin governs a fetched tool artifact's bytes, while a tool binding's identity and trust are governed by the binding's own keyed base-config hash. Neither substitutes for the other.

### Canvas layout is not definition bytes (SA-35)

The **canonical definition** is the JCS-canonicalized JSON body the BLAKE3 content hash already covers. Canvas geometry — each node's coordinates, the viewport's pan and zoom, the sticky notes, and any other purely visual attribute — is **excluded from that body** and from the hash preimage, and so is a node's pinned data. Dragging a node or pinning an output changes no byte of the definition, mints no content hash and creates no version. This exclusion is **hash-scope only, never semantics-scope**: nothing that affects execution may be moved into the layout channel to escape hashing, and every field the engine reads stays inside the hashed body.

Layout is nonetheless **persisted and portable**, because it is part of the document rather than a client's private note. It lives in the document's own `layout` section and is stored in a column beside the definition body, and the file form of §Definition file form — export and import (C-17) carries it as an optional top-level section outside the hashed body. A workflow an agent authored or a user exported therefore carries its picture with it instead of arriving as an arrangement a machine invented.

Where a document does arrive with no layout — written through the SDK, the CLI or an agent — it is laid out **deterministically, left to right**, by the same layered layout library in the daemon and in the renderer, so a definition is never unopenable, opens the same way twice, and looks the same wherever it is opened (§Implementation Notes).

### Definition scope in the builder (SA-36)

The builder loads and saves at every scope of §State And Data Implications. What the surface shows of it is deliberately narrow: **scope is one control in the Save panel, one chip in the catalog's filter row, and one line on a workflow's own row.** There is no scope group, no resolution-order sentence, no copy-on-write banner and no Promote button on either the builder or the Workflows tab.

- **Loading** lists the definitions visible from the current context — the session's own, its project's, and the daemon's `shared` tier — as one list. Resolution still walks `session`, then `project`, then `shared`, most-specific-first, and that is what a run picks.
- **Saving at `session` or `project` scope** creates a new immutable version of that definition.
- **Saving an edit to a `shared` definition is copy-on-write, never edit-in-place.** Opening a `shared` definition and editing it produces a **new definition at the editing context's scope** (`project` by default, `session` if there is no project context), carrying the shared definition's content hash as its parent content hash so provenance is recorded in the existing version-chain field. The `shared` original is untouched, and the Save panel says so in one line before the save.

  Copy-on-write is required, not preferred. Definition versions are immutable by construction — each save writes a new version row and none is ever rewritten — so "editing in place" would mean appending a version to the shared definition, which silently repoints **every project on the daemon** that resolves it, with no signal at any consuming project and no way for a consumer to pin. Copy-on-write keeps the blast radius of an edit equal to the scope the editor is standing in, which is the same containment principle that makes two same-scope-name MCP bindings distinct entries rather than a merge.

- **Promotion `project → shared` is an explicit, separately-invoked action**, never an implicit consequence of saving. It creates the definition at `shared` scope from the promoted version's exact bytes, riding `workflow.definitionCreate` at `shared` scope and therefore clearing the same authorization every `shared`-target create clears (§Core SDK and persistence contracts) — the boundary keys on the target scope, never on the invoking gesture, so no route into `shared` bypasses it.

### Entry node and the V1 trigger surface (SA-37)

Every definition has exactly one entry node — its trigger — and that node records **how a run begins**. V1 ships eight kinds, and every arm is honored at ship time; none is declared and left unwired.

| Kind | How a run begins |
| --- | --- |
| `trigger.manual` | Run now in the builder or on a workflow's row, the chat run verb, or an agent's own run tool. |
| `trigger.schedule` | Cron or every-N, in the trigger's own timezone, with a missed-fire policy of skip or catch-up-once. |
| `trigger.file-watch` | A path, a set of globs and the event kinds to honor, debounced 250 ms. |
| `trigger.webhook` | The daemon's loopback listener, with a per-workflow bearer token and a response mode of immediate or on-finish. |
| `trigger.session-event` | An event-type filter over the session log — a run finished, an approval resolved, an artifact published. |
| `trigger.chat` | A message in a session (§Chat-start surface (SA-38)). |
| `trigger.sub-workflow` | The entry point an Execute workflow node calls, taking the parent's items in and handing the child's terminal items back, the child's run carrying its parent's id. |
| `trigger.error` | Any other workflow failing, receiving that run's id, its error and its last node. |

**A workflow is either enabled or not.** Enabling arms every trigger it declares; disabling disarms all of them, and the workflow stays that way until someone changes it back. A workflow with no trigger that can arm cannot be enabled, and the toggle says so rather than silently accepting. The enabled toggle on a workflow's row acts immediately and reverts visibly where the daemon refuses it.

**Arming is durable; the timer is only a cache.** Each armed trigger holds its own row — kind, config hash, next fire, last fire, whether it is enabled — and the in-process timer is a cache over that row. On daemon start, after the projection rebuild completes, every enabled workflow re-arms from its rows. A fired occurrence carries a dedup key of the workflow, the node and the scheduled instant, so neither a restart nor a double-arm can fire twice. Trigger cursor state lives in the daemon's per-(workflow, node) key-value store and never on the document, so the document stays hashable and safe to edit.

**Two policies decide what a fire does, and they answer different questions.**

- The **missed-fire** policy is per schedule and covers a fire that arrived while the daemon was down: skip the occurrence, or catch up exactly once. The run's trigger record says which happened.
- The **overlap** policy covers a fire arriving while a run of the same workflow is still going. It is one control on the trigger that fires — the schedule node's and the webhook node's alike, because every workflow has exactly one trigger — named **While a run is going**, with three values: **Skip**, the default, where no run is created and the workflow's row and that trigger's own panel show the skipped time and the run that was still going (`3:00 AM skipped · the 2:00 AM run was still going`), so a skip is visible without widening the run status list; **Wait, then run once**, where the next run starts when the current one finishes and several fires that arrived meanwhile collapse into one; and **Run alongside**, where a second run starts regardless. A start a person or an agent asked for always starts, because someone asked. File-watch is already debounced, and a loop's sub-workflow calls are sequential by the loop.

**Runs that start runs form a chain, and the person decides how far one goes.** A run started by a person, a schedule, a webhook, a chat message or a file event nobody's step made begins a chain of its own. A run started by an `Execute workflow` node, by an error trigger, by a session-event trigger on an event another run emitted, or by a file-watch trigger on a path a run's step wrote joins the chain of the run that started it, and carries that chain's first run: `workflow.runRead` returns it as `chainRoot {runId, workflowId, workflowName, startedAt}`. An agent that starts a workflow through its run tool starts a chain of its own, as a chat start does. A run that belongs to a chain an error trigger joined never fires an error trigger when it fails: its failure reaches the person as the `Failed` banner, so no two error workflows can fire each other.

- The engine counts the runs each chain has started, the first run included. When a chain has started as many as `Ask me after one start leads to` allows — one select on the Runtime settings page beside `Stop a run after`, of 25, 100, 500 or 2,000 runs or `Never ask`, on at 100 by default, kept as `workflowChainAskAfterRuns` on `daemon.configRead` and `daemon.configUpdate` (a number, or `null` for `Never ask`) — the next start in it waits for the person instead of starting. The engine raises one approval for the whole chain, on the chain's first run and in that run's session, and every start the chain makes meanwhile waits behind that one question. An `Execute workflow` step whose child is held reads `waiting` with cause `chain`; a held session-event fire creates no run until the answer.
- The question reads `Summarize folder has started 100 runs from its 2:00 AM start. Keep going?`, naming the workflow of the chain's first run, the count and the first run's start in the machine's own clock, with `Keep going` and `Stop them all`. It stands on the first run's page and as that session's question card, and the first answer through either settles both; a held `Execute workflow` step's live line reads `waiting on you · 100 runs from one start`. Once answered it becomes a one-line receipt with no way back, `Kept going at 100 runs` or `Stopped at 100 runs`. `Keep going` starts everything held and does not ask again for that chain; `Stop them all` cancels every run of the chain still going, the first run included, each reading `canceled`. The question rides `workflow.gateResolve` — `approved` for `Keep going`, `rejected` for `Stop them all` — so it is recorded in `workflow_gate_resolutions` like any approval, counted by the bell, bannered as `Waiting on you`, and holds no reservation while it waits. `Never ask` never raises it; the count is still kept.
- Nothing refuses a chain: there is no depth cap and no save-time refusal of a workflow that reaches itself, so a recursive walk finishes, and the number at which the person is asked is the person's.
- A file-watch fire joins a chain when a path in it was written by a step of a run in that chain. The daemon knows those paths from its own records: a `Write files` step's writes, which the daemon makes itself; a capture of the step's checkout before and after every step whose writes come from a process the daemon starts or calls — `Run a command`, a full-tier Code program, `Git`, `Run tests` and an `MCP tool` call — taken directly, with no handshake, into the capture folder (§Interfaces And Contracts); and an agent step's own edits and commands, which the per-edit checkpoint and the command wrapper on Claude Code or the relay on Codex already capture. A write outside the step's checkout, which only the YOLO level or an approved ask allows, is outside every capture; for it, a file-watch event on a path outside the checkout that arrives while a step's process or command is running, or within 1 s of its after-capture, counts as that step's, which can only bring the chain's question sooner. A fire whose paths fall in a checkout whose after-capture is still running waits for it, and each step's written paths are kept in memory until 1 s after its after-capture, then dropped. A fire with paths from more than one chain joins the chain that has started the most runs. A before-capture adds about 105 ms median to the start of such a step on a 5,000-file checkout and 276 ms on 50,000; the after-capture costs about 1 ms per changed file, off the run's path.

Editing a schedule writes a new version and re-arms the trigger only after a successful save. A workflow's own row and the builder's toolbar both read the schedule as off or as the next fire, written in the trigger's timezone and in the machine's own clock.

**One webhook address per workflow, on one port for the machine.** The daemon's loopback listener binds a single configured port — the default one constant chosen from a range no common developer tool uses — and the console's settings hold the one control that changes it. A workflow's address is therefore `http://127.0.0.1:<port>/hooks/<the workflow's id>` and changes only when the user changes the port. The path is the workflow's own id, so two workflows can never share one and the author never types one; the trigger has no `Path` field. The webhook trigger's own panel shows the full address under an **Address** heading with `Copy the address` beside it, and under both the line "One port for every workflow on this machine, set in Settings. The address changes only when you change the port." Where the port is already held at daemon start the listener does not start and nothing moves: settings show the port and that it is in use, and every webhook trigger shows the same reason in place of its address — "Port 7391 is in use, so the listener did not start and this workflow has no address. Change the port in Settings and the address comes back unchanged." — with no address and no copy control while that stands. No ephemeral port, and no silent move to the next free one. On a Windows computer whose daemon runs in a WSL 2 distribution, the listener binds the distribution's loopback, where Windows reaches it only through WSL, so "held" also covers the port on the Windows side: in WSL's default networking, a Windows loopback listener on that port that is not WSL's own relay, or no listener at all because Windows reserves the port; in mirrored networking, the distribution's own bind failing because a Windows program holds it. When the check says held, the daemon closes the listener it opened in the distribution, so nothing listens and the same line stands. `workflow.webhookListenerRead` reads the port and whether it is listening or taken.

**The token sits under `Address` too.** With no token the section reads `Create token`, and every call to the address is refused until a token exists. A token just created or rotated is shown once, with `Copy token`, and is never shown again: only its hash is kept. After that the token reads `Created <date>` — `Created today` on the day it was made — with `Last used <time>` once it has been used, and `Rotate token`, which confirms in place with `The old token stops working at once.` under `Cancel` and `Rotate token`; confirming makes the old token invalid at that moment and shows the new one once (`workflow.webhookTokenRotate`). A local program fires the webhook with `POST` to the address and `Authorization: Bearer <token>`; a call with the wrong token, or any call while no token exists, is refused with `workflow.webhook_token_mismatch`.

**A workflow declares the inputs it asks for on its trigger**: each one named, typed, and carrying the value it starts on. Run now on a workflow that declares any opens a small panel under the control with one labeled field per input, drawn from its type — a checkbox for a yes or no, a list for a choice, a folder picker for a path, a box otherwise — seeded from those values, with the ones that may be left alone marked `(optional)`. Run starts the latest saved version with what was filled in, and a required field left empty says so in place while the panel stays open. A workflow that declares no inputs starts on the press.

**Three daemon dependencies carry this surface** and are recorded with the rest in §Implementation Notes: `croner` computes a schedule's next fire in its timezone; the file-watch trigger uses Node's own recursive `fs.watch` on the pinned Node 24 line, debounced 250 ms, with `picomatch` filtering the globs; and `@dagrejs/dagre` lays out a document that arrives with no layout section — an agent's, the CLI's or the SDK's — in the daemon as in the renderer. The durable next-fire row remains the truth; none of the three holds state that outlives the process.

### Definition file form — export and import (C-17)

A workflow definition has one canonical file form, and it is the file the authoring commitment already names, carrying the schema-version marker the versioning commitment already requires. **No second schema dialect exists**: the file is the definition, and its canonical bytes are the JCS-canonicalized JSON of the parsed document — which is precisely the existing hash preimage, so a definition's content hash is identical whether it arrived through the builder, the SDK, or a file.

The document has exactly two top-level parts:

1. The **definition body** — the hashed, canonical part. Everything the engine reads.
2. An **optional `layout` section** — the canvas geometry, outside the hashed body. An importer that does not understand it, or a consumer that does not want it, ignores it and loses nothing executable. A file written through the CLI or the SDK omits it entirely, and the document it produces is laid out deterministically when it is opened (§Canvas layout is not definition bytes (SA-35)).

Export serializes the current version to that one form, body plus the optional layout section, and writes it to the file the platform's own save chooser picked (`native.showSaveDialog`). Import reads the file the platform's own open chooser picked (`native.showOpenDialog`) and submits the parsed body through the ordinary create path with the ordinary validation, all or nothing, so an imported definition is subject to every refusal rule above and to the ordinary tool-governance resolution — an import can never carry governance state with it, and an import whose schema version is unknown refuses with its registered code rather than being read optimistically. Round-tripping holds in both directions: builder → file → CLI → daemon and CLI → file → builder produce the same definition body bytes and therefore the same content hash.

## Chat-Invoked Start and Start Authorization

Governed by [ADR-027](../decisions/027-chat-invoked-workflow-start.md). Workflows are first-class objects of session chat in both directions: the user reaches them through one command root, and an agent reaches them through a curated set of callback tools. Every caller resolves to the typed operations of §Interfaces And Contracts and introduces no wire contract of its own — the shape [Spec-014 §Addressing](./014-multi-agent-orchestration.md#addressing) already establishes for acts typed in a chat.

**Sixteen callback tools, each with a policy action.** An agent that builds or fixes a workflow needs to read the catalog, read a definition, validate one, read a run and read a step; a half set makes it guess. Each tool registers the same way: a JSON-schema input, an approval category, and an activity record on every invocation. An agent's own tool allowlist decides which of the sixteen that agent holds.

| Tool | Adjudicated as |
| --- | --- |
| `workflow_kinds`, `workflow_list`, `workflow_read`, `workflow_runs`, `workflow_run_read`, `workflow_step_read`, `workflow_validate` | reads, gated on the session itself |
| `workflow_create`, `workflow_update`, `workflow_schedule_set`, `workflow_enable` (which takes the enabled flag, so it serves both the enable and the disable verb) | `Action::"workflow::author"` |
| `workflow_run`, `workflow_node_execute` | `Action::"workflow::start"` |
| `workflow_cancel` | `Action::"workflow::cancel"` |
| `workflow_resume` | `Action::"workflow::resume"` |
| `workflow_results_post` | `Action::"workflow::author"`, with the session derived from the invoking turn and never tool-supplied |

`workflow_results_post` never takes a session as an argument: the daemon derives it from the invoking turn's own session and validates it, so a forged target cannot be reached (§Discussion Integration Path). Registering each action in the Cedar schema is Spec-010 and Plan-010 surface, not this spec's; while the daemon's approval service is not running the callback-tool registry is withheld at spawn and a stray invocation is answered `denied`, and it is offered once that service runs. Each tool reaches a provider over the one per-session tool server of §Interfaces And Contracts.

**The tools' input schemas are generated, never written by hand.** The `workflow_create` and `workflow_update` input schemas are generated from the shared document schema with Zod's `z.toJSONSchema`. Claude Code keeps the workflow tools behind its tool search until the model loads one, then sends the schema to the model unchanged, `$defs` and the recursive `$ref` included; once loaded, the schema's whole text counts against the session's context — 100 KB fits, and 1 MB refuses the turn on a 200K window, which compaction cannot recover — so the schema stays as small as the document's shape allows. A Codex model sees the schema as a TypeScript declaration typed two levels deep, with no patterns, lengths or bounds but with each field's `.describe()` text, so every constraint the model must meet is also stated in its field's `.describe()` text, and the daemon's validation at write catches a bad deeper node.

### Chat-start surface (SA-38)

**One command root, thirteen verbs.** The session composer registers exactly one root, `workflow`, and under it: `run`, `list`, `runs`, `results`, `open`, `create`, `edit`, `fix`, `schedule`, `cancel`, `resume`, `enable` and `disable`. One root is what keeps the command namespace collision-free, and verbs are additive under it; no verb is ever repurposed. Typing `/` in the composer lists the console's commands with `/workflow` among them, and typing `/workflow ` lists the thirteen verbs with one line of help each.

- A verb's name argument autocompletes over the definitions the caller can already see, through `workflow.definitionList`, and resolves most-specific-first — the session's own, then its project's, then the daemon's `shared` tier — so enumeration discloses nothing the caller could not already list. With no workflow saved, the second level reads `No workflows yet`, the Workflows tab's own empty line.
- Most of the verbs are direct, and each acts as its control would: `/workflow list` opens the Workflows tab, `/workflow runs <name>` opens the Runs tab with its workflow filter set to that workflow, `/workflow open <name>` opens it in the builder, `/workflow run` lands the progress row and `/workflow results` the results row. `enable`, `disable`, `schedule`, `cancel` and `resume` each land one flow row in the system message's shape saying what was done — `Enabled <name>`, `Disabled <name>`, `<name> runs <the schedule in words> · next <time>` or `<name> no longer runs on a schedule`, `Canceled <run>`, `Resumed <run>` — and a refused one lands the daemon's own words in that row, pressing nothing else. `create`, `edit` and `fix` are not direct: they compose a message to the session's current agent carrying the instruction plus a structured hint naming the intent and, where one exists, the definition, so the agent knows to reach for its own workflow tools. The reply lands as an ordinary chat message carrying a definition row or a results row.
- An unrecognized verb lands one flow row reading what the word takes. It presses nothing and never composes into a message.
- An agent's tool call that Cedar denies is answered denied and lands as an activity record, and the chat shows that refusal rather than a silent failure.
- Interception is total for the console's own words: `/workflow` and its verbs are executed by the client and never reach a session message, an agent's context or a provider turn, on any path. Leading-`/` text the console does not own is not the runtime's to hold (§Command interception — the reserved `/` prefix (C-18)).

**No surface here shows internal code syntax.** Every error code, refusal reason, status, event kind and enum value renders as words in sentence case, so a wire pair like `agent.resolution_refused · account_unavailable` reads "Sidekick resolution refused · Account unavailable", the label writing the screen word for the `agent` root, and `workflow.start_denied` reads "Workflow start denied", each followed by the daemon's message in plain words. Tool names, policy actions and node kinds are wire spelling too: each daemon tool and each policy action registers the label a person reads — `workflow_results_post` reads "Post workflow results", and a refusal under `Action::"workflow::author"` reads "Needs permission to author workflows" — and the inspector's kind chip shows a kind's display name and version, never its id. An unlabeled code falls back to its own sentence-case words. Only what a person or an agent wrote or would type stays as written: model ids, file names and paths, commands, diffs, log output and prose. A parser's or a runtime's own error text is a code message and never reaches the screen — an import that does not parse says what is wrong in plain words and names the line.

### Command interception — the reserved `/` prefix (C-18)

Leading-`/` input in the session composer sorts into three classes, and exactly one of them belongs to the runtime. Which class a word falls into is decided by **who holds the value it would change** ([Spec-004 §The provider command and skill surface](./004-provider-driver-contract-and-capabilities.md#the-provider-command-and-skill-surface) fixes the three and this rule consumes them):

- **A word the console owns is intercepted and executed by the client**, pressing the console control that owns the value or doing the console's own work through the daemon. The text never composes into a session message, an agent's context, or a provider turn — under any path, including the steer-through-composer surfaces that share the input box. A provider's own command for something a console control already holds is not forwarded either, because forwarding it would move the provider's state and leave the control reading the old value. `/workflow` and its verbs are console words, which is what makes a chat-borne start collision-proof by construction rather than by convention.
- **A word the bound provider's own enumeration carries that the console does not own is forwarded to that provider exactly as typed**, so the provider's own client dispatches it as it would in that provider's terminal. It is offered in the command list marked with the provider it came from, it is offerable and dispatchable only through the binding it was read under, and the runtime asserts no effect it did not witness.
- **Anything else is sent as the user's own prose**, with no press and no console message, neutralized at the driver's outbound frame boundary as [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior) requires, and the provider answers it as it would in its terminal: one provider's client replies that the command does not exist and spends a turn doing so, the other reads the words as prose. **There is no literal-slash escape and no unknown-command refusal of the product's own invention** — a word no row matches is a word going to the provider, not a word being refused.
- A console word whose argument its own control cannot take — a name the control does not offer, a value outside its range — answers with one flow row saying what the word accepts and presses nothing. It is never forwarded as text instead.
- The namespaces never overlap. `@` names a file or another session, never an agent or a workflow; an agent is named from its row in the `/` list, which writes the provider's own form for that agent into the message ([Spec-014 §Addressing](./014-multi-agent-orchestration.md#addressing)); and `/workflow` is the one command root for workflows. A definition name occupies argument position only (`/workflow <verb> <name>`), so no workflow name can ever collide with a command verb.

**The prose class rests on the driver boundary.** Neutralizing leading-`/` text where it is carried as prose is specified in [Spec-004 §Required Behavior](./004-provider-driver-contract-and-capabilities.md#required-behavior) — transport-only neutralization at the driver's outbound frame boundary, a closed frame-origin discriminator whose unknown arm neutralizes, and a runtime tripwire that fails the turn rather than letting a provider's zero-turn success be recorded as a completed one — and [Plan-004](../plans/004-provider-driver-contract-and-capabilities.md) builds it. The same boundary governs the steer and queue paths, which carry free text into provider turns from outside the composer. Spawning a provider with its command dispatch disabled is not the mechanism: a provider flag is the provider's promise, not the daemon's guarantee, and may be set only as defense in depth.

### Start authorization (SA-39)

Starting a workflow run is adjudicated **per start** as the named Cedar operation action `Action::"workflow::start"`, in the `Spec-010` named-operation-action shape (the `Action::"intervene"` and `Action::"dispatch::<capability>"` precedents) — deliberately **not** a new approval category. A start traverses no approval pipeline, mints no approval row, and is never remembered: remembered grants key on approval category, so a category-shaped grant would silently cover every definition on the daemon — the wrong width for a per-definition operation. The default, mirrored as one row in the security-architecture Permission Matrix: the user may start workflow runs from any linked device, and an agent may start one only through its curated `workflow_run` or `workflow_node_execute` callback tool under the same adjudication.

One rule governs the user, their agents and the triggers the user arms: the CLI path, the desktop path, the chat surfaces of SA-38, the `workflow_run` and `workflow_node_execute` callback tools, and every run a trigger fires all adjudicate the same action. An agent's principal is the invoking turn's effective principal under the Spec-010 actor-axis rules — consumed here, authored there.

**Principal resolution.** The product has one user, and every start's principal is that person, as a **daemon-resolved value, never a client-supplied body field** (the admitting-principal-carrier class). On the local daemon socket every JSON-RPC caller — the desktop app, the `/workflow` verbs its composer intercepts, and the CLI — binds to the daemon's recorded node-owner user, who is that one user (the transport rule the contract doc records), so a chat-borne start reaches the daemon exactly as a desktop start does and resolves the same way. A linked device is a client of the same user's account and drives the same sessions through Remote Control, so a start from any linked device resolves to that person too. An agent's start through a tool that takes this action (`workflow_run`, `workflow_node_execute`) resolves to the invoking turn's effective principal, as above, and is adjudicated on that tool invocation. A run a trigger fires — a schedule, a webhook, a file-watch, a session event, an error trigger, or the sub-workflow entry an `Execute workflow` step calls — is a start too: arming the trigger is judged under `Action::"workflow::author"`, and each fired run is judged under `Action::"workflow::start"` when it fires, its principal the one user and its arrival path the trigger that fired, which is what the run's started-by shows, so a policy changed after arming still stops the run. The matrix row therefore tells apart how a start arrives — the person directly, an agent through its tool, or a trigger — and never one person from another. A start whose principal the daemon cannot resolve **refuses on every path**, a fired trigger's included — fail-closed, with the refusal below — and never runs under a substituted or default identity, because a placeholder identity reads as a real caller to the policy check.

**Refusal.** A denied start — a principal the matrix does not admit, a principal the daemon cannot resolve on any path, or a session the resolved starter cannot see — refuses with `workflow.start_denied`, registered in `error-contracts.md` §Workflow. The arms are ordered and their disclosure is scoped: the principal adjudication runs first and may refuse with a message naming the denied action — the matrix is public surface, so naming it leaks nothing — and the session validation runs second, only for a start the matrix admits, with its not-visible and nonexistent-session outcomes collapsed into one byte-identical message, so a denied caller — an agent leg above all — learns no session-visibility or session-existence fact (the `runtimenode.permission_denied` shape: one code, distinct messages where nothing leaks, collapse exactly where a distinction would). The refusal is a registered code, as §Loud-errors discipline (C-12) requires.

**Cedar registration is upstream surface.** The action literal sits in [Spec-010 §Implementation Notes](./010-approvals-permissions-and-trust-boundaries.md#implementation-notes)' named-operation-action enumeration, and the principal carrier is the admitting-principal-carrier class of [api-payload-contracts.md §Authenticated Principal And Authorization Model](../architecture/contracts/api-payload-contracts.md#authenticated-principal-and-authorization-model); this spec names the semantics and consumes the adjudication (`PermissionCheckService`), authoring no Cedar schema entry.

## Implementation Notes

- Workflow authoring belongs in the product surface, but workflow execution still uses the same run, approval, and artifact primitives as free-form sessions.
- Version immutability simplifies replay and support.
- Parallel steps come only from branches the graph draws, admitted by the memory gate — no implicit concurrency.
- Persistence uses a LangGraph-inspired checkpoint pattern on the existing SQLite store (Spec-013), with the normalized-tables-over-JSON-blob decision documented in State And Data Implications. No external workflow engines (Temporal, Restate) — contradicts ADR-002 (local execution).
- One execution model at V1 per C-11: local daemon runs workflows locally. Do not ship a `local | queued | remote` enum at V1.

**The kinds that run an agent or ask a person compile down at run time, not at save time**, which is what keeps the document node-shaped end to end. Their executors reimplement nothing:

- The `agent.run` kind calls the existing run admission with the definition id from its `agent` param (the one param its kind spec types `agent`), and with the provider account, posture and tool allowlist resolved from that definition under any per-node binding override.
- The `agent.multi-agent` kind runs a lead and its helpers in the run's session through the existing orchestration path, `orchestration.runCreate`.
- The approval kind raises a request through the existing approval pipeline and its Cedar check.
- The form kind writes through the existing form-state store.

The park-and-resume rules for provider limits apply to these steps unchanged, so a spent account parks the step and the run resumes itself when the account recovers (§Provider-limit pacing and durable resumption (SA-40)). The step record is a projection over the events those pipelines already emit.

**One process, a thread per quick step.** Each quick Code step runs in its own interpreter instance whose WebAssembly memory is created with the step's budget as its maximum, and the instance is discarded after the step: the interpreter's own memory limit does not hold (strings reached about 1.9 GB and objects about 1.2 GB within the 5 s deadline under a 256 MiB limit), a shared instance never gives WebAssembly memory back, and an instance that ran out of memory is unusable, so none is reused. Each quick step runs on a `worker_threads` thread of its own, started for the step and ended with it. The daemon compiles the interpreter once, when it starts, and hands each thread that `WebAssembly.Module`; each thread still creates its own capped `WebAssembly.Memory` and discards it (a thread compiling its own copy costs more when twenty start together, and twenty threads starting at once hung in 8 of 160 runs on Node 24.18.0 with per-thread compiles and in none with the module compiled once). Into the thread go the program, the step's budget and deadline, the compiled module, a four-byte shared cancel flag and the step's input — an inline input as one buffer of its stored JSON text, transferred rather than copied, and an input kept as an artifact by its id, which the thread reads from disk itself, so the daemon's thread never serializes or copies a large input. Out come the output as JSON text — one over 64 KiB written by the thread to a file and handed back by path, taken in as the step's artifact — the step's log lines, and the size of the interpreter's memory at the end, which is its peak. No binding to the host crosses in either direction. The interrupt handler reads the cancel flag and the deadline, so a step ends when its deadline passes, when its run ends or when the person cancels; a thread that has not answered 250 ms after that is ended with `terminate()`. The thread's own JavaScript heap is capped with `resourceLimits` at the reservation's part beyond the budget, so a defect in the step's host, never the step's program, ends that thread with `workflow.step_thread_failed`, reason `out_of_memory`, and never grows the daemon. A thread that is not running 5 s after it was started fails its step with reason `start_timeout`; one that exits without an answer, with reason `exited`. A thread that never started cannot be ended, so its reservation stays held until the daemon restarts, and because it also keeps the daemon's process from exiting, the daemon's supervisor stops the daemon hard once it has been asked to stop: after the flush, SIGTERM, and SIGKILL 2 s later. A deadline cut reads `failed · timed out` (`workflow.step_timed_out`, cause `step_timeout`), and a program over its memory budget keeps `workflow.code_over_budget`.

## Pitfalls To Avoid

### Structural pitfalls

- Mutating running workflow definitions in place.
- Hiding workflow step outputs outside the session timeline.
- Treating workflow pause as a UI-only banner with no durable execution state.
- Using mutable tags instead of content-addressed pins for external tool references — directly opens the CVE-2025-30066 class.
- Recording sibling cancellation in async callbacks instead of at a deterministic synchronous tick checkpoint — reintroduces the non-determinism class observed in Temporal Java SDK #902.
- Collapsing a `human.approval` step's approval and a human step's `human_step_contribution` submission into one category, or routing a question an agent asks through the approval pipeline — a question and an MCP elicitation are one `question.asked` record, answered outside it, so the split is load-bearing.
- Recognizing a provider usage-limit refusal by matching message text, an error string, a rate-limit window name, or a model id. Prose is not a contract; it changes without a version bump, and a matcher that silently stops matching converts a park into a burned retry ladder and then a false `failed` verdict, with no signal that anything changed (C-19).
- Holding a resume schedule in an in-memory timeout. A timeout is lost at the exact moment it is most needed — a daemon restart — and a run whose only route forward died with the process is stuck without anything having recorded that it is.
- Computing resume jitter with a modulus. When the intended span exceeds the operand's range the modulus never wraps, so the real spread collapses to a fraction of the declared width while every bound assertion still passes — the test proves the value is inside the window and proves nothing about the distribution.
- Arming a schedule from a window whose provenance is `model_default` or `estimated`. Those values are the driver's honest statement that the number is a guess; scheduling against a guess either fires into a still-spent account or holds a run that could have run, and both look like the engine knew something it did not.
- Letting the attention record gate work. A correlation record consulted by start, resume, or retry becomes an availability lock, and a stale one then makes a run unstartable after the account has quietly recovered — the "protection that isn't" class of C-12 in its most expensive form.
- Writing the engine's park cause into a step output, an artifact, or an agent-visible context. Engine prose arriving through a model-output channel reads as something a model said, and a step output is immutable truth (SA-16), so the sentence is unretractable once written.
- Re-pinning a run's frozen definition version silently, or as a side effect of an ordinary resume. A run whose early steps executed a definition no longer recoverable from the run cannot be replayed, verified, or explained.
- Re-pinning while any attempt of the run is in flight — the resume **continuing one** rather than entering a step fresh, or a re-pin admitted through one branch's fresh entry while a parked parallel sibling still holds one — the same class as the silent re-pin above, reached by a caller who asked explicitly. The units already dispatched were launched from bytes the run would no longer be pinned to, so neither the attempt's inputs nor the outputs it returns remain explainable by the version the run's record names, and the person who asked for a repair is told it succeeded over a run that repaired nothing.
- Clearing a durable resume schedule because its timer fired, rather than because the run left the park. A fire that re-checked and then failed to transition the run leaves a parked run whose only route forward has been deleted, with nothing recording that it is stranded.

### Security invariants (non-conformant if violated)

Engine implementations violating any of the following are **non-conformant**. Each invariant is a testable contract requirement; concrete CVE-reproducer corpora and test categories are specified in [Plan-015 §Testing](../plans/015-workflow-authoring-and-execution.md) (SA-29, SA-30, SA-31 — implementation detail, not spec surface).

- **I1 — argv-only execution.** The engine **MUST NOT** accept a shell-string command form for user-templated content. No `shell=true`, no `/bin/sh -c "..."` over author-controlled fields. All commands execute via argv-list spawn only. Closes [GitHub Actions — Script-injection guidance](https://docs.github.com/en/actions/concepts/security/script-injections), [n8n CVE-2025-68613 (CVSS 9.9)](https://github.com/n8n-io/n8n/security/advisories/GHSA-v98v-ff95-f3cp), and [Airflow CVE-2024-39877](https://nvd.nist.gov/vuln/detail/CVE-2024-39877) in one architectural choice.
- **I2 — every evaluation happens inside a boundary, and none of it happens on the host.** The engine **MUST NOT** hand a workflow-definition string to a host template engine or to any host evaluator — no Jinja2, no `${...}` interpolation, no `eval` of document text, and no expression that can reach a host API. Document text is evaluated in exactly two places. An **expression** runs in the sandboxed-by-construction evaluator of §Expressions, over a closed binding namespace, per item, in the daemon, under a per-evaluation time budget that aborts. A **program** runs only inside a boundary enforced either by the interpreter or by the operating system at the run's execution posture — the quick tier's WebAssembly interpreter under a memory budget and a deadline with nothing bound into it that it was not given, or the full tier and `developer.shell` inside the provider's own sandbox at that posture — and **MUST NOT** run unsandboxed on the host at `sandboxed`, where a sandbox that cannot start refuses the step. Anything else is the template-injection class this invariant closes.
- **I3 — typed approver capability.** The engine **MUST NOT** treat approver permission as a submitter string or as "whoever has `Read`". Approver principal is a typed capability bound to an identity (Spec-010). No override settles a gate outside that check: a gate's outcome is `approved` or `rejected`, and nothing else. Anti-pattern: Jenkins Pipeline Input Step historically approved on `Item/Read` (CVE-2017-1000108, fixed in plugin 2.8 on 2017-08-07) and still silently bypasses the `submitter` allow-list for holders of `Jenkins.ADMINISTER` with no audit emission ([Jenkins SECURITY-576 advisory, 2017-08-07](https://www.jenkins.io/security/advisory/2017-08-07); [`InputStepExecution.java` `canSettle`](https://github.com/jenkinsci/pipeline-input-step-plugin/blob/master/src/main/java/org/jenkinsci/plugins/workflow/support/steps/input/InputStepExecution.java); [JENKI16 Won't Fix](https://issues.jenkins.io/browse/JENKI16)).
- **I4 — secrets by reference only.** The engine **MUST NOT** accept inline secret material in workflow definitions. Secrets are referenced as `secret://<scope>/<name>` and resolved at step launch, from the value sealed in the operating system's keychain ([ADR-038](../decisions/038-workflow-secrets-in-the-os-keychain.md)), into env / stdin / named-file fd — never argv. Logging redaction is defense-in-depth on top, not primary control. Closes [tj-actions/changed-files CVE-2025-30066](https://nvd.nist.gov/vuln/detail/CVE-2025-30066) runner-memory-via-argv class. The redaction-is-defense-in-depth stance is motivated by [Airflow secret masker issue #54540](https://github.com/apache/airflow/issues/54540) Vault masking regression (Airflow 3.0.0-3.0.4).
- **I5 — content-addressed external references.** The engine **MUST NOT** resolve external tool references by mutable tag. References carry hash pins (`codex@v1.2.3#sha256=...`). Closes CVE-2025-30066 retroactive-tag-repointing class.
- **I7 — append-only approval history.** The engine **MUST NOT** permit mutation of `workflow_gate_resolutions` rows. Workflow-definition edits are a separate audit entry. Replays use at-execution-time policy — not current definition (Temporal's Event History is the reference pattern).
- **I1–I7 testability.** Every invariant has ≥1 test that fails when the invariant is violated. Test categories and CVE-reproducer corpora are specified in Plan-015 §Testing (SA-30).

### Terminology discipline (SA-17 / C-12)

- Use **"workflow"** (not pipeline / flow), **"node"** for one element of a workflow's graph, **"step"** for one node's execution in a run (not stage / task), and **"artifact"** (not output / capture when persisted). **"Phase"** survives only in the fixed names of the daemon's `human_phase_form_state` table and the contracts' `workflow_phase_lifecycle` events; in prose the unit a run executes is a step, and an approval is a `human.approval` node, never a gate type.
- Airflow Datasets→Assets, SubDAG→TaskGroup, execution_date→logical_date terminology churn is the precedent for cost of late rename ([Airflow — Upgrading to Airflow 3](https://airflow.apache.org/docs/apache-airflow/stable/installation/upgrading_to_airflow3.html)).

## Acceptance Criteria

- [ ] Workflows can be authored as versioned node-graph definitions with a schema version marker; the checks of §Graph shapes that are refused (SA-33) reject an invalid definition at author time.
- [ ] Every node kind of the catalog executes, `agent.multi-agent` as an orchestration run in the run's session.
- [ ] Every approval — a `human.approval` step and a chain's question, the only two gate kinds — resolves through the approval pipeline, scoped to the run's session, and is recorded in `workflow_gate_resolutions` keyed by the run, with the step's `nodeId` for a `human.approval` gate and no node for a `chain` gate; a form's answer writes no gate row (SA-7).
- [ ] Workflow runs survive reconnect and daemon restart with step state intact; replay reproduces deterministic `stepRunId` sequence (SA-21).
- [ ] A fan-in joins through `flow.merge` in each of its modes; a run that ends failed or canceled cancels every running sibling branch, and `First to arrive` cancels the branches still running, each recorded at a deterministic tick boundary (SA-4).
- [ ] Memory-gated admission holds a ready step while the machine has no room for its reservation, and the step reads `waiting-memory`; at least one step is always admitted; ready steps are admitted in the order they became ready and the head of the line is never passed over; a step waiting on a person or parked on a provider limit holds no reservation; a node's reservation moves from its kind's starting figure to the peak that node reached on this machine.
- [ ] A full-tier Code node and a shell-command node run under the run's execution posture, and at `sandboxed` a sandbox that cannot start refuses the step instead of running it unprotected (I2).
- [ ] The `max_duration` and `max_retries` bounds hard-fail with preserved `failure_reason`, and a chain that reaches its count holds its next start for the person's answer (SA-1, SA-2).
- [ ] Workflow step outputs are addressable after the run completes; a retry produces a new step record and rewrites none (immutability preserved — SA-16).
- [ ] A human step's `Timeout` is empty by default, meaning the step waits until it is answered; set, it is a durable deadline on the step's row, and at that instant the step fails with `workflow.step_timed_out`, cause `step_timeout`, and its `onError` routes it (SA-10).
- [ ] Security regression battery covers I1–I7 invariants with CVE-reproducer corpora (test surface lands in Plan-015 §Testing per SA-30).
- [ ] Every workflow event type emits in the Spec-005 envelope with correct ordering invariants.
- [ ] A parked step is renderable from one `workflow.runRead` response, and a step that resumed past an earlier park carries no park members on that response (§Park surfacing on the read model (SA-44)).
- [ ] A canceled run's status and its cleared live park columns rebuild from the log alone, with `workflow.canceled` as the sole durable producer of the `canceled` status (§Operator run control (SA-45)).
- [ ] Secrets referenced via `secret://...` never appear in argv, logs, artifacts or the daemon's database, and a reference outside a sensitive field refuses at save (canary-secret regression — I4).
- [ ] Every `/workflow` verb intercepts at the composer and never reaches a session message, an agent's context or a provider turn on any path, the steer-through-composer surfaces included; a slash word the bound provider's own enumeration carries is forwarded to that provider exactly as typed and only through the binding it was read under; anything else is sent as the user's own prose over the neutralized driver boundary, with no escape sequence and no refusal of the product's own invention; and a console verb given an argument its control cannot take answers with one flow row and presses nothing (C-18).
- [ ] Every start path — CLI, desktop, chat command, the `workflow_run` and `workflow_node_execute` callback tools, and a run a trigger fires — adjudicates `Action::"workflow::start"`, a fired run when it fires; a matrix-denied principal, a principal the daemon cannot resolve on any path, and a session the resolved starter cannot see each refuse with `workflow.start_denied` — principal adjudication first, session validation only for a matrix-admitted start (SA-39, SA-38).
- [ ] Every workflow callback tool is withheld at spawn while the daemon's approval service is not running; a stray invocation answers `denied`, never `completed` and never silence (SA-38).
- [ ] A usage-limit refusal is recognized from the typed driver signal alone and never from message text; it parks the step immediately, consumes no `max_retries` attempt, mints no new `stepRunId`, and adds nothing to its chain's count — including when no reset window was reported (SA-40, C-19).
- [ ] A durable `resumeAt` is armed only where the typed refusal's reset boundary is stamped provider-reported, is jitter-offset by a scaled — never modular — pure function of `workflowRunId` that replay reproduces, survives daemon restart via a post-rebuild re-arm, is never armed at or past the run's `max_duration` deadline, and is cleared by every transition out of the park (SA-40).
- [ ] Concurrently parked runs sharing a provider-account attention key present as one attention record; a mixed set of failures is never folded into a usage-limit record; and no start, resume, retry, or schedule fire consults the record — a run stays startable after its account recovers (SA-40).
- [ ] Every parked run is cancelable from every waiting state without precondition or wait, cancellation clears the durable schedule in the same unit of work, and the parked step's record with its `parkReason`, bounded `parkCause`, and completed outputs survives the cancel intact (SA-42).
- [ ] The person resuming a parked run may re-pin it to the definition's current version explicitly; the re-pin is recorded on `workflow.resumed`, never fires from a timer or an ordinary resume, never re-runs or rewrites a completed step output, and refuses at each of its refusal points — a run that is not parked, a repair requested while any of the run's attempts is still in flight (the resuming step continuing one rather than entering fresh, or a parked parallel sibling holding one), and a target version that cannot account for the steps the run already completed (SA-41).
- [ ] The engine event record is on for every run with no flag to turn it on, carries `workflowRunId` / `stepRunId` / `attemptNumber` / sequence on every record, carries no secret material and no raw provider prompt or completion text, and is read by no replay, verification, projection-rebuild, or audit path — its expiry degrades diagnosis only (SA-43).

## Open Questions

The one entry here is open against this spec, and it is narrow — it asks how a value this spec already constrains is rendered, not what the value must be. It gates no Required Behavior row: §Deterministic identity (SA-21) is satisfied by any rendering that stays a pure function of the digest, so the determinism row holds whichever rendering is chosen.

- **How a derived `stepRunId` is rendered into its text form.** §Deterministic identity (SA-21) fixes the preimage and fixes that the identifier is totally derived — but not the encoding of the digest into the column's stored characters. The obvious candidate, "ULID-shaped so the column type is unchanged," is not self-consistent as usually stated: Crockford base32 carries 5 bits per character, so a 26-character rendering spans 130 bits, and a ULID reaches 26 characters by padding its 128 bits and constraining the leading character — a rendering rule that must be written down rather than assumed. The encoding is deliberately left open: picking one is a design decision of the same class as the scope domain, and the identifier is a durable primary key, so the choice is one-way. Whichever encoding is chosen must state the digest function's output width, the truncation or padding rule, the alphabet, and whether any leading-character constraint applies. Until it is, implementation surfaces must describe the column as a derived opaque identifier and must not call it a ULID.

- [Node — `process.availableMemory()`](https://nodejs.org/docs/latest-v24.x/api/process.html#processavailablememory) — the call the admission gate re-reads each tick. From Node 24.16.0 it sums free, inactive and purgeable pages on macOS; on Node 22 it returns free pages alone, the same number as `os.freemem()`, which is why the daemon and the CLI run on Node 24.16 or later.
- Measured on an Apple-silicon Mac, 2026-09-21: a TypeScript program naming its package in its import line and a Python program naming its packages in its own inline metadata block each ran with their packages inside `codex sandbox` on the workspace profile, with home-directory writes and the network blocked, and the sandbox cost about 0.02 s per run. Linux and Windows are unmeasured.
- Measured on macOS and on Linux (Debian 12 in a container): the lock, install and run of a full-tier Code step under both providers' sandboxes and with no sandbox, the writes each allows, and clearing each package cache — installed steps kept running, a later run fetched nothing, and the other cache and the managed Python were untouched. Windows is unmeasured, and so is either sandbox started by the daemon on an Ubuntu 24.04 desktop.
