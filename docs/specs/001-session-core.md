## Purpose

Define the minimum session contract that all user, device, and agent behavior must build on.

## Scope

This spec covers session identity, default session structure, session creation, and what another of the user's devices receives when it opens a session.

## Non-Goals

- The machine's registration with the control plane
- Detailed run state or queue semantics

## Required Behavior

- The system must treat `Session` as the primary session container.
- Every agent, run, queue item, artifact, and approval must reference exactly one session id.
- Creating a session must produce a durable session record before any run starts.
- Opening an existing session on another of the user's devices must reach the same session id and existing transcript; it must not silently fork the session.
- A session must support concurrent devices, agents, and runs.
- Session identity must remain stable across reconnect, client restart, and transport changes.
- The Local Runtime Daemon on the machine that runs a session is that session's one store: the session record, its transcript and its execution state live there. The control plane holds no session record; a device reaches a session only through its machine over the relay.
- **Two session shapes.** A session is either a chat or a project ([ADR-030: Two Session Shapes](../decisions/030-two-session-shapes.md)). The shape is decided by what the session is bound to, never by a mode flag, and it is a durable column on the session record rather than something inferred from a path prefix. A chat session is bound to a daemon-owned, git-initialized managed workspace, one per session, which the daemon's managed-workspace service creates (`ManagedWorkspaceService.create`) as a step of `session.create`, and of `session.fork` for a chat, kept under the daemon's own state directory at `<home>/.ai-sidekicks/workspaces/<session-id>` and registered as a mount whose origin is marked managed. A project session is bound to a repository the user attached, and a project is defined against that mount's origin rather than against a folder existing on disk: attaching a folder that is already a project opens the project it already is, and the daemon refuses to mint a second project record for the same origin, so no path through the product can create a duplicate. A session the person runs in their own terminal is not one of these sessions: it has no shape, no row in the sessions list and no window here.
- **A chat becomes a project in place.** `Convert to project…` names the repository in a typed path field with no `Browse…`; the typed text travels as data and the daemon checks it. Converting attaches that repository and copies the managed workspace's files into it, and from then on the session is a project session: the same session id, the same transcript, the same history. Nothing beyond that copy is migrated and nothing is auto-merged, and the managed workspace and its own history are kept rather than deleted. The conversion changes the session's binding; it never mints a second session. **It never overwrites a file the repository already has:** such a file is not copied and stays in the kept managed workspace. The one system message the conversion appends to the session's transcript counts what was copied and what was not — `Converted to project · <n> files copied · <n> not copied`, or `Converted to project · <n> files copied` where nothing was skipped, which has nothing to open — and opens to one line per file that was not copied with its reason, such as `README.md · the repository already has this file`, each line opening the chat's copy; the daemon also sends the session's agent one short message naming those files, which lands as the `Note to the sidekick` system message, so the agent can say so and offer to bring them across. Nothing is quietly replaced and nothing is quietly lost.
- **A managed workspace at end of life.** A chat's managed workspace is deleted whole when its session is purged: the service's one purge, `daemon.retentionPurge` (`Delete old data`), deletes it through the managed-workspace service (`ManagedWorkspaceService.delete`). It is retained when the session is archived, and excluded from the archive sweep. Provable destruction of its contents is never claimed.
- **Forking a session.** A fork mints a new session of the same shape from a message anchor in the parent. The new session carries the transcript prefix up to and including that message, with live timers settled and streams stopped in the copy, and the parent is recorded on the new session's own creation record rather than as a second record beside it. A chat fork stays a chat and binds a managed workspace of its own; a project fork lands on a new worktree taken off the parent's current worktree at its current commit. The session's posture — its permission level, its model and its effort — and its tool configuration carry over. The parent is untouched: a fork never changes the parent's session id, its transcript or its runs. The composer word `/fork` forks with its end at the session's newest item of either side, the person's or the agent's, so a `/fork` typed after a reply keeps that reply. The copy of the conversation is the provider's own fork, reached through the driver's `forkConversation`: Claude Code's `--resume-session-at` with `--fork-session`, and Codex's `thread/fork` at an inclusive turn. **Fork and undo are two things.** A fork makes a second session and is never a rollback; undo stays inside the same session and puts back the conversation by the provider's own conversation cut and the files by the daemon's own checkpointer ([Spec-013 §Required Behavior](./013-persistence-and-recovery.md#required-behavior)).
- **An idle Claude Code session sleeps; nothing else of the runtime's stops a provider process.** The daemon stops the process of a Claude Code session it started once the session has been idle for 30 minutes, and only when the stop would end nothing: no turn running, no message queued or waiting to be taken, no approval or question open, no background task running (the last `background_tasks_changed` set Claude Code reported is empty), no wake-up or session-only scheduled job the provider holds, no side question running and no voice call. Wake-ups (`ScheduleWakeup`'s `scheduledFor`) and session-only jobs (`CronCreate`, until its last run or its `CronDelete`) are kept from their tool results, because they are never in that set and die with the process even across a resume; a session holding one stays awake until two minutes after it fires. The daemon checks every 5 minutes and again under the session's lock at the moment of the stop, so a message or a provider event that arrives in between keeps the session awake; the stop closes the process's input and waits for it to exit. The next message to the session, from the person, another agent or a workflow step, wakes it through Claude Code's own resume by id, on the same conversation, account, folder, settings and permission level, and is delivered once the woken process is ready (about 1.2 s, measured on Claude Code 2.1.283). Nothing is shown: no banner, no row, the same session; a sleep is not a provider exit. An archived session sleeps like any other. Claude Code's own idle exit, `CLAUDE_CODE_EXIT_AFTER_STOP_DELAY`, is never set: it exits with a wake-up pending and loses it, and it announces nothing. Codex is never slept, because its conversations share one service per account. A session the person runs in their own terminal is never stopped by the daemon. Beyond the sleep the runtime never stops a session's provider process while the session exists: no memory-pressure stop and no fixed bound on how long a process may live. A process ends when the person closes the session or when the provider exits on its own; one that exits on its own is started again by the daemon until it crashes five times within three minutes ([Spec-018 §Required Behavior](./018-observability-and-failure-recovery.md#required-behavior)), and otherwise it is **replaced** only by an act the person takes on the session itself — switching its provider, which lands at the end of the run ([Spec-014 §Same-Agent Provider Switch](./014-multi-agent-orchestration.md#same-agent-provider-switch)), or restarting it after the daemon stopped restarting it. Moving a session to another account replaces nothing: the session moves in place from its next request ([Spec-025 §Moving a session to another account](./025-provider-accounts-and-credential-homes.md#moving-a-session-to-another-account)). Stopping or restarting the background service is also the person's act, and each confirms in place, saying that work in flight on the machine stops ([Spec-006 §Required Behavior](./006-local-ipc-and-daemon-control.md#required-behavior)). Closing the desktop window or quitting the app is **not**: it leaves every session, run and shell going.
- **Archive, unarchive and close.** Archiving a session moves it into the sessions list's `Archived` group and leaves its provider process as it was. Unarchiving returns it to its own project's list. Closing a session ends its provider leg: on Claude Code its process, and on Codex its running commands and its conversations, while the account's service keeps running for its other conversations; a closed session sits in the same `Archived` group, readable and searchable, with no way back to the live list, until `Delete old data` purges it and counts it in its confirm.
- **Pin and mute.** A session pinned to the top of its group sits above the group's other sessions, the pinned ones in the order they were pinned, and never falls behind the group's cut; there is one pin and no second tier. A muted session's `Finished` and `Failed` notifications are withheld on every channel and every device, and muting withdraws the ones still standing; `Waiting on you`, a workflow's Notify step, the bell's list and its count are untouched ([Spec-017](./017-notifications-and-attention-model.md)). A mute has no timer. The daemon holds both, so every device draws the same pins and the same mutes.

### Groups, Links And Tags

A session is placed, related and described in three separate layers, each written by the person and by agents through the session tools ([Spec-014 §Session Tool Texts](./014-multi-agent-orchestration.md#session-tool-texts)).

- **Placement: one group per session.** Inside a project, sessions can sit in named groups, each group unique in its project ignoring case; a session is in at most one group, and a chat is in none. The sessions list shows a project's groups at its top as foldable rows above the sessions in no group, a folded group showing its count and the rolled-up status a project header shows, and a pinned session stays pinned inside its group. A group is made by moving a session into it, so no group is ever empty: the person moves a session from its actions list or by dragging it onto a group's row, drags it back out among the project's loose sessions, renames a group in place, starts a new session in a group, and ungroups a group, which puts its sessions back loose and archives or closes nothing. A group whose sessions are all archived or closed hides from the list and comes back when one of them is unarchived. An archived session keeps its group.
- **Relationships: a graph of links between sessions.** The daemon records one link per pair of sessions and kind, with how often it was used and when first and last, written at the moment the event that makes it happens and never by a rescan: `started` (one session's agent started the other), `copied_from` (a session made from another, by `Fork`, by `Build in a fresh session` or by an agent starting a copy), `messaged` (the two traded messages, with the count), `asked` (one asked a copy of the other), `mentioned` (a message named the other with `@`), and `related` (added on purpose, by the person or by an agent asked to). A link names sessions by id, so renaming a session changes no link. The links the daemon writes from events — `started`, `copied_from`, `messaged`, `asked` and `mentioned` — record what happened and cannot be removed; a `related` link can. The session inspector lists a session's related sessions in a `Related` section after Identity — `started by planner`, `copy of builder`, `12 messages with review-bot`, `related to stripe-webhook (billing)` — most relevant first, each opening that session, a `related` row carrying `Unlink`. The section's `Link a session…` opens the same session picker `@` uses and adds a `related` link to the session picked. With no related session the section reads `No related sessions yet`, with `Link a session…` as its one act.
- **Categories: any number of tags per session.** A tag crosses projects, nests with `/` (`billing/stripe`, found by searching `tag:billing`), is matched ignoring case, and holds no space: the daemon refuses one that does, from the person and from an agent alike. The inspector's Identity carries a `Tags` line: each tag a chip with a remove control, and an `Add tag` field that suggests the tags already in use.
- **Relevance, not hops.** A related session's score is personalized PageRank from the session, cut at two steps: a link's weight comes from its kind (`copied_from` 1.0, `started` and `related` 0.9, `messaged` 0.5, `asked` 0.4, `mentioned` 0.3), grows with how often it was used, and halves every 30 days without use, and a two-step path counts half. These are starting values, tuned on real sessions. Each session's ranked list is computed ahead and stored under its id, and a new link re-scores, in the background after its event is written, only the two sessions it joins and their neighbors.
- **Search reads all three layers.** A group's name and a session's tags are in the full-text index beside titles, message text and tool calls, so searching `auth` finds every session in `auth work`, and `tag:billing` finds the sessions tagged `billing` or under it. Where a search has words and a relation or a tag, the text rank and the relation rank are merged by Reciprocal Rank Fusion, each list contributing 1/(60 + its rank), and the agents' `session_search` results come grouped by project, then group, then session, each session placed by its score and each group and project by its best session's score; the person's `Search all sessions` box groups its hits by session.
- **Budgets.** At 10,000 sessions, 1,000,000 indexed messages, 100,000 links and 30,000 tags, a search answers in under 50 ms at p95 and a related list in under 1 ms, measured again on the daemon's own build. Measured on SQLite 3.50.4 at that size: a related list p95 0.012 ms read from its stored ranking, a tag or group lookup p95 0.033 ms, and a common word ranked across every message p95 8.2 ms.

## Default Behavior

- A newly created session starts in `provisioning` state and transitions to `active` once its initial storage on the machine that runs it is ready. See [Session Model](../domain/session-model.md) for the full lifecycle including the `archived`, `closed` and `purge_requested` states (see [Spec-020](../specs/020-data-retention-export-and-deletion.md) for GDPR states).
- A new session starts at the `YOLO` permission level — Claude Code's `bypassPermissions`, Codex's Full Access — however the last session was left; the level is never remembered, and the person picks another for that session from the level control. A session made from another, by `Fork` or by `Build in a fresh session`, starts at its source session's level instead, or, where the new session's provider cannot give that level, at the level the person picks ([Spec-010 §Required Behavior](./010-approvals-permissions-and-trust-boundaries.md#required-behavior)). A session an agent starts with `session_start` runs at the level of the agent's own session, never looser, and one it starts as a copy of another session runs at the stricter of the two levels. Its lead starts on the last model and the last effort the person used: that pair lives in the machine's settings file beside the switch that keeps it, written by the daemon each time the person's pick moves it and read through `machineSettings.read()` and `machineSettings.subscribe()`, so the line under the switch on Settings › General and a new session read the same value. With that remembering switched off on Settings › General, or on the first session ever, it starts on the first usable signed-in account's provider, on that provider's default model. The account is the daemon's to resolve, as §Interfaces And Contracts states. Nothing else carries over: not the mode, not the output speed, not the compaction bound. The app picks the model and effort and `session.create` carries them; the daemon takes them from the call, never from the machine's settings file. A workflow's sessions keep the workflow's own defaults.
- A newly created session belongs to the user who created it and starts with one lead agent.

## Fallback Behavior

- Creating a session never waits on the control plane: the session lives on the machine that runs it, so it is created there whether or not the control plane is reachable. While the machine has no relay connection the session is in `local-only` continuity, fully usable on that machine, and the user's other devices reach the same session once the connection is up — nothing is promoted, copied or re-created.
- If a client reconnects after missing live updates, it must restore from the canonical snapshot and the catch-up stream rather than trusting client cache.
- **A session whose provider is missing does not start.** When the provider a session runs on is not installed on the machine the daemon runs on, the daemon starts no provider process for it and lands one flow row naming the provider, a `session.notice` of kind `provider_missing`; pressing the row opens Settings › Providers on that provider's section. On a Windows computer where the place the service runs in has neither provider, the row reads `Choose where Claude Code and Codex are installed` and opens the place row on that page.

## Resource Limits

The runtime adds no count limit of its own: not on runs or agents in a session, and not on how many messages a session may queue. How many agents a provider will run at once, and how deep they may nest, is that provider's own limit under the person's own provider settings; where a provider refuses, its refusal is shown in its own words. A session can carry a spend limit and each run a token limit, both unlimited unless the person sets them.

## Interfaces And Contracts

- `session.create` must return the session id, session state, and the lead agent's resolved binding.
- `session.read` must return the authoritative session snapshot plus transcript cursors.
- Opening a session on another device is `session.read` plus `session.subscribe` over that device's own channel to the machine, which only the user's linked, non-revoked devices can open; it returns the same session id and the session's current snapshot. A device finds a session by asking each machine it can reach whether it holds the session and opens it there; if none does, it says `That session is not here.` No control-plane route creates, reads or streams a session.
- `session.subscribe` must stream canonical session events and catch up from a known cursor, then follow.
- The session surface on the wire is `session.create`, `session.read`, `session.list` (live), `session.subscribe` (catch up from a known cursor, then follow), `session.rename`, `session.archive`, `session.reactivate`, `session.close`, `session.pin` and `session.unpin`, `session.mute` and `session.unmute`, `session.convert`, `session.fork`, `session.setWorkingFolder`, `session.goalUpdate` and `session.goalClear` (`session.goalUpdate` sends one agent in the session a goal — the `/goal <condition>` command — or replaces its active goal, and `session.goalClear` clears it and succeeds with no goal set; a goal is a command sent to an agent, never what the session is, and no session field names, labels or groups a session by its goal; [Spec-014 §Session Goals](./014-multi-agent-orchestration.md#session-goals)), `session.maxStepsUpdate` (this session's own bound on how many steps a turn may take, and its removal), `session.draftUpdate`, `session.attachmentAdd` and `session.attachmentRemove`, `session.fileSearch` (the `@` file search in the session's working folder), the person's half of groups, links and tags — `session.groupCreate`, `session.groupMove`, `session.groupRename` and `session.groupUngroup`, a `groupId` on `session.create` for `New session in group`, `session.relatedList` (the ranked related list, live), `session.linkAdd` and `session.linkRemove` (a `related` link, through the `@` session picker, and `Unlink`), and `session.tagAdd`, `session.tagRemove` and `session.tagList` (the tags in use, which `Add tag` suggests), the daemon refusing a tag that holds a space — and the search reads: `session.search`, across the user's sessions over session titles, message text, tool calls, group names and tags, answering with hits grouped by session — the session's name, then one row per hit carrying the line the match sits in, in the full-text index's own ranked order with no cap — each hit with its own message anchor (grouping by project, then session group, then session belongs only to the agents' `session_search` tool, [Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other)), and the same search scoped to a single session, `transcript.search`, which counts every hit and loads the stretch of history a hit sits in only when the reader steps to it. No client walks history it does not already hold. The session namespace's other verbs — the permission level, the mode, compaction and context, tool servers and resources, provider commands, the side question, review, definitions reload, memory, hooks, undo and its snapshots, review notes, the terminal lease, the provider restart (`session.restart`, [Spec-004](./004-provider-driver-contract-and-capabilities.md)) and the terminal pane's overview read (`session.overviewRead`, [ADR-035](../decisions/035-claude-code-mods-are-an-optional-terminal-bridge.md)) — are specified by the documents that own that behavior.
- `session.create` names the session's one lead agent — a saved agent definition (`leadDefinitionId`), or the axes spelled out in `lead` (its driver, model and effort) — and carries the lead's model and effort, which the app picks by the rule under §Default Behavior. In a project its `binding` names the project and where the session works — a worktree of its own (`provisioned-worktree`) or the checkout the project already has (`bound-root`) ([Spec-008](./008-worktree-lifecycle-and-execution-modes.md)) — and the session is bound there in the same step. For a chat the daemon makes the managed workspace and registers it as a mount in the same step. Try it's scratch session is the same call with `scratch: true` and the definition under test as the lead; the session records that definition as `scratchForDefinitionId`, so Try it finds and reuses the scratch session it made rather than minting another. The reply echoes the binding the daemon resolved for the lead: the driver, the model, the effort, and the provider account ([Spec-026 §Resolution when a run starts](./026-agent-definitions-and-peer-invocation.md#resolution-when-a-run-starts)). Those same resolved values ride the session's own creation record, because no verb attaches an agent to a session and that record is where the agent's row in the session's `agents` projection is born ([Spec-014 §Interfaces And Contracts](./014-multi-agent-orchestration.md#interfaces-and-contracts)). **The account is resolved, never chosen by the client.** `session.create` carries no provider-account member and neither does any other request on this surface: the daemon resolves the account — the one the run's saved agent definition or workflow step pins, where one does, and otherwise that provider's current account — and the reply echoes what it resolved ([Spec-025 §Selection at run start](./025-provider-accounts-and-credential-homes.md#selection-at-run-start)). A client that wants the work to run on a particular account pins it on the definition or the step, or makes that account current on the provider surface, which is also the one act that moves a session already running.
- `session.setWorkingFolder` is one call requesting the move. Re-targeting it at the session's current directory is how a pending request is canceled, the pending intent lives on the session row rather than in a queue, and the move is applied when the session's active run reaches a boundary.
- `session.rename` writes a name field on the session record and appends `session.renamed`; a session with no name is shown by its first message. A session also names itself after its first completed exchange: the daemon's session auto-title (`SessionAutoTitle`) runs a short throwaway provider pass that reads the exchange and writes a few words through the same rename path, and where the pass returns nothing the name falls back to the first words of the first message. It writes only while the session is still unnamed and re-reads the name before it writes, so a name the person typed always wins. Naming a session never renames its branch or its worktree.
- `session.maxStepsUpdate` writes this session's own `Max steps per turn` override on the session record, or clears it so the session falls back to the machine's own value; an absent override is the ordinary state and means unlimited unless the machine's value says otherwise. What the bound does and how each provider realizes it are [Spec-003 §The Step Bound On A Turn](./003-queue-steer-pause-resume.md#the-step-bound-on-a-turn)'s, and nothing about the bound is a budget or an intervention.
- `session.list` is live: the list, then each change. Each entry carries the session's title, state and `shape` (`chat` or `project`), the branch taken from the session record so an entry costs no git read, `muted`, its `group` where it is in one, and, while the session is trading messages with another session, the exchange (`exchange: {peerSessionId, peerName, messageCount}`, the count being the messages the two have traded since the person last wrote), so one feed serves every row and no row opens a stream of its own. Each entry also carries `activity`, the one of five readings the daemon derives for the session (`running`, `waiting` on the person, `done`, `failed` or `idle`), and `activityRenewedAt`, when the daemon last stood behind that reading. While a run is `running` or `waiting` and sends nothing else, the daemon republishes its session's entry every 15 seconds, and a reader treats a `running` or `waiting` reading whose `activityRenewedAt` is more than 45 seconds old, three renewals missed, as `idle`, its timer standing where it froze, so a daemon that crashed never leaves a session reading `running`. A `failed` reading is never aged out, because it is a fact about the run rather than a claim about now. Archived and closed sessions are entries like any other. A session the person runs in a terminal has no entry. The list also carries the count of chats, which the Chats header shows, counted by the daemon and never by a reader.
- `session.read` answers one session's facts: its title, `shape`, state, project, worktree and base, elapsed time, how many commits its branch is ahead, its snapshot count, a pending folder move, its address, `muted`, the lead's binding, and the daemon-held draft with its staged files.
- `session.subscribe` batches the session's events into one frame per 16 ms or per 50 events, whichever comes first; each frame carries changes only, each with its cursor. The daemon never waits for a screen: a screen that falls behind is dropped for and told so on the very next frame, and repairs from the daemon's record by cursor, taking a snapshot read past a gap of 1,024 events. When a screen that fell behind has caught up on its queue, the daemon sends it one frame with no changes, carrying the drop mark and the newest cursor, so a session that goes quiet right after a drop still tells the screen it is behind.
- `session.archive` and `session.reactivate` archive a session and return it to the live list (events `session.archived` and `session.reactivated`); `session.close` closes a session and ends its provider leg, on Codex its commands and conversations while the account's service keeps running (event `session.closed`). Only an archived session is reactivated; a closed one is not.
- `session.pin` and `session.unpin` pin a session to the top of its group and unpin it (events `session.pinned` and `session.unpinned`).
- `session.mute {sessionId}` and `session.unmute {sessionId}` answer `{}` and append `session.muted {sessionId, at}` and `session.unmuted {sessionId, at}`. Both are idempotent: muting a muted session appends nothing. The session's `muted_at` is rebuilt from those events, and the notification gate reads it when it writes an entry and withdraws the session's standing `Finished` and `Failed` entries on `session.muted`.
- `session.convert {sessionId, path}` converts a chat to a project as §Required Behavior describes and appends `session.converted`; the path is the typed text, carried as data, and the daemon checks it before anything is copied.
- `session.search {query}` answers from SQLite's built-in full-text index (FTS5) over session titles, message text, tool calls, group names and tags, reaching every session the list holds, archived ones included, with the hits ranked as §Groups, Links And Tags sets out and no cap on how many come back. The agents' `session_search` reads the same index ([Spec-014 §Session Tool Texts](./014-multi-agent-orchestration.md#session-tool-texts)).
- `session.fileSearch {sessionId, query}` is the `@` file search. It runs on the machine holding the session's files and answers ranked paths relative to the session's working folder. The daemon lists the working folder with `git ls-files`, or with `fdir` and `ignore` outside a git repository, ranks the paths with the product's one fuzzy scorer from `packages/search-ranking` (the file name first, then the whole relative path, as the file search's own candidate fields), and returns at most a fixed number of paths, a daemon constant. Its answer tells apart a list still being built (`Searching…`, never `No matching files`), a query that matched nothing (`No matching files`), a folder with nothing to match (`No files available`), and a search that failed, the failure with its reason; a read that can be retried is retried once. Any path whose real location is outside the working folder is dropped, so no result follows a link out of it, and results carry names only.
- **A session's address rides its snapshot, not a read of its own.** The address another session writes to when it messages this one — the string the session inspector offers as `Copy address` ([Spec-014 §Sessions Talking To Each Other](./014-multi-agent-orchestration.md#sessions-talking-to-each-other)) — is a member of the snapshot `session.read` answers, because the one surface that shows it already reads that snapshot and a second verb would be a second source for one fact. It names an inbox the daemon holds for the session: one socket, `sidekicks-<session-id>.sock` in Claude Code's socket directory on a Mac and on Linux and the named pipe `\\.\pipe\sidekicks-<session-id>` on Windows, stable for the session's whole life, so a copied address keeps working across a restart and while the session sleeps. The daemon forwards each frame written to it to the session's live provider process; while the session sleeps, the daemon takes the first frame, wakes the session through Claude Code's resume and delivers the frame as the message.
- `session.fork` carries the message anchor — for `/fork`, the session's newest item of either side — returns the new session's id, and records the parent on that new session's creation record; the new session starts at the parent's permission level. The daemon makes the copy through the driver's `forkConversation`, and a chat fork gets a managed workspace of its own in the same step. `session.fork` is never a rollback: undo is `session.restore` in the same session ([Spec-013 §Required Behavior](./013-persistence-and-recovery.md#required-behavior)).
- The composer draft, its staged files and the review notes left on a file's lines are one daemon-held, session-scoped store: `session.draftUpdate` saves the draft, one second after typing pauses and at once when the session is left or the window closes; `session.attachmentAdd` stages several files at once — files only, never a folder, each picked or dropped file arriving as a token the main process's relay turns into a path — and also stages a Preview marks chip or a tool server's resource; `session.attachmentRemove` unstages one ([Spec-012](./012-artifacts-files-and-attachments.md)). A staged file is copied to the daemon when it is staged and held with the session outside the checkout, and a note left on a line is held the same way, scoped to the same session. Because the daemon holds all three, a half-written message, its files and an unsent review reach the user's other devices and sending needs no upload step; the draft and the staged files are read back through `session.read`, and the draft is cleared when the message is sent. Typed unsent text is never written to window storage.
- The session's canonical stream carries every `session.*` event: `session.created` (the lead, and the parent on a fork), `session.goal_updated` (the goal's status, one of `active`, `paused`, `blocked`, `usage-limited`, `budget-limited`, `complete` or `impossible`; `complete` and `impossible` are final, and only Claude Code sends `impossible`, carrying the judge's reason), `session.goal_cleared` (which ends a goal; clearing is never a status), `session.renamed`, `session.advisor_changed` (a Claude Code session's own advisor, set by `/advisor`), `session.archived`, `session.reactivated`, `session.closed`, `session.pinned`, `session.unpinned`, `session.muted`, `session.unmuted`, `session.converted`, `session.branch_changed`, `session.swept_to_repo_root`, `session.side_question_answered` (the question and the answer), `session.restore_finished` (every undo outcome), and `session.notice`, whose kinds each read as one plain sentence: `settings_ignored`, `conversation_reloaded`, `review_started`, `review_finished`, `goal_not_met`, `goal_check_unfinished`, `provider_warning` (counted on the working line and listed from it, never a flow row), `level_unavailable`, `provider_updated` (the banner under the header, never a flow row), `fast_output_unavailable` and `provider_missing` (§Fallback Behavior). The screen folds a list of events across every category ([Spec-005 §Event Type Enumeration](./005-session-event-taxonomy-and-audit-log.md#event-type-enumeration)); an event outside that list draws nothing on screen, no row and no notice, and the app may record it in its diagnostics log.

- See [Error Contracts](../architecture/contracts/error-contracts.md) for error response schemas and error codes.

## State And Data Implications

- Session records must be durable on the machine that runs the session before active run state is admitted. The control plane keeps no copy of a session record and no directory of sessions.
- The system must maintain a canonical session event stream and session snapshot projection.
- Clients may cache presentation state, but cache must not be authoritative for session or run truth.
- The session record carries the shape discriminator and, for a chat, the managed-workspace mount the session is bound to. The daemon-held draft, its staged attachments and the session's review notes are durable session-scoped state, never client state.
- The session record also carries its name, where it has one, whether it is pinned and its place among the pinned sessions, `muted_at`, rebuilt from the mute events and removed with the session, and, for Try it's scratch session, the definition it was made for (`scratchForDefinitionId`). Nothing on the record names, labels or groups a session by a goal.
- The session record additionally carries this session's own `Max steps per turn` override, absent where the person set none. It is durable because a session keeps its own bound across a restart, and it is on the session rather than on a run because a run does not outlive the turn it bounds. A Claude Code session's own advisor, the model or off, is durable beside it: copied from the app's default when the session is created and changed only by `/advisor` in that session. The session's group is a column on the record, indexed, and its tags and links are rows of their own keyed by session id, removed with the session; each session's ranked related list is stored under its id and recomputed when a link it depends on changes. The session's address is **not** on the record: it is the inbox the daemon holds for the session, named from the session id and stable for the session's whole life, so nothing stale is ever handed out.

## Implementation Notes

- Keep session ids globally unique and opaque.
- The lead agent is created with the session, not by the first run.
- `local-only` continuity must stay visible — the user's other devices show the machine not reachable — but it must not become a second session type.

## Pitfalls To Avoid

- Treating provider thread ids as session ids
- Letting the active client tab own session truth
- Creating hidden shadow sessions during reconnect or when another device opens a session

## Acceptance Criteria

- [ ] AC1 — Creating a session yields one stable session id and one lead agent.
- [ ] AC2 — The session record is durable on the machine that runs the session before any run admission.
- [ ] AC3 — Session id is stable across reconnect, client restart, and transport change.
- [ ] AC4 — A second device opening an existing session receives the same session id and full event history.
- [ ] AC5 — Opening a session on another device does not silently fork the session, change the session id, or reset existing runs.
- [ ] AC6 — Reconnecting clients restore session state from the authoritative snapshot plus catch-up events, never from client cache.
- [ ] AC7 — Concurrent agents and runs are supported without transcript corruption, with no count limit of the runtime's own on either.
- [ ] AC8 — A session is in at most one group of its project; its links and tags survive a rename; a link the daemon wrote from an event cannot be removed and a `related` link can; a search for a group's name or for `tag:<tag>` finds its sessions; and at 10,000 sessions and 1,000,000 indexed messages a search answers in under 50 ms at p95 and a related list in under 1 ms.
- [ ] AC9 — A session's shape is read from its binding and its durable discriminator; attaching a folder that is already a project opens that project and mints no second project record for the same origin.
- [ ] AC10 — A chat converted to a project keeps its session id and its full transcript, its managed workspace and history are kept, and a file the repository already has is left untouched, stays in the managed workspace, is named on the conversion's own transcript row, and is named to the session's agent in one short message.
- [ ] AC11 — A fork yields a new session id of the same shape carrying the transcript prefix through the anchor message, records the parent on its own creation record, and leaves the parent session's id, transcript and runs unchanged.
