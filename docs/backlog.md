## BL-108: Plan-022 Windows + macOS signing procurement evidence

- Status: `blocked` (external-world wait — no purchase is made while the 2026-08-25 user-ratified spend deferral stands)
- Priority: `P2`
- Owner: `unassigned`
- References: [Plan-022](./plans/022-rust-pty-sidecar.md) §Preconditions + Phase 4 (T-022-4-3), [ADR-019](./decisions/019-windows-v1-tier-and-pty-sidecar.md) §Decision item 8, [ADR-023](./decisions/023-v1-ci-cd-and-release-automation.md) §Axis 5, [Spec-021](./specs/021-desktop-shell-and-renderer.md) §macOS
- Summary: Procurement evidence record for Plan-022 signing-identity gates (per F-022-4-06). Four artifacts: (a) Microsoft eligibility-determination response (Track A) OR vendor procurement contract + token-shipment confirmation (Track B); (b) signing-identity attestation matching Spec-021's Electron shell per [ADR-019 §Decision](./decisions/019-windows-v1-tier-and-pty-sidecar.md#decision) item 8 + ADR-023 §Axis 5; (c) Plan-022 §Decision Log entry naming the chosen track + date; (d) macOS Developer ID Application certificate procurement evidence (cert thumbprint + team-ID + Apple Developer enrollment-confirmation email).
- V1 Release Impact: Does NOT block V1 release. V1 distributes via GitHub Releases — the Electron desktop shell (delivered via Plan-021, Tier 7) and the PTY sidecar binary (Plan-022) function on macOS and Windows without code-signing certificates. Users encounter a one-time first-launch macOS Gatekeeper / Windows SmartScreen security warning that is bypassable via documented instructions (macOS: System Settings → Privacy & Security → "Open Anyway" after the first blocked launch — corrected 2026-08-25: macOS 15 Sequoia removed the Control-click → Open path this entry previously named, and Privacy & Security is now the only route; Windows: "More info" → "Run anyway" on the SmartScreen dialog); distributing unsigned OSS Electron apps via GitHub Releases is a well-established pattern. The PTY sidecar is a daemon-spawned subprocess — the user-launched Gatekeeper/SmartScreen flow applies primarily to the Electron app installer (.dmg / .exe), not the sidecar binary. Cert procurement (the four artifacts above) is therefore a post-V1 UX-polish surface: certificates can be applied for and obtained when budget and timeline align, and the Plan-022 Phase 4 signing implementation activates on top of the existing GitHub-Releases distribution once certs are available. Tier 1 closure does NOT gate on this BL.
- Named gate: user-ratified spend deferral, 2026-08-25 — Apple Developer Program Individual ($99/yr) and Azure Artifact Signing Basic ($9.99/mo) are both purchases, and no purchase is initiated against this entry until the deferral is lifted. Nothing in-tree blocks; this is an external-world wait.
- Procurement targets, recorded 2026-08-25 so the artifacts have something concrete to be evidence _of_: **macOS** — Apple Developer Program **Individual** enrollment ($99/yr, no D-U-N-S — [Apple enrollment support](https://developer.apple.com/support/enrollment/): "The Apple Developer Program annual fee is 99 USD", and the D-U-N-S requirement is stated for organizations only), then a Developer ID Application certificate; artifact (d) is its thumbprint + Team ID + the enrollment-confirmation email, with an App Store Connect API key held as repo secrets for `notarytool`. **Windows** — **Track A**, Azure Artifact Signing Basic, selected and recorded in [Plan-022 §Decision Log](./plans/022-rust-pty-sidecar.md#decision-log) (which satisfies artifact (c)); individuals are eligible with identity validation via Microsoft Authenticator Verified ID plus a government-issued ID, and a **paid Azure subscription must already exist** — per the [Artifact Signing FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq), verbatim, "Artifact Signing doesn't support free, trial, or sponsored Azure subscriptions... upgrade your subscription to a pay-as-you-go or enterprise agreement". The billing account's Account Type must read "Individual" to run **Individual** identity validation. **Narrowed 2026-08-25 to what the source establishes:** an earlier revision of this line said the billing Account Type "is the sole source of the certificate subject", which overstates it — the FAQ ties the subject to the _identity validation_ ("you can't use a custom Common Name (CN) or a custom Organization (O)"; CN "must always be the legal entity's validated name", and the CN/O dropdown is populated from a completed identity validation). Account Type gates which validation type is available; the validation then supplies the subject. Confirm the country/region is supported against the [Artifact Signing quickstart prerequisites](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart) before opening any paid account — the FAQ defers the supported-region list to that page.
- Exit Criteria: All four artifacts attached; [Plan-022 §Decision Log](./plans/022-rust-pty-sidecar.md#decision-log) records the Windows signing-track choice + date (**met 2026-08-25** — Track A); Plan-022 Phase 4 Preconditions row flips checked. Also owned by the closure PR, five residuals left in place when ADR-023 and Plan-022 were corrected on 2026-08-25 because those sections are this BL's to touch: (i) [Spec-021 §Code Signing And Notarization](./specs/021-desktop-shell-and-renderer.md#code-signing-and-notarization) still carries the retired "EV for instant SmartScreen reputation" claim; (ii) [Spec-021 §Windows](./specs/021-desktop-shell-and-renderer.md#windows) still carries the pre-2026 OV price band; (iii) that same Spec-021 eligibility-gate bullet still says the ineligible-geography path "must use a traditional EV cert", which contradicts Plan-022 Track B's prefer-OV rule; (iv) [Plan-021 §Risks And Blockers](./plans/021-desktop-shell-and-renderer.md#risks-and-blockers) names EV as _the_ ineligible-geography fallback and spells the CSC-31 cap as "15-month validity" (the spelling Plan-022 flags as able to exceed the ≤460-day cap); and (v) [ADR-019 §Decision](./decisions/019-windows-v1-tier-and-pty-sidecar.md#decision) item 7's second disjunct, "or EV-chain-required distributions", is retired but still written. Items (iii)-(v) were added 2026-08-25 after an adversarial pass found the original two-item list under-enumerated: (iii) and (iv) are lane-mandate statements rather than reputation or price claims, and (v) sits in a different ADR entirely.

## BL-112: Plan-006 Ed25519 release-manifest signing custody procurement evidence

- Status: `blocked` (external-world wait — no purchase is made while the 2026-08-25 user-ratified spend deferral stands)
- Priority: `P2`
- Owner: `unassigned`
- References: [Spec-024](./specs/024-self-host-secure-defaults.md) §Required Behavior row 7b + §Interfaces And Contracts (release manifest schema), [ADR-023](./decisions/023-v1-ci-cd-and-release-automation.md) §Axis 5 items 4 and 5, [Plan-006](./plans/006-local-ipc-and-daemon-control.md) (daemon-side `self-update` Sigstore + Ed25519 dual-verification), [BL-108](#bl-108-plan-022-windows--macos-signing-procurement-evidence) (distinct code-signing-cert procurement; this BL covers a separate manifest-signing-key custody track that BL-108 does not own)
- Summary: Procurement-evidence record for the Spec-024 §7b release-manifest dual-trust signing infrastructure. BL-108 covers binary code-signing certificates (Apple Developer ID + Windows track) only; this entry tracks the orthogonal Ed25519 manifest-signing key custody specified by ADR-023 §Axis 5 items 4 and 5 — an [AWS KMS Ed25519 hot key](https://aws.amazon.com/about-aws/whats-new/2025/11/aws-kms-edwards-curve-digital-signature-algorithm/) (GA 2025-11-07; `KeySpec = ECC_NIST_EDWARDS25519`; ~$12.02/yr single-region custody-dominated) accessed via [GitHub Actions OIDC federated credential to AWS IAM](https://docs.github.com/en/actions/deployment/security-hardening-your-deployments/about-security-hardening-with-openid-connect) for routine releases, plus a [YubiHSM 2 standard-variant cold key ($650 one-time)](https://www.yubico.com/product/yubihsm-2/) in sole-maintainer custody for `next_signing_keys` rotation announcements and the `version=1` bootstrap manifest. Procurement is intentionally deferred until V1 is production-release-ready (no payments or applications initiated against this entry while V1 hardening is in flight). Sole-maintainer custody is the V1 model; multi-maintainer key-recovery custody is out of scope and tracked as a separate future backlog item to be opened when a second author joins the project.
- Named gate: user-ratified spend deferral, 2026-08-25 — the cold-key hardware and the AWS KMS key are both purchases. Open at procurement time and **not decided here**: whether the cold signer stays the YubiHSM 2 named in exit (a) or moves to a cheaper multi-device alternative. That device is named by [ADR-023](./decisions/023-v1-ci-cd-and-release-automation.md) §Axis 5 item 5, so any change is an ADR-023 amendment carried by this BL's closure PR, not a unilateral edit here.
- Exit Criteria: All four artifacts attached or hash-recorded under this entry — (a) YubiHSM 2 standard-variant procurement evidence (order confirmation + device serial number + first-power-on initialization timestamp); (b) AWS KMS Ed25519 key creation evidence (key ARN + key creation timestamp + attached KMS key policy with a `kms:Sign` statement conditioned on `"kms:SigningAlgorithm": "ED25519_SHA_512"` + matching IAM identity policy on the federated role with the same `kms:SigningAlgorithm` condition on `kms:Sign` for defense-in-depth (the `kms:SigningAlgorithm` key is a KMS service condition evaluated by KMS at `Sign`/`Verify` authorization time, **not** by STS at role-assume time, so it must live in the key policy and/or identity policy, never in the role's trust policy) + a GitHub Actions workflow run ID demonstrating a successful end-to-end Sign + verify against a test manifest); (c) GitHub Actions → AWS OIDC federation evidence (AWS IAM identity-provider thumbprint + repository-level OIDC subject-claim customization configured via `PUT /repos/{owner}/{repo}/actions/oidc/customization/sub` with `use_default: false`, `use_immutable_subject: true` per the [immutable-subject-claims format](https://github.blog/changelog/2026-04-23-immutable-subject-claims-for-github-actions-oidc-tokens/) for repo-ID binding — corrected 2026-08-25: repositories created after **2026-07-15** receive the immutable format automatically and existing repositories opt in, so this repository must opt in explicitly; the "enforcing 2026-06-18" date this entry previously carried was wrong, and an `include_claim_keys` array combining repository, environment, and ref context — the combined `sub` is required because default GitHub OIDC tokens emit only one context per claim (e.g. `repo:OWNER/REPO:environment:production` OR `repo:OWNER/REPO:ref:refs/heads/main`, not both), so the federation `StringEquals` condition is unreachable without the customization step + the AWS IAM federated-credential `sub` condition pinned to the literal `sub` value emitted by a test workflow run in the `production` environment on `main` after the customization is applied (record the emitted `sub` from the token introspection step of the test run; do not hand-assemble the value, since the exact join format depends on which `include_claim_keys` names GitHub accepts at the time of configuration) + `aws-actions/configure-aws-credentials` pinned to a commit SHA rather than the `@v6` floating tag); (d) first-key rotation rehearsal evidence (test-cutover ceremony walkthrough demonstrating the ADR-023 §Axis 5 item 5 dual-sign procedure — `next_signing_keys` pre-published ≥30 days ahead, current hot key signs the rotation manifest, cold YubiHSM 2 counter-signs the rotation announcement, transition-period dual-sign works end-to-end). When all four artifacts are recorded, Plan-006's release-manifest verification implementation has run green against signatures produced under this custody contract, and Spec-024 §7b's release-manifest schema fields (`version`, `released_at`, `expires_at`, `previous_manifest_hash`, `next_signing_keys`) have been exercised against a real signed manifest, this item is closeable.

## BL-124: npm Trusted Publisher + Sigstore identity bootstrap

- Status: `blocked` (the registration ceremony must run in an interactive 2FA session the maintainer performs; it cannot run from CI)
- Priority: `P2`
- Owner: `unassigned`
- References: [ADR-023 §Axis 1](./decisions/023-v1-ci-cd-and-release-automation.md) (Surface 1 npm-package publish flow naming `@ai-sidekicks/contracts` + `@ai-sidekicks/client-sdk`), [ADR-023 §F-6](./decisions/023-v1-ci-cd-and-release-automation.md) (per-package Trusted Publisher registration risk + npm-bootstrap chicken-and-egg ceremony), [ADR-023 §Consequences](./decisions/023-v1-ci-cd-and-release-automation.md) (a per-package 2FA registration ceremony — ADR-023 enumerated 7 packages at Tier 1, extended to 8 here with `@ai-sidekicks/crypto-paseto`). Cite corrected 2026-08-25: `§Manual Setup Required` names a heading that has never existed in ADR-023; the claim lives in §Consequences, where the "no automation possible through npm UI" clause was corrected in the same PR — `npm trust github` registers from the CLI, [`.github/workflows/release.yml`](../.github/workflows/release.yml) (`publish-npm` job at line 78 gated `if: false` at line 86; `sbom` job at line 135 gated `if: false` at line 152), [BL-108](#bl-108-plan-022-windows--macos-signing-procurement-evidence) (binary code-signing certificates — distinct procurement track), [BL-112](#bl-112-plan-006-ed25519-release-manifest-signing-custody-procurement-evidence) (Ed25519 release-manifest signing custody — distinct procurement track), Tier 1 closing audit A10 R-2.
- Summary: The `publish-npm` + `sbom` jobs in `.github/workflows/release.yml` are deliberately gated `if: false` pending procurement of the npm Trusted Publisher per-package registrations and the Sigstore production identity that ADR-023 §Axis 1 + §Axis 5 specify. ADR-023 §F-6 documents the bootstrap as a one-time chicken-and-egg ceremony: each of the 8 published packages (`@ai-sidekicks/contracts`, `@ai-sidekicks/client-sdk`, the 5 sidecar packages from ADR-023 Surface 3, plus `@ai-sidekicks/crypto-paseto` — the shared PASETO primitive, an 8th npm package introduced after ADR-023's Tier-1 enumeration of 7) must publish once via traditional `NPM_TOKEN` before npmjs.com will accept the Trusted Publisher registration. This entry tracks the npm-distribution-surface procurement track only; BL-108 covers the binary installer code-signing certificates (Apple Developer ID + Windows track), BL-112 covers the orthogonal Ed25519 release-manifest signing-key custody. Three distinct distribution surfaces, three distinct procurement BLs, one shared deferral pattern.
- V1 Release Impact: Does NOT block V1 release. V1 distributes the desktop runtime via GitHub Releases (Electron app + PTY sidecar + signed release manifest) — the npm-published packages (`@ai-sidekicks/contracts` + `@ai-sidekicks/client-sdk`) are SDK / integration surfaces for downstream integrators, not required for end-user V1 functionality. The `if: false` gates intentionally hold the publish flow until the procurement window aligns with maintainer capacity for the per-package 2FA ceremony documented in ADR-023 §Consequences. Tier 1 closure does NOT gate on this BL; the audit's A10 R-2 finding requested only that the deferral be tracked as a backlog entry (this item).
- Exit Criteria: (a) npm organization claimed + 2FA enforced on every maintainer with publish rights per [npm 2FA docs](https://docs.npmjs.com/configuring-two-factor-authentication); (b) §F-6 bootstrap step — each package published once under a granular access token to seed the npmjs.com package record that Trusted Publisher registration requires. **Scoped 2026-08-25:** only **3** of the 8 packages exist today (`@ai-sidekicks/contracts`, `@ai-sidekicks/client-sdk`, `@ai-sidekicks/crypto-paseto`), so those three are what this criterion can cover now; the 5 sidecar packages are created by Plan-022 Phase 5 and transitively gate this criterion on [BL-108](#bl-108-plan-022-windows--macos-signing-procurement-evidence). Publishing `client-sdk` needs the `workspace:*` specifier rewritten first, so the bootstrap runs through `pnpm pack` + `npm publish <tarball> --access public` rather than a bare publish from the workspace; (c) per-package Trusted Publisher entry registered **from the CLI** — `npm trust github <package> --file <workflow>.yml --repository <owner>/ai-sidekicks --environment production --allow-publish` (corrected 2026-08-25 from "via npmjs.com UI"; verified against the installed npm 11.16.0, the subcommand landed in 11.15.0, and `npm trust list` / `npm trust revoke` cover inspection and rollback) — pinned to this repo + the publishing workflow file + the `production` GitHub environment per [npm Trusted Publishers docs](https://docs.npmjs.com/trusted-publishers/) — npm Trusted Publishers binds each registration to a specific workflow **filename**, so the 7 ADR-023 packages pin to `release.yml` while `@ai-sidekicks/crypto-paseto` pins to `relay-node-release.yml` (the workflow that publishes it); (d) Sigstore production identity verified end-to-end via a test release run that emits a valid `actions/attest@v4` bundle for at least one package (Sigstore keyless via GitHub OIDC, no long-lived secrets per ADR-023 §Security Posture); (e) `publish-npm` + `sbom` `if: false` gates flipped to their respective release condition per the comments adjacent to each gate — in `.github/workflows/release.yml` (the 7 ADR-023 packages) to `if: ${{ needs.release-please.outputs.releases_created == 'true' }}`, AND in `.github/workflows/relay-node-release.yml` (`@ai-sidekicks/crypto-paseto`'s `publish-npm`/`sbom` jobs) to a tag-ref condition `if: ${{ startsWith(github.ref, 'refs/tags/relay-node-v') }}` — that workflow is triggered by the `relay-node-vX.Y.Z` tag and defines no `release-please` job, so it MUST NOT reference `needs.release-please.outputs.releases_created` (a missing-`needs` reference would leave the crypto-paseto publish/SBOM path skipped even after procurement); (f) first end-to-end release publishes signed npm package + provenance statement + SBOM attestation against which `npm audit signatures` passes on a downstream install; (g) [ADR-023 §Decision Log](./decisions/023-v1-ci-cd-and-release-automation.md#decision-log) entry recording procurement date + npm organization name + the registered Trusted Publisher entries. Before flipping (e), **dry-run the publish loop**: it uses `pnpm publish`, has never executed live, and pnpm's reliability as an OIDC carrier is contested upstream — the escalation path if it fails is to pin npm and publish the packed tarball instead.
- Tracked-by: ADR-023 §Axis 1 (Surface 1 npm-package publish flow) + §Axis 5 (production identity provisioning).
- Revisit Trigger: **This is the one procurement item with a closing window.** Per the [GitHub changelog of 2026-07-31](https://github.blog/changelog/2026-07-31-restricting-npm-bypass-2fa-granular-access-tokens/), bypass-2FA granular access tokens already cannot change package access, maintainers, or trusted-publishing configuration, and around **January 2027**, verbatim, "2FA-bypass tokens will also lose direct publish. Their publishing surface will reduce to reading private packages and staging a publish, which a maintainer approves with 2FA" — the recommendation being to "move automated publishing to trusted publishing (OIDC) or staged publishing." The §F-6 bootstrap is materially easier before that date than after — this entry moved `P3` → `P2` on 2026-08-25 for that reason, since a closing external window is not "lower urgency". The ceremony itself must run in an interactive 2FA session and cannot be automated from CI. Classic npm tokens no longer exist (revoked November–December 2025) and granular write tokens are capped at a 90-day lifetime, so "traditional `NPM_TOKEN`" in ADR-023 §F-6 must now be read as a granular access token. Other triggers: maintainer capacity aligns with the §F-6 bootstrap ceremony window; OR a downstream integrator requests npm-distributed access to `@ai-sidekicks/contracts` / `@ai-sidekicks/client-sdk` (signal that the SDK surface needs npm publication for ecosystem reach); OR V1.1 planning starts and npm publication is sequenced into V1.1 distribution scope.
