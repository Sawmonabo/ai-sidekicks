# Backlog

## Purpose

This file is the active development backlog for the product defined in [vision.md](./vision.md).

## How To Use This Backlog

- Add items only when they represent real remaining work.
- Link every item to the governing spec, plan, ADR, or operations doc where possible.
- Keep items outcome-oriented. A backlog item should describe a deliverable, not a vague area of concern.
- Remove or rewrite stale items instead of letting the file become a historical log.
- When work is complete, update the canonical docs it depends on first, then move the item to [Backlog Archive](./archive/backlog-archive.md).
- If information in a backlog item becomes durable product truth, move that information into the canonical docs and keep only the remaining work here.

## Status Values

- `todo`
- `in_progress`
- `blocked`
- `completed`

## Priority Values

- `P0` — blocks all implementation or blocks a critical feature
- `P1` — blocks a specific feature or must resolve before v1
- `P2` — should resolve before v1 ship
- `P3` — should resolve before v1 ship; lower urgency than `P2` (revisit-trigger BLs, post-v1-polish surfaces, deferred-but-tracked enhancements). Active P3 usage: BL-122/123/131/150; archive entries BL-109/110/117/118/121/126/127/128/130/134/136/147 all closed at P3. Uniform semantics: "tracked but not blocking" across every active and closed P3 entry.

### BL-122: Turborepo remote-cache wiring

- Status: `in_progress` (wiring merged; the measurement window is what remains)
- Priority: `P3`
- Owner: `unassigned`
- References: [ADR-023 §Axis 1](./decisions/023-v1-ci-cd-and-release-automation.md) (the remote-cache text lives in §Axis 1, not §Axis 2 — corrected 2026-08-25) + its §Decision Log 2026-08-25 rows; Tier 1 closing audit A10 G-2
- Summary: ADR-023 §Axis 1 names a Turborepo remote cache as a wall-clock-reduction lever. Wired 2026-08-25 against the GitHub Actions cache via `rharkor/caching-for-turbo`, replacing the self-hosted `ducktors/turborepo-remote-cache` the ADR originally named — a departure from `ADR-022 §Decision`'s self-hosting commitment, amended there in the same PR (ADR-022 sets no budget; an earlier draft of this line wrongly attributed a "$0 or equivalent" constraint to it). Scope is deliberately narrow: `build`, `typecheck`, and `lint` are cached, and **every task that executes a test is `"cache": false`** — a docs-only PR must not replay a suite that never ran. What remains is the measurement window, not the wiring.
- Exit Criteria: (a) **met 2026-08-25** — provider chosen (`rharkor/caching-for-turbo`, SHA-pinned, GitHub Actions cache backend, $0) and keyed by the `TURBO_REMOTE_CACHE_SIGNATURE_KEY` repository secret. This criterion previously named `TURBO_TOKEN`, which is Vercel Remote Cache's bearer auth; the chosen backend has no bearer token and the HMAC signature key is the only secret in play. (b) **met 2026-08-25** — `turbo.json` sets `remoteCache.signature`. Note the honest reading: Turborepo documents this as artifact **integrity** verification and states it "is not a security feature", so what defends the cache against fork poisoning is GitHub withholding secrets from fork-originated workflows, the read-only `GITHUB_TOKEN` on `pull_request`, and the `--cache=local:rw,remote:r` switch appended to every `turbo run` invocation in the two cache-enabled jobs on PR events — all eight of them; the advisory `coverage` job's two invocations carry no switch and need none, having no caching action and no `TURBO_API`. (c) **open** — CI wall-clock reduction validated against a >=5-PR sample. Baseline: **282 s** cache-cold `ci-gate` wall-clock (N=8, measured 2026-08-25 over the eight most recent merged PRs; the 218–223 s figure carried in earlier campaign records is superseded). Threshold: >=30% median reduction keeps the wiring and closes this item with the data attached; below 30% reverts the wiring and records the negative result here. **The window cannot open until the cache is seeded.** Per exit criterion (b)'s `--cache=local:rw,remote:r` switch, every `pull_request` run is read-only against the remote cache, so no PR can populate it; verified 2026-08-25, the repository's Actions cache listing holds zero `turbogha_*` entries and the wiring PR's post-step ledger reports `save: 0%`. The first write happens on the first `push` to `develop` after that PR merges, and only runs after that seed can produce a warm-cache figure — comparing against the 282 s baseline before then measures a permanently cold cache and will read as a null result for the wrong reason. Carry into the comparison that the OS is not part of Turborepo's cache key — harmless while the two cacheable jobs cover disjoint packages on one runner image, but a per-OS `globalEnv` discriminator must land with the first macOS or Windows test leg. (d) **met 2026-08-25** — `ADR-023 §Decision Log` records the provider adjudication, the cost rationale, and the never-cache-a-test rule.
- Revisit Trigger: Tier 2+ build wall-clock surfaces as a developer-experience pain point (PRs spending >10 minutes in CI on cache-cold builds), OR an ADR amendment promotes remote-cache to a required surface, OR a multi-author workflow appears where build-cache sharing has compounding payoff.
