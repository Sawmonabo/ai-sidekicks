# Backlog

## Purpose

This file is the active development backlog for the product defined in [vision.md](./vision.md).

## How To Use This Backlog

- Add items only when they represent real remaining work.
- Link every item to the governing spec, plan, ADR, or operations doc where possible.
- Keep items outcome-oriented. A backlog item should describe a deliverable, not a vague area of concern.
- Remove or rewrite stale items instead of letting the file become a historical log.
- When work is complete, update the canonical docs it depends on first, then move the item to [Backlog Archive](./archive/backlog-archive.md).
- If information in a backlog item becomes durable product truth, move that information into the canonical docs and keep only the remaining work here.

## Status Values

- `todo`
- `in_progress`
- `blocked`
- `completed`

## Priority Values

- `P0` — blocks all implementation or blocks a critical feature
- `P1` — blocks a specific feature or must resolve before v1
- `P2` — should resolve before v1 ship
- `P3` — should resolve before v1 ship; lower urgency than `P2` (revisit-trigger BLs, post-v1-polish surfaces, deferred-but-tracked enhancements). Active P3 usage: BL-122/123/124/131/134/147; archive entries BL-110/115/116/117/119/120/121 all closed at P3. Uniform semantics: "tracked but not blocking" across every active and closed P3 entry.

### BL-141: Runtime-node control-plane caller-authorization (caller-owns-the-node) model

- Status: `todo` — governing decision ratified 2026-08-10 ([ADR-025](./decisions/025-runtime-node-control-plane-caller-authorization.md), `accepted`), which discharges criterion (a); criterion (b) is discharged by the Spec-003 §Interfaces And Contracts and §Required Behavior amendments; criterion (c)'s plan-task condition is met by [Plan-003](./plans/003-runtime-node-attach.md) T3.10–T3.12. - Priority: `P1`
- Owner: `unassigned`
- References: [ADR-025: Runtime Node Control-Plane Caller Authorization](./decisions/025-runtime-node-control-plane-caller-authorization.md) (**the governing decision — `accepted` 2026-08-10**; the ADR-010 / ADR-007 / ADR-012 entries below remain as the substrate and candidate-enforcement-point references they always were, not as alternatives still under consideration), [Spec-003 §Interfaces And Contracts + §Required Behavior](./specs/003-runtime-node-attach.md#interfaces-and-contracts) (the four `runtimenode.*` procedures; attach carries `participant_id`), [Plan-003 Phase 3](./plans/003-runtime-node-attach.md) (the attach / heartbeat / capabilityupdate / detach services — each resolves its target by `nodeId` + `session_id`), [ADR-010 §PASETO/WebAuthn/DPoP](./decisions/010-paseto-webauthn-mls-auth.md) (the caller-identity substrate on the tRPC context — the authority this guard must consult), [ADR-007 Collaboration Trust And Permission Model](./decisions/007-collaboration-trust-and-permission-model.md), [ADR-012 Cedar approval policy engine](./decisions/012-cedar-approval-policy-engine.md) (candidate enforcement point), [cross-plan-dependencies.md §NS-32](./architecture/cross-plan-dependencies.md#ns-32-plan-003-phase-3--control-plane-attach--heartbeat-services--version-floor-enforcement) — surfaced at the PR #143 Codex review (the four-procedure reconciliation).
- Summary: The four runtime-node control-plane procedures (`attach`, `heartbeat`, `capabilityupdate`, `detach`) resolve the target attachment row by `nodeId` (+ `session_id`) alone, with **no documented check that the authenticated caller OWNS that row**. attach carries `participant_id` in its request, but no procedure verifies that the caller identity established by the ADR-010 PASETO/DPoP credential on the tRPC context matches the attachment's owning participant. In a multi-participant session this is a horizontal-privilege-escalation / IDOR surface: a caller who learns another active `nodeId` could refresh that node's roster capabilities, mutate its presence/health, or detach it. This is the caller-identity **authorization** axis — distinct from, and orthogonal to, the capability-health **authority** model that Spec-003 ratifies (which governs _which_ health state a daemon may self-report, not _whether_ a caller may act on a given node). It is unspecified in Spec-003 and in ADR-010/012, it spans all four procedures (three of which already shipped resolving by `nodeId`), and its enforcement depends on the ADR-010 caller-identity substrate that other plans own — so it is a cross-cutting decision owed to an ADR, not a one-line spec clause (a bare "must authorize" without the mechanism would be a documented-pin-not-enforced no-op). **Shipped-surface update (2026-06-10, PR #150):** the namespace gained its first non-mutation — the control-plane-only `runtimenode.roster` query (the four mutations had all shipped via PR #145, 2026-06-09) — carrying the same router-tier authz-deferral posture as `session.read`: `AttachService.readRoster` returns an empty roster (`{nodes: []}`) for an unknown session, with session existence/authorization the router tier's concern, so the eventual caller-owns-the-node model MUST cover the roster READ (who may enumerate a session's node roster) alongside the four mutations.
- V1 Release Impact: Blocks safe V1 multi-participant exposure of the runtime-node surface. The four procedures may land functionally (the single-participant / trusted-session execution paths are unaffected), but the control-plane procedures MUST NOT be exposed to untrusted multi-participant traffic until the ownership guard is enforced — a collaboration product cannot ship a path where participant A mutates participant B's node.
- Exit Criteria: (a) an ADR (new ADR-NNN, or an ADR-010 / ADR-007 amendment) decides the runtime-node caller-authorization model — how the authenticated caller identity (ADR-010 PASETO/DPoP on the tRPC ctx) is resolved, and the ownership predicate each of the four procedures enforces before mutating an attachment row (caller participant == attachment owner, or a Cedar policy per ADR-012); (b) `Spec-003 §Interfaces And Contracts` records the authorization precondition for all four mutating procedures and the roster-read precondition (who may enumerate a session's node roster via `runtimenode.roster` — a session-scoped enumeration authorization, distinct from the per-row caller-owns-the-attachment-row predicate); (c) Plan-003 carries an implementation task wiring the guard into each of attach / heartbeat / capabilityupdate / detach and into the roster read, with tests proving a cross-owner mutation and an unauthorized roster enumeration are each refused with a typed authorization error; (d) the guard is enforced in code, not merely documented — a cross-owner mutation attempt and an unauthorized roster-read attempt each return the typed error.
- Revisit Trigger: the runtime-node control-plane procedures are sequenced for multi-participant exposure (the dominant trigger — must land before untrusted multi-participant traffic); OR ADR-010 / ADR-007 is next amended; OR any integration test demonstrates one participant's daemon reaching another participant's node.
