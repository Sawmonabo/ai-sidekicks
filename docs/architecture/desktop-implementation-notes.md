# Desktop App Implementation Notes

The implementation notes of [Spec-021: Desktop App And Renderer](../specs/021-desktop-app-and-renderer.md).

_This document captures architecture-relevant, non-normative implementation guidance; its primary-source citations are in [Spec-021 §Research Conducted](../specs/021-desktop-app-and-renderer.md#research-conducted)._

## Electron Version And Support Window

Electron 41 reached end-of-support on 2026-08-25 with the release of Electron 44.0.0 (Chromium 152.0.7977.54, Node 24.18.1); the supported majors are 44 / 43 / 42. V1 builds target **Electron 44.x**, pinned at 44.5.1, and [ADR-015 §Decision](../decisions/015-electron-desktop-app.md#decision) carries the 42 / 43 / 44 supported-branch subset of the GHSA-3c8v-cfp5-9885 floors with **44.x the only admissible V1 runtime**. Two facts of that line the console depends on: the detached-`WebContentsView` bounds fix (electron/electron PR #53031, closing #43257) landed on 44 and was backported to 42 / 43 late in their lives, so earlier point releases on those branches clear the CVE floor and still lack the fix — rather than carry a per-branch fix floor the release feed cannot verify, V1 admits 44.x alone, and the `browser` pane kind is buildable on nothing below it; and the Electron 40 renderer-clipboard deprecation stays enforced through §Renderer Bundle. One dependency rides the floor: Electron 44 is Node ABI 149, which no `better-sqlite3` 12.x release ships a prebuild for, so the daemon's binding moves to the 13.x Node-API line before or with the pin ([ADR-021 §Decision](../decisions/021-v1-toolchain-selection.md#decision)).

Electron has **no LTS lane**. The project team supports the latest three stable majors on an 8-week release cadence aligned with Chromium's 4-week stable channel, so a major goes end-of-support roughly every eight weeks.

**Consequence:** Plan-020 must budget two forced major-version upgrades in V1's first year after ship. Same-week patch adoption is required on security-advisory drops. This is the single largest recurring operational cost of choosing Electron and is accepted per ADR-015; Plan-020 must include release-engineering capacity for the cadence.

## Electron Fuses

Electron Fuses are build-time toggles on the shipped binary that harden the binary against misuse as a generic Node runtime or against injection vectors. The posture [Spec-021 §Security Hardening Baseline](../specs/021-desktop-app-and-renderer.md#security-hardening-baseline) declares (RunAsNode disabled, NodeOptions disabled, CLI inspect disabled, asar integrity enabled, OnlyLoadAppFromAsar enabled, cookie encryption enabled) matches the current Electron-documented production hardening recommendation and the posture VS Code, Slack, and 1Password ship with. `electron-builder` sets them from its `electronFuses` configuration and embeds the integrity digest itself, before signing ([Spec-021 §Security Hardening Baseline](../specs/021-desktop-app-and-renderer.md#security-hardening-baseline)).

The `LoadBrowserProcessSpecificV8Snapshot` fuse makes the main process load its V8 snapshot from a file of its own while every other process keeps its usual one ([Electron Fuses, `loadBrowserProcessSpecificV8Snapshot`](https://www.electronjs.org/docs/latest/tutorial/fuses#loadbrowserprocessspecificv8snapshot): "the main process uses the file called browser_v8_context_snapshot.bin for its V8 snapshot"). Electron ships no `browser_v8_context_snapshot.bin`, only the usual `v8_context_snapshot*.bin`, and a main process that finds no file of its own stops at start with `Error loading V8 startup snapshot file`. So the packaging step's after-pack hook, `afterPack` in `apps/desktop/build/browser-snapshot.ts`, copies Electron's own snapshot under that name, before `electron-builder` flips the fuses and signs the app.

## Detached Service Launch

The daemon is the person's own background service, never a child of the desktop app. Main starts it with Node's `child_process.spawn` and `detached: true`, its standard streams not connected to the app — the service keeps its own log file ([Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior)) — and the child handle released with `unref()`, as Node's documentation requires for a detached child to keep running after its parent exits, and reaches it through its socket — on Windows, the per-user named pipe `\\.\pipe\ai-sidekicks-<user SID>` — so nothing between main and the service rides a process channel of the app's own. The service is not started with Electron's `utilityProcess.fork`: a utility-process child dies when the app quits, and a quit must leave the service running.

Measured on Electron 44.5.1 on macOS and Electron 44.1.0 on Linux: a detached child survives the app's quit, SIGTERM and SIGKILL. On Linux a logout ends the detached child unless lingering is on, as it does the per-user service. Where a detached child does not survive, the service runs through the per-user service `sidekicks daemon install` sets up. On a Windows computer whose providers live in WSL 2, a per-user logon task starts the Windows half (`sidekicks-windows-half.exe`), which starts the daemon inside the distribution with `wsl.exe --exec` and serves the same per-user named pipe. On native Windows the service outlives the app as it does everywhere else: a detached child where a measurement on a Windows machine shows one survives a quit, and the per-user service otherwise.

`daemon.hello` is the handshake. `daemon.ping` is sent after 5 s of quiet on the link, which counts as dead after 20 s of silence, and the connection state is the `daemon.status` topic on `daemon.subscribe`; no heartbeat is polled on a timer. A crash restarts the service with the backoff [Spec-021 §Daemon Supervision Lifecycle](../specs/021-desktop-app-and-renderer.md#daemon-supervision-lifecycle) declares.

A quit flushes the service (`daemon.flush`) and leaves the service, every run and every terminal shell running, and no surface explains it. Only Settings › Runtime's `Stop` and `Restart` end work: main waits at most 10 seconds for the flush, sends `daemon.stop` and counts the service's drain bound from that send; the service answers the stop at once and waits at most the drain bound for writes in flight beside its terminal drain. A daemon still running after the drain bound gets SIGTERM and, 2 seconds later, SIGKILL, because a workflow step's thread that never started keeps the daemon's process from exiting; a stop that goes unanswered gets SIGTERM at once and SIGKILL once the drain bound and 2 seconds have passed ([Spec-006 §Required Behavior](../specs/006-local-ipc-and-daemon-control.md#required-behavior)).

## Native Keystore

`node-keytar` is archived by its maintainers (last release v7.9.0) and is **not** a supported dependency for new projects. The replacement this project adopts is **`@napi-rs/keyring`** 2.1.0 (MIT, 47 kB plus one native package per platform — a napi-rs Rust binding to the `keyring-rs` crate, self-described as a "100% compatible node-keytar alternative"). It supports macOS Keychain, Windows Credential Manager, and Linux Secret Service. It does **not** require libsecret on Linux (it uses `secret-service-rs`), which matters in headless CI, WSL, and Codespaces environments. It is also the replacement path used by the Microsoft Authentication Library for JS and the Azure Identity SDK.

Main keeps no entry in the operating system's keystore and holds no credential: this machine's DPoP key, the hosted account's tokens and every other secret are the background service's, each its own item in the operating system's credential store — the login keychain on macOS, Credential Manager on Windows, the Secret Service on Linux. On macOS and Linux the service opens each item through `@napi-rs/keyring`, on Linux with `{ linux: { store: "secret-service" } }` so the kernel keyring, which empties at reboot, is never used. On Windows, where that binding writes every entry at a roaming persistence, the service writes each Credential Manager entry through its Windows half at `CRED_PERSIST_LOCAL_MACHINE`, whether the service runs on Windows or in a WSL 2 distribution, so a Windows computer has one place for secrets on either side.

On Linux with no Secret Service answering, the service keeps its items in one file, `secrets.json` in its own data folder, readable by this account alone (mode `0600`), as `gh` and Codex do. It never falls back silently: Settings › Runtime then shows one line under the service's own, `Secrets are kept unencrypted in <path>, readable by this account alone, because no Secret Service is running.`, `<path>` being that file. A Mac keeps them in the same file from the approved logged-out service's takeover until `sidekicks daemon uninstall` moves them back, including after that service is turned off in Login Items & Extensions, and never while it waits for approval, because that service cannot reach the login keychain, and the line there ends `because the service runs while you are logged out.`, or `because the service was set up to run while you are logged out.` once that service is turned off in Login Items & Extensions; it is absent on every other machine.

## Build And Packaging

`electron-builder` **26.17.x** is the packaging tool for V1 (26.17.0, published 2026-09-26 under the `v26` dist-tag, its newest release). The channels it builds are exactly these: on macOS 13 and later (Electron 44's floor), arm64 and x64, a `.dmg` to install and a `.zip` for updates; on Windows 10 and later, x64 and arm64, an NSIS installer per user; on Linux x64 and arm64, an AppImage, and `.deb` and `.rpm` packages, which on install add the project's signed apt or dnf repository (`signed-by=/usr/share/keyrings/…`). There is no MSI, no Snap and no Flatpak: the MSI exists for an organization's deployment tools and the updater does not update it; AppImage, `.deb` and `.rpm` with the signed repository already reach every mainstream distribution; and Flathub requires building from source with no network, which `electron-builder`'s Flatpak target, built from prebuilt binaries, does not do. Electron 44 publishes no 32-bit build, so none ships, and Windows on ARM ships, its terminal sidecar included. The repository is hosted on Cloudsmith's open-source plan ("at least 50GB of artifact data + 200GB of package delivery for free", with an attribution link), because each release adds four packages of about 120 MB and GitHub Pages' 1 GB cap would fill within three releases; it keeps the last ten versions, and older packages stay on GitHub Releases. The app knows its install kind from the package type `electron-builder` records (`resources/package-type`), from `APPIMAGE`, and from the platform's own marks. The app icon is `apps/desktop/build/icon.icon`, set as `electron-builder`'s `mac.icon` and compiled by Apple's `actool`, which needs Xcode 26 on the build machine; an `.icns` made from it serves macOS before 26, and the Windows and Linux icon files are made from it too. Reasoning: cross-platform installer-format coverage is broader than Electron Forge's, production-proven at the scale of VS Code / 1Password / Slack, and integrates cleanly with `electron-updater` for the update path on macOS, Linux and Windows.

**Alternative considered:** Electron Forge. Forge v7.11.1 (2026-01-12) is the Electron team's officially-maintained packaging tool, and the electronjs.org docs recommend it as the default. The Forge README directs production users to v7.x. Forge wins on "closer to Electron's official cadence and less third-party surface." It loses on auto-update: Forge requires wiring `update.electronjs.org` or a custom updater, neither of which covers Linux at all.

Decision: `electron-builder` wins for Spec-021 because cross-platform auto-update on macOS + Windows + Linux is a V1 requirement (see §Auto-Updater below). Plan-020 pins `electron-builder` to the 26.17.x minor line (electron-builder is outside "official Electron support," per the Electron docs). **Electron binary materialization.** The 44.x line publishes no install script, and the change it inherits is **Electron 42.0's**, not 44's: `docs/breaking-changes.md` §Breaking API Changes (42.0) records both that `electron` "no longer downloads itself via `postinstall` script" and that `ELECTRON_SKIP_BINARY_DOWNLOAD` "is no longer supported, as its primary purpose was to prevent the `postinstall` script from running" — 41.6.1 published `postinstall: node install.js` and every manifest from 42 through 45 carries no `scripts` field at all — binary acquisition having moved into a lazy download at module scope in `npm/index.js`, which every `require('electron')` reaches. A plain `pnpm install` therefore plants the launcher shim and no `dist/`, and the first process to require Electron pays a **120–160 MB** platform download wherever it happens to run (130 MB for `darwin-arm64` at 44.5.1; 158 MB for `win32-x64`), including inside a test's own timeout. The binary is materialized at INSTALL time instead: `apps/desktop` carries an idempotent `postinstall` that runs Electron's own install entry point when the binary is absent, skips when it is present, fails closed if it is still absent afterwards, and honors `ELECTRON_SKIP_BINARY_DOWNLOAD` — the escape 42.0 dropped, reinstated by this wrapper on its own terms rather than by Electron's — so a CI leg that never launches Electron stays fast. Every consumer calls that one script rather than a second acquisition path, and the smoke harness refuses before spawning, naming the remedy, rather than timing out.

**Release files and reproducible builds:** A release publishes its files and a checksum list. Neither `electron-builder` nor Electron Forge guarantees bit-reproducible binaries out of the box, and `electron-builder` does not read `SOURCE_DATE_EPOCH` itself; V1 claims no reproducible build on any platform, and CI runs no reproducible-build job.

## Auto-Updater

The app updates through `electron-updater` **6.8.10** (published 2026-09-26, part of the `electron-builder` project) as shipped, with its stock GitHub provider and nothing of the project's on top. The provider reads the update files `electron-builder` publishes to the project's GitHub Releases, and `electron-updater` enforces the SHA-512 they list on the download. The operating system's code signature decides the rest on macOS and Windows. Squirrel.Windows is explicitly unsupported and must not be used. The update block's steps:

1. **`Checked`.** The provider reads the latest release's update file. Main refuses a release whose version is not above the last one seen, and `allowDowngrade` stays off; the last version seen is kept for the life of the install in main's own updater record, `userData/updater-state.json`, which main reads and writes while the service is down and no wire writes; it is application state, never a setting, and a missing or broken record reads as the installed version.
2. **`Downloading`.** `autoDownload` is off, so the download starts on the person's press. It is a blockmap delta where the platform has one — NSIS, the macOS zip once a previous update is cached, and AppImage — and the full artifact otherwise.
3. **`Checking the signature…`.** `electron-updater` checks the downloaded file's SHA-512 against the release's update file before `update-downloaded`, and on Windows it also checks the installer's publisher (`verifyUpdateCodeSignature`).
4. **`Ready to install`.** `autoInstallOnAppQuit` is off, so on macOS Squirrel.Mac is handed the update only when the person presses `Restart to finish` (`quitAndInstall()`) and never before the check has passed; left on, `electron-updater` would feed Squirrel.Mac before any listener could refuse the file.
5. **`Restart to finish`.** The restart asks nothing and stops no session, run or terminal shell, because the service keeps them running through it. After relaunch the daemon handshake runs. Neither `electron-updater` nor Electron's built-in `autoUpdater` rolls back, and the app adds no rollback of its own: a bad release is fixed by the next one.

Any failed check discards the file and draws `The update could not be verified and was not installed.` with `Try again`. A check is two HTTPS requests of a few kilobytes each, every four hours and at startup; the first release measures a check's bytes and a delta's size against the full artifact. The update file never sets a staged rollout (`stagingPercentage`), which exists to protect a population of users. An install a package manager put there is that package manager's to update: a `.deb` or `.rpm` install never runs `electron-updater`'s own Debian or RPM updater, which installs with `--allow-unauthenticated` or `--nogpgcheck` and so bypasses the repository's signature. The service updates on its own path, from Settings › Runtime and `sidekicks self-update`, checking the downloaded program against the SHA-256 the release's manifest lists for it, and nothing more.

**Alternative (not chosen):** Electron's built-in `autoUpdater` module uses Squirrel.Mac on macOS and Squirrel.Windows (or MSIX updater, auto-detected) on Windows; it has **no built-in Linux support**. The hosted `update.electronjs.org` service is restricted to public GitHub repos, macOS (DMG) + Windows (NSIS) only, and requires signed macOS builds. Neither covers V1's Linux requirement.

## Code Signing And Notarization

**CA/Browser Forum Ballot CSC-31 (effective 2026-03-01, per [CSCBR v3.10.0 §6.3.2](https://cabforum.org/uploads/CA-Browser-Forum-CSCBR-3.10.0.pdf)):** All publicly-trusted code-signing certificates issued on or after 2026-03-01 have a maximum validity of **460 days** (≈14 months). EV and non-EV certs are both affected uniformly. Hardware-token holders must physically rekey every ≤14 months (≤460 days) (literal "15 months" can equal 456–465 days depending on month lengths and may exceed the cap).

### macOS

- **Identity:** until the Apple Developer ID Application certificate exists ([BL-108](../backlog.md#bl-108-windows--macos-signing-procurement-evidence)), every macOS build is signed with the project's own self-signed code-signing identity, held as a release secret, with the same bundle identifier on every build. Squirrel.Mac requires an update to satisfy the running app's designated requirement: a self-signed identity's requirement names its certificate, so every later build signed with it meets it and one-press update works, where an ad-hoc signature's requirement is one build's `cdhash` and an unsigned app cannot update at all. The privacy permissions, which follow the designated requirement, stay granted across updates. The first launch still meets Gatekeeper's prompt for an app that is not notarized, which the person clears once; that prompt, and nothing else in the update path, waits on the certificate. Once it exists, the identity is the Developer ID Application certificate, issued under the $99/year Apple Developer Program membership.
- **Process:** Hardened runtime enabled on every build; once the Apple certificate exists, Apple notarization via `xcrun notarytool` (the deprecated `altool` command must not be used) + `xcrun stapler` to attach the notarization ticket to the artifact so it works offline.
- **Entitlements:** The hardened runtime must declare only what the app needs. V8/JIT commonly requires `com.apple.security.cs.allow-unsigned-executable-memory` and `com.apple.security.cs.allow-jit`; dynamic loading of native modules may require `com.apple.security.cs.allow-dyld-environment-variables`.
- **Operational risk:** Apple's notarization queue can take 24–120+ hours, per developer-forum reports. Plan-020's release pipeline must include **timeout + retry** logic rather than synchronous blocking on notarization.

### Windows

- **Path:** [SignPath Foundation](https://signpath.org)'s free code signing for open-source projects signs the Windows installer and `sidekicks-windows-half.exe`. The certificate is issued to SignPath Foundation, so Windows names `SignPath Foundation` as the publisher rather than AI Sidekicks. Eligibility, per SignPath's terms: an OSI license without commercial dual-licensing for any component, no proprietary components, active maintenance, an existing release, MFA on the maintainers' GitHub accounts, and a published code-signing policy on the project site; Microsoft's code-signing options page names it as the route for qualifying open-source projects. A finding that the project is not eligible goes back to the project's owner for a decision, and the signing path never changes silently. The signature removes SmartScreen's hard block on an unsigned file and keeps the one-press NSIS update path, and the updater checks each downloaded installer's publisher (§Auto-Updater). There is no Azure Artifact Signing account and no bought OV or EV certificate. Until that signing is in place ([BL-108](../backlog.md#bl-108-windows--macos-signing-procurement-evidence)), Windows builds publish unsigned: SmartScreen's prompt is cleared once with `Run anyway`, and the updater's publisher check starts with the first signed build.
- **Smart App Control reality:** Valid code signing is **not sufficient** for Smart App Control to allow a binary. SAC evaluates cert trust chain _and_ cloud reputation (Intelligent Security Graph). New binaries with low distribution get blocked until reputation builds, even with a valid signature. First-launch UX on Windows 11 will be rough until reputation accumulates; the mitigation is `Run anyway` guidance in the release notes and the README's install section, because the prompt shows before the app can run.
- **Windows 10 EOL:** Windows 10 reached end-of-support on 2025-10-14. V1 supports Windows 10 and 11, x64 and arm64. Because Windows 10 is EOL, Spec-021 accepts the security-posture implication of shipping to an EOL OS for V1; whether a later release drops Windows 10 is [Spec-021 §Open Questions](../specs/021-desktop-app-and-renderer.md#open-questions)'.

### Linux

There is no universal code-signing model for Linux; each format the project ships carries its own:

- **`.AppImage`** — optional embedded GPG signature (rarely verified by users); this project additionally publishes the artifact hash alongside the download in the release's checksum list (§Build And Packaging).
- **`.deb` / `.rpm`** — the project signs neither package itself: Cloudsmith's per-repository key signs each RPM on upload and the apt and dnf repository metadata, and a `.deb` is checked through apt's signed Release file. On install each package adds the project's signed apt or dnf repository on Cloudsmith, its key file under `/usr/share/keyrings/` and named by `signed-by`, as Debian's guidance for third-party repositories asks, so every later version arrives through the package manager with the repository's signature checked.
- **Snap and Flatpak** — none ships (§Build And Packaging).

`electron-builder` supports all of the above. No automatic signing beyond what each format specifies.

## Crash Reporting

Electron's built-in `crashReporter` module uses **Crashpad** (not Breakpad as older docs suggest) and covers the main process, the renderers and every other process the app starts.

Crash reports stay on the machine that crashed. Crashpad writes each crash to that machine only (`crashReporter.start({ uploadToServer: false })`, which keeps reports on disk in the app's own data folder), and the service turns each one into a report there: the process type, the app and service versions, the platform, and the crashing thread's stack as module names and offsets, symbolicated where symbols are at hand — Electron's own from `symbols.electronjs.org`, the product's from its release — with file paths cut to their file name and session ids replaced by stable hashes. A native minidump holds process heap memory, which for main holds the daemon session token, and a pre-upload scrubber cannot reach a minidump's bytes, so the raw minidump never leaves the machine; it is deleted with the diagnostic logs past `Keep diagnostic logs for`.

`Keep crash reports`, under the update block on Settings › General, is the one control for it: on by default, under `Reports stay on this machine, with personal data stripped.`, and off, no report is kept. Nothing sends a report anywhere. Any of the person's linked devices reads a machine's reports through Remote Control (`daemon.crashList`), the relay carrying the read and storing nothing, and `sidekicks crash list` reads them from the command line.

Symbolication runs once per crash, with symbol files fetched only for the modules in the stack, cached in the service's folder and aged out with the diagnostic logs. The parser is `minidump-stackwalk` 0.27.0 (MIT, from rust-minidump), measured before it is adopted. Declined: a crash service on an account the person holds, which adds a third party; a project-run sink that collects every install's reports, which serves other people; Sentry self-hosted, which needs 16 GB of memory and is FSL-licensed; and `mini-breakpad-server`, which is archived.

### Repeated renderer crashes

A crash the reload brings back would otherwise loop: a session that crashes the renderer when drawn, or a kept layout that cannot be read, is restored and crashes it again. Main therefore counts renderer crashes in a row and acts on each in three steps.

- **First and second crash: restore.** Main logs `render-process-gone` with its reason and exit code, and reacts on a later task, never inside the event's own handler, because a reload started from inside it can crash the main process (Electron PR #51900). It builds the hidden console document again, and the reloaded renderer reopens every window from its kept layout.
- **Third crash in a row: safe start.** Main reloads the renderer without the kept layout and marks the load as a safe start on the console document it serves, as it stamps the appearance record. The renderer opens one window on the sessions list, reads no kept window layout and leaves it untouched, and shows one line above the list: `The app restarted after repeated problems and did not reopen its windows.` with `Restore windows` beside it. `Restore windows` reopens every window from the kept layout and then ends the safe start through `window.endSafeStart`, so main keeps each window's place again; until then main keeps no places. A crash after it counts on from three, so it lands on the safe start again.
- **The count clears** once a reloaded renderer has run five minutes with no crash. Sessions live in the background service, so no step loses work.

The steps follow how established apps break the same loop: ChromeOS sets a safe-mode flag and stops restoring the workspace when Chrome crashes more than three times within thirty seconds; Firefox offers its session-restore page after two startup crashes and starts in Safe Mode on the third, and Firefox for Android stops restoring the open tab after two crashes in a row and clears that count once the app runs thirty seconds without one; Android's Rescue Party escalates step by step when a persistent app crashes more than five times in thirty seconds or `system_server` restarts more than five times in five minutes; and VS Code never reopens a crashed window by itself, offering `Reopen` with a `Don't restore editors` box because restoring often brings the same crash back.

- [VS Code `windowImpl.ts`](https://github.com/microsoft/vscode/blob/main/src/vs/platform/windows/electron-main/windowImpl.ts) — `The window terminated unexpectedly`, `Reopen` / `Close`, `Don't restore editors`

**Renderer import direction.** The renderer's folders form a directed acyclic graph, low to high: `shared → lib / styles / assets → routing → components / hooks → store → services → registries → features → layout → app`. A folder may import any folder below it and none above it, and no feature imports another; the fix for an upward edge is to move the symbol down to the lowest folder that needs it, never to deep-import around the barrel. This order is owned by the `dependency-cruiser` gate, because an ordering over the folders is a graph property rather than a grep. **An upward edge is a CI failure, not a review note** — as is a cycle, an orphan module, an import from the renderer into `src/main/` or `src/preload/` or back, and an import from `src/shared/` into anything but the contracts package.

## Row-Cost Instrumentation

One flag, off by default and visible only to whoever sets it, logs what drawing the live rows costs in a running session — the middle case and the slow cases rather than every row — so a slowdown can be caught where it happens, in a real session, rather than only under the endurance tier's own load. It draws nothing, adds no control and no setting, and carries no figure onto a surface; it is a diagnostic for whoever turned it on.

## Renderer Bundle

React + Vite per ADR-015; TypeScript strict. Vite produces ES module output; the main process loads the bundle via a custom protocol (not `file://`, because the `GrantFileProtocolExtraPrivileges` fuse is disabled) with strict CSP (no `eval`, no inline scripts, no `unsafe-eval`). The same front end runs in the web client and the phone apps, in WebKit as well as Chromium, so Vite's `build.cssTarget` names the Chromium the desktop's Electron carries and the Safari and iOS versions those hosts carry, and the build writes `-webkit-user-select` beside `user-select`; no prefixed property is written by hand, and WebKit ignores the unprefixed form.

**Renderer scheme privileges.** The custom scheme the bundle is served from must be registered through `protocol.registerSchemesAsPrivileged` as `standard: true` and `secure: true` **before** `app.ready`. On a non-standard scheme Chromium exposes neither IndexedDB nor `localStorage`, so the console's persisted layouts and pins — UI state only; drafts are never persisted ([Spec-021 §Persistence on the renderer scheme](../specs/021-desktop-app-and-renderer.md#persistence-on-the-renderer-scheme)) — would have no home; Plan-020 carries the registration as I-020-6.

**Renderer clipboard deprecation (Electron 40+):** Direct clipboard-API usage in renderer processes was deprecated in Electron 40. In the desktop app, clipboard access must be exposed via the preload bridge's `native.copyToClipboard` and `native.readClipboardText` surfaces and implemented in the main process. The desktop renderer must not call `navigator.clipboard.*` directly; CI lint must catch such imports. The web client's and the phone apps' bridges answer the same two members through the browser's Clipboard API and their shell's clipboard.
