# Security Architecture

## Purpose

Define the system's trust boundaries, permission layers, and transport security posture.

## Scope

This document covers identity, session ownership, device and machine trust, approvals, capability grants, and transport boundaries.

## Context

The product combines one account, several of that account's devices, one or more machines, and local code execution. Security depends on not collapsing those concerns into one flat trust model: authenticating the account says nothing about which device is acting, and neither says a machine may execute.

## Responsibilities

- authenticate the user and authorize access to their own sessions
- distinguish device trust from machine trust
- govern tool, file, network, and execution permissions
- protect remote transport and relay paths
- preserve auditable approval and grant history

## Component Boundaries

| Component | Responsibility |
| --- | --- |
| `Identity And Session Authorization` | Authenticates the user and authorizes access to sessions they own. A machine signs in to the hosted account through its background service, which runs an authorization-code sign-in (RFC 8252, PKCE, PAR, DPoP) whether Settings › Devices' `Sign in` or `sidekicks account login` started it. Passkeys (WebAuthn) are used only in a browser and the iPhone app: on the relay's sign-in page, to approve a machine's sign-in and to make a new account's first passkey, and in the web client and the iPhone app, to sign in and to link a device with no other device at hand; the desktop app carries no WebAuthn. Tokens: PASETO v4 — access tokens (`v4.public`, 15 min, never stored) presented with a DPoP proof; a refresh token bound to the machine's DPoP key, kept as its own item in the machine's credential store, spent and replaced at each trade, lasting until sign-out or revocation. |
| `Approval Policy Engine` | Evaluates and records approval requests and resolutions. A provider's ask gets its designed answer from plain code in the service: it refuses `claude agents`, `claude daemon` and `--bg` and keeps Claude Code's own switch that turns them off pinned, allows an agent's own memory `.md` file, and answers for Codex where Codex has no command of its own. Only the workflow actions (`workflow::author`, `workflow::start`, `workflow::cancel`, `workflow::resume`) use Cedar (CNCF sandbox) with principal-action-resource-context model: their built-in rules are `.cedar` files in the service's own source, compiled into the service with it and changed only by an app update, like any other code, and evaluated in-process by `cedar-policy`'s `Authorizer`, linked into the service ([ADR-012](../decisions/012-cedar-approval-policy-engine.md)). Messaging other sessions and the browser are gated by the calling session's permission level, and Cedar holds no rules for them. |
| `Device And Machine Trust` | The account's append-only statement chain (`device.linked`, `device.renamed`, `device.revoked`, `account.passkey.added`, `account.passkey.removed`, `machine.added`, `machine.renamed`, `machine.removed`), which every machine verifies itself to decide which device and machine keys it trusts, and each machine's registration (id, owning user, public key, name, platform, version). |
| `Transport Security Layer` | Protects local IPC, client-daemon, and relay/control-plane traffic. Local daemon: socket reachability plus, from a process the daemon did not start itself, a 256-bit session token (mode 0600, rotated per restart) presented by the CLI and, on Linux and Windows, by the desktop app's client helper, or on macOS the client helper's code signature — see §Local Daemon Authentication for the model. Control plane: HTTPS/TLS. Another device: one end-to-end channel per device and machine, carried by a WebRTC data channel straight between the two wherever they can reach each other and by the relay otherwise, on the Noise Protocol Framework's two profiles, `Noise_KK_25519_AESGCM_SHA256` offered first and `Noise_KK_25519_ChaChaPoly_SHA256` second, with a fresh handshake on every connection and every 10 minutes, the relay seeing ids, the profile, sizes and times and nothing else, and the direct path's own DTLS encrypting beneath the channel (see §Relay Authentication And Encryption and [ADR-010](../decisions/010-tokens-passkeys-and-the-remote-channel.md)). |
| `Audit Layer` | Records grants, denials, escalations, and revocations. |

## Data Flow

1. Identity claims enter through the control plane.
2. A connection carries its device, and a write records the device it came from; nothing checks ownership per caller.
3. A device reaches a machine only over a channel whose keys that machine finds trusted in the account's statement chain.
4. Runs request tool, file, or network permissions when needed.
5. Approval decisions are recorded and propagated back into the run engine.

## Trust Boundaries

- Owning a session does not imply local machine trust.
- Reaching a machine over the channel does not bypass approval policy.
- Both remote carriers, the relay and the direct path, must be treated as less trusted than local IPC.
- The local daemon remains the enforcement point for local execution permissions.

## Failure Modes

- A linked device is over-trusted and gains unintended execution capability.
- Approval rules outlive their intended scope and create hidden privilege drift.
- Transport authentication succeeds while local authorization policy is misapplied.
- Relay or remote-path compromise exposes data that should have remained end-to-end protected.
- The direct path's socket answers a peer that does not hold the credentials exchanged inside the sealed channel.

## Authentication Implementation Specification

### Local Daemon Authentication

The local daemon uses a layered trust model based on socket reachability **plus** proof that the caller is the person's own client **plus** the connecting process's place in the process tree: a process the daemon itself started is never the machine's own client, whatever token it holds. The proof is a 256-bit session token, except for the packaged desktop app's client helper on macOS, which holds no token and is admitted by its code signature. The desktop **renderer is not a direct daemon client** — all renderer-originated requests travel over a `MessagePort` that main hands the page through the preload, to the client helper, which checks each against its method allowlist and params check, carries it on its own daemon connection, whose `connection.initialize` presented the session token or, on macOS, was admitted by the helper's signature, and returns only the sanitized reply. Main's own daemon calls reach the helper over `parentPort`, through the same allowlist, and main keeps the file tokens; neither main nor the renderer holds the session token. See [Spec-021 §Trust Stance](../specs/021-desktop-app-and-renderer.md#trust-stance) and [container-architecture.md §Trust Boundaries](./container-architecture.md#trust-boundaries) for the renderer-untrusted stance this section follows.

**Socket reachability model:**

| Client Type | Auth Required | Rationale |
| --- | --- | --- |
| Client helper of the desktop app (same machine) | On macOS: socket access + the helper's code signature. On Linux and Windows, and in an unpackaged development build on macOS: socket access + 256-bit session token | The client helper is the daemon client for the desktop app. On macOS it holds no token: the daemon admits it by its code signature and the signature of the app that started it (the desktop's client helper below). Elsewhere it holds the daemon session token, which neither main nor the renderer holds. It holds no control-plane credential, since the service holds the machine's DPoP key and tokens and makes every control-plane call, per [Spec-021 §Trust Stance](../specs/021-desktop-app-and-renderer.md#trust-stance); it forwards main's and the renderer's requests over its own connection, with response payloads sanitized. |
| CLI (same machine) | Socket access + 256-bit session token | Same-user process; socket permissions (mode 0700 on macOS and Linux, a user-only access list on the Windows pipe) prevent cross-user access; token is defense-in-depth against misconfigured socket permissions. |
| External process (same machine) | 256-bit session token (required) | Untrusted processes on the same machine must present a token. |
| A process the daemon started (same machine) | Refused, token or not | A provider process, a command an agent runs, a repository's git hook or setup command, and anything they start in turn descend from the daemon, and on macOS the system holds the daemon responsible for them; their hello is refused with `auth.callerRefused` (the caller check below). |
| Desktop renderer (same machine) | Not a daemon client | All renderer-originated requests travel over the `MessagePort` main hands the page through the preload, to the client helper, which checks each against its method allowlist and forwards it over its own connection. The renderer never holds the daemon session token, PASETO access tokens, or the DPoP key per [Spec-021 §Trust Stance](../specs/021-desktop-app-and-renderer.md#trust-stance). |
| Another of the person's devices | Not a daemon-socket client | It reaches the daemon only over its end-to-end channel, on the relay or on the direct path (§Relay Authentication And Encryption). The service binds no TCP port for its clients; the direct path's UDP socket exists only while a device is on it and answers only an ICE check carrying the password exchanged inside that channel. |

**Session token specification:**

- **Generation:** CSPRNG (`getrandom::fill` over 32 bytes) producing a 256-bit token
- **Storage:** Written with owner-only access: on macOS and Linux `$XDG_RUNTIME_DIR/ai-sidekicks/daemon.token` where the session sets `XDG_RUNTIME_DIR` (a Linux login session does), and otherwise `<temporary folder>/ai-sidekicks-<uid>/daemon.token`, the temporary folder being the first of `TMPDIR`, `TMP` and `TEMP` that is set and not empty, else `/tmp` (always the case on macOS, which never sets `XDG_RUNTIME_DIR`, where that is the per-user `$TMPDIR`), the folder resolved in `sidekicks-platforms`, never through `std::env::temp_dir()`, each with mode `0600` in a folder of mode `0700` beside `daemon.sock`; on Windows `%LOCALAPPDATA%\ai-sidekicks\run\daemon.token` with an access list that grants the person alone. The daemon makes a new token at every start, so clients read the file at every connect. Inside a WSL 2 distribution each WSL server writes the token's copy into its own run folder at each start, beside its Unix socket (mode `0600`), and every local client of that socket sends the token as its first message.
- **Rotation:** Regenerated on every daemon restart. Previous tokens are immediately invalidated.
- **Kept from agents:** The token file is on the curated credential list every run's posture names (`crates/sidekicks-provider/src/run/posture.rs`), as one file beside the home folder's `.ssh` and `.aws`: Claude Code receives it as a `Read(//<path>)` deny rule, which its file tools and, at `sandboxed`, its Bash sandbox honor, and Codex as a `deny` entry in every permission profile the daemon builds, so a sandboxed command reading it fails with `Operation not permitted`. At a level with no sandbox, and for a command that runs outside the sandbox, the deny binds only the file commands Claude Code recognizes in Bash; the known reach of the unsandboxed and the sandboxed levels, below, says what holds there.
- **Verification:** Constant-time comparison (`subtle`'s `ConstantTimeEq`, after a length check) to prevent timing attacks
- **Transport:** The first message on every connection: `connection.initialize` carries it as `sessionToken`. A hello without it or with a wrong one is refused with `auth.token.invalid`, and nothing more is served on that connection, unless on macOS the hello carries no token and comes from the desktop's signed client helper (below)

**Token presentation requirements:**

- **Always required** for the CLI, and for the desktop's client helper on Linux and Windows and in an unpackaged development build on macOS. Each reads the token file at every connect, never once at its own startup, because the daemon makes a new token at every restart, and presents it. The packaged desktop on macOS never reads the token file: its client helper sends no token and is admitted by its code signature. Socket permissions are defense-in-depth; the token is primary. The renderer is not a direct daemon client, and CLI presentation of the token is not optional.
- **Required** for any external integration or tool connecting to the daemon socket.
- **Not applicable** to the desktop renderer, which is not a direct daemon client per [Spec-021 §Trust Stance](../specs/021-desktop-app-and-renderer.md#trust-stance).
- **Caller check:** At each connect the daemon reads from the system which process is at the client's end of the connection (`SO_PEERPIDFD` on Linux, a process descriptor recorded at the connect; `LOCAL_PEERTOKEN` on macOS, whose audit token names the process that last used that end, the connecting one unless it handed the socket to another process that used it first; both through `getsockopt` in `sidekicks-platforms`, which `crates/sidekicks-ipc/src/caller_process/` calls), and at the hello, before the token is judged, judges where that process came from. On Linux it walks that process's parents (field 4 of `/proc/<pid>/stat`); on macOS it reads the process's responsible process (below). A chain that reaches the daemon refuses the hello with `auth.callerRefused` and latches the connection refused, unless the daemon's own child on it is a terminal the daemon opened for the person, whose programs are the person's own, or the caller is the `hook provider` hook of the person's own Codex service the daemon dials for `Reach Codex sessions started in a terminal`, which is admitted for that service's hook methods only, and only as the daemon's own program at a hook's exact place in the process tree under that service — Codex's own shell under the service, then `hook provider` — with no command wrapper and no `codex exec-server` on the chain and each link pinned; that service has no `thread/start` the daemon sends, so its hooks cannot be tool-hook rows without the route's secret on its command line. No other process in the daemon's tree has standing: Codex calls the daemon's hooks on every conversation the daemon starts over its own connection to the `sidekicks` tool server, `hook provider` running a helper's own command handlers dials nothing, and Claude Code reaches a signed-in tool server only through the daemon, which fronts it ([Spec-024 §OAuth Orchestration](../specs/024-mcp-server-configuration-and-governance.md#oauth-orchestration)). A chain that ends at the system's first process, as the desktop's client helper, which the desktop's main process starts, and a command line run from the person's own terminal do, goes on to the token. A chain through a process serving a provider service the daemon holds a connection to is refused the same way: for each Codex service socket it dials, the daemon reads the process at the other end from the system and holds it while the socket is open (`crates/sidekicks-ipc/src/caller_process/provider_services.rs`), so a command a session runs on the person's own Codex service, which the daemon dials but never starts, is refused as one the daemon started is; a Codex service the daemon started descends from it already. A caller the system cannot name, one that closed its end before the daemon read it, and one whose chain cannot be read because a process on it ended, are refused. On Linux a `/proc` mounted with `hidepid=2` hides other users' processes ([proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)), so a chain through another user's process, such as a root `sshd` or `login`, reads as ended, and a command line the person runs under such a login is refused. Programs in a terminal the daemon opened for the person pass as the person's own, so a command an agent types into one of a session's shells must not carry the person's standing to the daemon; [Plan-021](../plans/021-terminal.md) T-021-3B-7, which builds that typing, keeps it from doing so. On Linux, and in a WSL 2 distribution, the check pins the caller with `SO_PEERPIDFD` and each parent with `pidfd_open`, reading the child's parent again after pinning it, so a process id handed to another process during the walk is never judged in its place; the daemon and each WSL server set `PR_SET_CHILD_SUBREAPER` and reap the orphans that reach them, so a process orphaned inside the daemon's tree is adopted by the daemon or its WSL server rather than by the system's first process, and stays refused. This needs Linux 6.5 or later, the first with `SO_PEERPIDFD`; an older kernel refuses every caller. On macOS the check reads the caller's responsible process, the process the system charges for it and asks the person about in a privacy prompt, instead of walking its parents: a process keeps its responsible process through a double fork, `setsid` and its parent's exit, and a child inherits it unless its start disclaims it. The daemon makes itself its own: a per-user launchd agent already is, and otherwise the first thing its start does, before any thread, socket or lock, is run its own program again in place (`posix_spawn` with `POSIX_SPAWN_SETEXEC` and the disclaim attribute), which keeps its process id, so whatever started it still holds it; a start that is still not its own responsible process after that fails. A start whose responsible process runs the daemon's own program (the same program path, each process read pinned) does not run again: it stays under that daemon, which refuses it and everything it starts as its own, and a responsible process whose program file is gone fails the start. Every terminal the daemon opens runs its shell the same way, so a terminal's programs read that shell as responsible and are the person's own. The daemon's `shell` mode, through which each terminal's shell starts, does so only for a process the daemon started: the daemon hands the mode one end of a socket pair and writes on the other the id of the process it started, and the mode starts its program as its own responsible process only when that id is its own, its parent wrote it, and that parent is its own responsible process. A command an agent runs that starts the daemon's program in that mode has no such parent, since every process an agent runs reads the daemon as responsible, so the mode refuses it and starts nothing. A caller whose responsible process is the daemon, compared by unique id, is refused with `auth.callerRefused` whatever token it carries, and so is one that ended before the read. The parents are then walked only while the daemon holds a connection to a provider service, and only to look for that service. The calls are private to the system (`responsibility_get_uniqueid_responsible_for_pid`, `responsibility_get_pid_responsible_for_pid` and `responsibility_spawnattrs_setdisclaim`, exported by `libquarantine`), each looked up by name once: where one is missing the daemon does not start, and a caller it cannot read is answered as an internal error, never admitted. The caller read from `LOCAL_PEERTOKEN` is pinned by its unique id, taken through a read the kernel answers only while the token's id version still names that process; each parent is pinned by re-reading the child's parent through the child's pin, before and after the parent's unique id is read, so every later read names the process pinned; the token is not proof of who connected, since XNU derives it from `last_pid`. On Windows no caller is read, so every caller is refused until the daemon's named pipe is served.
- **The desktop's client helper on macOS:** a hello with no token is served when its caller meets the helper's code requirement and its responsible process is another process that meets the app's. The daemon looks each up from the audit token (`SecCodeCopyGuestWithAttributes`, then `SecCodeCheckValidity`). At start it reads its own signature and compiles each requirement once, in the form that signature allows, the identifier being the app's bundle identifier (`APP_BUNDLE_IDENTIFIER` in `crates/sidekicks-contracts`) followed by `.helper` for the helper, and the bundle identifier itself for the app. With a Team ID, as the person's own builds signed with their Apple Development identity have, the form is `anchor apple generic and identifier "<identifier>" and certificate leaf[subject.OU] = "<the daemon's Team ID>" and ! entitlement["com.apple.security.cs.disable-library-validation"] exists`. With a leaf certificate but no Team ID, as a build published for other people under the project's self-signed identity has, the form is `identifier "<identifier>" and certificate leaf = H"<the SHA-1 of the daemon's own leaf certificate>"`, with no library-validation clause, because a self-signed Electron app runs with library validation off. With neither, as a development build run from `cargo` has, no client is admitted by signature. A requirement that does not compile fails the start. The app's clause refuses a process that took over a connection and then ran the helper's program, since such a process reads itself or whatever started it as responsible; the desktop never starts its helper with `disclaim`. The Team ID form refuses code with library validation off, so no library planted in the installed app runs inside a helper that passes. The leaf form's guard is weaker: a library planted in the installed app of a self-signed build loads into the signed helper, which then passes, so a process that can write into the installed app is admitted as the desktop there. A code that fails the requirement, changed on disk or ended during the check reads as not the client, and the hello falls to the token; at most four signature checks run at once. On Linux and Windows no client is admitted by signature.
- **The second socket:** the daemon's HTTP socket that serves the terminal bridge plugin alone ([ADR-009](../decisions/009-json-rpc-ipc-wire-format.md), [ADR-035](../decisions/035-claude-code-mods-are-an-optional-terminal-bridge.md)) makes the caller check above, with the same exceptions, and takes the daemon token as `Authorization: Bearer <token>` on every request, refusing one without it or with a wrong one with `401`; the plugin reads the token with `$.fs.read` from the run folder it finds with `$.env.get`, and reads it again after a `401`, since the daemon makes a new token at every start. It mints a terminal session's entry for the `sidekicks` tool server only to a caller that passes the check, and that entry carries no more standing than a hosted session's entry. A peer-delivery hand-off is a hint: its row is drawn once it matches the peer frame the daemon reads off the receiving session's stream, and a hand-off that matches nothing draws nothing. In a WSL 2 distribution the WSL server's bridge socket does the same, with its own caller check. On Windows no documented call names the process at the other end of an AF_UNIX socket, so a probe is owed before unit `windows` ([Windows Service Probes](../operations/windows-service-probes.md)): `SIO_AF_UNIX_GETPEERPID` on the listener, or the bridge over the per-user pipe if a mod's `socketPath` reaches one; until then the socket there is guarded by the token and its access list.
- **The unsandboxed levels' known reach:** three levels run an agent's shell commands with no sandbox: Claude Code's `reviewed`, which is its auto mode, and `yolo` on Claude Code and on Codex. Claude Code's Bash sandbox is off by default ([Claude Code sandboxing §What the sandbox restricts](https://code.claude.com/docs/en/sandboxing#what-the-sandbox-restricts)) and works alongside auto mode only when turned on ([sandboxing §Permission modes](https://code.claude.com/docs/en/sandboxing#permission-modes), [§Sandbox modes](https://code.claude.com/docs/en/sandboxing#sandbox-modes)), and the daemon turns it on at `sandboxed` alone ([Plan-003](../plans/003-provider-driver-contract-and-capabilities-phase-3.md) T3.15 builds that leg); without it, its `Read` deny rules bind its file tools and the file commands it recognizes in Bash (`cat`, `head`, `tail`, `sed`, `tee`), but not a command that reads the file without naming it or a script that opens the file itself ([Claude Code permissions §Read and Edit](https://code.claude.com/docs/en/permissions#read-and-edit)), which only the sandbox they are merged into stops ([sandboxing §Permission rules](https://code.claude.com/docs/en/sandboxing#permission-rules)). Codex at `yolo` runs under its own `:danger-full-access` profile (`crates/sidekicks-provider/src/driver/codex/permission_level.rs`), not one of the daemon's profiles that carry the deny, and a deny is enforced only inside a profile's sandbox: with Codex 0.162.0, a sandboxed command reading a file one deny entry names fails with `Operation not permitted`. At those levels a command can read the token file. The caller check stops it while it stays in the daemon's tree, but on Linux and Windows the parent chain is what the system reports (`SO_PEERCRED` in [unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html) and the parent field of [proc_pid_stat(5)](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)), and a process leaves that tree on Windows when the command orphans it, since a process whose parent in the daemon's tree has exited reads as the person's own there (Linux and WSL 2 keep it, through the subreaper), and on every system when it has another program start it (`launchctl`, `open`, `osascript`, `systemd-run`); such a process reads as the person's own, and with the token it is served as the person. On macOS an orphaned or doubly forked process keeps the daemon as its responsible process, so besides having another program start it, as above, three escapes remain: a command that makes its own child its own responsible process with the private disclaim call, as Homebrew's sandboxed build workers, LLDB's debuggee and Deno's desktop tool do for theirs, which the daemon's own `shell` mode does not do for it (above), nor does the daemon's own start, which stays under the daemon running the agent (above), though a copy of the daemon's program at another path reads as another program and re-runs as its own responsible process, as any program calling the disclaim does; an orphan that outlives the daemon instance that started it, since a process whose responsible process has exited reads itself as responsible; and an orphan of a Codex service the person runs (below), which no system's subreaper reaches. On Windows a same-user process can also start a child whose recorded parent is another process (`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`), which the start-time test does not catch, so the child reads as that other process's. At Codex's `yolo` a command the person's own Codex service started also passes once the daemon's connection to that service has closed, if it is still running then, since the service is held only while that connection is open. At Claude Code's `reviewed` the only guard is the general judgment of Claude Code's own auto-mode classifier: none of its default block rules names this file, the nearest being "Reading credentials that belong to the host rather than to your task, such as node certificates or the node's container-registry auth" and "Printing a live credential or token into the transcript or a file" ([Claude Code permission modes §What the classifier blocks by default](https://code.claude.com/docs/en/permission-modes#what-the-classifier-blocks-by-default)). At `yolo`, on Claude Code and on Codex, nothing guards it.
  - **The saved MCP sign-ins.** On Windows and Linux, and in a WSL 2 distribution through interop, an agent's command that runs unsandboxed can read the daemon's saved MCP sign-ins from the operating system's store, as it can the person's other saved logins and the providers' own (Claude Code keeps its MCP sign-ins in a mode-0600 file there, [ADR-038 §Context](../decisions/038-mcp-credential-custody.md#context)): Windows' Credential Manager reads a credential from the set of the caller's logon session with no per-program check ([CredReadW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw)), and on Linux systemd's credential service opens the daemon's sealed items for any process of the person. On native Windows Claude Code runs every command unsandboxed ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing): "On native Windows, Claude Code runs commands unsandboxed"), and on Linux and in WSL 2 its sandbox stops a command reaching a socket only with its optional seccomp filter. On macOS the keychain item trusts only the daemon. The daemon and each WSL server call `prctl(PR_SET_DUMPABLE, 0)` on Linux, so another process of the same person cannot read their memory: neither writes a core dump, and a debugger attaches to them only as root ([PR_SET_DUMPABLE(2const)](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), [ptrace(2)](https://man7.org/linux/man-pages/man2/ptrace.2.html)). The daemon runs as the person, under no separate account.
  - **A Codex hook that fails.** The daemon's hooks on Codex are Codex's own tool-hook rows on the daemon's `sidekicks_hooks` entry, and Codex lets the call through when one of them errors, runs past its timeout, or finds that entry's connection lost in the middle of a conversation ([codex.md §Hooks and their trust](../reference/provider-wire/codex.md#hooks-and-their-trust)), so a pause, a deny or a hold on such a call does not happen.
- **Privacy prompts on macOS:** since the daemon is its own responsible process, macOS charges to the daemon's program every privacy prompt (the Desktop, Documents and Downloads folders, Automation and the like) that an agent's command triggers, and a denial holds for every session until the person changes it in System Settings. A program run in a terminal the daemon opened is charged to that terminal's shell, so its prompts name the shell's program.
- **The sandboxed levels' known reach:** at Claude Code's `sandboxed` a command inside the sandbox cannot read the token file, but not every command stays inside. The daemon passes `excludedCommands` empty in the `--settings` layer it starts Claude Code with and never sets `allowUnsandboxedCommands`, so the sandbox is not admin-required, and Claude Code then also takes `excludedCommands` from a repository's `.claude/settings.json` ([sandboxing §Repository settings under an admin-required sandbox](https://code.claude.com/docs/en/sandboxing#repository-settings-under-an-admin-required-sandbox)); a command such an entry names runs outside the sandbox with the person's full access, as hooks do ([sandboxing §What runs outside the sandbox](https://code.claude.com/docs/en/sandboxing#what-runs-outside-the-sandbox)), and there the `Read` deny binds only the file commands Claude Code recognizes. A repository's hooks in its settings files run too, since the daemon starts Claude Code with `-p`, which never asks for workspace trust ([Claude Code permissions §What runs before you trust a folder](https://code.claude.com/docs/en/permissions#what-runs-before-you-trust-a-folder)). Such a command or hook can read the token, and then only the caller check stands between it and the daemon, open to the same escapes from the daemon's tree as at the unsandboxed levels. Inside Claude Code's sandbox a command cannot reach the daemon's socket at all: the sandbox refuses every Unix socket while `allowUnixSockets` is unset ([Claude Code settings](https://code.claude.com/docs/en/settings)), which the daemon never sets. The daemon sends Codex no network setting: what an agent on Codex may do is set by the session's permission level, `yolo` being Codex's own full access, and below it by whatever Codex's own sandbox and the project's configuration allow. With Codex 0.163.0, a trusted project's `.codex/config.toml` that adds a Unix-socket entry for the daemon's socket reaches nothing by itself, and one that sets the profile's `network` `enabled = true` lets a sandboxed command connect to the socket. Whatever Codex lets a command reach, a command an agent runs that reaches the socket is refused, because the caller check recognizes it as the daemon's own: on macOS the daemon is its responsible process, and on Linux it descends from the daemon. At Codex's levels below `yolo` the deny holds against a repository's own Codex configuration. Codex reads a project's `.codex/` only when the person has marked the project trusted, below the overrides the daemon sends ([Codex config basics](https://learn.chatgpt.com/docs/config-file/config-basic)), and the daemon never marks one. With Codex 0.162.0 and a trusted project whose `.codex/config.toml` gave the daemon's profile read access to the file, made it extend `:danger-full-access`, made the file's folder or `:root` writable, or set `default_permissions`, `sandbox_mode` or a config `profile`, and whose `.codex/rules` let `cat` run outside the sandbox ([Codex rules](https://learn.chatgpt.com/docs/agent-configuration/rules)), reading the file still failed with `Operation not permitted`, also for a command that asked to run outside the sandbox and was allowed to. A trusted project's `.codex/config.toml` does merge filesystem entries the daemon's profile leaves unnamed into that profile, so it can make other folders writable, the daemon's run folder among them; a sandboxed command cannot write the project's `.codex/` itself.
- **On Windows the daemon's socket is a named pipe**, `\\.\pipe\ai-sidekicks-<user SID>`, one per person. On every Windows computer the service is the native daemon, started by a per-user logon task, and it serves the pipe in its own process through `sidekicks-platforms`' pipe code (tokio `ServerOptions` with `first_pipe_instance`, `reject_remote_clients` and the user-only access list). The server grants the person's SID alone, refuses remote clients, fails closed when the name is already held, and closes any client that is not the person or that descends from a process the service started, read through `GetNamedPipeClientProcessId` and the client's parent chain as the caller check reads a socket's. Windows never moves a process to a new parent: a process keeps its creator's id after the creator exits, and that id can be reused, so every chain from the person's own terminal reaches a parent that has gone (`userinit.exe` starts Explorer and exits). A parent that cannot be opened, or that started after its child because it took a freed id, therefore ends the chain the way the system's first process ends it on macOS and Linux, and the chain is judged by what was read up to it; the client (`sidekicks-client`, through `sidekicks-platforms`' pipe code: the standard library's `OpenOptions` with `FILE_FLAG_OVERLAPPED` and `security_qos_flags(SECURITY_IDENTIFICATION)`, which sets `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`) opens the pipe at identification level and, before it writes a byte, checks that the process serving the pipe runs as the person, through `GetNamedPipeServerProcessId`, that process token's user and `EqualSid`, and that the run folder holding the token is private: owned by the person, SYSTEM or the Administrators, with an access list (`GetSecurityInfo`) that lets in no other account. The server check reads a process id and then opens it, so a server that exits after handing its pipe to another process passes when its id has gone to one of the person's own processes; the daemon's token, demanded as the first message and readable by no other account, is the remaining gate. A session in a WSL 2 distribution runs through that distribution's WSL server, which the daemon reaches over the standard input and output of the `wsl.exe` it started, so the channel is the daemon's own child's and no port or socket on Windows serves it. **The WSL server's Unix socket makes the daemon socket's caller check.** That socket, which the in-distribution CLI and the `hook provider` hooks of that place's terminal Codex service dial, pins the caller at each connect with `SO_PEERPIDFD` and, at the hello and before the token is judged, walks its parents in `/proc` as the daemon's socket does, pinning each parent with `pidfd_open`. It refuses with `auth.callerRefused` a chain that reaches the WSL server, and one through a process serving that place's terminal Codex service, which the daemon dials, with the exceptions and the one `hook provider` admission the daemon's socket makes (the caller check above). Its terminal bridge's HTTP socket makes the same check and takes the token as the daemon's second socket does (the second socket above). The token's copy in the server's run folder is readable by every process of the person, so the token alone is no gate. The `sidekicks` tool server's loopback port inside a distribution is TCP, where no caller can be read, and stays gated by each session's secret. The command channel's folders there are each conversation's own folder, each party known by the public key read from `/proc/<pid>/cmdline`, and Codex's pass-through relay there is gated by its own bearer token. The inboxes the daemon serves for Claude Code sessions, its own inbox per place and each cross-place inbox, take the gate Claude Code's own inbox has: on Windows a pipe with the daemon pipe's user-only access list, and in a distribution a socket of mode `0600`. They make no caller check, because a frame is a peer message, which the receiving session acts on under its own permission level as it would words typed there; the known reach is that any process of the person's, an agent's command among them, can write a frame, as it can to Claude Code's own inbox.

### Control-Plane Authentication

**PASETO v4 access tokens (v4.public):**

```
Header: v4.public
Payload: {
  sub: UserId,          // user UUID
  iss: "ai-sidekicks-cp",     // issuer: control plane
  aud: "ai-sidekicks-api",    // audience: API endpoints
  exp: <iat + 900 s>,         // 15-minute TTL, an RFC 3339 instant
  iat: <RFC 3339 instant>,    // PASETO writes its times as RFC 3339 strings
  jti: <unique_token_id>,     // for revocation tracking
  cnf: {                      // DPoP confirmation claim
    jkt: <JWK_thumbprint>     // SHA-256 thumbprint of client's public key
  },
  scope: "session:read session:write run:create"  // space-delimited scopes
}
Signed with: Ed25519 signing key (control plane's private key)
```

**PASETO v4 refresh tokens (v4.local):**

```
Header: v4.local
Payload: {
  sub: UserId,
  iss: "ai-sidekicks-cp",
  iat: <RFC 3339 instant>,
  jti: <unique_token_id>,
  cnf: { jkt: <JWK_thumbprint> }, // the machine's DPoP key
  family: <rotation_family_id> // tracks rotation chain for reuse detection
}
Encrypted with: PASETO v4.local (XChaCha20 stream + BLAKE2b-MAC, encrypt-then-MAC; **not** XChaCha20-Poly1305 AEAD) under the control plane's symmetric key — per [ADR-010 §PASETO v4 Implementation Library](../decisions/010-tokens-passkeys-and-the-remote-channel.md#paseto-v4-implementation-library). No `exp`: the token lasts until sign-out or revocation, and each trade spends it.
```

**Refresh token rotation:**

1. Client presents refresh token to the `/oauth/token` endpoint with a DPoP proof under the token's key
2. Control plane validates token and reads its `family`: a live `refresh_token_families` row goes on to the trade, a `revoked_token_families` row refuses it, and a family with neither row is refused
3. Control plane issues new access token + new refresh token (new `jti`, same `family`)
4. The family's row records the new `jti` as its current one; any other `jti` of that family is spent. The trade is one compare-and-swap, `UPDATE refresh_token_families SET current_jti = <new> WHERE family_id = <presented family> AND current_jti = <presented jti>`: one row updated is a good trade, so two trades racing with one token settle to one
5. If a used `jti` is presented again (reuse detection), the entire `family` is revoked — all tokens in the rotation chain are invalidated. This detects token theft.

Each live sign-in has one row in `refresh_token_families` (`family_id`, `user_id` referencing `users` with `ON DELETE CASCADE`, `cnf_jkt`, `current_jti`, `issued_at`, `last_traded_at`), so the table holds one row per live sign-in, a machine's or a phone's or browser's, and nothing grows per trade. Every revocation ends the family the same way, in one transaction: the family's `refresh_token_families` row is deleted and its `revoked_token_families` row is written. That covers reuse (a swap that updates no row while the family's row exists), sign-out, a device revoked through the statement chain, and `account.delete`, where the live row also goes by `ON DELETE CASCADE`.

**Sign-in and the service's own credential:**

- The background service runs every sign-in, whether Settings › Devices' `Sign in` or `sidekicks account login` started it, and nothing asks it to stop; `sidekicks account login` starts a stopped service first. It runs the authorization code flow for a native app ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)) with PKCE S256 ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636), which [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700) requires): the service holds the verifier, `state`, a DPoP key made for the attempt and the issuer it talks to, opens a one-time listener on `127.0.0.1` at a free port, and pushes the request to `/oauth/par` first ([RFC 9126](https://www.rfc-editor.org/rfc/rfc9126)), signed with a DPoP proof ([RFC 9449 §10.1](https://www.rfc-editor.org/rfc/rfc9449#section-10.1)) and carrying the redirect address, the PKCE challenge, `state` and the machine's id, keys, name, platform and version, so the code can be redeemed only with that key and the machine's keys stay out of the browser bar. The browser opens `/oauth/authorize` with the returned `request_uri` alone. The listener accepts one `GET /callback` whose Host header is `127.0.0.1:<port>`, whose `state` matches in constant time and whose `iss` matches the attempt's issuer ([RFC 9207](https://www.rfc-editor.org/rfc/rfc9207); RFC 9700 §4.4.2); a wrong callback gets a 400 and the attempt keeps waiting, any other path or method a 404 or 405, its header size and read time are bounded, and it answers with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. It holds the browser's request while the service redeems the code at `/oauth/token` with the verifier and a fresh proof, then redirects to the relay's own result page and closes; at rest no listener is open. Where no browser can reach the machine, the relay's page shows a code the person pastes into the command line, worthless without the verifier. The code, the verifier, the DPoP key and the tokens never leave the service; the window and the command line see only the sign-in address and its state. The authorization code is good once, a reused code revoking what it issued, and the code and the attempt each have a bound ([Plan-015](../plans/015-hosted-account-and-identity.md) T5.4). The sign-in page accepts the account's passkey and verifies the person with it before it approves the sign-in, so a computer the person has never used signs in without any machine of theirs, and a machine new to the account adds itself in the same step, its `machine.added` signed by that passkey. A deployment holds one account, so the page offers `Create an account` only while none exists: it asks for `Name` once, makes the account's first passkey and approves the sign-in for the new account. That registration needs no sign-in, because it makes a new account and adds nothing to one that exists: it is bound to the authorization request the page was opened with, good once, and limited per source address under the same `auth.endpoint` row as the passkey sign-in. Adding a passkey to an account that exists stays signed in. The refresh token and the DPoP key are written to the credential store only once the sign-in has finished, so a failed attempt writes nothing.
- The control plane issues a refresh token bound to the machine's DPoP key (`cnf.jkt`), kept as its own item in the machine's credential store: the operating system's on macOS and Windows, or the service's one file readable by this account alone on Linux, sealed through systemd's credential service where it can seal, and on a Mac from its logged-out service's takeover until `sidekicks daemon uninstall`, even after that service is turned off in Login Items & Extensions ([ADR-020 §The Credential Store](../decisions/020-cli-identity-key-storage-custody.md#the-credential-store)). Every control-plane call the service makes on its own authenticates with an access token it gets by trading that refresh token; each trade returns a new refresh token and spends the old one, and the access token is never stored. Those calls are the machine's registration and its certificate challenge (`machine.register`, `machine.certificateChallenge.update`) and `device.push.send`.
- A spent refresh token presented again revokes its whole family (step 5 above). The service's next trade then fails, and `sidekicks daemon status` prints `Hosted account: signed out · its sign-in was used in two places; sign in again`. Sign-out revokes the family ([§Token revocation](#token-revocation)): its `refresh_token_families` row is deleted and its `revoked_token_families` row written in one transaction.
- **WebAuthn/Passkeys:** used only in a browser and the iPhone app: on the sign-in page, to approve a machine's sign-in and to make a new account's first passkey, and in the web client and the iPhone app, to sign in and to link a device with no other device at hand. The desktop app carries no WebAuthn, and no key is derived from a passkey.
- **The account's first passkey is trusted on first use.** At the account's very first sign-in the machine has no earlier trust to check against. The control plane makes that assertion's challenge from the sign-in's PKCE challenge, SHA-256(nonce ‖ SHA-256(PKCE verifier)), whose verifier only the machine's service holds, and refuses an assertion from any passkey but the one it just registered; the service verifies the assertion, recomputing the challenge from the nonce and its own verifier, and records it in an `account.passkey.added` signed by the machine key right after the chain-opening `machine.added`. That proves the passkey answered this sign-in, not that the person's own device made it, so the machine accepts it on the control plane's word bound to that sign-in, as SSH accepts a host's key at its first connection. Every later key, machine, device or passkey, enters only through the statement chain ([Spec-027 §Device registration and revocation](../specs/027-remote-control.md#device-registration-and-revocation); [Plan-015](../plans/015-hosted-account-and-identity.md) T5.4).

**DPoP sender-constraining:**

- The client holds a DPoP key pair; the machine's is its own credential-store item like every daemon secret, and its private half never leaves the daemon
- The access token accompanying the proof is presented as `Authorization: DPoP <token>` per [RFC 9449 §7.1](https://www.rfc-editor.org/rfc/rfc9449#section-7.1) — **never `Bearer`**, which a conforming resource server rejects for a DPoP-bound token and a lax one accepts while silently dropping proof-of-possession enforcement. The daemon session token, presented as `sessionToken` in `connection.initialize` above, is a different credential on a different transport
- Each API request includes a `DPoP` header containing a signed proof: `{jti, htm, htu, iat, ath}` signed by the client's private key — `ath` is the SHA-256 hash of the presented access token, required by [RFC 9449 §4.3](https://www.rfc-editor.org/rfc/rfc9449#section-4.3) when a proof accompanies an access-token presentation
- The control plane verifies the DPoP proof's signature matches the `cnf.jkt` thumbprint in the access token, accepts each proof's `jti` once inside its `iat` window, and refuses an access token whose `jti` is on the denylist. One signed-in procedure does this, and every signed-in control-plane route mounts on it ([Plan-015](../plans/015-hosted-account-and-identity.md) T6.6: `jwt-simple` for the embedded key and the RFC 7638 thumbprint, the proof built with `serde_json` and checked with `p256`)
- Prevents stolen access tokens from being used by a different client

#### Token revocation

- **Single-token revocation** via `POST /oauth/revoke` per [RFC 7009](https://www.rfc-editor.org/rfc/rfc7009) (the token to revoke is supplied in the request body). A refresh token sent there revokes its whole family. Sign-out sends it: the service deletes the DPoP key first, so the token can never be traded again, and sends the revoke with the token alone as soon as the relay can be reached, then deletes the token; signing in again meanwhile makes a new key and a new family, and the owed revoke is still sent.
- **Propagation semantics:** access tokens are short-lived (15 min) so access-token revocation is eventual; refresh-token revocation is immediate because every trade checks `revoked_jtis` and `revoked_token_families` on the request path.
- **How long a revocation is kept:** a refresh token has no fixed lifetime, so a revoked family never expires on its own. Its `revoked_token_families` row, written in the same transaction that deletes the family's live `refresh_token_families` row (at reuse, sign-out, a device's revocation or `account.delete`), stays for the account's life and goes with `account.delete`; a `revoked_jtis` entry is reaped a margin past the access token's lifetime, once the access token it blocks has expired anyway.
- **On device revocation:** a device is revoked one at a time, from the Devices page or `sidekicks device revoke`, as a `device.revoked` statement signed by any trusted key. When the statement reaches the control plane, it revokes that device's refresh-token family and every unexpired `jti` in it — in one transaction the family's `refresh_token_families` row is deleted and its `revoked_token_families` row written — so the device is signed out everywhere and cannot link again. Every device and passkey it linked or added before stays trusted, flagged on its card or row as linked or added from a device the person revoked. The hosted account itself is deleted one way only, by `sidekicks account delete` over the control plane's `account.delete`, run from a signed-in machine. A person who has lost every machine installs the command-line tool on another computer, runs `sidekicks account login`, confirms it with a passkey on the relay's sign-in page, and runs `sidekicks account delete`. The SQL in the [Hosted Account Deletion Runbook](../operations/hosted-account-deletion-runbook.md) is a break-glass procedure for the relay's owner, used only when the authenticated path is genuinely impossible (for example, the owner has no passkey left to verify a sign-in); it is never a second way to delete an account.

### Relay Authentication And Encryption

Per [ADR-010](../decisions/010-tokens-passkeys-and-the-remote-channel.md), every channel joins one device and one machine, straight across the network wherever the two can reach each other and through the person's own relay otherwise, and carries every session and screen on that machine. [Spec-027 §The encryption envelope](../specs/027-remote-control.md#the-encryption-envelope) is the full design; this section is its security summary.

**Keys and trust:**

| Key | Where it lives | What it does |
| --- | --- | --- |
| Machine identity key | Ed25519, minted at the service's first start, kept as its own item in the machine's credential store: the operating system's on macOS and Windows, on Linux the service's one file, sealed through systemd's credential service where it can seal, and that file on a Mac whose service runs while logged out ([ADR-020](../decisions/020-cli-identity-key-storage-custody.md)); never leaves the machine | Signs the machine's statements; every device pins it |
| Device identity key | P-256 in the iPhone's Secure Enclave; a non-extractable WebCrypto key in the web client; never exported | Signs the device's statements |
| Channel key | X25519, one per device and per machine; the machine's its own credential-store item, in the operating system's store or the service's one file as the identity key is, the iPhone's in the Keychain, the web client's a non-extractable WebCrypto key, kept in IndexedDB wrapped under a non-extractable AES-GCM key of its own and unwrapped at each load | The static key of the Noise handshake; certified by its identity key in the statement that trusts it |

Every device and machine public key carries its algorithm tag (`p256` or `ed25519`), and a passkey's its COSE algorithm (EdDSA, ES256 or RS256, the last for Windows platform authenticators). Trust is the account's append-only statement chain, which every machine verifies itself: a key is trusted only when a path of `machine.added`, `device.linked` and `account.passkey.added` statements reaches it from the machine's own key, each signed while its signer was still trusted at that point in the chain. A `device.revoked`, `machine.removed` or `account.passkey.removed` ends the key it names at that point: a statement that key signs afterward is refused, and what it signed before stands, so every device, machine and passkey it added stays trusted, and what a revoked device added is flagged on its card or row. An ended key is never trusted again. Every channel open exchanges the chain head, so a withheld revoke is caught at the next honest connection. A device refuses a machine that answers under a known id with a different key and no later `machine.added` for that id behind it; a removed machine that is linked again first mints a new identity key and a new channel key under its same machine id, and its new `machine.added` moves every device's pin for that id.

**The channel:**

| Component | Specification |
| --- | --- |
| Protocol | The Noise Protocol Framework's KK handshake and transport in two profiles, `Noise_KK_25519_AESGCM_SHA256` offered first and `Noise_KK_25519_ChaChaPoly_SHA256` second, on `snow` (built with `ring-accelerated`) on the machine and, on the devices, the channel package's implementation of the standard `KK` pattern written from Noise revision 34 on WebCrypto with `@noble/ciphers` for ChaChaPoly, its exchanges on each handshake's ephemeral key run by WebCrypto in the page on every host, and its exchanges on the channel key by WebCrypto in the web client and natively by the iPhone app's bridge; no cryptographic construction of the product's own |
| Authentication | Both static keys are known from the statement chain (`KK`); a handshake from a key the chain does not hold fails with nothing to click past |
| Forward secrecy | A fresh handshake on every connection and every 10 minutes on a long one, with the old keys erased; in the web client and the iPhone app, where the channel's keys pass through JavaScript memory, the erasure is best effort |
| Profile | The connection's first frame offers the channel version and the profiles the device runs; the machine answers with one it runs or closes the connection (`channel.noCommonProfile`); offer and answer are bound into the handshake's prologue. Every device offers two profiles, `Noise_KK_25519_AESGCM_SHA256` offered first and `Noise_KK_25519_ChaChaPoly_SHA256` second: WebKit's WebCrypto refuses ChaCha, and AES-GCM is 3–6× cheaper there; ChaCha serves a machine or device without AES instructions, and is never negotiated while both ends run AES-GCM |
| Post-quantum | Not provided: traffic recorded today could be opened by a future large quantum computer. The hybrid profile joins through the same negotiation once its specification is reviewed |
| What the relay sees | The device id and machine id at connection, the channel version and the profile, frame sizes and times; never a method, a name or a byte of a session. It learns that a channel moved onto the direct path only from its connection going quiet |

**The direct path:**

| Component | Specification |
| --- | --- |
| Carrier | One WebRTC data channel, reliable and ordered, between the device and the machine: `RTCPeerConnection` in the channel package on the web client and the iPhone app, and `str0m` on its default `aws-lc-rs` crypto on the machine, so the service links no second TLS library. The desktop app on another computer opens none itself: its service holds the channel as its own machine, `str0m` on both ends |
| Encryption | WebRTC's DTLS, which every data channel carries and nothing can turn off (RFC 8827 §6.5, RFC 8831 §6.1), and inside it the same sealed channel as on the relay: the same first frame, the same `KK` handshake on the same channel keys and profiles, and the same 10-minute rekey, so a flaw in either end's DTLS exposes no session byte |
| Setup | The device's offer, the machine's answer, the candidates and every ICE restart travel inside the sealed channel, over whichever carrier holds it, so only the paired keys read them; the data channel's DTLS fingerprint is trusted because it arrived that way. The device always offers. The machine names its own addresses only to the paired device, inside the channel, and never advertises itself on the network |
| What the socket answers | One UDP socket per address family per direct peer, answering only an ICE check that carries the password exchanged inside the sealed channel (at least 128 random bits, RFC 8445 §5.3) and silent to anything else; after ICE, DTLS against the signaled fingerprint, then the `KK` handshake against keys the statement chain trusts. A DTLS peer with another fingerprint is refused, and a handshake from a key the chain does not hold fails |
| With no direct peer | No UDP socket, no router mapping and no mDNS thread |
| Away from home | The router's port mapping (PCP or NAT-PMP, then UPnP-IGD) at the shortest lease the router grants, renewed at half its life and deleted when the path closes, so one mapping leads to the socket while the device is away |
| Code before any check | `str0m`'s fuzzed STUN parser and `dimpl`'s memory-safe DTLS; the sealed channel inside covers a flaw in `dimpl`, which has had no outside audit, and each upgrade of either is reviewed |
| Reachability | `Reachable`, `Connected now` and the two-places flag stay facts of the relay connection, so the direct path never adds a second answer to whether a machine or a device can be reached |

**Events a device originates:** no device signs the events it sends. The channel's handshake proves the device, and the machine records the connection's device on each event that device originates; an approval, question or plan resolution carries the answering device's id. A revoked device's channel is closed, so nothing new reaches the machine from it ([Plan-025](../plans/025-remote-control.md)).

**Access to the relay:**

1. A device or machine negotiates relay access with the control plane and receives a relay endpoint, the machine's current forwarding object on the Workers relay, the relay's STUN address, and a short-lived connect token bound to that device and that machine, never to a session; a token replayed for another device or machine, or an expired one, is refused.
2. The client connects over WSS and presents the connect token in the initial WebSocket handshake via two `Sec-WebSocket-Protocol` subprotocol values — `paseto-v4, <base64url(connectionToken)>` (value 1 names the scheme and is echoed by the relay as the negotiated subprotocol; value 2 carries the base64url-encoded token, since browsers cannot set custom WebSocket request headers).
3. The relay forwards the channel's frames and inspects none of them. It holds at most one live connection per machine key and, for each machine, one per device key (on the Workers relay on that machine's forwarding object, on the Compose relay in its one process); a new connection under a key closes the one before it, and a key that keeps displacing itself, three times within a minute, is flagged.
4. The relay forwards each device's frames as fast as the machine drains them; backpressure on the channel bounds both directions.

### Permission Matrix

A session has exactly one owner and no other people, so the matrix is not a grid of roles: every row below is something the session's owner may do from any of their linked devices, and every linked device can do everything the desktop can. A write records the device it came from; nothing checks ownership per caller.

| Action | Rule |
| --- | --- |
| **Session lifecycle** |  |
| Create, archive/close, and configure a session | Owner, from any linked device |
| **Devices** |  |
| Link a device, list linked devices, revoke a device | Owner, from any linked device |
| **Machines** |  |
| Rename or remove one of the account's machines, and read the account's machines | Owner, from any linked device |
| **Runs and messaging** |  |
| Send messages / create runs, queue work items, set/clear the session goal | Owner |
| Start workflow runs (an agent's start and each run a trigger fires are adjudicated per start under the named Cedar operation action `Action::"workflow::start"` — never an approval category; the person's own starts — the desktop app, the `/workflow` verbs, the CLI and any linked device — pass no policy check; an agent's start is a tool call under its chat's level, so a chat that asks first asks before it starts one; every adjudicated start carries a daemon-resolved principal, the one user, never a client-supplied field, and one whose principal does not resolve is refused — [ADR-025](../decisions/025-chat-invoked-workflow-start.md)) | Owner |
| Steer/interrupt, the faster-model retry, undo (`session.restore`), pause/resume runs, and compact a bound run's provider context (authorized by session write access, never by run authorship — "own" never scopes this row, so a run started from one device is steerable from any other. User-triggered context compaction shares this row's adjudication rather than minting a Cedar action of its own, per [Spec-004 §User-triggered context compaction](../specs/004-provider-driver-contract-and-capabilities.md#user-triggered-context-compaction) — a compaction target is always a binding this daemon holds) | Owner |
| Take a shell's control lease (one device holds a given shell at a time, and a device's first write to a free shell takes it; there is no release — a lease ends when another device takes it, when a forced take moves it, or when the last of the connections and pane output subscriptions it was taken or written through ends; an agent's command that takes it keeps it aside, and the run's hold, ending with its command or when the run leaves `running`, hands the shell back to it while one of those is open; and a revoked device's channel is closed, which ends its leases, per [Spec-002 §Required Behavior](../specs/002-machine-registration.md#required-behavior)) | Owner, one holding device per shell |

**Actions that ask at the asking levels:** at the session's permission levels that ask, these ask before they run unless an approval rule answers them; at Sandboxed and at YOLO none of them asks, as the person chose, save at YOLO a removal the provider's own check flags ([Spec-010 §Default Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#default-behavior)):

- `fileWrite` outside the bound workspace
- `networkAccess` unless the active policy explicitly allows it
- `destructiveGit` operations (force push, branch delete)

**Unconditional actions (no approval needed):**

- Reading the transcript, artifacts, and device presence
- Sending device presence heartbeats
- Registering the machine the service runs on

### Per-Device Presence Detail Authorization

The **Read the transcript, artifacts, and device presence** row above also governs the Devices page's reads: `device.subscribe`, which returns each machine, device and passkey with its connected state and last-seen time, and a machine's `presence.read` and `presence.subscribe`, which report the devices connected to it and whether an app window is in front on each. They are authorized as the transcript is: the owner, from any of their devices.

**Rationale.** Under Remote Control the device list is the product, not an exhaust: a person deciding whether to steer from their phone has to see which of their machines is reachable, and a person revoking a lost device has to find it. There is no second person for it to leak to — every entry belongs to the caller's own account — so no separate gate stands in front of it.

### Transport Security Requirements

| Transport | Protocol | Authentication | Encryption | Trust Boundary |
| --- | --- | --- | --- | --- |
| Local daemon (Unix socket) | Unix domain socket | Socket permissions (mode 0700) + 256-bit session token, or on macOS the desktop's client helper's code signature (per §Local Daemon Authentication) | None needed (same-machine) | Highest trust — local execution authority |
| Local daemon (Windows named pipe) | Per-user named pipe, served by the daemon in its own process through `sidekicks-platforms`' pipe code | Pipe access list granting the person alone, remote clients refused, the client's owner check + 256-bit session token | None needed (same-machine) | Highest trust — local execution authority |
| Client to control plane | HTTPS | PASETO v4.public + DPoP | TLS 1.3 minimum, no TLS 1.2 fallback | Medium trust — authenticated, reached over the public internet |
| Device to machine (via the relay) | WSS to the relay | Connect token bound to the device and the machine; inside it, the Noise `KK` handshake over keys the statement chain trusts | `Noise_KK_25519_AESGCM_SHA256` offered first, `Noise_KK_25519_ChaChaPoly_SHA256` second, rekeyed on every connection and every 10 minutes | Low trust — the relay sees ids, the profile, sizes and times only |
| Device to machine (direct path) | A WebRTC data channel over UDP, set up inside the sealed channel | The ICE password and the DTLS fingerprint exchanged inside the sealed channel; inside the data channel, the same Noise `KK` handshake over keys the statement chain trusts | DTLS beneath, and inside it the same two Noise profiles and rekey as on the relay | Low trust — the networks between the two ends see only the ICE checks, integrity-checked with the password exchanged inside the sealed channel, and DTLS packets |

**Certificate requirements:**

- Control plane: Valid TLS certificate from a public CA. No self-signed certificates in production.
- Relay: a relay whose certificate chains to a root the operating system trusts is checked by the platform's certificate validation and its host name; only a relay without a publicly trusted certificate has its key pinned when it is linked, and a changed key is refused (`relay.pin.refused`) until `sidekicks relay repin --force` accepts it. The machine-key pin inside the channel holds on either relay.
- Local daemon: No TLS needed (Unix socket or the Windows named pipe).

**Machine boundaries:**

- Owning a session does NOT imply machine trust. A session runs only on the machine it was started on, and no machine executes anything for another.
- Every channel is end-to-end encrypted between one device and one machine, on the direct path or through the relay. A desktop app on another computer reaches a machine through its own service, service to service, and no machine executes anything for another over that channel.
