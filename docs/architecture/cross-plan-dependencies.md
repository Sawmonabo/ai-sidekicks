# Cross-Plan Dependency Graph

This is the build order for the work that has not shipped yet. Each unit below is one PR off `develop`: the row says what it builds, the units it waits on, and the plan tasks it discharges. The PR that finishes a unit deletes its row here and its name from every other row's "Waits on".

## Platform order

Every unit in the desktop and daemon, Remote Control and command-line sections builds and checks on macOS. The code stays portable: each piece that differs by operating system sits behind one interface in the unit that owns it, which builds the macOS form, and nothing is hard-coded to macOS. Two groups in [Other platforms, release and email](#other-platforms-release-and-email) follow. **Other platforms** (`windows`, `linux`, `windows-wsl`) adds the Windows and Linux side of every such interface, and sessions in WSL 2 distributions after the native service on Windows, with the plan phases that build only for those systems. **Release** (`app-update`, `service-update`, `release`) holds packaging and signing on every platform, the release manifest, the app's update path, `sidekicks daemon update` and the background service's update, and a one-time vulnerability scan before the first release; there is no license scan. A feature is built in its own unit, and only its run on a signed, packaged build waits for the release units. `sidekicks-search`'s index builds and tests with the daemon on CI's Linux runner; its Windows builds and its Linux machine builds are verified in `windows` and `linux`. The email digest comes last of all.

## How the order is read

A unit is ready once every unit in its "Waits on" has merged; it starts then, with no wait for a batch or a group. "Waits on" lists only direct dependencies: one already implied by another is left out. "Every macOS unit" means every unit in the first section below, except, on a row in that section, the row itself and the units that wait on it. A plan task listed under several units is built in parts: each unit builds the part its row names, and the task is done when the last of them merges.

Free build lanes take ready units in the order of the sections below: desktop and daemon, then Remote Control, then the command line, then other platforms, release and email. Within the desktop and daemon section, the units a session with Claude Code or Codex and the Settings pages need go before the workflows, preview, the review pane and git flow. Within a section or that group, rows run from the unit with the longest chain of units after it to the shortest, so the first ready row goes first.

A unit with a daemon, command-line, contract or control-plane side builds that side in Rust, in the crate `crates/AGENTS.md` names for it.

A file several units edit (a `package.json` or `Cargo.toml`, the daemon's schema module, the handler registration, main's entry point) takes one block per unit. A unit that lands second on it rebases, keeps both blocks, and reruns its checks.
