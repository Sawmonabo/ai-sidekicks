# Workflow Implementation Notes

The implementation notes of [Spec-015: Workflow Authoring And Execution](../specs/015-workflow-authoring-and-execution.md).

- Workflow authoring belongs in the product surface, but workflow execution still uses the same run, approval, and artifact primitives as free-form sessions.
- Version immutability simplifies rebuilds and support.
- Parallel steps come only from branches the graph draws, admitted by the memory gate — no implicit concurrency.
- Persistence uses a LangGraph-inspired checkpoint pattern on the existing SQLite store (Spec-013), with the normalized-tables-over-JSON-blob decision documented in State And Data Implications. No external workflow engines (Temporal, Restate): a workflow runs on the user's own machine, inside its daemon, as all of a session's code does.
- One execution model at V1 per C-11: local daemon runs workflows locally. Do not ship a `local | queued | remote` enum at V1.

**The kinds that run an agent or ask a person compile down at run time, not at save time**, which is what keeps the document node-shaped end to end. Their executors reimplement nothing:

- The `agent.run` kind calls the existing run admission with the definition id from its `definition` param, with the provider account and tool allowlist resolved from that definition under any per-node `binding` override, and at the workflow run's level.
- The `agent.multiAgent` kind runs a lead and its helpers in the run's session through the existing orchestration path, `agent.run.create`.
- The approval kind raises a request through the existing approval pipeline and its Cedar check.
- The form kind writes through the existing form-state store.

The park-and-resume rules for provider limits apply to these steps unchanged, so a spent account parks the step and the run resumes itself when the account recovers ([Spec-015 §Provider-limit pacing and durable resumption (SA-37)](../specs/015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-37)). The step record is a projection over the events those pipelines already emit.

**One process, an engine per quick step.** Each quick Code step runs in its own `rquickjs` runtime on a thread of the service started for the step and ended with it, created with the step's budget as its `set_memory_limit` under `rust-alloc` and dropped after the step, the allocator's hand-back running after it; an engine that ran out of memory is never reused, and none is shared. Into the thread go the program, the step's budget and deadline, the run's cancel flag and the step's input — an inline input as its stored JSON text, moved rather than copied, and an input kept as an artifact by its id, which the thread reads from disk itself, so the service's other threads never serialize or copy a large input. Out come the output as JSON text — one over 64 KiB written by the thread to a file and handed back by path, taken in as the step's artifact — the step's log lines, and the engine's memory at its peak. No binding to the host crosses in either direction. The interrupt handler reads the cancel flag and the deadline, so a step stops when its `Timeout` passes where one is set, when its run ends or when the person cancels. A runaway past the limit raises QuickJS's catchable out-of-memory error, which fails only that step with `workflow.code.overBudget` and never grows the service; a thread or engine that cannot be made fails its step at once with `workflow.step.threadFailed`, reason `startFailed`. A deadline cut reads `failed · timed out` (`workflow.step.timedOut`, cause `stepTimeout`).

**Dependency decisions.** The JavaScript packages' versions, licenses and sizes below were read from the npm registry on 2026-09-21; each crate is named at its pinned release.

| What it carries | Pick and why |
| --- | --- |
| The canvas | `@xyflow/react` 12.12.0, MIT, already pinned in the desktop app, in fully controlled mode: nodes and edges derive from the document draft and every change callback translates back into a document mutation, so the store and not the library owns the bytes that get serialized. Its connection-validity predicate runs during the drag, so a refused connection is never created ([ADR-024](../decisions/024-visual-node-graph-workflow-authoring.md)). |
| Auto layout | `dugong` 0.9.0, MIT or Apache-2.0, left to right: one Rust module the daemon uses and the builder loads as a WebAssembly build, as the matcher's `ranking.rs` is. It is deterministic, and each kind's node size is stated, so it needs no measurement pass; the daemon needs it to lay out a document an agent authored with no layout section. |
| Expressions | `jsonata-core` 2.2.13 with no default features, taken from the fork `Sawmonabo/jsonata-core` by the root `Cargo.toml`'s `[patch.crates-io]` at one commit. The fork carries three changes, each offered upstream and dropped when a release carries it: regular-expression classes with JavaScript's meaning ([txjmb/jsonata-core#271](https://github.com/txjmb/jsonata-core/pull/271)), a cancel check per element in `$distinct` and `$keys` ([txjmb/jsonata-core#272](https://github.com/txjmb/jsonata-core/pull/272)), and object keys in JavaScript's order ([txjmb/jsonata-core#273](https://github.com/txjmb/jsonata-core/pull/273)). `timeout_ms` is unset; an evaluation nests at most 10,000 evaluator levels, a third of the crate's 30,000-level backstop, which by the crate's own figures is about 3,300 nested calls and 30 MB of stack at its peak, and a query builds a sequence of at most 1,000,000 items (`MAX_STACK_DEPTH` and `MAX_SEQUENCE_LENGTH` in `crates/sidekicks-workflow/src/expressions/evaluator.rs`); Phase 5 measures both figures. A cancel goes through the crate's `CancelToken` and answers `U1003`. Sandboxed by construction and rich enough that no host access is needed; the binding namespace registers on top of it. Expressions run on one long-lived evaluator thread, `workflow-expressions`, fed by its bounded job channel; it builds its input from inline and artifact data alike, and an expression stops on its step's cancel. Its regular expressions run on the `regex` crate in time linear in their input, their classes read with JavaScript's meaning (`\d` is `[0-9]`) and a case-insensitive match folding letters as the `regex` crate does; a backreference or a lookaround is refused at save. Considered: waiting for releases with the three gaps open; a copy of the crate in the tree, whose source files run far past the 900-line rule and, once edited, are no vendored copy; the class rewrite in our own crate over the parsed pattern. Chosen: the fork, because `[patch.crates-io]` is Cargo's own mechanism for an upstream gap, and this maintainer merged an outside cancel fix within two days of its opening. |
| The Code node, quick tier | `rquickjs` 0.14.0, MIT, in `crates/sidekicks-workflow`: the QuickJS interpreter under its memory limit, with an interrupt handler and no host access unless something is bound into it, so the quick tier's blast radius is a byte budget and, where the person sets one, a deadline rather than a policy argument. The memory budget is 256 MiB per node by default and the deadline is the step's `Timeout`, empty by default; both are settable and both ours — the library ships none. One engine runs per step on its own thread (above). |
| The Code node, full tier | No interpreter of ours: a child process, run from the version's code folder. `bun`, fetched during the app's first-run setup with its version and SHA-256 pinned per service release, locks at save with `bun install --lockfile-only`, installs from the lock with `bun install --frozen-lockfile`, and runs the step with `--config=<the daemon's own bunfig.toml> --no-env-file --preload <unpin preload>`. `uv` locks at save with `uv lock --script` and installs from the lock with `uv export --script --locked`, `uv venv` and `uv pip sync --require-hashes` into the folder's own `.venv`, and the step runs on that `.venv`'s Python with no `uv` at run — not `uv run`, which builds its environment in the shared cache, one per script path, and needs `uv` inside the sandbox. `uv` reaches a person's machine as one pinned release archive, with its per-platform sha256 values kept in the daemon's source; the first save that locks a Python step fetches the archive into a daemon-owned folder and checks it against that value before unpacking it whole, and a mismatch or no network leaves that save's Python steps `Packages not locked`, in plain words. `uv`'s standalone installer is never used, because it edits shell profiles, and the npm package named `uv` is an unrelated UTF-8 validator. `uv` is licensed MIT or Apache-2.0. `uv`'s cache clears through `uv cache clean`, bun's by removing its folder, which is all `bun pm cache rm` does — and that command refuses to run without a `package.json` in its working folder; installs and a clear of one cache run one at a time. Neither program is a library the daemon links; each is a program it spawns, which is why the tier costs no bundle and no native addon. |
| The sandbox around the full tier and `developer.shell` | Whichever the run's provider ships, never one of ours: `@anthropic-ai/sandbox-runtime` 0.0.79 under `bun` (macOS Seatbelt, Linux bubblewrap, a dedicated Windows account with an egress fence), one `bun` process per distinct network list (per set of write folders on Windows) holding the library's `SandboxManager` and wrapping each step's command with `wrapWithSandbox`, which the daemon then spawns itself; or `codex sandbox` under a named permission profile, run from `@openai/codex`'s native binary. No process is started per step. The sandbox runtime is labeled a beta research preview by its own authors, so its interface may move. The posture vocabulary they take — read-only, write these roots, reach these hosts — is already the product's own ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)), so the bridge is a wrapper and a profile rather than a sandbox of our making. |
| Schedules | The `croner` crate 4.0.1, MIT, with `default-features = false, features = ["jiff"]`: cron plus timezone plus a next-run computation. The durable next-fire row is the truth and the in-process timer is a cache over it, so a restart re-arms from the row. |
| File watching | One `notify` 9.0.0-rc.6 watcher, debounced 250 ms, with the globs filtered by `picomatch` 4.0.7 (`picomatch/posix`) on `rquickjs`, each trigger's globs compiled once when it is armed. Recursive watching works on macOS, Linux and Windows. |
| A run's graph and the graph check's cycles | `petgraph` 0.8.3, MIT or Apache-2.0, with `default-features = false, features = ["std"]`, in `crates/sidekicks-workflow` and `crates/sidekicks-contracts`: its iterative Kosaraju search finds the strongly connected components that hold the loops' back edges in a run's graph and the cycles the graph check refuses. One maintained library serves both crates where a hand-written search would be two, and its own stack keeps a long chain of nodes from exhausting the daemon's or the builder's WebAssembly stack. Its cost is a second `petgraph` in the lock beside the 0.7.1 that `lalrpop` brings in for `cedar-policy-core`'s build, and an older second copy of `hashbrown` and `foldhash`, each a duplicate warning from `cargo deny`. |
| A node's ancestors | `fixedbitset` 0.5.7, MIT or Apache-2.0, in `crates/sidekicks-workflow`: each node of a run's graph keeps its ancestors as one bit per node. A direct dependency because the engine names its `FixedBitSet` type rather than taking it through `petgraph`, which builds on the same release, so it adds nothing to the lock. |
| The three tables | The console's existing windowed list primitives, for the Workflows tab, the runs list and a step's output table. They are already budgeted and already styled from the design tokens, and a second table library would be a second scroll model. |

The node-graph automation tool whose mechanics the builder studies is **not** adopted at any version: its packages carry a source-available license that is neither an OSI license nor compatible with this repository's, and they would bring that product's runtime with them. This specification copies mechanics from a primary-source reading of it and takes no code and no branding.
