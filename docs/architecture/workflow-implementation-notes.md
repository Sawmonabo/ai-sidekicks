# Workflow Implementation Notes

The implementation notes of [Spec-015: Workflow Authoring And Execution](../specs/015-workflow-authoring-and-execution.md).

- Workflow authoring belongs in the product surface, but workflow execution still uses the same run, approval, and artifact primitives as free-form sessions.
- Version immutability simplifies rebuilds and support.
- Parallel steps come only from branches the graph draws, admitted by the memory gate — no implicit concurrency.
- Persistence uses a LangGraph-inspired checkpoint pattern on the existing SQLite store (Spec-013), with the normalized-tables-over-JSON-blob decision documented in State And Data Implications. No external workflow engines (Temporal, Restate) — contradicts ADR-002 (local execution).
- One execution model at V1 per C-11: local daemon runs workflows locally. Do not ship a `local | queued | remote` enum at V1.

**The kinds that run an agent or ask a person compile down at run time, not at save time**, which is what keeps the document node-shaped end to end. Their executors reimplement nothing:

- The `agent.run` kind calls the existing run admission with the definition id from its `definition` param, with the provider account and tool allowlist resolved from that definition under any per-node `binding` override, and at the workflow run's level.
- The `agent.multi-agent` kind runs a lead and its helpers in the run's session through the existing orchestration path, `orchestration.runCreate`.
- The approval kind raises a request through the existing approval pipeline and its Cedar check.
- The form kind writes through the existing form-state store.

The park-and-resume rules for provider limits apply to these steps unchanged, so a spent account parks the step and the run resumes itself when the account recovers ([Spec-015 §Provider-limit pacing and durable resumption (SA-37)](../specs/015-workflow-authoring-and-execution.md#provider-limit-pacing-and-durable-resumption-sa-37)). The step record is a projection over the events those pipelines already emit.

**One process, a thread per quick step.** Each quick Code step runs in its own interpreter instance whose WebAssembly memory is created with the step's budget as its maximum, and the instance is discarded after the step: the interpreter's own memory limit does not hold (strings reached about 1.9 GB and objects about 1.2 GB within 5 s under a 256 MiB limit), a shared instance never gives WebAssembly memory back, and an instance that ran out of memory is unusable, so none is reused. Each quick step runs on a `worker_threads` thread of its own, started for the step and ended with it. The daemon compiles the interpreter once, when it starts, and hands each thread that `WebAssembly.Module`; each thread still creates its own capped `WebAssembly.Memory` and discards it (a thread compiling its own copy costs more when twenty start together, and twenty threads starting at once hung in 8 of 160 runs on Node 24.18.0 with per-thread compiles and in none with the module compiled once). Into the thread go the program, the step's budget and deadline, the compiled module, a four-byte shared cancel flag and the step's input — an inline input as one buffer of its stored JSON text, transferred rather than copied, and an input kept as an artifact by its id, which the thread reads from disk itself, so the daemon's thread never serializes or copies a large input. Out come the output as JSON text — one over 64 KiB written by the thread to a file and handed back by path, taken in as the step's artifact — the step's log lines, and the size of the interpreter's memory at the end, which is its peak. No binding to the host crosses in either direction. The interrupt handler reads the cancel flag and the deadline, so a step ends when its `Timeout` passes where one is set, when its run ends or when the person cancels; a thread that has not answered 250 ms after that is ended with `terminate()`. The thread's own JavaScript heap is capped with `resourceLimits` at the reservation's part beyond the budget, so a defect in the step's host, never the step's program, ends that thread with `workflow.step_thread_failed`, reason `out_of_memory`, and never grows the daemon. A thread that is not running 5 s after it was started fails its step with reason `start_timeout`; one that exits without an answer, with reason `exited`. A thread that never started cannot be ended, so its reservation stays held until the daemon restarts, and because it also keeps the daemon's process from exiting, the daemon's supervisor stops the daemon hard once it has been asked to stop: after the flush and the stop request, it waits up to the daemon's drain bound for it to exit, and only a daemon still running after that gets SIGTERM and, 2 s later, SIGKILL ([Desktop App Implementation Notes §Detached Service Launch](desktop-implementation-notes.md#detached-service-launch)). A deadline cut reads `failed · timed out` (`workflow.step_timed_out`, cause `step_timeout`), and a program over its memory budget keeps `workflow.code_over_budget`.

**Dependency decisions.** Versions, licenses and sizes below were read from the npm registry on 2026-09-21.

| What it carries | Pick and why |
| --- | --- |
| The canvas | `@xyflow/react` 12.12.0, MIT, already pinned in the desktop app, in fully controlled mode: nodes and edges derive from the document draft and every change callback translates back into a document mutation, so the store and not the library owns the bytes that get serialized. Its connection-validity predicate runs during the drag, so a refused connection is never created ([ADR-024](../decisions/024-visual-node-graph-workflow-authoring.md)). |
| Auto layout | `@dagrejs/dagre` 3.1.1, MIT, 1.4 MB unpacked, left to right, in the renderer and in the daemon alike. It is deterministic, and each kind's node size is stated, so it needs no measurement pass; the daemon needs it to lay out a document an agent authored with no layout section. |
| Expressions | `jsonata` 2.2.2, MIT, no runtime dependencies, 0.85 MB unpacked, Node ≥ 8. Sandboxed by construction, mature, pure JavaScript, and rich enough that no host access is needed; the binding namespace registers on top of it. The engine yields after every 4 ms of evaluation. Its regular expressions run on `re2js` 2.8.6, a linear-time engine, through JSONata's own `RegexEngine` option, so no pattern can take time exponential in its input; a backreference or a lookaround is refused at save. |
| The Code node, quick tier | `quickjs-emscripten` 0.32.0, MIT, 2.4 MB unpacked, Node ≥ 16: a WebAssembly interpreter with memory and interrupt limits and no host access unless something is bound into it, so the quick tier's blast radius is a byte budget and, where the person sets one, a deadline rather than a policy argument. The memory budget is 256 MiB per node by default and the deadline is the step's `Timeout`, empty by default; both are settable and both ours — the library ships none. It is compiled once at daemon start and run on a thread per step (above). |
| The Code node, full tier | No interpreter of ours: a child process, run from the version's code folder. `bun` 1.4.2 — published on npm as its own binary, so the daemon can carry it — locks at save with `bun install --lockfile-only`, installs from the lock with `bun install --frozen-lockfile`, and runs the step with `--config=<the daemon's own bunfig.toml> --no-env-file --preload <unpin preload>`. `uv` locks at save with `uv lock --script` and installs from the lock with `uv export --script --locked`, `uv venv` and `uv pip sync --require-hashes` into the folder's own `.venv`, and the step runs on that `.venv`'s Python with no `uv` at run — not `uv run`, which builds its environment in the shared cache, one per script path, and needs `uv` inside the sandbox. `uv` reaches a person's machine as one pinned release archive, with its per-platform sha256 values kept in the daemon's source; the first save that locks a Python step fetches the archive into a daemon-owned folder and checks it against that value before unpacking it whole, and a mismatch or no network leaves that save's Python steps `Packages not locked`, in plain words. `uv`'s standalone installer is never used, because it edits shell profiles, and the npm package named `uv` is an unrelated UTF-8 validator. `uv` is licensed MIT or Apache-2.0. `uv`'s cache clears through `uv cache clean`, bun's by removing its folder, which is all `bun pm cache rm` does — and that command refuses to run without a `package.json` in its working folder; installs and a clear of one cache run one at a time. Neither program is a library the daemon links; each is a program it spawns, which is why the tier costs no bundle and no native addon. |
| The sandbox around the full tier and `developer.shell` | Whichever the run's provider ships, never one of ours: `@anthropic-ai/sandbox-runtime` 0.0.78 on npm, linked as a library (macOS Seatbelt, Linux bubblewrap, a dedicated Windows account with an egress fence), or `codex sandbox` under a named permission profile, run from `@openai/codex`'s native binary. Neither package's npm launcher script is used, each of which would add a 15 to 38 MB Node process to every step. The sandbox runtime is labeled a beta research preview by its own authors, so its interface may move. The posture vocabulary they take — read-only, write these roots, reach these hosts — is already the product's own ([Spec-010 §Required Behavior](../specs/010-approvals-permissions-and-trust-boundaries.md#required-behavior)), so the bridge is a wrapper and a profile rather than a sandbox of our making. |
| Schedules | `croner` 10.0.1, MIT, 155 kB unpacked, no dependencies, Node ≥ 18: cron plus timezone plus a next-run computation. The durable next-fire row is the truth and the in-process timer is a cache over it, so a restart re-arms from the row. |
| File watching | Node's own recursive `fs.watch` on the pinned Node 24 line, debounced 250 ms, with the globs filtered by `picomatch` 4.0.7, MIT, 94 kB unpacked — already present transitively and becoming a direct daemon dependency. No new watcher library, and recursive watching works on macOS, Linux and Windows. |
| The Node line | The daemon and the CLI run on Node 24.21 or later, the workspace's one Node line. The memory gate needs 24.16 or later, because from 24.16.0 `process.availableMemory()` on macOS sums free, inactive and purgeable pages; on Node 22 it returns free pages alone. |
| The three tables | The console's existing windowed list primitives, for the Workflows tab, the runs list and a step's output table. They are already budgeted and already styled from the design tokens, and a second table library would be a second scroll model. |

The node-graph automation tool whose mechanics the builder studies is **not** adopted at any version: its packages carry a source-available license that is neither an OSI license nor compatible with this repository's, and they would bring that product's runtime with them. This specification copies mechanics from a primary-source reading of it and takes no code and no branding.
