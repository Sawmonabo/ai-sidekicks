# Settings Payload Contracts

Part of [API Payload Contracts](./api-payload-contracts.md), which holds the shared types, the error envelope and the conventions every shape here uses.

## Settings Surface Reads And Writes

**No `settings.*` method is registered.** The Settings screen is ten pages, and every page reads and writes through a named surface: the daemon's own verbs, the main process's bridge members, or the machine's settings file. This section says which each page uses; the build status of each daemon verb is in [§Operations Not Yet Built](./api-payload-contracts.md#operations-not-yet-built).

- **General** goes through the main process's own update channel — `update.getState`, `update.subscribe`, `update.requestCheck`, `update.requestDownload` and `update.requestRestart` — and the app's reported facts (`app.version`, `app.platform`, `app.arch`, `app.locale`), with `native.listEditors()` for the editor list. The editor preference, the default checkout for a new project session, the provider and model Generate writes its text with (`commitTextModel`, `{provider, modelId}`, or `null` for `Automatic` until one is picked, on the `Commit and pull request text` row under the line `Writes the text Generate fills in. Automatic uses the session's provider and its lowest-priced model.`), the new-session switch and the last model and effort it carries, the keep-awake switch and the crash-report switch are the machine's settings file's, read and written through `machineSettings.read()`, `machineSettings.write(change)` and `machineSettings.subscribe()`; the background service reads the keep-awake switch and holds the machine and its screen awake itself while any agent works.
- **Providers** is one section per provider, and its two halves read through different surfaces. **The accounts half** goes through the `provider.account.*` namespace of provider-account-payloads.md §Plan-023: `provider.account.list` and `provider.account.subscribe`, `.register`, `.update`, `.delete`, `.current.update` (which moves the `Default` mark; a session on that provider moves to the new account in place at its next request), `.probe` (`Check now`, and the five-minute read), `.credentialHome.reset` (the page's `Sign out`), `.signIn` and `.signInAttempt.cancel` (the brokered sign-in), `.memory.import` (the one-time copy of the person's own provider memories into an account's home) and `.usage.list`. An account is named by the identity its provider reports — the address, the plan in the provider's own word, and the organization where the plan carries one — and the one label the person types is the name of an account added by a pasted token or API key (`displayLabel`), so the fields the update mutation corrects that the person authors are the billing mode and that name. **The provider's half** goes through the `provider.*` root: `provider.list` (each provider with a registered driver, one section each, `{provider, name, planWords, builtInTools, appSetEnvironmentNames, mcp: {transports, configMembers}, skillNameMaxLength | null, voiceKinds, outputSpeedLevels?, places, availableForNewSessions, helpersAtOnce, autoCompactPercent, rows, sessionOptions}`: its driver's fixed facts, among them the voice kinds it offers (`dictation` and `call`, each at most once, empty where it offers no voice), which the composer reads to start `voice.dictation.start` or `voice.call.start`, its status per place, the shared rows every provider offers, the rows its driver declares with their live values, each a `setting` (a `switch` per place, a `choice` or a `text`), a `status` or an `action` (a switch per place whose state is whether the driver's act is done there), and the session options its driver declares (agent-definition-payloads.md §Plan-024); on a Windows computer with at least one WSL 2 distribution its installation, command path and status per place, a list of `{place?, installation, commandPath, checkedAt}`, which `Command` draws one row per place, `Windows` and then each distribution read `Ubuntu (WSL)`, and each per-place switch as one `{place?, enabled}` entry per place and each action row as one `{place?, isDone, progress}` entry per place, `progress` settled, running (with whether it can stop) or failed with the provider's reason, in the words the row declares. Each row's `installation` is tagged by `state`: `installed`, `notInstalled` or `indeterminate`, or one of two rows no check runs on and no install offers, `{state: "noBuildForSystem"}`, where the provider's descriptor declares no build for the place's system family and the row reads `Not available on Linux.`, and `{state: "distributionNeedsWsl2"}`, a WSL 1 distribution, where no session runs, whose row reads `Needs WSL 2` with no command field and whose `place` is `{distro}`. The rows run Windows first, then each distribution in WSL's list order with WSL's default first, a WSL 1 distribution among them; `docker-desktop*` and `rancher-desktop*` are never listed. An `installed` row carries `rawVersion`, `parsedVersion?` and `latestVersion?`, the newer build the provider's latest-version marker names, absent while the command resolves to the latest build. `provider.list`'s answer, and the `{settings}` answer of `provider.update`, `provider.probe` and `provider.terminalPlugin.update` and each `provider.subscribe` delivery, carry `stoppedDistributions?: [{distro}]`, the WSL 2 distributions that are stopped, whose rows show their last reading and whose check starts the distribution, absent while none is stopped; each list of places or distributions is unique.), `provider.subscribe` (every provider's section in the provider table's order, then one provider's whole section, `{settings, stoppedDistributions?}`, each time it changes), `provider.update` (one setting per press: a shared row — the command path, named for its place as `{provider, place?, commandPath}`, `{provider, availableForNewSessions}`, `{provider, helpersAtOnce}`, `{provider, autoCompactPercent}` — or one of the setting rows the provider's driver declares, `{provider, rowId, place?, value}`, `place` naming the place of a per-place switch, taken by no other row, and `value` checked against the row's declaration, or one of an action row's two verbs, `{provider, rowId, place?, enabled}` running it in that place (on does the act and off undoes it) and `{provider, rowId, place?, stop: true}` stopping that run: today Claude Code's driver declares `Advisor` and `Output style`, and Codex's `Reach Codex sessions started in a terminal`, a switch per place; refused `provider.notFound` for a provider no registered driver answers, `provider.row.notFound` for a row its driver does not declare, `provider.row.valueInvalid` for a value outside the row's declaration or a place on a row that is not per place, `provider.row.notRunning` for a stop of an action not running in that place, and `provider.row.notStoppable` for a stop of one whose progress says it cannot stop), `provider.probe {provider, place?}` (a place's `Check` or `Check again`: the executable resolved again in that place and its version re-read; for a stopped distribution it starts it, whose hover label reads `Checking starts Arch.`), `provider.protectedPath.list` (each protected path with the source it came from, a `global` one with `place?`, the place its file is in), `provider.install.start {provider, place?}`, `provider.install.subscribe {provider, place?}` (`{state: running | installed | failed {reason, command}}`, each arm carrying `provider`; the install is keyed by provider and place, and the stream's first message is the last outcome in that place) and `provider.install.stop {provider, place?}` (`Install`, or `Install in <place>` on a place's row), `provider.installUpdate.start {provider, place?}` and `provider.installUpdate.subscribe {provider, place?}` (`{state: running | updated {fromVersion, toVersion} | current {version} | notUpdated {version, reason, command} | needsAdministrator {command}}`, each arm carrying `provider`, its first message the last outcome; `Update` on a place's row and its last-result line, the service's own scheduled run reporting on the same stream, with no stop verb; `Update available · <version>` reads the row's `latestVersion`), and `provider.terminalPlugin.update {provider, place?, enabled}` (the terminal plugin's action row in one place, through the provider's own commands — on Claude Code its own two plugin commands to install and its own two to remove, the app writing nothing in Claude Code's settings file; a provider whose driver offers no terminal plugin is refused `provider.capability.unsupported`). A value a declared row is set to in the app is kept in the machine's settings file's `providerSettings`, `{<providerId>: {<rowId>: text | null | [{place?, enabled}]}}`, by the row's shape: a choice's or a text's value, or `null` for none, and a per-place switch's entry for each place it was set in, keyed by place; it is written only by `provider.update` and never into the provider's own settings, and a row or a place left out follows the provider's own value. Claude Code's `Advisor` row is such a row: the advisor default for sessions created later, following Claude Code's own `advisorModel` until a pick here; a session takes it when it is created and keeps its own value from then on. Claude Code's `Dictation language` row, under the line `Also the language Claude Code replies in. Applies to sessions started later.`, and Codex's `Voice` row, under the line `Applies from the next call.`, are keys of the machine's settings file under `voice`, written through `machineSettings.write(change)` and never into the provider's own settings: each follows the provider's own value (Claude Code's `language`, Codex's `realtime.voice`) until a pick here, and a pick is passed to the app's sessions as Claude Code's `language` in `--settings` and as `voice` on each Codex `thread/realtime/start`. The standing rules the provider itself holds on this machine are read and revoked in the provider's own files through `provider.standingRule.list` and `provider.standingRule.revoke`, each rule with its id, its scope, its source file and the place that file is in (`place?`); the daemon derives the id from the rule's place, its file and its text, so one file path in two places names two rules. The session inspector's `Rules` section reads the same files, with the session's own answers, for one session through `approval.rule.list` and `approval.rule.revoke` of approval-payloads.md §Plan-009; the daemon keeps no rule store of its own. The import of the provider's own existing conversations is `session.import.preview`, `session.import.start`, `session.import.subscribe` (its first message each provider's last outcome; each failed conversation `{source, place?, reason}` and each unreadable file `{path, place?}`, `place` the distribution a file is in) and `session.import.stop`. On a Windows computer with a WSL 2 distribution, the terminal Codex service and terminal plugin switches, the standing rules, both imports and `Remove`'s confirm read per place from the same calls, each row naming its place, and each `provider.account.list` entry carries `homePlaces?`, the places where the account has a home, which `Remove`'s confirm reads. Every `place` above that can name Windows (`"windows"` or `{distro}`) is present on a Windows computer with a WSL 2 distribution and absent elsewhere; an import's `place`, which names a distribution alone, is present only on a file in one. Each per-place call is refused by the distribution it names: `provider.distributionNotFound` for one not on this computer and `provider.distributionNeedsWsl2` for a WSL 1 one on `provider.probe`, `provider.install.start`, `provider.install.subscribe`, `provider.install.stop`, `provider.installUpdate.start`, `provider.installUpdate.subscribe`, `provider.terminalPlugin.update` and `provider.update`'s place arms, and `provider.noBuildForSystem` on `provider.install.start` and `provider.installUpdate.start` for a place the provider ships no build for (error-contracts.md §Provider). On a Windows computer `"windows"` names Windows and a `{distro}` is judged by its name whether or not a WSL 2 distribution remains; no `place` names the computer's one place where no WSL 2 distribution is and is refused `provider.place.required` where one is; on macOS and Linux any `place` is refused `provider.place.notOffered`.

Use the program's name without its folder.`
- **Projects** goes through the repository surface of repo-payloads.md §Repo Method-Name Registry, with a project record beside its mount: `project.subscribe` (each row with its `place` on a Windows computer, a folder in a distribution reading `Ubuntu · ~/code/beacon`; a project whose distribution is no longer on this computer carries `isDistributionRemoved: true` and reads `Ubuntu is no longer on this computer.` with `Remove`), `project.rename`, `project.archive`, `project.reactivate`, `project.setup.update`, `project.environment.update` and `repoMount.detach`, which is the row's `Delete` (the sessions and the folder stay), with `native.openInEditor` for opening the project. The machine-wide environment rows and `Clone new repositories into` are the settings file's, the clone folder kept as `{path, place?}`, `place` the WSL 2 distribution a Linux path is in and absent wherever the path's own form says, or `null` until the person sets one; the background service reads the environment rows when it starts a project's process and the clone folder at each clone. `project.clone.folder.read {}` → `{folder, place?, source: setting | lastProject | home}`, `place` the distribution a Linux folder is in, served by the background service, is the one answer to where a clone goes, which this page's row and the session picker's `Clones into` line both draw.
- **Browser** goes through the `browser.*` root of page-host-payloads.md §Page-Host Method Registry — `browser.siteData.list`, `browser.siteData.forget`, `browser.siteData.clear`, `browser.cookie.clear {origin}`, `browser.site.signIn {origin}`, `browser.chromium.read` and `browser.chromium.fetch` — and through `git.host.list`, `git.host.add {host}` and `git.host.remove` of gitflow-payloads.md §Plan-008 for the self-hosted git hosts. Its three switches, `Remember site data`, `Browser tools for sidekicks` and `Sandbox the background browser`, are no verb: they are the machine's settings file's, and the background service reads them each time it launches the headless browser or a provider; the main process reads `Remember site data` at launch to pick the Preview partition. Off, the saved set keeps working while the browser is open and is erased when it closes, as Chrome's "Delete data sites have saved to your device when you close all windows" does (`chrome://settings/content/siteData`, [Technipages](https://www.technipages.com/chrome-clear-cookies-exit/); page-host-payloads.md §Page-Host Method Registry).
- **Keyboard** goes through nothing on the daemon's wire: the chord map is its own file on this install, `userData/keyboard-map.json`, holding only the overridden rows, read and written by the main process through `keyboardMap.read()` and `keyboardMap.write()`, which returns the map as stored. There is no change feed: one renderer drives every window, so one reader holds the map.
- **Appearance** goes through one bridge member rather than the daemon's wire: the theme, the color scheme, the text size and the transcript's width go to the main process through `window.setAppearance`, which writes its appearance record, and come back to every open console window, the one that made the change included, through `window.subscribeAppearance`, with the root token the session screen reads the transcript column's width from, so the two screens can never disagree about it. The screen-reader switch is the settings file's, because the background service reads it when it starts a Terminal pane's shell.
- **Notifications** goes through the machine's settings file — the switches, the kinds, the web address's switch and `Send` kinds, and the email digest's switch, `Send to`, `Mail server`, `Port`, `User name` and `After`, all under `notifications` and written by the background service — through `machineSettings.read()`, `machineSettings.write(change)` and `machineSettings.subscribe()`; the operating system's notification permission, read by the main process through `native.getNotificationPermission()` (on macOS through `notify-status`: `granted` reads as allowed, `denied` as refused, `notDetermined` as not asked yet, `unsupported` as unsupported); and the delivery verbs of attention-payloads.md §Attention Method-Name Registry — `attention.delivery.list`, `attention.delivery.test`, `attention.mailPassword.update`, `attention.mailPassword.delete`, `attention.webAddress.update`, `attention.webAddress.secret.rotate` and `attention.webAddress.delete`. The daemon keeps no notification preference of its own: it reads the settings file each time it writes an entry, and keeps a session's mute on the session.
- **Runtime** goes through the service's own surface, the supervisor in the main process, and the folders the service can reach. **The machine's settings file** is `<home>/.ai-sidekicks/machine-settings.json`, a place both the main process and a background service started from the command line can find without the app. It holds the auto-update preference, the crash-report switch, the editor preference, the values set in the app on the rows each provider's driver declares (`providerSettings`, `{<providerId>: {<rowId>: value | null}}`, empty until one is set while each provider's own values are followed, written by `provider.update` and never by `machine.settings.update`; Claude Code's advisor default for new sessions is its `Advisor` row's value there), the provider and model Generate writes its text with (`commitTextModel`, `{provider, modelId}`, or `null` for `Automatic`, the session's provider and its lowest-priced model), the default checkout, the new-session switch and beside it the last model and effort the person picked (the service writes the pair each time a pick moves it: the lead's model and effort a person's `session.create` carries, and an `agent.config.update` on a session's lead that settles a new model or effort; the line under the switch and a new session both read it here), the two keep-awake switches (`keepAwakeWhileAgentWorks` and `keepAwakeForOtherDevices`), the notification preferences (the switches, the kinds, and the web address's and the email digest's settings other than their secrets), the browser's three switches, the screen-reader switch, the environment rows for every project, the backup switch and the backup folder, the `Branch names` pattern, the folder new clones go into (`null` until the person sets one; a folder naming no complete location is refused at save `request.paramsInvalid`, and one whose place names a WSL distribution not on this computer `repoMount.distributionNotFound`), and voice's settings: the mode (`voice.mode`), the call's voice (`voice.callVoice`) and the dictation language (`voice.dictationLanguage`), each voice choice `null` until the person picks one, while the provider's own value is followed. The folders this machine can reach are not in it: they are the background service's, because only it knows which sessions use a folder. The background service is its one writer, so a change made on another device reaches it as surely as one made at the machine, and a machine running the service with no desktop app can still be changed: the service serves the file through `machine.settings.read`, writes a change through `machine.settings.update {change}`, a change carrying exactly one member, answered with the file as written, and delivers each written change through `machine.settings.subscribe`, the first delivery being the current file. The main process's `machineSettings.read()`, `machineSettings.write(change)` and `machineSettings.subscribe()` carry them; the main process alone may read the file directly, and only before the service first answers, for the values it needs at start (the auto-update preference and the crash-report switch); the renderer never reads the file. The service reads it each time it starts the headless browser, a provider process, a project session, a project's process, a Terminal pane's shell, a clone or a Codex voice call, and keeps no copy; a missing or broken file reads as the defaults there, and the service repairs it. One type, `MachineSettings` in `crates/sidekicks-contracts/src/machine/settings.rs` (its generated TypeScript and validator at `packages/contracts/src/machine/settings.ts`) beside `machine.settings.read`, `machine.settings.update` and `machine.settings.subscribe`, describes the file for both readers. It is written by an ATOMIC RENAME over a schema-checked parse with fail-closed defaults, so a half-written file is never read and a malformed one falls back rather than crashing the screen. A small value may additionally be sealed through the platform's own one-blob encryption. Credential material — a token, a key, the web address's signing secret, the mail password — is never in this file and never in the app's own durable store: it lives in the operating system's keystore, which is why no payload above carries one.

**Settings appends no session event.** Its values are machine-local configuration, so nothing on the screen writes to a session's event log. The one stream the screen reads is the tool-server status and sign-in stream of mcp-governance-payloads.md §Plan-022, `mcp.subscribe`, which it reads and never writes.
