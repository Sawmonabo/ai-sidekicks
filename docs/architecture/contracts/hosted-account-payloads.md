## Account Method-Name Registry

The hosted account's name read and update are exposed as `account.*` methods, beside `account.delete` and `account.export` (Plan-015 CP-015-3). The reciprocal `provides` is recorded on [Plan-005](../../plans/005-local-ipc-and-daemon-control.md). Names follow the [wire-name grammar](./local-ipc-payloads.md#wire-name-grammar), as every namespace's do.

| Method | Procedure type | Request schema | Response schema |
| --- | --- | --- | --- |
| `account.read` | `query` | `EmptyPayload` | `AccountReadResponse` |
| `account.name.update` | `mutation` | `AccountNameUpdateRequest` | `AccountNameUpdateResponse` |

`account.read` returns the account's id and display name and carries no device presence. Which devices are connected is a fact of the device cards on the Devices page in Settings, which read each device's connected state and last-seen time from the live `device.subscribe`, and each machine reports the devices connected to it through its own `presence.read {}` and `presence.subscribe {}`. `account.name.update` is the one mutation. Every method's daemon-side responder is authored (T4.4) per the D-015-3 no-method-without-responder rule. The Rust types live in `crates/sidekicks-contracts`, the generated TypeScript in `packages/contracts/`, per the api-payload-contracts.md §Source-of-Truth Policy.

## WebAuthn Ceremony Procedure Registry

These are **control-plane HTTP procedures, routes served by `axum` on `worker`** (remote-control-payloads.md §Plan-025 — Remote Control Bootstrap), not daemon JSON-RPC methods. Their callers are the web client, the iPhone app and the relay's sign-in page, where the platform offers passkeys: the desktop app carries no WebAuthn, so no passkey is added or used from it. Each is one POST at `/<its wire name>`, the names `sidekicks-contracts` declares in its method table: `webauthn.registrationOptions.issue`, `webauthn.registration.verify`, `webauthn.authenticationOptions.issue`, `webauthn.authentication.verify` and `webauthn.credential.revoke`. Plan-015's I-015-3 daemon-as-gateway rule is untouched. The table holds **the ceremony operations and the credential-lifecycle operation**.

| Operation | Procedure type | Authentication | Request schema | Response schema |
| --- | --- | --- | --- | --- |
| `WebAuthnRegistrationOptionsIssue` | `mutation` | required; **none** for account creation on the sign-in page, which sends `{requestUri, displayName}` in place of a session and receives the creation options with a `transactionId` (below) | `WebAuthnRegistrationOptionsIssueRequest` | `WebAuthnRegistrationOptionsIssueResponse` |
| `WebAuthnRegistrationVerify` | `mutation` | required: it adds a passkey to an account that exists; account creation's registration is verified by the sign-in page's creation arm at `/oauth/authorize` (below) | `WebAuthnRegistrationVerifyRequest` | `WebAuthnRegistrationVerifyResponse` |
| `WebAuthnAuthenticationOptionsIssue` | `mutation` | **none**; for account creation's first passkey on the sign-in page the request is `{requestUri, credentialId}`, and the control plane makes the challenge SHA-256(nonce ‖ SHA-256(PKCE verifier)) from the PKCE challenge on that request's `authorization_requests` row, keeps the nonce there and returns `allowCredentials: [credentialId]`, so the assertion answers only the sign-in whose service holds the verifier (Plan-015 T5.4) | `WebAuthnAuthenticationOptionsIssueRequest` | `WebAuthnAuthenticationOptionsIssueResponse` |
| `WebAuthnAuthenticationVerify` | `mutation` | **none** | `WebAuthnAuthenticationVerifyRequest` | `WebAuthnAuthenticationVerifyResponse` |
| `WebAuthnCredentialRevoke` | `mutation` | required | `WebAuthnCredentialRevokeRequest` | `EmptyPayload` |

Both issue legs are `mutation` rather than `query` because each one **writes** — it records a challenge row, which is the fence the whole ceremony rests on. `WebAuthnRegistrationVerify` and `WebAuthnCredentialRevoke` mount on the control plane's signed-in procedure (Plan-015 T6.6), and `WebAuthnRegistrationOptionsIssue` takes either a session on that procedure or, for account creation, a pending authorization request.

**The authentication pair is deliberately unauthenticated.** Sign-in is pre-authentication by construction: the ceremony is what produces the credential, so a new phone or browser holds nothing to present, and gating it would make the flow unreachable exactly when it is needed ([Spec-016 §Required Behavior](../../specs/016-hosted-account-and-identity.md#required-behavior)). What bounds that caller instead is the **ceremony transaction id** — server-minted on the options reply, quoted back on the verify request, single-use, and expiring on the challenge's own clock, so the caller is bound to one transaction rather than to a session. Throttling is the existing [Spec-019 §Canonical Endpoint Group Registry](../../specs/019-rate-limiting-policy.md#canonical-endpoint-group-registry) `auth.endpoint` row (per source address); **no registry row is minted**, because a per-token budget beside the per-source one would have nothing to bound here, single-use consumption already capping attempts per transaction at exactly one. The registration pair stays authenticated: enrollment binds an authenticator to an existing user, and an unauthenticated enrollment would let anyone bind a key to someone else's account. **Account creation is the one exception.** `Create an account` on the sign-in page makes a new account and adds nothing to one that exists, and a deployment holds one account, so it is offered only while none exists and needs no sign-in: its registration is bound to the authorization request the page was opened with, good once, and limited per source address under the same `auth.endpoint` row as the passkey sign-in. Adding a passkey to an account that exists stays signed in. **`WebAuthnCredentialRevoke` is authenticated for the same reason and one more:** it resolves the credential row under the **caller's own** user id, which there is no way to know without a session. That resolution is also what makes the operation safe to expose — a request naming another user's credential id deletes nothing and returns success, exactly as a request naming an id that does not exist does, so the reply enumerates no one's authenticators. Revocation is a hard `DELETE` rather than a `revoked_at` tombstone: a tombstone would let the verify leg tell _revoked_ from _unknown_, the one distinction every refusal arm of this registry is written to withhold, and it would mint a column to obtain it. Removing the user's **last** credential is permitted — a new device still links through a link from a device already in use, and refusing would keep a compromised authenticator enrolled precisely when the user is trying to retire it.

**What the replies carry, and why the split is where it is.** The registration-**options** reply names the account as `user.name` and `user.displayName`, both the typed `Name`, and `user.id`, its `identity_ref`; it requires a discoverable credential and user verification, asks for no attestation, offers EdDSA, ES256 and RS256, and lists the account's passkeys as `excludeCredentials`. The registration-**verify** reply carries the credential id, its COSE public key (base64url) and COSE algorithm, its AAGUID and the provider name the community AAGUID list gives it, which the device writes into the `account.passkey.added` statement it records (Plan-015 T6.2). The authentication-**options** request may carry a `statementHash`, the hash of a statement a passkey is to sign; the reply carries the `rpId`, the origin, the challenge, `userVerification: 'required'` and the transaction id, and with a `statementHash` the nonce the challenge was made from, SHA-256(nonce ‖ hash), which the passkey signature arm of a statement carries as `challengeNonce` (Plan-015 T6.3, T6.4). The authentication-**verify** reply carries the verdict and a **freshly issued PASETO access/refresh pair**. The token pair rides the verdict because that is the moment the user is known, and it is issued rather than merely unlocked because a new device holds no refresh token to unwrap — a sign-in that only unlocks a stored one is unreachable exactly on the device that needs it. It is sender-constrained per [ADR-010](../../decisions/010-tokens-passkeys-and-the-remote-channel.md) to the DPoP key the caller proves possession of on the verify request; that proof binds a key and establishes no identity, so it does not make this pair a credentialed one and the `Authentication` column above stays **none**.

**Which DPoP proof, and why the signed-in procedure's validator cannot serve this route.** [RFC 9449](https://datatracker.ietf.org/doc/html/rfc9449) defines two proof forms, and the control plane checks both (Plan-015 T6.6). A **token-request** proof ([§5](https://datatracker.ietf.org/doc/html/rfc9449#section-5)) accompanies a request _for_ a token and carries no `ath`, because no access token exists yet. A **resource-request** proof ([§4.3](https://datatracker.ietf.org/doc/html/rfc9449#section-4.3)) accompanies a request that _presents_ one and **requires** `ath`, the hash of that token — which is the form the signed-in procedure validates on every signed-in route, and the form the CP-015-7 daemon credential seam makes. Pointing that validator at `WebAuthnAuthenticationVerify` would reject every legitimate sign-in for a missing `ath`; relaxing the check instead would accept a proof minted for some other request. So the verify leg validates the §5 form with T6.6's §5 validator: `typ` `dpop+jwt`, `htm` and `htu` matching this request's method and URI, `iat` inside the accepted window, a single-use `jti`, an embedded public `jwk` of a permitted algorithm carrying no private parameters, a signature verifying under that `jwk` — and **`ath` required to be absent** rather than merely unchecked, so an oversupplied proof is refused rather than accepted-and-ignored. The issued pair's `cnf.jkt` is the JWK SHA-256 thumbprint of that same key and is computed from the proof, never taken from a separate claim the caller makes; without that the route would hand an unauthenticated caller a bearer pair. A missing, malformed, replayed, or `ath`-bearing proof refuses the whole verification with `auth.dpopMismatch` (401) and `WWW-Authenticate: DPoP algs="ES256", error="invalid_dpop_proof"`, and issues nothing; it is checked before the challenge is read, so the challenge stays and an honest client retries under it (Plan-015 I-015-9 / T6.3).

Refusals are `account.passkey.challengeInvalid` (400) for an unknown, consumed, or expired challenge or transaction id, and `account.passkey.verificationFailed` (400) for every verification arm — bad signature, wrong origin, wrong `rpId`, a missing or foreign user handle, a response whose user-verified flag is absent, regressed counter — so the reply is no oracle for which check failed. A refused DPoP proof answers `auth.dpopMismatch` (401), as on every route that checks one.

## Account Sign-In Method Registry

The service runs every sign-in to the hosted account itself, started by the Devices page's `Sign in` or by `sidekicks account login`, and these are its local daemon methods, beside `account.read` ([Plan-015](../../plans/015-hosted-account-and-identity.md) T5.4). The window and the command line see only the sign-in address and its state: the code, the PKCE verifier, `state`, the DPoP key and the tokens never leave the service. The shapes are in `crates/sidekicks-contracts/src/account.rs`; the cancel and code-submit replies are the sign-in attempt module's, which the provider sign-in broker shares.

- `account.signIn {way: browser | pastedCode, relayAddress?}` returns `{attemptId, authorizationUrl, expiresAt}`, the address `https://<relay>/oauth/authorize?client_id=…&request_uri=…`, which holds no secret; `relayAddress` is sent only while the machine has none, from the Devices page's `Relay address` field.
- `account.signInCode.submit {attemptId, code}` returns `submitted | notFound`; the command line alone calls it, where no browser can reach the machine.
- `account.signInAttempt.cancel {attemptId}` returns `canceled | notFound`.
- `account.signIn.subscribe {}` streams the newest of `signedIn {userId}`, `signingIn {attemptId, way, authorizationUrl, expiresAt, step: inBrowser | finishing}` and `signedOut {cause?: reusedSignIn | machineRemoved, lastAttempt?}`, never a queue of them. A failed attempt carries one reason from the closed set `declined`, `relayUnreachable`, `refused`, `credentialStoreUnavailable`, `passkeyNotVerified` and `machineKeyChanged`; expiry is its own outcome.
- `account.signOut {}` returns `{}`.

`account.signIn` refuses with `account.alreadySignedIn` on a signed-in machine, `account.relay.addressInvalid` for a `relayAddress` that is not a relay address, `account.relay.notConfigured` with no relay address set or given, and `relay.connectionFailed {reason}` when the pushed authorization request cannot reach the relay ([Error Contracts §Account](./error-contracts.md#account)). A new `account.signIn` while one waits replaces it and closes its listener; every window and the command line follow the newest through `account.signIn.subscribe`. `account.signOut` deletes the DPoP key first, closes the relay connection, ends the device-list stream and drops the kept list, reports `signedOut`, and revokes the refresh-token family at `/oauth/revoke` once the relay can be reached. The desktop calls `account.signIn`, `account.signInAttempt.cancel` and `account.signIn.subscribe`; `account.signInCode.submit` and `account.signOut` are the command line's, since the desktop's browser is always on its own machine and no screen carries a sign-out control.

## Hosted Account Route Registry

The control plane's account routes the service's sign-in, its token trade and its sign-out run, the route `sidekicks account delete` runs, and the reply the data export writes as `hosted-account.json`. They are control-plane routes, never daemon methods. The sign-in is the OAuth 2.0 authorization code flow for a native app on a loopback redirect ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)) with PKCE S256 ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)), a pushed authorization request ([RFC 9126](https://www.rfc-editor.org/rfc/rfc9126)), DPoP ([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449)) and the `iss` response parameter ([RFC 9207](https://www.rfc-editor.org/rfc/rfc9207)), under the practice of [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700); sign-out is token revocation ([RFC 7009](https://www.rfc-editor.org/rfc/rfc7009)). The `/oauth/*` routes speak the RFCs' own wire, form bodies and the standard `error` codes (`invalid_grant`, `invalid_request_uri`, `invalid_dpop_proof`, `use_dpop_nonce`), the one exception to the JSON procedure shape. The shapes are in `crates/sidekicks-contracts/src/account.rs` and the unit's refusal codes in `crates/sidekicks-contracts/src/error.rs`, each landing with the task that builds it ([Plan-015](../../plans/015-hosted-account-and-identity.md) T5.4, T5.5).

| Route | Caller | Authentication | Request | Reply |
| --- | --- | --- | --- | --- |
| `/oauth/par` | the service, at the start of a sign-in | a DPoP proof under the attempt's key (RFC 9449 §10.1) | the redirect address (`http://127.0.0.1:<port>/callback`, or the relay's `/signed-in/code` for a pasted code), the PKCE challenge, `state`, the client id, and the machine's id, identity key, channel key, name, platform and version | a single-use `request_uri` that lives as long as the attempt and survives a page reload; writes one `authorization_requests` row (T5.4) |
| `/oauth/authorize` | the browser, at the address `account.signIn` returned | none: the sign-in page | `client_id` and `request_uri` | the sign-in page: `Create an account` while the deployment holds no account, `Sign in with a passkey` once it does, a machine new to the account adding itself in the same step with its `machine.added` signed by that passkey; on approval a redirect to the request's redirect address with `code`, `state` and `iss`, the code good once for 60 seconds; on failure a redirect to `/sign-in-failed?reason=<code>`; an unknown or expired `request_uri` refused with `invalid_request_uri` (T5.4). Account creation's arm takes `{requestUri, registrationTransactionId, attestation, authenticationTransactionId, assertion, browser}` and writes the user record, its first passkey and the approval in one transaction |
| `/oauth/token`, authorization code | the service, once the callback brings the code | a token-request DPoP proof (RFC 9449 §5) under the key that signed the pushed request | the code and the PKCE verifier | a refresh token bound to the proved key (`cnf.jkt`, that key's JWK SHA-256 thumbprint); enrolls the machine, writing its `machines` row under the account and refusing a different key for a machine already enrolled unless a later `machine.added` for that id is on the chain (`machineKeyChanged`); for a new account `firstPasskey`: the passkey's credential id, COSE key and algorithm, AAGUID, provider name and `browser`, with its assertion over SHA-256(nonce ‖ SHA-256(PKCE verifier)) and the nonce, which the service verifies before it records the passkey's `account.passkey.added` right after the `machine.added` that opens the chain; for a machine new to the account its passkey-signed `machine.added`; keeps the request's row, marked with the family it issued, until the code's own expiry passes, so a code presented again is refused with `invalid_grant` and revokes what it issued (T5.4) |
| `/oauth/token`, refresh token | the service, through its credential provider | the refresh token, with a token-request DPoP proof under the same key | the refresh token | a short-lived PASETO v4.public access token and a new refresh token of the same family, the presented one marked spent; a spent refresh token presented again revokes the whole family (T5.4) |
| `/oauth/revoke` | the service's `account.signOut`, once the relay can be reached | the refresh token | the refresh token | revokes its family; the refresh token has no expiry of its own and lasts until sign-out or revocation (T5.4) |
| `/signed-in` | the browser, redirected by the service's listener | none | none | the relay's own page that ends a sign-in in the browser (T5.4) |
| `/signed-in/code` | the browser, for a sign-in whose `way` is `pastedCode` | none | `code`, `state` and `iss` | shows the code for the person to paste into the command line, which hands it to the service with `account.signInCode.submit`; the code is worthless without the PKCE verifier only the service holds (T5.4) |
| `/sign-in-failed` | the browser, redirected by the sign-in page or the service's listener | none | `reason`, one of the closed set of failure reasons | the relay's own page for a sign-in that did not finish, naming its reason (T5.4) |
| `account.delete` | `sidekicks account delete` | the signed-in account | none | revokes every refresh-token family of the account, hard-deletes the account's rows through [Spec-020 §Erasure Paths](../../specs/020-data-retention-export-and-deletion.md#erasure-paths) Path 2, and returns; a second call returns the same result and deletes nothing more; the command line then signs this machine out (T5.5) |
| `account.export` | the data export ([Plan-019](../../plans/019-data-retention-export-and-deletion.md)) | the signed-in account | none | `{account: {userId, createdAt, displayName}, devices}`: the account record and its device list, each device as its card on the Devices page carries it, written as `hosted-account.json`; changes nothing (T5.5) |
