### 3.1 Unit A ground truth — runtime-node authorization (BL-141)

- All five `runtimenode.*` procedures live on `packages/control-plane/src/runtime-nodes/runtime-node-router.factory.ts#createRuntimeNodeRouter`, merged into the host beside the session router. Row resolution per procedure: `attach` upserts `ON CONFLICT (node_id, session_id)`; `heartbeat` upserts presence keyed on `node_id` alone (`packages/control-plane/src/runtime-nodes/heartbeat-service.ts#HeartbeatService`, method `ingest` — single statement, **no attachment lookup at all**, so a never-attached `node_id` can forge presence); `capabilityupdate` row-locks the active attachment `SELECT id, state, client_version, session_id … FOR UPDATE` by `node_id` (verified 2026-07-09 — **`participant_id` is NOT in that column list**, so the ownership predicate must extend the SELECT); `detach` is a conditional `UPDATE … WHERE node_id = $1 AND state IN (active-band)`; `roster` selects `WHERE attachment.session_id = $1` with **no membership filter** (`packages/control-plane/src/runtime-nodes/attach-service.ts#AttachService`, methods `updateCapabilities` / `detach` / `readRoster`).

Only `attach`'s reconnect-immutability WHERE-clause and `readRoster` read it.

This is a **write** IDOR, strictly higher-severity than the roster read. First-attacher node-identity ownership (axis b) is already enforced by the shipped upsert; session membership (axis a) is not enforced anywhere. Both become live at the same Plan-008 R1 event, so both are built now (decision 5).
- **Caller identity**: no auth middleware exists. `SessionRouterContext` is `{ readonly requestId: string }` (`packages/control-plane/src/sessions/trpc.ts#SessionRouterContext`). The constructor-injected `resolveCurrentParticipantId` callback is production-wired to `throw tier5DeferralError("resolveCurrentParticipantId (PASETO auth)")` (`packages/control-plane/src/server/host.ts` bootstrap) — fail-closed until Plan-008-remainder R1 (T-008r-1-5, `paseto-validation-middleware.ts`, 0% shipped). Tests inject deterministic stubs. Today only `attach` calls the resolver; `heartbeat` / `capabilityupdate` / `detach` / `roster` never resolve a caller, so in production they execute **unauthenticated** — threading the resolver into them is itself a hardening.
- The router's own comment block names this exact gap as Tier-5-deferred; `attach` carries the only authorization-shaped check today — a **raw untyped** `TRPCError(UNAUTHORIZED)` self-check (`input.participantId !== current`), outside the `AisWireException` typed-error family.

Plan-008 header Status is already `review`.
- **Spec-003** requires active session membership for attach (§Required Behavior) but records **no caller-ownership precondition** for heartbeat/capabilityupdate/detach/roster (confirmed by full read). Plan-003 is `approved`, Phases 1–5 all shipped (Tier 3; last Phase-3 task is T3.9).

### 3.5 Unit E ground truth — remote cache (BL-122)

- `turbo.json` has **no `remoteCache` block**; zero `TURBO_*` env vars and zero `.turbo` persistence in any workflow — every CI run is cache-cold. Measured medians: push 218s / PR 223s (outliers were runner-queue delays, not cache misses). **This baseline is recorded only in this design + plan today** — PR-E persists it onto BL-122 so a future measurer following the BL finds it (a doc defect the campaign closes). The BL's own >10-min revisit trigger is unfired — this unit is justified as the BL's cheap reversible experiment with the ADR-decided lever, not by pain.
- [ADR-023 §Axis 1](../../decisions/023-v1-ci-cd-and-release-automation.md) commits to a **self-hosted** remote cache (Vercel-hosted explicitly rejected on ADR-022's relicensing-risk grounds), names the specific project `ducktors/turborepo-remote-cache`, and mandates HMAC ≥32 bytes via `TURBO_REMOTE_CACHE_SIGNATURE_KEY`. The **"or equivalent" latitude is [ADR-022](../../decisions/022-v1-toolchain-selection.md)'s toolchain row, not ADR-023 §Axis 1** (verified 2026-07-09 — the phrase "or equivalent" does not appear in ADR-023); swapping the provider therefore rides an ADR-023 §Decision Log entry (added by PR-E) that reconciles the mechanism against the ADR-022 latitude. Three doc defects PR-E fixes: BL-122's References cite §Axis 2 (pre-commit hooks — zero cache text; everything lives in §Axis 1); ADR-023's prose describes the cache as already "deployed in our infrastructure" (decided-but-unimplemented); and BL-122's exit-criterion (a) names auth via `TURBO_TOKEN`, which the ducktors S3-backed model needed but the rharkor GitHub-Actions-cache model does not (it uses only the HMAC `TURBO_REMOTE_CACHE_SIGNATURE_KEY`) — the BL wording is reconciled to the chosen mechanism.
- ducktors fails the $0 constraint (needs paid hosting). **`rharkor/caching-for-turbo`** (v2.5.0, 2026-06-23, active, MIT; maintained successor to the abandoned dtinth action) is the $0 "or equivalent": a localhost proxy inside the CI job backed by GitHub's own Actions cache (10 GB/repo, 7-day eviction) — no external account, no data leaves GitHub, so the Vercel-relicensing rationale does not apply. **Source-verified** (its `src/lib/server/index.ts`): the `x-artifact-tag` header round-trips on PUT/GET, so `signature: true` works end-to-end — a backend that drops the header silently converts every download into a cache miss.
- Threat model for a public repo: fork PRs never see repo secrets → cannot forge the HMAC → a poisoned artifact is a cache miss; fork PRs get read-only cache tokens; GitHub's 2026-06-26 changelog auto-issues read-only cache tokens for untrusted triggers (<https://github.blog/changelog/2026-06-26-read-only-actions-cache-for-untrusted-triggers/>). Defense-in-depth: `--remote-cache-read-only` on all `pull_request` runs so only develop/main pushes populate; SHA-pin the action; `permissions: actions: write` scoped to the job. Turborepo (current 2.10.4, v8 cache API) natively supports `--remote-cache-read-only`.

## 4. Unit designs

### 4.A Unit A — BL-141 caller-ownership authorization (P1)

**Canon** (all verified 2026-07-09): OWASP API1:2023 BOLA — the ownership check must run "in every function that uses an input from the client to access a record" and ship with two-account IDOR tests as a merge gate (<https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/>). OWASP ASVS v5.0 V8: 8.2.2 (object-level restriction), 8.3.1 (enforce at a trusted service layer), 8.3.3 (originating subject's permissions) (<https://github.com/OWASP/ASVS/blob/master/5.0/en/0x17-V8-Authorization.md>). tRPC v11 has no first-class ownership primitive — the docs stop at authentication middleware (<https://trpc.io/docs/server/authorization>). `@cedar-policy/cedar-wasm` carries a long-standing Node-ESM packaging defect (<https://github.com/cedar-policy/cedar/issues/1226>) plus per-call entity-marshalling — the wrong tool for a boolean predicate. 403-vs-404 canon: return a uniform negative for objects the caller cannot see so existence never leaks (Matrix MSC3266's explicit posture, <https://github.com/matrix-org/matrix-spec-proposals/blob/main/proposals/3266-room-summary.md>).

**Design decisions (the new ADR-025 records these with full antithesis/synthesis; this section is the content contract):**

1. **Enforcement point = inside the service transaction**, not a row-loading tRPC middleware. `updateCapabilities` already row-locks `SELECT … FOR UPDATE`; a middleware pre-fetch would double-fetch and open a TOCTOU window between check and mutation. `detach` follows the shipped `acceptInvite` conditional-UPDATE + zero-row-reclassification pattern: ownership joins the WHERE clause, and a zero-row result is re-read to classify the refusal. ASVS 8.3.1's "trusted service layer" is the service method, transaction-interior.

   **Locking discipline (normative — the classify-then-mutate contract).** Transaction-interior is necessary but not sufficient: the rows the verdict is computed from must also be **locked for the remainder of the transaction**, or READ COMMITTED lets a concurrent write land between the classify and the mutation and the stale verdict authorizes it. Two rows are load-bearing — the caller's `session_memberships` row and the target `runtime_node_attachments` row — and they are taken in a **fixed global order**.

   **Canonical lock order (extends the shipped I-002-4 order): `sessions` → `session_memberships` → `runtime_node_attachments`.** Plan-002's I-002-4 (inheriting Plan-001 I-001-1) already pins `sessions` → `session_memberships` for any transaction that mutates a membership while validating its session — `MembershipService.updateMembership` issues `SELECT id FROM sessions WHERE id = $1 FOR UPDATE` before any membership statement, and `packages/control-plane/src/memberships/__tests__/lock-ordering.test.ts` pins the ordering with a logging-proxy `Querier`. This campaign introduces the **first** `session_memberships` reference from the runtime-node domain, so `runtime_node_attachments` is appended as the third and last level. Every runtime-node procedure acquires locks in that order; none of them locks `sessions` (skipping a level in a total order is safe). **Without the fixed order this design deadlocks**: `attach` would lock the membership row and then insert the attachment, while `detach` / `heartbeat` / `capabilityupdate` locked the attachment row and then read membership — an ABBA cycle whenever an attach and a capabilityupdate race on the same `node_id`.

   **Lock mode on `session_memberships` is `FOR SHARE` — not `FOR UPDATE`, and emphatically not `FOR KEY SHARE`.** The row is read, never written, so an exclusive lock would needlessly serialize one participant's concurrent node operations against each other. `FOR SHARE` is nonetheless sufficient to block a concurrent revoke: PostgreSQL's row-level lock conflict matrix (Table 13.3) has `FOR SHARE` conflicting with `FOR NO KEY UPDATE`, which is exactly the mode a plain `UPDATE session_memberships SET state = 'revoked'` acquires (`state` is not a key column), while two concurrent `FOR SHARE` holders do not conflict with each other. `FOR KEY SHARE` would be **insufficient** — it does _not_ conflict with `FOR NO KEY UPDATE`, so it would be a silent no-op guard against the precise race it was added to close (<https://www.postgresql.org/docs/current/explicit-locking.html>, verified 2026-07-10).

   **Per-procedure consequence.** `attach` carries `sessionId` on the wire, so it locks the membership row `FOR SHARE` first and then upserts the attachment — the canonical order, directly. The three `nodeId`-keyed mutators (`detach`, `heartbeat.ingest`, `updateCapabilities`) carry **no** `sessionId` (`RuntimeNodeDetachRequest` is `nodeId` + optional reason; `RuntimeNodeHeartbeatRequest` is `nodeId` + `healthState`), so they cannot lock membership first without first learning the session. They therefore use a **two-phase resolve**:

   1. **Unlocked pre-read** of the active attachment by `node_id`, yielding `(session_id, participant_id)`. It takes no lock, so it cannot invert the order.
   2. **Lock the membership row** `FOR SHARE` for `(session_id, callerParticipantId)` — level 2 — and classify.
   3. **Lock the attachment row** `SELECT … FOR UPDATE` by `node_id` over the active band — level 3 — and **re-verify** that `(session_id, participant_id)` still equal the step-1 snapshot. Any mismatch (a concurrent detach + re-attach, possibly by a different participant or into a different session) yields the procedure's uniform negative, never the stale verdict.

   The step-3 re-verification is what makes the unlocked pre-read safe: the authorization decision is only ever applied to the exact row it was computed from. `detach` additionally carries `participant_id` in its UPDATE `WHERE` (defence in depth beside the lock). `updateCapabilities` keeps its shipped `FOR UPDATE` but it **moves below** the membership lock. `readRoster` is the one exempt caller — a pure read that mutates nothing, so a plain membership `SELECT` (no lock) suffices. Unlocked classify-then-mutate would re-open the exact wrong-owner-retire and presence-forgery windows this decision closes; the `classifyRuntimeNodeCaller` doc comment states the lock order and the re-verification as a **caller contract**, and `lock-ordering.test.ts` is extended with a runtime-node block that pins it the same way it pins I-002-4.

2. **Caller identity flows as an explicit parameter.** The router resolves `deps.resolveCurrentParticipantId(ctx)` (production: still the Tier-5 fail-closed throw; tests: injected stubs) and passes `callerParticipantId` into the service methods. When Plan-008 R1 lands PASETO validation on the context, enforcement becomes production-live with zero further code change — the maximum honest satisfaction of BL-141 exit (d) pre-Tier-5.
3. **Caller classification — one predicate, four verdicts.** A single transaction-interior helper `classifyRuntimeNodeCaller(transaction, callerParticipantId, row)` returns `"owner_active_member"` | `"owner_inactive_member"` | `"member_not_owner"` | `"not_visible"`. It resolves the caller's `active` `session_memberships` row for `row.session_id` (`FOR SHARE`, decision 1) **first**, and that membership result gates every verdict — **including the owner's**.

   **Why the owner check may not short-circuit the membership query.** The attachment row keeps its creator's `participant_id` forever, so an `if (row.participant_id === callerParticipantId) return "owner"` early return classifies a **suspended or revoked** participant as the owner and lets them keep heartbeating, updating capabilities, and detaching nodes in a session they no longer belong to. This is not hypothetical: `MembershipService.updateMembership` ships `suspend` / `revoke` / `reactivate` today (`ACTION_TARGET_STATE`), and `session_memberships.state` admits `pending` / `active` / `suspended` / `revoked`. Ownership of the node identity and active membership of the session are **independent** facts; the guard must require both.

   `member_not_owner` always raises the new typed **`runtimenode.permission_denied`** (403) — node existence is already legitimately disclosed to session members via `roster`, and the sibling domains (invite/membership/presence) all carry a `*.permission_denied` row (R5). `not_visible` raises each procedure's uniform negative (decision 4).

   **`owner_inactive_member` — the detach carve-out, and why the obvious alternative is forbidden.** Denying an inactive-membership owner every procedure would **permanently strand their node**: `idx_node_attachments_active` is `UNIQUE ON runtime_node_attachments(node_id)` **globally** (I-003-5), so while the stale `active` row survives, that `node_id` can never attach to _any_ session — and only its owner could have detached it. The tempting fix — have `MembershipService.updateMembership` retire the participant's attachments in the same transaction — is **explicitly forbidden by the shipped Plan-003 I-003-3**: _"`MembershipUpdate` MUST NOT trigger runtime-node detach as a side effect."_ Writing `runtime_node_attachments.state = 'revoked'` from the membership path would additionally usurp the deliberately-deferred Cedar-gated authority producer (`attach-service.ts`, "the `revoked` trust-revocation producer … NOT in scope here"; ADR-012). So the resolution lives entirely inside the runtime-node domain: **`owner_inactive_member` may `detach`, and may do nothing else.**
   - `detach` — permitted. It is a self-service **release** of the caller's own resource: it writes only the two runtime-node tables, touches no membership row, reduces the revoked participant's footprint rather than extending it, and cannot be reached by a non-owner (a stranger still classifies `not_visible`). It therefore discloses nothing and grants no session authority.
   - `heartbeat` / `capabilityupdate` — refused with the uniform negative (decision 4). These _drive_ a node inside a session, which an inactive member has no standing to do. Their presence row goes stale and the T3.6 sweep demotes it to `offline` on schedule.
   - `attach` / `roster` — refused by the axis-a membership guard before any row is resolved (decisions 5 and 7).

   This yields a clean, daemon-driven recovery protocol with no new authority surface: a revoked participant's daemon attempting to attach elsewhere receives `409 runtimenode.attach_conflict`, calls `detach` on its own `node_id` (permitted), and re-attaches. The pre-existing dead-daemon case — a crashed node whose attachment row outlives it — is **unchanged** by this campaign (it is already recovered by the same-owner reconnect upsert) and is not a regression this design introduces.
4. **`not_visible` maps to each procedure's own no-active-row response — never a distinct one.** This is the oracle-closing rule, and it is the constraint a naive "cross-session → 404" design violates: if `capabilityupdate` answered 409 for a nonexistent node but 404 for a not-visible one, an attacker distinguishes "this `node_id` is actively attached in a session I cannot see" from "this `node_id` does not exist" — and `node_id` is caller-chosen `TEXT` (guessable, unlike the random-UUID `session_id`), so the distinction is exploitable.

   **Scope of the invariant (stated precisely, because the naive phrasing is falsifiable).** The uniformity guarantee binds the four **`nodeId`-keyed** procedures — `detach`, `heartbeat`, `capabilityupdate`, and `roster`'s session-membership negative. It does **NOT** extend to `attach`, and `attach` is not a gap in the guard but a **structural consequence of the shipped I-003-5 global node identity**: `idx_node_attachments_active` is `UNIQUE ON runtime_node_attachments(node_id)` — global, not per-session (verified). So any authenticated participant holding a session of their own can probe a guessed `node_id` by attempting an attach into **their own** session and observing 409 `runtimenode.attach_conflict` (whose shipped description literally reads "already actively attached to another session") versus success. **This is an accepted residual disclosure channel, recorded here so ADR-025 (Type 2) carries its own counterexample rather than a claim its own contract table refutes.** Accepted because: (i) it is pre-existing and inherent — the 409 is the semantic that makes "detach before attaching elsewhere" actionable, and hiding it would require overturning I-003-5's global-uniqueness invariant, a separate one-way decision this campaign does not open; (ii) the leak is one bit ("this `node_id` is attached somewhere"), never the session id, participant, or capabilities; (iii) it costs the attacker an attach attempt per guess, which the Tier-6 rate limit (CP-002-3 sibling) bounds. **Mitigation of record:** `node_id` SHOULD be a high-entropy machine-generated identifier, not a guessable hostname — the entropy, not the response shape, is what makes the channel useless. **Revisit criterion:** if node-id squatting (an attacker attaching a _victim's_ node_id first to deny its attach) is ever observed, or `node_id` becomes user-authored, re-open I-003-5 for per-session uniqueness + server-minted node ids. Per procedure:
   - `detach` — no-active-row is an **idempotent `null` no-op** (retry-safety, explicitly valued in the shipped code); therefore `not_visible` also returns `null`. Detach never emits a not-found. The row is never touched. `owner_inactive_member` **proceeds** (the decision-3 carve-out): the release path stays open so a revoked owner's node is never permanently stranded by the global `node_id` uniqueness of I-003-5.
   - `heartbeat` — no-active-row becomes the new typed `runtimenode.not_found` (404); `not_visible` **and `owner_inactive_member`** return the identical error.
   - `capabilityupdate` — its shipped 409 `runtimenode.capabilityupdate_conflict` is **overloaded today**, covering both "no active attachment" and the I-003-2 `registering→online` guard. Split it: no-active-row → `runtimenode.not_found` (404); the state-conflict guard keeps the 409. `not_visible` **and `owner_inactive_member`** → the same 404. This is a contract change to a shipped code, recorded in Spec-003 + error-contracts; it is required (not cosmetic), because leaving both cases on one 409 is the only alternative that preserves uniformity, and it would cement a 409 that means "not found".
   - `roster` — no visible session (nonexistent **or** caller not an active member) → `runtimenode.not_found` (404), superseding the shipped empty-roster-for-unknown-session posture. A visible session (caller IS an active member) that simply has no attachments still returns `{ nodes: [] }` — the membership predicate gates the 404, and an empty roster inside a visible session is legitimately empty, not hidden.
   - `attach` — a **non-member** of `input.sessionId` (or a nonexistent session) → `runtimenode.not_found` (404), the same uniform negative as `roster` (see decision 5). This supersedes today's behavior where a non-member attach **succeeds** and a nonexistent-session attach surfaces a raw FK violation as `INTERNAL_SERVER_ERROR` (500); both now collapse to the typed 404 before the upsert.

   Two new contracts constants and two new `AisWireException` subclasses (both code+message-only, like the 409 siblings): `RUNTIME_NODE_PERMISSION_DENIED_CODE` / `RuntimeNodePermissionDeniedException` → router maps to `TRPCError({code: "FORBIDDEN", cause})`; `RUNTIME_NODE_NOT_FOUND_CODE` / `RuntimeNodeNotFoundException` → `TRPCError({code: "NOT_FOUND", cause})`. Both project through the shared `errorFormatter`'s single `instanceof AisWireException` match with no formatter change. Every refusal message names the `nodeId` only — never the other session's id.

5. **`attach` has two authorization axes; one is shipped, the other is built now.**
   - **Axis (b) — node-identity ownership (already enforced).** The shipped upsert's `DO UPDATE … WHERE runtime_node_attachments.state <> 'revoked' AND runtime_node_attachments.participant_id = EXCLUDED.participant_id` clause suppresses a different participant's reconnect to zero rows, and the partial-unique `idx_node_attachments_active` index raises `23505` → the typed 409 `runtimenode.attach_conflict` for a cross-session second active attach. ADR-025 _names this rule globally_ — while any active attachment exists for a `node_id`, that attachment's `participant_id` owns the node identity — which is what makes heartbeat's `nodeId`-only predicate well-defined and forecloses cross-session node-identity hijack. PR-A2 adds the missing **regression tests** for both arms; it adds no code to this axis. **Residual disclosure (accepted, decision 4 §Scope):** because `idx_node_attachments_active` is globally unique on `node_id`, the surviving 409 `attach_conflict` tells its caller that a guessed `node_id` is actively attached _somewhere_ — a one-bit channel inherent to I-003-5, bounded by node-id entropy and the Tier-6 rate limit, with a named revisit criterion. The uniform-negative rule therefore binds the four `nodeId`-keyed procedures, not `attach`'s conflict arm; ADR-025's synthesis records this explicitly rather than asserting a blanket non-disclosure the contract table would refute.
   - **Axis (a) — session membership (NEW guard, built now).** `AttachService.attach` gains `callerParticipantId` as its first parameter (uniform with the other four methods, decision 2) and, inside its existing transaction, verifies the caller holds an `active` `session_memberships` row for `input.sessionId` **before** the version-floor read and upsert. Absent → `RuntimeNodeNotFoundException` (the uniform 404, decision 4). This is the maximally hardened satisfaction of Spec-003 §Required Behavior ("a participant with active session membership must be able to attach"), which was **required but unenforced**. The membership row is taken `FOR SHARE` (decision 1): an unlocked read would let a concurrent revoke commit between the check and the upsert, so a stale authorization would create a **durable** attachment row — the one classify-then-mutate window in this design whose artifact outlives the transaction. **I-003-3 is preserved**, because that invariant governs _mutation_ ("`RuntimeNodeAttach` MUST NOT modify session_memberships"), and a `FOR SHARE` row lock modifies nothing. The existing I-003-3 no-mutation test (`attach-service.test.ts` "leaves a co-resident `session_memberships` row byte-for-byte unchanged", verified 2026-07-09) still passes. Two shipped `attach-service.ts` comments **do** become false and are corrected in PR-A2: the header's I-003-3 note claiming attach "acquires NO `session_memberships` lock — it never references, SELECTs FOR UPDATE, or UPDATEs that table", and `detach`'s mirror claiming it "NEVER references … `session_memberships`". Both are restated as **reads for authorization under a shared lock; never mutates**. The router keeps its raw `UNAUTHORIZED` self-check and gains a `RuntimeNodeNotFoundException → NOT_FOUND` catch-arm.
   - **Why uniform 404 and not 403 for a non-member attach:** identical to roster's antithesis (decision 7) — a 403 confirms the session exists; the uniform 404 leaks neither session existence nor the caller's membership, and `session_id` being a random UUID makes the distinction unexploitable anyway. Consistency with roster (both are session-membership-keyed, not node-ownership-keyed) settles it.
6. **Heartbeat hardening (behavior change, spec-recorded):** `ingest` gains a transaction and the decision-1 **two-phase resolve** — unlocked pre-read of the active attachment for `nodeId`, classify under the membership `FOR SHARE`, then re-resolve `FOR UPDATE` and re-verify before the presence upsert. Today a never-attached `node_id` forges a presence row unconditionally; henceforth presence is writable only through an owned active attachment. `not_visible` / `owner_inactive_member` / no-active-row → 404 per decision 4; `member_not_owner` → 403.
7. **Roster read = session-membership predicate** (BL-141 exit (b)): `readRoster` verifies the caller holds an `active` `session_memberships` row for `input.sessionId` before the roster SELECT. **Antithesis considered and rejected:** answering 403 for a non-member of an _existing_ session (mirroring `presence.permission_denied`) would read better but converts `roster` into a session-existence oracle for any leaked or guessed `session_id`; the uniform 404 leaks nothing and costs only a less specific message. **Honesty note for owner ratification:** BL-141 exit (d) says an unauthorized roster read returns "the typed error" — under this design it returns the typed `runtimenode.not_found` (404) rather than a 403, because enumeration authorization and per-row ownership are different questions. The ADR records this reading explicitly; it is a refinement of the BL's pre-analysis phrasing, not a silent narrowing.
8. **Cedar explicitly rejected** for this class, with a named revisit criterion: re-evaluate Cedar-shared-with-approvals vs CASL only if the predicate grows relational/conditional (node→org hierarchies, delegated operators). Records cedar#1226 and the ADR-012 scope rationale.
9. **Plan-008 I-008-4 amendment**: the gated-endpoint list adds the five runtimenode procedures, closing the invariant omission; the runtime-node guard consumes the same R1 middleware output (the resolved principal), not a parallel mechanism.

### 4.B Unit B — BL-133 invite preview + missing invite wire transport (P2)

**Canon** (verified 2026-07-09): Discord `GET /invites/{code}` — non-consuming resolve returning bounded metadata; entropy + rate limiting carry the security (<https://docs.discord.com/developers/resources/invite>). Matrix MSC3266 — bounded field set, no existence divulgence to unauthorized callers (<https://github.com/matrix-org/matrix-spec-proposals/blob/main/proposals/3266-room-summary.md>). OWASP Forgot Password Cheat Sheet — ≥128-bit single-use tokens are safe to read without consuming when rate-limited (<https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html>). RFC 9700 — consumption/redemption is the guarded transition; a read that doesn't redeem doesn't violate single-use (<https://www.rfc-editor.org/info/rfc9700/>). Design rule adopted from all four: separate the read (preview) from the write (consume); the preview path must share no code with the consume path's mutation.

**Design decisions:**

1. **`invite.preview` procedure — decrypt → parse claims → `SELECT state, join_mode FROM session_invites WHERE token_hash = $1` → **row-first, then** claim-expiry — zero UPDATE anywhere on the path.** New `InviteService.previewInvite(request)` reuses the SAME file-scope helpers `acceptInvite` uses — `decryptV4Local(token, activeKey)` (inline), `decodeClaims(payloadBytes)`, `createHash("sha256").update(token).digest("hex")`, `isExpiredClaim(claims.expires_at, now)` — but never the conditional-UPDATE consume step, and never the `SELECT id FROM sessions … FOR UPDATE` lock (that lock exists only for accept's membership write; preview is a pure read, so no transaction is needed). **Error order MUST match accept exactly** (§3.2 correction): decrypt-fail → `invite.not_found`; claims-parse-fail → `invite.not_found`; **row missing → `invite.not_found` (checked BEFORE expiry)**; then expired-claim → `invite.expired`; then the state ladder in accept's own order — **revoked → `invite.revoked`; persisted `expired` → `invite.expired`; accepted → `invite.already_accepted`; pending → the bounded response.** Checking expiry before the row lookup (the earlier draft) would return `invite.expired` for a MAC-valid-but-unknown-hash token while accept returns `invite.not_found` — a posture divergence and a mild oracle. **The persisted-`expired` rung is load-bearing, not dead code**: `session_invites.state`'s CHECK admits `'expired'` and `acceptInvite` (`invite-service.ts`) explicitly reclassifies such a row to `InviteExpiredException` "so the reclassification stays complete." It is latent today (the claim-authoritative check fires first), but a DB-side expiry sweep whose clock runs ahead of the app clock would make a preview that omits the rung answer healthy-pending for an invite accept refuses as expired — precisely the divergence this decision forbids. Non-consumption invariant test: preview N times, then accept still succeeds.
2. **Two-tier errors matching the shipped accept posture** (R5, overruling the web canon's flat-negative): garbage/tampered/unknown-hash → uniform `invite.not_found`; MAC-valid + row-matched → distinct `invite.expired` / `invite.revoked` / `invite.already_accepted`. Spec-002 §Invite Revocation mandates the revoked message on click; tokens are unguessable v4.local envelopes (not enumerable codes); accept already discloses these states without consuming on its failure paths — preview adds zero new information exposure.
3. **Response shape (bounded, forward-compatible, one amendment not two):** `{ joinMode, expiresAt, sessionName: string | null, inviterDisplayName: string | null }`. Raw UUIDs (`session_id`, `inviter_id`) are deliberately **excluded** — the renderer needs display data only, and accept's response already returns `sessionId` to the accepter. The null display fields are documented as Plan-018-fed (`participants.display_name`) and session-name-fed (no owner today — noted, not invented).
4. **Scope is the control-plane tRPC transport (the layer with standalone, testable value) — the daemon-integration leg stays a Tier-5 deferral, honestly.** BL-133's "missing wire transport" is the absent **invite tRPC procedures**: today `InviteService` has no router, so no invite call is reachable over HTTP. PR-B2 builds `invite-router.factory.ts` (mirroring `runtime-node-router.factory.ts`'s already-namespaced `t.router({ invite: { … } })` shape) exposing **create / accept / revoke / preview** over the shipped `InviteService`, with a catch-arm per procedure mapping each typed exception to the tRPC error code whose native HTTP status matches [error-contracts.md §Invite](../../architecture/contracts/error-contracts.md) — and it is **merged into the host** (`host.ts` `t.mergeRouters(session, runtimeNode, invite)`, `ControlPlaneDeps` gains `InviteRouterDeps`, the production default-export wires a placeholder throwing service beside the attach/heartbeat placeholders) so it is reachable and HTTP-tested through `buildControlPlaneFetchHandler` exactly as the runtime-node router is. This makes Plan-002 Phase 4's T4.1 premise ("the invite tRPC procedures") true. The per-exception tRPC-code map (the two 410 codes are carried per decision 8):

Guarded by the map, so runtime-node / session / resource codes (absent from the map) get a byte-identical envelope — `host-runtime-node.test.ts`'s 409 assertions stay green.

This mirrors tRPC's own canonical `responseMeta` idiom (`clientErrors[0].data?.httpStatus`), the map being the shared source so envelope and transport can never diverge.
   - **error-contracts.md §Error Response Shape mechanism note (discoverability — the map must not orphan).** [error-contracts.md](../../architecture/contracts/error-contracts.md) gains a short note under §Error Response Shape documenting the delivery path for registry codes whose pinned HTTP status has no native tRPC code: `AIS_WIRE_HTTP_STATUS_OVERRIDES` (`@ai-sidekicks/contracts` `error.ts`) is the single registration point — the `errorFormatter` stamps `data.httpStatus`, the host `responseMeta` lifts `response.status`, and unmapped codes ride their carrier tRPC code's native status. ### 4.E Unit E — BL-122 remote-cache experiment (P3, honest framing)

Per §3.5: `turbo.json` gains `"remoteCache": { "signature": true }`; both `ci.yml` test jobs gain the SHA-pinned `rharkor/caching-for-turbo` step before the turbo run, `--remote-cache-read-only` appended on `pull_request` events, and job-scoped `permissions: actions: write`.

**`TURBO_REMOTE_CACHE_SIGNATURE_KEY` is declared at `env:` on the JOB, not on the caching-action step.** GitHub Actions step-level `env:` is scoped to that single step and does not propagate to later steps, so a key placed on the `rharkor/caching-for-turbo` step would be invisible to the subsequent `pnpm turbo run …` steps — which is where it is actually consumed: Turborepo signs each uploaded artifact "using the value of the environment variable `TURBO_REMOTE_CACHE_SIGNATURE_KEY`" at `turbo run` time (<https://turborepo.dev/docs/reference/configuration>, verified 2026-07-10). Job-level `env:` (or repeating it on every turbo invocation) is therefore required for the signed-cache path to operate at all. The secret itself is an **executor step, not an owner hand-off**: `openssl rand -hex 32 | gh secret set TURBO_REMOTE_CACHE_SIGNATURE_KEY` with the owner-authenticated `gh` CLI at PR-E time; only a 403/permission refusal downgrades it to an owner ACTIONABLE surfaced in the PR body; forks never see the secret either way.

**Honest framing of the signature (upstream's own words).** Turborepo documents `remoteCache.signature` as an **artifact-integrity** mechanism — it "is not a security feature. Rather, it verifies the integrity of a cached artifact" (same source). So the HMAC is _not_ the control that defends against fork cache-poisoning; the controls that do are GitHub withholding secrets from fork-originated workflows, the read-only `GITHUB_TOKEN` on `pull_request`, and `--remote-cache-read-only` on PR events. PR-E's body states it that way rather than crediting the HMAC with a property upstream disclaims. ADR-023 §Axis 1's "HMAC ≥32 bytes" requirement is still satisfied; only the rationale is corrected. Doc ride-alongs: BL-122 References §Axis 2 → §Axis 1 citation fix; ADR-023 §Decision Log entry recording the provider adjudication (rharkor as the $0 "or equivalent" — GitHub-native, so the Vercel-relicensing rationale doesn't apply; ducktors fails the $0 constraint) and correcting the ADR's "deployed" overstatement to decided-now-implemented. **Measurement window**: ≥5 subsequent PRs against the recorded 218–223s cache-cold baseline; <30% reduction → revert the wiring and record the negative result on the BL (the experiment's own exit criterion (c) is the arbiter either way).

## 8. Risks

- **Status-flip blast radius (A/B)**: while Plan-003/Plan-002 sit in `review` between amendment and promotion PRs, any _other_ lane-1 dispatch against them halts at preflight Gate 7. Both plans' phases are shipped; exposure is the campaign's own code PRs, which sequence after promotion by design. Mitigation: promotion micro-PRs are two-line diffs prepared in advance; merge same-day.
- **Census merge races (A1 vs B1)**: both doc PRs touch the README census + status tables. Serialize their merges; the second rebases its census lines (re-derive by counting).
- **Four shipped-behavior changes in Unit A**: attach's session-membership precondition becomes **enforced** (a non-member attach that silently succeeded now refuses with a typed 404, and a nonexistent-session attach that raised a raw FK-500 now returns the same 404); hardened refusals replace silent-accept postures (heartbeat presence forgery; roster empty-for-unknown-session); and `capabilityupdate`'s overloaded 409 splits into 404 (no visible active row) + 409 (state conflict). All four are recorded as explicit Spec-003 + error-contracts amendments before the code lands; the IDOR suite pins the new contract; existing tests asserting the old postures are updated in the same PR — a reviewer seeing changed assertions should read them as the ratified contract change, not regression masking (called out in the PR body). The attach-membership enforcement is a genuine **security-posture change** (closes a write-IDOR: a non-member could create an attachment row in another session), so it is the highest-value of the four; its only regression surface is a caller that depended on cross-session attach succeeding — none exists (attach has never had a legitimate cross-session caller), and the `client-sdk` OTHER_SESSION roster-isolation test is the one enumerated fixture that must seed membership (§4.A code deliverables). The `capabilityupdate` split has the widest wire-code blast radius (a shipped code changes for one arm); it is required rather than cosmetic, because the alternative that preserves oracle-uniformity would cement a 409 meaning "not found" (§4.A decision 4).
- **Decision-8 cross-cutting edits (shared `trpc.ts` + Plan-008 `host.ts`)**: migrating the invite exceptions and adding the 410 override touches the shared error formatter and the control-plane host — files this campaign does not own. Every edit is additive and **map-guarded** (`AIS_WIRE_HTTP_STATUS_OVERRIDES` contains only the two invite codes), so the shipped runtime-node/session envelope and transport statuses are byte-identical and `host-runtime-node.test.ts` stays green without modification. The residual risk is a future code adding a map entry without the matching error-contracts row (or vice versa); the `error.test.ts` completeness assertion (every key is a real code, every value matches the §Invite status column) fails closed on that drift. The tRPC-code-vs-httpStatus divergence for expired/revoked (carrier `CONFLICT`, status 410) is intentional and documented — consumers key on `aisError.code`, which is exact.
- **Oracle regression risk**: the uniform-negative rule (§4.A decision 4) is per-procedure and easy to break later by "improving" one procedure's error message. The IDOR suite asserts the not-visible response is byte-identical to the no-active-row response for each procedure, so a future divergence fails the suite rather than silently reopening the oracle.
- **Coverage instrumentation overhead**: control-plane's PGlite suites carry raised timeouts; coverage runs only in the advisory job, never the required path. If the advisory job flakes on timeouts, raise its per-job timeout — never loosen the required gate.
- **Remote-cache experiment failure**: <30% reduction → revert PR-E's wiring per BL-122 exit (c); the BL records the negative result. The wiring is a single action step + one turbo.json key — designed to revert cleanly.
- **Fork-PR cache poisoning**: mitigated by construction (secret withheld from forks + read-only tokens + HMAC signature verification + `--remote-cache-read-only` on PRs); documented in the PR body for the Codex reviewer.
