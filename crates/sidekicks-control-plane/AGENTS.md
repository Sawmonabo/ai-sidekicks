# crates/sidekicks-control-plane — Worker rules

Applies to every change under `crates/sidekicks-control-plane/`, the Cloudflare Worker and the Compose relay, on top of the [root `AGENTS.md`](../../AGENTS.md) and [`crates/AGENTS.md`](../AGENTS.md), which this file never restates.

## The Worker

- **The Worker (`sidekicks-control-plane`):** `std::time::SystemTime::now` and `Instant::now` compile on `wasm32-unknown-unknown` but panic when called, so the Worker reads time through `time` with its `wasm-bindgen` feature, and a dependency that reads the std clock is refused. Every await on a JS promise or `worker::Delay` inside an axum handler is wrapped in `worker::send::SendFuture`. `worker-build` runs in its default release profile (a `--dev` build panics in `worker::Delay` from compat date 2026-08-04), and the npm manifest stays out of the crate root, which `worker-build` refuses when it lists dependencies. The relay's Durable Objects, the account object and each machine's forwarding object, are declared with `worker`'s `#[durable_object]`, and the account object keeps the account's data in its SQLite storage; the macro needs `wasm-bindgen` as a direct dependency of the crate.
- **The Worker's config** is `wrangler.jsonc`. Production deploys only through `--env production`; `workers_dev` and `preview_urls` are `false` in every environment; every binding, var and secret is declared again under `env.production`, since none is inherited. Credentials stay in the package's gitignored `.env`, never in `wrangler.jsonc`, and `wrangler dev` never loads `.env` into the Worker: the development gate's keys sit in a `.dev.vars` made from `.dev.vars.example` and are listed in the top-level `secrets.required`, and every production secret in `env.production.secrets.required`. A test deploy on the free plan needs no yes and is deleted with `wrangler delete` once its check is read; a production deploy, a production secret or anything that could put a charge on the account waits for the user's yes.
