# crates/sidekicks-platforms — operating-system rules

Binding for every change under `crates/sidekicks-platforms/`, where all operating-system code lives, on top of the [root `AGENTS.md`](../../AGENTS.md) and [`crates/AGENTS.md`](../AGENTS.md), which this file never restates.

## Spawning a child and the shell mode

- On Linux a `Command` child arms `PR_SET_PDEATHSIG` (SIGHUP) in its own `pre_exec`, then compares `getppid()` with the daemon's pid and exits on a mismatch. A shell starts through the daemon's `shell` mode (`sidekicks-daemon shell <daemon-pid>`), which the platforms crate's terminal start (`sidekicks_platforms::start_terminal`) spawns with no fork, on macOS and Linux through its own `posix_spawn` with `POSIX_SPAWN_SETSID`, the terminal's follower on the three standard streams and the confirmation's end the one descriptor besides (Linux closes every other with `posix_spawn_file_actions_addclosefrom_np`), and on Windows through `alacritty_terminal`'s ConPTY (the PTY writes the shell's program, arguments, folder, environment and any text the shell parses itself, and the fallback shell's launch, into the mode's start confirmation, so the mode's command line carries none of the person's input and the shell's own line is the only one bounded): the PTY spawns the mode, not the shell, in a stable folder, and the mode starts the shell in the folder the confirmation names. On Linux it arms the signal and re-checks `getppid()`; on macOS it does the `getppid()` check. On both it then waits for the daemon's confirmation that it started this process (`sidekicks_platforms::ShellStartConfirmation`: a socket pair whose end the mode inherits, on which the daemon writes the id of the process it started and which it keeps open for the shell's life) and refuses to start anything unless that id is its own and the daemon wrote it (on macOS also unless the daemon is its own responsible process, on Linux unless the end is one of a pair the daemon made); then, before the folder change and any exec, it takes its terminal as its controlling one with `ioctl(0, TIOCSCTTY, 0)`, since macOS runs a spawn's file actions before its new session, so no spawn can hand it one, and enters the folder with `nix::unistd::chdir`; the shell inherits the folder across the exec. The command wrapper's inner form, which `start_inner_terminal` spawns the same way, takes its terminal with the same call. On Windows the mode starts the shell with the program exactly as the start confirmation carries it, the arguments through `args`, `Command::current_dir` set to the folder and the raw tail written last through `CommandExt::raw_arg`, which makes the shell's own line the whole bound, and keeps its own folder for its whole wait. On macOS and Linux it sets SIGPIPE back to its default, as std does for a `Command` child, then execs the program's resolved absolute path: on Linux with `execve`, on macOS with `posix_spawn` and `POSIX_SPAWN_SETEXEC` plus the attribute that disclaims the daemon's responsibility, so the shell is its own responsible process; never `execvp`, `posix_spawnp` or `Command::exec`: std's exec path calls `execvp`, and glibc's and macOS's `execvp`, like macOS's `posix_spawnp`, run a file the kernel refuses (`ENOEXEC`) through `/bin/sh`. Where the exec fails, the mode writes one line above the prompt naming the shell it could not start, the reason in plain words and the shell it runs instead, then execs the platform's default shell the same way. The calls are `nix` 0.31.3's (features `process`, `event`, `signal`, `fs`) in `sidekicks-platforms`, except the spawns, the `shell` mode's exec on macOS, a lasting or session child's start on macOS and the terminal's start on macOS and Linux, which are `libc`'s: `nix`'s `spawn` module has no `POSIX_SPAWN_SETEXEC`, no `POSIX_SPAWN_SETSID` or `POSIX_SPAWN_CLOEXEC_DEFAULT` flag and no folder change (`posix_spawn_file_actions_addchdir`, found by name at run time, its `_np` name the fallback, since the plain name is macOS 26's first and the `_np` one deprecated there).

## The socket path

- **A socket path** is checked with `std::os::unix::net::SocketAddr::from_pathname` (Windows: `uds_windows`' own check) before binding: std refuses an over-long path with `InvalidInput` before any system call, so no probe waits for `EINVAL`; one fresh test checks a path at the limit and one past it.
