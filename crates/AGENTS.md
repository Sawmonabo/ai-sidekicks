# crates/ — Rust rules

Binding for every change under `crates/`, on top of the [root `AGENTS.md`](../AGENTS.md), which this file never restates. It adds only what Rust needs. [`sidekicks-contracts`](sidekicks-contracts/AGENTS.md), [`sidekicks-platforms`](sidekicks-platforms/AGENTS.md), [`sidekicks-cli`](sidekicks-cli/AGENTS.md) and [`sidekicks-control-plane`](sidekicks-control-plane/AGENTS.md) each add an `AGENTS.md` of their own for the rules that bind that crate alone; read it with this one when you touch that crate.

## Layout and names

- **Every Rust crate lives in `crates/`, one level deep, its folder named exactly as its crate:** `crates/sidekicks-contracts/` holds the package `sidekicks-contracts`. Package names are kebab-case with the `sidekicks-` prefix; code reads them with underscores (`use sidekicks_contracts::…`). A program takes its crate's name (`sidekicks-daemon`); only two set `[[bin]] name`: the command line (`sidekicks`) and the macOS wake helper (`sidekicks-wake-helper`, a root program linking only `objc2-io-kit`'s `pwr_mgt` and talking only over its socket), which `sidekicks-platforms` builds.
- **What each crate holds:** `sidekicks-std` (primitives with no daemon concept: locks, waits, settling, retries, file writes and the scheduler), `sidekicks-store` (where the daemon keeps its data: the database, the event log, the credential store and the data folder), `sidekicks-ipc` (the local socket's server side without its handlers: the method registry and dispatch, the caller check, the stream subscriptions and their frame batching, the presence register of the devices connected, and the errors), `sidekicks-workspace` (workspaces, repositories, git and worktrees, the file watch and the run setup gates), `sidekicks-policy` (the rules: shell commands and their read bound, destructive git, the Cedar authorizer, the workflow start rule and the ask rules), `sidekicks-workflow` (workflow definitions and versions, runs, secrets and the agent tools that write them, the table of node kinds and the engine's ports), `sidekicks-provider` (the driver interface, the run ports, the code every provider shares and each provider's driver), `sidekicks-agent` (saved agent definitions, skills, plugins and the shared tool server's provider-independent part: its tool contracts, discovery, registration and listener), `sidekicks-mcp` (the MCP client a session's tool servers are reached through, its tool calls and command receipts, each server's status folded from its bindings and session legs, and the MCP governance tables), `sidekicks-shell` (the terminal service: a session's shells, their control lease, output flow and the orphans a crash leaves), `sidekicks-session` (sessions, the run engine, the transcript, questions, interventions, the queue store, the session directory, the agent tree, the session's agents and its spend and token limits), `sidekicks-approval` (the permission gate, the asks the daemon answers itself, the approval seam of the callback tools, the check a workflow start passes, the approval service, its store and projection), `sidekicks-queue` (the run queue: sending, ordering, admitting, delivering and recording runs per session), `sidekicks-artifact` (artifacts and plans: publishing, ingesting and storing what a run produces, and each plan's record), `sidekicks-browser` (the one browser runtime the agents' browser tools and the preview screen share, with the preview's serving pieces: the page store, the relay to main and dev-server discovery), `sidekicks-recovery` (repair of what the daemon keeps after a stop: the start's checks, the settling of runs a stop left live, damaged history, the gate that holds writes until the daemon can trust its state, projection rebuilds, the recovery status and the database file's repair), `sidekicks-daemon` (the daemon's program over those crates: the start, the IPC handlers, orchestration, remote, observability and highlighting; its one program also runs the helper modes the daemon starts), `sidekicks-cli` (the `sidekicks` command line; it reaches the daemon only through `sidekicks-client`), `sidekicks-contracts` (the wire's source: serde types, garde checks, the method table and the frame codec), `sidekicks-client` (the typed daemon client for the CLI and, through `sidekicks-client-addon`, the desktop), `sidekicks-client-addon` (the client's Node-API addon, which the desktop loads in a helper process), `sidekicks-control-plane` (the gated Cloudflare Worker on `worker` and `axum`, whose account object keeps the account's data in its SQLite storage beside one forwarding object per machine, and the Compose relay's native program, which keeps it in a SQLite file), `sidekicks-search` (the session search index on Tantivy, which only the daemon's crates link, and the one fuzzy matcher), `sidekicks-terminal` (the PTY, run inside the daemon), `sidekicks-compression` (lz4 packing of a reply's text chunks, built to WebAssembly, which the desktop's markdown worker compiles and the page runs), `sidekicks-platforms` (all operating-system code behind one interface; it also builds the macOS wake helper).
- **A crate's TypeScript face** lives in its `packages/<name>` workspace package under its `@ai-sidekicks/*` name, imported by topic path (`@ai-sidekicks/contracts/preview/methods`), with no root `index.ts`.
- **Files and module folders are `snake_case`.** A module with children is `name.rs` beside `name/`, never `name/mod.rs`, tests included (a crate's integration binary is `tests/it/main.rs`, its helpers `tests/it/helpers.rs`). That parent file sits beside its folder, not inside it, so the [root's rule](../AGENTS.md#folders-by-topic) against a file named like its folder does not touch it (`provider.rs` beside `provider/` is right; `provider/provider.rs` is a defect). A file inside its namesake folder (`mcp/mcp.rs`) is still a defect.
- **Names follow Rust's API guidelines:** types, traits and enum variants `UpperCamelCase`; functions, methods, locals and modules `snake_case`; constants and statics `SCREAMING_SNAKE_CASE`. An acronym is one word (`JsonRpcMessage`, `Uuid`). No `get_` on a getter (`fn state(&self)`). Conversions: `as_` (cheap view), `to_` (copy), `into_` (consumes). Booleans read as questions (`is_held`, `can_take`). A trait takes no prefix. An identifier keeps its full name inside its module (`DaemonProcess` in `daemon`).
- **Operating-system code lives only in `sidekicks-platforms`,** in its `macos`, `linux` and `windows` modules and the `posix` module the first two share, behind one interface the core calls. No other crate holds a `cfg` on the operating system (`#[cfg(target_os = …)]`, `cfg!(windows)`, `#[cfg(unix)]`) or calls a platform API; where another crate needs a platform's behavior, `sidekicks-platforms` supplies it as a function or a value (`SHOULD_MEMORY_MAP_READS`, which the search index reads). How a system spells, joins and compares a path is `sidekicks_platforms::PathRules`, whose `PathRules::NATIVE` the platforms crate sets for the running system, with `resolve_path` and `resolve_path_against` beside it, so no caller checks which system it runs on. The direct path's operating-system pieces are its: the network watch's address set, the default-gateway read for the router's port mapping, and the Windows firewall rule's install and removal; `str0m`, `mdns-sd`, `crab_nat` and `igd-next` are cross-platform, so the daemon's `remote` module calls them without a `cfg`.
- **Provider code stays inside its own driver folder, `sidekicks_provider::driver::claude` and `sidekicks_provider::driver::codex`,** which `crates/sidekicks-provider/src/driver.rs` declares privately beside the one table of providers, `PROVIDER_REGISTRATIONS`: one entry per provider, its descriptor, its driver's build and the end of its recorded services that the erase runs with no daemon, in the order the registry keeps, an id that repeats another or breaks the provider id pattern failing the build. A provider is its own folder and one entry in that table, so the compiler keeps every module outside `sidekicks_provider::driver` from naming a provider. That one provider's module never reaches the other's, that no shared module under `sidekicks_provider::driver` reaches either, and that drivers are built from the table only by the daemon's start and, in test builds, by the provider crate's test registry, are held in review.
- **A provider is an open id (the root's rule); in Rust, also:** shared code reaches a provider only through the driver interface and never branches on which model it is, what a screen names (the provider, its models, its settings) comes from the driver's descriptor and its live reads, and a provider added is one driver module and its entry in the table.
- **Every stored row id and event id is minted by the one `mint_uuid_v7`:** `clippy.toml`'s `disallowed-methods` lists `uuid::Uuid::new_v4`, `uuid::Uuid::new_v7` and `uuid::Uuid::now_v7`; `mint_uuid_v7` and each ephemeral token no row or event stores (a scratch file name, a subscription id, a terminal handle) carry `#[expect(clippy::disallowed_methods, reason = "…")]` at the call.
- **The read-side projectors** (`sidekicks_workspace::projector`, `sidekicks_workspace::git::worktree::projector`) and the provider crate's `hand_over::brief::projection` take their inputs as arguments and read no clock, store, file or process; review holds it.

## Toolchain and manifests

- `rust-toolchain.toml` pins one exact stable release (`1.99.0`, profile `minimal`, `rustfmt` and `clippy`, target `wasm32-unknown-unknown`); `rust-version` names the same one, and CI installs what the file names. Moving to a new stable is its own PR, which fixes every lint it brings.
- A crate built to WebAssembly (`sidekicks-compression`, the matcher's build of `sidekicks-search`, the workflow checks' build of `sidekicks-contracts`) builds with the root `[profile.wasm-release]` (`panic = "abort"`, LTO, `strip`); the workflow checks' build strips debug info only, since the wasm-bindgen tool reads the link's `target_features` section.
- The root `Cargo.toml` holds the shared facts: `resolver = "3"`; edition 2024, `rust-version`, license and `publish = false` in `[workspace.package]`; every dependency version once in `[workspace.dependencies]`, internal crates by path. A crate writes `x.workspace = true` and `[lints] workspace = true`. Nothing sets lints through `rustflags`.
- A dependency entry longer than 100 columns, in any manifest, is written as dotted keys, each key on its own line: in a crate, `x.workspace = true` with `x.features = [...]`; in the root `Cargo.toml`, `x.version = "…"` with `x.features = [...]`, and `x.default-features = false` where used. tombi wraps a long inline table across lines, a TOML 1.1 form, and Turbo reads manifests as TOML 1.0 and refuses it.
- **Turbo drives Cargo** through its Cargo support (`turbo` pinned exact): the root `Cargo.toml` names the workspace `sidekicks-crates` in `[workspace.metadata]`, no crate has a `package.json`, and no folder is both a crate and a pnpm package. A pnpm package that ships a crate's WebAssembly build depends on that crate's `build`, which the root `turbo.json` sets to `"command": null` so it carries only the crate's hash.
- **Dependencies between crates:** `sidekicks-contracts` depends on no workspace crate. The daemon's crates stack in one order, bottom to top: `sidekicks-std`, `sidekicks-store`, `sidekicks-ipc`, `sidekicks-workspace`, `sidekicks-policy`, `sidekicks-workflow`, `sidekicks-provider`, `sidekicks-agent`, `sidekicks-mcp`, `sidekicks-shell`, `sidekicks-session`, `sidekicks-approval`, `sidekicks-queue`, `sidekicks-artifact`, `sidekicks-browser`, `sidekicks-recovery`, then the program, `sidekicks-daemon`, at the top; each depends only on crates below it among these, and any of them may also take the foundation crates `sidekicks-contracts`, `sidekicks-platforms`, `sidekicks-search` and `sidekicks-terminal`, of which `sidekicks-terminal` sits over `sidekicks-std`. `sidekicks-std` holds only what names no daemon, session, run or provider concept and could have lived in std. The CLI links only `sidekicks-client`, `sidekicks-contracts`, `sidekicks-platforms` and `sidekicks-std`, and the client only the last three, never `sidekicks-daemon` or `sidekicks-control-plane`; no other program links a daemon crate until a real second user appears. The daemon's program takes `sidekicks-client` only for the helper modes that dial the daemon, and only that way: the client never links the daemon. Only `sidekicks-client-addon` binds the client to Node-API. A crate uses another only through its `[dependencies]`, by path. Two parts of the order no compiler checks: a crate's schema part declares foreign keys only into its own part or a lower crate's, so a reference to a higher crate's row is kept by value with no `REFERENCES`; and `sidekicks-store`'s SQL names no table of a crate above store.

## Commands

`cargo fmt --all`, `cargo clippy --workspace --all-targets --all-features`, `cargo nextest run --workspace`, `cargo test --workspace --doc`, `cargo doc --workspace --no-deps`, `cargo shear`, `cargo deny check advisories bans sources`, `typos`, `tombi format`. CI sets `CARGO_BUILD_WARNINGS=deny`, so any lint warning fails it, rustdoc's included, and runs each Cargo command with `--keep-going` so every crate reports. `turbo run build lint test` drives Cargo beside the pnpm packages; the root `turbo.json` names `CARGO_BUILD_WARNINGS` in `globalEnv`, which Turbo otherwise withholds.

## Format and lints

- rustfmt with `style_edition = "2024"` and its defaults: 100 columns, 4-space indent. Comments wrap at 100 by hand. Imports sit in three groups (std, other crates, this crate), a blank line between.
- Clippy `pedantic` is on, with `must_use_candidate`, `missing_errors_doc`, `missing_panics_doc`, `too_many_lines` and `similar_names` allowed. Also on: `unwrap_used`, `panic`, `exit`, `todo`, `unimplemented`, `dbg_macro`, `print_stdout`, `print_stderr`, `allow_attributes`, `allow_attributes_without_reason`, `let_underscore_must_use`, `map_err_ignore`, `unused_result_ok`, `wildcard_enum_match_arm`, `mod_module_files`, `undocumented_unsafe_blocks`, `redundant_clone`, and `missing_docs_in_private_items` limited to `pub(crate)` items. Off on purpose: `expect_used` and `indexing_slicing` (they force branches for proven invariants) and `module_name_repetitions` (it flags `DaemonProcess`).
- rustc: `unsafe_code` denied; `missing_docs`, `unreachable_pub`, `dead_code_pub_in_binary`, `unused_lifetimes`, `redundant_lifetimes` and `unit_bindings` warn. `dead_code_pub_in_binary` is set in each program's `main.rs` (`#![warn(…)]`), never in the workspace table: rustc builds every library's unit tests as a program, where it would report each `pub` item the tests leave unused.
- **A suppression is `#[expect(lint, reason = "…")]`, never `#[allow]`;** the reason says why in plain words. One that no longer fires fails the build, so it is removed.

## Code

- **Errors:** a library crate defines its errors with `thiserror`; only `main` and the command line's top level use `anyhow`, with context. No `unwrap`, `panic!`, `todo!`, `unimplemented!` or `process::exit` in product code, except the `shell` mode's Windows middle process's one `process::exit`, which passes on the shell's 32-bit exit code that `ExitCode` cannot hold; `expect("why this holds")` states a proven invariant. `let _ =` never drops a `Result`, and `map_err(|_| …)` never drops a cause.
- **Stopping a child:** a child stopped with SIGTERM gets process-wrap's `ChildWrapper::signal(libc::SIGTERM)` on Unix, which reaches the child's own pid, never tokio's `kill()` or `start_kill()` (SIGKILL); a provider child is never wrapped in `ProcessGroup`, whose `signal` reaches the whole group and whose `wait` waits for the child, then reaps the group's members that are the daemon's own children, waiting for any still running; a process the child started is never the daemon's child, so the wait reaps none of those. On Windows the stop ends the child's whole tree, as `taskkill /T /F` does: the child runs in process-wrap's `JobObject`, whose `start_kill()` is `TerminateJobObject`.
- **A child's exit crosses the wire as a signal name or a code:** an end by signal is read with `ExitStatusExt::signal()` and crosses the wire as its name, `nix::sys::signal::Signal::try_from(n)` then `.as_str()` (`SIGKILL`); a number the enum does not list (a Linux real-time signal) crosses as `SIGRTMIN+<n>`, the form signal(7) uses, which `sidekicks-platforms` names, never as exit code 0. A Windows exit code is `i64::from(code as u32)`, so a crash reads 3221225477. A missing code with no signal reads 0. On Windows a child the daemon itself ended (`start_kill`) crosses the wire with the name of the signal the stop asked for (`SIGTERM` or `SIGKILL`), and any other end with its exit code. A test checks that every signal the platform defines has a name. The exit is composed only after both `wait()` and the stderr reader's end. stderr is decoded across chunks: bytes are held until a whole UTF-8 sequence and decoded lossily once. The failure tail keeps the last 32,768 code points, the unit of the cap it fills, moved forward to the next grapheme boundary; the Codex proxy's stderr tail keeps its last 1,000 the same way. A shell's title takes whole graphemes up to 256 code points, and is cut at 256 code points only when one grapheme is longer than that. Every program a mode starts goes through `std` or `tokio` `Command` (`CommandExt::exec` where it replaces the process), never a raw `execvp`, so the child's SIGPIPE is back at its default, which std restores; the `shell` mode execs the program itself (below) and sets SIGPIPE back to its default itself first, a lasting child's and a session child's macOS start set it through `POSIX_SPAWN_SETSIGDEF`, and the terminal's start on macOS and Linux sets it there too, with the six more signals a shell expects at their default (SIGCHLD, SIGHUP, SIGINT, SIGQUIT, SIGTERM and SIGALRM). A test runs `yes | head -1` through the command wrapper and in a shell, and reads no `Broken pipe` from either.
- **Spawning a child:** every child the daemon starts is spawned from one long-lived spawner thread, `sidekicks_platforms::Spawner` (made at start with `std::thread::Builder` and fed by a channel; the daemon makes it once and hands a cloneable handle to every crate that starts a child, and `run(job)` runs a closure there and answers through a oneshot), never from a tokio worker or `spawn_blocking`: Linux sends the parent-death signal when the thread that forked the child ends, and tokio's blocking threads end after 10 s idle. On macOS a child starts through `posix_spawn`, std's path for a command with no `pre_exec` and a program given by its absolute path, because a `fork` in a process running threads runs libSystem's fork handlers in the child, which abort it when another thread was inside a one-time initialization; a child that must be ended as one leads a process group of its own (`process_group(0)`, process-wrap's `ProcessGroup`); the login shell's environment capture, an interactive shell, which opens the terminal and stops itself while its group is not the terminal's foreground one, leads a session of its own as a session child (`sidekicks_platforms::start_session_child`), and so does a lasting child: on macOS both start through the platforms crate's own `posix_spawn` with `POSIX_SPAWN_SETSID`, and on Linux a session child makes its session with `setsid` in its own `pre_exec`. A shell starts through the daemon's `shell` mode (`sidekicks-daemon shell <daemon-pid>`), which the platforms crate's terminal start (`sidekicks_platforms::start_terminal`) spawns with no fork, on macOS and Linux through its own `posix_spawn` with `POSIX_SPAWN_SETSID`, the terminal's follower on the three standard streams and the confirmation's end the one descriptor besides (Linux closes every other with `posix_spawn_file_actions_addclosefrom_np`), and on Windows through `alacritty_terminal`'s ConPTY (the PTY writes the shell's program, arguments, folder, environment and any text the shell parses itself, and the fallback shell's launch, into the mode's start confirmation, so the mode's command line carries none of the person's input and the shell's own line is the only one bounded): the PTY spawns the mode, not the shell, in a stable folder, and the mode starts the shell in the folder the confirmation names. On Linux it arms the signal and re-checks `getppid()`; on macOS it does the `getppid()` check. On both it then waits for the daemon's confirmation that it started this process (`sidekicks_platforms::ShellStartConfirmation`: a socket pair whose end the mode inherits, on which the daemon writes the id of the process it started and which it keeps open for the shell's life) and refuses to start anything unless that id is its own and the daemon wrote it (on macOS also unless the daemon is its own responsible process, on Linux unless the end is one of a pair the daemon made); then, before the folder change and any exec, it takes its terminal as its controlling one with `ioctl(0, TIOCSCTTY, 0)`, since macOS runs a spawn's file actions before its new session, so no spawn can hand it one, and enters the folder with `nix::unistd::chdir`; the shell inherits the folder across the exec. The command wrapper's inner form, which `start_inner_terminal` spawns the same way, takes its terminal with the same call. On Windows the mode starts the shell with the program exactly as the start confirmation carries it, the arguments through `args`, `Command::current_dir` set to the folder and the raw tail written last through `CommandExt::raw_arg`, which makes the shell's own line the whole bound, and keeps its own folder for its whole wait. On macOS and Linux it sets SIGPIPE back to its default, as std does for a `Command` child, then execs the program's resolved absolute path: on Linux with `execve`, on macOS with `posix_spawn` and `POSIX_SPAWN_SETEXEC` plus the attribute that disclaims the daemon's responsibility, so the shell is its own responsible process; never `execvp`, `posix_spawnp` or `Command::exec`: std's exec path calls `execvp`, and glibc's and macOS's `execvp`, like macOS's `posix_spawnp`, run a file the kernel refuses (`ENOEXEC`) through `/bin/sh`. Where the exec fails, the mode writes one line above the prompt naming the shell it could not start, the reason in plain words and the shell it runs instead, then execs the platform's default shell the same way. The calls are `nix` 0.31.3's (features `process`, `event`, `signal`, `fs`) in `sidekicks-platforms`, except the spawns, the `shell` mode's exec on macOS, a lasting or session child's start on macOS and the terminal's start on macOS and Linux, which are `libc`'s: `nix`'s `spawn` module has no `POSIX_SPAWN_SETEXEC`, no `POSIX_SPAWN_SETSID` or `POSIX_SPAWN_CLOEXEC_DEFAULT` flag and no folder change (`posix_spawn_file_actions_addchdir`, found by name at run time, its `_np` name the fallback, since the plain name is macOS 26's first and the `_np` one deprecated there). A Linux test opens a shell, leaves the blocking pool idle for 15 s and asserts the shell is alive.
- **The run folder** resolves in `sidekicks-platforms`, for the daemon and the CLI, exactly as desktop main's TypeScript resolver (`resolveDaemonRunFolder`) does. On Linux it is `$XDG_RUNTIME_DIR/ai-sidekicks` when `XDG_RUNTIME_DIR` is set and non-empty, else `<home>/.ai-sidekicks/run`; on macOS it is always `<home>/.ai-sidekicks/run`, since no system cleans a runtime folder there. A file the daemon writes in it is made with mode `0o600` on macOS and `0o1600` on Linux (`RUN_FOLDER_FILE_MODE`), whose sticky bit tells a session manager that cleans the runtime folder to keep it. A folder has one trailing `/` removed when it is longer than one character. On Windows it is `%LOCALAPPDATA%\ai-sidekicks\run`, the local application data folder read through the known-folder call (`FOLDERID_LocalAppData`), holding `daemon.token`, and the socket is the named pipe `\\.\pipe\ai-sidekicks-<user SID>`. Desktop main's supervisor keeps calling the TypeScript resolver, because main keeps the file tokens. One case table runs against both: `XDG_RUNTIME_DIR` set, set with a trailing `/`, set empty, and unset with a home folder ending in `/`, and on Windows a local application data folder with and without a trailing `\`. Before the daemon binds, and before `sidekicks-client` writes its first byte, `sidekicks-platforms` checks that the folder is private. On macOS and Linux `std::fs::symlink_metadata` (never `metadata`, which follows a link) reports a folder (`is_dir()`), owned by the user (`MetadataExt::uid`), with no group or other bits (`mode() & 0o077 == 0`). On Windows the check opens the folder with `FILE_FLAG_OPEN_REPARSE_POINT`, so a link is not followed, refuses a reparse point or a file, and reads the owner and the access list with `GetSecurityInfo`: the owner is the user, SYSTEM or the Administrators (who own what an elevated process makes); allowing entries name only those three; inherit-only and deny entries are skipped; any other entry type is refused, and so is a missing access list.
- **The home folder** is `std::env::home_dir()` (`HOME`, else the password entry; on Windows `USERPROFILE`, else `GetUserProfileDirectoryW`), the same home the desktop's main process reads, never `dirs::home_dir`, which asks Windows' known folders. It differs from main's only on an empty `HOME` (main answers `""`) and a `USERPROFILE` under three characters (main throws).
- **Resolving a path:** every symlink-resolving call goes through `sidekicks-platforms`' one helper, `real_path`, never `std::fs::canonicalize` alone: on Windows it strips the verbatim prefix (`\\?\UNC\` becomes `\\`, any other `\\?\` goes, and a result with neither prefix is an error; `std::fs` re-adds the verbatim prefix itself for a path of 248 UTF-16 units or more, so the stripped form still opens), so a path shown, stored or handed to git or a provider carries no `\\?\` prefix and still opens, a network share and a path over 260 characters included; never `dunce`, which keeps the prefix on both. It returns the not-found error; only the deny-path caller keeps an absent path's expanded form; every other caller keeps its own answer to a missing path (a refusal, or no result). Containment is compared by components (`Path::starts_with`), never by string prefix. Environment names are compared under the host's rules (Windows: `env_remove` is case-insensitive). Windows tests: a deny path carries no `\\?\`, and a drive path, a `\\server\share` path, a name ending in a dot and a path over 260 characters each round-trip.
- **A path on the wire** is `Path::to_string_lossy()`, which writes one U+FFFD per invalid sequence, as the desktop renders it: the bytes `F0 80 80 41 E2 82` read as U+FFFD, U+FFFD, U+FFFD, `A`, U+FFFD on both, a test case.
- **Signatures:** an Ed25519 signature is checked with `ed25519-dalek`'s `VerifyingKey::verify_strict`, and an imported key is refused when `is_weak()`; never `verify`, which accepts a small-order forgery. `pasetors` keeps its own `ed25519-compact`. A secret is compared with `subtle`'s `ConstantTimeEq`.
- **Credentials:** on macOS and Windows every value goes through `keyring-core` with the platform's store, from `sidekicks-platforms`; on Linux the store is systemd's credential service, reached through the platforms crate's own client (`io.systemd.Credentials.Encrypt` and `Decrypt` with `scope: "user"` and no other option, one JSON message ended by a NUL byte each way over `/run/systemd/io.systemd.Credentials`, one connection per call, every buffer holding a value wiped on drop), which seals each item into the daemon's `secrets.json`, and the plain file where that service is absent, refuses at the first start, or binds PCR 7. An entry is built through the store, never a process default: on Windows `store.build(service, user, Some(&HashMap::from([("persistence", "local")])))`, since `windows-native-keyring-store` writes Enterprise persistence, a roaming one, unless told; a test reads `entry.get_attributes()?["persistence"]` back as `Local`. A refused call's `cause` is read from the store error's source, never its variant or message: on macOS `security_framework::base::Error::code()` (a direct `security-framework` 3.7.0 dependency, so the downcast type is the store's), -25308 `locked`, -25291 or -25294 `unavailable`; on Windows, whose store keeps its error type private, every store error reads `unavailable`; a store call in `spawn_blocking` that does not answer within `tokio::time::timeout` reads `locked`, its blocking thread held until the prompt ends. On Linux nothing can be unlocked, so every refusal, a seal that does not answer in time included, reads `unavailable`, and the daemon never branches on the credential service's error name but for the three its first start reads. A store error never carries a stored value: `keyring_core::Error::BadEncoding` and `BadDataFormat` hold the item's bytes, so the platforms error drops them. A test on macOS and Windows feeds each error and checks the cause.
- **Types:** an ID is a newtype. A closed set is an `enum`, the discriminated union the [closed-sets rule](../apps/desktop/AGENTS.md#closed-sets-of-values) asks for; a `match` names every variant. No `#[non_exhaustive]` and no `#[deprecated]` on workspace types.
- **Async and logs:** tokio's multi-thread runtime with two workers (`worker_threads(2)`); blocking work goes through `spawn_blocking`, except a child's spawn, which goes to the spawner thread (above); `tokio::sync` and `tokio::process` in async code. Logs go through `tracing` with typed fields; no `println!` outside the command line's output writer. An error is logged as `error = &error as &(dyn Error + 'static)`, which the fmt layer prints with its causes (`error.sources=[…]`), never `%error` or `?error`, which print only its top message or its debug form. The daemon's service log is one `tracing-subscriber` fmt layer writing to standard error and to flexi_logger's `FileLogWriter`: `logs/service-<local time begun, to the millisecond>.log`, a new file at each start, each day and at 16 MiB, flexi_logger's own cleanup off. The service's scheduler deletes a file last written longer ago than `Keep diagnostic logs for`, never the one being written. tokio's clock stops while the machine sleeps, so a wall-clock instant is armed on the operating system's wall-clock timer through `sidekicks-platforms`, which fires at that time across sleep and any clock change, and re-armed from its durable row at start; sleep, wake and clock changes reach the scheduler as the operating system's events, and nothing looks at the clock on a timer.
- **Network changes:** the daemon learns of them only from `sidekicks-platforms`' network watch, which reports one change after 1 s quiet and only when usable addresses or the network path changed, loopback and link-local aside: macOS `NWPathMonitor` through `nw_path_monitor_*` on `block2`, never SCNetworkReachability; Linux and Windows through `netwatcher` on tokio. It never polls and never claims the network works. The same watch reports the usable address set, which is the direct path's host candidates, so the addresses have one source; a change pings the relay connection and asks every direct peer to restart ICE.
- **Keyed locks:** a lock that can be held across a nested call is `KeyedLock` (`sidekicks_std::keyed_lock`), never a bare mutex. Taking the lock returns a hold, and code the holder calls takes that hold as an argument instead of locking again, so the type system rules out a nested call waiting on its own holder, and a spawned task carries the hold it was given; no task-local carries it.
- **Visibility:** private by default, `pub(crate)` when the crate shares an item, `pub` only for the crate's API.
- **Doc comments, beyond the root's rule:** every `pub` and `pub(crate)` item carries one, with its error contract in the sentence, and every crate root has a `//!` doc.
- **Unsafe:** a crate that binds a C interface allows it at its root with a reason, and every `unsafe` block carries a `// SAFETY:` comment. Where a library's trait or an export form demands `unsafe` in another crate, that one item carries `#[expect(unsafe_code, reason = "…")]`, and an `unsafe impl` or block in it its `// SAFETY:` comment: `sidekicks-provider`'s `ProvidesStaticType` impl that hands `starlark`'s builtins their context, and the matcher's WebAssembly exports in `sidekicks-search`.

## One crate's rules

### `sidekicks-daemon`

- **The daemon's stop and crash:** the stop request comes from `sidekicks-platforms` behind its one interface: on macOS and Linux SIGTERM and Ctrl-C; on Windows Ctrl-C and `WM_ENDSESSION` at the daemon's hidden top-level window, which answers `WM_QUERYENDSESSION` `TRUE` at once and returns from `WM_ENDSESSION` within about 4 s, inside the 5 s Windows gives a program with no visible window. `main` takes it before the start as the stop request every start step watches, and no code outside the platforms crate names a signal API. `main` also installs a `std::panic::set_hook` that writes the panic, its location and its backtrace to the service log and into the crash reports folder, flushes the file writer and calls `std::process::abort()`, so a panic in any task ends the service and the supervisor restarts it. The hook is the one place product code ends the process (`abort` is not `exit`); it keeps the workspace's `panic = "unwind"`, which the client addon needs. In the WSL server (`sidekicks-daemon wsl`) the end of the `h2` channel (`Connection::accept` returning `None` once standard input ends) or a failed write to standard output (`EPIPE`; Rust ignores `SIGPIPE`, so the write returns the error) is the same stop request SIGTERM raises, so a killed `wsl.exe`, which sends no signal, ends the server within a second.

### `sidekicks-client-addon`

- **Node-API:** the client's addon, `sidekicks-client-addon`, builds with `panic = "unwind"` and puts `#[napi(catch_unwind)]` on every sync export, so a panic becomes a JavaScript error; its reader task fails every pending call and ends every stream when it stops.

## Tests

- **Tests sit at the critical minimum.** A behavior is proven by the fewest tests that fail when it breaks, and only where a failure is expensive (root `AGENTS.md` rule 5): the critical path, data loss, a leaked secret, a resource budget, a boundary another surface reads. No test of shape, wiring, a derive, a getter, generated code or coverage; tests that prove one behavior are one test.
- Unit tests sit in `#[cfg(test)] mod tests` at the bottom of their file (`name/tests.rs` past the 900-line limit). A crate's integration tests are one binary, `tests/it/main.rs`, declaring a module per behavior (`tests/it/provider_turns.rs`), with shared helpers in `tests/it/helpers.rs`: Cargo links each file directly under `tests/` as its own binary, so one binary keeps link time and disk down. Data a test reads is in `tests/fixtures/`.
- **Reuse.** Plain `#[test]` by default; `rstest` (`#[case]`, `#[fixture]`) where several cases share one body or one fixture, so near-duplicate tests become one case table. A helper another crate's tests need sits in the module that owns its type under `#[cfg(any(test, feature = "test-support"))]`, and the consuming crate turns `test-support` on in `[dev-dependencies]` only, which the feature resolver keeps out of the normal build. A helper both of the daemon's test binaries need sits there too.
- Property tests (`proptest`) guard parsers, wire decoding and crypto, regression files committed, at 100 cases on a PR and 10,000 in the nightly run (`PROPTEST_CASES`). Fuzz targets live in `crates/sidekicks-artifact/fuzz/` (the package `sidekicks-artifact-fuzz`), a workspace member left out of `default-members` whose dependencies come from the workspace table, so it shares the root lock and the artifact crate's feature lists; `libfuzzer-sys` is declared under `cfg(fuzzing)`, which only `cargo fuzz` sets, so a workspace check, lint or test builds none of libFuzzer and the target there is an empty program. Targets are run by `cargo fuzz run <target> -s none` on the pinned stable toolchain: `-s none` passes no `-Z` flag and keeps libFuzzer's coverage guidance, giving up only AddressSanitizer, where unsafe code is denied. Crashers are minimized into `fuzz/corpus/<target>/regressions/`, and each target's whole corpus, crashers included, is replayed by one nextest test in the normal run. Snapshot tests (`insta`) only where the snapshot is the behavior. No retries in the runner. `cargo mutants --in-diff` proves a failure-path test.
- The endurance tests are the daemon's `tests/endurance.rs` binary, which only nextest's `endurance` profile runs; every other test run, mutation and coverage included, goes through nextest, whose default filter keeps it out. Both filters are written in the change that adds the binary, since nextest refuses a filter naming a binary no workspace target has.

## Memory

Memory is why the service is in Rust; each of these holds by default:

- The global allocator is mimalloc on macOS and Linux and the system allocator on Windows, supplied by `sidekicks-platforms` as `GlobalAllocator` and `GLOBAL_ALLOCATOR` and declared once, in the daemon's `main.rs`, so the command line and the client's Node addon keep the system allocator, with the call that hands freed memory back (`mi_collect(true)`, a no-op on Windows until the allocator switch), which the daemon makes once its work has been quiet for 10 seconds, from a one-shot timer that new work resets. On Linux the daemon turns transparent huge pages off for itself at start and clears that in each child before exec.
- JSON is read with `from_slice` into typed structs, except a message a server receives, which takes the shape check ([`sidekicks-contracts/AGENTS.md`](sidekicks-contracts/AGENTS.md#wire-contracts-sidekicks-contracts)); a payload the service only relays and never hashes stays a `&RawValue` (`serde_json`'s `raw_value` feature).
- Each SQLite connection sets its `cache_size`, the connections are counted, and `prepare_cached` is sized to the statement set.
- `reqwest` clients cap `pool_max_idle_per_host`.
- File watching goes through the one file watch every owner shares, `sidekicks-workspace`'s `file_watch`, and its one bounded handler. Where the backend watches a tree (FSEvents, `ReadDirectoryChangesW`) it watches the root; inotify watches one folder at a time, so on Linux only the folders an ignore walk keeps are watched.
- The search index writes with one indexing thread and the smallest budget that keeps up.
- No queue drops a log line silently: a non-blocking writer either blocks or reports each dropped line.

## Unused code and spelling

- An item kept for a consumer a document names carries `#[expect(dead_code, reason = "<the consumer, in plain words>")]`; a file or dependency kept the same way takes one entry in the crate's `[package.metadata.cargo-shear]` with a plain comment, and so does a dependency used only through a path the tool does not follow (the fuzz crate's `file-format`), its comment naming that path. An item a document claims that another crate can reach is `pub` with its `///` and carries no marker: rustc reports nothing on a `pub` item another crate can reach, so an unused `pub` item is found by reading (`rg` for its name across `crates/` at review), and the search of the documents before any deletion (root `AGENTS.md` rule 13) is its record.
- `typos` checks code with `locale = "en-us"`; documents are not checked. A spelling a provider sends goes in its allow list.
